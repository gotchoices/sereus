# Formation and redemption read each row once

## Measured and traced

- `message-cost-accounting` baseline, B's `formStrand` phase: at the responder A, `queryFormationInvite` 5 reads, revoked stamps 5, `countFormationUsage` 4.
- Traced: the responder reads the FormationInvite row 5 times, the FormationUsage count 4 times, the Strand row 3 times (recorder, responder, connection gate). Only the count taken inside the write lock decides; the others are early refusals.
- Cadre invitation: the redemption reads `CadreInvite` 3 times and the use count twice; after the write, the reply's peer list re-reads rows the refresh just read. Owner grants have the same twins.
- Joiner: `addStrand`'s `rememberForeign` spends 2 control reads and a store list confirming the record `formStrand` wrote moments before; the `JoinedStrand` control row is written later in a reconcile pass, under a second owner approval.
- Minor: on a single-machine party, `createOpenInvitation` reads its own `CadrePeer` record and lists its own addresses twice.

`Revocation` and `CadrePeer` repeats are handled by `control-membership-rows-cached-until-changed`. This ticket is the per-flow rows that cache does not cover.

## Design

- **One early read, one decisive read.** Each flow reads the credential row once up front (to refuse cheaply and to carry the row through the flow), and takes the use count once, inside the write transaction, where it decides. Carry the row as a value between the gate, the recorder and the responder instead of each re-reading it.
- **The reply reuses the rows the flow already holds.**
- **`formStrand` hands its join record to `addStrand`** (or `addStrand` trusts the store it just wrote) instead of re-reading. Write the `JoinedStrand` row in `formStrand`'s own control transaction if the approval model allows one approval for both; otherwise say why it must stay separate.

## Edge cases & interactions

- **A race on the last use.** Two redemptions of a one-use invitation: the in-transaction count must still decide, and the loser must get today's rejection code (`Formation rejection codes`). The early read only refuses what is already used up. Verify by the existing formation-rejection specs.
- **A revoked or cancelled credential between the early read and the write.** The transaction's CHECKs refuse it; the carried row must not be used to skip them. Verify by inspection.
- **The connection gate** runs before the stream handler and has its own reason to read; if it cannot share the handler's read (different call, different time), leave it and note why.

None new; the formation and cadre-invite specs cover outcomes. `control-founding-consult-budget.spec.ts`'s per-request membership reads may move; re-pin if so.
