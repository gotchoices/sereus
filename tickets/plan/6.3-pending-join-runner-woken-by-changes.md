# The pending-join runner wakes on a join request

## Measured

In #50's scenario the runner costs 24 of the 155 reads per minute (both nodes): every 30 s on each owner machine, owner keys (2 reads), revoked `JoinRequest` stamps (1) and the three-table pending-join select (3). The join tables are usually never written, so on a two-machine cadre each read of them consults the sibling (a never-written collection has no local answer).

## Design

- Subscribe through `control-and-strand-table-change-subscription`'s seam to the tables `queryPendingJoins` reads (find them at the query; `JoinRequest`, `JoinSuccess`, `JoinFailure`) and to `OwnerKey` (the runner needs an owner signer).
- Run once at start. After a run that finds nothing pending, schedule no timer; a change wakes it.
- While something is pending, keep today's retry cadence for it (the work is waiting on another machine or the network, not on a table change).
- Keep a backstop, default 10 minutes, for a cadre larger than 16 machines.

## Edge cases & interactions

- **A pending join finished on a sibling owner machine.** The sibling's commit to the join tables wakes this runner, which then sees nothing pending. This is the path `backlog/debt-pending-join-finished-on-another-owner-machine-unscenarioed` wants a scenario for; that ticket's scenario, if written, now also covers this wake. Do not add a second scenario here.
- **The owner signer is wired after start.** The runner must run once when the signer arrives, as today.
- **Non-owner machines** do not run it, as today.

## Tests

None new. Existing runner specs cover the join logic; the scheduling contract is the seam's.
