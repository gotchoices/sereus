# The control reconcile pass runs on change and reads each table once

## Measured and traced

- **Share of idle reads.** In #50's scenario the pass makes 72 of the 155 reads per minute (both nodes): the membership gate refresh (`Revocation`, `OwnerKey`, revoked stamps and `CadrePeer`), the reap (`Revocation`), the sibling list and per-sibling address records (`CadrePeer`), and the strand peer-address refresh (`CadrePeer`). Every member-list or peer-record read also reads `Revocation` first.
- **Repeated reads.** Tracing one pass, the same rows are read about 11 times: the refresh already holds the whole `Revocation` table, then `queryCadrePeers` reads it again (`cadre-node.ts` ~2781 vs `control-database.ts` ~1755); refresh, reap, `listMembers` and each `queryPeerRecord` each read again. While any `CadrePeer` row was admitted by invitation, or any owner key seated by a grant, each refresh also re-verifies that chain (+2 reads each).
- **Network cost on a two-machine cadre.** Each held block read after its 10 s read-repair window starts a background `/sync` to the sibling. The pass's 15 s period is longer than the window, so every pass checks every block it reads with the sibling.
- **The pass sets the pace of joins.** After a QR claim, A reconnects to the restarted B only on its next pass, and B publishes its own record only on its next pass. (The `Revocation` ledger marker, filed on the owner's first connected pass, is superseded by `control-collections-created-at-cadre-founding`.)

## Design

1. **Read once per pass.** With `control-membership-rows-cached-until-changed` in place, the repeated `Revocation` and `CadrePeer` reads become reads of the in-memory view. What remains here is structural: take the rows once at the start of a pass and hand them to the gate refresh, the reap, the sibling enumeration and the strand peer-address refresh, so one pass sees one consistent set. Target: at most one table read each per pass when nothing changed, zero when the view is current.
2. **Remember verified chains.** An invitation or grant chain that verified for a given row stays verified until that row or the chain's rows change. Cache the verdict keyed by the row's signature and the chain rows' signatures, and drop it on a change to `CadreInvite`, `OwnerGrant` or `Revocation`.
3. **Run on change.** Subscribe through `control-and-strand-table-change-subscription`'s seam to `CadrePeer`, `OwnerKey`, `Revocation`, and the invitation and grant tables the chain checks read. Also run on `connection:open` / `connection:close` of a control connection (a sibling that dropped is redialled on the existing backoff, not on the next 15 s tick).
4. **Backstop.** Keep the timer as a backstop, default 2 minutes. It still bounds gate staleness for a change that arrives without a storage event, and for a cadre larger than 16 machines.
5. **The ledger marker is not this ticket's.** `control-collections-created-at-cadre-founding` gives `Revocation` its collection at genesis and `revocation-ledger-marker-removed` deletes the marker's filing step from the pass; do not move it. If this ticket lands first, leave the step where it is.

## Settled choices

- **Gate staleness is now bounded by delivery, not by the timer.** A replicated `CadrePeer` or `Revocation` change re-materializes the per-stream gate's authorized set when it lands, which is sooner than today's 15 s. A removed machine is hung up on as soon as its revocation is stored here. Say so in docs/architecture.md where the 15 s bound is stated today.
- **No merge of the refresh and the reap.** Keep them separate functions fed the same rows; small functions over one big pass.

## Edge cases & interactions

- **A pass already running when a change lands.** The seam's single-flight rule queues exactly one follow-up. Passes stay single-flight, as today.
- **A dial to an unreachable sibling takes the full `controlDialBudget()`.** Change-driven passes must not start a second dial to the same sibling. Keep the per-sibling backoff state across passes. Verify by inspection.
- **A burst of membership writes** (an owner adding several machines) collapses into one pass. The seam's debounce covers it.
- **The write lock.** `notifyMembershipChanged` runs its listener with the write lock held. The pass must not be started inline from there. The seam schedules; verify by inspection.
- **Rows read at the start of a pass go stale during it.** Acceptable: a change during the pass schedules the next pass. Note it at the shared read.
- **Owner anchor sync** (`syncOwnerAnchor`: `OwnerKey`, `Revocation`) rides the same pass and the same rows.
- **The membership view's maximum age follows the backstop.** `control-membership-rows-cached-until-changed` sets `MEMBERSHIP_VIEW_MAX_AGE_MS = DEFAULT_CONTROL_COHORT_RECONCILE_MS`, so lengthening the timer to 2 minutes also lets the view serve rows up to 2 minutes old when a change arrives with no storage event. One of those cases is a machine that was offline when a sibling committed (for example a removal): it picks the change up only when it next reads the block. When this ticket subscribes to control `connection:open`, also invalidate the membership view there, so a reconnecting machine re-reads at once instead of waiting out the maximum age.
- **Tests that drive the pass by time.** Specs that advance the 15 s timer need to drive it by change or by an explicit call instead. Update them; do not keep the old interval for their sake.
