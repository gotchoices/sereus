# Membership rows are read once and kept until they change

## Measured (message-cost-accounting baseline, 2026-10-19)

- Owner admits a member: `cadrecontrol/Revocation` read 24 times in a 362 ms phase.
- Strand formation, responder side: 14 times in 293 ms; joiner's first insert: 17 times.
- Idle: 24 times a minute per node.

Every member-list or peer-record read reads `Revocation` first (to exclude retired rows), and every flow calls several of them. On a single-machine party each read is local work. On a two-machine cadre each held-block read past the 10 s read-repair window starts a background `sync` to the sibling, so repeated reads are repeated network requests.

## Design

- A small in-memory view inside `ControlDatabase` of `Revocation`, `CadrePeer`, `OwnerKey` and the revoked-stamp rows those queries read. Each query that today reads these tables reads the view; the view loads the table on first use after an invalidation.
- Invalidate a table's view from a `watchTables` subscription (from `control-and-strand-table-change-subscription`). Invalidation is setting a flag, done inline in the handler; that is the one thing a watch handler may do synchronously, and it is what keeps read-your-writes: `watch` handlers run before the committing call returns, so a write followed by a read always sees its own row.
- Leave alone any read that must see a specific committed state for a CHECK or a decision inside a write transaction (the counts taken under the write lock in redemption and formation). Those stay SQL reads inside their transaction; find them by reading the redemption and formation paths, and list them in the implement ticket.

## Settled choices

- **This, not per-flow deduplication.** Passing rows between functions within one flow (as `queryOwnerKeyRows` already does for the retired set) fixes one flow at a time; the measured repeats come from at least five different flows. A cached view removes the class. `control-reconcile-woken-by-changes-reads-once` still restructures the reconcile pass, but it reads through this view.
- **Only small, hot tables.** These are bounded by machines and owner keys in one party. Do not cache strand lists or app-sized tables here.

## Edge cases & interactions

- **Read-your-writes.** Covered by inline invalidation; verify with the spec below.
- **A replicated change that lands without a storage event** (a cadre larger than 16 machines, outside the block's cohort). The view would stay stale until the next local commit. Give the view a maximum age (the reconcile backstop's period is the natural choice) after which it reloads. Note the bound at the constant.
- **Concurrent load and invalidate.** A load in flight when an invalidation lands must not install stale rows. Use a generation counter. Verify by the spec below.
- **`close()`.** The view and its subscription go with the database.
- **The never-written `Revocation` collection** before the ledger marker or before `control-collections-created-at-cadre-founding` lands: a load is one consult instead of many, which is the point.

## Tests

- One spec over the view's branching: a write then a read sees the write; an invalidation during a load causes a reload, not stale rows; no second read of the table between changes.
- Re-pin `control-founding-consult-budget.spec.ts`'s per-call membership reads (pinned exactly today); they should drop.
