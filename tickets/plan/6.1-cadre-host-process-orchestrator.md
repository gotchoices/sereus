## Context

Today the `Orchestrator` interface (`packages/cadre-provider/src/service/orchestrator.ts`) has two implementations: `DockerOrchestrator` (real, Docker-API-backed) and `MockOrchestrator` (testing-only, in-memory). Self-hosted basement-PC deployments need a third: **`HostProcessOrchestrator`**, which runs cadre nodes as plain Node child processes on the host machine. Docker Desktop on Windows is a licensed, heavyweight install; on Linux desktop it's lighter but still a setup hurdle; for the self-host persona it's not acceptable as a prerequisite.

This implementation also has incidental value to cadre-provider's bare-metal operators — anyone running the provider on a host where Docker is undesirable can use it — so the implementation is general-purpose, even though its primary consumer is cadre-host.

## Behaviour

`HostProcessOrchestrator implements Orchestrator`. Each "container" in the interface maps to a child Node process running `@serfab/cadre-core`'s node entrypoint (verify exact bin or module path during plan — currently a cadre node is constructed programmatically via `CadreNode`; this ticket may need to add a thin runnable wrapper around it in `cadre-core` or in `cadre-host` itself).

### `createContainer`

- Allocates a working directory under a configurable root (default `<userData>/cadre-host/nodes/<containerId>/`).
- Allocates listen ports: P2P, health, metrics. Either accepts caller-specified ports (preferred when NAT port-forwards dictate) or picks free ones via a port-finder utility. Persists the choice in the store so restarts use the same ports.
- Spawns a child process with `child_process.spawn`, passing config (party ID, bootstrap nodes, profile, strand filter, ports, data dir) via either env vars or a JSON config file the child reads. JSON file is cleaner — env vars get unwieldy at this size.
- Captures `stdout` and `stderr` to rotating log files in the working directory (`node.log`, with size-based rotation — see logging below).
- Records the child PID in the store via a new field on the orchestrator-create-result (`pid` alongside `dockerId`). The `dockerId` field becomes "the orchestrator's opaque handle" — for host-process mode it's the PID-plus-startup-token; see "identity" below.
- Returns the result with `healthEndpoint` / `metricsEndpoint` / `p2pPort` populated from the chosen ports.

### `stopContainer`

- Sends `SIGTERM` to the child, waits a configurable timeout (default 10 s), then `SIGKILL` if still alive.
- Closes the log file handles cleanly.
- Updates the in-process tracking; the working directory is preserved so logs and any persistent state survive (separate `removeContainer` clears it).

### `removeContainer`

- Ensures the process is gone (calls `stopContainer` first if needed).
- Deletes the working directory.
- Removes from the in-process tracking map.

### `isRunning`

- Cross-platform PID-liveness check. `process.kill(pid, 0)` works on POSIX but on Windows it throws `EPERM` for processes the caller doesn't own and `ESRCH` for genuinely-dead ones — needs platform-specific handling. The `is-running` npm package wraps this but is small enough to vendor; alternatively check the child reference held in memory (orchestrator instance) first and fall back to PID probe only after a restart-recovery.
- Also verifies the **startup token** (see below) to detect PID-reuse: a fresh process that happens to get the old PID is not "the same container."

### `getStats`

- CPU/memory: `pidusage` is the de-facto cross-platform npm package; small, no native deps. Pragmatically the right choice.
- Network bytes: not generally available cross-platform without OS-specific tools. Acceptable to return zeros for v1 and document the gap. Cadre-provider's billing flow consumes these but cadre-host doesn't bill, so this gap doesn't block the self-host persona.

### `getLogs`

- Tails the captured log file. Default 100 lines. The rotation policy means "the most recent log file"; older rotated files are also accessible via a separate API call if needed by the local UI.

## Identity and PID-reuse

PIDs can be recycled by the OS, so storing only `pid` is unsafe across restarts. The orchestrator persists a `(pid, startupToken)` pair where `startupToken` is a random nonce written to a file the child process drops in its working directory on startup. To verify "is this PID still my container," check that the file exists and contains the expected token. This survives orchestrator restart, host reboot (where PIDs reset), and the case where the user manually kills the child and the OS hands the PID to something else.

## Logging

- Log files: `node.log` in the container's working directory, with size-based rotation (e.g. 10 MB per file, keep 5). The `pino`-built-in rotation or a small custom rotator on top of `fs.createWriteStream` — decided at plan stage.
- Log lines are passthrough from the child's stdout/stderr; the child controls its own log format. The orchestrator doesn't parse or transform.
- The local UI ticket will surface log viewing; this ticket just makes the files exist and rotate.

## Process supervision and orchestrator-exit behaviour

When the cadre-host process itself exits (clean shutdown, crash, host reboot), what happens to the spawned cadre node children?

- **Default**: children are detached (`detached: true, stdio: 'ignore'-but-with-our-pipes`) so they survive a cadre-host crash. The cadre-host service-host integration (systemd / Windows Service via NSSM) restarts cadre-host on crash; on restart it reconnects to the running children using the persisted `(pid, startupToken)` pairs in the store.
- **Clean shutdown**: cadre-host sends `SIGTERM` to each child before exiting, so a deliberate `cadre-host stop` takes the nodes with it.
- **Host reboot**: children die with the OS. cadre-host's service-host integration starts it back up, and on startup it sees the persisted container records, finds no live processes for them, and restarts each via `createContainer` (reusing the same working directory and ports).

This is more conservative than the Docker mode (where the daemon takes children with it on graceful restart) but matches what the self-host persona expects: "my node should be running unless I told it not to."

## Resource limits

Docker gives us `--memory` and `--cpus` cheaply. Cross-platform Node equivalents are limited:

- **Memory**: pass `--max-old-space-size=<MB>` to the child node process for heap cap. Doesn't cap RSS but covers the dominant V8 allocation. Adequate for v1.
- **CPU**: no portable way. On Linux we could use `nice` / `cgroups`; on Windows `start /low`; on macOS `nice`. Out of scope for v1 — document the gap. The self-host persona doesn't need fine-grained CPU limits; the basement PC is dedicated enough that "the cadre node should not eat the machine" is handled by being well-behaved, not by being capped.

## Interface impact

The current `Orchestrator` interface uses `dockerId` as the opaque handle. The name is Docker-specific. **Option A**: rename to `orchestratorHandle` (or just `handle`) — touches every implementation and call site. **Option B**: keep the name, document that for host-process mode the value is `<pid>:<startupToken>`. Plan stage decides; my lean is Option A (the rename is cheap and the current name leaks an implementation choice), but it's debatable.

If renamed, the change lives in this ticket and the call sites in `cadre-provider/src/service/container-service.ts` get updated.

## Use cases

1. A self-host user starts cadre-host with no Docker installed; their cadre node is spawned as a child Node process. They never know Docker exists.
2. A cadre-provider operator runs the provider on a bare-metal box with no Docker; selects `orchestrator: hostProcess` in config; the provider works identically to its Docker mode (modulo the network-bytes stat gap).
3. The cadre-host process is killed by the user via Task Manager / `kill`. The service-host integration restarts it. On restart, it finds the child cadre node is still alive (detached), reattaches to it via the persisted `(pid, startupToken)`, and continues. The node never went down.
4. The host machine reboots. Cadre-host comes back up via its service unit, sees persisted container records, finds the processes are gone, restarts each one in its preserved working directory.

## Non-goals

- Sandboxing (bubblewrap, firejail, sandbox-exec, AppContainer). Self-host is a trust-circle environment; container-grade isolation is overkill. Revisit if a hostile-tenant use case emerges.
- Per-process disk-usage limits. The user controls their own disk; surface usage in the UI rather than enforcing caps.
- A full process-supervisor (PM2-style). Service-host integration handles cadre-host itself; cadre-host handles its children. We don't need a third layer.
