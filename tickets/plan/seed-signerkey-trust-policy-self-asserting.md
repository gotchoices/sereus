----
description: Seed enrollment trust gate is self-asserting with no out-of-band anchor
files: packages/cadre-core/src/seed-bootstrap.ts, docs/architecture.md
----

`applySeed` accepts a seed whose own signed payload claims the signer is an authority, so a forged self-consistent seed passes the trust gate. After validating the ed25519 signature against `seed.signerKey`, the only authority check confirms that `signerKey` matches a peer flagged `isAuthority` *within the same seed*: `seed.peers.some(p => p.isAuthority && p.publicKey === seed.signerKey)` (`packages/cadre-core/src/seed-bootstrap.ts:268-274`). Both the signature and the authority assertion are derived from attacker-controllable seed fields. An attacker can construct a seed that lists their own key as an authority peer (`isAuthority: true`, `publicKey` = their key) and self-sign it; it satisfies both the signature check and the authority check. This is the residual gap left by the prior `1-seed-authority-validation` work, which tightened the in-seed check but did not establish an external root of trust.

The core problem is the absence of an out-of-band trust anchor. There is no pinned per-party authority key and no explicit Trust-On-First-Use confirmation step; trust is bootstrapped entirely from data inside the seed itself. This is exploitable over the network because the cadre-cli health server exposes a public `POST /seed` endpoint bound to `0.0.0.0` with no authentication, allowing any reachable peer to submit a seed for application.

A related defect compounds the issue: `queryPeers` derives `isAuthority` and `publicKey` from the libp2p `peerId` rather than the `AuthorityKey` table. Specifically `isAuthority = (peerId === self peerId)` and the `authorityKeys` set built from `CadreControl.AuthorityKey` is constructed but never consulted (`packages/cadre-core/src/seed-bootstrap.ts:459-479`). As a result a seed generated by one authority node cannot mark another authority node as an authority, which breaks multi-authority cadres, and it conflates the libp2p `peerId` with the ed25519 `AuthorityKey` identity. Authority identity should be sourced from the `AuthorityKey` table, decoupled from the transport-level peer identity.

Expected behavior, per the TODO in `docs/architecture.md:291-293`, is to enforce a real trust policy for `signerKey` rather than accepting self-asserted authority. The trust decision for the signing key must rest on an external anchor — either authority keys pinned per party and supplied out-of-band (for example carried by the invite), or TOFU with explicit user confirmation on first acceptance — so that a seed cannot vouch for its own signer. Authority identity used during seed creation and validation must be derived from the `AuthorityKey` table so that multi-authority cadres are representable and ed25519 authority keys are not conflated with libp2p peer IDs. The unauthenticated network path that lets arbitrary peers submit seeds should be considered part of the threat model when designing the policy.
