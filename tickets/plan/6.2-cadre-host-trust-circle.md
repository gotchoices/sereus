## Context

Cadre-host's auth model is "me plus one or two friends" — a closed trust circle, not a multi-tenant API. The current cadre-provider auth (API keys hashed in storage, `customerId` per request, optional OAuth/JWT) is the wrong shape: too much ceremony for a closed circle, and it doesn't tie into the cadre node's existing cryptographic identity.

The good news is that the cadre stack already has the primitives we need. `packages/cadre-core/src/enrollment.ts` exposes `EnrollmentService`, and `packages/cadre-core/src/cadre-node.ts` has `encodeInvite` / `decodeInvite` / `dialFromInvite` / `authorizePeer` / `addPhoneWithRelay` — a full invite-and-authorize flow for joining a cadre. Cadre-host's trust-circle is essentially "an invite to my cadre," and the cadre-core primitives already model that.

This ticket wires cadre-core's identity and enrollment into cadre-host's API surface, replacing the API-key model entirely for the self-host package.

## Behaviour

### Invite generation

The host user generates an invite via:

- `cadre-host invite` (CLI) — prints an encoded invite token to stdout, optionally with a QR-renderable form.
- Local UI button "Invite a friend" — calls the same underlying API, displays the token plus a QR code, plus a copy-to-clipboard control.

The invite encodes (delegating to `cadre-core`'s `encodeInvite`):
- The host's cadre PeerId and reachable multiaddr(s) — including the DDNS-resolved hostname from the NAT ticket.
- A short-lived authorization token (TTL configurable, default 24 hours) that the recipient redeems to join the trust circle.
- A human-readable label set by the inviter ("Brother's phone") so the host UI can display "pending: <label>" until redeemed and "active: <label>" afterward.

The invite is base64url-encoded for out-of-band delivery (link, QR, text message). Length matters because QR density grows with payload — keep the encoded form under ~400 chars where possible.

### Invite redemption

The recipient's cadre node (or reference app) accepts the invite token, decodes it via `decodeInvite`, dials the host via `dialFromInvite`, and presents the authorization token. The host verifies the token, calls `authorizePeer` on its own cadre node, and the recipient is now a member of the trust circle.

Subsequent API calls from the recipient are authenticated by libp2p's transport-level peer identity — there's no separate session token. The host's HTTP API (the management API, not the cadre P2P protocol) trusts requests from peers whose PeerId is in the trust circle, established via mTLS or libp2p auth (decision at plan stage — depends on whether the management API is HTTP-over-libp2p or a separate Fastify port).

### Trust-circle storage

The trust circle is a list of `(peerId, label, addedAt, status)` records. Storage options:

- **Reuse `ProviderStore`** with a new `TrustCircleMember` entity. Keeps cadre-host's store schema flat and lets us share the `MemoryStore` / `FileStore` machinery.
- **Persist into the cadre control network** (the Optimystic `CadrePeer` / `AuthorityKey` tables already exist for this purpose). More canonical — the trust circle becomes part of the user's cadre control state, replicated across their own devices for free.

Plan stage decides. My lean is the second option (use the existing control network) because it gives free multi-device replication of the trust circle: the user's phone, the basement PC, and any other cadre node share the same "who's authorized" view without cadre-host needing to be the source of truth.

### Revocation

The host user can revoke an invite (before redemption) or remove a trust-circle member (after). Both surface in the local UI; both translate to control-network operations (delete the `FormationInvite` row, or remove the `AuthorityKey` / `CadrePeer` entry).

Revoking a member terminates any active sessions and the recipient's node loses access on its next request. There's no "session timeout" because there's no session — auth is per-request via peer identity.

### Self-access

The host user's own devices (their phone, their laptop) authenticate the same way as friends: they're members of the trust circle, just with a "this is you" flag. Adding the first device is a chicken-and-egg problem solved by the installer (`cadre-host-installer` ticket): the install flow generates an invite displayed in the installer's final screen so the user can immediately enroll their phone.

## API impact

The cadre-host HTTP API endpoints (defined in the local-UI and installer tickets — TBD scope) all use peer-identity auth rather than the customer-id-and-API-key model of cadre-provider's `routes.ts`. The container/process management endpoints check that the calling peer is in the trust circle; that's the entire auth check. No `customerId` field on requests, no `permissions` array — trust-circle membership is binary.

`cadre-provider`'s auth code (`packages/cadre-provider/src/server/auth.ts`) is not used by cadre-host. Cadre-host gets its own thin auth middleware.

## Use cases

1. **First-run self-enrollment**: user installs cadre-host on their PC. Installer's final screen shows an invite QR. User scans it with their phone. Phone joins the trust circle. User can now access their basement node from their phone.
2. **Inviting a family member**: user clicks "Invite" in the local UI, sets the label "Mom's phone", gets a QR + token. Sends the token over Signal. Mom's phone (running the reference app) redeems it. Host UI now shows "Mom's phone — active".
3. **Lost phone**: user removes "My old phone" from the trust circle via the local UI. The next request from that device fails.
4. **Multi-device trust circle replicated**: user's phone also runs cadre-host (or the cadre-host management features are accessible via the reference app). The trust circle reflects the same members on both, because it's stored in the control network the user's own cadre nodes share.

## Non-goals

- Fine-grained permissions ("Mom can read messages but not invite others"). The trust circle is flat for v1. Roles can come later if a real use case emerges.
- Federation across trust circles. Each host has its own circle; circles don't talk to each other through this mechanism.
- Password-based auth, magic links, OAuth integration. Out-of-scope; the cryptographic-identity-and-invite model is the design.
- Recovery of a trust-circle membership lost due to key loss. The recipient's device is gone, period; the invite flow re-enrolls them with a new identity.

## Constraints & considerations

- **Invite TTL**: 24 hours is a placeholder. Long enough that "I'll send it to Mom tonight" works; short enough that a leaked invite expires before someone abuses it. Configurable.
- **One-time vs reusable invites**: default one-time. A reusable invite is a different artifact (a join-link the host posts somewhere); not in scope for v1.
- **Management API transport**: the local UI talks to cadre-host over `http://localhost:<port>` — same-machine, no peer-identity auth needed (origin check + a localhost-only listener). Friends' nodes talk to cadre-host over the cadre P2P protocol, using peer-identity auth. These are two separate transports; the ticket clarifies the model so the UI ticket and the NAT ticket know what they're building against.
- **Where the invite-issuance API lives**: probably an HTTP endpoint on the localhost management API, not on the public cadre P2P surface. The local UI is the issuance UX. CLI piggybacks on the same endpoint.
- **Existing `CadreInvite` shape**: this ticket should not redesign the existing cadre-core invite format. If the format needs new fields for trust-circle membership (vs strand membership), extend it minimally and bring the cadre-core owner into the conversation at plan stage.
