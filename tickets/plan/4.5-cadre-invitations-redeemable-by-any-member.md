# Cadre invitations that any member machine can redeem

## Design intent (from the project owner)

An invitation implies the signature of the originator and does not need to be signed again to take effect. It may name a specific peer id, or leave the peer id empty, in which case whoever claims it designates the peer id.

## What the code does instead

- `createInvite` keeps the invitation only in the issuing process and opens that node's enrollment window. The invitee's peer id reaches the issuer out of band (cadre-cli admin server, cadre-host trust circle), and `acceptPhone` → `authorizePeer` signs the `CadrePeer` row at that moment (`seed-bootstrap.ts` ~1343). The issuer must therefore be online, and it signs every join.
- `CadrePeer.AuthorizedInsert` has a single branch: an owner signature over `(PeerId, StampId)`. `OwnerKey.Authorized` is likewise owner-signature only. Neither has the consent branch that `Strand.AuthorizedInsert` has for `FormationInvite` redemptions.

## What to build

**Schema.** A `CadreInvite` table (name to settle), modelled on `FormationInvite`:
- `Token` (or its hash, so the replicated row cannot be redeemed by someone who only reads the table; strongly preferred), optional `PeerId` (target), `GrantsOwner` (bool), `ExpiresAt`, `TotalUses`, `StampId`. Owner-signed insert and delete; immutable otherwise.
- A usage table like `FormationUsage` (append-only): the redeemer's peer id and public key, a consent signature by the redeemer's own key over the invitation and its usage stamp, and the invitation reference.
- **Consent branch on `CadrePeer.AuthorizedInsert`:** the row is admitted when a usage row in the same transaction names this `PeerId`, the invitation is live (unexpired, uses left, not tombstoned), and its `PeerId` is null or equals this `PeerId`. `VouchOwner` / `VouchSig` then reference the invitation's signer and signature, so readers can check them against their anchor. Settle the stored form.
- **Consent branch on `OwnerKey`** for invitations with `GrantsOwner`, under the same conditions. Mind the `committed.*` rule: the invitation must predate the redeeming transaction.
- `Revocation` covers the new tables; deleting an invitation withdraws it.

**Protocol.** Redemption runs on any member machine. Add the redemption message to a stranger-open protocol (extend `/sereus/seed/1.0.0` or add one protocol to the allowlist in `membership-connection-gater.ts`). The redeemer sends the token proof, its peer id and its consent signature. The member writes the usage and `CadrePeer` (and `OwnerKey`) rows and answers with a seed.

**Gate.** The connection gate admits a stranger for redemption while a live invitation row exists, the same rule as the outstanding-`FormationInvite` exemption. Replace the issuer-local enrollment window with this.

**Client.** `createInvite({ peerId?, grantsOwner, expiresIn, uses })` writes the row and returns the encoded invitation: token, party id, the issuer's anchored owner keys, and up to N reachable member addresses, chosen like `createOpenInvitation`'s sibling list. `redeemInvite(encoded)` on the new device dials those machines in order and pins the invitation's owner keys (the existing invite-pin trust path).

**Replace** the `acceptPhone` / admin-route / trust-circle redemption path with this. No backwards compatibility.

## Edge cases & interactions

- Untargeted owner invitation: it is a bearer credential granting ownership. Keep it single-use, give it a short default expiry, and have the UI say so. Targeted invitations are safe to share openly. (Inspection of defaults; test of expiry and use count.)
- Two redeemers race for a single-use invitation on different machines: the usage key is evaluated locally (the same convergence note as `FormationUsage`), so both may be admitted until merge. Decide whether that is acceptable for owner grants or whether owner-granting redemption must be serialized. (Design decision recorded in the ticket.)
- A targeted invitation redeemed by another peer id: refused by the schema. (Test.)
- The redeeming member has not yet received the invitation row: answer a retryable "unknown" so the redeemer tries the next machine, as formation does with `token-unknown`.
- Trust on the redeemer: it anchors the owner keys the invitation carries, so a forged invitation from someone who is not an owner yields a seed nobody else in the cadre accepts. Make sure the redeemer can tell that apart from success.
- Interaction with `owner-anchor-follows-owner-key-changes`: an owner admitted by invitation must chain to the invitation signer's anchored key.
