## Context

A basement PC sits behind a residential NAT. For the host's cadre node to be reachable by friends' nodes (and by the host's own phone outside the LAN), traffic needs an inbound path. The two pieces are:

1. **Port reachability** — a specific TCP/UDP port on the host machine is reachable from the public internet.
2. **Hostname stability** — friends need a name to dial that survives the ISP rotating the public IP.

Cadre-host targets the friction profile of the self-host persona: it should *try* to make both work automatically, and where it can't, it should clearly tell the user what to do and verify when they've done it.

## Port reachability

Three layers, tried in order:

### Layer 1 — UPnP / NAT-PMP

On startup, cadre-host attempts to negotiate a port mapping with the local router. Most consumer routers support UPnP or NAT-PMP; many ship with it enabled by default. The libp2p ecosystem already uses `@achingbrain/nat-port-mapper` for this purpose (likely already in the dependency graph via cadre-core's libp2p setup). Cadre-host wraps it with:

- Map the configured external port → internal port (default both 4001, configurable).
- Verify mapping by querying the router back.
- Refresh the lease periodically (most routers expire UPnP mappings after a few hours).
- On `cadre-host stop`, release the mapping.
- Surface mapping status in the local UI: "Router port forward: auto (UPnP)" / "auto (NAT-PMP)" / "manual" / "failed".

### Layer 2 — Manual port-forward

If UPnP/NAT-PMP fails (router doesn't support it, or admin disabled it, or the network has multiple NAT layers), the local UI presents a "Manual setup needed" panel with:

- The local IP and port to forward to.
- A link/instructions for common router vendors (Linksys, Netgear, TP-Link, ASUS, Ubiquiti — short list, generic guidance for others).
- A "Test" button that fires a request through an external check service (or queries the libp2p AutoNAT result) and reports whether inbound connectivity works.

The UI keeps the panel visible until the test passes. Once it passes, the panel collapses into a status indicator.

### Layer 3 — Relay fallback

If the user can't get port forwarding working (CGNAT, dorm wifi, no router admin access), cadre-host should not be useless. Libp2p's circuit-relay v2 lets nodes accept inbound connections via a relay node. Cadre-host can:

- Detect from AutoNAT that the host is unreachable directly.
- Surface "Direct connections unavailable — using relay (slower)" in the UI.
- Continue working through relay, with a clear note that performance is degraded.

The relay endpoint(s) used are the same relays the rest of the cadre stack uses (cross-reference `4-relay-bootstrap-infrastructure` in backlog). This is a fallback, not the primary path, but ensures the user is never told "your PC is unreachable, sorry."

## Hostname stability — DDNS

The ISP rotates the public IP. Friends need a name to dial.

### Built-in DDNS clients

Cadre-host ships with a small DDNS client supporting a few providers. **Start with DuckDNS** (free, token-based, no account ceremony — just register a subdomain). Add more providers (Cloudflare, No-IP, Dynu) as user feedback dictates.

Each provider integration is a thin module:

```typescript
interface DdnsProvider {
  id: string;            // "duckdns", "cloudflare", ...
  displayName: string;
  configFields: Array<{ key: string; label: string; secret: boolean }>;
  update(config: Record<string, string>, ip: string): Promise<void>;
}
```

The provider modules live under `packages/cadre-host/src/nat/ddns/` — one file per provider, plus a registry. The DuckDNS implementation is a single HTTP GET; Cloudflare is a couple of API calls (zone lookup + record update). Vendoring thin clients per provider beats taking on per-provider npm dependencies that may go unmaintained.

### Update cadence

- On startup, after layer-1 port mapping resolves, detect external IP (via the router's UPnP query if available, else via a public IP service like `api.ipify.org`).
- Update the DDNS record if changed.
- Re-detect every 5 minutes (configurable). Only call the provider's update API if the IP actually changed — keeps free-tier providers happy.
- Surface in UI: "DDNS: yourname.duckdns.org → 71.xx.xx.xx (updated 2 min ago)".

### Manual / external DDNS

For users who already run DDNS at the router level or via a separate client (some routers have built-in DDNS), they should be able to set a "DDNS managed externally — hostname: foo.bar" entry and skip cadre-host's own updater. The hostname is still used in invite generation.

## How NAT settings feed the invite system

The trust-circle ticket (`cadre-host-trust-circle`) encodes the host's reachable multiaddr into the invite. This ticket determines what that multiaddr is:

- If layer-1 UPnP succeeded and DDNS is configured: `/dns4/<ddns-hostname>/tcp/<external-port>/p2p/<peerId>`.
- If layer-2 manual port-forward + DDNS: same shape (cadre-host doesn't know how the mapping was created, just that the test passed).
- If layer-3 relay: a relay-addressed multiaddr `/dns4/<relay>/tcp/<relay-port>/p2p/<relay-id>/p2p-circuit/p2p/<host-peerId>`.

The invite-encoding code calls into a "what's my reachable address" helper this ticket exposes.

## Local UI surface

The NAT/DDNS settings panel in the local UI shows:

- Current external IP, last detected at.
- Port-forward status (auto / manual / failed / relay-only).
- DDNS provider, hostname, last successful update.
- A test-reachability button that runs an end-to-end probe (have a public AutoNAT-style service dial back, or use libp2p's built-in AutoNAT).
- Configuration controls for choosing a DDNS provider and entering credentials.

The UI ticket (`cadre-host-local-ui`) renders these; this ticket exposes the data via the management API.

## Constraints & considerations

- **AutoNAT / libp2p NAT detection**: libp2p has its own NAT detection and AutoRelay. Cadre-host's NAT layer should not duplicate libp2p's work — it should *configure* libp2p (announce-address overrides, relay reservations) based on what this layer detected, and *consume* libp2p's AutoNAT verdict.
- **UPnP security**: enabling UPnP on a router is a security trade-off some users (or their network admin) won't accept. Make UPnP-attempt configurable; "off" is a valid choice that pushes the user straight to layer-2 manual.
- **DDNS credential storage**: tokens are secret-grade. Store via the platform's native credential store (Keychain on macOS, Credential Manager on Windows, libsecret on Linux). Library: `keytar` is the standard cross-platform wrapper; has native deps but is well-maintained. Fallback to encrypted file with a host-machine-bound key if keytar fails to load (some headless Linux servers).
- **IPv6**: residential IPv6 is increasingly common and bypasses NAT entirely. Detect IPv6 reachability and prefer it where available. The multiaddr can carry both; libp2p tries both. This is a nice-to-have for v1, not a blocker.
- **CGNAT**: some ISPs put residential customers behind carrier-grade NAT, in which case neither UPnP nor manual port-forward works. Layer-3 relay is the only option. Detection: external IP from public service differs from external IP at the router. Surface this state explicitly in the UI ("your ISP uses CGNAT — direct connections aren't possible, using relay").
- **Test-reachability service**: who runs the dial-back service for the layer-2 test? Options: (a) a sereus-owned service, (b) leverage libp2p AutoNAT against bootstrap nodes, (c) skip the test and just trust the user. (b) is the cleanest — AutoNAT exists for exactly this.
