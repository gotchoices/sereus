## Problem

The `CadreControl` store is **designed** to converge P2P over the control network via Optimystic's network transactor (deterministic collection ids → FRET routing → cluster consensus replication + pull-on-read read-repair) — the **same** machinery that converges strand databases today.

> **Correction (from `control-db-two-node-convergence-test` review).** An earlier draft of this ticket called control convergence "settled" and assumed only cohort discovery was missing. That premise is **wrong**: the `CadreControl` tables are **not network-backed at all today** — `ControlDatabase.initialize()` never sets `optimystic` as the default vtab, so the tables fall back to Quereus's in-memory vtab and a write never reaches the transactor. The "did not converge after 24s" observation below is explained by that, not (only) by cohort non-formation. Network-backing is a **prerequisite** of this ticket (`control-db-network-backed`, now in `prereq:`); cohort discovery cannot make in-memory tables replicate. Design this ticket assuming network-backing has landed.

But convergence only happens when the control collections' **cohort/cluster actually forms** across the party's nodes: the nodes must be connected such that FRET seats each peer in the others' keyspace cohort, and a write must occur while that cohort has ≥2 members (otherwise it commits **local-only** and never broadcasts — the `getClusterSize(blockId) <= 1` branch in optimystic's `coordinator-repo.ts`).

Today there is **no production mechanism that makes a party's control nodes actively connect to each other** for this purpose. The integration tests that achieve convergence do so with a **manual, test-only `dial()` + both-sides connection wait** between specific nodes (`strand-formation-e2e.integration.ts:413-445`); the control plane has no equivalent. A node started with only `bootstrapNodes` (and possibly a relay) does not reliably form the control cohort — empirically, a two-node control pair did not converge after 24s. The result: in production, sibling-written control rows (membership, peer addresses, device tokens) may never reach a node that only ever connected over the control network — which would break push-wake authorization (`isMember` reads an empty/partial local table) and any other sibling-written-row read.

This is the **production correctness fix** the convergence plan identified. It is **distinct from** `strand-cohort-seed-uses-control-network-addresses` (that publishes *strand*-network addresses so a resumed strand can join its *strand* cluster); this is about the **control** network's own cohort forming.

## Design question to resolve (this plan ticket's job)

How should a party's cadre nodes discover and stay connected to each other so the control collections converge — without a human/test manually dialing? Resolve the mechanism, then emit implement ticket(s).

Key sub-questions to settle (with defensible decisions, not handed to the implementer):

- **Source of sibling addresses.** A node already has the pieces: it can `listMembers()` (`queryCadrePeers`) and `resolvePeerAddrs(peerId)` for each sibling, and the seed pre-populates the peerstore for cold start (`applySeed`). But there is a **cold-start chicken-and-egg**: resolving siblings requires the `CadrePeer` rows, which require convergence, which requires connection. How does the seed (already applied at enrollment) bootstrap the first connections, and how does the node transition from seed-driven dials to converged-row-driven dials?
- **Who dials whom, and how many.** All members? The `clusterSize`-nearest in the control keyspace? Authority nodes preferentially (as `applySeed` already dials `isAuthority` peers — `seed-bootstrap.ts:522-535`)? Decide a connection policy that keeps the control cohort ≥2 for the relevant block keys without N² full-mesh dialing at scale.
- **Eager vs lazy, and refresh cadence.** Dial on start + on a refresh interval (reuse/extend the existing self-record refresh timer + `self:peer:update` listener, `cadre-node.ts:705-720`)? React to newly-discovered `CadrePeer` rows?
- **NAT / relay reality.** Many cadre nodes are NAT'd/mobile. Does a relayed connection seat control-cohort membership, or is a direct (WebRTC/hole-punched) path required? This intersects `resolvePeerAddrs` (signaling-first ordering) and the relay setup in `createControlNode`. If relay-only is insufficient for cohort formation, specify the upgrade-to-direct path.
- **The write-while-alone durability gap.** Even with discovery, an authority that writes a `CadrePeer` row while no sibling is online commits local-only. Decide the remedy: re-publish/re-touch on cohort growth, or rely on a later reader's pull-on-read repair once the writer is in its cohort, or an explicit "ensure replicated" step after authorize. This may be its own implement ticket.
- **Relationship to FRET-backed liveness.** `tickets/backlog/fret-backed-peer-record-liveness.md` proposes a FRET put/get freshness layer behind `resolvePeerAddrs`. Decide whether control-cohort discovery and FRET liveness are independent, sequenced, or one subsumes the other. (Liveness is a *freshness* optimization for a single record; this is *cluster formation* for whole collections — likely complementary, but the boundary should be drawn here.)

## Notes

- The convergence mechanism itself is NOT in question and need not be re-investigated — `control-db-two-node-convergence-test` (implement/) will have an executable proof and a `waitForCrossNodeControlSync` harness helper to build on.
- Strong starting direction (validate, then design around): on start and on the existing refresh cadence, a node resolves its known siblings' control addresses (seed peerstore first, converged `CadrePeer` rows thereafter) and proactively dials a bounded set to keep the control cohort connected — mirroring, in production, what the strand tests do by hand. The hard parts are the cold-start ordering, the connection policy at scale, NAT/relay sufficiency, and the write-while-alone durability remedy.
- Output: one or more implement ticket(s) (e.g. "control-cohort proactive dial on start+refresh" and, if separate, "ensure-replicated control writes / re-publish on cohort growth"), each sized to one agent run, each with an `## Edge cases & interactions` section.
