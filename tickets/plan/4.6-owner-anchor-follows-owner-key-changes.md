# The node-local owner anchor must follow OwnerKey additions and removals

## The gap

Membership trust rests on each node's **node-local** trusted-owner anchor (`TrustedOwnerStore`), not on the replicated `OwnerKey` table (docs/architecture.md → "Node-local trusted-owner anchor"). A `CadrePeer` row counts as an authorized member only if its `VouchOwner` is in the reader's anchor, and seed trust checks the same anchor.

The anchor gains a key only through genesis or an applied seed (`seed-bootstrap.ts` ~918 → `trustedOwners.trust`), and `TrustedOwnerStore` has no removal at all.

Consequences for the flows now planned:
- `app-joins-existing-cadre-by-invitation` makes app B an owner of cadre A. The basement node's anchor holds only A's key (pinned at claim). Every device B later vouches is **not** an authorized member on the basement node or on A, so B's admin work silently does nothing outside B's own node.
- `remove-a-device-or-app-from-a-cadre` removes an `OwnerKey` row, but every node that anchored that key keeps trusting it for seeds and vouchers.

The replicated table cannot simply feed the anchor: the anchor exists because a node with an empty local copy can seat its own key through the genesis branch, and that row replicates.

## Design direction

An owner addition is trusted only along a verifiable chain to a key the node already anchors:
- Owners added by invitation (`cadre-invitations-redeemable-by-any-member`) chain to the invitation's signer; the stored approval below must be able to express that.
- `OwnerKey` stores its approval, like `CadrePeer`: new columns `VouchOwner` and `VouchSig` (the 'add' digest signature), pinned to the insert context as `CadrePeer.AuthorizedInsert` does. The founding row (genesis branch) carries none.
- Each node extends its anchor with an `OwnerKey` row whose `VouchOwner` is already anchored and whose `VouchSig` verifies. Repeat until nothing changes, so chains of owners work. Run this wherever membership snapshots are refreshed.
- **Removal:** a committed `OwnerKey` tombstone removes the key from the anchor, but only when the removal is itself verifiable as coming from an anchored owner. `Revocation` stores no signature today (context only), so the tombstone needs one stored, or the anchor keeps its own record. Settle this in planning. `TrustedOwnerStore` gains a removal operation with the same all-or-nothing persistence rules.
- Keys anchored out of band (genesis, claim, invite pin, operator pin) are never removed by replicated state alone unless a verifiable owner removal names them. Otherwise one compromised owner could strip the others; the existing "no self-resignation" and `MinOneOwner` rules still apply.

## Edge cases & interactions

- Owner C was vouched by B, and B is later removed: C stays trusted (it was validly added at the time) unless removed itself. State this rule explicitly. (Test.)
- Anchor extension sees a row whose voucher it does not yet anchor: defer, don't reject; re-run on the next refresh. (Test.)
- Convergence: two partitioned owners each add an owner; both chains verify after merge. (Inspection.)
- `MinOneOwner` is a per-transaction local check (NOTE at `OwnerKey.MinOneOwner`); the anchor must never become empty either. A removal that would empty it is ignored and logged.
- Membership read paths (`isAuthorizedMember`, wake gate, strand-addr gate) pick up anchor changes without a restart.
