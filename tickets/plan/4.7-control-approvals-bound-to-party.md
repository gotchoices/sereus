# Bind every control approval to its party

## The gap

Every signed digest in `schemas/control.qsql` leads with a table tag and an action tag, but not a party. The schema says so itself (NOTE on `OwnerKey`, ~line 41): "Two parties that share an owner key would accept each other's approvals. Fine today (each party has its own owner key); if shared-owner multi-party ever ships, bind a party identity row into these digests."

It is shipping now:
- `app-joins-existing-cadre-by-invitation`: app B's node key is the owner of its own cadre and becomes an owner of cadre A, at least until `dissolve-empty-cadre`.
- `move-strand-between-cadres` runs on a node that is an owner of both cadres and writes the same strand's rows into each.
- A hardware owner key (`backlog/feat-owner-keys-only-on-user-devices`) would naturally own several cadres.

The digests bind each row's `StampId`, so most replays need an identical stamp in both parties. The move copies rows, which makes identical stamps likely unless something prevents it, and closing the gap by convention is fragile.

## What to build

- Add the party id to every digest in control.qsql (insert, delete, vouch, publish, reissue, Revocation) and to the matching builders in cadre-core (`control-authorization.ts`, `peer-authorization.ts` and the others). The schema needs a way to read its own party id inside a CHECK: a context value checked against a stored party identity, or a schema constant. Pick one; it must not be writer-chosen.
- No backwards compatibility: existing parties are recreated, as the architecture already states for schema changes.
- Remove the NOTE on `OwnerKey` once done.

## Edge cases & interactions

- `CadrePeer.VouchSig` is stored and replicated; it must carry the party binding too, so a voucher copied into another party's table fails.
- Seeds: `canonicalSeedPayload` already includes `partyId`. Confirm, and leave it.
- Device-side signers (phone, future hardware key) must show which cadre they are signing for, once owner prompts exist.
