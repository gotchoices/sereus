# A joining machine's own record is written once

## Traced (this planning pass; counted from code)

- **Invitation path:** the member writes B's `CadrePeer` row at admission, then B rewrites it (`publishSelfRecord`) with its signed address record. Two two-member commits for one row. The insert CHECK's consent branch does not constrain `Sig` (`control-schema.ts` ~451-463), so the admission can carry B's signed record.
- **Claim path:** `vouchPeer` writes B's row on A; B restarts into the party and publishes its own record only on its next 15 s pass.
- **Seed path:** A's first-connection drain re-signs B's unsigned row.
- **Founding:** `hasOwnerKey` read twice; `registerSelf` runs explicitly and again on its 1 s timer, usually a redundant self-update write.
- **After acceptance B runs two full refreshes back to back** (`cadre-node.ts` ~9560, then the reconcile pass at ~3839).

## Design

1. **B sends its signed address record with the request** (cadre-invite request; seed acknowledgement for the claim and seed paths). The member writes that row at admission. B's follow-up publish happens only if its addresses changed since.
2. **Founding publishes the self row once:** the explicit call, with the timer only re-arming for later address changes.
3. **One refresh after acceptance.** With `control-membership-rows-cached-until-changed` the second refresh is cheap, but the call is still redundant; remove it, or merge the acceptance refresh into the first reconcile pass.
4. **Read `hasOwnerKey` once in genesis.**

## Edge cases & interactions

- **A record signed by B that the member cannot verify** (B's clock, a malformed record). The admission must still seat B, without the record, and B publishes afterwards as today. Do not let a bad record fail the join.
- **B's addresses change between request and admission** (a phone switching networks). The follow-up publish covers it.
- **Protocol shape.** The request and seed-ack messages gain a field. No backwards compatibility is owed (AGENTS.md), but both sides of a mixed-version pair should fail clearly, not hang. Check the per-stream protocol guard.
- **Writes before the push** (traced: on the seed and claim paths a node's first-connection drain writes to a cohort that already includes a peer it has not yet pushed blocks to; the invitation path pushes first; hazard noted at `cadre-node.ts` ~2160). Fewer writes here shrinks that window; do not try to fix the ordering in this ticket. If it shows up as a defect in review, it gets its own ticket.
