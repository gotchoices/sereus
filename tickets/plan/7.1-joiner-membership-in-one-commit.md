# The joiner seats itself in one commit

## Measured

- `message-cost-accounting` baseline (2026-10-19): the joiner's first insert phase 24 app streams (20 `sync`, 4 `cluster`); in the following settle window, `consumeInvite` accounts for 47 block reads and 20 `cluster` streams B→A, after A had already read B's row.
- The reconciler's own NOTE: the two commits measured at 27 and 18 `/cluster` streams on 2026-09-17 (older stack). It left them separate because the saving was unmeasured and merging merges failure modes, and asks for a measurement against that baseline before trying.
- A transaction over several collections costs about 4 `cluster` requests per collection on a two-member cohort, unbatched (Optimystic, traced this pass). `consumeInvite` touches `Member`, `ConsumedInvite` and their unique-enforcement trees; `registerMemberPeer` touches `MemberPeer` and its trees. Every collection also reads its CHECK subqueries' tables (Invite three times, Manager, CancelledInvite, Revocation, Header).

## Design

1. **One transaction for Member, ConsumedInvite and MemberPeer.** `MemberPeer.MemberExists` reads the live `Member` table, and `MemberPeer.Authorized`'s add branch verifies only a self-signature over the new row, so the batch should satisfy the constraints. Confirm with the parity spec.
2. **Keep the heal path.** Today a redemption that lands but reports torn heals on the next pass, which sees the member row and goes on to the binding. With one transaction, a torn report heals the same way: the next pass sees either both rows (done) or neither (retry the whole). A pass that sees Member without MemberPeer (a seat written by the old two-step code, or by another of this party's machines) still runs the binding alone. Keep `ensureBinding` for that case.
3. **Stop the retry ladder on success.** Find why `ensureMembership` keeps reading after the seat committed (the measurement suggests the ladder runs again before the commit's own durability is reported, or a torn report). Fix that cause, not the symptom; record what it was.

## Edge cases & interactions

- **The seat commits but the reply is lost** (slow relay; GitHub #44's shape). The next pass must see the rows and not write them again. Verify by inspection plus the parity spec.
- **Another machine of the same party seats first** (a sibling ran the join). The pass sees Member and MemberPeer for its own peer only if it wrote them; read how the binding is keyed and keep it per peer.
- **Invitation used up between attempts.** The single transaction fails on `ConsumedInvite.ValidUsage`; that must surface as today's rejection, not a retry forever.
- **A founder that is offline.** A cohort-of-self commit is not allowed for the joiner's first commit (#44 work); unchanged.

## Tests

The parity spec is the gate for item 1. Item 3 is a bug: write its reproduction at the lowest layer that shows the extra pass (likely a reconciler spec with an injected writer that reports success), then fix.
