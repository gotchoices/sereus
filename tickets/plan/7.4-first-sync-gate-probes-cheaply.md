# The first-sync gate probes cheaply and wakes on arrival

## Measured and traced

- `message-cost-accounting` baseline, B's `addStrand`: 26 app streams, 25 of them `sync` B→A, one block at a time; `appTablesReadable` 12 reads, `strandHeaderHeld` 6.
- Traced: `count(1)` on an app table is a full scan, so a probe reads every leaf. Each block B does not yet hold costs two identical `sync` round trips (gotchoices/Optimystic#39), and the gate's `for … await` makes them strictly sequential. A probe that fails on one table restarts from the first table on the next 500 ms tick; on the phones in GitHub #44 the gate took 155–390 s.
- Meanwhile the founder's join backfill pushes its whole store to B starting about 1 s after B identifies (`peer-join-backfill.ts`), so the gate is fetching block by block what is about to arrive in bulk.
- `addStrand` / `whenStrandWritable` wait on an event, but that event fires only on a gate tick.

## Design

1. **One-row probes.** Replace `count(1)` with `select 1 … limit 1` (as `openTables` already does). Reading one row proves the collection is held and its root readable.
2. **Concurrent probes.** Probe the Header, then all remaining tables at once (`Promise.all`), so a probe round costs one round trip per tree level, not one per block.
3. **Remember what is held.** A table whose probe succeeded is not probed again in this gate's lifetime.
4. **Wake on arrival.** Subscribe through `control-and-strand-table-change-subscription`'s strand wrapper to the probed tables; a storage change (the backfill push landing raises it) triggers the next probe. Keep a timer as the backstop for a push that never comes, at a longer period than 500 ms (e.g. 2–5 s; pick and justify against `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS`).
5. **The backlog arm.** `backlog/debt-first-sync-gate-reads-every-strand-table` wants the gate to also cover the `Strand` tables a joiner writes (a correctness gap). Items 1–3 make adding them cheap. If that ticket is promoted alongside this one, implement both in one change; they edit the same loop.

## Edge cases & interactions

- **An empty app table.** With the founder's empty collections (`strand-founder-commits-every-table-collection`), every declared table has a collection; `select 1 … limit 1` returns no row but succeeds. The probe's success criterion is "the read completed without `BlockUnavailableError`", not "a row came back". Verify by reading the current probe's error handling.
- **A table added by a later schema version** (no collection): it still fails the probe forever. That is today's behaviour and `backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`'s subject; do not special-case it here.
- **Concurrency against a slow link.** Several concurrent probes to one peer each open a stream beyond the first prepared one (+1 round trip each, `prepared-streams.ts`). Still fewer sequential round trips than today; note it.
- **The gate times out** (`StrandAwaitingFirstSyncError`): unchanged semantics.
- **Hibernation wake** re-runs the gate over a kept store: probes succeed locally at once.
