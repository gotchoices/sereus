# Make harness parties state their cohort requirement instead of assuming it

Split out of `debt-harness-control-cohort-never-multi-peer` (deleted; this ticket and
`debt-harness-record-fret-ring-convergence-finding` replace it).

## Plain statement of the problem

`createTestParty` can start a party with extra machines ("drones"). Those machines
connect, but every control-database write is approved by the writing machine alone — the
group offered the write contains one member. Measured on `happy-path.integration.ts` with
two drones: 213 of 213 cohort-selection events reported a single peer. Nothing in the
suite notices, because a one-machine group commits happily.

The consequence is the point of this ticket: no harness-based test has ever exercised the
approval threshold, replication to a second machine, or a partial-failure write path. A
regression in any of them passes the suite green.

**Why it happens (measured since this ticket was written).** The group is not permanently
one member — the owner's peer ring reaches every party member within about five seconds of
party creation. The single-member groups are writes issued in that start-up window, before
the ring warms. See `debt-harness-record-fret-ring-convergence-finding` for the numbers.
One permanent limit remains: the extra machines only ever connect to the owner, never to
each other, so a write coordinated by a drone tops out at a two-member group no matter how
long it waits. Only owner-coordinated writes can reach three.

## What already exists (do not rebuild it)

`packages/integration-tests/src/harness/forced-cluster.ts` already solves the "make a real
multi-peer cohort happen in a test" problem — `forceFullCohort` and `pinCoordinator`
prototype-patch `Libp2pKeyPeerNetwork.findCluster` / `findCoordinator` so cohort
*discovery* is substituted while the real cluster clients, transports, response deadlines
and `ClusterMember`s stay in place. Read its file header before touching anything here; it
explains why the patch is on the prototype and not the instance (every node has two
`Libp2pKeyPeerNetwork` instances, and the transactor's coordinator assignment goes through
the second one).

`control-write-degraded-cohort-member.integration.ts` uses both helpers today and is the
worked example of an honest three-machine write test. It also carries the anti-vacuity
pattern worth copying: assert `forced.callCount()` grew and every `cohortSizes()` entry
was 3, so a test cannot silently regress to a narrower cohort.

**The gap:** `forceFullCohort` takes `readonly CadreNode[]` and reaches through
`node.getControlNode()`. A `createTestParty` party holds `TestCadreNode`s — bare libp2p
nodes from `createLibp2pNode`, with no `CadreNode` wrapper — so harness parties cannot use
it at all.

## What to build

Two pieces, both in `packages/integration-tests/src/harness/`.

**1. `waitForControlCohort(party, minPeers, options?)`** — the loud-failure helper. It
must observe the cohort the *writer actually consults*, not a proxy for it (connection
count is not a proxy: the drones are connected and the cohort is still one). Resolve it
against `findCluster` on the owner's key network for a control-tree key, and on timeout
throw naming the observed size, the required size, and the party name. Scenarios that mean
to test multi-machine behaviour call this before writing; scenarios that do not are
single-machine tests and should say so in a comment.

**2. A cohort-forcing entry point that accepts a harness party.** Either widen
`forceFullCohort` to take the structural shape it actually needs (peer id, multiaddrs,
public key — `TestCadreNode` and `CadreNode` can both supply it) or add a sibling that
takes `TestParty`. Prefer widening: two near-identical forcing helpers is the shape that
drifts. Keep the returned `ForcedCohortHandle` contract (`restore`, `callCount`,
`cohortSizes`) identical so existing call sites are untouched.

**Decision, now answered by the prereq: forcing is a stopgap, not a permanent fixture.**
Real cohorts do converge (~5 s), so `waitForControlCohort` is the primary tool for
owner-coordinated writes and forcing exists for determinism and for the one case a wait
can never satisfy — a drone-coordinated write, capped at two members by the star topology.
Put that conclusion in the helper's header; a future reader must not have to re-derive it.

## Expect scenarios to start failing — that is the finding

Once a harness scenario really writes into a three-machine cohort, it commits at the
production bar: `ceil(3 × 0.75) = 3`, i.e. unanimity. A scenario that has been passing on
a self-only cohort may now fail. Those failures are results, not regressions to paper
over. Record each one; the production-side fragility is tracked as
`debt-control-write-unanimity-at-three-nodes`. Do not lower the threshold to make them
pass — `debt-harness-supermajority-threshold-diverges-from-production` deliberately
aligned it with production.

## Edge cases & interactions

- **Two key-network instances per node** — a fix that only covers the node-attached
  instance leaves the transactor's coordinator assignment following the real, cold
  network. This is the exact bug `forced-cluster.ts` was rewritten to fix; do not
  reintroduce it by patching instances.
- **`allowClusterDownsize` is true by default**, so a self-only cohort commits silently.
  A passing write is never evidence that the cohort was multi-peer — every new assertion
  needs the cohort-size anti-vacuity check alongside it.
- **Restore ordering** — `pinCoordinator` wraps whatever `findCluster` is installed, so
  force first / unpin first. A test that tears down in the wrong order leaves a patched
  prototype behind for the rest of the file.
- **Prototype patches are process-wide within a vitest worker**, including any
  strand-network `Libp2pKeyPeerNetwork`. A harness party that also drives strand traffic
  must not hold a forced cohort while that traffic is live.
- **Addressless forced entries** — `forceFullCohort` already throws when a node has no
  multiaddrs, because an addressless entry surfaces downstream as a dial failure that
  looks exactly like an injected degradation. The widened version must keep that check for
  `TestCadreNode`s, whose addresses come from `node.getMultiaddrs()` after the ephemeral
  port is bound.
- **`waitForControlCohort` on a party with `droneCount: 0`** — must succeed trivially at
  `minPeers: 1` rather than deadlocking, and must reject `minPeers` greater than the
  party's node count with an immediate, clear error rather than a timeout.
- **Teardown after a timeout** — a scenario whose `waitForControlCohort` throws in
  `beforeAll` still has nodes running; the failure path must not leak listeners or ports
  (`releasePorts` in `shutdownTestParty`).
