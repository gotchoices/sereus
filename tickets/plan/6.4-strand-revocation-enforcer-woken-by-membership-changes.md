# The strand revocation enforcer wakes on a membership change

## Measured

GitHub #50's comment: two relay-only parties through relay.sereus.org, after a join, 120 s idle, both parties together. About 33 relayed `db-p2p/sync/1.0.0` requests per strand per two minutes, 83–98% of them within 2 s of a `deny set refreshed` log line, for `default/strand/Member`, `default/strand/MemberPeer` and two more blocks. On a Galaxy S7 it is the phone's main remaining idle traffic: about 8 inbound sync requests a minute per strand.

Why (traced this planning pass): each refresh scans `MemberPeer` and `Member`. Each scan reads the collection's header and log tail. A held block read more than 10 s after its last check starts one background `/sync` to every other cohort member (Optimystic lazy read repair, `readRepairWindowMs` 10 s, which Sereus does not set). Commits this node received as a cohort member do not refresh that window. So every 30 s refresh finds all four blocks stale and asks the other party about each. The "two tree blocks" in the comment are most likely the two log tails; check the block ids when re-measuring.

## Design

- Subscribe through `control-and-strand-table-change-subscription`'s strand wrapper to `Strand.Member` and `Strand.MemberPeer`. On a change, run `doRefresh`.
- Run once when the strand's database comes up, as today.
- Keep a backstop poll, default 5 minutes, through the existing `revocationEnforcement.pollIntervalMs`.
- The membership reconciler currently mirrors the enforcer's interval as its own idle cadence (`strand-instance-manager.ts` ~952-978). Give it its own default instead of inheriting the new 5-minute backstop by accident; it settles and stops on its own once joined, so its cap matters only while joining.

## Settled choices

- **The removal bound gets tighter, not looser.** A removal is a commit to `Member` / `MemberPeer`. On a two-party strand both members are in every block's cohort (strand cluster size 4), so the commit lands in this node's storage and wakes the enforcer at once, instead of up to 30 s later. The backstop covers a member that was offline when the removal was committed: its storage receives the blocks by join backfill or read repair on reconnect, which also raises the storage event. Update docs/strands.md where the 30 s bound is stated.
- **Do not widen `readRepairWindowMs` instead.** That would trade away how quickly a reader notices it missed a commit, for every read on the strand, to save a poller that should not be polling.

## Edge cases & interactions

- **Hibernation.** A hibernated strand has no database; on wake the enforcer is rebuilt with the retained launch config and must re-subscribe. Verify by reading `hibernation-manager.ts`'s rebuild path; the existing hibernation specs should cover the wake.
- **Open strands** have no enforcer, as today.
- **Strands larger than the cluster size,** where this node may not be in a membership block's cohort: the backstop is the only path. Note it at the backstop constant.
- **A burst of membership commits** during a join (Member, ConsumedInvite, MemberPeer) collapses into one refresh.
- **Many strands.** Today's cost grows linearly with strands held (#50 comment: 1 strand → 41 requests / 2 min, 3 strands → ~100). After this, an idle node's per-strand cost is the backstop only. `message-cost-accounting`'s idle arm should be run with 1 and 3 strands to show it.

## Tests

None new; the enforcer's existing specs cover deny-set logic and the seam's spec covers scheduling. Any spec that advances the 30 s timer to observe a removal must drive it by a membership commit instead.
