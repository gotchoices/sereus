## Context

The self-host user will not run `systemctl enable`. The package's value is "install and forget" — double-click an installer (or run a one-line command), and cadre-host registers itself as a system service that survives reboots, with a sensible default config, and points the user at the local UI to finish setup.

This ticket covers the installer on three platforms, the service-host registration that makes cadre-host survive reboots, and the update-at-launch check that notifies the user when a new version is available.

## Platforms and install targets

### Linux — systemd user unit (preferred) or system unit

- **User unit** (`~/.config/systemd/user/cadre-host.service`) when installed as a non-root user. `loginctl enable-linger <user>` so the service starts at boot without the user logging in. Lower-friction install (no `sudo` needed), better security posture (no root).
- **System unit** (`/etc/systemd/system/cadre-host.service`) when explicitly installed system-wide. Runs as a dedicated `cadre-host` user the installer creates.

Unit file:

- `Type=simple`
- `Restart=on-failure`, `RestartPreventExitStatus=0` (clean exit stays dead — matches the one-shot-shutdown design)
- `ExecStart=/usr/bin/node /opt/cadre-host/dist/bin/host.js start --no-tui`
- Standard hardening: `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome=read-only` (with explicit `ReadWritePaths` for the data dir).
- `Environment=NODE_ENV=production`.

### macOS — launchd LaunchAgent (preferred) or LaunchDaemon

- **LaunchAgent** (`~/Library/LaunchAgents/com.serfab.cadre-host.plist`) for per-user install. Runs when the user is logged in.
- **LaunchDaemon** (`/Library/LaunchDaemons/com.serfab.cadre-host.plist`) for system-wide. Requires admin install.

Plist:

- `Label`: `com.serfab.cadre-host`
- `RunAtLoad=true`, `KeepAlive` omitted (clean exit stays dead).
- `ProgramArguments`: node + path-to-bin + `start --no-tui`.
- `StandardOutPath` / `StandardErrorPath` to a log dir under the user's Library or `/var/log/`.

### Windows — NSSM-installed Service

- Bundle NSSM (`nssm.exe`) with the installer.
- Install command: `nssm install CadreHost <node-path> <bin-path> start --no-tui`.
- `nssm set CadreHost AppExit 0 Exit` — clean exit doesn't restart.
- `nssm set CadreHost AppExit Default Restart` — failures do restart.
- `nssm set CadreHost AppThrottle 5000` — avoid restart loops.
- `nssm set CadreHost Start SERVICE_AUTO_START` — start at boot.
- Service runs as `LocalSystem` for v1; a dedicated user account is a follow-up.

Native `sc.exe` services don't auto-restart on clean exit by default but their exit-code handling is less expressive than NSSM's. NSSM is the standard wrapper for Node services on Windows.

## Installer flow

### Acquisition

Three distribution channels, all in scope (decided at plan stage how many ship for v1):

1. **npm**: `npm install -g @serfab/cadre-host && cadre-host install`. Works for users with Node already installed. Lowest-friction for technical users.
2. **Standalone installer**: pre-packaged binary using `pkg`, `nexe`, or `node-sea` (Node's experimental single-executable feature). Includes a Node runtime; user doesn't need Node installed. The right answer for non-technical users.
3. **Platform installer**: `.deb` / `.rpm` / `.pkg` / `.msi`. Highest polish, most work to maintain. Probably out of scope for v1; the standalone installer covers the gap.

### Interactive setup wizard

On first run (`cadre-host install`), the installer wizard:

1. Detects platform and chooses appropriate service-host integration.
2. Asks where to install (default: platform-appropriate, e.g. `/opt/cadre-host`, `~/Library/Application Support/CadreHost`, `%LocalAppData%\CadreHost`).
3. Asks where to store data (default: nested under install dir or in a platform-conventional location).
4. Asks for a starter config:
   - Port to listen on (default 4001).
   - Whether to attempt UPnP (default yes).
   - DDNS provider (optional — can skip and configure in UI later).
5. Generates the host's cadre node identity (Ed25519 keypair via cadre-core).
6. Registers the service with the platform's service host.
7. Starts the service.
8. Opens `http://localhost:<ui-port>` in the default browser to land the user on the local UI for finish-setup.
9. Displays an enrollment invite (QR + token) so the user can immediately enroll their phone (resolves the trust-circle chicken-and-egg from `cadre-host-trust-circle`).

### Non-interactive install

`cadre-host install --non-interactive --config <path>` for scripted deploys, CI, and recovery. All wizard prompts have config-file equivalents.

### Uninstall

`cadre-host uninstall`:

- Stops the service.
- Unregisters from the platform service host.
- Optionally removes data dir (prompt; default no — don't lose user's trust circle and cadre identity on a fat-fingered uninstall).
- Removes binaries.

## Update-at-launch

On every `cadre-host start` (i.e. every service start, including boot), before binding ports:

1. Check for a new version. Mechanism: a single HTTP GET to a sereus-owned manifest endpoint (`https://releases.serfab.io/cadre-host/latest.json` or similar — endpoint owner decides at plan stage). Manifest includes latest version, download URL, signature, optional release notes.
2. Compare with current `package.json` version.
3. If newer:
   - Write an "update available" record to the store.
   - Log a notice.
   - Continue startup as normal — do not auto-apply, do not block on the network call (5-second timeout, treat failure as "no update available").
4. Local UI reads the record and surfaces a "Version X available — Update now" banner.
5. User clicks "Update now" → cadre-host downloads the new package, verifies signature, runs platform-appropriate update procedure (npm-installed: `npm install -g`; standalone: download replacement binary to a side path, register pending-swap, restart service which swaps and starts the new binary).
6. Failed update: rollback to previous version, surface error in UI. The basement PC must not be bricked by a failed update.

### Why notify, not auto-apply

A bad update on a headless basement machine is hard to recover from. The user must consent to apply, even if they consent once and we record "always auto-update" for future versions. Default is notify; auto-apply is an opt-in setting in the local UI.

### Signature verification

Update manifests and download artifacts are signed by a sereus release key. The installer ships the public key embedded. Mismatched signature → refuse to apply, surface error. Standard supply-chain hygiene; no novel cryptography.

## Constraints & considerations

- **Privilege escalation**: the user-unit / LaunchAgent / per-user install paths avoid root/admin for v1. System-wide install paths exist but require explicit `--system` flag and elevated invocation. The installer fails fast and tells the user how to re-run with elevation rather than auto-elevating.
- **Bundled Node**: standalone installer needs a Node runtime. `node-sea` is the future (built-in to Node 20+); `pkg` is mature but Vercel deprecated it; `nexe` is alive but smaller community. Plan-stage decision; my lean is `node-sea` if Node 22 is acceptable as the minimum, else `pkg` fork.
- **Firewall prompts**: Windows will prompt for firewall access on first run of a service binding a network port. NSSM service install can pre-add the firewall rule via `netsh advfirewall`. Linux `iptables` / `firewalld` we leave alone — most desktop distros don't have host firewall on by default; document for users who do. macOS firewall is opt-in and prompts; user handles.
- **Antivirus heuristics**: pre-packaged Node binaries get flagged by Windows Defender heuristics sometimes. Code-signing the executable (Authenticode) helps; budget for a code-signing cert.
- **CI for cross-platform builds**: producing standalone installers for three platforms means cross-platform CI jobs (or matrix builds). Likely uses the same CI that builds the docker images today — coordinate with `6-ci-pipeline-maestro`.
- **Data-dir migration on upgrade**: if a future version changes the on-disk format, the update flow must run a migration before swapping binaries. Out of scope for v1 (no migrations yet) but design with the hook in mind.
- **Service-host integration shares unit-file design with the one-shot-shutdown ticket** (`5-provider-one-shot-shutdown`). Both want `Restart=on-failure` / equivalents. The unit files in this ticket and in that one should be consistent; one set may be generated from a shared template.
