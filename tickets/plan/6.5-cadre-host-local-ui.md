## Context

The self-host user won't `curl` an API, edit YAML, or read logs. They need a small, polished surface for the four things they actually do:

1. Confirm "is it running" at a glance.
2. Generate and share invite codes.
3. See and resolve NAT/connectivity issues.
4. Approve updates when available.

Anything beyond those four is secondary — and most of cadre-host's surface area is *not* user-facing (the orchestrator, the auth layer, the NAT detection all do their job in the background). The UI exists to make the cases where the user *does* need to act obvious and tractable.

## Surface

### Localhost web UI

The primary surface. Cadre-host's process binds a Fastify server on `http://127.0.0.1:<ui-port>` (default 8765, configurable, never on `0.0.0.0`). Serves a small SPA that talks to the management API on the same origin.

Constraints:

- **Localhost-only listener**. Origin check on every request. No mDNS or LAN exposure; the UI is for the machine's local user, not for remote management. Friends interact via the cadre P2P protocol, not via this UI.
- **No login**. Same-machine access is the auth. (A future SSH-tunnel use case might want a different model; out of scope.)
- **Server-rendered or SPA, plan stage decides**. The page count is small (4-5 views). A small SPA (React / Solid / Svelte) is fine; vanilla HTML+HTMX is also fine. The decision criterion is "what's the lightest thing that gets us a good experience" — not bundler theatrics. If the rest of the monorepo standardizes on a framework already used elsewhere, prefer that for consistency.
- **No external CDNs at runtime**. Assets ship with the package. The basement PC may not have great connectivity; the UI must work even if the cadre node is the only network path that's failing.

### Pages

1. **Home / Status**
   - "Cadre-host is running" indicator (green/yellow/red).
   - Cadre nodes managed by this host — count, status badge per node (running, restarting, stopped).
   - Trust circle size, last-seen times.
   - Connectivity status (port-forward, DDNS, external IP).
   - Update banner if a new version is available.

2. **Trust Circle**
   - List of members with labels, status, last-seen.
   - "Invite a friend" button → modal with label input → generates invite, displays QR + copyable token + expiry.
   - Per-member: remove, re-label.

3. **Connectivity** (the NAT/DDNS panel)
   - Port-forward status with diagnostic info (UPnP / manual / failed / relay).
   - DDNS provider, hostname, last update.
   - "Test reachability" button (runs libp2p AutoNAT probe).
   - Manual setup instructions if needed.

4. **Nodes**
   - Per-node detail: party, profile (storage/transaction), resource usage (CPU/RAM from `pidusage`), recent logs (tail of `node.log`).
   - Start / stop / restart controls (gated by "are you sure" for stop).
   - Add a new cadre node (when the user joins another party) — minimal form, mostly delegates to cadre-core's enrollment.

5. **Settings**
   - Update preference (notify-and-prompt vs auto-apply).
   - DDNS provider configuration.
   - Data directory (read-only display, "open in file manager" button).
   - Uninstall instructions.

### Tray icon (optional, plan-stage decides whether v1)

A system tray icon (Win/macOS/Linux) showing running/stopped status with a context menu: "Open dashboard", "Status", "Quit cadre-host" (which sends a clean shutdown).

Tray on Linux is messy (depends on desktop environment, libappindicator, etc.). Tray on Windows and macOS is straightforward via Electron, but pulling in Electron just for a tray is a 100MB hammer. Alternatives:

- **`systray2`** / **`@cretueusebiu/node-tray`** — small native modules, cross-platform, no Electron.
- **Defer the tray to v2** and ship only the web UI + a "browser-bookmark to localhost" instruction in v1.

My lean is **defer to v2**. The web UI plus the installer-opens-browser-on-finish covers the discoverability case; a tray icon is polish that doesn't unlock new behaviour. If we ship it, use a non-Electron native module.

## Management API

Backend that the local UI calls. Fastify on the localhost-only listener. Endpoints (sketch):

- `GET /api/status` — overall health.
- `GET /api/nodes` — list cadre nodes the host manages.
- `GET /api/nodes/:id` — detail including stats and recent log tail.
- `POST /api/nodes/:id/start` / `/stop` / `/restart`.
- `GET /api/trust-circle` — members.
- `POST /api/trust-circle/invite` — generates invite, returns token + QR data URL.
- `DELETE /api/trust-circle/:peerId` — revoke.
- `GET /api/connectivity` — NAT/DDNS state.
- `POST /api/connectivity/test` — kick AutoNAT probe.
- `GET /api/connectivity/ddns/providers` — list available DDNS providers.
- `PUT /api/connectivity/ddns` — set provider + credentials.
- `GET /api/update` — current version + available version.
- `POST /api/update/apply` — trigger update flow.
- `GET /api/settings` / `PUT /api/settings`.

All return JSON. All localhost-only. Errors follow a shape compatible with cadre-provider's `{ ok: false, error: { code, message } }` for consistency.

## Design notes

- **Reactive status without polling**: the status page should update live. Server-Sent Events from the management API is the simplest fit (one-way push, no WebSocket complexity, works through any proxy). Push events: node-state-changed, trust-circle-changed, connectivity-changed, update-available.
- **No accounts, no roles**: there's exactly one user (the host machine's user). All controls are unguarded except destructive ones (remove member, stop node, uninstall), which prompt for confirmation.
- **Errors must be specific**: when something fails ("can't reach router for UPnP", "DDNS update failed: invalid token"), the UI shows what failed and what to try. Generic "something went wrong" is a regression.
- **Logs view**: tail-and-follow on the selected node's log file. Filtering is nice-to-have, not v1. Download-as-text for sending to support.
- **Accessibility**: standard semantic HTML, keyboard navigation, decent contrast. Not WCAG-AA-audited for v1 but should be respectable.
- **Bundle size**: under 1 MB of JS+CSS gzipped is the target. The page count is tiny; modern frameworks easily fit if used judiciously.

## Use cases

1. User opens the dashboard after install, sees green "running" indicator, copies the invite QR, sends it to their brother.
2. User notices "Connectivity: relay-only" in the status bar, clicks through to Connectivity page, sees "your router rejected UPnP — open port 4001 in router admin", follows the link to their router's vendor instructions.
3. New version banner appears one morning; user clicks "Update", waits 30 seconds, sees "Updated to 0.7.0" and the cadre nodes are back up.
4. A friend's phone goes offline for a week; user opens Trust Circle page, sees "Brother's phone — last seen 7 days ago", decides whether to remove or leave it.
5. User wants to participate in a new party; clicks "Add cadre node" on the Nodes page, follows the cadre-core enrollment flow, ends up with a second node listed under "Nodes".

## Non-goals

- Remote management (mobile app for managing the basement PC over the internet). The mobile app *is* a cadre node in the trust circle; it consumes the host's resources, it doesn't manage cadre-host itself. Remote management is a follow-up if a real demand surfaces.
- Multi-host management ("my basement PC and my parents' basement PC"). Each cadre-host has its own UI; coordinating across them is out of scope.
- Theming, dark mode, customization beyond what comes for free from system-color-scheme media queries.
- Plugin / extension surface. Cadre-host's UI is closed-set for v1.

## Constraints & considerations

- **UI port collision**: 8765 is unlikely to collide but not guaranteed. Fallback: try the configured port, then a small range, persist whichever worked, mention in the install summary.
- **Browser auto-open**: works via `open` (npm) on first install, the user navigates manually thereafter. Keep a `cadre-host ui` CLI shortcut that prints + opens the URL.
- **Cross-package code reuse**: the management API's error shape and JSON conventions should mirror cadre-provider's where they overlap. Don't extract a "shared HTTP utils" package on day one — fold the convention in via copy + lint, factor later if duplication grows.
- **Security review** before public release: even though the listener is localhost-only, a malicious local process could hit it. The trust-circle ticket gives us a peer-identity model for friends; for the local UI itself, document the threat model (any process on the host can fully control cadre-host) and the mitigation (don't run untrusted code on the host PC — same trust assumption as the rest of the user's OS-level apps).
