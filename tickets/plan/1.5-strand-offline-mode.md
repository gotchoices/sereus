## What upstream offers

From `../optimystic/packages/quereus-plugin-optimystic/README.md` → "Offline mode" (read the whole section and `docs/offline-sync.md`):

- **Registration.** An `offline` register option holds `journal` (an `IKVStore`, or a function returning one, where queued transactions are saved; default memory only, and a `MemoryKVStore` is refused), `journalLabel` (required with a journal; two `Database`s over one store need two labels), `networkCommitTimeoutMs` and others. An unknown key is refused at `register`.
- **The controller, `plugin.offline`.** `enter()` and `exit()`; the acknowledgement is fixed when a transaction begins. `whenDrained()`, `onStatus(listener)` per transaction, `onQueueState(listener)` and `queueState()` for a status bar (`readsServedLocally` included), `entries()`, `status(id)`, `discard(id)`.
- **Restart.** `plugin.hydrate(db)` puts saved transactions back in the queue before it resolves, so the first statement sees their rows. `OfflineJournalError` stops the restore when a record comes from a newer build.
- **Tables.** A `"optimystic.offline" = 'network'` tag keeps a table network-acknowledged, in the mode and out of it. A transaction writing any such table is network-acknowledged as a whole. DDL that changes how a table's rows are stored is refused while queued transactions wrote that table (`QueuedEntriesBlockSchemaChangeError`).
- **Reads.** In offline mode, a read the other machines cannot answer is served from this machine's copy. Rows the machine never held still fail with `BlockUnavailableError`.
- **Outlook.** Each queued transaction reports whether another writer could make it fail (`CommitOutlook()` in SQL, `dependsOn`, `kind`). Two tags and generated ids (`StampId()`) make a transaction "assured".
- **Sending.** The queue sends only when the block's cohort is reachable (`cohort-reachability` in db-p2p). Each send sets the solo-refusal option, so a queued transaction is never committed by this node alone while it knows members are missing.

## Questions the plan must settle

Each has a recommended default. Settle it by research, or route it to `blocked/` with proposed text if the specification is silent and the choice matters.

1. **Which databases.** Recommended: strand databases composed by `composeStrand` only. The cadre control database (`control-database.ts`) never enters offline mode, because its writes are owner-signed membership and authorization facts whose retry and veto rules (`control-write-retry.ts`) assume a network answer. Always-on nodes (cadre-host, cadre-provider, cadre-cli) gain nothing and do not configure it.
2. **Sereus's own strand tables.** `schemas/strand.qsql` defines the `Strand` schema (`Header`, `Member`, `Manager`, `MemberPeer`, and the others), which the membership reconciler, revocation enforcer and formation write. Recommended: tag them `'network'`, so membership changes are never acknowledged locally and later refused. Check every Sereus writer of those tables against the "a transaction writing any `'network'` table is network-acknowledged as a whole" rule, and against `OfflineCommitTimeoutError` (a network commit waits behind the queue).
3. **The existing "commit alone" rule.** `docs/strands.md` → "Writable does not mean connected" says a strand write with no peer connected commits with a cohort of only this machine and succeeds. Offline mode does the opposite for queued transactions: it holds them until the cohort is reachable and refuses a lone commit. Decide how the two rules sit together. Recommended: outside offline mode nothing changes; in offline mode the queue's rule applies to queued transactions. Rewrite that section of the doc to state both.
4. **Who enters the mode.** Recommended: the app decides, through the strand handle Sereus gives it. Sereus does not toggle the mode from connectivity, because the mode changes what a successful commit promises. Sereus exposes `plugin.offline` (or a typed subset) per strand from `StrandInstance` and the cadre-rn kit, along with the status and queue-state events. Decide whether the kit offers a default (for example, "always offline-acknowledged") for apps that want it on all the time.
5. **Journal per platform.** RN: `@optimystic/db-p2p-storage-rn`'s store. Web: the IndexedDB store from `db-p2p-storage-web`. Node and NativeScript: decide whether to support them now or leave them in-memory with a refusal. Recommended `journalLabel`: derived from the strand id, so one store can hold several strands. Check whether the strand's existing kv store can be reused (upstream keys sit under `optimystic-offline/`, which is in `NODE_KV_NAMESPACES`).
6. **Startup order.** `hydrate` must finish before the app's first statement. Check that `composeStrand`'s current `hydrate` call (~332), the first-sync gate (`docs/strands.md` ~234) and publication of `StrandInstance.database` keep that order. Decide what a restored queue means for the gate. A machine with queued writes has synced before by definition.
7. **App schema changes.** An sApp schema upgrade applied at connect can hit `QueuedEntriesBlockSchemaChangeError` while transactions are queued. Decide whether connect waits for `whenDrained()`, refuses the upgrade with a named error, or applies only the storage-neutral parts.
8. **Reactivity.** Sereus's table watches and strand reactivity must report a queued transaction's rows, and their removal when the network refuses one (upstream announces removals to live queries). Confirm this happens without Sereus changes, or name the change needed.

## Reference apps

`reference-app-rn` and `reference-app-web` show the feature: an offline toggle, a queue status line (`onQueueState`), each queued transaction's status, and a discard action. Keep it small. These apps are how embedders learn the API.

## Edge cases & interactions

The plan carries these into each implement ticket, with how each is verified:

- Restart with a non-empty journal; restart right after the network accepted an entry (upstream guarantees it is sent once; confirm it through Sereus's composition).
- A refused queued transaction: the app is told, its rows disappear from reads and watches, and transactions that depended on it fail with it.
- Leaving a strand (`forgetJoinedStrand`/`stopStrand`) with a non-empty queue: what happens to the journal records. Recommended: refuse, or require an explicit discard, rather than delete silently.
- Strand moved between cadres, and hibernation and resume (cadre-rn) with a queue.
- Two strands on one device sharing a journal store (labels).
- A `'network'` Sereus table written in the same transaction as app tables.
- Mixed versions: a 1.19 member receiving a queued send from a 1.20 phone. This is ordinary commit traffic, so confirm with the adoption ticket's mixed-version notes.

## Tests

One real-network integration scenario earns its cost: a phone-shaped node in offline mode writes while its only partner is stopped, restarts, then the partner returns and the row lands on it exactly once. Add others only where the plan finds branching that Sereus itself owns (for example, the schema-upgrade decision in question 7).
