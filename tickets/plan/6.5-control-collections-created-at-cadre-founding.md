# Every control table has a collection from the cadre's founding

## Why

A table nobody has written has no collection. Optimystic keeps no memo of an absence, so whether the collection exists is a question for the whole cohort on every read (sereus#47 measured this on strands; `strand-founder-commits-every-table-collection` fixed it there by committing every declared table's empty collection at founding). The control database has the same problem once the cadre has a second machine:

- `JoinedStrand` is read by the strand watcher every 5 s, and on a party that never joined another party's strand it is never written.
- The pending-join tables (`JoinRequest`, `JoinSuccess`, `JoinFailure`) are read every 30 s and are usually never written.
- `Revocation` is read before nearly every membership read; the ledger marker (`openRevocationLedger`) exists only to give it a collection, and is filed late (owner's first connected reconcile pass).
- `FormationUsage` is counted 2–4 times on a party's first strand formation.

On a single-machine party these reads are local (a cohort of one answers alone). With two machines each is a consult of the sibling, and a sibling that is offline makes them fail or wait.

## Design

- At cadre founding (genesis, on the founding machine only), after the control schema is applied, commit an empty collection for every control table and index tree, using `createEmptyCollections` from `quereus-plugin-sereus` (the same helper strand founding uses).
- Do it before the first connection, so the collections reach a joining machine with the founder's first catch-up push.
- If the `Revocation` ledger marker becomes redundant (its only purpose was to make that collection exist), remove it and its filing path. If something else reads the marker row, keep it but file it in genesis. Decide by reading `openRevocationLedger`'s callers.
- Existing cadres: a cadre founded before this has no such collections. Control schema changes already go through `control-store-migrates-on-start` (in implement/). Do not add a separate path; either the migration step creates missing collections when it runs, or existing cadres keep today's behaviour. Pick by reading that ticket; no backwards compatibility is owed yet (AGENTS.md).

## Edge cases & interactions

- **Two machines founding independently** cannot happen for one party (a party has one genesis). Verify by reading genesis.
- **Cost at founding.** Strand founding measured about 23 ms and ~25 storage operations per empty collection, each its own commit (`empty-collections.ts` syncs them one at a time). The control schema has about 17 tables and 3 indexes plus unique-enforcement trees. That is local work on a solo founder, no messages. `control-start-storage-op-budget.spec.ts` and `control-founding-consult-budget.spec.ts` will move; re-pin them with their `MEASURED_ON` dates.
- **Batching the empty commits** is `blocked/optimystic-empty-collections-commit-in-one-batch` if filed by `strand-founding-writes-batched`; do not build a private batching path here.
- **Tables added by a later control schema version** have the same gap; that is the control analogue of `backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`. Mention it there rather than solving it here.
