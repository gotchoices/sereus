files: packages/cadre-core/src/schema-verification.ts, packages/cadre-core/src/types.ts, packages/cadre-core/src/strand-instance-manager.ts, packages/integration-tests/src/scenarios/strand-formation-e2e.integration.ts

Sereus's stated security goal is that ed25519-signed sApp schemas gate strand join: before a node allocates resources or applies schema DDL for a strand, the schema's signature is verified against the author's public key so that a strand cannot be formed or joined under an unauthorized or tampered schema. This was the intent of the completed `3-app-schema-verification` work, which added `signSchema()`, `verifySchema()`, and `assertSchemaSignature()` and wired `assertSchemaSignature(sAppConfig)` into `StrandInstanceManager.startStrand()` ahead of any resource allocation.

The gate as implemented does not deliver that guarantee, because it is opt-in rather than required. `assertSchemaSignature` silently returns success when no signature is present: if `sAppConfig.signature` is falsy it logs "skipping verification" and returns without error (`packages/cadre-core/src/schema-verification.ts:70-85`). The `SAppConfig.signature` field is itself declared optional and documented as "omit to skip verification" (`packages/cadre-core/src/types.ts:257`). Consequently a strand config with no signature — whether supplied by a malicious actor or simply assembled carelessly — passes the gate unconditionally. Since `startStrand` has no policy or flag that requires a signature to be present, there is no configuration under which the verification step can be relied upon to reject an unsigned schema. The gate therefore protects only against tampering of configs that *happen* to be signed, not against the absence of a signature, which undermines the schema-gates-join property the feature was meant to provide.

The negative path is also uncovered at the integration level. Every `addStrand`/`startStrand` caller in the integration scenarios supplies a correctly-signed config, and no scenario feeds a tampered, unsigned, or wrong-key `SAppConfig` through strand creation or join to assert that it is rejected (`packages/integration-tests/src/scenarios/strand-formation-e2e.integration.ts` and adjacent scenarios). The existing unit and `strand-instance-manager` tests cover tampered-schema and wrong-key rejection for signed configs, but nothing exercises the unsigned-config bypass or asserts an enforced-signature policy end to end.

Expected behavior: introduce an explicit policy controlling whether signed sApp schemas are required, surfaced as configuration on the node/strand manager (for example a `requireSignedSchemas` policy flag) that defaults to enforcing signatures outside of development contexts and may be relaxed only for explicit dev/test use. Under the enforcing policy, `assertSchemaSignature` (or its caller in `startStrand`) must reject a config whose `signature` is absent — not merely log and continue — so that an unsigned schema cannot gate-pass. The distinction between "no signature provided" and "invalid signature" should remain in the error/diagnostic surface (`SchemaVerificationError` already carries `sAppId` and `version`), but both must fail closed when the policy requires signing. The optionality and the "omit to skip verification" semantics of `SAppConfig.signature` should be reconciled with the policy so the type and its documentation no longer imply that skipping is a generally safe default.

Use case: a node configured for production receives (or is asked to form) a strand whose `SAppConfig` carries a schema with no signature, a signature over a different schema/version, or a signature from a key other than `sAppConfig.id`. In all three cases strand creation/join must be refused before any libp2p node or schema DDL is brought up, and the refusal must be observable to the operator. The integration suite should grow negative-path coverage that drives each of these three cases (unsigned, tampered, wrong-key) through the real creation/join path and asserts rejection, complementing the existing unit-level coverage in `packages/cadre-core/test/schema-verification.spec.ts` and `strand-instance-manager.spec.ts`.
