----
description: Update service ships an all-zeros release public key, rejecting every real signed manifest
files: packages/cadre-host/src/update/release-key.ts, packages/cadre-host/src/update/manifest.ts, packages/cadre-host/src/update/index.ts
----
The cadre-host update subsystem verifies signed release manifests against an embedded Ed25519 production public key, but the key that ships in the binary is a placeholder consisting of 32 zero bytes. As a result the entire notify/auto-apply update flow is non-operational in shipped binaries: any genuinely-signed production manifest is rejected.

`release-key.ts` defines `PROD_KEY_BASE64 = 'AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA='` (all-zero 32-byte raw Ed25519 key, see `packages/cadre-host/src/update/release-key.ts:25`). `verifyManifest` uses this key for the Ed25519 signature check of the signed manifest (`packages/cadre-host/src/update/manifest.ts:88-101`). The check fails safe — `crypto.verify()` returns `false` for any real signature against the zero key — but the consequence is that every authentic production manifest is rejected with `signature_invalid`.

This makes the notify-by-default and auto-apply update flow described in `docs/cadre-host.md` unusable in a shipped binary. Only the `CADRE_HOST_UPDATE_DEV_KEY` env override path functions, which is intended for development and CI smoke tests rather than production. The auto-apply path is gated on a `check()` that can never pass for real manifests (`packages/cadre-host/src/update/index.ts:199-206`), so a shipped binary will never auto-apply or even surface a verifiable update. The update flow is therefore a named subsystem that is effectively non-operational until a real release key and a signing pipeline land.

This was explicitly deferred from the update-flow hardening work, which notes the placeholder `PROD_KEY_BASE64` is the release-operator's responsibility and is tracked separately (see `tickets/complete/cadre-host-update-flow-hardening.md`). It is distinct from OS-level binary code-signing (signtool/codesign/notarytool/GPG) tracked in `tickets/backlog/later/cadre-host-standalone-binary.md`; this ticket concerns the Ed25519 release-manifest signing key only.

Expected behavior: a real production Ed25519 release public key is generated, kept offline with the release operator, and embedded in the shipped binary so that authentically-signed manifests verify and the notify/auto-apply flow operates as documented. This requires a supporting key-management and manifest-signing pipeline: key generation and rotation procedure, secure custody of the private signing half, the signing step that produces the manifest signature consumed by `verifyManifest`, and atomic replacement of the embedded public key by the release build. The `CADRE_HOST_UPDATE_DEV_KEY` override must remain available for development and CI but must not be relied upon as the production verification path.
