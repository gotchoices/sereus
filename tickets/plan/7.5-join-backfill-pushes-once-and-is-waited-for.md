# Join backfill pushes each block once, and the joiner waits for it

## Measured and traced

- `message-cost-accounting` baseline, strand case, settle window after the join: 44 `block-transfer` streams A→B and 38 `sync` B→A; cadre-invite case: 17 `block-transfer` A→B in settle, plus 2 each way during redemption.
- GitHub Optimystic#39 comment: a `blocks=33 reason=replication` push appears twice per join, and one took 8 s to cross the public relay, stalling the attach's other requests behind it.
- Traced (this pass): every upstream pusher sends one block per request, so a 33-block frame is Sereus's `PeerJoinBackfill`. A peer is memoized as caught up only after a clean run. Any rejected block (the receiver's default `requirePushCertificate` refuses a block without a retained proof), or a reply that misses its deadline, leaves the peer un-memoized, and the next `peer:identify` (identify-push fires on any address or protocol change) re-pushes everything. On the control network, `forceCatchUpPeer` ignores the memo, and every membership refresh re-schedules peers not yet caught up. The joiner, once it holds blocks, pushes them all back to the founder. On storage-profile nodes Optimystic's rebalance growth arm pushes the same blocks again, one per request, because the backfill's success never reaches the sender's holder tracking.

## Design

1. **Per-block memo per peer.** Remember which blocks (id and revision) a peer has accepted. A rerun pushes only blocks not accepted. A rejected block is a per-block verdict: log it, do not retry it on every identify, retry it only if its revision changes.
2. **Do not push back what came from that peer.** A block received from peer P (by push or fetch) is not pushed to P.
3. **`forceCatchUpPeer` respects the per-block memo.** It forces a run, not a resend of accepted blocks.
4. **Permission check from the in-memory member list,** not a membership-table read per run (`cadre-node.ts` ~2112).
5. **The joiner waits for the push.** Push on first contact, not after the 1 s debounce, when the peer is new to this strand. The gate (`first-sync-gate-probes-cheaply`) then wakes on arrival instead of fetching block by block.
6. **Rebalance duplicate.** Decide between passing `rebalance: { enabled: false }` on strand nodes whose cohort is the whole membership (two-party strands), and reporting the missing holder-recording hook upstream. Prefer the config if it costs nothing else (read what else the growth arm does); otherwise file it in `blocked/` with the measurement.

## Dependencies

On Node hosts with file storage, `FileRawStorage.listBlockIds` never lists a block id containing `/`, which is every collection header (gotchoices/Optimystic#41, fixed on Optimystic main, unreleased). Backfill enumerates the store with `listBlockIds`, so on those hosts the push carries no headers and the joiner fetches them anyway. Item 5's saving on Node depends on that fix being released; the in-memory and phone storages are unaffected. Record which storages were measured.

## Edge cases & interactions

- **A push larger than one chunk** (64 blocks / 1 MiB): the memo is per block, so a partial run resumes where it stopped.
- **The peer's store is wiped** (reinstall, new store under the same peer id). The memo would wrongly skip blocks. Key the memo by the peer's store identity if one exists, or drop the memo when the peer reconnects after a restart; read what identifies a store today.
- **Memo growth.** Bounded by blocks × peers; for a large strand cap it or keep only revisions of the strand's log tails. Note the bound.
- **A slow relay.** One whole-store push can occupy the relayed path for seconds (the 8 s case above). Smaller, memoized pushes reduce that; do not add concurrency to pushes.
- **Control network vs strand network.** Both use `PeerJoinBackfill`; the control network's 250 ms debounce and forced catch-up differ. Cover both.

## Tests

One spec over the memo's branching (accepted blocks are not resent; a rejected block is not retried until its revision changes; blocks received from the peer are not pushed back) at the `PeerJoinBackfill` level with an in-memory store.
