## What landed

### The view (`membership-view.ts`)

`MembershipView<Row>` holds one table's rows, the time the load that produced them started, a generation counter and the in-flight load per `retry` flag.

- `read(retry)` serves installed rows younger than `MEMBERSHIP_VIEW_MAX_AGE_MS`; otherwise it joins the in-flight load with the same `retry` flag or starts one. A `retry: false` caller (under the write lock) therefore never awaits a retrying load's backoff.
- A finished load installs only if its loader said `installable` and the generation has not moved since it started. Its own callers get its rows either way. A failed load installs nothing and rejects.
- `invalidate()` bumps the generation, drops the rows and forgets the in-flight loads. It is synchronous and only sets fields, because the watch handler calls it inside the committing call.
- `readThrough(retry)` runs the loader without serving, joining or installing (the bypass below).
- `MEMBERSHIP_VIEW_MAX_AGE_MS = DEFAULT_CONTROL_COHORT_RECONCILE_MS` (15 s), with a `NOTE:` naming the two cases it bounds (a machine outside the block's cohort; a machine that was offline when a sibling committed) and saying that lengthening the reconcile interval lengthens it too.

### Wiring in `ControlDatabase`

- Three views (`revocationView`, `cadrePeerView`, `ownerKeyView`), each loaded by one full-table scan (`*_SELECT_SQL`) through the existing read funnel. The `CadrePeer` scan keeps the `select PeerId, Multiaddr, StampId` prefix the read-retry spec rigs, and the `Revocation` scan contains `from CadreControl.Revocation`.
- `readRowsOnce` now returns `{ rows, committed }` (`RoutedRead`); `readRowsRouted` carries that out of the retry loop, and `readRows` keeps its signature. The loader reports `installable: !committed`, so rows served by the committed-read path are never kept.
- `readMembershipRows(view, retry)` reads SQL directly (`readThrough`) when `retry` is false and an explicit transaction is open (`!getAutocommit()`), otherwise reads the view.
- `initialize()` empties the views first and, after the schema is applied and just before `initialized` is set, subscribes once to the three tables through `tableWatches.watch(...)` with a no-op run and an `onInvalidate` that maps the qualified name to its view. No backstop. `close()` disposes it with the registry and empties the views after its second `disposeAll()`, so a load still in flight then cannot install.
- Readers: `queryRevokedStamps` filters the `Revocation` rows by `TableName`; `queryRevocations` maps them minus the ledger marker; `queryCadrePeers`, `queryOwnerKeyRows` / `getOwnerKeys` read their views and still call `this.queryRevokedStamps(...)` for the retired set (specs interpose there); `queryPeerRecord` finds the row in the `CadrePeer` view instead of a point read. Results are fresh objects on every call.
- The cohort-unreachable rule moved to `readRevocationRowsOrNone` (formerly `readRevokedStampRows`), around the view read; the empty answer is not installed because the failed load installs nothing. `queryRevocations` still throws. The accepted-tradeoff NOTE stays with the rule.

### Choices that differ from the plan

- **No separate `clear()`.** `invalidate()` already forgets in-flight loads (a load from an older generation can never be joined again), so `clear()` would have been the same method. `initialize()` and `close()` call `invalidate()` on every view.
- **Clock is `performance.now()`**, not `Date.now()`: monotonic, so a wall-clock step backward cannot stretch the maximum age. `performance.now()` is already used in `initialize()` on every platform.
- **`loadedAt` is when the load started**, not when it installed, so the age bounds how old the rows can be.
- **The maximum age follows the default reconcile constant, not a node's configured `controlCohort.reconcileMs`.** That is what the plan specified; a node configured with a longer interval keeps the 15 s bound.
- **The subscription is taken before `initialized = true`**, through the registry directly rather than `watchTables` (which calls `ensureInitialized`), so a throw there leaves the database uninitialized instead of half-initialized.

## Notes for the reviewer (once it reaches review)

- An unlocked read while a locked write body runs takes the committed-read path, so its load is not kept; during write-heavy flows a cold view stays cold for unlocked readers until the bodies finish. The rule is conservative: such rows would be safe to keep once the table is fully initialized, but this layer cannot see that. Revisit if the message-cost measurement shows membership reads during writes still dominating.
- The membership-gate refresh passes `retry: false` on unlocked triggers too (the NOTE in `readRowsRouted`), so when another writer's explicit transaction is open it takes the bypass: correct rows, no saving.
- `queryPeerRecord` now scans the `CadrePeer` rows in memory instead of a primary-key point read. The table is bounded by the party's machines.

## Why

Measured by `message-cost-accounting` (2026-10-19): an owner admitting a member read `CadreControl.Revocation` 24 times in a 362 ms phase; strand formation read it 14 times on the responder in 293 ms and 17 times on the joiner's first insert; an idle node reads it 24 times a minute. Every member-list or peer-record read reads `Revocation` first (to drop retired rows), and every flow calls several of them. On a single machine each read is local work. On a two-machine cadre every read of a held block past the 10 s read-repair window starts a background `sync` with the sibling, and every read of a never-written block consults the cohort, so repeated reads are repeated network requests.

Per-flow deduplication (passing rows between functions, as `queryOwnerKeyRows`' `retired` parameter does) fixes one flow at a time, and the repeats come from at least five flows. An in-memory view of the tables removes the whole class. `control-reconcile-woken-by-changes-reads-once` restructures the reconcile pass on top of this view; `formation-and-redemption-read-each-row-once` likewise reads through it.
