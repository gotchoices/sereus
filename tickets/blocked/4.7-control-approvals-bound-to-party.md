## What the implement stage changed

The implement commit is `ticket(implement): control-approvals-bound-to-party`.

**Field vector.** `controlAuthorizationFields(domain, action, partyId, rowFields)` returns `[domain, action, partyId, ...rowFields]`. `buildAuthorizationMessage` (control-database.ts) and the private `taggedDigest` (peer-authorization.ts) take the same required positional `partyId`. `unboundAuthorizationFields(domain, action, rowFields)` serves the two digests that carry no party; its `domain` is typed `UnboundControlDomain` (`'CadreControl.FormationUsage' | 'Cadre.Enrollment'`) and the bound builders take `BoundControlDomain` (everything else), so the type checker refuses a bound digest for `FormationUsage` and an unbound one for any other table.

**SQL.** Every `digest('CadreControl.<Table>', '<action>', ...)` in both schema copies has `party_id()` third, 28 digests per copy; the two `FormationUsage` digests (`'vouch'` and `'consent'`) are the only ones left alone, with the reason written once at `FormationUsage.Authorized`. The header comment states the rule.

**`party_id()`.** `registerPartyIdFunction(db, partyId)` registers a zero-argument, deterministic scalar on a Quereus `Database` returning the configured party id. `ControlDatabase.initialize` calls it right after the optimystic plugin registration and before `hydrate`, since a warm restart parses the persisted CHECK text. The `ControlDatabase` constructor throws on an empty or non-string `partyId`.

**TypeScript signers and verifiers.** `partyId` is the first parameter of every bound builder and verifier in peer-authorization.ts, of the peer-record and device-token sign/verify functions, and of the three cadre-invite message builders. `OwnerAnchorInputs` gained `partyId`. Every in-class `ControlDatabase` signer passes `this.config.partyId`; `cadre-node.ts` passes `this.partyId`; the invite protocol signs and verifies the reply with `invitation.partyId` after the existing party comparison, and the member verifies the request with its own party after its existing party check.

**Docs.** docs/architecture.md gained one paragraph after the control table list stating the binding, where the SQL reads the party from, the `FormationUsage` exception, and which specs pin it.

**Tests.** `control-schema-drift.spec.ts` pins that every digest in `CONTROL_SCHEMA` puts `party_id()` third except the two on `FormationUsage`, with an anti-vacuity count. `control-party-binding.spec.ts` (new) refuses an `OwnerKey` add, a `CadrePeer` voucher and a `Revocation` tombstone signed by the node's own founder for another party, by constraint name, then accepts the same row signed for the node's party. `peer-authorization.spec.ts` pins the reader-side verifiers the same way. `digest-variadic-parity.spec.ts` case (d) now quotes the schema's `party_id()` call verbatim against a bare `Database`. `peer-record.spec.ts` and `device-token.spec.ts` each gained an other-party negative.

**Checked, nothing found.**

- Every bound TypeScript signer passes the party of the database it writes to, and every verifier the party of the node that judges: the type checker proves arity, and reading each site proves the value (`this.config.partyId`, `this.partyId`, `invitation.partyId` after the party comparison, `this.options.partyId` after the request's party check). No signer reads the party from a replicated row or a wire frame without first comparing it to the local one.
- The two unbound digests are exactly the two the plan named, and the type split (`BoundControlDomain` / `UnboundControlDomain`) makes a third unbound digest a compile error rather than a review item.
- `registerPartyIdFunction` runs before `hydrate`, so warm start parses the persisted CHECK text with the function present. Each `Database` holds its own registration; Quereus's module-level caches are `WeakMap`s keyed by `SchemaManager` or `TableSchema`, both per `Database`, so two parties in one process (every two-node spec) cannot see each other's folded id.
- No downstream package (cadre-host, cadre-cli, cadre-rn, cadre-provider, integration-tests) calls a changed signature with the old shape; root `yarn typecheck` covers them all and is clean. No docs or README carries a call sample with the old parameter order.
