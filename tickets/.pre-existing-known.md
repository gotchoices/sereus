- `packages/cadre-core/test/validation-key-enrollment.spec.ts > CadreNode validation-key enrollment > a redemption approved BEFORE removal survives the removal (removal is not retroactive)` — reported as "cadre-core/cadre-cli suites cannot start (stale + broken linked `quereus` build)". (2) Behind it sat a real failure: `QuereusError: Column not found: ValidationKey`. The spec (authored blind, since the guard meant it never ran) asserted `select ValidationKey from CadreControl.FormationUsage`, but the approver key is **not** a `FormationUsage` column — it arrives as write-time `context.ValidationKey`, read only by `FormationUsage.Authorized` to pick which enrolled row the sign-off claims, with the signature verified against the stored `ValidationKey.Key` (`schemas/control.qsql`, and the column list in `docs/architecture.md` line 40). Fixed 2026-07-30 by pointing the assertion at columns that exist — the consent row must survive the removal still naming the same `Token`/`PeerId`/`StrandId` — which keeps the not-retroactive intent (a retroactive revocation deletes the row and fails it). Schema unchanged; persisting the approver key would be a control-schema change, not a triage fix. Verified: spec 9/9, whole `cadre-core` suite 73 files / 1155 passed (1 pre-existing win32 `skipIf` in `key-store.spec.ts:231`), `cadre-cli` 99/99, `yarn lint` exit 0.

- `strand-formation-e2e.integration.ts > E2E Strand Formation > Phase 2: Strand instance lifecycle > should form a strand with three parties` — was `Timeout waiting for data replicates to Bob after 15000ms`. Root cause was **not** the control-DB replication class it was suspected of: a three-party strand replicates each block to only 2 of the 3 members (`DEFAULT_STRAND_CLUSTER_SIZE` = 2), and the member outside the cohort had no way to obtain a block it had never seen — `BlockStorage.getBlock` returned before `ensureRevision` when local metadata was empty, so the corroborated cluster revision was established and then discarded. Fixed upstream by `../optimystic` `559df6a` ("let a read acquire a block the node has never seen"), which is in optimystic HEAD; the third member now acquires the block at read time (`cluster-fetch:synced`). Verified 2026-07-29 at sereus HEAD: **13/13 green** — 8/8 alone via `-t` (1.3–1.6 s each, well inside the unchanged 15 s budget), 4/4 whole-file, 1/1 in a mixed run behind `convergence-stress`/`multi-party-sync`/`control-cohort-auto-convergence`/`happy-path`. The remaining behaviour — that adding parties never adds copies, so members read from a cohort instead of holding data — is not a defect and is tracked as `backlog/debt-strand-replication-breadth-ignores-party-count` plus the human decision in `blocked/replication-breadth-two-signoff`.
