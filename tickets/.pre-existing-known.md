## Resolved in place (no ticket — root cause landed)

- `push-wake-e2e.integration.ts > E2E push-wake over the control network > wakes a member whose authorization and address were learned by control-DB replication, not local seeding` — was intermittent (6 failures in 20 when run alone via `-t`; 4 in 10 in the original measurement) while the control database replicated each block to only 2 nodes, which left a member that missed a write dependent on read repair, and read repair cannot converge at a two-member cohort. Fixed by `control-db-replicates-to-whole-party` (control breadth is now `CONTROL_REPLICATION_BREADTH` = 16, i.e. the whole party); **20/20 green alone via `-t`, plus 2/2 in whole-suite runs**, verified 2026-07-29 by `control-db-replicates-to-whole-party-validation`. The earlier stale-revision retry work (`bug-control-db-stale-revision-not-retryable`, `bug-control-db-rx-record-never-converges-on-sender`) reduced but did not remove the failure rate. The unexplained 1-in-20 failure previously listed here (log lost) has not recurred.

- `cadre-host-bootstrap.integration.ts > install + start → /api/status returns the live service snapshot`, both `cadre-host-origin-guard.integration.ts` accept-cases, and `cadre-host-trust-circle.integration.ts > completes issue → list → redeem → list → remove cycle` — all four were the `createTestCadreHost` harness diverging from `bin/host.ts`: `defaultFakeCadreNode()` was missing `listAuthorizedMembers`/`isAuthorizedMember` (→ `TypeError` → bare 500), and the harness never ran the `ensureSelfLabel` startup step (→ owner's own row absent from the listing). Fixed 2026-07-29; `yarn typecheck` in `packages/integration-tests` had been failing on the same gap and is now clean.
