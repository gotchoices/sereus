### The wedge is a half-applied commit, and it is not the orphan upstream already fixed

The `0/3 approvals, 0 rejections` symptom the ticket was filed for **did not appear once**. What

## 2026-09-01 (0.26 upgrade: peer-join catch-up is refused wholesale; overnight run started)

### What the upgrade broke, and where the fix has to land

`@optimystic/db-p2p` 0.26's block-transfer receiver requires a cohort commit proof on every pushed
block (`requirePushCertificate`, default `true`). A proof is minted in exactly one place — the
consensus commit path in `ClusterMember.applyConsensusOperation` — and `CoordinatorRepo.commit`
short-circuits consensus entirely when the cohort is one peer. So a founder writing alone retains
no proof for anything it wrote, and no later step can manufacture one: the signatures never existed.

Measured with a two-node probe (real `CadreNode`s over libp2p, `getBlockProof` per block): **0 of 18**
founder blocks held a proof after strand bootstrap, **0 of 21** after a joiner attached and a further
write landed. `CoordinatorRepo` logged `cluster-fetch:solo-self-skip` 140 times in that run. In the
full scenario, the founder offers 15-21 blocks per peer, the joiner accepts 3, and all 74 rejections
logged `push:reject-uncertified … reason=no-proof`.

`StrandBackfill` is not at fault — it reads the proof for exactly the revision it pushes and ships
what it finds. There is nothing to find.

Direction decided by the maintainer: **mint a real one-peer proof on the solo path** rather than
weakening the receiver. Filed upstream as `../optimystic/tickets/fix/1-solo-cohort-commits-mint-no-proof`;
tracked here as `blocked/strand-catch-up-refused-until-solo-writes-carry-proof`, which also records
why relaxing `requirePushCertificate` on strand nodes is **not** an available stopgap on its own —
strand nodes wire no `authorizeInboundStream` and no membership gater, so the certificate is
currently the only thing between an arbitrary dialer and a member's block store.

## 2026-08-25 (two fixes, from instrumenting rather than reasoning)

Both of today's fixes came out of measuring something a ticket had asserted. Both assertions were
wrong, and in both cases the ticket had been steering work away from the fix for weeks.

### `secondary-index-seek-blind-to-sibling-rows` → the seat cap is fixed; the engine defect is not

Ran the failing scenario with optimystic's `index:seek` trace, which had already landed and had
never been run here. The seek is **stale, not blind**: both machines resolve the same index
collection, their copies of the table agree, and their copies of the index sub-collection differ by
exactly one revision — with `arm=live`, so a refresh ran immediately before the descent and did not
close the gap. Each machine finds exactly the entry it wrote. That is the first explanation
consistent with all three controls the ticket had carried since 2026-08-12.

Acting on it, `FormationUsageByToken` came out of the control schema. It had been declared purely
to spare a table scan, and the review that declared it recorded a tripwire — the seat cap is that
count, so an under-reporting descent admits a seat the invitation never paid for, *"a failure mode
a scan could not produce"*. The tripwire fired. `strand-formation-concurrent-redemption`: 3
deterministic failures → 3 passes, sub-second each.

**This removes the only reliable reproducer of the engine defect.** Re-adding the one index line to
both schema copies restores it; that is written at the schema site, in `docs/architecture.md`, and
on the upstream ticket. Every `unique` constraint still rides a secondary index, so cross-machine
uniqueness keeps the same exposure (`strand-unique-index-sync-stale-revision`).

### `control-reads-blocked-by-stalled-write` → fixed, and the expected-failure count is now zero

The ticket's own note said routing was automatic and there was no public API to call, and sent the
fix stage hunting for which eligibility rule disqualified control reads. No rule was firing:
`Statement.tryRouteConcurrent` returns false on its first line for anyone who did not pass
`readConcurrency: 'committed'`, which is public. The original plan's step 2 was right all along.

The opt-in is taken **only while a write is in flight**, and that gate is load-bearing. The option
also connects the table with `_readCommitted`, which the optimystic vtab serves from a snapshot that
never refreshes from the network — so asking for it unconditionally traded "reads block" for "reads
stop seeing other machines", killing this very scenario at suite setup on two runs out of two.
Filed upstream in quereus as `bug-committed-read-opt-in-also-forfeits-refresh`.

### Wave 2 — re-running the hunt against the swept tree

The first sweep's inventory was not the whole set. Repeating the search afterwards found one
affordance that was not redundant at all:

`cadre-cli` decoded an identity key by guessing — `privateKeyFromProtobuf`, falling back to
`privateKeyFromRaw` on failure, the fallback explicitly labelled backward-compat. `privateKeyFromRaw`
validates **length only**. So a protobuf key file truncated to 64 bytes did not fail: it decoded as
a *different, perfectly valid* identity and the node came up under a PeerId nobody expected, with
every `MemberPeer` row and relay reservation naming the real one going stale. The ticket was written
to require that claim be *verified* before being built on; the implement stage measured it and it
held.

Four doors collapsed to one: `identity.keyFile`, `CADRE_KEY_FILE`, `--identity-file`, binary libp2p
protobuf. Anything else throws, with the libp2p error preserved as `cause` — deliberately not
falling through to "no identity configured", because that path generates a fresh keypair and
reaches the same wrong-identity outcome by a different route.

### What the verification run found — a real dial defect

A full root `yarn test` after wave 1 came back 8 red of 251, seven documented. The eighth was
`push-wake-e2e`'s circuit-relay case timing out on a dial to `10.255.0.1` — a Hyper-V/WSL
virtual-adapter address on the development host, not a peer address in the topology. It passed 3/3
in isolation and 4/4 under the review that had just hardened it, so it was whole-suite-only.

It was filed as `fix/` rather than folded into the documented intermittent set, and the ticket said
plainly that one green and one red full-suite observation is not enough to call it a regression or
an intermittent, making that determination the first task rather than an inherited assumption.

The cause was neither. `libp2p.dial(addrs)` refuses a list that mixes addresses ending in
`/p2p/<peer>` with bare ones — all or none — and it refuses *before touching a transport*, so the
caller sees one thrown error and skips that peer **entirely, on every reconcile pass, forever**,
with only a debug line. A `CadrePeer` row routinely holds both shapes: a circuit-relay address
always carries the suffix, a bare direct address does not.

Landed as `wake-and-cohort-dials-mishandle-peer-address-lists`: one rule,
`withTrailingPeerId(addr, peerId)`, discriminating on whether the address's last component names a
peer — the same test libp2p's own `calculateMultiaddrs` applies. The implement stage fixed one of
the **three** places a control dial gets its candidates; the review found and closed the other two,
including the cold-start peer-store fallback, whose source strips trailing peer ids and is therefore
messier than the signed record, not tidier.

**This was a production defect, not a test artefact** — the reason the ticket insisted on root cause
over raising the 10 s timeout. A fix that only moved the timeout would have hidden it.

### The night's finding: sereus cannot build or run at all

Baseline `yarn build` was red before any ticket work, and the cause is outside this repo:

```
node -e "import('@serfab/cadre-core')"
  → The requested module 'p2p-fret' does not provide an export named 'readAllBounded'
```

`../Fret` commit `f5f2eb6` (2026-08-18, "ticket(implement): rpc-framing-src") replaced its exported

root `resolutions`, so the break lands here whole: `cadre-core` fails at ES-module link time, which
takes every suite that touches it with it.

Note that `tsc` passes — the type-check never descends into `db-p2p`'s internals, so only the
esbuild browser bundle and actual module loading catch it. A green `yarn typecheck` means nothing
about this class of drift.

This is not a rename. The old reader consumed a stream to EOF; the new one reads exactly one
length-prefixed frame and pairs with a matching writer. Porting changes what goes over the wire for
`db-p2p`'s cohort-topic and reactivity protocols, so it is a design call, not a mechanical swap.

**The twelve-day-old theory is dead.** Upstream landed a `commit:collections` trace; run here
under `DEBUG='optimystic:quereus-plugin:txn-bridge'`, **all four** writes to the failing table
carry both collections, both staged:

```
count=2 default/FormationUsage=staged default/FormationUsage/index/FormationUsageByToken=staged
```

So "the index collection is absent from the write transaction entirely" — the claim three
investigations chased — is refuted. The write side is closed; the fault is after the commit.

**A sixth upstream reproduction attempt failed, and its exclusion list is the lead.** The
144-ordering interleaving sweep passed every case. It states that each node writes "its own
disjoint id (100 / 200)" — disjoint primary keys *and*, since the index is single-column over
those same values, disjoint **index keys**. Every attempt so far has that shape.

**The failing case does not.** From `schemas/control.qsql`: `FormationUsage`'s primary key is
`UsageStampId`, a per-redemption **nonce**, while its index is `FormationUsageByToken` over the
*invite*. Two machines redeeming one invite therefore write **disjoint primary keys and the same
index key** — the schema even states the rule outright ("two FormationUsage rows for one token").
Both index writes land in one entry that must hold both row references.

If a commit replaces that entry rather than merging into it, each machine sees only its own row
through the index while scan and primary-key descent see both. That is the reported symptom
exactly, and it explains five clean sweeps without anything exotic. Filed upstream as
`fix/1-two-nodes-writing-one-index-key-was-never-tested` (`c4adad4`), `repro: suspected` — the
first job there is to run the shape, not to fix anything.

**Next discriminator, already built and waiting.** Upstream also landed revision tracing:
`commit:collections` now carries `revs=<id>:<rev>`, where **`:none` means the collection was
invented** (nothing ever committed under that id), plus `index:tree-open` naming the resolved
collection id per node and `collection:invented` from `db-core`. One run here says whether the
two machines share one index lineage or invented two wearing one name.
