### The night's finding: sereus cannot build or run at all

Baseline `yarn build` was red before any ticket work, and the cause is outside this repo:

```
node -e "import('@serfab/cadre-core')"
  → The requested module 'p2p-fret' does not provide an export named 'readAllBounded'
```

`../Fret` commit `f5f2eb6` (2026-08-18, "ticket(implement): rpc-framing-src") replaced its exported
`readAllBounded` with a `sendFramed` / `readFramed` pair. `../optimystic/packages/db-p2p` still
imports the removed name at 16 sites across 7 files. Both repos are linked into this one through
root `resolutions`, so the break lands here whole: `cadre-core` fails at ES-module link time, which
takes every suite that touches it with it.

Note that `tsc` passes — the type-check never descends into `db-p2p`'s internals, so only the
esbuild browser bundle and actual module loading catch it. A green `yarn typecheck` means nothing
about this class of drift.

This is not a rename. The old reader consumed a stream to EOF; the new one reads exactly one
length-prefixed frame and pairs with a matching writer. Porting changes what goes over the wire for
`db-p2p`'s cohort-topic and reactivity protocols, so it is a design call, not a mechanical swap.

Reviewed the embedding app's checkout at `../sereus-health2` against their solo-hang report.
Their node configuration is ours, and coordinator selection is not their problem: on the 0.22.0
they actually resolve, `networkMode` is `'forming'`, the high-water mark is 1 (cadre-core passes
no `persistence`, so it resets every launch), and `shouldAllowSelfCoordination` grants self-
coordination as `bootstrap-node`. Their app's own comments assert that solo control operations
block forever, which `docs/cadre-consistency.md:52` and our solo spec both contradict — that
belief did not come from our docs, and it is why every control failure in their app is swallowed
and rendered as an empty screen.

What the review did surface for *us* is a coverage gap, filed as
`fix/solo-warm-start-blocks-on-prior-cohort-peers`: their boot awaits an unbounded control read
(`resolveCohortSeed` → `queryCadrePeers`) before genesis, on a device whose persistent storage
still holds `CadrePeer` rows from an earlier multi-device session. Our solo spec is cold and
memory-backed, so it cannot construct that state. The ticket's deliverable is the reproduction,
and it says explicitly that "it does not hang" is a publishable result.

Two of the analysis conclusions we had been carrying were wrong and are corrected in that ticket:
the write-queue re-entry hypothesis (their timeout wraps `ensureOwnerKey`, which blocks at an
unlocked read), and the inference that the stall sits above optimystic (drawn from a missing debug
line in a trace we cannot reproduce from their tree).
