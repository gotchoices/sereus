## 2026-09-16 (small hours — the device run came back with the biggest fix of the night)

The phone session finished at about 00:45 and handed the tree back. Its uncommitted work verified here (RN suite 17 files / 277 tests, typecheck and lint clean) and committed as `7a0fd6c`.

**The headline: the phone could not dial anybody, and now it can.** React Native/Hermes is missing three web APIs libp2p depends on — `AbortSignal.timeout`, `AbortSignal.any` and `WebSocket.bufferedAmount`. The dial queue calls `AbortSignal.timeout` for every dial that carries no signal of its own, and `@libp2p/websockets` gates sending on `bufferedAmount`, where `undefined < n` is false — so the socket opened, the handshake was never written, and every dial died on the 10 s timeout. The same address dialled from the PC in 37 ms. With the polyfills: dial in 1.6 s, a relay reservation held for the first time ("Reachable: Yes — via relay"), and a cross-party `formStrand` in 2.3 s. **This is the kind of defect no headless test can find**, because Node has all three.

**Tonight's earlier fixes confirmed on the device:** a fresh party id lists 0 strands (it saw ten from other parties before the per-party control storage fix), node start 2629 ms, founding 2380 ms.

**Five tickets filed from that run**, sequenced here: `0-cross-party-strand-messages-do-not-converge`, `1-phone-cannot-dial-websocket-peers` (the guard and audit for the fix above — it is in the tree unguarded until this runs), `2-host-loan-connect-step-never-sees-the-node`, plus `cadre-host-respawn-leaves-loan-unseedable` and `metro-reloads-the-app-on-any-repo-write`.

**The most important one, and the connection worth not losing.** Two parties form a closed strand, membership crosses, and then **no message crosses in either direction** — and the joiner cannot read back *its own* insert, failing with `Block default/Message is unavailable (cohort-unreachable)`. That is the same error shape this suite hit hours earlier on `Revocation`, and the read-only investigation already on that ticket bears on it directly: sereus already selects a committed read when a writer's transaction is open, the plugin's live arm does a network refresh before reading, and a node that cannot reach its cohort therefore fails a live read **even for rows it holds**. Both tickets now cross-reference each other and say to run the one committed-read experiment first, because it splits the cross-party ticket in two directions: shared read-arm cause, or `formStrand` cohort provisioning. Assert which row comes back, not just that rows come back.

**Audit item recorded, deliberately not fixed:** the new `AbortSignal.any` never removes its listeners, so on a phone left running they accumulate on long-lived signals. The committed version is the one verified on hardware and there is no device to re-verify against tonight; risking the change that made dialling work at all, to fix a leak that grows over hours, is the wrong trade. It is written into ticket 1 for whoever has a phone.

**Board order, and why it is not "worst bug first".** Sequenced `0-phone-cannot-dial-websocket-peers`, `2-host-loan-connect-step-never-sees-the-node`, `3-cross-party-strand-messages-do-not-converge`. ### What the verification run found — a real dial defect

A full root `yarn test` after wave 1 came back 8 red of 251, seven documented. The eighth was

It was filed as `fix/` rather than folded into the documented intermittent set, and the ticket said

an intermittent, making that determination the first task rather than an inherited assumption.

The cause was neither. `libp2p.dial(addrs)` refuses a list that mixes addresses ending in
`/p2p/<peer>` with bare ones — all or none — and it refuses *before touching a transport*, so the
caller sees one thrown error and skips that peer **entirely, on every reconcile pass, forever**,
with only a debug line. A `CadrePeer` row routinely holds both shapes: a circuit-relay address
always carries the suffix, a bare direct address does not.

`withTrailingPeerId(addr, peerId)`, discriminating on whether the address's last component names a
peer — the same test libp2p's own `calculateMultiaddrs` applies. The implement stage fixed one of
the **three** places a control dial gets its candidates; the review found and closed the other two,
including the cold-start peer-store fallback, whose source strips trailing peer ids and is therefore
messier than the signed record, not tidier.

**This was a production defect, not a test artefact** — the reason the ticket insisted on root cause
over raising the 10 s timeout. A fix that only moved the timeout would have hidden it.

### Second half of 2026-08-24 → 25 — the secondary-index question moved a long way

`yarn check` is still red; none of this closed a test. What changed is that the
secondary-index defect went from an untestable theory to a falsifiable prediction.

**The twelve-day-old theory is dead.** Upstream landed a `commit:collections` trace; run here
under `DEBUG='optimystic:quereus-plugin:txn-bridge'`, **all four** writes to the failing table
carry both collections, both staged:

```
count=2 default/FormationUsage=staged default/FormationUsage/index/FormationUsageByToken=staged
```

So "the index collection is absent from the write transaction entirely" — the claim three
investigations chased — is refuted. The write side is closed; the fault is after the commit.

**A sixth upstream reproduction attempt failed, and its exclusion list is the lead.** The
144-ordering interleaving sweep passed every case. It states that each node writes "its own
disjoint id (100 / 200)" — disjoint primary keys *and*, since the index is single-column over
those same values, disjoint **index keys**. Every attempt so far has that shape.

**The failing case does not.** From `schemas/control.qsql`: `FormationUsage`'s primary key is
`UsageStampId`, a per-redemption **nonce**, while its index is `FormationUsageByToken` over the
*invite*. Two machines redeeming one invite therefore write **disjoint primary keys and the same
index key** — the schema even states the rule outright ("two FormationUsage rows for one token").
Both index writes land in one entry that must hold both row references.

If a commit replaces that entry rather than merging into it, each machine sees only its own row
through the index while scan and primary-key descent see both. That is the reported symptom
exactly, and it explains five clean sweeps without anything exotic. Filed upstream as
`fix/1-two-nodes-writing-one-index-key-was-never-tested` (`c4adad4`), `repro: suspected` — the
first job there is to run the shape, not to fix anything.

**Next discriminator, already built and waiting.** Upstream also landed revision tracing:
`commit:collections` now carries `revs=<id>:<rev>`, where **`:none` means the collection was
invented** (nothing ever committed under that id), plus `index:tree-open` naming the resolved
collection id per node and `collection:invented` from `db-core`. One run here says whether the
two machines share one index lineage or invented two wearing one name.
