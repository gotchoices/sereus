# The phone reference app rents a provider node

Fifth ticket of the `provider-client-and-sign-up` chain. One configured test provider is enough: where a list of providers comes from, and whether paying on the provider's page is acceptable under the app stores' rules, is `tickets/blocked/decide-provider-directory.md`.

## Kit: `@serfab/cadre-rn/provider`

A new subpath, following the kit's pattern of injected platform pieces and a "What the app must install" section:

- `signInWithProvider({ descriptor, clientId, redirectUri, openAuthSession, fetch? }): Promise<ProviderTokens | 'cancelled'>`: `createPkce` and a random state, `authorizationUrl`, then `openAuthSession(url, redirectUri)`, whose signature is `expo-web-browser`'s `openAuthSessionAsync` (`{ type: 'success', url } | { type: 'cancel' | 'dismiss' | 'locked' }`), so the app passes that function in and the kit does not depend on expo-web-browser; on `success` `readAuthorizationRedirect` and `exchangeAuthorizationCode`. Anything but success is `'cancelled'`: nothing was created.
- `providerTokensSlot(secureStore, providerId)`: the tokens are credentials, so they go in the secure store through the existing `secureStoreSlot`; `createTokenSource`'s `persist` writes there. `clearProviderTokens` for sign-out.
- `rentalStore(kv)`: the app-private record of rentals, keyed by party: `Rental = { providerId, containerId, join: 'claim' | 'invitation', peerId?, createdAt, finished: boolean }`, in the app-private KV store through `kvStoreSlot` (a new `rentalsKvKey(partyId)` in `node-local.ts`). This is what lets the app find an unfinished rental on the next launch and tell a rented node from any other machine in Devices and nodes.

## App

- `src/providers.ts`: the configured providers: `[{ descriptorUrl: 'http://<dev machine>:3000/api/v1/descriptor', clientId: 'sereus-chat' }]`, read like `drone.cadre.yaml`'s address is read today (an env or config value the README documents), with the second install's client id when `APP_VARIANT=second`. The descriptor is fetched when the section opens and parsed with `parseProviderDescriptor`.
- `src/provider-store-section.tsx`, Settings → "Rent an always-on node", shown while connected: the provider's name, icon and regions, its plans from `plansUrl` (name and price per hour), a Terms link, and **Subscribe and add node**. Owner only (`node.isOwner()`; members see the same line the add-node section shows). The approval prompt, in the style of the add-node section's pending prompt: "Rent a node from ‹name› and add it to cadre ‹party›? You will sign in and pay on ‹name›'s site." Approve → sign-in when no tokens are stored (or when the client reports `reauthorize`) → `rentNode` with a progress line per step and the 20-second slow hint while claiming → the rental is recorded before `rentNode` returns a claim (`finished: false` at create, `true` at the end), so a kill mid-flow leaves a record to resume.
- Rentals list in the same section: one row per rental, polled every 5 s while the section is on screen (`getContainer`): the node's status, the join state in words ("Waiting for this phone to claim it", "Joining through ‹member›", "Joined", "Could not join: ‹error›"), the peer id short form, and the subscription's "Renews ‹date›" or "Unpaid, stops ‹date›" from `getBillingStatus`. Rows:
  - unfinished claim (`finished: false`, `join awaiting`): **Finish adding** (`finishRental`) and **Cancel** (delete the container, drop the record);
  - invitation `failed`: **Try again** (delete, then `rentNode` again) and **Cancel**;
  - `stopped` with `stopReason: 'non-payment'`: "‹name› stopped this node for non-payment." with **Remove from cadre** (the Devices and nodes confirmation and `removeMachine`, reached through the existing `machines.ts` plan helpers; the rental record is dropped on success) and **Forget** (drop the record only);
  - `stopped` with `stopReason: 'customer'` or a container the provider no longer knows (404): the row says so and offers **Remove from cadre** when the machine is still listed and **Forget**;
  - running and joined: **Cancel subscription** is not here (the provider's own page is where a subscription ends; a Terms-style link to the provider's site is enough).
- Devices and nodes: a machine whose peer id matches a rental shows "Rented from ‹name›" as a fact, and nothing else changes.
- Links: `redirectUri` is `Linking.createURL('provider-auth')` (`sereus-chat://provider-auth`, or the second install's scheme). `app/+native-intent.tsx` rewrites a `provider-auth` path to `/settings` with no query: the auth session owns the result, and the code is single-use and must not sit in navigation state. If a device run finds the session not resolving on Android, read the query the way `nodeCode` is read and hand it to the pending sign-in; say so in the handoff.
- Sign-out: a line under the section ("Signed in to ‹name›. Sign out") clears the tokens; rentals stay.

## Edge cases & interactions

- User cancels checkout or closes the browser: `signInWithProvider` returns `'cancelled'`; no container, no record. By inspection.
- Token expired mid-flow: the client's one retry after refresh; a refused refresh surfaces as `reauthorize`, the section runs sign-in again and retries the step the user asked for (not a silent loop). By inspection.
- App killed after the create but before the claim: the record exists with `finished: false`; the section offers Finish adding. Killed after the node accepted the claim but before `claimNode` wrote the row: `finishRental` finds the container claimed into this party and reports done without a row, because the provider withholds the code once the claim is folded (architecture.md → Renting a node from an app, Resuming); the remedy is Cancel (delete the container) and rent again. The accepted tradeoff NOTE in `use-cadre.ts` about this window for cadre-host nodes applies the same way and is referenced, not repeated.
- The provider stopped the node while the app was closed: the next poll shows the row's non-payment state; `removeMachine` works without the node being reachable (it writes tombstones). Devices and nodes already handles a dead machine.
- Two rentals in one cadre: each its own row and record; the second goes the invitation path once the first node is joined and announces a public address (`invitationReach` reads `anywhere`), which the handoff should state as the expected behaviour for a device run to confirm.
- The descriptor fetch fails (dev machine off): the section shows the error and a retry; nothing else in Settings is affected.
- The Settings tab stays mounted (the NOTE in `add-node-section.tsx`): a running `rentNode` survives a tab switch; the same NOTE covers this section.

## Tests

None new in the app beyond a unit test for `rentals.ts` if it holds a pure projection (the row state from a container, its join state, the billing status and the record); the flow is kit glue over cadre-core, whose logic `cadre-core-provider-client-and-rent-node` tests. `test/` in the app runs pure modules in Node, as `node-claim.spec.ts` does. The kit's `rentalStore` and `providerTokensSlot` are storage glue; no test.
