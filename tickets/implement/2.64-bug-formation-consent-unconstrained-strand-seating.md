# Constrain what a redeemed invitation may seat

## Background

A `CadreControl.Strand` row is the party's record of one network it participates in. It can be
seated two ways: **owner-signed** (an owner signs a digest over the whole row), or **by
consent** — no signature at all, authorized purely by the existence of a
`CadreControl.FormationUsage` row (a redemption record) naming that strand row's one-off
`StampId`.

The consent branch places no limit on *which* strand a redemption seats or *what* it puts in
it. Both attacks below were re-confirmed empirically on this branch (real `CadreNode`, empty
bootstrap, `transaction` profile) at commit `06a3dbe`, i.e. after the
`bug-formation-validation-key-never-checked` prereq landed:

- **A** — a `totalUses: 2` invite seats strand `X` closed with key `HONEST`; the owner then
  does a fully legitimate signed delete of `X` plus its `Revocation` tombstone; the **second
  use of the same token** re-seats `X` carrying `MemberPrivateKey = 'ATTACKER'`. Accepted.
- **B** — an invite bound to host strand `H` (`FormationInvite.StrandId = H`) redeems against
  an unrelated id `Z`, seating `Z` closed with an attacker key. `H` untouched. Accepted.

Invitation tokens live in plaintext in `FormationInvite`, replicated across the party's whole
cadre, and these CHECK constraints *are* the authorization boundary (peers write SQL to the
control database directly). So the capability belongs to any node that can reach the control
network for as long as any invitation has a use left (`TotalUses` null = unlimited, forever).

No production writer needs the latitude. `ControlFormationUsageRecorder.provisionAndRecord`
(the only consent-creates-strand path) mints its **own** 128-random-byte strand id and always
passes `type: 'o'` with no member key. The bound path (`recordUsage` →
`ControlDatabase.recordFormationUsage`) inserts no `Strand` row at all.

## Decisions settled during the fix stage

**The re-join story survives, in owner-signed form.** Consent may seat a given strand id
**once, ever**. After a removal, re-joining that same id requires the owner to re-seat it
(`insertStrand`, fresh stamp + fresh signature) and then issue a **bound** invite the returning
party records consent against. Verified working end-to-end (scratch test A3 below). Consent-
driven re-join of a *removed* id is therefore deliberately **withdrawn** — it was
indistinguishable from attack A, and the legitimate unbound path never re-uses an id (it mints
128 random bytes each time).

**`redeemInvitation`'s `type` / `memberPrivateKey` parameters go away.** Consent-seated
strands must be open and keyless, so both parameters become dead. Drop them rather than
splitting the method; `provisionAndRecord` already passes `type: 'o'` and nothing else calls
the consent path. (No backwards-compat obligation — see `AGENTS.md`.)

## The fix (validated on a scratch schema during the fix stage; now applied to this tree)

### 1. `FormationUsage.Authorized` — a bound invite may only name its own strand

Inside the existing `exists (select 1 from FormationInvite FI where ...)`, after the
`ExpiresAt` clause:

```sql
and (FI.StrandId is null or FI.StrandId = new.StrandId)
```

### 2. `Strand.AuthorizedInsert` — narrow the consent branch

Replace:

```sql
or exists (select 1 from FormationUsage FU where FU.StrandId = new.Id and FU.StrandStampId = new.StampId)
```

with:

```sql
or (
    new.Type = 'o'
    and new.MemberPrivateKey is null
    and exists (
        select 1 from FormationUsage FU
            where FU.StrandId = new.Id
                and FU.StrandStampId = new.StampId
                and exists (select 1 from FormationInvite FI where FI.Token = FU.Token and FI.StrandId is null)
    )
    and not exists (
        select 1 from FormationUsage FU2
            where FU2.StrandId = new.Id and FU2.StrandStampId <> new.StampId
    )
)
```

Four independent clauses, each closing one thing:

- `new.Type = 'o'` / `new.MemberPrivateKey is null` — a consent-seated strand looks like what
  `provisionAndRecord` actually writes. A closed strand carrying a caller-chosen member key
  (the party's own read-gating secret for that network) has no legitimate producer.
  `MemberKeyClosedOnly` already implies the second from the first today; both are stated so
  the rule does not silently depend on another constraint staying as it is.
- the inner `FI.StrandId is null` — only an **unbound** invite may seat a strand at all. Without
  it, edit 1 still lets a bound invite seat *its own* host strand `H` unsigned, open and
  keyless, on a node where the real (possibly **closed**, key-bearing) `H` has not converged
  yet — a downgrade that would then merge against the genuine row. `resolveStrand` already
  reports that case as `missing` and the manager rejects it, so no legitimate writer is
  affected.
- `not exists (... FU2.StrandStampId <> new.StampId)` — a strand id may be consent-seated
  **once, ever**. `FormationUsage` is append-only, so the first redemption's record survives
  the removal and permanently forecloses a second consent-seating of that id. This is what
  closes attack A. It cannot be weaponised to pre-block a legitimate id: `StrandExists`
  refuses a usage row naming a strand that does not exist, so no usage row can be pre-planted
  for an unseated id — and ids are 128 random bytes anyway.

## Which constraint reports the rejection

Measured on the patched schema — needed to write rejection assertions that pin the right rule
(`expectConstraintFailure` in `test/control-constraint-helpers.ts`):

| Attempt | Reports |
|---|---|
| re-seat a removed id via a spare use (attack A) | `AuthorizedInsert` |
| consent-seat a closed strand with a caller key | `AuthorizedInsert` |
| bound invite seats an unrelated id (attack B) | `AuthorizedInsert` |
| bound invite consent-seats its own host strand | `AuthorizedInsert` |
| bound invite **records** usage against another existing strand (no `Strand` insert) | `Authorized` |

Attack B violates *both* new rules and the engine reports `AuthorizedInsert`. To pin
`FormationUsage.Authorized` specifically, arrange a case with **no** `Strand` insert — a bound
invite plus `recordFormationUsage` against a different, already owner-signed strand (last row).
That is the technique `control-constraint-helpers.ts` documents: shape the write so exactly one
constraint can fail.
