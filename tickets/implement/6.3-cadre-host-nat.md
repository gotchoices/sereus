## Scope summary

This ticket lands the NAT/DDNS substrate that the host process uses to make itself dialable from the open internet and to publish a stable hostname to friends. It is library + CLI + cadre-core hook only — the long-running NAT service is *constructed and owned* by `cadre-host-local-ui`, the same way `cadre-host-local-ui` owns the management-API process that exposes `TrustCircleService`. This mirrors the pattern from `6.2-cadre-host-trust-circle`.

In scope:

- `packages/cadre-host/src/nat/` module tree (see "Module layout" below).
- A small surgical hook in `cadre-core` so the host can override the multiaddrs embedded in invites (replace direct `libp2pNode.getMultiaddrs()` with an optional resolver).
- CLI commands (`cadre-host nat status`, `cadre-host nat ddns set <provider>`, `cadre-host nat test`) that POST/GET against the management API (currently a stub — see "Process integration").
- `createNatHandlers(service)` factory mirroring `createTrustCircleHandlers`, so local-ui plugs it into Fastify.
- Documentation in `docs/cadre-host.md`.

Explicit non-goals (deferred):

- AutoNAT (libp2p service) integration. cadre-core's libp2p stack does not enable AutoNAT today; enabling it requires changes in `@optimystic/db-p2p`'s `libp2p-node-base.ts`. v1 uses the cheaper "external IP from router vs. external IP from public service" check (see "External IP detection"); a future ticket can swap in AutoNAT.
- Circuit-relay client/reservation wiring. `enableRelay` exists for the *server* side already; the *client* side (so a host behind CGNAT *consumes* a relay) needs work in cadre-core/db-p2p and is filed as a backlog ticket below.
- Additional DDNS providers beyond DuckDNS. Architecture is open for them; v1 ships DuckDNS only.
- IPv6 announcement — detect-and-prefer is nice-to-have; the address resolver returns whatever multiaddrs are observable and lets libp2p pick.
- Tray icon, web UI, browser auto-open — owned by `cadre-host-local-ui`.

## Process integration

The NAT service is long-running (refreshes port-mapping leases, polls external IP, fires DDNS updates). cadre-host has no long-running process today — `cadre-host start` is still a stub waiting on `cadre-host-local-ui`. So:

- This ticket exports `NatService` (constructor + start/stop + getters) and `createNatHandlers(service)`. Both are *libraries* with unit tests; neither is hooked into a process.
- The CLI subcommands talk to the management API over loopback (same pattern as the existing `invite`/`trust` commands at `packages/cadre-host/src/bin/host.ts:64-217`). Until local-ui mounts the handlers, `nat status` will print "cadre-host is not running — start it first" (same UX as `invite` today).
- A short note in `docs/cadre-host.md` documents the local-ui ticket's integration contract: construct `NatService`, call `await service.start()` after the libp2p node is up, mount `createNatHandlers(service)` on Fastify, call `await service.stop()` on shutdown.

This is the same handoff shape the trust-circle ticket left behind.

## Port-mapping layer

`port-mapper.ts` wraps `@achingbrain/nat-port-mapper`:

- `mapPort({ externalPort, internalPort, protocol: 'tcp', ttl })` → returns `{ mode: 'auto-upnp' | 'auto-natpmp', externalIp, lease }`.
- `refresh()` and `release()`.
- `verify()` — re-query the router to confirm the mapping is still installed (some routers silently expire under load).
- Periodic refresh timer (1 hour by default; configurable). On refresh failure, set `portMode = 'failed'` and emit through status snapshot.

If the user sets `upnpEnabled: false` in `nat.json`, port-mapping skips straight to `mode: 'manual'` and we surface "manual setup needed".

## External IP detection

`external-ip.ts`:

- Primary: query router via nat-port-mapper's gateway interface (it exposes external-IP on the WANIPConnection service).
- Fallback: HTTPS GET to a public IP service. Use multiple endpoints and pick the first to succeed (`https://api.ipify.org`, `https://ifconfig.me/ip`, `https://icanhazip.com`). Hard-code the list; no runtime config.
- CGNAT detection: if router-reported IP and public-service IP both resolve and differ, `cgnatDetected = true`. (CGNAT means the router thinks it's on a public IP that's actually private to the carrier's network.) The detection is heuristic; document the limitation.
- Returns `{ routerIp: string | null; publicIp: string | null; cgnat: boolean; detectedAt: Date }`.

## Reachability probe

`reachability.ts`:

- v1 implementation: `cgnatDetected ? 'cgnat' : portMode === 'failed' ? 'unreachable' : portMode === 'auto-*' ? 'reachable' : 'unknown'`. Cheap heuristic; doesn't actually dial back.
- Architected so a future ticket can swap in a real probe (libp2p AutoNAT or a sereus-owned dial-back).
- The "Test reachability" button in the UI invokes `NatService.testReachability()` which re-runs IP detection + verify(), then this heuristic.

## DDNS

### Provider interface

```typescript
// nat/ddns/index.ts

export interface DdnsProvider {
  readonly id: string;
  readonly displayName: string;
  readonly configFields: ReadonlyArray<{ key: string; label: string; secret: boolean }>;
  /** Pushes `ip` to the provider for the configured hostname. Throws on failure. */
  update(config: Record<string, string>, hostname: string, ip: string, deps: { fetch: typeof fetch }): Promise<void>;
}

export const PROVIDERS: Record<string, DdnsProvider> = {
  duckdns: duckDnsProvider,
};
```

### DuckDNS implementation

`nat/ddns/duckdns.ts`:

- `configFields`: `[{ key: 'token', label: 'DuckDNS token', secret: true }]`.
- `update(cfg, hostname, ip, { fetch })`:
  - Strip a trailing `.duckdns.org` from `hostname` to derive the subdomain.
  - GET `https://www.duckdns.org/update?domains=<sub>&token=<token>&ip=<ip>`.
  - Response is plain text `OK` or `KO`. Map `KO` → `NatError('ddns_update_failed', …)`.

### Updater loop

`nat/ddns/updater.ts`:

- Owned by `NatService`. On `start()`:
  - If `ddns.externallyManaged === true` or `ddns.providerId == null`: no-op (`lastUpdateAt` stays null).
  - Otherwise: read credentials from `SecretsStore`, run an immediate update, then schedule `setInterval(intervalMs)`.
- On every tick: re-detect external IP. If unchanged, *don't* call the provider (DuckDNS rate-limits / appreciates this). If changed, call `provider.update(...)`. Record outcome in status.
- Errors are recorded (`lastError`) but never throw out of the timer — the timer keeps running for the next attempt.

## Address resolver — hook into cadre-core

The existing `SeedBootstrapService.createInvite` reads multiaddrs directly:

```typescript
// packages/cadre-core/src/seed-bootstrap.ts:644-646
const addrs = this.libp2pNode.getMultiaddrs();
const authorityAddrs = addrs.map(a => a.toString());
```

Add an optional resolver hook at the `CadreNode` / `SeedBootstrapService` construction boundary:

```typescript
// packages/cadre-core/src/types.ts (extension of NetworkConfig)

export interface NetworkConfig {
  // … existing fields …
  /**
   * Optional async resolver that returns the multiaddrs to embed in invites
   * (and other authority-address contexts). When unset, `libp2pNode.getMultiaddrs()`
   * is used. Hosts behind NAT supply this to substitute their DDNS hostname
   * and externally-mapped port.
   */
  inviteAddressResolver?: () => Promise<string[]>;
}
```

Plumbing:

- `CadreNode` accepts `network.inviteAddressResolver` (already merges other `network.*` fields).
- `CadreNode` passes it into `SeedBootstrapService` (new constructor option).
- `SeedBootstrapService.createInvite` uses the resolver when present, falls back to `getMultiaddrs()` otherwise.
- Add a single test in `packages/cadre-core/test/seed-bootstrap.spec.ts` that asserts the resolver is consulted when set.

`NatService.getInviteAddresses()` constructs the multiaddr from current state:

- If DDNS configured + reachable: `/dns4/<hostname>/tcp/<externalPort>/p2p/<peerId>`.
- Else if reachable via raw IP: `/ip4/<externalIp>/tcp/<externalPort>/p2p/<peerId>`.
- Else (unreachable / CGNAT): return whatever `cadreNode.getMultiaddrs()` reports, since libp2p's own relay reservations (when wired in by the future ticket) will populate `/p2p-circuit/` addresses there. Document that this is the path-of-last-resort until the relay client lands.

## Credential storage

`nat/secrets/`:

- Try `keytar` via dynamic import inside a try/catch (native-dep failures shouldn't crash the package import). Service name `sereus-cadre-host`, account = `ddns:<providerId>:<key>` (e.g. `ddns:duckdns:token`).

## Tests

Per-module unit tests using `vitest`; mirror the trust-circle pattern (mock `CadreNodeLike`, mock `fetch`, mock the secrets store, mock `setInterval` via fake timers).

Key cases:

- **port-mapper**: success → mode + externalIp set; refresh failure → mode flips to 'failed'; release on stop; mapping verify mismatch flips to 'failed'.
- **external-ip**: router IP only → no CGNAT, public IP only → no CGNAT, both equal → no CGNAT, both differ → CGNAT, both fail → status remains `unknown`.
- **ddns-duckdns**: `OK` response → resolves, `KO` response → throws `NatError('ddns_update_failed')`, hostname with and without `.duckdns.org` suffix handled.
- **ddns-updater**: no-op when externally managed, no-op when providerId null, IP unchanged → no provider call, IP changed → one call, provider throws → `lastError` captured + timer keeps running.
- **secrets**: keytar success path, keytar throws → falls back to file, file path has 0600 mode (skip on Windows where mode bits don't apply), warning emitted exactly once per fallback session.
- **nat-service**: full happy-path with stubbed sub-modules: start → status reflects auto-upnp + ip detected + ddns updated; stop → release called + DDNS timer cleared; testReachability re-runs and updates status; getInviteAddresses builds dns4 multiaddr when DDNS configured + reachable, ip4 when only raw IP, falls back to `cadreNode.getMultiaddrs()` otherwise.
- **address-resolver / seed-bootstrap**: cadre-core test asserts `inviteAddressResolver` overrides `getMultiaddrs()` when supplied (`packages/cadre-core/test/seed-bootstrap.spec.ts`).
- **handlers**: `createNatHandlers` smoke test — every handler delegates correctly and propagates `NatError` codes.

CLI tests follow the `cli-invite.smoke.test.ts` pattern (run the compiled bin against a mocked Fastify server; assert exit codes + stdout). Add at least one happy-path + one "cadre-host not running" path.
