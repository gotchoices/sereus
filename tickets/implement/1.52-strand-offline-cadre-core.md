Second of the `strand-offline-mode` chain. `strand-offline-composition` gives `connectToStrand` an `offline` option, a `StrandOfflineController` on its result, and `appSchema: Promise<AppSchemaOutcome>`. This ticket is the cadre-core layer above it. The guards (membership writers, leaving a strand) are the next ticket, `strand-offline-cadre-guards`.

## Decisions

**Configuration.** `CadreNodeConfig.strandOffline?: StrandOfflineConfig`:

```ts
interface StrandOfflineConfig {
  /** The journal for one strand: called once per database build with the strand id (a storage scope key). */
  journal: (scope: string) => IKVStore | Promise<IKVStore>;
  /** The mode every strand starts in until the app sets one. Default 'online'. */
  initialMode?: 'online' | 'offline';
}
```

Absent means today's behaviour. No strand gets `offline`, and the always-on programs (cadre-host, cadre-provider, cadre-cli) configure none, because an always-on node has nothing to gain from a local acknowledgement. A journal is required: an acknowledgement that a process exit loses breaks the promise a local commit makes, so cadre-core never builds a memory-only queue. A `journal` that throws or rejects fails the build, like a storage provider that throws.

**Which databases.** Strand databases only. The control database (`control-database.ts`) registers Optimystic without `offline` and keeps doing so. Its writes are owner-signed membership and authorization facts, whose retry and veto rules (`control-write-retry.ts`) assume a network answer. Nothing changes there. State it in `docs/strands.md`.

**The mode belongs to the strand, not to one database.** A strand's `Database` is closed and rebuilt on hibernation, wake and every other runtime rebuild, and upstream's `enter()` lives on one plugin instance. So `StrandInstanceManager` keeps `offlineModes: Map<strandId, 'online' | 'offline'>`, seeded from `initialMode`. Each build applies the strand's mode at the end of `StrandDatabase.initialize`: after `connectToStrand` returns (`hydrate` has restored the queue) and after the founder bootstrap (whose `Strand` writes are network-acknowledged anyway), and before the first-sync probe and publication. The map lives as long as the process; after a restart a strand starts in `initialMode` again, and an app that wants something else sets it again at startup.

- `CadreNode.setStrandOfflineMode(strandId, mode)` records the mode. When the strand's database is live it also calls `enter()`/`exit()` on it, which affects transactions begun from then on (upstream fixes the acknowledgement when a transaction begins). It throws `StrandOfflineUnavailableError` (new, exported) when `strandOffline` is not configured, and the usual error for an unknown strand. A hibernating strand gets the mode at its next build.
- `CadreNode.getStrandOfflineMode(strandId)`.

**The first-sync gate is unchanged.** Applying the mode before the probe is what makes it work offline. In offline mode a read the cohort cannot answer is served from this machine's copy, so a machine that holds every collection passes the probe with its peers unreachable, and one that never held a table still fails it (`BlockUnavailableError`), as the gate requires. A restored non-empty queue is not used to skip the gate. Its transactions may cover only some tables, and the gate's rule is "what the local store holds" (docs/strands.md → "Joining: no writes before the first sync").

**What the app reads, on `StrandDatabase`.** `strand.database.offline: StrandOfflineQueue | undefined` (undefined when `strandOffline` is not configured). It is the controller minus `enter`/`exit`, since the mode is set through `CadreNode` so that it survives rebuilds: `queueState`, `entries`, `status`, `outcomes`, `acknowledge`, `discard`, `whenDrained`, `onStatus`, `onQueueState`. Listeners on it die with the database, as `watchTables` subscriptions do.

**Events that survive rebuilds**, wired like `strand:commit-durability` (listeners passed through the launch config, and `CadreNode` emits):

- `strand:offline-status`: `{ strandId, status: QueuedTransactionStatus }`, every upstream `onStatus` delivery.
- `strand:queue-state`: `{ strandId, state: OfflineModeState }`, every upstream `onQueueState` delivery, plus one at each publication with the current `queueState()`. Restored transactions' `queued` statuses are delivered during `hydrate`, before cadre-core subscribes, and that publication emit is how the app learns of them. Say so in the doc.

**A commit's durability for a queued transaction.** `commitDurability(Tx)` stays `undefined` until the drain commits the transaction. The plugin's durability report arrives then, during no `exec`, and the existing record takes it, so `strand:commit-durability` and later `strand:commit-held` fire as for an online commit. In offline mode an app reads `offline.status(Tx)` first. Update "A commit's durability" in `docs/strands.md`: today it says `undefined` means "nothing new to mark", which is wrong for a queued transaction.

**Hibernation counts sending as activity.** Each `submitting`, `committed`, `partially-committed` or `failed` status calls `hibernationManager.recordActivity(instance)`. Do not call `CadreNode.recordStrandActivity`, whose push fan-out would wake other phones. The effect: a check-in window that finds the cohort reachable stays up while the queue drains, and the idle timer does not cut a drain short. A queue that is merely waiting for its cohort (`queued`) is not activity, or an offline phone would never hibernate. A hibernation or `hibernateAll` that closes the database mid-send is safe. The send was journaled before it went out, and the next build's restore re-sends it under the same action id (upstream guarantee, README "Restarting").

**The app-schema deferral reaches the app.** When a build's `appSchema` outcome was deferred (`appSchemaDeferredBy` set), `CadreNode` emits `strand:app-schema-deferred` (`{ strandId, transactionIds }`) at publication and `strand:app-schema-applied` (`{ strandId }`) when the retry lands. A retry that fails for another reason is emitted as `strand:error`, and a cancelled one emits nothing. `StrandDatabase.appSchemaState(): 'applied' | 'waiting-for-queue' | 'failed'`. Meanwhile `StrandInstance.sAppInfo` names the new version while the database still runs the earlier `App` schema. Document that the app checks `appSchemaState()` before relying on new tables or columns.

## Edge cases & interactions

- **Database rebuilt mid-session** (hibernate, then wake): the mode is re-applied from the map before publication, and queued transactions come back through `hydrate`. Inspection. The scenario in `strand-offline-mode` covers a restart.
- **`setStrandOfflineMode` during an open app transaction:** upstream leaves that transaction's acknowledgement unchanged. Nothing to do.
- **`setStrandOfflineMode` racing a build** (called between `connectToStrand` returning and the mode being applied): the build reads the map at the moment it applies, so the newest value wins. Read it there, not at build start. Inspection.
- **Listener on a closing database:** `StrandDatabase.close` unsubscribes the offline listeners first, as it does the commit listeners, so no event reaches the app from a closing connection. Inspection.
- **Control database:** no `offline` key. Inspection, plus one line in the doc.
- **Revocation enforcer and membership reconciler reads** of `Strand` tables: those tables are `'network'`-tagged, so their reads behave as outside offline mode. No change. Inspection.
- **Table watches and reactivity:** `watchTables` is built on Quereus's `Database.watch`, which fires on a queued commit (a local commit) and on a refused transaction's removal (upstream announces it with `notifyExternalChange`). Strand reactivity (other machines' commits) is unchanged. No Sereus change. Inspection; say so in "Change notifications (reactivity)".

## Tests

None in this ticket. The branching is thin: a map read at one point, and event forwarding. The real-network scenario in `strand-offline-mode` runs the whole path (mode applied at build, queue restored after restart, status events, drain to the partner).
