# Authorize writes to `CadreControl.Revocation`

## Background

`CadreControl.Revocation` is the append-only table that retires the one-time authorization
nonce (`StampId`) of a removed `OwnerKey` / `CadrePeer` / `ValidationKey` / `Strand` row. It
exists so a never-expiring add-approval signature cannot resurrect a removed row.

Every other table in the schema requires an owner signature to change. `Revocation` has **no
`with context` clause and no `verify(...)`** — any writer that can reach the control database
may append rows. The only barrier is `RowIsGone`, a check against *locally visible* rows, which
the schema's own comments already document as non-authoritative on a node that has not
converged.

## Reproduced (fix stage, real `CadreNode`, empty bootstrap, `transaction` profile)

All four confirmed against the schema at HEAD:

- **A1 — unbounded junk.** 25 `insert into CadreControl.Revocation` statements with *no context
  clause at all* were accepted; `queryRevokedStamps('CadrePeer')` then returned all 25. The
  rows are permanent, replicate party-wide, and `CadreNode.listAuthorizedMembers` re-reads the
  whole set on every inbound gate request.
- **A2 — eviction / pre-block.** A tombstone written while the target `CadrePeer` row is not
  locally visible (the not-yet-converged writer the schema already warns about) lands
  unauthenticated, and the **owner's own** later admission of that exact row is then refused by
  `NotRevoked` — permanently. Once the tombstone replicates, every node also drops that peer
  from the authorized-membership set (`cadre-node-authorized-surface.spec.ts:218` already pins
  that reader behavior as intended).
- **A3 — the only existing barrier.** Tombstoning a *live, locally visible* peer is refused by
  `RowIsGone`. That is the whole of today's protection.
- **A4** — junk rows survive a legitimate removal transaction unchanged (append-only, by design).

## The fix (validated end-to-end on a patched schema copy)

Give `Revocation` the same shape every sibling table has: a context clause plus an owner
signature over a domain- and action-tagged digest covering the row being written.

### Schema — `Revocation`

Add after `RowIsGone`, and give the table a context clause:

```sql
        constraint Authorized check on insert (
            exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(digest('CadreControl.Revocation', 'remove', new.TableName, new.StampId), context.Signature, A.Key, 'ed25519'))
        )
    ) with context (OwnerKey text, Signature text);
```

Notes for the comment block you write around it:

- The digest binds `(TableName, StampId)` — the whole row. The `'CadreControl.Revocation'`
  domain tag makes it disjoint from every other rule, including the `'CadreControl.CadrePeer'`
  `'remove'` digest signed in the *same transaction* by the same owner (verified: that
  signature does **not** satisfy this check).
- Reads live `OwnerKey`, matching `ValidationKey` / `Strand` / `CadrePeer` / `DeviceToken`
  (not `committed.OwnerKey`). The one theoretical difference is that live-`OwnerKey` lets a
  founding transaction on an owner-less database seat an owner key and tombstone in one go —
  an owner-less control database is already a total loss, and a second transaction achieves
  the same thing under `committed.*`, so the consistency is worth more than the distinction.
  Say this in the comment so a later reader does not "tighten" it without knowing.
- `RowIsGone` and `Immutable` stay exactly as they are — both re-verified working under the
  patched schema. They guard a *legitimate* owner retiring a stamp early or withdrawing one
  later, which authorization does not cover.
- The existing `NOTE: append-only, so this table only ever grows` comment above the table
  should now say growth is owner-gated, so the unbounded-junk surface is closed.

### Which constraint reports the rejection

Measured on the patched schema — write rejection assertions against these names
(`expectConstraintFailure` in `test/control-constraint-helpers.ts`):

| Attempt | Reports |
|---|---|
| tombstone with no context (`OwnerKey`/`Signature` null) | `Authorized` |
| tombstone signed by a non-owner | `Authorized` |
| owner-signed tombstone over a *different* stamp | `Authorized` |
| owner's `CadrePeer` `'remove'` signature replayed as the tombstone | `Authorized` |
| owner-signed tombstone of a still-live row | `RowIsGone` |
| delete of an existing tombstone | `Immutable` |

### TypeScript

Two production writers file tombstones; both already hold the owner key at that moment.

- **`peer-authorization.ts`** — add `revocationDigest(tableName: string, stampId: string)`
  alongside the existing helpers (`taggedDigest('CadreControl.Revocation', 'remove', [tableName,
  stampId])`), with the SQL-mirror doc comment the neighbours carry. Type the parameter as
  `RevocableTable` if that does not create an import cycle (`RevocableTable` currently lives in
  `control-database.ts`, which `peer-authorization.ts` deliberately does not import — moving the
  type to `control-authorization.ts` is the clean option, since that module already owns
  `ControlTable` and has no runtime imports).
- **`seed-bootstrap.ts:removePeer`** — the `insert into CadreControl.Revocation` at ~line 489
  gains `with context OwnerKey = ?, Signature = ?`, signed with the existing
  `this.signDigest(revocationDigest('CadrePeer', stampId))`. Verified: the base64url-digest
  signing encoding `signDigest` uses satisfies the SQL `verify` for this digest.
- **`control-database.ts:deleteGuardedRow`** — same for the insert at ~line 805, signed via
  `signMessage(buildAuthorizationMessage('CadreControl.Revocation', 'remove', [table, stampId]))`.
  Verified: the raw-bytes encoding also satisfies the check.
- **`control-authorization.ts`** — the `CONTROL_TABLES` doc comment says *"`Revocation` derives a
  `'CadreControl.Revocation'` domain tag like every other entry, but no signature is ever minted
  for it — the table's CHECKs carry no `verify(...)`; it is listed so `countRows` can count it."*
  That is now false; rewrite it.

## Existing tests that write unauthenticated tombstones

Each has a local `tombstoneStamp(tableName, stampId)` helper doing a bare insert. Give each a
context clause and an owner signature over the new digest — the founder keypair is already in
scope in all three:

- `control-revocation-replay.spec.ts:268` (`tombstoneStamp`, plus the comment on it that says
  *"no context clause — the table declares none"*).
- `control-ownerkey-self-authorization.spec.ts:124`.
- `control-authorization-domain-separation.spec.ts:100`.

Watch the tests that assert a *specific* constraint name while filing a tombstone: with a valid
tombstone signature the rejection stays on the constraint they already pin. Do **not** widen an
accepted-name list to get green — re-shape the write instead (see the helper's own note).

## Regression tests to land

In `control-revocation-replay.spec.ts` (it already owns the `Revocation` rules), one per row of
the reporting table above, plus:

- the flooding repro inverted: an unsigned tombstone is refused, so `queryRevokedStamps` stays
  empty.
- the eviction repro inverted: an unsigned tombstone naming a stamp with no locally visible row
  is refused, and the owner's later admission of that row still succeeds.
- positive guards that the whole legitimate removal still works for `CadrePeer` (via
  `SeedBootstrapService.removePeer`), `OwnerKey` (two-owner removal transaction), `Strand` and
  `ValidationKey` (via `deleteGuardedRow`) — all four confirmed working under the patched schema.
