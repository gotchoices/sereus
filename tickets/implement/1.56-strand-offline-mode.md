Earlier tickets built the pieces: `strand-offline-composition` (plugin layer), `strand-offline-cadre-core` (mode per strand, events), `strand-offline-cadre-guards`, `strand-offline-platform-journals` (phone and browser journals, kit default) and `strand-offline-reference-apps`. This one runs the whole path on a real network and finishes the doc.

## The scenario

One real-network integration scenario. It is the only test the plan judged worth its cost for the feature as a whole.

Two parties share a strand: A, the partner, and B, phone-shaped. B runs as a child process over on-disk stores, so that its restart is a real one (new process, no module state carried over). Use the two-process harness of `strand-relay-only-restart-reconverges` (`harness/strand-restart-party.ts`, `fixtures/strand-restart-party.mjs`): it already keeps `FileRawStorage`, `FileKeyStore` and `FileStrandNetworkStateStore` under a state directory. Extend the child with `strandOffline: { journal: scope => new FileKVStore(<stateDir>/<scope>/offline), initialMode: 'offline' }` (`@optimystic/db-p2p-storage-fs`), and with ops to insert a row returning its `StampId()`, read rows, and read `offline.entries()` / `offline.status(tx)`. Use direct connections; the relay-only shape is not what is under test.

1. A and B form or join the strand and both reach `active`. B reads A's rows, so every collection is held on both.
2. Stop A, and wait until B no longer counts A as connected.
3. B inserts a row (`insert into App.<table> … returning StampId() as Tx`). The statement resolves promptly. B's `offline.status(Tx)` is `queued` with `persisted: true`, and the row reads back on B.
4. Stop B's child and respawn it over the same directory, A still down. B's strand reaches `active` through the first-sync gate with A unreachable: the mode is applied before the probe, so reads are served from B's own copy. The row reads back on B, and `entries()` still lists `Tx` as `queued`, waiting for the cohort. That last assertion depends on B remembering A after the restart, which is what the saved strand network state is for. If B instead reports itself alone and sends the transaction by itself, stop and find out why before weakening the assertion. Sending alone is the path offline mode exists to avoid.
5. Start A again. Within the scenario's budget B reports `committed` for `Tx` (through the `strand:offline-status` event the child forwards), and A reads exactly one row with that content and that key.

Sizing: a fixed, small number of writes, and everything under the 10-minute idle limit. Print elapsed-time lines per step, as the restart scenario does (`[OFFLINE] …`), so a slow step is visible.

## Edge cases & interactions

How each case named in the plan is verified, now that the pieces exist:

- **Restart with a non-empty journal:** this scenario, step 4.
- **Restart right after the network accepted an entry:** sent once by upstream's guarantee (README → "Restarting": the send is journaled first, and a restart re-sends under the same action id or reports `committed`). Sereus adds nothing to the send path. Inspection of the composition order (`strand-offline-composition`). No test.
- **A refused queued transaction:** upstream removes its rows and announces the tables with `notifyExternalChange`, which Sereus's `Database.watch`-based table watches hear (`strand-offline-cadre-core`). Inspection. No Sereus-owned branch to test.
- **Leaving a strand with a queue:** `strand-offline-cadre-guards`. Inspection.
- **Strand moved between cadres, hibernation and resume:** `strand-offline-cadre-guards` and `strand-offline-cadre-core`. Inspection.
- **Two strands sharing a journal store:** labels (`strand-offline-composition`). Inspection.
- **A `'network'` Sereus table written with app tables:** network-acknowledged as a whole (upstream rule) and refused while transactions are queued (guards). Inspection.
- **Mixed versions** (a 1.19 member receiving a queued send from a 1.20 phone): ordinary commit traffic. The adoption ticket's mixed-version notes cover it. No test.
