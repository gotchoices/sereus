# Owner signer seam, owner-key slot, and export/import

First of the owner-key tickets (`docs/architecture.md` → [Owner Keys](../../docs/architecture.md#owner-keys)). This one is purely additive in `@serfab/cadre-core`: three new modules and their exports. `owner-signing-through-one-signer` wires them into the node.

## The signer interface (`owner-signer.ts`)

```ts
export interface OwnerSigningRequest {
	/** The cadre the signatures are for. Every owner digest already binds it (party_id()); a prompting backend shows it. */
	partyId: string;
	/** What the user is approving, in plain words ("Remove the machine 12D3…", "Add owner key ‹label›"). */
	action: string;
}

/** Signs one message (the raw bytes of an owner digest, e.g. buildAuthorizationMessage output); resolves to a base64url Ed25519 signature. */
export type OwnerSign = (message: Uint8Array) => Promise<string>;

export interface OwnerSigner {
	/** base64url Ed25519 public key — the OwnerKey.Key this signer signs for. */
	readonly publicKey: string;
	/** Run one user-approved action. A backend that prompts does so at most once per call and may keep the user's presence until `body` settles. */
	approve<T>(request: OwnerSigningRequest, body: (sign: OwnerSign) => Promise<T>): Promise<T>;
}

/** Thrown by a prompting backend when the user declines or the prompt times out. */
export class OwnerSigningDeclinedError extends Error { … }

export function softwareOwnerSigner(privateKeyB64: string): OwnerSigner;
```

Why `approve(request, body)` and not `sign(payload)`: the control schema verifies one signature per row, and one owner action writes several (a removal signs the delete and its `Revocation` tombstone; a machine removal signs many). A session shaped like this lets `ControlDatabase` keep signing per row while a hardware or biometric backend prompts once per action, as PIV touch caching and the platform vaults' authentication-validity windows allow. Batching all digests into one call was weighed and declined: every writer reads the stamps it signs inside its write lock, so precomputing the batch would duplicate each writer's digest construction outside it.

`softwareOwnerSigner` signs with the existing synchronous `sign(…, 'ed25519', …)` from `@optimystic/quereus-plugin-crypto`, producing exactly the bytes `SeedBootstrapService.signMessageBytes` produces today (base64url of the message as the digest input). It validates the private key up front and derives `publicKey` with `ed25519PublicKeyFromPrivate`.

## The owner-key slot (`owner-key-store.ts`)

- `DEFAULT_OWNER_KEY_ID = 'cadre/owner'` (beside `DEFAULT_IDENTITY_KEY_ID = 'cadre/identity'` in `key-store.ts`). Not party-scoped: one owner key may own several cadres.
- Stored form: the libp2p protobuf bytes of an Ed25519 private key, the same canonical form the identity slot uses, generated with `generateKeyPair('Ed25519')` and converted with `ed25519KeyPairFromLibp2p`. Using that function here is a format conversion of the owner key's own bytes, never a derivation from the node identity.
- `createOwnerKey(keyStore, keyId?): Promise<OwnerSigner>` — generates and persists; refuses with `OwnerKeySlotOccupiedError` when the slot holds anything (never overwrites, so a second "create" cannot orphan the user's key).
- `loadOwnerSigner(keyStore, keyId?): Promise<OwnerSigner | undefined>` — `undefined` on an empty slot; never generates (unlike `loadOrCreateIdentityKey`); corrupt bytes throw; `KeyStoreAccessError` propagates.
- `importOwnerKey(keyStore, privateKeyB64, keyId?): Promise<OwnerSigner>` — idempotent for the same key, refuses (`OwnerKeySlotOccupiedError`) for a different one.
- `readOwnerPrivateKey(keyStore, keyId?)` (or an equivalent) for export only.

## Export / import (`owner-key-export.ts`)

Text forms, following the invitation encoding (versioned prefix + base64url canonical JSON, the helpers `encodeCadreInvitation` already uses):

- Plain: `sereus-owner-key:1.` + `{ v: 1, key, label? }`; `key` is the 32-byte Ed25519 seed, base64url; `label` at most 64 characters.
- Locked: `sereus-owner-key-locked:1.` + `{ v: 1, kdf: { name: 'scrypt', N, r, p, salt }, nonce, sealed }`; `sealed` is XChaCha20-Poly1305 of the plain JSON under the scrypt-derived 32-byte key.

API: `encodeOwnerKeyExport({ privateKeyB64, label?, passphrase? })`, `decodeOwnerKeyExport(text)` → `{ locked: false, privateKeyB64, publicKey, label? } | { locked: true }`, `unlockOwnerKeyExport(text, passphrase)`. One error class `OwnerKeyExportError` with `code: 'malformed' | 'wrong-passphrase' | 'not-an-owner-key' | 'cost-too-high'`.

- Crypto: `scrypt` from `@noble/hashes` (already a dependency), `xchacha20poly1305` from `@noble/ciphers` (add as a direct dependency of cadre-core; 2.1.1 is already installed transitively through `@libp2p/noise`). Both are pure JS, so the same code runs on Node, the browser and Hermes. Random bytes from `crypto.getRandomValues`.
- Encoder default N = 2^16, r = 8, p = 1; the parameters ride in the text, so a later default reads old exports. The decoder refuses N above 2^20 (or r·p beyond a matching bound) with `cost-too-high` before deriving, so a hostile file cannot run the KDF for minutes. Measure the default's time on Node and record it in a code comment; Hermes timing is unmeasured — leave a `NOTE:` at the constant (if a device run shows it is slow, lower N for the locked form or move the KDF to native).
- Cross-refusal by name: `decodeOwnerKeyExport` refuses `sereus-invite:`, `sereus-join-request:` and `sereus-join:` text (`not-an-owner-key`, message naming what it is), and `decodeCadreInvitation` and `decodeCadreJoinRequest` refuse `sereus-owner-key` text by name, as `decodeCadreInvitation` already refuses a join request. That keeps an owner key pasted into an invitation field from being sent to a member.

## Edge cases & interactions

- Empty vs unreadable owner slot: `undefined` only for empty; access failure propagates (same contract as the identity slot, `docs/architecture.md` → Node Key Material). By inspection.
- Create over an existing slot refuses; import of the same key is a no-op; import of a different key refuses. Test (one spec covering the three branches; this is the guard against silently losing a user's key).
- Locked export round trip, wrong passphrase → `wrong-passphrase` (AEAD failure, not a garbled key), tampered `sealed`/`nonce` → `wrong-passphrase`, oversize cost → `cost-too-high` without running scrypt. Test (one spec; the KDF bound is branching logic that pins a named part of the design).
- Plain round trip preserves label; label over 64 characters refused at encode. Covered by the same spec.
- Cross-refusal of invitation / join request / owner-key text in both directions. Test (two assertions in the export spec plus one in the existing invitation decoder spec).
- A signature from `softwareOwnerSigner` verifies under the schema exactly as one from `SeedBootstrapService` does today: assert in the signer's spec against `buildAuthorizationMessage` output and the `verify` the schema uses (this pins the seam's byte contract that every later ticket relies on).
- `approve` with a body that throws propagates the error and leaves no state behind. By inspection for the software backend.
