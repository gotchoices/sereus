## The gap (measured)

Cross-party strand discovery has **no production path at all**. Strand formation
(`/sereus/formation/1.0.0`) carries only **control**-network addresses both ways
(`FormationContactMessage.cadrePeerAddrs`, `strand-formation-protocol.ts:176`;
`FormationResultMessage.cadrePeerAddrs`, `:187`), and `FormationProvisionResult`
(`:129-139`) / `FormStrandResult` (`types.ts:904-918`) carry no addresses. The joiner's
strand seed comes from `CadreNode.resolveCohortSeed` (`cadre-node.ts:4638-4656`), which
asks own-party siblings only (the strand-addr RPC is membership-gated and states
cross-party is out of scope, `strand-addr-protocol.ts:21-28`). So between two parties
the seed is `[]` and the mesh forms only because tests hand-dial
(`strand-formation-e2e.integration.ts:454-457`, `harness/strand-join.ts:101-130`).

## Design

**The formation result carries the responder's live strand-network multiaddrs**, and
the initiator seeds its strand node from them. One-shot by design — durability/refresh
is `backlog/feat-cross-party-strand-addr-durability` (see tradeoffs there).

- `FormationResultMessage` gains `strandAddrs?: string[]`: the responder's live
  strand-network multiaddrs for the provisioned strand, signaling-first (`/p2p-circuit`
  entries first), each ending in `/p2p/<responder strand transport peerId>` (append the
  suffix if `getStrandMultiaddrs` omits it — `groupAddrsByPeerId` drops unattributable
  entries). Disclosed **only after token + disclosure validation**, exactly like
  `partyId`/`cadrePeerAddrs` — a rejection leaks nothing. Cap the list (~16 entries) so
  the frame stays bounded.
- Seam: `StrandFormationManager` cannot reach the strand runtime, so give it a
  `resolveStrandAddrs?: (strandId: string) => string[]` hook (config), wired by
  `CadreNode` to `getStrandMultiaddrs`. Empty/absent is legal — see edge cases.
- `FormStrandResult` gains `strandAddrs: string[]` (possibly empty) so the embedding
  app sees them too.
- **Initiator seeding**: `CadreNode` keeps an in-memory per-strand cross-party contact
  map, written on `formStrand` success. `resolveCohortSeed` unions the map's entries
  into the returned seed, and `launchStrand`/`resumeStrandRuntime`'s
  `mergeStrandPeerAddrs` merge (`cadre-node.ts:4603-4605`) plus each
  `refreshStrandPeerAddrs` pass (`:4833-4884`) re-merge them into the strand node's
  peerStore — the refresh re-merge is what keeps them past the peerStore's one-hour
  address expiry. No re-RPC exists for them (nothing cross-party is dialable
  on demand yet); they are merged as-stored.
- **Responder direction needs nothing**: once the initiator's strand node dials in, the
  strand network's own identify handshake populates the responder's peerStore. The
  strand network has no connection gater by default, so a cross-party dial-in is
  admitted; data authorization stays with the strand schema's signed constraints.
- Docs: update `docs/strands.md` "Within-party answer" / cross-party open question and
  the architecture strand-formation section to describe the carried seed and its
  limits.

## Honest limits (document, do not solve here)

- **In-memory**: an initiator restart loses the map; with no siblings running the
  strand, its seed is `[]` again and the cross-party mesh does not re-form until the
  durability ticket lands. Say so in the docs.
- **Staleness**: if the responder's relay reservation rotates before the initiator
  dials, the carried addr is dead; recovery today is a fresh invitation.

## Edge cases & interactions

- **Strand not live at provisioning** (unbound/open-strand path provisions at
  redemption; the strand may not have launched yet): `strandAddrs` comes back empty.
  The initiator treats empty as "no cross-party seed" and proceeds; the response
  validator (`strand-solicitation.ts` structural default) must NOT reject an empty or
  absent `strandAddrs`. The bound-invite closed-strand path — the release scenario —
  has the host strand pre-created and founded, hence live.
- Wire compat: additive optional JSON field; an older responder simply omits it (no
  backwards-compat guarantee required repo-wide, but the field must be optional so
  mixed builds fail soft, not on parse).
- A malformed entry in `strandAddrs` must be skipped, not fatal (runtime-discovered
  addrs — same posture as `extractCircuitRelayTargets`, `delegate-admission.ts:203`).
- Addrs are scoped to the result's `strandId` only; never merge them into any other
  strand's peerStore or the control peerStore.
- Rejection paths (invalid token, exhausted invite, provisioning timeout) must carry no
  `strandAddrs` — extend the existing disclosure-timing tests.
- `resolveCohortSeed` union: dedupe against sibling-RPC answers; contact-map entries
  must not displace fresher sibling answers (union, signaling-first ordering
  preserved).
- Hibernation resume (`resumeStrandRuntime`, `cadre-node.ts:3874-3886`) must also union
  the contact map.

## Tests

- Unit: formation manager passes `strandAddrs` through post-validation only; empty-ok;
  cap; malformed-entry skip; validator accepts absence.
- Integration: remove the hand-dial at `strand-formation-e2e.integration.ts:454-457`
  (and the harness strand-join hand-dial for this scenario's path) — the cross-party
  mesh must now form from the carried seed alone over direct loopback addresses. The
  relayed cross-party proof is the follow-on `blind-relay-phone-to-phone-e2e`.
