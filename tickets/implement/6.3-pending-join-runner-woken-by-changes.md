# The pending-join runner wakes on a change to its tables

## Background

`PendingJoinRunner` (`pending-join-runner.ts`) carries on, in the background, every join this party asked for through another party's strand invitation (`CadreNode.requestJoin`; behaviour in `docs/strands.md` → "Joining while the inviter is offline"). It is started on every machine and acts only while `isOwner()` is true. Today it runs a *pass* once at start and then every `PENDING_JOIN_POLL_MS` (30 s). A pass:

1. `isOwner()` → `CadreNode.enrolledOwnerSigner` → `ControlDatabase.getOwnerKeys` (reads `OwnerKey` and revoked `OwnerKey` stamps; no reads at all when no owner signer is wired);
2. `readRows()` → `ControlDatabase.queryPendingJoins` (revoked `JoinRequest` stamps from `Revocation`, then one select over `JoinRequest` left-joined to `JoinSuccess` and `JoinFailure`);
3. hands the rows to `observeRows` (stages membership invitations), forgets joins that vanished, and `consider`s each row: schedules a per-join attempt timer for a pending one, ages out a finished one 7 days after its outcome, attempts at once a join held as `joinedHere` or past its expiry.

The *attempts* themselves are not driven by passes: each pending join has its own timer (`scheduleAttempt`), first at a stable fraction of `baseDelayMs`, then on the backoff ladder up to `PENDING_JOIN_MAX_BACKOFF_MS` (10 min). The pass only discovers what changed in the rows: a join asked for or dismissed on another machine, an outcome another machine recorded, this machine becoming or ceasing to be an owner.

**Measured** (#50's two-machine idle scenario, both nodes): the runner costs 24 of the 155 control reads per minute. The join tables are usually never written, so on a two-machine cadre each read of them consults the sibling.

## Design

Copy `StrandWatcher`'s shape (`strand-watcher.ts` → `subscribe`): the runner owns no pass timer; every pass is one run on a `TableChangeWatch`.

**Dependency.** Add to `PendingJoinRunnerDeps`:

```ts
/** Subscribe `onChange` to the tables a pass reads. Absent → `scheduleRuns` (tests). */
watchChanges?(onChange: () => Promise<void>, options: TableChangeWatchOptions): TableChangeWatch;
/** Run a pass at least this long after the last one settled; default {@link PENDING_JOIN_BACKSTOP_MS}. */
backstopMs?: number;
```

The runner builds its watch in `start()`:

```ts
const options: TableChangeWatchOptions = { label: 'pending-join', backstopMs, scheduler: this.scheduler };
this.watch = this.deps.watchChanges?.(onChange, options) ?? scheduleRuns(onChange, options);
this.watch.trigger(0);
```

Passing `scheduler` keeps the spec's fake clock in charge of the fallback's timers.

**Tables.** `CadreNode.startPendingJoinRunner` wires `watchChanges` to `controlDatabase.watchTables([...], onChange, options)` with:

- `CadreControl.JoinRequest`, `CadreControl.JoinSuccess`, `CadreControl.JoinFailure`: what `queryPendingJoins` selects.
- `CadreControl.OwnerKey`: `isOwner()` reads it; a key seated or removed changes whether this machine runs.
- `CadreControl.Revocation`: `queryPendingJoins` and `getOwnerKeys` filter by it. A dismissal or rewrite writes its tombstone in the same transaction as a `JoinRequest` delete, so this is mostly redundant. It is subscribed anyway because the tombstone and the row live in different collections and can replicate separately (a re-seated stale incarnation is hidden only once its tombstone arrives). Revocations are rare at idle (removals only), so the spurious wakes cost little.

**Schedule.**

- Start: `trigger(0)`, as today's `schedulePass(0)`.
- `kick()` (owner signer wired after start): `watch.trigger(0)`.
- A change to any table above: the seam's coalesced, single-flight run.
- **Backstop:** `PENDING_JOIN_BACKSTOP_MS = 10 * 60_000`, replacing `PENDING_JOIN_POLL_MS` (renamed in `index.ts`; no compatibility alias). It covers a machine outside a block's cohort (cadre above 16 machines), a change that arrives without a storage event, and the 7-day age-out of a finished join, which is time-driven (it lands up to 10 min late; acceptable).
- **Pass-level retry, at today's 30 s:** `PENDING_JOIN_PASS_RETRY_MS = 30_000` (module-private). `trigger(PENDING_JOIN_PASS_RETRY_MS)` when a pass throws (today: "the next one retries"), when `consider` throws for a row (today: "the next one retries"), and when `writeOutcome` gives up after `MAX_OUTCOME_WRITE_ROUNDS` (today: "the next pass decides"). Update those three log lines to say "retried in 30 s".
- Per-join attempt timers and their backoff are unchanged. This is how "while something is pending, keep today's retry cadence" is met: the retry cadence of a pending join was always its own attempt timer, never the pass.

**Settled choice: no 30 s pass while a join is pending.** The plan ticket floated keeping the 30 s pass while any join is pending. It is not needed: the pass only discovers row changes, which the subscription now delivers, and pending joins can last up to `MAX_PENDING_JOIN_MS` (30 days), so a pending-time poll would keep today's cost for a whole month whenever an inviter stays offline. The cost of this choice: on a cadre above 16 machines, a dismissal or another machine's outcome reaches a machine outside the block's cohort up to 10 min late (previously 30 s). The worst effect is one extra attempt on a dismissed join, whose outcome write finds the row gone (`resolveLostWrite` → `'gone'`), or a `token-spent` answer whose `onSpent` re-read adopts the other machine's outcome. Put a `NOTE:` on `PENDING_JOIN_BACKSTOP_MS` stating this and the revisit condition (a cadre above 16 machines seen attempting dismissed joins).

**Code removed.** `pollTimer`, `schedulePass`, `clearPollTimer`, `passInFlight`, `passAgain` and `pass()`: the seam provides single-flight and the one follow-up run. `onChange` is a small wrapper over `runPass` that catches, logs and triggers the 30 s retry (the seam also catches, but would not retry).

**`stop()`** disposes the watch (a pass in flight finishes; `running` stops it scheduling more, as `runPass` already checks).

## Edge cases & interactions

- **A pass's own writes wake one follow-up.** An age-out delete, an expiry outcome write or a re-issue commits to the watched tables, so the seam runs one more pass, which must find nothing to do: `consider` on a finished row with no due age-out does nothing, on a pending row with a timer armed does nothing, on a row with an attempt in flight returns. No loop. Verify by inspection; also say so in the review handoff.
- **`requestJoin` on this machine.** Its insert wakes a pass while `attemptNow`'s attempt runs; `consider` sees `entry.attempt` and returns. Same for `dismissPendingJoin` after `forgetRow`. Verify by inspection.
- **A pending join finished on a sibling owner machine.** The sibling's outcome row wakes this runner, which adopts the outcome and cancels its attempt timer (`adopt`). This is the path `backlog/debt-pending-join-finished-on-another-owner-machine-unscenarioed` wants a scenario for; that scenario, if written, covers this wake too. Do not add a second scenario here.
- **Tables not yet touched hear only local commits** (the seam's NOTE). The start pass on an owner machine reads all five tables and arms them. On a machine with no owner signer, `isOwner()` returns before any read, so nothing is armed and replicated join rows are not heard. That is correct: such a machine does nothing with them, and becoming an owner comes through `useOwnerSigner` → `kick()`, whose pass reads and arms. An `OwnerKey` row seating this machine's already-wired key is heard because `isOwner()` read `OwnerKey` in the start pass.
- **Owner signer wired after start** (the common embedder order): `kick()` → `trigger(0)` runs a pass at once, as today.
- **Becoming or ceasing to be an owner by a replicated `OwnerKey` change** now takes effect on arrival (was up to 30 s). Ceasing → `pauseAttempts`.
- **Non-owner machines** still start the runner; each backstop or `OwnerKey` wake costs one `isOwner()` call, which reads nothing without a signer.
- **`kick()` or a change before `start()` / after `stop()`.** `kick` checks `running`; the watch exists only between `start` and `stop`. `stop()` then `start()` on the same instance must build a fresh watch (today `CadreNode` builds a new runner per start, but keep the instance restartable).
- **`watchTables` throwing.** It throws synchronously on an unqualified name or a missing table; all five are in the control schema, and `startPendingJoinRunner` runs last in `start()`, after the control database is initialized. A throw there is a programming error and should fail `start()`.
- **Control database closing.** `CadreNode.cleanup()` stops the runner before closing the database (~5302), and `ControlDatabase.close()` disposes any live watch anyway.
- **`reissueWritesMadeAlone`** (on control-connection growth) is unchanged and not a pass; its rewrite wakes one pass through the change event, harmlessly.

## Tests

Its `advanceToNext` loop fires the earliest timer, which is now an attempt timer or the 10-min backstop instead of a 30 s pass; expect the cases to pass unchanged, and adjust only a case that depended on a 30 s pass (none is expected to: sibling writes in the harness are seen through `onSpent`'s re-read and `writeOutcome`'s `PendingJoinChangedError`, not a pass).
