# Redeem a cadre invitation at any member

## Where this sits

`cadre-invite-schema-and-chain` landed the `CadreInvite` and `CadreInviteUsage` tables, the consent branches and the read-time chain check. This ticket adds the wire protocol, the connection-gate rule and the owner- and device-facing calls. It is additive: `createInvite`, `acceptPhone`, `dialInvite` and the enrollment window stay until `cadre-invitations-redeemable-by-any-member` removes them, so every existing test keeps passing while the new path is built.

## Design (settled in planning)

### The invitation bundle

What the owner hands out (QR, paste, link) is a `CadreInvitation`:

```ts
interface CadreInvitation {
  v: 1;
  partyId: string;
  invitePrivateKey: string;   // base64url ed25519 seed; the proof of possession
  invite: CadreInviteRow;     // the owner-signed row exactly as issued (Key, PeerId, GrantsOwner, ExpiresAt, TotalUses, IssuerKey, IssuerSig, StampId)
  ownerKeys: string[];        // the issuer's anchored owner keys; the redeemer pins them
  members: string[];          // multiaddrs ending in /p2p/<peerId>: the issuer first, then up to INVITATION_SIBLING_MACHINES other members
}
```

Carrying the signed row is what makes the invitation work at a member that has not received the row by replication: the member seats it from the bundle (`seatCadreInvite`, its own transaction) and redeems in the next. This replaces the plan ticket's "answer a retryable unknown" for an unreplicated row; the only retryable refusal left is an issuer the member does not know as an owner yet. `encodeCadreInvitation` / `decodeCadreInvitation` are standalone functions in the protocol module (base64url JSON, as the seed and the open invitation are encoded; decode validates the shape and rejects any other `v`), so a client without a node can decode one. The plan ticket `app-joins-existing-cadre-by-invitation` may wrap the encoding in a URI scheme; the address caps are the open invitation's (`INVITATION_SIBLING_MACHINES`, `INVITATION_ADDRS_PER_SIBLING`; the NOTE there about QR codes applies).

### Protocol `/sereus/cadre-invite/1.0.0`

A new module `cadre-invite-protocol.ts` (message types, codes, handler, dialer), parallel to `strand-formation-protocol.ts` and sharing `control-stream.ts` (`readStreamToEnd`, `exchangeFrame`, `replyAndClose`, `withDeadline`). The seed protocol is left untouched so the plan ticket `node-claim-protocol` can extend `SeedMessage` independently.

Request (device → member), one length-prefixed JSON frame, capped at 64 KiB:

```ts
interface CadreInviteRedeemRequest {
  v: 1;
  invite: CadreInviteRow;   // from the bundle
  peerKey: string;          // the device's ed25519 public key, base64url
  multiaddrs: string[];     // may be empty (a phone); an always-on redeemer gives its listen addresses
  usageStampId: string;     // minted by the device (generateStampId)
  inviteSig: string;        // by invitePrivateKey over the 'redeem' digest
  peerSig: string;          // by the device's identity key over the 'consent' digest
}
```

Reply (member → device):

```ts
interface CadreInviteRedeemReply {
  accepted: boolean;
  code?: CadreInviteRejectionCode;   // iff !accepted
  reason?: string;
  partyId?: string;                   // iff accepted
  invite?: CadreInviteRow;            // the row as this member holds it, iff accepted
  peers?: SeedPeer[];                 // dial hints, unsigned (the seed's isOwner NOTE applies)
}
```

Codes and retryability, in one table like `FORMATION_REJECTION_RETRYABLE`: `issuer-unknown` (retryable: the issuer's `OwnerKey` row is not on this member, or the issuer was removed; the device cannot tell which, so it tries the next address), `invite-invalid` (final: a signature does not verify, the peer key does not match the connecting identity, the row is malformed, or the invitation names another peer), `invite-spent` (final: expired, withdrawn or exhausted), `party-mismatch` (final), `busy`, `conflict` and `internal` (retryable).

Member-side handling, in this order, so no database work happens for a stranger that cannot prove anything: shape check; derive the peer id from `peerKey` (`publicKeyFromRaw` + `peerIdFromPublicKey`) and require it to equal the connection's remote peer, so the row being written is the identity on this very connection; verify `inviteSig` with `invite.Key` and `peerSig` with `peerKey`; `invite.PeerId` null or equal; then `seatCadreInvite(invite)` (an authorization failure → `issuer-unknown`), then `redeemCadreInvite` (exhaustion/expiry/withdrawal → `invite-spent`, the write-retry's transient failure → `conflict`). On success reply with the party id, the row as held and `querySeedPeers()` (move the peer projection `SeedBootstrapService.queryPeers` into `ControlDatabase` and have the seed service call it, so the handler needs no seed service). Concurrency cap and read timeout as the seed handler has (`maxConcurrentRedemptions`, `redeemReadTimeoutMs`), over the cap → `busy`.

Device-side dialer: `redeemAtMembers(libp2p, bundle, request, budget)` tries `members` one address at a time (`dialPeerAddrs` semantics, each under the per-address budget), sends the request under a deadline derived from the link (a relayed dial plus one request, as `seedDeliverTimeoutMs` is), and stops at the first accept or the first final code. A retryable code or a dial failure moves to the next address; when every address is exhausted it throws `CadreInviteUnreachableError` carrying the per-address outcomes, and a final code throws `CadreInviteRejectedError(code, reason)`.

### Gate

`CadreNode.admitInboundControlConnection` gains the check "a live cadre invitation exists" (`ControlDatabase.hasLiveCadreInvite`), placed with the formation check so a stranger pays the two reads only on the deny path; the enrollment window stays for now. `STRANGER_OPEN_PROTOCOLS` adds `CADRE_INVITE_PROTOCOL`, and the module doc of `membership-connection-gater.ts` gets its entry: stranger-facing by design, its own trust decision is the proof of possession, and the exemption is keyed on the expectation of a stranger (a live row), as formation's is. The per-stream control-DB gate needs nothing: the redeemed device's `CadrePeer` write goes through `mutateCadrePeer`, which already notifies the membership hub, so its control-DB streams are admitted by the time the reply is sent.

### Owner-side API on CadreNode

- `createCadreInvitation({ peerId?, grantsOwner, expiresInMs?, uses? })` → `{ invitation, encoded }`. Requires the seed bootstrap service (the owner key); the signing goes through a thin `SeedBootstrapService.insertCadreInvite` like `insertSelfDeviceToken`. Defaults: `uses` 1 always; expiry 15 minutes for an untargeted owner-granting invitation (a bearer credential for admin rights; the doc and the cadre-cli help must say so), 24 hours otherwise. `ownerKeys` come from the node-local anchor only (the existing rule for `createInvite`); an empty anchor throws, because a redeemer verifies the member's reply against these keys and an invitation without them cannot be checked. `members` is this node's addresses (`resolveInviteAddresses`, which honours the pushed NAT addresses) followed by `siblingInvitationAddrs()`, so factor that helper out of `createOpenInvitation` for both callers.
- `listCadreInvitations()` → rows with `live`, `withdrawn`, `usesRecorded`.
- `withdrawCadreInvitation(key)` → the owner-signed tombstone.

### Device-side API on CadreNode

`redeemCadreInvitation(invitation)` → `{ peerId, grantsOwner, redeemedAt: string }` (the member's peer id). Steps: refuse when `invitation.partyId` differs from the node's; `trustOwnerKeys(invitation.ownerKeys, 'invite')` (the pin sticks even if the redemption then fails, as the reference apps already reason for seeds); build the request (the identity signature through `ed25519-key.ts`'s pair-from-libp2p helper; the node's own addresses as `multiaddrs`); dial. On accept: verify `reply.invite.IssuerKey` is one of the pinned keys and `IssuerSig` verifies over the row (the forged-member check: a machine that is not a member of the cadre the invitation names cannot produce an owner-signed row for this key), else throw a final error naming that; merge `reply.peers` into the peerstore with the seed path's merge (factor `verifyAndMergeSeed`'s merge half out so both use it); `retainDialTarget` for the answering member; `refreshMembershipGate('invitation-redeemed')`; `reconcileControlCohort()`. The device then syncs the control database over the connection it already holds, the same unified behaviour as after a seed. When `grantsOwner`, the caller still has to wire its own key for signing (`initializeSeedBootstrap(ownKey)`, which anchors it; never `ensureOwnerKey`, since the `OwnerKey` row arrived by consent). Say so in the method doc; until the plan ticket `owner-anchor-follows-owner-key-changes` lands, other machines accept this device's vouches only after a seed from it.

## Edge cases & interactions

- **Reply dropped after the member committed**: the device retries the next address, or the same one; `redeemCadreInvite` returns `alreadyMember` and the member replies accepted without a second usage. (Protocol test.)
- **The device is already a member through the old path** (owner-vouched row) and redeems an owner-granting invitation: `redeemCadreInvite` seats the `OwnerKey` row only and records a usage. (Covered by the schema ticket's test; inspection here.)
- **Forged bundle** (owner keys and members pointing at an attacker's machine): the device joins that machine's cadre, which is what pasting an attacker's invitation means. The check above only catches a legitimate invitation whose addresses were swapped. State the limit in the method doc.
- **Member runs the relay server**: a stranger is admitted for relay only when no live invitation exists; with one, admitted outright, as for formation. Nothing new; name it in the gate doc.
- **Connecting identity is not the key in the request**: `invite-invalid` before any read. (Test.)
- **Member at its concurrency cap**: `busy`, retryable. (Inspection.)
- **Node without a control database** (a dial-only temporary service): the handler is registered only by a started `CadreNode`, after the control database is up, like the formation responder; `redeemCadreInvitation` needs a started node.
- **Owner mints while alone** (a phone with no connection): the row commits local-only and replicates later; the bundle carries it, so redemption at a member works before replication. The owner's node notes the write for its re-replication path like any other local-only write.
- **Interaction with `node-claim-protocol`**: none on the wire; both are stranger-open protocols with their own proof.

## Tests

- `cadre-invite-protocol.spec.ts`, with an in-process libp2p pair as `strand-formation-protocol.spec.ts` uses: accept end to end (rows present on the member, reply verified on the device); a retryable `issuer-unknown` from the first address moves the device to the second, which accepts; `invite-invalid` stops the dial; a reply whose row is not signed by a pinned key is refused by the device; a dropped reply followed by a retry returns accepted with one usage row.
- `membership-connection-gater.spec.ts`: a live `CadreInvite` row admits a stranger; a withdrawn or expired one does not.
- `createCadreInvitation`: defaults by kind; empty anchor refusal; member list order (self first).
