# Reap container records the provider abandoned mid-flight

Sibling of the cadre-host fix `bug-stuck-provisioning-donation-holds-quota` (see
`DonationService.reapStaleProvisioning` / `DONATION_PROVISIONING_TTL_MS` in
`packages/cadre-host/src/donation/donation-service.ts` and `docs/cadre-host.md`
§ Respawn). cadre-provider has the same crash window and, unlike cadre-host, no
reap sweep of any kind.

## The stuck states

`ContainerService.createContainer` writes the record as `pending` *before*
provisioning starts; `provisionContainer` moves it to `creating` *before*
calling the orchestrator. If the provider process dies anywhere in that window
— or during the orchestrator call itself, which includes a Docker image pull
when `pullPolicy: 'always'` — nothing across a restart advances the record.
There is no in-flight call left to reach its post-create write. Three statuses
can be abandoned this way:

- `pending` — nothing was started; nothing to reclaim.
- `creating` — the orchestrator may or may not have started a container. If it
  did, that container is **orphaned**: it is running under
  `RestartPolicy: unless-stopped`, holding host ports and a volume, and no
  record names its Docker id.
- `stopping` — `terminateContainer` writes `stopping` before stopping and
  removing. A crash here leaves a record that never reaches `stopped`.

A fourth is not a crash window but has the same "nobody is watching this" shape:

- `enrolling` — the in-process `waitForEnrollment` gives up after
  `CONTAINER_ENROLLMENT_TIMEOUT_MS`, and after a provider restart there is no
  waiter at all. A container that came up healthy while the provider was down
  stays `enrolling` forever, which means **it is never metered**:
  `BillingService.collectUsage` only reads `running` records.

## Why the quota is not freed by marking `error`

`BillingService.canCreateContainer`
(`packages/cadre-provider/src/service/billing-service.ts:167`) counts
`c.status !== 'stopped'` as an active container. So `error` records count
against `plan.maxContainers` — and nothing ever deletes a container record
(`ProviderStore.deleteContainer` exists but no service or route calls it;
`DELETE /containers/:id` terminates to `stopped`). A tenant that accumulates
failed provisions is permanently locked out of their plan, and terminalizing a
stuck record to `error` — what the cadre-host fix does — would not free the slot
here. **Both halves are needed**, which is why the quota predicate is part of
this ticket rather than a separate one.

## What to build

### 1. `resolveDockerId` on the orchestrator

Extend the `RecoverableOrchestrator` interface added by the prereq ticket
(`packages/cadre-provider/src/service/orchestrator.ts`) with a second optional
member:

```ts
/**
 * Map a provider container id back to the orchestrator's current handle for it.
 * The reap needs this for a record that names no `dockerId` — the provider died
 * before it could write one — so a container that WAS started can still be
 * found and reclaimed instead of orphaned.
 */
resolveDockerId?(containerId: string): Promise<string | undefined>;
```

Note the deliberate signature difference from cadre-host's synchronous
`DonationOrchestrator.resolveDockerId`: this one is async because Docker is the
source of truth, not an in-memory map. Keep it off the base `Orchestrator`
interface — `HostProcessOrchestrator implements Orchestrator` and carries the
sync version, so a same-named member on the base type breaks that build.

Implementations:

- `DockerOrchestrator` — `listContainers({ all: true, filters: { label:
  ['sereus.container-id=<id>'] } })`, return the first match's `Id`. The label
  is already written on every container it creates (`CONTAINER_ID_LABEL`), and
  because Docker is authoritative this **survives a provider restart** — unlike
  the in-memory `containerPorts` map. Return `undefined` on no match; let a
  Docker error propagate to the sweep's per-record `catch`.
- `MockOrchestrator` — it already stores each create `request`; index by
  `request.containerId`.
- `ProviderProcessOrchestrator` (integration harness) — its `handles` map
  already carries `containerId`; scan it.

### 2. `ContainerService.reapStuckContainers()`

Modelled directly on `reapStaleProvisioning`, including its **re-read guard**:
the candidate list is a snapshot, every reclaim awaits, and an in-flight
provision in the same process can advance a record between snapshot and action.
Re-read each record and re-test the predicate immediately before acting; skip if
it no longer qualifies. Best-effort per record — a failure is logged and the
sweep continues. Return the reaped ids.

Constants, exported and documented alongside the enrollment ones:

```ts
/**
 * Age past which a `pending` / `creating` / `stopping` record is treated as
 * abandoned. Generous compared with cadre-host's 5 minutes because `creating`
 * spans an orchestrator call that can include a Docker image pull
 * (`pullPolicy: 'always'`) over a slow link — and the record is not touched
 * during that pull, so the TTL is the only thing standing between a slow pull
 * and a false reap.
 */
export const CONTAINER_PROVISIONING_TTL_MS = 15 * 60 * 1000;

/**
 * Age past which an `enrolling` record is no longer owned by an in-process
 * `waitForEnrollment` (which gives up after CONTAINER_ENROLLMENT_TIMEOUT_MS),
 * so the sweep may resolve it without two writers racing on the same record.
 */
export const CONTAINER_ENROLLMENT_TTL_MS = 5 * 60 * 1000;

/** How often the sweep runs while the provider is up. */
export const CONTAINER_REAP_SWEEP_MS = 5 * 60 * 1000;
```

Per-status behaviour, age measured from `updatedAt`:

- `pending` / `creating` older than `CONTAINER_PROVISIONING_TTL_MS` → write
  `status: 'error'` with `error: 'stuck in <status> past TTL — provider likely
  restarted mid-provision'` **first**, then resolve a handle
  (`record.dockerId ?? await resolveDockerId(id)`) and, if one is found,
  best-effort `stopContainer` + `removeContainer`. Status-before-reclaim matches
  `terminate`'s ordering in both packages: a crash mid-reap must leave a
  terminal record, not a repeat of the same stuck state.
- `stopping` older than the same TTL → same handle resolution, best-effort stop
  + remove, then `status: 'stopped'`.
- `enrolling` older than `CONTAINER_ENROLLMENT_TTL_MS` → re-run the enrollment
  decision once, reusing what already exists:
  - `fetchContainerHealthStatus` reports healthy → `updateStatus(id, 'running',
    { peerId })`, exactly as `waitForEnrollment`'s success branch. This is what
    closes the never-metered hole after a restart.
  - otherwise probe `inspectRunState` (prereq ticket): child died
    (`restartCount > 0 || exitedAt !== undefined`) → `error` + reclaim.
  - otherwise **leave it alone** and log. An alive-but-not-yet-healthy container
    is genuinely consuming its resources, the record honestly reflects that, and
    `enrolling` is still seedable (`applySeed` accepts it). Do not terminalize a
    tenant's merely-slow node.

Guard the sweep against overlapping itself with an in-flight flag — a sweep that
inspects many containers can outlast the interval.

### 3. Sweep wiring

Mirror `BillingService.start()` / `.stop()`: `ContainerService.startReaper()`
sets a `setInterval` and runs one sweep immediately (so records recovered from
disk are handled at startup, not five minutes later), `stopReaper()` clears it.
Call both from `createProviderServer` in
`packages/cadre-provider/src/server/server.ts` — `start()` next to
`billingService.start()`, and **both** `stop()` and `runShutdownSequence()` next
to `billingService.stop()`. A leaked interval keeps the process alive after
shutdown and hangs the test runner.

### 4. Quota predicate

In `canCreateContainer`, replace `c.status !== 'stopped'` with an explicit
exported set:

```ts
/**
 * Statuses that consume one of a customer's plan slots: everything that may
 * still name live resources. `stopped` and `error` do not — every path that
 * writes `error` reclaims the container first (provisioning failure, enrollment
 * failure, the reap above), and nothing ever deletes a container record, so
 * counting `error` would lock a tenant out of their plan permanently.
 */
export const QUOTA_CONSUMING_STATUSES: ReadonlySet<ContainerStatus> = new Set([
	'pending', 'creating', 'enrolling', 'running', 'stopping',
]);
```

Tripwire to record as a `NOTE:` at `terminateContainer`'s catch (not a ticket):
that catch writes `error` on a record whose stop-or-remove failed, so the
container may still be up while the record no longer counts against quota. It is
the same trade the reap makes deliberately; if provider quota ever has to be
exact rather than generous-to-the-tenant, that catch is the site to revisit.

### 5. Docs

`docs/architecture.md` § `@serfab/cadre-provider` — a couple of sentences on the
reap sweep: which statuses it collects, that Docker labels let it find a
container the provider lost the id for, and that `error` no longer holds a plan
slot.

## Edge cases & interactions

- **In-flight provision must not be reaped.** A `creating` record older than the
  TTL because its image pull is genuinely still running. The re-read guard does
  *not* help here (the pull touches nothing), so the TTL is the whole defence —
  state that in the constant's comment and pick 15 min deliberately.
- **Re-read race.** Snapshot says `creating`, the in-flight provision advances it
  to `enrolling` before the reap acts → the re-read must skip it. Test this
  directly with a store whose `getContainer` returns the advanced record.
- **Orchestrator without `resolveDockerId`.** Reap still terminalizes the record
  and simply has nothing to reclaim (same fallback cadre-host documents).
- **`resolveDockerId` finds a container for an already-`error` record.** Not a
  reap candidate; leave it. The sweep must key off status, never off "Docker has
  a container".
- **Reclaim failure.** `stopContainer`/`removeContainer` throwing must not abort
  the sweep or roll back the status write; log and continue to the next record.
- **`removeContainer` deletes the named volume**, so reaping a stuck `creating`
  record destroys that container's node identity. Correct here — the container
  never enrolled — but call it out in the handoff.
- **Sweep overlapping itself** on a slow Docker daemon → in-flight flag.
- **Interval leak at shutdown** → cleared in both `stop()` and the shutdown
  sequence; assert it in the test that exercises server shutdown.
- **Quota change is tenant-visible.** A tenant sitting at their plan limit
  purely because of `error` records can suddenly create containers again. That
  is the intended fix, not a regression — say so in the handoff.
- **Clock.** Take an injectable `now?: () => Date` on `ContainerServiceOptions`
  (cadre-host's `DonationServiceOptions` does the same) so TTL tests do not
  depend on wall-clock or fake timers.

## Key tests

`packages/cadre-provider/src/service/__tests__/`, over `MemoryStore` and the
existing stub-orchestrator shape:

- `pending` older than the TTL → `error`, no reclaim attempted when nothing
  resolves a handle
- `creating` older than the TTL, `resolveDockerId` finds a container → `error`,
  and `stopContainer` + `removeContainer` called with the resolved id
- `creating` record that already names a `dockerId` → that id is used;
  `resolveDockerId` is not consulted
- `creating` younger than the TTL → untouched
- record advanced out of `creating` between snapshot and action → skipped (no
  write, no reclaim)
- `stopping` older than the TTL → ends `stopped`, reclaim attempted
- `enrolling` past its TTL and healthy → `running`, `peerId` recorded
- `enrolling` past its TTL with a dead child → `error` + reclaim
- `enrolling` past its TTL, alive and unhealthy → untouched
- `enrolling` younger than its TTL → untouched (the in-process waiter owns it)
- reclaim throws → record still terminal, sweep still returns the id, no throw
  out of the sweep
- `canCreateContainer`: an `error` record does not consume a slot; `pending`,
  `creating`, `enrolling`, `running`, `stopping` each do
- `DockerOrchestrator.resolveDockerId` against `fake-docker.ts`: label filter
  hit returns the id, miss returns `undefined`
- server wiring: `stop()` clears the sweep interval (no open handle keeps the
  process alive)
