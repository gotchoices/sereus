# Adversarial cases for the one-redemption formation approval

The schema and writer change is already in the tree (see the prereq ticket for exactly what
landed and where). The prereq ticket makes the existing specs compile and green. This ticket
adds the cases the whole change exists for: proving a copied approval cannot be spent twice
or spent on someone else.

## Background: what one approval covers

When a `FormationInvite` carries a `ValidationUrl`, a `FormationUsage` row is only admitted if
an outside approver enrolled in `CadreControl.ValidationKey` signed a digest over five fields:

```
digest('CadreControl.FormationUsage', 'vouch', Token, UsageStampId, StrandId, PeerId, Disclosure)
```

`UsageStampId` is a single-use nonce the redeeming node mints BEFORE it asks the approver;
`PeerId` is the joining peer. `packages/cadre-core/src/control-database.ts` →
`formationVouchMessage()` builds the identical bytes in TypeScript. Replay is closed twice
over by two INDEPENDENT mechanisms, and keeping them distinct is the point:

- re-presenting an approval **verbatim** repeats its `UsageStampId`, which the column's
  `unique` refuses — a duplicate-row error, **not** a named CHECK failure;
- re-presenting it under **any other** redemption changes a signed field and fails the
  `Authorized` CHECK's `verify`.

## Where the cases go

All of these belong in the `FormationUsage.Authorized validation-key branch` describe block of
`packages/cadre-core/test/control-formation-invite.spec.ts`. The prereq ticket leaves that
block with three helpers to build on: a `Redemption` interface (the five signed fields, named
to spread straight into `recordFormationUsage`), `vouch(privateKey, fields)` (built on
`formationVouchMessage`), and `validatingInvite(tag, { totalUses?, bound? })`.

**Keep the block's record-only shape.** Every case records against a pre-existing owner-signed
strand via `recordFormationUsage` (never `redeemInvitation`) precisely so `Authorized` is the
only constraint that can reject — `StrandExists` is satisfied by the committed strand and
`Monotonic` by the writer's use-number read. That is what makes
`expectConstraintFailure(..., 'Authorized')` a single-rejector assertion; it is documented at
spec:584–596.

**Asserting the duplicate-nonce rejection.** `expectConstraintFailure`
(`test/control-constraint-helpers.ts:24`) matches `/CHECK constraint failed: (<names>)\b/` and
cannot express a uniqueness violation. Use
`rejects.toThrow(/UNIQUE constraint failed: FormationUsage\.UsageStampId/i)` — already
confirmed against the optimystic vtab's message builder
(`quereus-plugin-optimystic/src/optimystic-module.ts` → `uniqueConstraintMessage`, ~line 817,
which renders an UNQUALIFIED table name). Keep the two rejectors distinct deliberately, so a
later refactor cannot collapse them into one accidental pass.

## Cases

- **Cross-joiner replay on a multi-use bound invite — the headline case.** One owner-signed
  host strand, one `ValidationUrl` invite bound to it with `TotalUses` 2+, an approval issued
  for joiner A. A's redemption lands. A second redemption then presents **A's signature** with
  a different `peerId` and its own fresh nonce: rejected by `Authorized` (the nonce is fresh,
  so `unique` cannot be what fires). Then show B is not locked out — the same enrolled approver
  issues B its own approval over B's nonce and peer id, and that lands as use #2.
- **Verbatim replay.** The identical approval re-presented with the SAME `usageStampId`. Every
  signed field matches, so `Authorized` PASSES; the rejector is the nonce's `unique`.
- **Cross-strand replay.** Same token, same joiner, same disclosure, approval filed against a
  DIFFERENT owner-signed strand with a fresh nonce. Use an **unbound** validating invite here:
  the schema deliberately leaves an unbound invite free to name any strand (see the NOTE on
  `FormationUsage.Authorized`), so the own-strand clause cannot fire and the digest's
  `StrandId` field is the single reason for the refusal.
- **Cross-token replay.** An approval minted over another live invite's token, presented for
  this one. Pre-existing behavior (`Token` was always bound); pin it so it cannot regress out.
- **Disclosure tamper.** Disclosure text edited after the sign-off. Also pre-existing behavior;
  pin it.
- **Race retry keeps the approval alive.** This is the ergonomic property the nonce design was
  chosen over binding `UseNumber`, so pin it. `UseNumber` is `max+1` over the table
  (`Monotonic`), so a concurrent redemption invalidates it; binding it would force the loser of
  a race to obtain a SECOND approval (for a manual review queue, a second human review). Shape:
  joiner A commits use #1 while B holds its own approval for use #1; B's in-flight insert —
  fully approved, via the raw helper with B's real `validationKey`/`validationSignature` and the
  colliding `useNumber: 1` — is refused; B then retries the SAME nonce and SAME signature
  through `recordFormationUsage` and lands as use #2. Finish by confirming A's
  already-committed nonce cannot be inserted a second time.
  - The raw helper's rejection may be reported as the `(Token, UseNumber)` primary-key
    collision or as the `Monotonic` CHECK. **Observe which the engine actually emits and pin
    that one** — do not leave a bare `rejects.toThrow()` and do not widen the accepted set to
    cover both.
- **Non-validating invites unaffected.** An invite with no `ValidationUrl` still redeems with no
  approval at all, now carrying the two new columns. The existing case (~spec:711) covers the
  redemption; extend it to assert the returned `usageStampId` is what landed in the row.
- **Approver removal still holds under the new digest.** The existing "stops approving future
  redemptions, does not unwind past ones" case (~spec:722) must still pass. No new case needed
  if it does.
- **Both redemption paths.** `redeemInvitation` (unbound: `Strand` + `FormationUsage` in one
  transaction, mutually-circular deferred CHECKs) and `recordFormationUsage` (record-only). The
  added columns must not disturb the deferral — both CHECKs must still see both rows at commit.
  The existing specs cover this incidentally; no new case needed if they pass.
- **`Monotonic` unaffected.** Sequential use numbers still come out 1, 2, 3 with the new columns
  present (existing case ~spec:261).
