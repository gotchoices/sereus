# Joiner-consent signature: schema-level negative matrix

Split out of `debt-formation-consent-tests-docs` when that run hit its token budget during
investigation, before writing code. Nothing was implemented; everything below is measured,
not guessed. Sibling ticket `debt-formation-consent-e2e-docs` owns the end-to-end assertion
and the documentation.

## Background (what already landed)

`debt-formation-consent-core` made the joining peer sign its own
`CadreControl.FormationUsage` row. The row carries `PeerKey` (the joiner's own base64url
ed25519 public key) and `PeerSig` (its signature). The schema constraint `PeerConsented`
re-verifies that signature on every insert.

Two digests exist over the same table and must never be interchangeable:

| digest | tag | fields, in order | signed by |
|---|---|---|---|
| vouch | `'vouch'` | `token, usageStampId, strandId, peerKey, disclosure` | the approver (an enrolled `ValidationKey`) |
| consent | `'consent'` | `token, usageStampId, peerKey, disclosure` | the joining peer itself |

`strandId` is deliberately absent from the consent digest — the joiner cannot know the
strand when it signs.

## Measured facts the implementer should not re-derive

- **Constraint firing order.** In `src/control-schema.ts`, `PeerConsented` (line ~608) is
  `check on insert` and contains no subquery, so it evaluates at the insert.
  `Authorized` (line ~533) is also `check on insert` but contains a subquery, so it
  auto-defers to commit. When both would fail, `PeerConsented` is what surfaces. Arrange
  every rejection case so exactly one constraint can fail — that is the house rule in
  `test/control-constraint-helpers.ts`, and `expectConstraintFailure` matches ONE name.
- **How to make each constraint the single rejector.**
  - `PeerConsented` cases: pre-insert an owner-signed strand and use
    `db.recordFormationUsage` (not `redeemInvitation`), on an invite with NO
    `ValidationUrl`. That satisfies `StrandExists` and disarms `Authorized`'s vouch branch.
  - `Authorized` cases: supply a consent signature that is valid over the row's actual
    fields, so `PeerConsented` passes and only the vouch check can fail.
- **Helpers already exist; do not re-mint them.** `test/formation-consent-helper.ts` has
  `mintJoiner()`, `signJoinerConsent(joiner, {token, usageStampId, disclosure})` and
  `mintConsent(token, disclosure?, joiner?)` (returns a spreadable
  `{peerKey, usageStampId, peerSignature}`). `test/control-constraint-helpers.ts` has
  `expectConstraintFailure` and `expectUniqueViolation`.
  `signFormationApproval(fields, validationKey, privateKeyB64)` from
  `src/formation-approval.ts` produces a real vouch signature.
  `verifyFormationConsent({token, usageStampId, peerKey, disclosure, peerSig})` lives in
  `src/peer-authorization.ts` and is re-exported from `src/index.ts`.
- **Harness pattern.** `control-formation-invite.spec.ts`'s `beforeAll` boots
  `new CadreNode({ controlNetwork: { partyId, bootstrapNodes: [] }, profile: 'transaction' })`,
  then `db.ensureOwnerKey(ownerPublicKey)`. Copy that shape; ~60 s `beforeAll` timeout.
- **Spending a nonce twice** needs no raw insert: `recordFormationUsage` derives the next
  use number itself, so calling it twice with the SAME consent object against an
  unlimited-use invite yields `UseNumber` 2 and collides on `UsageStampId`'s `unique`.

## Where the new cases go

`control-formation-invite.spec.ts` is ~1587 lines. Put the matrix in a NEW sibling spec,
`packages/cadre-core/test/control-formation-consent-signature.spec.ts`, and MOVE the three
existing cases across so the constraint's coverage lives in one place. They are the
`describe('FormationUsage.PeerConsented joiner-consent branch')` block at roughly lines
1295–1365 of the existing file: the positive path, the wrong-key refusal, and the
seating-rollback case.

Phase 2 — single-field mutations ("lifting consent onto another row")

- Consent minted over a DIFFERENT token, inserted under this one → `PeerConsented`.
- Same key, same token, DIFFERENT nonce signed than inserted → `PeerConsented`.
- Same key, same token, same nonce re-presented after it was spent → `unique` on
  `FormationUsage.UsageStampId`, NOT `PeerConsented`. Assert with `expectUniqueViolation`.
  Keeping these two rejectors distinct is the point — a case refusable by either would go
  green after a refactor that dropped one.
- Consent minted over a DIFFERENT disclosure text than the row carries → `PeerConsented`.

Phase 3 — action-tag disjointness (the two digests cannot stand in for each other)

- The approver's `'vouch'` signature presented as `PeerSig` → `PeerConsented`. Sign the
  vouch digest with the JOINER's own key so the key matches and only the tag plus field
  list differ; otherwise the case proves nothing about tagging.
- The joiner's `'consent'` signature presented as `context.ValidationSignature` →
  `Authorized`. Enroll the joiner's own public key as a `ValidationKey` first, so the
  enrolled-row lookup succeeds and the vouch verify is the only thing left to fail.

Phase 4 — a `ValidationUrl` invite needs BOTH signatures, over the same nonce and bytes

- Both valid → lands.
- Vouch signed over nonce A while the row carries nonce B (consent valid over B) →
  `Authorized`.
- Consent signed over nonce A while the row carries nonce B (vouch valid over B) →
  `PeerConsented`.
- Same pair of cases for a disclosure-text mismatch.
- No vouch supplied at all → `Authorized`.

Phase 5 — `verifyFormationConsent` as a re-checker

  strings).
