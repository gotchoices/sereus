# A harness scenario that really writes into a three-machine control cohort

Split out of `debt-harness-control-cohort-observable-and-forced` (deleted; this ticket and
`debt-harness-cohort-wait-and-force-helpers` replace it). The helpers land in the prereq;
this ticket is the first honest consumer of them.

## The gap this closes

`createTestParty` can start a party with extra machines ("drones"). They connect, but no
harness scenario has ever checked that a control-database write was offered to more than the
writing machine. Measured on `happy-path.integration.ts` with two drones: 213 of 213 cohort
selections reported a single peer. Nothing failed, because a one-member cohort commits on the
writer's own vote (`allowClusterDownsize` defaults to true). So the approval threshold,
replication to a second machine, and the partial-failure write path have never been exercised
from the harness — a regression in any of them passes the suite green.

The prereq-of-the-prereq (`debt-harness-record-fret-ring-convergence-finding`, in `complete/`)
established why, and it is not a structural defect: the owner's peer ring reaches every party
member within about five seconds, so those 213 single-peer selections were writes racing
start-up. Waiting fixes them. What waiting cannot fix: drones dial only the owner and never
each other, so a **drone**-coordinated write caps at two members permanently.

## Decision already made — do not retrofit `happy-path`

`happy-path.integration.ts` is the suite's broad smoke test. Wiring its existing writes onto a
three-machine cohort would bind the canary to the unanimity bar
(`ceil(3 × 0.75) = 3` — every machine must approve), which is a known fragility tracked
separately as `debt-control-write-unanimity-at-three-nodes`. A flaky canary costs more than it
buys.

So: the new scenario owns the multi-machine claim, and the two existing scenarios only get a
comment saying plainly what cohort they do and do not exercise. Concretely —

- `happy-path.integration.ts` — add a short comment to the file header: Bob's party is one
  machine (a genuinely single-machine cohort); Alice's two drones connect but her control
  writes race the peer ring and may be offered to one, two or three machines, so **nothing
  here asserts cohort size** — that claim lives in `harness-party-control-cohort.integration.ts`.
- `basic-connectivity.integration.ts` — same, one sentence: it asserts libp2p connectivity
  only, and a connection is not evidence of cohort membership.

Do not change the behaviour or assertions of either file.

## The new scenario

`packages/integration-tests/src/scenarios/harness-party-control-cohort.integration.ts`.

Header must state, for a reader with no context: what a control cohort is, that a one-member
cohort commits silently so a passing write proves nothing, the ~5 s ring convergence, and the
permanent two-member cap on drone-coordinated writes.

### Case 1 — the drone cap is real and permanent (fast, no writes)

Party with `droneCount: 2`.

- `waitForControlCohort(party, 3)` (owner's view) resolves, and the returned ids are exactly
  the owner's plus both drones'.
- `waitForControlCohort(party, 2, { node: party.droneNodes[0] })` resolves — a drone does see
  the owner.
- `waitForControlCohort(party, 3, { node: party.droneNodes[0] })` **throws** on timeout, with
  a message naming an observed size of 2. Use a short explicit `timeoutMs` (~8 s) so the case
  stays cheap, and assert on the observed-size text, not merely that it threw.

This is the executable form of the recorded finding, and it is deterministic.

### Case 2 — a real (unforced) owner-coordinated write into a three-machine cohort

- Party with `droneCount: 2`; `await waitForControlCohort(party, 3)` first.
- Start `observeControlCohorts()`, take a `callCount()` baseline.
- Issue one real control write — `network.createStrand(party, { schema, type: 'o' })`, the
  same path `happy-path` uses, so it goes through the real `CadreControl` CHECK constraints.
- Read the row back from `party.controlDatabase.queryStrands()`.

**Anti-vacuity assertion, and the subtlety that makes it different from the forced case.**
`observeControlCohorts` patches the prototype, so it records cohort selections from *every*
node in the process — and the drones legitimately see 2. Asserting "every observed size is 3"
is therefore **wrong here** and will fail for a correct system. Assert instead that at least
one selection since the baseline returned ≥ 3, alongside the pre-write wait's returned set of
three ids. Put that reasoning in a comment: the next person to read this will otherwise
"tighten" it to `every` and get a red suite.

**How to assert the write's outcome.** Write it honestly — the write is expected to commit —
then measure. Run the file at least five times and follow this decision tree:

- Commits every run → leave it as a plain `it`. Done.
- Fails every run with `Failed to get super-majority: N/3 approvals (needed 3, …)` → this is
  `debt-control-write-unanimity-at-three-nodes` reproducing. Convert to `it.fails` with a
  header comment naming that slug and the measured behaviour, following the pattern already
  established in `control-write-degraded-cohort-member.integration.ts` (which uses `it.fails`
  for `control-reads-blocked-by-stalled-write`). `it.fails` still runs the body and still
  fails the suite if it ever starts passing, which `it.skip` would not.
- Mixed → do **not** leave a coin-flip in the suite and do **not** weaken it to "passed or
  failed". Keep the deterministic claims as hard assertions (the cohort was three; the write
  settled), and assert that *if* it failed, the failure was the named super-majority error and
  nothing else — flatten the `.cause` chain the way
  `control-write-degraded-cohort-member.integration.ts`'s `errorChainText` does. That excludes
  every other failure mode, so it is not vacuous. Record the observed pass rate in the header.

In all three branches: record the outcome and the measured latency in the ticket handoff.
**Never** lower the super-majority threshold to get green —
`debt-harness-supermajority-threshold-diverges-from-production` deliberately aligned the
harness with production.

### Case 3 — the forced three-member cohort commits deterministically

The counterpart to case 2, and the only way to reach three members on a write a drone
coordinates.

- Same party shape. `forceFullCohort([party.ownerNode, ...party.droneNodes])`, then
  `pinCoordinator([party.ownerNode])` (force first — the pin wraps whatever `findCluster` is
  installed).
- One control write; assert the outcome the same way case 2 settled on.
- Anti-vacuity: here `forced.callCount()` must have grown and **every** `cohortSizes()` entry
  since the baseline must be 3 — forcing substitutes for all nodes, so "every" is correct in
  this case and only this one. Same pattern as
  `control-write-degraded-cohort-member.integration.ts`'s `expectThreePeerCohortConsulted`.
- Tear down `pinCoordinator` first, then `forceFullCohort`.

## Edge cases & interactions

- **`observeControlCohorts` is process-wide** — drone-side selections of size 2 are expected
  and correct. See case 2. Do not filter them out by guessing; if a per-node view is needed,
  use `readControlCohort(party, node)` on the specific node instead.
- **Never hold a force while strand traffic is live.** The prototype patch hits every
  `Libp2pKeyPeerNetwork` in the vitest worker, strand networks included. Case 3 creates a
  strand *row* in the control database, which is a control write — that is fine. Do not
  extend it into starting a strand instance while forced.
- **Restore ordering** — reverse of application, across all three patch kinds
  (`forceFullCohort`, `pinCoordinator`, `observeControlCohorts`). A case that tears down out
  of order leaves a patched prototype live for the rest of the file.
- **Teardown on the failure path.** `waitForControlCohort` throwing inside `beforeAll` leaves
  the party's nodes running and its ports held. Every party this file creates must be shut
  down via `shutdownTestParty` / `network.shutdown()` in `afterAll` regardless of how the
  setup ended, and any active force/pin/observer restored there too — mirror the
  `activeDegradation` pattern in `control-write-degraded-cohort-member.integration.ts`.
- **Case isolation.** Cases 2 and 3 both write; give each its own party so a failed write in
  one cannot leave the other's control database or transaction state mid-flight.
- **Timeouts.** The unanimity failure path settles at ~20–40 s (two 10 s response-deadline
  attempts). Size each `it` timeout above the sum of the deadlines it can pay, so a labelled
  error wins over vitest's anonymous one — same discipline as the degraded-cohort scenario.
- **Ring convergence is ~5 s, not instant.** Do not shorten `waitForControlCohort`'s default
  timeout to make the file feel fast; a too-tight wait turns a real convergence into a flake.
- **Port pressure.** Each party is 3 nodes; the file creates several. Keep the party count to
  what the cases need and release ports on every path.
