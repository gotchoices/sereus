# push-wake-e2e scenario 4: gate denials fixed; a control-DB commit race remains

Continuation of the earlier run of this same ticket (the stream-authz chain root is
`control-repo-protocol-stream-authz`). The previous run hit its token budget mid-
investigation; this file now records what LANDED, what the evidence actually says,
and the one open question.

## What landed (in the working tree, uncommitted — runner commits)

Only `packages/integration-tests/src/scenarios/push-wake-e2e.integration.ts` is
touched. No cadre-core change. The per-stream gate was NOT weakened.

- Scenario 4's sender `S` and receiver `Rx` are now built with
  `bootstrapNodes: [<A's control multiaddr>]`. That puts owner `A` in each of
  their configured-infrastructure sets, which is the already-shipped
  unconditional-admit path (`admitControlPeerUnconditionally` →
  `getBootstrapPeerIds`). Same treatment scenario 2 already gives relay `L` on `Rx`.
- Scenario 4's design-note block gained a new note 3 explaining why (the old note 3

  `seedReceiverRecord` write pair recording the stale-snapshot tripwire below.
- `yarn typecheck` in `packages/integration-tests` passes.

## Corrections to the previous run's root-cause writeup

Two claims in the old ticket body were wrong, and anyone continuing should not
re-derive from them:

- **"A's trusted-owner anchor is empty forever, so A never denies anyone."** False.
  `CadreNode.initializeSeedBootstrap` self-anchors the owner key it is handed with
  source `'genesis'` (cadre-node.ts ~2884). The test helper `makeOwnOwner` calls it,
  so `A`'s anchor is non-empty and `A` *does* judge inbound peers.
- **"The denied peer is A."** It was `A` denying **Rx**, not the reverse. Confirmed
  by matching the denied peer id against the `Wake ack from …` and
  `Incoming strand-addr request from …` lines in the same debug log — both identify
  it as `Rx`.

Why `A` denied `Rx`: the test helper `seedReceiverRecord` calls
`SeedBootstrapService.insertSelfPeerRecord` **directly**, bypassing the `CadreNode`
membership wrappers. Every wrapper (`authorizePeer`, `removePeer`, `addDrone`,
`acceptPhone`, `applySeed`, `registerSelf`) re-materializes the gate snapshot;
the raw service call does not. So after writing Rx's row, `A`'s snapshot stays
`{S}` until the 15-second cohort-reconcile refresh, and for that window `A` denies
Rx's own `…/db-p2p/sync/1.0.0` pulls. This is test-harness-only — a repo-wide grep
shows only tests reach `getSeedBootstrapService()` directly — so it is recorded as a
`NOTE:` tripwire at the write site rather than filed as a defect.

## Measured state

All counts are scenario 4 alone (`-t 'learned by control-DB replication'`).

| tree state | passes | denials seen |
| --- | --- | --- |
| before any fix (previous run) | 0/2 | yes, many |
| **current tree** (bootstrapNodes fix) | **4/5** | bursts in ~2/6 runs; those runs still pass, but take ~17s instead of ~3s |
| bootstrapNodes fix + the two A-writes swapped | 2/6 | **0/6 runs** |

The swap was tried because running `A.authorizePeer` last leaves A's snapshot
`{S, Rx}` and provably eliminates every denial. It was **reverted**: denials went to
zero but the pass rate got worse, and the new failure mode was a
`waitForCrossNodeControlSync` timeout (S never converged on Rx's record) rather
than a commit error — i.e. the swap perturbs commit ordering into a different
failure. The reasoning and the numbers are recorded in the code comment so nobody
re-tries it blind.

## The open question

The residual ~1-in-5 failure is **not** a gate denial. In the failing runs the
debug log contains **zero** `authorizeInboundControlStream: DENYING` lines. The
failure is:

```
PartialCommitError: Legacy multi-tree commit was not atomic: …
  Persisted: [default/CadrePeer]  Not persisted: [default/CadrePeer/index/_uniq_5]
  Underlying: … stale revision: block <id> at rev 2, requested rev 2
              … The stream has been reset
  at SeedBootstrapService.insertCadrePeerRow (seed-bootstrap.ts:343)
```

and it aborts inside `A`'s **first** write (`A.authorizePeer(sPeerId)` — the log
shows `Authorizing peer: <S>` with no matching `authorized successfully`). At that
moment `S` and `Rx` have both skipped `registerSelf` (both log `no self-signing
key` / `no owner service to self-insert`), so no other cadre node is writing. The
one other in-flight actor is the write-while-alone re-replication drain: all three
nodes log `Control cohort grew (0 → ≥1 connection); draining write-while-alone
re-replication queue` roughly 500ms before the failing write.

Whether this race is pre-existing or was introduced by the stream-authz chain is
**unresolved**. The previous run's A/B (baseline `548236e` = 2/2 green, chain HEAD
= 2/2 red) predates the bootstrapNodes fix and is too small a sample to separate a
1-in-5 race from a deterministic break. Scenario 4's own file header and
`tickets/blocked/control-db-convergence-optimystic-p2p` already describe 3-node
control-DB commit instability, so pre-existing is plausible but unproven.
