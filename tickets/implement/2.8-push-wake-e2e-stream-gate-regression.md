# push-wake-e2e scenario 4: intermittent failure caused by the new per-stream control-DB gate

Continuation of `control-repo-protocol-stream-authz-tests-docs` (chain root
`control-repo-protocol-stream-authz`). That work armed a fail-closed
per-stream gate (`CadreNode.authorizeInboundControlStream`) on the four
Optimystic control-DB protocols (`repo`, `cluster`, `sync`, `block-transfer`):
once a node has ANY authorized-member row, further inbound control-DB
streams from peers NOT in that node's materialized authorized set are
denied.

## Confirmed: this is a regression, not pre-existing flake

`push-wake-e2e.integration.ts` was not part of the run-5 validation sweep
(prior ticket ran out of budget before reaching it). Running it now:

- Scenarios 1–3 always pass.
- Scenario 4 ("wakes a member whose authorization and address were learned
  by control-DB replication, not local seeding") fails intermittently —
  failed 2/2 runs I tried, each with a DIFFERENT underlying error (`stale
  revision`, `Cannot write to a stream that is closed`, `Cannot dial self`,
  `Failed to get super-majority: 1/2 approvals`) — a race, not a
  deterministic break.

To confirm this was actually caused by the stream-authz chain (and not
some unrelated pre-existing instability in 3-node commits — the file's own
comments warn those can be flaky), I A/B tested against the commit right
before the chain started (`548236e`, parent of `189392f`):


Baseline: 2/2 clean full-suite runs. Current: 2/2 runs with scenario 4

somewhere in the `control-repo-protocol-stream-authz` chain, not
pre-existing flake — do not add it to `.pre-existing-known.md`.

## Root cause (found via `DEBUG='sereus:cadre:*'`)

Running scenario 4 with cadre debug logging enabled shows one peer
repeatedly denied:

```
authorizeInboundControlStream: DENYING 12D3KooWEn7u...z on
/optimystic/control-pushwake-repl-<ts>/db-p2p/sync/1.0.0 — not in the
materialized authorized set (1 member(s))
```

That denied peer id is node **A** — the scenario's sole owner. Scenario 4
is a 3-node FULL MESH (A, S, Rx all directly connected — the file's own
header note explains this is required so a 3-member commit's cluster can
route between all three, not just to A). Once Rx has pulled and converged
S's authorized row, Rx's `authorizedControlPeers` snapshot becomes `{S}`
(non-empty) — from that point on, ANY other inbound stream to Rx that
isn't from S gets denied by `authorizeInboundControlStream`. That includes
A, because **A's own peer id is never an authorized-member row anywhere**:
A uses an EPHEMERAL libp2p identity (no `privateKey`) specifically so it
never self-publishes a `CadrePeer` row (file's own scenario-4 design note
#3) — ownership in this system is a KEY (`aOwnerPub`), not a peer id, and
by design the two are deliberately NOT bound for A/S in scenarios 2 and 4.

So once ANY of A's fellow cluster members' authorized-set snapshots go
non-empty, A — despite being the party's actual authority and needing to
keep talking to every cluster member as part of the 3-way commit — looks
like an unauthorized outsider to them and gets denied.

This is different from why `control-db-two-node-convergence.integration.ts`
needed repairing: that test is a 2-node shape where A is ONLY ever the
one being dialed (B pulls FROM A) — A's own anchor is empty forever (A
never trusts itself), so A's gate is permanently in the unconditional-admit
branch and never denies B. Scenario 4's problem is the mirror image: A is
also a DIALER into other members, not just a target, and there is no
existing carve-out for "this dialer is my party's owner infrastructure."

## Why "vouch A like a member" does not work

Unlike the two-node-convergence fix (which vouched the READER), A cannot
simply be `authorizePeer`'d as a member here: `isMember`/`isAuthorizedMember`
filter out `row.peerId === selfPeerId` only from each reader's own
perspective — that part would be fine — but the real blocker is that A's
peer id and A's owner key are INTENTIONALLY unbound (ephemeral identity).
There is no way for Rx to cryptographically verify "the dialer holding
this connection is legitimately my party's owner" from peer id alone,
short of a live challenge-response the per-stream gate cannot do
synchronously (see `authorizeInboundControlStream`'s own doc: it must stay
sync/in-memory or it deadlocks).

## Recommended fix direction (not yet implemented)

The codebase already has exactly this kind of carve-out: configured
control bootstrap/relay infrastructure is unconditionally admitted
(`admitControlPeerUnconditionally` → `getBootstrapPeerIds()`). Scenario 2
in the SAME file already relies on it — Rx is configured with
`bootstrapNodes: [lAddr]`, so relay L is always-admitted on Rx regardless
of the authorized-member snapshot. Scenario 2 never hits this bug only
because its commit shape is 2-node ({L, S}); Rx joins last and writes
nothing, so it never needs to admit a THIRD inbound dialer.

Proposed fix: in scenario 4, configure A's control multiaddr as
`bootstrapNodes` on BOTH S's and Rx's `nodeConfig(...)` (mirroring
scenario 2's treatment of L on Rx). This requires starting A first (already
the case), reading `controlAddrs(A)` before constructing S/Rx configs, and
threading it through. No core-code change needed if this works — it reuses
an existing, already-shipped admission path.
