# Every control table has a collection from the party's founding

## Why

A table nobody has written has no Optimystic collection, and Optimystic keeps no memo of an absence, so every read of such a table asks the block's cohort (the machines responsible for it) to prove it absent. On a solo party that is one local lookup. With a second machine it is a round trip to it on every read, and an error or a wait when it is offline (gotchoices/sereus#47 measured this on strands; `strand-founder-commits-every-table-collection` fixed it there). The control reads that hit this on a normal party:

- `JoinedStrand`, read by the strand watcher every 5 s, written only when this party joins another party's strand.
- `JoinRequest`, `JoinSuccess`, `JoinFailure`, read by the pending-join loop every 30 s, usually never written.
- `Revocation`, read before nearly every membership read. Today the Revocation ledger marker (one owner-signed row filed on the owner's first *connected* reconcile pass) exists only to give it a collection.
- `FormationUsage`, counted 2–4 times on a party's first strand formation.

## Design

**Where.** `ControlDatabase.ensureOwnerKey` is the one genesis entry point: the edge node (`edge-node/config.ts` `enrollFoundedOwner`), the CLI (`cadre-cli/src/commands/start-owner.ts` `wireServerOwnerKey`) and the web e2e fixtures all found a party through it, and it inserts only when `hasOwnerKey()` finds no `OwnerKey` row. When it finds none, it first commits an empty collection for every `CadreControl` table, index tree and unique-enforcement tree, then inserts the founding owner key as today.

**Before the insert, not after**, mirroring strand founding's "empty collections before the Header": a crash between the two steps leaves no `OwnerKey` row, so the next start runs genesis again and commits only the collections still missing (the helper syncs only collections in Optimystic's "invented" state — never committed, staged locally by the open). A founder restart finds the row and does nothing, so it can never commit a second, empty history beside a table another machine has since written.

**Why this is fork-safe.** A collection committed while a machine is alone is local-only, and becomes a fork if another machine creates the same collection independently. Before genesis the party has no owner, and no other machine can be admitted without one, so no other machine can hold any of the party's collections. That is the argument the reconcile pass's NOTE (~3912-3921 in `cadre-node.ts`) asked for ("filed inside the genesis transaction, before any other machine can hold the party's collections"). The collections reach a joining machine the ordinary way: its reads consult the cohort, which now includes the founder holding the blocks.

**The helper.** Generalize `createEmptyCollections(db, bridge)` in `quereus-plugin-sereus` to take the schema names: `createEmptyCollections(db, bridge, schemaNames: readonly string[])`. Move the `['Strand', 'App']` list to the strand call site in `compose-strand.ts`; the control database passes `['CadreControl']`. Make the error text in `assertMainCollectionsRegistered` name the schemas rather than "the strand's tables", and add a guard that the named schemas yield at least one optimystic table (the filter is `vtabModuleName === 'optimystic'`; the control tables get that module through `setDefaultVtabName`, not a `using` clause, so a filter that silently matched nothing would leave every control table without a collection while appearing to work). Export `createEmptyCollections` and the `CollectionRegistrySource` type from `quereus-plugin-sereus`'s `index.ts`; `cadre-node.ts` already imports from that entry point, so no new dependency or bundle path is added.

**The control side.** Add `txnBridge: CollectionRegistrySource` to the local `OptimysticPluginResult` interface in `control-database.ts` and keep the bridge from `initialize`. A private step (for example `commitEmptyControlCollections`) runs the helper under `withWriteLock`, because the helper commits whatever is staged in those collections outside any SQL transaction and is sound only while nothing else writes. The lock is not re-entrant, and `insertOwnerKey` takes it itself through `execWrite`, so call the two one after the other, never nested. Log the count committed and the time taken. A failure propagates, as strand founding's does: genesis fails, nothing was inserted, and the next start repeats it.

**The ledger marker stays in this ticket.** After this lands the marker's insert just adds a row to an existing collection, which is harmless. Removing the filing path and its tests is `revocation-ledger-marker-removed`, which follows this ticket.

**Existing parties keep today's behaviour.** A party founded before this has no such collections, and nothing creates them later. `control-store-migrates-on-start` makes the start-time schema apply a migration that every machine runs for itself, with no owner key and possibly while alone; committing missing collections there is exactly the alone-commit fork the marker's connected-only rule avoided. No backwards compatibility is owed (AGENTS.md). Tables added by a later control schema version have the same gap; it is recorded beside the strand analogue in `backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`.

## Cost

About 32 collections: 17 tables, 3 indexes, and the unique-enforcement trees of the `StampId text unique` columns (about 12; count them from the registry). Strand founding measured about 23 ms per empty collection on `FileRawStorage` (`createDeclaredCollections`' NOTE in `strand-membership-writer.ts`), so expect roughly 0.7 s added to genesis on disk, all local on a solo founder. Measure it the way that NOTE did (a lone node over the network transactor, in memory and on `FileRawStorage`, 3 runs), and put the figures in a `NOTE:` at the new step with its tripwire: if genesis latency starts to matter (phone flash under launch contention runs 50–90 ms per storage operation, see the NOTE in `initialize`), commit them in one batch through upstream, which is `blocked/optimystic-empty-collections-commit-in-one-batch` if `strand-founding-writes-batched` has filed it. Do not build a private batching path. The edge node bounds genesis at `DEFAULT_OWNER_GENESIS_TIMEOUT_MS` (60 s, `edge-node/config.ts`); say in the NOTE how far below it the measurement sits.

## Edge cases & interactions

- **Founder restart.** `hasOwnerKey()` finds the row; no empty commits. By inspection.
- **Crash between the empty commits and the insert.** Repeats on the next start, committing only collections still invented. By inspection of `syncInventedCollections`.
- **A row arrives between `hasOwnerKey()` and the insert** (the existing race `ensureOwnerKey`'s callers already handle by re-judging the key). The empty commits then ran against a connected cohort, so they were coordinated commits, not alone-commits. By inspection; no new handling.
- **A machine that runs genesis for a party that exists elsewhere while it cannot see it** (a `--owner` CLI start on an empty store that reaches nobody). Today this already forks `OwnerKey`; this ticket adds empty forks of the other tables to the same mistake. Unchanged in kind; do not add handling here.
- **Concurrent control writers during genesis** (the reconcile pass, self-registration). Excluded by running the step under `withWriteLock`. By inspection.
- **The `vtabModuleName` filter on default-vtab tables.** Covered by the new at-least-one-table guard and by the consult spec's per-call phases going to zero (below); confirm once that the logged count matches the registry's size.
- **Collection ids.** `mainCollectionId` uses `vtabArgs['0']` or `defaultCollectionUri(schemaName, name)`. The control tables' default vtab args carry no `'0'`, so the default URI applies; confirm by the guard in `assertMainCollectionsRegistered` passing.
- **`strand-founding-writes-batched` edits the same helper** (it skips the collections the founding writes itself). Whichever lands second keeps both the schema-name parameter and that skip.
- **The ledger marker, until `revocation-ledger-marker-removed` lands**, is still filed by the owner's first connected pass, into the now-existing `Revocation` collection. Harmless; no change here.
