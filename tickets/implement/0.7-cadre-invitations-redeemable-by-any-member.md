# Invitations redeemable by any member: remove the old path and move the callers

## Where this sits

`cadre-invite-schema-and-chain` and `cadre-invite-redemption-protocol` built the new mechanism beside the old one. This ticket deletes the old one, moves every caller, adds the integration scenario and finishes the docs. No backwards compatibility: a control store written by an earlier build is recreated (the schema ticket already forced that).

## What goes

- cadre-core: `SeedBootstrapService.createInvite`, `acceptPhone`, `dialInvite`, `encodeInvite`, `decodeInvite` and the `CadreNode` wrappers; the types `CadreInvite`, `AddPhoneOptions`, `InviteResult`; `CadreNode.openEnrollmentWindow`, `enrollmentWindowUntil`, `DEFAULT_ENROLLMENT_WINDOW_MS` and the window check in `admitInboundControlConnection` (the live-invitation check from the protocol ticket replaces it); their `index.ts` exports; the tests that pinned them (`seed-bootstrap.spec.ts` invite and `acceptPhone` blocks, `membership-connection-gater.spec.ts` window cases, the `control-stream-authorization.spec.ts` window case, rewritten against a live `CadreInvite` row). `inviteAddressResolver`, `setInviteAddresses` and `invite-address-push.spec.ts` stay: `createCadreInvitation` uses them. `addDrone`, `addPhoneWithRelay` and `authorizePeer` stay: they are the owner-online paths the plan ticket `node-claim-protocol` builds on. Doc comments in `seed-trust-policy.ts`, `trusted-owner-store.ts`, `ed25519-key.ts` and `cadre-node.ts` that say "carried by `CadreInvite.ownerKeys`" now say the cadre invitation's `ownerKeys`.
- cadre-cli admin server: `POST /admin/accept-phone` is removed. `POST /admin/invites` takes `{ peerId?, grantsOwner?, expiresInMs?, uses? }` and returns `{ invitation, encoded }`; add `GET /admin/invites` (the listing) and `DELETE /admin/invites/:key` (withdraw). `admin-client.ts`, `admin-server.spec.ts` and the README's admin route table follow.
- cadre-cli commands: `cadre enroll invite [--peer-id <id>] [--owner] [--ttl <duration>] [--uses <n>]` prints the encoded invitation through the admin route, with the help text saying what an untargeted owner invitation is; `cadre start --invitation <encoded>` redeems at start, right after the node is up and before `--seed` would apply (the two are mutually exclusive), so a headless machine can join a cadre whose owner is offline. The plan ticket `cadre-host-join-a-cadre` relies on this flag for "join by invitation". `enroll create`'s next-steps text mentions both routes.
- cadre-host: the trust circle is deleted outright rather than rewritten, because its one mechanism (`createInvite` on the owner node and `acceptPhone` through `redeemInvite`) no longer exists and the plan ticket `cadre-host-join-a-cadre` removes the trust circle and the founder role anyway. Delete `src/auth/` (service, store, handlers, self-label, their tests), `routes/trust-circle.ts` and its mount, `OwnerNodeClient.createInvite`/`acceptPhone`/`encodeInvite`, the `invite` and `trust` CLI subcommands and `--no-invite`, the Trust Circle UI page, `InviteModal.svelte`, the `trust-circle` route, state and `trust-circle-changed` event, and the `founder.trustCircle` wiring in `bin/host.ts`. The `trust-circle-integration.test.ts` goes with it. Until `cadre-host-join-a-cadre` lands, an operator adds a device to a host-founded cadre with `cadre enroll invite` against the owner node's admin port; say so in `docs/cadre-host.md` where the trust circle section was. Nothing in production called `redeemInvite`; only the integration test did.
- Reference apps: the "Paste enrollment invite (for trust)" input and `ownerKeysFromInvite` go, and `applySeed` loses its pin argument (a seed is applied by a node that already anchors the owner: founding, or a `--pin-owner-key`-style operator pin). In their place, one input "Paste cadre invitation" and a "Join cadre" button that call `redeemCadreInvitation(decodeCadreInvitation(text))` and show the result or the failure code in plain words. That is the thin wiring only; the request/response flows, the deep links and the progress states are the plan tickets `app-joins-existing-cadre-by-invitation` and `reference-apps-join-existing-cadre`. Update `fake-cadre-node.ts` and the view-model specs (NS) and the RN settings tests.
- Integration harness and scenarios: `test-cadre-host.ts` drops its `createInvite`/`acceptPhone` fakes; `control-trio.ts`'s comment names the new path; `control-bring-up-quiet-period.integration.ts` opens the stranger gate by minting a cadre invitation on A instead of calling `openEnrollmentWindow`; `enrollment-e2e.integration.ts` replaces its three invite cases with: owner mints, phone-shaped device redeems at the owner itself and syncs; an expired invitation is refused with `invite-spent`.

## The scenario that proves the feature

New scenario `cadre-invite-any-member.integration.ts`: owner A (phone-shaped: no listen addresses, dials only) founds a cadre and adds always-on member M (`storage` profile, listens on ws) through `addDrone` plus seed delivery, as the existing scenarios do. A mints an untargeted owner-granting invitation (M's address is in its `members` list because M's signed record resolves), waits until M holds the `CadreInvite` row, then stops. Phone-shaped device P, started with only A's owner key as its expected anchor source (it pins from the bundle), redeems at M. Assert: M admits P's control streams and lists P as an authorized member; P's `OwnerKey` row exists on M; P's own `listAuthorizedMembers` lists M once its rows replicate; A restarts, syncs, and lists P as authorized (A is the issuer, so the chain resolves against A's own anchored key). Then A withdraws the invitation and a second device Q is refused with `invite-spent` at M.

Deadlines follow the link declaration as the formation scenarios do; register the file in the topology coverage map if `docs/testing.md` asks for it.

## Edge cases & interactions

- **`cadre start --invitation` on a node that is already a member** (restart with the flag still in the service file): `redeemCadreInvitation` returns `alreadyMember` through the member's idempotent reply; the start logs it and continues. (Covered by the protocol ticket's retry test; inspection here.)
- **`--invitation` and `--seed` together**: refused at argument parsing. (Inspection.)
- **The expired-invitation refusal in `enrollment-e2e`** needs a negative `expiresInMs`; `createCadreInvitation` must accept one for tests, as `createInvite` did. (Test.)
- **A scenario file or doc still naming `openEnrollmentWindow`** after the removal: grep the tree before handing off; the lint gate does not catch prose.
- **The reference apps' seed path without pins**: a phone that is not the founder can no longer apply a seed without an invitation; the two-node startup in `docs/reference-app-rn.md` has the phone as the owner, so it is unaffected. State the limit beside the new input.
