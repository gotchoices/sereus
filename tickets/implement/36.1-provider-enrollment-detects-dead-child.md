# Enrollment must notice the child died, not just wait out the clock

Observed for real during the `provider-seed-accepted` work: a node crashed
during its own startup, and the container record sat on status `enrolling`
permanently. Nothing re-polled it, nothing marked it failed, nothing told the
tenant or an operator. The information needed was already available — the
orchestrator knew the process had exited — but `ContainerService` never asked.

## Where it is today

`ContainerService.waitForEnrollment`
(`packages/cadre-provider/src/service/container-service.ts:208`) polls the
container's `/status` every 2 s for a hard-coded 60 s and then returns
silently. The only exits are "healthy → `running`" and "clock ran out → give up
with a log line". Both the 60 s and the 2 s are inline literals.

The record is left `enrolling`, which:

- counts against the tenant's plan (`BillingService.canCreateContainer` treats
  anything that is not `stopped` as an active container), and
- is skipped by usage metering (`collectUsage` only reads `running` records).

So the tenant is charged a plan slot for a container that never came up and is
never billed for its usage. The crash-loop keeps running too:
`DockerOrchestrator.createContainer` sets `RestartPolicy: unless-stopped`, so
Docker restarts the dead node forever.

## What to build

Give the orchestrator a way to report how a started container is *actually*
doing, and have the enrollment wait consult it.

### The orchestrator capability

Do **not** add the method to the base `Orchestrator` interface.
`packages/cadre-host/src/orchestrator/host-process-orchestrator.ts:119` declares
`implements Orchestrator` and already carries a *synchronous*
`resolveDockerId(id): string | undefined`; a same-named async member on the base
interface would break that package's build. Declare a provider-local extension
instead, in `packages/cadre-provider/src/service/orchestrator.ts`:

```ts
/** How a container the orchestrator started is actually doing right now. */
export interface ContainerRunState {
	/** The container's process is up at this instant. */
	running: boolean;
	/** Times the orchestrator has restarted the child since it was created. */
	restartCount: number;
	/** When the child last exited; absent when it has never exited. */
	exitedAt?: Date;
	/** Exit code of that last exit; meaningful only alongside `exitedAt`. */
	exitCode?: number;
}

/**
 * Optional recovery capabilities beyond the base `Orchestrator`. Optional
 * because a test double or a future orchestrator may not offer them — every
 * caller must keep working (with the pre-existing, weaker behaviour) when the
 * method is absent.
 */
export interface RecoverableOrchestrator extends Orchestrator {
	inspectRunState?(dockerId: string): Promise<ContainerRunState | undefined>;
}
```

`ContainerServiceOptions.orchestrator` becomes `RecoverableOrchestrator`. Every
existing call site keeps compiling — the new member is optional, so any
`Orchestrator` is still assignable.

Implementations:

- `DockerOrchestrator.inspectRunState` — one `container.inspect()`, the same
  call `isRunning` already makes. Map `State.Running`, `State.RestartCount`,
  `State.ExitCode`, and `State.FinishedAt` (Docker writes the zero timestamp
  `0001-01-01T00:00:00Z` when the container has never exited — treat that as
  absent, not as an exit). Return `undefined` when the inspect throws 404
  (container gone); rethrow other errors so a Docker outage is not read as "the
  child is fine".
- `MockOrchestrator` — track `running` and a `restartCount` that stays 0;
  `stopContainer` records `exitedAt`/`exitCode: 0`.
- `ProviderProcessOrchestrator`
  (`packages/integration-tests/src/harness/provider-process-orchestrator.ts:116`)
  — it holds the live `ChildProcess`, so `running` is the existing
  `exitCode === null && signalCode === null` test, `restartCount` is always 0
  (it never respawns), and `exitedAt`/`exitCode` come from the child. This is
  the orchestrator the crash was observed under; implementing it here is what
  makes the observed symptom actually go away in that suite.

### The enrollment change

In `waitForEnrollment`, per poll, **health is checked first** — a container that
restarted once and is now healthy must still enrol normally. Only when the
health read is not `healthy` does the loop probe liveness:

- Probe only when the record names a `dockerId` and the orchestrator offers
  `inspectRunState`; otherwise behave exactly as today.
- Treat the child as dead when `restartCount > 0 || exitedAt !== undefined`.
  Plain `running === false` is **not** sufficient on its own: with
  `RestartPolicy: unless-stopped` a container is briefly not-running between
  restarts, so a single false reading would falsely fail a container that is
  merely bouncing.
- On dead: best-effort `getLogs(dockerId, 50)` into the `debug` log (the
  operator's only view of *why* the node died — do not store log text on the
  record, it is tenant output), then **throw**. `provisionContainer`'s existing
  `catch` already writes `status: 'error'` with the message and calls
  `safeReclaim(dockerId)`, so failure handling and cleanup stay in one place.
  Error message shape: `container process exited during enrollment (restarts=N,
  exitCode=C)`.
- If the probe itself throws, log and keep waiting. A Docker API blip must not
  fail a provision that is otherwise fine.

### Name the constants and make them injectable

Export from `container-service.ts`, in the spirit of
`DONATION_PROVISIONING_TTL_MS` on the cadre-host side:

```ts
/** How long a freshly-created container has to report healthy before the wait gives up. */
export const CONTAINER_ENROLLMENT_TIMEOUT_MS = 60_000;
/** How often the enrollment wait re-reads the container's `/status`. */
export const CONTAINER_ENROLLMENT_POLL_MS = 2_000;
```

Add `enrollmentTimeoutMs?` / `enrollmentPollMs?` to `ContainerServiceOptions`,
defaulting to those constants. Tests drive `provisionContainer` directly and
must not burn 60 s of wall clock to reach the give-up path.

container's process has died, rather than waiting out a fixed timeout.

## Edge cases & interactions

- **Healthy after a restart.** `restartCount > 0` but `/status` reports healthy
  on the same poll → must enrol as `running`. Health is read first precisely
  for this.
- **Slow but alive.** Node still starting, `restartCount === 0`, never exited →
  loop must keep waiting to the full timeout and leave the record `enrolling`
  (unchanged behaviour, no reclaim). A merely-slow node still gets seeded
  because `applySeed` accepts `enrolling`.
- **Probe throws** (Docker unreachable) → keep waiting; provision not failed.
- **Orchestrator without `inspectRunState`** → identical behaviour to today, no
  crash, no `undefined` method call.
- **Record vanished / already `error` mid-wait** → existing early-return still
  wins; do not probe or throw for a record that is gone.
- **Reclaim destroys the volume.** `DockerOrchestrator.removeContainer` deletes
  the named `cadre-<id>-data` volume, so failing enrollment discards that
  container's node identity. That is already what every other provisioning
  failure does (`safeReclaim` on the catch path) and the tenant recreates under
  a fresh container id; do not invent a different policy here, but say so in the
  handoff so the reviewer sees it was deliberate.
- **Crash-loop cleanup.** `removeContainer` uses `remove({ force: true })`, so it
  does kill a container Docker is mid-restart. Confirm the reclaim actually
  stops the loop rather than racing it.
- **Concurrent terminate.** A `DELETE /containers/:id` landing while enrollment
  is waiting sets `stopping`/`stopped` and removes the container. The next poll
  then sees a record that is neither missing nor `error`, and a `dockerId` the
  orchestrator no longer knows. `inspectRunState` returning `undefined` (gone)
  must **not** be read as "died" — leave that record alone and let the loop end.
- **Per-poll cost.** One extra Docker inspect every 2 s per container in
  enrollment, bounded by the enrollment window. Fine at expected concurrency;
  worth a `NOTE:` at the site if many simultaneous provisions ever become normal.

## Key tests

`packages/cadre-provider/src/service/__tests__/` — follow the stub-orchestrator
shape already in `container-provision-cleanup.test.ts`, and inject a short
`enrollmentTimeoutMs`/`enrollmentPollMs` so nothing waits on real time.

- child exited during enrollment → record ends `error` with a message naming the
  exit, `removeContainer` called with the dockerId, and the call returns after
  roughly one poll rather than the full timeout
- `restartCount > 0` but `/status` healthy on that poll → record ends `running`
- alive and never healthy → record still `enrolling`, `removeContainer` not
  called, no throw
- `inspectRunState` rejects → treated as "keep waiting"; provision not failed
- orchestrator without `inspectRunState` → unchanged pre-fix behaviour
- `inspectRunState` resolves `undefined` (container gone) → no `error` written
- `DockerOrchestrator.inspectRunState` against the existing `fake-docker.ts`:
  zero `FinishedAt` maps to `exitedAt: undefined`; a real finish maps through;
  404 → `undefined`; other inspect errors rethrow
