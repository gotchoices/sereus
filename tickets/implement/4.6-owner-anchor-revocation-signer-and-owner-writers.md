# Tombstones carry their signer; owner keys get a signed add and a signed remove

First of three tickets. The next one (`owner-anchor-derivation`) makes every node's trusted-owner anchor follow the `OwnerKey` table, and the last (`owner-anchor-follows-owner-key-changes`) proves it over a real network. This ticket lands the two things the reader-side work cannot do without: a removal a reader can verify from stored columns, and production writers for adding and removing an owner.

## Why the tombstone needs stored columns

A reader judges membership against its node-local anchor (`docs/architecture.md` → "Node-local trusted-owner anchor"). To let an owner *removal* reach that anchor, the reader has to verify that an anchored owner signed the removal. Today `Revocation.Authorized` verifies the owner's signature from the write context and stores nothing; a node that receives the tombstone by replication cannot tell who filed it. `CadrePeer` and `CadreInvite` already solve this by pinning the context pair into the row (`VouchOwner`/`VouchSig`, `IssuerKey`/`IssuerSig`). `Revocation` gets the same treatment.

## Arm 1: `Revocation.SignerKey` / `SignerSig`

In `schemas/control.qsql` and its hand-kept mirror `control-schema.ts` (the drift spec compares them):

- Two columns: `SignerKey text` (the owner that signed the tombstone, equal to the insert `context.OwnerKey`) and `SignerSig text` (that owner's signature over `digest('CadreControl.Revocation', 'remove', TableName, RowKey, StampId)`, equal to `context.Signature`).
- `Authorized` (insert) keeps its `verify(...)` and adds `coalesce(new.SignerKey, '') = context.OwnerKey and coalesce(new.SignerSig, '') = context.Signature`, null-safe as the schema header requires.
- `ReissueOnly` (update) also pins `new.SignerKey = old.SignerKey and new.SignerSig = old.SignerSig`. A re-issue moves only the counter; the re-issue signature stays in context, as today.
- The ledger marker (`openRevocationLedger`) is written through the same path and so stores its signer too. Harmless; its `RowIsGone` branch is unchanged.
- Update the `Revocation` row of the control table list in `docs/architecture.md` and the constraint comments. No warm-start migration: existing control stores are recreated (no backwards compatibility yet, as the invitation tables already state in the docs note under the table list).

In cadre-core:

- `execTombstone` writes both columns. `reissueRevocations`' update statement names only `ReissuedAt`, so it needs no change; confirm by reading it.
- `RevocationRow` (`types.ts`) gains `signerKey` and `signerSig`. `RevokedRowRef` becomes an explicit `Pick<RevocationRow, 'tableName' | 'rowKey' | 'stampId'>` so the eleven sites that build or consume the triple (`noteGuardedDelete`, the pending-revocation queue, `signGuardedRemoval`) do not have to carry the signer. `queryRevocations` reads the two columns and gains a `retry = true` parameter like `queryCadrePeers`, because the next ticket reads it from inside the membership listener with the write lock held.
- `peer-authorization.ts`: `verifyRevocationSigner(row: RevocationRow): boolean`, the never-throws read-side mirror of `Revocation.Authorized` over `revocationDigest(row.tableName, row.rowKey, row.stampId)`, `row.signerSig`, `row.signerKey`. Whether the signer is anchored is the caller's question, as for `verifyCadrePeerVoucher`.

## Arm 2: owner-key writers

The schema already has both branches (`OwnerKey.Authorized`: an owner-signed add pinning `VouchOwner`/`VouchSig`; a remove signed by a *different* owner, with `MinOneOwner` and `RevocationRecorded`). Only tests drive them today, with hand-rolled SQL. Production writers, following the `removePeer` shape (`CadreNode` → `SeedBootstrapService` → `ControlDatabase`):

- `peer-authorization.ts`: `ownerKeyAddDigest(key, stampId)` over `('CadreControl.OwnerKey', 'add', key, stampId)` and `verifyOwnerKeyVoucher(key, stampId, vouchOwner, vouchSig)`, the read-side pair the next ticket uses. The remove digest needs no new builder: `signGuardedRemoval` already builds `('CadreControl.<Table>', 'remove', rowKey, stampId)` for any removable table.
- `ControlDatabase.insertOwnerKeyVouched(key, ownerKey, signMessage)`: through `mutateCadrePeer` (see below); inside the locked body, read whether the key is already live (`queryStampId('OwnerKey', key, false)`) and answer idempotently if so, else mint a stamp, sign the add digest, and insert with `with context OwnerKey = ?, Signature = ?` and `VouchOwner`/`VouchSig` set to that same pair, `VouchUsage` null. Stamps and signatures are minted inside the body because `lockedWithRetry` re-runs it.
- `ControlDatabase.deleteOwnerKey(key, ownerKey, signMessage)`: widen `RemovableTable` to include `'OwnerKey'` and add this as a thin wrapper over `deleteGuardedRow`, through `mutateCadrePeer`, exactly as `deleteCadrePeer` is. Update the comment on `deleteGuardedRow` and the `RemovableTable` doc that say no owner-key removal path exists. Two pre-checks by name before the delete, both read from this node's rows so the schema stays the authority: the signer's own key (`'an owner cannot remove itself'`) and a live owner count of one (`'cannot remove the last owner'`).
- `mutateCadrePeer` is the membership hub for these writers too, so the membership listener (and, after the next ticket, the anchor sync) runs after commit. Update its doc comment to say it covers every membership-relevant write (`CadrePeer`, `OwnerKey`, the invitation redemption that already goes through it). Keep the name; a rename is optional cleanup.
- `SeedBootstrapService.addOwner(ownerPublicKey)` / `removeOwner(ownerPublicKey)`: `requireOwnerPublicKey` first (a keyless service fails before any read, the order `removePeer` pins), then the database call with the service's signer.
- `CadreNode.addOwner(ownerPublicKeyB64)` / `removeOwner(ownerPublicKeyB64)`: require the seed service, shape-check the key with `requireEd25519PublicKeyB64`, delegate. Removal needs no `noteControlWrite`: the tombstone rides the existing committed-delete seam (`noteGuardedDelete`) and is re-issued on cohort growth like every other guarded delete. Export both from the package index as the other owner operations are.

An add committed while the node is alone has no re-issue path (the `CadrePeer` re-touch has no `OwnerKey` equivalent, and `NoUpdate` is load-bearing there). That is filed as `backlog/debt-owner-key-add-while-alone-has-no-reissue`; here, log the committed-alone case loudly at `CadreNode.addOwner`, as the delete path does, and put a `NOTE:` at the site pointing at that ticket.

## Arm 3: `getOwnerKeys()` drops retired stamps

`ControlDatabase.getOwnerKeys` reads the table raw. `OwnerKey` rows are not reaped (`REAPABLE_TABLES` excludes it: `MinOneOwner` makes an automated owner-key reap a party-bricking hazard), so after a removal every node but the remover keeps the physical row with a retired stamp. Filter it the way `queryCadrePeers` does (`queryRevokedStamps('OwnerKey', retry)`), and give the method the same `retry` parameter. `hasOwnerKey` stays raw: it decides the genesis insert and must see any physical row. Consequences, each by inspection:

- `enrolledOwnerSigningKey`: a removed owner stops signing on its own node once it holds its own tombstone, instead of writing rows every converged reader rejects.
- `isCadreInviteLive` / `listCadreInviteStatuses`: an invitation issued by a removed owner reads as not live, so a member answers `invite-spent` rather than admitting a device whose proof chain no reader will accept. This matches what `CadreInviteUsage.Authorized` does on a converged node.
- `projectSeedPeers` (`isOwner` dial hint) and the cohort dial preference in `reconcileControlCohort`: a removed owner is no longer preferred. Both are hints.

## Edge cases & interactions

- **Test fixtures that insert tombstones by hand** (`grep -n "into CadreControl.Revocation" packages/cadre-core/test`) now fail the signer pin until they store the pair. Fix the fixtures; do not weaken the pin.
- **The signer pair survives a re-issue.** `ReissueOnly` pins it; extend the assertion of the existing "update may move only the counter" case in `control-revocation-replay.spec.ts` to the two columns rather than adding a test.
- **Re-adding a removed owner from a machine that still holds the old physical row** fails on the primary key, because `OwnerKey` is not reaped. Loud, not silent. Put a `NOTE:` at `insertOwnerKeyVouched` naming the remedy (an `OwnerKey` reap branch, gated by `MinOneOwner`, is the fix if this becomes routine); the device-removal plan ticket is told below.
- **Removing an owner whose row this node does not hold** is answered as absent (`false`), as `deleteGuardedRow` does for every table. No tombstone is filed. Inspection.
- **The pre-checks read stale local rows.** A concurrent removal elsewhere can make the "last owner" count wrong in either direction; the schema's `MinOneOwner` and the primary-key collision on the tombstone then decide, as the `deleteGuardedRow` note already describes. Inspection.
- **`control-approvals-bound-to-party`** (plan, sequence 4.7) will later add the party id to every digest, including the ones stored here. Keep each digest in its one builder (`ownerKeyAddDigest`, `revocationDigest`) so that ticket changes one site per digest.
- **Idempotent add of a key that is live**: no write, no notification beyond the hub's (the hub notifies whenever the body resolves, as `redeemCadreInvite` already accepts). Inspection.
