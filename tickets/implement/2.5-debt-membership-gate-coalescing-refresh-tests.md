## Remaining work

### Tests to write (`control-stream-authorization.spec.ts`, `refreshMembershipGate` describe)

Use `fakeDb(node)` + `nodeWithMutableRows()`; a "write" is
`fakeDb(node).mutateCadrePeer('peer-insert', async () => { members.push(vouchedRow(X, owner)); })`.

- **A write through a service built OUTSIDE `CadreNode` admits the peer with no explicit
  refresh call** — the historically-missed shape. Gate flips false → true across the write
  alone.
- **Removal drops the peer on return, and the notify fires after commit** — mutate by
  splicing the row out of `members`; assert the snapshot no longer holds it when the write
  resolves. (Do NOT re-assert the hub's own post-commit ordering — `control-membership-hub.spec.ts`
  already owns that against a real DB.)
- **A throwing mutation body fires no notification and leaves the snapshot intact.**
- **A listener/refresh that rejects does not make the write reject**, and the snapshot keeps
  its previous contents (swap `queryCadrePeers` for a thrower mid-test, as the existing
  "keeps the previous snapshot" case does).
- **Coalescing:** N concurrent `mutateCadrePeer` writes ⇒ `fakeDb(node).peerQueries` strictly
  less than N, AND every writer's promise resolves with its own peer already in the snapshot
  (this is the assertion that protects the outer `while` re-check in `refreshMembershipGate` —
  a naive single `await` passes the count check and fails this one).
- **`deferMembershipGateRefresh`:** drive `drainPendingPeerWrites` (or call the private scope
  directly) over N re-issues and assert exactly one refresh — `peerQueries` delta of 1.
- **Teardown:** after `cleanup()`-style detach (`setMembershipChangeListener(null)`), a further
  `mutateCadrePeer` raises no refresh.
- **`registerSelf` insert / cold-start carve-out:** self is filtered out of the authorized set,
  so the automatic refresh there must not turn an empty snapshot non-empty (`snapshot.size === 0`
  ⇒ admit-all must survive).
- The existing `refreshMembershipGate` cases must keep passing (public, idempotent, never rejects).

## Risks worth an explicit look while testing

- `drainMembershipGate` is only safe because `membershipGateDirty` is guaranteed true at the
  moment it is invoked (set synchronously by `refreshMembershipGate` with no await between).
  If it were ever called with the flag already clear, its body would never suspend, its
  `finally` would null the slot *before* the caller's `??=` assigned it, and the caller's
  `while` would spin. Worth a comment or an assertion if the test pass makes it feel fragile.
- `deferMembershipGateRefresh`'s depth counter is instance-level, so it suppresses a
  genuinely concurrent external write's refresh until scope exit (documented on the method).
  Confirm no scope in the codebase is long-lived enough for that to matter.
