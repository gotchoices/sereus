# Require the formation approval to come from an enrolled validation key

## What is going on

A party can mint an invitation (`CadreControl.FormationInvite`) that carries a `ValidationUrl`
— a web hook that is supposed to look at the joiner's disclosure and sign off before the
invitation may be redeemed. The party separately keeps a table of the public keys allowed to
give that sign-off: `CadreControl.ValidationKey`.

Redemption writes a `CadreControl.FormationUsage` row, gated by its `Authorized` CHECK. Today
that CHECK verifies the sign-off signature against a key **the redeemer passes in on the
insert** and never looks at `ValidationKey` at all:

```sql
and (FI.ValidationUrl is null or verify(
        digest('CadreControl.FormationUsage', 'vouch', new.Token, new.Disclosure),
        context.ValidationSignature, context.ValidationKey, 'ed25519'))
```

`context.ValidationKey` is a plain insert parameter. A redeemer generates a throwaway keypair,
signs its own disclosure, passes both, and the gate is satisfied. `ValidationUrl` therefore
buys nothing beyond "supply *some* signature", and `ValidationKey` has no consumer anywhere in
the schema.

## Reproduction — confirmed, and the fix confirmed alongside it

Reproduced in a scratch spec against a real `CadreNode` (empty bootstrap, `transaction`
profile), then re-run with the candidate fix applied. Scratch spec was deleted afterwards —
landing it as-is would mean asserting the hole. The fix's regression tests below are the
permanent version.

| Scenario | Before fix | With candidate fix |
| --- | --- | --- |
| Invite with `ValidationUrl`, redeemed with a **rogue, unenrolled** key + its own valid signature | **accepted** (the bug) | rejected — `CHECK constraint failed: Authorized` |
| Same invite, **no** approval supplied at all | rejected | rejected |
| Same invite, **enrolled** `ValidationKey` signs the `'vouch'` digest | (not reachable — nothing enrolls) | accepted |
| Same invite, enrolled key named but signature from a *different* key | — | rejected |
| Invite with **no** `ValidationUrl` | accepted | accepted (unchanged) |

## The fix

Replace the bare `verify(...)` with an existence test over `ValidationKey`, verifying against
the **stored** key rather than the supplied one:

```sql
and (FI.ValidationUrl is null or exists (
    select 1 from ValidationKey VK
        where VK.Key = context.ValidationKey
            and verify(digest('CadreControl.FormationUsage', 'vouch', new.Token, new.Disclosure),
                       context.ValidationSignature, VK.Key, 'ed25519')))
```

Verified: Quereus handles this nested `exists` inside the outer `exists`'s `where` clause, and
the whole `Authorized` CHECK keeps deferring to commit as before. `context.ValidationKey` stays
in the context tuple — it selects *which* enrolled key is being claimed; `VK.Key` is what the
signature is actually checked against, so a mismatched pair cannot pass.

### Points the fix settles (raised by the source ticket)

- **Removal semantics.** CHECKs run on write only, so `FormationUsage` rows recorded before a
  validation key was removed are never re-examined — the approval was valid when given, and
  the strand it authorized stays formed. Deliberate; say so in the constraint comment. This
  matches `ValidationKey`'s own note about having no per-request read surface.
- **Bootstrap.** No flow relies on redeeming a `ValidationUrl` invite before a validation key
  is enrolled. Checked: no test in the repo redeems a `ValidationUrl` invite (the
  `control-authorization-binding` specs only insert/delete such invites, never redeem), and no
  production caller supplies an approval at all — see below. So there is nothing to weaken
  around.
- **Reference / integration flows.** Nothing to change. `strand-solicitation.ts`'s
  `FormationSigner` hook is not reachable from the formation protocol today (next section), and
  the reference apps never enroll or use a validation key — `reference-app-web` only counts the
  table's rows on its diagnostics screen.

## Scope boundary: the web hook is not wired up at all

Worth knowing before you touch the plumbing, so you do not go looking for a caller that does
not exist. The production redemption path
(`ControlFormationUsageRecorder.recordUsage` / `provisionAndRecord` → `ControlDatabase`) never
passes a `validationKey`/`validationSignature` pair, and `StrandSolicitationService`'s
`validateStrandFormation` — the method that would call the `FormationSigner` hook — is invoked
by nothing outside its own unit test. Consequence: **a `ValidationUrl` invite cannot be
redeemed through the real formation protocol today, before or after this fix** (confirmed
empirically: the no-approval redemption is rejected). The hole this ticket closes is in the
control database's write API, which is the actual security boundary — the control tables are
replicated and their CHECKs are what stop a hostile peer writing directly.

Wiring the hook end-to-end is a separate feature, filed as
`backlog/feat-formation-validation-webhook-unwired`. Do **not** fold it in here.

Also out of scope (as in the source ticket): `context.PeerId` / `context.PeerSignature` on the
same insert are declared and never verified, making an invitation token a bearer credential.
Separate question about invitation design.

## Where the schema lives

The schema is two hand-maintained copies that must stay byte-identical:
`schemas/control.qsql` and `CONTROL_SCHEMA` in `packages/cadre-core/src/control-schema.ts`
(the latter is what actually runs). `control-schema-drift.spec.ts` fails the build if they
diverge — mirror every edit, comments included.
