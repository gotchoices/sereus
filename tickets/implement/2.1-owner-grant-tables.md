# Owner grants: tables, rules and the control-database writers

## Where this sits

The project owner decided (ticket `owner-grant-separate-from-machine-invitation`, now split into `2.1`–`2.7`) that admitting a machine and granting ownership are two separate credentials:

- A **machine invitation** (`CadreInvite`, today's table) admits a machine and never grants ownership. Removing `GrantsOwner` from it is ticket `machine-invitation-grants-no-ownership`.
- An **owner grant** (this ticket's tables) seats an owner key that the holder generates or already holds, and admits no machine. It names no peer id: peer identity and ownership are unrelated. Its protection is possession of the grant's private half, single use, expiry, and how it is handed over.

This ticket is **additive**: the new tables, a second consent branch on `OwnerKey`, the read-side verification, the anchor derivation and the `ControlDatabase` methods. The existing owner-granting `CadreInvite` branch stays until `machine-invitation-grants-no-ownership` removes it. Nothing calls the new methods outside tests until `owner-grant-node-api`.

## Schema

The grant follows `CadreInvite`'s keypair design ("Why the invitation is a keypair" in `docs/architecture.md`): the row holds the grant's ed25519 public key, the holder proves possession by signing with the private half, and any member can verify that signature but never produce it, so a member machine can write the redemption without being able to redeem a grant for itself.

```sql
-- An owner-signed grant of ownership to whoever holds its private half (OwnerGrantUsage.GrantPossessed).
-- Admits no machine and names none. Never deleted: an OwnerKey row seated through it proves itself
-- through the chain key -> usage -> grant, so the row must outlive every key it seated. Withdrawal is
-- an owner-signed Revocation tombstone with the row kept. Liveness: no tombstone, unexpired, uses
-- left, issuer still an owner (OwnerGrantUsage.Authorized).
table OwnerGrant (
    Key text primary key,       -- the grant's ed25519 public key (base64url)
    Label text null,            -- the label the seated OwnerKey row carries, chosen by the issuer
    ExpiresAt datetime null,    -- null: never (a backup grant, chosen explicitly)
    TotalUses int null check (TotalUses >= 0),
    IssuerKey text,             -- the owner that signed the row (== insert context.OwnerKey)
    IssuerSig text,             -- that owner's 'add' signature (== insert context.Signature)
    StampId text unique,
    constraint NotRevoked ...   -- as CadreInvite, TableName 'OwnerGrant'
    constraint LabelLength ...  -- as OwnerKey.LabelLength
    constraint AuthorizedInsert check on insert (
        -- live owner, verify(digest('CadreControl.OwnerGrant', 'add', party_id(), new.Key,
        --   coalesce(new.Label, ''), coalesce(cast(new.ExpiresAt as text), ''),
        --   coalesce(cast(new.TotalUses as text), ''), new.StampId), ...)
        -- and the stored issuer pair pinned to context, as CadreInvite.AuthorizedInsert
    ),
    constraint NoUpdate check on update (false),
    constraint NoDelete check on delete (false)
) with context (OwnerKey text, Signature text);

-- Append-only record of owner-grant redemptions: the proof an OwnerKey row was seated by a grant.
table OwnerGrantUsage (
    UsageStampId text primary key,  -- nonce minted by the holder, signed into both signatures
    GrantKey text,                  -- the OwnerGrant redeemed
    SeatedKey text,                 -- the owner key seated (base64url ed25519)
    SeatedStampId text,             -- the OwnerKey.StampId this usage seats; minted by the writer, not signed
    GrantSig text,                  -- by the grant's private key over the 'redeem' digest: possession
    OwnerSig text,                  -- by SeatedKey over the 'consent' digest: the new key is held
    constraint InsertOnly check on update, delete (false),
    constraint Authorized check on insert (
        -- committed.OwnerGrant G where G.Key = new.GrantKey: no 'OwnerGrant' tombstone for G.StampId,
        -- unexpired against context.Now, uses left (count of committed.OwnerGrantUsage for the key),
        -- and G.IssuerKey a live committed.OwnerKey row (tombstone-aware), exactly as
        -- CadreInviteUsage.Authorized reads CadreInvite
    ),
    constraint GrantPossessed check on insert (
        verify(digest('CadreControl.OwnerGrantUsage', 'redeem', party_id(), new.GrantKey, new.UsageStampId, new.SeatedKey),
               new.GrantSig, new.GrantKey, 'ed25519')
    ),
    constraint OwnerConsented check on insert (
        verify(digest('CadreControl.OwnerGrantUsage', 'consent', party_id(), new.GrantKey, new.UsageStampId, new.SeatedKey),
               new.OwnerSig, new.SeatedKey, 'ed25519')
    ),
    -- deferred, so the same-transaction OwnerKey insert counts (CadreInviteUsage.PeerExists)
    constraint SeatedExists check (exists (select 1 from OwnerKey K where K.Key = new.SeatedKey and K.StampId = new.SeatedStampId))
) with context (Now datetime);

index OwnerGrantUsageByGrant on OwnerGrantUsage (GrantKey);
```

Column names are a suggestion (`SeatedKey` avoids a column named like the `OwnerKey` table and context field); keep whatever reads best, consistently.

**`OwnerKey.Authorized` gains a grant consent branch**, beside the existing invitation one:

```sql
or (old.Key is null and new.VouchSig is null and new.VouchUsage is not null
    and exists (
        select 1 from OwnerGrantUsage U
            where U.UsageStampId = new.VouchUsage
                and U.SeatedKey = new.Key
                and U.SeatedStampId = new.StampId
                and exists (select 1 from committed.OwnerGrant G
                    where G.Key = U.GrantKey and G.IssuerKey = new.VouchOwner
                        and coalesce(G.Label, '') = coalesce(new.Label, ''))
    ))
```

The existing invitation branch requires `new.Label is null`; keep that until `machine-invitation-grants-no-ownership` deletes the branch.

**Revocation**: `'OwnerGrant'` joins the `TableName` list, and `RowIsGone` gets `or (new.TableName = 'OwnerGrant')` beside `'CadreInvite'` (a tombstone there withdraws; the row stays).

**Header comment**: add `OwnerGrant` to the guarded-tables list and to the "never deleted" sentence beside `CadreInvite`.

## Decisions taken here

- **Labels are the issuer's.** The grant row carries `Label`, covered by the issuer's `'add'` signature, and the seated `OwnerKey` row must carry the same label. The issuer is the person making the grant ("Backup", "YubiKey", "Sam's phone") and the apps already ask for a name when making a backup. Rejected: a label chosen by the holder and covered by the new key's consent signature, which adds a field to the redemption and a naming prompt on a fresh device during recovery. One grant with several uses seats several keys under one label; that is acceptable.
- **A separate table, not a kind column on `CadreInvite`.** A kind column would need constraints forbidding a target peer id and a `CadrePeer` row for one kind and requiring them for the other, on a table whose rows are verified at read time by chain; two tables keep each table's rules simple, which the ticket asked to prefer.
- **The seated key need not be fresh.** The schema only requires that the holder proves it holds the key (`OwnerConsented`). The apps generate a fresh key when the device's owner slot is empty and use the slot's key otherwise (`owner-grant-node-api` and the app tickets say why); the rule is the same either way.
- **The single-use race carries over.** The use cap counts committed usage, so two holders of one single-use grant redeeming on different machines may both be seated until merge, and both rows stand. Put the same accepted-tradeoff `NOTE:` on `OwnerGrantUsage.Authorized` that `CadreInviteUsage.Authorized` carries, with the mitigations rewritten for grants: single use and a 15-minute expiry by default, a long lifetime only when the user chooses one, and the owner seeing the extra key in the owner-key list and removing it. Revisit condition unchanged (a cross-machine sequencer). Drop "the targeted form for owner grants" from the mitigations there: grants have no targeted form.

## Digests, verification and anchor derivation

- `control-authorization.ts`: `ownerGrantAddMessage(partyId, fields)` with the field order above (nullable fields as `''`, `ExpiresAt` through `canonicalDatetime` as `insertCadreInvite` does), `ownerGrantRedeemMessage` and `ownerGrantConsentMessage`; the row types `OwnerGrantRow` / `OwnerGrantSignedFields` / `OwnerGrantUsageRow` in `types.ts`, exported from `index.ts`.
- `peer-authorization.ts`: `verifyOwnerGrantAdmission(partyId, row: OwnerKeyRow, usage: OwnerGrantUsageRow, grant: OwnerGrantRow, isAnchored)`, the read-side mirror of the new branch: anchored `vouchOwner` equal to `grant.issuerKey`; `usage.usageStampId === row.vouchUsage`; `usage.seatedKey === row.key`; `usage.seatedStampId === row.stampId`; `usage.grantKey === grant.key`; labels equal; the grant's `'add'` signature, the `'redeem'` signature with the grant key and the `'consent'` signature with the seated key all verify for `partyId`. Same never-throws contract as `verifyInvitationOwnerAdmission`, and the same deliberate omissions (expiry, use count and withdrawal are redemption-time conditions).
- `owner-anchor-sync.ts`: a consent-seated `OwnerKey` row is judged by the grant chain when its `VouchUsage` names an `OwnerGrantUsage` row, and by the invitation chain otherwise (until `machine-invitation-grants-no-ownership` removes that arm). Read the usage and grant rows the way the invitation pair is read now.

## ControlDatabase

Mirror the `CadreInvite` methods; share code where the shape is the same rather than copying it (for example the liveness predicate and the withdrawal-tombstone builder):

- `insertOwnerGrant({ key, label?, expiresAtMs?: number | null, totalUses? }, ownerKey, sign)` → `OwnerGrantRow` (signs and inserts, as `insertCadreInvite`).
- `seatOwnerGrant(row)` → insert-if-absent from a bundle's copy, `CadreInviteIssuerUnknownError`-style refusal by name when the issuer is not an owner here (a new `OwnerGrantIssuerUnknownError`, or generalize the existing error; pick one and say which).
- `queryOwnerGrant(key)`, `listOwnerGrantStatuses()` (live, withdrawn, expired, redemptions), `isOwnerGrantLive(row)`, `countOwnerGrantUsage(key)`.
- Withdrawal tombstones for `'OwnerGrant'` through the same path `withdrawCadreInvite` uses (owner-signed, riding the committed-delete seam so a withdrawal made alone is re-issued).
- `redeemOwnerGrant({ grantKey, seatedKey, usageStampId, grantSig, ownerSig, nowMs? })` → `{ alreadyOwner, seatedStampId }`: one transaction writing the `OwnerKey` row (consent branch: `VouchOwner` = issuer, `VouchSig` null, `VouchUsage` = the usage stamp, `Label` = the grant's) and then the usage row. Idempotent: a live `OwnerKey` row for `seatedKey` already present means `alreadyOwner: true` and nothing written, no use spent. Exhausted grants refused by name before the write (`InvitationExhaustedError` or a grant twin, as `assertCadreInviteSeatRemains`). Through the membership-notifying path, so the hub refreshes and anchors follow. Stamps minted inside the locked body, reads with `retry: false`, as `redeemCadreInvite`.

Any code that walks every guarded table by name (the reaper `reapRevokedRow`, `queryRevocations`, the re-issue drains, `RevokedRowRef` table-name unions) must treat `'OwnerGrant'` like `'CadreInvite'`: a tombstone with the row kept, never a row to reap.

## Edge cases & interactions

- **Seated in the same transaction as granted?** No: the usage reads `committed.OwnerGrant`, so a grant cannot be inserted and redeemed in one transaction, and a member seats a bundle's copy in its own transaction first (as `seatCadreInvite`). Verified by the schema test below.
- **Issuer removed before redemption**: refused by `Authorized` (the tombstone-aware `committed.OwnerKey` clause). Keys it already seated stay owners, and they are among its `dependents` when it is removed (they carry `VouchOwner` = issuer), so `removeOwner`'s re-vouch choice covers them unchanged. Verified by the schema test.
- **Withdrawn, expired, exhausted**: each refused by `Authorized`. Verified by the schema test.
- **The seated key is already a live owner**: `alreadyOwner`, nothing written, no use spent. Verified by the schema test.
- **The seated key was removed earlier**: a fresh stamp is minted, so `NotRevoked` passes and the re-seat succeeds. A machine holding that key's tombstone without its delete refuses by name, the limit already documented at `insertOwnerKeyVouched`; check the same refusal reaches this path and say so in the handoff.
- **A grant-seated key's label** must equal the grant's; a writer that drops or changes it is refused. Verified by the schema test.
- **Forged chain on read**: a replicated row whose usage or grant fails any link is not derived into the anchor. Verified by one anchor test.
- **Reaper and re-issue**: never delete an `OwnerGrant` row (it has `NoDelete`). Verified by inspection of every table-name switch.
