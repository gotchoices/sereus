# The formation provisioning step needs its own timeout budget

## What happens today

`strand-formation-protocol.ts` has two timeouts: `sessionTimeoutMs` (default 30 s) for a whole
formation session, and `stepTimeoutMs` (default 5 s) for each individual wire step. The
initiator waits for the responder's result frame under `stepTimeoutMs`:

```ts
const response = await withTimeout(stepTimeoutMs, `Formation await-response#${id}`, ...)
```

But that "step" is not a wire step. Between reading the contact frame and writing the result
frame the responder runs `provisionStrand`, which performs real work: reading the invite, and —
in `ControlFormationUsageRecorder` — writing `FormationUsage` (and, on the unbound path, a
`Strand` row) through the replicated control database. Once `feat-formation-approval-wiring`
lands it also makes an outbound HTTP call to the invitation's approval hook.

Five seconds is not a sane budget for that. Worse, the failure is asymmetric: the initiator
gives up while the responder keeps going and commits, so a single-use invitation is spent on a
join the joiner believes failed.

The responder has no per-provisioning budget at all — a hook or a database call that hangs is
bounded only by the 30 s session timeout, and when that fires the session dies without ever
sending a result frame, so the initiator sees a read error rather than a reason.

## Change

Introduce a third budget, `provisionTimeoutMs`, distinct from the per-wire-step budget:

- `FormationListenerOptions.provisionTimeoutMs` — default **12_000**. The responder wraps its
  `provisionStrand` hook call in `withTimeout(provisionTimeoutMs, ...)`.
- `FormationDialOptions.provisionTimeoutMs` — default **15_000**. The initiator uses it for the
  `await-response` read only. `dial-connect` keeps `stepTimeoutMs`.
- `StrandFormationManagerConfig.provisionTimeoutMs` — threaded into both by
  `StrandFormationManager` (listener construction and `dialFormation` options).

The default ordering is deliberate and must be stated in a comment where the constants live:

```
approval hook (10 s, feat-formation-approval-client)
  < responder provisioning (12 s)
  < initiator await-response (15 s)
  < session (30 s)
```

Each layer must be able to fail and report before the layer above it gives up. The margin
between 12 s and 15 s is the wire latency for the result frame.

Responder-side timeout handling: catch the provisioning timeout **explicitly** inside
`runSession` and `send({ approved: false, reason: 'Formation provisioning timed out' })`. Do not
let it fall through to the generic `catch`, which reports `'Internal formation error'` — the
joiner should be told this is a retryable timeout, not an internal fault. Keep the existing
`log(...)`-then-convert shape so the failure is still recorded (AGENTS.md: don't eat
exceptions silently).

## Edge cases & interactions

- **Misconfiguration where provisioning outlives the session** — if `provisionTimeoutMs >=
  sessionTimeoutMs`, the session timeout fires first and no result frame is ever sent, which is
  exactly the failure this ticket removes. On construction, log a warning and clamp
  `provisionTimeoutMs` to `sessionTimeoutMs - stepTimeoutMs`.
- **Existing callers that set only `stepTimeoutMs`** — tests and the integration harness set a
  short `stepTimeoutMs` to make timeout cases fast. After this change those no longer shorten
  the await-response wait. Grep for `stepTimeoutMs` in tests and set `provisionTimeoutMs`
  alongside it wherever a test is asserting a slow-responder timeout.
- **Timeout fires while the write is in flight** — the responder still commits. That is
  pre-existing (a joiner timeout has always been able to race a commit) and this ticket only
  narrows the window; do not attempt to make provisioning cancellable. Leave a `NOTE:` at the
  responder timeout site saying the row may still land and the invite use may still be spent.
- **The `maxConcurrentSessions` interaction** — a longer provisioning budget means sessions
  occupy slots longer, so a slow hook can exhaust `maxConcurrentSessions` and make the listener
  reject fresh joiners with `'Too many concurrent formation sessions'`. Fine now (the default
  cap is not tight); record it as a `NOTE:` at the cap, not as a ticket.
- **Zero / negative configured values** — treat `0` as "use the default", not "time out
  immediately"; a caller passing `0` almost certainly means unset.
