# A strand commit's durability reaches the app

GitHub gotchoices/sereus#44 (a joiner that writes while no other member is connected, then stops, loses the write) and optimystic#26. Sereus decided not to refuse or hold such a write (`docs/strands.md` → Joining → "Writable does not mean connected"); the remaining gap is that the app is never told the write is held only on this machine. Optimystic main (`1b352916`, the release candidate linked here through root `resolutions`) now reports it. This ticket passes it through to the app. The reference apps' "not yet delivered" mark is the follow-up `reference-apps-mark-undelivered-messages`.

## What Optimystic provides (read the shipped code, do not restate it)

`register(db, config)` from `@optimystic/quereus-plugin-optimystic/plugin` now also returns:

- `onCommitDurability(listener) => unsubscribe`. After every SQL commit that wrote something, called once, **synchronously, before the commit returns**, with a frozen `SqlCommitDurability { transactionId, durability: { collections, overall }, tables, followed }`. `transactionId` is what `StampId()` returns inside that transaction.
- `onCommitFullyHeld(listener) => unsubscribe`. Called once with `{ transactionId }` when a `followed` commit that was below full replication becomes held by its whole cohort. Always after that commit's durability report; it can fire **synchronously right after the report, inside the same commit** (the follower's `covered` verdict).
- `dispose()`: `txnBridge.dispose()` (drops the follower's subscription to the node's `StorageRepo` and forgets every followed commit), then `collectionFactory.dispose()`.
- `isFullyDurable` and the four types are re-exported from the plugin entry.

Followed commits live in memory: a database close, a hibernation, or a restart forgets them, and no event ever fires for a forgotten one (upstream backlog `feat-a-host-can-ask-whether-an-earlier-commit-is-fully-held`).

## Matching a report to the app's write

Verified during planning against the linked builds (`test` transactor): a single statement `insert … returning StampId() as Tx` through `db.get(...)` or `db.eval(...)` returns the commit's id, and the plugin's report for that id has already been delivered by the time the statement resolves. That is exact even on a `Database` cadre-core's background writers share (the membership writer, the reconciler): one statement is one hold of Quereus's execution mutex, so no other writer's commit is mixed in. "Take the reports delivered while my `await db.exec` ran" is **not** exact here — a report from a background writer that held the mutex while the app's exec waited would be taken as the app's.

Because the report (and possibly the fully-held event) arrive before the app learns its id, cadre-core keeps a short record of recent commits that the app reads afterwards by id.

## Design

### `@serfab/quereus-plugin-sereus`

- `SereusPluginResult` gains `onCommitDurability` and `onCommitFullyHeld`, forwarding to the optimystic plugin result. `index.ts` re-exports the types `SqlCommitDurability`, `CommitFullyHeld` (from the optimystic plugin entry).
- The local shim `OptimysticPluginResult` in `compose-strand.ts` gains those two plus `dispose` (or `txnBridge.dispose`).
- **Every release path disposes the transaction bridge.** Today `releaseCollectionFactory` calls only `collectionFactory.dispose()` / `shutdown()`, so the bridge's durability follower stays subscribed to the strand node's `StorageRepo` after the database is closed. cadre-core keeps the node across a database rebuild (deferred-join retry, hibernation wake), so each rebuild would leak a subscription, and the old bridge would keep matching events against commits nobody listens for. Release the bridge first, then the factory as today (the created-node path still needs `shutdown()`; check whether calling the plugin's `dispose()` and then `collectionFactory.shutdown()` disposes the factory twice and whether that is safe, or call `txnBridge.dispose()` directly). This covers `shutdown()` and the failed-composition `catch`.
- README: one short paragraph under the result description naming the two listeners, pointing at the optimystic README for the semantics.

### `@serfab/cadre-core`

New module `strand-commit-durability.ts`:

```ts
/** What one commit on a strand wrote, and whether it survives this machine stopping for good. */
export interface StrandCommitDurability {
  readonly strandId: string;
  /** `StampId()` inside the committed transaction. */
  readonly transactionId: string;
  /** Another member holds every block the commit wrote: the overall answer is `majority` or `full`
   *  (`durabilityRank` from `@optimystic/db-core`). False for `local`, `unrouted`, or an unknown
   *  overall (`undefined`). Becomes true once `strand:commit-held` fires for the commit. */
  readonly heldElsewhere: boolean;
  /** The plugin's `followed`: when `heldElsewhere` is false, `strand:commit-held` will fire for this
   *  commit if it reaches the others while this database stays open. False means nothing will say so. */
  readonly followed: boolean;
  /** The plugin's report, for per-table detail. */
  readonly report: SqlCommitDurability;
}
```

Why `majority` counts as held elsewhere: a strict majority of a cohort of at least two is at least two machines, so the write survives this one stopping, which is the case #44 is about. Do not compare quorum strings by hand in apps; this field is the one place the rule lives.

`StrandDatabase`:

- `StrandDatabaseConfig` gains optional `onCommitDurability?: (commit: StrandCommitDurability) => void` and `onCommitHeld?: (event: { strandId: string; transactionId: string }) => void`.
- `initialize()` subscribes to both plugin listeners right after `connectToStrand` returns (before the founder bootstrap, so its commits are reported like any other). `close()` unsubscribes (the plugin's dispose also drops them; unsubscribe anyway so a late event from a closing database is not forwarded).
- A bounded record of recent commits (256, oldest dropped first; `NOTE:` tripwire at the cap: "if an app reads a commit's durability later than 256 commits after it, raise this or let the app pass the id up front"). A held event updates the record's `heldElsewhere` to true; a held event for an id not in the record is still forwarded.
- `commitDurability(transactionId): StrandCommitDurability | undefined` — a fresh snapshot of the record entry, so a caller that reads after a `covered` held event sees `heldElsewhere: true`. Throws like `getDatabase()` before initialize.
- The record is updated **before** forwarding, and a throwing forward callback is caught and logged, so an app handler that throws neither breaks the record nor is mistaken by the plugin for its own listener's failure.

`StrandInstanceManager` / `CadreNode`:

- `StartStrandConfig` gains `onCommitDurability` / `onCommitHeld`, retained with the launch config exactly like `onWritable` (so a hibernation wake's rebuilt database is wired too), and passed into each `StrandDatabase` it builds.
- `CadreNode` wires them to two new events in `CadreNodeEvents` (types.ts):
  - `'strand:commit-durability': StrandCommitDurability`
  - `'strand:commit-held': { strandId: string; transactionId: string }`
  Doc comments: emitted synchronously inside the commit, so keep handlers short; covers every commit on the strand database, including cadre-core's own membership writes, so an app filters by the ids it holds; a commit made before a listener attached, or forgotten by a close, hibernation or restart, never gets `strand:commit-held`.
- `index.ts` exports the `StrandCommitDurability` type.

## Edge cases & interactions

- **Background writers on the same database.** Membership writes produce reports and events too. Correlation is by id only (the `returning` pattern); verified by inspection and stated in the event docs.
- **Held before the app asks.** A `covered` commit fires its held event inside the commit, before `db.get` resolves. The record must reflect it — by inspection of the record update order.
- **Commit that wrote nothing** (`insert or ignore` that ignored, an update matching no rows): no report, so `commitDurability(tx)` returns `undefined`; documented, and the follow-up ticket's apps treat `undefined` as "nothing new to mark".
- **Database rebuilt on the same node** (deferred-join retry `awaiting-seed`, hibernation wake, `discardDatabaseAttempt`): the old bridge is disposed on release (the compose-strand fix), the new database subscribes fresh, its record starts empty. By inspection of every `close()` path in `strand-instance-manager.ts` (lines ~1114, 1148, 1284, 1287).
- **Storage replica** (no sApp): same wiring; it writes only membership rows. No special case.
- **Gated joiner** (`'syncing'`): the database is withheld from the app until writable, but it is subscribed at `initialize()`, so nothing is missed.
- **Lone founder before anyone joins:** every commit is `local`, followed, and stays not-held-elsewhere until a member joins and takes the copies. Correct ("nobody else has it"); say so in the docs section.
- **`followed: false` below `heldElsewhere`** (a ledger fault, `unrouted`, holders unknown, a commit coordinated by another machine whose answer was below `majority`): no event will come; documented as "nothing will say so this session".
- **Throwing app handler** on either CadreNode event: caught and logged in `StrandDatabase`'s forward; the commit and the record are unaffected.
- **`test` / `local` transactors** (quereus-plugin-sereus unit tests): reports arrive with `followed: false` and no held events; nothing breaks.
- **Version floors:** the API exists only in the linked Optimystic RC; the `^1.12.1` floors stay until the release is adopted (that step lives on `blocked/optimystic-write-made-alone-owes-no-one`). Say so in the review handoff; do not edit floors here.
- `cadre-node.ts` is the subject of `backlog/debt-cadre-node-single-file-size`; keep the additions there to the event wiring.
