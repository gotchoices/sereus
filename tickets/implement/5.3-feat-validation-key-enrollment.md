# Surface approver-key enrollment

An invitation carrying a `ValidationUrl` is only redeemable if the approval it comes back with
is signed by a key the party has enrolled in its `ValidationKey` table. `ControlDatabase` already
has `insertValidationKey` and `deleteValidationKey` (both owner-signed, with the removal writing
the required `Revocation` tombstone in the same transaction), but nothing above that layer calls
them: `CadreNode` exposes no method, and there is no command or UI. A party therefore cannot
enroll the approver whose sign-off its own invitations demand.

This ticket adds the read query, the node-level API, and a headless command. It is independent
of the approval-client and wiring tickets — the database calls it needs already exist — but it is
what makes those two usable end to end.

## Read query

`ControlDatabase.queryValidationKeys(): Promise<string[]>` — `select Key from
CadreControl.ValidationKey`, sorted, mirroring the existing read helpers' shape.
`queryValidationKeyStampId` already exists for the single-row case; do not duplicate it.

## Node API (`cadre-node.ts`)

Three methods modelled directly on `publishStrand` / `publishFormationInvite` — same
`getSelfSigningKey()` lookup, same `sign(message, ..., 'bytes', 'base64url', 'base64url')`
callback, same loud failure when the node is not started or exposes no owner signing key:

```ts
/** Enroll an approver public key allowed to sign off on ValidationUrl redemptions. */
async enrollValidationKey(key: string): Promise<void>;

/** Remove an approver key. Narrows who may approve FUTURE redemptions only — the schema's
 *  CHECKs run on write, so joins already approved by this key stay valid. Say this in the
 *  doc comment; it is the single most likely operator misunderstanding. */
async removeValidationKey(key: string): Promise<void>;

/** The approver keys currently enrolled. */
async listValidationKeys(): Promise<string[]>;
```

## CLI (`packages/cadre-cli/src/commands/validation-key.ts`)

Follow `commands/strands.ts` exactly: resolve the config file, construct a `CadreNode`, wait for
`control:connected` with a timeout, act, print, stop, exit. Same `-c, --config`, `--json`,
`-d, --debug` options.

```
cadre validation-key add <key>      Enroll an approver public key (base64url)
cadre validation-key remove <key>   Remove an approver public key
cadre validation-key list           List enrolled approver keys
```

Register it in `src/bin/cadre.ts` and re-export from `src/index.ts` alongside the other commands.
`add`/`remove` print a one-line confirmation; `list` prints one key per line, or a JSON array
under `--json`, and says "No approver keys enrolled." when empty.

## Edge cases & interactions

- **Node not started / no owner signing key** — throw with the same message shape
  `publishStrand` uses (which names owner genesis as the fix). The CLI catches, prints to
  stderr, and exits non-zero. Do not let a missing signing key surface as a raw constraint error.
- **Removing a key that is not enrolled** — `deleteGuardedRow` is already a documented no-op
  (no throw, no tombstone). Keep that, and have the CLI say "not enrolled — nothing to do"
  rather than claiming a removal happened.
- **Enrolling a key that is already enrolled** — the row exists and `StampId` is unique, so the
  insert fails. Report it as "already enrolled" rather than surfacing the raw error.
- **Malformed key input** — reject empty/whitespace before writing. Anything that reaches the
  database and fails the signature check produces an opaque constraint error, which is exactly
  the class of failure this ticket set out to avoid.
- **Rotation is add-then-remove, in that order** — removing the only enrolled key while
  `ValidationUrl` invitations are outstanding makes every one of them unredeemable until a new
  key is enrolled. The `remove` command should warn when it is about to remove the last key.
- **Removal is not retroactive** — assert it in a test (a redemption approved before removal
  stays valid; the row is not re-examined), so a later reader does not "fix" it into a
  retroactive revocation.
- **Convergence** — a key enrolled on one cadre node is visible to a sibling only after control
  replication converges, so a redemption arriving at a node that has not caught up is refused
  as not-enrolled. Same class as the existing `Strand.StampId` convergence notes in
  `schemas/control.qsql`; record it as a `NOTE:` at `enrollValidationKey`, not as a ticket.
- **Node's own owner key enrolled as an approver** — permitted and harmless: the domain/action
  tags in the digest mean an owner-key approval can never satisfy the vouch rule and vice versa.
  Worth one sentence in the doc comment so nobody adds a guard against it.
