# Tests for the React Native durable node-local stores

The implementation half of `2.2-rn-durable-node-local-stores` has **already landed
in the working tree** (that ticket was split under a token-budget cutoff). This
ticket finishes it: tests, lint, and one stale doc comment. Do not redesign the
code — read it, test it, and report honestly.

## What already landed (verify, don't rebuild)

`packages/reference-app-rn/src/node-local-slots.ts` (new):

- `secureStoreSlot(backend: SecureStoreApi, key, options?: SecureStoreKeyStoreOptions): DurableSlot`
  — the trusted-owner anchor's backend, over `expo-secure-store`. Maps a `null`
  read to `undefined` (absent) and lets a thrown read propagate. **Throws at
  construction** if `options.requireAuthentication === true`, because the
  `null ⇒ absent` mapping is only sound for an ungated slot.
- `kvStoreSlot(kv: KvStoreApi, key): DurableSlot` — the bootstrap-peer store's
  backend, a direct pass-through over `LevelDBKVStore`.
- `KvStoreApi` — the two-method (`get`/`set`) local seam, mirroring
  `SecureStoreApi`, so tests pass an in-memory fake and no native module loads.
- `anchorSlotKey(partyId)` → `sereus.anchor.<base64url(partyId)>`;
  `bootstrapPeersKvKey(partyId)` → `bootstrap-peers.<partyId>`;
  `NODE_LOCAL_DB_NAME = 'sereus-node-local'`;
  `NODE_LOCAL_KV_PREFIX = 'sereus:node-local:'`.

`packages/reference-app-rn/src/secure-key-store.ts` — two helpers were extracted
out of `SecureStoreKeyStore` and exported so the anchor slot reuses them rather
than re-deriving the rules: `secureStoreKeySegment(value)` (base64url key-segment
encoding, now also used by `safeKey`) and
`forwardedSecureStoreOptions(options)` (build the forwarded `SecureStoreOptions`,
omitting unset fields; now also used by the constructor).

`packages/reference-app-rn/src/cadre-phone.ts`:

- one shared `SECURE_STORE_OPTIONS` const (`keychainAccessible:
  AFTER_FIRST_UNLOCK`, no `requireAuthentication`) feeds both the identity
  `SecureStoreKeyStore` and the anchor slot;
- module-level `nodeLocalDb`, opened `??=` once in `startPhoneNode` (so the
  cold-start re-entry from `use-cadre` cannot leak a native handle per resume)
  and closed in a `finally` inside `stopPhoneNode`;
- `trustedOwners: { store }` + `bootstrapPeers: { store }` on the
  `CadreNodeConfig`, both opened before `new CadreNode(config)` and both allowed
  to reject the start on an unreadable slot.

`yarn typecheck` in `packages/reference-app-rn` passes at exit 0. **No tests were
written and no lint run happened** — that is this ticket.

## Tests to write

New file `packages/reference-app-rn/test/node-local-slots.spec.ts`, picked up by
the existing `node` vitest project (`vitest.config.ts` includes
`test/**/*.spec.ts` outside `test/react/`). Model it on
`packages/reference-app-web/test/node-local-slots.spec.ts` — the sibling web
ticket's spec, same two-layer shape (slot in isolation, then the real stores over
a real slot) — and on the in-memory `FakeSecureStore` double already in
`packages/reference-app-rn/test/secure-key-store.spec.ts`.

Scope note: the node-local *store policy* over an arbitrary slot (cold start,
corrupt JSON, foreign `partyId`, discard-all vs drop-entry, synchronous
visibility, failed-persist recovery) is owned by
`packages/cadre-core/test/node-local-snapshot.spec.ts`. Cover here only what the
RN app owns: the two slots themselves and their composition with the stores.

Slot-level:

- `secureStoreSlot` round-trips `save` → `load` through the fake, and a fresh
  slot instance over the same fake reads it back (the slot holds no state);
- absent key ⇒ `load()` resolves `undefined`;
- `getItemAsync` rejecting ⇒ `load()` rejects (must NOT resolve `undefined`);
- `setItemAsync` rejecting ⇒ `save()` rejects;
- forwarded options: given `{ keychainAccessible: <n> }` the fake sees exactly
  `{ keychainAccessible: <n> }` and the object has **no** `requireAuthentication`
  property, on both the read and the write path;
- `secureStoreSlot(..., { requireAuthentication: true })` throws at construction;
- the same round-trip / absent / read-rejects / write-rejects four for
  `kvStoreSlot` against a fake `KvStoreApi`.

Key-shape (these are persistence contracts — renaming one silently orphans every
installed phone's anchor and dial targets rather than failing):

- `anchorSlotKey` output starts with `sereus.anchor.`, never with the key store's
  `sereus.ks.`, and matches `/^[A-Za-z0-9._-]+$/` even for a party id containing
  `/` and `+`;
- `bootstrapPeersKvKey('p')` is `'bootstrap-peers.p'`; pin
  `NODE_LOCAL_DB_NAME` and `NODE_LOCAL_KV_PREFIX`.

Composition with the real cadre-core stores (`PersistentTrustedOwnerStore` /
`PersistentBootstrapPeerStore`, both exported from `@serfab/cadre-core`):

- anchor round-trip: `trust(key, 'invite')`, then re-`open` the same fake ⇒
  `has(key)` true. Assert the recorded **source** by parsing the raw slot text out
  of the fake (`owners[key].source === 'invite'`) — the store's public surface
  exposes keys only, and this also pins the envelope shape;
- bootstrap-peer round-trip: `record(peerId, ['/ip4/1.2.3.4/tcp/4001/ws'])`, then
  re-`open` ⇒ the peer is present with those addrs;
- junk text pre-seeded in the SecureStore slot ⇒ empty store, no throw; same for
  the KV slot;
- an envelope carrying a foreign `partyId` ⇒ empty store, for both;
- `getItemAsync` rejecting ⇒ `PersistentTrustedOwnerStore.open` rejects and the
  fake's map is still untouched (no empty anchor written); same for a rejecting
  `KvStoreApi.get` and `PersistentBootstrapPeerStore.open`;
- `setItemAsync` rejecting ⇒ `trust()`'s promise rejects but `has()` is still
  true (this session's decision stands); same for `record()` / `all()`.

**Peer-id fixture.** The bootstrap store's loader runs `peerIdFromString` on
every key, so a fixture that must survive a reload has to actually parse.
`@libp2p/crypto` and `@libp2p/peer-id` are NOT direct dependencies of
`reference-app-rn` (they only resolve transitively), so prefer a hardcoded real
Ed25519 peer id with a comment saying why it is a literal, e.g.
`12D3KooWQVo7JTYHgoj9rt9HScoxaM5axn3uB8P1WHiKrhhUqed3` (generated for this
purpose; it parses). Adding the two packages as devDependencies just for a
fixture is the fallback, not the first choice.

## For the review handoff, state plainly

- **End-to-end survival across an app relaunch is NOT delivered by this work
  alone.** Both records are party-scoped, and this app does not persist
  `opts.partyId` — it is typed into Settings each launch (see the comment in
  `push-wake-native.ts`). With a fresh party id per launch, both slots load empty
  every time. Backlog ticket `feat-rn-persist-node-start-options` closes that;
  until it lands, the durable stores are correct but not yet observable on device.
- Nothing here has run on a device or under the Expo e2e harness — the coverage is
  unit-level against fakes. In particular, the real `AFTER_FIRST_UNLOCK` value at
  the `cadre-phone.ts` call site is not unit-covered (that module imports the
  native `expo-secure-store`); what the tests can pin is that the slot forwards
  whatever it is given, ungated. The single shared `SECURE_STORE_OPTIONS` const is
  what actually keeps the anchor and the identity slot from drifting.
- The LevelDB handle lifetime (`??=` open, `finally` close) is likewise
  reasoned-about rather than device-verified.
