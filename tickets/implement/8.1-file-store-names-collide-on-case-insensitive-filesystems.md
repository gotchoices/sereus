# File names built from ids must not depend on letter case

Same class as `bug-scope-keys-collide-on-case-insensitive-filesystems` (sibling ticket, storage scope keys), at a different site: `encodeFileSafeComponent` (`packages/cadre-core/src/fs-atomic.ts`) turns an arbitrary string into a file name by percent-encoding, which preserves letter case. Windows (NTFS) and macOS (APFS/HFS+ by default) ignore case in file names, so two ids that differ only in case map to one file.

Two users of it:

- `FileKeyStore` — each slot is `<dir>/<encodeFileSafeComponent(keyId)>.key`. `KeyStoreJoinedStrandStore` writes slot ids `cadre/joined-strand/<base64url party id>/<strand id>`; base64url is case-significant, so two parties sharing one key directory can collide.
- `FileDurableSlot` — `<dir>/<name>.<encodeFileSafeComponent(partyId)>.json`, for the trusted-owner, bootstrap-peer, enrolled-machine and strand-peer-book stores. Party ids `Alice` and `alice` share one file. (These stores record their party id and fail closed on a mismatch, so the effect there is a refused or reset store rather than a cross-read.)

Reproduced on this machine (Windows 11) against the built `FileKeyStore`:

```
set('cadre/joined-strand/YWFA/strand-1', [1])
set('cadre/joined-strand/YWFa/strand-1', [2])
get('cadre/joined-strand/YWFA/strand-1') -> [2]            (party A's record overwritten by party B's)
list() -> ['cadre/joined-strand/YWFa/strand-1']             (one slot, not two)
```

(`YWFA`/`YWFa` are the base64url encodings of party ids `aa@` and `aaZ`.)

## Design

Change `encodeFileSafeComponent` so that **no letter outside a `%XX` escape is uppercase**: additionally escape `A`–`Z` as `%41`–`%5A`. Keep `encodeURIComponent`'s uppercase hex in the escapes. Why this is sufficient: a literal `%` is always escaped (`%25`), so in any output every `%` begins a three-character escape and every other character is a lowercase letter, digit, `-` or `_`. Folding the output's case therefore changes only the hex digits of escapes, which `decodeURIComponent` reads case-insensitively — so two different inputs can never produce outputs that are equal ignoring case. `decodeURIComponent` still reverses it unchanged.

Why keep the escapes' hex uppercase rather than lowercasing the whole output: it keeps every existing file name whose id has no capital letters byte-for-byte the same. That includes the node identity slot (`cadre/identity` → `cadre%2Fidentity.key`); lowercasing it would, on Linux, lose every CLI node's peer identity on upgrade. Only names built from ids containing capitals move.

`FileKeyStore.list` decodes whatever `.key` files it finds, so after the change an old-format file (`...YWFa...`) still decodes to a valid key id that `get` then cannot find (it looks for the new name). Make `decodeKeyId` accept only canonical names — re-encode the decoded id and skip (with the existing log line) any file whose name is not exactly that — so `list` and `get` always agree.

Update the doc comment on `encodeFileSafeComponent` ("The result contains only `A-Za-z0-9-_` and `%XX`") to state the new rule and the reason.

## Release note

Add to `.release-notes.pending.md`, alongside the sibling ticket's entry: file-backed key stores and per-party record files whose names came from ids containing capital letters are stored under new names. In practice this is the "joined strands" records (strands joined from another party are not re-offered after upgrade until joined again) and, only for party ids containing capital letters, the trusted-owner / bootstrap-peer / enrolled-machine / strand-peer-book files. The node identity key and every lowercase party id (such as a UUID) are unaffected. Old files are left in place and ignored; they can be deleted.

## Tests

Pin it at the encoder, which is platform-independent (the file-level collision only shows on a case-insensitive filesystem, so a Linux CI run would not catch a regression there). In `key-store.spec.ts`'s "round-trips awkward keyIds" test, add a pair of ids that differ only in case (e.g. `['Case-Pair', …]` and `['case-pair', …]`) — this reproduces the bug on a Windows/macOS dev machine and keeps the round-trip and `list` assertions honest. Plus one assertion, wherever `encodeFileSafeComponent` is most naturally reached (it is not exported from the package entry; import it from `../src/fs-atomic.js`), that for a mixed-case input the output with `%XX` escapes removed matches `/^[a-z0-9_-]*$/`. Add a case to the existing "skips a foreign .key file" test (or its neighbour) for a non-canonical but decodable name being skipped.
