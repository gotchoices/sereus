# A probe's failure cleanup releases only a runtime it built

## The defect (reproduced)

`CadreNode` brings a hibernating strand back up from three callers: a wake (`handleStrandWake`, reached through `HibernationManager.beginWake` from `wakeStrand`, push-wake, activity, and `serviceWake`'s `probeWake`), the periodic check-in (`handleStrandCheckIn`), and the mobile `serviceWake` (`runServiceWake`). Every rebuild first reads the cohort discovery seed (`resolveCohortSeed`, a control-database read that can throw) and only then calls `StrandInstanceManager.resumeStrand`, which shares one build between overlapping callers and leaves the instance `'error'` when that build fails.

`handleStrandCheckIn` and `runServiceWake` wrap resume *and* window in one `try`, and their `catch` calls `rehibernateAfterFailedResume` (quiesce, then status `'hibernating'`) for any failure. A seed-read failure happens before this caller has built anything, while the strand may be another caller's:

- a wake's rebuild in flight (`'starting'`, libp2p node attached, database not yet) — the check-in stops the node the build is still wiring (`quiesceStrand` does not wait for `runtimeBuilds`) and marks the strand `'hibernating'` under it;
- a wake's rebuild just finished — the check-in quiesces a strand whose waker was told it is up.

`runServiceWake` has the same shape: its wake goes through `handleStrandWake`, which already applies the right rule and rethrows, and then its own `catch` quiesces unconditionally.

Reproduction: `packages/cadre-core/test/cadre-node.spec.ts` → `a check-in that fails before rebuilding leaves a wake's mid-build runtime alone` (added by the fix stage, currently **failing**: `quiesceStrand` is called once). Run with `yarn workspace @serfab/cadre-core vitest run test/cadre-node.spec.ts -t "mid-build"`. It sits next to the wake-side test `a wake that fails before rebuilding leaves a check-in's mid-build runtime alone`, which already passes.

## Required behaviour

- A caller's resume-stage failure re-hibernates the strand only when the instance reads `'error'` — the build it started or joined failed. Any other status means the failure came before the rebuild and the strand belongs to whoever is building or holding it; leave it alone. This is the rule `handleStrandWake` already applies; share it (for example a small `rehibernateIfResumeFailed(instance, context)` used by the wake and check-in), don't copy the condition.
- A window-stage failure (the window's own `quiesceStrand` throwing, with this caller's runtime live) still quiesces best-effort and marks `'hibernating'`, as today.
- `runServiceWake`: the resume stage needs no cleanup of its own — `handleStrandWake` has already re-hibernated a failed build and rethrown. Catch, log, return `{ serviced: true, hadActivity: false }`. The window stage keeps today's quiesce-on-failure. `hibernationManager.endProbe(instance)` must stay in the `finally` and run last on every exit path (it arms timers from the final status — see `bug-strand-wake-leaves-no-hibernation-timers`).
- `handleStrandCheckIn` still resolves (never rejects) on every failure, so `HibernationManager.runCheckIn` decides from the status.

Shape: split each probe's single `try` into a resume `try` (return after the resume-stage cleanup) and a window `try`. Keep the long comment in `handleStrandCheckIn`'s catch accurate to the new split.

## Keeping the check-in chain alive (needed by the change above)

Today the bad cleanup at least leaves the strand `'hibernating'`, so `runCheckIn` escalates and schedules the next check-in. After the fix, a check-in whose seed read failed while a wake owns the strand returns with the strand `'starting'` (or live), and `runCheckIn` reads that as "woke" and ends the chain. If that wake then fails, `handleStrandWake` re-hibernates the strand and `settleWake` → `rearmAfterWake` restores a chain only when the wake recorded one (`checkInsCancelledByWake`, or a probe's `hadCheckInChain`). The wake never did: a check-in that is running has already been removed from `checkInTimers`, so `clearTimersForWake` / `probeWake` found nothing to remember. The strand ends up hibernating with no check-in scheduled.

Fix in `HibernationManager.runCheckIn`: when `onCheckIn` leaves the strand non-`'hibernating'` **and a wake is in flight** (`wakePromises.has(strandId)`), hand the chain to that wake instead of dropping it — set `hadCheckInChain = true` on the strand's `probes` entry if a probe holds it, otherwise add the strand to `checkInsCancelledByWake`. The wake's settle (or `endProbe`) then restores the chain at the base delay if the strand ends `'hibernating'`, and arms the idle countdown if it ends live, exactly as for a chain the wake cancelled itself. With no wake in flight, today's behaviour is unchanged. Note in the `clearTimersForWake` comment that a running check-in now hands its chain over this way rather than "rescheduling itself".

## Out of scope here

A wake that lands while a window (or the timer-driven hibernate) is *quiescing* is told the strand is up and then has it marked `'hibernating'` — that is `strand-wake-during-quiesce-is-told-the-strand-is-up`, which builds on this ticket.
