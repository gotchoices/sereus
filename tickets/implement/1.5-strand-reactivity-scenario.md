# Strand reactivity: real-network scenario

`strand-reactivity-node-option` adds `CadreNodeConfig.strandReactivity`. This ticket proves it wakes a `Database.watch` on another machine, and settles one open question about Optimystic.

## Why the obvious two-machine test proves nothing

At or below the strand's replication breadth (`strandClusterSize`, default 4) every machine stores every block — `strand-two-party-two-machine.integration.ts` gates that with raw-store coverage at four machines. A machine whose storage applies a commit wakes its watchers through the plugin's **local** change path, with or without the option. So a two-machine scenario's positive arm passes with the feature broken, and a negative arm ("option off, no wake") fails because the local path wakes it anyway. Both are replaced below.

## The open question it settles

The plugin README (§Network change notification) says a notification verifies only when "every machine is in every cohort". That was written before Optimystic rooted each collection's reactivity tree at the storage group of its log tail block (`../optimystic/docs/reactivity.md` §Origination point). If root placement works, a watcher **outside** the tail's storage group is woken by push. Only a strand with more machines than its breadth has such a watcher.

## Topology

One party, three machines, one strand across all three, `strandClusterSize: 2` and `strandReactivity: { enabled: true }` on every machine. Production profiles (the harness default: machine 0 `storage`, the others `transaction`). Every block lives on two of the three machines, so exactly one machine is outside the tail block's storage group — the scenario does not need to know which.

`TopologyMachineSpec` has no field for either option. Add `strandClusterSize?: number` and `strandReactivity?: StrandReactivityConfig` to `TopologyMachineSpec` and to `ControlNodeOpts` in `node-fixtures.ts`, passed straight into `CadreNodeConfig` (two fields, matching how `revocationPollMs` is threaded; no generic `Partial<CadreNodeConfig>` escape hatch). Reuse `bootTopology`, `joinStrandOn`, `connectStrandNodes`, `waitUntil`; build no new harness.

The sApp schema declares one table tagged `with tags ("optimystic.network_watch" = true)` (sign it with `createSignedSAppConfig` as the other scenarios do).

## Attributing a wake to the push path

Each strand node built with the option carries `node.reactivitySubscribers` (an untyped attachment from `createLibp2pNode`; its `deliver(topicId, notification)` is where every socket-delivered notification reaches this node's subscribers). Wrap `deliver` on each machine's strand node (`instance.libp2pNode`) to record a timestamp per call, then call through — it observes, it does not replace behaviour. Fail the test with a clear message if the attachment is missing (an Optimystic upgrade renamed it). This is the only way to tell a push wake from a local-apply wake; latency alone cannot, since a local apply is also fast.

## Rounds

Three rounds; in round *i* machine *i* commits one row and the other two are watchers. The tail block stays the same over three small commits, so the one machine outside its storage group is a watcher in two of the three rounds — whichever it is.

Per watcher, before the first round: run the watched `select` once (an app renders before it watches, and the plugin opens a table's network watch when the table is first initialized), call `db.watch(scope, cb)` with `scope = db.prepare(sql).getChangeScope()`, and wait for and discard the first wake — the watch service fires once when it first reads a committed tail (`collection-watch.ts` module doc). Reset counters at the start of each round.

Assert, per round and watcher:

- **Bound (hard):** the watch fires within `30 s + 5 s` of the commit resolving (one core-profile renewal plus slack; edge renews every 20 s).
- **Push (hard):** at least one `deliver` call on that watcher's node between the commit and the wake.
- **Log** the commit-to-wake and commit-to-deliver latencies for every watcher and round, in one summary line per round, so the review handoff can quote them.

If the push assertion fails only for one machine in two rounds (the outsider) while the other watchers pass, the README's "every machine in every cohort" caveat still holds. Before concluding that, rerun once with all three machines `profile: 'storage'` to rule out the edge profile as the cause. Then do **not** work around it here:

- weaken the push assertion to "at least one watcher per round is pushed" (the test cannot know in advance which machine is the outsider), keep the bound assertion for every watcher, and leave a `NOTE:` at the weakened assertion naming the upstream report and saying to restore the per-watcher form once it is fixed;
- record the limit in docs/strands.md's change-notification section (watchers outside the tail's storage group are woken only by the renewal read, 20/30 s), with the measured numbers;
- file `tickets/blocked/report-optimystic-reactivity-outside-tail-group.md` (a human posts it to optimystic-tend), with draft text: topology, the exact assertion that failed, the latencies, and the README sentence it confirms.

If every watcher is pushed, update docs/strands.md to say a strand above its breadth is woken by push, and file the same `blocked/report-…` ticket as a short note that the plugin README's caveat looks stale, with the evidence.

## Edge cases & interactions

- Initial wake on watch start (first tail read) — discarded before round 1, **in the test**.
- A machine that both stores and watches can wake twice for one commit (local apply and push) — assertions are "at least one", never "exactly one".
- Commits are sequential, never `Promise.all` across machines (simultaneous writers block each other; see `convergence-stress.integration.ts`).
- First-registration proof of work (0.3–17 s on Node, optimystic backlog `bug-first-registration-proof-of-work-freezes-the-node-for-seconds`) lands during bring-up; wait for each watcher's first wake before round 1 so it is not counted against the bound. Log how long that first wake took.
- Teardown: stop every `CadreNode`; unsubscribe watches first. Never recursively delete a directory holding `link:` junctions (project rule).
- Runtime: three machines boot six libp2p nodes; keep the whole file well under the runner's 10-minute idle limit, streaming output (no redirection). If one run exceeds ~3 minutes, say so in the handoff.
