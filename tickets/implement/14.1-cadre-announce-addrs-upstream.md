# `network.announceAddrs`: request upstream support, and stop advertising it as working

## What is broken

`NetworkConfig.announceAddrs` (`packages/cadre-core/src/types.ts:144`) is the list of addresses a
node should tell other peers to reach it at — the setting an operator needs when the node listens
on `0.0.0.0:4001` behind a router but is actually reachable at `mynode.example.com:4001`. It is
settable in `cadre.yaml`, via `CADRE_ANNOUNCE_ADDRS`, and through the Docker entrypoint
(`packages/cadre-cli/docker/entrypoint.sh:69-75`), and it is read by nobody. A throwaway unit test
during the fix pass confirmed the value never reaches the libp2p node options.

Unlike its sibling `relayAddrs` (fixed by `cadre-relay-addrs-wiring`), there is no in-repo way to
implement this. libp2p takes announce addresses only at construction, via `addresses.announce` /
`addresses.appendAnnounce`, and `@optimystic/db-p2p` builds that object as `addresses: { listen }`
with no announce key and exposes no option for it
(`../optimystic/packages/db-p2p/src/libp2p-node-base.ts:477-482`, `NodeOptions` at line 138).
Reaching libp2p's `AddressManager` after the node is up is not public API and is not worth the hack.

This is *not* covered by `NetworkConfig.inviteAddressResolver` or by `@serfab/cadre-host`'s NAT
service: those substitute externally-reachable addresses into **invite payloads** only. The
addresses the node advertises on the wire — over identify, to the DHT, to relays — still come from
libp2p's address manager and are unaffected.

## Decision taken

Keep the field and get it working, rather than deleting it. A port-forwarded self-host with a DNS
name is a first-class deployment for this project, relay reachability is a strictly worse
substitute for it, and the invite-only path above does not cover the wire.

Since the change is upstream, this ticket does two separable things: file the upstream request, and
make the currently-dead field honest here until that request lands.

## Upstream request

`../optimystic` is a linked workspace with its own tess pipeline (`../optimystic/tickets/`). The
precedent for raising something there from here is `tickets/complete/0-optimystic-cluster-size-gate-defaults.md`.

The change being asked for is small and additive:

```ts
// NodeOptions, libp2p-node-base.ts
/** Multiaddrs to advertise instead of the listen addrs (NAT / reverse proxy / DNS front). */
announceAddrs?: string[];
/** Multiaddrs to advertise IN ADDITION to the listen addrs. */
appendAnnounceAddrs?: string[];
```

```ts
// createLibp2pNodeBase, where `addresses` is assembled
addresses: {
    listen: listenAddrs,
    ...(options.announceAddrs && { announce: options.announceAddrs }),
    ...(options.appendAnnounceAddrs && { appendAnnounce: options.appendAnnounceAddrs })
}
```

Both keys are stock `@libp2p/interface` address-manager options, so this is pure forwarding. Write
the upstream ticket describing the operator-facing need (a node behind NAT/reverse proxy that must
advertise a different address than it binds), the two options, and the consumer here.

**Do not commit in `../optimystic`.** Its working tree has unrelated in-flight changes. Leave the
new ticket file untracked and say so in the review handoff so a human or that repo's runner picks it
up.

## Sereus side, until it lands

The harm today is silence: an operator sets `CADRE_ANNOUNCE_ADDRS` to their DDNS name, the node
keeps advertising its LAN address, and nothing anywhere says the setting was dropped. Fix the
silence without deleting the field.

Log a single clear warning at `CadreNode.start()` when `network.announceAddrs` is non-empty, naming
the setting and saying it is not yet supported. Warn, do not throw — an operator who set this in a
Docker environment file already has a running node, and turning that into a boot failure trades one
bad outcome for a worse one.

Once upstream lands and the `@optimystic/db-p2p` dependency range here moves (see
`scripts/check-dep-ranges.mjs` and the `test:dep-ranges` gate), the follow-up is a one-line spread
in `buildControlNodeOptions` plus the same in `strand-instance-manager`, and deleting the warning.
That follow-up is deliberately not filed yet — file it when the dependency actually moves.
