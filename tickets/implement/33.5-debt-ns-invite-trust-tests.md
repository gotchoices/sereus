# Tests for the NativeScript invite-trust glue

## Situation

`feat-ns-invite-trust-pinning` landed `CadreViewModel.ownerKeysFromInvite` plus a
widened `CadreViewModel.applySeed` in `src/cadre-vm.ts`, and the Settings screen
wiring in `app/settings/settings-view-model.ts`, with **no test of any kind** —
purely because the package had no runner. `debt-ns-unit-test-harness` (this
ticket's `prereq`) adds the runner; this ticket adds the two suites.

The load-bearing behaviour is an *ordering*: when the user pastes an enrollment
invite alongside a seed, the invite's owner keys are written into the node-local
trusted-owner anchor **before** the seed is applied, so the anchor already holds
them when seed trust consults it. `src/cadre-vm.ts` says so in a comment and
warns against folding the two calls together. A test that asserts only "both
calls happened" would not catch the tidy-up that breaks it.

## The one thing the harness ticket did not do

Both modules under test import `Observable` from `@nativescript/core`. That
package's entry point cannot be loaded under plain Node — measured during
planning:

```
Error [ERR_UNSUPPORTED_DIR_IMPORT]: Directory import '.../@nativescript/core/globals'
  is not supported resolving ES modules imported from .../@nativescript/core/index.js
```

Its `data/observable/index.js` submodule, however, imports cleanly (verified the
same way). So add a stub and alias to it.

### `packages/reference-app-ns/test/stubs/nativescript-core.ts` (new)

```ts
export { Observable, WrappedValue } from '@nativescript/core/data/observable/index.js';
export type { EventData, PropertyChangeData } from '@nativescript/core/data/observable/index.js';
```

The **real** `Observable`, not a hand-written double — `notifyPropertyChange`
and the property-change plumbing are what the view models are built on, and a
double would quietly diverge.

### `packages/reference-app-ns/vitest.config.ts` (edit)

```ts
resolve: {
	alias: [
		// Exact match only. A plain string `find` in Vite also matches every
		// `@nativescript/core/...` subpath, which would redirect the stub's own
		// deep import back into itself.
		{ find: /^@nativescript\/core$/, replacement: '<abs path>/test/stubs/nativescript-core.ts' },
	],
},
```

Resolve the replacement path from `import.meta.url` rather than hard-coding a
relative string. Keep the comment about exact matching — it is a real trap, not
a stylistic note.

Adding a `test/stubs/` directory means `test/**/*.ts` is already covered by the
type-check `include` the prereq ticket set up; nothing further is needed there.
The stub is not a `*.spec.ts`, so Vitest will not collect it as a suite.

## Test shape

Both suites drive the view models against **one fake node object**. The view
model only ever calls `decodeInvite`, `decodeSeed`, `trustOwnerKeys`,
`applySeed` on it, plus `isRunning` / `peerId` / `getStrands` / `on` / `off`
from the lifecycle paths. Build it as a plain object and hand it over as
`as unknown as CadreNode` — no `any`.

Record every node call into one shared `calls: string[]` so **order** can be
asserted, not merely presence.

Two mocks:

```ts
vi.mock('../src/cadre-phone', () => ({
	startPhoneNode: /* resolves the fake node */,
	stopPhoneNode: /* resolves */,
	getPhoneNode: /* null by default — the VM constructor calls this */,
	dialPeer: /* resolves; steerable to reject */,
}));
vi.mock('../src/chat-strand', () => ({ createChatStrand: /* resolves a stub StrandInstance */ }));
```

`@serfab/cadre-core` stays **real**: `cadre-vm.ts` uses `pinnedKeyTrustPolicy`
as a runtime value, and the point of the pinned-keys tests is that a real policy
object reaches `applySeed`. That is also why the prereq's build-freshness
`globalSetup` covers these suites too — no change needed to it.

`getCadreVm()` caches a module-level singleton and `SettingsViewModel`'s
constructor grabs it, so each test needs `vi.resetModules()` and a dynamic
`await import(...)` of both modules — same pattern the prereq ticket used for
`cadre-phone.spec.ts`.

### Phase 2 — `test/cadre-vm.spec.ts`

`ownerKeysFromInvite`:

- An invite carrying two owner keys yields both, **in order**.
- An invite with no `ownerKeys` field yields `[]` (not `undefined`, not a throw).
- Unreadable invite text (`decodeInvite` throws) raises an error whose message
  names the enrollment invite rather than surfacing a bare JSON parse failure,
  and whose `cause` is the original error.
- Before the node is started it throws `'Node not started'` and never touches
  the node — assert the guard runs first, matching `applySeed`'s guard order.

`applySeed`:

- With pinned keys, the recorded call order is exactly
  `['trustOwnerKeys', 'applySeed']`. Assert the array, not two `toHaveBeenCalled`s.
- `trustOwnerKeys` receives the keys and the source string `'invite'`.
- With pins, `applySeed`'s second argument carries a `trustPolicy`.
- With **no** pins, `trustOwnerKeys` is never called and `applySeed`'s second
  argument is `undefined` — no trust policy is overridden.
- An **empty** pin list behaves exactly as no pins at all (same two assertions).
- A seed the node refuses (`{ success: false, error: 'not for this party' }`)
  surfaces the node's own text to the caller.
- A refusal with no `error` field falls back to `'Seed application failed'`.
- **The pin sticks when the seed is refused**: after a rejected `applySeed`,
  `trustOwnerKeys` was still called and nothing rolled it back. Pasting the
  invite is itself the out-of-band trust act; rolling back would cost the user a
  re-paste on every retry.
- Before the node is started it throws `'Node not started'` and `decodeSeed` is
  never called.

### Phase 3 — `test/settings-view-model.spec.ts`

- Success clears **both** `seedInput` and `enrollInviteInput`.
- Any failure clears **neither** — a mistyped seed must not cost the user the
  pasted invite. Cover both failure sources separately: `applySeed` rejecting,
  and `ownerKeysFromInvite` rejecting on an unreadable invite.
- The success message distinguishes pinned from not-pinned: with pins it names
  the count; with no invite pasted it says no owner keys were pinned.
- **An invite that yields zero keys must report "no owner keys pinned"** — it
  must never claim a pin that did not happen.
- With no invite pasted, `ownerKeysFromInvite` is never called at all.
- A blank (or whitespace-only) seed returns early: no node calls, no modal.
- Surrounding whitespace is trimmed off both the seed and the invite before
  either reaches the view model.
- A failure raises the modal with the `'Seed failed'` title and the error text.

## Edge cases & interactions

- **The ordering assertion is the ticket.** If `trustOwnerKeys` and `applySeed`
  are both recorded but the order is not asserted, this ticket has not done its
  job. Prefer one shared `calls` array over per-spy call-order plumbing.
- **Vite alias matching.** A string `find` of `'@nativescript/core'` matches
  subpaths too, so the stub's own `@nativescript/core/data/observable/index.js`
  import would resolve back to the stub — an import cycle that fails in a way
  that does not name the cause. Use the anchored regex.
- **`ObservableArray` is out of reach by this route.** `src/chat-vm.ts` imports
  it, and `@nativescript/core/data/observable-array/index.js` re-imports
  `'../observable'` as a directory, which Node's ESM loader rejects for an
  externalized dependency. Do not widen the stub to cover it and do not chase it
  here — parked as `debt-ns-chat-vm-unit-tests` in `backlog/`.
- **Singleton bleed between suites.** `getCadreVm()` caches; a test that starts
  the VM leaves a `_node` behind for the next one unless modules are reset. Two
  tests that each assert "constructor adopted nothing" will catch a reset that
  is not taking.
- **The VM constructor calls `getPhoneNode()`.** Default the mock to `null`, and
  cover the adopt path explicitly at least once: a fake returning
  `isRunning: true` must leave a freshly constructed VM `connected`, with the
  peer id and strands read off that node.
- **`start()` swallows failures by design** — it sets `status: 'error'` and
  `error` rather than throwing, and the Settings screen reads those. A test that
  expects `start()` to reject is asserting the wrong contract.
- **`stop()` must unbind the node's event handlers** before dropping the
  reference; a stopped VM that still receives `strand:started` would repopulate
  strands from a dead node. Assert `off` was called for each of the three events.
- **Error text is asserted, and error text is UI copy.** Match on a distinctive
  substring (e.g. `/enrollment invite/i`), not the whole sentence, so a wording
  tweak does not fail the suite for no reason.
