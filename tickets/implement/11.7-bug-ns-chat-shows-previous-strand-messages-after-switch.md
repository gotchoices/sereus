# NS chat view model applies the previous strand's results after a switch

## Cause

`ChatViewModel` (`packages/reference-app-ns/src/chat-vm.ts`) attaches to the first strand the cadre view model lists. It re-attaches in `start()` (the chat page calls it on `navigatedTo`) and on every poll while unregistered. The attached strand can change to a different instance, or to none. Nothing in the view model notices that change:

- **Late read (`refresh()`, line ~220).** It captures `strand`, awaits `queryMessages`/`queryParticipants`, then unconditionally calls `setMessages`, `settlePendingDraft`, `setParticipantCount` and `setError`, and in `finally` `setLoading(false)`. A read of strand A that settles after the view model re-attached to B overwrites B's list with A's. The per-strand single-flight guard (`readsInFlight`) deliberately lets B's read start while A's is running, so this ordering is expected, not contrived.
- **No reset on switch (`attach()`, line ~182).** When the strand changes, `_messages` and `_participantCount` keep the old strand's values until the new strand's first read lands. When the new strand is none, they stay indefinitely, because `refresh()` returns early without a database.
- **Late send (`send()`, line ~279).** After `insertMessage` resolves, `this._messages.push(...)` appends the row without checking that `strand` is still the attached one.

The RN hook (`packages/reference-app-rn/src/use-chat.ts`) already does both halves: a reset-on-switch effect keyed on `strand?.strandId`, and `refresh()` dropping any result or error whose strand is no longer `strandRef.current`, clearing `loading` only for the current strand.

## Fix

Mirror the RN hook; two rules.

**Results belong to the strand instance they were read from.** In `refresh()`, after the `await`, return without touching anything visible if `this.strand !== strand`; the same check in `catch` (no `setError`) and in `finally` (`setLoading(false)` only for the current strand; `readsInFlight.delete(strand)` always). Keyed on the instance, as `readsInFlight` already is, so a replaced instance of the same strand also drops its predecessor's late read. In `send()`, skip the `_messages.push` when `this.strand !== strand`.

**The list belongs to the strand id it shows.** In `attach()`, when the attached strand's id changes (including to or from none), clear `_messages`, set the participant count to 0 (through `setParticipantCount` so `statusText` notifies), clear the poll error `_error` via `setError('')`, and re-enter loading with `setLoading(true)`. `start()` calls `refresh()` right after `attach()`, and `refresh()` clears loading again when there is no database, so the no-strand case does not stick in loading. Key this on `strandId`, as RN does, not on the instance: a reconnect that replaces the instance of the same strand should keep showing the conversation until the next read rather than flash an empty list. The existing `strand !== this.strand` instance check for `registered` stays as is.

Decided, with the reason, so the reviewer need not re-derive it:

- **The composer is not reset on switch.** After a send settles for a strand the view model has left, it still clears the draft and retires `pendingDraft` on success, and still shows "Not confirmed sent" on failure. Those describe what happened to the text the user submitted, which is the same text in the same box whichever strand is attached. Only the list append is gated. Consequence: a resend after an uncertain failure on A, made once attached to B, stores the message in B under the same id (at most one row per strand, not one row overall). Acceptable here: the NS app runs one strand, and the switch needs the first strand to stop mid-send.
- **`settlePendingDraft` is covered by the refresh guard.** A late read of A is dropped before it can settle a draft.

Not in scope, noticed while comparing: RN's `send` in `use-chat.ts` also appends `message` with no check that `strandRef.current` is still the strand it sent to. Same one-line gap in the other app. Leave it unless it is trivial to include; if left, say so in the review handoff so review can record it.
