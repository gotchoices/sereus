# Bind the `Strand` consent branch to the redemption that authorized it

## The defect (reproduced, current `master`)

`CadreControl.Strand` rows may be seated two ways: owner-signed, or "by consent" —
no signature at all, authorized purely by the existence of a `CadreControl.FormationUsage`
row naming the same strand id (`Strand.AuthorizedInsert`, second branch).

Removal requires an owner signature over a distinct `'remove'` digest **plus** a
`CadreControl.Revocation` tombstone retiring the row's one-off nonce (`StampId`) in the
same transaction. The tombstone is what makes removal permanent — `NotRevoked` refuses
any later insert naming a retired nonce.

The consent branch names no nonce. It only asks "does *a* `FormationUsage` row exist for
this strand id?", and `FormationUsage` is append-only (`InsertOnly check on update, delete
(false)`), so that row outlives the strand's removal forever. After a fully legitimate
owner-signed, tombstoned removal, any writer can re-insert the `Strand` row with **no owner
key, no signature**, a **fresh** `StampId` (sidestepping `NotRevoked`, which only retires
the one nonce the removed row carried), and an **attacker-chosen** `MemberPrivateKey` —
the party's own secret key for that network.

The control database is replicated across the party's cadre and peers write SQL to it
directly, so the CHECK constraints *are* the authorization boundary; "any writer" means any
node that can reach the control network.

**Confirmed empirically** during the fix stage with a scratch spec against a real
`CadreNode` (empty bootstrap, `transaction` profile): redeem an invite → owner-signed
tombstoned removal → unsigned re-insert with a fresh stamp and `MemberPrivateKey =
'ATTACKER-KEY'` → **accepted**, row back with the attacker's key. The scratch spec was not
left in the tree (it asserts the hole, so it would pass today and fail once fixed); the
regression tests below replace it and must land with the fix.

## Chosen fix

Carry the strand's nonce onto the consent record, so consent authorizes **one specific
strand row**, not a strand id forever.

`FormationUsage` gains a `StrandStampId` column. `Strand`'s consent branch requires the
inserted `Strand.StampId` to equal it, and `FormationUsage.StrandExists` is tightened to
match the strand on **(id, stamp)** rather than id alone. Removing the strand retires that
stamp into `Revocation`, so `NotRevoked` permanently closes that consent record's branch.

**This retires the specific authorization, not the strand id.** A legitimate re-join still
works: a new redemption writes a new `FormationUsage` row carrying a new `StrandStampId`
alongside a `Strand` row with that fresh stamp, and both deferred CHECKs see both rows at
commit — exactly the shape `redeemInvitation` already writes.

### Schema shape (both copies, kept byte-identical — see the drift guard)

```sql
-- CadreControl.Strand, AuthorizedInsert, consent branch:
or exists (select 1 from FormationUsage FU where FU.StrandId = new.Id and FU.StrandStampId = new.StampId)

-- CadreControl.FormationUsage:
StrandStampId text not null,   -- the Strand.StampId this consent record authorizes
constraint StrandExists check (
    exists (select 1 from Strand S where S.Id = new.StrandId and S.StampId = new.StrandStampId)
),
```

Both CHECKs carry subqueries, so Quereus auto-defers them to commit — the existing mutual
circularity (`Strand.AuthorizedInsert` ↔ `FormationUsage.StrandExists`) is unchanged in
kind; only the join key widens. `redeemInvitation`'s single `begin … commit` still satisfies
both.

`StrandStampId` is **not** unique: in the bound (provision-then-record) path several
invitees each write a `FormationUsage` row against the same host strand, so many usage rows
legitimately share one stamp.

### Rejected alternatives (record the reasoning; don't re-litigate)

- **Derive the strand stamp from `(Token, UseNumber)` instead of adding a column.** A
  derived stamp is *guessable*. `Revocation.RowIsGone` deliberately permits tombstoning a
  never-existing stamp, on the stated grounds that stamps are 128 bits of CSPRNG output and
  cannot be pre-planted. A guessable stamp turns that into a denial-of-service: anyone
  pre-files a tombstone and the future redemption is refused by `NotRevoked`.
- **Have the consent branch require that no `Revocation` row exists for any nonce ever tied
  to this strand id.** Needs the strand id recoverable from the tombstone (`Revocation`
  stores only `(TableName, StampId)`), and it blacklists the id permanently — the ticket
  explicitly wants re-join to stay possible.

### Known residual, to state in the constraint comment

An invitation with `TotalUses` null (unlimited) or with uses left over can be redeemed again
after a removal and will re-seat the strand id with a fresh stamp. That is the legitimate
re-join path, not a hole — but it means **removing a strand does not revoke the invitations
that could re-form it.** Say so plainly in the `AuthorizedInsert` comment: an operator who
wants a removal to be final must delete the `FormationInvite` too (`AuthorizedDelete` on
`FormationInvite` already exists for that).

## Writer changes (`packages/cadre-core/src/control-database.ts`)

- `execFormationUsageInsert` takes `strandStampId: string` and writes it in the column list.
- `redeemInvitation` already mints `strandStampId` for the `Strand` insert — pass that same
  value through to the usage insert.
- `recordFormationUsage` (the bound path — usage against an already-existing, owner-signed
  strand) must read the live strand's stamp before inserting. Add a
  `queryStrandStampId(strandId): Promise<string | null>` reader, symmetrical with the
  existing `queryCadrePeerStampId`. Throw a clear error when the strand is absent rather
  than letting the deferred `StrandExists` CHECK drop the write at commit —
  `ControlFormationUsageRecorder.resolveStrand` already reports `missing` for the ordinary
  case, so a null here is a genuine race and deserves a named exception, not a silent
  rollback.
  - Alternative considered: widen `StrandRow` with `StampId` and thread it from
    `resolveStrand` through `FormationUsageRecorder.recordUsage`. That saves a read and
    keeps the stamp from the snapshot `resolveStrand` already validated, but it changes a
    cross-package interface. Prefer the extra read unless it gets in the way.

No signature/digest changes: the consent branch is signature-free by design, and the
owner-signed `'add'` / `'remove'` digests are untouched, so `control-authorization.ts`,
`buildAuthorizationMessage` callers, and every existing owner-signed writer are unaffected.

## Callers that do NOT change

- `packages/reference-app-web/src/lib/cadre-web.ts` `attemptUnauthorizedStrandWrite` — a
  deliberately-rejected probe; it stays rejected (now via a stricter consent branch).
- `ControlDatabase.insertStrand` / `deleteStrand` — owner-signed branches, untouched.
- `FormationUsageRecorder` interface and `StrandFormationManager` — unchanged if the stamp
  lookup lives inside `recordFormationUsage`.

## Regression tests

`packages/cadre-core/test/control-revocation-replay.spec.ts` (harness already there: real
`CadreNode`, empty bootstrap, `transaction` profile, `expectConstraintFailure` from
`test/control-constraint-helpers.ts`). Put these beside the existing *"a formation
invitation authorizes forming a strand, never destroying one"* test:

- **The hole itself.** Redeem an invite → owner-signed + tombstoned removal → unsigned
  re-insert with a **fresh** stamp must fail `AuthorizedInsert` (owner branch false, consent
  branch finds no usage row naming that stamp), and the row must stay gone. Also assert the
  re-insert with the **original** stamp fails `NotRevoked`, so both doors are pinned.
- **Re-join still works.** After that removal, a second `FormationInvite` + a second
  `redeemInvitation` for the **same strand id** succeeds and seats a row with a new stamp.
  This is the property that must not regress into a permanent id blacklist.

`packages/cadre-core/test/control-formation-invite.spec.ts`:

- The usage row written by `redeemInvitation` carries `StrandStampId` equal to the seated
  `Strand.StampId`.
- The usage row written by `recordFormationUsage` against a pre-existing owner-signed strand
  carries that strand's live stamp.
- A hand-written `FormationUsage` insert naming a live strand with a **wrong**
  `StrandStampId` is refused by `StrandExists`.
