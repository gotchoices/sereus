# Scenario: the always-on machine hosts a strand its phone joined from another party

## What it proves

This is the end-to-end path `party-wide-joined-strands` builds. The two new behaviours are that a join is published party-wide and that a replica host launches from it, and that leaving is party-wide. Neither has a node-level unit test, by design.

The same-party replica already serves a replacement phone (proved by `strand-always-on-replica-survives-phone-loss`), so this file does not repeat the phone-loss and replacement arm. It proves that the party-wide record gets the strand onto the always-on machine and later takes it off.

## Topology

- **HOST party.** One machine, sole owner, storage profile, `hostUnclaimedStrands: false` (the harness default). It founds an **open** strand and publishes a formation invitation bound to it, following `strand-formation-cross-party-seed`.
- **JOINER party.** Two machines:
  - **Phone:** `profile: 'transaction'`, the party's genesis owner (the reference React Native deployment: the phone founds the party and enrolls its always-on machine). It redeems the invitation with `formStrand`, `addStrand`s with the app config, and writes rows.
  - **Always-on machine:** `profile: 'storage'`, `hostUnclaimedStrands: true` set explicitly (the harness defaults it to false), enrolled by the phone. It never calls `formStrand` or `addStrand`.

Use an open strand, for the reason `strand-always-on-replica-survives-phone-loss` gives: it keeps the scenario off the closed-strand admission path, which has a flake history. The closed-strand difference (the replica resolving the `StrandPartyKey` row `formStrand` seated) runs the same launch code, so a comment is enough.

## Steps and assertions

1. After the phone's `formStrand` and `addStrand`, and **before** any publication, assert that the always-on machine runs no instance of the strand. Measure this, don't narrate it, following the model scenario's ordering rule.
2. Drive publication deterministically: call `reconcileControlCohort()` on the phone (it is public) rather than waiting on the 15 s timer. Assert that the phone's control database holds the `JoinedStrand` row (`queryJoinedStrand`), and that the phone's joined-strand store no longer holds the local record (the record was drained).
3. Wait for the always-on machine's watcher to launch the replica (instance present, no `sAppInfo`). Then check block coverage of the phone's strand store against the always-on machine's raw store, using the model scenario's `block-store-probe` check, after the phone writes rows. Include at least one row written after the replica came up.
4. The phone calls `forgetJoinedStrand`. Assert that the `JoinedStrand` row is gone and a `Revocation` tombstone names it on the phone. Then wait for the always-on machine's instance to be gone (watcher poll, then `handleStrandRemoved`). Assert that the HOST's strand instance is still running.

There must be no test-side strand dial, following the model scenario's rule. The joiner phone reaches the host through the formation-carried addresses, and the always-on machine reaches the phone through the strand-addr RPC over the control connections that enrollment opened. If the always-on machine cannot reach any strand peer this way, that is a finding for the handoff, not something to hand-dial around.

## Edge cases & interactions

- **Publication gate.** `reconcileControlCohort` publishes only with a control connection, and only on an owner. Both hold here (phone and always-on are connected after enrollment, and the phone is the owner). Assert that the connection exists before step 2, so a failure reads as "not connected" rather than "not published".
- **Watcher timing.** The default poll interval is 5 s. Lower `strandWatchInterval` on the always-on machine if the harness allows it, as other scenarios do, rather than widening waits. Every wait needs a stated deadline and a failure message that names what was not seen.
- **Replica's first-sync gate.** The replica is a joiner. It publishes nothing until it holds the Header from the phone. The coverage check therefore has to wait on coverage, not on the launch.
- **Cleanup.** Stop all three nodes in `finally`, following the model scenario. Never recursively delete a directory that may hold `link:` junctions (`tickets/rules/sibling-repos.md`). Use the harness's own storage helpers.
