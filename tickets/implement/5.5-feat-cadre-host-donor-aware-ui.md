# Make the cadre-host local UI donor-aware

## Background

cadre-host has two roles (see `docs/cadre-host.md` → "Two roles: donor and founder"):

- **Donor** (default, always on) — the host runs cadre nodes for *other people's* cadres, authorised by grant tokens.
- **Founder** (opt-in, `ownCadre.enabled` in `host.config.json`) — the host additionally runs its *own* cadre: an owner node, a trust circle, NAT/DDNS, and strand management.

In donor-only mode the server already leaves `/auth/*`, `/nat/*` and `/api/strands` unmounted (they 404) and `GET /api/status` omits `trustCircle` and `connectivity`. The Svelte SPA under `packages/cadre-host/ui/` was never updated, so on a default install:

- The top nav offers **Trust Circle**, **Connectivity** and **Strands**; each page calls its unmounted route on mount and shows an error toast.
- `App.svelte`'s boot calls `refreshTrustCircle()` and `refreshConnectivity()` unconditionally → two error toasts on every page load.
- Home's Connectivity tile says "Loading connectivity…" forever, and the Trust circle tile shows "0 members".
- The overall status dot (header and Home) is stuck at "loading" (`…`), because `deriveOverallStatus` returns `'loading'` whenever `connectivity` is null — which in donor mode is always.
- The node detail page offers Start / Restart / Stop on donated nodes, which the server answers with `501 not_implemented`; and on a leftover owner node from a previous founder run it offers Start, which the server would honour (see `bug-cadre-host-owner-node-startable-in-donor-mode` in backlog).

## Design

### Server: an explicit role on `/api/status`

The SPA must not guess the role from missing fields. `GET /api/status` gains a required `role: 'founder' | 'donor'`.

To give that flag exactly one source, group the three founder-only services in `LocalUiServerOptions` (`src/server/index.ts`) into one optional object:

```ts
/** The host's own-cadre services. Present iff `ownCadre.enabled`; all three or none. */
export interface FounderServices {
  trustCircle: TrustCircleService;
  nat: NatService;
  strands: StrandService;
}

export interface LocalUiServerOptions {
  // … existing fields, minus trustCircle / nat / strands …
  founder?: FounderServices;
}
```

`createLocalUiServer` mounts `/auth/*`, `/nat/*`, `/api/strands`, the settings route's `nat` hook and the boot-time `connectivity-changed` publish from `opts.founder`, and passes `role: opts.founder ? 'founder' : 'donor'` to `registerStatusRoute`. "Founder with no trust circle" or "donor with a NAT service" can no longer be expressed, so the role and the mounted surfaces cannot disagree.

`StatusRouteOptions` keeps its optional `trustCircle` / `nat` (the status route only reads them) and gains `role: HostRole`, where `export type HostRole = 'founder' | 'donor'` lives in `status.ts`. `StatusResponse`:

```ts
export interface StatusResponse {
  service: { name: 'cadre-host'; version: string; uptimeSeconds: number };
  /** Which role this running process is in — decided at start from `ownCadre.enabled`. */
  role: HostRole;
  nodes: Array<{ id; partyId; status; profile; owner?: true }>;  // `owner` mirrors ManagedNodeInfo.owner
  trustCircle?: …;   // unchanged: omitted in donor mode
  connectivity?: …;  // unchanged: omitted in donor mode
  update?: …;
}
```

The node summary gains `owner` (copied from `ManagedNodeInfo.owner`, present only when true) because `refreshStatus` projects this summary into `state.nodes` when the list is empty; without it, the node detail page could briefly treat the owner node as a donated one before the full `/api/nodes/:id` fetch lands.

`bin/host.ts` builds `founder` inside its existing `if (hostOwnsCadre(cfg))` branch and passes `...(founder ? { founder } : {})`. The role reflects the **running process**, not the file on disk — `ownCadre` edited in `host.config.json` without a restart does not change it (that is why `/api/settings`, which reads the file, is not the source).

Test call sites (`publishers.test.ts`, `server.smoke.test.ts`, `strands-route.test.ts`) move to `founder: { … }`. Those that passed only some of the three now need fakes for all three; if that duplicates fakes across files, hoist them into one `src/server/__tests__/fakes.ts`. Extend the existing status assertions (`status-route.test.ts`, and the smoke test's "no trustCircle / connectivity" case) to check `role` in both modes — no new test file.

### SPA state (`ui/src/lib/state.svelte.ts`)

- Mirror types: `StatusResponse` gains `role`, `nodes[].owner?`, and `trustCircle` / `connectivity` become optional (they are today, on the wire). `NodeInfo` gains `owner?: boolean`. Export `type HostRole = 'founder' | 'donor'`.
- `AppState` gains `role: HostRole | null` — `null` until the first successful `/api/status`.
- `refreshStatus` sets `state.role = r.role`, `state.connectivity = r.connectivity ?? null`, and carries `owner` through the node projection.
- Move `deriveOverallStatus` into a new plain module `ui/src/lib/overall-status.ts` (the pattern `strand-removal.ts` and `typed-confirm.ts` already follow, so it is testable without the Svelte compiler) and give it the role:

  ```ts
  deriveOverallStatus(role: HostRole | null, connectivity, nodes, update): OverallStatus
  ```

  - `role === null` → `'loading'`.
  - `role === 'founder'` → today's rules exactly (null connectivity → `'loading'`; unreachable/cgnat → `'warn'`; …).
  - `role === 'donor'` → connectivity is not consulted; any stopped node or `update.lastError` → `'warn'`, else `'ok'`.

  `recomputeStatus` passes `state.role`. Remove `deriveOverallStatus` from the `__test__` seam in `state.svelte.ts` (nothing imports it).

### Which pages are founder-only (`ui/src/lib/router.ts`)

Add, next to `RouteName`:

```ts
/** Pages that exist only when the host runs its own cadre (their API routes 404 in donor mode). */
export const FOUNDER_ROUTES: ReadonlySet<RouteName> = new Set(['trust-circle', 'connectivity', 'strands']);
export function isFounderRoute(name: RouteName): boolean
```

`parseHash` / `hrefFor` are unchanged — the hashes stay parseable in every mode; gating happens at render.

### App shell (`ui/src/App.svelte`)

- **Nav**: show a founder-only item only when `app.role === 'founder'`. While the role is still `null`, hide them too — a founder dashboard gains its three items a moment after load; a donor dashboard never flashes links that would 404.
- **Boot fetches**: drop the unconditional `refreshTrustCircle()` / `refreshConnectivity()`. Instead chain them after the status fetch: `void refreshStatus().then(() => { if (app.role === 'founder') { void refreshTrustCircle(); void refreshConnectivity(); } })`. (`refreshStatus` already catches and reports its own errors, so the chain never rejects.)
- **Route gate**: in `<main>`, if `isFounderRoute(route.route.name)` and `app.role !== 'founder'`, do **not** mount the page component (its `onMount` fetch is what 404s). Render instead:
  - role `null` → a card with "Loading…" (status still in flight — do not decide yet).
  - role `'donor'` → a card: "This page is for running your own cadre, which is turned off on this machine." plus a link back to Home. This covers bookmarks and hand-typed hashes.

  Once the role resolves to `'founder'`, the real page mounts and fetches as it does today.

### Home (`ui/src/routes/Home.svelte`)

- Founder: the Connectivity and Trust circle tiles render exactly as today.
- Donor: those two tiles are replaced by one **Donation** tile: a line saying the machine donates cadre nodes to other people's cadres; the count of donated nodes (`app.nodes.filter((n) => !n.owner)`), running vs total; and, since the dashboard has no grants page yet, the command that issues a grant: `cadre-host grant issue <label>` (in a `<code>`). The grants page is `feat-cadre-host-ui-grants-page` in backlog; when it lands it replaces the command hint with a link.
- `null` role: render neither the founder tiles nor the Donation tile (the Overall and Nodes tiles still render).
- The Overall and Nodes tiles are unchanged in both roles.

### Node detail (`ui/src/routes/NodeDetail.svelte`)

`/api/nodes` already reports `owner: true` on the host's own node, and every other node it lists is a donated node (see the header comment in `src/server/routes/nodes.ts`). The action row branches on that — never on the `grn_` id prefix:

- **Owner node, role `'founder'`** → Start / Restart / Stop exactly as today.
- **Owner node, role not `'founder'`** → no buttons; a muted line: "Your own cadre is turned off on this machine, so this node is not run here." (This is the leftover owner node a previous founder run leaves behind; the server-side hole behind it is filed separately.)
- **Donated node** (`!node.owner`) → one danger button, **Terminate**, behind `ConfirmDialog`. Message: shutting down donated node `<id>` removes it from the borrower's cadre and frees one node slot on their grant; they can ask for another while the grant is valid; the grant itself is untouched (revoke it with `cadre-host grant revoke`). On confirm: `apiDelete('/grants-admin/donations/' + encodeURIComponent(node.id))`; on success clear the 5-second poll timer **before** anything else, push a success toast, `await refreshNodes()`, then `navigate(hrefFor('nodes'))`. On failure: error toast in the same form `postAction` uses, and leave the page (and poll) as is.

`DELETE /grants-admin/donations/:id` is the same loopback, no-bearer admin surface the `cadre-host grant terminate` CLI uses, served by the same origin as the SPA, so the origin guard admits it. Terminating a donation stops and reclaims its orchestrator handle (`DonationService.terminate`), so the node leaves `/api/nodes` — which is why the page must stop polling and navigate away rather than stay on a node that now 404s.

### Docs (`docs/cadre-host.md`)

- API surface table: `/api/status` row mentions `role` (`'founder' | 'donor'`).
- "Two roles" → donor-only consequences: add one bullet — the local UI hides the Trust Circle, Connectivity and Strands pages and the Home tiles for them, shows a Donation tile instead, and offers Terminate (not Start/Stop) on donated nodes.
- Status section's SPA line (the "Local UI SPA (`6.5.2`)" bullet): note the pages adapt to the role.

## Edge cases & interactions

- **Status fetch fails on boot** → `role` stays `null`: founder nav items stay hidden, founder routes show "Loading…", overall status goes to `'error'` via the existing catch. A later successful `refreshStatus` (Home calls it on mount) resolves the role and everything appears. Verified by inspection.
- **Founder dashboard, first paint** → founder nav items and tiles appear once status lands; the founder boot fetches (`refreshTrustCircle` / `refreshConnectivity`) run after status, not in parallel. No toast in either role on a healthy boot. Verified by running the UI (see TODO) in both roles.
- **Deep link to `#/strands` (or trust-circle / connectivity) on a donor host** → page component never mounts, so no 404 toast; donor card shown. Verified by running the UI.
- **Deep link to a founder page on a founder host before status resolves** → "Loading…" card, then the page mounts and does its own fetch. Verified by inspection.
- **SSE events** `trust-circle-changed` / `connectivity-changed` / `strands-changed` are only published by founder services, so a donor dashboard never receives them; `applyEvent` needs no role check. Verified by inspection of `src/server/index.ts` (nothing publishes them without `founder`).
- **Donor host with a leftover stopped owner node** (previous founder run): it appears in the Nodes list and counts as a stopped node, so overall status is `'warn'` and Home's Nodes tile shows it as not running. Accept for this ticket — it is true that the node is stopped; whether the server should list it at all belongs to `bug-cadre-host-owner-node-startable-in-donor-mode`. The Donation tile's count excludes it (`!n.owner`). Node detail shows no lifecycle buttons for it. Verified by inspection.
- **Overall status derivation** — the one piece of real branching: donor with `connectivity === null` and all nodes running must be `'ok'`, not `'loading'` (today's bug); founder with `connectivity === null` must still be `'loading'`; `role === null` is `'loading'` regardless of the rest. Verified by the test below.
- **Terminate races the poll** → the timer is cleared before the refresh/navigate, so no "node … not found" toast follows a successful terminate. Verified by running the UI or by inspection.
- **Terminate on an already-terminated or unknown donation** → server error (the `DonationError` code mapped by `error-handler.ts`) surfaces as an error toast; page stays. Verified by inspection.
- **Terminate while the node is `stopped`** (crashed, awaiting the supervisor's respawn) → still allowed; terminate is the correct way to end it either way. Button is enabled regardless of `node.status`; disabled only while the request is in flight.
- **Node detail first render from the status projection** (full node not fetched yet) → `owner` is carried in the projection, so the owner node never flashes a Terminate button. Verified by inspection.
- **Founder role behaviour** → every founder page, tile and button renders and fetches as before; the only founder-visible change is that the three nav items and two tiles appear after the status fetch rather than immediately. Verified by running the UI in founder mode.

## Tests

- New `ui/__tests__/overall-status.test.ts` (plain Vitest, no DOM needed) pinning `deriveOverallStatus`: (1) `role: null` → `'loading'`; (2) `'donor'`, `connectivity: null`, all nodes running, no update error → `'ok'`; (3) `'founder'`, `connectivity: null` → `'loading'`; (4) `'founder'`, reachable connectivity, one stopped node → `'warn'`. Case (2) is the reproduction of the stuck-status bug.
- Extend existing status assertions with `role` (see Server section). Nothing else: nav/tile/button gating is template wiring, and the package cannot mount Svelte components in tests yet (`debt-cadre-host-ui-component-tests` in backlog).
