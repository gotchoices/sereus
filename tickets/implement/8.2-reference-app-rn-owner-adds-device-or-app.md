# Phone reference app: "Add a device or app" (the owner side)

Split from the plan ticket `reference-apps-join-existing-cadre`. This is the owner app's half (app A). The joining app's half is `reference-app-rn-joins-existing-cadre`, which reuses the QR/copy component and the generalized scanner built here. The web app's owner half is `reference-app-web-owner-adds-device-or-app`.

The protocol is done (`app-joins-existing-cadre-by-invitation`, architecture.md → "Handing an invitation from app to app"). This ticket is UI over these cadre-core calls on the running node:

- `decodeCadreJoinRequest(text)` → `{ v, peerId, appName }`; refuses an invitation pasted here by name.
- `node.createCadreInvitation({ peerId?, grantsOwner, expiresInMs?, uses? })` → `{ invitation, encoded, reach }`. Throws when this node has no owner key wired, or when neither this machine nor any other member has a dialable address.
- `node.listCadreInvitations()` → `CadreInviteStatus[]` (`invite`, `live`, `withdrawn`, `usesRecorded`).
- `node.withdrawCadreInvitation(key)` → `boolean`.

## Terminology (UI strings)

The plan fixed these: "Paste request" then approve with the owner choice (targeted flow), "Copy invitation" (open flow). Section title: **Add a device or app**.

## Screen

A new component `src/add-device-section.tsx`, rendered by Settings while connected, below "Join my existing cadre" (or where "Join a Cadre" sits today, until the join ticket replaces it). Settings is already 547 lines; keep everything in the new file, as `add-node-section.tsx` does.

**Who sees what.** The hook's `isOwnerDevice()` decides. A member (not an owner) sees one line: "Only an owner of this cadre can add a device or app. This app is a member." and nothing else. Re-check when the section mounts and after each join (the owner standing can change).

**Two ways in:**

1. **Paste request** (targeted, recommended): a multiline field (placeholder `sereus-join-request:1.…`), a "Scan request" button (the scanner, generalized below) and "Use request". `decodeCadreJoinRequest`; a refusal shows its own message in the alert. Then local checks before the prompt:
   - the request's peer id is this phone's own (`cadre.peerId`): "This is this app's own request. Open the other app and copy its request there."
   - the peer id is already a machine of this cadre (`getControlDatabase().queryCadrePeers()` lists it): "‹appName› is already in this cadre." No invitation.
   Then the **approval prompt** (a Modal, as `ApprovalPrompt` in `add-node-section.tsx`): title "Add ‹appName› to your cadre?"; facts: the app name with the note "The name is what the app calls itself; check the code below matches the one it shows" and the peer id shortened (`shortPeerId`, first 12 … last 6); the **Also an owner** switch (default on) with its one line; "Add" and "Cancel". Add mints `{ peerId: request.peerId, grantsOwner }` with core's default expiry (24 h).
2. **Copy invitation** (open): the **Also an owner** switch (default on) and a "Make invitation" button. When the switch is on, show the bearer warning above the button before minting, in the warning colour: "Anyone who gets this invitation in the next 15 minutes can manage your cadre. Send it only to your own app, and not through a chat or email others can read." Mints `{ grantsOwner }` with core's default expiry (15 minutes for an owner grant, 24 hours otherwise).

**"Also an owner", one line:** "An owner can add and remove devices and apps and approve everything in this cadre. Turn this off for an app that should only take part."

**The invitation, once minted** (`ShareCode`, below): title "Invitation for ‹appName›" or "Open invitation"; the QR code; Copy; the selectable text; expiry as a local time ("Valid until 14:32"); and the reach line from `result.reach`:

| `reach` | Shown |
| --- | --- |
| `anywhere` | nothing extra |
| `local-network` | "Your cadre's other machines are reachable only on their home network: the new app must be on the same Wi-Fi to join." |
| `issuer-only` | warning colour: "No always-on machine of your cadre can answer this invitation, so the new app can join only while this app is open and reachable. Add an always-on node (below) to avoid this." |

Keep the minted invitation on screen until the user taps "Done" (or mints another); it is not stored anywhere else.

**Outstanding invitations.** Below, a list of `listCadreInvitations()` filtered to `live`, newest first (`invite.expiresAt` descending is acceptable if there is no creation time on the row). Each row: "For ‹shortPeerId›" or "Anyone with the text"; "owner" or "member"; expiry; `usesRecorded` / total uses when more than one use. A "Withdraw" button per row, with a one-step confirm ("Withdraw this invitation? Nobody can join with it afterwards."), then `withdrawCadreInvitation(key)` and a refresh. Refresh when the section mounts, after a mint, after a withdraw, and on a "Refresh" button. No polling. Labels for which app an open invitation was meant for are not kept (the row has no such field); `app-recommends-another-app-and-enrolls-it` adds that.

**Room for the deep link.** `same-phone-apps-exchange-join-by-deep-link` will deliver a request from another app on the same phone. Let it reuse this flow by adding only an entry point: `AddDeviceSection` takes a `linkedRequest` prop (text, or null) handled exactly like a pasted one, and an `onLinkedRequestTaken` callback, the way `AddNodeSection` takes `linkedCode`. The return path (handing the minted invitation back) is that ticket's.

## Shared pieces this ticket builds

- **`src/share-code.tsx` → `ShareCode({ title, text, testIDPrefix })`**: QR + Copy + selectable text. The QR is drawn with `react-native-svg` as one `<Path>` built from the module matrix of the pure-JavaScript `qrcode` encoder (`QRCode.create(text, { errorCorrectionLevel: 'L' }).modules`): one path keeps a ~150×150-module code cheap to render, and level L keeps the modules as large as possible (an invitation is up to about 2,000 characters; architecture.md measured 1,972 with three owner keys and six addresses). Import only the encoder, not the renderers (they pull in PNG/canvas code); verify the import works under Metro with `yarn workspace @serfab/reference-app-rn test:bundle`. When `create` throws (text too long for any QR version), show "Too long for a QR code; use Copy instead." Copy uses `expo-clipboard` (`setStringAsync`) and shows "Copied" for a moment.
- **Scanner generalized**: `node-code-scanner.tsx` accepts only `sereus-join:` codes (`NODE_CODE_SCHEME`). Turn it into `CodeScanner({ visible, accepts, otherCodeHint, onScanned, onClose })` where `accepts(text)` decides and `otherCodeHint` is the line shown for a code it does not accept; `AddNodeSection` passes the node-code predicate and its current hint, this section passes `text.trim().startsWith(CADRE_JOIN_REQUEST_PREFIX)`. Rename the file to `code-scanner.tsx` and keep the latching behaviour.
- **Dependencies** (in `packages/reference-app-rn`, with `yarn expo install` so the versions match Expo SDK 53): `expo-clipboard`, `react-native-svg`; plus `qrcode` and `@types/qrcode` (dev). `expo-clipboard` and `react-native-svg` are native modules: a dev client built before this change fails to load Settings. Add them to docs/reference-app-rn.md → "When Native Rebuild Is Needed" and "Key Dependencies".

## Hook and module surface

- `cadre-phone.ts`: `createCadreInvitation(options)`, `listCadreInvitations()`, `withdrawCadreInvitation(key)` as thin pass-throughs over `running()`, like the formation helpers.
- `use-cadre.ts` (`UseCadreResult`): the same three, plus `isMemberPeer(peerId): Promise<boolean>` for the already-a-machine check (reads `queryCadrePeers()`; false when not running). Each throws "Node not started" when there is no node, as the other actions do.

## Edge cases & interactions

- This phone has no address of its own (relay not `reserved`) and the cadre has no other member with an address: `createCadreInvitation` throws. Alert "Could not make an invitation" with the core message as the detail; when `relayStatus !== 'reserved'`, add "This phone has no relay address, and no always-on machine of your cadre has one either." Verified by inspection.
- `createCadreInvitation` while the owner key is not wired (status `owner: 'timed-out'`, a joined app whose grant has not arrived): the section shows the member line because `isOwnerDevice()` reads the `OwnerKey` rows; if it races and minting throws "not initialized with an owner key", show the same alert. By inspection.
- A request whose peer id is not Ed25519, an over-long app name, an invitation pasted as a request: refused by `decodeCadreJoinRequest` with its own words. By inspection (core has its own tests).
- Mint, then Disconnect before handing it over: the invitation stays valid in the cadre until it expires or is withdrawn; the list shows it after the next Connect. By inspection.
- Withdraw an invitation already redeemed: `live` is already false, so it is not listed; `withdrawCadreInvitation` returning `false` (already withdrawn elsewhere) refreshes the list without an error. By inspection.
- Withdraw while alone (no connection): the tombstone commits locally and is re-issued on cohort growth (core behaviour). Say nothing extra. By inspection.
- Double tap on Add / Make invitation: guard with a ref while minting, as `runFounding` does (`foundingRef`). By inspection.
- The scanner change must keep the node-code flow unchanged (same hint text, same latch). By inspection, plus the existing `node-claim.spec.ts` stays green.
- QR too long: fallback line, Copy still works. By inspection.

## Tests

No new tests. The logic is UI over cadre-core calls that have their own tests; the one branch with real choices (the reach table) is a typed `Record<CadreInvitationReach, string | null>`, so a new reach value fails typecheck.
