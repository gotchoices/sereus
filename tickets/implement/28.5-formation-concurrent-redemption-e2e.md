# The acceptance test for concurrent redemption across two machines

## Why this exists

An invitation can admit several people, and can require outside approval first — the inviting
party's node calls a web hook that may be a queue a **human** works through. Two failure modes
matter, and only two real machines can produce them:

1. a joiner is told its join succeeded and its consent record then vanishes (what was measured
   on 2026-08-02 under the old sequence-number design, and what
   `formation-unique-token-redesign` removes by giving every acceptance its own row key);
2. a human is asked to approve the same join twice because the node discarded an approval it
   already held.

Every existing test of the second mode stages its collision inside one node with stubs. This
scenario is the missing half: a genuine cross-machine race, no stubs, against the redesigned
schema.

## What changed since this ticket was first written

There is no collision-retry loop any more. `withUseNumberRetry`, `isLostUseNumberRace`,
`USE_NUMBER_ATTEMPTS` and the `UseNumber` column are all deleted by the prerequisite ticket.
Two concurrent redemptions no longer contend for anything: each writes under its own
joiner-minted nonce (`UsageStampId`, now the primary key). The invitation's use cap is a count
against the committed snapshot, which means it is **eventually audited, not strictly enforced** —
two nodes racing the last seat may both land, by explicit human decision (see the prerequisite
ticket's decision-context section). Do not write an assertion that treats that as a failure.

What survives from the original ticket: the two-node harness recipe and its ordering
constraints, both-nodes'-views assertions, per-row attribution, and the hard-equality approval
count.

## What to build

A scenario under `packages/integration-tests/src/scenarios/` — real network, two real
`CadreNode`s. It cannot live in `cadre-core`'s unit suite: one node's writes are serialized by
its own write queue, so they never race.

**Case 1 — concurrent redemption of a multi-use invite.** One invitation permitting at least two
acceptances, requiring approval from an `ApprovalHookServer`
(`packages/integration-tests/src/harness/fixtures/approval-hook-server.ts` — a real in-process
HTTP approver over a real socket, with a real signature and a `requestCount`). Two nodes redeem
it concurrently (same-tick `Promise.allSettled`), neither waiting on the other. Then:

- both acceptances are recorded — two rows, distinct `UsageStampId`, distinct `PeerKey`;
- each stored row carries its own joiner's key, signature, and disclosure exactly as submitted
  (re-verifiable with `verifyFormationConsent`);
- both rows are visible in **both nodes'** views after convergence;
- the approval hook was asked **exactly twice** — hard equality, not `>= 2`.

**Case 2 — concurrent redemption of a single-use invite (the accepted over-admission case).**
An invitation permitting ONE acceptance, redeemed concurrently by two nodes. The outcome is
deliberately non-deterministic, so assert the invariant rather than a count:

- **every joiner that received an approved response has its row present, on both nodes' views** —
  responses and surviving rows correspond one-to-one. This is the assertion that would have
  caught the original defect, where both writers were told they succeeded and one row was
  silently dropped;
- at least one joiner succeeded (the invite is not lost);
- if a joiner was refused, the refusal is the terminal `'Invalid token'` reason
  (`InvitationExhaustedError` mapped by `StrandFormationManager.provisionAsResponder`), never
  the retryable `'Formation conflict, retry'`;
- if BOTH landed, that is a pass — log it, and assert the overage is observable: a count of
  `FormationUsage` rows for the token exceeds the invite's `TotalUses` on both nodes. Report in
  the review handoff how often each outcome occurred across runs.

**Case 3 — sequential exhaustion across nodes.** After case 2 has converged, a THIRD redemption
of the spent invite, issued once the cohort agrees on the committed rows, must be refused
terminally (`'Invalid token'`), not told to retry. This is the arm of the cap that is still
strict, and the one a reader will assume is broken when they see case 2 pass with two rows.

## Edge cases & interactions

- **Cohort size.** A one-member cohort commits on the writer's own vote, so a passing write
  proves nothing about two machines. Establish `readCohort(node.getControlNode()!)` ≥ 2 on BOTH
  sides before racing (`packages/integration-tests/src/harness/control-cohort.ts`).
- **Write-while-alone ordering.** Connect the two nodes BEFORE the first control write. A row
  committed while a node is alone cannot be read back once its cohort grows (tracked separately
  in `control-db-cross-node-convergence-halted`). `bootPair` in
  `packages/integration-tests/src/harness/node-fixtures.ts` calls `makeOwnOwner(A, aKey)` while
  A is still alone — that ordering fails. Add a variant that connects first and writes the owner
  key after, or take the connect-then-write sequence explicitly in the scenario; do not "fix"
  `bootPair` itself, other scenarios depend on its current order.
- **Which node observes the final state.** Assert on both nodes' views. Asserting only on the
  writer's own view is exactly what missed the lost update this line of work uncovered.
- **Attribution, not counting.** Assert `UsageStampId` and `PeerKey` per row. A count of 2 holds
  even when both rows belong to the same joiner.
- **The approval count is a hard equality.** `>= 2` would pass the very regression this exists
  to catch. Note that the hook is asked once per redemption ATTEMPT that reaches the approval
  step — with the retry loop gone there is no re-ask path left, so equality is now the plain
  expectation rather than a property recovered by machinery.
- **Convergence lag is not a failure.** Both nodes converge on both rows eventually; use the
  harness's wait helpers (`packages/integration-tests/src/harness/wait-utils.ts`) rather than a
  fixed sleep, and let the wait's timeout be the failure, so a slow run reads as slow rather
  than as a lost row.
- **Duplicate-nonce convergence.** Two nodes that have not converged could each admit the SAME
  nonce (documented on `UsageStampId` in `schemas/control.qsql`). This scenario's joiners mint
  independent nonces, so it cannot arise here — do not add an assertion that would fail if it
  ever did; that caveat is accepted, not under test.
- **Teardown on the failure path.** A wait that throws inside `beforeAll` leaves both nodes
  running. Stop both nodes and close the hook server in `finally`, whatever happened.

## On flakiness

The race was provoked on the FIRST attempt with a plain same-tick `Promise.allSettled`, both on
a single node with two database handles and on two real machines — so provoking it is easy. The
risk is the reverse: over-tight assertions on an outcome the design deliberately leaves
non-deterministic (case 2). If a case turns out to need luck to pass, say so in the review
handoff rather than weakening a case-1 or case-3 assertion. A flaky test here is worse than none.
