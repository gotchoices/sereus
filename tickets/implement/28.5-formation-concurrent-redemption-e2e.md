# The acceptance test for concurrent redemption across two machines

## Why this exists

An invitation can allow several people in, and can require outside approval first — the
inviting party's node calls a web hook that may be a queue a **human** works through. If the
node discards an approval it already holds because it lost a race for a sequence number,
that person is asked to approve the same join twice.

`debt-formation-approval-retry-lost-race` fixed that: the node re-uses the approval it holds
and takes the next free sequence number, up to three tries. Every test of that fix stages the
collision artificially inside one node — one replaces the "what is the next number?" lookup
with a stub, another replaces the write with a stub that throws a previously captured error.
They prove the recovery LOOP is correct. None of them produces the collision the way two
machines produce it.

This scenario is the missing half: a genuine cross-machine race, no stubs.

## Read this first

Do not start until `28-formation-use-number-lost-update-cross-node` (in `blocked/`) is
resolved. That ticket records the measured behaviour today: two machines racing the same
sequence number are BOTH told they succeeded and only one row survives — no error is raised,
so the recovery loop is never entered. Written against today's storage layer, every
assertion below fails, and it fails by *silently losing a joiner*, not by a message this
scenario could weaken an assertion around.

That ticket also carries the working boot recipe, including the one non-obvious ordering
constraint (connect the nodes BEFORE the first control write). Reuse it.

## What to build

A scenario under `packages/integration-tests/src/scenarios/` — real network, two real
`CadreNode`s. It cannot live in `cadre-core`'s unit suite: that suite boots one node with an
empty bootstrap list, and one node's writes are serialized by its own write queue, so they
never race.

**The positive case.** One invitation permitting at least two acceptances, requiring approval
from an `ApprovalHookServer` (a real in-process HTTP approver with a `requestCount`, over a
real socket with a real signature). Two nodes redeem it concurrently, neither told to wait for
the other. Then:

- both acceptances are recorded, numbered 1 and 2 — no gap, no duplicate;
- the approval hook was asked **exactly twice**, once per joiner;
- each stored acceptance carries its own joining peer's key, signature, and disclosure,
  exactly as submitted.

**The negative case.** An invitation permitting only ONE acceptance, redeemed concurrently by
two nodes: exactly one acceptance is recorded, and the other is refused in a way that does not
tell the joiner to retry (`InvitationExhaustedError`, not the generic `CHECK constraint
failed: Authorized` the manager maps to a retryable `Formation conflict, retry`).

## Edge cases & interactions

- **Cohort size.** A one-member cohort commits on the writer's own vote, so a passing write
  would prove nothing about two machines. Establish `readCohort(node.getControlNode()!)` ≥ 2
  on BOTH sides before racing.
- **Which node observes the final state.** Assert on both nodes' views. Asserting only on the
  writer's own view is exactly what misses the lost update this line of work uncovered — in
  the measured failure both nodes agreed on a single surviving row while both writers had been
  told they succeeded.
- **Attribution.** Assert on `UsageStampId` / `PeerKey`, not only on the set of use numbers.
  `[1, 2]` can hold while both rows belong to the same joiner.
- **The approval count is a hard equality, not a lower bound.** `>= 2` would pass the very
  regression this exists to catch.
- **Retry-loop interaction.** `withUseNumberRetry` sits OUTSIDE `lockedWithRetry`, so a
  transient cluster failure retries INSIDE a use-number attempt. The two classifiers
  (`isLostUseNumberRace`, `isRetriableControlWriteFailure`) are documented as disjoint; a real
  cross-machine failure is the first thing that can test that claim against a live cluster
  rather than against string literals. Record which classifier claimed the loser's error.
- **Bounded attempts.** `USE_NUMBER_ATTEMPTS` is 3. Two racing writers must converge well
  inside that. A scenario needing more than 3 is reporting a real problem, not a flaky test —
  do not raise the bound to make it green.
- **Write-while-alone ordering.** Connect the two nodes before the first control write. A row
  committed while a node is alone cannot be read back once its cohort grows (tracked
  separately in `control-db-cross-node-convergence-halted`); getting this order wrong makes the
  scenario fail in setup for an unrelated reason.
- **Teardown on the failure path.** A wait that throws inside `beforeAll` leaves both nodes
  running. Stop both nodes and close the hook server in `finally`, whatever happened.

## On flakiness

The race was provoked on the FIRST attempt with a plain same-tick `Promise.allSettled`, on
both a single node with two database handles and on two real machines. So provoking it is
easy; the risk runs the other way — a test written before the storage layer's behaviour is
settled is flaky *because the behaviour is*. If, after the blocking fix lands, the race turns
out to be hard to provoke reliably, say so in the review handoff rather than weakening the
assertions. A flaky test here is worse than none.
