# An invited machine does not publish the record its admission wrote

`new-machine-self-record-written-once` made the redemption request carry the device's signed address record, and the admitting member writes it on the device's `CadrePeer` row when it verifies (`admittedRecord` in `cadre-invite-protocol.ts`). It also added `CadreNode.publishSelfRecordUnlessCurrent()`: it writes nothing when the row still holds the record this process last signed, that record is less than half a heartbeat old, and the node's addresses and profile are unchanged. Today only the boot timer uses it, and only after an insert (a founding owner's explicit publish).

The rest was held back. With it in place, `cadre-invite-any-member`'s returning owner never lists the new device (5 of 5 runs), because the writes it removes were hiding a fork: the restarted owner's first write after reconnecting commits on a cohort of one before its sibling identifies, and only a later conflicting write healed it. See `implement/reconnect-writes-wait-for-sibling-identify` for the measurements. Do this once that ticket lands.

## What to change

- **Remember the redemption's record before dialing.** In `redeemCadreInvitation`, call `rememberSignedSelfRecord(record, false)` right after `signRedeemRequest`, not after acceptance. The member's commit reaches the device (it is in the write's cohort) before the reply does, and a reconcile pass that sees the row first must find it current. This race was observed: P's pass picked up its row before the reply and wrote its record again, a 10.8 s write. A record no member wrote matches no row, so a failed redemption costs nothing.
- **`publishFirstSelfRecord` calls `publishSelfRecordUnlessCurrent()`** instead of `registerSelf()`, and its NOTE goes.
- **Boot timer** (`scheduleSelfRegistration`): call `publishSelfRecordUnlessCurrent()` unconditionally, dropping the `lastSelfRecordRefreshedARow` branch and its NOTE, and the field if nothing else reads it. Do not key it on whether the node has control connections: a device that redeems within a second of starting is connected when the timer fires, and would write again.
- **Drain step 2** (`runDrainControlReplication`): `pendingSelfPeerWrite ? registerSelf() : publishSelfRecordUnlessCurrent()` on first growth. A self write made while alone is always re-touched, because the re-touch is what spreads it.
- Update `docs/architecture.md`: the Cadre Node self-record step 4 ("it still publishes again once the row reaches it") and the owner self-registration paragraph ("After a refresh of a row an earlier process left, it writes again").

## Validation

- `cadre-invite-any-member` at least 3 runs, A listing P about 12 s after reconnecting; `cadre-invite-row-unreplicated`, `machine-removal`, `owner-grant-backup-recovery`, `owner-grant-without-machine`.
- With `DEBUG=sereus:cadre:node`, the device logs `reconcileControlCohort: first self-record publish: current`, and no `refreshed own CadrePeer record` until its heartbeat.
- Message cost, `MESSAGE_COST_CASE=invite`, against the numbers recorded in `new-machine-self-record-written-once`'s complete ticket: the B→A `cluster` streams of B's own record write should go to 0 (measured with the full change: redeem plus settle, 129 → 116 app streams and 97 → 79 gets against HEAD `e389e66b`, a single run each).
