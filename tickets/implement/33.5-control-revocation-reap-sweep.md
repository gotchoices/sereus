# Reap sweep: enumerate held tombstones and drop the rows they retire

## Background

`control-revocation-reap-authorization` (prereq) adds the schema branch that lets a node
delete a guarded row when it already holds a **committed** `Revocation` tombstone naming that
exact row incarnation, plus `ControlDatabase.reapRevokedRow(table, rowKey, stampId)` which
performs one such delete. Nothing calls it. This ticket adds the enumeration and decides when
it runs.

## Where the reap runs, and why

**The periodic cohort reconcile pass** (`CadreNode.runReconcileControlCohort`,
cadre-node.ts:1758, ~15 s cadence), gated on the node having at least one control connection.

The two alternatives were rejected:

- **The cohort-growth drain** (`runDrainControlReplication`) fires only on the 0→≥1
  control-connection edge. A node that stays continuously connected and converges on a
  tombstone by ordinary replication never sees that edge, so it would never reap. The drain
  is the wrong trigger for a condition that arrives by replication rather than by a local
  write.
- **Lazily on read.** `queryCadrePeers` is called from `refreshMembershipGate`, which runs
  inside `mutateCadrePeer`'s non-re-entrant write lock. A write issued from that read path
  self-deadlocks. Reads in this class stay reads.

### The connectivity gate is load-bearing

Run the reap **only when `getControlConnectionCount() > 0`** (i.e. `!committedAlone()`).

A reap is a write. A write committed while the node is alone is local-only and forks that
node's own revision history — which is the exact condition this whole line of work exists to
stop creating (`tickets/blocked/forked-control-collection-sync-livelocks.md`). There is no
urgency: the stale row is already inert to every reader, so waiting for connectivity costs
nothing and keeps the reap a fork-*closing* operation instead of a fork-creating one.

Honest scope note, because the source ticket asked: **this does not close the fork at the
storage-revision level, and must not be described as fixing the livelock.** It makes the two
nodes agree on *content*. Whether two histories that now agree on content still reconcile is a
question about optimystic's `Collection` sync semantics, tracked upstream in the blocked
ticket above and in `tickets/blocked/strand-unique-index-sync-stale-revision`. Claim content
convergence and garbage removal; claim nothing about the retry loop.

## What to build

### `ControlDatabase.reapRevokedRows(selfPeerId: string): Promise<number>`

Enumerate and reap; returns how many rows were removed.

```
held = await this.queryRevocations()
if (held.length === 0) return 0
for each tombstone t in held:
    skip unless t.tableName is in REAPABLE_TABLES
    skip if (t.tableName is 'CadrePeer' or 'DeviceToken') and t.rowKey === selfPeerId
    if (await this.reapRevokedRow(t.tableName, t.rowKey, t.stampId)) reaped++
```

- **Enumerate unlocked, delete per-row locked.** `reapRevokedRow` takes the write lock
  itself (via `mutateCadrePeer` / `execWrite`), so this loop must not hold it — the lock is
  not re-entrant. Same structure as `CadreNode.reissueAuthoredMembershipRows`.
- **Cost is O(tombstones), not O(live rows):** one `queryRevocations()` scan plus one
  `queryStampId` point lookup per tombstone, and the empty-table early return makes the
  common case (a party that has never revoked anyone) a single scan per pass. Add a `NOTE:`
  tripwire at the method: `Revocation` is append-only and unbounded, so this is O(all
  tombstones ever) point lookups every reconcile tick; fine while revocations stay rare for a
  cadre-sized party, but if the table grows, persist a node-local high-water mark of what has
  already been reaped rather than re-scanning. (Mirror the wording of the existing sweep
  `NOTE:` on `CadreNode.drainPendingRevocations`.)
- `selfPeerId` is a parameter, not read from `config.libp2pNode.peerId`, so the skip-self
  rule is testable without a libp2p node.

### Why self is skipped

A node reaping its *own* `CadrePeer` / `DeviceToken` row would immediately fight its own
re-registration: `registerSelf` and `retouchSelfDeviceToken` run on the heartbeat and on the
growth drain, and after a self-reap the insert-if-absent guard sees an absent row and takes
the insert path — which needs an owner signature `NotRevoked` will refuse anyway for a
retired stamp, and which a revoked drone cannot produce at all. The result is recurring
failure noise every cycle, in exchange for removing the one stale row nobody else reads from
this node (every other node filters it by tombstone).

Skipping self is a deliberate, documented limit, not an oversight: a revoked node keeps its
own copy of its own row. If "a node that learns it has been revoked should shut itself down"
is ever wanted, that is a distinct behaviour and its own ticket, not a widening of this
sweep.

`ValidationKey` has no self notion; do not special-case it.

### Wiring into `runReconcileControlCohort`

Place the call **after** `refreshDelegateGrants()` and **before** step 1 (the sibling
enumeration), with the usual `_running` / `controlNode` / `controlDatabase` re-guard after
the preceding await.

Position matters: the pass early-returns when `siblings.length === 0`, and a cadre whose only
sibling row is the tombstoned one lands in exactly that branch — `listMembers()` filters
retired stamps, so the row that needs reaping is invisible to the sibling count. A reap
placed after step 1 would never run for the smallest and most likely case.

```ts
// Reap guarded rows this node still holds for incarnations an already-committed
// Revocation tombstone retires — the half of a removal replication cannot carry
// (a delete of an already-absent row replays as nothing). Connected-only: a reap
// is a write, and a write committed alone is local-only and forks this node's own
// history, which is the condition this work exists to stop creating.
if (this.getControlConnectionCount() > 0) {
  try {
    const reaped = await this.controlDatabase.reapRevokedRows(selfPeerId);
    if (reaped > 0) {
      log('reconcileControlCohort: reaped %d revoked control row(s)', reaped);
    }
  } catch (error) {
    log('reconcileControlCohort: reap pass failed (continuing): %o', error);
  }
}
```

`selfPeerId` is currently computed at cadre-node.ts:1783, after the delegate-grants block —
hoist that one line above the reap rather than reading the peer id twice.

Best-effort by contract, like every other step in this pass: a reap failure is logged and the
pass continues to the dial work. Do **not** let it abort reconcile — reconnecting siblings
outranks garbage collection.

## Edge cases & interactions

- **Alone with rows to reap** → nothing happens, no log spam beyond the existing pass line.
  Assert this: it is the gate, and a regression here silently reintroduces fork creation.
- **Tombstone for a table outside `REAPABLE_TABLES`** (`Strand`, `OwnerKey`) → skipped
  silently. `Strand` tombstones are the common case in a party that has unpublished a strand;
  they must not produce per-pass log noise.
- **Tombstone whose row this node never held** → `reapRevokedRow` returns `false` after the
  raw stamp read, no write. This is the majority case on most nodes and every pass will walk
  it; keep it allocation-cheap and silent.
- **Tombstone whose row was re-seated at a fresh stamp** → stamp mismatch, no write. Covered
  by the prereq ticket's tests; assert here that the sweep does not turn a safe per-row no-op
  into a throw that aborts the pass.
- **Several tombstones for one row key** (seat → delete → re-seat → delete) → at most one can
  match a live stamp; the rest are no-ops.
- **`stop()` mid-sweep.** Re-guard `_running` / `controlDatabase` inside the loop and return
  the count so far, exactly as `reissueAuthoredMembershipRows` does. A pass that outlives
  teardown must not touch a torn-down node.
- **Concurrent passes.** `reconcileControlCohort`'s single-flight guard already collapses
  them, so the sweep inherits it — do not add a second guard.
- **Interaction with the growth drain.** `drainPendingRevocations` re-issues tombstones;
  this sweep consumes them. They can run in the same window (a growth edge fires the drain
  while a reconcile tick is mid-sweep). They touch different tables (`Revocation` update vs
  guarded-row delete) and both take the write lock per statement, so there is no shared
  mutable state — but state that in a comment so a later reader does not add a mutex.
- **Interaction with the membership gate.** Reaping a `CadrePeer` row cannot change the
  authorized-member snapshot: `queryCadrePeers` already dropped that row for its retired
  stamp. The refresh `mutateCadrePeer` fires is therefore redundant-but-harmless. If a future
  change makes it load-bearing, that is a real behaviour change and needs its own reasoning.
- **Blocked upstream, do not chase:** integration proof of the reap crossing a real network
  is unreachable today — `control-delete-while-alone-convergence.integration.ts` dies in
  Phase 1 setup on `tickets/blocked/control-db-cross-node-convergence-halted.md`. Do not add
  a new integration scenario that will only join the pre-existing-failure ledger; say plainly
  in the handoff that the sweep has no live-network proof.

## Testing

Extend `packages/cadre-core/test/control-revocation-reap.spec.ts` (created by the prereq) and
`packages/cadre-core/test/cadre-node-control-cohort.spec.ts`.

`ControlDatabase.reapRevokedRows`:

- reaps a `CadrePeer` row whose committed tombstone matches (using the prereq's
  `RowIsGone`-stripped schema fixture), returns 1, row gone
- **skips the node's own peer id** for `CadrePeer` and `DeviceToken` — that row survives a
  sweep that reaps a sibling's in the same pass
- skips a `Strand` tombstone, leaving the strand row intact
- returns 0 and performs no write when `Revocation` is empty
- returns 0 when every tombstone names a row this node does not hold

`CadreNode` wiring:

- a reconcile pass with **zero control connections** performs no reap (spy on
  `reapRevokedRows`, assert not called) — the gate
- a reconcile pass with ≥1 connection calls it once with the node's own control peer id
- a reap that **throws** does not abort the pass: the sibling enumeration and dial steps
  still run
- a pass on a cadre whose only sibling row is tombstoned (so `listMembers()` returns none and
  the pass takes the `dialColdStartBootstrap` early return) still reaped — pins the
  before-step-1 placement
