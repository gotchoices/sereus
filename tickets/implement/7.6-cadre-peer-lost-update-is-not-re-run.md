# A `CadrePeer` row's two writers refuse each other, and the loser is never re-run

Supersedes `tickets/backlog/bug-owner-write-racing-a-machines-own-publish-fails` (same defect, seen there on `removeMachine`). Delete that backlog ticket as part of this work.

## The defect

A machine's `CadrePeer` row has two writers that fire at the same moment during a cadre's start:

- **The owner's write-while-alone drain** (`CadreNode.reissuePendingPeerWrites` → `reissuePeerAuthorize` → `SeedBootstrapService.reauthorizePeer` → `ControlDatabase.reauthorizeCadrePeer`) re-touches rows the owner authorized while it had no control connection. It fires when the owner first gets a reachable sibling, which is the moment the other machines connect.
- **The machine's own self-publish** (`CadreNode.scheduleSelfRegistration` → `publishSelfRecordUnlessCurrent` → `publishSelfRecord` → `ControlDatabase.updateSelfPeerRecord`) writes its signed address record about a second after start, and again on first growth, the same moment.

Both read the row, then commit. Whichever commits second is refused: Optimystic's conflict replay throws `TreeEntryChangedError` inside the action's atomic handler, and the Quereus bridge maps it to `ConcurrentModificationError` (`StatusCode.BUSY`). `ControlDatabase.lockedWithRetry` does not re-run the body, because `isRetriableControlWriteFailure` claims only a cohort that did not answer. The write is reported through `control:write-abandoned` and dropped. An owner's `removeMachine` that loses to the machine's publish fails to the user the same way.

### Reproduction (verified)

```
yarn workspace @serfab/integration-tests exec vitest run control-write-degraded-cohort-member -t "commits with a healthy three-member cohort"
```

The file's `afterEach` abandoned-write check (~line 1060) fails. The losses happen in `beforeAll`'s trio boot; the first case is the first check that sees them. Measured at `0ae0c669`, stale-build guard green: the fix-stage run of 2026-10-21 failed 1 of 1 (A `[peer-reauthorize]`); the triage before it failed 4 of 4 (twice B and C `[self-record-update]`, once B and C again, once A `[peer-reauthorize]` plus C `[self-record-update]`). The abandonment line:

```
[abandoned-write A] [peer-reauthorize] declined after 1/3 attempt(s) in 7451ms: concurrent modification: another writer changed or removed the row in CadrePeer at primary key ("<B>") | Tree collection default/cadrecontrol/CadrePeer: the entry at key … was changed by another writer since this change read it
```

Timeline from that run's log: A's re-touch attempt started at 07:55:48.9 and B's own publish of the same row committed at 07:55:49.85, one second in. A's attempt did not fail until 07:55:56.36, so a single attempt here can run about 7.5 s (its read phase waits out one per-peer read deadline). Under the 10 s retry budget the lost write gets exactly one retry. That is enough, and it is the ceiling to expect.

The stack of the refusal: `TransactionBridge.sweepDirtyTreesLegacy` → `mapCommitRefusal` → `new ConcurrentModificationError` (`quereus-plugin-optimystic/src/optimystic-adapter/txn-bridge.ts` ~1320, ~751, ~261). Not the `TransactionCoordinator` path: a one-tree update takes the per-tree sweep.

## Why re-running a lost update is safe (confirmed in the linked 1.17.0 build)

- `TreeEntryChangedError` is raised inside the action's atomic handler, so none of that action's entries land (`db-core/src/collections/tree/struct.ts`, doc on `TreeGuardRefusedError`). It is not a `StaleFailure`; Optimystic never absorbs it itself.
- **Per-tree sweep** (the path the trace shows): `sweepDirtyTreesLegacy` throws the mapped refusal bare only when no tree has synced (`synced.length === 0`) or from the pre-sweep refresh, both before anything is durable. A refusal after an earlier tree synced is wrapped in `PartialCommitError` with the refusal as its `cause` (txn-bridge.ts ~1320 onward).
- **Batched commit** (`commitBatchLegacy`, a per-commit coordinator) and the transactional path: a refusal that escapes `TransactionCoordinator.commitAttempts` through `refreshBetweenAttempts` leaves `commit()` through `reportSaved`, which rethrows it as `CoordinatorPartialCommitError` whenever any participant was saved (`db-core/src/transaction/coordinator.ts` ~389, ~595).
- `reportsPossiblyStoredWrite` already vetoes `PartialCommitError` and `CoordinatorPartialCommitError` by `instanceof` before any matcher runs. So a chain carrying `ConcurrentModificationError` with no partial-commit type above it means nothing was saved.
- The bridge's own doc on `ConcurrentModificationError` (txn-bridge.ts ~251): "retrying the statement sequentially re-reads the row and decides again."
- `ConcurrentModificationError` is exported from both the plugin's root and `/plugin` entries (`quereus-plugin-optimystic/src/index.ts:26`, `src/plugin.ts:24`) and both dist entries share one chunk (`dist/chunk-*.js`), so one `instanceof` covers both, as it does for `PartialCommitError`.

## Why widening the default classifier alone is wrong

The funnel re-runs only the locked body. For two of the three writers the read, the decision and the signature happen outside that body, so a bare re-run of the same statement is either refused again or does damage:

1. **Self-publish** (`updateSelfPeerRecord`). `publishSelfRecord` reads the row, `signSelfRecord` signs `UpdatedAt = max(now, current.updatedAt + 1)`, then `execWrite` runs the one statement. A re-run presents the same signed record. If the rival was the owner's re-touch, it bumped `UpdatedAt` to `max(now@owner, old + 1)`, which can exceed the signed value, and the self branch of `CadrePeer.AuthorizedUpdate` fails `new.UpdatedAt > old.UpdatedAt`, a CHECK failure that is correctly never retried. The row must be re-read and the record re-signed inside the retried body.
2. **Owner re-touch** (`reauthorizeCadrePeer`). The drain reads `record.sig` outside the lock and skips a row the machine has already self-published (`reissuePendingPeerWrites`, `reissueAuthoredMembershipRows`). The database method then reads the stamp outside the lock, signs, and runs the statement inside `mutateCadrePeer`. A bare re-run after losing to that self-publish would commit the owner branch over the self-signed row: it rewrites `UpdatedAt`, leaves `Sig` signed over the old `UpdatedAt`, and makes the machine's address record unverifiable to resolvers until its next heartbeat (the `NOTE:` on `AuthorizedUpdate` in `control-schema.ts` ~477). The "only while unsigned" decision must move into the locked body.
3. **Removal** (`deleteCadrePeer`, `removeMachine`). Both bodies already read the stamp and sign inside the lock (`deleteGuardedRow` ~3420, `signMachineRemovals` ~2630, both `retry: false`), and the `'remove'` digest binds `(PeerId, StampId)`, which a self-publish never changes. These need only the opt-in.

## Design

### The policy (`control-write-retry.ts`)

Add a second named policy beside `SCHEMA_INIT_RETRY_POLICY`, say `LOST_UPDATE_RETRY_POLICY`, whose classifier is the default one plus `ConcurrentModificationError` claimed **by type** (`instanceof`, imported from `@optimystic/quereus-plugin-optimystic`, the same entry `PartialCommitError` comes from; the `NOTE:` on `reportsPossiblyStoredWrite` about the two entries sharing one chunk applies to it too). Both vetoes (`reportsPossiblyStoredWrite`, `reportsIndeterminateCommit`) still run first, so a lost update carried inside `PartialCommitError` / `CoordinatorPartialCommitError` / `SyncRetryExhaustedError` / a non-final `TornActionError` stays declined. Attempts, backoff and the 10 s budget stay the default. `matchesRetriableFailure` needs a way to claim a typed link after the vetoes; a third parameter (a link predicate) beside the message matchers keeps the vetoes in one place.

Do not add it to `RETRIABLE_CONTROL_WRITE_MATCHERS`. The module's rule stands: anything in the default list must be safe for all ~19 callers, and several other bodies sign over rows read outside the lock. Write the policy's `NOTE:` the way `SCHEMA_INIT_RETRY_POLICY`'s is written: the re-run safety is each opted-in body's, not a general property; a body may opt in only when its read of the row, its decision and its signature all run inside the locked body; name the three sites.

`mutateCadrePeer` gains an optional `policy` parameter it passes to `lockedWithRetry`, so the three sites opt in without a second wrapper. Keep `insertCadrePeer` and the other `mutateCadrePeer` callers on the default.

### Self-publish: read and sign inside the body

Change `ControlDatabase.updateSelfPeerRecord` to take the peer id and a signer callback, `(current: PeerAddressRecord) => PeerAddressRecord`, and to run under `lockedWithRetry(…, LOST_UPDATE_RETRY_POLICY, 'self-record-update')`. Inside the body: re-read the row without the read retry (thread a `retry` flag through `queryPeerRecord` down to `readMembershipRows` and its revoked-stamp read, as `queryStampId` does; a read retrying inside the lock would sleep holding it), return `null` without writing when the row is absent or its stamp retired, otherwise call the signer over the row just read and run the update. Return the record actually written.

In `CadreNode.publishSelfRecord`, the update branch becomes one call with `current => this.signSelfRecord(peerId, signingKey, addrs, current)`; its own `current` re-read and `!current` branch fold into the `null` return (keep the two log messages). `noteSelfPeerWritten` must record the returned record, so `lastSignedSelfRecord`, `isCurrentSelfRecord` and `pendingSelfPeerWrite` describe the record in the row, not the first one signed. `collectSelfAddrs` can stay outside the body; a few hundred milliseconds of address staleness across a retry is what the heartbeat exists for.

Two test callers hold the key and sign the record themselves today: `control-write-degraded-cohort-member.integration.ts` ~1443 (`bDb.updateSelfPeerRecord(record)`) and the explanation in `control-trio.ts` ~408. The first passes a signer callback building the same record shape instead; the second's comment follows the new name if it changes.

This body re-signs on each attempt, which departs from the `withWriteLock` contract text ("signatures and stamp ids minted outside the body are deliberately not re-minted per attempt"). Amend that paragraph: a body opted into the lost-update policy must mint inside, because its re-run is a re-decision over a changed row, not a re-presentation of the same write. The `ControlSign` type's `NOTE:` (~590) already states the precedent for owner signatures.

### Owner re-touch: decide inside the body

Move `reauthorizeCadrePeer`'s stamp read, its "still unsigned?" decision and its signature inside the `mutateCadrePeer` body, with `retry: false` reads, under `LOST_UPDATE_RETRY_POLICY`. The method has two callers with different intents, and the body has to know which:

- **Re-broadcast** (the drain: `reissuePendingPeerWrites`, `reissueAuthoredMembershipRows`): write only while the row's `Sig` is null, computing `UpdatedAt = max(now, current.UpdatedAt + 1)` from the row read inside the body. When the row is gone or now self-signed, write nothing. Report which of the three happened (for example `'retouched' | 'absent' | 'self-published'`) so the drain clears its queue entry on all three and `reissuePeerAuthorize` no longer needs the `currentUpdatedAt` it reads outside. The drain's own `queryPeerRecord` pre-check can go; it was the decision, and the body now makes it.
- **Re-vouch** (`removeOwner` → `revouchDependents`): write regardless of `Sig`, and leave `UpdatedAt` untouched (drop it from the `set` list in this mode). The owner branch of `AuthorizedUpdate` has no monotonic rule, and today's caller already passes the row's own `updatedAt`, so this is the same write minus a column; it also removes the one way a re-run could move `UpdatedAt` backwards past a self-signed value. Both modes are then safe to opt in. The `VouchOwner` rebinding caveat in the method's doc is unchanged.

`SeedBootstrapService.reauthorizePeer` passes the mode through; its "no row" log moves to the `'absent'` outcome.

### Removal: opt in only

`deleteCadrePeer` and `removeMachine` pass `LOST_UPDATE_RETRY_POLICY` through `mutateCadrePeer`. Confirm nothing else in those bodies is decided outside: `removeMachine`'s invitation keys come from the caller's plan (a withdrawal of an already-withdrawn invitation collides on `Revocation`'s primary key, which is a constraint failure and stays unretried, as today). `SeedBootstrapService.removePeer`'s stamp gate before the delete is unchanged.

### Constraints

- Match by type, not text. Do not widen the default list.
- The vetoes run first. Spec both the bare and the vetoed shape.
- The 10 s budget and three attempts stay. A publish that lost after 7.5 s gets one retry; acceptable.
- Do not loosen the degraded-cohort `afterEach` check.
- No schema change, no determinism edition, no migration: the chosen design decides in the body rather than in a `where` clause, so `control-schema.ts` is untouched (the `AuthorizedUpdate` `NOTE:` ~477 still describes the owner-branch bump honestly; leave it).
- Sibling repos are read-only; everything above is on this side of the bridge.
