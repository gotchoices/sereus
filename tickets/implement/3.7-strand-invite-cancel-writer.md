## What the schema (3.6) gives you

```sql
    table CancelledInvite (
        InviteKey text primary key,
        constraint OnlyClosed check (...Header.Type = 'c'...),
        constraint Immutable check on update, delete (false),
        constraint Authorized check on insert (
            exists (select 1 from committed.Manager A
                where A.MemberKey = context.ManagerKey
                    and verify(digest('Strand.CancelledInvite', 'cancel', new.InviteKey),
                               context.ManagerSignature, A.MemberKey, 'ed25519'))
        )
    ) with context (ManagerKey text, ManagerSignature text);
```

plus, on `ConsumedInvite`:

```sql
        constraint NotCancelled check on insert (
            not exists (select 1 from CancelledInvite C where C.InviteKey = new.InviteKey)
        ),
```

Blocking the `ConsumedInvite` insert blocks the whole join: `Member.Authorized`'s invite
branch needs a same-transaction fresh `ConsumedInvite` row, and `consumeInvite` writes both
rows in one transaction, so a cancelled invitation rolls the entire join back.

Note the context on `CancelledInvite` is **non-null** (`ManagerKey text, ManagerSignature
text`), unlike `Invite`/`ConsumedInvite`/`Member`'s nullable contexts — same shape as
`Revocation`. Both fields are always supplied.

## Writer surface

```ts
export interface CancelInviteParams {
  /** A manager's strand keypair — must be a PRE-EXISTING `Strand.Manager` row. */
  managerKeyPair: Ed25519KeyPair;
  /** The `Invite.Key` to kill. */
  inviteKey: string;
}
export async function cancelInvite(db: Database, params: CancelInviteParams): Promise<void>;

export interface OutstandingInvite {
  /** The `Invite.Key` (invite public key, base64url). */
  inviteKey: string;
  /** Canonical-datetime expiry string, or null for never-expires. */
  expiration: string | null;
}
/** Invites that are neither consumed, cancelled, nor expired at `nowMs` (default `Date.now()`). */
export async function listOutstandingInvites(db: Database, nowMs?: number): Promise<OutstandingInvite[]>;
```

Both go in `packages/cadre-core/src/strand-membership-writer.ts`, in the
`── Invite issuance + consumption ──` section beside `issueInvite` (line 426) and
`consumeInvite` (line 512).

- `cancelInvite` signs `signStrandApproval(['Strand.CancelledInvite', 'cancel', inviteKey],
  managerKeyPair.privateKeyB64)` and inserts with
  `with context ManagerKey = ?, ManagerSignature = ?`. Make it **insert-if-absent** (quiet
  `log()` no-op when already cancelled), matching `registerMemberPeer`'s and
  `revokeMember`'s restart-safe shape. It needs no transaction — one row, and the
  `Authorized` check defers to that statement's own commit.
- Both helpers must read via **unfiltered scans + JavaScript comparison**, never a
  where-equality on a full primary key. `memberStampId` (line 559) and the `scanMemberPeers`
  doc block (lines 814-850) carry the argument in full: a full-PK predicate becomes a
  single-key point lookup in the optimystic vtab module, which can MISS on a networked
  strand. `CancelledInvite`'s PK is the single `InviteKey` column, so any
  `where InviteKey = ?` is a full-PK predicate — scan instead.
- `listOutstandingInvites` scans `Invite`, `ConsumedInvite`, and `CancelledInvite` into JS
  `Set`s and filters expiry against `canonicalDatetime(db, nowMs ?? Date.now())` — the same
  transform `issueInvite` uses to store `Expiration` (line 434), so the string comparison
  orders chronologically. `consumeInvite` (line 521) has the precedent for the
  `nowMs ?? Date.now()` convention and the comment explaining why plain `Date.now()` is fine
  in a lib.
- Export both plus `type CancelInviteParams` and `type OutstandingInvite` from
  `packages/cadre-core/src/index.ts` — the `strand-membership-writer.js` export block is
  lines 105-136, `issueInvite`/`consumeInvite` at 111-112 and the param types at 124-126.

## `revokeMember`'s doc block is now wrong

`strand-membership-writer.ts:646-651` currently says:

> It does NOT, however, neutralize an UNSPENT invite the revoked party holds: `Strand.Invite`
> has no deactivation path (only an optional `Expiration`), so any unexpired invite whose
> private key it kept still consumes into a fresh `ConsumedInvite` and re-seats it.
> Revocation is therefore not a re-entry gate on its own — tracked as
> `bug-strand-invite-no-revocation`, pinned by `test/strand-member-revocation.spec.ts`.

Replace with the post-fix rule: a manager cancels outstanding invitations explicitly with
`cancelInvite` (enumerate them with `listOutstandingInvites`); removal does **not** cascade
into cancellation, because an invitation names no invitee, so there is nothing to match a
removed member against — invitee binding is `feat-strand-invitee-bound-invites` (backlog).
Keep the preceding paragraph about the *spent* invite (lines 641-645) as-is; it is still
accurate.

## Off-engine pre-flight

`StrandMemberVerifier.isAuthorizedToJoin` (`strand-member-registry.ts:89`) answers "door is
open" from a raw `Strand.Invite` count (lines 99-104). Once cancellation exists that count is
wrong twice over: it counts cancelled invitations, and it counts already-consumed ones.
Reuse `listOutstandingInvites` for the invite half.

Its `ConsumedInvite` short-circuit (lines 90-97) also returns `true` for a *revoked* member
still holding a stale consumption row. That is harmless — the on-engine constraints are the
real gate and this pre-flight is advisory — but comment it rather than leaving it silent.

Also update the method's doc block (lines 72-88), whose closing paragraph currently
describes only expiry filtering.

Cases, in a new `describe('cancelInvite')` plus one for `listOutstandingInvites`:

  constraint that can fire on an otherwise-valid consume.

  not exported — duplicate it or drive the transaction inline.

  (the digest binds `new.InviteKey`).
- UPDATE and DELETE of a `CancelledInvite` row are refused — pin `/Immutable/`. Copy the
  shape from the `Revocation` `Immutable` test at `strand-member-revocation.spec.ts:785`.
- a second `cancelInvite` for the same key is a quiet no-op (no throw, still one row).
- `listOutstandingInvites` omits consumed, cancelled, and expired invitations, and includes
