# Machine invitations grant no ownership

## What changes

After `owner-grant-tables` and `owner-grant-node-api`, ownership has its own credential. This ticket removes the old route, so that a machine's network identity is never an owner key anywhere (`docs/architecture.md` → Owner Keys, "Independent of machines"):

- **Schema.** `CadreInvite.GrantsOwner` goes, and with it the field in the `'add'` digest (`cadreInviteRowFields` / `cadreInviteAddMessage`). `CadreInviteUsage.OwnerStampId` and `OwnerExists` go; `PeerExists`'s second sentence (a usage completing an already-admitted device with its owner row) goes. The invitation consent branch of `OwnerKey.Authorized` goes, leaving three ways a row is seated: the founding row, an owner-signed add, and a grant redemption. Rewrite the `OwnerKey` table comment and the `CadreInvite` / `CadreInviteUsage` comments to match; the `CadreInviteUsage.Authorized` tradeoff `NOTE:` now speaks of machine invitations only (its owner-grant half lives on `OwnerGrantUsage` since `owner-grant-tables`). Bump `CONTROL_SCHEMA_VERSION`, re-pin the drift hash, keep both schema copies identical. Stores from before refuse to start (`ControlStoreIncompatibleError`); no backward compatibility.
- **cadre-core.** `grantsOwner` leaves `CadreInviteRow`, `CreateCadreInvitationOptions`, `RedeemCadreInvitationResult`, `ControlDatabase.insertCadreInvite` / `redeemCadreInvite` (the owner insert, `readSeatedAdmission`'s owner read and the "completed" case go), the protocol's row shape check, the seed-bootstrap log wording and `rentNode`. Every machine invitation defaults to 24 hours; the 15-minute default now belongs to owner grants only. `verifyInvitationOwnerAdmission` and the invitation arm of the anchor derivation go; `verifyAdmissionChain` folds into `verifyInvitationAdmission` if nothing else shares it.
- **No identity-key owner.** `CadreNode.wireOwnKeyIfOwner()` given no signer tries only the signer already wired; `identityOwnerSigner` goes. `edge-node/config.ts`'s `wireJoinedOwner` tries only the owner slot's key. Remove the `NOTE:` in cadre-cli's `start-invitation.ts` and its warning, and the "identity key an owner-granting invitation seated" wording in `owner-key-flows.ts`. This also retires the effect the `reference-app-web-owner-keys` review found: an app that joined a cadre no longer signs there with a key other than its owner slot's, so "Export this device's/tab's key" always exports the key it signs with.

## Joining as an owner: the edge node takes an owner grant

The phone kit's and edge node's join today needs an owner-granting invitation to move the app's strands (`StrandsNeedOwnerJoinError`, `docs/architecture.md` → "An app joins an existing cadre", step 2). It now takes either credential:

```typescript
joinCadre(credential: CadreInvitation | OwnerGrantBundle, options?: JoinCadreOptions): Promise<JoinCadreResult>
```

- **A machine invitation** admits the app as a machine, as today. When the party it leaves has strands to move, the join is refused before anything stops with `StrandsNeedOwnerJoinError`, whose message now says to join with an owner grant (made under the owner app's Owner keys).
- **An owner grant** makes the app a machine and an owner (`CadreNode.joinWithOwnerGrant`). The key it seats is the **owner slot's key, created when the slot is empty** (`createOwnerKey`). That key may already be an owner of the party the app founded and is leaving; one key may own several cadres (Owner Keys, "One key, several cadres"). A fresh key would need a second owner slot and a second signer per node, which the kits do not have; replacing the slot's key would lose the party being left, which the join's rollback restarts. Strands move as before, signed with that key.
- **Already running in the grant's party** (`redeemInPlace`): redeem the grant locally (`redeemOwnerGrant`) with the slot's key, wire it, and finish a deferred move, which is what the existing comment there anticipates.
- **Progress.** The `admitted` progress event's `grantsOwner` becomes whether the app joined as an owner (rename it, for example `asOwner`); the apps' join-flow lines follow.
- The phone kit, the browser app (since `reference-app-web-runs-the-edge-node`) and the NativeScript app (since `reference-app-ns-runs-the-edge-node`) all join through this edge node, so each gets the change with it; none keeps its own join code. The browser's and NativeScript's join fields still decode only a machine invitation's text (`decodeInvitationForThisTab` in `web-join.ts`); `reference-app-web-owner-grants` lets the browser's field take an owner grant, and the NativeScript app stays machine-invitation-only.

## The app flows become machine-only

The decided UI: "Add a device" has no "also an owner" choice; ownership is added through the owner-key screens with owner grants (`reference-app-rn-owner-grants`, `reference-app-web-owner-grants`). Here, mechanically:

- **Phone app**: `add-device-section.tsx` loses both owner switches (open invitation and request prompt) and the `owner`/`member` word in its invitation list; `machines-section.tsx` likewise; `recommend-app-section.tsx` loses its switch, and `AppRecommendationStore` loses `grantsOwner` (a stored entry that still has it parses, the field ignored). `join-failure.ts`'s `StrandsNeedOwnerJoinError` text says to join with an owner grant from the owner app's Owner keys.
- **Browser app**: `add-device.svelte.ts` / `AddDevice.svelte` / `Machines.svelte` the same.
- **NativeScript app**: `settings-view-model.ts` reports standing from the edge node's owner status (`status.owner`), not from the redemption's `grantsOwner`, if anything there still reads that field after `reference-app-ns-runs-the-edge-node`.
- **cadre-cli**: `cadre enroll invite --owner` goes (refused as an unknown option), the admin channel refuses a `grantsOwner` body field as `bad_request`; the README's `--owner` bullet and "An invitation minted with `--owner` seats …" sentence go. The CLI's owner-grant commands are `cli-owner-grants`.

Whether a request or recommendation answered by link between two apps on one phone should carry ownership is not settled; it is `tickets/blocked/decide-app-link-join-carries-ownership.md`. Until it is decided those flows admit a machine only, and an app with conversations to bring joins with a pasted owner grant.

## Edge cases & interactions

- **An app whose slot is empty joins by owner grant**: the key is created in the slot before the redemption; if the join then fails and rolls back, the key stays in the slot, an owner of nothing, and the next founding or grant uses it. Inspection.
- **An app joins by owner grant while its slot key is already an owner of the target party**: `alreadyOwner`, no use spent, joined as owner. Inspection (the database answer is tested in `owner-grant-tables`).
- **Rollback after the owner grant was redeemed but the self-invitation failed**: the key is an owner of the target party and the app is back in its old party. A later join with a machine invitation picks the ownership up through the slot key. Say so in `edge-join.ts`; no test.
- **Restart of a joined app**: `'joined'` origin wires the slot key only; an app that joined as a member and later redeemed a grant is an owner at its next start. Inspection.
- **`removeMachine` withdraws** the invitations the removed machine could redeem; nothing among owner grants targets a machine, so nothing more. Inspection; state it in "Removing a machine".
- **cadre-cli started with an owner-granting invitation from an older build**: impossible, since that store refuses to start. No handling.
- **`adoptStrandBundle`'s `wireOwnKeyIfOwner()`** (no argument) now only ever finds the wired signer; check it still finds the slot key the edge node wired before adopting. Inspection, and `strand-moves-between-cadres`.
