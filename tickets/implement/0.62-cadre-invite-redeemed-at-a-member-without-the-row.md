# Redemption at a member that never held the invitation row

## Background

After `stranger-connections-admitted-provisionally`, a member admits a connecting device it cannot place, and the device's `/sereus/cadre-invite/1.0.0` stream reaches `CadreInviteHandler`. When the member does not hold the `CadreInvite` row, the handler seats the owner-signed copy the bundle carries (`seatCadreInvite`, its own transaction), then redeems. Until now that seat has been a no-op in every scenario: `cadre-invite-any-member` waits for the row to replicate to the member first. This ticket exercises the path for real.

## The ordering problem in `seatAndRedeem`

Current order: check the request, seat the row, push the member's control store to the device (`catchUpDeviceIfLive`), redeem.

When the device connects, it joins the member's FRET cohort for control blocks. The handler's own doc on `catchUpDeviceIfLive` says a cohort node with no base revision of a block refuses a commit to it, so a member alone with the device would tear its write. That is why the push precedes the redemption. When the row is not held, the seat is now the first write of the exchange: it inserts into the `CadreInvite` table, whose blocks the device lacks. With cohort {member, device}, the seat is expected to tear the same way and come back `conflict` (retryable). Repeating it cannot succeed, because the push only happens after a successful seat. This is inferred from the code, not observed; the scenario below is what observes it.

**Fix: push before the seat, judging liveness on the bundle's copy when the row is not held.**

- New order: check the request (unchanged: shape, party, connecting identity, both signatures, target device); decide liveness; push the control store; seat; redeem.
- Liveness for the push decision. Use the held row when there is one. Otherwise use the bundle's copy, but only after `verifyCadreInviteRow` confirms its issuer signature. Without that check, a forged row naming a real owner as issuer would earn the forger the member's whole control store. Then apply the same conditions `isCadreInviteLive` applies: not withdrawn here (`Revocation` tombstone over its stamp), unexpired, issuer still an owner here, uses left by the local usage count. Concretely: change `isCadreInviteLive(key)` to take the row (`isCadreInviteLive(invite: CadreInviteRow)`), with the held row winning when present. Its only callers are this handler and its tests; check with grep.
- The seat stays the authority. An issuer this member does not know as an owner is still refused by the seat's constraint as `issuer-unknown`. The pre-check only decides whether the device is sent anything.
- The existing accepted-tradeoff NOTE in `catchUpDeviceIfLive` (the device keeps a copy of the control store if the write then fails) now also covers a failed seat. Extend its wording; don't add a second note.

## Scenario: `cadre-invite-row-unreplicated.integration.ts`

A new file, not a second `it` in `cadre-invite-any-member`, because `phone-owner-never-leaves-members-cohort` is rewriting that file's machines. Reuse its harness calls. If more than a few lines of helper code would be copied (`redeemWithRetry`), hoist it into `packages/integration-tests/src/harness/` and use it from both files.

Machines, as in `cadre-invite-any-member`:

- **A**, the owner, on a loopback WebSocket listen address, so the member's FRET evicts it once it stops.
- **M**, a storage-profile member admitted by A (`addDrone` plus seed delivery), pinning A's owner key.
- **P**, a phone-shaped device with no pinned key.

Steps:

1. A and M converge as members.
2. Sever A from M. Give A a test connection gater that denies dials to M and inbound connections from M (the pattern in `control-cohort-edge-carries-data.integration.ts`), then hang up every A–M connection. Wait until neither holds a connection to the other.
3. A mints an untargeted, owner-granting invitation (`createCadreInvitation`). Its address list names A first, then M; `siblingInvitationAddrs` reads M from A's replicated `CadrePeer` rows. Assert that M does **not** hold the row (`M`'s `isCadreInviteLive` / `queryCadreInvite` for the invitation key returns nothing).
4. Stop A. Wait until M's control cohort no longer includes A (`readCohort`, as the any-member scenario does).
5. P redeems. Expect success on the **first** attempt (`attempts === 1` with `redeemWithRetry`). That pins the push-before-seat order: without it, the seat tears and the first attempt answers `conflict`.
6. Assert:
   - M now holds the row, seated from the bundle;
   - M lists P as an authorized member;
   - P has anchored A's owner key from the bundle;
   - P reads M's control tables (the catch-up landed).
7. Optional, if cheap: restart A without the severing gater, and assert A converges to see P as a member.

## Edge cases & interactions

- **Forged bundle row** (issuer signature does not verify). No push, then the seat refuses. Test at the unit level in `cadre-invite-protocol.spec.ts` with the existing store fake: one case asserting `catchUpDevice` is not called. This is the security contract of the reorder.
- **Bundle row withdrawn here** (a tombstone replicated to M while the row itself did not). No push; the seat succeeds or no-ops; the redemption answers `invite-spent`. Verify by inspection, since `isCadreInviteLive` is shared.
- **Issuer not an owner here.** No push; the seat answers `issuer-unknown`, retryable, and the device tries the next address. Unchanged outcome, verify by inspection.
- **Row already held** (the ordinary `cadre-invite-any-member` path). Liveness is read from the held row; the push and the no-op seat happen in a different order but with the same effect. `cadre-invite-any-member` must still pass with its one-attempt pin.
- **Two devices redeeming a one-use invitation concurrently at a member without the row.** Both may be pushed the store before one redemption wins. That is the existing accepted tradeoff (a failed write leaves the device holding the store) and needs no new handling.
- **Provisional-connection deadline.** The push now runs before the seat. Until the seat commits, the member's gate still has the device in provisional state, and the deadline (`relayedRequestBudgetMs`) re-asks at expiry. On loopback the exchange finishes far inside it. If the scenario ever shows a close at expiry, the push is slower than the device's own per-address budget, and the budget derivation is what needs revisiting, not the order.
