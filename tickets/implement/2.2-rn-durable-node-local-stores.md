# Durable trusted-owner anchor + bootstrap peers on React Native

`startPhoneNode` (`cadre-phone.ts`) injects neither `trustedOwners.store` nor
`bootstrapPeers.store`, so both node-local records are in-memory only. A phone invited
while the owner is momentarily unreachable retries only until the app is relaunched, then
has nothing left to dial *and* no anchored owner key to judge the group's rows with.
Recovery today needs a human to obtain and apply a fresh seed.

## Two records, two backends — deliberately

The two records have different security properties, so they do not get the same store.

**Trusted-owner anchor → `expo-secure-store`** (iOS Keychain / Android
Keystore-encrypted preferences), via the same injected `SecureStoreApi` seam
`secure-key-store.ts` already uses. The anchor is not secret, but it *is* trust-bearing:
anything that can silently edit it can make this device believe a stranger is an owner.
Secure store is the most tamper-resistant thing this app has, it is where the identity
key already lives (so the anchor and the key it qualifies share one fate — including iOS
Keychain surviving an app reinstall, which is the *desirable* direction: same peer id,
same trusted owners, device rejoins), and the payload is tiny — one base64url ed25519 key
(43 chars) plus `{source, trustedAt}` is roughly 90 bytes, and a real anchor holds one to
three keys, far under SecureStore's ~2048-byte soft value limit.

**Bootstrap peers → LevelDB** (`LevelDBKVStore` from `@optimystic/db-p2p-storage-rn`,
over a dedicated `sereus-node-local` database opened with the existing `openLevelDb`
helper). These are dial hints; dialing grants no authority, and `CadreNode` re-binds every
address to the peer id it was retained under, so ordinary app-private storage is adequate.
They also do not *fit* in secure store: multiaddrs run 80–120 characters each, several per
peer, and the snapshot grows for the node's whole lifetime — it would cross the
2048-byte limit and fail the write.

No new native dependency: `expo-secure-store` and `rn-leveldb` are both already linked, so
no dev-client rebuild is needed. (`expo-file-system` was the other candidate for the dial
hints and was rejected purely for that reason — it would force a native rebuild for no
behavioural gain.)

Slot keys:

- SecureStore: `sereus.anchor.<base64url(partyId)>` — kept clear of the
  `sereus.ks.` prefix `SecureStoreKeyStore` owns, and encoded because SecureStore keys
  permit only `[A-Za-z0-9._-]`. Reuse the same encoding helper shape as `safeKey`.
- LevelDB `sereus-node-local`, `LevelDBKVStore` key `bootstrap-peers.<partyId>`.

Both slots are ungated (`requireAuthentication` unset, `keychainAccessible:
AFTER_FIRST_UNLOCK`), matching the identity slot: the node must come up headless / on a
push wake, and a biometric-set change must not invalidate the anchor.

## Sketch

```ts
// SecureStore-backed slot for the anchor.
function secureSlot(backend: SecureStoreApi, key: string, options: SecureStoreOptions): DurableSlot {
	return {
		async load() {
			// A throw means access denied / backend failure — NOT an empty slot.
			// Propagate, so the shared loader's "present but unreadable ⇒ throw"
			// policy holds and the next save cannot destroy an intact anchor.
			const raw = await backend.getItemAsync(key, options);
			return raw ?? undefined;
		},
		save: (text) => backend.setItemAsync(key, text, options),
	};
}
```

The `null` ⇒ `undefined` mapping is safe here because the slot is ungated — the
gated-`null` ambiguity documented in `SecureStoreKeyStore.gatedNullResult` does not apply.
Say so in a comment so a later reader does not "fix" it by copying the index-marker dance.

Wire in `startPhoneNode`, after the identity migration and before `new CadreNode(config)`.

## Edge cases & interactions

- **`partyId` is not persisted on this app.** Start options (party id, bootstrap addrs)
  are typed into Settings each launch and are not saved — see the comment in
  `push-wake-native.ts`. Both stores are party-scoped, so with a fresh party id per launch
  they load empty every time and this ticket delivers nothing user-visible on its own.
  Fixing that is out of scope here and filed as backlog `feat-rn-persist-node-start-options`;
  build the stores keyed by whatever `opts.partyId` the app supplies, and **say plainly in
  the review handoff** that end-to-end survival across a relaunch is gated on that ticket.
  Do not silently narrow this ticket to "the anchor only".
- **SecureStore read throws** (cancelled prompt, backend failure) ⇒ `startPhoneNode`
  rejects. Do not degrade to an empty anchor: that both hides a misconfiguration and lets
  the next write destroy an intact one.
- **SecureStore value-size ceiling.** A snapshot approaching ~2048 bytes will fail the
  native write. Do not truncate. Let the error surface, and add a `NOTE:` at the slot
  recording the headroom (~20 keys) and the escape hatch (move the anchor to its own
  LevelDB slot if a party ever anchors that many owners).
- **App reinstall on iOS.** Keychain entries survive; the LevelDB dial hints do not. The
  device keeps its identity + anchor and re-learns addresses on the next seed. Correct;
  note it rather than trying to equalise the two lifetimes.
- **App data cleared / Android reinstall.** Everything goes ⇒ fresh node, trusts no one
  until re-invited. That is the required degradation.
- **Corrupt / foreign-party snapshot.** Cold start (empty), never a crash — shared-loader
  behaviour; add an RN-level test that junk text in the SecureStore slot does not break
  startup.
- **LevelDB handle lifetime.** `openLevelDb` opens a database that must stay open for the
  node's life and be closed in `stopPhoneNode`. Today's helpers open-and-close per call;
  do not leak a handle per `startPhoneNode`, and make `startPhoneNode`'s idempotent
  early-return path (`if (node?.isRunning) return node`) not open a second one.
- **Background / push wake.** `background-runner.ts` and the push-wake path can start the
  node while the device is locked. `AFTER_FIRST_UNLOCK` is what makes the anchor readable
  there; without it the wake path would fail to start. Cover the ungated+accessible
  options in a test.
- **Persist failure.** In-memory record stands, the caller's promise rejects, the next
  successful write re-lands the full snapshot. Do not make a failed anchor persist abort
  the session's trust decision.
