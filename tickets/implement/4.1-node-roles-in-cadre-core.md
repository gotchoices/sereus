# Node roles: one preset, separately settable roles

## Why

After `node-class-replaces-node-profile`, `CadreNodeConfig.nodeClass` (`'device' | 'server'`) is still the only device-class input, and each consumer maps it on its own. That bundles four independent decisions:

- **Overlay resource tier**: FRET's `edge`/`core` profile, which sets rate limits, snapshot sizes, and dial and inbound concurrency. It is mapped by hand in two places (the control node in `cadre-node.ts`, strand nodes in `strand-instance-manager.ts`).
- **Always on**: drives the relay server default, storage replicas of unclaimed strands (`hostUnclaimedStrands`), Ring Zulu, and the published `CadrePeer.Profile`, which siblings use to dial always-on machines first and seeds use to mark preferred peers.
- **Reactivity role**: whether the node forwards change notifications to other subscribers (Optimystic cohort-topic `coreProfile()`) or only receives them (`edgeProfile()`). It is not mapped today, so every node, phones included, is a forwarder (the NOTE in `strand-reactivity.ts`).
- **Strand cohort membership**: whether the node holds and signs blocks for the strands it runs. Every node does today, and that is the intended default for phones, which participate at the transaction level. Opting out is needed for very large strands, such as a voting system with many phones. It cannot be honoured until Optimystic supports a node that serves no blocks (blocked ticket `strand-node-that-holds-no-blocks`; Optimystic `plan/client-only-node`).

## Design

`nodeClass` is the **preset** that supplies every role the config does not set.

```ts
// node-roles.ts
export interface NodeRoles {
  /** Published to the party (CadrePeer.Profile via encodeAlwaysOn) so siblings dial this machine first and seeds mark it preferred; also the default for relay serving, storage replicas and Ring Zulu. */
  alwaysOn: boolean;
  /** FRET overlay resource tier, on the control node and every strand node. */
  overlayTier: 'edge' | 'core';
  /** 'forwarder': may serve other subscribers' change notifications (cohort-topic coreProfile). 'subscriber': only receives them (edgeProfile). Only has an effect on strands with reactivity enabled. */
  reactivity: 'forwarder' | 'subscriber';
  /** Holds and signs blocks for the strands this node runs. Strands only: the control network always replicates to every party member. */
  strandCohortMember: boolean;
}

export const NODE_ROLE_PRESETS: Record<NodeClass, NodeRoles>;
export function resolveNodeRoles(nodeClass: NodeClass, overrides?: Partial<NodeRoles>): NodeRoles;
```

`CadreNodeConfig` gains `roles?: Partial<NodeRoles>`.

Presets:

| Role | `device` | `server` |
|---|---|---|
| `alwaysOn` | false | true |
| `overlayTier` | edge | core |
| `reactivity` | forwarder | forwarder |
| `strandCohortMember` | true | true |

`reactivity` stays `forwarder` for both presets because that is today's behaviour. The right default for phones is an open question for `backlog/feat-decide-phone-reactivity-role-by-simulation`; this setting lets that question be tested by changing configuration.

Decisions made here, with the tradeoff:

- **Ring Zulu is not a role.** It follows `alwaysOn`, because the storage rings it hints at are not implemented (`backlog/later/5-ring-zulu-storage-rings`). That ticket adds a storage-ring role when there is something to configure; a setting for a stub would only add surface.
- **Existing per-feature switches keep their own fields** (`network.enableRelay`, `hostUnclaimedStrands`). Their defaults move from the node class to `roles.alwaysOn`, and an explicit value still wins. This avoids two fields for one decision.
- **`strandCohortMember: false` is refused at `CadreNode` construction** with an error saying a node that holds no strand blocks is not supported yet. The field is in the type now so the API does not change again when the Optimystic dependency lands. `strand-node-that-holds-no-blocks` removes the refusal.

Roles are resolved once, in the `CadreNode` constructor. The node, `StrandInstanceManager` and `resolveRelayServer` all read the resolved `NodeRoles`, and nothing outside `node-roles.ts` compares `nodeClass` to a literal. `StrandInstanceManager`'s config and retained launch config carry `roles` in place of `nodeClass`, so a strand woken from hibernation launches with the same roles.

Mapping into Optimystic, one function per option so the control node and strand nodes share it:

- `fretProfile: roles.overlayTier`
- `arachnode: { enableRingZulu: roles.alwaysOn }`
- strand nodes with reactivity enabled: `cohortTopic: { enabled: true, host: { profile: roles.reactivity === 'forwarder' ? coreProfile() : edgeProfile() } }`, with `coreProfile`/`edgeProfile` from `@optimystic/db-core`. Passing `coreProfile()` explicitly for `forwarder` keeps today's behaviour by construction.
- published record: `encodeAlwaysOn(roles.alwaysOn)` in place of the class-based argument the prereq left.

## Edge cases & interactions

- **The published record follows `alwaysOn`, not the preset.** `nodeClass: 'device'` with `roles: { alwaysOn: true }` publishes always-on. Both the publish site and the "record still current" comparison must use the same `encodeAlwaysOn(roles.alwaysOn)`; if they disagree, the node republishes on every heartbeat forever. Verified by inspection.
- **Explicit switches still win.** `network.enableRelay: false` on an always-on node, or `hostUnclaimedStrands: true` on a phone, behave as today. Verified by inspecting the two default sites.
- **A subscriber-only node inside a strand's root group.** A collection's root (announcing) group is the storage group of its tail block, so a node with `strandCohortMember: true` and `reactivity: 'subscriber'` can be in it. Read Optimystic `docs/reactivity.md` § Origination point and the cohort-topic admission path, and record in the handoff whether that node declines registrations (so subscribers retry another member) and whether a commit it coordinates is announced at all. Either way, the watch service's tail poll (30 s core, 20 s edge) bounds a missed notification, so the expected cost is latency, not lost changes. State that in `docs/strands/app-schema.md` → "Known cost" (the item that points at the NOTE), replacing the `strand-reactivity.ts` NOTE. Do not refuse the combination: the simulation ticket needs it.
- **Reactivity disabled for a strand.** `reactivity` has no effect, and no warning is given.
- **Control node.** It never enables cohort-topic, so `reactivity` and `strandCohortMember` do not affect it. `overlayTier` and `alwaysOn` do.
- **Edge-node config** (`edge-node/config.ts`) keeps `nodeClass: 'device'` and sets no roles.
- **Unknown or ill-typed role values from a JavaScript embedder.** `resolveNodeRoles` throws on a value outside each role's set rather than falling back to the preset's value.
