# The claimed node restarts at once and keeps its owner's addresses

## Background

A node started with a claim secret (`cadre start` with `CADRE_CLAIM_SECRET`) runs under a placeholder party until an owner delivers a seed with a proof of the secret (`CadreNode.claimNode`, the `/sereus/seed/1.0.0` protocol). `cadre start` then stops that node and builds a new one under the claimed party (`restartIntoClaimedParty` in `start.ts`), with fresh node-local stores keyed on that party (`openNodeStores` in `start-node.ts`).

Two things slow the rejoin today (traced from code in the planning pass, not measured):

1. **The restart waits on dials.** The inbound seed handler (`SeedBootstrapService.handleSeedStream`) verifies and merges the seed, acks, then dials each of the seed's preferred peers (the minter and the party's always-on machines; `dialPreferredPeers`), and only then calls `onSeedApplied`, which `CadreNode` turns into `seed:applied`. `afterClaimSeedSettles` restarts on `seed:applied`. An unreachable preferred peer holds that dial for the per-peer budget (86 s at the default declared link), and those dials are wasted anyway: they are made from the placeholder node that is about to stop.
2. **The restarted node has no address for its owner.** `onSeedApplied` retains the seed's preferred peers as cold-start dial targets (`CadreNode.recordSeedBootstrapPeers`), but into the placeholder party's bootstrap-peer store. The claimed party's store, opened by `buildClaimedNode`, is empty (the NOTE in `start-node.ts` ~145 says so). So the restarted node can only wait for the owner to dial in.

## Design

### `seed:applied` means verified, merged and acknowledged

`handleSeedStream` calls `onSeedApplied` right after the ack is written and the stream closed, and runs `dialPreferredPeers` after it. The dials stay best-effort and counted as today. `seed:applied` therefore no longer waits for any connection; the preferred-peer dials follow it. The non-wire `applySeed` path is unchanged (it returns the dial counts to its caller and fires no event).

This is safe for the other `seed:applied` consumers: the reference web app only logs it, and `CadreNode.seedEventCallbacks` retains dial targets and refreshes the membership gate, both of which are better done before the dials than after.

### The dial targets a seed nominates, in one place

Add a pure exported helper in `seed-bootstrap.ts`, e.g. `seedDialTargets(seed, selfPeerId): SeedDialTarget[]` with `SeedDialTarget = { peerId: string; multiaddrs: string[] }`: the seed's preferred peers that have at least one address and are not `selfPeerId`. Three callers use it, so the filter exists once:

- `dialPreferredPeers` (it applies exactly this filter today, inline),
- `CadreNode.recordSeedBootstrapPeers` (same filter; `retainDialTarget` keeps its own self/empty guard for its other callers),
- the `seed:applied` event payload, below.

### `seed:applied` carries the targets

`'seed:applied': { partyId; peersAdded; dialTargets: SeedDialTarget[] }` (types.ts). `CadreNode.seedEventCallbacks` fills it from the helper with its control node's peer id. The event already has the seed in hand; this is the one field an embedder restarting into another party needs from it.

### cadre-cli carries the targets into the claimed party's store

- `afterClaimSeedSettles(node, claimedPartyId, onSettled)` hands `onSettled` the settling event's `dialTargets` (`seed:applied`), or `[]` (`seed:error`).
- `restartIntoClaimedParty(accepted, dialTargets)` passes them to `buildClaimedNode`.
- `buildClaimedNode(config, storage, claim, claimConfig, dialTargets = [])` records each into `stores.bootstrapPeerStore` before the node is constructed. `record` reflects the entry synchronously and its promise tracks durability only, so a persist failure is logged (`log(...)`) and not fatal, the same choice `CadreNode.retainDialTarget` makes. The start from `claim.json` passes nothing: by then the claimed party's file store already holds the targets the restart wrote.
- Replace the NOTE at `start-node.ts` ~145 with a sentence saying the claim seed's preferred peers are carried into the claimed party's store, so the restarted node dials its owner from its first reconcile pass (`dialColdStartBootstrap`, which runs while the control database has no siblings).

### What the restarted node does next (no change, confirm only)

Its eager start pass finds no `CadrePeer` rows and dials the carried targets. When the owner's rows reach it (backfill over that connection, or over the owner's own dial), the membership gate watch starts a reconcile pass, which publishes the node's own signed record (`publishFirstSelfRecord`). That path landed in `control-reconcile-woken-by-changes-reads-once`; this ticket changes nothing in it.

When the owner has no address in the seed (a phone with no relay reservation, the common case), `dialTargets` is empty and the node waits for the owner to dial in, as today. `claimant-redials-a-restarting-claimed-node` shortens that wait on the owner's side.

## Edge cases & interactions

- **The node stops while its preferred-peer dials are in flight.** The restart now begins right after `seed:applied`, so `dialPreferredPeers` is usually mid-dial when `node.stop()` runs. Each dial must reject (libp2p aborts pending dials on stop) and be counted and logged inside the per-peer `try`, never thrown out of `handleSeedStream`; `SeedBootstrapService.shutdown` nulls `libp2pNode`, and `dialPreferredPeers` reads it once at the top, so a loop that continues after shutdown just collects more rejections. Verify by inspection, and by the restart line in the node-claim scenario's log appearing without an 86 s gap. `node.stop()` must not wait for those dials to time out; if it does, cancel them through the service's shutdown instead.
- **The ack must reach the claimant before the node stops.** `replyAndClose` writes the frame and awaits `stream.close()` before `onSeedApplied` runs, so the ack is flushed before the restart begins. Verify by the node-claim scenario: step 3's `claimNode` and step 5's repeat claim resolve without error.
- **A seed whose work after the ack fails** (an exception after `acked = true` in `handleSeedStream`) emits `seed:error`; the restart then carries no targets and behaves as today.
- **A second claimant of the same party** whose refusal lands in the settle window: the existing NOTE on `afterClaimSeedSettles` still holds; the window is now shorter, not different in kind.
- **Self in the targets.** A seed minted after the claimed node joined (a re-claim by the same owner) can name the node itself; the helper drops it, so neither the dials nor the carried store ever target self.
- **Process killed between the ack and the restart.** `claim.json` is written but the claimed party's store is not; the next start from the record has no targets and waits for the owner, as today. Accepted; no test.
- **cadre-host and cadre-provider** run `cadre start` children, so they get this through cadre-cli with no change of their own. No other package restarts on `claim:accepted` (grep confirmed in planning: cadre-cli and two integration scenarios only).
