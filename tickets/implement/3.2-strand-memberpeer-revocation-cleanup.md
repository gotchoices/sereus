# `Strand.MemberPeer` cleanup after a member is removed

Split out of `bug-strand-member-delete-unauthorized`, whose reproduction turned up two things
about `MemberPeer` that are true independently of the revocation gate.

## What was measured

Against a real closed strand (`connectToStrand`, bootstrap mode):

- A member's `MemberPeer` rows **survive** the deletion of that member's `Member` row. Nothing
  cascades.
- A **self-signed** `delete from Strand.MemberPeer` **succeeds**.

That second result contradicts two places in the codebase that state the opposite:

- `schemas/strand.qsql` / `strand-schema.ts` — `MemberPeer.MemberExists` is documented as blocking
  deletes because it reads `new.MemberKey`, which is null on a delete.
- `registerMemberPeer`'s doc block in `packages/cadre-core/src/strand-membership-writer.ts`
  ("Out of scope: peer DELETION … a `MemberPeer` delete is currently rejected by the schema"),
  which also cites the `apply-strand-membership-schema` review.

Both are wrong for the same reason the parent bug existed: `MemberExists` is written as a bare
`check (...)`, which in Quereus carries the default `insert|update` operation mask and simply does
not run on DELETE (`../quereus/docs/sql-ddl.md` line 303, confirmed: "`check (expr)` is enforced on
INSERT and UPDATE by default; `check on {insert | update | delete}[,...]` restricts the
operations"). The `new.MemberKey is null` argument never gets a chance to fire.
`MemberPeer.Authorized` *is* declared `on insert, update, delete`, so deletes are genuinely
signature-checked against the member's own key — the table is safer than its comments claim, just
differently shaped.

## Why this needs work

Only the member itself can sign a `MemberPeer` delete, so an administrator removing a member has no
way to clear that member's peer bindings — and a member being removed against its will has no
reason to cooperate. The rows are orphans: they name a `MemberKey` with no `Member` row.

They are **inert today**. Nothing in the runtime reads `MemberPeer` for authorization —
`StrandMemberRegistry.isMember` resolves against `Strand.Member`, and
`packages/cadre-core/src/strand-addr-protocol.ts` (line 26) explicitly notes peer-record resolution
is out of its scope. So this is not an active access-control hole; it is a correctness and hygiene
gap that becomes one the moment a reader starts trusting `MemberPeer` on its own.

## Established facts from the prior run (do not re-derive)

- **The parent ticket landed.** `signStrandMemberAction(action, memberKey, privateKeyB64)` exists at
  `strand-membership-writer.ts:98` and signs `digest(['Strand.Member', action, memberKey],
  'sha256', 'bytes')`. `Member.Authorized` resolves its authorizer as
  `select 1 from committed.Manager A where A.MemberKey = context.ManagerKey and verify(...)`.
  **Reuse both idioms** — variadic tagged digest, `committed.Manager` authorizer.
- **`verify()` always returns a boolean.** `optimystic/packages/quereus-plugin-crypto/src/crypto.ts:450-480`
  wraps its whole body in `try { … } catch { return false }`. `exists (...)` never yields null
  either. So an all-null-context delete lands on `false`, not null — the same shape already pinned
  rejected for `Member` by `packages/cadre-core/test/strand-member-revocation.spec.ts:198`
  ("rejects an unsigned (all-null context) removal of a non-manager member").
- **Adding a subquery to `MemberPeer.Authorized` converts it from an IMMEDIATE check to a DEFERRED
  one** (Quereus auto-defers any CHECK containing a subquery). This is fine — `MemberExists` on the
  same table already defers, and every existing test only asserts `rejects.toThrow()`. But the
  comment at `packages/cadre-core/test/strand-membership-peer-rotation.spec.ts:125-128` says "the
  immediate `Authorized` check … fails" and **must be corrected** to say deferred.
- **The drift guard is strict.** `packages/quereus-plugin-sereus/test/strand-schema-drift.spec.ts`
  extracts the `declare schema Strand { … }` body from `schemas/strand.qsql` with a
  comment/string-aware scanner and compares it to `STRAND_SCHEMA` after normalizing **only**
  CRLF→LF, trailing horizontal whitespace, and leading/trailing blank lines. Interior whitespace,
  indentation (4 spaces inside the schema body) and comments are all compared verbatim — so the two
  copies must be character-identical.
- **RESOLVED — a `with context` clause may NOT omit a declared context param, even a nullable
  one.** `../quereus/packages/quereus/src/runtime/emit/dml-executor.ts:338-347` iterates
  `plan.contextAttributes` — built from ALL of the table's declared `mutationContext` vars, see
  `planner/building/delete.ts:125-140` (insert.ts / update.ts share the shape) — and throws
  `Missing mutation context value for '<name>'` for any declared var the statement's clause did
  not assign. (`runtime/emit/constraint-check.ts:106-113` silently skips missing ones via
  `if (valueExpr)`, so the dml-executor throw is the one that actually bites.) The throw only
  arises when the statement HAS a `with context` clause at all — with no clause,
  `contextAttributes` is empty and nothing is checked.

  Consequence: widening `MemberPeer`'s context tuple to three params forces **all three** raw
  call sites to pass all three:
  - `packages/cadre-core/src/strand-membership-writer.ts:654` (`registerMemberPeer`'s insert)
  - `packages/cadre-core/test/strand-membership-peer-rotation.spec.ts:133`
  - `packages/integration-tests/src/scenarios/strand-membership-closed-strand-e2e.integration.ts:313`

  Each becomes `with context Signature = ?, ManagerKey = null, ManagerSignature = null`. This is
  why the schema edit cannot be landed on its own — it breaks peer registration until the call
  sites move with it.
- **Order inside the `with context` clause is irrelevant** — values are looked up by NAME
  (`delete.ts:142-144` builds a name→expr map; `dml-executor.ts:340` reads it by `attr.name`).
- **Deferred-constraint context availability is documented, not assumed:**
  `../quereus/docs/sql-ddl.md:387` — "Context is captured for deferred constraints and evaluated
  at COMMIT time". So widening `Authorized` into a deferred check does not lose `context.*`.
- **The 4-argument tagged digest needs no new parity test.**
  `packages/cadre-core/test/digest-variadic-parity.spec.ts` case (d) already pins

- **Exports live at `packages/cadre-core/src/index.ts:105-131`** (one `export { … } from

## Design

### Schema — install this text in BOTH copies, character-identical

Replaces `schemas/strand.qsql:182-196` and `packages/quereus-plugin-sereus/src/strand-schema.ts:193-207`.
(4-space indent, matching the surrounding schema body.)

```sql
    -- A member-associated peer (node)
    --
    -- NOTE: a MemberPeer row can OUTLIVE the Member row it names. MemberExists runs on
    -- insert/update only, and nothing cascades a Member delete, so revoking a member leaves
    -- its peer bindings behind as orphans until a manager clears them (removeMemberPeer).
    -- Any consumer that treats a MemberPeer row as evidence of membership MUST join to
    -- Member rather than trusting the row alone.
    table MemberPeer (
        MemberKey text,
        PeerId text,
        primary key (MemberKey, PeerId),
        -- Mask is explicit: a bare check defaults to insert|update and silently never runs on
        -- DELETE. Stated rather than inherited — a delete removes no row image to validate.
        constraint MemberExists check on insert, update (exists (select 1 from Member M where M.Key = new.MemberKey)),
        constraint Authorized check on insert, update, delete (
            -- The member itself signs the binding, verified against the MemberKey the row
            -- names — so only that member registers (or removes) its own peers.
            verify(
                digest(coalesce(new.MemberKey, old.MemberKey) || '|' || coalesce(new.PeerId, old.PeerId)),
                context.Signature,
                coalesce(new.MemberKey, old.MemberKey),
                'ed25519'
            )

                -- or a manager clears ANOTHER member's binding — the cleanup path after a
                -- revocation, which the departing member has no reason to cooperate with.
                -- Gated to DELETE and bound to a remove-tagged digest over the exact row, so a
                -- captured registration signature can never be replayed as a removal. The
                -- authorizer is read from the PRE-transaction snapshot (committed.Manager) for
                -- the same reason Member.Authorized does: this check now defers to commit, by
                -- which point a manager seated in the SAME transaction would otherwise be able
                -- to authorize its own cleanup.
                or (new.MemberKey is null and exists (
                    select 1 from committed.Manager A
                        where A.MemberKey = context.ManagerKey
                            and verify(digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId), context.ManagerSignature, A.MemberKey, 'ed25519')
                ))
        ),
    ) with context (Signature text null, ManagerKey text null, ManagerSignature text null);
```

Deliberate properties:
- The manager branch is **not** gated on the member being gone. A manager may clear any member's
  peer binding, matching "any manager can remove any member".
- The removal digest tags domain **and** action (`'Strand.MemberPeer'`, `'remove'`), distinct from
  the untagged `MemberKey || '|' || PeerId` registration payload — that is what makes a register
  signature unusable as a remove signature.

### Writer — `packages/cadre-core/src/strand-membership-writer.ts`

Add next to `signStrandMemberAction`:

```ts
export function signStrandMemberPeerRemoval(memberKey: string, peerId: string, privateKeyB64: string): string {
  const hashBytes = digest(['Strand.MemberPeer', 'remove', memberKey, peerId], 'sha256', 'bytes') as Uint8Array;
  return sign(hashBytes, privateKeyB64, 'ed25519', 'bytes', 'base64url', 'base64url') as string;
}
```

Params as a discriminated union so each case carries exactly the fields it needs (the two cases
sign DIFFERENT payloads, so a single opaque keypair param — the `removeManager` shape — does not
apply here):

```ts
/** Self-signed removal: the owning member deletes its own peer binding. */
export interface RemoveOwnPeerParams { memberKeyPair: Ed25519KeyPair; peerId: string }
/** Manager-signed cleanup: a manager clears another member's peer binding. */
export interface RemoveMemberPeerByManagerParams { managerKeyPair: Ed25519KeyPair; memberKey: string; peerId: string }
export type RemoveMemberPeerParams = RemoveOwnPeerParams | RemoveMemberPeerByManagerParams;
```

`removeMemberPeer(db, params)` narrows on `'memberKeyPair' in params` and delegates to two small
private helpers (one per branch). Both issue
`delete from Strand.MemberPeer with context … where MemberKey = ? and PeerId = ?`.

**Delete-if-present, then verify.** Wrap both branches in the existing `memberPeerExists` scan:
skip quietly when the row is already absent (mirrors `registerMemberPeer`'s insert-if-absent,
keeps cleanup idempotent/restart-safe), and re-check after the delete, throwing if the row is
still there. The reason is specific, not blanket defensiveness: this `where` puts an equality on
**both** composite-PK columns, which is exactly the shape `memberPeerExists`' own doc block
(`strand-membership-writer.ts:682`) says the optimystic vtab module serves via a single-key seek
that can miss on a networked strand. A missed seek here deletes zero rows and returns success —
a silent no-op on the very cleanup path this ticket exists to provide. `memberPeerExists` scans
(partial-PK predicate), so it does not share the hazard. Cite backlog
`debt-composite-pk-point-lookup-unreliable-untracked` in the NOTE. This is an availability
failure, never a security one.

### Do not cascade automatically

A revocation that also had to clear an unbounded number of peer rows in the same transaction
couples two concerns and makes the revocation's failure modes harder to reason about. Peer cleanup
stays an explicit follow-up call by the revoking manager.

## What the replay test must actually assert

The TODO bullet "a register-peer signature cannot be replayed as a remove-peer signature" is
about the **manager branch only**, and a naive reading of it produces a test that fails.

On the **self** branch the registration and removal payloads are deliberately the SAME untagged
`MemberKey || '|' || PeerId`, so a member CAN present its own registration signature to delete
its own binding. That is intended and harmless — it is the same principal either way, and the
row is the member's own.

The branch that must not be replayable is the manager one. So the test shape is: a real manager
signs the **untagged registration payload** over another member's row and presents it as
`context.ManagerSignature` for a delete → rejected, because the manager branch verifies the
remove-tagged `digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId)` instead.
