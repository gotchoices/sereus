# `Strand.MemberPeer` cleanup after a member is removed

Split out of `bug-strand-member-delete-unauthorized`, whose reproduction turned up two things
about `MemberPeer` that are true independently of the revocation gate.

## What was measured

Against a real closed strand (`connectToStrand`, bootstrap mode):

- A member's `MemberPeer` rows **survive** the deletion of that member's `Member` row. Nothing
  cascades.
- A **self-signed** `delete from Strand.MemberPeer` **succeeds**.

That second result contradicts two places in the codebase that state the opposite:

- `schemas/strand.qsql` / `strand-schema.ts` — `MemberPeer.MemberExists` is documented as blocking
  deletes because it reads `new.MemberKey`, which is null on a delete.
- `registerMemberPeer`'s doc block in `packages/cadre-core/src/strand-membership-writer.ts`
  ("Out of scope: peer DELETION … a `MemberPeer` delete is currently rejected by the schema"),
  which also cites the `apply-strand-membership-schema` review.

Both are wrong for the same reason the parent bug existed: `MemberExists` is written as a bare
`check (...)`, which in Quereus carries the default `insert|update` operation mask and simply does
not run on DELETE (`../quereus/docs/sql-ddl.md` line 303). The `new.MemberKey is null` argument
never gets a chance to fire. `MemberPeer.Authorized` *is* declared `on insert, update, delete`, so
deletes are genuinely signature-checked against the member's own key — the table is safer than its
comments claim, just differently shaped.

## Why this needs work

Only the member itself can sign a `MemberPeer` delete, so an administrator removing a member has no
way to clear that member's peer bindings — and a member being removed against its will has no
reason to cooperate. The rows are orphans: they name a `MemberKey` with no `Member` row.

They are **inert today**. Nothing in the runtime reads `MemberPeer` for authorization —
`StrandMemberRegistry.isMember` resolves against `Strand.Member`, and
`packages/cadre-core/src/strand-addr-protocol.ts` explicitly notes peer-record resolution is out of
its scope. So this is not an active access-control hole; it is a correctness and hygiene gap that
becomes one the moment a reader starts trusting `MemberPeer` on its own.

## Design

- **Add a manager branch to `MemberPeer.Authorized`** so a manager can remove another member's peer
  bindings: alongside the existing self-signature branch, accept a `committed.Manager` row matching
  `context.ManagerKey` that signed a remove-tagged digest over `old.MemberKey || old.PeerId`. Reuse
  whichever tagged-payload signer `bug-strand-member-delete-unauthorized` lands, and whichever
  authorizer-resolution shape it settled on (`committed.*` or the documented fallback) — do not
  invent a third idiom.
- **Give `MemberExists` an explicit operation mask** (`check on insert, update`) so its intent is
  stated rather than inherited from a default. It should not fire on delete — a delete removes no
  row image to validate.
- **Add a `removeMemberPeer(db, { ... })` writer** covering both the self-signed and the
  manager-signed cases, exported from `packages/cadre-core/src/index.ts`, and replace the
  now-incorrect "Out of scope: peer DELETION" paragraph in `registerMemberPeer`'s doc.
- **Do not cascade automatically.** A revocation that also had to clear an unbounded number of peer
  rows in the same transaction couples two concerns and makes the revocation's failure modes harder
  to reason about. Keep peer cleanup an explicit follow-up call by the revoking manager.
- **Record the orphan-row hazard where a future reader will meet it.** Add a `NOTE:` comment on the
  `MemberPeer` table saying that rows can outlive their `Member` row, so any consumer that treats a
  `MemberPeer` row as evidence of membership must join to `Member` rather than trusting the row
  alone. That is the real durable risk here, and a comment at the site is the right home for it.
