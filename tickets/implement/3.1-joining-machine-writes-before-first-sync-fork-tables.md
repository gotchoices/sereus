# A joining machine can write before its first sync, forking every table it touches

Split out of `fix/cross-party-strand-messages-do-not-converge` (device run, 2026-09-16). The other defect from that report is `strand-app-table-names-collide-with-strand-tables`, which this ticket follows so the regression scenario can use the renamed chat schema.

## Observed (headless, direct connections, no relay)

Two `CadreNode`s, different parties. Host founds a closed strand, writes one member and message `h-pre`, publishes a bound invitation. Joiner redeems with `formStrand`, then `addStrand` with the returned member key. The chat schema was used with its member table renamed so the name collision above is out of the picture.

`addStrand` resolved `status: active` with **0 strand connections**. Then:

| joiner behaviour | joiner after 5-30 s | host after 5-30 s |
| --- | --- | --- |
| writes member `joiner` + message `j-1` immediately | members `[joiner]`, messages `[h-post, h-pre]` — **`j-1` gone**, host member never arrives | members `[host]`, messages `[h-post, h-pre]` — nothing from the joiner |
| waits until it reads `host` and `h-pre` (1.3 s), then writes the same rows | members `[host, joiner]`, messages `[h-post, h-pre, j-1]` | identical |

Both writes reported success in the first case, and immediately afterwards the joiner read its own rows back. The message was later replaced by the host's copy of the table; the member table stayed forked for the whole 30 s observation window and showed no sign of converging.

This is the device report's "party B wrote a message, the next read returned 0 messages": the joiner's locally created `Message` table was replaced by the phone's. The device's intermittent `Block default/Message is unavailable (cohort-unreachable)` was **not** reproduced headlessly over direct connections; it is plausibly the same fork read over the slower relay path, and the device re-run in the TODO list is what settles it.

**The committed-read experiment from the original ticket was run and rules out the read path:** a committed read (`readConcurrency: 'committed'`) returned the same rows as the live read at every sample from 5 s on (immediately after the write it returned no messages while the live read showed `j-1`), and neither served `j-1` once it was lost. The row was really gone, not hidden by the live read's network refresh. So this is independent of `fix/control-cohort-edge-carries-data-fails-cohort-unreachable`.

## Why it happens

With no strand peer connected, the joiner's cohort for every block is itself. Its first write to a table finds no collection locally, treats that as "does not exist", and creates a new one — exactly what a founder writing alone legitimately does. When the connection comes up, two independently created histories share one collection id; optimystic keeps one and drops the other's commits (`Message`), or never reconciles them (`Member`). Optimystic cannot tell a founder from a joiner here; sereus can, because the launch knows whether it is founding (`StrandConfig.founder`).

## What to build

**Invariant: a machine that has never held this strand's `Strand.Header` row must not commit to it.** A founder writes the Header in its bootstrap; every other machine can only get it from a peer, so "no local Header" means "never synced".

Recommended shape (implementer may refine, and should record the choice in `docs/strands.md`):

- For a non-founder launch, `buildStrandRuntime` does not publish the database to the app (`instance.database` / `active`) until `Strand.Header` is readable. The strand node, reconciler and backfill keep running meanwhile so catch-up can happen. A distinct status (e.g. `'syncing'`) is preferable to overloading `'starting'`, so an app can show "waiting for the other member".
- `addStrand` resolves only once the strand is writable, with a bounded wait; on timeout it rejects with a legible, retryable error naming the strand ("no member of this strand has been reachable yet") and leaves the runtime launched so a later call or event can complete it. Decide whether a launch-ready event/promise is also exposed for apps that do not want to block.
- A machine that already holds the Header (a restart, a hibernation resume, a founder) is not gated — offline-first writes on a machine that has synced before must keep working (`complete/offline-node-cannot-serve-its-own-data`).
- Reference apps: `joinClosedChatStrand` and `useChat` must not write until the strand is writable (with the above, awaiting `addStrand` is enough; check the NS and web equivalents too).

**Known residual, say so in the docs rather than solve here:** a Header only proves one past sync. A machine that synced the Header, lost its connection, and then writes to a table whose collection it has never fetched (e.g. the first ever message, when no message has been written by anyone) can still create a divergent copy. Whether the founder should create every app table's collection eagerly at founding (so peer-join backfill ships them all) is a design question worth raising in the handoff, not something to build under this ticket without measuring the founding cost. The underlying "two histories silently lose committed rows" behaviour is upstream (same class as `blocked/forked-control-collection-sync-livelocks`); report the strand instance to optimystic, whose `fix/1-a-second-party-cannot-read-the-messages-it-just-wrote` is waiting on this diagnosis.

## Regression scenario

Base it on `strand-formation-cross-party-seed.integration.ts` test 2: host founds a closed strand with the chat schema and writes a participant and message; joiner redeems via `formStrand`, calls `addStrand`, and **writes immediately after it resolves** (the device shape). Assert on both machines, by exact id: both participants and every message from both sides, stable across a later write from each side. Before the fix this scenario loses the joiner's message; that is the check that the test has teeth. Add a second case where the host is stopped before the joiner launches: `addStrand` must reject within its budget, and the joiner's store must hold no app collection.
