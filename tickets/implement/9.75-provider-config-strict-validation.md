# cadre-provider: strict config validation

## Problem

`loadConfig` (`packages/cadre-provider/src/config/loader.ts`, 162 lines) deep-merges defaults ← config file ← environment ← programmatic overrides, casting the file to `PartialProviderConfig` without looking at it, then checks only the auth block (`validateAuthConfig`) and push completeness (`validatePushConfig`). Consequences seen by reading the code (`repro: static` for each):

- A misspelled key anywhere (`server.prot`, `storage.pth`) is ignored and the default applies.
- **Cross-package:** `resolveTenantPush` (`service/container-service.ts`) hands a tenant's push object to `buildNodeEnv` (`service/container-env.ts`), which writes it verbatim as `CADRE_PUSH=${JSON.stringify(request.push)}`. cadre-cli now rejects unknown keys inside `push`, so one stray key in the provider's `push` block makes every affected tenant node fail at boot, at provision time, long after the provider started cleanly.
- `server: ` with no children (YAML `null`) overwrites the default block with `null` in `deepMerge`, and the server crashes reading `config.server.port`.
- `storage.type: file` with no `path` silently runs the in-memory store (`createStore`, `service/store.ts:231`): every tenant record is lost on restart.
- `docker.defaultResources.memoryLimit: 512MB` does not match `parseMemoryLimit`'s pattern (`docker-orchestrator.ts:457`), which returns `undefined`: tenant containers run with no memory limit.
- Environment values are cast, not checked: `PROVIDER_AUTH_MODE=apikey` becomes an unknown mode (every request then gets 401, with no start-up error); `PROVIDER_PORT=abc` becomes `NaN`.
- Environment variables are applied only in groups: `PROVIDER_ALLOW_INSECURE_NO_AUTH`, `PROVIDER_JWKS_URI`, `PROVIDER_ISSUER`, `PROVIDER_AUDIENCE` are ignored unless `PROVIDER_AUTH_MODE` is also set; `PROVIDER_DOCKER_NETWORK` unless socket or image is set; `STRIPE_*` unless `PROVIDER_BILLING_ENABLED` is set. `validateAuthConfig`'s own error message tells the operator to set `PROVIDER_ALLOW_INSECURE_NO_AUTH=true` — which does nothing on its own when the file says `auth.mode: none`.

Maintainer decision (2026-09-28): the provider's config is checked with cadre-cli's strictness — an unknown key or ill-typed value fails start, naming the key and its source.

## Design

Same pipeline as cadre-cli, on the shared `@serfab/config-check` package that `config-check-shared-package` extracts:

```
loadConfigFile(path)            parse only → unknown             (YAML/JSON; parse errors name the file)
applyEnvironmentOverrides(raw)  → { tree, provenance }           (package's applyEnvOverrides + PROVIDER_ENV)
validateProviderConfig(tree, provenance, path) → ProviderConfigFile   (package's validateTree + field tables)
deepMerge(DEFAULT_CONFIG, validated) ← overrides → validateAuthConfig, validatePushConfig
```

Because what gets merged is the validator's **output** (built only from accepted keys, with `null` blocks dropped), nothing the validator did not accept can reach `DEFAULT_CONFIG`'s merge, the server, or `CADRE_PUSH`.

### Types (`config/types.ts`)

Move `DeepPartial<T>` out of `loader.ts` into `types.ts`; add `export type ProviderConfigFile = DeepPartial<ProviderConfig>` — what a file plus environment may contain (every key optional; defaults fill the rest). `PartialProviderConfig` stays as the type of programmatic `overrides` (public API). Export `ProviderConfigFile` from `src/index.ts`.

### Environment (`config/env.ts`, new)

One table, each variable written on its own (removes the grouping above):

| Variable | Path | Parser |
|---|---|---|
| `PROVIDER_HOST` | `server.host` | string |
| `PROVIDER_PORT` | `server.port` | number |
| `PROVIDER_BASE_PATH` | `server.basePath` | string |
| `PROVIDER_AUTH_MODE` | `auth.mode` | string |
| `PROVIDER_ALLOW_INSECURE_NO_AUTH` | `auth.allowInsecureNoAuth` | boolean |
| `PROVIDER_JWKS_URI` | `auth.jwksUri` | string |
| `PROVIDER_ISSUER` | `auth.issuer` | string |
| `PROVIDER_AUDIENCE` | `auth.audience` | string |
| `PROVIDER_DOCKER_SOCKET` | `docker.socketPath` | string |
| `PROVIDER_DOCKER_IMAGE` | `docker.image` | string |
| `PROVIDER_DOCKER_NETWORK` | `docker.network` | string |
| `PROVIDER_BILLING_ENABLED` | `billing.enabled` | boolean |
| `STRIPE_SECRET_KEY` | `billing.stripeSecretKey` | string |
| `STRIPE_WEBHOOK_SECRET` | `billing.stripeWebhookSecret` | string |
| `PROVIDER_STORAGE_TYPE` | `storage.type` | string |
| `PROVIDER_STORAGE_PATH` | `storage.path` | string |
| `PROVIDER_LOG_LEVEL` | `logging.level` | string |

Parsers are the package's (`boolean` accepts `true`/`false`/`1`/`0`, anything else throws naming the variable — stricter than today's "anything but `true` is false"; `number` rejects non-numeric text, so `PROVIDER_PORT=3000abc` fails where `parseInt` read 3000). Empty values count as unset (`specifiedEnv`), as today. Values are type-checked by the validator, not here, so `PROVIDER_AUTH_MODE=apikey` is reported as `Environment variable PROVIDER_AUTH_MODE: auth.mode must be one of 'none', 'api-key', 'oauth', got "apikey"`. The debug log of applied variables redacts `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`.

`loadEnvConfig` is replaced by `applyEnvironmentOverrides(raw: unknown, env = process.env): OverrideResult`; update `config/index.ts` and `src/index.ts` exports (no backwards compatibility needed; nothing outside the package imports `loadEnvConfig` — `grep -rn loadEnvConfig packages --include=*.ts` outside `cadre-provider/src` and `dist` finds nothing).

**No unknown-variable check.** cadre-cli rejects unknown `CADRE_*` names because it owns that prefix. `PROVIDER_` is generic enough that unrelated software in the same environment may use it, and `STRIPE_*` certainly is shared; rejecting unknown names there would fail starts for reasons outside this service. Say so in a one-line comment on the table.

### Field tables (`config/schema.ts`, new)

`FieldTable`s typed against `ProviderConfigFile`'s blocks, so a key added to a config interface without a checker fails to compile. No block is `required` (defaults supply every required key). Checkers:

- `server`: `host` non-empty string; `port` whole number 0–65535 (`numberWhere`; 0 = pick a free port); `basePath` string; `cors`: `origin` — a local checker accepting a string, a list of strings, or a boolean, else `server.cors.origin must be a string, a list of strings, or true/false, got …`; `credentials` boolean.
- `auth`: `mode` `oneOf` the three modes; `allowInsecureNoAuth` boolean; `apiKeyHashes` list of non-empty strings; `jwksUri`, `issuer`, `audience` non-empty strings.
- `docker`: `socketPath`, `network`, `image` non-empty strings; `pullPolicy` `oneOf`; `defaultResources`: `memoryLimit` and `cpuLimit` checked by the **same parse functions the orchestrator uses** (move `parseMemoryLimit` / `parseCpuLimit` out of `DockerOrchestrator` into a small exported module, e.g. `service/resource-limits.ts`, used by both — one definition of what a limit may look like); a value they cannot read is a problem (`docker.defaultResources.memoryLimit must be a size like 512M or 2G, got "512MB"`); `cpuLimit` stays a string in the type, and an unquoted YAML number fails with a message that says to quote it; `storageQuotaBytes` whole number ≥ 0; `portRange`: `start`, `end` port numbers.
- `billing`: `enabled` boolean; `stripeSecretKey`, `stripeWebhookSecret` `secretString`; `defaultPlanId` non-empty string; `usageCollectionIntervalSec` number > 0.
- `storage`: `refine(objectOf(...))` — `type` `oneOf('memory','file')`, `path` non-empty string; cross-field: `type: 'file'` with no `path` → `storage.path is required when storage.type is 'file' (or set PROVIDER_STORAGE_PATH)` (via `ctx.missing` with `suppliersOf` from the env table, the way cadre-cli's storage rule does).
- `logging`: `level` `oneOf`.
- `push`: `default` → the credentials table; `tenants` → `recordOf(credentials)`. Credentials tables typed against the provider's own mirror types in `types.ts` (`FcmCredentials`, `ApnsCredentials`, `PushCredentials`), same checkers as cadre-cli's push tables (strings, `secretString` for `privateKey`, boolean `production`, `cooldownMs`/`debounceMs` number ≥ 0). Completeness (a present `fcm` block has all its fields) stays with the existing `validatePushConfig` after the merge — same split as cadre-cli, and it also covers push supplied through `overrides`.

`validateProviderConfig(tree, provenance, configPath)` wraps the package's `validateTree` with `suppliersOf` = reverse lookup in the env table, and `concealUnder: ['push', 'billing']` (below). With no config file there is nothing to attribute to a file: pass the literal label `(no config file)` — every key in such a tree was written by a variable, so the label is never printed in practice.

### Additions to `@serfab/config-check`

- `recordOf<T>(value: Checker<T>): Checker<Record<string, T>>` — a mapping whose keys are caller-chosen (tenant ids), each value checked at `<keyPath>.<key>`; `nullIsAbsent` like `objectOf`; an empty key (`""`) is a problem. A `null` **value** is not absent: `tenants: { acme: }` is reported (`push.tenants.acme must be a mapping of keys, got null`) because treating it as absent would silently give that tenant the default credentials.
- **Hiding values under secret subtrees.** `describeValue`'s `NOTE:` says: if push blocks are ever hand-written rather than orchestrator-generated, describe every value under `push` by kind only — a private key pasted where a mapping belongs (`fcm: "-----BEGIN PRIVATE KEY…"`) is otherwise echoed in the error. The provider's `push` block **is** hand-written, so that condition has tripped here. Add `concealUnder?: readonly string[]` to `ValidateOptions`; `ValidationContext` gets a `describe(keyPath, value)` method that returns the kind only for a key path equal to or under a listed prefix and `describeValue(value)` otherwise; every checker in the package calls `ctx.describe(keyPath, value)` instead of `describeValue(value)`. cadre-cli passes nothing, so its messages are unchanged; update the `NOTE:` to say the option exists and cadre-cli has not opted in because its push block is orchestrator-written.

### Loader (`config/loader.ts`)

- `loadConfigFile(filePath): unknown` — parse only; YAML and JSON parse errors are rethrown as `Config <resolved path>: <parser message>` (`{ cause }` kept). Missing file and unsupported extension keep their current errors.
- `loadConfig(options)` — the pipeline above. Add `env?: Readonly<Record<string, string | undefined>>` to `LoadConfigOptions` (default `process.env`) so tests stop mutating `process.env`.
- Keep the redacted debug dump.

## Edge cases & interactions

- **Empty file / root not a mapping** — empty mapping / one problem naming the file. By inspection (package behaviour, pinned in cadre-cli).
- **`server:` with no children** — absent, defaults apply (no crash). Inspection: `objectOf`'s `nullIsAbsent` and merging the validator's output.
- **Attribution** — a problem under a path the environment wrote names the variable; a sibling key in the same block from the file names the file (`PROVIDER_PORT` set and `server.prot` in the file → `server.prot` attributed to the file). Test (see below).
- **Env-only operation, no file** — every value from variables; nothing attributed to a file. Existing `auth-closed-default.test.ts` covers the no-file path once moved to `options.env`.
- **Programmatic `overrides`** — typed, not validated (same as today); `validateAuthConfig` / `validatePushConfig` still run after them. By inspection.
- **Secrets** — `privateKey`, Stripe keys never appear in an error: `secretString` for the leaves, `concealUnder` for everything else under `push` and `billing`. One assertion in the push test (below).
- **Tenant id keys** — arbitrary strings (ids may contain `-`, digits); a key containing `.` makes the reported path ambiguous but is harmless. Empty key rejected.
- **`tenants.<id>: null`** — rejected, not treated as "use default" (see `recordOf`).
- **Stricter environment parsing** — `PROVIDER_BILLING_ENABLED=yes`, `PROVIDER_PORT=3000abc` now fail start. Intended; note in the README.
- **Existing deployments** — a config with a key the provider never read now refuses to start. Intended by the maintainer decision; the error names the key and suggests the nearest accepted one.
- **Concurrent provisioning** — none: validation runs once at start, before the server listens.
- **cadre-host** depends on cadre-provider but does not call `loadConfig` (`grep -rn "loadConfig" packages/cadre-host/src` finds none) — no change there beyond its build.

## Tests (provider, one new spec file `src/config/__tests__/config-validation.test.ts`)

Each pins one behaviour; per-field checkers get no tests (the field tables are compile-time checked).

- A file with `server: { prot: 3000 }` → `loadConfig` throws; message contains `Config <path>: unknown key server.prot (did you mean 'port'?)`.
- A file with `push.tenants.acme.fcm.projectID` (alongside valid `projectId`/`clientEmail`/`privateKey`) → throws naming `push.tenants.acme.fcm.projectID` — the reproduction of the cross-package defect; the same message does not contain the `privateKey` value.
- `env: { PROVIDER_AUTH_MODE: 'apikey' }` → throws with `Environment variable PROVIDER_AUTH_MODE:`.
- File `auth: { mode: none }` + `env: { PROVIDER_ALLOW_INSECURE_NO_AUTH: 'true' }` → loads (reproduction of the grouping bug; fails on today's code).
- `example.provider.yaml` loads with an empty `env`.

Existing `auth-closed-default.test.ts` and `push-validate.test.ts` keep passing (switch to `options.env` where they set `process.env`).
