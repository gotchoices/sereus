Third of the `strand-offline-mode` chain. It relies on `offlineControllerOf(db)` from `strand-offline-composition` and the per-strand queue state from `strand-offline-cadre-core`.

## Why membership writes need a guard

The `Strand` tables are tagged `"optimystic.offline" = 'network'` (`strand-offline-composition`), so every membership write is network-acknowledged. Upstream queues a network-acknowledged commit made while transactions are queued behind them, and `commit` waits for it to settle, up to `networkCommitTimeoutMs` (5 minutes by default). The commit runs inside `db.exec`, which holds Quereus's execution lock, so for that whole wait every other statement on the strand database, the app's included, waits too. Offline, with app transactions queued, a reconciler pass, an `issueInvite` or a `revokeMember` would freeze the app for up to five minutes and then fail with `OfflineCommitTimeoutError`.

## Decisions

**Refuse before taking the lock.** In `execStrandTransaction`, before `db.exec`: when `offlineControllerOf(db)` reports queued transactions, throw `StrandOfflineQueueBusyError` (new, exported, carrying the queued `transactionIds`) and write nothing. Count every transaction a network-acknowledged commit would wait behind, which is `entries()` (it lists the deferred-after-restart ones too), not only those waiting for the cohort. This applies to every writer, including a call that would join a transaction the app opened. A writer joining an app transaction makes that transaction network-acknowledged, so the app's own commit would then take the same wait. One guard, one rule: "a membership write is refused while this strand's queue holds transactions; await `strand.database.offline.whenDrained()` and retry".

- The membership reconciler treats it like `StrandTransactionBusyError`: the pass retries on its existing doubling ladder. Extend `isTransactionBusy` (or add a sibling) so the cause-chain check finds either error.
- The unpublish binding cleanup (`removeMemberPeer` from `strand-instance-manager.ts`) handles it as it handles the busy error today. Read that call site and match it.
- Calls an app makes (`issueInvite`, `addMemberByManager`, `revokeMember`, `leaveStrand`, …) get the error. Its message says what to await.

The check is racy by nature: an app commit can be queued between the check and the membership `exec`, and that membership commit then waits behind it. That is upstream's bounded wait, the rare case rather than the normal one. Leave a `NOTE:` tripwire at the check: if a frozen strand database is ever traced to a membership write that slipped past it, hold the app's writes during membership commits instead.

**`OfflineCommitTimeoutError` reaching a background writer** (that race): the reconciler retries the pass like any failed pass. Its writes are insert-if-absent and read state first, so a membership commit that landed after all (`sent: true`) is found on the next pass. Confirm by reading how the reconciler classifies an unknown error. If it would not retry, make it retry.

**Leaving a strand with unsent transactions.** `forgetJoinedStrand(strandId, options?: { discardQueued?: boolean })` and `unpublishStrand` (same option) check the strand's queue before they change anything:

- When the strand is live, ask its controller (`entries()`). When it is hibernating, use the last `strand:queue-state` depth the manager saw for it; `strand-offline-cadre-core` already receives every one, so keep the latest per strand. A strand this process never ran is not checked. Leave a `NOTE:`: its journal may hold transactions, and they would come back if the strand is ever attached again.
- Non-empty and no `discardQueued`: throw `StrandQueueNotEmptyError` (new, exported, with the `transactionIds`). Nothing is left or removed. The app shows the user the unsent changes and asks.
- `discardQueued: true`: wake a hibernating strand first (the existing wake path), then `discard` each entry that can be discarded (never sent). Upstream refuses to discard an entry that was sent or is being sent (`EntryNotDiscardableError`: it may have landed). Those stay in the journal. The leave goes on with one `console.warn` naming them, since a cohort that never returns would otherwise block the leave forever. They settle if this machine ever attaches the strand again.
- Rejected: deleting the journal records silently. The app was told each of those transactions was acknowledged, so dropping them must be the user's explicit choice.

Self-revocation does not consult the queue. The machine has been removed from the strand, so anything it queued would be refused, and the strand stops. Nothing to build; one line in the doc.

## Edge cases & interactions

- **The founder bootstrap** goes through the same writers. On a fresh founding the queue is empty. `ensureFounderBootstrap` on a live database with a queue (a contrived joiner-then-founder case) is refused by name like any membership write. Inspection.
- **A `Strand` write inside an app transaction:** refused while queued transactions exist, by the rule above. Document it in the "Offline mode" section.
- **Strand moved between cadres:** the strand's storage scope is its strand id, which a move does not change (`edge-node/dissolve.ts` NOTE: strand databases stay), so the journal moves with nothing. The strand relaunches under the new party and `hydrate` restores the queue. Inspection of `edge-node/strand-move.ts`. No guard.
- **`stopStrand`** (no leave) needs no guard: the journal persists and the next start restores it.
- **Discard while the drain is sending the head:** upstream refuses that entry (`because: 'submitting'` or in doubt). The warn path covers it. Inspection.

## Tests

None. Each guard is a short check on state that upstream computes, and the branches are visible by reading. A test would need a cohort held closed through `composeStrand`, which exposes no seam for it, and adding one only to test a two-line check costs more than it buys.
