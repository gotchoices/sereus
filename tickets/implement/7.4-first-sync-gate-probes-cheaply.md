# The first-sync gate probes cheaply and wakes on arrival

## Background

A joining machine's strand database is held back from the app (`StrandFirstSyncGate`, `strand-first-sync-gate.ts`) until the machine holds the strand's `Strand.Header` row and a read of every `App` table has settled. Today each check ("probe") runs `select count(1) from Strand.Header`, then `select count(1)` on each `App` table one after another, and the gate re-probes every 500 ms (`DEFAULT_STRAND_FIRST_SYNC_POLL_MS`).

Measured and traced in the plan pass:

- `message-cost-accounting` baseline, joiner B's `addStrand`: 26 app streams, 25 of them `sync` B→A, one block at a time; `appTablesReadable` made 12 reads, `strandHeaderHeld` 6.
- `count(1)` is a full scan, so a probe reads every leaf of the table. Each block B does not hold costs two identical `sync` round trips (gotchoices/Optimystic#39, `blocked/optimystic-attach-fetches-each-block-twice`), and the `for … await` makes them strictly sequential. A probe that fails on one table restarts from the first table on the next tick. On the phones in GitHub #44 the gate took 155–390 s.
- The founder's join backfill (`peer-join-backfill.ts`) pushes its whole store to B starting about 1 s after B identifies, so the gate fetches block by block what is about to arrive in bulk.
- `addStrand` / `whenStrandWritable` wait on an event, but that event fires only on a gate tick.

## Design

### 1. One-row probes

Every probe is `select 1 from <Schema>."<Table>" limit 1`, the read `openTables` in `quereus-plugin-sereus/src/empty-collections.ts` already uses to open a collection. Opening the table's vtab fetches its collection header (the thing a premature write would otherwise invent), and one row walks the root to its first leaf.

- **`Strand.Header`**: held means a row came back. No row, or a throw, means not held (today's `count > 0` rule).
- **An `App` table**: readable means the read completed without throwing. No row is a success: the founder commits an empty collection for every declared table (`strand-founder-commits-every-table-collection`), so an empty table is a settled read. Keep today's error handling: catch, log under `sereus:cadre:strand-first-sync`, report false.

### 2. Concurrent probes, off the execution mutex

Probe the Header first and alone (a joiner with no peer must not pay one failing network read per table), then every remaining table at once with `Promise.all`, each probe catching its own error so all settle.

**`Promise.all` alone does not overlap the reads.** Quereus serializes every `db.eval` behind its execution mutex by default, and a scan holds the mutex across its network awaits, so plain concurrent `eval`s would still run one after another. Each table probe therefore passes `{ readConcurrency: 'committed' }` as `db.eval`'s third argument (`StatementOptions`, `../quereus/packages/quereus/src/common/types.ts` ~63-95). Traced in the plan pass:

- Eligibility (`Database._isConcurrentReadEligible`, `core/database.ts` ~740-800): autocommit, a relational statement, no side effects, no table-valued function, and every table's module declaring `readCommittedSnapshot` (the Optimystic module does, `optimystic-module.ts` ~4068). `select 1 from App."T" limit 1` qualifies. An ineligible statement silently falls back to the serialized path, so this can never make a probe wrong, only sequential.
- A committed read of a table not yet initialized runs `initializeForCommittedRead`, which takes the ordinary full initialization when no write is in flight (`optimystic-module.ts` ~708-731). Nothing writes on the gated database (the app does not have it, and the membership reconciler reads `instance.database`, which is unset), so each probe fully initializes its table: the collection header is fetched from the network, and the plugin arms that table's change bridge, exactly as a serialized read would.
- A committed read does not call `collection.update()` before reading (`runQuery` ~1455-1465). That does not matter for the gate: it asks whether the collection is held, not for the newest rows. A missing leaf still throws (`Missing block` / block unavailable), which is "not yet".

Concurrent probes to one peer each open a stream beyond the first prepared one (+1 round trip each, `prepared-streams.ts`); that is still fewer sequential round trips than today. Say so in the code comment.

### 3. Remember what is held

The gate keeps, for its own lifetime, whether the Header is held and the set of `App` tables whose probe succeeded. A later probe skips them. The memory lives on the gate, and the instance manager's first probe goes through the same gate, so what the first probe established is not re-read on the second:

- Add `StrandFirstSyncGate.probeOnce(): Promise<boolean>` (the current private `probeHeld`, made to use and update the gate's memory, with its outer try/catch kept). `buildStrandDatabase` calls `config.founder === true || await gate.probeOnce()` in place of `strandFirstSyncComplete(...)`.
- Replace the exported free functions with one probe that takes the memory: `strandFirstSyncComplete(db, label, held: FirstSyncProgress)` where `FirstSyncProgress` is `{ header: boolean; tables: Set<string> }`, mutated in place. Drop `strandHeaderHeld` / `appTablesReadable` from `index.ts` unless something outside the gate needs them (grep says only the spec does); keep small private helpers for one probe each. No backwards compatibility needed.
- The memory is per gate, and a gate is per database build: `releaseRuntime` drops it, so a hibernation wake or a deferred-join retry starts fresh over the kept store. Over a store that holds everything, every probe answers locally on the first try.

Write the table list so that adding the `Strand` tables (item 5) is a change to which names are probed, not to the loop: the probe takes qualified names (`'App.Message'`), and the `App` names come from `appTableNames`.

### 4. Wake on arrival, with a backstop timer

**The wake source is the node's storage-wide change feed, not `StrandDatabase.watchTables`.** The plan named the prereq's strand wrapper. It cannot do this job: the Optimystic plugin arms a table's replicated-change bridge only at the end of a SUCCESSFUL full initialization (`ensureChangeSubscription`, called at `optimystic-module.ts` ~979 after `isInitialized = true`; `docs/architecture.md` → "Table change subscriptions", "What it does not hear"). The tables the gate is still waiting on are exactly the ones whose initialization failed because their collection could not be fetched, so a per-table watch would not hear the backfill push that delivers them.

Instead subscribe to `node.storageRepo.onAnyCollectionChange(listener)` on the strand's own libp2p node. It is part of Optimystic's typed host surface (`OptimysticNodeAttachments.storageRepo: StorageRepo`, `../optimystic/packages/db-p2p/src/optimystic-node.ts` ~31), and `StorageRepo.saveReplicatedBlock` emits it for every block a push lands (`storage-repo.ts` ~1424-1432), as well as for commits this node applies. Each strand has its own libp2p node and store, so the feed hears only this strand.

- Extend `Libp2pNodeWithRepo` (`types.ts` ~33) with an optional structural `storageRepo?: { onAnyCollectionChange(listener: (event: unknown) => void): () => void }`, optional for the same reason `keyNetwork` is (the base factory assigns it, the upstream `Libp2p` type does not declare it). Use Optimystic's `CollectionChangeListener` type if `@optimystic/db-core` exports it to cadre-core already; otherwise the structural shape.
- The gate takes a dep `subscribeStorageChanges?: (onChange: () => void) => () => void`, supplied by `buildStrandDatabase` from `node.storageRepo?.onAnyCollectionChange`. Absent (test doubles, a node without it): log once and rely on the backstop.
- Schedule probes with the prereq's `scheduleRuns(onChange, { label, backstopMs, scheduler })` (`table-change-watch.ts`): single-flight, a change during a run produces exactly one follow-up, and the backstop runs a probe that long after the last one settled. The storage listener runs synchronously inside the storage commit path, so it only calls `watch.trigger(TABLE_CHANGE_COALESCE_MS)`; one push lands blocks one by one, and the 50 ms window plus the single follow-up fold a burst into at most two probes.
- `start()` subscribes the feed and creates the schedule. It does not probe at once: `scheduleRuns` arms the backstop at construction, so the first gated probe runs on the first arrival or one backstop later, as today's "the caller already probed once".
- `stop()` and `open()` unsubscribe the feed and dispose the schedule. A probe in flight completes and its answer is ignored (keep the existing re-check after the await). `onHeaderHeld` still fires exactly once, from the gate's own probe.
- **Backstop period: 2 000 ms** (`DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS`). It covers a probe that failed for a reason no storage event follows: a consult that missed its deadline while the founder held the block, or a push that never comes. Why 2 s: arrivals now wake the gate, so the timer is no longer the main path; at the supported 3 s link round trip one consult takes about 6 s (two round trips, on `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS`'s 1.8.0 measurements), so a 2 s idle gap after a failed probe adds at most a third of one probe round; and it is under 1% of the 300 s `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS`. Shorter brings back the polling cost the ticket removes; much longer (5 s) delays the case with no storage event by most of a probe round for nothing. Record this reasoning on the constant.
- Rename the config field `StrandFirstSyncConfig.pollIntervalMs` → `backstopMs` and `DEFAULT_STRAND_FIRST_SYNC_POLL_MS` → `DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS`; update `index.ts`, the `types.ts` docs (~936-943, and the `StartStrandConfig.firstSync` doc in `strand-instance-manager.ts` ~276), the integration harness's `strandFirstSync` option type (`node-fixtures.ts` ~162) and both cadre-core specs that set it.
- Update the class `NOTE:` about relay `hop connect denied` lines: probes now run on arrivals plus a 2 s backstop and skip held tables, so the count it describes falls; keep the revisit condition.

## Edge cases & interactions

- **An empty `App` table** (founder's empty collection): the one-row read returns nothing and succeeds; the table counts as readable. Verified by the spec's fake returning no row for a readable table (see Tests).
- **An empty `Strand.Header` read** (no row, no throw): not held. Same spec.
- **A table added by a later schema version** (no collection anywhere): its probe fails forever, as today; that is `backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`'s subject. No special case. By inspection.
- **The committed-read route falling back to serialized** (any eligibility check failing): probes are then sequential, never wrong. By inspection; say it in the comment.
- **A probe that self-wakes.** The probe's own network reads can land blocks in storage (a read-repair, a fetched block), which fires the storage feed and schedules one follow-up probe. Each such wake means a block newly arrived, so the follow-ups stop when nothing new lands. Park as a `NOTE:` tripwire at the subscription: if gated launches ever show probe storms in the logs, ignore events while a probe is in flight.
- **An arrival between the instance manager's first probe and `start()`**: missed, and caught by the first backstop (2 s). By inspection; note it in `start()`'s doc.
- **Stop / force-open during a probe**: the existing re-check after the await covers it; the schedule is disposed, so no follow-up runs. Kept by the existing open/stop spec.
- **A throw from outside the probe's own read guards** (`getDatabase()`, the `App` schema lookup): still reported as "not yet" by `probeOnce`'s outer catch, so the schedule always re-arms. `scheduleRuns` also logs a thrown `onChange`, but keep the catch so the gate's log line says what happened.
- **Timeout** (`StrandAwaitingFirstSyncError`): unchanged; `whenWritable` is untouched.
- **Hibernation wake / deferred-join retry**: a new gate per database build, fresh memory, probes answer locally over a kept store. By inspection.
- **A founder request against a gated instance** (`foundStrand`): `open()` disposes the schedule and the feed subscription. Existing spec.
- **Storage feed absent** (the cadre-core spec's node double has no `storageRepo`): backstop only, one log line. The manager-level specs exercise this path.
