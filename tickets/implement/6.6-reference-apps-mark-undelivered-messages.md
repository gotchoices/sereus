# The reference apps mark a message that is not yet delivered

Follow-up of `strand-commit-durability-reaches-the-app`, which gives cadre-core `StrandDatabase.commitDurability(transactionId)` (a `StrandCommitDurability` with `heldElsewhere` and `followed`) and the `CadreNode` events `strand:commit-durability` and `strand:commit-held`. Read that ticket's docs section in `docs/strands.md` first; this ticket applies it, it does not extend it.

The three reference apps (React Native `reference-app-rn`, NativeScript `reference-app-ns`, Svelte `reference-app-web`) each insert a chat message and show the list. Each now shows a "not yet delivered" mark on a message whose commit no other member holds, and clears it when that changes.

## Behaviour

- **Write.** The message insert becomes one statement that returns the commit's id: `insert into App.Message (Id, ParticipantId, Content, Timestamp) values (?, ?, ?, ?) returning StampId() as Tx`, run with `db.get(...)` (or `eval`). One statement is required: it is what makes the id belong to this write on a database cadre-core's background writers share (see the prereq ticket, "Matching a report to the app's write"). The web app's `insert or ignore` of the `Participant` row stays a separate statement before it; only the message's commit is marked.
- **Mark.** After the insert, read `strandDatabase.commitDurability(Tx)`. If it is defined and `heldElsewhere` is false, record the message id as undelivered under `Tx`. `undefined` (no report) or `heldElsewhere: true` records nothing.
- **Clear.** On `strand:commit-held` for the strand shown, clear the mark of the message recorded under that `transactionId`. Subscribe where each app already subscribes to `strand:writable` (RN `use-cadre.ts`, NS `cadre-vm.ts`, web `store.svelte.ts`) or in the chat view model, whichever keeps the mark state next to the message list; unsubscribe where the existing subscriptions are removed.
- **Show.** A small "not yet delivered" label on the message row, with a test id in each app's `test-ids.ts` (web: a `data-testid`). Same words in all three apps.
- **Marks are in memory.** Messages loaded from storage carry no mark (the app cannot know). A mark whose commit was not `followed`, or whose follow was forgotten by a hibernation, stays until the app restarts; that is honest ("not confirmed delivered") and the docs section says so. Do not add persistence.

The RN and NS apps' `chat-operations.ts` are near-copies; keep them parallel. The NS app's `cadre-vm.spec.ts` asserts the exact list of event subscriptions (`'on:strand:writable'` …), so a new subscription there changes those expectations.

## Edge cases & interactions

- **Resend that finds the row already stored** (`messageExists` / `chatMessageExists` path): no new commit, so no id and no mark. By inspection.
- **Held before the app reads** (the commit's blocks were already covered): `commitDurability(Tx)` already reports `heldElsewhere: true`, so no mark is set and no clear is needed. Relies on the prereq's record; by inspection.
- **Strand switch while a send is in flight** (NS `chat-vm.ts` and RN keep the composer across switches): key marks by strand id as well as transaction id, or drop marks on switch; a `strand:commit-held` for a strand not shown must not clear a mark on the shown one.
- **Founder alone before anyone joins:** every message is marked until a member joins and takes the copies. That is the intended reading; mention it in `docs/reference-app-rn.md` next to the chat description.
- **Web `writeChatMessage`** (e2e helper in `cadre-web.ts`): shares `insertChatMessage`; keep its return value (the message id) unchanged so the e2e test is unaffected.
