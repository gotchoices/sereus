# Await protocol-handler registration instead of dropping its rejection

## Problem

libp2p's `node.handle(protocol, handler, opts)` is async. In the installed `libp2p/dist/src/registrar.js` it throws `DuplicateProtocolHandlerError` when the protocol already has a handler, and it then awaits `peerStore.merge` of the node's own protocol list, which can fail on a datastore error (phones use a persisted peer store). Four cadre-core services call it as `void node.handle(...)` from a synchronous method:

- `StrandAddrService.initialize` (strand-addr-protocol.ts), called from `CadreNode.start`
- `StrandWakeService.initialize` (strand-wake-protocol.ts), called from `CadreNode.start`
- `SeedBootstrapService.registerProtocolHandler` ← `initialize` (seed-bootstrap.ts), called from the public `CadreNode.initializeSeedBootstrap` / `enableSeedListener`
- `FormationListener.register` (strand-formation-protocol.ts) ← `StrandFormationManager.registerResponder` ← `StrandSolicitationService.registerResponder` ← the public `CadreNode.initializeStrandSolicitation`. `FormationListener.unregister` also does `void node.unhandle(...)`.

A rejection there is unhandled. Node's default `--unhandled-rejections=throw` kills the process. The caller has already returned success.

**Reproduced 2026-09-28:** `StrandAddrService.initialize({ handle: async () => { throw new Error('dup handler') } })` returned without throwing, and exactly one `unhandledRejection` fired. The `no-floating-promises` lint rule does not catch this, because `void` is the sanctioned way to silence it.

`strand-peer-book-protocol.ts` (`async initialize(node)` → `await node.handle(...)`) already does it right. Copy that.

## Design

- Make each of the four registration methods `async` and `await node.handle(...)`. Set the service's stored `node` reference only after the await resolves, so a failed registration leaves nothing for `shutdown()` to unhandle. (`unhandle` of an unregistered protocol is harmless in libp2p, but the service state should be honest.) `FormationListener.unregister` becomes async and awaits `unhandle`, and its `registered` set is updated after the await.
- `CadreNode.start`: `await` the wake and strand-addr `initialize` calls. A rejection then reaches the existing `start()` catch, which runs `cleanup()` and rethrows. No new handling is needed.
- The chain up to the public API becomes async: `SeedBootstrapService.initialize`, `CadreNode.initializeSeedBootstrap`, `CadreNode.enableSeedListener`, `StrandFormationManager.registerResponder`/`unregisterResponder`, `StrandSolicitationService.registerResponder`/`unregisterResponder`, `CadreNode.initializeStrandSolicitation`. No backwards compatibility is owed.
  - The temp services in `applySeed` / `dialInvite` call `initialize(..., { registerHandler: false })`, so they register nothing, but the method is now async and they must await it too (lint enforces this in `src/`).
  - The `unregisterResponder` call in `CadreNode` teardown (~L4386) must be awaited.
- **Callers.** `no-floating-promises` is enforced in package `src/` trees, so `yarn lint` finds every production caller. Grep for the rest: tests and integration scenarios are not lint-checked for this rule. Missing an `await` there still works, because libp2p stores the handler synchronously before its first await, but add the `await` anyway. Measured 2026-09-28 with `grep -rln "initializeSeedBootstrap(\|enableSeedListener(\|initializeStrandSolicitation(\|registerResponder(" --include=*.ts --include=*.tsx packages`, excluding node_modules and dist: about 60 files across cadre-core src/test, cadre-cli (`src/commands/start.ts`, 2 specs), cadre-host (`trust-circle-integration.test.ts`), integration-tests (harness `node-fixtures.ts` + ~20 scenarios), reference-app-rn (`cadre-phone.ts`, `phone-node-config.ts`) and reference-app-web (`src/lib/cadre-web.ts`, `e2e/fixtures/formation-responder.ts`). The edits are mechanical: add `await`, and make the enclosing function async where it isn't. Check that each enclosing function is not a sync callback whose caller ignores the promise. If it is, handle the rejection there with a logged catch, and say which in the handoff.

## Tests

One test, at the lowest layer: in `strand-addr-protocol.spec.ts`, `StrandAddrService.initialize` with a node whose `handle` rejects must reject, and nothing may reach `unhandledRejection`. The other three services get the same edit and no test of their own (the pattern is identical, and a test per service only exercises the same `await`). Do not try to drive a full `CadreNode.start()` for this. The existing start() catch already covers the rollback.
