## Confirmed reproduction (prior run, against the existing `MockStream` harness)

A `provisionStrand` hook that sleeps past `provisionTimeoutMs` and *then* increments a use
counter: the `FormationListener` replies `approved: false, reason: 'Formation provisioning
timed out'` while the counter is still 0; ~100 ms later the abandoned hook finishes and the
counter hits 1 — invite spent. A second session with the *same* contact frame is answered
`'Invalid token'`. The joiner holds a permanently unusable invitation indistinguishable from
a genuinely bad token.

Decision (investigated across prior runs — do not relitigate): cancel the work via the
signal plumbing the prereq ticket landed, PLUS a short "did it land anyway?" settle grace.
The recoverable-spend alternative was rejected: every retry mints a fresh Ed25519 keypair
(`StrandSolicitationService.formStrand`), so `(Token, PeerId)` recovery can never match a
retry, and a recovery path would hand the strand id + closed-strand `MemberPrivateKey` to
anyone re-presenting a spent token under the recorded (writer-asserted) peer id.

## Design

Split `provisionTimeoutMs` into work budget + settle grace — grace carved OUT of the budget,
never added on top, so the documented timeout ladder (hook 10 s < provisioning 12 s <
initiator await 15 s < session 30 s) is untouched:

```
graceMs = min(PROVISION_SETTLE_GRACE_MS, floor(provisionTimeoutMs / 2))   // clamp keeps tiny test budgets sane
workMs  = max(1, provisionTimeoutMs - graceMs)
```

Outcomes after the work budget expires and the signal is aborted:

| provisioning settles within the grace as | listener replies |
| --- | --- |
| approved | the real approval (identity + cadre + provision result disclosed as usual) |
| rejected (`approved: false`) | that rejection reason, non-disclosing |
| threw (incl. `FormationAbortedError`) | `approved: false, reason: 'Formation provisioning timed out'` |
| still pending at grace end | same timed-out reply; keep the `void pending.then(...)` late-settle logging |

Keep the reply string `'Formation provisioning timed out'` verbatim — three existing tests
assert it. `runSession` needs NO change: its `!outcome` / `!outcome.approved` / approved
branches already handle every row above.

Replace `FormationListener.provision()` (do NOT use `withDeadline` — it exposes neither a
timed-out flag nor the signal outside `op`). Drafted bodies, verified against `withTimeout`
semantics:

```ts
private async provision(id: number, contact: FormationContactMessage): Promise<ResponderProvisionOutcome | undefined> {
	const graceMs = Math.min(PROVISION_SETTLE_GRACE_MS, Math.floor(this.provisionTimeoutMs / 2));
	const workMs = Math.max(1, this.provisionTimeoutMs - graceMs);
	const controller = new AbortController();
	let timedOut = false;
	const pending = this.options.provisionStrand(contact.token, contact.partyId, contact.disclosure, controller.signal);
	try {
		return await withTimeout(workMs, `Formation provisioning#${id}`, () => pending,
			() => { timedOut = true; controller.abort(); });
	} catch (err) {
		if (!timedOut) throw err;   // preserves the internal-error path for a throwing hook
		log('formation session #%d provisioning work budget expired after %dms; aborted, settling up to %dms', id, workMs, graceMs);
		return await this.settleWithinGrace(id, pending, graceMs);
	}
}

private async settleWithinGrace(id: number, pending: Promise<ResponderProvisionOutcome>, graceMs: number): Promise<ResponderProvisionOutcome | undefined> {
	let stillPending = false;
	try {
		const outcome = await withTimeout(graceMs, `Formation settle#${id}`, () => pending, () => { stillPending = true; });
		log('formation session #%d provisioning settled within its grace: approved=%s — adopting', id, outcome.approved);
		return outcome;
	} catch (err) {
		if (!stillPending) {
			log('formation session #%d provisioning failed after its abort: %o', id, err);
			return undefined;
		}
		log('formation session #%d provisioning still pending after its %dms grace', id, graceMs);
		void pending.then(
			(late) => log('formation session #%d provisioning settled after its grace: approved=%s', id, late.approved),
			(err2) => log('formation session #%d provisioning failed after its grace: %o', id, err2)
		);
		return undefined;
	}
}
```

A hook rejecting right after abort is safe: `withTimeout`'s promise already settled, and
`settleWithinGrace` attaches handlers to `pending` in the same catch — no
unhandled-rejection window.

Delete the stale `NOTE:` inside the old `provision()` catch ("provisionStrand is not
cancelled on timeout…"). The narrowed residual goes in `settleWithinGrace`'s docblock as a
tripwire (NOT a ticket): the one unclosable window is a work budget expiring after the
`FormationUsage` insert was issued AND the commit outlasting the grace — invite spent while
the joiner is told timeout. Nothing can un-spend the append-only table, and a retry arrives
under a fresh keypair; the late-settle logging is the observability for it.

Grace clamp re-checked against all five existing timeout tests: pT 20 → 10/10
(never-settles still replies 'timed out'); clamped 900 → 450/450 vs 950 ms hook → timed
out; clamped 600 → 300/300 vs 700 ms hook → timed out; pT 200 → work 100 vs 30 ms hook →
approves; pT 0 → default 12 000 → work 10 000. `slowProvision` ignores the signal, so no
existing test breaks.

## Tests (`test/strand-formation-protocol.spec.ts`; timings clear CI jitter)

- **Adoption regression**: module-scope-per-test `let uses = 0`; pT 400 (work 200 / grace
  200); hook sleeps 300 ms, THEN increments `uses`, returns approved;
  `validateToken: async () => ({ valid: uses < 1 })`. First session → `approved: true`,
  strand disclosed, `uses === 1`. Second session, same contact → `'Invalid token'` (the
  spend belongs to a join the joiner was TOLD succeeded — honest refusal).
- **Abandon-without-write**: pT 100; hook call #1 returns a promise that rejects when its
  `signal` fires (no counter bump); call #2 approves and bumps. Session 1 →
  `'Formation provisioning timed out'` with `uses === 0`; session 2 (same contact) →
  approved — the invite survived the timeout.
- **Extend the existing never-settles test** ('reports a timed-out provisionStrand as a
  retryable rejection…'): capture the hook's 4th `signal` arg, assert
  `capturedSignal?.aborted === true` after the reply.
- **Reply-bound**: pT 500 (250/250), signal-ignoring never-settling hook; assert the
  timed-out reason AND elapsed ≤ 700 ms (a grace-added-on-top bug would reply at ~750 ms).
