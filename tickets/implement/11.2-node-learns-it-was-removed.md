# A removed machine reports its own removal

## Why

docs/architecture.md → "What is deliberately not reaped" names "a node that learns it has been revoked should shut itself down" as a distinct behaviour, and nothing builds it: a removed node only logs `registerSelf: own CadrePeer row not readable …` every heartbeat, and `drainPendingRevocations` carries a `NOTE:` that its repeated failures on a removed owner device belong to this work. The embedders (cadre-cli and cadre-host, the phone kit, the web app) need one signal to act on.

## Contract

- **What counts as removed.** A `CadrePeer` tombstone (`Revocation` with `TableName = 'CadrePeer'`) whose `RowKey` is this node's peer id, and no live `CadrePeer` row for this node (its stamp retired, or the row gone), **after this node has seen its own live row at least once in this process**.
  - The "seen live in this process" condition keeps a machine that is joining again (a fresh store that syncs the old tombstone before the new row) from reporting itself removed. A rejoined machine has a live row under a fresh stamp, which ends the condition.
  - It also means a machine that was removed, synced the tombstone, and restarted before acting never reports. The embedders close that gap by persisting what they did (cadre-cli writes a marker, the kits delete the party), so the window is a crash between the event and the embedder's action. `NOTE:` at the check.
- **Where it is detected.** In the membership refresh (`refreshMembershipGate`), from the tombstones `syncOwnerAnchor` already reads and the own-row read the refresh already does (or `queryPeerRecord(self)`, which reads a retired stamp as absent). No new timer and no extra `Revocation` scan. Also track "seen live" there.
- **What it reports.**
  - Event `cadre:removed` on `CadreNodeEvents`: `{ partyId: string; stampId: string; signerKey: string | null; at: number }` from the tombstone (`SignerKey`, verified with `verifyRevocationSigner` against this node's anchor; when it does not verify, still report — the tombstone is in the store and every other machine honours it — but log that the signer is not anchored here). Raised once per process.
  - `CadreNode.removedFromCadre(): CadreRemoval | null`, the same record, for an embedder that subscribes after the event fired.
- **What the node itself does.** Nothing beyond reporting, and it stops the owner-side growth drains that can only fail now: `drainPendingRevocations`, `reconstructAuthoredMembership` and `drainPendingPeerWrites` return early once removed (replace the `NOTE:` in `drainPendingRevocations`). The node does not stop itself: stopping and deleting are the embedder's, because storage, saved starts and process lifetime are the embedder's (the same split as `strand:revoked`). The three embedders that act are `hosted-node-stops-when-removed` (cadre-cli, cadre-host), `phone-kit-forgets-a-cadre-that-removed-it` and `reference-app-web-devices-and-nodes`.
- **Best-effort.** A removed machine learns only if the tombstone reaches it. Every other machine refuses its control streams once it holds the tombstone, and the remover closes its connections (`cadre-node-removes-a-machine`), so a machine offline at removal time usually never learns. Docs say so plainly.

## Edge cases & interactions

- **Removed, then re-added under a fresh stamp before this node noticed**: a live row exists, so not removed. Covered by the test.
- **Re-added after the event fired**: the record stays (once per process); the embedder has already acted. By inspection; the docs say re-adding a removed machine means joining it again.
- **Tombstone for self whose signer is not anchored here**: reported, with a log line. By inspection.
- **Node never admitted (claim waiting, invitation joining)**: never saw a live row, never reports. Covered by the test.
- **Refresh read failure**: the refresh already skips; detection runs only on a successful pass.
- **Node shutting down**: no event after `stop()` begins (`_running` guard). By inspection.
- **The `registerSelf` heartbeat log** for a removed node stays (it is the debug trail).

## Tests

One spec, using the gate suites' fake control database (`test/membership-gate-helpers.ts`), three cases on the rule's branches: seen live then tombstone with no live row → one `cadre:removed` and `removedFromCadre()` set, and a second refresh does not repeat it; tombstone present but never seen live → nothing; tombstone plus a live row under a fresh stamp → nothing. The fakes hand-mirror `queryCadrePeers`'s retired-stamp filter (NOTE in `control-database.ts`); keep that true.

No integration assertion: whether the removed machine receives the tombstone before it is cut off is a race by design, so gating a scenario on it would be flaky. The scenario from `cadre-node-removes-a-machine` may log whether B reported, for information.
