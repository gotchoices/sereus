# Cadre invitation tables and the consent branches

## Where this sits

Today a device joins a cadre only while an owner is online: the owner signs the device's `CadrePeer` row at that moment (`authorizePeer`, reached through `acceptPhone` and the cadre-cli admin route). The three-ticket chain `cadre-invite-schema-and-chain` → `cadre-invite-redemption-protocol` → `cadre-invitations-redeemable-by-any-member` replaces that with an owner-signed **invitation row** that any member machine can redeem on the owner's behalf. This ticket is the schema and the database layer only: no protocol, no client API, and the old path stays in place until the last ticket removes it.

## Design (settled in planning)

### An invitation is a keypair, not a bearer token

The plan ticket proposed a random token stored as a hash. That was rejected because the member machine that redeems the invitation would see the token and could redeem the invitation for itself: for an owner-granting invitation that is an owner escalation available to every member machine. Instead the owner mints an ed25519 keypair. The row stores the public half (`Key`, the primary key); the holder proves possession by signing with the private half; a member can verify that signature but cannot produce it. This is the shape `Strand.Invite` already uses (`strand-membership-writer.ts` → `issueInvite`).

### Invitation rows are permanent; withdrawal is a tombstone with the row kept

A device admitted by invitation carries no owner signature of its own. Its proof of membership is the chain invitation row → usage row → peer row, verified at read time (below), so the invitation row must outlive every device it admitted. Rows are therefore insert-only, and **withdrawing** an invitation is an owner-signed `Revocation` tombstone over the row's stamp while the row stays. `Revocation.RowIsGone` gets a branch for `CadreInvite` with no row-gone test; say so at the branch. Liveness is read as: no tombstone for the stamp, unexpired, uses left. Expired and withdrawn rows accumulate at cadre scale; the same tripwire as `hasOutstandingFormationInvite` applies, and an owner can retire the chain dependency of any admitted device by re-vouching its row (`reauthorizePeer`, the owner branch of `CadrePeer.AuthorizedUpdate`), after which the invitation row is no longer consulted for that device.

### Seat, then redeem: two transactions

The invitation row is committed before the transaction that redeems it. Every consent branch reads `committed.CadreInvite`, so a single transaction that seats an invitation and redeems it is refused. This matters for `OwnerKey`, whose owner branch already reads the pre-transaction snapshot so that no row can authorize itself; the consent branch keeps that property.

### Tables

`CadreInvite`:

- `Key text primary key` — the invitation's ed25519 public key, base64url.
- `PeerId text null` — the device the invitation is for; null means whoever redeems first designates it.
- `GrantsOwner integer` — 0 or 1 (`check (new.GrantsOwner = 0 or new.GrantsOwner = 1)`): whether redemption also seats an `OwnerKey` row.
- `ExpiresAt datetime null`, `TotalUses int null check (TotalUses >= 0)` — as `FormationInvite`.
- `IssuerKey text`, `IssuerSig text` — the owner that signed the row and its `'add'` signature, pinned to the insert context exactly as `CadrePeer.VouchOwner`/`VouchSig` are. A reader checks `IssuerKey` against its node-local anchor, never against the replicated `OwnerKey` table.
- `StampId text unique`.
- `AuthorizedInsert`: an owner signature over `digest('CadreControl.CadreInvite', 'add', new.Key, coalesce(new.PeerId, ''), cast(new.GrantsOwner as text), coalesce(cast(new.ExpiresAt as text), ''), coalesce(cast(new.TotalUses as text), ''), new.StampId)`, verified against live `OwnerKey`, and `new.IssuerKey = context.OwnerKey and new.IssuerSig = context.Signature`.
- `NotRevoked` on insert (no `Revocation` row under `'CadreInvite'` for the stamp): a withdrawn invitation cannot be re-seated from the signed copy its holder keeps.
- `NoUpdate` and `NoDelete` (`check on delete (false)`).
- `with context (OwnerKey text, Signature text)`.

`CadreInviteUsage` (append-only, one row per redemption):

- `UsageStampId text primary key` — a nonce minted by the redeeming device, signed into both signatures below. Same convergence note as `FormationUsage.UsageStampId`.
- `InviteKey text` — the invitation redeemed.
- `PeerId text`, `PeerKey text` — the redeeming device. `PeerId` is the identity multihash of `PeerKey`; the writer asserts it and a reader re-derives it.
- `PeerStampId text` — the `CadrePeer.StampId` this usage seats. Minted by the writer inside the redeeming transaction and not signed, as `FormationUsage.StrandStampId` is.
- `OwnerStampId text null` — the `OwnerKey.StampId` this usage seats when the invitation grants ownership.
- `InviteSig text` — signature by the invitation's private key over `digest('CadreControl.CadreInviteUsage', 'redeem', new.InviteKey, new.UsageStampId, new.PeerKey)`, verified against `new.InviteKey` itself: proof of possession.
- `PeerSig text` — signature by `PeerKey` over `digest('CadreControl.CadreInviteUsage', 'consent', new.InviteKey, new.UsageStampId, new.PeerKey)`: the device agreed to join.
- `InsertOnly check on update, delete (false)`.
- `Authorized check on insert`: exists `committed.CadreInvite I` with `I.Key = new.InviteKey`, no `Revocation` row under `'CadreInvite'` for `I.StampId`, `(I.ExpiresAt is null or I.ExpiresAt > context.Now)`, `(I.TotalUses is null or I.TotalUses > (select count(1) from committed.CadreInviteUsage U where U.InviteKey = new.InviteKey))`, `(I.PeerId is null or I.PeerId = new.PeerId)`, and `exists (select 1 from committed.OwnerKey K where K.Key = I.IssuerKey)` (an owner removed since issuing takes its outstanding invitations with it).
- `InvitePossessed check on insert` and `PeerConsented check on insert`: the two `verify` calls above.
- `PeerExists check`: `exists (select 1 from CadrePeer P where P.PeerId = new.PeerId and P.StampId = new.PeerStampId)` — deferred, so the same-transaction peer insert counts; a usage row can never be held in reserve to seat a row later (the `FormationUsage.StrandExists` rule).
- `OwnerExists check`: `new.OwnerStampId is null or exists (select 1 from OwnerKey K where K.Key = new.PeerKey and K.StampId = new.OwnerStampId)`.
- `with context (Now datetime)`.
- `index CadreInviteUsageByInvite on CadreInviteUsage (InviteKey)` — serves the cap count and the liveness reads, as `FormationUsageByToken` does.

`CadrePeer` gains `VouchUsage text null` and a consent branch on `AuthorizedInsert`: `new.VouchSig is null and new.VouchOwner is not null and new.VouchUsage is not null` and exists `CadreInviteUsage U` with `U.UsageStampId = new.VouchUsage and U.PeerId = new.PeerId and U.PeerStampId = new.StampId and U.PeerKey = new.PublicKey` and exists `committed.CadreInvite I` with `I.Key = U.InviteKey and I.IssuerKey = new.VouchOwner`. The liveness conditions are the usage row's; this branch only requires a usage row naming this exact row incarnation. The owner-signed insert branch and the owner re-vouch update branch add `new.VouchUsage is null` (a row carries exactly one proof); the self-publish update branch adds `new.VouchUsage = old.VouchUsage`.

`OwnerKey` gains `VouchOwner text null`, `VouchSig text null`, `VouchUsage text null`. The genesis branch requires all three null. The owner-signed add branch pins `new.VouchOwner = context.OwnerKey and new.VouchSig = context.Signature and new.VouchUsage is null`, so the stored approval the plan ticket `owner-anchor-follows-owner-key-changes` builds on already exists (no writer in `ControlDatabase` seats a second owner today, so only the schema and its test change). The consent branch: `old.Key is null and new.VouchSig is null and new.VouchUsage is not null` and exists `CadreInviteUsage U` with `U.UsageStampId = new.VouchUsage and U.PeerKey = new.Key and U.OwnerStampId = new.StampId` and exists `committed.CadreInvite I` with `I.Key = U.InviteKey and I.GrantsOwner = 1 and I.IssuerKey = new.VouchOwner`. `MinOneOwner`, `NoUpdate`, `NotRevoked`, `RevocationRecorded` and the remove branch are unchanged.

`Revocation`: the `TableName` comment lists `'CadreInvite'`; `RowIsGone` gets the branch `(new.TableName = 'CadreInvite')` with the comment that for this table a tombstone is a withdrawal and the row stays.

`control-authorization.ts`: `CONTROL_TABLES` adds `'CadreInvite'` and `'CadreInviteUsage'` in schema order (after `FormationUsage`); `RevocableTable` adds `'CadreInvite'` with its comment amended (tombstone without delete); `ControlAction` adds `'redeem'`. The `control.qsql` header paragraph that lists the guarded tables and the `Revocation` header are updated.

### ControlDatabase

- `insertCadreInvite({ key, peerId, grantsOwner, expiresAtMs, totalUses }, ownerKey, signMessage)`: mints the stamp, signs the `'add'` digest (TS mirror `cadreInviteAddMessage` beside `formationConsentMessage`; `ExpiresAt` through `canonicalDatetime` so the signed segment matches the stored form, as `issueInvite` does), inserts, and returns the stored row as a `CadreInviteRow` (every column, `expiresAt` in the stored canonical form) for the invitation bundle the next ticket encodes.
- `seatCadreInvite(row: CadreInviteRow)`: insert-if-absent under the row's own `IssuerKey`/`IssuerSig` as context, in its own transaction, inside the write lock. A member that receives the row inside an invitation uses this; present → no-op. An `AuthorizedInsert` failure means the issuer is not an owner on this node (not replicated yet, or removed); surface it as a named error so the protocol ticket can map it to a retryable code.
- `queryCadreInvite(key)`, `queryCadreInvites()`, `queryCadreInviteUsages()`, `countCadreInviteUsage(key)`, `hasLiveCadreInvite(nowMs)` (same loop shape and NOTE as `hasOutstandingFormationInvite`; a withdrawn stamp, read through `queryRevocations`, counts as not live).
- `withdrawCadreInvite(key, ownerKey, signMessage)`: appends the owner-signed tombstone through the existing tombstone writer (`revocationDigest('CadreInvite', key, stamp)`), no delete.
- `redeemCadreInvite({ inviteKey, peerId, peerKey, multiaddrs, usageStampId, inviteSig, peerSig, nowMs })` → `{ alreadyMember, peerStampId, ownerStampId }`. Inside `lockedWithRetry`, in this order: seat check (`assertCadreInviteSeatRemains`, counting committed usage, throwing the named exhaustion error as `assertSeatRemains` does), existing-row check (`queryStampId('CadrePeer', peerId, false)`): if the row exists and (the invitation does not grant ownership or an `OwnerKey` row for `peerKey` exists) return `alreadyMember: true` with nothing written — the idempotent retry after a dropped reply; otherwise one transaction through `mutateCadrePeer` (so the membership hub is notified) that inserts the `CadrePeer` row when absent (`PublicKey = peerKey`, comma-joined `Multiaddr`, `UpdatedAt = nowMs`, `Sig null`, fresh stamp, `VouchOwner = invite.IssuerKey`, `VouchSig null`, `VouchUsage = usageStampId`; when present, `PeerStampId` is the existing stamp), the `OwnerKey` row when granted and absent (same vouch columns), and the usage row last.
- `queryCadrePeers` returns `vouchUsage`; `CadrePeerRow` in types.ts gains it.

### The reader: listAuthorizedMembers

`CadreNode.listAuthorizedMembers` keeps the existing voucher check for rows with `VouchSig`. A row with `VouchSig` null and `VouchUsage` set is judged by `verifyInvitationAdmission(row, usage, invite, isAnchored)` in `peer-authorization.ts`, which returns true only when: `row.vouchOwner` is anchored; `invite.issuerKey === row.vouchOwner`; `invite.issuerSig` verifies over the invite `'add'` digest rebuilt from the stored row; `usage.inviteKey === invite.key`; `usage.peerStampId === row.stampId`; `usage.peerId === row.peerId`; the peer id derived from `usage.peerKey` equals `row.peerId`; `usage.inviteSig` verifies with `invite.key` over the `'redeem'` digest; `usage.peerSig` verifies with `usage.peerKey` over the `'consent'` digest; `invite.peerId` is null or equals `row.peerId`. Expiry, use count and withdrawal are not re-checked: they were conditions at redemption, and membership persists until an owner removes the row. The usage and invitation reads run only when at least one row needs them, so the common path stays one read. The per-stream gate snapshot and the connection gate already go through this one function.

A removed device may redeem a still-live invitation again and come back; keeping a device out is remove the row **and** withdraw the invitation. Record this at the `CadrePeer` consent branch.

## Edge cases & interactions

- **Two redeemers race for a single-use invitation on different machines.** The cap counts committed usage locally, so both may be admitted until merge, and after merge both rows stand (the `FormationUsage` convergence note). Decision: accepted, for owner grants too. Serializing would need cross-machine coordination the control plane does not have; the mitigations are the defaults the protocol ticket sets (untargeted owner invitations single-use with a short expiry), the targeted form for owner grants, and the owner seeing the extra owner and removing it. Record this at the usage table's cap clause. (Inspection.)
- **Targeted invitation redeemed by another peer id**: refused by `CadreInviteUsage.Authorized`. (Test.)
- **Invitation seated and redeemed in one transaction**: refused by the `committed.` reads. (Test, on the `OwnerKey` branch.)
- **Usage row with no peer row in its transaction**: refused by `PeerExists`. (Test.)
- **Withdrawn invitation re-seated from the holder's signed copy**: refused by `CadreInvite.NotRevoked` on nodes that hold the tombstone; a node that has not converged on the tombstone accepts it, the same gap every guarded table has (schema header). (Test for the refusal.)
- **Issuer removed after issuing**: its invitations stop redeeming (`committed.OwnerKey` clause). Devices it already admitted stay members: their chain verifies against the reader's anchor, which the plan ticket `owner-anchor-follows-owner-key-changes` will make follow removals. (Inspection.)
- **Writer asserts a `PeerId` that does not derive from `PeerKey`**: the schema cannot derive peer ids; the reader refuses the row. (Unit test of `verifyInvitationAdmission`.)
- **Non-ed25519 redeemer**: has no `PeerKey`; the protocol ticket refuses it before any write. Nothing to do here.
- **Warm start of an existing control store**: every constraint edit forces recreation (docs note under the table list). No migration; say so in the handoff.
- **`countRows` and the schema-drift tests** read `CONTROL_TABLES`; check `test-harness`'s schema-text comparison and `control-schema-drift.spec.ts` after the edit.

## Tests

One new spec, `control-cadre-invite.spec.ts`, using `control-constraint-helpers.ts` (`expectConstraintFailure` names exactly one constraint per case):

- redemption seats `CadrePeer`, and `OwnerKey` when `GrantsOwner`, with no owner context; both carry `VouchUsage` and a null `VouchSig`; a second call for the same peer returns `alreadyMember` and writes nothing.
- targeted invitation, other peer id → `Authorized`; expired → `Authorized`; withdrawn (tombstone present) → `Authorized`; exhausted → the named exhaustion error from the pre-check.
- `InviteSig` by a different key → `InvitePossessed`; `PeerSig` by a different key → `PeerConsented`.
- `GrantsOwner = 0` with an `OwnerStampId` → `OwnerKey.Authorized`.
- `seatCadreInvite` with an issuer not in `OwnerKey` → `CadreInvite.AuthorizedInsert`; seating twice is a no-op.
- usage row without a peer row → `PeerExists`.
- invitation and redemption in one transaction → `OwnerKey.Authorized`.
- tombstone accepted with the row present; the row re-seated afterwards → `NotRevoked`.
- `verifyInvitationAdmission` (no database): anchored issuer passes; unanchored issuer fails; `PeerKey` not deriving to `PeerId` fails; `invite.peerId` naming another peer fails.

Update `control-ownerkey-self-authorization.spec.ts` for the pinned `VouchOwner`/`VouchSig` on an owner-signed add.
