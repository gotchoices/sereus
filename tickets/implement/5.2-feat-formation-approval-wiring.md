# Wire the approval hook into the redemption path

## The gap

An invitation may carry a `ValidationUrl`. The control database enforces it: when
`FormationInvite.ValidationUrl` is non-null, `FormationUsage.Authorized` requires a signature
from an enrolled `ValidationKey` over
`formationVouchMessage({ token, usageStampId, strandId, peerId, disclosure })`. No production
code path supplies one, so redeeming such an invitation fails with
`CHECK constraint failed: Authorized`. The invitation is unusable, and the party that configured
it has locked its own network rather than gated it.

`feat-formation-approval-client` built the client surface (`FormationApprover`,
`createHttpFormationApprover`, `signFormationApproval`, `verifyFormationApproval`,
`FormationApprovalError`). This ticket calls it from the real redemption path.

## Where the approval is fetched — settled

**Inside `ControlFormationUsageRecorder`**, not in `StrandFormationManager`.

The approval is bound to the redemption's single-use nonce and to the strand id. The recorder is
already the component that reads the invite row, mints the strand id on the unbound path, and
performs the database write — so it is the only place where "the nonce we signed" and "the nonce
we insert" are trivially the same value. Putting the fetch in the manager would mean widening
the deliberately database-agnostic manager interface with nonce and strand-id plumbing for no
gain. The tradeoff: the recorder now performs network I/O, so it needs its own failure taxonomy
(handled below) and its unit tests need a fake approver.

The manager's remaining job is to (a) serialize the disclosure once and pass it down, and (b)
translate approval failures into rejection reasons the joiner can act on.

## Disclosure text — settled

`FormationUsage.Disclosure` is written as `''` today, always. The approver signs over that
column's value, so it has to carry the real disclosure.

The responder serializes the disclosure **once** (`JSON.stringify(disclosure)`), in
`StrandFormationManager.provisionAsResponder`, and passes that exact string to both the approver
and the insert. No canonical-JSON scheme is needed and none should be invented: the two consumers
of the string are the same process holding the same string, and the hook receives it verbatim
and signs the bytes it was given (documented in the client ticket).

Cap the serialized text at **8 KiB**. Over the cap, reject the formation before any hook call or
database work with reason `'Disclosure too large'`. The disclosure is initiator-supplied and ends
up in an append-only, replicated table; an unbounded field there is a growth surface.

Note that this makes every redemption — with or without a `ValidationUrl` — start recording real
disclosure text where it recorded `''` before. That is the intended behaviour of an audit log,
but call it out in the handoff: existing rows keep `''`, and nothing reads the column.

## Interface changes

`strand-solicitation.ts`:

```ts
export type ResolvedHostStrand =
  | { kind: 'unbound'; validationUrl: string | null }
  | { kind: 'bound'; strandId: string; memberPrivateKey: string | null; validationUrl: string | null }
  | { kind: 'missing'; strandId: string };

export interface FormationUsageRecorder {
  recordUsage(params: {
    token: string;
    /** The joining peer — written to FormationUsage.PeerId and inside the approval digest. */
    peerId: string;
    strandId: string;
    /** Exact text to write to FormationUsage.Disclosure; the approver signs these bytes. */
    disclosure: string;
  }): Promise<void>;

  provisionAndRecord?(params: {
    token: string;
    peerId: string;
    sAppId: string;
    disclosure: string;
  }): Promise<{ strandId: string; memberPrivateKey: string | null }>;

  // isTokenUsed / isTokenValid / resolveStrand / hasOutstandingInvitation unchanged
}
```

The old positional `(token, initiatorKey, strandId)` shape is replaced (no back-compat). Rename
`initiatorKey` → `peerId` throughout so the argument matches the column it lands in.

`StrandSolicitationService.recordFormationComplete(token, peerId, strandId, disclosure = '')`
forwards to the new object shape.

`control-database.ts`: add `mintUsageStampId(): string` — `generateStampId(localPeerId)` using
the database's own libp2p node — so the recorder can mint the nonce without reaching for the peer
id itself.

## Recorder wiring (`control-formation-recorder.ts`)

```ts
constructor(
  private readonly controlDatabase: ControlDatabase,
  options?: { approver?: FormationApprover }
)
```

Default the approver to `createHttpFormationApprover()`. Defaulting it **on** is deliberate:
`ControlFormationUsageRecorder` is constructed by the reference apps and the integration harness,
not by `CadreNode`, so an opt-in approver would leave every real deployment with the bug this
ticket fixes. Tests inject a fake.

Private helper, used by both write paths:

```ts
private async obtainApproval(request: Omit<FormationApprovalRequest, 'usageStampId'> & { validationUrl: string | null })
  : Promise<{ usageStampId?: string; validationKey?: string; validationSignature?: string }>
```

- `validationUrl === null` → return `{}` (the database mints its own nonce; unchanged behaviour).
- otherwise: mint `usageStampId` via `controlDatabase.mintUsageStampId()`, build the full
  `FormationApprovalRequest`, call `approver.requestApproval`, then run two local pre-checks
  before writing:
  - `verifyFormationApproval(request, approval)` false → throw
    `FormationApprovalError('malformed', ...)`.
  - `controlDatabase.queryValidationKeyStampId(approval.validationKey)` null → throw
    `FormationApprovalError('unenrolled', ...)` (add `'unenrolled'` to
    `FormationApprovalFailure` in the client module).

  Both pre-checks exist purely for legibility — the database re-verifies against the **stored**
  `ValidationKey` row and remains the authority. Say so in a comment so a later reader does not
  mistake them for the security boundary and try to "simplify" the database check away.

`recordUsage` and `provisionAndRecord` each read the invite (they already do), call
`obtainApproval`, and pass `disclosure`, `usageStampId`, `validationKey`, `validationSignature`
through to `recordFormationUsage` / `redeemInvitation` — which already accept all four.

`resolveStrand` already reads the invite row; return its `validationUrl` on the `unbound` and
`bound` variants so the manager can see approval is required without a second read.

## Manager wiring (`strand-formation-manager.ts`)

`provisionAsResponder` currently ignores its `_disclosure` argument. Now it:

- serializes the disclosure once, enforcing the 8 KiB cap (reject early otherwise);
- passes `{ token, peerId: initiatorPartyId, strandId, disclosure }` to `recordUsage`, and
  `{ token, peerId, sAppId, disclosure }` to `provisionAndRecord`;
- maps `FormationApprovalError` to a distinct rejection reason instead of the current catch-all
  `'Formation conflict, retry'`:

  | `failure`        | reason sent to the joiner                      |
  |------------------|------------------------------------------------|
  | `refused`        | `Formation approval refused`                   |
  | `unavailable`    | `Formation approval unavailable, retry`        |
  | `malformed`      | `Formation approval invalid`                   |
  | `unenrolled`     | `Formation approval key is not enrolled`       |
  | `misconfigured`  | `Formation approval misconfigured`             |

  Everything else keeps `'Formation conflict, retry'`. Keep the existing log-then-convert shape.

No usage row is written on any approval failure, so the invitation is **not** consumed and the
joiner may retry.

## Edge cases & interactions

- **Approval refused / hook unreachable** — clean `approved: false` with the mapped reason, no
  `FormationUsage` row, invite still redeemable afterwards. Assert the use count is unchanged.
- **Approval for a non-enrolled key** — must produce `'Formation approval key is not enrolled'`,
  specifically NOT `'Formation conflict, retry'`; that mis-mapping is the opaque failure this
  ticket set out to remove.
- **Approval signed over different fields** (wrong nonce, wrong strand, wrong joiner, wrong
  disclosure text) — caught by the local verify, mapped to `'Formation approval invalid'`, no
  write attempted.
- **Nonce mismatch between sign and insert** — the single most important invariant: the
  `usageStampId` inside the signed request must be the one written to the column. Assert it
  directly (read `UsageStampId` back and compare to the value the fake approver saw).
- **Invite with no `ValidationUrl`** — the approver must not be called at all (assert zero
  invocations), redemption unchanged, but `Disclosure` now carries the real text.
- **Concurrent redemption of a single-use `ValidationUrl` invite** — both responders obtain
  approvals; one wins the `(Token, UseNumber)` primary key, the loser gets
  `'Formation conflict, retry'` and its approval is spent (the nonce it signed is never inserted,
  so a retry needs a fresh approval — for a manual review queue that means a second human
  review). Acceptable now; leave a `NOTE:` at the retry mapping rather than filing a ticket.
- **Approval obtained, database write then fails for an unrelated reason** — same shape: no row,
  approval spent, retryable. Covered by the same `NOTE:`.
- **Bound invite whose host strand is `missing`** — unchanged: reject before any hook call. The
  hook must never be contacted for a redemption that cannot proceed.
- **Disclosure over the cap** — rejected before the hook call and before any database read that
  could burn work; assert the approver was not invoked.
- **Hook latency vs. session budgets** — the approval fetch (10 s) sits inside the responder
  provisioning budget (12 s) from `debt-formation-provision-step-timeout`. A test with a slow
  fake approver must confirm a 6-second approval still completes rather than tripping a timeout.
- **`FormationUsage.Disclosure` is now attacker-influenced text in a replicated table** — the
  8 KiB cap is the bound. Nothing parses the column; do not add parsing.
- **`isTokenUsed` was checked earlier in the session** — the hook call widens the window between
  that check and the write. This is why the primary-key collision path must stay a clean
  rejection; do not add a second pre-write `isTokenUsed` check, it cannot close the race.
