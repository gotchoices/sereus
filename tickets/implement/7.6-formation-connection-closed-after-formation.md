# The cross-party formation connection closes when formation is done

## Measured (before)

`message-cost-accounting`, strand case, 60 s idle: failed `control-<party>/fret/ping` negotiations A.ctl→B.ctl 2 and B.ctl→A.ctl 2, plus libp2p pings on that connection; in the settle window 4 failed FRET pings each way between the two control nodes. Also `/sereus/strand-addr/1.0.0` sent to the dedicated relay and refused, once at `foundStrand` (A) and once at `addStrand` (B).

Cause of the first: the joiner's control node dials the inviter's control node for `/sereus/formation/1.0.0` and never closes the connection. The two control nodes are on different FRET networks (`control-<partyA>`, `control-<partyB>`), so every FRET ping on that connection fails negotiation, and the connected off-ring peer also keeps FRET's stabilization interval near its 1.5 s base instead of backing off toward 60 s (FRET's NOTE at `../Fret/packages/fret/src/service/fret-service.ts` ~3079 and ~3110). FRET's own handling of off-ring peers is upstream (`fret-maintenance-probes-peers-off-its-ring`); this ticket is Sereus's share.

Cause of the second: the launch seed pass (`resolveSiblingSeed`, awaited before the strand node starts) and the periodic grant refresh announce the strand's delegate peer id to every circuit relay. A dedicated `ops/` relay does not serve strand-addr; the refusal is remembered only in memory (`relaysRefusingStrandAddr`), so each process pays one refused negotiation on its first launch.

## Design

### 1. The formation dialer closes the connection it opened

Only the dialer (joiner) closes. It is the side that opened the connection, so it is the side that knows whether the connection existed before. The responder never dials the joiner back after formation (checked: `cadrePeerAddrs` in the contact is only carried, never dialed), and a responder-side close would race the reply's delivery and could cut a connection the joiner was already using. A dialer that crashes takes the connection with it; a dialer that times out still runs the close in its `finally`.

Mechanism, in `strand-formation-protocol.ts`:

- `openFormationStream` splits `node.dialProtocol(addrs, protocolId, { signal })` into `node.dial(addrs, { signal })` then `connection.newStream(protocolId, { signal })`, keeping the existing late-resolution abort for both steps (a connection that resolves after the deadline is closed if this dial opened it, the stream aborted). It returns the stream and the connection.
- Before dialing, it snapshots the ids of all of the node's current connections (`node.getConnections().map(c => c.id)`; all peers, so no peer id is needed — `dialFormation` accepts entries with no trailing peer id). If the returned connection's id is not in the snapshot, this dial opened it: add the `Connection` object to a module-level `WeakSet<Connection>` of connections opened for formation. (WeakSet keyed by the object: no cleanup, no growth.)
- `exchangeContact`'s `finally`, after `stream.close()`: if the connection is in that WeakSet and no other open stream on it has `protocol === protocolId` (`connection.streams`), close it (`await connection.close()`, catching and logging any error — do not abort it; a graceful close lets the responder's side finish its own stream close). Otherwise leave it: either it pre-existed (someone else's connection), or another formation exchange is still using it and that exchange will close it when it finishes, because the WeakSet membership is per connection, not per dial.
- This runs for success, rejection, validation failure and timeout alike, since all pass through `exchangeContact`'s `finally`. A session timeout that fires while `exchangeContact` is still awaiting the read: `withTimeout` rejects the outer promise but the inner `finally` still runs when the read settles or the stream is torn down; confirm by reading `withTimeout` (`control-stream.ts` or wherever it lives) that it does not leave the inner work hanging forever. If it can, close in the outer path too (`dialFormation`'s catch), using the same rule.

Rejected alternatives:
- `node.hangUp(peer)`: closes every connection to the peer, including one that pre-existed.
- Closing whenever `connection.streams` is otherwise empty: FRET pings, identify and libp2p ping streams come and go on that connection, so the check would often leave it open, which is the bug.
- Closing on the responder too: see above.

**Same-party counterpart.** If an invitation's responder is a machine of the joiner's own party, the connection normally pre-exists (the cadre mesh), so it is left alone. If it did not, the dial opened it and it is closed; the mesh re-dials its sibling as it would after any drop. Accepted, note it in the code comment.

### 2. Skip a relay whose identify says it does not serve strand-addr

Prefer identify over persisted state. Control nodes run `identify` and `identifyPush` (`../optimystic/packages/db-p2p/src/libp2p-node-base.ts` ~1026/~1043), and the dedicated relay runs `identify` (`ops/docker/libp2p-infra/src/main.ts` ~96), so the control node's peer store holds the relay's protocol list once identify has run on the relay connection, which the control node opens at start for its reservation.

- Add an async step after `circuitRelayTargets()` in both announce passes that use it (`resolveSiblingSeed`, `refreshDelegateGrants`): for each relay, read `controlNode.peerStore.get(peerIdFromString(relay.relayPeerId))`; drop the relay when its `protocols` list is **non-empty and lacks** `STRAND_ADDR_PROTOCOL`. A `NotFoundError`, an empty list (identify has not run), or any other read error (log it) keeps the relay: ask it, as today. Read the relays concurrently. The pure decision (`protocols` → skip or not) can sit beside `relaysNotRefusing` in `delegate-admission.ts`.
- `announceDelegateToRelay` (the reservation supervisor's `beforeRedrive` hook) stays unconditional, exactly as it treats `relaysRefusingStrandAddr` today: a party-run relay registers its strand-addr handler late in its own `start()`, and this hook is the path that recovers it. With `identifyPush` on party-run relays the peer store list is updated when that handler registers, so the identify skip in the two passes is not stale for long; the hook covers the window.
- Keep `relaysRefusingStrandAddr` as is: it covers a relay whose identify has not run yet.
- Update `circuitRelayTargets`' doc and the `relaysRefusingStrandAddr` doc to mention the identify skip, and the "Delegate announce" bullet in `docs/architecture.md` (one clause: a relay whose identify lists no strand-addr is not asked).

Rejected: persisting the refusal in node-local state. It needs a store, invalidation when a relay is redeployed as a party-run relay, and a cleanup policy, while identify already carries the answer each process needs.

## Edge cases & interactions

- **Formation retried** (pending-join runner, or `dialFormationByMachine` moving to the next machine): each attempt opens and closes its own connection. Verified by inspection.
- **Reply lost / responder stalls**: the dialer's read times out and its `finally` closes the connection it opened. Verified by inspection of `withTimeout` (see Design 1).
- **Dial resolves after its deadline**: the late connection must be closed too if this dial opened it, not only the stream aborted. Inspection.
- **Two formations from this node to the same responder machine at once** (two pending joins on invitations from one inviter): libp2p's dial queue joins them onto one new connection; the first to finish sees the other's open formation stream and leaves the connection, the second closes it. Inspection; this is the case the WeakSet plus the open-stream check exist for.
- **Pre-existing connection** (same-party responder, or any connection opened before the dial): never closed by formation. Inspection.
- **Responder side**: no change; its handler already closes its stream. After the joiner closes the connection, the responder's FRET may still try to dial the joiner's control node from its routing table (the joiner's gate refuses strangers at the connection level). That is FRET's off-ring behavior, upstream; if the re-measurement shows such dials, record the counts in the complete ticket as evidence for `fret-maintenance-probes-peers-off-its-ring` (do not edit `../Fret`).
- **Relay identify not yet run at first launch**: the relay is asked once, as today; the refusal set then covers the rest of the process. Acceptable.
- **Party-run relay with strand-addr registered late**: skipped by the passes until identify-push updates its list; the supervisor's re-drive hook announces regardless. Same window as the existing refusal set has.
- **Relay connection drops and reconnects to a redeployed relay** with a different protocol set: identify on reconnect replaces the list. Inspection.
