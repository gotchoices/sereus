## What's already done (verify, don't redo)

All four pieces from the original ticket landed in `packages/cadre-core/src/control-database.ts`:

- `queryStrandStampId(strandId): Promise<string | null>` and
  `queryValidationKeyStampId(key): Promise<string | null>` — added right before
  `queryRevokedStamps`, mirroring `queryCadrePeerStampId`.
- `queryRevokedStamps`'s parameter widened from `'OwnerKey' | 'CadrePeer'` to
  `'OwnerKey' | 'CadrePeer' | 'ValidationKey' | 'Strand'`.
- `deleteStrand(strandId, ownerKey, signMessage)` — added right after `insertStrand`.
- `deleteValidationKey(key, ownerKey, signMessage)` — added right after `insertValidationKey`.

Both delete methods: read the row's current StampId via the new query methods, return
early (log + no-op) if null; build the `'remove'`-tagged message via
`buildAuthorizationMessage('CadreControl.Strand'|'CadreControl.ValidationKey', 'remove', [id, stampId])`;
sign it; `beginTransaction` → `delete ... with context OwnerKey = ?, Signature = ?` →
`insert into CadreControl.Revocation (TableName, StampId) values ('Strand'|'ValidationKey', ?)` →
`commit`, with the same rollback-swallow `catch` `SeedBootstrapService.removePeer`
(`seed-bootstrap.ts:460`) uses.

Tests added to `packages/cadre-core/test/control-authorization-binding.spec.ts` (appended
after the last `it(...)` in the describe block, right before its closing `});`, around
line 602 onward):

- `deleteValidationKey with a correct owner signature removes the row and leaves a matching Revocation tombstone`
- `deleteStrand with a correct owner signature removes the row and leaves a matching Revocation tombstone`
- `deleteValidationKey is a no-op (no throw, no tombstone) when the target row does not exist`
- `deleteStrand is a no-op (no throw, no tombstone) when the target row does not exist`
- `after a deleteStrand, queryRevokedStamps("Strand") contains the retired stamp`
- `deleteStrand on a closed strand carrying a real MemberPrivateKey succeeds (the remove digest binds only Id, StampId)`

Two new test-file helpers were added near the top of the describe block (next to
`inviteCount`): `revocationCount()` and `revocationRow(tableName, stampId)`.

`CadreNode.removeStrand` was deliberately NOT touched (out of scope per the original ticket
— it only stops the strand locally today; wiring in `deleteStrand` is a separate decision).
