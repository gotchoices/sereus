# Signed `deleteStrand` / `deleteValidationKey` writers on `ControlDatabase`

<!-- resume-note -->
Split out of `control-validationkey-strand-delete-authorization` when a prior run hit its budget
during investigation. No code has been written for either ticket. The prereq ticket adds the
schema constraints (`AuthorizedDelete`, `RevocationRecorded`, `NotRevoked`, `NoUpdate` on
`CadreControl.Strand` and `CadreControl.ValidationKey`, plus the matching `Revocation.RowIsGone`
branches); this ticket adds the code that can satisfy them.

## Why this is not optional

Without a writer, the new delete rules are reachable only through hand-built SQL in tests. The
byte-layout agreement between `buildAuthorizationMessage` (TypeScript) and the SQL `digest(...)`
call — the exact drift the `buildAuthorizationMessage` doc block warns about — would then go
untested from the production side. Every other guarded table has a real signed writer
(`SeedBootstrapService.removePeer` for `CadrePeer`, `deleteDeviceToken` for `DeviceToken`); these
two would be the odd ones out.

## Interface

Two new `ControlDatabase` methods, mirroring `insertStrand` / `insertValidationKey` in signature
and `SeedBootstrapService.removePeer` (`seed-bootstrap.ts:460`) in transaction shape:

```ts
async deleteValidationKey(
  key: string,
  ownerKey: string,
  signMessage: (message: Uint8Array) => string,
): Promise<void>

async deleteStrand(
  strandId: string,
  ownerKey: string,
  signMessage: (message: Uint8Array) => string,
): Promise<void>
```

Each one:

- read the row's current `StampId`; **return early if the row is absent**, mirroring `removePeer`'s
  `stampId === null` log-and-return;
- build the `'remove'`-tagged message via `buildAuthorizationMessage` — field vectors
  `['CadreControl.ValidationKey', 'remove', key, stampId]` and
  `['CadreControl.Strand', 'remove', strandId, stampId]`, matching the prereq ticket's SQL;
- `beginTransaction` → `delete from CadreControl.<T> with context OwnerKey = ?, Signature = ?` →
  `insert into CadreControl.Revocation (TableName, StampId) values ('<T>', ?)` → `commit`, with the
  same rollback-swallow `catch` and comment `removePeer` carries (a failed `commit()` already tears
  the transaction down, so `rollback()` would throw "No transaction active" and mask the real cause).

Supporting reads, mirroring `queryCadrePeerStampId` (`control-database.ts:425`):

- `queryStrandStampId(strandId: string): Promise<string | null>`
- `queryValidationKeyStampId(key: string): Promise<string | null>`

And widen `queryRevokedStamps`'s parameter (`control-database.ts:446`) from
`'OwnerKey' | 'CadrePeer'` to also accept `'ValidationKey' | 'Strand'`.

## Explicitly out of scope

`CadreNode.removeStrand` today only stops the strand locally (untrack, stop instance, emit) and
never touches the control row. **Do not** wire the new delete into it — that would change an
existing method's meaning and belongs to whoever wants that behavior.

## Tests

Extend `packages/cadre-core/test/control-authorization-binding.spec.ts` (its `CadreNode` +
founding-owner harness fits; the shared node is fine because these are happy paths that create
their own rows).

- `deleteValidationKey` with a correct owner signature removes the row and leaves a
  `Revocation` row with `TableName = 'ValidationKey'` and the row's old stamp.
- `deleteStrand` likewise, `TableName = 'Strand'`.
- Both are a no-op (no throw, no tombstone written) when the target row does not exist.
- After a `deleteStrand`, `queryRevokedStamps('Strand')` contains the retired stamp.
- A `deleteStrand` on a **closed** strand (one carrying a real `MemberPrivateKey`) also succeeds —
  the remove digest binds only `(Id, StampId)`, so the member key must not affect it.
