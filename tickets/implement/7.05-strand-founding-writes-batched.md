# The founder's strand rows land in one transaction

## What happens today (traced)

`bootstrapFounderMembership` on a fresh closed strand (`StrandDatabase.initialize` → `bootstrapFounder`):

1. `assertNotPreSplitStrand`: scans `Member` and `Manager` for the shared-key fingerprint. On a first founding neither table has rows, so it cannot match.
2. `foundIfHeaderAbsent`: counts `Header`; finds none; `createEmptyCollections()` commits an empty collection, one `sync()` each, for every tree the `Strand` and `App` schemas declare (13 for the chat schema: 8 strand tables, the 3 `StampId` unique trees of `Member`/`Manager`/`MemberPeer`, 2 app tables); then inserts `Header` (autocommit).
3. `insertFounderMemberIfAbsent`: counts `Member`, inserts (autocommit).
4. `insertFounderManagerIfAbsent`: counts `Manager`, scans `Revocation` for a sealed strand, inserts (autocommit).
5. After the runtime is built, the membership reconciler's first pass writes this machine's `MemberPeer` binding (another autocommit) through `registerMemberPeer`.

Seven of the 13 empty collections (`Header`, `Member`, `Manager`, `MemberPeer` and the 3 unique trees) are superseded within a second by steps 2–5, which write real rows into them. Everything is local on a solo founder; once the strand's storage cohort includes a sibling machine each commit is a two-member commit.

## Design

### One strand transaction for every founding row that is missing

`bootstrapFounderMembership` becomes: read state, then write once.

- **Read.** `Header` count. For a closed strand also `Member` count, `Manager` count (and the sealed `Revocation` scan only when `Manager` is absent, as today) and, when a peer id is given (below), whether this machine's `MemberPeer` row exists (`memberPeerStampId`). Keep every one of these reads: they are the insert-if-absent guards that make a re-run after a crash or a torn commit write only what is missing, and they are what makes the healing write append to a collection another machine may have created instead of inventing a second (see Edge cases).
- **Pre-split check only when the Header already existed.** A strand founded before the key split always has a Header (old code committed it first, alone), so `Header` absent at entry means no pre-split rows can exist. Run `assertNotPreSplitStrand` only when the `Header` count was non-zero.
- **Empty collections** (only when the Header is absent, as today, and before the write): for every table the founding will write on this run, skip its empty commit. See the plugin change below.
- **Write.** Assemble the missing rows' statements with `combineStatements` (each fragment uses its own named parameters) and run them through `execStrandTransaction(db, statements)` with the default `joinOpenTransaction` (true). That matches today's behaviour on the `foundExistingStrand` path, where the database may already be shared with the app; at `initialize` nobody else holds it. Statement order inside the batch stays Header → Member → Manager → MemberPeer, for readability.
- **`MemberPeer` joins the transaction.** `FounderBootstrapParams` gains `founderPeerId?: string`: this machine's strand transport peer id. `StrandDatabase.bootstrapFounder` (and the in-place founding path) pass `this.config.libp2pNode.peerId.toString()`, the same id the reconciler binds (`instance.libp2pNode?.peerId`, `strand-instance-manager.ts` ~970 — confirm they are the same node object). The fragment is the `registerMemberPeer` insert, signed with the founder key pair over `('Strand.MemberPeer', 'add', memberKey, peerId, stampId)`; extract a statement builder from `registerMemberPeer` so both share it. Optional because unit specs over a raw database have no transport; with it absent the bootstrap writes no binding and the reconciler does it later, as today. The reconciler is unchanged: its first pass on the founder finds the binding and stops.
- Open strand: unchanged in shape — `Header` only, now through the same path.

**Why this is constraint-compatible** (`schemas/strand.qsql`): every relevant CHECK has a subquery, so Quereus defers it to commit, where it sees the whole batch. `Member.Authorized`'s bootstrap branch needs `committed.Member` empty (the pre-transaction snapshot; true) and at most one live member. `Manager.Authorized`'s bootstrap branch needs at most one live `Manager` and `Member`, this manager to be that member (live table), and no `Manager` tombstone. `Manager.MemberExists` and `MemberPeer.MemberExists` read the live `Member` table. `MemberPeer.Authorized`'s add branch checks only the member's own signature. `Member`/`Manager` `OnlyClosed` read the live `Header`. The old "Header → Member → Manager must be separate commits in that order" is no longer needed; the order inside one transaction is enough. `strand-membership-network-transactor-parity.spec.ts` runs `openStrand('c', 'network')`, which goes through this bootstrap, so it is the gate that the batch commits over the network transactor.

### `createEmptyCollections` skips named tables

`packages/quereus-plugin-sereus/src/empty-collections.ts`:

```ts
export async function createEmptyCollections(
	db: Database,
	bridge: CollectionRegistrySource,
	schemaNames: readonly string[],
	except: readonly string[] = []   // qualified names, e.g. 'Strand.Header'
): Promise<number>
```

- A table in `except` is not opened and not asserted registered.
- In the sync loop, skip every registered collection whose id is that table's main collection id or starts with `<main id>/index/` (where the plugin keeps index and unique-enforcement trees; `optimystic-module.ts` ~3718). Filter by id, not by "was it opened here": the bootstrap's own count reads register those tables before this runs.
- An `except` entry naming no declared Optimystic table throws, so a renamed table cannot silently fall back to "commit everything".
- `SereusPluginResult.createEmptyCollections` (types.ts ~120, compose-strand.ts ~397) and `FounderBootstrapParams.createEmptyCollections` become `(except?: readonly string[]) => Promise<number>`. `ControlDatabase`'s genesis call (`control-database.ts` ~1821) passes nothing.
- The bootstrap passes exactly the tables it will write on this run: `Strand.Header` always; for a closed strand also `Strand.Member` and `Strand.Manager`, and `Strand.MemberPeer` only when `founderPeerId` is given. An insert writes every tree of its table (main and unique trees), so excluding the whole table is exact.

For the chat schema that is 6 empty commits and 1 founding transaction on a closed strand, instead of 13 + 3 (+1 from the reconciler); 12 + 1 on an open strand, instead of 12 + 1 + 1.

## Settled choices

- **No private batching of the remaining empty commits.** Committing several empty collections in one coordinator round needs an Optimystic plugin API; reaching into db-core's `TransactionCoordinator` would copy upstream internals. Measure the remaining cost; if it still matters, file `blocked/optimystic-empty-collections-commit-in-one-batch` with the figures, and update the NOTE on `createDeclaredCollections` to point at it.
- **The two `apply schema` catalog commits stay.** One catalog commit per apply is upstream's batching.
- **`control-collections-created-at-cadre-founding`** (landed) added the `schemaNames` parameter and the control genesis call (`ControlDatabase.commitEmptyControlCollections`). Keep both alongside the `except` parameter; the control caller passes no `except`.

## Edge cases & interactions

- **Crash or failure before the founding transaction commits.** The empty collections for the other tables are committed; the Header is absent; the next run commits none of them again (`syncInventedCollections` finds none invented) and retries the whole write. Same as today. Verify by inspection.
- **Torn founding commit** (a `PartialCommitError` / `CoordinatorPartialCommitError`: some of the batch's collections saved, others not). Before this change no founding commit could leave the Header committed beside a founding table with no collection, because the empty commits ran first. Now a torn report can, for example, save `Header` and `Member` but not `MemberPeer`. The error propagates out of `initialize`, the runtime rolls back, and the watcher's retry re-runs the bootstrap; the per-row guards see what was saved and write only the rest. A sibling machine of the same party (a storage replica holding the replicated party key) could meanwhile see `Member`, run its reconciler and create the `MemberPeer` collection with its own binding. The founder's healing run reads `MemberPeer` before writing it, and on the network transactor a read of a block missing locally asks the cohort, so it appends to the sibling's collection rather than forking it — unless the sibling is unreachable at that moment, which is the same exposure every non-founding write to a strand table already carries (docs/strands.md → "A table a later app schema version adds"). Record this as a `NOTE:` tripwire at the founding write: if torn founding commits are ever observed, commit the founding tables' empty collections before the batch again for the tables a sibling's reconciler writes. Verify by inspection.
- **Sealed strand restarted by its founder.** `Manager` absent, a `Manager` tombstone present: the sealed scan still skips the `Manager` row, and the batch carries only what else is missing (normally nothing). Covered by `strand-seal.spec.ts`; run it.
- **Pre-split strand.** Has a Header, so the check still runs; `strand-pre-split-founder.spec.ts` covers it.
- **Founder request on an instance first launched as a joiner** (`foundExistingStrand` → `ensureFounderBootstrap`). Same function, same batch, run against a live database; the reconciler may already be armed. A reconciler pass can only bind once it sees the member row, which arrives in the same commit as the founder's `MemberPeer` row, so it finds the binding present. If both ever insert the same `(MemberKey, PeerId)`, the second fails on the primary key and the reconciler's outer catch retries into a no-op. Covered by `publish-strand.spec.ts` ~621 and ~673; run it.
- **Open strand.** `except` is `['Strand.Header']`; nothing else changes.
- **Unit specs without a peer id.** `openStrand` and `strand-membership-writer.spec.ts` pass no `founderPeerId`; `MemberPeer` is then neither written nor excluded, and the existing MemberPeer specs keep their counts.
