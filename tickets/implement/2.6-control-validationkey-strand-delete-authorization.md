# Authorize `ValidationKey` and `Strand` deletes (and forbid their updates)

## Confirmed by reproduction

Ran against a real `CadreNode` control database (transaction profile, founding owner seated),
driving the real writers for the inserts and raw SQL for the attacks. Results:

| attempted write | result today |
| --- | --- |
| `delete from CadreControl.ValidationKey with context OwnerKey = null, Signature = null` | **accepted**, row gone |
| `delete from CadreControl.Strand with context OwnerKey = null, Signature = null` | **accepted**, row gone |
| `update CadreControl.Strand ... set Type = 'o', MemberPrivateKey = null` on a **consent-formed** strand, no signature | **accepted**, row rewritten |
| `update CadreControl.Strand ...` on an owner-signed strand, no signature | refused (`Authorized`) |
| `update CadreControl.ValidationKey ...`, no signature | refused (`Authorized`) |
| `delete from CadreControl.OwnerKey`, no signature (control) | refused (`RevocationRecorded`) |

## Root cause

A bare `constraint X check (...)` in Quereus covers **insert and update only**. Both
`ValidationKey.Authorized` and `Strand.Authorized` are bare, so neither table's delete is gated
by anything. `OwnerKey`, `CadrePeer`, `DeviceToken` and `FormationInvite` all say
`check on delete` explicitly, and `FormationUsage` says `check on update, delete (false)` — those
are the shapes to copy.

The consent-update finding is the same bare-check pattern, one action over. `Strand.Authorized`'s
second branch is

```sql
or exists (select 1 from FormationUsage FU where FU.StrandId = new.Id)
```

Because the constraint also covers UPDATE, that branch says: *any* row whose (post-image) `Id`
has a formation-usage record may be rewritten by anyone, with no signature. For a closed strand
that means flipping `Type` to `'o'` and nulling `MemberPrivateKey` — destroying the party's own
membership key for that network and dropping its read gate.

This matters for the fix itself, not just as a sweep note: turning the bare `Authorized` into
`check on insert` **without** also handling UPDATE would leave update completely ungated — strictly
worse than today. The two must be decided together.

## Sweep result

Checked every `CadreControl` table for the same pattern. `ValidationKey` and `Strand` are the only
two with an ungated delete. The remaining bare `check`s are non-authorization validity rules
whose tables already block update and delete elsewhere (`FormationInvite.TotalUses >= 0`,
`FormationUsage.Monotonic`, `FormationUsage.StrandExists`, `Strand.MemberKeyClosedOnly`), so they
need no change. `Revocation` has no authorization at all — that is separately tracked as
`bug-control-revocation-unauthenticated-writes` in `tickets/fix/`; do not fix it here.

## Impact, stated accurately

- **`Strand` — live data destruction.** `ControlDatabase.listStrands` (`control-database.ts:294`)
  is what tells a node which networks to participate in, and a closed strand's row carries
  `MemberPrivateKey`, the party's own membership key for that network. Deleting the row destroys
  it; the unsigned update destroys it in place.
- **`ValidationKey` — latent, not live.** Nothing reads this table for a decision today. The
  formation-disclosure check (`FormationUsage.Authorized`) verifies against `context.ValidationKey`
  supplied by the writer, not against this table; the only other reader is a row count in the web
  reference app's diagnostics. The original ticket's "dropping them disables that check" overstates
  present behavior — the table is a registry with no consumer yet. It still needs the rule, because
  the registry is the intended anchor for that check and an ungated delete would silently pre-empt it.

The attacker position is the same one the rest of the control-plane authorization work assumes: an
already-admitted cadre peer that can write to the party's control collection. No owner key, no
captured signature, no network position needed.

## Design

### Both tables get the `CadrePeer` treatment

Replace each bare `Authorized` with three named constraints, so each action fails under its own
name (the tests below assert by constraint name):

- `AuthorizedInsert check on insert (...)` — the existing `'add'`-tagged predicate, unchanged
  (including `Strand`'s `FormationUsage` consent branch, which is correct for insert).
- `AuthorizedDelete check on delete (...)` — an owner signature over a **distinct
  `'remove'`-tagged** digest bound to the stored row:
  - `digest('CadreControl.ValidationKey', 'remove', old.Key, old.StampId)`
  - `digest('CadreControl.Strand', 'remove', old.Id, old.StampId)`

  Same shape as `CadrePeer.AuthorizedDelete` / `OwnerKey`'s remove branch: row key plus the row's
  single-use `StampId`, which already pins the exact row instance. The distinct action tag is what
  stops an add approval being replayed as a removal.
- `NoUpdate check on update (false)` — mirroring `OwnerKey.NoUpdate` and
  `FormationInvite.Immutable`. Verified: **no writer anywhere in the repo updates either table** —
  `grep` for `update CadreControl.Strand` / `update CadreControl.ValidationKey` across
  `packages/` returns nothing, in `src` and in tests. Rotation is add-then-remove, exactly as for
  `OwnerKey`. This is also what closes the consent-update hole above.

Note `Strand.MemberKeyClosedOnly` stays bare; its update coverage becomes redundant once
`NoUpdate` lands, which is harmless. Leave it alone.

### Extend `Revocation` rather than inventing a second mechanism

Both tables carry a `StampId` whose `unique` constraint only holds over **live** rows, so once
deletes are authorized the original add approval — a signature that never expires — would verify
again after a delete and resurrect the row. `CadreControl.Revocation` already exists with a
`TableName` discriminator for exactly this. Extend it:

- `Revocation.RowIsGone` is a closed `or` over `TableName` values, so an unlisted name is refused
  outright. **It must gain `'ValidationKey'` and `'Strand'` branches, or the new
  `RevocationRecorded` checks below can never be satisfied and every delete deadlocks.** Land this
  edit in the same change, not after.
- Update the `TableName` column comment (`'OwnerKey' | 'CadrePeer'`) and the table's leading
  doc comment, which both enumerate the guarded tables.
- Each table gains the `OwnerKey`/`CadrePeer` pair:
  - `NotRevoked check on insert (...)` — refuse an insert naming a retired stamp.
  - `RevocationRecorded check on delete (...)` — the delete must carry the matching tombstone
    in the same transaction.

Interaction with `bug-control-revocation-unauthenticated-writes` (sequence 2.7, still in `fix/`):
that ticket will add an owner signature requirement to `Revocation` writes. Whichever lands
second updates the other's writers/tests. Nothing here needs to wait for it.

### Signed deleters: add them

The original ticket left this open. **Add them.** Without a writer, the new rules are reachable
only through hand-built SQL, and the byte-layout agreement between `buildAuthorizationMessage`
and the SQL `digest(...)` — the exact drift the `buildAuthorizationMessage` doc block warns
about — would go untested. Two new `ControlDatabase` methods, mirroring `insertStrand` /
`insertValidationKey` in signature and `SeedBootstrapService.removePeer` in transaction shape:

```ts
async deleteValidationKey(
  key: string,
  ownerKey: string,
  signMessage: (message: Uint8Array) => string,
): Promise<void>

async deleteStrand(
  strandId: string,
  ownerKey: string,
  signMessage: (message: Uint8Array) => string,
): Promise<void>
```

Each one: read the row's current `StampId`, return early if the row is absent (mirroring
`removePeer`'s `stampId === null` log-and-return), build the `'remove'`-tagged message via
`buildAuthorizationMessage`, then `begin` → `delete` → `insert into Revocation` → `commit` with
the same rollback-swallow comment `removePeer` carries.

Supporting reads, mirroring `queryCadrePeerStampId`:

- `queryStrandStampId(strandId)` and `queryValidationKeyStampId(key)`.
- Widen `queryRevokedStamps`'s parameter from `'OwnerKey' | 'CadrePeer'` to also accept
  `'ValidationKey' | 'Strand'`.

`CadreNode.removeStrand` today only stops the strand locally (untrack, stop instance, emit) and
never touches the control row. **Do not** wire the new delete into it — that would change an
existing method's meaning and is outside this ticket.

## Tests

Extend `packages/cadre-core/test/control-authorization-binding.spec.ts` (its `CadreNode` +
founding-owner harness is already exactly right) unless a new file reads better. Every rejection
assertion must name the constraint, e.g. `rejects.toThrow(/AuthorizedDelete/)`.

- unsigned delete of a `ValidationKey` row → `AuthorizedDelete`
- unsigned delete of a `Strand` row → `AuthorizedDelete`
- an `'add'` approval for the row replayed as its delete → `AuthorizedDelete` (action-tag separation)
- a valid remove signature for row A transplanted onto row B → `AuthorizedDelete`
- an owner-signed delete with **no** sibling `Revocation` row → `RevocationRecorded`
- re-insert of the removed key/id replaying the original add approval and its retired stamp →
  `NotRevoked` (the resurrection case)
- unsigned update of a **consent-formed** strand (`insertFormationInvite` + `redeemInvitation`,
  then `set Type = 'o', MemberPrivateKey = null`) → `NoUpdate` — this is the regression guard for
  the second hole and passes today, so it must fail before the fix
- unsigned update of a `ValidationKey` row → `NoUpdate`
- happy path: `deleteValidationKey` / `deleteStrand` with a correct owner signature remove the row
  and leave a `Revocation` tombstone

`control-schema-drift.spec.ts` must stay green — mirror every schema edit into **both**
`schemas/control.qsql` and `packages/cadre-core/src/control-schema.ts`.

## Tripwire to record while here

`Revocation`'s existing doc comment already notes that `NotRevoked` is a per-transaction check
against *locally visible* rows, so a not-yet-converged node can still accept a replayed add and
end up holding the resurrected row alongside its tombstone. `CadrePeer` has a read-side mitigation
for this (`CadreNode.listAuthorizedMembers` drops rows whose stamp is retired); `ValidationKey` and
`Strand` will not. Do **not** build read-side filters here — there is no per-request authorization
surface for either table today. Add a `NOTE:` comment at the new `Strand.NotRevoked` constraint
saying so, so a future reader meets it at the site.
