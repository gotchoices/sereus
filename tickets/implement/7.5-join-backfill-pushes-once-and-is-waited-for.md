# Join backfill pushes each block once per peer, and the joiner waits for it

## Background

`PeerJoinBackfill` (`peer-join-backfill.ts`) copies every committed block in a network's local store to each peer that identifies as speaking that network's block-transfer protocol. One instance per strand network, one for the control network (gated on membership). Today it remembers only one thing per peer: "caught up" (`done`), set after a run with no thrown push **and** no block the receiver refused.

Measured (`message-cost-accounting`, 2026-10-19/20 baselines in that file's doc comment) and traced while planning:

- A receiver running Optimystic's default `requirePushCertificate: true` refuses any block pushed without a retained commit proof. One refused block leaves the peer un-memoized, so every later `peer:identify` (identify-push fires on any address or protocol change) re-pushes the whole store. GitHub Optimystic#39 shows a 33-block `reason=replication` frame twice per join, one taking 8 s over a public relay.
- The joiner, once the founder's push has landed, runs its own catch-up toward the founder and pushes those same blocks back.
- `forceCatchUpPeer` (the control network's cadre-invitation path) re-pushes the whole store even to a peer that already holds it.
- The control gate (`authorizePeer` → `CadreNode.isAuthorizedMember`) runs a full membership query per run, and every membership refresh re-schedules every connected peer not yet caught up.
- The joiner's first first-sync probe runs right after its database builds, and on a first join reads `Strand.Header` and each `App` table from the founder block by block (`sync` streams B→A in the `B addStrand` phase), while the founder's push of the same blocks is still on its way.

## Design

### Per-peer, per-block memo

Replace the bare `done` set's role as the only memory with a per-peer record:

```ts
interface PeerMemo {
	/** blockId → highest revision this peer accepted from this node. */
	accepted: Map<string, number>;
	/** blockId → revision this peer refused (its `missing` list). Not re-pushed until the local revision moves past it. */
	rejected: Map<string, number>;
}
```

A run, for each committed, materialized block with local `latest.rev`, skips the block when any of these holds, counting it in a new `PeerJoinBackfillResult.alreadyHeld`:

- `accepted.get(id) >= rev`
- `rejected.get(id) >= rev` (a refusal is a per-block verdict: logged once when it happens, not retried on every identify)
- the retained commit proof for that revision, which the run already reads to attach (`storage.getBlockProof(blockId, rev)`), has `proof.commits[peerId]?.type === 'approve'` (see next section)

Otherwise the block is pushed as today. On the reply, each id not in `missing` goes into `accepted` at the pushed revision, each id in `missing` into `rejected`. A chunk that throws records nothing for its blocks.

`done` stays, with a new meaning: the peer is caught up once a run finishes with **no push that threw** (and was not denied, and the store is listable). Refusals no longer keep a peer un-memoized, because they are now remembered per block. Consequences:

- A backoff retry after a failed push re-sends only the blocks not yet accepted, so a run that dies mid-store resumes where it stopped.
- `forceCatchUpPeer` still forces a run past `done` and past an in-flight run, but the run skips memoized blocks; for a peer that already holds everything it pushes nothing and returns with `alreadyHeld` equal to the store size. `admitRedeemingDevice` keeps working unchanged (a device being admitted has no memo, so it gets the whole store).
- `peer:identify` churn for a `done` peer is still dropped before any work, as today.
- The memo lives for the runtime, exactly like `done` today; nothing is persisted.

Update the module comment's RETRY section, which currently explains why refusals keep a peer un-memoized; that reasoning is replaced by the per-block verdict. Update the `catchUpPeer`/`forceCatchUpPeer`/`settleRun` docs and the `maxBlocks` `NOTE:` accordingly (memoized blocks are not offered, so they do not count toward `maxBlocks`).

### "This peer already signed it" replaces "this block came from that peer"

The plan asked that a block received from peer P not be pushed back to P. Sereus cannot see where a block came from: Optimystic's receiver reports the sender only to its own rebalance monitor (`BlockTransferService.reportSenderHolds` → an internal `BlockHoldersSink`), and no node option exposes it to an embedder. The commit proof is the available evidence instead. A block's proof lists, in `commits`, the cohort members that signed the commit round for that exact revision. A solo commit's proof is signed by the writer alone. So:

- Founder writes alone → proof signed by the founder → the joiner, holding that block after the founder's push, does not push it back to the founder.
- Founder and joiner commit together later → proof signed by both → a forced run on either side skips it.
- The joiner's own commit made alone → signed by the joiner only → still pushed to the founder. This keeps the restart-delivery role the module's kvStore `NOTE:` relies on.

Tradeoff, accepted: a signer that crashed between signing and applying, or later lost its store, is not re-sent that revision by this path; read repair covers its reads, as for any block a cohort member lacks. A block with no retained proof falls back to the memo (pushed once; the default receiver refuses it and that verdict is remembered). An exact "who holds what" would need Optimystic to expose its holder evidence to embedders. Do not file that unless the measurement below shows pushes this rule misses.

### Push on first contact

A peer this instance has never started a run for (track a `contacted` set, separate from the memo) is run immediately on its first schedule, with no debounce. Later schedules for it use the debounce as today (1 s strand, 250 ms control). Churn during that first run already lands in `rearmAfterFlight`, so one identify burst still produces one run. Applies to both networks. On the control network the first-contact run is usually denied (the join order is connect-then-authorize), which is now cheap (next section), and the membership refresh re-drives it as today.

### Control gate from the in-memory member set

`startControlBackfill`'s `authorizePeer` becomes `admittingDevices.has(peerId) || authorizedControlPeers.has(peerId)`. That set is what `refreshAuthorizedControlPeers` materializes from the same rows and the same `authorizedAmong` rule `isAuthorizedMember` queries, and that refresh is what calls `scheduleConnectedPeers()`, so the set is already updated when a membership change re-drives the backfill. Do **not** use `isControlNetworkMember`: it admits everyone while the set is empty, and it admits bootstrap/relay peers unconditionally, neither of which may receive the control store. Keep the gate async-shaped (the dep's type does not change). Update the `NOTE:` in `refreshAuthorizedControlPeers` (~2950): a re-armed pass no longer costs a `CadrePeer` query.

### The joiner waits for the push on a first join

In `StrandInstanceManager.buildStrandDatabase`, a non-founder launch whose strand raw store holds no blocks at the first-probe point (the first value of `storage.listBlockIds()` is absent) skips `gate.probeOnce()` and goes straight to `gate.start()`. The gate then probes when the push lands (the storage change feed) or at its 2 s backstop, whichever is first. A launch over a store that holds anything (restart, hibernation resume, a push already landed) probes at once as today, so offline-first re-attach is not delayed. A store without `listBlockIds` probes at once as today. Worst case on a first join with no push coming: the first probe is 2 s later than today.

Document in docs/strands.md "How a gated launch probes", one sentence.

## Edge cases & interactions

- **Push larger than one chunk** (64 blocks / 1 MiB): a chunk that throws leaves its blocks out of `accepted`; the backoff retry pushes only those and later blocks. Verified by the spec.
- **Local revision moves after a push**: the memo holds the pushed revision, so a later forced run sends the newer one. A refused block whose revision moves is offered again. Verified by the spec (the refusal half).
- **Peer store wiped under the same peer id** (a strand transport id is derived from the machine identity and strand id, so a machine that deleted its strand storage and rejoins comes back with the same id): the memo, and the proof-signer rule, skip blocks it no longer has, for the rest of this runtime. Same as `done` today. Reads are served by fetch. Nothing in Sereus identifies a store separately from its peer id. Record as a `NOTE:` on the memo with the revisit condition "if a machine can rejoin a strand with an emptied store while other members' runtimes stay up, and must hold blocks physically before its first read, clear the peer's memo on a full disconnect".
- **Memo size**: at most (blocks in store, capped by `maxBlocks` 10 000) × (peers ever identified this runtime) small entries. `NOTE:` with the bound; if a strand's peer count grows into the hundreds (open strands), drop a peer's memo on `peer:disconnect`.
- **Concurrent runs**: still one run per peer (`inFlight`). A forced run waiting out an in-flight run sees that run's memo entries and skips those blocks. Inspection.
- **Denied run**: records nothing, does not set `done` or `contacted`-only state that would suppress the membership re-drive. A peer denied on first contact and authorized later gets the whole store. Covered by the existing gate specs (adjust if they count pushes).
- **Stopped mid-run**: as today; blocks of an unflushed chunk are not memoized.
- **Slow relay**: pushes stay sequential per peer; do not add concurrency. Fewer and smaller pushes are the whole gain.
- **Control vs strand**: both use the same class; the control instance keeps its 250 ms debounce for repeat schedules and its gate. The cadre-invitation path (`admitRedeemingDevice` → `forceCatchUpPeer`) must still push the whole store to a device with no memo: covered by `cadre-node-control-backfill.spec.ts`; keep it green.
- **Proof signer ids**: proof `commits` are keyed by the peer ids of the network the commit ran on, which are the same ids this instance pushes to (strand transport ids on a strand network, control node ids on the control network). Inspection.

## Tests

Rewrite, do not add beside, the existing specs whose contract this changes: "lands remote-reported missing ids in rejected and does NOT mark the peer done — a second run retries" and "does not re-arm when the receiver REFUSED the blocks" in `peer-join-backfill.spec.ts`. One spec over the memo's branching, at the `PeerJoinBackfill` level with the existing in-memory storage and captured `createPushClient` the file already uses (no mocking of Optimystic's block-transfer service):

- a forced second run after a clean run pushes nothing; `alreadyHeld` equals the blocks offered the first time;
- a block the receiver refused is not pushed by a forced second run, and is pushed once its local revision moves;
- a block whose stored proof has `commits[<peer>] = { type: 'approve' }` is not pushed to that peer, and is pushed to another peer;
- after a mid-run chunk failure, the retry pushes only the blocks not accepted.

One assertion in an existing debounce spec that a never-contacted peer runs without waiting `debounceMs`. No new test for the control gate swap or the joiner's skipped first probe (wiring; the scenarios below exercise both).
