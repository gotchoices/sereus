# A wake that lands during a quiesce must wait for it and rebuild

## The defect

`StrandInstanceManager.quiesceStrand` releases a strand's runtime through `releaseRuntime`, which awaits several teardown steps (peer-book swap stop, reconciler settle, database close, node stop) and only clears `instance.database` / `instance.libp2pNode` near its end. Nothing marks the strand as "being quiesced" while that runs, and its callers set status `'hibernating'` only after it returns:

- `CadreNode.runWakeWindow` (end of a check-in or `serviceWake` window with no activity): the strand reads `'active'` during the quiesce.
- `CadreNode.handleStrandHibernate` (timer-driven hibernate from `'idle'`, and the mobile `hibernateStrand` / `hibernateAll`): the strand reads `'idle'` or `'active'` during the quiesce.

A wake during that await — `wakeStrand`, a push-wake, or activity on an `'idle'` strand (`HibernationManager.recordActivity` → `beginWake`) — reaches `handleStrandWake`, sees handles still attached, takes the already-live branch (sets the live status, emits `strand:waking`) and resolves. The quiescer then finishes and writes `'hibernating'`. The waker (a push-wake, `wakeHostStrandForFormation`, the founder `needs-resume` path, the app) was told the strand is up; it is asleep. Activity recorded on an `'active'` strand during the window's quiesce does not wake at all — it only reschedules the idle timer — so that activity is lost the same way. The timer-driven case additionally leaves the wake's freshly armed idle countdown running on a hibernating strand.

Found while fixing `strand-probe-failure-cleanup-owns-only-its-resume` (the `runWakeWindow` arm); `handleStrandHibernate` is the same class at a sibling site. Not run: confirm with a `StrandInstanceManager`- or `CadreNode`-level test where `quiesceStrand` is held open (a deferred promise in the fake, or a real manager whose node stop is delayed) and a `wakeStrand` is issued meanwhile; expected today: the wake resolves and the strand ends `'hibernating'` with no handles.

## Required behaviour

A wake that lands while a quiesce is in flight must end with the strand live (or with the wake's own error), never resolve over a strand that is about to be asleep. The quiescer's final status write must not overwrite a status a later resume has set.

## Recommended shape (one mechanism, covers every quiesce caller)

Make an in-flight quiesce visible and ordered against resume inside `StrandInstanceManager`, mirroring how `runtimeBuilds` / `settleRuntimeBuilds` order a resume after a build:

- `quiesceStrand` tracks its release per strand (a `quiescesInFlight` map) and, as the last step *inside* the tracked operation, sets `instance.status = 'hibernating'` itself. Callers stop writing `'hibernating'` after it returns (`runWakeWindow`, `handleStrandHibernate`). `rehibernateAfterFailedResume` still writes `'hibernating'` because its quiesce may be a no-op (a failed build already released its runtime) or may throw.
- `runResume` waits for an in-flight quiesce before its "already live" check, exactly as it waits for `runtimeBuilds`. Because the status write happens inside the tracked quiesce, the resume's `'starting'` write always comes after it.
- `handleStrandWake`'s already-live branch is skipped while a quiesce is in flight (a small `strandManager.isQuiescing(strandId)`), so the wake takes the rebuild path and joins or starts a resume that waits for the quiesce.
- Consider making `quiesceStrand` also wait for an in-flight runtime build (`settleRuntimeBuilds`) before releasing, so no caller can tear down a node a build is still wiring. After the prereq no caller does this, so treat it as optional hardening and say in the review handoff whether it was done.

The narrower alternative — `runWakeWindow` re-reads `lastActivity` after its quiesce and resumes if it moved — was rejected: it leaves the waker's "up" answer false for the length of a rebuild, misses probe wakes that record no activity, and does nothing for `handleStrandHibernate`.

Timers: after this change a wake that lands during a timer-driven hibernate settles with the strand live and rearms the idle countdown; `HibernationManager.handleHibernateTimeout` then schedules a check-in chain on a live strand once `onHibernate` resolves. Guard that `.then` to schedule only if the strand still reads `'hibernating'` (the wake's settle has already armed the right timers otherwise).
