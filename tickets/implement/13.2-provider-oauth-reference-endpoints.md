# OAuth 2 authorization code with PKCE, and the provider descriptor

Second ticket of the `provider-client-and-sign-up` chain. The client half (PKCE generation, the code exchange, the token source) is `cadre-core-provider-client-and-rent-node`; it follows the wire shapes fixed here.

## Why these endpoints live in cadre-provider

An operator runs cadre-provider behind their own account and checkout pages. The app needs a token scoped to one customer's containers, obtained without the app ever seeing the customer's password or card. OAuth 2 authorization code with PKCE (RFC 6749 and RFC 7636) is the standard for a public client such as a phone app. The provider package ships a reference implementation of the two endpoints so an operator gets them by configuration and plugs their account system in through one hook; an operator with an identity provider of their own keeps using `AuthHooks.validateJwt`.

## Configuration

```yaml
auth:
  mode: oauth
  oauth:
    clients:
      - clientId: sereus-chat
        redirectUris: ["sereus-chat://provider-auth", "sereus-chat-second://provider-auth"]
        scopes: ["containers:*", "billing:read"]   # the most a token for this client may carry
    accessTokenTtlSec: 3600       # default
    refreshTokenTtlSec: 2592000   # default, 30 days
    devConsentPage: false         # true serves the built-in consent form; needs allowInsecureNoAuth: true
provider:
  id: acme-nodes                  # stable, what an app's rental records are keyed by
  name: Acme Cadre Nodes
  publicUrl: https://nodes.acme.example   # the origin this API is reached at; the descriptor derives every URL from it plus server.basePath
  termsUrl: https://acme.example/terms    # optional
  regions: ["eu-west"]            # optional
  icon: https://acme.example/icon.png     # optional
```

Checked by the strict schema (`config/schema.ts`), with environment forms for the scalars (`PROVIDER_OAUTH_DEV_CONSENT_PAGE`, `PROVIDER_PUBLIC_URL`, `PROVIDER_ID`, `PROVIDER_NAME`; clients are file-only). Rules: `auth.oauth` is allowed only with `mode: oauth`; `clients` non-empty, each `clientId` unique, each redirect URI an absolute URL with no fragment (custom schemes allowed, `http` only for a loopback host); `devConsentPage: true` requires `auth.allowInsecureNoAuth: true`, since the dev page lets anyone type a customer id and get a token for it, the same openness `mode: none` acknowledges with that flag. `provider` is optional, but `GET /descriptor` answers 404 `NOT_CONFIGURED` without it, and `check` says so. `publicUrl` must be `https` except for a loopback host.

## Endpoints

All under `server.basePath`, unauthenticated (the auth preHandler skips them by exact path, as it skips `/status`):

- `GET /oauth/authorize` with `response_type=code`, `client_id`, `redirect_uri`, `scope` (space-separated), `state`, `code_challenge`, `code_challenge_method=S256`. Validation order: the client must be registered and the redirect URI must match one of its registered URIs exactly, else a 400 HTML page naming the problem and no redirect (redirecting to an unregistered URI is the attack). Every other fault (`plain` challenge method, a challenge outside 43 to 128 base64url characters, an unknown scope, a scope outside the client's allowance, a missing state) redirects to the registered URI with `error=invalid_request` (or `invalid_scope`) and the state. Then the customer is resolved:
  - `AuthHooks.authorizeCustomer?(request: AuthorizationRequest): Promise<AuthorizationDecision>` where `AuthorizationRequest` is `{ clientId, scopes, headers, query }` (the operator's site reads its session cookie from `headers`) and `AuthorizationDecision` is `{ customerId, planId? }`, `{ redirect: string }` (send the browser to the site's login or checkout, which brings it back to the same authorize URL afterwards) or `{ deny: string }` (redirects with `error=access_denied`). The hook is the only place the operator's account system touches the provider.
  - Without the hook and with `devConsentPage: true`: an HTML form (`oauth-consent-page.ts`, no templating dependency, every value HTML-escaped) showing the client id and scopes, a customer id field, a plan select from `BillingService.listPlans()`, Approve and Deny. It posts to `POST /oauth/authorize` with the authorize parameters as hidden fields plus `customer_id`, `plan_id`, `decision`.
  - Neither: 500 `NOT_CONFIGURED` at start time, not request time: `registerAuth` refuses `mode: oauth` with `auth.oauth` set but no `authorizeCustomer` hook and no dev page.
  - A customer with no billing record gets one on the first code issued (`BillingService.initializeCustomer(customerId, planId)`), so `GET /billing/status` answers for every signed-in customer.
  - Issue: 32 random bytes base64url as the code; store `{ codeHash: hashApiKey(code), clientId, customerId, scopes, codeChallenge, redirectUri, expiresAt: now + 10 min }`; redirect to `redirect_uri?code=…&state=…`.
- `POST /oauth/token`, form-encoded (add `@fastify/formbody`) or JSON:
  - `grant_type=authorization_code` with `code`, `code_verifier`, `client_id`, `redirect_uri`: take the code record (get-and-delete, so a code is single-use); `invalid_grant` when unknown, expired, for another client or redirect URI, or when base64url(SHA-256(verifier)) differs from the stored challenge (`pkce.ts`, Node `crypto`). Mint an access token (32 random bytes base64url) stored as an `ApiKey` record `{ keyHash, customerId, name: 'oauth:<clientId>', permissions: scopes, createdAt, expiresAt }` and a refresh token record `{ tokenHash, clientId, customerId, scopes, accessKeyHash, expiresAt }`. Answer `{ access_token, token_type: 'Bearer', expires_in, refresh_token, scope }` with `Cache-Control: no-store`.
  - `grant_type=refresh_token` with `refresh_token`, `client_id`: take the record (rotation: the old refresh token is gone after one use), delete the old access key, mint a new pair with the same scopes; `invalid_grant` when unknown, expired or for another client.
  - Errors as RFC 6749 §5.2: 400 JSON `{ error, error_description }` with `invalid_request`, `invalid_client`, `invalid_grant`, `unsupported_grant_type`.
- `GET /descriptor` (public): the provider descriptor, the document an app's store screen renders:

```json
{
  "v": 1,
  "id": "acme-nodes",
  "name": "Acme Cadre Nodes",
  "apiBaseUrl": "https://nodes.acme.example/api/v1",
  "oauth": { "authorizeUrl": "https://nodes.acme.example/api/v1/oauth/authorize", "tokenUrl": "https://nodes.acme.example/api/v1/oauth/token", "scopes": ["containers:*", "billing:read"] },
  "plansUrl": "https://nodes.acme.example/api/v1/billing/plans",
  "termsUrl": "https://acme.example/terms",
  "regions": ["eu-west"],
  "icon": "https://acme.example/icon.png"
}
```

The descriptor carries no client id: each app has its own registered client, and the app pairs a descriptor with the client id it registered. `oauth.scopes` is the union of the clients' allowances. Where an app gets descriptors from is `tickets/blocked/decide-provider-directory.md`; this route is the source every option in that ticket can read from.

## Bearer validation in `oauth` mode

`registerAuth`, mode `oauth`: hash the bearer and look it up as an `ApiKey` record; an expired record is deleted and treated as absent. Not found and `hooks.validateJwt` present: the hook, as today. This lets one provider serve built-in tokens and an external identity provider at once; the README says built-in tokens are consulted first.

## Store

`ProviderStore` gains `saveAuthorizationCode`, `takeAuthorizationCode(codeHash)` (returns and deletes), `saveRefreshToken`, `takeRefreshToken(tokenHash)`, implemented in `MemoryStore` and `FileStore` (two more collections in its cache and files). Secrets are stored hashed, as API keys are; the raw code and tokens exist only in the redirect and the token response.

## Edge cases & interactions

- The redirect URI comparison is exact string equality after no normalization; the registered list is what makes that safe. Table test.
- The authorize page's HTML never reflects `redirect_uri` or `state` unescaped; the dev page escapes every value. By inspection, plus the 400 page test with a `<` in the client id.
- A code presented twice: the second call gets `invalid_grant`; the tokens from the first use are not revoked (RFC 6819 recommends it; NOTE at the site: add revocation if a leaked code is ever a worry, since a code lives 10 minutes and needs the verifier).
- Refresh with a token whose access key was already deleted (clock skew, a crash between the two deletes): still rotates; the access-key delete is best-effort.
- `allowInsecureNoAuth` already exists for `mode: none`; reusing it for the dev consent page keeps one acknowledgement for "this provider is open". Config test.
- The billing record created at sign-in means `canCreateContainer` applies the chosen plan's `maxContainers` from the first create. By inspection of `BillingService.canCreateContainer`.
- Fastify's form-body parser is registered once in `createProviderServer`; JSON bodies on the token endpoint keep working, since clients built on `fetch` with a JSON body are common.
- `basePath` changes move the OAuth routes with the API; the descriptor is computed at request time from the config, so it never disagrees with the registered routes.

## Tests (`packages/cadre-provider/src/server/__tests__/oauth.test.ts` and config tests)

Fastify `inject`, `MemoryStore`, `MockOrchestrator`, a fake `authorizeCustomer` hook:

- Round trip: authorize with a known verifier's S256 challenge → code in the redirect with the state → token → the bearer passes `GET /containers` and is refused on `DELETE` when the scope is `containers:read` only. Expected: 302 then 200 `{ access_token, refresh_token, scope }`, then 200 and 403.
- Wrong verifier → 400 `invalid_grant`; the same code again → `invalid_grant`.
- Unregistered redirect URI → 400 HTML, no `Location` header.
- Refresh rotates: the first refresh succeeds, the old refresh token then fails, the old access token no longer authenticates.
- Config: `devConsentPage: true` without `allowInsecureNoAuth` fails validation; `auth.oauth` under `mode: api-key` fails; `publicUrl: http://nodes.acme.example` fails and `http://127.0.0.1:3000` passes.
- `GET /descriptor`: the URLs are `publicUrl + basePath + route`; 404 without the `provider` block.
