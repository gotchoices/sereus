# Context: what this closes

Deleting a `CadreControl.OwnerKey` or `CadreControl.CadrePeer` row used to free its one-off
`StampId` nonce, so the original add-approval signature (which never expires, and which rides
to every replica — for `CadrePeer` it is even stored on the row as `VouchSig`'s sibling
context) verified again: anyone who kept a copy could re-seat a removed owner or peer
verbatim. Fix: an append-only `CadreControl.Revocation` table retires `(TableName, StampId)`
on removal; guarded tables refuse an insert naming a retired stamp (`NotRevoked`) and refuse
a delete that doesn't retire one (`RevocationRecorded`). Legitimate re-adds mint a fresh
stamp per insert, so they are unaffected.

## B. New spec — `packages/cadre-core/test/control-revocation-replay.spec.ts`

Real `CadreNode` per test, exactly the shapes of `control-ownerkey-self-authorization.spec.ts`
(copy its `bootFreshParty` / `inTransaction` / `expectConstraintFailure` / `freshKeyPair` /
`signAs` / `stampIdOf` helpers; assert by constraint NAME). For `CadrePeer` raw inserts copy
the 8-column insert shape from `control-authorization-domain-separation.spec.ts` (~line 190)
— `AuthorizedInsert` requires `VouchOwner`/`VouchSig` to equal the context pair. Sign
`CadrePeer` digests with `signB64` over `cadrePeerVoucherDigest`/`cadrePeerRemoveDigest`
(peer-authorization.ts); sign `OwnerKey` digests with `signAs` over
`buildAuthorizationMessage('CadreControl.OwnerKey', 'add'|'remove', [key, stamp])`.
Tombstone helper: `insert into CadreControl.Revocation (TableName, StampId) values (?, ?)` —
no `with context` clause (the table declares none).

Cases:
- `OwnerKey`: founder enrolls K (CAPTURE enrollSig + stamp) → signed remove + tombstone in
  one transaction → replay the captured enrollment insert verbatim → refused `NotRevoked`;
  owner set unchanged. (Only `NotRevoked` fails — the signature still verifies — so the name
  is unambiguous.)
- `CadrePeer`: same shape with an admission (capture vouchSig + stamp) → signed remove +
  `('CadrePeer', stamp)` tombstone → verbatim replay refused `NotRevoked`; row absent.
- Both tables: a SIGNED delete with no tombstone → refused `RevocationRecorded`; row
  survives.
- Both tables: after removal, a re-add with a FRESH stamp + fresh signature SUCCEEDS
  (removal is stamp-retirement, not an identity ban).
- `Revocation`: tombstoning a LIVE row's stamp (no accompanying delete) → refused
  `RowIsGone` (cover both TableName branches); a tombstone whose TableName is neither
  'OwnerKey' nor 'CadrePeer' is also refused by `RowIsGone` (both branches false).
- `Revocation`: insert a tombstone for a never-existing stamp (allowed, harmless — stamps
  are 32-byte CSPRNG), then `delete` it → `Immutable`; `update` it → `Immutable`.

## C. Update `control-ownerkey-self-authorization.spec.ts` (7 `rawDeleteOwnerKey` uses)

Keep `rawDeleteOwnerKey` bare. Add a `tombstoneOwnerKeyStamp(stampId)` primitive (the
Revocation insert above). Per test:

- "accepts: a pre-existing owner removes ANOTHER owner" (~244): wrap the existing signed
  delete + `tombstoneOwnerKeyStamp(stamp)` in `inTransaction` (the stamp is already read).
- "rejects: an unsigned delete of one owner while two exist" (~317): read the target's
  stamp, then `inTransaction { bare delete; tombstone }`, still asserting `Authorized`.
  Rationale: with the tombstone alongside, `RevocationRecorded` is satisfied and the ONLY
  failing constraint should be the authorization one — assertion stays strong instead of
  adding `RevocationRecorded` to the alternatives.
- "rejects: an unsigned delete of the LAST owner" (~326): same wrap (founder's stamp);
  alternatives stay `MinOneOwner`, `Authorized`.
- "rejects: a signed mutual removal ... (MinOneOwner floor)" (~339): add BOTH tombstones
  inside the existing transaction (stamps already read); assertion stays `MinOneOwner` only.
- "rejects: an owner signing its OWN removal" (~367): wrap + tombstone; stays `Authorized`.
- "rejects: unsigned delete-of-founder + insert-of-attacker" (~391): add founder-stamp
  tombstone inside the existing transaction; stays `Authorized`.
- "rejects: an ENROLLMENT signature replayed as a removal" (~406): wrap + tombstone; stays
  `Authorized`.

**Empirical fallback** (the one open question): the prior prototype confirmed the delete and
tombstone see each other at commit in a SUCCESSFUL transaction, but for a REJECTED delete it
is unverified whether `RowIsGone` evaluates against the view with the delete applied
(expected: yes → passes → only the auth constraint reports) or the pre-delete view (then
`RowIsGone` co-fails). If a rejected-delete test fails on the constraint name, add
`RowIsGone` to that test's accepted alternatives — the deferred queue does not promise
report order. Do NOT silently switch to bare deletes + `RevocationRecorded` alternatives
without noting it in the handoff (it weakens what the tests pin).
