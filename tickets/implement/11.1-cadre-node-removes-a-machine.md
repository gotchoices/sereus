# Remove a machine from a cadre

## What exists

- `CadreNode.removePeer(peerId)` deletes one `CadrePeer` row plus its `Revocation` tombstone (`ControlDatabase.deleteCadrePeer` → `deleteGuardedRow`, through the membership hub `mutateCadrePeer`), queues the tombstone for re-issue when committed alone (`noteGuardedDelete`), and forgets the peer's dial entry (`bootstrapPeerStore.forget`).
- `CadreNode.removeOwner(key)` deletes one `OwnerKey` row plus tombstone (`ControlDatabase.deleteOwnerKey`), refusing by name self-removal and the last live owner.
- `CadreNode.addOwner`, `reauthorizePeer` (`SeedBootstrapService.reauthorizePeer` → `ControlDatabase.reauthorizeCadrePeer`, which rebinds `VouchOwner` to this node's key and clears `VouchUsage`), `listCadreInvitations`, `withdrawCadreInvitation` (`ControlDatabase.withdrawCadreInvite`).
- A machine's owner key is its own identity key: an owner-granting invitation seats `OwnerKey.Key = CadreInviteUsage.PeerKey = CadrePeer.PublicKey`, and `enrolledOwnerSigningKey` signs owner writes with `getSelfSigningKey()`. So "this machine is an owner" means "the ed25519 key behind its peer id is a live `OwnerKey`".
- The anchor rule (`owner-anchor-sync.ts`, docs/architecture.md → "How the anchor follows the owner table"): when an owner is removed, every `CadrePeer` row it vouched (or admitted through an invitation it issued) stops passing the membership predicate on every machine, because `VouchOwner` is judged against the anchor. An owner it added keeps its anchor place where it was already derived, and cannot be derived on a machine that never held it, until a remaining owner re-adds it.
- `schemas/control.qsql`, `CadrePeer.AuthorizedInsert` comment: "A removed device may redeem a still-live invitation again and come back: keeping a device out is removing its row AND withdrawing the invitation."
- No machine-level listing exists: `listMembers` returns peer id and address only, `queryCadrePeers` has no `PublicKey`, `UpdatedAt` or profile.

## What to build

### Listing

`CadreNode.listMachines(): Promise<CadreMachine[]>` (type in `types.ts`, exported):

```ts
interface CadreMachine {
  peerId: string;
  publicKey: string | null;      // ed25519 base64url behind peerId; null when the id is not ed25519
  isSelf: boolean;
  isOwner: boolean;              // publicKey is a live OwnerKey (getOwnerKeys)
  isMember: boolean;             // has a live CadrePeer row; false for an owner key with no machine row
  trusted: boolean;              // passes this node's membership predicate now (listAuthorizedMembers)
  profile: NodeProfile | null;   // self-published (cadre-peer-record-carries-machine-kind); null until it publishes
  lastPublishedAt: number | null;// UpdatedAt of its self-signed record: re-stamped every 7.5 min while it runs
  vouchedBy: string | null;      // CadrePeer.VouchOwner (or OwnerKey.VouchOwner for an owner-only entry)
}
```

One entry per live `CadrePeer` row, plus one per live `OwnerKey` whose key derives a peer id with no live `CadrePeer` row (an owner key added by `addOwner` for a machine not yet admitted, or a founder that never self-published). Reads: `queryCadrePeers` widened (or a sibling read) for `PublicKey`, `UpdatedAt`, `Profile`; `getOwnerKeys`; `listAuthorizedMembers`. Unlocked reads, default retry.

### Removal plan

`CadreNode.planMachineRemoval(peerId): Promise<MachineRemovalPlan>`, read-only, for the UI's confirmation step:

```ts
interface MachineRemovalPlan {
  machine: CadreMachine | null;          // null: no such machine here
  refusal: null | 'not-an-owner' | 'self' | 'last-owner';
  removesOwnerKey: boolean;
  dependents: {
    owners: string[];   // live OwnerKey rows whose VouchOwner is the machine's key (excluding this node's own key)
    peers: string[];    // live CadrePeer rows whose VouchOwner is the machine's key (excluding the machine itself)
  };
  invitations: string[]; // live CadreInvite keys the machine could use to come back
  ownDependency: boolean; // this node's own OwnerKey or CadrePeer row was vouched by the machine
}
```

- `refusal`: `'not-an-owner'` when this node has no enrolled owner key (`enrolledOwnerSigningKey` null); `'self'` when `peerId` is this node (an owner cannot sign its own `OwnerKey` removal, `A.Key <> old.Key`; refusing the whole self-removal keeps one rule for owners and non-owners: "ask another owner"); `'last-owner'` when the machine is the only live owner (cannot coexist with this node being a different owner, but the local count can be wrong under concurrency, so keep the name).
- `invitations`: live (`listCadreInviteStatuses(...).live`) invitations either targeted at the machine (`CadreInvite.PeerId = peerId`) or redeemed by it (`CadreInviteUsage.PeerId = peerId`; a multi-use invitation, or an open owner invitation inside its 15 minutes, could re-admit it).
- `dependents`: only meaningful when `removesOwnerKey`; empty otherwise.
- `ownDependency`: this node cannot re-vouch its own rows (it would have to sign its own `OwnerKey` removal). It keeps its anchor place where already derived (owner rows), but its own `CadrePeer` row, if vouched by the removed owner, stops passing the predicate elsewhere. The UI says "ask another owner to re-add this device afterwards". Surface it, do not attempt it.

### Removal

`CadreNode.removeMachine(peerId, options?: { revouch?: { owners?: string[]; peers?: string[] } }): Promise<MachineRemovalResult>`:

1. Re-plan (same reads as `planMachineRemoval`); throw by name on a refusal (an error class or a `code` the apps can switch on; follow how `CadreInviteRejectedError` is shaped).
2. **Re-vouch first**, before the removal, so the dependents are never untrusted in between. Only keys/peers that are in the plan's `dependents` are accepted; anything else throws before any write.
   - Peers: `seedBootstrapService.reauthorizePeer(peerId, updatedAt)` each (`updatedAt` as `reissuePeerAuthorize` computes it).
   - Owners: new `ControlDatabase.revouchOwnerKey(key, ownerKey, signMessage)` — in one transaction inside `mutateCadrePeer`, the guarded delete plus tombstone of the current row and an insert of the same key under a fresh stamp signed by this node (the bodies of `deleteOwnerKey` and `insertOwnerKeyVouched`, composed bare). `OwnerKey` has `NoUpdate`, so this is the only way to rebind its voucher; the anchor rule lets a re-add under a fresh stamp beat the older tombstone. Exposed as `SeedBootstrapService.revouchOwner` for `removeMachine` only; no `CadreNode` public method.
   - A re-vouch failure stops the call before the removal and rethrows; the caller retries. Re-vouches already made stay (they are harmless: the row is only re-signed by a current owner).
3. **One transaction** (new `ControlDatabase.removeMachine`, inside `mutateCadrePeer`, bodies composed bare as `deleteStrandAndPartyKey` does): the `CadrePeer` delete + tombstone, the `OwnerKey` delete + tombstone when `removesOwnerKey`, the `DeviceToken` delete + tombstone when the machine has one (a removed phone must not be push-woken), and a `CadreInvite` withdrawal tombstone for each plan invitation. Factor `withdrawCadreInvite`'s locked body into a bare private body the transaction can call. Stamps are read inside the locked body (retry: false), as `deleteOwnerKey` does. After commit, `notifyGuardedDelete` for every tombstone filed (so a removal committed alone re-issues all of them on growth).
4. After commit, on this node: `noteControlWrite(peerId, 'remove')`, `bootstrapPeerStore.forget(peerId)` (as `removePeer` does), and close this node's control connections to the machine (see below).
5. Return `{ removedPeer, removedOwnerKey, removedDeviceToken, withdrawnInvitations, revouched: { owners, peers } }`.

`removePeer` and `removeOwner` stay (tests and the CLI use them); point their JSDoc at `removeMachine` as the call that removes a machine completely.

### Removed machines lose their open control connections

Today a removed peer is refused per stream by the control protocol guard, but a connection it already holds stays open. Add to the membership refresh (`refreshMembershipGate`, after the snapshot is applied), on every machine: hang up control-node connections to every peer that **a `CadrePeer` tombstone names (`RowKey`) and that has no live `CadrePeer` row**. Deny only on evidence held (the strand enforcer's rule, `strand-revocation-enforcer.ts`): do not hang up peers that merely dropped out of the authorized snapshot (an anchor read that failed, an orphaned voucher), and never hang up self. A failed `hangUp` is logged and retried by the next refresh. Read the tombstones the refresh already reads (`syncOwnerAnchor` reads them once per refresh); do not add a second `Revocation` scan. On the remover this runs from the removal's own membership notification, so the connection closes before `removeMachine` returns.

## Edge cases & interactions

- **Removing self**: refused by name (`'self'`), before any read of dependents. By inspection.
- **Non-owner caller**: refused (`'not-an-owner'`). By inspection.
- **Machine with no live `CadrePeer` row but a live owner key** (owner-only entry): removes only the `OwnerKey` (and withdraws its invitations). Covered by the listing's owner-only entries; by inspection.
- **Machine already removed elsewhere** (row gone, or stamp retired): `machine` null in the plan, `removeMachine` returns all-false without writing. By inspection.
- **Concurrent removal of the same machine by two owners**: the second transaction collides on `Revocation`'s primary key and fails as a whole (the NOTE on `deleteGuardedRow`); `removeMachine` rethrows; a re-plan then reports `machine: null`. By inspection.
- **Two partitioned owners removing each other**: both commit locally; on merge `MinOneOwner` is not re-checked and the anchor rule refuses the removal that would empty an anchor. Documented, not guarded (recovery is `decide-owner-recovery`).
- **Removal committed alone** (no control connection): every tombstone goes through `notifyGuardedDelete`, so the growth drain re-issues all of them. The re-vouch writes committed alone: `reauthorizePeer` rows are re-touched by the existing drain; a `revouchOwner` insert committed alone is not re-issued (`debt-owner-key-add-while-alone-has-no-reissue` owns that). Log it as `addOwner` does.
- **A dependent that is also being removed** (the UI passes the machine itself in `revouch.peers`): refused by the "must be in `dependents`" check, since `dependents.peers` excludes the machine.
- **`ownDependency`**: surfaced, not acted on. By inspection.
- **Re-adding a removed machine later**: a fresh invitation re-admits it under fresh stamps. An owner-granting re-admission answered by a machine that received the `OwnerKey` tombstone without the delete collides on the primary key (the NOTE at `insertOwnerKeyVouched`); that machine state needs a removal committed alone, so it stays a documented limit.
- **Hang-up rule vs. a re-added machine**: a peer with a tombstone and a live row under a fresh stamp is not hung up (live row present). Pinned by the test below.
- **Hang-up while the removed machine is mid-redemption of a still-live invitation**: the invitation is withdrawn in the same transaction, so the redemption fails on any machine holding the tombstone.
- **Strand access**: unchanged by this ticket; documented (see Docs).

## Tests

- **cadre-core, one spec** (beside the owner-writer cases in `control-revocation-replay.spec.ts`, or a new `cadre-node-remove-machine.spec.ts` if a `CadreNode` is needed): an owner machine B admitted through a multi-use owner-granting invitation, with a push token and one device D it vouched. `removeMachine(B, { revouch: { peers: [D] } })` leaves no live `CadrePeer`, `OwnerKey` or `DeviceToken` row for B, files their tombstones, withdraws the invitation (a second redemption of it by B is refused), and D is still in `listAuthorizedMembers` with `VouchOwner` = the remover. A second case: a `revouch` naming a key outside `dependents` throws before any write.
- **Integration**: extend `owner-anchor-follows-owner-changes.integration.ts` with a step, or add `machine-removal.integration.ts` reusing its harness (A owner, M always-on member pinning A, B owner by invitation with a vouched device C): `A.removeMachine(B, { revouch: { peers: [C] } })`; M stops authorizing B and keeps authorizing C (after M's next membership refresh); B's control connection to A is closed by the time `removeMachine` returns. Prefer a new file if the existing scenario's run time (~47 s) would grow past a minute.
