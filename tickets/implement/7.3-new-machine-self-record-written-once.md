# A joining machine's own record is written once

Line numbers are from HEAD at planning time (after `joiner-hands-its-join-to-the-launch`); they drift.

## What happens today (traced from code)

- **Invitation path.** Device B redeems at member M. M writes B's `CadrePeer` row in the admission transaction (`ControlDatabase.redeemCadreInvite`) with `Sig` null and `UpdatedAt` set to M's clock, so the row cannot be resolved to an address. Once the row reaches B, B's next connected reconcile pass runs `publishFirstSelfRecord` → `registerSelf`, a self-update that writes the signed record. That is two commits to the same row, each to a cohort of at least M and B. The `CadrePeer.AuthorizedInsert` CHECK's consent branch (`control-schema.ts` ~451-463) does not constrain `Sig`, `UpdatedAt`, `Multiaddr` or `Profile`, so the admission insert can carry B's signed record as it is.
- **Founding.** `cadre start --owner` calls `registerSelf()` explicitly (`registerOwnerNode`, `cadre-cli/src/commands/start-owner.ts` ~204), and the boot timer (`scheduleSelfRegistration`, 1 s after start) calls it again. When the explicit insert lands first, the timer's call finds the row and writes a self-update carrying the same addresses.
- **Two refreshes after acceptance.** `redeemCadreInvitation` awaits `refreshMembershipGate('invitation-redeemed')` and then starts `reconcileControlCohort()`, whose first step is `refreshMembershipGate('reconcile')`. The gate watch (`membershipGateWatch`) already refreshes on replicated membership changes, local or remote, so the first refresh is redundant.
- **`hasOwnerKey` read twice at genesis.** `ownerKeyStanding` (CLI ~73) and `enrollFoundedOwner` (edge node, `edge-node/config.ts` ~252) each call `hasOwnerKey()`, then `ensureOwnerKey`, which calls it again (~1861). `hasOwnerKey` is a `count(1)` through `readRows`, not served from the cached `ownerKeyView`.

Out of scope here, routed elsewhere:

- **Claim path** (`claimNode` → `vouchPeer` while B restarts): left to `plan/claimed-node-rejoins-without-waiting` (its item 3); a note was added there about the write-while-alone re-touch.
- **Seed path** (`addDrone`; A's first-connection drain re-vouches B's unsigned row before B publishes): filed as `backlog/debt-seeded-machine-row-revouched-before-it-publishes`. The seed there usually travels out of band, so there is no acknowledgement to carry a record, and the re-vouch is the safety net for a write made alone.

## Design

### 1. The redemption request carries B's signed address record

**Wire shape.** `CadreInviteRedeemRequest` changes from `v: 1` to `v: 2`, and `multiaddrs: string[]` is replaced by:

```typescript
/** The device's own address record for its `CadrePeer` row, signed as `registerSelf` signs it (`signPeerRecord`) for the invitation's party. */
record: {
  addrs: string[];              // stored verbatim as Multiaddr (comma-joined); the signature covers this exact list
  updatedAt: number;            // epoch ms, the device's clock
  profile: NodeProfile | null;  // the device's node profile
  sig: string;                  // the device's 'publish' self-signature
};
```

`peerId` and `publicKey` are not repeated: the connection gives the peer id, and `peerKey` is already in the request and checked against it.

**Device side (`CadreNode.redeemCadreInvitation`).** Build the record with `signSelfRecord(peerId, signer, sanitizeAddrs(await this.collectSelfAddrs()), null)`. This is the same address source `publishSelfRecord` uses (today the request uses `resolveInviteAddresses()` alone, without the relay address). Sanitize before signing, because the signature covers the exact list that is stored. `signRedeemRequest(invitation, signer, usageStampId, record)` copies the record into the request unchanged. `this.partyId` equals `invitation.partyId`, which is already checked. The request is still signed once for every pass (its `usageStampId` must stay the same), so the record's `updatedAt` is the time of signing.

**Shape check (`isWellFormedRedeemRequest`).** It requires `v === 2` and `record` to be an object whose `addrs` is an array. The other record fields are judged by the member's verification below, so a bad value there drops only the signature, not the join.

**Member side (`CadreInviteHandler.redeemAdmitted`).** Before calling the store, decide whether to use the signed record. Put this in a small pure function (for example `admittedRecord(partyId, remotePeerId, request)`) that returns `{ addrs, signed: { updatedAt, profile, sig } | null }`:

- `addrs = sanitizeAddrs(request.record.addrs)`. If that differs from `request.record.addrs` (an entry dropped or the list capped), the signature cannot match what would be stored, so `signed = null`.
- `profile` must be `null`, `'transaction'` or `'storage'`; anything else gives `signed = null`. This keeps the insert from failing the `KnownProfile` CHECK.
- `updatedAt` must be a positive safe integer, and `sig` a bounded string. Otherwise `signed = null`.
- `verifyPeerRecordSignature(this.partyId, { peerId: remotePeerId, publicKey: request.peerKey, addrs, updatedAt, profile, sig })` must be true. Otherwise `signed = null`.
- When `signed` is null, log one debug line saying why, and admit B as today: addresses stored, `Sig` null, `UpdatedAt` = the member's now, `Profile` null.

There is no clock-skew check. A record dated in the future or long ago is what B's own self-publish could write today, and B republishes an old one itself (item 2).

**Store (`ControlDatabase.redeemCadreInvite`).** Add the optional param `record?: { updatedAt: number; profile: NodeProfile | null; sig: string }`. When it is present, the `CadrePeer` insert writes `UpdatedAt = record.updatedAt`, `Sig = record.sig`, `Profile = record.profile` (add `Profile` to the column list). Otherwise it writes `nowMs`, null, null, as today. The `alreadyMember` path still writes nothing.

**Reply.** Unchanged. B does not need to be told whether its record was used, because item 2 checks the row itself.

**Mixed versions.** A v1 member that receives a v2 request, or the reverse, fails the shape check and answers the final `invite-invalid` "Malformed redemption request". The device stops at once with `CadreInviteRejectedError`, so the mismatch neither hangs nor retries. No backwards compatibility is owed (AGENTS.md). The per-stream protocol guard does not cover `/sereus/cadre-invite/1.0.0` (it is stranger-facing and the handler does its own checks), so it needs no change. Keep the protocol id. Bumping it would turn the mismatch into a retryable "protocol not supported" dial failure at every address.

### 2. A record that is already current is not published again

Add one field and one private method to `CadreNode`:

- `lastSignedSelfRecord: PeerAddressRecord | null`. This is the newest record this process signed for its own row. `publishSelfRecord` sets it on both of its write paths. `redeemCadreInvitation` sets it to the record it sent, once the redemption is accepted. `cleanup()` clears it.
- `publishSelfRecordUnlessCurrent(): Promise<SelfRegistrationOutcome | 'current'>`. It reads the own row (`queryPeerRecord`, served from the membership view). The record counts as current when all of these hold:
  - the row exists, and `row.sig === lastSignedSelfRecord.sig`;
  - `Date.now() - lastSignedSelfRecord.updatedAt < DEFAULT_PEER_RECORD_HEARTBEAT_MS / 2` (3.75 min);
  - `await this.collectSelfAddrs()`, sanitized the same way, equals `lastSignedSelfRecord.addrs` element by element;
  - `this.config.profile` equals the record's profile.

  When it is current, call `noteSelfRecordPublished` with the record's `updatedAt` (give that method an optional timestamp, defaulting to `Date.now()`) and return `'current'` without writing. Otherwise return `this.registerSelf()`. `'current'` is a private return value of this method only. The public `SelfRegistrationOutcome` and the public `registerSelf()` are unchanged: an explicit call still always writes, which many tests and the CLI depend on.

  The age bound keeps the resolver's freshness rule safe. A skipped record is at most 3.75 min old, the heartbeat re-stamps every 7.5 min, so the row is never older than 11.25 min. Resolvers discard records older than 15 min (`DEFAULT_PEER_RECORD_MAX_AGE_MS`).

Use it at these three call sites, and only these:

- **The boot timer** (`scheduleSelfRegistration`). A founding owner whose explicit `registerSelf` already inserted the row now writes nothing at the timer. The timer still wires `startRecordRefresh` and the first reconcile run, as today.
- **`publishFirstSelfRecord`.** B's first connected pass after its row arrives finds the member-written row carrying B's signature and stops there. If B's addresses changed since signing, or the member dropped the record, or the redemption took longer than 3.75 min, B publishes as today.
- **Drain step 2** (`runDrainControlReplication` ~4814): `if (this.pendingSelfPeerWrite) registerSelf() else if (firstGrowth) publishSelfRecordUnlessCurrent()`. A self write made while alone (`pendingSelfPeerWrite`) is still re-touched unconditionally, because that re-touch is what spreads it. On first growth, a row this process signed and committed while connected is not written again. A row carried over from an earlier process still gets re-touched, because `lastSignedSelfRecord` starts null.

The heartbeat and the `self:peer:update` listener keep calling `registerSelf()` directly. The heartbeat exists to re-stamp freshness, and changing the address-change listener is not part of this ticket.

### 3. One membership refresh after acceptance

Delete `await this.refreshMembershipGate('invitation-redeemed')` from `redeemCadreInvitation` and keep the `void this.reconcileControlCohort()` kick. The pass's own head refresh and the gate watch (which fires on replicated membership changes) cover it. Update the method doc ("refresh the membership gate and start a cohort reconcile pass") and the comment above the deleted line.

Fallback, already decided: if one of the invitation scenarios below shows that a caller needs the gate current when `redeemCadreInvitation` returns, keep the awaited refresh and replace the deleted line's comment with a `NOTE:` naming that caller. Do not await the reconcile pass instead, because that would make the return wait on dials. The owner-grant protocol path's refresh (`redeemOwnerGrantAtMembers`) is left alone.

### 4. `hasOwnerKey` read once at genesis

Serve `ControlDatabase.hasOwnerKey()` from `ownerKeyView`: true when the view holds any row, retired rows included, the same rows the `count(1)` counted. The pre-check in the CLI (`ownerKeyStanding`) and in the edge node (`enrollFoundedOwner`), and `ensureOwnerKey`'s own re-check, then share one storage load. That keeps the re-check that guards the "an owner row arrived between the two reads" race, and the edge node keeps its pre-check, which decides whether to create an owner key before founding. Read through `readMembershipRows(this.ownerKeyView, retry)`, as `queryOwnerKeyRows` does. Check that `ensureOwnerKey`'s call is not inside the write lock (it is not today: it runs before `commitEmptyControlCollections`).

## Edge cases & interactions

- **A record the member cannot verify** (bad signature, an address `sanitizeAddrs` drops, more than 16 addresses, an unknown profile, a non-integer `updatedAt`): B is admitted without the signature, as today, and B's first connected pass publishes (the row's `Sig` is null, which does not match). *Verified by the one new spec (Tests).*
- **B's addresses change between signing and admission, or before its row arrives** (a phone switching networks, a relay reservation rotating during `waitForMember` passes): the `self:peer:update` publish skips while B has no row, and `publishFirstSelfRecord` then sees different addresses and publishes. *Verified by inspection of the current-check's address comparison.*
- **A long `waitForMember` redemption** (the record was signed minutes before a member accepted it): the row lands with an old `UpdatedAt`, which resolvers treat as stale, no worse than today's unsigned row. B's age bound makes it publish on its first connected pass. *Inspection.*
- **Retry after a dropped reply / restart with the invitation still configured:** the member answers `alreadyMember` and writes nothing. The row holds whatever an earlier attempt or process wrote: the same record (and the same sig) if the earlier pass of this same call committed, so B skips correctly, or an older record, whose sig differs, so B publishes. *Inspection.*
- **`joinWithOwnerGrant`** goes through `redeemCadreInvitation` with a self-invitation, so it gets the same behaviour with no separate change. *Inspection.*
- **Founding while alone:** the explicit insert sets `pendingSelfPeerWrite`, so the first-growth drain still re-touches the row unconditionally. Only the boot timer's write is dropped. *Inspection of drain step 2.*
- **Boot timer firing before the explicit founding publish** (genesis taking more than 1 s on file storage): the timer finds no row and no owner signer yet, `registerSelf` skips as today, and the explicit call inserts. No double write in either order. *Inspection.*
- **Write-while-alone re-touch of rows that carry a `Sig`:** `reconstructAuthoredMembership` and `drainPendingPeerWrites` skip rows whose `Sig` is set (`cadre-node.ts` ~4988/~5038). An invitation-admitted row now carries B's `Sig`, but the member writes it with B counted in its write cohort, so it is never a write made alone, and the skip costs nothing. *Inspection.*
- **`listMachines` / `describeMachines`** now report `profile` and `lastPublishedAt` for an invitation-admitted machine from the moment it is admitted, because the row's self-signature verifies. That is correct: it is the machine's own record. *Inspection.*
- **Interaction with `backlog/bug-owner-write-racing-a-machines-own-publish-fails`:** B no longer publishes right after joining when its record is current, which narrows that race for the invitation path. Do not fix that bug here.
- **Writes before the push** (on the seed and claim paths a node's first-connection drain writes to a cohort that includes a peer it has not yet pushed blocks to; the hazard is noted at `cadre-node.ts` ~2160). The invitation path pushes before it writes. Do not change the ordering here.
- **Pinned budgets:** `control-founding-consult-budget.spec.ts` and the specs that count writes or consults around founding may see fewer writes. Update a pin only if it is an exact count that went down, and say so in the handoff. An increase is a defect in this change.
