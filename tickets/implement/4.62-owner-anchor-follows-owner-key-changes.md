# End-to-end: the anchor follows an owner addition and an owner removal

Last of three tickets. `owner-anchor-revocation-signer-and-owner-writers` landed the stored tombstone signer and `CadreNode.addOwner` / `removeOwner`; `owner-anchor-derivation` landed the rule by which every node recomputes its anchor from the owner table. This ticket is the live-network proof the plan asked for, and it keeps this slug so the plan tickets that name `owner-anchor-follows-owner-key-changes` as a prerequisite resolve when it lands.

## The scenario

One file, one `it`, loopback WebSockets, the harness shapes `cadre-invite-any-member.integration.ts` uses (`controlNodeConfig`, `makeOwnOwner`, `startPinningMember`, `admitMember`, `waitUntil`).

Machines:

- **A**, the founding owner (`makeOwnOwner`), listening.
- **M**, an always-on member pinning A's key (`startPinningMember`), admitted through `admitMember`. M is the machine whose anchor is under test: it never pins anything but A.
- **B**, a second owner machine with its own identity key: started pinning A's key and admitted through `admitMember` like M, then made an owner by A (`A.addOwner(bKey)`), then wired to sign (`B.initializeSeedBootstrap(bPrivateKey)`, which anchors its own key as genesis on B only).
- **C**, a device B vouches (`B.authorizePeer(cPeerId)`; a bare peer id with no node is enough, as `cadre-host-owner-node` does, unless a wake or stream check is wanted, in which case start it phone-shaped).

Steps and assertions, each wait bounded by the file's named constants:

1. After `addOwner`, M derives B: `waitUntil(() => M.getTrustedOwnerStore().has(bKey))`; `sources()` reports `chain` for it. A's own anchor also derives B (A wrote the row; the hub refresh runs on A).
2. B vouches C. M lists C as an authorized member (`listAuthorizedMembers`), not only an addressable one. A lists C too.
3. B signs a seed (`B.createSeed()`); `M.applySeed` accepts it.
4. A removes B (`A.removeOwner(bKey)`). M's anchor drops B; M no longer lists C; `M.applySeed` of a fresh seed signed by B is refused with the anchored policy's reason. The tombstone reached M by replication (A and M are connected), so no re-issue is involved; assert `M`'s `queryRevocations` holds the `OwnerKey` tombstone with `signerKey === aKey` before asserting the anchor, so a timing failure names the right stage.
5. A re-adds B under a fresh stamp; M derives B again and lists C again. This is the "re-add beats an older tombstone" rule crossing a real network, and the only step that needs no new mechanism, so keep it if it fits inside the file's budget and drop it with a note if it makes the scenario flaky.

## Edge cases & interactions

- **Replication timing.** Every assertion that depends on a row or tombstone arriving at M waits on the row first and the anchor second, so a failure names which crossed. Use the existing `waitUntil` with the file's `OP_MS`.
- **Stale builds.** The stale-build guard in `test-harness` refuses to run against a stale `dist` of this repo's packages; rebuild cadre-core before the run. If it names a sibling repository's `dist`, stop and record it in the handoff (project rule `tickets/rules/sibling-repos.md`).
- **Pre-existing failures** in the integration suite are listed in `tickets/.pre-existing-known.md`; this scenario shares no fingerprint with them.
- **`B.initializeSeedBootstrap` after `admitMember`**: B is already a member vouched by A and now also an owner. Its self-published `CadrePeer` row keeps A's voucher; nothing re-vouches it, and nothing needs to.
- **C with no running node** cannot be dialed, so the assertion is on the membership predicate, not on a wake. If a stream-level check is wanted, start C phone-shaped and use the per-stream guard the `control-stream-authz` scenario drives.
