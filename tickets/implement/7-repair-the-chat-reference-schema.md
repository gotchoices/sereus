# Repair `schemas/chat.qsql`

Answers **gotchoices/sereus#7**, where an outside consumer used our schemas as a reference, hit
the defects, and lost time to the detour.

`schemas/chat.qsql` is the **richer** chat design (invitations, per-member keys, signature
verification). It is not superseded by `chat-simple.qsql` and must not be deleted — the owner's
ruling (2026-09-09):

> "chat-simple.qsql wasn't intended to replace chat, but rather evolved as part of bringing the
> reference app to maturity. The reason it seems more evolved is because the original chat app
> wasn't really brought to maturity."

So: repair it in place, keeping its own design. Do **not** converge it toward `chat-simple.qsql`.

## What the reproduction established

The fix stage loaded the file the way a consumer would — as the sApp schema through
`connectToStrand` (`@serfab/quereus-plugin-sereus`) on the `local` transactor with a
`FileRawStorage` — and then drove real writes through every constraint, signing with real
ed25519 keys generated by `generatePrivateKey` / `getPublicKey` from
`@optimystic/quereus-plugin-crypto`.

Two facts shape the whole job:

- **The file has never been executed.** It fails on the very first `create table`, and after
  that failure is cleared it still cannot be bootstrapped, cannot accept a second member, and
  never enforces its one-time invitations.
- **A schema that parses proves almost nothing.** Applying the DDL does not plan check
  constraints, so a call to a function that does not exist, a name that binds to the wrong
  table, and a wrong signature curve all load perfectly and only fail when somebody writes a
  row. That is exactly why these defects survived. Any test that only applies the schema would
  have stayed green through every defect below except the first.

Each defect below was confirmed by making the change and watching the failing write start to
pass (or, for D10, watching a write that should be refused be accepted).

## Defects

### D1 — `Attachment` primary key names a column that does not exist  (load failure)

`schemas/chat.qsql:92`: `primary key (MessageId, Sequence)` with no `Sequence` column.

```
QuereusError: Failed to execute DDL: create table App.Attachment (...)
Error: PRIMARY KEY column 'Sequence' not found in table definition
```

This is the first error and it stops the load. Attachments are ordered within a message, so add
the column — `Sequence integer` — rather than re-keying.

### D2 — identifier columns carry wrong types

`Response.OriginalId` and `Response.ResponseId` are declared `datetime` but hold `Message.Id`
values, which are `integer`. `Attachment.MessageId` is declared `string` for the same integer
key. Neither is caught by the engine — it is a correctness/readability defect in a file whose
entire job is to be read as a reference.

Retype all three to `integer`. While there: `Attachment` and `Response` carry no constraints at
all — no foreign key back to `Message`, no `InsertOnly`, and no `TimeValid` on
`Attachment.Timestamp` even though `Message` has one. Give them at least the referential checks
the rest of the file's style implies.

### D3 — `valid(...)` is not a function

The crypto plugin (`../optimystic/packages/quereus-plugin-crypto/src/plugin.ts`) registers
`digest`, `sign`, `verify`, `cid`, `cid_v1`, `cid_decode`, `set_commit`, `set_verify`,
`hash_mod`, `random_bytes`. There is no `valid`. Two sites use it — `Invite.InsertValid` and
`Member.InsertValid`; the other two constraints already say `verify`. Rename to `verify`.

Note for the reader: an unknown function name in a `check` does **not** fail at DDL apply. It
fails at write time.

### D4 — bare vs `context.` qualification is NOT a bug  (close as no-change, but tidy)

The fix ticket suspected that `Member.UpdateValid` reading `MemberSignature` / `MemberKey`
unqualified — where its sibling reads `context.InviteKey` — meant the update path had never
been exercised. It does not. Quereus registers **both** `X` and `context.X` for every declared
mutation-context variable, and registers them *before* column symbols so a context variable
shadows a same-named column
(`../quereus/packages/quereus/src/planner/building/mutation-context.ts`,
`registerMutationContextSymbols`). Verified empirically: the bare form and the qualified form
behave identically.

Still worth unifying on the `context.` form throughout, for one concrete reason: `MemberKey` is
also a **table name** in this schema, so the bare spelling reads as a table reference to a
human. Consistency here is clarity, not correctness — say so in the commit message so a future
reader does not think a bug was fixed.

### D5 — `new.Id = old.id` case inconsistency  (cosmetic)

Identifiers are case-insensitive; this works. Fix the spelling for consistency, nothing more.

### D6 — `Message.IdValid` gapless sequence: keep, but comment it honestly

`constraint IdValid check (Id >= 0 and (Id = 0 or exists (select 1 from Message M where M.Id =
new.Id - 1)))` does work as written — a write of `Id = 5` with no `Id = 4` present is refused.
Keep it as a demonstration of constraint syntax.

But it **must** carry a comment saying plainly that the pattern itself is unsafe on this stack.
A concurrent duplicate key here is not refused, it is silently last-writer-wins, so the losing
row is lost with no error. Match the wording already at `schemas/chat-simple.qsql:14-18` (do not
use the older "would collide" phrasing, which understates it), and point at
`docs/schema-guide.md` → "Ordering Events (There Is No Commit-Order Column)".

### D7 — every `verify(...)` omits the `'ed25519'` curve argument  (major)

`verify(data, signature, publicKey, curve?, ...)` defaults `curve` to **secp256k1**. Member keys
in this project are ed25519 — `schemas/strand.qsql` and `schemas/control.qsql` both pass the
curve explicitly, and `strand-schema.ts` documents the requirement in as many words.

Four sites omit it: `Invite.InsertValid`, `Member.InsertValid`, `Member.UpdateValid`,
`Message.MessageAuthorized`. Verified: with genuine ed25519 signatures every signed write was
refused until the argument was added; with it, all of them pass.

### D8 — the bootstrap branches are unsatisfiable, so the schema cannot be started  (major)

`Invite.InsertValid` opens with `not exists (select 1 from Invite)` and `Member.InsertValid` with
`not exists (select 1 from Member)`. Both constraints are evaluated with the new row **already
present**, so both are false on the very first row. The first invitation and the first member
are rejected. There is no way to bring this schema up.

The working idiom is already in this repo at `schemas/strand.qsql:245-246` — compare the
committed (pre-transaction) state against zero, and the in-flight table against one:

```sql
(select count(1) from committed.Member) = 0 and (select count(1) from Member) <= 1
```

Verified: both bootstrap inserts pass once written this way.

### D9 — name capture in `Invite.InsertValid` signs the wrong values  (major)

The non-bootstrap branch is:

```sql
select 1 from MemberKey K join Member M on K.MemberId = M.Id where K.Key = MemberKey and M.CanInvite
   and verify(digest(Key, OneTime, CanInvite), MemberSignature, MemberKey)
```

`Key` and `CanInvite` are unqualified **inside a subquery whose `from` clause has a `Key` column
(`MemberKey K`) and a `CanInvite` column (`Member M`)**. They bind to those, not to the row being
inserted. So the digest covers the inviting member's public key and the inviting member's
`CanInvite` flag instead of the new invitation's `Key`, `OneTime` and `CanInvite` — no correctly
produced signature can ever match.

Verified: a second invitation, correctly signed by the founding member, is refused until the
references are `new.`-qualified; then it is accepted.

Qualify every reference to the inserted row as `new.<column>` and every context reference as
`context.<name>`, wherever a check contains a subquery. Check the whole file for this pattern —
it is a class, not a single site.

### D10 — `UsedInvite.ValidUsage` never enforces `OneTime`  (major)

```sql
exists (select 1 from Invite I where I.Key = new.Key
        and (not I.OneTime or (select count(1) from UsedInvite U where U.Key = new.Key)))
```

The right arm is a bare `count(1)` used as a boolean. Because the check sees the new row, that
count is at least 1 — truthy — on every redemption, including the second and the tenth. So a
one-time invitation is reusable forever. (Had it been evaluated before the row landed, the count
would be 0 and a one-time invitation could never be redeemed at all. Broken either way.)

Verified: an invitation with `OneTime = true`, already redeemed by the founding member, was
accepted again for a second member.

Fix by comparing the count explicitly against the limit, counting the in-flight row — e.g.
`(select count(1) from UsedInvite U where U.Key = new.Key) <= 1` — and, if this schema wants the
stricter reading, against `committed.UsedInvite` as in D8.

### D11 — `Member` and `UsedInvite` are mutually dependent, so joining needs one transaction  (major, design)

`UsedInvite.MemberValid` requires the `Member` row to exist. `Member.InsertValid` requires the
matching `UsedInvite` row to exist. Neither can go first.

Verified: with all the above repaired, inserting them in either order as separate auto-commit
statements fails; wrapping the pair in a single `begin` / `commit` succeeds.

This is a real property of the design, not necessarily a mistake — but it is invisible, and a
consumer reading the file will write the two inserts separately and conclude the schema is
broken. Resolve it one of two ways, and say which in the commit:

- **Document it** — a comment on both tables stating that redeeming an invitation is a single
  transaction that inserts both rows, because each row's constraint requires the other; or
- **Break the cycle** — drop `UsedInvite.MemberValid` (the `Member` insert already proves the
  redemption) so the two can be written independently.

Prefer documenting unless breaking the cycle turns out to be clearly safe: `MemberValid` is a
real integrity check and removing it widens what `UsedInvite` accepts.

## Orientation headers

Both files ship and a reader cannot tell which is which. Add a short header comment to each —
two lines, no more:

- `chat.qsql` — the fuller design, including invitations, per-member keys and signature
  verification.
- `chat-simple.qsql` — the schema the reference app actually runs; deliberately omits
  application-level crypto. It already says the second half at `chat-simple.qsql:1-3`.

Do **not** phrase either as a pointer to the other, and do not add anything that reads as a
deprecation. Neither file is retired.

## The test

Nothing in the product loads `chat.qsql`, which is why none of this was caught, and is also why
a repair with no test rots straight back. The test must therefore **write rows**, not merely
apply the schema — see the reproduction note above: every defect but D1 survives a load-only
test.

Put it alongside the existing strand suite, `packages/quereus-plugin-sereus/test/e2e/`, whose
`strand-schema.e2e.spec.ts` is a close model: `local` transactor, real `FileRawStorage` in a
temp dir, `connectToStrand`, torn down in `afterEach`. Read the `.qsql` from `schemas/` relative
to `import.meta.url` and pass its `declare schema Chat { ... }` body as the `schema` option
(`composeStrand` wraps what it is given in `declare schema App { ... }`). Reuse the
comment/string-aware body extractor already written for `test/strand-schema-drift.spec.ts`
rather than a fresh `indexOf('{')`.

Cover, at minimum, the sequence the reproduction ran — each of these caught at least one real
defect:

- both schemas apply cleanly (`chat-simple.qsql` too — cheap, and it makes the test the guard
  for both files)
- the first invitation and the first member are accepted (D8)
- a member key is registered, and a member renames themselves with a valid ed25519 signature (D7, D3)
- a message at `Id = 0` is accepted with a valid signature, and one at `Id = 5` over a gap is
  refused (D6, D7)
- a second invitation, signed by the founding member, is accepted (D9)
- a second member redeems that invitation and joins — in whatever shape D11 is resolved into
- a one-time invitation cannot be redeemed twice (D10)
- deleting a member is refused (`CantDelete`)

Sign with real keys via `generatePrivateKey` / `getPublicKey` from
`@optimystic/quereus-plugin-crypto` and produce signatures through SQL —
`select sign(digest(...), ?, 'ed25519')` — so the test's digest is built by the same code path
the constraint checks against. Signing by hand in JavaScript re-implements `digest`'s field
framing and will drift.

Watch the syntax details that cost time in the fix stage: on an `update`, `with context` goes
either before `set` or after `where`, never between them.
