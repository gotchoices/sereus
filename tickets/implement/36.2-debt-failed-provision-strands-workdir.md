# A provision that never spawns leaves its working directory behind

## Background

When someone redeems a grant, `DonationService.provision` writes a donation
record (`status: 'provisioning'`) and then asks the orchestrator to start a
node. `HostProcessOrchestrator.createContainer`'s first step is
`ensureNodeIdentity(workdir)`, which calls `generateIdentity` — and that does
`mkdirSync(dirname(filePath), { recursive: true })` before writing the key. So
the node's working directory `<rootDir>/<donationId>/` comes into existence
before any port is reserved and before any child is spawned.

If the spawn then fails, the record is marked `error` and the call throws — but
the record never got a `dockerId`, because none was produced. Every cleanup path
keys off that id:

- `terminate()` skips its stop-and-reclaim entirely when the record has no
  `dockerId`;
- `reclaimStuckProvisioning` (the stuck-`provisioning` reap) asks the
  orchestrator to resolve the id from the container name, and there is no handle
  to resolve.

So `<rootDir>/<donationId>/` stays on disk — an `identity.key`, and whatever
else the failed spawn got as far as writing — with nothing that will ever remove
it. Every failed provision adds another.

Nothing else leaks: no ports are held (the completed
`debt-failed-respawn-strands-donated-workdir` closed that), and the record is
correctly `error`, so the grant's quota frees.

## Decisions made during planning

**Shape: unwind-on-failure, plus a record-driven reclaim-by-name. Not a
directory sweep.** The plan ticket asked whether a periodic sweep for workdirs
that no donation record names would be the better shape. It is not. `rootDir`
also holds `state.json` and the admin's *own* owner node (`<rootDir>/owner/`),
and any future managed-node kind lands there too; a sweep has to decide, by
inference from a directory listing, which entries are safe to delete — a
delete-by-guess on the one directory that holds the host owner's own control-DB
storage. The record-driven paths already know the exact id to reclaim, so they
get the job.

**Distinguishing "this spawn created the directory" from "this spawn is reusing
one".** Deleting the workdir on *any* failed `createContainer` would be actively
wrong: on the re-spawn path the surviving workdir is the whole point — it holds
the `identity.key` that makes the node come back as the same peer, plus its
node-local stores. The test is simply whether the directory existed on entry:
`existsSync(workdir)` is sampled *before* `ensureNodeIdentity` runs, and only a
spawn that found no directory may delete one on its way out.

**Precedent.** `cadre-provider`'s `DockerOrchestrator.createContainer` already
does exactly this with its durable `/data` volume: `ensureVolume` returns `true`
only when *that call* created it, and the failure path runs
`if (createdVolume) await this.removeVolume(...)` with the comment "a
pre-existing one belongs to the container being recreated and still holds its
identity". So the answer to the plan ticket's "whether `cadre-provider`'s
equivalent path has the same hole" is **no — it is already closed**, and this
work makes cadre-host match it. Do not change `cadre-provider` in this ticket.

**`ensureOwnerNode` is deliberately out of scope.** The owner node's workdir is
a single fixed path (`<rootDir>/owner`) reused by every restart, and it holds
the host's own control-DB storage. It does not grow without bound and deleting
it on a failed spawn would destroy real state. Leave it alone; say so in a
comment so the asymmetry does not read as an oversight.

## Architecture

### Arm 1 — `createContainer` removes a workdir its own failed spawn created

Widen `HostProcessOrchestrator.createContainer`'s existing `try`/`catch` to
cover `ensureNodeIdentity` as well, sample the directory's prior existence
before it, and delete on the way out only when this call brought it into being:

```ts
async createContainer(request: OrchestratorCreateRequest): Promise<OrchestratorCreateResult> {
  const workdir = this.workdirFor(request.containerId);
  // Sampled BEFORE `ensureNodeIdentity`, which creates the directory as a side
  // effect of writing the key. Only a spawn that found nothing here may delete
  // anything on its way out — a re-spawn is reusing the identity key and
  // node-local stores this directory holds, and they are the whole reason the
  // node comes back as the same peer.
  const isNewWorkdir = !existsSync(workdir);
  let dropped: Handle[] = [];
  let ports: NodePorts | undefined;
  try {
    const identity = await ensureNodeIdentity(workdir);
    ...                                  // push resolve, extraEnv (unchanged)
    dropped = this.dropStaleHandle(request.containerId);
    ports = allocateNodePorts(this.portAllocator);
    return this.launchChild({ ... });    // unchanged
  } catch (err) {
    // Release BEFORE restoring — see the existing note.
    if (ports) this.releasePorts(ports);
    this.restoreDroppedHandles(dropped);
    if (isNewWorkdir) this.discardWorkdir(workdir);
    throw err;
  }
}
```

Three properties this rests on, all already true — state them in comments so a
later edit cannot quietly break them:

- **Nothing between the drop and the launch is `await`ed.** Widening the `try`
  adds no `await` in that window, so `restoreDroppedHandles`'s documented
  precondition still holds. `restoreDroppedHandles([])` is a no-op for the
  failures that happen before the drop.
- **A throw out of `launchChild` means no child is running.** Its throw surface
  ends where the child is spawned and its handle stored (established by the
  completed `debt-failed-respawn-strands-donated-workdir`; `persist()` past that
  line is best-effort). The `if (!child.pid) throw` also sits on the no-process
  side — an undefined `pid` from `spawn` means nothing started. So there is
  never a live process holding the directory this catch deletes.
- **`isNewWorkdir` false is the safe default.** A directory that exists for any
  reason — respawn, a prior failed provision, an operator's file — is never
  touched by this path.

New private helper, next to `removeContainer`'s existing removal:

```ts
/**
 * Best-effort removal of a workdir this host created and no handle owns.
 * Logs, never throws: every caller is already unwinding a failure and must
 * report *that* error, not this one.
 *
 * Fewer retries than `removeContainer`'s: that one races the OS releasing a
 * just-killed child's cwd handle (Windows), while every caller here has
 * established no process ever attached to this directory.
 */
private discardWorkdir(workdir: string): void {
  try {
    rmSync(workdir, { recursive: true, force: true, maxRetries: 5, retryDelay: 100 });
  } catch (err) {
    log('failed to discard workdir %s: %o', workdir, err);
  }
}
```

### Arm 2 — reclaim by container name when no handle exists

Arm 1 covers a spawn that failed *in this process*. It does not cover the host
dying between `ensureNodeIdentity` and the handle write: the record stays
`provisioning`, no handle exists across the restart, and the directory is
orphaned. That is precisely the case `reclaimStuckProvisioning` already exists
for — it just has nothing to act on today.

Add an optional orchestrator capability alongside the existing
`resolveDockerId`, in `donation-service.ts`:

```ts
export interface DonationOrchestrator extends Orchestrator {
  resolveDockerId?(containerId: string): string | undefined;
  /**
   * Remove the working directory a spawn created for `containerId` when no
   * handle owns it — the cleanup of last resort for a record that never got a
   * `dockerId`. Returns whether anything was removed. Refuses when a handle
   * still resolves (that child's directory belongs to `removeContainer`).
   */
  reclaimWorkdir?(containerId: string): boolean;
}
```

`HostProcessOrchestrator.reclaimWorkdir(containerId)` — synchronous, mirroring
`resolveDockerId`; nothing on this path is async:

- return `false` when `containerId === OWNER_CONTAINER_ID` (never reclaim the
  admin's own node by this route);
- return `false` when `this.resolveDockerId(containerId)` resolves — a live
  handle owns that directory and `removeContainer` is the only thing allowed to
  delete it;
- resolve `<rootDir>/<containerId>` via `workdirFor` and refuse anything that
  does not stay inside `rootDir` (donation ids are `grn_<base64url>` and cannot
  contain a separator or a dot, so this is defence, not a live case — say that
  in the comment);
- return `false` when the directory does not exist;
- otherwise `discardWorkdir(workdir)` and return `true`.

Two donation-service call sites:

1. `reclaimStuckProvisioning` — when `resolveDockerId` returns nothing, call
   `reclaimWorkdir` instead. The record is written terminal (`error`) first, as
   it already is. Update the method's existing `NOTE:` about a child the reap
   cannot reach: an orphan *process* is still unkillable, but its directory is
   no longer unreachable.
2. `terminate` — the `if (donation.dockerId)` branch gets an `else` that calls
   `reclaimWorkdir(id)`. Without it arm 2 has an obvious bypass: terminating a
   stuck-`provisioning` record before the reap sees it moves it to `terminated`,
   which `isStaleProvisioning` no longer matches, stranding the directory for
   good.

Both call sites go through a `safeReclaimWorkdir(id)` private that swallows and
logs, matching `safeStop` / `safeReclaim`.

## Edge cases & interactions

- **Re-spawn whose launch fails must keep its workdir.** The load-bearing case.
  `existsSync` is true on entry → no delete → `identity.key` and the node-local
  stores survive, and the restored handle still names them.
- **First spawn that fails at port allocation.** `ensureNodeIdentity` has
  already created the directory and written the key; `allocateNodePorts` throws
  before `launchChild`. Directory must be gone.
- **First spawn that fails inside `launchChild`** (`mkdirSync(storage)`,
  `writeFileSync(cadre.json)`, `openSync(node.log)`, `spawn`). Same catch,
  same outcome. Coverage of the others is by construction — do not write four
  near-identical tests.
- **`ensureNodeIdentity` itself throws.** Two sub-cases, and the widened `try`
  gets both right: an undecodable *pre-existing* `identity.key` (directory
  existed → kept, which is correct: the operator needs to see it), and a write
  failure part-way through `generateIdentity` (directory did not exist → the
  partial directory is removed).
- **`<rootDir>/<containerId>` exists as a plain *file*.** `existsSync` is true,
  so `isNewWorkdir` is false and nothing is deleted; `mkdirSync` throws and the
  error propagates. Deliberate — do not "fix" this into a delete.
- **A launch that already spawned but whose `persist()` failed** must NOT reach
  the catch at all (the completed respawn ticket made that write best-effort
  precisely so it cannot). There is an existing regression test — *does not
  unwind a launch that already spawned when the state write fails*. Confirm it
  still passes and that it now also asserts the workdir survives.
- **`terminate` racing an in-flight provision on the same record.** `terminate`
  marks `terminated` and, finding no `dockerId`, reclaims by name — possibly
  while `createContainer` is between its `mkdirSync` and its `spawn`. The end
  state is still correct: `provisionLocked`'s post-spawn re-read sees a
  non-`provisioning` record and `safeReclaim`s the new child (which deletes the
  workdir anyway). The interim delete can make the child fail to start with a
  missing identity file — noisy, self-healing, and strictly better than the
  permanent strand. Note it at the call site rather than trying to close it.
- **`reclaimWorkdir` must never touch a live node's directory.** Guarded by the
  `resolveDockerId` check and the `OWNER_CONTAINER_ID` check. Both need a test.
- **An orchestrator without the capability** (a test double, a future
  orchestrator) — `reclaimWorkdir?.()` is optional, exactly like
  `resolveDockerId?.()`; the reap and `terminate` degrade to today's behaviour.
- **`DonationSupervisor.giveUp` must stay unaffected.** It marks a record
  `error` *keeping* the workdir on purpose, so the identity key the borrower's
  cadre approved survives. Its records always name a `dockerId` (a respawn
  recorded one), so `terminate`'s new `else` branch never fires for them, and
  `giveUp` itself never calls `reclaimWorkdir`. Verify, do not assume.
- **`ensureOwnerNode` unchanged.** Its catch keeps its current two statements.
