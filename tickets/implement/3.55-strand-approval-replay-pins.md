# Pin the six replay attacks as rejected, plus digest-parity and tripwire follow-ups

Split out of `strand-approval-stamps-and-tags` (that ticket lands the single-use stamp +
tagged-digest mechanism; this one adds the explicit attack pins and small follow-ups). Its
resume note carries the full orientation — read it first; do not re-derive.

## New replay spec: R1–R6 as `rejects.toThrow(...)`

Each of the six replays below was reproduced as SUCCEEDING against a real closed strand before
the stamp mechanism landed. Write a spec (new file, e.g.
`packages/cadre-core/test/strand-approval-replay.spec.ts`) that performs each capture-and-replay
and asserts rejection, PLUS the positive path each replay was derived from (legitimate
re-promotion, re-admission, re-registration all still work — with fresh stamps and fresh
signatures via the writers). Copy the harness from `strand-member-revocation.spec.ts`
(`openStrand`, `freshKeyPair`, `inTransaction`).

| # | Captured approval | Replayed as | Expected now |
|---|---|---|---|
| R1 | `addManager` promotion of X at generation 1 | re-insert `Manager(X, 1)` after X was removed | rejected — stamp retired (`NotRevoked`), signature bound to old stamp |
| R2 | `removeManager` removal of X | delete `Manager(X)` after re-promotion | rejected — new row has a fresh `StampId`, captured digest mismatches |
| R3 | X's own resignation | delete `Manager(X)` after re-promotion, by a party that never held X's key | rejected — same fresh-stamp mismatch |
| R4 | `addMemberByManager` admission of X | re-insert `Member(X)` after X was revoked | rejected — stamp retired |
| R5 | `revokeMember` removal of X | delete `Member(X)` after re-admission | rejected — fresh-stamp mismatch |
| R6 | `registerMemberPeer` binding (M, P) | delete that binding then re-insert it | rejected — insert and delete digests now differ AND carry stamps |

To "capture" an approval: mint the signature/context exactly as the writer does (call the
exported signer over the live row's StampId before the legitimate remove), then replay it via a
raw `db.exec` after the state change. Mind the pin-confound hazard from the parent ticket's
resume note: raw DELETE replays fail both `Authorized` and `RevocationRecorded` — pin
`/CHECK constraint failed/` unless the test supplies a valid same-transaction tombstone to
isolate `Authorized`.

## Five-element digest parity case

`digest-variadic-parity.spec.ts` case (d) pins four-element digests only. Add a five-element
case for the Manager promotion digest
(`'Strand.Manager', 'add', memberKey, generation, stampId`). Pin the INTEGER→TEXT coercion
explicitly: bind the generation as a NUMBER parameter in the SQL `digest(...)` call and pass
`String(generation)` on the TS side — the coercion parity is what the case proves (case (d)
covers text fields only).

## Tripwire NOTE

At the `Strand.Revocation` table (both schema copies — they must stay byte-identical, see the
parent ticket's mirror-regeneration recipe): it grows one row per membership deletion and never
shrinks. Fine at strand scale; if membership churn ever gets large, it needs pruning bounded by
something other than "forever". Record as a `NOTE:` comment if the parent ticket did not
already; mention in the review handoff's findings either way.
