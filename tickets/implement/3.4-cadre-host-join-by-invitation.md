# Join by invitation

Fifth of the `cadre-host-join-a-cadre` chain. The invitation mechanism itself landed in `cadre-invitations-redeemable-by-any-member`: `cadre start --invitation <encoded>` decodes the bundle, checks its party against the node's, redeems at the members the bundle names right after start, and keeps running on a failure. The bundle carries the owner keys the node pins, and members admit the node on the invitation's signature, so no claim secret is involved.

## What to build

**cadre-cli.**

- `CADRE_INVITATION` (env only, set-but-empty is unset) is the equivalent of `--invitation`; passing both is refused by name. The host uses the env form because the bundle carries the invitation's private half and an argument shows in the process list, the same reason `CADRE_CLAIM_SECRET` is env only. Add it to `env.ts`'s known names and the README's env table.
- `/status` gains `node.invitation?: { state: 'pending' | 'accepted' | 'failed'; memberPeerId?: string; error?: string; retryable?: boolean }`, present only when the node was started with an invitation. `pending` from start until the redemption settles; `accepted` with the admitting member; `failed` with the error message and `retryable` from `CadreInviteRejectedError` / `CadreInviteUnreachableError` (an unknown error is `retryable: false`). The redemption block in `start.ts` records the outcome; the existing `NOTE:` about not retrying stays.

**cadre-host.**

- `HostedNode.join` gains `{ kind: 'invitation'; encoded: string }`; `partyId` is the invitation's party from the start; a new status `joining` (child up, redemption pending). `HostedSpawnRequest` gains `invitation?: string`, passed as `CADRE_INVITATION`; a request with both `claimSecret` and `invitation` throws before anything is spawned (cadre-cli would refuse the child anyway).
- `join({ invitation })`: decode with cadre-core's `decodeCadreInvitation`; a bundle that does not decode is `400 invalid_request` with the decoder's message, before any record is written. Spawn with `partyId: invitation.partyId`, write `joining`.
- The status watcher polls `joining` nodes every 2 seconds, as it polls unclaimed ones: `accepted` → `joined`, `ownerKey` = the invitation's issuer key (the bundle carries it); `failed` → `error` with the message, plus a new `retryable: boolean` field on the record so the UI can offer Retry. A failure on a `joined` node's later status is ignored (see respawn).
- Respawn: a `joining` record respawns with the invitation (cadre-cli redeems again; a member's redemption is idempotent for a node that already got in). A `joined` invitation node respawns **without** it: it is a member, its rows are in its own control database, and an invitation that expired meanwhile must not turn a healthy member into `error`. An `error` record with `retryable: true` is respawned only by an explicit Retry (`POST /api/hosted-nodes/:id/retry`, which rewrites it `joining` and calls `respawn` without counting an attempt); the supervisor never touches `error`, as now. Supervised statuses: `unclaimed`, `joining`, `joined`.
- Routes: `POST /api/hosted-nodes` accepts `{ invitation?: string }`; `POST /api/hosted-nodes/:id/retry` → `409 invalid_state` unless `error` and `retryable`.
- CLI: `cadre-host join --invitation <encoded>` prints "Joining cadre `<partyId>` through the invitation…" then polls to `joined` ("✓ Joined cadre `<partyId>` at member `<peer>`") or `error` ("✗ Could not join: `<message>`" plus, when retryable, "No member of the cadre could be reached. If this is the cadre's first always-on node, use `cadre-host join` without `--invitation` and scan the QR code from the phone instead."). `cadre-host node retry <id>`.
- UI Join page: below the button, "Or paste a cadre invitation" with a textarea and a Join button; progress "Joining…" → the joined state line, or the error with the same hint and Retry when retryable. The node detail's `error` card offers Retry when `retryable`.

**Scenario** `cadre-host-join-by-invitation.integration.ts`: an in-process owner A listening on loopback (as `cadre-invite-any-member.integration.ts` builds one) founds a cadre and mints an untargeted invitation with `grantsOwner: false`; the host (`createTestCadreHost`) joins with it; the record becomes `joined` naming A as the member, A lists the node as authorized. Then: A stops, a second invitation minted earlier (naming only A) is joined; the record ends `error`, `retryable: true`, with a message naming reachability; `POST …/retry` after A restarts makes it `joined`. Then: an invitation with a 1-second expiry, joined after it expired, ends `error`, `retryable: false`, with `invite-spent` in the message. Each case its own `it`.

## Edge cases & interactions

- Invitation that does not decode: 400 before any spawn. Route test.
- No reachable member (the first-node case): `error`, retryable, the hint shown. Scenario.
- Respawn of a `joining` node: the invitation is passed again. Supervisor test with the fake orchestrator: the spawn request carries `invitation`.
- Respawn of a `joined` invitation node: no invitation passed. Same test, second case.
- Expired invitation: `error`, not retryable; Retry refused 409. Scenario and route test.
- A `joined` node whose later `/status` still says `failed` (a respawn that re-redeemed before this ticket's rule, or a host restart that re-attached such a child): ignored, the record stays `joined`. By inspection; state it in the watcher.
- Targeted invitation naming a peer id that is not the new node's: the member refuses; `error`, not retryable; the message says the invitation was for another device. Scenario not needed; by inspection of the member's refusal code mapping.
- `CADRE_INVITATION` and `CADRE_CLAIM_SECRET` both set: cadre-cli refuses (extend `refuseClaimConflicts` to name the env form); the host never sets both. By inspection.
