# Grants page in the cadre-host dashboard

## Background

A **grant token** is the secret the host owner gives a friend so the friend's cadre (their phone) can ask this machine for donated nodes, up to the grant's `maxNodes`. Grants are long-lived and reusable until they expire or are revoked. The owner manages them through the loopback, no-bearer admin surface `/grants-admin` (`src/server/routes/grants-admin.ts`), whose only client today is the `cadre-host grant issue|list|revoke|terminate` CLI (`src/bin/host.ts`, ~line 725 onward). The dashboard's Home page (donor role) shows a Donation tile that tells the user to run `cadre-host grant issue <label>`.

The donor-aware UI work (`feat-cadre-host-donor-aware-ui`, complete) gave the SPA `app.role`, founder-only route gating (`FOUNDER_ROUTES` in `ui/src/lib/router.ts`) and a Terminate button on donated nodes' detail pages (`DELETE /grants-admin/donations/:id`).

## Decisions (the three open points, settled)

**1. Per-grant node information comes from the server, not a client-side join.** `/api/nodes` carries `partyId` (the requester's cadre), never the grant token, so the page cannot join nodes to grants. `GET /grants-admin` is extended instead: each grant carries `liveNodes` (the quota tally, same rule as `DonationStore.liveNodeCount`) and `donations` (the id and status of every donation under it that is not `terminated` — exactly the set `DonationService.terminateGrant` would tear down on revoke, `error` records included). The revoke confirmation therefore states the real teardown count, and the page links each donation to its node detail page. This replaces the "link to the Nodes page" idea in the original ticket: the Nodes page has no filter, and the per-donation links serve the same purpose without adding query-string parsing to the hash router.

**2. The token is shown at issue time and on an explicit "Show token" action, never in the list.** The list response must carry tokens (they are the key for `DELETE /grants-admin/:token`), so hiding them is about what sits on screen (screen-sharing, shoulder-surfing), not about what the browser holds. Grants are reusable, so the owner does need a way to re-share one (friend's new phone, lost message); a per-row "Show token" button on active grants opens the same token view the issue flow ends in. This matches the Trust Circle page, whose pending-invite list shows label and dates but no token. The CLI's `grant list` keeps printing tokens — same machine, same posture. Tokens are never written to browser storage.

**3. A `grants-changed` server-sent event, plus a refresh on node state changes.** The admin routes publish `grants-changed` (`kind: 'issued' | 'revoked' | 'terminated'`) after issue, revoke and single-donation terminate, the same way the trust-circle routes publish `trust-circle-changed`. That covers the CLI acting while the page is open. Node counts also change through the grantee-facing `/grants` surface and the donation supervisor; rather than thread the event bus into `DonationService`, the SPA re-fetches grants on `node-state-changed` once the grants slice has loaded. This is consistent because a donation record is written `provisioning` before its child spawns (so the spawn event sees it live) and written `terminated` before its child is stopped (so the stop event sees it gone). Refresh-on-focus is not added.

## Server changes

`src/donation/types.ts`:

```ts
/** One grant as the admin list reports it: the grant plus what is running under it. */
export interface GrantListing extends Grant {
  /** Donations counting against `maxNodes` (provisioning / awaiting_seed / seeded). */
  liveNodes: number;
  /** Every donation under this grant that is not `terminated` — what revoke would tear down. */
  donations: Array<{ id: string; status: DonationStatus }>;
}

// GrantAdminHandlers.listGrants(): Promise<{ grants: GrantListing[] }>;
```

- `src/donation/donation-store.ts`: export `isLiveDonationStatus(status)` built on the existing `LIVE_STATUSES`; `liveNodeCount` uses it. One definition of "live" for both the quota check and the listing.
- `src/donation/grant-service.ts` `createGrantAdminHandlers`: widen `donations` to `Pick<DonationService, 'terminate' | 'terminateGrant' | 'list'>`. `listGrants` reads `donations.list()` once (one store read, not one per grant), groups by `grantToken`, and builds each `GrantListing`. With no donation service wired, every grant reports `liveNodes: 0, donations: []`. Donations whose token names no grant are ignored.
- `src/server/events/types.ts`: add `{ type: 'grants-changed'; kind: 'issued' | 'revoked' | 'terminated' }`.
- `src/server/routes/grants-admin.ts`: `GrantsAdminRoutesOptions` gains a required `events: EventBus`; publish after each successful mutation (not on error). Update the module header comment. `src/server/index.ts` passes `events`; `grants-admin-route.test.ts` passes `new EventBus()`.
- `src/bin/host.ts` `grant list`: print `live=<liveNodes>` next to `max=<maxNodes>` (response type widened accordingly).

- `ui/src/lib/grants.ts` (pure, testable without Svelte): `grantState(grant, now): 'active' | 'expired' | 'revoked'` — revoked is checked before expiry, matching `GrantService.validate`; and `sortGrants` (active, then expired, then revoked; newest `createdAt` first within each).
- `ui/src/components/TokenShare.svelte`: the QR (`QrCode.svelte`) + read-only textarea + Copy button block, extracted from `InviteModal.svelte` and used by both `InviteModal` and the new modal. The grant QR encodes the bare token, exactly what `cadre-host grant issue` QR-encodes (`printGrantToken` in `host.ts`).
- `ui/src/components/GrantIssueModal.svelte`: two modes.
  - *Issue*: label (required, `maxlength=200`, trimmed), max nodes (integer ≥ 1, placeholder 1; empty → omitted so the server default applies), lifetime select (30 days, 90 days, 1 year, No expiry; default No expiry, matching the CLI's default). `POST /grants-admin`. Submit disabled while busy.
  - *Show*: given an existing grant, skip the form. Both modes end in `TokenShare` plus a line saying what the friend does with it (enter this machine's address and the token in the app's "Host Node" settings) and the grant's max nodes / expiry.
- `ui/src/components/ConfirmDialog.svelte`: add an optional `children` snippet rendered between the message/note and the actions, so a caller can put a control in the dialog. No other behavior change.
- `ui/src/routes/Grants.svelte`: header + "Issue grant" button; a list (the `ul.list` layout Trust Circle uses, which works at phone width) with, per grant: label, state badge, `liveNodes / maxNodes nodes`, issued and expiry (relative, via `format.ts`), its donations (ids with status; `awaiting_seed` / `seeded` ones link to `#/nodes/<id>`, others are plain text since the orchestrator may have no node for them yet or any more), and actions: **Show token** (active grants only) and **Revoke** (any grant not already revoked — an expired grant's nodes keep running, so revoking it is how to shut them down). Loading, error and empty states as on the Strands page; empty text: "No grants yet. Issue one to let a friend borrow nodes from this machine."
  - *Revoke*: `ConfirmDialog` (danger, no typed confirmation — a new grant can be issued, so this is not unrecreatable) whose message names the label and says the friend can no longer ask for nodes; when the grant has donations, the message says how many donated nodes will be shut down, and a checkbox (passed as `children`) "Keep its N donated node(s) running" switches the call to `?keepNodes=true` and the message accordingly. The checkbox resets each time the dialog opens. On success, toast using the server's `terminated.length` (the honest number, which may differ from the count shown if something changed meanwhile) and refresh.
- `ui/src/routes/Home.svelte`: in the Donation tile, replace the CLI hint and its comment with `Manage grants →` linking to `#/grants`.

## Edge cases & interactions

- **CLI and page acting at once.** CLI issue/revoke publishes `grants-changed`, so an open page refreshes. Revoking an already-revoked grant is idempotent server-side (`markRevoked`) and still tears down what remains; the page just refreshes. Verified by inspection.
- **Revoke count goes stale while the dialog is open** (a friend borrows or releases a node meanwhile). The dialog shows the last-listed count; the toast reports the server's `terminated` list. By inspection.
- **Revoke of an unknown token** (grants.json edited by hand): 404 → error toast via `reportError`, then refresh. By inspection.
- **Donation state changes not coming from an admin route** (grantee provision/release, supervisor respawn, reaper sweeps): covered by `node-state-changed` → refresh once loaded, relying on the write-record-before-spawn / write-terminated-before-stop ordering described above. One path is not covered: the supervisor's give-up writes `error` after the crash event already fired, so `liveNodes` stays one too high on an open page until the next refresh. Leave a `NOTE:` tripwire at the `node-state-changed` refresh in `state.svelte.ts`.
- **Overlapping refreshes** (an action's own refresh racing its SSE echo) are last-response-wins, as with strands; both are post-mutation so the result converges. By inspection.
- **Expiry computed client-side**: browser and server are the same machine (loopback), so clocks agree. `grantState` test pins the precedence.
- **`/grants-admin` not mounted** (only when a caller of `createLocalUiServer` omits `grants`; `bin/host.ts` always wires it): the page shows its error state and one toast. No event is ever published there, so no background 404s. By inspection.
- **Founder role**: the page and nav item appear for founders too; no founder-only fetch is involved. By inspection / browser check.
- **Issue validation**: empty label is blocked client-side; server `invalid_label` / `invalid_max_nodes` / `invalid_ttl` (400) surface as error toasts with the server message, and the form stays filled.
- **Closing the issue modal** discards the token from component state; it can be shown again via Show token. Nothing is stored in `localStorage`.
- **Donation links**: only `awaiting_seed` / `seeded` link to node detail; `provisioning` and `error` render as text to avoid a 404 toast from a node the orchestrator does not (yet / any longer) hold.
- **Revoked grant with kept nodes**: still listed, with its donations linked, so the owner can Terminate them one by one from node detail.
