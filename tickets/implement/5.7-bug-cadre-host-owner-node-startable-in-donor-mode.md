# Refuse owner start/restart on a donor-only host

## Cause (confirmed by reading)

cadre-host runs its own personal cadre (an "owner node" plus trust circle, NAT and strands) only when `ownCadre.enabled` is true. When that flag is turned off after an earlier founder run, `cadre-host start` takes the donor branch in `src/bin/host.ts` (around line 426) and calls `orchestrator.stopOwnerNode()`. That only stops the child; the owner handle and the saved `OwnerSpawnConfig` stay in the orchestrator (they have to, so that turning the flag back on re-spawns from the saved config).

`registerNodesRoutes` in `src/server/routes/nodes.ts` is given only the orchestrator — it has no way to know the process is in the donor role. Its start/restart handlers take the owner branch whenever `isOwnerNode(id)` and `hasOwnerConfig()` are both true, which is exactly the state a founder→donor switch leaves behind, so `POST /api/nodes/owner/start` (or `/restart`) re-spawns the owner node with no trust circle, NAT or strand service wired. The existing test `start ensures the owner node` in `src/server/__tests__/nodes-route.test.ts` already shows the route spawning in that state; nothing in the route could refuse it.

`ensureOwnerNode` / `restartOwnerNode` have no other callers than this route and the founder branch of `host.ts` (grep), so the route is the one site to guard.

The role is already decided once, in `createLocalUiServer` (`src/server/index.ts`): `founder ? 'founder' : 'donor'`, passed to `registerStatusRoute` as `role: HostRole`. The nodes route should take the same value.

## Decision

- **Start/restart of the owner node in the donor role → `409` with code `own_cadre_disabled`.** 409 rather than 501: the operation exists, it conflicts with how this process was started. Message along the lines of: `start owner: this host's own cadre is turned off (donor-only mode). Set ownCadre.enabled in host.config.json (or start with --own-cadre) and restart cadre-host to run it again.` The role check comes before the saved-config check, so a donor always gets the same answer whether or not a saved config exists.
- **Stop of the owner node stays allowed** in both roles. In donor mode the node is already stopped at startup; a stop is a harmless no-op and refusing it adds nothing.
- **The stopped owner node stays listed** in `/api/nodes` and `/api/status`. It is real state on disk (its workdir and saved config persist so the founder role can resume), and the node detail page already explains it ("your own cadre is turned off", `ui/src/routes/NodeDetail.svelte` line ~146). Hiding it would leave that branch dead and make `GET /api/nodes/owner` disagree with the listing.
- **But it must not raise the dashboard's health warning.** `deriveOverallStatus` in `ui/src/lib/overall-status.ts` returns `'warn'` for any node not running, so a donor that once ran as a founder is permanently in "Attention" (noted in the review of `feat-cadre-host-donor-aware-ui`). For the donor role, ignore owner nodes in that check. `NodeInfo.owner` is already populated from `/api/status`.
