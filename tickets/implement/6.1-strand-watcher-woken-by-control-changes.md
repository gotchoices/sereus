# The strand watcher wakes on a change to Strand or JoinedStrand

## Why

GitHub #50 measured two single-machine parties sharing one strand, 60 s idle: 155 block reads across both nodes. 48 of them are the strand watcher — `queryStrands` plus `queryJoinedStrands`, one read each, every 5 s, on every node. On a two-machine cadre those reads are not local: the sibling is in the control cohort, a block read more than 10 s after its last check starts a background `/sync` request to the sibling (Optimystic's read repair, `readRepairWindowMs` 10 s), and a read of a never-written table (usually `JoinedStrand`) consults the sibling every time. A 5 s period under a 10 s window keeps that traffic going on its own. Baseline numbers are in the doc comment of `packages/integration-tests/src/scenarios/message-cost-accounting.integration.ts`.

The change subscription seam (`table-change-watch.ts`, `ControlDatabase.watchTables`, docs/architecture.md → "Table change subscriptions") has landed and has no consumer yet. This ticket is its first.

## Design

### Scheduling moves into the seam

`StrandWatcher` drops its own `setInterval` / initial `setTimeout` and drives every run through one `TableChangeWatch`:

- `StrandQueryable` gains an optional member, so the watcher still has a single "what to read and how to hear it change" interface and tests keep their plain `{ queryStrands }` fakes:

  ```ts
  export interface StrandQueryable {
    queryStrands(): Promise<StrandRow[]>;
    /** Subscribe to changes of the tables queryStrands reads. Absent: runs come from trigger and backstop only. */
    watchChanges?(onChange: () => Promise<void>, options: TableChangeWatchOptions): TableChangeWatch;
    /** True when the last queryStrands answered part of its result from a stand-in after a failed read. */
    lastReadPartial?(): boolean;
  }
  ```

- `start()`: build the watch first (subscribe), then `watch.trigger(INITIAL_RUN_DELAY_MS)` (100 ms, today's deferral, so `start()` still does not poll synchronously). Subscribing before the first read means a commit landing between them is either seen by that read or produces a follow-up run. When the queryable has no `watchChanges`, use a timer-only watch from the seam (below).
- `stop()`: dispose the watch first, then clear state as today. A run already in flight finishes as today (`poll` checks `running` on entry only).
- The backstop is `backstopMs` on the watch options, `label: 'strand-watcher'`.

**Seam addition.** Export from `table-change-watch.ts` a timer-only variant — e.g. `scheduleRuns(onChange, options): TableChangeWatch` — with the same single-flight, `trigger` and backstop rules and no table subscription. Implement it by making `TableChangeWatcher`'s subscription optional rather than duplicating the scheduler. Doc it as "for a consumer with no database to watch (tests, fakes)".

### The constructor's interval becomes the backstop

The 4th constructor argument and `CadreNodeConfig.strandWatchInterval` keep their names and now mean the backstop: the longest the watcher goes without re-reading when no change is heard. Default `DEFAULT_STRAND_WATCH_BACKSTOP_MS = 5 * 60 * 1000`, exported from `strand-watcher.ts` and used by both the constructor default and `cadre-node.ts`.

Rename rejected: the value is still "how often the watcher reads unprompted", and renaming cascades into the CLI's `CADRE_STRAND_WATCH_INTERVAL` variable, config schema, Docker entrypoint, provider orchestrator and every test that sets it, for no change in behaviour. The doc comments change instead.

Put a `NOTE:` at the constant: on a cadre larger than `CONTROL_REPLICATION_BREADTH` (16), a machine outside the `Strand` block's cohort hears no change event, so the backstop is its only path, and a strand founded elsewhere reaches it up to 5 minutes later; if that matters, shorten the backstop for such machines rather than for everyone.

### Retry bases stop riding on the interval

Today the launch-retry backoff is `pollInterval * 2^(failures-1)`. With a 5-minute interval that would make the first retry 5 minutes. Use `retryBaseMs = Math.min(backstopMs, LAUNCH_RETRY_BASE_MS)` with `LAUNCH_RETRY_BASE_MS = 5000`:

- In production (5 min backstop) the base is 5 s, as today.
- Tests and scenarios that pass a short interval (1000, 200, 250, 5000) get the same base they get today, so `strand-watcher.spec.ts`'s failed-launch tests (which use `INTERVAL = 1000` as the base) and `discovered-strands-late-subscriber.spec.ts` (`BARE_POLL_INTERVAL_MS = 5000`) need no change. Update the comment above `INTERVAL` in `strand-watcher.spec.ts` to say the base is `min(interval, 5 s)`.
- `MAX_RETRY_BACKOFF_MS` (5 min cap) is unchanged.

### Follow-up runs the watcher asks for itself

The seam clears every pending wake when a run starts, so the watcher re-arms what it needs at the end of every run. Wrap `poll()` in a `runOnce()` used both as the watch's `onChange` and by `forcePoll()`; after `poll()`, if still running, `scheduleFollowUps()`:

- **Launch retry.** If any `failureStates` entry remains, `watch.trigger(max(0, earliest nextAttemptAt - now()))`. Without this a failed launch would wait for an unrelated change or the 5-minute backstop. `forgetStrand` (called by `CadreNode.addStrand` on a failed claim, outside any run) also calls `scheduleFollowUps()` after `recordFailure`.
- **Read retry.** `poll()` reports whether its read failed (the `queryStrands` throw it already catches, or `queryable.lastReadPartial?.()` true after a successful one). On failure, `watch.trigger(readRetryDelay)` with `readRetryDelay` starting at `retryBaseMs`, doubling per consecutive failed run, capped at `min(backstopMs, READ_RETRY_CAP_MS = 60_000)`; reset on a fully successful read. Reason, stated in a comment at the site: the plugin arms a table's replicated-change bridge on the table's first successful initialization, so a machine whose first read failed (cut off from its party, or its sibling unreachable for a never-written `JoinedStrand`) would otherwise hear nothing until the backstop. Today such a machine retries every 5 s; the ladder keeps it prompt early and cheap later. The existing `NOTE:` in `poll()`'s catch about `cohort-unreachable` logging stays, adjusted to say it now logs once per ladder step.
- **Provisional `sAppId` admissions** are not polled for. Add `StrandWatcher.sAppIdLearned(strandId)`: if `provisional` holds the id, `watch.trigger()`. `CadreNode` calls it where an id becomes known: in `recordReplicaSAppId` after `replicaSAppIds.set`, and after `sAppConfigs.set` in the claim path (~5795). Today these resolve on the next 5 s poll.

### `JoinedStrandSession` reports local changes and partial reads

`withControlRows` merges the control rows with two things the control database's change events do not cover: this machine's unpublished joins (the machine-local `JoinedStrandStore`) and the joins kept for this session. Today the 5 s poll picks up changes to them.

- Constructor gains `onLocalChange: () => void`, called after `remember`, `rememberForeign` (when it recorded), `leave` and `forgetAfterThisSession` complete. `CadreNode` passes `() => this.strandWatcher?.refresh()`, where `refresh()` is `watch.trigger()`. (`syncWithParty`'s publish and remove are control writes and arrive through the subscription.)
- Record whether the last `partyWide()` read was fresh; expose it as `lastReadPartial(): boolean`. `createStrandQueryable` returns `lastReadPartial: () => this.joinedStrands?.lastReadPartial() ?? false`.

### CadreNode wiring

`createStrandQueryable` adds:

```ts
watchChanges: (onChange, options) => this.controlDatabase!.watchTables(
  ['CadreControl.Strand', 'CadreControl.JoinedStrand'], onChange, options),
```

(the watcher is constructed only after `controlDatabase.initialize()`, so the non-null holds; throw a clear error rather than `!` if the implementer prefers). `strandWatchInterval ?? DEFAULT_STRAND_WATCH_BACKSTOP_MS` replaces `?? 5000`. Remove the `NOTE:` in `createPartyJoinedStrandLedger` (~3068) that this ticket answers.

### Defaults outside cadre-core that pin 5000

These would silently keep every container on a 5 s backstop:

- `packages/cadre-cli/docker/entrypoint.sh` ~119 writes `strandWatchInterval: ${CADRE_STRAND_WATCH_INTERVAL:-5000}`. Change the fallback to `300000`.
- `packages/integration-tests/src/harness/provider-process-orchestrator.ts` ~423 mirrors the entrypoint's fallback (its doc comment says so). Change to `300000`.
- `packages/cadre-cli/example.cadre.yaml` ~126: `300000`, with a comment that it is the backstop.
- `packages/cadre-cli/README.md` ~408 and `packages/cadre-cli/src/config/types.ts` ~137, `packages/cadre-core/src/types.ts` ~943: describe it as the backstop (ms, default 300000; also caps the retry bases at 5 s).

Integration scenarios that pass a short `strandWatchMs` keep it; a short backstop is still correct, just more reads.

## Edge cases & interactions

- **Commit between subscribe and first read.** Subscribe in `start()` before `trigger(INITIAL_RUN_DELAY_MS)`. A commit before the read is seen by it; one after produces a follow-up run. By inspection.
- **Burst of strand rows** (an app founding several strands, a strand move adopting a bundle): coalesced into one run by the seam's window; changes during a run produce one follow-up. Covered by the seam's tests.
- **Slow `onStrandAdded`** (a strand launch takes seconds): a change arriving meanwhile queues exactly one follow-up run, never a concurrent one. Seam's single-flight rule.
- **`forcePoll` concurrent with a scheduled run.** `forcePoll` (tests, `unpublishStrand` ~6282, `forceStrandPoll`) still calls `poll` directly, as today, so it can overlap a seam run. Today's interval had the same overlap; `knownStrands.set` before the await and the synchronous `knownStrands.delete` before `onStrandRemoved` keep it from double-launching or double-removing. `unpublishStrand`'s own write also wakes the watch, so it gets a second, local, run. By inspection; leave as is.
- **Run start clears pending wakes.** A launch-retry or read-retry trigger armed before an unrelated change run is cleared when that run starts; `scheduleFollowUps()` at the end of every run re-arms it. A `forgetStrand` during a run arms a wake that survives (wakes are only cleared at run start). By inspection.
- **Failed first read leaves a table unarmed** (cut-off machine, unreachable sibling for `JoinedStrand`): the read-retry ladder, including the partial-read signal from `JoinedStrandSession`. By inspection.
- **Machine outside the `Strand` block's cohort** (cadre > 16 machines): backstop only; `NOTE:` at the constant.
- **Provisional `sAppId` admission**: re-evaluated on `sAppIdLearned`, not by polling. A strand whose header never syncs stays provisional until the backstop; that was already harmless ("a syncing replica").
- **Local joined-strand store changes** (`formStrand`'s `remember`, `addStrand`'s `rememberForeign`, `forgetJoinedStrand`'s `leave`, self-revocation's `forgetAfterThisSession`): `onLocalChange` → `refresh()`.
- **Stop.** `StrandWatcher.stop()` disposes the watch before clearing state; `CadreNode.stop()` stops the watcher (~5361) before `controlDatabase.close()` (~5400), and `close()` also disposes any watch still live. After `stop()`, `scheduleFollowUps` and `refresh`/`sAppIdLearned` are no-ops (the disposed watch ignores `trigger`; also guard on `running`). A `start()` failure after the watcher started goes through the same stop path; check `cleanup()` does stop it.
- **Restart.** `CadreNode` builds a new watcher per `start()`; `StrandWatcher.start()` after `stop()` must build a new watch, not reuse the disposed one.
- **`watchChanges` throws** (a table missing): let it propagate from `start()`; both tables are in the fixed control schema, so this is a programming error, not a runtime condition.
- **Control-founding consult budget.** `control-founding-consult-budget.spec.ts` pins consults during founding with `strandWatchInterval: IDLE_TIMER_MS`. If founding writes `Strand`/`JoinedStrand`, the watcher now runs on that change; its reads are of blocks held locally, so no new consult is expected. Run the spec; if a budget moves, record the measured figure and the reason, do not just raise it.
