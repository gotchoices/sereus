# The joiner hands its join to the launch

Split from `plan/formation-and-redemption-read-each-row-once` (the joiner arm, including the party-key arm moved there from `strand-founding-writes-batched`). Siblings: `implement/formation-responder-reads-the-invitation-once`, `implement/cadre-invite-and-grant-redemption-read-the-row-once`.

## What runs today (traced)

`CadreNode.formStrand` (joiner B): formation → `recordFormationStrandAddrs` → `adoptFormationMembershipInvite` (closed strand: `ensureStrandPartyKey` reads `StrandPartyKey`, mints and inserts one under its own owner approval when absent) → `rememberFormedStrand` (`JoinedStrandSession.remember`: a record in the machine-local joined-strand store; no control write).

The app then calls `addStrand(config)`:

- `rememberable` is true unless the strand watcher already offered the row (`discoveredStrands`), so `rememberForeignStrand` → `JoinedStrandSession.rememberForeign` runs: `namedByParty` = the ledger's `names` (`queryStrand` + `queryJoinedStrand`, 2 control reads), then `store.list()`, then finds the identical record `formStrand` wrote and returns.
- `launchStrand` → `startOrFoundStrand` → `resolveStrandPartyKey(strand, undefined)` → `queryStrandPartyKey`: re-reads the key `ensureStrandPartyKey` returned moments before.

The party-wide `JoinedStrand` control row is written later by an owner machine's connected reconcile pass (`JoinedStrandSession.syncWithParty` → `publish`), under its own owner approval.

## Design

**`rememberForeign` checks the local store first.** Move the `store.list()` lookup ahead of `namedByParty`: when an identical record (same `Type` and `MemberPrivateKey`) is already in the store, return without reading the control database. Behaviour is unchanged in every case: a record identical to the row and named by the party returned before too (on the `namedByParty` branch); a non-identical or missing record still goes through `namedByParty` first and is recorded only when the party does not name the strand. The `pendingRemovals.delete` stays first. The store answers from memory after its first load (`KeyStoreJoinedStrandStore.loaded`), so the reordered path costs no I/O after a join.

**The party key travels from the formation to the launch.** `adoptFormationMembershipInvite` keeps the key `ensureStrandPartyKey` returned in a node-local map (e.g. `formedPartyKeys: Map<strandId, key>`, in memory, beside `pendingMembershipInvites`). `resolveStrandPartyKey` checks, in order: the explicit attach-time key, then this map, then the `StrandPartyKey` row (then the founder mint, unchanged). The entry is consumed by the read that uses it (deleted), so a later relaunch (watcher retry, wake) reads the row as today, and is also dropped in `detachStrand` and `forgetJoinedStrand`. This mirrors what the founder side does through `StrandConfig.partyMemberPrivateKey` (`strand-founding-control-writes-in-one-transaction`), without asking the app to carry a secret.

**The `JoinedStrand` row stays a separate, later save.** The ticket asked to write it in `formStrand`'s own control transaction if one approval could cover both. The approval model allows it (`ensureStrandPartyKey` already takes a held `sign`, and `insertFoundingRows` batches owner-signed rows), but the publish must stay in the reconcile pass:

- The publish is gated on `getControlConnectionCount() > 0` so that it never commits while this machine is cut off from its own party (a write made alone is local-only and is not re-issued later). That count includes every control-node connection, and during `formStrand` it always includes the connection to the other party's responder. So inside `formStrand` the gate would always read "connected", and a disconnected machine of a multi-machine party would publish alone on every join, the fork the gate exists to avoid.
- The machine-local store path must remain regardless: a non-owner machine, or one with no signer wired, can form an open strand but cannot sign the row. A second publish path in `formStrand` adds its own conflict handling (a sibling already published, a re-formation by a party already holding the row) for a write that happens once per join.

Record this as an accepted-tradeoff `NOTE:` at `rememberFormedStrand`, with the revisit condition: the publish gate can tell a connection to this party's own machines from any other control connection.

## Edge cases & interactions

- **App passes a row that differs from the remembered record** (different `MemberPrivateKey`, e.g. a re-formation that delivered a new read secret): the store lookup does not match, so `namedByParty` runs and the record is rewritten as today. Verify by inspection.
- **Party already names the strand and the store holds no record**: `namedByParty` returns true, nothing recorded, as today.
- **Store `list()` throws** (a KeyStore load refused): today it is reached only when the party does not name the strand, then `rememberForeignStrand` catches and warns. After the reorder it is reached first, so a failed early lookup must fall through to `namedByParty` (return quietly when the party names the strand) rather than warn for a strand that needs no record; when the party does not name it, the record path fails and warns as today. Verify by inspection.
- **Open strand formation**: no party key, no map entry; `resolveStrandPartyKey` is not called for an open strand.
- **Launch before the formation** (a re-formation against a strand already running here, the removed-party case): `claimTrackedStrand` does not resolve a party key for a joiner, so the map entry is not consumed by that launch. It stays until the next launch of the strand, a detach, or `forgetJoinedStrand`. The key it holds is the same row `ensureStrandPartyKey` returned, which only changes by a deliberate delete-then-insert; check that path (`deleteStrandPartyKey`) and drop the map entry there too if it can run while the node is up.
- **Pending-join attempts** (`requestJoin` → `PendingJoinRunner.attempt` → `formStrand`): same path, same handoff; the runner's own outcome writes are untouched.
