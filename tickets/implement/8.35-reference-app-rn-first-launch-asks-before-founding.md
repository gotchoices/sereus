# Phone reference app: first launch asks before founding

Split from the plan ticket `reference-apps-join-existing-cadre`. Moving strands and dissolving the old cadre (`move-strand-between-cadres`, `dissolve-empty-cadre`) stay for apps that started on their own; this ticket keeps a new app from starting on its own when the user already has a cadre. `app-recommends-another-app-and-enrolls-it` (iOS path) relies on this question existing.

## Today

The app founds its party when the user taps Connect with an empty Party ID (`handleConnect` → `uuid()` → `cadre.start`, the kit runs owner genesis). Nothing asks first. The join section (`reference-app-rn-joins-existing-cadre`) can already run from a stopped app: the kit's `joinCadre` needs no running node, and `identityPeerId()` gives the request's peer id without one.

## Behaviour

- **When to ask:** the launch read of the saved start has resolved, it found nothing (`savedStartOptions === null`, and the read did not fail), the hook's status is `idle`, and no join flow is active. A saved start means the app has a party (founded or joined), so it never asks again. If the read failed, do not ask: the existing error line already explains, and the Connect form is the recovery.
- The hook exposes `savedStartLoaded: boolean`, set when the launch read resolves (found or not). Today `savedStartOptions` is null both before the read and when nothing is saved, so Settings cannot tell them apart.
- **The question** replaces the Node card's Connect form until answered: title "Do you already use Sereus apps?", one line "If another Sereus app, on this phone or another device, already holds your cadre, this app joins it instead of starting its own.", buttons **Yes, join my cadre** and **No, start fresh**.
  - Yes: render the join section (`JoinCadreSection` in its stopped mode: request, paste, join) in place of the form, with a **Back** link to the question.
  - No: the Connect form as today.
  - The answer is screen state, not saved: until a start is saved the question comes back on the next launch, which is what a user who backed out expects.
- **A first-launch join** starts the node for party A with the build's default relay and Noise mode; the join ticket already passes those when neither a running nor a saved start exists. After it, the saved start exists (`origin: 'joined'`, no `formerPartyId`), so the next launch resumes A and never asks.
- The `Add an always-on node` and the deep-link node-code hint (`waitingNodeCode`) keep working: a node code opened before the question is answered shows the existing "Connect first" hint under whichever card is visible.

## Edge cases & interactions

- The launch read resolves after Settings mounted: the question appears then; before that the Node card shows its status line only (no Connect button flashes then disappears). By inspection.
- A push wake on a fresh install: there is no saved start, so a push wake starts nothing; unchanged. By inspection.
- The user answers Yes, then the join fails: the kit leaves the app stopped (nothing ran before); the question's Yes state stays, so the user can paste again or go Back. By inspection.
- The user answers No, taps Connect, and it fails: status `error`, not `idle`, so the question does not return mid-session. By inspection.
