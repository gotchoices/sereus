# Phone reference app: "Join my existing cadre" (the joining side)

Split from the plan ticket `reference-apps-join-existing-cadre`. App B is this app; party B is the one-node cadre it founded; party A is the user's main cadre. The owner side (minting the invitation) is `reference-app-rn-owner-adds-device-or-app`, which also builds `ShareCode` (QR + Copy) and the generalized `CodeScanner` used here. The first-launch question that lets a new app reach this flow without founding a cadre is `reference-app-rn-first-launch-asks-before-founding`.

Everything below the UI exists in the kit (`@serfab/cadre-rn/phone-node`, README → "Joining another cadre", "Moving the app's strands", "Dissolving the left cadre"):

- `joinCadre(invitation, { signal, onProgress, relayAddrs?, noiseCryptoMode? })` → `JoinCadreResult` (`grantsOwner`, `peerId`, `formerPartyId?`, `strandMove?`). Switches party, carries B's strands, rolls back to B on any failure or cancel. `onProgress` receives `PhoneJoinProgress` (`redeeming`, `waiting` with `reason`, then `admitted`, `moving-strands`; the last two from `phone-kit-identity-peer-id-and-join-phases`).
- `identityPeerId()` (same prereq): the app's peer id, with or without a node.
- `pendingStrandMove()`, `finishStrandMove()` (throws cadre-core's `StrandMoveNotOwnerError` while the key is no owner).
- `dissolveFormerParty({ discard? })`: refuses with `StrandMovePendingError` or `FormerPartyNotEmptyError` (`otherMachines`, `strandIds`, `pendingJoinIds`).

## Screen: `src/join-cadre-section.tsx`

Replaces Settings' "Join a Cadre" section. Title **Join my existing cadre**. One line: "If another Sereus app already holds your cadre, this app can join it. Its chats move with it, and its own cadre is then removed from this phone."

Terminology fixed by the plan: B shows **Copy request**, and accepts **Paste response** (the targeted invitation the owner app made from the request) or **Paste invitation** (an open one). Both are the same `sereus-invite:1.` text, so one field serves both, labelled "Paste response or invitation".

1. **Copy request.** `ShareCode` with `encodeCadreJoinRequest({ v: 1, peerId: await cadre.identityPeerId(), appName })`. `appName`: `Constants.expoConfig?.name` (expo-constants, already a dependency), trimmed, falling back to "Sereus reference app"; cap at `CADRE_JOIN_REQUEST_MAX_APP_NAME`. Hint: "Paste this in the app that holds your cadre, under Add a device or app → Paste request. Or ask that app for an open invitation."
2. **Paste response or invitation.** Multiline field (keep test id `input-cadre-invitation`), "Scan" (`CodeScanner` accepting `CADRE_INVITATION_PREFIX`), "Join" (keep `btn-join-cadre`). Before calling the hook:
   - `decodeCadreInvitation` (it names a request pasted here); its message in the alert.
   - Targeted at another peer: `invitation.invite.peerId` set and not equal to `identityPeerId()` → "This response was made for another app. Copy this app's request again and ask for a new one." No join.
3. **Progress** (below), replacing the two inputs while a join flow is active.

**Room for the deep link.** `same-phone-apps-exchange-join-by-deep-link` will make a link between two apps on one phone the main path, with copy/paste as its fallback. Structure this so that ticket only adds an entry point and a return handler: the request text comes from a hook action (`joinRequestText()`), not from inside the component, and a returned invitation enters through the same `joinExistingCadre(encoded)` the Join button calls, with the targeted-at-another-app check inside the hook rather than the component.

**Visibility.** Settings renders this section while connected, and also whenever the hook's `joinFlow` is not null, whatever the status: during a join the status is `connecting` and Settings hides its connected sections today, which is why nothing showed the wait (review note on `app-joins-existing-cadre-by-invitation`). It is also rendered while stopped when the first-launch ticket asks for it (accept a prop for that; this ticket renders it connected-only otherwise).

## The join flow: `src/join-flow.ts` and the hook

`join-flow.ts` holds the flow's state type and its plain-language text, no React:

```ts
export type JoinFlow =
	| { step: 'joining'; wait?: 'no-member-answered' | 'member-not-ready'; retryAtMs?: number }
	| { step: 'admitted'; grantsOwner: boolean }
	| { step: 'moving-strands' }
	| { step: 'removing-old-cadre' }
	| { step: 'move-incomplete'; moved: number; waiting: string[]; reason: 'owner-key-not-wired' | 'adoption-failed' | 'partial'; message?: string }
	| { step: 'old-cadre-kept'; otherMachines: string[] }
	| { step: 'confirm-discard'; strandIds: string[]; pendingJoinIds: string[] }
	| { step: 'old-cadre-remains' }
	| { step: 'done'; grantsOwner: boolean; moved: number };

export function joinFlowText(flow: JoinFlow): { line: string; detail?: string };
```

Text (adjust wording, keep the meaning):

| Step | Line |
| --- | --- |
| `joining` | "Joining your cadre…" |
| `joining` + `no-member-answered` | "Waiting for an always-on machine of your cadre to answer. Next try at ‹time›." |
| `joining` + `member-not-ready` | "Your cadre is catching up. Next try at ‹time›." |
| `admitted` | "Admitted. Setting this app up as an owner…" (member: "Admitted as a member…") |
| `moving-strands` | "Moving this app's chats into your cadre…" |
| `removing-old-cadre` | "Removing this app's old cadre from this phone…" |
| `move-incomplete` | "‹moved› chats moved; ‹waiting.length› are still waiting." + reason line: not an owner yet ("This app is not an owner of your cadre yet, so its chats cannot move. They move as soon as it is.") / failed ("Moving stopped: ‹message›") / partial ("Some could not be moved this time.") |
| `old-cadre-kept` | "This app's old cadre also has other machines (‹n›), so it was kept on this phone. Nothing was lost; you can ignore this." |
| `confirm-discard` | "‹n› items from this app's old cadre are not in your cadre (they may have been removed there). Delete them with the old cadre?" |
| `old-cadre-remains` | "This app's old cadre is still on this phone." |
| `done` | "This app is now part of your cadre (as an owner / a member). ‹moved› chats moved." |

Buttons: `joining` → **Cancel**. `move-incomplete` → **Retry moving** and **Later**. `confirm-discard` → **Delete them** and **Keep old cadre**. `old-cadre-remains` → **Remove it now**. `old-cadre-kept`, `done` → **OK** (clears the flow). No cancel after admission: the kit never rolls back an admitted join.

**Hook (`use-cadre.ts`)**, new state `joinFlow: JoinFlow | null` and actions; the flow lives in the hook (the app-root context), not in Settings, so it survives a tab switch:

- `joinExistingCadre(encoded)` replaces `joinCadre`:
  1. `setJoinFlow({ step: 'joining' })`, status `connecting`, a new `AbortController` in a ref, and **`showNode(null)`**: the node the join stops must not stay in the hook, where a screen could write through it (review note).
  2. `joinCadreByInvitation(invitation, { signal, onProgress, ...startDefaults })`. `onProgress` maps `waiting` / `admitted` / `moving-strands` onto `joinFlow` (`redeeming` keeps `joining`, clearing `wait`). `startDefaults`: when the kit has neither a running nor a saved start (a first-launch app), pass `relayAddrs: resolveRelayAddrs(undefined)` and `noiseCryptoMode: defaultNoiseCryptoMode()`, the defaults a Connect tap uses; otherwise pass nothing and the kit uses the running or saved start's.
  3. `finally`: `adoptRunningNode()`, then `setSavedStartOptions(getRunningOptions())` so the Connect form shows the party the app is in now (review note: it kept the party id from launch, so Disconnect → Connect restarted the left party).
  4. Admitted: publish the device token as today; then `settleAfterJoin(result)`: `strandMove` `partial` / `deferred` → `move-incomplete` (counts from `report.moved` / `pendingStrandMove().strandIds`); otherwise, when `result.formerPartyId` is set, `removeOldCadre()`; otherwise `done`.
  5. Failed: clear the flow; when the signal was aborted, alert "Join cancelled. This app is back in its own cadre."; otherwise `describeJoinFailure(err)`.
- `cancelJoin()`: aborts the controller (only meaningful during `joining`).
- `retryStrandMove()`: `finishStrandMove()` through `cadre-phone.ts`; `StrandMoveNotOwnerError` → stay in `move-incomplete` with the not-owner reason; a report with nothing failed → `removeOldCadre()`; still failing → `move-incomplete` again.
- `removeOldCadre(discard?)`: `removing-old-cadre`, `showNode(null)` (the dissolve stops and restarts the node), `dissolveFormerParty({ discard })`, then `adoptRunningNode()` and `setSavedStartOptions(getRunningOptions())`. `StrandMovePendingError` → `move-incomplete`; `FormerPartyNotEmptyError` with `otherMachines` → `old-cadre-kept`; with only strands or joins → `confirm-discard` (Delete them → `removeOldCadre([...strandIds, ...pendingJoinIds])`; Keep → `old-cadre-kept` with no machines, wording "kept on this phone"); success → `done`. Any other error → alert with the message and `old-cadre-remains`.
- **On connect and at launch**, when the running options name a `formerPartyId` and no flow is active: `pendingStrandMove()` → `move-incomplete`, else `old-cadre-remains`. This covers a kill between the steps and a user who tapped Later.
- `dismissJoinFlow()`.
- `cadre-phone.ts`: pass-throughs for `identityPeerId`, `pendingStrandMove`, `finishStrandMove`, `dissolveFormerParty`. `UseCadreResult` gains `joinFlow`, `identityPeerId`, the actions above; `joinCadre` is removed (Settings is its only caller).
- Settings' launch-refill effect comment ("The hook sets them exactly once") becomes: set at launch and after a join or dissolve, both while the Connect form is hidden.

**`join-failure.ts`**: add `StrandsNeedOwnerJoinError` (from `@serfab/cadre-rn/phone-node`): "This invitation makes the app a member, and only an owner can bring this app's ‹strandCount› chats along. Ask for one with “Also an owner” on." The reference-app-ns twin is not touched (it has no cadre join).

## Edge cases & interactions

- Cancel while waiting: the kit restarts B (or leaves it stopped if it was stopped); the hook adopts B, the flow clears, the alert says so. B is unchanged. By inspection.
- Kill while waiting: nothing saved; relaunch runs B; no flow shown. By inspection (kit behaviour).
- Kill after admission, before the move finished: relaunch runs A and the kit's start adopts the record; if it is still pending, the launch check shows `move-incomplete`, else `old-cadre-remains`. By inspection.
- Kill during the dissolve: the kit finishes the removal at the next start (dissolve marker); the launch check then finds no `formerPartyId` and shows nothing. By inspection.
- Paste an invitation for the party the app is already in: the kit redeems in place (no switch, no move); `result.formerPartyId` may name an earlier party, in which case the dissolve step runs. By inspection.
- A member (non-owner) invitation while B holds chats: the kit refuses before anything stops (`StrandsNeedOwnerJoinError`); the new wording explains. By inspection.
- An owner grant that has not reached the phone when the join ends (`strandMove` deferred, `owner-key-not-wired`): `move-incomplete` with Retry; a later start also adopts by itself. By inspection.
- The request shown while the app is stopped (first launch) and the peer id later used by the start must match: guaranteed by `identityPeerId()` running in the kit's queue (tested in the kit ticket).
- The background runner during a join: `showNode(null)` tears its effect down, `adoptRunningNode` brings it back for the new node; `optsRef` is refreshed in `adoptRunningNode` already. By inspection.
- A second Join tap during a flow: the inputs are not rendered while `joinFlow` is set. By inspection.
- Push-wake during a join queues behind it in the kit and gets whatever node the join left running (existing behaviour). By inspection.
