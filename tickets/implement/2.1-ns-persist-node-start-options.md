# NativeScript: remember the node's start options

## Problem

`packages/reference-app-ns` takes its `PhoneNodeOptions` (`partyId`, `bootstrapAddrs` — `cadre-phone.ts`) from two Settings fields and stores them nowhere; `SettingsViewModel.onConnect` mints a fresh party id whenever the field is blank. Every node-local record in the `sereus-peer-identity` SQLite `kv` table is filed under the party id, so a relaunch with a new id reads empty records. The sharpest case: pasting a group leader's invitation writes that leader's key into the trusted-owner anchor under the current party id (`feat-ns-invite-trust-pinning`); relaunch, get a new id, read an empty anchor, and the next join bundle from that leader is refused. The NativeScript app has no push-wake path, so the only unattended start is app launch.

## Design (settled — mirrors `rn-persist-node-start-options`)

Read the landed React Native change first (`packages/reference-app-rn/src/start-options.ts`, its `cadre-phone.ts`, `use-cadre.ts`) and follow the same shape. Differences are listed below; everything not listed is the same decision for the same reason.

### Record and parser

`src/start-options.ts` (no NativeScript or SQLite imports): `SavedStartOptions { options: PhoneNodeOptions; autoStart: boolean }`, `parseSavedStartOptions`, `serializeSavedStartOptions`, serialized as `{ "version": 1, "partyId", "bootstrapAddrs", "autoStart" }`. Same parse rules as the RN parser minus the two fields this app does not have (no `relayAddrs`, no `noiseCryptoMode`): absent / unparseable / wrong version / blank `partyId` ⇒ `undefined` with a warning; malformed `bootstrapAddrs` ⇒ `[]`; non-boolean `autoStart` ⇒ `false`. A separate copy rather than a shared module, as `node-local-slots.ts` already is: the two apps share no app-level package, and a start-options record does not belong in `@serfab/cadre-core`.

`PhoneNodeOptions` is declared in `cadre-phone.ts`, which imports SQLite and libp2p. Move the interface into `start-options.ts` and re-export it from `cadre-phone.ts` so existing imports keep working, keeping the parser module import-free.

### Backend

The `sereus-peer-identity` SQLite database's `kv` table, through the same unprefixed `SqliteKVStore` the node-local records use, under the literal key `start-options` (add `START_OPTIONS_SLOT_KEY` to `node-local-slots.ts`, extend its module comment). No new dependency; this database is already the app's one app-private store.

### `cadre-phone.ts`

- **Cached open.** Replace `identityDb ??= await openOptimysticNSDb(...)` with an accessor that caches the in-flight open *promise* (`identityDbOpening`), as the existing NOTE in `startPhoneNode` prescribes. Unlike React Native, this open is asynchronous: a launch-time load and a Connect tap can now both reach it, and two overlapping opens would leak one native handle. Clear the cached promise wherever `identityDb` is cleared today (in `stopPhoneNode`, and on a rejected open so the next call retries). Delete the NOTE.
- `loadSavedStartOptions()` exported; a read fault propagates.
- Save `{ options: opts, autoStart: true }` after a successful `node.start()`; best-effort, logged. Record the started options in a module variable.
- `stopPhoneNode` saves `{ options: <recorded>, autoStart: false }` before `stopping.stop()` and before the handle is closed; best-effort, logged; skipped when nothing was recorded.
- Single-flight `startPhoneNode` via a cached `starting` promise, and `stopPhoneNode` awaits an in-flight start (ignoring its rejection) before tearing down — same as RN.
- Update the NOTE in `startPhoneNode` that names `feat-rn-persist-node-start-options`.

### `cadre-vm.ts` — launch restore

Add `CadreViewModel.restore(): Promise<void>` and a `savedStartOptions: PhoneNodeOptions | null` observable property (notify `'savedStartOptions'`). `restore` loads once; sets `savedStartOptions`; if `autoStart` is true and `status` is still `'idle'` (the user has not started anything while the load was in flight), calls `this.start(saved.options)`. A read fault ⇒ `console.warn` plus `setError('Could not read the saved connection settings: …')`, no start.

Call `void vm.restore()` from `getCadreVm()` when it first creates the singleton — not from the constructor, so tests that construct the view model directly are unaffected. The Chat page is the default page (`app/app-root.xml`) and binds the singleton on load, so this runs at launch.

### `settings-view-model.ts`

In the constructor, prefill `partyId` and `bootstrapAddr` from `cadre.savedStartOptions` when present (bootstrap as `bootstrapAddrs.join(', ')`); if it is still `null`, subscribe to the cadre view model's `propertyChange` for `'savedStartOptions'` and prefill once when it arrives, only into fields that are still empty. `onConnect` splits the bootstrap field on commas (trimmed, blanks dropped) so a saved list round-trips; a single address behaves exactly as today.

## Edge cases & interactions

- **Relaunch with `autoStart: true`** ⇒ same party id, so the trusted-owner anchor from a pasted invitation is read back and a later join bundle from that leader is accepted with the invite field blank. Covered by the `cadre-phone.spec.ts` test below (record round-trip across a module reload); the anchor's own reload is already covered by the existing "surfaces a trusted-owner envelope pre-seeded under the literal key" test.
- **Relaunch after Disconnect** ⇒ fields prefilled, nothing started.
- **Connect tapped while the launch load is in flight** ⇒ `restore` sees `status !== 'idle'` and does not start; the cached open prevents a second handle. By inspection.
- **Disconnect during the launch auto-start** ⇒ stop waits for the start, then stops; record ends `autoStart: false`. By inspection.
- **Corrupt record** ⇒ absent, warned, replaced by the next successful start. Parser branches are identical to the RN copy, which carries the parse test; do not duplicate it here.
- **Save failure** ⇒ logged, node unaffected. By inspection.
- **`startSolo`** (`solo-smoke.ts`) goes through `startPhoneNode`, so it also writes the record. Harmless — it is a smoke path — but say so in `startSolo`'s doc comment.
