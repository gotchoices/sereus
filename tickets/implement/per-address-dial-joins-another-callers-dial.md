# Finish the queue-free per-address dial

## What was wrong

libp2p 3.3.11's `DialQueue.dial` joins any queued job whose peer id equals the new dial's, whatever address the new dial names (`dial-queue.js` ~100–122). The new address is only added to that job's address set, which the job reaches after the address it is on finishes under libp2p's own `addressDialTimeout` (39 s at cadre's default). A joined job aborts only once every caller that joined it has aborted (`job.js` → `onAbort`). So while anything else dials the same peer by id, every per-address attempt in `tryAddrsInTurn` joins that job and times out on whichever address the job is on. In the claim flow the other caller is FRET's membership probe: `seedStreamOpener` merges the target's addresses into the address book before `connectForDelivery` dials, and FRET pings the new peer. Any Optimystic cluster dial, reconcile pass or strand redial can do the same.

Reproduced in `test/peer-dial.spec.ts` → "dials every address even while another dial of the same peer is in flight": a `dialer.dial(peerId)` started 100 ms into attempt 1 made every attempt time out at its limit, the second silent server was never contacted, and the live address was never dialed. The same shape made `cadre-node-dial-past-dead-addresses.spec.ts` fail every time at a 2000 ms per-address limit, and intermittently at 500 ms under full-suite load.

## What the fix stage landed (in the tree, verified)

`peer-dial.ts` → `dialAddr(dialer, addr, signal, label)` dials ONE address through `libp2p.components.transportManager.dial` — the internal seam `relay-reservation.ts` already uses — instead of `libp2p.dial`. The transport manager dials exactly the address given and never joins anything. `dialPeerAddrs` uses it for every attempt. Consequences the helper covers:

- **Gating.** The queue consulted `denyDialPeer` and `denyDialMultiaddr`; `dialAddr` runs both itself before dialing (cadre's control-node gater refuses outbound dials during bring-up through `denyDialPeer`, and a closed strand's gater refuses revoked peers there). The upgrader still runs `denyOutboundConnection` and verifies the peer id the address carries during the Noise handshake, so identity is still checked for a bound address. The integration harness's `peer-dial-gate.ts` relies on exactly these three hooks and needs no change.
- **Shutdown.** The queue aborted its jobs on `libp2p.stop()`; a transport-manager dial has no such tie. `dialAddr` refuses to start when `dialer.status` is not `started` and aborts an attempt in flight on the node's `stop` event (`AddrDialer` gained optional `status`; the event is read structurally so test doubles need not supply it).
- **Relayed addresses.** A circuit address must keep its target id, and the circuit transport dials the relay leg by peer id through the queue (`openConnection(relayPeer)`), so the relay leg can still be joined. The one-macrotask wait between attempts stays for that reason, and `nextMacrotask`'s other caller (`cadre-invite-protocol.ts`) is unchanged.
- **Fallback.** Without `transportManager.dial` (libp2p internals moved) the attempt goes through the queue with a log line. The concurrent-dial spec is the pin: it fails on the fallback.

Verified: `tsc -p tsconfig.typecheck.json`, eslint, `peer-dial.spec.ts` (10 cases), `cadre-node-dial-past-dead-addresses.spec.ts` at 500 ms and at 2000 ms per address, `control-database-offline-peers.spec.ts`, `strand-wake-protocol.spec.ts`, `strand-peer-redial.spec.ts`, and one full `yarn workspace @serfab/cadre-core test` (161 of 162 files green before the one edit below, log in `tickets/.logs/per-address-dial-joins-another-callers-dial.suite.log`). `docs/architecture.md` → "Cohort auto-connect" has the new paragraph.

The one test edit: `control-database-offline-peers.spec.ts` → "stop() resolves inside its budget with a WebRTC dial in flight" asserted that the sibling's own dial sat in the dial queue beside its relay hop. The sibling's dial no longer enters the queue; the assertion was dropped with a comment and the case still waits on the relay hop, which does.

## What this ticket finishes

**Identity for unbound addresses.** `applySeed`'s owner dial passes `parseDialAddrs` output, which is not bound to the owner's id; through the queue that already meant no expected peer, and through the transport manager it still does (Noise derives the remote, nothing compares it). Give `dialPeerAddrs` the expected peer id explicitly — every caller has it (`sibling.peerId`, bootstrap `peerId`, `peer.peerId`, the redial map key, `target.peerId`) — bind each address with `withTrailingPeerId`, and drop one that names another peer, logged. `dialAddr` then needs no post-dial check. `peer-dial.ts` currently imports `trailingPeerId` from `peer-record.ts`; its header promises independence from the rest of the package (to stay import-cycle-free), and `peer-record.ts` pulls in the crypto plugin, so move `trailingPeerId`/`withTrailingPeerId` into `peer-dial.ts` and re-export from `peer-record.ts`, or write the two-line equivalent locally.

**Reuse of an open connection.** The queue's `findExistingConnection` is skipped now. `connectForDelivery` checks first (`openUnlimitedConnection`), reconcile skips connected siblings, and the strand redial filters members it is connected to — confirm that last one in `strand-peer-redial.ts` → `eligible`. `dialWake` (`dialProtocol(addr)`) and `exchangeRedemption` (`dialProtocol(addr, protocol)`) reuse an open connection today and must keep doing so when they move to `dialAddr` (next item). The shape is the open question: `RedialNode extends AddrDialer` declares `getConnections(): ReadonlyArray<{ remotePeer }>` with no `status`/`limits`, so an optional `getConnections?(peerId): Connection[]` on `AddrDialer` fails the typecheck (tried). Options: a separate structural slice `dialAddr` reads like `StopEventsLike`, a reuse step in the callers that have a real `Libp2p`, or widening `RedialNode`'s double. Pick one and say why at the site.

**The two other per-address dialers.** `sendWake` (`strand-wake-protocol.ts`) and `exchangeRedemption` (`cadre-invite-protocol.ts`) still dial through `dialProtocol(addr)`, so a concurrent dial of the target joins them exactly as before. Switch both to `dialAddr` followed by `connection.newStream(protocolId, { signal, runOnLimitedConnection: true })`, keeping each one's own order (signalling first for wake; the invitation's member order) and the macrotask wait. `dialWake`'s existing spec covers the stream exchange; one new case per dialer is not needed unless the switch changes an observable order or error.

**Shutdown tests.** `control-database-offline-peers.spec.ts` → "stop() resolves inside its budget with a blackhole dial in flight" waited for the queue to be non-empty; the blackhole's direct dial never enters the queue now, so the wait runs until the pass settles and `stop()` is tested after the dials, not during. Give both stop-mid-dial cases an observation point that holds for a queue-free dial — for example an exported in-flight attempt count from `peer-dial.ts`, or a loopback silent server (`test/silent-server.ts`) whose `accepted()` shows the attempt — and add one `peer-dial.spec.ts` case that an attempt in flight to a silent server rejects promptly when the dialer stops (the `stop` event path has no test yet). `dialQueuePeerIds` is then used only for the relay hop.

**Queue bookkeeping that is now skipped.** The queue also recorded last-dial success/failure in the peer store (`LAST_DIAL_SUCCESS_KEY`, used by libp2p's address sorter, which these dials do not use), applied `maxParallelDials`/`maxDialQueueLength`, and refused self-dials before the network (the upgrader still throws `Can not dial self` after the handshake; `applySeed` filters self; reconcile never lists self). Say this in `dialAddr`'s doc comment so the next reader does not rediscover it, and leave a `NOTE:` tripwire at the relay-leg line: the relay leg still goes through the queue and can be joined by another dial of the relay; fine while a relay connection is normally already open for the reservation, revisit if a relayed attempt is ever seen timing out while a relay dial by id is in flight.

**Integration check.** Run the two scenarios whose isolation depends on the dial gate — `control-cohort-edge-carries-data.integration.ts` and `control-cohort-three-node-isolation.integration.ts` — plus `blind-relay-phone-to-phone-e2e` for a relayed attempt. Run single files; the full integration suite is not agent-runnable.

**Timing.** Re-measure `cadre-node-dial-past-dead-addresses.spec.ts` under full-suite load (two or three `yarn workspace @serfab/cadre-core test` runs, the spec's elapsed values from the log). With the join gone the live address gets its whole 500 ms; isolated it needed 110–190 ms and under load up to 345 ms before the fix. Raise `PER_ADDRESS_MS` only with that measurement, and record the numbers in the spec's constant comment.
