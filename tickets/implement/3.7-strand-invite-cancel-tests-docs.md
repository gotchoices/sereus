## What already landed in the working tree (uncommitted, UNVALIDATED)

Nothing below has been compiled, typechecked, linted, or run. Treat it as a draft to
verify, not as working code.

- `strand-membership-writer.ts`
  - `scanInviteKeys(db, 'ConsumedInvite' | 'CancelledInvite')` — module-private helper
    returning a `Set` of `InviteKey` values via an unfiltered scan (the scan-not-seek idiom
    the `scanMemberPeers` doc block argues for: those tables' primary key is the single
    `InviteKey` column, so any where-equality on it is a full-primary-key predicate the
    optimystic virtual-table module serves as a point lookup that can miss on a networked
    strand).
  - `cancelInvite(db, { managerKeyPair, inviteKey })` — signs
    `signStrandApproval(['Strand.CancelledInvite', 'cancel', inviteKey], ...)`, inserts one
    row `with context ManagerKey = ?, ManagerSignature = ?`. Insert-if-absent (quiet `log()`
    no-op when the key is already cancelled). No transaction — one statement.
  - `listOutstandingInvites(db, nowMs?)` → `OutstandingInvite[]` (`{ inviteKey, expiration }`)
    — scans `Invite`, subtracts the `ConsumedInvite` and `CancelledInvite` key sets, drops
    anything with `expiration <= canonicalDatetime(nowMs ?? Date.now())` (strict `>` to
    match the on-engine `NotExpired` gate, so expiry is exclusive).
  - `revokeMember`'s doc block: the paragraph claiming an unspent invite cannot be
    neutralized is replaced with the post-fix rule (explicit `cancelInvite`; removal does
    not cascade, because an invitation names no invitee — pointer to
    `feat-strand-invitee-bound-invites`).
- `index.ts` — exports `cancelInvite`, `listOutstandingInvites`, `type CancelInviteParams`,
  `type OutstandingInvite`.
- `strand-member-registry.ts` — `isAuthorizedToJoin` now uses `listOutstandingInvites` for
  the invite half instead of a raw `Strand.Invite` count (which over-reported: it counted
  consumed and cancelled invitations). Its `canonicalDatetime` import was dropped along with
  the inline expiry query. The `ConsumedInvite` short-circuit is unchanged but now carries a
  `NOTE:` explaining that it returns `true` for a revoked member holding a stale consumption
  row, and why that is harmless (the on-engine constraints are the real gate).

Read those before writing tests — the doc comments state the intended semantics precisely,
and a test that contradicts one of them has found either a bug or a wrong comment.

## Build order trap — read before running anything

**Before any `cadre-core` test run:**

```
yarn workspace @serfab/quereus-plugin-sereus build
```

`cadre-core` loads the embedded strand schema from that package's `dist/`, and the root test
wiring does not build first. On an unbuilt tree a `cadre-core` run silently uses the OLD
schema and reports a meaningless green, or fails with `Table not found:
Strand.CancelledInvite`. Filed as `backlog/debt-embedded-schema-stale-dist-false-green`.

## Tests

### `packages/cadre-core/test/strand-membership-invite.spec.ts`

Add `'CancelledInvite'` to the `tableCount` table union (line 55). The harness gives
`openStrand('c')` (founder is Member #1 and sole Manager), `freshKeyPair()`, and 30s
per-test timeouts — follow the existing shape exactly. Import `cancelInvite` /
`listOutstandingInvites` from `../src/strand-membership-writer.js`.

New `describe('cancelInvite')`:

- A cancelled invitation cannot be consumed — pin `/NotCancelled/`; it is the only
  constraint that can fire on an otherwise-valid consume.
- The whole join rolls back: no new `Member` row, no `ConsumedInvite` row. Mirror the
  existing wrong-key / expired atomicity assertions (lines 220-234, 258-273).
- A non-manager cannot cancel — pin `/Authorized/`.
- A manager seated in the SAME transaction cannot cancel — pin `/Authorized/`. Copy the
  shape from `strand-member-revocation.spec.ts:695` (`addManager` plus the action under test
  inside one transaction). That spec's local `inTransaction` helper (line 229) is not
  exported — duplicate it or drive `beginTransaction`/`commit` inline.
- A cancel approval minted for invite A does not cancel invite B — pin `/Authorized/` (the
  digest binds `new.InviteKey`). Needs a hand-rolled insert, since `cancelInvite` always
  signs the key it inserts.
- UPDATE and DELETE of an existing `CancelledInvite` row are refused — pin `/Immutable/`.
  Copy the shape from the `Revocation` `Immutable` test
  (`strand-member-revocation.spec.ts:785`).
- A second `cancelInvite` for the same key is a quiet no-op: no throw, still one row.

New `describe('listOutstandingInvites')`:

- Omits consumed, cancelled, and expired invitations; includes a live one. Pin `nowMs` so
  expiry is deterministic — the existing expiry tests use
  `const base = Date.UTC(2031, 2, 4, 12, 0, 0)` and `86_400_000` for a day.
- Worth one case on the returned `expiration`: a never-expires invitation reports `null`, a
  timed one reports the canonical string (compare against `canonicalDatetime(db, ms)`, which
  the spec already imports).

Also extend the existing `StrandMemberVerifier.isAuthorizedToJoin` describe (line 408) — its
three cases only cover expiry. The changed behavior is that a **cancelled** invitation, and
an **already-consumed** one, no longer hold the door open. Both are new false cases.
