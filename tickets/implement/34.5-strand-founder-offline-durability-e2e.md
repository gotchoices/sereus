## Why a second ticket

`strand-block-backfill-on-peer-join` proves the **bytes moved** — it polls the joiner's raw block
store and asserts it covers the founder's. That is a storage claim. It does not prove the joiner
can *use* those bytes without the founder, which is the reason the gap mattered in the first
place. This ticket adds the survivability test: stop the founder, then read the strand's founding
membership rows from the joiner's own database.

Separate ticket, not a fifth bullet on the first one, because it carries a distinct failure mode
(see *The dependency that can sink this*) and because a red result here must not hold back a
mechanism that is otherwise measurably working.

## The test to add

In `packages/integration-tests/src/scenarios/strand-membership-closed-strand-e2e.integration.ts`,
a new `it(...)` alongside the existing four. Shape:

- `bringUpClosedStrand('offline-founder')` — the existing fixture; it already gates on the
  founder's bootstrap rows becoming visible to the joiner.
- **Wait for the catch-up to finish, through the RAW STORE only**: poll
  `blockCoverageIsComplete(await compareBlockCoverage(founderStore, joinerStore))` (no `include`
  narrowing) until complete, under the file's `GATE` budget. Reading the raw store cannot itself
  pull a block in; a `joinerDb` read could. Failing this poll is a failure of the *previous*
  ticket, so report it as such rather than proceeding into a meaningless second half.
- **Stop the founder**: `await founderNode.stop()`. Then assert the joiner's strand node really is
  alone — `joinerStrand.libp2pNode!.getConnections().length === 0`, polled — otherwise the reads
  below could still be answered over the wire and the test would prove nothing. This is the same
  trap the disconnection scenario fell into; see the second caveat in
  [`tickets/blocked/offline-node-cannot-serve-its-own-data.md`](../blocked/offline-node-cannot-serve-its-own-data.md).
- **Now read `joinerDb`** — from this point it is not only allowed but the whole point:
  - `select count(*)` on `Strand.Header`, `Strand.Member`, `Strand.Manager` each ≥ 1
  - `Strand.Header.Type` is `'c'`
  - the founding member's key resolves: `select Key from Strand.Member where Key = ?` bound to
    `founderKeyPair.publicKeyB64` returns that row
  - `select MemberKey from Strand.Manager` returns the same key
- Teardown must stop the joiner (and tolerate the already-stopped founder) — extend or reuse
  `stopBoth`.

Give the test its own generous timeout in line with the file's others (60 s), and log the block
counts on both sides before the founder is stopped, so a future reader can see what the joiner was
holding when it went solo.

## The dependency that can sink this, and what to do about it

With the founder stopped, the joiner's strand libp2p node has **zero** connections, so every read
must resolve *itself* as the coordinator. Optimystic guards that: `shouldAllowSelfCoordination`
refuses for 30 seconds after the last connection drops (`grace-period-not-elapsed`). The guard now
has a **degraded-read** escape — a denial that is `deferrable`, with `intent === 'read'` and zero
connections, admits self anyway (`libp2p-key-network.ts`, `findCoordinator` →
`findCoordinator:fret-self-degraded`) — which is exactly this test's case, so it is expected to
pass. That escape landed upstream recently; this repo consumes `../optimystic` through the root
`package.json` `resolutions` `link:` entries, so a stale build there is the likeliest way to see
the old behaviour. If the guard fires, the error is verbatim:

```
Self-coordination blocked: grace-period-not-elapsed. No coordinator available for key.
```

If and only if that exact fingerprint appears:

- Rebuild `../optimystic` and re-run before concluding anything.
- If it still fires, this is the pre-existing dependency already tracked as
  `blocked/offline-node-cannot-serve-its-own-data`. Do **not** commit a red test, do **not**
  add a 30-second sleep to step around the guard, and do **not** skip or weaken the assertions —
  each of those buries the exact defect the test exists to expose. Move this ticket to
  `blocked/` instead, with the measured output and the re-run command, naming that slug as the
  unblock condition.

Any *other* failure is a real finding about the backfill and belongs in the handoff.

## Edge cases & interactions

- **The joiner must be genuinely alone.** Assert zero strand connections after the stop, and do it
  by polling — the founder's transport teardown is not instantaneous.
- **Control network still up.** Only the founder's *node* is stopped; the joiner's control node is
  unaffected. Self-coordination is decided per key-network, i.e. per strand libp2p node, so the
  live control connections do not rescue (or contaminate) the strand read.
- **Cold read, not cached read.** The bring-up gate already read those rows through `joinerDb`, so
  a Quereus/collection-level cache could answer from memory and hide a missing block. Prefer a
  read shape the earlier gate did not issue (the keyed `where Key = ?` lookups above, not just
  `count(*)`), and say in a comment why the shape was chosen. If the block-level evidence and the
  row-level result ever disagree, that disagreement is the finding.
- **Founder restart is out of scope.** This test ends with the founder down. Do not add a
  reconnect phase; convergence-after-reconnect is a different scenario's job.
- **Known-red neighbourhood.** All four existing tests in this file are listed in
  [`tickets/.pre-existing-known.md`](../.pre-existing-known.md) against the blocked ticket
  `strand-unique-index-sync-stale-revision`. If the file is red for that tracked fingerprint, note
  it and move on — do not chase it, skip it, or loosen it.
