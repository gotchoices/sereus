## Semantics to test against (read the source doc blocks — they are precise)

- `cancelInvite(db, { managerKeyPair, inviteKey })` signs
  `signStrandApproval(['Strand.CancelledInvite', 'cancel', inviteKey], ...)` and inserts one
  `Strand.CancelledInvite` row `with context ManagerKey = ?, ManagerSignature = ?`. No
  transaction — one statement. Insert-if-absent: already-cancelled is a quiet `log()` no-op.
- `listOutstandingInvites(db, nowMs?)` → `OutstandingInvite[]` (`{ inviteKey, expiration }`),
  in storage order. `Invite` minus `ConsumedInvite` keys minus `CancelledInvite` keys, minus
  anything where `expiration <= canonicalDatetime(nowMs ?? Date.now())` — strict `>`, so
  expiry is **exclusive**, matching the on-engine `NotExpired` gate.
- `CancelledInvite` constraints (`schemas/strand.qsql:133`): `OnlyClosed`, `Immutable`
  (`check on update, delete (false)`), `Authorized` (reads `committed.Manager`). Its context
  is `(ManagerKey text, ManagerSignature text)` — **non-null**, unlike the sibling tables'.
- `ConsumedInvite.NotCancelled` (`schemas/strand.qsql:101`) is `check on insert`, reading
  only stored rows.

A test that contradicts one of those doc blocks has found either a bug or a wrong comment.

### New `describe('cancelInvite')`

- **A cancelled invitation cannot be consumed** — pin `/NotCancelled/`. It is the only
  constraint that can fire on an otherwise-valid consume: `InviteExists`, `ValidUsage`,
  `NotExpired` (null expiry) and `MemberExists`/`MemberValid` all pass, and
  `Member.Authorized`'s invite branch is satisfied because the `ConsumedInvite` row *is* in
  the post-image at commit.
- **The whole join rolls back** — no new `Member` row, no `ConsumedInvite` row. Mirror the
  existing wrong-key / expired atomicity assertions (lines 220-234, 258-273).
- **A non-manager cannot cancel** — pin `/Authorized/`.
- **A manager seated in the SAME transaction cannot cancel** — pin `/Authorized/`. Copy the
  shape from `strand-member-revocation.spec.ts:695`: `addMemberByManager(founder → m2)`
  committed, then one transaction containing `addManager(founder → m2)` followed by
  `cancelInvite(m2, inviteKey)`.
- **A cancel approval minted for invite A does not cancel invite B** — pin `/Authorized/`;
  the digest binds `new.InviteKey`. Needs a hand-rolled insert, since `cancelInvite` always
  signs the key it inserts:

  ```ts
  const signature = signStrandApproval(
    ['Strand.CancelledInvite', 'cancel', inviteA],
    founder.privateKeyB64,
  );
  await expect(db.exec(
    `insert into Strand.CancelledInvite (InviteKey)
       with context ManagerKey = ?, ManagerSignature = ?
       values (?)`,
    [founder.publicKeyB64, signature, inviteB],
  )).rejects.toThrow(/Authorized/);
  ```

- **UPDATE and DELETE of an existing `CancelledInvite` row are refused** — pin `/Immutable/`.
  Copy the shape from the `Revocation` `Immutable` test
  (`strand-member-revocation.spec.ts:785`), which passes a placeholder `'ignored'` signature
  because `Immutable` is unconditional.
- **A second `cancelInvite` for the same key is a quiet no-op** — no throw, still one row.

### New `describe('listOutstandingInvites')`

Pin `nowMs` so expiry is deterministic. The existing expiry tests use
`const base = Date.UTC(2031, 2, 4, 12, 0, 0)` and `86_400_000` for a day.

- **Omits consumed, cancelled, and expired; includes a live one.** Four invites: one
  never-expires (live), one consumed, one cancelled, one with `expiration: base`; then
  `listOutstandingInvites(db, base + 86_400_000)` returns only the live key.
- **The returned `expiration`**: a never-expires invitation reports `null`, a timed one
  reports the canonical string — compare against `await canonicalDatetime(db, ms)`.
- **The expiry boundary is exclusive**: an invitation whose `expiration` equals `nowMs` is
  omitted (the strict `>` half of the on-engine parity, matching the existing consume-side
  boundary test at line 316).

### Extend `describe('StrandMemberVerifier.isAuthorizedToJoin ...')` (line 408)

Its three existing cases only cover expiry. The changed behavior is that a **cancelled**
invitation and an **already-consumed** one no longer hold the door open — both are new
`false` cases. For the consumed case, ask about a *different* member key than the one that
consumed, or the `ConsumedInvite` short-circuit answers first.

Note the describe's title says "expiry filtering" — widen it.
