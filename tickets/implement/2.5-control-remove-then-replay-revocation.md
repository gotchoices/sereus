# Retire an approval's one-off stamp when the row it admitted is removed

## The bug, reproduced

Two control tables gate who is in the party: `CadreControl.OwnerKey` (keys allowed to make
control changes) and `CadreControl.CadrePeer` (nodes that are members of the cadre). Adding a
row to either needs an owner signature over `(row key, StampId)`, where `StampId` is a random
one-off value stored in a `unique` column.

`unique` only constrains rows that currently exist. Deleting the row frees its stamp, and the
original signature — which never expires — verifies again. Both cases were re-confirmed against
a real (optimystic-backed) control database during this fix pass:

```
OwnerKey : founder enrolls K -> founder removes K (properly signed) -> replay the ORIGINAL
           enrollment insert verbatim  =>  K is an owner again
CadrePeer: founder admits P  -> founder removes P (properly signed) -> replay the ORIGINAL
           admission insert verbatim   =>  P is a member again
```

For `CadrePeer` the approval is *stored on the row itself* (`VouchOwner` / `VouchSig`), so the
peer being removed can read and keep it while still a member. For both tables, the approval also
rides along with the write to every other node in the party. The replayer need not be the removed
party — any writer works, which is the attacker position the rest of the control-plane
authorization work assumes (an already-admitted cadre peer).

## The fix: an append-only `Revocation` table

Retire the stamp instead of letting it free up. A new table records `(TableName, StampId)` pairs
whose row has been removed; the guarded tables refuse an insert naming a retired stamp, and
refuse a delete that does not retire one.

A legitimate re-add is unaffected: `SeedBootstrapService.insertCadrePeerRow` and
`ControlDatabase.insertOwnerKey` both mint a **fresh** `StampId` per insert
(`control-database.ts:generateStampId`, 32 bytes of CSPRNG output) and sign over it, so
re-admitting a removed peer just works with a new approval.

This shape was prototyped end-to-end during the fix pass — both against a bare in-memory
Quereus `Database` and against a real `CadreNode` control database — and all of the following
hold:

- Quereus accepts the forward reference (`OwnerKey` referencing `Revocation`, declared later).
- `check on delete` and `check on insert` both auto-defer (they carry subqueries), so the
  delete and its sibling tombstone insert see each other at commit **in either statement order**.
- Delete without a tombstone is refused by name; tombstoning a live row is refused by name;
  clearing or re-pointing a tombstone is refused by name.
- Replaying the original add after removal is refused by name; a re-add with a fresh stamp
  succeeds.

### Schema delta

Add to **both** `OwnerKey` and `CadrePeer` (substituting the table name in the two literals):

```sql
        -- A removed row's StampId is retired into Revocation, and this refuses any insert
        -- naming a retired stamp: the approval that seated this row can never re-seat it after
        -- removal. `unique` alone did not do this — it only holds over LIVE rows, so a delete
        -- freed the stamp and the original never-expiring signature verified again. A
        -- legitimate re-add mints a FRESH StampId and a fresh signature, so it is unaffected.
        constraint NotRevoked check on insert (
            not exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = new.StampId)
        ),
        -- Retirement is MANDATORY: a delete must carry the matching Revocation row in the same
        -- transaction, or the stamp would free up again. Deferred (subquery), so the sibling
        -- insert is visible at commit regardless of statement order.
        constraint RevocationRecorded check on delete (
            exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = old.StampId)
        ),
```

And a new table, declared **after** `FormationUsage` (last in the schema):

```sql
    -- Append-only retirement record for the one-off StampId nonces of removed OwnerKey /
    -- CadrePeer rows. Without it a removal was undoable: the add approval is a signature over
    -- (row key, stamp) that never expires, and deleting the row freed the stamp, so anyone who
    -- kept a copy of the approval could resurrect the row.
    table Revocation (
        TableName text,             -- 'OwnerKey' | 'CadrePeer' (confined by RowIsGone below)
        StampId text,               -- the retired nonce
        primary key (TableName, StampId),
        -- Retirement is permanent: clearing or re-pointing a tombstone would restore the replay.
        constraint Immutable check on update, delete (false),
        -- A stamp may only be retired once its row is actually gone. Deferred (subquery), so a
        -- delete in the same transaction has already landed. Retiring a stamp that never
        -- existed is permitted and harmless: stamps are 32 bytes of CSPRNG output
        -- (control-database.ts:generateStampId), so a future legitimate one cannot be guessed.
        constraint RowIsGone check on insert (
            (new.TableName = 'OwnerKey' and not exists (select 1 from OwnerKey K where K.StampId = new.StampId))
                or (new.TableName = 'CadrePeer' and not exists (select 1 from CadrePeer P where P.StampId = new.StampId))
        )
    );
```

`Revocation` needs no `with context (...)` clause — none of its predicates reads context (verified
in the prototype).

### Writer change

`SeedBootstrapService.removePeer` (`seed-bootstrap.ts:445`) is the only production deleter of a
guarded row — there is no production `OwnerKey` deleter at all (only tests). Its single
`delete from CadreControl.CadrePeer` must become a `beginTransaction` / `commit` pair holding the
delete plus `insert into CadreControl.Revocation ('CadrePeer', <stampId>)`. It already reads the
row's current `StampId` before signing, so the value is in hand. Copy the
rollback-swallow-and-rethrow shape from `ControlDatabase.redeemInvitation`
(`control-database.ts:770-798`) rather than inventing a second one.

`SeedBootstrapService.deleteDeviceToken` is untouched — `DeviceToken` has no stamp at all and is
covered by `bug-devicetoken-authority-antireplay`.

### Comment corrections

The current comments overstate what the stamps do and must be rewritten to describe the fix:

- `OwnerKey.StampId` — currently describes the bug as live ("once a row is deleted its stamp
  frees up ... can resurrect a removed owner"). Now retired via `Revocation`.
- `CadrePeer.StampId` — currently asserts "single-use authorization nonce (anti-replay)" as fact.
- `seed-bootstrap.ts:336-341` — the `NOTE:` in `insertCadrePeerRow` describing this exact hole and
  deferring it to the connection gater. Delete it; the hole is closed at the schema.
- `peer-authorization.ts` doc comments on `cadrePeerVoucherDigest` / `cadrePeerRemoveDigest`
  claim single-use anti-replay via stamp uniqueness — make them point at `Revocation`.

Do **not** touch the `ValidationKey` / `Strand` / `FormationInvite` stamp comments: those tables
are handled by `bug-control-validationkey-strand-unauthorized-delete`.

## Known limits — record as tripwires, not follow-up tickets

- **Convergence ordering.** These are per-transaction CHECKs against locally visible rows, so a
  node that has not yet converged on a `Revocation` row would still accept the replayed add; the
  two rows then coexist after merge. Same class as the existing `MinOneOwner` note on `OwnerKey`.
  Put a `NOTE:` on the `Revocation` table saying so. The read-side voucher check is the mitigation
  (below), and it is worth adding for exactly this reason.
- **Unbounded growth.** `Revocation` only ever grows. Cadres are a handful of peers and owner
  rotation is rare, so this is fine now; `NOTE:` it on the table.

## Read-side second layer (in scope)

Membership decisions should not depend on a write-time CHECK having been evaluated by the right
node. `CadreNode.listAuthorizedMembers` (`cadre-node.ts:~2836-2895`) already re-verifies each
`CadrePeer` row's stored voucher against the node-local trusted-owner anchor; extend it to also
drop a row whose `StampId` appears in `Revocation`. That makes a resurrected row inert for the
reader even if it lost the write-time race, and it is a cheap set lookup over a table the node
already has. Needs a `ControlDatabase` read helper (e.g. `queryRevokedStamps(table)`).
