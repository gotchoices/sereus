# Wake a hibernating host strand for an authorized closed-strand join

## The defect

A bound closed-strand redemption (someone joining a private workspace through the formation handshake) makes the host issue a single-use membership invitation against its **live** strand database, in `CadreNode.issueStrandMembershipInvite`. That method reads `this.strandManager.getInstance(strandId)?.database?.getDatabase()` and throws when there is none. `StrandFormationManager.issueBoundMembershipInvite` maps the throw to `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` ('Strand membership invitation unavailable, retry') and leaves the join token unspent.

With hibernation enabled, an idle strand is quiesced (`handleStrandHibernate` → `quiesceStrand` releases the libp2p node and closes the database, the instance record stays with `status: 'hibernating'`). From then on every redemption is refused, and the joiner cannot change that:

- the formation path never wakes the strand;
- the push-wake receiver (`StrandWakeService`) only accepts the host's own authorized cadre members;
- the host's own check-in schedule (30 s backing off toward an hour for `interactive`) keeps the runtime up only for a `checkInWindowMs` window each time.

So a retry succeeds only if it lands inside a check-in window. Not reached by the reference apps or default embedders (`CadreNode` defaults `hibernation` to `{ enabled: false }`, and both reference apps pass that explicitly), but reached by any embedder or `cadre-cli` config that enables hibernation and hosts closed strands. Also reachable with hibernation disabled when an embedder calls `hibernateStrand` / `hibernateAll` (the mobile background path), since `hibernateStrand` gates on the latency hint, not on `config.hibernation.enabled`.

Confirmed by reading the code only (`repro: static`); the first TODO below is the reproducing test.

## The fix

In `issueStrandMembershipInvite`, distinguish a hibernating instance from one with no runtime for another reason, and wake the former before issuing:

- `getInstance(strandId)` is `undefined` → never launched on this responder: keep throwing (retryable rejection), as today.
- instance present, `status === 'hibernating'`, no `database` → wake it (below), then continue with the existing pre-split check and `issueInvite`.
- any other state with no database (`'starting'`, `'syncing'`, `'error'`, a quiesce in flight) → keep throwing. Only `'hibernating'` is a state this node is expected to recover from on demand.

The wake:

- Count it as activity first: `this.hibernationManager.recordActivity(instance)`. On a hibernating instance that starts the coalesced wake and, once the wake leaves the strand `'active'`, re-arms the idle → hibernate timers, so the strand does not go back to sleep before the joiner's first sync (5 minutes idle for `interactive`). Use the hibernation manager directly, not `CadreNode.recordStrandActivity`, which would also fire the push fan-out and wake this party's hibernating phones for no reason.
- Then `await this.wakeStrand(strandId)`. It coalesces onto the wake `recordActivity` just started (same `HibernationManager.beginWake` promise), and it still wakes the strand when `recordActivity` is a no-op (hibernation disabled but the strand force-hibernated, or the manager stopped). The `.then` that re-arms the idle timer was attached first, so it runs before this await resumes.
- Bound the wait with the formation provisioning signal (next section). If the signal aborts first, stop waiting and throw an ordinary `Error` (maps to the retryable reason) but let the wake carry on in the background, with a `.catch` that logs, so there is no unhandled rejection. A retry after that finds the strand live.
- After the wake, re-read `instance.database`; if it is still absent (the wake failed or the strand was stopped concurrently), throw as today. A failed resume leaves `status: 'error'` via `resumeStrand`; that is the existing wake-failure behaviour and is not this ticket's to change.

Keep the wake after the existing Strand-row, `Type`, recorded-refusal and `StrandPartyKey` checks: all are cheap control-database reads, and a strand that cannot issue anyway should not be woken.

### Bounding the wake

The wake runs inside the responder's provisioning budget (`DEFAULT_PROVISION_TIMEOUT_MS` 12 s in `strand-formation-protocol.ts`, of which 10 s is work budget; the listener aborts the `provisionStrand` hook's `AbortSignal` when it expires). That budget is also shared with the outside-approval hook when an invite demands approval. Rather than adding a second timeout, thread the existing signal through:

- Widen `StrandFormationManagerOptions.issueMembershipInvite` to `(strandId: string, signal?: AbortSignal) => Promise<StrandMembershipInvite | null>`, and the matching option wherever `StrandSolicitationService` passes it through.
- `provisionAsResponder` already receives `signal`; pass it to `issueBoundMembershipInvite`, which passes it to the hook.
- `CadreNode.initializeStrandSolicitation` wires `(strandId, signal) => this.issueStrandMembershipInvite(strandId, signal)`.

The token stays unspent on every failure path: the wake happens before `authorized.record()`, and `record()` already throws `FormationAbortedError` without writing when the signal has aborted (`control-formation-recorder.ts`). Check `signal?.aborted` once more after the wake and before `issueInvite`, so a wake that finished just after the budget expired does not issue an invitation nobody will receive. (That orphan would expire on its own after `MEMBERSHIP_INVITE_TTL_MS`, so this check avoids a wasted write rather than a correctness bug.)

### Authorization ordering (unchanged, but it is what makes the wake safe)

`issueBoundMembershipInvite` runs only after `runSession` has validated the token and disclosure and after `authorizeBoundUsage` (outside approval + seat pre-check) has passed. So only a caller holding a valid, unspent formation token with a matching disclosure can cause a wake — the same bar that already lets them receive the strand's member key.

### Side benefit

`approve()` reads `resolveStrandAddrs(strandId)` after issuance. With the strand awake, the approval now carries the host's live strand-network addresses instead of an empty list, so the joiner's seed is populated.
