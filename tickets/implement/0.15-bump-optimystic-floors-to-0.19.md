# Move the declared `@optimystic/*` floors from `^0.18.0` to `^0.19.0`

## What happened

`../optimystic` cut `v0.19.0` on 2026-08-03 (commit `9b86eb3`) and it is on npm as `latest`. Every
`@optimystic/*` package in this repo's `resolutions` therefore now links to `0.19.0`, while our
seven `package.json` files still declare `^0.18.0`.

Because these are `0.x` versions, `^0.18.0` means `>=0.18.0 <0.19.0` — it **excludes** `0.19.0`
outright. This is not a cosmetic drift: an installer taking our declared range gets a version we no
longer build or test against, which is the same class of defect that produced
`blocked/report-dependency-floor-bump-to-embedding-app` in the first place.

`yarn check:dep-ranges` (part of `yarn dep-check`) is already red on it:

```
22 declared range(s) do not admit their linked workspace version.
```

So this is a currently-failing repo gate, not a future concern.

## What 0.19.0 actually contains

**Nothing but version numbers.** `git show --stat 9b86eb3` in `../optimystic` is twelve
`package.json` files, one line each. Its parent `610d6d1` is the commit this repo's whole-repo test
measurement of 2026-08-03 was taken against (`docs/STATUS.md` → "Release readiness"), so those
numbers describe `0.19.0`'s code exactly, byte for byte. Do not re-measure to justify this bump;
re-measure only to confirm the bump changed nothing.

Two things this release does **not** contain, both worth stating so nobody re-derives them:

- The coordinator fix that cross-machine replication needs
  (`blocked/control-coordinator-answers-absent-without-asking-cohort`). Still unfixed.
- A fix for the consumer-install failure
  (`blocked/optimystic-testing-barrel-breaks-consumer-install`). `0.19.0` still ships
  `packages/db-p2p/src/testing/raw-storage-conformance.ts` importing `chai` from a barrel that
  shipped runtime code reaches. Verified at that commit. **Publishing stays blocked.**

## How

`yarn upgrade:optimystic` exists for this (`ncu -u --workspaces --filter '/@optimystic/.*/'`), and
is the intended path. `@quereus/quereus` is a separate range and is not part of this ticket; check
`yarn check:dep-ranges` output before assuming it agrees.

Note which ranges move. All seven workspaces that declare an `@optimystic/*` dependency are in
scope, including the three private reference apps — they are not published, but their ranges are
what `test-harness/build-targets.ts` classifies as `link:`-backed, and a range that excludes the
linked version there is the same drift. `@serfab/cadre-host` and `@serfab/cadre-provider` declare
none of their own and need no edit.

## Edge cases & interactions

- **The gate is the acceptance criterion, and it must go fully green.** `yarn check:dep-ranges` must
  report all linked packages admitted and `0` too-old ranges — not "fewer than 22". A partial bump
  is worse than none: it hides the remainder behind a smaller number.
- **`yarn install` must run and the lockfile must be committed.** The ranges are declared but the
  packages resolve through `link:`, so an install may look like a no-op — check `yarn.lock` for
  movement either way and do not leave the tree half-installed.
- **Rebuild before testing anything.** The stale-build guard compares mtimes, and an install can
  touch trees. Run `yarn build` and expect the guard to be satisfied; if `../quereus` trips it, see
  the caveat below.
- **`../quereus` is under concurrent automation and currently does not compile.** As of 2026-08-03
  it carries uncommitted `alter-table`/`add-constraint` work, so
  `yarn workspace @quereus/quereus build` fails there and the stale-build guard cannot be cleared
  the normal way. Its `dist` is a clean build of its committed HEAD. Do **not** revert or stash
  anything in that repo. Document what you did to get a measurement.
- **Confirm the bump changed nothing.** `0.19.0` is byte-identical code to what was measured, so
  `packages/cadre-core`'s suite should still be 5 red of 1507 and `packages/integration-tests`
  around 13 red of 241, all multi-machine. A *different* failure count is a real signal — most
  likely that an install pulled a different transitive version — and should be chased, not averaged
  away. Several of those failures are routing races, so judge the shape (which files, which
  fingerprints) rather than the exact count.
- **Do not touch our own package versions.** All ten workspaces stay at `0.9.0`; bumping them is the
  human's release step (`blocked/cut-the-interim-release`).
- **Do not speculatively go past `0.19.0`.** If `../optimystic` releases again mid-ticket, take
  whatever `yarn upgrade:optimystic` resolves to and say so in the handoff — but only if it is
  published and linked, never a version nobody can install.

## Docs

The prose has **already been written for the post-bump world** — `docs/STATUS.md` ("Release
readiness"), `docs/releasing.md` ("The interim release" and runbook step 2),
`tickets/blocked/optimystic-testing-barrel-breaks-consumer-install` and
`tickets/blocked/cut-the-interim-release` all say the floors move to `^0.19.0` and why. So this
ticket should need no doc edits.

Read them anyway and confirm they read true once the change has landed, particularly the claim that
`0.19.0` changes no code and carries neither the coordinator fix nor the `chai` fix. If your
measurement contradicts any of that, the doc is what is wrong, and fixing it is in scope.
