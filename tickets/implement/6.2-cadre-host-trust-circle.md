## Goal

Build cadre-host's trust-circle layer on top of cadre-core's existing invite + authorize + CadrePeer primitives. The user runs `cadre-host invite "Mom's phone"`, gets an encoded token, ships it out-of-band; the recipient's cadre node redeems it and ends up authorised in the host's cadre. Local UI surfaces a list of members and pending invites with their labels.

This ticket is the auth substrate for the local-UI and installer tickets; it does NOT itself stand up the local HTTP server (that's `cadre-host-local-ui`). It exposes typed handlers the UI ticket wires into Fastify, plus the CLI command bound to those handlers.

## Decisions committed at plan stage

These were open in the plan ticket; this section locks them in so implement doesn't re-litigate.

### 1. Trust-circle membership lives in `CadrePeer` (cadre-core control network)

The set of peers in the trust circle is exactly the set of rows in the `CadrePeer` table of the host's cadre control network. Cadre-core already authorises this table through `authorizePeer()` and replicates it across the user's cadre. No new schema, no parallel list.

**Implication:** A trust-circle "membership check" is a `CadrePeer` lookup keyed by peer ID. Whoever needs the check (the management API auth middleware in `cadre-host-local-ui`, the cadre P2P transport's connection-gating in cadre-core, etc.) queries the control database directly.

### 2. Labels and pending-invite state live in a local cadre-host file

Labels (`"Mom's phone"`, `"My laptop"`) are display-only — losing them just shows the bare peer ID in the UI. Pending-invite state (tokens that haven't been redeemed yet) is operational rather than canonical — it lives on the issuing node and doesn't need to replicate.

A single `trust-circle.json` file under cadre-host's data dir holds both:

```typescript
interface TrustCircleFile {
  // Labels for redeemed members (peerId → label, addedAt)
  members: Record<string, { label: string; addedAt: string; self?: boolean }>;
  // Outstanding invites awaiting redemption (token → label, expiresAt, createdAt)
  pendingInvites: Record<string, { label: string; createdAt: string; expiresAt?: string }>;
}
```

JSON, atomic write (write to `.tmp` then rename — same pattern as `state-store.ts` in the orchestrator). The file is co-located with the orchestrator's state under cadre-host's rootDir.

If a future ticket wants cross-device label replication, a new `CadreMemberLabel` table can be added to the control schema then. Not now.

### 3. Management-API transport is localhost-only in v1

Cadre-host's management HTTP API binds to `127.0.0.1` only. There is no peer-identity-authed HTTP endpoint exposed over the cadre P2P transport in v1. Friends' cadre nodes interact with the host purely through the cadre control network they already share (CadrePeer membership, control DB sync, strand participation) — no cadre-host-specific RPC.

**Implication:** the management API's auth check is "are you connecting from `127.0.0.1`?" — the OS provides that guarantee. No header check, no peer-identity middleware. The trust circle is *displayed and managed* by the management API; it doesn't *gate* it. (The local-UI ticket may add a same-machine origin check on top, but that's a defence-in-depth detail, not auth.)

Cadre-host-over-P2P is a future ticket (logged in the "Out of scope / follow-ups" section below).

### 4. Cadre-core's existing `CadreInvite` shape is reused as-is

The cadre-core `CadreInvite` type (`partyId`, `authorityAddrs`, `token`, `createdAt`, `expiresAt`) is sufficient. Labels are not encoded into the invite payload; they live only on the issuing host. The recipient sees the host's display name (e.g. "Nathan's basement") in the redemption UI, not the inviter's chosen label for them.

If a future ticket wants invites to carry a label, that's an additive change. Out of scope here.

### 5. One-time enforcement on the issuing side

`CadreInvite.token` is just a random string. One-time enforcement is implemented by the issuing host: when a redemption arrives via cadre-core's `acceptPhone` flow, cadre-host removes the token from `pendingInvites` atomically; a second attempted use finds no matching pending row and is rejected.

Default invite TTL: **24 hours**, configurable per-invite via the issuance endpoint.

### TrustCircleService surface

```typescript
class TrustCircleService {
  constructor(opts: {
    cadreNode: CadreNode;         // for createInvite / authorizePeer / decodeInvite
    store: TrustCircleStore;      // labels + pending file
    now?: () => Date;             // injectable for tests
  });

  /** Create an invite. Persists pending row keyed by token. */
  issueInvite(opts: { label: string; ttlMs?: number }): Promise<{
    encodedInvite: string;
    invite: CadreInvite;
    expiresAt?: Date;
  }>;

  /** Redeem on behalf of an incoming peer. Validates token, authorises peer, promotes pending → member. */
  redeemInvite(opts: { token: string; peerId: string }): Promise<{ peerId: string; label: string }>;

  /** Revoke a pending invite (before redemption) by token. */
  revokePending(token: string): Promise<void>;

  /** Remove an authorised member by peer ID. Deletes from CadrePeer + local label store. */
  removeMember(peerId: string): Promise<void>;

  /** Quick membership check for the management API. */
  isMember(peerId: string): Promise<boolean>;

  /** Snapshot for the UI: members + pending invites with labels. */
  list(): Promise<{ members: TrustCircleMember[]; pending: PendingInvite[] }>;
}
```

### Wiring into the CLI

`src/bin/host.ts`'s stub `invite` action becomes a thin client that:
1. Reads `--label <name>` (required) and `--ttl <duration>` (optional, default 24h) from argv.
2. POSTs to `http://127.0.0.1:<mgmt-port>/auth/invites` with the body.
3. Prints the encoded token to stdout and a QR-renderable representation (use `qrcode` package — already in the workspace dep graph? if not, vendor a minimal ASCII QR or print the URL only and let the UI render the QR).
4. Exits 0 on success, prints the API error and exits 1 otherwise.

If the management server isn't running (no socket), print a hint pointing to `cadre-host start` and exit 2. (Don't try to spin up an inline service for the CLI — that complicates lifecycle.)

The `--ttl` flag accepts a duration string (e.g. `24h`, `7d`, `30m`); parse with the same helper the orchestrator uses for `stopTimeoutMs` if there is one, else add a tiny duration parser under `auth/`.

### Wiring into the management API (handler contract for `cadre-host-local-ui`)

This ticket exports typed handler functions; `cadre-host-local-ui` wires them into Fastify routes. The contract:

```typescript
// In src/auth/index.ts
export interface TrustCircleHandlers {
  postInvite(body: { label: string; ttlMs?: number }): Promise<{ encodedInvite: string; expiresAt?: string }>;
  deleteInvite(token: string): Promise<void>;
  deleteMember(peerId: string): Promise<void>;
  listTrustCircle(): Promise<{ members: TrustCircleMember[]; pending: PendingInvite[] }>;
}

export function createTrustCircleHandlers(service: TrustCircleService): TrustCircleHandlers;
```

No request/response validation here — handlers take typed objects, Fastify schema validation is the UI ticket's job. Errors throw; the UI ticket maps them to HTTP status codes (404 for unknown token/peer, 410 for expired invite, 409 for already-redeemed, 500 otherwise).

### Redemption flow — wiring into cadre-core

Cadre-core's existing redemption is `acceptPhone(options, issuedInvite)`. The recipient dials in (over libp2p), declares a peer ID + token, and the host calls `acceptPhone` which validates and calls `authorizePeer`.

Cadre-host needs a hook in this flow so it can match the incoming token against `pendingInvites` and promote on success. Two options:

**Option A — wrap `acceptPhone` on the cadre-host side.**
Cadre-host exposes its own `redeemInvite(token, peerId)` that:
1. Looks up the pending row by token, throws if missing/expired.
2. Re-materialises a `CadreInvite` from the pending row.
3. Calls `cadreNode.acceptPhone({ phonePeerId: peerId, token }, materialisedInvite)`.
4. On success: removes the pending row, writes the label to `members`.

The caller is whatever cadre-core hook wires the incoming libp2p stream to host-level redemption. **In v1, cadre-host exposes `redeemInvite` only via the localhost management API** (not over cadre P2P) — because the recipient is expected to have a local user agent (the reference app, or `cadre-host invite redeem <token>` if we add it) that calls the host's management API. Out-of-LAN redemption (recipient is remote) is not in v1; remote recipients dial via `dialInvite` over libp2p, which goes through cadre-core directly, bypassing the host-level pending list.

This is a v1 simplification — see "Known gaps" below.

**Option B — extend cadre-core to invoke a host-supplied hook during `acceptPhone`.**
Cleaner but requires a cadre-core change. Defer to a later ticket.

**Decision: Option A.** v1 supports the LAN/same-machine redemption case (your phone scans the QR, calls the host's localhost management API via the reference app's LAN-connected web view, redeems). Cross-WAN redemption defers until the cadre-host-over-P2P ticket exists.

## Key test expectations

- **Issue → redeem happy path**: pending row created with correct label and expiry; after redeem, member appears in list with the same label, pending row gone, CadrePeer has the peer.
- **Redeem with wrong token**: rejected, pending unchanged, CadrePeer unchanged.
- **Redeem expired invite**: rejected with a distinct error code; pending row removed (don't leave dead tokens around forever).
- **Double redeem**: second attempt rejected because pending row was removed on first redemption.
- **Revoke pending**: pending row gone; subsequent redemption with that token rejected.
- **Remove member**: CadrePeer deletion authorised, local label removed, `isMember` returns false.
- **List with orphan labels**: a local label whose peerId is not in CadrePeer is pruned on read (covers the case where another device removed the peer).
- **Store atomic-write under crash**: kill mid-write (simulate by failing the rename); next load either sees the old state or throws clearly, never partial.

## Known gaps / out of scope (logged for follow-up)

- **Cross-WAN redemption via the reference app**: requires either cadre-host-over-P2P (a libp2p protocol for management API operations) or the recipient app dialling the host's management API over WAN. Neither is in v1. Log a follow-up ticket if real usage demands it.
- **Friend-side label**: the recipient sees no label for themselves; their own UI shows what they call the host, not vice versa. Out of scope.
- **Multi-device label replication**: requires a control-network table for labels. Out of scope.
- **Roles / permissions**: trust circle is flat — every member has full access to the host's localhost management API once their device is on the host's machine, but since the API is localhost-only, this is moot. When cadre-host-over-P2P lands, roles become meaningful.
- **Invite link UI rendering (QR generation)**: this ticket prints the encoded token; QR rendering is `cadre-host-local-ui`'s job. The CLI may print a terminal-rendered QR (nice-to-have, last priority).
- **Recovery from authority key loss**: not addressed here. The cadre-core authority-key model owns this; cadre-host inherits whatever cadre-core provides.
