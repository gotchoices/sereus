# Hosted nodes: join a cadre by QR, grants removed

Third of the `cadre-host-join-a-cadre` chain. Server, service, CLI and the proving scenario. The web page is `cadre-host-join-ui`; the second way in (paste an invitation) is `cadre-host-join-by-invitation`; the doc rewrite is `cadre-host-join-docs`. This ticket makes the minimal doc edits that keep docs/cadre-host.md and the README true.

## Product decisions (settled with the project owner, restated)

- The realistic case: you start a cadre on your phone and add the always-on machine in your basement to it. Setup is out of band and happens once; the host does not listen for requests to provision nodes.
- The host shows the QR and the phone scans it, because the phone cannot be dialed and the QR has to carry the node's addresses.
- Grants are dropped. To put up a node for a friend, run "Join a cadre" again and let the friend scan it. The node belongs to whoever claims it.
- A hosted node is not an owner. Hosted nodes run the `storage` profile.

## The model

One kind of node, the **hosted node**: a child process the host runs for some cadre. Its record lives in `<dataDir>/hosted-nodes.json` (`HostedNodeStore`, the renamed `DonationStore`), id `hn_<base64url of 12 random bytes>`, which is also its orchestrator container id and workdir name.

```ts
interface HostedNode {
  id: string;
  /** How this node gets into its cadre. `cadre-host-join-by-invitation` adds the second member of the union. */
  join: { kind: 'claim'; secret: string };
  /** `unclaimed` until the claim reports the party; the claimant's party after. */
  partyId: string;
  profile: 'storage';
  status: 'spawning' | 'unclaimed' | 'joined' | 'error';
  dockerId?: string;
  /** The child's loopback `/status` URL, from the spawn result. */
  statusEndpoint?: string;
  /** Read once from `/status`; the claim details need it before the claim. */
  peerId?: string;
  /** `/status.node.claimedBy` once claimed; the UI shows its first 8 characters. */
  ownerKey?: string;
  /** From the last status poll: the node holds at least one control connection. */
  connected?: boolean;
  respawn?: { attempts: number; lastAttemptAt: string };
  createdAt: string;
  updatedAt: string;
  error?: string;
}
```

No `seedToken`, no `seedEndpoint`, no `grantToken`, no `bootstrapNodes`, no `ownerKeys`. The orchestrator still mints `CADRE_SEED_TOKEN` and returns `seedToken` because `OrchestratorCreateResult` (cadre-provider's shape) carries it; cadre-host ignores both. `HostedNodeView` strips `join.secret`; only `claimDetails` (below) ever returns it.

Statuses: `spawning` (record written, child not yet spawned; the stuck-`spawning` reap at 5 minutes stays), `unclaimed` (child up with a claim secret, waiting), `joined` (claimed; the claim named the party), `error` (the supervisor gave up, or the reap found it stuck). Removal deletes the row; there is no `terminated` status. `error` keeps the workdir as the give-up path does today, and removal reclaims it.

## What to build

**cadre-core: the claim payload encoding.** `node-claim-payload.ts`, exported from the package root: `encodeNodeClaimPayload({ peerId, multiaddrs, secret })` → `sereus-join:1.<base64url of canonical JSON>` and `decodeNodeClaimPayload(text)`, which refuses anything but version 1, a peer id that does not parse, an address that does not parse or whose last `/p2p/` is not that peer id, and a secret `parseClaimSecret` refuses. The decoder lives in cadre-core because the phone (`rn-app-joins-host-node-by-qr`) and the host both need it. One unit test: round trip, and refusal of an address naming another peer. The payload carries no party id (the claim supplies it, `claim-carries-the-party-id`).

**Orchestrator.** `createContainer(request: HostedSpawnRequest)` with `HostedSpawnRequest = OrchestratorCreateRequest & { claimSecret?: string }`: the secret reaches the child as `CADRE_CLAIM_SECRET` through `extraEnv`, never as an argument (an argument shows in the process list) and never in `state.json` or a log line. The `pinnedOwnerKeys` to `CADRE_OWNER_KEYS` wiring is deleted (nothing pins keys any more: a claim anchors the claimant, an invitation pins its own), and with it the "foreign party gets no push block" rule: every `storage`-profile node gets the push block when credentials are configured. `orchestrator-pin-keys.test.ts` is replaced by one test that the claim secret reaches the child's environment and is absent from `state.json`; `orchestrator-push.test.ts` loses its foreign-party case.

**`HostedNodeService`** (from `DonationService`, `src/hosted/hosted-node-service.ts`):

- `join()`: mint a 32-byte base64url secret, write `spawning`, spawn with `partyId: 'unclaimed'`, `profile: 'storage'`, `claimSecret`; re-read after the spawn (a removal that landed mid-spawn wins, as today: reclaim the child, answer `not_found`); write `unclaimed` with `dockerId` and `statusEndpoint`. No per-grant queue remains; one plain serialization tail for `join` is enough.
- `claimDetails(id)`: `409 invalid_state` unless `unclaimed`. Reads the node's `/status` for `peerId` and `multiaddrs` (`503 node_unavailable` until it answers, the CLI and UI poll), builds the address list in this order: the node's public addresses from `NatService.publicAddressesFor(id, ports)` with `/p2p/<peerId>` appended (TCP then WebSocket), then the node's own non-loopback LAN addresses from `/status.multiaddrs` (which already carry the `/p2p/` suffix), loopback dropped. Returns `{ payload: encodeNodeClaimPayload(...), peerId, multiaddrs, reachability: NodeReachability | null }` so callers can warn when the node is not reachable from outside (the claim still works at home over the LAN address).
- `remove(id)`: delete the row first, then stop and reclaim the child; the supervisor's exit-triggered pass finds no record and does nothing. A `spawning` row with no handle reclaims by workdir name as today.
- `reset(id)`: `remove` then `join`; returns the new record. For the case where someone else photographed the QR and claimed the node first.
- `respawn(id, opts)`: replays `partyId` from the record (the placeholder while unclaimed, the real party once joined) and the same `claimSecret`. Keeping the secret after the claim is deliberate: cadre-cli honours `claim.json` and, with the secret still set, answers a rival `already-claimed` (`claim-carries-the-party-id`). Same ports, same identity, so the claim details already shown stay valid across a respawn while unclaimed.
- `list()` and `get(id)` return `HostedNodeView`.
- The stale-`awaiting_seed` reap is deleted: an unclaimed node waits indefinitely, nobody can claim it without the secret. The stuck-`spawning` reap stays.
- **Status watcher.** While any record is `unclaimed`, poll each one's `/status` every 2 seconds (`HOSTED_NODE_CLAIM_POLL_MS`); on `claim === 'claimed'` write `joined`, `partyId = node.partyId`, `ownerKey = node.claimedBy`, and publish. Poll `joined` nodes every 15 seconds for `connected` (`node.connectionPaths` total above zero) and publish on change. The watcher is best-effort: a poll that fails is retried next tick. Node-state changes from the orchestrator also trigger a poll, so a respawn is noticed at once. Events go through a listener the server wires to the bus as `hosted-nodes-changed` with `kind: 'added' | 'claimed' | 'removed' | 'changed'`.

**`HostedNodeSupervisor`** (from `DonationSupervisor`): supervised statuses `unclaimed` and `joined`; the respawn rules, backoff, give-up and `restart` unchanged. `NatService.onNodeAddressesStale` calls `restart` for every node (the owner branch went in the previous ticket).

**Routes** (`routes/hosted-nodes.ts`, mounted by `createLocalUiServer` when `hostedNodes` is passed; loopback, no bearer): `GET /api/hosted-nodes`, `POST /api/hosted-nodes` with an empty body (the invitation ticket adds a body) → 201 `{ node }`, `GET /api/hosted-nodes/:id`, `GET /api/hosted-nodes/:id/claim`, `DELETE /api/hosted-nodes/:id` → 204, `POST /api/hosted-nodes/:id/reset` → 201 `{ node }`. `HostedNodeError` codes: `not_found` 404, `invalid_state` 409, `invalid_request` 400, `node_unavailable` 503, `orchestrator_error` and `storage_error` 500. Every mutation publishes `hosted-nodes-changed`. `/api/nodes` keeps listing orchestrator handles (the handle's `partyId` stays the placeholder until the first respawn after the claim; the UI shows the record's party, not the handle's). The `/grants` empty-body tolerance in `server.ts` stays as a general rule; reword its comment.

## Edge cases & interactions

- Host restart while a node is unclaimed: the orchestrator re-attaches the child; it is still running with the same secret, peer id and ports, so a QR already shown stays valid. If it died while the host was down, the supervisor's startup pass respawns it with the same secret and ports. Supervisor test with the fake orchestrator: an `unclaimed` record whose handle is dead is respawned with the record's secret and the previous handle's ports.
- The node is not yet reachable from outside: `claimDetails` still answers, with `reachability` carrying the verdict; the CLI prints the warning; the LAN address is in the list. By inspection.
- Respawn after the claim keeps the ports, so the cadre's stored addresses stay valid. Scenario step on the kill-and-respawn.
- The secret appears only in the `claim` response, the CLI's payload output and the child's environment; `list`, `get`, events, `state.json` and logs never carry it. Orchestrator test for the environment and `state.json`; the scenario asserts the host's own log output and `GET /api/hosted-nodes` do not contain the secret.
- Someone else claims the node first: the watcher reports `joined` with that owner's key; the UI ticket shows the fingerprint and offers Reset. `reset` here is the mechanism; by inspection.
- `remove` racing `join`'s spawn: the post-spawn re-read sees no record and reclaims the child, as the donation code does today. Existing service test adapted.
- `claimDetails` before the child's `/status` answers: `503 node_unavailable`; the CLI polls. By inspection.
- Two `join` calls at once: each gets its own id, secret and ports; nothing is shared. By inspection.
- The watcher and a `remove` in flight: the watcher re-reads before writing, as every long operation in the service does, so a removed row is not resurrected as `joined`. Service test: a poll result for a row deleted mid-poll writes nothing.
- `publicAddressesFor` with no public address: the list is the LAN addresses only; no warning beyond the reachability verdict. By inspection.
- `reset` on a node that is `joined` and healthy: allowed (the admin's call), removes it from its cadre's point of view too; the UI ticket confirms before calling. By inspection.
- **A handle with no record (arm added by the `cadre-host-remove-founder-role` review).** The supervisor reconciles records to handles, never handles to records, so an orchestrator handle that no record names stays in `/api/nodes` for good. If it is stopped, the Home status reads "warn" from then on, and the node page's Remove answers 404. Today this happens when someone re-runs `cadre-host install` over a founder-era data dir: the installer overwrites `host.config.json` and leaves `orchestrator/state.json`, which still holds the old `owner` handle. It would also happen after `hosted-nodes.json` is lost. When the supervisor is reshaped, decide whether its startup pass stops and reclaims any handle that has no record, or logs it. Either one makes "every handle belongs to a record" hold after startup. Found by reading the code; not run.
