## Context

`turn-issuer-peer-assertion` (prereq) teaches the TURN credential issuer to accept
a **peer assertion**: five request headers carrying a signature made with the
caller's libp2p Ed25519 node key, over a domain-separated five-line message. A
verified caller gets a TURN credential labelled with its peer id; operators can
allow-list, deny-list, and rate-limit per peer.

This ticket is the client half. Today `loadIceConfig()` is a pure
fetch-and-validate with no notion of identity, and it is deliberately
framework-free — the file header in both copies states it takes no
`@serfab/cadre-core` or node dependency so the browser bundle stays lean and the
RN port stays a mirror. **Keep that property.** The signing capability arrives as
an injected structural interface; `ice-config.ts` owns the wire format and never
imports a crypto library.

Read the prereq ticket's "Wire format" section before starting — it is normative,
including the pinned test vector this ticket's specs reuse.

## Design

### 1. `cadre-core`: one identity helper, two consumers

`CadreNode.resolveIdentityKey` (`packages/cadre-core/src/cadre-node.ts:852`) is
today the only place that knows the load-or-create-and-persist rule for a
`KeyStore`-backed identity, including the load-bearing rule that a rejected `get`
(e.g. `KeyStoreAccessError` from a cancelled biometric prompt) **propagates** and
never falls through to generating a fresh key. The React Native app now needs that
same key *before* `CadreNode` is constructed, so extract it rather than growing a
second copy that can drift.

New `packages/cadre-core/src/identity-key.ts`, exported from `index.ts`:

```ts
/** Load the identity key from `keyStore`, generating + persisting on first run. */
export async function loadOrCreateIdentityKey(
  keyStore: KeyStore,
  keyId?: KeyId,           // default DEFAULT_IDENTITY_KEY_ID
): Promise<PrivateKey>;

/**
 * Prove possession of a node key to an out-of-band HTTP service. Deliberately
 * generic (no ICE/TURN vocabulary) — it is "sign a string with the node key".
 */
export interface PeerKeySigner {
  /** base58btc peer id — `privateKey.publicKey.toString()`. */
  readonly peerId: string;
  /** base64url of the libp2p protobuf-encoded public key. */
  readonly publicKeyB64: string;
  /** Sign the UTF-8 bytes of `message`; resolves to a base64url signature. */
  sign(message: string): Promise<string>;
}

export function peerKeySigner(privateKey: PrivateKey): PeerKeySigner;
```

`peerKeySigner` throws on a non-Ed25519 key (the issuer only accepts Ed25519).
`publicKeyB64` comes from `publicKeyToProtobuf` + `uint8arrays` `toString(…,
'base64url')`; `peerId` from `privateKey.publicKey.toString()`, which for Ed25519
is already the base58btc peer id (identity multihash) — no `@libp2p/peer-id`
round-trip needed. `cadre-core` already depends on `@libp2p/crypto` and
`uint8arrays`.

Then rewrite `resolveIdentityKey` to delegate to `loadOrCreateIdentityKey`, keeping
its own responsibilities: the `keyStore` + `privateKey` mutual-exclusion error, the
`privateKey` and ephemeral branches, the idempotent early return, and the existing
log lines.

### 2. `ice-config.ts` (both apps): optional signer, options object

Replace the positional `url` parameter — `AGENTS.md` says no backwards compat yet,
so change the signature rather than overloading it:

```ts
/** Structural mirror of cadre-core's `PeerKeySigner`; no import, keeps this file dep-free. */
export interface IceConfigPeerSigner {
  readonly peerId: string;
  readonly publicKeyB64: string;
  sign(message: string): Promise<string>;
}

export interface LoadIceConfigOptions {
  url?: string;
  signer?: IceConfigPeerSigner;
}

export async function loadIceConfig(options?: LoadIceConfigOptions): Promise<RTCIceServer[]>;
```

New exported, individually testable helpers in the same file:

- `iceConfigAudience(url: string): string` — the target URL with query and fragment
  stripped. This is what the issuer's `PEER_AUTH_AUDIENCE` must equal, character
  for character.
- `peerAssertionMessage(audience, peerId, issuedAtSec, nonce): string` — the
  five-line builder. Byte-identical to the issuer's; the pinned vector locks it.
- `randomNonceHex(): string` — 16 bytes from `crypto.getRandomValues` rendered as
  32 lowercase hex chars. Hex, not base64url, so neither copy needs a base64
  encoder. `crypto.getRandomValues` exists in browsers and in RN via the
  `react-native-get-random-values` polyfill the app already bundles (see
  `packages/reference-app-rn/src/uuid.ts`, which documents that only
  `getRandomValues` — not `randomUUID` — is polyfilled).
- `buildPeerAssertionHeaders(signer, audience, nowSec): Promise<Record<string,string>>`
  — returns the five `X-Sereus-Peer-*` headers.

Load flow:

1. Resolve the target URL (unchanged).
2. If a signer is present, build the assertion headers **before** starting the
   5 s abort timer, so signing time never eats the fetch deadline.
3. Fetch with `accept` plus the assertion headers.
4. On HTTP `401` or `403` **with** assertion headers attached, retry **once**
   without them. A rejected assertion (skewed device clock, an operator who moved
   the audience, a deny-listed peer) must degrade to the unauthenticated path
   rather than to `[]` — `[]` would strip STUN as well and leave the node worse
   off. Log the status and that the retry is unauthenticated. Do not retry a retry.
5. Everything else — no URL, network error, other non-OK status, malformed body,
   timeout — behaves exactly as today: log, return `[]`, never throw.

If building the assertion throws (signer failure, missing `getRandomValues`), log
and continue unauthenticated. Identity trouble must not stop a node from booting.

The abort deadline covers both attempts: create one `AbortController`/timer for
the whole `loadIceConfig` call so a hostile host cannot double the boot stall.

Add the issuer's new informational manifest fields to the local
`IceConfigManifest` interfaces (`peerAuth?: 'off' | 'none' | 'verified'`,
`peerId?: string`) so the shape stays documented. `parseIceServers` still reads
only `iceServers` — do not make either field load-bearing.

### 3. App wiring

**Web** (`packages/reference-app-web/src/lib/cadre-web.ts`): the identity key is
already resolved at line ~291, before `loadIceConfig()` at ~296. Wrap it —
`peerKeySigner(privateKey)` — and pass `{ signer }`. The brand-skew cast already
applied on that line covers the type.

**React Native** (`packages/reference-app-rn/src/cadre-phone.ts`): the app passes
`keyStore` + `identityKeyId` to `CadreNode` and never touches the key itself, so on
a first run the slot is still empty when `loadIceConfig()` is called at ~238. Add
an explicit `loadOrCreateIdentityKey(keyStore, DEFAULT_IDENTITY_KEY_ID)` call
placed **after** `migrateLegacyIdentity` (~line 192, which may populate the slot)
and **before** `loadIceConfig`, then build the signer from the result. Keep passing
`keyStore` + `identityKeyId` to `CadreNode` — it will load the very key just
persisted. Do **not** switch to `config.privateKey`; it is mutually exclusive with
`keyStore` and would take the identity out of the secure enclave path.

## Testing

Existing specs — `packages/reference-app-web/test/ice-config.spec.ts` and
`packages/reference-app-rn/test/ice-config.spec.ts` — call
`loadIceConfig('https://explicit.example/ice.json')` positionally and must move to
the options object.

New cases, mirrored in both specs:

- **Pinned vector.** With a stub signer built from the prereq ticket's fixture
  (peer id `12D3KooWK99VoVxNE7XzyBwXEzW7xhK7Gpv85r9F3V3fyKSUKPH5`, public key
  `CAESIIqI4910CfGV_VLbLTy6XXLKZwm_HZQSG_N0iAG0D29c`), `peerAssertionMessage`
  returns exactly the pinned message string. This is the lock against drift from
  the issuer.
- No signer → no `X-Sereus-Peer-*` headers on the request.
- With a signer → all five headers present; nonce matches `/^[0-9a-f]{32}$/`;
  timestamp is the current unix second; audience equals the URL with query and
  fragment stripped.
- `signer.sign` rejects → request still goes out, unauthenticated, result parsed
  normally.
- HTTP 401 with headers → exactly two fetches, the second carrying no
  `X-Sereus-Peer-*` headers; a successful second response is parsed.
- HTTP 401 on the retry → `[]`.
- HTTP 401 with **no** signer → single fetch, `[]` (no retry loop).
- `iceConfigAudience` strips `?a=b` and `#frag`, leaves path and trailing slash
  untouched (a trailing slash is significant — the issuer compares exactly).
- Existing timeout/malformed/never-throws cases still pass, and the timeout still
  fires once across the retry.

`cadre-core`: a spec for `loadOrCreateIdentityKey` (generates and persists into an
empty `InMemoryKeyStore`; returns the stored key on a second call without
re-persisting; a `get` that rejects propagates and nothing is written) and for
`peerKeySigner` (peer id and public key match the pinned vector; the signature over
the pinned message equals the pinned signature; a non-Ed25519 key throws). The
existing `packages/cadre-core/test/cadre-node-identity.spec.ts` must still pass
unchanged — that is the regression guard on the extraction.

## Edge cases & interactions

- **First run, RN.** Slot empty → `loadOrCreateIdentityKey` generates and persists,
  and the same key is what `CadreNode` then loads. Must not produce two different
  identities.
- **Legacy-identity migration ordering.** `migrateLegacyIdentity` runs first and may
  fill the slot; calling the loader before it would generate a fresh key and orphan
  the migrated identity. Order is load-bearing — comment it.
- **Cold-start re-entry, RN.** `use-cadre`'s cold-start hook re-runs
  `startPhoneNode` after the OS killed the node. The loader must be idempotent (it
  is — `get` then return) and must not add another native handle, unlike the
  `nodeLocalDb ??=` case documented at ~line 218.
- **`KeyStoreAccessError`.** A cancelled biometric / unlock prompt rejects `get`.
  That rejection propagates out of `loadOrCreateIdentityKey` — it must **not** be
  swallowed into "no signer, continue unauthenticated", because generating a
  replacement key would silently orphan the real identity. It fails
  `startPhoneNode`, matching today's `CadreNode` behaviour.
- **Device clock skew.** A phone whose clock is off by more than the issuer's
  `PEER_AUTH_SKEW_SECONDS` (default 60) always fails verification; the 401 retry is
  what keeps such a device on the working unauthenticated path.
- **Audience mismatch.** The client derives the audience from the URL it actually
  fetched; the operator configures `PEER_AUTH_AUDIENCE` by hand. A trailing slash,
  an `http`/`https` difference, or a reverse proxy that rewrites the path breaks
  every assertion. Document the exact string in `ops/docs/ice-servers.md` and make
  the client log the audience it sent when it takes the 401 retry — that log line
  is the only way an operator diagnoses this.
- **`localStorage` override, web.** `ICE_CONFIG_URL_STORAGE_KEY` can repoint the
  manifest URL at runtime, which changes the audience. Deriving the audience from
  the resolved target (not from a constant) handles this automatically — do not
  hoist the audience to module scope.
- **Nonce quality.** `randomNonceHex` must use `crypto.getRandomValues`, not
  `Math.random` (which `uuid.ts` uses for non-cryptographic ids). A predictable
  nonce is a replay handle.
- **Timer discipline.** One `AbortController` + one `setTimeout` per
  `loadIceConfig` call, cleared in `finally`, covering both fetch attempts. The
  existing "no `AbortSignal.timeout` in RN" constraint still holds.
- **Two copies stay mirrors.** `ice-config.ts` exists twice by design (web uses DOM
  `RTCIceServer` + `localStorage` + `import.meta.env`; RN uses a structural
  `IceServer` + `process.env.EXPO_PUBLIC_*`). Every helper added here lands in both
  with identical logic, and both specs pin the same vector.
- **No new RN dependency.** The signer comes from `@serfab/cadre-core`, which
  `reference-app-rn` already depends on. Do not add `@libp2p/crypto` to the RN app
  — see backlog `debt-reference-app-ns-resolve-nested-libp2p-deps` for why nested
  libp2p copies are a live hazard there.
- **Unrelated, do not fix here.** A TURN-relayed WebRTC path is still classified as
  `direct` by `connection-path.ts` — backlog `web-turn-relayed-path-detection`.
