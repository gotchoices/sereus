# Validate the `ValidationKey` / `Strand` delete-authorization schema change

This is the **validation continuation** of `control-validationkey-strand-delete-authorization`.
That ticket's code is fully written and sitting in the working tree. It was **never run** — the
agent hit its token budget immediately after the last edit and stopped before any test, lint, or
type check. Treat every claim below as unverified.

## What was changed (already in the tree)

**Schema — `schemas/control.qsql` and the `CONTROL_SCHEMA` template literal in
`packages/cadre-core/src/control-schema.ts`** (the two must stay byte-identical):

- `ValidationKey`: the single bare `constraint Authorized check (...)` was replaced by five
  constraints — `NotRevoked` (on insert), `RevocationRecorded` (on delete), `NoUpdate`
  (on update, `false`), `AuthorizedInsert` (on insert), `AuthorizedDelete` (on delete, verifying a
  `'remove'`-tagged digest over `old.Key, old.StampId`).
- `Strand`: same five, with `AuthorizedInsert` keeping the existing signature-free consent branch
  (`exists (select 1 from FormationUsage FU where FU.StrandId = new.Id)`) and `AuthorizedDelete`
  deliberately **not** mirroring it. `MemberKeyClosedOnly` was left bare and untouched.
- `Revocation`: `RowIsGone` gained `'ValidationKey'` and `'Strand'` branches; the `TableName`
  column comment and the table's leading doc comment now enumerate all four guarded tables.

**Important consequence:** the constraint name `Authorized` no longer exists on `ValidationKey`
or `Strand`. Anything asserting that name against those two tables must be updated.

**Tests:**

- New `packages/cadre-core/test/control-constraint-helpers.ts` exporting
  `expectConstraintFailure(promise, ...names)` — asserts
  `/CHECK constraint failed: (Name|Name)\b/`. The identical local copy was removed from
  `control-revocation-replay.spec.ts` and both that spec and
  `control-authorization-binding.spec.ts` now import it. A third, still-duplicated copy lives in
  `control-ownerkey-self-authorization.spec.ts`; it was left alone to keep the diff scoped, and
  folding it in is optional cleanup, not required work.
- `control-revocation-replay.spec.ts` gained six tests plus two extra branches on the existing
  `RowIsGone` live-stamp test: delete-authorization (unsigned / add-approval-replayed-as-delete /
  transplanted-remove-signature) for both tables, the consent-formed-strand delete case, mandatory
  tombstone + wrong-`TableName` tombstone for both tables, and remove-then-replay + fresh-stamp
  re-add for both tables.
- `control-authorization-binding.spec.ts` gained two `NoUpdate` regression guards: rotating a
  `ValidationKey.StampId` by update, and rewriting a consent-formed strand
  (`Type = 'o'`, `MemberPrivateKey = null`) with no signature.

**Docs:** `docs/architecture.md` control-table listing — the `ValidationKey`, `Strand` and
`Revocation` rows were rewritten to describe the new rules.

## Known risks to check first

These are the places the unverified work is most likely to be wrong.

**Constraint-name pinning may be ambiguous.** With the fix, a delete that is both unsigned *and*
missing its tombstone violates `AuthorizedDelete` **and** `RevocationRecorded` at once, and the
deferred-check queue does not promise which one reports. The new tests dodge this by running each
authorization attack inside a transaction that also files the matching tombstone, so
`RevocationRecorded` is satisfied and only the authorization constraint can fail — the same
technique `control-ownerkey-self-authorization.spec.ts` already uses (see its comment "The
tombstone rides along so `RevocationRecorded` is satisfied"). If a test still reports the wrong
name, check whether `Revocation.RowIsGone` surfaces first instead (its subquery is deferred, and
the row it looks for is only gone if the refused delete provisionally applied). Widening the
accepted-name list is the last resort, not the first move — it weakens the assertion.

**Existing tests asserting the old `Authorized` name.** Grep the cadre-core test tree for
`'Authorized'` used against `ValidationKey` or `Strand` and repoint it at `AuthorizedInsert`.

**Fallout candidates** named by the originating ticket: `control-formation-invite.spec.ts`,
`strand-formation-consent.spec.ts`, `control-member-key-constraint.spec.ts`,
`control-authorization-domain-separation.spec.ts`, `control-schema-drift.spec.ts`. Also worth a
look: `publish-strand.spec.ts`, `strand-founder-bootstrap.spec.ts`, `seed-bootstrap.spec.ts`.

**Byte-identical mirroring.** `control-schema-drift.spec.ts` compares the two schema copies. Inside
`control-schema.ts` the schema is a backtick template literal, so every literal backtick in a
comment must stay escaped as `` \` ``. The new comments contain several. If the drift guard fails,
that escaping is the first thing to check.

**Unverified premise.** The originating ticket asserted, from a repo-wide grep, that no writer
anywhere updates `Strand` or `ValidationKey`, so `NoUpdate` breaks nothing. That grep was not
re-run. If a `NoUpdate` failure appears in a spec that is *not* one of the two new regression
guards, re-check that claim before assuming the test is at fault.
