# Confirm the schema-init retry actually engages

## What already landed

`third-node-join-ddl-init` routed `ControlDatabase.loadSchema`'s `db.exec(CONTROL_SCHEMA)`
through `lockedWithRetry` (`packages/cadre-core/src/control-database.ts`, end of
`loadSchema`), so a node joining a party that already has two live members no longer dies on
startup when one peer fails to answer during a single `create table`. The call site carries
the argument for why re-running the whole `exec` is safe (`apply schema` is a diff against
the live catalog, and a failed `create table` leaves the catalog clean, so attempt 2 re-emits
exactly the failed table and its successors).

Unit coverage landed alongside it in
`packages/cadre-core/test/control-write-retry.spec.ts`:

- `ControlDatabase.loadSchema — transient-failure retry` (three cases) drives the private
  `loadSchema` against a stubbed `exec`, proving a schema init that fails once with the
  observed super-majority message succeeds on the second attempt, that a commit-phase
  (`[blocks:`) failure and a `Missing block` failure are each surfaced from attempt 1
  unretried, and that budget exhaustion rethrows the last attempt's error object unchanged.
- a classifier case pinning that `Missing block` matches nothing, both bare and wrapped in
  Quereus' `Failed to execute DDL: …` text.

`yarn workspace @serfab/cadre-core typecheck` is clean; the spec file passes (19/19); all four
cadre packages build.

## What is NOT yet established — the whole point of this ticket

**Nobody has captured a real failing DDL aggregate.** The unit cases assert against the
super-majority message transcribed from the failing run recorded in the predecessor ticket
(`Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`), but the bracketed
per-batch segment of the surrounding transactor aggregate was elided when it was transcribed.

That segment decides whether the fix does anything at all. `isRetriableControlWriteFailure`
vetoes any failure whose `cause` chain contains `[blocks:` — the token Optimystic's *commit*
phase uses to format its per-batch details, marking an outcome too indeterminate to re-run.
The read and pend phases format `[block:` instead. The three formatting sites all feed
`formatBatchStatuses` in
`../optimystic/packages/db-core/src/transactor/network-transactor.ts` (two `[block:` sites,
one `[blocks:` site).

Reading the engine says the create path *should* carry `[block:`: the super-majority error is
raised by `ClusterCoordinator.executeClusterTransaction` while collecting promises
(`../optimystic/packages/db-p2p/src/repo/cluster-coordinator.ts`, ~line 374), which
`CoordinatorRepo.pend` reaches — and a pend-phase aggregate formats `[block:`. But
`CoordinatorRepo.commit` calls the SAME `executeClusterTransaction`, so the identical
super-majority text can also arrive from the commit phase, where the veto correctly fires.
Which one the joining node actually hit is unknown, and a static read is not evidence.

If real captures carry `[blocks:`, the retry silently never engages — the change looks
correct and does nothing. **Do not loosen `reportsIndeterminateCommit` to make it match.**
That veto exists because re-running a write that may have landed turns a success into a
constraint failure. Report it as a finding and re-scope instead.

## The `Missing block` face is expected, not a regression

Two different errors were seen in two runs of the same scenario. Only the super-majority one
is in scope. The other — `Missing block (jQlkVafUFlI6FzOGGAlViyK5GrgcSm_4SL7HfPKwhis)` on
table `Revocation` — is a durable convergence fault already tracked at this exact call site
in `tickets/blocked/control-db-cross-node-convergence-halted.md` (see its "Folded in
2026-08-01" section). A retry cannot heal it and must not pretend to; it matches no matcher,
so it propagates unchanged. If it reappears, that belongs in the handoff, not in a widened
classifier — and follow the pre-existing-failure procedure naming
`control-db-cross-node-convergence-halted` rather than chasing it here.

Expect, therefore, that the scenario does not become unconditionally green. The dependent
ticket `provider-seed-accepted-by-real-node` should be judged on that basis.
