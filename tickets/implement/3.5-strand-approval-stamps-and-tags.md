Every signed write in the `Strand` schema is authorized by an ed25519 signature over a digest of
the affected key(s). Nothing in the signed bytes says *which incarnation of the row* the approval
was minted for, and nothing marks an approval as spent. Constraint context values travel with the
write out to the strand's peers, so any party that saw a membership write holds a permanently
valid copy of the approval it carried.

## What is already fine — do not "fix" these

- `Invite` and `ConsumedInvite` are insert-only and their primary keys are minted fresh per
  issuance/consumption, so a replayed insert collides on the primary key. **No stamp needed on
  either table.**
- `Member.Authorized`'s invite branch is already single-use via its same-transaction freshness
  clause against `committed.ConsumedInvite`. Leave that branch's logic alone.
- `Member.Authorized`'s `add`/`remove` action tags already stop an admission approval from being
  replayed as an eviction. That axis is closed for `Member`; still open for `Manager` and the
  `MemberPeer` self branch.
- `StrandMemberVerifier.verifyMember` verifies a member self-proof, not a constraint payload —
  confirmed clean, leave alone.

## The design: mirror `CadreControl`'s retired-stamp idiom

Copy `schemas/control.qsql` → `table OwnerKey` + `table Revocation` (read regions noted in the
resume note). The shape, per protected table:

- A `StampId text not null unique` column — per-row authorization nonce, minted at insert and
  bound into the signed digest.
- `constraint NotRevoked check on insert` — refuses any insert naming a **retired** stamp.
- `constraint RevocationRecorded check on delete` — a delete MUST carry the matching tombstone
  row in the same transaction, or the stamp frees up again.
- A shared `Revocation (TableName, StampId)` insert-only tombstone table with `Immutable`,
  `RowIsGone`, and `Authorized` constraints.

Why `unique` alone is not enough: `unique` holds over LIVE rows only, so deleting the row frees
its stamp and the original never-expiring signature verifies again — precisely R1 and R4. The
permanent tombstone closes them. The delete-side replays (R2, R3, R5, R6) are closed differently:
the delete digest binds `old.StampId`, so once the row is re-created with a FRESH stamp, the
captured removal approval no longer matches any row.

### New `Strand.Revocation` table

Adapted from `CadreControl.Revocation`. Two deliberate differences, both argued in the schema
comment:

- `TableName` confined to `'Member' | 'Manager' | 'MemberPeer'` by `RowIsGone`.
- `Authorized` verifies against a **`committed.Member`** row, not an owner key: every strand
  delete path is authorized by a manager or the departing party, both members. Filing a
  tombstone for a live row is blocked by `RowIsGone`; withdrawing one by `Immutable`; junk
  stamps only grow the table (a stamp carries 256 bits of CSPRNG output — unguessable). Add
  `OnlyClosed` like sibling tables.

Suggested digest: `digest('Strand.Revocation', 'retire', new.TableName, new.StampId)`.

### Per-table digest changes

Every payload gains a domain tag, an action tag, and the stamp. Subsumes the whole of
`tickets/backlog/bug-strand-approval-domain-separation.md` — delete it here.

| Table / branch | New signed digest |
|---|---|
| `Member` add-by-manager | `digest('Strand.Member', 'add', new.Key, new.StampId)` |
| `Member` remove-by-manager | `digest('Strand.Member', 'remove', old.Key, old.StampId)` |
| `Member` self-departure | `digest('Strand.Member', 'leave', old.Key, old.StampId)` |
| `Manager` promotion | `digest('Strand.Manager', 'add', new.MemberKey, new.Generation, new.StampId)` |
| `Manager` self-resignation | `digest('Strand.Manager', 'resign', old.MemberKey, old.StampId)` |
| `Manager` removal-by-another | `digest('Strand.Manager', 'remove', old.MemberKey, old.StampId)` |
| `MemberPeer` self register | `digest('Strand.MemberPeer', 'add', new.MemberKey, new.PeerId, new.StampId)` |
| `MemberPeer` self remove | `digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId, old.StampId)` |
| `MemberPeer` manager remove | `digest('Strand.MemberPeer', 'manager-remove', old.MemberKey, old.PeerId, old.StampId)` |

Notes on tag choices:

- `Member` self-departure moves `'remove'` → `'leave'`; `MemberPeer` manager-removal `'remove'`
  → `'manager-remove'`. Neither collision is exploitable today (different verifying keys;
  `Member.NotAManager` blocks the coinciding case). Distinct tags are free belt-and-braces —
  say so in the comment so a future reader does not misread them as the fix for R3/R5.
- Bootstrap branches of `Member.Authorized` / `Manager.Authorized` sign nothing and stay
  unchanged; founding rows still need a `StampId` (column is `not null`), minted by the founder.
