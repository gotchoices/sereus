## Run-7 learnings (load-bearing for the remaining work)

1. **The crypto plugin digest is FRAMED and TYPE-TAGGED** (optimystic
   `quereus-plugin-crypto/src/crypto.ts` `encodeField`): INTEGER 1 and TEXT '1' encode
   under different tags and NEVER collide (injective by design). So `String(generation)`
   could never match SQL `new.Generation`. **Fixed in the writer**: `signStrandApproval`
   now takes `ReadonlyArray<string | number>` and `addManager` signs over the NUMBER
   `generation`. Integer `number` and `bigint` encode identically (both via
   `BigInt(...).toString()`), so JS numbers match however the engine represents the SQL
   integer. Docstrings updated. NO schema change was needed. **Every test signing a
   promotion digest must pass the generation as a NUMBER, not a string.**
2. **Stale dist bites**: cadre-core tests resolve `@serfab/quereus-plugin-sereus` via its
   built `dist/`, which was stale (no StampId — "Column 'StampId' not found" on every
   test). Fixed by `yarn build` in `packages/quereus-plugin-sereus` (fast, esbuild). **If
   the schema mirror is ever edited again, rebuild that package before running cadre-core
   tests.**
3. **Pin-preserving tombstones**: `Revocation.Authorized` shares the constraint NAME
   `Authorized` with the Member/Manager/MemberPeer gates. Consequences:
   - A raw negative DELETE pinning `/Authorized/` needs a same-transaction tombstone
     (else `RevocationRecorded` may report first) — but the tombstone's signer may be
     the ATTACKER: if it isn't a committed member, `Revocation.Authorized` fails and the
     message is still `CHECK constraint failed: Authorized`. Pin holds either way.
   - Writer-driven negative tests (e.g. `removeManager` with a stranger keypair) file a
     stranger-signed tombstone internally → `Revocation.Authorized` fails → still
     `/Authorized/`. **Existing writer-driven pins hold unchanged.**
4. The `@quereus/quereus` "Cannot find module" IDE diagnostics on writer/spec files are
   language-server noise (linked-workspace resolution) — vitest resolves and runs fine.
   Ignore; typecheck in Phase 5 is the arbiter. A stale diagnostic for the deleted
   throwaway spec (`test/throwaway-stamp-proof.spec.ts`) may also linger.

## Background (original analysis, condensed)

Every signed write in the `Strand` schema is authorized by an ed25519 signature over a
digest of the affected key(s). Before the schema change, nothing in the signed bytes said
which incarnation of the row the approval was minted for, and nothing marked an approval
as spent; context values travel with the write to the strand's peers, so any party that
saw a membership write held a permanently valid approval. Six replays (R1–R6: manager
re-seat/re-demote/forced-resign, member re-admit/re-evict, peer unbind/rebind) were
reproduced on a real closed strand. The landed schema closes them: insert replays die on
`NotRevoked` (stamp retired permanently at delete), delete replays die because the delete
digest binds `old.StampId` and a re-created row carries a fresh stamp.

Already fine, do not "fix": `Invite`/`ConsumedInvite` (insert-only, fresh PKs — no
stamps); `Member.Authorized`'s invite-branch freshness clause;
`StrandMemberVerifier`/`strand-member-registry.ts` (off-engine self-proof only — leave the
whole file alone).
