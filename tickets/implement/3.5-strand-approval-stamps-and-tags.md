Every signed write in the `Strand` schema is authorized by an ed25519 signature over a digest of
the affected key(s). Nothing in the signed bytes says *which incarnation of the row* the approval
was minted for, and nothing marks an approval as spent. Constraint context values travel with the
write out to the strand's peers, so any party that saw a membership write holds a permanently
valid copy of the approval it carried.

## Reproduced, on a real strand DB

Six replays were confirmed against a real closed strand (libp2p node + `MemoryRawStorage` +
`connectToStrand` in bootstrap mode — the same path `StrandDatabase` uses). All six currently
**succeed**; each must be inverted into a `rejects.toThrow(...)` case by this ticket.

| # | Captured approval | Replayed as | Consequence |
|---|---|---|---|
| R1 | `addManager` promotion of X at generation 1 | re-insert `Manager(X, 1)` after X was removed | **Privilege restoration** — X is an admin again with no living admin's consent |
| R2 | `removeManager` removal of X | delete `Manager(X)` after X was deliberately re-promoted | Repeatable forced demotion |
| R3 | X's own resignation | delete `Manager(X)` after re-promotion, by a party that never held X's key | Forced resignation |
| R4 | `addMemberByManager` admission of X | re-insert `Member(X)` after X was revoked | **Revocation is not durable** — X is a member again |
| R5 | `revokeMember` removal of X | delete `Member(X)` after X was re-admitted | Repeatable eviction |
| R6 | `registerMemberPeer` binding (M, P) | delete that binding, then re-insert it | Availability only; also proves insert and delete share one payload |

Reproduction code for all six is in the git history of this ticket's fix run; it is short enough to
rewrite from the table above. The harness to copy is `test/strand-member-revocation.spec.ts`

## What is already fine — do not "fix" these

- `Invite` and `ConsumedInvite` are insert-only and their primary keys (`Invite.Key`,
  `ConsumedInvite.InviteKey`) are minted fresh per issuance/consumption, so a replayed insert
  collides on the primary key. **No stamp needed on either table.**
- `Member.Authorized`'s invite branch is already single-use via its same-transaction freshness
  clause against `committed.ConsumedInvite`. Leave that branch's logic alone.
- `Member.Authorized`'s `add`/`remove` action tags (landed by `bug-strand-member-delete-unauthorized`)
  already stop an admission approval from being replayed as an eviction. That axis is closed for
  `Member`; it is still open for `Manager` and for the `MemberPeer` self branch.
- Cross-table collisions between the two-field pipe-joined payloads (`Manager` promotion
  `X|Generation`, `Invite` `Key|Expiration`, `MemberPeer` `MemberKey|PeerId`) were checked and are
  not currently reachable — but only by accident of value formatting and of the promotion branch's
  `A.MemberKey <> new.MemberKey` clause, not by design. Domain tagging (below) removes the
  accident.
- `StrandMemberVerifier.verifyMember` in `packages/cadre-core/src/strand-member-registry.ts`
  verifies `memberRegistrationPayload`, which is a member self-proof and **not** one of the
  constraint payloads. Confirm, then leave it alone.

## The design: mirror `CadreControl`'s retired-stamp idiom

The control plane already solved exactly this problem and its solution is proven in
`schemas/control.qsql`. **Copy that idiom rather than inventing one.** Read
`schemas/control.qsql` → `table OwnerKey` (lines ~4–44) and `table Revocation` (lines ~489–528)
before writing anything.

The shape, per protected table:

- A `StampId text not null unique` column — a per-row authorization nonce, minted at insert and
  bound into the signed digest.
- `constraint NotRevoked check on insert` — refuses any insert naming a **retired** stamp.
- `constraint RevocationRecorded check on delete` — a delete MUST carry the matching tombstone row
  in the same transaction, or the stamp frees up again.
- A shared `Revocation (TableName, StampId)` insert-only tombstone table with `Immutable`,
  `RowIsGone`, and `Authorized` constraints.

Why `unique` alone is not enough (this is the whole point, and it is the tripwire the control-side
ticket parked): `unique` holds over LIVE rows only, so deleting the row frees its stamp and the
original never-expiring signature verifies again. That is precisely R1 and R4. The permanent
tombstone is what closes them. The delete-side replays (R2, R3, R5, R6) are closed by a different
mechanism: the delete digest binds `old.StampId`, so once the row is re-created with a FRESH stamp,
the captured removal approval no longer matches any row.

### New `Strand.Revocation` table

Adapted from `CadreControl.Revocation`. Two deliberate differences from the control version, both
of which need to be argued in the schema comment:

- `TableName` is confined to `'Member' | 'Manager' | 'MemberPeer'` by `RowIsGone`.
- `Authorized` verifies against a **`committed.Member`** row, not an owner key. Every strand delete
  path is authorized by either a manager or the departing party itself, and both are members, so
  "any committed member may file a tombstone" covers all of them. Filing a tombstone for a still-live
  row is blocked by `RowIsGone`; withdrawing one is blocked by `Immutable`; filing junk stamps only
  grows the table (a stamp carries 128+ bits of CSPRNG output, so a future legitimate stamp cannot
  be guessed and pre-planted). Add `OnlyClosed` like its sibling tables.

Suggested digest: `digest('Strand.Revocation', 'retire', new.TableName, new.StampId)`.

### Per-table digest changes

Every payload below gains a domain tag, an action tag, and the stamp. This subsumes the whole of
`tickets/backlog/bug-strand-approval-domain-separation.md` — re-signing these payloads twice would
be pure churn, so absorb it here (see TODO).

| Table / branch | New signed digest |
|---|---|
| `Member` add-by-manager | `digest('Strand.Member', 'add', new.Key, new.StampId)` |
| `Member` remove-by-manager | `digest('Strand.Member', 'remove', old.Key, old.StampId)` |
| `Member` self-departure | `digest('Strand.Member', 'leave', old.Key, old.StampId)` |
| `Manager` promotion | `digest('Strand.Manager', 'add', new.MemberKey, new.Generation, new.StampId)` |
| `Manager` self-resignation | `digest('Strand.Manager', 'resign', old.MemberKey, old.StampId)` |
| `Manager` removal-by-another | `digest('Strand.Manager', 'remove', old.MemberKey, old.StampId)` |
| `MemberPeer` self register | `digest('Strand.MemberPeer', 'add', new.MemberKey, new.PeerId, new.StampId)` |
| `MemberPeer` self remove | `digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId, old.StampId)` |
| `MemberPeer` manager remove | `digest('Strand.MemberPeer', 'manager-remove', old.MemberKey, old.PeerId, old.StampId)` |

Two notes on the tag choices:

- `Member` self-departure moves from `'remove'` to `'leave'`, and `MemberPeer` manager-removal from
  `'remove'` to `'manager-remove'`. Neither collision is exploitable today (each pair verifies
  against a different key, and `Member.NotAManager` blocks the one case where the keys could
  coincide). Distinct tags are free and state the intent locally — but say in the comment that this
  is belt-and-braces, not a live hole, so a future reader does not misread it as the fix for R3/R5.
- The bootstrap branches of `Member.Authorized` and `Manager.Authorized` sign nothing and stay
  unchanged. The founding rows still need a `StampId` (the column is `not null`), minted by the
  founder like any other.

### Writer changes (`packages/cadre-core/src/strand-membership-writer.ts`)

- Mint stamps with a strand-local generator. `control-database.ts`'s `generateStampId(peerId)` is
  peer-derived; strand rows are not peer-scoped, so a plain 32-random-byte base64url value is
  right. Reuse the same cross-platform `randomBytes` helper `generateStampId` uses — do not reach
  for `node:crypto` directly (React Native).
- There are now nine payload shapes. Replace the ad-hoc `signStrandPayload` /
  `signStrandMemberAction` / `signStrandMemberPeerRemoval` trio with ONE tagged variadic signer
  rather than growing the trio (AGENTS.md: stay DRY, small single-purpose functions).
  `signStrandPayload`/`verifyStrandPayload` must survive for `Invite`, `ConsumedInvite`, and the
  off-engine `memberRegistrationPayload` self-proof, which stay untagged.
- Every delete writer (`revokeMember`, `leaveStrand`, `removeManager`, `removeMemberPeer`) becomes
  transactional: the delete plus its `Revocation` insert in ONE transaction. Copy `consumeInvite`'s
  existing begin/commit/rollback shape — including its "a failed commit already tore the
  transaction down" rollback handling.
- Delete writers must read the live row's `StampId` before signing. Follow `scanMemberPeerIds`'
  scan-and-filter shape, not a composite-primary-key seek — see its docstring for why a point
  lookup is unreliable on a networked strand. `addManager`'s existing generation read has the same
  caveat already NOTE'd; do not make it worse.
- `bootstrapFounderMembership` mints stamps for the founding `Member` and `Manager`;
  `consumeInvite` mints one for the invited `Member`.
- Delete the stale doc paragraphs that point at the now-absorbed backlog ticket: the `MemberPeer`
  table NOTE in `schemas/strand.qsql`, and `RemoveOwnPeerParams`' docstring in the writer.
