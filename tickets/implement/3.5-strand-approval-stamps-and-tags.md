- `Strand.Revocation`: PK `(TableName, StampId)`; `TableName` confined to
  `'Member'|'Manager'|'MemberPeer'` by `RowIsGone`; `OnlyClosed`; `Immutable`;
  `Authorized` reads **`committed.Member`** (any pre-transaction member may file; the
  departing member in `leaveStrand` qualifies — it is committed pre-txn). Context is
  `(MemberKey text, Signature text)` — **non-null**, mirroring the control layer, unlike
  the `text null` contexts on sibling tables. Every tombstone insert must supply both.
- Member self-departure moved `'remove'` → `'leave'`; MemberPeer split its formerly shared
  self payload into `'add'`/`'remove'`; manager cleanup is `'manager-remove'`. Comments in
  the schema state these tag splits are belt-and-braces only (different verifying keys) —
  the anti-replay fix is the stamp.

## Background (original analysis, condensed)

Every signed write in the `Strand` schema is authorized by an ed25519 signature over a
digest of the affected key(s). Before this ticket's schema change, nothing in the signed
bytes said which incarnation of the row the approval was minted for, and nothing marked an
approval as spent; context values travel with the write to the strand's peers, so any
party that saw a membership write held a permanently valid approval. Six replays (R1–R6:
manager re-seat/re-demote/forced-resign, member re-admit/re-evict, peer unbind/rebind)
were reproduced on a real closed strand. The landed schema closes them: insert replays die
on `NotRevoked` (the stamp is retired permanently at delete), delete replays die because
the delete digest binds `old.StampId` and a re-created row carries a fresh stamp.

Already fine, do not "fix": `Invite`/`ConsumedInvite` (insert-only, fresh PKs — no
stamps); `Member.Authorized`'s invite-branch freshness clause;
`StrandMemberVerifier`/`strand-member-registry.ts` (off-engine self-proof only — leave the
whole file alone).
