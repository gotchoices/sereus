## Background (original analysis, condensed)

Every signed write in the `Strand` schema is authorized by an ed25519 signature over a
digest of the affected key(s). Before the schema change, nothing in the signed bytes said
which incarnation of the row the approval was minted for, and nothing marked an approval
as spent; context values travel with the write to the strand's peers, so any party that
saw a membership write held a permanently valid approval. Six replays (R1–R6: manager
re-seat/re-demote/forced-resign, member re-admit/re-evict, peer unbind/rebind) were
reproduced on a real closed strand. The landed schema closes them: insert replays die on
`NotRevoked` (stamp retired permanently at delete), delete replays die because the delete
digest binds `old.StampId` and a re-created row carries a fresh stamp.

Already fine, do not "fix": `Invite`/`ConsumedInvite` (insert-only, fresh PKs — no
stamps); `Member.Authorized`'s invite-branch freshness clause;
`StrandMemberVerifier`/`strand-member-registry.ts` (off-engine self-proof only — leave the
whole file alone).
