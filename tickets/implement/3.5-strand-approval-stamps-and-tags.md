## ✔ OPEN QUESTION RESOLVED (run 6) — nesting fix LANDED

Quereus `Database.beginTransaction()` (database.ts:1022) HARD-THROWS
`"Transaction already active"` on ANY active transaction. (The SQL `BEGIN` path via
TransactionManager.beginTransaction upgrades implicit→explicit; only explicit-in-explicit
throws there — but the public API checks `isInTransaction()` first and always throws.)
No savepoint stacking, no no-op.

**Fix landed in `strand-membership-writer.ts` `inStrandTransaction`:** when
`!db.getAutocommit()` (caller owns an open transaction), it JOINS — `await fn(); return;`
— no begin/commit/rollback; deferred checks fire at the CALLER's commit and
failure/rollback belongs to the caller. Docstring updated with rationale. `getAutocommit()`
is false exactly while a transaction is open; between writer statements no implicit txn
lingers (autocommit finalizes per statement), so the probe is reliable at writer entry.

Walked both outer-txn compositions against the schema — both work under join mode:
- **:592 (resign + revoke, one txn, accepts):** all deferred checks pass at outer commit —
  Manager.Authorized resign branch, Manager.RevocationRecorded, MinOneManager (founder
  remains), Member.Authorized remove branch (founder in committed.Manager),
  Member.RevocationRecorded, NotAManager (post-image Manager row gone), Revocation
  RowIsGone + Authorized (both retirees are committed members).

## Background (original analysis, condensed)

Every signed write in the `Strand` schema is authorized by an ed25519 signature over a
digest of the affected key(s). Before the schema change, nothing in the signed bytes said
which incarnation of the row the approval was minted for, and nothing marked an approval
as spent; context values travel with the write to the strand's peers, so any party that
saw a membership write held a permanently valid approval. Six replays (R1–R6: manager
re-seat/re-demote/forced-resign, member re-admit/re-evict, peer unbind/rebind) were
reproduced on a real closed strand. The landed schema closes them: insert replays die on
`NotRevoked` (stamp retired permanently at delete), delete replays die because the delete
digest binds `old.StampId` and a re-created row carries a fresh stamp.

Already fine, do not "fix": `Invite`/`ConsumedInvite` (insert-only, fresh PKs — no
stamps); `Member.Authorized`'s invite-branch freshness clause;
`StrandMemberVerifier`/`strand-member-registry.ts` (off-engine self-proof only — leave the
whole file alone).
