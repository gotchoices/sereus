# Formation deadlines derived from the declared link

## Why

Strand formation is the protocol one party's machine runs to join another party's strand: the joiner (initiator) dials the host's control node (responder), sends one contact frame, and waits for one result frame. Every deadline on it is a fixed number chosen on a fast network. Each one waits on work that crosses the machine-to-machine link, so each has a link speed above which it always fails. Sereus supports relayed links up to a 3-second round trip, and `NetworkConfig.linkRoundTripMs` (default 3 500 ms, `DECLARED_LINK_ROUND_TRIP_MS` in `link-budget.ts`) declares it; this ticket derives the whole formation ladder from that declaration.

Two defects today, both `repro: static` (arithmetic from measured counts, not observed):

- **The dial.** `dialFormation` bounds `node.dialProtocol` with `stepTimeoutMs` (5 000 ms). A relayed dial is 4 link round trips (measured), plus the called machine's admission decision, plus one round trip to negotiate the formation protocol. 5 000 ms cannot open a relayed connection above a 1.25-second round trip. `withTimeout` also passes no abort signal, so an expired dial keeps running.
- **The provisioning grace.** The responder's provisioning budget is 12 000 ms, of which the last 2 000 ms is a settle grace for work that already issued its `FormationUsage` insert (an insert cannot be undone, so a late success is adopted rather than reported as "timed out"). One control commit at the supported link takes far longer than 2 000 ms (see the commit count below), so on a slow link a work budget that expires after the insert is issued reports "timed out" over a spent invite, and the joiner cannot recover. `settleWithinGrace`'s NOTE (~607) documents this window.

## The counts (new, in `link-budget.ts`)

- `PROTOCOL_NEGOTIATION_ROUND_TRIPS = 1`: already in the module's table ("negotiate a protocol over an established circuit", measured at 2 one-way delays). Re-express `CIRCUIT_REQUEST_ROUND_TRIPS` as `PROTOCOL_NEGOTIATION_ROUND_TRIPS + 1` so the two cannot drift.
- `relayedStreamOpenBudgetMs(link) = relayedDialBudgetMs(link) + PROTOCOL_NEGOTIATION_ROUND_TRIPS × link`: what `dialProtocol` costs, a relayed dial plus the protocol negotiation. 16 000 + 3 500 = 19 500 ms at the default.
- `COMMIT_ROUND_TRIPS = 20`, **measured, not a static count**. Source: `packages/integration-tests/src/scenarios/relay-round-trip-measure.integration.ts`, `delayed` configuration (150 ms one-way on one party's link, so a 300 ms link round trip), at optimystic `9e5c1e85`, 2026-09-23: one insert took 3.8–6.1 s, i.e. up to 20.3 link round trips including about 0.1–0.2 s of local work (loopback inserts took 57–195 ms). The static inventory of the write path (3 repo messages × 3 consensus rounds = 9 sequential requests, each a negotiation plus a request, so 18) agrees. The measurement's record lives in `tickets/complete/relay-round-trips-remeasure-optimystic-9e5c1e85.md`, which will be swept from the board, so **copy these figures into the constant's doc comment**; that comment is their home from now on. Say there that the count depends on the Optimystic version and is re-measured with that scenario (`RELAY_RRT_MEASURE=1 RELAY_RRT_CONFIG=delayed`) when `@optimystic/*` is bumped, not recomputed. It measures a strand insert; a control-database insert runs the same network transactor, and its cohort is the responder's own party's machines, which the module doc already says must declare the same link.
- `commitBudgetMs(link) = COMMIT_ROUND_TRIPS × link`: 70 000 ms at the default. No admission allowance: a commit runs over connections already open.

Add the three rows to the module's count table, and pin both helpers in `link-budget.spec.ts`'s existing "multiplies each operation's round-trip count" test (one `expect` each, same style).

## The ladder (in `strand-formation-protocol.ts`)

One exported function computes every formation deadline from one declaration, so the ordering holds by construction instead of by hand-chosen numbers:

```ts
export interface FormationDeadlines {
  /** Initiator: open a possibly relayed connection and negotiate the formation protocol. */
  dialMs: number;
  /** Responder: from the handler starting to the contact frame arriving. */
  awaitContactMs: number;
  /** Responder: validateToken + validateDisclosure. Counted, not wrapped (see below). */
  validationMs: number;
  /** Responder: the provisioning hook's work budget, after which its signal aborts. */
  provisionWorkMs: number;
  /** Responder: the settle grace after the abort, which must contain one control commit. */
  provisionGraceMs: number;
  /** Initiator await-response minus responder provisioning. */
  responseTravelMarginMs: number;
  /** Initiator: the result frame read. */
  initiatorAwaitResponseMs: number;
  /** Both roles: the whole session. */
  sessionMs: number;
}
export function formationDeadlines(linkRoundTripMs?: number): FormationDeadlines;
```

With `L` the declared link round trip, `R = cohortReadDeadlineMs(L)` (2L: the counting convention the consistency doc already uses, one silent cohort peer per read) and `K = commitBudgetMs(L)` (20L):

| field | formula | at default (L = 3 500) | at L = 100 |
| --- | --- | --- | --- |
| dialMs | `relayedStreamOpenBudgetMs(L)` = 5L + 2 000 | 19 500 | 2 500 |
| awaitContactMs | `CIRCUIT_REQUEST_ROUND_TRIPS × L` = 2L | 7 000 | 200 |
| validationMs | 2R = 4L | 14 000 | 400 |
| provisionWorkMs | approval hook (10 000, flat) + 2R + K = 10 000 + 24L | 94 000 | 12 400 |
| provisionGraceMs | R + K = 22L | 77 000 | 2 200 |
| responseTravelMarginMs | L + validationMs = 5L | 17 500 | 500 |
| initiatorAwaitResponseMs | work + grace + margin = 10 000 + 51L | 188 500 | 15 100 |
| sessionMs | dialMs + initiatorAwaitResponseMs = 12 000 + 56L | 208 000 | 17 600 |

Why each term:

- **awaitContactMs**: the listener's handler starts when it answers the negotiation; the answer reaches the joiner and the contact frame comes back, one round trip. Counted as a request over an open stream (2) so the bound has the same headroom as the module's other one-exchange reads.
- **validationMs**: `validateToken` reads the control database (`isTokenValid`) and a production disclosure validator may read too. Both run on the initiator's await-response clock but before the responder's provisioning clock starts, so they belong in the travel margin. They are not wrapped in their own deadline; the session bounds them.
- **provisionWorkMs**, production (bound) path in `provisionAsResponder`: `resolveStrand` (a control read), `authorizeUsage` (the outside approval hook, 10 000 ms by `formation-approval.ts`'s `DEFAULT_TIMEOUT_MS`, which is link-independent because it is an HTTP call; plus the seat pre-check read), then `issueMembershipInvite`, a strand-database write (one commit). Waking a hibernating host strand inside `issueMembershipInvite` is **not** counted: `wakeHostStrandForFormation` already cuts it off by design with a retryable rejection and leaves the wake running, so the retry finds the strand live. Say so in the comment.
- **provisionGraceMs**: the window the grace exists for starts when the insert attempt passes its abort check. `ControlDatabase.redeemInvitation` / `recordFormationUsage` check the signal once per attempt inside the write lock, then run `assertSeatRemains` (a read) and the transaction (a commit), so the grace contains one read plus one commit. A retry after a failed attempt re-checks the abort, so only one attempt needs containing.
- **responseTravelMarginMs**: the contact frame's trip out and the result frame's trip back (half a round trip each), plus the validation reads above. This replaces `PROVISION_RESPONSE_TRAVEL_MARGIN_MS` (3 000), whose own NOTE asks for exactly this.
- **sessionMs**: the initiator's dial plus its await-response. The responder needs awaitContact + validation + work + grace = 10 000 + 52L, which is inside it at every L.

Ordering, strict at every L > 0: approval hook (10 000) < provisionWorkMs < work + grace < initiatorAwaitResponseMs < sessionMs, and the responder's whole path < sessionMs.

**What this costs**, and the comment on `formationDeadlines` must say it: at the default declaration, a joiner whose responder accepts the contact and then hangs waits up to 188.5 s (about 3 minutes) before being told, where today it waits 15 s; the whole session is bounded at 208 s. A responder that is unreachable still fails at the dial, 19.5 s. A host that knows its party is on a fast link lowers `linkRoundTripMs` and gets roughly today's numbers (the L = 100 column).

## Wiring and configuration

- `FormationListenerOptions` and `FormationDialOptions` gain `linkRoundTripMs?: number`. Each role computes `formationDeadlines(options.linkRoundTripMs)` once and takes its fields as defaults.
- Explicit overrides still win, field by field, for tests: `sessionTimeoutMs`, `provisionTimeoutMs` (both roles), `stepTimeoutMs` (listener only, now meaning the await-contact read), and a new `dialTimeoutMs` (initiator only). **Remove `stepTimeoutMs` from `FormationDialOptions`**: the initiator has no frame step any more (the contact write is not awaited), and keeping the name there is how the dial came to live under a "step" budget. No backwards-compatibility shim (AGENTS.md).
- A configured `provisionTimeoutMs` splits as today: grace = `min(derived provisionGraceMs, floor(configured / 2))`, work = the rest. The initiator's await-response for a configured budget is the configured value plus the derived `responseTravelMarginMs` at the same link (`StrandFormationManager.initiatorProvisionTimeoutMs`), replacing the use of the retired constant.
- The session clamp (`provisionCeilingMs` / `resolveProvisionTimeoutMs`) keeps working for overrides, with the room it holds back per role changed from `stepTimeoutMs` to what actually precedes provisioning in that role: the dial for the initiator; await-contact plus validation for the responder. The responder's extra reserve becomes the derived travel margin.
- `StrandFormationManagerConfig` gains `linkRoundTripMs?` and `dialTimeoutMs?`, forwarded to the listener and to `dialFormation`.
- `CadreNode.initializeStrandSolicitation` sets `formationConfig.linkRoundTripMs` to `this.config.network?.linkRoundTripMs` unless the caller's `formationConfig` already carries one. No other production caller builds a formation manager.
- The dial moves to `withDeadline(dialMs, 'Formation dial-connect', (signal) => node.dialProtocol(addr, protocolId, { signal }))`, so an expired dial is cancelled. Do not add `runOnLimitedConnection`: that is a separate question about the relay's limits (see Out of scope).
- `formation-approval.ts` exports its `DEFAULT_TIMEOUT_MS` (rename to `DEFAULT_APPROVAL_TIMEOUT_MS`) for the ladder to import. If that import creates a module cycle (`formation-approval.ts` imports `control-database.ts`), move the constant into `strand-formation-protocol.ts` and have `formation-approval.ts` import it from there instead. Its `link-independent` lint directive moves with it.
- The four `link-bound, not yet derived: debt-formation-and-relay-admission-deadlines-ignore-the-declared-link` directives in this file go away with the literals. `PROVISION_SETTLE_GRACE_MS` and `PROVISION_RESPONSE_TRAVEL_MARGIN_MS` are retired (the latter is exported; drop it from `index.ts` if listed there and from every importer). `yarn lint` must pass with no new directive; the ladder's only literal is the approval constant, which already carries `link-independent`.

## Edge cases & interactions

- **Dial resolves just as the deadline fires.** `withDeadline` aborts the signal; libp2p's `dialProtocol` rejects on abort, but if the stream resolved in the same tick the timeout rejection wins and the stream is left open. Close it: attach a `.then(stream => stream.abort(...))` to a dial that settles after the deadline, or follow `exchangeFrame`'s "freshly-opened stream after the deadline fired is reset" pattern (`control-stream.ts` ~116). Verified by inspection.
- **Overrides that break the ordering.** A test that sets `sessionTimeoutMs` small with a derived provision budget must still clamp, not hang. The existing clamp tests (`strand-formation-protocol.spec.ts` ~283, ~310) cover this once they are moved from `stepTimeoutMs` to the new per-role room; keep their assertions, adjust only the option names and expected numbers.
- **Configured `provisionTimeoutMs` smaller than twice the derived grace.** The half-cap keeps at least half the budget for work. Unchanged behaviour; by inspection.
- **Both roles on different declarations.** The initiator derives from its own link, the responder from its own. If the joiner declares a faster link than the host, its await-response can end before the host's grace does, which is the same mismatch the module doc's "A machine that declares a faster link than its peers" bullet describes. Add formation to that bullet rather than engineering around it.
- **Concurrent sessions.** `DEFAULT_MAX_CONCURRENT_SESSIONS` (100) has a NOTE saying to revisit if the provisioning budget is raised well above its default; at the default declaration it rises from 12 s to 171 s. Only a caller holding a valid token and a valid consent signature reaches provisioning (strangers are cut at await-contact, 7 s, or at the first validation read), so the new exposure is one invitee opening many sessions with one token. Rewrite that NOTE to say this, with the revisit condition "if invitation tokens are published where untrusted parties can read them, cap in-flight sessions per token". Tripwire, not a ticket.
- **Hibernating host strand.** Not counted in the work budget by design (above). A slow wake still produces the retryable "did not wake within the formation provisioning budget" rejection; the larger work budget only makes that rarer.
- **Unbound (responder-provisions) path.** `provisionUnbound` does one read (`resolveInviteSAppId`) and `provisionAndRecord` (approval, then one commit). It is inside the bound path's numbers; by inspection.
- **Integration tests** declare no link, so they get the default ladder: successful formations are unaffected, and any scenario that waits on a formation *failure* now waits longer. The one known site is `strand-formation-e2e.integration.ts` Phase 6 (~1503-1690): it configures `provisionTimeoutMs: 3000` on the responder, so its work/grace split stays 1500/1500 under the half-cap and its assertions hold; only the comment at ~1514 ("22 s" ceiling, "15 s initiator default") needs the new numbers. Grep `packages/integration-tests/src` for any other formation-failure expectation and give it an explicit short override rather than a longer test timeout.
