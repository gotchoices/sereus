# Membership rows are read once and kept until they change

## Why

Measured by `message-cost-accounting` (2026-10-19): an owner admitting a member read `CadreControl.Revocation` 24 times in a 362 ms phase; strand formation read it 14 times on the responder in 293 ms and 17 times on the joiner's first insert; an idle node reads it 24 times a minute. Every member-list or peer-record read reads `Revocation` first (to drop retired rows), and every flow calls several of them. On a single machine each read is local work. On a two-machine cadre every read of a held block past the 10 s read-repair window starts a background `sync` with the sibling, and every read of a never-written block consults the cohort, so repeated reads are repeated network requests.

Per-flow deduplication (passing rows between functions, as `queryOwnerKeyRows`' `retired` parameter does) fixes one flow at a time, and the repeats come from at least five flows. An in-memory view of the tables removes the whole class. `control-reconcile-woken-by-changes-reads-once` restructures the reconcile pass on top of this view; `formation-and-redemption-read-each-row-once` likewise reads through it.

Only small tables bounded by the party's machines and owner keys are cached here. Strand lists and app-sized tables are not.

## Design

### The view (`membership-view.ts`)

One small class per cached table, generic over the raw row type, holding:

- `rows` — the table's raw rows (every column the readers below select, no filtering), or absent;
- `loadedAt` — when `rows` were installed;
- `generation` — bumped by every invalidation;
- the in-flight load, keyed by generation and by the caller's `retry` flag.

`read(retry)`:

1. If `rows` is present and younger than the maximum age, return it. No I/O.
2. Otherwise join an in-flight load with the same generation and the same `retry` flag, or start one. A `retry: false` caller (one reading under the write lock) never awaits a retrying load: a retrying load sleeps its backoff, and sleeping inside the lock stalls every local writer (the NOTE on `readRows`).
3. When the load finishes, install its rows only if (a) the generation is unchanged since the load started, and (b) the load was eligible to install (below). Either way, the load's own callers get its rows — a read that raced a write sees the pre-write state, exactly as an uncached read would.
4. A failed load installs nothing and rethrows.

`invalidate()` — bump `generation`, drop `rows`. Synchronous, flag-setting only; this is what the watch handler calls.

`clear()` — invalidate and forget in-flight loads; called by `ControlDatabase.close()` and at the start of `initialize()`.

Keep it independent of `ControlDatabase`: it takes a loader function (`(retry) => Promise<{ rows; installable: boolean }>`) and a clock (default `Date.now`), so its branching is testable without a database.

### Wiring in `ControlDatabase`

- Three views: `Revocation` (all six columns, marker row included), `CadrePeer` (the ten columns `queryCadrePeers` selects today), `OwnerKey` (the six columns `queryOwnerKeyRows` selects today). One full-table scan each; the per-`TableName` `where` of today's revoked-stamps read goes away.
- At the end of `initialize()`, after the schema is applied: one `this.watchTables(['CadreControl.Revocation', 'CadreControl.CadrePeer', 'CadreControl.OwnerKey'], async () => {}, { label: 'membership-view', onInvalidate })`, where `onInvalidate` maps the qualified name to its view and calls `invalidate()`. No backstop (the maximum age does that job). `close()` already disposes it through the registry; also `clear()` the views there.
- Readers derive their results from the view's raw rows, building fresh result objects per call (callers may mutate what they get; the cache must not change under them):
  - `queryRevokedStamps(table, retry)` — filter `Revocation` rows by `TableName`, collect `StampId`.
  - `queryRevocations(retry)` — `Revocation` rows minus the ledger marker, mapped as today.
  - `queryCadrePeers(retry)`, `queryOwnerKeyRows(retry, retired?)`, `getOwnerKeys(retry)` — as today, from their views. Keep calling `this.queryRevokedStamps(...)` for the retired set: specs interpose on that method to model a replicated live-row-plus-tombstone state.
  - `queryPeerRecord(peerId)` — find the row in the `CadrePeer` view (today a `where PeerId = ?` point read).
  - Every other `queryRevokedStamps` caller (`queryPendingJoins`, invitation/grant/device-token/strand status reads, `signWithdrawals`, `liveOwnerKeyStamp`, `CadreNode.resolveDeviceToken`) benefits without change.

### When the view is bypassed or a load is not installed

- **An explicit transaction is open on this `Database` and the caller is under the write lock** (`retry: false` and `!db.getAutocommit()`): read SQL directly, do not touch the view. Such a read may see the transaction's own uncommitted rows; a rollback fires no watch event, so installing them would cache rows that never existed. Today no reader of these three tables runs inside an `inTransaction` body; the rule makes that safe if one is added, and covers raw-handle transactions in specs.
- **A load served by the committed-read path** (`writeInFlight(...)` true when the attempt ran — see `readRowsOnce`) is not installed. A committed read may initialize an untouched table provisionally, and the Optimystic plugin arms its replicated-change bridge for a table only on a full initialization (`OptimysticTable.initializeForCommittedRead` in `../optimystic/packages/quereus-plugin-optimystic/src/optimystic-module.ts`). Installed rows from that load could then never be invalidated by a replicated change. The loader reports which path its successful attempt took (`installable`).
- **The `cohort-unreachable` fallback.** `readRevokedStampRows`' rule — an isolated node that has never held the `Revocation` block reads it as holding no revocations — moves to `queryRevokedStamps`, around the view read: catch `isCohortUnreachableRead` from the view's load, return an empty set, and install nothing, so the next call asks again once connectivity returns. `queryRevocations` keeps throwing on that failure, as today. Keep the accepted-tradeoff NOTE with the rule.

### Maximum age

`MEMBERSHIP_VIEW_MAX_AGE_MS = DEFAULT_CONTROL_COHORT_RECONCILE_MS` (import from `control-cohort.ts`; no import cycle — `control-cohort.ts` imports only a type from `strand-cohort.ts`). After it, the next read reloads. That reload is also what restarts read-repair for these blocks, since cached reads no longer touch storage. It bounds staleness for a change that reaches this node with no storage event: a machine outside a block's cohort (a cadre larger than 16 machines), and a machine that was offline when a sibling committed and has not yet re-read the block. Today's bound for both is the 15 s reconcile pass; tying the constant to it keeps that bound. Put a `NOTE:` at the constant naming both cases and saying that lengthening the reconcile interval lengthens this too (the reconcile ticket owns that decision).

### Reads that stay SQL

- `queryStampId` (all tables, including `CadrePeer` and `OwnerKey`) — physical-presence read keyed by row, used inside locked bodies for insert-if-absent guards and to bind a removal digest to the row's current nonce. Deliberately raw (sees retired rows).
- `hasOwnerKey` — deliberately raw `count(1)` for the genesis decision; once per start.
- `openRevocationLedger`'s marker presence read (~3599) — runs once per connected owner pass until filed; `revocation-ledger-marker-removed` deletes it.
- The schema's CHECK constraints (`NotRevoked`, `Authorized`, `MinOneOwner`, the live-owner clauses) — they read inside the committing transaction by construction.
- The seat counts under the write lock in redemption and formation (`assertSeatRemains`, `assertCadreInviteSeatRemains`, `assertOwnerGrantSeatRemains`) — they read usage tables, not these three; listed so the reviewer does not look for them.

The pre-transaction reads inside locked bodies (`deleteOwnerKey`'s `getOwnerKeys(false)`, `revouchOwnerKey`'s `queryOwnerKeyRows(false)`, `liveOwnerKeyStamp`, `signMachineRemovals`' `queryRevocations(false)`, `signWithdrawals`) do serve from the view: no transaction is open, the view reflects every local commit, and the schema's CHECKs re-decide inside the transaction.

## Edge cases & interactions

- **Read-your-writes.** Quereus runs the watch handler inside the committing call, so a write awaited and then followed by a read always reloads. Verified by the spec.
- **The membership listener.** `notifyMembershipChanged` runs `CadreNode.refreshAuthorizedControlPeers` under the write lock after the commit, with `retry: false`. The commit has invalidated `CadrePeer`/`OwnerKey`, so the refresh loads them fresh (non-retrying, no transaction open, installable). By inspection.
- **Concurrent load and invalidate.** A load in flight when an invalidation lands must not install. Generation check; verified by the spec.
- **A caller arriving after an invalidation while an older load is in flight** must not join it: in-flight loads are keyed by generation. By the spec.
- **`retry: false` and `retry: true` callers concurrently on a cold view.** Two loads; the retrying one's backoff is never awaited under the lock. By inspection.
- **Writes through another handle on the same `Database`** (specs use `db.getDatabase()` to `exec` raw SQL) fire the watch too, so the view invalidates. A spec that mutates storage through a different `Database` instance would read stale rows; fix any such spec by invalidating or re-reading, not by bypassing the view globally.
- **Both events of one local commit** (Quereus's dispatch and the plugin's storage event) invalidate twice; harmless.
- **A replicated change with no storage event** — bounded by the maximum age (above).
- **Never-written `Revocation`** (before `control-collections-created-at-cadre-founding` / the ledger marker): the first load consults, installs an empty table, and later reads cost nothing. A replicated first tombstone arrives through the bridge armed by that load's full initialization.
- **`revocation-ledger-marker-removed`** (in `implement/`) may remove the marker before or after this lands. The marker filter in `queryRevocations` and the `TableName` filter in `queryRevokedStamps` keep working either way; if that ticket has landed, drop the marker filter.
- **`close()` then `initialize()` again** — the views are cleared at both; the old subscription is disposed by the registry; a load in flight across `close()` must not install (clearing bumps the generation).
- **Gate-suite fakes** (`test/membership-gate-helpers.ts`, `test/cadre-node-authorized-surface.spec.ts`) mirror the retired-stamp filter's shape, which does not change. By inspection.
- **Specs that rig a read by its SQL text** (`control-read-retry.spec.ts` rigs `from CadreControl.Revocation` and `select PeerId, Multiaddr, StampId`; `control-read-routing.spec.ts` records options for the `OwnerKey` scan) — keep the view's load SQL containing those fragments, and make each test start from a cold view (fresh database or explicit invalidation). Tests asserting the cohort-unreachable fallback on several consecutive calls still pass because that answer is never installed.
