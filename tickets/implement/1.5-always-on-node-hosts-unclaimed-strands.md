# Always-on nodes host strands they have no app for ("storage replicas")

## Decision this implements

Maintainer, 2026-09-28 (option A of the former blocked ticket `always-on-nodes-host-strands-of-apps-they-do-not-run`): an always-on node joins every strand its strand filter admits, as an ordinary Optimystic node that stores and serves the strand's blocks, whether or not the app is installed there. It needs no sApp config (the app's schema + id + version + signature) and never applies the app's schema. Acceptance: once a phone's write has reached the party's always-on node, losing the phone loses nothing.

## Terms

- **Strand**: one app's shared data network, with its own replicated SQL database and its own libp2p node on each participating machine.
- **Claimed strand**: one whose sApp config this node holds (`CadreNode.sAppConfigs`, filled only by `addStrand`). **Unclaimed**: a strand row in the control database with no config — today it is only announced as `strand:discovered` and never launched.
- **Storage replica**: what this ticket adds — a strand instance launched with no sApp config.

## What research established

**The runtime already supports a strand with no app schema.** `composeStrand` (`quereus-plugin-sereus/src/compose-strand.ts`) applies the `Strand` membership schema unconditionally and the `App` schema only `if (schema)`. So a storage replica is the existing `StrandInstanceManager.startStrand` path with `sAppConfig` absent: same libp2p node, same raw storage, same `StrandDatabase`, only without `declare schema App`. Keeping the `StrandDatabase` (instead of running a bare libp2p node) is deliberate:

- The closed-strand revoked-peer gate (`StrandRevocationEnforcer`) reads `Strand.Member`/`MemberPeer` through that database. Without it, an always-on node would serve a closed strand's blocks to revoked peers.
- The membership reconciler writes this machine's own `Strand.MemberPeer` binding for closed strands — which is exactly the census `feat-strand-yardstick-from-serving-machines` wants to count.
- The first-sync gate works unchanged: `appTablesReadable` iterates the catalog's `App` tables, which is an empty loop on a replica.

None of this executes anything the app supplied: the `Strand` schema is cadre's own (`schemas/strand.qsql`).

**Credentials for closed strands are already on the machine.** `resolveStrandPartyKey` reads the party's own membership key from the control database's `StrandPartyKey` row, which replicates to every machine in the party; the strand row's shared read secret (`MemberPrivateKey`) comes from the control row too. So a replica on a closed strand seats its `MemberPeer` binding through the same reconciler path every second machine of a party already takes (`strand-membership-second-machine.integration.ts`). Nothing new to build; verified by inspection.

**Replication breadth.** `DEFAULT_STRAND_CLUSTER_SIZE` is 4 (not 20), and Optimystic shrinks a cohort to the machines actually serving the strand. So for a strand served by up to 4 machines, every block committed while a machine serves lands on it. Blocks committed while it was absent reach it through the peer-join catch-up (`peer-join-backfill.ts`), which pushes a machine's *whole* local store to each newly connected strand peer. So a phone + one always-on node (the maintainer's case) ends with every block on the always-on node once the two have been connected once after the write. Above 4 serving machines, a given always-on node holds only its share of new commits until some peer's catch-up pushes the rest on reconnect — the strand still has 4 copies. Nothing to change for the acceptance case; the doc update below says this plainly instead of "every node holds every block".

**Which machines host replicas.** `strandFilter` defaults to `all` on every `CadreNode`, phones included, so the filter alone cannot be the switch. The node profile is: `NodeProfile` is documented as "determines storage participation", every always-on node is `profile: 'storage'` (cadre-cli configs such as `reference-app-rn/drone.cadre.yaml`, cadre-host donations requested by the reference app, cadre-provider containers by default), and phones are `transaction`.

## Design

### Config

`CadreNodeConfig.hostUnclaimedStrands?: boolean` — launch a storage replica for a strand row this node's filter admits but holds no sApp config for. Default `profile === 'storage'`. Document it next to `strandFilter` in `types.ts`. cadre-cli needs no change (it already passes `profile`); do not add a cadre-cli key unless the implementer finds a real need.

### Launch path (`cadre-node.ts`)

`handleStrandAdded`, no-config branch:
1. Record in `discoveredStrands` and emit `strand:discovered` **only if the id is not already recorded** — a replica launch that fails is retried by the watcher (`forgetStrand` + backoff), and each retry re-enters this branch; the app must still see one announcement per strand.
2. If `hostUnclaimedStrands` resolves true, `await this.launchStrand(strand, undefined)` inside the same try/emit-`strand:error`/rethrow shape the claimed branch uses (so the watcher's retry ladder works). Otherwise return as today.

The strand stays in `discoveredStrands` while it runs as a replica: it is still unclaimed by any app, and a later `addStrand` claim removes it as today.

`launchStrand` / `startOrFoundStrand` take `sAppConfig: SAppConfig | undefined`. A replica launch is **always a joiner**: pass `founder: false` whatever `isSelfFoundedRow` says. (A storage-profile machine that founded a strand and restarted can have its watcher poll land before its app's `addStrand`; the claim then founds the tracked instance through `foundExistingStrand` as it does today — but see the prereq-chained ticket `claiming-a-hosted-strand-upgrades-in-place` for the ordering that claim needs.)

`getSAppId` (the watcher's `sAppId` filter lookup): fall back to the sApp id the replica read from its own `Strand.Header`. Record it once the replica's database is published (the first-sync gate opening, or immediately when the Header is already held), with one `select sAppId from Strand.Header` read; keep it in a map cleared by `detachStrand` and `cleanup`. Without this an `sAppId`-filtered storage node admits every strand provisionally forever and hosts all of them; with it, the watcher's existing re-evaluation rejects a non-matching strand and stops the replica. A failed read logs and leaves the id unknown (the strand stays provisionally admitted) — never throws into the launch.

### Instance manager (`strand-instance-manager.ts`, `strand-database.ts`)

- `StartStrandConfig.sAppConfig` becomes optional. Absent: skip `assertSchemaSignature`, leave `instance.sAppInfo` unset (the field is already optional), latency hint = `defaultLatencyHint`, log "storage replica" in place of the sApp id/version.
- `StrandDatabaseConfig.sAppConfig` optional; `connectToStrand` gets `schema: undefined`.
- `StrandDatabase.initialize` with `founder === true` and no `sAppConfig` throws a clear error (the founder bootstrap writes the `Header`'s sApp columns). Unreachable through `CadreNode` after the launch rule above; the throw is the guard against a future caller.
- `ensureFounderBootstrap` on a config without `sAppConfig` hits the same throw.

Now: on those machines **plus** storage-profile machines (with `hostUnclaimedStrands`) whose filter admits it. The conclusion stands — the party's machine count is still not the serving count (phones serve only what their app claims) — so only the premise changes.

Many scenarios run a `profile: 'storage'` machine (`topology.ts` makes machine 0 storage by default; `node-fixtures.ts`, `control-trio.ts`, `test-party.ts`, `strand-restart-party.ts`) to hold control blocks, and they assert which machines run a strand. ## Edge cases & interactions

- **Repeated `strand:discovered` on replica-launch retries** — guarded by the `discoveredStrands.has` check. Verify: extend the existing no-config unit spec (`discovered-strands-late-subscriber.spec.ts` or `cadre-node-strand-added-failure.spec.ts`, whichever already stubs `strandManager`) with one case: storage-profile node, stubbed launch rejects twice then resolves → exactly one `strand:discovered`, two `strand:error`, instance launched without `sAppConfig`. This is the one unit test worth adding (real branching: profile × config present × retry).
- **Transaction-profile node** (phone): behaviour unchanged — no launch, one `strand:discovered`. Covered by the existing specs, which use `profile: 'transaction'`.
- **`hostUnclaimedStrands: false` on a storage node**: today's behaviour. Inspection.
- **Filter `none` / `strandId`**: the watcher never calls `handleStrandAdded` for rejected rows; nothing new. Inspection.
- **Filter `sAppId`**: provisional admission → replica runs → Header's sApp id recorded → next poll's re-evaluation rejects a mismatch → `handleStrandRemoved` → `detachStrand`. Header never arrives (no peer reachable): stays provisionally admitted as a syncing replica, which is harmless. Inspection; no test.
- **Founder-derived row on a replica launch**: forced joiner. Inspection plus the `StrandDatabase` throw.
- **Closed strand**: revocation enforcer and reconciler arm as for any joiner; a replica that is revoked gets `onSelfRevoked` → `strand:revoked` like any machine. Inspection (same code path as `strand-membership-second-machine`).
- **Strand unpublished / removed while replica runs**: watcher's removed-strand loop → `detachStrand`, same as a claimed strand. Inspection.
- **Hibernation**: storage nodes default to `hibernation: { enabled: false }`; a replica on a node with hibernation enabled quiesces like any strand and misses live commits until woken, then catches up through the peer-join push. Inspection; note in the Deployment doc bullet.
- **Warm restart hydrate**: `pluginResult.hydrate` may load `App` table definitions persisted in the replicated store into the replica's catalog. That is declarative metadata, not execution; the first-sync probe then reads those tables once, from blocks the replica holds. Verify it does not throw in the scenario's restart-free run; mention in a comment at the `schema: undefined` site.
- **Disk growth**: a replica host stores every admitted strand with no quota (Arachnode quotas are unimplemented). Tripwire: a `NOTE:` at the `hostUnclaimedStrands` resolution — if always-on nodes host strands by the hundred, per-strand quotas or a filter default change is the lever.
- **Cross-party strands a phone joined by hand-carried row** (not in the party's control database): not hosted — the replica host never sees the row. Parked as `backlog/feat-always-on-node-hosts-strands-joined-from-other-parties`.

## The test that matters

New scenario `packages/integration-tests/src/scenarios/strand-always-on-replica-survives-phone-loss.integration.ts`, built on the helpers and the three rules of `strand-late-cadre-join.integration.ts` (ordering measured, no test-side strand dial, physical claim read off raw stores via `block-store-probe.ts`):

1. One party: an always-on node (`profile: 'storage'`, `hostUnclaimedStrands: true`, never calls `addStrand`) and a phone-shaped node (`profile: 'transaction'`) that founds an **open** strand with the simple chat-style schema and writes N rows.
2. Assert the always-on node runs the strand with no `sAppInfo`, and — raw stores only — that every block the phone's store holds for that strand is present in the always-on node's store.
3. Stop the phone and delete its storage.
4. Enroll a fresh phone-shaped machine into the same party, `addStrand` with the same sApp config, and read all N rows back while the always-on node is the only other machine up.

Expected: N rows, identical content. An open strand keeps the scenario off the closed-strand admission path, whose physical-replication scenario has a known flake history; the closed-strand replica is verified by inspection as above.

Run with `yarn workspace @serfab/integration-tests test <file>` in the foreground; also run `yarn workspace @serfab/cadre-core test`, `yarn lint`, and the type check. Do not build or run anything in `../optimystic`, `../quereus`, `../Fret` (see project rules).
