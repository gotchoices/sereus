# The phone kit acts on `cadre:removed`

`node-learns-it-was-removed` gives `CadreNode` a `cadre:removed` event and `removedFromCadre()`. The phone kit (`@serfab/cadre-rn/phone-node`, `PhoneNode`) owns the node's lifetime, its saved start and the party's local storage, so it is the layer that acts.

## Behaviour

- **Subscribe** when a node is built (`buildAndStart`, next to the kit's other node subscriptions), and check `removedFromCadre()` once after start.
- **On removal**, in the kit's transition queue (`inTurn`, so no start, stop or join interleaves):
  1. Shut the node down (`shutDown`).
  2. Delete the removed party's local storage with the dissolve machinery: `removeParty(this.partyStorage(), partyId)` (`dissolve.ts`), which writes the marker first so an interrupted deletion finishes on the next start (`finishMarkedRemoval`). No holdings check: unlike a dissolve, this party's other machines already refuse this phone, and what it wrote that reached them stays there. Removing the running party is the point here, so call `removeParty` directly, not `dissolve` (which refuses the running party).
  3. Saved start: when the running options carry a `formerPartyId` (an app that joined this cadre from one it founded and did not dissolve), save a start for the former party with `origin: 'founded'` and `autoStart: false`; otherwise clear the saved start. Never auto-start anything: the user should see why the app left its cadre before it does something else.
  4. Status `{ state: 'removed'; partyId: string; removal: CadreRemoval; formerPartyId?: string }` (new `PhoneNodeStatus` arm). `node` and `options` read null, as for `stopped`.
- **From `removed`**, `start(options)` and `joinCadre(invitation)` work as from `stopped`. The app offers "Go back to your own cadre" by starting the saved start (`loadSavedStart`), or a join.
- **Background start** (push wake, `createPhoneNode` with a saved start): with the saved start cleared or `autoStart: false`, nothing starts.

## Edge cases & interactions

- **Removal during a join in progress** (`joining` into another party): the join's node is the one in the new party; a removal of the old party cannot be reported by it. If the removal fires on a `running` node and a `joinCadre` is queued behind it, the removal's transition runs first; the join then starts from `removed` (as from `stopped`). By inspection.
- **Removal reported while the kit is stopping**: `inTurn` serializes. If the stop runs first, the queued removal transition finds the reporting node already shut down; it still deletes the party, sets the saved start and reports `removed`, because the report came from that node while it ran. Check this by the node identity the report came from, not by `this.node`.
- **Removed while the app was not running**: after the next start the node never sees its own live row, so it never reports (the rule in `node-learns-it-was-removed`), and the data stays while every other machine refuses the phone. `NOTE:` at the subscription, with the revisit condition: if users meet this, persist "seen live" per party so the rule survives a restart.
- **Deletion failure** mid-way: the marker finishes it on the next start (existing `finishMarkedRemoval`). By inspection.
- **Owner key** on the phone: it lives in the kit's key store per party (`keyStore`); `removeParty` already deletes the party's keys with its storage — check that it does (the dissolve path deletes everything for a party), and if not, delete them here.
- **Former party already dissolved**: `formerPartyId` is absent once dissolved (`withoutFormerParty`), so the saved start is cleared. By inspection.

## Tests

One `node.spec.ts` case: a running joined node (options with `formerPartyId`) whose node reports removal ends in status `removed`, the removed party's storage is gone (as the existing dissolve test checks it), and the saved start names the former party with `autoStart: false`. Drive the report through a fake or by emitting the event on the real node; do not mock the kit's own modules.
