# All owner signing goes through one signer

## What is wrong today

A node signs owner writes from two sources that are not kept in step (`cadre-node.ts`):

- `SeedBootstrapService` signs with the private key passed to `initializeSeedBootstrap` (`seed-bootstrap.ts` `signDigest`, the one place it applies the key): `CadrePeer` vouches and removals, `OwnerKey` add/remove/re-vouch, machine removal, `DeviceToken`, `CadreInvite` issue/withdraw, `Revocation` re-issue and the ledger marker, and seeds.
- `CadreNode` signs its own writes with the **identity** key (`getSelfSigningKey` → `ed25519KeyPairFromLibp2p(identityKey)`) through `requireOwnerSigningKey` (~6363), `ownerSigningKeyCandidate` (~3015), `enrolledOwnerSigningKey` (~2989), `requireOwnerSigner` (~9576) and `signMessageWith` (~297): `Strand` add/delete (`publishStrand`, `unpublishStrand`), `StrandPartyKey` (`ensureStrandPartyKey`), `FormationInvite` (`publishFormationInvite`), `ValidationKey` add/remove, the `JoinedStrand` ledger (~2950), `JoinRequest` / `JoinSuccess` / `JoinFailure` / rewrite / dismiss, and `strand-move.ts` adoption (its own `OwnerSigner` interface, ~255, fed by `getIdentityOwnerKey`).

The two agree only because every caller today passes the identity-derived key to `initializeSeedBootstrap`. A node given any other owner key (as `reference-app-rn/test-fixture/start.mjs` already does) signs seeds and vouches with it and strands, joins and pending joins with its identity key, which the schema refuses.

## Design

- `CadreNode` holds at most one `OwnerSigner` (from `owner-signer-seam`). New `CadreNode.useOwnerSigner(signer)` does what `initializeSeedBootstrap(priv)` does today (refuse on a claim-configured node, anchor the key as `genesis`, build the seed-bootstrap service) with the signer. `initializeSeedBootstrap(privateKeyB64)` stays as the software-key convenience, `useOwnerSigner(softwareOwnerSigner(privateKeyB64))`, because ~100 test sites call it; its doc comment says so.
- `SeedBootstrapServiceConfig.ownerPrivateKey` becomes `ownerSigner?: OwnerSigner`; `canAuthorize()` is "has a signer"; the owner public key is `signer.publicKey`. Each owner-signed service method takes an optional trailing `sign?: OwnerSign`: when the caller passes one (a `CadreNode` action already inside `approve`), it signs with it; when not, the method opens its own `approve` with its own action text. That keeps the service's direct callers (its spec, `push-wake-e2e.integration.ts`) working with one config change, and lets a multi-step `CadreNode` action share one approval.
- `ControlDatabase` writers keep their per-row callback, widened to `(message: Uint8Array) => string | Promise<string>` (export the alias, e.g. `ControlSign`) and awaited, so existing synchronous test lambdas still type-check. `signGuardedRemoval` and its siblings become async.
- Every public owner action on `CadreNode` is exactly one `approve` call whose `action` names what the user is approving, with `partyId` the node's party: `addOwner`, `removeOwner`, `removeMachine` (re-vouches and removal together), `authorizePeer` / `claimNode` / `addDrone` (vouch + seed), `createCadreInvitation`, `withdrawCadreInvitation`, `publishStrand` / `foundStrand`, `unpublishStrand`, `forgetJoinedStrand`, `requestJoin`, `dismissPendingJoin`, validation-key add/remove, `adoptStrandBundle` (one approval for the whole bundle). Background writers (JoinedStrand publication, the pending-join runner, re-issue drains, the ledger marker, the self-row insert in `registerSelf`, device-token publish) call `approve` per write with their own action text; a software signer never prompts, and gating them for a prompting signer is `backlog/feat-owner-key-on-a-hardware-key`.
- Delete `requireOwnerSigningKey`, `ownerSigningKeyCandidate`, the owner use of `signMessageWith`, and `strand-move.ts`'s local `OwnerSigner` interface (adoption takes the node's signer). `getSelfSigningKey` stays: it signs the machine's own address record and device token (`Sig`), which are identity signatures, not owner ones.
- `isOwner()` / `enrolledOwnerSigningKey` become: a signer is wired and `signer.publicKey` is a live `OwnerKey` row here. `PendingJoinRunnerDeps.isOwner` and `rent-node.ts` keep calling `isOwner()`.
- `wireOwnKeyIfOwner(signer?)`: wires `signer` when its key is a live owner here and returns whether it did; with no argument it tries a software signer over the identity key. That default is the interim path for owners admitted by an owner-granting `CadreInvite`, which still seats the device's identity key (`docs/architecture.md` → Owner Keys, "Invitation-granted owners"); `owner-grant-separate-from-machine-invitation` removes it.
- `publishStrand` writes `FounderOwnerKey = signer.publicKey` and `isSelfFoundedRow` compares against `signer.publicKey` (not the identity key). `owner-key-label-and-founder-machine` replaces that comparison with a machine signal; this ticket only moves the key source.
- `getIdentityOwnerKey()` stays for now (cadre-cli, the harness, cadre-rn and the web app still call it); `phone-and-web-kits-hold-a-separate-owner-key` deletes it once the last caller is gone.

## Edge cases & interactions

- A node whose owner signer key differs from its identity key: every owner write listed above commits and verifies (schema `verify`, the anchor derivation, `verifyRevocationSigner`, `listAuthorizedMembers` for the vouched row), and a seed it mints carries `signerKey = signer.publicKey`. **Test** — one spec in `cadre-core/test` over a single-node party with genesis on a fresh owner key: `foundStrand` (founds), `publishFormationInvite`, validation-key add, `requestJoin`, `authorizePeer` + `createSeed`, a `JoinedStrand` publish, `unpublishStrand`. This is the reproduction of the two-source bug: today the strand/join writes fail the schema.
- One approval per action: a counting test signer sees exactly one `approve` for `unpublishStrand` of a closed strand (two deletes, two tombstones) and one for `removeMachine` with a re-vouch. **Test**, in the same spec; it pins the seam contract the hardware backends depend on.
- A node with no signer: every owner action refuses as it does today without an owner key (`not-an-owner` / "Seed bootstrap service not initialized"); `isOwner()` is false; background owner writers do nothing. By inspection plus existing specs.
- A signer whose key is not (or no longer) an owner: writes fail at the schema as today; `isOwner()` is false; the removed-self path still stops the re-issue drains (`noteOwnRemoval`). By inspection.
- The write lock is held across `approve`'s signing calls, because writers read the stamps they sign inside the lock. Free for a software signer; leave a `NOTE:` at `withWriteLock` (or at the `ControlSign` alias): if a prompting signer holds the lock long enough to stall other writes, sign outside the lock with a stamp re-check.
- `lockedWithRetry` re-runs a writer body, so a retried write signs again inside the same `approve`. Free for software; a prompting backend relies on presence held for the session. By inspection; mention in the same `NOTE:`.
- `wireOwnKeyIfOwner` default must not wire the identity key on a machine where it is not a live owner (a joined member). Existing coverage (`app-joins-cadre-by-invitation`, cadre-rn joined-party specs) — run them.
- strand-move adoption refuses up front when the node's signer is not an owner of its party, as today with the identity key. Existing `strand-move` specs.
