# Joiner-consent signature: negative-test matrix + docs

Follow-up to `debt-formation-consent-core`, which made the joining peer sign its own
`CadreControl.FormationUsage` row (`PeerKey` + `PeerSig` columns, `PeerConsented` schema
constraint over the `'consent'`-tagged digest of `(Token, UsageStampId, PeerKey,
Disclosure)`, joiner-minted `UsageStampId` nonce carried in `FormationContactMessage`,
responder-side pre-check rejecting `'Invalid joiner consent'`). The core ticket lands the
mechanism plus positive-path tests; this ticket completes the adversarial test matrix and
the documentation.

## Key tests

Schema-level (`packages/cadre-core/test/control-formation-invite.spec.ts`):

> Note added by the review of `debt-formation-consent-tests-db`: that file is already
> ~1580 lines, and it now holds a small `FormationUsage.PeerConsented joiner-consent
> branch` describe (positive path, wrong-key refusal, seating-rollback). The matrix
> below roughly doubles it. Put the new cases in a sibling spec — e.g.
> `control-formation-consent-signature.spec.ts` — rather than growing the existing file,
> and move the three existing `PeerConsented` cases across so the constraint's coverage
> lives in one place. Reuse `test/formation-consent-helper.ts` and
> `test/control-constraint-helpers.ts`; do not re-mint either.


- insert with a valid `(PeerKey, PeerSig)` pair → accepted (may already exist from core ticket).
- insert with `PeerSig` signed by a *different* key → `CHECK constraint failed: PeerConsented`.
- insert with a signature valid over a *different* `(Token | UsageStampId | Disclosure)` →
  rejected (cover all three single-field mutations — the "lifting consent onto another row"
  cases: same key + same token + different nonce fails verify; same nonce fails `unique`;
  different disclosure text fails verify).
- insert reusing a spent `UsageStampId` → rejected by `unique`, not by `PeerConsented`.
- the approver's `'vouch'` signature presented as `PeerSig` → rejected (action-tag
  disjointness), and the joiner's `'consent'` signature presented as
  `context.ValidationSignature` → rejected (and cannot satisfy any other table's rule).
- a `ValidationUrl` invite requires BOTH signatures; a mismatch in either the nonce or the
  canonical disclosure bytes between the `'vouch'` and `'consent'` digests fails.
- `verifyFormationConsent` returns `true` for a row read back out of the table, `false`
  after mutating any signed field, and `false` (never throws) on garbage input.

Protocol/manager-level:

- responder rejects `approved: false` with `'Invalid joiner consent'` when `peerKey`
  disagrees with `partyId`, when the signature is bad, and when `peerKey` is malformed —
  and **discloses no responder identity or cadre addrs** in that reply.
- rejection happens before `provisionStrand` is called (assert the hook is never invoked)
  and leaves the invite unspent (`countFormationUsage` unchanged).
- joiner nonce reuse across two attempts surfaces as a clean `approved: false`
  (`'Formation conflict, retry'`), not a dropped result frame, and leaves the invite
  unspent for the second attempt.

End-to-end (`strand-formation-e2e.integration.ts`): a real two-party formation writes a row
whose stored `PeerSig` re-verifies via `verifyFormationConsent` against the `PeerKey` the
joiner actually used, and whose `PeerKey` matches the joiner's returned `memberKey`
(the Ed25519 peer id is the identity multihash of exactly the `PeerKey` bytes).

## Docs

- `docs/api.md` — approval-hook wire contract: POST body field `peerId` → `peerKey`, note
  the value is now the joiner's Ed25519 public key (libp2p peer id derivable from it), and
  that the redemption nonce is minted by the JOINER, not the responder.
- `docs/strands.md` / `docs/architecture.md` — wherever formation is described as the
  joiner contributing no signature, update to describe the stored, re-checkable consent
  signature.
