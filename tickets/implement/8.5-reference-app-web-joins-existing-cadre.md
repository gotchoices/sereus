# Browser reference app: join an existing cadre

Split from the plan ticket `reference-apps-join-existing-cadre`. Tab B is this browser tab; party B is the party it founded (every tab founds one on first load and runs owner genesis, `runOwnerGenesis` in `cadre-web.ts`); party A is the user's main cadre. Removing party B afterwards is `reference-app-web-dissolves-left-cadre`.

The web app has no kit. It follows the phone kit's rules itself (architecture.md → "An app joins an existing cadre"; the kit's implementation is `packages/cadre-rn/src/phone-node/node.ts` → `joinCadre`, `switchParty`, `startAndRedeem`, `returnToLeftParty`, and `strand-move.ts`). Read those first; this ticket is that sequence over IndexedDB. The duplication is parked as `debt-web-app-repeats-the-phone-kit-join-sequence`.

Decided here, not left to the implementer:

- **No first-launch question in the browser.** The tab keeps founding on first load: its e2e tiers and its purpose (boot a real node on page load) depend on it, and a founded tab that joins later carries its party along and dissolves it, which is what the move and dissolve exist for.
- **The chat strand stays local.** `addChatStrand` adds the fixed `sereus-web-chat` strand with `founder: true` and no control row, so it is not in any strand bundle; it keeps working in party A as the same local strand (its database is keyed by strand id). No change.
- **Moved strands are carried, not opened.** The tab has no `strand:discovered` handler (accepted-tradeoff NOTE beside `formedStrands` in `cadre-web.ts`), so strands adopted into A sit in the node's discovered map, as a joined strand does after a reload today. The move still matters: their rows, party keys and invitations reach A, and the dissolve's check then finds them held.

## 1. Per-party node-local records

Today each record in the node-local `kv` store has one key per tab (`trusted-owners`, `bootstrap-peers`, `enrolled-machines`, `strand-network`) and fails closed on a party mismatch, so the first save in party A would overwrite B's records, and a rollback to B would start without them. Key them per party, as the phone kit does: `<key>.<partyId>` (a small `partyKvKey(key, partyId)` in `node-local-slots.ts`). Records under the old keys are orphaned (development builds only; the repo keeps no backwards compatibility yet).

## 2. The start record

Replace the `party-id` kv entry with one JSON record, `party-start`: `{ v: 1, partyId, origin: 'founded' | 'joined', formerPartyId? }`, written in one `put`. Absent → mint a party id and write `{ origin: 'founded' }`, as `loadOrCreatePartyId` does today. A malformed record is a start failure with a clear message (same posture as an unreadable anchor), not a silent new party. A tab with only the old `party-id` key starts a fresh party (no compatibility read).

`startCadre(start?)` takes an optional record to start (used by the join and the rollback) instead of always reading the stored one. It never writes the record when one is passed; the join writes it after admission.

**Owner step by origin:**

- `founded`: `runOwnerGenesis` as today.
- `joined`: never `ensureOwnerKey`. Call `node.wireOwnKeyIfOwner()`; `true` → owner state `enrolled`, `false` → `member`. After an owner grant (`redemption.grantsOwner`), ask again every 2 s for up to 60 s, as the kit's `wireJoinedOwnerKey` does; a later start wires it otherwise. Extend `OwnerState` with `'enrolled' | 'member'` and show them on Home (`home-owner`).

## 3. Joining (`cadre-web.ts` → `joinCadre(encoded, { signal, onProgress })`, driven by a store action)

1. Decode (`decodeCadreInvitation`); refuse an invitation targeted at another peer id (`invite.peerId` ≠ this tab's) with the phone ticket's wording.
2. **Same party as the running node:** redeem in place (`waitForMember: true`, `signal`, `onProgress`), wire the owner key, adopt any move naming this party, done.
3. **Leaving a founded party:** `exportStrandBundle(node)`. If it holds strands, pending joins or invitations and the invitation does not grant owner, throw before anything stops: "This invitation makes the tab a member, and only an owner can bring its ‹n› strands along. Ask for one with “Also an owner” on." Non-empty: save the move record (below). Empty: delete B's move record if any (a stale one would bring deleted strands back; see the kit's `recordStrandMove`).
   Leaving a joined party: nothing is exported (that party's strands are its owners'); `formerPartyId` is carried from the current record.
4. Stop B's node through the store's teardown (subscriptions, chat strand, stores closed: `stopCadre`), start A with `{ partyId: A, origin: 'joined', formerPartyId }`, no bootstrap addresses, the same relay. Store status `joining`.
5. `redeemCadreInvitation(invitation, { waitForMember: true, signal, onProgress })`; then the owner step above.
6. Admitted: write the start record (`autoStart` has no meaning in a tab: a tab always starts), then adopt every move record naming A when the owner state is `enrolled`, then status `running`, chat strand added, subscriptions re-attached as after any start.
7. Any failure or cancel before admission: delete the move record this join wrote, stop A, start B from the stored (unchanged) record, rethrow. A failure restarting B leaves the store in `error` with that message logged; the join's error is the one shown.

**Progress** for the page: map `CadreJoinProgress` (`redeeming`, `waiting` + `reason` + `retryAtMs`) and two tab-emitted steps, `admitted` and `moving-strands`, onto the same step texts as the phone ticket `reference-app-rn-joins-existing-cadre` (its `join-flow.ts` table; copy the wording, the apps share no code).

## 4. The move record (`src/lib/web-strand-move.ts`)

Same shape and rules as the kit's `StrandMoveRecords` / `joinMoveRecord` / `adoptMoveRecord` / `adoptMovesInto` (`packages/cadre-rn/src/phone-node/strand-move.ts`): one record per left party under kv key `strand-move.<partyId>`, `{ v: 1, targetPartyId, bundle, moved, refused }`; adoption leaves out refused strands, calls `adoptStrandBundle`, deletes the record when `failed` is empty, else saves progress. An unparseable record is deleted with a warning. The bundle holds read secrets, party keys and bearer invitations; in a browser it sits in the same IndexedDB database as the tab's private identity key, which is that storage's existing trust level (say so in the module comment).

**Every start whose owner state is `enrolled` adopts records naming its party** before reporting `running`, so a tab closed after admission finishes the move on the next load.

## 5. Page: "Join my existing cadre" on `#/cadre`

Above "Add a device or app": the request (`encodeCadreJoinRequest({ v: 1, peerId: node.peerId, appName: 'Sereus web reference' })`) with `QrCode` and `Copyable`; a textarea "Paste response or invitation" and Join; while joining, the progress line and Cancel (aborts the signal; only before admission); afterwards the outcome (`done` with standing and moved count; a refusal in plain words, reusing the rejection table idea of the phone's `join-failure.ts`). Home's party id and owner rows update from the store as they do after a Restart.

## Edge cases & interactions

- Cancel while waiting: back in B, unchanged (move record deleted, start record untouched). By inspection.
- Tab closed while waiting: nothing written except B's move record, which names A; the next load starts B (start record unchanged) and the record is adopted only if the tab later joins A, matching the kit. By inspection.
- Tab closed after admission, before adoption: the start record names A; the next load's start adopts. By inspection.
- Reload after joining: `origin: 'joined'` → no genesis, no `OwnerKey` row inserted for the tab in A. **e2e test** (below).
- Two tabs of the same origin: both share the node-local database and the start record; joining in one tab switches the other only on its next load, and until then the other keeps running party B against B's stores. Document in the README as unsupported (same footing as the existing two-tab NOTE in `node-local-slots.ts`). By inspection.
- Restart button on Home after a join: restarts party A from the record. By inspection.
- `exportStrandBundle` from B reads the persisted strand network state through the store opened for B's party; the per-party keys of step 1 must be in place before this works. By inspection.
- The relay reservation: A's node reserves the same relay; B's reservation ends when B's node stops. By inspection.
- An owner grant whose row has not synced when the 60 s pass ends: owner state `member`, move deferred; the next start wires and adopts. By inspection.

## Tests

- `e2e/distributed/join-cadre.spec.ts`, one test, "a tab joins a cadre by invitation and stays a member after a reload": an in-process headless party A (reuse the `formation-responder.ts` fixture's boot, or add a sibling fixture with owner genesis and a loopback WebSocket listener) mints a **member** invitation targeted at the tab's peer id (read from `home-peer-id`). The tab pastes it on `#/cadre` and joins (allowed: the tab's chat strand has no control row, so its bundle is empty). Expect `home-party-id` to be A and `home-owner` to read `member`; reload; expect the same two values, and the tab's owner key absent from the tab's own `OwnerKey` rows (add the `isOwner()` pass-through from `reference-app-web-owner-adds-device-or-app` to the `__cadre` debug hook and expect `false`; the existing `readControlAuthorizationState` reports only a count). This reproduces the founding-row defect at the web layer: with the origin ignored (genesis on every start), the reload inserts the tab's key.
