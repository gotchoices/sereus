# Every strand machine binds itself to its party's membership

Third ticket of the party-identity chain. The founder has its own identity (ticket 1) and a joiner receives a membership invitation plus its own party key (ticket 2). This ticket makes strand bring-up finish the job on every machine: redeem the invitation if one is pending, and write the durable machine→party binding (`Strand.MemberPeer`) that revocation enforcement and future admission control key on.

## Design (settled)

**One seam, one background loop.** The single point where a strand node's transport peer id and a live strand `Database` both exist, for launch *and* hibernation resume, is `StrandInstanceManager.buildStrandRuntime` immediately after `strandDb.initialize()` (before the revocation enforcer starts). Hook a per-instance **membership reconciler** there for closed strands that have a local control `StrandPartyKey` row. It must never block or fail bring-up: a joiner at this instant has not synced the founder's rows and may not have write quorum, so the reconciler runs asynchronously and retries on the revocation-enforcer cadence (default 30 s; share or mirror that timer) until it reaches the done state, then stops. Each pass:

1. **Ensure membership.** If `Strand.Member` shows this party's key: done with this step — and if a pending formation invitation (ticket 2's in-memory cache) is still unspent, *burn* it: insert the `ConsumedInvite` row alone, naming the existing member key (all its constraints are satisfiable without a `Member` insert), so the bearer credential cannot be spent by anyone else; ignore burn failures (expired/cancelled) beyond a log. If the member row is absent and a pending invitation exists: `consumeInvite` with the party key (retried across passes until the `Invite` row has replicated here and the write commits). If absent with no pending invitation (founder rows not yet synced, or a machine whose party never joined): keep waiting — log at a visible level after a bounded number of passes, never throw.
2. **Ensure the binding.** `registerMemberPeer(partyKeyPair, ownStrandTransportPeerId)` — already insert-if-absent and restart-safe. Runs only after step 1 sees the member row locally (its `MemberExists` check reads the live local table).
3. **Done state**: member row visible + own binding visible → loop stops (a later revocation is the enforcer's business, not this loop's).

**Clearing.** When this node unpublishes/removes the strand through the runtime path, clear its own binding first (`removeMemberPeer`, self arm) — best-effort with a log on failure, since the strand may already be unreachable. Deliberately *not* handled here: clearing bindings of a machine removed from the **cadre** at the control layer (the party still holds the key and can clear from any surviving machine). Record that as a `NOTE:` tripwire at the clearing site: the stale binding grants nothing today (admission is not allowlist-gated) and only mis-credits diversity; revisit when `feat-strand-member-allowlist-admission` lands.

**Revocation-enforcer interplay.** Until now production strands had no `MemberPeer` rows, so the enforcer's denied set was always empty; this ticket makes it real. Invariants to assert in tests: a binding whose member is live is never denied; the enforcer's bindings-before-members read ordering keeps a mid-reconcile machine (binding write racing member sync) out of the denied set; and a party revoked then re-admitted (fresh formation → fresh invitation → same party key) heals automatically — its old bindings stop being orphans the moment the fresh `Member` row lands.

## Edge cases & interactions

- **Both roles**: founder machines skip straight to step 2 (bootstrap seated their member row); joiner machines exercise the full ladder. A founder-party *sibling* whose `StrandPartyKey` row has not replicated yet: reconciler sees no party key, idles, and picks up once the control row arrives — bring-up never blocked.
- **Write failures are per-pass, not fatal**: `consumeInvite` rolls back atomically on any constraint rejection; `registerMemberPeer` may hit transient quorum unavailability; both just retry next pass.
- **Duplicate machines / restarts / resume**: every write in the loop is idempotent (insert-if-absent guards, single-use invite handled by the burn rule); resume re-runs the same seam.
- **Open strands**: reconciler never armed (`OnlyClosed` tables; mirror the enforcer's `Type === 'c'` guard).
- **Sealed strands**: `consumeInvite` on a sealed strand is schema-rejected (`NotSealed`) — the loop must treat that as terminal-with-log, not retry forever.
- **Self-revoked while reconciling**: if the enforcer flags this node's own party as revoked, the reconciler must stop rather than fight (re-admission arrives, if ever, via fresh formation).
- **Two member keys claiming one peer id**: cannot happen via this flow (each machine registers only itself under its party's key), but the schema permits it; consumers already treat such a peer as unlabelled — do not add cleverness here.
- **A `MemberPeer` row is not proof of membership** — every consumer must join to a live `Member` row (schema NOTE); keep that discipline in anything this ticket adds.

## Key tests

- Instance-manager unit specs (fake clock): full joiner ladder — invite redeemed once, binding registered once, loop stops; already-member path burns the invitation; no-invite path idles quietly; bring-up returns before any of this completes.
- Enforcer interplay spec: live-membered binding never denied; revoke → denied; re-admit under same party key → un-denied.
- Unpublish clears own binding (and tolerates failure).
- Update `docs/strands.md` "Removing Members" housekeeping wording where it assumes device records are only ever written by hand.
