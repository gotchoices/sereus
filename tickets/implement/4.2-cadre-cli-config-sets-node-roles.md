# CLI config surface for node roles

`node-roles-in-cadre-core` adds `CadreNodeConfig.roles?: Partial<NodeRoles>` and `resolveNodeRoles`. The CLI is the main way an always-on node is configured, so it needs the same surface.

## Shape

Config file, beside the required `nodeClass` (renamed from `profile` by `node-class-replaces-node-profile`):

```json
{
  "nodeClass": "server",
  "roles": { "overlayTier": "edge", "reactivity": "subscriber" }
}
```

- `roles` is optional; each key optional; unknown keys refused (the CLI's strict config checking via `@serfab/config-check`, like every other block in `schema.ts`). Values are checked against the same sets `NodeRoles` declares: `alwaysOn` boolean, `overlayTier` `edge|core`, `reactivity` `forwarder|subscriber`, `strandCohortMember` boolean.
- Environment overrides, one per role, in `ENV_MAPPINGS`: `CADRE_ROLE_ALWAYS_ON` (boolean), `CADRE_ROLE_OVERLAY_TIER` (string), `CADRE_ROLE_REACTIVITY` (string), `CADRE_ROLE_STRAND_COHORT_MEMBER` (boolean).
- `roles` is passed through to `CadreNodeConfig.roles` at both node construction sites (`start-node.ts`, `node-session.ts`). `strandCohortMember: false` is refused by cadre-core; the CLI does not duplicate that check.
- Status (`status-query.ts` text and JSON, `/status` in `health.ts`) reports the **resolved** roles (from `resolveNodeRoles`) next to the preset, so an operator sees what the node is actually doing rather than only what they overrode.

`cadre-host` and `cadre-provider` keep passing only a node class; neither needs per-role control yet. Not in scope.

## Edge cases & interactions

- **Env value outside a role's set** (`CADRE_ROLE_OVERLAY_TIER=fast`): refused by the validator with the path named, like any other bad env value. Verified by the existing env/validation pattern; no new test unless the boolean/string kinds need a new `EnvKind`.
- **`roles` present but empty** (`{}`): valid, same as absent.
- **Status for a node started before roles existed** (status reads a running node's health endpoint): the endpoint is in the same build, so no compatibility case.

## Tests

- Extend the existing config-validation spec with one accepted `roles` block and one refused unknown key. Nothing for the pass-through or status formatting.
