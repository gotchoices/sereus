# Plan the schema guide's query examples against a named schema

## Background

`packages/quereus-plugin-sereus/test/schema-guide-examples.spec.ts` reads `docs/schema-guide.md` with `marked`, and every fence's info string must be `sql schema` (an sApp schema body: applied through `applyAppSchema`, then an insert/update/delete planned per table and a select per view), `sql script` (run as-is) or `sql fragment` (never run). Most query examples are `fragment`, so nothing catches a query that uses a missing function, a missing column or an unsupported form.

Probed 2026-09-29 against an in-memory Quereus `Database` with the crypto plugin registered, the guide's queries planned against a schema with `db.getPlan`:

- Planned cleanly: the Ordering `insert … with context now_iso = datetime('now') values …`; the Pattern A `select … order by Timestamp asc, Id asc`; all three RETURNING statements against the "Putting It All Together" `messages` table (which has `body` and `sent_at` — the ticket that filed this compared them to the skeleton's `content`, the wrong table); non-recursive CTE; recursive CTE with `option (maxrecursion 1000)`; `as materialized` / `as not materialized`; `union`, `except`, `diff`; `sum(...) over (partition by … order by … rows between unbounded preceding and current row)`; `count`/`avg`/`min`/`max` as window functions; `row_number() over (…)`; `json_each(:doc)` and `json_tree(:payload)` with a parameter; named parameters (`:who`, `:pid`) unbound.
- Failed:
  - `json_array_elements_text(...)` — "Function not found: json_array_elements_text/1". Quereus has `json_each` and `json_tree`.
  - A comma join passing a preceding table's column into a table-valued function (`from posts p, json_each(p.tags) as t`) — "p.tags isn't a column". So does `join json_each(p.tags) t on 1`. Only `cross join lateral json_each(p.tags) as t` planned.
  - `DigestAll(Digest(x)) over (…)` — "Unknown window function: DigestAll". `group_concat(...) over (…)` also fails ("Unknown window function: group_concat"), so a running digest cannot be built from a window aggregate. A recursive CTE `with recursive chain(x, cumulative_digest) as (select 1, digest(1) union all select x + 1, digest(cumulative_digest, x + 1) from chain where x < 3) select …` planned.
  - The CTE block's literal `select ...;` is a parse error by design; `users.last_seen`, `employees`, `big_table`, `small_table`, `a`, `b`, `posts`, `messages.tags` and the window example's `ledger(account_id, amount, ts)` exist in no guide schema.
- Negative controls: `select nosuchfn(1) …` fails "Function not found", `select nocol …` fails "Column not found", an unknown table fails "Table 'x' not found in schema path: App". Planning catches the drift this ticket is about.

## Design

### Fence grammar

The info string becomes one of:

- `sql schema` or `sql schema <name>` — unchanged behaviour; the optional name lets query blocks refer to it.
- `sql query <name>` — every statement in the block is planned (never run) against the schema block called `<name>`.
- `sql script`, `sql fragment` — unchanged; they take no name.

`<name>` is lowercase letters, digits and hyphens, starting with a letter (`/^[a-z][a-z0-9-]*$/`). Anything else — a `query` without a name, a name on `script`/`fragment`, a third word — fails the existing "every fence is marked" test, whose message should list the new forms. Schema names are unique across the guide; that same test also fails on a duplicate name. A query may refer to a schema block anywhere in the guide, before or after it (Pattern A's query sits above the Pattern B schema it uses).

Rejected alternatives: planning a query against the nearest preceding `sql schema` block needs no names, but it picks the wrong schema for most sections (RETURNING's nearest schema is the Seeds `roles` table) and breaks silently when a block moves. Embedding a schema in each query fence repeats tables the guide already declares. Naming costs one word per block and is invisible in rendered Markdown.

### Planning a query block

For each `sql query <name>` block, in its own `it`:

- Look up the schema block by name; an unknown name throws `query refers to no \`sql schema <name>\` block`.
- Fresh `guideDatabase()`, `applyAppSchema(db, schemaBody)` (no seed, no per-table write planning — the schema block's own test already does that), then `db.setSchemaPath(['App'])` so the guide's unqualified table names resolve. `setSchemaPath` is public (`../quereus/packages/quereus/src/core/database.ts`); do not use `getPlan`'s second argument, which Quereus documents as internal.
- `new Parser().parseAll(block.text)` (`Parser` is exported from `@quereus/quereus`) and `db.getPlan(statement)` for each parsed statement. A parse error fails the block — that is how placeholder text is caught. Zero statements fails too (`query block has no statements`), so an empty fence cannot pass vacuously.
- Wrap planning failures as the existing `planOrExplain` does, but name the statement by its 1-based position in the block (`statement 2 of 3: …`), since the parsed AST has no source text to quote. Generalise `planOrExplain` to take a label and a `string | AST node` rather than copying it.
- `db.close()` in `finally`, as the existing loop does.

Test titles follow the existing form: `${name} (query → ${schemaName})`. Add the `query` blocks to the existing `for` loop (or a sibling loop right after it); no other new tests.

Extend the spec's header comment with the `query` marker and one sentence that planning a query proves it compiles against the schema, not that it succeeds when run (an insert omitting a NOT NULL column plans cleanly); fold this into the existing `NOTE:` rather than adding a second one.

### Guide changes

Intro ("What the examples are"): add `sql query <name>` to the marker list ("every statement is planned, not run, against the `sql schema <name>` block; tables are named unqualified"), mention the optional name on `sql schema`, and add one sentence that Sereus puts the app's tables in schema `App`, so app code qualifies them (`App.messages`) as the reference apps do (`packages/reference-app-web/src/lib/chat-dml.ts`). Keep `sql fragment`'s description accurate once fewer blocks use it (a lone constraint line).

Block by block (heading → change):

- **Putting It All Together**: `sql schema chat`. Add `tags text null` to `messages` with a short comment (JSON array of tag strings) — the TVF example needs a JSON column and this is the guide's realistic table.
- **Global Assertions**: `sql schema ledger`.
- **Ordering Events**, first schema (`events` with `now_iso`): `sql schema event-clock`; the `insert … with context now_iso = datetime('now')` fence → `sql query event-clock`.
- **Ordering Events**, Pattern B schema (`Message`, `MessageParent`): `sql schema message-graph`; the Pattern A `select` fence → `sql query message-graph`.
- **Integrity** lone constraint lines: stay `sql fragment` (not statements; the same lines run in the "Id immutability" schema at the end).
- **Common Table Expressions**: add a small `sql schema org` block before the queries — `table employees (employee_id text primary key, manager_id text null references employees(employee_id), last_seen text);` — and make the query fence `sql query org`. Rewrite: the non-recursive CTE reads `employees.last_seen`; the recursive reporting chain stays as is (it already fits `employees`); the materialization-hint example uses two CTEs over `employees` and a real final select (e.g. managers `as materialized`, staff `as not materialized`, joined), with no `big_table`/`small_table` and no `select ...;`. It does not need `recursive`.
- **Set operations** (same heading): `sql query chat`, rewritten over real columns with a comment each — e.g. `union`: users who started a conversation or posted (`select created_by from conversations union select sender_id from messages`); `intersect`/`except`: users who have / have never posted (`select id from users … select sender_id from messages`); `diff` over the same pair, keeping the "Quereus extension: multiset difference" comment.
- **RETURNING**: `sql query chat`. The insert supplies `sent_at` (NOT NULL by default — as written it would plan but fail when run) and returns `NEW.slug`, so "returning generated values" is true. `body` is correct for `chat`; update and delete unchanged.
- **Table-Valued Functions & JSON Helpers**: `sql query chat`. First example → `from messages m cross join lateral json_each(m.tags) as t`, `t.value as tag`. Replace the `my_table_valued_func(:arg1, :arg2)` placeholder with a parameter-fed built-in, e.g. `select key, value from json_tree(:payload) where type = 'integer';`. Add one sentence after the block: a table-valued function sees a preceding table's columns only through `cross join lateral`; a comma join fails with "<alias>.<column> isn't a column".
- **Additional Coverage → LATERAL with JSON table-valued function**: delete the lead-in line and its fence — after the TVF rewrite it repeats that example.
- **Additional Coverage → Window functions**: `sql query ledger`. Running total rewritten over `ledger(id, kind, amt)` as a signed balance: `sum(case when kind = 'credit' then amt else -amt end) over (order by id rows between unbounded preceding and current row) as running_balance`. Replace the `DigestAll` example with the recursive-CTE hash chain from the probe above (each step `digest(previous, next value)`), with a one-line note that `group_concat` is not available as a window function, so a running digest is a recursive CTE. Rename the lead-in from "Window functions (analytics) and cumulative digests" as fits.

Do not change any other `sql schema` block beyond adding a name.

`docs/testing.md` → "Schema guide examples execute" (line ~377): add the `sql query <name>` marker (planned against the named schema with `App` on the search path; parse errors fail), and replace the last sentence ("The guide's query examples (`sql fragment`) are not checked …") with what `fragment` now covers.

## Edge cases & interactions

- **Unknown schema name, duplicate schema name, `query` without a name, name on `script`/`fragment`** — each fails with a message naming the block. Verified by inspection of the grammar code plus one manual run with a deliberately broken fence (revert after); no permanent test — the per-block loop is the contract.
- **Forward reference** (Pattern A query above the Pattern B schema; set ops, RETURNING and TVF above `chat`) — lookup is by name over all blocks, not order. Verified by those blocks passing.
- **Placeholder or parse error inside a query block** — `parseAll` throws and the test fails; that is the intended catch for text like `select ...;`. Verified by the manual broken-fence run.
- **Empty query fence** — fails explicitly rather than passing with zero statements. Inspection.
- **Writes in query blocks needing context** — the block supplies `with context` itself (the `event-clock` insert does); planning an insert into a context-declaring table without it should fail. Do not auto-supply context for query blocks.
- **Plan, not run** — a query that would fail at run time (NOT NULL omission, a CHECK refusing the row, a foreign key) still passes. Covered by the header `NOTE:`; fix the one known instance (RETURNING insert missing `sent_at`) by hand.
- **Named parameters** (`:who`, `:payload`) — planned unbound; the probe confirmed this works. Inspection.
- **Built-in table-valued functions with `App`-only search path** — `json_each`/`json_tree` resolved in the probe with the path set to `App` only. Keep the path `['App']` so a guide table name can never resolve against `main`.
- **Test titles** — heading-based `#n` numbering shifts when the CTE section gains a schema block; titles only, nothing keys on them.
- **Other open work on the guide** — `tickets/backlog/feat-shared-causal-history-for-sapps.md` edits "Ordering Events" and must keep the `message-graph` / `event-clock` names; the grammar test enforces that. The Seeds caution and `tickets/blocked/decide-sapp-schema-seed-rows.md` are unaffected.
- **Sibling repos** — `../quereus` and `../optimystic` are read-only; everything here is this repo's test and docs. If the stale-build guard reports a sibling `dist` stale, stop and record it rather than building.
