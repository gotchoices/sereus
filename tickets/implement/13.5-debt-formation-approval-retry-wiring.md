# Wire the approval retry up through the join handler, comments, and docs

Split out of `debt-formation-approval-retry-lost-race`, which does the `ControlDatabase`
work. That ticket makes a redemption that loses a use-number race retry the SAME approver
sign-off under a fresh use number, and adds an exported `InvitationExhaustedError` for the
case where no seat remains. Read its "What is wrong today" and "Shape of the fix" sections
for the background — this ticket does not repeat them.

Everything here is downstream of that change: nothing in this ticket alters behaviour on
the success path, but three places now describe the system inaccurately, and one place
gives a joiner advice that is now provably wrong.

## What needs to change

### The joiner is told the wrong thing when the invitation really is used up

`StrandFormationManager.provisionAsResponder`'s catch-all (`strand-formation-manager.ts`,
~line 335-355) answers `Formation conflict, retry` for anything it does not recognise. An
`InvitationExhaustedError` reaching it means the invite has no seat left — retrying can
never succeed. Add one branch mapping it to `{ approved: false, reason: 'Invalid token' }`,
with the token, attempted use number, and limit in the local `log` line.

Deliberately reuse the existing wording rather than minting `'Invitation fully redeemed'`:
`strand-formation-protocol.ts` already answers `'Invalid token'` when the up-front
`validateToken` finds the invite used up, and a joiner that arrives a moment later gets
exactly that — so the race-loser sees the same string as the non-racing case, and no new
distinction between "invalid" and "exhausted" is exposed on the wire. Operator signal
lives in the log.

The same catch block carries a `NOTE:` (~lines 345-352) explaining that an approval
obtained before landing there is DISCARDED because this path does not retry, and pointing
at `tickets/backlog/debt-formation-approval-retry-lost-race.md`. That is now false and the
pointed-at ticket is gone. Replace it with a statement of what actually happens: the
approval is retried in the database layer, and reaching this catch means either the retry
was exhausted or the failure was never retryable.

### The recorder's doc comment overstates the failure

`ControlFormationUsageRecorder.provisionAndRecord`'s doc comment
(`control-formation-recorder.ts`, ~lines 267-269) ends with "A concurrent redemption of the
same single-use invite collides on the `(Token, UseNumber)` PK and this call THROWS for the
loser". That is no longer the whole story — the collision is retried first, and the throw
only survives sustained contention or a genuinely exhausted invite. Reword.

### The schema comment credits nothing for resolving the collision

`FormationUsage.Monotonic`'s comment says concurrent redemptions "collide on the
`(Token, UseNumber)` PK" and stops there. Extend it to name `ControlDatabase`'s retry as
what resolves that collision, and note that the deferred check itself is the other surface
the same race can take (a concurrent row the insert's key probe did not see trips
`Monotonic` at commit rather than the PK).

**Both copies, byte-identical.** `schemas/control.qsql` (the constraint is at lines 516-524)
and `CONTROL_SCHEMA` in `packages/cadre-core/src/control-schema.ts` are two hand-maintained
copies of one text, and `control-schema-drift.spec.ts` fails the build on a one-sided edit.
The `Monotonic` comment currently reads, in part: *"…giving sequential 1,2,3... per token
(cross-transaction; concurrent redemptions of the same token collide on the
`(Token, UseNumber)` PK)."*

### Docs

- `docs/architecture.md` — in the `StrandFormationManager` / formation section, state that a
  redemption that loses a use number is retried with the same approval, and that the approval
  hook is asked once per join, not once per attempt.
- `docs/STATUS.md` — the "Control DB local write serialization — covered" section lists
  recovery from a lost race as covered only for the peer-record path. Add the formation
  use-number race and the specs the prereq ticket landed.
