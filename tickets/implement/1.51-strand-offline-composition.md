## Background: what upstream gives

Optimystic 1.20.0's Quereus plugin has an opt-in offline mode (README section "Offline mode", design in `../optimystic/docs/offline-sync.md`). With the `offline` register option, `plugin.offline.enter()` makes each later transaction's commit resolve once it is queued (and saved in the `journal` store, if one is given); the plugin sends queued transactions in order once the block's cohort is reachable, and `plugin.hydrate(db)` puts saved ones back in the queue after a restart. A table tagged `"optimystic.offline" = 'network'` is always network-acknowledged. A statement that changes how a table's rows are stored is refused with `QueuedEntriesBlockSchemaChangeError` while queued transactions wrote that table.

## Decisions

**Opt-in per connection.** `StrandConnectionOptions.offline?: StrandOfflineOptions`, where `StrandOfflineOptions` is upstream's `OfflineConfig` without `journalLabel` (import the type from `@optimystic/quereus-plugin-optimystic/plugin`). Absent means today's behaviour exactly: no `offline` key in the register config, and no `offline` on the result. Present: `registerStrandPlugins` passes it into the register config (object-typed, like `rawStorageFactory`), adding `journalLabel` when a `journal` is given.

**Journal label from the strand id.** `strandJournalLabel(strandId)`: upstream's label alphabet is `[a-z0-9_-]` and strand ids are `[a-z0-9._-]` (`assertStrandScopeKey`), so escape `_` as `__` and `.` as `_d`, then prefix `strand-`. Injective, so two strands sharing one store never share a label. Every platform store Sereus ships is per strand anyway (`strand-offline-platform-journals`); the label is the second guard for an embedder that passes one shared store.

**The controller on the result.** `SereusPluginResult.offline?: StrandOfflineController`, present only when `options.offline` was given: a typed `Pick` of upstream's `OfflineMode` with `enter`, `exit`, `isEntered`, `whenDrained`, `onStatus`, `onQueueState`, `queueState`, `entries`, `status`, `discard`, `outcomes`, `acknowledge`. Not the whole class: its other public methods are the plugin's internals. Re-export the status, state and error types an app needs (`QueuedTransactionStatus`, `OfflineModeState`, `OfflineCommitTimeoutError`, `QueuedEntriesBlockSchemaChangeError`, `EntryNotDiscardableError`, `UnknownEntryError`, `QueueDisposedError`, `OfflineJournalError`, `CommitOutlook`) from the package index, as `SqlCommitDurability` is today.

**A lookup by database, for Sereus's own writers.** `offlineControllerOf(db: Database): StrandOfflineController | undefined`, backed by a module-level `WeakMap` that `composeStrand` fills after registration and clears in `shutdown`. `strand-offline-cadre-guards` needs it: the membership writers take a bare `Database` (their exported signatures are public API) and must see whether that database's queue holds transactions. Export it from the index.

**Release disposes the queue first.** `releaseOptimysticPlugin` must `await plugin.offline.dispose()` before `txnBridge.dispose()` (upstream's `dispose` does the same, for the reason in its comment: a submission in flight reports its commit through the bridge's follower). Composition does not call upstream's whole `dispose()` (the existing comment explains why), so without this the drain's timers outlive the strand and keep trying to send through a released factory. Add `offline` to the local `OptimysticPluginResult` shim.

**Sereus's strand tables are always network-acknowledged.** Tag all eight `Strand` tables (`Header`, `Invite`, `ConsumedInvite`, `CancelledInvite`, `Member`, `MemberPeer`, `Manager`, `Revocation`) `with tags ("optimystic.offline" = 'network')`, in `schemas/strand.qsql` and `STRAND_SCHEMA` alike (the drift spec compares them). They are authorization facts: a membership change, an invitation redemption or a revocation must never be acknowledged locally and refused later. Consequences to state in `docs/strands.md`:

- A transaction that writes any `Strand` table is network-acknowledged as a whole, app tables included.
- A live read of a `Strand` table behaves as outside offline mode (it is not served from this machine's view while the cohort is unreachable).
- A network-acknowledged commit made while transactions are queued waits behind them, holding Quereus's execution lock, for up to `networkCommitTimeoutMs` (upstream default 5 minutes); `strand-offline-cadre-guards` keeps Sereus's own writers out of that wait.

The tag is the only schema change, and upstream does not refuse a tag change while transactions are queued, so the first connect after upgrade applies it as `alter table … set tags` on each table (one catalog write each, then nothing on later connects).

**An app schema upgrade waits for the queue, on a published database.** Settled against the alternatives:

- Rejected: waiting in `composeStrand` for `whenDrained()` before returning. Offline, that withholds the strand from the app right after an app update — the moment offline mode exists for.
- Rejected: refusing with a named error. The strand never comes up, and its queue can drain only while the composition is alive, so nothing ever clears.
- Rejected: applying only the storage-neutral parts. Quereus's `apply schema` is one declarative diff; splitting it means a second schema differ.
- Chosen: when step 7's `applyAppSchema` fails with `QueuedEntriesBlockSchemaChangeError` anywhere on its `cause` chain (Quereus rewraps it), `composeStrand` keeps the catalog it has (the hydrated, earlier `App` schema; Quereus unwound the failed apply), returns normally, and retries in the background: await `whenDrained()`, apply again, repeat while the same error comes back. The result carries `appSchema: Promise<AppSchemaOutcome>`, which never rejects: `{ state: 'applied' }` immediately when the apply succeeded the first time, `{ state: 'applied', deferred: true }` when a retry landed, `{ state: 'failed', error }` when a retry failed for another reason, and `{ state: 'cancelled' }` when `shutdown` ran first (`whenDrained` rejects with `QueueDisposedError` on dispose). Also `appSchemaDeferredBy?: readonly string[]`, the queued transaction ids the first refusal named.

Put the retry in a small exported function (`applyAppSchemaAfterQueue(db, schema, controller)` or similar) so it is testable without a network. Any other apply error still fails the composition as today. `StrandDatabase.attachAppSchema` (a replica claimed by an app) keeps throwing: a replica writes no app transactions, so only a network-acknowledged commit waiting behind the queue could refuse it. Leave a `NOTE:` there.

**The browser connect defaults the journal.** In `connectToStrandBrowser`, when `options.offline` is given without a `journal` and the storage was defaulted to IndexedDB, open an `IndexedDBKVStore` over the same database handle (`openOptimysticWebDb('sereus-strand-<id>')`; it has the `kv` object store) and pass it. The Node connect passes what it is given: without a `journal` the queue is memory-only, which upstream permits. cadre-core never configures that (`strand-offline-cadre-core`).

**No SQL-config path.** `parse-config.ts` stays as it is. A journal is an object, the plugin loader's config is `SqlValue`s, and unknown keys are already refused, so offline mode is programmatic only. Say so in the doc.

**`networkCommitTimeoutMs` keeps upstream's default.** Nothing was measured to choose another. Leave a `NOTE:` tripwire at the registration site: if a network-acknowledged commit stuck behind an offline queue ever shows up as a frozen app, lower it for strands.

## Edge cases & interactions

- **Restart with a non-empty journal.** `hydrate` (step 5) restores before the `Strand` and `App` applies and before `composeStrand` returns, so the first statement any caller runs sees the restored rows. Verified by inspection of the step order. The integration scenario in `strand-offline-mode` exercises it end to end.
- **`OfflineJournalError` from `hydrate`** (a record written by a newer build, after a downgrade): composition fails and releases as for any hydrate failure. Nothing is dropped, and upgrading again restores. Inspection.
- **The `Strand` apply is not deferred.** Its only change is the tag. Every `Strand` write is network-acknowledged, so the only queued entries on those tables are network commits waiting behind app transactions. Leave a `NOTE:` at the `Strand` apply: if a later strand schema changes row storage, that apply can be refused the same way.
- **A failed apply that dropped a column first** can leave the schema partly migrated (Quereus cannot undo a `DROP COLUMN`; see the existing `NOTE:` at step 7). The retry diffs from that state and continues. The spec below uses an added index only. Inspection.
- **Shutdown during the background retry:** `whenDrained` rejects with `QueueDisposedError`. Map it to `{ state: 'cancelled' }`, with no unhandled rejection and nothing logged above debug. Covered by the outcome type.
- **Two strands in one process sharing a journal store:** different labels by construction. Inspection.
- **`releaseOptimysticPlugin` on a failed composition** (the catch at step 7): it must dispose the queue too, since `hydrate` may have restored entries before the failure. Inspection.
- **Mixed versions** (a 1.19 member receiving a queued send): the send is an ordinary pend/commit, and `refuseSoloCommit` is local to the sender. Nothing to build here. The adoption ticket's notes cover it.

## Tests

One spec, in `packages/quereus-plugin-sereus/test/`, for the deferral, the one branch Sereus owns here. Register the Optimystic plugin directly (not through `composeStrand`) on the `local` transactor with `offline: {}`. Hold the queue closed by registering a closed `ICohortReachability` for the transactor (`collectionFactory.registerCohortReachability('<transactor>:<keyNetwork>', gate)`; read upstream `reachability.ts` for the interface and how to wake it). Apply an `App` schema with a table, `enter()`, insert a row, then call the retry function with an upgraded schema that adds an index on that table. Expect:

- The first apply refuses and the function reports deferred with that transaction's id. The table has no index, and its row reads back.
- After the gate opens and the queue drains, the outcome resolves `{ state: 'applied', deferred: true }` and the index exists.

No test for the config pass-through, the label escape, the tags or the release order. They are wiring, and the drift spec already pins the schema text.
