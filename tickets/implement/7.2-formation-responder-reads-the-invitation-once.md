# The formation responder reads the invitation once

Split from `plan/formation-and-redemption-read-each-row-once` (the responder arm). Siblings: `implement/cadre-invite-and-grant-redemption-read-the-row-once`, `implement/joiner-hands-its-join-to-the-launch`.

## What runs today (traced)

At responder A, during one bound (closed host strand) formation, `message-cost-accounting`'s baseline counts `queryFormationInvite` 5 times and `countFormationUsage` 4 times. Where they come from:

| step | `FormationInvite` | use count | `Strand` |
|---|---|---|---|
| connection gate, `StrandSolicitationService.hasOutstandingInvitation` → `isTokenUsed` (minted token) | 1 | 1 | |
| `StrandFormationManager.validateToken` → `isTokenValid` | 1 | | |
| `validateToken` → `isTokenUsed` | 1 | 1 | |
| `resolveStrand` | 1 | | 1 (`queryStrand`) |
| `authorizeUsage` (+ `assertSeatFree`) | 1 | 1 | |
| `issueStrandMembershipInvite` (cadre-node) | | | 1 (`queryStrand`) |
| `recordFormationUsage`: stamp read, then `assertSeatRemains` in the write lock (budget passed in, so no invite read) | | 1 | 1 (`queryStrandStampId`) |

The unbound path additionally re-reads the invite through `resolveInviteSAppId` → `isTokenValid`, then again in `provisionAndRecord`.

## Design

**One read per session, carried as a value.** The recorder gets one read method that returns everything later steps need, and every later step takes that value instead of a token.

New module `packages/cadre-core/src/formation-token.ts` (types plus one pure function, imported by both the protocol layer and the recorder layer, so `strand-formation-protocol.ts` does not import upward from `strand-solicitation.ts`):

```ts
/** The `FormationInvite` columns a formation session acts on. */
export interface FormationInviteFacts {
  sAppId: string;
  expiresAtMs: number | null;   // null: never expires
  totalUses: number | null;     // null: unlimited
  strandId: string | null;      // null: unbound (responder-provisions)
  validationUrl: string | null; // null: no outside approval
}

/** One formation token as read once at the start of a session. Later steps take this instead of reading again. */
export interface FormationTokenRead {
  token: string;
  invite: FormationInviteFacts | null;  // null: no row here (may not have replicated)
  usesRecorded: number | null;          // counted only for a metered, unexpired invite; else null
}

/** `token-unknown` / `token-spent` / valid, from a read and the clock; the same rules `isTokenValid`/`isTokenUsed` apply today. */
export function classifyTokenRead(read: FormationTokenRead, nowMs: number): FormationTokenCheck;
/** Used up: a metered invite whose recorded uses reached `totalUses`. An unknown token is not used up. */
export function isTokenReadSpent(read: FormationTokenRead): boolean;
```

`FormationTokenCheck` moves into this module too (re-exported from `strand-formation-protocol.ts` if that keeps imports simple), and its valid arm carries the read: `{ valid: true; read?: FormationTokenRead }`. `read` is optional only because a manager with no recorder accepts every token with nothing read.

**`FormationUsageRecorder` after the change:**

- `readToken(token): Promise<FormationTokenRead>`: one `queryFormationInvite`, then one `countFormationUsage` only when the invite is metered and unexpired. Replaces `isTokenValid` and `isTokenUsed`, which are removed.
- `resolveStrand?(read): Promise<ResolvedHostStrand>`: no invite read. One strand read that also selects `StampId` (a new `ControlDatabase` method or a variant of `queryStrand` returning the row with its stamp; `STRAND_COLUMNS` has no `StampId` today). The `bound` arm grows `strandType: 'o' | 'c'` and `strandStampId: string`.
- `authorizeUsage?(params, read, host)` and `provisionAndRecord?(params, read)`: take the invite's `validationUrl` and `totalUses` from `read`. `authorizeUsage` passes `host.strandStampId` to `recordFormationUsage`.
- `recordUsage(params)` (used only by `recordFormationComplete`, test mocks) keeps reading for itself.
- `hasOutstandingInvitation?()` unchanged.

**Manager and listener.** `FormationListenerOptions.provisionStrand(contact, signal, read?)`: `runSession` passes the valid check's `read` through. `validateToken` calls `readToken` once and `classifyTokenRead`. `provisionAsResponder` passes the read to `resolveStrand`, `authorizeUsage`, `provisionAndRecord`; `resolveInviteSAppId` reads `read.invite?.sAppId` instead of calling the recorder again.

**The issuer seam takes the resolved strand.** `StrandFormationManagerOptions.issueMembershipInvite(host, signal)`, where `host` is the `bound` resolution (`strandId`, `strandType`, `memberPrivateKey`). `CadreNode.issueStrandMembershipInvite` drops its own `queryStrand`; it still reads `StrandPartyKey` (a different row). Its "Strand row is gone → reject" guard goes away with the read; the `FormationUsage.StrandExists` CHECK still refuses a consent row against a strand removed in between (see edge cases).

**`recordFormationUsage(params)` gains `strandStampId?: string`.** When given, the stamp read is skipped; when absent (the `recordUsage` path), it reads as today. The stamp is immutable for the life of a `Strand` row, so a stamp read earlier is the stamp the CHECK compares, unless the row was removed and re-inserted in between, which the CHECK refuses.

**The use count: one early, one decisive.** The early count in `readToken` refuses a spent token before anything costly (the outside approval call, the strand-database write that issues the membership invite). The count inside the write lock (`assertSeatRemains`) decides. `assertSeatFree`'s count after the approval stays, but only when an approval was actually obtained (`validationUrl !== null`), since only then has time passed in which a same-node rival could take the last seat; update its doc and the NOTE there.

**The connection gate keeps its own read.** `hasOutstandingInvitation` runs when a stranger's connection is being admitted, before any stream or token exists, under the gate's 2 s fail-open deadline; the session's read happens later on a different call. It switches from `isTokenUsed` to `readToken` + `isTokenReadSpent` (same answer: an unknown token stays outstanding). Leave a `NOTE:` there saying why it does not share the session's read.

**Expected reads after**, bound path, no approval hook: `FormationInvite` 2 (gate 1, session 1), use count 3 (gate 1, early 1, in-lock 1), `Strand` 1. With an approval hook, one more count. Unbound path: `FormationInvite` 2, no `Strand` read before the insert.

## Edge cases & interactions

- **Two redemptions racing for the last use of a one-use invitation.** The in-lock count still decides; the loser gets `InvitationExhaustedError` → `token-spent`, the same code a latecomer gets from the early check. Verified by the existing `control-formation-seat-budget.spec.ts` and the integration scenario `strand-formation-concurrent-redemption` (run if the stale-build guard allows).
- **Invite withdrawn (deleted) or expired between the early read and the write.** The `FormationUsage.Authorized` CHECK refuses at commit; the carried read must never be used to skip or pre-satisfy it. The NOTE in `authorizeUsage` about a missing invite reading as "no approval required" still applies to `read.invite === null`; keep it. Verify by inspection.
- **Host strand removed between resolution and issue/record.** Without the issuer's re-read, a membership invite can be issued into a strand being removed, and the consent write then fails the `StrandExists` CHECK → `conflict` rejection, invite orphaned until its expiry (`MEMBERSHIP_INVITE_TTL_MS`). The same orphan window already exists for a record failure (comment in `provisionAsResponder`); extend that comment rather than adding a re-read. Verify by inspection.
- **Closed vs open host strand.** The issuer now decides open (`null` invite) from `host.strandType`; an open strand must still get no invitation. Covered by `strand-formation-membership-invite.spec.ts`.
- **Manager with no recorder.** `validateToken` returns `{ valid: true }` with no read, and `provisionStrand` gets `undefined`; the unbound placeholder/provisioner paths must not need a read. Covered by the mock-transport specs.
- **Expiry boundary.** `classifyTokenRead` keeps `expiresAtMs <= now` as expired (identical to today's `isTokenValid` and to `hasOutstandingFormationInvite`). Pin nothing new; the existing recorder spec covers it once rewritten.
- **Abort.** `signal` checks stay where they are (before approval, after approval, inside the lock). The read is taken before the first check, so an aborted session has read once and written nothing.

## Tests

No new tests. The specs listed in `files:` that build `FormationUsageRecorder` fakes are rewritten to the new interface: replace `isTokenValid` / `isTokenUsed` with `readToken` (most fakes can build the read from an in-memory map) and adapt `issueMembershipInvite` fakes to take the resolved host. `control-formation-recorder.spec.ts` tests the real recorder: rewrite its `isTokenValid`/`isTokenUsed` cases against `readToken` + `classifyTokenRead`, keeping one case per outcome (unknown, expired, spent, valid) rather than adding new ones. `control-founding-consult-budget.spec.ts` does not run a formation; if its figures move anyway, re-pin and say why.

One existing case pins the count this design drops: `control-formation-seat-budget.spec.ts` → "refuses a spent seat at authorization, before the manager could issue anything" (~360) calls `authorizeUsage` on a spent invite with **no** `ValidationUrl` and expects `InvitationExhaustedError`. Once `assertSeatFree` runs only after an obtained approval, that call passes and the case fails. Its own comment says what it means to pin ("a seat taken while this redemption waited on its approval"), so re-point it, don't delete it: give the invite a `ValidationUrl`, and have the fake approver record the rival's usage before it returns its approval. The spec already has an approving fake for "lands both uses of a two-use invite". Without a `ValidationUrl`, a spent token is now refused by the early count in `readToken`, and that is covered by the recorder spec's spent case.
