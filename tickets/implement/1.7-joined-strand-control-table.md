# `CadreControl.JoinedStrand`: the party-wide record of strands joined from other parties

## Why

A strand (a shared app workspace) that a party joins from another party has no row in the joiner's control database: its `Strand` row lives in the founding party's control database. Today the joining machine remembers the join only in its own `KeyStore` (`joined-strand-store.ts`, one slot per join, not replicated). So the party's other machines never learn of it, and an always-on machine that hosts storage replicas of the party's strands (`hostUnclaimedStrands`, landed in `always-on-node-hosts-unclaimed-strands`) never hosts it. The next ticket (`party-wide-joined-strands`) makes nodes publish and read joins party-wide; this ticket gives it the table.

This applies to both ways a join happens: `CadreNode.formStrand` (formation with another party) and `CadreNode.addStrand` of a row handed over directly. Neither writes a control row for the strand today. The original plan ticket said formation does; it does not (`formStrand` → `rememberFormedStrand` writes only the local store).

## Decision: a new table, not a row in `Strand`

Considered and rejected: seating the foreign row in `CadreControl.Strand` with a provenance marker. `Strand` means "this party's own strand" everywhere it is read:

- founder derivation (`FounderOwnerKey`, `isSelfFoundedRow`), which the owner-signed insert branch pins to the signer;
- formation: `FormationInvite.StrandId` binds a host strand, and `FormationUsage.StrandExists` checks it, so a joined row there would let this party issue invitations to another party's strand;
- `unpublishStrand` / `deleteStrand` (which also deletes a `StrandPartyKey`);
- the `JoinedStrandRows` rule that a control `Strand` row supersedes a remembered join;
- the heavily reviewed `Strand.AuthorizedInsert` digest and consent branch.

Every one of those would need a provenance check. A separate table keeps the meaning of `Strand` unchanged and needs no new branch in any existing rule.

## Schema

Add after `StrandPartyKey` in `schemas/control.qsql`, mirrored byte-for-byte in `control-schema.ts` (`control-schema-drift.spec.ts` enforces this):

```sql
-- A strand THIS party joined from ANOTHER party: the founding party's control database holds
-- its Strand row, so without this table only the machine that joined would know of it.
-- Every machine of the party reads it (the strand watcher offers each row like a Strand row),
-- so a replica host keeps a copy and the party's other machines can attach. MemberPrivateKey
-- is the closed strand's shared read secret the formation delivered — replicated in plaintext
-- to every machine the party owns, under the same accepted risk as Strand.MemberPrivateKey
-- (docs/strands.md → "Closed-Strand Member Key Handling"). Unlike that column it is NOT stored
-- nowhere else: the founding party and every member hold it, so this row is recoverable by
-- re-forming, which is why it (unlike Strand) carries a REAP branch.
table JoinedStrand (
    Id text primary key,
    Type text not null,              -- 'o' | 'c', as Strand.Type
    MemberPrivateKey text null,      -- closed strand's shared read secret; null for open
    StampId text not null unique,
    constraint NotRevoked check on insert (not exists (select 1 from Revocation R where R.TableName = 'JoinedStrand' and R.StampId = new.StampId)),
    constraint RevocationRecorded check on delete (exists (select 1 from Revocation R where R.TableName = 'JoinedStrand' and R.StampId = old.StampId and R.RowKey = old.Id)),
    constraint NoUpdate check on update (false),
    constraint KnownType check (new.Type = 'o' or new.Type = 'c'),
    constraint MemberKeyClosedOnly check (new.MemberPrivateKey is null or new.Type = 'c'),
    constraint AuthorizedInsert check on insert (
        exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(digest('CadreControl.JoinedStrand', 'add', new.Id, new.Type, coalesce(new.MemberPrivateKey, ''), new.StampId), context.Signature, A.Key, 'ed25519'))
    ),
    constraint AuthorizedDelete check on delete (
        exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(digest('CadreControl.JoinedStrand', 'remove', old.Id, old.StampId), context.Signature, A.Key, 'ed25519'))
            or exists (select 1 from committed.Revocation R where R.TableName = 'JoinedStrand' and R.RowKey = old.Id and R.StampId = old.StampId)
    )
) with context (OwnerKey text, Signature text);
```

Write the comments in the house style of the neighbouring tables: each constraint gets a one-line reason, and a longer reason goes on the constraint it belongs to, pointing to where the full reason already lives (for example "same rationale as `StrandPartyKey.NotRevoked`"). Don't restate them. Keep the lowercase SQL keywords.

- Owner-signed insert, like every other table. **Rejected: letting any enrolled machine (a `CadrePeer`) self-sign a join.** That would let a non-owner machine make every always-on machine of the party download an arbitrary strand. Consequence: a machine that is not an owner cannot publish a join, and its joins stay machine-local, as they are today. A non-owner also cannot join a closed strand by formation today, because `ensureStrandPartyKey` is owner-signed, so this adds no new limit for closed strands.
- The `KnownType` check is new compared with `Strand`. It is included because the reader casts `Type` to `'o' | 'c'`. If quereus rejects the `or` form in a table check, use whatever form `Strand.MemberKeyClosedOnly` proves works.
- There is no `unique` on `MemberPrivateKey`, unlike `Strand`. Nothing reads by it.
- `Revocation`: add `'JoinedStrand'` to the `TableName` and `RowKey` column comments. Add a `RowIsGone` branch: `or (new.TableName = 'JoinedStrand' and not exists (select 1 from JoinedStrand J where J.StampId = new.StampId))`.

  - `queryJoinedStrands(): Promise<StrandRow[]>`. Every row, as `StrandRow` with `FounderOwnerKey: null` (a joiner never founds). It reads raw, like `queryStrands`, with no retired-stamp filter.
  - `queryJoinedStrand(strandId): Promise<StrandRow | null>`.
  - `insertJoinedStrand(row: { Id; Type; MemberPrivateKey }, ownerKey, signMessage)`. It mints a stamp with `generateStampId`, signs `buildAuthorizationMessage('CadreControl.JoinedStrand', 'add', [Id, Type, MemberPrivateKey ?? '', stampId])`, and uses `execWrite`. Pin the field order with a comment, as `insertStrandPartyKey` does.
  - `deleteJoinedStrand(strandId, ownerKey, signMessage): Promise<boolean>`, which is `lockedWithRetry(() => this.deleteGuardedRow('JoinedStrand', …))`, like `deleteStrandPartyKey`.
  - Add an idempotency classifier for a second insert of an already-seated id, like `isStrandIdConflict` (`/UNIQUE constraint failed: JoinedStrand\.Id\b/i`), so the next ticket can treat "a sibling already published this join" as success. Put it next to `isStrandIdConflict`. If the two regexes differ only in the table name, generalize the one helper instead of copying it.

## Tests

A new `packages/cadre-core/test/control-joined-strand.spec.ts`, modelled on `control-strand-party-key.spec.ts` and reusing its raw-database helpers. Keep it to the cases that pin this table's own rules:

- `insertJoinedStrand` lands, and `queryJoinedStrands` / `queryJoinedStrand` read it back as a `StrandRow` with `FounderOwnerKey: null`.
- An unsigned insert is refused (`AuthorizedInsert`).
- An approval is bound to the key material: a valid signature cannot seat a different `MemberPrivateKey`.
- An update is refused (`NoUpdate`).
- `deleteJoinedStrand` retires the stamp, and the original insert approval cannot re-seat the row (`NotRevoked`). A bare signed delete with no tombstone is refused (`RevocationRecorded`).

The reap branch: if `control-revocation-reap.spec.ts` or `control-revocation-replay.spec.ts` is driven by a table list (`REAPABLE_TABLES`, the RowIsGone branch cases), extend that list rather than adding a case. If it is not, add one reap case to the new spec: a committed tombstone lets an unsigned delete of the stale row through.

## Edge cases & interactions

- **Warm start over a control database created before this table existed.** Check how `StrandPartyKey` joined a live schema, and confirm that a warm start's catalog hydrate adds the new table and does not fail because of it. The policy is "no backwards compat yet", so a party created on an older build does not need migrating. But the warm-start spec (`control-database-solo-warm-start.spec.ts`) must stay green, and if an old store fails to start, record that in the handoff rather than working around it. Verify by running that spec.
- **Mixed builds in one party.** A machine on an older build receives `JoinedStrand` blocks for a table it does not declare. This is out of scope under "no backwards compat". Say so in the handoff and do not engineer for it.
- **Never-written block.** For most parties this table stays empty, and the next ticket reads it on every strand-watcher poll (every 5 s). A read of a block no machine holds consults the cohort (see the `Revocation` ledger-marker comment), and on an isolated machine it fails `cohort-unreachable`. This ticket adds no reader. The next ticket's rows view owns that failure. Nothing to do here beyond not filing a marker row.
- **Concurrent first writes to the new table from two machines** can fork its collection. This is the same class as every other control table (`tickets/blocked/forked-control-collection-sync-livelocks.md`). Nothing new to do, and the next ticket publishes only while connected.
- **Tombstone for a row that is the party's own `Strand` too.** The tables are independent, and a `RowKey` in `Revocation` is scoped by `TableName`, so a `JoinedStrand` tombstone never closes the `Strand` consent branch (which filters `R.TableName = 'Strand'`). Verify by inspection.
