# Two-node convergence for party-wide strand removal

## The claim being proven

`docs/architecture.md:566` and the `unpublishStrand` doc comment
(`packages/cadre-core/src/cadre-node.ts:3003-3049`) both promise: *every node of the party
stops its instance once its watcher observes the missing row*. Repo-wide, nothing tests it
across two nodes. Every existing assertion lives on the node that issued the removal.

There is a second, sharper gap underneath it: **no scenario anywhere proves that a control-plane
DELETE becomes visible to a sibling reader at all.** `control-db-two-node-convergence.integration.ts`
proves an INSERT converges (A writes a `CadrePeer` row, B observes it by pull-on-read).
`control-write-degraded-cohort-member.integration.ts` exercises `removePeer` but only ever reads
the result back on the *writer* (`A.isMember(...)`). So this scenario is the first read-back of a
deletion from the other side.

## Recipe

Model on `control-db-two-node-convergence.integration.ts` — same harness, same connect-before-write
discipline. New file:
`packages/integration-tests/src/scenarios/strand-unpublish-sibling-convergence.integration.ts`.

**Harness change first.** `controlNodeConfig` (`harness/node-fixtures.ts`) hardcodes the strand
watch cadence at the `CadreNode` default of 5 s. Add an optional `strandWatchMs` to
`ControlNodeOpts` mapping to `CadreNodeConfig.strandWatchInterval`, and an optional options
argument to `bootPair` that applies it to **both** nodes. Purely additive; the three existing
`bootPair` callers stay unchanged. Note that `plan/10-integration-test-harness-helper-consolidation-remaining-files`
is also in flight on this file — it folds scenario-local copies *into* the harness, so an added
field does not collide, but read it before editing.

**Phase 0 — bring-up.** `bootPair('unpublish', 'ctrl', { strandWatchMs: 1_000 })` gives A (owner,
storage profile) and B (a plain reader that is deliberately **not** its own owner, so every row it
sees must have arrived over the wire). Then `connectControlNodes(B, A)` **before** the publish and
before the removal. Connect-before-write is load-bearing: a delete committed with a cluster of one
is the separate delete-while-alone durability gap (`plan/10-control-delete-while-alone-tombstone`)
and is explicitly out of scope here.

**Phase 1 — B discovers and runs the strand.** `A.publishStrand(strandId)` (open strand, `'o'`).
B holds no sApp config for it, so B's next watcher poll emits `strand:discovered`
(`cadre-node.ts:2589`). Wait for that event (30 s budget). It is also this scenario's
**anti-vacuity anchor**: B never wrote the row and is not an owner, so observing it at all proves
a genuine network read. Then, from the test body (not inside the event handler), take the
`StrandRow` off the event payload and:

```ts
await B.addStrand({ strandRow, sAppConfig: createSignedSAppConfig(SCHEMA, '1.0.0'), mode: 'bootstrap' });
```

Pass `mode: 'bootstrap'` explicitly. Left to inference, `selectStrandMode` would pick `'networked'`
(A is a `CadrePeer` sibling) and B would resolve an empty strand-network seed, since A runs no
strand instance — a slower, flakier path that proves nothing extra. The subject here is the
**control-plane** watcher, not strand-data replication. Assert `B.getStrand(strandId)` is defined.

**Phase 2 — the removal.** `A.unpublishStrand(strandId)`. Sanity-check A's own view is empty
(cheap; already unit-covered).

**Phase 3 — the headline.** Wait (30 s budget) for B to emit `strand:stopped` for that id. Assert
`B.getStrand(strandId)` is `undefined`, `B.getStrands().size === 0`, and B's own
`queryStrands()` no longer lists the id.

**Phase 4 — no re-add.** Quiet window of ~5 poll intervals: no further `strand:stopped`, no
`strand:discovered`, no `strand:started`, no `strand:error` for that id on B. Derive the window
from the configured `strandWatchMs` rather than hardcoding it.

**Phase 5 — a re-publish is rediscovered.** `A.publishStrand(strandId)` again (fresh stamp; the id
is not blacklisted). Wait for a **second** `strand:discovered` on B. This proves B's watcher
cleared the id rather than tombstoning it locally, and that the `Revocation` row the delete left
behind is not read back as a strand.

`try { … } finally { await B?.stop(); await A?.stop(); }`, as every sibling scenario does.

## If Phase 3 does not converge

Diagnose the recipe before concluding a product defect — in order: was the connection established
before the write (both sides), did Phase 1's discovery actually fire (if not, the failure is in
the read path, not the delete), and does the `sereus:cadre:strand-watcher` debug output show polls
completing or throwing (`strand-watcher.ts:179` swallows a throwing read and retries, so a
persistently-erroring read looks exactly like non-convergence).

If it is genuinely the product — a delete that commits on a connected cohort and never becomes
visible to the sibling — that is a real defect and a significant finding. Do **not** weaken the
assertions, loosen the budget past reason, or skip the test. File
`tickets/fix/bug-strand-removal-not-visible-to-sibling` with `repro: verified`, the exact recipe,
and the log excerpt; land the scenario with the unconverged phases under vitest's `it.fails`
(which *asserts* the current broken behaviour and flips red the moment it is fixed — unlike
`skip`, it hides nothing), carrying a `NOTE:` comment naming the fix ticket. Say so plainly in the
review handoff.

## Edge cases & interactions

- **Connect before write, both sides.** `connectControlNodes` already waits for both peers to
  report the connection; a write issued before that is local-only and the scenario would be
  measuring the wrong thing.
- **A must vouch B.** `bootPair` does this (`A.authorizePeer(B)`), and without it B's pull streams
  are refused by A's per-stream control-DB gate — every poll would fail silently and Phase 1 would
  time out looking like a convergence bug.
- **Watcher must hold the row before the removal.** Gate on `strand:discovered`, never a sleep. If
  B's first sighting of the row came *after* the delete, its removal path can never fire.
- **Exactly once.** B's `strand:stopped` must fire once, not once per subsequent poll.
- **Poll cadence vs. budgets.** 1 s polling on B means every poll is a network scan of
  `CadreControl.Strand`; keep the cadence no shorter, and derive every quiet window from it.
- **B's strand instance must shut down cleanly** — assert `getStrands().size === 0`, and make sure
  the `finally` stops B before A so B's last polls are not reading a dead peer.
- **Out of scope, deliberately:** delete-while-alone durability (its own ticket); A running its own
  instance of the strand (A-side convergence is already unit-covered by
  `strand-unpublish.spec.ts` and adding it costs a strand-node boot for no new assertion); closed
  strands and `MemberPrivateKey` destruction; a third node.
- **Filter-excluded siblings** are covered as fast unit tests by
  `implement/19-debt-strand-removal-watcher-stop-unit-tests` — do not stand up a third node here.
- **Windows test filtering.** A path filter did not match for a prior ticket on this suite; use
  `cd packages/integration-tests && yarn vitest run -t "<test name>" 2>&1 | tee` (stream it — never
  a silent redirect, the runner's idle timer will kill the run). The suite's stale-build guard may
  require `yarn workspace @quereus/quereus build` in `../quereus` first.
