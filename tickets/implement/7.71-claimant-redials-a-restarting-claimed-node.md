# The claimant redials the claimed node while it restarts

## Background

`CadreNode.claimNode` (owner A) delivers the claim seed to node B, vouches B (`vouchPeer`, a `CadrePeer` row with a null `Sig`), retains B's QR addresses as a dial target (`retainDialTarget`), and kicks a reconcile pass. B then restarts into A's party (`cadre start`'s `restartIntoClaimedParty`): it stops the placeholder node and brings up a new one, which refuses connections during its control-database bring-up (the connection gate's quiet period).

A phone owner with no listen address and no relay reservation (the common QR claim, `docs/architecture.md` "Which Side Dials" row 6) cannot be dialed, so only A can reconnect. Today (traced from code, not measured):

- the kick pass finds the seed connection still open and dials nothing, or finds it gone and fails against the restarting node;
- the seed connection's close starts a pass (B is in A's authorized set after the vouch; `onControlSiblingConnectionChange`), whose dial fails while B is restarting;
- the failed dial arms the redial ladder's first step, `CONTROL_COHORT_REDIAL_MS` (15 s), so A reconnects up to 15 s after B is back.

A second delay: the QR code lists B's public addresses before its LAN ones, and a home router often drops a connection to its own public address from inside. Each address is dialed in turn on its own limit (21.5 s at the default link), so every later dial from the retained target spends that limit on the public address before it tries the LAN address that carried the claim.

`claimed-node-restarts-without-waiting-on-dials` covers B's side (it restarts at once and dials A when the seed carries A's address). This ticket covers A's side.

## Design

### The address that carried the claim goes first

In `claimNode`, after a successful `deliverSeed`, read the open control connection to B (`controlNode.getConnections(peerIdFromString(target.peerId))`) and, when one of `target.multiaddrs` is its `remoteAddr` (compare with any trailing `/p2p/<B>` removed on both sides), move that address to the front of the list passed to `retainDialTarget`. Otherwise keep the QR order. Every later dial from the retained target, this ticket's and the reconcile pass's, then tries the working address first. `warmSiblingAddrBook` replaces the entry once B's signed record resolves, as today.

### A short redial window after the claim

After the vouch and the retained target, `claimNode` starts (not awaited, `void` with a logged catch) a private `redialClaimedNode(peerId)`:

- Every `CLAIM_RESTART_REDIAL_STEP_MS` (1 s; name it so it does not match the lint rule's `(timeout|budget|deadline)_?ms` pattern, since it is a poll step, not a deadline) for `CONTROL_COHORT_REDIAL_MS` (15 s, reused, not a new literal) measured from the ack:
  - stop if the node is no longer running, or if B's retained target is gone (a `removePeer` raced it);
  - if A holds an open control connection to B, dial nothing this step (it is the old seed connection, or B is back and connected; either way dialing would only return it);
  - otherwise dial B once through `dialBootstrapPeer(peerId, entry.addrs)` (the existing helper: binds addresses to B's peer id, uses `controlDialBudget()`, logs failures, returns whether it connected); stop on success.
- Steps are sequential: a dial in flight finishes on its own budget before the next step, and the window is checked by elapsed time, so a dial that outlasts the window ends the loop.
- A successful dial opens an authorized sibling's connection, which starts a reconcile pass through `onControlSiblingConnectionChange` (backfill, membership refresh, the write-while-alone drain). The loop does nothing else.
- After the window the ordinary ladder carries on (the failed passes above armed it); the loop never touches `reconcileRedialStreak`.

One loop per claimed peer: a second `claimNode` for the same peer (an idempotent repeat) while a loop runs does not start another; keep a `Set<string>` of peers being redialed, cleared in the loop's `finally`. `cleanup()` needs nothing beyond the running check, since each step re-checks `_running`.

### B's own record is not carried in the claim acknowledgement (decided here)

B publishes its signed record after it restarts, on the reconcile pass the arrival of A's rows starts. Carrying a record in the ack was considered and declined, for two reasons:

- it would be signed before B restarts, so its addresses may not match the restarted node (for example, a new relay reservation);
- A's vouch usually commits while A is alone, and the write-while-alone drain re-signs only queued rows whose `Sig` is null (`drainPendingPeerWrites`, `reconstructAuthoredMembership`), so a vouch that carried B's `Sig` would never be re-sent to A's other members.

Record this as an accepted-tradeoff `NOTE:` at the `vouchPeer` call in `claimNode` (what was declined, the two reasons, revisit if the drain ever re-sends signed rows). The wasted re-sign of B's null-`Sig` row on A's first connection to B is the same shape as `backlog/debt-seeded-machine-row-revouched-before-it-publishes`, which now owns the claim path too (noted there in planning).

## Edge cases & interactions

- **The old seed connection is still open at the first steps.** The loop must not count it as success; it only skips dialing while a connection is open. If B never restarts (a cadre-core embedder that does not restart on `claim:accepted`), the connection stays open, the loop dials nothing and ends at the window. By inspection.
- **B's bring-up quiet period refuses the dial.** Each refused or refused-by-port dial fails fast and the next step retries; at most 15 dials, each logged at debug level by `dialBootstrapPeer`. By inspection.
- **A dial to an unreachable first address** takes the per-address limit; the address reorder above makes that rare after a claim. The loop then ends at the window, and the ladder takes over. By inspection.
- **A stops during the window.** Each step re-checks `_running`; an in-flight dial rejects on libp2p stop and `dialBootstrapPeer` returns false. By inspection.
- **B is removed during the window** (`removePeer` forgets the retained target): the loop stops at its next step. By inspection.
- **Concurrent reconcile-pass dials of B.** The loop and a pass may dial B at once; per-address dials to the same peer join (`per-address-dial-joins-another-callers-dial`), so this costs nothing extra. By inspection.
- **A claimant that is dialable** (relay reservation or listen address): B dials A from the carried targets (other ticket) and the loop sees the connection and stops dialing. Either direction is enough.
- **Repeat claim by the same owner** (step 5 of the scenario): the address reorder replaces the entry (still one target); the loop guard prevents a second loop. Step 5 already asserts one row and one dial target.
