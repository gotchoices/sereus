## Design (settled — do not re-open)

1. **`FormationUsage.PeerId` → `PeerKey`**, holding the joiner's base64url 32-byte
   Ed25519 PUBLIC key (not a libp2p peer-id string; SQL cannot unwrap the multihash,
   and storing the key IS the identity — no unverifiable key↔peer-id binding).
   Nothing in the repo selects `FormationUsage.PeerId` back, so the rename costs no
   reader; the peer id stays derivable (identity multihash of these bytes).
2. **The joiner mints the redemption nonce** (`UsageStampId`) and sends it in the
   contact message — no extra round trip; protocol stays 2 messages; timeout ladder
   (hook 10s < responder 12s < initiator 15s < session 30s) untouched. Colliding/reused
   nonce fails the joiner's own insert via `unique` — self-harm only. Responder must
   use the joiner's value verbatim for BOTH the approval request and the insert.
3. **The joiner signs** `digest('CadreControl.FormationUsage', 'consent', new.Token,
   new.UsageStampId, new.PeerKey, new.Disclosure)`. Action tag `'consent'` keeps it
   disjoint from the approver's `'vouch'`. **`StrandId` deliberately NOT in the
   digest** — the joiner doesn't know it at contact time (bound: arrives in result
   frame; unbound: responder mints). Adequate because the responder can't freely pick
   the strand: bound invites are pinned by `Authorized`'s `FI.StrandId = new.StrandId`;
   unbound mints fresh (no victim strand). Record this as a `NOTE:` beside the
   constraint so the missing StrandId doesn't read as an oversight.
4. **Signature stored on the row** (`PeerSig` column, base64url, `not null`) so any
   later reader can re-check it; table is append-only, so it's tamper-proof.
   `context.PeerSignature` is REMOVED from the context list entirely. Both `PeerKey`
   and `PeerSig` `not null` — no unsigned-join mode.
5. **Canonical disclosure bytes on both sides**: joiner and responder both derive the
   disclosure text via `canonicalJson` (canonical-json.ts:12), and that exact string is
   signed by joiner AND approver AND written to `Disclosure`. Canonical form makes the
   responder's parse→re-serialize of the wire object byte-stable.
6. **Hook wire rename `peerId` → `peerKey`** through `FormationApprovalRequest` /
   `FormationVouchFields` / `formationVouchMessage`; POST body renames automatically
   via `vouchFields`. No backwards compat (AGENTS.md). `docs/api.md` update is the
   follow-up ticket's.

```sql

        -- public key and PeerSig is its signature over the 'consent'-tagged digest below.
        -- Unlike the approver's sign-off (context.ValidationSignature, checked against a STORED

        -- strand is responder-minted). The responder cannot substitute a strand anyway: bound
        -- invites are pinned by Authorized's FI.StrandId check, unbound invites mint fresh.
        constraint PeerConsented check on insert (
            verify(digest('CadreControl.FormationUsage', 'consent',
                          new.Token, new.UsageStampId, new.PeerKey, new.Disclosure),
                   new.PeerSig, new.PeerKey, 'ed25519')
        ),
```

## Edge cases to hold (from the settled design)

- Nonce reuse by the joiner → second insert fails `unique` → surfaces as
  `'Formation conflict, retry'` with the invite unspent, not a dropped frame.
- ValidationUrl invite needs BOTH signatures, over the same nonce + same canonical
  disclosure bytes.
- `redeemInvitation` runs its two inserts with deferred CHECKs; `PeerConsented` has
  no subquery so it is NOT deferred — confirm it evaluates correctly inside that
  transaction.
- Concurrent redemptions of one multi-use invite: loser's consent signature must stay
  re-presentable under a new use number (free-nonce property) — do not bar it.
- `FormationAbortedError` / settle-grace paths unchanged; a consent-check rejection is
  an ordinary `approved: false`, never an abort.
- Listener pre-check runs for ALL responder configs (including provisioner-only /
  no-recorder fallbacks) — their tests must send well-formed contacts even though
  those branches write no `FormationUsage` row.
