# Owner grants: the node API, the redemption protocol and the bundle

`owner-grant-tables` added the `OwnerGrant` / `OwnerGrantUsage` tables and the `ControlDatabase` writers. This ticket makes them usable from a `CadreNode`. It is additive: machine invitations keep `grantsOwner` until `machine-invitation-grants-no-ownership`.

## The bundle

An owner grant travels as text, like a machine invitation (`CadreInvitation`, `encodeCadreInvitation` in `docs/architecture.md` → "Enrollment Flow: Invitation Redeemed at Any Member"):

```typescript
interface OwnerGrantBundle {
  v: 1;
  partyId: string;
  grantPrivateKey: string;    // base64url ed25519 seed: the proof of possession
  grant: OwnerGrantRow;       // the owner-signed row exactly as issued
  ownerKeys: string[];        // the issuer's node-local anchor; the redeemer pins them
  members: string[];          // as CadreInvitation.members, cut by selectCadreInvitationMembers
}
```

- Encoded `sereus-owner-grant:1.` + base64url canonical JSON (`encodeOwnerGrant` / `decodeOwnerGrant`, standalone like the invitation codec, so a client without a node can decode one). The same six-address cap keeps it inside one QR code.
- **Cross-refusal by name.** `decodeOwnerGrant` refuses a machine invitation, a join request and both owner-key export forms by name; `decodeCadreInvitation`, `decodeCadreJoinRequest` and `decodeOwnerKeyExport` refuse an owner grant by name. A grant pasted into the wrong field is refused, never sent to a member.
- `ownerKeys` come from the issuer's node-local anchor, never the replicated `OwnerKey` table, for the reason the invitation gives.

## CadreNode API

- `createOwnerGrant({ label?, expiresInMs?: number | null, uses? })` → `{ grant: OwnerGrantBundle, encoded, reach }`. Owner only (the seed-bootstrap service's signer, one `approve`). Default lifetime 15 minutes (`OWNER_INVITATION_DEFAULT_TTL_MS`, renamed if that reads better) and one use; `expiresInMs: null` means no expiry and must be passed explicitly (a backup). `label` follows `addOwner`'s rule (trimmed, at most 64, blank meaning none). `reach` as `createCadreInvitation` computes it.
- `listOwnerGrants()` → statuses (live, withdrawn, expired, redemptions), and `withdrawOwnerGrant(key)` → `boolean`, as the cadre-invitation pair.
- `redeemOwnerGrant(bundle, signer: OwnerSigner, options?: { waitForMember?, signal?, onProgress? })` → `{ ownerKey, alreadyOwner, memberPeerId: string | null }`. `signer` holds the key to seat; its one `approve` call names the party and says the key becomes an owner of it, and signs the `'consent'` digest. The grant's `'redeem'` signature is made with `grantPrivateKey` in memory. Steps:
  1. Refuse a bundle for another party; pin `ownerKeys` into the node-local anchor (`'invite'` provenance, or a new `'grant'` one if the anchor store distinguishes; pick one).
  2. **Local path** when this node is a live member of the party: seat the grant from the bundle when absent (`seatOwnerGrant`, its own transaction), then `ControlDatabase.redeemOwnerGrant`. Refused `alone` under `addOwner`'s rule (`ownerKeyWriteAlone`: no control connection while the party has other members), because an `OwnerKey` row has no re-issue path; the error names the fix (connect, then try again).
  3. **Protocol path** otherwise: dial the bundle's members over `/sereus/owner-grant/1.0.0` (below), one signed request for every address and every pass, as `redeemAtMembers` / `redeemInPasses` do for invitations. Reuse those loops by parameterizing them over the request and reply types rather than copying them.
  - It does not wire the signer: the caller calls `wireOwnKeyIfOwner(signer)` once the row is present locally (at once on the local path; after the control store syncs on the protocol path).
- `joinWithOwnerGrant(bundle, signer, options?)` → the machine-invitation redemption result plus `ownerKey`. For a node started in the grant's party that is not a member (a fresh install recovering with a backup grant; an app joining as an owner):
  1. `redeemOwnerGrant` over the protocol path.
  2. Build a **self-invitation**: a `CadreInvite` row targeted at this node's peer id, one use, short expiry, signed by `signer` (not inserted locally: this node's store holds no `OwnerKey` row yet, so the local insert would be refused), with the grant bundle's `members` (the member that accepted the grant first) and `ownerKeys`. Factor the row-and-bundle signing out of `createCadreInvitation` / `ControlDatabase.insertCadreInvite` so both use it.
  3. `redeemCadreInvitation(selfInvitation, options)`: the member seats the row from the bundle (its issuer, the new key, is a live owner there because that member just wrote it) and admits this node.
  4. `wireOwnKeyIfOwner(signer)` once the `OwnerKey` row has synced, retried up to the genesis bound as the edge node does after an owner-granting join today.
  - One `approve` covers the consent signature and the self-invitation's signature, so a prompting signer asks once.
- `planOwnerKeyRemoval(key)` additionally lists the **live grants that key issued** (`grants`), since removing the issuer makes them unredeemable (`OwnerGrantUsage.Authorized`): an app must be able to say "the backup made with this key stops working". `removeOwner` does not withdraw them (they are dead anyway; a tombstone would add nothing).

## The redemption protocol

`/sereus/owner-grant/1.0.0` (`owner-grant-protocol.ts`), one frame each way over `control-stream.ts`, 64 KiB cap, classed `stranger-open` in `control-protocol-guard.ts`:

```typescript
interface OwnerGrantRedeemRequest {
  v: 1;
  partyId: string;
  grant: OwnerGrantRow;    // from the bundle
  ownerKey: string;        // the key to seat
  usageStampId: string;    // minted by the holder; both signatures cover it
  grantSig: string;        // grant key over the 'redeem' digest
  ownerSig: string;        // ownerKey over the 'consent' digest
}
interface OwnerGrantRedeemReply {
  accepted: boolean;
  code?: OwnerGrantRejectionCode;  // the cadre-invitation codes with grant wording: issuer-unknown,
                                   // grant-invalid, grant-spent, party-mismatch, busy, conflict, internal
  reason?: string;
  partyId?: string;
  grant?: OwnerGrantRow;           // the row as this member holds it
  alreadyOwner?: boolean;
}
```

The member checks in cost order (shape, party, both signatures, then database work). There is **no connecting-identity check**: the holder's peer id has nothing to do with the key it seats, and both signatures already bind the grant, the nonce and the key. Then, as for invitations, it pushes its control store to the holder and counts the holder in its control write cohort until the writes settle (`admitRedeemingDevice`), seats the row from the bundle when absent, and redeems. The push goes only to the holder of a grant live on this member (`isOwnerGrantLive`, on the held row or the bundle's copy once its issuer signature verifies).

- **Why push to a holder that is not a machine.** A member alone with the holder (the issuer's phone offline, the only always-on node answering) could otherwise commit the `OwnerKey` row only to itself, and that row has no re-issue path. Counted in, the holder holds the write too. The accepted tradeoff is the invitation's: a holder whose write then fails keeps a control store; it is someone the owner chose to make an owner.
- **The device verifies the reply** against its pinned keys (party, grant key, row signature), with the same limit `verifyRedeemReply` documents: that catches a wrong-party or wrong-row answer, not a forged member.

## The connection gate

**A live owner grant does not count as expecting a stranger.** A backup grant with no expiry is live indefinitely, and counting it would keep every member admitting every stranger outright for the party's life. The holder rides the provisional admission instead. So that a verified exchange is never cut at the provisional deadline, `admitInboundControlConnection` admits a peer that is in `admittingDevices` (a redemption, of either kind, that has verified and is under way with it). Update the gate's "What it admits outright" paragraph in `docs/architecture.md` to say both.

## Edge cases & interactions

- **Grant for another party**: refused before any network or write. Inspection.
- **Holder already an owner** (its key listed): `alreadyOwner`, no use spent, on both paths. Covered by `owner-grant-tables`' test at the database; the node test checks the reply carries it.
- **Retry after a lost reply**: the same `usageStampId` on every pass, so a member that wrote the row answers `alreadyOwner`. Inspection (it is the invitation loop, parameterized).
- **Member that does not hold the issuer's `OwnerKey` row yet**: `issuer-unknown`, retried at the next address. Inspection.
- **Self-invitation dialed at a member that has not received the new `OwnerKey` row**: `issuer-unknown` (retryable); dial the member that accepted the grant first. Inspection.
- **Issuer removed between mint and redemption**: `grant-spent`. Covered at the database.
- **Holder disconnects mid-exchange**: the push fails or the write completes without a reply; the member releases the cohort count (`admitRedeemingDevice`'s release), and the holder's retry answers `alreadyOwner`. Inspection.
- **Local path while alone**: refused `alone` before the approval. One node test.
- **Backup grant that never expires and the gate**: the gate's answer does not change while it is live. One assertion in the node test (a stranger is admitted provisionally while a no-expiry grant is live).
- **Two bundles in one paste box**: the codecs refuse each other by name. Codec test.
- **`planOwnerKeyRemoval` on an issuer**: lists its live grants; a withdrawn or spent one is not listed. Node test.
- **Protocol classification**: the guard spec fails on an unclassified protocol, so registering it without a class is caught by the existing test.
