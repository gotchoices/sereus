# Phone kit and web app hold an owner key of their own

## Today

- cadre-rn `phone-node/config.ts` `enrollOwner` (~134–205): `node.getIdentityOwnerKey()`, `ensureOwnerKey(pub)`, `initializeSeedBootstrap(priv)` — the phone's identity (`SecureStoreKeyStore`, `DEFAULT_IDENTITY_KEY_ID`, loaded at `node.ts` ~431) is its owner key. `wireJoinedOwnerKey` (~148–166) polls `wireOwnKeyIfOwner()`. `PhoneNode.ownerPublicKey()` (~554–563) returns the identity-derived key.
- reference-app-web `cadre-web.ts` `runOwnerGenesis` (~615–627) and `wireJoinedOwnerKey` (~635–659) do the same over the tab's peer key in IndexedDB; the e2e fixtures `cadre-member.ts` (~77–83) and `formation-responder.ts` (~162–168) copy it.
- `CadreNode.getIdentityOwnerKey()` exists for these callers.

## Design

**Shared flows in cadre-core** (`owner-key-flows.ts`, so the kit, the web app and the CLI do not each write them):

- `addBackupOwnerKey(node, { label, passphrase? }) → { publicKey, exportText }`: generate a key in memory, `node.addOwner(publicKey, { label })`, encode the export, keep nothing. The app shows or saves `exportText` once.
- `importOwnerKeyInto(keyStore, node | null, text, passphrase?) → { publicKey, wired: boolean }`: decode/unlock, `importOwnerKey` into the store's owner slot (refuses a different key already there), and, given a running node, wire it when it is a live owner of that node's party.
- `exportOwnerKey(keyStore, { label?, passphrase? }) → exportText` for the device's own key.

**Phone kit (cadre-rn):**

- The owner key lives in the same `SecureStoreKeyStore` as the identity, in the owner slot (`DEFAULT_OWNER_KEY_ID`), ungated like the identity slot (`AFTER_FIRST_UNLOCK`, no `requireAuthentication`), because background owner writers sign with no user present; biometric gating belongs with prompting signers in `backlog/feat-owner-key-on-a-hardware-key`.
- `origin: 'founded'`: on a party whose `OwnerKey` table is empty, `createOwnerKey` (or load the slot's key if one exists, e.g. imported before founding), genesis-insert it with a label (`PhoneNodeOptions.ownerKeyLabel`, default `"phone"`), `useOwnerSigner`. On a founded party whose table is not empty, load the slot and wire it only when it is a live owner; never create a key then (a new key could not be seated without another owner's signature).
- `origin: 'joined'`: wire the owner slot's signer when its key is a live owner of the party, else `wireOwnKeyIfOwner()` (the identity default, the interim path for an owner-granting invitation); the existing polling loop calls both.
- `PhoneNode.ownerPublicKey()` returns the wired signer's key, or null.
- New pass-throughs on `PhoneNode`: `listOwnerKeys()`, `addBackupOwnerKey(…)`, `exportOwnerKey(…)`, `importOwnerKey(text, passphrase?)`, `planOwnerKeyRemoval(key)`, `removeOwner(key, { revouch })`. They run in the kit's transition queue like the other node calls.
- `PhoneNode.joinCadre`'s `StrandsNeedOwnerJoinError` rule is unchanged: adoption signs with whatever signer is wired in A (the identity default until owner grants exist).
- `reference-app-rn/test-fixture/start.mjs` already uses a random owner key; switch it to `createOwnerKey` over an in-memory store so it uses the shipped path.

**Web app (`reference-app-web/src/lib/cadre-web.ts`):** a `KeyStore` over the node-local IndexedDB (`node-local-slots.ts`) holding the owner slot beside the peer key, then the same founded / joined rules and the same flows. The e2e fixtures use a generated owner key. Exposure is the same as the tab's peer key today (origin-scoped IndexedDB); non-extractable WebCrypto Ed25519 keys were weighed and declined for this pass because an exportable key is what file/QR backup needs.

**Delete `CadreNode.getIdentityOwnerKey()`** and its export; move any remaining cadre-core spec off it (generate an owner key). After this ticket nothing in the repository derives an owner key from a node identity except `wireOwnKeyIfOwner`'s interim default.

## Edge cases & interactions

- Founded party, owner slot empty, `OwnerKey` table not empty (slot lost, store kept): the phone is a member, no key is created, no genesis is attempted. **Test** — the kit's owner-genesis spec gets this arm beside the empty-table arm; it is the guard against a second genesis attempt.
- Joined party where the user imported a backup key that is an owner: the slot key is wired, the identity default is not consulted. Same spec, one arm.
- Joined party admitted by an owner-granting invitation: the identity default wires. Existing joined-party spec.
- One owner key on two devices (imported): both wire it and both sign; concurrent writes conflict like any two owners'. No test; documented.
- `importOwnerKey` while the slot holds another key: refused; the app must say so (one owner key per app in this pass). By the cadre-core store spec.
- `addBackupOwnerKey` while alone with siblings: `addOwner`'s `alone` refusal surfaces unchanged; the app shows it. By inspection.
- A cancelled or failed export/import never touches the identity slot. By inspection (different key id).
- iOS reinstall keeps Keychain items, so the owner slot survives while app data does not: a fresh install then founds with the surviving key (load, not create). By inspection; note it in the reinstall table.
