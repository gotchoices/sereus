# Per-stream authorization for the Optimystic control-DB protocols

The upstream seam has landed and is built. **Nothing has been implemented on the
sereus side yet** — a prior run spent its budget on design verification, and the
findings below are the whole reason this ticket is not a five-line wiring job.
Read "The trap" before writing code.

## What we are wiring

`@optimystic/db-p2p`'s `createLibp2pNode` now takes:

```ts
authorizeInboundStream?: (remotePeerId: string, protocol: string) => Promise<boolean> | boolean;
authorizeInboundStreamTimeoutMs?: number;   // default 5000
```

consulted once per inbound stream on all four database protocols
(`/optimystic/control-<party>/{repo,cluster,sync,block-transfer}/…`), before any
frame is decoded. Fail-closed: only a literal `true` allows; `false`, a throw, a
rejection, a timeout, and an unidentifiable remote all deny and abort the stream.
Absent predicate = previous behavior exactly.

Verified present and compiled in the linked workspace:
`../optimystic/packages/db-p2p/dist/src/inbound-authorization.js`, and
`NodeOptions.authorizeInboundStream` is in the emitted `.d.ts`. `@optimystic/db-p2p`
is a `link:` resolution to that workspace, so no version bump is needed.

Wire it in `CadreNode.createControlNode` **only**. Strand cohort nodes
(`strand-instance-manager.ts`) are cross-party and must NOT get it — their peers are
members of other parties and would all be denied.

## The trap: the predicate must be a pure in-memory lookup

The obvious implementation — `(remotePeerId) => this.isAuthorizedMember(remotePeerId)`
— is **wrong**, and wrong in a way that only shows up under load or on a small cadre.

`isAuthorizedMember` → `listAuthorizedMembers` → `controlDatabase.queryCadrePeers()`
+ `queryRevokedStamps()`. The control tables are network-backed (default vtab routed
to the optimystic network transactor — see the header of
`control-db-two-node-convergence.integration.ts`). So those reads **pull blocks over
the very four protocols this predicate is gating.**

That closes a circular wait:

```
 peer P opens an inbound repo stream to us
   → our predicate runs a control-DB read
     → that read needs a block held by P
       → we dial P's repo protocol
         → P's predicate runs a control-DB read
           → that read needs a block held by us
             → P dials our repo protocol
               → our gate runs our predicate again … 
```

Nothing here resolves. The upstream 5s deadline eventually fires, and because the
seam is fail-**closed**, the timeout DENIES — so the cascade ends in mutual denial,
not mutual admission. The existing connection gater does the same DB read and
survives only because it is deliberately fail-**open** behind a 2s deadline
(`ADMISSION_DECISION_TIMEOUT_MS`); that escape hatch does not exist here.

There is a second, independent reason: amplification. Every peer's periodic
membership read (`reconcileControlCohort` every 15s, `strandWatcher` every 5s) fans
out as inbound streams to every sibling; if each such stream triggers a full
control-DB read here, which itself fans out, the traffic multiplies with cadre size.
Upstream's own doc states the expectation plainly: *"the predicate sits in the hot
path of every inbound stream… Embedders are expected to make it cheap — an in-memory
set lookup — and to memoize anything that would otherwise hit storage or the
network per stream."*

**Therefore:** keep a materialized in-memory `Set<string>` of authorized peer ids on
`CadreNode`, refreshed OUT OF BAND, and have the predicate consult only that set. The
predicate must never `await` anything that can touch the network. With a pure
in-memory predicate, `authorizeInboundStreamTimeoutMs` never trips — leave it at the
default rather than tuning it.

Refresh points to wire (all in `cadre-node.ts`):

- once after `start()` brings the control DB up;
- inside `runReconcileControlCohort` (~L1283) — it already performs the membership
  read every 15s, so the snapshot rides along at no extra cost;
- immediately after every LOCAL membership mutation, so a just-vouched peer is
  admitted without waiting for the timer: `insertSelfPeerRecord` (~L995),
  `removePeer` (~L1644, ~L3016), `reauthorizePeer` (~L1665), `authorizePeer`
  (~L3001), `applySeed` (~L3071), `acceptPhone` (~L3156), `addDrone` (~L3129).

A change that arrives by REPLICATION rather than local write is picked up on the next
timed refresh — bounded staleness, which is acceptable because this gate is defense
in depth: rows an unadmitted peer manages to write are still disbelieved at read time
by the voucher-anchored predicate. Say so in the doc comment.

## The predicate's carve-outs

The stream gate is the STRICT SUBSET of the connection gate
(`admitInboundControlConnection`, ~L811): same "no basis to judge" admissions, minus
the two stranger carve-outs. Concretely, admit when ANY of:

1. the node is not running / has no control database (the predicate exists from
   libp2p bring-up, before the DB does);
2. the node-local trusted-owner anchor is absent or empty — an un-enrolled node has
   no basis to judge anyone;
3. the peer is one of the configured control bootstrap/relay peers
   (`getBootstrapPeerIds`) — operator-configured infrastructure;
4. the materialized authorized set is empty — cold start, before the rows that would
   authorize anyone have replicated in;
5. the peer IS in the materialized authorized set.

Otherwise deny (and log the denial with peer id + protocol; upstream logs its own
line but ours carries the *why*).

**Deliberately NOT carried over from the connection gater:** the enrollment window
(`enrollmentWindowUntil`) and the outstanding-open-invitation exemption. Those exist
so a stranger can reach `/sereus/seed/1.0.0` and `/sereus/formation/1.0.0`; neither
protocol is one of the four gated here, and admitting a stranger to `repo` during an
enrollment window is exactly the hole this ticket closes.

Factor the shared checks so the two gates cannot drift — but keep
`admitInboundControlConnection`'s cheap in-memory checks (window, anchor, bootstrap)
ahead of anything costlier, as it does today.

None of these carve-outs weakens the property being tested: the target scenario has a
non-empty anchor AND a non-empty authorized set, so it lands on the deny path.

## Enrollment ordering — verified, does not deadlock

Checked rather than assumed (the unblock note asked for this):

- `SeedBootstrapService.applySeed` (seed-bootstrap.ts ~L616) writes **no** `CadrePeer`
  rows. It merges multiaddrs into the libp2p peer store and dials owner peers. The
  rows themselves arrive later by replication.
- The invite flow (`createInvite` → `dialInvite` → `acceptPhone`) rides
  `/sereus/seed/1.0.0`, which is not one of the four gated protocols. `acceptPhone`
  calls `authorizePeer` — so the joining peer is authorized on the owner BEFORE it
  has any reason to open a repo stream.
- The joining node's own gate is inert while its anchor is empty (carve-out 2) and
  while its authorized set is empty (carve-out 4), so it can accept the inbound
  replication that fills those in. This is precisely why carve-outs 2 and 4 are not
  optional.

Also checked: `ops/docker/libp2p-infra/src/main.ts` (the `relay` / `bootstrap` /
`bootstrap-relay` roles) registers only identify, ping, circuit-relay and kad-DHT —
it never speaks the four database protocols, so it is unaffected either way. Carve-out
3 is for a party's own storage node listed as a control bootstrap address.

## Test fallout — one existing scenario will break

`packages/integration-tests/src/scenarios/control-db-two-node-convergence.integration.ts`
boots node B as a reader that A **never vouches** (`bootPair` deliberately makes B
"not its own owner", and the test's own comment notes "B here never pins anyone").
B converges by pull-on-read — i.e. by opening streams to A.

Sequence under the new gate: `connectControlNodes(B, A)` runs while A's authorized set
is still empty, so the CONNECTION is admitted (carve-out 4). Then `A.authorizePeer(xPeerId)`
makes A's set non-empty, and from that moment A denies B's inbound repo/sync streams —
B never converges and the test times out.

This is the gate working as designed: B genuinely is not an admitted member of A's
party. Fix the scenario by having A authorize B's peer id in `bootPair` (B still pins
nobody, so the test's real point — `isMember` row presence vs. `isAuthorizedMember`
trust — is preserved). Re-read its header comment and keep it accurate.

Scenarios that construct a real `CadreNode` are the only ones exposed; the rest build
nodes through `packages/integration-tests/src/harness/test-party.ts`, which calls
`createLibp2pNode` directly and passes no predicate. The exposed list:
`control-cohort-auto-convergence`, `control-db-two-node-convergence`,
`control-write-while-alone-convergence`, `convergence-stress`,
`membership-connection-gater`, `multi-party-workflows`, `push-wake-e2e`,
`rbac-signed-write`, `strand-formation-e2e`, `strand-membership-closed-strand-e2e`,
`websocket-chat`, `cadre-host-bootstrap`, `cadre-host-trust-circle`.

Three of these already have known pre-existing failures — see
`tickets/.pre-existing-known.md` (`bug-control-cohort-no-auto-dial`,
`bug-strand-three-party-replication`). Do not chase those.
