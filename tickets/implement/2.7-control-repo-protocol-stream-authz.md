# Blocked: per-stream authorization hook for the Optimystic control-DB protocols

**Why blocked:** the change is in the `optimystic` repository (linked workspace,
not part of this monorepo). A human needs to either open the corresponding
ticket/PR there or decide the seam's shape with the optimystic maintainers.

## What is needed upstream

The membership hardening chain (step 6, `membership-connection-gater`) gates the
sereus-owned control protocols per stream (`/sereus/strand-wake/1.0.0` and
`/sereus/strand-addr/1.0.0` check `isAuthorizedMember` on every inbound stream)
and now also denies whole connections from positively-unauthorized peers. But
the protocols that actually carry database writes — the surface an outsider
would use to inject rows that replicate —

- `/optimystic/control-<party>/repo/1.0.0`
- `/optimystic/control-<party>/cluster/1.0.0`
- `/optimystic/control-<party>/sync/…`
- `/optimystic/control-<party>/block-transfer/…`

are registered inside `@optimystic/db-p2p`'s `createLibp2pNode` by services that
expose **no per-stream authorization seam**: `RepoService.handleIncomingStream`
(and its cluster/sync/block-transfer siblings) go straight from "stream opened"
to "decode and execute the operation". Sereus cannot wrap the handlers from
outside without re-implementing the protocol framing (explicitly ruled out).

**Requested seam (either works):**

- an optional per-service init option, e.g.
  `authorizeInboundStream?: (remotePeerId: string, protocol: string) => Promise<boolean> | boolean`,
  consulted at the top of each service's inbound stream handler (reject = abort
  the stream / error response, never execute the operation); or
- one node-level `createLibp2pNode` option threaded to all four services.

Fail-open must NOT be the default once a predicate is supplied: a supplied
predicate that returns false rejects the stream.

## Sereus-side wiring once the seam lands (bring this ticket back through the pipeline)

In `CadreNode.createControlNode`, pass the predicate
`(remotePeerId) => this.isAuthorizedMember(remotePeerId)` — the voucher-anchored
membership check — for the control network node only (strand cohort nodes are
cross-party and must NOT get it). Add an integration test: an unauthorized peer
that somehow holds a connection (e.g. admitted during an enrollment window)
still cannot execute a repo `pend`/`commit` against the control DB.

## Interim coverage (what holds the line today)

- Rows an outsider writes are **disbelieved at read time** (the voucher-anchored
  `isAuthorizedMember` predicate — chain step 4) — this is the primary fix.
- The connection gater denies an unauthorized peer's inbound control connection
  outright in the steady state, so reaching the repo protocol at all requires
  hitting an enrollment window, a formation-open node, or an un-enrolled node.

## Unblocked 2026-07-29 — the upstream seam landed

Filed upstream as `feat-inbound-stream-authorization-hook` and implemented in `../optimystic`
commit `0919e55`. This ticket moves from `blocked/` to `implement/`; the sereus-side wiring
described above is now buildable as written.

### The API you get

A single node-level option on `createLibp2pNode`, threaded to all four database services
(`repo`, `cluster`, `sync`, `block-transfer`):

```ts
authorizeInboundStream?: (remotePeerId: string, protocol: string) => Promise<boolean> | boolean;
authorizeInboundStreamTimeoutMs?: number;   // default 5000
```

`remotePeerId` is `PeerId.toString()`. **Compare like with like** — a representation mismatch
here fails open in practice, because every comparison returns false and the temptation is to
"fix" it by loosening the check.

Semantics, all verified upstream by test: only a literal `true` allows. `false`, a throw, a
rejection, a timeout, and an unidentifiable remote all deny, with no path to executing the
operation. Denial aborts the stream with a coded error, so the caller sees a stream reset —
deliberately indistinguishable from a transport fault at the remote end, fully distinguishable
in the denying node's logs. Supplying no predicate is byte-identical to previous behavior.

### Two answers you were relying on, now confirmed rather than assumed

- **Per-stream is per-operation.** None of the four protocols multiplexes multiple logical
  operations onto one stream — each handler returns after its first response. One check per
  stream is sufficient.
- **Self-dials never reach these handlers**, at three libp2p layers plus every internal caller.
  A predicate that only knows about remote members will not deny your own node.

One caveat to design around: `RepoMessage.operations` is an array and a single operation can name
many block ids. This seam is **peer admission, not a per-block ACL** — it answers "may this peer
talk to this database at all", not "may it touch this row".

### Scope reminder

Wire it on the **control network node only** (`CadreNode.createControlNode`), with
`(remotePeerId) => this.isAuthorizedMember(remotePeerId)`. Strand cohort nodes are cross-party and
must NOT get it — a strand's peers are members of *other* parties and would all be denied.

Watch the enrollment window: the predicate is consulted on every inbound stream, so a peer
mid-enrollment must already be authorized by the time it opens a repo stream, or enrollment
deadlocks. The ticket body above notes the connection gater is deliberately fail-open in exactly
that ambiguous state; this seam is not, so verify the ordering rather than assuming it carries
over.

### Test to add

Per the ticket body: an unauthorized peer holding a connection (e.g. admitted during an
enrollment window) still cannot execute a repo `pend`/`commit` against the control DB. Assert the
control database was not written, not merely that an error surfaced.
