# Durable trusted-owner anchor + bootstrap peers in the browser

`startCadre` (`cadre-web.ts`) injects neither `trustedOwners.store` nor
`bootstrapPeers.store`, so both node-local records are in-memory only and die on reload.
A tab invited while the owner is briefly unreachable has nothing left to dial after a
refresh, and no anchored owner key to judge the group's rows with if it did reconnect.

## Where they go, and why

The tab's Ed25519 identity, its party id, and its identity-first-seen marker already live
in the **`kv` object store of the control IndexedDB database** (`sereus-strand-control`,
opened as `CONTROL_STORE_KEY` in `strand-storage.ts`; see `loadOrCreatePartyId` and
`loadOrCreateBrowserPeerKey(controlHandle)` in `cadre-web.ts`). Both node-local records go
in the **same object store, same database**.

The decisive property is **shared fate with the identity**. Nothing in a browser is
tamper-resistant against the page's own scripts, and every same-origin store is equally
clearable by the user — so "which storage is safer" has no answer here. What *is* a real
choice is whether the anchor can outlive, or be outlived by, the key it is supposed to
qualify. Keeping them in one database means "Clear site data" wipes identity, anchor and
dial targets together and the tab cold-starts as a genuinely fresh node that trusts no
one until re-invited — which is the required degradation. Splitting them across
`localStorage` and IndexedDB permits a half-cleared state where the tab keeps its peer id
but its anchor is gone (silently authorizes nobody) or keeps a stale anchor under a
regenerated identity. `localStorage` is rejected for that reason, not for capacity.

Slot keys (in `kv`, alongside the existing `party-id` / `identity-first-seen`):

- `trusted-owners` — the anchor snapshot
- `bootstrap-peers` — the retained dial targets

Both are party-scoped inside the envelope, and the shared loader already treats a foreign
`partyId` as a cold start, so a single key per record is enough (one browser profile runs
one party per origin).

The `kv` store's value type is `string | Uint8Array`; `DurableSlot` deals in text, so
write strings. A stored value that is not a string is a corrupt slot ⇒ treat as absent.

## Sketch

```ts
// cadre-web.ts (or a small lib/node-local-slots.ts if it reads better)
function kvSlot(handle: OptimysticWebDBHandle, key: string): DurableSlot {
	return {
		async load() {
			const raw = await handle.get('kv', key);   // throws ⇒ unreadable ⇒ propagate
			return typeof raw === 'string' ? raw : undefined;
		},
		save: async (text) => { await handle.put('kv', text, key); },
	};
}
```

Wire into `startCadre` after `partyId` is resolved and before `new CadreNode(config)`:

```ts
trustedOwners: { store: await PersistentTrustedOwnerStore.open(kvSlot(controlHandle, 'trusted-owners'), partyId) },
bootstrapPeers: { store: await PersistentBootstrapPeerStore.open(kvSlot(controlHandle, 'bootstrap-peers'), partyId) },
```

An IndexedDB read failure must **propagate** — do not swallow it into `undefined`. The
`open()` calls therefore run inside `startCadre`'s normal error path (unlike
`runOwnerGenesis`, which is deliberately fail-soft): an unreadable anchor is a refusal to
start, not a silent downgrade to trusting nobody.

## Edge cases & interactions

- **Migration.** None. An existing install has no persisted anchor, so it cold-starts
  once: `runOwnerGenesis` re-anchors the founder's own key on every start, and an
  invited tab re-anchors on its next applied seed. State this in the code comment so a
  reader does not go looking for a migration that was skipped by mistake.
- **User clears site data.** Identity, party id, anchor and dial targets all vanish
  together ⇒ fresh node, trusts no one, must be re-invited. Assert this is what happens
  rather than a tab that keeps its peer id and an empty anchor.
- **Corrupt / foreign-party slot.** Cold start (empty), never a crash — handled by the
  shared loader; add a web-level test that a junk string in `kv` does not break
  `startCadre`.
- **Unreadable IndexedDB.** `handle.get` rejecting (blocked upgrade, storage error) must
  fail `startCadre` loudly, not start a node with an empty anchor.
- **`stopCadre` → `closeStores()`.** The slot closures capture the control handle. After
  `stopCadre` the handle is closed; a store held past that point would throw on the next
  write. `stopCadre` already drops the node, so nothing should still be writing — verify
  no path records a bootstrap peer after stop, and null the stores alongside `partyId`.
- **Private / incognito browsing.** IndexedDB may be ephemeral or unavailable. The tab
  degrades to the same behaviour it has today (no persistence); do not special-case it,
  but make sure an unavailable store surfaces as an error rather than silent data loss.
- **Two tabs, same origin.** Both open the same IndexedDB database and each
  snapshot-writes its own view, so the last writer wins and the other tab's newly-recorded
  dial targets can be dropped. Acceptable — re-seeding refills them — but record it as a
  `NOTE:` comment at the slot site.
- **Quota exceeded.** A `save` rejection leaves the record correct in memory for this
  session and rejects to the caller; the next successful write re-lands the full snapshot.
