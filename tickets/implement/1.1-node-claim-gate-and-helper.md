# The unclaimed gate in `CadreNode`, and `claimNode` on the owner side

Second of three tickets. `node-claim-proof-and-policy` landed the proof, the `claimSecretTrustPolicy` and the `deliverSeed` extensions below `CadreNode`. This ticket wires them into the node: configuration, the policy's construction, what an unclaimed node lets strangers do, and the one-call owner-side helper. The cadre-cli surface (`CADRE_CLAIM_SECRET`) and the end-to-end scenario are `node-claim-cli-and-scenario`.

## Configuration (`types.ts`)

`CadreNodeConfig` gains:

```ts
claim?: {
  /** The one-time claim secret, base64url of 32 bytes. Never written to replicated state or logs. */
  secret: string;
};
```

`start()` validates it before any network bring-up, the way `trustedOwners.store` party mismatch is refused today (`initializeTrustedOwnerStore`):

- `parseClaimSecret` must accept it (malformed → throw, naming the problem, never the value).
- `claim` together with a non-empty `trustedOwners.pinnedKeys` or with `seedTrustPolicy` is a configuration error: a node has exactly one cold-start trust source. Throw.
- `claim` on a node that later calls `initializeSeedBootstrap` (an owner key) is not refused at start, because the call comes after start; `initializeSeedBootstrap` throws if `config.claim` is set. A hosted node never holds an owner key.

## Policy construction and the listener (`cadre-node.ts`)

- After `initializeTrustedOwnerStore` in `start()`, when `config.claim` is set, build `claimSecretTrustPolicy({ secret, trustedOwners: this.trustedOwnerStore, onClaimed })` once and keep it on the instance. Replace the three reads of `this.config.seedTrustPolicy` (`initializeSeedBootstrap`, `enableSeedListener`, the temp service in `applySeed`) with one private accessor that returns the claim policy when configured, otherwise `config.seedTrustPolicy`.
- A node with `config.claim` calls `enableSeedListener()` itself at the end of `start()`; a node that nobody can deliver a seed to cannot be claimed. Keep `enableSeedListener` idempotent as it is.
- `onClaimed(ownerKey)` emits a new event `'claim:accepted': { ownerKey: string }` (add to `CadreNodeEvents`). cadre-cli and cadre-host read claim state from it and from the predicate below.
- `isAwaitingClaim(): boolean` is public: `config.claim !== undefined && this.trustedOwnerStore?.all().size === 0`. Read live from the anchor every time, which is what `admitControlPeerUnconditionally` already does per stream; a cached flag would need its own invalidation and the anchor is the one source of truth.

## What an unclaimed node lets a stranger do

Today an un-enrolled node (empty anchor) admits everything: connections, control-database streams, relay reservations. That is tolerable on loopback and wrong for a node exposed to the internet while it waits to be claimed. While `isAwaitingClaim()`:

- **Connections**: admitted, unchanged. The seed has to ride one, and a libp2p gater cannot say "seed only". `admitInboundControlConnection` needs no change; its empty-anchor rule already answers `'admit'`.
- **Control-database streams** (`authorizeInboundControlStream`): refused, as the first check, ahead of the unconditional admits. The empty-anchor and empty-snapshot rules exist so a brand-new node can take replication from the siblings that will authorize it; an unclaimed node has no siblings yet, and the rows that will authorize anyone arrive only after the claim. Configured bootstrap infra is refused too; a relay opens no control-database stream.
- **Relay reservations** (`admitControlRelayReservation`): refused, as the first check. A storage-profile node runs the relay server by default; an unclaimed node on a public address must not become anyone's relay.
- **Wake, strand-addr, formation, cadre-invite**: no change needed. Wake and strand-addr check `isAuthorizedMember`, which is false for everyone on an empty anchor. Formation and cadre-invite verify tokens and rows in-protocol, and an unclaimed node holds none.

After the claim the anchor is non-empty, `isAwaitingClaim()` is false, and the existing rules apply: the authorized snapshot is empty, so the owner's streams are admitted (the replication cold start), its rows replicate in, and from then on membership is judged as on any node. `onSeedApplied` already calls `refreshMembershipGate('seed-applied')`.

Update the module doc of `membership-connection-gater.ts` (the stranger-allowlist section) and `docs/architecture.md` (the "What it admits anyway" and "Per-stream control-DB gate" paragraphs under Seed Delivery Protocol) with the unclaimed state: connection admitted, streams and reservations refused, until the claim.

## `claimNode` (owner side, `cadre-node.ts`)

```ts
async claimNode(target: { peerId: string; multiaddrs: string[]; secret: string }): Promise<void>
```

Requires the seed service with an owner key (the same precondition and error as `addDrone`). Steps:

1. `parseClaimSecret(secret)`.
2. `seed = await createSeed()`; `proof = claimProof(secretBytes, target.peerId, seed.signerKey, seedDigest(seed))`.
3. `ack = await seedBootstrapService.deliverSeed({ peerId, multiaddrs }, seed, { claimProof: proof })`. A dial failure propagates as thrown.
4. `ack.accepted === false` → throw `ClaimRefusedError` (new, exported; carries `code?: SeedRefusalCode` and `reason`), and write nothing. A refused claim must leave no `CadrePeer` row and no retained dial target behind on the phone, which is why the order here is seed first, row second, the reverse of `addDrone`.
5. On acceptance: `authorizePeer(peerId, multiaddrs)` (the existing wrapper, which queues the write for re-replication) and `retainDialTarget(peerId, multiaddrs, 'claimNode')`, so the phone's control-cohort reconcile pass keeps dialing the node on this launch and later ones.
6. Kick `reconcileControlCohort()` without awaiting it (log a rejection), so the first dial happens now rather than on the next timed pass. Document that a caller who wants to wait for the connection awaits `reconcileControlCohort()` itself, as `addDrone`'s doc says.

Idempotent for the same owner: a second `claimNode` after a dropped response is accepted by the node (policy step 1), `authorizePeer` is an existing-row no-op in `ControlDatabase.insertCadrePeer`, and `retainDialTarget` is idempotent. Say so in the doc comment; the scenario in the next ticket proves it.

## Edge cases & interactions

- **Unclaimed node denies control-database streams and relay reservations, admits the connection**: one unit test in `test/cadre-node-claim.spec.ts` built the way `test/cadre-node-authorized-surface.spec.ts` or `test/cadre-node-seed-trust.spec.ts` drives the admission predicates; assert the three verdicts before the claim and the stream admission after `trust(key, 'claim')` on the store.
- **Configuration conflicts** (`claim` + pinned keys, `claim` + `seedTrustPolicy`, malformed secret): refused at `start()` before bring-up. By a type where possible; otherwise one assertion each at the seam, no test.
- **Claimed node restarted with `claim` still set**: anchor non-empty, so `isAwaitingClaim()` is false and the policy answers on its anchored branch; the listener stays on and harmless. By inspection.
- **Restart with the anchor present but the secret changed**: still claimed; the secret is never consulted again. By inspection.
- **Host respawn keeps identity and workdir**: the anchor file is in the node-state directory, which cadre-host's orchestrator keeps across respawns. Nothing to do here; the scenario covers it.
- **Claim seed from a phone with a relay reservation**: the seed's owner peer carries the circuit address and `dialSeedOwners` dials it after the ack, as for any seed. Unchanged.
- **`applySeed` called locally on an unclaimed node** (a `--seed` flag, say) carries no proof and is refused `claim-proof-invalid`. Correct; the CLI also refuses the flag combination in the next ticket.
- **`claimNode` on a phone that has no listen address and no relay**: the seed lists the phone with no addresses, the node attempts zero owner dials, and the phone's reconcile pass opens the connection. This is the donation-phone scenario's existing shape.
- **Two apps on one phone**: `claimNode` runs on whichever app's node holds the owner key for the cadre the user picked; nothing here chooses. The RN ticket (`rn-app-joins-host-node-by-qr`) names the cadre in its prompt.
- **`claim:accepted` and the `seed:applied` event order**: the policy fires `onClaimed` before the peer merge and before the owner dials, so `claim:accepted` precedes `seed:applied`. State that in the event's doc comment.
