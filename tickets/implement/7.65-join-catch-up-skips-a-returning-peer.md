# Re-run the join catch-up for a peer that reconnects

## The defect

`PeerJoinBackfill` (cadre-core's peer-join catch-up, shared by every strand network and the control network) pushes a newly identified peer every block in this network's raw store that the peer is not known to hold, then adds the peer to `done`. `done` lives for the runtime: `schedulePeer` and `catchUpPeer` drop any later `peer:identify` for that peer before doing any work, including the identify that follows a reconnect.

So when peer M is caught up, goes offline long enough that it stops serving (FRET drops it, so Optimystic's `findCluster` leaves it out of every cohort), and the others keep writing, M is sent nothing on return:

- the catch-up does not re-run (M is in `done`);
- Optimystic's under-replication drain pushes only to the peers a ledger entry names in `missingPeerIds`, which are the cohort members that did not confirm the write. M was not in the cohort, so it is owed nothing.

M then holds the old revision, or nothing for a block created while it was away, until it reads that block and read repair fetches it.

Until `cohort-join-catch-up-runs-once-per-node`, storage-profile nodes also ran Optimystic's rebalance reaction, whose growth arm (`carryGrowthState` in `../optimystic/packages/db-p2p/src/cluster/rebalance-monitor.ts` intersects the confirmed-holder set with the current cohort) re-pushed every tracked block to a peer re-entering the cohort. That ticket turned the reaction off wherever the catch-up runs, which removed the only push for this case.

The same gap also affects the reverse direction: M's own catch-up has S in `done`, so a write M made alone while disconnected (Optimystic records such a solo commit as owing no one, `blocked/optimystic-write-made-alone-owes-no-one`) is not pushed to S on reconnect either, unless M restarted in between. This fix covers that non-restart case as well.

## Reproduction (verified)

Run against HEAD with this case added to `peer-join-backfill.spec.ts`, it fails with `condition never held`: the second identify pushes nothing. It needs one addition to the `makeLibp2p` fake, next to `dropConnection`:

```ts
    /** Close a peer's last connection and fire libp2p's `peer:disconnect` (its detail is the PeerId). */
    dispatchDisconnect(remotePeer: PeerId) {
      const at = open.findIndex((c) => c.remotePeer.toString() === remotePeer.toString());
      if (at >= 0) open.splice(at, 1);
      for (const handler of handlers.get('peer:disconnect') ?? []) {
        handler({ detail: remotePeer });
      }
    },
```

```ts
  it('re-runs for a caught-up peer that disconnected and came back, pushing only what moved', async () => {
    const blocks: Record<string, FakeBlock> = { b1: committed('b1', 1), b2: committed('b2', 1) };
    const { backfill, pushes, fake } = makeBackfill(blocks, { debounceMs: 1 });
    backfill.start();

    fake.dispatchConnectionOpen(peer('p1'));
    await until(() => pushes.length === 1);

    fake.dispatchDisconnect(peer('p1'));
    blocks.b1 = committed('b1', 2);
    blocks.b3 = committed('b3', 1);
    fake.dispatchConnectionOpen(peer('p1'));
    await until(() => pushes.length === 2, 500);
    expect(pushes[1]!.ids.sort()).toEqual(['b1', 'b3']);

    backfill.stop();
  });
```

`makeStorage` reads the literal map on every call, so mutating `blocks` between the runs is enough. The existing case "marks the peer done after a clean run — a second peer:identify pushes nothing" must keep passing unchanged: an identify without a disconnect (an identify-push, a second connection) is still dropped.

## The fix

Subscribe to libp2p's `peer:disconnect` (fired when the last connection to a peer closes; `evt.detail` is the `PeerId`, as `strand-peer-redial.ts` already uses it) in `start()`, remove it in `stop()`, and on it delete the peer from `done`. Nothing else is cleared:

- **Keep the memo** (`memos`). It is what makes the re-run cheap: a block the peer accepted at its current revision, or whose retained proof carries the peer's approval, is skipped. A reconnect after nothing changed pushes nothing.
- **Keep `contacted`.** The re-run waits out `debounceMs`, so a flapping relayed link that reconnects several times in a settle window costs one run.
- **Keep `retryAfter`, `failures` and any pending backoff timer.** Clearing them on disconnect would bring back the 2026-09-26 behaviour the module comment's RETRY paragraph describes: an unreachable peer re-dialled on every reconnect. The existing NOTE "a peer that disconnects INSIDE a backoff wait still costs the one attempt" stays true; leave it.

**A disconnect during a run.** If the peer disconnects while its run is in flight and the run still settles clean (its last push was answered just before the connection closed), `settleRun` would add the peer back to `done` after the disconnect cleared it, and the following reconnect would be dropped again. Record a disconnect that arrives while `inFlight` holds the peer (a small set, cleared in `trackRun`'s `finally`), and have `settleRun` skip adding to `done` when it is set. Do not gate on `isConnected` at settle time instead: hand-driven `catchUpPeer` calls (the tests, an embedder) run against peers the fake reports as unconnected, and `done` must still mean "caught up" for them.

**The control network** needs nothing extra: every re-run passes through `authorizePeer` at push time, so a removed member gets nothing.

## The cost, accepted

- A re-run that finds nothing to push costs one `listBlockIds` walk plus one `getMetadata` per block (and a `getBlockProof` for blocks whose memo revision is behind), with no network traffic. Paid once per reconnect after the debounce.
- **Duplicate pushes of a returning peer's offline commits.** When M wrote while away (with a cohort, so the ledger names S), M's re-run and M's under-replication drain both push those blocks to S. The receiver's `saveReplicatedBlock` is monotonic and idempotent, so this costs bytes, not correctness. It is the same duplicate the first catch-up already causes on a join, and it goes away when Optimystic lets an embedder report what a peer holds (`blocked/optimystic-embedder-cannot-report-block-holders`). The rejected alternative — re-run only when the peer was away long enough to leave the cohort — needs a cohort-membership history this module cannot observe.

Record the duplicate as an accepted-tradeoff `NOTE:` at the disconnect handler: what was weighed (duplicate push of the returning peer's offline commits, per reconnect, versus leaving the return case to read repair), and the revisit condition (the upstream holder-report API lands, or a measurement shows reconnect re-runs dominating push traffic).
