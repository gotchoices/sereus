# Phone reference app recommends another app (owner side)

The owner app's half of "recommend an app and enroll it on first launch". **A** is this app, holding the cadre; **B** the app it recommends. The kit pieces (`AppRecommendationStore`, `storePageLink`, `recommendedByLink`, the `SereusApp` store fields, Android `<queries>`) are `phone-kit-app-recommendations`; read the "Recommending another app" section it adds to docs/architecture.md first. B's side is `reference-app-rn-joins-the-app-that-recommended-it`.

## What the user sees

A new sub-heading **Recommend an app** inside Settings → **Add a device or app**, owner view only, below **Copy invitation**. It goes in a new component, `src/recommend-app-section.tsx`, which `AddDeviceSection` renders; `add-device-section.tsx` is already 557 lines (`wc -l`).

- **The list** shows the other Sereus apps: `KNOWN_SEREUS_APPS` and `extraSereusApps()`, this app's own scheme left out, one per scheme. Each is shown when `canOpenURL('<scheme>://')` reports it installed (button **Open ‹B›**), or when `storePageLink(app, Platform.OS, ownScheme())` is non-null (button **Get ‹B›**). Apps with neither are hidden. With none left, the line reads "No other Sereus app to recommend." The installed check is the same wrapped `Linking.canOpenURL` as `installedOwnerApps` in `join-link.ts`; factor the shared candidate list rather than repeating it. Read the list when the section appears and on the section's existing Refresh.
- **Tapping an app** opens a prompt titled "Let ‹B› join your cadre?". It contains:
  - The line "If ‹B› asks to join within the next hour, this app lets it in without asking again."
  - The **Also an owner** switch (`OwnerSwitch`, on by default, as in the other two flows).
  - **Allow and get ‹B›** or **Allow and open ‹B›**, and **Cancel**.
- **Allow** saves the pre-approval with `recommendations.approve({ scheme, appName: app.name, partyId, grantsOwner })`, then opens either `recommendedByLink(app, ownScheme())` (installed) or the store page. Save first: B may ask before A comes back to the front. `partyId` is the connected node's party; the section shows only while the node is connected. When the link does not open, the pre-approval stays and an alert says ‹B› could not be opened, so the user can open it themselves. A failed save is an alert, and nothing is opened.
- **Allowed to join** lists `recommendations.live(partyId)` under the Recommend list, one row per app: "‹B› · owner|member · until 15:30" (reuse `validUntilText`), with **Withdraw**, which calls `recommendations.withdraw(scheme)` with no confirmation, since nothing has been issued yet. The list is read when the section appears, after Allow and Withdraw, and after a pre-approval is used.
- `src/cadre-phone.ts` gains `export const recommendations = new AppRecommendationStore(phone.recommendationSlot())`, beside `linkRequests`. `extraSereusApps()` also passes through and validates `androidPackage` and `iosAppStoreId`; a malformed field reads that entry as none and is logged, as a malformed entry is today.

## Answering B without a prompt

This happens in `AddDeviceSection.handleRequest`, the seam `reference-app-rn-answers-join-requests-by-link` left. It applies only when `answerTo` is set, which means the request arrived as a link carrying a reply; a pasted request is never answered this way. The order:

1. Own request. Unchanged.
2. Deny cooldown, answering `denied`. Unchanged and still first. A recommended app that asks within 30 s of a Deny is denied, its pre-approval is not taken, and its next request after the cooldown is answered without a prompt. That is rare and recoverable; reordering the checks would change the reviewed cooldown behaviour.
3. Not owner, answered `not-owner`. Unchanged.
4. Already a member, answered `already-member`. Unchanged. The pre-approval stays until it expires.
5. **New:** `const rec = await recommendations.take(answerTo.reply.scheme, partyId)`. When it is non-null:
   - Mint `{ peerId: request.peerId, grantsOwner: rec.grantsOwner }` through the existing `mint`.
   - Answer with `answerJoinRequest`.
   - Set `linkNotice` to "Sent an invitation to ‹rec.appName›, which you allowed when you recommended it." Use `rec.appName`, A's own name for B. Never use `request.appName`, which is unverified.
   - Refresh the Allowed list.
   - When the answer cannot be opened, show the invitation for copying, as the Allow path does (`note`).
   - When the mint fails, show the usual mint alert; the pre-approval is gone (kit decision).
   - A `take` that throws (the slot is unreadable) is logged and falls through to the prompt. The user can still decide, and refusing would hide the request.
6. Prompt. Unchanged.

The one-at-a-time rule (the `linkedRequest` effect, with `mintingRef` and `pending`) applies unchanged. The invitation then shows under **Outstanding invitations** like any targeted one, with Withdraw.

## Edge cases & interactions

- **B asks after the hour:** `take` returns null, so A shows the ordinary Allow / Deny prompt. Check by inspection.
- **B is already in the cadre:** answered `already-member` before `take`; the entry expires. Check by inspection.
- **A switched cadre since the approval:** `take` for the new party returns null, so A prompts. This is the kit's party rule.
- **Two apps recommended:** the Allowed list has two rows, and each request takes its own. This is the kit's rule.
- **An impostor sends B's scheme within the hour:** it is admitted, and the answer goes to B's scheme. This is the accepted tradeoff in docs/architecture.md → "Recommending another app". The notice and the Outstanding list make it visible. Nothing to build.
- **A in the background when B asks:** the link brings A to the front, and Settings holds the request until the node is connected, as today. Answered then.
- **A not connected when the request arrives:** held as today. `take` runs only in `handleRequest`, after connection, so the party id is known.
- **Recommend while minting is in progress, or with a prompt open:** the Recommend buttons are disabled while `minting`. A prompt over a prompt cannot happen, because each is a modal.
- **Store page cannot open** (no Play Store on an emulator, say): this is the alert path above; the pre-approval stays and can be withdrawn.
- **The user taps Allow twice:** the second `approve` replaces the first, and the store opens twice. Harmless.
