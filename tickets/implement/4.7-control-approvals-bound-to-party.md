# Bind every control approval to its party

## The gap

Every signed digest in `schemas/control.qsql` starts with a table tag (`'CadreControl.<Table>'`) and an action tag (`'add'`, `'remove'`, `'vouch'`, …), but nothing that says which party (cadre) it is for. The schema says so in the NOTE inside `OwnerKey.Authorized` (~line 68): two parties that share an owner key would accept each other's approvals.

That sharing is about to happen:
- `app-joins-existing-cadre-by-invitation`: app B's node key owns its own cadre and becomes an owner of cadre A as well.
- `move-strand-between-cadres` runs on a node that owns both cadres and writes the same strand's rows into each.
- A hardware owner key (`backlog/feat-owner-keys-only-on-user-devices`) would normally own several cadres.

Two places check a signature, and both must bind the party:
1. **The SQL checks** in control.qsql, run by the engine of the machine doing the write. Optimystic cohort members do not re-run them today (`createQuereusValidator` has no production caller, see its NOTE in `../optimystic/packages/quereus-plugin-optimystic/src/transaction/quereus-validator.ts`). The design must still hold if they start re-running statements, because a re-run replays the writer's context values as literals.
2. **The TypeScript reader-side verifiers** in `peer-authorization.ts`, `peer-record.ts` and `device-token.ts`. A machine uses them to judge stored proofs it received by replication (`CadrePeer.VouchSig`, `CadreInvite.IssuerSig`, `Revocation.SignerSig`, the `CadreInviteUsage` signatures, `CadrePeer.Sig`, `DeviceToken.Sig`) against its own trusted-owner list. Since no cohort member re-validates writes, these verifiers are the real defence against a hostile writer.

## Design (settled)

### Where the SQL gets the party id: a node-local `party_id()` function

`ControlDatabase.initialize` registers a zero-argument scalar function `party_id()` on its own Quereus `Database`, marked deterministic, that returns `config.partyId`. Every bound digest puts it third:

```sql
verify(digest('CadreControl.OwnerKey', 'add', party_id(), new.Key, new.StampId), context.Signature, A.Key, 'ed25519')
```

Why this and not the other options:
- **A `context.PartyId` value is rejected.** The writer chooses it. If cohort members ever re-run statements, they replay the writer's context literals, so a hostile writer would just supply the other party's id.
- **A stored `Party` table seated at founding is rejected.** It is replicated data, and this schema already treats replicated tables as untrusted ("a reader judges the stored proof against its node-local anchor, never against this replicated table"). It would also add a table to every check's reads, a step to the founding transaction, and a change to the start-up storage-operation budget pinned by `control-start-storage-op-budget.spec.ts`.
- **Writing the party id into the schema text is rejected.** It means building SQL from a config string. The two schema copies would no longer be byte-identical (`control-schema-drift.spec.ts`), and the schema hash would differ per party.
- `party_id()` comes from the machine's own configuration, the same source the TypeScript verifiers use. The schema text stays identical for every party. A cohort member that re-runs a statement evaluates its **own** `party_id()`. Each `ControlDatabase` owns its own `Database`, so a phone serving two parties gets two separate functions.

Register it with `createScalarFunction` (`@quereus/quereus`, `numArgs: 0`, `FunctionFlags.UTF8 | FunctionFlags.DETERMINISTIC`, `TEXT_RETURN`; see `../quereus/docs/plugins.md` → Scalar Functions). Registration goes **before** `pluginResult.hydrate(this.db)`, because a warm restart parses the persisted CHECK text, which calls `party_id()`. Put the registration in one small exported function (e.g. `registerPartyIdFunction(db, partyId)` in control-database.ts) so tests that build their own `Database` can call it.

`ControlDatabase` refuses an empty or non-string `partyId` when it is constructed. Every party with an empty id would otherwise share approvals.

### Field order

`controlAuthorizationFields(domain, action, partyId, rowFields)` returns `[domain, action, partyId, ...rowFields]`. `buildAuthorizationMessage(domain, action, partyId, rowFields)` and `taggedDigest` in peer-authorization.ts take the same new argument. The party is a required positional `string`, so the type checker finds every caller. Don't make it optional.

### Which digests are bound

Bind every digest in control.qsql **except the two on `FormationUsage`**:

| Table | Digests bound |
|---|---|
| OwnerKey | `add`, `remove` |
| ValidationKey, Strand, StrandPartyKey, JoinedStrand, JoinRequest, FormationInvite | `add`, `remove` |
| JoinSuccess, JoinFailure | `add` |
| CadrePeer | `vouch` (insert and owner-update branch), `remove`, `publish` (the peer's own record) |
| DeviceToken | `add`, `remove`, `publish` |
| CadreInvite | `add` |
| CadreInviteUsage | `redeem`, `consent` |
| Revocation | `remove` (tombstones, including the ledger marker), `reissue` |

**Not bound: `FormationUsage` `'consent'` and `'vouch'`.** Neither signer knows the party. The joiner signs consent before it learns the responder's party id, which only arrives in the result frame, and it signs with a key made fresh for that one formation (`StrandSolicitationService.formStrand`). The outside approver behind a `ValidationUrl` is sent only five fields (`formation-approval.ts`). Both digests bind the invitation `Token`, a random secret that exists in one party's `FormationInvite` table, so replaying one in another party would need that party's owner to seat the same token in its own database, and the only database harmed would be its own. Write this reason once, as a comment at `FormationUsage.Authorized` / `PeerConsented`, and in the docs paragraph below.

Also not bound, and out of scope: the `'Cadre.Enrollment'` vouch (`peerAuthorizationDigest`). No table checks it, and it authorizes nothing; it is only the offline `cadre enroll register` check. Seeds already bind the party: `canonicalSeedPayload` (seed-bootstrap.ts:99) signs `{ partyId, peers }`, and the claim proof binds that seed digest. Confirmed; leave both alone.

### Where TypeScript callers get the party id

- **`ControlDatabase`**: `this.config.partyId`, for every in-class signer (`signedInsert` ~line 752, the guarded-delete helper ~line 419, `ownerKeyAddMessage`, `revocationTombstoneMessage`, the Strand / StrandPartyKey / JoinedStrand / JoinRequest / ValidationKey / CadrePeer / FormationInvite / CadreInvite / reissue writers), and for `verifyCadreInviteRow` over a bundle's copy (~line 4146). The exported module functions `cadreInviteAddMessage`, `cadreInviteRedeemMessage` and `cadreInviteConsentMessage` gain a `partyId` argument. `formationVouchMessage` and `formationConsentMessage` stay unbound.
- **`peer-authorization.ts`**: every digest builder and verifier for a bound digest takes `partyId` as its first parameter (`deviceTokenAddDigest`, `deviceTokenRemoveDigest`, `cadrePeerVoucherDigest`, `cadrePeerRemoveDigest`, `revocationDigest`, `verifyRevocationSigner`, `ownerKeyAddDigest`, `verifyOwnerKeyVoucher`, `verifyCadrePeerVoucher`, `cadreInviteAddDigest`, `cadreInviteRedeemDigest`, `cadreInviteConsentDigest`, `verifyCadreInviteRow`, `verifyCadreInviteRedemption`, `verifyInvitationAdmission`, `verifyInvitationOwnerAdmission`, and the private `verifyAdmissionChain`). `formationConsentDigest`, `verifyFormationConsent`, `peerAuthorizationDigest` and `verifyPeerAuthorization` are unchanged.
- **`peer-record.ts` / `device-token.ts`**: `peerRecordSignedPayload`, `signPeerRecord`, `verifyPeerRecordSignature`, `deviceTokenSignedPayload`, `signDeviceTokenRecord` and `verifyDeviceTokenSignature` take `partyId`. Their only production caller is `cadre-node.ts` (`signSelfRecord` ~line 2944, `resolvePeerRecord` ~line 3225, ~4556, ~4653), which passes `this.partyId`. These records come only from this party's control database, so verifying against the node's own party is correct.
- **`owner-anchor-sync.ts`**: add `partyId: string` to `OwnerAnchorInputs`. `cadre-node.ts` (~line 7797) passes `this.partyId`.
- **`cadre-node.ts`**: `verifyCadrePeerVoucher` (~line 7893) and `verifyInvitationAdmission` (~line 7741) get `this.partyId`.
- **`cadre-invite-protocol.ts`**: the redeeming device signs `redeem` and `consent` with `invitation.partyId` (~line 469). It verifies the reply's invitation row with `invitation.partyId` (~line 499), **after** the existing `reply.partyId !== invitation.partyId` refusal (~line 490). The responder verifies the redemption with `this.options.partyId` (~line 660), **after** its existing `request.partyId` check (~line 653).

### Schema text

- Change both copies identically: `schemas/control.qsql` and `CONTROL_SCHEMA` in `control-schema.ts`. The drift guard fails on any difference.
- Header comment (lines 3–6): every digest leads with the domain tag, the action tag and `party_id()`, the party this machine is configured for (registered by `ControlDatabase`, never read from a replicated table), so an approval verifies only against the one rule **in the one party** it was minted for. `FormationUsage` is the exception, with the token reason (one line, pointing at its constraint comment).
- Delete the last sentence of the comment in `OwnerKey.Authorized` ("The domain tag scopes an approval to a table and an action, not to a party: two parties sharing an owner key would accept each other's approvals.").

No backwards compatibility: parties are recreated after a schema change, as the architecture already states.

## Edge cases & interactions

- **A stored `CadrePeer.VouchSig` copied into another party's table** fails both the insert check and the reader's `verifyCadrePeerVoucher`. Verified by the behavioural test below.
- **Warm restart**: the persisted CHECK text calls `party_id()`, so the function must be registered before `hydrate`. Verified by the existing warm-restart / start-budget specs passing (`control-start-storage-op-budget.spec.ts`; the counts must not change, since nothing new is stored).
- **Cadre invitation round trip**: the device signs for `invitation.partyId`, and the member verifies with its own party, so an invitation that names the wrong party is refused at the existing `partyId` comparison before any signature check. Verified by the existing `control-cadre-invite` and `cadre-invite-protocol` specs passing with the new argument.
- **Owner-anchor derivation**: a voucher or tombstone signed for another party no longer verifies, so it neither seats nor removes an anchored key. Verified by inspection plus `owner-anchor-sync.spec.ts` passing with `partyId` threaded through.
- **Revocation ledger marker** (`openRevocationLedger`) and **re-issue** (`reissueRevocations`) sign through the bound builders. Verified by `control-revocation-ledger-marker` / `control-revocation-reissue` specs passing.
- **Empty party id**: refused at `ControlDatabase` construction. Verified by inspection.
- **Specs that build their own `Database`** with a copy of a constraint (`control-cadrepeer-voucher-constraint`, `control-devicetoken-stamp-constraint`, `control-member-key-constraint`, `digest-variadic-parity`): update any copied digest to the bound form and register `party_id()` there, or leave the copy as is if it does not mirror a bound digest. Don't weaken any assertion.
- **Phone (cadre-rn) and reference apps**: they don't call the changed functions (grep confirms only cadre-core and integration-tests do). `yarn typecheck` across the workspace confirms.
- **Owner signing prompts on a user's device** (phone, hardware key) don't exist yet. When they do, they must show which party is being signed for. This ticket adds that requirement to `backlog/feat-owner-keys-only-on-user-devices` (already done during planning) and adds no UI.

## Tests

Most existing specs sign with the correct party once the new argument is threaded in, and they keep passing. That proves the TypeScript builders and the SQL agree for every table. Add only these:

- **Structural guard** (in `control-schema-drift.spec.ts`, as a second `it`): every `digest('CadreControl.<Table>', '<action>', …)` in `CONTROL_SCHEMA` has `party_id()` as its third argument, except `CadreControl.FormationUsage`, which must not. This catches a future digest that forgets the binding. No node boot.
- **Behavioural** (new `packages/cadre-core/test/control-party-binding.spec.ts`, one `CadreNode` booted the same way `control-authorization-domain-separation.spec.ts` boots one). Each case signs with the node's own owner key but builds the message for a different party id (e.g. `'other-party'`), and asserts rejection **by constraint name** through `expectConstraintFailure`:
  - an `OwnerKey` signed add → `Authorized`;
  - a `CadrePeer` insert whose `VouchOwner` / `VouchSig` is a voucher minted for the other party → `AuthorizedInsert`;
  - a `Revocation` tombstone → `Authorized`.
  Each case also writes the same row with the correct party first or afterwards, so the test shows that only the party changed the result.
- **Reader side** (in `peer-authorization.spec.ts`, one `it`): `verifyCadrePeerVoucher` and `verifyRevocationSigner` return `false` for a signature minted for another party, and `true` for the right one.
