# Integration harness: owner keys separate from node identities

## Today

- `harness/test-party.ts` (~101–119) generates an Ed25519 key and starts the owner node with it as its **libp2p identity**, because seed owner-marking used to derive each peer's key from its peer id; the comment says the owner node "MUST adopt the owner keypair as its libp2p identity".
- `makeOwnOwner(node, key)` (`node-fixtures.ts` ~286–293) runs `ed25519KeyPairFromLibp2p(key)` on the node's libp2p key, inserts it as genesis and wires it. Also used by `control-trio.ts` (~293), `topology.ts` (~216), `node-fixtures.ts` (~455, ~574), and copied into `fixtures/strand-restart-party.mjs` (~64–66).
- 33 scenario files call `makeOwnOwner`; 15 derive owner keys from libp2p keys directly (`ed25519KeyPairFromLibp2p` / `getIdentityOwnerKey`); the harness's `ownerPrivateKey` is a libp2p protobuf `Uint8Array` (`types.ts` ~21) passed to `signMessageEd25519`.
- Scenarios that depend on owner key == peer-id key: `push-wake-e2e` scenario 3 (~455–517: the outsider's owner key is derived from its libp2p key and pinned with `trustOwnerKeys`; the other `trustOwnerKeys` calls at ~238, ~388, ~625 too), `machine-removal` (after `machine-removal-leaves-owner-keys` it removes the owner key by name, but still derives `bOwnerKey` from `bKey`), `enrollment-e2e` (after `dial-preference-without-owner-machines` it asserts `preferred`), `control-delete-while-alone-convergence`, `control-offline-read-after-restart`, `pending-join-survives-restart`.

## Design

- **One generator.** A harness helper creates an owner key independent of any libp2p key (`createOwnerKey(new InMemoryKeyStore())`, or a `softwareOwnerSigner` over fresh random bytes) and returns `{ publicKey, privateKeyB64, signer }`. The harness's owner key type is that, replacing the libp2p-protobuf `ownerPrivateKey`.
- **`makeOwnOwner(node, label?)`**: generates such a key, genesis-inserts it (with the label) and calls `useOwnerSigner`; returns the owner key record. No libp2p key parameter. Update the 33 callers and the four harness modules; callers that also need the private key for a restart re-wire (the two files `debt-harness-fold-own-owner-genesis` describes) keep the returned record across the restart and call `useOwnerSigner` again. That folds that backlog ticket in: delete it.
- **`test-party.ts`**: the owner node gets a random libp2p identity like every other node; delete the "MUST adopt" comment and the protobuf byte-slicing that pulled the public key out of it.
- **Scenarios that derive owner keys from libp2p keys** (the 15, plus `strand-restart-party.mjs`): use the generated owner key. `push-wake-e2e`'s pins (`trustOwnerKeys`) pin the outsider's / owner's generated owner key; `seedReceiverRecord`'s check that the address record's public key is the key behind the receiver's peer id is an identity binding and stays.
- A sentinel against regression: `makeOwnOwner` asserts the owner key it generated is not the key behind the node's peer id (`ed25519PublicKeyB64FromPeerId`) — cheap, and it fails loudly if a later edit reintroduces the derivation in the harness.

## Docs

`docs/testing.md`: wherever it describes the owner fixture or `makeOwnOwner` (search "makeOwnOwner", "owner key"); state that test owner keys are independent of node identities.

## Edge cases & interactions

- Scenarios that restart an owner node over its reused store (`control-offline-read-after-restart`, `control-delete-while-alone-convergence`, `strand-relay-only-restart-reconverges`, `pending-join-survives-restart`): the owner key must survive the restart in the test's own variables, since it is no longer recoverable from the libp2p key file. By running them.
- Cross-process fixture `strand-restart-party.mjs` runs in a child: pass the owner key's private half to it as it passes the libp2p key today. By running the scenario that spawns it.
- Multi-party scenarios (two cadres): each party's owner key is its own; a scenario that once relied on "one node key owns two cadres" (`docs/architecture.md` → the party-binding paragraph) now uses one generated owner key for both parties explicitly, if it needs that shape. By reading the scenarios that create two parties.
- Run time: the full integration suite does not fit one agent run's idle window comfortably; run every scenario file this ticket edits (in batches, foreground, streamed — `docs/testing.md` has the commands) and list in the handoff any not run.
