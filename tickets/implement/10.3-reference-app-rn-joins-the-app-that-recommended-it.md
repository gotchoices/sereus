# Phone reference app joins the app that recommended it (recommended side)

The recommended app's half. **B** is this app, just installed or opened by a recommendation. **A** is the owner app that recommended it and holds a pre-approval for B's scheme. The kit pieces are `phone-kit-app-recommendations`: `recommendedBySchemeFromReferrer`, and `parseCadreLink`'s `recommended-by` kind. A's side is `reference-app-rn-recommends-an-app`. Read docs/architecture.md → "Recommending another app" first.

B needs no new protocol. It opens A with its ordinary join request (`askOwnerApp(app)`), and A answers without a prompt because of the pre-approval. What this ticket adds is learning *which* app recommended B, so B can name it and open it directly.

## Where "recommended by" comes from

`src/recommended-by.ts` resolves a scheme hint to a `SereusApp`. It looks the scheme up by exact equality in the same candidate list `installedOwnerApps` uses: `KNOWN_SEREUS_APPS` plus `extraSereusApps()`, this app's own scheme left out. Anything else is dropped and logged as "not a known Sereus app". The name shown is the list's, never anything from the hint (the kit's trust rule). There are two sources:

- **Android install referrer.** Add `expo-application` at the SDK-matched version (`npx expo install expo-application`, from `packages/reference-app-rn`; it needs a native rebuild) and read `Application.getInstallReferrerAsync()`. Read it only on Android, only while the first-launch question would show (`asking` in `settings.tsx`), and once per mount. Pass the result through `recommendedBySchemeFromReferrer`.
  - Rejection, and installs not from Play (dev builds, sideloads), are logged and read as none.
  - The question waits at most 2 s for the read, then shows its plain form. It never changes once it is on screen: a referrer that arrives late is dropped for that mount.
  - iOS has no install referrer. An iOS B always shows the plain question, and its **Yes → Choose → A** path is answered by A without a prompt, as it is today.
- **The `cadre-recommended-by` link**, which A opens when B is already installed. In `app/+native-intent.tsx`, replace the pass-through branch the kit ticket left: route it to `/settings?recommendedBy=<scheme>`. Settings reads the parameter and clears it, the same way `useLinkedJoinRequest` does.
  - While `asking`, it names A in the first-launch question.
  - Otherwise (B has a cadre, a join is on screen, or the launch read is not done) it waits until the launch read and any start have settled (`startSettled`). Then it shows an alert: "‹A› suggests joining the cadre it holds", with **Join through ‹A›**, which calls `askOwnerApp(A)`, and **Not now**. While a join is on screen it is dropped with an info log, because the join on screen wins.

## The named first-launch question

When `asking` and a hint resolved to app A, the Node card shows a variant of `FirstLaunchQuestion`:

- "‹A› suggested this app. Join the cadre it holds?"
- **Join through ‹A›**: sets the answer to `'join'`, so the join section and its waiting line show, and calls `cadre.askOwnerApp(A)`.
  - On Android, if opening A by its scheme fails, it falls back to `askOwnerApp(null)` (the chooser).
  - A failure that remains shows the same alerts as `AskOwnerApp.ask` in `join-cadre-section.tsx`. Share that function rather than copy it.
- **Other choices**: drops the hint for this mount and shows the plain question.

The answer comes back through the existing `useLinkedJoinResponse` path. B's first-launch join runs as it does today: nothing to move, and nothing to dissolve.

**Not automatic: one tap.** The plan asked for B to join "automatically". B instead asks once, for two reasons:
- **The hint is unauthenticated.** Anyone can build a Play link with any referrer.
- **The app switch should be the user's.** Opening another app at first launch without a tap would switch apps on the user unasked.

The tap costs one confirmation. The user already approved in A, so nothing more is asked there.

## Edge cases & interactions

- **The referrer names an unknown scheme, B's own scheme, or `utm` text:** none, logged. The plain question shows. Check by inspection; the token parse is the kit's test.
- **The referrer names a known app that is no longer installed** (A uninstalled): Join through A fails to open. On Android it falls back to the chooser. On iOS it alerts with the copy-request line, as today. The "A uninstalled" case from the plan.
- **The referrer read never settles:** the 2 s bound shows the plain question.
- **A saved start exists** (not a first launch): the referrer is never read.
- **A recommended-by link arrives during a first-launch join that is already running:** dropped, logged.
- **A recommended-by link and a join response arrive in one launch:** the response is taken by its own hook. The hint only adds the question or alert, and an open request or a running join suppresses the alert. Check by inspection that `linkRequest !== null || cadre.joinFlow !== null` suppresses it.
- **A's pre-approval expired, was withdrawn or was used:** A shows its ordinary prompt. B notices no difference. Nothing to build here.
- **The pre-approval was member-only and B has chats** (the alert path): the join is refused up front with `StrandsNeedOwnerJoinError`, using the existing failure alert. Nothing new.
- **Both a referrer and a link name different apps:** the link wins, because it is the user's latest action. Check by inspection.
