# The joiner's seat stays two commits

This replaces `plan/joiner-membership-in-one-commit`'s first two design items. Planning found that merging the joiner's two commits (`Member` + `ConsumedInvite`, then `MemberPeer`) into one transaction is not worth doing. This ticket only records why, at the sites a future reader will meet. No behaviour changes. The plan ticket's third item (the joiner's redemption apparently re-reading after it landed) is `fix/joiner-redemption-reads-in-the-settle-window`.

## Why the merge was dropped

**It saves no requests today.** Optimystic runs one pend and one commit per collection of a transaction, about 4 `/cluster` requests per collection on a two-member cohort, with no per-transaction saving once a transaction has two or more collections. Upstream pins 3 requests for one collection and 8 for a table with one index (`blocked/optimystic-multi-collection-commit-costs-four-requests-per-collection`). Both of the joiner's commits already span several collections (each table plus its UNIQUE trees), so one transaction over all of them costs about the same as the two. The saving is one commit's serial latency (about four round trips, which matters over a relay). It becomes worth requests only once upstream batches a transaction's collections per coordinator.

**It breaks the revocation enforcer's premise.** `strand-revocation-enforcer.ts` denies, and hangs up on, every peer whose `MemberPeer` row has no live `Member` row. Its module doc says such an orphaned binding "can only mean this member existed and was removed", because `MemberPeer.MemberExists` requires the member row. That holds on the network only because the joiner commits `Member` first and starts `MemberPeer` after that commit returns. In one Optimystic transaction the collections commit independently and can be reported partly saved (`CoordinatorPartialCommitError`, "reported visibility, NOT all-or-nothing"). Two ways a merged commit would then show a binding with no member:

- **Torn commit:** `MemberPeer` saved, `Member` not. The founder's enforcer reads the joiner's machine as revoked and hangs up on it, so the joiner's own retry cannot reach the cohort. It fails closed, and only a manager clearing the binding (`removeMemberPeer`'s manager branch) undoes it.
- **Arrival order:** even when everything is saved, the founder can apply the `MemberPeer` collection before the `Member` collection. A refresh in that window denies the joiner and hangs up its connection, possibly while the `Member` commit is still in flight over it.

**It merges failure modes in the reconciler.** Today's half-committed-join handling (`reportHalfCommittedJoin`) drops the invitation, which is correct only while `ConsumedInvite` is the collection likely to have been saved. A merged commit adds a shape (`MemberPeer` saved, neither of the others) where the invitation is still live and dropping it strands the joiner.

The founder's bootstrap already writes its `Member` and `MemberPeer` in one transaction (`strand-founding-writes-batched`). That is acceptable there because the founding commit runs before any other party has joined the strand, so no other party's enforcer is reading yet. Its torn-commit `NOTE:` should name the orphaned-binding effect too.

## Edge cases & interactions

- **Accuracy of the enforcer's doc.** The amended sentence must stay true for every writer of `MemberPeer`: the reconciler (separate commit after the member row is visible), `registerMemberPeer` called directly (requires an existing member), and the founder's batch (the stated exception). Check by grepping `memberPeerInsertStatement` callers.
- **No behaviour change.** Comment and doc text only; `yarn lint` and `yarn workspace @serfab/cadre-core typecheck` stay clean.
