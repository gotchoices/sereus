# The web reference app runs the edge node

After `edge-node-in-cadre-core`, `@serfab/cadre-core/edge-node`'s `createEdgeNode(platform)` holds the lifecycle the web app copies by hand in `cadre-web.ts` (bring-up, owner step), `web-join.ts` (join, move, dissolve, removal), `web-strand-move.ts`, `web-dissolve.ts` and `party-start.ts`. This ticket gives the tab one edge node over an IndexedDB platform and deletes the copies. What the copy lacks today (GitHub #45, verified at 70b2dc1d): no start-in-flight tracking and no transition queue; `reserveRelays` reaches the control node only, so strand nodes publish no circuit address; owner genesis unbounded; `store.svelte.ts` subscribes only after a start resolves, so events during the start are missed. This also absorbs the former `debt-web-app-repeats-the-phone-kit-join-sequence`.

## The platform (`web-edge-platform.ts`, new)

```ts
export function createWebEdgeNode(): EdgeNode  // called once at module load of cadre-web.ts
```

- **`keyStore`**: a cadre-core `KeyStore` over the node-local database's `kv` object store, generalizing `ownerKeyStore` (`node-local-slots.ts`). Slot → `kv` key: `cadre/identity` → `peer-private-key` and `cadre/owner` → `owner-private-key` (the keys tabs hold today, so identity and owner key survive the upgrade; both are libp2p protobuf bytes, the format `loadOrCreateIdentityKey` reads); every other slot (joined strands, strand-move records) → `keystore.<keyId>`. `list()` reports the two mapped keys when present plus every `keystore.` key. Writes in strict-durability transactions where supported, as `ownerKeyStore` does now. Text under any slot's key → `KeyStoreAccessError`, never "absent".
- **`storage.id`**: `'sereus-web'` (one tab, one node; two tabs are two processes).
- **`storage.rawStorage(scope)`**: `lazyRawStorage(() => openStore(scope))` over `strand-storage.ts`, which keeps its per-scope handle map so diagnostics can still read `getStoreHandle(controlStorageScope(partyId))` once the node has opened it. The `openStores([...])` pre-opens before `start`, `addStrand` and `foundStrand` go away, and so does the "no pre-opened handle" throw. A strand the control network lists now gets storage instead of a throw.
- **`storage.destroyScope(scope)`**: `deleteStore(scope)`; `StoreDeleteBlockedError` propagates (the edge node keeps the marker and reports it through `dissolveFormerParty`'s error or `unfinishedRemoval`).
- **`storage.nodeLocal()`**: `get`/`set`/`delete` over the `kv` store of `NODE_LOCAL_STORE_KEY`, opening it on first use and after `close`; `flush` is a no-op (each `put` is its own transaction, as now). Values are text; a non-string value reads as absent, as `kvSlot` does now.
- **`storage.close()`**: `closeStores()`.
- No `trustedOwnerSlot`: the default node-local key `trusted-owners.<partyId>` is the key tabs use today.
- **`transports(relayAddrs)`**: `webSockets()`, `circuitRelayTransport()`, `webRTC({ rtcConfiguration: { iceServers: resolveStunServers(relayAddrs, import.meta.env.VITE_STUN_URLS) } })`, `webRTCDirect()`.
- **`listenAddrs(relayAddrs)`**: `['/webrtc']` when relays are named, else `[]`. cadre-core adds the bare `/p2p-circuit` for a named relay (`relay-addrs.ts` → `resolveListenAddrs`).
- `allowPrivateDial: true` (today's permissive gater), `dataVersion` unset, no `configure`.

Relays go through `network.relayAddrs` with `requireRelay: false` (the edge config), so each strand node gets a supervised reservation of its own. Delete the `reserveRelays` call and the NOTE about it (~cadre-web.ts 504-528). `getRelayState()` keeps reading `node.getRelayReservationState()`.

## The start record

The tab's start is the edge node's saved start (`start-options` key, the kit's record), replacing `party-start.ts`:

- On load: `loadSavedStart()`; when it gives one, start its options with `relayAddrs` replaced by the current `resolveRelayAddrs()`. The tab ignores `autoStart`: a tab starts on load, as now ("Go back to your own cadre" after a removal is a load).
- With none, found a party: `{ partyId: crypto.randomUUID(), bootstrapAddrs: [], relayAddrs, origin: 'founded', ownerKeyLabel: 'browser' }`.
- Keep the tab's refusal to found over an unreadable record: when `nodeLocalRecords().get('start-options')` holds text but `loadSavedStart()` gives `undefined` (the kit's parse logs and drops a record it cannot use), report an error and do not mint a party. Today's `readPartyStart` throws in that case for the reason that still holds: a fresh party would orphan the one the record names.
- A tab upgraded across this change has a `party-start` record and no `start-options`, so it founds a fresh party once; the old party's data and any `strand-move.*` records stay unread in IndexedDB. Development builds only, no compatibility (AGENTS.md). Say so in the README's storage section.

## The store (`store.svelte.ts`)

- Subscribe once, at module load, through `edge.on(event, handler)` for every event `subscribe(node)` registers today, and `edge.onStatus`. The handlers are re-applied to every node a start, restart, join or dissolve builds, before it starts, so `control:connected` no longer needs the synthetic record and events during a start are kept. Delete `subscribed`, `releaseNode`'s unsubscription role, and the per-node `subscribe`.
- `state.status` follows the edge status (`stopped`, `starting`, `joining`, `running`, `removed`, `failed` → the store's `error`), plus the store's own steps around it. Attach the page layer (chat strand, poll, cards) whenever a status `running` reports a node the store has not attached yet. That covers the start after a join, the restart after a dissolve, and the left party coming back after a failed join, none of which the store drives itself any more.
- Removal: the edge node acts on `cadre:removed` itself (stops, rewrites the start, deletes the party's storage, reports `removed` with `formerPartyId`). The store maps that status to `state.removed`, and deletes `onRemoved`, `actOnReportedRemoval`, `leaveRemovedParty`, the `transitions` counter and `inTransition`. The edge node's queue does what they did. The NOTE on `actOnReportedRemoval` about dropping a report for a party being left is resolved: the kit deletes that party's storage.
- `joinCadre(encoded)`: `decodeInvitationForThisTab` (stays in `web-join.ts`, with `joinRequestText` and `WEB_APP_NAME`; nothing else in that file survives), then `edge.joinCadre(invitation, { relayAddrs: resolveRelayAddrs(), signal, onProgress })`. `WebJoinProgress` → the edge node's `EdgeJoinProgress`; `JoinOutcome` → `JoinCadreResult` (the page reads `redemption` fields from the result itself).
- `retryStrandMove()` → `edge.finishStrandMove()`. That call now re-asks a joined party for the owner row first (`edge-node-in-cadre-core`). It throws where the web copy reported `deferred`: show `StrandMoveNotOwnerError` and adoption failures as the move card's stalled state.
- `dissolveFormerParty(discard)` → `edge.dissolveFormerParty({ discard })`. The edge node starts the running party again itself; the store re-attaches through the status rule above.
- `stop()` → `edge.stop()`; `restart()` → `edge.restart(options)`, options from `edge.options` with fresh relays.
- `importOwnerKey` → `edge.importOwnerKey`; the owner state follows `status.owner`.

## Edge cases & interactions

- **A start during a stop, two starts at once, Restart during a join**: all queued by the edge node. Verified by the kit's `node.spec.ts` cases, which now run the same runtime; no web test.
- **Events during a start** (`control:connected`, `strand:started` of a joined strand at boot) reach the store because handlers are attached before `start()`. By inspection; the solo `boot.spec.ts` event log shows `control:connected` from the real event.
- **Attaching twice.** The status rule attaches once per node; a `running` report for the same node after an `importOwnerKey` (owner becomes `enrolled`) must not add the chat strand again.
- **`addChatStrand` on the joined party** still works with no pre-open: lazy storage opens `CHAT_STRAND_ID`'s database on first use.
- **Diagnostics before the control store opens**: `getControlDbHandle()` is null until the node's first control read opens it, as it is null before a start now.
- **Two tabs of one origin** share the node-local database as now (the NOTE on `kvSlot` stays true); `StoreDeleteBlockedError` still surfaces when the other tab holds the left party open.
- **Identity across the upgrade**: `cadre/identity` → `peer-private-key` keeps the tab's peer id (`e2e/solo/reload-persistence.spec.ts`). Pin the slot-to-key map in `test/node-local-slots.spec.ts`'s existing key-name test, retargeted to the new key store; keep its two `ownerKeyStore` tests (round trip, text under the key → `KeyStoreAccessError`) against it.
- **Strand nodes reserve on the relay** with a relay configured: the formation e2e (`formation-convergence.spec.ts`) dials strand addresses by hand today. Leave it as is; do not widen this ticket into proving inbound strand dials.
- **svelte-check**: `backlog/reference-app-web-libp2p-interface-dedup` reports two type errors at the `loadOrCreateBrowserPeerKey` result passed as `privateKey`. This ticket deletes that call. If svelte-check is then clean, say so in the handoff so that ticket can be closed; if another site shows the same skew, it stays.
