# Cancelling an outstanding invitation

## The measured defect

`packages/cadre-core/test/strand-member-revocation.spec.ts` →
`'a revoked member re-admits ITSELF off an invite it held but never consumed'` passes today
(verified this run: `yarn vitest run test/strand-member-revocation.spec.ts -t "re-admits ITSELF"`
in `packages/cadre-core`, 1 passed). A manager issues two invitations to one party; the party
joins on the first, is removed, then consumes the second and is a member again. No manager
action can stop it.

The removal gate closed the *spent*-invitation path only: `Member.Authorized`'s invite branch
requires the admitting `ConsumedInvite` row to be absent from the committed snapshot, so a
stale consumption record is inert. An **unspent** invitation produces a genuinely fresh
consumption record, so it re-admits normally. `Strand.Invite` is insert-only with no
deactivation path (its own standing `TODO: ability to deactivate?`), no invitee binding, and
only an optional expiry.

Sharpest case: managers are the parties that issue invitations, so a manager anticipating its
own removal can mint a stack of never-expiring invitations for itself and re-seat itself
indefinitely.

## Chosen shape: an insert-only cancellation tombstone

Add a fourth table beside `Header`/`Invite`/`ConsumedInvite`:

```sql
    -- A manager has cancelled invitation [InviteKey]: it may never be consumed.
    table CancelledInvite (
        InviteKey text primary key,
        constraint OnlyClosed check (
            exists (select 1 from Header H where H.Type = 'c')
        ),
        constraint Immutable check on update, delete (false),
        constraint Authorized check on insert (
            exists (select 1 from committed.Manager A
                where A.MemberKey = context.ManagerKey
                    and verify(digest('Strand.CancelledInvite', 'cancel', new.InviteKey),
                               context.ManagerSignature, A.MemberKey, 'ed25519'))
        )
    ) with context (ManagerKey text, ManagerSignature text);
```

and one new deferred check on `ConsumedInvite`:

```sql
        constraint NotCancelled check on insert (
            not exists (select 1 from CancelledInvite C where C.InviteKey = new.InviteKey)
        ),
```

Blocking the `ConsumedInvite` insert is sufficient to block the join: `Member.Authorized`'s
invite branch requires a same-transaction fresh `ConsumedInvite` row, and `consumeInvite`
writes both rows in one transaction, so the whole join rolls back. Keep the rule in one place
(`ConsumedInvite`) rather than duplicating it into `Member.Authorized`.

### Why a tombstone rather than deleting the `Invite` row, or a state column

- **Deleting the `Invite` row re-opens a replay surface.** `InviteValid` verifies signatures
  over `(Key, Expiration)` only — there is no per-row `StampId` on `Invite` — so a deleted
  `Invite` row can be re-created by replaying the captured issue signatures. Closing that
  would mean adding `Invite.StampId` and widening `Revocation.RowIsGone` to a fourth table.
  A monotone tombstone needs neither. (The control layer's `CadreControl.FormationInvite`
  *is* deletable, but it carries a `StampId` for exactly this reason.)
- **A state column needs an UPDATE**, and `Invite` is insert-only on purpose.
- **Insert-only converges.** A growing set of "dead" markers merges cleanly across nodes; a
  delete/re-insert pair does not. This matches `Strand.Revocation`'s existing rationale.
- **No caller-supplied value decides admission.** The ticket's warning about `NotExpired`
  reading `context.Now` does not apply: `NotCancelled` reads only stored rows.

### Deliberate omissions in the table

- **No `StampId`.** The table is insert-only and its primary key *is* the invite key, so a
  replayed insert collides on the PK — the same argument the existing comment above
  `ConsumedInvite` makes for `Invite`/`ConsumedInvite`.
- **No `InviteExists` gate.** Do *not* require the `Invite` row to be visible. A node that
  has not yet converged on the `Invite` row must still be able to record the cancellation —
  refusing it would fail **open** on a security control. Junk rows only grow the table (the
  tradeoff `Revocation.RowIsGone` already documents for junk stamps); record that as a
  `NOTE:` on the table, in the style of `Revocation`'s growth note.
- **`committed.Manager`, not `Manager`.** The check has a subquery so it defers to commit;
  reading the pre-transaction snapshot stops a manager seated in the same transaction from
  authorizing its own cancellation, matching every sibling `Authorized` in this schema.
- **`Immutable` on update and delete.** Un-cancelling would restore the re-entry. To
  re-invite a party, issue a fresh invitation.

### Residual behavior, stated plainly

Cancellation is an **operator action, not a cascade**. Removing a member does not
automatically cancel anything, because an invitation names no invitee — there is nothing to
match a removed member against. Auto-cancellation requires binding invitations to an intended
invitee at issue time, which is a separate design change filed as
`feat-strand-invitee-bound-invites` (backlog). Keep this ticket's scope to the primitive plus
enumeration; do not attempt binding here.

Convergence caveat to note in the schema: a cancellation must propagate before the holder
consumes, so a holder redeeming on a node that has not yet seen the tombstone still gets in.
Same convergence class as the existing `NotRevoked` / `MinOneMember` local-visibility notes —
document it, do not attempt to solve it.

Considered and rejected: forcing every invitation to carry a bounded expiry. The bound would
have to be checked at issue time against a caller-supplied "now", so an issuer picks its own
clock — it does not constrain a hostile manager, and it costs legitimate never-expiring
invitations.

## Writer surface

```ts
export interface CancelInviteParams {
  /** A manager's strand keypair — must be a PRE-EXISTING `Strand.Manager` row. */
  managerKeyPair: Ed25519KeyPair;
  /** The `Invite.Key` to kill. */
  inviteKey: string;
}
export async function cancelInvite(db: Database, params: CancelInviteParams): Promise<void>;

export interface OutstandingInvite {
  /** The `Invite.Key` (invite public key, base64url). */
  inviteKey: string;
  /** Canonical-datetime expiry string, or null for never-expires. */
  expiration: string | null;
}
/** Invites that are neither consumed, cancelled, nor expired at `nowMs` (default `Date.now()`). */
export async function listOutstandingInvites(db: Database, nowMs?: number): Promise<OutstandingInvite[]>;
```

- `cancelInvite` signs `signStrandApproval(['Strand.CancelledInvite', 'cancel', inviteKey], ...)`
  and inserts with `with context ManagerKey = ?, ManagerSignature = ?`. Make it
  **insert-if-absent** (quiet no-op when already cancelled), matching
  `registerMemberPeer`/`revokeMember`'s restart-safe shape.
- Both helpers must read via **unfiltered scans + JavaScript comparison**, never a
  where-equality on a full primary key — see the `scanMemberPeers` doc block in
  `strand-membership-writer.ts` for why a full-PK predicate becomes an unreliable point
  lookup on a networked strand. `listOutstandingInvites` scans `Invite`, `ConsumedInvite`,
  and `CancelledInvite` into JS sets and filters expiry against
  `canonicalDatetime(db, nowMs ?? Date.now())` — the same transform `issueInvite` uses to
  store `Expiration`, so the string comparison orders chronologically.
- Export both from `packages/cadre-core/src/index.ts` alongside `issueInvite`/`consumeInvite`.

## Off-engine pre-flight

`StrandMemberVerifier.isAuthorizedToJoin` (`strand-member-registry.ts:89`) currently answers
"door is open" from a raw `Strand.Invite` count. Once cancellation exists that count is wrong
in two ways: it counts cancelled invitations, and it counts already-consumed ones. Reuse
`listOutstandingInvites` for the invite half. Its `ConsumedInvite`-short-circuit also returns
`true` for a *revoked* member holding a stale consumption row — harmless (the on-engine
constraints are the real gate, and the pre-flight is advisory) but worth a comment rather than
silence.
