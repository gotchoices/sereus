## The measured defect

`packages/cadre-core/test/strand-member-revocation.spec.ts:573` →
`'a revoked member re-admits ITSELF off an invite it held but never consumed'` passes
today. A manager issues two invitations to one party; the party joins on the first, is
removed, then consumes the second and is a member again. No manager action can stop it.

The removal gate closed the *spent*-invitation path only: `Member.Authorized`'s invite
branch requires the admitting `ConsumedInvite` row to be absent from the committed
snapshot, so a stale consumption record is inert. An **unspent** invitation produces a
genuinely fresh consumption record, so it re-admits normally. `Strand.Invite` is
insert-only with no deactivation path (its own standing `TODO: ability to deactivate?` at
`schemas/strand.qsql:56`), no invitee binding, and only an optional expiry.

Sharpest case: managers are the parties that issue invitations, so a manager anticipating
its own removal can mint a stack of never-expiring invitations for itself and re-seat
itself indefinitely.

That test is **rewritten in ticket 3.7**, not here. This ticket lands the schema rule; on
its own it makes the schema *capable* of refusing a cancelled invitation, but nothing yet
writes a `CancelledInvite` row, so 3.6 alone changes no observable behavior. The drift
guard is the only test 3.6 needs to newly pass.

## Chosen shape: an insert-only cancellation tombstone

### Why a tombstone rather than deleting the `Invite` row, or a state column

- **Deleting the `Invite` row re-opens a replay surface.** `InviteValid` verifies
  signatures over `(Key, Expiration)` only — there is no per-row `StampId` on `Invite` —
  so a deleted `Invite` row can be re-created by replaying the captured issue signatures.
  Closing that would mean adding `Invite.StampId` and widening `Revocation.RowIsGone` to a
  fourth table. A monotone tombstone needs neither. (The control layer's
  `CadreControl.FormationInvite` *is* deletable, but it carries a `StampId` for exactly
  this reason.)
- **A state column needs an UPDATE**, and `Invite` is insert-only on purpose.
- **Insert-only converges.** A growing set of "dead" markers merges cleanly across nodes;
  a delete/re-insert pair does not. Matches `Strand.Revocation`'s existing rationale.
- **No caller-supplied value decides admission.** Unlike `ConsumedInvite.NotExpired`
  (which reads `context.Now`), `NotCancelled` reads only stored rows.

Considered and rejected: forcing every invitation to carry a bounded expiry. The bound
would have to be checked at issue time against a caller-supplied "now", so an issuer picks
its own clock — it does not constrain a hostile manager, and it costs legitimate
never-expiring invitations.

### Deliberate omissions, and why they are omissions rather than oversights

- **No `StampId`.** Insert-only, and the primary key *is* the invite key, so a replayed
  insert collides on the PK — the same argument the existing comment above `ConsumedInvite`
  makes for `Invite`/`ConsumedInvite`.
- **No `InviteExists` gate.** Do *not* require the `Invite` row to be visible. A node that
  has not yet converged on the `Invite` row must still be able to record the cancellation;
  refusing it would fail **open** on a security control. Junk rows only grow the table.
- **`committed.Manager`, not `Manager`.** The check has a subquery so it defers to commit;
  reading the pre-transaction snapshot stops a manager seated in the same transaction from
  authorizing its own cancellation, matching every sibling `Authorized` in this schema.
- **`Immutable` on update and delete.** Un-cancelling would restore the re-entry. To
  re-invite a party, issue a fresh invitation. (Named `Immutable` like
  `Revocation.Immutable`, not `InsertOnly` like `Invite`/`ConsumedInvite` — 3.7's tests pin
  `/Immutable/`.)

### Edit 2 — `ConsumedInvite.NotCancelled`

Insert immediately **after** the `NotExpired` constraint and **before** `MemberValid`
(`schemas/strand.qsql:93` / `strand-schema.ts:101` is the `),` that closes `NotExpired`):

```sql
        -- A cancelled invitation may never be consumed. Blocking the ConsumedInvite
        -- insert is sufficient to block the JOIN: Member.Authorized's invite branch
        -- requires a same-transaction FRESH ConsumedInvite row, and consumeInvite writes
        -- both rows in one transaction, so the whole join rolls back. The rule lives here
        -- alone rather than being duplicated into Member.Authorized. Reads only stored
        -- rows — no caller-supplied context decides admission (unlike NotExpired's Now).
        constraint NotCancelled check on insert (
            not exists (select 1 from CancelledInvite C where C.InviteKey = new.InviteKey)
        ),
```

### Edit 3 — the `CancelledInvite` table

Insert after the `ConsumedInvite` declaration (`schemas/strand.qsql:95` /
`strand-schema.ts:103`, the `) with context (InviteSignature text null, Now datetime null);`
line) and before the `-- A party in the closed strand network` / `table Member` block, with
one blank line either side:

```sql
    -- A manager has cancelled invitation [InviteKey]: it may never be consumed.
    --
    -- A monotone TOMBSTONE, not a delete of the Invite row and not a state column on it:
    --   1. Deleting the Invite row would re-open a replay surface. InviteValid signs only
    --      (Key, Expiration) — there is no per-row StampId on Invite — so a deleted Invite
    --      row can be re-created by replaying the captured issue signatures. Closing that
    --      would mean adding Invite.StampId and widening Revocation.RowIsGone to a fourth
    --      table. (CadreControl.FormationInvite IS deletable — it carries a StampId for
    --      exactly this reason.)
    --   2. A state column needs an UPDATE, and Invite is insert-only on purpose.
    --   3. Insert-only converges: a growing set of dead markers merges cleanly across
    --      nodes, a delete/re-insert pair does not. Same rationale as Strand.Revocation.
    -- No StampId here: the table is insert-only and its primary key IS the invite key, so
    -- a replayed insert collides on the PK — the argument the comment above ConsumedInvite
    -- makes for Invite/ConsumedInvite.
    -- Deliberately NO InviteExists gate: a node that has not yet converged on the Invite
    -- row must still be able to record the cancellation. Refusing it would fail OPEN on a
    -- security control, which is strictly worse than accepting a junk row.
    -- NOTE: this table only grows — one row per cancellation, plus any junk a manager
    -- chooses to file, and Immutable means rows never go away (the tradeoff
    -- Revocation.RowIsGone already documents for junk stamps). Fine at strand scale; if
    -- invite churn ever gets large it needs pruning bounded by something other than
    -- "forever".
    -- NOTE: a cancellation must PROPAGATE before the holder redeems — a holder consuming
    -- on a node that has not yet seen this row still gets in. Same convergence class as
    -- the NotRevoked / MinOneMember / MinOneManager local-visibility notes; not solved here.
    table CancelledInvite (
        InviteKey text primary key,
        constraint OnlyClosed check (
            exists (select 1 from Header H where H.Type = 'c')
        ),
        -- Cancellation is permanent: un-cancelling would restore the re-entry it closed.
        -- To re-invite a party, issue a fresh invitation.
        constraint Immutable check on update, delete (false),
        -- committed.Manager, not Manager: this check has a subquery so it defers to
        -- commit, by which point a manager seated in the SAME transaction would otherwise
        -- be able to authorize its own cancellation. Every sibling Authorized in this
        -- schema reads committed.* for the same reason.
        constraint Authorized check on insert (
            exists (select 1 from committed.Manager A
                where A.MemberKey = context.ManagerKey
                    and verify(digest('Strand.CancelledInvite', 'cancel', new.InviteKey),
                               context.ManagerSignature, A.MemberKey, 'ed25519'))
        )
    ) with context (ManagerKey text, ManagerSignature text);
```

## Residual behavior this schema deliberately does NOT cover

Cancellation is an **operator action, not a cascade**. Removing a member does not
automatically cancel anything, because an invitation names no invitee — there is nothing to
match a removed member against. Auto-cancellation requires binding invitations to an
intended invitee at issue time, filed separately as `feat-strand-invitee-bound-invites`
(backlog). Do not attempt binding here.
