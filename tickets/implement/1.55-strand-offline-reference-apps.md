Fifth of the `strand-offline-mode` chain. The API it uses: `CadreNode.setStrandOfflineMode` / `getStrandOfflineMode`, `strand.database.offline` (`queueState`, `entries`, `status`, `discard`, `whenDrained`), and the events `strand:offline-status` and `strand:queue-state` (`strand-offline-cadre-core`). Also the edge-node start option `strandOfflineMode` (`strand-offline-platform-journals`), and the errors `StrandQueueNotEmptyError` / `StrandOfflineQueueBusyError` (`strand-offline-cadre-guards`).

Keep it small. Each app gets the same four things.

## What each app shows

- **An offline toggle** for the open chat strand, calling `setStrandOfflineMode`. The phone keeps the user's choice as its start option `strandOfflineMode`, so every strand starts in it after a restart. The web app does the same through its edge node's start options. Default off, so the existing flows and their tests are unchanged.
- **A queue status line**, from `strand:queue-state` for the open strand. Show nothing while `depth` is 0. Otherwise show "N waiting to send", with "waiting for the other members" when `waitingFor` is `'cohort'`, and "showing saved messages" while `readsServedLocally` is true.
- **Each queued message's progress**, by its transaction id. `insertMessage` already returns `StampId() as Tx`. Map `strand:offline-status` onto the existing per-message mark: `queued` shows "Waiting to send" (plus "May not go through" when `outlook.kind` is `'exposed'`); `submitting` / `partially-committed` show "Sending"; `committed` falls through to the existing durability logic (the drained commit's `strand:commit-durability` and `strand:commit-held` arrive as for an online one); `failed` shows "Not sent" with the reason. A message whose row a refusal removed disappears from the list by itself, because the table watch re-queries. The mark keeps the id so the user sees what happened.
- **Discard**, on a message still `queued` that was never sent: `strand.database.offline.discard(Tx)`. Show `EntryNotDiscardableError` as "already being sent".

Messages are assured, not exposed. Tag `Message.Id` with `"optimystic.fresh" = true` in `schemas/chat-simple.qsql`: the apps generate it as a local UUID, so no other machine can take the same key, and without the tag every queued message would read "may not go through". Mirror the tag into the three `CHAT_SCHEMA` copies (React Native, web, NativeScript) and the fenced block in `docs/reference-app-rn.md`. The drift specs compare them byte for byte after normalising. Its effect on an existing strand is a tag-only `alter table … set tags` at the next connect, which upstream allows while transactions are queued. NativeScript gets the schema change only; its offline mode is backlog `feat-strand-offline-mode-nativescript`. The integration fixtures' own hand copies of the chat schema (backlog `debt-test-fixtures-hand-copy-the-chat-schema`) are not guarded and need not change.

When a leave or delete-strand action in either app hits `StrandQueueNotEmptyError`, ask the user whether to discard the waiting messages, and retry with `{ discardQueued: true }` on yes. Only where the app already offers leaving a strand. If neither app has such an action, skip this.

## Edge cases & interactions

- **Restart with queued messages:** after the strand is published, the app lists `strand.database.offline.entries()` once and builds its marks from them. Restored transactions' `queued` statuses were delivered during `hydrate`, before any listener could attach. The publication's `strand:queue-state` is the cue.
- **Strand switch:** marks are kept per strand, as the existing undelivered marks are (`use-chat.ts`).
- **Hibernate / resume:** the events come from `CadreNode` and survive the database rebuild. A listener taken on `strand.database.offline` would not, so the apps use the events.
- **Toggle off with messages still queued:** later commits wait behind them (strands.md → Offline mode). The apps show the status line and leave the choice to the user. Inspection.
