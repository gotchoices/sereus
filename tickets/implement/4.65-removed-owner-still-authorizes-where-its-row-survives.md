# A retired `OwnerKey` row still authorizes owner-signed writes

## The defect

Every owner-gated check in `schemas/control.qsql` decides "is the signer an owner?" by reading the raw `OwnerKey` table: `exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(...))`. None of them excludes a row whose `StampId` is retired in `Revocation`. Counted in the schema: 22 live-table sites of that shape (`grep -c "from OwnerKey A" schemas/control.qsql`), plus three reads of the pre-transaction snapshot `committed.OwnerKey` that matter here: the signed-add and remove branches of `OwnerKey.Authorized`, and the issuer-still-an-owner clause of `CadreInviteUsage.Authorized`. (The founding count on `committed.OwnerKey` is a fourth read and must stay raw, below.)

`OwnerKey` is never reaped (the `REAPABLE_TABLES` comment in `control-database.ts`: an automated reap could take the table below `MinOneOwner`). So a machine that receives an owner's removal tombstone without the physical delete keeps the removed owner's row beside its tombstone forever. That is the ordinary outcome of removing a lost device: `CadreNode.removeOwner` run on an owner machine that is alone commits the delete locally only, and only the tombstone is re-issued to the other machines on the next cohort growth (`docs/architecture.md` → "Deletes made while alone"). Every machine except the remover then holds the removed owner's row, the removed machine included.

The checks run on the machine that writes; replication carries committed blocks and never re-runs them. So the machine that matters most is the removed device itself: it still holds its own owner key, its own row and now the tombstone, and every owner-signed write it issues passes the schema there and replicates to the whole cadre. From that machine the removed key can still: vouch and remove `CadrePeer` rows, remove another owner, delete a `Strand` row and its `StrandPartyKey` (no reap, the party's only copy of that identity), add a `ValidationKey`, file `Revocation` tombstones that evict devices, and re-issue tombstones.

The read side is already covered: `ControlDatabase.getOwnerKeys` and `queryOwnerKeyRows` drop retired stamps, and the trusted-owner anchor (`owner-anchor-derivation`) removes the key, so membership snapshots, seed trust and voucher judgement stop honouring it. The gap is purely the schema's write-time checks.

## What to build

**One invariant, applied at every owner lookup: an `OwnerKey` row whose stamp is retired in `Revocation` authorizes nothing.** Concretely, every `exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and ...)` gains the conjunct

```sql
and not exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = A.StampId)
```

placed before the `verify(...)` call, so a retired row never pays the signature check. The same conjunct goes on the two `committed.OwnerKey A` signer lookups in `OwnerKey.Authorized` (signed add, remove) and on the `committed.OwnerKey K` issuer clause of `CadreInviteUsage.Authorized` (binding `K.StampId`). Read live `Revocation`, not `committed.Revocation`, at every site: the checks are deferred to commit, so a tombstone filed in the same transaction also disqualifies, which matches `NotRevoked` and is strictly safer; the pre-transaction read on `committed.OwnerKey` exists only to stop a row authorizing itself and is unaffected by where the tombstone is read.

**Leave raw, deliberately:**

- The founding branch `(select count(1) from committed.OwnerKey) = 0`. A machine holding only a retired owner row must still be refused a second genesis; filtering here would let a removed device re-found the party on its own copy. Say so in the constraint comment.
- `MinOneOwner` (`(select count(1) from OwnerKey) >= 1`). With the invariant in place the signer of any owner delete is live and is not the removed key (`A.Key <> old.Key`), so at least one live row survives every owner-signed delete without this count being live-aware. Counting live rows only would change nothing; do not widen the diff.
- `ControlDatabase.hasOwnerKey` (genesis guard, documented raw) and `queryStampId` plus the insert-if-absent guards, which need physical presence.

**Why the clause is inlined rather than shared.** Checked while researching: Quereus accepts a `view` item inside `declare schema`, and a table CHECK may read a view (`../quereus/docs/sql-ddl.md`, "CHECK Constraints", the "through a view over it" case), so a `LiveOwnerKey` view written once was possible. Rejected for three reasons read from the code: (1) the `committed.` pseudo-schema resolves tables only (`../quereus/packages/quereus/src/planner/building/schema-resolution.ts`, `resolveTableSchema`), so the three snapshot sites would need the inline clause anyway; (2) the optimystic catalog hydration that runs before `apply schema` restores tables and indexes only (`ControlDatabase.initialize`: `pluginResult.hydrate` returns `{ tables, indexes }`), so a view would be missing from every warm-start catalog, every start would run a non-empty migration that fires the plugin's schema-batch hooks, and the no-op fast path that `control-start-storage-op-budget.spec.ts` and `control-database-solo-warm-start.spec.ts` rest on would be gone; (3) the schema already repeats `NotRevoked` and `RevocationRecorded` per table by design, so one more per-site clause is in keeping. The nested shape `exists (... and not exists (select 1 from Revocation R where ... R.StampId = X.StampId) ...)` already runs in `CadreInviteUsage.Authorized`, so no new planner surface is involved.

**Cost.** One more correlated `Revocation` point lookup per owner check, keyed on that table's primary key `(TableName, StampId)`, the same shape `NotRevoked` already issues on every guarded insert. Every owner-gated insert and delete already reads `Revocation` in the same transaction, so the new read adds no new class of cohort consult; the two owner-gated updates that did not read it before (`CadrePeer.AuthorizedUpdate` owner re-vouch, `Revocation.AuthorizedReissue`) now do. The storage-operation budgets (`control-start-storage-op-budget.spec.ts`, `strand-solo-write-budget.spec.ts`) may move by a few operations: re-measure and update both the measurement and its date per the provenance protocol in that file; do not widen blindly.

**Schema-change consequence.** Editing constraint text of an existing table makes a control store written by an earlier build fail its warm start (`ALTER TABLE ... DROP CONSTRAINT`, refused by the optimystic module; `docs/architecture.md` after the Control Network table list). Under the no-backwards-compatibility policy such parties are recreated; nothing to do beyond noting it in the handoff.

## Repro, and the one test to add

A schema-level unit repro on one database is impossible, and stays impossible after the fix: `Revocation.RowIsGone` refuses an `OwnerKey` tombstone while the row is present, and `OwnerKey.NotRevoked` refuses the row while the tombstone is present, so the row-plus-tombstone state only arises through replication of an alone-delete. Do not try to construct it in `control-revocation-replay.spec.ts`.

The repro is an integration scenario built on the restart choreography of `control-delete-while-alone-convergence.integration.ts` (its header explains why "alone" needs the stop-A, stop-B, restart-A-on-the-same-storage sequence). Shape:

1. A founds the party (`insertOwnerKey`, `initializeSeedBootstrap`). B starts owner-capable with its own key (as `owner-anchor-follows-owner-changes.integration.ts` wires its B: `ownerCapable`, `makeOwnOwner`), A vouches B's peer row and calls `A.addOwner(bKey)`; B connects. A vouches a bare peer X; wait for X's row and B's owner row to land physically on B (`awaitBlockCoverage`, as the delete-alone scenario does before stopping anything).
2. Quiesce A then B; restart A on its storage; `A.removeOwner(bKey)` commits alone. Assert A's connection count is zero.
3. B restarts on its storage (still holding its own `OwnerKey` row) and reconnects; wait until `B.getControlDatabase().queryRevokedStamps('OwnerKey')` holds B's stamp, and assert B's raw `OwnerKey` row is still physically present (read it with a raw `select`, as the replay spec's `stampIdOf` does; `getOwnerKeys` would hide it).
4. The write under test, issued from B and signed by B: `B.removePeer(xPeerId)`. Neither `SeedBootstrapService.removePeer` nor `authorizePeer` has a by-name liveness guard (`canAuthorize()` only checks that a private key is configured), so this reaches the schema. Before the fix it commits on B and A observes X gone; after the fix it rejects with `CHECK constraint failed: AuthorizedDelete` (the paired tombstone's `Revocation.Authorized` fails too; match either name). Also assert `A.isMember(x)` stays true. Do not use `B.removeOwner(aKey)` as the probe: `ControlDatabase.deleteOwnerKey` refuses it by name today ("cannot remove the last owner", because B's own key is already filtered out of `getOwnerKeys`), so it proves nothing about the schema.

One test, in a new scenario file beside the delete-alone one, or as a third `it` in it if an owner-capable B fits its `removeWhileAlone` fixture without contortion. The anchor scenario's header already says this ticket owns the tombstone-only case; point that sentence at the new scenario.

## Tripwire to record (a `NOTE:` comment, not a ticket)

A removed device whose node is still running keeps attempting its owner-signed re-touches on every growth drain (`reauthorizePeer`, tombstone re-issue) and now gets constraint failures where it used to succeed silently. Noise, not harm; "a node that learns it has been revoked shuts itself down" belongs to the device-removal plan ticket. One `NOTE:` where the owner-gated drain logs its failures (`CadreNode.drainPendingRevocations` or its sibling for membership re-touches).
