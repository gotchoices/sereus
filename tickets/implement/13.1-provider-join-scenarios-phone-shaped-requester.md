# Provider join scenarios with a phone-shaped requester

The wire proof for `provider-container-joins-by-claim-or-invitation`, in the shape of `provider-drone-phone-requester.integration.ts` (an in-process `ContainerService` + `MemoryStore` + `ProviderProcessOrchestrator` spawning a real `cadre-cli` child from the provider's own `buildNodeEnv`, with `publicHost: 'localhost'` so the announced `/dns4/localhost/…/ws` pair is what the phone dials) and of `node-claim-by-phone.integration.ts` (what a claim proves). Read both headers first; reuse `buildPhoneOwner`, `requireContainerRunning`, `adminClient`, `hasOutboundTo`, `waitUntil`.

## Scenario 1: `provider-container-claimed-by-phone`

Ordered steps, one `it` each:

1. The phone-shaped requester (`buildPhoneOwner`) is up and listens on nothing.
2. `createContainer({ join: { kind: 'claim' }, profile: 'storage', ... })` reaches `running`; the record's `partyId` is `unclaimed` and `joinState` is `{ kind: 'claim', state: 'awaiting' }` after the enrol read.
3. `nodeCode(id)` answers `not-ready` until the node reports an address, then a code whose `multiaddrs` are exactly one `/dns4/localhost/tcp/<ws>/ws/p2p/<peerId>` entry (no TCP, no in-container address). cadre-core's `decodeNodeClaimPayload` accepts it.
4. A wrong secret is refused `claim-proof-invalid` and the record still reads `awaiting`.
5. The requester claims it with the code: `getContainerStatus` folds `claimed` with the requester's owner key and party; the requester dials in (outbound on its side, a WebSocket connection on the node's) and is in the node's authorized member set (admin channel); `nodeCode` now answers `already-claimed`; the response never carried the secret anywhere but the code.
6. A second owner presenting the same secret is refused `already-claimed`.
7. The child restarted on the same volume and environment (`removeContainer` keeps the volume; recreate under the same container id, as `provider-drone-phone-requester` relies on) reads `claimed` with no further claim and the requester reconnects.
8. `terminateContainer` stops the record and the child.

## Scenario 2: `provider-container-joins-by-invitation`

Needs a reachable member: an always-on owner `cadre-cli` node from `startOwnerCliNode` (`owner-cli-node.ts`), which `cadre-host-join-by-invitation` uses to mint invitations through the admin client. Steps:

1. The owner node is up with a public `/ws` address; it mints an untargeted single-use invitation (`grantsOwner: false`, 15-minute expiry).
2. `createContainer({ join: { kind: 'invitation', invitation }, ... })` without `publicHost` set on the orchestrator (an invitation container need not be dialable) reaches `running`, and the fold reaches `{ kind: 'invitation', state: 'accepted', memberPeerId: <owner node> }` within the owner node's budget.
3. The container is in the owner node's authorized member set, and its own signed record reaches the owner node.
4. A second container created with an already-spent invitation (the one from step 1 again) reaches `running` with `joinState` `failed`, `retryable: false`, and `invite-spent` in `error`; nothing is in the owner's member set for it.
5. No response of `getContainerStatus` or `listContainers` carries the bundle text.
6. Both containers terminate.

## Edge cases & interactions

- Step 7 of scenario 1 is the Docker restart in miniature: the harness's `removeContainer` keeps the volume dir, so a second `createContainer` under the same `containerId` with the same `join` env comes back as the same peer and starts from `claim.json`. The `ContainerService` normally generates a fresh id per create, so this step drives the orchestrator directly, as the identity test in `provider-drone-phone-requester` does if it already exists; otherwise add a small harness hook rather than a service option.
- The claimed node restarts in-process into the requester's party: `/status` is briefly `unhealthy` during the restart. Step 5 waits on the fold with `waitUntil`, not a single read.
- Invitation scenario timing: the node redeems right after it is up; the fold happens on the first `getContainerStatus` read after acceptance. Poll the status, not the child's log.
- A spent invitation's refusal code must come from a member, so step 4 needs the owner node reachable; assert `retryable: false` to tell "refused" from "no member reached".
- Resource cleanup as the sibling scenarios: stop both in-process nodes and every child in `afterAll`; the temp root holds no `node_modules`, so its recursive delete cannot follow a junction (see `tickets/rules/sibling-repos.md`).
