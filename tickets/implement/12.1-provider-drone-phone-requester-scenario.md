# End-to-end: a phone-shaped requester rents a provider node

`provider-drone-reachable-by-phone` gives provider containers a `/ws` listener, a public announced address (`docker.publicHost`) and an optional `bootstrapNodes`. Its unit tests stop at the provider's boundary. This scenario is the wire proof of "Enrollment Flow: Phone Adds Provider Drone" in `docs/architecture.md`, the provider counterpart of `cadre-host-donation-phone-requester.integration.ts` (cadre-host's lent node, same requester shape).

## Shape

New file `packages/integration-tests/src/scenarios/provider-drone-phone-requester.integration.ts`, separate from `provider-seed-accepted.integration.ts`: that suite threads one party, a TCP cadre-cli owner and two pinned containers through ordered steps; a different owner shape in the same file would make both harder to read.

- **Provider side:** in-process `ContainerService` + `MemoryStore` + `ProviderProcessOrchestrator` spawning a real `cadre-cli` child, as `provider-seed-accepted` does. The harness orchestrator computes `appendAnnounceAddrs` with the provider's own `publicNodeAddrs('127.0.0.1', …)` and passes it to `buildNodeEnv`, so `CADRE_APPEND_ANNOUNCE_ADDRS` is exercised on a real child. If the harness change in `provider-drone-reachable-by-phone` did not already add a `publicHost` option, add it here.
- **Requester:** an in-process `CadreNode` with `listenAddrs: []`, WebSocket and circuit-relay transports only (no TCP), `profile: 'transaction'`, owner genesis on itself: copy `buildPhoneOwner` from `cadre-host-join-by-qr.integration.ts` / the requester of `cadre-host-donation-phone-requester.integration.ts`. This is its third copy; if the copies are identical, hoist it into `src/harness/node-fixtures.ts` and use it from all three, otherwise keep the local copy.
- **Port band:** pick one no other scenario uses (`grep -rn "portRange: { start\|PORT_RANGE" packages/integration-tests/src`).

## Steps (ordered `it`s, so a failure names its step)

1. Requester up; it listens on nothing.
2. `ContainerService.createContainer` with `bootstrapNodes: []` and `pinnedOwnerKeys: [<requester's owner key>]`; the record reaches `running`.
3. `getPeerInfo` returns an address `/ip4/127.0.0.1/tcp/<ws>/ws/p2p/<peerId>` (the announced public pair, not just the bound one).
4. Requester `addDrone` with the peer info's addresses, then the provider's `applySeed` delivers the seed; it is accepted.
5. Requester `reconcileControlCohort()`; the node admits it. Rows cross both ways: the node holds the requester's `CadrePeer` row and the requester sees the node's self-published row.
6. `deleteContainer`; the child exits.

Restarts of either side are out of scope: the requester's reconnect logic is shared cadre-core code that `cadre-host-donation-phone-requester` already drives through a node respawn and a requester restart.

## Edge cases & interactions

- **The requester can dial only `/ws`.** It carries no TCP transport, so step 5 passes only through the WebSocket listener; no address filtering in the test is needed or wanted.
- **In-container (loopback here) addresses in the peer info.** In the harness the bound and announced hosts coincide; step 3 asserts on the announced `/ws` form explicitly so the test fails if `CADRE_APPEND_ANNOUNCE_ADDRS` stops reaching the node.
- **Cold-start admission.** The node has no authorized members when the requester dials; it admits by cadre-core's cold-start rule. Step 5 is what shows that rule plus the seed is enough on the provider path.
- **Stale-build guard.** The suite depends on `../optimystic` and `../quereus` builds. If the guard reports a sibling stale, stop and record it in the handoff; never build siblings (see `tickets/rules/sibling-repos.md`).
