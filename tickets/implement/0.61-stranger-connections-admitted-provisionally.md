# Enrolled members admit strangers' connections provisionally

## Decision being implemented

Maintainer, 2026-10-07 (plan ticket `cadre-invite-redeemable-before-the-row-replicates`, option B). An enrolled member admits a connection from a peer it cannot place, rather than refusing it. Per-stream checks decide what that peer may speak; the guard from `control-protocol-guard` is the fail-closed layer. Purpose: a device can redeem the owner-signed `CadreInvite` row its bundle carries at a member that has not yet received that row by replication. Today that member's connection gate refuses the device before `/sereus/cadre-invite/1.0.0` runs, because check 6 of `admitInboundControlConnection` keys on the row being held locally.

## Scope: every stranger, provisionally

The member cannot know what a connecting stranger carries; the gate sees only a peer id, after the encrypted handshake and before any protocol. So "admit only while the node expects a stranger" cannot cover this case. Every enrolled member admits every stranger, on these terms:

- **Checks 1–6 are unchanged and still mean "admit outright"**: shared unconditional admissions, delegate grant, empty member set, member, outstanding formation invitation, live cadre invitation. Peers they cover get no deadline. Today's carve-outs keep their meaning: a formation session with an invited stranger is never cut short.
- **The fall-through becomes "admit provisionally" on every node**, relay server or not. It replaces both `'deny'` (relay-disabled) and `'admit-for-relay'` (relay-enabled). `InboundConnectionVerdict` becomes `'admit' | 'admit-provisionally'`. The policy no longer has a deny verdict. The bring-up quiet period's denial is the gater's own and is unchanged.
- **A provisional connection carries a deadline. At expiry the policy is asked again**, instead of the connection being closed outright:
  - `admitInbound(peer)` returns `'admit'`: the peer has since become a member, holds a delegate grant, or this node now holds a live invitation (the device's row has been seated). The connection stays and nothing is re-armed.
  - `'admit-provisionally'` again: the connection is closed through the existing bounded close-then-abort path.
  - The question times out or throws: keep the connection and log. This layer is fail-open (module doc, "Fail-open, deliberately"), and the guard is what fails closed.
  - An admitted relay reservation still disarms the deadline early (unchanged).
- **Deadline length: `relayedRequestBudgetMs` of this node's declared link** (28.5 s at the default declaration), replacing `relayAdmissionReserveDeadlineMs` (5.5 s). The longest exchange a stranger legitimately starts on a fresh connection is a cadre invitation redemption. The device abandons that address after `relayedRequestBudgetMs` of its own declared link (`redeemAtMembers`' per-address budget). That budget covers dial, request, the catch-up push, the seat and the redemption, so a member never cuts an exchange the device is still waiting on. A reservation request lands well inside it. Use this node's own declaration: the member is the one deciding. Remove `relayAdmissionReserveDeadlineMs` and `RELAY_RESERVE_REQUEST_ROUND_TRIPS` if nothing else uses them, and rename `RELAY_ADMISSION_RESERVE_DEADLINE_MS` / `RELAY_ADMISSION_CLOSE_TIMEOUT_MS` / `PendingReserveDeadlines` to provisional-admission names. Update `index.ts` and `strand-revocation-enforcer.ts` references.

Tradeoff accepted: a stranger can now hold an idle connection to any enrolled member for up to about 28.5 s, against 5.5 s on relay-enabled nodes and none on relay-disabled ones today. It can open only stranger-open and transport streams (the guard), and libp2p's connection manager limits still bound the count. Record this as a `NOTE: accepted tradeoff` at the deadline constant, with the revisit condition: stranger connections showing up as load on a member.

## What does not change

- **Relay reservations** (`admitControlRelayReservation`, the unauthorized-reservation budget, `MAX_UNAUTHORIZED_RELAY_RESERVATIONS`). Decided per RESERVE request as now. The invitation carve-outs still do not extend to reservations.
- **Claim wait** (`isAwaitingClaim`). Such a node has an empty anchor and is admitted by check 1 as today. Its streams and reservations are refused by the existing claim checks.
- **Bring-up quiet period.** Still denies both directions before the policy is asked.
- **The hop-connect defect** (`backlog/bug-party-run-relay-drops-a-stranger-dialing-through-it`). A stranger dialling *through* a party-run relay is still dropped at expiry, now after about 28.5 s instead of 5.5 s; that ticket's fix (disarm on a hop) now belongs to the provisional deadline. Don't fix it here.

## Edge cases & interactions

- **A device mid-redemption at expiry.**
  - Once the seat has committed, check 6 admits, so the connection is kept.
  - Once the redemption has committed, check 4 admits.
  - Before the seat (the device is still being caught up): the device's own per-address budget has run out by then too, so closing loses nothing.
  - Verify by inspection, and by the next ticket's scenario.
- **An unreplicated sibling** (a genuine member whose `CadrePeer` row is still on the way). Now admitted provisionally on every node. If its row lands before expiry, it is kept. If not, it is closed, and its next reconcile dial or ours re-forms the link (outbound is never gated). Today such a sibling is refused outright on relay-disabled nodes, so this is strictly more permissive. Verify with `membership-connection-gater.integration.ts`, updated.
- **The same peer, several provisional connections.** The existing per-peer set handles several entries. Each expiry re-asks independently; an admitted reservation disarms them all (existing).
- **Expiry decision racing node stop.** `admitControlPeerUnconditionally` admits when not running, so a stop in flight keeps the connection and teardown closes it. Verify by inspection.
- **Cost.** A stranger's connection still runs checks 3–6, which are control-database reads (the existing NOTE about caching them). Expiry adds one more decision per provisional connection. Extend that NOTE's revisit condition to cover the expiry read; don't add caching now.
- **Tests that asserted denial.**
  - `membership-connection-gater.integration.ts` and the second `control-stream-authz` test ("denies an un-announced stranger connection") must change: the connection is admitted provisionally, speaks nothing members-only, and is closed at expiry.
  - `relay-only-control-addr`'s drop assertion waits 10 s against the old 5.5 s deadline. Either declare a shorter `linkRoundTripMs` on the relay in that scenario or wait out the new deadline; pick one and say which in the handoff.
  - `relay-admission-deadline.spec.ts` keeps pinning disarm-on-reservation. Add the expiry re-check branch (re-asked `'admit'` keeps the connection; `'admit-provisionally'` closes it): it is new branching logic and worth one test.
