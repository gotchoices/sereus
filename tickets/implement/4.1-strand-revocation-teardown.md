# Strand revocation teardown

Second of three tickets implementing `plan/4-removal-must-cut-the-network-not-just-the-row`.
The gate (`strand-revoked-peer-gate`) refuses NEW streams, dials, connections, and relay
reservations from a revoked party's machines. This ticket closes what is already OPEN: a
long-lived strand connection may never re-dial, so without teardown a removed party keeps
its live sessions indefinitely — the gate alone only half-honors the owner ruling ("no
longer be answered to or communicated with").

## The teardown seam (plan TODO 4, settled)

The enforcer's snapshot refresh IS the seam. There is no push notification for a
replicated revocation (the strand DB has no change subscription — `StrandWatcher`'s own
comment: polling until Optimystic supports reactive subscriptions), and a LOCAL
`revokeMember`/`leaveStrand` call goes through a bare `Database` handle the runtime cannot
hook. So teardown rides the same poll that updates the deny set, with an on-demand path
for immediacy:

1. **Diff-and-hangUp.** On every snapshot refresh, compute the peer ids that ENTERED the
   revoked set. For each with an open connection on the strand's libp2p node, call
   `libp2p.hangUp(peerId)` — this closes direct AND relayed connections for that peer, and
   on a strand node running the relay server it also kills any reservation the revoked
   peer holds there (a reservation dies with its connection —
   `membership-connection-gater.ts`'s relay-seam doc). Failures logged, never thrown; the
   next refresh retries because membership in the set, not the diff, drives a sweep: also
   hang up any CURRENTLY-connected peer that is in the set, so a missed diff (resume,
   crashed refresh) cannot leave a session standing.
2. **On-demand refresh.** Expose `StrandInstanceManager.refreshRevocationEnforcement(strandId)`
   (delegating to the enforcer's `refresh()`), and surface it on `CadreNode` so an
   embedding app that just called `revokeMember` can make the cut immediate instead of
   waiting out the poll interval. Document on `revokeMember`/`leaveStrand` in
   `strand-membership-writer.ts` that callers running inside a cadre runtime should follow
   the write with this call.
3. **Self-revocation signal.** If the node's OWN peer id is in the revoked set, do not
   tear anything down (the gate on the other side already refuses us) — emit a
   `strand:revoked` event through the existing CadreNode strand-event surface (beside
   `strand:error`) exactly once per arming, and log. Best-effort by nature: the removed
   party only learns if the tombstone replicated to it before the cut — the plan names
   this as a product question, and "emit an event, do not auto-stop" is the decided
   answer; stopping or leaving is the app's call. Document that apps may treat the event
   as "this strand will no longer sync".

## Cohort participation (plan TODO 5, settled: automatic — verify, don't build)

Dropping the revoked peer from the Optimystic cohort needs no separate action. Evidence:
machines quiesce strands routinely (hibernation) and the remaining cohort keeps
committing — the push-wake scenarios write while a sibling is down — so Optimystic
provably tolerates an unreachable cohort peer. `denyDialPeer` makes the exclusion FAST
(local refusal, not a dial timeout). The residual facts, to be stated in the docs ticket,
not fixed here: the removed node keeps every block it already replicated (revocation is
forward-looking), and blocks whose only holders were the removed party's machines may
become unavailable to the remaining cohort until repair — if post-removal commit latency
or `cluster-fetch:no-quorum` ever shows up in the e2e, that is an upstream conversation,
not a workaround here (tripwire, record at the site).

## Edge cases & interactions

- **Removal racing a refresh**: revocation replicates between the read and the hangUp
  sweep — the next tick catches it; the sweep-not-diff rule above is what makes this safe.
- **Multi-machine removed party**: sweep hangs up every connected revoked peer id, not
  just the first.
- **Relay-mediated session**: `hangUp` must close a relayed connection too — assert this
  in a test (unit with a stubbed libp2p is fine; the e2e proves it on a real relay).
- **Re-admission mid-sweep**: a peer that left the set between read and hangUp — compute
  the sweep list from the SAME snapshot the refresh produced, never re-read mid-sweep.
- **Quiesce/stop during a sweep**: enforcer `stop()` must cancel the interval and make an
  in-flight sweep against a stopping node harmless (hangUp on a stopped node: catch, log).
- **`strand:revoked` idempotence**: repeated refreshes keep finding self in the set; the
  event fires once (per enforcer lifetime — a resume may legitimately re-fire).
- **What is still flowing until teardown lands** (noted by the gate's review): the gate is
  one-directional — `authorizeInboundStream` judges streams the revoked peer opens to us,
  and the gater refuses NEW connections. Nothing stops THIS node from pushing over a
  connection that is already open, and `PeerJoinBackfill` does exactly that (it pushes
  this strand's blocks on `peer:connect`, per-peer, for the connection's life). So until
  the hangUp sweep exists, a removed party that stays connected can keep receiving blocks
  from us. `hangUp` closes it in both directions, so no separate outbound gate is needed —
  but a test asserting the push stops after the sweep is worth having.
- **Self-departure**: the departing node sees ITSELF revoked (it filed the tombstone) —
  `strand:revoked` fires for voluntary leave too; that is correct and the event doc says
  so ("removed or left").

## Tests this must produce (unit)

- Newly-revoked connected peer → hangUp called; already-disconnected → no call, no error.
- Sweep catches a revoked peer connected while the diff missed it.
- hangUp rejection logged, refresh loop survives.
- Self peer id in set → `strand:revoked` once; no hangUp of others suppressed by it.
- `refreshRevocationEnforcement` triggers refresh + sweep on demand; unknown strand id is
  a quiet no-op (matching `quiesceStrand`'s posture).
