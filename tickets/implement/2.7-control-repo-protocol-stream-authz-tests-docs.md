Continuation of `control-repo-protocol-stream-authz` — that run hit its token
budget after landing the **implementation** (Phase 1) but before any tests or
docs. A second run (2026-07-29) hit its budget during investigation, **before

## What already landed (all in `packages/cadre-core/src/cadre-node.ts`)

- `authorizedControlPeers: Set<string>` — materialized in-memory snapshot of
  the authorized member peer ids (`listAuthorizedMembers` result). Its field
  doc explains WHY the per-stream predicate must never do a live control-DB
  read (the read pulls blocks over the very protocols being gated → circular
  wait → mutual denial, since the upstream stream gate is fail-closed on
  timeout). Not cleared on stop, matching `enrollmentWindowUntil`.
- `admitControlPeerUnconditionally(remotePeerId)` — the factored shared
  baseline both gates use: admit when not running / no control DB, when the
  trusted-owner anchor is absent or empty, or when the peer is configured
  bootstrap/relay infrastructure. `admitInboundControlConnection` was reworked
  to call it (its doc's check numbering updated to 1–5).
- `authorizeInboundControlStream(remotePeerId, protocol)` — the SYNCHRONOUS
  per-stream predicate: shared baseline, else admit when the snapshot is empty
  (cold start) or contains the peer, else deny + log. Deliberately does NOT
  carry the connection gater's enrollment-window or outstanding-invitation
  carve-outs (those exist for `/sereus/seed/1.0.0` and
  `/sereus/formation/1.0.0`, which are not gated here).
- Wired as `authorizeInboundStream` in `createControlNode`'s `nodeOptions`
  (control node ONLY — strand cohort nodes untouched).
  `authorizeInboundStreamTimeoutMs` left at its upstream default.
- `refreshAuthorizedControlPeers(reason)` — best-effort refresh; a failed read
  keeps the previous snapshot. Refresh points wired: after `start()`
  (non-blocking `void`), inside `runReconcileControlCohort` (rides the 15s
  cadence; replication-arrived changes land here), and after every local
  membership mutation: `publishSelfRecord`'s insert branch,
  `drainPendingPeerWrites`' re-issue loop, `authorizePeer`, `removePeer`,
  `applySeed` (both the temp-service and persistent-service paths),
  `addDrone`, `acceptPhone`.

**Unit-test design.** `membership-connection-gater.spec.ts` keeps its harness
module-private: `inject(...)` (sets `_running`, a stub `controlNode` with
peerId `'self-peer'`, a stub `controlDatabase` exposing `queryCadrePeers` +
`queryRevokedStamps`, `trustedOwnerStore`, optional solicitation stub),
`makeOwner`/`vouchedRow` (real ed25519 voucher over
`cadrePeerVoucherDigest`)/`bareRow`/`anchorWith`/`createConfig`, constants
`MEMBER`/`STRANGER`. Extract those into a shared flat helper file (repo
precedent: `test/wake-stream-helpers.ts`), import from both the existing spec
and a NEW `test/control-stream-authorization.spec.ts`. Keep the gater-spec's
`fakePeerId`/`MA_CONN`/`admit()` local to it; give the new spec its own
`authorize()` + `refresh()` casts through `unknown` (both methods private).
Matrix for `authorizeInboundControlStream` (after `refresh`, since the
snapshot starts empty):
  - not running → admit; no controlDatabase → admit; anchor absent/empty →
    admit; configured bootstrap peer → admit while a stranger alongside is
    denied (reuse the existing spec's `/p2p/<id>` bootstrap-addr pattern);
  - empty snapshot (anchored, rows all bare/unvouched) → admit (cold start);
  - vouched member in snapshot → admit; stranger → deny;
  - `openEnrollmentWindow(Date.now()+60_000)` admits the CONNECTION predicate
    but NOT the stream predicate (the key divergence — assert both in one
    test); same divergence for an outstanding open invitation
    (solicitation stub true);
  - snapshot excludes revoked-stamp rows (parity with the connection-gate
    revocation test: two vouched rows, one stamp revoked → revoked peer
    denied at stream layer, sibling admitted).
Matrix for `refreshAuthorizedControlPeers`: populates from vouched rows only
(bare rows excluded); a `queryCadrePeers` that throws on the SECOND refresh
keeps the first snapshot (member still admitted, stranger still denied); no-op
when not running.

**Integration-scenario design** (new file, suggest
`control-stream-authz.integration.ts`): three `CadreNode`s on one party —
A (owner, `profile: 'storage'`, `enableRelay`), M (member: A calls
`authorizePeer(M.peerId)` BEFORE M dials, so A's snapshot holds M), O
(outsider). `A.createInvite(...)` opens the enrollment window; O dials and
HOLDS an admitted connection (assert it, copying the `waitForConnection`
shape from `membership-connection-gater.integration.ts`). Then drive the repo
protocol RAW with `RepoClient` from `@optimystic/db-p2p`:
  - `RepoClient.create(aPeerId, peerNetwork, '/optimystic/control-<partyId>')`
    — the client appends `/repo/1.0.0`; prefix formula confirmed in
    `libp2p-node-base.ts` (`/optimystic/${networkName}`, networkName =
    `control-${partyId}`).
  - `peerNetwork` can be a minimal inline `IPeerNetwork` stub:
    `{ connect: (peerId, protocol, opts) => libp2p.dialProtocol(peerId, protocol, opts) }`
    cast as needed — the real `Libp2pKeyPeerNetwork` is heavyweight and only
    `connect` is exercised.
  - Positive control (M): `pend({ transforms: { inserts: { B1: block } },
    actionId, policy: 'c' }, { expiration })` then `commit({ blockIds: ['B1'],
    tailId: 'B1', actionId, rev: 1 }, ...)` — request shapes in
    `../optimystic/packages/db-core/src/network/struct.ts`. UNVERIFIED
    CAVEAT: the service executes against a coordinator repo, so the commit
    runs cluster consensus (cluster size default 2, supermajority = unanimity
    at 2) among the connected peers; whether a synthetic raw block commit
    passes cleanly was NOT verified. If it proves flaky, fall back to: the
    positive control is M's `get` returning a decoded RESPONSE (proves an
    authorized stream passes the gate into decode+execute) PLUS an
    owner-written row converging to M (proves the write path end-to-end,
    exactly as `control-db-two-node-convergence` does).
  - Denial (O): same pend (block id B2) → expect the call to REJECT (the gate
    aborts the stream before any frame is decoded — `RepoService.
    handleIncomingStream` runs `authorization.deny` first; remote observes a
    stream reset, surfacing from `RepoClient` as an error, message varies).
  - "**DB not written**" assertion: probe A's LOCAL store via an authorized
    path — M's `RepoClient.get({ blockIds: ['B2'] })` against A. The service
    serves `get` with `skipClusterFetch: true` (repo/service.ts ~264), i.e.
    from A's local storage only, no network pull — so an absent/blockless B2
    result IS "A's control DB was not written", while B1 present proves the
    probe can see writes. Also assert O's connection was STILL open when the
    stream was denied (the scenario's whole point: connection admitted,
    stream refused).
  - Do NOT make O its own owner or write via O's own control database: same
    party id ⇒ same collection/block ids, and two independently-founded
    histories fork the collection — messy and beside the point. Raw
    `RepoClient` is the honest attack surface.

**Convergence-scenario repair** (exact known fix): in
`control-db-two-node-convergence.integration.ts` `bootPair`, after
`B.start()`, add `await A.authorizePeer(B.peerId!.toString())` — A then
vouches B so A's non-empty snapshot admits B's pull streams, while B still
pins nobody (preserving the test's real point: `isMember` row presence vs
`isAuthorizedMember` trust, per its closing comment). Update the header
comment to note A must vouch B for B's inbound pulls to pass A's per-stream
gate.
