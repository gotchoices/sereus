# Machine removal leaves owner keys; owner-key removal gets the re-vouch plan

## Today

`machine-removal.ts` decides a machine "is an owner" by deriving an Ed25519 key from its peer id (`ed25519PublicKeyB64FromPeerId`, ~94, ~108) and lists owner keys "whose machine has no row" by the inverse (`peerIdFromEd25519PublicKeyB64`, ~73). `planMachineRemoval` (~147) then plans the `OwnerKey` delete, the dependents that key vouched and the `last-owner` refusal; `ControlDatabase.removeMachine` (~2167, `signMachineRemovals` ~2213) deletes that `OwnerKey` row with the machine's `CadrePeer` and `DeviceToken` rows. With owner keys independent of machines (`docs/architecture.md` → Owner Keys) none of that holds.

## Design

**Machine removal** — `listMachines`, `planMachineRemoval(peerId)`, `removeMachine(peerId)`:

- `CadreMachine` loses `isOwner` and the owner-only entries (an owner key is not a machine); `listOwnerKeys` (from `owner-key-label-and-founder-machine`) is the owner-key listing.
- `MachineRemovalPlan` loses `removesOwnerKey`, `dependents` and `ownDependency`; `RemoveMachineOptions.revouch` goes. A machine vouches nothing (a `CadrePeer.VouchOwner` is an owner key), so removing one strands no other row.
- `ControlDatabase.removeMachine` / `MachineRemovalTarget` drop the `OwnerKey` arm: one transaction removes the `CadrePeer` row, the `DeviceToken` row and withdraws the invitations the machine could come back with, each with its tombstone, as today.
- Refusals (`MachineRemovalRefusedError.code`): `not-an-owner` (this node has no live owner signer) and `self` (this node's own machine). `last-owner` leaves machine removal: it cannot empty the owner table any more. Keep `self`: leaving a cadre is the embedder's flow (it stops the node and deletes local data), and the removal notice (`noteOwnRemoval`) is designed around being removed by another machine; restate its reason in the docs without the "cannot sign its own owner-key removal" argument.

**Owner-key removal** — `planOwnerKeyRemoval(key)` and `removeOwner(key, { revouch? })`:

- The plan is what `planMachineRemoval` computed for an owner machine, keyed by the owner key: the `OwnerKey` row, its `dependents` (live `CadrePeer` and `OwnerKey` rows whose `VouchOwner` is this key), `ownDependency` (this node's own rows among them, which it cannot re-vouch), and a refusal: `not-an-owner`, `self` (the signer's own key: `A.Key <> old.Key`), `last-owner` (`MinOneOwner`), or `unknown` (no live row).
- `removeOwner(key, { revouch })` re-vouches the chosen dependents under the signer's key first (`reauthorizePeer`, `ControlDatabase.revouchOwnerKey`), then removes the row with its tombstone — the "Re-vouching first" logic moved from machine removal, unchanged in substance, all under one `approve`. Anything outside the plan's dependents is refused before any write. Re-vouching an `OwnerKey` row is a delete-and-re-add with no re-issue path, so the whole call refuses `alone` under the same rule as `addOwner` (no control connection while the party has other members).
- `removeOwner(key)` with no options keeps today's single-row behaviour (no re-vouch).
- Typed refusal `OwnerKeyRemovalRefusedError` with the codes above; `MachineRemovalRefusedError` keeps its own.
- Pure projections stay in `machine-removal.ts` (rename or split into an owner-key module if it reads better), with no peer-id ↔ key derivation left in it. Delete `peerIdFromEd25519PublicKeyB64` from `ed25519-key.ts` if nothing else uses it.

## Edge cases & interactions

- Removing a machine whose user also holds an owner key: the owner key stays live and keeps authorizing; it can mint and redeem a machine invitation to come back. That is the documented reason to remove the key too. Covered by the docs and the app tickets; no test here.
- `MinOneOwner` / last owner: refused by name in `planOwnerKeyRemoval`; machine removal never reaches it. **Test** — the existing owner-writer refusal cases move to `removeOwner`; keep one per code (`self`, `last-owner`, `unknown`).
- Re-vouch before removal: a dependent the user keeps is never untrusted in between, and one not kept stops passing the membership predicate on every machine. **Test** — move the existing `cadre-node-remove-machine.spec.ts` re-vouch cases to `removeOwner`, and the `machine-removal` integration scenario's owner arm to: remove machine B (its row only), then `removeOwner(bOwnerKey, { revouch })` from A. Also move the "one approval per action" assertion from `owner-signing-through-one-signer` from `removeMachine` with re-vouch to `removeOwner` with re-vouch.
- Two owners removing each other while partitioned both commit; the anchor derivation refuses a removal that would empty an anchor. Unchanged; docs only.
- A machine removed while the remover was alone: tombstones re-issue on growth as today (`Deletes made while alone`). Unchanged.
- `noteOwnRemoval` on the removed machine still stops its owner re-issue drains: it is no longer a member, whatever key it holds. By inspection.
- `hangUpRevokedControlPeers` and the protocol guard key off `CadrePeer` tombstones only, so they are unaffected. By inspection.
