# cadre-cli and cadre-host act on `cadre:removed`

`node-learns-it-was-removed` gives `CadreNode` a `cadre:removed` event and `removedFromCadre()`. This ticket makes the two server programs act on it.

## cadre-cli (`cadre start`)

- On `cadre:removed` (subscribe in `start-node.ts` where the node's other events are wired; also check `removedFromCadre()` once after start, for a removal detected before the subscription), the process:
  - writes a marker `removed.<partyId>.json` (`{ partyId, stampId, signerKey, at }`) into the node-state directory beside `claim.json` and the other node-local stores, through the same private-file helper (`commands/private-file.ts`);
  - stops the `CadreNode` (strands included) but keeps the process and its admin/health server running, so `/status` can report the removal and a supervisor does not read an exit as a crash to respawn;
  - prints one `console.warn`: the node was removed from cadre `<partyId>` by owner `<fingerprint>`, it has stopped, and what to do (delete the node-state directory to start fresh, or join a cadre again).
- At start, when the marker for the configured party exists, `cadre start` does not start the node: it runs the health server in the same removed state and prints the same warning. Rationale: `removedFromCadre()` only fires for a machine that saw its own live row in the current process, so a restart would otherwise bring a removed node back to run against a cadre that refuses it.
- `/status` (`server/health.ts`) gains `node.removed: { stampId, signerKey, at } | null`; `cadre status` prints it.
- The node-state directory is **not** deleted by the CLI: it holds the identity key, and deleting it is the operator's call (on cadre-host, the admin's Remove). Say so in the README.

## cadre-host

- `readNodeStatus` (`hosted/node-status.ts`) parses `node.removed`.
- The watcher (`hosted-node-watcher.ts`), on a `joined` (or `joining`) record whose node reports `removed`: moves the record to `error` with `error: 'Removed from its cadre by an owner'` and `retryable: false`, then stops the child (`orchestrator.stopContainer`), as it already does for a failed invitation. The supervisor's give-up rule already leaves an `error` record's workdir in place, so the admin's **Remove** deletes the node and its identity; **Reset** stays available for a claim node (it starts a fresh node with a new code).
- Whether to model this as a distinct status (`removed`) instead of `error` with a reason: keep `error`. `types.ts` documents that there is no terminal "removed" status because Remove deletes the row; a node an owner removed is, from the host's view, a node that failed and waits for the admin. Add a `removedByOwner: true` field (or reuse the `error` string) only if the UI needs to word the card differently; the implementer picks, smallest change.
- UI node page: the error card shows the reason and the existing Remove button. No new control.

## Edge cases & interactions

- **Removed while the host was down**: the child restarts with the marker present and reports removed at once; the watcher's first poll moves the record. By inspection.
- **Removed node that never received the tombstone**: never reports; the host shows it `joined` with `connected` false. That is the best-effort limit `node-learns-it-was-removed` documents; docs/cadre-host.md says the admin removes it locally.
- **Race: watcher write vs. admin Remove**: the watcher's write must follow the re-read-then-merge rule in docs/cadre-host.md ("every long operation re-reads the record after the wait"); a deleted row is never recreated. By inspection, using the existing failed-invitation path as the model.
- **Supervisor respawn**: the child does not exit on removal, so the supervisor does not respawn it; after the watcher stops it, the record is `error`, which the supervisor does not respawn. By inspection.
- **Standalone CLI under systemd** (`cadre service`): the process stays up in the removed state; a unit restart lands in the marker check. By inspection.
