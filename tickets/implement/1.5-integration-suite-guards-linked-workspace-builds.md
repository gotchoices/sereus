# Guard the integration suite against stale builds of the linked sibling workspaces

## Background: the wasted investigation this prevents

This ticket exists because a bug was filed, investigated, and re-investigated three
times before anyone noticed the failing run was testing code that had already been
fixed.

The suite depends on two sibling projects that live outside this repository —
`../optimystic` and `../quereus` — wired in through `resolutions` in the root
`package.json`. In `node_modules` they are **symlinks straight into those working
copies**:

```
node_modules/@optimystic/db-p2p  ->  C:/projects/optimystic/packages/db-p2p
node_modules/@quereus/quereus    ->  C:/projects/quereus/packages/quereus
```

Those packages are consumed from their compiled `dist`, not their `src`. So the
suite runs whatever those sibling projects last *built* — which is not necessarily
what they last *committed*, and those projects are under active development at the
same time as this one.

That is exactly what happened with the three-party strand failure:

- `../optimystic` commit `559df6a` ("let a read acquire a block the node has never
  seen") was committed at 01:47.
- The strand bug ticket was filed at ~01:55, reporting the failure as still live —
  and explicitly noting that `559df6a` had already landed.
- `../optimystic`'s `db-p2p` was not actually rebuilt until 02:17.

So the run behind the bug report executed pre-fix compiled code. Once the sibling
was rebuilt, the test passed — ten consecutive runs, with no change to this
repository at all. The bug report described a real past failure, but the fix for it
already existed; the only thing missing was a build.

## What already exists

`packages/integration-tests/src/harness/build-freshness.ts` solves precisely this
problem, and solves it well — but only for this repository's own packages. Its
`TARGETS` list covers three:

```ts
const TARGETS: BuildTarget[] = [
	{ packageName: '@serfab/cadre-core', distEntry: 'dist/index.js' },
	{ packageName: '@serfab/cadre-cli',  distEntry: 'dist/bin/cadre.js' },
	{ packageName: '@serfab/cadre-host', distEntry: 'dist/index.js' },
];
```

and `resolvePackageRoot` finds them by scanning `<repo>/packages` only, so a package
living outside this repository cannot be expressed as a target at all. The comparison
logic itself (`checkBuildFreshness` — newest source mtime under `src` versus the
`dist` entry point's mtime) is already generic and needs no change.

## What to build

Extend the same guard to cover the linked sibling workspaces, so a stale sibling
build is reported up front with an actionable remedy instead of surfacing later as a
mysterious replication or query failure.

Two things have to change:

**Locating the package.** The current `resolvePackageRoot` deliberately avoids module
resolution (the packages are ESM-only, don't all export `./package.json`, and this
module is loaded through Vite). Keep that approach, but for external packages resolve
through the `node_modules` symlink instead of the `packages/` scan: read the link
target of `node_modules/<name>` and use that directory as the package root. The
existing comment in that function explains why the workspace copy is the one the tests
load — the same reasoning holds for a symlink into a sibling repository.

**Only check what is actually linked.** This is the important correctness detail. Some
of these dependencies are symlinks into a sibling working copy, and some are ordinary
copies installed from the registry:

```
LINK @optimystic/db-core                    LINK @optimystic/quereus-plugin-optimystic
LINK @optimystic/db-p2p                     LINK @optimystic/quereus-plugin-crypto
LINK @optimystic/db-p2p-storage-web         LINK @quereus/quereus
copy @optimystic/db-p2p-storage-fs
```

A registry copy must be **skipped**, not checked. Its `src` and `dist` mtimes are
whatever the package tarball happened to record, and comparing them produces
meaningless results — the copied `db-p2p-storage-fs` currently reports "stale" purely
because packing wrote its `src` roughly ten milliseconds after its `dist`. Decide
"is this linked?" by testing whether the `node_modules` entry is a symlink
(`lstat`/`isSymbolicLink`), not by name.

## Design question to settle: how loudly to fail

For this repository's own packages a hard failure is clearly right — you edited the
source, you forgot to build, fix it and re-run.

For the sibling workspaces it is less obvious, and the implementer should choose
deliberately rather than copying the existing behaviour by reflex. The sibling repos
are worked on concurrently by their own automation. During this very investigation
`@quereus/quereus` was momentarily stale because a run in that repository was
mid-edit between commits at 05:33 and 05:44. A naive hard failure would abort this
suite whenever a neighbour happens to be mid-edit — noisy, and not something the
person running these tests can act on.

Options, roughly in order of preference:

- **Report clearly, fail the run** — consistent with the existing guard, and a stale
  sibling genuinely does invalidate the results. The remedy message must name the
  sibling build command, since `yarn workspace ...` cannot reach outside this repo.
- **Report loudly, continue** — print a prominent banner naming the stale package and
  the remedy, but let the suite proceed. Avoids failing on a neighbour's transient
  state at the cost of being ignorable.
- **Fail only past a grace margin** — treat a sibling as stale only when its source
  leads its build by more than some interval, so a mid-edit neighbour is tolerated but
  a genuinely forgotten build is not.

Whichever is chosen, say why in a comment at the site. The remedy string matters as
much as the detection: someone hitting this needs to be told to go build the sibling,
and where.

## Not in scope

Do not change what the guard does for the three `@serfab/*` packages, and do not
change `checkBuildFreshness`'s comparison semantics.
