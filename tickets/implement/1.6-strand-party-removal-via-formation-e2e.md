# Removal cuts the network on a strand formed the ordinary way

Final ticket of the party-identity chain. The enforcement machinery (`strand-revocation-enforcer.ts`) and its proof (`strand-removal-cuts-network.integration.ts`) already exist — but that scenario's own "FIXTURE HONESTY" comments state that it hand-registers every member and device record, because production wrote none. The previous three tickets make production write them. This ticket proves it and makes the docs true.

## The scenario

New integration scenario (or a new test inside `strand-removal-cuts-network.integration.ts`, reusing its helpers): host party (2 machines) publishes a closed strand and a bound formation invitation; joiner party (2 machines, or 1 if two is impractical in the harness) redeems via the **real formation handshake** — no `issueInvite` / `consumeInvite` / `registerMemberPeer` calls from the test for the parties under test. Then:

- Assert the membership the pipeline wrote by itself: two distinct `Strand.Member` rows (founder party key ≠ joiner party key, and neither equals `strandMemberKeyPair(MemberPrivateKey).publicKeyB64`), plus a `MemberPeer` row per machine under the right party key.
- Founder revokes the joiner party (`revokeMember` with the founder party keypair — the one app-facing write this feature intentionally leaves to the caller) and calls `refreshRevocationEnforcement`.
- Reuse the existing cut assertions: connections existed before, are gone after; the removed party can neither read new rows nor push writes back (the gotchoices/sereus#4 concern — a removed member must not be able to post into the conversation); remaining machines keep committing.
- Assert the removed party's machines were denied by rows production wrote, not the test.

Also worth one cheap assertion while here: a **re-join** after removal (fresh formation) lands a fresh `Member` row for the same party key and the party's machines become reachable again — the healing path ticket 3 designed.

## Edge cases & interactions

- **Timing**: membership and bindings land via a background reconciler on a poll cadence — the scenario must wait on row visibility (the existing `awaitBindingsVisible` style), never sleep-and-hope, and use the suspended-poll + explicit-refresh discipline the existing tests use.
- **Write wobble after a cut**: the first post-removal write may transiently fail ("block unavailable") — the existing tests' retry pattern applies.
- **The removed party still holds `MemberPrivateKey`**: assert nothing that pretends otherwise; the residual (past reads, no key rotation) stays documented, not fixed here.
- **Scenario cost**: this is a four-machine, two-network scenario in the same weight class as `strand-removal-cuts-network` (~minutes). Run it in the foreground; if it cannot fit the runner's idle window alongside the existing suite, land it as its own vitest file so it can be run alone.
