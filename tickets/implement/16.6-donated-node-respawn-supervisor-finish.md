# Finish the donated-node respawn supervisor

Continuation of `16.5-donated-node-respawn-supervisor`, which was cut short by a
token budget limit **after all the code was written but before anything was
compiled, executed, or documented**. Treat every claim below as unverified.

## What already landed on disk (uncommitted, unvalidated)

- **`packages/cadre-host/src/donation/donation-supervisor.ts` (new).**
  `DonationSupervisor` with `reconcile()` / `start()` / `stop()`, the five module
  constants (`DONATION_RESPAWN_BACKOFF_BASE_MS` 5 s, `…_BACKOFF_MAX_MS` 5 min,
  `…_MAX_ATTEMPTS` 5, `…_HEALTHY_MS` 10 min, `…_SWEEP_MS` 60 s), exponential
  backoff, the healthy-reset that refills the attempt budget, and the
  give-up-to-`status: 'error'` path (writes the record first, then stops the
  child, never removes it). Passes are serialized through a tail promise so the
  timer and exit-event triggers cannot overlap on one id. Exit events are
  coalesced so a crash storm queues at most one extra pass.
- **`donation/index.ts`** exports the class, the five constants, and the
  `DonationSupervisorOptions` / `SupervisedOrchestrator` types.
- **`bin/host.ts`** constructs the supervisor next to `donationService` (the
  `DonationStore` is now hoisted into a `donationStore` local so both share one
  instance), calls `start()` there, and `stop()` beside `clearInterval(reapTimer)`.
- **`donation/__tests__/fake-orchestrator.ts` (new).** The `FakeOrchestrator`
  formerly inlined in `donation-service.test.ts`, moved out and extended with
  per-`dockerId` liveness (`isRunning` now reflects it instead of returning a
  hardcoded `true`), an `onStateChange` subscription, a `crash(dockerId)` helper
  that marks a child dead *and* emits the exit event, and a raw `emit(info)`.
  `donation-service.test.ts` was edited to import it (its local copy and the
  now-unused `sleep`/orchestrator type imports were deleted).
- **`donation/__tests__/donation-supervisor.test.ts` (new).** Twelve cases over
  the fake orchestrator, a real on-disk `DonationStore`, and an injected clock:
  seeded-but-stopped is respawned with a new handle and unchanged status; a
  running node is left alone; a `terminated` loan is never respawned; a stopped
  `awaiting_seed` node is respawned; the backoff window is honoured and then
  expires; the give-up path lands `error` after 5 attempts, stops but never
  removes the child, frees the grant quota, and stops attempting; the healthy
  reset fires only past the window and does not touch `updatedAt`; a record with
  no persisted spawn inputs is skipped without ending the sweep; a record with no
  `dockerId` is skipped; overlapping passes never double-spawn; `start()` sweeps
  at startup and on a child exit; owner-node exits are ignored; `stop()`
  unsubscribes.

## Honest gaps to carry into the review handoff

- The supervisor is only exercised against a fake orchestrator. Nothing proves a
  *real* respawned child rejoins the borrower's cadre — that needs the
  cross-package `cadre-host-node-donation` integration scenario, out of scope
  here and worth flagging to the reviewer.
- `backlog/debt-failed-respawn-strands-donated-workdir` is now reachable: the
  give-up path is exactly the "failed re-spawn left the orchestrator with no
  handle" case that ticket describes, so `giveUp`'s `stopContainer` is expected
  to throw "Container not found" and is caught and logged. The workdir is
  therefore leaked in that case. Mention it; do not fix it here.
- The startup sweep and the stale-`awaiting_seed` reap both run at boot and can
  interleave. This is believed safe because `DonationService.respawn` re-reads
  the record and refuses any non-`awaiting_seed`/`seeded` status, so a
  just-reaped record cannot be resurrected — but that reasoning has not been
  exercised by a test.
