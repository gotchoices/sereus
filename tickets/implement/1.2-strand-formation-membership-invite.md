# Formation admits the joining party as its own member

Second ticket of the party-identity chain (after `strand-party-member-key`). The founder now has its own identity; this ticket gets the **joiner** one. The bring-up-side redemption and device binding are the next ticket (`strand-node-binds-member-peer`) — this ticket ends with the invitation delivered and the joiner's party key persisted.

## The gap

A closed-strand join today delivers only the shared `MemberPrivateKey`. The joining party never mints a key of its own and never gets a `Strand.Member` row — it *is* the founder, as far as the strand can tell. The strand schema already has the right admission flow (`Strand.Invite` issued by a manager, redeemed once via `consumeInvite`); production never uses it.

## Design (settled)

**Ride the strand's own invite flow on the formation result — no contact-message change, no control-schema change.** The production closed-strand join is the **bound** formation path (`StrandFormationManager.provisionAsResponder`, `'bound'` branch): the responder is the founder party, its host strand already exists and is normally running, and (after the previous ticket) its machines hold the founder party key. So:

- **Responder, bound closed path only**: after token + disclosure validation passes, issue a single-use strand membership invitation against the live host strand — `issueInvite(strandDb, { managerKeyPair: founderPartyKeyPair, expiration: now + INVITE_TTL })` — and return it in the provision result. `FormationProvisionResult` gains `membershipInvite?: { inviteKey: string; invitePrivateKey: string }`. Same disclosure timing as `memberPrivateKey`: a rejected redemption discloses nothing. Suggested `INVITE_TTL`: 7 days (an exported constant) — long enough for a slow joiner to bring its strand node up, short enough that a lost formation result does not leave a live bearer credential forever.
- The formation **listener/session code cannot reach the strand runtime**, so this needs a seam like the existing `resolveStrandAddrs` hook: `CadreNode` wires an `issueMembershipInvite(strandId)` callback into the formation manager that finds the running strand instance's database and the party keypair from the control `StrandPartyKey` row.
- **If the host strand runtime is not live at provision time, the closed-strand redemption fails with a clear, retryable reason** rather than approving without an invitation. Rationale, recorded deliberately: a joiner admitted to a closed strand with no membership would look joined and be unable to ever become a member, and a host that is not running the strand cannot serve the joiner's sync anyway — failing loudly beats a silent half-member. (Open strands and the unbound/consent path are untouched: no members, no invitation.)
- **Joiner**: on an approved formation, `CadreNode.formStrand` (the same place cross-party strand addresses are cached today) does two things keyed by the returned strand id: (1) **mint-or-reuse the party key** — if the control DB already holds a `StrandPartyKey` row for this strand (a re-join), reuse it; otherwise mint via `generateStrandMemberKey` and insert the row; (2) **cache the pending invitation in memory** on the node, per strand, for the bring-up flow in the next ticket to redeem. The pending invitation is deliberately not persisted: today a restarted joiner re-forms from scratch anyway (`backlog/feat-cross-party-strand-addr-durability` owns durability), and re-forming issues a fresh invitation.
- **Reference apps**: no key handling changes — they keep passing `memberPrivateKey` into `addStrand`. Verify the pass-through paths (`cadre-web.ts` `joinViaInvitation`, RN `joinClosedChatStrandFromFormation`) still work and surface the new failure reason legibly.

Why invite-redemption and not manager-admission-at-provision: admission by the responder would need the joiner's public key in the **contact** message (a wire + consent-digest change), a durable responder-side "already admitted" ledger to stay idempotent across restarts and revocations, and reconciliation across the founder party's machines. The invite flow gets single-use, replay-safety, revocation semantics (a revoked party's stale `ConsumedInvite` cannot re-admit; a fresh formation issues a fresh invitation) and joiner-held identity from constraints that already exist and are already tested.

## Edge cases & interactions

- **Re-formation by an existing member party** (lost addresses, app reinstall with intact control DB): party key is reused, a fresh invitation is issued anyway. The next ticket's redemption logic must handle "already a member" (burn, don't re-admit — see there); this ticket just documents that an approved result may carry an invitation the joiner will not spend on a `Member` insert.
- **Concurrent joiners**: each redemption issues its own invitation; `Invite.Key` is a fresh keypair per issue, no collision.
- **Formation result validation**: `validateResponse` / result parsing must treat `membershipInvite` as optional and bounded (two base64url strings); a malformed field from a hostile responder must not crash the initiator.
- **Rejection parity**: assert (as the existing specs do for `partyId`/`strandAddrs`) that a rejected or already-used token discloses no invitation.
- **`issueInvite` failure on the responder** (strand DB write rejected): fail the provision the same way as runtime-absent — do not approve a closed-strand join without an invitation.
- **Invitation expiry vs slow joiners**: expired-invite redemption already rolls back cleanly (`NotExpired`); the joiner's recovery is a fresh formation. State this in the failure-path logging.
- **Security note for the ticket record**: the invite private key travels next to `memberPrivateKey` in the same validated, post-approval frame — same sensitivity class, same handling; it is never written to the responder's or joiner's control DB.
- **Open strands / unbound path**: `membershipInvite` absent; nothing minted, nothing cached.

## Key tests

- Formation-manager unit specs: bound closed approval carries a well-formed `membershipInvite`; bound closed with no live strand runtime rejects with the new reason; open/unbound carries none; rejection parity holds.
- `CadreNode.formStrand` spec: party key minted once and reused on a second formation of the same strand; pending invitation cached and exposed to the bring-up seam.
- Integration: extend `strand-formation-cross-party-seed` (or its harness) to assert the result's invitation redeems on the joiner's strand DB — a real `Strand.Member` row lands under the joiner's own party key, distinct from the founder's. (Full automatic bring-up redemption is the next ticket; here the scenario may redeem explicitly to prove the carried invitation is genuine.)
