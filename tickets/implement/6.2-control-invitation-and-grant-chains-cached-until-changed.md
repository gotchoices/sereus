# Invitation and owner-grant chains kept in memory until they change

## Why

`CadreNode.refreshAuthorizedControlPeers` runs on every local membership write and on every control reconcile pass. When any `CadrePeer` row was admitted by an invitation (`isConsentSeated`), it loads the invitation chain: full scans of `CadreInviteUsage` and `CadreInvite` (`loadInvitationChain`). When any `OwnerKey` row was seated by an owner grant, `syncOwnerAnchor` loads the grant chain: full scans of `OwnerGrantUsage` and `OwnerGrant` (`loadOwnerGrantChain`). These are plain `readRows` calls, so each reaches storage, and on a multi-machine party a read of a held block past its 10 s read-repair window starts a background `/sync` with the sibling. Since invitations are the normal way a machine joins (`cadre-invitations-redeemable-by-any-member`), most parties pay this on every refresh. The `invite` case of `message-cost-accounting` is the one that shows it.

The plan for `control-reconcile-woken-by-changes-reads-once` asked for a cache of verified chain verdicts. This ticket does something simpler that removes the same reads: put the four tables in the membership rows view that `control-membership-rows-cached-until-changed` built for `Revocation`, `CadrePeer` and `OwnerKey`. The verification code does not change at all; only where the rows come from changes.

Why this is safe. All four tables are append-only: `NoUpdate` and `NoDelete` on `CadreInvite` and `OwnerGrant` (`schemas/control.qsql` ~682-684, ~802-804), and the usage tables are insert-only redemption records. Withdrawal is a `Revocation` tombstone over a row that stays, and the chain queries return withdrawn rows anyway (their doc comments say so), so no verdict depends on `Revocation`. A stale view of these tables can therefore only be missing rows that arrived since it loaded, which makes an admission fail to verify (fail-closed) until the change event drops the view or the maximum age passes. It can never authorize anything that a fresh read would refuse.

Tradeoff kept: the ed25519 verifies still run on every refresh (three per invitation-admitted row, plus the grant chain's). That is CPU only, well under a millisecond per row, and the existing NOTE on `hasAnchoredVoucher` already accepts per-call verification. Caching verdicts would also have to track the node-local trusted-owner anchor, which `syncOwnerAnchor` rewrites, and that is more security-sensitive code than the reads are worth.

## Design

- In `ControlDatabase`, add four views next to the existing three, built by the same `membershipView(sql, label)` helper: `CadreInvite` (`CADRE_INVITE_SELECT_SQL`), `CadreInviteUsage` (the select now inline in `queryCadreInviteUsages`; hoist it to a constant beside the others), `OwnerGrant` (`OWNER_GRANT_SELECT_SQL`), `OwnerGrantUsage` (hoist likewise). Register each under its qualified name in `membershipViews`, so the existing subscription in `watchMembershipTables` and `invalidateMembershipViews` cover them with no other change.
- `queryCadreInvites`, `queryCadreInviteUsages`, `queryOwnerGrants`, `queryOwnerGrantUsages` read through `readMembershipRows(view, retry)` and map to fresh row objects, as `queryCadrePeers` does. Their `retry` contract is unchanged.
- Leave plain SQL where it is plain today: `countCadreInviteUsage` / the owner-grant usage count (index reads that are pre-checks), `queryCadreInvite` and any other point read, `listCadreInviteStatuses` unless it is already a full scan of `CadreInvite` (if it is, it may derive from the view; decide by reading it, and say which in the handoff).
- Rename nothing. Update the docs that name "the three tables": `readMembershipRows`' doc, the `membershipViews` field doc, `membership-view.ts`'s module doc if it says three, and `docs/architecture.md` → "Membership rows view" (list the seven tables, and add one sentence saying why the four chain tables are safe to serve stale: append-only, so a stale copy only lacks rows).
- Remove the NOTEs that this ticket answers: `loadInvitationChain`'s "memoise verified pairs" NOTE and the grant-chain NOTE in `syncOwnerAnchor` ("two whole-table reads per membership refresh"). Replace each with one line saying the rows come from the membership view, so they reach storage only after the table changed or the view's maximum age passed.

## Edge cases & interactions

- **Chain rows that arrive after the `CadrePeer` row they prove.** The first refresh finds no usage row and does not authorize the machine. The view load touches the chain tables, which arms their replicated-change bridge, so the usage row's arrival drops the view. Today the gate is re-checked on the next reconcile pass; that does not change in this ticket. Verify by inspection.
- **A load served by the committed-read path** is not kept (existing rule), so a chain table first read during a locked write body stays uncached for unlocked readers until a later load. Same as the existing three tables; no change.
- **Redemption under the write lock.** Readers that hold the write lock with an explicit transaction open already bypass the view (`readMembershipRows`). Check by reading every caller of the four queries (`cadre-node.ts` `loadInvitationChain`, `loadOwnerGrantChain`, `planMachineRemoval` ~9157, and any in `control-database.ts` / `seed-bootstrap.ts` / `cadre-invite-protocol.ts`) that none relies on seeing its own uncommitted insert through a path that would not bypass.
- **Shared rows.** The kept rows are shared between callers; every query must build fresh objects and no caller may mutate them, as for the existing three. Verify by inspection of the four mapping functions.
- **Specs that rig SQL.** `control-read-retry.spec.ts` and `control-read-routing.spec.ts` empty the views in `beforeEach` because a warm view issues no SQL. If either rigs reads of these four tables, it is already covered by that reset; if another spec rigs them, add the same reset there.
