# Remove the Revocation ledger marker's filing path

## Why

The marker, `('Revocation', 'ledger', 'opened')` in `CadreControl.Revocation`, exists only to give that table a collection, so reads of it stop consulting the cohort (`ControlDatabase.openRevocationLedger`'s doc comment). `control-collections-created-at-cadre-founding` commits every control table's empty collection at genesis, so on any party founded from then on `Revocation` has a collection before the first membership read. Reading the callers: the only reader of the marker's presence is the filing path's own guard (`revocationLedgerFiled`); every other mention is a reader skipping the row. Nothing else depends on it.

## Design

**Remove the writer.** Delete `ControlDatabase.openRevocationLedger`, `revocationLedgerFiled`, `REVOCATION_LEDGER_CONFLICT`, `isRevocationLedgerConflict`; `SeedBootstrapService.openRevocationLedger`; `CadreNode.openRevocationLedgerIfDue`, the `revocationLedgerOpened` flag and the filing step (with its accepted-tradeoff NOTE) in `runReconcileControlCohort`; the `RevocationLedgerOpenResult` type. Drop helpers that become unused (lint will name them).

**Keep the readers' skip.** Parties founded before the prereq hold a marker row, and `queryRevocations` must keep skipping it: without the skip the reap sweep and the re-issue sweep would see a row whose `TableName` is not a guarded table (`RevocationRow.tableName` is typed `RevocableTable`). So `REVOCATION_LEDGER_MARKER` stays, re-documented as "a row that parties founded before `control-collections-created-at-cadre-founding` may hold; nothing files it now", along with the skips in `queryRevocations` (~2017) and the type at ~3197 if still used.

**Keep the schema branch.** `RowIsGone`'s last branch admits the marker. Removing it changes the schema's hash, which requires a `CONTROL_SCHEMA_VERSION` bump and a fixture (`control-schema-versions.spec.ts`), and until `control-store-migrates-on-start` lands a changed CHECK refuses every existing store. Comment edits do not change the hash (the spec strips comments), so update the `Revocation` table comment in both `control-schema.ts` and `schemas/control.qsql` to say the branch admits a row older parties hold and nothing files it now. Add at the branch: `-- NOTE: drop this branch, REVOCATION_LEDGER_MARKER and the readers' skip together with the next CONTROL_SCHEMA_VERSION change that already needs a migration.` (A tripwire, not a ticket: it is free only when a version change is happening anyway.)

**Comments that describe the cost of a missing `Revocation` block.** Rewrite each listed in `files:` to the current fact: `Revocation` has a collection from genesis on parties founded since the prereq; a party founded earlier that never filed the marker keeps consulting on each read until its first tombstone. Drop sentences that only explain the marker. Keep each comment's remaining point.

## Edge cases & interactions

- **A party founded before the prereq that never filed the marker** (its owner never had a connected reconcile pass) now never gets a `Revocation` collection until its first removal, and keeps paying one cohort consult per `Revocation` read. Accepted: no backwards compatibility is owed (AGENTS.md), and the cost is today's for such a party. Say so in the docs, not in code.
- **A party founded before the prereq that holds a marker.** Every reader still skips it; the reap and re-issue sweeps never see it. By inspection of `queryRevocations`.
- **`queryRevokedStamps` and the guarded tables' `NotRevoked` checks** filter on their own `TableName`, so the marker never matched them. Unchanged; by inspection.
- **Owner approval prompts.** The marker was one of the background writers that open their own approval (`docs/architecture.md` ~242); one fewer. By inspection.
- **`control-write-degraded-cohort-member`** files the marker in `beforeAll` so that A's `revocation-ledger-open` write cannot be the write that stalls against the delayed member. With no such write, delete that step and its comments; the scenario's write under test is unchanged. Run the scenario once to confirm it still passes.
- **`control-reconcile-woken-by-changes-reads-once`** restructures `runReconcileControlCohort`. It no longer moves the marker filing (its item was dropped in favour of this ticket); if it has landed first, delete the filing wherever it moved it.
