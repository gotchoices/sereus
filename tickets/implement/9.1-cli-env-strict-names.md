# Strict `CADRE_*` environment variables for cadre-cli

## Decision (settled)

Same maintainer decision as `cli-config-strict-validation` (2026-09-28, strict): an unrecognised `CADRE_*` variable fails start, naming it. This ticket builds on that one's pipeline (`loadValidatedConfig(path, env)`, provenance-attributed errors) and covers what it leaves out: variable *names*, and how variable *values* are turned into typed config values.

## Today

- `applyEnvironmentOverrides` loops over `ENV_MAPPINGS` and reads only those names. Any other `CADRE_*` variable — a typo (`CADRE_LISTEN_ADDR`), a retired name — is never looked at. The one exception is `rejectRetiredIdentityEnv` (`CADRE_IDENTITY_PROTOBUF`), a one-off.
- `parseEnvValue` picks the value's type from the variable's *name*: `_NODES`/`_ADDRS` suffix → list, name containing `_ENABLED` or `_RELAY` → boolean. Booleans are `value.toLowerCase() === 'true' || value === '1'`, so `CADRE_ENABLE_RELAY=yes` silently means `false`.
- Three variables the Docker image and `docker-compose.yml` set are consumed only by `entrypoint.sh` when it writes `cadre.yaml`: `CADRE_STORAGE_QUOTA`, `CADRE_LATENCY_HINT`, `CADRE_STRAND_WATCH_INTERVAL`. Outside Docker the CLI ignores them. The integration harness's `ensureConfigFile` comment works around exactly this.
- `docker/env.example` documents `CADRE_ENROLLMENT_TOKEN`, `CADRE_PROVIDER_API`, `CADRE_PROVIDER_API_KEY`. Nothing in the repo reads them.

## Design

### One registry of names (`config/env.ts`, new)

Every `CADRE_*` name the node process may legitimately see, in four groups:

- **Config overrides** — `ENV_MAPPINGS` (moves here from `types.ts`, still exported), each entry now `{ path, kind }` with an explicit `kind` instead of the name heuristics:

  | kind | parse | failure |
  |---|---|---|
  | `string` | value as-is | — |
  | `list` | split on `,`, trim, drop empties (today's behaviour) | — |
  | `boolean` | `true`/`false`/`1`/`0`, case-insensitive, trimmed | anything else → error naming the variable and the accepted spellings |
  | `number` | `Number(trimmed)`, must be finite | error naming the variable |
  | `strandFilter` | existing `parseStrandFilterEnv` | existing |
  | `json` | existing `parsePushEnv` (rename to fit if it helps) | existing |

  Add three mappings so the variables the image already sets mean the same thing inside and outside Docker: `CADRE_STORAGE_QUOTA → storage.quotaBytes` (number), `CADRE_LATENCY_HINT → hibernation.defaultLatencyHint` (string), `CADRE_STRAND_WATCH_INTERVAL → strandWatchInterval` (number). Inside Docker the entrypoint already wrote the same values to the file, so the override is a no-op there. The resulting value is still checked by the config validator, attributed to the variable.
- **Read directly by CLI commands** — `CADRE_HEALTH_PORT`, `CADRE_METRICS_PORT`, `CADRE_ADMIN_PORT`, `CADRE_OWNER_KEYS`, `CADRE_SEED_TOKEN`, `CADRE_STARTUP_TOKEN`. Export them as named constants from `env.ts` and use those constants at the existing read sites (`start.ts`, `status.ts`, `enroll-add.ts`, `admin-client.ts`, `admin-server.ts`, `health.ts`) so a read site cannot name a variable the registry lacks without a compile error. The parsing at those sites is unchanged.
- **Read by launchers around the CLI, not by the CLI** — `CADRE_CONFIG` (systemd unit `contrib/cadre-node.service`), `CADRE_CONFIG_FILE` and `CADRE_DEBUG` (`docker/entrypoint.sh`). Known, so their presence is not an error.
- **Retired** — map of name → message. `CADRE_IDENTITY_PROTOBUF` moves here with its current message ("set CADRE_KEY_FILE instead…"); `rejectRetiredIdentityEnv` is deleted. Keep its transitional `NOTE:`.

Names beginning `CADRE_HOST_` are cadre-host's own settings (`CADRE_HOST_DATA_DIR`, `CADRE_HOST_PORT`, `CADRE_HOST_UPDATE_*`) and are skipped: a shell or unit that runs both programs may carry them. cadre-host already strips every `CADRE_*` variable from its children's environment (`scrubbedParentEnv`), so its spawned nodes never see them either way.

### The check

`checkEnvNames(env)` runs at the start of `applyEnvironmentOverrides` (so every path through `loadValidatedConfig` — `start`, `status`, the one-shot strand commands — gets it). For every `CADRE_*` key with a non-empty value (an empty value means "unspecified", matching the override loop, so compose's `CADRE_X=${CADRE_X:-}` stays harmless):

- retired → error with its message;
- not in any group and not `CADRE_HOST_*` → error `Unknown environment variable CADRE_LISTEN_ADDR (did you mean CADRE_LISTEN_ADDRS?)`, suggestion by the same nearest-key helper the config validator uses.

Collect all bad names and throw once, listing each — same convention as the config validator.

### Clean-ups this forces

- Delete the three unread variables from `docker/env.example` (and its "Provider Integration" heading). Leaving them documented would now make an operator who follows the example unable to start a node.
- Update the integration harness `ensureConfigFile` comment: `strandWatchInterval` and `hibernation.defaultLatencyHint` now have mappings. Leave the file content alone unless it becomes redundant with the harness env; if the harness env sets `CADRE_HIBERNATION_ENABLED` and the image-default layer sets the other two, the file can shrink to `{}` — only do that if the scenario still passes.
- README → Environment Variables table: add the three new mappings; add a line that unrecognised `CADRE_*` variables fail start and which non-override variables are recognised.

## Edge cases & interactions

- **Every variable the repo's launchers set must be in the registry**, or the CLI rejects its own deployments: Docker `Dockerfile` `ENV`, `docker-compose.yml`, `entrypoint.sh` (including the ones it exports: `CADRE_KEY_FILE`, `CADRE_NODE_STATE_DIR`), `contrib/cadre-node.service`, `contrib/cadre-install.sh`, cadre-provider `service/container-env.ts`, cadre-host's child env block in `host-process-orchestrator.ts` (`CADRE_STARTUP_TOKEN`, `CADRE_HEALTH_PORT`, `CADRE_METRICS_PORT`, `CADRE_LISTEN_ADDRS`, `CADRE_SEED_TOKEN`, `CADRE_NODE_STATE_DIR`, `CADRE_OWNER_KEYS`). Verified by the registry test below (cadre-host's block by inspection — that file also has the constant `CADRE_ENV_PREFIX`, which a token scan would misread).
- **`cadre start --identity-file`** writes `CADRE_KEY_FILE` into `process.env` before config resolution — a registered name, fine.
- **Boolean strictness vs existing values**: the Dockerfile and compose set `CADRE_HIBERNATION_ENABLED=true`; compose's `CADRE_ENABLE_RELAY=${CADRE_ENABLE_RELAY:-}` is empty and skipped. Inspection of Dockerfile/compose/env.example values against the new accepted spellings.
- **Separators-only list value** (`CADRE_LISTEN_ADDRS=,`): keep the existing `NOTE:` in `parseEnvValue`; behaviour unchanged.
- **Tests that set `process.env` directly** (`env-override-empty.spec.ts`, `identity-key.spec.ts`, `push-config.spec.ts`, `strand-filter.spec.ts`): a leftover `CADRE_*` var from one test can now fail another. Prefer the `env` parameter; where a test must set `process.env`, it restores it in `afterEach`.
- **A developer shell or CI runner with stray `CADRE_*` exports** now fails `cadre start` / the CLI test suite. That is the decided behaviour; the error names the variable.

## Tests

- **Unknown and retired names are rejected**: `env` with `CADRE_LISTEN_ADDR=/ip4/0.0.0.0/tcp/1` → error naming it and suggesting `CADRE_LISTEN_ADDRS`; existing "rejects the retired CADRE_IDENTITY_PROTOBUF" test keeps passing through the general mechanism.
- **Boolean parsing is strict**: `CADRE_ENABLE_RELAY=yes` → error naming the variable (today: silently `false`).
- **Registry covers the repo's launchers**: read `docker/Dockerfile`, `docker/docker-compose.yml`, `docker/entrypoint.sh`, `docker/env.example`, `contrib/cadre-node.service`, `contrib/cadre-install.sh`, and cadre-provider's `src/service/container-env.ts`; extract `\bCADRE_[A-Z0-9_]+\b`; assert each is registered, retired, or `CADRE_HOST_*`. This is the one test that stops a future launcher variable from turning into a node that refuses to start in production. Read-only file reads within this repo.
