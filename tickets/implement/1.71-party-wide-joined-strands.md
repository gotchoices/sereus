# Joins from other parties are recorded party-wide

## Behaviour today

A strand joined from another party (by `formStrand`, or by `addStrand` of a row handed over directly) is remembered only in the joining machine's `KeyStore` (`JoinedStrandStore`). The strand watcher offers those records beside the control `Strand` rows (`JoinedStrandRows.withControlRows`). No other machine of the party learns of the join. So an always-on machine with `hostUnclaimedStrands` never hosts a replica of it, and a lost phone takes the party's copy with it.

The prereq `joined-strand-control-table` adds `CadreControl.JoinedStrand` (owner-signed insert and delete, tombstoned, reapable) and its `ControlDatabase` methods. This ticket makes nodes use it.

## Design

### Two records, one authority

- The **party-wide record** is the `JoinedStrand` row. Once it exists it is the authority. Every machine's watcher offers it, a replica host launches it, and the party's other phones get `strand:discovered` for it (the React Native reference app claims such a row, as it claims the party's own strands).
- The **machine-local record** (`JoinedStrandStore`, in the KeyStore) becomes a queue of joins **not yet published**. Joining records locally first, exactly as today: `formStrand` still throws if it cannot, and `addStrand` still warns and continues. Publication happens later. Once the party-wide row is visible locally, the local record is forgotten. A local record therefore always means "this machine joined it and the party does not know yet", which removes any ambiguity between "never published" and "removed elsewhere".

### Publication: in the connected reconcile pass, owners only

Publish from `reconcileControlCohort`'s connected branch (`getControlConnectionCount() > 0`), beside the reap sweep and `openRevocationLedgerIfDue`. It is gated on this machine being able to sign as an owner (the same `seedBootstrapService?.canAuthorize()` gate the ledger marker uses). The reason is written there already: a control write committed while alone is local-only and forks the collection (`tickets/blocked/forked-control-collection-sync-livelocks.md`). Nothing here is urgent. The pass runs every 15 s, so a join reaches the party within one pass of the machine being connected.

For each local record, the pass does this:
- If this party's control database already names the id (a `Strand` row or a `JoinedStrand` row), forget the local record. There is nothing to publish.
- Otherwise insert the `JoinedStrand` row (owner-signed), then forget the local record.
- An insert refused because the id is already seated (the prereq's id-conflict classifier: a sibling published the same join) counts as success. Any other failure is logged, the record is kept, and the next pass retries.

A machine that is not an owner never publishes, so its joins stay machine-local, as today. Say so in the docs. Do not log it on every pass.

### Reading: union with fallback

`JoinedStrandRows` (rename it if its role outgrows the name) takes a ledger seam alongside the store. `withControlRows(control)` returns rows in this precedence, one row per id:

1. control `Strand` rows (the party's own strands);
2. `JoinedStrand` rows not named by (1);
3. local records and `keptForSession` entries not named by (1) or (2).

A local record named by (1) or (2) is forgotten. This is the existing "control row wins" drain, widened to cover (2), and it also cleans up after a crash between a publish and the local forget.

The `JoinedStrand` read is separate from the `Strand` read and gets its own last-good fallback, the same one the local store's list has today. A failed read offers the last list that succeeded (empty at first) and never fails the poll. **This is required, not optional:** the watcher's poll is one try/catch (`strand-watcher.ts` `poll`), so a throwing read would stop an isolated machine from offering even its own strands. Such a machine fails `cohort-unreachable` on a table block it never received, which is the normal state for a party that has never joined anything.

Suggested seam, defined in `joined-strand-store.ts` so the module stays free of the runtime and is built in `cadre-node.ts` over `ControlDatabase` plus the owner signing key:

```ts
/** The party-wide joined-strand table (`CadreControl.JoinedStrand`), as the node's control database exposes it. */
export interface PartyJoinedStrandLedger {
	/** Every party-wide join, as offerable rows (`FounderOwnerKey: null`). */
	list(): Promise<StrandRow[]>;
	/** Whether this party's control database names `strandId`, as its own strand or as a party-wide join. */
	names(strandId: string): Promise<boolean>;
	/** Owner-signed insert. Resolves when the row landed or a sibling's identical join already holds the id. */
	publish(record: JoinedStrandRecord): Promise<void>;
	/** Owner-signed delete + tombstone; false when there is no row. Throws when this machine cannot sign. */
	remove(strandId: string): Promise<boolean>;
}
```

The adapter reads `this.controlDatabase` at call time, not at construction time, so start-up order does not matter.

### Leaving is party-wide

`forgetJoinedStrand(strandId)` now removes the `JoinedStrand` row (owner-signed, with tombstone) first, then forgets the local record, the strand peer book entries and the session-kept entry, then `stopStrand`s. Every other machine's watcher then sees the row gone and detaches the strand (`handleStrandRemoved`, which emits `strand:stopped`). The always-on replica stops with them. A machine that was offline at the time drops the stale row through the reap branch once the tombstone reaches it. This mirrors `unpublishStrand` for the party's own strands, and like `unpublishStrand` it writes at once rather than waiting for the reconcile pass, because the user asked for it.

- **Rejected: leave stays per-machine.** A per-machine forget cannot suppress a party-wide row except through a per-machine suppression list. And a "leave" after which the always-on machine keeps hosting the strand forever is not a leave. The per-machine options remain: `stopStrand` for this session, and `strandFilter`.
- A non-owner machine cannot remove the row. When a row exists and this machine cannot sign, `forgetJoinedStrand` throws an error saying that leaving for the whole party takes an owner machine and that `stopStrand` stops it on this one. When no party-wide row exists (a join still local-only), it behaves as today.
- `StrandPartyKey` is untouched. The party's `Strand.Member` row stays in the strand (a leave never told the other members), and a later re-formation reuses the same identity. Keep `forgetJoinedStrand`'s doc comment saying the other members are not told.

### Removal from a strand (`strand:revoked`) removes the party-wide record

Today `forgetRevokedJoin` forgets the local record after this session, so the next start does not re-attach a strand this party was removed from. Keep that outcome party-wide. The machine that observes the revocation keeps offering the strand for its own session (the existing `keptForSession`, now seeded from a local record or from the last party-wide list) and queues the id for removal. The connected, owner-gated reconcile pass removes the queued `JoinedStrand` rows, and an in-memory queue is enough. If the process dies first, the next start relaunches the strand, the revoked-peer gate raises `strand:revoked` again, and the id is queued again. A `formStrand` or remembered `addStrand` of an id clears any removal queued for it, so a re-join is never deleted by a stale revocation.

- **Accepted tradeoff, to be recorded as a `NOTE:` at `forgetRevokedJoin` and in `docs/strands.md`.** A sibling machine that has not yet raised `strand:revoked` itself detaches the strand when the removal reaches it (`strand:stopped`), instead of keeping it running for the session. The docs promise that nothing is stopped on the removed machine's behalf, so this weakens that promise for siblings. It was weighed against the alternative, which is a party-wide record that brings a revoked strand back on every start of every machine. Revisit if apps need the "you were removed" screen on every device: the sibling could re-check its own revocation state (`refreshRevocationEnforcement`) before detaching a vanished joined row.

### What else changes

- `rememberForeignStrand`: replace the `queryStrand` check with `ledger.names` (either table). Otherwise it is unchanged.
- `formStrand` / `rememberFormedStrand`: unchanged apart from clearing a queued removal. Publication happens in the reconcile pass.
- `initializeJoinedStrandStore`: build the rows view with the ledger adapter.
- **Keep `cadre-node.ts` growth small.** It is 8131 lines (`wc -l`, 2026-09-28) and has its own backlog ticket (`debt-cadre-node-single-file-size`). The logic belongs in `joined-strand-store.ts`: union, drain, publish loop and removal queue. `cadre-node.ts` gets the adapter and the call sites.

## Edge cases & interactions

- **Isolated machine, `JoinedStrand` block never received.** The read fails, the fallback is the last good list, and the machine's own `Strand` rows and local joins are still offered. Verify with the unit test below (a throwing ledger list).
- **Crash between publish and local forget.** On the next poll the local record is superseded by the row and forgotten. Verify by inspection, since it is the same code path as the drain.
- **Two machines of the party joined the same strand** (both phones redeemed invitations). The second insert hits the id conflict, is treated as published, and its local record is forgotten. Types and secrets match because both come from the same founding party. If they ever differ, the party-wide row wins. Verify by inspection.
- **A `JoinedStrand` row and a `Strand` row with the same id** (the party both founded and joined it, which is contrived). The `Strand` row wins, and the stale `JoinedStrand` row is left in place: a watcher poll must not make owner-signed deletes. Put a `NOTE:` in the union code: if the party later unpublishes, the join row resurfaces; if that is ever seen, remove the join row inside `unpublishStrand`.
- **Leave racing a sibling's unpublished local join.** A sibling that joined the same strand and has not yet published publishes after the leave, and the strand comes back party-wide. This is contrived, since it needs two devices joining the same strand within one reconcile interval of a leave. Put a `NOTE:` in the publish loop.
- **Revocation observed on two machines.** Both queue the removal. The second finds no row and does nothing, or loses the tombstone insert race, logs it, retries, and finds no row. Verify by inspection.
- **Non-owner machines** never publish and never remove. A revoked strand whose row no owner machine runs stays party-wide until an owner leaves it. Document this and do not engineer for it.
- **Replica of a closed joined strand.** `resolveStrandPartyKey` finds the `StrandPartyKey` row that `formStrand` already seats (`adoptFormationMembershipInvite`), so the replica's membership reconciler seats its own `MemberPeer`. An `addStrand` join that passed an explicit `partyMemberPrivateKey` never persisted it, so a replica launched from the party-wide row has no party key and seats no `MemberPeer`. It still stores and serves, because the revoked-peer gate is a deny set, not an allow set. Verify by inspection, and state it in the storage-replica docs.
- **The party's other phones** receive `strand:discovered` for each party-wide join. The RN reference app auto-claims open rows and closed rows that carry a key, so a second phone joins the strand. That is the intended multi-device behaviour. Document it and do not gate it.
- **`sAppId` strand filter.** Joined rows carry no sApp id, so they take the same provisional path as the party's own rows (the replica reads it from `Strand.Header`). There is nothing new to do.
- **`stopStrand`** stays per-machine and per-session. The watcher's suppression is cleared on absence, as today.
- **Poll cost.** There is one more control read per watcher poll (5 s), and for most parties it reads a never-written block that consults the cohort. Park a `NOTE:` at the adapter's `list`: if poll cost shows up in a device profile, cache the list and re-read it on the reconcile cadence.
- **cadre-cli / cadre-host always-on nodes** use a memory joined-strand store and never join anything themselves, but they read the party-wide table through the watcher, which is the point of this ticket. There is nothing to change there.

## Tests

Extend `joined-strand-store.spec.ts`. Use `MemoryJoinedStrandStore` and a plain in-test `PartyJoinedStrandLedger` over arrays, which is a stand-in for the seam and not a mock of `ControlDatabase`. Write at most two cases:

- **Union and drain:** control rows `[A]`, ledger rows `[A, B]`, local records `[B, C]`. `withControlRows` returns A (the control version), B (the ledger version) and C. After that, the store holds only C. When the ledger's `list` then throws, B is still offered.
- **Publish loop:** local records `[D, E]`. The ledger accepts D and throws on E. After the pass the store holds only E, and the ledger holds D.

The end-to-end path (a phone joins, the always-on machine hosts it, the phone leaves, the always-on machine stops) is the next ticket's integration scenario. Do not add a node-level unit test for it.
