# Extract the strict config checker into `@serfab/config-check`

## Why

`cli-config-strict-validation` gave cadre-cli a hand-written strict validator (`packages/cadre-cli/src/config/schema.ts`, 461 lines by `wc -l`; about 250 of them are a generic mechanism, the rest are cadre-cli's own field tables). The maintainer decided on 2026-09-28 that cadre-provider's config file must be checked with the same strictness (the follow-up ticket `provider-config-strict-validation`).

cadre-provider cannot import cadre-cli or cadre-core: both pull in libp2p, optimystic and quereus, and the provider deliberately takes no dependency on cadre-core (`packages/cadre-provider/src/config/types.ts` header; `docs/architecture.md`, trusted-owner anchor entry). Copying ~300 lines of mechanism into the provider would break the project's DRY rule for code that is not small, and cadre-host's `host.config.json` reader (`packages/cadre-host/src/installer/config.ts`, a hand-rolled shape check) is a likely third consumer. So the generic part moves into a new workspace package with zero runtime dependencies that both cadre-cli and cadre-provider depend on.

Rejected alternatives:

- **Copy into cadre-provider.** Cheapest now; two copies of the message conventions, the typo suggestion and the `null`-means-absent rule then drift. The provider already carries two small hand-kept duplicates of cadre-core rules (owner-key shape, push completeness), both tens of lines; this would be several hundred.
- **A schema library (zod etc.) in the provider only.** Two validation mechanisms in one repo with different error formats; cadre-cli chose "no schema library" on purpose and its compile-time field-table drift guard would have no counterpart.
- **A dependency-free subpath of cadre-core.** Installing cadre-core still installs its whole dependency graph; the provider's install footprint is the thing being protected.

Cost accepted: one more published package (`yarn pub` chain), one more workspace in the Docker node image, and a stale-build guard target in every suite that runs cadre-cli's compiled output.

This ticket is a **move with no behaviour change**: every cadre-cli error message and every cadre-cli test stays as it is. The additions the provider needs (a free-key mapping checker, hiding values under secret subtrees) belong to `provider-config-strict-validation`.

## The package

`packages/config-check`, name `@serfab/config-check`, version equal to the other workspaces (`1.7.0` today — `release-guard` requires every workspace to share one version). Shape modelled on `packages/cadre-provider` (`type: module`, `main`/`types`/`exports["."]` to `dist/index.js`, `files`, `build`/`typecheck`/`clean` scripts, `tsconfig.json` + `tsconfig.build.json` + `tsconfig.typecheck.json`, tabs per `.editorconfig`). **No runtime `dependencies`.** No `node:` imports and no `NodeJS.*` types: environment maps are typed `Readonly<Record<string, string | undefined>>` so the package stays usable from any runtime and needs no `@types/node` at runtime.

No test suite of its own: its behaviour is pinned through cadre-cli's `config-validation.spec.ts`, `env-override-empty.spec.ts` and friends, which keep running unchanged. Without a `test` script, check that root `yarn test` (`yarn workspaces foreach -A ... run test`) skips it rather than failing; if it does not, add `"test": "vitest run --passWithNoTests"` the way cadre-provider has.

A short `README.md` (what it is, that it exists for Sereus's own packages, the public functions in one list). No doc summary beyond that.

### What moves (from cadre-cli, verbatim apart from the two generalisations below)

From `src/config/schema.ts`: `Problem`, `ValidationContext`, `Checker`, `FieldTable`, `ObjectOptions`, `isPlainObject`, `kindOf`, `describeValue` (with its `NOTE:`), `MAX_ECHOED_CHARS`, `stringValue`, `nonEmptyString`, `secretString`, `booleanValue`, `numberWhere` (now exported — the provider needs port ranges), `finiteNumber`, `positiveNumber`, `nonNegativeNumber`, `nonNegativeInteger`, `oneOf`, `arrayOf`, `objectOf`, `refine`, `joinPath`, `rejectKey`, `reportMissing`, and the entry-point helpers `checkRoot`, `sourceOf`, `isPathPrefix`.

All of `src/config/nearest-key.ts`.

From `src/config/env.ts` / `src/config/loader.ts`, the parts that do not know about `CADRE_*`: `specifiedEnv`, the `boolean` / `number` / `list` text parsers (`parseBoolean`, `parseNumber`, the comma-split list parser with its `NOTE:`), `setNestedValue` + `cloneBranch`, and the override loop of `applyEnvironmentOverrides` as a generic function over a mapping table (see below).

**Stays in cadre-cli:** every field table (`identity`, `controlNetwork`, `storage`, `network`, `hibernation`, `nodeState`, the push tables typed against cadre-core's credential types, `root`), `RETIRED_IDENTITY_KEYS`, `identityKeyFile`, the `strandFilter` checker, `ENV_MAPPINGS`, `COMMAND_ENV`, `LAUNCHER_ENV`, `RETIRED_ENV`, `checkEnvNames`, `parseStrandFilterText`, `parseJsonObject`, `loadIdentityKey`, `resolveConfig` and the rest of the loader. cadre-cli's `validateConfig(tree, provenance, configPath)` and `applyEnvironmentOverrides(raw, env)` keep their current signatures and become thin wrappers.

### The two generalisations

1. **Who can supply a missing key.** `ValidationContext.missing` today calls cadre-cli's `envVarsFor` (a reverse lookup in `ENV_MAPPINGS`). In the package the context takes it as an optional constructor argument, `suppliersOf?: (keyPath: string) => readonly string[]` (default: none). cadre-cli passes `envVarsFor`, so `controlNetwork.partyId is required (or set CADRE_PARTY_ID)` is unchanged.

2. **The entry point.** A generic

   ```ts
   export interface ValidateOptions {
   	/** Named in every problem the environment did not cause. */
   	configPath: string;
   	/** Dotted path the environment wrote → the variable that wrote it. */
   	provenance?: ReadonlyMap<string, string>;
   	/** Variables that could supply a missing key, for "is required" messages. */
   	suppliersOf?: (keyPath: string) => readonly string[];
   }
   export function validateTree<T>(tree: unknown, root: Checker<T>, options: ValidateOptions): T;
   ```

   holding what `validateConfig` / `checkRoot` / `sourceOf` do today (empty tree is an empty mapping, non-mapping root is one problem, one `Error` listing every problem prefixed `Environment variable X:` or `Config <path>:`).

   And a generic environment writer:

   ```ts
   export interface EnvOverride {
   	/** Dotted config path the variable writes. */
   	readonly path: string;
   	/** Text → value written at `path`; throws naming `name` when the text cannot be read. */
   	readonly parse: (text: string, name: string) => unknown;
   }
   export interface OverrideResult { tree: unknown; provenance: ReadonlyMap<string, string> }
   export function applyEnvOverrides(
   	raw: unknown,
   	env: Readonly<Record<string, string | undefined>>,
   	overrides: Readonly<Record<string, EnvOverride>>,
   	onApply?: (variable: string, text: string) => void,
   ): OverrideResult;
   ```

   plus the exported parsers (`parseBooleanEnv`, `parseNumberEnv`, `parseListEnv` or similar names) and `specifiedEnv`. cadre-cli keeps `ENV_MAPPINGS` with its `kind` field (the README and other code read it) and maps each kind to a parser when calling; it runs `checkEnvNames` first and passes an `onApply` that keeps today's debug line with `CADRE_PUSH` redacted. Exact names are the implementer's call; the split (package knows nothing of `CADRE_*`, cadre-cli knows nothing of how a path is written) is not.

## Wiring the new workspace

- `packages/cadre-cli/package.json`: `"@serfab/config-check": "workspace:^"` in `dependencies`; `yarn install` at the root.
- cadre-cli imports from `@serfab/config-check` instead of `./schema.js` / `./nearest-key.js`; delete `src/config/nearest-key.ts`; `src/config/index.ts` keeps exporting `validateConfig`.
- **Stale-build guard targets.** cadre-cli's suite now runs `@serfab/config-check`'s compiled `dist`. Add `{ packageName: '@serfab/config-check', distEntry: 'dist/index.js', location: 'workspace' }` to `packages/cadre-cli/test/global-setup.ts` `TARGETS` (its `build-targets.spec.ts` fails until you do). Suites that reach cadre-cli's `dist` transitively list their transitive targets by hand and nothing fails when one is missing: grep every `global-setup.ts` for `@serfab/cadre-cli` (today: `packages/cadre-host/src/__tests__/global-setup.ts` and `packages/integration-tests/test/global-setup.ts`) and add the entry there too.
- **Docker node image.** `packages/cadre-cli/docker/Dockerfile` copies only `cadre-core` and `cadre-cli` manifests, sources and `dist` into its four stages, and `packages/cadre-cli/docker/workspace-root.package.json` lists only those two workspaces. Without adding `packages/config-check` to each (manifest in `deps` and `prod-deps`, `src` + tsconfigs in `build`, `dist` + `package.json` in the runtime stage, and the workspaces list), the image builds cadre-cli against a package that is not there. Check `.dockerignore` does not exclude it.
- **Publishing.** Root `package.json`: `"pub:config-check": "node scripts/publish-package.mjs config-check"` and put it **first** in the `pub` chain (before `pub:cadre-cli`; the provider joins in the follow-up). `publish-package.mjs` already passes `--access public`, which a first publish of a new scoped name needs.
- `knip.ts`: add `'packages/config-check': {}` to `workspaces`.
- Docs: add the package to AGENTS.md "Repo orientation" and the package list near the end of `docs/architecture.md`; in `docs/testing.md` nothing about the provider changes yet (it gains its guard in the follow-up).

## Edge cases & interactions

- **Message text is contract.** cadre-cli's specs assert message strings; they must pass untouched. Verified by running them unchanged.
- **Build order.** Root `yarn build` is `foreach -At` (topological), so the new package builds before cadre-cli. A fresh clone that runs only `yarn workspace @serfab/cadre-cli build` fails to resolve the import until the package is built — same as cadre-core today; nothing to add.
- **Stale dist.** Editing `packages/config-check/src` without rebuilding must fail cadre-cli's, cadre-host's and integration-tests' suites up front (the guard targets above). Verified by inspection of the three `TARGETS` lists and cadre-cli's `build-targets.spec.ts` passing.
- **Published install.** A registry install of `@serfab/cadre-cli` must resolve `@serfab/config-check` from its own tarball: run `yarn test:published-smoke-support` and `yarn test:published-check-support`; if a script there enumerates packages by hand, add the new one. `yarn smoke:published` / `yarn check:published` (tarball install of every package) is the end-to-end check — run it if it finishes inside the idle window, otherwise say in the handoff that it was not run.
- **Docker image.** A real `docker build` of `packages/cadre-cli/docker/Dockerfile` is likely too slow for an agent run; if it is, verify the four stages by inspection and say so in the handoff.
- **Cross-platform.** No `node:` import in the package (`yarn lint` + `typecheck` of the package with no `@types/node` in `types` would catch a slip; at minimum grep).
- **Release gates.** `release-guard` checks every workspace shares the version; `check-dep-ranges` only covers `link:` resolutions, so a `workspace:^` range needs nothing there.
