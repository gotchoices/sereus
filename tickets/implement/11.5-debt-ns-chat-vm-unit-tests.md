# Unit tests for `ChatViewModel` on `reference-app-ns`

## Background

`src/chat-vm.ts` (`ChatViewModel`) is the NativeScript chat screen's logic: it polls the active strand's Quereus database every 2 s, keeps an `ObservableArray` of message rows for the ListView, registers the local participant once the strand is writable, and sends messages with a retry key that survives an uncertain failure. None of it is tested. Three rules in it landed without tests because the suite could not load `ObservableArray`:

- the poll's single-flight guard (`readsInFlight` in `refresh()`), from `rn-chat-poll-overlaps-slow-reads`;
- the send rule in `send()`, from `bug-chat-resend-after-uncertain-failure-can-store-message-twice`;
- the retry key's release (`draft` setter, `settlePendingDraft()`), from `bug-chat-retry-key-outlives-the-draft-it-belongs-to`.

## The loading blocker is gone (measured in plan, 2026-09-29)

The earlier record (the stub's own comment, `docs/reference-app-ns.md` → "Unit suite") says `ObservableArray` fails with `ERR_UNSUPPORTED_DIR_IMPORT` because `data/observable-array/index.js` imports `'../observable'` as a directory. Probed with Vitest 4.1.8 on Node 24.2.0 using the package's current alias setup:

- Adding `export { ObservableArray } from '@nativescript/core/data/observable-array/index.js';` to the stub loads the real class with **no config change**. `new ObservableArray()` works, `push`/`splice`/`getItem` behave, and it is `instanceof` the same `Observable` the stub already exports. Vite transforms these files itself rather than handing them to Node, because `@nativescript/core` ships ESM syntax under a `package.json` with no `"type": "module"`. The extra "Sourcemap … points to a source file outside its package" warnings (now three, not one) show that this happens.
- `test.server.deps.inline: [/@nativescript\/core/]` in `vitest.config.ts` also works. It is not needed today. If the full suite ever reproduces the directory-import error, add it and note why at the site.

So: extend the stub by one line. Do not write an `ObservableArray` double.

## Test harness design (decided)

**A real in-memory Quereus database, not a hand-written fake.** `src/chat-operations.ts` runs unmocked against `new Database()` from `@quereus/quereus` with the app's own chat schema applied. That schema comes from `getChatSAppConfig().schema`, read via `vi.importActual('../src/chat-strand')` because the suite mocks that module for `cadre-vm`, wrapped as `declare schema App { … } apply schema App;` the same way `applyAppSchema` in `packages/quereus-plugin-sereus/src/compose-strand.ts` does. The plan probe ran this and got real primary-key and foreign-key refusals. This also covers `chat-operations.ts` and the NS copy of the chat schema, because a query that stops matching the schema fails here. Do not `vi.mock('../src/chat-operations')`, as RN's `use-chat.spec.ts` does. That module is repo-owned, and mocking it would put the tests at the wrong layer.

**A thin decorator over the real database** is the only scripted part. `strand.database.getDatabase()` returns it. It passes `exec`/`eval` through to the real `Database` and gives the test two hooks:

- a gate run before each statement is delegated, which receives the SQL text. The test can hold the statement on a promise it settles by hand, or reject it. Every started statement is recorded so a test can count reads and inserts per database.
- an after-exec hook run once an `exec` has been applied. It throws on the `insert into App.Message` the test picks, which models "stored, then the outcome was lost" (RN's `UncertainDatabase` in `packages/reference-app-rn/test/chat-send.spec.ts`).

Match statements by the table they touch (`App.Message` insert, `App.Participant` insert, the `select Id from App.Message where Id = ?` lookup, the poll's two reads), not by full SQL text. Keep the decorator in the spec file; it has one consumer. Its `as unknown as Database` cast should be the only cast in the file.

**Fake strand.** Extend `fakeStrand()` in `test/stubs/fake-cadre-node.ts` to take an optional database (and `strandId`), so the `as unknown as StrandInstance` cast stays at its one existing site. `database` must be settable to `undefined` and back to model a `'syncing'` joiner becoming writable.

**Cadre VM.** `ChatViewModel`'s constructor calls `getCadreVm()`, which caches a module-level singleton that adopts `getPhoneNode()`. Reuse `cadre-vm.spec.ts`'s pattern: `vi.hoisted` import of `./stubs/fake-cadre-node`, `vi.mock` of `../src/cadre-phone` and `../src/chat-strand`, and a load helper doing `H.reset()` → `H.presentRunningNode()` → put strands in `node.strands` → `vi.resetModules()` → `import('../src/chat-vm')`. Construct `new ChatViewModel(POLL_MS)` directly rather than `getChatVm()`. Peer id is the fake node's `'peer-abc'`. To change which strand the cadre VM offers, mutate `node.strands` and `node.emit('strand:started', …)`. Keep the side-effect `import '@serfab/cadre-core'` at the top so the ~10 s graph load is charged to the import phase (see `cadre-vm.spec.ts`). The existing `test/global-setup.ts` stale-build guard already covers this.

**Time.** Fake only the poll timer: `vi.useFakeTimers({ toFake: ['setInterval', 'clearInterval'] })`, so Quereus and the gate promises run on real microtasks. Tick polls with `vi.advanceTimersByTime(POLL_MS)`, and wait for outcomes with `vi.waitFor` on something observable (row count, `loading`, `error`, statement counts). The plan probe used default fake timers and passed, but faking less is the more robust choice. Always `vm.stop()` and `vi.useRealTimers()` in teardown.

## Tests (one per rule; expected outcomes)

Poll single-flight guard (`refresh()`):
- **Held read:** hold strand A's poll read open, then advance several poll intervals. No second read of A starts: the recorded read count for A's database is unchanged.
- **Failure releases the guard:** make A's read reject. `error` shows the message. The next tick starts a new read, and when it succeeds `error` is `''`.
- **Re-attach reads the new strand at once:** while A's read is held, make the cadre VM offer strand B instead and call `vm.start()` (what the page's `navigatedTo` does). B's read starts immediately, before A's settles. **Do not assert on the message list after A's held read later settles.** Today that late result overwrites B's list, which is the defect filed as `bug-ns-chat-shows-previous-strand-messages-after-switch`. Pinning either outcome here would be wrong.

Participant registration (`attach()` / `register()`):
- **Held insert:** hold the `App.Participant` insert. Later polls start no second participant insert for that strand.
- **Failed insert is retried:** reject the first `App.Participant` insert. A later poll issues another. Once one succeeds, no further participant inserts start.
- **Waits for the database:** a strand with no `database` (a `'syncing'` joiner) gets no participant insert and no read, and `loading` goes false. Give it a database, and the next poll registers and reads. This is the contract in `docs/strands.md` ("The reference apps rely on this: … register the local participant only once `strand.database` is set").
- **No strand:** with no strand offered, `start()` issues no statements, `loading` goes false, and `inputEnabled` is false. When a strand is then offered (`strand:started`), the next poll attaches, registers and reads (the "strand may be created after the chat screen is already open" branch in `refresh()`).

Send rule (`send()`), ported from `packages/reference-app-rn/test/chat-send.spec.ts`:
- **Resend of unchanged text stores one row:** the first insert stores the row and then throws. `send()` rejects and `error` starts "Not confirmed sent". Pressing Send again on the same draft leaves exactly one `App.Message` row (count the real table), with `draft` `''` and `error` `''`.
- **Edited text is a new message:** after the same uncertain failure, change the draft and Send. Two rows.
- **Second Send while the first is in flight does nothing:** hold the first insert and call `send()` again. Only one `App.Message` insert has started, and the second call resolves without error. Release the first insert. One row, draft cleared.

Retry key release (`draft` setter, `settlePendingDraft()`), RN counterpart also in `chat-send.spec.ts`:
- **Changing the draft retires the key:** after an uncertain failure, set the draft to `''`, then back to the same text, and Send. Two rows.
- **A poll that shows the pending row settles it:** after an uncertain failure (row stored), the next poll clears the "Not confirmed" error and empties the draft. A later Send of the same text typed again stores a second row, which shows the key is gone.
- **Not while a send is in flight:** after an uncertain failure, press Send again and hold that resend's `select Id … where Id = ?` lookup. Meanwhile, let a poll return the stored row. Then reject the held lookup, so the resend fails and the banner shows again. A third Send must still reuse the original key and leave exactly one row. If the poll had released the key mid-flight, the third Send would mint a new id and store a second row.

Not tested, deliberately:
- `settlePendingDraft`'s "clear the box only if it still holds that text" arm. It cannot be reached: the `draft` setter drops the pending draft whenever the text stops matching, so a live key always matches the box.
- `src/chat-strand.ts`. It is a thin wrapper around `addStrand(founder: true)`. The decision not to use `foundStrand` there was taken on purpose (`tickets/complete/strand-founding-resume-path.md`, "Deliberately out of scope"), and a test would only pin the wiring. The schema it carries is exercised by every test above.
- `src/chat-operations.ts` on its own. It is exercised by the view-model tests against the real database, and it has no branching beyond what those tests cover.

## Edge cases & interactions

- **Module singletons across tests:** both `getCadreVm()` and the fake node carry state. Every test must load through the reset helper, and a leak shows up as statement counts from the previous test. Verify by inspection. A test that passes alone but fails in the file is this problem.
- **Timer leaks:** a test that fails before `vm.stop()` leaves a live interval. Put teardown in `afterEach`, not at the end of each test.
- **Held promises never released:** a test that holds a statement and fails before releasing it leaves a pending Quereus call. Release all gates in `afterEach`.
- **Fake timers vs Quereus internals:** faking only `setInterval`/`clearInterval` keeps any Quereus `setTimeout`/`setImmediate` real. If a test hangs, this is the first thing to check.
- **`crypto.randomUUID`:** `newChatMessageId()` uses the global. Node 24 has it, so do not stub it.
- **Foreign key:** `App.Message.ParticipantId` references `App.Participant`, and Quereus enforced it in the probe. Send tests must let registration land first, which happens on the first poll, or the insert fails for the wrong reason.
- **Unhandled rejections:** `send()` rethrows after setting the banner. Always `await expect(vm.send()).rejects…`. Never `void vm.send()` on a path that rejects.
- **Sourcemap warnings:** expect three warnings per run instead of one. Update the stub's `NOTE:` so it no longer says "one".
