# Retry control-schema init on a transient cohort failure

## The one site that must change

`ControlDatabase.loadSchema` (`packages/cadre-core/src/control-database.ts`, the
`await this.db!.exec(schemaContent)` at the end of the method) runs the whole
`CadreControl` DDL exactly once. Every table in that schema is optimystic-backed
(the default vtab is set to `optimystic` immediately above, in `initialize`), so
each `create table` is a distributed operation that needs a super-majority of the
party's peers to answer. On a node joining a party that already has two live
members, one unanswered peer during any one of those creates kills node startup:
`cadre-cli start` prints `Failed to start cadre node: Failed to execute DDL: …`
and exits.

Every other control write in this package is already protected. The classifier
and loop in `packages/cadre-core/src/control-write-retry.ts`
(`isRetriableControlWriteFailure`, `retryControlWrite`) sit under
`ControlDatabase.lockedWithRetry`, the funnel every local control write passes
through. Schema init is the one distributed operation that bypasses them —
not by decision, just by never having been routed through them.

## Why retrying the whole `exec` is safe

This was the open design question in the fix ticket; it is settled by reading the
engine, and the answer is that the DDL is already re-runnable as-is.

**`apply schema` is a diff, not a replay.** `emitApplySchema`
(`../quereus/packages/quereus/src/runtime/emit/schema-declarative.ts`) collects
the *live* catalog with `collectSchemaCatalog`, computes `computeSchemaDiff`
against it, and only then calls `generateMigrationDDL`. Tables already present in
the catalog generate no statements. This is the same property that makes a warm
restart cheap — `initialize` already relies on it, hydrating persisted optimystic
schemas *before* `loadSchema` precisely so the diff sees them and re-emits nothing.

**A failed `create table` leaves the catalog clean.**
`SchemaManager.createTable` (`../quereus/packages/quereus/src/schema/manager.ts`,
~line 2807 onward) calls `module.create(...)` inside a `try`, rethrows as
`Module '<mod>' create failed for table '<t>': …`, and only reaches
`schema.addTable(completeTableSchema)` on success. So the table that failed is
*not* registered, and neither are the ones after it.

Together: re-running `db.exec(CONTROL_SCHEMA)` after a partial failure re-emits
exactly the failed table and its successors, and skips everything that already
landed. No `if not exists` juggling, no per-table loop, no statement splitting —
retry the whole `exec`.

The migration loop (`runBatchedMigrationLoop`, same file) wraps each statement's
failure as
`QuereusError("Failed to execute DDL: <ddl>\nError: <msg>", …, cause)`, preserving
the cause chain — which is what makes the existing classifier usable here, since
`isRetriableControlWriteFailure` walks the chain with Quereus' `unwrapError`
rather than matching only the outermost message.

## Which failures this fixes, and which it does not

Two different errors were observed in two runs of the same scenario. They are not
the same defect and only one is in scope.

**In scope — the cohort did not answer.** Run 1 died on table `FormationUsage`
with `Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)`
alongside `cause=The stream has been reset`. That message is already matched by
`isUnansweredSuperMajorityShortfall` in `control-write-retry.ts`: zero rejections
means nobody voted no, the shortfall is raised while collecting promises, and
nothing has committed. This is precisely the class the existing retry was built
to absorb, and it is the class that makes a *third* node's join fragile — with
three live peers a control transaction needs 2 approvals, so a single flaky peer
response is fatal where a two-node party would have tolerated it.

**Out of scope — already tracked upstream.** Run 2 died on table `Revocation`
with `Missing block (jQlkVafUFlI6FzOGGAlViyK5GrgcSm_4SL7HfPKwhis)`. That face is
already documented, at this exact call site, in
`tickets/blocked/control-db-cross-node-convergence-halted.md` — see its
"Folded in 2026-08-01" section, which records
`Failed to execute DDL: create table CadreControl.OwnerKey …` traced to
`ControlDatabase.loadSchema`, and its observation that the most exposed scenarios
are exactly those where a node joins a party whose control collections were
already committed by another node. That ticket's evidence is that the condition is
durable, not transient (a collection reporting a committed revision whose header
block reads as affirmatively absent), so a retry cannot heal it and must not
pretend to. `Missing block` matches no matcher in the classifier, so it will
propagate unchanged — which is the correct outcome. **Do not widen the classifier
to catch it.**

Expect, therefore, that this change makes the joining node *reliably survive one
class of hiccup* without making the provider scenario unconditionally green. The
dependent ticket `provider-seed-accepted-by-real-node` should be judged on that
basis.

## Interface

No new public surface. `retryControlWrite` is already generic over the attempt's
return type and takes its pacing seams as an optional second argument:

```ts
retryControlWrite<T>(
  attempt: () => Promise<T>,
  options?: ControlWriteRetryOptions
): Promise<T>
```

`loadSchema` becomes an `attempt` passed to it. The existing budget
(`CONTROL_WRITE_ATTEMPTS` = 3, `CONTROL_WRITE_RETRY_BUDGET_MS` = 10 s, backoffs
~250 ms / ~1 s) is the right shape for startup too: a transient stream reset
surfaces in well under a second, and a genuinely unreachable cohort blows the
budget on the first attempt's return and so adds zero startup latency.

Reuse the retry rather than writing a second one. If the pacing seams need to
reach this call (they should, so a spec need not sleep), thread
`this.controlWriteRetryPacing` — the field already on `ControlDatabase` for
`lockedWithRetry` — into the call.

## One thing to verify before trusting the match

The classifier vetoes any failure whose cause chain contains `[blocks:`
(`reportsIndeterminateCommit`), the token the transactor's *commit* phase uses to
format its per-batch details — an indeterminate commit must never be re-run. The
read and pend phases format `[block:` instead; the three formatting sites are in
`../optimystic/packages/db-core/src/transactor/network-transactor.ts` (the two
`[block:` sites and the one `[blocks:` site all feed `formatBatchStatuses`).

The observed DDL aggregate was transcribed into the fix ticket with the bracketed
segment elided, so **it is not established which token a create-path aggregate
carries.** If it carries `[blocks:`, the veto fires and the retry silently never
engages — the change would look correct and do nothing. Capture one real failing
aggregate verbatim (see below) and assert against it before declaring this done.
