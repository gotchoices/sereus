# Browser reference app: dissolve the cadre it left

Split from the plan ticket `reference-apps-join-existing-cadre`. After `reference-app-web-joins-existing-cadre`, a tab that founded party B and joined party A runs A with `formerPartyId: B` in its `party-start` record, B's control block store still in IndexedDB (`sereus-strand-` + `controlStorageScope(B)`), B's per-party node-local records (`<key>.<B>`) and possibly B's move record.

Mirror the phone kit's dissolve (`packages/cadre-rn/src/phone-node/dissolve.ts` and `node.ts` → the `dissolve` transition; architecture.md → "Dissolving the party it left"; kit README → "Dissolving the left cadre"). Read those first. cadre-core supplies the comparison: `readStrandHoldings(node)` and the pure `unheldBundleContent(bundle, holdings, nowMs)` (`strand-move.ts`).

## Sequence (`cadre-web.ts` → `dissolveFormerParty({ discard? })`, driven by a store action)

1. Refuse, before anything stops, unless the running record has a `formerPartyId` different from its own party; and while a move record for B names any party (B's strands are not all adopted yet): "Moving this tab's strands has not finished" (the page offers Retry, which re-runs the adoption on the running node when its owner state is `enrolled`).
2. Read A's holdings (`readStrandHoldings`) on the running node.
3. Stop A through the store's teardown, start a node for B alone: B's record shape `{ partyId: B, origin: 'founded' }`, no chat strand, no relay reservation, no move adoption, nothing written to `party-start`. Read `exportStrandBundle` and `node.listMembers()` (or `queryCadrePeers()`), then stop it.
4. Compare: `unheldBundleContent(bundle, holdingsOfA, Date.now())` minus `discard`; machines other than this tab's peer id. Anything left → start A again and throw a typed refusal carrying `strandIds`, `pendingJoinIds`, `otherMachines` (the kit's `FormerPartyNotEmptyError` shape; define the web's own class).
5. Remove, in this order, with a marker so a closed tab finishes it on the next load: write kv `dissolving-party` = `{ v: 1, partyId: B }`; close and delete B's control block database (`indexedDB.deleteDatabase`, through a new `deleteStore(key)` in `strand-storage.ts` that closes a cached handle first); delete B's per-party node-local records (`partyKvKey(key, B)` for each of the four keys) and B's move record; rewrite `party-start` without `formerPartyId`; delete the marker.
6. Start A again (chat strand, subscriptions, as after any start).

**Every start** checks the marker first: one naming a party other than the record's own finishes steps 5's deletions and drops `formerPartyId` if the record names it, then starts. A marker naming the party being started (only reachable by hand) is deleted with a warning, not acted on.

Strand block databases are not deleted: a moved strand's database (`sereus-strand-<strandId>`) is A's copy too.

## Page

On `#/cadre`, the join card's outcome continues with "Removing this tab's old cadre…" automatically after a join that left a founded party with nothing pending, as the phone app does. On load, a running record with `formerPartyId` shows "This tab's old cadre is still in this browser" with **Remove it now**. Refusals: other machines → "kept in this browser; nothing was lost"; only strands or joins A does not hold → a confirm listing the count, then a retry with `discard`. Same wording as the phone ticket's `join-flow.ts` table.

## Edge cases & interactions

- Tab closed after the marker is written: the next load finishes the deletion before starting A. By inspection; the kit has the equivalent test.
- `indexedDB.deleteDatabase` blocked by another open connection (a second same-origin tab still running B): the request fires `blocked` and waits. Do not wait forever: on `blocked`, report "Close this site's other tabs to finish removing the old cadre" and leave the marker, so the next load finishes it. By inspection.
- A failure starting A again after the removal: the call's error, store `error`; the next load starts A from the rewritten record. By inspection.
- A refusal: A is started again and nothing is deleted. By inspection.
- `discard` naming an id that is not in the unheld set: ignored. By inspection.
- Reading B alone uses B's per-party records and control store, untouched by A's run since the join. By inspection.

## Tests

No new test. The deletion and marker resume are a straight sequence mirrored from the kit, which tests its own resume; the refusal arithmetic is cadre-core's `unheldBundleContent`, tested there. If the implementer finds a branch the kit does not share (the `blocked` handling), that is the one worth a unit test against a fake `indexedDB`.
