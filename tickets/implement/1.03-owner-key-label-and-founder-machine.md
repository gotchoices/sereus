# Owner-key labels, `addOwner` by public key, and the founding machine

## Schema (`schemas/control.qsql`, mirrored in `control-schema.ts`)

**`OwnerKey.Label text null`** — the user's name for the key, at most 64 characters (CHECK `Label is null or length(Label) between 1 and 64`; confirm Quereus `length` semantics). Bound into the owner-signed add digest so a relayed approval cannot seat the key under another name:

- add digest becomes `digest('CadreControl.OwnerKey', 'add', party_id(), new.Key, coalesce(new.Label, ''), new.StampId)` (and `ownerKeyAddMessage` in `control-database.ts` to match);
- the genesis branch allows any label (it is unauthorized by design);
- the invitation consent branch (`GrantsOwner`) requires `new.Label is null` — `owner-grant-separate-from-machine-invitation` gives owner grants their own label rule;
- `revouchOwnerKey` (delete and re-add under a fresh stamp) carries the label over;
- the anchor derivation (`verifyOwnerKeyVoucher`, `owner-anchor-sync.ts`) verifies the new digest.

**`Strand.FounderPeerId text null`** — the peer id of the machine that runs the founder bootstrap. The owner-signed branch of `Strand.AuthorizedInsert` requires it non-null and binds it into the add digest: `digest('CadreControl.Strand', 'add', party_id(), new.Id, new.Type, coalesce(new.MemberPrivateKey, ''), new.FounderPeerId, new.StampId)`. The consent branch requires it null, as it requires `FounderOwnerKey` null. `FounderOwnerKey` keeps its meaning (the signing owner key, pinned to `context.OwnerKey`): provenance.

Decision: `FounderPeerId` is not pinned to a live `CadrePeer` row. The owner's signature already binds it, so only an owner can name a founding machine, and a solo founder publishes before its own `CadrePeer` row exists (`registerSelf` runs after genesis), which a pin would refuse. A wrong peer id costs that strand its founder bootstrap, the same failure as a consent-seated strand today, and only an owner can cause it.

Editing constraint text makes an older control store unable to warm-start (`docs/architecture.md` → Control Network, the paragraph after the table); under the no-backwards-compatibility policy such a party is recreated. Update `control-schema-drift.spec.ts` / `control-party-binding.spec.ts` pins for the changed digests.

## Writers and readers

- `ControlDatabase.getOwnerKeys()` keeps returning the live key set; add a row reader returning `{ key, label, vouchOwner, vouchUsage, stampId }` for listing.
- `CadreNode.addOwner(publicKey, { label? })` — validates with `requireEd25519PublicKeyB64`, signs the new digest. **Refuses while alone**: when the node holds no control connection and the party has other authorized members (`authorizedControlPeers` non-empty), throw a typed refusal (`OwnerKeyAddRefusedError`, code `alone`) instead of committing a write that has no re-issue path. This is option 2 of `backlog/debt-owner-key-add-while-alone-has-no-reissue`, folded in here; delete that backlog ticket and replace the `addOwner` log-only paragraph in `docs/architecture.md` → "Writes made while alone" (the `OwnerKey` sentence) with the refusal. A party with no other members cannot fork, so a solo founder adding its backup key is unaffected.
- `CadreNode.listOwnerKeys(): Promise<CadreOwnerKey[]>` — `{ key, label: string | null, vouchedBy: string | null, heldHere: boolean (key === this node's signer key), trusted: boolean (in this node's anchor) }`, live rows only. The apps' owner-key list is built on it.
- `ensureOwnerKey(key, label?)` / `insertOwnerKey(key, label?)` (genesis) accept the label so a founder names its first key.
- `publishStrand` writes `FounderPeerId = this node's peer id`; `adoptStrandBundle` (`strand-move.ts`) writes the adopting node's peer id (the app's node keeps its identity across the move, so the founder stays the same machine).
- `isSelfFoundedRow` (`cadre-node.ts` ~3311) becomes `strand.FounderPeerId === this node's peer id`; null is never self-founded (consent rows keep relying on the responder's explicit `founder: true`). Delete the "one owner key per machine" warning comment there. `launchStrand`, `foundStrand` and `addStrand` keep calling it.
- `strandRowMismatches` excludes `FounderPeerId` as it excludes `FounderOwnerKey` (provenance, so two machines racing to found one id still resolve as "the winner's row stands").
- `queryStrands` / `queryStrand` / `StrandRow` carry the new column; rows built elsewhere with `FounderOwnerKey: null` (`joined-strand-store.ts`, `reference-app-rn/src/chat-strand.ts`, `reference-app-web/src/lib/cadre-web.ts`) add `FounderPeerId: null`.

## Edge cases & interactions

- Two machines of one party holding the same owner key (a key imported from QR): only the machine whose peer id the row names founds; the other attaches as a joiner. **Test** — extend the existing founder-derivation spec (the one covering `isSelfFoundedRow` / `foundStrand` adoption) with a second node sharing the signer: it adopts as joiner, `founded: false`.
- A strand row signed with one `FounderPeerId` cannot be re-presented with another: the digest binds it. Covered by the drift/binding spec pins; no new test.
- Label bound into the add digest: an add approval replayed with a different label is refused. **Test** — one case in the existing `OwnerKey` authorization spec (`control-database-genesis` or the owner-writer spec), since this is the security property the binding exists for.
- Consent branch with a label → refused. Same spec, one assertion.
- `addOwner` while alone with siblings → `alone` refusal and no row; while alone with no siblings → commits. **Test** — the branching rule from the folded backlog ticket; one spec with both arms.
- `revouchOwnerKey` preserves the label. By inspection (the re-add reuses the row's label).
- Moving strands: `adoptStrandBundle` on the app's node writes its own peer id, and `strand-moves-between-cadres.integration.ts` still sees the founder bootstrap run once in A and write nothing. Run that scenario.
- Hibernation wake and restart re-attach derive founder-ness from the row on every launch (`launchStrand`), so they follow the new column with no extra work. Existing strand restart specs.
- A node with no owner signer still derives founder-ness (it compares peer ids, not keys), so a non-owner machine named as founder by the owner would found. Only an owner can name it; by inspection.
