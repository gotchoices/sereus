# cadre-cli: an owner key in its own file

## Today

`cadre start --owner` (`start.ts` ~416–450) runs `ed25519KeyPairFromLibp2p(config.privateKey)` on the node identity, inserts that as the genesis `OwnerKey` and wires it with `initializeSeedBootstrap`. The one-shot sessions (`node-session.ts`, behind `cadre strand remove` and `cadre validation-key`) rely on the identity being an owner (after `owner-signing-through-one-signer` they wire it with `wireOwnKeyIfOwner()`). The README says those commands need "a config whose identity key is an enrolled `OwnerKey`".

## Design

- **Owner key file.** New config key `owner.keyFile` (env `CADRE_OWNER_KEY_FILE`, flag `--owner-key-file <path>`), default `<nodeStateDir>/owner.key`. Same on-disk format as the identity file (libp2p protobuf of an Ed25519 private key), written through `private-file.ts` (0600, crash-atomic like the identity writer). Strict config checking covers the new key (`@serfab/config-check` schema in `config/schema.ts`). The loader refuses an owner key file that resolves to the same path as `identity.keyFile`.
- **`cadre start --owner`** loads the owner key file and wires `useOwnerSigner(softwareOwnerSigner(…))` (the protobuf → base64url seed conversion is `ed25519KeyPairFromLibp2p` over the owner key's own bytes, never the identity's).
  - File absent: create it, then print to stderr that this server now holds an owner key for the party, where the file is, and that anyone who can read it controls the cadre. This is the deliberate "add an owner key to this server" path the architecture describes.
  - Fresh party (empty `OwnerKey` table): genesis-insert the key with label `--owner-label <text>` (default `server <hostname>`).
  - Existing party where the key is not a live owner: fail start-up naming the key's fingerprint and saying to add it from an owner device first (`addOwner`), rather than letting the schema refuse an insert.
  - Existing party where it is: wire it, no insert.
  - `registerSelf()` afterwards, as today (the self-row insert is vouched by the owner key).
- **One-shot sessions** (`strand remove`, `validation-key`): wire the owner key file's signer when the file exists and its key is a live owner; otherwise refuse with the same "not an owner" message the commands give today. Remove the identity default from `node-session.ts`.
- **`cadre owner-key show|export|import`** (new `owner-key.ts`, registered beside `enroll`):
  - `show` prints the public key (base64url) and the 8-character fingerprint the apps show.
  - `export [--passphrase-file <path>]` prints the export text (`encodeOwnerKeyExport`, locked when a passphrase is given) on stdout and, on stderr, that it makes its holder an owner.
  - `import [<text> | -] [--passphrase-file <path>]` decodes (`decodeOwnerKeyExport` / `unlockOwnerKeyExport`) and writes the owner key file; refuses to overwrite a file holding a different key; idempotent for the same key.
  - Passphrases come from a file or `CADRE_OWNER_KEY_PASSPHRASE`, never a command-line argument (it would land in shell history and the process list).
- `enroll create`'s printed next steps and `enroll add`'s "Owner key to pin" stderr line name the owner key (the seed's `signerKey`), not the identity; check the wording only.
- The admin channel's identity route (`GET /admin/identity`) reports the owner key from the signer, if it reports one.
- `--invitation` together with `--owner` stays refused (unchanged; an always-on node that joins by invitation and also holds an owner key is a later choice).
- `integration-tests/src/harness/owner-cli-node.ts` spawns `cadre start --owner`: give the child an owner key file of its own (or let it create one) and read the owner public key back from `owner-key show` or the admin channel instead of deriving it from the identity file.

## Edge cases & interactions

- Owner key file path equal to the identity file → refused at config load. **Test** (loader spec).
- `--owner` against an existing party whose `OwnerKey` table does not list the file's key → start-up fails with the fingerprint and the add-it-first message, nothing inserted. **Test** — one-shot-node / start spec; the three arms of the `--owner` decision (fresh party, listed, not listed) are the branching logic worth pinning.
- Owner key file unreadable or corrupt → start-up fails naming the file; never regenerated over it (same rule as the identity key). By inspection, mirroring `loader.ts`'s identity handling.
- `owner-key import` over a different existing key → refused; same key → no-op. Covered by cadre-core's `importOwnerKey` spec; by inspection here.
- A claim-configured node still refuses `--owner` (`refuseClaimConflicts`). Unchanged.
- The systemd unit and Docker image set `CADRE_NODE_STATE_DIR`; the default owner key path follows it, so a read-only config directory is not written. By inspection.
- cadre-host and cadre-provider never pass `--owner` (`docs/cadre-host.md` → the host holds no owner key). Unchanged; by inspection.
