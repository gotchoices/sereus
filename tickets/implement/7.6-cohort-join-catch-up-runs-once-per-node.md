# One cohort-join catch-up per node

## Why

On a node built with `arachnode.enableRingZulu` (Sereus sets it for `profile === 'storage'`, on both the control node and every strand node), Optimystic wires its rebalance reaction (`libp2p-node-base.ts`, the `options.rebalance?.enabled` block). Its growth arm pushes every block whose cohort gained a peer to that peer, one block per request. The sender's rebalance monitor learns that a peer holds a block only from its own pushes, commits, reconciles and pushes it received (`RebalanceMonitor.recordBlockHolders`); it never learns of Sereus's `PeerJoinBackfill` pushes, and db-p2p exposes no embedder API to report them. So a storage-profile node pushes each block to a joiner twice: once in Sereus's chunked backfill, then again one request per block.

`PeerJoinBackfill` pushes every block to every peer it serves (members only, on the control network), which always includes the growth arm's targets (the newly co-responsible peers among them). The growth arm adds no coverage where the backfill runs.

## Decision

Pass `rebalance: { enabled: false }` to `createLibp2pNode` on a strand node exactly when that strand's backfill will be armed (strand storage present and `config.backfill?.enabled !== false`), and on the control node exactly when the control backfill will be armed (`controlBackfill?.enabled !== false` and control storage resolves). A host that disables the backfill keeps Optimystic's rebalance as its only join catch-up.

What else turning rebalance off turns off, read in `libp2p-node-base.ts`, and why each is acceptable:

- **The lost arm** (confirm a shed block replicated, then untrack it and add it to `gcEligibleBlocks`): nothing consumes that set yet (Optimystic's own `NOTE:`), and a Sereus storage node is meant to keep every strand it serves.
- **Ring shifts** (`RingShiftCoordinator`, moving the node between Arachnode rings under storage pressure): stay inert, which Optimystic documents as the safe state ("a node with the rebalance reaction disabled stays at its bootstrap ring"). A transaction-profile node has no Arachnode at all today.
- **The receiver's holder reports** (`BlockTransferService` → `onBlockHolders`): their only consumer is the rebalance monitor.

The spread-on-churn monitor and the under-replication drain are separate wiring and stay on.

Tradeoff: if Sereus ever needs ring shifts or storage reclamation on storage nodes, this has to become "report the backfill's accepted pushes to the rebalance monitor" instead, which needs an Optimystic API (a public `recordBlockHolders` on the node). Record that as a `NOTE:` at each of the two option sites, naming the revisit condition. Reversible: one option per node builder.

## Edge cases & interactions

- **Backfill disabled by config** (`strandBackfill.enabled: false` / `controlBackfill.enabled: false`): rebalance stays on. Inspection; keep the two conditions in one place per site (compute the "backfill will arm" flag once, use it for both the option and the arming), so they cannot drift.
- **Strand node without storage** (`strandStorage` absent): no backfill, rebalance as before.
- **Transaction-profile nodes**: unaffected, rebalance is never wired there. Passing the option is harmless.
- **Hibernation resume** rebuilds the strand node through the same options path. Inspection.
- **Integration tests that read `(node as any).rebalanceMonitor`**: none in this repo (grep `rebalanceMonitor` under `packages/`).

## Measurement

Run `MESSAGE_COST_MEASURE=1 MESSAGE_COST_CASE=invite` (A is storage profile, so its control node runs the rebalance reaction) before and after; report the settle window's A→B `block-transfer` count and attribute it with `DEBUG=optimystic:db-p2p:*` (rebalance pushes log under the block-transfer coordinator). The strand case's machines are transaction profile, so it should not move; run it once to confirm. Add the after-row to the scenario's baseline doc comment.

No new test: this is a configuration choice on two node builders; the measurement is the evidence.
