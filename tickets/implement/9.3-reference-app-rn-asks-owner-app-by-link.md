# Phone reference app asks the owner app by link (joining side)

The joining app's half of the same-phone join. Kit pieces: `phone-kit-same-phone-join-links` (`@serfab/cadre-rn/app-link`: `joinRequestLink`, `installedSereusApps`, `LinkRequestStore`, `decodeCadreJoinResponse`, `PhoneNode.linkRequestSlot()`). Owner side and link routing: `reference-app-rn-answers-join-requests-by-link`. That ticket routes `<scheme>://cadre-join-response/…` to `/settings?joinResponse=…`.

Terms: **B** is this app, joining; **A** is the owner app it opens.

## Behaviour

**The button.** In `JoinCadreSection`'s request view, above the QR code, add the primary button **Choose the app that holds your cadre**. The existing request, Code and paste field stay below it as the fallback.
- **Android:** open `joinRequestLink(requestText, null)`, and Android's chooser lists the installed owner apps.
- **iOS:** the button opens a list of `installedSereusApps(apps, ownScheme, Linking.canOpenURL)`, where `apps` is the kit's `KNOWN_SEREUS_APPS` plus this build's extras (below). Picking one opens `joinRequestLink(requestText, app)`. An empty list says "No other Sereus app is installed on this phone. Copy this app's request into the app that holds your cadre."

**Opening the request** is a hook action, `askOwnerApp(app: SereusApp | null)`, in `use-join-flow.ts` beside the join flow:
1. `store.begin(app?.name ?? null)`, where `store = new LinkRequestStore(phone.linkRequestSlot())` is built in `cadre-phone.ts`.
2. Build the request text with `reply: { scheme: ownScheme, nonce }` (`joinRequestText` in `cadre-phone.ts` takes an optional reply).
3. `Linking.openURL(link)`. If it rejects, `store.cancel()` and alert "Could not open ‹app›" with the paste fallback line.

`ownScheme` is `Constants.expoConfig.scheme`.

**Waiting.** The hook holds `linkRequest: OpenLinkRequest | null`, read from `store.current()` at launch and set by `askOwnerApp`. While it is set, the section shows "Waiting for ‹ownerAppName› to answer…" ("…for the app you chose…" on Android) with **Cancel** (`store.cancel()`), and the paste inputs stay visible below it. A relaunch with an open request shows the same line, which covers the user coming back by the app switcher.

**The answer** arrives as the `joinResponse` parameter. Add `useLinkedJoinResponse()` in `settings.tsx`, modelled on `useLinkedNodeCode()`: it reads and clears the parameter, then calls the hook's `takeJoinResponse(text)`. That action does the following:
- **A join is already on screen** (`joinFlow` set, for example the user pasted meanwhile): do not take the answer. Alert "A join is already under way" and leave the request open.
- **Otherwise `store.take(text)`.**
  - `UnsolicitedJoinResponseError`: alert "This answer was not for a request this app has open", and log without the text.
  - A codec error: the same alert, with the error as its detail.
- **An invitation:** run the existing `joinExistingCadre(invitation)`. It already refuses an invitation made for another app before anything stops, and its failures go through `joinFailureAlert`. Show the alert from Settings, since the section may not be mounted.
- **A refusal:** alert with the wording below, naming `response.appName`, and add "You can still copy this app's request into it."

| Refusal | Alert |
| --- | --- |
| `denied` | ‹app› did not allow this app to join. |
| `no-cadre` | ‹app› has no cadre yet. Open the app that holds your cadre. |
| `not-owner` | ‹app› is a member of your cadre, not an owner. Open an owner app. |
| `already-member` | This app is already in the cadre ‹app› holds. |

**Own request came back.** The owner-side ticket hands over a request link that carries this app's own peer id. This happens when the user picked this app in the Android chooser, or when it is the only handler, so Android opened it with no chooser. Add the hook action `linkRequestCameBack()` for it: it cancels the open request and shows in the section, once, "That opened this app again. Choose the app that holds your cadre, or copy this app's request into it." Replace the owner-side ticket's interim alert with this action.

**A second install for trying it on one phone.** Two Sereus apps are needed on one device, so add `app.config.js` beside `app.json`.
- **The variant.** Under `APP_VARIANT=second`, the config takes `app.json`'s config and sets: name "Sereus P2P Chat (second)", scheme `sereus-chat-second`, `ios.bundleIdentifier` and `android.package` suffixed with `.second`.
- **The extras list.** It defines the one list of extra apps: `[{ name: 'Sereus P2P Chat (second)', scheme: 'sereus-chat-second' }]`, the main app being in the kit's list already. It passes the list both as the kit plugin's `appLinks.extraApps` and as `extra.sereusApps`. The runtime reads `Constants.expoConfig.extra.sereusApps` and validates its shape (malformed reads as empty, logged).
- **Builds.** The main build is unchanged apart from the plugin option. `README.md` gets the build command for the second install, and docs/reference-app-rn.md notes it in "Device test runs".

## Device run (blocked ticket to file)

Write `tickets/blocked/rn-device-run-same-phone-join-by-link.md`, in the shape of `tickets/blocked/rn-device-run-join-existing-cadre.md`.
- **Category and unblocker:** hardware and a person. It needs an Android device or emulator and an iOS device or simulator, each with both installs (main and `APP_VARIANT=second`), plus an always-on machine. Unblock by running the table and recording the results.
- **Rows:**
  - first launch: Yes → Choose → Allow, on each platform;
  - an app with its own cadre and chats: Choose → Allow, with chats moved;
  - Deny, then a second request within 30 s (answered without a prompt);
  - A with no cadre, and A as a member only;
  - A disconnected: the waiting hint, then Connect answers;
  - B killed while A's prompt is open, then Allow (B cold-starts and joins);
  - Cancel in B, then Allow in A (B refuses the unsolicited answer);
  - the Android chooser listing B itself, and B being picked;
  - the Android system camera opening a request QR code;
  - the iOS list empty when only one install is present;
  - the response link length (log the length only, never the link) against the kit's estimate of about 4 KB.

## Edge cases & interactions

- **Cold start with the answer.** A start on a phone with a saved start runs auto-start; the kit queues the join behind the start (`inTurn`). Verified by inspection against `PhoneNode.joinCadre`.
- **Cold start on a first launch.** Nothing is saved, and the first-launch question shows. The answer still starts the join with nothing running, which the existing first-launch join supports. The join section shows because `joinFlow` is set. Verified by inspection of `settings.tsx`'s section condition.
- **Answer arriving before the hook has read `store.current()`.** `take` reads the slot itself, so it does not depend on the hook's state. Verified by inspection.
- **`resumeUnfinishedJoin` after a start, racing the answer.** Both go through the hook's existing flow guard; the second is refused with the guard's existing behaviour. Verified by inspection.
- **Tapping Choose twice.** The kit's `begin` reuses the nonce, so an answer to either tap is taken. Verified by the kit's test.
- **Cancel, then an answer arrives.** Refused as unsolicited. The targeted invitation A minted stays outstanding in A until it expires or is withdrawn, and is useless to anyone else. Verified by inspection; documented.
- **An answer older than 30 minutes.** Refused; the user asks again. Verified by the kit's test.
- **A slot read fault at launch.** Log it and show no waiting line; `take` still surfaces the fault as an alert. Verified by inspection.
- **The second install.** The two installs have different peer ids, storage and schemes (separate app sandboxes), so they are two independent apps to every Sereus mechanism. Verified by inspection of the variant config.
- **Web.** `reference-app-web` is out of scope and keeps copy and paste.

No new unit tests: the hook actions map kit results to UI, and the kit's store test pins the security contract. The device run covers delivery.
