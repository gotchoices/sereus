## The scenario this release is for

"Phone → blind proxy → phone": two **different parties**, each a single node that
cannot listen (`listenAddrs: []`), sharing one **dedicated** relay that is strictly a
relay — not a cadre member, in no cohort, holding no data (the harness fixture from
`strand-circuit-same-party-e2e`, config-parity with `ops/docker/libp2p-infra`). This is
the only shape that works when two strangers each have only phones, and no test has
ever run it: cross-party relaying exists in the suite only as denial/budget-cap cases,
and the only both-ends-unreachable case anywhere is a synthetic bare-libp2p loopback.

## Flow under test (all over the one relay)

1. Party A's node boots relay-only (`relayAddrs: [relay]`, `listenAddrs: []`); control
   node reserves. A founds a **closed** strand and creates a **bound** invitation.
   Assert the encoded invitation's bootstrap addresses include A's `/p2p-circuit`
   control address (`OpenInvitation.bootstrap` is filled from `getMultiaddrs()`,
   signaling-first — `cadre-node.ts:6102`).
2. Party B's node boots the same way. B decodes the invitation and runs `formStrand`
   over the relayed control connection. The formation protocol is stranger-open while
   an unexpired invitation is outstanding (`membership-connection-gater.ts` →
   `STRANGER_OPEN_PROTOCOLS`); this is its first exercise over a circuit. Note the
   formation handler does NOT set `runOnLimitedConnection` — it works only because the
   dedicated relay runs `applyDefaultLimit: false`; assert the harness relay keeps that
   parity.
3. B receives `strandAddrs` (A's strand-network circuit address, from
   `formation-carries-strand-addrs`), adds the strand, and its strand node — holding
   its own reservation on the same relay — dials A's strand node through the relay.
4. Rows written by A are read by B and vice versa (real strand data over the circuit
   both directions, including B→A where B is a total stranger to A's party).
5. Assert **every** A↔B connection — control and strand — is classified `relayed` by
   `summarizeConnectionPaths` (`diagnostics/connection-path.ts`), so a direct fallback
   cannot pass for relayed success.
6. Record the relay's reservation count (expected 4: two control + two strand). This
   answers the plan ticket's open cost question: today every strand a NAT'd node joins
   costs one extra relay slot per node; write the number into the docs update.

## Edge cases & interactions

- **Circuit CONNECT from a stranger**: B connects *through* the relay to A's strand
  node. The relay is ungated; A's strand node has no connection gater by default. If
  anything on A's side (e.g. the strand node's own relay/limits posture) refuses the
  inbound circuit connection, that is in-scope product fallout.
- **Strand DB streams over the circuit**: db-p2p's database protocols do not opt into
  limited connections; they work only over an unlimited relay. Keep one assertion that
  the connection is not flagged limited (or that streams survive >128 KiB / >2 min if
  cheap to arrange), so an ops config regression is caught by name.
- **Delegate admission is a non-participant here**: the dedicated relay speaks no
  strand-addr protocol, so no grants exist and none are needed. Assert nothing in the
  flow blocks on the delegate-announce path (it folds to a no-op —
  `cadre-node.ts:4632-4635`).
- **Ordering**: A's strand must be live before formation replies (bound invite →
  pre-created and founded); B's strand launch happens after `formStrand` returns. No
  sleeps — event/`waitUntil` driven.
- **Two relays** (A and B on different relays) is explicitly out of scope; note it in
  the scenario doc as untested.
