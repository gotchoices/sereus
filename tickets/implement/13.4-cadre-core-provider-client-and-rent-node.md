# Provider client and `rentNode` in cadre-core

Fourth ticket of the `provider-client-and-sign-up` chain. Everything here runs on React Native, in a browser and in Node: `fetch`, `URL`, `URLSearchParams`, `crypto.getRandomValues` (polyfilled on React Native by the kit), `TextEncoder`, `@noble/hashes/sha2` for SHA-256 (already a dependency; `claim-proof.ts` uses it) and `uint8arrays` for base64url. No Node imports. Opening a browser is the app's or the kit's (`reference-app-rn-rents-a-provider-node`).

The wire shapes are those of `provider-container-joins-by-claim-or-invitation` (`join`, `joinState`, `GET /containers/:id/code`), `provider-oauth-reference-endpoints` (authorize, token, descriptor) and `provider-subscription-state-and-lapse` (`subscription`, `stopReason`), as `docs/architecture.md` → Provider Integration states them. Write the client against the doc, and fix the doc where it is unclear rather than reading the provider's source into the client.

## `provider/descriptor.ts`

`ProviderDescriptor` (the JSON above in the OAuth ticket) and `parseProviderDescriptor(json: unknown): ProviderDescriptor`, refusing with a plain message: not `v: 1`; `id` or `name` missing or blank; `apiBaseUrl`, `oauth.authorizeUrl`, `oauth.tokenUrl`, `plansUrl` not absolute URLs; any of them `http` unless the host is loopback (`localhost`, `127.0.0.1`, `::1`), because the node code and the tokens travel over these; `regions` not a string array when present. A fetch helper `fetchProviderDescriptor(url, fetch?)` for an app that holds a URL rather than the document.

## `provider/oauth.ts` (RFC 7636 client side)

- `createPkce(): { verifier, challenge }`: 32 random bytes as a 43-character base64url verifier, challenge = base64url(SHA-256(verifier)).
- `authorizationUrl(descriptor, { clientId, redirectUri, state, challenge, scopes })`: the authorize URL with `response_type=code`, `code_challenge_method=S256`, scopes space-joined.
- `readAuthorizationRedirect(url, { expectedState }): { code } | { error, description? }`: throws `ProviderAuthError` on a state mismatch or a missing code and error; never logs the code.
- `exchangeAuthorizationCode(descriptor, { clientId, redirectUri, code, verifier, fetch? }): Promise<ProviderTokens>` and `refreshTokens(descriptor, { clientId, refreshToken, fetch? })`, form-encoded bodies, `ProviderTokens = { accessToken, refreshToken, expiresAt: number (ms), scopes: string[] }`; the provider's `{ error, error_description }` becomes `ProviderAuthError` with the error code.
- `createTokenSource({ descriptor, clientId, tokens, persist })`: a `TokenSource = { accessToken(): Promise<string>; invalidate(): Promise<string> }` that refreshes when the token is within 60 s of expiry or after the client's one 401 retry (`invalidate`), calls `persist(tokens)` after every refresh, serializes concurrent refreshes, and throws `ProviderAuthError('reauthorize')` when the refresh is refused, which is the app's cue to run the authorization again.

## `provider/client.ts`

`ProviderClient` interface and `createProviderClient({ apiBaseUrl, tokens: TokenSource, fetch? })`:

- `createContainer(body: { join: { kind: 'claim' } | { kind: 'invitation'; invitation: string }; profile?: 'storage' | 'transaction'; tags? })` → `RentedContainer`
- `getContainer(id)` → `{ container: RentedContainer; health?; join?: ContainerJoinState }` (the container carries `status`, `stopReason?`, `peerId?`, `partyId`, `joinState?`)
- `listContainers()`, `deleteContainer(id)`, `getBillingStatus()` → `{ planId, subscription: { status, renewsAt, lapsesAt } } | undefined`, `getNodeCode(id)` → `{ code, peerId, multiaddrs } | { notReady: true }` (503) with `ProviderApiError` for 409s.
- One request helper: bearer from `tokens.accessToken()`, JSON in and out, a 401 answered once by `tokens.invalidate()` and a retry, every other non-2xx a `ProviderApiError { status, code, message }` from the provider's `{ ok: false, error }` envelope. Dates arrive as ISO strings and are parsed into milliseconds at this boundary, so nothing above the client handles strings.
- The interface is what `rentNode` and the apps depend on; a hand-written object implementing it is how the tests below avoid HTTP.

## `rentNode` (`provider/rent-node.ts`)

```ts
export type RentNodeJoin = 'claim' | 'invitation';
export interface RentNodeOptions {
  profile?: 'storage' | 'transaction';          // default 'storage'
  onProgress?: (step: RentNodeStep) => void;    // 'creating' | 'waiting-for-code' | 'claiming' | 'inviting' | 'done'
  nodeCodeDeadlineMs?: number;                  // default 120_000; the provider's enrolment window is 60 s and an image pull can precede it
}
export interface RentNodeResult { containerId: string; join: RentNodeJoin; peerId?: string }
export type RentingNode = Pick<CadreNode, 'invitationReach' | 'createCadreInvitation' | 'withdrawCadreInvitation' | 'claimNode'> & { isOwner(): Promise<boolean> };
export function rentNode(node: RentingNode, client: ProviderClient, options?: RentNodeOptions): Promise<RentNodeResult>;
export function finishRental(node: RentingNode, client: ProviderClient, containerId: string, options?): Promise<RentNodeResult | { containerId; outcome: 'failed'; error: string; retryable: boolean }>;
```

- Owner check first: `RentNodeError('not-an-owner')`. `CadreNode` gains `isOwner(): Promise<boolean>` (this node's enrolled owner key is in the live `OwnerKey` set), which is what the reference app's `isOwnerDevice` computes by hand today; the app switches to it.
- Path choice: `await node.invitationReach()`; `anywhere` → invitation path, else claim path. `CadreNode.invitationReach()` is a new read-only method returning `CadreInvitationReach` from the same member selection `createCadreInvitation` uses (`selectCadreInvitationMembers` and `cadreInvitationReach` in `invitation-bootstrap.ts`), hoisted so the two cannot disagree; `createCadreInvitation` then calls it for its `reach` field. `local-network` counts as not reachable: the provider's container is never on the member's LAN.
- Invitation path: `createCadreInvitation({ grantsOwner: false, uses: 1, expiresInMs: 15 * 60_000 })` → `client.createContainer({ join: { kind: 'invitation', invitation: encoded }, profile })`; a create failure withdraws the invitation before rethrowing. Returns at once with `join: 'invitation'`; the container joins by itself and the app watches `getContainer(id).join`.
- Claim path: `client.createContainer({ join: { kind: 'claim' }, profile })` → poll `getNodeCode(id)` every 2 s until the deadline (`RentNodeError('node-not-ready', { containerId })` when it passes; the container exists, and `finishRental` resumes it) → `decodeNodeClaimPayload(code)` → `node.claimNode(payload)` → `{ join: 'claim', peerId }`. The claim is the owner's signature; the app asked the user before calling `rentNode`.
- `finishRental`: for an app that was killed mid-flow or hit the deadline. `getContainer(id)`: a claim container `awaiting` → the code → `claimNode`; `claimed` → `claimNode` again (idempotent for the same owner; a container claimed by another owner surfaces `ClaimRefusedError('already-claimed')` to the app); an invitation container `accepted` → done; `failed` → the failed outcome, and the app deletes the container and rents again (the claim path will be chosen if the member that answered is now gone); a `stopped` or `error` container → `RentNodeError('container-gone')`.
- Nothing here persists anything: which container belongs to which cadre is the app's record (`reference-app-rn-rents-a-provider-node`).

## Edge cases & interactions

- `claimNode` can take up to the per-peer dial limit plus the seed request when no address answers (its doc: 114.5 s at the default link); `rentNode` does not add a timeout of its own on top of it. By inspection; `onProgress('claiming')` lets the app show a slow hint, as the add-node section does at 20 s.
- The node code carries the claim secret: `rentNode` never logs the code or the payload, only the container id and peer id, as `node-claim.ts` in the app does.
- The token source's refresh runs during a long claim: the client only touches the token on a request, so a token that expires mid-claim is refreshed on the next call. Covered by the client's 401 retry.
- Two `rentNode` calls at once on one node: both mint or both create; nothing in cadre-core serializes them, as nothing serializes two `claimNode` calls; the app's `claimingRef` guard is the right place, as today.
- `cadreInvitationReach` judges the minting machine's siblings; a phone that is the only member reads `issuer-only` and goes to the claim path, which is the case the ticket names.
- A descriptor whose `apiBaseUrl` host differs from the token endpoint's host is allowed (an operator may front the API separately); the token is sent only to `apiBaseUrl`. By inspection.
