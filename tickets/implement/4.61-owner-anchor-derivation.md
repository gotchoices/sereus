# The anchor is derived from the owner table along verifiable chains

Second of three tickets (after `owner-anchor-revocation-signer-and-owner-writers`, before `owner-anchor-follows-owner-key-changes`).

## The gap

The node-local trusted-owner anchor (`TrustedOwnerStore`) gains a key only through genesis, a pin or a claim, and nothing removes one. So an owner seated by another owner (the signed add, or an owner-granting invitation) is trusted nowhere but on machines that happened to pin it, and a removed owner stays trusted everywhere. `docs/architecture.md` → "Node-local trusted-owner anchor" says why the replicated `OwnerKey` table cannot simply be the anchor: an empty local copy can seat any key through the genesis branch, and that row replicates.

## The rule

Every node recomputes its anchor from a set of keys it trusts out of band plus the chains that lead from them, on every membership refresh. Terms used below:

- **base**: the anchor's entries whose provenance is not `chain` (today's `genesis`, `invite`, `operator`, `claim`).
- **live owner rows**: `OwnerKey` rows whose `StampId` is not retired in `Revocation`.
- A live row is **derivable from a set S** when its stored proof verifies against S. Owner-signed (`VouchSig` set): `VouchOwner` is in S and `verifyOwnerKeyVoucher(key, stampId, vouchOwner, vouchSig)` holds. Invitation-admitted (`VouchSig` null, `VouchUsage` set): the usage row names this key and this row's stamp (`usage.peerKey === row.key`, `usage.ownerStampId === row.stampId`), the invitation grants ownership, its issuer is `VouchOwner` and is in S, and the three signatures of the chain verify (the invitation's add signature, the holder's redeem signature, the device's consent signature). The founding row (all three null) is never derivable; founders enter anchors only out of band.
- **derived**: the least fixpoint starting from base: add every key whose live row is derivable from what is already in the set, until nothing changes. **chainDerived** is derived minus base, plus any base key that also has a live derivable row.
- **removed**: a key K is removed when an `OwnerKey` tombstone names K whose signer is in base ∪ derived, whose signer is not K, whose stored signature verifies (`verifyRevocationSigner`), **and** K is not in chainDerived. The last condition is what makes a re-add win over an older tombstone: a removed owner re-added under a fresh stamp has a live derivable row again, and the old stamp's tombstone no longer applies.
- **target** = (base ∪ chainDerived) minus removed. If target would be empty, no removal is applied this pass (target = base ∪ chainDerived) and a line is logged. All tombstones are judged against the pass-start set at once, so the outcome does not depend on the order they are read in.
- Apply: `trust(k, 'chain')` for every key in target but not in the store; `remove(k)` for every key in the store but not in target. That second step both drops base keys a verifiable tombstone names and prunes `chain` entries whose row is gone.

**Deviation from the plan ticket, kept deliberately.** The plan said an owner C vouched by B stays trusted when B is removed. That rule diverges: a machine that already held C keeps it, a machine enrolled afterwards can never derive it (B's row is retired, so the chain from base to C is broken), and the two never agree. The rule above prunes C everywhere until a remaining owner re-adds it, which is what `CadrePeer` already does for devices vouched by a removed owner (the rotation NOTE on `listAuthorizedMembers`). The device-removal plan ticket is told to re-vouch what a removed owner added.

**Order of owner removals is not recoverable from replicated state.** A removed owner whose own copy has not converged can still file tombstones that replicate (the schema's write-time checks read the local live table, as its header says). A node that processes such a tombstone before the owner's own removal honours it; a node that processes them together or in the other order does not. Accept and document: the remaining owner heals it by re-adding the wrongly removed owner under a fresh stamp, which every node then re-derives.

## Where it runs

`CadreNode.syncOwnerAnchor(reason, retry)` is the first step of `refreshAuthorizedControlPeers`, before `listAuthorizedMembers`, so the membership snapshot built in the same refresh judges rows against the updated anchor. That refresh already runs on every membership write (the hub in `mutateCadrePeer`, which the owner-key writers and the invitation redemption go through), at start, after a seed, after an invitation redemption and on every timed cohort reconcile, so replicated changes are picked up with the same bounded staleness as membership rows. Seed trust needs nothing: `SeedBootstrapService.applySeed` reads `trustedOwners.all()` per seed. `createCadreInvitation` exports `all()` as the bundle's pins, so an invitation now carries every current owner; that is the intended meaning of "the issuer's anchored owner keys".

The reads honour `retry` for the reason on `refreshAuthorizedControlPeers` (the listener runs with the database write lock held): `queryOwnerKeyRows(retry)` (new; `Key`, `StampId`, `VouchOwner`, `VouchSig`, `VouchUsage`, retired stamps excluded as `queryCadrePeers` does), `queryRevocations(retry)` filtered to `tableName === 'OwnerKey'`, and the invitation chain (`loadInvitationChain`, only when some owner row is invitation-admitted). Load the chain once per refresh and hand it to `listAuthorizedMembers` too, rather than reading the two tables twice. Any read failure skips the whole sync and leaves the anchor as it was; the refresh then keeps its previous snapshot, as it already does.

With an empty base the sync does nothing and anchors nothing. A node waiting to be claimed (`isAwaitingClaim`: claim secret set, anchor empty) must stay empty until the claim; assert the early return at the seam.

## Pieces

- `trusted-owner-store.ts`: `TrustSource` gains `'chain'` (and `KNOWN_SOURCES`, or the discard-all loader drops the whole anchor on reload); the interface gains `sources(): ReadonlyMap<string, TrustSource>` on both backends so the sync can split base from chain; `trust()` with a non-chain source over an existing `chain` entry rewrites the provenance (out of band wins), while `trust(k, 'chain')` over any existing entry stays a no-op. ## Edge cases & interactions

- **Chain of two in one pass, mixed proofs** (base {A}; B owner-signed by A; C admitted by B's owner-granting invitation): both derived in one pass. Unit test on `deriveOwnerAnchor`, with a real signed chain built the way `control-cadre-invite.spec.ts` builds one.
- **A row whose voucher is not anchored yet** is simply not derived; no error, no log above debug; it is derived on the pass where the voucher is. Same code path as the fixpoint test; inspection.
- **Owner C vouched by B; B removed** (tombstone by A, B's row retired): C is pruned from every anchor; after A re-adds C (fresh stamp, vouched by A), C is derived again. Unit test.
- **Re-add beats an older tombstone**: K removed under stamp s1, re-added under s2; the s1 tombstone is ignored because K is in chainDerived. Unit test.
- **Mutual removal that would empty the anchor** (base {A, B}, each tombstoned by the other): no removal applied, logged; with a third owner C in base both are removed and C remains. Unit test.
- **Partition merge**: two owners each add an owner; both rows verify from the same base after merge; the fixpoint is set-based and order-free. Inspection.
- **Read failure**: anchor untouched, snapshot kept. Inspection; the refresh's existing never-rejects contract.
- **The node's own key is removed**: applied like any other key, so its own vouches stop verifying locally; `initializeSeedBootstrap` re-anchors it as `genesis` at the next start and the first sync removes it again. Self-shutdown on removal is the device-removal plan ticket's. Inspection; name the window in the docs.
- **An operator pin of a removed key** is re-anchored at every start (`initializeTrustedOwnerStore`) and removed by the first sync (`refreshMembershipGate('start')` is fired without await at start). Bounded by one refresh; `NOTE:` at `initializeTrustedOwnerStore`.
- **Persisted `chain` entries** are honoured between start and the first sync, then recomputed. Inspection.
- **A tombstone whose signer is only a stale pin here** (pinned by the operator, removed elsewhere) still counts if the signer is in the pass-start set; its own tombstone removes it in the same pass. Covered by the simultaneous semantics; inspection.
- **Cost**: one `OwnerKey` read and one `Revocation` read more per membership refresh, plus the invitation chain when any owner row is invitation-admitted; `NOTE:` at the sync pointing at the existing memo suggestion on `loadInvitationChain`.
- **`trust()` provenance upgrade**: one unit test in `trusted-owner-store.spec.ts`, "trusting a chain-derived key out of band promotes it; trusting an out-of-band key as chain does not demote it", on the memory backend (the persistent one shares the branch through the same method body or gets the same assertion).
- **The CLI and host surfaces** list nothing new here; `cadre enroll` and the admin routes are unchanged. The reference apps' `runOwnerGenesis` self-anchor is base and unaffected.
