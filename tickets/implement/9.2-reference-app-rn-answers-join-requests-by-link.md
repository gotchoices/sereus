# Phone reference app answers a join request opened as a link (owner side)

The owner app's half of the same-phone join. The kit pieces (link formats, the request's `reply`, the config plugin's `appLinks` option) come from `phone-kit-same-phone-join-links`; the request, the targeted invitation and the existing approval prompt are Settings → **Add a device or app** (`src/add-device-section.tsx`, docs/reference-app-rn.md → "Adding a Device or App"). The joining app's half is `reference-app-rn-asks-owner-app-by-link`.

Terms: **A** is this app holding the cadre; **B** is the app asking to join. "Arrived as a link" means the request came through `+native-intent.tsx`, not the paste field or the scanner.

## Behaviour

1. **Routing.** `app/+native-intent.tsx` stays the one link hook. It keeps the node-code case and adds a kit `parseCadreLink` case: a `join-request` link becomes `/settings?joinRequest=<encodeURIComponent(text)>`; a `join-response` link becomes `/settings?joinResponse=…`. The response case is routed here so the hook stays in one place; the joining-side ticket handles that parameter. Nothing logs either path.
2. **Holding.** `useLinkedJoinRequest()` in `settings.tsx`, modelled on `useLinkedNodeCode()`, copies the parameter into screen state and clears it. It decodes the request with `decodeCadreJoinRequest`; a request that does not decode shows the existing "Cannot use this request" alert and sends nothing back, since there is no reply to trust.
3. **Settled before the section.** Two outcomes are settled at the Settings level, because Add a device or app is not mounted in either case:
   - This app's own request (its peer id equals `identityPeerId()`): hand it to the joining-side hook (`reference-app-rn-asks-owner-app-by-link` adds that action; until it lands, show the existing "This is this app's own request" alert).
   - No cadre (the first-launch condition `asking` in `settings.tsx`: nothing saved, nothing running or starting, no join on screen): answer `no-cadre` when the request has a reply, else alert "This app has no cadre yet".
4. **Waiting for a node.** Otherwise, while the node is not connected, the request waits. The Node card gets a hint like `nodeCodeHint`: "A join request from ‹appName› is waiting; connect to answer it". While auto-start is connecting, it is handed over once connected. When connected, it passes to `AddDeviceSection` through the existing `linkedRequest` / `onLinkedRequestTaken` props, which settings.tsx does not pass today.
5. **In the section.** `handleRequest` runs as for a pasted request, plus:
   - **Answering instead of alerting.** When the request arrived as a link and carries `reply`, the outcomes that are alerts today are answered instead: not an owner → `not-owner`; already in this cadre (`isMemberPeer`) → `already-member`. The cadre-read failure alert stays an alert, with no answer; B's waiting line and Cancel cover it.
   - **Prompt wording for a link.** The approval prompt reads: title "An app on this phone asks to join your cadre"; a line "It calls itself ‹appName›. That name cannot be checked."; the shortened peer id as **Code**, with "Check it matches the code the asking app showed"; a line saying what is granted ("Allowing lets it take part in your cadre. With Also an owner on, it can also add and remove devices and apps and approve everything in the cadre."); the **Also an owner** switch (on by default, as today); and the buttons **Allow** / **Deny**. A pasted request keeps today's prompt.
   - **Allow.** Mint the targeted invitation (`mint`, as today, 24 h default). Then open `joinResponseLink(reply, { invitation: encoded, appName })`, where `appName` is this app's `expo.name`, the name the request builder already uses.
     - Opened: show the notice "Sent an invitation to ‹appName›", not the ShareCode view. The invitation also shows under Outstanding invitations.
     - `Linking.openURL` rejects, or `joinResponseLink` throws for length: show the minted invitation in the ShareCode view as today, with the notice "Could not open ‹appName›; copy this invitation into it". Log the error without the link.
   - **Deny.** Open the `denied` answer, and start a 30-second cooldown (a ref holding a timestamp). During it, a request that arrived as a link with a reply is answered `denied` without a prompt. This bounds prompts to one per 30 seconds after a denial whatever peer ids a repeating app sends. Opening another app needs the opener in the foreground, so a flood is visible to the user anyway.
   - **One at a time.** A request arriving while a prompt is open or a mint runs is dropped with the existing notice and gets no answer: opening B then would pull the user out of the prompt on screen.
6. **Request without `reply`** (the Android camera opening a request QR code, or a plain link): handled exactly like a pasted request; the invitation shows for copy.
7. **Native config.** In `app.json`, change the kit plugin entry to `["@serfab/cadre-rn", { "appLinks": true }]`. The joining-side ticket replaces this with the variant-aware config. This needs a native rebuild; docs/reference-app-rn.md → "When Native Rebuild Is Needed" says so.

Put answering in a small module, `src/join-link.ts`: `answerJoinRequest(request, answer)` builds the link with the kit and opens it with `Linking.openURL`. It returns whether the link opened and logs the failure.

**Seam for `app-recommends-another-app-and-enrolls-it`:** that ticket will answer a request from an app with a pending handoff without a prompt. The check belongs at the top of the arrived-as-link branch in `handleRequest`; leave the branch shaped so one early return fits there. Do not build it here.

## Edge cases & interactions

- A request arrives during a cold start. Auto-start is connecting, so it waits and the prompt opens once connected, as a node code does. Verified by inspection against `useLinkedNodeCode` and `AddNodeSection`.
- A request arrives while this app is mid-join, switching its own cadre (`joinFlow` on screen): it waits until connected. Verified by inspection.
- A stopped node (user disconnected) gives the waiting hint and no answer; B's Cancel is the way out. Verified by inspection.
- The first-launch question is on screen: answered `no-cadre`. When the launch read is still `reading`, wait for it; when it `failed`, hold like a disconnected node. Verified by inspection.
- A member-only device answers `not-owner` and never shows the prompt. Verified by inspection.
- The same request arrives twice (B tapped twice): the second is dropped while the first prompt is open, and B's store reuses its nonce (kit ticket), so answering the first satisfies B. Verified by inspection.
- A request with a reply arrives through the paste field: no link is opened, and the invitation shows for copy. Verified by inspection of where the arrived-as-link flag comes from: only `linkedRequest` sets it.
- Allow, then the link fails to open (B uninstalled meanwhile): the invitation shows for copy, and an unused targeted invitation expires on its own or can be withdrawn. Verified by inspection.
- Deny when the refusal link fails to open: log only. Verified by inspection.
- The cooldown never applies to a pasted request. Verified by inspection.
- A Settings remount loses the held request and the cooldown (screen state, as the minted invitation already is; see the `NOTE:` at `AddDeviceSection`). Acceptable, because B's Cancel and a retry recover. No change.
- iOS opening A while A is in the background with a prompt already open: it is dropped as "one at a time". Verified by inspection.

No new unit tests: the branches are routing and mapping over kit calls that carry their own tests. The device run (filed by the joining-side ticket) covers the real link delivery.
