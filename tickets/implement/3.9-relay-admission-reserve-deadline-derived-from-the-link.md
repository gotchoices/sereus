# Relay admission's reserve deadline derived from the declared link

## Why

A control node that runs a relay server admits an inbound connection it cannot place as a member (verdict `'admit-for-relay'`) only so the peer can ask for a relay reservation. `createMembershipConnectionGater` arms a timer at that verdict and closes the connection unless a reservation is **admitted** at `denyInboundRelayReservation` first. The timer is `RELAY_ADMISSION_RESERVE_DEADLINE_MS`, a fixed 5 000 ms marked `link-bound, not yet derived`.

What the timer has to contain, from the moment it is armed (checked against `node_modules/@libp2p/circuit-relay-v2/dist/src/transport/reservation-store.js` `addRelay`, which opens the connection and immediately opens the hop stream, with no wait for identify):

1. The client sent its last Noise handshake message and, with its dial resolved, immediately opened the hop stream; both arrive at the relay together. The relay's gate runs on the handshake message and arms the timer; the relay then answers the protocol negotiation.
2. The answer reaches the client and the client sends the RESERVE request, which reaches the relay: one round trip on the client-to-relay hop. When all of the link's delay is on the client's own hop (a phone on a congested mobile link), that hop's round trip is the whole link round trip.
3. The relay's hop handler calls `denyInboundRelayReservation`, whose decision may take the full `ADMISSION_DECISION_TIMEOUT_MS` (2 000 ms) before it disarms the timer.

So the deadline needs one link round trip plus one admission decision. At the supported 3-second link that is 5 000 ms, exactly the current value, with no margin. `repro: static`: arithmetic, not observed. If it expires, the relay closes the connection and the client's reservation drive retries on its own backoff, so the failure is quiet.

## Change

In `link-budget.ts`:

- `RELAY_RESERVE_REQUEST_ROUND_TRIPS = 1`, documented with the three steps above. It is the table's existing "request a reservation on an open relay connection" count; reuse it in that row rather than adding a second row.
- `relayAdmissionReserveDeadlineMs(linkRoundTripMs?) = RELAY_RESERVE_REQUEST_ROUND_TRIPS × resolveLinkRoundTripMs(link) + ADMISSION_DECISION_TIMEOUT_MS`: 5 500 ms at the default declaration. The comment states the cost: a stranger that connects and never reserves holds a mute connection 0.5 s longer at the default.
- Pin it with one `expect` in `link-budget.spec.ts`'s existing "multiplies each operation's round-trip count … plus its admission decisions" test.

In `membership-connection-gater.ts`:

- `RELAY_ADMISSION_RESERVE_DEADLINE_MS` becomes `relayAdmissionReserveDeadlineMs()` (the default declaration), so its `link-bound, not yet derived` directive goes away. Keep the exported name; it is the default of `createMembershipConnectionGater`'s `reserveDeadlineMs` parameter and tests use it. The import from `link-budget.ts` adds no cycle: the gater already imports `ADMISSION_DECISION_TIMEOUT_MS` from there.
- Say in its comment that the relay's **own** declaration is the input, because the relay is the machine that decides.

In `cadre-node.ts` (~1907): pass `ADMISSION_DECISION_TIMEOUT_MS` and `relayAdmissionReserveDeadlineMs(network?.linkRoundTripMs)` as the gater's third and fourth arguments.

**The dedicated relay container is not affected.** `ops/docker/libp2p-infra/src/main.ts` runs no cadre gater (its own comment says so at ~160), so it has no reserve deadline to derive. The original ticket said the derivation had to reach it; that was wrong.

## Edge cases & interactions

- **Admission decision that fails open.** When `admitRelayReservation` exceeds its deadline or throws, the gate admits and disarms. The derived deadline already contains one full decision, so a fail-open disarm always lands before the timer. By inspection.
- **Reservation refused.** The timer clears only on admission; a refused reservation leaves it to fire and close the connection. Unchanged.
- **A client with the reservation queue busy.** libp2p's reservation store runs reservations one at a time, but it opens the connection inside the queued job, so the connection is never armed while waiting. By inspection; no change.
- **Declared link faster than the client's.** A relay declaring 500 ms gets a 2 500 ms deadline and closes a slow client's connection before its request arrives. This is the module doc's existing "A machine that declares a faster link than its peers" case; add relay admission to that bullet.
- `packages/integration-tests/src/scenarios/relay-only-control-addr.integration.ts` ~313 quotes the timer as "5 s" in a comment; update the figure. Check that the scenario does not wait a fixed time tuned to 5 s.
- `tickets/backlog/bug-party-run-relay-drops-a-stranger-dialing-through-it.md` quotes this timer as "(5 s)". Update the figure there to "5.5 s at the default declaration"; that bug is about whether such a connection should be dropped at all, which this ticket does not change.
