## Why

`cadre-host start` must delegate authority operations to a spawned **authority cadre node** rather than embedding an in-process `CadreNode` (control-plane separation — see `docs/cadre-host.md` § "Control-plane separation"). For that to be possible, the node a cadre-cli child runs must expose those operations over a same-machine channel. Today `cadre-cli start` builds a `CadreNode` but never calls `initializeSeedBootstrap`, so it cannot mint invites or authorize peers, and it has no admin surface at all (only the read-only `/health` + `/metrics` `HealthServer`).

This ticket adds that surface. It is consumed by `6.7-cadre-host-authority-node-delegation`, which spawns the node and builds the channel adapters; nothing in cadre-host depends on this landing in a *particular* shape beyond the wire contract below, so design the contract first.

## Decisions (resolving the plan-stage open questions)

- **Topology — single authority node.** A cadre is *one party's* nodes sharing one control network; trust-circle members are `CadrePeer` rows (devices that dial in), per `docs/architecture.md`. cadre-host spawns exactly one authority node that founds/joins the household control network. The older "one node per member" sketch in `cadre-host.md` is rejected; 6.7 updates that doc.
- **Transport — loopback HTTP, startup-token auth.** The admin surface is a `127.0.0.1` HTTP listener on an orchestrator-allocated `adminPort`, authenticated by the existing `CADRE_STARTUP_TOKEN` presented as `Authorization: Bearer <token>`. Rationale: the orchestrator spawns children **detached** with direct-fd log inheritance so they survive an orchestrator restart and are re-attached via `init()` (see `HostProcessOrchestrator` class docstring). A stdin/stdout IPC pipe cannot survive that re-attach; an HTTP loopback port can — the manager only needs the persisted `{adminPort, token}` to reconnect. This mirrors how cadre-provider drives its drones over REST.
- **Authority node = normal `start` child + flags.** No separate entrypoint. New `start` options turn an ordinary node into the authority node.

## Wire contract (admin channel)

All routes bound to `127.0.0.1:<adminPort>`, require `Authorization: Bearer <CADRE_STARTUP_TOKEN>` (constant-time compare), JSON bodies, and the cadre-provider-style envelope `{ ok, data }` / `{ ok:false, error:{ code, message } }`. Errors carry stable codes the host maps to HTTP status (`not_authorized`, `not_ready` when the node/seed-bootstrap isn't up yet, `bad_request`, `internal`).

| Method & path | Purpose | Request → Response |
|---|---|---|
| `GET /admin/identity` | peer-id read | → `{ peerId, partyId }` |
| `GET /admin/multiaddrs` | observed libp2p addrs | → `{ multiaddrs: string[] }` |
| `GET /admin/members` | `CadrePeer` enumeration (replaces handing a `ControlDatabase` to the manager) | → `{ members: { peerId, multiaddr }[] }` |
| `GET /admin/members/:peerId` | membership probe | → `{ member: boolean }` |
| `POST /admin/invites` | mint a `CadreInvite` | `{ token?, expiresInMs? }` → `{ invite: CadreInvite, encodedInvite }` |
| `POST /admin/accept-phone` | authorize a redeeming peer | `{ phonePeerId, token?, issuedInvite?: CadreInvite }` → `{ ok:true }` |
| `DELETE /admin/members/:peerId` | signed `CadrePeer` delete | → `{ ok:true }` |
| `PUT /admin/invite-addresses` | push NAT-resolved invite addrs (resolver transport) | `{ addresses: string[] }` → `{ ok:true }` |

`encodeInvite` does not need its own route — it is pure (`CadreNode.encodeInvite`) and the host already has the `CadreInvite` from `POST /admin/invites`; the host can encode locally by importing the helper, or the mint route returns `encodedInvite` (it does). Keep `encodeInvite` reachable from the host adapter via the returned `encodedInvite` to avoid a round-trip.

### inviteAddressResolver transport (the one cross-plane hook)

`SeedBootstrapService.createInvite` already consults an optional `inviteAddressResolver: () => Promise<string[]>` (`seed-bootstrap.ts:644`). Replace the synchronous in-process callback model with a **push** model:

- The node keeps a `latestInviteAddresses: string[] | null`, set by `PUT /admin/invite-addresses`.
- The node installs an `inviteAddressResolver` that returns `latestInviteAddresses` when non-null, else falls back to `libp2pNode.getMultiaddrs()` (current default behavior).
- The host (6.7) pushes addresses at spawn and on every NAT change (`NatService.start` / `putSettings` / `testReachability`).

Push (host→node) is chosen over callback (node→host) so the control-network node never needs to know or dial the manager's address; invite addresses change rarely, so push-on-change is cheap and avoids a synchronous boundary inside `createInvite`.

## Authority initialization & genesis

The host identity is a libp2p Ed25519 protobuf key at `<dataDir>/identity.key` (`installer/identity.ts`). The cadre node already takes this as its libp2p `privateKey`. The **authority key** used by `SeedBootstrapService` is a base64url Ed25519 private key (`@optimystic/quereus-plugin-crypto`). Use the *same* household identity for both so the node's peer identity and its authority key are one keypair:

- On `start` with `--authority`, after `node.start()`, derive the base64url raw Ed25519 private key from the loaded libp2p `PrivateKey` (its `.raw` 32-byte seed → base64url) and call `node.initializeSeedBootstrap(authorityKeyB64)`.
- **Genesis**: if `CadreControl.AuthorityKey` is empty (fresh party), insert this node's authority public key via `ControlDatabase.insertAuthorityKey(pubKey)` — the schema's `Authorized` constraint permits the first key with no prior authorization (`control-database.ts:26`). On an existing party the key is already present; skip.

> **Implementation risk to verify first:** confirm the byte-for-byte bridge between libp2p's `privateKeyFromProtobuf(...).raw` and what `getPublicKey(privKeyB64, 'ed25519', 'base64url', 'base64url')` expects (Ed25519 seed vs. expanded key). Write the bridge as a tiny tested helper in cadre-core (e.g. `authorityKeyFromLibp2p(privateKey): { privateKeyB64, publicKeyB64 }`). If the encodings don't line up, fall back to persisting a dedicated authority key alongside the identity and document that the peer-id and authority public key differ — but the single-key path is strongly preferred.

## CadreNode/CLI surface changes

`cadre-cli start` new options:
- `--authority` — initialize seed-bootstrap from the node identity + run genesis (above).
- `--admin-port <port>` (or `CADRE_ADMIN_PORT`) — bind the admin HTTP listener on `127.0.0.1`. Requires `CADRE_STARTUP_TOKEN` in env; refuse to bind without it.

The admin listener lives next to `HealthServer` in `cadre-cli/src/server/` (new `admin-server.ts`), attaches to the `CadreNode`, and is started after `node.start()` + authority init. It must `close()` on shutdown alongside the health server.

`HostProcessOrchestrator` (in cadre-host) already spawns `cadre-cli start` with `--health-port/--metrics-port/--startup-token-file`; 6.7 extends the spawn args with `--authority --admin-port`, allocates the admin port, and passes the identity via the child config. Confirm here that the child config / `start` can load the host identity: either via `identity.keyFile` pointing at `identity.key` (note: `loadPrivateKey` currently expects hex-or-raw; the installer writes a libp2p **protobuf** key — the loader needs a protobuf path, or `start` gains a `--identity-protobuf <path>` that uses `privateKeyFromProtobuf`). Resolve this loader gap as part of this ticket since it's node-side.

## Tests (TDD targets)

- **authority-key bridge helper**: given a generated libp2p Ed25519 key, `authorityKeyFromLibp2p` yields a base64url priv/pub pair where `getPublicKey(priv)` === pub, and `verify` round-trips a signature. (Pure, fast.)
- **admin-server auth**: requests without/with-wrong bearer → 401 `not_authorized`; correct token → 200. Body parse errors → 400.
- **admin-server delegation** (mock `CadreNode`): each route calls the matching `CadreNode` method with the decoded args and maps thrown errors to `{ ok:false }` with `not_ready` when seed-bootstrap is uninitialized.
- **invite-address push**: after `PUT /admin/invite-addresses`, a subsequent `POST /admin/invites` embeds the pushed addresses; with none pushed, it embeds `getMultiaddrs()`.
- **genesis**: starting `--authority` against an empty control DB inserts exactly one AuthorityKey; starting again is idempotent (no duplicate / no throw).
- **protobuf identity load**: `start` loads the installer-written `identity.key` and the node's `peerId` matches `peerIdFromPrivateKey` of that key.
