# Claiming a strand this node already hosts as a storage replica

## Context

`always-on-node-hosts-unclaimed-strands` lets a storage-profile node run a strand with no sApp config (a **storage replica**: the strand's libp2p node, raw storage and `Strand` membership schema, without the app's `App` schema). If an app on that same machine later calls `CadreNode.addStrand` for the strand — the realistic case is a storage-profile embedder whose watcher poll wins the race against its app's `addStrand` after a restart — `startOrFoundStrand` finds the tracked instance and returns it unchanged. The app then holds a database with no `App` tables, and `addStrand` has already recorded the config in `sAppConfigs`, so nothing ever retries.

## Design

Upgrade the tracked instance in place by applying the `App` schema to its **live** database. No runtime rebuild: the libp2p node, its peer id, its connections, the raw store and its warm cache all stay. The replica already holds the strand's blocks, so the new tables read from local storage; nothing re-syncs.

Rejected alternative: quiesce and resume the instance with the sApp config added to its retained launch config. It reuses a proven path, but it drops every strand connection for the rebuild and races the hibernation manager's own quiesce/wake of the same instance (the manager owns that bookkeeping; `StrandInstanceManager` does not). The in-place apply has neither problem and is the same declarative apply a warm restart already runs.

### One schema-apply site

Extract step 7 of `composeStrand` into an exported `applyAppSchema(db: Database, schema: string): Promise<void>` in `compose-strand.ts` (the `declare schema App { … } apply schema App;` exec), call it from `composeStrand`, and export it from the package index. The comment at step 7 says strand DDL wiring stays at one composition point; this keeps it there.

### `StrandDatabase.attachAppSchema(sAppConfig)`

Requires an initialized database. Calls `applyAppSchema`, then records `sAppConfig` on its own config (so a later `ensureFounderBootstrap` has the sApp for the `Header`). Idempotent: the apply is a declarative diff, so re-applying the same schema emits nothing.

### `StrandInstanceManager.attachSApp(strandId, sAppConfig, { requireSignedSchemas })`

Modelled on `foundExistingStrand`:

1. Throws for an untracked id (caller bug).
2. If `instance.sAppInfo` is already set: returns `'already-attached'`. (A *different* sApp for a claimed strand is out of scope — today's behaviour for a second `addStrand` is to return the tracked instance; keep that and log when the ids differ.)
3. `assertSchemaSignature(sAppConfig, { requireSignature })` **before** touching anything, exactly as `startStrand` does.
4. Replace the retained launch config with `{ ...config, sAppConfig }` (fresh object — the retained one is the caller's), so every later rebuild (hibernation wake, relaunch) applies the schema through `composeStrand`.
5. If a live database exists — `instance.database`, or the first-sync gate's held database while the instance is still `'syncing'` — `attachAppSchema` on it. If quiesced, skip: the next resume applies it.
6. Only after success: set `instance.sAppInfo` and, when the config carries one, `instance.latencyHint`. Return `'attached'`.

A failed live apply leaves the retained config updated (still the wanted state) and `sAppInfo` unset, so the next claim retries the apply; the rejection propagates.

### `CadreNode.startOrFoundStrand`

On the tracked-instance branch, when `sAppConfig` is present and the instance has no `sAppInfo`, call `attachSApp` (passing `this.config.requireSignedSchemas`) **before** the founder branch. Order matters: `foundExistingStrand` → `ensureFounderBootstrap` writes the `Header`'s sApp columns and must see the attached config. After a successful attach emit nothing new (`strand:started` already fired for the replica); `addStrand`'s existing `whenWritable` wait covers a still-syncing instance.

## Edge cases & interactions

- **Claim of a hibernating replica**: config updated, no live apply, `addStrand` returns the hibernating instance as it does today for any hibernating strand; the wake's rebuild applies the schema via `composeStrand`. Inspection.
- **Claim while the replica is `'syncing'`** (no `Header` yet): apply on the gate-held database; the gate's probe then also reads the new `App` tables (`appTablesReadable` walks the catalog), which is correct — the app's tables must be fetched before the app writes. Inspection.
- **Claim racing a hibernation quiesce**: the quiesce closes the database mid-apply → apply rejects → `addStrand` rejects and hands the strand back to the watcher (`forgetStrand`) → the retry goes through `handleStrandAdded`'s claimed branch → tracked instance, `sAppInfo` unset → apply again (or, if now quiesced, config-only). Converges. Inspection.
- **Founder claim on a replica** (storage-profile embedder founded the strand, restarted, watcher launched a replica first): attach, then `foundExistingStrand` runs the insert-if-absent bootstrap with the sApp present. This is the case worth a test (below).
- **Unsigned schema on a node requiring signatures**: `attachSApp` throws before changing anything; the replica keeps running as a replica. Inspection — the throw is the same `assertSchemaSignature` `startStrand` uses.
- **Latency hint change**: `HibernationManager` reads `instance.latencyHint` at each timer action, so the new hint applies from the next timer; an already-armed timer keeps its old duration once. Acceptable; say so in a one-line comment at the assignment.
- **`getSAppId` after the claim**: `sAppConfigs` now answers first; the Header-derived fallback from the prereq ticket agrees (same strand). Inspection.
- **`discoveredStrands`**: `addStrand` already deletes the entry before launching. Inspection.

## The test that matters

One unit spec in `packages/cadre-core/test/` against a real `StrandInstanceManager` (the existing strand-manager specs show how to start one on in-memory storage with no peers): start a strand as a **founder-less replica** (no `sAppConfig`), then call `attachSApp` followed by `foundExistingStrand` (the order `startOrFoundStrand` will use), and assert: the `App` table exists and accepts an insert, the `Strand.Header` row carries the sApp id/version, and the instance's libp2p peer id is unchanged across the upgrade (no rebuild). If driving `foundExistingStrand` needs `CadreNode` wiring the spec cannot reach cheaply, drop the founder half and assert the attach alone — the ordering is then verified by inspection in `startOrFoundStrand`.

Run `yarn workspace @serfab/cadre-core test`, `yarn workspace @serfab/quereus-plugin-sereus test`, `yarn lint`, and the type check in the foreground.

## Added at implement of `always-on-node-hosts-unclaimed-strands`

Two more ways a claim reaches a running replica, found while building the replica launch. Both resolve at the same site this ticket owns (`CadreNode.startOrFoundStrand`), so they are arms here, not new tickets.

- **Concurrent launches can bypass the tracked-instance branch.** `handleStrandAdded` skips the replica launch when a `strand:discovered` listener claims the strand synchronously (the `sAppConfigs.has` re-check after the emit). A claim that arrives *while the replica launch is still awaiting* `resolveCohortSeed` (or the party-key read) passes `startOrFoundStrand`'s `getInstance` check before the replica's `startStrand` registers the instance. Whichever reaches `StrandInstanceManager.startStrand` second hits its "already running" early return and gets the other's instance back — if the replica won, `addStrand` returns the replica with no `App` tables, and the tracked-instance branch this ticket adds never ran. So the attach has to run on the instance `startStrand` returns as well (sApp config given, returned instance has no `sAppInfo`), or launches of one strand id have to be serialized. Pre-existing for two claimed launches of the same strand (harmless there: same config both ways).
- **`foundStrand` on a storage-profile node.** `foundStrand` is `publishStrand` then `addStrand({ founder: true })`. A watcher poll between the two sees an unclaimed row and launches a replica (forced joiner); the `addStrand` then finds it tracked and calls `foundExistingStrand` → `StrandDatabase.ensureFounderBootstrap`, which throws "Cannot found strand … as a storage replica". Attaching before the founder branch (this ticket's ordering) fixes it; it is a second trigger for the "founder claim on a replica" case worth covering in the same spec.

Until this ticket lands, both fail visibly (`strand:error` on the retry ladder for the founder case; a strand with no `App` tables for the joiner case). No shipped embedder runs `profile: 'storage'` and calls `addStrand`/`foundStrand` — the reference apps are phones (`transaction`), and the integration harness defaults `hostUnclaimedStrands` to false.
