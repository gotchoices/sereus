# Strand removal e2e and docs

Third of three tickets implementing `plan/4-removal-must-cut-the-network-not-just-the-row`.
The gate and teardown exist; this ticket proves the whole claim over a real network and
then makes `docs/strands.md` tell the truth about it — the original issue
(gotchoices/sereus#4) was an app author unable to word a "remove member" button honestly.

Build on the fixtures and idioms of `strand-membership-closed-strand-e2e.integration.ts`
(bring-up, `waitUntil` gates, distinct per-party member keys via `consumeInvite`,
`registerMemberPeer` for real strand peer ids, rejection assertions last).

## Scenarios (the plan's test list, made concrete)

1. **Closed strand, two parties, one removed.** Register both parties' real strand peer
   ids as `MemberPeer` rows; revoke party B; drive/await enforcement refresh on A; assert:
   - A holds no connection to B's strand node (teardown of the already-open connection —
     assert the connection existed BEFORE the revocation, then is gone, not merely that
     future dials fail).
   - B's writes no longer replicate to A, and B cannot pull new blocks from A (its reads
     of post-removal writes fail or never converge — bound with a timeout assertion, and
     assert A's gate denial rather than relying on silence alone: the per-stream gate logs
     under `sereus:cadre:*`; prefer asserting observable state, e.g. B's `waitUntil` on
     the new row times out while a control read on A succeeds).
   - Writes still commit among the REMAINING cohort after the cut (the cohort-eviction
     arm: exclusion is automatic once connections are cut; if this stalls or throws
     `cluster-fetch:no-quorum`, stop and report — that is the upstream tripwire the
     teardown ticket names, not something to work around in the test).
2. **Removed party on two machines.** B registers two strand peer ids; both are cut.
3. **Open strand unaffected.** An open (`Type='o'`) strand: a stranger connects and
   participates; perform an unrelated closed-strand removal in the same process to show
   the enforcement did not leak across strands; assert no enforcer armed on the open
   strand (options-level assertion is acceptable here if a full open-strand fixture is
   disproportionate — say which in the test comment).
4. **Stale revocation view, asserted deliberately.** Before the revocation replicates to
   a remaining member C (or by suspending C's refresh), C still serves B — assert the
   chosen fail-open direction holds, then let the tombstone arrive and assert the cut.
   A two-machine remaining party (A's second machine) is the cheapest C.
5. **Self-revocation signal.** B (still connected at revocation time) eventually observes
   `strand:revoked` — this doubles as the "is the removed party told" product answer:
   best-effort, only if the tombstone reached it first.

Keep the file within the integration-test conventions (foreground run, no output
redirection; if a log is needed, `| tee tickets/.logs/<slug>.test.log`).

## Docs (`docs/strands.md` → "Removing Members" and around)

State plainly, in the existing section's voice:

- **What removal now guarantees**: once the revocation replicates to a remaining member's
  machines, they refuse the removed party's machines at the network layer — new
  connections, new streams, relay reservations, and outbound dials — and close the
  sessions already open. Enforcement is per-machine and eventually consistent: a machine
  that has not yet seen the revocation serves the removed party until it has (the chosen
  fail-open direction, and why: never partition a legitimate member on missing data).
- **The deny record is the orphaned device row.** A removed member's `MemberPeer` rows are
  what remaining machines recognize its nodes by. Update the existing "clearing the
  removed member's device records is a separate step" bullet: clearing an orphan now also
  forgets the network denial of that machine — housekeeping is no longer free; do it only
  for a machine that is truly gone or a binding that should never have existed.
- **What removal still does NOT do** (each already tracked, reference, don't absorb):
  past reads stay readable and the member key is not rotated (existing "forward-looking"
  bullet stands); a held unspent invitation still re-admits
  (`feat-strand-invitee-bound-invites`); and on a production-formed strand today every
  party presents the same founding member identity and no device rows are written, so
  per-party removal is not yet reachable from an app at all until
  `feat-strand-party-identity` lands — the enforcement machinery is in place and proven,
  the identity it needs is not.
- **Delegate admission is not a bypass** (plan TODO 7, resolved as no-change): delegate
  grants are announced over the membership-gated `/sereus/strand-addr/1.0.0` RPC, i.e.
  only within a party's own control network, so another (removed) party's machines never
  hold one; and a grant admits only a connection and a relay reservation on the granting
  party's own control node — the removed peer that somehow rides a relay still hits the
  strand node's own per-stream gate. One sentence in the docs; no code.

Also fix the now-stale claim in the "Relay willingness" deferred bullet that the durable
`MemberPeer` attestation "waits for strand-mesh admission control" — the revocation side
of that binding now exists; the admission (allowlist) side still waits on
`feat-strand-party-identity`.

## Edge cases & interactions

- **Fixture honesty**: tests must register `MemberPeer` rows explicitly (production does
  not yet — that is `feat-strand-party-identity` step 2); put one comment at the
  registration site saying so, so the e2e does not silently overstate production behavior.
- **Timing**: drive the enforcer's on-demand refresh rather than sleeping for the poll
  interval wherever determinism needs it, but keep at least one path that exercises the
  interval-driven route.
- **Relay-mediated variant**: if the blind-relay fixture makes it cheap, a removed party
  reached via `/p2p-circuit` is the strongest form of scenario 1; if it is not cheap,
  note the gap in the review handoff rather than forcing it here.
