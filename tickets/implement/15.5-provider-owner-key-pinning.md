# Provider containers reject every seed they are given

## What is wrong

Found while fixing `provider-container-durable-identity`, which asked whether
`OrchestratorCreateRequest.pinnedOwnerKeys` being dropped by `DockerOrchestrator` is a real
gap. It is: it makes the provider's whole seed-delivery feature dead on arrival.

A "seed" is the small signed bundle that tells a fresh node which peers form a cadre and how
to dial them. Delivering one is how a tenant's node joins the tenant's cadre.
`ContainerService.applySeed` posts it to the container's `POST /seed` route with the
per-container bearer token — that half works. What fails is *trust*.

The bearer token gates **delivery**; whether the seed's contents are honoured is decided
separately, by the node's `SeedTrustPolicy`
(`packages/cadre-core/src/seed-trust-policy.ts`). The chain in a provider container:

- `cadre-cli start` builds a `pinnedKeyTrustPolicy` only when `--pin-owner-key` or
  `CADRE_OWNER_KEYS` supplies at least one key. cadre-provider passes neither, so
  `CadreNodeConfig.seedTrustPolicy` is `undefined`.
- `SeedBootstrapService` then falls back to `anchoredTrustPolicy()`, which trusts a signer
  only if that key is already in the node's node-local `TrustedOwnerStore`.
- That store is empty on a fresh container and nothing fills it: it is deliberately *not*
  seeded from the replicated `CadreControl.OwnerKey` table (any peer can genesis-insert its
  own key there), and the node is not started with `--owner`.

So `applySeed` fails for every provider-hosted container with
`Signer key is not an anchored owner (anchored trust policy)`. The comment on
`pinnedOwnerKeys` in `packages/cadre-provider/src/service/orchestrator.ts` says the Docker
orchestrator ignores it because "its tenants pin owner trust through their own path" — that
path does not exist. The comment is wrong and should go with the fix.

This is not caught today because `__tests__/container-seed-endpoint.test.ts` stubs `fetch`,
so it exercises the provider's delivery side and never a real node's trust decision.

## Expected behaviour

The caller creating a container can say which owner key(s) that node should trust as
seed-signers — the tenant's own cadre owner key, known to the caller before the container
exists. The node is started with those keys pinned, so the first seed the provider delivers
is accepted, and the key is anchored into the node's own trusted-owner store so later seeds
from the same owner are accepted without re-supplying the pin.

A container created without owner keys keeps today's behaviour — it refuses seeds — but the
refusal should be predictable rather than a surprise at delivery time: the create request is
the point where the caller can still fix it.

## Notes for the implementer

- `CADRE_OWNER_KEYS` is comma-separated and is unioned with repeated `--pin-owner-key` flags
  by `collectPinnedOwnerKeys` in `packages/cadre-cli/src/commands/start.ts`. The env var is
  the container-friendly half; no new plumbing is needed on the cadre-cli side.
- Keys are base64url ed25519 public keys and are deliberately **not** validated at pin time
  — a malformed pin simply never matches a real `signerKey` and the seed is refused with the
  policy's reason. Keep that property; do not add a validator that turns a bad pin into a
  container that fails to start.
- Pinning is per-tenant data on a shared host. It flows only from that tenant's own create
  request into that tenant's own container — the same one-tenant-in, one-tenant-out
  discipline `resolveTenantPush` documents. Do not add a provider-level default owner key:
  a provider-wide pin would let one tenant's owner seed another tenant's node.
- Anchoring happens on first accepted seed (`anchorAs`), and the trusted-owner store lives in
  the node's state directory — which lands on the durable volume from the prereq ticket. So
  once that ticket lands, a restarted container keeps its anchored trust as well as its
  identity; the pin then only matters for the cold first seed.
- `pinnedOwnerKeys` is already on `OrchestratorCreateRequest` and already threaded by
  cadre-host's `HostProcessOrchestrator` — mirror that naming rather than inventing a second
  field, and pass it through `ContainerService.provisionContainer`, which currently drops
  everything it is not explicitly told to forward.

## TODO

- Add owner keys to the public create-container request (`CreateContainerRequest` in
  `packages/cadre-provider/src/types.ts`) and accept them in
  `POST /containers` (`server/routes.ts`), alongside the existing `bootstrapNodes`
  validation. Reject a non-array / non-string-element value with `INVALID_REQUEST`.
- Persist them on the `Container` record so a re-provision (and an operator debugging a
  refused seed) can see what the node was told to trust.
- Thread them through `ContainerService.provisionContainer` into
  `OrchestratorCreateRequest.pinnedOwnerKeys`.
- In `DockerOrchestrator.createContainer`, inject `CADRE_OWNER_KEYS=<comma-joined>` when the
  list is non-empty, and omit the var entirely when it is empty (the CLI's env override
  layer skips empty values, but omitting is clearer than relying on that).
- Replace the "the Docker orchestrator ignores this for now" paragraph on
  `OrchestratorCreateRequest.pinnedOwnerKeys` with what actually happens.
- Log (do not fail) at create time when a container is provisioned with no owner keys, so
  the eventual seed refusal is traceable to the create call that caused it.
- Tests: orchestrator injects the joined var and omits it when empty; the create route
  accepts and validates the field; `ContainerService` forwards exactly the keys it was given
  and never a default. Extend the fake-dockerode env assertions in
  `__tests__/docker-orchestrator-push.test.ts` rather than building a second harness.
- Docs: `docs/architecture.md` seed-trust section should state that a container-hosted node
  needs its tenant's owner key pinned at create time; `docs/STATUS.md` should record the
  provider seed path as working end-to-end once this lands.
