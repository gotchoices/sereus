# Replace the hardcoded `clusterSize: 3` with one party-wide value that defaults to 2

## Background

`clusterSize` is the number of nodes we tell Optimystic a replication group ("cluster")
should have for any given block. Five call sites hardcode `3`:

| File | Line | Which network |
| --- | --- | --- |
| `packages/cadre-core/src/cadre-node.ts` | 739 | control network |
| `packages/cadre-core/src/strand-instance-manager.ts` | 260 | per-strand networks |
| `packages/integration-tests/src/harness/test-party.ts` | 48 | test harness |
| `packages/quereus-plugin-sereus/test/e2e/networked.e2e.spec.ts` | 89 | plugin e2e |

Since Optimystic 0.16.x (the `cluster-membership-admission-gate` work) the value is also
handed to the *member* side of a write and used as an admission gate. A member refuses to
vote on a write when the coordinator's declared peer set is smaller than the member's own
configured `clusterSize` and its network-size estimate is not confident. Because a commit
needs a super-majority (`ceil(2 × 0.75) = 2` at two nodes — i.e. unanimity), one refusal
kills the write.

## Reproduced

Ran `control-write-while-alone-convergence.integration.ts` with
`DEBUG='optimystic:db-p2p:cluster*'`. All six cluster transactions in the run were
rejected, every one for the same reason:

```
optimystic:db-p2p:cluster-member cluster-member:admission-reject {
  reason: 'low-confidence-downsize',
  declaredSize: 2,
  configuredClusterSize: 3,
  confidence: 0
}
... cluster-tx:rejected-by-validators { peerCount: 2, rejections: 2, maxAllowed: 0 }
```

`confidence: 0` is the normal state for these small in-process test networks — FRET never
gets a confident network-size estimate, so the gate always takes the fail-closed branch
where the *only* thing that matters is `declaredSize >= configuredClusterSize`.

## Facts established during investigation

Read against `../optimystic` at `ed95d77` (v0.16.3, linked into this repo via the root
`resolutions`).

**1. `clusterSize` is consumed once, at node construction — never re-read.**
`createLibp2pNode` builds a single `consensusConfig` object
(`packages/db-p2p/src/libp2p-node-base.ts:639-650`) and hands it to the cluster member,
which copies it into a `readonly` field (`cluster/cluster-repo.ts:259`). The same number is
also frozen into `Libp2pKeyPeerNetwork` (line 620), the network-manager service (line 552),
and the churn-spread monitor (line 900). There is no setter. **A membership change cannot
update it without re-creating the libp2p node.**

**2. A solo node never reaches the gate.** `CoordinatorRepo.pend`/`commit` short-circuit to
local storage when the block's cluster has `peerCount <= 1`
(`packages/db-p2p/src/repo/coordinator-repo.ts:413` and `:487`). Confirmed empirically —
the write-while-alone scenario's solo writes succeeded and produced no cluster transaction
at all. **So the one-node case is unaffected by whatever we choose here.** (Its writes do
fail if they ever *do* enter the cluster path: Optimystic hardcodes
`minAbsoluteClusterSize: 2` at `libp2p-node-base.ts:642`, and the escape hatch for that,
`allowUnvalidatedSmallCluster`, is not exposed through `createLibp2pNode`.)

**3. The declared set is itself bounded by the coordinator's own `clusterSize`.**
`findCluster` takes the nearest `clusterSize - 1` serving peers plus self
(`packages/db-p2p/src/libp2p-key-network.ts:604-618`). So a coordinator can never declare
more peers than its configured size, and declares fewer when the network is smaller.

**4. Under-declaring is safe; over-declaring is fatal.** The low-confidence branch rejects
only when `declared < configured`. A node configured *low* admits everything at or above
its number. A node configured *high* rejects any smaller cohort. **Therefore all nodes on
one network should carry the same value, and when in doubt the value should be too small
rather than too big.**

**5. The cost of a smaller number is replication breadth, not correctness.** `clusterSize`
also bounds the write cohort (fact 3) and the churn-spread expansion cohort
(`libp2p-node-base.ts:900`), so `2` means blocks land on two nodes rather than three.

## Why not derive it from actual membership

The original ticket proposed deriving the number from the party's `CadrePeer` rows (control
network) and the strand's participants (strand networks). Investigation says don't:

- **Chicken-and-egg on the control network.** `CadreNode.start()` creates the control
  libp2p node (`cadre-node.ts:438`) *before* opening the `ControlDatabase` on top of it
  (`:450`) — the membership rows live in the very database whose transport we are
  configuring. There is no count to read at construction time.
- **The value is frozen anyway (fact 1).** A number derived at start-up goes stale the
  moment the cadre grows, and refreshing it means tearing down and re-creating the control
  node — dropping every connection and every strand riding on it.
- **Divergence is the failure mode we are fixing (fact 4).** Membership is replicated and
  eventually consistent, so two nodes routinely hold different counts. Deriving
  per-node re-creates the exact "one member's number is bigger than the cohort it is shown"
  situation, just with different arithmetic. The same applies to strand participants, which
  are known only as local cohort knowledge at `launchStrand` time
  (`cadre-node.ts:2427 resolveCohortSeed`).

**Decision: one party-wide constant, defaulting to 2, overridable in config.** Two is
Optimystic's own `minAbsoluteClusterSize`, it is the smallest value that reaches the cluster
path at all, and it is the permissive direction of the gate. An operator running a
consistently larger cadre can raise it — but **must set the same value on every node of the
party**, which the config doc comment has to say plainly. The control network and strand
networks take the same value: nothing established here justifies two numbers, and a second
knob is a second chance for the two sides to disagree.

## Shape

```ts
// packages/cadre-core/src/types.ts

/**
 * Number of nodes Optimystic is told a replication cluster should have. Every
 * node in the same party MUST use the same value — a node configured higher than
 * the cohort it is shown refuses to vote on writes, which fails the commit.
 * Frozen when the libp2p node is created; a change takes effect on restart.
 * Default 2 (Optimystic's own minimum). Raise only for a cadre that reliably
 * runs that many nodes.
 */
clusterSize?: number;
```

`StartStrandConfig` gains the same optional field; `CadreNode.launchStrand` forwards
`this.config.clusterSize`. Both call sites resolve through one exported constant so there is
a single place to read the rule:

```ts
export const DEFAULT_CLUSTER_SIZE = 2;
```
