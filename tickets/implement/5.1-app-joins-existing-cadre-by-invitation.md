# A phone app joins an existing cadre by invitation

## Product decisions (settled with the project owner)

- Owner authority stays on user devices; cadre-host nodes are not owners.
- An invitation is the owner's signature; nothing is signed again at redemption. It may name a peer id or leave it to whoever redeems it.
- An app that joins usually becomes an owner too (default yes: any Sereus app on the phone should be able to do admin work).
- Two flows (targeted request/response, and open one-paste) — encodings, `reach`, `waitForMember` and `wireOwnKeyIfOwner` come from `cadre-invitation-requests-and-waiting-redemption`.

## Decision: one node per app; joining switches its party

B (the joining app) already runs a one-node cadre of its own. Options were (a) one node serving two parties, (b) a second node for party A beside B's own, (c) one node at a time, switched from party B to party A. **Chosen: (c), keeping the same identity key.** Reasons, from the code:

- A `CadreNode` serves one party by construction: every node-local store is party-scoped and refuses another party's (`trustedOwners`, `bootstrapPeers`, `enrolledMachines`, `joinedStrands`, `strandNetworkState` checks in `cadre-node.ts`), and `redeemCadreInvitation` refuses an invitation for another party. (a) would be a rewrite of the node.
- (b) means two libp2p hosts in one process. With the same identity they share one peer id (competing relay reservations on the same relay, and `createPhoneNode` refuses a second node over the same storage prefix because the two would "share databases and an identity"); strand storage scopes are the strand id, not party-scoped, so both nodes would open the same strand databases. With a second identity, B's owner key in A would differ from the key that founded B's strands, and `move-strand-between-cadres` needs the same key (`Strand.AuthorizedInsert` requires `FounderOwnerKey = context.OwnerKey`).
- (c) keeps the identity: the phone kit's identity is per app, not per party (`SecureStoreKeyStore`, `DEFAULT_IDENTITY_KEY_ID`), so the peer id in B's join request is the peer id that redeems, and B's owner key in A equals its owner key in B. B's own party's data stays on disk under its own names (`controlStorageScope(B)`, the `<record>.<partyB>` node-local keys, the `anchor` slot for B) for the move and dissolve tickets.

Cost: while B runs as a member of A, its own cadre's strands are not open on this phone until `move-strand-between-cadres` moves them. The reference screens show the join → move → remove-old-cadre progress (`reference-apps-join-existing-cadre`).

## Decision: a joined party never runs owner genesis

`PhoneNode.start` runs `runOwnerGenesis` on every start: `ensureOwnerKey(identity)` (inserts a founding `OwnerKey` row if the local table is empty) then `initializeSeedBootstrap(identity)` (anchors the key as `genesis`). Started under someone else's party id before its control store has arrived, that inserts B's key as a second founder of A — the "stranger's genesis-inserted key" the trusted-owner anchor exists to contain (`docs/architecture.md`, node-local trusted-owner anchor). The reference app does this today: its Join section redeems on a node the user started by typing A's party id, after genesis ran, and the Maestro setup relies on it (the drone fixture mints `grantsOwner: false`, yet the phone then creates a strand as an owner — only possible through its self-inserted founding row).

So the saved start record learns how this app came to the party:

```typescript
interface PhoneNodeOptions {
  // … existing fields
  /** How this app came to `partyId`. Absent means 'founded' (every record written before this field). */
  origin?: 'founded' | 'joined';
  /** The party this app founded and left by joining another; kept until the old cadre is dissolved (`dissolve-empty-cadre`). */
  formerPartyId?: string;
}
```

- `origin: 'founded'` → `runOwnerGenesis` as today.
- `origin: 'joined'` → never `ensureOwnerKey`; call `CadreNode.wireOwnKeyIfOwner()` instead. `OwnerGenesisResult` gains `'member'` (joined, not an owner). The bound (`ownerGenesisTimeoutMs`) applies to it too.
- Serialize both fields in `serializeSavedStart` / `parseSavedStart` (malformed → default, as for the other optional fields).

## What to build: `PhoneNode.joinCadre`

```typescript
interface JoinCadreOptions {
  /** Relays for the joined start; default: the running (or saved) start's. */
  relayAddrs?: string[];
  noiseCryptoMode?: NoiseCryptoMode;
  signal?: AbortSignal;
  onProgress?: (progress: CadreJoinProgress) => void;
}
interface JoinCadreResult extends RedeemCadreInvitationResult {
  /** The party this app left, when it had one; also saved as `formerPartyId`. */
  formerPartyId?: string;
}
joinCadre(invitation: CadreInvitation, options?: JoinCadreOptions): Promise<JoinCadreResult>;
```

Steps, run as one transition in the existing `inTurn` queue so no start, stop or restart interleaves:
1. **Already in that party** (the running node's party is `invitation.partyId`): redeem on the running node with `waitForMember: true` (idempotent for a device already admitted), then `wireOwnKeyIfOwner`; no restart.
2. **Otherwise**: remember the running options (or the saved start when stopped; none on a first launch that never founded). Shut the node down and build one for `{ partyId: invitation.partyId, bootstrapAddrs: [], relayAddrs, noiseCryptoMode, origin: 'joined' }`. Do **not** save the start record yet (a kill while waiting must relaunch into B, not into a party B was never admitted to). `bootstrapAddrs` stay empty: the redemption retains the answering member as a cold-start dial target in the party's bootstrap-peer store.
3. `redeemCadreInvitation(invitation, { waitForMember: true, signal, onProgress })`.
4. **Accepted**: `wireOwnKeyIfOwner()`; save the start record (`origin: 'joined'`, `formerPartyId` = the left party when it was founded here, else carried over from the left record; `autoStart: true`); status `running` with `owner` `'enrolled'` or `'member'`.
5. **Refused, expired, aborted, or the start failed**: shut down the party-A node and restart the remembered options (or stay stopped when there were none), then rethrow the original error. A failure restoring is logged and leaves status `failed`; the original error is still the one thrown.

Status while waiting: `running` with `owner: 'member'` would claim admission it does not have. Add a `{ state: 'joining'; node: CadreNode }` variant to `PhoneNodeStatus` for steps 2–3; `node` getter returns null while joining (nothing should use an unadmitted node), and `start` called during a join runs after it, as during a restart.

The kit's `ownerPublicKey()` and the app's "owner" display must not report an owner for `'member'`.

## Edge cases & interactions

- **Kill while waiting** (iOS backgrounds and kills B): the saved record still names B, so the next launch starts B; party A's partial local storage is left and reused by the next attempt. If the member had admitted B before the kill, re-pasting the same invitation is answered "already a member". By inspection of the save ordering (step 2).
- **Cancel** (abort signal): B is back in its own cadre, unchanged. Test (below).
- **Join from a first launch with no cadre** (the screens ticket's "Do you already use Sereus apps?" → yes): no remembered options; on failure the kit stays stopped. By inspection.
- **Joined app restarts later**: `origin: 'joined'` → no genesis; `wireOwnKeyIfOwner` re-wires an owner. Test (below).
- **Joined as a plain member, later made an owner by another owner** (`addOwner`): the next start's `wireOwnKeyIfOwner` picks it up. By inspection.
- **Joined owner mints an invitation** (app #2 inviting app #3): its anchor holds the founder's pinned keys, keys derived along owner chains, and its own (wired by `wireOwnKeyIfOwner`, a live owner) — all genuine owners. By inspection.
- **Push wake into a killed process** reads the saved start: after a join it starts A with `origin: 'joined'`; during a join it starts B. By inspection.
- **A second join while joined** (B, now in A, gets an invitation to party C): allowed; `formerPartyId` keeps the party this app founded, not A. Document; no test.
- **Strands B joined from other parties** (`JoinedStrandStore`, keyed per party) are B's party's; they come back only through the move ticket. Nothing here.

## Tests (the ones that pay)

In `packages/cadre-rn/test/phone-node/node.spec.ts` (real `CadreNode` over the existing fakes, no network):
- A start with `origin: 'joined'` on an empty party inserts no `OwnerKey` row and reports `owner: 'member'` — the reproduction of the founding-row defect.
- `joinCadre` with an invitation that has already expired restarts the original party with its options and saved record unchanged, and throws `invite-spent` — the rollback contract. (An expired invitation fails before any dial, so no member is needed.)
- `options.spec.ts`: extend the round-trip case with `origin` and `formerPartyId`, and the absent-field default.

The admitted path is covered by the prereq's integration scenario at the cadre-core layer, and by the device run.
