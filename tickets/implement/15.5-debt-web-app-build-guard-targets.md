# Complete `reference-app-web`'s stale-build target list, and pin it

## Background

`packages/reference-app-web/test/global-setup.ts` currently guards exactly one
package, `@serfab/cadre-core`, with a comment explaining why: the sibling
`@optimystic/*` / `@quereus/*` packages live in this app's own
`node_modules` (`installConfig.hoistingLimits: "workspaces"`), and the guard
looked them up only in the repo root's. The prereq ticket
`debt-build-guard-node-modules-chain` removes that limitation — `linked` targets
now resolve through the consuming package's own `node_modules` chain — so the
list can be completed.

It is also the only guarded suite with no `build-targets.spec.ts`. That spec is
what stops a hand-written target list rotting: it holds the list against the
package's own `dependencies` (see `test-harness/build-targets-spec.ts`, and the
four existing copies in `cadre-core`, `cadre-cli`, `quereus-plugin-sereus`,
`integration-tests`). It was absent for the same reason — it would have demanded
exactly the entries the guard could not resolve.

## The dependency range

`packages/reference-app-web/package.json` declares `"@serfab/cadre-core": "*"`
where every other package in the repo uses `workspace:^` (or `workspace:*` in
`integration-tests`). `yarn.lock` records it as `"@serfab/cadre-core": "npm:*"`
— an npm range that yarn happens to satisfy from the local workspace, rather
than a declaration that the workspace is what is wanted.

Two consequences:

- `test-harness/build-targets.ts`'s `distBackedDependencies` classifies a
  workspace dependency by its `workspace:` prefix, so this one is invisible to
  the drift spec — which is the whole point of adding that spec here.
- The declared intent is "any published version of `@serfab/cadre-core`", which
  is not what this app means.

**`hoistingLimits` is not the reason for the bare `*`.** `packages/reference-app-ns`
sets the same `hoistingLimits: "workspaces"` and declares `"@serfab/cadre-core":
"workspace:^"`, and installs correctly. `scripts/check-dep-ranges.mjs` only
inspects names that appear in the root manifest's `resolutions` with a `link:`
target, and `@serfab/cadre-core` is not one, so the range change is invisible to
that gate either way. Change it to `workspace:^`.

## Target list

`targetListProblems` checks *coverage* of the package's own `dependencies`, so
all five dist-backed dependencies must be listed:

```ts
export const TARGETS: BuildTarget[] = [
	{ packageName: '@serfab/cadre-core', distEntry: 'dist/index.js', location: 'workspace' },
	{ packageName: '@optimystic/db-core', distEntry: 'dist/src/index.js', location: 'linked' },
	{ packageName: '@optimystic/db-p2p', distEntry: 'dist/src/index.js', location: 'linked' },
	{ packageName: '@optimystic/db-p2p-storage-web', distEntry: 'dist/src/index.js', location: 'linked' },
	{ packageName: '@quereus/quereus', distEntry: 'dist/src/index.js', location: 'linked' },
];
```

The four `distEntry` values are each package's declared `main`, confirmed against
the sibling checkouts (`@optimystic/db-p2p-storage-web@0.17.0` →
`dist/src/index.js`); the first four also match what `cadre-core` and
`integration-tests` already guard.

`@optimystic/db-p2p-storage-web` is worth a word in the file's comment: the
current vitest suite (`node-local-slots.spec.ts`) imports it only as a *type*,
which erases at runtime, so that suite alone never loads its `dist`. It is listed
anyway — it is a declared, link-resolved dependency the app itself runs, and the
drift spec checks the manifest rather than the import graph. The accepted cost is
that a stale `db-p2p-storage-web` build fails this unit suite; that is the same
bias towards a loud, fixable failure the guard is built on.

## The drift spec

`packages/reference-app-web/test/build-targets.spec.ts`, matching the four
existing ones:

```ts
import { describeBuildTargets, packageRootFrom } from '../../../test-harness/build-targets-spec.js';
import { TARGETS } from './global-setup.js';

describeBuildTargets('reference-app-web', {
	packageDir: packageRootFrom(import.meta.url, '..'),
	targets: TARGETS,
	expectFound: {
		'@serfab/cadre-core': 'workspace',
		'@quereus/quereus': 'linked',
	},
});
```

`expectFound` deliberately pins one of each origin, so an empty manifest scan
cannot let the coverage assertion pass having checked nothing. Pinning
`@serfab/cadre-core` as `workspace` is also what makes the range change
load-bearing: with the bare `*` this assertion fails.

`vitest.config.ts`'s `include` is `test/**/*.spec.ts`, so the new file is picked
up with no config change. Its comment on `globalSetup` names only cadre-core —
widen it.

## Edge cases & interactions

- **The range change moves `yarn.lock`.** Run `yarn install` and commit the
  lockfile with the manifest edit. Confirm afterwards that
  `packages/reference-app-web/node_modules/@serfab/cadre-core` is still a symlink
  to `packages/cadre-core` and that `yarn workspace @serfab/reference-app-web build`
  still succeeds (it runs `tsc --noEmit` twice plus `vite build`).
- **A guard that fires is the point — prove it does.** With the list in place,
  touch a source file in a sibling checkout
  (`../optimystic/packages/db-core/src/index.ts`, mtime only — do not edit
  content) and confirm `yarn workspace @serfab/reference-app-web test` now aborts
  naming that package and `Run in <optimystic checkout>: yarn workspace
  @optimystic/db-core build`. Rebuild the sibling (or restore the mtime)
  afterwards. A list that silently resolves nothing looks identical to a list
  that passes.
- **Siblings may be genuinely stale on this machine.** If the guard fires on a
  first honest run, that is the guard working — build the named sibling, do not
  trim the list.
- **`db-p2p-storage-fs` precedent.** `integration-tests` lists a `linked` target
  whose root `node_modules` entry is a real registry directory; the guard skips
  it. Nothing here should change that behaviour — if any of these four resolve to
  a real directory on some checkout, `not-linked`/skip is the correct outcome,
  not a failure.
- **The e2e (Playwright) harness is separate.** `playwright.config.ts` has its
  own `globalSetup` under `e2e/`; it is out of scope and must not be touched.
- **`reference-app-ns` and `reference-app-rn`** set the same `hoistingLimits` but
  have no vitest suite calling `assertBuildFresh` today. Do not add one here —
  `debt-ns-unit-test-harness` in `backlog/` is where that lands.
