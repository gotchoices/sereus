# Phone kit: the identity's peer id without a node, and the join's later phases

Part of the "join an existing cadre" screens (split from the plan ticket `reference-apps-join-existing-cadre`; the screens are `reference-app-rn-joins-existing-cadre`). Kit changes only; no UI here.

## 1. `PhoneNode.identityPeerId(): Promise<string>`

A join request (`encodeCadreJoinRequest({ v: 1, peerId, appName })`, cadre-core `cadre-join-request.ts`) carries the app's peer id. The kit keeps one identity per app in the secure store (`DEFAULT_IDENTITY_KEY_ID`, see architecture.md → "An app joins an existing cadre": "The identity is per app, not per party"), so the peer id is the same in every party. Today the app can read it only from a running node (`phone.node.peerId`). A new app that answers "yes, I already use Sereus apps" on first launch has no node and must not found a cadre just to learn its id.

Behaviour:

- Status `running` or `joining` (a node exists): return that node's `peerId.toString()` at once, without queueing. A join may wait for minutes, and the screen showing the request must not wait with it.
- Otherwise: run in the kit's transition queue (`inTurn`, the same queue `start` / `stop` / `joinCadre` / `dissolveFormerParty` use), and inside it call cadre-core's exported `loadOrCreateIdentityKey(keyStore, DEFAULT_IDENTITY_KEY_ID)` on the kit's own `SecureStoreKeyStore` (the one `buildConfig` hands the node, with the same `secureStoreOptions`), then `peerIdFromPrivateKey(key).toString()` (`@libp2p/peer-id`).
- Why the queue: on a fresh install the slot is empty, and `CadreNode.start` also calls `loadOrCreateIdentityKey`. Two first-run generations racing would each write a different key; the last write wins and the peer id shown in the request would not be the one that later redeems. Inside the queue, the generation and a start never overlap, and once written the key is only read.
- A secure-store read error propagates (same rule as `loadOrCreateIdentityKey`: never regenerate over an unreadable key).

## 2. Join progress after admission

`JoinCadreOptions.onProgress` today receives cadre-core's `CadreJoinProgress` (`redeeming` / `waiting`) only. After a member admits the app, `startAndRedeem` still wires the owner key (up to `ownerGenesisTimeoutMs`, 60 s, after an owner grant), saves the start and adopts the moved strands (`settleJoinMove`), and the UI has nothing to show for that time.

New exported type in `node.ts`, used by `JoinCadreOptions.onProgress`:

```ts
/** A join's progress: the redemption's passes and pauses, then the steps after a member admitted the app. */
export type PhoneJoinProgress =
	| CadreJoinProgress
	/** A member admitted the app; the kit is wiring its owner key and saving the start. */
	| { state: 'admitted'; grantsOwner: boolean }
	/** The app's key is wired as an owner and the strands this join recorded are being adopted. */
	| { state: 'moving-strands' };
```

- Emit `admitted` right after `redeemCadreInvitation` resolves, in both `startAndRedeem` and `redeemInPlace`.
- Emit `moving-strands` in `startAndRedeem` just before `settleJoinMove`, only when this join recorded a move (`movingFrom !== undefined`, thread it in) and the owner step returned `'enrolled'`. A start-time adoption (`buildAndStart`) emits nothing: it has no join listener.
- A listener that throws is logged and ignored, as cadre-core does for its own progress callback (`console.warn` with the kit's `[cadre-rn/phone-node]` prefix). Wrap the two kit-emitted calls in one small helper; the redemption's own calls are already guarded by cadre-core.
- Export `PhoneJoinProgress` from `phone-node/index.ts`.

## Edge cases & interactions

- `identityPeerId()` during `starting`: queued behind the start, returns the started node's identity (the same key). By inspection.
- `identityPeerId()` while a `stop()` is tearing down: queued behind it, then reads the key from the store. By inspection.
- `identityPeerId()` on a fresh install, then `start()`: the node's peer id equals the returned one. **Test** (below): this is the contract the screens rely on, and the race it guards is invisible in normal use.
- `identityPeerId()` while `joining`: returns the joining node's id without queueing behind the join. By inspection (the `joining` status carries `node`).
- `admitted` then a rollback: cannot happen; nothing after admission rolls back (move-strand review: "an admitted join is never rolled back"). By inspection.
- `moving-strands` when the owner key is not wired (`member` / `timed-out`): not emitted; the result's `strandMove` says `deferred`. By inspection.
- A listener throwing on `admitted` must not fail an admitted join (the app is already in party A). By inspection of the helper.

## Tests

- `node.spec.ts`: "reports the identity's peer id before any start, and the first start uses it": a fresh `device()`, `await phone.identityPeerId()`, then `start(...)`; expect `phone.node.peerId.toString()` to equal the earlier value. Nothing else; the progress events ride the admitted path, which the in-process harness cannot reach (see the move-strand ticket's note), so they are checked by inspection.
