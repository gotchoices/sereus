The push sender (`cadre-push-notifier`) + fan-out (`cadre-push-fanout`) run inside the always-on `CadreNode`, which is a **child process** the host/provider spawns (`HostProcessOrchestrator` → `cadre-cli start -c cadre.json`; cadre-provider → Docker). This ticket is the small, distinct subsystem that gets the FCM/APNs credentials *into that child's `cadre.json`* under the `push` key `cadre-core` now reads (`CadreNodeConfig.push: PushCredentials`). It owns no delivery logic — only secret storage + config plumbing.

The actual creation of a Firebase project / service-account JSON and an Apple APNs auth key (`.p8` + key id + team id + bundle id) is **human/infra work, out-of-agent** — this ticket provisions the *config surface* to hold those secrets and inject them, and documents the provisioning steps; it must not invent or fake credentials.

## cadre-host (single-party, self-hosted)

The host already mints per-child config in `HostProcessOrchestrator.buildAuthorityChildConfig` / `buildChildConfig` and persists host secrets through the secret store (`nat/secrets/index.ts`, keytar with file-store fallback). Add:

- A `push` secret bundle in the host's secret store (FCM `{ projectId, clientEmail, privateKey }`, APNs `{ keyId, teamId, bundleId, privateKey, production }`), set via a new local-UI Settings field / CLI flag (the entry path mirrors how NAT/DDNS secrets are entered; reuse `settings-store.ts` for non-secret bits like `bundleId`/`production`/`cooldownMs`, keep the private keys in the secret store, never in `settings.json`).
- `AuthoritySpawnConfig` (orchestrator `types.ts`) gains an optional resolved-`PushCredentials`; `buildAuthorityChildConfig` (and `buildChildConfig` for managed storage nodes that participate in strands) writes `config.push = { fcm?, apns?, cooldownMs?, debounceMs? }` when present. The always-on **authority/storage** node is the one that participates in strands and should fan out; a transaction-only node need not (document which profiles get the block — storage/authority yes).
- Secret hygiene: the `push` block lands in the child's `cadre.json` on the host filesystem (same trust boundary as the existing control-DB storage in the workdir). Do **not** log private keys; redact in any orchestrator debug line. The startup-token/seed-token redaction precedent applies.

## cadre-provider (multi-tenant)

- Per-tenant credentials: provider config (`config/types.ts` + `validate.ts`) gains an optional per-tenant `push` block (or a provider-level default with per-tenant override). The container orchestrator (`service/orchestrator.ts` / `docker-orchestrator.ts`) injects the resolving tenant's `push` into that tenant's node config/env — **never** another tenant's. This is the multi-tenant scoping the parent ticket flagged: device-token scoping is already per-control-network (each node reads its own party's DB); credential scoping must match — one tenant's FCM/APNs creds must not reach another tenant's node.
- `validate.ts` rejects a partial credential set (e.g. APNs `keyId` without `privateKey`) so a misconfig fails fast at provider start, not at first push.

## Edge cases & interactions

- **No push credentials configured** → no `push` block written → the node constructs no notifier/fan-out and behaves exactly as today. This must be the default; pushes are opt-in per deployment.
- **Partial credentials** (FCM only, or APNs only) → write only the present platform; `createPushNotifier` already tolerates one-sided creds. Validate that a present platform's required fields are all set.
- **Cross-tenant leak (provider)** → assert in a test that tenant A's node config never contains tenant B's credentials; resolve creds strictly from the tenant being launched.
- **Secret at rest** → private keys live in the secret store (keytar/file-store on host; provider's existing secret mechanism), and transiently in the child `cadre.json`/env on the same host trust boundary; never in committed config, never in logs, redacted in debug output.
- **Restart re-spawn** → `ensureAuthorityNode` re-spawns from persisted `AuthoritySpawnConfig`; the resolved `push` creds must be re-resolved from the secret store on each spawn (do not persist raw private keys in `state.json` — persist only a reference/flag and re-read the secret).
- **Bundle id / production toggle mismatch** (APNs sandbox vs prod) → surfaced as plain config; document that a TestFlight/dev build needs `production:false`. Out-of-agent to verify on-device.
