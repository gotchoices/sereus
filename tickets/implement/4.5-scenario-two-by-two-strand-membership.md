# Membership actions driven from a party's non-founding machine

New scenario `strand-membership-second-machine.integration.ts`: a closed strand across
two parties × two machines, with the membership writer calls issued from machine
index 1 — a machine that neither founded the strand nor is its party's owner.

`strand-membership-closed-strand-e2e.integration.ts` already proves every action
across parties at one machine each (its third and fifth tests are joiner-authored),
and its permission semantics are settled in cadre-core unit specs. **The new variable
is the machine, not the action** — so this scenario is one lean lifecycle pass, not a
port of that file's nine tests. Do not duplicate its accept/reject breadth.

## Design (settled during plan)

**Bring-up.** Same skeleton as the sibling core scenario: `bootTopology` 2×2
(`genesis-first`, full mesh), then `joinStrandOn` with `members: [a0, a1, b0, b1]` and a
**closed** strand — `type: 'c'`, a shared `memberPrivateKey` from
`generateStrandMemberKey`, `founder: true` (a0 seats the bootstrap Manager/Member/Header
rows). One narrative `it`, timeout sized per `topology.ts`'s TIME BUDGET (8 libp2p
nodes ≈ 80–120 s bring-up; ~360 s test timeout is reasonable).

**The writer APIs take a database handle** (`issueInvite(db, …)`,
`consumeInvite(db, …)`, `registerMemberPeer(db, …)`, `addManager(db, …)` — see the
closed-strand e2e's imports), so "driven from machine X" means calling them against
X's strand instance database. No new API surface is involved.

**Lifecycle, each step gated visible from a0's database before the next (the GATE
pattern and budgets of the closed-strand e2e):**

1. a0 (founder, holding the founder keypair via `strandMemberKeyPair`) issues an invite;
   party B's member identity is a fresh keypair.
2. **b1 consumes the invite against its OWN database** — `consumeInvite(b1Db, …)`. The
   deferred `ConsumedInvite` checks (`InviteExists`/`ValidUsage`/`NotExpired`) must
   resolve the a0-authored `Strand.Invite` row over the network from a machine that is
   two hops of novelty away from anything tested: wrong party AND wrong machine.
3. **Both of party B's machines register as devices of the one member:**
   `registerMemberPeer(b1Db, { memberKeyPair: bMember, peerId: <b1 strand peer id> })`
   and then, from b0's database, the same member registering b0's strand peer id. A
   party with two `MemberPeer` rows under one member is the data shape this topology
   exists to create and nothing has ever written. Assert both rows enumerate from a0
   via `listMemberPeers`.
4. **Manager rotation driven from the second machine:** a0 promotes party B's member
   (`addManager(a0Db, …)`); then **from b1's database** the new manager issues a further
   invite and admits a third member key (`issueInvite(b1Db, { managerKeyPair: bMember })`,
   `consumeInvite`/`addMemberByManager` per the e2e's fifth-test recipe). Gate the
   resulting rows visible from a0 AND from a1 — a1 is a machine that authored none of
   this and must still converge on all of it.
5. **Negative floor (one case, not a suite):** a fresh unadmitted keypair attempting
   `issueInvite` from b1's database rejects (`rejects.toThrow()` only — the rejection
   floor: no post-state assertions after a rejected write, per the optimystic
   deferred-constraint-rollback gap).

## Edge cases & interactions

- **Rejection floor and lookup shape rules are inherited:** rejected writes assert via
  `rejects.toThrow()` with no following count/enumeration assertions; absence
  assertions scan-and-filter in JavaScript, never a full-PK point lookup
  (`debt-composite-pk-point-lookup-unreliable-untracked`). Copy the closed-strand e2e's
  discipline, and its header's reasoning, where applicable.
- **Visibility, not physical replication:** every gate here is a database-visibility
  claim, deliberately — the physical story for this topology is the sibling core
  scenario's job. State that in the file header so a reviewer doesn't demand raw-store
  gates that would double the runtime.
- **`waitUntil` swallows throwing conditions:** a gate whose read errors every attempt
  reports a plain timeout. The closed-strand e2e's header NOTE applies verbatim; keep
  gates on the shared-budget pattern so a timeout names the claim that failed.
- **Ordering between steps 3's two registrations:** they are writes from different
  machines touching one member's rows — issue them sequentially with the first gated
  visible before the second (synchronous replication; concurrent cross-machine writes
  mutually block).
- **The strand cohort is exactly at breadth (4):** the `joinStrandOn` barrier waits for
  4 on every member; if bring-up flakes here it flakes for the core scenario too — fix
  in the harness, not with a local workaround.

## Out of scope

Sealing, member-peer removal, revocation breadth (all covered founder-side and
joiner-side in the closed-strand e2e); closed-formation-over-the-wire delivery of the
member key (control layer, `strand-formation-e2e` Phase 4); physical replication
(sibling core scenario); relayed reachability and larger networks (same slugs as the
sibling ticket).
