## Context

`ops/docker/turn-credential-issuer/` serves `/ice-servers.json` — the runtime
ICE-server manifest — and, when the operator has TURN enabled, mints a short-lived
coturn credential into it (coturn `use-auth-secret` REST scheme:
`username = "<unixExpiry>:<id>"`, `credential = base64(HMAC_SHA1(secret, username))`).

Today's admission posture is: optional shared bearer token → per-IP fixed-window
rate limit → mint, with coturn's own quotas as the hard backstop. That bounds
abuse but binds a credential to **nobody**: a shared token shipped in a browser
bundle is effectively public, and per-IP limits are coarse (carrier NAT, proxies).
There is no per-node attribution and no way to cut off one misbehaving node.

Sereus nodes already hold a libp2p Ed25519 identity key. This ticket adds a
**peer assertion**: the client signs a short, domain-separated statement with that
key; the issuer verifies it, derives the peer id from the presented public key, and
stamps that peer id into the coturn credential's `<id>` label. Operators get
per-peer allow/deny and per-peer rate limiting; coturn logs attribute relayed bytes
to a peer id that matches the one in relay logs.

This ticket is the **server half only**. The client half (web + React Native
signers, `loadIceConfig` wiring) is `ice-config-peer-assertion-client`, which
consumes the wire format pinned here.

## Wire format (normative — the client ticket mirrors this exactly)

Five request headers on `GET /ice-servers.json`. All values are ASCII and
header-safe by construction, so nothing is base64-wrapped a second time:

| Header | Value |
|---|---|
| `X-Sereus-Peer-Key`   | base64url of the libp2p **protobuf-encoded** Ed25519 public key (48 chars) |
| `X-Sereus-Peer-Aud`   | the audience string the client signed (see below) |
| `X-Sereus-Peer-Ts`    | issued-at, unix **seconds**, decimal digits |
| `X-Sereus-Peer-Nonce` | exactly 32 lowercase hex chars (16 random bytes) |
| `X-Sereus-Peer-Sig`   | base64url Ed25519 signature over the signed message |

The **signed message** is the UTF-8 bytes of exactly five LF-separated lines, no
trailing newline:

```
sereus.turn-issuer.v1
<audience>
<peerId>
<issuedAtUnixSeconds>
<nonce>
```

- Line 1 is the domain tag. Bump `v1` if any line's meaning changes.
- `<audience>` is the manifest URL the client fetched, **query and fragment
  stripped** (e.g. `https://issuer.example/ice-servers.json`). It binds the
  assertion to one issuer so a harvested signature cannot be replayed elsewhere.
- `<peerId>` is the base58btc peer id. The issuer does **not** trust a
  client-supplied peer id — it derives it from `X-Sereus-Peer-Key` and rebuilds
  the message with the derived value, so a mismatch simply fails verification.
- The encoding is injective because no field can contain an LF: peer id is
  base58btc, timestamp is digits, nonce is hex, and the issuer rejects an audience
  containing CR or LF (400) before it is used.

Peer id derivation, verified against the installed libp2p packages:
`publicKey.toString()` on an Ed25519 `PublicKey` already returns the base58btc peer
id string (identity multihash), identical to
`peerIdFromPublicKey(publicKey).toString()`. Use `publicKeyFromProtobuf(bytes)`
from `@libp2p/crypto/keys` and then `.toString()` / `.verify(data, sig)`.

## Why a client timestamp instead of a server-issued nonce

The plan ticket sketched a two-round-trip challenge (issuer mints a nonce, client
signs it). Rejected: a server nonce needs shared state across issuer replicas, adds
a round trip to every node start, and buys nothing here. What it would prevent is
replay of a captured assertion — and a client-chosen nonce plus a bounded
acceptance window gives the same property, as long as the replay cache retains
entries for the **whole** acceptance window (it does; retention is 2× the skew
bound). An attacker positioned to capture an assertion in transit can also capture
the minted credential from the response, which is strictly worse and unaffected by
either design. One round trip, no cross-replica state.

Tradeoff accepted: a device with a badly wrong clock fails verification. The client
ticket handles that by falling back to the unauthenticated path on a 401.

## Configuration

New env knobs (add to `env.example`, `docker-compose.yml` passthrough, README):

| Var | Default | Meaning |
|---|---|---|
| `PEER_AUTH_MODE` | `off` | `off` \| `optional` \| `required` — see admission table |
| `PEER_AUTH_AUDIENCE` | *(empty)* | Exact audience string the issuer requires. Empty disables audience binding (warn at boot). |
| `PEER_AUTH_SKEW_SECONDS` | `60` | Accept `\|now − issuedAt\| ≤ skew`. Clamp `[5, 300]`. |
| `PEER_ALLOW_LIST` | *(empty)* | Comma-separated peer ids. Empty = every verified peer may get TURN. |
| `PEER_DENY_LIST` | *(empty)* | Comma-separated peer ids denied outright. |
| `RATE_LIMIT_PER_PEER_PER_MIN` | `10` | Per-verified-peer fixed-window issuance limit. `0` disables. |
| `REPLAY_CACHE_MAX` | `50000` | Hard cap on live replay-cache entries. |

`CRED_ID` stays as the label for the **unverified** path; a verified request uses
the peer id instead.

Boot-time validation, alongside the existing `logEffectiveConfig` warnings:
reject/warn on an audience containing CR or LF; warn when `PEER_AUTH_MODE` is not
`off` and `PEER_AUTH_AUDIENCE` is empty; warn when `PEER_AUTH_MODE=required` (it
changes who can get TURN); drop blank entries from the allow/deny lists.

## Admission order and outcomes

Gates run in this order. Note the deliberate change from today's comment: the
**per-IP limit now runs before signature verification**, so an unauthenticated
flood cannot burn Ed25519 verification CPU. The shared bearer token stays first
because it is a constant-time compare.

1. Shared bearer token (when `ISSUER_AUTH_TOKEN` set) — miss → `401 unauthorized`.
2. Per-IP rate limit — over → `429 rate_limited` + `Retry-After: 60`.
3. If `PEER_AUTH_MODE=off`: ignore the peer headers entirely; manifest carries
   `peerAuth: "off"`. Done — existing behaviour.
4. Peer headers **all absent** → unverified. In `optional` **and** `required` this
   yields `200` with a **STUN-only** manifest and `peerAuth: "none"`; in
   `optional` the existing token/rate-limited TURN path still applies (see table).
5. Peer headers **partially present, malformed, or over the length caps** →
   `400 invalid_peer_assertion`. A half-configured client must be loud, not
   silently downgraded.
6. Verify: key decodes as a protobuf public key, type is `Ed25519`, timestamp
   within skew, `(peerId, nonce)` not already in the replay cache, audience matches
   when configured, signature verifies. Any failure → `401 invalid_peer_assertion`.
7. Deny list hit → `403 peer_denied`, **before** the per-peer bucket is touched.
8. Allow list non-empty and peer absent from it → `200` STUN-only,
   `peerAuth: "verified"`, no TURN entry. (Verified but not vetted is not an
   error — this is what `turnPolicy: gated` has always meant.)
9. Per-peer rate limit — over → `429 rate_limited` + `Retry-After: 60`.
10. Mint with `<id>` = peer id. Manifest carries `peerAuth: "verified"` and
    `peerId`.

The existing TURN gating matrix (`shouldEmitTurn`) still wins over all of this: if
TURN is disabled, the secret or URLs are empty, or `TURN_POLICY=off`, the manifest
is STUN-only no matter how good the assertion was.

| `PEER_AUTH_MODE` | no assertion | valid assertion | invalid assertion |
|---|---|---|---|
| `off` | today's behaviour | headers ignored | headers ignored |
| `optional` | today's behaviour (token + IP limit) | peer-labelled TURN | 400/401 |
| `required` | 200 STUN-only | peer-labelled TURN | 400/401 |

`required` deliberately serves a STUN-only `200` rather than `401` to an
assertion-less client: `loadIceConfig` turns a non-OK response into `[]`, which
would strip STUN too and leave the node worse off than it needs to be.

## Edge cases & interactions

- **Async handler.** `PublicKey.verify` may return a promise, so
  `handleIceServers`/`handleRequest` become async. The `createServer` callback's
  current `try/catch` only catches synchronous throws — an async rejection would
  escape as an unhandled rejection. Attach a `.catch` that logs and sends
  `500 internal_error` when headers are not yet sent.
- **Replay cache growth.** Key `${peerId}|${nonce}` → expiry ms. Evict on the
  existing `RATE_LIMIT_WINDOW_MS` timer alongside the rate-limit buckets. At
  `REPLAY_CACHE_MAX` entries, reject further verifications with `503` and a warn
  log — never silently accept an unrecorded nonce, which would disable replay
  protection exactly when under attack.
- **Multi-replica.** The replay cache and both rate limiters are per-process, so
  two replicas each admit a replay once. Bounded by the per-peer limit and coturn's
  quotas; document it in the README next to the existing per-process rate-limit
  caveat rather than reaching for shared state.
- **Clock.** Verification uses the issuer clock, coturn checks expiry against its
  own; both already require NTP. A skewed *client* is rejected — the client ticket
  degrades to the unauthenticated path on 401.
- **Header caps before use.** Key ≤ 128 chars, audience ≤ 512, timestamp ≤ 12,
  nonce exactly 32, signature ≤ 128. Enforce before decoding or logging so one
  request cannot turn into a megabyte log line (same reasoning as
  `describeRejected` in `packages/cadre-core/src/ed25519-key.ts`).
- **Nonce shape.** Reject anything that is not exactly 32 lowercase hex chars, so
  `${peerId}|${nonce}` cache keys stay unambiguous.
- **Never echo secrets.** Error bodies stay generic codes; the assertion's public
  fields may be logged, the token and `TURN_SECRET` never.
- **CORS.** Add the five headers to `Access-Control-Allow-Headers`; the browser
  preflight must still answer `204`. `/healthz` stays unauthenticated and
  unmetered.
- **Query-string token.** `?token=` still works; do not add a query fallback for
  assertion fields — signatures in URLs land in proxy access logs.
- **Coturn `<id>` semantics.** Per-peer usernames change what appears in coturn
  logs. Do not claim a quota change in the docs: in `use-auth-secret` mode the
  username already varies per mint (the expiry ticks), so `user-quota` semantics
  are unchanged by this ticket. `total-quota` / `max-bps` remain the hard backstop.
- **`TURN_POLICY=gated` wording.** `ops/docs/ice-servers.md` describes `gated` as
  "issued to all callers the issuer admits (rate-limited / token)". With this
  ticket, `gated` + `PEER_AUTH_MODE=required` + a non-empty `PEER_ALLOW_LIST` is
  the real "vetted clients" configuration. Update that wording and the forward
  pointer that lists `turn-issuer-peer-bound-auth` as backlog.
- **`ops/` is outside the yarn workspaces** (`packages/*` only), so root `yarn
  lint` / `yarn typecheck` do not cover this code. The issuer's own `tsc` build is
  the type gate; run it. Do not widen the lint config here — that is the separate
  plan ticket `debt-tooling-scripts-unlinted-and-unchecked`.
