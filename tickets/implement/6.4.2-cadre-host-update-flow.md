## Scope

Adds the "is there a new version?" check that runs on every `cadre-host start`, the signed-update apply flow that the local UI can trigger, and rollback on apply failure. **Notify-by-default; auto-apply is opt-in.**

This ticket only covers the **npm-installed** update path. The standalone single-executable update path (download a replacement binary, side-by-side swap, restart with new binary) lives with the standalone-binary backlog ticket; both paths share the manifest format and signature verification primitives this ticket lands.

## Design decisions (pinned from plan)

- **Manifest URL:** `CADRE_HOST_UPDATE_MANIFEST_URL` env var, default `https://releases.serfab.io/cadre-host/latest.json`. The endpoint owner ships the manifest separately; cadre-host treats absence (`ENOTFOUND`, `404`, `5xx`, connect timeout) as "no update available" — never blocks startup.
- **Check cadence:** once at every `start` (i.e. every service start, including boot) plus an in-process daily timer while running. 5 s connect timeout, 10 s read timeout; failures are logged at debug only (not warn — most users will see this fail behind firewalls).
- **Signature:** Ed25519. The release public key is embedded in `src/update/release-key.ts` as a hardcoded base64 string. Mismatched signature → refuse to apply, surface error.
- **Update record:** persisted to `<dataDir>/update-state.json`. Local UI reads this to render the banner.
- **Apply default:** notify. Auto-apply is an opt-in setting in `host.config.json` (`updates.autoApply: boolean`, default false) — settable from the local-UI Settings page.
- **Rollback:** for npm installs, rollback = reinstall the previous version via `npm install -g @serfab/cadre-host@<prev>`. Apply records the previous version before invoking npm; on apply-failure, run the rollback command and surface the original error.

### Manifest schema (`latest.json`)

```jsonc
{
  "v": 1,
  "version": "0.7.0",
  "publishedAt": "2026-05-15T18:00:00Z",
  "channels": {
    "npm": { "package": "@serfab/cadre-host", "tag": "latest" }
  },
  "releaseNotesUrl": "https://github.com/gotchoices/sereus/releases/tag/cadre-host-v0.7.0",
  "minPreviousVersion": "0.6.0"     // refuse to update from older than this
}
```

Signed envelope:

```jsonc
{
  "manifest": { ... },                 // the object above, embedded as a sub-object
  "sig": "ed25519:base64(...)"         // signature over JSON.stringify(manifest), canonical key order
}
```

(Canonical serialization: sort object keys recursively, no whitespace. Implementation note: a tiny canonical-JSON function in `manifest.ts` — don't pull in `json-canonicalize` for one place.)

### `UpdateService` surface

```ts
export interface UpdateState {
  /** Last successful manifest fetch. */
  lastChecked?: string;
  /** Latest available version per the manifest (only set if > current). */
  available?: {
    version: string;
    publishedAt: string;
    releaseNotesUrl?: string;
  };
  /** Records the version before an apply, so a rollback can target it. */
  applyInProgress?: {
    fromVersion: string;
    toVersion: string;
    startedAt: string;
  };
  /** Most recent apply error, surfaced by UI. Cleared on next success. */
  lastError?: { code: string; message: string; at: string };
}

export interface UpdateServiceOptions {
  dataDir: string;
  currentVersion: string;          // from package.json
  manifestUrl?: string;            // defaults from env / built-in
  fetcher?: typeof fetch;          // for tests
  npmExecutor?: (args: string[]) => Promise<{ exitCode: number; stdout: string; stderr: string }>;
  autoApply?: boolean;             // from host.config.json
}

export class UpdateService {
  constructor(opts: UpdateServiceOptions);
  /** Background check. Never throws — logs failures and updates state silently. */
  check(): Promise<void>;
  /** Reads the persisted state for UI consumption. */
  getState(): Promise<UpdateState>;
  /** Triggers an apply. Throws on hard failures (e.g. signature mismatch). */
  apply(): Promise<UpdateApplyResult>;
  /** Stops the in-process daily-check timer. */
  stop(): void;
}
```

### Apply flow

1. Re-fetch the manifest and re-verify signature (don't trust the cached `UpdateState.available`).
2. Reject if `manifest.version <= currentVersion` (no-op).
3. Reject if `currentVersion < manifest.minPreviousVersion` (the user needs to step through an intermediate release).
4. Write `applyInProgress = { fromVersion: current, toVersion: manifest.version, startedAt }` to the store.
5. Invoke `npm install -g @serfab/cadre-host@<manifest.version>` (5-minute timeout).
6. On npm success: clear `applyInProgress`, set `lastError = undefined`, log success. Trigger a service-host restart via:
   - systemd: `systemctl --user restart cadre-host`
   - launchd: `launchctl kickstart -k gui/<uid>/com.serfab.cadre-host`
   - NSSM: `nssm restart CadreHost`
   (Reuse the `ServiceHost.restart()` method added in `6.4.1`.)
7. On npm failure: read `applyInProgress.fromVersion`, run `npm install -g @serfab/cadre-host@<from>`, set `lastError = { code: 'apply_failed', message: <npm stderr tail>, at: now }`, clear `applyInProgress`. Surface error to caller. Service-host does **not** restart on rollback (the still-running binary is fine).

### `cadre-host start` integration

`start` constructs an `UpdateService` instance from `host.config.json` + current `package.json` version + the data dir. It calls `check()` after the management-API listener is up (don't block port binding on the network round-trip), and arms a 24 h interval timer. The service is exposed via a getter on the orchestrator-context for the local-UI ticket to surface.

### Management API hooks (consumed by local UI in `6.5`)

This ticket adds the routes; the UI ticket consumes them.

- `GET /update` → returns `UpdateState` JSON.
- `POST /update/apply` → triggers `UpdateService.apply()`; returns `202 Accepted` with the new state; later GETs reflect the in-progress / failed / success result.
- `GET /update/settings` / `PUT /update/settings` — `{ autoApply: boolean }`. PUT writes through to `host.config.json` via a helper.

If `autoApply` is true, the daily-check timer triggers `apply()` itself on detecting a newer version (instead of just writing the available record).

### Tests

- `manifest.test.ts` — given a known keypair, sign a manifest, round-trip through verify; assert that mutated payload, mutated signature, wrong public key, and malformed JSON each fail with distinct error codes.
- `version.test.ts` — `compareVersions('0.6.0', '0.7.0') < 0`; prerelease (`0.7.0-rc1` vs `0.7.0`) handled per semver §11; ill-formed input throws.
- `store.test.ts` — round-trip every field; reject `version` other than the schema version with `'unsupported_state_version'`.
- `apply.test.ts` — mock the npm executor:
  - happy path: install succeeds → state cleared, restart called.
  - npm fails: state records `lastError`, rollback npm call is invoked with the previous version, restart **not** called.
  - rollback also fails: `lastError` records compound failure; an integration test ensures the service does not exit even in this case.
- `update-service.integration.test.ts` — drive `check()` against a fake fetch that returns a signed manifest with version `0.7.0` when current is `0.6.0`; verify state updates and the timer is armed.

### Failure modes & invariants

- Manifest fetch failure (DNS/timeout/non-200): logged at debug, state untouched, no UI noise.
- Signature mismatch: logged at warn, state's `lastError = { code: 'signature_invalid', ... }`, available remains unset. (User sees "update available but unverifiable" warning in the UI banner.)
- Network round-trip never blocks port binding or service startup.
- Apply during another apply: second `apply()` rejects with `'apply_in_progress'`. (UI button is disabled while `applyInProgress` is set in state.)
- Service-host restart failure (e.g. systemctl returns non-zero): surfaced as a warning but the binary swap *did* succeed; user must restart manually. State remains successful.
