# Dial preference without "owner machines"

## Today

Three places pick dial targets by asking whether the key behind a peer id is in the replicated `OwnerKey` table:

- `projectSeedPeers` (`control-database.ts` ~600–618) sets `SeedPeer.isOwner` and `SeedPeer.publicKey` that way; `SeedBootstrapService.applySeed` (`seed-bootstrap.ts` ~1027) dials only `isOwner` peers, and `CadreNode.recordSeedBootstrapPeers` (~4246) retains only those as cold-start dial targets. The invitation reply's `peers` (`CadreInviteRedeemReply`, parsed at `cadre-invite-protocol.ts` ~420) is the same type.
- `selectControlCohortDials` (`control-cohort.ts` ~91–125, called at `cadre-node.ts` ~3875) dials every "backbone" (owner) sibling and caps the rest at `targetDegree`.
- `cadre enroll add` (`enroll-add.ts` ~145) prints the seed's owner addresses and warns when "no owner in it has one".

Each comment there already says the flag is a dial hint, not trust. With owner keys independent of machines (`docs/architecture.md` → Owner Keys), the lookup matches no machine, so seeds would be applied with nothing to dial.

## Design

- **`SeedPeer`**: replace `isOwner` and `publicKey` with `preferred: boolean` — a hint to dial this peer first. `projectSeedPeers(rows, minterPeerId)` marks the machine minting the seed and every always-on machine (`CadrePeer.Profile = 'storage'`) preferred, reading no `OwnerKey` row. The minter is preferred because it is the one machine certain to be reachable by the receiver at that moment (it is delivering the seed, or the invitation reply); always-on machines because they are the ones that stay dialable. A minter with no `CadrePeer` row yet (a solo founder before `registerSelf`) contributes no entry, as today.
- `applySeed` dials `preferred` peers; `recordSeedBootstrapPeers` retains `preferred` peers. Same addresses-per-peer and dial-budget rules (`dialPeerAddrs`).
- **Control cohort backbone**: `selectControlCohortDials(siblings, targetDegree)` treats always-on siblings (`profile === 'storage'`, carried on `CohortPeerRow` from the `CadrePeer` row) as backbone: all dialed, phones and unknown-profile siblings fill up to `targetDegree`. Drop the `getOwnerKeys()` read at the call site and its NOTE. Rename `cappedNonOwner` accordingly.
- **cadre-cli `enroll add`**: print the preferred peers' addresses ("addresses in the seed"), warn when no peer in the seed has one; reword the `start.ts` comment at ~441.
- **Seed signature and trust are unchanged**: `signerKey` is the owner key that signed, judged against the anchor; nothing in a seed claims a machine is an owner. Update the `seed-trust-policy.ts` header comment that mentions "the seed's own `isOwner` peer flags".
- **Audit, then record**: confirm by reading that no membership, admission, wake or strand-addr decision treats a peer as privileged because its identity key is an owner — `isAuthorizedMember` / `listAuthorizedMembers`, the inbound gater and relay-reservation admission, the per-stream protocol guard, `resolvePeerAddrs` / `resolveDeviceToken` trust gates, push-wake. The remaining `ed25519PublicKeyB64FromPeerId` uses are identity bindings (an address record's `PublicKey` is the key behind its peer id; a redeeming device's `peerKey` is its connecting identity; the formation contact check) and stay. Record anything found as an arm of this ticket's review; fix in place if small.

`docs/architecture.md`: the `SeedPeer` interface and the paragraph after `PeerAddressRecord` (the owner node's self-registration "so every seed it mints already carries the owner's own dialable address as an owner peer" → as the minter); `CadreInviteRedeemReply.peers` comment; Seed Delivery Protocol receiver-hardening line "only then dials the seed's owner peers"; "What the replicated table is still for" (it no longer feeds a dial hint); Cohort auto-connect, wherever it names owner backbone siblings; Implementation Status `enroll add` line ("the command warns when no owner in it has one").

## Edge cases & interactions

- A party with no always-on machine (phone-only): a seed's only preferred peer is the minter, which is how today's phone-owner seed behaves. By inspection.
- A seed minted by an always-on machine that holds an owner key (`cadre start --owner`): preferred by both rules; no duplicate entry (one per `CadrePeer` row). By inspection.
- A sibling whose `Profile` is still null (has not self-published): treated as non-backbone, so it is dialed within `targetDegree`; once it publishes, it moves to backbone if always-on. By inspection.
- Seeds minted by a build without this change are not readable by one with it (`isOwner` gone, `preferred` absent → no dial targets). No backwards compatibility is required; the decoder treats a missing `preferred` as false. By inspection.
- `selectControlCohortDials` ordering is deterministic (by peer id) within each class, as today. **Test** — update the existing `control-cohort` spec to the profile classification (one case: two storage siblings both dialed past a `targetDegree` of 1, phones capped).
- `enrollment-e2e.integration.ts` asserts `ownerPeer?.isOwner` and its comment describes the owner flag; change to `preferred` on the minter.
