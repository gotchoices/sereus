# Browser reference app: owner keys, and closing the owner-key work

## The web UI

Mirror the phone app's Owner keys section (`reference-app-rn-owner-keys`, documented in `docs/reference-app-rn.md` → Owner Keys) on the Cadre page (`#/cadre`), using the web lib's flows from `phone-and-web-kits-hold-a-separate-owner-key`:

- List (label, fingerprint from `cadre-format.ts`, "This tab", "Not trusted here").
- Make a backup key: name, passphrase on by default, the export shown once as a QR code (`QrCode.svelte`) and text (`Copyable.svelte`) plus **Download** as a `.txt` file, under the same warning text as the phone.
- Export this tab's key; import by paste (a tab has no scanner), with the same outcomes and refusals.
- Remove with the keep-switches and the `last-owner` refusal.
- `machines.svelte.ts`: add the lost-device line pointing at Owner keys to machine removal. Dropping "Its owner key is removed too.", the keep-switches, the owner facts and the `last-owner` line was done by `machine-removal-leaves-owner-keys` (code and README); the owner-key removal prompt's switches are written fresh, one per dependent row.

Keep the copy identical to the phone's where the platform does not differ, so the two READMEs describe one behaviour.

## Edge cases & interactions

- A tab's owner key lives in its origin's IndexedDB: clearing site data loses it, as it loses the tab's identity today. Say so in the README beside the backup prompt. By inspection.
- Download uses a `Blob` URL revoked after the click; nothing is written to `localStorage`. By inspection.
- The page re-reads after each action and drops a read that finishes after the node was replaced, like the machine list. By inspection.
- Web e2e (Playwright) coverage for the backup path if the existing e2e fixtures make it cheap; otherwise list it as not covered in the handoff.

The owner-key removal plan (`OwnerKeyRemovalPlan`) reports the remover's own rows in two fields: `revouchesOwnRow` (this device's own machine row stood on the key; `removeOwner` re-vouches it unasked, so nothing to ask) and `ownDependency` (this device's own owner key was added by the key being removed; it cannot re-vouch that itself, so the prompt can say another owner may re-add it later). ## From the review of `phone-and-web-kits-hold-a-separate-owner-key`

- `cadre-web.ts` `importOwnerKey` updates the module's owner state when it wires the key, but the store's reactive `state.owner` changes only when `store.svelte.ts` `syncOwner()` runs: call it after an import.
- `wired: false` has two causes, as in `reference-app-rn-owner-keys`: the key is not an owner of this cadre, or the tab already signs with its identity key (a joined party, owner by invitation) and wires the imported key at its next start. Tell them apart with `listOwnerKeys()` before saying the key is not an owner.
