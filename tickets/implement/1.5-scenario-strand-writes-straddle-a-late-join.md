# Writes that straddle a late join must all land

A third test in the file created by `scenario-strand-follows-a-late-joining-cadre-node`, plus the
small refactor of that file's local bring-up needed to slot it in.

## Why this is its own case

The companion ticket covers a quiet handover: the founder writes, *then* the newcomer arrives. Real
use is not quiet — a person keeps writing on their phone while the machine they just added is still
catching up. That window is served by **two different mechanisms with a seam between them**, and
nothing exercises the seam:

- Rows written **before** the newcomer's strand node connects are delivered by the peer-join block
  catch-up (`cadre-core/src/peer-join-backfill.ts`), a whole-store push from the holder.
- Rows written **after** it connects are delivered by ordinary cohort replication, because the
  newcomer's strand node is now in the cohort.

The catch-up enumerates the store once (`listBlockIds()`, `peer-join-backfill.ts:403`) and marks the
peer permanently caught up for that runtime on a clean run (`:308`, `done`), never retrying it while
the connection stays up. So a block committed after its id was passed over during enumeration, but
before the peer was marked done, is never pushed — it must have arrived by replication instead. If
the two mechanisms do not meet cleanly, a row written in that window is silently absent on the new
machine. This test is what would find that.

The original plan ticket framed this as "the newcomer joins before the strand is fully quiet."
That framing has no deterministic staging: a founder writing alone commits local-only and fast, so
there is no reliable way to hold a single write open across an enrollment. Straddling the whole
window with a continuous writer is the same hazard, stated in a way a test can actually produce.

## What the test does

Reuses the party, schema, node construction and event collector from the companion file's Test 1.
The one change to shared code: split that file's local bring-up into two functions —
`foundStrandAlone()` (the founder starts, founds, publishes, writes its pre-join rows) and
`enrollAndJoin()` (vouch, seed, apply, converge, discover, `addStrand`, gate the strand mesh both
ways) — so a test can run code *between* them. Test 1 and Test 2 call them back to back and are
otherwise untouched.

Then:

1. `foundStrandAlone()` writes five pre-join rows, as in Test 1, and one row that Test 3 will later
   **update** (so the run covers a revision advancing, which `compareBlockCoverage` reports as
   `behind` rather than `absent` — a different failure shape from a missing block).
2. Start a bounded continuous writer against the founder's strand database: one
   `insert into App.Data` per tick with a short delay, keys tagged with the phase so the failure
   message can say *when* a missing row was written, plus periodic `update`s to the row from step 1.
   The writer must be awaited to completion before any assertion, and any error it hits must be
   captured and re-thrown by the test rather than swallowed — a writer that died early would make
   every assertion below pass vacuously.
3. `enrollAndJoin()` runs while that writer is going.
4. Once the strand mesh is up in both directions, record the writer's cursor, let it run for a few
   more ticks, then stop it. Assert the set of rows written **after** the mesh formed is non-empty —
   without that, this test degenerates into Test 1.
5. **Physical gate.** Poll `compareBlockCoverage(founderStore, newcomerStore)` to completion with no
   `include` narrowing — the founder's whole store, at revisions no older than the founder's, with
   content bytes present. Carry the last gap into the failure message, and log which of the three
   gap kinds (`absent`, `behind`, `metadataOnly`) was last non-empty: `absent` on a post-mesh key
   points at the replication half, `absent` on a pre-join key at the catch-up half, and `behind` on
   the updated row at the seam between them. Read raw stores only here — the same rule as the
   companion ticket's Phase 3.
6. **Behavioural gate.** Read every key the writer recorded back from the newcomer's strand database
   and assert the full set is present with the expected values, naming any missing keys and the
   phase they were written in.

Suggested timeout 180_000.

## Edge cases & interactions

- **The writer must not outlive the test.** Stop it in the test body and again in `finally`, and
  await it before stopping either node — a stray insert against a stopping strand database throws
  into the teardown and masks the real failure.
- **A clean catch-up run is memoized per runtime, not per connection state.** If the newcomer's
  strand connection drops and re-opens mid-window, the peer is already `done` and gets no second
  push. That is by design; ordinary replication is expected to cover it. Do not add a reconnect to
  this test — a drop is not something it can stage deterministically, and asserting on one would
  make the file flaky.
- **Revision advance, not just presence.** The updated row is the reason the whole-store gate is used
  rather than a presence check: a newcomer holding an old revision of a block reports as `behind`,
  which is a real defect and reads as a pass to any assertion that only checks for the key.
- **`bug-strand-join-dies-on-missing-block` applies here too**, and a founder writing concurrently
  with the joiner's schema creation is a plausible way to make it more likely. If this test draws
  `Missing block` at a materially higher rate than Test 1 does, that rate difference is itself
  evidence worth recording on that ticket. Do not weaken the assertions here to get a green run.
- **Founder-side ordering.** The writer runs against the founder while the founder is also serving
  the catch-up push. Nothing serializes those; that is the point. If the founder's own writes start
  failing under that load, that is a finding, not something to tune around with a longer delay.

## Out of scope

Concurrent writes from *both* machines (this test writes only on the founder — a second writer would
make an absent row ambiguous between the two directions). Enrolling a third machine. Anything the
companion ticket already covers.
