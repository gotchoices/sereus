This is the **trigger policy + fan-out** half of server-side push-wake — the piece the parent `mobile-background-service` design called out as still-owned. It consumes the `PushNotifier` delivery from `cadre-push-notifier` and the existing `pushWake`/`resolveDeviceToken`/`listMembers` primitives, and adds: who decides to wake hibernating mobile peers, how they are enumerated, the direct-dial-vs-platform-push fallback, and the dedup/cooldown that keeps a chatty strand from spamming pushes.

## Trigger source (design question resolved)

There is **no passive activity-detection primitive** a participating node can subscribe to: Optimystic syncs pull-on-read and exposes no repo-level "new transaction" / "pull pending" hook (`IRepo` is get/pend/commit/cancel only — the same constraint that forces the check-in wake to be a blind resume→probe; see `tickets/backlog/hibernation-control-network-pending-precheck.md`). So a self-driving "detector that hooks strand-network traffic" is **not buildable today** without an Optimystic change, and we will not pretend otherwise.

The v1 trigger is therefore the node's existing **activity signal**, surfaced as an explicit seam:

- New `CadreNode.notifyStrandActivity(strandId, reason?)` — the imperative entry point an always-on host/relay/sApp calls when it observes activity for a strand this node participates in (mirrors how `recordStrandActivity` / `serviceWake` are imperative seams). This is the supported, honest trigger.
- The node also binds the fan-out to its own `recordStrandActivity(strandId)` call: recording activity on a participated strand additionally notifies the fan-out. This means whatever already drives activity on the server's strand (its relay/app layer doing pull-on-read, exactly as any host app does) also triggers fan-out — no new contract, the same seam local-wake (Wake Mechanism #1) already uses.

**Deferred (documented, not blocked):** a passive Optimystic-level detector (fan-out with zero application involvement) requires Optimystic to expose a commit/block-received hook. File that as a follow-up depending on the upstream hook; it is an enhancement over the explicit trigger, not a correctness gap. The explicit trigger fully serves a server/relay sApp that knows when activity lands.

## Fan-out + delivery flow

`PushFanoutService.notify(strandId, reason)`:

1. **Participation gate.** If `getStrand(strandId)` is undefined (we do not participate), no-op — never push for a strand we cannot vouch for, mirroring `StrandWakeService`'s membership gating and the "server not a member of the strand" edge case.
2. **Debounce per strand.** Coalesce bursts: if a fan-out for this strand ran within `debounceMs`, drop (the cohort is chatty; one wake is enough). A short trailing/leading debounce, not a queue.
3. **Enumerate candidates.** `listMembers()` → every `CadrePeer` except self. (Mobile-ness is discovered lazily in step 5 via `resolveDeviceToken`; do not maintain a separate registry.)
4. **Per-(peer,strand) cooldown.** Skip a candidate woken for this strand within `cooldownMs`. This is the anti-spam guarantee a chatty strand needs.
5. **Wake each surviving candidate — direct first, platform fallback** (`wakePeer`):
   - Try `pushWake(peerId, strandId, reason)` (direct control-network dial). **Success ⇒ done for this peer**: a reachable peer (foreground, or backgrounded-but-alive keeping its control network up) gets the direct wake; we deliberately **do not** also send a platform push (this is exactly how the "skip foreground/connected peer → would double-wake" edge case is satisfied — reachability is *probed by the dial*, not guessed from presence data we do not have).
   - On `pushWake` failure (no dialable address / dial timeout ⇒ the phone is suspended): `resolveDeviceToken(peerId)`. `null` ⇒ not a registered mobile peer, done. Otherwise `notifier.send({ token, platform, payload:{ type:STRAND_WAKE_TYPE, strandId, reason } })`.
   - Set the (peer,strand) cooldown once a wake of either kind is attempted.
6. **Stale-token handling.** If `send` returns `unregistered:true`, expire the peer's `DeviceToken` so it is not retried until the peer re-registers. `CadreNode.clearDeviceToken()` is **self-only** (it hardcodes the local peerId). Add a `CadreNode.expireDeviceToken(peerId)` that, when this node has an authority seed service, calls `seedBootstrapService.deleteDeviceToken(peerId)` (already authority-gated, accepts an arbitrary peerId); when the node is **not** an authority it cannot delete the row, so it records the token locally as stale (a `Set` of dead tokens consulted in step 5 to skip resolve→send) and logs that a re-registration is needed. Lossy on restart is fine (see below).

`wakePeer`/`notify` never throw to the trigger — failures are logged best-effort. The check-in wake remains the backstop, so a dropped push is recoverable.

## Wiring into CadreNode

- `CadreNode.start()` constructs a `PushFanoutService` **only when** `config.push` (FCM and/or APNs credentials) is present, injecting: `listMembers`/`getStrand`/`pushWake`/`resolveDeviceToken`/`expireDeviceToken` bound to `this`, a `PushNotifier` from `createPushNotifier(config.push)`, a monotonic clock (injectable for tests), and `cooldownMs`/`debounceMs` from `config.push` (defaults below). Without `config.push`, the node behaves exactly as today (no notifier, no fan-out) — every existing test stays green.
- `CadreNode.notifyStrandActivity(strandId, reason?)` delegates to the service (no-op when no service); `recordStrandActivity` additionally calls it.
- `CadreNode.cleanup()`/`stop()` calls `notifier.close()` (APNs session teardown) and drops the service.
- Self-exclusion: never fan a wake to our own peerId.

### Config additions

```ts
// extend PushCredentials (from cadre-push-notifier) or CadreNodeConfig.push
cooldownMs?: number;   // per-(peer,strand) min gap. default 5 * 60_000
debounceMs?: number;   // per-strand burst coalescing. default 10_000
```

## Edge cases & interactions

- **Peer with a DeviceToken but currently foreground/connected** → `pushWake` dials through; no platform push (no double-wake). The single most important interaction; assert it.
- **Multiple strands active for one device in a short window** → each strand's cooldown is independent, but cap fan-out so a device is not pelted: the per-(peer,strand) cooldown bounds per-strand; document that cross-strand coalescing into one push is **not** done in v1 (each strand-wake names its own `strandId`; the phone's `serviceWake` is per-strand). If on-device measurement shows pelting, add a per-peer (any-strand) rate cap as a follow-up. Name this limit in `STATUS.md`.
- **Token rotated between resolve and send** → `send` returns `unregistered`; `expireDeviceToken` clears (authority) or marks-stale (non-authority); next registration re-seeds. No retry.
- **Server not a member of the strand whose activity it sees** → participation gate (step 1) drops it before any enumeration.
- **Self in the member list** → excluded; never wake self.
- **`pushWake` succeeds but receiver rejects (`accepted:false`, e.g. non-member/unknown strand)** → treat as "reached, decision made by receiver"; do **not** fall back to platform push (the control path reached the peer). Only a *dial/transport* failure triggers fallback. Be explicit about ack-rejected vs dial-failed.
- **Cooldown/debounce state survives restart?** → **in-memory, acceptably lossy** by design. A restart resets cooldowns; worst case one duplicate wake, and `serviceWake` is idempotent/coalesced, so a duplicate is harmless. No persistence in v1 (document the choice; matches the parent ticket's "acceptably lossy" allowance).
- **Multi-tenant provider** — a `CadreNode` is single-party (one control network, one `partyId`); credentials are injected per spawned node. Device-token scoping cannot cross parties because `listMembers`/`resolveDeviceToken` read this node's own control DB. The cross-tenant boundary is enforced by the per-node credential injection in `cadre-host-push-credentials`; this service has no multi-tenant surface to leak across. Note it; no code here spans tenants.
- **Fan-out storm under burst** — debounce (per strand) + cooldown (per peer,strand) bound total sends; no unbounded queue, no retry loop. A `notify` for an already-debounced strand returns immediately.
- **Concurrent `notify` for the same strand** — guard with a per-strand in-flight marker so two near-simultaneous triggers do not both enumerate+send; the second joins/drops (mirror `serviceWakePromises` coalescing).

## Key tests (push-fanout.spec.ts, fakes for node primitives + notifier)

- participation gate: `notify` for an unparticipated strand → zero `pushWake`/`send` calls.
- reachable peer: `pushWake` resolves → `send` **not** called; cooldown set.
- suspended peer: `pushWake` rejects → `resolveDeviceToken` → `send` called with the exact `{type,strandId,reason}` payload + right platform.
- non-mobile peer: `pushWake` rejects, `resolveDeviceToken` → null → no `send`.
- cooldown: second `notify` within `cooldownMs` for same (peer,strand) → no second wake; after cooldown → wakes again (inject clock).
- debounce: two `notify(strandId)` within `debounceMs` → one fan-out pass.
- unregistered: `send` → `{unregistered:true}` → `expireDeviceToken` called (authority path deletes; non-authority marks stale and skips next resolve).
- self-exclusion: own peerId never woken.
- ack-rejected ≠ dial-failed: `pushWake` resolving `{accepted:false}` → no platform fallback.
- no-push-config node: `notifyStrandActivity` is a no-op; `recordStrandActivity` unchanged.
