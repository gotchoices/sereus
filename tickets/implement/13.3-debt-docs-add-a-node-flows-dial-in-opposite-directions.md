# Compare the add-a-node flows by who dials whom

Docs only. No code, no tests.

## The rule the section states first

Every flow that adds a machine to a cadre can arm a connection from either end, and one working direction is enough:

- **The adder dials the new machine** when it knows the new machine's addresses. `CadreNode.addDrone` (`packages/cadre-core/src/cadre-node.ts`, ~line 7769) calls `retainDialTarget(dronePeerId, droneMultiaddrs, …)`, and the control-cohort reconcile pass dials from that retained entry (every 15 s, or at once via `reconcileControlCohort()`). An empty `droneMultiaddrs` arms nothing.
- **The new machine dials the adder** when the seed (or its bootstrap list) carries the adder's addresses. A seed minted by a phone carries none, because a phone listens on nothing.

A node that never joins is one where the armed direction's target is not reachable and the other direction was never armed. Nothing fails at configuration time: the seed is accepted, `ApplySeedResult.ownerDialsFailed` is non-zero, the `CadrePeer` table stays empty, and the cold-start branch retries forever. That looks like a NAT or trust problem. Say so in one or two sentences; the retry mechanism is already described under "Cold-start bootstrap retries" — link, don't restate.

## The table

Columns: flow (linked to its own documentation), who dials, who must be reachable. Rows, with the facts verified during planning:

| flow | who dials | who must be reachable |
| --- | --- | --- |
| Reference app, phone plus a `cadre-cli` drone ([reference-app-rn.md → Two-Node Startup Sequence](../../docs/reference-app-rn.md)) | the phone dials the drone's `/ws` bootstrap address | the drone (same LAN, or a public address) |
| Phone borrows a cadre-host node, no `bootstrapNodes` ([cadre-host.md → The donate-a-node lifecycle](../../docs/cadre-host.md), [reference-app-rn.md → Borrowing a Node](../../docs/reference-app-rn.md)) | the requester dials the lent node's `/ws` address from `GET /grants/:id/peer`, retained by `addDrone` | the lent node — today only on the host's LAN |
| cadre-host donation with `bootstrapNodes` (a dialable requester such as a desktop `cadre-cli` node) | the lent node dials the requester; a `CadreNode` requester that passes the step-2 addresses to `addDrone` also dials the lent node | either one |
| `cadre enroll add` without `--addr` ([cadre-cli README → Add a Machine to the Cadre](../../packages/cadre-cli/README.md)) | the new machine dials the owner addresses in the seed | the owner (its listen addresses on a LAN, `network.appendAnnounceAddrs`, or a relay) |
| `cadre enroll add --addr <new machine>` | both: the owner also dials the new machine | either one |
| cadre-provider container | the container dials the requester's `bootstrapNodes`, which `POST /containers` requires | the requester; a phone cannot rent one yet (container listens on TCP only) — `tickets/backlog/feat-provider-drone-reachable-by-phone.md` |
| cadre-host founder invites a device (`cadre-host invite`; architecture.md → "Enrollment Flow: Server Adds Phone") | the invitee dials the host's addresses carried in the `CadreInvite` | the host's owner node |

Re-check each row against the linked page while writing; if a page disagrees with the row, the page's current text (and the code it cites) wins — fix the row, and if the page itself is wrong, fix the page.

Follow the table with a "when to use which" paragraph of two to four sentences, keyed on which of the two machines can accept a connection: a phone is never the dial target, so a phone adding a node needs the node reachable (rows 1, 2); a machine that can be dialed passes its own address so the new node dials it (rows 3, 4, 6); give both sets of addresses when unsure (rows 3, 5).

Where a reachability cell could be satisfied through a relay, do not restate the relay rules.
