# Cadre invitation and owner grant redemptions read the row once

Split from `plan/formation-and-redemption-read-each-row-once` (the cadre-invitation and owner-grant arms, plus the open-invitation minor). Siblings: `implement/formation-responder-reads-the-invitation-once`, `implement/joiner-hands-its-join-to-the-launch`.

## What runs today (traced)

At the member answering `/sereus/cadre-invite` (`CadreInviteHandler`, through `MemberRedemptionHandler.decide`):

| step | `CadreInvite` row | use count | other |
|---|---|---|---|
| `admitIfLive` → `isLive` → `isCadreInviteLive` (only when `admitDevice` is wired) | 1 (`queryCadreInvite`) | 1 | revoked stamps + owner keys (membership views) |
| `redeemAdmitted` → `seatCadreInvite` → `seatIssuedRow`, in the write lock | 1 (`queryStampId`) | | |
| `redeemCadreInvite`, in the write lock | 1 (`queryCadreInvite`) | 1 (`assertCadreInviteSeatRemains`) | `queryStampId('CadrePeer')` |
| reply → `peersBestEffort` → `querySeedPeers` → `queryCadrePeers` | | | `CadrePeer` (+ `Revocation`) view load |

The reply's load happens after the redemption committed: the commit dropped the `CadrePeer` view, and the membership refresh that `mutateCadrePeer` runs inside the write lock loaded it through the committed-read path, which the view does not keep (`complete/control-membership-rows-cached-until-changed`, "unlocked reads during a locked write body are not kept"). So the reply loads it again from storage.

Owner grants (`OwnerGrantHandler` and `CadreNode.redeemOwnerGrantLocally`) have the same shape: `isOwnerGrantLive` reads `OwnerGrant`, the seat reads its stamp, `redeemOwnerGrant` reads `OwnerGrant` again in the lock.

## Design

**One up-front read of the held row.** `CadreInvite` and `OwnerGrant` rows are never deleted and every column is under the issuer's signature (withdrawal is a `Revocation` row, not a change to the row), so the row this member holds, read once before the lock, is the row the in-lock read would return.

- New store method per credential (names indicative): `ControlDatabase.readHeldCadreInvite(key)` → the held row or null; same for grants. This is the existing `queryCadreInvite` / `queryOwnerGrant`; reuse them, don't add new SQL.
- `MemberRedemptionHandler` reads the held row once in `decide` (a new abstract hook, e.g. `readHeld(request): Promise<Held | null>`, generic over the held type) and passes it to `isLive(request, held)` and `redeemAdmitted(request, remotePeerId, held)`. This keeps the read when `admitDevice` is not wired, where `isLive` is not called.
- `isCadreInviteLive(invite, held?)`: judges `held ?? (verified bundle copy)` without reading.
- **Seat only when nothing is held.** `redeemAdmitted` calls `seatCadreInvite` only when `held === null`. When it seats, `seatIssuedRow` keeps its in-lock stamp read (that guard is what makes the seat insert-if-absent against a concurrent seat).
- **`redeemCadreInvite(params)` takes `invite?: CadreInviteRow`.** When given, the in-lock `queryCadreInvite` is skipped and `invite.issuerKey` / `invite.totalUses` come from it. Pass the **held** row only, never the bundle's copy: a requester can put any `totalUses`/`issuerKey` on a copy of a key this member already holds, and the in-lock seat check (`assertCadreInviteSeatRemains`) must judge the stored cap. After a fresh seat (`held === null`), pass nothing, so the in-lock read stays on that path (one redemption per member per invitation, the rare path). Same for `redeemOwnerGrant` with `grant?: OwnerGrantRow`.
- **The use count stays twice, on purpose.** The early count (inside `isLive`) decides whether to push the control store to the holder before the write (`admitIfLive`); a holder of a spent invitation must be refused without being sent anything. The in-lock count decides the seat. Note both in the doc of `isCadreInviteLive`.
- **The reply's peer list is built before the write.** In `redeemAdmitted`, call `querySeedPeers` before `redeemCadreInvite` (best-effort, as today: a failure costs hints, not the redemption). At that point the `CadrePeer` view is normally warm (the connection gate read it when the device connected). The list then lacks the device's own row, which the device drops anyway (`CadreNode` filters `reply.peers` by its own peer id, ~9899). Only build it once the request passed `checkRequest`, and don't send it on a refusal (refusal replies carry no peers today).
- **`redeemOwnerGrantLocally`** (cadre-node): read the held grant once, seat only when absent, pass it to `isOwnerGrantLive` and `redeemOwnerGrant`. Its existing ordering (alone refusal, seat, liveness refusal, then one approval around signing and the write) stays.

**Open-invitation minor.** `CadreNode.resolveInvitationSiblings` walks `listAuthorizedMembers()`, which includes this machine, so `createOpenInvitation` and `createCadreInvitation` resolve this machine's own `CadrePeer` record and add its addresses as a "sibling" next to `getMultiaddrs()`. Skip this machine's own peer id in that loop. Confirm first that the bootstrap list today carries this machine's addresses twice (a solo node's `createOpenInvitation` is the simplest check); if `selectInvitationSiblingAddrs` / `selectCadreInvitationMembers` already dedupe, the skip still saves the record read.

**Expected after**, typical redemption at a member that already holds the row: `CadreInvite` 1 read (from 3), use count 2 (unchanged, reason above), no `CadrePeer` storage load for the reply when the view is warm.

## Edge cases & interactions

- **Two redemptions racing for the last use.** Both may pass the early count; the in-lock count refuses the loser with `InvitationExhaustedError` → `invite-spent`. The carried row changes nothing here. Covered by the existing cadre-invite protocol and redemption specs.
- **Withdrawn between the early read and the write.** `NotRevoked` / `Authorized` CHECKs refuse at commit (`invite-spent`). The carried row must not be used to skip them. Verify by inspection.
- **Retry after a dropped reply.** `redeemCadreInvite` answers `alreadyMember` before the seat check; unchanged, since that check reads `CadrePeer`, not the invite.
- **Member that does not hold the row and whose cohort does (`adoptCohortHeldRow`).** The seat adopts the cohort's row; `redeemCadreInvite` then reads in the lock as today (no carried row). `IssuedRowNotHereYetError` keeps its meaning.
- **Bundle copy forged with a real key.** Covered by passing only the held row (above); `isLive` judges a bundle copy only after its issuer signature verifies, as today.
- **Owner grant for a key that is already an owner.** `redeemOwnerGrantLocally` skips the liveness check for an existing owner, and `redeemOwnerGrant` answers `alreadyOwner` before reading the grant's cap; keep both.
- **Reply peers read failing.** Best-effort as today: empty list, redemption still accepted.
- **Skipping this machine when its live address list is empty.** Today, when `getMultiaddrs()` is empty but this machine's own `CadrePeer` record still has fresh addresses (for example a relay-only node between reservations), the self "sibling" fills the bootstrap list. Once self is skipped, `createOpenInvitation` throws "No multiaddrs available for invitation" in that case. That is the right answer, because those addresses are ones the machine is not listening on now, but say so in the doc of `resolveInvitationSiblings`. Verify by inspection.
