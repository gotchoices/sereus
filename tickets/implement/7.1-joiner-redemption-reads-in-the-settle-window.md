# Record that the settle window's redemption cost is one redemption

## Finding (fix stage, 2026-10-20, `repro: verified`)

Run, after the sibling `@optimystic/db-p2p` was rebuilt and `@serfab/cadre-core` was built:

```
MESSAGE_COST_MEASURE=1 MESSAGE_COST_CASE=strand MESSAGE_COST_IDLE_S=5 DEBUG='sereus:cadre:strand-membership*' yarn workspace @serfab/integration-tests exec vitest run src/scenarios/message-cost-accounting.integration.ts
```

B's membership log lines, all printed during the `settle 15s` phase (after "A sees B insert" ended):

- `membership reconciler started` (during `B addStrand`)
- one `Consumed invite … -> member …`
- one `redeemed the staged membership invitation`
- one `Registered MemberPeer (…)`, about 150 ms later
- `membership reconciler stopped (done)`

There were no `consumeInvite failed — retrying next tick` lines and no `redeeming the staged invitation deferred` lines. So the redemption ran once and succeeded the first time. There was no retry, no busy refusal and no half-saved commit.

Settle-phase counts in this run: 93 app streams and 73 gets, the same as the doc comment's 2026-10-20 strand row. Of those gets, `consumeInvite` accounts for 33 and `registerMemberPeer` for 5. B opened 20 `/cluster` streams to A, which is the redemption commit (`Member`, its `StampId` UNIQUE tree, `ConsumedInvite`) plus the binding commit (`MemberPeer` and its `StampId` UNIQUE tree). That fits about 4 requests per collection, the cost tracked in `blocked/optimystic-multi-collection-commit-costs-four-requests-per-collection`. The 2026-10-19 baseline's 47 reads were the same single call; the count has fallen since then.

These land in the settle window because the scenario's "A sees B insert" step waits for B's `App.Seat` row, not for B's `Strand.Member` row. The membership reconciler redeems in the background after `publishDatabase` wakes it. Do not add a phase that waits for membership: it would move counts between phases and make the baseline incomparable.

## Not filed: the 33 reads inside one `consumeInvite`

The strand schema's `ConsumedInvite` checks `InviteExists`, `ValidUsage` and `NotExpired` each look up the same `Invite` row, and `MemberExists`, `NotCancelled`, `NotSealed` and the `Member` insert's own checks read more. This is a one-time cost per join, so no ticket was filed. Neither `formation-responder-reads-the-invitation-once` nor `cadre-invite-and-grant-redemption-read-the-row-once` covers it (both are about control-database reads). If someone later wants to reduce join cost, a general fix would be a transaction-scoped block cache in Optimystic rather than merging security checks in `schemas/strand.qsql`.
