# Scenario: an app's strands move between cadres

The cadre-core primitives (`exportStrandBundle`, `adoptStrandBundle`) are unit-tested on their own; this scenario is the only proof that a moved strand's other member, who was never told anything, keeps syncing with it, and that the new cadre's always-on machine picks it up.

## Machines

- **N**, the app's one node, phone-shaped (`listenAddrs: []`, `transaction` profile), one identity key for its whole life. Founds party B as its own owner (`makeOwnOwner`), with a durable `KeyStore`-backed joined-strand store and a strand network state store, so its records survive the switch like the phone kit's do.
- **P**, an external party of its own: one storage-profile node, its own owner.
- **O**, the owner of party A, phone-shaped. **M**, A's always-on member, `storage` profile with `hostUnclaimedStrands: true`, admitted by O (`startPinningMember`, `admitMember`, as `app-joins-cadre-by-invitation` does).

Both N and P need an address the other can dial while N is phone-shaped: follow `strand-formation-cross-party-seed` (a loopback WebSocket listen on the strand side, or a dedicated relay from `dedicated-relay.ts`), whichever that scenario uses today.

## Steps

1. **In B.** N founds a closed strand S with the chat-style sApp the formation scenarios use, publishes a bound formation invitation for it; P redeems it (`formStrand`) and becomes a member. P founds an open strand T and invites N; N joins T, so N holds a machine-local joined record for T (its party never publishes it: B is alone). Both write a row each way and the rows arrive. N writes one more row to S that P has not yet received (stop P's strand node for S, or sever the link, before the write), so the move carries a write made alone.
2. **Export.** `bundle = await exportStrandBundle(N)`. Assert, read not narrated: two entries (S `own` with a party key, T `joined`), S's network state present, one formation invitation entry for S's token with its uses reduced by one.
3. **Switch.** Stop N. Start a new `CadreNode` with the same identity key for party A, no owner genesis (as the kit's `origin: 'joined'` start), on the same raw storage capture (`captureRawStorage`) so S's and T's strand blocks are the ones written in B. O mints an owner-granting invitation targeted at N's peer id; N redeems it (`redeemWaitingForMember`), wires its key (`wireOwnKeyIfOwner` true).
4. **Adopt.** `report = await adoptStrandBundle(N, bundle)`. Assert `moved` is `[S, T]`, nothing refused or failed, `invitationsMoved` 1. Then adopt the same bundle again and assert the same report with nothing duplicated in A's tables.
5. **The strands run in A.** N claims S and T with the sApp config (the reference app claims a discovered row). Assert:
   - P's strand node for S reconnects with N (P's `MemberPeer` view of N is unchanged: same member key, same peer id) and P receives the row N wrote alone in step 1.
   - P writes a new row to S and T; N, now in A, receives both.
   - M launches replicas of S and T from A's `Strand` and `JoinedStrand` rows (its strand instances exist; block coverage of N's strand stores against M's, as `strand-always-on-replica-hosts-cross-party-join` checks with `block-store-probe.ts`).
   - The formation invitation moved for S is redeemable in A: a fresh third party redeems the same envelope against N (now answering from A) and is admitted, and A's `FormationUsage` holds one row for the token.
6. **The strand's identity is unchanged.** Read S's `Member` and `Manager` rows on P: N's party key's public half is still the one seated, and no second founding member appeared.

## What this scenario deliberately leaves out

- Dissolving B: `dissolve-empty-cadre`.
- The kit's timing (export before the switch, adopt after the owner wires): `move-strand-between-cadres`, which has its own unit tests.
- A relay-only link: the move changes no addresses, so the relayed variants of the formation scenarios cover it.

## Edge cases & interactions

- **The order of adoption versus the watcher** is exercised live here: A's watcher runs during adoption, and step 6 is the assertion that no second identity was minted.
- **N's unsynced write** (step 1) crossing the switch: asserted in step 5. Strand storage is scoped by strand id, not by party, so the blocks written in B are the blocks A's launch reads.
- **M's cohort seed**: M has no address for S's other party; it reaches P through N over the strand-address RPC inside A. If step 5's replica assertion is flaky for that reason, wait on `strand:started` on M before the coverage check, as the replica scenario does.
