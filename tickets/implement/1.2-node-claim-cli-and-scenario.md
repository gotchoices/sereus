# `CADRE_CLAIM_SECRET`, claim state on `/status`, and the phone-claims-a-node scenario

Third of three tickets. `node-claim-proof-and-policy` and `node-claim-gate-and-helper` landed the mechanism in `@serfab/cadre-core`. This ticket exposes it on the headless CLI, which is what cadre-host spawns, and proves the whole flow with real processes. cadre-host's own join flow (QR, UI, minting the secret) is `cadre-host-join-a-cadre` and is not touched here.

## cadre-cli

- **`CADRE_CLAIM_SECRET`** joins `COMMAND_ENV` in `config/env.ts`: a secret, read by the command, never a config-file path, like `CADRE_SEED_TOKEN`. Env only; there is no flag, because a flag value shows in the process list.
- **`start.ts`**: when set, pass `claim: { secret }` in `CadreNodeConfig`. Refuse, before `resolveConfig` finishes its other work, any of `--owner`, `--seed`, `--invitation`, `--pin-owner-key` or `CADRE_OWNER_KEYS` alongside it, with one message naming the conflict (the node refuses the pin conflict too, but the CLI's message is the one an operator reads). `--listen-for-seeds` is redundant with it and allowed. Print `✓ Awaiting claim` after start and, on `claim:accepted`, `✓ Claimed by owner <first 8 characters of the key>`. The secret is never printed or logged.
- **`/status`** (`server/health.ts`): add `claim: 'awaiting' | 'claimed' | 'none'` under `node`, from `isAwaitingClaim()` and whether `claim` was configured. cadre-host's join UI will poll this; nothing else in the status body changes.
- **README**: a row for `CADRE_CLAIM_SECRET` in the environment table, and a short "Waiting to be claimed" paragraph in the enrollment section: what the node admits while unclaimed, that the secret is one-time and bound to this node's identity, and that a claimed node ignores the variable.

## Scenario: `node-claim-by-phone.integration.ts`

A phone-shaped claimant (in-process `CadreNode` with `listenAddrs: []`, WebSocket and circuit transports only, owner genesis on itself; `controlNodeConfig` and `makeOwnOwner` in `harness/node-fixtures.ts`, as `cadre-host-donation-phone-requester.integration.ts` builds it) against a real `cadre-cli` child started with `CADRE_CLAIM_SECRET`, a `/ws` listen address, a persistent identity file and a node-state directory under a temp root. Spawn it the way `harness/provider-process-orchestrator.ts` spawns the provider's child, or through cadre-host's `HostProcessOrchestrator` with its extra-env seam if that is less code; either way the child's `CADRE_*` environment must be scrubbed first, as both do. Steps, one `it` each so a failure names the step:

1. The child is up and `/status` reports `claim: 'awaiting'`; the claimant is genuinely undialable (`getMultiaddrs()` empty).
2. `claimNode` with a wrong secret throws `ClaimRefusedError` with code `claim-proof-invalid`; `/status` still says awaiting; the claimant holds no `CadrePeer` row for the node and no retained dial target.
3. `claimNode` with the right secret resolves; `/status` says `claimed`; the claimant dials in (an outbound connection on its side, a WebSocket control connection on the child's); rows cross both ways: the child's self-published, signed `CadrePeer` record reaches the claimant, and the claimant's row is in the child's authorized set. Reuse the donation-phone scenario's waits for this.
4. A second phone-shaped owner, a different cadre, calls `claimNode` with the same secret and gets `already-claimed`.
5. The first owner calls `claimNode` again: resolves (idempotent), one `CadrePeer` row for the node, no duplicate dial target.
6. The child is stopped and restarted on the same workdir and environment: `/status` says `claimed` without any further claim, and the claimant reconnects on its retained dial target.

Budgets generous, as the sibling scenarios' are: two real child starts plus an in-process node. Register the file wherever the integration suite lists scenarios, and add it to the topology coverage map in `docs/testing.md` if that map lists per-scenario shapes (check "Topology coverage map" there).

## Edge cases & interactions

- **Env name check**: `checkEnvNames` rejects unknown `CADRE_*` names, so the variable must be in `COMMAND_ENV` or the child dies at start. Covered by the scenario's step 1.
- **Set-but-empty value**: `specifiedEnv` treats it as unset, as for every other variable; the node then starts without a claim and admits everything, as today. Document in the README row that an empty value is "no claim".
- **Flag conflicts**: refused with the message, before anything binds a port. By inspection.
- **Restart with the variable still set after the claim**: step 6.
- **`CADRE_SEED_TOKEN` and `POST /seed`**: untouched. A node with a claim secret and a seed token would refuse a `POST /seed` seed as `claim-proof-invalid`, which is correct; removing the HTTP seed path is `cadre-host-join-a-cadre`'s call.
- **Stale-build guard**: the scenario runs real `cadre-cli` from `dist`; build `@serfab/cadre-core` and `@serfab/cadre-cli` before running, and never build a sibling repository (`tickets/rules/sibling-repos.md`).
