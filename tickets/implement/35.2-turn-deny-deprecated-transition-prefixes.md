## Context

`turn-ssrf-peer-deny-hardening` added `denied-peer-ip` entries in
`ops/docker/coturn/turnserver.conf` for IPv4-mapped (`::ffff:0:0/96`) and
NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`) so a TURN relay peer can't reach
private IPv4 services through an IPv6 encoding. The block comment above those
entries (lines 67-71) claims "every non-public IPv6 range," which isn't
literally true: two deprecated IPv6-to-IPv4 transition prefixes also encode
an IPv4 address and aren't covered.

Decision (made in planning): add both ranges. Low realistic exposure (both
mechanisms are deprecated and need a specific transition gateway in path),
but the fix is cheap, consistent with the existing deny-list style, and
correcting the overclaiming comment either way requires touching this block.

## What the two ranges are

- **6to4 — `2002::/16` (RFC 3056, deprecated by RFC 7526).** Addresses of
  form `2002:<v4-hex>::` encode an IPv4 address in bits 16-48, e.g.
  `2002:0a00:0001::` encodes `10.0.0.1`. The 6to4 relay anycast destination
  `192.88.99.0/24` is already denied in the IPv4 block (line 60), which
  covers the return path but not an attacker directly addressing
  `2002:<private-v4-hex>::` if a 6to4 tunnel happens to be in path.
- **Teredo — `2001:0000::/32` (RFC 4380).** Encodes a Teredo server IPv4 and
  an obfuscated client IPv4. Requires a Teredo tunnel in path.

## Edge cases & interactions

- Malformed start-end range syntax is silently ignored by coturn in some
  versions rather than erroring — the config parse check's grep for
  `Unknown config option|ERROR|...` may not catch a subtly wrong range
  (e.g. off-by-one in the end address). Double-check the hex range math by
  hand against `2002::/16` and `2001:0000::/32` boundaries before relying
  solely on the parse check.
- `2001::/32` is close to (but distinct from) other allocated 2001:: space
  (e.g. `2001:db8::/32` documentation prefix is separately outside this
  range at the high end — Teredo is only the first /32 of 2001::). Don't
  widen the range beyond `2001:0000::/32`.
- These entries only take effect once TURN is enabled (`TURN_ENABLED=true`
  appends the auth+relay block per `entrypoint.sh`) — no behavior change for
  STUN-only deployments, consistent with the rest of this deny block.
