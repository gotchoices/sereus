# Owner grants: integration scenarios

`owner-grant-node-api` added `createOwnerGrant`, `redeemOwnerGrant` and `joinWithOwnerGrant`, with in-process unit tests. These two scenarios run them across real libp2p nodes, the way `cadre-invite-any-member.integration.ts` runs machine invitations. Follow that scenario's setup (an owner phone with no listen address, one always-on member) and its harness helpers (`harness/cadre-invite.ts`, `harness/owner-key.ts`); add grant helpers there rather than in the scenarios.

## Scenario 1: an owner key with no machine

`owner-grant-without-machine.integration.ts`.

1. Owner O (phone shape) and always-on member M form a cadre.
2. O mints an owner grant labelled "hardware key", single use.
3. A third node H is started in the party with an empty store (not a member) and redeems the grant over the protocol with a fresh software signer; it never redeems a machine invitation.
4. Expect: the new key is a live `OwnerKey` row on M and, after replication, on O, labelled "hardware key", with `VouchOwner` = O's key; O's and M's anchors derive it (`listOwnerKeys` reports it trusted); `listMachines` on O is unchanged (no machine was admitted).
5. Redeeming the same grant again from another node with another key is refused `grant-spent`.

## Scenario 2: a backup grant used later, issuer offline

`owner-grant-backup-recovery.integration.ts`.

1. O and M form a cadre; O mints a backup grant (`expiresInMs: null`).
2. O stops (the lost phone).
3. A fresh node F, started in the party with an empty store, calls `joinWithOwnerGrant` with a fresh key.
4. Expect: F is a member (its `CadrePeer` row admitted by its self-invitation) and an owner (`isOwner()` true after its key is wired); M's anchor trusts F's key.
5. F, now an owner, removes O's machine and O's owner key (`removeMachine`, `removeOwner`), which is the recovery a lost-phone user needs.

## What these do not cover

The single-use race across two machines is an accepted tradeoff (`OwnerGrantUsage.Authorized`'s `NOTE:`) and gets no scenario, as for machine invitations.

## Edge cases & interactions

- **M alone with the holder** (scenario 2, O stopped): the write must commit with the holder counted in the cohort; that is the point of the push. Verified by scenario 2 succeeding with O gone.
- **Stranger connection deadline**: H and F are strangers to M until the exchange verifies; the exchange must not be cut at the provisional deadline. Verified by both scenarios on default timings.
- **Anchor derivation on a machine that was offline at redemption** (O in scenario 1, if it reconnects after): verified by step 4's check on O.
