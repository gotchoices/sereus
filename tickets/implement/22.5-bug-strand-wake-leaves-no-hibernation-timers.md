# After a wake settles, the strand's timer cycle must match its resulting state

## What is wrong

`HibernationManager` (`packages/cadre-core/src/hibernation-manager.ts`) keeps two kinds of per-strand timers: the idle countdown (active → idle → hibernating, in `timers`) for a live strand, and the check-in chain (in `checkInTimers`) for a hibernating one. Every wake first clears both (`clearTimersForWake`). Only some callers put the right timers back afterwards:

- **Activity-driven wake** (`recordActivity` on an idle or hibernating strand): its `.then` after `beginWake` re-arms the idle countdown when the strand reads `'active'`. Correct.
- **Explicit or peer-sent wake** (`CadreNode.wakeStrand` → `HibernationManager.wakeStrand`; used by the push-wake receiver in `strand-wake-protocol.ts`, `wakeHostStrandForFormation`, and the founder `needs-resume` path in `claimTrackedStrand`): nothing re-arms the idle countdown. The strand stays `'active'` with no timer until something records activity. Calling it on a strand that is already live also cancels that strand's running idle countdown and never restarts it.
- **`CadreNode.serviceWake`** (mobile on-demand check-in): its wake (`hibernationManager.wakeStrand`) cancels an armed check-in chain, then `runWakeWindow` re-hibernates the strand when no activity arrived, and nothing re-arms the chain. On a node that hibernates on timers, one `serviceWake` ends that strand's check-ins until the next idle-driven hibernation. (The mobile runner force-hibernates with no chain, so it is unaffected; the fix must keep it that way.)

A failed wake already restores a cancelled chain (`restoreCheckInChain`), and a check-in that leaves the strand live restarts the idle countdown (`rearmIdleAfterCheckIn`). This ticket is the success-path counterpart.

### Reproduction (verified)

A throwaway spec against `HibernationManager` with `idleTimeout: 1000, hibernateTimeout: 1000, checkInInterval: 100` and fake timers, callbacks that set `instance.status` as `CadreNode` does (deleted after the run):

- Track, advance 2050 ms (strand hibernating, chain armed), `await manager.wakeStrand(id)` (status → `'active'`), advance 5000 ms: `onIdle` ran once (the pre-wake one) — the woken strand never idled again. Expected 2.
- Track an active strand, `await manager.wakeStrand(id)` immediately, advance 5000 ms: `onIdle` ran 0 times. Expected 1.

The `serviceWake` chain loss is static (read from `runServiceWake` + `beginWake`'s `finally`, which drops `checkInsCancelledByWake` on success).

## Expected behaviour

When a wake settles, the manager leaves the strand with the timers its state calls for, whoever triggered it:

- a live (`'active'` or `'syncing'`) strand with a finite idle timeout has its idle countdown running;
- a strand that reads `'hibernating'` again and had an armed check-in chain before the wake has that chain re-armed (at the base delay, as `restoreCheckInChain` does today);
- a strand force-hibernated without a chain gains none;
- nothing is armed when hibernation is disabled (`config.enabled` false — `CadreNode.wakeStrand` still wakes then, see `wakeHostStrandForFormation`'s doc) or the manager is stopped.

For `serviceWake`, the window — not the wake's settle — decides the timers, because the window runs after the wake settles and may re-hibernate the strand. If the wake's settle armed the idle countdown, an `archive` strand (10 s idle timeout, 15 s default window, `DEFAULT_CHECKIN_WINDOW_MS`) would idle mid-window and schedule a hibernate timer that later fires `onHibernate` → `scheduleCheckIn`, giving a force-hibernated mobile strand a chain.

## Design

**One settle helper, run from `beginWake`.** Change `beginWake(strandId)` to `beginWake(instance: StrandInstance)` (the manager needs the instance to arm timers; `recordActivity` already has it, and `CadreNode` passes the shared instance from `strandManager`). After `onWake` settles — success or failure — call one helper, e.g.:

```ts
/** Leave a strand whose wake (or probe) settled with the timers its state calls for. */
private rearmAfterWake(instance: StrandInstance, hadCheckInChain: boolean): void {
	if (!this.config.enabled || !this.running) return;
	if (instance.status === 'hibernating') {
		this.clearTimer(instance.strandId);          // a hibernating strand has no idle countdown
		if (hadCheckInChain) this.scheduleCheckIn(instance);
		return;
	}
	this.rearmIdleIfLive(instance);                 // today's rearmIdleAfterCheckIn, renamed
}
```

`hadCheckInChain` for a plain wake is `checkInsCancelledByWake.has(strandId)` read in the settle, before that entry is deleted. This replaces `restoreCheckInChain` (its failure-path job is the `'hibernating'` arm) and folds away the `.then` re-arm in `recordActivity` (keep its `.catch` log). Note the live check widens the activity path from `'active'` to `'active' | 'syncing'`, matching `rearmIdleAfterCheckIn` and the expected behaviour above.

**`wakeStrand(instance)`.** `HibernationManager.wakeStrand` takes the instance. `CadreNode.wakeStrand` already looks it up; when it is missing, `handleStrandWake` would only log "not found", so skip the manager call (log it) instead.

**Probe entry points for `serviceWake`.** Add a small per-strand record held from the probe's wake until its window ends:

```ts
/** Strands an on-demand probe (CadreNode.serviceWake) holds from its wake to the end of its window, with whether a check-in chain was armed when it began. While held, the probe's end — not the wake's settle — sets the timers. */
private readonly probes: Map<string, { hadCheckInChain: boolean }> = new Map();

async probeWake(instance: StrandInstance): Promise<void>   // record (checkInTimers.has || checkInsCancelledByWake.has), clearTimersForWake, await beginWake(instance)
endProbe(instance: StrandInstance): void                     // take the record (no-op if absent), rearmAfterWake(instance, record.hadCheckInChain)
```

`beginWake`'s settle skips `rearmAfterWake` while `probes` holds the strand. `runServiceWake` calls `probeWake` instead of `wakeStrand`, and `endProbe` in a `finally` that runs after its `catch` (so the failure path, after `rehibernateAfterFailedResume`, also gets its chain back). If activity during the window left the strand live, `endProbe` arms the idle countdown (restarting one `recordActivity` already armed is harmless).

Clear `probes` alongside `checkInsCancelledByWake` in `stop()`, `untrackStrand()` and `forceHibernate()` — a force-hibernate during a probe means "keep it down, no chain", so `endProbe` then finds no record and arms nothing.

Coalescing notes, checked while designing:
- A probe joining a push-wake's in-flight `beginWake`: the push-wake set `lastActivity` (in `CadreNode.wakeStrand`), so the window sees activity and leaves the strand live; `endProbe` arms the idle countdown. Reading `checkInsCancelledByWake` in `probeWake` keeps the chain record even though the push-wake already cleared the timer.
- A push-wake joining a probe's `beginWake`: settle is skipped (probe held); the window sees the push-wake's activity and `endProbe` arms idle.
- A wake joining a check-in's rebuild (`handleStrandWake` → `'starting'` → joins `resumeStrand`): the wake's settle arms idle; the check-in window sees activity, stays up, and `runCheckIn` → `rearmIdleIfLive` re-arms idle. Consistent.
