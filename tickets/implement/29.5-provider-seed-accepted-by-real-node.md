# Prove a provider-started node accepts the seed the provider delivers

A "seed" is the signed bundle telling a fresh node which peers form a cadre and
how to dial them. On the hosting-provider path two independent gates decide the
outcome: the provider must be *allowed* to deliver (the per-container
`CADRE_SEED_TOKEN` bearer), and the node must be *willing* to honour what was
delivered (its own trust check against the owner keys it was started with,
`CADRE_OWNER_KEYS`).

Every provider test today stops on the provider's side of that boundary —
`container-seed-endpoint.test.ts` replaces `fetch` with a stub, so no real node
ever decides anything. If the *provider's* side of the env contract drifts,
every provider test still passes and every customer's first seed is silently
refused. This ticket closes that gap with a real `@serfab/cadre-cli` child
started from the provider's own `buildNodeEnv()` output.

## Shape of the scenario (spec — unchanged from run 1, condensed)

Model on `cadre-host-node-donation.integration.ts`: ordered-step `it()`s,
`STARTUP_MS = 90_000`, `OP_MS = 30_000`, `waitUntil` from the harness,
teardown that never masks the test failure.

Three moving parts:

1. **Owner authority** — copy donation scenario lines 116–163 verbatim-ish:
   `writeIdentity` (protobuf key), `HostProcessOrchestrator` (use port band
   **20200–20339** — 19600–20199 are claimed by other suites) with
   `libp2pPort: 0`, `ensureOwnerNode`, `OwnerNodeClient`, readiness `waitUntil`
   with node-log dump on failure. Owner key =
   `ed25519KeyPairFromLibp2p(identityKey).publicKeyB64`; bootstrap addrs =
   `getMultiaddrs()` each suffixed `/p2p/<peerId>` (donation's `withPeerId`).
2. **Provider-shaped nodes** — the new `ProviderProcessOrchestrator` (done).
3. **Real delivery path** — `new ContainerService({ store: new MemoryStore(),
   orchestrator })` from `@serfab/cadre-provider`; real `fetch`, no stubs.

### Steps to assert

1. **Authority up**: `getPeerId()` matches identity on disk; ≥1 multiaddr.
2. **Provision node A pinned to the owner**: `createContainer({ customerId,
   partyId, bootstrapNodes, profile: 'storage', pinnedOwnerKeys: [ownerKey] })`;
   poll store until `running` (real `waitForEnrollment` `/status` loop);
   assert `seedToken` persisted and
   `seedEndpoint === healthEndpoint.replace('/health', '/seed')`.
3. **Node A accepts the owner's seed** *(the assertion this ticket exists
   for)*: poll `getPeerInfo(id)` until real peerId+multiaddrs; feed to
   `ownerClient.addDrone({ dronePeerId, droneMultiaddrs })` → `encodedSeed`;
   poll `containerService.applySeed(id, encodedSeed)` until
   `success === true` (seed route can race readiness); assert
   `peersAdded >= 1`.
4. **Node B pinned to a stranger refuses the same seed**: provision B with
   `pinnedOwnerKeys: [ed25519KeyPairFromLibp2p(await generateKeyPair('Ed25519')).publicKeyB64]`
   (must be well-formed — `validatePinnedOwnerKeys` runs at startup, a garbage
   pin means B never starts). Wait until B is `running` in the store FIRST
   (a not-yet-ready node must not masquerade as a trust refusal), then a
   SINGLE `applySeed` with step 3's seed: `success === false`, `peersAdded`
   absent/0, error matches `/(neither|not).*(anchored|pinned)/i` — the real
   reason string is `Signer key is neither an anchored nor a pinned owner
   (pinned-key trust policy)` (`cadre-core/src/seed-trust-policy.ts:113`; the
   run-1 ticket's suggested `/not .*/` regex never matches — do not use it).
   `ContainerService.applySeed` wraps non-OK as
   `Seed endpoint returned 400: <raw body>` (`container-service.ts:350-353`) —
   assert against the wrapped string.
5. **Token gate vs trust gate are independent** (can live inside step 4's
   `it`): direct `fetch` POST to B's `seedEndpoint` with a WRONG bearer →
   HTTP **401** body `{"success":false,"error":"unauthorized"}`; the correct
   bearer + untrusted signer above → **400**-with-reason. Two refusals, two
   causes.
6. **Restart node A with no pin; a second seed from the same owner is still
   accepted** (proves the first seed anchored the owner key on the durable
   volume):
   - first assert `trusted-owners.<encoded party>.json` in
     `orchestrator.volumeDirFor(idA)` has `owners` containing ownerKey (copy
     donation scenario's `readNodeLocalStore` prefix-match helper, lines
     75–96 + 275–304 — poll: the store write lags applySeed's response);
   - `ContainerService.createContainer` CANNOT restart (always mints a fresh
     `ctr_` id): instead `orchestrator.stopContainer(record.dockerId)` (NOT
     `terminateContainer` — that sets the store record `stopped` and
     `applySeed` requires `running`/`enrolling`), then call
     `orchestrator.createContainer` DIRECTLY with the same `containerId` and
     NO `pinnedOwnerKeys` (volume reused → same identity), patch the store
     record via `store.saveContainer` with the fresh
     dockerId/healthEndpoint/metricsEndpoint/seedEndpoint/seedToken and
     `status: 'running'`, poll `getPeerInfo` until live, mint a second seed
     via `addDrone` (multiaddrs changed — new p2p port), poll `applySeed`
     until accepted.
   - If total wall-clock approaches the runner's 10-minute idle window, drop
     this step to a follow-up ticket rather than making the suite
     un-runnable — and say so in the handoff.

### Edge cases (from run 1, all still apply)

- **No pin at all** (`pinnedOwnerKeys: []` → no `CADRE_OWNER_KEYS` → must
  refuse): cheap variant only if B is parameterised; a third child process is
  not worth it — step 4 already proves discrimination. Note the choice in the
  handoff.
- **Enrollment timeout tripwire**: `provisionContainer` hard-codes
  `waitForEnrollment(id, 60000)`; on timeout the record stays `enrolling`
  forever (nothing re-polls). A cold real node normally beats 60s but the
  donation suite budgets 90s. If this flakes, the fix is a configurable
  timeout in ContainerService, not test papering — flag in handoff.
- **Teardown**: iterate `orchestrator.listHandles()` → `stopContainer` each
  (swallow per-handle errors); authority via `stopOwnerNode()` +
  `removeContainer`; then
  `rmSync(tmpRoot, { recursive: true, force: true, maxRetries: 10, retryDelay: 200 })`
  in a swallowed catch (Windows lags on workdir release).
- Every negative assertion gated on the node being `running` first — a fetch
  error from a still-starting node is not a trust refusal.
