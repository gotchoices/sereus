# Prove a provider-started node accepts the seed the provider delivers

A "seed" is the signed bundle telling a fresh node which peers form a cadre and
how to dial them. On the hosting-provider path two independent gates decide the
outcome: the provider must be *allowed* to deliver (the per-container
`CADRE_SEED_TOKEN` bearer), and the node must be *willing* to honour what was
delivered (its own trust check against the owner keys it was started with,
`CADRE_OWNER_KEYS`).

Every provider test today stops on the provider's side of that boundary —
`container-seed-endpoint.test.ts` replaces `fetch` with a stub, so no real node
ever decides anything. The claim that the whole path works rests on the
self-hosted sibling (`cadre-host-node-donation.integration.ts`) proving the
equivalent flow with the same environment-variable contract. If the *provider's*
side of that contract drifts, every provider test still passes and every
customer's first seed is silently refused.

## Shape of the scenario

New file `packages/integration-tests/src/scenarios/provider-seed-accepted.integration.ts`.
Model it closely on `cadre-host-node-donation.integration.ts` — same ordered-step
`it()` structure, same generous timeouts (`STARTUP_MS = 90_000`, `OP_MS = 30_000`),
same `waitUntil` helper, same afterAll teardown discipline.

Three moving parts:

1. **The owner authority** — reuse cadre-host's `HostProcessOrchestrator` +
   `ensureOwnerNode` + `OwnerNodeClient` exactly as the donation scenario does
   (`cadre-host-node-donation.integration.ts:127-163`). It founds party `P`,
   exposes `getPeerId()` / `getMultiaddrs()` for bootstrap addresses, and mints
   seeds via `addDrone({ dronePeerId, droneMultiaddrs })`. This is proven
   machinery; do not reinvent it. Its owner key is
   `ed25519KeyPairFromLibp2p(identityKey).publicKeyB64`.

2. **A provider-shaped node** — a new test harness orchestrator (below) that
   spawns a real `@serfab/cadre-cli` child using the provider's own
   `buildNodeEnv()` output. This is the whole point: the environment is *taken
   from the provider*, not hand-written in the test.

3. **The provider's real delivery path** — a real `ContainerService`
   (`@serfab/cadre-provider`) over a `MemoryStore` with the harness orchestrator
   injected. `createContainer` → `provisionContainer` → real `/status` polling →
   `applySeed` with a real `fetch`. No stubbing anywhere.

`@serfab/cadre-provider` must be added to `packages/integration-tests/package.json`
dependencies (`workspace:*`); today the suite only depends on `cadre-host`.

## The harness orchestrator

`packages/integration-tests/src/harness/provider-process-orchestrator.ts`,
exported from `harness/index.ts`:

```ts
/**
 * Runs a cadre node as a plain child process using the environment
 * `@serfab/cadre-provider` builds for its Docker containers. Stands in for
 * DockerOrchestrator so a real node can be started the provider's way
 * without a Docker daemon in CI.
 */
export class ProviderProcessOrchestrator implements Orchestrator { ... }
```

It implements the provider's `Orchestrator` interface (`createContainer`,
`stopContainer`, `removeContainer`, `getStats`, `isRunning`, `getLogs`) so
`ContainerService` drives it unmodified.

`createContainer` must:

- allocate a per-container "volume" directory under the suite's tmp root — this
  is the stand-in for the image's `/data` durable volume, and it must survive a
  restart of the same container id (that is what step 5 tests);
- pick three free host ports (bind-to-0-then-close, or a fixed private band as
  the donation scenario does with `portRange`);
- materialise the node identity the way `entrypoint.sh` does: if
  `<volume>/cadre-peer.key` is absent, run
  `node <cadre-cli bin> enroll create --output <volume> --name cadre-peer`
  as a child and wait for exit;
- build the child env as, **in this precedence order**:
  1. parent env with every `CADRE_*` key scrubbed (copy the rationale from
     `host-process-orchestrator.ts:57-75` — an inherited `CADRE_PARTY_ID` on the
     dev's shell would otherwise silently reconfigure the child),
  2. the image's own `ENV` block from `packages/cadre-cli/docker/Dockerfile:117-124`,
     with `/data` rewritten to the volume dir (`DATA_DIR`, `CADRE_STORAGE_TYPE`,
     `CADRE_STORAGE_PATH`, `CADRE_HIBERNATION_ENABLED`),
  3. the two vars `entrypoint.sh` derives and exports (`CADRE_KEY_FILE`,
     `CADRE_NODE_STATE_DIR` — both under the volume dir),
  4. **`buildNodeEnv({ request, seedToken, ports })` parsed into key/value
     pairs** — last, because in Docker the container `Env` overrides the image
     `ENV`, and the provider's values must win here for the same reason;
- write a minimal config file into the volume dir. `cadre-cli start` fails if
  `-c` names a missing file, and the container gets one from `entrypoint.sh`'s
  `generate_config`. Everything that generated YAML carries is re-applied from
  the env anyway (`applyEnvironmentOverrides` beats the file), *except*
  `strandWatchInterval` and `hibernation.defaultLatencyHint`, which have no
  `ENV_MAPPINGS` entry — write those two with the entrypoint's defaults (5000 /
  `interactive`) and nothing else. Add a comment saying exactly this, so the
  next reader knows the file is deliberately near-empty rather than incomplete.
- spawn `node <cadre-cli bin> start -c <config>` with stdout/stderr appended to
  `<volume>/node.log` via an inherited fd (same pattern as
  `host-process-orchestrator.ts:481-508`), and expose the log through `getLogs`
  so a failing test can print why the node never came up;
- return the real `OrchestratorCreateResult`: `healthEndpoint`,
  `metricsEndpoint`, `seedEndpoint` (`http://127.0.0.1:<health>/seed`),
  `seedToken`, `p2pPort`.

`getStats` may return zeros — `ContainerService` never calls it on this path.

**Do not reimplement the env assembly inline in the scenario file.** The
orchestrator is the single place the provider's environment meets a real child;
a second copy in the test defeats the ticket.

## Steps to assert

1. **Owner authority up.** `OwnerNodeClient.getPeerId()` matches the identity
   written to disk; `getMultiaddrs()` yields at least one dialable address
   (suffix `/p2p/<peerId>` as `withPeerId` in the donation scenario does).

2. **Provider provisions node A with the owner's key pinned.**
   `ContainerService.createContainer({ customerId, partyId: P, bootstrapNodes,
   profile: 'storage', pinnedOwnerKeys: [ownerKey] })`, then poll the store until
   the record reaches `running` (this exercises the real `waitForEnrollment`
   `/status` loop). Assert `seedToken` and `seedEndpoint` are persisted and the
   endpoint is the health port's `/seed`.

3. **The node accepts the owner's seed.** `getPeerInfo(id)` (live `/status`) →
   real peerId + multiaddrs. Feed those to `ownerClient.addDrone(...)`, then
   `containerService.applySeed(id, encodedSeed)`. Poll (the seed route can race
   node readiness) until `success === true`; assert `peersAdded >= 1`.
   **This is the assertion the whole ticket exists for.**

4. **A node pinned to a different owner refuses the same seed.** Provision node
   B with `pinnedOwnerKeys: [<a freshly generated, well-formed ed25519 owner
   key>]` — not the authority's. Deliver the *same* `encodedSeed` from step 3.
   Assert `success === false`, `peersAdded` is absent/0, and the error mentions
   the pinned-key policy (the node's reason string is
   `Signer key is neither an anchored nor a pinned owner (pinned-key trust
   policy)`; match loosely — `/not .*(anchored|pinned)/i` — so a reworded reason
   fails the *message*, not the test). Delivery is authorised (correct bearer
   token) and still refused: that is what proves the trust check is real rather
   than absent. Do **not** poll-until-success here; a single call, and give the
   node the same readiness wait node A got before asserting refusal, so a
   not-yet-ready node cannot masquerade as a trust refusal — assert node B is
   `running` in the store first.

5. **Restart with no pin still accepts a second seed from the same owner.**
   Stop node A's child (`stopContainer`), re-create it under the **same
   container id and same volume dir** but with `pinnedOwnerKeys` omitted, and
   deliver a second freshly-minted seed. Assert accepted. This is what proves
   the first accepted seed anchored the owner key on the durable volume
   (`trusted-owners.<party>.json` in the volume dir — assert the file's `owners`
   map contains the owner key, mirroring
   `cadre-host-node-donation.integration.ts:275-304`). If the harness
   orchestrator's `removeContainer` deletes the volume, add a `keepVolume`
   option — `DockerOrchestrator` re-attaches an existing volume on recreate
   (`ensureVolume` returns "not ours"), so re-attaching is the faithful
   behaviour.

## Edge cases & interactions

- **Boundary: no pin at all.** A container created with `pinnedOwnerKeys: []`
  gets no `CADRE_OWNER_KEYS` var and must refuse. Cheap to add as a variant of
  step 4 if node B is parameterised; if it costs a third child process, skip it
  and say so in the handoff — step 4 already proves the check discriminates.
- **Token gate vs trust gate are independent.** Add one assertion that a POST to
  `seedEndpoint` with a *wrong* bearer returns 401 while the correct bearer with
  an untrusted signer returns a 400-with-reason. Two different refusals, two
  different causes — a single "it failed" assertion cannot tell them apart, and
  conflating them is precisely how a broken pin hides behind a working token.
- **Node not yet listening.** The `/seed` route only exists once the health
  server is up; `applySeed` against a still-starting node yields a fetch error,
  not a trust refusal. Every negative assertion must be gated on the node
  having reached `running` first (see step 4).
- **Windows workdir release.** `rmSync` on a tmp root whose child just exited
  can fail; copy the donation scenario's `{ recursive: true, force: true,
  maxRetries: 10, retryDelay: 200 }` + swallowed catch.
- **Port collisions across suites.** `fileParallelism: false` is set, but pick a
  private band distinct from the ones already claimed
  (19600–19899 owner-node, 19900–20039 requester, 20040–20199 host) or use
  OS-assigned ports and read them back.
- **Leaked children.** Every spawned child must die in `afterAll` even when an
  early step throws — iterate the orchestrator's handles, `stopContainer` each,
  and never let a teardown failure mask the test failure.
- **Stale build.** The suite's `global-setup.ts` guards dist-vs-src staleness;
  this scenario needs `cadre-core`, `cadre-cli`, `cadre-host` **and now
  `cadre-provider`** built. Confirm the guard covers cadre-provider; if not,
  that is a one-line addition, not a new ticket.
- **Cost.** Three real cadre-cli children (authority, node A, node B) plus a
  restart. Expect minutes, not seconds. If wall-clock approaches the runner's
  10-minute idle window, drop step 5's restart to a follow-up rather than
  letting the suite become un-runnable — and say so in the handoff.

## Explicitly not in scope

- Spawning a real Docker container. A real child process with the
  provider-built environment gets nearly all the value at a fraction of the CI
  cost; the Docker image's own `entrypoint.sh` remains unexercised, and that
  residual gap belongs in the handoff, not in this ticket.
- Provider-side unit coverage (env injection, create-request validation) — it
  already exists and is fine.

### Verified facts (save re-discovery)

- **Stale-build guard already covers cadre-provider.** `packages/integration-tests/test/global-setup.ts:32`
  lists `@serfab/cadre-provider` in `TARGETS`. No guard change needed — that
  TODO item is done by inspection.
- **Identity materialisation:** `cadre enroll create` writes a **hex** private
  key to `<output>/<name>.key` plus `<name>.id` (`packages/cadre-cli/src/commands/enroll.ts:34-39`)
  — not protobuf. `CADRE_KEY_FILE` maps to `identity.keyFile`, and the loader's
  `decodePrivateKey(loadPrivateKey(...))` handles hex (`packages/cadre-cli/src/config/loader.ts:174-209`).
  So spawning `node <bin> enroll create --output <volume> --name cadre-peer`
  exactly reproduces `entrypoint.sh`'s `create_identity`.
- **Port env vars are read straight from `process.env`, not ENV_MAPPINGS:**
  `start.ts:225-231` does `process.env.CADRE_HEALTH_PORT ?? options.healthPort`
  (same for metrics and `CADRE_SEED_TOKEN`). So do NOT pass `--health-port`
  flags (Docker path passes none); instead pass the allocated host ports as the
  `ports` argument to `buildNodeEnv({ request, seedToken, ports })` so
  `CADRE_HEALTH_PORT` / `CADRE_METRICS_PORT` / `CADRE_LISTEN_ADDRS` carry them.
- **Minimal config file:** `ENV_MAPPINGS` (`packages/cadre-cli/src/config/types.ts:100-116`)
  has no entry for `strandWatchInterval` or `hibernation.defaultLatencyHint` —
  confirmed those two must live in the file. `CliConfigFile.hibernation`
  requires `enabled: boolean`, so write
  `{ strandWatchInterval: 5000, hibernation: { enabled: true, defaultLatencyHint: 'interactive' } }`
  (env `CADRE_HIBERNATION_ENABLED=true` from the image ENV block overrides
  `enabled` anyway). `controlNetwork`/`profile`/`storage` can be omitted
  entirely — `applyEnvironmentOverrides`'s `setNestedValue` creates the nested
  paths (`loader.ts:45-60,152-162`). Name it `cadre.json` (loader switches on
  extension, `.json` parses as JSON — `loader.ts:26-39`).
- **Env assembly precedence** as the ticket specifies; concrete values:
  scrub = `host-process-orchestrator.ts:57-76` (`scrubbedParentEnv`); image ENV
  block = `packages/cadre-cli/docker/Dockerfile:117-124` (`DATA_DIR`,
  `CADRE_PROFILE=storage`, `CADRE_STORAGE_TYPE=file`,
  `CADRE_STORAGE_PATH=<volume>/storage`, `CADRE_LISTEN_ADDRS=/ip4/0.0.0.0/tcp/4001`,
  `CADRE_HEALTH_PORT=8080`, `CADRE_METRICS_PORT=9090`,
  `CADRE_HIBERNATION_ENABLED=true`); entrypoint exports
  `CADRE_KEY_FILE=<volume>/cadre-peer.key`, `CADRE_NODE_STATE_DIR=<volume>`
  (`entrypoint.sh:19-22`); then `buildNodeEnv` output last
  (`container-env.ts:42-74` — `KEY=value` strings; split on first `=`).
- **Seed-route semantics confirmed** (`packages/cadre-cli/src/server/health.ts:286-366`):
  wrong bearer → HTTP **401** body `{"success":false,"error":"unauthorized"}`;
  correct bearer + untrusted signer → HTTP **400** with the applySeed result
  JSON. `ContainerService.applySeed` wraps any non-OK response as
  `{ success:false, error: 'Seed endpoint returned 400: <raw body text>' }`
  (`container-service.ts:350-353`) — assert against that wrapped string.
- **The ticket's suggested refusal regex is WRONG.** The real reason string is
  `'Signer key is neither an anchored nor a pinned owner (pinned-key trust policy)'`
  (`packages/cadre-core/src/seed-trust-policy.ts:113`). It contains "neither",
  not "not", so `/not .*(anchored|pinned)/i` never matches. Use
  `/(neither|not).*(anchored|pinned)/i`.
- **Node B's foreign pin must be well-formed or node B never starts:**
  `validatePinnedOwnerKeys` runs `requireEd25519PublicKeyB64` at startup
  (`start.ts:63-65,119`). Generate it with
  `ed25519KeyPairFromLibp2p(await generateKeyPair('Ed25519')).publicKeyB64` —
  same helper the donation scenario uses for the real owner key
  (`cadre-host-node-donation.integration.ts:125`).
- **Step 5 cannot go through `ContainerService.createContainer`:** it always
  mints a fresh `ctr_<nanoid>` id (`container-service.ts:77-79`), so "same
  container id" is impossible via the service. Recommended shape: use
  `stopContainer` only (NOT `terminateContainer` — that would set the store
  record to `stopped`, and `applySeed` requires `running`/`enrolling`), call
  the harness orchestrator's `createContainer` directly with the same
  `containerId` (volume dir keyed by containerId → reused), then patch node A's
  store record via `store.saveContainer` with the fresh
  `seedEndpoint`/`seedToken`/`healthEndpoint` from the new
  `OrchestratorCreateResult` — mirroring "re-provision from the record" — poll
  `/status` healthy, then deliver via the real `containerService.applySeed`.
- **No `keepVolume` option needed:** Docker's `removeContainer` does not delete
  a named volume, so the faithful harness behaviour is that `removeContainer`
  never deletes the volume dir; the suite's tmpRoot `rmSync` in `afterAll`
  cleans up. Document this on the orchestrator.
- **Enrollment timeout risk:** `provisionContainer` hard-codes
  `waitForEnrollment(id, 60000)` polling every 2s (`container-service.ts:177,204-233`);
  on timeout it only logs — the record stays `enrolling` forever (nothing
  re-polls). A cold real node normally beats 60s but the donation suite budgets
  90s. `applySeed` accepts `enrolling` too, but step 2 asserts `running`. If
  this flakes, the fix is in ContainerService (configurable timeout), not the
  test — flag it in the handoff rather than papering over.
- **Dependencies:** integration-tests lacks BOTH `@serfab/cadre-provider` AND
  `@serfab/cadre-cli`. The donation scenario resolves the cli bin through
  cadre-host's own dependency; the new harness resolves from integration-tests
  (`createRequire(import.meta.url).resolve('@serfab/cadre-cli/bin/cadre.js')`,
  pattern at `host-process-orchestrator.ts:883-895`) — and cadre-provider does
  not depend on cadre-cli — so add **both** as `workspace:*` deps.
- **Spawn/log pattern:** open `<volume>/node.log` with `openSync(path, 'a')`,
  `stdio: ['ignore', fd, fd]`, `closeSync(fd)` after spawn, spawn
  `process.execPath` (`host-process-orchestrator.ts:483-516`). The harness
  child need not be `detached`/`unref` (no restart-survival requirement) —
  keeping the `ChildProcess` handle makes `stopContainer`'s exit-wait simpler.
  `getStats` may return zeros (never called on this path); `isRunning` can
  check `child.exitCode === null`.
- **Port bands:** 19600–19899, 19900–20039, 20040–20199 are claimed by other
  scenarios. Use e.g. authority orchestrator 20200–20339 and harness nodes
  20340–20499, or OS-assigned (bind 0, read back).
- **Owner-authority machinery to copy verbatim:**
  `cadre-host-node-donation.integration.ts:116-163` (writeIdentity,
  `HostProcessOrchestrator` + `ensureOwnerNode` + `OwnerNodeClient`,
