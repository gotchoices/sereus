# Operator command for strand removal

Depends on `CadreNode.unpublishStrand` from `feat-strand-removal-node-api`. Assume it landed
exactly as that ticket specifies: owner-signed, party-wide, no-op when the row is absent,
converges the local node before it resolves.

## Decisions already made — implement these, do not re-open

**The CLI is the operator surface for this pass.** The owner key lives inside the cadre node,
and the one-shot `withConnectedNode` session is the established path for every owner-signed
control write (`cadre validation-key add|remove`, `cadre enroll`). A cadre-host UI that
prompts an owner is parked in `backlog/feat-cadre-host-strand-removal-ui` and is not this
ticket.

**Shape: turn `strands` into a `strand` command group with `list` and `remove`.** The existing
`strandsCommand` (`packages/cadre-cli/src/commands/strands.ts`) is a single-action "list active
strands" command. Restructure it exactly like `validation-key.ts`: a parent `strand` command
with `list` and `remove` subcommands, each carrying the shared `-c/--config`, `--json`,
`-d/--debug` options via a local `withCommonOptions`, and each running through a
`runSubcommand`-style wrapper. Keep `.alias('strands')` on the parent so the documented name
still resolves — that is an alias, not a compatibility shim, and costs one line. `list` keeps
its current output verbatim (`printStrand` / `formatStrandJson` move across unchanged).

**Closed-strand removal requires `--yes`.** Not an interactive prompt: these commands run
non-interactively in scripts and under agents, and a prompt that reads EOF would either hang or
silently proceed. `remove` reads the row first, and if `Type === 'c'` and `--yes` was not
given, it refuses with a non-zero exit and a message naming the exact consequence. `--yes` is
not required for an open strand.

## Command

```
cadre strand list                       # unchanged behaviour, was `cadre strands`
cadre strand remove <strandId> [--yes]
```

`remove`, in order:

1. Read the row: `node.getControlDatabase()?.queryStrand(strandId)` (`control-database.ts:395`)
   — returns the row or null.
2. Decide, in a **pure exported function** (`planRemove(row, { yes })` — mirror
   `validation-key.ts`'s `planAdd`/`planRemove`/`ValidationKeyPlan` triple of
   `{ write, json, human, warnings }`), so the decision is testable without standing a node up:
   - row absent → no write, `• Strand not published — nothing to do: <id>`.
   - `Type === 'c'` and no `--yes` → **refuse** (exit 1), naming the consequence: the row
     carries this party's membership key for that closed network, it is stored nowhere else,
     and removing it means the party can never admit another member to that strand. Tell the
     operator to re-run with `--yes` if that is intended.
   - otherwise → write.
3. `await node.unpublishStrand(strandId)` when the plan says to write.
4. Report via a `reportPlan`-style helper: `--json` prints the machine-readable outcome,
   otherwise the human line plus warnings on stderr.

Warnings the human path must print on a successful removal:

- Removal is party-wide: every cadre node in this party stops running the strand. Other
  *parties* in that strand are unaffected — this removes our participation only.
- A removal that commits while this node has no control connections is local-only and may not
  reach siblings when they come back (see "Delete-while-alone durability" in
  `docs/architecture.md`). Do not promise durability the layer beneath does not deliver.
- For a closed strand: the membership key is gone and unrecoverable.

## Edge cases & interactions

- **`--json` must not lose the refusal.** A closed strand without `--yes` under `--json` must
  still exit non-zero and emit a structured refusal, not a bare stack trace.
- **Absent row is success, not failure** — exit 0, "nothing to do". Matches
  `validation-key remove`'s not-enrolled path.
- **Read-then-write is not atomic.** A concurrent removal between the read and
  `unpublishStrand` makes the write a silent no-op — harmless, because the outcome the operator
  wanted is the outcome they get. Record it as a `NOTE:` at the site, the way
  `validation-key.ts:116-124` does for `applyAdd`; do not widen the window trying to close it.
- **Blank / whitespace id** — commander requires the argument; the node layer refuses blank.
  Assert the CLI does not turn it into a confusing node error.
- **Not an owner / node not started** — surfaces as the node's own error text through the
  existing catch; assert the failure prefix names the operation (`Failed to remove strand`).
- **`strands` alias** — assert `cadre strands` still lists, so the rename does not silently
  break the documented invocation.
- **`process.exit` does not flush a pipe.** Same repo-wide pattern already noted on
  `validation-key.ts:157-161`; do not re-file it, just keep output small.

## Tests

New `packages/cadre-cli/test/strand.spec.ts`, modelled on
`packages/cadre-cli/test/validation-key.spec.ts` (a narrow store interface + a fake node, no
real network):

- `planRemove` — absent row; open strand without `--yes`; closed strand without `--yes`
  (refuses, no write); closed strand with `--yes` (writes, warns); open strand (writes).
- `applyRemove` calls `unpublishStrand` only when the plan says to write.
- Commander wiring: `strand list` / `strand remove` exist, `remove` requires the argument,
  `--yes` parses, the shared options carry the `cadre.yaml` default, and `strands` still
  resolves to the group.
