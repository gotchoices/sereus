## Context

`Orchestrator` (`packages/cadre-provider/src/service/orchestrator.ts`) currently has two implementations — `DockerOrchestrator` (real) and `MockOrchestrator` (tests). Self-hosted basement-PC deployments need a third, **`HostProcessOrchestrator`**, which spawns each cadre node as a plain Node child process on the host. Docker on Windows is heavyweight and licensed; on desktop Linux it's a setup hurdle; for the self-host persona it's not acceptable as a prerequisite.

The implementation is general-purpose — any bare-metal `cadre-provider` operator who doesn't want Docker can pick it — but its primary consumer is `cadre-host`.

## Architecture

```
packages/cadre-host/src/orchestrator/
├── index.ts                     # barrel
├── types.ts                     # HostProcessConfig
├── host-process-orchestrator.ts # the Orchestrator implementation
├── port-allocator.ts            # range-based port tracker
├── log-rotator.ts               # size-based rotating WriteStream
├── pid-liveness.ts              # cross-platform `is the pid alive?`
└── state-store.ts               # persists per-container handle records
```

### Component responsibilities

**`HostProcessOrchestrator`** — implements `Orchestrator`. Holds the in-memory map `containerId → { child?: ChildProcess, pid: number, startupToken: string, ports, workdir, logRotator }`, plus the persisted `StateStore` it mirrors. Constructor takes a `HostProcessConfig` (root dir, port range, defaults, spawn options).

**`PortAllocator`** — same shape as the one inside `DockerOrchestrator`, but exported as its own module so we can persist + restore allocations. Range is configurable, default `10000–20000`. Allocations survive orchestrator restart via the `StateStore` rehydrating the used-set.

**`LogRotator`** — wraps `fs.createWriteStream` for `<workdir>/node.log`. Tracks bytes written; on threshold, renames `node.log → node.log.1`, shifts older files (`.1 → .2`, …, drops `.5`), opens a fresh stream. Defaults: 10 MB per file, 5 rotated files.

**`pid-liveness`** — single function `isPidAlive(pid: number): boolean` using `process.kill(pid, 0)`. Returns `true` on success or on `EPERM` (process exists, owned by another user / different security context — Windows hits this often). Returns `false` on `ESRCH` (or any other error). Pure stdlib, no native deps.

**`StateStore`** — JSON file at `<root>/state.json`, atomically written via temp-file rename. Schema:
```ts
interface PersistedHandle {
  containerId: string;       // provider-assigned ID, passed in createContainer
  dockerId: string;          // the opaque handle we return (see "Identity" below)
  pid: number;
  startupToken: string;
  workdir: string;
  ports: { health: number; metrics: number; p2p: number };
  spawnedAt: string;         // ISO timestamp
  partyId: string;           // for diagnostics / restart recreation
  profile: 'storage' | 'transaction';
}
interface PersistedState { handles: PersistedHandle[]; }
```

### Identity and the `dockerId` field

**Decision: keep the field name `dockerId` (Option B from the plan).** The rename to `orchestratorHandle` would sprawl into `Container.dockerId` in `cadre-provider/src/types.ts`, every container-service callsite, every API/response shape, every test, and the file-backed store schema. That's a separate refactor — not blocking host-process work. For host-process mode, the value is the opaque token `<pid>:<startupToken>` (colon-separated; tokens are hex from `crypto.randomBytes(16)` so they have no colons). `HostProcessOrchestrator` parses this back out internally; callers treat it as opaque, exactly like Docker's container hash.

The token is necessary to detect PID reuse: if the OS recycles the PID and hands it to a different process, `isRunning` must return false. Verification is by file: the child writes `<workdir>/.startup-token` containing the token early in startup; `isRunning(dockerId)` confirms `(pid alive) && (file contains expected token)`.

### Child process entrypoint

The child is `@serfab/cadre-cli`'s `cadre start` command, invoked as:
```
node <cadre-cli-bin> start -c <workdir>/cadre.json --health-port H --metrics-port M --startup-token-file <workdir>/.startup-token
```

We add **a tiny option to `cadre-cli`'s `start` command**: `--startup-token-file <path>`. When set, the child reads `process.env.CADRE_STARTUP_TOKEN` and writes that string to the file after `node.start()` resolves. This is the only change to cadre-cli — about ten lines, gated entirely on the flag, with no impact on other callers.

Locating the bin from cadre-host:
```ts
const cliBin = require.resolve('@serfab/cadre-cli/dist/bin/cadre.js');
```
(Works at runtime even though cadre-host is an ESM package — `createRequire(import.meta.url)` to obtain `require`.)

The `cadre.json` written into the workdir is a minimal `ResolvedConfig` (the YAML/JSON config cadre-cli already accepts; see `packages/cadre-cli/src/config/index.ts` for the shape). The orchestrator populates `controlNetwork.partyId`, `controlNetwork.bootstrapNodes`, `profile`, `strandFilter`, `storage.path` (set to `<workdir>/storage`), and any other fields derived from the `OrchestratorCreateRequest`.

### Spawning and detachment

```ts
const child = spawn(process.execPath, [cliBin, 'start', '-c', configPath,
                                       '--health-port', String(ports.health),
                                       '--metrics-port', String(ports.metrics),
                                       '--startup-token-file', tokenPath], {
  cwd: workdir,
  detached: true,
  stdio: ['ignore', 'pipe', 'pipe'],
  env: {
    ...process.env,
    CADRE_STARTUP_TOKEN: token,
    CADRE_HEALTH_PORT: String(ports.health),
    CADRE_METRICS_PORT: String(ports.metrics),
    CADRE_LISTEN_ADDRS: `/ip4/0.0.0.0/tcp/${ports.p2p}`,
    NODE_OPTIONS: heapLimitOpt,   // from resources.memoryLimit
  },
});
child.stdout!.pipe(logRotator.writeStream());
child.stderr!.pipe(logRotator.writeStream());
child.unref();
```

`detached: true` + `unref()` lets the child outlive the parent (cadre-host crash). On clean shutdown cadre-host SIGTERMs each child explicitly. On host reboot everything dies together and cadre-host restarts from persisted state.

### Restart recovery

`HostProcessOrchestrator` exposes an `init()` method (not part of the `Orchestrator` interface — called by cadre-host wiring before the orchestrator is handed to `ContainerService`):
1. Read `state.json`.
2. For each handle: probe PID liveness + token file. If both pass, mark "attached" (we have the persisted record but no live `ChildProcess` ref — that's OK; SIGTERM via `process.kill(pid, 'SIGTERM')` works without it).
3. If PID is dead or token mismatches: leave the handle in the state map with an `alive: false` flag. Callers can list "dead handles" via a new `listDeadHandles(): PersistedHandle[]` method and decide whether to recreate.
4. Re-populate `PortAllocator`'s used-set from the surviving handles' ports.

Decision: `init()` does not auto-recreate dead containers. That policy belongs in cadre-host's lifecycle (a follow-up integration ticket) — the orchestrator just reports state. This keeps `Orchestrator` callable code paths predictable.

### Method behaviour summary

| Method | Behaviour |
|---|---|
| `createContainer(req)` | Allocate workdir + ports, write config + log files, mint token, spawn child, persist handle, return `{ dockerId, healthEndpoint, metricsEndpoint, p2pPort }`. |
| `stopContainer(dockerId)` | SIGTERM via `process.kill(pid, 'SIGTERM')`; wait up to `stopTimeoutMs` (default 10 000) polling `isPidAlive`; SIGKILL if still up. Flush + close log rotator. Update persisted record `alive: false`. |
| `removeContainer(dockerId)` | `stopContainer` if still running; release ports; delete workdir; drop from persisted state. |
| `isRunning(dockerId)` | `isPidAlive(pid) && readToken(workdir) === storedToken`. Cheap, no spawn. |
| `getStats(dockerId)` | `pidusage(pid)` → `{ cpuPercent, memoryBytes, networkRxBytes: 0, networkTxBytes: 0 }`. Network stats deferred — documented v1 gap. |
| `getLogs(dockerId, tail = 100)` | Read tail of the active `<workdir>/node.log`. Implementation: line-buffer read from the end. |

### Resource limits (v1)

- **Memory**: `NODE_OPTIONS=--max-old-space-size=<MB>` derived from `resources.memoryLimit` (parsed by the same `parseMemoryLimit` helper Docker uses — copy into a shared utility or duplicate; this ticket duplicates to avoid cross-package coupling). Caps V8 heap, not RSS — adequate v1.
- **CPU**: not capped. Documented gap.

### Configuration

`HostProcessConfig` (in `types.ts`):
```ts
export interface HostProcessConfig {
  /** Root directory under which per-container workdirs live. */
  rootDir: string;
  /** Port allocation range (default 10000..20000). */
  portRange?: { start: number; end: number };
  /** Default resource limits (memory only in v1). */
  defaultResources?: { memoryLimit?: string };
  /** SIGTERM → SIGKILL grace period (default 10000 ms). */
  stopTimeoutMs?: number;
  /** Log rotation: bytes per file (default 10 MB). */
  logMaxBytes?: number;
  /** Log rotation: max rotated files (default 5). */
  logMaxFiles?: number;
}
```

### Tests (`packages/cadre-host/src/__tests__/orchestrator.spec.ts`)

Use a tiny fake child script (small JS file written to a temp dir before spawn, NOT the real cadre-cli) so unit tests stay fast and don't require cadre-cli to be built. Add a separate **integration test** behind `describe.skipIf(!fullBuild)` that spawns the real `cadre-cli` bin if available.

Key cases:
- **createContainer** spawns a child whose PID is alive; returns `healthEndpoint`/`metricsEndpoint`/`p2pPort` derived from allocated ports; persists handle in `state.json`.
- **isRunning** is `true` after spawn, `false` after SIGKILL, `false` when the token file is tampered with even though PID is alive.
- **stopContainer** with a child that ignores SIGTERM → orchestrator escalates to SIGKILL after `stopTimeoutMs` and the child is gone.
- **stopContainer** with a child that exits on SIGTERM → no SIGKILL needed; `isRunning` flips to `false` within timeout.
- **removeContainer** deletes workdir, releases ports, removes persisted record. Subsequent `getStats` rejects with a "not found" error.
- **getStats** returns plausible numbers (cpuPercent ≥ 0, memoryBytes > 0); networkRx/Tx are exactly 0.
- **getLogs** returns child stdout content after the child has written N lines.
- **Log rotation**: with `logMaxBytes: 256`, a chatty child causes rotation; assert `node.log.1` exists and total files ≤ `logMaxFiles + 1`.
- **PortAllocator**: allocate sequentially, release, reuse; exhaustion throws.
- **Restart recovery**: spawn two containers, throw away the orchestrator instance, instantiate a new one with the same `rootDir`, call `init()`, assert (a) port allocator has those ports marked used, (b) `isRunning(dockerId)` returns true for both, (c) killing one externally then re-`init()` reports it as a dead handle.
- **Identity**: parsing the returned `dockerId` round-trips `(pid, token)`; two orchestrators with the same persisted state agree on `isRunning`.

For the fake child script template:
```js
// fake-child.js
import fs from 'node:fs';
fs.writeFileSync(process.env.TOKEN_FILE, process.env.CADRE_STARTUP_TOKEN);
let alive = true;
process.on('SIGTERM', () => { if (process.env.IGNORE_SIGTERM !== '1') { alive = false; process.exit(0); } });
setInterval(() => { if (alive) console.log('tick'); }, 50);
```
The orchestrator under test gets `cliBin` overridden to point at this script (constructor-injected via `HostProcessConfig.spawn?.entrypoint?: string` — add this hidden hook for tests).
