# The phone kit moves the app's strands when it joins another cadre

`PhoneNode.joinCadre` already switches the app's one node from the cadre it founded (party B) to the invitation's cadre (party A) and keeps B as `formerPartyId`. This ticket makes the join carry B's strands: it exports them from B's node before the switch, keeps the bundle in the secure store, and adopts it in A once the app's owner key is wired there. `strand-bundle-export-and-adopt` provides `exportStrandBundle` and `adoptStrandBundle`.

## When the move runs

**Export, before anything stops.** In `switchParty`, when the party being left was founded by this app (`leaving.origin !== 'joined'`, the same test `formerPartyAfterJoining` makes), call `exportStrandBundle` on the running node and write the move record (below) before `shutDown()`. Two refusals happen here, before any switch, so a refused join leaves B running and unchanged:

- The bundle has strands, pending joins or invitations and the invitation does not grant owner (`invitation.invite.grantsOwner` false): throw `StrandsNeedOwnerJoinError` naming how many strands would be left behind. Only an owner can seat rows in A, and a plain member's join would orphan B's strands in a cadre the app no longer runs.
- The export or the record write fails: throw it. Switching without the record would lose the strands.

An empty bundle (the app founded B and created nothing) writes no record and the join proceeds as today, owner or not.

**Adopt, after the owner key is wired.** In `startAndRedeem`, when `wireJoinedOwnerKey` returns `'enrolled'` and a move record names this party, adopt it (below) before `markRunning`, so the start is saved with the strands already seated. When the key is not wired (`'member'` or `'timed-out'`), leave the record; the join still succeeds, and the report says the move is deferred.

**Finish on a later start.** In `buildAndStart`, after `settleOwnerKey` returns `'enrolled'` and before `markRunning`, adopt any record that names this party. This is the resume path for an app killed between admission and adoption, and for a `'timed-out'` wiring that succeeds on the next launch. It is origin-agnostic: it keys on the record's target party, not on `origin`.

**Rollback discards the record.** `returnToLeftParty` deletes a record written by the failed join, so a refused or cancelled join leaves no record behind and the next join exports afresh. A record is never adopted into a party other than the one it names.

## The move record

One secure-store slot, through the kit's `SecureStoreKeyStore` (the bundle carries read secrets, party keys and bearer invitations, the same material the joined-strand records keep there): id `cadre/strand-move/<base64url source party id>`, holding JSON `{ v: 1, targetPartyId, bundle, refused: Array<{ strandId, reason }> }`. One record per source party; a second join from the same B overwrites it, which is right because the newer export is the fuller one. `refused` accumulates permanent refusals from earlier adoption attempts so a retry does not repeat them, and the record is deleted once an adoption reports nothing under `failed`. A record that does not parse is deleted with a warning: the strands are still in B's storage, and `dissolve-empty-cadre` will refuse to dissolve a B it cannot prove moved, so nothing is silently lost.

## Adopting

`adoptPendingMove(node, partyId)` in `strand-move.ts`: read the record for `formerPartyId` of the resolved options (and, to be origin-agnostic, scan the key store's `cadre/strand-move/` ids for any record whose `targetPartyId` is this party); call `adoptStrandBundle`; merge its `refused` into the record; delete the record when `failed` is empty, otherwise save the updated record; return the report. Errors from the adoption (a typed not-an-owner refusal, a control write that threw) are logged and reported, never thrown out of a start: the node is up, and the move is retried on the next start or by `finishStrandMove`.

## API

- `JoinCadreResult.strandMove?: StrandMoveOutcome` where `StrandMoveOutcome = { state: 'done' | 'partial'; report: StrandMoveReport } | { state: 'deferred'; reason: 'owner-key-not-wired' }`. Absent when nothing was exported.
- `PhoneNode.pendingStrandMove(): Promise<{ fromPartyId: string; strandIds: string[] } | undefined>`, what a record still waiting holds, for a screen that shows "strands still to move".
- `PhoneNode.finishStrandMove(): Promise<StrandMoveReport | undefined>`, a manual retry on the running node, in the transition queue; `undefined` when no record names the running party.
- `PhoneNodeStatus` is unchanged; a running status with a record pending is read through `pendingStrandMove`.
- A new `onStrandMove(listener: (outcome: StrandMoveOutcome) => void)` is not added: the result and the two methods are enough for the screens ticket, and a status field would duplicate them.

## Tests

In `packages/cadre-rn/test/phone-node/node.spec.ts`, with the existing in-process harness (`device()`, `expiredInvitation()`):

- **A join that cannot carry the strands is refused before anything changes**: the device founds B and `foundStrand`s one open strand; `joinCadre` with a well-formed invitation whose `grantsOwner` is false rejects with `StrandsNeedOwnerJoinError`; afterwards `status` is still `running` on the same `CadreNode` instance (no stop happened), and the key store holds no `cadre/strand-move/` slot.
- **A failed join leaves no move record**: same device, an owner-granting expired invitation (refused by the device's clock); `joinCadre` rejects with `CadreInviteRejectedError`; afterwards B runs again and the key store holds no `cadre/strand-move/` slot. This pins the rollback contract.

The admitted path (export, switch, adopt) is covered at the cadre-core layer by `scenario-strand-moves-between-cadres` and is not unit-tested here; the kit's part of it is sequencing, checked by inspection.

## Edge cases & interactions

- **Killed between admission and adoption**: the start is saved only after adoption (`markRunning` runs last), so the relaunch comes up in A with `origin: 'joined'`, wires the key and adopts from the record. By inspection; the record's `targetPartyId` makes the scan exact.
- **Killed between export and admission**: nothing saved for A, so the relaunch starts B; the stale record is overwritten by the next join from B and never adopted anywhere else. By inspection.
- **Owner grant arrives late** (`'timed-out'` wiring): the join succeeds with `deferred`, the next start adopts. By inspection.
- **Admitted as a member only** despite the invitation granting owner (the grant row did not land): `deferred` forever until an owner adds the key; `pendingStrandMove` keeps reporting it. By inspection.
- **A joined app joins again** (A to C): `leaving.origin === 'joined'`, nothing is exported; A's strands are A's owners' to move. By inspection, matching `formerPartyAfterJoining`.
- **`stop()` during the adoption**: the adoption runs inside the join's transition, so the stop queues behind it; the record is deleted or saved before the stop runs. By inspection.
- **A strand refused permanently** (A already participates in it under its own identity): kept in the record's `refused`, never retried, reported each time. By inspection.
- **Secure store refuses a read while scanning records at start**: `KeyStoreAccessError` fails the start, as it does for the identity slot; never read as "no record". By inspection.
- **Dissolving B** reads "moved" as "no record for B in the key store and the saved start's `formerPartyId` is B" (noted in `dissolve-empty-cadre`).
