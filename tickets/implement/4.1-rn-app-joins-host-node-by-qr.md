# Phone app: add your home machine's node by scanning its code

## Where things stand

cadre-host no longer lends nodes through grant tokens. Its one action is "Join a cadre": it starts a node that is waiting to be claimed and shows a code, as a QR code and as text, of the form `sereus-join:1.<base64url JSON of { multiaddrs, peerId, secret }>` (docs/cadre-host.md → "Join by QR code"; encoder and decoder in `packages/cadre-core/src/node-claim-payload.ts`). The owner's phone decodes it and calls `CadreNode.claimNode({ peerId, multiaddrs, secret })`, which dials the node, sends it a seed with a proof that the sender holds the secret, and on acceptance writes the node's `CadrePeer` row and keeps its addresses as a dial target. The node then records the claim, restarts itself once under the claimed cadre, and from then on the phone's reconcile passes reconnect to it.

The phone app still ships the old **Settings → Host Node** section (`app/settings.tsx` near line 416) driving `src/host-node-request.ts`, an HTTP client for the deleted `/grants` routes. This ticket replaces both.

After the prereq `claim-delivery-dials-each-address-in-turn`, `claimNode` dials the code's addresses one at a time in the order given (public addresses first, then LAN, which is how cadre-host orders them), each on its own time limit, and fails in one of three ways the app can tell apart:

- `ClaimRefusedError` (exported from `@serfab/cadre-core`): the node was reached and said no. `code` is one of `already-claimed`, `claim-proof-invalid`, `claim-rate-limited`, `claim-not-persisted` (`SeedRefusalCode` in `cadre-core/src/types.ts`), or absent.
- `PeerUnreachableError`: no address connected; nothing was sent.
- Anything else: the node was reached and the exchange, or a local step, failed. Claiming again with the same code is safe: the node accepts a repeat from the same owner key, the row insert is a no-op on an existing row, the dial target is replaced.

## What to build

### `src/node-claim.ts` (replaces `src/host-node-request.ts`)

Pure functions, no React, no native imports, so `test/node-claim.spec.ts` runs them in Node. It may import from `@serfab/cadre-core` (decoder, error classes) and `@libp2p/utils`.

- `readNodeCode(text)`: trims, then decodes with `decodeNodeClaimPayload`. Returns the payload, or a failure with a plain message and the decoder's own message as detail. Three branches: text that does not start with `sereus-join:` ("That is not a node code from cadre-host. It starts with sereus-join:."); text that starts with `sereus-join:` but not `sereus-join:1.` ("This code comes from a newer cadre-host than this app understands. Update the app."); a `sereus-join:1.` code the decoder refuses ("This node code is damaged or incomplete. Scan it again, or copy the whole text.").
- `nodeReach(multiaddrs)`: `'anywhere'` when at least one address names a public IP or a DNS name, else `'home-network'`. Classify each address's host component from `multiaddr(a).getComponents()` with `isPrivateIp` from `@libp2p/utils` (add `@libp2p/utils` to the app's `dependencies` at the version already installed under `packages/reference-app-rn/node_modules/@libp2p/utils`, 7.4.1 today). Confirm `isPrivateIp` counts loopback, link-local and `100.64.0.0/10` (shared address space, which Tailscale uses) as private; if it does not, treat those as home-network too and say so in a comment. No hand-written IP parsing.
- `describeClaimFailure(error, payload)`: returns `{ message, detail?, canRetrySameCode }`. `detail` is the underlying error's message, for bug reports.

| failure | message (plain language; adjust wording, keep the content) | same code again? |
|---|---|---|
| `PeerUnreachableError`, reach `home-network` | The node can only be reached on the machine's home network so far, and this phone could not reach it. Connect to the same Wi-Fi as the machine and try again. To reach it from anywhere, see Reachability on the machine's Join page. | yes |
| `PeerUnreachableError`, reach `anywhere` | This phone could not reach the node at any of its addresses. Check that the machine is on and online. On the same Wi-Fi, also check that the machine's firewall allows incoming connections. | yes |
| refused `already-claimed` | This node already belongs to another cadre. On the machine, Reset the node to get a new code, and scan that. | no |
| refused `claim-proof-invalid` | The node did not accept this code. Scan the code the machine shows now; it changes when the node is reset. | no |
| refused `claim-rate-limited` | The node is refusing claims for a while after several wrong codes. Wait a minute, then try again. | yes |
| refused `claim-not-persisted` | The node could not save its new owner. Check the machine's disk space, then try again. | yes |
| refused, no code | The node refused to join this cadre. (`reason` as detail) | no |
| anything else | Adding the node did not finish. Trying again with the same code is safe. | yes |

- `ownerFingerprint(publicKeyB64)`: the first 8 characters, the same form cadre-host shows as "owner" for a claimed node (`packages/cadre-host/ui/src/lib/hosted-nodes.ts` → `ownerFingerprint`, and `cadre-host node list`). Check that the key cadre-host records (`claim.json`'s `ownerKey`, which is the claim seed's `signerKey`) is the same base64url string as the phone's `getIdentityOwnerKey().publicKeyB64` / `ownerPublicKey`, so the two fingerprints match; if the encodings differ, convert before slicing and note it.

Never log the code text or the payload object: it carries the secret. Log the peer id only.

### `use-cadre.ts`

Replace `requestHostNode` with `claimHostNode(payload: NodeClaimPayload): Promise<void>`: requires a running node (`'Node not started'` otherwise), a re-entry guard in a ref (two taps must not run two claims), and calls `current.claimNode(payload)`. Delete `HOST_REQUEST_CANCEL_WAIT_MS`, `InFlightHostRequest`, `hostRequestRef` and the cancel-and-wait block in `stop`: a claim leaves nothing to clean up when it fails (no row, no dial target before acceptance; see `claimNode`'s doc comment), so Disconnect during a claim just stops the node and the claim fails. Update `UseCadreResult`'s doc comment.

### Settings → "Add an always-on node" (`src/add-node-section.tsx`, used by `app/settings.tsx`)

`settings.tsx` is 617 lines; put the new section in its own component under `src/` (not `app/`, where every file is a route) and pass it `showAlert`. Shown only while the node is connected; when the device holds no owner key (`ownerPublicKey` is null, e.g. it joined someone else's cadre as a member), the section says only an owner device can add a node and offers nothing else.

- One short explanation: "A machine running cadre-host shows a code when you choose Join a cadre. Scan it, or paste its text."
- **Scan code** opens a full-screen modal with the camera (`src/node-code-scanner.tsx`, below).
- A paste field and **Use code**, the fallback when there is no camera, the code is on the same phone, or the user copied the text.
- A code, from either path, goes through `readNodeCode`. A failure opens the usual alert. A payload opens the **approval prompt**.
- **Approval prompt** (a modal, nothing claimed until the user agrees). It names the cadre the node will join, because an app still in its own one-machine cadre would otherwise add the node there without the user noticing:
  - Cadre: the full Party ID (the same value the Node card shows).
  - Owner: `ownerFingerprint(ownerPublicKey)`, with a line saying the machine shows the same fingerprint once the node joins.
  - Node: the peer id, shortened for display.
  - Reach: `nodeReach` → "Reachable from anywhere" or "Reachable only on the machine's home network: this phone must be on the same Wi-Fi".
  - **Add to this cadre** and **Cancel**.
- **Progress line** while the claim runs: one stage, "Reaching the node and adding it to this cadre…", plus a second line after 20 s: "Some of the node's addresses are not answering; still trying the others." (A dead address costs up to 21.5 s before the next is tried; all dead costs up to about two minutes.)
- **Success:** alert "Node added", body: the node's peer id and "The machine restarts the node once to switch to this cadre; it then connects by itself." Clear the paste field and the kept payload.
- **Failure:** alert with `describeClaimFailure`'s message and detail. When `canRetrySameCode`, keep the payload and show **Try again** in the section (re-runs the claim without a rescan, no second approval since the payload is unchanged), with **Discard** beside it.

Success is "the claim was accepted", not "a connection is open": the node restarts itself right after accepting, which drops the connection the claim used, and the phone's next reconcile pass (within 15 s) reconnects. Waiting for that inside the flow would race the restart. The Settings connection rows already show when it reconnects.

## Edge cases & interactions

- **Phone on cellular, code with only home-network addresses:** the approval prompt already says "only on the machine's home network"; if the user goes ahead, the claim fails with `PeerUnreachableError` and the home-network message. Verified by the spec (the failure mapping) and the device run.
- **Phone at home, router does not loop back to its own public address:** handled by the prereq (each address its own time limit); the progress line's 20-second hint covers the wait. Device run.
- **Node already claimed by another cadre:** `already-claimed` → the definite message telling the user to Reset on the machine; no Try again. Spec.
- **Wrong or stale code** (the node was reset after the code was shown): `claim-proof-invalid`. Spec.
- **Node already claimed by this same owner** (the user scans again after success, or after a lost answer): the node accepts again, `claimNode` resolves, the app reports success. By inspection of `claimNode`'s idempotency.
- **Answer lost after the node accepted** (Wi-Fi drops mid-exchange): "anything else" → Try again with the kept payload; the node accepts the repeat. Important because the host stops showing the code within about 2 s of accepting (its watcher sees `claim: claimed`), so a rescan is no longer possible. Spec for the mapping; inspection for the payload being kept.
- **App killed, or Disconnect, mid-claim:** before the node accepted, nothing happened anywhere; rescan. In the window between the node accepting and the phone writing the row (one local insert), the node belongs to this owner but the phone has no row and the kept payload is gone with the process; the recovery is Reset on the machine and a fresh scan. Leave an accepted-tradeoff `NOTE:` at `claimHostNode` saying so, with the revisit condition: if a device run sees this window hit (slow control writes on React Native), persist the pending code in the app-private `sereus-node-local` store and finish the claim on the next start.
- **Device is a member, not an owner:** section says only an owner can add a node. By inspection.
- **Node not connected:** section hidden or disabled with "Connect first". By inspection.
- **Two taps / scan while a claim runs:** the ref guard in `use-cadre.ts` rejects the second; the button is disabled during the claim. By inspection.
- **Scanner sees an unrelated QR code, or the same code many times per second:** hint and keep scanning; latch on the first node code. By inspection.
- **Camera permission denied or no camera:** message plus settings link; paste still works. Device run.
- **The secret never reaches a log:** no `console.*` of the code text or payload; the decoder never echoes it. By inspection.
