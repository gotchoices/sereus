# Rebuild the provider's port bookkeeping from Docker before handing out ports

## The defect

`DockerOrchestrator` (`packages/cadre-provider/src/service/docker-orchestrator.ts`) gives each tenant container three host ports — health, metrics, p2p, in the order of `CONTAINER_PORT_KEYS` — from a bounded range (`config.portRange`, default 10000–20000). Two pieces of in-memory state track them:

- `portAllocator` (a `PortAllocator` from `port-allocator.ts`) — the set of ports in use; `allocate()` returns the lowest free port in the range.
- `containerPorts` — Docker container id → that container's three ports, read by `removeContainer` to give them back.

Both are created empty in the constructor and nothing fills them except `createContainer`. The containers themselves outlive the provider process (`RestartPolicy: unless-stopped`, records persisted by `FileStore`). So after a provider restart:

- the first `createContainer` is offered the bottom of the range — the very ports the surviving containers are bound to — and Docker refuses the create ("port is already allocated"); the provision fails, the ports are released, and every later create repeats the same collision until enough old containers are gone;
- removing a container created before the restart releases nothing (no `containerPorts` entry). Harmless alone, but it is the same gap.

`repro: static` — read off the code, not run against a daemon. Confirmed by grep that nothing in `packages/cadre-provider/src` calls `markUsed` or `reservePortSet` (the prereq ticket `debt-duplicate-port-allocator-across-orchestrators`, now complete, added both to the provider's `port-allocator.ts` and nothing uses them yet). A real-daemon confirmation: start the provider, create a container, restart the provider, create a second container.

## The fix

Docker is the source of truth; no separate port ledger is persisted. Before the orchestrator hands out or gives back any port for the first time in a process, it lists the containers it created and reserves their ports.

**Finding the containers.** `this.docker.listContainers({ all: true, filters: { label: [CONTAINER_ID_LABEL] } })` — the bare label key matches every container wearing `sereus.container-id`, whatever its value. `all: true` matters: a stopped container keeps its port bindings and gets them back when Docker restarts it (`unless-stopped`, or an operator `docker start`), so its ports are not free.

**Reading their ports.** Not from the list result's `Ports` field — Docker only fills that for running containers. Inspect each one and read `HostConfig.PortBindings[`${CONTAINER_PORTS[key]}/tcp`]?.[0]?.HostPort` for each key in `CONTAINER_PORT_KEYS` (`CONTAINER_PORTS` from `container-env.ts` holds the in-container ports 8080/9090/4001 that `createContainer` publishes against). These are the bindings `createContainer` wrote, so the read is the exact inverse of the write. Parse with `Number(...)`.

A key with no binding (a container from a build that published fewer ports — `feat-provider-drone-reachable-by-phone` in backlog would add one) yields `undefined`, which `markUsed` already ignores; a port outside the configured range (the operator narrowed the range) is ignored the same way. That is correct: such a port cannot be handed out by `allocate()` anyway.

**Recording them.** For each container: `reservePortSet(this.portAllocator, CONTAINER_PORT_KEYS, ports)` and `this.containerPorts.set(info.Id, ports)`. Filling `containerPorts` too means `removeContainer` releases a pre-restart container's ports through the same path as a fresh one. `ContainerHostPorts` is `Record<key, number>`; a partially-bound container makes some values `undefined`. Either widen the map's value type to `Partial<ContainerHostPorts>` and have `reservePortSet`/`releasePortSet` accept a partial set (their doc comments already say a missing key is skipped — `Set.delete(undefined)` and `markUsed(undefined)` are both no-ops), or skip absent keys when building the record. Prefer widening the helpers' parameter to `Partial<Record<K, number>>`: it makes the documented "a key the set lacks is skipped" true in the type, and keeps cadre-host (which imports these helpers from `@serfab/cadre-provider`) compiling unchanged since `Record` is assignable to `Partial<Record>`.

**When it runs.** Lazily, memoized, inside the orchestrator — not a new `Orchestrator`/`RecoverableOrchestrator` method called from `server.ts`. Reasons: `createServer` also accepts an injected orchestrator and `MockOrchestrator`, neither of which needs it; and a lazy gate cannot be forgotten by a future caller. Shape:

- a private `portsRehydrated: Promise<void> | undefined` and a private `ensurePortsRehydrated()` that starts the pass once and returns the same promise to every caller;
- if the pass rejects (daemon unreachable), clear the memo so the next call retries, and let the rejection propagate;
- `createContainer` awaits it **before** `allocatePortSet`. A failed pass fails the create: handing out ports blind is exactly the defect, and the retry happens on the next create;
- `removeContainer` awaits it **before** removing the container, best-effort (catch and `log`, then continue — a removal must not fail over bookkeeping). Awaiting first matters: if the pass were still running when the container was removed, it could record the removed container's ports after the removal released nothing, stranding them until the next restart.

Because every allocation awaits the pass first, no allocation can happen between the list and the reservation, so there is no window for a collision within this process. The pass runs once per process; after it, `createContainer`/`removeContainer` keep the state current as today.

Keep the pass small and decomposed per AGENTS.md: e.g. `rehydratePorts()` (list + loop), and a pure `hostPortsOf(info: Docker.ContainerInspectInfo)` that reads the bindings. An inspect that fails for one listed container (it was removed between list and inspect: 404) should be logged and skipped, not fail the whole pass; any other inspect error rethrows, matching the file's existing stance that a Docker outage must not read as "nothing there".

Update the two comments that currently describe the gap as permanent: the `durableVolumesOf` doc ("`containerPorts` already loses its contents across a provider restart") and the `resolveDockerId` doc ("the map is empty after a provider restart"). After this fix the map is rebuilt, but only once a create or remove triggers the pass — `resolveDockerId` should still ask the daemon directly, so reword rather than delete: the reason becomes "the reap can run before any create/remove has rebuilt the map, and the daemon is authoritative anyway".

## Tests

One reproduction test, in `orchestrator-port-leak.test.ts` (it already owns the port-accounting cases and the `OrchestratorInternal` accessor):

- Fake daemon whose `listContainers` returns one labelled container `old-1` (and records its args), whose `getContainer('old-1').inspect()` returns `HostConfig.PortBindings` holding 10000/10001/10002 on 8080/9090/4001 and `Config.Labels` with `sereus.container-id`, range 10000–10005. `createContainer` must publish 10003–10005 (read from the create options' `PortBindings`, as the loopback test in that file already does). Before the fix it publishes 10000–10002.
- In the same test, or a second `it` only if it reads cleaner: `removeContainer('old-1')` then `portAllocator.has(10000)` is false — the pre-restart container's ports come back.

Do not add tests for the memo/retry wiring or the 404-skip — they are glue.

The other fake dockers that call `createContainer` or `removeContainer` (`docker-orchestrator-volume.test.ts`, `docker-orchestrator-push.test.ts`, `container-env.test.ts` if it constructs an orchestrator, and the rest of `orchestrator-port-leak.test.ts`) have no `listContainers` and will now throw. Add a `listContainers: vi.fn(async () => [])` default to the shared stubs in `fake-docker.ts` (rename or add a sibling to `volumeStubs` if "volume" no longer describes it — its doc comment says it exists so every orchestrator fake agrees on the daemon surface), rather than patching each file. `docker-orchestrator-resolve-id.test.ts` calls neither create nor remove, so it is unaffected; confirm its `toHaveBeenCalledWith` assertion still holds.
