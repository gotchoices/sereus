# Claiming a strand this node already hosts as a storage replica

A **storage replica** is a strand a storage-profile node runs with no sApp config: its libp2p node, raw store and `Strand` membership schema, but no `App` tables. An app on the same machine that claims such a strand (`CadreNode.addStrand`, or `foundStrand`) now upgrades the running replica in place instead of getting it back unchanged: the `App` schema is applied to the live database, and the libp2p node, peer id, connections, store and warm cache all stay.

## What landed (`ticket(implement): claiming-a-hosted-strand-upgrades-in-place`)

- `applyAppSchema(db, schema)` in the plugin: the one site that applies an `App` schema, used by `composeStrand` at bring-up and by `StrandDatabase.attachAppSchema` on a live database.
- `StrandInstanceManager.attachSApp(strandId, sAppConfig, { requireSignedSchemas })` → `'attached' | 'already-attached'`. It waits out any runtime build in flight for the strand (`runtimeBuilds`, filled by `startStrand` and `resumeStrand`). It checks the schema signature before changing anything, then updates the retained launch config, then applies the schema to the live database (published, or held by the first-sync gate), and only then records `sAppInfo` and the latency hint. A quiesced instance gets the config only, and its next resume applies the schema.
- `CadreNode.claimTrackedStrand`: attaches before any founding (the founder bootstrap writes the sApp into `Strand.Header`), and runs both at the first tracked-instance check and at a second check placed right before `startStrand`, which closes the race between a replica launch and a claim of the same strand.
- Docs: a bullet under "Storage replicas" in `docs/architecture.md`; doc comments on `StartStrandConfig.sAppConfig` and `launchStrand`.

## Review findings

Read the implement diff first, then the surrounding code in `strand-instance-manager.ts` (startStrand, resumeStrand, foundExistingStrand, ensureFounderBootstrap), `cadre-node.ts` (addStrand, discovered-strand and replica sApp-id bookkeeping), `strand-database.ts`, and `hibernation-manager.ts`.

**Correctness and races checked, no defect found:**
- Stale-config overwrites: `attachSApp`, `resumeStrand` and `withdrawFounderRequest` each read and replace the retained launch config with no await in between. `foundExistingStrand` awaits (party-key resolve) between its read and its write, but inside `claimTrackedStrand` it always runs after that caller's attach, and a concurrent claimer either finds `sAppInfo` set or has already written its own config first. So no path drops the attached `sAppConfig`.
- The second tracked check before `startStrand`: `timedStep` invokes its op synchronously and `startStrand` checks `instances.has` before its first await, so the "no third launch can slip in" claim holds. A replica launch that loses to a claim takes `claimTrackedStrand` with no config and returns the claimed instance untouched.
- Failed launch while a claim waits on it: I checked by reasoning about the order of queued promise callbacks, then confirmed with a throwaway spec that made the build fail. `startStrand`'s catch deletes the instance before the waiter resumes, so the claim rejects with "not tracked" and never touches the dying record. That spec replaced the manager's own private method, which fails the test bar, so it was deleted. The ordering assumption is now a `NOTE:` on `settleRuntimeBuilds`.
- `StrandDatabase.attachAppSchema` mutates its own config object (constructed fresh per build), not the caller's. A gate-held database founded after attach goes through `ensureFounderBootstrap`'s gate path and is published.
- Claim bookkeeping: `addStrand` removes the strand from `discoveredStrands` and does not remember it as a foreign join (the discovered entry makes it non-rememberable). `recordReplicaSAppId` is a no-op once `sAppConfigs` holds the strand. No other code branches on `sAppInfo` being absent, apart from the CLI's display.
- Latency hint change: `HibernationManager` re-reads `instance.latencyHint` at every timer arm; a claim to `realtime` over an armed timer idles once and never hibernates. This matches the comment at the assignment and is harmless.

**Tests:** the one new spec (`strand-replica-claim.spec.ts`) pins the upgrade contract on a real manager and libp2p node, covering the in-flight wait (mutation-checked by the implementer) and founding after the attach. It pays for itself, so I kept it. No test added: the CadreNode-level paths (the attach in `claimTrackedStrand`, the second check, `addStrand`'s writable wait on a claimed syncing replica) were checked by reading the code. A spec for them would need a two-launch race on a full `CadreNode` for logic that is two sequential calls into the already-tested manager seam.

**Docs:** `docs/architecture.md` was already updated. `docs/strands.md` said a storage node launches the strand as a replica after the restart announcement without saying what the app's claim then does. I added that the claim upgrades the running replica in place. `docs/cadre-host.md` and `docs/reference-app-rn.md` mention replicas only from the storage side and are still accurate.

**Tripwires recorded:**
- Failure-ordering dependency between `startStrand`'s cleanup and an attach waiting on the build: `NOTE:` on `settleRuntimeBuilds` (added in this pass).
- Concurrent claims of one replica applying twice: the existing `NOTE:` on `attachSApp` (from implement), left as is.

**Major findings / new tickets:** none. The implementer's listed gaps (one rejected `addStrand` when a claim waits on a failing replica launch; a hibernating replica's claim being config-only until wake; `replicaSAppIds` left shadowed rather than cleared) are acceptable behaviour, not defects: each converges, and none leaves wrong data.

**Source hygiene:** `strand-instance-manager.ts` and `cadre-node.ts` were already large before this change. The diff adds small single-purpose methods (`claimTrackedStrand`, `attachSApp`, `trackRuntimeBuild`, `settleRuntimeBuilds`) rather than growing existing ones, and moving the founder branch into `claimTrackedStrand` made `startOrFoundStrand` shorter. The comments say why, not what.
