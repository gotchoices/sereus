# Complete: every strand machine binds itself to its party's membership

Third ticket of the party-identity chain (`strand-party-member-key` → `strand-formation-membership-invite` → this → `strand-party-removal-via-formation-e2e`, which sits in `implement/`). Closed-strand bring-up now finishes the join on every machine by itself.

## What shipped

**`strand-membership-reconciler.ts`** — one `StrandMembershipReconciler` per closed-strand instance launched with a party key. Each pass: stop if the revocation enforcer flags this party as revoked → ensure the party's `Strand.Member` row (visible → done, and any still-staged invitation is *burned* via a standalone `ConsumedInvite` row naming the existing member; absent + staged invitation → `consumeInvite`, retried until the `Invite` row replicates here; absent + nothing staged → idle, with one `console.warn` after 10 passes) → ensure this machine's own `Strand.MemberPeer` binding via `registerMemberPeer`, then stop for good. Terminal without done: sealed strand, self-revocation, undecodable party key. A dead invitation (expired / cancelled / consumed elsewhere) is dropped and the loop keeps idling. Passes are serialized on a promise tail, never reject, and never block bring-up; cadence mirrors the revocation enforcer's `pollIntervalMs` (30 s default).

**Writer** — `burnInvite` and `isStrandMember` exported; `consumeInvite`'s `ConsumedInvite` insert factored into a shared private helper.

**Instance manager** — the reconciler is armed in `buildStrandRuntime` right after `strandDb.initialize()` (launch and hibernation resume alike), stopped and dropped in `releaseRuntime`. New `clearOwnMemberPeerBinding(strandId)` self-signs `removeMemberPeer` with the retained launch config's party key, best-effort, never throws. `StartStrandConfig` gained `pendingMembershipInvite` and `membershipReconciliation`.

**CadreNode** — `launchStrand` wires `pendingMembershipInvite` as a live view over `pendingMembershipInvites` (the reconciler owns invalidation) and threads `CadreNodeConfig.strandMembershipReconciliation`. `unpublishStrand` clears this machine's binding after the control delete and before the local stop, while the party key can still sign.

**Harness / scenarios / docs** — `controlNodeConfig` gained `membershipReconciliation: false`; `strand-formation-cross-party-seed` now proves the fully automatic path over a real two-party network; `strand-membership-closed-strand-e2e` disarms the loop (it hand-drives the writers); `strand-removal-cuts-network`'s fixture-honesty comments rewritten. `docs/strands.md`, `docs/architecture.md`, `docs/testing.md`, `docs/strand-contracts.md`, `docs/strand-contracts-review.md` updated.

## Review findings

**Checked:** the implement diff read first and whole (reconciler, writer additions, manager arming/lifecycle/clear, node wiring, all five new/extended spec files, harness and three scenarios); the pass ladder and every terminal state against the real strand engine; the arming gate across open/closed, keyed/keyless, quiesce→resume and stop; the unpublish ordering claim; failure-classification regexes against the constraint names in `schemas/strand.qsql`; resource cleanup (interval unref'd, map entries dropped on release, rollback path on a failed build); and every doc the change touched, re-read against the code rather than trusted.

**Major findings: none — and specifically not by omission.** Two candidates were weighed and rejected as ticket-worthy. (1) The `DEAD_INVITE_REJECTION` regex matches the bare table name `ConsumedInvite`, which looked like it could swallow the *transient* `InviteExists` rejection — the exact case the loop must retry — and permanently drop a good invitation. It does not: the engine's deferred-check message is `CHECK constraint failed: <constraint name>`, so only the primary-key UNIQUE violation names the table. Already pinned by the "not replicated here yet is RETRIED" test, and now by a new one for the consumed-elsewhere arm. (2) `cadre-node.ts` is 6673 lines (`wc -l`); `tickets/backlog/debt-cadre-node-single-file-size.md` already claims that site, and this change added 25 lines to it, so there is nothing to append.

**Minor findings, all fixed in this pass:**

- **`clearOwnMemberPeerBinding` could have its removal undone by a racing reconciler pass.** Its doc claimed "the reconciler is stopped FIRST so a racing pass cannot re-register", but `stop()` only disarms the poll — a pass already past its own stopped check runs to completion and can `registerMemberPeer` after the removal committed, leaving exactly the stale binding an unpublish is meant to clear. Added `StrandMembershipReconciler.settle()` (resolves when no pass is in flight) and awaited it after `stop()`; corrected the comment. Two tests: a real-DB one that stops the loop from inside a pass and proves the pass still completes (so `settle()` is what waits), and an invocation-order assertion in the manager spec.
- **An untested classification arm.** The handoff said every classified path was pinned against the real engine; the "invitation already consumed by someone else" arm was not. Added a real-DB test (two parties, one bearer credential, the loser's copy is dropped and the loop keeps idling). It passes — coverage gap, not a defect.
- **`getPendingMembershipInvite`'s doc was stale.** It pointed at this ticket as future work and never said that `undefined` now also means "already redeemed, burned, or found dead" — which is what a caller polling it actually observes. Rewritten.
- **The new config knob was undocumented.** `docs/architecture.md` documents `CadreNodeConfig.strandRevocationEnforcement`'s cadence and off switch (an undocumented knob was a finding on an earlier ticket in this area); `strandMembershipReconciliation` had no such line. Added one, including the warning that a production node disarming it seats no joiner and binds no machine.

**Tripwires recorded** (index only — the reasoning lives at each site):

- `strand-membership-reconciler.ts` → `noteIdlePass`: an idling loop never gives up, costing one `Strand.Member` scan per strand per interval for the life of the process; bound the idle phase if a node ever runs strands by the hundred or member sets grow large.
- `cadre-node.ts` → `unpublishStrand`: unpublish now awaits a strand-network write it never used to; give the call its own deadline if unpublish ever hangs on an isolated strand.
- Carried over from implement, re-read and still accurate: the stale-binding NOTE on `clearOwnMemberPeerBinding` (revisit when `feat-strand-member-allowlist-admission` lands) and the `enabled: false` warning on the reconciler config.

**Accepted tradeoff tagged:** the ticket specified that a failed burn is logged and dropped rather than retried, so a transiently-failed burn leaves a bearer credential spendable until it expires. That is the same state `docs/strands.md` already documents as normal ("removal does not cancel an unspent invitation"), so it stands — but it was only explained in prose. Now tagged `NOTE: accepted tradeoff` at `burnLeftoverInvite`, with its revisit condition, so the next reviewer does not re-discover it.

**Not filed, deliberately:** the remaining gaps the handoff lists — hibernation resume re-running the ladder has no real-network run, and the full form → remove → cut journey on production-written rows — are the subject of `strand-party-removal-via-formation-e2e`, already in `implement/`.
