# Complete: tombstones carry their signer; owner keys get a signed add and a signed remove

First of three tickets (`owner-anchor-derivation` and `owner-anchor-follows-owner-key-changes` follow, both in `implement/`). Implementation commit: `ticket(implement): owner-anchor-revocation-signer-and-owner-writers`.

## What landed

- **Schema** (`schemas/control.qsql`, mirrored in `control-schema.ts`): `Revocation` gains `SignerKey` / `SignerSig` (`text null`). `Revocation.Authorized` pins both, null-safe, to the write context; `ReissueOnly` keeps them equal to the old values, null-safe. Existing control stores are recreated (constraint text changed).
- **`ControlDatabase`**: `execTombstone` stores the signer pair and now also files the ledger marker; `queryRevocations(retry)` returns the pair; `insertOwnerKeyVouched` (idempotent on a live owner, refuses by name a re-add over a retired row it still holds) and `deleteOwnerKey` (refuses self-removal and the last live owner by name; `false` for a key that is not a live owner), both through the membership hub `mutateCadrePeer`; `getOwnerKeys(retry)` drops retired stamps; `hasOwnerKey` stays raw on purpose.
- **Verifiers** (`peer-authorization.ts`, exported): `verifyRevocationSigner`, `ownerKeyAddDigest`, `verifyOwnerKeyVoucher`.
- **API**: `SeedBootstrapService.addOwner` / `removeOwner`; `CadreNode.addOwner` / `removeOwner` (an add committed alone is logged; `tickets/backlog/debt-owner-key-add-while-alone-has-no-reissue.md` owns the missing re-issue).
- **Docs**: `docs/architecture.md` table rows for `OwnerKey` and `Revocation`, the two "made while alone" sections, Implementation Status.

## Review findings

**Read first:** the full implement diff (schema, `control-database.ts`, `peer-authorization.ts`, `seed-bootstrap.ts`, `cadre-node.ts`, `types.ts`, the spec changes, docs), then the handoff.

**Checked and fine (no change):**
- Lock discipline: `deleteOwnerKey` calls the bare `deleteGuardedRow` inside its `mutateCadrePeer` body and reads with `retry: false`; no locked public method is re-entered. `insertOwnerKeyVouched` mints stamp and signature inside the body, so a `lockedWithRetry` re-run re-signs.
- `getOwnerKeys` callers: all but `deleteOwnerKey` run unlocked (`enrolledOwnerSigningKey`, the cohort dial preference, `querySeedPeers`, the three invitation-liveness reads), so the default `retry = true` is right for them.
- Null handling in the new constraints: a null context fails the `exists` clause, so the `coalesce(..., '') = context.X` pins cannot pass on nulls; the `ReissueOnly` coalesce closes the re-issue-to-null hole, and the implementer's test probes it.
- The two deviations the handoff flagged (`text null` columns; `deleteOwnerKey` answering `false` for a retired row) are sound for the reasons given; kept.
- Error handling: refusals throw with names; verifiers log and return `false` rather than throw, matching `verifyCadrePeerVoucher`.
- Tests: the implementer's new and changed cases each pin a constraint clause or a writer contract; none restates the implementation or verifies a mock. Nothing cut.
- `docs/api.md` lists a selection of the seed API and does not list `removePeer` either; left as is.

**Fixed in this pass (minor):**
- **Read-side verifiers had no test against production-written rows.** Added two assertions to the existing "insertOwnerKeyVouched then deleteOwnerKey…" case in `control-revocation-replay.spec.ts`: `verifyOwnerKeyVoucher` accepts the stored voucher and `verifyRevocationSigner` accepts the stored tombstone. This pins that `ownerKeyAddDigest` / `revocationDigest` agree with the writers' raw-byte message builders, which the handoff listed as a gap. No new test case.
- **Docs and comments overclaimed where a removed owner's row survives.** The `OwnerKey` row in `docs/architecture.md`, the `getOwnerKeys` JSDoc and the `insertOwnerKeyVouched` NOTE said every machine except the remover keeps the row. A delete made while connected replicates like any write; the row survives only on machines that received the tombstone without the delete (a removal committed while the remover was alone, whose tombstone is re-issued on growth). Reworded all three; the re-add guidance now says "from a machine the delete reached".

**Filed (major):**
- **A removed owner keeps schema-level write authority wherever its row survives.** Every owner check in the schema reads raw `OwnerKey`, none excludes a retired stamp, and `OwnerKey` is never reaped. After `removeOwner` commits while alone, every other machine (the removed one included) keeps the row beside the tombstone, and there the removed key can still remove other owners, delete strands, add validation keys and file tombstones. This is reachable now through the API this ticket added, on the usual path for removing a lost device. Filed at the invariant rung: `tickets/fix/4.65-removed-owner-still-authorizes-where-its-row-survives.md` ("a retired `OwnerKey` row authorizes nothing", one clause in every owner lookup; repro: static). Added a pointer to it in `tickets/implement/4.61-owner-anchor-derivation.md`, whose ordering paragraph assumed the window closes on convergence.

**Tripwires (already parked by the implementer, unchanged):**
- `hasLiveCadreInvite` scans `Revocation` twice on the stranger path; `NOTE:` at the site.
- The removal pre-checks read local rows, and the schema decides under concurrent removals; covered by the existing `NOTE:` on `deleteGuardedRow`.

**Left untested, deliberately:** the by-name refusals (self-removal, last owner, re-add over a retired row), the not-live `false`, and `CadreNode.addOwner` / `removeOwner`. They are single-branch guards in front of schema checks that already refuse those shapes (`A.Key <> old.Key`, `MinOneOwner`, the primary key). The re-add refusal cannot be reached on one database anyway: `Revocation.RowIsGone` refuses an `OwnerKey` tombstone while the row is present, so the row-plus-tombstone state arises only through replication.
