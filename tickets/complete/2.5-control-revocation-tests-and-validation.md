# What landed

Deleting a `CadreControl.OwnerKey` or `CadreControl.CadrePeer` row used to free its one-off
`StampId` nonce, so the original add-approval signature — which never expires, and which for
`CadrePeer` is even STORED on the replicated row as `VouchSig` — verified again: anyone holding a
copy could re-seat a removed owner or peer verbatim. Every removal was undoable.

An append-only `CadreControl.Revocation` table now retires `(TableName, StampId)` on removal:

- `NotRevoked` (both guarded tables) refuses an insert naming a retired stamp — the replay itself.
- `RevocationRecorded` (both guarded tables) refuses a delete not carrying the matching tombstone
  in the same transaction — a bare delete would free the stamp.
- `RowIsGone` / `Immutable` (on `Revocation`) keep tombstones honest: only a gone row's stamp may
  be retired, and never un-retired.
- `SeedBootstrapService.removePeer` wraps its signed delete + tombstone in one transaction.
- Read-side mitigation for the replication race: `CadreNode.listAuthorizedMembers` /
  `isAuthorizedMember` drop any `CadrePeer` row whose stamp is retired.

Legitimate re-adds mint a fresh stamp per insert, so removal is stamp-retirement, not an identity
ban.

Test coverage: `control-revocation-replay.spec.ts` (11 tests, real `CadreNode` per test) pins
verbatim replay refusal, tombstone-less delete refusal, fresh-stamp re-add, tombstone honesty, and
(added in review) TableName scoping + stamp-rotation refusal — all by constraint NAME;
`cadre-node-authorized-surface.spec.ts` and `membership-connection-gater.spec.ts` pin the
read-side filter on both the membership surface and the inbound gate; `seed-bootstrap.spec.ts`
proves the real `removePeer` round-trip retires the stamp.

## Review findings

Reviewed the implement diff (`90461b1`) plus the production code it validates (`a150826`,
`f91bfad`) — schema constraints, read-side filter, `removePeer` transaction, all six touched
specs, and the docs the change should have updated.

**Major — filed as a ticket:**

- `CadreControl.Revocation` accepts writes with **no authorization at all** — it is the only table
  in the schema with no `with context` clause and no `verify(...)`. Any control-DB writer (any
  admitted cadre node, owner or not) can append tombstones. A tombstone naming a live peer's stamp
  evicts that peer from every reader's authorized-membership set, which is an owner-only action
  performed with no owner signature; the only barrier is `RowIsGone`'s local-visibility check,
  which the schema's own NOTE says does not hold across a not-yet-converged node. Junk tombstones
  for never-existing stamps are always accepted, permanent, replicated, and re-scanned per inbound
  gate request. → `tickets/fix/2.7-bug-control-revocation-unauthenticated-writes.md`.

**Minor — fixed in this pass:**

- **Stamp rotation escaped the tombstone.** The owner branch of `CadrePeer.AuthorizedUpdate` did
  not pin `new.StampId = old.StampId` (the self-update branch did). An owner re-vouch that changed
  the stamp would strand the OLD stamp: never tombstoned (a delete only retires the stamp it
  carries), no longer on a live row — so the original admission approval would resurrect the peer
  after the next removal, reopening exactly the hole this work closes. Dormant today
  (`reauthorizePeer` preserves the stamp), latent the moment any rotation path is written. Pinned
  in both schema copies, with a test that also confirms the legitimate re-touch still passes.
- **`RowIsGone`'s comment misstated the code it relies on.** It claimed stamps are "32 bytes of
  CSPRNG output"; `generateStampId` is 16 bytes of `sha256(PeerId)` followed by 16 random bytes.
  The security conclusion holds (128 random bits cannot be pre-planted), but the argument cited
  the wrong fact. Corrected in both schema copies and the spec comment.
- **Test gaps closed.** (a) A tombstone filed under the WRONG `TableName` now must not satisfy
  `RevocationRecorded` — nothing previously pinned that scoping, so a stamp retired under any
  table name would have unlocked every guarded delete. (b) The gater-level revoked-peer-dials-in
  test the implementer flagged as missing now exists (`membership-connection-gater.spec.ts`),
  with a live sibling admitted alongside so the fail-open "empty authorized set" branch cannot
  mask the result.
- **Docs were out of date.** `docs/architecture.md` control-table list did not mention
  `Revocation`; added. The delete-while-alone durability note now records that the new tombstone
  is a re-issuable insert the write-while-alone queue does not yet carry — the cheapest lever for
  `tickets/backlog/control-delete-while-alone-tombstone.md`.

**Checked, no change needed:**

- `OwnerKey` cannot rotate its stamp — `NoUpdate check on update (false)` already forbids all
  updates.
- A tombstone planted under the other guarded table's name is inert in both directions: every
  reader and every `NotRevoked` subquery scopes on `TableName`.
- `listAuthorizedMembers`' `row.stampId === null ||` branch reads like a fail-open, but a
  null-stamp row is rejected a step later by `hasAnchoredVoucher`. Redundant, not wrong; left as
  written rather than churn a security-critical predicate.
- `OwnerKey` has no read-side revocation filter — deliberate and documented: the node-local
  trusted-owner anchor gates owner trust, not the replicated table.
- No production `OwnerKey` deleter exists; owner-rotation removal is test-only SQL today. When one
  is built it must copy the delete-plus-tombstone transaction shape (`removePeer` is the
  reference) — already stated in the implement handoff and still true.

**Tripwires (parked in code, not filed):**

- Write-time `NotRevoked` only sees locally visible tombstones, so a not-yet-converged node can
  still accept a replayed add and the resurrected row coexists with the tombstone after merge —
  parked as a `NOTE:` in the `Revocation` table header (both schema copies), mitigated for
  `CadrePeer` by the read-side filter.
- `Revocation` is append-only and grows forever — parked as a `NOTE:` in the same header.
- `queryRevokedStamps` re-reads the whole retired set per call and the caller runs per inbound
  gate request — parked as a `NOTE:` on the method in `control-database.ts`.
