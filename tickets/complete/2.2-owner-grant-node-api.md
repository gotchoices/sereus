# Owner grants: the node API, the redemption protocol and the bundle

## What shipped

Implemented in `ticket(implement): owner-grant-node-api`, reviewed and amended in `ticket(review): owner-grant-node-api`. Additive: machine invitations keep `grantsOwner` until `machine-invitation-grants-no-ownership`.

- **One shared redemption core, two protocols on it.** The credential-independent parts of the invitation protocol moved into `member-redemption.ts`: the shape checks and the 64 KiB frame cap, the refusal helpers, an abstract member-side handler (`MemberRedemptionHandler`: concurrency cap, read timeout, shape then protocol checks, push of the control store to a holder of a live credential, writes under that admission) and the holder-side dial loops (`dialRedemption`, `dialRedemptionInPasses`). `cadre-invite-protocol.ts` keeps its whole public API as thin instances of those; `CadreInviteAddressOutcome` is an alias of `RedemptionAddressOutcome`.
- **`owner-grant-protocol.ts`**: `OwnerGrantBundle`, `encodeOwnerGrant` / `decodeOwnerGrant` behind `sereus-owner-grant:1.` (`OWNER_GRANT_PREFIX`, declared in `cadre-join-request.ts` beside the other prefixes), the wire request and reply, the codes with grant wording and `OWNER_GRANT_REJECTION_RETRYABLE`, the three holder-side errors, `signOwnerGrantRequest`, `verifyOwnerGrantReply`, `OwnerGrantHandler` (party and both signatures; no connecting-identity check; seat then redeem) and `redeemOwnerGrantAtMembers` / `redeemOwnerGrantInPasses`. All four pasted texts refuse each other by name.
- **`CadreNode`**: `createOwnerGrant` (15-minute, one-use default; `expiresInMs: null` is the explicit backup; label through `ownerKeyLabel`; bundle parts through `issuedBundleParts`, shared with `createCadreInvitation`), `listOwnerGrants`, `withdrawOwnerGrant`, `redeemOwnerGrant` with a local path (a live member or an enrolled owner writes in its own store) and a protocol path (anyone else dials the bundle's members), `joinWithOwnerGrant` (grant plus a self-invitation under one approval, then `wireOwnKeyIfOwner` once the row syncs, bounded at 60 s), and the owner-grant handler registered at start and unregistered at stop beside the invitation handler. `SeedBootstrapService` gained `insertOwnerGrant` / `withdrawOwnerGrant`; `ControlDatabase.signCadreInvite` is the signing half of `insertCadreInvite`.
- **Gate and guard**: `admitInboundControlConnection` admits a peer whose redemption this node is writing (`admittingDevices`); a live grant deliberately does not count as expecting a stranger. `/sereus/owner-grant/1.0.0` is `stranger-open`.
- **`planOwnerKeyRemoval`** lists the live grants the key issued (`grants`); `removeOwner` does not withdraw them.
- **Docs**: `docs/architecture.md` "Owner grants" section, the gate's admission paragraph, the guard's `stranger-open` lists, "Removing an owner key", the `OwnerGrant` table row and the Owner Keys pointer; the cadre-core README names `createOwnerGrant` among the owner-only flows.

## Review findings

Read the implement diff file by file before the handoff, then every touched source and doc; ran the repo typecheck and lint and the cadre-core unit suite.

**Checked, and found sound:**

- The handler base's cost order (shape, protocol checks, admission, writes), its `busy` / `internal` paths, the `release` in `finally`, the dial loop's "final refusal and failed reply check thrown outside the per-address catch" change (no visible effect, as the handoff said), the pause's listener and timer cleanup, and the caller-abort relay without `AbortSignal.any`.
- The invitation protocol's public API after the extraction: every consumer (`cadre-node.ts`, `membership-connection-gater.ts`, `index.ts`, the protocol spec, the `cadre-invite-row-unreplicated` scenario) still typechecks; the invitation and protocol specs pass unchanged.
- The holder-side reply check, the single `usageStampId` across addresses and passes, the self-invitation's issuer among the pins, the accepting member's addresses first, the `isLiveMemberSelf` read (own row judged as `listAuthorizedMembers` judges the others), the `alone` refusal before the approval, the ephemeral-identity refusal in `joinWithOwnerGrant`, and the 60 s wire bound returning `ownerWired: false` rather than failing a join that already succeeded.
- The gate's check 3 (`admittingDevices`) and the renumbered list; the guard spec's literal four-protocol list.
- The removal plan's `grants` and the `removeOwner` decision not to withdraw them.
- The docs: the new section, the gate paragraph, the guard lists and the README row match the code. The stale reference to the plan ticket `owner-grant-separate-from-machine-invitation` in "Invitation-granted owners" and in `wireOwnKeyIfOwner`'s doc is `machine-invitation-grants-no-ownership`'s to retire with the route it describes, not this ticket's.

**Found and fixed in this pass (minor):**

- **The owner-grant handler was never unregistered.** `stop()` unregistered the invitation handler and left `ownerGrantHandler` registered on the stopping libp2p node and non-null. The control node is rebuilt on every start, so no duplicate-handler error followed, but the handler kept a dead node in its registry and the field outlived the node. `stop()` now unregisters and nulls it beside the invitation handler.
- **The local path pinned pasted `ownerKeys` into an enrolled member's anchor.** `redeemOwnerGrant` called `trustOwnerKeys(bundle.ownerKeys, 'invite')` before choosing a path, so a member machine or owner node redeeming a bundle locally anchored whatever keys the text named, as base keys that only a verifiable tombstone removes. A fresh device needs that pin (it is how it bootstraps trust); a member does not, since it judges the issuer by its own `OwnerKey` table (`seatOwnerGrant` refuses an unknown issuer). The pin now happens on the protocol path only. The node spec's local redemption passes a bundle with a stranger key appended to `ownerKeys` and asserts the anchor does not gain it.
- **A dead grant prompted the approval before failing.** On the local path a withdrawn, expired or spent grant was seated (a no-op when held) and then the signer's approval opened, and only the write refused. The path now checks `isOwnerGrantLive` after the seat and before the approval, unless the key is already an owner (the write answers that case without reading the grant), and throws `OwnerGrantRejectedError` `grant-spent`, the code a member would answer. The node spec withdraws a grant and asserts the refusal by name with zero approvals. The error class's doc now says the local path's member is this node.

**Considered and left as is:**

- **A forged grant row (issuer signature that does not verify) is answered `issuer-unknown`, retryable**, so the holder tries every address before giving up. The handler could verify the row's own signature in `checkRequest` and answer `grant-invalid`, final. The invitation handler behaves the same way and its spec pins it ("sends nothing to the holder of a forged row naming a real owner, and the seat refuses it"); the cost is one pass over the holder's own forged text. Not a tripwire: it is a settled design shared by both protocols, and diverging the grant handler alone would be worse than either choice.
- **`joinWithOwnerGrant` passes one `onProgress` to both redemptions**, so the pass counter restarts for the self-invitation. The callback's `state` tells the phases apart well enough for a UI; no change.
- **Trust provenance stays `'invite'`** for grant pins, as the handoff proposed: a new `TrustSource` value would be unusable to an older build reading the anchor file, and the store does not distinguish base sources.
- **A partial `joinWithOwnerGrant`** (grant accepted, self-invitation then refused) leaves the key an owner and the node not a member; a retry answers `alreadyOwner` and signs a fresh self-invitation. Documented by the existing `@throws`; no change.

**Tests:** the implementer's two new specs verify contracts rather than wiring (the codec's cross-refusals, the defaults, both paths, the gate, the removal plan) and were kept. Two assertions were added for the defects above, in the existing local-path test; no test was cut.

**Tripwires:** none new. The three `NOTE:` comments in `member-redemption.ts` (the `conflict`-versus-`internal` measurement, the accepted tradeoff on pushing a store to a holder whose write then fails, the holder's-clock expiry) moved with the code and read correctly for both credentials.

**Tickets filed:** none. `cadre-node.ts` is now 10,635 lines (`wc -l`), tracked by `backlog/debt-cadre-node-single-file-size`.

**Pre-existing failures:** none seen.
