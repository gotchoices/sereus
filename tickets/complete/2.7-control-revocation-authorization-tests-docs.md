# Complete: writes to `CadreControl.Revocation` are owner-signed

Closes the chain that began as `bug-control-revocation-unauthenticated-writes`
(fix → implement → implement → review).

## What shipped

`CadreControl.Revocation` is the append-only table that retires the one-time authorization
nonce (`StampId`) of a removed `OwnerKey` / `CadrePeer` / `ValidationKey` / `Strand` row, so a
never-expiring add-approval signature cannot resurrect a removed row. It had **no
authorization at all**: any writer reaching the replicated control database could append.

One constraint now gates the append:

```sql
constraint Authorized check on insert (
    exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(digest('CadreControl.Revocation', 'remove', new.TableName, new.StampId), context.Signature, A.Key, 'ed25519'))
)
) with context (OwnerKey text, Signature text);
```

The digest binds the whole row; its `'CadreControl.Revocation'` domain tag keeps it disjoint
from the `'CadreControl.CadrePeer'` `'remove'` digest the same owner signs in the **same
transaction** for the delete the tombstone accompanies, so neither signature stands in for
the other.

Production signers: `SeedBootstrapService.removePeer` (via `revocationDigest`, base64url
encoding) and `ControlDatabase.deleteGuardedRow` — the shared body of `deleteStrand` /
`deleteValidationKey` (via `buildAuthorizationMessage`, raw canonical bytes). `RevocableTable`
moved to the import-free `control-authorization.ts` so the lightweight signer can type
against it.

Rejections, each asserted by constraint name:

| Attempt | Reports |
|---|---|
| tombstone with no context, or either half of the context alone | `Authorized` |
| tombstone signed by a non-owner (own key, or claiming the founder's) | `Authorized` |
| owner-signed tombstone over a different `StampId`, or a different `TableName` | `Authorized` |
| the delete's own `'remove'` signature replayed as the tombstone's | `Authorized` |
| tombstone signed by a key that was an owner when it signed but has since been removed | `Authorized` |
| owner-signed tombstone of a still-live row | `RowIsGone` |
| `TableName` outside the four guarded tables | `RowIsGone` |
| delete or update of an existing tombstone | `Immutable` |

Accepted: any **live** owner (not only the founder) filing a tombstone for a row that is
gone, and all four production removal paths end to end.

Docs: the `Revocation` row of the control-table list in `docs/architecture.md` now states
that appending is an owner action and why it is gated; the delete-while-alone durability
note gained a clause that a future re-issue path must carry the tombstone's signature in its
write context.

  `OwnerKey`'s delete branch already refuses an owner signing its own removal, and
  `MinOneOwner` refuses a mutual removal that would empty the table, so the tombstone's
  signer always outlives the transaction. Verified against
  `control-ownerkey-self-authorization.spec.ts`, not just by reading the schema.

  `docs/STATUS.md`. The first two never mention the table; `STATUS.md`'s only nearby line is
  a historical roadmap entry about `CadrePeer`'s insert/delete split, not a description of
  current authorization rules. Nothing stale found.

### Major — none

No finding warranted a new ticket. The authorization rule, its two production signers, and
the schema-drift guard are consistent, and every rejection path is pinned by constraint
name rather than by a bare "it threw".

### Minor — fixed in this pass

- **Two coverage holes in the `Authorized` section**, both security-relevant semantics that
  were unpinned in either direction. Added to `control-revocation-replay.spec.ts`:
  - `ANY live owner may file a tombstone, not only the founder` — every existing accept-side
    test signs as the founder, so a future narrowing of the rule to one key would not have
    failed anything. Drives a second owner through a full signed delete + tombstone
    transaction.
  - `a tombstone signed by an owner REMOVED since is refused` — the handoff listed this as a
    known gap. It follows from reading live `OwnerKey`, but "follows from" is not "pinned":
    the test signs while the key is an owner, removes that owner, then files the tombstone
    against an orphan stamp (so `RowIsGone` passes and only `Authorized` can reject).
- **Stale cross-reference** in the section's header comment ("inverted in the last two tests
  of this section") — no longer true once tests were appended; now names the FLOOD and
  PRE-BLOCK tests directly.

### Tripwires — recorded, not filed

- `control-revocation-replay.spec.ts` is past 1200 lines covering four constraints. It stays
  whole because every section shares one fixture and one set of signing helpers; if the
  `Authorized` section keeps growing, split it out and lift the shared helpers into
  `control-constraint-helpers.ts`. Parked as a `NOTE:` in the spec's header docblock.
- The append-only growth surface and the per-gate-request re-read of the whole retired set
  already carry `NOTE:` comments (`control-schema.ts` above the table,
  `control-database.ts:491`); both remain accurate after this change — nothing added.

### Known gaps left open (deliberately, unchanged from the handoff)

- **Single-node only.** Every test boots one `CadreNode` on the `transaction` profile. The
  convergence hazard — a node that has not yet seen a `Revocation` row accepting a replayed
  add, then holding both after merge — is a pre-existing property of the whole `NotRevoked`
  design, not something this change introduces, and testing it needs `integration-tests`.
- **`Authorized` reads live `OwnerKey`, not `committed.OwnerKey`.** Deliberate and consistent
  with every sibling table. Reviewed and accepted: the only behavioural difference is that a
  founding transaction on an owner-less database could seat an owner and file a tombstone in
  one go, and an owner-less control database is already a total loss.
- **Single-rejector technique.** Several assertions rely on Quereus reporting exactly one
  violated deferred constraint per commit (see the `NOTE:` in `control-constraint-helpers.ts`).
  If an engine change ever reports a different one, re-shape the write — do not widen the
  accepted-name list.
- **No production `OwnerKey` delete path exists.** `deleteGuardedRow` covers `Strand` and
  `ValidationKey` only, and `removePeer` covers `CadrePeer`; the two-owner `OwnerKey` removal
  transaction is exercised through raw SQL in tests. That is the pre-existing shape, noted
  here so a future owner-rotation feature knows it must mint the tombstone signature itself.
