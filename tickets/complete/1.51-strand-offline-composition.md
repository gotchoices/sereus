First of the `strand-offline-mode` chain, in `@serfab/quereus-plugin-sereus`. Implemented in `ticket(implement): strand-offline-composition`; reviewed and amended here.

## What landed

- **`StrandConnectionOptions.offline?: StrandOfflineOptions`** (upstream `OfflineConfig` less `journalLabel`). Absent: nothing reaches the plugin and the result has no `offline`.
- **Register pass-through** (`strandOfflineConfig` in `compose-strand.ts`): the caller's options, the platform's default journal when none is given, and `journalLabel: strandJournalLabel(strandId)` only when a journal exists. Label = `strand-` + id with `_`→`__`, `.`→`_d`.
- **`StrandPlatform.defaultOfflineJournal()`**: the browser connect answers an `IndexedDBKVStore` over the IndexedDB database it defaulted the storage to (`sereus-strand-<id>`). Node supplies none, so the queue is memory-only there.
- **`SereusPluginResult.offline?: StrandOfflineController`** (a `Pick` of upstream `OfflineMode`), and **`offlineControllerOf(db)`** (module `WeakMap`, cleared on shutdown and on a failed connect). Status, state and error types re-exported from the package index.
- **Release order**: `releaseOptimysticPlugin` disposes the offline queue before the transaction bridge, on shutdown and on a failed connect.
- **All eight `Strand` tables tagged `"optimystic.offline" = 'network'`** in `schemas/strand.qsql` and `STRAND_SCHEMA`.
- **App-schema deferral**, now in its own module `src/app-schema.ts` (with `applyAppSchema`): `applyAppSchemaAfterQueue(db, schema, queue, released)` returns `appSchema: Promise<AppSchemaOutcome>` and, when queued transactions refused the first apply, `appSchemaDeferredBy`; the background retry waits for `whenDrained()`, then applies as one atomic batch that waits out any transaction another caller holds open. Outcomes: `applied` (+`deferred`), `failed`, `cancelled`.
- **Docs**: `docs/strands.md` "Offline mode" section (option, controller, programmatic only, release order, journal and label, network-acknowledged `Strand` tables, app-schema deferral including the open-transaction wait); "Writable does not mean connected" has an *In offline mode* sub-paragraph. Plugin README has the `offline` option row and a short section.

## Review findings

**Checked.** Read the implement diff before the handoff. Compared `releaseOptimysticPlugin` with upstream `plugin.dispose()` (`../optimystic/packages/quereus-plugin-optimystic/src/plugin.ts`): same order for queue → bridge → factory. Read upstream `OfflineMode.whenDrained`/`dispose`/`assertNoQueuedEntries` and db-core `OfflineQueue.whenDrained` to check the retry loop's outcome mapping: dispose rejects with `QueueDisposedError` (→ `cancelled`), a drain defect rejects with the defect (→ `failed`), and journaled records not yet put back keep `OfflineMode.whenDrained` pending. The `WeakMap` set/delete sites, the absent-option path, the label escape, the `cause`-chain walk, and the browser journal's key space (records live under `optimystic-offline/<label>/` in the strand's own IndexedDB `kv` store, so no clash with other keys there). Docs: `docs/strands.md`, the plugin README, and `docs/schema-guide.md` (it named the file `applyAppSchema` lives in).

**Throwaway checks (deleted):** shutdown while a retry is waiting settles `{ state: 'cancelled' }`; a non-queue first-apply error (a misspelled `tabel`) is thrown.

**Found and fixed: the deferred retry ran inside the app's open transaction.** The retry runs after the connect has returned, on the `Database` the app is using. Quereus's execution lock is per statement, so a plain `db.exec('apply schema App;')` that runs while the app holds `beginTransaction()` open joins that transaction. Verified: apply inside an open app transaction, then roll back, and `plugin.verifyIndexes` reports an orphaned `NoteByBody` entry for the rolled-back row, with the catalog keeping the index. The membership writers already guard this case (`execStrandTransaction` in cadre-core). Fix: the retry declares the schema, then runs `apply schema App;` with `{ transaction: true }`. On `TransactionActiveError` it waits `OPEN_TRANSACTION_RETRY_MS` (250 ms, stops early on shutdown) and tries again. The connect-time first apply is unchanged, because nothing else holds the database then. Regression test added to `app-schema-deferral.spec.ts` ("waits for a transaction the app holds open to end…"). It fails without the fix and passes with it. Documented in `docs/strands.md` and on `applyAppSchemaAfterQueue`.
