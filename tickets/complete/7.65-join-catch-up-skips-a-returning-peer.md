# Complete: the join catch-up re-runs for a peer that reconnects

## What landed

`PeerJoinBackfill` (cadre-core's peer-join catch-up, shared by every strand network and the control network) now subscribes to libp2p's `peer:disconnect` in `start()` and removes it in `stop()`. The handler, `forgetCaughtUp`, removes the peer from `done` (the "caught up" set) and keeps everything else: the per-peer memo of what the peer holds, `contacted`, and the backoff state. A reconnect's `peer:identify` therefore re-runs the catch-up after the debounce, pushing only blocks whose revision moved or that are new.

A disconnect that arrives while the peer's run is in flight adds the peer to `disconnectedInFlight`, so that run does not mark it `done` even if it settles clean; `trackRun`'s `finally` clears the mark. Connectivity is deliberately not checked at settle time, because hand-driven `catchUpPeer` runs target peers with no connection.

Accepted-tradeoff `NOTE:` on `forgetCaughtUp`: a returning peer that wrote while away with a cohort naming this node gets those blocks pushed both by its re-run and by its under-replication drain. This costs bytes only, because `saveReplicatedBlock` is idempotent. Revisit when `blocked/optimystic-embedder-cannot-report-block-holders` lands.

The work landed across three commits: the reproduction test (`78ea8af4`), the source and most of the docs (in the pre-existing-failure triage commit `tess: triage pre-existing test failure`), then `ticket(implement): join-catch-up-skips-a-returning-peer` (the in-flight test and the remaining doc and comment updates).

Tests: `re-runs for a caught-up peer that disconnected and came back, pushing only what moved` and `re-runs on reconnect for a peer that disconnected while its clean run was in flight`, both in `peer-join-backfill.spec.ts`.

## Review findings

**Correctness, checked by reading and tracing.**
- libp2p 3.3.11's connection manager dispatches `peer:disconnect` with the `PeerId` as `detail` only when it removes the peer's last connection entry (`node_modules/libp2p/dist/src/connection-manager/index.js:270`). That matches the fake's `dispatchDisconnect` and what `forgetCaughtUp` assumes. No defect.
- Disconnect while a debounce or backoff timer is pending (not yet in flight): the timer's run dials the peer. If the dial fails, the run is not clean and is not marked done. If it succeeds, the whole push landed, so `done` is correct. No defect.
- Disconnect mid-run followed by a reconnect mid-run: the reconnect's identify goes to `rearmAfterFlight`, the run stays out of `done`, and the replay re-runs it, pushing only what moved. Traced, not separately tested; the existing replay path already covers it.
- A mid-run disconnect where the run's own push re-dials the peer: the peer stays out of `done`, and the new connection's identify replays one cheap re-run (one store walk, no push). Acceptable.
- `forceCatchUpPeer` racing a disconnect: the mark is cleared in `finally` before the next run starts. No defect.
- The in-flight test is robust to timing. Whether the second identify arrives before or after the first run settles, removing the `disconnectedInFlight` guard makes it fail: either `done` drops the identify, or the replay sees `done`.

**Docs and comments: three stale statements, fixed in this pass.**
- `strand-late-cadre-join.integration.ts` header said the catch-up "marks the peer done for that runtime". It now says "until it disconnects".
- `docs/cadre-consistency.md` ("And it holds for ordinary writes too") said the catch-up "runs *once*, at join". It now says it runs when the joiner connects and again only after it reconnects.
- The emptied-store `PeerMemo` NOTE proposed clearing the memo on disconnect without naming the cost. It now points to the size NOTE: clearing the memo re-pushes the whole store on every reconnect. Both stay tripwires.
- Every other file the ticket listed was read and already describes the new behaviour: the module comment, the field docs, the backoff NOTE, `types.ts`, `cadre-node.ts`, `strand-instance-manager.ts`, and `docs/architecture.md` lines 138, 140, 144 and 2236. `packages/integration-tests/dist` carries the old header text, but it is build output and was not edited.

**Tests.** Both new tests pin the behaviour the ticket is about on code with real branching (the reproduction, and the in-flight guard), so both stay. No test was cut. I added no listener-count assertion for `peer:disconnect` in the start/stop test: it would test wiring, and a leaked listener on a stopped instance only removes a key from a set.

**Real-network coverage: not added.** No integration scenario drops a node, writes, reconnects, and checks the returning node's raw store before any read. libp2p's event semantics were checked against its source instead (above). I judged that check good enough for a change this narrow, and filed no ticket.

**Performance.** A re-run where nothing moved costs one `listBlockIds` walk plus one `getMetadata` per block, with no network traffic, once per reconnect after the debounce. Not measured on a large store. The existing memo-size NOTE already covers how this scales.

**Resource cleanup, error handling, types.** The listener is removed in `stop()`. `disconnectedInFlight` is always cleared in `finally`, so it cannot grow. The handler does no I/O and cannot throw. The event is typed `CustomEvent<PeerId>`. No findings.
