# Scenario: the always-on machine hosts a strand its phone joined from another party

## What was built

`strand-always-on-replica-hosts-cross-party-join.integration.ts` adds one `it` that covers, end to end, the path `party-wide-joined-strands` built. A phone in the JOINER party redeems a formation invitation from a one-machine HOST party, claims the open strand, and writes rows. The phone's connected owner reconcile pass publishes the join as a party-wide `JoinedStrand` row, which drains the local record. The joiner party's always-on machine (storage profile, `hostUnclaimedStrands: true`, never calls `formStrand`/`addStrand`) launches a storage replica from that row, and the replica holds every block the phone holds, checked on the raw store. Finally `forgetJoinedStrand` on the phone removes the row, leaves one `Revocation` tombstone carrying the row's stamp, and stops both the phone's strand and the always-on replica, while the host's strand stays `active`.

Race handling: the phone's reconcile timer is parked, and the formation handler is registered and settled before `formStrand`, so step 1's "join recorded locally, no party-wide row, no replica" state is read, not assumed. `freshReconcilePass` calls `reconcileControlCohort()` twice because the call is single-flight and can hand back a pass that started before the join was recorded.

Coverage map entry: `docs/testing.md` (after the two-party × two-machine line). Architecture note: `docs/architecture.md` Storage replicas, joined-strand bullet.

Known gaps, out of scope by the ticket's choice: closed strand (argued in the file header, not exercised), non-owner joiner (the join stays local, so no replica launches), sibling-device `strand:discovered` from the party-wide row, the always-on machine re-hosting after its own restart, and relayed links (everything here is direct loopback).

## Review findings

Checked by reading the implement diff (`ticket(implement): scenario-always-on-hosts-cross-party-join`) against `cadre-node.ts` (`reconcileControlCohort`, its single-flight guard, `startRecordRefresh` triggers, the connected-only `joinedStrands.syncWithParty` step, `forgetJoinedStrand`, `initializeStrandSolicitation`), then running the scenario and lint.

- **Correctness of the race handling:** confirmed. The only reconcile triggers are the start pass, the interval (parked here), and `self:peer:update`. `initializeStrandSolicitation` awaits `registerResponder` → `node.handle`, which awaits the peer-store merge that dispatches `self:peer:update`, so any pass that registration triggers is already in flight when `freshReconcilePass` joins it. The double call in `freshReconcilePass` is right: the in-flight owner's `finally` clears the guard before the joining caller's promise resolves, so the second call starts a new pass. The per-strand protocol handlers (strand-addr, peer book, wake) sit on the strand's own libp2p node or are registered at start, so `formStrand`/`addStrand` register nothing else on the phone's control node.
- **Residual timing assumption (tripwire):** an address change on the phone's control node between the prelude and step 1's reads would fire `self:peer:update` and publish early. That does not happen on loopback. Parked as a `NOTE:` beside the prelude comment in the test file.
- **Test value:** the one `it` stays. It is the only end-to-end check of publish → replica launch → party-wide removal, and the implementer's mutation check (local `stopStrand` instead of `forgetJoinedStrand` makes step 4 time out) shows step 4 depends on the party-wide removal. No assertion checks a mock or restates the implementation. Nothing cut, nothing added.
- **Docs:** `docs/testing.md` bullet is accurate and points to the one-party sibling scenario. `docs/architecture.md` joined-strand bullet said the scenario ran "beside" another one. Reworded to state plainly that the scenario runs both the launch and the stop. `docs/strands.md` → "What a joiner's node remembers" describes the mechanism rather than listing coverage, so it needed no change.
- **Hygiene:** file is 334 lines with small helpers per actor (`startHost`, `startPhone`, `enrollAlwaysOn`), teardown logs instead of swallowing errors, no `any`, SQL keywords lowercase. No findings.
- **Error paths / resource cleanup:** `stopAll` in `finally` stops all three nodes in reverse dependency order, and each stop is guarded. No findings.
- **Major findings / tickets filed:** none. No product defect surfaced, and the known gaps above are scope choices, not latent defects.
- **Validation:** `yarn workspace @serfab/integration-tests exec vitest run strand-always-on-replica-hosts-cross-party-join` passed (test 8.9 s; the phone's strand store held 11 blocks). `yarn lint` exit 0. The full integration suite was not run, only this file, because the only other edits are a comment and one doc sentence.
