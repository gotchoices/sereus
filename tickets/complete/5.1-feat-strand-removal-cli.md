# Complete: `cadre strand list|remove`

## What shipped

`cadre strands` became a **`cadre strand` group** with `list` and `remove` subcommands.
`.alias('strands')` keeps the old name, and `list` is the group's **default subcommand**, so the
pre-group invocations (`cadre strands`, `cadre strands --json`, `cadre strands -c <path>`) all
still list, with their options intact.

`remove <strandId> [--yes]` reads the `Strand` row, decides, then writes:

| Row state | `--yes` | Outcome |
|---|---|---|
| absent | either | no write, `• Strand not published — nothing to do`, **exit 0** |
| `Type='o'` (open) | either | `unpublishStrand`, exit 0, party-wide + delete-while-alone warnings |
| `Type='c'` (closed) | no | **refuses**, no write, **exit 1**, names the consequence |
| `Type='c'` (closed) | yes | `unpublishStrand`, exit 0, above warnings + "membership key gone" |

The decision is a pure exported `planRemove(row, strandId, { yes })`; `applyRemove(store, id,
opts)` trims the id, rejects blank, reads via a narrow `StrandStore`, and writes only when the
plan says to.

Shared subcommand scaffolding lives in `packages/cadre-cli/src/commands/subcommand.ts`
(`CommonOptions`, `PlanReport`, `withCommonOptions`, `runSubcommand`, `reportPlan`), used by both
`strand` and `validation-key`. A subcommand action may return an exit code (falsy means 0),
which is how a refusal exits non-zero while still printing a structured body rather than being
thrown and rendered as a `Failed to …:` line. A refusal's human text goes to stderr; the `--json`
body always goes to stdout.

## Review findings

### Checked

Read the implement diff before the handoff summary. Scrutinised: command surface and exit codes
(by running the built `dist/bin/cadre.js`), the `validation-key` extraction diff line by line,
type safety of the `PlanReport` narrowing, the `nodeStore` adapter against the real `CadreNode`
and `ControlDatabase` signatures, resource cleanup in `withConnectedNode`, warning wording versus
what `CadreNode.unpublishStrand` actually guarantees, source-file size and function granularity,
and every doc that mentions the command (`README.md`, `docs/architecture.md`, `docs/STATUS.md`;
`docs/strands.md` and `docs/cadre-consistency.md` were read and correctly say nothing about the
CLI). Ran `yarn build`, `yarn lint`, `yarn dep-check`, `yarn --cwd packages/cadre-cli test`.

### Major — fixed in this pass (regression, not deferred)

- **`cadre strands` was broken, and three docs claimed otherwise.** The alias was placed on the
  *group*, which has no action handler, so a bare `cadre strands` answered with usage text and
  **exit 1** instead of listing, and `cadre strands --json` / `-c <path>` failed outright with
  `error: unknown option '--json'`. The handoff, `README.md` and `docs/architecture.md` all
  stated the old invocation still worked; it did not. Verified against the built CLI before and
  after. Fixed by making `list` the default subcommand
  (`.addCommand(listCommand, { isDefault: true })`, `strands.ts`), which restores the bare call
  *and* the group-level options. Two new tests fail without the fix and pass with it. One
  cosmetic consequence: `cadre strand <bogus>` now reports `too many arguments for 'list'`
  rather than an unknown-command error — a correct rejection with a slightly indirect message.

### Minor — fixed in this pass

- **`strand list --json` was not pipeable.** `Connecting to control network...` went to stdout
  ahead of the JSON payload; the implementer parked it as a `NOTE:` and invited disagreement. It
  is progress output, not a result, so it now goes to stderr and the `NOTE:` is gone. A terminal
  still shows it. Verified: `cadre strands --json 2>/dev/null` emits only the payload. README's
  `list` example now says so.
- **`docs/STATUS.md` still described `cadre strands` as "list-only"** in the unrelated
  "no CLI surface to create a strand" gap note. Updated to `cadre strand` is list/remove only.
- **`docs/STATUS.md`'s "Not exercised end-to-end" claim was overstated after the new tests.**
  Narrowed to name what is actually still uncovered (`withConnectedNode` and the real write) and
  to cite the new spec.

### Minor — closed the biggest test gap the handoff flagged

The handoff called out that nothing drove the command through commander → `runSubcommand` →
`nodeStore`, including the refusal's non-zero exit ("the security-relevant half of this ticket"),
and that the extracted `runSubcommand`/`reportPlan` had no direct tests in either suite. Added
`packages/cadre-cli/test/subcommand-wiring.spec.ts` (11 cases): it stubs only
`withConnectedNode` and drives the real parsing and scaffolding over a fake node, asserting exit
codes, stream routing (refusal on stderr, `--json` payload parseable from stdout), that nothing
is written on a refusal, that `--yes` does not leak between invocations, that the default-`list`
dispatch works, and that `validation-key` still behaves identically through the shared code.
136 → 147 tests, all passing.

### Major — filed as a new ticket

- **No CLI command is tested against a real node.** With the wiring spec in place, the residual
  gap is `withConnectedNode` itself — config resolution, node construction, the connect-or-time-out
  race, shutdown — shared by every one-shot command and never executed by any test. Too large to
  stand up inside this pass. Filed as `backlog/debt-cli-one-shot-node-integration-coverage`.

### Considered and deliberately left alone

- **`--yes` is not required for an open strand.** The ticket's decision, and correct: an open
  strand's row carries no secret. The removal is still party-wide and still subject to
  delete-while-alone, and both are warned about.
- **"Not published" exits 0 even though the read is this node's unsynced view.** Exit 0 with an
  explicit warning is the right call — the alternative (non-zero for an absent row) would make
  the command unusable in idempotent scripts. The warning is asserted by a test.
- **`--json` success output drops the warnings.** Intentional: the JSON body carries `type` and
  `changed`, from which a consumer derives everything the warnings say in prose.
- **`nodeStore`'s "node has no control database" branch is untested.** Defensive only —
  unreachable inside `withConnectedNode`, which cannot yield an unstarted node. Not worth a
  fixture.
- **`strands.ts` is ~280 lines and the file name no longer matches the command name.** Under the
  size where splitting helps; a rename would be pure churn against a file this ticket already
  rewrote. Left as is.
- **No multi-node convergence coverage for removal** — already tracked as
  `backlog/debt-strand-unpublish-multi-node-convergence-test`, not re-filed.

### Tripwires (conditional; parked in code, not filed)

Both were placed by the implementer and survive review as correctly scoped:

- `strands.ts`, `applyRemove` — `NOTE:` the read and the write are not atomic; a concurrent
  removal in between makes this one a silent no-op. Harmless today: the operator gets the
  outcome they asked for.
- `subcommand.ts`, `runSubcommand` — the pre-existing repo-wide `NOTE:` that `process.exit` does
  not flush a pipe. Fine at these output sizes; matters only if a subcommand ever prints a large
  listing.

The third tripwire (`listCommand`'s stdout progress line) was removed by fixing it, above.

### Pre-existing failures

None. `yarn lint` and `yarn dep-check` are clean; the three `cadre-cli` entries in `dep-check`'s
unused-export report (`oneShotNodeConfig`, `RuntimeLive`, `RuntimeUnreachable`) predate this
ticket and are informational — the command exits 0.
