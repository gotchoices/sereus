# Machine invitations grant no ownership

A `CadreInvite` admits a machine and nothing else. The schema (version 3) has no `GrantsOwner` column, no `CadreInviteUsage.OwnerStampId` and no `OwnerKey` consent branch through a `CadreInviteUsage` row; a version-2 store refuses to start. `createCadreInvitation` takes no `grantsOwner`, every invitation defaults to 24 hours and one use, `redeemCadreInvite` writes the peer row and the usage row only, and the anchor derivation reads the owner-grant chain alone. `CadreNode.wireOwnKeyIfOwner()` never tries the node's identity key. The edge node's `joinCadre` takes a machine invitation or an owner grant (`JoinCredential`): a grant seats the owner slot's key, created when the slot is empty, through `joinWithOwnerGrant` on a switched node and `redeemOwnerGrant` on one already running in the party, and a join that would leave the founded party's strands behind is refused unless the credential is a grant. The phone, browser and NativeScript apps, the kit, the CLI, the harness, eleven scenarios and the docs follow. The implementation is `ticket(implement): machine-invitation-grants-no-ownership`; its handoff is summarised there and not repeated here.

**Major findings: none.** The change is subtractive and every consumer of the removed fields was updated; the clean typecheck is the proof that no caller still names them, and the re-pinned drift hash that the two schema copies moved together. The retained `PeerExists` clause (`P.PublicKey = new.PeerKey`) is right: it still binds a usage row to the admitted machine's own key.

**Minor, fixed in this pass.**

Rewritten: a machine invitation is refused when there is something to move, a join with an owner grant moves them, and this app's join field does not take a grant yet (the backlog ticket below).

**Tripwires, recorded as `NOTE:` at the site.**

- `edge-join.ts` → `redeemOnJoinedNode`: `joinWithOwnerGrant` already waits up to its own bound (60 s) for the key's `OwnerKey` row and wires it, and `wireJoinedOwner(node, true)` then asks again for up to the owner-step bound (60 s by default) while it is still unwired, so a row that never arrives costs both waits before the start reports `timed-out`. Fine now; if it shows up, carry `ownerWired` in the admission and skip the second wait.
- `edge-join.ts` → `redeemOnRunningNode`: a member running with no control connection is refused `alone` by the grant's local path, where the invitation path would wait for a member. Fine now, since no app can paste a grant in place yet.

**Filed.** `tickets/backlog/feat-reference-app-ns-owner-grant-join.md`: the NativeScript app's join field decodes a machine invitation only, while its refusal text for a phone with conversations of its own says to join with an owner grant, so that user has no way in. The phone and browser apps have the same gap, already owned by `reference-app-rn-owner-grants` and `reference-app-web-owner-grants`; nothing owned the NativeScript one. The site-claim grep found `debt-ns-maestro-flow-parity-gaps` naming `cadre-vm.ts` for an unrelated concern (automation ids), so this is a fresh ticket.

**Judgement calls weighed and kept.** `JoinCadreResult.asOwner` stays beside the progress event's field: it says which credential admitted the app, which is not the same as whether the key is wired (`status.owner` can be `timed-out` with `asOwner` true), and the NativeScript fake and the phone app's hook spec already carry it. The CLI refusing any `grantsOwner` field, `false` included, is right: a caller still sending it believes the field does something. `wireJoinedOwner` asking about an already-wired signer and never replacing it matches the one-signer-per-node rule and the previous behaviour once the identity default is gone. Considered and left alone: an owner grant redeemed in place on a node that runs the party but is neither a member nor an owner (a founded start whose key the party does not list, reachable only by typing another cadre's party id, which the docs already warn against) seats the key without admitting the machine, as `redeemOwnerGrant` documents; `joinWithOwnerGrant` is the right call there, and no app reaches it today.

**Tests.** None cut: the implementer's new and changed cases each pin a named contract (the removed schema branch, the 24-hour default, a redeemed device holding no owner row, the grant-seated chain in the derivation, a grant join refused by the holder's clock leaving the slot key).
