# Owner grants: integration scenarios

`owner-grant-node-api` added `createOwnerGrant`, `redeemOwnerGrant` and `joinWithOwnerGrant`. This ticket runs them across real libp2p nodes over loopback WebSocket. The household shape is the one `cadre-invite-any-member` uses: a phone-shaped owner O that listens nowhere, and one always-on member M. M pins O's key and was admitted the owner-online way.

## What landed

- **`owner-grant-without-machine.integration.ts`.** O mints a single-use grant labelled "hardware key". H, a party node on an empty store, redeems it at M with a fresh key, and the commit happens on the first pass. M and O (which did not write the row) both derive the key under `chain` provenance and list it with O as voucher. No machine row is added for H. A second holder H2 is refused `grant-spent`, `retryable: false`.
- **`owner-grant-backup-recovery.integration.ts`.** O mints a backup grant (no expiry), M holds its row, O stops and leaves M's control cohort. Fresh device F calls `joinWithOwnerGrant`, and each of its two redemptions commits on the first pass. M derives F's key, and F's machine row is vouched by F's own key. F then removes O's machine, and removes O's owner key with `revouch: { peers: [M] }`. M's anchor drops O's key and keeps F's.
- **Harness (`harness/cadre-invite.ts`, `harness/node-fixtures.ts`).**
  - `buildPartyDevice(partyId, key?)` builds an unstarted phone-shaped party node on an empty store.
  - `waitingForMember(budgetMs, label, redeem)` runs any redemption call with `waitForMember` under an abort budget. It returns the most passes any single redemption needed. `redeemWaitingForMember` is now a thin wrapper over it.
  - `machinePeerIds(node)` returns the sorted peer ids from `listMachines`.
- **Docs.** The "Owner grants" Proof line and the Testing list in `docs/architecture.md` name both scenarios. The cadre-core owner-grant spec header points at them.

## Review findings

Read the diff of `ticket(implement): owner-grant-scenarios` before the handoff, then the core API it drives (`joinWithOwnerGrant`, `RedeemOwnerGrantOptions`, `CadreInvitationReach`, the connection gate's provisional admission).

**Fixed in this pass:**

- **DRY.** The handoff said three sibling scenarios built the same unadmitted phone-shaped device that the new harness helper builds: a module function in `app-joins-cadre-by-invitation`, a local closure in `cadre-invite-any-member`, and an inline constructor in `cadre-invite-row-unreplicated`. All three now use the shared helper, and the unused `PrivateKey`/key-generation lines are gone.
- **Resource cleanup.** The implementer's `startPartyDevice` started the node inside the helper. If `start()` threw, the half-started node was never assigned to the caller's variable, so the caller's `finally` could not stop it. The three sibling scenarios had avoided this by assigning the node before starting it. The helper is now `buildPartyDevice`, which returns the node unstarted, as `buildPhoneOwner` does, and every caller assigns and then starts. `startPinningMember` has the same shape and was left as it is (pre-existing, outside this diff).
- **Overclaimed coverage.** The scenario 1 header said the run "shows [the exchange] is not cut at the provisional connection deadline". That deadline is `PROVISIONAL_ADMISSION_DEADLINE_MS` (`relayedRequestBudgetMs()`, several seconds), while H's whole redemption took under a second. So the scenario never comes near the deadline. The comment now says that H rides a provisional admission, that it finishes well inside the deadline, and that the deadline is therefore not exercised. The handoff's "Tests added" table made the same claim; it is not carried into this ticket.

**Checked, nothing to change:**

- **Pass counting.** `joinWithOwnerGrant` passes the same `options` (one `onProgress`) to both of its redemptions, and each counts its passes from 1. So `Math.max` in `waitingForMember` measures "the most passes any one redemption made", and `passes === 1` pins both. For a single redemption the pass count only increases, so `redeemWaitingForMember` behaves as before.
- **Option types.** `MemberWaitOptions = Required<RedeemCadreInvitationOptions>` is correct because `RedeemOwnerGrantOptions` is an alias of that type.
- **`reach: 'local-network'` in scenario 2.** Per `CadreInvitationReach`, this value means other machines are named, at private or loopback addresses only. That is the right assertion that the backup grant names M and so can be redeemed once O is gone.
- **The removal in scenario 2.** The `revouch` of M is required, because O's key vouched M's row. F's own row stays trusted under the "kept" rule even though O is its voucher. The assertions match `docs/architecture.md` → "How the anchor follows the owner table".
- **Docs.** `docs/architecture.md`'s Proof line and Testing list are accurate. `docs/testing.md` lists scenarios by topology and omits protocol scenarios such as `cadre-invite-any-member`, so leaving these two out is consistent. Nothing in any doc named the removed local helpers.
- **Tests.** Both scenarios pin named parts of the specification: a grant seats a key with no machine, single use, backup recovery with the issuer offline, and lost-phone removal. Neither restates the implementation or verifies a mock, so none were cut. The reviewer added none.

**Gaps carried from the handoff (not filed):**

- **Issuer offline at redemption.** No scenario covers an issuer that is offline when the grant is redeemed, then restarts and derives the grant-seated key. Grant-seated keys reach the anchor through the same `OwnerKey`-row chain derivation that `cadre-invite-any-member` covers for invitation-seated keys after a restart. This is a coverage choice, not a defect, so there is no ticket and no tripwire.
- **Multi-use backup grant.** A multi-use backup grant still live at removal time is covered only by the unit spec's removal plan.
- **The single-use race.** The race across two members already has an accepted-tradeoff `NOTE:` at `OwnerGrantUsage.Authorized`, so it was left alone.

**Tripwires:** none. No finding was "fine now, only matters if…".

**Major findings / tickets filed:** none. Every finding was minor and fixed inline.
