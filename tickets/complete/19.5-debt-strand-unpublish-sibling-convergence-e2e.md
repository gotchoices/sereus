# Complete: two-node convergence for party-wide strand removal

## What shipped

A single integration scenario,
`packages/integration-tests/src/scenarios/strand-unpublish-sibling-convergence.integration.ts`,
running two real `CadreNode`s over real libp2p:

- **Phase 0** — `bootPair('unpublish', 'ctrl', { strandWatchMs: 1_000 })`: A is owner + storage
  profile, B is a plain reader vouched by A. Connected *before* any write.
- **Phase 1** — `A.publishStrand` → B's watcher emits `strand:discovered` (B is not an owner and
  never wrote the row, so the sighting is a genuine network read). B joins from the event's
  `StrandRow` with an explicit `mode: 'bootstrap'`.
- **Phase 2** — `A.unpublishStrand`, plus a cheap sanity read on A.
- **Phase 3** — the headline: B emits `strand:stopped`; `B.getStrand` is undefined,
  `getStrands()` is empty, and B's own control-DB `queryStrands()` no longer lists the id.
- **Phase 4** — a five-poll quiet window derived from the configured cadence: exactly-once, no
  re-add, no errors.
- **Phase 5** — `A.publishStrand` again → a second `strand:discovered` on B, discovered rather
  than relaunched.

Harness change is additive: `ControlNodeOpts.strandWatchMs` → `CadreNodeConfig.strandWatchInterval`,
and a third optional `opts` argument on `bootPair` applying it to both nodes. Existing callers
untouched.

Docs: the party-wide-removal paragraph in `docs/architecture.md` and the scenario inventory in
`docs/STATUS.md` both name the scenario.

## Review findings

### Verified, no change needed

- **The convergence really is watcher-driven on B, and the assertion is not vacuous.** Traced the
  product path: `StrandWatcher.poll` (`packages/cadre-core/src/strand-watcher.ts:167`) drops the
  id from `knownStrands` and calls `onStrandRemoved` → `CadreNode.handleStrandRemoved` →
  `detachStrand`, which is the **only** emitter of `strand:stopped` besides the caller-driven
  `stopStrand`. B never calls `stopStrand`. `unpublishStrand`'s `forcePoll()` shortcut
  (`cadre-node.ts:3070`) runs on the *issuing* node only, so it cannot be what stopped B. The
  implement handoff's honest gap ("the wait resolved in 0 ms every run — could visibility have
  been forced during the cohort commit?") resolves to: the wait resolves instantly because a 1 s
  poll lands inside the multi-second `await A.unpublishStrand()`, but the mechanism is still B's
  own poll. A never-converging sibling fails the test via the 30 s `waitUntil` timeout.
- **Phase 5's "discovered, not relaunched" is real.** `detachStrand` does
  `this.sAppConfigs.delete(strandId)` (`cadre-node.ts`), so the rediscovery takes
  `handleStrandAdded`'s no-config branch. Strengthened anyway — see below.
- **The "first sibling read-back of a control-plane DELETE" claim in the docs holds.** Grepped
  every scenario for `removePeer` / `deauthorizePeer` / `isMember`: every existing delete
  read-back is on the writer (`control-write-degraded-cohort-member`) or through a single host
  client (`cadre-host-owner-node`). No other scenario reads a delete back on a second machine.
- **The architecture.md cross-reference is accurate.** `strand-unpublish.spec.ts` does contain
  both the issuing-node-convergence test and the filter-excluded test the sentence attributes
  to it.
- **No duplication introduced.** `collectStrandEvents` and `strandIdsSeenBy` are the only strand
  lifecycle-event collectors in the whole suite (grepped `strand:discovered|started|stopped`
  across `packages/integration-tests/src`) — nothing to hoist into the harness yet. The
  `finally { await B?.stop(); await A?.stop(); }` shape matches the house pattern in
  `control-db-two-node-convergence.integration.ts`, so it was left alone.
- **Harness change does not collide** with the in-flight
  `plan/10-integration-test-harness-helper-consolidation-remaining-files`: that ticket folds
  *other* files' private helpers into `node-fixtures.ts`; this added one option and one optional
  argument.
- Scenario file is 194 lines, functions are small and single-purpose, tabs per `.editorconfig`.
  No size or hygiene concern.

### Fixed in this pass (minor)

- **Phase 5 asserted only what it needed, not what it claimed.** The file's own comment says
  "discovered, NOT relaunched", but only `discovered.length === 2` and `getStrand === undefined`
  were checked; a regression that relaunched *and* re-emitted would have been caught only
  indirectly (via the wait timing out). Added `expect(events.started).toEqual([strandId])` and
  `expect(events.stopped).toEqual([strandId])` so the claim is pinned outright.
- **An untested doc claim was not listed among the deliberate exclusions.** architecture.md, same
  paragraph, says a stopped node *retains* the strand's local durable storage. This harness uses
  `MemoryRawStorage` owned by the node being torn down, so nothing outlives the stop to read
  back; proving retention needs a persistent-storage fixture. Added to the file header's
  "Deliberately NOT covered" list rather than left as a silent gap.
- **`docs/STATUS.md` still credited the sibling side to the unit spec alone.** The 2026-07-30
  party-wide-removal bullet said both sides were "pinned by `strand-unpublish.spec.ts`"; it now
  also names the new scenario. (The same bullet's "still not exercised against a real node" note
  is about the **CLI**'s `withConnectedNode` path and remains true — left as is.)
- **A wrong how-to-run note in a live ticket was costing ~2 minutes per run.**
  `tickets/plan/10-control-delete-while-alone-tombstone.md` (and, following it, the implement
  handoff) claimed a path filter "did not match on Windows", pushing everyone onto
  `vitest run -t "<name>"`, which matches the test but still imports all 36 scenario files.
  Disproved: `cd packages/integration-tests && npx vitest run src/scenarios/<file>.integration.ts`
  works — a package-relative, forward-slash path. Measured 37.9 s total for this scenario that
  way versus the ~95–120 s of import overhead the `-t` form pays. Corrected that ticket's note in
  place.

### Filed as new tickets

One product defect found, appended as an arm to an existing ticket rather than filed fresh,
because it resolves at the same site: **`tickets/fix/duplicate-strand-started-on-rediscovery`**.
That ticket's root cause is `CadreNode.launchStrand` emitting `strand:started` unconditionally
after an idempotent manager call. `CadreNode.detachStrand`, two methods away, has the mirror
defect — it emits `strand:stopped` after `StrandInstanceManager.stopStrand`, which returns early
for an id it does not hold. So a node emits `strand:stopped` for a strand it never started.

Reachable on an ordinary path, and this scenario walks straight through it: node A publishes the
strand without running it, its own watcher tracks the row, and `A.unpublishStrand` therefore
fires a spurious `strand:stopped` on A. The scenario only listens on B, so nothing here fails —
which is why it needed reading, not running, to find. `repro: static` on the arm.

### Why the full-suite failures are not this change

The suite's stale-build guard refused to start, reporting that `@optimystic/db-core` and
`@optimystic/db-p2p` dist were older than their src. Rebuilding both from `C:\projects\optimystic`
cleared the guard and let the suite run.

But `git status` in that sibling workspace shows an **uncommitted, in-flight change set** — a
concurrent agent run mid-ticket there, with modifications to `collection.ts`,
`network-transactor.ts`, `transactor-source.ts`, `coordinator-repo.ts`, `storage-repo.ts` and an
untracked new spec. The rebuild therefore compiled that half-finished work into the dist this
suite links against.

Every one of the 18 failures is a cross-node replication or convergence assertion — the exact
surface those optimystic files own — and none touches a sereus source file this change went near.
Written up for the triage pass in `tickets/.pre-existing-error.md`, with the explicit
recommendation **not** to chase them individually but to re-run once `../optimystic` is clean and
committed. Nothing was skipped, disabled, or loosened.

The full-suite run also re-executed this scenario **after** the Phase 5 assertions were added, so
those edits are covered by a green run, not just by lint.
