# Provider seed trust: owner keys pinned at container-create time — complete

## What shipped

A "seed" is the signed bundle that tells a fresh node which peers form a cadre and how to
dial them. The provider could always *deliver* one (`PUT /containers/:id/seed` →
the container's `POST /seed`, gated by a per-container bearer token), but no
provider-hosted node ever *accepted* one: whether a seed is honoured is a separate
decision made by the node against its own trusted-owner store, which is empty on a fresh
container and which nothing replicated can fill. Every seed failed with
`Signer key is not an anchored owner`.

The tenant now names its own owner key(s) on the create request; they reach the node as
`CADRE_OWNER_KEYS`, which `cadre-cli start` turns into a cold-start pinned-key trust
policy.

- `CreateContainerRequest.pinnedOwnerKeys?: string[]` — base64url ed25519 owner public
  keys, also recorded on the `Container` record (public keys, so not redacted at the API
  boundary).
- `POST /containers` validates the field as absent-or-array-of-strings; anything else is
  `400 INVALID_REQUEST` and provisions nothing. Key *encoding* is deliberately not
  checked — a malformed pin never matches a real signer and is refused by the trust
  policy, which beats a container that fails to start.
- `ContainerService.createContainer` normalizes (trim / drop blanks / dedupe) onto the
  record; `provisionContainer` reads the record and forwards into
  `OrchestratorCreateRequest.pinnedOwnerKeys`, logging when a container is created with
  none.
- `DockerOrchestrator.createContainer` injects `CADRE_OWNER_KEYS=<comma-joined>` when the
  list is non-empty, and omits the var entirely otherwise.
- Docs: `docs/architecture.md` (Control Network Seed) separates delivery from trust;
  `docs/STATUS.md` records the provider seed path as working with its coverage gap named;
  `packages/cadre-provider/README.md` gains a "Seed trust" section with a curl example.

**Isolation invariant:** pins flow only from one tenant's own create request into that
tenant's own container. There is no provider-level default tier at all (unlike push
credentials, which have one) — a provider-wide pin would let one tenant's owner seed
another tenant's node. Verified by test, and by the ownership check on every
per-container read route.

## Review findings

### Checked

Implement-stage diff read first, before the handoff summary. Covered: the create-request
type and its record counterpart, route validation and response redaction, service
normalization/forwarding, Docker env construction, the `Orchestrator` interface contract
against `cadre-host`'s implementation of the same field, `cadre-cli`'s
`collectPinnedOwnerKeys` (the consumer of the env var), both store implementations
(`MemoryStore`, `FileStore`) for round-tripping the new field, tenant isolation on every
route that returns a container, and all four docs the change touched plus the ones it
should have. Gates: `yarn typecheck`, `yarn build`, `yarn test` in `packages/cadre-provider`
(19 files / **126 tests** passed, up from 124) and `yarn eslint packages/cadre-provider/src
--max-warnings=0` from the repo root — all clean. No pre-existing failures encountered, so
`tickets/.pre-existing-error.md` was not written.

### Fixed in this pass (minor)

- **A blanks-only key list produced a pin the operator could see but the node did not
  have.** `pinnedOwnerKeys: [""]` passed validation, was recorded on the container, and
  injected as a bare `CADRE_OWNER_KEYS=`, which the CLI parses back to "trust nobody" —
  directly contradicting the orchestrator's own comment that a node told to trust nobody
  should not look configured. `ContainerService` now normalizes the list the same way the
  CLI does (trim, drop blanks, dedupe) before writing the record, so a blanks-only list is
  exactly equivalent to omitting the field. Two service tests added.
- **The stored `pinnedOwnerKeys` was never read back.** `provisionContainer` took its pins
  from the in-flight request while the record held a parallel copy — two sources of truth,
  and the flagged "a future re-provision from the record alone must read this field" hazard
  sitting open. It now reads the record, which is the normalized authority. Existing test
  retargeted (request and record deliberately disagree; the record wins).
- **Route validator used a cast where a type guard works.** `value.some(k => typeof k !==
  'string')` followed by `value as string[]` replaced with `value.every((k): k is string
  => …)`, so the narrowing is checked rather than asserted.
- **Docs named the wrong HTTP method for seed delivery.** The provider route is `PUT
  /containers/:id/seed`; `docs/architecture.md` (delivery table *and* the sequence
  diagram), `docs/STATUS.md`, and the `CreateContainerRequest` doc comment all said `POST`.
  All corrected, and the sequence diagram's step 1 now shows the pin travelling with the
  create request — the diagram previously gave no hint that trust is established there.

### Filed as a new ticket (major)

- `backlog/debt-provider-seed-accepted-by-real-node` — no test proves a real node accepts a
  provider-delivered seed. Everything green is on the provider's side of the boundary;
  `container-seed-endpoint.test.ts` stubs `fetch`, so the end-to-end claim rests on
  `cadre-host` proving the same env-var contract. If the provider's side of that contract
  drifts, every provider test still passes and every customer's first seed is silently
  refused. The ticket asks specifically for the negative case (a seed from a *different*
  owner must be refused), since that is what proves the check exists rather than is absent.

### Recorded as a tripwire, not a ticket

- Pins are settable only at create time; there is no way to change what a running node
  trusts. Fine today (recreate the container), but owner-key rotation without a recreate
  would need both an update path on the record *and* a way to push the new pin into a
  running node, because the env var is read once at start. Parked as a `NOTE:` on
  `Container.pinnedOwnerKeys` in `packages/cadre-provider/src/types.ts`.

### Considered and deliberately left alone

- **Creating a container with no pins only logs.** The implementer asked whether the
  `debug`-namespace log (off by default) is discoverable enough or whether the create
  response should carry a warning. Left as is: the absence is visible in the API itself —
  `pinnedOwnerKeys` is simply missing from the returned container and from every later
  `GET` — and adding a warning field to a success response is an API-shape decision, not a
  review fix. The provider has no severity channel other than `debug`, so raising the level
  would mean diverging from every other log in the package.
- **Key encoding is still unvalidated.** Correct as designed: rejecting an unparseable key
  at create time buys nothing a refused seed does not already report, and it would put an
  ed25519 encoding assumption into the provider that belongs in the node.
- **`cadre-host` has the same blanks-only asymmetry** in `HostProcessOrchestrator`. Not
  touched — outside this ticket's diff, and unlike the provider it records nothing, so the
  only consequence is a bare env var the CLI already reduces to no policy.

### Nothing found

- **Cross-tenant leakage**: none. `GET /containers` filters by `customerId`; every
  per-container route re-checks ownership before returning the record; there is no default
  pin tier to leak from.
- **Resource cleanup / error paths**: unaffected — the change adds no allocation and sits
  entirely inside the existing provision try/catch, which already reclaims the Docker
  container and its ports on every non-success exit.
- **Store persistence**: both stores serialize the whole record, so the new field
  round-trips with no migration.
