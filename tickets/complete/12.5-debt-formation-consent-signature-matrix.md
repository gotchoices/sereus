# Joiner-consent signature: schema-level negative matrix (complete)

Tests only — no `src/` behaviour changed, in either the implement or the review pass.

## What a joining peer signs

A peer joining a network writes its own row in `CadreControl.FormationUsage` carrying its
public key (`PeerKey`) and its own signature (`PeerSig`). Two different signatures exist
over that one table and must never be usable in each other's place:

| digest | tag | fields, in order | signed by |
|---|---|---|---|
| vouch | `'vouch'` | token, usageStampId, strandId, peerKey, disclosure | the approver (an enrolled `ValidationKey`) |
| consent | `'consent'` | token, usageStampId, peerKey, disclosure | the joining peer itself |

`strandId` is deliberately absent from the consent digest — the joiner cannot know the
strand when it signs. The schema constraint `PeerConsented` re-verifies the consent
signature on every insert; `Authorized` re-verifies the approver's vouch.

## What landed

- *the constraint itself* — the three cases moved out of `control-formation-invite.spec.ts`

- *one-field mutations* — consent minted over a different token / a different nonce than
  presented / a different disclosure text, each → `PeerConsented`; plus a spent nonce
  re-presented verbatim → `unique` on `FormationUsage.UsageStampId`. Each of the first
  three is followed by the corrected write landing, pinning the refusal to the one varied
  field.
- *action-tag disjointness* — the joiner signs the vouch digest with its own key and files
  it as `PeerSig` → `PeerConsented`; and the mirror, where the joiner's key is enrolled as
  a `ValidationKey` and the same consent bytes are presented as the approver sign-off →
  `Authorized`. Key held constant both ways, so only the tag and field list differ.
- *ValidationUrl invites* — both signatures valid → lands; stale vouch with fresh consent →
  `Authorized`; stale consent with fresh vouch → `PeerConsented`; the same pair again for a
  disclosure mismatch; and a fully-consented redemption with no vouch → `Authorized`.
- *`verifyFormationConsent` re-checks a stored row* — true for columns read back out of the
  table; false after altering each signed field; false (never throws) on garbage keys and
  signatures, empty strings, and a well-formed-but-wrong-length key.

## Why every rejection is a single-constraint assertion

`PeerConsented` is `check on insert` with no subquery, so it fires AT the insert.
`Authorized` is also `check on insert` but contains a subquery, so Quereus auto-defers it
to commit. When both would fail, `PeerConsented` surfaces — and `expectConstraintFailure`
matches ONE name. So `PeerConsented` cases pre-insert an owner-signed strand and call
`recordFormationUsage` on an invite with no `ValidationUrl` (satisfying `StrandExists`,
disarming `Authorized`'s vouch branch), while `Authorized` cases supply a consent valid
over the row's actual fields. Verified against the schema during review: correct as
described.
