# Strand nodes opt in to reactivity: the node option

## What landed

A node-local operator setting, `strandReactivity: { enabled: boolean; strandIds?: string[] }` (`CadreNodeConfig.strandReactivity`, and the `strandReactivity` key in a cadre-cli config file). `strandCohortTopicOption` in `packages/cadre-core/src/strand-reactivity.ts` turns it into `@optimystic/db-p2p`'s `cohortTopic: { enabled: true }` node option for a strand when `enabled === true` and `strandIds` is absent, empty, or names the strand; anything else yields `{}` (no `cohortTopic` key). `CadreNode.launchStrand` → `StartStrandConfig.reactivity` → `StrandInstanceManager.buildStrandRuntime` spreads it into `createLibp2pNode`. A hibernation wake rebuilds with the retained launch config, so the setting carries through. The control node never sees it. `quereus-plugin-sereus` needs no change: the Optimystic plugin reads `node.reactivityWatch` from the node `compose-strand.ts` registers.

cadre-cli checks the block (`enabled` required boolean, `strandIds` array of non-empty strings, unknown keys refused) and passes it through; README and `example.cadre.yaml` document it. `docs/strands.md` → "Change notifications (reactivity)" covers the table tag, filter rules, frozen-at-build, enable-on-every-machine, exposure on closed strands, and the proof-of-work cost. cadre-host and cadre-provider are not wired (`backlog/feat-cadre-host-and-provider-nodes-carry-strand-reactivity`). The real-network proof is `strand-reactivity-scenario`.

Commit: `ticket(implement): strand-reactivity-node-option`, plus this review pass.

Since cadre passes no `host`, every strand node with the option — phones included — is a core host: forwarder-eligible, 30 s renewal.
