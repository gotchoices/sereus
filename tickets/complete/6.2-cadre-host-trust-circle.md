## What landed

A self-contained `packages/cadre-host/src/auth/` module exposing the trust-circle substrate consumed by `cadre-host-local-ui` (and later `cadre-host-installer`).

- **`auth/types.ts`** — `TrustCircleMember`, `PendingInvite`, `TrustCircleFile`, `TrustCircleSnapshot`, `TrustCircleHandlers`, `TrustCircleError` with stable codes for HTTP mapping.
- **`auth/trust-circle-store.ts`** — atomic JSON store for `<rootDir>/trust-circle.json` (write `<path>.tmp`, rename). Caches in memory; throws `storage_error` on malformed file rather than silently wiping.
- **`auth/trust-circle.ts`** — `TrustCircleService` with `issueInvite`, `redeemInvite`, `revokePending`, `removeMember`, `isMember`, `list`. Depends on a narrow `CadreNodeLike` interface for unit testability. Also exports `createTrustCircleHandlers(service)`.
- **`auth/duration.ts`** — `parseDuration('24h')` etc. for the CLI `--ttl` flag.
- **`auth/index.ts`** — re-exports for `src/index.ts` consumers.

CLI (`src/bin/host.ts`):

- `cadre-host invite <label> [--ttl 24h] [--port 8765]` — POSTs `/auth/invites`, prints the encoded invite.
- `cadre-host trust list` — GETs `/auth/trust-circle`, prints members + pending invites.
- `cadre-host trust revoke <token-or-peerId>` — DELETEs `/auth/invites/<token>` or `/auth/members/<peerId>` (peer-ID auto-detect supports Ed25519 `12D3Koo…`, secp256k1 `16Uiu2HAm…`, and legacy RSA `Qm…` prefixes).
- `install` / `start` / `status` / `uninstall` remain "not yet implemented" stubs.

cadre-core additions:

- `SeedBootstrapService.removePeer(peerId)` — signs `digest(peerId, 'sha256', 'utf8')` with the authority key and executes a signed DELETE on `CadreControl.CadrePeer`.
- `CadreNode.removePeer(peerId)` — wrapper.

`src/index.ts` re-exports everything from `auth/`. Docs: `docs/cadre-host.md` has a "Trust circle" section; `README.md` reflects the new working commands.

## Review findings

### What was checked

- **Single-purpose / DRY / modular** — `TrustCircleService` keeps each method short and single-purpose; the `CadreNodeLike` seam keeps it testable; the JSON store reuses the orchestrator's atomic-rename pattern. ✓
- **Resource cleanup** — no long-lived handles, no listeners; nothing to leak. ✓
- **Error handling** — every entry point throws `TrustCircleError` with a stable code; the storage layer never silently wipes. ✓
- **Type safety** — no `any` (the test mock has one localised `as unknown as ReturnType<…>` for a structurally-typed mock, which is acceptable). ✓
- **Correctness** — found one real concurrency bug (see "Major findings turned into inline fixes" below).
- **Docs vs reality** — `docs/cadre-host.md` and `README.md` accurately describe what shipped, including the limited stub surface and v1 localhost-only mgmt API.
- **Test coverage** — six gaps identified and patched in this pass.
- **Build + tests** — green on both packages.

### Empty categories

- **Performance** — nothing was measured because the trust-circle is bounded by a handful of members and pending invites; the sequential `for await` over `CadrePeer` and the per-orphan-prune `save()` are documented O(N) hits that are fine at the v1 scale and were not worth optimising.
- **Security regressions** — no new attack surface beyond what the plan already accepted (localhost-only management API as the entire auth story; this is documented and out of scope to harden in v1).
- **Cross-platform concerns** — atomic rename works on NTFS via Node's `MoveFileEx`; no platform-specific paths were introduced.

### Major findings turned into inline fixes

**One-time-enforcement race in `redeemInvite`** *(real bug — fixed)*. The original ordering was `getPending` → `await acceptPhone(...)` → `removePending`. Two concurrent HTTP requests for the same token can both pass the synchronous `getPending` check before either reaches `removePending`, with the result that two distinct peerIds get authorised by a single-use token. The implementer flagged "one-time enforcement is in the service" as a known boundary; the boundary was actually broken under concurrency. Fixed by claiming the pending row synchronously (`removePending` before `acceptPhone`); if that returns false, the caller gets `already_redeemed`. Added a regression test that gates `acceptPhone` to drive both calls into the window and asserts only the winner authorises a peer (`packages/cadre-host/src/auth/__tests__/trust-circle.test.ts:189`).

### Minor findings fixed inline

- **CLI peer-ID heuristic** missed secp256k1 keys (`16Uiu2HAm…` prefix). Centralised in `looksLikePeerId()` covering Ed25519, secp256k1, and legacy RSA.
- **CLI port validation** was only applied in `invite`; ported into a shared `resolvePort()` used by `invite`, `trust list`, and `trust revoke`. Bad `--port` now exits 1 with a clear message instead of failing later with a cryptic fetch error.
- **Missing test for label-length cap** — added.
- **Missing test for `removeMember(inControl=true, inLocal=false)`** — added.
- **Stale comment** in `redeemInvite` about "consume the pending row first" — updated to describe the new claim-first ordering.

### Major findings filed as new tickets

- **`tickets/fix/cadre-host-trust-circle-e2e-verification.md`** — stand up a real CadreNode + Quereus control DB and verify (a) the DELETE-with-context syntax for `removePeer` works against the live DB, and (b) the full issue→redeem→list→remove cycle works against a real cadre-core. These were explicitly called out by the implementer as the riskiest gaps; closing them belongs to a dedicated ticket because it needs control-DB bring-up plumbing that lives in cadre-core's test harness, not in cadre-host's unit-test scope.

### Items intentionally left as-is

- **Reconstructed `CadreInvite` is sparse** (`partyId: ''`, `authorityAddrs: []`). `acceptPhone` only validates `token` and `expiresAt`, so this matches reality today; the e2e ticket above will catch any drift if cadre-core starts demanding more.
- **Lazy reaping of expired pending rows** — at trust-circle scale (handful of members) this is fine; a sweeper would be premature.
- **`list()` emits `addedAt: ''` for unlabelled CadrePeer rows.** The UI ticket can render or hide as it sees fit; changing the interface here would force a coordinated change.
- **No mgmt-API auth.** Per the plan, localhost-only binding is the entire auth story in v1; the local-UI ticket adds Fastify-layer defences if it wants them.
