# Per-node reachability in the CLI and UI

Last of three (`cadre-host-nat-per-node-mappings` → `cadre-host-nodes-announce-public-addresses` → this). The server side (status model, `PUT /nat/nodes/:nodeId/forward`, restart on new addresses) came from the first two; this ticket is the client side plus docs. `cadre-host-join-a-cadre` (plan/) depends on it and can reuse `NodeReachabilityCard.svelte` next to its QR code.

## What changed

### CLI

- **`src/bin/nat-output.ts` (new).** The `nat` printers moved out of `host.ts` (1200 lines) with the loose `NatStatusLike` mirror. `printNatStatus` prints the host lines, then DDNS (moved before the nodes, as the ticket orders it), then one block per node: `TCP` / `WebSocket` as `internal N → external M (UPnP | forwarded by hand)` or `→ not mapped (error)`, `Public` (one address per line, or `none`), `Why` (the server's `reason`), `To fix`.
- **`To fix`** is printed only for an `unreachable` node:
  - ports with no route → `On your router, forward TCP port 10008 to 192.168.1.20:10008 and WebSocket port 10009 to …, then run:` and `cadre-host nat forward <id> --tcp <external port> --ws <external port>`, naming only the unrouted ports;
  - `gateway.lanAddress` null → `to port 10008 on this machine's LAN address`;
  - CGNAT → says a router forward will not help and cadre-host cannot reserve a relay yet, then still offers the command for every port (the detection can misfire);
  - every port routed (host's public address unknown) → nothing; the reason already says to set DDNS.
- **`cadre-host nat forward <nodeId> [--tcp N] [--ws N] [--clear-tcp] [--clear-ws] [--clear]`** → `PUT /nat/nodes/:nodeId/forward`. A port is parsed by commander (`InvalidArgumentError`, 1–65535). `--tcp` with `--clear`/`--clear-tcp` is refused, as is no flag at all. Prints the node's block from the returned snapshot plus the restart note (restarts only if its public addresses changed; waits out the 10-minute per-node limit).
- **Errors.** `callJson` takes an optional `describeError` that receives the typed `{ code, message }` of an error body. `nat forward` maps `unknown_node` to `No node with id "x" runs on this host. Run \`cadre-host nat status\` to list node ids.` and anything else to `cadre-host refused the forward: <message> (<code>)`. Other commands keep the raw `cadre-host returned <status>: <body>` line.

### Server wording (one string)

- `reachability.ts`: the reason's forward hint ended "then enter the external port here", which reads wrong in a terminal. It is now "then tell cadre-host the external port(s)". The test expectation and the `types.ts` doc comment were updated to match. Nothing else on the server changed.

### UI

- **`NodeReachabilityCard.svelte` (new)**, used by Connectivity and Node detail. It shows: an optional `header` snippet, a verdict badge (`warn` for unreachable, so it matches `overall-status.ts`), a `stopped` badge, the TCP and WebSocket rows, public addresses each with a copy button, the reason, a CGNAT note (relay not available yet; enter forwards anyway if the detection is wrong), and the forward instruction. Below that is an "I forwarded these ports" `<details>` form: external TCP, external WebSocket (left out when the node has no `ws`), Clear, Save. It starts open when the node is unreachable or already has a manual forward.
  - **Form semantics.** Save sends `{ tcp, ws }` exactly as the fields read, with a blank field sent as `null`. `null` only removes a manual forward and never touches a UPnP route, so the form always shows "what I forwarded by hand". Clear sends both `null` and is disabled when no manual forward exists. The fields follow the stored forward (saved from another tab or the CLI) until the user types.
  - **Validation.** `parsePortField` (whole number 1–65535, blank allowed) refuses bad input inline before anything is sent. A `400 invalid_config` that gets through shows inline. A `404 unknown_node` shows a toast ("Node x is no longer running on this machine.") and refreshes connectivity. Anything else shows a toast.
- **`lib/reachability.ts` (new)**: pure helpers (`routeLabel`, moved from Connectivity, plus `verdictTone`, `portsOf`, `forwardInstruction`, `manualPortText`, `parsePortField`).
- **`state.svelte.ts`**: `ManualForwardPatch` mirror, `saveForward(nodeId, patch)` (the returned snapshot replaces `state.connectivity`), `copyText(text)`. The two existing clipboard copies (Settings, TokenShare) now use `copyText`, so Settings' toast reads "Copied to clipboard" instead of "Copied".
- **Connectivity page**: the host panel (status, Test reachability, UPnP toggle, DDNS form) stays. The "Manual fix" card is now either the CGNAT notice (ask the ISP for a public IP; relay not available yet; the detection can be wrong) or "N of M running nodes cannot be reached … each one below says which ports to forward", linking to the new doc section. The read-only node list is replaced by one card per node, headed by the node id (a link to its node page) and a label: "your own node" for the owner, or `lent under grant "<label>"` when the grant list is already loaded in this session (`grantLabelFor` in `lib/grants.ts`).
  - **Removed.** The CGNAT bullet suggesting Cloudflare Tunnel or Tailscale Funnel: cadre-host has no way to announce a tunnel's address except a manual forward, so the advice did not lead anywhere.
  - **No external-port field to remove.** The first ticket had already removed the single external-port field.
- **Node detail**: a "Reachable from outside" card with the same component, or "no entry yet" if the mapping table has none.
- **Home tile**: "N of M nodes reachable from outside" (running nodes), "No nodes are running yet.", or in warning colour "The running node cannot / None of the N running nodes can be reached from outside your home network." It always links to Connectivity ("Resolve →" unless all are reachable). It shows in every role, as before.
- **`ConnectivityBadge`**: `unreachable` is now `warn` (was `err`), so the host badge agrees with the header's "Attention" and with `overall-status.ts`. `overall-status.ts` itself needed no change: it already returns `warn`.
- **Events.** No change to `applyEvent`. The server already publishes `connectivity-changed` on every change to the NAT snapshot's signature, which includes each node's `running` flag, routes and public addresses (`nat-service.ts` `signatureOf`; state changes queue a pass, and every pass ends in `publish()`). So a node's spawn, its mapping completing, and its stop/start for new addresses all reach the page through `connectivity-changed` → `refreshConnectivity`. Adding a refresh on `node-state-changed` would fetch a snapshot from before the pass. The SSE row in the doc now says this explicitly.

### Docs

- `docs/cadre-host.md`: a new "Manual port forwarding" subsection (which ports, forwarded to which address, the three ways to tell cadre-host, the restart and its rate limit, a forward surviving respawns because ports are reused, the verdict not being verified, CGNAT). "Port mapping → Manual wins" links to it. `/nat/nodes/:nodeId/forward` has its own API-table row. The `connectivity-changed` SSE row names node start/stop/removal and says the SPA re-reads `/nat/status`.
- `docs/architecture.md`: the CLI list gains `forward`.
- `packages/cadre-host/README.md`: the Reachability section drops "the next step" and the stale "still to come (`cadre-host-nodes-announce-public-addresses`)" sentence and shows `nat forward`. There is a new `### cadre-host nat forward …` reference heading (required by `cli-reference.test.ts`). The `nat status` reference describes the new block. The Home and Connectivity page lines and the `/nat/*` route line were updated.

## Known gaps / things to look at

- **The forward sentence is built twice**: `forwardAdvice` in `src/bin/nat-output.ts` (ends in a command) and `forwardInstruction` in `ui/src/lib/reachability.ts` (ends in "enter … below"). Both filter for ports with `externalPort === null` and format `<Kind> port N to <lan>:N`. The UI imports nothing from `src/` today (`state.svelte.ts` mirrors server types by convention), so I kept the copies rather than add a cross-build import. If the rule changes, the server could add a structured `forwardPorts` list to `NodeReachability` and both clients would render it.
- **CGNAT plus a refused port**: the server reason for a refused (not UPnP-mapped) port still says "Forward port … on your router", while the client CGNAT note says a forward will not help. In that case the page shows both sentences. Fixing it means `describeCause` in `nat/reachability.ts` taking `cgnatDetected` into account for every cause. I did not change it.
- **UPnP still being asked** (reason "not mapped yet; the router is being asked"): the clients still print the forward instruction for those ports, as a fallback. This state lasts one router call (up to 10 s).
- **Grant labels** appear only after the Grants page has loaded `/grants-admin` in the session. The Connectivity page does not fetch grants itself ("where the page already has it").
- **Not run against a real host or router.** Everything above was checked against stubs. The obvious next check is a hand test: `cadre-host start` with a node and UPnP off, then `nat status`, `nat forward`, and the Connectivity form, watching for the address restart.
- **The cadre-host integration scenarios were not run.** No server behaviour changed except one reason string, and nothing in `packages/integration-tests` asserts that string (grepped).

No pre-existing test failures seen.

## Review findings

Reviewed the diff of `ticket(implement): cadre-host-node-reachability` first, then the handoff. Read the server side the clients call (`NatService.putForward`, `validateForwardPatch`, `NatStore.setForward`, `server/error-handler.ts`) to confirm the form and CLI semantics hold.

**Checked and correct**
- Form semantics: a blank field sends `null`, and `setForward` deletes only the manual entry for that port, so a UPnP route is never cleared by the form. A node without a WebSocket port sends `ws: null`, a no-op.
- `$effect` in `NodeReachabilityCard`: it tracks `storedTcp`, `storedWs` and `edited`, so after a save (`edited = false`) the fields re-sync from the returned snapshot, and while typing they are left alone.
- CLI: `forwardPatchFrom` conflict and empty-flag handling; `apiErrorOf` matches the `{ ok: false, error: { code, message } }` envelope and falls back to the raw body for non-JSON responses; `unknown_node` → 404 mapping exists in `error-handler.ts`.
- `ConnectivityBadge` tone now agrees with `overall-status.ts` and the per-node `verdictTone`.
- Events: no `applyEvent` change is needed; confirmed `connectivity-changed` covers node start/stop through the NAT snapshot signature, as the handoff says.
- Docs: `docs/cadre-host.md` (new "Manual port forwarding" section, API row, SSE row), `docs/architecture.md` CLI list, and the README reference headings all match the code. `cli-reference.test.ts` passes.
