# Complete: browser reference app joins an existing cadre

Landed in `ticket(implement): reference-app-web-joins-existing-cadre`, reviewed here. The web app follows the phone kit's join sequence over IndexedDB: a start record (`party-start`) names the party and whether the tab founded or joined it; the four durable node-local records are filed per party; a join records the founded party's strands as a move record, stops the node, starts it in the invitation's party, redeems there, writes the start record once admitted, wires the owner key only when the party lists it, and adopts the move; any failure before admission starts the stored party again. The Cadre page's "Join my existing cadre" card shows the tab's request, takes a pasted response or open invitation, and shows each step with the phone app's wording. A joined party never runs owner genesis, so a reload cannot seat the tab as a founder of a cadre it only joined.

## Review findings

**Read first:** the implement commit's diff, every new module in full, the store, the two Svelte cards, the e2e spec and fixture, the README and architecture diffs; then the phone kit's `node.ts` join section, `strand-move.ts` and `config.ts` side by side with the web copies.

**Checked.**

- The join sequence against the kit, step by step: the pre-switch refusals (another peer's invitation, member invitation with strands to move), the move record's write before the stop and its replace-or-remove rule, the rollback's record discard, the write of the start record only after admission, owner wiring by origin, adoption gated on a wired key, `redeemInPlace` for a second invitation in the running party. The rules agree with the kit's; the one ordering shared with the kit that has a window is recorded as a tripwire below.
- Error and teardown paths by reading: a failed `startCadre` tears down what it opened; `stopCadre` clears the node and closes the stores in a `finally`, so a rollback over a node whose `stop()` throws still starts clean; `openStores` is idempotent, so the rollback's early open of the node-local store does not double-open; a `bringUp` that throws before or after `node` is set is cleaned by either path; cancel is honoured before the stop and inside the redemption, never after admission.
- Every status check in the UI for the new `joining` status: Restart is disabled, `stop()` and `start()` ignore it, the Messages and Home effects wait for `running`, the add-device card hides itself. The diagnostics poll tolerates closed handles during the switch, as it already did across a restart.
- The e2e's discriminating power, which the handoff doubted. With the origin ignored, a reload of a joined party runs `runOwnerGenesis`: `ensureOwnerKey` inserts nothing (the party already has owner rows) but `initializeSeedBootstrap` wires the key, and Home reads `existing`, not `member`. The `home-owner` assertion catches the regression; the `isOwner()` assertion pins the row's absence. The test stays.
- Docs: README storage names (`sereus-strand-control-<encoded party id>` matches `controlStorageScope`), routes, the new section, the file map and the e2e tier list; architecture.md's two paragraphs and the package table row.

**Found and fixed in this pass (minor).**

- `JoinCadre.svelte`: the join-failure notice rendered only inside the branch shown while the node is `running`. A join whose rollback also failed left the node stopped, so the card said only "The node is not running." and the reason the join failed was lost. The notice now renders outside the status branch.
- `AddDevice.svelte`: the card re-read the owner standing only when the node became `running`. An owner grant redeemed in place (a second invitation for the party the tab already runs) changes the standing with the node still `running`, so the card kept showing `member` until the page was remounted. The effect now also depends on the owner step's outcome.
- `store.svelte.ts`: the in-place redemption logged nothing to the Activity page; it now records `join:admitted` like the switch does.
- `cadre-web.ts`: the existing note that fail-soft covers thrown errors but not a hung call now also names `wireJoinedOwnerKey`, whose deadline bounds the re-asks, not one `wireOwnKeyIfOwner` call (the kit races each call against a timer; this copy does not).
- README: the "Two databases" section still said a tab upgraded across the party-scoping change "keeps its identity, party id and trust anchor", which contradicted the new paragraph above it (the old `party-id` key is not read; such a tab starts a fresh party). Rewritten to state only what is true now: the old unscoped blocks sit in the node-local database, unread.

**Tripwires recorded (conditional, not tickets).**

- `cadre-web.ts` → `switchToParty`, at the start-record write: the record is written after the owner key is wired, as the kit's `startAndRedeem` does. With an owner grant whose row is slow to arrive, that wait can run up to 60 s after admission; a tab closed inside it reloads into the party it left while the joined party already lists it, and its targeted invitation is spent (an open invitation still works). `NOTE:` at the site says to write the record right after the redemption, here and in the kit, if this is ever hit. Kept in step with the kit rather than fixed in one copy, since the duplication ticket (`debt-web-app-repeats-the-phone-kit-join-sequence`) names drift between the copies as the failure to avoid.
- `cadre-web.ts` is 1,401 lines (`wc -l`). The implementer's `NOTE:` at the join section says to move that section to its own module if the file grows; the dissolve ticket (`reference-app-web-dissolves-left-cadre`, in `implement/`) is the growth that will trip it. Left as the trigger, not pre-empted here.

**Major findings:** none. No class-level invariant is missing: the load-bearing rules (no genesis on a joined party, adoption after wiring, record discarded on rollback) are the kit's and are mirrored exactly; the duplication itself already has its backlog ticket.

**Tickets filed:** none. No finding met the filing bar.

**Tests.** None added and none cut. The one e2e test pins the contract the ticket asked for and does discriminate the defect (see above). The move-record and start-record modules mirror the kit's, which tests its own copies; a unit test here would restate the mirror. The non-empty move path (strands carried into the joined party) is still untested in the browser because creating a strand with a control row needs a relay; it is cadre-core's `adoptStrandBundle` plus the mirrored record rules, and remains a known gap, not a regression risk introduced here.

**Considered and declined.**

- Redeeming an invitation in place on a party the tab founded (pasting one's own open invitation) would relabel the owner state from `genesis` to `enrolled`. Contrived (the tab would have to dial itself), cosmetic, and the kit behaves the same. Nothing recorded.

## Known gaps carried forward

- Moved strands are carried as rows, not opened by the tab (accepted-tradeoff `NOTE:` beside `formedStrands`).
- Two same-origin tabs share the start record; documented as unsupported in the README and `node-local-slots.ts`.
- No Retry for an incomplete move; the dissolve ticket plans it over `pendingStrandMove()`.
- The tab's one e2e covers a member join with an empty export only.
