# Owner-key labels, `addOwner` refused while alone, and the founding machine on each strand

## What was built

**Schema** (`schemas/control.qsql`, mirrored byte-for-byte in `control-schema.ts`):

- `OwnerKey.Label text null` with `constraint LabelLength check (Label is null or length(Label) between 1 and 64)`. Quereus `length` returns the JS string length (UTF-16 code units), the same measure the export's 64-character cap uses. The empty string is refused because the digest binds `coalesce(Label, '')`, so `''` and null would otherwise sign the same.
- `OwnerKey.Authorized`: the signed-add digest is now `digest('CadreControl.OwnerKey', 'add', party_id(), new.Key, coalesce(new.Label, ''), new.StampId)`. The genesis branch accepts any label. The invitation-consent branch requires `new.Label is null`.
- `Strand.FounderPeerId text null`. The owner-signed branch of `Strand.AuthorizedInsert` binds it into the digest (`…, coalesce(new.MemberPrivateKey, ''), new.FounderPeerId, new.StampId`) and requires it non-null. The consent branch requires it null. It is not pinned to a `CadrePeer` row (ticket decision: a solo founder publishes before its own row exists).

**Writers and readers** (`control-database.ts`):

- `ownerKeyAddMessage(partyId, key, label, stampId)`. `ownerKeyLabel()` is exported and idempotent: it trims, stores a blank label as null, and refuses one over `OWNER_KEY_MAX_LABEL` by name. `insertOwnerKey(key, label?)`, `ensureOwnerKey(key, label?)` and `insertOwnerKeyVouched(key, ownerKey, sign, label?)` all go through it.
- `revouchOwnerKey` reads the live row through `queryOwnerKeyRows(false)` and re-adds it with the same label. It shares the signed-add statement with `insertOwnerKeyVouched` via `execOwnerKeyVouchedInsert`.
- `queryOwnerKeyRows` selects `Label`, and `OwnerKeyRow.label` is new. That row type is the listing reader the ticket asked for: it already carried key, stamp and vouch columns, so no separate reader was added.
- `insertStrand` writes `FounderPeerId` as the control node's own peer id and signs it. Callers' signatures are unchanged. `queryStrand` / `queryStrands` read the column through one `strandRow` mapper. The consent insert writes both founder columns as explicit nulls.

**Read side** (`peer-authorization.ts`, `owner-anchor-sync.ts`): `ownerKeyAddDigest(partyId, key, label, stampId)` and `verifyOwnerKeyVoucher(partyId, key, label, stampId, vouchOwner, vouchSig)`. Both are public exports, and their signatures changed.

**`CadreNode`**:

- `addOwner(publicKey, { label? })`. The service's approval text names the label. It throws `OwnerKeyAddRefusedError` (code `alone`, new module `owner-keys.ts`, exported) before any write when `committedAlone()` is true and `authorizedControlPeers.size > 0`. The private `refuseOwnerKeyWriteAlone(key)` holds the rule, so `machine-removal-leaves-owner-keys` can reuse it for `removeOwner`'s re-vouch.
- `listOwnerKeys(): Promise<CadreOwnerKey[]>` returns `{ key, label, vouchedBy, heldHere, trusted }` through `describeOwnerKeys` in `owner-keys.ts`. `trusted` means the key is in this node's trusted-owner anchor.
- `isSelfFoundedRow` compares `FounderPeerId` with this node's peer id; null is never self-founded. The "one owner key per machine" NOTE is gone.
- `publishStrand`'s desired row carries `FounderPeerId`.
- `strandRowMismatches` still compares only `(Type, MemberPrivateKey)`; its doc now names both founder columns as provenance.
- `adoptStrandBundle` needed no code change, because it publishes through `publishStrand`, which writes the adopting node's own peer id.

**Other changes**:

- `OWNER_KEY_EXPORT_MAX_LABEL` is renamed `OWNER_KEY_MAX_LABEL`. It is a public export, and the old name had no users outside cadre-core.
- Every fixture that builds a `StrandRow` now sets `FounderPeerId`: across cadre-core, cadre-cli, integration-tests, and the reference apps (rn, web, ns).
- Specs that hand-build owner-key or strand digests were updated to the new field lists.
- `control-read-routing.spec.ts` matches on the owner-key query's SQL text, so its marker now includes `Label`.
- The backlog ticket `debt-owner-key-add-while-alone-has-no-reissue` is deleted; this ticket folds it in.
- Docs:
  - `architecture.md`: the `OwnerKey` and `Strand` control-table rows; "Writes made while alone"; "Re-vouching first"; "The founder rule"; the second-identity bullet under "An app joins an existing cadre"; Strand Membership Bootstrap ("Founder-ness is persisted on the row", "Plumbing", the closed-strand e2e paragraph); Implementation Status → Owner Key API.
  - `strands.md`: the "Offering" paragraph.

## For the reviewer: known gaps and judgment calls

- **Alone check, then approval.** `addOwner` refuses before it opens the owner approval. If the last connection drops while the user approves, the add still commits alone; this is logged, and a `NOTE:` in `addOwner` says what to do if that window ever loses a key in practice.
- **Re-vouch while alone.** `removeMachine`'s owner re-vouch still only logs when it commits alone. The doc comment and `architecture.md` → "Re-vouching first" now point to `machine-removal-leaves-owner-keys`, which moves the re-vouch to `removeOwner` with the same refusal.
- **Two specs stopped calling `addOwner`.** In `cadre-node-owner-signer.spec.ts` and `cadre-node-remove-machine.spec.ts`, `addOwner` became `db.insertOwnerKeyVouched`. Both specs have an authorized sibling and no connection, so the refusal would fire. `machine-removal-leaves-owner-keys` rewrites both specs.
- **Behaviour change in `resolveStrandPartyKey`.** Founder-ness no longer waits for the owner signer. On restart, a watcher launch on the founding machine before the embedder wires its signer now founds instead of joining. If that closed strand also lacks its `StrandPartyKey` (a publish interrupted between the row and the mint), `ensureStrandPartyKey` throws "owner signer is not initialized". The launch fails, and the watcher retries on its backoff until the signer is wired. Previously this case came up as a joiner and skipped the heal. It is rare, and it heals, but it is louder than before.
- **Domain-separation spec weakened.** In `control-authorization-domain-separation.spec.ts`, the `OwnerKey` arms no longer isolate the domain tag: the owner add digest now has one more field than the `ValidationKey` / `CadrePeer` digests it is compared with. The cases still pass and the tag is still there; they just no longer prove it is the tag doing the refusing.
- **Public API changes, no compatibility shims** (per the project's no-backwards-compat rule): `addOwner`'s second argument is now `options`, `SeedBootstrapService.addOwner(key, label?, sign?)` takes the label before `sign`, plus the two digest helpers above and the constant rename.
- **Older control stores.** The constraint text changed, so a control store from before this ticket cannot warm-start (`docs/architecture.md` → Control Network). Under the no-backwards-compat policy such a party is recreated. Nothing in the code handles it.
- `FounderPeerId` is not checked against `CadrePeer`; this is the ticket's decision, recorded in the schema comment and the docs.
- **Pre-existing failures** recorded in `tickets/.pre-existing-error.md`, neither caused by this diff:
  - The `reference-app-ns` typecheck fails because `../optimystic`'s `IRawStorage` gained `flush` / `whenDurable` / `durability`.
  - The `control-concurrent-same-pk-insert` publish race fails because the scenario wires no owner signer on B, which `owner-signing-through-one-signer` now requires.

## Use cases to exercise

- A solo founder runs `addOwner(backupKey, { label: 'paper backup' })` with no connection. The row commits with its label, and `listOwnerKeys` shows it as trusted and not held here.
- An owner phone in a party with an always-on node, offline: `addOwner` throws `OwnerKeyAddRefusedError` with code `alone`, and no row is written. Back online, the same call commits.
- A relayed add approval re-presented with a different label, or with none, is refused by `OwnerKey.Authorized`.
- Redeeming an owner-granting invitation seats an unlabelled owner row. A consent insert carrying a label is refused.
- Two machines hold the same owner key (one imported it from an export). The machine that published the strand founds it; the other attaches as a joiner and writes no `Header`.
- Restart, hibernation wake and the watcher re-launch all derive founder-ness from `FounderPeerId` on every launch, whether or not an owner signer is wired.
- An app's strands moving to another cadre (`adoptStrandBundle`): the adopting app node names itself as founder, and the bootstrap over the existing `Header` writes nothing.
