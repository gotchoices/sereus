# The control reconcile pass runs on change, with a 2-minute backstop

## What was built (implement stage, `ticket(implement): control-reconcile-woken-by-changes-reads-once`)

`CadreNode.reconcileControlCohort` is the control network's upkeep pass (gate refresh, first self-record publish, delegate grants, strand address books, reap, ledger marker, joined-strand publication, sibling dials). It used to run on a 15 s `setInterval`. It now runs on a `scheduleRuns` schedule from `table-change-watch.ts` (single-flight runs, one timer set), and only when something it acts on changes:

- **Gate watch.** `start()` takes `controlDatabase.watchMembershipTables(…, { label: 'membership-gate' })` right after the membership listener is wired: a `watchTables` on the seven tables the control database's membership views copy (`CadrePeer`, `OwnerKey`, `Revocation`, `CadreInvite`, `CadreInviteUsage`, `OwnerGrant`, `OwnerGrantUsage`), so the list lives only in `ControlDatabase`. Its run (`onMembershipGateTablesChanged`) awaits `refreshMembershipGate('table-change')`, then triggers the reconcile schedule. A replicated revocation therefore hangs up the removed machine within the 50 ms coalescing window, without waiting behind a pass that is spending its dial budget.
- **Reconcile schedule.** `controlReconcileRuns` replaces `controlCohortReconcileTimer`, built in `startRecordRefresh` with `backstopMs = network.controlCohort.reconcileMs ?? DEFAULT_CONTROL_COHORT_RECONCILE_MS` (now 120 s). Its run waits for any pass in flight and then calls `reconcileControlCohort()`, so a change that arrived while a pass was reading is never dropped by joining that pass. Explicit callers keep today's contract and join an in-flight pass.
- **Triggers.** The eager start pass (`trigger(0)` after `startRecordRefresh`), `self:peer:update`, every gate-table change, and a control `connection:open` or `connection:close` whose remote peer is in `authorizedControlPeers` (`onControlSiblingConnectionChange`; on open it first calls the now-public `ControlDatabase.invalidateMembershipViews()`, so a machine that was offline while that sibling committed reads storage on the pass the connection starts). A connection to a relay, a bootstrap node or another party's machine starts nothing.
- **Wakes a pass arms.** `runReconcileControlCohort` returns a private `ControlCohortPassOutcome` (`dialed` plus `unconnected`). The wrapper `runReconcileControlCohortAndArmWake` advances or resets `reconcileRedialStreak` and triggers the schedule for `nextReconcileWakeMs(...)` (`control-cohort.ts`): the redial `min(15 s × 2^(streak − 1), backstop)` and the earliest strand-address due time later than the pass's start when it is sooner than the backstop; the smaller wins, `undefined` otherwise. The public `ControlCohortReconcileResult` (`{ dialed }`) is unchanged.
- **Backstop.** `DEFAULT_CONTROL_COHORT_RECONCILE_MS = 120_000`, documented as the backstop with a `NOTE:` on machines that take no storage event for a change.
- **Teardown.** `stopRecordRefresh` disposes the schedule and resets the streak; `cleanup` disposes the gate watch before `setMembershipChangeListener(null)` and `controlDatabase.close()`.
- **Declined restructure.** The pass still makes its own membership reads, all served from the membership rows view. The NOTEs in `runReconcileControlCohort` and on `strandAddrRefreshTargets` state that cost and that sharing one row set across the pass was declined.

A local membership write's second gate refresh (from the gate watch, 50 ms after the awaited listener's) is not served from the view: the listener's refresh runs under the control write lock, so its load is returned but never kept (`membership-view.ts`), and the watch's refresh is the read that refills the view. It is not an extra storage read; some read would have had to load the view after the change anyway. The consult-budget spec's genesis move (+4 consults, −3 at founding) is this effect, documented in that spec's `BASELINE_UPSTREAM` paragraph.

## Review findings

The review ran in three passes. The first two (`ticket(review): control-reconcile-woken-by-changes-reads-once`, two commits) read the implement diffs and every touched file, fixed what they found, and were then refused every vitest run by the stale-build guard, because `@optimystic/db-p2p`'s `dist` was older than its source. The third pass, this one, ran once the sibling's build was fresh again, read the code as it stood after the three later tickets that touched `cadre-node.ts`, and ran the validation list the first passes left.

### Checked by reading and reasoning, no defect found (first two passes)

- **Scheduler semantics.** `scheduleRuns` arms a timer on `trigger` even while a run is in flight (`fire` sets `rerun` only when the timer fires mid-run), and `clearWakes` runs at fire time, so a wake `armReconcileWake` arms from inside a scheduled run survives that run's settle; `settled()` then re-arms the backstop. A `trigger(0)` from inside a run fires on the next macrotask, after the run has settled. The scheduled run's "await the in-flight pass, then start a fresh one" cannot join a pass that began before the change.
- **No self-wake loop.** `refreshAuthorizedControlPeers` writes no gate table, so a gate-watch refresh never re-triggers the watch. The pass's own writes (first self-record, marker, reap) wake exactly one follow-up pass, which writes nothing.
- **Revoked-sibling close.** The remover's refresh replaces `authorizedControlPeers` before `hangUpRevokedControlPeers` closes the connection, so the resulting `connection:close` starts no pass. A machine that was itself removed and does not yet know keeps redialing its siblings, each provisional admission lasting the 28.5 s deadline; the period and the dial count match the old timer's. Recorded as a tripwire (below).
- **Teardown order.** `cleanup` calls `stopRecordRefresh` (disposing the schedule and removing the connection listeners) before the control node stops, so the closes teardown causes trigger nothing; the gate watch is disposed before the membership listener is detached and the database closes.
- **Write lock.** Neither new subscription runs consumer code inside a commit: `watchTables`' handler only arms a timer; the reconcile schedule has no subscription.
- **Strand-address wake.** Due times a pass stamps are later than its start (10 min on an answer, ignored as beyond the backstop; 60 s on a failure, woken for). Entries at or before the start survive only when the pass skipped the read for zero connections, and the rule ignores them, so no spin.
- **Docs.** Every stale cadence claim in `docs/`, both READMEs and the source was gone after the first pass; the eight remaining ones were in test and harness comments (fixed).

### Found and fixed in the first two passes (minor)

- **A sibling with no dialable address ran the redial ladder.** `dialControlSibling` returned `false` both for a failed dial and for a sibling it could not dial at all, and the pass counted either as `unconnected`, so a phone member with no dialable address would have armed three passes (15 s, 30 s, 60 s) that dial nothing after every change. Fixed: `dialControlSibling` returns a `SiblingDialOutcome` (`'connected' | 'failed' | 'undialable'`) and only `'failed'` counts.
- **The seven-table list was written twice.** `cadre-node.ts` carried a copy of the keys of `ControlDatabase.membershipViews`. The control database now hands out the watch (`ControlDatabase.watchMembershipTables`), so the gate hears exactly the tables the views copy by construction.
- **`docs/architecture.md`** → "How the snapshot refreshes" contradicted the code on which refresh refills the view (rewritten); "The automatic reap sweep" said "per tick" (now "per pass"). Stale cadence comments in `packages/cadre-core/README.md`, four specs, `node-fixtures.ts`, four scenario headers and `control-trio.ts` reworded; no assertion changed.

### Found and fixed in this pass

The first run of the validation list failed three of the nine scenarios. Each was traced with `DEBUG='sereus:cadre:node,optimystic:db-p2p:coordinator-repo*'` logs (in `tickets/.logs/`, prefix `control-reconcile-woken-by-changes-reads-once.review2.`).

- **Regression (major, fixed here rather than filed, since it is this ticket's own change): the membership rows view inherited the 2-minute backstop.** `MEMBERSHIP_VIEW_MAX_AGE_MS` was defined as `DEFAULT_CONTROL_COHORT_RECONCILE_MS`, so raising the backstop from 15 s to 120 s also raised the view's maximum age. The implement and first review passes reasoned that the reconnect invalidation covered every in-cohort case; it does not cover a machine that is online and in the block's cohort but that the writer could not reach when it committed (one side of a NAT pair). Such a machine's storage takes no event, nothing drops its view, and it serves the stale row for 2 minutes. `control-cohort-three-node-isolation` and `control-cohort-edge-carries-data` build exactly that shape: B's lookups of C's row returned the owner-vouch revision (no address, no signature) for the whole 45 s wait, 199 times in one run, with no read-repair on B because B never read storage. Before this ticket the view aged out every 15 s, so the next pass's read consulted the cohort. Fixed: `MEMBERSHIP_VIEW_MAX_AGE_MS` is its own constant, 15 s, longer than Optimystic's 10 s read-repair window (so a reload consults instead of being served locally) and shorter than any backstop (so the backstop pass, the only reader on an idle party, always reloads). The staleness bound for such a change is therefore the backstop, as the `DEFAULT_CONTROL_COHORT_RECONCILE_MS` NOTE now says, and the idle-minute saving is unchanged because the reload rate on an idle party is the pass rate. The NOTEs in `membership-view.ts` and `control-cohort.ts`, the `reconcileMs` doc in `types.ts`, and `docs/architecture.md` ("Maximum age", "What starts a pass") now name the unreachable-from-the-writer case. The ladder in *Before you file a ticket* was climbed: the class is "a bound that follows another constant for a case the other constant does not cover", and the fix is the representation change (an independent constant with its two bounding reasons stated), not a point fix.
- **Test choreography: `strand-always-on-replica-hosts-cross-party-join`.** The always-on machine's boot timer writes its `CadrePeer` record again 1 s after start (the write `new-machine-self-record-written-once` kept, see that ticket). That write replicates to the phone, whose gate watch, new in this ticket, starts a pass that published the join before step 1 read it ("join recorded on the phone: expected [] to deeply equal [strandId]"). The scenario's own note predicted the race. Fixed in the scenario: `enrollAlwaysOn` waits until `ALWAYS_ON_BOOT_WRITE_SETTLE_MS` (2 s) after the machine's start before returning, so the pass the write starts is drained by the `freshReconcilePass` the test already runs; the header rule and the step-1 note say so.
- **Test attribution: `control-cohort-edge-carries-data`.** Step 8 asserted the carry pin (coordinator pinned to C for B's poll read) had been consulted. The pass that the B→C `connection:open` starts now drops B's views and its storage reads consult the cohort over the new edge, so R1 lands on B before the poll's first read, which is then served locally with no coordinator lookup (debug run: read-repair on B 27 ms after the open, table change 17 ms later). The carry still crossed the only connection B holds, which every per-poll invariant and the connection-identity check still prove. Fixed in the scenario: the carry pin stays (for the run where the poll's read comes first), its call count is no longer asserted, and the header's PIN SCOPING explains why.

### Why the `openingPass` assertions were kept

The ticket suggested asserting only that B holds a connection to C after the explicit pass. The stronger attribution holds, now confirmed by the runs: B's harness dial gate denies every dial to C outside `dialsToC.reconcile()`, passes are single-flight, and a scheduled run that overlaps an explicit call either is joined by it (its result, including `dialed`, is then recorded as the explicit call's) or waits for it and starts after the gate has shut again. The debug logs show B's own change-driven and 2 s backstop passes dialing C and being refused by the gate throughout, with the explicit pass the only one to open the link.
