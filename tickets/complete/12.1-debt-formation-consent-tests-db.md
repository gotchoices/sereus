# Complete: joiner-signed formation records — DB-level test sweep (part 1 of 2)

Test-only follow-up to `debt-formation-consent-core` for the three specs that drive
`ControlDatabase` directly. The rule under test: every `CadreControl.FormationUsage` row
carries the JOINER's own signature over a consent digest of (`Token`, `UsageStampId`,
`PeerKey`, `Disclosure`), verified against the row's `PeerKey` by the schema's
`PeerConsented` check-on-insert constraint. The specs previously passed a bare `peerId`
string; they now mint a real ed25519 keypair and sign.

## What landed

- New `test/formation-consent-helper.ts` — `mintJoiner()`, `signJoinerConsent()`,
  `mintConsent()`; the last returns a spreadable `{ peerKey, usageStampId, peerSignature }`.
- `control-formation-invite.spec.ts` — all `peerId:` sites converted, `rawInsertFormationUsage`
  reworked to the 8-column row shape, local `Redemption` interface extended with the joiner's
  key material plus a `reconsent()` re-signing helper, and a new
  `FormationUsage.PeerConsented joiner-consent branch` describe (3 cases).
- `control-revocation-replay.spec.ts` — nine formation call sites converted. `CadrePeer`
  `peerId` usages are a different column and were correctly left alone.
- `control-formation-recorder.spec.ts` — abort-path fixtures carry the consent triple as
  literal placeholder strings; `mintUsageStampId` dropped from the fake DB (the method no
  longer exists in production — the joiner mints the nonce).

## Review findings

### Verified against the source, not taken on trust

The implementer flagged three claims in the new `PeerConsented` describe as unverified.
All three were checked against `src/control-schema.ts:490-616` and `src/control-database.ts`:

- **`PeerConsented` is `check on insert`** (`control-schema.ts:608`) and verifies
  `new.PeerSig` against `new.PeerKey` over the `'consent'`-tagged digest of exactly
  (Token, UsageStampId, PeerKey, Disclosure). The seating-rollback case's premise holds:
  the constraint fires at the usage insert *inside* `redeemInvitation`'s explicit
  transaction, so the strand insert that preceded it rolls back with it. Confirmed by the
  test's own strand-count and usage-count assertions, which pass.
- **The single-rejector assumption holds.** `expectConstraintFailure` matches ONE constraint
  name, so a second constraint firing first would redden the test. The forged-consent case
  pre-inserts an owner-signed strand (satisfying `StrandExists`) and uses an approver-free
  invite (so `Authorized`'s ValidationUrl branch cannot fire).
- **Neither write path validates `peerKey` in TypeScript** before the insert
  (`control-database.ts:1363-1492`), so nothing preempts the CHECK and the tests reach it.

### Fixed in this pass (minor)

- `rawInsertFormationUsage` accepted the three consent fields as three independent optionals
  and non-null-asserted the missing ones. Supplying a subset would have inserted `undefined`
  for the rest and failed every such case on `PeerConsented` rather than on the constraint it
  meant to pin. The triple is now all-or-nothing at the type level
  (`JoinerConsent | { usageStampId?: undefined; peerKey?: undefined; peerSignature?: undefined }`),
  so a subset is a compile error. No call site was supplying a subset, so no behavior changed.
- `formationConsentMessage`'s doc comment (`src/control-database.ts:193`) still said "nothing
  signs or checks these bytes yet" — untrue since `debt-formation-consent-core` landed.
  Sentence removed.
- `approvalDemandingDatabase`'s doc comment in the recorder spec still advertised "plus the
  nonce mint" after `mintUsageStampId` was deleted from the fake. Corrected.

### Recorded as tripwires (conditional; NOT filed as tickets)

## Settled design — do not re-open

- Nonce reuse is prevented by `UsageStampId` being `unique`; the verbatim-replay case pins it.
- A ValidationUrl invite needs BOTH signatures over the same nonce and the same disclosure.
- A race loser's consent stays re-presentable under a new use number — `UseNumber` is outside
  the consent digest.
- `StrandId` is deliberately outside the consent digest: the joiner cannot know it when it
  signs, and the responder cannot substitute one (bound invites are pinned by `Authorized`,
  unbound invites mint fresh).
