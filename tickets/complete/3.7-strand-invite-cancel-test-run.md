# Cancel + list outstanding invitations — complete

Shipped across five runs: schema (`bug-strand-invite-no-revocation`, which added
`Strand.CancelledInvite` and `ConsumedInvite.NotCancelled`), source
(`strand-invite-cancel-writer`), docs (`strand-invite-cancel-tests-docs`), tests
(`strand-invite-cancel-tests`), first test execution (`strand-invite-cancel-test-run`),
and this review pass.

## What shipped

A closed (private) strand's managers can kill an outstanding invitation and enumerate
which invitations are still redeemable.

- **`cancelInvite(db, { managerKeyPair, inviteKey })`** files one permanent
  `Strand.CancelledInvite` tombstone, manager-signed over
  `digest('Strand.CancelledInvite', 'cancel', InviteKey)`. The `Invite` row is left
  alone — cancellation is a tombstone, not a delete, because `Invite` carries no
  per-row nonce and a deleted row could be re-created by replaying the captured issue
  signatures. Repeat calls are a quiet no-op (restart-safe). `Immutable` makes
  un-cancelling impossible; re-inviting someone means a fresh `issueInvite`.
- **`ConsumedInvite.NotCancelled`** is the enforcement point: redeeming a cancelled
  invitation is rejected at commit, and since `Member.Authorized`'s invite branch needs
  a same-transaction fresh `ConsumedInvite` row, the whole join rolls back — no
  half-joined member.
- **`listOutstandingInvites(db, nowMs?)`** computes the redeemable set (`Invite` minus
  consumed minus cancelled minus expired). "Outstanding" is not a column: `Strand.Invite`
  is insert-only and stateless. Expiry is exclusive — dead *at* the expiry instant,
  matching the on-engine `NotExpired` gate.
- **`StrandMemberVerifier.isAuthorizedToJoin`** shares that computation for its
  "is the door open" pre-flight, so it no longer reports a door `NotCancelled` will slam.

Removal does **not** cascade into cancellation, by design: an invitation names no invitee,
so the strand cannot tell which invitations a departing member holds. Cancelling is a
separate, explicit manager step. Invitee binding is `feat-strand-invitee-bound-invites`
(backlog).

## Review findings

### Checked

Read the four implement diffs (`bbf3ead`, `4a304c5`, `fe35053`, `15622b1`) and the schema
they build on (`ad60eaa`) before the handoff summary. Reviewed for: single purpose,
DRY, error handling, type safety, resource cleanup, source hygiene (file size, comment
density, function length), doc accuracy, and test coverage across happy path / edge / error /
regression / interaction. Re-derived the two claims the feature's correctness rests on
rather than taking them from the handoff:

- **Lexical expiry comparison is chronologically correct.** `canonicalDatetime` emits
  `YYYY-MM-DDTHH:MM:SS[.frac]`; the fraction only ever *appends*, so the shorter string is
  a strict prefix and `<=`/`>` order correctly at mixed granularity. `listOutstandingInvites`'
  JS `expiration <= nowCanonical` (skip) is the exact complement of the schema's
  `I.Expiration > context.Now` (pass). Verified consistent, not just asserted.
- **The cancel approval cannot be cross-replayed.** The digest binds no strand id and no
  `StampId`, which would normally be a replay surface — it is safe only because
  `Invite.Key` is a freshly generated ed25519 public key, so no two strands (and no two
  invitations) ever share one. Confirmed against `issueInvite`.

Verifying the "green on never-executed code" claim was **not** repeated — the predecessor's
three-way attack (verbose reporter naming all tests, captured constraint-message text,
two-mutation coverage proof on `listOutstandingInvites` with a byte-for-byte restore) is
documented well enough to audit, and re-running it would have bought nothing.

### Found and fixed in this pass (minor)

- **A test comment described an enumeration the test never performed.**
  `strand-member-revocation.spec.ts` said "the manager enumerates what is still
  redeemable and kills the spare" but never called `listOutstandingInvites`. Now it does,
  asserting the spare is the sole candidate — which also pins the operator workflow
  (removal reports nothing about which invitations the departing member holds) in the one
  test where that workflow is the point.
- **Nothing pinned `NotCancelled` to the *specific* invite key.** An unkeyed
  `not exists (select 1 from CancelledInvite)` — one dead invitation freezing the whole
  strand's admissions — would have passed the *entire* suite: every rejection test has
  exactly one invite, and every sibling positive test has no tombstone at all. Added
  `cancelInvite` → "cancelling one invite leaves a SIBLING invite redeemable"
  (`strand-membership-invite.spec.ts:481`), which consumes the survivor after the
  tombstone lands. This is a real coverage hole, not a hypothetical: the mutation pass
  covered only `listOutstandingInvites`, whose JS is where the schema clause was *not*.
- **`listOutstandingInvites` documented an ordering nothing provides.** Its `@returns`
  promised results "in storage order" while `scanInviteKeys` two functions above states
  the scans guarantee only a *superset* of live rows. Softened to no-guaranteed-order,
  with a pointer to sort by `expiration`. (This also retires the handoff's "storage order
  is effectively untested" gap — the right resolution was to stop claiming it, not to
  test it.)
- **`OutstandingInvite.expiration`'s form was unstated.** The API takes epoch-ms in
  (`issueInvite`) and hands a canonical `datetime` string back, which a first caller would
  plausibly feed to `Date.parse` — it has no zone suffix. The field now names its format
  and says why the stored form is deliberate.
- **Two stale table enumerations the docs run missed.** `strand-schema-drift.spec.ts`'s
  header listed the `verify()`-bearing tables without `CancelledInvite` or `Revocation`
  (understating what the drift guard protects). `docs/reference-app-rn.md`'s open-vs-closed
  table listed strand tables without `CancelledInvite` *or* `Revocation`, and claimed an
  open strand has "Header only" — every table is declared on every strand; what differs is
  which ones can be populated. Both corrected.

### Recorded as tripwires, not tickets

- **Whole-column reads per call.** `cancelInvite`'s idempotence guard reads every cancelled
  key to answer one membership question, and `listOutstandingInvites` reads both marker
  tables per call. Fine at strand scale; a filtered read is only possible once the
  networked point-lookup gap closes. Parked as a `NOTE:` on `scanInviteKeys`
  (`strand-membership-writer.ts:555`).
- **`isAuthorizedToJoin` materialises the whole outstanding set to answer non-empty**,
  where it used to run one `select count(1)`. Deliberate — one shared definition of
  "outstanding" beats a second drifting copy of the three exclusions — but worth a
  short-circuiting variant if the pre-flight ever runs hot. Parked as a `NOTE:` at the call
  site (`strand-member-registry.ts:96`).

### Deliberately not done

- **No test for `cancelInvite` on an open strand.** The handoff flagged this as an
  untested `OnlyClosed` path and invited disagreement. It is in fact **unreachable**:
  `Invite.OnlyClosed` and `Manager.OnlyClosed` mean an open strand can hold neither an
  invitation to cancel nor a manager to cancel it. `CancelledInvite.OnlyClosed` is
  defence-in-depth against a schema that lost those two, so a test would pin the wrong
  thing. Closed as not-a-gap rather than left open.
- **The sibling bare-constraint-name ambiguity in `strand-member-revocation.spec.ts`**
  ("rejects a revocation authorized by a manager seated in the SAME transaction") still
  has the two-candidate `Authorized` ambiguity that `15622b1` fixed on the cancel side.
  Left alone: outside this ticket's diff, and the reasoning is already parked as a comment
  at the fixed site (`strand-membership-invite.spec.ts:527`) where the next person writing
  such a test will meet it.
- **`cancelInvite`'s insert and the `NotCancelled` clause remain un-mutation-tested**
  (mutating the schema means rebuilding the plugin package). Their evidence is the captured
  constraint-message text plus, now, the sibling-invite test above — weaker than the
  `listOutstandingInvites` mutation proof, but no longer resting on message text alone.

## Known residuals (tracked elsewhere)

- **An invitation is a bearer credential.** It names no invitee, so a revoked member
  holding an unspent, uncancelled invitation still re-admits itself — pinned as deliberate
  by `strand-member-revocation.spec.ts`'s "bearer semantics" test, so a future reader can
  tell "open by design" from "regressed". Binding an invitation to its invitee is
  `feat-strand-invitee-bound-invites` (backlog).
- **Cancellation must propagate before the holder redeems.** A holder consuming on a node
  that has not yet seen the tombstone still gets in — the same convergence class as the
  `NotRevoked` / `MinOneMember` / `MinOneManager` local-visibility notes in
  `schemas/strand.qsql`. Not solved here; noted on the table.
- **`CancelledInvite` only grows** — one row per cancellation, plus any junk a manager
  files (there is deliberately no `InviteExists` gate, so a node that has not converged on
  the `Invite` row can still record a cancellation; refusing it would fail *open* on a
  security control). Noted on the table in `schemas/strand.qsql`.
- **No CLI or host UI surface.** Nothing in `cadre-cli`/`cadre-host` calls `issueInvite`
  today, so cancellation is library surface only.
