# CLI config surface for node roles

`node-roles-in-cadre-core` landed `CadreNodeConfig.roles?: Partial<NodeRoles>` and `resolveNodeRoles`. This change gave cadre-cli the same surface and shows the result in `status`. Built in `ticket(implement): cadre-cli-config-sets-node-roles`; reviewed and amended in this ticket.

## What landed

**Config block.** `CliConfig.roles?: Partial<NodeRoles>`, checked by an `objectOf<Block<'roles'>>` table in `schema.ts` with no required keys — `alwaysOn` and `strandCohortMember` as `booleanValue`, `overlayTier` and `reactivity` as `oneOf` over cadre-core's own unions. `roles` is in the root field table. Because `FieldTable<T>` is `{ [K in keyof T]-?: … }` and `oneOf<T>` takes `Record<T, true>`, a role or a role value added in cadre-core without a line here fails to compile.

**Environment.** One variable per role in `ENV_MAPPINGS` — `CADRE_ROLE_ALWAYS_ON`, `CADRE_ROLE_OVERLAY_TIER`, `CADRE_ROLE_REACTIVITY`, `CADRE_ROLE_STRAND_COHORT_MEMBER` — so overriding one role does not mean restating the other three, and each leaf keeps its own attribution in the validator's report. No new `EnvKind` was needed.

**Pass-through.** `roles: config.roles` at both construction sites: `buildNodeConfig` (the long-running node) and `oneShotNodeConfig` (`cadre enroll`, `cadre strand`, ...). The CLI does not duplicate cadre-core's `strandCohortMember: false` refusal; the schema accepts it and `CadreNode`'s constructor rejects it, naming the key as the config file spells it.

**Status.** The resolved roles, not the overrides: `HealthServerOptions.roles` and `HealthStatus.node.roles` (`/status`), `ConfigSummary.roles` and `RuntimeLive.roles` (`cadre status --json`), and a `Roles:` line under `Node class:` in both sections of the text report. `startHealthServer` takes `Pick<ResolvedConfig, 'nodeClass' | 'roles'>` and resolves once.

**Docs.** The README gained a "Node roles" section (YAML shape, role-to-variable table, the two refusals) and a `roles` row in the Configuration table; `example.cadre.yaml` a commented block; `.release-notes.pending.md` a section, with the earlier section's "the CLI gains this later" bullet corrected.

## Review findings

### Checked

Read the implement diff before its handoff summary, then the four surfaces against cadre-core's `node-roles.ts`, `@serfab/config-check`'s `objectOf`/`oneOf`/`setNestedValue`, and the CLI's env attribution. Both compile-enforcement claims hold as stated.

Environment edges, from `config-check/src/env.ts`: a bare `roles:` (YAML null) is replaced by a fresh block, a scalar where the block belongs is an error naming the variable, and successive `CADRE_ROLE_*` writes accumulate on one block rather than clobbering each other.

By hand against the rebuilt `dist`: a `server` with two roles in the file and a third in the environment reports `alwaysOn=false overlayTier=edge reactivity=subscriber strandCohortMember=true`; `CADRE_ROLE_REACTIVITY=sub` is refused and blamed on the variable; `roles: { alwaysOne: true }` is refused with the typo suggestion and blamed on the file.

Error paths: `status.ts` resolves inside the try that degrades to a warning, `start.ts` resolves after `CadreNode` has already applied cadre-core's refusals, and `--no-health-server` returns before the resolution. No site in cadre-cli derives behaviour from `nodeClass` any more (grep), so nothing was left mapping the class. cadre-host, cadre-provider and integration-tests all cast `/status` bodies, so the newly required `HealthStatus.node.roles` compiles there untouched — each typechecked. The shipped container stack needs no change: compose's `env_file: .env` carries every `CADRE_*` variable to the node, and the entrypoint's generated YAML is overridden by the environment on every start.

### Found and fixed in this pass

- **The README's `network.enableRelay` default was stale.** It said the default follows `nodeClass`; cadre-core takes it from `roles.alwaysOn` (`relay-server.ts` → `resolveRelayServer`), which this change makes settable, so a `server` with `roles: { alwaysOn: false }` runs no relay. The row now names the role and links to the new section.
- **`start-node.ts`'s `hostUnclaimedStrands` NOTE was stale.** It said `strandFilter` is "the only opt-out here"; the default is `?? roles.alwaysOn`, so `roles.alwaysOn: false` is now a second one. Reworded to say which opt-out keeps the node always-on.
- **`docker/env.example` did not mention the four variables** although the container path accepts them. A commented block was added in its Node Class section (empty keeps the class's value).

### Tests

The misspelled-role test was **cut**: it restates config-check's unknown-key and typo-suggestion mechanism, which the same spec's first test already pins on `network.listenAddr`, and that spec's header says per-field checks are not tested there. The behaviour was confirmed by hand instead (message above).

One test was **added** in its place — "takes each role from its `CADRE_ROLE_*` variable, a false included". The dotted paths and kinds in `ENV_MAPPINGS` are plain strings no type checks, and the one case with semantics in it was unverified: `false` must beat a `server` preset rather than read as unset. The file-surface test ("accepts a roles block and carries it through") was kept.

Two existing tests were **completed** rather than new ones added: "surfaces live runtime fields (no hardcoded false/null/[])" now asserts `runtime.roles` — the `?? null` is exactly the hardcoding that test exists to catch — and the text-report test asserts the `Roles:` line, which was `formatRoles`'s only coverage.

### Considered and declined

- **Two `resolveNodeRoles` calls** (health server, config summary) are not duplication: the logic is cadre-core's, and these are two callers of a pure function with the same inputs, so they cannot disagree. A `resolvedRoles` field on `ResolvedConfig` would collapse them at the price of two role-shaped fields where exactly one may be handed to cadre-core. The comment at `start.ts` already records why it resolves there. No ticket and no tripwire.
- **`formatRoles` on an empty object** prints an empty list instead of `(not reported)`. No build produces `roles: {}` — `/status` carries the resolved four or omits the key — so the guard stays as written.
- **A README note that `roles.reactivity` matters only where strand reactivity is on** would be a second home for a fact `docs/strands/app-schema.md` → "Change notifications" owns and `docs/cadre/node.md` → "Node classes" links from.
- **`docker/entrypoint.sh` does not mirror `CADRE_ROLE_*` into the generated `cadre.yaml`** as it does the identity and the strand filter. Mirroring buys debugging visibility only, and `cadre status` in the container now prints the resolved roles, which is better.

### Noticed, not this change's

`cadre status` prints `Configuration: (no config file found; skipped)` for a file that was found and rejected; the warning above it carries the real reason. Pre-existing in `formatConfigSection`, and telling the two apart means carrying a reason into the report rather than editing a string — cosmetic, and below the filing bar.

### Not found

No correctness defect in the change itself. Nothing is allocated, so there is no cleanup or lifetime question; the resolution is pure, so there is no error path beyond the refusals cadre-core already owns. No size debt: `status-query.ts` 247 lines, `schema.ts` 257, `start.ts` 582, `health.ts` 583, all within what this package already carries. No new ticket was filed and no tripwire parked, because every finding was either fixed here or decided above.
