description: Joining a network used to time out after only 5 seconds even when the join actually succeeded, because the responder's real work (writing to the database, and soon calling an approval webhook) shared a budget meant for a bare network read; the joining side now waits long enough for that work to finish before giving up.

## What shipped

A third timeout budget, `provisionTimeoutMs`, separate from the per-wire-step `stepTimeoutMs`:

- `FormationListenerOptions.provisionTimeoutMs` (responder) — default **12_000 ms**; bounds the
  `provisionStrand` hook call.
- `FormationDialOptions.provisionTimeoutMs` (initiator) — default **15_000 ms**; bounds only the
  `await-response` read (`dial-connect` still uses `stepTimeoutMs`).
- `StrandFormationManagerConfig.provisionTimeoutMs` — threaded into both sides.

Nesting, documented at the constants and now in `docs/architecture.md`: approval hook (10s,
`formation-approval.ts`) < responder provisioning (12s) < initiator await-response (15s) <
session (30s). Each layer can fail and report before the layer above it gives up.

`resolveProvisionTimeoutMs()` treats `0`/negative as "unset" (uses the default) and clamps a
budget that leaves no room under the session timeout to `sessionTimeoutMs - stepTimeoutMs`.

A responder whose provisioning overruns replies `approved: false, reason: 'Formation
provisioning timed out'` — a retryable reason, not the generic internal error — instead of
dropping the stream.

### Fixed in this pass (minor)

- **Timeout detected by exact error-message string match.** The responder compared
  `err.message` against a reconstruction of `withTimeout`'s internal label format; any change to
  that message would have silently routed a provisioning timeout to the misleading
  `'Internal formation error'` path. Replaced with `withTimeout`'s existing `onTimeout` callback
  setting a local flag — the same pattern `formation-approval.ts` already uses — and the whole
  block extracted into `FormationListener.provision()`, which returns `undefined` for a timeout
  and rethrows everything else.
- **A late-settling provisioning outcome was swallowed.** After the timeout, `withTimeout`
  discards whatever the abandoned hook eventually returns *or throws*, so a provisioning failure
  arriving 1ms late vanished with no log at all. `provision()` now attaches a debug log to both
  settle paths.
- **The clamp guard ignored the wire step that precedes provisioning.** It clamped only when
  `provisionTimeoutMs >= sessionTimeoutMs`, but the session budget also has to cover the
  responder's contact read / the initiator's dial-connect. `sessionTimeoutMs: 1000,
  stepTimeoutMs: 400, provisionTimeoutMs: 800` passed the old guard unclamped and could still let
  the session timeout fire with no result frame — exactly the failure the clamp exists to
  prevent. Guard now requires a full step of headroom (`requested + stepTimeoutMs >=
  sessionTimeoutMs`); clamp value unchanged.
- **Test gaps.** Added: the `provisionTimeoutMs: 0` "unset means default, not instant timeout"
  path (behavior was implemented and documented but unexercised); the new headroom clamp case;
  and the initiator's `await-response` *failure* path (only its success path was covered) —
  asserting it rejects with its own budget in the message and still closes the stream.
- **Duplicated test fixture.** The slow-provisioning hook was spelled out three times; extracted
  to a `slowProvision(delayMs, strandId)` helper.
- **Docs.** `docs/architecture.md` → "Strand Formation" described the protocol but said nothing
  about timeouts, so the nesting rationale lived only in a code comment. Added a paragraph
  covering the four budgets, why provisioning does not share `stepTimeoutMs`, the timed-out
  reply, and the clamp.

### Filed as a new ticket (major)

- `backlog/bug-formation-timeout-can-spend-an-invite.md` — provisioning is not cancelled when its
  budget expires, so its database write can land *after* the joiner has been told the join failed,
  consuming the single-use invitation and leaving retries rejected as an invalid token. The
  implementer documented this as a `NOTE:` and declared it out of scope, which was the right call
  for that ticket, but it is a reachable, user-visible defect today, not a conditional one, so it
  gets a ticket rather than a tripwire. The mirror-image `NOTE:` in `formation-approval.ts`
  (`FormationApprover` has no caller-supplied `AbortSignal`) describes the same missing
  cancellation capability from the other end; the ticket links them.

### Recorded as tripwires, not tickets

- **Concurrency cap.** A longer provisioning budget holds a session slot longer, so a slow hook
  can exhaust `DEFAULT_MAX_CONCURRENT_SESSIONS` sooner. Conditional on the cap being lowered or
  the budget raised well above its default; parked as the implementer's `NOTE:` at that constant
  (kept as written).
- **Late commit after timeout.** The `NOTE:` in `FormationListener.provision()` stays as the
  at-the-site explanation; the ticket above carries the fix.

### Considered and deliberately not changed

- **`0`/negative means "unset".** This is inconsistent with its sibling options in the same
  interface (`sessionTimeoutMs`/`stepTimeoutMs` use `?? default`, so `0` there means a 0ms budget)
  and with `createHttpFormationApprover()`, which *throws* on a non-positive `timeoutMs`. Left
  permissive: a config typo yielding the sane default is the safe direction for a budget whose
  whole purpose is to stop premature failure, and the behavior is documented at all three option
  sites and now pinned by a test.
- **Non-finite budgets.** `NaN` falls through to the default, `Infinity` hits the clamp; both land
  somewhere sane, so no extra validation was added.
- **No real-libp2p integration test** (flagged by the implementer). Not filed: the branches this
  change adds are pure timer/budget logic on top of an already-integration-covered protocol; a
  real stream would exercise the same code with worse determinism and slower runtime.
- **Wall-clock margins in the clamp test** (flagged by the implementer). Kept — the two timers
  involved are scheduled within microseconds of each other, so their firing order is stable under
  load. The new headroom test uses wider margins (700ms hook / 600ms clamp / 1000ms session).
