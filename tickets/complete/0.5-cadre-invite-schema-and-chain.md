# Cadre invitation tables and the consent branches

## What shipped

Implemented in `ticket(implement): cadre-invite-schema-and-chain`; reviewed and amended in this pass.

- **Schema** (`schemas/control.qsql`, mirrored by hand in `control-schema.ts`, drift spec green). `CadreInvite`: the invitation row keyed by its ed25519 public key, owner-signed over the whole row, insert-only, never deleted. `CadreInviteUsage`: one append-only row per redemption, carrying the holder's possession signature and the device's consent signature, with the invitation's liveness conditions (not withdrawn, unexpired, uses left, issuer still an owner) checked against the committed snapshot. `CadrePeer` and `OwnerKey` gain consent branches that seat a row with no owner signature when a usage row in the same transaction names that exact row; `OwnerKey` also stores how every row was seated (`VouchOwner`/`VouchSig`/`VouchUsage`). `Revocation` accepts a `'CadreInvite'` tombstone while the row stays: that is how an invitation is withdrawn. Every comparison over a nullable proof column is written null-safe, because a check that evaluates to null passes.
- **`ControlDatabase`**: `insertCadreInvite`, `seatCadreInvite` (insert-if-absent from the holder's signed copy; an issuer unknown here surfaces as `CadreInviteIssuerUnknownError`), `queryCadreInvite(s)`, `queryCadreInviteUsages`, `countCadreInviteUsage`, `hasLiveCadreInvite`, `withdrawCadreInvite` (tombstone only), `redeemCadreInvite` (one transaction: peer row if absent, owner row if granted and absent, usage row last; a retry answers `alreadyMember` and writes nothing). `queryCadrePeers` returns `vouchUsage`; an owner re-vouch clears it so the row stands on the signature again.
- **Reader**: `CadreNode.listAuthorizedMembers` judges a row with a null `VouchSig` and a `VouchUsage` through `verifyInvitationAdmission` (`peer-authorization.ts`), which re-verifies the chain row → usage → invitation → anchored issuer against the node-local anchor, including that the stored device key really derives to the row's peer id. The usage and invitation tables are read only when some row needs them.
- **Docs**: `docs/architecture.md` control table list (new rows for the two tables; `OwnerKey`, `CadrePeer`, `Revocation` rows updated), and the two passages that describe the membership predicate.

Deliberate deviations from the implement ticket, all kept: redemption checks the existing rows before the seat budget so a retry of a single-use redemption is `alreadyMember` rather than exhausted; `hasLiveCadreInvite` also requires the issuer to still be an owner, matching the schema; withdrawal is read through the per-table retired-stamp seam; `InvitationExhaustedError` is reused for cadre invitations.

## Review findings

**Checked**

- The implement diff, read before the handoff: both schema copies clause by clause, the three-valued-logic argument for every `coalesce`, each consent branch against the usage row's checks, the `Revocation` branch, the database methods, the reader, the type changes, the budget re-measurements, and every doc passage the change touched or should have.
- Replay and reuse paths by reading: a committed usage row cannot seat a second peer or owner row (the stamp it names is retired on removal and `NotRevoked` refuses it; `PeerId`/`Key` are primary keys); an invitation cannot be seated and redeemed in one transaction; a withdrawal in the same transaction as a redemption refuses the redemption; the tombstone re-issue and reaper paths treat `'CadreInvite'` correctly (re-issued, never reaped).
- Error mapping in `seatCadreInvite`: a tampered signature maps to the same retryable error as an unknown issuer. Documented at the error; the protocol ticket's call, left as is.
- The implementer's tests: each pins one constraint or one error by name against the real engine; none restates the implementation or verifies a mock. None cut.
- The integration scenario the handoff could not run (`control-concurrent-same-pk-insert`) after rebuilding the three own packages the stale-build guard named: 3 of 3 passed.

**Found and fixed in this pass (minor)**

- **A usage row that only completes an already-admitted device could name any device key.** When the peer row already exists, no peer insert pins `PeerKey`, so a holder of an owner-granting invitation targeted at an admitted device could seat an `OwnerKey` row under a key that device never held, with every signature valid. `CadreInviteUsage.PeerExists` now also requires `P.PublicKey = new.PeerKey`; the same-transaction path already pinned it through the `CadrePeer` consent branch, so nothing else changes. One new test refuses the case by name.
- **Self-publish by an invitation-admitted device was unverified against the real schema** (named as a gap in the handoff). One new test admits a device, re-publishes its addresses with its own key through `updateSelfPeerRecord`, and reads the proof columns back untouched.
- **A backwards-compatibility re-export** of `ed25519PublicKeyB64FromPeerId` from its old home in `seed-bootstrap.ts` (the repo has no compatibility policy yet). Removed; the eight importers and the package index now import from `ed25519-key.ts`.
- **The `Revocation` tombstone message was built at three sites** (guarded removal, ledger marker, invitation withdrawal). Factored into `revocationTombstoneMessage` in `control-database.ts`.
- **Two doc passages still described membership as voucher-only** (the yardstick count and the anchor's consumers in `docs/architecture.md`). Both now name the invitation chain.

**Tripwires recorded**

- `NOTE:` at `CadreNode.loadInvitationChain`: once invitations are the only admission route, every membership refresh in a cadre with a not-yet-re-vouched member reads two more whole tables and verifies three signatures per row; both tables are append-only and a verified chain never changes, so a per-node memo is the fix if the admission deadline ever shows it.
- Kept from the implement pass: the full-table scan and per-invitation count in `hasLiveCadreInvite`, the accumulation of expired and withdrawn `CadreInvite` rows (schema comment), and the accepted tradeoff at `CadreInviteUsage.Authorized` that two machines racing a single-use invitation may both admit.

**Not filed, with reasons**

- No major findings; nothing met the filing bar.
- The owner-anchor does not follow owner additions or removals, so an `OwnerKey` row seated by consent is not yet judged by any reader against the anchor. That is the plan ticket `owner-anchor-follows-owner-key-changes`, which already names the columns this ticket added as its input.
- `alreadyMember` is answered for a device admitted by any route, not only this invitation. Documented on `CadreInviteRedemptionResult`; the protocol ticket is told not to read it as attribution.
- No warm-start migration for existing control stores: accepted by the implement ticket, recorded in the docs note under the table list.
