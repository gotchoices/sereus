# OAuth 2 authorization code with PKCE, and the provider descriptor: complete

Second ticket of the `provider-client-and-sign-up` chain. The client half is `cadre-core-provider-client-and-rent-node`, which implements against `docs/architecture.md` → "Provider descriptor and sign-in".

## What shipped (`ticket(implement): provider-oauth-reference-endpoints`, plus the review fixes below)

**Configuration.** `auth.oauth` (`clients[]` with `clientId`, `redirectUris`, `scopes`; `accessTokenTtlSec`, `refreshTokenTtlSec`, `devConsentPage`) and a `provider` block (`id`, `name`, `publicUrl`, optional `termsUrl`, `regions`, `icon`). Shape rules in `config/schema.ts`: `auth.oauth` only with `mode: oauth`; at least one client, unique ids, each with at least one redirect URI and one scope; a redirect URI is an absolute URL with no fragment and `http` only at a loopback host; a scope is a `Scope` value or `<resource>:*` (`*` excluded); `provider.publicUrl` is `https` or loopback `http` with no query or fragment. `devConsentPage: true` needs `allowInsecureNoAuth: true` (`validateAuthConfig`, post-merge). Environment forms: `PROVIDER_OAUTH_DEV_CONSENT_PAGE`, `PROVIDER_ID`, `PROVIDER_NAME`, `PROVIDER_PUBLIC_URL`. `check` prints one line after the JSON when there is no `provider` block.

**Endpoints**, all under `server.basePath`, skipped by the auth preHandler by exact path. `GET /oauth/authorize` validates the client and the redirect URI first (exact string match; a failure is a 400 HTML page with no redirect), then redirects every other fault to the registered URI with `error`, `error_description` and `state`; the customer is resolved by `AuthHooks.authorizeCustomer` or by the dev consent page (`GET` renders the form, `POST /oauth/authorize` takes it back). Codes are 32 random bytes base64url stored as SHA-256 hex with a ten-minute expiry; a customer with no billing record gets one when the first code is issued. `POST /oauth/token` takes form-encoded or JSON bodies: `authorization_code` takes-and-deletes the code and checks client, redirect URI and the S256 verifier in constant time; `refresh_token` rotates the pair. Tokens are `ApiKey` records named `oauth:<clientId>`; refresh tokens are a `RefreshToken` record. `GET /descriptor` builds the descriptor from the config at request time; 404 `NOT_CONFIGURED` without a `provider` block.

**Bearer validation in `oauth` mode.** A bearer is first looked up as a stored key (expired → deleted, treated as absent), then handed to `validateJwt` when present. The lookup helper is shared with `api-key` mode, which now also deletes an expired stored key.

**Store.** `saveAuthorizationCode`, `takeAuthorizationCode`, `saveRefreshToken`, `takeRefreshToken` on `ProviderStore`, in `MemoryStore` and `FileStore` (`authorization-codes.json`, `refresh-tokens.json`).

**Decisions kept from the implement handoff.** `response_type` other than `code` is `unsupported_response_type` and an absent `scope` is `invalid_scope` (both RFC-permitted; the client always sends scopes). `invalid_client` is a 400. The descriptor omits `oauth` when `auth.oauth` is unset (a provider with an external identity provider publishes its own descriptor). `lastUsedAt` is not updated for OAuth tokens. Malformed JSON bodies and a throwing hook get Fastify's default 400/500 shapes. Dependency added: `@fastify/formbody`.

## Review findings

**Checked.** The whole implement diff with fresh eyes before the handoff: every new module (`oauth.ts`, `pkce.ts`, `oauth-consent-page.ts`, `descriptor.ts`), the auth preHandler rewrite, the schema rules, both store implementations, the type fix to `DeepPartial`, the tests, the README, the example config and the architecture doc. Cross-checked the collaborators the new code leans on (`hasPermission`, `isKnownScope`, `BillingService.initializeCustomer`, the routes the descriptor names, `FileStore` date revival) and the client ticket `cadre-core-provider-client-and-rent-node` for wire-shape agreement. Walked the happy path, the two page-not-redirect faults, each redirected fault, replay, rotation, expiry, the hook's three decisions, the dev page, the start-time refusals, repeated query parameters (Fastify yields an array, treated as absent, so a 400 page), custom-scheme redirect URIs through `URL.searchParams`, and the `basePath` derivation of every descriptor URL.

**Found and fixed inline.**

- **The plan list was not public, though the descriptor says it is.** `GET /billing/plans` was never in the auth preHandler's skip set, so it answered 401 without a bearer; the README's "none (public listing)" row predates this ticket and was never true. The descriptor now names it as `plansUrl` for a store screen that runs before sign-in, so the route is in the skip set (`auth.ts` `publicPaths`). Verified by running the new assertion against the old set (401) and the new one (200); the assertion lives in the descriptor test.
- **The dev consent page's `POST` stayed live beside an `authorizeCustomer` hook.** With both configured, the `GET` served the hook but the page's `POST /oauth/authorize` was still registered and issued a code to anyone for any customer id, a sign-in the operator's account system never saw. The start-time check (`assertOneCustomerResolver`, `auth.ts`) now refuses the combination as it refuses neither, so a dev flag left on in production fails loudly. One assertion added to the existing start-refusal test; README and the `devConsentPage` type comment say so.
- **Duplicated validation in the two authorize handlers, with non-null assertions.** The `GET` and the dev page's `POST` each ran resolve-client, check-request and build-grant by hand, then asserted `codeChallenge!` and `state!`. One `resolveGrant` plus `refuse` now serves both, and `checkAuthorizeRequest` returns the narrowed `codeChallenge` and `state` itself, so no assertion remains (`oauth.ts`).
- **A failed billing initialization left an orphan code.** `issueCode` saved the code before creating the billing record; the order is swapped so a throwing `initializeCustomer` leaves nothing behind.
- **Architecture doc overstated the `https` rule.** "Every URL is `https` except at a loopback host" is true of the API URLs only; `termsUrl` and `icon` are ordinary web URLs (`webUrl` in the schema). The sentence now says which.

**Tests.** The implementer's tests were read as code under review. None restates the implementation or verifies a mock: each pins a wire contract from the architecture doc (the round trip, the two page faults, the redirected faults, single use, rotation, the hook's decisions, the dev page, the start refusal, the descriptor document) or a schema rule. All kept. Two assertions added, one per defect above; no new test file. `FileStore`'s two new collections remain untested glue, as the handoff said; the pattern is the existing collections' and nothing under `__tests__` covers `FileStore` today, so no test was added for them.

**Major findings filed as tickets.** None. Both defects were fixable at their site in this pass, and neither names a class beyond itself: the public-route list is one set in one function, and the resolver check is the one place both resolvers meet.

**Tripwires (recorded in code by the implement pass, confirmed in place).** `store.ts` `ProviderStore`: expired codes and refresh tokens are removed only when presented; sweep on the reaper's tick if a long-running provider accumulates enough to matter. `oauth.ts` `exchangeCode`: a replayed code is refused but the tokens its first exchange minted are not revoked; add revocation if a leaked code is ever a worry. No new tripwire from this review.

**Considered and left alone.** `registerAuth` does not refuse `mode: oauth` with neither `auth.oauth` nor `validateJwt` (every bearer is then 401: closed, pre-existing). `oauth.ts` is 425 lines after the refactor, under the size where a split would pay; a natural seam (`oauth-token.ts` for mint, exchange and refresh) exists if it grows. The hook receiving the browser's full headers is the design: cookies are how the operator's site knows who is signed in.
