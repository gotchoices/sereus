## Summary

NAT/DDNS substrate for cadre-host landed as a self-contained `packages/cadre-host/src/nat/` module tree (library + `createNatHandlers` factory, no inline service process) plus a small cadre-core hook so invites can substitute the host's dialable surface:

- `NatService` orchestrates port mapping (UPnP/NAT-PMP via `@achingbrain/nat-port-mapper`), external-IP detection (router-side + public probe, CGNAT diff), DDNS push (DuckDNS v1), and `getInviteAddresses()` (dns4 → ip4 → libp2p fallback).
- `nat.json` is atomic JSON next to `trust-circle.json`; DDNS credentials live in `keytar` with a 0600 file fallback.
- `cadre-host nat {status,test,settings,ddns set,ddns external}` subcommands hit `/nat/*` over loopback (same pattern as `trust`).
- `NetworkConfig.inviteAddressResolver` + `SeedBootstrapConfig.inviteAddressResolver` thread through `CadreNode.initializeSeedBootstrap` / `enableSeedListener`; `createInvite()` consults the resolver first and falls back to `libp2pNode.getMultiaddrs()` either unset or on resolver-throw.
- `docs/cadre-host.md` adds a NAT and DDNS section; the package README's command table now includes the five `nat` sub-commands.

## Integration contract for `cadre-host-local-ui`

1. `new NatService({ rootDir, cadreNode })` (cadreNode exposes `getPeerId()` / `getMultiaddrs()`).
2. `await service.start()` after libp2p is up; `await service.stop()` on shutdown to release the lease.
3. Mount `createNatHandlers(service)` on Fastify under `/nat/*` (`GET /nat/status`, `POST /nat/test`, `GET /nat/ddns/providers`, `PUT /nat/ddns`, `PUT /nat/settings`).
4. Map `NatError.code` → HTTP: `invalid_config|ddns_provider_unknown|ddns_credentials_missing` → 400; `secrets_unavailable|storage_error` → 500.
5. Wire `service.getInviteAddresses.bind(service)` as `network.inviteAddressResolver` on `CadreNodeConfig`.

## Follow-up tickets to file

These are deliberate scope-outs (already noted by the implementer; restated here so they don't get lost):

- **AutoNAT integration** — enable `autoNat()` in `@optimystic/db-p2p`'s `libp2p-node-base.ts`, consume verdict in `reachability.ts` (the current heuristic is portMode + cgnat only).
- **Circuit-relay client reservations** — until cadre-core reserves through a relay, `getInviteAddresses` fallback never emits `/p2p-circuit/` addrs, so CGNAT hosts remain un-dialable from the public internet. See backlog `4-relay-bootstrap-infrastructure`.
- **Additional DDNS providers** — Cloudflare, No-IP, Dynu. Architecture is open (drop a new file under `nat/ddns/` and register it).
- **IPv6 announcement** — `address-resolver` only emits `/ip4/` for raw-IP fallback; IPv6 falls through to libp2p addrs.
- **Live-router e2e fixture** — `createDefaultPortMapper()` adapter is not exercised against a real router in CI.
- **`nat ddns list` CLI** — `NatService.listDdnsProviders()` is wired into the handler but no CLI sub-command surfaces it. Add when the local-ui provider picker needs it.
- **`providerId: 'external'` sentinel** — `nat ddns external` sets `providerId: 'external'` + `externallyManaged: true`. Works today because the updater short-circuits on `externallyManaged` before resolving the provider — but if a user later flips `externallyManaged` to `false` without picking a real provider, the updater will silently record a `ddns_provider_unknown` error on every tick. A future cleanup could allow `providerId: null` for this case.

### Architecture / design (SPP, DRY, scalability, error handling)

- Module layout mirrors `auth/` (libraries + `createXxxHandlers` factory, no inline service), keeping cadre-host coherent. Good.
- `NatService` is the single seam: lifecycle, status, settings persistence, and address resolution all funnel through it. Pure pieces (`buildInviteAddresses`, `evaluateReachability`, `isPlausibleIp`) are split out for unit testability.
- `NatError` carries a stable `code` enum for HTTP mapping; documented in the integration contract.
- Resource cleanup is explicit and idempotent: `stop()` clears DDNS timer, calls `portService.unmap()` + `mapper.stop()` with each in a try/catch so a failure of one doesn't abort the other.
- `inviteAddressResolver` defensively falls back on resolver-throw — the implementer's choice (and the new test that locks it in) is right: cadre-host crashes should never silently stop invite generation in cadre-core.
- The DDNS updater's unchanged-IP skip matches DuckDNS's documented guidance (don't re-push), and `forceUpdate()` is the bypass for `testReachability`.

### Correctness — minor (left as known gaps; no fix-in-pass)

- **`PortMapperService.refresh()`** always calls `installMapping()` regardless of the `verify()` result — `verify()` is essentially a status probe, not a gate. The `verifyResult: true` test confirms this (`mapper.calls.map` goes from 1 → 2). Matches the current `@achingbrain/nat-port-mapper` shape (no per-mapping introspection). Documented gap #2 in the handoff.
- **`scheduleRefresh()` re-arms before the prior refresh resolves.** Cadence-correct, but a slow refresh could overlap with the next tick. Acceptable at a 30-minute cadence.
- **`PortMapperService.start()` schedules a refresh timer even when the initial mapping failed.** Intentional (the periodic retry is the recovery path) but undocumented in code. Not severe enough to comment-inline.
- **`port-mapper.ts:134` adapter `verify()`** has `void externalPort; void protocol;` rather than the project convention of `_`-prefixed param names. Cosmetic; left alone.
- **`DdnsUpdater.scheduleNext()` uses `setInterval`** without awaiting the previous tick. At default 5-min cadence this is fine; only a concern if `runOnce` ever exceeds 5 minutes (the DuckDNS HTTP call is single-digit-second).
- **`isPlausibleIp` IPv6 branch** is *very* liberal (`/^[0-9a-fA-F:]+$/` + `split(':').length >= 3`). Accepts e.g. `aaaa:bbbb:cccc`. The downstream consumer in `address-resolver` only emits `/ip4/...` so a junk-but-plausible-looking IPv6 string just rejects at multiaddr build time. Acceptable for v1.
- **`nat ddns external` uses `providerId: 'external'` as a sentinel.** See "Follow-up" above.
- **`readSecretLine` in `bin/host.ts`** doesn't have an automated TTY-interactive test (non-TTY error path IS covered by `cli-nat.smoke.test.ts`). Implementer's note #11 stands — a targeted manual smoke test on a real TTY is warranted before shipping.
