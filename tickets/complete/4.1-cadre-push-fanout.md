## What shipped

The **trigger-policy + fan-out** half of server-side push-wake. `PushFanoutService` (cadre-core) is fully deps-injected (no transport/DB of its own) and never throws to its trigger. On `notify(strandId, reason='activity')` it: gates on participation, coalesces concurrent triggers + debounces per strand, enumerates `listMembers()` minus self, skips per-`(peer,strand)` cooldown, then wakes **direct-first** (`pushWake`; a resolved `WakeAck` — even `accepted:false` — counts as reached ⇒ no platform push; only a dial/transport rejection falls back to `resolveDeviceToken → notifier.send`), expiring `unregistered` tokens. Wired into `CadreNode` (`start` constructs it only when `config.push` is set, via a guarded dynamic `import('./push-notifier.js')`; `notifyStrandActivity`/`recordStrandActivity` triggers; `expireDeviceToken`; `cleanup` teardown). `metro.config.js` gains a `node:http2`/`http2` empty shim. Full design in `docs/architecture.md` (mechanisms 3 & 5) and `docs/STATUS.md`.

## Review findings

**Scope reviewed:** the full implement diff (e685338) read first with fresh eyes, then the handoff. The injected-primitive contracts were verified against their real implementations in `cadre-node.ts` (not just the fakes): `pushWake` (throws on "no dialable address" = suspended phone, otherwise returns the `WakeAck` from `dialWake` — confirming the "rejection ⇒ fallback, resolved ack ⇒ no fallback" semantics), `listMembers` (`queryCadrePeers`, may include self → self-exclusion is required and present), `resolveDeviceToken` (membership + key-binding + self-sig + freshness gated, `null` on any failure), `seedBootstrapService.deleteDeviceToken` (authority-gated, accepts any peerId).

### Major — fixed inline (1)

- **Concurrency join-path leaked a rejection → unhandled rejection at the `void notify(...)` trigger.** When a second `notify` for the same strand joined an in-flight pass via `return inflight`, and that pass's `runFanout` rejected (e.g. `listMembers()` throwing on a control-DB hiccup — a real path, since `queryCadrePeers` can throw), the joiner *adopted that rejection*. A returned promise settles in the **caller's** context, so `notify`'s own `try/catch` did **not** catch it — and the call site is `void this.pushFanoutService?.notify(...)`, which attaches no handler ⇒ an unhandled rejection, violating the documented "never throws to the trigger" guarantee. The originator path was safe (`await op` sits inside the catch); only the joiner leaked.
  - **Fix** (`push-fanout.ts`): the stored in-flight promise is now guarded — `runFanout(...).catch(log)` — so both the originator and any joiner observe a non-rejecting promise. A dropped pass is recoverable via the check-in-wake backstop. Comment added explaining why the returned promise escapes the try/catch.
  - **Regression test** added (`push-fanout.spec.ts` → "a concurrent joiner does not reject when the in-flight pass rejects"): parks the first call on a pending `listMembers`, lets the second join, then rejects. **Verified it fails on the pre-fix code** (`git stash` of the src change → the new test is the only failure) and passes with the fix — a genuine guard, not a vacuous assertion.

### Minor — observed, accepted for v1 (1, not filed)

- **`deadTokens` is never pruned on re-registration within a process.** Once a `send` returns `unregistered:true`, the peer is added to the in-memory `deadTokens` set, which short-circuits *before* `resolveDeviceToken`. So if that phone later re-registers a fresh token while the server process keeps running, the **direct platform-push path stays disabled for it until restart** (the authority node also deleted the row, so even the resolve would need the new row). This sits inside the implementer's documented "in-memory, acceptably lossy" envelope and is backstopped by the check-in wake (mechanism 2), and re-registration is rare relative to the 5-min cooldown — so it is **accepted as a v1 limitation, not filed**. A future enhancement would clear a peer from `deadTokens` on `registerDeviceToken`; if on-device measurement shows phones losing direct wakes after a token rotation, file then. (Noting it here rather than silently.)

### Checked — no action

- **Direct-first vs platform-fallback semantics** — verified against the real `pushWake` contract; `ack-rejected ≠ dial-failed` holds. A *transient* `pushWake` rejection (not just no-address) also falls through to a platform push of an otherwise-reachable peer — this is the safe over-wake direction (`serviceWake` is idempotent/coalesced), so acceptable and unchanged.
- **Cooldown armed up-front in `wakePeer`** — armed before the dial, so a non-mobile/null-token or transient-send-failure peer is not re-dialed for `cooldownMs`. Correct for anti-spam; the next activity past cooldown retries.
- **Self-exclusion, per-`(peer,strand)` cooldown (independent per strand), leading-edge debounce-from-pass-start, participation gate** — all correct; covered by existing tests.
- **Stale-token expiry** — `unregistered` → `deadTokens` + `expireDeviceToken`; transient failure does not expire. Authority deletes the row, non-authority logs (its `deadTokens` set is the real guard). Covered.
- **Cross-platform import-cleanliness** — `push-fanout.ts` imports only the `PushNotifier` *type* + the dependency-free `STRAND_WAKE_TYPE` value, so it is safely re-exported as a runtime value from `index.ts` with no `node:http2`/`node:crypto` edge. The guarded dynamic `import('./push-notifier.js')` in `CadreNode.start` is the only edge to the Node-only modules; the new `metro.config.js` `http2` shim (mirroring the existing `net`/`tls` stubs) satisfies Metro's graph resolution for that edge. A phone never sets `config.push`, so the notifier never loads.
- **Docs** — re-read every touched file. `docs/architecture.md` (mechanisms 3 & 5) and `docs/STATUS.md` accurately reflect the shipped reality (fan-out now `[x]`, sender `[x]`, passive-detector deferral, in-memory/lossy + no-cross-strand-coalescing caveats). Accurate.
- **`PushCredentials.cooldownMs`/`debounceMs`** threaded `types.ts → CadreNode.start → service`. Correct.

### Deferred — out-of-agent (unchanged from handoff)

- **RN bundle build / on-device run** not exercised here (same as the RN push-wake-receive ticket). The `node:http2` Metro shim is the correct fix by inspection, but a real Metro/EAS bundle + a phone (no `config.push`) booting unaffected must be confirmed by a human/CI out-of-band.
- **Real-network fan-out** (actual FCM/APNs delivery) not exercised in unit tests.
- **Passive Optimystic-level activity detector** filed as `tickets/backlog/passive-strand-activity-fanout-detector.md` — needs an upstream `IRepo` commit/block-received hook that does not exist yet. An enhancement over the explicit `notifyStrandActivity`/`recordStrandActivity` trigger, not a correctness gap.
