## What landed

The **client half** of peer-bound TURN issuance. The server half shipped in
`turn-issuer-peer-assertion`; until now nothing sent the five `X-Sereus-Peer-*`
headers, so `PEER_AUTH_MODE` was dormant. Both reference apps now sign every ICE
manifest fetch with their libp2p node key, so the issuer can attribute (and revoke)
a TURN credential per peer id.

### `cadre-core` — new `src/identity-key.ts`

- `loadOrCreateIdentityKey(keyStore, keyId?)` — the load-or-create-and-persist rule
  lifted out of `CadreNode.resolveIdentityKey`, including the load-bearing rule that
  a rejected `get` (e.g. `KeyStoreAccessError` from a cancelled biometric prompt)
  **propagates** rather than falling through to generating a fresh key.
- `peerKeySigner(privateKey)` → `PeerKeySigner { peerId, publicKeyB64, sign() }`.
  Ed25519-only; `peerId` is `publicKey.toString()` (already the base58btc peer id for
  an identity multihash), `publicKeyB64` is `publicKeyToProtobuf` + base64url.
- Both exported from the package root. `resolveIdentityKey` delegates and keeps only
  the `keyStore`+`privateKey` mutual-exclusion error, the `privateKey`/ephemeral
  branches, and the idempotent early return.

The two identity log lines moved *into* the helper (namespace
`sereus:cadre:identity-key`, still under `sereus:cadre:*`, so the
no-key-material-in-logs regression test still covers them). Reviewed and kept: the
helper is the only place that knows which branch it took, and both callers now get
the line.

### `ice-config.ts` (both apps, kept as mirrors)

`loadIceConfig(url?)` → `loadIceConfig(options?: { url?, signer? })`. No back-compat
overload (per AGENTS.md). New exported, individually tested helpers in both copies:
`iceConfigAudience`, `peerAssertionMessage`, `randomNonceHex`,
`buildPeerAssertionHeaders`, plus the `IceConfigPeerSigner` structural interface.
Both files stay dependency-free — the signer is injected, no crypto import.
`IceConfigManifest` gained the informational `peerAuth` / `peerId` fields;
`parseIceServers` still reads only `iceServers`.

### App wiring

- `cadre-web.ts`: `loadIceConfig({ signer: peerKeySigner(privateKey) })` using the
  already-resolved browser peer key.
- `cadre-phone.ts`: an explicit `loadOrCreateIdentityKey(keyStore, DEFAULT_IDENTITY_KEY_ID)`
  placed **after** `migrateLegacyIdentity` and **before** `loadIceConfig`. Still
  passes `keyStore` + `identityKeyId` to `CadreNode` (not `config.privateKey`), so the
  node loads the very key just persisted and the identity stays in the enclave path.

### The retry, widened beyond the original ticket

The ticket said a thrown fetch behaves "exactly as today: log, return `[]`". The
implementer widened the retry to cover it, and the review confirmed the reasoning:
attaching five non-safelisted headers turns a **cross-origin** browser fetch into a
*preflighted* one. The issuer answers that `OPTIONS`; a static host commonly does
not — and the common CDN/static configuration (`Access-Control-Allow-Origin` set,
`Access-Control-Allow-Headers` not) fails only the preflight, so the unsigned retry
genuinely succeeds where the signed attempt could not. A failed preflight reaches JS
as a network error with no HTTP status, so a status-only retry list would never have
fired.

`shouldRetryUnauthenticated` therefore retries on `400`/`401`/`403`/`503` **or** on a
thrown attempt, guarded by `if (controller.signal.aborted) return []`. `429` stays
excluded (the per-IP limit fires before the assertion is parsed).

### The cross-repo lock

The pinned vector (seed = 32 bytes of `0x01`) is asserted on four sides — the issuer's
`self-test.ts`, `cadre-core/test/identity-key.spec.ts` (a real `peerKeySigner`
produces exactly the pinned peer id, public key, and signature), and both apps'
`test/ice-config.spec.ts` (`peerAssertionMessage` byte for byte). Verified during
review that all four literals are character-identical.

## Review findings

### Checked and clean

- **The widened retry.** Re-derived the CORS argument from the spec rules rather than
  taking it on trust: `accept: application/json` stays safelisted, the five custom
  headers do not, and the retry lands on a genuinely different (simple) request. The
  abort guard means a blown deadline never buys a second doomed fetch. Correct as
  written.
- **Wire-format agreement with the issuer.** Header names, the five-line message, the
  nonce shape (32 lowercase hex), base64url encodings, and the pinned vector all match
  `ops/docker/turn-credential-issuer/src/peer-assertion.ts`. The issuer's
  printable-ASCII and length caps on the audience mean a hostile/odd URL degrades to a
  `400` and an unsigned retry, not a crash.
- **Identity safety.** `loadOrCreateIdentityKey` is the only load-or-create rule left;
  a rejecting `get` propagates and writes nothing, corrupt bytes throw without
  overwriting the slot — both directly tested. The RN call sits after
  `migrateLegacyIdentity`, so it cannot pre-empt a migration and mint a second
  identity.
- **`peerKeySigner` throwing on a non-Ed25519 key** would now fail a boot that
  previously proceeded. Traced both key sources: `loadOrCreateBrowserPeerKey` and
  `loadOrCreateIdentityKey` both generate Ed25519 only, and cadre-core already
  hard-requires Ed25519 downstream (`ed25519KeyPairFromLibp2p`). Not a reachable
  regression; no change made.
- **Resource cleanup / never-throws contract.** One `AbortController` and one timer
  for both attempts, cleared in `finally`; `loadIceConfig` returns `[]` on every
  failure path. Covered by tests including a fake-timer test that the single 5 s
  deadline spans both attempts.
- **Secrets in logs.** No key material, no TURN credential, and no signature is
  logged; there is an explicit test asserting a failure warning carries no credential.
- **Test quality.** The two specs mirror each other case for case and cover happy
  path, every fallback status, the excluded ones (`429`/`500`), thrown attempts with
  and without a signer, no-third-attempt, abort, and the audience log line. This is a
  floor, not a ceiling — see "Known gaps" below, which the review confirms are still
  open and are honest.

### Found and fixed in this pass (minor)

- **`docs/architecture.md` and `docs/reference-app-rn.md` were left stale.** Both
  describe identity resolution as something `CadreNode` does privately; it is now an
  exported rule an embedding app calls first. Updated both: the resolution-order
  section now names `loadOrCreateIdentityKey`/`identity-key.ts` and says why it is a
  package-root export, the `SecureStoreKeyStore` section records that `startPhoneNode`
  resolves the key before constructing the node, and the RN doc's "Peer identity"
  section states the ordering constraint and the fail-the-start-on-locked-enclave
  behaviour. Also corrected a pre-existing stale sentence in the same bullet claiming
  the `expo-secure-store` backend "lands in a dependent ticket" — it shipped.
- **The relative-URL audience trap was undocumented.** `iceConfigAudience` normalizes
  nothing, so a same-origin deployment configured with `VITE_ICE_CONFIG_URL=/ice-servers.json`
  signs the audience `/ice-servers.json` — the page origin never enters the signed
  string, and `PEER_AUTH_AUDIENCE` must match *that*. The near-miss table in
  `ops/docs/ice-servers.md` listed trailing slash, scheme, and rewritten path but not
  this one, and "Where to host it" actively recommends same-origin. Added it to the
  table with the fix, added the clause to both `iceConfigAudience` docstrings, and
  added a `does not absolutize a relative URL` case to both specs so the behaviour is
  locked rather than merely described.
- **Redundant `as string | string[]` cast** in the RN copy's `toIceServer`, where the
  web copy relies (correctly) on the `isValidUrls` type predicate. Removed, so the two
  mirrors stay literally identical there.

### Filed as a ticket (major)

- `tickets/backlog/debt-ice-config-two-hand-synced-copies.md` — the two
  `ice-config.ts` copies are 275 identical lines out of 380 (measurement command in
  the ticket), and as of this change that duplicated region includes the signing wire
  format. The pinned vector catches a message-format drift, but nothing catches a
  change made consistently to one app and its own spec. Suggested direction: move the
  assertion wire format next to `peerKeySigner` in `cadre-core/src/identity-key.ts`,
  subject to keeping the two files' dependency-free property (or explicitly retiring
  that property). Low urgency, non-zero cost. Checked first that no open ticket
  already claims these paths — only `dead-code-cleanup-and-knip-gate` mentions
  `ice-config`, and that is about unused exports, a different site.

### Tripwires parked (not tickets)

- `ops/docs/ice-servers.md`, in the 4xx/503 fallback bullet — the retry spends a
  second token of the per-IP limit `RATE_LIMIT_PER_MIN`. Harmless when the fallback is
  rare; a *persistently* rejected assertion (a misconfigured audience) halves the
  effective per-IP budget, which only matters for many clients behind one NAT. Parked
  in the doc rather than in code because there are two mirrored call sites and the
  reader who needs it is the operator tuning that limit.
- `packages/reference-app-rn/src/cadre-phone.ts`, at the `loadIceConfig` call
  (from the implement pass, reviewed and kept) — one signed fetch per cold start /
  foreground resume burns a replay-cache nonce and a per-peer bucket slot
  (`RATE_LIMIT_PER_PEER_PER_MIN`, default 10). Ten-plus resumes in a minute take a
  `429`, which is deliberately not retried, so that one resume runs STUN-less. Fix if
  resume churn ever gets that high: cache the manifest for the credential TTL.

### Considered and deliberately not changed

- `fetchManifest` maps a malformed JSON body on a `200` to the same `{ kind: 'error' }`
  as a network failure, so a signed request against a host serving broken JSON burns
  one extra doomed retry. Distinguishing the two would touch both mirrors and both
  specs to save one fetch in a misconfiguration that is already broken. Not worth the
  churn; recorded here so the next reader knows it was seen.
- The two `ice-config.ts` copies use different indentation (spaces on web, tabs on RN),
  as do `cadre-node.ts` and `key-store.ts` within cadre-core. Pre-existing throughout
  the repo and not introduced here; lint does not enforce it. Left alone.

### Empty categories

- **No correctness defects found in the shipped logic.** The retry decision, the
  deadline, the audience derivation, and the identity ordering were each traced
  against the issuer's implementation and hold.
- **No security defects found.** Specifically checked: nonce source (CSPRNG only,
  with a throwing guard), no client-supplied peer id trusted by the server, no key
  material or credential in any log line, no assertion reuse across the retry (the
  retry sends no headers at all).
- **No skipped, disabled, or loosened tests** — the suites grew by one case per app
  and nothing was weakened.

## Known gaps — treat the tests as a floor

- **Never run against a live issuer.** No end-to-end request has been made from a real
  browser or device to a real `turn-credential-issuer` with `PEER_AUTH_MODE=optional`.
  Everything is stubbed `fetch` plus the pinned vector.
- **The CORS preflight is reasoned about, not observed.** No test in this repo can
  exercise a real preflight; the retry that handles it is covered only by a
  "fetch rejects" stub.
- **`crypto.getRandomValues` on a device is untested.** `randomNonceHex` runs on
  Node's `crypto` under vitest. RN gets it from `react-native-get-random-values` via
  `polyfills/hermes.js` (verified by reading, not by running on a device); a missing
  polyfill degrades to unauthenticated rather than crashing, which *is* tested.
- **RN cold-start re-entry is not covered by a test.** The reasoning (a `get`-then-
  return is idempotent and opens no native handle, unlike `nodeLocalDb`) is in a
  comment at the site; nothing asserts it.
- **The audience-log assertion is loose** — it checks the URL and status appear in
  *some* warn line, not the exact message.

### Behaviours worth exercising by hand

- **Web, cross-origin static manifest.** Point `VITE_ICE_CONFIG_URL` at a JSON file on
  another origin served by something that sets `Access-Control-Allow-Origin` but does
  not answer the preflight. Expect two requests (failed preflight, then a plain GET)
  and STUN servers still present.
- **RN first run.** Wipe the app, start it: the identity slot must end up with exactly
  one key, and the node's peer id must equal the one in the `X-Sereus-Peer-Key`-derived
  assertion.
- **RN with a locked keychain.** Cancel the biometric prompt: `startPhoneNode` must
  *fail*, not boot with a fresh identity.
- **Audience mismatch.** Set `PEER_AUTH_AUDIENCE` with a trailing slash, or point the
  app at a relative URL, and confirm the client console prints the audience it actually
  sent, then still gets STUN.
