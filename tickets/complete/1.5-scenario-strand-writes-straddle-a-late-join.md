# Landed: writes that straddle a late join

Third test in `strand-late-cadre-join.integration.ts`, the bring-up split it needed, one additive
harness option, and the doc paragraph that describes the property.

## What shipped

**`strand-late-cadre-join.integration.ts`** — the old single bring-up function split into three
(`foundStrandAlone`, `enrollNewcomer`, `joinDiscoveredStrand`) so a test can run code between the
founder's solo phase and the newcomer's enrollment; a bounded continuous writer
(`startStraddleWriter`) that inserts one row per 100 ms and updates a fixed row every fourth tick,
tagging each row with the phase it was written in; and Test 3, which enrolls and joins a second
machine *while the writer keeps going*, then proves every straddling row reached the new machine.
Tests 1 and 2 were verified behaviour-preserving against the previous revision — the same statements
in the same order, only relocated.

**`harness/block-store-probe.ts`** — one additive optional field, `AwaitBlockCoverageOptions.onGap`,
called with every poll's gap. A successful coverage wait ends on an empty gap by definition, so
without it there was no way to report which kind of gap a run passed through on its way to coverage.

**`docs/cadre-consistency.md`** — the paragraph on the peer-join catch-up gained the seam property,
its measurement, and (from this review) the limits of what the measurement shows.

## Review findings

**Read the implement diff first**, then the handoff. Tests 1 and 2 were diffed line-by-line against
the previous revision to confirm the refactor claim; the writer, both gates, the harness field and
the doc paragraph were read in full.

### Major — fixed in this pass

- **Test 3's behavioural gate said nothing the physical gate had not already said.** It read every
  row back through the newcomer's strand database *with the founder still running*. Optimystic picks
  one coordinator per block and that coordinator answers from its own storage first, so a
  coordinator resolving to the author would have served all of those rows out of the founder — the
  assertion would have held on a newcomer that received nothing. The handoff listed this as a known
  gap and judged Test 1's isolated read sufficient; it is not, because Test 1 only reads the five
  rows written *before* the join, which is the half this test is not about. **Fixed:** the founder is
  now stopped and the newcomer's strand node polled down to zero connections before the read, with a
  second zero-connection assertion after it, matching Test 1's Phase 4a. Green on 5 consecutive runs.
  Rule 3 in the file header was rewritten to state the requirement rather than merely note where the
  reads happen.

### Major — filed, not fixed here

- **The specific seam the test aims at is never forced.** A block committed after the catch-up's
  enumeration passed its id but before the peer is marked done is the case the test exists for, and
  nothing establishes that any run ever produced one: the founder's store is ~9 blocks against a
  default batch size of 64, so the enumerate-and-push is a single batch measured in milliseconds
  against a 100 ms writer tick. Filed as
  `tickets/backlog/debt-late-join-catch-up-seam-is-never-forced.md`, naming the two config levers
  (`PeerJoinBackfillConfig.maxChunkBlocks`, `debounceMs`) that widen the window from a test without
  putting test hooks in production code. Site-claim grep run first: the only other open ticket
  touching `peer-join-backfill.ts` is `debt-strand-write-breadth-observed-end-to-end`, which is about
  counting cohort width — a different claim, so this is a new ticket rather than an arm on that one.

### Minor — fixed in this pass

- **Measurement claims were stale and understated.** `docs/cadre-consistency.md` and two code notes
  said "12 runs" where the handoff's own series was 13, and the doc's "3 to 5 blocks absent
  mid-window" was contradicted by run 13's logged `absent=6`. The `WRITER_TICK_MS` comment claimed
  "25-30 rows inside enrollment" against a measured 23-29. All reconciled against the full 18-run
  series (13 from implement, 5 from this review) and the doc now also states the coverage gate's
  first-poll limitation rather than leaving the reader to infer a stronger claim.

### Tripwires — parked in code, deliberately not filed

- `NOTE:` at the physical gate — coverage has completed on its **first poll** in all 18 runs, so
  `kindsSeen` logs `[]` and the gate proves the end state, never the window closing. The mid-flight
  diagnostic is what shows the newcomer genuinely behind. Witnessing the close from the gate itself
  needs staging this test does not have.
- `NOTE:` at `WRITER_UPDATE_EVERY` — an update is guaranteed to land in the post-mesh half only
  because 4 is smaller than `POST_MESH_ROW_FLOOR` (5); any run of 5 consecutive ticks contains a
  multiple of 4. Move either constant the wrong way and every revision advance falls in the catch-up
  half, leaving the `behind` gap shape unexercised on the replication side with nothing asserting.
- Two `NOTE:`s from the implement stage were re-read and left as they stand (`COVERAGE_BUDGET_MS`
  sizing, `WRITER_MAX_TICKS` unreachability), with their run counts corrected.

### Checked and found clean — no finding

- **Writer lifecycle and error handling.** It captures rather than swallows its own error; `stop()`
  re-throws it and is idempotent; `awaitPhaseRows` fails fast with a distinct message when the writer
  has already exited, so a dead writer cannot let downstream assertions pass for having nothing left
  to lose. `writes` is only appended after an insert resolves, so it never claims an uncommitted row.
- **Resource cleanup.** The writer is stopped in the body and again in `finally` (where its re-thrown
  error is caught and warned so it cannot mask the real failure); `stopLateJoin` stops watcher nodes
  before the founder they read, with `try`/`catch` rather than a promise tail so a synchronous throw
  cannot abandon the rest of the list.
- **Anti-vacuity.** Every gate has a floor behind it: the warm-up rows, `enrollingRows > 0`,
  `postMeshRows >= 5`, `updateCount > 0`, the founder-side read-back that catches a silently no-op
  `update`, `newcomerStore !== founderStore`, and "founder blocks new or advanced since the pre-join
  snapshot" (6 of 9 every run). `readBlockIndex` throws rather than reporting empty when the backend
  lacks `listBlockIds`.
- **The harness change.** `onGap` is optional, additive, destructured out of the options passed
  through to `compareBlockCoverage`, and cannot throw into the poll. All three consumers of
  `block-store-probe.ts` were re-run green.
- **Source hygiene.** 788 lines is unremarkable for this suite (three scenario files are 1030-1811).
  Functions are short and single-purpose; the bring-up split is a genuine decomposition rather than
  a comment-block rename. Deviations from the implement ticket (three bring-up functions rather than
  two; the update-target row inserted by Test 3) were checked and are correct — Test 2 must not run
  the strand, and putting the extra row in the shared bring-up would have changed Tests 1 and 2.
- **Documentation.** `docs/testing.md` does not inventory scenario files, so nothing was owed there;
  `docs/strands.md` and `docs/architecture.md` carry no claim this change contradicts.
- **Empty categories, stated explicitly:** no "considered-and-declined" finding arose — no accepted-
  tradeoff `NOTE:` exists at any site touched. No pre-existing test failure was encountered, so
  `tickets/.pre-existing-error.md` was not written.

### Not re-tested here

The wider integration suite was not run. The harness change is one optional field and typecheck
covers its reach; all three files that consume `block-store-probe.ts` were run in full. A full-suite
run is well past the ten-minute agent budget and belongs to CI.
