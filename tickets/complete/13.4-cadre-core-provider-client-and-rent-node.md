# Provider client and `rentNode` in cadre-core: complete

Fourth ticket of the `provider-client-and-sign-up` chain, implemented in `ticket(implement): cadre-core-provider-client-and-rent-node` and reviewed here. `packages/cadre-core/src/provider/` holds the provider descriptor parser, the app's side of the OAuth 2 + PKCE sign-in with a self-refreshing token source, the typed client over cadre-provider's container API, and `rentNode` / `finishRental`, which add a rented container to the node's cadre by invitation when `CadreNode.invitationReach()` reads `anywhere` and by claim otherwise. `CadreNode.isOwner()` and `invitationReach()` are new; both reference apps delegate their owner check to `isOwner()`. `docs/architecture.md` → "Renting a node from an app" is the design as built.

## Review findings

**Read first, before the handoff:** the implement diff in full (five new modules, the `CadreNode` additions, the shared `fetch-impl.ts`, the two app edits, the docs, the four specs), then the provider's `routes.ts`, `create-request-validation.ts`, `descriptor.ts`, `oauth.ts`, `container-service.ts` (`nodeCode`) and `types.ts`, since nothing has run against a live provider and the wire shapes are taken on trust.

**Wire shapes, confirmed against the provider's code.** `POST /containers` with `{ join, profile }` and nothing else is what the validator accepts for both join kinds (`partyId`, `bootstrapNodes` and `pinnedOwnerKeys` are refused beside a `join`, and `profile` defaults to `storage`). The envelopes match: `201 { ok, data: { container } }`, `{ data: { containers } }`, `{ data: { container, health } }` with `health.status` in the three values the client knows, `DELETE`'s bare `{ ok, message }`, `{ data: { billing } }` where `billing` is absent for a customer without a record, and the node-code refusals `409 NOT_CLAIMABLE | ALREADY_CLAIMED | CONTAINER_GONE` and `503 NOT_AVAILABLE`. The token endpoint answers `{ access_token, token_type, expires_in, refresh_token, scope }` and refuses with `400 { error, error_description }`; the authorize endpoint reads exactly the seven query names `authorizationUrl` sets and requires `state`. The provider's `nodeCode` does refuse `already-claimed` once a live read folds the claim, which is the fact the `finishRental` deviation rests on.

**Deviation weighed: `finishRental` on a claimed container.** Accepted. The provider withholds the code after the fold, so re-running `claimNode` is impossible without a provider change; judging by `join.partyId` is the right call for this ticket. The alternatives the implementer listed (widening `RentingNode` with `authorizePeer`, or a provider that keeps serving the code to the claiming owner) stay unfiled: the window is a kill between two consecutive awaits, the React Native app already accepts the same window for cadre-host claims, and the recovery (delete and rent again) is one tap. Recorded at `judgeClaimed` (`NOTE:`) and in the architecture doc; no ticket. The downstream ticket `reference-app-rn-rents-a-provider-node` still described the old `claimNode`-again behaviour in its "killed after the node accepted" bullet; corrected there, since that ticket is gated on this one and had not started.

**Descriptor without `oauth` refused: confirmed.** The provider's descriptor type says a provider on an external identity provider publishes its own descriptor naming that provider's endpoints, so every published descriptor carries `oauth`; cadre-provider's route omits it only when it runs no sign-in at all, and an app could not use such a provider anyway.

**Fixed inline (minor).**
- `rentNode` on the claim path let a `409 CONTAINER_GONE` from the code poll escape as a `ProviderApiError`, while `finishRental` reports the same condition (a container found `stopped` or `error`) as `RentNodeError('container-gone')`, so an app had to handle one fact at two sites. `awaitNodeCode` now maps it (`requestNodeCode` in `rent-node.ts`); the `RentNodeErrorCode` doc and the architecture doc's claim-path paragraph say so.
- `parseContainer` cast the record's `status` to `RentedContainerStatus` unchecked; it is now validated against the seven known values, as `parseJoinState` and `parseBilling` already do for theirs, so an unknown status is a clear error at the boundary rather than a container `joinKindOf` silently treats as live.
- `packages/cadre-core/src/index.ts` repeated the provider barrel's 52-name export list; it is now `export * from './provider/index.js'`, the barrel being the curated list. Typecheck confirms no name collides with the rest of the package root.
- `test/rent-node.spec.ts` imported `RentNodeError` as a value where only its type is used (lint).

**Test added.** One table-driven `finishRental` case in `test/rent-node.spec.ts` over the same hand-written node and client fakes, nine rows: stopped → `container-gone`; no join → `not-a-rental`; claim awaiting → code polled and claimed; claimed into this party → done with the container's peer id and no second claim; claimed into another party → `claimed-by-another`; `ALREADY_CLAIMED` mid-poll → re-read and judged done; `CONTAINER_GONE` mid-poll → `container-gone` (the defect above); invitation pending → done; invitation failed → the failed outcome. It pins the resume contract the architecture doc states, which had no test; the fakes gained `reports` and `codeRefusal` to drive it.

**Tests kept.** The three implement-stage specs stand: the RFC 7636 vector, the state check, the loopback rule and the token source's sharing/rotation/refusal in `provider-oauth.spec.ts`; the 401 retry, date parsing, envelope mapping and the 503/409 code answers in `provider-client.spec.ts`; the two `rentNode` paths and the withdrawal on a failed create in `rent-node.spec.ts`; the two real-node assertions in `cadre-node-cadre-invitation.spec.ts`. None restates the implementation or verifies a mock; each is a contract an app relies on. `provider-client.spec.ts` folds four assertions into one case; left as is, since they exercise one request helper and splitting adds setup without a new behaviour.

**Checked and found sound (no change).** The token source's single in-flight refresh and the `invalidate(stale)` skip; `persist` awaited after `current` is replaced, so a failed persist leaves a working in-memory pair; a network failure rethrown as is; `tokensFrom` refusing a response without `refresh_token` or a positive `expires_in`; the client's one 401 retry with the token it sent; `readEnvelope` tolerating a non-JSON body; `encodeURIComponent` on container ids; `LOOPBACK_HOSTS` holding `[::1]`, which is how `URL.hostname` spells it (the handoff wrote `::1`); `readAuthorizationRedirect` over a custom-scheme URL; `invitationReach()` and `createCadreInvitation` sharing `selectInvitationMembers`; `isOwner()` being the stricter check, with both apps wiring the key on every start; `fetch-impl.ts` deduplicating formation-approval's resolver while keeping its `misconfigured` error; the `link-independent` lint directive on the node-code deadline; no Node imports anywhere under `provider/` (Metro export and `vite build` both pass).

**Tripwires recorded.**
- `judgeClaimed` (`rent-node.ts`): the claimed-without-a-row window, as above.
- `createTokenSource` derives `expiresAt` from the real clock (`requestTokens`), while `now` only drives the freshness check; harmless, the fake-clock log line's "expires in" is the only thing it skews. Not worth a comment at the site.

**Not filed, and why.** No per-request deadline in the client (the handoff's gap): the ticket named none, the claim path is bounded by its poll deadline, and React Native's `fetch` times out on its own; it becomes work only if a device run meets a hung provider, and the budgeted-fetch pattern in `formation-approval.ts` is the remedy then. The token source cannot take a new pair after `reauthorize`: the app builds a new source and client, which the downstream ticket already plans. `health` carrying three fields: add when an app reads more. The handoff's "nothing has run against a live cadre-provider" stands; `reference-app-rn-rents-a-provider-node` is the first real run and its handoff should say what it saw.

**Site-claim grep.** Nothing open touches `packages/cadre-core/src/provider/` or `fetch-impl.ts`; `debt-cadre-node-single-file-size` already owns `cadre-node.ts`'s size, and the two methods added there are small.
