# What landed

A cadre node keeps an in-memory list of which peer IDs may open control-database streams to
it. That list used to be rebuilt only when a caller remembered to ask, so any write path
that forgot left a freshly-admitted member locked out for up to ~15 s (until the next timed
reconcile). The obligation now sits in the one place a membership write cannot avoid — the
control database's `CadrePeer` mutation wrapper, which notifies a listener after each
committed write; the node wires that listener to its own refresh at startup. The refresh
coalesces (concurrent callers share one database read) and a caller always observes its own
change by the time its write resolves.

Production code + docs landed in the first phase; the second phase added the unit and
real-database tests. This review pass closed the coverage gaps that phase flagged and ran
the validation it could not.

# Review findings

## Correctness of the coalescing machinery — checked, nothing found

Walked `refreshMembershipGate` / `drainMembershipGate` / `deferMembershipGateRefresh` for
lost wake-ups, spin, and unbounded re-read:

- Every interleaving of "mark stale" against "drain re-checks the flag" is closed, because
  the drain's loop-exit and its `finally` (which releases the single-flight slot) run in one
  synchronous step — there is no window where the slot is occupied by a drain that will no
  longer look at the flag.
- A throwing read cannot spin: the flag is cleared *before* the read, so a failure exits the
  loop and leaves the previous snapshot.
- The one genuine fragility is already documented as a tripwire at the site (see below).

## Write-path completeness — checked, nothing found

`CadreControl.CadrePeer` has exactly four mutation sites in `packages/cadre-core/src`. Three
run inside `mutateCadrePeer`. The fourth, `updateSelfPeerRecord`, is a deliberate carve-out
(it can only touch this node's own row, which is filtered out of the snapshot anyway) and is
pinned by `control-membership-hub.spec.ts` ("does not notify on a self-signed address
refresh, the one carved-out mutator"). No writer bypasses the hub.

## Documentation — checked, already accurate

`docs/architecture.md` L353 was rewritten in the first phase and describes the write-driven,
coalescing behaviour, the two public-API carve-outs (replicated rows, newly anchored owner
key), and the writer's own-read guarantee. `docs/STATUS.md` L1130 already points at the unit
suite. `seed-bootstrap.ts` carries the matching note on why anchoring a key still needs an
explicit refresh. Nothing stale found; no doc edits needed.

## Coverage gaps closed in this pass (minor — fixed inline)

Three of the handoff's five listed gaps were real and cheap to close:

- **The defer scope's second caller was untested.** Only `drainPendingPeerWrites` was
  driven; `reconstructAuthoredMembership` wraps the same helper and had nothing pinning it.
  Added `collapses the owner-authored reconstruction sweep into ONE refresh` — three
  re-issued rows cost the sweep's own read plus exactly one flush at scope exit.
- **The documented suppression case was untested.** The defer scope's depth counter is
  instance-level, so a genuinely unrelated concurrent write also has its refresh held to
  scope exit — the one place the "a caller always observes its own change" contract does not
  hold. Added `suppresses a CONCURRENT unrelated write refresh until the drain scope exits`,
  driven through the real `drainPendingPeerWrites`, not a direct call to the private method.
  Both scopes in the codebase are short; confirmed neither has grown long-lived.
- **The burst test over-trusted the fake.** The real `mutateCadrePeer` notifies *inside* the
  control DB's write lock, so four local `CadrePeer` writes never actually overlap that way.
  The coalescing property is still real — it is exercised in production by a write-driven
  refresh racing an undriven one (`start`, `reconcile`, `applySeed`, `onSeedApplied`), none
  of which hold the lock. Added a fidelity comment saying so, so a future reader does not
  mistake the fake's missing lock for a modelled production race.

Also de-duplicated the three private-internals pokes the drain tests share into named
helpers (`stubPeerRecordReads`, `queuePendingWrites`, `drainPendingPeerWrites`), and gave the
drain test the weaker `< N` claim alongside its exact count.

## Gaps judged acceptable — no change

- **Exact read-count assertions (`toBe(2)`, `toBe(1)`) are impl-shaped.** Kept. Each is now
  paired with the weaker "strictly fewer than one read per write" claim, so a legitimate
  refactor that changes the read pattern fails one assertion with the property still visibly
  intact — that is the signal you want, not noise.
- **The burst test's white-box listener counter.** Kept. It is the only way to release the
  held read deterministically rather than betting on microtask ordering; it wraps (rather
  than replaces) whatever `inject` wired, so it cannot silently drift from it.
- **The removal case runs against the fake, not a real DB.** Not a gap: the real-DB removal
  round-trip in `seed-bootstrap.spec.ts` and `control-membership-hub.spec.ts` both cover it.

## Tripwire — recorded at the site, not filed

The first phase left a `NOTE:` on `drainMembershipGate`
(`packages/cadre-core/src/cadre-node.ts` ~L4030): the method is correct only because its
stale flag is guaranteed true on entry, and a second caller that did not mark the flag first
would strand an already-settled promise in the single-flight slot. Verified still accurate
and still unreachable (one caller, which marks the flag synchronously). Left as a comment.

The handoff called running `push-wake-e2e` "the single highest-value review action", and it
paid off in both directions:

- **The change is proven end-to-end.** `seedReceiverRecord` no longer refreshes the gate at
  all, and scenario 4 — the one that reads a sibling-written membership row — passes in
  **1.7 s**, the fast path. (A stale gate snapshot is what stretched that scenario to ~17 s
  before any of this existed.) Under `DEBUG='sereus:cadre:*'` the automatic refresh is
  visible firing on the write (`refreshAuthorizedControlPeers(peer-insert): 1 authorized
  peer(s)` → `… 2 authorized peer(s)`) with **zero** `authorizeInboundControlStream: DENYING`
  lines anywhere in the run.
- **One scenario fails, and it is not this change.** The NAT'd circuit-relay scenario fails
  2/2 runs, both block-availability shaped (a receiver that cannot load its own control-DB
  schema for a missing block; a `CadrePeer` row that never converges inside 30 s) — the
  fingerprint of the already-blocked `control-db-cross-node-convergence-halted`. Reported in
  `tickets/.pre-existing-error.md` rather than folded in silently, because this scenario is
  currently listed in `.pre-existing-known.md` under *"Resolved in place"* for a different,
  unrelated root cause. Nothing was skipped or loosened to get a green run.
