## What shipped

The config-plumbing subsystem that gets FCM/APNs credentials into a spawned node's `CadreNodeConfig.push` (the block cadre-core's already-shipped fan-out reads). It owns no delivery logic — only secret storage, config injection, and validation. Five coordinated parts:

- **cadre-core** — `push-credentials.ts`: `validatePushCredentials` (a present platform block must carry all required fields; empty bundle valid — push is opt-in) and `redactPushCredentials` (`privateKey → [redacted]`). Type-only imports, so a provisioner pulls neither the FCM/APNs senders nor any heavy graph. Exported from `index.ts`.
- **cadre-cli** — carries `push` from `cadre.json` and a JSON `CADRE_PUSH` env override through `ResolvedConfig` into `CadreNodeConfig.push`. This closed a **real prior gap**: `start.ts` previously built `nodeConfig` without `push`, silently dropping any block before `CadreNode.start`.
- **cadre-host** — secret store (keytar / `0600` fallback, accounts `push:fcm` / `push:apns`) holds the FCM `{projectId,clientEmail,privateKey}` and APNs `{keyId,teamId,privateKey}` blobs; `host.config.json` (`PushSettings`) holds non-secret APNs `bundleId`/`production` + `cooldownMs`/`debounceMs`. The orchestrator's `pushResolver` re-resolves on **every (re-)spawn** (no raw key in `state.json`) and writes `config.push` for the authority/storage node (and managed storage nodes; transaction nodes get none). Entry path: `cadre-host push {fcm,apns,options,status,clear}` (direct-on-disk, like `install`).
- **cadre-provider** — per-tenant `push?: { default?, tenants?: Record<customerId, creds> }` (local types — see decision below); `validate.ts` rejects a partial set at `loadConfig`; `ContainerService` resolves **strictly by the launching tenant's `customerId`** and the Docker orchestrator injects `CADRE_PUSH=<json>` (PEM-newline-safe). One tenant's creds never reach another's node.
- **Docs** — `cadre-host.md` "Push credentials" section (with out-of-agent infra steps), `architecture.md` mechanism 5, `STATUS.md`.

Headline design decision (verified sound): `state.json` never persists a resolved key — the orchestrator uses a `pushResolver` callback re-invoked per spawn instead of carrying `PushCredentials` in `AuthoritySpawnConfig`, reconciling the ticket's two conflicting bullets (carry-in-config vs. secret-at-rest). A resolver error degrades to "no push" (logs, does not fail the spawn).

## Review findings

**Scope reviewed:** the full implement diff (bcc899f) read first with fresh eyes, then the handoff. Every changed file was read in full plus the consuming seams it does not touch — `cadre-node.ts` (how `config.push` is actually consumed at `start`), `installer/config.ts` `updateHostConfig` merge semantics, the `SecretsStore` interface, and both provider/host orchestrator call paths. Lint (repo-wide, clean), typecheck (all four packages, clean), and the four affected test suites were run green before and after the one inline change.

### Major — none.

No correctness defect, isolation hole, or secret-leak path was found in the shipped diff. The cross-tenant isolation assertion, the no-raw-key-in-`state.json` assertion, the re-resolve-on-respawn behavior, and the PEM-newline-survives-JSON-env behavior are all real (not vacuous) tests and were confirmed by reading the assertions against the implementation. No new fix/plan ticket was warranted.

### Minor — fixed inline (1)

- **cadre-cli was the one unvalidated injection seam.** cadre-host (`resolvePushCredentials` throws → orchestrator degrades) and cadre-provider (`validatePushConfig` at `loadConfig`) both reject a partial credential set before it reaches a node. But cadre-cli — the **common sink** that carries both a file-config `push` block and the `CADRE_PUSH` env override into `CadreNode.start` — passed the block straight through, and `CadreNode.start` (`cadre-node.ts:333`) builds the notifier from `config.push` **without validating** it. So a hand-edited `cadre.json` with a partial block (e.g. an FCM block missing `privateKey`), or a partial `CADRE_PUSH`, would build a `PushNotifier` that only fails at the first push attempt rather than failing fast at start — the exact failure mode cadre-core's `validatePushCredentials` was built to prevent.
  - **Fix** (`packages/cadre-cli/src/config/loader.ts`): `resolveConfig` now calls a small `validateResolvedPush` helper (using cadre-core's shared `validatePushCredentials`) on the resolved block and throws on a partial set, before the node is constructed. cadre-core was already a runtime dependency of cadre-cli (it imports `CadreNode`), so this adds no new dependency and pulls no FCM/APNs sender graph (the validator is type-only internally). An empty/absent block stays valid (push is opt-in).
  - **Tests added** (`packages/cadre-cli/test/push-config.spec.ts`, +4): a new `resolveConfig push validation` block writes a temp `cadre.json` and asserts a complete block passes, an absent block resolves to `undefined`, a partial file-config block throws (`/push\.fcm\.privateKey/`), and a partial block injected via `CADRE_PUSH` throws (`/push\.apns\.bundleId/`). cadre-cli suite: 84 → 88, green.

### Minor — observed, accepted (not filed)

- **`CADRE_PUSH=` (empty) wipes a file-config `push` block** in the cli env merge (empty → `undefined` override, which `setNestedValue` writes over the file value). Differs from the strand-filter precedent (empty → the `all` sentinel). Benign and already documented by the implementer: the provider omits the var entirely when it has no creds (so it never sends an empty value), and the host never uses the env channel at all. Left as-is — changing it would diverge from the "explicit-encoding, empty means unset" intent without a real caller that needs the file value preserved under an explicit empty env.
- **cadre-core's `redactPushCredentials` is exported + tested but not consumed in production.** The host logs platform presence inline (even safer — it never builds a redacted object), and the provider uses its own `redactPushConfig`. It remains a documented, tested public utility of the shared seam, not dead internal code. No action.

### Checked — no action

- **Cross-tenant isolation** (the security-critical property) — `resolveTenantPush` resolves strictly by the owning `container.customerId` (per-tenant override → provider default → none); `ContainerService.provisionContainer` passes only that result to the orchestrator, which performs no tenant lookup of its own. The regression test serializes tenant B's full create request and asserts it contains B's secret and **neither** tenant A's nor the default's. Verified by reading the resolution path end-to-end, not just the test.
- **No raw key at rest** — `AuthoritySpawnConfig` (persisted to `state.json`) carries no credentials; the `pushResolver` re-reads the secret store on every `ensureAuthorityNode`/`restartAuthorityNode`/`createContainer`. Test asserts the rotated key is picked up on restart and that `state.json` never contains the PEM. Confirmed against the orchestrator source.
- **Provider type duplication (decision #2)** — diffed the provider-local `Fcm/Apns/PushCredentials` shapes field-by-field against cadre-core's `types.ts`: identical (`fcm{projectId,clientEmail,privateKey}`, `apns{keyId,teamId,bundleId,privateKey,production?}`, `push{fcm?,apns?,cooldownMs?,debounceMs?}`). The `CADRE_PUSH` JSON round-trips through cadre-cli's parse into cadre-core's `PushCredentials` cleanly. The sync risk is real but **currently in sync**; both sides carry the keep-in-sync comment. The author's reasoning (a `@serfab/cadre-core/push` subpath export is more plumbing/risk than the duplication) is sound for now; if the shapes drift, factor the subpath then.
- **`updateHostConfig` merge semantics vs. `push clear`** — `updateHostConfig` shallow-merges top-level `push` (whole-object replace), so `push clear apns`/`clear all` correctly drops the `apns` sub-block (spreading `rest` to preserve `cooldownMs`/`debounceMs`), and `push apns`/`push options` correctly preserve sibling keys. Read the read-modify-write path to confirm; no deep-merge that would strand a removed sub-key.
- **PEM newlines over the env channel** — `JSON.stringify` escapes `\n` to two chars, so the `CADRE_PUSH` env entry is single-line; cadre-cli's `parsePushEnv` `JSON.parse` restores the PEM. Asserted by `docker-orchestrator-push.test.ts` (`not.toContain('\n')`).
- **Secret hygiene in logs** — host `resolvePush` logs only `fcm=… apns=…` presence; `resolvePushCredentials` logs presence only; provider `loadConfig` redacts `push` before its `%O` dump; the secret-store account name carries no key (tested). No private key reaches a log sink on any path read.
- **Profile gating** — only `profile === 'storage'` (and the authority node, which is storage) resolves push; transaction-only nodes get no block (they do not participate in strands). Tested both directions.

### Gaps reviewed and dispositioned

- **No HTTP route / Svelte UI field for push entry (CLI-only).** Not a defect — the CLI subcommands fully provision push directly on disk (the `install` pattern), and the ticket scoped the entry path as "a local-UI Settings field / CLI flag" (either/or). Filed as a backlog future-concern ticket (`cadre-host-push-credentials-ui-entry`) so the optional convenience surface is tracked; it does not block this work.
- **`createContainer` push path wired + unit-tested but not exercised by a live host flow** — `bin/host.ts` only spawns the authority node via `ensureAuthorityNode`; managed storage nodes via `createContainer` are not spawned anywhere in the host today. The authority path (the one that matters now) is live and tested. No action — when the host begins spawning managed storage nodes, the path is already correct.
- **No real-container / on-device integration test** — explicitly out-of-agent. The provider→container `CADRE_PUSH` handoff and host→child `cadre.json` handoff are unit-verified at each seam; end-to-end against a running node/real device, plus the Firebase/Apple credential creation and the sandbox-vs-production decision per build, remain human/infra prerequisites (documented in `docs/cadre-host.md`).
