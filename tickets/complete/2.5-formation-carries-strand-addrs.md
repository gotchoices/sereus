# Cross-party strand addresses carried by the formation handshake

## What shipped

Before this, two different parties had **no production way** to find each other's strand
nodes. The strand-address RPC (`/sereus/strand-addr/1.0.0`) is membership-gated and answers
own-party siblings only, so a joiner from another party resolved an empty seed and every
cross-party integration scenario reached its mesh by dialing one strand node at the other by
hand.

The formation handshake is the one moment two parties are authenticated to each other and
agreeing on a strand id, so the address now travels there.

- **Wire.** `FormationResultMessage.strandAddrs?: string[]` — the responder's live
  strand-network multiaddrs for the strand it just provisioned. Written on the approval path
  only, beside `partyId`/`cadrePeerAddrs`, so it rides the existing disclosure gate (token +
  disclosure validated **and** provisioning approved). Omitted when empty. Sanitized and
  capped at 16 entries by `sanitizeStrandAddrs`, on **both** sides — the responder bounds
  what it sends, the initiator bounds what it stores, because a peer may ignore a cap.
- **Seam.** `FormationListenerOptions.resolveStrandAddrs?(strandId)`, threaded through the
  formation manager and solicitation service, wired by `CadreNode` to its own
  `getStrandMultiaddrs`. Unwired, the responder discloses nothing; a hook that throws is
  logged and folded to `[]` — the seed is an optimization, the consent row is the commitment.
- **Return path.** `dialFormation` returns `FormationDialResult { provision, strandAddrs }`;
  `FormStrandResult` gains `strandAddrs: string[]` (always an array, frequently empty) so an
  app launching a strand outside `CadreNode` can seed it too.
- **Bookkeeping.** `CadreNode.crossPartyStrandAddrs` (in-memory `strandId → addrs`, written
  by `formStrand`) reaches the strand's address book three ways: `resolveCohortSeed` unions
  it after the sibling RPC answers on launch and on hibernation resume, and
  `refreshStrandPeerAddrs` re-merges it every pass. That last one required restructuring the
  refresh so a pass with no connected sibling skips only the **RPC** and still merges the
  contact addresses — the two-party joiner's steady state.
- **Docs + proof.** `docs/architecture.md`, `docs/strands.md`, `docs/api.md`,
  `docs/testing.md`, and a new integration scenario `strand-formation-cross-party-seed`:
  two real parties, host founds a strand and publishes a bound invitation, joiner redeems and
  stands the strand up, **no hand-dial anywhere in the file**, with a row replicating across
  the resulting mesh.

## Review findings

Reviewed the implement diff (`cf454ef`) against the source before reading the handoff.
Everything below was checked; empty categories are called out with a reason.

### Fixed in this pass (minor)

- **`withAddressedPeerId` was a near-duplicate of the existing `withTrailingPeerId`, with
  weaker semantics.** The new 40-line helper in `peer-addr-book.ts` reimplemented what
  `peer-record.ts` has done since the peer-record work: append `/p2p/<id>` when an address
  names no destination, including the `…/p2p/<relay>/p2p-circuit` relay-hop case. The
  existing helper additionally **drops** an address terminating in a *different* peer id —
  announcing one of those would file this node's address under someone else's id in the
  receiver's book — and it already had that case under test. Deleted the new helper and its
  tests; `getStrandMultiaddrs` now goes through `CadreNode.bindAddrToPeer`, the existing
  logged, never-throwing wrapper over `withTrailingPeerId`. One wrinkle worth knowing: libp2p
  hands back its own nested `@multiformats/multiaddr` copy, a structurally different type, so
  the address is re-parsed through this package's `multiaddr` first — a comment at the site
  says so and points at `backlog/reference-app-web-libp2p-interface-dedup`. Replaced the
  deleted isolated-helper tests with tests at the real seam (`getStrandMultiaddrs`): bare
  addr and relay hop both bound and surviving `groupAddrsByPeerId` attribution, a
  wrong-peer-id addr dropped, and no live node → `[]`. `bindAddrToPeer`'s log lines said
  `normalizeDialAddrs:`, which is now only one of its two callers; made them caller-neutral.
- **The stored cross-party list could grow without bound.** `sanitizeStrandAddrs` caps each
  *arriving* list at 16, but `recordCrossPartyStrandAddrs` unions each new list onto what is
  already stored, and nothing there can tell a dead entry from a live one. Re-forming against
  one strand — the documented recovery when a responder's relay reservation rotates — would
  add up to 16 more entries per redemption for the node's lifetime, every one of them
  re-merged into the strand's peerStore on every refresh pass. Capped the accumulation at the
  same `MAX_STRAND_ADDRS` (now exported); `unionAddrs` keeps the freshest list first, so the
  oldest entries are what fall off. Test added.
- **A re-formation's fresh addresses could sit unused for up to ten minutes.** If the strand
  was already running, `recordCrossPartyStrandAddrs` wrote the map but nothing merged it
  until the strand's ~10-minute refresh throttle next expired — which matters precisely
  because re-forming *is* the recovery path for a dead address. It now clears that strand's
  throttle stamp, so the next 15 s reconcile tick merges them. Test added.
- **An accepted-tradeoff `NOTE:` had become inaccurate.** `mergeStrandPeerAddrs` carries a
  weighed-and-declined note about address-book poisoning whose stated bound is "a bad entry
  costs one failed dial that ages out at the peerStore's one-hour expiry". That is no longer
  true of the new input: nothing can re-resolve a carried cross-party address, so the refresh
  pass re-merges the same stored list forever and a junk entry survives for the node's
  lifetime rather than an hour. Did **not** re-file the declined finding — the decision still
  holds (bounded to 16 entries, from a party the node deliberately formed a strand with, and
  an address grants no authority) — but corrected the note to say what is actually true now,
  and recorded the eviction lever. This is the reason the cap above is load-bearing rather
  than tidy.
- **A doc comment was orphaned onto the wrong function.** `unionAddrs` was inserted between
  `signMessageWith`'s docblock and `signMessageWith` itself, so the "build the signing
  callback" comment described the address-union helper. Reordered.
- **`docs/api.md` documented a `formStrand` return shape that no longer exists** — the
  published contract still listed four fields with `strandAddrs` missing. Added it, with the
  one thing an app integrator needs to know: empty is the ordinary outcome, not an error.
- **`docs/testing.md`'s coverage map did not know about the new scenario.** That map exists so
  a missing network shape is visible; the new scenario is the *only* cross-party one that
  reaches the mesh without a hand-dial, which is exactly the distinction the map should carry.
  Added, with why the other cross-party scenarios still dial by hand, and kept the standing
  "cross-party relayed shape is uncovered" caveat.

### Filed as tickets (major): none

Nothing rose to a separate ticket. Every defect found had a single named site, and each fix
was a few lines against code already under test — cheaper to land here than to hand off. The
one candidate that was weighed and rejected is the address-authenticity question below.

### Weighed and left alone

- **No authenticity check on the carried addresses** (the handoff asked for a second opinion).
  `sanitizeStrandAddrs` checks that each entry parses, not that it names the responder's
  strand peer. This is the same exposure the `mergeStrandPeerAddrs` NOTE already accepts for
  sibling RPC answers, and the widening is real but small: the peer supplying them is one
  this node **chose to form a strand with**, an address grants no authority, and the dialed
  peer authenticates by peer id at the handshake. The one thing that genuinely changed —
  permanence, since these never age out — is now capped and written down at the site. Not
  re-filed; the revisit lever (evict on `unpublishStrand`) is recorded where the next reader
  will meet it.
- **The ticket's de-hand-dial target at `strand-formation-e2e.integration.ts:454`.** Verified
  the implementer's reasoning against the fixture rather than taking it on trust: that
  scenario forms through `createMockProvisioner` on an **unbound** invitation and calls
  `addStrand` only after `formStrand` returns, so the host has no live strand node at
  redemption and there is nothing to disclose. Removing the dial would hang the test.
  Reshaping the fixture into a bound-invite flow would duplicate the new scenario and cost
  its mock-provisioner coverage. Both remaining hand-dial sites carry a comment saying why.
  Agreed — no ticket.
- **`getStrandMultiaddrs` normalization is still unproven against a real omission.** No
  observed case has libp2p returning a strand addr without `/p2p/<self>`, and the new
  integration scenario asserts the carried addrs match the host's raw announced list exactly,
  which is itself evidence the append is a no-op in practice. Kept anyway, but at zero
  duplication cost now that it routes through the existing helper — and the wrong-peer-id
  drop it gained is a genuine hardening the string version did not have.

### Tripwires parked in code: one (pre-existing, unchanged)

`CadreNode.crossPartyStrandAddrs` keeps an entry per strand for the node's lifetime,
including across `stopStrand` (deliberate — a watcher-rediscovered strand still needs its
seed). The `NOTE:` at the declaration says to evict on `unpublishStrand` or cap the map if a
node ever forms strands at scale; updated it to distinguish the per-strand list (now capped)
from the number of keys (still unbounded). No new tripwires were added.

### Checked and clean

- **Disclosure timing.** Every rejection arm — bad consent, invalid token, invalid
  disclosure, concurrency cap, post-validation rejection, provisioning timeout, internal
  error — carries no `strandAddrs` and never *calls* the resolver, with the hook wired by
  default in the test's `baseOptions` so the assertions are real, plus an explicit positive
  control. Confirmed against the source, not just the test names.
- **Scoping.** Addresses are recorded and read under their own `strandId`; the merge helper
  also refuses to write self. Unit-tested for the two-strand case, and the integration
  scenario asserts the joiner's strand connections are all to the host's *strand* peer id and
  that no control address ever appears among the carried ones.
- **The refresh restructure.** Verified the case it was reshaped around: a solo node running
  a strand with no cross-party addresses still asks nobody, merges nothing and leaves its
  throttle unstamped (so the next 15 s tick retries), and the unbounded `queryCadrePeers`
  read is still skipped at zero connections. Both unchanged from before the diff.
- **Empty-seed legality.** `isValidResponderCreatesResult` has no opinion on `strandAddrs`;
  an unbound-invite redemption stays a normal approval. Tested for absent, empty and present.
- **The reference apps inherit the seed with no change.** Confirmed by reading both: web
  `joinViaInvitation` and RN `joinClosedChatStrandFromFormation` each call `formStrand` and
  then attach on the *same* `CadreNode`, which is what makes the recorded map apply.
- **Public-surface fallout.** `FormStrandResult.strandAddrs` is required, so every
  construction site had to be updated; grep confirms no consumer builds one outside
  cadre-core, and the reference apps only read the result.

## Known limits, carried forward deliberately

- **In-memory and one-shot.** A joiner restart loses the map; with no sibling running the
  strand its seed is `[]` again. Addresses are never re-resolved, so a responder relay
  reservation that rotates before the joiner dials leaves a dead entry (recovery: a fresh
  invitation, which now takes effect within one reconcile tick). Documented in
  `docs/strands.md`; durability is `backlog/feat-cross-party-strand-addr-durability`.
- **Loopback only.** The new scenario proves the mesh over direct addresses. The relayed
  cross-party proof is the follow-on `blind-relay-phone-to-phone-e2e` (2.8), which is where a
  relay-routed `strandAddrs` entry actually gets exercised.
- **The reference-app Playwright e2e still hand-dials** through the `__cadre.dialStrandPeer`
  debug hook. That dial is now redundant for the web app's bound-invite path, but the browser
  suite is a separate proof surface and was out of scope.
