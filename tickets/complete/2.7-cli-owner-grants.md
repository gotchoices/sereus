# cadre-cli: owner grants

## What was built

**Admin channel** (`admin-server.ts`):

- `POST /admin/owner-grants`, body `{ label?, expiresInMs?: number | null, uses? }` → `{ grant, encoded, reach, warnings }` (`AdminOwnerGrant`). `expiresInMs` left out takes the node's 15-minute default; an explicit `null` is a backup. Validation as the invite route's (`parseOwnerGrantOptions`): label a string of at most 64 characters after trimming, `expiresInMs` finite or `null`, `uses` a positive integer, each a `bad_request` naming the field. `peerId` is refused, for the reason `grantsOwner` is refused on invites: a caller sending it believes the grant is bound to a device.
- `ownerGrantWarnings(result)`: always the bearer warning first (whoever holds it can become an owner of cadre X until it is used / its N uses are spent, it expires, or it is withdrawn, naming `DELETE /admin/owner-grants/<key>`), then the backup warning when `expiresAt` is null, then a reach warning for `issuer-only` / `local-network`.
- `GET /admin/owner-grants` → `{ grants: OwnerGrantStatus[] }`; `DELETE /admin/owner-grants/:key` → `{ withdrawn }`.

**`cadre enroll owner-grant`** (`enroll-owner-grant.ts`, registered in `enroll.ts`): `--label`, `--ttl <duration>|never`, `--uses`, `--json`, plus the admin connection options `enroll invite` takes. Only the encoded grant on stdout; stderr has party, key, label, uses, expiry, member addresses, how to redeem (the `CADRE_OWNER_GRANT=` form first, since a flag shows in the process list), then every warning. Reuses `parseDuration` and (now exported) `parseUses` from `enroll-invite.ts`.

**`cadre start --owner-grant <encoded>` / `CADRE_OWNER_GRANT`** (`start.ts`, `start-owner.ts`, `start-invitation.ts`):

- `start-invitation.ts` generalised: one `startupCredential` source picker (flag or env, both refused), one `decodeCredentialFor` (decode, then party check before anything starts) behind `decodeInvitationFor` / `decodeOwnerGrantFor`, `refuseOwnerGrantConflicts` (`--seed`, `--invitation`/`CADRE_INVITATION`), and `describeRedemptionFailure` extended to the grant errors (`OwnerGrantRejectedError` with its code, `OwnerGrantUnreachableError`, `OwnerKeyAddRefusedError` → `(alone)` retryable, `OwnerGrantIssuerUnknownError` → `(issuer-unknown)` retryable).
- The claim refusal (`refuseClaimConflicts`) names `--owner-grant` / `CADRE_OWNER_GRANT` too. `--owner-label` without `--owner` is refused (a grant never founds); `--owner-key-file` is accepted with `--owner` or a grant.
- The owner key file is loaded or created before the node is built, as for `--owner`. After `node.start()`, `settleServerOwner`: with `--owner` beside the grant, `refuseFoundingBesideGrant` throws on a store with no `OwnerKey` row; then `redeemStartupOwnerGrant` (never throws):
  1. key already a live owner here (`wireOwnKeyIfOwner(signer)` true) → "already an owner; the owner grant was not used; start with --owner", nothing spent;
  2. `isMember(self)` → one `reconcileControlCohort()` dial pass, then `redeemOwnerGrant` (local path) and `wireOwnKeyIfOwner`;
  3. otherwise → `joinWithOwnerGrant`.
  When the key is wired, `registerOwnerNode` (the "Owner seed-bootstrap initialized" + `registerSelf` block moved out of `start.ts`, shared with `--owner`).
- `/status` gains `node.ownerGrant` (`OwnerGrantRedemptionStatus` in `health.ts`: `InvitationStatus`'s shape plus `ownerKey`, `alreadyOwner`, `ownerWired` on `accepted`). `cadre status` prints `Invitation:` and `Owner grant:` lines and carries both under `--json` (`status-query.ts`).
- `CADRE_OWNER_GRANT` added to `COMMAND_ENV`.
- Message updates: `--invitation` + `--owner` now points at `--owner-grant`; `wireServerOwnerKey`'s not-an-owner refusal names the grant route.

**Docs:** cadre-cli README ("Make this server an owner" → "With an owner grant", new "Owner grants" section with the endpoints, "Check Status", "Join by invitation" no longer says the CLI does not mint grants, the claim-conflict lists, the env table rows for `CADRE_OWNER_GRANT`, `CADRE_STARTUP_TOKEN`, `CADRE_ADMIN_PORT`, `CADRE_OWNER_KEY_FILE`). `docs/architecture.md`: an "On a server" paragraph under Owner grants and a line in the cadre-cli section.

## Deviations from the ticket — reviewer, please weigh

- **`POST /admin/owner-grants` also returns `reach`** (the ticket said `{ grant, encoded, warnings }`): it is cadre-core's result passed through, as the invite route passes it, and a manager UI wants the enum, not the sentence.
- **A dial pass before the in-place redemption.** Not in the ticket. `start()` returns with no control connection, so without it a member started with `--owner-grant` was refused `alone` every time its cadre had other machines. With it, the smoke run below redeemed in place.
- **`--owner` beside `--owner-grant`** is refused only on a store with no owner, as the ticket says; the check needs the store, so it runs after `node.start()` (ports already bound, nothing written or redeemed). A `NOTE:` at `refuseFoundingBesideGrant` says so.
- **`cadre status` also prints the invitation's line**, not just the grant's: one formatter serves both and the invitation's was missing.

## Known gap, filed

**`tickets/fix/owner-grant-seat-fails-on-a-member-whose-store-lags.md`** (repro: verified). A member restarted with a grant that was minted while it was offline fails with `UNIQUE constraint failed: OwnerGrant.Key`: cadre-core's `seatIssuedRow` reads the row locally (absent, store not caught up), inserts, and the cohort, which holds the row, refuses. It is reported as a final failure (raw message, `retryable: false`); starting again once synced works. The CLI only exposes it; the site is cadre-core's seat, shared with the invitation seat and the apps' Redeem on a member device.

## Review findings

Read the `ticket(implement): cli-owner-grants` diff before the handoff, then the cadre-core methods it calls (`createOwnerGrant`, `redeemOwnerGrant` and its local path, `joinWithOwnerGrant`, `wireOwnKeyIfOwner`, `reconcileControlCohort`) and the docs it touches.

**Checked, no change needed**

- Admin routes: validation matches the invite route's; a node fault from `createOwnerGrant` (no owner key wired, no address) goes through the same `classifyError` path as the invite route's. The label is checked trimmed and passed untrimmed, which is right: cadre-core trims it (`ownerKeyLabel`).
- `ownerGrantWarnings`: correct for every grant `createOwnerGrant` can mint. Its `totalUses ?? 'unlimited'` branch (and the formatter's) is unreachable from the mint route, since `uses` is always a positive integer; it is harmless, so left.
- Start-up ordering: conflict checks before any decode; party check before anything dials; owner key file loaded before the node is built; identity required for a grant. A throw from `refuseFoundingBesideGrant` exits through the action's `process.exit(1)`, as `wireServerOwnerKey`'s refusal for `--owner` already does (its `NOTE:` covers the bound-ports point).
- Redemption paths: the "already an owner" check first, then member → local path, else join. `isMember(self)` in the CLI and cadre-core's own path choice (`isLiveMemberSelf() || isOwner()`) can disagree only toward the protocol path, which also works.
- Claim conflicts: `refuseClaimConflicts` names the grant at all three call sites (env secret, `claim.secretFile`, claim on record).
- `/status` and `cadre status`: `formatRedemption` takes both status shapes; `--json` carries both as `null` when absent.
- Docs: cadre-cli README sections and env table, `docs/architecture.md` ("On a server" under Owner grants, the cadre-cli section). No other doc lists the admin routes (`docs/cadre-host.md` does not list `/admin/invites` either).
- Deviations the implementer flagged (`reach` in the POST answer, the dial pass before the in-place redemption, `--owner` refused only after start, the `Invitation:` status line): all sound; kept.
- Resource cleanup: nothing new is held open; the redemption runs inside the existing start-up try.

**Found and fixed in this pass**

- The dial pass before the in-place redemption (`start-owner.ts` → `redeemForServerKey`) was awaited bare, so an error from `reconcileControlCohort` would have been reported as the redemption's failure, classified final (`retryable: false`). It is now caught and logged (`cadre:cli:start-owner`); the redemption then reports `alone`, retryable, itself. Every other caller of `reconcileControlCohort` already catches and logs.
- Test trim: the owner-grant route test's list/withdraw half asserted the mock's own grant bookkeeping (the routes are one-line pass-throughs); cut it and the mock methods it needed.
