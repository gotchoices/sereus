# A retired `OwnerKey` row authorizes nothing

## What landed

Every owner lookup in `schemas/control.qsql` (25 sites: the 22 live-table `OwnerKey A` lookups, the two `committed.OwnerKey A` signer branches of `OwnerKey.Authorized`, and the `committed.OwnerKey K` issuer clause of `CadreInviteUsage.Authorized`) carries `not exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = A.StampId)`, placed before `verify(...)`. It reads live `Revocation`, so a tombstone filed in the same transaction also disqualifies the signer. Left raw on purpose: the founding count (a machine holding only a retired row must not re-found the party), `MinOneOwner`, `ControlDatabase.hasOwnerKey`, `queryStampId` and the insert-if-absent guards. The embedded `control-schema.ts` copy matches (drift spec passes). Docs: schema header, founding-count and `CadreInviteUsage` comments, the `OwnerKey` row and "What the derivation cannot settle" paragraph in `docs/architecture.md`, the `getOwnerKeys` JSDoc, and the anchor scenario header.

Test: `control-revocation-replay.spec.ts` → "OwnerKey: an owner removed in the same transaction cannot vouch an add there", the one row-beside-tombstone state a single database can hold. The integration scenario the fix ticket asked for was built and dropped by the implementer because the removed machine converged on the delete too (whole-store catch-up from the remover), so it passed before the fix; the state it wanted needs a forked `OwnerKey` collection, which `tickets/blocked/forked-control-collection-sync-livelocks.md` owns. Consult budgets in `control-founding-consult-budget.spec.ts` moved by exactly one `Revocation` read per owner-gated write before the ledger marker; storage-op budgets did not move.

Consequence: constraint text changed on every guarded table, so control stores from earlier builds fail warm start and parties are recreated (no-backwards-compatibility policy).

## Review findings

Read `ticket(implement): removed-owner-still-authorizes-where-its-row-survives` before the handoff.

- **Coverage of owner lookups — checked, complete.** Grepped every `OwnerKey` read in `schemas/control.qsql`. The only ones without the conjunct are the deliberate raw set above, `NotRevoked`/`RevocationRecorded`/`RowIsGone` (themselves tombstone checks) and `CadreInviteUsage`'s `OwnerStampId` binding (`K.Key = new.PeerKey and K.StampId = new.OwnerStampId`), which ties a usage row to the owner row it seats and authorizes nothing.
- **Cost of the conjunct — checked, fine.** `Revocation`'s primary key is `(TableName, StampId)`, so each conjunct is a point lookup on the full key, not a scan of the tombstone list. Matching on the stamp alone (no `RowKey`) is consistent with `OwnerKey.NotRevoked`.
- **Self-retirement and same-transaction interaction — checked, no defect.** `Revocation.Authorized` now sees the row being inserted. An owner cannot use that to lock itself out by mistake: `RowIsGone` refuses an `OwnerKey` tombstone while the row is live, and the delete that would remove it must be signed by a different owner (`A.Key <> old.Key`).
- **Mutual removal across a partition — checked, not new.** Two owners removing each other while apart now lose authority as soon as both tombstones arrive, rather than when both deletes arrive. Both paths end with no usable owner; `MinOneOwner`'s comment already records the converge-to-zero case.
- **Client-side owner gates — checked.** `enrolledOwnerSigningKey` reads `getOwnerKeys` (retired stamps filtered), so owner-signed node operations that go through it refuse locally by name. The growth-edge drains (`drainPendingRevocations`, `reconstructAuthoredMembership`, `drainPendingPeerWrites`) gate on `canAuthorize()` (config only) and so still attempt and fail on a retired device. The implementer's `NOTE:` tripwire in `drainPendingRevocations` covers this. Confirmed it is not new behaviour, only a wider case of it: before this change, a device whose own row had been deleted already failed the same way.
- **Tests — kept the one new test.** It checks a named property (live `Revocation` is read beside the committed snapshot) on real branching, and the implementer confirmed it failed before the change. The 22 live-table sites share the identical conjunct text and have no per-site repro. Accepted: a test for each site would only repeat the clause, and the anchor scenario plus delete-while-alone scenarios run the reissue, vouch and invitation paths over the new text.
- **Docs — checked every touched file plus `docs/architecture.md` → "Deletes made while alone".** The sentence the handoff called possibly stale ("retires its stamp ... not physically deleted there") does not exist in the docs. The `OwnerKey` table row's "keeps the removed owner's row beside it" describes why rows are never reaped and is still accurate. One minor fix inline: the `ControlDatabase.insertOwnerKey` comment said the other `OwnerKey.Authorized` branches need "a PRE-EXISTING owner". It now says "a PRE-EXISTING, unretired owner".
- **Budget spec prose — checked.** The re-measurement paragraph and tables agree with the pinned constants. The corrected 5 → 6 idle-reconcile figure predates this change, as the handoff said.
- **Major findings / new tickets — none.** Nothing reached the filing bar.
