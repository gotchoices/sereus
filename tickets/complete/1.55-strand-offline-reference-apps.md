Fifth of the `strand-offline-mode` chain. Implemented in `ticket(implement): strand-offline-reference-apps`. Both reference apps (React Native phone app, Svelte web app) now show offline mode to the user. NativeScript got the schema tag only (its offline mode is backlog `feat-strand-offline-mode-nativescript`).

## What landed

**Schema.** `Message.Id` is tagged `with tags ("optimystic.fresh" = true)` in `schemas/chat-simple.qsql`, the three `CHAT_SCHEMA` copies and the doc block in `docs/reference-app-rn.md`. The app generates the id as a local UUID, so an ordinary queued message reads as assured, not "may not go through". App version left at `0.1.0` (cadre-core has no same-version schema-text check; the tag reaches an existing strand as a tag-only `alter table … set tags`, per strands.md).

**New edge-node call (cadre-core) — not in the ticket's plan, needed to meet it.** The ticket asks that the toggle be kept as the `strandOfflineMode` start option, but the edge node had no way to change a saved start option while running (only `restart`). Added `EdgeNode.setStrandOfflineMode(mode)` (`edge-node.ts`):
- applies the mode to every strand the running node runs (`CadreNode.setStrandOfflineMode`), and saves it in the start record (`runningOptions` updated, so a join/removal carries it as before);
- strands that start later on the same node take it too: `followOfflineMode` listens for `strand:started` and re-applies it, because the node applies the mode it was *built* with (`strandOffline.initialMode`) to every launch. Only active once the call has been made on that node (`changedOfflineMode` is keyed by node and cleared on shutdown);
- in turn with start/stop/join; throws while not running or with no offline journal.
Documented in `docs/strands.md` → "On the edge node" and on `EdgeNodeOptions.strandOfflineMode`. Also re-exported `EntryNotDiscardableError` and `UnknownEntryError` from `@serfab/cadre-core` (the phone app has no direct `@optimystic/db-core` dependency).

**What each app shows** (rules in `send-marks.ts`, one copy per app):
- **Offline switch.** Phone: Settings → Node card (`offline-mode-switch.tsx`), shown while connected. Web: checkbox in the Messages page header, disabled unless the node runs. Both call the edge node's `setStrandOfflineMode`. Default off.
- **Queue line** from `strand:queue-state` for the open strand: nothing at depth 0, else "N waiting to send", plus "waiting for the other members" (`waitingFor === 'cohort'`) and "showing saved messages" (`readsServedLocally`).
- **Per-message mark** by transaction id: `queued` → "Waiting to send" (+ "May not go through" when `outlook.kind === 'exposed'`); `outlook-changed` updates that flag; `submitting` / `partially-committed` → "Sending"; `committed` → the existing durability rule ("Not yet delivered" until `strand:commit-held`, else cleared); `failed` → "Not sent: <reason in words>"; `failed` with reason `discarded` clears the mark (the user did it). The online path is unchanged: with no queue status the mark is the old "Not yet delivered" rule.
- **Discard** on a waiting message whose status has `inDoubt: false`, via `strand.database.offline.discard(tx)`. `EntryNotDiscardableError` shows "Already being sent, so it can no longer be discarded."; `UnknownEntryError` (settled meanwhile) shows nothing.
- **Refused messages.** The refusal removes the row, so the next poll drops it from the list; the mark is kept and shown as a notice above the list ("“text” — Not sent: …") with a Dismiss button. The ticket said "the mark keeps the id so the user sees what happened" without saying where; this is the reading taken.

**Restart (design decision, deviates from the ticket's wording).** The ticket says to build marks from `offline.entries()` after publication. Entries carry transaction ids and table names only, never the row key, so nothing maps a restored transaction to its message. Each app therefore keeps a small durable record, `chat-queued-messages` in the node-local store (`queued-messages.ts`, `{ strandId, transactionId, messageId, content }`), added when a send comes back queued or sending, removed when the queue reports the transaction committed or failed or no longer knows it. At each database publication (`strand:queue-state`, once per database object via a `WeakSet`; also swept for strands already published when the phone hook attaches, and from `ensureReady` on the web), the app reads `offline.status(tx)` for each recorded transaction — which covers live, restore-pending and retained terminal outcomes, so it also catches outcomes settled during `hydrate` — rebuilds the marks, and prunes the record. `outcomes()`/`acknowledge()` are not called; retained outcomes expire on their own.

**Leave prompt.** Skipped: neither app has a leave/delete-strand action (`forgetJoinedStrand`/`unpublishStrand` are not called anywhere in either app).

## Known gaps (from the implement handoff)

- **Duplication across the two apps.** `send-marks.ts` and `queued-messages.ts` exist once per app with near-identical bodies (~200 lines in total). It follows the apps' existing mirroring (`chat-operations.ts` / `chat-dml.ts`), but a kit-level "durable map from a queued transaction id to an app value" in `@serfab/cadre-core/edge-node` could replace both records if wanted.
- **Kit call scope.** `EdgeNode.setStrandOfflineMode` sets *every* strand, which the start option means anyway; a strand an app set individually via `CadreNode.setStrandOfflineMode` is overridden when the kit call runs, and again if that strand starts again on the same node.
- **Record writes.** Each queued send writes and flushes one node-local record; each settled status does a read (and a write only when the record changes). A crash between the queued commit and the record write loses the mark after restart (the message itself is fine, and still counts in the queue line).
- **Status line counts all queued transactions**, including a queued `Participant` registration, not only messages.
- **`waitingFor: 'restore'` entries** show as "Waiting to send" (no outlook yet, so never "May not go through" until the queue puts them back).
- **Phone switch state** is read once when the switch mounts (connected), from `phone.options.strandOfflineMode`; it remounts on reconnect. A failed change shows an alert and leaves the switch as it was.
- The web's restore runs from `followQueueState` only while the edge node reports `running` (`getCadreNode()` is null during a start); `ensureReady` covers the chat strand once the node is running.

## Review findings

Read the implement diff first (kit, both apps, schema copies, docs), then the handoff.

**Found and fixed**

- **The saved offline mode was dropped by most restarts on the phone (defect, reachable now).** `EdgeNode.setStrandOfflineMode` saved the mode in the start record, but the kit's `resolveOptions` carried only `origin`/`formerPartyId` forward from it. The RN app starts from options that never name the mode: Settings → Disconnect → Connect builds `{ partyId, bootstrapAddrs, relayAddrs, noiseCryptoMode }`, and the background runner's cold start (`use-cadre.ts` `ensureNode`) reuses `optsRef`, captured before the switch changed. Either start came up online and overwrote the saved start without the mode, contradicting the docs ("a background restart ... starts every strand in it"). Fixed at the kit, so every start path is covered: options naming no `strandOfflineMode` take the saved start's, whatever its party (`edge-node.ts` `resolveOptions`; documented on `EdgeNodeOptions.strandOfflineMode` and in `docs/strands.md` → "On the edge node"). The web app (`startOptions` spreads the saved start; `restart` spreads `edgeNode.options`) and push wake (saved options) already kept it. Pinned by extending the new phone-node test: after the change, stop and start with options naming no mode, and the node and the saved start are still offline.
- **Web offline checkbox stayed toggled after a failed change.** `checked={msgs.offline === true}` is one-way and `msgs.offline` does not change on failure, so nothing re-rendered the box the click flipped. `Messages.svelte` now resets the input on failure. (The RN `Switch` is controlled, so it already reverted.)

**Checked, no change**

- Kit call: runs in turn with start/stop/join; `changedOfflineMode` is keyed by node and cleared on stop; `strand:started` is emitted synchronously before `addStrand` returns, so no app transaction begins in the built-in mode first. The listener needs no removal (the node is discarded on stop).
- Restore of marks: `database.offline` is a stable object per database build (`strand-database.ts`), and `instance.database` is cleared when a database closes, so the `WeakSet` dedupe holds and the `getStrands()` sweep never touches a closed database. The restore's status reads and its state update run in one synchronous step after the record read, so no live status can slip between them. Record add/remove run in one queue, so a settle after a send removes after the add.
- Marks: online sends unchanged (`status()` returns nothing for an online transaction, so the old durability rule applies); `discarded` clears; refused rows become a notice once the poll drops the row. Docs (`docs/reference-app-rn.md`, web README, `docs/strands.md`) match the behaviour.
- Tests: the one added kit test pins a stated contract with real branching (built mode vs changed mode, saved start); kept and extended. The `use-chat.spec.ts` mock change is required wiring. No UI tests, per the ticket; none cut.
- Duplication across the two apps (`send-marks.ts`, `queued-messages.ts`): left as is; it follows the apps' existing mirroring, and a kit-level map would serve only these two reference apps. Not filed.

**Tripwires recorded**

- The kit call overrides a mode an app set on one strand: `NOTE:` at `followOfflineMode` in `edge-node.ts`.
- Queued-message record entries for a strand never published again are never pruned: `NOTE:` on `forStrand` in both `queued-messages.ts` copies (matters only once an app has a leave-strand action).
