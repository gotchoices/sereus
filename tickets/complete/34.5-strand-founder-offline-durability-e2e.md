# What shipped

A sixth test in `packages/integration-tests/src/scenarios/strand-membership-closed-strand-e2e.integration.ts`:

> `serves the strand's founding membership from the joiner alone after the founder stops`

Three phases, in a load-bearing order:

1. **Wait for peer-join catch-up through the RAW BLOCK STORE only** — whole-store coverage
   (`founder ⊆ joiner`, no narrowing). Not a `joinerDb` read: a read issued through the joiner can
   itself pull the block in (`CoordinatorRepo.get` → `restoreCorroborated` → `acquireBlockFromCohort`
   → `saveReplicatedBlock`), placing the very bytes this step waits for. The timeout message says in
   words that a failure here is a **catch-up** failure (`cadre-core/src/strand-backfill.ts`), not an
   offline-durability failure.
2. **Stop the founder, then poll the joiner's strand libp2p node down to zero connections.** Polled,
   not asserted once — transport teardown is not instantaneous, and one leftover connection would let
   the reads below be answered over the wire.
3. **Only now read `joinerDb`.** `Header`/`Member`/`Manager` counts ≥ 1, `Header.Type` is `'c'`, the
   founding member's key resolves by keyed equality, and the founding manager's key comes back from an
   unfiltered `Manager` scan.

No product code changed — this is test + docs only. The founder is never restarted;
convergence-after-reconnect stays out of scope.

Docs: `docs/cadre-consistency.md` → *What Ships Today* (implement pass), plus `docs/architecture.md`
→ *End-to-end coverage* and the test-count note in `docs/STATUS.md` (review pass — see findings).

## Review findings

### Fixed in this pass (minor)

- **Triplicated coverage-gate block (DRY).** The "poll `waitUntil` for block coverage, and on timeout
  re-run the comparison outside the wait so the missing block ids are named" shape appeared **three
  times** — twice in the fourth test (narrowed and whole-store) and once in the new sixth. Extracted to
  one `awaitBlockCoverage(source, target, description, failure, options?)` helper; each call site keeps
  its own distinct failure wording, which is the only thing that legitimately varied. Net −33 lines.
  Caveat: the fourth test dies on the tracked pre-existing failure *before* reaching its gates, so the
  `include`-narrowed call path is currently covered by typecheck only; the un-narrowed path runs green
  in the sixth test.
- **Isolation asserted only BEFORE the reads.** The test polled the joiner to zero strand connections,
  then read — but never re-checked afterwards, so a connection landing mid-test would have been
  invisible and every assertion would still have passed. Added a closing
  `expect(getConnections()).toHaveLength(0)` with the reason stated inline.
- **Docs were stale beyond the one file the implement pass touched.** `docs/architecture.md` →
  *End-to-end coverage* narrates each test in this file one paragraph at a time and stopped at the
  fifth; added a paragraph for the sixth (what it proves, why the zero-connection poll is polled, the
  measured first-read latency, the optimystic dependency, and the two deliberate scope exclusions).
  `docs/STATUS.md` still said the file "has grown to **five** tests"; corrected to six, and its "four of
  the five are intermittent" line re-stated against the 2026-08-03 measurement.

### Filed (major)

- `backlog/debt-offline-read-of-post-dial-strand-rows` — only the BOOTSTRAP rows are proven durable
  (header, founding member, founding manager). A row written *after* the two nodes are dialled together
  and then read with the founder gone is not covered by any test, and it takes a different route to the
  joiner (per-commit replication rather than the catch-up sweep). The implement pass flagged this
  honestly; it is a coverage extension, not a suspected defect, so it is parked in `backlog/`.
  Board check: three open tickets name this file — `debt-composite-pk-point-lookup-unreliable-untracked`
  (lookup shape), `debt-hoist-strand-tombstone-helpers` (helper location) and
  `debt-replication-proof-above-cohort-size` (strands larger than four machines). None of the three
  would ever be worked together with this arm, so it is filed fresh rather than appended.

### Recorded as tripwires, not tickets

- The coverage gate re-indexes both stores and does one content-bytes lookup per source block on every
  250 ms poll — O(blocks) per attempt. Free at the 20–29 blocks these tests hold. Parked as a `NOTE:` on
  `awaitBlockCoverage` naming the incremental-compare fix if a scenario ever gates on thousands of
  blocks.
- Whether a collection-level cache could satisfy a repeated read from memory and hide a block the joiner
  does not hold was already parked by the implement pass, in the comment on the keyed `Member` lookup at
  the exact site. Left there; not re-tagged.

### Checked and found clean (with reasons, not "looks good")

- **Zero-connection assertion covers the strand libp2p node only, not the control node.** Confirmed
  correct rather than accepted: coordinator selection runs per key-network in
  `Libp2pKeyPeerNetwork.findCoordinator`, and the strand database's transactor is bound to the strand's
  own libp2p node, so a control-network connection can neither rescue nor contaminate a strand read.
  The implementer listed this as an unverified reading; it is now a read one.
- **Resource cleanup / double-stop.** `founderNode.stop()` is a step of the test, so the `finally` hands
  `stopBoth` an `undefined` founder once it has succeeded; if `stop()` rejects, the flag stays false and
  teardown retries. `stopBoth` settles both stops in parallel and logs rather than rethrows, so a
  teardown fault cannot mask the failure that brought us there.
- **Vacuity floors.** `founderStore` and `joinerStore` come from two separately constructed captures, so
  `founder ⊆ joiner` cannot pass by comparing a store with itself; `readBlockIndex` throws rather than
  returning an empty index when the backend lacks `listBlockIds`; the coverage gate would pass vacuously
  only on an empty founder store, which the logged block counts (20) contradict.
- **Lookup shapes.** The keyed `where Key = ?` on `Member` is a presence-by-equality assertion, which
  this file's rule permits (a point-lookup miss fails rather than passes), and the same key is asserted
  again through the scan-based `memberKeys`, so the two shapes disagreeing is itself a failure. The
  `select Type from Strand.Header` read is a shape the bring-up gate never issued against `joinerDb`,
  which strengthens the cold-read argument the implementer could only make by design choice.
- **File header inventory.** "SIX independent tests", "four of the six end with rejected writes" and the
  "first, second, third and fifth" visibility list are all consistent with the new test, which issues no
  rejected write and is not a visibility-only test.
- **Error paths.** Both `waitUntil` gates throw on expiry; step 1's message explicitly distinguishes a
  catch-up failure from an offline-read failure, and step 2's names what it was waiting for. No
  swallowed exceptions, no `it.skip`, no loosened assertions anywhere in the diff.
- **Type safety.** No `any`; `libp2pNode!` non-null assertions match the established pattern in the five
  sibling tests. `BlockCoverageOptions` is imported as a type.
- **Source hygiene.** File is 1330 lines and its comment density is high, but both are the established
  shape of this file (every test carries a why-this-order preamble) and the review's extraction reduced
  rather than grew it. Not flagged as size debt: no measurement here supports a split that the file's
  own per-test isolation does not already provide.
