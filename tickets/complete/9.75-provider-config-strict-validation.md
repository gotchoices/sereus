# cadre-provider: strict config validation

## What shipped

The provider's `loadConfig` runs the same pipeline as cadre-cli, on `@serfab/config-check` (landed in `ticket(implement): provider-config-strict-validation`): parse the file, write each `PROVIDER_*`/`STRIPE_*` variable over it on its own, check the result against field tables typed against the config interfaces, and merge only the validator's output over the defaults. An unknown key, a `null` block or an ill-typed value cannot reach the server or the `CADRE_PUSH` block handed to a tenant's node, which is the cross-package defect the ticket was filed for: one stray key under `push` used to stop every affected tenant node at provision time, long after the provider had started cleanly.

Operator-visible changes: a misspelled key refuses start naming the key and its nearest accepted spelling; `PROVIDER_BILLING_ENABLED=yes` and `PROVIDER_PORT=3000abc` fail start instead of meaning false and 3000; `PROVIDER_AUTH_MODE=apikey` fails start instead of turning every request into a 401; each environment variable works on its own (the acknowledgement variable no longer needs `PROVIDER_AUTH_MODE` beside it); `storage.type: file` without a path fails start instead of silently running in memory; `memoryLimit: 512MB` fails start instead of running the container with no limit; `--port 80x` is refused; values under `push` and `billing` are never echoed into an error.

`@serfab/config-check` gained `recordOf` (a mapping under operator-chosen keys such as tenant ids) and `concealUnder` (subtrees described by kind only in messages); cadre-cli's messages are unchanged. cadre-provider gained the stale-build guard it lacked, now that it has a workspace dependency, and `docs/testing.md` no longer names it as the unguarded package.

## Review findings

Reviewed the implement diff file by file before the handoff, then ran the built CLI against hand-made configs to probe the edge cases the handoff listed and a few it did not.

**Checked and found sound:** the merge order and that only accepted keys reach `deepMerge`; attribution of a problem to the variable whose written path is the longest prefix (a file typo beside a variable-written sibling is blamed on the file); `null` blocks treated as absent and `null` leaves rejected; secrets kept out of every message path (`secretString` for leaves, `concealUnder` for `push` and `billing`, the debug dump redacted); the `--port` check running inside the existing catch so the exit code and prefix are unchanged; the field tables compile-checked against the config interfaces; the README example config and `example.provider.yaml` both loading; no `PROVIDER_*` or `STRIPE_*` usage anywhere else in the repo (no compose file or doc breaks under the stricter boolean and number parsing); cadre-host typechecks without the removed `loadEnvConfig`; the stale-build guard wiring and its companion spec.

**Fixed in this pass (minor):**

- The loader's comment claimed its `(no config file)` label is never printed. It is: `PROVIDER_STORAGE_TYPE=file` with no path, and no file, printed `Config (no config file): storage.path is required …`, because the cross-field rule's key was written by no variable. The label now reads `(no file; environment only)` and the comment says when it appears.
- An inverted `docker.portRange` (`start: 20000, end: 10000`) passed `check` and then killed `start` with the allocator's `Invalid port range` message, which names neither the key nor the file. Added a `refine` on the block (end must be at least start, both at least 1, since the allocator refuses 0) with one test.
- The handoff's open question on request-supplied resources: a create request's `memoryLimit: "512MB"` passed the route as "a string" and started the container with no memory limit at all. The route's `validateResources` now uses the same `parseMemoryLimit`/`parseCpuLimit` the config validator and the orchestrator use, so unreadable text is a 400. Two cases added to the existing wrong-typed-fields table in `bootstrap-node-validation.test.ts` rather than a new spec; the orchestrator's comment updated to say both sources are checked upstream.
- `check` printed the full config, Stripe keys and push private keys included, to stdout. It now prints through the loader's redaction (`redactConfigSecrets`, exported), and says so in its heading. README updated for all three rules.

**Tests:** the implementer's five in `config-validation.test.ts` each pin one behaviour and stay; none restate the implementation. One added for the port-range rule, two rows added to the route table for unreadable limits. The `auth-closed-default` and `push-validate` suites were only moved off `process.env`; their `validateAuthConfig` unit cases predate this ticket and were left.

**Tripwires recorded:** none new. The implementer's `NOTE:` in `config-check`'s `cloneBranch` (a scalar echoed before `concealUnder` applies, reachable only when the file puts a secret where a block belongs and a variable writes under that block) stands as the right disposition; nothing in this pass changes its odds.

**Considered and declined, no ticket:** `recordOf` accepting a `__proto__` tenant id would set the output object's prototype rather than an own key. The id is provider-generated, no global prototype is touched, and the file is the operator's own; not worth a tripwire. `parseCpuLimit` and `parseMemoryLimit` accepting `"0"` (Docker reads 0 as unlimited) is unchanged behaviour and a deliberate operator choice. `concealUnder` covering all of `billing`, so `billing.enabled: "yes"` reports `got a string` rather than the value, is as the ticket specified.

**Tickets filed:** none. Every finding resolved inline and no site is claimed by an open ticket (checked with the site-claim grep over `backlog`, `fix`, `plan`, `implement`, `review`).

## Known limits carried forward

- Programmatic `loadConfig({ overrides })` is typed, not validated, as before; `validateAuthConfig` and `validatePushConfig` still run after it.
- A `portRange` split across the file and the defaults (file sets only `start`, above the default `end`) is caught by the allocator at start, not by the validator, which sees one layer.
- The README's example error uses a hypothetical `/etc/cadre-provider.yaml` path.
