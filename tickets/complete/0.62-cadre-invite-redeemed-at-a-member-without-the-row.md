# Redemption at a member that never held the invitation row

## What shipped

`CadreInviteHandler.seatAndRedeem` now runs: request checks, then the liveness check and push of the member's control store to the device (`catchUpDeviceIfLive`), then the seat of the bundle's row (`seatCadreInvite`), then the redemption. The device is in the member's control write cohort from the moment it connects, so the seat is already a write it must hold; pushing first lets that write commit on a member alone with the device.

`ControlDatabase.isCadreInviteLive` takes the invitation row instead of a key. It judges the row the node holds, or, when it holds none, the bundle's copy only if its issuer signature verifies (`verifyCadreInviteRow`), so a forged copy naming a real owner gets nothing pushed. The seat remains the authority on admission.

Harness: `peerDialGate({ inbound: true })` also refuses inbound connections from a denied peer; `startPinningMember`, `admitMember` and `redeemWithRetry` moved to `harness/cadre-invite.ts` and are shared by both invitation scenarios.

Tests: a protocol spec case for the forged row (no push, `issuer-unknown`, nothing seated), and `cadre-invite-row-unreplicated.integration.ts`, where the owner mints while cut off from the member and stops, and the device must join on its first attempt. The implementer measured that the scenario fails with the old order (second attempt needed, first refused `internal`).

Docs: the architecture enrollment section states the order and why, names the new scenario, and links the fork limitation.

## Review findings

Read the `ticket(implement): cadre-invite-redeemed-at-a-member-without-the-row` diff first, then the handoff.

**Checked and correct.**
- Order and error handling: a failed liveness read (for example `cohort-unreachable` on a member whose `CadreInvite` blocks lag) is caught and logged, and the writes go ahead; a refused seat after a push is covered by the extended accepted-tradeoff `NOTE:` in `catchUpDeviceIfLive`.
- Security of the reorder: `checkRequest` verifies only the redemption signatures (made with the invitation key, which a forger can mint), not the row's issuer signature, so the new `verifyCadreInviteRow` call in `isCadreInviteLive` is what keeps a forged row from receiving the control store. The new spec case pins exactly that; without the check the forged row would read as live. Kept.
- Withdrawn copy: `cadreInviteStillOpen` compares the bundle copy's `stampId` against the `CadreInvite` revocation set, so a withdrawal that reached the member blocks the push even when the row did not.
- No import cycle: `peer-authorization.ts` does not import `control-database.ts`.
- Callers: `isCadreInviteLive` has one caller (the handler); the `CadreInviteStore` pick and the spec's stub store are consistent.
- Open tickets touching the moved helpers (`phone-owner-never-leaves-members-cohort`, `fret-evicts-an-address-less-peer-that-disconnects`) reference the scenario file and `buildA`, both still present; nothing stale.
- Tests: both new tests meet the bar (one pins a security contract with real branching, the other is the reproduction of the redemption failure); none cut. `redeemWithRetry` retrying while asserting one attempt is deliberate and documented.
- Docs: `docs/architecture.md` enrollment section, diagram and the integration-tests bullet match the code.

**Fixed inline (minor).**
- `verifyCadreInviteRow`'s doc said only the device runs it; it now names the member-side use (`peer-authorization.ts`).

**Tripwire.**
- The implementer saw a torn seat answered `internal` rather than `conflict` and did not investigate. Both codes are retryable, so devices are unaffected; parked as a `NOTE:` on `writeFailureRejection` in `cadre-invite-protocol.ts`.

**Major: the returning owner cannot mint again.** Not introduced here (the old order formed the same fork, one attempt later), but this ticket surfaced it: an owner that minted while apart from the member, then returns, has every later `CadreInvite` write refused with `content-digest-mismatch`. It is an instance of the class `blocked/forked-control-collection-sync-livelocks` owns (two commits of one collection while partitioned), already appended there as its fourth trigger by the implementer, so no new ticket. In review I turned that section's open question into a decision for the human: how often a user meets it (a phone owner minting with no connection to the home server, in any cadre past its first invitation), a recommended default (wait for the upstream fork healing every trigger needs), the alternative weighed (seat bundle rows into a separate member-written table so only minting owners write `CadreInvite`) with its cost, and what doing nothing means. Severity is high for the feature: it breaks the advertised "minted while alone, redeemable at any member" path for the owner's later invitations.

**Not covered by tests (accepted).** Two devices racing a one-use invitation at a member without the row can both receive the store; this is the existing accepted tradeoff, unchanged.

The implementer's full cadre-core run (2398 passed, 1 skipped) stands; review edits are comment-only.
