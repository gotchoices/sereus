# Node hosts carry WebRTC, opt-in: `network.webrtc`

## What landed

**cadre-core: a `/webrtc` listen kind only a Node host can bind.** `listenTransportKind` (`relay-addrs.ts`) gained a `webrtc` kind read from the outermost transport component, so a bare `/webrtc` and a relayed `…/p2p-circuit/webrtc` classify alike; `/webrtc-direct` deliberately does not, since `webRTCDirect` is a transport nothing here supplies. `resolveTransportOptions` accepts a `/webrtc` entry only from a node that passed `network.defaultTransports` — the Node-only injected transport list, the one thing in the repo that can supply `@libp2p/webrtc`'s Node build — and otherwise adds it to the existing `UnbindableListenAddressError`, whose message now names `network.defaultTransports` and cadre-cli's `network.webrtc`. When accepted, the resolution carries `webrtcIceServers`, the value of `resolveStunServers(network.relayAddrs, network.stunUrls)`; present-but-empty is still the switch (host and LAN candidates only), absent is the only "no WebRTC" answer. New `NetworkConfig.stunUrls` overrides the per-relay derivation with the same spelling the apps take from `VITE_STUN_URLS` / `EXPO_PUBLIC_STUN_URLS`. New `listenTransportNodeOptions(listen)` returns the db-p2p-bound subset (`wsPort` alone), so neither libp2p-node build site hands db-p2p a key it does not know. `StrandNodeAddrs` carries the ICE servers through to strand nodes.

**cadre-core: the transport is loaded on demand.** `node-default-transports.ts` gained `loadNodeWebrtcTransport()` — the one run-time `import()` in the package, because `@libp2p/webrtc`'s Node build reaches `node-datachannel`, which loads a native addon as its module is evaluated and throws where the platform has no prebuilt binary — and `nodeDefaultTransports(listen, webrtc?)`, which adds `webRTC({ rtcConfiguration: { iceServers } })` when the ICE field is present and throws when it is present with no factory. `@libp2p/webrtc` 6.0.33 moved from cadre-core's devDependencies to dependencies.

**cadre-cli: one flag sets all three halves.** `network.webrtc` (`CADRE_WEBRTC`) and `network.stunUrls` (`CADRE_STUN_URLS`) in the config type, the schema field table and the env registry; a `refine` on the `network` block rejects a hand-written `/webrtc` in `listenAddrs`, naming the flag. New `commands/node-network.ts` → `resolveNodeNetwork(network)`, shared by `cadre start` and the one-shot commands, consumes the CLI-only `webrtc` key, always supplies `defaultTransports`, and on the opt-in-with-relay branch loads the transport and appends `/webrtc` to `listenAddrs ?? [DEFAULT_DIRECT_LISTEN_ADDR]`. With the flag on and no relay it warns once and changes nothing.

**Docs** were brought along in the same pass: the cadre-cli README (two config rows, the bindable-transports bullet, a new "Direct connections over WebRTC" section with the platform-support list), `example.cadre.yaml`, `docker/env.example`, `docker/docker-compose.yml`, `docs/cadre/node.md`, `docs/network/relay.md` (a new "Which nodes offer a WebRTC address" sub-section), and `ops/docs/ice-servers.md`.

Implement commit: `ticket(implement): node-hosts-carry-webrtc`.

## Review findings

**Read order.** The implement diff was read before the handoff summary, then every file it touched, then the sites it did not: `node-transports.ts`, `relay-stun.ts`, `webrtc-upgrade.ts` (`canDialWebrtc`), `cadre-node.ts`'s `warnIfAnnounceAddrsDiscardRelay` and `buildControlNodeOptions`, `strand-instance-manager.ts`'s build, `edge-node/listen-addrs.ts`, `config-check`'s `refine` and `specifiedEnv`, `subcommand.ts`'s exit path, `docker/Dockerfile`, `yarn.lock`'s cadre-core workspace entry, and `@libp2p/webrtc` 6.0.33's own manifest.

**Major, fixed in this pass: a `/webrtc` node with no relay was given no transport list at all, so the entry it was allowed to keep was dropped in silence.** `nodeTransportsOption` (`node-transports.ts`) called `network.defaultTransports` only when cadre had generated bare `/p2p-circuit` entries to supervise. With no relay it returned `{}` and `@optimystic/db-p2p` built its own default list — which carries TCP, WebSocket and circuit-relay and knows nothing of `webrtcIceServers`. So a Node host that passed `defaultTransports` and a `/webrtc` listen entry with no `relayAddrs` passed the new acceptance check, got no WebRTC transport, and libp2p discarded the address with no error, since a sibling TCP address carried the start. That is the exact defect `resolveTransportOptions` was added to prevent, reappearing on the node that was allowed to keep the entry, and `nodeDefaultTransports`'s guard throw could not fire because the function was never called. Not reachable through cadre-cli, whose flag requires a relay and whose schema refuses a hand-written entry — reachable today by a programmatic Node embedder, which is a documented way to build a node (`docs/cadre/node.md` → Configuration) and a configuration the code explicitly endorses: `ListenTransportOptions.webrtcIceServers` says an empty set is still the switch because ICE with no STUN server finds a LAN path.

Fixed at the root rather than by narrowing acceptance, because the no-relay LAN case is legitimate: the list is now built from `network.defaultTransports` for either of the two reasons cadre has to own it — supervised relay slots, or listen entries naming a transport db-p2p's default list cannot carry — and only the supervised case is wrapped in `withoutRelayDiscovery`. Split into `resolveTransportList` so each reason is stated once. Everything else is unchanged by construction: a node with no relay and no `/webrtc` still inherits db-p2p's list, and a node that passed no `defaultTransports` still logs and inherits it. Verified against the built output through the real control-node mapping, not just the unit: `listenAddrs: ['/ip4/127.0.0.1/tcp/0', '/webrtc']` with `defaultTransports` and no relay now yields three transports where it previously yielded none; the same config with a relay is unchanged at three; a plain TCP config still yields no `transports` option.

**Minor, fixed in this pass.**

- **`/webrtc` had three homes.** `edge-node/listen-addrs.ts` and the new `commands/node-network.ts` each spelled the literal out, while `relay-addrs.ts` is where the component is classified and where `RELAY_SEARCH_LISTEN_ADDR` and `DEFAULT_DIRECT_LISTEN_ADDR` already live — the implement pass exported the second of those for exactly this reason. Added `WEBRTC_LISTEN_ADDR` beside them, exported from `index.ts`, and pointed both sites at it; the entry's own doc (binds no socket, derives its address from each reservation) moved there with it.
- `resolveNodeNetwork` counted `core.relayAddrs` twice; hoisted.

**Tripwire, parked at its site.** `listenTransportNodeOptions`'s allow-list is its destructuring, so a third `ListenTransportOptions` field that *is* a db-p2p option has to be added there or it is dropped silently. Recorded as a `NOTE:` on that function, with why the default is deliberate: the opposite one leaks a cadre-only field into db-p2p's options, which is the failure the function exists to prevent. Not a ticket — there is no third field.

**Considered and left alone.** `warnIfAnnounceAddrsDiscardRelay` names only the `/p2p-circuit` address, though a WebRTC-enabled node also loses its `…/p2p-circuit/webrtc` address to a non-empty `announceAddrs`. It still fires for every such node (the flag requires a relay) and what it tells the operator — relay reachability is discarded, use `appendAnnounceAddrs` — is true of both addresses. Adding a node-kind-specific clause to a general warning buys nothing. The handoff's other deferrals were checked and stand: `WEBRTC_SIGNALING_PROTOCOL` is already classed `transport` in `control-protocol-guard.ts`, so a node also running a relay server has no admission change.

**Verified, found sound.** Every claim the handoff asked a reviewer to confirm holds, plus three it did not raise.

- **The CLI's four shapes**, exercised against the built output: flag off with a relay gives `['/ip4/0.0.0.0/tcp/0', '/p2p-circuit']` and two transports; flag on with no relay warns once and leaves the listen set unresolved; flag on with a relay gives `['/ip4/0.0.0.0/tcp/0', '/webrtc', '/p2p-circuit']`, three transports and `[{urls: 'stun:relay.example.org:3478'}]`; `stunUrls` replaces that set. The strand derivation matches the control node's in all four, and the CLI-only `webrtc` key never reaches cadre-core.
