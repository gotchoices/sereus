## The behaviour under test

When someone joins a cadre by pasting an invitation next to a "seed" (the file
that tells a new phone who else is in the cadre), the app must write the
invitation's owner keys into its local trusted-owner record **before** it applies
the seed — otherwise the check that runs during seed-apply looks at an empty
record and rejects a perfectly good seed.

Every call the view models make to the node is appended to one shared ordered
array, and the tests assert that array whole, so a reorder fails where two
`toHaveBeenCalled()`s would pass.

### Fixed in this pass

- **The fake was not type-checked against the real `CadreNode`** — the handoff's
  own top known gap. `FakeNode` now declares `implements NodeSurface`, where
  `NodeSurface = Pick<CadreNode, …>` names the nine members the view models
  reach. Verified it bites: renaming `decodeInvite` on the fake now fails
  `typecheck` with TS2420 instead of leaving 100 tests green. Return types are
  now the real ones (`CadreInvite`, `ControlNetworkSeed`, `ApplySeedResult`,
  `StrandInstance`), with the three unavoidable casts collected into
  `fakeStrand()` / `sentinels` / `peerId` rather than scattered through the specs.
- **`implements` alone would NOT have caught the handoff's own example.** A swap
  to `trustOwnerKeys(source, keys)` type-checks either way: method parameters are
  compared bivariantly, and a `TrustSource` string is itself an `Iterable<string>`.
  `trustOwnerKeys` therefore binds through `Parameters<CadreNode['trustOwnerKeys']>`,
  which lands the swap on the `trusted` record's field types instead. Verified:
  the simulated swap now fails `typecheck` with TS2322.
- **An unreadable *seed* surfaced a raw `SyntaxError` in the modal.** The invite
  path was deliberately rewrapped with copy naming the field; the seed path,
  decoded the identical way (base64url → `JSON.parse` → cast), was not — so a
  typo'd seed paste read `SyntaxError: Unexpected token < in JSON at position 0`,
  naming neither of the two fields the user pasted into. Fixed at the one site
  (`CadreViewModel.decodeSeedOrThrow`), with three tests: the rewrap, the
  original riding along as `cause`, and the anchor staying untouched (a seed that
  never decoded is not an apply attempt, so the "pin sticks past a rejection"
  rule does not reach it). This deepens an existing deliberate divergence from
  reference-app-rn, which surfaces the bare parse error; called out in
  `docs/reference-app-ns.md` so a human can object.
- **`applySeed` evaluated `pinnedOwnerKeys?.length` twice**, once for the policy
  and once for the anchor write — two places deciding the same question. Now one
  `pins` const. (Constructing the policy after the anchor write is safe:
  `pinnedKeyTrustPolicy` is a total function over an array.)
- **Every Settings action outside the seed path was untested** — the handoff
  listed `onConnect`, `onDisconnect`, `onDialPeer`, `onCreateStrand`, `onModalOk`
  and `uuid()` as out of scope but real. 13 tests added: the minted-vs-pasted
  party id and its write-back, trimming, the failure modal that only fires
  because `start()` reports through `status` rather than throwing, dial
  success/failure/blank, strand create success/failure, and modal dismissal.
- **`strandItems` truncation was asserted with an 8-character id**, so
  `title: id.slice(0, 8)` was indistinguishable from `title: id`. Re-asserted
  with a long id, alongside `strandSummary`.
- **Two `refreshStrands` branches were uncovered**: the `strand:error` handler
  (it logs before refreshing) and the `isRunning` guard that stops a late event
  from repopulating the list off a node being torn down.
- **`docs/STATUS.md` said "Both its suites"** of `reference-app-ns` — stale the
  moment two more landed. Corrected, and now names why the view-model suites
  leave cadre-core unmocked.
- **`docs/reference-app-ns.md`** described the unit suite as covering "the
  seed/invite path"; it now covers the whole Settings screen. Rewritten, plus
  the `implements` guarantee and the seed/invite error copy.

### Found and corrected in the handoff, not in the code

### Tripwires (recorded, not ticketed)

- `test/stubs/fake-cadre-node.ts` — `implements` compares method parameters
  bivariantly, so a same-arity reorder of two mutually-assignable parameter types
  is invisible to it. Closed for `trustOwnerKeys` (the one place argument order
  is load-bearing) via the real parameter tuple; noted at that site so the next
  person reaching for the same trick on another method knows why it is written
  that way.
- `test/stubs/nativescript-core.ts` — every `vitest run` prints one cosmetic Vite
  sourcemap warning from `@nativescript/core`'s own `.js.map`. Harmless today;
  the fix to reach for is noted at the site if a zero-warning CI gate ever lands.
- `test/stubs/nativescript-core.ts` — why the stub must not be widened to
  `ObservableArray`.
- `vitest.config.ts` — why the alias `find` is an anchored regex rather than the
  plain string a reader would reach for first.
- `docs/reference-app-ns.md` — the NS-only error-copy divergence from
  reference-app-rn, so whoever next touches either app's paste handling sees that
  the two now differ on purpose.
