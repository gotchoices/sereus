# Joins from other parties are recorded party-wide

## What was built

A strand joined from another party has two records (`joined-strand-store.ts`):

- **Party-wide:** a `CadreControl.JoinedStrand` row. Once it exists it is the authority: every machine's strand watcher offers it, a storage replica host launches it, and the party's other devices get `strand:discovered` for it.
- **Machine-local:** the `KeyStore` record (`JoinedStrandStore`), now a queue of joins not yet published, forgotten once a successful read shows the party-wide row.

`PartyJoinedStrandLedger` is the seam over the table (`list`, `names`, `canSign`, `publish`, `remove`); `CadreNode.createPartyJoinedStrandLedger` implements it over `ControlDatabase`. `JoinedStrandSession` (renamed from `JoinedStrandRows`) unions control rows, party-wide rows, local records and session-kept entries for the watcher; `syncWithParty` publishes local records and removes rows a self-revocation queued, from the connected branch of `reconcileControlCohort`, on owner machines only (`enrolledOwnerSigningKey`: seed-bootstrap owner key **and** enrolled in `OwnerKey`). `forgetJoinedStrand` leaves party-wide (`leave`), throwing on a non-owner machine when a party-wide row exists, and when the table cannot be read.

Implementation commit: `ticket(implement): party-wide-joined-strands`. The implement handoff listed these deliberate deviations, all kept: the stricter owner gate; `forgetJoinedStrand` throwing when the table is unreadable; a removal queued even for a local-only revoked join; `rememberForeign` cancelling a queued removal before its early returns; session-kept entries kept while a party-wide row still names them; the relay-connection residual of `getControlConnectionCount`.

## Review findings

**Checked:** the full implement diff (`joined-strand-store.ts`, `cadre-node.ts` adapter, owner check, reconcile wiring, `forgetJoinedStrand`, `rememberForeignStrand`, `forgetRevokedJoin`, `rememberFormedStrand`), how `ControlDatabase.queryJoinedStrand(s)`, `deleteGuardedRow` and `readRows` behave on a missing row and on a never-written block, the `addStrand` `rememberable` gate, the watcher's failed-poll path, the tests, and every doc the change touched (`docs/strands.md`, `docs/architecture.md`, `docs/api.md`, `types.ts`, `index.ts`, release notes).

**Found and fixed in this pass (minor):**

- **A leave could be undone by a publish already in flight on the same machine.** `syncWithParty` checks `names()` (no row), then `leave` removes nothing and forgets the local record, then the publish inserts the row: the party keeps a strand the app just left, and every machine re-offers it. Fixed by running `leave`, `forgetAfterThisSession` and `syncWithParty` one at a time (`JoinedStrandSession.serialized`). New test `does not let a publish already checking for the row land it after a leave` fails without the fix.
- **Local records were deleted on the word of a stale list.** When the party-wide read failed, `withControlRows` still forgot a local record whose id was in the last-good list, which may predate a sibling's leave the record re-joined after; the join was then lost once reads recovered. Now a local record is forgotten only when a control row or a party-wide read that succeeded this poll names it (`partyWide()` returns `fresh`). The first session test gained an arm for this that fails without the fix.
- **A published join could drop out of the poll.** After `publish` forgets the local record, a failed party-wide read before any successful one offered neither record, so the watcher would detach the strand, and a self-revocation in that window found no row to queue. `publish` now adds the row it inserted to the last-good list. No test: a one-line consequence of the same "last-good list" contract the first test pins.
- **`addStrand` of a foreign row recorded nothing when the new table could not be read.** `rememberForeign` now goes through `namedByParty`, which logs and answers false on a read failure (a machine cut off from its party before it received the `JoinedStrand` block fails `cohort-unreachable`). Recording is the safe side: a duplicate local record is drained by the next poll that reads the table. `formStrand`'s path was unaffected (`remember` does not read the table).
- `docs/strands.md`: a doubled parenthetical in the sibling-revocation limit; added the two new guarantees to "Offering". `docs/api.md`: `forgetJoinedStrand` also throws when the party-wide table is unreadable (was only in the code's `@throws`).

**Tripwires / NOTEs:** none added; the implement's four NOTEs (sibling detach on revocation, `Strand`/`JoinedStrand` id shadowing, sibling publish racing a leave, poll cost of the party-wide read) were read and are accurate. The sibling-publish NOTE covers the cross-machine version of the race fixed above, which serialization within one session cannot reach.
