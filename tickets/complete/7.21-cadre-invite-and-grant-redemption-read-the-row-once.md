# Cadre invitation and owner grant redemptions read the row once

Split from `plan/formation-and-redemption-read-each-row-once`. Siblings: `formation-responder-reads-the-invitation-once`, `joiner-hands-its-join-to-the-launch`.

## What landed

Implementation: `ticket(implement): cadre-invite-and-grant-redemption-read-the-row-once`.

- `MemberRedemptionHandler` (shared member side of `/sereus/cadre-invite` and `/sereus/owner-grant`) has a `readHeld(request)` hook. `decide` calls it once, after the checks that cost no database work, and passes the held row (or null) to `isLive(request, held)` and `redeemAdmitted(request, remotePeerId, held)`. The base class has a third type parameter, `Held`. A failed `readHeld` is answered `internal` (retryable; nothing written).
- `ControlDatabase.isCadreInviteLive(invite, held, nowMs?)` and `isOwnerGrantLive(grant, held, nowMs?)` no longer read the row; they judge `held`, else the bundle's copy once its issuer signature verifies. `held` is required, so no caller can fall back to judging the copy by omission.
- Both handlers seat the bundle's copy only when `held === null` (private `seat()` per handler).
- `redeemCadreInvite` / `redeemOwnerGrant` take an optional `held` and then skip their in-lock read. Callers pass only the row read from this database, never the bundle's copy. After a fresh seat nothing is carried and the in-lock read stays.
- `CadreInviteHandler` builds the reply's `peers` before the redemption write; the list lacks the device's own new row, which the device drops anyway (`cadre-node.ts` filters `reply.peers` by `selfPeerId`).
- Replies carry `held ?? request.invite` (resp. `grant`).
- `CadreNode.redeemOwnerGrantLocally` reads the grant once, seats only when absent, and carries the row into the liveness check and the write.

Measured by the implementer (`message-cost-accounting`, invite case, phase "B redeemCadreInvitation"): the answering member's `CadreInvite` block reads went from 4 to 2; `CadreInviteUsage` stayed at 6 (the use count is read twice on purpose: once to decide the push, once in the lock to decide the seat); `CadrePeer` stayed at 12, because the first reader after the commit now loads the view the reply used to load. Phase totals moved within run-to-run noise.

## Review findings

**Can the carried row weaken the write's checks? No.** Checked `schemas/control.qsql`: `CadreInvite` and `OwnerGrant` carry `NoUpdate check on update (false)` and `NoDelete check on delete (false)`, so the row read before the lock is the row a locked read would return. The in-lock bodies use `issuerKey` (written as `VouchOwner`), `totalUses` (seat cap) and, for grants, `label`; all are fixed at insert, and `IssuerKey` is pinned to the verified signer by `AuthorizedInsert`. Withdrawal is a `Revocation` row, which the `NotRevoked` / `Authorized` CHECKs still read inside the committing transaction. The only rows ever passed as `held` come from `queryCadreInvite` / `queryOwnerGrant` on this database; the bundle's copy reaches the write only through the seat, whose `AuthorizedInsert` verifies it.

**Docs gave the wrong reason for that safety — fixed.** `member-redemption.ts` (class doc), `control-database.ts` (`redeemCadreInvite`'s `held` doc) and `docs/architecture.md` ("What stays plain SQL") justified the carried row by "never deleted and every column is under its issuer's signature". The signature argument is about a bundle's copy matching the stored row; what keeps the stored row stable is that the schema refuses every update and delete. All three now say that, and the architecture paragraph also notes that the row is read again inside the lock after the redemption seats it.

**Test: vacuous assertion removed.** The implementer flipped the end-to-end case in `cadre-invite-protocol.spec.ts` from "peers contain the device" to "peers do not contain the device". In that fixture the member's peer projection is empty (verified: asserting it contains the member's own peer id fails with `expected [] to include …`), so the new assertion could not fail and pinned nothing. Removed it rather than replace it; the order (peers before the write) is a cost detail, not a contract, and the device drops its own row either way. The other test edits (`untouchable` and issuer-unknown fakes gaining `queryCadreInvite`; `liveHere` helper in `control-owner-grant.spec.ts`) are needed for the new signatures and keep the same four outcomes. No tests added.

**Judgement calls from the handoff, each accepted:**
- Reply row is the held row: the device's `verifyRedeemReply` checks the key, a trusted issuer and the row signature, so receiving the stored genuine row is correct; for an honest device it is identical to its copy.
- `readHeld` failure answered `internal` rather than via `writeFailureRefusal`: both codes are retryable (`CADRE_INVITE_REJECTION_RETRYABLE`) and nothing is written, so the device moves to the next address either way. No change.
- Liveness after a fresh seat judges the bundle's copy (local grant path previously re-read the seated row): liveness is only the pre-check that decides the push / the approval prompt; the write still reads the stored row inside the lock and enforces every condition. A difference needs a second row signed by a real owner under the same key.
- Peers built before the write: on a refusal from the redemption write the read is wasted, but it is normally served from the warm membership view. The measured phase total did not drop, so the gain is limited to the reply itself. Left as is.

**Open-invitation minor (skip self in `resolveInvitationSiblings`):** confirmed by reading that `listAuthorizedMembers` → `authorizedAmong` already filters `row.peerId !== selfPeerId` (`cadre-node.ts`), so no change was needed.

**Other angles, nothing found:** type safety (no `any`; `Held` threaded through both subclasses; `...(held ? { held } : {})` is the repo's optional-property idiom); resource cleanup (the admission release still runs in `decide`'s `finally`); DRY (the two `seat()` helpers differ only in error type and wording, matching the existing per-protocol split); no other callers of the changed signatures outside `cadre-core` (grepped `packages/`). File size of `cadre-node.ts` is already tracked by `debt-cadre-node-single-file-size`.
