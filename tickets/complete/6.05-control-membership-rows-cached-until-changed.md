# Control membership rows kept in memory until they change

## What landed

**`MembershipView<Row>`** (`membership-view.ts`) holds one table's rows, the time the load that produced them started, a generation counter, and one in-flight load per `retry` flag.

- `read(retry)` serves the kept rows while they are younger than `MEMBERSHIP_VIEW_MAX_AGE_MS` (the default reconcile interval, 15 s). Otherwise it joins the in-flight load with the same `retry` flag or starts one, so a caller holding the write lock (`retry: false`) never waits out a retrying load's backoff.
- A finished load keeps its rows only if its loader said `installable` and no `invalidate()` ran since it started. Its own callers get its rows either way. A failed load keeps nothing and rejects.
- `invalidate()` is synchronous and only sets fields (it runs inside the committing call): it bumps the generation, drops the rows and forgets the in-flight loads.
- `readThrough(retry)` runs the loader without serving, joining or keeping.
- The clock is `performance.now()`, so a wall-clock step cannot stretch the maximum age.

**In `ControlDatabase`**: three views (`Revocation`, `CadrePeer`, `OwnerKey`), each loaded by one full-table scan through the existing read path. `readRowsOnce` now also reports whether the read took the committed-read path, and such a load is not kept (no change event is guaranteed for a table only provisionally initialized). `readMembershipRows` reads SQL directly when a caller under the write lock has an explicit transaction open (it may see uncommitted rows, and a rollback fires no event). `initialize()` subscribes once to the three tables through the table-change registry, with only an `onInvalidate` hook; `close()` disposes it and empties the views. `queryRevokedStamps`, `queryRevocations`, `queryCadrePeers`, `queryOwnerKeyRows` / `getOwnerKeys` and `queryPeerRecord` derive their answers from the rows and return fresh objects each call. The isolated-node rule (a `cohort-unreachable` failure reads as "no revocations") moved to `readRevocationRowsOrNone`; the empty answer is not kept, because a failed load keeps nothing.

Docs: `docs/architecture.md` → "Membership rows view" (what is kept, when it is dropped, bypassed, or not kept, the maximum age, what stays plain SQL), plus a Consumers paragraph under "Table change subscriptions".

**Choices that differ from the plan**: no separate `clear()` (`invalidate()` already forgets in-flight loads); `loadedAt` is when the load started, so the age bounds how old the rows can be; the maximum age follows the default reconcile constant, not a node's configured `controlCohort.reconcileMs`; the subscription is taken before `initialized = true`, through the registry directly, so a throw leaves the database uninitialized rather than half-initialized.

## Known gaps and notes for the reviewer

- The re-pinned consult spec has not run (above).
- The view-off cost figures are single runs, and the strand case has no view-off comparison.
- Comments that still describe the ledger marker as what makes `Revocation` held, and that cite this spec as pinning that state (`cadre-node.ts` cost NOTEs in `runReconcileControlCohort` and on `syncOwnerAnchor`, `link-budget.ts` ~396), are now inaccurate. They are listed for rewriting in `implement/revocation-ledger-marker-removed`, so I left them alone.
- An unlocked read made while a locked write body runs takes the committed-read path, so its load is not kept. During write-heavy flows a cold view stays cold for unlocked readers until the bodies finish. Such rows would be safe to keep once the table is fully initialized, but this layer cannot see that. Revisit if membership reads during writes still dominate a measurement.
- The membership-gate refresh passes `retry: false` on unlocked triggers too (the NOTE in `readRowsRouted`). So when another writer's explicit transaction is open, the refresh takes the bypass: the rows are correct, but nothing is saved.
- `queryPeerRecord` now scans the `CadrePeer` rows in memory instead of doing a primary-key point read. The table is bounded by the party's machines.
- No spec was found that writes through a different `Database` instance or reads membership inside a raw-handle transaction. If a test fails with "row never appears", suspect an invalidation that did not fire.

## Review findings

Reviewed the two implement commits (`ticket(implement): control-membership-rows-cached-until-changed`, the source change and the later consult-budget re-pin) before the handoff.

**Correctness, checked and holding:**
- Read-your-writes. Quereus awaits its post-commit watcher dispatch inside the commit path (`../quereus` `database-transaction.ts` → `runPostCommitWatchers`), so `onInvalidate` has run before a write returns. A load that started before the change captures the older generation and installs nothing; the view's race test covers this.
- The in-transaction bypass in `readMembershipRows`. At first it looked redundant, because `readRowsOnce` asks for a committed read under the lock when a transaction is open. It is needed: Quereus refuses the committed-read route while an explicit transaction is open (`_isConcurrentReadEligible`, `../quereus` `database.ts:769`), so that read falls back to the serialized path and sees the transaction's uncommitted rows. The comment and the architecture doc are accurate.
- Committed-path loads are never kept, which also covers an unlocked reader whose load falls back to the serialized path while another writer's explicit transaction is open.
- `close()` invalidates after `disposeAll()`, and `initialize()` invalidates again before re-subscribing, so a load in flight across a close/reopen installs nothing.
- Shared rows. All cached column values are strings, numbers or null (`NodeProfile` is a string union), and every caller builds fresh result objects, so the shared row array cannot be changed through a result.
- Seed application writes no membership rows (it anchors an owner key in node-local state and refreshes the gate), so it does not need a change event.
- `performance.now()` is available in Node, browsers and React Native (Hermes); `control-database.ts` already uses it.
