## What shipped

The stale-build guard already refused to start the integration suite when one of
this repo's own packages had been edited without a rebuild. It now covers the two
sibling projects checked out beside this one — `../optimystic` and `../quereus` —
which reach `node_modules` as symlinks (junctions on Windows) via the `link:`
entries in the root `package.json`'s `resolutions`. Those repos are developed at
the same time as this one, so the suite used to run whatever they last *built*;
an already-landed `@optimystic/db-p2p` fix was investigated three times against a
build that predated it.

`BuildTarget` gained a `location` field:

- **`workspace`** — found by scanning `<repo>/packages`; remedy
  `yarn workspace <name> build`.
- **`linked`** — found by reading `node_modules/<name>` as a symlink
  (`resolveLinkedPackage`); remedy names the sibling's own checkout, e.g.
  `Run in C:\projects\quereus: yarn workspace @quereus/quereus build`, because
  `yarn workspace` cannot reach outside this repository. The checkout is the
  nearest ancestor of the link target whose `package.json` declares `workspaces`;
  with none, the remedy falls back to `Run in <package dir>: yarn build`.

Linkedness is decided by `lstat`, never by package name — which dependencies are
linked changes with `resolutions` and with whoever last ran `yarn install`. A
dependency that is a real directory (installed from the registry) is **skipped**,
never judged: its `src` and `dist` mtimes are packing artifacts, and the installed
copy of `@optimystic/db-p2p-storage-fs` really does have `src` newer than `dist`,
so judging it would report a permanent "stale" no build could clear.

A stale sibling **fails** the run rather than warning. The reasoning is written at
the site in `checkLinkedTarget`'s doc comment: a banner is ignorable, and being
ignored is exactly how the original investigation went wrong; and a grace margin
cannot distinguish "neighbour mid-edit" from "someone forgot to build", because
both present identically as `src` newer than `dist`.

`checkBuildFreshness` — the newest-`src`-mtime versus `dist`-entry-mtime
comparison — was left untouched.

## Review findings

### Checked and clean

- **Entry points.** Every target's `distEntry` was compared against its own
  package's declared `main`/`exports["."]`. All eleven match. `@serfab/cadre-cli`
  intentionally points at `dist/bin/cadre.js` — the binary the scenarios spawn —
  which comes from the same `tsc` build as its `dist/index.js`, so freshness is
  equivalent.
- **Real-tree wiring.** Inspected `node_modules/@optimystic`, `@quereus`,
  `@serfab`. Five optimystic packages plus `@quereus/quereus` are junctions into
  the sibling checkouts; `@optimystic/db-p2p-storage-fs` is a registry copy (and
  is absent from `resolutions`), so it is correctly skipped rather than reported
  permanently stale. `@optimystic/db-p2p-storage-web` is junctioned but is only
  reached from `connect-browser.ts`, a browser path Node never loads — leaving it
  out is right, since adding it would only create false failures.
- **Exclusion set versus sibling conventions.** The guard ignores `*.test.ts`,
  `*.spec.ts`, `test/` and `__tests__/`. Counted files under the sibling `src`
  trees (`quereus` 489, `db-core` 162, `db-p2p` 122): **zero** match any
  test-shaped name, so the exclusions neither over- nor under-fire there.
- **Cost.** The guard now walks roughly a thousand sibling source files.
  Measured end to end at 589 ms *including* Node boot — negligible beside a
  229-second suite. No tripwire recorded because there is nothing to trip.
- **Symlink loops.** `newestMtime` cannot recurse into one: a symlink `Dirent` is
  neither `isDirectory()` nor `isFile()`, so it is skipped outright.
- **Docs.** Every file the change touches was re-read. `docs/STATUS.md` →
  "Testing / CI" describes the extension accurately. Nothing else in `docs/`,
  `AGENTS.md` or any package README mentions the guard, so nothing else went
  stale; `packages/integration-tests` has no README.

### Found and fixed in this pass

- **Two packages the suite runs from `dist` were not guarded at all.**
  `@serfab/quereus-plugin-sereus` is imported by `cadre-core`'s own entry point
  (`strand-database.ts`, and a re-export in `types.ts`), and
  `@serfab/cadre-provider` is re-exported from `cadre-host/src/index.ts` — so
  both load on essentially every scenario, and a stale build of either was
  invisible. This contradicted the `TARGETS` doc comment's claim to list "every
  package a scenario ends up running compiled code from". Both added as
  `workspace` targets (`dist/index.js`), with a comment saying why they are on
  the list despite no scenario importing them directly. The hole predates this
  ticket — it came in with the original guard — but the ticket's own definition
  of the list is what makes it a defect, so it is fixed here rather than filed.
- **A misleading message.** The `unresolved` line for a workspace target read
  "not resolvable from `@serfab/integration-tests`", which describes module
  resolution — but the guard deliberately doesn't resolve modules, and the
  condition it actually hit is that no directory under `packages/` declares that
  name. Reworded to say so. (This branch is workspace-only; the linked path
  builds its own, more specific `unresolved` message.)

### The handoff's open gap is now closed

The implement stage could not observe "guard passes, suite proceeds", because
`../quereus` was mid-edit for the whole ticket and every run aborted at the guard.
The siblings are now built. The guard reports fresh across all eleven targets, and
the full suite ran through it: **29 files, 129 tests, all passing, 229 s**. Both
entries in `tickets/.pre-existing-known.md` passed in this run too (the
three-party replication one has since had a fix ticket; the push-wake one is the
known intermittent). Nothing was skipped, disabled or loosened, and
`.pre-existing-error.md` was not written.

### Filed as new tickets

None. Nothing found in this pass needed work larger than the two edits above.

### Tripwires (recorded, not ticketed)

- Two were already placed as `NOTE:` comments by the implement stage, both in
  `build-freshness.ts`: linked packages are looked for only in the repo-root
  `node_modules`, and each `distEntry` is written out rather than read from the
  target's own `main`/`exports`. Both were re-checked and are genuinely
  conditional — neither is wrong today — so both stay as NOTEs.
- No new ones. The one candidate considered was the cost of walking the sibling
  `src` trees; it measured fast enough that there is no condition to name.

### Known limits, carried forward unchanged

- **Junctions were only exercised on Windows.** The spec creates links with
  `symlinkSync(target, path, 'junction')`, which needs neither developer mode nor
  admin rights on Windows; on POSIX the third argument is ignored and an ordinary
  symlink is created, running the same `isSymbolicLink()`/`realpath` path. That
  path is reasoned about, not observed on a Linux host.
- **Consequence of the hard-fail choice.** While a sibling repo is mid-edit, this
  suite will not start for anyone, including other tickets in this repo that run
  integration tests. Accepted deliberately; the message names exactly what to
  rebuild and where.
- **`assertCadreBuildFresh` and `checkWorkspaceTarget` have no unit tests.** Both
  read module-level repo state (`findRepoRoot`, the cached `packages/` scan) with
  no injection seam, and what they add over the tested functions is a `flatMap`
  and a `join`. Adding a seam would be more machinery than the logic warrants;
  the real-tree run is the coverage, and it was exercised above.

skipped — the regression most likely to reappear as a spurious permanent failure.
