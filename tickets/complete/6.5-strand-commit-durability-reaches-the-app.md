# A strand commit's durability reaches the app

GitHub gotchoices/sereus#44 / optimystic#26. Optimystic's release candidate (linked through root `resolutions`) reports, per SQL commit, who holds what it wrote, and later when a commit held only below full replication becomes held by its whole cohort. Sereus passes that through to the app. The contract is `docs/strands.md` → "A commit's durability".

## What was built

- **`@serfab/quereus-plugin-sereus`**: `SereusPluginResult` gains `onCommitDurability` / `onCommitFullyHeld`, forwarded from the Optimystic plugin; `SqlCommitDurability` and `CommitFullyHeld` are re-exported. `releaseOptimysticPlugin` disposes the plugin's transaction bridge (its durability follower's subscriptions) before releasing the collection factory, on both `shutdown()` and the failed-composition path.
- **`@serfab/cadre-core`**: `strand-commit-durability.ts` holds `StrandCommitDurability` / `StrandCommitHeld`, the `heldElsewhere` rule, and `StrandCommitRecord` (the last 256 commits by transaction id, frozen entries replaced when a commit becomes held; app handlers run try/catch-isolated). `StrandDatabase` subscribes right after `connectToStrand`, unsubscribes first in `close()`, and exposes `commitDurability(tx)`. `StartStrandConfig` gains `onCommitDurability` / `onCommitHeld`, retained with the launch config so a hibernation wake's rebuilt database is wired too. `CadreNode` emits `strand:commit-durability` / `strand:commit-held`.
- **Docs**: `docs/strands.md` section "A commit's durability"; cadre-core README event table; plugin README paragraph.
- **Test**: one integration arm in `joiner-first-commit-over-slow-relay.integration.ts`, "tells the writer a commit made while the other member was stopped is held only here, then held once it returns".

App pattern: `const { Tx } = await db.get("insert into App.X (…) values (…) returning StampId() as Tx")`, then `instance.database.commitDurability(Tx)` → `{ heldElsewhere, followed, report }`; listen for `strand:commit-held` to clear a "not yet delivered" mark. The reference apps do this in `implement/reference-apps-mark-undelivered-messages`.

## Review findings

Read the `ticket(implement): strand-commit-durability-reaches-the-app` diff first, then the Optimystic plugin's `plugin.ts`, `commit-durability.ts`, `txn-bridge.ts` (listeners, `dispose`, `reportCommitDurability`) and db-core's `network/durability.ts` / `network-transactor.ts` to check the contract the code relies on.

- **Defect, fixed: a torn commit was reported `heldElsewhere: true`.** The implementer flagged this as unchecked. A SQL commit with `torn` blocks can succeed: `NetworkTransactor` returns `success: true` with `withTornBlocks(...)`, which clamps a `full` answer to `majority`, and `transactionDurability` carries `torn` into `overall`. The old rule (`rank >= majority`) would then tell the app the change survives this device stopping, while the abandoned blocks are held by nobody. `isHeldElsewhere` now also requires an empty `torn`. Such a commit reports `heldElsewhere: false, followed: false` (Optimystic's follower refuses torn commits), which the strands doc already lists as "nothing will say so". The field doc and the strands.md bullet say so. No test added: it is one more condition on a three-line rule, and reproducing a torn sweep needs a fault-injected multi-cohort commit.
- **Docs, fixed:** cadre-core's README event table, the app-facing list of `CadreNode` events, did not list the two new events; added rows linking to strands.md. Re-wrapped the `NOTE:` in `releaseOptimysticPlugin`, whose middle line ran past the others.
- **Release dependency, recorded:** Sereus now calls `onCommitDurability`, `onCommitFullyHeld` and `txnBridge.dispose()`, which published Optimystic 1.12.1 lacks, while the floors still say `^1.12.1`. Floors stay with `blocked/optimystic-write-made-alone-owes-no-one`; added a line under its "What Sereus does when it lands" saying the raised floors must carry these and Sereus must not be published before.
- **Checked, no change:**
  - Wiring: the only `new StrandDatabase` site passes both listeners from the retained `StartStrandConfig`, so wake rebuilds are covered.
  - Failure paths: a founder-bootstrap throw after subscribing is cleaned up by the caller's `close()`, which unsubscribes; a `connectToStrand` throw leaves nothing subscribed. The plugin's catch path releases the bridge.
  - The plugin follows commits only while a listener of either kind is registered (`reportCommitDurability`), so subscribing before the founder bootstrap is what makes its commits reported; schema-apply commits inside `connectToStrand` are not, as the implementer noted, and apps never hold those ids.
  - `reportHeld` for an evicted record still forwards the event; correct, the app may hold the id.
  - Type safety: no `any`; the plugin result shim declares the three new members.
- **Tripwires, already parked by the implementer:** release order (`NOTE:` at `releaseOptimysticPlugin`: a write begun between release and `db.close()` re-subscribes the follower) and the 256-commit cap (`NOTE:` at `RECENT_COMMIT_LIMIT`). Nothing new parked.
- **Tests:** the one integration arm is the only end-to-end check of a real-node `followed: true` commit and the held event through cadre-core's injected node; kept. No unit tests were added by the implementer and none are warranted beyond the above.
- **Observations carried forward, not acted on:** the stopped member was not named in `unconfirmed` (upstream behaviour, recorded on the blocked ticket); slow-link joins stalling in the scenario's third to fifth arms is recorded on `backlog/debt-libp2p-nodes-built-outside-cadre-core-miss-the-ping-defaults`, and this change adds no network traffic.
