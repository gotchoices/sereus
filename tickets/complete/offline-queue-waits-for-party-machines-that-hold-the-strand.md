# The offline queue waits for the party's machines that hold the strand (gotchoices/sereus#56)

## What was built

Implemented in `ticket(implement): offline-queue-waits-for-party-machines-that-hold-the-strand`. Cadre-core composes a second reachability gate over the strand node's own, built from the party's control database: a block whose cohort names nobody but this node is unreachable while another live, trusted machine of the party has written a `CadreControl.StrandPeer` row for the strand. Only a node offering offline mode builds it, and the plugin asks any gate only in offline mode, so online mode is unchanged.

- `strand-party-machines.ts` (new): `StrandPartyMachines` keeps the last good read of the party's other machines holding one strand (coalesced `refresh()`, a failed read keeps the last answer and is flagged, `settled()` after the first read, `onChange` on a change of the set); `cohortGateWaitingForMachines` is the composed gate, in the ticket's order (inner closed answers closed and reads nothing further; await the first read and ask for another after a failed one; no machines answers open; a cohort naming nobody but self, or whose lookup throws, answers closed).
- `PartyStrandPeers.live` is now `PartyStrandPeer[]` (`{ peerId, strandPeerId }`), so an app can name a machine; `removed` is unchanged.
- Open strands get a `StrandPeer` row too: `launchStrand` wires `partyPeers` for every strand and the runtime build publishes the row for every strand. The membership reconciler still arms for closed strands only.
- Wiring: the tracker is built in `buildStrandRuntime` before the libp2p node when the launch has both `offline` and `partyPeers`, its first read started at once, stopped in `releaseRuntime` (a resume reads afresh), refreshed by `notifyPartyPeersChanged`. `buildStrandDatabase` builds the gate from `node.cohortReachability`, `node.keyNetwork` and the tracker, and `composeStrand` registers it with the collection factory before hydrate, so every table takes it.
- `CadreNode.getUnreachedStrandMachines(strandId)`: the tracker's machines less those with an open connection from the strand node.
- Redial: `StrandRedialDeps.partyMachines` feeds the strand peer ids to the loop; a machine neither FRET nor the seed names is dialed at its address-book addresses and skipped with none; a connected party machine counts as a member.
- Docs: `docs/strands.md` → *Waiting for the party's own machines* and three cross-references; `docs/testing.md` lists the scenario.

## How to use it

An app in offline mode reads `strand.database.offline.status(tx)`; while the hold applies it stays `queued` with `waitingFor: 'cohort'`, and `node.getUnreachedStrandMachines(strandId)` names the machines, whose `peerId` is what `listMachines` and `removeMachine` take. Nothing releases the hold on its own. Debug logs: `sereus:cadre:strand-party-machines`, `sereus:cadre:strand-redial`.
