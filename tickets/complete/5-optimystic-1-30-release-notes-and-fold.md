# Release notes for the Optimystic 1.30 storage upgrade, and the board it empties

Last of the five tickets adopting Optimystic 1.30.0 (tickets 1–4 were the code). This one was prose and board edits; it wrote no tests and the ticket asked for none.

## What shipped

**`.release-notes.pending.md`** gained the release's section — ten headed changes, each written for an app builder embedding `@serfab/cadre-core` or `@serfab/cadre-rn` or an operator running `cadre-cli`, `cadre-host` or `cadre-provider`: the version floor (1.30.0 / Quereus 5.7.1, every machine of a party and every partner of a strand together, nothing to migrate), `storage.open(scope)` replacing `storage.provider`, `quotaBytes` → `allotmentBytes` and the environment variable rename, what a filling node does, which platforms must declare an allotment because they cannot measure free space, the `EdgeNodeStorage` shape change, a strand client now getting a storage scope, blob pieces and records surviving a restart, NativeScript's offline journal, and one bullet saying Quereus 5.7's three behaviour changes reach nothing here so a reader does not go looking.

**`docs/schema-guide.md`** — the `blobref` limit line now says what is actually left (no app-facing way to put or read bytes; a phone holds its strand's blobs eagerly) rather than "kept in memory".

**Board:** `feat-strand-blobs-persist` and `feat-strand-offline-mode-nativescript` rewritten down to their remaining work, each saying in its body that the storage (resp. platform) half landed with this adoption so the next reader does not redo it; `backlog/later/5-quota-enforcement` rewritten to its three still-missing arms (per-strand usage accounting, usage reported for billing, a machine-wide rather than per-network budget) with the "blocked on Arachnode" framing dropped; `backlog/later/3-mobile-resource-awareness`'s one stale `storage.quotaBytes` line replaced; `debt-shared-store-provider-never-exercised-end-to-end` deleted.

**Two web-app e2e fixtures** (`cadre-member.ts`, `formation-responder.ts`) were still on `MemoryRawStorage` / `storage.provider` — leftovers from an earlier ticket in the chain, moved to `memoryNodeStorage()` and `storage.open`.

## Why `debt-shared-store-provider-never-exercised-end-to-end` went

Its subject was the "one `IRawStorage` for every scope" form of `storage.provider`, which ticket 2 removed outright: `OpenNodeStorage` carries a `close()` a shared instance would have closed once per scope, `levelDbNodeStorage` refuses a second call over one handle, and an embedder that wants sharing now gets it from `fileNodeStorage`'s holder counting. The counting invariant the ticket existed to protect moved upstream into `withReadCache` and is tested there. There is no longer a code path for the ticket to exercise.

## The reply to gotchoices/sereus#67 — ready for a human to post, NOT posted

Posting was deliberately left to a human: the issue is outward-facing. The issue's own two gaps were the unregistered `blobref` type (already fixed in 1.24) and blobs lost on hibernate; the reporter's follow-up comment then asked for three things in priority order, and this release answers the first. Suggested text:

> This release (Optimystic 1.30.0, Quereus 5.7.1) answers the first of the three things your comment asked for, and we think it closes the hibernate repro.
>
> **1. A persistent piece store and `kvStore` on strand nodes — done, on every platform.** A node now takes all of its storage as one value (Optimystic's `NodeStorage`: blocks, the node-local key-value store and blob pieces together), and that value has no part a platform can leave out, so there is no longer a way for a node to be built with a file block store and a memory piece store. `CadreNodeConfig.storage.provider` is replaced by `storage.open(scope)`, which returns that whole value; each platform calls its own storage package's factory — files on Node (cadre-cli, cadre-host, cadre-provider), LevelDB on React Native, SQLite on NativeScript, IndexedDB in the browser. A strand node a machine runs as a *client* — holding none of the strand's blocks — now gets a storage scope too, precisely because the pieces it holds may be its own host's only copy. `blob-survives-hibernate.mjs` should pass as written; please re-run it, since the repro lives in your tree and not ours.
>
> **2. `hold: 'on-demand'` for the `device` class — not done.** Tracked in `feat-strand-blobs-persist`, along with the open question of whether that choice follows the node class or becomes a per-machine role. Until it lands, a phone that is a cohort member holds its strand's blobs eagerly, which is the wrong default for a photo library.
>
> **3. Access to the strand node's blob service from the app — not done.** Also in `feat-strand-blobs-persist`. `instance.libp2pNode.blobs` is still the only way in and is still not a supported surface; the decision to make is whether it hangs off the strand handle an app already holds or comes through the SQL plugin keyed on the table. Because of 2 and 3, `docs/schema-guide.md` still says not to declare a `blobref` column yet.
>
> Two things to know about the upgrade itself. Every machine of a party, and every partner of a strand, has to move together: a coordinator on 1.29.1 counts an out-of-space vote as neither an approval nor a rejection, so a writer gets a promise shortfall instead of being told the cohort is full. And a node now measures what it stores against an allotment the operator sets, shrinking its blob read cache as it fills and refusing new data above 95%; on a phone the kit declares that figure for you (2 GiB by default, overridable), because LevelDB and SQLite report no free space of their own.
>
> One limit worth stating plainly, since it bears on a strand whose history is mostly blocks: a node cannot yet free old revisions of blocks it is still responsible for, so a node whose disk is mostly block history reaches its refusing stage and stays there until its allotment is raised. Optimystic's three automatic responses to pressure — ring move-in, ring move-out and the released-block sweep — are all driven by its rebalance reaction, which a Sereus node turns off wherever it arms its own peer-join block catch-up instead, which is every node that serves blocks and was given storage; so peers do not take such a node's ranges here either. Upstream tracks the reclaim work as `feat-cold-range-transform-offload`.
>
> We would take you up on the Galaxy S7 / S21 offer for part 1 whenever it suits.

## Figures this chain moved

- **A phone's storage allotment: 2 GiB** — `DEFAULT_DEVICE_STORAGE_ALLOTMENT_BYTES` in `packages/cadre-core/src/edge-node/platform.ts`, overridable per app through `PhoneNodePlatform.storageAllotmentBytes` on React Native. Declared because LevelDB and SQLite report no free space; the browser deliberately declares none, since IndexedDB reports the origin's own estimate.
- **The refusal threshold: 0.95** of the smaller of the allotment and the backend's free space — upstream's `refuseAbove` default, with `reclaimBelow` 0.40 and `shedAbove` 0.85 beside it (the latter two inert on a node whose peer-join catch-up is armed).
- **Restart timings the suite reported**, for anyone wondering what "survives a restart" costs: the offline-queue restart scenario 52 s; the joiner's first commit over a slow relay, restarting over its kept storage, 277 s, and 313 s for the variant that stays on the slow link.

**Fixed in this pass.**

- **The release notes overstated when Optimystic's rebalance reaction is off.** Two bullets said "every Sereus node turns off the rebalance reaction". It is off only where the node arms its own peer-join block catch-up — `rebalance: { enabled: false }` is gated on `backfillArms` in `strand-instance-manager.ts` and on `controlBackfillStorage` in `cadre-node.ts`, and both source comments say plainly that with the catch-up disabled the reaction stays on. A node given no storage at all, or one whose operator set `backfill.enabled: false`, keeps ring move-in, move-out and the released-block sweep live — and the no-storage case is exactly a node under memory pressure, which is what that paragraph is about. `CadreNodeConfig.storage.allotmentBytes`'s own doc comment and `docs/cadre/node-storage.md` both carry the qualifier correctly; the notes had dropped it. A reader scanning that section for what breaks on mixed versions got a bullet about neither.
