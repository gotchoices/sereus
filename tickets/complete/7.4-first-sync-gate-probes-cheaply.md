# Complete: the first-sync gate probes cheaply and wakes on arrival

## What landed (`ticket(implement): first-sync-gate-probes-cheaply`)

The joining machine's first-sync gate (`StrandFirstSyncGate`) holds a strand database back from the app until the machine holds `Strand.Header` and a read of every `App` table has settled.

- Every probe read is `select 1 from <Schema>."<Table>" limit 1`, the same form the plugin's `openTables` uses. Header held = a row came back; a table is settled = the read did not throw.
- The gate keeps a `FirstSyncProgress` (`header`, `tables`) for its lifetime, and later probes skip what earlier ones settled. The manager's first probe goes through `gate.probeOnce()`, so its findings carry over. A gate lives for one database build.
- Header first and alone, then each pending `App` table in turn, stopping at the first failure.
- `start()` runs probes on a `scheduleRuns` schedule with a 2 s backstop (`DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS`), woken by the strand node's storage-wide change feed (`node.storageRepo.onAnyCollectionChange`, new optional `Libp2pNodeWithRepo.storageRepo`). The first block landing after a probe started triggers one probe 50 ms later.
- Renames: `pollIntervalMs` → `backstopMs`; `DEFAULT_STRAND_FIRST_SYNC_POLL_MS` (500 ms) → `DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS` (2 s). The probe functions are no longer exported.
- Deviation from the plan: the table reads are serialized, not `readConcurrency: 'committed'`. A committed read does not refresh a table that schema apply initialized over an in-memory empty collection before any peer answered, so it would report that table settled and open the gate onto a fork. Recorded as a `NOTE:` on `strandFirstSyncComplete` with a revisit condition, and in `docs/strands.md`. The reasoning is static; the implementer named the scenario that would confirm it.
- Measured (one run each, `@optimystic/*` 1.15.0): no change in either instrument, because the gate never armed in either. The woken path was confirmed once on `harness-topology`'s cross-party share with the backstop raised to 10 s: the founder's backfill push opened the gate 2.1 s after it armed. Figures are on `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS`.

**Correctness: no defects found.**
- Wake scheduling: walked every ordering of `onDataLanded`, `probe()` and the `scheduleRuns` wakes (data during a run; trigger wake firing after the run settled; the backstop firing ahead of a pending trigger). The `landedSinceProbe` flag is cleared synchronously when a run starts, and every path where it is set leaves a wake pending or a run that will read the data. The flag cannot stick with nothing scheduled.
- The feed exists at runtime: `libp2p-node-base.ts` assigns `storageRepo` through `OptimysticNodeAttachments`, and `onAnyCollectionChange` fires for commits, replica pushes (`saveReplicatedBlock`) and read-driven promotions, after the storage critical section. The gate's listener only arms a timer.
- Progress memory is sound, since a collection this machine holds stays held. Stop/open during an in-flight probe is re-checked after the await. Founder, awaiting-seed and released paths are unchanged.
- The serialized-read deviation is the conservative choice and is documented with a revisit condition. Accepted as is.

**Known gaps, accepted.** Data landing between the manager's first probe and `start()` is caught by the first 2 s backstop, as documented on `start()`. Subscribing earlier would make the first probe's own fetches trigger an immediate follow-up, which is no clear improvement. `storageRepo` is typed structurally, matching `keyNetwork`.
