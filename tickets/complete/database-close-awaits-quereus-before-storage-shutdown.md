# Database close awaits Quereus before storage shutdown

## What landed

- `ControlDatabase.close()` (`control-database.ts`): disposes table watches, drains the write queue, then `await this.db.close()` (a rejection is logged and teardown continues), then `collectionFactory.shutdown()` (which stops the control node), then the second watch disposal, membership-view invalidation, and nulls `db` / `initialized` last. The existing `NOTE:` now also accepts waiting on a statement stuck in a network wait (bounded by Optimystic's RPC deadlines), with its revisit condition.
- `StrandDatabase.close()` (`strand-database.ts`): same reorder before `shutdownStrand()`. Two `NOTE:`s: the network-wait tripwire, and that commit-durability / commit-held reports are raised from inside the committing statement through listeners nobody awaits (safe; breaks only if a delivery path starts awaiting its listeners).
- `compose-strand.ts`: two `NOTE:`s reworded to say cadre-core closes the `Database` before releasing the plugin; comment-only.
- `this.db` stays set across the awaits so a concurrent second `close()` (from `StrandInstanceManager.buildStrandRuntime` after a stop released the runtime mid-`initialize()`) awaits Quereus's latched close promise instead of skipping to storage shutdown.
- New spec `packages/cadre-core/test/control-database-close.spec.ts`: reproduction on a real `ControlDatabase` — open iterator, spy on Quereus `close()` and the test's own node `stop()`, assert Quereus closed before the node stopped and before `close()` resolved, and the iterator rejects with `Database is closed`. The implementer confirmed it fails on the old order.

## Review findings

- **Diff read first** (`ticket(implement): database-close-awaits-quereus-before-storage-shutdown`), then the fix ticket's requirements. Both close methods match the required order; the second `disposeAll()` and the membership-view invalidation stay after every await.
- **Quereus close semantics checked** (`../quereus/packages/quereus/src/core/database.ts`, `closeAfterRunningWork` / `tearDown`): close aborts running work, waits on the execution mutex, disconnects connections, then `schemaManager.clearAll()` — which only clears maps and calls no vtab `destroy`, so closing Quereus while the collection factory is still live cannot drop or delete storage. Optimystic's `CollectionFactory.dispose()` doc says to call it after `db.close()`, which is now the order.
- **Concurrent second close — fixed a doc inaccuracy.** The `StrandDatabase.close()` comment (and the handoff) said the strand shutdown "is latched"; it is not — only the storage-cache release inside it is. Both `shutdownStrand()` calls run, as they did before this change. Verified each release it makes is idempotent (`CollectionFactory.dispose()` documents "safe to call more than once"; the offline controller's `dispose()` is documented idempotent; `txnBridge.dispose()` twice was already the pre-change behaviour). Reworded the comment to "safe to run twice (each release it makes is idempotent, and the storage-cache release is latched)". Rebuilt `@serfab/cadre-core` so its `dist` stays fresh for the stale-build guard.
- **Deferred sApp schema apply settles `failed` when the close catches it mid-apply** — verified in `app-schema.ts`: the `Database is closed` error is not a deferral, `retryableRefusalOf` returns `undefined` without touching the closed database, so the outcome is `failed` and the log line is the only effect (the report is released before close). An apply still waiting in `nextChance` when close runs settles `cancelled` once `shutdownStrand` aborts `released`, or `failed` if it wakes in between; both unheard. The comment in `compose-strand.ts` is accurate.
- **Durability reports raised inside the committing statement** — spot-checked `txn-bridge.ts` (`reportCommitDurability` called synchronously at end of commit). The implementer's `NOTE:` on `StrandDatabase.close()` records it with its trip condition; no deadlock today because no layer awaits listeners. Agreed.
- **Background control work during the close window** (handoff question on a `closing` flag): `reapRevokedRows` and other guarded background callers see `initialized`/`db` still set and now fail each statement with `Database is closed`, logged and continued. That window existed before (both fields stayed set across the factory-shutdown await, statements failed against the stopped node instead). Declined adding a flag: no new failure class, only a different error text in an existing log path.
- **Error handling:** a rejected `db.close()` is logged with the file's `log` and teardown continues, as the fix ticket required. No exceptions eaten silently.
- **Callers:** `CadreNode` stop (`cadre-node.ts` ~5993) stops the control node after `controlDatabase.close()`; `StrandInstanceManager` (`releaseRuntime`, `discardDatabaseAttempt`, `buildStrandRuntime`) stops the strand node after `close()`. All benefit from the new wait; none runs inside a statement.
- **Tests:** the new spec is the bug's reproduction at the lowest layer and spies only on the Quereus `Database` and the test's own libp2p node — kept. No strand spec added: it would need new libp2p scaffolding to assert only that Quereus closed, and the two methods changed identically. No tests cut.
- **Docs:** read `docs/strands.md` close/hibernation passages and `docs/architecture.md`; none describes the close order, so nothing is out of date.
- **Source hygiene:** comments state reasons and constraints, not narration. No size concern (changes are local to two methods).
- **Validation:** `yarn lint` exit 0; `yarn workspace @serfab/cadre-core test` — 197 files, 2621 passed, 1 skipped (pre-existing); new spec passes on its own. The implementer ran the six restart integration scenarios; not re-run here since this pass changed only a comment.
