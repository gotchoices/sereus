# Complete: provider-started node accepts the provider's seed (real `cadre-cli`)

## What landed

`packages/integration-tests/src/scenarios/provider-seed-accepted.integration.ts` starts real
`@serfab/cadre-cli` child processes from the provider's own `buildNodeEnv()` output (via
`ProviderProcessOrchestrator`) and drives them through the real `ContainerService`. No stubs. It is
the first test that observes what a node *does* with a provider-delivered seed rather than what the
provider *sends* — `container-seed-endpoint.test.ts` stubs `fetch`, so a drift in the
provider→node environment contract used to pass every existing test while every customer's first
seed was silently refused.

Five ordered steps, each proven green in this review pass:

1. owner authority node up with a dialable identity
2. provider provisions node A pinned to the owner; the record reaches `running` through the
   service's own enrollment loop
3. **node A accepts the owner-signed seed** — the assertion the suite exists for
4. node B pinned to a stranger refuses the same seed (400, trust gate), and a wrong bearer on B's
   endpoint gets 401 instead (delivery gate) — the two gates fail independently
5. node A restarted from its volume with **no** pin still accepts a second seed, proving the first
   accepted seed anchored the owner key durably

Also in the implement pass: the seed mint and delivery were folded into one retried helper
(`deliverSeed`) that attaches the last mint error, the last delivery result and the child's
`node.log` on timeout, and step 4 gained an explicit guard on step 3's minted seed so a step-3
failure can no longer present as a step-4 defect.

### A second, previously-unattributed failure fingerprint — filed

The incoming ticket said "a red with any other fingerprint is a real finding". One appeared. In the
run where steps 1/2/3/5 all passed, **step 4 failed because node B — the third real child in the
party — died inside control-schema DDL**:

```
Module 'optimystic' create failed for table 'Revocation': Failed to initialize Optimystic table:
Self-coordination blocked: grace-period-not-elapsed. No coordinator available for key.
```

That is the same message and throw site as the existing
`fix/1-bug-rejoining-node-cannot-self-coordinate-after-reconnect`, but on a node that has **never
been on the network** and that never finishes starting — where that ticket's original arm is about a
node rejoining after a disconnect and failing a query. Same code site, so it was appended to that
ticket as a second arm rather than filed fresh, with the log, the frequency (1 of 3 runs), and one
new observation: the control-write retry classifier
(`packages/cadre-core/src/control-write-retry.ts`) does not treat `Self-coordination blocked: …` as
transient, so this DDL is never re-presented — and unlike a commit-phase failure, it is a proven
non-commit, so whether it *should* be retried is a real question for that ticket rather than
something to leave to omission. `tickets/.pre-existing-known.md` gained a matching entry so a future
red on this scenario is checked against both fingerprints.

The other red is `fix/0-bug-control-collection-header-absent-at-committed-revision`, exactly as the
incoming ticket described; that ticket was updated with the review pass's numbers, not re-filed.

### Tripwires parked (not tickets)

- **Port bands are claimed by convention, not allocated.** The four child-process scenarios
  hard-code disjoint health/metrics port ranges because `HostProcessOrchestrator` cannot use port 0.
  Disjoint today. Recorded as a `NOTE:` in
  `packages/integration-tests/src/harness/port-allocator.ts` — which already owns the
  ports-across-parallel-workers concern — listing every claimed band and the condition (a new
  child-process scenario, or two overlapping ranges in one worker window) that would make an
  allocated table worth building.
- **Step 5 hand-patches a production record shape.** The same-volume restart goes through the
  orchestrator directly, because `ContainerService.createContainer` can only mint fresh `ctr_` ids,
  so the test patches the store record's endpoints/token/status itself. It is silent if that shape
  changes — a new field is simply not patched and the step reads as a seed-path failure. Recorded as
  a `NOTE:` at the site, pointing at the restart-in-place service method that would replace it.
- The implement pass's own tripwire — `ContainerService.waitForEnrollment` stranding a record on
  `enrolling` after a timeout — was reviewed and kept as a `NOTE:` at its site. It is genuinely
  conditional: `applySeed` accepts `enrolling`, so a merely-slow node still works today.

### Filed as new work

- `backlog/debt-docker-entrypoint-untested` — nothing runs `packages/cadre-cli/docker/entrypoint.sh`
  (190 lines, and what actually starts every hosted node). `ProviderProcessOrchestrator`
  *reimplements* it so scenarios can skip Docker, so this suite proves the environment contract
  against the copy rather than the original, and the two can drift silently in either direction. The
  ticket lays out three closure shapes without picking one, cheapest first. This was the incoming
  ticket's own flagged gap; it is a real coverage hole, not a conditional one, so it is a ticket
  rather than a tripwire.

### Checked and deliberately left alone

- **The retried `addDrone` is safe to retry.** `deliverSeed` re-mints on every poll iteration, which
  looked like it could hammer the owner's control DB into the very unique-index insert failure the
  scenario reds on. It cannot: `authorizePeer` → `insertCadrePeerRow` →
  `ControlDatabase.insertCadrePeer` performs an existence check and no-ops when the row is already
  seated, so iterations after the first re-encode a seed and write nothing.
- **`applySeed` never throws** (it catches and returns `{ success: false, error }`), so the poll's
  `result` is always populated when the mint succeeded — the diagnostic message cannot silently lose
  a delivery-side exception.
- **Step 4's refusal-reason regex** `/(neither|not).*(anchored|pinned)/i` matches the real policy
  message (`Signer key is neither an anchored nor a pinned owner (pinned-key trust policy)`) and is
  loose enough to survive rewording.
- **The dropped no-pin-refuses variant.** The incoming ticket invited disagreement. Step 4's
  stranger-pin already proves the trust gate discriminates, and a third child process costs real
  wall-clock on a suite that is already the slowest in the package. Agreed with the implementer; not
  filed.
- **Two consecutive green runs still not achieved** — the incoming ticket's own bar. 1 green of 3
  this pass, 1 of 4 in the implement pass. It stays unmeetable until the two tracked database
  defects land, and it is not worth holding this ticket open for.
