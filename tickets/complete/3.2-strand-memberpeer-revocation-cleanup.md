# Complete: `Strand.MemberPeer` cleanup after a member is removed

## What shipped

`Strand.MemberPeer` binds a member's devices (libp2p peer ids) to that member. Removing a
member did not remove those bindings — nothing cascades — and only the member itself could
sign a delete, so a manager had no way to clear a departed member's device records.

**Schema** (`schemas/strand.qsql` + the mirrored `STRAND_SCHEMA`, character-identical — the
drift guard compares verbatim):

- `Authorized` gained a manager branch: a `committed.Manager` row matching
  `context.ManagerKey` may delete ANY member's binding, verifying
  `digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId)` against
  `context.ManagerSignature`. Gated to DELETE via `new.MemberKey is null`.
- Context tuple widened from `(Signature)` to `(Signature, ManagerKey, ManagerSignature)`.
- `NoUpdate check on update (false)` added **in review** — see findings below.
- Masks stated explicitly: `MemberExists check on insert`, `Authorized check on insert, delete`.
- Table-level `NOTE` that a `MemberPeer` row can outlive its `Member` row.

**Writer** (`packages/cadre-core/src/strand-membership-writer.ts`):

- `signStrandMemberPeerRemoval(memberKey, peerId, privateKeyB64)` — the manager's
  remove-tagged signature.
- `removeMemberPeer(db, params)` — discriminated union: `{ memberKeyPair, peerId }` (self) or
  `{ managerKeyPair, memberKey, peerId }` (manager); delete-if-present plus post-delete
  re-verify.
- `listMemberPeers(db, memberKey)` — added **in review**; enumerates a member's peer ids.
- `scanMemberPeerIds` — added **in review**; the shared leading-key scan both readers consume.
- All exports plus the param types added to `packages/cadre-core/src/index.ts`.

**Design choices, all deliberate and pinned by tests:** the manager branch is not gated on
the member already being gone; the authorizer is read from `committed.Manager` (pre-transaction
snapshot); peer cleanup is an explicit follow-up call, not a cascade inside `revokeMember`.

## Review findings

### Major — fixed in this pass

- **Any member could clear another member's device binding via UPDATE.** `MemberPeer` had no
  `NoUpdate` constraint, unlike its siblings `Member` and `Manager`, and `Authorized`'s mask
  included `update`. `Authorized` reads the NEW row image (`coalesce(new.X, old.X)` picks
  `new` on an update), so an attacker could run
  `update Strand.MemberPeer set MemberKey = <attacker> where MemberKey = <victim> and PeerId = <victim's>`,
  signing only over its own new values — hijacking, and thereby clearing, a binding it held
  no signature to delete. The victim never consented. `MemberExists` did not help: the
  attacker is itself a member.

  **Proved before fixing** — a probe test ran against a real closed strand and the UPDATE
  succeeded, leaving the row owned by the attacker's key. Fixed by adding
  `constraint NoUpdate check on update (false)` (mirroring `Member` / `Manager`, which carry
  it for the same reason) and narrowing `Authorized` to `on insert, delete` and `MemberExists`
  to `on insert`. The probe is now a regression test asserting the update is rejected and the
  row still belongs to the victim.

  Fixed inline rather than filed: the hole was proven reachable, and the fix is one constraint
  matching a pattern already used twice in the same schema.

- **The feature was not drivable — no way to discover which device records to clear.**
  `removeMemberPeer` takes a single `peerId`, and nothing exported could enumerate a member's
  bindings (`memberPeerExists` was module-private). A manager cleaning up after a revocation
  knows only the departed key. Added `listMemberPeers`, factored over a new shared
  `scanMemberPeerIds` generator that `memberPeerExists` now also consumes — removing the
  duplicated scan-and-recompare that a second reader would otherwise have introduced. Tested,
  including the enumerate-then-clear loop the feature exists to support.

### Major — filed as a ticket

- **No real-network coverage of removal.** All new coverage is single-process. The
  post-delete re-verify guards a storage-layer lookup miss that only occurs across the
  network, so its error path has never executed; and the happy path has never run on two
  nodes. Filed as `backlog/debt-strand-memberpeer-networked-removal-coverage`. Not fixed
  here: nothing reads `MemberPeer` rows yet, so the exposure is a removal that silently
  does nothing — availability, never permissions.

### Corrected — a claim in the implement handoff that was wrong

- **The self branch's shared insert/delete payload is not "harmless".** The handoff argued a
  member replaying its own registration signature to delete its own binding is "the same
  principal, own row, harmless". But constraint context travels with the write out to the
  strand's peers (as `bug-strand-approval-domain-separation` and
  `bug-strand-manager-authority-antireplay` both state), so **anyone who observed the
  registration** holds a valid delete approval for that binding. The exposure is real but
  bounded: availability only — the binding is re-registerable, and no other member's row is
  reachable through this branch. No new ticket, because
  `backlog/bug-strand-approval-domain-separation` already names this exact case ("An approval
  minted for a `MemberPeer` insert is refused for its delete"). The misleading comments in
  the schema, the writer doc, and the test were rewritten to state the real exposure and
  cross-reference that ticket.

### Gaps from the handoff — closed in this pass

- **"No test asserts a same-transaction manager cannot authorize its own cleanup."** Now
  tested: seating a manager and spending its authority in one transaction is rejected at
  commit, and a positive control (same seat, same removal signature, seat committed first)
  succeeds — so the rejection is provably the ordering, not a malformed seat.
- **"Nothing verifies the manager branch cannot delete via UPDATE."** Now tested; `NoUpdate`
  makes it unreachable rather than merely unsatisfied.
- **"The stale-comment claim was not re-measured."** Confirmed against
  `../quereus/docs/sql-ddl.md:303`: "`check (expr)` is enforced on INSERT and UPDATE by
  default". The mask change is consistent with it and all tests pass.

### Checked, nothing found

- **Documentation.** Read every file the change touches and the ones it should have.
  `docs/strands.md` "Removing Members" updated for the enumerate-then-clear flow and for the
  new no-edit rule. `docs/architecture.md` and `docs/reference-app-rn.md` only name
  `MemberPeer` in table lists — accurate as-is.
- **Consumers of `MemberPeer`.** Swept every SQL reference in the repo. Nothing in the
  runtime reads the table: `StrandMemberRegistry.isMember` resolves against `Strand.Member`,
  and `strand-addr-protocol.ts:26` explicitly excludes peer-record resolution. So orphan
  rows are inert today.
- **Resource cleanup / error handling.** The transaction in the new same-transaction test
  rolls back in a `finally`. `removeMemberPeer` throws rather than eating a failed delete.
  No swallowed exceptions in the diff.
- **Type safety.** No `any`. The discriminated union narrows on `'memberKeyPair' in params`;
  `scanMemberPeerIds` is typed `AsyncGenerator<string>`.
- **Source hygiene.** `strand-membership-writer.ts` is 1038 lines — large but cohesive, one
  writer per membership operation. The wall of scan-shape commentary formerly on
  `memberPeerExists` moved to `scanMemberPeerIds` where it belongs, leaving each caller a
  short purposeful doc.

### Tripwires (recorded, not filed as tickets)

- **A `MemberPeer` row can outlive its `Member` row.** Parked as the table-level `NOTE` on
  `MemberPeer` in both schema copies, where a future reader who starts trusting a peer row as
  proof of membership will meet it.
- **The exact-key lookup hazard on the delete path.** Parked as a `NOTE` at the re-verify
  guard in `removeMemberPeer`, citing `debt-composite-pk-point-lookup-unreliable-untracked`.
- **`listMemberPeers` / `memberPeerExists` walk the whole table.** The predicate is not pushed
  down. Parked as a `NOTE` on `scanMemberPeerIds`; fine at strand scale, and the fix if
  `MemberPeer` ever grows is a reliable composite-key seek, not a bigger scan.
