# Join backfill pushes once per peer, and the joiner waits for it

## What landed

Implemented in `ticket(implement): join-backfill-pushes-once-and-is-waited-for`.

- **`PeerJoinBackfill` remembers, per peer and per block, the revision the peer accepted and the revision it refused** (`PeerMemo`, filled from each push reply). A run skips a block (counted in the new `PeerJoinBackfillResult.alreadyHeld`) when the peer accepted or refused that revision, or when the retained commit proof for that revision carries the peer's own approval. The proof rule stands in for "don't push a block back to the peer it came from", which Optimystic does not expose to embedders; it is recorded as an accepted-tradeoff `NOTE:` with a revisit condition.
- **A peer counts as caught up once a run has no failed push.** Refusals no longer keep it un-memoized, since they are remembered per block. A backoff retry resends only the blocks not yet accepted.
- **First contact runs at once** (zero-delay timer); later schedules use the debounce.
- **The control gate reads the in-memory authorized-member snapshot** (`authorizedControlPeers`), not a control-database query, and not `isControlNetworkMember` (which admits everyone while the snapshot is empty).
- **A joining machine waits for the push on a first join.** "First join" is judged before `initialize()`, since `initialize()` itself fetches the schema catalog. On a first join the gate listens to the storage change feed from before `initialize()` (`StrandFirstSyncGate.listen()`), and the manager skips its own first probe only when nothing has landed yet. Restart, hibernation-wake and founder launches are unchanged.

Measured (message-cost-accounting, recorded in the scenario's doc comment): on the strand case, B→A block-transfer went 2 → 0 (`alreadyHeld=42`), and B→A sync inside `addStrand` went 13 → 2. On the invite case, settle + idle A→B block-transfer went 92 → 182. That is an interim regression: the owner's Optimystic rebalance growth arm stopped learning the joiner holds the blocks once the joiner stopped pushing them back. `cohort-join-catch-up-runs-once-per-node` (implement, prereq on this ticket) turns that arm off where the backfill runs. The Optimystic under-replication drain re-sending blocks the backfill already delivered is filed as `blocked/optimystic-embedder-cannot-report-block-holders`.

## Review findings

Read the implement diff first, then the plan (`ticket(plan): join-backfill-pushes-once-and-is-waited-for`), then the handoff. **Checked**
- Memo branching (`memoSettled`, `recordReply`, `readOffer`): revision comparisons, a thrown chunk records nothing, skipped blocks don't count toward `maxBlocks`, the proof is read for exactly the pushed revision. Correct.
- Scheduling: a same-turn identify burst collapses on the zero-delay timer; `contacted` is set in `trackRun`, so a denied first run moves the peer to the debounce for its membership re-drive (as the plan intended); `rearmAfterFlight` replay still works. Correct.
- Control gate: the snapshot is set before `scheduleConnectedPeers()` in `refreshAuthorizedControlPeers`; a failed refresh keeps the previous snapshot; revocation lag is bounded by the next refresh, which also hangs up revoked peers. An unauthorized receiver drops the stream without replying, so the sender sees a thrown push (retry), never a refusal that would be memoized. Acceptable.
- First-join path: `strandStorages` is populated before `buildStrandDatabase`; a release during the emptiness check makes `listen()` a no-op on the stopped gate; the `awaiting-seed` retry re-judges emptiness on its next build; `gate.stop()` unsubscribes a listen-only gate. `probeOnce()` clearing the flag is right for both the manager's probe and the scheduled one. Correct.
- Docs: architecture.md (new "What the catch-up pushes, and when" paragraph), strands.md ("How a gated launch probes", "Writable does not mean connected"), cadre-consistency.md and the `types.ts` config docs all reflect the new behaviour.
- Tests: the rewritten and added specs each pin real branching (memo per revision, signer skip, resume after a failed chunk, first contact without debounce, empty snapshot admits no one, listen-before-start). Nothing to cut. The two deleted specs had contracts this ticket changed on purpose.

**Fixed in this pass (minor)**
- `strand-instance-manager.ts`: a first join now also requires the node to have a storage change feed (`storageRepo`). Without one the gate cannot hear the push, so skipping the first probe would only add a 2 s backstop wait. Such a node now probes at once, as before.
- `peer-join-backfill.ts`: the `rearmAfterFlight` doc still said the gate is "a control-database read". Reworded to say why the replay is still needed: the gate is judged once, at the start of a run.
- `peer-join-backfill.ts`: the "What is pushed" comment left out that a receiver's persist failure also lands in `missing`. Added it.

**Tripwires recorded**
- A receiver's transient persist failure is now remembered as a refusal and not retried this runtime, because the reply gives no per-block reason. Parked as a `NOTE:` in the module comment of `peer-join-backfill.ts` (revisit if receivers log `persist:fail` in practice).

**Noticed, not acted on**
- Optimystic's `handleRequest` answers `{ blocks: {}, missing: [] }` when `handlePush` throws, so any sender (this one, and Optimystic's own) reads every block as accepted. This predates the ticket: the old code also counted them accepted and marked the peer done. It is upstream and only reachable on a non-persist throw inside `handlePush`, so no ticket was filed.
- Interim invite/cadre regression (92 → 182 settle + idle pushes) until `cohort-join-catch-up-runs-once-per-node` lands. That ticket is already in `implement/`, next in sequence, with this ticket as its prereq, so the runner picks it up next. No reordering needed.
- On a first join whose members all run with the backfill disabled, the joiner's first probe waits one backstop (2 s). Covered by the manager comment ("or at its backstop"). No change.

**Empty categories**
- Major findings: none. Each concern was either fixed inline or is conditional.
- Security: none. The control gate is stricter than the stream gate (an empty snapshot admits no one), and the spec pins that.
- Resource cleanup: the memo and `contacted` live until `stop()`, which ends the instance. The size bound is in the `PeerMemo` `NOTE:`.
