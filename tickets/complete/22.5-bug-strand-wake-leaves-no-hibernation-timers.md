# After a wake settles, the strand's timer cycle matches its resulting state

## What changed

`HibernationManager` (`packages/cadre-core/src/hibernation-manager.ts`) keeps an idle countdown (active → idle → hibernating) for live strands and a check-in chain for hibernating ones. Every wake clears both; before this change only the activity-driven wake put the idle countdown back, and only a failed wake put the chain back.

- **One settle path.** `beginWake` takes the `StrandInstance` and, in its `finally` (`settleWake`), calls `rearmAfterWake(instance, hadCheckInChain)`: a `'hibernating'` strand has any idle countdown cleared and gets back the check-in chain the wake cancelled (base delay), if it had one; a live (`'active'` / `'syncing'`) strand gets the idle countdown (`rearmIdleIfLive`, shared with `runCheckIn`); nothing when hibernation is disabled or the manager is stopped. Replaces `restoreCheckInChain` and the `.then` re-arm in `recordActivity`.
- **`wakeStrand(instance)`** takes the instance; `CadreNode.wakeStrand` logs and returns for an unknown strand.
- **Probe entry points for `serviceWake`.** `probeWake(instance)` records whether a check-in chain was armed (or already cancelled by a wake it joins) in a `probes` map, then wakes; while a probe holds the strand, the wake's settle arms nothing. `endProbe(instance)`, called from `runServiceWake`'s `finally`, runs `rearmAfterWake` from the window's outcome. A force-hibernate or untrack mid-probe drops the record ("keep it down").
- `docs/architecture.md` Strand Hibernation items 1 and 4 describe the rule; a merge note in `tickets/fix/22.6-bug-strand-probe-failure-quiesces-a-runtime-it-does-not-own.md` keeps `endProbe` last on every exit of `runServiceWake`.

Tests (`test/hibernation-manager.spec.ts`, "check-in backoff"): `an explicit wake leaves the idle countdown running, for a hibernating strand and an already-live one` (the ticket's two reproductions) and `a probe that ends hibernating restores the check-in chain it interrupted, and arms nothing else`.

## Review findings

Read the `ticket(implement): bug-strand-wake-leaves-no-hibernation-timers` diff first, then `CadreNode`'s wake (`handleStrandWake`), check-in (`handleStrandCheckIn`), window (`runWakeWindow`), `serviceWake` and formation-wake paths it interacts with.

- **Correctness — settle paths walked, no defect found.** Checked: activity/explicit wakes that join a probe's wake (settle skipped, `endProbe` decides); a probe joining an explicit wake (records the already-cancelled chain via `checkInsCancelledByWake`); a wake joining a check-in's rebuild (settle arms idle; the check-in's window sees the wake's activity stamp and keeps the strand up, and `runCheckIn` re-arms idle again); an idle-strand wake (`handleStrandWake` flips it live, so the idle countdown is armed); a pre-rebuild failure (status stays `'hibernating'`, chain restored as before); a failure while a check-in holds the runtime (`'starting'`/live, so no chain is restored and the check-in reschedules itself); force-hibernate mid-wake and mid-probe; hibernation disabled or manager stopped (early return; `probes` cleaned by `endProbe`/`stop`); realtime strands (`idleTimeout: Infinity`, nothing armed).
- **Test gap closed (minor, fixed).** The implementer flagged that the "settle arms nothing while a probe holds the strand" branch was unpinned. Without it, a hint whose idle timeout is shorter than the window (archive: 10 s vs the 15 s default) flips the probed strand to `'idle'` and emits `strand:idle` mid-window. Extended the existing probe test (no new test): both probes now run concurrently and time advances past the idle timeout before the mid-probe activity. Verified it fails with the `probes.has` guard removed (temporary edit, reverted) and passes with it.
- **Tripwire — explicit wake racing a probe (pre-existing).** A `wakeStrand` already resuming when `serviceWake` starts stamps its activity before the probe's `activityMark`, so the probe joins it without counting it and can re-hibernate a strand the waker asked to keep up. Needs a foreground wake and a background push-driven `serviceWake` to overlap; not caused by this change. Parked as a `NOTE:` at `runServiceWake`'s `activityMark` in `cadre-node.ts`.
- **Tripwire — window longer than idle + hibernate (pre-existing, from the handoff).** Moved from ticket prose to a `NOTE:` at `runWakeWindow` in `cadre-node.ts`: only reachable with a custom `windowMs`.
- **Behaviour widening accepted.** Activity-driven wakes now also re-arm idle for `'syncing'` (joiner behind its first-sync gate), matching the check-in path; correct, since a syncing strand is live and was previously left without a countdown.
- **No `CadreNode`-level test for `runServiceWake` (declined).** The change there is two calls into the manager, whose behaviour the manager spec pins; the existing `serviceWake` tests in `test/cadre-node.spec.ts` run with the manager stopped and still pass. A `CadreNode`-level timer test would mostly re-verify wiring.
- **Tests kept as written.** Both new tests reproduce the ticket's defects and fail with the re-arm calls removed; neither restates the implementation or verifies a mock.
- **Pre-existing, not touched:** `settleWake` deletes `wakePromises[strandId]` unconditionally, so a wake left in flight across `stop()` + `start()` could drop a newer wake's coalescing entry (the old `finally` did the same). It needs a manager restart during a live wake; not filed.
- **Docs.** `docs/architecture.md` items 1 and 4 match the code; `docs/strands.md` and `docs/cadre-host.md` do not describe these timers. No stale references to `restoreCheckInChain` / `rearmIdleAfterCheckIn` remain.
- **Hygiene.** `hibernation-manager.ts` is 543 lines (`wc -l`), with small single-purpose methods; comments explain the reasons rather than narrating the statements. No type-safety regressions (`Map<string, StrandInstance>` became `Set<string>` because the instance now arrives with the wake).
