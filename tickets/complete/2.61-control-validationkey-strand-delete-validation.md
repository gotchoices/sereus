# Complete: `ValidationKey` / `Strand` delete authorization

Delete + update authorization for `CadreControl.ValidationKey` and `CadreControl.Strand`,
implemented across `78242ce` / `3dd8052` / `7732b1d`, reviewed here.

## What shipped

Both tables previously had a single bare `constraint Authorized check (...)`. In Quereus a bare
`check` covers insert and update, never delete — so both tables accepted an unauthenticated
delete from anyone, and (for `Strand`) an unauthenticated rewrite. Each is now five named
constraints:

| constraint | fires on | rule |
| --- | --- | --- |
| `NotRevoked` | insert | the row's one-off nonce (`StampId`) must not already be retired in `Revocation` |
| `RevocationRecorded` | delete | the delete must file the matching `Revocation` row in the same transaction |
| `NoUpdate` | update | `false` — these rows are insert + delete only |
| `AuthorizedInsert` | insert | an owner signs an `'add'`-tagged digest over the new row |
| `AuthorizedDelete` | delete | an owner signs a distinct `'remove'`-tagged digest over the stored row |

`Strand.AuthorizedInsert` keeps its signature-free consent branch (a `FormationUsage` row for
the strand id *is* the authorization); `AuthorizedDelete` deliberately does not mirror it.
`Revocation.RowIsGone` gained `'ValidationKey'` and `'Strand'` branches.

### Major — filed as tickets

- **`fix/bug-strand-consent-resurrects-removed-strand`.** After a fully legitimate
  owner-signed, tombstoned removal of a strand that was seated *by invitation*, anyone can
  re-insert that strand id with no owner key, no signature, a fresh `StampId`, and an
  attacker-chosen `MemberPrivateKey`. The consent branch authorizes on the existence of a
  `FormationUsage` row, and `FormationUsage` is append-only, so that authorization outlives the
  removal. **Confirmed empirically** with a scratch test on this harness (the re-insert was
  accepted); the scratch test was removed rather than committed, since a test asserting the
  hole would go red on the fix. This does not undo the shipped work — the delete rule is
  correct — but it means removal is not durable for consent-formed strands.
- **`fix/bug-formation-validation-key-never-checked`.** `FormationUsage.Authorized` verifies
  the formation-validation signature against `context.ValidationKey`, a value the redeemer
  supplies, and never joins it to the `CadreControl.ValidationKey` table. A redeemer signs its
  own disclosure with a throwaway key and the `ValidationUrl` gate passes. **Confirmed
  empirically** the same way. Directly relevant here: this ticket hardened enrollment and
  removal for a table that no rule in the schema currently consults.

### Minor — fixed in this pass

- The renamed constraints left ~13 stale references to `Strand.Authorized` /
  `ValidationKey.Authorized` in comments and doc-comments across `control-database.ts`,
  `cadre-node.ts`, `strand-solicitation.ts`, four cadre-core specs, `reference-app-web`, and
  three files in `integration-tests`. All repointed to `AuthorizedInsert` (or, where the text
  was generic across tables, reworded). References describing the *pre-fix* state — e.g. the
  file header in `control-revocation-replay.spec.ts` — were left as written.
- The gap the implementer flagged (no test for an owner-signed delete of a *consent-formed*
  strand) is closed: the existing consent test in `control-revocation-replay.spec.ts` now also
  removes the row the legitimate way and asserts it is gone.
- `control-constraint-helpers.ts` claimed two consumers; it has four. Corrected, and the
  single-rejector convention is now stated where callers will read it.

### Tripwires — recorded, not ticketed

- The constraint-name assertions depend on Quereus reporting one violated deferred constraint
  per commit. Parked as a `NOTE:` in `packages/cadre-core/test/control-constraint-helpers.ts`,
  next to the instruction not to widen the accepted-name list if it ever goes flaky.
- Per-node convergence on `NotRevoked` (a node that has not seen the `Revocation` row can still
  accept a replayed add) was already parked by the implementer as a `NOTE:` on
  `Strand.NotRevoked` in `schemas/control.qsql`. Left as is — still conditional.

### Considered, no action

- `Strand.MemberKeyClosedOnly` is still a bare `check` (insert + update). Not a hole: `NoUpdate`
  rejects every update anyway, and a bare check is the stricter of the two forms here.
- `Revocation` remains writable by anyone. Already tracked as
  `fix/bug-control-revocation-unauthenticated-writes`; not re-filed.

## Standing gap

Neither table has a shipped writer that signs the `'remove'` digest and files the tombstone, so
these delete rules have no production exercise yet — only raw-SQL tests delete these rows. That
writer is `implement/control-signed-strand-validationkey-deleters`. Read it together with
`fix/bug-strand-consent-resurrects-removed-strand`: for consent-formed strands, the removal that
writer performs is currently reversible by anyone.
