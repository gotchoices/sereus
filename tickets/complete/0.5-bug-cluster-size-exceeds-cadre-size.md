# Complete: one party-wide replication cluster size, defaulting to 2

## What shipped

Optimystic replicates each block to a group of nodes it calls a **cluster**. The size a node
declares is an admission gate: a member refuses to vote on a write when the coordinator's
declared peer set is smaller than the member's own configured size and the member has no
confident network-size estimate. A commit needs a super-majority (unanimity at two nodes), so
one refusal fails every write. Cadre hardcoded `3` while real parties run one or two nodes.

**Implement stage** made it one optional config value, `CadreNodeConfig.clusterSize`, defaulting
to a `DEFAULT_CLUSTER_SIZE = 2` constant, used by the control network, every strand network, and
the integration-test harness.

**Review stage** found the fix was incomplete and finished it: the number is now resolved through
a single shared function, `resolveClusterSize`, that every node-creating path calls.

| File | Change (review stage) |
| --- | --- |
| `packages/quereus-plugin-sereus/src/cluster-size.ts` | new — canonical `DEFAULT_CLUSTER_SIZE` + `resolveClusterSize(configured?)`, which applies the default and rejects non-integers and values below 2 |
| `packages/quereus-plugin-sereus/src/types.ts` | new `StrandConnectionOptions.clusterSize` |
| `packages/quereus-plugin-sereus/src/compose-strand.ts` | resolves the value once, up front, and puts it on `CreateNodeContext` (now required, so a future platform adapter cannot forget it) |
| `packages/quereus-plugin-sereus/src/connect.ts`, `connect-browser.ts` | both now pass `clusterSize` to `createLibp2pNode` — **this was the bug**, see below |

| `docs/architecture.md`, `packages/quereus-plugin-sereus/README.md` | document the plugin option, the shared resolver, and that an unset value is *not* neutral |

`@serfab/cadre-core`'s public surface is unchanged — `DEFAULT_CLUSTER_SIZE` still imports from
there (the integration-test harness does), now via re-export. The plugin package is the canonical
home because it also creates libp2p nodes and cannot depend on `cadre-core`.

## Review findings

### Major — found and fixed in this pass

- **The SQL access library still declared a ten-node cluster.**
  `connectToStrand` / `connectToStrandBrowser` create a libp2p node when the caller does not
  inject one, and neither passed `clusterSize`. Optimystic's own fallback is **10**
  (`libp2p-node-base.ts:566,666,917` — `options.clusterSize ?? 10`), so any peer joining a strand
  through the plugin's public API gated every write on a ten-node cohort: exactly the shipped bug,
  on the package whose entire purpose is SQL access to a strand. The implement stage patched that
  package's *e2e test* to 2 but not its `src/`. Fixed by threading the option through
  `composeStrand` to both platform adapters.
  Not reached by `cadre-core`'s `StrandDatabase`, which injects an already-built node — so this
  affected direct plugin embedders, not the cadre runtime.
- **No validation of nonsense values.** The implement handoff asked whether `start()` should
  reject a value below 2. It should — 0 and 1 are below Optimystic's `minAbsoluteClusterSize` and
  would silently mis-gate. `resolveClusterSize` now throws on non-integers and anything below 2,
  before any node is created.

### Minor — fixed in this pass

- **Duplicate literal** (flagged in the handoff): the plugin's e2e spec hardcoded `2` with a
  comment saying it mirrors cadre-core. It now imports `DEFAULT_CLUSTER_SIZE` from its own
  package, and cadre-core re-exports that same constant — one definition, no drift.
- **Three `?? DEFAULT_CLUSTER_SIZE` sites** collapsed into one resolver call each.
- **Docs were out of date the moment the plugin gained the option** — `docs/architecture.md` and
  the plugin README both updated. Every file the change touches was read; no other doc describes
  cluster sizing (`docs/STATUS.md:597` mentions `min(2, clusterSize)` in an optimystic-upstream
  context and is still accurate).
