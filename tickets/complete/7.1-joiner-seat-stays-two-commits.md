# The joiner's seat stays two commits

Comment and doc text only; no behaviour change. This replaces the first two design items of `plan/joiner-membership-in-one-commit`, which found that merging the joiner's two commits (`Member` + `ConsumedInvite`, then `MemberPeer`) into one transaction is not worth doing. That plan's third item is `fix/joiner-redemption-reads-in-the-settle-window`.

## What changed

- **`StrandMembershipReconciler.attempt`** (`strand-membership-reconciler.ts`): the old NOTE ("saving unmeasured; try one transaction and measure against 27 + 18") is now an accepted-tradeoff `NOTE:`. It says the two commits stay separate on purpose: one transaction saves no `/cluster` requests while Optimystic costs about 4 per collection (`blocked/optimystic-multi-collection-commit-costs-four-requests-per-collection`), only one commit's latency; a torn commit or out-of-order collection arrival could show a `MemberPeer` without its `Member`, which the revocation enforcer reads as a removed member (fail closed); and it would add a half-committed shape that `reportHalfCommittedJoin`'s dropping of the invitation gets wrong. Revisit condition: Optimystic offers an all-or-nothing multi-collection commit, or its per-coordinator batching lands and the enforcer can tell a not-yet-seated binding from a removed member's.
  - **The 27 + 18 figure was dropped.** It was measured on 2026-09-17, before upstream cut a commit from 9 to 4 `/cluster` streams per collection (`complete/relay-round-trips-remeasure-optimystic-cadcb919`), so it is no longer the latest measurement of these commits. No newer measurement of both commits exists; the 2026-10-19 `message-cost-accounting` baseline covers only the redemption, and whether that is one call is still open in the fix ticket.
- **`strand-revocation-enforcer.ts` module doc:** after "an orphaned binding can only mean this member existed and was removed", it now says this holds on the network only because every writer commits `Member` before `MemberPeer` as separate commits, and names the founder's bootstrap batch as the one exception (acceptable because it commits before any other party has joined). The "Everything NOT in the set is admitted" sentence moved after the new text so "That holds" refers to the orphaned-binding claim.
- **`readStrandRevocationRows` doc:** the "Member row then MemberPeer row" remark points at the module doc instead of repeating it.
- **`bootstrapFounderMembership` torn-founding NOTE** (`strand-membership-writer.ts`): one added sentence. A torn founding that saves this machine's `MemberPeer` without its `Member` leaves an orphaned binding, which every machine's revocation enforcer (this one's and any joiner's) reads as a removed founder until a later run of the bootstrap seats the `Member`.

## Accuracy check of the enforcer doc

`memberPeerInsertStatement` has two callers: `founderBindingIfAbsent` (the founder's batch, the named exception; it only joins a run that also seats the founding `Member`) and `registerMemberPeer` (its own transaction; `MemberExists` requires an existing member). Outside tests, `registerMemberPeer` is called only by the reconciler's `ensureBinding`, after `ensureMembership` sees the member row. The integration tests call it directly, always after the member is seated.
