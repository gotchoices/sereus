# One change-subscription seam for control and strand tables

## What landed

- `table-change-watch.ts`: `watchTables(db, tables, onChange, options)` subscribes one Quereus `Database.watch` with a `full` scope per qualified `'Schema.Table'` name and runs `onChange` single-flight: changes inside the coalescing window (`TABLE_CHANGE_COALESCE_MS`, 50 ms) share one run, any number of changes during a run produce exactly one follow-up, and the consumer's `trigger(delayMs)` and the optional `backstopMs` go through the same rule (whichever armed timer fires first starts the run and clears the rest). Optional synchronous `onInvalidate` hears each changed table by the name the consumer passed. `TableWatchRegistry` tracks what each database handed out.
- `ControlDatabase.watchTables` / `StrandDatabase.watchTables`, disposed by each `close()` before its first await and again just before the `Database` handle is dropped.
- `setMembershipChangeListener` doc: local writes notify there; replicated membership changes reach the gate through the control-cohort reconcile pass.
- `docs/architecture.md` → "Table change subscriptions": what the seam hears, what it does not (a machine outside the block's cohort; a table not yet touched), scheduling, why consumers keep a backstop, why the membership listener stays separate.
- Nothing consumes it yet. The consumer tickets (`strand-watcher-woken-by-control-changes`, `control-reconcile-woken-by-changes-reads-once`, `pending-join-runner-woken-by-changes`, `strand-revocation-enforcer-woken-by-membership-changes`, `control-membership-rows-cached-until-changed`) are the first real use, including the first run against the Optimystic plugin's replicated-change events.

## Review findings

Read `ticket(implement): control-and-strand-table-change-subscription` first, then checked it against Quereus's `WatcherManager` (`../quereus/packages/quereus/src/core/database-watchers.ts`, `change-scope.ts`) and the Optimystic plugin's `handleCollectionChange` / `followSchemaTags` (`../optimystic/packages/quereus-plugin-optimystic/src/optimystic-module.ts`).

**Correctness of the scheduler (checked by reading, no defect).** Traced: a change during a run whose window fires mid-run (sets `rerun`, one window after settle); a second change during the same run whose window is still armed at settle (the `??=` reuses it, so still one follow-up); a `trigger` fired mid-run; dispose mid-run (settle returns early, no backstop re-arm); a synchronous throw from `onChange` (inside the `try`, logged). The handler returns `undefined`, so Quereus's `await` on the handler result never waits on consumer work. `event.matched` entries are keyed through the same lowercased `schema.table` Quereus uses, so `onInvalidate` gets the consumer's spelling. The "a change can cut a pending backoff short" behaviour the handoff flagged is the specified "earliest wins" rule; left as is.

**Fixed inline — a subscription taken while `close()` was awaiting outlived the database.** Both `close()` methods disposed watches only before their first await, while `ensureInitialized` keeps passing until the end of `close()`. A `watchTables` call in that span registered a watch whose backstop and trigger timers kept calling `onChange` after the `Database` closed (Quereus disposes its own subscription on close, not the cadre timers). Added a second `disposeAll()` immediately before each `close()` drops the handle, with no await between them. A permanent "closed" flag on the registry was rejected because both wrappers allow `initialize()` again after `close()`.

**Fixed inline — doc.** `timeout-scheduler.ts`'s header listed its users and missed the new one; added it.

**Checked, accepted.** The `NOTE:` that control and strand schemas are fixed for a database's life holds: `Strand` is applied once in `compose-strand.ts` before `initialized` is set, an sApp attach applies only `App`, and the control schema is applied in `initialize()`. Plugin tag overlays raise `table_modified` (which would silently dispose the Quereus subscription) only for an `alter … tags` or an `apply schema` tag diff, and none runs on `CadreControl` or `Strand` after init. The architecture text "a machine outside the block's cohort does not hear it" is still true despite Optimystic's network watch, since that is enabled only for sApp tables tagged `"optimystic.network_watch"` on strand nodes and the plan declined it for the control database.

**Tests.** The four specs are kept. Each pins a branch the consumers depend on: coalescing plus `onInvalidate` naming, exactly one follow-up, no run after dispose, and earliest-wake plus backstop-from-settle. The fourth was beyond the plan's list but covers real branching four consumers rely on, so it meets the bar. No test added for the `close()` sweep: it is one line of ordering in each wrapper, and a test would need a fully initialized Optimystic-backed database to exercise a race.

**Not found / no action.** Type safety: no `any`, Quereus types imported as types. Resource cleanup: wakes are bounded because every run start clears them. Cross-platform: timers only go through `TimeoutScheduler`. File size: `table-change-watch.ts` is 268 lines (`git show --stat`), and the spec is 174. Comments say why, not what. No new tripwires.
