# Reap container records the provider abandoned mid-flight

Shipped. Implement stage landed in `312ece5`; this review pass added the
reclaim-ordering correction below.

## What the feature does

A provider that dies between writing a container record and finishing the
orchestrator call leaves a record no in-flight call will ever advance. A periodic
sweep (`ContainerService.reapStuckContainers`, started with the server and run
once immediately at startup) now finishes those records off:

| Status | Age limit | Outcome |
| --- | --- | --- |
| `pending`, `creating` | `CONTAINER_PROVISIONING_TTL_MS` (15 min) | `error`, container reclaimed |
| `stopping` | same 15 min | `stopped`, container reclaimed |
| `enrolling` | `CONTAINER_ENROLLMENT_TTL_MS` (5 min) | healthy → `running` + peerId; child proven gone → `error` + reclaim; otherwise left alone |

Supporting pieces:

- `RecoverableOrchestrator.resolveDockerId?(containerId)` — maps a provider
  container id back to the runtime's current handle, so a record whose
  `dockerId` was never written is still reclaimable. `DockerOrchestrator` filters
  on the `sereus.container-id` label (labels survive a provider restart; the
  in-memory port map does not). Implemented on `MockOrchestrator` and the
  integration harness's `ProviderProcessOrchestrator` too.
- `QUOTA_CONSUMING_STATUSES` — `error` and `stopped` no longer count against
  `plan.maxContainers`. Nothing deletes container records, so counting `error`
  locked a tenant out of their plan permanently.
- `terminateContainer` routes through `stopAndRemove`, which forgives a
  stop/remove failure when `inspectRunState` affirmatively reports the handle is
  gone, and rethrows otherwise — so a record left pointing at an
  already-reclaimed handle can still reach `stopped`.
- `docs/architecture.md` § `@serfab/cadre-provider` documents all of the above.

## Review findings

### Fixed in this pass

**The sweep could write a terminal status over a container it had failed to
reclaim, orphaning it permanently.** As implemented, three of the four arms wrote
the terminal status *before* reclaiming, and the `stopping` arm reclaimed with
`safeStop`/`safeReclaim` — both of which swallow their errors — then wrote
`stopped` unconditionally. A terminal record is the last time the sweep will ever
look at that container, so a daemon outage during the reclaim left a tenant node
running under `unless-stopped` with its host ports and volume held, unbilled, and
with no record naming it. Nothing could ever find it again.

The implement handoff flagged the `stopping` half of this and asked for a second
opinion; on inspection the same hole existed in the `pending`/`creating` and
dead-child `enrolling` arms, so all four are now one rule:

- `safeReclaim` returns whether the container is now **gone** — removed, or a
  handle `orchestratorKnows` affirmatively no longer recognises (reusing the same
  seam `terminateContainer` already relies on). It still never throws.
- `reclaimStuckContainer` propagates that answer, and returns `true` when no
  handle names a container at all (nothing to reclaim).
- `reapOne` / `reapStuckEnrolling` reclaim **first** and write the terminal
  status only on a confirmed-gone answer. A visibly failed reclaim leaves the
  record in its stuck status, which the next sweep retries — self-healing, which
  is exactly what a *periodic* sweep can afford and `terminateContainer` (a
  one-shot API call that owes its caller an answer) cannot.

This also deleted the arm-by-arm ordering asymmetry the implement stage had to
justify in comments, and crash-safety is unchanged: a crash between reclaim and
status write leaves the stuck status for the next sweep.

Four tests added for it (`container-reap-stuck.test.ts`): reclaim throws but the
handle is gone anyway → still terminalizes; `creating` and `stopping` records
whose container is still there after a failed reclaim → left stuck; a dead-child
`enrolling` record whose reclaim fails → left `enrolling` with no error stamped.
The pre-existing "reclaim throws" test was split into the gone and still-there
cases; previously only the gone case was covered, which is why the hole passed.

**Multi-record sweep continuation was untested** (the handoff said so). Added:
three stuck records where the first throws out of `resolveDockerId` — the other
two are still reaped and the thrower keeps its status.

Docs updated: the `docs/architecture.md` reap bullet now states the
reclaim-then-terminalize rule and why, replacing "every terminal arm reclaims the
container first".

### Recorded as tripwires (not tickets)

- `CONTAINER_ENROLLMENT_TTL_MS` is a module constant, not a function of the
  per-service `enrollmentTimeoutMs` override. A caller raising that override past
  5 minutes would let the sweep and the in-process enrollment wait both write the
  same record. Harmless today — they agree on every outcome, and the waiter
  re-reads status each poll — and nothing in the repo sets the override outside
  tests. `NOTE:` parked at the constant.
- `DockerOrchestrator.resolveDockerId` returns the *first* label match.
  Unreachable today: containers are named `cadre-<containerId>` and the daemon
  refuses duplicate names. `NOTE:` parked at the method.

### Checked, nothing to do

- **No new tickets filed.** Nothing found needed one; the two conditional
  concerns above are tripwires, and the one real defect was fixable in this pass.
- **Port bookkeeping after a provider restart.** `resolveDockerId` finds a
  container by label, but `DockerOrchestrator.containerPorts` is empty after a
  restart, so reclaiming it releases no ports. Already fully described by
  `tickets/backlog/bug-provider-port-allocator-forgets-live-ports-on-restart`
  (same file, same root cause, explicitly names the label as the fix) — not
  re-filed.
- **File size.** `container-service.ts` is 847 lines (`wc -l`), up from ~610.
  Twelfth largest source file in the repo; ten packages carry bigger ones
  (`cadre-core/src/cadre-node.ts` is 4771). Within the norm, no split filed.
- **`fake-docker.ts` not reused** by `docker-orchestrator-resolve-id.test.ts`.
  That helper is scoped to the volume surface by its own doc comment, no other
  test needs `listContainers`, and the local stub is eight lines. Broadening the
  shared helper for one caller would cost more than it saves.
- **The 15-minute provisioning TTL is a judgement call, not a measurement** (the
  handoff says so). No slow `pullPolicy: 'always'` pull was timed here either;
  timing one needs a real registry over a real slow link, which is not something
  this pass can produce. The constant's doc comment states plainly that the TTL
  is the only defence against reaping a genuinely in-flight pull, which is the
  honest form of the claim.
- **`fetchContainerHealthStatus` has no fetch timeout**, so a sweep can sit on an
  unresponsive `enrolling` container until undici's default (~300 s). Not new:
  billing's `collectUsage` reads the same helper for every running container on
  every cycle. The `sweeping` flag bounds the consequence to skipped ticks rather
  than piled-up sweeps, and the sweep logs when it skips.
- **`enrollIfHealthy` writes `running` without re-asserting the record is still
  `enrolling`.** A `DELETE` landing inside the health fetch could be overwritten.
  Pre-existing and identical in `waitForEnrollment` (it checks status, then
  awaits the fetch, then writes) — the sweep does not widen the window per
  attempt. Left alone rather than changing the shared write path outside this
  ticket's scope.
- **Tenant-visible quota change** (a customer at their plan limit purely from
  `error` records can create again immediately) — the intended fix, correctly
  documented in `architecture.md`; not a regression.
- **No integration-level exercise** of `ProviderProcessOrchestrator.resolveDockerId`
  (the handoff says so). It is a four-line scan of the harness's own `handles`
  map, typechecked and structurally identical to `MockOrchestrator`'s, and the
  real-network suite routinely exceeds the runner's idle budget. Not worth a
  coverage ticket at that ratio.
