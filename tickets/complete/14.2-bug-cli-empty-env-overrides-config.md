# Empty environment variables no longer override configured values

## What was wrong

`applyEnvironmentOverrides` (`packages/cadre-cli/src/config/loader.ts`) treated any *defined*
env var as an override, including the empty string (`FOO=`). Docker Compose's `${VAR:-}` syntax
sets an unset optional var to `''` rather than leaving it unset, so every optional var in
`packages/cadre-cli/docker/docker-compose.yml` (e.g. `CADRE_ENABLE_RELAY=${CADRE_ENABLE_RELAY:-}`)
reintroduced a `false`/`[]`-style override on every container start, clobbering values the node's
own config file had set. `docker/entrypoint.sh` was already correct (it guards every optional key
with `[ -n "$VAR" ]`); the bug was solely in the CLI-side override pass, which runs *after* the
file loads and stomped what the entrypoint had correctly omitted.

## What shipped

- The override loop skips a var when `undefined` **or** `value.trim() === ''`, before any
  per-variable parsing — one guard covering every `ENV_MAPPINGS` entry
  (`packages/cadre-cli/src/config/types.ts`): scalars, `_NODES`/`_ADDRS` lists, `_ENABLED`/`_RELAY`
  booleans, `CADRE_STRAND_FILTER`, `CADRE_PUSH`.
- `parsePushEnv` / `parseStrandFilterEnv` lost their own empty-string branches (returned
  `undefined` / `'all'`), which the loop-level guard makes unreachable. The functions themselves
  remain — they still do real JSON parsing.
- **(review)** `setNestedValue` now copies each intermediate object on the way down, so an
  override no longer mutates the caller's config (see findings below).
- **(review)** `README.md`'s env-var table now documents the empty-value rule and the five
  mappings it was missing.

`packages/cadre-host/src/orchestrator/host-process-orchestrator.ts` builds its child's env
explicitly rather than blanket-passing optional vars with empty defaults, so it never exhibited
this bug. The separate concern of *ambient* env leaking from a host process into a spawned child
stays tracked by `tickets/plan/22-debt-host-child-env-inheritance.md`.

## Review findings

**Checked:** the full `f0e262f` code diff read before the handoff summary (the `8b3de74`
"implement" commit only moved the ticket file — all code landed in the fix-stage commit);
`loader.ts` in whole, not just the hunks; `ENV_MAPPINGS` vs `docker-compose.yml` vs
`entrypoint.sh` vs `README.md` for drift; the dead-code claim's call graph; every existing
`cadre-cli` spec that touches `applyEnvironmentOverrides`; `docs/STATUS.md` and
`docs/architecture.md` mentions of `CADRE_PUSH`.

**Fixed in this pass (minor):**

- *`applyEnvironmentOverrides` mutated its input.* It shallow-copies (`{ ...config }`), so
  `setNestedValue` wrote through to the caller's own nested objects — an override of
  `network.enableRelay` mutated the passed-in `network` block, and `controlNetwork.partyId` /
  `.bootstrapNodes` mutated a shared `controlNetwork`. Dormant in production (`resolveConfig`
  discards the pre-merge object) but a live cross-test contamination hazard: the sibling specs
  share a module-level `baseConfig` and spread only its top level, so an ambient `CADRE_PARTY_ID`
  in the runner's environment would have leaked between test files. `setNestedValue` now
  copy-on-writes each branch via a small `cloneBranch` helper; regression test added.
- *Two existing test names became lies.* `push-config.spec.ts` "treats an empty CADRE_PUSH as
  undefined" and `strand-filter.spec.ts` "treats an empty value as all" still pass, but only
  because their base configs never set the field — they now describe a parser behavior that no
  longer exists. Renamed to state what they actually assert.
- *Missing coverage on exactly the two paths whose branches were deleted.* The new spec covered
  booleans and lists but not `CADRE_STRAND_FILTER=` / `CADRE_PUSH=` against a config file that
  *does* set those fields — the case the removed branches used to get wrong. Both added.
- *`README.md` env table was stale.* It omitted `CADRE_IDENTITY_PROTOBUF`, `CADRE_ANNOUNCE_ADDRS`,
  `CADRE_ENABLE_RELAY`, `CADRE_STRAND_FILTER`, and `CADRE_PUSH`, and said only "environment
  variables override config file values" — the sentence this ticket falsified. Rows added and the
  empty-value rule spelled out, including how to actually force a value off
  (`CADRE_ENABLE_RELAY=false`).

**Filed as new tickets (major):** none. The fix is a single correct guard at the right layer,
fully contained in `cadre-cli`, and everything found was small enough to land here.

**Tripwires recorded:** one — a separators-only list value (`CADRE_BOOTSTRAP_NODES=,`) passes the
non-empty check but splits to `[]` and clobbers the file's list. Only reachable via a
hand-written launcher value no template produces, so it is a `NOTE:` comment at the list branch
in `loader.ts`, not a ticket.

**Verified but not changed:**

- The dead-code claim holds: `parsePushEnv`/`parseStrandFilterEnv` are reachable only through
  `parseEnvValue`, itself called only from the override loop, which now guarantees non-empty
  input.
- `entrypoint.sh`'s comment about the CLI re-applying `CADRE_STRAND_FILTER` over the loaded config
  is still accurate — its `[ -n ]` guard means the CLI only ever sees a non-empty value there.
- `CADRE_STORAGE_QUOTA` appears in `docker-compose.yml` with no `ENV_MAPPINGS` entry; that is by
  design, `entrypoint.sh` writes `quotaBytes` into the generated YAML instead. Not a defect.
- `docs/STATUS.md` and `docs/architecture.md` describe `CADRE_PUSH` as a JSON env override; still
  true, no edit needed.

**Known gap carried forward:** no end-to-end test brings up the Compose stack with
`CADRE_ENABLE_RELAY` unset to confirm the container-level symptom. Coverage is at the
`applyEnvironmentOverrides` unit level, which is where the confirmed root cause lives; a live
container repro was not run in either stage. Not filed as a ticket — the missing piece is
Docker-in-CI infrastructure, not a defect in this change.
