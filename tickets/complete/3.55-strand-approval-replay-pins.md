# Complete: approval-replay attack pins + five-element digest parity

Implement stage added the six replay pins (R1–R6) and the five-element digest parity case.
Review stage re-derived every pin against the schema, then closed the two weak spots the
implement handoff itself flagged and added the one uncovered replay vector.

## What the implementation shipped

`packages/cadre-core/test/strand-approval-replay.spec.ts` (new) — each of R1–R6 captures the
approval a writer minted over a live row, performs the legitimate state change, replays the
captured approval, and asserts rejection; each then runs the legitimate operation the replay
was derived from, so a rejection can never be an artifact of an impossible state.

| # | Captured approval | Replayed as | Pinned rejector |
|---|---|---|---|
| R1 | `addManager` promotion of X at generation 1 | re-insert `Manager(X, 1)` after removal | `NotRevoked` |
| R2 | `removeManager` removal of X | delete `Manager(X)` after re-promotion | `Authorized` |
| R3 | X's own resignation | delete `Manager(X)` after re-promotion, by a party that never held X's key | `Authorized` |
| R4 | `addMemberByManager` admission of X | re-insert `Member(X)` after revocation | `NotRevoked` |
| R5 | `revokeMember` removal of X | delete `Member(X)` after re-admission | `Authorized` |
| R6 | `registerMemberPeer` binding (M, P) | re-insert (M, P) after removal; plus the same approval on the DELETE | `NotRevoked`, then `Authorized` |

`digest-variadic-parity.spec.ts` case (e) pins the only signed digest carrying an SQL INTEGER
(the Manager promotion's `Generation`): bound number ⇔ SQL integer literal hash identically,
and both stringified directions fail to verify.

## Review findings

**Checked:** the implement diff read first, before the handoff; every one of R1–R6 re-derived
by hand against `schemas/strand.qsql` (which constraint fires, and that each *sibling*
constraint on that statement genuinely passes); each captured digest element vector compared
against the writer that mints it in `strand-membership-writer.ts`; the `Strand.Revocation`
growth tripwire confirmed present byte-identically in both schema copies (drift is pinned by
`quereus-plugin-sereus/test/strand-schema-drift.spec.ts`); coverage compared against every
signed rule in the schema; docs re-read for staleness.

**Confirmed sound, nothing changed:** all six pins name the right constraint. Every
re-insert replay (R1/R4/R6a) genuinely reaches `NotRevoked` with its `Authorized` branch
satisfied, and every delete replay (R2/R3/R5/R6b) genuinely fails `Manager`/`Member`/
`MemberPeer.Authorized` with `RevocationRecorded`, `MinOneMember`/`MinOneManager`,
`NotAManager`, `RowIsGone`, and `Immutable` all passing. The implement note about the
ticket's self-contradictory parity wording is correct: type-tagged framing makes the number
and the stringified generation hash differently, so the case pins parity on the number leg
and mismatch on the string leg. Both are asserted.

**Fixed in this pass (minor):**

- *`/Authorized/` could not distinguish two different constraints.* The engine's message is
  `CHECK constraint failed: <name>` with no table qualifier, and `Strand.Revocation` carries
  its own `Authorized`. Every delete replay files a tombstone in the same transaction, so a
  broken tombstone helper would produce an identically-matching failure while the pin
  silently measured the wrong gate. Added a control test that commits the *same* raw
  delete + `fileTombstone` shape with a valid approval against all three guarded tables —
  the tombstone leg is now proven to pass on its own, so the captured signature is the only
  differing input in a replay.
- *"Capture" rested on an unpinned assumption.* Nothing here can intercept the writers' real
  signature bytes, so each capture re-mints them; that is only a real attacker capability
  because ed25519 signing is deterministic. Added a test asserting two mints of the same
  vector are byte-identical, so a future signer swap that introduced randomness fails loudly
  instead of quietly turning the whole spec into strawmen.
- *One replay vector was uncovered.* The `Member` self-departure branch (`'leave'`, verified
  against the departing key itself) is the one delete path R5 does not reach and no sibling
  spec pinned. Added **R7**: a captured departure replayed after re-admission is rejected by
  `Authorized`; a genuine second departure still works.
- *Docs were stale.* `docs/architecture.md` described the single-use stamp mechanism without
  citing any pin, though the surrounding text cites spec files for every other closed hazard.
  Added the citation for both new specs and stated plainly that coverage is single-node only.

**Filed as new tickets:** none. Nothing found rose to a separate ticket — the mechanism
itself was already reviewed under `strand-approval-stamps-and-tags`, and this ticket's
surface is tests plus one doc paragraph.

**Recorded as tripwires:** none newly parked. The `Strand.Revocation` growth tripwire (the
table only grows — one row per membership deletion plus any junk a member files, and
`Immutable` means rows never leave; needs pruning if churn ever gets large) was already
written into both schema copies by the parent ticket and is unchanged.

**Deliberately not addressed:**

- *Multi-node replay is untested and untestable in this harness.* Every test runs against a
  bootstrap-mode strand (MemoryRawStorage + the optimystic local transactor). The
  convergence hazard the schema documents — a node that has not yet seen a `Revocation` row
  still accepts a replayed add, and the resurrected row coexists with the tombstone after
  merge — has no coverage. Now stated in `docs/architecture.md` rather than only in a schema
  comment.
- *`Strand.Invite` / `ConsumedInvite` have no replay pins*, by design: both are insert-only
  with a fresh primary key per row, so a replayed insert collides on the key. The separate
  gap that a revoked member re-admits itself off an unspent invite is pinned as accepted
  behavior in `strand-member-revocation.spec.ts` and tracked as
  `bug-strand-invite-no-revocation`.
- *`fileTombstone` is duplicated across three specs*, mirroring the writer's private
  `insertRevocation`. The parent review considered and kept the duplication; not re-opened.
