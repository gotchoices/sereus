## Summary

`packages/reference-app-ns/src/polyfills/text-decoder.ts` is a TypeScript port of the `TextDecoder` block in `packages/cadre-rn/polyfills/hermes.js`: the Encoding Standard's UTF-8 decoder with replacement, output built in chunks of 4096 code units. `hermes.ts` installs it when the global is missing. The decoder inputs that cadre-rn's conformance test used moved to `test-harness/utf8-decoder-inputs.ts`, and both apps' tests compare their decoder with Node's on those inputs. Each copy of the decoder has a comment pointing to the other. `docs/reference-app-ns.md` describes the new decoder. Landed in `ticket(implement): bug-ns-textdecoder-misdecodes-invalid-utf8`.

## Review findings

- **Port fidelity**: compared `text-decoder.ts` with cadre-rn's block line by line. The logic is the same; the only differences are type annotations, the `as unknown as number[]` cast in `pushString`, and class fields in place of constructor assignments. No defect.
- **Test strength**: weakened the E0 lower bound in the NS decoder by hand (`0xA0` → `0x80`). The NS test failed with 143 mismatches; I restored the file. The implementer had already run the old decoder against the test and seen 3,691 mismatches. The test is the bug's reproduction and is kept; I added no tests and cut none.
- **Duplication**: the decoder now exists in two places, cadre-rn's JavaScript and the NS TypeScript. The NS app cannot import cadre-rn's `hermes.js`, because that file installs React Native globals when loaded. The two copies point at each other in comments and are tested on the same inputs, so if one changes and the other does not, a test fails. I accepted this and filed no ticket.
- **Edge cases**: empty input, `null`/`undefined`, `ArrayBuffer`, other typed-array views and offset subarrays all reach `decodeUtf8` correctly. Empty input gives `[].join('')`, which is `''`. Any label other than UTF-8 throws `RangeError`, as before. The `{ stream: true }` option is still ignored, as in cadre-rn and the old decoder; nothing in the dependency graph calls it with that option, so I left it alone.
- **Resource and concurrency**: the shared module-level `Uint16Array` is safe because `decode` runs synchronously and never calls itself. The same constraint is commented in both copies.
- **Type safety**: `AllowSharedBufferSource` matches the DOM lib's `TextDecoder.decode`. `toBytes` in `hermes.ts` overlaps with the byte conversion in `decode`. The two stay separate so that `text-decoder.ts` does not import the module that installs globals. I accepted that; it is three lines.
- **Tripwire**: the `structuredClone` `NOTE:` the implementer added in `hermes.ts` (ungap is used for every clone; port cadre-rn's direct-copy path if profiling shows a cost) is a correct tripwire. I left it as written.
- **Docs**: the `TextDecoder` row in `docs/reference-app-ns.md` is accurate. Fixed inline: the `src/polyfills/` line in that doc's source tree named 8 of the 17 files and not the new one. It now describes the directory and points to the "Polyfilled on NativeScript" table rather than listing files. `docs/testing.md` documents only cadre-rn's polyfill specs and has never covered the NS app's `polyfills.spec.ts`. That gap predates this ticket, and the change does not make it worse, so I left it.
- **Validation**: `yarn workspace @serfab/cadre-rn vitest run --project polyfills` passed (3 files, 33 tests). `yarn workspace @serfab/reference-app-ns vitest run test/polyfills.spec.ts` passed (8 tests). `yarn workspace @serfab/reference-app-ns typecheck` passed. `yarn lint` exited 0. Not run: `test:bundle` and on-device runs. The only change to what the bundle sees is one relative `.ts` import in `hermes.ts`, so I expect no effect, but that is not verified.
- **Major findings**: none, so I filed no tickets.
