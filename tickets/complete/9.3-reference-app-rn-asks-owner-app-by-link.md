# Phone reference app asks the owner app by link (joining side)

The joining app's half of the same-phone join. **B** is this app, joining; **A** the owner app it opens. Kit: `@serfab/cadre-rn/app-link` (`phone-kit-same-phone-join-links`). Owner side and link routing: `reference-app-rn-answers-join-requests-by-link`. Landed as `ticket(implement): reference-app-rn-asks-owner-app-by-link`.

## What was built

- **Settings → Join my existing cadre → Choose the app that holds your cadre** (`join-cadre-section.tsx`): Android opens the request text, so the system chooser lists every owner app (this one included); iOS shows a list of the installed Sereus apps (`installedOwnerApps` in `join-link.ts`), with a line when there are none. Then "Waiting for ‹app› to answer…" with **Cancel**, or the line saying this app's own request opened it again. Copy and paste stay below as the fallback.
- **`src/use-link-request.ts`**, composed into `useJoinFlow` so `useCadre()` exposes it: `linkRequest` (read from the store at mount), `linkRequestReturned`, `askOwnerApp`, `cancelLinkRequest`, `linkRequestCameBack`, and `takeJoinResponse`, which never throws and returns an outcome (`joined`, `join-failed`, `refused`, `join-under-way`, `unsolicited`, `unreadable`) that `joinResponseAlert` in `join-link.ts` puts into words.
- **`app/settings.tsx`**: `useLinkedJoinResponse` reads and clears the `joinResponse` parameter and holds it until the launch read is done and no plain start is connecting, so the join does not stop a node the hook is still showing as starting. The owner-side own-request alert became `linkRequestCameBack`.
- **`src/cadre-phone.ts`**: the one `LinkRequestStore` (`linkRequests`), `ownScheme()`, `extraSereusApps()` (validated; malformed reads as none, logged), `joinRequestText(reply?)`.
- **`app.config.ts`** (the kit plugin entry moved here from `app.json`) with one list of extra Sereus apps, given to the kit plugin (`appLinks.extraApps`) and to the app (`extra.sereusApps`); `APP_VARIANT=second` builds a second install ("Sereus P2P Chat (second)", scheme `sereus-chat-second`, ids ending `.second`). `eas.json` profile `development-second`.
- **Docs**: `docs/reference-app-rn.md` ("Joining an Existing Cadre", "Open link request" storage, "A second install for one phone", own-request bullet, file listing), `docs/architecture.md` (both paragraphs), README ("A second install on one phone").
- **Device run**: `tickets/blocked/rn-device-run-same-phone-join-by-link.md`. Nothing here has run on a device.

## Review findings

Read the implement diff first, then the kit's `LinkRequestStore`, `links.ts` and `PhoneNode.linkRequestSlot`, `use-cadre.ts`'s launch read and `start`, `use-join-flow.ts`, `+native-intent.tsx` and every doc the change touches.

**Checked, no change needed**
- *Cold-start ordering:* the launch read sets `savedStartRead: 'read'` and `start` sets `status: 'connecting'` in the same continuation (batched), so `useLinkedJoinResponse`'s hold has no one-render window in which the answer would race the auto-start. A start that fails ends in `error`, which releases the hold.
- *Own request before `no-cadre`:* `useLinkedJoinRequest` checks for this app's own request before the no-cadre answer, so a first-launch B picked in Android's chooser does not answer itself `no-cadre`.
- *Android "came back" race:* `askOwnerApp`'s read-back, the came-back cancel and the store's single turn queue settle on "no open request" in either order.
- *Log hygiene:* `withoutLinkText` cuts the request body after `sereus-join-request:1.`, which both the Android form and the iOS `<scheme>://cadre-join-request/<text>` form contain; `refusedAnswer` logs only error messages.
- *`extraSereusApps` and `installedOwnerApps`:* each install leaves out its own scheme, so the main install lists the second and the second lists the main.
- *Deviations in the handoff* (`app.config.ts` over `.js`, a separate `use-link-request.ts`, `askOwnerApp` resolving false, holding the answer until the start settles, the alert wording, the came-back line persisting until the next Choose): all sound; kept.
- *Tests:* none added and none cut. The hook maps kit results to words; the kit's store tests pin the nonce/once/30-minute contract. The react spec's two mock additions are the minimum to keep it loading.
- *Docs:* read `docs/reference-app-rn.md`, `docs/architecture.md`, the app README and the kit README; the kit README's `app.json` mentions describe a generic Expo app and stay.

**Found and fixed (minor)**
- A join from a pasted or scanned response left an open link request behind: the section kept saying "Waiting for ‹app› to answer…" after the join, and a late answer from that app, once the flow was dismissed, would have run a second join. `JoinCadreSection.join` now cancels the open request after a join (`join-cadre-section.tsx`); the "Open link request" storage paragraph in `docs/reference-app-rn.md` lists it among what clears the record.

**Tripwires parked (`NOTE:`)**
- The waiting line does not notice the 30-minute expiry by itself until the next read: `showOpenRequest` in `use-link-request.ts`.
- On iOS a second Choose of a different app reuses the open request, including the first app's name, so the waiting line names the first app: `askOwnerApp` in `use-link-request.ts` (kit `begin` behaviour).

**Not filed**
- A take that passes the `join-under-way` check and then loses a race with a paste-join surfaces as `join-failed` ("A join is already on screen") with the request consumed. Needs two joins started within one store read; contrived, and the alert is accurate. No ticket, no note.
- No major findings; nothing filed.
