# The deadline ladder under a strand's reads and writes

Doc-only. `docs/cadre-consistency.md` → "Deadlines Over Optimystic's Reads and Commits" gains a subsection, "Deadlines Below Cadre": a 26-row table, in six groups, of the Optimystic, FRET and libp2p deadlines a strand's reads and writes wait on. For each row it gives the value at the default declaration, whether the value follows `NetworkConfig.linkRoundTripMs` or is fixed (or a host option), what it bounds, and where it is defined. One sentence after the table explains why FRET's ring deadlines matter to a write. The table was read at `@optimystic/*` 1.15.0 (`28e6e044`) and `p2p-fret` 1.1.0 (`6c04166`). `docs/architecture.md` → "Known limits at the supported round trip" gains one bullet: FRET's maintenance deadlines are fixed below the supported round trip. It links `blocked/fret-maintenance-deadlines-below-the-declared-link` and the new subsection.

The sentence that points to the phone-link scenario was handed to `implement/strand-workload-on-a-phone-link-scenario` as a TODO, because the scenario file it names does not exist yet.

## Review findings

Read the diff of `ticket(implement): strand-deadline-ladder` first, then checked each row against its site in the sibling trees. Both trees are at the commits stated, with no local changes. Nothing was built or written there.

- **Values checked and correct.** In `rpc-deadline.ts`, `resolveLinkDeadlines` derives these, with cadre's explicit request dial of 42 500 ms: hedge 1.5 × 3 500 = 5 250; dead connection = request dial = 42 500; inbound upgrade 5 × 3 500 = 17 500; response 3 × 3 500 = 10 500; transaction 4 × 42 500 = 170 000. Those are the values `collection-factory.ts` reads from `node.linkDeadlines`, and the cancel budget is `max(5 000, dial)`. Also checked: `optimysticDialLimits` (39 000 / 42 500) and `cohortReadDeadlineMs` (2 round trips, 7 000). The reconcile pass is `max(5 000, 5 × per-peer)`. FRET's redial is `libp2pDialTimeoutMs`, the resolved `connectionManager.dialTimeout` (39 000). `DEFAULT_CONNECTION_MONITOR` is 30 000 / 35 000 and can be replaced with `NetworkConfig.connectionMonitor`. `@libp2p/ping` 3.1.13 `TIMEOUT` is 10 000. FRET's constants are 2 000 / 1 000 / 3 000 / 5 000 / 5 000, and `readFramed` defaults to `RPC_TIMEOUT_MS`. `deadAfterFailures` defaults to 3, Optimystic does not set it, and `isLiveMember` excludes `dead` peers. `readRepairWindowMs` is 10 000, a `CoordinatorRepo` default that applies only when no value is declared. `DEFAULT_PEND_DELIVERY_DEFERRAL_MS` is 2 000. The commit-broadcast retry defaults are 250 / ×2 / 8 000 / 5, and `resolveClusterPolicy` passes none of them. `DEFAULT_SIGN_COLLECT_TIMEOUT_MS` and `DEFAULT_INBOUND_AUTHORIZATION_TIMEOUT_MS` are both 5 000.
- **Claims that are not constants, checked.** `RepoClient` sets no response timeout: the request is bounded by the caller's `expiration`, which the transactor sets from `timeoutMs` per operation (`network-transactor.ts` 181, 701, 1140). `processBatches` retries at once, with no backoff, while `expiration > Date.now()`. `findCoordinator` throws `all candidates excluded` once self is in the excluded set and the network has more than one peer, so a two-member strand gets two attempts. `get:retry` runs only while `Date.now() < expiration` and has no timer of its own. `updateMember` makes `1 + immediateRetries` attempts.
- **Fixed inline (minor).** The commit-broadcast row left out that the first broadcast asks each member twice (`commitBroadcastImmediateRetries`, default 1). The scheduled retries ask once (`commit-retry` uses 0). One clause added to the row.
