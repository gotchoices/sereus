# Schema guide examples execute in a test

## What landed

`packages/quereus-plugin-sereus/test/schema-guide-examples.spec.ts` (plugin's `unit` Vitest project) reads `docs/schema-guide.md` with `marked` (new devDependency) and walks every fenced block. Each fence's info string must be `sql schema`, `sql script` or `sql fragment`; anything else fails. A `script` block is run as-is. A `schema` block is applied through the plugin's own `applyAppSchema` in a fresh in-memory `Database` (crypto plugin registered, `has_role` stubbed), applied again `with seed`, and then an insert, update and delete are planned against every table (supplying every declared context variable) and a select against every view — because Quereus compiles CHECK constraints when a write is planned, not at `create table`. `fragment` blocks are not run (`tickets/backlog/debt-schema-guide-query-examples-unchecked.md`).

The guide was repaired so every example passes: fences marked, the fictional `schema "…" version 1 using (…)` header dropped, seed syntax fixed, `ifnull` → `coalesce`, `create unique index` / `create assertion` → item forms, `with context (…)` declarations added, invented functions replaced with the crypto plugin's `digest` / `verify`, missing columns added. The Seeds section says Sereus applies app schemas without `with seed` (`tickets/blocked/decide-sapp-schema-seed-rows.md`).

In review, `applyAppSchema` (`packages/quereus-plugin-sereus/src/compose-strand.ts`) now declares the schema, refuses it if the declaration holds any item the Quereus parser skipped (`declareIgnored` — a `create …` prefix, a misspelled item keyword), and only then applies it. That check was a test-only copy in the implement pass.

## Review findings

Read the `ticket(implement): debt-schema-guide-examples-never-executed` diff first, then the whole guide, the spec, `applyAppSchema`, the Quereus parser's `declareBlockItem` / `declareIgnoredItem`, and the crypto plugin's `digest` / `verify` signatures.

- **Class-level (fixed inline): app schemas silently lost items.** The spec checked for parser-ignored items only on guide examples, via a second copy of `applyAppSchema`'s wrapper. Every real sApp schema had the same hole: Quereus keeps an item with an unknown leading keyword as an opaque placeholder and apply ignores it, so `create table X (…)` produces no table and no error. Moved the check into `applyAppSchema` itself (reads `db.declaredSchemaManager` after the declare, so the browser bundle still never imports `@quereus/quereus` at runtime), which also removed the spec's duplicate wrapper and its `Parser` import. It immediately exposed two live instances: `packages/cadre-core/test/cadre-node.spec.ts` and `schema-verification.spec.ts` used `create table …` as their sApp schema, so those strands had been running with no app table; both fixed to `table …`. Confirmed once by reverting the cadre-node schema: 4 tests fail with the new message. Added one test in `plugin.spec.ts` (`applyAppSchema` › refuses a skipped item before applying anything). README `schema` option row and guide intro now say such items are refused. Grepped the reference apps' embedded schemas, `schemas/*.qsql` and the integration-test schemas for `create`/`domain`/`import`/`collation` item forms: none.
- **Guide bug the harness cannot see (fixed):** Generated Columns example had `check (like(author_email, '%@%'))`. Quereus's `like(pattern, text)` takes the pattern first (`../quereus/packages/quereus/src/func/builtins/string.ts`), so that check would have refused every real email. Changed to `author_email like '%@%'`. It planned cleanly, which is the known gap: planning proves a check compiles, not that it accepts a sensible row. Parked as a `NOTE:` tripwire in the spec header and a sentence in `docs/testing.md` → "Lint coverage"; not a ticket, since the remaining checks were read and look right (`verify(data, sig, key, curve)` order matches the plugin; `digest` is variadic).
- **Upstream (Quereus, sibling repo, read-only here — not filed):** a `seed <table> values (<cols>) values (…)` column list is dropped at apply and rows insert positionally (`../quereus/packages/quereus/src/runtime/emit/schema-declarative.ts` stores only `seedData`); and `DeclareIgnoredItem.text` is always empty, which is why the new refusal can report only a count. No matching open Quereus ticket found by grep. A human should file both in the Quereus repo; the guide's caution sentence in "Seeds" is the in-repo reminder and should go once the first is fixed.
- **Tests:** the implementer's cases are one per guide example plus the "every fence is marked" case; each is the guide's own contract, none restates implementation. Kept all. The dropped assertion (ignored-item count) now lives in `applyAppSchema` and its one new test.
- **Code quality:** spec is ~150 lines of small single-purpose functions; comments state why (compile-at-plan, determinism of the stub, loop instead of `it.each`). `marked` placement and range fine. No resource leaks (`db.close()` in `finally`).
- **Docs:** `docs/testing.md`, the guide, and the plugin README updated. `docs/architecture.md`'s description of the sApp apply is still accurate (it does not describe item validation).
- **Not checked / left:** query fragments (backlog ticket above); runtime execution of writes (tripwire above); `feat-shared-causal-history-for-sapps` also edits "Ordering Events" and must keep the fence markers — the unmarked-fence test enforces that.
