# Approver-key enrollment — complete

## What shipped

An invitation can carry a web address that an outside approver has to sign off on before the
invitation can be redeemed. The party decides which approvers it trusts by enrolling their
public keys. The database could always store those keys; nothing above it could add, list, or
remove one, so approval-gated invitations were unusable.

Now:

- `ControlDatabase.queryValidationKeys()` — reads the enrolled set, sorted in TypeScript.
- `CadreNode.enrollValidationKey` / `removeValidationKey` / `listValidationKeys` — the first
  two owner-signed, the third read-only.
- `cadre validation-key add|remove|list` — the operator command, with `-c/--config`,
  `--json`, `-d/--debug` like the other one-shot commands.
- A shared `node-session.ts` helper (`resolveStorageConfig`, `oneShotNodeConfig`,
  `withConnectedNode`) replacing what would have been a third copy of the connect/act/stop
  dance; `start.ts` and `strands.ts` were moved onto it.

Two module-level helpers in `cadre-node.ts` — `signMessageWith` (the sign callback the
`ControlDatabase` writers expect) and `requireNonBlank` — plus a private
`requireOwnerSigningKey(action)` guard, now used by all four owner-signed writes.

### Fixed in this pass

- **The new `requireOwnerSigningKey` / `signMessageWith` helpers were not applied to the two
  methods they were extracted from.** `publishStrand` and `publishFormationInvite` still
  carried their own copies of the identical not-started / no-signing-key guard and the
  identical sign closure — the duplication the helpers exist to remove, left in place.
  Both now call the helpers; 22 lines of copy deleted. No test pinned the old message
  wording, and `cadre-core` + `cadre-host` stay green.
- **`requireOwnerSigningKey`'s error tail said "before publishing"** whatever the action was,
  so enrolling a key advised the operator to run genesis "before publishing". Reworded to
  "before writing owner-signed control state".
- **`withConnectedNode` could crash the process instead of reporting a timeout.** `start()`
  was awaited before the connect promise, so if `start()` outlived the 30s timer the
  timeout's rejection had no handler attached at the moment it fired — an unhandled
  rejection, which Node turns into a process exit, losing the very message the timeout is
  there to print. Both are now awaited together via `Promise.all`.
- **No test existed for the CLI command.** Added `packages/cadre-cli/test/validation-key.spec.ts`
  (17 tests). To make the read-then-decide logic testable it was extracted into pure
  `planAdd` / `planRemove` / `formatKeyList` and a thin `applyAdd` / `applyRemove` over a
  narrow `ValidationKeyStore` interface — the same shape `status.spec.ts` uses against
  `status-query.ts`. Covers: already-enrolled writes nothing, not-enrolled writes nothing,
  last-key warning fires only when the set empties, key trimming on both paths, empty-list
  wording, and the commander wiring (subcommands, shared options + `cadre.yaml` default,
  required arguments).
- **Docs were stale in three places.** `docs/architecture.md`'s CLI command list omitted
  `validation-key`; `packages/cadre-cli/README.md` had no section for it; `docs/STATUS.md`
  still carried "an operator still cannot enroll the approver key" as an open item pointing
  at this ticket in `implement/`. All three updated, and the STATUS entry now names the two
  gaps that remain (below) instead of implying the feature is finished.

### Filed as tickets

- **`backlog/debt-control-key-enrollment-accepts-malformed-keys`** — enrollment validates only
  "not blank". `schemas/control.qsql` puts no format constraint on the column, and the row's
  signature is made by the owner *over* the key as data, so the key's own well-formedness is
  never exercised. `cadre validation-key add "nto-a-key"` succeeds, `list` echoes it back,
  and the failure surfaces much later as a generic authorization refusal on a different
  machine. Owner-key enrollment has the identical hole, so the fix belongs in one shared
  guard rather than in this command. (The implement handoff stated a malformed key "fails the
  signature CHECK" — it does not; it enrolls silently, which is what makes this worth a
  ticket.)
- **`backlog/debt-validation-url-redemption-e2e`** — no test runs an approval-gated invitation
  end to end, and the approval client has never been pointed at a real HTTP server. Every
  component is unit-tested; the seams between them are not. Pre-existing, but this ticket is
  what makes it the next thing standing between the feature and being usable.

### Recorded as tripwires, not tickets

- `process.exit` does not flush a pipe, so piped output written immediately before it can be
  lost. Fine at these sizes and identical in `strands` / `status` / `start`, so it is a
  repo-wide pattern rather than this command's bug — `NOTE:` on `runSubcommand` in
  `validation-key.ts`.
- `add`'s read and write are not atomic; a concurrent enroller makes this one fail on the raw
  primary-key constraint instead of reporting "already enrolled". Harmless for a human at a
  terminal — `NOTE:` on `applyAdd`.

### Checked and found sound

- **`queryValidationKeys` needs no revocation filter.** A removal deletes the live row and
  retires only its stamp into `Revocation`, so the live table *is* the enrolled set. Verified
  against `schemas/control.qsql`.
- **Enrolling this node's own owner key is safe.** The domain/action tags baked into each
  authorization digest mean an owner-key signature cannot satisfy an approval rule or vice
  versa. The doc comment's claim holds.
- **Sorting in TypeScript rather than SQL.** No `order by` appears anywhere in this package;
  the enrolled set is a handful of rows. Correct call, and the spec pins the ordering.
- **The `strands.ts` refactor.** Reviewed line by line: the timeout became a rejected promise
  caught by the existing `catch` (previously an inline `console.error` + `process.exit(1)`
  inside the timer), and `process.exit(0)` moved out of the `control:connected` handler to
  after `withConnectedNode` resolves. Behaviour is equivalent and the error path is strictly
  better (an async handler's throw used to be an unhandled rejection). **Not runtime-verified**
  — it needs a live control network, which no test in this repo stands up for the CLI. That is
  unchanged from before the refactor; `strands` had no test then either.
- **Removal's non-retroactivity, and its complement.** The new node-level spec pins that a
  redemption approved before removal survives it. The complement — that the removed key can no
  longer approve *future* redemptions — is already pinned at the database layer by
  `control-formation-invite.spec.ts:857`. The implement handoff listed this as an untested
  gap; it is not.
- **The spec reaching into the node's private `identityKey`.** Flagged by the handoff as
  possibly wanting a public accessor. Left as is: it is one line in one test, and widening
  `CadreNode`'s surface to avoid it would be the larger cost.
- **The `add` "already enrolled" check being a read rather than error-text matching.** Right
  call — matching Quereus constraint text would break on any message change.
- **`requireNonBlank` trimming and writing the trimmed value.** Consistent across enroll,
  remove and the CLI's comparison, and now pinned by tests on both sides.
- **Convergence.** A key enrolled on one node is invisible to a sibling until control
  replication catches up. Recorded as a `NOTE:` in the `enrollValidationKey` doc comment by
  the implementer; correct placement, and it mirrors the note the schema already carries on
  `ValidationKey`. Not testable without a multi-node harness.

### Not found

No correctness defect in the shipped behaviour itself — enroll, remove, list, the tombstone,
re-enrollment on a fresh stamp, the no-op paths and the guard errors all behave as documented
and are covered by the 9-test core spec, which passes.
