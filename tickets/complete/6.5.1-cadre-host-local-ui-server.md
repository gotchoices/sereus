## What landed

A long-lived Fastify management server bound to `127.0.0.1:<uiPort>`, exposed via `createLocalUiServer(opts)` and wired into `cadre-host start`. The CLI's existing `/auth/*`, `/nat/*`, and `/update/*` contract is preserved; new UI-only routes live under `/api/*` (`status`, `nodes`, `settings`, `events`); a hand-rolled Server-Sent Events stream powers reactive updates. A loopback-origin guard rejects non-localhost `Host` / `Origin` headers. A `cadre-host ui` subcommand prints + opens the local URL.

See the implement ticket for the full file inventory; this section captures only what changed during review.

### Findings & dispositions

**Minor — fixed inline**

1. **`/api/nodes/:id/stop` double-published `node-state-changed`.** Both the orchestrator's `onStateChange` listener (registered by `createLocalUiServer.start`) and the route handler explicitly published the same event, so each manual stop produced two `node-state-changed` events on the SSE stream. The nodes-route test didn't catch this because it never registered the orchestrator-listener path, so only the route's explicit publish fired and the test was satisfied with a count of 1.
   - Removed the explicit publish from `routes/nodes.ts`. The orchestrator listener is now the single publication point (it also covers `createContainer` and unexpected child-exit transitions, which the route version never did).
   - Dropped `events: EventBus` from `NodesRoutesOptions` (no longer needed) and the `index.ts` call site.
   - Updated `nodes-route.test.ts` to mirror production by wiring `orchestrator.onStateChange → bus.publish`, and renamed the test to "publishes exactly one event via the listener" so it now acts as a regression guard.

**Minor — known weakness, not blocking**

2. **Settings propagation is not atomic.** `PUT /api/settings { upnpEnabled: false }` calls `nat.putSettings` *then* `settingsStore.update`. If the disk write fails after the NAT service has accepted the toggle, `nat.json` and `host.config.json` diverge. Same applies to `updates.*` propagating to `UpdateService.putSettings`. Acceptable: the divergence is rare (disk write failure on a fresh, validated patch), self-healing on next restart (the installer's `upnpEnabled` is only used to seed `nat.json` on first run, after which `nat.json` is authoritative), and the alternative — two-phase write — adds significant complexity. Documented as a known weakness in this review; not worth a follow-up ticket.

3. **`status.ts`'s `readPackageVersion()` walks `dist/server/routes` → `../../../package.json`.** The primary candidate is correct for both src (vitest) and dist. The second candidate (`'..', '..', 'package.json'`) resolves to a non-existent path in both — dead fallback. Harmless; left as-is to avoid bikeshedding.

4. **Orchestrator `child.once('exit')` emits state but does not persist.** Pre-existing — the original code also didn't persist on exit. The on-disk state is reconciled at next startup via `listDeadHandles()`. Out of scope for this review.

5. **Flaky pre-existing test**: `src/__tests__/orchestrator.test.ts` › `HostProcessOrchestrator.getStats` › "returns plausible numbers with zero network counters". Standalone wall-clock ~4.2 s, default Vitest timeout 5 s. Under the full-suite parallel load it occasionally times out (observed once during this review). Re-ran in isolation and it passes. Not introduced by this ticket. A future maintenance ticket could either raise the per-test timeout or replace `pidusage` with a faster stub in this test.

**Major — filed as follow-up tickets**

None. All major risks were already openly documented as "honest gaps" by the implementer and are tracked by named follow-up tickets:

- `/api/nodes/:id/{start,restart}` returning 501 is gated on a future "spawn cadre nodes from saved trust-circle membership" ticket.
- `cadre-host start` wiring `TrustCircleService` / `NatService` with `missingCadreNodeStub` / `missingNatNodeStub` is gated on the inline libp2p `CadreNode` ticket — calling out to libp2p (issuing/redeeming/resolving invite addresses) surfaces a 500 today. Listing the trust circle works.
- `cadre-host install` end-to-end smoke on Windows requires `nssm.exe` on PATH, which the sandbox doesn't have. The installer tests cover the `HostConfigFile` v1→v2 migration and individual installer steps; a Linux/macOS reviewer running the full `cadre-host install` flow is the real proof. Not introduced by this ticket — pre-existing posture for the package.
- SSE is hand-rolled (~50 LOC vs adding `@fastify/sse-v2`); the static mount is hand-rolled (no range / ETag / compression). Both are documented as deliberate scope choices in the implement summary; either could be swapped without breaking the bus contract or API surface.
- Update observer is poll-based (60 s `setInterval`) rather than listener-driven; an update appearing-and-disappearing within the 60 s window is silently missed. Deliberate scope cap — replacing it requires adding a listener API to `UpdateService`.
- No round-trip test for the `trust-circle-changed` event kind `'redeemed'`. The route adapter only publishes `'invited'` and `'revoked'`; the recipient redemption today happens over libp2p, not HTTP. A future ticket should publish `redeemed` from wherever the cadre node calls `service.redeemInvite(...)` — but that publication point doesn't exist until the inline-libp2p-node ticket lands.

### Open design questions — resolved

- **PUT'ing `uiPort` returns 400 vs 200-with-restart-required-flag**: kept 400 (matches the ticket's original spec). The SPA can show a read-only view by reading the value via GET.
- **SSE origin check**: the on-request origin guard runs before the SSE handler, so non-loopback origins never reach it. Sufficient — no upgrade-time check needed because SSE is plain HTTP.
- **`EventBus` exported publicly**: kept as a public export from `@serfab/cadre-host` so future inline subsystems (e.g. cadre-node) can publish events without going through HTTP.
