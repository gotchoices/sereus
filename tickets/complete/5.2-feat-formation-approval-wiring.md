# Complete: approval hook wired into the invite-redemption path

## What shipped

An invitation may carry a `ValidationUrl` — a web hook an outside approver operates, asked
whether one specific redemption may proceed. The client for that hook already existed but
nothing called it, so a `ValidationUrl` invitation could not be redeemed at all.

`ControlFormationUsageRecorder` now calls it, on both redemption paths:

- `recordUsage` — consent against an already-existing host strand.
- `provisionAndRecord` — the unbound path that mints a strand and records consent atomically.

Each reads the invite to learn its `ValidationUrl`, and when one is present mints the
redemption nonce (`usageStampId`), posts the five signed fields to the hook, verifies the
returned signature over *this* redemption, checks the signing key is an enrolled
`ValidationKey`, and passes nonce + key + signature into the same write that inserts the
`FormationUsage` row. The recorder is the right home for this precisely because it performs the
write: the nonce that is signed and the nonce that is inserted are the same value by
construction.

`StrandFormationManager` maps the five `FormationApprovalError` categories to distinct
joiner-visible rejection reasons (`APPROVAL_REJECTION_REASONS`) and caps disclosures at 8 KiB
before the hook is contacted.

## Review findings

### Checked and found clean

- **Digest field order.** `formationVouchMessage` (`control-database.ts`) matches the schema's
  `'vouch'` digest in `FormationUsage.Authorized` (`schemas/control.qsql`): `Token,
  UsageStampId, StrandId, PeerId, Disclosure` — same order, same arity.
- **Nonce round-trip.** `mintUsageStampId()` → signed → passed as `usageStampId` into
  `redeemInvitation` / `recordFormationUsage`, both of which use
  `usageStampId ?? generateStampId(...)`. The value signed is the value inserted; asserted
  against a real database in `strand-formation-consent.spec.ts` case (h).
- **Enrollment pre-check parity.** `queryValidationKeyStampId` reads the live `ValidationKey`
  table — the same table the database CHECK verifies against — so the local pre-check and the
  authority agree on what "enrolled" means.
- **Approver resource hygiene.** `createHttpFormationApprover()` validates only `timeoutMs` at
  construction and resolves `fetch` lazily per request, so building a recorder in a runtime
  without `fetch` does not throw. Abort timer cleared in `finally`; response body released on
  every reject path. No leak.
- **Outbound-request surface (SSRF) — considered, deliberately not filed.** The recorder now
  makes an outbound POST to a URL read from a replicated table. Not a defect:
  `FormationInvite.ValidationUrl` is covered by the owner signature (`insertFormationInvite`
  signs it as field 5), so the URL is the party operator's own choice rather than
  attacker-supplied, and the hook's response is never echoed back to the joiner.
- **Fail-safety when the write loses.** Every failure path — approval error, PK collision,
  deferred-CHECK rollback — writes no `FormationUsage` row, so the invitation is not consumed.
  Case (j) asserts this across all five failure categories.

### Found and fixed in this pass (minor)

- **Dead `validationUrl` on `ResolvedHostStrand`.** The implement stage added it to the
  `unbound` and `bound` variants "so the manager can see approval is required without a second
  invite read". Neither held: nothing read the field, and the recorder does its own invite read
  on both write paths anyway. Threading it through a caller would also move the choice of
  *which hook to trust* outside the component that performs the write. Removed from the type,
  from both `resolveStrand` returns, from the manager's no-recorder fallback, and from three
  `toEqual` expectations in `control-formation-invite.spec.ts`.
- **Factually wrong `NOTE:` about spent approvals.** The comment at
  `strand-formation-manager.ts`'s catch-all claimed an approval obtained before a failed write
  is spent "because the `unique` UsageStampId column bars re-presenting it" — self-contradictory
  (a nonce that was never inserted leaves no row to collide with) and contrary to both
  `redeemInvitation`'s doc and the schema's stated reason for using a free nonce instead of the
  use number. Rewritten to say the approval is discarded *because this path does not retry*,
  pointing at the new ticket below.
- **Docs described the pre-wiring world.** The implement handoff claimed no doc work; four
  places were false. Fixed: `docs/api.md` lost its "Not yet contacted automatically"
  blockquote (replaced with one sentence naming the caller), gained `'unenrolled'` in the
  `FormationApprovalError.failure` union, gained an `unenrolled` row in the hook-answer table
  plus a new table mapping all five categories to the rejection reason a joiner actually sees,
  and now documents the 8 KiB disclosure cap for hook authors sizing a review UI.
  `docs/architecture.md` present-tenses "once approval is wired" and names the recorder as the
  component that calls the approval client. `docs/STATUS.md`'s gap item is rewritten: redemption
  is wired and unit-tested; what remains open is approver-key enrollment
  (`feat-validation-key-enrollment`, in `implement/`), so the item stays unchecked — for that
  reason, stated.
- **Untested failure category.** Case (j) covered four of five categories; `misconfigured` was
  unexercised, so a typo in `APPROVAL_REJECTION_REASONS.misconfigured` would ship green. Added a
  fifth scenario.

### Filed as a ticket (major)

- `tickets/backlog/debt-formation-approval-retry-lost-race.md` — the schema and
  `redeemInvitation` were built so the loser of a `(Token, UseNumber)` race can re-present the
  **same** approval under a new use number, avoiding a second approval. Nothing wires it:
  `provisionAsResponder`'s catch-all discards the approval and returns
  `Formation conflict, retry`, so the joiner restarts formation and the hook is asked again —
  exactly the second review the free-nonce design set out to avoid. A real capability gap
  (wrong every time the race happens), not a conditional one.

### Parked as tripwires (comments, not tickets)

- **Approval skipped when the invite row is absent.** `recordUsage` / `provisionAndRecord`
  compute `invite?.validationUrl ?? null`, so an invite that vanished between `resolveStrand`
  and the write reads as "no approval required". Safe only because the database's `Authorized`
  CHECK demands a matching `FormationInvite` and rolls the write back regardless. `NOTE:` at
  the `?? null` site in `control-formation-recorder.ts` (one comment covers both callers).
- **Disclosure cap lives only in the manager.**
  `StrandSolicitationService.recordFormationComplete` reaches `recordUsage` without passing
  through `provisionAsResponder`, so its `disclosure` is uncapped. Harmless now (its three
  callers are integration-test mocks defaulting to `''`) but it is a public service method.
  `NOTE:` on that method in `strand-solicitation.ts`.

### Known gaps carried forward (declared, not defects of this pass)

- The HTTP approver is never exercised against a real server — all coverage injects a fake.
  Already tracked as `tickets/backlog/debt-formation-approval-real-fetch-coverage.md`.
- Integration suites remain typecheck-only; they stand up real networking and exceed the agent
  idle budget.
- The PK-collision race is reasoned about and its failure handling tested, but not forced
  concurrently in a test.
- End-to-end redemption of a `ValidationUrl` invitation still cannot happen until an operator
  can enroll an approver key (`feat-validation-key-enrollment`).
