# A joining machine cannot write before its first sync

## What shipped

A non-founder strand launch comes up `'syncing'` with `StrandInstance.database` withheld, and re-probes every 500 ms until the probe passes: the strand's `Strand.Header` row is readable AND a `select count(1)` of every table the sApp declared in `App` settles. Then the database is published, the status flips to `'active'`, `CadreNode` emits `strand:writable`, and every `whenStrandWritable` waiter resolves. `CadreNode.addStrand` waits for that by default (30 s, `strandFirstSync.timeoutMs`), rejecting retryably with `StrandAwaitingFirstSyncError` and leaving the launch up. Founders, and machines whose store already holds the strand's data (restart, hibernation resume), pass the probe on the first try and are never gated. A founder request against a gated instance runs the bootstrap through the gate and opens it. The hibernation cycle stops the probe on quiesce and rebuilds it on resume; a waiter survives the cycle.

The implement stage's summary of the design, the reference-app changes, and why so many tests had to found explicitly stands as written there (commit `0fe8a79`); the review changes are below.

## Review findings

### Read first, with fresh eyes

The full implement diff (48 files), then every source file it touched and the ones it should have: the hibernation manager (idle transition and activity re-arm), the watcher's auto-launch path, the membership reconciler / revocation enforcer lazy reads, the CLI health and status code, the provider's copy of the health payload, the strand-database bootstrap path, the docs, and the reference apps. Then the ticket's handoff.

### Defects found and fixed inline (minor)

- **`strand:writable` was skipped after the idle flip.** The hibernation manager relabels a still-gated joiner `'idle'` after `idleTimeout` (5 min at the interactive hint) since nothing records activity on it, and `publishDatabase` announced only when the status was exactly `'syncing'`. A host that came back after that window published the database silently: the strand stayed `'idle'`, no event, and the pending hibernate timer would then quiesce a strand the app had just started using. Now any publish after bring-up (status not `'starting'`) flips to `'active'` and announces, and `CadreNode.handleStrandWritable` records hibernation activity so the idle timer re-arms. Unit test added ("the Header arriving after the hibernation idle timer flipped the label still opens"). The `isAwaitingFirstSync` NOTE was reworded to match.
- **The Header alone was not the sync (major in effect, contained in size).** The regression scenario's device-shape case (joiner writes participant + message the instant `addStrand` resolves) passed 1 run in 4 under the Header-only probe: the Header is one collection and reaches the joiner ahead of the founder's app-table collections, so a write to a table whose collection had not been fetched still forked (two runs timed out on convergence, the pre-gate shape). The probe now also reads every `App` table once, after the Header is held, before publishing; a throwing read is "not yet", an empty table is a settled read, and no table is read before the Header (a peerless joiner pays no failing network reads). Unit tests cover the table enumeration, the stop-at-first-throw, the no-Header short-circuit, and the gate staying closed until a table's read settles. Nine mocked-manager doubles gained a `schemaManager` stub. This did NOT make the device shape pass (see the residual below); it changed the failure from a silent fork to a loud constraint error, which is the better failure, and it closes the never-fetched-collection hole by construction for any table the founder has written.
- **CLI health and status counted no `syncing` strands.** `/status`, `/metrics` (`cadre_strands_syncing` gauge) and `cadre status` now count them, through one shared `countStrandStatuses`. The provider's copy of the payload is a documented subset and needed no change.
- Doc wording in `CadreNodeConfig.strandFirstSync` and the gate module now describes the two-part probe. `docs/strands.md` and `docs/architecture.md` updated for the invariant, the idle-flip announcement, and the two residuals.

### Verified by reading, no change needed

- The watcher's auto-launch goes through `launchStrand`, not `addStrand`, so it never blocks 30 s per gated strand. `foundStrand` forwards `awaitFirstSync` and a founding launch is never gated.
- `releaseRuntime` closes a gated database through the gate and a published one through the instance, never both; a probe in flight when the gate stops completes and is ignored; a failed `initialize()` rolls back through the gate.
- `stopAll` goes through `stopStrand`, which rejects waiters. `whenWritable` on a hibernating instance waits (documented; the wait spans a resume).
- The regression scenario's block-id assertion (`default/` prefix, `optimystic/schema` catalog id) still holds under optimystic's new `tree://default/<schema>/<table>` keying; test 3 passed.
- Table-name casing across devices (raised by the optimystic session): every strand table is declared from one source, the embedded strand schema and the signed sApp schema string, so two devices cannot disagree. No action.

### Residual, parked as a blocked ticket (major, upstream)

The device-shape case remains intermittent: 1 pass in 5 with the extended gate, every failure `CHECK constraint failed: _fk_Message_ParticipantId` on the joiner's message insert, i.e. the joiner cannot read the participant row it committed in the previous statement, on a collection it had already fetched. The optimystic session reviewed the measurement and is filing it on its board as its own read-your-own-write fix (explicitly not the cohort-assembly chain: a two-party strand resolves every collection to one cohort). `tickets/blocked/device-shape-join-write-blocked-on-optimystic-read-after-write.md` holds the re-verification steps. The test stays in the suite unchanged; skipping or loosening it would hide the loss.

### Pre-existing failures reported (not this ticket's)

`tickets/.pre-existing-error.md`: 11 cadre-core tests in 7 files plus 2 integration scenarios, all warm-restart or hydration shapes (`ALTER TABLE CadreControl.CadrePeer ALTER COLUMN` refused by the optimystic module on restart; a local-transactor store reading back empty through the network transactor; a membership-hydration CHECK rejecting `context.ManagerKey`). They arrived with the optimystic rebuild at `6302f2e8` that landed mid-review, are outside every file this ticket touched, and the optimystic session has taken them as its highest-priority fix.

### Tripwires recorded (no ticket)

- `strand-first-sync-gate.ts` module `NOTE:` (unchanged): the schema catalog is written by every launch alone before any peer contact; safe only while the catalog is byte-identical across machines. The optimystic session confirmed its 0.5 keys derive from schema and table names alone.
- `strand-instance-manager.ts` `isAwaitingFirstSync` `NOTE:` (reworded): the idle timer relabels a gated joiner `'idle'`; only the label changes, every decision uses the predicate and the publish announces regardless.
- Probe cost: one Header read plus one count read per `App` table per 500 ms per gated strand, only after the Header is held. Not measured under many gated strands or wide schemas; if it ever shows up, read the tables once and remember which settled instead of re-reading all of them each probe.
