# Formation approval must come from an enrolled validation key

## What the bug was

A party mints an invitation (`CadreControl.FormationInvite`). If that invitation carries a
`ValidationUrl`, someone is supposed to look at the joiner's disclosure and sign off before the
invitation may be redeemed. The party keeps the list of keys allowed to give that sign-off in
`CadreControl.ValidationKey`.

Redemption writes a `CadreControl.FormationUsage` row, gated by its `Authorized` CHECK. That
CHECK verified the sign-off signature against `context.ValidationKey` — a plain parameter on the
redeeming insert. A redeemer generated a throwaway keypair, signed its own disclosure with it,
passed key + signature, and the gate opened. `ValidationKey` had no consumer anywhere in the
schema.

## What shipped

`FormationUsage.Authorized`'s validation branch, in both hand-maintained copies of the schema
(`schemas/control.qsql`, `packages/cadre-core/src/control-schema.ts`, kept byte-identical by
`control-schema-drift.spec.ts`):

```sql
and (FI.ValidationUrl is null or exists (
    select 1 from ValidationKey VK
        where VK.Key = context.ValidationKey
            and verify(digest('CadreControl.FormationUsage', 'vouch', new.Token, new.Disclosure),
                       context.ValidationSignature, VK.Key, 'ed25519')))
```

`context.ValidationKey` stays in the context tuple but is now only a *selector* — it picks which
enrolled row is being claimed. The signature is verified against the **stored** `VK.Key`, so a
mismatched (name, signature) pair cannot pass in either direction.

Alongside: constraint comments stating stored-vs-supplied key and the non-retroactive removal
semantics; a `NOTE:` on `ValidationKey.NotRevoked` recording that the table now has a consumer;
the `ValidationKey` row of the control-table list in `docs/architecture.md`; and seven tests in
`packages/cadre-core/test/control-formation-invite.spec.ts` under
`FormationUsage.Authorized validation-key branch` (six from implement, one added in review).

Each test records against a pre-existing owner-signed strand via `recordFormationUsage` rather
than `redeemInvitation`, so `StrandExists` and `Monotonic` are already satisfied and `Authorized`
is the only constraint that can reject — which makes `expectConstraintFailure(..., 'Authorized')`
a genuine single-rejector assertion. Coverage: rogue unenrolled key with its own valid signature
(rejected — this is the bug, and the only case that distinguishes pre-fix from post-fix); no
sign-off at all (rejected); enrolled key signs the `'vouch'` digest (accepted); enrolled key named
with a foreign signature (rejected); enrolled key's signature under an unenrolled name (rejected);
invite with no `ValidationUrl` and no sign-off (accepted, unchanged); enroll → approve → remove →
approve again (second approval rejected, first approval's row untouched).

## Review findings

**Checked:** the implement diff read before the handoff summary; the `Authorized` CHECK against
every way a sign-off can be presented (null selector, wrong pairing, cross-token, cross-rule
digest reuse); both schema copies for drift; `ValidationKey`'s enrollment/removal rules for
interaction with the new consumer; every repo reference to `ValidationKey` /
`validationKey` in `packages/*/src`, `packages/*/test` and `docs/` for staleness; test-suite
design for single-rejector honesty; source hygiene of the touched files.

**Fixed in this pass (minor):**

- *Missing removal test.* The implementer flagged the enroll-then-remove-then-redeem case as
  untested because the `exists` makes it near-tautological. It is also the half of the constraint
  comment that makes a security claim ("removal narrows who may approve future redemptions"), so
  it is now pinned: a second, self-contained approver key is enrolled, approves a redemption,
  is removed via `deleteValidationKey`, and is then refused on a fresh invite while its earlier
  `FormationUsage` row stays put. Written to be order-independent so it does not disturb the
  block's shared approver key.
- *Bloated doc cell.* The `ValidationKey` row in `docs/architecture.md` had grown to five
  sentences, restating rationale that lives in the constraint comment, while its sibling rows
  defer. Trimmed to the facts a reader of the table needs, with a pointer to the schema comments.

**Filed as a new ticket (major):** `backlog/debt-formation-approval-signature-replayable`. The
approver's sign-off digest binds only `(Token, Disclosure)` — not `UseNumber`, not the strand,
not the joining peer, and `Disclosure` is supplied by the redeemer. So one approval authorizes
*any* redemption of that invitation repeating the same disclosure bytes: a second holder of a
multi-use invite copies an approved joiner's disclosure and signature verbatim and gets in. This
is not a regression — the digest shape predates the fix, and the source ticket scoped
`context.PeerId` / `context.PeerSignature` out — but it materially limits what the now-real gate
buys, and it was not named in the handoff. Kept as a ticket rather than a tripwire because it is
a definite defect the moment the dormant path runs; `debt-` rather than `bug-` because nothing
calls the `ValidationUrl` hook today, so no approvals exist to capture. A `KNOWN GAP:` comment on
the constraint in both schema copies points at the ticket, since anyone reading the CHECK will
otherwise over-trust it.

**Tripwire (carried from implement, verified and left as-is):** `ValidationKey` now has a
consumer, so the `Revocation` convergence gap reaches it — on a node that has not yet seen the
tombstone, a replayed enrollment re-seats the key and it can approve redemptions there until the
`Revocation` row arrives. Same class as the notes already on `Strand.StampId` and `OwnerKey`'s
`MinOneOwner`, and there is no per-request *read* surface to filter (the gate is a write-time
CHECK), so there is nothing to do today. Parked as a `NOTE:` on `ValidationKey.NotRevoked` in
both schema copies.

**Checked and clean, explicitly:**

- *Null / absent selector.* `context.ValidationKey` is nullable; `VK.Key = null` matches no row,
  so an omitted sign-off is rejected rather than silently passing. Covered by test.
- *Cross-domain signature reuse.* The digest is tagged `('CadreControl.FormationUsage', 'vouch')`,
  distinct from every other rule's tuple, so an approver signature cannot be laundered between
  rules — `control-authorization-domain-separation.spec.ts` still passes.
- *Drift.* The two schema copies match byte-for-byte, including all comments added here.
- *Docs.* Every doc mentioning validation keys was re-read: `docs/architecture.md` (updated),
  `docs/api.md` line 62 (the `validateStrandFormation` signature — unchanged and still accurate,
  since the hook itself is untouched), `docs/STATUS.md` line 171 (a bare table inventory). No
  other doc describes the redemption gate.
- *Untouched consumers.* `reference-app-web`'s diagnostics only counts `ValidationKey` rows; the
  strand-solicitation `FormationSigner` path still produces a `(validationKey, validationSignature)`
  pair and is still unwired. Neither needed a change here.
- *Cost.* The new subquery is a primary-key lookup on a table holding a handful of rows, and runs
  one `verify` — no measurable write-path cost, nothing to note.
- *Source hygiene.* Both schema files stay ~460 lines with the repo's existing dense-constraint-
  comment style; the added comments earn their length (each states a security property, not a
  restatement of the SQL). No new functions, so no decomposition concerns.

## Known gaps left open, deliberately

- **Only the rogue-key test distinguishes pre-fix from post-fix.** The two mismatched-pair cases
  were already rejected by the old CHECK. They pin the new pairing semantics rather than
  regressing the original hole. Accepted as adequate — the hole itself is pinned.
- **No multi-node / replication test.** The CHECK is evaluated locally on each node; nothing
  exercises two nodes disagreeing about `ValidationKey`'s contents. Same shape as the convergence
  tripwire above.
- **The web hook is still unwired end-to-end.** `ControlFormationUsageRecorder.recordUsage` /
  `provisionAndRecord` never pass a `validationKey` / `validationSignature` pair, and
  `StrandSolicitationService.validateStrandFormation` has no caller outside its own unit test, so
  a `ValidationUrl` invite still cannot be redeemed through the real formation protocol — before
  or after this fix. Out of scope by design; tracked as
  `backlog/feat-formation-validation-webhook-unwired`. The hole closed here is in the control
  database's **write API**, which is the actual security boundary: the control tables are
  replicated and their CHECKs are what stop a hostile peer writing directly.
- **`context.PeerId` / `context.PeerSignature` on the same insert remain declared and unverified**,
  so an invitation token is still a bearer credential. Scoped out by the source ticket; it is also
  the first option listed in `debt-formation-approval-signature-replayable`.
