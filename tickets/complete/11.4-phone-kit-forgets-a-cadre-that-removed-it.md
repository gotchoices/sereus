# The phone kit acts on `cadre:removed`

## What was built

The phone kit (`@serfab/cadre-rn/phone-node`) now answers cadre-core's `cadre:removed` event (`ticket(implement): phone-kit-forgets-a-cadre-that-removed-it`).

- **New status** `{ state: 'removed'; partyId; removal: CadreRemoval; formerPartyId? }` on `PhoneNodeStatus`. `node` and `options` read null. `start` and `joinCadre` from `removed` behave as from `stopped`. `createPhoneNode` replaces a runtime in `removed`, as it replaces a stopped one.
- **`watchRemoval(node)`** is attached in `bringUp`, before `node.start()`, for every node a start, restart or join builds. It is never detached, so a report raised while a stop is in progress is still answered.
- **`forgetRemovedParty(removal)`** is queued through `trackStop` (shared with `stop()`), so `loadSavedStart()` and the app-link slots wait for it. In order:
  1. If another party's node is running (a join or restart moved the app before this turn), it deletes only the removed party's storage and drops it from `runningOptions.formerPartyId`.
  2. Otherwise it shuts the node down, then rewrites the saved start through `startAfterRemoval` (`options.ts`). The new start names `formerPartyId` with `origin: 'founded'` and `autoStart: false`. If there is no former party, the saved start is deleted.
  3. It deletes the party's local storage with the dissolve's marked `removeParty`, after finishing any older marker.
  4. It sets status `removed`.
  
  A failure rewriting the saved start leaves the storage in place and sets status `failed`. The function never rejects.
- **Departure from the plan, kept:** the saved start is rewritten *before* the deletion. If the order were reversed, a deletion that failed partway would leave a saved start with `autoStart: true` naming the removed party. A wake would then rebuild that party on empty storage.
- **Departure from the plan, kept:** there is no `removedFromCadre()` check after start. The watcher is attached before `node.start()`, and cadre-core can only report a removal after an earlier refresh saw the node's own row live, so the event cannot fire before the watcher exists.
- **Docs:** `packages/cadre-rn/README.md` has a "Removed from the cadre" section, the status in the member table, and a `loadSavedStart` note. `docs/architecture.md` → "An app joins an existing cadre" has a "Removed from A" paragraph.
- **Test:** `node.spec.ts` → "createPhoneNode — removed from its party by an owner". It emits `cadre:removed` on the real node, then checks the status, that the node stopped, the rewritten saved start, the deleted anchor and control database, and that "go back to your own cadre" reaches `running`.

## Review findings

**Checked:** read the implement diff first, then `dissolve.ts` (`removeParty`, `finishRemoving`, `dropFromSavedStart`), cadre-core's `noteOwnRemoval` and `stop()` (`packages/cadre-core/src/cadre-node.ts`), the kit's transition queue (`inTurn`, `trackStop`, `trackStart`, `shutDown`), and the callers that start the node: `phoneNodeLifecycle` (`packages/cadre-rn/src/lifecycle/index.ts`), the reference app's `push-wake-native.ts` and `use-cadre.ts`. Ran `yarn workspace @serfab/cadre-rn build`, `typecheck` and `test` (17 files, 184 passed), and `yarn lint`. All clean.

**Correctness and interactions (read, not new tests):**
- Removal reported during a stop: the removal is queued behind the stop, `this.stopping` points at the later promise, and `loadSavedStart` waits for it. Correct.
- Reported between `node.start()` and `markRunning`: the start finishes and saves `autoStart: true`, then the removal shuts the node down and rewrites the saved start. Correct. A caller awaiting that start gets a node that stops right after, which is acceptable.
- Reported while a restart or join moves the node to another party: branch 1 runs. The saved start's `formerPartyId` is dropped by `dropFromSavedStart`, and `runningOptions` is dropped in memory. The app gets no status for this, which is acceptable because it is already in another party. A deferred strand move from the removed party is deleted with that party, as the handoff says. This is a judgement call and was accepted.
- Status reads `removed` while no node runs and the saved start names a different party: practically unreachable. It needs a stale node's report after the app has left for a party whose start then failed or was stopped, and every transition that could get there is queued before the removal. Left as is.
- If `finishMarkedRemoval` fails on an older marker, the new party's removal does not run and nothing marks it, so its data stays on disk. This only happens after a fault and costs only disk space. No action.

**Found and fixed in this pass:**
- `dissolve.ts`: the module doc and `removeParty`'s doc still said a removal runs only after the dissolve check. Both now name the owner-removal caller too, and say that the decision to remove comes before the marker.

The kit does not refuse those options.
