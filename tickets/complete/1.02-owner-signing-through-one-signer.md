# All owner signing goes through one signer

## What was built

Implemented in `ticket(implement): owner-signing-through-one-signer`.

Before this, a node signed owner writes from two sources: `SeedBootstrapService` used the private key passed to `initializeSeedBootstrap`, and `CadreNode`'s own writes (strands, party keys, formation invitations, validation keys, joined-strand rows, join requests and outcomes, strand-move adoption) used the node's identity key. A node given any other owner key wrote strands and joins the schema refused. Now there is one source:

- **`CadreNode.useOwnerSigner(signer)`** wires the node's one `OwnerSigner`: it refuses on a `claim` node, anchors the key as `genesis`, and builds the owner-capable seed service. `initializeSeedBootstrap(priv)` is `useOwnerSigner(softwareOwnerSigner(priv))`. `getOwnerSigner()` reads it back.
- **`SeedBootstrapServiceConfig.ownerSigner`** replaces `ownerPrivateKey` / `ownerPublicKey`. Every owner-signed service method takes an optional trailing `sign?: OwnerSign`: given one it signs inside the caller's approval, otherwise it opens its own. `addDrone` / `addPhoneWithRelay` put the vouch and the seed under one approval.
- **`ControlDatabase`** writers take `ControlSign = (message) => string | Promise<string>` and await it. The write-lock / retry `NOTE:` sits on that alias.
- **One `approve` per public action** (`unpublishStrand`, `enrollValidationKey`, `removeValidationKey`, `dismissPendingJoin`, `removeMachine` with its re-vouches, `claimNode`, `requestJoin`'s request row, `adoptStrandBundle`'s whole bundle, `publishStrand` with a closed strand's party-key mint). `publishStrand`, `ensureStrandPartyKey` and `publishFormationInvite` take a trailing optional `sign` so a composing caller can share its approval.
- **Background writers** (joined-strand ledger, pending-join runner, the drains, the ledger marker, the self-row and device-token writes, the launch-time party-key mint) open one approval per write.
- **`isOwner()`** / `planMachineRemoval`'s `selfOwnerKey`: a signer is wired and its key is a live `OwnerKey`. **`wireOwnKeyIfOwner(signer?)`** picks the argument, then the wired signer, then a software signer over the identity key (the interim path for invitation-granted owners), and throws if a different key is already wired.
- **cadre-cli** `withConnectedNode` calls `node.wireOwnKeyIfOwner()` before every one-shot action.
- **Docs**: `docs/architecture.md` (Owner Keys status note, The owner signer and its "Composing an action" paragraph, invitation-granted owners, the Enrollment Flow paragraph, Implementation Status, the `cadre validation-key` bullet) and the `types.ts` doc comments.

Tests: new `cadre-node-owner-signer.spec.ts`, where one node's owner key is a fresh key rather than its identity key. It covers every owner write landing under that key, and checks that a multi-row action asks for one approval. Fixtures and specs that built the seed service from a key, or relied on the identity default, were adjusted. The full list is in the implement commit.

## Review findings

Read the full implement diff first: cadre-node, seed-bootstrap, control-database, strand-move, owner-signer, the CLI session, the docs, and the new and changed specs.

**Fixed in this pass**

- **Signed phone seed broken by a relay address added after signing** (correctness; the bug predates this ticket, in a function the diff restructured). `SeedBootstrapService.addPhoneWithRelay` pushed the node's relay address into its own seed entry *after* `createSeed` signed it. The seed signature covers every peer address (`seedDigest` over `{ partyId, peers }`), so whenever the node held a relay address that its own `CadrePeer` row lacked, the phone got a seed whose signature failed `validateSeedSignature` and refused it. Fix: the relay address is now read first and added before signing, through a private `mintSeed(sign, selfRelayAddr)` that `createSeed` also uses, plus a small `addSelfRelayAddr` helper. Regression test: `seed-bootstrap.spec.ts` → "addPhoneWithRelay — the relay address is signed". I confirmed by a temporary edit that the test fails under the old order (`expected false to be true`) and passes with the fix.
- **Duplicate approval helper** (DRY). `CadreNode.withOwnerApproval` and `SeedBootstrapService.withOwnerSign` had the same "use the caller's `sign`, else open one approval" logic. It is now one exported function, `withinOwnerApproval` in `owner-signer.ts`. The three CadreNode call sites call it directly and the private method is gone; the service's `withOwnerSign` is a one-line delegate that supplies its signer and party id. It is not added to `index.ts`, because nothing outside the package composes approvals yet.

**Checked, no change**

- *No owner path left on the identity key.* I grepped every `getSelfSigningKey` / `getIdentityOwnerKey` / crypto `sign` use in package sources. The remaining identity-key uses are the node's own address record, its device-token `Sig`, the invitation redemption, and the `wireOwnKeyIfOwner` identity default, none of which is an owner signature. Embedders (cadre-cli `start --owner`, the RN and web kits, the harness) still hand in the identity key on purpose; tickets 1.06 to 1.10 change that.
- *Async signing inside write locks and retries.* Writers that read their stamp inside `lockedWithRetry` now await the signer while holding the lock. `reissueRevocations` still signs before the lock, so a retry re-presents the same signatures. The tripwire `NOTE:` on `ControlSign` covers prompting signers. No change.
- *Founder detection now waits for the signer to be wired.* `isSelfFoundedRow` compares against the wired signer's key. On restart, a watcher launch that runs before the embedder wires the signer brings the node's own strand up as a joiner, and it skips the party-key healing mint. The `NOTE:` at `isSelfFoundedRow` records this, and `implement/1.03-owner-key-label-and-founder-machine` replaces the comparison with a `FounderPeerId` match, which is available at start. No new ticket.
- *CLI wires the owner key for every one-shot command.* That costs one local `OwnerKey` read per command, including read-only ones, and only one call site (`subcommand.ts`) exists. It is accepted for now; `implement/1.06-cli-owner-key-separate-from-node-identity` reworks this path. On a claimed node the identity key is never an `OwnerKey`, so the `claim` refusal in `useOwnerSigner` cannot fire from here.
- *Approvals held across the network.* `claimNode` holds one approval across seed delivery, and `adoptStrandBundle` holds one across its per-strand peer seating. The ticket asked for this; how long a hardware key's presence lasts is `backlog/feat-owner-key-on-a-hardware-key`'s concern.
- *Error paths.* With no signer, `requireOwnerSigner` throws before any DB read, keeping the existing order (signer first, then control DB). `removeMachine` and `claimNode` check `service.ownerSigner` before opening an approval. A declined approval propagates as `OwnerSigningDeclinedError` from `approve`.
- *Type safety.* There is no `any`. Making the `ControlSign` callback async-capable still accepts the synchronous test lambdas.
- *Resource cleanup.* No new handles. `useOwnerSigner` is still once per node because libp2p rejects a second seed handler; `wireOwnKeyIfOwner` refuses a different key by name.
- *Tests.* The new spec pins the two contracts the ticket names, each with real branching: the owner key differs from the identity key, and one approval covers a multi-row action. No cuts. `removeMachine`'s `signatures > 1` check is loose but adequate, because the approval count is the contract under test.
- *Docs.* I read every `docs/architecture.md` passage the diff touched, plus the ones that still describe the identity derivation; the Owner Keys status note says those stay current until tickets 1.06 to 1.10 land. There are no stale references to removed symbols (`requireOwnerSigningKey`, `enrolledOwnerSigningKey`, `signMessageWith`, the `ownerPrivateKey` seed config) in docs or package sources. The `addPhoneWithRelay` fix changes no documented behaviour.

**Tripwires**: none new. The existing ones at `ControlSign` (lock held across a prompting signer) and `isSelfFoundedRow` (founder detection depends on when the signer is wired) still apply.

**Tickets filed**: none. The one defect found was fixed inline, and the remaining items are owned by tickets already on the board (1.03, 1.06, `feat-owner-key-on-a-hardware-key`).
