# Removal cuts the network on a strand formed the ordinary way

Last ticket of the party-identity chain (`strand-party-member-key` → `strand-formation-membership-invite` → `strand-node-binds-member-peer` → this one). The enforcement code and a proof of it already existed. This ticket adds a proof that runs on rows **production** wrote, not rows the test registered by hand, and corrects the docs to match.

## What landed

- **`strand-party-removal-via-formation-e2e.integration.ts`**, a scenario file with two tests that needs no other scenario file. *Test 1*: two parties with two machines each. The joiner redeems a bound invitation over the real formation handshake, and the runtime seats two distinct `Strand.Member` rows and four `Strand.MemberPeer` bindings by itself. The file never calls `issueInvite`, `consumeInvite` or `registerMemberPeer`, and a grep confirms it. Revoking the joiner cuts both of its machines on both host machines. The remaining machines can still commit, while the removed party can neither read their write nor push one back (gotchoices/sereus#4). At the end, the removed party's own two machines refuse each other. *Test 2*: re-joining after removal. A fresh formation succeeds but the invitation is never spent, and re-admission only works when a remaining manager authors it.
- **Harness:** `ControlNodeOpts.membershipReconciliation` widened from `false` to `false | { pollIntervalMs }`, and `TopologyMachineSpec` forwards it. A scenario can now keep the membership reconciler fast while the revocation poll stays suspended.
- **Docs:** the "not yet proven end to end" gap in `docs/strands.md` is removed. New bullets cover a removed party's own machines refusing each other and the re-join dead end. The retired `feat-strand-party-identity` slug now points at its surviving tickets in `architecture.md`, `strand-contracts*.md` and `cluster-size.ts`.
- **Filed:** `backlog/bug-removed-party-cannot-redeem-its-way-back`. Arms added to `debt-hoist-strand-read-helpers-integration` and `feat-strand-member-allowlist-admission`.

### Major — test 2 names the wrong cause for its central negative claim (fixed inline; filed ticket's root cause corrected)

The test comment, the file header, `docs/strands.md` (three places), `docs/testing.md`, `feat-strand-member-allowlist-admission`, and the filed bug all said the re-invitation cannot be redeemed *because the membership write can't travel through the cut network*. **That is not what the test demonstrates.**

- **The code.** `StrandMembershipReconciler` latches a terminal stopped state on its `done` path (`ensureBinding` → `finish` → `stop`), and `start()` returns early on a stopped loop. Only a strand relaunch builds a new reconciler. `CadreNode.adoptFormationMembershipInvite` just stages the new invitation in an in-memory map and never re-arms anything. Nothing else redeems automatically: `StrandMemberRegistry` also calls `consumeInvite`, but it is an enrollment path the embedder constructs, not part of formation.
- **Measured, `repro: verified`.** I ran test 2 with `DEBUG=sereus:cadre:strand-membership-reconciler`. All three reconcilers (host[0], host[1], join[0]) logged `stopped (done)` by 21:54:54, before the removal. None of them logged a single line during the 8-second negative window. No pass ever tried the redemption, so the negative assertion passes because nothing ran.
- **Consequence beyond wording.** The filed ticket offered "clear the removed party's leftover device records first, then redeem normally" as a working recipe. On a live node that recipe does not work: clearing the records lifts the refusal but does not restart the stopped loop. `docs/strands.md` repeated the same recipe.
- **Architecture-first placement.** The class of defect is "the reconciler's finished state assumes membership only grows," and removal breaks that assumption. That problem sits at the same site as the filed bug, so I **corrected that ticket** instead of filing a new one. The stopped loop is now the first and root cause, with the fix shapes "re-arm on a new staged invitation" or "make `done` conditional on still being a member." The network refusal is now a second dead end that is real but never reached today. `cadre-node.ts` was added to its `files:`. The broken recipe is withdrawn, and the description and tradeoffs are rewritten to be accurate.
- **Test made honest (inline).** The negative-assertion comment now names both blockers and says which one the test pins. I added two assertions that tell the two causes apart. The second invitation is still staged (a) after the quiet window and (b) **after the strand is fully healed**, when a host write has already reached join[0]. A loop that was merely blocked by the network would have redeemed or burned it by then. Both assertions pass, which confirms the loop is stopped rather than blocked. If a fix re-arms the reconciler, the second assertion flips; its comment says to rewrite it to the new behaviour, not to delete it.
- **Production-site NOTEs (inline).** `strand-membership-reconciler.ts`: the self-revoked `finish` reason says "re-admission arrives via a fresh formation", which is aspirational. A NOTE there now says so and names the ticket. `cadre-node.ts` `adoptFormationMembershipInvite`: a NOTE that staging does nothing on a node whose reconciler has already finished. Both are comment-only changes.
