## What landed

**No product code changed, in implement or in review.** The cross-party relay path —
stranger-open formation over a circuit, the formation-carried strand address, the
closed-strand secret delivery, the joiner's seeded auto-dial through the relay — worked
end to end on the first run. What landed is one new scenario plus docs recording the
proven shape and the measured cost.

**`packages/integration-tests/src/scenarios/blind-relay-phone-to-phone-e2e.integration.ts`**
— one phased test. Two DIFFERENT parties, each a single `CadreNode` with
`listenAddrs: []` and `relayAddrs: [<relay>]`, sharing the existing dedicated ungated
relay fixture (`harness/dedicated-relay.ts`, config-parity with `ops/docker/libp2p-infra`;
fixture unchanged). Asserts, in order: the relay speaks no `/sereus/strand-addr/1.0.0`
(delegate admission can only be a no-op); A boots relay-only (`enableRelay: false` — a
phone relays for nobody) with every control addr `/p2p-circuit` and reservation state
`reserved`; A founds a CLOSED strand live BEFORE the invitation exists and its strand
node's configured-route reservation lands; the bound invitation round-trips encode →
decode with every bootstrap address a circuit addr naming A's control peer; B boots the
same way and `formStrand` succeeds — same `strandId`, `memberPrivateKey` EQUAL to the
founder's minted secret, every carried `strandAddrs` entry circuit-routed, naming A's
STRAND peer, live in A's announced set, never a control addr; the control link is
classified `relayed`/`circuit-relay` on BOTH ends and `connection.limits` is absent on
every relayed connection (the live assertion of the fixture's `applyDefaultLimit: false`
parity contract); B `addStrand`s the closed row and its strand node reaches A's from the
carried seed alone with no hand-dial anywhere in the file; relay reservations total 4
(2 control + 2 strand) — one slot per node per network, party boundaries change nothing;
the founder-bootstrap `Strand.Header` row becomes visible on B, then App rows replicate
BOTH ways including B→A; and a final sweep over all four nodes shows every connection to
a non-relay peer is relayed, so no assertion above could have been served by a direct
fallback.

**Docs** — `docs/strands.md` (SN–SN use case: proven end to end, measured slot cost, what
remains open), `docs/architecture.md` (Relay Integration: cross-party paragraph),
`docs/testing.md` (topology coverage map: new covered line, narrowed uncovered line).

## Review findings

Reviewed the implement diff (`fb15818`) fresh before reading the handoff, then the
scenario against its two siblings, the relay fixture, `summarizeConnectionPaths`,
`controlNodeConfig`, the strand-addr/delegate-announce path, and every doc section the
change touches or should have touched.

### Checked and clean

- **The assertions are load-bearing, not decorative.** Every relayed claim is classified
  through `summarizeConnectionPaths` rather than inferred from topology, and the final
  four-node sweep closes the "a direct fallback passed for relayed success" hole. The
  `strandAddrs` assertions compare against A's LIVE announced set sampled at assertion
  time, not a stale snapshot — the right shape, and the same one the sibling settled on.
- **Ordering hazards are handled.** `initializeStrandSolicitation` is wired before
  `createOpenInvitation` (a lazy init would build a recorder-less service and silently
  drop the gate's stranger carve-out), and the strand is founded before the bound
  invitation is published (the reply carries addresses and the secret only if the strand
  is live at redemption). Both are commented at the site with the reason.
- **The header's mechanism claims are accurate**, verified against source, not taken on
  faith: delegate-announce genuinely rides the same `STRAND_ADDR_PROTOCOL` RPC
  (`cadre-node.ts:970-978`), whose fan-out folds a per-peer failure to `[]`
  (`strand-addr-protocol.ts:324-327`), so protocol absence on the relay does make the
  announce half a no-op.
- **Exact reservation counts (1 → 2 → 3 → 4) are not a flake risk**: each is asserted only
  after something that proves the reservation already landed (fail-fast `relayAddrs` on
  `start()`, or a circuit addr present in `getMultiaddrs()`).
- **Resource cleanup** is the suite's established shape (`Promise.allSettled` on the nodes,
  then the relay, in `finally`) — 19 scenarios do the same; no leak introduced.
- **No product code, no harness code touched**, so nothing outside this scenario can
  regress from it. Test-only change, purely additive.
- **Flake probe**: ran the new scenario 5 further times this pass (4 solo + 1 in the mixed
  set), all green, in addition to the implementer's 3. Test body ~2 s.

### Fixed in this pass (minor)

- **`docs/architecture.md` "the machine count is not a party count" bullet was stale** —
  it still claimed "the only path that *discovers* a strand's peers seeds the mesh from

  only by hand". Both stopped being true when `formation-carries-strand-addrs` landed
  (that ticket updated the Strand-Address Resolution section but not this bullet), and
  this scenario is the flat counterexample: two strangers, zero hand-dials. Rewritten to
  name formation as the one automatic cross-party path, with its one-shot,
  never-refreshed limits, while keeping the bullet's actual point (cohort selection is
  still owner-blind; still no *discovery*).
- **`docs/architecture.md` Strand-Address Resolution cross-party bullet** named only
  `strand-formation-cross-party-seed` as the end-to-end proof; it now distinguishes that
  loopback proof from this one, where every carried address is `/p2p-circuit`-routed.
- **`docs/strands.md` SN–SN "Still open" understated what is unproven.** The paragraph
  opens "The use case itself is proven end to end" but the use case's own bullet list

  Now listed as open alongside two-relay and discovery/roaming, and the two-relay entry
  cites its new ticket.
- **`docs/testing.md`'s new uncovered line cited no ticket**, breaking the convention the

### Filed (major)

- **`backlog/feat-scenario-two-relay-circuit`** — the two-relay shape (each party reserved
  on a DIFFERENT relay) is untested, and it is the *ordinary* real-world case, not an
  exotic one: two strangers meeting through an invitation have no reason to have picked
  the same relay. The implement stage recorded it as out of scope in four places but filed
  nothing, leaving a coverage gap with no queue entry. Site-claim grep over
  `backlog/fix/plan/implement/review` found nothing open touching it. Filed as a scenario
  ticket rather than a bug: nothing is known to be broken, it is simply unmeasured — the
  ticket says explicitly that the predicted per-relay reservation count (2 and 2) is a
  prediction, and measuring it is part of the work.

### Filed as an arm on an existing ticket (major)

- **`backlog/debt-hoist-strand-read-helpers-integration`** already owns "scenario files
  each keep their own copy of the same helpers, and the copies drift". This scenario is
  the next instance, so it was appended as a second arm rather than filed fresh:
  `expectAllPathsRelayed` now exists in two relay scenarios and has ALREADY diverged — the
  new copy asserts `conn.limits === undefined` (the fixture's `applyDefaultLimit: false`
  parity contract) and the older one does not, so the same-party scenario would meet that
  regression as a mysterious replication timeout rather than by name. `readDataRows` is at
  five copies, `isCircuit`/`GATE` at two. Not deduplicated inline because every module
  under `src/harness/` deliberately avoids importing `vitest` and throws plain `Error`s
  instead (stated at `harness/control-trio.ts:37`); hoisting an `expect`-based helper needs
  that convention decided, which is the ticket's call, not a side effect of this review.

### Recorded as tripwires (conditional — deliberately not tickets)

- **The control-link relayed assertion samples the formation connection immediately after
  `formStrand` resolves**, assuming libp2p still holds it open. True today (8 consecutive
  green runs). `NOTE:` at the site in the scenario file says what to do if a future libp2p
  or cadre change closes formation connections eagerly: it goes flaky, not wrong, and the
  fix is to capture the classification while the stream is live.

### Considered and deliberately not filed

- **The delegate-admission no-op is proven indirectly** (protocol absence on the relay +
  both strand launches resolving) rather than by instrumenting `resolveCohortSeed`. The
  indirect proof is sound for the claim actually made, and a direct probe would need a new
  product seam existing only for a test. Not a defect; not worth a ticket.
- **No bulk payload crosses the circuit** (the ticket's expensive ">128 KiB / >2 min
  stream survival" alternative). The `limits === undefined` assertion tests the property
  directly instead of inferring it from a payload that happens to fit, which is the
  stronger form, not a weaker substitute.
- **A is `profile: 'storage'`, B is the default `'transaction'`** — an asymmetry in a
  scenario framed as "two identical phones". It is the same founder/joiner shape the
  same-party sibling uses, neither profile runs a relay server here, and both ends
  replicate rows in both directions, so it changes nothing the scenario claims. Left alone.
- **B never becomes a member of A's party**, so there are no membership or authorization
  assertions. Deliberate in the implement stage and correct: the strand mesh is the only
  shared surface between two strangers, and asserting party membership would assert
  something the product does not do.
