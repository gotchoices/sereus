# Enrollment gives up early when the container's process died

Shipped. While `ContainerService` polls a brand-new container's `/status` waiting
for it to report healthy, an unhealthy poll now also asks the orchestrator how
the container's own process is doing. A process proven gone fails the provision
straight away — `status: 'error'` with the exit recorded, orchestrator resources
reclaimed — instead of waiting out the 60 s window and stranding the record on
`enrolling` forever.

## What is in place

**The capability** (`service/orchestrator.ts`) — `ContainerRunState`
(`running`, `restartCount`, optional `exitedAt`/`exitCode`) and
`RecoverableOrchestrator extends Orchestrator` with an **optional**
`inspectRunState?(dockerId)`. Optional on purpose: any plain `Orchestrator` stays
assignable, so `@serfab/cadre-host`'s `HostProcessOrchestrator` (which declares
`implements Orchestrator`) needed no change.

Implemented by `DockerOrchestrator` (one `container.inspect()`; `undefined` on a
404, **rethrow** on every other failure so a Docker outage can never read as "the
child is fine"; Go's zero timestamp `0001-01-01T00:00:00Z` filtered by
`parseDockerFinishedAt`), by `MockOrchestrator`, and by the integration harness's
`ProviderProcessOrchestrator` (`exitedAt` stamped from the child's own `exit`
event, `restartCount` always 0 since it never respawns).

**The enrollment change** (`service/container-service.ts`) — health is read
*first* every poll, so a container that came back healthy enrols regardless of
its history. Only an unhealthy read probes liveness. On proven death: a 50-line
`getLogs` tail into the `debug` log (not onto the record — it is tenant output),
then throw, so `provisionContainer`'s existing catch is still the single failure
path (`error` + `safeReclaim`). Every ambiguous answer keeps waiting: no
`inspectRunState`, a container the orchestrator no longer knows, or a probe that
threw. The wait also bails on any record that is no longer `enrolling`, so a
concurrent `DELETE` (which stops, then removes) is never read as a crash.

**Constants** `CONTAINER_ENROLLMENT_TIMEOUT_MS` (60 s) /
`CONTAINER_ENROLLMENT_POLL_MS` (2 s) exported, with `enrollmentTimeoutMs?` /
`enrollmentPollMs?` overrides on `ContainerServiceOptions`.

**Death is judged on a trend across two consecutive polls, not one reading** —
changed during review, see finding 1 below. `hasChildDied` is true when the
restart count is past `ENROLLMENT_TOLERATED_RESTARTS` (1), or when the container
was down-with-an-exit on the previous poll and still is.

Still unchanged and intended: a container that is alive but never healthy times
out silently and stays `enrolling`.

## Review findings

### Fixed in this pass

1. **The death rule condemned containers that had already recovered.** The rule
   as implemented (`restartCount > 0 || exitedAt !== undefined`, one reading) is
   true of *any* container that has restarted once — and `DockerOrchestrator`
   creates every tenant node with `RestartPolicy: unless-stopped` precisely so a
   transient first-boot failure recovers by itself. A node that crashed once and
   is booting again reads unhealthy for the several polls it takes to come up, so
   the first of those polls failed the provision and destroyed the container and
   its volume — where before this ticket it simply enrolled a few seconds later.
   The implement ticket's own edge case ("`restartCount > 0` but healthy on that
   poll → must enrol") was satisfied only in the narrow case where health
   happened to be healthy on the very first poll after the restart.

   Replaced with a two-reading rule (`hasChildDied` / `isChildDown` /
   `ENROLLMENT_TOLERATED_RESTARTS` in `container-service.ts`): a restart count
   past one is a crash loop, and down-with-an-exit on two consecutive polls is a
   process nothing will bring back — which is the only state a never-restarting
   orchestrator (the integration harness, `MockOrchestrator`, a Docker container
   whose restart policy gave up) can reach. Costs one extra poll (2 s of a 60 s
   window) before a genuinely dead child is condemned. A failed probe now also
   resets the accumulated evidence rather than pairing with a real reading.

2. **`assertChildAlive` hand-rolled its optional call.** It captured
   `this.orchestrator.inspectRunState` and invoked it with `.call(...)`, then
   branched separately on "no method" and "resolved `undefined`" — which have the
   identical outcome. Split into `checkChildAlive` (decides and throws) and
   `probeRunState` (one optional call, one catch), both short.

3. **`ContainerRunState.running` was declared but read by nobody.** Every
   implementation filled it in; no consumer looked at it. It is now the first
   half of `isChildDown`.

4. **The `docs/architecture.md` bullet was a ~200-word single bullet** in a list
   whose other entries are one-line phrases. Restructured into a lead sentence
   plus two nested bullets, and rewritten for the corrected rule.

### Tests

The implementer's seven cases were a good floor and all still pass. Added three
(provider suite 160 → 163 tests, 22 files):

- **restarted once and booting again → stays `enrolling`, nothing reclaimed** —
  the regression guard for finding 1; it fails against the shipped rule.
- **down-and-exited across polls with `restartCount: 0`** — the shape the
  integration harness and `MockOrchestrator` actually produce, which no existing
  case covered on its own (the death case supplied both signals at once). Also
  pins the `exitCode=unknown` half of the message, previously untested.
- **a probe failure between two down readings must not add up to a proof.**

### Filed as tickets

Both appended as new arms to `tickets/implement/36.11-provider-reap-stuck-container-records.md`
rather than filed fresh — that ticket is already open against
`container-service.ts` + `billing-service.ts` and is prereq'd on this one, so it
is the site.

- **`terminateContainer` throws on an already-reclaimed handle.** Every path that
  writes `error` reclaims the container but leaves `dockerId` on the record. A
  tenant's `DELETE` then calls `stopContainer` on a container Docker no longer
  has, gets a 404, and the catch rewrites `error` — the record can never reach
  `stopped`. This change makes that state common (a crashed node lands there in
  seconds, where it used to sit on `enrolling` with its container still present,
  so `DELETE` worked). 36.11 § 5.
- **36.11's text encoded the old death rule** verbatim, so implementing it as
  written would have reintroduced finding 1 in the reap sweep. Corrected to point
  at the landed helpers, with the sweep's own single-reading variant spelled out
  (sound there only because the record is already past its TTL).

Not re-filed: **`error` records still consume a plan slot**
(`canCreateContainer` counts `status !== 'stopped'`), so this change makes the
failure *visible* without freeing the quota. 36.11 § 4 already fixes exactly this
with `QUOTA_CONSUMING_STATUSES`.

### Tripwires (parked in code, not filed)

- `ProviderProcessOrchestrator.getLogs` throws once `removeContainer` has
  forgotten the handle, mirroring `docker logs` on a removed container — so an
  integration scenario tailing a node *after* a failed provision now gets
  nothing. The output is not lost (the file survives under `<volumeDir>/node.log`
  and `ContainerService` tails it into `debug` before failing). `NOTE:` at the
  method saying where to look; the harness's Docker-mirroring behaviour is
  deliberate and was left alone.
- The implementer's existing `NOTE:` about one extra orchestrator inspect per
  poll per enrolling container is still accurate and stays.

### Checked, nothing to change

- **`container?.status !== 'enrolling'`** (the implementer's flagged deviation
  from the ticket) — correct and strictly safer than the `!container ||
  status === 'error'` it replaced. The record enters the loop as `enrolling` and
  only this loop promotes it, so any other status means another writer owns it.
  Its test drives the real `terminateContainer` ordering.
- **`parseDockerFinishedAt`'s `ms <= 0` sentinel** — verified rather than
  reasoned about: V8 parses `0001-01-01T00:00:00Z` to `-62135596800000`, and
  RFC3339 nanosecond precision (`...T00:00:00.123456789Z`) truncates cleanly to
  milliseconds instead of yielding `NaN`. Both the year-1 sentinel and an
  empty/unparseable value are absorbed. Matching the literal string instead would
  be narrower for no gain.
- **Volume destruction on reclaim** — unchanged policy, and correct here: the
  container never enrolled, so there is no node identity worth preserving.
- **`isRunning` vs `inspectRunState`** both issue the same inspect. Not merged:
  `isRunning` swallows every error and answers `false`, which is deliberately the
  opposite of what the liveness probe must do.
- **50-line tail to `debug` only** — the record carries the exit code and restart
  count, which is what an operator without `DEBUG` needs to triage; the tail is
  tenant output and does not belong on provider-side metadata.

### Not verified — unchanged from the handoff

There is no Docker daemon in this environment. `RestartCount` / `FinishedAt` /
the 404 `statusCode` shape, and whether `remove({ force: true })` stops a
container Docker is mid-restart rather than racing it, are proven only against a
hand-rolled fake dockerode. This remains the largest untested claim in the
change.
