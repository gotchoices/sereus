# The claimed node restarts at once and keeps its owner's addresses

## What landed

A node started with a claim secret runs under a placeholder party until an owner delivers a seed carrying proof of the secret; `cadre start` then stops it and builds a new node under the claimed party (`restartIntoClaimedParty`).

- **`seed:applied` means verified, merged and acknowledged.** `SeedBootstrapService.handleSeedStream` calls `onSeedApplied` after the ack is written and the stream closed, and only then runs `dialPreferredPeers`. cadre-cli restarts on `seed:applied`, so the restart no longer waits up to 86 s per unreachable preferred peer. The non-wire `applySeed` path is unchanged.
- **The claim seed's dial targets survive the restart.** Pure helper `seedDialTargets(seed, selfPeerId)` (exported, with type `SeedDialTarget`) is the one filter for preferred, addressed, non-self peers, used by `dialPreferredPeers`, `CadreNode.recordSeedBootstrapPeers` and the new `seed:applied` field `dialTargets`. cadre-cli threads them through `afterClaimSeedSettles` → `restartIntoClaimedParty` → `buildClaimedNode`, which records them into the claimed party's bootstrap-peer store before constructing the node; the restarted node's start-time reconcile pass dials them through the cold-start branch.

Code landed in the commit `tess: timed out on claimed-node-restarts-without-waiting-on-dials — added resume note`; the `ticket(implement): claimed-node-restarts-without-waiting-on-dials` commit only moved the ticket after verification.

## Review findings

Read the implement diff first, then the surrounding code in `seed-bootstrap.ts`, `cadre-node.ts` (`seedEventCallbacks`, `recordSeedBootstrapPeers`, `retainDialTarget`, `dialColdStartBootstrap`, `reconcileControlCohort` scheduling), `peer-dial.ts` (`dialAddr`), `start-node.ts`, `start.ts`, and every doc mentioning `seed:applied` / `onSeedApplied` / the claim restart.

**Fixed inline (minor):**
- **Stale doc.** `docs/architecture.md`, the seed protocol's "Receiver hardening" bullet, still said `onSeedApplied` "still fires after" the dials. Rewritten to say it fires after the close and before the dials, so a listener that stops the node waits on no dial. The implementer had updated the claim paragraph but not this one.
- **Stale rationale.** `CadreNode.retainDialTarget`'s doc gave `createSeed` projecting self as a reason for its self-guard; seed intake now arrives pre-filtered by `seedDialTargets`, so the doc now names `addDrone` as the caller the guard is for. The guard itself is kept (cheap, and it protects `addDrone` / `claimNode` / `refreshDialHint`); the overlap the handoff asked about is not worth removing.

**Checked, no change needed:**
- Correctness of the reorder: `onSeedApplied` runs after `await replyAndClose`, so the ack is flushed before the cadre-cli listener calls `node.stop()` (which it does synchronously inside the emit). `dialPreferredPeers` then either finds the libp2p node not `started` (`dialAddr` refuses at once) or has its attempt aborted by the node's `stop` event; each failure is caught and counted per peer. `activeStreams` is decremented in `finally`.
- A listener throwing inside `onSeedApplied` lands in the handler's `catch` and also emits `seed:error` and skips the dials — same behaviour as before the reorder (the callback was inside the same `try`), so not a regression.
- `CadreNode.seedEventCallbacks` computes `dialTargets` before emitting; `refreshMembershipGate` after the emit on a node being stopped is `void`ed and was already in that position before.
- Restarted node: `buildClaimedNode` records into the in-memory store synchronously before `new CadreNode`; `reconcileControlCohort` runs once after start and, with an empty claimed-party control database, takes `dialColdStartBootstrap`. Same private key across the restart, so the placeholder's self-filter holds for the claimed node.
- Only one `seed:applied` emitter (`seedEventCallbacks`) and two in-repo listeners (cadre-cli's console line, which ignores the new field; reference-app-web's log). cadre-host reads `/status`, not events.
- Type safety: `afterClaimSeedSettles` shares one listener between `seed:applied` and `seed:error` with `dialTargets?` optional; loose but correct, left as is.
- cadre-cli README "Waiting to be claimed" and `docs/architecture.md` "On the node and on the owner" already describe the new behaviour.

**Tests:** the one changed test (`seed-bootstrap.spec.ts`, "acks and reports the seed applied before it dials the seed's preferred peers") fails under the old order and pins the new contract; kept. No test added: `seedDialTargets` is a one-line filter whose self/addressless skips are exercised through the existing dial and retention specs, and the cadre-cli threading is glue.
