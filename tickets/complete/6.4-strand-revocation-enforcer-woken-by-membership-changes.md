# Complete: the strand revocation enforcer wakes on a membership change

## What landed

Built in `ticket(implement): strand-revocation-enforcer-woken-by-membership-changes`, adjusted in this review.

`StrandRevocationEnforcer` no longer polls. Every scheduled refresh runs on one `TableChangeWatch` (`table-change-watch.ts`):

- on a change to `Strand.Member` or `Strand.MemberPeer` (`StrandDatabase.watchTables`, supplied by the instance manager as the `watchChanges` dep);
- once at start;
- on a backstop, `DEFAULT_REVOCATION_BACKSTOP_MS` (5 min) after the last refresh settled;
- 30 s (`REVOCATION_REFRESH_RETRY_MS`) after a failed read or a failed `hangUp`;
- 30 s (`REVOCATION_WIDE_STRAND_REFRESH_MS`) after each successful read on a strand with more distinct bound peer ids than its cluster size (`cohortBreadth`).

`refresh()` stays public and serialized, and resolves after the sweep. The enforcer now starts in `StrandInstanceManager.publishDatabase`, so every publish path (ungated launch, first-sync gate, founder bootstrap, deferred join retry, hibernation wake) starts it once the database exists. The membership reconciler has its own `DEFAULT_MEMBERSHIP_RECONCILE_INTERVAL_MS` (30 s) and no longer mirrors the enforcer's cadence.

Config: `{ enabled?, backstopMs?, autoRefresh? }`. `autoRefresh: false` (renamed in review from `wakeOnChange`) stops the enforcer scheduling any refresh of its own: no change subscription, no failure retry, no wide-strand follow-up. Refreshes then run only at start, on the backstop, and on `refreshRevocationEnforcement`. The integration harness's `revocationSuspended` sets it, together with a backstop longer than any test.

## Review findings

**Read first:** the implement diff in full (enforcer, instance manager, reconciler, writer and node docs, types, index, four cadre-core specs, harness, five scenarios, both docs), then `table-change-watch.ts` and `timeout-scheduler.ts` to check how `trigger` interacts with a run in flight.

**Correctness, checked and sound:**
- `trigger` called from inside a run (failure retry, wide-strand follow-up, failed `hangUp`) arms a wake. When the run settles the backstop is armed too, and the earlier wake wins and clears the others. A follow-up armed while a run is in flight sets `rerun` instead of overlapping it. No double runs and no lost wakes.
- `publishDatabase` sets `instance.database` before `start()`, so `watchChanges`' `liveDatabase()` cannot throw on that path. If it ever does, `subscribe()` logs and falls back to `scheduleRuns`. `instance.libp2pNode` is set (line ~919) before the database phase (~941), so the first sweep has a network.
- Resource cleanup: `stop()` disposes the watch, `StrandDatabase.close()` disposes it through its registry, and both disposals are idempotent. A failure after publication rolls back through `releaseRuntime`, which stops the enforcer.
- A gated joiner's deny set is empty until publication, as it was before (its reads failed with "no live database" then).
- Moving `resolveStrandClusterSize` out of the `try` is safe: it runs before anything is allocated, the same as the round-trip check above it.
- `revokeMember` / `leaveStrand` commit on `instance.database.getDatabase()`, the same `Database` the watch is on.

**Found and fixed (minor):**
- **The suspended test mode was not suspended.** `wakeOnChange: false` removed only the change subscription, but a suspended machine still scheduled its own refresh 30 s after a failed read or `hangUp`, and every 30 s on a strand wider than its cluster size. The harness promised that "every cut it makes is one the test drove", and the implementer named this retry as the one way the change could explain the intermittent formation-scenario failure (test 1: the removed party's machines already cut off from each other before the test's refresh). The knob is now `autoRefresh` and gates all three follow-ups through one helper, `scheduleFollowUp`. Its log line says when a re-read is actually scheduled, where the old failure log claimed a retry even when none was armed. The harness NOTE that documented the leak was replaced by the corrected contract. `docs/architecture.md` was updated for the rename.
- **Test added:** "autoRefresh: false takes no subscription and schedules no retry or wide-strand follow-up — only start and the backstop" (`strand-revocation-enforcer.spec.ts`). It pins the harness's determinism contract, which is branching logic a regression would otherwise surface only as an integration flake.

**Tests cut or kept:** the implementer's deletions (the poll-cadence constant test, the skip-a-tick test now owned by `table-change-watch.spec.ts`, and the two reconciler-mirroring specs for behaviour that no longer exists) are right. The rewritten start/retry/wide-strand spec checks real branching and stays. No other test was added: publish-path wiring is glue, and the formation and removal scenarios exercise it end to end.

**Docs:** read every doc change and grepped the tree for `pollIntervalMs` / `DEFAULT_REVOCATION_POLL` / `revocationPollMs` / `RevocationRefreshScheduler`. The two remaining `pollIntervalMs` hits in docs belong to the reconciler and the first-sync gate, so they are correct. strands.md's removal sections and architecture.md's consumer list, `revokeMember` bullet and backstop paragraph describe the new schedule.

**Tripwires (already parked by the implementer; checked, left in place):** the read-repair self-wake (`NOTE:` on `StrandRevocationEnforcer.subscribe`); what the backstop covers (`NOTE:` on `DEFAULT_REVOCATION_BACKSTOP_MS`); the two full-table scans per refresh (`NOTE:` on `readStrandRevocationRows`); the undeadlined `readRows`/`hangUp` (`NOTE:` on `doRefresh`). No new tripwires.

**Considered and not acted on:** the wide-strand count includes orphaned bindings, so it errs toward refreshing more often. The plan chose this, the cost is bounded at the old 30 s cadence, and it applies only to wide strands.

**Performance:** an idle closed strand at or below its cluster size now does no enforcer reads until a membership change or the 5-minute backstop. A wide strand keeps the old 30 s cost by design. Informational measurement (see below) saw the enforcer's idle sync share go from 18 streams to 0.

**Type safety / lint:** no `any`; `yarn lint` passes.
