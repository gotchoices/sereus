# `CadreControl.JoinedStrand`: the party-wide record of strands joined from other parties

## What landed

A strand joined from another party has its `Strand` row in the founder's control database, so until now only the joining machine remembered the join (in its own `KeyStore`). `CadreControl.JoinedStrand` is the table the next ticket (`party-wide-joined-strands`) publishes joins into, so every machine of the party can see them. Nothing in the node writes or reads it yet.

- **Schema** (`schemas/control.qsql`, mirrored byte-for-byte in `control-schema.ts`): `JoinedStrand (Id pk, Type, MemberPrivateKey null, StampId unique)` with `NotRevoked`, `RevocationRecorded`, `NoUpdate`, `KnownType` (`'o'`/`'c'`), `MemberKeyClosedOnly`, an owner-signed row-bound `AuthorizedInsert` (binds the read secret), and an `AuthorizedDelete` with an owner-signed `'remove'` branch plus a committed-tombstone reap branch. `Revocation` gained a `RowIsGone` branch and column-comment entries for the table.
- **TypeScript**: added to `CONTROL_TABLES`, `RevocableTable`, `GUARDED_KEY_COLUMN` and `REAPABLE_TABLES`. New `ControlDatabase` methods `queryJoinedStrands`, `queryJoinedStrand`, `queryJoinedStrandStampId`, `insertJoinedStrand`, `deleteJoinedStrand` (through `deleteGuardedRow`). The strand-id conflict classifier is now `isStrandIdConflict(error, table)` over one regex builder; `publishStrand` passes `'Strand'`.
- **Tests**: new `control-joined-strand.spec.ts` (happy path, repeat-insert classification against the live engine error, unsigned insert, signature bound to the read secret, update refused, bare delete refused, delete-then-replay refused). Reap coverage by extending the multi-table sweep case in `control-revocation-reap.spec.ts`; `RowIsGone` coverage by extending the live-row case in `control-revocation-replay.spec.ts`; table lists extended in the ledger-marker and apply-unwind specs; op budgets re-measured (cold 46/21 → 48/23, warm unchanged at 13/3).
- **Docs**: Control Network table row for `JoinedStrand`, `Revocation` row updated, and a paragraph after the table recording that a changed constraint makes an older control store fail to start.

## Review findings

Read the implement diff (`ticket(implement): joined-strand-control-table`) before the handoff, then the generic revocation paths it relies on, the sibling code it mirrors, and the docs it touches or should have touched.

**Correctness (checked, no defect found).**
- `deleteGuardedRow`, `reapRevokedRow`, `reapRevokedRows`, `queryStampId`, `queryRevokedStamps` and the guarded-delete listener (`CadreNode.noteGuardedDelete`) are all generic over the table via `GUARDED_KEY_COLUMN` / `REAPABLE_TABLES`; no per-table switch was missed. `reapRevokedRows`' skip-self rule applies only to `CadrePeer`/`DeviceToken`, correctly.
- Schema digest field order in `AuthorizedInsert` matches `insertJoinedStrand` (`Id, Type, MemberPrivateKey ?? '', StampId`); the delete digest matches `deleteGuardedRow`'s `[keyValue, stampId]`.
- Tombstone scoping: every `Revocation` reader filters on its own `TableName`, so a `JoinedStrand` tombstone never closes `Strand`'s consent branch (confirmed by reading the schema, as the handoff said).
- Replay after late convergence (the `NotRevoked` NOTE on `Strand`): for `JoinedStrand` a replayed add reuses the retired stamp, so the reap branch removes it on the next connected pass. Better than `Strand`, which keeps such a row.
- The reap branch is justified: the tombstone that authorizes it is itself owner-signed, and the read secret is held by the founding party and every member.
- The warm-start break on old stores: confirmed plausible by reading `../quereus` (`runtime/emit/alter-table.ts` raises exactly the reported message for `drop constraint`); I did not re-run the implementer's throwaway experiment.
