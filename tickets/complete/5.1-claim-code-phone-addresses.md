# Claim codes carry only phone-usable addresses (PR #37, kjeib)

External PR, stacked on PR #36, merged locally as `Merge PR #37: claim codes carry only addresses a phone can use, and the admin can choose` (feature commit `feat: claim codes carry only addresses a phone can use, and the admin can choose`).

## What landed

- **cadre-core `selectNodeClaimAddresses(reported, peerId, { lan, includeTcp })`** beside the claim-payload codec (no Node imports, so it loads on React Native): drops loopback, unspecified, unparsable and (unless `includeTcp`) plain TCP; public names first, raw public IPs only when there is no name; private addresses narrowed by `lan` (a string keeps that IP, `null` drops all, absent keeps all); relay last; appends `/p2p/<peerId>` to an address that names no destination.
- **cadre-core `withClaimDestination(addr, peerId)`** and **`destinationPeerIdOf(addr)`** (added in review): the one rule for "does this address already name its destination peer", shared by the selection rule, cadre-host's exact addresses and `cadre code --addr`.
- **`@serfab/cadre-core/primary-lan-address`** (Node-only subpath): `primaryLanAddress()` by a UDP connect that sends nothing.
- **cadre-host**: `claim-details.ts` applies the rule over the NAT layer's public addresses plus the node's own; `claimLanAddress` resolves `host.config.json` `claimAddresses.lan` (`auto` | `none` | IP); `claimAddresses.addrs` gives an exact list. Read on every claim request; `PUT /api/settings` and `readHostConfig` both validate it; a Settings card in the UI.
- **cadre-cli `cadre code`**: `claimAddressesFor` with `--lan <ip>`, `--no-lan`, `--addr <multiaddr>` (repeatable), `--all`.

## Review findings

Read the feature commit's diff first, then the current files, the docs it touched, and `docs/architecture.md` for claim-code statements.

### Fixed in this pass

- **Bug — offline host lost every LAN address** (`primary-lan-address.ts`). A failed UDP connect reports through the connect callback, not the `'error'` event, and leaves the socket bound to `0.0.0.0`; the callback ignored its error and returned `socket.address().address`, so with no route the function returned `'0.0.0.0'` instead of `undefined`. That became `lan: '0.0.0.0'`, which drops every private address, the opposite of the documented "keep every LAN address" fallback; a host with its internet down showed no claim code at all. Reproduced with a probe to an unresolvable host (callback `ENOTFOUND`, `address()` = `0.0.0.0`). Fixed: the callback checks its error and logs it via `debug`; `finish` is idempotent; the empty `catch` blocks are gone. `probe` is now an optional parameter so the regression test (`is undefined, not the unbound 0.0.0.0, …`) can point it at `route-probe.invalid`.
- **Relay address without its destination** (review focus 1). The selection rule and both exact-address paths treated any `/p2p/` as "already has a destination", so `…/p2p/<relay>/p2p-circuit` stayed unsuffixed and the codec later refused it. All three now use cadre-core's `withClaimDestination`, built on the codec's own `destinationPeerIdOf` (last `/p2p/` after any circuit hop). Pinned in the core spec and the host service test.
- **Exact addresses naming a peer** (review focus 2). `claimAddresses.addrs` is host-wide and each node's code appends its own peer id, so an entry that already ends in `/p2p/<id>` is wrong for every node but at most one. `claimAddressSettingsProblem` now refuses such an entry at save time ("must not end in /p2p/<peer id>"). `cadre code --addr` serves one node, so a matching destination there is legitimate and the codec still catches a wrong one.
- **Hand-edited `claimAddresses` was never validated.** The README invites editing `host.config.json`, but `readHostConfig` did not check the field, so a bad `lan` or `addrs` surfaced as a TypeError or codec error on the Join page. `readHostConfig` now runs the same validator and names the field.
- **Public-IP mode** (review focus 4, interaction with PR #41). Decided: `lan: auto` keeps no LAN address in public mode. `HostedNodeAddressSource.getStatus()` now exposes `network.mode` (`NatService` already returned it), and `claimLanAddress` returns `null` there. Without this, a public-mode machine whose route source is a private interface would put an unreachable private address in every code.
- **DRY in the LAN resolution.** `HostedNodeService.claimDetails` and `dialAddressesFor` both re-derived the `auto`/`none`/IP logic and called `getStatus()` twice. Replaced by one async `claimLanAddress` in `claim-details.ts`. It probes the primary address only when no gateway answered, and not at all when exact `addrs` are set.
- **Wording.** `--all` help and the CLI README said "every address", but a raw public IP still gives way to a public name; both now say so. The supervisor-test fake had a mis-indented line.
- **Docs**: `docs/cadre-host.md` Join-by-QR step 2 and the settings table, the cadre-host README, the Settings card label and the release notes now cover the public-mode default, the no-destination rule for `addrs`, and that `addrs` applies to every hosted node. `docs/architecture.md` line ~701 ("a claim QR code lists the node's public addresses before its LAN ones") still holds; nothing there claims codes carry every address.

### Tripwire

- **`claimAddresses.addrs` is host-wide.** Every hosted node's code carries the same exact addresses with its own peer id, so they reach every node only if each node has its own address (one node, or a port per node); several nodes behind one proxy port would each get a code that dials the wrong node. Parked as a `NOTE:` in `dialAddressesFor` (`claim-details.ts`) and stated in `docs/cadre-host.md` and the README.

### Checked, no change

- **DRY of `isPrivateIp` (cadre-core) vs `isPublicIpv4` (cadre-host `nat/address-resolver.ts`)** (review focus 3). Declined. They are different predicates: cadre-core's says "on a LAN a phone could share", covers IPv6 and must stay free of Node imports; cadre-host's says "a real internet address" and also excludes multicast, reserved and `0/8`. Only four IPv4 ranges overlap. Making one call the other would change one predicate's meaning.
- **Error swallowing** (review focus 5): resolved by the rewrite above. The probe failing means "unknown", and it is now logged.
- **Settings route**: whitelist, whole-value replacement, trimming and dropping empty `addrs` entries, and refusal leaving the stored value unchanged are all covered by `settings-route.test.ts`.
- **CLI flag interplay**: commander leaves `lan` undefined unless `--lan`/`--no-lan` is given; `--addr` overrides `--all` and `--lan`; `--all` ignores `--lan`. This matches the README.
- **Tests**: the implementer's tests pin real branching in the selection rule and the settings behaviour, so none were cut. Added only regressions for the defects above: the offline probe, a relay hop gaining the node's id (core and host), the destination-named `addrs` refusal, and `auto` in public mode.
- **Edge left alone**: `lan` compares IP text exactly, so an IPv6 LAN address typed in a non-canonical form would not match. That is admin input and IPv4 is the norm, so it was left as is.
