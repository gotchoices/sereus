# Rebuild the provider's port bookkeeping from Docker before handing out ports

## What was wrong

`DockerOrchestrator` gives each tenant container three host ports (health, metrics, p2p) from `config.portRange` and tracked them only in memory (`portAllocator` and the `containerPorts` map). Containers outlive the provider (`RestartPolicy: unless-stopped`), so after a provider restart the first `createContainer` was handed the ports the surviving containers were still bound to, and removing a pre-restart container released nothing.

## What landed

- `docker-orchestrator.ts`:
  - `hostPortsOf(info)` reads the host ports back from an inspect's `HostConfig.PortBindings`, the inverse of what `createContainer` writes. It uses inspect rather than the list result's `Ports`, which Docker fills only for running containers.
  - `rehydratePorts()` lists every container wearing the `sereus.container-id` label (`all: true`, so stopped ones count), inspects them, reserves their ports and fills `containerPorts`. It records nothing unless every inspect succeeds; a container that 404s between list and inspect is skipped.
  - `ensurePortsRehydrated()` runs the pass once per process and forgets a failed pass so the next call retries. `createContainer` awaits it before allocating; a failed pass fails the create.
  - `removeContainer` does not start a pass. After the container is gone and before releasing, it calls `settlePortRehydration()`, which waits out a pass already in flight and logs (does not rethrow) its failure. See review findings for why this replaced the implement-stage design.
  - `inspectIfPresent(dockerId)` (inspect, or `undefined` on 404) is shared by the pass and `inspectRunState`.
- `port-allocator.ts`: `reservePortSet` / `releasePortSet` accept a partial port set and skip missing keys, as their doc comments already promised. cadre-host compiles unchanged.
- Test fakes: `volumeStubs` renamed to `daemonStubs` and given a default empty `listContainers`.

## Tests

`orchestrator-port-leak.test.ts`, "DockerOrchestrator port bookkeeping after a provider restart":

- "reserves a surviving container's ports before allocating, and frees them when it is removed": the reproduction. Without the fix the create publishes 10000–10002, the survivor's ports.
- "frees a removed container's ports that a pass in flight records after the removal": added in review. It fails if the `settlePortRehydration()` call in `removeContainer` is removed (checked by disabling that line).

## Review findings

Read the implement diff (`ticket(implement): bug-provider-port-allocator-forgets-live-ports-on-restart`) first, then the full `docker-orchestrator.ts` and `port-allocator.ts`.

- **Correctness, fixed inline: a removal could strand ports.** In the implement-stage design, `removeContainer` ran the pass up front and continued if it failed. If a concurrent create then started a new pass that listed the container before the removal and recorded it after the release, those ports stayed reserved until the next restart (the implementer flagged this). Rewritten: `removeContainer` no longer starts a pass and instead waits for any pass in flight just before releasing. This closes the race completely. A pass that starts after the removal cannot list the container, only one pass is in flight at a time, and if no pass has run, the container's ports were never reserved, so there is nothing to release. This also stops the first removal after a restart from listing and inspecting every container. A new test pins it (above).
- **Comments updated to match:** `resolveDockerId` doc, the `fake-docker.ts` header and `daemonStubs` doc, and the `docker-orchestrator-resolve-id.test.ts` header said the map is rebuilt by "a create or remove"; now "a create".
- **Tests:** folded the survivor fixture into a shared `survivorInfo` plus a `restartedOver()` helper so the two restart tests don't duplicate the fake daemon. No existing test was cut: the implement-stage edits to the other four test files were the mechanical rename only.
- **Tripwire, parked as a `NOTE:` in `rehydratePorts`:** every labelled container is inspected at once with `Promise.all`; bound the concurrency if a provider ever carries thousands. Not measured.
- **Error handling:** checked. A failed pass fails the create before any port is allocated, so a create never collides with a live container. A removal never fails because of the port bookkeeping. `inspectIfPresent` rethrows everything except a 404, so a daemon outage is not read as "nothing there".
- **Malformed or out-of-range `HostPort`:** checked. `Number('')` gives 0 and garbage gives NaN, and `markUsed` ignores both, as it does ports outside the range. Correct, because `allocate()` can never hand those out.
- **Id consistency:** checked. The pass keys `containerPorts` by the inspect's full `Id`. Callers pass `container.id` from create or `Id` from `listContainers`, both the full id.
- **Type safety:** no `any`, and the widening to partial port sets is sound. Nothing to change.
- **Resource cleanup / performance beyond the tripwire:** nothing found. The pass runs once per process.
- **Docs:** `docs/` and `packages/cadre-provider/README.md` do not describe provider port allocation, so nothing needed updating.
- **Not done:** no check against a real Docker daemon, as in implement. Manual check: start the provider, create a container, restart the provider, create a second, and confirm it gets the next three ports and starts.
