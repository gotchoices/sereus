## The gap this closes

A party's control database (its members, strands, invitations) is replicated across the
party's machines. Each write is offered to a set of them — the **cohort** — and commits
once a super-majority approves. A cohort of ONE commits on the writer's own vote, so a
control write that merely passes is equally consistent with "three machines agreed" and
"one machine wrote to itself". Before this ticket no harness scenario established which
of those it got.

## `harness-party-control-cohort.integration.ts`

Three cases, each against its own owner-plus-two-drones party:

- **Case 1 — the drone cap.** No writes. From the owner the cohort reaches all three
  machines; from a drone it reaches two (itself + the owner) and asking for three times
  out, asserted on the observed size reported in the error rather than merely on "it
  threw". This is the executable form of the finding recorded by
  `debt-harness-record-fret-ring-convergence-finding`: drones dial only the owner, never
  each other, so a drone-coordinated write caps at two machines permanently.
- **Case 2 — a real, unforced write into a waited three-machine cohort.** Waits for the
  cohort, starts an observer, issues one real `createStrand` through the real
  `CadreControl` CHECK constraints, reads the row back by strand id.
- **Case 3 — a forced three-machine cohort.** `forceFullCohort` then `pinCoordinator`
  (force first — the pin wraps whatever is installed), one write, restore in reverse.

Both writing cases are plain `it` — no `it.fails`, no weakened assertion — because both
commit on every run measured. The unanimity fragility that
`debt-control-write-unanimity-at-three-nodes` tracks is about a member that is slow or
silent, not about three healthy machines.

## Found and fixed in this pass (minor)

- **Read-back asserted only that *a* strand row existed** (`queryStrands().length >= 1`)
  in both writing cases, so it could not tell the row the write created from any other
  row. The cause was the local `settle` helper discarding its operation's return value.
  Made `settle` generic (`Settled<T>` carries the value through) and both cases now assert
  `strands.map(s => s.Id)` contains the created `strandId` — the idiom `happy-path`
  already uses. This was the handoff's own second-listed gap.
- **Case 1's error-text assertion pinned a literal cohort size of 2.** The drone's
  converged view is 2 and every run reports 2, but a transiently dropped FRET
  classification would make the probe time out at 1 and fail the case for the wrong
  reason. Widened to `[12]`, with a comment saying what must never match (a 3) and why
  nothing is lost — that the two-member view is a *real* cohort is already established by
  the preceding wait and membership-equality assertion.
- **The header's measured latencies were stated as tight numeric ranges that this pass
  fell outside.** Measured here: case 2 at 711 ms and 818 ms (header said 875–987 ms),
  case 3 at 182 ms and 257 ms (header said 283–374 ms). A header range narrower than the
  real spread invites a future reader to treat a normal run as a regression. Rewritten as
  the observed spread (~0.7–1.0 s and ~0.2–0.4 s) and explicitly labelled as observation,
  not a bound anything asserts.
- **The `happy-path` comment characterised only the first test's parties.** It explained
  Bob's one-machine party and Alice's two drones, but the file's second test creates two
  further parties with one drone each, whose writes may reach one machine or two. Added
  that sentence.

## Checked and found sound — no change made

- **Case 2's `some(size >= 3)` versus case 3's `every(size === 3)`.** The handoff asked
  whether the weaker claim could be tightened. It should not be. `observeControlCohorts`
  patches the prototype, so it records selections from every `Libp2pKeyPeerNetwork` in the
  worker — including the drones' own cluster-membership re-derivations, which legitimately
  return 2 (the permanent cap case 1 asserts), and including the other two parties' nodes,
  which are alive for the whole file. `.every` would fail against a correct system. The
  observed sizes are exactly as described: `[3,2,2,3,3,2,2,3,...]` for case 2 and all-3s
  for case 3. The in-file comment warning the next reader off `.every` is accurate and
  prominent, and the claim is anchored on both ends anyway — the waited cohort is asserted
  to equal the party's three machines immediately before the write.
- **Restore ordering and teardown.** Force-then-pin at application, unpin-then-unforce at
  restore, per `key-network-patch.ts`'s enforced rule; each case restores in `finally` and
  the describe-scope handles are the safety net for a mid-case failure; `afterAll` unwinds
  pinned → forced → observer and then shuts the network down through `network?.shutdown()`
  so a `beforeAll` that threw still releases ports.
- **The 180 s `it` timeouts, ~200x the measured latency.** Sized for the unanimity failure
  path (two 10 s response-deadline attempts per pend round, rounds not deterministic) that
  does not reproduce on the healthy path. They never fire on a green run and cost nothing;
  lowering them would only convert a future genuine hang from a named assertion failure
  into an anonymous vitest timeout. Left as-is.
- **`settle` / `errorChainText` duplicated with
  `control-write-degraded-cohort-member.integration.ts`.** The judgement — two small copies
  beat a harness module with one importer, extract when a third file needs them — is
  recorded as a `NOTE:` at the definition site and is the right call. Checked
  `plan/10-integration-test-harness-helper-consolidation-remaining-files`: it tracks the
  node-fixture builders, not these two, so there is no ticket this belongs to yet.
- **Three parties (nine nodes) created up front in `beforeAll`.** Deliberate — the later
  cases' rings converge while case 1 burns its 8 s probe. Ports are released by
  `network.shutdown()` on every path.
- **The 8 s drone-cap probe is a deliberate timeout**, so a future change that let drones
  dial each other would fail as "a timeout that did not happen" rather than with a clear
  message. That is the intended shape of the tripwire and the header says so; the
  surrounding assertion message ("the sibling-drone cap is gone") names the diagnosis a
  reader needs.
