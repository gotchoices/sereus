# The pending-join runner wakes on a change to its tables

## What landed

`PendingJoinRunner` (`pending-join-runner.ts`) no longer owns a pass timer. Every pass runs on a `TableChangeWatch`, built in `start()` from the new `watchChanges` dependency, or from `scheduleRuns` when that is absent, as in the unit spec. `CadreNode.startPendingJoinRunner` subscribes it to `CadreControl.JoinRequest`, `JoinSuccess`, `JoinFailure`, `OwnerKey` and `Revocation` through `ControlDatabase.watchTables`.

A pass runs at these times:

- on `start()`;
- on `kick()`, as a 0 ms trigger, used when the owner signer is wired;
- on any change to the five tables, using the watch's 50 ms coalescing and one run at a time;
- at the latest `PENDING_JOIN_BACKSTOP_MS` (10 min) after the last pass.

A failed pass, a failed `consider` for one row, and an outcome write that gave up to another machine's writes each trigger a pass after `PENDING_JOIN_PASS_RETRY_MS` (30 s). `PENDING_JOIN_POLL_MS` is replaced by `PENDING_JOIN_BACKSTOP_MS` and has no alias. The attempt timers for each join are unchanged. A `NOTE:` on the backstop constant records the accepted cost on cadres larger than the replication breadth. The docs (`strands.md` → "Who retries", `architecture.md` → "Consumers") describe the new schedule.

The full suites and the idle message-count measurement are parked as the "Second arm" of `tickets/blocked/strand-watcher-change-driven-verification.md`. They wait on the stale `@optimystic/db-core` build in `../optimystic`.

## Review findings

Read the diff from `ticket(implement): pending-join-runner-woken-by-changes` first, then `table-change-watch.ts`, the rest of `pending-join-runner.ts`, the runner's lifecycle in `cadre-node.ts`, and the docs.

**Correctness, checked by reading:**
- Single-flight and `kick` during a pass: `trigger(0)` while a pass runs sets the watch's `rerun` flag, and one more pass follows 50 ms after it settles. This matches `kick`'s doc.
- Retry triggered inside a pass: the 30 s wake survives `settled()`, which only adds the backstop. When several rows fail, several wakes are armed, and the first one to fire clears the others. No issue.
- Self-wake from the runner's own writes: the expiry outcome write, the `joined` re-write, the age-out delete and the re-issue each wake one follow-up pass. That pass does nothing, because the row now has an outcome whose age-out is not yet due, or has an attempt in flight, or is gone. `observeRows` (`stageMembershipInvitesFromPendingJoins`) only changes memory. No loop.
- Teardown order: `CadreNode` stops the runner before the control database goes, and builds a new runner on each start. `watch.dispose()` is idempotent, so a second dispose from `ControlDatabase`'s `TableWatchRegistry.disposeAll` is safe. After stop, `retryPass` and `kick` do nothing because `watch` is null.
- Subscribe failure: `start()` builds the watch before setting `running`, so a bad table name throws from `CadreNode.start()` and leaves the runner stopped.
- Non-owner machines: `isOwner()` reads nothing without a signer, so their passes touch no join table. The `kick` in `useOwnerSigner` makes the first read that arms the tables. This is correct, because a non-owner does nothing with join rows.

**Found and fixed (minor):**
- `stop()` then `start()` on the same instance could run a pass left over from the first start alongside the new watch's passes. The old `passInFlight` guard had prevented this. Production builds a new runner on every start, and the spec never restarts one, so this cannot happen today. It is recorded as a `NOTE:` tripwire on `start()` in `pending-join-runner.ts`.

**Tripwires already parked by the implementer (left as is):**
