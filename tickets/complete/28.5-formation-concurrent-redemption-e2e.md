# Complete: concurrent-redemption e2e scenario (built, reviewed, standing red upstream)

## What shipped

**`strand-formation-concurrent-redemption.integration.ts`** — the acceptance scenario for the
nonce-keyed `FormationUsage` design, on real network with no stubs. One inviting party with two
live cadre nodes (A owner/storage, B plain member), each answering formation through its own
DB-backed `ControlFormationUsageRecorder`; two more real joiner nodes redeem the SAME token in
the same tick through different responders, so the two writes race across the distributed
control collection rather than through one node's write queue.

- **Case 1** — multi-use invite behind a real HTTP approval hook: both redemptions survive,
  each row attributable (distinct joiner-minted nonce, the joiner's own key, re-verified from
  the stored bytes via `verifyFormationConsent`), rows on BOTH nodes' views, hook asked
  **exactly** twice (hard equality, asserted before the convergence waits).
- **Case 2** — single-use invite raced by both nodes: approved responses ↔ surviving rows
  one-to-one on both views, a refused joiner told terminally `'Invalid token'` and never to
  retry, and — when both land — the accepted over-admission asserted as *observable* rather
  than as a failure.
- **Case 3** — a third redemption of the spent invite refused terminally through either node,
  adding no row. A standing unlimited "door" invite keeps the membership connection gate open
  so a gate refusal cannot masquerade as the token refusal under test.

**`bootConnectedPair`** (`harness/node-fixtures.ts`) — pair fixture with connect-then-write
ordering: both nodes confirm a control cohort ≥ 2 before the first control write, owner genesis
included, plus an `ownerSign` closure for publishing owner-signed control rows. `bootPair`
untouched.

**`countFormationUsage` NOTE** (`cadre-core/src/control-database.ts`) — records that the seat-cap
count is blind to sibling-written rows.

## Status: red, deterministically, on a defect outside this repo

Reproduced independently in the review pass, matching the implement pass's fingerprint exactly:
both joiners approved, hook asked twice, both rows commit under distinct nonces — and then each
node's per-token view holds only its OWN row after 30 s.

```
node A holds 1 row(s) [UGyh9Q9q…]; node B holds 1 row(s) [bXCKK2mA…]
```

Cause (isolated and filed by the implement pass): a sibling's data tree converges but its
**secondary**-index root never does, so a `where Token = ?` descent honestly finds nothing.
Tracked upstream as `../optimystic/tickets/fix/secondary-index-update-never-reaches-the-sibling.md`,
here as `tickets/blocked/secondary-index-seek-blind-to-sibling-rows`, and listed in
`tickets/.pre-existing-known.md`. This file is the re-measurement instrument for that ticket's
unblock condition — its assertions are not to be weakened for a green run.

## Review findings

### Checked

Implement diff read first, before the handoff summary. Scenario file (439 lines) line by line
against the ticket's spec; harness addition; the `control-database.ts` NOTE; both ticket-board
files. Cross-file: `verifyFormationConsent`'s parameter shape against the test's `UsageRow`, the
approval-hook fixture's surface (`requestCount` / `validationKey` / `validationUrl` / `close`),
the harness barrel export, and `strand-formation-e2e.integration.ts`'s header directive that new

Aspect sweep: assertion strength, resource cleanup, error handling, type safety, DRY, source
hygiene, test-timeout budgets, docs.

### Found and fixed in this pass (minor)

- **`bootConnectedPair` leaked every node it had started when boot threw.** Its doc claimed the
  caller owns shutdown "including on the failure path", but a caller that never receives the
  handles cannot stop anything — and the 30 s cohort wait is the likeliest thrower, so a boot
  failure would leave two libp2p nodes outliving the run. Now stops what it started
  (newest-first, a failed stop reported not rethrown) before rethrowing; doc corrected to say
  the caller owns shutdown of a boot that *returns*.
- **Per-case vitest timeouts were under-budgeted, which would destroy the file's diagnostics.**
  Case 1 can issue three 30 s convergence waits plus two 30 s formation sessions — 120 s against
  a 120 000 ms budget, an exact tie; case 3's two waits plus two sessions are 120 s against
  90 000 ms. When vitest's clock wins, the both-nodes "node A holds … node B holds …" message
  those waits raise is replaced by a bare test timeout — and that message is the entire reason
  the assertions are shaped the way they are. Hoisted to one documented
  `CASE_TIMEOUT_MS = 180_000` on all three cases.
- **Dead suite-scope state in `assertRowsMatchApprovals`.** `let observed` was assigned on every
  poll and never read outside the poll (the failure path re-reads both nodes for itself). Now a
  poll-local const.
- **Docs were out of date about the cap — the review's most consequential finding.** The
  implement pass recorded the index blindness at the code site only. But `docs/architecture.md`,
  `docs/api.md` (user-facing, tells hook authors to "treat `TotalUses` as an audited bound") and
  `docs/STATUS.md` (on `hasOutstandingFormationInvite`) all still stated the over-admission is
  bounded by the number of concurrent redeemers and that a spent token cannot hold the
  connection gate open. Both statements are false today on any multi-node party, for the same
  reason the scenario is red. All three now carry the current-limitation caveat pointing at the
  blocked ticket, stated as a storage-layer defect being fixed upstream rather than a property
  of the invitation design. `docs/STATUS.md` also gained the missing scenario-checklist entry —
  filed as `[ ]`, not `[x]`, with why it is red.

### Found and left alone (major)

None new. The one major defect in play — the blind secondary index — was already found,
isolated, filed upstream and cross-linked by the implement pass; the review's job was to check
that story rather than re-file it, and reproducing it confirmed it. The scenario is correct as
written; nothing in it was weakened.

### Evidence added to an existing ticket, not filed as a new one

`blocked/secondary-index-seek-blind-to-sibling-rows` gained a **control observation** the earlier
measurements did not isolate: in every run, node B reads back A's `FormationInvite` row by its
own primary key (`queryFormationInvite`) inside the same 30 s window in which the
`FormationUsage` secondary-index seek stays empty — likewise A's `Strand` and `ValidationKey`
rows. So the blindness is specific to *secondary*-index sub-collections, not to indexed descent
in general. That narrows the upstream search; it is an arm on the existing ticket, not a class of
its own.

### Verified-no-gap (the ticket asked)

Case 3's terminal-vs-retryable refusal mapping does have coverage that is **green today**:
`packages/cadre-core/test/control-formation-seat-budget.spec.ts` — 12/12 passing in this pass —
covers sequential exhaustion raising `InvitationExhaustedError` rather than a retryable conflict,
through the recorder as well as the database directly. No single-node stand-in needs writing and
no gap ticket was filed.

### Tripwires (recorded at the site, not filed)

- `harness/node-fixtures.ts`, at `bootConnectedPair` — a `NOTE:` explaining that its ~8 lines of
  node construction duplicate `bootPair`'s deliberately: factoring them out would move
  `B.start()` ahead of A's owner genesis in `bootPair`, i.e. change the exact ordering the two
  fixtures exist to keep apart, and the full integration suite that would prove that safe
  exceeds the 10-minute agent run budget. Revisit condition stated: if a **third** pair fixture
  lands, extract a helper that takes the ordering as an argument rather than copying again.
