# Cohort read deadline declared at 5000 ms on both networks, with a host override

## What shipped

Before serving a read whose local copy may be stale, an Optimystic node asks the block's cohort which revision is newest and believes an answer only if it arrives inside a per-peer deadline. Optimystic's default is 1000 ms — a LAN budget, shorter than one round trip between two phones that reach each other only through a relay. Sereus declared nothing, so both of its networks ran at 1000 ms; at a cohort of two there is exactly one peer to ask, so one late answer left the read with nothing to corroborate against and it was declined and retried (18 declines over one measured rejoin at 1000 ms, 2 at 5000 ms).

`COHORT_READ_DEADLINE_MS = 5000` now sits beside `MIN_CLUSTER_SIZE` in `cluster-size.ts`, and both `CONTROL_CLUSTER_POLICY` and `STRAND_CLUSTER_POLICY` declare it. The two policy objects stay separate, as they were; this is the one field they agree on by argument rather than by coincidence, because the reason to widen it is a property of the link and a phone's control node and its strand nodes ride the same link. A host moves both at once with `NetworkConfig.cohortQueryTimeoutMs`, threaded at `buildControlNodeOptions` and `buildStrandRuntime`; `resumeStrand` retains `network`, so the field survives a hibernation wake with no new plumbing. A value that is not a finite number above zero, or is above Optimystic's `MAX_COHORT_QUERY_TIMEOUT_MS`, is passed through unvalidated and throws where the libp2p node is constructed — the `NetworkConfig` field's doc says so, so an embedder knows where the throw comes from.

Upstream context: Optimystic GitHub #22, reported by a sereus-based chat app.

Both builders take a named declarations object — `controlClusterPolicy({ enrolledMachines?, cohortQueryTimeoutMs? })` and `strandClusterPolicy(clusterSize, { servingMachines?, cohortQueryTimeoutMs? })` — and return their frozen base object **by identity** when nothing is declared, which is the production path for both networks today. That shape came out of the review pass; see below.

## Review findings

Read the implement diff (`21915884`) before the handoff summary. Checked: the threading on both networks and across a hibernation wake; the frozen-policy identity path; Optimystic's own `resolveCohortQueryTimeoutMs`, `MAX_COHORT_QUERY_TIMEOUT_MS` (about 4.97 days) and `reconcilePassTimeoutMs` against every claim the comments make about them (all accurate, including the 2.6x first-sync margin, the 25 s derived pass bound, and the 3000 ms fallback arithmetic); every other `createLibp2pNode` caller and every hand-built `clusterPolicy` in the repo; the docs the change touched and the ones it did not.

**Major — interaction the change did not weigh (filed).** Raising the per-peer deadline 1000 → 5000 also raises Optimystic's derived whole-pass bound, `max(5000, 5 x per-peer)`, from 5000 to 25000 ms. Six cadre-core deadlines that wrap an Optimystic read or commit were sized against the old pair and now sit below the new one; only the 120 s first-sync budget was weighed, and its own comment says so. Two consequences are already true, not hypothetical, and were verified by reading the code:

  - The inbound membership admission gate reads the control database **uncached** (`isAuthorizedMember` → `listAuthorizedMembers`, no cache in that path) and fails open after 2 s (`ADMISSION_DECISION_TIMEOUT_MS`). A read whose consult finds one silent peer now cannot settle inside that deadline at all, so on the very deployment this change targets the gate's answer is always the fail-open one: an unplaced peer is admitted at the connection layer for about 5 s instead of about 1 s. It is admitted to nothing more than a connection — the per-protocol stream gates still refuse it every members-only protocol, and unplaced relay reservations stay capped at 8 — so this is a widened cost of a deliberate fail-open posture, not a hole.
  - `CONTROL_READ_RETRY_BUDGET_MS` (1500 ms) is checked *between* attempts, so a first attempt that burns the 5 s deadline overshoots the whole budget and the loop stops. The `cohort-unreachable` case that retry was widened to cover is now unreachable; the ~25 ms transactor-aggregate case it was built for still retries.

  Root cause is neither number but the missing record: the ladder between cadre's deadlines and Optimystic's has no owner and no check, and the four remaining sites are unexamined. Filed as `backlog/debt-cadre-deadlines-sized-against-old-optimystic-bounds` (rung 3 — a boundary invariant at the cadre/Optimystic seam — rather than six point tickets), with the two verified consequences also recorded at the code sites where a reader meets them: a new paragraph on `COHORT_READ_DEADLINE_MS`, and a `NOTE:` on `CONTROL_READ_RETRY_BUDGET_MS`, whose own doc already said "do not raise these numbers without re-checking against `ADMISSION_DECISION_TIMEOUT_MS`" and now says the obligation runs both ways. Checked and cleared: `strand-formation-protocol.ts`'s 5 s per-step budget bounds one bare wire read/write, not a database read, so it is not a new interaction; `debt-relay-reservation-decision-repeatable-cost` touches the same file but resolves at a different site, so this is not an arm of it.

**Minor — representation, fixed inline.** The builders had grown to three positional `number` parameters, two of them optional, and one call site already needed `strandClusterPolicy(size, undefined, 12_000)`. All three are `number`, so a transposition compiles and lands either a 5 ms read deadline or a repair yardstick of 5000 on a real node; a fourth number is already queued (`backlog/feat-strand-yardstick-from-serving-machines`). Replaced with one named declarations object per builder — each keeps its own count name, for the reason the original comment gave — and the two shared bodies extracted into one private `declarePolicy`. Both call sites now read as named fields, which let two multi-line comments that narrated *which argument was which* be deleted. `Object.freeze`, the `satisfies`, the independent spreads and the identity return are unchanged.

**Minor — tests at the wrong layer, fixed inline.** `plugin.spec.ts` already owns a `describe('controlClusterPolicy / strandClusterPolicy')` block testing the builders directly; the implement pass added nothing there and instead pinned four builder contracts in cadre-core by constructing a `CadreNode` or a `StrandInstanceManager` to reach a pure function two packages away. Moved: the base-by-identity case (now genuinely load-bearing, because every call site passes an object whose fields may both be `undefined`), the count-and-deadline-together case, and the "5000 exceeds Optimystic's 1000" anti-tidy assertion, which had been duplicated in both cadre-core specs. Two tests cut outright — "keeps the frozen policy by identity when a network block declares no deadline", once per network — because `network?.cohortQueryTimeoutMs` yields `undefined` whether the key is absent or the block is `{}`: they took the same branch as tests already present and guarded against an implementation (`'cohortQueryTimeoutMs' in network`) that nothing has. Two assertions added where they pay: that a caller declaring only a machine count still carries the declared deadline through the base spread, which nothing covered. Net 6 new cadre-core tests → 3 (two wiring tests, one extended shape test), plus 3 new and 2 extended at the builders' own layer.

**Minor — docs, fixed inline.** `docs/reference-app-rn.md` carries a run of "already widened, for every node" paragraphs — the ping deadline, and the first-sync wait added by the ticket that landed one commit earlier. This change is the third member of that set, on the page about phones through relays, and was missing; added. `cadre-cli`'s config `network` block exposes plain-number tuning fields (`unauthorizedRelayReservationCap`) but had no way to set this one, so an operator running the headless CLI on a link unlike the measured one could not reach the knob the ticket exists to provide; added to both config shapes (pure structural passthrough — `loader.ts` assigns `network` whole — so no test, per the no-testing-glue rule). Also trimmed the "re-measure the first-sync band before raising" instruction in `COHORT_READ_DEADLINE_MS`'s comment, which was stated twice in the same comment.

**Answering the question the handoff asked** — whether the reviewer could see a way to make this assertable that the implement pass missed: **no, and the reasoning holds.** The effect lives entirely inside Optimystic's read path; what sereus can assert is that the declaration is made, that it exceeds the upstream default, and that a host's value reaches both networks, all of which is now pinned at the right layer. The remaining candidates were considered and rejected: the `satisfies` clause already gives compile-time key checking, so an upstream rename cannot survive typecheck; feeding the policies through Optimystic's own `resolveClusterPolicy` would pin validation bounds that 5000 is nowhere near; and on the one topology that can be built locally both values pass at 900 ms one-way delay, so the only difference is a debug-log-line count. `docs/testing.md` records the recipe and why no scenario gates it.

**Conditional/speculative — nothing new parked.** The two tripwires the implement pass left (the first-sync coupling on the constant, the absent override on the plugin's own connect path) were read and both say enough for the reader who meets them; the second was corrected to the builder's new call shape. No accepted-tradeoff `NOTE:` at any finding's site had its revisit condition tripped, and the one at `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS` (what 120 s costs) was left alone.

**Source hygiene — nothing to act on.** `cluster-size.ts` is 597 lines, up from 549, which is within what this file's density of recorded rationale has always cost; no narrated-statement comments survive the two deletions above. The single `docs/architecture.md` bullet the change extends is now very long, but that shape predates this ticket and splitting it is not this ticket's work.

## Known gaps carried forward

- **The decline-count measurement was not re-taken.** 18 declines at 1000 ms and 2 at 5000 ms come from the reproduction pass of the preceding `fix/` ticket (2026-09-26, one Windows machine, blind-relay topology, one-way delay raised to 900 ms after formation). Those logs have been pruned; the numbers in `COHORT_READ_DEADLINE_MS`'s comment are now the record, and no committed instrument can re-verify them.
- **No committed scenario gates the deadline**, by design and after a second look — see the answer above. `docs/testing.md` → "Where measurements live" holds the recipe and the shape to build if it is ever re-measured, plus the one fixture change that needs to land first (`backlog/debt-relay-scenarios-never-see-link-latency`).
- **Every integration scenario now runs at 5000 ms**, because the harness passes the frozen constants directly. Four of the most exposed have been run across the implement and review passes. Any scenario that asserts a *duration* against a deliberately silent-but-connected peer is worth a second look, since a consult against one now costs 5 s rather than 1 s.
- **The degenerate-value path is untested**, deliberately: passing `0` or `NaN` through to Optimystic's throw is a non-behaviour, and a future reader who adds a check here would break the `NetworkConfig` doc's promise about where the throw comes from without failing anything.
- **The follow-on audit is filed, not done** — `backlog/debt-cadre-deadlines-sized-against-old-optimystic-bounds` still owns four unexamined cadre-core deadlines.
