# Phone kit: the identity's peer id without a node, and the join's later phases

Kit side of the "join an existing cadre" screens (the screens are `reference-app-rn-joins-existing-cadre`).

## What landed

- `PhoneNode.identityPeerId(): Promise<string>`: answers at once from the node while `running` or `joining`; otherwise, in the kit's transition queue, loads or creates the identity key from the kit's secure-store key store under `DEFAULT_IDENTITY_KEY_ID` (the same slot `buildPhoneNodeConfig` passes as `identityKeyId`) and returns `publicKey.toString()`, which is the peer id string. That avoids adding `@libp2p/peer-id` as a direct dependency.
- `PhoneJoinProgress` = cadre-core's `CadreJoinProgress` plus `{ state: 'admitted'; grantsOwner }` and `{ state: 'moving-strands' }`. `admitted` is emitted after redemption in both the in-place and switch paths. `moving-strands` is emitted only on the switch path when this join recorded a move and the owner key was wired. Kit-emitted events go through `reportProgress`, which logs a throwing listener. cadre-core guards its own emits the same way.
- README rows and the join example are updated.

## Review findings

Read the diff from `ticket(implement): phone-kit-identity-peer-id-and-join-phases` first, then the surrounding `node.ts` (`inTurn`, `buildConfig`, `settleJoinMove`, `ownerPublicKey`), cadre-core's `loadOrCreateIdentityKey` and `CadreNode` identity loading, and cadre-core's `redeemInPasses` progress reporting.

- **Correctness, identity:** The key slot and key store match what the node's start uses (`config.ts` sets `identityKeyId: DEFAULT_IDENTITY_KEY_ID`, and `keyStore` is the same `SecureStoreKeyStore` instance). Running the read inside `inTurn` means a concurrent first start cannot generate a second key. The fast path skips the queue, so a screen does not wait behind a join that is waiting for a member. Errors from the store propagate rather than regenerating. No defect found.
- **Correctness, progress:** `moving-strands` is gated on `owner === 'enrolled'`, which is the same condition under which `settleJoinMove` adopts. `admitted` is emitted before owner wiring, so a later wiring failure leaves the listener having seen `admitted` before the join throws. That is acceptable because the call's rejection is the final word. The README claim that a throwing listener is ignored holds for both kit-emitted and cadre-core-emitted events (cadre-core's `reportProgress` in `cadre-invite-protocol.ts`). No defect found.
- **Type safety / API:** `PhoneJoinProgress` is a widening of the listener's parameter, and passing it to cadre-core is assignable. It is exported from `phone-node/index.ts`. Nothing to change.
- **Tests:** The one new test (identity read before the first start equals the started node's peer id) pins the cross-path contract and the `publicKey.toString()` = peer id equivalence. It is kept. Progress events after admission cannot be reached by the in-process harness, as the implementer noted. Adding a test for them would mean mocking the repo's own `CadreNode`, so none was added.
- **Docs:** README was already updated. `docs/architecture.md` → "An app joins an existing cadre" now says, in its per-app-identity bullet, that `identityPeerId()` reads the peer id before any party is started (fixed inline).
- **Size / hygiene:** `node.ts` is about 1000 lines. The existing `NOTE:` tripwire at the join section already covers splitting it, so nothing new was filed. New comments state reasons (why the fast path exists, why the listener is guarded) and do not narrate the code.
- **Major / tickets / tripwires:** None. There was nothing that needed a ticket or a new tripwire.
