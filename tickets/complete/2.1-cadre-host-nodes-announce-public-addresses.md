# Hosted nodes announce their public addresses

Second of three (`cadre-host-nat-per-node-mappings` → this → `cadre-host-node-reachability`). Design: `docs/cadre-host.md` → "Public addresses reach the node" and "Respawn" → "An address restart is not a crash".

## What landed

- **At spawn.** `HostProcessConfig.announceAddrs(containerId, ports)`, a synchronous hook the orchestrator asks once per spawn (`announceAddrsFor`). A non-empty result reaches the child as `CADRE_APPEND_ANNOUNCE_ADDRS`, which adds to the LAN addresses rather than replacing them. A throw is logged and the node starts with no public addresses. The list is kept as `announcedAddrs` on the handle, in `state.json` and in `/api/nodes`.
- **Stale detection.** `nat/address-watch.ts` (`AddressWatch`). `NatService.publish()` ends every pass and settings write: it fires the change listeners, then compares each running node's `announcedAddrs` with `publicAddressesFor` as sets and calls `onNodeAddressesStale` listeners, at most once per node per 10 minutes (`NAT_ADDRESS_RESTART_MIN_INTERVAL_MS`).
- **Restart.** `DonationSupervisor.restart(id)` runs on the supervisor's serialization queue, stops a running supervised node and calls `DonationService.respawn(id, { countAttempt: false })`, which leaves the attempt counters and `updatedAt` alone. `bin/host.ts` sends the owner node to `restartOwnerNode()` only in the founder role.
- **Hostname guard.** `NatStore` refuses a DDNS hostname that is not an RFC 1123 name (`isDnsHostname`), and `buildPublicAddresses` ignores one already in a hand-edited `nat.json`, because one malformed announce entry stops a child from starting.
- **Full DDNS name (added in review).** `DdnsProvider.qualifyHostname`; `putDdns` stores DuckDNS's bare `foo` as `foo.duckdns.org`.

Validation (implement): cadre-host typecheck/test/build, `yarn lint`, integration-tests typecheck, four cadre-host integration scenarios (31/31), and a hand-run real `cadre-cli` child whose `/status` listed the two public addresses beside its LAN ones. Review re-ran typecheck, unit tests (64 files, 626 passed, 4 skipped by pre-existing `skipIf`), build and `yarn lint`: all clean.

## Review findings

Read the diff of `ticket(implement): cadre-host-nodes-announce-public-addresses` before the handoff, then the surrounding code in the orchestrator, NatService, DonationService/Supervisor, the DDNS provider and `bin/host.ts`.

**Checked and fine (no change):**

- *Restart repeats.* An address restart could loop if a respawn came back on new ports, since the router would again grant an unpredicted port. It does not: `stopContainer` keeps the handle, `createContainer` reuses the dropped handle's ports (`reusedNodePorts`), and the existing route is matched by internal port within the 3-minute unmap grace, so the respawned node announces the granted port and is not restarted again. The first nat-service test covers this.
- *Startup ordering.* `NatService.start()` awaits gateway discovery and IP detection before its first pass, so re-attached nodes are not compared against empty addresses at boot. Nodes spawned before `start()` resolves get `[]` from the late-bound hook and are restarted once; documented as a cost in the handoff.
- *Serialization.* `restart` re-reads the record on the supervisor queue; the exit event that `stopContainer` raises queues a reconcile pass that runs after the restart and finds the new child running. `disposed` is honoured.
- *`nat.json` load.* `NatStore.load` does not call `validate`, so the stricter hostname check cannot stop an existing host from starting; the resolver guard covers a hand-edited file.
- *Docs.* `docs/cadre-host.md` and `docs/reference-app-rn.md` match the code; anchors resolve. README's `/api/nodes` line needs no change.
- *Tests.* The four added tests each pin a specified behaviour with branching (stale-only-differing-node, rate-limit boundary, uncounted restart, malformed hostname). Kept all; none restates a mock.
- *Security.* Announce entries come only from validated settings and router responses; no new input surface.

**Found and fixed in this pass:**

- *DuckDNS bare subdomain announced as an unresolvable name (wrong-result, reachable now).* The handoff flagged it: DuckDNS accepts `--hostname foo`, but the node announced `/dns4/foo/...`. Added `qualifyHostname` to `DdnsProvider` (`nat/ddns/index.ts`, DuckDNS adds `.duckdns.org`), used in `NatService.putDdns`. The existing nat-service DDNS test now puts `foo` and expects `/dns4/foo.duckdns.org/...`, which reproduces the defect without a new test. Docs bullet added under "Public addresses per node". An externally managed hostname is still stored as typed, which is what the user asserted.
- *Stale `NOTE:` in `DonationService.applySeed`.* Its revisit condition was "a second `respawn` caller appears", which this ticket met: the address restart respawns a child that is still up, so the NOTE's claim that a concurrent respawn means the seed fetch would have failed no longer holds. The conclusion still holds because both spawns share the workdir (and `stopContainer` waits for the old process to exit before the respawn reads it). Rewrote the NOTE to rest on that alone, keeping the "if respawn stops sharing the workdir" trigger.

**Tripwires (already parked by the implementer, re-checked):**

- Failed owner-node address restart leaves the owner node down: `NOTE:` at the listener in `bin/host.ts`.
- `nat-service.ts` is 889 lines (`wc -l`); its `NOTE:` says to move the mapping table out when the next capability lands. This ticket's capability went into `address-watch.ts`, so the move is not yet due.
- Mapping that fails and later recovers costs two restarts per node (rate-limited): described in the docs ("a flapping router costs each node at most one restart per window").

**Not filed:** nothing met the filing bar. Owner restart not serialized against `POST /api/nodes/owner/restart` is covered by `refuseRespawnOverLiveChild` and the tripwire above.
