# Relayed connections try a WebRTC upgrade in the background

## What landed

`webrtc-upgrade.ts`, in two parts:

- **`decideWebrtcUpgrade`**, pure: given this node's and the remote's peer ids, the kinds of every open connection to that peer, the remote's identified listen addresses, whether this node publishes a WebRTC address, and the peer's backoff deadline, it answers "attempt, at this address" or "no, for this reason" (`not-relayed`, `already-direct`, `no-webrtc-addr`, `remote-dials`, `in-backoff`). `nextWebrtcUpgradeBackoffMs` sits beside it as the second pure rule: the wait a peer's next failure puts in force, 1 minute doubling to a 30-minute ceiling.
- **`WebrtcUpgradeService`**, the wiring: subscribes to `peer:identify`, judges each one, dials at most one upgrade per peer at a time through `peer-dial.ts`'s `dialAddr` (not `node.dial`, whose queue would join the dial to another caller's relayed dial of the same peer and report a success that upgraded nothing), and holds the per-peer backoff deadline in memory.

Installed on the control node (`cadre-node.ts`, beside `startControlBackfill`, stopped in `cleanup`) and on every strand node (`strand-instance-manager.ts`, beside the peer redial, stopped first in `releaseRuntime`). Inert on a node that cannot dial WebRTC, judged by whether the node serves `/webrtc-signaling/0.0.1` — one constant that `control-protocol-guard.ts`'s class table also uses, verified against the installed `@libp2p/webrtc` 6.0.33 (`dist/src/constants.js`).

`start()` also judges the peers already connected, from their peer-store addresses, because the control node is armed at the end of `CadreNode.start()` and the control database bring-up before it has already connected to every reachable sibling — whose `peer:identify` will not come again until one of them changes addresses.

The dial budget is `link-budget.ts`'s `webrtcUpgradeDialBudgetMs`: `WEBRTC_SIGNALING_ROUND_TRIPS` (9) at the declared link, plus two admission allowances, plus a flat `ICE_NEGOTIATION_ALLOWANCE_MS` of 25 s — 60.5 s at the default. Deliberately longer than the roughly 23 s the WebRTC stack takes to give up on its own: nothing waits on this dial, so the only way to lose by the deadline is to cut a slow working negotiation off.

Docs: a "Relayed connections are upgraded in the background" subsection and one new limit in `docs/network/relay.md`, a row in the budget table in `docs/network/deadlines.md`, and the rewritten coverage row in `docs/contributing/topology-coverage.md`.

## Review findings

The implement commit is `ticket(implement): relayed-connections-try-a-webrtc-upgrade`. The diff was read before the handoff summary, and the mechanism was confirmed to be the cause of the scenario's direct connections rather than some dial happening to pick the WebRTC address: re-run under `DEBUG='sereus:cadre:webrtc-upgrade'`, one side logs `remote-dials`, the other logs `upgraded <peer> to the …/p2p-circuit/webrtc/p2p/<peer>` address, and both then log `already-direct`.

### Fixed in this pass

- **A dropped direct connection is never replaced while the relayed one survives, and the handoff recorded this as covered.** The handoff listed "a dropped WebRTC connection being re-evaluated on the next identify" among the things verified by inspection. There is no such identify: libp2p runs identify per new connection and on an address push, never on a timer, so after an ICE consent failure on a network that is otherwise still up, that peer stays relayed until it reconnects or publishes new addresses. Traffic keeps flowing over the relay throughout, so this costs speed, not reachability — recorded as a tripwire at the trigger's doc in `webrtc-upgrade.ts` and as a limit in `docs/network/relay.md`, with `connection:close` named as the second trigger to add if peers are seen stuck relayed.
- **The backoff ladder had no test, and could not get one.** `noteFailure` held the doubling and the ceiling inside the service, where the only way to observe them was a log line. Extracted as `nextWebrtcUpgradeBackoffMs`, which is where the module already says its rules belong ("Pure, so the rules that carry the judgement are testable without a libp2p node"), and table-tested: the first wait, one doubling, and a 20-failure climb asserting the ladder never overshoots the ceiling and holds there. `Math.min` is the kind of clamp an edit silently turns into a `Math.max`.
- **`webrtcUpgradeDialBudgetMs` was the one budget `link-budget.spec.ts` did not pin.** That file asserts every other budget's derivation, and has a dedicated case for exactly this shape — that a flat allowance must not scale with the declared link, so a slow-link declaration does not inflate it. Added the matching case for the upgrade dial, plus the assertion that ICE's allowance stays above the stack's own give-up time, which is what makes the deadline a backstop rather than the thing that ends an attempt.
- **`start()`'s already-connected pass could raise an unhandled rejection.** `void this.considerConnectedPeers().then(log)` had no rejection handler, while `consider` catches its own for the stated reason that an unhandled rejection is what a libp2p listener produces. Same treatment applied to the start path.
- **`canDialWebrtc` was exported with no consumer.** Made module-private. With the two backoff constants now imported by the spec and the two round-trip constants by `link-budget.spec.ts`, the ticket's six new entries on knip's unused-export list are down to one: `WebrtcUpgradeSkipReason`, which has to stay exported because it names the reasons in the exported `WebrtcUpgradeDecision` union. Repo-wide unused exports 101 to 96.
- **Five of the unit spec's 19 cases were strictly weaker duplicates.** The first table's declining rows for `['direct']`, `['relayed','webrtc']`, `remoteAddrs: []`, the higher-peer-id tie-break and a running wait repeat, with the same inputs, rows of the reason table below, which asserts `attempt: false` *and* the reason. Cut, with a line saying where the declining cases are asserted. The distinct inputs that happen to share a reason (an empty connection set, a `['webrtc']`-only set) were kept.
- **`hasWebrtcTo` and `hasRelayedTo` in the scenario differed only by a transport literal.** Folded into one `holdsTransportTo(node, peerId, transport)`.

### Checked and found sound

- **The three deviations the handoff asked to be weighed all hold.** `dialAddr` over `node.dial`: libp2p's `dial-queue.js` does join by peer id regardless of the address named, and `force` does not bypass it, so the handoff's reasoning is right; the relayed-outcome branch in `noteOutcome` is a guard against a future move back to `node.dial` and is worth its five lines. Collapsing "identify arrived on a relayed connection" and "no direct connection open" into one `openConnections: AddrKind[]` input is sound — the identify's own connection is necessarily in that set — and it is what lets the already-connected pass reuse the same function. The already-connected pass is needed for the reason given.
- **The tie-break cannot deadlock or double-dial outside the window already noted.** Both sides reach the comparison only when both publish a WebRTC address (a side that publishes none is never a dial target, because the other side finds no `webrtc` address for it), and they then compare the same two strings with `>`, so exactly one dials. The asymmetric case — one side publishes a WebRTC address, the other has the transport but no listener — resolves to a single dialer, not two.
- **An upgrade over a capped relay works, and the relay named in the address does not matter.** Read in `@libp2p/webrtc`'s `initiateConnection`: it opens the signalling stream with `runOnLimitedConnection: true`, and it reuses *any* existing connection to the target peer rather than dialing the circuit address, so picking the first WebRTC address in identify order is correct even with two relays.
- **`dialAddr` really does refuse to stand the relayed connection in for the WebRTC address.** `Connection.direct` is a real field on `@libp2p/interface`'s `Connection` (`false` for a relayed one), so `reusableConnection`'s branch is reached and returns `undefined`, and the dial proceeds. Without that the whole feature would be a no-op; the integration arm confirms it end to end.
- **Resource cleanup.** One `AbortController` and one timer per attempt, both released in `finally`; `stop()` aborts every attempt in flight and unsubscribes, and is idempotent. The strand service is registered in `webrtcUpgrades` *before* the awaited database phase, so the `!isCurrentRuntime` rollback path reaches it through `releaseRuntime`. `CadreNode.start()` is guarded against re-entry, so the control node cannot install two.
- **Comment density is house style, not an outlier.** `webrtc-upgrade.ts` is 208 comment lines to 187 code lines (ratio 1.11), against 1.44 for `peer-dial.ts`, 1.17 for `peer-join-backfill.ts` and 1.02 for `relay-reservation.ts`, each measured with the same `awk` line classifier. The overlap with `docs/network/relay.md`'s new subsection was weighed against "one home per fact" and left: the doc states the mechanism, the module doc states libp2p-internal reasons the doc correctly omits. 417 lines total is well inside the file sizes around it.
- **Arithmetic.** `WEBRTC_SIGNALING_ROUND_TRIPS` is 5 + 2x2 = 9; the budget is 9x3500 + 2x2000 + 25000 = 60,500 ms, matching the `deadlines.md` row. The flat ICE allowance keeps the budget above the stack's give-up time at every declaration, fast links included.

### Found and deliberately not filed

- **The control-node install site is exercised by nothing, and cannot easily be.** Confirmed from the debug run: both parties' control nodes log `started (0 peer(s) already connected)` and then nothing until `stopped` — no judgement at all. Optimystic names identify per network, so two parties' control nodes never identify each other and are never candidates. What the site covers is a party's own machines reaching each other through a relay, plus a device redeeming an invitation into the party; a scenario for that is a multi-machine fixture, not a defect in this ticket's work.
- **The already-connected pass is still verified by inspection only.** Exercising it needs a libp2p double carrying `getProtocols`, `getConnections`, `peerStore.get`, `getMultiaddrs` and `components.transportManager.dial` — a test that would assert the pass reads the peer store, which is wiring at the layer where a reviewer is told to cut tests rather than add them. The reasoning it rests on (the control node is armed after the database bring-up has already connected to its siblings) was re-read and is right.
- **`canDialWebrtc` tolerating a node with no `getProtocols()`** is production code shaped by test doubles (9 unit-spec files build libp2p doubles without it). Left as it stands: it is the fail-safe answer, it reads the node structurally exactly as `peer-dial.ts` and `relay-reservation.ts` do, and the alternative is editing nine specs to satisfy a probe only this module makes.
- **`attempt()`'s `withTrailingPeerId`-returns-null branch records no backoff,** so a peer publishing an address that ends in someone else's id would log on every identify. Not reachable: identify strips the trailing peer id, and peer-store addresses for a relayed peer end in `p2p-circuit`.
- **The load flake the handoff recorded did not recur.** `cadre-node-owner-grant.spec.ts` "a member redeeming locally while alone is refused by name" passed in two further full `@serfab/cadre-core` runs here (four green full runs across both passes). Written to `tickets/.pre-existing-known.md` as a `one-off` so the next agent does not re-triage a phantom; nothing written to `.pre-existing-error.md`.
