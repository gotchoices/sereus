# Optimystic floors `^0.18.0` → `^0.19.0` — landed, gate green, stale docs corrected

## What shipped

All 24 declared `@optimystic/*` ranges across the seven consuming `package.json` files moved from
`^0.18.0` to `^0.19.0` (implement commit `2c81f0b`), plus the matching `yarn.lock` entries. Nothing
else moved in the lock. `yarn check:dep-ranges` reports zero too-old ranges.

Review pass then corrected the documentation and ticket text that still described the pre-bump
world (details under *Review findings*).

## Review findings

### Checked and clean

- **The diff itself.** All 24 declarations enumerated by grep across `packages/*/package.json` and
  root `package.json`; every one reads `^0.19.0`, none missed, no `@optimystic/*` left in any
  `devDependencies`/`peerDependencies`. Linked `../optimystic/packages/db-core` is at `0.19.0`, so
  the declared floor now equals what we link.
- **Lock hygiene.** `yarn.lock` `@optimystic/*` entries are all either `link:` resolutions
  (unversioned) or `npm:^0.19.0`. No transitive drift.
- **The 22-vs-24 discrepancy is explained, not a defect.** The gate reports 22 because it only
  checks ranges whose package is a root `resolutions` `link:` target; `db-p2p-storage-fs` is not
  one, so its two declarations are ungated. Both were bumped anyway. See the tripwire below.
- **Build.** `yarn build` at repo root, exit 0 — including `reference-app-web`, whose production
  Vite bundle the implement handoff reported as broken (see *Resolved before this pass*).
- **Gates.** `yarn lint` exit 0, `yarn typecheck` exit 0 (incl. both coverage checks), `yarn
  dep-check` exit 0, `yarn test:dep-ranges` 9/9, `yarn test:published-smoke-support` 22/22.
- **Tests.** `cadre-core` 1501 passed / 5 failed — the 5 are the ledger-tracked
  `10-revocation-reissue-same-pk-update-unique-collision` Quereus DML defect, unchanged.
  `cadre-cli` 210/210, `cadre-host` 601 passed / 4 skipped, `cadre-provider` 201/201, all green —
  these four were *not* verified by the implement pass, which only checked their builds, so this
  closes the gap it flagged. `quereus-plugin-sereus` 75–77 passed with 1–5 red in
  `test/e2e/networked.e2e.spec.ts` across three consecutive runs, every failure the ledger's
  documented `Missing block (<id>)` fingerprint → `blocked/control-coordinator-answers-absent-without-asking-cohort`.
  Not re-filed. The run-to-run spread (1, 2, 5) sits above the ledger's "~1 per run" band but is the
  same fingerprint class the ledger already calls a routing race, and it cannot be caused by this
  ticket — see next bullet.
- **Why no test in this repo can regress on this change.** Every `@optimystic/*` import resolves
  through root `resolutions` `link:` to `../optimystic`, so the declared ranges are never consulted
  at test time. Only `yarn check:dep-ranges` and `yarn smoke:published` exercise them. A
  range-only diff is therefore inert to the suites; test noise above is orthogonal.

### Found and fixed in this pass — stale documentation

The implement handoff judged the remaining `^0.18.0` mentions to be "dated historical records". Four
of them were not: they were present-tense claims about the repo's current state, false the moment
the bump landed, and three pointed at a ticket path (`tickets/implement/0.15-…`) that no longer
exists.

- `docs/releasing.md` "Dependency floors" — said the gate "is red on 22 ranges until they move" and
  pointed at `tickets/implement/0.15-…`. Rewritten to past tense, now records that all 24 moved and
  which two the gate does not cover.
- `docs/releasing.md` runbook step 2 — said "It is red today" and pointed at the same dead path.
  Now says the floors already sit at `^0.19.0` and the gate is green.
- `docs/releasing.md` "Why a minor bump" — said the layer "moved two minor versions
  (`^0.14.1` → `^0.19.0`)". That is five, not two. The implement pass noticed the arithmetic was
  wrong and deferred it as pre-existing; it is a one-word fix and the sentence's whole job is to
  justify a minor bump, so it was corrected here.
- `docs/STATUS.md` ×2 — "at the `^0.18.0` floor this repo declares", present tense, in the
  `yarn smoke:published` and "What this means for publishing" sections. Both now read `^0.19.0`.
  The surrounding claim (a registry install throws `Cannot find package 'chai'`) is unaffected —
  STATUS itself records that the break is present in `0.19.0` too.
- `docs/STATUS.md` "The declared floors do move" — future tense plus "currently red (22 ranges)"
  plus the dead `tickets/implement/…` path. Now past tense, points at `tickets/complete/…`.
- `tickets/blocked/cut-the-interim-release.md` — told the human reader the guard check "is red
  until the edit lands" and to land `implement/0.15-…` before starting. That is a decision ticket a
  human reads to act on, so a stale instruction there is the most expensive kind. Now says the edit
  landed and there is nothing to do first.
- `tickets/blocked/optimystic-testing-barrel-breaks-consumer-install.md` — its list of affected
  upstream versions stopped at `0.18.0` and it said the declared minimum was corrected "to
  `0.18.0`". `0.19.0` ships the same broken import (already recorded in `docs/STATUS.md`), so the
  list and the minimum were both extended. This matters because the ticket's whole subject is which
  published versions are installable.

### Tripwire recorded, not filed

`@optimystic/db-p2p-storage-fs` is the only optimystic package absent from root `resolutions`, so
it resolves from npm while its eight siblings resolve to `../optimystic` — and since
`scripts/check-dep-ranges.mjs` only walks `link:` targets, its declared range is ungated. Benign
today (published `0.19.0` is the same commit we link) but it means local edits to that package are
invisible to `cadre-cli` and `quereus-plugin-sereus`. Parked as a `NOTE:` bullet in `docs/STATUS.md`
beside the dep-range gate description, since the concern is about the gate's coverage and has no
single code site (root `package.json` is JSON and cannot carry a comment).

### Resolved before this pass — no ticket needed

The implement handoff filed `tickets/.pre-existing-error.md` for a `reference-app-web` production
build failure (`Rollup failed to resolve import "temporal-polyfill"`) and asked the reviewer to make
sure it got a `fix/` ticket. The runner's triage agent already handled it (commit `fa0b73c`) and
found it was **build drift, not a defect**: `../quereus` was mid-`yarn build` in a sibling repo when
the implement pass measured, so its `dist/` was half-written. Re-run at HEAD, `yarn build` exits 0 —
confirmed independently in this pass. `temporal-polyfill` resolves fine through the `link:`
realpath into `../quereus/node_modules`. Correctly no ticket filed.

### Not covered, deliberately

`packages/integration-tests` was not re-run. It exceeds the runner's 10-minute idle window (the
implement pass needed six batches), its failures are known multi-machine routing races that move
between runs, and — per the "why no test can regress" bullet above — a range-only diff cannot reach
it. The implement pass ran it at 241 tests, an exact match to the 2026-08-03 baseline count, with no
new failure fingerprint. Nothing further is learnable from a re-run at this cost.

`../quereus` and `../optimystic` were not touched. `../quereus` carries someone else's in-flight
uncommitted work.
