# The reference apps mark a message that is not yet delivered (complete)

Applies the prereq's API (`StrandDatabase.commitDurability(tx)`, `CadreNode` event `strand:commit-held`; contract in `docs/strands.md` → "A commit's durability") to the three reference chat apps. A message this device sent whose commit no other member holds shows a "Not yet delivered" label; the label clears when `strand:commit-held` names that commit.

## What was built

The same shape in all three apps:

- **Write.** The message insert is one statement, `insert into App.Message (…) values (?, ?, ?, ?) returning StampId() as Tx`, run through `db.get`. The web app's `insert or ignore` of the `Participant` row stays a separate statement before it.
- **Mark.** In the same synchronous step that records the mark, the app reads `strand.database.commitDurability(Tx)`. If a report exists and `heldElsewhere` is false, it records a mark `{ strandId, transactionId, messageId }`. No report, or `heldElsewhere: true`, records nothing. A resend that finds the row already stored writes nothing and records nothing.
- **Clear.** On `strand:commit-held`, the app removes the mark that matches both `strandId` and `transactionId`. Marks are keyed by strand, so switching away from a strand and back still shows them, and an event for one strand cannot clear a mark on another.
- **Show.** The label reads "Not yet delivered". Test ids: RN `TEST_IDS.chat.undeliveredMark(id)` (`message-undelivered-<id>`); NS has the same id, set as the label's `automationText`; web `data-testid="message-undelivered"` inside the `message-row` item.
- **In memory only.** There is no persistence. Messages read from storage carry no mark. A mark whose commit is never followed stays until the app restarts (or the web page reloads).

Per app:

- **RN.** `insertMessage` returns `StoredMessage { message, transactionId: string | null }`. The durability decision is the exported `isHeldOnlyHere(strand, transactionId)` in `chat-operations.ts`, which `useChat.send` calls in the same step that records the mark (changed in review; see below). `ChatSender.send` now returns `{ stored, alreadyStored }`, where `stored` replaces the old `message` field. `useChat` takes a new `node` option, keeps the marks in React state, subscribes to `strand:commit-held` in its own effect, and returns `undelivered: ReadonlySet<string>`, the marked message ids of the strand on screen. `app/index.tsx` passes `extraData={chat.undelivered}` to the `FlatList`. Without it, a mark clearing would not re-render the row, because `data` does not change.
- **NS.** `chat-operations.ts` has the same change as RN, and the two files stay parallel (a whitespace-insensitive diff shows no difference in the new lines). `CadreViewModel` binds and unbinds `strand:commit-held` next to `strand:writable` and re-sends it as its own Observable event, `CadreViewModel.commitHeldEvent` (`CommitHeldEventData`). `ChatViewModel` listens to that event, holds the marks, and adds `undeliveredVisibility` and `undeliveredId` to `ChatRow`. When a mark clears, the shown row is replaced with `setItem`. `chat-page.xml` has the label and `app.css` has `.undelivered`.
- **Web.** `insertChatMessage` returns the commit id (`string | null`). `writeChatMessage` ignores it and still returns the message id, so the e2e helper is unchanged. `messages.svelte.ts` holds `state.undelivered` and exports `markDelivered` and `isUndelivered`. `store.svelte.ts` subscribes `markDelivered` to `strand:commit-held` beside its other node events. I chose not to log the event to the Activity list: it fires once per held commit, cadre-core's own writes included, and would push lifecycle events out of the capped log.
- **Docs.** New section `docs/reference-app-rn.md` → "Messages Not Yet Delivered". It covers the mark, the founder-alone reading, and the in-memory limit. The package-structure line for `use-chat.ts` is updated. The "What apps do with it" bullet in `docs/strands.md` links to the new section.

## Review findings

Reviewed the diff of `ticket(implement): reference-apps-mark-undelivered-messages` first, then the handoff, the prereq's contract (`docs/strands.md` → "A commit's durability", `strand-commit-durability.ts`, `StrandDatabase.commitDurability`) and Quereus `Database.get` / `Statement.get`.

**Fixed in this pass (correctness): a mark could be set after its clear and never go away.** On RN the durability read ran inside `insertMessage`, and the mark was recorded several `await` hops later in `useChat.send` (through `ChatSender.send`). On NS there was one hop. The handoff argued nothing could land in between because only microtasks run there. That does not hold: the commit itself completes on network responses, and other promise chains started by those responses run in between our hops, so the `strand:commit-held` emit can fall in that gap. The clear then finds nothing to remove, and the mark that follows stays until restart. `StrandCommitRecord.reportHeld` updates the record *before* it emits the event, so reading the durability in the same synchronous step that records the mark closes the gap. An event that landed earlier shows in the read, and one that lands later finds the mark to clear. On RN, React applies the two `setMarks` updaters in the order they were queued. Changes:
- `chat-operations.ts` (RN and NS, still the same in both): `StoredMessage.undeliveredCommit` → `transactionId` (the commit id, always). The private `undeliveredCommit()` → exported `isHeldOnlyHere(strand, transactionId)`, whose doc comment says it must be called in the same step that records the mark, and why.
- `use-chat.ts` and `chat-vm.ts` call `isHeldOnlyHere` right before they record the mark. The web app's `markIfHeldOnlyHere` already read and recorded in one step; its doc comment now gives the reason.
- `use-chat.spec.ts`: the `chat-operations` mock gains `isHeldOnlyHere`, since the hook now imports it.
- `docs/reference-app-rn.md` → "Messages Not Yet Delivered" now says where the read happens and why.

**Checked, nothing to change:**
- *Single-statement write.* `Database.get` on `insert … returning StampId() as Tx` runs under the exec mutex and commits before it resolves. The prereq's `joiner-first-commit-over-slow-relay.integration.ts` relies on the same pattern. Every other caller of the changed inserts (`solo-smoke.ts`, the web e2e `formation-responder.ts`, `cadre-web.ts` `writeChatMessage`) runs against a real strand database, which registers `StampId()`.
- *Strand scoping.* Marks are keyed by `strandId` and `transactionId` in all three apps. An event for another strand does not clear a mark, and switching strands keeps the marks.
- *Resource cleanup.* RN unsubscribes in the effect cleanup. NS binds and unbinds next to `strand:writable` (`cadre-vm.spec.ts` asserts it). The web store never unsubscribes any node event; that was already the case and is unchanged here. NS `ChatViewModel` subscribes in its constructor, as it already does for `propertyChange`.
- *Reactivity.* RN `extraData={chat.undelivered}` gets a new `Set` only when the marks or the shown strand change. The web template reads `state.undelivered` through a `$state` proxy, so it is tracked. NS replaces the shown row with `setItem`, and rows rebuilt by polling read the marks through `toRow`.
- *Marks that survive a node change, or a commit that is not followed.* These stay until restart. That matches the documented meaning ("not confirmed delivered", not "lost") in the RN doc and the in-code comments, so no change was made.

**Tests:** I added none. The race fix depends on event timing that the unit fixtures cannot produce without faking cadre-core's commit record, and the prereq's integration test covers the chain from the record to the event. The fixture updates from implement are needed for the new statement shape, so I kept them. The NS `setItem` clear path is checked only by the typechecker, as the handoff says.

**Docs:** `docs/strands.md` (link added in implement) and `docs/reference-app-rn.md` are accurate. `docs/reference-app-ns.md` needs no change, since the RN section covers the NS and web apps.

**Tripwires:** none new.
