# Owner signer seam, owner-key slot, and export/import

This is the first owner-key ticket (`docs/architecture.md` → Owner Keys). All of it is new code in `@serfab/cadre-core` and is exported from the package root. `owner-signing-through-one-signer` wires it into the node.

## What landed

- **`owner-signer.ts`**: the `OwnerSigner` interface (`publicKey`, `approve(request, body)`), plus `OwnerSigningRequest`, `OwnerSign` and `OwnerSigningDeclinedError`. `softwareOwnerSigner(privateKeyB64)` signs `base64url(message)` with the crypto plugin's `sign`. That is the input `SeedBootstrapService.signMessageBytes` signs, so the two produce the same signatures.
- **`owner-key-store.ts`**: the owner slot `cadre/owner` (`DEFAULT_OWNER_KEY_ID`). The functions are `createOwnerKey`, `loadOwnerSigner`, `importOwnerKey` and `readOwnerPrivateKey`. A key in the slot is never replaced: an occupied slot refuses with `OwnerKeySlotOccupiedError`, and importing the key already there changes nothing.
- **`owner-key-export.ts`**: plain `sereus-owner-key:1.` and locked `sereus-owner-key-locked:1.` text forms. The lock uses scrypt to derive a key from the passphrase and XChaCha20-Poly1305 to seal the plain form. The encoder's scrypt default is N=2^16, r=8, p=1; the decoder refuses N above 2^20 or r·p above 8 before it runs scrypt. Errors are `OwnerKeyExportError` with a `code`, and no message carries key material.
- **Cross-refusal**: the invitation and join-request decoders refuse owner-key text by name. The owner-key decoder refuses invitations, join requests and machine join codes by name.
- **`requireEd25519PrivateKeyB64`** in `ed25519-key.ts`: validates a seed and re-encodes it in canonical form.
- **New dependency**: `@noble/ciphers`.

## Review findings

Reviewed the `ticket(implement): owner-signer-seam` commits (the salvaged partial and the docs pass) from the diff first, then the handoff.

**Correctness: one minor defect, fixed.**
- `importOwnerKey` over a slot holding bytes that do not decode as a key threw the raw protobuf/type error, while `createOwnerKey` refused the same slot with `OwnerKeySlotOccupiedError`. An app that maps the typed error to "this device already holds a different key" would have shown a generic failure. Both functions were safe already, since neither overwrote the slot; only the error type was inconsistent. The fix: `importOwnerKey` now compares the slot's bytes with the imported key's stored form, which is deterministic for a given seed. Any other contents, unreadable ones included, refuse with `OwnerKeySlotOccupiedError`. It no longer decodes the stored key. A second spec in `owner-key-store.spec.ts` pins this: create and import over unreadable bytes both refuse and leave the bytes in place. The docs Key store sub-paragraph now says so.
- Checked and found sound:
  - Signature parity with `signMessageBytes`: same `sign` call over the base64url of the bytes.
  - `await keyStore.get(...) !== undefined`: the precedence is correct.
  - The canonical seed comparison: multiformats base64url strips padding and rejects non-zero trailing bits.
  - The plain prefix is not a prefix of the locked one.
  - The `N & (N - 1)` power-of-two check uses 32-bit bitwise maths, but it is exact for every N up to the 2^20 cap, and any larger N is refused either way.
  - `SCRYPT_MAXMEM` matches noble's own `128·r·(N+p+1)` check, read in the installed `@noble/hashes/scrypt.js`.
  - `canonicalJson` drops an `undefined` label.

**Security and error handling.** No error message or `cause` carries key material:
- `JSON.parse` is rethrown without its cause.
- uint8arrays' decode errors do not echo their input.
- `requireEd25519PrivateKeyB64` never names the value.

`parseJsonObject` and `lockedEnvelope` do echo a hostile file's `v` and `kdf.name` fields. Neither is key material, so this was left as is. A wrong passphrase and an altered text both refuse as `wrong-passphrase`, because the AEAD (authenticated encryption) check fails.

**Tripwires (already in place, not re-filed).**
- Hermes cost of the scrypt default and cap: `NOTE:`s at `DEFAULT_SCRYPT_COST` and `MAX_SCRYPT_N`. At the cap, a deliberately imported hostile file asks for a 1 GiB allocation. On a low-memory phone that could crash the app rather than just run slowly. The existing NOTE covers lowering the cap if a device run shows this.
- No compare-and-set on the slot: `NOTE:` in the `owner-key-store.ts` header.

**Tests.** All the implementer's specs are kept:
- `owner-signer.spec.ts` pins that the control schema's verify accepts the signer's output.
- `owner-key-store.spec.ts` pins the rule that a key in the slot is never replaced.
- `owner-key-export.spec.ts` pins the round trips, the wrong-passphrase and altered-text refusals, and the cost cap firing before scrypt runs.
- `cadre-invite-protocol.spec.ts` and `cadre-join-request.spec.ts` each gained one owner-key refusal assertion.

None of them restates the implementation or tests a mock. One spec was added, for the defect above. The machine-join-code refusal and the newer-version message are left untested; each is a single branch, and both were checked by reading.

**Type safety, size and hygiene.** There is no `any`. The files are small: export 343 lines, store 85, signer 78. The comments explain constraints rather than narrating the code.

**Cross-platform.** All three modules use pure-JS crypto only. Importing `@noble/hashes/*.js` already has precedent in `claim-proof.ts` and `provider/oauth.ts`. `@noble/ciphers` resolves from cadre-core's own dependency, and the root `react-native` export condition is unchanged.

**Docs.** I read Owner Keys (the signer, key store, export subsection and Status note), Node Key Material & the KeyStore Seam (line ~2261 already names `createOwnerKey`/`loadOwnerSigner` for app-controlled genesis), and both Implementation Status bullets. They are accurate. The Status note still correctly says the node derives its owner key from its identity until `owner-signing-through-one-signer` lands. I also checked the API names that the downstream implement tickets (1.02, 1.06–1.09) expect; they match what shipped. `exportOwnerKey` is a later flow in `owner-key-flows.ts`, not part of this ticket.
