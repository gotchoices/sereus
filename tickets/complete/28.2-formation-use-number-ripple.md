# Sweep of the readers of the dropped `FormationUsage.UseNumber` column

`formation-unique-token-redesign` dropped `FormationUsage.UseNumber` and made `UsageStampId` the
table's primary key. Every remaining reader of the old column lived inside a SQL string or a
`row.X as number` cast, so neither `yarn build` nor `yarn lint` saw them — they would have failed
at runtime (SQL error) or rendered a column of `undefined` in the browser app's diagnostics panel.

## What shipped

- `packages/reference-app-web/src/lib/cadre-web.ts` — `FormationUsageRow.useNumber: number` →
  `usageStampId: string`; the diagnostics query selects `UsageStampId` instead of `UseNumber`.
- `packages/reference-app-web/src/Diagnostics.svelte` — keyed-each key is now `use.usageStampId`
  alone (the primary key, unique on its own), and the rendered line shows a labelled 12-character
  prefix of the stamp with the full value in a `title` tooltip. `data-testid` / `data-count`
  attributes unchanged, so no e2e assertion moved.
- `packages/reference-app-web/e2e/fixtures/formation-responder.ts` — `readFormationUsage()`
  returns `usageStampId: string`, query selects `UsageStampId`. The read-back row shape is now a
  named exported `FormationUsageReadback` interface instead of the same object literal spelled
  out three times.
- `packages/integration-tests/src/scenarios/strand-formation-e2e.integration.ts` — comment only:
  a multi-use token is disambiguated by `UsageStampId`, not the removed `UseNumber`. The
  scenario's query already selected `UsageStampId`.
- `packages/reference-app-web/e2e/distributed/formation-convergence.spec.ts` — no change needed;
  it only reads row counts and `strandId` off the handle.

## Review findings

Read the implement diff (`f5251be`) against the current schema before the handoff summary, then
checked the handoff's own claims. Sweep covered: every source consumer of `FormationUsage`, the
schema definition, the browser app's docs/README, and the specs that assert on the touched paths.

### Fixed in this pass (minor)

- **The read-back row shape was written out three times** in `formation-responder.ts` (handle
  type, function signature, local array), so a fourth column would have to be added in three
  places. Extracted to an exported `FormationUsageReadback` interface with a doc comment saying
  why `usageStampId` is the distinguishing field.
- **The diagnostics line rendered a bare truncated nonce with no label** — `· a1b2c3d4e5f6… →
  strand …`. Every sibling row in that panel uses `· <label> <value>` (`· sApp …`, `· uses …`,
  `· expires …`), and the removed text it replaced was self-describing (`· use #2`). Now reads
  `· stamp a1b2c3d4e5f6… → strand …`, with `title={use.usageStampId}` so the full value is
  recoverable by hover rather than lost to the truncation.

### Checked and found correct

- **The `as string` casts are sound.** `schemas/control.qsql:521-562` declares both `Token` and
  `UsageStampId` as `text not null`, with `primary key (UsageStampId)`. `Token` regained its
  explicit non-nullity in the prereq's own review pass, so neither cast can silently produce
  `undefined`. This also closes the handoff's third stated gap (it did not re-verify the prereq's
  schema) — the schema was read directly here and it matches the new readers.
- **Nothing else reads the dropped column.** Repo-wide grep for `UseNumber` / `useNumber` over
  source (`packages docs schemas`, excluding `node_modules` and the `reference-app-ns` /
  `reference-app-rn` build-artifact trees) returns hits only in `tickets/` prose — no source,
  schema or doc file. Every other `FormationUsage` consumer (`cadre-core`, `integration-tests`,
  `reference-app-rn`, `quereus-plugin-sereus`) either never selected the column or was already
  swept by the prereq.
- **The convergence spec's assertions still mean what they say.** It reads only
  `usageAfter.length` versus `usageBefore.length` and `u.strandId === r.strandId` — never the
  renamed field — so the rename could not have quietly weakened them.
- **Docs are current.** `packages/reference-app-web/README.md:188` describes the panel as showing
  "the `FormationInvite` / `FormationUsage` audit rows" without enumerating columns, and
  `docs/architecture.md` / `docs/STATUS.md` reference the app and the spec but not this column.
  Nothing needed editing — that is a real check, not an omission.

### No new test needed (handoff gap #2)

The handoff flagged that nothing tests the new keyed-each behaviour when two rows share a token.
The invariant the Svelte key depends on — `UsageStampId` is unique — is enforced by the database
primary key and is already covered by three cadre-core specs that assert the exact engine refusal
(`control-formation-invite.spec.ts:1100`, `control-formation-seat-budget.spec.ts:490`,
`strand-formation-consent.spec.ts:658`). A browser-level test of the same fact would re-assert the
database's constraint through a UI, which is a worse place to pin it. Declining to add one is a
judgement, not an oversight.

### Major findings

None. The change is a mechanical column rename with no behavioural surface of its own.

### Tripwires

None recorded. The one candidate — two stamps sharing a 12-character display prefix would render
identically — was considered and dismissed rather than parked: the each-key uses the full value so
list identity is unaffected, only the visible text would collide, and 12 base64url characters is
72 bits of nonce.
