# Verify the schema-init retry engages

## Outcome

Two claims, with very different evidence behind them, and the handoff was honest about
both:

- **The retry wrapper is live on the schema-init path** — proven against a real
  three-process cluster. A debug line was added at the point where the retry loop DECLINES
  to retry; a real provider-started `cadre-cli` child then logged `attempt 1/3` for its
  DDL failure, which only the retry loop can print. Independently re-confirmed by reading
  the call site: `control-database.ts:580` is `await this.lockedWithRetry(() =>
  this.db!.exec(schemaContent))`.
- **The retry absorbs a transient cohort failure** — still unproven. The failure class it
  targets did not occur once in twelve runs of `provider-seed-accepted.integration.ts`, so
  it never had the chance. Every case proving it works drives a stub.

The implementation changes were a single debug line plus test coverage; behaviour is
otherwise unchanged.

## Review findings

### Verified independently (not taken on the handoff's word)

Every reconstructed message constant was checked against `../optimystic` source rather
than accepted as described. All four claims hold:

- `network-transactor.ts:240` (`get`) and `:522` (`pend`) format `[block:<id>]`; `:727`
  (`commitBlocks`) formats `[blocks:<count>]`. The tokens are disjoint as documented.
- `cluster-coordinator.ts:374` raises the super-majority shortfall, and `CoordinatorRepo`
  calls it from `pend` (774), `cancel` (882) and `commit` (916) — so the spec's new claim
  that the same sentence can arrive from either phase is correct, not merely plausible.
- The `SUPER_MAJORITY_IN_PEND_AGGREGATE` constant's "retried twice over" note is right:
  the shortfall regex is unanchored, so it matches the sentence inline in the aggregate
  while the `[block:` matcher claims the same string.

### Fixed in this pass

- **Latent defect: the classifier throws on a non-`Error` link in the `cause` chain.**
  `unwrapError` declares its `message` as `string` but follows `.cause` without checking
  what it holds (`quereus/packages/quereus/src/common/errors.ts:187`). A link that is a
  string or plain object yields `message === undefined`, and `reportsIndeterminateCommit`
  then calls `.includes` on it — a `TypeError` raised from inside `retryControlWrite`'s
  own catch, replacing the real control-write failure with a confusing one. Not
  hypothetical in shape: optimystic sets `aggregate.cause = firstBatchError(batches) ??
  error`, where the batch error is a raw rejection value of type `unknown`, so a stream
  rejected with a non-`Error` reason produces exactly this. Extracted `chainMessages`,
  which drops unreadable links (a link nobody can read matches nothing, which is already
  the conservative answer), and added a spec case asserting the classifier answers instead
  of throwing and still reads the levels that ARE strings. Not filed as a ticket: one call
  site, three lines, fixed here. `repro:` would have been `static` — derived from the two
  sources, not observed in a run.
- **The new log line said something false for one path.** It read `not retried`, but
  lost-use-number constraint failures reach this branch and ARE retried, by
  `ControlDatabase.withUseNumberRetry`, which wraps this loop. Now `not retried here`,
  with the reason stated at the site.
- **The comment on that log was ticket history, not code.** Five lines narrating what the
  verification effort cost, trimmed to the timeless reason the line exists.
- **A spec constant pinned a wire shape the transactor cannot emit.**
  `TRANSACTOR_AGGREGATE_COMMIT_PHASE` read `[blocks:3](no-response) cause=…`.
  `no-response` means the batch has no request at all (`network-transactor.ts:723`), and
  the `cause=` segment is only appended when the batch `isError` — and `Pending.isError`
  implies `isResponse` is false (`db-core/src/utility/pending.ts`), which renders
  `in-flight`. So a detail carrying a cause is always `(in-flight)`. Corrected, with the
  derivation recorded at the constant. Pre-existing, but constant fidelity is the whole
  subject of this ticket family, so it was not left standing.

### Found, deliberately NOT filed as a new ticket

- **The unproven success path** — the handoff's own headline concern.
  `tickets/implement/control-write-retry-scenario-coverage.md` already owns this exact
  site: its section 1 is "assert the classifier against the real super-majority message
  and verify the real aggregate carries `[block:`", and its section 2 is "a transient
  stream reset is absorbed". That IS the bracketed-token question this ticket could not
  settle, plus the success path. Filing a second ticket would have duplicated it. Instead
  an arm was appended there carrying the two things that ticket did not know: that the
  success path is unobserved at *every* call site (so section 2 is the high-value half,
  not the afterthought), and that the shortfall sentence is phase-ambiguous — so a future
  capture must record the whole aggregate, never the sentence alone, which is precisely
  the transcription mistake that left this question open.

### Tripwires parked (conditional — not tickets)

- A cause chain containing a **cycle** would spin forever inside `unwrapError` itself. No
  error in this repo builds one. `NOTE:` at `chainMessages` in `control-write-retry.ts`,
  so a future hang localised to a control-write failure path has a first place to look.
- The decline log fires on **every** non-retriable control-write failure, constraint ones
  included, so a debug-enabled run of a constraint-heavy suite is noisier than before.
  Debug-namespaced and off by default; already noted at the call site by the implementer,
  left as is.

### Checked and clean — stated explicitly rather than passed over

- **Docs.** Read every file describing this mechanism: `docs/architecture.md` line 76
  ("Replication cluster size"), `docs/cadre-consistency.md:28`, `docs/STATUS.md:917`. All
  three already describe the three attempts, the 10 s elapsed budget, the never-retry-a-
  rejection rule, and the `[block:`/`[blocks:` discriminator, and all three are accurate
  against the code as it now stands. This diff added a debug line and test coverage and
  changed no described behaviour, so no doc edit was warranted — not "docs look fine", but
  "the described reality and the code still match, checked line by line".
- **Resource cleanup / error handling.** Nothing acquired, nothing to release; the retry
  loop rethrows the last error by identity (asserted by two existing cases) and never
  wraps.
- **Source size.** `wc -l` gives 319 lines for `control-write-retry.ts` and 519 for its
  spec — well under any split threshold; no size finding.
- **Scope creep.** `reportsIndeterminateCommit` was left untouched, as the ticket
  instructed.
