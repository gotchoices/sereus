# The unclaimed gate in `CadreNode`, and `claimNode` on the owner side

Second of three tickets. `node-claim-proof-and-policy` landed the proof and the policy below `CadreNode`; this ticket wired them into the node (landed in `ticket(implement): node-claim-gate-and-helper`, reviewed here). The cadre-cli surface and the end-to-end scenario are `node-claim-cli-and-scenario`.

## What shipped

- **Configuration.** `CadreNodeConfig.claim?: { secret: string }` (`types.ts`). `start()` refuses `claim` beside a non-empty `trustedOwners.pinnedKeys` or a `seedTrustPolicy` (`validateClaimConfig`, before the anchor is written), then builds the claim policy over the node's anchor right after `initializeTrustedOwnerStore()` (`initializeClaimPolicy`; a malformed secret throws through `parseClaimSecret`, which never echoes the value). The policy is built once per node instance, with `onClaimed` emitting the new `claim:accepted` event, and kept across `stop()`→`start()` like the anchor it writes. `initializeSeedBootstrap` throws on a node with `claim` set.
- **One policy accessor.** `inboundSeedTrustPolicy()` returns the claim policy when configured, else `config.seedTrustPolicy`; the owner service, the listener and `applySeed`'s temp service all read it. A node with `claim` calls `enableSeedListener()` itself inside `start()`, before `control:connected`.
- **`isAwaitingClaim()`** (public): `config.claim !== undefined && anchor.size === 0`, read live from the anchor. False on a node with no claim secret, on a claimed one, and before `start()` has built the anchor.
- **The unclaimed gate.** `authorizeInboundControlStream` and `admitControlRelayReservation` refuse everyone as their first check while `isAwaitingClaim()`, ahead of the empty-anchor and bootstrap-infra admissions. `admitInboundControlConnection` is unchanged: the empty-anchor rule already admits the connection the claim seed rides. After the claim the anchor is non-empty and the existing rules apply.
- **`claimNode({ peerId, multiaddrs, secret })`.** Requires the owner-keyed seed service (same error as `addDrone`). Parses the secret, mints a seed, builds the proof over `seedDigest(seed)`, delivers with the object target and `claimProof`. A refusal throws `ClaimRefusedError` (in `claim-proof.ts`, exported from the package root; carries `nodePeerId`, `reason` and the node's `code` when given) and writes nothing. On acceptance: `authorizePeer`, `retainDialTarget(..., 'claimNode')`, then an un-awaited `reconcileControlCohort()` kick with its rejection logged. Idempotent for the same owner.
- **Events.** `CadreNodeEvents['claim:accepted']: { ownerKey }`, preceding that seed's `seed:applied`.
- **Docs.** `membership-connection-gater.ts` module doc, `docs/architecture.md` (claim-secret entry, "What it admits anyway", "Per-stream control-DB gate"), `docs/api.md` (`claimNode`, `isAwaitingClaim`).

## Review findings

Read the implement diff first, then every file it touched plus `seed-trust-policy.ts`, `claim-proof.ts`, the connection, reservation and stream predicates, `enableSeedListener`, `installSeedBootstrapService`, `cleanup`'s seed-service teardown, `applySeed`, `addDrone`, the gater's relay-only deadline semantics, and the next ticket's expectations of this one. After the edits below: `yarn lint`, the four typechecks (`cadre-core`, `cadre-cli`, `cadre-host`, `integration-tests`) and `yarn workspace @serfab/cadre-core test` all clean: 156 files, 2394 passed, 1 skipped (the pre-existing skip in a spec this ticket never touched). Log at `tickets/.logs/node-claim-gate-and-helper.review.test.log`.

**Checked, nothing to change.**

- Gate order and coverage: the claim refusal precedes `admitControlPeerUnconditionally` in both the stream and reservation predicates, so it also wins over "not fully up" during `start()` and over configured bootstrap infra; the connection gate still answers `'admit'` on the empty anchor. After the claim the anchor is non-empty, the authorized snapshot is empty, and both predicates admit (the cold start the claimant's streams need); `onSeedApplied` refreshes the snapshot. The wake, strand-addr, formation and cadre-invite handlers need no change for the reasons the plan gave.
- Lifecycle: `cleanup()` shuts the seed service down and nulls it, and `start()` re-enables the listener because `claim` is still configured; the kept policy answers on its anchored branch after a claim, so the surviving in-process latch and failure window are never consulted. A listener registration failure fails `start()` on the ordinary cleaned-up path.
- `claimNode`: seed-before-row ordering holds, so a `ClaimRefusedError` or a thrown delivery leaves no row and no dial target; `parseClaimSecret` runs before `createSeed`, so a malformed secret costs nothing; the refusal code and reason come straight from the ack. The reconcile kick's rejection is logged, not swallowed.
- Secret handling: no code path logs the whole config; the policy and the parser never echo the value. `ClaimRefusedError`'s type-only import keeps `claim-proof.ts`'s runtime import list cross-platform.
- The one implementer test pins the contract (connection admitted, stream and reservation refused, both admitted once the anchor holds a key, and the no-claim empty-anchor node admitting both) without restating the implementation or asserting on a mock. Kept.
- Deviations the handoff declared (listener before `control:connected`, error class in `claim-proof.ts`, policy per instance): each is sound and documented at its site.

**Found and fixed inline (minor).**

- **Configuration conflict checked after the pins were written.** `initializeTrustedOwnerStore()` anchored `trustedOwners.pinnedKeys` before `initializeClaimPolicy()` refused `claim` beside them. On a persistent anchor the pin outlived the failed start, and the node restarted with the pin dropped and `claim` kept would read as claimed by that pin and never accept its claimant. The conflict checks now run in `validateClaimConfig()` before the anchor is built; the policy build stays after it. One test added in `cadre-node-trusted-owners.spec.ts` (`start()` rejects and the injected store stays empty), the reproduction of this defect at the lowest layer that shows it.
- Two phrasings said the listener is enabled "at the end of start()" (the policy's log line and `enableSeedListener`'s doc comment); it runs before `control:connected`. Corrected.
- `applySeed`'s doc now says the per-call `trustPolicy` override wins on a claim node too: the claim is the default inbound policy, not a lock on the local operator. Not a hole (the caller already controls the process; the next ticket refuses the CLI flag combination), but the reader of a "one trust source" rule deserves the exception stated.
- The claim-secret entry in `docs/architecture.md` described the proof and the policy but not the node and owner halves this ticket added. A sub-paragraph now names the configuration rule, the listener, `isAwaitingClaim`, `claim:accepted` and `claimNode`'s write-nothing-on-refusal order, and points at the admission paragraphs for what an unclaimed node lets a stranger do.

**Major.** None: no finding named a site that must change beyond the inline fixes, and no class-level invariant surfaced that a type or general test would retire.

**Tripwires.**

- Idle stranger connections on an unclaimed node (the handoff's flagged gap): recorded as a `NOTE:` at the top of `admitInboundControlConnection` in `cadre-node.ts`, with why `'admit-for-relay'` is the wrong fix (its deadline clears only on an admitted reservation, which an unclaimed node refuses, so it would also cut the claimant's connection after the claim).
- `isAwaitingClaim()` is false before `start()`: already stated in its doc comment; cadre-cli reads it after start. No further note.
