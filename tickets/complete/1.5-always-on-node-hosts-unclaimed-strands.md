# Always-on nodes host unclaimed strands as storage replicas

## What was built

Maintainer decision (2026-09-28): an always-on node joins every strand its strand filter admits as an ordinary Optimystic node that stores and serves the strand's blocks, whether or not the app is installed there.

- `CadreNodeConfig.hostUnclaimedStrands?: boolean`, default `profile === 'storage'`, resolved once in the `CadreNode` constructor. A `NOTE:` on the field flags disk growth, since there is no quota.
- A storage replica is `StrandInstanceManager.startStrand` with `sAppConfig` absent. It has no schema-signature check, no `App` schema, no `sAppInfo`, and the default latency hint. The `Strand` membership schema, revoked-peer gate, membership reconciler and first-sync gate all run as usual. A replica is always a joiner, and `StrandDatabase` refuses to found without an sApp (`founderSApp()`).
- `handleStrandAdded`'s no-config branch announces once (`announceDiscoveredStrand`). On a replica host it then launches with `launchStrand(strand, undefined)`, unless a synchronous `strand:discovered` listener already claimed the strand.
- `recordReplicaSAppId` reads `Strand.Header.sAppId` after launch, on `strand:writable` and after a hibernation resume. `getSAppId` falls back to it, which lets an `sAppId` filter reject another app's replica. `cleanup` clears the map, but `detachStrand` does not, so a rejected replica is not relaunched.
- In the harness (`controlNodeConfig`, the restart-party fixture), `hostUnclaimedStrands` defaults to false.
- Docs across architecture, strands, reference-app-rn, testing and cadre-consistency were updated.
- Handling an app that claims a strand this node already hosts as a replica is follow-up ticket `claiming-a-hosted-strand-upgrades-in-place`.

Tests:
- One unit case: announce once across failed replica launches, then launch without a config as a joiner.
- One integration scenario: `strand-always-on-replica-survives-phone-loss`. The phone writes, the replica covers every block, the phone is lost, and a replacement reads all rows with the replica as its only strand peer.

## Review findings

Read the diff of `ticket(implement): always-on-node-hosts-unclaimed-strands` first, then the handoff.

**Checked, no change needed:**
- **Lifecycle of the `sAppId` re-evaluation.** Traced it through `StrandWatcher.poll`. A rejected replica leaves `knownStrands` and `provisional`. The retained `replicaSAppIds` entry makes the next poll reject it before any launch. Keeping the map past `detachStrand` is correct, as the handoff says.
- **Launch-time read of the app id.** `recordReplicaSAppId` runs before first sync, where the database is still withheld. There it is a no-op, and the `strand:writable` hook records the id later. A read in flight during `cleanup` can leave one strand-id → sApp-id entry after `stop()`. That mapping never changes, so it is harmless. Nothing parked.
- **Consumers of `sAppInfo`.** It was already optional. The cadre-cli `strands` command and the reference-app-web diagnostics both guard it.
- **`strand:discovered` consumers on storage-profile nodes.** None in cadre-host, cadre-cli or cadre-provider. The RN app claims only on phones.
- **RN drone test fixture (`reference-app-rn/test-fixture`).** The Maestro sidecar endpoints read the drone's own claimed strand, so replica hosting does not affect them.
- **Every other storage-profile node built by integration scenarios** goes through `controlNodeConfig`, where the default is false.
- **Unit test.** It pins the dedupe and retry branch with real branching and does not just restate the code. Kept.
- **Integration scenario.** Well structured. It asserts the ordering, reads raw stores for the physical claim, and does no dial from the test side. Kept as is.
- **Control-plane observation in the handoff.** On one run, `authorizePeer` failed with `cohort-unreachable` on `Revocation` right after the lost phone stopped. At a control cohort of two, that is the known fail-closed behaviour when the departed member is still in the cohort. The same failure is measured in `backlog/debt-replication-proof-above-cohort-size` ("Second arm"). The scenario's wait for the cohort to shrink is realistic. No new ticket.
