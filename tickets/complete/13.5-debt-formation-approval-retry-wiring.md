# Approval-retry wiring — implemented and reviewed

Downstream of `debt-formation-approval-retry-lost-race`, which made a redemption that loses a
use-number race re-present the SAME approver sign-off under a fresh use number, and added
`InvitationExhaustedError` for the case where no seat remains. This ticket brought the join
handler, a schema comment, and three docs in line with that. No behaviour changed on the success
path.

## What shipped (implement pass)

- `strand-formation-manager.ts` — `provisionAsResponder`'s catch block gained a dedicated
  `InvitationExhaustedError` branch (after `FormationApprovalError`, before the catch-all). It
  logs token / attempted use number / seat limit, then rejects with the same wording the up-front
  `validateToken` path already sends for a spent invite, so a race loser is indistinguishable from
  a non-racing latecomer. The stale `NOTE:` at the catch-all (which claimed an obtained approval
  is DISCARDED because "this path does not retry") was replaced.
- `schemas/control.qsql` + `src/control-schema.ts` — `FormationUsage.Monotonic`'s CHECK comment
  now names `ControlDatabase.withUseNumberRetry` as what resolves the `(Token, UseNumber)`
  collision, and notes the deferred check is the other surface the same race can take. Both copies
  edited byte-identically (`control-schema-drift.spec.ts` enforces this).
- `docs/architecture.md`, `docs/api.md`, `docs/STATUS.md` — new paragraphs/bullet describing the
  retry, the "hook contacted once per redemption, never once per write attempt" guarantee, and the
  use-number-race test coverage.
- `test/strand-formation-consent.spec.ts` — new case (p): a fake `FormationUsageRecorder` throwing
  `InvitationExhaustedError` must map to `{ approved: false, reason: 'Invalid token' }` with
  `partyId` / `provisionResult` undisclosed.

## Review findings

Read the implement diff (`28736e7`) first, then the surrounding sources — `control-database.ts`
(`withUseNumberRetry`, `assertSeatRemains`, `isLostUseNumberRace`, `withWriteLock`),
`control-formation-recorder.ts`, `strand-formation-protocol.ts` — and the three docs.

### Fixed in this pass (minor)

- **Docs and comments blamed the wrong race.** The new text in `docs/architecture.md`,
  `docs/api.md` and the manager's rewritten catch-all comment all attributed the use-number retry
  to the **local** race ("two joins of the same invite landing on this node at once", "two joins
  … race on the responding node"). That is the one case that CANNOT reach the retry: a node has a
  single write queue (`ControlDatabase.withWriteLock`), so two local redemptions serialize and the
  second reads a use number the first already committed. `withUseNumberRetry`'s own doc comment
  says exactly this — the new text contradicted the code it was documenting. All three sites now
  say the retry exists for writers the local queue does not reach (another node of the cadre,
  another `Database` handle over the same store), and architecture.md states the local case
  explicitly so the distinction is not lost again.
- **Stale class-level doc comment on `provisionAsResponder`** — flagged by the implementer as
  "slightly imprecise", but it was wrong, not imprecise: it named the concurrent
  `(Token, UseNumber)` PK collision as the notable failure "caught and mapped to a logged,
  retry-suggesting rejection" here, and that collision is now retried a layer down and never
  reaches this method. Rewritten to say the mapping is per-failure and that an exhausted
  invitation is deliberately reported non-retryably.
- **The wire string `'Invalid token'` was duplicated** across `strand-formation-manager.ts` and
  `strand-formation-protocol.ts`, tied together only by a comment saying the two must match.
  Extracted as `INVALID_TOKEN_REASON`, exported from the protocol module (which the manager
  already imports; the protocol does not import the manager, so no cycle) and used at both sites.
  Tests keep asserting the literal, so the wire text stays pinned independently.
- **Four `.tess-*.log` scratch files** (streamed build/lint/test output from the implement pass)
  were committed at the repo root by `28736e7`. Untracked (`git rm --cached`, files left on disk)
  and added to `.gitignore`.

### Filed as a ticket (major enough not to fix here)

- `backlog/bug-spent-invite-told-to-retry-on-same-node-race` — `assertSeatRemains` (the guard that
  produces `InvitationExhaustedError`) runs only on attempt 2 and later, justified by "the first
  attempt is already gated by `validateToken`'s `isTokenUsed` check". Concurrency is exactly what
  defeats that gate: two joiners arriving at one node together both clear it, the second serializes
  behind the write queue, takes a use number past the invite's seat budget on its FIRST attempt,
  and is refused by `FormationUsage.Authorized` as a generic CHECK failure → reported as
  `'Formation conflict, retry'`. So the named, non-retryable answer only ever fires for the
  cross-node race, not the more common same-node one. Impact is bounded — the joiner's next
  attempt hits `isTokenUsed` and gets the right answer — so this is a wrong wire-visible reason
  plus one wasted round trip, not the never-closing loop the guard's doc comment warns about.
  Pre-existing (the same input produced the same message before the prereq ticket), so not a
  regression of this diff.

### Recorded as a tripwire, not a ticket

- The exhaustion branch gives the joiner no wire-visible distinction between "never valid" and
  "used up" — deliberate, and fine while the operator signal in the node log is enough. `NOTE:` at
  the branch in `strand-formation-manager.ts` says that if a client ever needs the distinction
  without node logs, that is a new protocol reason string, not a local change.
