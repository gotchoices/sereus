# The phone listens on `/webrtc` when it has a relay

## What landed

**A shared listen-address helper.** `webrtcListenAddrs(relayAddrs)` in a new `packages/cadre-core/src/edge-node/listen-addrs.ts`, exported from `@serfab/cadre-core/edge-node` and re-exported from `@serfab/cadre-rn/phone-node`. It returns `['/webrtc']` when `relayAddrs` is non-empty, `[]` otherwise. Its comment carries the reason a `/webrtc` listener is free of the "a phone cannot listen" objection: it binds no socket, it registers the signalling handler and derives its address from the relay reservation, so with no relay there is no signalling path and the solo posture of accepting nothing is kept.

**Both edge apps use it.** `web-edge-platform.ts` dropped its own local copy for the helper, same behaviour. `cadre-phone.ts` passes `listenAddrs: webrtcListenAddrs`, which is the behaviour change: the phone advertises `<relay>/p2p-circuit/webrtc/p2p/<id>` whenever it holds a reservation, so a peer can dial it directly, and a relayed connection to it can be upgraded.

**Comments and docs** were corrected wherever they said an edge device listens on nothing without qualification: `cadre-phone.ts`, `edge-node/config.ts`, `edge-node/platform.ts`, `host-process-orchestrator.ts`, `docs/platforms/react-native.md` → "Transport and reachability" and "Reachability: configuring a relay", `docs/platforms/browser.md`, `docs/cadre/membership.md`, and the kit README's platform-options table (which gained the `listenAddrs` row it never had).

Implement commit: `ticket(implement): phone-listens-on-webrtc`.

## Review findings

**Read order.** The implement diff was read before the handoff summary, then every file it touched, then the sites it did not: `relay-addrs.ts` (`resolveListenAddrs`, `resolveTransportOptions`), `strand-network-config.ts`, `webrtc-upgrade.ts`, `control-protocol-guard.ts`, `invitation-bootstrap.ts`, `node-claim-payload.ts`, the installed `@libp2p/webrtc` 6.0.33, the kit's WebRTC polyfill, and the specs and docs that describe the old posture.

**Verified, found sound.** Every claim the handoff asked a reviewer to confirm holds:

- **The helper's branch is the whole decision, and it is re-derived at every start.** `edge-node.ts` → `buildConfig` evaluates `platform.listenAddrs?.(relayAddrs)` from the same `relayAddrs` it evaluates `platform.transports` from, so a relay changed through Settings (which restarts the node) re-derives both and there is nothing live to update.
- **`/webrtc` cannot make a start throw.** `resolveTransportOptions` returns `{}` unconditionally when `network.transports` is set, and `buildEdgeNodeConfig` always sets it, so the `UnbindableListenAddressError` path that refuses `/webrtc` is unreachable from an edge node. The handoff's reading is right, and the combination that would hit it (this helper with no transports) cannot be produced by `createEdgeNode`.
- **Strand nodes.** `strandNodeAddrs` keeps non-circuit entries, and `ephemeralPortListenAddr` passes `/webrtc` through unchanged because it names no port. Every strand node therefore offers a WebRTC address too, which is what is wanted.
- **The kit re-export was the right call.** `phone-node/index.ts` already republishes roughly twenty edge-node names under its own doc ("the kit is published and used outside this repo"), so one more is consistent and the app keeps a single import door. Judgement upheld, no change.
- **The upgrade service's tie-break behaves correctly now that a phone advertises.** `decideWebrtcUpgrade` reads `localAdvertisesWebrtc` live from `getMultiaddrs()`. Before a reservation lands, the phone counts as a non-advertiser and dials while its peer, seeing no WebRTC address from the phone, declines with `no-webrtc-addr` — so there is no window in which both sides dial, and none in which neither does once both have published.
- **No admission path is newly exposed.** A `/webrtc` listener accepts inbound signalling, which the control node's per-stream guard already classes as `transport` and the connection gate already decides per connection. The browser tab has listened this way since before this ticket, so the posture is not new ground.
- **The React Native bundle needs nothing new.** `@libp2p/webrtc`'s listener (`private-to-private/listener.js`) touches no RTC object at all — it maps the circuit listener's addresses — and the inbound signalling handler imports the same `webrtc/index.js` the outbound path already used, which Metro rewrites through `withCadreMetro` and `@serfab/cadre-rn/polyfills/webrtc` supplies globals for. Confirmed in the installed 6.0.33.

**Major finding, appended to an open ticket rather than filed.** The site-claim grep over the board found `fix/webrtc-address-can-displace-a-working-one`, which already owns this finding in full: `classifyDialAddress` and `isSignalingAddr` answer "relay" for both address shapes, so a WebRTC address consumes an invitation slot, a wake attempt, or a per-address redemption deadline that a working address needed. What is new is that its closing paragraph predicted it would be worked before this ticket ("this sits in `fix/`, so it is worked before that ticket either way") — and it was not: nothing on the board expressed the dependency, since this ticket named only `webrtc-addresses-never-hold-a-dial` as its prereq. An arm saying so is appended there. Nothing is incorrect as a result — each arm costs a retry, a slot or wall-clock time, not correctness — but the exposure is now every phone rather than the reference web app and a hand-configured node. No new ticket: one root cause, one home.
