# cadre-cli: an owner key in its own file (complete)

## What was built

cadre-cli no longer turns the node identity into an owner key anywhere. A server holds an owner key only in the **owner key file**, and every owner signature the CLI makes uses that key.

- **Config.** New `owner.keyFile` (env `CADRE_OWNER_KEY_FILE`, flag `cadre start --owner-key-file`), checked strictly (`schema.ts`), resolved to `ResolvedConfig.ownerKeyFile`: an absolute path, default `<nodeStateDir>/owner.key`. `resolveConfig` refuses an owner key file that is the identity key file (`loader.ts` `resolveOwnerKeyFile`; string comparison, case-insensitive on Windows and macOS).
- **The file** (`owner-key-file.ts`). A one-slot `KeyStore` over the single file, so cadre-core's owner-key slot functions (`createOwnerKey`, `loadOwnerSigner`, `importOwnerKey`, `readOwnerPrivateKey`) run unchanged: an absent file is never filled on read, nothing is created over an occupied file, and importing a different key is refused. A file that cannot be read is reported as `KeyStoreAccessError`, and bytes that do not decode as a key are reported as "Invalid owner key file …". Neither case is ever treated as an absent file. Writes go through the new `writePrivateFileAtomically` in `private-file.ts`: a temp file, fsync, then rename, mode 600. `claim-record.ts`'s copy of the same code now calls it.
- **`cadre start --owner`** (`start-owner.ts`, called from `start.ts`). The key is loaded or created after every conflict and removal check and before the node is built. When the file is created, stderr says this server now holds an owner key for the party, where the file is, and that anyone who can read it controls the cadre. Once the control database is up, `ownerKeyStanding` decides what happens:
  - **founding** (`hasOwnerKey()` false): `ensureOwnerKey(key, label)`, with the label from `--owner-label`, or `server <hostname>` cut to 64 characters.
  - **owner** (the key is in `getOwnerKeys()`): the key is wired and nothing is inserted.
  - **not an owner**: start-up fails, naming the fingerprint, the file and the public key, and saying to add the key from an owner device or import one of the party's keys. Nothing is inserted or wired.

  If the genesis insert returns false (a row replicated in between), the key's standing is checked again. After that come `useOwnerSigner` and `registerSelf`, as before. `--owner` still requires a node identity, because the self row is signed with it. `--owner-label` and `--owner-key-file` given without `--owner` are refused.
- **One-shot sessions** (`node-session.ts`). The owner key file is loaded before the node starts. When the file exists, `wireOwnKeyIfOwner(signer)` is called. When it does not, nothing is called, because `wireOwnKeyIfOwner()` without a signer would fall back to the identity key. Owner writes then refuse with cadre-core's existing "needs an owner signer" error.
- **`cadre owner-key show|export|import`** (`owner-key.ts`, registered in `bin/cadre.ts` and exported from `index.ts`). Each subcommand resolves the file through the config (`-c`, `--owner-key-file`), so the same-path refusal applies to them too.
  - `show` prints the public key, the fingerprint (the first 8 characters, as in the apps) and the file; `--json` prints the same as JSON.
  - `export [--passphrase-file] [--label]` puts only the export text on stdout and the warning on stderr.
  - `import [text|-]` takes the text as an argument, or reads stdin when given `-` or nothing (with a paste prompt on a terminal). A locked export needs the passphrase. Importing the same key is a no-op; a different key is refused, naming both fingerprints.
  - Passphrases come from `--passphrase-file` or `CADRE_OWNER_KEY_PASSPHRASE` (added to `COMMAND_ENV`); giving both is refused.
- **Admin channel.** `GET /admin/identity` now returns `{ peerId, partyId, ownerKey }`, where `ownerKey` is the wired signer's public key or null.
- **Invitations.** `refuseInvitationConflicts`' `--owner` message no longer says that a later `--owner` start wires an owner grant seated by an invitation. When a redemption's `grantsOwner` is true, the node now prints a warning that the grant seated its identity key, which cadre-cli never signs with. There is a `NOTE:` at that site.
- **Harness.** `owner-cli-node.ts` lets the child create its own `owner.key` and adds `getOwnerKey()`, read from the admin channel. `provider-container-joins-by-invitation` step 1 now asserts that the invitation's issuer and its one pinned owner key are that key, and not the key behind the node's peer id.
- **Docs.**
  - The README has a new "Make this server an owner" section covering `--owner` and `cadre owner-key`. The `strand remove` / `validation-key` requirements, the invitation paragraph, the environment table (`CADRE_OWNER_KEY_FILE`, `CADRE_OWNER_KEY_PASSPHRASE`) and Data Locations are updated.
  - `example.cadre.yaml` has a commented `owner:` block.
  - `docs/architecture.md`: the Owner Keys status note (cadre-cli taken out of the "still derives from identity" list), the key-store bullet (servers use the owner key file, not `FileKeyStore`), "Invitation-granted owners", and the cadre-cli status bullets (a new `--owner` / `owner-key` bullet, and the `validation-key` bullet).
  - `docs/cadre-host.md` links `cadre start --owner` to the README. `docs/testing.md` describes the owner child's key file and the new step-1 assertion.
  - `reference-app-web/README.md` drops its "mirroring `cadre-cli start --owner`" claim, which is now false.
  - The comment-only cadre-core change: the `useOwnerSigner` `NOTE:` no longer counts `cadre start --owner` among the callers that wire a key unconditionally. cadre-core was rebuilt after it.

## Tests

- `test/start-owner.spec.ts` (new) runs real solo `CadreNode`s in process, over memory stores shared across "restarts", one test per arm of the `--owner` decision:

  - **Wires:** on a party that lists the key, it is wired with no second row, and `isOwner()` is true.
  - **Refuses:** on a party whose owners do not include the key, the call throws, naming the fingerprint, the file and the party; the owner rows are unchanged and no signer is wired.

  - `admin-server.spec.ts`: the identity route's expected body.
  - `node-session-branches.spec.ts`: the fake node's `wireOwnKeyIfOwner` was removed; with no owner key file it is unreachable.

  - show with no file: exit 1
  - plain import from stdin, then a second import that changed nothing
  - show, and show `--json`
  - export locked with a passphrase file and a label
  - locked import with no passphrase, with the wrong one, and with both sources set: each refused

  - a corrupt file: "Invalid owner key file"
  - an invitation pasted in place of an owner key: refused by name

## Known gaps and judgment calls for the reviewer

- **No upgrade path for a party founded by an older cadre-cli.** Such a party's only owner key is its server's identity key. After this change, `--owner` there creates `owner.key` and fails with "not an owner", and no command turns the identity file into an owner key export. AGENTS.md says no backwards compatibility yet, so I added none. A one-off migration command (identity file → owner-key text) would be the fix if one is wanted.
- **An all-CLI party has no "add owner" command.** The not-an-owner message says to add the key from an owner device. For a party whose only owners are CLI servers, the route today is `owner-key export` on one server and `owner-key import` on the other, which gives both the same key. An admin route over `CadreNode.addOwner` was out of scope.
- **Owner-granting invitations to a CLI node go unused.** The grant seats the node's identity key, and the CLI never wires the identity key. A warning is printed and a `NOTE:` sits in `start-invitation.ts`; `plan/2-owner-grant-separate-from-machine-invitation` resolves it.
- **`import <text>` as an argument.** The ticket asked for it. A plain export on the command line lands in shell history, so the README and `--help` recommend stdin. Refusing a plain export given as an argument is a possible tightening.
- **Same-path check.** It compares resolved path strings, so a symlink or hard link to the identity file passes. There is a `NOTE:` in `loader.ts` `samePath`.
- **Passphrase file permissions.** Unlike `claim.secretFile`, a passphrase file other accounts can read draws no warning.
- **Unchanged:** `--owner` on a local store that has not synced a party that exists elsewhere still genesis-inserts, as before, because `hasOwnerKey()` reads local state right after start.
- **Unused interface methods.** The `KeyStore` adapter's `delete` and `list` exist only to satisfy the interface; nothing in the CLI calls them.
- `implement/1.07-harness-owner-keys-separate-from-node-identity` (the in-process harness) is separate and untouched here.

## Review findings

**Fixed in this pass**

- **The owner key file could be replaced by a concurrent create or import.** `OwnerKeyFileStore.set` wrote through `writePrivateFileAtomically` (temp file, then rename), and rename replaces an existing file. cadre-core reads the slot empty before it sets it, so two processes on one node-state directory (a `cadre start --owner` beside a `cadre owner-key import`) could both read "absent", and the second rename would silently replace a key that may already have founded the party, losing it. `set` now goes through the new `createPrivateFileDurably` (`private-file.ts`): an exclusive `wx` create, fsync, and on a write error the partial file is removed. `EEXIST` becomes `OwnerKeySlotOccupiedError` naming the file. A crash part-way leaves a short file, which the reader already refuses as "Invalid owner key file", never as absent; that key was never used, since the create had not returned. Checked by hand against the built code: create, a refused bad import, an empty file reported as invalid, and the file left unchanged. No test added: the race cannot be driven deterministically through the public functions, and the exclusive flag on its own is not worth one.
- **No warning when other accounts can read the owner key file or the passphrase file.** `claim.secretFile` already gets one. Its check moved to `modeOpenToOtherAccounts` in `private-file.ts` (`claim-secret.ts` uses it). `loadServerOwnerKey` now warns for the owner key file on every `--owner` start, and `resolvePassphrase` warns for `--passphrase-file`. POSIX only, as before. The README's "Make this server an owner" bullet says so.
