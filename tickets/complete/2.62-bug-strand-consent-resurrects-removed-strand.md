# Complete: `Strand` consent bound to the redemption that authorized it

## What shipped

`CadreControl.Strand` rows can be seated without any signature, authorized purely by the
existence of a `CadreControl.FormationUsage` redemption record. That record used to name only
the strand **id**, and `FormationUsage` is append-only — so the record outlived the strand
forever. After a legitimate owner-signed, tombstoned removal, any writer on the party's
replicated control database could re-insert the strand with no owner key, no signature, a fresh
one-off nonce (`StampId`, sidestepping the `NotRevoked` tombstone check, which retires only the
removed row's nonce) and an attacker-chosen `MemberPrivateKey` — the party's own read-gating
secret for that network.

Consent now binds to **one specific strand row**:

- `FormationUsage` gained `StrandStampId text not null` — the `Strand.StampId` the record
  authorizes. Deliberately not unique: in the bound (provision-then-record) path several
  invitees write usage rows against the same host strand.
- `FormationUsage.StrandExists` matches the `(id, stamp)` pair.
- `Strand.AuthorizedInsert`'s consent branch additionally requires `FU.StrandStampId = new.StampId`.
- Removal retires that stamp into `Revocation`, so `NotRevoked` closes that consent record's
  branch permanently.

Mirrored byte-identically into both schema copies (`schemas/control.qsql`, `CONTROL_SCHEMA` in
`control-schema.ts`); `control-schema-drift.spec.ts` is the guard.

Writers: `execFormationUsageInsert` takes and writes `strandStampId` (the repo's only
`FormationUsage` insert site); `redeemInvitation` passes the same freshly-minted stamp it gives
the `Strand` insert; `recordFormationUsage` reads the live stamp via `queryStrandStampId` and
throws a new exported `MissingHostStrandError` when the strand is absent.

No signature or digest changes — the consent branch is signature-free by design and the
owner-signed `'add'`/`'remove'` digests are untouched.

## Review findings

### Verified correct

- **The reported hole is closed, both doors.** Re-checked the constraint algebra and the two
  committed regression tests in `control-revocation-replay.spec.ts`: after a tombstoned removal,
  an unsigned re-insert with a **fresh** stamp fails `AuthorizedInsert` (no usage row names that
  pair) and with the **original** stamp fails `NotRevoked`. There is no third door: creating a
  usage row for a fresh `(id, stamp)` pair requires a live `Strand` row for that same pair
  (`StrandExists`), so the only way through is a full redemption — which is the finding below,
  not a gap in this fix.
- **Re-join is not a permanent id blacklist.** Pinned by the committed test.
- **Blast radius.** Grepped every `FormationUsage` producer and consumer across `packages/` and
  `schemas/`: exactly one insert site (`execFormationUsageInsert`) plus one test helper; every
  reader names its columns explicitly (no `select *`), so the reference web app, the e2e
  formation-responder fixture, and the integration harness need no change. Only two schema
  copies exist. `recordFormationUsage`'s public signature is unchanged, so
  `integration-tests/src/harness/test-network.ts:198` still compiles and behaves the same.

### Found and fixed in this pass (minor)

- **`MissingHostStrandError` had no test.** A newly exported error class with zero coverage.
  Added *"recordFormationUsage throws MissingHostStrandError when the host strand is absent"* to
  `control-formation-invite.spec.ts`.
- **`docs/architecture.md` control-table summary was stale.** The `Strand` row said adding "may
  instead be authorized by a redeemed formation invitation" with no mention of the stamp
  binding. Corrected.

### Found and filed (major)

- **`tickets/fix/2.64-bug-formation-consent-unconstrained-strand-seating.md`** — redeeming an
  invitation is an unconstrained strand-seating capability, so the *headline* symptom of this
  ticket is still reachable whenever any invitation has a use left. Confirmed empirically in a
  scratch spec (deleted after; asserting today's behavior would mean asserting the hole):
  - **A.** One invite with `totalUses: 2`: redeem → owner-signed tombstoned removal → redeem
    the **same** token again for the **same** strand id with `memberPrivateKey: 'ATTACKER'`.
    **Accepted** — the strand is back with the attacker's key.
  - **B.** An invite **bound** to host strand `H` redeemed for an unrelated id `Z`, closed, with
    an attacker key. **Accepted** — `FormationUsage.Authorized` never compares `new.StrandId`
    against `FormationInvite.StrandId`, and the consent branch never constrains `Type` or
    `MemberPrivateKey`.

  This is narrower than the pre-fix hole (it needs a spare invite use rather than nothing at
  all), so the fix here is real hardening, not a no-op — but invite tokens sit in plaintext in
  the replicated `FormationInvite` table and an unlimited-use invite is the normal open-invite
  state, so the residual is not theoretical. The implement handoff called this out as by-design
  ("removal does not revoke the invitation") and framed it as the legitimate re-join path; the
  attacker's free choice of id, `Type`, and `MemberPrivateKey` is what makes it a defect rather
  than a design note. Prereq'd behind `bug-formation-validation-key-never-checked` — both edit
  the same `FormationUsage.Authorized` block. `docs/architecture.md` now states the gap.
