# Complete: joiner-consent end-to-end re-verification + documentation

Two independent parts, both landed: one new integration case, and doc corrections. Sibling
`debt-formation-consent-signature-matrix` owns the schema-level negative matrix; nothing here
overlapped it.

## What landed

### End-to-end assertion

`strand-formation-e2e.integration.ts`, in `Phase 4: Responder consent enforcement (real recorder)`:

- Helper `readFormationUsage(party, token)` reads `Token, UsageStampId, PeerKey, PeerSig,
  Disclosure` back out of a party's control database, returning exactly the shape
  `verifyFormationConsent` takes. `Disclosure` is passed through verbatim — re-serializing it
  would defeat the property under test.
- Case `(iii) stores a joiner consent signature that re-verifies against the joiner's own key`.
  After a genuine `bobService.formStrand(...)` against alice's real
  `ControlFormationUsageRecorder` over libp2p, it asserts:
  - exactly one usage row exists for the token (added in review — see findings);
  - `verifyFormationConsent(row)` is `true` — the stored signature re-checks from the row alone,
    with nothing carried over from the session that wrote it;
  - `ed25519PublicKeyB64FromPeerId(result.memberKey) === row.peerKey` — the key the signature
    verifies against is the joiner's own identity;
  - a one-character-mutated `disclosure` makes the same check return `false` — a guard so the
    first assertion cannot pass vacuously.

## Review findings

### The implement handoff's central caveat is resolved

The handoff was explicit that the new case had **never executed**: an attempt to run it was
refused by the shared stale-build guard because the sibling `../quereus` workspace's `dist` was
older than its `src`. That is real — an early rebuild attempt from this review failed with
`src/runtime/emit/join.ts(105,8): error TS2304: Cannot find name 'usingResolved'`, and
`../quereus` had uncommitted in-flight edits from concurrent work, so it was left alone rather
than touched. It came green partway through this review (that concurrent work finished), and the
case was then **run for real and passed**. Everything the handoff listed as "only surfaces at
runtime" is now observed rather than inferred: the `db.eval` column names come back as written,
the unbound path does reach the DB-backed recorder, and `result.memberKey` is populated.

Before that window opened, the riskiest assertion — `ed25519PublicKeyB64FromPeerId(memberKey)
=== peerKey` — was proved independently off-network with a throwaway probe against the built
`@serfab/cadre-core`, reconstructing `formStrand`'s key/nonce/signature sequence. It held, as did
mutated-`disclosure` and mutated-`usageStampId` rejection. That probe was scratch and is not in
the tree.

### Correctness of the rewritten prose — checked, correct

The handoff flagged the `docs/api.md` nonce argument as the one place prose was *replaced* rather
than corrected, and asked whether it is right and not merely different. Checked against source:
`strand-solicitation.ts:317` is the **only** site that mints a `usageStampId` (grepped every
`generateStampId` call in `cadre-core/src`), and it is on the joiner. `control-database.ts:173`
already said so. The responder inserts that same value and asks the approver about it, and cannot
substitute one because a swapped nonce fails the joiner's `PeerSig`. The rewritten argument is
correct.

### The `docs/strands.md` no-change call — checked, agreed

Re-grepped it independently. Its `## Strand Creation` / `## Inviting Parties` sections are stubs
pointing at `architecture.md`, and everything else signature-related there is the layer-2
`Strand.*` membership RBAC (managers, member invites, removals) — a different consent layer this
change does not touch. No stale claim to correct. The implementer's call stands.

### Stale claims the change missed — fixed in this pass

Three sites still carried the pre-change story and were not in the handoff's list:

- **`docs/STATUS.md`** said `ControlFormationUsageRecorder` "mints the redemption nonce" — the
  exact claim corrected in `docs/api.md` but missed one file over. Corrected to "calls the
  approval hook with the redemption nonce the joiner minted".
- **`schemas/control.qsql`** and its byte-identical twin **`packages/cadre-core/src/control-schema.ts`**:
  the `UsageStampId` column comment read "The redeeming node mints it BEFORE it asks the
  approver". Rewritten in both to say the joining peer mints it, signs it into its own `'consent'`
  digest, and sends it in the contact message; the responder inserts that value and asks the
  approver about it. The two copies are pinned together by `control-schema-drift.spec.ts`, which
  passes.

### Documentation gap the change introduced — fixed in this pass

`docs/api.md`'s new `peerKey` paragraph was accurate but incomplete in a way that could mislead a
hook author. `formStrand` generates a **fresh keypair per formation**, so `peerKey` is the
joiner's per-strand membership key — the key behind the `partyId` inside `disclosure`, not a
long-lived node identity, and different for every strand the same joiner forms. The page's own
example hook does `mayJoin(fields.peerKey, ...)` under a `// not on the roster` comment, which
cannot work as a persistent allow-list. Added a paragraph saying so and pointing an allow-list at
the disclosed identity instead. (The example itself is unchanged — its shape is fine; what it
demonstrates is that the disclosed identity provably signed.)

### Test strength

The implementer's case is well-shaped. Two additions:

- **Asserted the single-row premise.** `readFormationUsage` returns whichever row the scan yields
  first, sound only because every Phase 4 case redeems a single-use invite — parked by the
  implementer as a `NOTE:`. Added `expect(await alice.controlDatabase.countFormationUsage(token)).toBe(1)`
  so a future multi-use case fails loudly there rather than silently asserting the wrong row.

  weight for a network test whose job is the round-trip, not the permutation space.
- Style: the helper's `row['Token']` bracket access changed to `row.Token`, matching every other
  `db.eval` call site in `control-database.ts`.
