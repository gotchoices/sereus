# Complete: extract the strict config checker into `@serfab/config-check`

## What landed

A new workspace, `packages/config-check` (`@serfab/config-check` 1.7.0). It has no runtime dependencies and no `node:` imports; its `tsconfig.json` sets `"types": []` and `"lib": ["ES2022"]`, so a Node import fails its type check. It holds the checker mechanism that used to live in cadre-cli's `schema.ts`, `loader.ts` and `env.ts`:

- `checkers.ts`: `ValidationContext` (now takes an optional `suppliersOf(keyPath)` that names the variables for "(or set …)" hints), the scalar checkers, `numberWhere`, `oneOf`, `arrayOf`, `objectOf`, `refine`, `describeValue`, `kindOf`, `isPlainObject`.
- `validate.ts`: `validateTree(tree, root, { configPath, provenance?, suppliersOf? })`, which prefixes each problem with `Environment variable X:` or `Config <path>:`.
- `env.ts`: `specifiedEnv`, `applyEnvOverrides(raw, env, overrides, onApply?)`, and the text parsers `parseListEnv`, `parseBooleanEnv`, `parseNumberEnv`.
- `nearest-key.ts`: moved unchanged.

cadre-cli keeps its field tables, `envVarsFor`, `ENV_MAPPINGS` (now also exposed as `ENV_OVERRIDES`, each kind resolved to its parser), `checkEnvNames`, and the `CADRE_PUSH`-redacting debug log. `validateConfig` and `applyEnvironmentOverrides` keep their signatures. The stale-build guard lists in cadre-cli, cadre-host and integration-tests, the Dockerfile's four stages, the Docker workspace root, the `pub` chain (config-check first), knip, and the docs were all updated. See `` `ticket(implement): config-check-shared-package` `` for the full diff.

## Review findings

**Behaviour preserved (checked by reading and running).**
- Order of overrides and problems: `ENV_OVERRIDES` is built with `Object.fromEntries` over `ENV_MAPPINGS`, which keeps insertion order, so variables are applied in the same order as before. `objectOf` still reports unknown keys before missing and ill-typed ones.
- Parse before clone: `setNestedValue(result, path, parse(text, variable), variable)` evaluates the parser before any branch is cloned, as before. A probe against the built `dist` confirmed three things: a throwing parser's error comes out before any `cloneBranch` error; the caller's `{ a: { b: 1 } }` is left unmodified while the returned tree gains the write; and the `cloneBranch` error names the variable (`Cannot apply X: config key a is "file" where a mapping of keys was expected`).
- "(or set CADRE_…)" hints and the source prefixes: `validateConfig` passes `suppliersOf: envVarsFor` and `provenance` through, and cadre-cli's unchanged specs (`config-validation`, `env-override-empty`, `env-names`, `build-targets`) pin the text. They pass: 19 files, 254 tests.
- Module-load order in cadre-cli's `env.ts`: `ENV_OVERRIDES` is computed at load time. `PARSERS` and `ENV_MAPPINGS` are defined above it, and `parseJsonObject` is a hoisted function declaration, so nothing is read before it is defined.
- Dockerfile: the four stages match the header comment ("three workspaces"). config-check's manifest is copied in both install stages, its `src` and tsconfigs in the build stage, and its `dist` and manifest in the runtime stage, where the `node_modules` symlink points. `yarn workspaces foreach -At` builds it before cadre-cli.
