# Phone reference app joins an existing cadre

Settings' old "Join a Cadre" section is now **Join my existing cadre** (`src/join-cadre-section.tsx`). It shows this app's join request (QR code, Copy, text, and the short peer-id "Code"). It takes a pasted or scanned response or open invitation, then shows each step the join goes through: joining (with Cancel while it waits for a member), admitted, moving chats, removing the old cadre, done. It also handles the cases that need the user: a move that did not finish (Retry moving / Later), an old cadre that holds what the joined one does not (Delete them / Keep old cadre), an old cadre with other machines (kept), and a failed removal (Remove it now / Later). The flow lives in the app-wide hook, so it survives a tab switch, and a start into a party whose join was left unfinished shows the step again. The user-facing description is docs/reference-app-rn.md → "Joining an Existing Cadre".

Code layout:

- `join-flow.ts`: the `JoinFlow` union, its words, and `JoinCancelledError`. No React.
- `use-join-flow.ts`: the hook part that runs the flow, used from `useCadreInternal` (split out in review; see below).
- `cadre-phone.ts`: pass-throughs to the kit (`identityPeerId`, `joinRequestText`, `pendingStrandMove`, `finishStrandMove`, `dissolveFormerParty`) and the relay default used when the app never connected.
- `join-failure.ts`: alert wording for failures before admission.

The implement-stage handoff (`ticket(implement): reference-app-rn-joins-existing-cadre`) lists the calls where the work differs from the ticket. The reviewer checked each one against the kit (below) and accepted it.

## Review findings

**Read first:** the implement diff, then the kit's `PhoneNode.joinCadre` / `finishStrandMove` / `dissolveFormerParty` / `pendingStrandMove`, `strand-move.ts` and `dissolve.ts` in `packages/cadre-rn/src/phone-node/`, and cadre-core's `StrandMoveReport` and `CadreJoinProgress`.

**Correctness, checked by reading against the kit; no defect found:**
- Mapping a join's `strandMove` to a step covers all four outcomes: `done`, `partial`, deferred because the owner key is not wired, and deferred because the adoption failed.
- `retryStrandMove` sets the moved count from `report.moved`, not adding to it. That is correct because cadre-core's `StrandMoveReport.moved` already includes strands seated by an earlier attempt. Left a one-line comment saying so, since the assignment looks like a bug without it.
- Mapping dissolve refusals: `StrandMovePendingError` → move-incomplete. `FormerPartyNotEmptyError` with other machines → kept, never discarded. Without other machines → confirm-discard, passing the ids back as `discard`.
- Cancel: the hook's controller is relayed into the kit's `signal`. A stop that aborts the join from inside the kit is not reported as a user cancel. Cancel is offered only in the `joining` step.
- Two taps on Join in one frame: the guard runs after the last `await` before the flow is set, so the second tap is refused.
- No flicker between the join resolving and the removal starting. `adoptSwitchedNode` → `settleAfterJoin` → `dissolveOldCadre` → `showSwitching` all run in one synchronous stretch with no `await` between them, so React batches the connected/null node updates into one render.
- In-place redemption (the app is already in the invitation's party, for example a second invitation granting owner): the kit does not stop the node, and the hook re-adopts the same node. Harmless.
- The relaunch check runs only after a successful `start`, and backs off when a flow is already showing.
