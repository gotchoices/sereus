# Complete: single-use, action-scoped authority tokens for CadrePeer

Follow-up to `membership-cadrepeer-voucher-persist`: persisting the authority voucher
(`VouchSig`) on a replicated row turned ONE signature over `digest(peerId)` into a
lift-and-replay token authorizing insert AND delete AND reauthorize. This ticket makes each
action a distinct, single-use token. The bulk of the implementation was already committed in
`2e41e54`; the review below is the adversarial pass over it.

## What landed

- **`StampId text not null unique`** on `CadrePeer`, minted per (re)insert via `generateStampId`.
- **Action-scoped digests** (`peer-authorization.ts`): voucher signs
  `cadrePeerVoucherDigest(peerId, stampId)` = `digest([peerId, stampId])`; delete signs
  `cadrePeerRemoveDigest(peerId, stampId)` = `digest([peerId, stampId, 'remove'])` — a
  distinct payload the stored voucher can never satisfy. `peerAuthorizationDigest(peerId)`
  is unchanged, still used by `DeviceToken` + the offline `enroll register` verify.
- **Split constraints (both schema copies, drift-guarded):** `AuthorizedInsert check on
  insert` verifies `digest(new.PeerId, new.StampId)` and binds the stored voucher ==
  context pair; `AuthorizedDelete check on delete` verifies `digest(old.PeerId,
  old.StampId, 'remove')`; `AuthorizedUpdate` self-branch makes `StampId`+voucher
  immutable, authority branch re-vouches over `digest(new.PeerId, new.StampId)`.
- **Write paths:** `insertCadrePeerRow` mints StampId + signs the voucher digest;
  `removePeer` reads the live StampId and signs the remove digest; `reauthorizePeer` reads
  the StampId and re-signs the voucher. A single `signDigest` is the one place the
  authority key is applied.
- **Read:** `queryCadrePeers` surfaces `stampId`; `queryCadrePeerStampId` added for the
  delete/reauthorize paths and ticket 4's read-time re-verification.

## Review findings

Adversarial pass over the diff (SPP/DRY/modularity/type-safety/error-handling/resource
cleanup/test coverage), plus a full lint + typecheck + test run.

**Fixed inline (minor):**

- **Regression — wrong error precedence in `removePeer`/`reauthorizePeer`.** Threading the
  row's `StampId` made both methods read the control DB *before* signing, so the
  control-DB check fired ahead of the authority-key check. `seed-bootstrap.spec.ts >
  removePeer > requires an authority private key` failed (`'Control database not
  initialized'` instead of `'Authority private key required'`), and worse, a keyless
  caller targeting an absent row hit the `stampId === null` early-return and **silently
  no-op'd** instead of rejecting. Fixed by a `requireAuthorityPrivateKey()` guard invoked
  up front in both methods (and DRY-factored through `signDigest`). Full cadre-core suite
  now 657 pass / 1 pre-existing skip / 0 fail.
- **Stale docstrings.** `insertCadrePeerRow` still said "Signs `digest(peerId)`" (now
  `digest(peerId, stampId)`), and `removePeer` described the removed combined `check on
  insert, delete` over `digest(old.PeerId)` (now `AuthorizedDelete` over `digest(old.PeerId,
  old.StampId, 'remove')`). Both rewritten to the new reality. Added a 2.5 roadmap note to
  `docs/STATUS.md` explaining why `StampId`/split-constraints exist.

**Tripwire (recorded at the site, not a ticket):** `StampId` uniqueness only blocks
insert-replay while the row (or its nonce) is still present — a delete frees the `StampId`,
so a captured authorized insert could be replayed to re-add a peer the authority removed (a
revocation bypass). This is fully subsumed by ticket 6's connection gater (no outsider write
⇒ no replay at all). Parked as a `NOTE:` at the insert site in `seed-bootstrap.ts`.

**Checked, no change needed:**

- Schema drift: `control-schema-drift` green — both copies byte-identical.
- Digest separation: voucher vs remove payloads are distinct; the stored `VouchSig` cannot
  satisfy the delete verify. Covered by the crypto-free predicate spec + real-crypto specs.
- Voucher binding: `new.VouchAuthority/VouchSig == context` on insert, re-bound on the
  authority-update branch, immutable on self-update. StampId immutable on self-update.
  Truth table exercised (single-use, immutability, admit-untouched) — 8 crypto-free cases.
- Widened `queryCadrePeers()` return type is a structural superset of `CohortPeerRow`; all
  callers (cadre-node cohort/re-touch, admin, web diagnostics, integration harness) read
  field subsets and compile clean.
- `reauthorizePeer` rebinding `VouchAuthority` to this node's key — already NOTE-documented
  as benign (drain only re-touches self-authored rows; matters only once ticket-4's
  predicate anchors authorities).

**Residual, by design (not regressions):**

- A self-appointed-authority *outsider* (key in the pollutable replicated `AuthorityKey`
  table) can still author a valid `remove`/insert. This ticket closes stored-voucher replay
  by a non-authority reader and adds single-use nonces; the outsider-authority vector is the
  node-local anchor / connection gate (tickets 4/6).
- `DeviceToken` still signs `digest(peerId)` and stores no sig (no stored-sig replay) but
  lacks single-use nonces. Deferred to `backlog/bug-devicetoken-authority-antireplay`
  (already filed).
- The `AuthorizedUpdate` authority branch does not enforce `StampId`/`PublicKey`
  immutability or `UpdatedAt` monotonicity — pre-existing design within the
  outsider-authority residual above, not this ticket's scope.

**No major findings** → no new fix/plan tickets filed (the only deferral, DeviceToken, was
already backlogged by the implementer).
