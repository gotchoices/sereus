# Phone reference app: first launch asks before founding

## What landed

Implemented in `ticket(implement): reference-app-rn-first-launch-asks-before-founding`.

- **Hook (`use-cadre.ts`):** `savedStartRead: 'reading' | 'read' | 'failed'` reports how the launch read of the saved start went. It is three states, not a boolean, so Settings can tell a failed read (do not ask) from "nothing saved" (ask). `start` now sets `savedStartOptions` on success, so after No → Connect → Disconnect the question does not come back mid-session.
- **Settings (`app/settings.tsx`):** while the read found nothing saved and no node runs or starts, the Node card shows `FirstLaunchQuestion` in place of the Connect form. **Yes, join my cadre** shows the Join my existing cadre section with no node running, plus **Back**; **No, start fresh** shows the Connect form. While a first-launch join switches the node the card says "Joining your cadre…". The answer is screen state only.
- **Test ids:** `btn-first-launch-join`, `btn-first-launch-fresh`, `btn-first-launch-back`.
- **Maestro:** `_setup.yaml` answers Yes and joins the drone's cadre without founding one; flow 4 taps No only when the question shows, because the NativeScript app reuses the flow and has no question.
- **Docs:** `reference-app-rn.md` (Joining an Existing Cadre → First launch, startup Step 3, the e2e flows table and `_setup` paragraph) and `reference-app-ns.md` (flow 4).
- **Device run:** `tickets/blocked/rn-device-run-join-existing-cadre.md` covers this ticket and its three RN prereqs; nothing here has run on a device or emulator, and the Maestro flows are unrun.

## Review findings

**Checked:** the implement diff against `docs/architecture.md` → "An app joins an existing cadre" (a fresh install's join: no export, nothing to move, a failed join leaves nothing running), the kit's failure paths in `packages/cadre-rn/src/phone-node/node.ts` (`buildAndStart`, `returnToLeftParty`), the join flow in `use-join-flow.ts` (the join section stays the same mounted instance from Yes through `joinFlow`, `adoptSwitchedNode` replaces the saved start on success), the state sequences named in the handoff (read resolving after mount, push wake on a fresh install, Yes then join refused, No then Connect fails, an unfinished join from an earlier session), the Maestro flows, and every doc the change touches.

**Fixed in this pass:**

- **A first-launch join whose node start failed dropped to the Connect form.** When the kit fails to start the joined party's node it reports `failed`, and with nothing to restore it stays there, so the hook's status became `error`. `asking` required `idle`, so the Yes state and its paste disappeared and the Connect form (which founds a cadre) showed instead. `asking` now also holds for `error`; No → Connect failing still shows the Connect form, because the answer stays `fresh`. Doc sentence in `reference-app-rn.md` → First launch updated.
- **The launch read set `read` before the saved options.** Under a renderer that does not batch updates after an `await`, one render could see `read` with no saved start and flash the question on a phone that has a cadre. The options are now set first (`use-cadre.ts`, launch effect).
- **Tests:** added two hook tests in `test/react/use-cadre.spec.ts` — nothing saved reads as `read` with no party and a start keeps the party across Disconnect (the defect the implementer fixed in `start`, otherwise unpinned), and a read that throws reports `failed` (the branch the three-state value exists for). No implementer tests to cut; none were added.

**Found, not changed:**

- Flow 4's conditional tap depends on Maestro's `when: visible` waiting like an optional lookup; the flow's comment states the assumption, and the device-run ticket's Maestro row will show whether it holds. No tripwire added beyond that comment.
- The waiting node code hint under the question reads "Connect first, and the prompt to add the node opens" — slightly off when the screen offers Yes/No rather than Connect, but either answer ends connected; left as is.
