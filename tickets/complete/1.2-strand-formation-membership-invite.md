# Complete: formation admits the joining party as its own member

Second ticket of the four-ticket party-identity chain (`strand-party-member-key` → this → `strand-node-binds-member-peer` → `strand-party-removal-via-formation-e2e`). Ticket 1 gave the founder its own identity; this one gives the **joiner** one. A closed-strand formation result now carries a single-use strand membership invitation, and the joiner's node mints (or reuses) and persists its own party key. Automatic redemption at strand bring-up is deliberately the NEXT ticket; this one ends with the invitation delivered, shape-checked, staged in memory, and the party key persisted.

## What landed

**Wire/type layer** (`types.ts`, `strand-formation-protocol.ts`): new `StrandMembershipInvite` interface (`{ inviteKey, invitePrivateKey }`, structurally identical to `strand-membership-writer`'s `IssuedInvite` but declared in `types.ts` so the wire layer never imports the writer). `FormationProvisionResult` and `FormStrandResult` gained optional `membershipInvite`. New exported `isWellFormedMembershipInvite(value)` — exactly two non-empty base64url strings, each capped at 256 chars — and `isValidResponderCreatesResult` now rejects a result whose `membershipInvite` is present but malformed (absence stays legal). No contact-message or control-schema change.

**Responder** (`strand-formation-manager.ts`, `strand-solicitation.ts`, `cadre-node.ts`): `StrandFormationManagerOptions` (threaded through `StrandSolicitationServiceOptions`) gained an `issueMembershipInvite(strandId)` hook, force-wired by `CadreNode.initializeStrandSolicitation` — like `resolveStrandAddrs` — to `CadreNode.issueStrandMembershipInvite`: open strand → `null`; closed strand → `issueInvite(liveStrandDb, { managerKeyPair: strandMemberKeyPair(StrandPartyKey row), expiration: now + MEMBERSHIP_INVITE_TTL_MS })`; closed strand with a vanished `Strand` row / no party key / no live runtime → throw. The manager calls the hook on the **bound** branch of `provisionAsResponder` before `recordUsage`, so a throw becomes a clean rejection with the exported `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` while the formation token is still unspent. `MEMBERSHIP_INVITE_TTL_MS` is 7 days. Disclosure timing is unchanged: the invitation rides `provisionResult` in the approval frame only.

**Joiner** (`cadre-node.ts`): `CadreNode.formStrand`, after recording cross-party strand addrs, sees `result.membershipInvite` and (1) calls `ensureStrandPartyKey(strandId)` — reusing a stored `StrandPartyKey` row on a re-join, minting + persisting otherwise — then (2) stages the invitation in an in-memory `pendingMembershipInvites` map exposed via public `getPendingMembershipInvite(strandId)` (the seam the next ticket's bring-up reconciler reads). A party-key persistence failure fails `formStrand` loudly, naming the spent token; nothing is staged in that case. The map is deliberately not persisted, documented alongside `crossPartyStrandAddrs`.

**Reference apps**: zero code changes — `membershipInvite` is optional and the new failure reason surfaces through the existing `Formation rejected: <reason>` path.

**Docs**: `docs/strands.md` (Closed-Strand Member Key Handling — the joiner-mint path), `docs/architecture.md` (formation sequence diagram + Strand Membership Bootstrap), `docs/strand-contracts.md` + `docs/strand-contracts-review.md` (prerequisite status advanced to "identities landed, automatic Member seating pending").

## Review findings

**What was checked.** The implement diff read first, before the handoff summary: wire/type layer, manager ordering and rejection parity, the `CadreNode` responder issuer and joiner adoption, the `Strand.Invite` / `ConsumedInvite` schema constraints the issuance has to satisfy, the recorder seam the issuance was ordered against, both new unit specs, the extended integration scenario, and every doc file the change touched (plus `docs/strand-contracts*.md`, which it correctly updated). Angles: single-purpose functions, DRY, error handling, type safety, resource cleanup, disclosure timing, hostile-responder input handling, source-file size.

**Fixed in this pass — a regression the handoff missed.** `blind-relay-phone-to-phone-e2e` failed on this change: `ConstraintError: CHECK constraint failed: AuthorizedInsert`, surfaced as the new "formation approved but persisting this party's membership identity failed" error. Its joining party (B) was a bare node with no owner genesis, so the new owner-signed `StrandPartyKey` write is refused and the whole join now fails. The handoff's "every sibling workspace green" was recorded without running the full integration suite; the scenario had been noted as "the field rides along untested there", which turned out to mean "untested and broken". Fixed the way the cross-party seed scenario handles its own joiner — `makeOwnOwner(B, bKey)` after `B.start()`, with the reason stated at the call — and, since the scenario is now the only **relay-routed** exercise of the new field, added assertions that the invitation crossed the circuit, that B's own party key persisted, and that the invitation is staged. This closes the handoff's "no relay-routed run of the new field exists" gap. `blind-relay-phone-to-phone-e2e` **1/1** after the fix.

**Fixed in this pass (minor).**

- `CadreNode.issueStrandMembershipInvite` checked for a live strand runtime *before* checking for the party identity, which made the identity branch unreachable without standing a strand runtime up — so the documented failure branch had no test. Reordered to identity-then-runtime (both map to the same retryable rejection, and the identity check is the cheaper read and the more actionable diagnosis when both are missing), and its rationale is stated at the site.
- The responder-side issuer had no unit coverage at all — the handoff's "there is exactly one production implementation and it is tested" rested on the integration happy path. New `cadre-core/test/cadre-node-issue-membership-invite.spec.ts` (4 tests) pins the four branches that decide whether a bound redemption is approved: open strand → `null`, vanished `Strand` row → throw, missing `StrandPartyKey` → throw, runtime not live → throw.
- The manager's second-layer defense (`membershipInviteFrom` dropping a malformed invitation that a custom `FormationResponseValidator` waved through) was described in comments but only the default-validator floor was tested. Added a test driving a permissive validator and asserting the malformed invitation is dropped rather than carried.
- `isWellFormedMembershipInvite`'s length bound was only tested one character *over*; added the inclusive-boundary case so a future longer key encoding cannot be broken silently.

**Filed as a ticket (major).** `backlog/bug-formation-issues-invite-before-approval` — the membership invitation is issued before the recorder consults the approval hook, because `ControlFormationUsageRecorder.recordUsage` fuses "ask the approver" with "write the consent row" and only the second half needed to come after issuance. Every refused, malformed, or unenrolled approval on a bound closed-strand redemption therefore commits one permanent, unusable `Strand.Invite` row (insert-only; its expiry stops redemption, it does not remove the row), and a refused joiner's token stays unspent by design, so retries repeat it. Nothing is disclosed to the refused joiner — this is durability and write amplification, not a leak. Filed at the boundary-invariant rung rather than as a point fix: the invariant is "no strand-side side effect until the redemption is fully authorized", and splitting the recorder's approve/record seam also covers the multi-use seat race that fails in the same window. `repro: static` — the existing deny-hook integration cases are all unbound or open; the ticket names the bound+deny scenario that would confirm it.

**Recorded as a tripwire, not a ticket.** The schema's `InviteValid` gate requires the issuing key to be a `Strand.Manager`, and only the founding party's key is seated as one. A party that *joined* a strand could therefore never issue invitations into it — but it also cannot host a bound formation today, because a joiner never receives the host strand's control `Strand` row and `resolveStrand` reports `missing`. Genuinely conditional, so it is a `NOTE:` on `issueStrandMembershipInvite` saying that a future re-invite / multi-hop-join feature needs manager delegation, not a retry, since every such redemption would otherwise reject forever with a retryable-sounding reason.

**Checked and deliberately left alone.**

- `issueStrandMembershipInvite` re-reads the `Strand` row that `resolveStrand` read moments earlier. One extra control read on a path that already does several, and the re-read is what detects a concurrent unpublish; not worth coupling the recorder's resolution to the hook's signature.
- The `(strandId: string) => Promise<StrandMembershipInvite | null>` hook signature is spelled out six times across the manager and the solicitation service. Exactly the shape `resolveStrandAddrs` already has in the same files; extracting a named type for one and not the other would be worse than either.
- The joiner adopts on `membershipInvite` presence alone, without cross-checking that the strand is closed. A hostile responder can therefore make a joiner mint one junk `StrandPartyKey` row. Gating on `memberPrivateKey` would be wrong (a closed strand row may legitimately carry a null one), and the cost is a single removable row per hostile formation.
- `cadre-node.ts` is 6,648 lines and this ticket added ~150. Already claimed by `backlog/debt-cadre-node-single-file-size`; no new arm needed.
- `docs/architecture.md` states the "never an invitation-less closed join" guarantee flatly, which holds where the hook is wired — always, in production, and the handoff already records the mock-manager caveat.

**Empty categories.** No considered-and-declined findings: no accepted-tradeoff `NOTE:` exists at any site this diff touches. No blocked-worthy findings: nothing here needs a human decision or an out-of-repo dependency.

## Known gaps carried forward (unchanged from the handoff)

- The joiner-side unit spec stubs the solicitation service rather than dialing; the joiner's real wire is covered by the (loopback) cross-party-seed scenario and, since this review, the relay-routed blind-relay scenario.
- Redemption in the integration scenario is explicit (`consumeInvite` by hand); automatic bring-up redemption, burn-on-already-member, and `MemberPeer` binding are `strand-node-binds-member-peer`, already in `implement/` with its prereq now satisfied.
- The pending-invite cache has no consume/clear API — the next ticket owns invalidation; until it lands, `getPendingMembershipInvite` keeps returning a spent invitation after a manual redeem.
- `issueStrandMembershipInvite` does not distinguish "instance hibernating" from "never launched"; both reject with the same retryable reason.
