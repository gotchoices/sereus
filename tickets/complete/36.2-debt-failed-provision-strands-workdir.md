# Complete: a provision that never spawns no longer strands its working directory

## What shipped

Two arms, as specified.

**Arm 1 — the failed spawn cleans up after itself.** `HostProcessOrchestrator.createContainer`
samples whether the working directory already existed *before* `ensureNodeIdentity` brings it into
being, and widens its `try` to cover the identity step. On any throw out of the launch, a directory
this attempt created is deleted (`discardWorkdir`); a directory it merely found is left alone,
because that directory holds the identity key and node-local stores that make a re-spawned node come
back as the same peer the borrower's cadre approved. `ensureOwnerNode` is deliberately excluded —
`<rootDir>/owner` is one fixed path holding the host's own control-DB storage.

**Arm 2 — reclaim by container name when no handle exists.** New public
`HostProcessOrchestrator.reclaimWorkdir(containerId)`, synchronous, refusing the owner id, a
containerId that still resolves to a live handle, a path outside `rootDir`, and (added in review) a
path that is not a directory. `DonationOrchestrator` gained an optional `reclaimWorkdir`;
`DonationService` calls it via `safeReclaimWorkdir` from both `reclaimStuckProvisioning` and
`terminate` when the record names no `dockerId`. Both call sites are needed: terminating a stuck
`provisioning` record moves it to `terminated`, which the stuck-`provisioning` reap no longer
matches, so without the `terminate` arm the reap has a bypass.

**Docs.** `docs/cadre-host.md` — the "a respawn attempt that fails leaves the host exactly as it
found it" paragraph now states the behaviour that holds (first spawn deletes, re-spawn keeps, owner
excluded, mid-spawn-crash covered by the two reclaim-by-name call sites) instead of pointing at a
backlog ticket file that no longer exists.

## Review findings

### Checked

Read the implement diff (`0fc2df7`) before the handoff summary. Traced the whole unwind path by
hand: `createContainer` → `ensureNodeIdentity` → `dropStaleHandle` → `allocateNodePorts` →

`terminate`, `reapStaleProvisioning`, and `DonationSupervisor.reconcileOne` (which early-returns on
a record with no `dockerId`, so `giveUp`'s deliberate keep-the-workdir behaviour is genuinely
unaffected — confirmed, not assumed). Checked the wiring in `bin/host.ts` passes the real
`HostProcessOrchestrator`, so the optional capability is structurally type-checked at that call.
Read every added test. Checked test-fixture hygiene — the escape-guard test creates a directory
outside `rootDir` but inside the suite's `mkdtempSync` root, which `afterEach` removes.
Re-read `docs/cadre-host.md` and grepped the whole repo for surviving references to the ticket slug:
none.

### Fixed in this pass (minor)

- **`reclaimWorkdir` would delete a plain file, including `<rootDir>/state.json`.** It gated on
  `existsSync`, which is true for a file, and `discardWorkdir`'s `rmSync(recursive, force)` removes
  files as readily as trees. `rootDir` is not only container directories — `state.json` is the
  orchestrator's own persisted handle map. Unreachable with real `grn_<base64url>` container ids, but
  the function's sibling guards (owner id, path escape) are explicitly defence-only for the same
  class of caller, so the missing one was an inconsistency with a large blast radius. Now gates on
  `statSync(..., { throwIfNoEntry: false })?.isDirectory()`. New test: *refuses an id that names a
  file rather than a workdir*.
- **`discardWorkdir`'s docstring claimed something false of one of its callers.** It said "every
  caller here has established no process ever attached to this directory" — true of
  `createContainer`'s unwind, but not of `reclaimWorkdir`, whose whole purpose is a host that died
  mid-spawn, and which `DonationService.reclaimStuckProvisioning`'s own docstring says can leave an
  orphan process running with that directory as its cwd. Corrected. The behaviour is unchanged and
  correct — a removal blocked by a live cwd handle logs and leaves the directory, which is no worse
  than the pre-existing strand.
- **`removeContainer` duplicated the rmSync-and-swallow block.** Folded onto `discardWorkdir` with
  the retry pair as a parameter, so its longer retries (20 × 200ms, because that path has just killed
  a child that held the directory) stay visible at the call site instead of being a second copy of
  the same four lines.

### Recorded as tripwires, not tickets

- **`reclaimWorkdir` can delete a workdir out from under an orphan process** left by a previous
  host's mid-spawn death. On Windows the removal fails and logs; on Linux it succeeds and the orphan
  loses its config and storage. Acceptable today — such a record was never seeded, so it carries no
  borrower data, and it is being terminalized anyway — and it only becomes work if the host ever
  gains a real orphan-*process* sweep, which `reclaimStuckProvisioning`'s docstring already names as
  the missing piece. Parked in `discardWorkdir`'s docstring.
- **`discardWorkdir`'s 5 × 100ms retry budget is a judgement call, not a measurement.** The
  reasoning (and the case where it does not hold) is now stated in that docstring; if reclaimed
  directories start surviving in the wild, that is the number to raise.
- **The `terminate` ↔ in-flight-`provision` race** — a delete landing between a concurrent spawn's
  `mkdirSync` and its `spawn` — was already documented at the `terminate` call site by the
  implementer, is self-healing (`provisionLocked`'s post-spawn re-read reclaims the child), and
  strictly better than the permanent strand it replaces. Left as written; no test.

### Filed / amended

- **No new tickets.** Nothing found rose to a root cause needing its own site.
- **Amended `tickets/backlog/debt-host-process-orchestrator-untested.md`.** That ticket's premise —

### Deliberately not pursued

- **The two untested paths the handoff flagged** — `ensureNodeIdentity` failing part-way through
  `generateIdentity` on a fresh directory, and `<rootDir>/<containerId>` existing as a plain file —
  were re-derived by reading rather than executed, and both come out where the handoff said. The
  first would need a filesystem-level stub the suite has no precedent for, and introducing that
  machinery to pin one branch of an already-correct unwind is not worth its maintenance cost. The
  second is deliberate behaviour in `createContainer` (nothing is deleted, `mkdirSync` throws and
  propagates); the reclaim side of the same hazard *is* now guarded and tested, per the fix above.
- **`safeReclaimWorkdir` swallowing the return value.** Nothing branches on it, and both
  `FakeOrchestrator` and the real class document the gap. Adding a branch nothing consumes would be
  speculative.
- **`cadre-provider`** — untouched and correctly so; its `DockerOrchestrator.createContainer`
  already runs the same created-it-so-remove-it unwind against its durable volume. This work brings
  cadre-host to that precedent.
- **`docs/cadre-host.md`'s paragraph is long.** Accurate and matching the code, which is the bar;
  restructuring it is not this ticket's work.

### Not applicable

No security surface, no public API for external consumers (`reclaimWorkdir` is host-internal, reached
only through the optional `DonationOrchestrator` capability), no schema change, no performance
dimension — every path here runs at most once per failed spawn.
