# Invitation and owner-grant chains kept in memory until they change

## What landed

`ControlDatabase` keeps seven membership views instead of three. `CadreInvite`, `CadreInviteUsage`, `OwnerGrant` and `OwnerGrantUsage` are built by the existing `membershipView(sql, label)` helper and registered in `membershipViews`, so the existing table-change subscription and `invalidateMembershipViews` cover them. `queryCadreInvites`, `queryCadreInviteUsages`, `queryOwnerGrants` and `queryOwnerGrantUsages` read through `readMembershipRows` and map each row to a fresh object. The redemption path's point reads (`queryCadreInvite`, `queryOwnerGrant`) and indexed usage counts stay plain SQL. The old "memoise verified pairs" NOTEs are gone; the ed25519 verify cost they recorded is now an accepted-tradeoff `NOTE:` in `hasAnchoredProof`. `docs/architecture.md` → "Membership rows view" lists the seven tables and explains why the chain tables are safe to serve stale for admission (append-only, so a stale copy only lacks rows, which fails closed).

The code shipped across two commits: the bulk was picked up by a concurrent runner commit for another ticket, `ticket(implement): strand-watcher-change-driven-verification`, and `ticket(implement): control-invitation-and-grant-chains-cached-until-changed` added a one-space fix to `CADRE_INVITE_SELECT_SQL`.

## Review findings

Read the diffs of both commits (this ticket's files only), then the views machinery (`membershipView`, `readMembershipRows`, `watchMembershipTables`, `MembershipView`), every caller of the four queries, and the docs section.

- **Correctness, admission path: no defect.** `loadInvitationChain` / `loadOwnerGrantChain` and the membership refresh never run inside `inTransaction`, and `readMembershipRows` reads through directly for a caller under the write lock with a transaction open, so uncommitted rows are never cached. A local commit fires the change hook inside the commit (read-your-writes). All four row mappers build new objects, so cached raw rows are never shared or mutated. The `CADRE_INVITE_SELECT_SQL` spacing fix is in place.
- **Correctness, machine removal: the docs overstated the claim; fixed inline, tripwire parked.** The "a stale copy fails closed" argument holds for admission only. `CadreNode.planMachineRemoval` (through `listCadreInviteStatuses` and `queryCadreInviteUsages`) now also reads through the views. There a missing row fails open: an invitation the machine could return through goes unwithdrawn. Before this change, a plain read of a block this node does not hold went to the cohort and was fresh. Now, on a node outside the block's cohort, an invitation issued elsewhere in the last 15 s (`MEMBERSHIP_VIEW_MAX_AGE_MS`) can be missed. That needs a cadre larger than the replication breadth and a removal within 15 s of the invitation being issued, so it is a tripwire, not a ticket. Added a sub-paragraph to "Membership rows view" in `docs/architecture.md` and a `NOTE:` at `planMachineRemoval` in `cadre-node.ts`.
- **`hasLiveCadreInvite` (the implementer's open question): not decided here.** While this review ran, another run's uncommitted edit in the working tree was moving `hasLiveCadreInvite` onto `queryCadreInvites()` and updating the doc's "What is kept" line to match. That edit is not this ticket's, so I left it alone and did not add `hasLiveCadreInvite` to the doc's "stays plain SQL" list.
- **Tests: none added, none cut.** The change adds one map entry and one read route per table; `membership-view.spec.ts` already pins the caching rules. The removal-window finding is a tripwire, not a defect worth a reproduction test.
- **Docs.** `membership-view.ts` module doc, `readMembershipRows` doc, `membershipViews` field doc, `loadInvitationChain` / `syncOwnerAnchor` docs and `docs/architecture.md` all describe the new state. The only correction needed was the removal caveat above.
- **Hygiene, DRY, types, resource cleanup: nothing found.** The four views reuse the existing helper, subscription and close path; no new `any`; the new select constants sit beside their mappers.
- **Performance: unmeasured.** The before/after `message-cost-accounting` invite measurement was not run (the implementer could not measure "before" without reverting the tree). `control-reconcile-woken-by-changes-reads-once` re-runs that scenario.
