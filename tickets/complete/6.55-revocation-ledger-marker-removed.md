# Revocation ledger marker: filing path removed

The marker is the row `('Revocation', 'ledger', 'opened')` in `CadreControl.Revocation`. An owner machine used to file it on its first connected reconcile pass, only to give that table an Optimystic collection. `control-collections-created-at-cadre-founding` now commits every control table's empty collection at genesis, so the filing path was removed (`ticket(implement): revocation-ledger-marker-removed`).

**Removed:** `ControlDatabase.openRevocationLedger` and its guard and conflict helpers; `SeedBootstrapService.openRevocationLedger`; `CadreNode.openRevocationLedgerIfDue`, its flag, and the filing step (with its accepted-tradeoff NOTE) in `runReconcileControlCohort`; the `RevocationLedgerOpenResult` type; the marker spec file and its ESLint exemption; the marker section of `cadre-node-control-cohort.spec.ts`; and the degraded-member scenario's `beforeAll` step that filed the marker while the cohort was healthy. `execTombstone` now takes only `RevokedRowRef`.

**Kept for parties that already hold a marker:** `REVOCATION_LEDGER_MARKER` (now module-private), `queryRevocations`' skip of it, and the `RowIsGone` branch that admits it. The schema edits are comment-only, so `CONTROL_SCHEMA_VERSION` stays 3. The branch carries a `NOTE:` to drop it, the constant and the skip together with the next schema-version change that already needs a migration.

**Docs:** `docs/architecture.md`'s `Revocation` row, the background-writers list and the "What stays plain SQL" list; `docs/cadre-consistency.md`'s write-lock paragraph. On the board, `debt-revocation-ledger-marker-live-network-scenario` was deleted, and the ledger marker was removed from the background-writer list in `feat-owner-key-on-a-hardware-key`.

Implement-stage validation: lint and typechecks clean; cadre-core 2520 passed, 1 skipped; `control-write-degraded-cohort-member` 7/7 in one full run (stalled cases 84–105 s, none queued behind a second failing write).
