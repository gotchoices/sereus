# The founder's strand rows land in one transaction

## What changed

**Bootstrap shape** (`bootstrapFounderMembership`). It now reads, then writes once:

- Reads the `Header` count. Runs the pre-split check (`assertNotPreSplitStrand`) only when the Header was already present: a strand founded before the key split always committed its Header first, alone.
- Closed strand: reads the `Member` count, then `founderManagerMissing` (the `Manager` count, plus the sealed-strand `Revocation` scan when no manager exists, as before), then, only when the run seats the founding `Member` and a peer id was given, whether this machine's `MemberPeer` row exists (`memberPeerStampId`).
- When the Header was absent, commits the empty collections with `except` = exactly the tables the batch will write (`createDeclaredCollections(params, rows.map(r => r.table))`).
- Writes every missing row (Header → Member → Manager → MemberPeer) with `combineStatements` + one `execStrandTransaction` (default `joinOpenTransaction`). The per-row insert functions became statement builders. `registerMemberPeer` and the founding share `memberPeerInsertStatement`.
- A torn-commit `NOTE:` tripwire sits at the founding write, as the ticket asked.

**Plugin.** `createEmptyCollections(db, bridge, schemaNames, except = [])`: excluded tables are not opened or asserted registered. Every registered collection whose id is an excluded table's main id, or starts with `<main id>/index/`, is skipped. An `except` name that matches no declared Optimystic table throws; the match is case-insensitive, like SQL identifiers. `SereusPluginResult.createEmptyCollections` and `FounderBootstrapParams.createEmptyCollections` take `(except?)`. The control genesis caller is unchanged (it passes no `except`).

**Peer id plumbing.** `StrandDatabase.bootstrapFounder` passes `founderPeerId = libp2pNode.peerId.toString()` for a closed strand when `StrandDatabaseConfig.bindFounderPeer` is true. That node is the same object the reconciler reads (`instance.libp2pNode = node` in `buildStrandRuntime`). `StrandInstanceManager.buildStrandDatabase` sets `bindFounderPeer: config.membershipReconciliation?.enabled !== false`. Both founding paths (`initialize` and `ensureFounderBootstrap`) go through `bootstrapFounder`.

## Two deliberate deviations from the ticket — please weigh them

1. **The binding joins only a run that seats the founding `Member`.** The ticket read `MemberPeer` whenever a peer id was given. But on a founder restart where the founder's own `Member` row has since been removed (it left, or a later manager revoked it while other members remain), a binding insert fails `MemberPeer.MemberExists`. That would refuse the whole founding transaction and fail every bring-up of that strand. The reconciler today only binds once it sees this party's member row, so it never hits this. Gating on "this batch seats `Member`" avoids it, and it also keeps restarts from paying an extra `MemberPeer` scan. The cost: a healing run after a torn commit that saved `Member` but not `MemberPeer` leaves the binding to the reconciler, which writes it as its own commit, the way it does today.
2. **`bindFounderPeer` is false when the reconciler is disarmed.** The `enabled: false` contract says it is for fixtures that hand-drive the membership writers and assert exact row sets. `strand-membership-closed-strand-e2e` disarms it and asserts "exactly one MemberPeer row" after binding the joiner. Writing the founder's binding unconditionally would break that contract. The gate does not require a party key at launch, so the in-place founding of an instance launched as a joiner without a key (no reconciler armed) still gets its binding in the founding.

## Review findings

Reviewed the diff of `ticket(implement): strand-founding-writes-batched` first, then the handoff above.

**Checked, no defect found:**

- **Batch shape.** `combineStatements` throws on a duplicated parameter name; the founding fragments use distinct names (`header*`, `founderMember*`, `founderManager*`, `peer*`), so the closed batch binds cleanly. `execStrandTransaction` runs it as one `exec(..., { transaction: true })` and joins an open transaction only on the in-place founding path, the same join behaviour the old per-row `db.exec` calls had.
- **Constraint order inside one transaction.** The checks that read another founding row (`OnlyClosed`, `Manager.MemberExists`, the bootstrap branches, `MemberPeer.MemberExists`) defer to commit. `Member.Authorized`'s bootstrap branch reads `committed.Member`, which is empty before the founding, so it still holds. The closed-strand spec and the network-transactor parity spec both commit the full four-table batch.
- **Exclusion list (plugin).** Index and unique-enforcement trees live at `<main uri>/index/<name>` in `../optimystic`'s `optimystic-module.ts`, which matches `belongsToExcludedTable`. An unknown `except` name throws before any table is opened. The control genesis caller passes no `except`, so it is unchanged.
- **Reads moved before the empty commits.** `Member`, `Manager`, `Revocation` and `MemberPeer` are now read before their collections exist, where only `Header` was before. This adds no new failure mode: a founder whose cohort cannot prove a collection absent already fails on the `Header` read, which comes first. The re-pinned budgets record what the extra reads cost.
- **Peer id.** `StrandDatabase` gets the same `node` object that `buildStrandRuntime` stores as `instance.libp2pNode`, and the reconciler binds `instance.libp2pNode.peerId`, so both bind the same id.
- **Deviation 1 (the binding is written only on the run that seats `Member`)** is accepted. The failure it avoids is real: on a restart after the founder's `Member` has been removed, `MemberPeer.MemberExists` would refuse the whole batch. The cost is the reconciler's own commit after a torn founding, which is acceptable.
- **Deviation 2 (`bindFounderPeer` follows the reconciler's `enabled` flag)** is accepted. It keeps the `enabled: false` fixture contract ("sees only the rows it wrote").
- **Pre-split check moved behind `headerPresent`.** This is sound. A strand founded before the split committed its Header alone, before its other rows, so a strand with no Header cannot have pre-split rows.
- **Docs.** `docs/architecture.md` (Strand Membership Bootstrap, and "Every control table has a collection from genesis"), `docs/strands.md`, the plugin README, and the `types.ts` / `strand-first-sync-gate.ts` / `strand-instance-manager.ts` comments all describe the one-transaction founding. A grep for the old names (`insertFounderMemberIfAbsent`, `foundIfHeaderAbsent`, "before its Header") finds only history lines in the budget specs.
