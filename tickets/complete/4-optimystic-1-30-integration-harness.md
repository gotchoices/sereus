# Complete: the integration harness opens one node storage per scope

Fourth of five tickets adopting Optimystic 1.30.0. Implemented in `ticket(implement): optimystic-1-30-integration-harness`, reviewed and amended in this pass. Tickets 1, 2 and 3 are in `complete/`; ticket 5 (release notes and the board fold) is the only one left.

## What landed

`RawStorageCapture.provider` became `open(scope): Promise<NodeStorage>`, still memoized per scope; `forStrand`, `control` and the coverage helpers keep taking and returning the **block** store, because nothing in the package reads a scope's key-value or blob-piece store through the capture. The capture's factory takes the scope (`(scope) => NodeStorage`), which is the one deviation from the ticket's letter and the right one — see the first item under "The deviations the handoff asked to have weighed".

`ControlNodeOpts.storageProvider`, `TopologyMachineSpec.storageProvider` and `PinningMemberOptions.storageProvider` kept their names and were retyped to a new `NodeStorageOpener` in `node-fixtures.ts`, read off `StorageConfig['open']` rather than re-spelled. `slowMemoryStorageProvider` returns a `NodeStorage` whose `blocks` alone is the slow wrapper, and gained the `deleteBlock` the 1.30 interface requires. `test-party.ts` passes `memoryNodeStorage()` as a value. `strand-offline-waits-for-party-machine`'s phone became file-backed, one directory per scope, with its offline journal taken from that scope's own key-value store; the child-process fixture `strand-restart-party.mjs` did the same and now closes the opened storages where it used to close the journals. `control-delete-while-alone-convergence`'s two nodes take captures instead of one store pinned to every scope. Everything else was the `capture.provider` → `capture.open` rename across 25 scenario files plus the comments that named the retired contract.

**The assertion that inverted.** `strand-client-node-holds-no-blocks` step 3 used to assert the client's provider was never asked for the strand's scope. Under 1.30 it is asked — a client keeps the strand's clock high-water mark, blob records, owed-blob ledger and blob pieces — so the step now asserts the scope IS opened and the client's block store holds nothing, while both serving machines hold every block (measured on the run: 45 committed blocks on server 0, none on the client).

## Review findings

Read the implement diff first, then the handoff, then the upstream contracts the diff leans on (`NodeStorage`, `IRawStorage`, `withReadCache`, cadre-core's `StorageConfig` and `node-storage-cache.ts`). Checked by reading, and by running: `yarn lint`, the suite's typecheck, its 7 unit spec files (94 tests), and 7 scenario tests across the three reworked scenarios.

### Fixed in this pass (minor)

- **The one emptiness claim in the package was read through a committed-only index.** `strand-client-node-holds-no-blocks` step 3 asserted "the client stores none of the strand's blocks" from `readBlockIndex`, which drops any block whose metadata carries no committed revision. `IRawStorage.listBlockIds` yields one id per block with ANY durable state, pending-only blocks included — so a client that had written pending transforms into its own block store would have passed the assertion the handoff called "the stronger thing". Added `readDurableBlockIds` to `block-store-probe.ts` (both readers now share one `durableBlockIds` guard, so the refusal of a backend without `listBlockIds` still has one home and `readBlockIndex` still streams), and re-aimed the step at it. It passes: the client's block store holds no durable state of any kind, which is what the step claims.
- **`slow-raw-storage.ts` claimed a determinism this release took away.** Its header said multiplying per-operation latency is "a DETERMINISTIC way to make bring-up take a chosen number of seconds". cadre-core now fronts every scope's block store with a leased read cache (`node-storage-cache.ts`), which passes a `MemoryRawStorage` through untouched but not this wrapper around one — so a block read the cache already holds never sleeps, and bring-up costs the operations that MISS the cache, not the operations issued. Corrected the claim and recorded the mechanism as a `NOTE:` with the measured margin: `control-bring-up-quiet-period` at `storageOpDelayMs: 50` brought up in 4,639 ms against the 1,000 ms bootstrap fuse it has to clear, and `control-start-storage-op-budget.spec.ts` passes.
- **That scenario's own arithmetic had gone stale with it.** `STORAGE_OP_DELAY_MS`'s rationale read "48 × 50 ms = 2400 ms as measured today"; measured today it is 4,639 ms, so more than 48 operations reach the slow store under 1.30. Updated the figure, kept the floor argument (24 × 50 ms = 1200 ms, still past the fuse) and labelled it a floor rather than a forecast, with a pointer to the cache note.
- **`ControlNodeOpts.storageProvider` described the default wrongly.** It said "one fresh `memoryNodeStorage()` per scope", which reads as memoized; the default mints one per CALL, which is why a scope opened a second time starts empty and why `captureRawStorage` memoizes. That distinction is the whole difference between `strand-reattach-first-sync-measure`'s `reattach-kept` and `reattach-empty` arms, and that file states it correctly — so this was the one place a reader would have been misled.
- **`slowMemoryStorageProvider` re-spelled the opener signature a fourth time.** The handoff's own reason for `NodeStorageOpener` was that three seams should read the signature off the config instead of copying it; the producer in `slow-raw-storage.ts` then spelled `(scope: string) => Promise<NodeStorage>` by hand. Now typed `NodeStorageOpener`, as a type-only import so there is no runtime cycle with `node-fixtures.ts`.

### Tripwire

- **`strand-offline-waits-for-party-machine` intermittently leaves one empty directory in the OS temp directory.** Seen once in 8 test executions on 2026-11-26: `<temp>/sereus-offline-hold-*/storage/<strand id>/under-replicated` survives a run whose four tests all passed. A ledger write lands after both `CadreNode.stop()` and the storage's `close()` and recreates the path `rmSync` has already removed, so retrying the removal would not catch it — and a write to a store the contract says is "not usable afterwards" is the part worth knowing about. Parked as a `NOTE:` at the cleanup site in that scenario, with what to look for if it ever costs more than one empty directory. Not filed as a ticket: the cost today is litter in a temp directory, the writer is unidentified (it may be a monitor inside Optimystic's node rather than anything in this repository), and one intermittent empty directory is not enough evidence to name a site.

### The deviations the handoff asked to have weighed

**1. The scope-taking capture factory is right; keep it.** The alternative the handoff offered — a bespoke file-backed `open` built outside the capture — costs the scenario `phoneCapture.forStrand(strandId)`, which is the assertion that proves the phone physically holds the blocks the node must then cover. And `StorageConfig.open` is itself scope-taking: a capture whose factory cannot see the scope models a narrower contract than the one under test, and would make a file-backed capture impossible for the next scenario that needs one. The memo means the factory is still called at most once per scope, so none of the capture's existing guarantees changed.

**2. Making the phone file-backed is an acceptable change in what that scenario exercises.** It is the only configuration Optimystic permits, since it refuses a `MemoryKVStore` journal outright, so the alternative is not a lighter phone but no journal at all. Re-run here: 4 of 4, 68.9 s of test time, step timings ordinary. It also widens coverage rather than only costing it — this is now the one scenario in the package whose block store is read-cached by cadre-core (`withReadCache` skips a `MemoryRawStorage`, which every other machine in the package has), so the cached path gets exercised at all. The cost found is the tripwire above.

**3. `control-delete-while-alone-convergence`'s header rationale holds.** Verified rather than taken on trust: the file contains no `addStrand`, no strand creation and no strand publication, so the control database really is the only scope either node opens and `capture.control()` is the whole story. The comment does warn the next author, which is what was asked of it.

**4. The client-holds-no-blocks assertion was not as strong as claimed; it is now.** See the first fixed item. The remaining limit the handoff named is real and inherent: it proves the store is empty at the moment it is read, after the client has written and read through the serving machines, not that nothing could land there in a longer run. The step's comment says what it reads, which is the honest form.

### Considered and left alone

- **`storageProvider` still names a contract that no longer exists.** "Provider" was `RawStorageProvider`, which 1.30 retired; the option is now an opener. 65 references across 34 files, every one mechanical. Left as it is: the rename is pure churn across the whole scenario corpus for one word, the type beside it (`NodeStorageOpener`) already says what the value is, and a reader at any call site sees `capture.open` on the right-hand side. Worth folding into the next change that touches these files for another reason.
- **`captureRawStorage` holds every storage it opened but offers no way to close them.** That is why `strand-offline-waits-for-party-machine` keeps a parallel `opened: OpenNodeStorage[]` filled from inside its factory — the capture's own map, duplicated for lifecycle. A `closeAll()` would remove the duplication, but it would also put lifecycle into a module whose single purpose is observation, against upstream's own rule that whatever built a storage closes it, and there is exactly one file-backed consumer. Revisit when there is a second.
- **`SlowRawStorage` forwards none of `getStoreIdentity`, `getApproximateBytesFree` or `close`.** All three are optional by design upstream, and omitting them is the documented way to report a capability the wrapper does not have. No consequence here: one instance per node makes identity-based cache sharing moot, and a memory store reports no free space anyway. Pre-existing, and not worth stubs that would lie.

### Checked and found correct

- **The capture's two guards and its scope-collapse detection.** `control()` still throws rather than minting an empty store, `forStrand` still refuses a control key, and the collapse check still compares block-store identity — so a factory that returns a distinct `NodeStorage` wrapper per scope while sharing one `blocks` is still caught. Its spec covers the same eight behaviours as before, none added, none removed.
- **Every other `readBlockIndex` caller.** Swept them: the five remaining uses are positive floors (`size` above a bound, `arrayContaining` a collection name). The committed-only filter is right for each; the client step was the only emptiness claim in the package.
- **Close ordering and holder counting, both file-backed sites.** The scenario and the `.mjs` fixture each memoize per scope, so `fileNodeStorage` is called once per directory and closed once — which matters because that factory counts holders per directory, and a second unmemoized call would be a second holder needing a second close. Both close after the node has stopped, both even after a failed stop, and the fixture still exits 1 when a close fails. The fixture now closes on non-offline runs too, where before only the offline journals were closed and the file block stores never were.
- **The offline journal really is the scope's own key-value store.** `StrandOfflineConfig.journal` accepts an async resolver, so `async (scope) => (await phoneCapture.open(scope)).kv` is a legal journal, and the memo makes it the same store cadre-core opened for that scope. Optimystic declares the journal's key prefix in `NODE_KV_NAMESPACES` precisely so one store can serve the node and the journal, which is what the comments at both sites say. `strand-offline-queue-survives-restart` proves it end to end across a real process restart: the queued write survived and committed exactly once.
- **No concurrency hole in the capture's memo.** `open` is async but sets its map entry in the same tick as the factory call, with no `await` in between, so two concurrent first asks for one scope cannot both open. The factory is synchronous by type, which is what makes that hold.
- **`control-node-config.spec.ts`'s reshaped case is the better test.** Asserting opener identity (`built.storage.open === open`) pins what a capture actually needs — that the builder neither wraps nor re-memoizes — where the old one-store-for-every-scope demonstration pinned a configuration a caller can no longer write. Deleting `storeForScope` with the single-instance form it resolved is correct; there is no union left to narrow.
- **Documentation.** `docs/contributing/testing.md` is the anchor and genuinely says nothing about this seam — its three storage mentions are about sizing deadlines from storage latency and about index collections — so nothing there went stale. Swept the whole of `docs/`, every package README and the root README for `RawStorageProvider`, `storage.provider`, `storageProvider` and `MemoryRawStorage`: no hits at all. The topology coverage map needs no change, since no scenario was added or removed.
- **Source hygiene.** Largest touched file is `node-fixtures.ts` at 668 lines, which this change grew by about a dozen; `block-store-probe.ts` is 330, the two reworked scenarios 341 and 473. Nothing near a size concern. The comments added carry constraints and consequences — why the capture memoizes, why only `blocks` is slowed, why the phone must be file-backed, why identity is the property the config spec checks — rather than narrating statements.
- **No new tests, as the ticket specified**, and none wanted. The one change to a test file is the re-aimed step above, which is a defect found in this pass rather than a new case. The eight capture cases became `async` and compare against `.blocks`; nothing was added to or cut from them.
