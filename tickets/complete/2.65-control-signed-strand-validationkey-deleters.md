# Complete: signed `deleteStrand` / `deleteValidationKey` writers on `ControlDatabase`

Closes the gap the prior ticket (`control-validationkey-strand-delete-authorization`) left
open: the schema already *required* an owner signature plus a matching `Revocation` tombstone
to delete a `Strand` or `ValidationKey` row, but only raw-SQL test helpers could produce that
pair. Production code now can.

## What shipped

**Writers** (`packages/cadre-core/src/control-database.ts`):

- `deleteStrand(strandId, ownerKey, signMessage)` / `deleteValidationKey(key, ownerKey,
  signMessage)` — read the row's current `StampId`, sign the `'remove'`-tagged authorization
  message over `(Id, StampId)` / `(Key, StampId)` (a digest distinct from the `'add'` one, so
  an enrollment approval can never be replayed as a removal), then commit the signed delete
  and the matching `CadreControl.Revocation` tombstone in one transaction. A no-op — no
  throw, no tombstone — when the row is already absent.
- `queryStrandStampId` / `queryValidationKeyStampId` — public stamp readers alongside the
  existing `queryCadrePeerStampId`.
- `queryRevokedStamps` now accepts all four guarded tables, via a new exported
  `RevocableTable` type.

**Structure (added during review):**

- The three stamp readers delegate to one private `queryStampId(table, keyColumn, value)`.
- The two deleters delegate to one private `deleteGuardedRow(...)` — they were ~95% identical.
- A private `inTransaction(label, body)` now holds the begin/commit/rollback-tolerating-a-
  failed-rollback dance that was pasted at three sites in the file (`deleteStrand`,
  `deleteValidationKey`, `redeemInvitation`).
- `RevocableTable` is `Extract`ed from `ControlTable` rather than re-listed as literals, so a
  renamed table is a compile error rather than a dead branch. Exported from
  `packages/cadre-core/src/index.ts`.

Net: 196 lines changed in `control-database.ts` for roughly 40 fewer lines than the
pre-review implementation, with the deleters' shared security rationale stated once.

## Review findings

### Checked and clean — no action

- **Digest field order vs the schema.** `Strand.AuthorizedDelete` verifies
  `digest('CadreControl.Strand', 'remove', old.Id, old.StampId)` and `ValidationKey`'s the
  `(Key, StampId)` equivalent (`schemas/control.qsql`); the writers build exactly those, in
  that order. Cross-checked against both schema copies.
- **Read-side filtering of resurrected rows.** Only `CadrePeer` drops rows whose stamp was
  retired (`CadreNode.listAuthorizedMembers`); `Strand` / `ValidationKey` do not. Investigated
  as a possible security gap — it is **deliberate and already documented** in the schema
  comment (`control-schema.ts`, `Strand.NotRevoked`): neither table has a per-request
  authorization surface today, and the comment already says to filter there if one appears.
  Nothing to change.
- **Schema drift between `schemas/control.qsql` and the embedded `control-schema.ts`** —
  guarded by `control-schema-drift.spec.ts`, which passes.
- **Rollback-on-failure semantics** — the swallow is narrowly scoped to a rollback that
  fails, the original error always propagates, and the secondary is logged. Correct; only
  moved, not altered.
- **Source file size.** `control-database.ts` is 1173 lines. Judged acceptable rather than
  split: it is a facade over eight tables, every method is short and single-purpose, and this
  pass reduced it. Flagging the number so a future reader can re-judge.

### Found and fixed in this pass (minor)

- **Duplication.** Two ~35-line near-identical deleters, three identical stamp readers, and
  three copies of the transaction/rollback block. Collapsed as described above.
- **Type narrower than needed, stated twice.** `queryRevokedStamps` took an inline four-literal
  union duplicating a subset of `ControlTable`. Replaced with the derived `RevocableTable`.
- **Stale test-file header.** `control-authorization-binding.spec.ts`'s docblock said the
  delete half lives entirely in `control-revocation-replay.spec.ts` — untrue once this ticket
  added writer tests to it. Rewritten to say which half lives where.
- **Stale doc.** `docs/architecture.md`'s "Delete-while-alone durability" paragraph attributed
  the tombstone-alongside-delete pattern to `removePeer` alone; it now names all three guarded
  deletes, since the new writers inherit exactly the same non-propagation limitation. The rest
  of the control-table documentation (the `ValidationKey` / `Strand` / `Revocation` rows in
  the schema table) was already written for this behaviour and needed no change.

### Test gaps found and closed (4 new tests, 855 → 859 passing)

The implementer's six tests covered happy path, missing-row no-op, `queryRevokedStamps`
integration, and the closed-strand case. Missing:

- **Re-add after removal, through the writers** (both tables). The tombstone retires one
  token, not the identifier — so add → remove → add must work, with a *fresh* token, and the
  old tombstone must survive. Asserted on both. The schema half of this was already pinned on
  raw SQL elsewhere; these prove the real writer pair composes.
- **Wrong signer, through the writers** (both tables). The writers hold the signing callback,
  which makes them the surface where a caller could wire up the wrong key. Both now assert the
  write is refused by the named `AuthorizedDelete` constraint (via `expectConstraintFailure`,
  so a mistyped statement cannot pass the test) and that the row survives.

### Recorded as tripwires, not tickets

- **Stamp read sits outside the transaction.** A concurrent writer removing the same row in
  between makes the signature bind a token that is no longer live. It fails safe — the delete
  matches nothing and the tombstone insert collides on `Revocation`'s primary key, so the
  transaction aborts rather than half-applying. Parked as a `NOTE:` in `deleteGuardedRow`'s
  docblock with the fix if concurrent owner-device removals ever become routine. The
  implementer flagged the same area as "no concurrent-delete test"; analysis says the shape is
  safe today, so it is knowledge, not queued work.

### Filed as new tickets (major)

- `tickets/backlog/feat-owner-approved-strand-key-removal.md` — **nothing in production calls
  these writers.** Confirmed by grep: zero callers outside the module and its tests.
  `CadreNode.removeStrand` still only stops the strand locally and never touches the shared
  table. Wiring this up needs a product decision about where an owner's approval to destroy a
  shared network comes from, so it is a spec ticket, not mechanical follow-up.
- `tickets/backlog/debt-share-transaction-rollback-helper.md` — `SeedBootstrapService.removePeer`
  is the fourth copy of the transaction/rollback block and, more broadly, a third copy of the
  whole signed-delete-plus-tombstone shape. Left alone here (different file, different class,
  outside this diff) but now trivially foldable into the helper this pass introduced.
