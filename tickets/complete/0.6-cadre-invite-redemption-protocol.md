# Redeem a cadre invitation at any member: complete

## What shipped (`ticket(implement): cadre-invite-redemption-protocol`)

The wire protocol `/sereus/cadre-invite/1.0.0` (`cadre-invite-protocol.ts`: the invitation bundle and its encoding, the two frames, the seven refusal codes with their retryability table, the member-side handler and the device-side dialer), the connection-gate rule (a stranger is admitted while this node holds a live `CadreInvite` row), and the node calls `createCadreInvitation`, `listCadreInvitations`, `withdrawCadreInvitation` and `redeemCadreInvitation`. The seed peer projection moved into `ControlDatabase.querySeedPeers` and the seed's peer-store merge became the shared `mergeSeedPeers`, both reused by the redemption reply. The old owner-online path and the enrollment window stay until `cadre-invitations-redeemable-by-any-member` removes them. The implement handoff's deviations from its ticket (the request carries the party id; the connecting identity is checked by deriving the key from the peer id; the reply echoes the request's row; a generic `Authorized` refusal at redemption is the final `invite-spent`; the reconcile pass is fired, not awaited) were each read against the code and stand.

## Review findings

**Read first:** the whole implement diff, with the schema (`schemas/control.qsql` `CadreInvite` / `CadreInviteUsage`), the seed and formation handlers it is modelled on, and the plan ticket it descends from; then the handoff. Lint, typecheck (cadre-core, and integration-tests against a fresh cadre-core build) and the full cadre-core suite run clean after the edits below: 153 files, 2399 passed, 1 skipped (the pre-existing skip). Log at `tickets/.logs/cadre-invite-redemption-protocol.review.test.log`.

**Major, filed to `blocked/` (one ticket):** the plan contradicts itself about a member that has not yet received the invitation row. The gate admits a stranger only while the member itself holds a live row, but the bundle carries the row precisely so a member without it can seat it. At an enrolled member with no live row the device's connection is refused before the protocol runs, so the "minted while the owner is alone, redeemed before the owner reconnects" claim in the implement handoff, the `createCadreInvitation` doc and the architecture section did not hold. Fixed in this pass by correcting all three to describe the real behaviour (the device's dial fails, it tries the next address, and it ends with the retryable unreachable error), with a `NOTE:` at gate check 7 pointing to `decide-cadre-invite-redeemed-before-the-row-replicates`, which proposes accepting the limit and names the alternative (drop connection-level stranger denial) as a human security decision. The follow-on ticket's scenario waits for the member to hold the row, so it is unaffected. Behaviour is safe either way: no device is admitted that should not be.

**Minor, fixed inline:**

- An unreadable request frame (read timeout, oversize, not JSON) was answered with the final code `invite-invalid`, so one slow link could stop a device from trying the other members. The handler now lets the read failure reach its catch-all and answers the retryable `internal`, as the formation responder does; the shape check after a successful read stays `invite-invalid`. The code's doc and the architecture codes table say so.
- The device's reply decoder folded a refusal code this build does not know into `internal`, which made the `'unrecognized'` branch of `CadreInviteRejectedError` unreachable and its doc false. The decoder now passes the code and reason through verbatim and the error class alone classifies them, matching the formation dialer.
- `nextMacrotask` was a copy of the one in `peer-dial.ts`; the original is exported and shared.
- Cut the test "needs the owner key" from `cadre-node-cadre-invitation.spec.ts`: it pinned a one-line guard clause by its message text. The empty-anchor refusal test stays, since the implement ticket names it as a contract.

**Checked and found sound (no change):** the cost-ordered checks in the handler and that nothing reaches the database before both signatures verify; the constraint-to-code mapping against the schema's clause names (`Authorized\b` does not match `AuthorizedInsert`, which `seatCadreInvite` already wraps); seat-then-redeem as two transactions, as the usage table's pre-transaction read requires; idempotent retry after a dropped reply with one usage row; the targeted-device check ahead of the schema's generic refusal; the gate's fail-open try around check 7; handler registration after the control database is up and unregistration in `cleanup()` before the control node stops, on the failed-start path too; the device pinning the bundle's owner keys before dialing and checking the reply's issuer against that pin; the retained dial target filtered to the answering member's addresses; the sanitizing bounds on both directions; the reply's peer list filtered of self; the two default lifetimes by kind; `cadreInviteStillOpen` shared between the gate read and the listing. Doc comments in `seed-bootstrap.ts`, `control-database.ts` and the gater module match the code.

**Tests:** the implementer's protocol and node specs exercise real engine refusals rather than mocks and were kept, bar the cut above. No test added: the two defects fixed are a code mapping and a decoder passthrough with no branching worth a case of their own, and the gate finding is a design decision, not a defect a unit test could pin without a three-node network.

**Tripwires, recorded at the site:** `NOTE:` at gate check 7 (`cadre-node.ts`, `admitInboundControlConnection` doc) on the row-must-be-held key; the existing `NOTE:`s on the per-stranger control reads in `hasLiveCadreInvite` and the per-row usage count in `listCadreInviteStatuses` already cover the read costs.

**Not covered here, as the handoff said and still true:** `busy`, `party-mismatch` and `conflict` are verified by inspection only; redemption through a real relay is untested; check 7 over the wire with a vouched member present belongs to the follow-on ticket's scenario. `cadre-node.ts` is now 9,000 lines (`wc -l`); the open ticket `debt-cadre-node-single-file-size` already claims that site, and this ticket's 180 added lines are one more instance for it.
