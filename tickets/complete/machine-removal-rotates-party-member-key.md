# Removing a machine rotates the party's member key in each strand it manages

Third ticket of the chain (`control-schema-strand-peer-and-pending-party-key` → `strand-peer-rows-and-sibling-binding` → this → `scenario-machine-removal-rotates-party-key`). Implemented in `ticket(implement): machine-removal-rotates-party-member-key`; reviewed here. The design lives in `docs/architecture.md` → "Removing a machine" and `docs/strands.md` → "Replacing the party's key".

## What was built

- **The removal transaction writes the intent.** `ControlDatabase.removeMachine` writes a `PendingStrandPartyKey` row per closed strand the party holds a `StrandPartyKey` for, in the same transaction and owner approval as the machine's tombstones. A stored pending row is retired and replaced, with the replaced key's public half appended to `Superseded`. A removal that finds no live row writes nothing, pending rows included.
- **The driver** (`strand-party-key-rotation.ts`) moves the party onto the new key in the strand's own rows: seat the new key, bind this machine and every live sibling under it, promote it to manager, the old key resigns and leaves, then one control swap per run across every strand that finished (`ControlDatabase.swapStrandPartyKeys`, a second owner approval). Every step reads before it writes, so a crash at any point is resumed by the next run and two owner machines driving one strand converge. Blocked as `needs-another-party` when the party holds no manager seat.
- **Who drives.** An owner machine running the strand: inside `removeMachine` (waking a hibernating strand first), on a closed strand launched, resumed or made writable here, on the party key watch over `StrandPartyKey` and `PendingStrandPartyKey`, and on the growth drain for a swap deferred while alone.
- **Re-keying a running instance.** `StrandInstanceManager.rekeyParty` replaces the retained launch config and rebuilds the membership reconciler over the new key; a resume re-reads the `StrandPartyKey` row rather than trust the key it hibernated with.
- **The plan and the result.** `MachineRemovalPlan.strands` (`here` / `later` / `another-party`) and `MachineRemovalResult.strands` (`rotated` / `pending` / `needs-another-party`); the events `strand:party-key-rotated` and `strand:party-key-rotation-blocked`.
- **Stale rows** (a tombstone that arrived without its delete) are removed by the owner-signed delete alone, since the key tables have no reap branch and a second tombstone would collide.

## Review findings

**Read.** The implement diff in full before the handoff: the driver against the step list in the architecture doc, including the `prepare` and `stepDown` state table for the crash points the test does not reach; `ControlDatabase.removeMachine` and `swapStrandPartyKeys` for their lock and retry contracts (both sign inside the locked body with `retry: false` reads; the swap's retry re-reads the row and skips one already naming the new key, so a retried commit cannot double-swap); `rekeyParty` for the build-in-flight ordering and the quiescing case; the table watch (`table-change-watch.ts`: single flight with a rerun flag, fires on local commits too); `CadreNode.emit` (catches listener errors); the reconciler's step 5 gate on the pending row and the `MemberPeer.MemberExists` constraint; the founder bootstrap's skip over existing rows; both docs and the schema `NOTE:` on the pending table.

**Found and fixed inline (minor).**

- **A call that joined a run in flight was never re-run.** The driver's single-flight join returned the in-flight run's outcome and did nothing else, but that run had read its pending row before the joining call was made. A second removal while a rotation was running replaced the pending key, its trigger joined the run, and the second rotation then waited for an unrelated trigger (the watch's rerun covers most of this window on one node, not all of it) while the second `removeMachine` reported the strand `rotated`. `drive` now re-drives joined strands once the run they joined ends; a strand with nothing left costs one pending read. Reproduced and pinned by a new test in `strand-party-key-rotation.spec.ts` (hold the first run at its sibling read, replace the pending key, trigger again: two swaps, the strand ends on the second key).
- **`drive` could reject despite its "never rejects" contract.** `onRotated` (the re-key and the event) and `onBlocked` were awaited or called unguarded; a rejection from the instance manager would have rejected `removeMachine` after its control write committed, and the per-strand `finally` registrations would have surfaced as unhandled rejections. Both callbacks are now guarded with a log; a failed re-key leaves the strand `rotated`, since the control row is swapped and the party key watch re-keys the instance on its next run.
- **`rekeyParty` waited on a build in flight before checking whether the key had changed.** The watch calls it for every tracked closed strand on every change to either key table, serially, so a long build on one strand delayed the pending check for all of them. An unchanged key is now answered before the wait (`rekeyNeeded`, re-checked after it).
- **Double log** when the driver found the strand not running here; the `failed` branch already logs it.
- **`docs/architecture.md`** "Removing a machine": the `MachineRemovalPlan` parenthetical now names the per-strand entries the plan gained.

**Tests.** The implementer's two tests stay: the parametrised crash-point run over a real strand engine is the proof of the design's resumability, and the one-database removal test pins the pending-row replacement. One added for the defect above. None cut: neither restates the implementation or verifies a mock. The fixture's in-memory swap now retires the pending row only when it holds the swapped key, as `swapStrandPartyKeys` does.

**Major findings.** None. The trigger set, the control swap and the re-key are wired by reading, as the handoff said; the real-network proof is `scenario-machine-removal-rotates-party-key` (next in the chain, already in `implement/`), which also replaces the apps' removal wording and the `docs/reference-app-rn.md` bullet that still names this ticket. Left to that ticket deliberately: the bullet describes the app's prompt, and the prompt still says it.

**Tripwires recorded.** None new. The costs the handoff listed (one control read per closed strand launch, resume and writable transition; one `rekeyParty` per tracked closed strand per key-table change) are bounded by events that only a rotation fires, and the second is now a map lookup when nothing changed. The `driveRotationIfPending` read also runs for open strands (the pending query returns null); not worth a type check on the hot path today. `cadre-node.ts` is at 11903 lines, which `backlog/debt-cadre-node-single-file-size` already owns; no new ticket.

**Accepted tradeoffs met.** The pending table's `NOTE:` (no re-issue path for a pending row committed while alone) stands; its revisit condition has not tripped.

**Observed, not acted on.** A swap skipped because another driver already swapped the row reports `rotated` without calling `onRotated` here; the party key watch re-keys the running instance from the replicated row, so only the `strand:party-key-rotated` event is missed on this machine, and it is documented as firing on the machine that swapped. Between the old key leaving the strand and the swap replicating, a sibling's reconciler still signing with the old key has its sibling bindings refused by `MemberPeer.MemberExists` and polls on its flat interval; the rekey ends it. Both are inherent to the design and stated in the module doc.
