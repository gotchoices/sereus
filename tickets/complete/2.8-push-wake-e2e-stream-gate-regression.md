# push-wake-e2e: stale membership-gate snapshot denied a starting member

## What shipped

A node judges every inbound control-database stream from a sibling against an **in-memory
snapshot** of the peers it currently believes are authorized
(`CadreNode.authorizeInboundControlStream`). The snapshot is deliberately in-memory: reading
the database to answer the question would require admitting the very stream being judged.

Each `CadreNode` membership method re-materializes that snapshot right after it writes. A
caller that wrote a peer row **below** those methods — straight through
`getSeedBootstrapService().insertSelfPeerRecord(...)` — did not, so the writer kept judging
against a snapshot that predated its own write and denied the peer it had just vouched for
until the next timed cohort reconcile (~15 s later).

- `CadreNode.refreshMembershipGate()` — public, idempotent, best-effort re-materialize;
  thin wrapper over the private `refreshAuthorizedControlPeers`. The gate itself is
  unchanged: not weakened, no new carve-outs, no stranger admission.
- The integration-test helper `seedReceiverRecord` calls it after its insert.
- Review added: `CadreNode.addPhoneWithRelay` now refreshes too (it forwards to a service
  method that authorizes the phone internally — the same defect, in a production path).
- `docs/architecture.md` states the invariant; the scenario 4 comment records why the
  obvious alternative (swapping the two writes) was measured worse.

Measured by the implementer: scenario 2 failed 5 of 8 full-file runs before, 0 of 8 after;
denials per full-file run under `DEBUG='sereus:cadre:*'` fell from 14–18 to 1–3.

## Scope

Production writes peer rows through the `CadreNode` wrappers. A repo-wide grep finds only
tests reaching `getSeedBootstrapService()` directly — but see the review's `addPhoneWithRelay`
finding: the grep pattern was too narrow, because a wrapper can forward to a service method
that writes a row on its own.

## Review findings

### Checked

- Read the implement diffs (`bbe0727`, `a12e72f`) before the handoff prose.
- Every `CadrePeer` row writer: `SeedBootstrapService.insertCadrePeerRow` has exactly two
  callers (`authorizePeer`, `insertSelfPeerRecord`), reached from `addDrone`,
  `acceptPhone`, `addPhoneWithRelay`, and `registerSelf`. Traced each to its `CadreNode`
  wrapper and checked for a refresh.
- Whether inbound seed delivery (`/sereus/seed/1.0.0` handler → `SeedBootstrapService.applySeed`)

- `refreshMembershipGate`'s doc claims ("best-effort, never rejects, idempotent") against
  `refreshAuthorizedControlPeers` — accurate: it returns early when not running, and its
  `catch` keeps the previous snapshot.
- Docs touched and docs that should have been: `docs/architecture.md` bullet is correct and
  now lists `addPhoneWithRelay`; `docs/STATUS.md`'s summary ("refreshed on membership writes
  and each reconcile pass") stays accurate without duplicating the obligation text.
- Lint (`yarn lint`, exit 0), `yarn workspace @serfab/cadre-core test` (828 passed | 1

### Found and fixed in this pass (minor)

- **`CadreNode.addPhoneWithRelay` never refreshed the gate.** It forwards to
  `SeedBootstrapService.addPhoneWithRelay`, which calls the service-level `authorizePeer`
  and inserts the phone's `CadrePeer` row — the exact defect this ticket fixed, in a
  production (phone-to-phone NAT'd enrollment) path rather than a test helper. Dormant today
  (no in-repo caller besides the wrapper itself) but public API, and wrong the moment it
  runs. Fixed with the same one-line refresh its sibling wrappers use; the wrapper list in
  the `refreshMembershipGate` doc comment and in `docs/architecture.md` updated to match.
- **No regression test for the fix itself** — the implementer flagged this as the most
  valuable thing to add next. Added a `CadreNode.refreshMembershipGate` suite to
  `packages/cadre-core/test/control-stream-authorization.spec.ts` (using the existing
  `membership-gate-helpers.ts` injector): a row appearing below the wrappers is denied until
  the refresh runs and admitted after, while a stranger stays denied; the call is idempotent
  and does not reject when the control-DB read throws; and `addPhoneWithRelay` admits the
  phone it just authorized. That last one pins the fix above.

### Found and filed (major)

- `tickets/backlog/debt-membership-gate-refresh-unskippable.md` — make the refresh automatic
  at the single row-write site instead of a documented obligation on seven wrappers. The
  implementer raised this as a design question; the `addPhoneWithRelay` miss is the second
  time the obligation was skipped silently, which is the evidence for doing it.

### Parked as tripwires (not tickets)

- `packages/cadre-core/src/cadre-node.ts`, `NOTE:` on `authorizeInboundControlStream`: the
  snapshot keys on peer id, so a node with **no persistent identity key** never lands a
  `CadrePeer` row (`registerSelf` skips) and its siblings deny its control-DB streams once
  their snapshot is non-empty — being the owner does not exempt it, since ownership is a key,
  not a peer id. Harmless today (real deployments persist their identity; only tests run
  ephemeral owners, and they configure the owner as bootstrap infrastructure — scenario 4
  design note 3). Becomes real work only if an ephemeral-identity node becomes a supported
  deployment.
- Carried forward from implement, unchanged: the scenario 4 note recording that swapping
  `A.authorizePeer` and `seedReceiverRecord` also clears denials but measured worse
  (2/6 vs 4/5), and the `docs/architecture.md` statement of the below-the-wrapper obligation.

### Checked and deliberately left alone

- `packages/cadre-core/src/cadre-node.ts` is 3.5k lines and overdue for a split, but this
  diff adds ~25 lines to it; carving it up here would bury the change. Not filed — it is a
  known shape of the file, not a finding from this work.
- Residual denials after the fix (1–3 per full-file run) were not attributed line by line.
  Scenario 3 exercises rejection deliberately, so a nonzero count is expected, and no run
  in this pass failed on one.

### Test failure seen, not mine

The one `DEBUG='sereus:cadre:*'` run failed scenario 4 (`wakes a member whose authorization
and address were learned by control-DB replication…`) with `Timeout waiting for S resolves
Rx's address record via replication`, preceded by `Missing block` errors out of the Optimystic
storage layer. That test is already listed in `tickets/.pre-existing-known.md` against the
in-flight `bug-control-db-stale-revision-not-retryable` (in `tickets/fix/`), so it is not
re-reported and nothing was skipped or loosened. All four plain runs were green.
