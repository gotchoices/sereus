# Complete: a phone app joins an existing cadre by invitation

## What was built

**Phone kit (`@serfab/cadre-rn/phone-node`)**

- `PhoneNode.joinCadre(invitation, { relayAddrs?, noiseCryptoMode?, signal?, onProgress? })` → `JoinCadreResult` (the redemption result plus `formerPartyId`). Runs in the kit's transition queue (`inTurn`), so no start, stop or restart interleaves.
  - Running node already in the invitation's party: redeem in place (`waitForMember: true`), wire the owner key, no restart (`redeemInPlace`).
  - Otherwise (`switchParty`): shut the node down, start one for `{ partyId, bootstrapAddrs: [], relayAddrs, noiseCryptoMode, origin: 'joined', formerPartyId }` with status `joining`, redeem with `waitForMember: true`. Admitted: wire the owner key, save the start (`autoStart: true`), status `running`. Any failure: shut down, start again the options that were *running* before (`returnToLeftParty`), rethrow the join's error; a failure restarting is logged and leaves status `failed`.
- `PhoneNodeStatus` gains `{ state: 'joining'; node }`; `node` and `options` getters stay null while joining. `createPhoneNode` treats `joining` as live (refuses a second node over the same storage).
- Saved start (`options.ts`): `origin?: 'founded' | 'joined'` and `formerPartyId?`, serialized and parsed (malformed → absent, like the other optional fields). Absent origin means founded.
- Owner step (`config.ts`): `OwnerGenesisResult` gains `'member'`. A start with `origin: 'joined'` calls the new `wireJoinedOwnerKey` (wraps `CadreNode.wireOwnKeyIfOwner`, never `ensureOwnerKey`) under the same bound (`ownerGenesisTimeoutMs`) as `runOwnerGenesis`. Both now share a `withinBound` helper.
- `ownerPublicKey()` returns null for `owner: 'member'`.

**Reference app**: `cadre-phone.ts` exposes `joinCadreByInvitation`, `getRunningOptions`, `getPhoneNodeStatus`. `use-cadre.ts` `joinCadre` decodes, sets status `connecting`, calls the kit, then adopts whatever node runs afterwards (`adoptRunningNode`: node, peer id, owner key, Noise mode, strands, `optsRef` for the background runner's cold start, status/error); it no longer needs a started node. The six repeated "show this node" state updates in the hook are folded into `showNode`. Settings' Join hint says the join switches cadre. The fixture mints `{ grantsOwner: true, expiresInMs: 60 * 60_000 }`; `_setup.yaml` connects with blank fields, joins, then scrolls to and taps Create Strand.

**Docs**: `docs/architecture.md` → new "An app joins an existing cadre" subsection (one node per app and why, `origin` and why a joined party never runs genesis, switch and rollback). The prereq had already fixed the `initializeSeedBootstrap(ownKey)` sentence. `packages/cadre-rn/README.md` → `joinCadre`, `joining`, `member`, a "Joining another cadre" subsection. `docs/reference-app-rn.md` → Start options lists `origin`/`formerPartyId` and the Join behaviour; e2e description updated. The cadre-core NOTE in `initializeSeedBootstrap` no longer points at this ticket for the kit's joined path.

## Where this differs from the plan

- **Rollback restores only a node that was running.** The ticket said to remember the saved start when stopped and restart it on failure. I restart only what was running; an app that was stopped (the user had disconnected) stays stopped, which matches "B is back in its own cadre, unchanged". The saved start still supplies the default relays, Noise mode and `formerPartyId` when stopped.
- **`stop()` cancels a join in progress** (the ticket did not say). Without this, Disconnect queued behind a join that can wait up to the invitation's expiry (15 minutes to 24 hours). The cancelled join restarts the left party and the stop then stops it. `NOTE:` at the abort in `stop()` describes the cheaper alternative if that restart ever makes Disconnect slow.
- **A start whose options name no `origin` takes the saved start's `origin` and `formerPartyId` when the saved start is for the same party** (`resolveOptions`). Reason: the reference app's Connect builds options without `origin`; after a relaunch the Settings form shows the joined party's id, and Disconnect → Connect would otherwise run genesis on the joined party (an `initializeSeedBootstrap` that self-anchors a key that may be no owner's). The read happens inside the transition, through `readSavedStart`, not `loadSavedStart` (which would wait on a stop queued behind it).
- **Owner key wiring retries after an owner grant.** The prereq's review left "`wireOwnKeyIfOwner` false right after an owner grant on a slow network" to this ticket. With `granted: true`, `wireJoinedOwnerKey` asks again every 2 s until wired or the genesis bound passes (`'timed-out'`; the next start wires it). Without a grant it asks once.
- **Maestro**: also dropped `BOOTSTRAP_ADDR` (a blank Connect needs none) and the now-unread `partyId`/`droneBootstrapAddr` from `test-data.json`; the join wait is 60 s (stop, start, redeem, wire) instead of 15 s. The README's troubleshooting note about overriding `BOOTSTRAP_ADDR` is replaced.
- The hook also publishes the push-wake device token after a successful join, as after a Connect.

## Tests

- `node.spec.ts` "never seats itself as a founder of a party it joined…": a start with `origin: 'joined'` on an empty party inserts no `OwnerKey` row, reports `owner: 'member'`, and `ownerPublicKey()` is null. This is the reproduction of the founding-row defect: with `settleOwnerKey` forced back to `runOwnerGenesis` it fails ("expected true to be false"); checked, then restored.
- `node.spec.ts` "goes back to the party it left…": `joinCadre` with a well-formed invitation to another party that expired a minute ago (refused by the device's clock before any dial) rejects with `CadreInviteRejectedError` `invite-spent`; afterwards the phone runs a new node in the original party, `owner: 'enrolled'`, with `options` and the saved start unchanged.
- `options.spec.ts`: the round-trip record now carries `origin: 'joined'` and `formerPartyId`; the malformed-field case adds `origin: 'adopted'` and `formerPartyId: 7`, both read as absent.

The admitted path is not unit-tested here; it is covered by the prereq's `app-joins-cadre-by-invitation` integration scenario at the cadre-core layer, and by the device run.

## Use cases to check

- First launch, nothing running, paste invitation (the hook path works without a started node; Settings only shows Join while connected): admitted → running in A, `origin: 'joined'`, no `formerPartyId`; failed → stays stopped, status `idle` in the hook.
- Running in B (founded), join A: admitted → saved start is A with `formerPartyId: B`; refused/expired/cancelled → B running again, saved start unchanged.
- Running in A already, paste an A invitation: redeemed in place, no restart; status upgrades to `enrolled` only if wiring succeeds.
- Joined app (in A) joins C: `formerPartyId` stays B (carried), not A. By inspection (`formerPartyAfterJoining`), no test.
- Kill while waiting: nothing saved yet, so relaunch and push wake start B. By inspection.
- Relaunch after joining, Disconnect, Connect with A's id: `resolveOptions` keeps `origin: 'joined'`, so no genesis. By inspection.
- `stop()` during `joining`: join throws "the phone node was stopped during a join", B restarts, then the stop stops B with `autoStart: false`.

## Known gaps

- After a join, the Settings Connect form still shows the party id it showed before (it is filled once at launch), so Disconnect → Connect without a relaunch starts the left party (founded) again. That is safe (B's own origin), but it reads as the join being undone. It belongs to the screens ticket.
- An app that attaches strands through `phone.on('strand:discovered')` and reads `phone.node` inside the handler (the README's pattern) sees null during `joining` and during the owner wiring, as it already did during `starting`. The reference app drains `getDiscoveredStrands()` per node instead, so it is unaffected.
- A stop that lands after admission, during the owner wiring, waits for it (up to the genesis bound) rather than cancelling. Rolling back an admitted join would leave the device admitted in A while the app runs B.
- `wireJoinedOwnerKey` is exported beside `runOwnerGenesis` for apps that build their node another way; nothing outside the kit calls it yet.

**Checked and found sound**

- Transition ordering: `joinCadre` runs in `inTurn`, clears `starting` so a later `start` queues behind it, and `stop()` aborts every registered join before queueing itself; a join queued behind a stop is not in the set yet, so it runs after the stop. `throwIfAborted` at the head of `join` covers a join cancelled while queued.
- Rollback: `switchParty` restores only `runningOptions`; `buildAndStart(restore)` re-reads the saved start (unchanged, since nothing is saved before admission) so a founded party keeps its origin. A failure while bringing up A's node (`bringUp` throws) lands in the same `returnToLeftParty`, which shuts down the half-built node first. Nothing after admission can throw (`markRunning` swallows a save failure, `setStatus` swallows listener errors), so an admitted join is never rolled back.
- `formerPartyAfterJoining` for founded, joined (carried), same-party and first-launch inputs; saved start serialization and malformed-field parsing.
- `resolveOptions` inheriting `origin`/`formerPartyId` only for the same party: Disconnect → Connect with the former party's id correctly starts it as founded.
- Reference app: the push-wake device-token registrar is stateless over the kit's node (`push-wake.ts`), so publishing after the join targets party A and leaving B's row behind is harmless (B has no push server; dissolving B is `dissolve-empty-cadre`). The background runner's cold start during a join queues behind it and returns whatever node the join left running.
- The implementer's deviations (rollback only of a running node, `stop()` cancelling a join, origin inheritance, owner-key retry after a grant, Maestro changes): each is reasoned, documented in the kit README and `docs/architecture.md`, and consistent with the plan's intent. Accepted as is.
- Docs: `docs/architecture.md` (new subsection and the invitation-flow link), `packages/cadre-rn/README.md`, `docs/reference-app-rn.md`, `packages/reference-app-rn/README.md` all describe the new behaviour; the README's `onProgress` example matches `CadreJoinProgress` in cadre-core `types.ts`.
