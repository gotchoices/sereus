# Owner grants: tables, rules and the control-database writers

## What shipped

Implemented in `ticket(implement): owner-grant-tables`; reviewed and amended in this pass. The work is additive: machine invitations keep `GrantsOwner` and the invitation consent branch on `OwnerKey` until `machine-invitation-grants-no-ownership` removes them, and nothing outside tests calls the new writers until `owner-grant-node-api`.

- **Schema** (`schemas/control.qsql`, mirrored byte for byte in `control-schema.ts`; the drift spec pins version 2 and hash `GrqGOvAk`): `OwnerGrant` (the grant's public key, the issuer's label, expiry, use cap, issuer pair, stamp; `NotRevoked`, `LabelLength`, `AuthorizedInsert` over the whole row, `NoUpdate`, `NoDelete`) and `OwnerGrantUsage` (a holder-minted nonce, the grant, the seated key and row stamp, the `'redeem'` signature by the grant key and the `'consent'` signature by the seated key; `InsertOnly`, `Authorized` against the committed snapshot, `GrantPossessed`, `OwnerConsented`, deferred `SeatedExists`), with the `OwnerGrantUsageByGrant` index. `OwnerKey.Authorized` gained the grant consent branch, which requires the seated row to carry the grant's label. `Revocation.RowIsGone` admits an `'OwnerGrant'` tombstone with the row kept, as it admits `'CadreInvite'`. A store from version 1 refuses to start with `ControlStoreIncompatibleError` and must be recreated.
- **Read side** (`peer-authorization.ts`): the three digests, `verifyOwnerGrantRow`, `verifyOwnerGrantAdmission` (every link of row, usage, grant and anchored issuer, labels compared null-safe, expiry and use count deliberately not re-checked) and, added in review, `verifyOwnerGrantRedemption`, the pre-check twin of the invitation's. The anchor derivation (`owner-anchor-sync.ts`) takes a required `grantChain` beside `chain` and looks a consent-seated row's usage up in the grant chain first; `CadreNode.syncOwnerAnchor` loads both chains whenever any owner row is consent-seated.
- **Writers and readers** (`control-database.ts`): `insertOwnerGrant`, `seatOwnerGrant` (refusing a foreign issuer by `OwnerGrantIssuerUnknownError`), `queryOwnerGrant`, `queryOwnerGrants`, `queryOwnerGrantUsages`, `countOwnerGrantUsage`, `isOwnerGrantLive`, `listOwnerGrantStatuses`, `withdrawOwnerGrant`, `redeemOwnerGrant` (one transaction, `alreadyOwner` for a key that is already a live owner, an exhausted grant refused by name with `InvitationExhaustedError`), and the three message builders. The invitation and grant paths share one body each for seating, withdrawal, liveness, standings and the seat-remains check, keyed by an `IssuedTable` union; `RemovableTable` excludes both issued tables and the exhaustive `GUARDED_KEY_COLUMN` record forced the new key column at compile time.
- **Docs** (`docs/architecture.md`): the two new rows in the control-table list, the `OwnerKey` and `Revocation` rows, the schema-recreation loss list and the anchor-derivation paragraph. The flow description belongs to `owner-grant-node-api`.

## Review findings

**Checked.** The implement commit's diff was read first, file by file, before the handoff. The schema was compared constraint by constraint with `CadreInvite` / `CadreInviteUsage` (the `Authorized` body reads the same snapshot and tombstone sets, the signatures bind the same field triple under distinct action tags, the deferred existence check binds the usage to one row incarnation). The `OwnerKey` grant branch was checked for holes: a null `VouchOwner` fails the issuer equality, a replayed usage row cannot seat another key (`SeatedKey`) or a second incarnation (`SeatedStampId` plus the stamp's `unique` over live rows and `NotRevoked` once retired), and a member machine cannot produce the grant signature. Every table-name switch was confirmed by grep: `GUARDED_KEY_COLUMN`, `RemovableTable`, `REAPABLE_TABLES`, the re-issue drain and the tombstone writer are table-generic or exhaustive, and no package outside cadre-core switches on revocable table names. The owner-removal plan lists grant-seated rows as dependents (it filters on `vouchOwner` alone) and the re-vouch is a delete-and-re-add that keeps the label, so a removed issuer's grant-seated keys are re-vouched unchanged. The redemption writes the owner row before the usage row in the same order the invitation redemption does. The two re-baselined pinned-count specs were re-pinned exactly, not loosened (cold start 37 over 29 to 41 over 33, the four never-written blocks; seventeen tables, three indexes). Docs were read for every touched table. Lint, the cadre-core typecheck, the repo typecheck and the cadre-core unit suite were run: 182 files, 2517 passed, 1 skipped (the standing skip in the ledger), log in `tickets/.logs/2.1-owner-grant-tables.review.test.log`.

**Minor, fixed inline.**

- The handoff's "no pre-check twin of `verifyCadreInviteRedemption`" gap: added `verifyOwnerGrantRedemption` in `peer-authorization.ts`, exported from `index.ts`. The node API ticket checks both signatures before any database work, so the twin would otherwise have been written there, out of place beside its invitation sibling. No test, as the invitation twin has none: it is two digest verifications already pinned by the schema tests.
- The `OwnerGrant` doc row named the next ticket by file path with its sequence prefix, which goes stale on the first board move; now the slug.

**Major.** None. The one class-level concern, a new table-name switch somewhere forgetting `'OwnerGrant'`, is already guarded: the key-column record is typed over `RevocableTable`, the revocable-table list in the ledger-marker spec is typed the same way, and the reap list is a literal that never included the issued tables.

**Handoff gaps, resolved without work.** The missing `hasLiveOwnerGrant` gate read is not wanted: `owner-grant-node-api` decides that a live grant never counts as expecting a stranger (a backup grant with no expiry would keep every member admitting strangers for the party's life), so the holder rides the provisional admission instead. The by-name refusal of a re-seat on a machine holding the key's retired row reaches the grant path through the shared `liveOwnerKeyStamp`; it stays unpinned by a test because that state arrives only by replication and `Revocation.RowIsGone` refuses building it locally.

**Tripwires.** The grant chain is two whole-table reads per membership refresh while any owner row is consent-seated, and until `machine-invitation-grants-no-ownership` lands such a row may be invitation-seated, so the reads find nothing: `NOTE:` at `syncOwnerAnchor`. Expired and withdrawn grant rows accumulate for the life of the party: `NOTE:` on the `OwnerGrant` table comment. The per-row usage count in the standings listing: `NOTE:` on `issuedRowStandings`. The single-use race: accepted-tradeoff `NOTE:` on `OwnerGrantUsage.Authorized`, mitigations rewritten for grants.

**Size.** `control-database.ts` is 5,107 lines and `cadre-node.ts` 10,218 after this ticket; appended as a measurement arm to `debt-cadre-node-single-file-size`, which already tracks both files.

**Tests.** The implementer's specs were kept whole: each case in `control-owner-grant.spec.ts` drives a distinct constraint or writer branch through the production writers against a real control database, the standings test is the first coverage of the shared `issuedRowStandings`, and the anchor-sync case covers the anchored, unanchored, forged-grant and no-chain outcomes. The refusal table matches the constraint name `Authorized` without the table, so a case that names `OwnerKey.Authorized` would also pass on `OwnerGrantUsage.Authorized`; each such case's statement order makes the named constraint the only one that can fail, so nothing was changed.

**Not run.** The integration-tests workspace, for the handoff's reason: nothing there constructs an invitation chain or calls `deriveOwnerAnchor`, and the dist was rebuilt before the unit suite.
