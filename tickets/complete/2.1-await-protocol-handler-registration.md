# Await protocol-handler registration instead of dropping its rejection

## What was built

libp2p's `node.handle(...)` is async. It rejects with `DuplicateProtocolHandlerError` when a protocol already has a handler, and also when its peer-store write of the node's own protocol list fails. Four cadre-core services called it as `void node.handle(...)`, so a rejection became an unhandled rejection. Under Node's default `--unhandled-rejections=throw` that kills the process after the caller has already seen success.

- `StrandAddrService.initialize`, `StrandWakeService.initialize`, `SeedBootstrapService.initialize` (and its private `registerProtocolHandler`) and `FormationListener.register`/`unregister` are async and await `handle`/`unhandle`. Each keeps its node reference only after the registration resolves, so a failed service's `shutdown()` does not unhandle a handler it never owned.
- `CadreNode.start` awaits the wake and strand-addr registrations. A rejection reaches the existing `start()` catch, which runs `cleanup()` and rethrows.
- The public chain is async: `StrandFormationManager`/`StrandSolicitationService` `registerResponder`/`unregisterResponder`, `CadreNode.initializeSeedBootstrap`, `enableSeedListener` and `initializeStrandSolicitation`. `CadreNode` sets its service field before awaiting the registration, so a concurrent `enableSeedListener`, `createOpenInvitation` or `formStrand` reuses that service instead of registering a second, colliding handler. If registration fails, `CadreNode` restores the previous service.
- Visible behaviour change: `initializeSeedBootstrap` over an existing seed service, or a second `initializeStrandSolicitation`, now rejects with `DuplicateProtocolHandlerError` instead of crashing the process later. The "must be started" precondition errors are now rejections.
- All callers await. In `reference-app-rn`, `initializeFormationResponder` is async and still fails soft (it logs the error). In `reference-app-web`, `ensureSolicitation` memoizes a `Promise<void>`, so concurrent callers share one registration, and a failure clears it so the next call retries.
- `docs/architecture.md` (the strand-addr receiver bullet and the `registerResponder` bullet) says the registrations are awaited and reject.

## Review findings

I read the `ticket(implement): await-protocol-handler-registration` diff before the handoff. I checked every source change, every `.handle(`/`.unhandle(` call in `packages/`, and every caller of the now-async methods across all packages, including untyped `.mjs`/`.js` files.

- **Missed callers (fixed).** Two untyped `.mjs` fixtures still called the now-async methods without `await`. Typecheck and lint cannot see these files:
  - `packages/reference-app-rn/test-fixture/start.mjs` (`initializeSeedBootstrap`)
  - `packages/integration-tests/src/harness/fixtures/strand-restart-party.mjs` (`initializeSeedBootstrap` in `makeOwnOwner`, `initializeStrandSolicitation` in the `found` handler)

  A registration failure in either would have been an unhandled rejection, which is exactly what this ticket removes. I added `await` to each call. To verify the second fixture, I rebuilt cadre-core and ran `strand-relay-only-restart-reconverges.integration.ts` with `RESTART_TWO_PROCESS=1`, the case that spawns that fixture. The first attempt failed after about 200 s, and I did not capture its output. The next two runs passed (about 20 s each). That suggests a one-off, but the lost output means nothing can be ruled out. The `start.mjs` fixture is a manually run RN sidecar and was not run.
- **Stale tests (simplified).** Two `cadre-node-seed-trust.spec.ts` cases (temp-service `applySeed` idempotence, and enabling the listener after a temp-service `applySeed`) installed a process-wide `unhandledRejection` listener and slept 50 ms. That existed to catch a fire-and-forgotten `handle()` rejection. Now that registration is awaited, a duplicate rejects the awaited call itself, so the listener and sleeps could never catch anything. I removed them and reworded the comments. The protocol-list assertions that do the actual checking are unchanged.
- **Peer-store failure leaves a stray handler (tripwire).** Confirmed in `node_modules/libp2p/dist/src/registrar.js`: `handle` stores the handler before it awaits the peer-store merge. A failed merge therefore leaves the protocol registered with no service owning it, and a retry through a public entry point rejects as a duplicate. This is not reachable in practice today, because the merge is a local peer-store write. Parked as `NOTE:` comments on `CadreNode.installSeedBootstrapService` and in `initializeStrandSolicitation`. The notes name the fix: unhandle on a non-duplicate failure only.
- **Concurrency (checked, no action):**
  - If `enableSeedListener` races an in-flight `initializeSeedBootstrap`, it returns early as soon as the field is set, before that registration resolves. This is the same "already initialized" idempotency it had before, and the concurrent caller that owns the registration still sees any failure.
  - `FormationListener.register` and `StrandFormationManager.registerResponder` check their "already registered" sets before the await, so two concurrent calls on the same manager would get a duplicate rejection. This is not reachable: `CadreNode` only reaches them through its field guard.
  - In `cadre-web.ts`, a registration still in flight across `stopCadre()` and a restart could, if it fails, clear the new session's memo. This is contrived (a stop, a restart and a failed registration must interleave), and the only cost is one extra registration attempt. Left as is.
- **Error handling and resource cleanup (checked, no action).** Services store the node only after a successful registration, so `cleanup()` after a failed `start()` does not unhandle a handler that was never registered. `cleanup()` awaits `unregisterResponder` without a guard, which matches the sibling `shutdown()` calls. No exceptions are swallowed, and the RN fail-soft path logs.
- **Tests.** The implementer's `StrandAddrService.initialize` rejection test checks that `initialize` rejects and that `shutdown()` does not unhandle, and it was shown to fail on the old code. Kept. No tests added: the install-before-await and restore-previous logic and the web memo have no branching beyond what the code shows, and testing them would mean faking libp2p's registrar.
- **Docs.** `docs/architecture.md` is accurate. No other doc or README shows a synchronous call to any of the changed methods (grepped `*.md`).
- **Type safety, DRY, size.** No `any`. `installSeedBootstrapService` removes the duplicated seed wiring. `initializeStrandSolicitation` inlines the same install-and-restore pattern for a different field. Two instances do not justify a generic helper.
- **Validation.**
  - `yarn lint`: clean.
  - cadre-core `tsc --noEmit`: clean.
  - `yarn workspace @serfab/cadre-core test`: 144 files, 2338 passed, 1 skipped.
  - cadre-core rebuilt; the integration two-process restart scenario passed (see above).
  - Not run by the implementer or this review: the other integration scenarios, the web Playwright suite and the RN suite.
