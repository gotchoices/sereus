# The phone reference app rents a provider node: complete

Fifth ticket of the `provider-client-and-sign-up` chain, landed by `ticket(implement): reference-app-rn-rents-a-provider-node` and reviewed here. Settings → **Rent an always-on node** shows the one provider the build names, signs the user in on the provider's pages in the system browser, rents a container through cadre-core's `rentNode` and lists each rented node with its standing, its join and the subscription's dates; a node the provider stopped offers Remove from cadre. The kit gained `@serfab/cadre-rn/provider` (sign-in through an injected browser, tokens in the secure store, the rental record) and `PhoneNode.nodeLocalRecords()`. `docs/reference-app-rn.md` → "Renting a Provider Node" is the user-facing description, including the dev setup; the kit README's "Provider" section is the API. Nothing has run on a device or against a live cadre-provider: `tickets/blocked/rn-device-run-rent-provider-node.md` lists what a human run must confirm.

## What was built

**Kit, `packages/cadre-rn/src/provider/`.** `signInWithProvider` runs cadre-core's PKCE handshake through a passed-in `openAuthSession` (the shape of expo-web-browser's `openAuthSessionAsync`); anything but a redirect is `'cancelled'`, a redirect carrying the provider's refusal throws `ProviderAuthError`. `providerTokensSlot` keeps one provider's pair in the secure store under `sereus.provider-tokens.<base64url id>`, refusing a gated slot as `secureStoreSlot` does. `rentalStore(kv)` keeps the app's rentals by party under `rentalsKvKey(partyId)`, one call at a time. `PhoneNode.nodeLocalRecords()` exposes the node-local database as a key-value store that re-resolves the handle per call; the app-link slots now go through it.

**App.** `providers.ts` reads the configured provider from `EXPO_PUBLIC_PROVIDER_DESCRIPTOR_URL` and `EXPO_PUBLIC_PROVIDER_CLIENT_ID` and builds the redirect URI `<own scheme>://provider-auth`. `provider-session.ts` holds one provider's descriptor, tokens and client; `withClient` signs in when signed out and, on a refused refresh, drops the pair, signs in again and runs the step once more. `rentals.ts` turns a rental record, the provider's answer and the machine list into a row with its actions, and puts each failure into words. `provider-store-section.tsx` is the section; `use-rental-poll.ts` re-reads the rows while Settings is in front. `useCadre` gained `rentProviderNode`, `finishProviderRental`, `listRentals`, `noteRentalPeer` and `forgetRental`; the record is written inside `createContainer` and marked finished when `rentNode` or `finishRental` returns. Shared pieces were extracted so nothing is a third copy: `machine-removal.tsx`, `owner-standing.ts`, `ConfirmPrompt` and `useLaterThan` in `settings-controls.tsx`, `shortPeerId`, `machineCode` and `machineName` in `machines.ts`. Devices and nodes shows "Rented from ‹name›" on a machine a rental names.

**Deviations from the plan, kept.** `Rental` carries `providerName` so the machine list needs no descriptor; the subscription line is once per provider, under the rows, since billing is per customer; the redirect URI is built from the scheme, not `Linking.createURL`, because the provider compares it by exact string; both installs default to client id `sereus-chat`, the one client cadre-provider's README registers with both redirect URIs; a container in `error` offers Cancel, and Remove from cadre while listed.

## Review findings

Reviewed from the implement diff first, then the handoff. Lint, the kit's and the app's typechecks, the kit's tests (18 files, 186 passed), the app's tests (20 files, 175 passed) and the app's Metro export all pass after the changes below. No pre-existing failures were met.

**Checked by reading and running.**

- The sign-in against cadre-core's `oauth.ts`: the state is checked by `readAuthorizationRedirect`, the verifier goes to the exchange, a result without a URL is a cancel. The token slot's parser matches `ProviderTokens` field for field.
- The reauthorize retry in `provider-session.ts`: cadre-core's `createTokenSource` single-flights a refresh, so the poll and an action sharing one client cannot spend the rotated refresh token twice; a refused refresh surfaces as `ProviderAuthError('reauthorize')`, which `withClient` turns into one sign-in and one re-run. The re-run is safe for every action: `rent` resumes the created container through `onCreated`, Cancel's delete treats a 404 as deleted, Finish adding and Try again are idempotent by construction.
- The row table in `rentals.ts` against the plan's table, including the states the plan did not name (`error`, signed out, unreadable), and `finishRental`'s outcomes against `use-cadre.ts`'s handling (a failed invitation join leaves the record for Try again).
- The redirect hand-off: expo-web-browser's Android polyfill listens on `Linking` for a URL starting with the redirect URI, independently of expo-router's `+native-intent` rewrite, so rewriting the same link to `/settings` with no query does not take the code away from the pending sign-in. Whether the auth session resolves on a device is the blocked ticket's.
- `new URL(apiBaseUrl).origin` on the phone: React Native's own `URL` throws on `origin`, but Expo's runtime (`expo/src/winter`) installs a WHATWG `URL` first. Confirmed in the app's installed `expo`; a one-line comment at the site says so.
- The extracted `machine-removal.tsx` and `owner-standing.ts` against the code they replaced in `machines-section.tsx`: same prompt, same refusal lines, same stale-node guard; the "Already removed" path now also tells the provider section to drop the record, which is right since the node is out of the cadre.
- `nodeLocalRecords()` keeps the wait-for-stop and the per-call re-resolution the private `appLinkSlot` had; `machines.ts` still runs under Node with its new import of `node-claim.ts`.
- Docs: the kit README, `docs/architecture.md`'s sign-in paragraph and `docs/reference-app-rn.md`'s section and file tree describe what landed; one sentence corrected below.

**Found and fixed in this pass (minor).**

- **The poll ran unattended.** The rows were re-read every 5 seconds for as long as the section was mounted, and Settings stays mounted behind the Chat tab while Android keeps JavaScript timers running in the background, so the provider was polled from the Chat tab and from the background. The relay posture poll in `use-cadre.ts` already stops when the app leaves the foreground; the rental poll now does the same and also pauses while Settings is not the focused tab (expo-router's `useFocusEffect`), reading again at once on return. The poll moved into `src/use-rental-poll.ts`, which owns the rows' state; the section went from 543 to 454 lines. The poll is also keyed on the session rather than the whole store object, so the plans arriving no longer restarts it. The doc sentence "while the section is on screen" now says what is true.
- **A failed record write could have rented a second container.** `rentProviderNode` told the caller the container id only after the record was written, so if the write failed and the provider then refused the token, the retry would have rented again. The id is now reported first; `finishProviderRental`'s update is a no-op without a record, which is the lesser harm.
- The Terms link's closure no longer carries a `?? site` fallback that only existed to satisfy narrowing.

**Tests.** Kept the implementer's `test/rentals.spec.ts`: it pins the plan's row table and the error classes `instanceof` depends on. Kept the `use-cadre.spec.ts` mock additions, which only let the module load. Added `packages/cadre-rn/test/provider/rental-store.spec.ts`, two cases: the per-party record contract the app's resume and poll rely on (update in place, an update for an unknown container is a no-op, remove), and the unreadable-record contract (not JSON or the wrong shape reads as no rentals, logged; a read fault still throws). The kit's token slot and the app's `provider-session.ts` stay untested, as the plan allowed: glue over cadre-core, with the retry checked by inspection above.

**Considered and left.**

- `recordingClient` logs and continues when the record write fails, so the claim still happens and the node joins with no record on this phone. Weighed again: an orphaned container the user pays for is worse than a node without a "Rented from" fact. Kept.
- A user who taps Deny on the consent page sees "‹name› did not sign you in." rather than a silent cancel. Kept; `signInFailure` in `rentals.ts` is the one place to flip it.
- `getBillingStatus` is read on every poll even with no rentals while signed in: one request per 5 seconds while Settings is in front. Small, and the subscription line is the only thing a signed-in user with no nodes has to look at. Left without a note.
- `add-device-section.tsx` keeps its own owner-standing code rather than `useOwnerStanding`. Its read is interleaved with its invitation flow and settles late on purpose; converting it is a refactor with no defect behind it. Left.

**Tripwires.** The `NOTE:` about re-reading the whole machine list on every poll moved with the poll into `use-rental-poll.ts`. No new tripwires.

**Not filed.** No major findings, so no tickets. The device run stays in `tickets/blocked/rn-device-run-rent-provider-node.md`, which already names the fallback if the Android auth session does not resolve.
