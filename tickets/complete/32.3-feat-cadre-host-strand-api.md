# Complete: `/api/strands` on the cadre-host management server

## What shipped

Two routes on cadre-host's local management server, founder-role only (404 in donor-only mode,
the same gate `/auth/*` and `/nat/*` use):

- `GET /api/strands` → `{ ok: true, data: { strands, controlConnections } }`
- `DELETE /api/strands/:id?confirm=1` → `{ ok: true, data: StrandRemovalResult }`

Both delegate to the owner node's loopback admin channel (`GET /admin/strands`,
`DELETE /admin/strands/:id`). cadre-host holds **no strand state of its own** — no `strands.json`.
`StrandService` (`src/strands/`) exists to validate the id and to translate the admin channel's
single `OwnerNodeUnavailableError` into a code vocabulary the HTTP layer maps to a status:

| `nodeCode` | `StrandErrorCode` | HTTP |
|---|---|---|
| `confirmation_required` | `confirmation_required` | 428 |
| `bad_request` | `invalid_id` | 400 |
| `not_ready`, `not_authorized`, absent | `node_unavailable` | 503 |
| anything else | `internal` | 500 |

A removal that issued a delete publishes `strands-changed` on the local UI event bus; a call that
found no row publishes nothing.

Supporting wiring: `OwnerNodeClient` gained `listStrands`/`removeStrand` (a third trimmed
`CadreNodeLike` it satisfies); `error-handler.ts` gained the status map; `events/types.ts` gained
the event; `server/index.ts` gained an optional `strands?: StrandService`; `bin/host.ts`
constructs it in the founder branch; `src/index.ts` re-exports the public surface.

The UI screen that drives these routes is a separate ticket
(`tickets/implement/feat-cadre-host-strand-removal-screen`, sequence 32.6).

## Review findings

### Fixed in this pass

- **The `/`-in-id refusal was a self-imposed limit with no basis, and it broke the only form that
  worked.** `validateStrandId` rejected any id containing `/` with 400 `invalid_id`, on the stated
  premise that `/api/strands/:id` is one path segment and cannot carry it. The implement handoff
  flagged this as unverified and asked a reviewer to establish it. Measured: Fastify decodes path
  params, so `DELETE /api/strands/ns%2Fstrand` arrives at the handler with `request.params.id ===
  'ns/strand'`; `OwnerNodeClient` re-encodes it; the admin channel splits on the still-encoded
  `%2F` and decodes it back (`admin-server.ts` documents exactly that). The whole chain carries it.
  Worse, the guard was **unreachable for the case it claimed to protect** — an *unencoded* `/`
  never reaches the handler at all, because the router 404s it first. So its only effect was to
  make a `/`-bearing strand un-removable from the manager while the CLI could still remove it.
  Guard removed; the comment now records what was measured. Proved three ways: a route test
  (`%2F` reaches the service as a literal `/`), a route test (unencoded `/` 404s before any
  handler runs), and a **real-node integration case** that round-trips `ns/never-published`
  through the spawned `cadre-cli` child.
- **The local UI would have silently dropped `strands-changed`.** `ui/src/lib/events.ts` registers
  one `addEventListener` per name in a hard-coded `EVENT_TYPES` array, and the new event was not
  in it. A named SSE event only arrives for a name the client subscribed to, so the server would
  publish and nothing would receive — with no error anywhere. The screen ticket (32.6) plans a
  `'strands-changed'` case in `applyEvent` but never names `events.ts`, so it would have hit a
  dead handler and had to debug the SSE layer. Added the entry, plus a comment saying the array
  must track `LocalUiEvent['type']`, and left a note on 32.6 that this half is already done.
- **`StrandRemovalResult.alone` was documented more narrowly than it behaves.** The host type said
  "the node had no control connections *at the write*", implying a write happened. The node samples
  it on **every** call including one that found no row and wrote nothing. Corrected on the type and
  in `docs/cadre-host.md` to match the node's own wording: read it as "this machine sees no
  siblings", and only as "your delete may not have travelled" when `removed` is also true.
- **`StrandErrorCode.invalid_id`'s comment** still cited "unusable as a path segment" — a leftover
  from the removed guard. Now: blank or whitespace-only, here or at the node.
- **`docs/STATUS.md` was stale and had no record of this surface.** Line 1143 pointed at
  `backlog/feat-cadre-host-strand-removal-ui`, which no longer exists (that ticket was planned and
  is now `implement/feat-cadre-host-strand-removal-screen`). Replaced with a description of the
  landed API and a live pointer to the in-flight screen.

### Tests added

The implementer's 31 tests were a fair starting point but had holes on the error and encoding
paths. Net +2 unit, +1 integration (`cadre-host` 566 → 568; the two `/`-refusal tests were
replaced by one forwarding test):

- `GET /api/strands` had **no error-path test at all** — the fake service's `list()` could not
  throw. It now can, and a test pins `node_unavailable` → 503 through the real error handler.
- Route: a percent-encoded `/` reaches the service as a literal.
- Route: an unencoded `/` 404s at the router with the service never called.
- Integration: `removeStrand('ns/never-published', { confirm: true })` against the real spawned
  node. This is the first test anywhere that exercises `OwnerNodeClient`'s URL construction over a
  character that actually needs escaping **and** the `?confirm=1` suffix, against a real admin
  channel — the handoff named that as an uncovered gap. It stays a no-op (`published: false`) on a
  fresh party, so it needs no formation flow and costs one round trip.

### Tripwires parked (not tickets)

- `strands/strand-service.ts`, on `toDomainError` — the trust-circle and NAT services translate the
  same `OwnerNodeUnavailableError` blanket-style (everything → `node_unavailable`), because neither
  has a node code worth distinguishing yet. Fine at two shapes. If a *second* surface ever needs a
  code-aware mapping, hoist the switch into a shared owner-error translator rather than growing a
  third copy.
- `server/routes/strands.ts`, on `CONFIRM_VALUES` — the `{'1','true'}` set and its rationale are
  duplicated verbatim from cadre-cli's `admin-server.ts`. That is deliberate: cadre-host depends on
  cadre-cli for its **bin path** only, never its source, so importing would create a real source
  dependency. Noted at the site so a future DRY pass doesn't "fix" it into an import.

### Checked, found nothing to change

- **Error-status mapping.** 428 for `confirmation_required` is the right code (the request was
  well-formed, nothing conflicts, the caller must re-send with the precondition satisfied — not 400,
  not 409). `not_authorized` → 503 is a slightly loose fit (a wrong bearer token is a manager
  misconfiguration, not a down node), but the node's message survives inside the wrapper and it
  matches what trust-circle and NAT already do for the same error. Not worth diverging.
- **Secret exposure.** `AdminStrandSummary` is a deliberately narrow node-side projection that
  excludes `MemberPrivateKey`; nothing in this diff widens it or reconstructs the row.
- **Mount gating.** `strands` is registered exactly like `trustCircle`/`nat` — optional option,
  founder-only construction in `bin/host.ts`, falls through to the static 404 handler otherwise.
  Both verbs are tested in donor-only mode.
- **`confirm` parsing.** Strict `{'1','true'}` only, matching the node's pair exactly. `?confirm=yes`,
  `?confirm=`, and a repeated `?confirm=1&confirm=2` (which Fastify hands over as an array, failing
  the `typeof === 'string'` guard) all read as NOT confirmed. Right default for an operation that
  destroys a membership key.
- **No automatic retry-with-confirmation.** Unit-tested: a refused removal is surfaced, never
  re-sent with the flag added.
- **Resource handling / source hygiene.** The service holds no state, no handles, no timers.
  `strand-service.ts` 134 lines, `types.ts` 102, `routes/strands.ts` 55 — all small, functions are
  single-purpose, comments explain *why* rather than restating code. No size or decomposition
  concern.
- **`docs/strands.md`** documents the strand model, not management surfaces — it names no CLI or
  admin route today, so this change introduces no gap there. `docs/cadre-host.md` is the right home
  and carries both route-table rows, the SSE row, and the Strands section.

### Known gap, accepted (no ticket)

**The closed-strand confirmation gate has no integration coverage, and correctly so.** Proving a
real 428 needs a real closed strand, which needs the formation flow — that belongs to the formation
scenarios, not here. What *is* covered: the node's own decision (`cadre-cli`'s
`admin-server.spec.ts`), this layer's forwarding and translation of the refusal (unit), the 428
status mapping (route), and — new in this pass — that the `?confirm=1` suffix physically reaches a
real node. The chain is covered in overlapping halves; only the single end-to-end
route→client→node→row span is not, and no test in this repo spans that today for any admin route.
