## What landed

After `npm install -g @serfab/cadre-host`, the user runs `cadre-host install`
and ends up with:

- A populated data dir (default per platform; honors XDG / `LocalAppData`).
- A fresh Ed25519 node identity persisted to `identity.key` (mode 0600 on
  POSIX).
- `host.config.json` capturing UI port, libp2p port, UPnP toggle, and
  install metadata.
- `nat.json` seeded with the chosen libp2p port + UPnP toggle so
  `NatService.start()` picks them up on first boot.
- A registered system service that survives reboot:
  - Linux: `~/.config/systemd/user/cadre-host.service` + `loginctl enable-linger`.
  - macOS: `~/Library/LaunchAgents/com.serfab.cadre-host.plist`.
  - Windows: NSSM-managed `CadreHost` service (requires `nssm.exe` on PATH).
- A best-effort browser tab on `http://127.0.0.1:<uiPort>/`.

The wizard is plain readline (no extra TUI dep). The CLI now wires
`install`, `uninstall`, `status`, and `start` to real implementations in
`packages/cadre-host/src/bin/host.ts`. `start` loads config + identity and
waits on SIGTERM — the local UI HTTP listener lands in
`cadre-host-local-ui-server` (6.5.1), so the wizard's enrollment-invite
fetch silently degrades until that ticket is in.

### Minor issues — fixed in pass

1. **`docs/cadre-host.md` was stale.** Lines 199 + 202 still said
   `install / start / status / uninstall` print "not yet implemented" and
   that "the installer and local UI implementations are forthcoming." The
   installer just landed — only the local UI HTTP server is still
   pending. Rewrote those two lines to reflect reality.

2. **`fetchEnrollmentInvite()` had no fetch timeout.** Node 18+'s fetch
   has no default timeout. Once `6.5.1` lands and the local UI listener
   binds, if it ever hangs the `cadre-host install` command would wedge
   indefinitely (since `.catch()` only fires on a real error, not on a
   stall). Added a 5-second AbortController-based timeout —
   `packages/cadre-host/src/installer/index.ts` `fetchEnrollmentInvite()`.

3. **`cadre-host uninstall --remove-data` skipped confirmation.** The
   README example showed `cadre-host uninstall --remove-data --yes`,
   implying `--yes` exists to skip a prompt — but no prompt existed and
   `UninstallOptions.yes` was a silent no-op. Concrete risk: a user
   typing `cadre-host uninstall --remove-data` (without `--yes`) would
   silently wipe their identity + trust circle. Added an interactive
   confirmation in `bin/host.ts` that fires only when `--remove-data` is
   set and `--yes` is not, plus a hard-fail when stdin is not a TTY (so
   scripted callers can't accidentally rely on the prompt). The library
   surface (`Installer.uninstall`) is unchanged — interactivity stays in
   the CLI.

### Major issues — none filed

Nothing rose to the level of a new ticket. Items below are documented
gaps from the implementer's handoff that are already tracked elsewhere
and I see no reason to re-file:

- **`start` is a SIGTERM-wait stub** — pending `6.5.1-cadre-host-local-ui-server`.
  TODO markers exist at the right spots.
- **The "configure DDNS now? [y/N]" wizard prompt is a no-op** — captured
  to `WizardAnswers.configureDdns` but never acted on. Acceptable for v1
  per the implementer; DDNS still goes through `cadre-host nat ddns set`
  against a running management API.
- **NSSM not bundled** — v1 expects `nssm.exe` on PATH. The standalone
  binary distribution (`tickets/backlog/cadre-host-standalone-binary.md`)
  will ship it.
- **No CI cross-platform smoke** — `systemctl --user enable`,
  `launchctl bootstrap`, and `nssm install` are not exercised in CI.
  Documented in `packages/cadre-host/service/README.md`. The installer
  was manually smoked on Windows 11 (PowerShell 5.1, Node 24.2.0,
  yarn 4.12.0); systemd / launchd code paths are render-only via the
  template tests until a human runs them.

### What I deliberately did *not* change

- **`Installer.uninstall(opts.yes)` API surface.** Kept it on the
  interface even though the library doesn't consume it, because removing
  it from a public-export type would be a churn-only change. The CLI
  reads it for symmetry; the library treats it as informational. If we
  want strict hygiene later, drop the field — but for v1 it's harmless.
- **Browser auto-open path.** Gated on `process.stdout.isTTY && !nonInteractive`.
  Correct for CI / headless boxes.
- **Identity file format (protobuf, not raw).** Implementer flagged this
  for "second pair of eyes" — confirmed: `privateKeyFromProtobuf` is what
  every libp2p caller in cadre-core uses, and the protobuf form preserves
  the key-type tag for future migrations. No change needed.
- **Wizard UX wart**: when the user passes `--data-dir /foo` *and* runs
  interactively, the wizard shows `[platform-default]` instead of
  `[/foo]` — then the CLI flag wins regardless. Minor and only surfaces
  if someone mixes flags + prompts. Not worth a fix in this pass.
