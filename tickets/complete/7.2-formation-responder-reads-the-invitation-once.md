# The formation responder reads the invitation once

Split from `plan/formation-and-redemption-read-each-row-once` (the responder arm). Siblings: `cadre-invite-and-grant-redemption-read-the-row-once`, `joiner-hands-its-join-to-the-launch`.

## What changed

A responder session now takes one value, a `FormationTokenRead` (`formation-token.ts`), and hands it to every later step:

```
runSession
  validateToken ── recorder.readToken(token) ── 1 FormationInvite read
                                               + 1 use count (metered, unexpired only)
               └─ classifyTokenRead(read, now) → { valid: true, read } | token-unknown | token-spent
  provision(contact, signal, read)
    provisionAsResponder
      resolveStrand(read)       ── 1 Strand read, with StampId (queryStrandWithStamp)
      bound:  authorizeUsage(params, read, host)   approval from read.invite.validationUrl;
                                                   seat re-count ONLY after an obtained approval
              issueMembershipInvite(host, signal)  open/closed from host.strandType; no Strand read
              record() → recordFormationUsage({ ..., totalUses, strandStampId })
                                                   no stamp read; in-lock count still decides
      unbound: provisionAndRecord(params, read)    sAppId / validationUrl / totalUses from the read
```

- `isTokenValid` / `isTokenUsed` are gone from `FormationUsageRecorder`; `readToken` replaces both. `resolveInviteSAppId` is gone.
- `FormationTokenCheck` moved to `formation-token.ts`; its valid arm carries `read?` (absent only when the manager has no recorder). `FormationInviteRow` now `extends FormationInviteFacts`.
- `MembershipInviteIssuer` takes the resolved `BoundHostStrand` (`strandId`, `strandType`, `strandStampId`, `memberPrivateKey`). `CadreNode.issueStrandMembershipInvite` no longer reads `Strand`; its "Strand row is gone" guard is gone with that read.
- `recordUsage` (only `recordFormationComplete` and test mocks reach it) still reads the invite and the stamp for itself; it now checks the abort before its invite read.
- Connection gate (`StrandSolicitationService.hasOutstandingInvitation`) uses `readToken` + `isTokenReadSpent`, with a `NOTE:` saying why it does not share the session's read.
- `classifyTokenRead` and `isTokenReadSpent` are exported from the package index (the integration tests use them), with the new types.
- `StrandFormationManager.requireRead` throws when a recorder is wired but the listener handed over no read. This cannot happen through the manager's own listener; it exists so a wiring fault refuses the redemption instead of falling through to a path that records no usage. Reviewer: judge whether that is worth its lines.

## Behaviour changes for the reviewer to weigh

- **Host strand removed between `resolveStrand` and the write.** Before, the issuer re-read `Strand` and rejected retryably (`host-strand-unavailable`) without issuing. Now the membership invite is issued, then the consent insert fails the `StrandExists` CHECK, which surfaces as the catch-all `conflict` rejection, also retryable. The invite is orphaned until `MEMBERSHIP_INVITE_TTL_MS`. The ticket accepted this, and the orphan comment in `provisionAsResponder` names it. `MissingHostStrandError` is now reachable only on the `recordUsage` path, which passes no stamp; its doc says so.
- **Seat re-count only after an approval.** Without a `ValidationUrl`, a seat taken between `readToken` and the write is caught only by the in-lock count, which throws the same `InvitationExhaustedError` → `token-spent`. The difference is that this can now happen after the membership invite was issued, which orphans it. The `assertSeatFree` NOTE covers that window.
- **Gate on a row-expired token.** `readToken` does not count an expired invite, so `isTokenReadSpent` says "not spent". A minted-registry entry whose own expiry has not passed, but whose row has, therefore stays outstanding until the registry expiry. Before, it was counted and dropped once used up. The registry and the row normally carry the same expiry. Not parked anywhere; reviewer can decide whether it deserves a `NOTE:`.
- **`strandProvisioner` fallback `sAppId`.** It now comes from the session read. Mock recorders that used to return no invitation (so `''`) now pass their fake invite's `sAppId`. No mock provisioner reads it.
- Comment-only change in the schema text (`readToken` replaces `isTokenUsed` in the `FormationUsageByToken` comment), made identically in `control-schema.ts` and `schemas/control.qsql`. The schema-text comparison ignores comments, and the version check works off the DDL diff.

## Review findings

Read `ticket(implement): formation-responder-reads-the-invitation-once` first, then the handoff.

- **Carried values vs. the database's final checks (the ticket's main question).** Checked every value the session carries into a write. The seat budget (`totalUses`) is still counted inside the write lock (`assertSeatRemains`) for both paths; the host strand's `strandStampId` is checked at commit by `FormationUsage.StrandExists`, which matches the (id, stamp) pair, so a row removed or re-seated since `resolveStrand` is refused (pinned at raw-insert level by the existing "WRONG StrandStampId" case in `control-formation-invite.spec.ts`); expiry and the approval signature are re-verified by `FormationUsage.Authorized`. A `StrandExists` CHECK failure is not one `lockedWithRetry` retries. Nothing to change.
- **Defect, fixed: connection gate kept a row-expired token open.** `readToken` counts no uses for an expired invite, so the gate's `isTokenReadSpent` read an expired, used-up row as "not spent", and a minted registry entry stayed outstanding until its own expiry. `StrandSolicitationService.hasOutstandingInvitation` now classifies the read with `classifyTokenRead` and keeps the token only when valid or `token-unknown` (unpublished row, as before); an expired or used-up row is dropped. Docblock updated. One test added in `strand-solicitation.spec.ts` ("drops a mint whose invite row has expired, though the registry entry has not"), which fails on the implement-stage code.
- **`requireRead`.** Kept: it is the narrowing that lets `resolveStrand` and `provisionAndRecord` take a non-optional read, and refuses the redemption on a wiring fault rather than inventing a read. Seven lines; worth them.
- **Host strand removed after `resolveStrand`.** Now surfaces as the catch-all retryable `conflict` after the membership invite is issued (orphaned until its TTL). Accepted by the plan ticket; already named in the orphan comment in `provisionAsResponder` and in `MissingHostStrandError`'s doc. No further action.
- **Seat re-count only after an approval.** Correct by the plan; the in-lock count decides and the `assertSeatFree` NOTE covers the orphan window. No action.
- **Two `Date.now()` reads** (`readToken`, then `classifyTokenRead`): monotonic, so an invite expiring in between reads as spent; harmless. No action.
- **Leftover names.** Grepped the tree for `isTokenUsed` / `isTokenValid` / `resolveInviteSAppId`: only `test/fixtures/control-schema/v3.qsql`, a frozen old-version schema fixture, which must not change.
- **Docs.** Read the `architecture.md` and `api.md` edits and the docblocks in `control-database.ts`, `strand-formation-deadlines.ts`, `strand-solicitation.ts`; they match the code. No other doc names the removed methods.
- **Tests.** The rewritten cases each pin a contract (classification outcomes, seat taken during approval, bound resolution carrying type and stamp). The deleted "Strand row gone" case pinned a guard that no longer exists; its replacement contract is the schema CHECK, already tested. Nothing cut. `readsAs()` reports `usesRecorded: 0` for an expired metered fake where the real recorder reports null; no test depends on it.
- **Tripwires.** None new.
- **Validation.** `yarn workspace @serfab/cadre-core typecheck`, `yarn lint`: clean. Full cadre-core suite: 188 files, 2540 passed, 1 skipped. Integration scenarios not re-run: the only change after the implement stage is the gate's handling of an expired row, which they do not exercise.
