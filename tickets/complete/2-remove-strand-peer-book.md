# Remove the strand peer book

## What landed

The commit `ticket(implement): remove-strand-peer-book` deleted the strand peer book: its five modules and two specs, `CadreNodeConfig.strandPeers`, `CadreNode.getStrandPeerBookStore()`, the `./strand-peer-book-file` subpath, and the `/sereus/strand-peers/1.0.0` protocol. It also removed the book from the CLI and from all three reference apps. The saved FRET routing table (`strand-network-state-persisted`) now carries addresses across a restart. Two replacements cover the book's other jobs:

- **Formation-carried addresses.** `CadreNode.formationStrandAddrs` is an in-memory map from strand id to the addresses the formation carried, grouped by peer. A re-formation replaces the entry, and an empty list or one naming no peer changes nothing. `resolveCohortSeed` reads it on launch and resume. `formStrand` merges it straight into a strand that is already running. The entry is dropped on unpublish, leave and self-revocation. The accepted tradeoff (a restart between forming and first launch loses the list) is a `NOTE:` at the field.
- **Keeping other parties dialable on a running node.** `strand-fret-addrs.ts` (`strandFretPeerAddrs`) reads the strand node's FRET table. It verifies each signed peer record: the record must be signed by, and describe, the peer it is filed under. It then binds each address to that peer. Every refresh pass re-merges the result into the strand node's address book (`remergeStrandFretRecords`).

The review added one more piece, described under Review findings: carried addresses are re-merged on each refresh until FRET holds that peer's record.

## Review findings

Read the implement diff first (57 files), then the handoff. Read FRET's `exportTable`/`SerializedTable`, `Libp2pFretService`, `seedFromBootstraps` and the neighbour-snapshot handler in `../Fret` to check the structural type and the replacement's assumptions.

**Fixed in this pass (one defect):**

- **Formation-carried addresses were no longer kept alive before the first connection.** The book re-merged them every 15 s. After the change they were written once, by the launch seed, and FRET's `seedFromBootstraps` takes only the peer id from a bootstrap address and dials through the peerStore. So if a joiner's strand stayed up and the responder was unreachable for more than an hour after launch, the carried address expired. The joiner then had no way to dial the responder until the strand relaunched or resumed. The host had not met the joiner either, so neither side could redial. Fix in `cadre-node.ts`: `remergeStrandFretRecords` now returns the ids it holds a record for, and a new `remergeUnrecordedFormationAddrs` re-merges the carried addresses of every peer not in that set on each refresh pass. Once FRET holds the peer's own signed record, the carried list stops being merged for that peer. Updated the comments on `formationStrandAddrs`, `refreshOneStrandPeerAddrs`, `recordFormationStrandAddrs` and the `NOTE:` at `mergeStrandPeerAddrs`. Updated `docs/architecture.md` (Strand-Address Resolution → "When it is read") and `docs/strands.md`. Added one regression test: `cadre-node-strand-addr-refresh.spec.ts` → "re-merges a formation's carried addrs on every tick until FRET holds that peer's record".
- **Unverified fact in a blocked decision ticket.** The handoff left `decide-public-read-only-strand-access` saying it was not re-checked whether FRET's neighbour snapshots answer any connected peer on an open strand. Checked by reading the source: an open strand has no per-stream gate (`StrandInstanceManager` arms one only for closed strands), and `handleNeighborsRequest` answers any caller subject only to a rate limit. The ticket's triage fact now says so and that this was found by reading the code, not by a run.

**Checked, no change needed:**

- *Correctness of the FRET reader.* `SerializedPeerEntry.addressRecord.envelope` is base64url of the marshaled envelope, which matches the structural type. `services.fret` is `Libp2pFretService`, whose `exportTable()` is synchronous. The signer and subject checks close the "any peer rewrites another's addresses" hole, and the spec pins this with a real signature. Hibernating strands are skipped (the refresh loop requires `libp2pNode`). A FRET read that throws is caught per strand.
- *Shipping deleted modules from an old `dist`.* Not a risk for releases: `scripts/publish-package.mjs` runs `yarn clean && yarn build` before every publish. A developer's own old `dist` keeps orphaned files until a clean, which affects no one else.
- *New dependency.* `@libp2p/peer-record` `^9.0.5` resolves to the single 9.0.5 entry libp2p already pulled in, so bundles gain nothing.
- *Web app rename* (`strandPeers` → `strandConnectedPeers`). It was the chat strand's live connection count, not a book count. Keeping the display was right, and nothing else references the field (the e2e asserts only `home-strand-status` text).
- *Leftover references.* No live code or open ticket names the book. The only hits are completed tickets, the release note (which lists the removals on purpose) and `forgetStrandPeers` (a method name that still describes what it does).
- *Deleted `debt-strand-peer-book-remote-write-bounds`.* Its two protections now fall to FRET. FRET rate-limits neighbour requests (`bucketNeighbors`) and caps merged snapshots (`mergeSnapshotCaps`). Did not check whether FRET eviction protects peers this node has met.
- *Tests.* The implementer's new specs pin real branching: signer/subject rejection, relay-hop binding, the replace and no-wipe rules, and the direct merge on re-formation. None of them only restates the implementation. The always-on one-sided restart arm costs about 3 s and pins a documented claim ("one side remembering is enough"), so it was kept. No tests were cut.
- *Docs.* Read the changed sections of `architecture.md`, `strands.md`, `testing.md`, `reference-app-rn.md` and the release note. They match the code, apart from the formation re-merge gap fixed above. The "One side remembering is enough" paragraph reports a measurement, but it explains current behaviour, so it was left as is.

**Minor, left as is:** `recordFormationStrandAddrs` and `remergeUnrecordedFormationAddrs` group addresses by peer, and `mergeStrandPeerAddrs` groups them again. The map stores flat strings so that the seed can union them. The duplicate grouping is negligible at 16 addresses.

**Tripwires:** none added. The two the implementer parked stand: the per-pass FRET-table cost `NOTE:` at `remergeStrandFretRecords`, and the accepted-tradeoff `NOTE:` at `formationStrandAddrs`. The `NOTE:` at `mergeStrandPeerAddrs` now also says that a junk carried address from a responder this node never meets keeps being re-merged for the life of the process. The exposure is failed dials only, and a re-formation or leave clears it.

**No tickets filed:** the one defect was fixed inline.
