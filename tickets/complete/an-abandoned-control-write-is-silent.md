# What shipped

Every local control write goes through one retry funnel (`ControlDatabase.lockedWithRetry` → `retryControlWrite` → `retryControlOperation`). It gives up two ways — the classifier declines the failure as non-transient, or attempts/budget run out — and before this ticket both only wrote a `debug('sereus:cadre:control-db')` line, a namespace nothing turns on by default. Foreground writes also reject to their caller, so an operator sees those. Background writes do not: the self-address republish and the two replication drains in `cadre-node.ts` are fired unawaited with a `debug`-only catch, so a permanently failed one reached nobody at all.

**The loop reports both give-up exits.** `retryControlOperation` notifies an optional per-call `onAbandon` observer exactly once before the rethrow, with a `ControlRetryAbandonment`: label, attempts made, attempts allowed, elapsed ms, a `reason` of `declined` / `attempts` / `budget`, and the error object itself (identity preserved, so an app can classify it with the same matchers). A throwing observer is logged and swallowed — the loop is on its way to rethrowing the failure that actually matters.

**Writes only.** Nothing on the read path passes an observer, and `control-read-retry.ts` says why at its own seam: every control read is awaited by the caller that issued it, so an abandoned read surfaces as that caller's rejection and nothing is lost silently.

**`ControlDatabase` owns one settable listener.** `setControlWriteAbandonedListener`, same one-listener-per-database contract already written on `setMembershipChangeListener`. It is merged into `lockedWithRetry`'s options last (after policy and spec-injected pacing) and read through the field rather than captured, so wiring or clearing it mid-flight still governs a write already in backoff.

**Three surfaces above it.** A `control:write-abandoned` entry in `CadreNodeEvents`, wired in `start()` beside the membership and guarded-delete listeners and cleared on teardown. One operator escalation whose bar is the consequence, not a failure count: other machines discard a `CadrePeer` record older than `DEFAULT_PEER_RECORD_MAX_AGE_MS` (15 minutes) and the heartbeat re-stamps at half that, so once this node has gone that long without publishing, anyone not already connected can no longer reach it — `console.warn` once, re-armed by the next successful publish. And a warning line per abandoned write in `cadre start`, the headless CLI (added during review; see findings).

The classifier's behaviour is unchanged, deliberately. Contention is no longer a rejection: upstream made "another write holds this block right now" a `held` verdict counting toward neither approvals nor rejections, so a contended write arrives as `SyncRetryExhaustedError`, which no matcher claims and which must stay declined. What remains rejectable at the promise phase is stale revision, block-unavailable, membership-not-admitted and a configured validator's refusal — and stale revision is precisely the one a re-presentation fixes, because the loop re-runs the whole write body including its reads. A blanket rejection veto would remove a retry that helps to save two wasted attempts on the ones that do not. The reasoning is recorded at the accepted-tradeoff `NOTE:` on `isUncommittedTransactorAggregate`, in the module comment above it, and in `docs/architecture.md`.

## Fixed in this pass

- **`ControlRetryPolicy.onAbandon` was dead, and three comments described a mechanism that did not exist.** No policy ever set it: `CONTROL_WRITE_RETRY_POLICY` and the read policy both omit it, and the only producer is the per-call `options.onAbandon` that `lockedWithRetry` passes. Yet the field's own comment claimed "the write policy carries one … the read policy deliberately does not", `control-read-retry.ts` said it "deliberately carries NO `onAbandon` observer, unlike the write policy", and `retryControlWrite`'s comment said the seam "is deliberately not taken by the read policy" — while `ControlReadRetryOptions` is a straight alias of `ControlRetryOptions`, so a reader passing one would have worked fine. Removed the field (`retryControlOperation` now reads `options.onAbandon` alone) and rewrote all four comment sites, `lockedWithRetry`'s included, to describe what the code actually does: the observer is per call, because the only thing that wants one is per `ControlDatabase` instance.
- **`cadre start` never surfaced the event.** The headless CLI is the operator's process, and it already prints `strand:error`, `control:connected` and `control:disconnected` — but an abandoned control write reached it only as the 15-minute self-record escalation. The ticket's whole premise is that giving up was silent, and for the one shipped operator surface it still was. Added a `console.warn` handler beside the existing ones, naming the label, reason, attempts and underlying failure, and a clause in `docs/architecture.md` recording that surface.
- **The escalation warning read "last failure: heartbeat — …"**, where `heartbeat` is the *trigger* for the republish, not the failure. Reworded to "The latest attempt (heartbeat) failed with: …". The existing spec assertions all still hold.
- **`cadre-node-abandoned-write-report.spec.ts` claimed coverage it does not have** — that `start()` setting the listener and teardown clearing it "is asserted … in `control-write-retry.spec.ts`". That file asserts `ControlDatabase`'s listener seam, not `CadreNode`'s wiring to it. Replaced with an honest note: the wiring needs a started node, which is why the membership and guarded-delete listeners beside it are unit-tested only at the `ControlDatabase` end too, and end-to-end coverage is the integration scenario's `afterEach`.
- **`tickets/.pre-existing-known.md` had a claim this ticket invalidated** — "a green run of this file is not evidence that this class did not occur … until `an-abandoned-control-write-is-silent` lands". It has landed; updated, with the review run's own numbers.

## Checked and found clean

- **Every control write really does funnel through one seam.** `this.withWriteLock(` has exactly one call site in `control-database.ts`, inside `lockedWithRetry`, and every public write method reaches it. No write can be abandoned without the listener hearing about it.
- **The loop's three exits classify correctly.** The budget exit is distinguishable from the attempts exit (the `attemptNumber === attempts` break precedes the budget check, so the last attempt reports `attempts` even if it also blew the budget — the loop's actual exit, and the honest label). `declined` carries the attempt it stopped on. The review run confirmed all three shapes in production: `declined after 1/3`, `declined after 3/3`, `budget after 1/3 … in 163101ms` (one attempt that stalled 163 s against a never-answering member).
- **Two layers of throwing-listener protection, both justified.** `notifyAbandoned` catches, and `CadreNode.emit` catches per handler. The inner one covers a non-`CadreNode` listener.
- **Teardown.** `lastSelfRecordPublishAt` and `selfRecordStaleWarned` reset in `stopRecordRefresh` (called from `stop()`), so a stop/start cycle does not inherit the previous lifetime. The listener is cleared before `controlDatabase.close()`, and because `lockedWithRetry` reads the field rather than capturing it, a write still in backoff at teardown reports to nobody rather than to a dead node.
- **Handle scoping in the scenario.** All six `activeDegradation` assignments are covered by the single `releaseDegradation()`, `degradesCohort` is false only for the zero-delay observer the healthy case holds, and the healthy case is first so no stale grace window precedes it.
- **`cadre-host` and `cadre-provider` need no wiring** — neither subscribes to `CadreNode` events at all; they manage the CLI as a child process.

## Parked as tripwires, not tickets

- **`ABANDON_SETTLE_GRACE_MS` (5 s) is a judgement call, not a measurement.** The review run neither confirmed nor refuted it: no abandonment landed inside a grace window at all — every loss was either inside a held degradation or many seconds clear of the last release. A `NOTE:` at the constant now states both failure modes and how each shows up in the `[abandoned-write …]` lines, so the next person to see one knows what they are looking at.
- **The `skipped`-publish asymmetry the handoff flagged for a second opinion stands as documented.** A node that stops being able to publish without *erroring* — revoked, or its row removed — neither stamps nor warns. The accepted reading is already written at `escalateIfSelfRecordStale`: a revoked node has nothing to publish and its unreachability is the point. The one case it leaves quiet is a node removed by another owner that is not its own owner, which then goes stale silently; that is a membership-revocation notification, a different feature, not a defect in this one. No ticket.
