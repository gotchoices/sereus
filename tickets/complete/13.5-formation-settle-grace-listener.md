description: A host that ran out of time part-way through letting someone join used to burn that person's one-time invitation and then tell them it failed; the work is now cancelled instead, and if it finishes anyway during a short grace period the joiner is correctly told it succeeded.

## What landed

`FormationListener.provision()` used to run the `provisionStrand` hook for the whole
`provisionTimeoutMs`, pass no cancellation signal, and — on expiry — reply
`approved: false, reason: 'Formation provisioning timed out'` while the abandoned hook kept
running and spent the joiner's single-use invite ~100 ms later. The joiner then got
`'Invalid token'` on every retry: a permanently unusable invitation indistinguishable from a
genuinely bad one.

The budget is now split, with the grace carved **out** of `provisionTimeoutMs` (never added
on top, so the nested ladder — hook 10 s < provisioning 12 s < initiator await 15 s <
session 30 s — is unchanged). `splitProvisionBudget()` owns the arithmetic and the listener
stores the two halves once at construction:

```
graceMs = min(PROVISION_SETTLE_GRACE_MS /* 2_000 */, floor(provisionTimeoutMs / 2))
workMs  = provisionTimeoutMs - graceMs          // ⇒ always ≥ half the budget
```

When `workMs` expires the listener aborts an `AbortController` threaded into
`provisionStrand`'s 4th arg (plumbing from prereq `formation-abort-signal-plumbing`), then
`settleWithinGrace()` waits out `graceMs`:

| provisioning settles within the grace as | listener replies |
| --- | --- |
| approved | the real approval (identity + cadre + provision result disclosed as usual) |
| rejected (`approved: false`) | that rejection reason, non-disclosing |
| threw (incl. `FormationAbortedError`) | `approved: false, reason: 'Formation provisioning timed out'` |
| still pending at grace end | same timed-out reply; late-settle logged via `void pending.then(...)` |

`runSession` is unchanged — its `!outcome` / `!outcome.approved` / approved branches already
covered every row. The reply string `'Formation provisioning timed out'` is byte-identical to
before.

Docs: `docs/architecture.md` "Strand Formation" — the nested-timeouts paragraph names the
settle grace inside the 12 s, and a new paragraph states that an overrunning provisioning is
aborted (invite left unspent when the recorder observes the signal), that a late success
inside the grace is adopted and reported as an approval, and that the 10 s default work
budget now equals the approval hook's own 10 s so a dead hook races two retryable,
invite-preserving rejections.

## Review findings

### Checked and clean

- **Composed behaviour across the chain.** Traced listener abort → `StrandFormationManager.provisionAsResponder`
  (rethrows `FormationAbortedError` rather than mislabelling it a conflict) →
  `ControlFormationUsageRecorder.recordUsage` / `provisionAndRecord` →
  `ControlDatabase.recordFormationUsage` / `redeemInvitation`, where the signal is checked
  inside the write lock immediately before the insert. Every row of the table above maps to
  a real code path; no gap found.
- **Promise hygiene.** `pending` is created once and awaited by two separate `withTimeout`
  calls plus the post-grace logging `void pending.then(...)`; every settlement path has a
  rejection handler, so no unhandled rejection escapes and no timer is left armed.
- **Timeout-flag races.** Both `timedOut` and `stillPending` are set by `withTimeout`'s
  `onTimeout` hook, which fires on a macrotask after the promise's `.finally` would have
  cleared the timer — a genuine failure arriving at the deadline is at worst reported as a
  timeout, which is benign and unavoidable.
- **Docs.** Read every doc that mentions formation (`architecture.md`, `STATUS.md`,
  `strands.md`, `cadre-host.md`, `cadre-consistency.md`, `api.md`). Only `architecture.md`
  describes formation timeouts, and its update is accurate. No stale claim about an
  abandoned hook surviving a timeout survives anywhere.
- **Behaviour change for small configured budgets.** The implementer asked for a second
  opinion on `floor(provisionTimeoutMs / 2)` halving the work budget below ~4 s. Verdict:
  keep it. The grace must be strictly smaller than the budget, and "work is always at least
  half the budget" is the cleanest invariant available; it is now stated on
  `splitProvisionBudget` rather than buried in the method body. No change made.

### Fixed in this pass (minor)

- **`settleWithinGrace` adopting a late *rejection* was untested.** The one adoption test
  covered `approved: true` only, so nothing pinned the branch that relays the hook's own
  reason instead of the generic timeout. Added *"adopts a REJECTION that lands inside the
  settle grace, reporting its reason non-disclosingly"*, which also asserts the rejection
  still discloses no responder identity/cadre.
- **Nothing asserted the signal stays un-aborted on the happy path.** A listener that
  aborted unconditionally would have passed every existing test while cancelling healthy
  redemptions. Added *"does not abort provisioning that finishes inside its work budget"*.
- **Budget arithmetic recomputed per session and inlined in `provision()`.** Extracted
  `splitProvisionBudget()` next to `resolveProvisionTimeoutMs()`; the listener now stores
  `provisionWorkMs` / `provisionGraceMs` as constructor fields and `settleWithinGrace` no
  longer takes a grace parameter. `Math.max(1, …)` on the work budget was dead (the grace is
  capped at half the budget, which `resolveProvisionTimeoutMs` already floors at 1) and is
  gone.
- **`PROVISION_SETTLE_GRACE_MS` was exported with a comment claiming the tests share it.**
  Nothing imports it — the tests use literal budgets small enough that the 2 s cap never
  applies. Made it module-private and dropped the false claim. (The repo has an open
  `dead-code-cleanup-and-knip-gate` backlog item, so an unused export is not free.)

### Filed as new tickets (major)

- `backlog/debt-formation-one-budget-drives-both-sides` — `StrandFormationManager` passes the
  single configured `provisionTimeoutMs` to **both** the responder listener and the initiator
  dialer, so any explicit configuration collapses the 3 s wire-latency margin this ticket's
  whole design rests on and the two sides give up simultaneously. Dormant today (nothing in
  the repo sets `formationConfig`), but wrong the moment anyone does — a latent defect, not a
  tripwire. The field's own doc comment describes the ordering it cannot produce.
- `backlog/debt-formation-abort-end-to-end-coverage` — the implementer's flagged gap, upheld.
  The listener tests use a hand-rolled hook over `MockStream`; the recorder/database tests
  never involve the listener. No test proves the composed path leaves the `FormationUsage`
  row genuinely absent and the token re-redeemable, which is the one thing this three-ticket
  chain exists to guarantee and the thing a refactor would break silently.

### Tripwires (parked, not filed)

- **The residual unclosable window** — a work budget that expires *after* the
  `FormationUsage` insert was issued AND a commit that outlasts the grace. The joiner is told
  'timed out' while its invite is in fact spent, and no recovery can match a retry because
  `StrandSolicitationService.formStrand` mints a fresh Ed25519 keypair per attempt. Parked as
  a `NOTE:` in `settleWithinGrace`'s docblock, beside the late-settle logging that is its
  only observability. Widen the grace only if it shows up in the wild.
- **Timing-based tests.** Three of the six grace tests use real `setTimeout` and one asserts
  wall-clock elapsed (≤ 700 ms against a 500 ms budget, ~200 ms of CI jitter headroom). Green
  locally on every run. If CI proves flaky the fix is a wider bound, never a skip. Left as
  the implementer wrote it; noted here rather than in code because it is a property of the
  suite, not of one site.

### Rejected / not relitigated

- A recoverable-spend path (letting a joiner re-present a spent token to recover the strand)
  was investigated and rejected across prior runs: the fresh keypair per retry defeats
  `(Token, PeerId)` matching, and such a path would hand the strand id plus the closed-strand
  `MemberPrivateKey` to anyone re-presenting a spent token under a writer-asserted peer id.
  Unchanged verdict.
