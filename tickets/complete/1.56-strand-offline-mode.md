## What landed

**Harness** (`harness/strand-restart-party.ts`, `fixtures/strand-restart-party.mjs`), shared with the two-process arm of `strand-relay-only-restart-reconverges`:

- `StrandRestartPartyOptions.offline`: the child configures `strandOffline: { journal, initialMode: 'offline' }`, one `FileKVStore` per strand scope under `<stateDir>/offline/<strand id>` (the ticket suggested `<stateDir>/<scope>/offline`; this keeps the layout parallel to `storage/<scope>`). Stores are cached per scope, as `StrandOfflineConfig.journal`'s doc asks, and closed after `node.stop()`.
- `write` now inserts with `returning StampId() as Tx` and returns `{ transactionId }` (the restart scenario ignores the result).
- New ops `rows` (every App.Data row, by scan), `offlineEntries` (`offline.entries()`), `offlineStatus` (`offline.status(tx)`, `null` for `undefined`). Statuses cross IPC as `OfflineStatusSummary` (kind, id, and per kind `persisted`/`waitingFor`/`attempts`, `effect`, or `reason`/`error` message), because the channel is JSON and an `Error` arrives as `{}`.
- The child forwards every `strand:offline-status` as `{ type: 'offline-status' }`; the driver collects them in `party.offlineStatuses` (per process, in arrival order). The send is skipped once the IPC channel is closed.
- `readDataRows` returns an array of `{ key, val }` rather than a Map (`waitRow` adjusted).

**Scenario** `strand-offline-queue-survives-restart.integration.ts`, runs by default (about 14 s):

1. A founds; B (`offline: true`) forms. B reads A's row. Control step not in the ticket: B writes one row while A is up and must report it `committed` and A must read it, so a failure after the restart cannot be a queue that never sent anything. Both saved network states must name the other.
2. A's process exits; wait until B's strand node has no connection to A's (`pathKinds` empty).
3. B inserts; the statement resolved in 10–18 ms over five runs. `offline.status(Tx)` is `queued` with `persisted: true`; the row reads back on B.
4. B's process exits and is respawned over the same directory, A still down. B's `claim` returns `active` (first-sync gate passed on B's own copy, about 2.1 s after the respawn began); the row reads back. The restored queue submits at once (A, restored from the saved table, reads as serving), so the test polls `entries()` until the entry is `queued` again: it settles `queued`, `waitingFor: 'cohort'`, `attempts: 2`, about 2 s later. Asserted: no `committed` for Tx in either B process's forwarded statuses before A is respawned.
5. A's process is respawned and claims (founder, `active`). B reports `committed` about 3 s after A's respawn began; A then holds exactly the rows `[from-a, from-b-online, from-b-queued]`; B's second process forwarded exactly one `committed` and no `failed` for Tx.

**Deviation from the ticket: relay-only, not direct connections.** The ticket asked for direct connections. They cannot run this journey: a strand node always listens on an ephemeral port (`strand-network-config.ts` rewrites fixed ports), and here each party restarts while the other is down, so each comes back remembering only the other's old port, and neither can dial (the design boundary in `docs/strands.md` → "a member whose address changed while it was connected to nobody is unreachable"). A relayed address (relay + strand peer id) is stable across a restart, so both parties stay relay-only on one loopback relay, the fixture's existing shape. No transport option was added to the fixture. Stated in the scenario header and in `docs/testing.md`.

## Known gaps

- **Lone time after the restart is short.** B is alone for about 4 s after its restart, while FRET still lists the restored A as live, so each send runs on a cohort of two and falls short. The path where FRET has dropped A and Optimystic's reachability gate (`absent-members`) is what keeps B from committing alone is not exercised; noted in the scenario header.
- **"Resolves promptly" is not asserted as a time bound.** The `queued` status is the assertion; the elapsed time is logged (10–18 ms measured).
- **The restored transaction's rows are visible in this run because reads are served locally;** a transaction restored with `waitingFor: 'restore'` (a table it wrote unreachable) was not produced here.
- **One run shape:** loopback relay, one Windows machine, no link delay.

## Review findings

Read with fresh eyes from `ticket(implement): strand-offline-mode` (fixture, parent harness, new scenario, `docs/strands.md`, `docs/architecture.md`, `docs/testing.md`), then checked against Optimystic's queue (`db-core/src/offline/queue.ts`, `status.ts`, the plugin's `offline-restore.ts`).

- **Correctness, fixed: step 4's wait could pass before B had sent anything.** A restore lists the entry `queued` with `waitingFor` unset (attempts 0 or 1) until its first post-restart send, so "poll until `queued`" could succeed at once and the "no `committed` while A was down" check then ran before B had made any decision. The wait now requires `waitingFor` to be set (only a send or the reachability gate sets it). Re-run: the wait now takes about 2.1 s after the claim and ends at `waitingFor: 'cohort'`, `attempts: 2`.
- **Resource cleanup, fixed: journals were not closed when `node.stop()` threw.** The fixture's `stopAndExit` closed the `FileKVStore` journals inside the same `try` as the stop, so a failed stop skipped the flush the next process reads. Now they close after the stop either way (`allSettled`, each failure logged, exit code 1).
- **Tripwire: the parent never reads the child's exit code**, so a failed stop or journal close shows only on stderr. Parked as a `NOTE:` on `exit` in `harness/strand-restart-party.ts`.
- **Minor:** `statusesOf`'s doc said it returns statuses; it returns a count. Reworded.
- **Docs:** every `strands.md#…` anchor linked from docs, READMEs and source still resolves (scripted check over all headings); `docs/strands.md → "…"` prose references in source name sections that still exist. The "always-on programs configure no `strandOffline`" claim holds (only cadre-core, the edge node and the two reference apps reference it). The reorganized section follows AGENTS.md's one-claim-per-item rule. No further doc edits needed.
- **Relay-only deviation:** accepted; the reason (ephemeral strand ports, both parties restarting while the other is down) is stated in the scenario header and `docs/testing.md`.
- **Tests:** the one scenario is the ticket's required end-to-end proof and pays for itself; nothing cut, nothing added. The `where-equality can miss` scan comment matches the established pattern in five other scenarios.
- **Type safety / error handling:** status summaries cross IPC as plain JSON with errors as message chains; the forwarded-status send is guarded on `process.connected`. No issues.
- **Known gaps from the handoff stand** (the long-lone `absent-members` path, the `waitingFor: 'restore'` path, one run shape). They are coverage limits stated in the scenario header, not defects; no ticket filed.
