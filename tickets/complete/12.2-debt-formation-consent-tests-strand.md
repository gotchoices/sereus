# Joiner-signed formation records — strand-layer test sweep (complete)

## What landed

The joiner-consent mechanism (the joining peer signs its own `FormationUsage` row; the
responder and the schema's `PeerConsented` CHECK verify that signature over
`(Token, UsageStampId, PeerKey, Disclosure)` before accepting the join) came from
`debt-formation-consent-core`. The test catch-up ran in two parts — the database layer
(`complete/12.1-debt-formation-consent-tests-db`) and this one, the strand/protocol layer
plus the cross-package test harness. Implement commits: `f8f5539`, `7c384c6`, `10339d0`,
`e3fbf66`; review edits are uncommitted in this run's tree.

Implement-stage content:

- `test/formation-consent-helper.ts` — `mintContactJoiner()` (a real libp2p ed25519 peer
  identity, so `partyId` genuinely embeds `peerKey`) and `mintContactConsent()`, which signs
  over the canonical JSON form of the disclosure. Shared by the strand-layer specs.
- `strand-formation-consent.spec.ts` — all 17 contact sites carry genuinely signed consent;
  disclosure assertions compare canonical JSON. New: an invalid-consent rejection matrix that
  proves the invite is left unspent and still redeemable, and a nonce-reuse test
  (`'Formation conflict, retry'`, then a fresh nonce succeeds).
- `strand-formation-protocol.spec.ts` — new `FormationListener joiner-consent pre-check`
  describe proving the consent check runs BEFORE token validation (the token-check counter
  stays at 0) and leaks no responder identity.
- `formation-approval.spec.ts`, `peer-authorization.spec.ts`,
  `validation-key-enrollment.spec.ts`, `strand-solicitation.spec.ts` — `peerId` → `peerKey`
  renames, real consent minting wherever a row hits real verification, vouch and consent
  signatures bound to the same nonce and disclosure bytes.
- Harness `test-network.ts` `joinStrand` — mints a throwaway ed25519 identity and signs a
  real consent digest, because it writes through the real `ControlDatabase.recordFormationUsage`
  where the CHECK verifies the signature.
- Integration scenarios — mock usage recorders track `peerKey`; the three
  `recordFormationComplete` call sites pass fixture consent strings, deliberately, since
  nothing in a mock verifies them.

### Found and fixed in this pass (minor)

- **Duplicated rejection matrix.** The bad-consent case list was written twice, once per
  spec, and the two copies had already drifted in labelling. Replaced with one
  `invalidConsentContacts(good)` builder in `formation-consent-helper.ts`, used by both
  layers — so the protocol-layer pre-check and the recorder-backed responder now assert the
  same matrix by construction.
- **Missing negative cases.** The matrix tampered the signature, the `partyId` and the
  `peerKey`, but never moved the other two signed inputs. Added three cases: consent minted
  for another token, disclosure swapped after signing, nonce swapped after signing. Each
  keeps the signature intact and moves exactly one signed field, so a responder that dropped
  any field from the digest fails exactly one case. All pass.
- **Canonicalization was untested.** Nothing proved the canonical-JSON step is load-bearing
  rather than incidental — a responder comparing raw JSON text passed every existing test.
  Added a positive test in `strand-formation-protocol.spec.ts`: a contact whose disclosure
  keys arrive in a different order is still approved.
- **Harness nonce could collide.** `joinStrand` built `usageStampId` as
  `stamp-<token>-<Date.now()>`; two joins of one multi-use invite in the same millisecond
  produce the same nonce and the unique-column insert fails. Now keyed on the per-join
  throwaway public key.

## Settled design decisions (unchanged by review)

- A failed consent check is an ordinary `approved: false` with reason `'Invalid joiner
  consent'`, never an abort; the `FormationAbortedError` / settle-grace paths are untouched.
- Joiner nonce reuse surfaces as `'Formation conflict, retry'` with the invite unspent.
- The consent pre-check runs for every responder configuration and burns no nonce at the
  protocol layer, so protocol-spec tests may reuse one contact object.
- A `ValidationUrl` invite requires BOTH the approver's vouch and the joiner's consent, over
  the same nonce and the same canonical disclosure bytes.
