# Complete: constrain what a redeemed invitation may seat

## What shipped

Two CHECK-constraint edits, applied byte-identically in `schemas/control.qsql` and the
`CONTROL_SCHEMA` string in `packages/cadre-core/src/control-schema.ts` (parity pinned by
`control-schema-drift.spec.ts`):

- **`FormationUsage.Authorized`** — a bound invite (`FormationInvite.StrandId` non-null) may
  only record usage against its own named strand.
- **`Strand.AuthorizedInsert` consent branch** narrowed to four clauses: the seated strand
  must be open (`Type='o'`) and keyless (`MemberPrivateKey` null), the redeeming invite must
  be unbound, and the id must never have been consent-seated under any other stamp
  (once-ever, leaning on `FormationUsage` being append-only).

TypeScript side: `ControlDatabase.redeemInvitation` lost its `type` / `memberPrivateKey`
parameters (the `Strand` insert is hard-coded `values (?, 'o', null, ?)`);
`ControlFormationUsageRecorder.provisionAndRecord` dropped `type: 'o'`.

**Behavior deliberately withdrawn:** consent-driven re-join of a removed strand id. Re-join
is owner-gated — owner re-seats the id signed, then issues a bound invite the returning
party records consent against.

### Major — one, filed as a new ticket

**The once-ever rule does not cover ids that were only ever owner-seated.** It is enforced
by looking for a *surviving* `FormationUsage` row naming the id, and an owner-signed
`insertStrand` writes none. So a strand created owner-signed, never consent-recorded, and
then legitimately removed (signed delete + tombstone) can still be seated afterwards by a
spare unbound invite use. Confirmed empirically, not inferred: a probe re-seated a removed
closed, key-bearing strand id and the row came back as open/keyless. The shape clauses hold,
so no secret is chosen — what breaks is that the removal does not stick, which is the exact
class the ticket set out to close.

Filed as `tickets/backlog/bug-consent-reseats-owner-only-removed-strand-id.md`. Filed rather
than fixed inline because the tombstone table (`Revocation`) records only the deleted row's
stamp, never its id, so closing this needs a schema/design decision that would also have to
carve out the owner-signed re-join path this ticket just established.

Pinned by a new test in `control-revocation-replay.spec.ts` —
`'Strand: RESIDUAL — an id seated ONLY owner-signed, then removed, is still consent-seatable'`
— which asserts the *current* behavior so it cannot regress unnoticed and flips to an
`expectConstraintFailure` when the new ticket lands.

### Minor — fixed in this pass

- **Documentation overclaimed the fix.** `docs/architecture.md` said consent "can neither
  choose the party's secrets nor re-seat a removed id" and "a spare use of an old invitation
  can never re-form a removed id unsigned". Both are false for the owner-only case above.
  Narrowed to "an id it already seated once" and added an explicit residual paragraph
  pointing at the new ticket.
- **Schema comments carried the same overclaim.** Added a `RESIDUAL:` block to the once-ever
  bullet in both `schemas/control.qsql` and `control-schema.ts`.
- **The two shape clauses were only ever tested together.** The implementer's closed-strand
  test supplies both a closed `Type` *and* a caller-chosen `MemberPrivateKey`, so dropping
  either clause would still have gone green. Added
  `'rejects a consent redemption seating a CLOSED but keyless strand (AuthorizedInsert)'` to
  `control-formation-invite.spec.ts`, which isolates the `Type='o'` clause.

### Tripwire — one, parked in code

An **unbound** invite is deliberately left free to name any strand in
`FormationUsage.Authorized`, so a holder can spend a use appending a consent row to an
unrelated existing strand. Harmless today — the row grants nothing, it burns a use, and it
only forecloses that id's consent-seating (the safe direction). Recorded as a `NOTE:` at the
clause in both schema copies: if unlimited-`TotalUses` invites ever become common, this is an
append-only growth surface worth bounding.

### Checked and clear

- **Constraint logic itself** — no defect found. `StrandStampId` is `not null`, so the

  `FormationInvite.Token` is the primary key, so the bound clause cannot be dodged by

## Known limits carried forward

- `context.PeerId` / `PeerSignature` on `FormationUsage` are declared but never verified —
  the invitation token is a bearer credential. Pre-existing, out of scope.
- The `ValidationUrl` sign-off digest binds only (Token, Disclosure), so one approval is
  replayable across redemptions of the same token
  (`tickets/backlog/debt-formation-approval-signature-replayable.md`).
- Where a write violates both new rules, the tests assert the single constraint Quereus
  reports. If that reporting order ever changes, diagnose it as an engine change rather than
  widening the accepted-name list — `control-constraint-helpers.ts` says the same.
