# Join by invitation — complete

Fifth of the `cadre-host-join-a-cadre` chain. The host can now start a hosted node with a cadre invitation instead of a claim secret; the node redeems it at a member of the cadre (the mechanism from `cadre-invitations-redeemable-by-any-member`). Built as the implement ticket specified, with the deviations listed under **Deviations**.

## What changed

**cadre-cli.**
- `CADRE_INVITATION` (env only; set-but-empty is unset) is `--invitation` without the argument; passing both is refused. The invitation helpers moved from `start.ts` into a new `commands/start-invitation.ts`: `startupInvitation` (flag vs env), `decodeInvitationFor`, `refuseInvitationConflicts` (both now name whichever form was used), `redeemStartupInvitation`, `describeRedemptionFailure`. `refuseClaimConflicts` takes the `StartupInvitation` and names `--invitation` or `CADRE_INVITATION`. The "no retry here" `NOTE:` moved with the redemption into `redeemStartupInvitation`.
- `/status.node.invitation?: { state: 'pending' | 'accepted' | 'failed'; memberPeerId?; error?; retryable? }` (`InvitationStatus` in `server/health.ts`), present only when started with an invitation. A member's refusal keeps its code: `error` is `"<message> (invite-spent)"`. An unreachable failure is `"No member named in the invitation could be reached. <cadre-core's message>"`, `retryable: true`. Anything else (reply check failed, a precondition) is `retryable: false`.

**cadre-host.**
- Record (`hosted/types.ts`): `join` is `{ kind: 'claim'; secret } | { kind: 'invitation'; encoded }`; new status `joining`; new fields `memberPeerId?` and `retryable?`; new change kind `'joined'`. The view strips both credentials (`join: { kind }`).
- `HostedSpawnRequest.invitation?` reaches the child as `CADRE_INVITATION` (`joinEnv` in the orchestrator). A request carrying both a claim secret and an invitation throws before anything is allocated.
- Service: `join({ invitation? })` decodes with `decodeCadreInvitation` and throws `invalid_request` before any record is written (now `async`, so the error is a rejection). It spawns under the invitation's party and records `joining`. `spawnRequestFor` passes the invitation unless the record is `joined`. `retry(id)` requires `error` + `retryable: true` (409 otherwise). It stops a still-running child, writes `joining`, and respawns without counting an attempt.
- **Respawn queue.** `retry` is a second caller of `respawn`. The service now owns one respawn queue (`serializeRespawns`), shared by the supervisor's reconcile passes and restarts and by `retry`. Without it, the exit event from Retry's stop could queue a supervisor pass that double-spawns the node. The supervisor's private tail is gone.
- `abandonRespawn`, when the record went `error` mid-spawn, now writes the new child's handles onto the `error` record so a later `remove` reclaims them. The old `NOTE:` asked for exactly this once a second `error` writer could overlap a respawn, and the watcher's invitation-failure write can. The existing test `stops but does not reclaim the new child when the record goes error mid-spawn` now expects `dockerId: 'dock_2'`.
- Watcher: polls `joining` nodes every tick, as it polls `unclaimed` ones.
  - `accepted` → `joined`, with `ownerKey` = the invitation's issuer key (decoded from the record) and `memberPeerId`; emits `'joined'`.
  - `failed` → `error` with `error` and `retryable`, then stops the child (record written first). The child and workdir are kept for Retry.
  - A `failed` seen on a `joined` record is ignored (stated in `applyJoined`'s comment).
- Supervisor: supervises `unclaimed | joining | joined`. It never touches `error`, as before.
- The service's size `NOTE:` asked for the claim-details code to move out when this kind landed. It now lives in `hosted/claim-details.ts` (`ClaimDetails`, `HostedNodeAddressSource`, `buildClaimDetails`, `isDialableFromLan`); the NOTE is gone.
- Routes: `POST /api/hosted-nodes` takes `{ invitation? }`. A non-object body or a non-string or empty `invitation` gets 400. New route: `POST /api/hosted-nodes/:id/retry`.
- CLI:
  - `cadre-host join --invitation <encoded> [--no-wait]` prints "Joining cadre <party> through the invitation…", then "✓ Joined cadre <party> at member <peer>", or "✗ Could not join: <reason>" (exit 1) plus the first-node hint when retryable.
  - `cadre-host node retry <id> [--no-wait]`.
  - `node list` shows an invitation node's cadre from the start.
  - The claim path's error exit was folded into a shared `waitUntilSettled` poll.
- UI:
  - Join page: an "Or paste a cadre invitation" textarea with a Join button (the field clears once the node starts). Joining nodes are followed with their live line. A failure shows the reason, and when retryable adds the hint plus Retry and Remove.
  - Node page: a joining node gets Cancel. A failed invitation node gets Retry (the retry route, no confirmation) and the hint only when retryable, plus Remove. A joined invitation node gets Remove only, with no Reset. The claim-node buttons are unchanged.
  - `isWaiting` now takes the node and means "a claim node not yet claimed"; new helpers `isPending` and `canRetryInvitation`, and the constant `UNREACHABLE_HINT`. The Home tile's "waiting" count includes joining nodes.

**Docs.** docs/cadre-host.md: a new "Join by invitation" subsection under Hosted nodes covering when it works, the first-node case, Retry, the respawn rule and Reset. Also updated there: the statuses table, "Where the secret goes" (the invitation is a credential too), the API tables, the CLI paragraph, the local-UI bullets, the supervisor invariant and queue, the respawn and abandon bullets, the SSE kinds, and Status. The cadre-host README has the walkthrough's second way, a `retry` line under "Manage hosted nodes", reference headings for `join --invitation` and `node retry`, and Local UI and start-routes text. The cadre-cli README has the env row, the `/status` field paragraph and the conflict wording. docs/testing.md has a scenario bullet. docs/architecture.md got a minimal edit to the cadre-host summary line (the full pass belongs to `cadre-host-join-docs`). `harness/port-allocator.ts` records the new port band 20200–20359.

## Deviations and known gaps

- **Hint wording.** The ticket's hint starts "No member of the cadre could be reached.", but the reason printed just above already says that (the cadre-cli message starts "No member named in the invitation could be reached."). The CLI and UI instead say: "If this is the cadre's first always-on node, no member can be reached yet: use `cadre-host join` without `--invitation` and scan the QR code from the phone instead. Otherwise, once a member is online, run `cadre-host node retry <id>`." The UI version names the Join button and Retry.
- **Failed child is stopped.** The ticket did not say what happens to the child of a failed invitation. The watcher stops it (record written first, workdir kept), the same as a give-up, so an `error` record never has a running child behind it. Retry also stops a still-running one before respawning.
- **Reset of an invitation node** starts a node waiting to be claimed (the invitation may be spent). The UI hides Reset for invitation nodes; the CLI `node reset` still does this, as documented.
- **By inspection only:**
  - The targeted-invitation-for-another-device case. The member answers `invite-invalid` with reason "The invitation names another device", so the record reads "Cadre invitation refused: The invitation names another device (invite-invalid)", `retryable: false`.
  - The `CADRE_INVITATION` + `CADRE_CLAIM_SECRET` refusal.
  - The CLI's `join --invitation` and `node retry` polling and output.
  - Every UI template branch. There is still no component-test harness (`debt-cadre-host-ui-component-tests`), and the pages were not opened in a browser.
- **Scenario A runs the relay server** (`enableRelay: true`) so that, once its invitations are spent or expired, its gate still admits the device for relay only and answers the expired redemption by name (the any-member scenario's withdrawal arm relies on the same). Without it, step 3 would depend on the sibling members listed in the bundle answering instead.
- **Step 2 waits for A to reconnect to step 1's node** before Retry, because A's admission write needs that cohort member. A Retry sent sooner can fail again, retryably. That is correct behaviour; the scenario just avoids the race.
- `hosted-node-service.ts` is 794 lines (was 765) even after the claim-details move: the invitation join, `retry` and the respawn queue added about 80.

**Checked and correct (no change):**
- Races between the watcher's `failed` write, Retry and the supervisor. The watcher writes `error` before it stops the child, so the exit it raises finds a record the supervisor leaves alone. Retry runs on the shared respawn queue, re-reads after its stop, and a respawn that throws leaves the record `joining` with the old stopped handle, which the supervisor's next pass respawns. `abandonRespawn` now points an `error` record at the new child, so a later `remove` reclaims it.
- `retryable` semantics. cadre-core throws `CadreInviteRejectedError` from redemption only for a final refusal (`cadre-invite-protocol.ts`, `if (!refusal.retryable) throw refusal`), so `retryable: true` on `/status` means exactly `CadreInviteUnreachableError`, as the cadre-cli README says. An unreachable error can also collect busy/conflict refusals; its cadre-core message lists them, and Retry is the right action there too.
- Credential handling. The orchestrator scrubs every inherited `CADRE_*` variable, so a stray `CADRE_INVITATION` in cadre-host's own environment cannot reach a claim child. The view strips `join` to `{ kind }`, and the integration scenario checks that no invitation text appears in `GET` or SSE.
- Route body handling (`joinOptionsOf`): a non-object body, or a non-string or blank `invitation`, gets 400; the service trims and decodes before any record is written.
- Respawn rule (`spawnRequestFor`): the invitation goes to the child only while the record is not `joined`.
- Tests. Each new test pins a contract with real branching: the lifecycle through failure, Retry and acceptance; the respawn rule; the 400 and 409 routes over the real service. The shared `test-invitation.ts` fixture is shape-only, which is correct because the host never verifies signatures. Nothing to cut and nothing to add: the cadre-cli conflict and `retryable` mapping are exercised end to end by the integration scenario's steps 2 and 3.
