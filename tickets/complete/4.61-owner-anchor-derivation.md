# Complete: the trusted-owner anchor is derived from the owner table along verifiable chains

Second of three tickets (after `owner-anchor-revocation-signer-and-owner-writers`, before `owner-anchor-follows-owner-key-changes`, the live-network proof). Implementation landed as `ticket(implement): owner-anchor-derivation`; the review pass changed the derivation rule (below) and is in the review commit.

## What landed

- **The rule as a pure function** (`owner-anchor-sync.ts`, no I/O): `deriveOwnerAnchor({ anchor, rows, tombstones, chain })` returns `{ target, refusedRemovals }`. The out-of-band entries are the base; a `chain` entry is kept while its own row is live; the least fixpoint from base and kept adds every key whose live row's stored proof verifies (owner-signed through `verifyOwnerKeyVoucher`, invitation-admitted through `verifyInvitationOwnerAdmission`, the founding row never); a key is removed when a tombstone names it, the tombstone's signer is in the pass-start set and is not the key, the signature verifies, and the key has no live derivable row (a re-add under a fresh stamp wins); a removal that would empty the anchor is refused and reported. Every tombstone is judged against the pass-start set, so the result is independent of read order.
- **The anchor store** (`trusted-owner-store.ts`): `TrustSource` gains `'chain'` (persisted and reloaded); `sources()` on both backends; `trust()` promotes a `chain` entry to any out-of-band source and never demotes one.
- **The verifier** (`peer-authorization.ts`): `verifyInvitationOwnerAdmission` for `OwnerKey` rows, sharing the signature-chain tail (`verifyAdmissionChain`) with the `CadrePeer` verifier.
- **The reader** (`control-database.ts`): `queryOwnerKeyRows(retry, retired?)`; `getOwnerKeys` reads through it.
- **The sync** (`cadre-node.ts`): `syncOwnerAnchor` is the first step of every membership refresh, reads the tombstones once and hands the retired `OwnerKey` stamps to the row reader, loads the invitation chain at most once per refresh (shared with the membership read through `invitationChainSource`), diffs against the pass-start snapshot so a key trusted out of band mid-pass survives, and skips the pass on any read failure without failing the refresh.
- **Docs**: `docs/architecture.md` (the `OwnerKey` table row, the anchor bullet, the sub-paragraphs "How the anchor follows the owner table" and "What the derivation cannot settle", "What invitations carry", the invitation-redeemed-at-any-member sentence).

## Review findings

**Read first:** the implement diff (`ticket(implement): owner-anchor-derivation`), then the handoff.

### Major, fixed in this pass: the rule broke owner rotation

The implemented rule (and the plan's formal rule, which it followed) recomputed every `chain` entry from the out-of-band base on each pass, and the sync returned early when the base was empty. Owner rotation is add-then-remove (the docs' own pattern): A adds A', A' removes A. The pass that sees both derives A' from A and removes A, correctly. On the next pass A' has no path from any base key (A's row is retired), so on a machine whose only base was A the sync returned early and A' was frozen as a `chain` entry that could never be removed and whose additions were never derived, and on a machine with another base key A' was pruned outright. A sole owner could therefore never rotate, and a co-owned cadre lost the rotated-in key on every machine that had not pinned it. Reproduced against the pure function (second pass with an empty base yielded an empty target) before the fix.

Fix: a derived entry is state, not something recomputed each pass. `deriveOwnerAnchor` now takes the whole anchor with provenance (`anchor: ReadonlyMap<string, TrustSource>`), starts the fixpoint from base plus every `chain` entry that still has a live row, and the sync's early return is on an empty anchor (the node-awaiting-claim seam is unchanged: an empty anchor derives nothing). Removal is unchanged: a chain entry still goes when its row is retired or a verifiable tombstone names it. Consequence, now stated in the module doc and the architecture doc: an owner C that a removed owner B added keeps its place wherever it was already derived, and is out of reach for a machine that never held it until a remaining owner re-adds it or an invitation pins it. That is the plan ticket's stated intent ("C stays trusted when B is removed"), which the implementer had deliberately deviated from for cross-machine consistency; rotation has exactly the same shape as that case and cannot be told apart from replicated state, so keeping is the only rule under which rotation works at all. The reviewer weighed the deviation's argument (machines enrolled later disagree) and judged it the lesser harm: a later-enrolled machine receives the issuer's anchor as invitation pins, while the pruning rule distrusted the rotated-in key everywhere.

Test: `owner-anchor-sync.spec.ts` gains "an owner rotation survives the pass after the old key is removed, and the new key then vouches and is removable" (the reproduction, plus that the kept key vouches and is itself removable), and the removed-voucher test is restated as "keeps an owner a removed owner had added where it was derived, and cannot derive it elsewhere until re-added". The `listAuthorizedMembers` rotation NOTE, the `TrustSource` doc and the `syncOwnerAnchor` doc now say the same.

### Checked and accepted

- **Happy path and chain shapes**: chain of two with mixed proofs, far end first; founding row never derivable; empty anchor derives nothing. Pure spec.
- **Removal semantics**: re-add beats an older tombstone; base pin of a removed key dropped; mutual removal of the last two refused and reported; stranger-signed, self-signed and forged tombstones ignored; a signer removed in the same pass still counts (pass-start set). Pure spec and reading.
- **The mid-pass race**: the apply diffs against the pass-start snapshot; the node test gates the tombstone read and pins a key meanwhile. Reading and the test.
- **`verifyAdmissionChain` refactor**: behaviour-preserving for `CadrePeer` rows (the targeted-invitation and key-derivation checks were restated over the usage's peer id, which the retained `usage.peerId === row.peerId` equality pins to the row's). Reading.
- **Read-failure path does not fail the refresh**: accepted. `queryRevocations` has no cohort-unreachable fallback where the membership read's `readRevokedStampRows` does; failing the refresh would freeze an isolated node's gate snapshot. The anchor the snapshot is judged against is then the one its previous snapshot used.
- **Consult budget**: one `Revocation` consult per refresh before the ledger marker, zero after; the figures in `control-founding-consult-budget.spec.ts` moved by that one and the spec explains it. Full suite green.
- **Type safety and hygiene**: no `any`; `pinnedSource` and `trustOwnerKeys` exclude `'chain'`; `isInvitationAdmitted` widened structurally rather than duplicated; `InvitationChain` moved to `types.ts`. `owner-anchor-sync.ts` is 169 lines.
- **Docs**: every touched doc site reread against the code; the deviation paragraph replaced by the kept rule; the row-type doc's reason for a non-null `stampId` corrected (the stampless row is dropped by the reader, not retired).

### Tripwires parked

- **Unverified tombstones retire rows** (`NOTE:` at the top of `deriveOwnerAnchor`): a stamp is retired by any tombstone that names it, verified or not, the reading `queryCadrePeers` and `getOwnerKeys` already give the table. A forged tombstone can prune a derived entry but never seat or keep one. Becomes work if tombstone pollution is closed at the write side (`stranger-joins-the-control-cohort-by-advertising-protocols` in `blocked/` is the route a stranger's row would need).
- **Isolated node, `Revocation` block never held**: the sync is skipped at every refresh until the block is held. `NOTE:` at `syncOwnerAnchor` (implementer's).
- **Cost per refresh**: one `OwnerKey` read and one `Revocation` read, plus the invitation chain when an owner row is invitation-admitted. `NOTE:` at `syncOwnerAnchor` (implementer's).
- **Operator pin of a removed key** is honoured for at most one refresh per start. `NOTE:` at `initializeTrustedOwnerStore` (implementer's).

## Known gaps

- **A machine that never derived a kept owner** (enrolled after the voucher's removal, or offline for the whole window and holding the voucher only as `chain`) cannot derive it from replicated state; a remaining owner re-adds it under a fresh stamp or an invitation pins it. The docs say so under "How the anchor follows the owner table".
- **Order of owner removals** is not recoverable from replicated state ("What the derivation cannot settle"); `fix/removed-owner-still-authorizes-where-its-row-survives` owns the unbounded window.
- **The node's own removed key** is re-anchored as `genesis` at each start and removed by the first refresh; self-shutdown on removal belongs to the device-removal plan ticket.
