# Phone kit: one app recommends another (complete)

First of three tickets for "app A links to app B; the user allows B to join before leaving A; B joins A's cadre on first launch". `reference-app-rn-recommends-an-app` (A's side) and `reference-app-rn-joins-the-app-that-recommended-it` (B's side) build on it. Landed in `ticket(implement): phone-kit-app-recommendations`; the design is in docs/architecture.md → "Recommending another app".

## What was built

- **`AppRecommendationStore`** (`src/app-link/recommendation-store.ts`) over the new `PhoneNode.recommendationSlot()` (`PhoneNodeNames.recommendationsKey`, default `recommended-apps`): one JSON list, at most one entry per scheme. `approve`, `live(partyId)`, `withdraw(scheme)`, `take(scheme, partyId)` (single use, party-bound, one-hour `RECOMMENDATION_TTL_MS`), calls serialized as `LinkRequestStore`'s are; a malformed record reads as none with one warning.
- **Links**: `recommendedByLink` and the `recommended-by` kind of `parseCadreLink` in `links.ts`; `storePageLink`, `recommendedByReferrer`, `recommendedBySchemeFromReferrer`, `RECOMMENDED_BY_REFERRER_PREFIX` in `recommend-links.ts`.
- **`SereusApp`** gains optional `androidPackage` and `iosAppStoreId`; the config plugin validates them on extras and declares a `<queries>` VIEW intent for every known and extra scheme (plus `sereus-join-request`) so Android's `canOpenURL` can see them.
- **Reference app** `+native-intent.tsx` passes `recommended-by` links through unrouted until B's ticket routes them.
- **Docs**: architecture.md "Recommending another app" section and the cross-references in "Between apps on one phone"; kit README "Recommending another app", store ids, plugin `appLinks` additions.

## Review findings

Read the implement diff first, then the handoff; reread every touched file plus `link-request-store.ts`, `known-apps.ts`, the reference app's `cadre-phone.ts` / `app.config.ts` (the consumers of the extras list), and the architecture section against the code.

- **Correctness / security contract** — checked `take`'s single-use, party and expiry filters, the replace-on-approve, the serialization through one promise chain, and the parse-to-empty on a malformed record against the architecture text. No defect found.
- **Docs drift (fixed)** — architecture.md said "Each write drops expired entries and other parties' entries", but `withdraw` keeps other parties' unexpired entries (it names no party). Reworded to say `approve` and `take` prune other parties and `withdraw` does not.
- **Clock set backwards (tripwire)** — an entry dated ahead of `now` passes `now - approvedAtMs <= TTL`, so it lives longer than the hour the user agreed to. Contrived (needs the clock moved back after approving); parked as a `NOTE:` at the expiry filter in `recommendation-store.ts`. `LinkRequestStore` has the same shape but there it only lengthens how long an answer is accepted, not a grant.
- **Type documentation (fixed)** — `AppRecommendation.grantsOwner` had no doc; added one line.
- **Handoff judgment calls** — agreed with each: `withdraw` keeping other parties' entries is storage tidiness only (never returned for the running party); `take` writing only on a match is fine; `recommendedByLink` / `recommendedBySchemeFromReferrer` not form-checking the scheme is covered by the exact-equality trust rule, documented in both the module comment and the `CadreLink` doc; placing `recommendedByLink` in `links.ts` beside its parser is the better home.
- **Interaction with consumers** — the reference app's `extraSereusApps` checks only `name` and `scheme`, so store ids pass through unvalidated at run time. That is the consumers' concern and lands with the two follow-up implement tickets, which already read store ids from that list; not filed.
- **Plugin** — `addViewQueries` dedupes against existing `<queries>` intents and within the given list; the app's own scheme is included, which is harmless. No Android cap on `<queries>` entries analogous to iOS's 50. Not re-run by hand (the implementer's scratch run is described in the handoff); no test added, consistent with the testing bar (manifest glue).
- **Tests** — the store spec (4 tests) pins the security contract with real branching; the `parseCadreLink` rows and referrer table cover parsing branches. Nothing to cut; nothing added (no defect needed a reproduction).
- **Resource cleanup / performance** — the store reads and rewrites one small JSON value per call; no handles held. Nothing to note.
- **Not verified on a device** (carried from the handoff): `canOpenURL` on Android 11+ with the new `<queries>`, and the Play referrer round trip. Both are exercised by the two follow-up tickets.
