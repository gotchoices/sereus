## What landed

The npm-install update flow for cadre-host. Signed Ed25519 manifest fetched from `https://releases.serfab.io/cadre-host/latest.json` on `cadre-host start` and every 24 h thereafter; available updates are announced via `<dataDir>/update-state.json` (notify-by-default) with auto-apply opt-in. Apply re-fetches, re-verifies, runs `npm install -g`, restarts the OS service unit via the platform's `ServiceHost.restart()`, and rolls back on install failure.

Module layout under `packages/cadre-host/src/update/`:

- `types.ts` — `UpdateManifest`, `SignedManifest`, `UpdateState`, `UpdateApplyResult`, `UpdateErrorException`, error codes.
- `version.ts` — hand-rolled semver compare (semver §11 prerelease rules; build metadata rejected).
- `release-key.ts` — embedded prod public key + `CADRE_HOST_UPDATE_DEV_KEY` env override (the shipped key is a placeholder; see "Known follow-ups").
- `manifest.ts` — `fetchManifest()`, `verifyManifest()`, `canonicalJson()`, `signManifestForTesting()`.
- `store.ts` — `UpdateStateStore` (atomic tmp+rename JSON, same pattern as `TrustCircleStore`/`NatStore`).
- `apply.ts` — `applyUpdate()` with pluggable `NpmExecutor` + `ServiceRestarter`; best-effort rollback on install failure.
- `index.ts` — `UpdateService` composition root, `createUpdateHandlers()` for the local-UI ticket.

Surrounding edits:

- `installer/config.ts` — `HostConfigFile` v1 → v2 with `updates: { autoApply, manifestUrl? }`; v1 files silently upgrade on read.
- `installer/service-host/{types,systemd,launchd,nssm}.ts` — adds `restart(ctx)` to the `ServiceHost` interface and all three impls.
- `installer/index.ts` — installer writes `version: 2` configs with `updates: { autoApply: false }`.
- `bin/host.ts` — `start` constructs `UpdateService`, wires `ServiceRestarter` to the platform's `ServiceHost.restart()`, registers an `onSettingsChanged` hook to persist back into `host.config.json`, fire-and-forgets `check()`, and arms the 24h timer (`unref()`d). `stop()` runs on SIGTERM.
- `index.ts` — exports the new types/values.
- `README.md`, `docs/cadre-host.md` — addendum sections covering the threat model, env override, autoApply, and the architecture sketch.

50 new tests + the integration suite, all green.

### Untested edges

- **`applyInProgress` reload-from-disk.** No test starts a fresh `UpdateService` against a pre-populated state file containing `applyInProgress` to verify what the next process actually does. (Today it just rejects subsequent applies with `apply_in_progress` — see follow-up #2.)
- **Env-var manifest-URL precedence.** I fixed an ordering bug here (see "Fixed inline" below) — a regression test would lock in the README's documented behavior.

### Findings — fixed inline this pass (minor)

1. **`FetchManifestOptions.connectTimeoutMs` was a dead config knob.** The fetch wires only `readTimeoutMs`. Removed the unused field; clarified the surviving timeout's docstring.
2. **Env-var manifest URL lost to constructor `opts.manifestUrl`.** `resolveManifestUrl(explicit, fromSettings)` was `explicit ?? envUrl ?? fromSettings ?? DEFAULT` — but the README + host.ts comment both promise "env var wins over config." Reordered so env wins, then explicit → settings → default. Documented in the inline comment.
3. **Redundant `mkdirSync(dirname(this.path))` inside `UpdateStateStore.save()`.** The constructor already creates the root dir, and `dirname(this.path)` equals that root. Removed (and the unused `dirname` import).
4. **`detectPlatform()` called twice in `bin/host.ts start`.** Hoisted to a local `const platform`.
5. **`docs/cadre-host.md` had no section on the update flow** — added one ("Updates") before the architecture sketch, updated the mermaid diagram to include `UpdateService`, and added a line to the Status section listing the new subsystem.

### Findings — filed as follow-up (medium severity)

Filed `tickets/backlog/cadre-host-update-flow-hardening.md` with three items the review surfaced but that don't block the current ticket:

1. **`defaultNpmExecutor` triggers Node `DEP0190`** on Windows (`spawn('npm', args, { shell: true })`). Real exploitability is gated by manifest-signature verification, but the deprecation is on a path to becoming an error in a future Node major. Suggested fix: PATH-resolve `npm.cmd` and spawn without a shell, plus tighten the npm-package-name regex before exec.
2. **`applyInProgress` can leak forever after a crash.** No recovery path short of editing JSON. Suggested fix: on `UpdateService` construction, clear stale `applyInProgress` and record a `lastError` so the UI surfaces it.
3. **Manifest field validation is type-only.** `isUpdateManifest` accepts any non-empty string for `version` / `publishedAt` and any string for `channels.npm.package`. A malformed (but signed) manifest surfaces as a confusing `compareVersions` throw downstream. Suggested fix: parse-validate `version`/`minPreviousVersion` in `verifyManifest`.

### Findings — not addressed (deliberately deferred)

- **Placeholder release public key.** Out of scope for this ticket; tracked as release-tooling work. The `CADRE_HOST_UPDATE_DEV_KEY` env override lets CI + local manifest testing proceed.
- **Standalone-binary apply path.** Separate backlog ticket per the original scope.
- **`npm install -g` permission issues** on Linux distros where `/usr/lib/node_modules` isn't writable by the cadre-host user. The error surfaces cleanly via `lastError.message`; the installer doesn't try to detect/warn proactively. Implementer flagged this as banner-copy work for the local-UI ticket (`6.5`), which is the right home.
- **24-hour timer is `unref()`d.** Correct for `cadre-host start` (we want SIGTERM, not a stranded timer, to keep the process alive). Documented in source.

### Categories checked but empty (intentionally noted)

- **Resource cleanup:** `stop()` clears the interval; SIGTERM path in `host.ts` calls it. No leaks.
- **Cross-platform:** `ServiceHost.restart()` lands on all three platforms (systemd/launchd/nssm) and the smoke `FakeServiceHost` was updated. Path handling in the package-version read uses `fileURLToPath` + `resolve` — safe on Windows.
- **Performance:** Daily timer + a single fetch is well below noise floor; canonical-JSON serializer is O(n log n) on a tiny fixed shape — fine.
- **Backwards compatibility:** v1 → v2 config migration is idempotent and tested. Per AGENTS.md the project doesn't broadly chase compat, but this specific path matters because users have v1 configs from the just-landed 6.4.1.
