# `reference-app-web`'s stale-build target list is complete and pinned

## What shipped

- `packages/reference-app-web/package.json`: `"@serfab/cadre-core"` changed from
  `"*"` (an npm range yarn happened to satisfy from the local workspace) to
  `"workspace:^"`, matching every other consumer in the repo. Without it the
  manifest cross-check cannot classify the dependency, so the drift spec would
  pass having checked nothing. `yarn.lock` regenerated and committed.
- `packages/reference-app-web/test/global-setup.ts`: `TARGETS` expanded from one
  entry to eight —
  `@serfab/cadre-core` and `@serfab/quereus-plugin-sereus` (`workspace`);
  `@optimystic/db-core`, `@optimystic/db-p2p`, `@optimystic/db-p2p-storage-web`,
  `@optimystic/quereus-plugin-crypto`, `@optimystic/quereus-plugin-optimystic`
  and `@quereus/quereus` (`linked`). The three plugin packages are not declared
  dependencies of this app: importing `@serfab/cadre-core`'s entry point
  evaluates `cadre-node.js` / `control-database.js` / `strand-database.js`, which
  import them statically, so the suite runs their compiled output regardless.
  Same transitive reach `cadre-cli` and `cadre-host` already list for.
- `packages/reference-app-web/test/build-targets.spec.ts`: new, one call to the
  shared `describeBuildTargets` / `packageRootFrom` helpers, matching the five
  existing copies. Pins `@serfab/cadre-core` → `workspace` and `@quereus/quereus`
  → `linked` in `expectFound`, so an empty manifest scan can't pass silently.
- `packages/reference-app-web/vitest.config.ts`: `globalSetup` comment widened
  beyond "cadre-core" to name the whole dependency chain.
- `docs/STATUS.md`: the paragraph asserting the web app's list "is a single entry
  and it has no `build-targets.spec.ts`" removed; a new bullet records the
  completed list, why it is wider than the manifest, and that `reference-app-rn`
  is now the one app with no guard at all.

## Why `@optimystic/db-p2p-storage-web` is listed

The vitest suite (`node-local-slots.spec.ts`) imports it only as a TypeScript
type, which erases at runtime — that suite alone never touches its `dist`. It's
listed anyway: it's a declared, link-resolved dependency the app itself runs, and
the drift spec checks the manifest, not the import graph. Accepted cost: a stale
build there fails this unit suite over code it doesn't currently exercise — same
bias toward a loud, fixable failure the whole guard is built on. Documented in
the `TARGETS` comment in `global-setup.ts`.

## Review findings

### Checked

Implement diff read first, before the handoff summary. Then: every `TARGETS`
entry against what `import '@serfab/cadre-core'` actually evaluates (grep of
`packages/cadre-core/src` for static imports, cross-checked against
`src/index.ts`'s re-exports); on-disk resolution of all eight targets
(symlink-vs-real-directory `lstat` in both `packages/reference-app-web/node_modules`
and the repo root's); the new spec against all five sibling `build-targets` specs
for shape and comment accuracy; the manifest/lockfile change; every doc mentioning
the guard; source hygiene of the three touched files.

### Found and fixed in this pass (minor)

- **`TARGETS` was incomplete, contradicting its own doc comment** ("Every package
  this suite runs compiled code from"). `@serfab/quereus-plugin-sereus`,
  `@optimystic/quereus-plugin-crypto` and `@optimystic/quereus-plugin-optimystic`
  are loaded and evaluated whenever a spec imports any real `cadre-core` symbol,
  and none were listed. The drift spec could not catch this — it only sees
  *declared* dependencies, and these three are transitive. Added, with the
  reasoning in both the `TARGETS` comment and the spec's header, matching how
  `cadre-cli` / `cadre-host` document their own wider lists.
- **`docs/STATUS.md` still claimed the web app's list was one entry with no
  `build-targets.spec.ts`** and pointed at this ticket as future work. Replaced
  with a bullet describing what actually landed.
- **`tickets/backlog/debt-reference-app-rn-build-guard.md` deferred a question to
  this ticket** ("whether the list should cover the siblings reached transitively
  through `cadre-core` … land that one first and copy its answer"). Answered in
  place, plus a note that RN's `workspace:^` range must stay as-is for the same
  reason web's `"*"` had to go.

### Major (new tickets)

None new. The one major gap found — `packages/reference-app-rn` runs real
`cadre-core` symbols (`PersistentTrustedOwnerStore`, `KeyStoreAccessError`, …)
with no stale-build guard at all — is already tracked by backlog
`debt-reference-app-rn-build-guard`, which this pass updated rather than
duplicated.

### Tripwires

None new. The two conditional concerns this change could raise are already
recorded as `NOTE:` comments at their sites in `test-harness/build-freshness.ts`:
the per-suite cost of walking every target's `src` and output tree (this suite
went from 1 to 8 targets; vitest still reports `setup 0ms`, the 10.8s→12.4s run
difference is module transform, not the guard), and `distEntry` being written out
by hand rather than read from the target's own `main`/`exports`.
