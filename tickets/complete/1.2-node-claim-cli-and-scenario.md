# `CADRE_CLAIM_SECRET`, claim state on `/status`, and the phone-claims-a-node scenario

Third of three tickets (after `node-claim-proof-and-policy` and `node-claim-gate-and-helper`). Implemented in `ticket(implement): node-claim-cli-and-scenario`.

## What shipped

- **cadre-cli.** `CADRE_CLAIM_SECRET` (env only; set-but-empty is unset) starts the node with `CadreNodeConfig.claim`. `refuseClaimConflicts` refuses `--owner`, `--seed`, `--invitation`, `--pin-owner-key` and `CADRE_OWNER_KEYS` beside it, all named in one error, before the config loads. Console lines: `✓ Awaiting claim`, `• Already claimed; CADRE_CLAIM_SECRET is ignored` on a restarted claimed node, and `✓ Claimed by owner <first 8 chars>` on `claim:accepted`. The secret is never printed.
- **`/status`** gains `node.claim: 'awaiting' | 'claimed' | 'none'` (`ClaimState`). `claimed` is reported only while the node is running and not awaiting, so a starting or stopping node reads `awaiting`, never a premature `claimed`.
- **cadre-core.** A claimed node's `CadrePeer` row is written by its owner after the claim and reaches the node by replication, after the boot-time publish and the first-growth drain have already found nothing. `publishSelfRecordOnceClaimed` runs on the control-cohort reconcile pass (claim nodes only) and publishes the node's signed address record until the first publish lands, instead of waiting 7.5 minutes for the heartbeat. `publishSelfRecord`'s no-row branch now checks `canAuthorize()`, so a listener-only seed service skips instead of throwing.
- **Integration.** `node-claim-by-phone.integration.ts` runs a real `cadre-cli` child against an in-process phone-shaped owner, in six steps: the node awaits a claim; a wrong secret is refused; the right secret claims it and rows cross both ways; a rival owner is refused `already-claimed`; a repeat claim by the same owner is idempotent; a restarted node stays claimed and is dialed again. The spawn helpers (`scrubbedParentEnv`, `isChildUp`, `stopChildProcess`, `allocFreePort`, `resolveCadreCliBin`) now live in `child-node-fixtures.ts`.
- **Docs.** architecture.md: Which Side Dials row 8 and the claim-secret entry. cadre-cli README: a "Waiting to be claimed" section and an env-table row. testing.md: the topology coverage map.

## Review findings

**Checked.**

- The implement diff in full, before the handoff: CLI wiring and conflict check, `/status` claim state, the cadre-core publish fix, the harness refactor, the scenario, and the docs.
- `/status` ordering. `CadreNode.start()` builds the trusted-owner anchor (`initializeTrustedOwnerStore`, `initializeClaimPolicy`) well before `_running = true`, so `isRunning && !isAwaitingClaim()` cannot report `claimed` before the anchor exists. The rule is correct.
- Secret hygiene. `parseClaimSecret` never echoes the value, including in its `cause`. The CLI's failure path prints `error.message`. Neither the CLI nor cadre-core dumps the node config to a log, so the secret does not leak through debug output. Step 6 asserts that the log never contains the secret.
- Conflict check. It runs inside the start `try`, before `resolveConfig` and before any port binds, and exits 1 with the message. `collectPinnedOwnerKeys` already treats a whitespace-only pin list as empty.
- `publishSelfRecordOnceClaimed`. It is gated on `config.claim`, not awaiting, and no publish yet this session; `lastSelfRecordPublishAt` is reset on stop, so it re-arms after a restart. It goes through `registerSelf`'s single-flight guard, and reconcile passes are single-flight too, so there is no duplicate insert. The running guard is rechecked after it.
- The `canAuthorize()` change. Every other owner-only site in `cadre-node.ts` already checks it this way. A listener-only node (including `--listen-for-seeds`) with no row now logs a skip where it used to throw from `insertSelfPeerRecord`. That matches the contract in `registerSelf`'s doc comment ("a non-owner node with no row yet must wait").
