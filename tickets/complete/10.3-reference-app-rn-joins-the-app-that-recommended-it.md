# Phone reference app joins the app that recommended it (recommended side)

The recommended app's half of "recommend an app and enroll it on first launch" (docs/architecture.md → "Recommending another app"). **B** is this app, installed or opened because of a recommendation; **A** is the owner app that recommended it and holds a one-hour pre-approval for B's scheme. B adds no protocol: it opens A with its ordinary join request, and A answers without a prompt. What this work adds is learning which app recommended B, so B can name it and open it directly.

## What landed

- **`src/recommended-by.ts`.** `recommendingApp(scheme, source)` looks a hinted scheme up by exact equality in this build's list of other Sereus apps and names the app from that list; anything else is logged (quoted, cut to 64 characters) and read as none. `appFromInstallReferrer()` reads the Android install referrer through `expo-application`, bounded by `REFERRER_WAIT_MS` (2 s), and parses it with the kit's `recommendedBySchemeFromReferrer`. Neither throws.
- **`src/use-recommending-app.ts`** (moved out of `settings.tsx` in review). `useRecommendingApp(asking, settled, joinUnderWay, onNamed)` combines the two hints: the referrer (Android, read once per mount while the first-launch question would show) and the `recommendedBy` route parameter (the `cadre-recommended-by` link, which wins). On a first launch it names the app in the question; with a cadre it opens a prompt once the start has settled, unless a request or join is already under way.
- **`app/+native-intent.tsx`** routes the `recommended-by` link to `/settings?recommendedBy=<scheme>`.
- **`app/settings.tsx`.** The named first-launch question ("‹A› suggested this app. Join the cadre it holds?", **Join through ‹A›** / **Other choices**), and the prompt for an app with a cadre ("‹A› suggests joining the cadre it holds", **Join through ‹A›** / **Not now**). While the referrer is pending, the Node card shows the status row.
- **`src/join-cadre-section.tsx`.** The ask-and-alert body is the exported `askOwnerAppOrAlert`, shared with Settings; on Android an app that does not open by its scheme falls back to the chooser.
- **`expo-application ~6.1.5`** added; already installed and autolinked as a dependency of `expo-notifications`, so the doc says no dev-client rebuild is needed (not confirmed on a device).
- **Docs:** docs/reference-app-rn.md → "Joining an Existing Cadre" has a new paragraph, "The app that recommended this one"; the package listing, Key Dependencies and When Native Rebuild Is Needed are updated. The device-run ticket in `blocked/` has a "Recommending an app" table.

No tests were added: this is hook and screen wiring over kit functions whose parsing has kit tests.

## Review findings

Read the diff of `ticket(implement): reference-app-rn-joins-the-app-that-recommended-it` first, then the handoff, then `use-link-request.ts`, `join-link.ts`, `use-join-flow.ts`'s `joinExistingCadre`, the kit's `links.ts` / `recommend-links.ts`, and docs/architecture.md → "Recommending another app".

**Checked, no defect found:**

- **Trust rule.** Both hints go through `recommendingApp`, which names the app from the build's own list by exact scheme equality and excludes this app's own scheme (`otherSereusApps` seeds its seen-set with `ownScheme()`). The hinted text only reaches a log line, quoted and truncated. Matches the architecture's "B trusts a hint only when its own list names the app".
- **Referrer timeout.** `Promise.race` subscribes to the referrer promise, so a rejection after the 2 s timer is handled, not an unhandled rejection; the timer is cleared in `finally`.
- **Android fallback in `askOwnerAppOrAlert`.** `openOwnerApp` returns false when `Linking.openURL` rejects (scheme not installed), and `askOwnerApp` cancels the open request it began before returning false, so the second call to the chooser begins a fresh request; no stale open request is left. The existing section never passes a non-null app on Android, so its behaviour is unchanged.
- **Request link at A's scheme on Android.** `joinRequestLink` with an app builds `<A>://cadre-join-request/…`, which A's `+native-intent` parses on either platform, as architecture step 3 requires.
- **State ordering.** The link waits for `startSettled`, so `asking` is read only after the launch read; `reading` is consulted only inside the first-launch branch, so a referrer that stays `'pending'` when the app has a cadre has no effect; `onNamed` is a stable state setter, so its absence from the effect's dependency list is harmless.
- **A link on first launch while a request is already open.** `asking` is checked before `joinUnderWay`, so the link names A in the question rather than being dropped (the handoff's use-case list implied it would be dropped; the docs scope the drop to "when this app already has a cadre", which matches the code). Naming A is the better result: the user's latest action was in A, and a new request supersedes the open one. No change.
- **Docs.** docs/reference-app-rn.md's new paragraph, First launch, Recommend an app, the package listing and When Native Rebuild Is Needed match the code. docs/architecture.md → "Recommending another app" already described B's side and needed no change.

**Fixed in this pass (minor):**

- **Source size.** `app/settings.tsx` had grown to 816 lines (`wc -l`); the new hook, its interface and its state type moved to `src/use-recommending-app.ts`, leaving `settings.tsx` at 742 lines. Settings drops its `Platform` and `recommended-by` imports. The doc's package listing, its "The app that recommended this one" paragraph and the device-run ticket's `files:` name the new module.

**Tripwire (parked as a `NOTE:`):**

The handoff judged this too rare to handle; the modal covers the controls that would open a request, so it needs a response to a request opened just before the link. Parked at the `setSuggested` site in `src/use-recommending-app.ts`.
