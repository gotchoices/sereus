# Strand revocation teardown — complete

Second of three tickets under the plan `removal-must-cut-the-network-not-just-the-row`.
The prereq (`strand-revoked-peer-gate`) shipped the gate that refuses NEW streams, dials,
connections, and relay reservations from a removed party's machines. This ticket closes
what is already OPEN, and gives a node a way to learn that IT was the one removed. The
third ticket (`4.2-strand-removal-e2e-and-docs`) proves the whole claim on a real network
and rewrites `docs/strands.md`; no docs were touched here, deliberately.

## What shipped

**Teardown sweep** (`strand-revocation-enforcer.ts`). Every deny-set refresh also hangs up
every currently-connected revoked peer. The enforcer takes an optional
`getNetwork: () => StrandRevocationNetwork | undefined` — a three-member surface
(`peerId`, `getConnections()`, `hangUp(peer)`) that a real `Libp2p` satisfies structurally
— read lazily on each sweep, because the enforcer is constructed before the strand's
libp2p node exists and the node is dropped again on quiesce.

- Swept by MEMBERSHIP, not by an entered-the-set diff: the sweep is a strict superset of a
  diff, so no diff is kept. A revoked peer that keeps reconnecting is re-swept each poll.
- The hangUp target is the connection's own `remotePeer` object, so no peer-id codec is
  pulled in. A peer holding two connections (direct + relayed) yields ONE `hangUp`.
- Every failure is contained: a missing/throwing network handle, a throwing
  `getConnections`, and a rejected `hangUp` each cost only that pass and are logged.

**On-demand refresh.** `StrandInstanceManager.refreshRevocationEnforcement(strandId)` →
`CadreNode.refreshRevocationEnforcement(strandId)`. Awaiting it resolves only after the
sweep, so "revoke, then refresh" is an immediate cut. Quiet no-op for an unknown,
quiesced, open, or gate-disabled strand. `revokeMember` and `leaveStrand` gained a doc note
telling callers inside a cadre runtime to follow the write with it.

**Self-revocation signal.** When the node's own peer id lands in the deny set, the enforcer
fires `onSelfRevoked`, which `StrandInstanceManager` tags with the strand id and `CadreNode`
emits as the new `strand:revoked` event. Nothing is torn down on our own behalf (the other
side's gate already refuses us); every OTHER revoked peer is still swept in the same pass.
Best-effort by nature: it fires only if the tombstone replicated here before the cut.

## Review findings

**Checked.** Read the implement diff (`f3d3c79`) with fresh eyes before the handoff summary:
all six source files and both spec files. Aspects: sweep correctness (membership vs diff,
self exclusion, dedupe across connections), resource cleanup and lifecycle (construct →
start → quiesce → resume, enforcer removal in `releaseRuntime`), error containment on every
new await, type safety of the structural `StrandRevocationNetwork` surface against
`Libp2p`, DRY, function size and naming, source hygiene (`strand-revocation-enforcer.ts` is
618 lines, of which 335 are comment lines — about 283 code lines across small
single-purpose methods; no split warranted). Swept `docs/*.md` for claims this change makes
stale, and every consumer of `CadreNodeEvents` for the new event. Ran `yarn lint` (clean),
`yarn typecheck` at root — all workspaces plus the three coverage guards — and
`yarn workspace @serfab/cadre-core test` (114 files, 1942 passing, 1 pre-existing skip) and
`yarn workspace @serfab/reference-app-web test` (66 passing). All green; no pre-existing
failures surfaced.

**Minor — fixed in this pass.**

- *The self-revocation latch never re-armed.* `selfRevokedSignaled` was one-shot per
  enforcer lifetime, so a party that is removed, re-admitted by a manager (a fresh `Member`
  row makes its orphaned bindings live again), and then removed a second time would never
  be told about the second removal — a silent miss on a reachable path, not a theoretical
  one. The latch now tracks the TRANSITION into the revoked set: fired on entry, re-armed
  on leaving it (`trackSelfRevoked`). The self check moved ahead of the empty-set early
  return so leaving the set is actually observed. Documented at all three surfaces
  (`StrandRevocationEnforcerDeps.onSelfRevoked`, `StartStrandConfig.onSelfRevoked`,
  `CadreNodeEvents['strand:revoked']`) and covered by a new test
  ("re-arms on re-admission, so a SECOND removal signals again").
- *A doc comment that did not match its code.* `connectedRevokedPeers` claimed "enumeration
  failure yields an empty sweep"; a throw partway through iteration actually keeps the
  targets collected so far and hangs them up. The behavior is the better one (a partial
  sweep beats none); the comment now says so.
- *The new event was unwired in the reference web app.* `store.svelte.ts` subscribes to
  every other `strand:*` event for its event log; `strand:revoked` — the one an app most
  needs to see — was missing. Added. (Typechecking that workspace required rebuilding
  `@serfab/cadre-core`'s `dist`, since consumers resolve it through the build.)

**Tripwire — recorded, not ticketed.** Nothing in `doRefresh` carries a deadline: a
`readRows` or a `hangUp` that never settles wedges the refresh chain, which freezes the deny
set (the poll skips while a refresh is in flight, and every later `refresh()` chains behind
the stuck one). Both are bounded in practice — Quereus reads settle, and libp2p's connection
close has its own timeout — so this is conditional, not a defect today. Parked as a `NOTE:`
at `doRefresh` in `strand-revocation-enforcer.ts`, with the symptom to look for and the fix
to reach for.

**Major — none filed, with reasons.** Three candidates were weighed and all three are
already owned elsewhere, so filing would have duplicated open work:

- *libp2p semantics are asserted only against a stub* — that `hangUp` really closes a
  RELAYED connection and drops the relay reservation riding it. Owned by scenario 1 of
  `4.2-strand-removal-e2e-and-docs`, which the handoff already names.
- *No test asserts `PeerJoinBackfill` stops pushing after the sweep.* At unit level this
  would assert libp2p's behavior rather than ours (the backfill pushes over a connection;
  closing the connection is what stops it). The same e2e owns it.
- *A node with no `MemberPeer` row of its own never learns it was removed*, because the
  deny set is built from `MemberPeer` bindings. Silent by construction, and downstream of
  `feat-strand-party-identity` not having landed — production strands write no device rows
  yet. Already in 4.2's docs list as a stated limitation.

**Considered and declined.**

- *Concurrent hangUps* (`Promise.allSettled` instead of the serial loop). It would bound
  the sweep's wall clock to the slowest close rather than their sum, but it does not fix
  the wedge risk above (an unsettled promise stalls either shape), and serial keeps call
  order deterministic for the tests. Kept serial.
- *Splitting the enforcer module.* 618 lines measured with `wc -l`, 335 of them comment
  lines — the code is small and the gater composition belongs next to the deny set it
  reads. No split.

**Adjacent ticket updated.** Appended an arm to `4.2-strand-removal-e2e-and-docs`'s docs
list: `docs/strands.md` must state what an app has to CALL
(`refreshRevocationEnforcement`, or wait out the ~30 s poll) and what a removed node is
TOLD (`strand:revoked`, best-effort). Those two facts are what let an app author word the
"remove member" button and the "you were removed" screen honestly, which is the original
issue behind the plan — without that arm the docs pass would have described the guarantee
but not the API that delivers it.

## Known gaps carried forward

- Up to one poll interval (default 30 s) of exposure between a revocation replicating and
  the session being cut, unless the app calls `refreshRevocationEnforcement`. Nothing calls
  it automatically, and nothing can today — the module doc states the seam argument.
- `stop()` mid-sweep does not break the loop; remaining `hangUp` calls run against a
  stopping node and are caught + logged. Deliberate.
- The cohort-participation arm of the plan was verify-don't-build and stayed that way: no
  code drops a revoked peer from the Optimystic cohort, because cutting the connection
  already does. The residual facts (the removed node keeps blocks it already replicated;
  blocks held only by its machines may need repair) are a `NOTE:` at `tearDownRevoked` and
  are due to be stated in the 4.2 docs pass.
