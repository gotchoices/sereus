# Complete: the first-sync gate reads every `Strand` table

## What landed

Landed in `ticket(implement): debt-first-sync-gate-reads-every-strand-table`.

- `strand-first-sync-gate.ts`: the probe now reads, after the `Strand.Header`, every other `Strand` table (`Invite`, `ConsumedInvite`, `CancelledInvite`, `Member`, `MemberPeer`, `Manager`, `Revocation`) and then every `App` table, one at a time, stopping at the first that fails. `schemaTables(db, schemaName)` lists a schema's non-view tables and `writableTables(db)` builds the probe order, leaving out the Header (compared case-insensitively). The serialization, `FirstSyncProgress`, the wake schedule and the Header-first read are unchanged.
- `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS` moved from 300 s to 360 s by the rule recorded on the constant: the re-measure on `@optimystic/*` 1.17.0 put a re-attach over an empty store at 105.9 s, over the 100 s threshold, and 3 × 105.9 s rounded up to the next whole minute is 360 s. The measurement is a dated paragraph on the constant: the seven added reads cost about 60 s on that arm (one baseline run with the probe cut back to Header and `App`). The `reattach-kept` arm was not run.
- The invariant's wording ("every `Strand` and `App` table") is updated in the module, class and function comments, the gate-opened log line, `types.ts`, `strand-instance-manager.ts`, `docs/strands.md`, `docs/architecture.md` (`syncing` row, state diagram, Known limits) and `docs/cadre-consistency.md`.
- The gate's spec test now declares a fake `Strand` schema (with `Header` in it) and checks the order Header → `Strand` → `App`, the stop at the first failing table in either schema, and that nothing settled is read again.
- Filed `backlog/debt-first-sync-gate-leaves-index-trees-unfetched`: the probe's full scan refreshes only a table's main tree, so on a launch with no seed peer the index and unique-enforcement trees can still be unfetched when the gate opens.

## Review findings

Read the implement diff first, then the handoff, then every file the change touches.

- **Correctness.** `writableTables` matches the schema: `schemas/strand.qsql` declares eight tables and no views, so the probe adds exactly the seven listed. The Header is still read once, first, and alone; a missing `Strand` schema yields no entries, and the Header read already fails in that case. `Strand.Member` and `App.Member` are separate keys in `progress.tables`. No defect found.
- **The budget change (300 s → 360 s).** Checked that it follows the constant's own rule and that the numbers in the comment agree with each other (3.4x the worst harness sample, 2.4x the reporter's 150 s re-attach, about 2x the 178 s device join). Every reference to the old value was updated: the constant, its accepted-tradeoff `NOTE:` ("six minutes"), the backstop comment, `architecture.md` Known limits and `cadre-consistency.md`. `link-budget.ts` refers to the constant by name only. Accepted as implemented. The evidence is thin (two runs of one arm, one baseline run, `reattach-kept` not run), and the comment says so.
- **Cost of the extra reads.** About 8.6 s per added read on the slow arm, because the reads are serialized. The existing `NOTE:` on `strandFirstSyncComplete` already explains why the reads are not overlapped and when to revisit that. No new tripwire is needed.
- **Interactions.** Several integration scenarios set a 300 s vitest timeout and rely on the default budget (for example `blind-relay-phone-to-phone-e2e`). That matters only when a scenario fails: a strand that never becomes writable now shows up as a vitest timeout instead of `StrandAwaitingFirstSyncError`. With the old 300 s budget the two already finished at the same moment. No change made.
- **Docs.** Grepped `docs/`, package READMEs, `cadre-core/src` and `integration-tests/src` for wording that limits the gate to the Header and `App` tables. Nothing stale remains. The 1.15.0 figure "8 block reads from the table probes" is in a dated paragraph and stays as a record of that date.
- **Source hygiene.** Fixed one minor issue inline: the `buildStrandRuntime` comment in `strand-instance-manager.ts` had been reflowed with one-and-a-half-word lines in the middle of the paragraph. It is now reflowed properly; the wording is unchanged.
- **Tests.** The extended gate test checks which tables the gate covers and in what order, and it fails against the old code, so it is worth keeping. No test was cut. None was added, because no defect turned up that needed a reproduction.

Agreed: the fix probably belongs in the plugin's read path, which this repo cannot edit, and the ticket carries `repro: static` plus the steps that would confirm it. No other open ticket covers `strand-first-sync-gate.ts`.
- **Error handling, resource cleanup, type safety.** Not affected: the read guards, the logging and the gate's lifecycle are unchanged, and the new helpers are typed with no casts.
