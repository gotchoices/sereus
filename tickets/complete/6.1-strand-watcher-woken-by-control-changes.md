# Strand watcher woken by changes to Strand and JoinedStrand

## What landed

Implemented in `ticket(implement): strand-watcher-woken-by-control-changes`.

- `StrandWatcher` owns no timers. Every read is one run on a `TableChangeWatch`: the queryable's `watchChanges` (in `CadreNode`, `ControlDatabase.watchTables(['CadreControl.Strand', 'CadreControl.JoinedStrand'])`), or `scheduleRuns` (same single-flight schedule, no subscription) for a queryable without one. The first run is 100 ms after `start()`; then on a change, the watcher's own retries, and the backstop (`strandWatchInterval`, default `DEFAULT_STRAND_WATCH_BACKSTOP_MS` = 300000).
- Retries it arms itself after each run: a launch retry at the earliest backoff expiry later than the run's start (an expiry at or before it belongs to a strand skipped for another reason, and waking for it would spin), and a read retry after a failed or partial read on a ladder from `min(backstop, 5 s)` doubling to `min(backstop, 60 s)`. The launch backoff base is `min(backstop, 5 s)`.
- Changes no table event reports wake it directly: `JoinedStrandSession`'s `onLocalChange` callback (`remember`, `rememberForeign`, `leave`, `forgetAfterThisSession`) calls `StrandWatcher.refresh()`, and a learned sApp id calls `sAppIdLearned` for a provisionally admitted strand.
- Every shipped default that pinned 5000 now says 300000 (`entrypoint.sh`, `env.example`, `example.cadre.yaml`, the provider orchestrator), and docs and comments describe a backstop and runs instead of a poll.

## Review findings

**Read first:** the implement diff, then the current `strand-watcher.ts`, `table-change-watch.ts`, `JoinedStrandSession`, the `CadreNode` wiring (`createStrandQueryable`, `initializeJoinedStrandStore`, start/cleanup order), and every doc and config file the change touched plus a repo-wide grep for leftover "poll" / 5000 wording.

**Correctness, checked by reading:**
- Retries armed from inside a run survive it: `trigger` adds a wake while the run is in flight, and `settled()` only adds the backstop, so nothing clears it.
- The `since` rule in `scheduleLaunchRetry` holds: a strand whose backoff expires during a slow run gets `trigger(0)` after it; a stale entry for a suppressed or filter-rejected strand causes at most one extra run, then is never re-armed.
- No self-feeding loop through the session callback: the writes a watcher run makes (`forgetSuperseded`) do not call `onLocalChange`, and `syncWithParty`'s publish wakes one run through the table event, which finds nothing left to publish.
- The control database exists before `watchChanges` is called (start order), and `cleanup()` stops the watcher before `controlDatabase.close()`; the registry's `disposeAll` covers the rest.
- `sAppIdLearned` from inside `handleStrandAdded` (replica sApp id) marks a rerun on the in-flight watch, so the provisional admission resolves in the next run.
- Bare-harness specs with an injected clock (`discovered-strands-late-subscriber`) arm real timers of up to 5 s from the injected clock, the same assumption the old 5 s interval made.
