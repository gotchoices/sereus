# One shared handle-lifecycle contract, run against both the real and the fake orchestrator

## What this is

`HostProcessOrchestrator` starts a node as a child process and keeps a record of it, called a *handle*, keyed by a per-spawn id called `dockerId`. `FakeOrchestrator` is the hand-written stand-in the donated-node unit tests use instead; it starts no processes. Each used to have its own tests for the handle rules, so the two could come to disagree without any test failing.

## What was built

- **`packages/cadre-host/src/__tests__/orchestrator-handle-contract.ts`.** Exports `describeHandleContract(label, harness)`, which registers one `describe` block named `<label> handle contract` holding six cases written against a small harness interface. It is not a `.test.ts` file, so vitest does not collect it on its own.
- **`orchestrator.test.ts`** calls it with a harness over the real class; **`fake-orchestrator.test.ts`** calls it with a harness over the fake.
- No production code changed.

The six cases, each run twice (real and fake), with every message checked whole rather than by substring:

- `rejects a dockerId it never issued`
- `rejects a dockerId once its container has been removed`
- `replaces the first spawn's dockerId when the container re-spawns`
- `refuses to re-spawn a container whose previous child is still running` (added in review)
- `leaves another container's dockerId alone when one container re-spawns`
- `keeps the first spawn's dockerId when the re-spawn fails`

## How to use it

To add a rule both classes must obey, add one `it` to `describeHandleContract`. It must use only `createContainer`, `stopContainer`, `removeContainer`, `resolveDockerId` and the harness, and must stop a container's first child before re-spawning it (use the local `respawn` helper).

## Review findings

Reviewed the `ticket(implement): debt-host-process-orchestrator-untested` diff before the handoff notes, then read `host-process-orchestrator.ts`, both test files, the fake, and the donation service and supervisor callers.

### Checked, nothing to change

- **The contract does catch drift on the real class.** The implementer had not demonstrated this. I made six temporary edits to `host-process-orchestrator.ts`, one at a time, ran the real-class contract block after each, and restored the file (it is byte-identical to the committed version; `git status` does not list it). Each edit failed exactly the cases expected: rewording the not-found message (3 cases), dropping every handle on re-spawn instead of one container's (1), not restoring handles after a failed launch (1), not deleting the handle on remove (1), not dropping the old handle on re-spawn (1), and not refusing a re-spawn over a running child (1, the case added in this review).
- **Deleting the fake's `drops only the re-spawned container…` case** is sound: the contract's `leaves another container's dockerId alone…` covers it on both classes.
- **The fake's remaining own cases** overlap the contract in places, but each also asserts a recording array (`stopped`, `removed`, `reclaimedWorkdirs`) or a hook, which the contract cannot see. Kept.
- **The real file's `failed launch › keeps the prior handle addressable…` case** overlaps the contract's failed-re-spawn case but also asserts the node list and that the working directory is deleted. Kept.
- **Resource cleanup.** The real harness makes orchestrators through `makeOrchestrator`, so the file's existing `afterEach` removes every child the contract spawns. The full package run reported no leftover child processes.
- **Docs.** No file under `docs/` or the package's markdown names the fake, the contract, or these test files, so there was nothing to bring up to date.
- **Type safety.** The generic harness needs no casts on either side; `orch.getNode(containerId)!` in the real harness is only called after that container has been spawned.

### Found and fixed in this pass

- **The fake allowed a re-spawn the real class refuses, and seven tests relied on it.** The real class rejects `createContainer` for a container whose previous child is still running (`container <id> is still running`); the fake silently replaced the child. The implementer recorded this as a `NOTE:` and did not check the callers. Checking showed the one production caller (the supervisor) only re-spawns after the child reads as not running, but seven `DonationService.respawn` tests and two of the fake's own cases re-spawned over a running fake child — a sequence that cannot succeed on a real host. Fixed: the fake now refuses with the same message, the contract gained the case `refuses to re-spawn a container whose previous child is still running`, those nine tests first take the first child down with `orch.crash(...)`, and the `NOTE:` was removed because the difference no longer exists.
- **Stale comments.** The contract's `respawn` helper comment and the harness's `started` doc said the fake does not model the refusal and described `started` as "can be stopped"; both now describe the current behaviour ("reads as running", which the new case depends on).

### Tripwires (recorded at the code site, not filed)

- `failNextCreate` is broader on the fake (fails every later create) than on the real harness (fails one container). No contract case creates again afterwards; the constraint is stated in the harness interface's doc comment in `orchestrator-handle-contract.ts`.
- Three rules the two classes still disagree on stay outside the contract, each with an existing `NOTE:` in `fake-orchestrator.ts`: `getStats` / `getLogs` on an unknown id, the `reclaimWorkdir` return value for an already-deleted directory, and `removeContainer` on a still-running child. No donation code path observes any of them.
- The fake's refusal covers only a child "this process spawned". The real class has a second branch for a handle re-attached after a host restart (it probes the ports). The fake has no notion of a restart, so that branch stays tested only on the real class in `orchestrator.test.ts`.
