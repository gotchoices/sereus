# `network.announceAddrs`: upstream request filed, dead setting now honest

## What shipped

`NetworkConfig.announceAddrs` was settable in `cadre.yaml`, via `CADRE_ANNOUNCE_ADDRS`, and through
the Docker entrypoint, and was read by nobody — silently. It cannot be implemented inside this repo:
libp2p only takes announce addresses at construction (`addresses.announce` / `addresses.appendAnnounce`),
and `@optimystic/db-p2p`'s `NodeOptions` / `createLibp2pNodeBase` has no field for either, with no
public post-construction escape hatch.

Two things landed:

1. **Upstream request filed:** `../optimystic/tickets/fix/announce-addrs-option.md` asks for
   `announceAddrs?` / `appendAnnounceAddrs?` on `NodeOptions`, forwarded into the `addresses` object
   `createLibp2pNodeBase` assembles. Pure additive forwarding of stock `@libp2p/interface` options.
   **Still untracked in that repo** (its working tree has unrelated in-flight edits) — a human or
   that repo's own tess runner has to pick it up.

2. **The field stopped lying:** `CadreNode.start()` warns once, at boot, when `announceAddrs` is
   non-empty, and the operator-facing docs for the setting (core type doc, CLI config type, Docker
   `env.example`, `example.cadre.yaml`, `docs/architecture.md`) all say plainly that it is accepted
   but not yet applied, and point at `relayAddrs` as today's answer for reachability behind NAT.
   Warns rather than throws — an operator who set this in a Docker env file already has a running
   node, and turning silent-drop into a boot failure would be worse.

Follow-up wiring (forwarding the field once the dependency carries it, then deleting the warning) is
deliberately not filed until this repo's `@optimystic/db-p2p` range actually moves — see
`scripts/check-dep-ranges.mjs` and the `test:dep-ranges` gate.

## Review findings

**Checked:** the implement diff read cold before the handoff; the warning condition and its placement
in `start()`; `console.warn` as the mechanism for a library; the new spec's assertions; every doc
surface that mentions the setting (`example.cadre.yaml`, `docs/architecture.md`, `docs/STATUS.md`,
Docker `env.example` / `docker-compose.yml` / `entrypoint.sh`, both `cadre-cli` config interfaces);
whether any other package silently depends on the setting working (`cadre-host`'s NAT path,
`cadre-provider`, `ops/`); the upstream ticket's factual claims; `yarn lint`; `cadre-core` and
`cadre-cli` test suites.

**Fixed in this pass (minor):**

- `packages/cadre-cli/docker/env.example` still described `CADRE_ANNOUNCE_ADDRS` as the thing to
  "use if behind NAT or proxy" — the single most operator-facing doc for this setting, and the one
  surface the implement pass missed. Now carries the not-yet-applied note and points at
  `CADRE_RELAY_ADDRS`.
- `packages/cadre-cli/src/config/types.ts` — `announceAddrs` was undocumented on both the input
  (`CadreConfig.network`) and resolved config interfaces, so an editor reading the CLI's own types
  saw a field that looks live. Both now carry the caveat.
- Stale ticket-stage paths in shipped source: `types.ts` pointed at
  `implement/14.1-cadre-announce-addrs-upstream` and `cadre-node-control-node-options.spec.ts` at
  `implement/cadre-announce-addrs-upstream` — both dead the moment the ticket advanced. Replaced with
  a reference to the upstream `announce-addrs-option` request, which is where the unblocking actually
  happens.
- `cadre-node-announce-addrs-warning.spec.ts` asserted `expect(warn).not.toHaveBeenCalled()` in the
  two negative cases, i.e. that *nothing at all* warns during a full node boot — any unrelated
  `console.warn` from libp2p or a dependency would have failed it for the wrong reason. Rewritten to
  collect and assert on warnings matching `network.announceAddrs` only, with the three cases sharing
  one start/stop helper instead of repeating the spy/try/finally block.

**Verified, no change needed:** the warning cannot double-fire (single `if` after the `_running`
guard, before the `try`, on no retry path); a `stop()` + `start()` re-warns, which is correct since
each start re-reads current config. The upstream ticket's quoted claims still hold at review time —
`../optimystic/packages/db-p2p/src/libp2p-node-base.ts` `NodeOptions` has no announce field and its
`Libp2pInit` sets `addresses: { listen: listenAddrs }` and nothing else. `{@link relayAddrs}` and
`inviteAddressResolver` both exist on `NetworkConfig`; the names did not drift. `cadre-host` maps an
external port and builds external multiaddrs (`nat/address-resolver.ts`) only for invite payloads —
it never claims the node advertises them, so no doc there overstates the gap. `ops/docker/libp2p-infra`
passes `ANNOUNCE_ADDRS` straight into its own libp2p `addresses.announce` and is unaffected.
`docs/STATUS.md`'s "listen/announce address handling" box is unchecked, which is still accurate.

**Major findings: none.** The only substantive gap left is the upstream change itself, which is not
work this repo can do and is already filed in `../optimystic` — no sereus ticket for it, since a
sereus ticket could only wait.

**Tripwire recorded:** this is the only direct `console.*` call in `cadre-core`'s `src/` (everything
else uses `debug`, opt-in via `DEBUG=`). Fine for one boot-time operator warning; if a second such
warning ever wants to exist, both should move to a `CadreNodeEvents` entry the embedder surfaces
rather than growing a console surface inside a library. Parked as a `NOTE:` comment at the warning
site in `packages/cadre-core/src/cadre-node.ts`.

**Test coverage:** three cases (set → warns once, unset → silent, `[]` → silent), each a real local
`start()`/`stop()` cycle with no mocking. Nothing tests the setting *working*, because nothing applies
it — that coverage lands with the upstream change.
