# Web reference app: "Devices and nodes" and acting on removal

The browser counterpart of `reference-app-rn-devices-and-nodes` (the section) and of `phone-kit-forgets-a-cadre-that-removed-it` (acting on the tab's own removal), since the web app has no kit. Documented in `packages/reference-app-web/README.md` → "Devices and nodes" and "When this tab is removed".

## What was built

**Devices and nodes card** (`src/Machines.svelte`, state and actions in `src/lib/machines.svelte.ts`, after Add a device or app on the Cadre page):

- One row per `CadreNode.listMachines` entry: kind from the profile ("App", "Always-on node", "Machine"), "(this tab)", Owner, Last seen, Key (8-character fingerprint), "Not trusted here", "Owner key, no machine joined". Then "Invited, not joined yet" rows for live invitations targeted at a peer that is not a member, with Withdraw (browser `confirm()`, as Add a device does).
- On an owner tab, Remove on every row but the tab's own (which shows "To remove this tab, use another owner device"). Remove reads `planMachineRemoval` and opens an inline confirmation in the card: key, effects, one Keep checkbox per dependent (on by default; a device added as an owner is one checkbox), the own-dependency line, what removal does not do. A refused plan shows the reason and Close; a machine already gone shows "Already removed". Plan reads and removals run one at a time (`busy`), and Remove buttons are disabled while a confirmation is open.
- Read when the node reaches `running` with its owner step settled (the same effect as Add a device), after a removal or withdrawal, after Add a device mints an invitation, and on Refresh. A read that finishes after the node changed is dropped.
- Words and helpers (`machineKind`, `lastSeenText`, `dependentsOf`, `revouchFor`, `removalEffects`, …) are hand-kept copies of the phone's `machines.ts` / `machines-section.tsx`, under a `NOTE:` naming the revisit condition (a third surface → move into cadre-core).
- `cadre-format.ts` gained `ownerFingerprint` (matches the phone's) and the shared `errorMessage` (Add a device's private copy removed).
- **Add a device or app** now lists open invitations only, as the phone does after its ticket; one made for a single app shows under Devices and nodes.

**Acting on the tab's removal:**

- `store.svelte.ts`: subscribes to `cadre:removed`. New statuses `removing` and `removed`, and `state.removed: { partyId, signerKey, formerPartyId? }`, cleared when a start next reaches `running`.
- **No transition queue existed in the store**, so one was added: `inTransition` (a counter) wraps `start`, `stop`, `joinCadre`, `retryStrandMove`, `dissolveFormerParty` and the removal. A report is held in `removalReported` and acted on (`actOnReportedRemoval`) only when no transition runs and status is `running`, and only if the running party is the removed one. It also reads `getCadreNode().removedFromCadre()` at that point, which covers a report raised before the store subscribed (the ticket's "check `removedFromCadre()` once after start").
- `leaveRemovedParty` (store) lets go of the node, forgets the party cards (`resetAddDeviceCard` + new `resetMachinesCard` via `forgetPartyCards`), sets `removing`, then `web-join.ts` → `forgetRemovedParty`: stop the node; rewrite the start record **before** deleting (kit order, same reason); `finishMarkedRemoval` for any older marker, then `removeParty` (marked, no check); close the stores. Then `removed`.
- `party-start.ts`: `startAfterRemoval` (founded start of `formerPartyId`, or none) and `deletePartyStart`. `web-dissolve.ts`: exported `finishMarkedRemoval`; the `removeParty` and `finishRemovalAtStart` docs widened as the ticket asked.
- **Cadre page removed card** (`Cadre.svelte`): "This tab was removed from cadre ‹id› by an owner (‹fingerprint›). Its copy of that cadre has been deleted from this browser.", with **Go back to your own cadre** (when `formerPartyId`) or **Start a new cadre**, both calling `start()`, and a hint that joining another cadre starts from the tab's own.
- `App.svelte`: an effect clears the join card's flow once status is `removed`, whichever page is open. The store cannot import `join-cadre.svelte.ts` without an import cycle.
- `Home.svelte`: Restart disabled during `removing`; status colours for the new states.
- Docs: `docs/architecture.md` "Removed from A." gained a sentence on the browser app, and the package table row mentions the card. `docs/cadre-host.md` "A host lost for good" links the web card too. The duplication arm was appended to `debt-web-app-repeats-the-phone-kit-join-sequence`.

## Departures from the ticket (judgement calls for the reviewer)

- **"Auto-start off" is not representable.** The web start record has no `autoStart` (`party-start.ts`: a tab always starts on load). The rewritten record is a founded start of `formerPartyId`, so a reload after a removal starts the tab's own cadre, which is the same thing Go back does. Without a former party the record is deleted, and the next start founds a fresh party. Adding an auto-start flag would leave a reloaded tab stopped with no card explaining why, since the card is screen state.
- **No "Join a cadre" from `removed`.** A web join switches a *running* node (`joinCadre` requires `running`; the request needs the node's peer id), so the card offers Go back or Start a new cadre and says to join from there. The join card itself shows "The node is not running" meanwhile. There is no OK button either: while nothing runs, the card is the only explanation.
- **A report for a party the tab has since left is dropped** (`NOTE:` at `actOnReportedRemoval`). The kit deletes that party's storage instead. In the web this only happens in the window between a join's first awaits and its stop of the old node. Deleting there would race the join card's own dissolve of the founded party. A left joined party's storage stays in the browser anyway, by design.
- **Removal during `joining`**: ordered by `inTransition`, checked by reading the code. If the join fails, the tab goes back to the removed party, and the deferred report is acted on after that rollback start. If the join is admitted elsewhere, the report is dropped as above.

## Known gaps

- **No unit test.** `test/` has no store or `web-join` spec that drives transitions with a real node, so per the ticket the removal case was skipped rather than mocking the app's own modules. Playwright was not extended either: a removal needs a second owner machine (stated in the README test section).
- **Removal failure** (start-record read or write throws): status `error`, storage left. The next start runs the removed party, and its new node does not report the removal (`NOTE:` at `leaveRemovedParty`; mirrors the phone review's tripwire).
- **In-flight non-transition work** (an invitation mint, a machine removal on this tab, formation, a message send) fails with node-stopped errors when a removal stops the node. Same as the phone.
- **Admitted then immediately removed**: the join card's automatic dissolve then throws "The node is not running.", which is logged and pushed to Diagnostics before the App effect clears the flow. This is a contrived case; only the noise remains.
- **Two tabs on one party** are unguarded (as before). The README's "Out of scope" now says what a removal does there. The card says the data was deleted even when `deleteStore` was blocked by the other tab; that case is only logged.
- **Observed in a probe run:** a solo founded tab lists *itself* as "Machine (this tab)" / "Owner key, no machine joined", because a solo founder has no `CadrePeer` row of its own (cadre-core `listMachines` data, not this app's logic). The phone's code shows the same data the same way. The wording reads oddly for the tab's own row; the reviewer may want a self-specific line. It was left as is to keep parity with the phone.

## Use cases to exercise by hand (needs a second owner machine, e.g. the phone app or a cadre-cli node)

- An owner tab in a two-machine cadre: both rows listed; Remove the other one; Keep checkboxes appear when its key vouched dependents; the list refreshes; "Already removed" when another owner got there first.
- A member tab: list only, with the member line and no buttons.
- Paste request → Add on an owner tab: the targeted invitation appears under Devices and nodes as "Invited, not joined yet", not under Outstanding invitations; Withdraw there.
- The tab removed by another owner while open: Home reads `removing` then `removed`; the Cadre card shows the fingerprint; Go back starts the founded party (or Start a new cadre founds one); a reload afterwards starts that same party; the removed party's `sereus-strand-control-…` database and `<record>.<party>` kv keys are gone.

## Review findings

Reviewed the diff of `ticket(implement): reference-app-web-devices-and-nodes` first, then the handoff. Checked against the phone app's `machines.ts` / `machines-section.tsx`, the kit's `watchRemoval` / `forgetRemovedParty` / `inTurn`, and cadre-core's `noteOwnRemoval` and `describeMachines`.

**Fixed in this pass**

- **The store stopped the node from inside the node's own `cadre:removed` emit.** `onRemoved` called `actOnReportedRemoval` synchronously, so `leaveRemovedParty` reached `stopCadre` → `node.stop()` while cadre-core's membership refresh was still on the stack (`noteOwnRemoval` → emit). The kit never does this: its `inTurn` runs the removal on a promise continuation. `onRemoved` now queues the check with `queueMicrotask`, re-testing `transitions === 0` when it runs (`store.svelte.ts` → `onRemoved`).
- **The tab's own row read "Owner key, no machine joined".** cadre-core lists a founder that has not published its `CadrePeer` row by its owner key alone (`describeMachines`), so a solo tab's own row said no machine had joined, which is false for the machine reading it. That fact now reads "Owner" when the row is `isSelf`, in both the web card and the phone's `machines-section.tsx` to keep the two apps' wording the same. Updated `packages/reference-app-web/README.md` → Devices and nodes and `docs/reference-app-rn.md` → Devices and Nodes.

**Checked, no change**

- Transition ordering (`inTransition`): every entry point that stops, starts or switches the node is wrapped, and the status guards keep them from overlapping. Traced removal during `joining` (rollback, then acted on), during a dissolve, during stop (held until the next start of that party), and a report raised before the store subscribed (`removedFromCadre()` read when a transition ends). The dropped-report case for a party a join already left carries a `NOTE:`.
- `forgetRemovedParty`: start record rewritten before the marker, older marker finished first, stores closed in `finally`, delete failures logged and not thrown, the same order as the kit. `startAfterRemoval` and `deletePartyStart` are correct. Not having an auto-start flag is a reasonable call: a reload starts the same party Go back starts.
- `machines.svelte.ts`: stale-node guards on reads, `busy` serialising plan reads and removals, confirm buttons disabled while a confirmation is open. The helpers are exact copies of the phone's `machines.ts`. The copy is a deliberate tradeoff under a `NOTE:` that names its revisit condition (a third surface lists machines), so no ticket was filed.
- Add a device lists open invitations only; targeted ones show under Devices and nodes. Shared `errorMessage` / `ownerFingerprint` moved to `cadre-format.ts`; no import cycle (`machines` imports only a type from `add-device`).
- Docs: `docs/architecture.md`, `docs/cadre-host.md`, the web README sections and the backlog debt ticket's new section match the code.
- Tests: there is still no unit test. The store and `web-join` have no spec harness that runs a real node, and testing them by mocking the app's own modules would test at the wrong layer. The helpers' branching logic is covered on the phone side (`test/machines.spec.ts`). No tests were cut, because none were added.

**Not changed, noted**

- The Messages page's module state and Home's formation state are not reset when the node moves to another party, whether by a join or by a removal followed by Go back. This was already true before this ticket and is outside its scope; recorded here only.
- The implementer's known gaps (removal failure leaves `error`, in-flight non-transition work fails on stop, two tabs on one party, noise when a tab is admitted and then removed straight away) stand as written. Each is either a `NOTE:` at its code site or documented in the README.
