# Tests for the web reference app's node-local durable stores

`packages/reference-app-web` had no unit tests at all — only Playwright e2e. It
now has a vitest suite (`yarn workspace @serfab/reference-app-web test`), and its
first spec covers the browser's durable-storage seam:

- **`kvSlot`** (`src/lib/node-local-slots.ts`) — the `DurableSlot` the app
  supplies over one key of the control database's `kv` IndexedDB object store,
  tested against a map-backed fake `OptimysticWebDBHandle` (no real IndexedDB
  needed): save→load round trip, statelessness, key independence, a non-string
  value reported as absent, a never-written key, and a failing read *and* a
  failing write both rejecting rather than resolving.
- **The two node-local stores over a real `kvSlot`** —
  `PersistentTrustedOwnerStore` (the trust anchor) and
  `PersistentBootstrapPeerStore` (the cold-start dial-target retry list): each
  round-trips through a fresh `open()`, both coexist in one database without
  clobbering each other, a non-text `kv` value cold-starts empty, and a failing
  IndexedDB read makes `open()` **reject** rather than look like a cold start (the
  property `startCadre` depends on — a cold start there would let the next
  snapshot write destroy an intact record).

The store *policy* itself (corrupt JSON, foreign party id, unknown envelope,
discard-all vs drop-entry, synchronous visibility, failed-persist recovery) is
covered once, in `packages/cadre-core/test/node-local-snapshot.spec.ts`, and is
deliberately not re-asserted per platform — see review findings.

Supporting wiring, all in `packages/reference-app-web`: `vitest.config.ts`
(single node environment, `test/**/*.spec.ts`), `test/global-setup.ts` (stale-build
guard), the `test` / `dev:test` scripts, the `vitest` devDependency, and
`test/**/*.ts` + `vitest.config.ts` added to `tsconfig.json`'s `include`.

## Explicitly not done: Playwright e2e case

The plan allowed an optional Playwright round-trip in
`e2e/solo/reload-persistence.spec.ts`. Skipped, and the reasoning still holds on
review: neither record has any UI surface (no Svelte component reads them, no
`data-testid` hooks exist), so an e2e case would mean adding test-only UI hooks
or reconstructing `cadre-web.ts`'s control-database name and party-id logic by
hand inside `page.evaluate()`. If wanted later, start from `cadre-web.ts`'s
control-database wiring (grep `TRUSTED_OWNERS_KV_KEY`, `BOOTSTRAP_PEERS_KV_KEY`).

## Still uncovered

`startCadre`'s own wiring of these stores into a running `CadreNode` — the layer
*above* the slot and stores — remains untested end to end. Recorded in
`docs/STATUS.md` under Testing / CI rather than as a ticket, since the e2e
reasoning above is what would have to change first.

### Fixed in this pass (minor)

- **The suite ran a stale `@serfab/cadre-core` build, and nothing said so.** The
  spec imports cadre-core for its real behaviour, and cadre-core resolves through
  a `node_modules` symlink whose manifest points at `dist` — exactly the
  false-green the repo's stale-build guard (`test-harness/build-freshness.ts`)
  exists to catch, and which `cadre-core` and `integration-tests` already wire in.
  The web suite had no guard. Added `test/global-setup.ts` + the `globalSetup`
  entry in `vitest.config.ts`. It failed on its very first run: cadre-core's
  `dist` predated its `src`, so the implement stage's reported green had been
  measured against an older build. Rebuilt cadre-core and re-ran; 12/12 pass.
- **The new test file was invisible to `tsc`.** `tsconfig.json`'s `include` was
  `src/**` only, so neither `test/` nor `vitest.config.ts` was type-checked by
  any script — the handoff noted this and left it. Both are now in `include`
  (matching `reference-app-rn`, which type-checks its tests); `typecheck` stays
  clean. A removed vitest option now fails typecheck instead of degrading
  silently, the same reason `integration-tests` did this.
- **Five of the eleven original tests duplicated cadre-core's own suite.** The
  foreign-party-id cases (×2), the corrupt-JSON cases (×2) and the
  junk-entry-dropped case all assert `NodeLocalSnapshot` load *policy*, already
  covered in `packages/cadre-core/test/node-local-snapshot.spec.ts` against its
  own fake slot; routing the same policy through a different slot proves nothing
  new and would have to be changed in two places. Removed, and replaced with the
  properties web actually owns and nothing covered: a failing `kvSlot` write, key
  independence, both records coexisting in one database, a non-text `kv` value
  cold-starting the store, and — the load-bearing one — a failing IndexedDB read
  making `open()` reject. Net 11 → 12 tests, with the composition seam now
  genuinely covered rather than the policy re-covered.
- **The handoff's claim that the trusted-owner store's whole-record-discard
  policy was "proven separately by the earlier corrupt-JSON case" was wrong** —
  unparsable JSON cold-starts empty under *both* policies, so that case cannot
  distinguish them. The distinction is `discard-all` vs `drop-entry` on one
  *unusable entry*, and it is covered in cadre-core's suite, not here. Corrected
  by removing the misleading cases outright (above) and stating the ownership
  boundary in the spec's module header.
- **Docs were stale on two counts.** `docs/STATUS.md` listed
  `reference-app-web` as shippable-source-only for type-check coverage (no longer
  true) and named only two stale-build-guard consumers (now three). Both updated,
  plus a Testing / CI bullet recording that the package has a unit suite at all
  and what it does not yet reach.

### Filed as a ticket (major)

- `tickets/backlog/debt-stale-build-guard-hoisting-limited-packages.md` — the
  stale-build guard resolves sibling-checkout packages (`../optimystic`,
  `../quereus`) only in the **repo root's** `node_modules`, but
  `reference-app-web` sets `installConfig.hoistingLimits: "workspaces"` and keeps
  its own. So its `@optimystic/*` / `@quereus/*` copies cannot be guarded (one,
  `db-p2p-storage-web`, is absent at the root entirely and would report a
  permanent "not installed"), and it is the only guarded package without a
  `build-targets.spec.ts`, because that spec's manifest cross-check would demand
  exactly those unresolvable entries. Its guard list is therefore one entry
  (`@serfab/cadre-core`, found by the workspace scan). Fixing it means changing
  shared harness code — beyond this ticket. The ticket also folds in that this
  package declares `"@serfab/cadre-core": "*"` where every other uses
  `workspace:^`/`workspace:*`, which exempts it from two checks that key off the
  `workspace:` prefix.
