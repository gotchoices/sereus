# Dial preference without "owner machines"

## What landed

Implemented in `ticket(implement): dial-preference-without-owner-machines`.

- `SeedPeer` carries `preferred: boolean` (a dial-first hint) in place of `isOwner` / `publicKey`. Nothing in a seed claims anyone is an owner; trust still rests only on `signerKey` against the receiver's node-local anchor.
- `projectSeedPeers(rows, minterPeerId)` marks a peer preferred when it is the minter (the seed minter, or the member answering a cadre invitation redemption) or its `CadrePeer.Profile` is `'storage'`. It reads no `OwnerKey` row.
- Seed application dials preferred peers (`SeedBootstrapService.dialPreferredPeers`), and `CadreNode` retains them as cold-start dial targets. `ApplySeedResult` reports `preferredDialsAttempted` / `preferredDialsFailed`.
- The control-cohort backbone (always dialed) is siblings with `profile === 'storage'`; the rest fill up to `targetDegree` in peer id order (`selectControlCohortDials(siblings, targetDegree)`, `cappedNonBackbone`). `CohortPeerRow` gained an optional `profile`; `CadreNode.listMembers()` is declared as `CohortPeerRow[]`.
- `cadre enroll add` reports `seedAddrs` (also in `--json`), the addresses of the seed's preferred peers other than the new machine's own.
- Docs (`architecture.md`, `reference-app-rn.md`, cadre-cli README) and comments describe the new rule.

## Review findings

**Read first:** the full implement diff (core source, cli, docs, tests, integration scenarios, fake node stub), then the handoff.

**Correctness — one minor defect, fixed.** `buildEnrollAddReport` listed every preferred peer's addresses, including the machine being added. `authorizePeer` seats a new machine with `profile: null`, so on a first run it is not preferred; but re-running `enroll add` for a machine that has since self-published `storage` (the documented way to pick up changed addresses) made it preferred in its own seed. Its own addresses then showed as "Addresses in this seed" and suppressed the "neither machine can dial the other" warning even when the owner had no address. Fixed in `enroll-add.ts` by excluding the target peer id; the existing spec's new-machine fixture is now `preferred: true`, so the one test covers the exclusion (it fails without the fix). The `seedAddrs` doc comment and the `enroll add` line in `architecture.md` say so.
