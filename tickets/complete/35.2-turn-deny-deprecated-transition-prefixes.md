## What shipped

`ops/docker/coturn/turnserver.conf`, IPv6 `denied-peer-ip` block — two entries
added after the NAT64 lines:

```
denied-peer-ip=2002::-2002:ffff:ffff:ffff:ffff:ffff:ffff:ffff
denied-peer-ip=2001::-2001:0:ffff:ffff:ffff:ffff:ffff:ffff
```

covering 6to4 (`2002::/16`, RFC 3056) and Teredo (`2001:0000::/32`, RFC 4380) —
the two remaining ways to encode an IPv4 address inside an IPv6 address that the
deny-list did not already cover.

Comments in the same file were rewritten (implement stage did the IPv6 block
comment; review stage did the section header and the tradeoff/gap notes — see
findings below).

No behaviour change unless TURN relaying is enabled (`TURN_ENABLED=true`); the
deny-list only governs relayed peers, and STUN never relays.

### Fixed in this pass (minor)

- **The overclaiming comment the ticket asked to fix was never touched.** The
  ticket flagged the phrase "every non-public IPv6 range". That phrase does not
  live in the IPv6 block comment the implementer rewrote (lines 67-74) — it lives
  in the `--- Abuse / SSRF controls ---` section header above it, as "deny
  multicast, loopback, and every non-public IPv4/IPv6 range, including IPv4-mapped
  and NAT64 prefixes". So the file still claimed total coverage *and* still listed
  only two of the four IPv6 transition mechanisms. Rewrote that header to say it is
  an enumerated deny-list rather than a proof of coverage, and to name the one case
  that is genuinely not enumerable: a NAT64 deployment using a network-specific
  prefix (RFC 6052) instead of the well-known `64:ff9b::/96`.
- **The connectivity tradeoff was undocumented.** Denying `2002::/16` and
  `2001:0000::/32` wholesale also refuses relaying to a peer whose address is a
  *legitimate* 6to4 or Teredo address encoding a public IPv4. That is the right
  call (both mechanisms are deprecated) but a future reader debugging "why won't
  this peer relay" needs to see it stated. Added one sentence to the IPv6 block
  comment.

### Verified, no change needed

- **Range boundaries, re-derived independently of the handoff's arithmetic.**
  `2002::` → `2002:ffff:ffff:ffff:ffff:ffff:ffff:ffff` is exactly `2002::/16`
  (16 fixed bits, 112 varying). `2001::` → `2001:0:ffff:ffff:ffff:ffff:ffff:ffff`
  expands to `2001:0000:ffff:…:ffff`, exactly `2001:0000::/32` (32 fixed bits,
  96 varying), and stops well below `2001:db8::/32` and the rest of allocated
  `2001::` space. Both correct.
- **Placement.** The two entries sit between the NAT64 and unique-local lines.
  coturn keeps IPv4 and IPv6 deny-lists as unordered range sets and tests
  membership, so file order is presentation only — grouping the v4-in-v6
  encodings together is the readable choice.
- **Handoff's claim that no other doc needed updating.** Re-ran the search
  without the file-type filter the implementer used, across `docs/`, `ops/`, and
  `packages/`: no file outside `turnserver.conf` describes the deny coverage.
  `ops/docker/coturn/README.md` documents *how to validate* the config, not what
  it contains, so it stayed correct as written. Confirmed.
- **Render output.** Re-ran the README's render-only recipe after the comment
  edits: config renders clean, both new lines present and correctly positioned,
  exit 0, and the only surviving `${...}` in the output is the literal one inside
  the template's own header prose (line 4, describing the substitution mechanism).

### Recorded as a tripwire, not a ticket

- The deprecated IPv4-compatible form (`::<v4>`, i.e. `::/96` — RFC 4291 §2.5.5.1)
  is the one v4-in-v6 encoding still not enumerated. No current host stack
  translates it to an IPv4 destination, so there is no path to a private service
  today — it only becomes real if one ever does. Parked as a `NOTE:` comment at
  the exact site (the IPv6 deny block), naming the one line to add if that
  changes.

### Known gap carried forward

- **The Docker "Config parse check" (README step 2) was not run in either the
  implement or the review pass** — there is no `docker` and no `turnserver`
  binary on this machine (`command -v` for both returns nothing). So no real
  coturn binary has confirmed it accepts the two new range strings; only that the
  config renders. Residual risk is low, because both new lines use the identical
  `start-end` full-form syntax as the `64:ff9b::…` lines that shipped and were
  parse-checked in the prior ticket — but coturn silently ignores a malformed
  range in some versions rather than erroring, so "renders fine" is not "parses
  fine". **Run README → "Config parse check" step 2 before enabling TURN in any
  deployment.** The new ticket above would remove this manual step.
