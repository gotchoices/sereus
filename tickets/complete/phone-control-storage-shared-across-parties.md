# Per-party storage scope for the control database

## What shipped

`CadreNodeConfig.storage.provider` is a factory cadre-core calls once per **scope**. The control database's scope used to be the literal string `'control'`, with no party id in it, so every party on one device shared one control database — its strands, owner keys, peers, invitations and revocations all in one place, read by whichever party's node started. That was the defect observed on a Galaxy Note 9: a node connected as one party read 10 `Strand` rows, some founded under a different party id.

The control scope key is now `controlStorageScope(partyId)` — the literal `control-` followed by the base64url encoding of the party id's UTF-8 bytes. New module `packages/cadre-core/src/storage-scope.ts` holds it and `isControlStorageScope`, both exported from `index.ts`; `resolveControlStorage()` passes that key to the provider and uses it as the cache label too.

The encoding is load-bearing, not cosmetic. A party id is arbitrary text (nothing in cadre-core validates it; the React Native app lets a user type one into Settings) and scope keys reach real namespaces unescaped — cadre-cli builds `${config.path}/${scope}`, React Native a LevelDB filename, the browser an IndexedDB database name. Base64url keeps every key inside `[A-Za-z0-9._-]`. It is the same encoding the React Native app's own `secureStoreKeySegment` already applies to a party id, for the same reason.

The web app took the one real logic change: its `kv` records (identity, party id, trust anchor, bootstrap peers, enrolled-machine count) live in the IndexedDB database the control blocks used to share, and the party id is read *out* of that database, so the database cannot be named after the party. `startCadre` now opens the node-local database first, reads the party id, then opens the party-scoped control block store before `node.start()`. The old key `'control'` survives under the name `NODE_LOCAL_STORE_KEY`, re-documented as the historical name of the node-local database rather than a cadre-core scope key. An existing tab keeps its identity, party id and anchor, and comes up with an empty control block store; the old unscoped blocks are left in place, unread and undeleted, because nothing recorded which party wrote them.

React Native and NativeScript needed no code change — `sereus-${scope}` already produces `sereus-control-<encoded party>`. The CLI needed a parameter rename only; two config files naming two parties over one `storage.path` were sharing a `control` directory before and now get `control-<encoded party id>` each. `cadre-host` was already isolated (one workdir and one party per managed node, and it builds no provider of its own — it spawns `cadre-cli`).

## Review findings

**Checked.** The implement-stage diff read cold before the handoff summary, every file it touched plus the ones it should have: the two provider call sites (`resolveControlStorage`, `resolveStrandStorage`), the strand launch paths that feed the second one, all five embedders, the integration harness and its scenarios, and every doc and README the diff edited. `yarn lint`, `yarn typecheck`, `yarn build`, `yarn workspace @serfab/reference-app-web check:svelte`, and the cadre-core (2125 passed / 1 skipped), cadre-cli (232), reference-app-web (66), reference-app-rn (209), reference-app-ns (103) and integration block-store-probe / control-offline-read-after-restart (25) suites — all green before and after the fixes below.

**Major — one ticket filed.** `tickets/backlog/bug-strand-scope-key-charset-unenforced`. This diff wrote the "every scope key stays within `[A-Za-z0-9._-]`, use it verbatim" charset rule into the public contract (`types.ts`, `docs/architecture.md`, the cadre-core README) and enforced it for the control key by encoding. The strand half of that rule is not enforced anywhere. A strand's key is `strandRow.Id`, and a strand row replicated into the control database by another node in the party carries that node's id verbatim — the strand watcher launches it (`cadre-node.ts` ~3919 → `launchStrand` → `startStrand`) and `resolveStrandStorage` hands the id to the embedder's provider with nothing in between looking at its shape. An id of `../../something` names a directory outside cadre-cli's storage path; one beginning `control-` additionally misleads `isControlStorageScope`. The hole predates this ticket — it is as old as the strand provider — but documenting the guarantee as absolute is what makes it worth closing rather than leaving implicit. Filed at the invariant rung, not the instance: one check at `resolveStrandStorage` covers every embedder at once, so the ticket asks for that seam rather than for escaping in five providers. `repro: static` — read from the code, not observed; the ticket names what would confirm it. The three doc sites now carry a one-clause caveat pointing at it, so the contract does not overclaim in the meantime.

**Minor — five fixed in this pass.**

- *A false premise in the load-bearing comments.* `storage-scope.ts` argued its prefix test is safe because "strand ids are uuids"; the same claim appeared in the `docs/architecture.md` scope table and the new spec. Strand ids in this codebase are never uuids — they are `strand-<digits>-<base36>` (`strand-formation-manager.ts:602`, `strand-solicitation.ts:378`) or `strand-<hex>` (`control-formation-recorder.ts:292`). The conclusion survives (both shapes are `strand-`-prefixed), but a reader checking the reasoning finds it wrong. Corrected at all three sites, and `isControlStorageScope`'s doc now says plainly that it is not a security boundary against a replicated id.
- *The decode snippet was wrong for the ids the tests deliberately cover.* `atob(...)` yields one character per byte, so the documented one-liner for reading a party id back off a device returns mojibake for any non-ASCII party id — and the spec exercises `партия-🗝`. Both copies (the `controlStorageScope` doc comment and `docs/architecture.md`) now wrap it in a `TextDecoder` and say why that step is not optional.
- *A stale key reference in the web app.* `strand-storage.ts`'s `openStores` doc still said the provider is hit "before `node.start()` for `'control'`", which is exactly the confusion the rename was meant to end — `'control'` is now the node-local database, opened for `cadre-web.ts` to read rather than for cadre-core to ask for. Reworded.
- *A diagnostics regression the split introduced.* `collectStorage` counted both databases inside one `try` gated on the control handle: a failure counting node-local `kv` discarded the block counts too, and the window where the node-local database is open but the party-scoped one is not (before the party id is read) reported no counts at all. Extracted a small `countInto` helper so each database is counted independently and either may be absent.
- *README caveat.* The cadre-core README's charset paragraph carries the same one-clause pointer to the filed ticket as the other two doc sites.

**Considered and not changed.** The RN/NS "orphaned `sereus-control` database" notes and the web app's equivalent are the right call and are already stated as such at each site — the rows have no recorded party, so adopting them into any party's store would recreate the defect, and deleting a user's blocks on a library upgrade is the worse failure. The harness's `control()` accessor deviating from the ticket's `capture.provider(controlStorageScope(partyId))` is a clear improvement, not a deviation to undo: `provider(...)` mints on demand, so a mistyped key would hand back a fresh empty store and every coverage assertion downstream would pass vacuously. Its two new unit tests cover both halves. The base64url choice matches `secureStoreKeySegment`, already in the tree for the same reason, so there is no second convention to reconcile.

**Tripwires — one, and it is the implementer's, left as filed.** `block-store-probe.ts`'s `controlOrNull` returns the first control-scoped store it finds, which is unambiguous only because one capture belongs to one node and one node serves one party; the `NOTE:` at the site says to make it refuse a second control scope if a scenario ever drives two party ids through one capture. Correct disposition — conditional, not a latent defect. No new tripwires from this pass: the concerns found were either wrong statements (fixed) or the unenforced charset rule, which is a real defect on a live path and so got a ticket rather than a comment.

**Pre-existing failure — verified, not re-reported.** The implementer's claim checks out: `strand-membership-closed-strand-e2e.integration.ts` → "a joining node runs the join against its OWN database and both nodes converge" is listed in `tickets/.pre-existing-known.md` (line 640) against `strand-unique-index-sync-stale-revision`, which is present in `tickets/blocked/`, recorded as intermittent. No `.pre-existing-error.md` was written, correctly, and none exists now.

## Gaps this leaves, stated honestly

- **No two-party device scenario end to end.** The regression guard is a pure unit test at `buildControlNodeOptions` — the seam where the bug lived — and it proves two parties over one memoizing provider get two keys and two stores, that one party twice gets the same store (so a restart still reaches its own data), and that the key stays path-safe and round-trips for six hostile party ids. It does not start two nodes for two parties against one file-backed backend and prove the rows stay apart. That would need a new integration scenario and was not written.
- **The web change was never run in a browser.** Typecheck, `check:svelte` and the unit suite cover it; `startCadre`'s two-phase open has no unit coverage because the web tests do not construct a `CadreNode`. Loading the app and confirming a tab comes up with its previous identity and an empty control store is still the obvious manual check.
- **`collectStorage` remains untested,** including the `countInto` helper added in this pass — the web unit tests cover the stores and formatting helpers, not this function. The same gap the implementer flagged, one small function larger.
- **The single-instance provider form** still shares one store across every scope and every party by construction. The contract now says so in three places; `backlog/debt-shared-store-provider-never-exercised-end-to-end` covers exercising it.
- **No migration path, deliberately** — data under the old unscoped key is never read and never deleted, on every platform.
