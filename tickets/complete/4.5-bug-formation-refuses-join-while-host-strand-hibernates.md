# Wake a hibernating host strand for an authorized closed-strand join

## What shipped

A bound closed-strand redemption makes the host issue a single-use `Strand.Invite` against its live strand database (`CadreNode.issueStrandMembershipInvite`). A hibernating host strand has no database, so every such redemption used to be refused with `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` until a check-in happened to line up.

After the existing control-database checks (Strand row, `Type`, recorded pre-split refusal, `StrandPartyKey`), the issuer now calls `wakeHostStrandForFormation(strandId, signal)`:

- Records activity through `HibernationManager.recordActivity` directly (no push fan-out to this party's phones), for every closed-strand issuance with a local instance. This keeps a check-in window that happens to have the strand live from re-quiescing it right after the invitation is issued, and restarts the idle timer on a live strand.
- Only when the instance is `'hibernating'` with no database, calls `wakeStrand` (coalesces with the wake `recordActivity` began; also covers hibernation disabled with a force-hibernated strand) and waits for it bounded by the formation provisioning `AbortSignal` via the module helper `resolvesBeforeAbort`. If the budget expires first the redemption is rejected retryably (token unspent) and the wake continues in the background, so the joiner's retry finds the strand live.
- Other states (never launched, `'starting'`, mid-quiesce, `'error'`) are refused retryably as before.

After the wake the issuer re-reads the database, runs the pre-split check, and refuses to write an invitation if the signal aborted meanwhile. The signal is threaded through a new exported `MembershipInviteIssuer` type used by `StrandFormationManager` and `StrandSolicitationService`. Authorization is unchanged: the hook runs only after token, disclosure, outside approval and seat pre-check pass, so only an entitled joiner can cause a wake.

Test: `cadre-node-issue-membership-invite.spec.ts` → "closed strand whose runtime is hibernating → wakes it and issues the invitation" (the reproduction; failed before the fix).

## Review findings

Read the diff of `ticket(implement): bug-formation-refuses-join-while-host-strand-hibernates` first, then the handoff.

**Checked and found correct**

- `resolvesBeforeAbort`: listener detached on both endings; an already-aborted signal returns `false` without attaching; a rejection of `work` before abort propagates; no unhandled rejection in any ordering (the `wake` promise always has a handler attached — via the race's `.then`, and via the `void wake.catch` when the budget expires; `recordActivity`'s shared `beginWake` promise has its own `.catch`).
- State handling: `'idle'` keeps its database, so it issues directly (activity flips it back to `'active'`); `'hibernating'` is the only state woken; a check-in mid-resume shows `'starting'` and is refused retryably; a check-in window shows `'active'` with a database and issues, and the recorded activity keeps the window from re-quiescing. The implementer's step beyond the ticket (recording activity in every state, not only when hibernating) is correct and belongs here — without it the host re-hibernates before the joiner syncs the `Strand.Invite` row.
- Open strands (`Type !== 'c'`) return `null` before any wake or activity. Waking a hibernating open-strand host so its live `strandAddrs` reach the joiner was considered and left out: it is not what this ticket fixes, and other members can serve an open strand.
- Budget: default provisioning work budget is 10 s (`DEFAULT_PROVISION_TIMEOUT_MS` 12 s minus 2 s settle grace), shared with the outside-approval hook. A slow resume can therefore exhaust it on the first attempt; the retryable rejection plus background wake is the designed answer, and it is documented in `docs/architecture.md`.
- Docs: `docs/architecture.md` Wake Mechanisms item 1 and the closed-strand formation paragraph match the code; `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` and the `issueMembershipInvite` option docs were updated. No other doc describes this path.
- Test: kept — it is the reproduction of the bug at the lowest layer that shows it. No tests cut; no new tests added (the budget-expiry branch is a two-line throw over a helper whose behaviour was verified by reading; a test would need a slowed `resumeStrand` on a real node and would mostly verify the stand-in).

**Fixed inline (minor)**

- The two log lines in `wakeHostStrandForFormation` were prefixed `issueStrandMembershipInvite:`; renamed to the method they are in.

**Filed (major, pre-existing, class-level)** — `backlog/bug-strand-resume-double-build-and-stuck-error`, two arms in the strand resume lifecycle, anchored to `docs/architecture.md#strand-hibernation`:

- Arm 1: check-in resumes (`handleStrandCheckIn` → `resumeStrand`) are not coalesced with wakes (`beginWake`). `resumeStrand`'s guard only checks `libp2pNode || database`, which are unset until the build is partway through, so a push-wake during a check-in's resume can build a second runtime and leak the first. The formation wake inherits a narrower version of this (a redemption landing between the check-in's status check and `resumeStrand` setting `'starting'`). The architecture doc's claim that coalescing prevents a push-wake racing a check-in is inaccurate; the ticket asks for it to be corrected with the fix. Filed at the invariant rung (one in-flight resume per strand at `resumeStrand`) rather than as a formation-specific guard.
- Arm 2: a failed wake leaves the strand `'error'` with no check-in and no retry (the implementer's "known gap"). The check-in path already recovers by forcing `'hibernating'`; the wake path does not. Formation is one more caller that depends on it.

**Tripwires**: none added. The double logging of a failed wake (once by `recordActivity`'s `.catch`, once by the formation manager or background `.catch`) is only log noise and not worth a site comment.

**Declined / not pursued**: extracting `resolvesBeforeAbort` into a shared utility — the other abort helpers in the package (`relay-reservation.ts`, `control-stream.ts`) do different things (delay, link, cancel), so there is no duplicate to merge yet.
