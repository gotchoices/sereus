# Complete: strand membership approvals — single-use stamps + action-tagged digests

Closes `bug-strand-manager-authority-antireplay` for the `Strand.*` membership/RBAC tables.

## What shipped

Every `Member`, `MemberPeer`, and `Manager` row carries a `StampId` — 256 bits of CSPRNG
output minted fresh per row incarnation. Every signed approval covers the table name, the
action, the row's key fields, and that stamp. Deleting a row requires filing a signed
tombstone into a new `Strand.Revocation` table in the same transaction, which retires the
stamp permanently; no row may ever be inserted carrying a retired stamp.

| Rule | Signed digest |
|---|---|
| Member add-by-manager | `'Strand.Member','add',new.Key,new.StampId` |
| Member remove-by-manager | `'Strand.Member','remove',old.Key,old.StampId` |
| Member self-departure | `'Strand.Member','leave',old.Key,old.StampId` |
| MemberPeer self register | `'Strand.MemberPeer','add',new.MemberKey,new.PeerId,new.StampId` |
| MemberPeer self remove | `'Strand.MemberPeer','remove',old.MemberKey,old.PeerId,old.StampId` |
| MemberPeer manager remove | `'Strand.MemberPeer','manager-remove',old.MemberKey,old.PeerId,old.StampId` |
| Manager promotion | `'Strand.Manager','add',new.MemberKey,new.Generation,new.StampId` |
| Manager self-resignation | `'Strand.Manager','resign',old.MemberKey,old.StampId` |
| Manager removal-by-another | `'Strand.Manager','remove',old.MemberKey,old.StampId` |
| Revocation tombstone | `'Strand.Revocation','retire',new.TableName,new.StampId` |

`Generation` is signed as a NUMBER — the crypto plugin's digest framing is type-tagged, so
integer `1` and text `'1'` produce different digests.

`Invite`/`ConsumedInvite` were deliberately left on the old `'|'`-joined-payload idiom: both
are insert-only with a fresh primary key per row, so an approval there already has exactly
one row it can ever seat. `strand-member-registry.ts` is untouched (off-engine self-proof
only).

## Review findings

The adversarial pass ran across three sessions (two were cut short by the token budget; the
analysis from both is folded in here). Categories with nothing in them say so explicitly.

### Attacks walked through — all refused, no exploitable hole found

- **Cross-table stamp confusion.** `Revocation`'s primary key is `(TableName, StampId)` and
  every `NotRevoked` / `RowIsGone` branch filters on `TableName`, so a stamp retired for one
  table cannot affect another. An invite-joining member picks its own `StampId` and could
  deliberately reuse the *value* of a live `Manager` row's stamp — harmless for the same
  reason. Per-table `unique` blocks reuse within a table; `NotRevoked` blocks retired values.
- **Unused approval replayed after the signer loses authority.** A promotion approval signed
  by manager F and never used is dead once F's row is gone: the promotion branch reads live
  `Manager`, the member-add branch reads `committed.Manager`. Both fail.
- **Tombstone as an attack primitive.** `Revocation.Authorized` accepts any committed
  member's signature, so any member can file tombstones for arbitrary stamps. Bounded by
  (a) `RowIsGone`, which refuses to retire a stamp whose row is still visible, and (b) stamps
  being 256 bits of CSPRNG output, so a not-yet-minted stamp cannot be guessed and
  pre-planted. Residual effect is table growth only (tripwire below).
- **Evicting a non-converged node.** Nothing on the strand read side filters rows whose stamp
  appears in `Revocation` (`NotRevoked` is insert-only), so a tombstone filed against a
  live-but-not-yet-converged row does not evict it. This is what keeps the control layer's
  remote-eviction hazard out of this schema (tripwire below).
- **Missed-seek deletes.** `revokeMember` / `leaveStrand` / `removeManager` delete via a
  single-column primary-key equality, which the optimystic module serves as a point lookup
  that can miss on a networked strand. A miss is not silent: the paired tombstone's
  `RowIsGone` sees the row still present and the commit fails loudly.

### Test quality — read both specs end to end, no assertion defect found

`strand-member-revocation.spec.ts` and `strand-membership-peer-rotation.spec.ts` were read in
full. Confirmed: constraint names are pinned only where exactly one check can fire (and each
such test explains in a comment why the siblings pass); where several can fire, only
`/CHECK constraint failed/` is pinned; rejection tests assert post-state, not merely that a
throw happened; several carry a positive control that re-runs the operation with the one
corrected element and expects success.

The `fileTombstone` helper is duplicated across both specs and mirrors the writer's private
`insertRevocation`. Left as-is deliberately — the writer's copy is private by design, and a
shared test helper would couple two otherwise-independent spec files. Recorded so it is not
re-opened as a fresh question.

### Tripwires recorded (not tickets)

Both are `NOTE:` comments on the `Revocation` table, written byte-identically into
`schemas/strand.qsql` and `packages/quereus-plugin-sereus/src/strand-schema.ts`:

- The table only grows — one row per deletion plus any junk any member files, and `Immutable`
  means rows never go away. Fine at strand scale; if membership churn ever gets large it needs
  pruning bounded by something other than "forever".
- Nothing on the read side drops a row because its stamp is retired, which is why a tombstone
  filed against a not-yet-converged live row is inert. If a read path ever starts filtering on
  `Revocation`, filing a tombstone becomes a remote eviction primitive and
  `Revocation.Authorized` must narrow from "any member" to "a manager, or the row's own owner".

### Test-coverage gap found and closed

Nothing anywhere tested `Strand.Revocation`'s own constraints, and the follow-up
`strand-approval-replay-pins` ticket does not cover them either. Six cases added to
`packages/cadre-core/test/strand-member-revocation.spec.ts`:

- `Authorized` rejects a tombstone signed by a stranger holding no `Member` row.
- `Authorized` rejects a tombstone signed by a member seated in the same transaction (the
  `committed.Member` read), with a positive control once the membership is committed.
- `RowIsGone` rejects retiring a stamp whose row is still live, with a positive control after
  the row is genuinely gone.
- `RowIsGone` confines `TableName` — a tombstone naming an unknown table is rejected.
- `Immutable` rejects both updating and deleting an existing tombstone.
- `RevocationRecorded` rejects a delete that files no tombstone (previously only worked
  *around* by the specs' helper, never pinned as its own assertion), with a positive control
  through the writer.

### Source hygiene — observation, no action

`packages/cadre-core/src/strand-membership-writer.ts` is 1224 lines, the large majority doc
comment, with several 40-60 line prose headers on single functions. This is the repo's
established convention (`schemas/control.qsql` and the strand schema read the same way) and
the rationale is load-bearing, so no trim was proposed. Recorded so the next reviewer does not
re-open it.
