# A probe's failure cleanup releases only a runtime it built

## What shipped

A hibernating strand is rebuilt by a wake (`handleStrandWake`), a periodic check-in (`handleStrandCheckIn`) or the mobile `serviceWake`. Before this change the check-in and `serviceWake` had one `catch` around seed read, rebuild and window that always quiesced and marked the strand `'hibernating'`, so a failed cohort-seed read could stop a node a concurrent wake was still building, or quiesce a strand whose waker had been told it was up.

- `CadreNode.rehibernateIfResumeFailed` — one rule for resume failures: re-hibernate only when the instance reads `'error'` (the rebuild this caller started or joined failed); otherwise log and leave the strand to whoever is building or holding it. Used by `handleStrandWake` and the check-in's resume stage.
- `handleStrandCheckIn` is split into a resume stage (the rule above) and a window stage (a quiesce that throws is still cleaned up by `rehibernateAfterFailedResume`).
- `runServiceWake` delegates to `wakeAndHoldForService`: a failed wake is only logged (the wake path already applied the rule); a failed window is cleaned up as before; `endProbe` still runs on every exit.
- `HibernationManager.handCheckInChainToHolder`: a check-in that returns while a wake is in flight or a `serviceWake` probe holds the strand hands its chain to that holder, whose outcome restores the chain at the base delay (strand ends `'hibernating'`) or starts the idle countdown (strand ends live).
- Review addition: `HibernationManager.runningCheckIns` — a force-hibernate, untrack or stop now ends the chain of a check-in that is already running, so its return schedules nothing (see findings).

The implementer broadened the ticket's hand-off rule from "strand non-`'hibernating'` and a wake in flight" to "any status, and also a probe holding the strand". Accepted in review: with the narrow rule, a check-in that returns while a `serviceWake` probe's window holds the strand reads it as woken and drops the chain, and if the probe's window then re-quiesces the strand, `endProbe` finds no chain to restore — the strand sleeps with no check-in, the same defect this ticket fixes. The cost (a failed wake that took the chain restarts it at the base delay rather than the escalated one) is small.

## Review findings

Read the implement commit (`ticket(implement): strand-probe-failure-cleanup-owns-only-its-resume`) first, then walked the interleavings of check-in / wake / probe / force-hibernate against `HibernationManager` and `CadreNode`.

- **Correctness of the split and the hand-off** — checked: wake fails its seed read during a check-in's build (wake settles `'starting'`, arms nothing; the check-in keeps its chain); check-in fails its seed read during a wake's build (hand-off, tested); check-in and wake both joining a failed build (both may quiesce; second is a no-op, and whichever reads `'hibernating'` first leaves it); probe starting during a check-in's seed read (hand-off to the probe restores the chain the probe did not know about); check-in returning while a wake is still in flight after its window stamped activity (hand-off, wake's settle arms the idle countdown). `checkInsCancelledByWake` and `probes` entries added by the hand-off are always consumed by `settleWake` / `endProbe`. No defect found.
- **Found and fixed — force-hibernate did not stop a check-in already running** (pre-existing, widened by the new probe arm). `forceHibernate` and `untrackStrand` cleared only an *armed* check-in; a check-in whose timer had fired and was mid-window would, on return, reschedule its chain (strand reads `'hibernating'`) or — through the new hand-off — give it to a probe that began afterwards, so the probe's end restored a chain on a strand the mobile runner had force-hibernated. Added `runningCheckIns` in `hibernation-manager.ts`: set when a check-in starts, removed by `forceHibernate` / `untrackStrand` / `stop`, and `runCheckIn` stops (and clears the stale `nextCheckIn`) if its entry is gone. Reproduction test added: `a force-hibernate during a running check-in ends its chain, even with a probe holding the strand` (failed before the fix with `nextCheckIn` @2250, passes now). Doc: `docs/architecture.md` mechanism 4 now says a force-hibernate also ends a running check-in's chain.
- **Out of scope, already ticketed** — a wake landing while a window or timer-driven hibernate is quiescing: `strand-wake-during-quiesce-is-told-the-strand-is-up` (implement stage, prereqs this ticket).
- **Known gap left as is** — two probes running windows over one shared runtime (a check-in whose resume joined a wake's build, or a probe started during a check-in's seed read): the first window to end quiesces a runtime the other window is still holding. Existing behaviour, noted by the implementer; the quiesce-ordering work in `strand-wake-during-quiesce-is-told-the-strand-is-up` is where overlapping windows would next be addressed. No new ticket.
- **Tests** — kept the fix stage's `a check-in that fails before rebuilding leaves a wake's mid-build runtime alone` (the defect's reproduction) and the implementer's hand-off test (reproduces the dropped chain; confirmed it fails without the hand-off). No tests cut: none restate the implementation. Did not add tests for the probe-in-window and `'hibernating'`-with-wake-in-flight hand-off arms; they share the one branch the hand-off test already covers.
