# A removed machine reports its own removal

## What was built

- **`CadreRemoval`** (`types.ts`): `{ partyId, stampId, signerKey: string | null, at }`. `signerKey` is the tombstone's signer only when `verifyRevocationSigner` passes and the key is in this node's trusted-owner anchor; otherwise null plus a log line, and the removal is still reported. Exported via `export * from './types.js'`.
- **Event `cadre:removed`** on `CadreNodeEvents` and **`CadreNode.removedFromCadre()`**, the query form for an embedder that subscribed late.
- **Detection** in `CadreNode.noteOwnRemoval`, the last step of every membership refresh: a `CadrePeer` tombstone names this node's peer id, the refresh's retired-stamp-filtered `CadrePeer` read has no live row for it, and an earlier refresh of this node object saw its live row. Reuses the refresh's shared tombstone read. Replicated removals are picked up by the reconcile pass's refresh. Reported once per node object (kept across stop()→start()).
- **Drains**: `drainPendingRevocations`, `reconstructAuthoredMembership`, `drainPendingPeerWrites` return early once removed. The old `NOTE:` that pointed at this work is replaced by a narrower tripwire for an owner whose key alone was removed.
- **Docs**: "The removed machine learns it, best-effort" under "Removing a machine" in `docs/architecture.md`, the "What is deliberately not reaped" aside links to it, and an Implementation Status bullet.
- **Tests**: `cadre-node-learns-removal.spec.ts` (three cases on the rule's branches: seen live then removed → one event over two refreshes; never seen live → nothing; re-added under a fresh stamp → nothing). `membership-gate-helpers.ts` gained a `tombstones` option.

Usage for the downstream tickets (`hosted-node-stops-when-removed`, `phone-kit-forgets-a-cadre-that-removed-it`, `reference-app-web-devices-and-nodes`): subscribe with `node.on('cadre:removed', …)`, and check `node.removedFromCadre()` once after `start()`. Then stop the node and delete the cadre's data. Calling `stop()` from the handler is safe even while another stop is in flight (see below).

## Review findings

Read the diff from `ticket(implement): node-learns-it-was-removed` first, then the handoff.

**Correctness, checked by reading:** the detection rule matches the ticket's contract on all branches. `rows` is the raw (not authorization-filtered) `queryCadrePeers(false)` read, so "seen live" means an un-retired row, as intended. A `CadrePeer` delete that replicates before its `Revocation` row yields no report on that refresh; the next reconcile-pass refresh reports it (`runReconcileControlCohort` refreshes the gate every pass). The tombstone read failure is caught locally. `emit` already catches handler exceptions, so a throwing handler cannot derail the refresh. Stamp selection when several tombstones name self prefers the last-seen live stamp. No defects found here.

**Found and fixed (minor):**
- **`stop()` re-entrancy.** The handoff flagged that a refresh in flight when `stop()` begins can still emit `cadre:removed` (`_running` stays true until `cleanup()` ends), and the intended embedder reaction is to call `stop()`. Confirmed that a second concurrent `stop()` ran `cleanup()` a second time over the half-torn-down node (reproduced: two `control:disconnected` emits). Fixed at the class level instead of guarding this one event: `stop()` now joins an in-flight stop (`stopInFlight`, body moved to `stopRunning`). Emitting during a stop is kept deliberately: suppressing it would lose the removal for good, since "seen live" is not persisted. Regression test added in `cadre-node.spec.ts` ("a stop() called while another is in flight joins it"); it fails without the fix (2 teardowns) and passes with it.
- **Stale comment in `control-database.ts`** (`reapRevokedRows`' doc) still said "a node that learns it has been revoked should shut itself down is … its own ticket"; now points at `removedFromCadre` / `cadre:removed`.
- **`refreshAuthorizedControlPeers` doc** said the hang-up "runs LAST"; it now names both end-of-refresh checks in order.

**Considered, no change:**
- **Kept across stop()→start() rather than reset.** Agreed with the implementer: a restart of the same object should not re-report, and `removedFromCadre()` must still answer after the restart for the downstream "check once after start()" usage.
- **`removePeer`-only removal of an owner machine** reports removal and stops the drains although the owner key could still sign. Only the lower-level single-row writer produces that state; `removeMachine` removes both. Not a current-release path; no ticket, no tripwire beyond the handoff's note, since the drains would only re-touch rows for a machine that is no longer a member.
- **Growth drain step 5 (`reissueWritesMadeAlone`) and `retouchSelfDeviceToken`** still run on a removed node. The ticket scoped only the three owner drains; these fail as log noise and stop when the embedder stops the node. No change.
- **Restart-before-acting gap**: carried by the implementer's `NOTE:` at the check, as the ticket required.

**Tests:** the three implementer cases each pin one branch of the specified rule and stay. The `tombstones` helper option is minimal. No integration assertion, per the ticket (receiving the tombstone before being cut off is a race).

**Docs:** `docs/architecture.md` paragraph, aside link and status bullet are accurate. `docs/api.md` does not cover the machine-removal API at all (architecture.md owns it), so nothing to add there.
