# A linked sibling loaded under two path spellings

A **spelling** is the exact path string a junction stores for the directory it points at. Windows compares paths without regard to case, so two junctions can point at one directory and store different strings for it. Node's resolution keeps whichever string a junction stored and keys its module cache on it, so a package reached under both spellings is loaded twice; the two copies share no classes, and every `instanceof` across them is false. That is what made `isCohortUnreachableRead` stop recognising a `BlockUnavailableError` the plugin had just thrown.

## What shipped

`test-harness/linked-package-spellings.ts` refuses a test run in that state. `findSpellingDisagreements(targets, setupUrl)` reports one entry per linked package name that resolves to two or more path strings, each entry carrying the string the loader keys on, the directory's own spelling on disk, and every junction that produced it; `assertOneSpellingPerLinkedPackage` throws with that listing, the consequence, and a remedy that branches on whether a sibling checkout holds one of the disagreeing junctions. The detector walks *loading contexts* — directories an `import '<pkg>'` resolves from — seeded with the setup module's own directory and the root of every `workspace` target, then extended breadth-first through each linked root it finds. Spellings are compared against each other, never against the disk, because a spelling every junction agrees on loads one copy and is harmless. There is no platform branch, and the check passes trivially where `resolutions` carries no `link:` entries.

`test-harness/build-freshness.ts` gained the three exports the new module needed: `workspacePackageRoots`, `readPackageJson` with its `PackageManifest` widened to the dependency maps, and a `junction` field on the `linked` variant of `LinkedPackage` so the message can name the link to repoint rather than only its target. All ten `globalSetup` modules call the new check between `assertUppercaseDriveLetter()` and `assertBuildFresh(...)` — before the freshness check because with two spellings live the freshness walk judges two roots for one package. `docs/contributing/testing.md` gained the section that owns the mechanism and the remedy.

On this machine, the eight `packages/reference-app-{web,rn,ns}/node_modules/@optimystic/*` junctions that stored `C:\Projects\optimystic\...` were repointed to `C:\Projects\Optimystic\...`, matching the root junctions and the sibling's own nested links. Each was deleted non-recursively and recreated; no recursive delete was used.

Implemented in `ticket(implement): linked-sibling-loaded-under-two-path-spellings`, reviewed in this ticket.

## Review findings

Read the implement diff first, then the handoff. Every junction under `node_modules`, `packages/*/node_modules`, `../Optimystic/packages/*/node_modules` and `../Quereus` was enumerated by hand to check the handoff's claims against the machine; the walk's logic, the message builder, the exports added to `build-freshness.ts`, the spec and the docs section were read line by line. No defect in the detector's logic was found: the loading-context walk terminates on a seen-set of context path strings, the declared-dependency filter is load-bearing exactly as the handoff says, the registry-copy and absent cases correctly contribute nothing, and `isInside`'s case-insensitive comparison on Windows is right because case is what the two spellings differ in.

**Verified against the machine, not just read.** `@optimystic/*` is now spelled `C:\Projects\Optimystic\...` by all 16 of this repository's junctions and by all 25 of Optimystic's own nested links — one spelling, so the check is correctly silent. `@quereus/quereus` is spelled `C:\Projects\quereus\...` by all four of this repository's junctions and by all four of Optimystic's nested links, while the directory is `C:\Projects\Quereus` on disk: uniformly odd, therefore one module instance, therefore correctly not reported. The handoff's warning stands — a reviewer who "fixes" that changes no behaviour and should not.

**Fixed in this pass (minor).**

- *One home per fact.* The module header restated the whole mechanism, the two-installs explanation and the three-bullet remedy that the new `docs/contributing/testing.md` section now owns, and retold the `isCohortUnreachableRead` diagnosis as a story. Trimmed to what the code itself rests on — the `realpathSync` versus `realpathSync.native` difference, the compare-against-each-other invariant, the read-only constraint, the wiring order, the two tripwires — with the doc link carrying the rest. 32 lines of the header replaced by 14.
- *An unstated "why not".* `declaredCandidates` reads `dependencies`, `peerDependencies` and `optionalDependencies` but not `devDependencies`, which a reader meets as an omission. It is correct — what a discovered context loads is its runtime imports, and the one package whose dev dependencies do get loaded is the suite's own, covered by the suite directory's seed because that seed's `node_modules` chain runs through its package. Said so at the site.
- *An ambiguous revisit condition.* The wiring tripwire said "if a third such setup check appears", which can be read as counting the gated `build-freshness` call. Reworded to "a third ungated setup check", so the next reader can tell whether it has tripped. (It has not: `assertUppercaseDriveLetter` and `assertOneSpellingPerLinkedPackage` make two.)

**Parked as a tripwire, not a ticket.** The walk seeds workspace package roots but never follows workspace-to-workspace edges, so a suite whose `TARGETS` omit a workspace package it loads only transitively would not consult that package's own `node_modules`. Conditional, and the condition is an install state rather than a dormant code path: no workspace keeps its own scoped junctions today except the three reference apps, which list what they load, and the `@serfab/*` junctions of one repository are all written by one `yarn install`, so they cannot disagree with each other the way two installs' can. `NOTE:` at `seedContexts` saying to seed every workspace root if a package-local copy ever appears somewhere a suite's `TARGETS` do not name.

**Tests: none added, one request declined.** The handoff asked for a judgement on covering the remedy's "every junction is ours" arm. Declining it: the branch selects prose, and the direction that matters — telling a reader they may freely repoint a link that is actually inside a read-only sibling — is the one case 1 already asserts, through `do not write in the sibling`. The uncovered direction is the harmless one (a reader sent to look at a sibling that is not involved), which does not earn a permanent fixture. The six existing cases were read as code under review; each is one real branch of the detector and none restates the implementation or verifies a mock, so none was cut. The `junction` field assertions added to `build-freshness.spec.ts` ride on existing whole-value comparisons rather than adding cases, which is the right shape.

**Untested by necessity, recorded rather than forced.** The `workspace`-target seeding arm of `seedContexts` is not reachable from a temp-dir fixture: `workspacePackageRoots()` resolves `<repo>/packages` from `build-freshness.ts`'s own module URL and memoises it, so a fixture cannot drive it, and a test against the real checkout would assert the machine's install state rather than the code. It is exercised by every real suite run. Adding an injection seam only to reach it was judged worse than the gap.

**Not re-filed.** The handoff's remaining known gaps were weighed and left as they are: the start-up cost is parked as a `NOTE:` that makes no magnitude claim (a setup-only `reference-app-web` run measured 2.72–2.86 s for vitest boot, both setup checks and the freshness walk together, which does not isolate the walk and does not need to); the wiring tripwire living in the module doc rather than at one of ten call sites is the better placement and the content is as the fix ticket specified; and `foreignCheckouts` reporting deduped sibling checkouts rather than every foreign junction is right, because the junctions are already listed per package above it in the same message.
