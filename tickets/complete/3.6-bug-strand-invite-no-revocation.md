# Completed: the invitation-cancellation tombstone (schema half)

## What the defect was

A manager issues two invitations to one party; the party joins on the first, is removed,
then consumes the second and is a member again. `Member.Authorized`'s invite branch only
closed the *already-spent* path (it requires the admitting `ConsumedInvite` row to be absent
from the committed snapshot, so a stale consumption record is inert). An **unspent**
invitation produces a genuinely fresh consumption record, so it re-admitted normally.
Managers are the parties that issue invitations, so a manager anticipating its own removal
could mint a stack of never-expiring invitations for itself.

Pinned by `packages/cadre-core/test/strand-member-revocation.spec.ts` →
`'a revoked member re-admits ITSELF off an invite it held but never consumed'` (line 573).

## What landed

Three edits, mirrored byte-for-byte into `schemas/strand.qsql` and the embedded
`STRAND_SCHEMA` copy in `packages/quereus-plugin-sereus/src/strand-schema.ts`:

1. `Invite`'s stale `-- TODO: ability to deactivate?` comment retargeted at the new table.
2. `ConsumedInvite.NotCancelled` — `not exists (select 1 from CancelledInvite C where
   C.InviteKey = new.InviteKey)`, on insert. This one constraint is the whole fix: blocking
   the `ConsumedInvite` insert blocks the join, because `Member.Authorized`'s invite branch
   needs a same-transaction fresh `ConsumedInvite` row and `consumeInvite` writes both rows
   in one transaction, so the whole join rolls back.
3. `table CancelledInvite (InviteKey text primary key, ...)` — insert-only tombstone with
   `OnlyClosed`, `Immutable` (no update, no delete), and `Authorized` (a `committed.Manager`
   must sign `digest('Strand.CancelledInvite', 'cancel', InviteKey)`). Context params
   `(ManagerKey text, ManagerSignature text)`, non-null, matching `Revocation`'s precedent.

Design rationale — tombstone vs. deleting the `Invite` row vs. a state column, why no
`StampId`, why deliberately no `InviteExists` gate — is written out in the comments above the
table, along with two `NOTE:` tripwires (unbounded growth; cancellation must propagate before
the holder redeems).

**Behavior change on its own: none.** Nothing writes a `CancelledInvite` row yet. Ticket
`strand-invite-cancel-writer` (3.7, in `implement/`) carries the `cancelInvite` /
`listOutstandingInvites` writers, the pre-flight correction, the behavioral tests and the
docs. The re-admit test at `strand-member-revocation.spec.ts:573` still passes — expected
and correct at this point; 3.7 rewrites it.

## Review findings

### Checked and found sound (no change)

- **Does `NotCancelled` on `ConsumedInvite` alone close the join, or does
  `Member.Authorized`'s invite branch need a matching gate?** Read adversarially against
  `strand.qsql:244-248`. The branch requires an uncommitted `ConsumedInvite` row with
  `CI.MemberKey = new.Key`; blocking that insert aborts the transaction, so the `Member`
  insert has no branch left. No duplicate gate needed. Also confirmed `NotCancelled` reads
  the LIVE `CancelledInvite` (not `committed.`), which is the strict direction, and that an
  attacker cannot delete the tombstone in-transaction to escape it (`Immutable`).
- **Can a manager seated in the same transaction authorize its own cancellation?** No —
  `Authorized` reads `committed.Manager`, matching `Member` / `MemberPeer` / `Revocation`.
- **Cancellation really is permanent.** `Invite` is insert-only with `Key` as its primary
  key and no delete path, so a cancelled `InviteKey` can never be re-issued to bypass the
  tombstone.
- **The absent `InviteExists` gate.** Confirmed the right trade. It cannot be used to
  pre-cancel a future invitation: an `Invite.Key` is a 256-bit ed25519 public key minted at
  issuance, so it is unguessable. What it permits is a manager filing junk rows — already
  covered by the growth `NOTE:` on the table, and managers can cancel real invitations
  anyway, so it grants no new power.
- **Non-null `with context`** on a table whose invite-chain siblings are nullable. Follows
  `Revocation` (`strand.qsql:502`), which is the closer precedent (tombstone table, both
  fields always supplied). Left as landed.

### Minor — fixed in this pass

- **Inaccurate comment.** The `Authorized` block claimed "Every sibling `Authorized` in this
  schema reads `committed.*` for the same reason." `Manager.Authorized` does not — it reads
  the live `Manager` table (`strand.qsql:422`, `:435`), deliberately, because its strict
  `Generation` ordering (not a snapshot) is what excludes a same-transaction authorizer.
  Reworded in both schema copies to name the three tables that do, and to state Manager's
  different mechanism.
- **`CancelledInvite` had no runtime proof it applies.** The drift guard compares text only,
  so a malformed table declaration — or the forward reference from `ConsumedInvite` to a
  table declared below it — would not have tripped anything. Added `CancelledInvite` to
  `STRAND_TABLES` in `packages/quereus-plugin-sereus/test/e2e/strand-schema.e2e.spec.ts`,
  which applies the real schema against a real strand and queries every listed table. Added
  `Revocation` in the same edit — it was missing from that list too, a pre-existing omission
  from the ticket that introduced it — and replaced the now-wrong "six membership tables"
  comment with a rule for keeping the list in sync.

### Major — none filed

No finding warranted a new ticket. Both real gaps below are already carried by tickets that
exist, so filing more would duplicate:

- **Removal does not cascade into cancellation** — an invitation names no invitee, so there
  is nothing to match a removed member against. `feat-strand-invitee-bound-invites`
  (backlog), filed during implement.
- **Stale `dist/` false green** — `cadre-core` loads the embedded schema through
  `quereus-plugin-sereus`'s `dist/`, and the root test wiring is not topological, so an
  unbuilt tree silently tests the OLD schema. `debt-embedded-schema-stale-dist-false-green`
  (backlog), filed during implement. Confirmed the trap is real: rebuilt before every run
  here.

### Tripwires

Two were already parked as `NOTE:` comments on the table by the implementer and were checked
rather than added to: unbounded table growth, and the requirement that a cancellation
propagate to a node before a holder redeems there. No new tripwire was warranted.

### Known gap left open deliberately

**No behavioral test asserts the three new constraints.** The implementer ran a throwaway
smoke spec (four assertions, all passing) and deleted it to keep this ticket's diff
schema-only. The e2e list addition above now proves the table *applies and is queryable*, but
not that `NotCancelled` / `Authorized` / `Immutable` *behave*. `strand-invite-cancel-writer`
(3.7, next in the queue) specifies every one of those cases against the real writer, which is
where they belong — writing them here with raw SQL would be thrown away days later. Flagged
explicitly rather than left silent: until 3.7 lands, the security property rests on the
implementer's transient run plus the constraint text itself.

Docs (`docs/architecture.md` table lists and digest table, `docs/strands.md` known-gap
bullets) are likewise 3.7's, and were left alone on purpose: at 3.6 the user-visible
statement "an invitation cannot be cancelled" is still *true*, because no code can write a
tombstone. Updating them now would document a capability that does not yet exist.
