# Provider join scenarios with a phone-shaped requester (complete)

Two integration scenarios run the claim and invitation paths of `provider-container-joins-by-claim-or-invitation` against the real provider HTTP API and real `cadre-cli` children, landed in `ticket(implement): provider-join-scenarios-phone-shaped-requester`. The claim scenario pins eight ordered steps (placeholder party, 503 before the node is up, a code carrying exactly the announced `/ws` address, a wrong secret refused, the right one folded onto the record with the phone dialing in, a rival owner refused, the container still claimed after a restart on its volume, delete). The invitation scenario pins six (an owner node mints a single-use invitation, the container redeems it and the fold names the owner, the owner lists it as authorized and holds its signed record, a second container on the spent invitation fails `invite-spent` and not retryable, no response or child output carries the bundle, delete). The harness gained `ProviderProcessOrchestrator.restartContainer` (same environment, ports and dockerId again), `OwnerCliNode.createInvitation`, `isAuthorizedMember`, `listMembers` and a `listenAddrs` option, and, from the review, `providerApi` in `provider-api.ts`.

## Review findings

**Checked.** The implement commit's diff before the handoff summary; both scenario files line by line against the product code they assert on (`nodeCode` and its refusals in `container-service.ts`, `redactContainer` and the code route in `routes.ts`, `claimAddressesFor` in `node-code.ts`, the fold's never-regress guard, `createContainer` returning the `pending` record before provisioning, the invitation redemption's row insert with `Sig` null in `control-database.ts`, `CadreNode.listMembers` returning whole rows, the `Already claimed` log line in `start.ts`); the orchestrator's restart path (`watchExit` guard on the current child, `exitedAt` cleared, launches forgotten with the handle, a failed respawn leaving the dead child on the handle); `waitUntil` tolerating a throwing predicate, which step 7's `/status` poll across the restart relies on; teardown order in both `afterAll`s; the docs bullets against the scenarios' actual steps; the Which Side Dials row citations in the headers (row 4 names the provider container's three arms, so "row 4, the claim arm" is right). Ran `yarn workspace @serfab/integration-tests typecheck`, `yarn lint`, and both scenario files twice: before and after the fixes below (14 of 14 steps pass, about 35 seconds for the pair).

**Found and fixed inline (minor).**

- Both scenarios carried their own copy of the provider's response-envelope types, an `inject` wrapper that records every body for the leak check, and a `readContainer` helper. Extracted to `harness/provider-api.ts` (`providerApi(server)` with `request`, `readContainer` and `answered`, plus the envelope types), exported from the barrel; both scenarios now use it and lost about 25 lines each. `docs/testing.md`'s claim bullet names it.
- The `sig !== null` check in the invitation scenario's step 3 depends on `CadreNode.listMembers` answering the control database's whole rows past its declared `{ peerId, multiaddr }`. The implementer's `NOTE` sits on the reader (`OwnerCliMemberRow.sig`), where someone narrowing the producer would never see it; added a matching `NOTE` on `CadreNode.listMembers` naming the reader, so the two are narrowed together. Comment only; `@serfab/cadre-core` rebuilt so the integration suite's stale-build guard passes.
- `OwnerCliNodeOptions.listenAddrs` doc read "OS-assigned ports so the admin channel reports the bound ones"; now says each address is on port 0, which is what makes the admin channel's report the bound ones.

**Considered and left as is.** The orchestrator keeps each child's launch (config path and environment) in a map beside the handles rather than on the exported handle: the environment carries the claim secret, and the handle is what scenarios hold, so the split is deliberate and the two maps are maintained at the same three sites. The scenario files are 420 and 300 lines, in line with their siblings. The invitation scenario's owner node is both minter and always-on member, which the header states and nothing in the steps depends on. The "not-ready until the node reports an address" window the handoff flagged is a timing window the scenario cannot force (the node announces its addresses in the same `/status` payload that first carries its peer id here), and the scenario already fails on any refusal before the code other than 503, so nothing further is pinned.

**Tripwires recorded.** The restart's port reuse (`restartContainer`'s `NOTE` in `provider-process-orchestrator.ts`: another process may take a port in the gap); the undocumented `sig` field (the two `NOTE`s above); step 7 not pinning which dial source the requester used (the `NOTE` in the claim scenario, as in `node-claim-by-phone`). None of these is a defect now.

**Tickets filed.** None. No finding served a class-level invariant or a current-release anchor beyond what was fixed inline; the one product-side observation (a method whose declared type is narrower than what it returns) is a comment-level contract and recorded at both sites.

**Tests.** No tests cut and none added: each `it` pins a distinct named step of the architecture's two join sequences, and the harness additions are glue those steps exercise.
