# Complete: browser reference app "Add a device or app" (the owner side)

## What was built

A new route `#/cadre` (nav **Cadre**, test id `nav-cadre`, placed after Home) renders `src/Cadre.svelte`: a page heading, one line about what a cadre is, and the **Add a device or app** card (`src/AddDevice.svelte`). The flows and wording are the phone app's (`packages/reference-app-rn/src/add-device-section.tsx`), with "this app" changed to "this tab" where it means the browser tab.

- **Owner check.** `cadre-web.ts` now keeps the tab's owner public key in `ownerPublicKey`, set where `runOwnerGenesis` already derives it and cleared in `stopCadre`. `isOwner()` asks whether `getControlDatabase().getOwnerKeys()` holds it. Standing is `checking | owner | member | unreadable`. A non-owner sees one line. If owner genesis failed (`node.owner === 'error'`), that line says the tab could not make itself the owner, instead of calling it a member. "Unreadable" offers Try again.
- **Paste request.** A textarea and **Use request**. Decoder errors show inline under the button. Before the approval panel opens, the tab refuses its own request (`currentPeerId()`), re-checks owner standing, and refuses an app already in the cadre (`isMemberPeer`, over `queryCadrePeers()`). The approval panel sits inline and replaces the two inputs while open. It shows the app name with the "check the code" note, the code (`peerCode`: 12 characters, …, 6, the same as the phone's `shortPeerId`), **Also an owner** (default on) with its line, and Add / Cancel. A successful Add clears the textarea; a failed one keeps the text.
- **Copy invitation.** **Also an owner** (default on), the 15-minute bearer warning while it is on, and **Make invitation** / "Making the invitation…".
- **Minted invitation.** It replaces both inputs until **Done**. It shows the title ("Open invitation" or "Invitation for ‹app›"), the QR code, the text in `Copyable`, "Valid until HH:MM" (with the weekday when that is not today), and the reach line (none for `anywhere`; a plain line for `local-network`; a warning for `issuer-only`).
- **Outstanding invitations.** `listCadreInvitations()`, filtered to `live` and sorted latest expiry first. Each row shows the target ("For ‹code›" / "Anyone with the text"), owner/member, expiry, and "X of Y used" only when more than one use is allowed (as on the phone). Withdraw asks `confirm()` first; withdrawing the invitation on screen also clears it. The list refreshes on every move of the store's status to `running` (which covers mount and Restart), after a mint, after a withdraw, and on Refresh. Withdraw returning `false` refreshes silently, with a `console.info`.
- **Mint failure.** Shown under the button that was pressed: "Could not make an invitation", core's message, and, when the live relay status is not `reserved`, the no-relay line, with core's message as a detail line below it.
- **QR** (`src/lib/QrCode.svelte`). `QRCode.toString(text, { type: 'svg', errorCorrectionLevel: 'L', margin: 2 })` is injected with `{@html}`. A scoped `eslint-disable-next-line svelte/no-at-html-tags` carries the reason, as cadre-host's `QrCode.svelte` does. A rejection is logged and shows "Too long for a QR code; use copy instead." The code is drawn at `min(24rem, 100%)` wide.
- **Pass-throughs in `cadre-web.ts`.** `isOwner`, `isMemberPeer`, `createCadreInvitation`, `listCadreInvitations`, `withdrawCadreInvitation`. Each throws "CadreNode not started" when no node is running. The `__cadre` debug hook was not extended, because no e2e needs it yet.
- **Dependencies.** `qrcode@^1.5.4` and the dev dependency `@types/qrcode@^1.5.5` (the versions the phone app uses), added with yarn.
- **Docs.** README: the `#/cadre` route, a new "Adding a device or app" section, and the file map. `docs/architecture.md`: "Handing an invitation from app to app" now names the browser app's managing side, and the package table row mentions it.

## Deviations from the ticket (please check)

- **Files beyond the ticket's list.**
  - `src/AddDevice.svelte` holds the card, so the join ticket can add its own card beside it on `Cadre.svelte`.
  - `src/lib/add-device.svelte.ts` holds the card's state at module level. The router unmounts the page on every route change, and a minted invitation's text exists nowhere else. The ticket's Restart case ("while the page shows a minted invitation", where Restart is on Home) assumes it survives a visit to Home. The phone flagged the same loss as a NOTE.
  - `src/lib/cadre-format.ts` holds `peerCode` and `validUntilText`. They are outside the rune module because `svelte/prefer-svelte-reactivity` flags the throwaway `Date`s in `validUntilText`, and because the join card needs `peerCode` too.
- **No-relay wording.** The ticket's text ("…and no always-on machine of your cadre has one either") claims something the card never checks. The phone's review corrected the same line for the same reason. The card says instead: "This tab has no relay address, so an invitation can be made only while an always-on machine of your cadre has one. Home shows the relay status and how to set one." The ticket's "runtime manifest" is really `VITE_RELAY_ADDR` / `localStorage["relay-addr"]`, which Home's relay warning already explains, so the line points there.
- **Issuer-only line.** The phone says "Add an always-on node (below)"; the web app has no add-node section. The card says "Add an always-on node (a cadre-host machine can join with an invitation made here) to avoid this." docs/cadre-host.md → "Join by invitation" confirms a cadre-host can do that.
- **Sibling ticket edited.** I appended one edge-case bullet to `tickets/implement/8.5-reference-app-web-joins-existing-cadre.md`: the minted invitation and the pending approval must be cleared on a party switch or rollback, and the join card can reuse `QrCode` and `peerCode`.

## Known gaps

- **QR readability by a phone camera is untested.** About 2.9 CSS px per module at 24rem for a ~1,200-character invitation; less for ~2,000 characters. The phone device run (`rn-device-run-join-existing-cadre`, in `blocked/`) covers reading a code off a phone, not off a laptop screen.
- **No e2e covers the card.** Every behaviour above was checked by the manual run only. A solo e2e for "no relay → mint refused with the no-relay line" would be cheap if the reviewer thinks it pays; I judged it did not.
- **Expiry is not polled.** An invitation that expires while on screen stays listed until the next refresh, as on the phone.
- **Join interaction.** A party switch (the join ticket) would leave the old party's minted invitation and pending approval on the card. That is now an edge case in that ticket.
- Errors from list reads and withdraws are logged to the console but not pushed to Diagnostics' "Recent errors"; only mint failures are (`pushError('createCadreInvitation', …)`).

## Review findings

Reviewed the diff of `ticket(implement): reference-app-web-owner-adds-device-or-app` before the handoff, and compared it with the phone app's `add-device-section.tsx` and `settings-controls.tsx`.
