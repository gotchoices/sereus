## What was wrong

`cadre-provider check` (in `src/bin/provider.ts`) and the `cadre:provider:config` debug dump in `loadConfig` printed the whole loaded config, including `billing.stripeSecretKey`, `billing.stripeWebhookSecret` and every push `fcm.privateKey` / `apns.privateKey`.

## The fix (landed earlier, in commit 2bef08fa)

`redactConfigSecrets` in `packages/cadre-provider/src/config/loader.ts` replaces the two Stripe secrets with `[redacted]` and passes the push block through `redactPushConfig` (`config/validate.ts`). Both outputs call it. The fix stage confirmed the behavior by running the built CLI on a config holding all four secrets: each printed as `[redacted]`.

## What this ticket added

- A test in `src/config/__tests__/push-validate.test.ts`: "redactConfigSecrets hides the Stripe secrets and the push private keys". It loads a config through `loadConfig`, with `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` in `env` and an FCM plus APNs push block in `overrides`. It first asserts that the loaded config contains all four planted values, so the test cannot pass because the input never held them. Then it asserts that the redacted config contains none of the four and still has the FCM `projectId`. Before this, only `redactPushConfig` had a test, so a refactor could drop the Stripe redaction without any test failing.
- The file's second `describe` is renamed from `redactPushConfig` to `secret redaction`. It now holds the existing `redactPushConfig` test and the new one.
- A `NOTE:` above `redactConfigSecrets`: any field marked `secretString` in `schema.ts` must also be redacted there. The schema's secret mark carries no metadata, so the two lists can drift apart.

## Validation

- `yarn workspace @serfab/cadre-provider test`: 31 files, 237 tests, all pass.
- `yarn lint`: exit 0.
- I commented out the `stripeSecretKey` redaction line and ran the test file. The new test failed and the other 7 passed. The line was then restored, so the only change left in `loader.ts` is the `NOTE:`.

## Known gaps

- The test covers the redaction function, not the `check` command's printout itself. That is enough because `check` prints `redactConfigSecrets(config)` directly.
- Nothing ties the `secretString` marks in `schema.ts` to the redaction list automatically. Adding a secret field to the schema without adding it to `redactConfigSecrets` would leak it, and the only guard is the `NOTE:`. A schema-driven redaction, where the secret mark carries a path the redactor walks, would close this. Nothing was filed for it because there are only four secret fields today.
