description: A relay can quietly forget that a node reserved a forwarding slot while the connection to that node stays open, and the node never asked again, so nobody could reach it until the connection dropped. The node now re-asks for the slot every five minutes while it believes it holds one.

gotchoices/sereus#64. `superviseRelayReservation` decided a reservation was held by reading the node's own advertised `/p2p-circuit` addresses — a local fact. A relay can forget a reservation while the connection to it stays open, and then every tick said "held", nothing was requested, and the node stayed undialable through that relay until the connection dropped.

## What changed (`ticket(implement): relay-supervisor-renews-a-held-reservation`)

While the reservation reads as held, the supervisor now re-sends the reservation request every `renewMs` (default 5 min, jittered ±10%). The renewal is the only thing that asks the relay itself.

- **`relay-reservation.ts`.** `RelayReservationStoreLike.getReservation?(peerId)` — new, optional for the same reason `relayFilter` is: a libp2p rename degrades to no renewal rather than making `findCircuitRelayTransport` return `null`. Module-private `renewRelayReservation` zeroes the held reservation's `expire` and calls `addRelay(peerId, 'discovered')`, which is the only route into libp2p's in-place refresh. `renewOneReservation` bounds one renewal by the loop's `timeoutMs` and cancel signal through the module's `delay` helper. `relayPeerIdOf` was split so `relayPeerOf` returns the `PeerId` the store is keyed by.
- **Cadence.** `DEFAULT_RELAY_RENEW_MS` (300 000) and `RELAY_RENEW_JITTER` (0.1), both exported from `index.ts`, plus `renewMs` on `RelayReservationSupervisorOptions`, clamped away from 0 like the other cadences. `RelayReservationLoop` arms the renewal clock when a drive lands a reservation or a tick first finds one held, restarts it after every renewal whatever the outcome, and clears it before every drive. A due tick renews, then re-checks: still held → the healthy cadence; no longer held → drive at once with no backoff. Renewals set the same `inFlight` flag a drive does, so the two stay serialized per supervisor.
- **No `NetworkConfig` field**, as specified: `CadreNode.reserveRelays(addrs, opts)` already spreads caller options into the supervisor.
- **Docs.** `docs/network/relay.md` → "The supervisor" states that "held" is a local read, that a relay can forget a reservation with the connection open, and what a renewal and a refused renewal do.

## Review findings

**The libp2p mechanism, verified against the installed source rather than the handoff.** I read `@libp2p/circuit-relay-v2` 4.2.13 (`transport/reservation-store.js`, `transport/listener.js`, `server/reservation-store.js`, `utils.js`) — no yarn patch, so the installed copy is upstream — and every claim the implementation rests on holds:
- `getReservation` returns the live stored `Reservation`, so writing `expire` reaches the object the refresh-window check reads. `getExpirationMilliseconds(0n)` is about −1.76e12, so the "still connected and not expiring soon" early return cannot fire and the refresh happens.
- A refresh with the original connection still open does not remove the entry first, and the `existingReservation != null` branch skips the free-pending-slot check, so a `'discovered'` renewal cannot meet `HadEnoughRelaysError`. The circuit listener reassigns `listeningAddrs` in place, never through an empty state.
- **The "renewal does not clear the `relayFilter`" question the handoff flagged: confirmed dead code, not an omission.** On a failed request libp2p adds the peer to `relayFilter` and then calls `#removeReservation`, which pushes the freed slot id back for a `'discovered'` reservation and runs `#checkReservationCount` synchronously — and that resets the whole filter whenever a pending slot is outstanding. Every reservation this module creates is `'discovered'`, so the reset is as unconditional as the handoff read it. (A `'configured'` reservation would not reset it, but nothing here makes one.)
- **The immediate fall-through after a refused renewal really is immediate.** `#removeReservation` dispatches `relay:removed` before its first `await`, and the listener's handler drops its listening addrs synchronously, so the `reservationHeld()` re-check right after `renewOnce()` already sees the withdrawal. `getMultiaddrs()` reads through live, so the one-second `self:peer:update` debounce does not apply.
- **`occupyTheOnlySlot` reaches the relay's own refusal.** The server refuses on `reservations.size >= maxReservations` with no record for the asking peer, which is exactly the state the helper builds. The handoff's second deviation is sound, and folding `startFixedRelayWithTtl` back into `startFixedRelay` removed a near-duplicate node starter.

**Non-vacuity re-verified independently, not taken on trust.** With `renewalDue()` forced to `false`, both new specs fail on their own renewal `waitFor` (30 s each) and nothing earlier — `re-requests a reservation the relay forgot` and `re-drives when the relay refuses the renewal`. Probe reverted.

**Minor findings, all fixed in this pass:**
- `RelayReservationSupervisor.driving` was still documented as "True while a drive is in flight" and `retryAtMs` as `null` "while a drive is running". A renewal sets the same flag. Both doc lines now say so. No status regression behind it: `resolveRelayReservationState` checks live circuit addrs before `driving`, and a renewal leaves the address advertised, so a renewing node still reports `reserved`.
- `renewOnce` logged "Renewed the relay reservation" when the pass had asked **nobody** — every addr skipped because the store holds no reservation on it. That is reachable through `circuitMultiaddrsVia`'s fallback (any unparsable entry in `addrs` makes any circuit addr count as held), and a log claiming success is exactly how #64 hid in the first place. `renewHeldReservations` now returns `{ asked, failure }` and the three outcomes log apart.
- `docs/network/relay.md` → "What takes a circuit address away" enumerated **three** events; a refused renewal is a fourth, and the paragraph two above it already said so. Fixed, including the "none of the three" sentence below.
- The new bound was not recorded as a limit. "Limits and accepted tradeoffs" now carries **a reservation the relay forgot without closing the connection costs up to 5 minutes of reachability**, with why the interval is where it is and a revisit condition.
- Spec hygiene: `relayReservations`'s four-member shape was written out twice (annotation plus cast) — extracted to one `RelayServerReservations` interface. `startFixedRelay`'s `reservations === undefined ? {} : { reservations }` is unnecessary (libp2p's server store defaults `init = {}` and `??`s every field, and the repo does not set `exactOptionalPropertyTypes`) — simplified.
- The first renewal spec's comment claimed discovery stays out of it because "discovery cannot nominate a relay whose hop protocol the namespaced client never learned", which `forgetRelayProtocol`'s own measured note in the same file contradicts — the reservation request writes that protocol into the peer store. The real reason is that the client's store still holds its reservation, so `relay:not-enough-relays` never fires. Corrected, and it now says why this spec needs no `forgetRelayProtocol` while the refusal one does.

**Tests: nothing cut, nothing added.** The two new specs are the reproduction of #64 and of the refusal fall-through, both at the lowest layer that reproduces them (the defect lives between libp2p's store and the relay's record, so a fake store reproduces neither). The `getReservation` assertion added to `findCircuitRelayTransport (libp2p seam)` belongs there: that test exists to fail loudly on a libp2p layout move, and without it the optional member would silently revert the node to never renewing. The implementer's decision to add nothing for the clock arithmetic, the option plumbing or the state surface is right — the renewal specs run at `renewMs: 500` and exercise the clock, and `RelayReservationState` gained no case.

**No tickets filed.** Nothing met the filing bar: the renewal is the root-cause fix at the one site, and the remaining concerns the handoff raised are either dead code (the `relayFilter` clear, above) or already parked as comments at their sites.

**Tripwires: the handoff's two were checked and left in place, and I added none.** `renewOneReservation`'s NOTE on what an abandoned renewal at the deadline costs, and `renewRelayReservation`'s NOTE on why `beforeRedrive` does not run before a renewal, both read correctly against the libp2p source. Two things I examined and deliberately did **not** record, because each is already stated where a reader meets it: renewals share one pass deadline, so a second relay on the same pass can be reported as "did not complete" while its renewal is in fact still running (the NOTE above says what that costs, and a node can hold only one `'discovered'` reservation per bare `/p2p-circuit` listener, so the case is near-unreachable); and an addr naming no relay peer id is skipped by the pass, which has a comment at the site and is the case `circuitMultiaddrsVia` already documents as approximate.

**`StrandInstanceManager` passing no `renewMs` is not an omission.** The 5-minute default costs one RESERVE stream per strand per interval against a two-hour reservation lifetime, and the implement ticket listed per-strand tuning as a capability, not a requirement.
