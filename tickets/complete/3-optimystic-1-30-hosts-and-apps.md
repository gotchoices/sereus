# Complete: every host and app opens one node storage per scope

Third of five tickets adopting Optimystic 1.30.0. Implemented in `ticket(implement): optimystic-1-30-hosts-and-apps`, reviewed and amended in this pass. Tickets 1 and 2 are in `complete/`; tickets 4 (`@serfab/integration-tests`) and 5 (release notes and the board fold) were still in `implement/` when this pass ran.

## What landed

**cadre-cli.** `openNodeStorage` builds `StorageConfig.open` over one `fileNodeStorage` per scope directory under `storage.path`, or one `memoryNodeStorage()` per scope, memoized per scope by a shared `storagePerScope` helper, with the handle's `close()` closing each. The local interface is `NodeStorageHandle`, so `NodeStorage` in that file means only Optimystic's type. `storage.quotaBytes` became `storage.allotmentBytes` and `CADRE_STORAGE_QUOTA` became `CADRE_STORAGE_ALLOTMENT`, and the value is read for the first time — into `StorageConfig.allotmentBytes` on the file branch. The schema takes a positive integer (`positiveInteger`, new in `@serfab/config-check`), because Optimystic throws on an allotment of zero when the node is constructed. The four launcher files and the README moved with the rename.

**cadre-host and cadre-provider.** `buildChildConfig` maps the management API's `resources.storageQuotaBytes` onto the child's `storage.allotmentBytes`; `container-env.ts` emits `CADRE_STORAGE_ALLOTMENT`. Both API field names are unchanged. Both hosting documents now state what the figure bounds and, for the provider, that the Docker volume is the enforcement.

**cadre-rn.** `LevelDBEdgeStorage` opens one `levelDbNodeStorage(handle)` per scope: `nodeStorage(scope)` replaces `rawStorage(scope)`, `offlineJournal(scope)` returns that storage's own `kv`, and `close()` / `destroyScope()` close the `OpenNodeStorage` before the handle. `PhoneNodePlatform` gained `storageAllotmentBytes`, defaulting to cadre-core's `DEFAULT_DEVICE_STORAGE_ALLOTMENT_BYTES`.

**reference-app-web.** `openNodeStorage(key)` over `indexedDbNodeStorage(handle)` replaces `openStore`, memoized per key; `openJournal` returns that storage's `kv`; the `lazyRawStorage` proxy and the stated `durability` constant are gone, because the store is built after the handle is open and reports its own. No `allotmentBytes`, deliberately: IndexedDB reports the origin's estimate.

**reference-app-ns.** `ScopeDb` holds the handle and an `OpenNodeStorage` from `sqliteNodeStorage(db)`. The platform gained `offlineJournal(scope)` — so NativeScript now has an offline journal — and `allotmentBytes: DEFAULT_DEVICE_STORAGE_ALLOTMENT_BYTES`.

**Docs.** The three platform storage sections, the two hosting documents, `docs/cadre/node.md`'s record table, and the two documents that asserted something this change makes false (`docs/strands/writes.md` and `docs/platforms/reference-apps.md`).

A scan of every `scripts` entry in every workspace manifest found no other POSIX-only command, so this is a one-off, not a class: no ticket, and no check script worth adding for a single site.
- **`packages/config-check/README.md` did not list `positiveInteger`.** That line is the package's checker inventory and a README owns usage, so a checker missing from it is invisible to the next caller. Added beside `nonNegativeInteger`.

### The two deviations the handoff asked to have weighed — both kept

**1. The two retired-name entries stay.** The implement ticket said to "rename outright rather than accepting both", and neither entry accepts anything: `RETIRED_STORAGE_KEYS` in `schema.ts` and the `CADRE_STORAGE_QUOTA` entry in `env.ts` *refuse* the old name with a message naming the replacement. That is a migration error, not backward compatibility, and both files already carry the identical pattern for the identity key and `CADRE_IDENTITY_PROTOBUF`. Cutting them would leave an operator's existing `quotaBytes` with a bare "unknown key" and `CADRE_STORAGE_QUOTA` with no near-match suggestion (the edit distance to the new name is too large). Verified by hand against the built `dist`: `storage.quotaBytes` in a file is refused as `storage.quotaBytes is no longer supported — renamed to 'allotmentBytes', and now read: …`, attributed to the config file.

**2. A `memory` store still may not name an allotment.** Refusing the key rather than dropping it is what this validator exists for — its own module header says a key that is never read "would otherwise be ignored without a word". The handoff is right that passing it through would also work (`effectiveTotalBytes(allotment, undefined)` is the allotment), so this is a choice; the refusal is the better one, because an operator who sets a limit on a store that nothing measures has misunderstood something and should be told. The only future case the refusal could bite — a cheap test that drives a node to 0.95 of an allotment over memory storage — builds its config directly rather than through the CLI schema, so it costs nothing (and ticket 4 says the harness needs no allotment today). Both cross-field rules are now in one named `storageCrossFields` function, which is the right shape.

**3. `allotmentBytes` in `reference-app-rn/test/solo-founding.spec.ts` is right.** The handoff asked for a second opinion. The spec's premise is that it builds the node `cadre-phone.ts` builds; that node's allotment comes from `createPhoneNode` → `LevelDBEdgeStorage` → the edge node, and the spec calls `buildPhoneNodeConfig` directly, so without the explicit figure it would build a node that measures nothing — a node the app never builds. Keep it.

### Checked and found correct

- **The offline journal's key prefix did not move, on either platform that already had one.** This is the check that mattered most: a changed prefix would silently orphan transactions an existing phone or tab had been told were saved. cadre-rn's old `new LevelDBKVStore(db)` and the web's old `new IndexedDBKVStore(handle)` both took the default `'optimystic:txn:'`, and `levelDbNodeStorage` / `indexedDbNodeStorage` keep that default deliberately (both upstream factories say so in their own comments). Queued writes survive the upgrade.
- **Close ordering, all four platforms.** Node storage before the handle in cadre-rn's `close()` and `destroyScope()`, reference-app-ns's `closeScopeDb`, reference-app-web's `closeStores` and `deleteStore`, and the CLI's `close`. Each matches what the upstream factory's `close()` actually does (RN releases the read-cache pool claim, NS flushes pieces then kv then closes blocks, the web commits kv then blocks, files release a holder). A failure closing one is still logged and the rest still close, in all four.
- **One call per handle, where a second one throws.** Only `levelDbNodeStorage` refuses a second call over an open handle; `sqliteNodeStorage`, `indexedDbNodeStorage` and `fileNodeStorage` tolerate it (files by holder counting). The cadre-rn memo is the defence and now says so at the site, and `destroyScope` drops both map entries so a relaunch opens a fresh handle and calls the factory again. The RN spec's own memo carries the same reason.
- **No first-ask race in any of the four memos.** Every platform factory is synchronous, and every memo sets its map entry in the same tick as the call, so two concurrent first asks for one scope cannot both open. The web's happens after one `await`, which its comment states.
- **The CLI's `restartIntoClaimedParty` path.** It stops the node, closes the storage handle and then reuses the handle for the claimed party's node. Correct with the memo: `close()` clears the map, so the next `open` opens afresh — a released file holder reopens the directory, and a memory scope starts empty (as it did before this change, where the provider minted a fresh store per call). The two parties' scope keys differ anyway.
- **The four new config behaviours, run against the built `dist`.** `quotaBytes` in a file → refused naming `allotmentBytes`; `allotmentBytes: 0` → "must be a whole number above zero, got 0"; `type: memory` with `allotmentBytes` in the file → refused naming the file; and the case the handoff had not exercised — `type: memory` in the file with `CADRE_STORAGE_ALLOTMENT` in the environment → refused and attributed to `Environment variable CADRE_STORAGE_ALLOTMENT`, not to the generated file. That last one matters for the Docker image, whose `entrypoint.sh` writes `type: ${CADRE_STORAGE_TYPE:-file}` and the allotment into one generated config: an operator who sets `CADRE_STORAGE_TYPE=memory` and an allotment together is refused by name, which `docker/env.example` now documents. `docker-compose.yml`'s `CADRE_STORAGE_ALLOTMENT=${CADRE_STORAGE_ALLOTMENT:-}` is safe because empty values count as unset (`specifiedEnv`).
- **`cadre-host`'s mapping of a zero or fractional `storageQuotaBytes`.** The provider's request validator accepts any finite number and `cadre-host` passes it through with `!== undefined`, so `0` would now reach a child as `allotmentBytes: 0` and fail that child's config load, where before it was accepted and ignored. Not reachable and not worth guarding: `HostedNodeService.spawnRequestFor` never sets `resources` at all, and `container-env.ts` drops a falsy quota. Negative and fractional figures were already refused by `nonNegativeInteger` before this change.
- **Diagnostics on the browser.** `getStoreStorage` now returns the node storage's `blocks`, which `indexedDbNodeStorage` constructs as a real `IndexedDBRawStorage`, so `diagnostics.svelte.ts`'s `instanceof` label and the e2e expectation of the string `IndexedDBRawStorage` still hold. (The e2e suite itself was not run — it needs a browser.)
- **Nothing else in the repository still speaks the old contract.** `rawStorage`, `storageProvider`, `storage.provider`, `RawStorageProvider`, `lazyRawStorage`, `quotaBytes` and `CADRE_STORAGE_QUOTA` appear only in `@serfab/integration-tests` (ticket 4), in two retired-name entries that refuse them, and in prose that is about the old name. No doc code block calls the old API — the failure mode `backlog/debt-doc-examples-that-call-the-api-are-executed` was filed for after ticket 2.
- **The documents, against the code.** Read every file this change touched and the ones it should have: the three platform storage sections, the two hosting statements, `writes.md`'s journal section (three per-platform stores collapsed to one rule, and the NativeScript limit withdrawn in both places it appeared), `node.md`'s record table, `node-storage.md` (ticket 2's, still accurate for this one), the cadre-cli README's env table and new allotment paragraph, `example.cadre.yaml`, `env.example`, and the cadre-rn README's option table and database table. Four stale statements found, all listed above as fixed. `reference-app-web/test/global-setup.ts`'s reason for listing `@optimystic/db-p2p-storage-web` was re-checked against `node-local-slots.ts` and is still true.
- **Source hygiene.** The largest touched file is 315 lines (`config-check/src/checkers.ts`); nothing is near a size concern. The comments added are dense but each carries a why, a constraint or a non-obvious consequence (one call per handle, why the memo exists, why close goes in that order) rather than narrating statements, which is this repository's house style. `storagePerScope` and `storageCrossFields` are both extractions of exactly the kind this stage asks for.
- **DRY across the four per-scope memos** (CLI, cadre-rn, reference-app-ns via `SharedOpen`, reference-app-web, plus the RN spec's). Considered hoisting one helper and declined: the handle types, the open's synchrony, the destroy path and the close ordering differ at every site, a shared helper would have to be generic over all four, and it would put platform plumbing in `cadre-core/edge-node`. Each site is about eight lines. Not filed and not tripwired — if a fifth platform arrives, the comparison is worth redoing.
- **reference-app-ns's `SharedOpen.take()` with one more caller** (the review focus the handoff named). `offlineJournal` awaits the same shared open the block store does, so it inherits the existing `NOTE:` on `take`: a caller holding the handle across a close hits a closed handle. No new exposure — the edge node stops its strands, and with them the offline queue that holds the journal, before `EdgeNodeStorage.close`. The `scopes` map is still not pruned by `close` or `destroyScope`; that leaves one empty `SharedOpen` per scope name and a later ask correctly reopens, so it is not a defect.
- **Behaviour changes the handoff flagged, all three agreed with.** The CLI's memory branch is now memoized (a stop/start or `stopStrand` inside one node's lifetime reads back what the scope wrote); NativeScript strands now get an offline queue object in `'online'` mode, which also populates a commit's `awaitedMachines` and registers `cohortReachability` there; and a hosted node's and a tenant's storage limit now does something. The first is what the ticket asked for and what `close` needs; the second follows from `buildEdgeNodeConfig` keying `strandOffline` off the journal's presence, with `initialMode` `'online'` so writes stay network-acknowledged; the third is the point of the ticket.
