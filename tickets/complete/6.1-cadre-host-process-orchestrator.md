## Summary

`HostProcessOrchestrator` (`@serfab/cadre-host`) implements the
`Orchestrator` interface from `@serfab/cadre-provider` against plain Node
child processes, no Docker. Per-container workdirs live under `rootDir`;
handles mirror to `<rootDir>/state.json` for restart re-attach. Child
identity is verified via a startup-token file written by the cadre-cli
child after `node.start()` succeeds, which protects against PID reuse.

Ports come from a configurable range allocator (default 10000..20000);
logs go through a sync-fd-backed size-rotator that doesn't race
`renameSync` on Windows. Stats are derived from `pidusage`; network
counters are hardcoded to zero (v1).

The cadre-cli `start` command got one new option, `--startup-token-file
<path>`, which writes `$CADRE_STARTUP_TOKEN` to disk after a healthy
`node.start()`. The cadre-cli `exports` map gained `./bin/cadre.js` and
`./package.json` so cadre-host can `createRequire(...).resolve(...)`
the cli bin.

## Review findings

### Build, tests, regressions

- `yarn workspace @serfab/cadre-host build` — clean.
- `yarn workspace @serfab/cadre-host test` — 14 passed, 1 skipped on
  Windows (SIGTERM-ignoring child — Windows always force-kills).
- `yarn workspace @serfab/cadre-provider test` — 10 passed (no
  regressions from the cadre-cli `exports` change).
- Full `yarn test` — all suites pass.
- No lint script exists for this package (none in repo at all); TS
  compilation acts as the type check and is clean.

### Interface conformance

- All six `Orchestrator` methods (`createContainer`, `stopContainer`,
  `removeContainer`, `getStats`, `isRunning`, `getLogs`) are implemented
  with matching signatures.
- The `dockerId` field is preserved per the implementer's intentional
  choice (no rename to `orchestratorHandle`).
- Generated child config matches `CliConfigFile` schema —
  `controlNetwork.{partyId,bootstrapNodes}`, `profile`,
  `strandFilter: 'all'`, optional `storage: { type: 'file', path,
  quotaBytes }`. `parseStrandFilter('all')` accepts the string form.
  `privateKey` is optional in `ResolvedConfig`, so omitting it is fine
  (the child generates a fresh keypair).
- `CADRE_LISTEN_ADDRS` is wired through `ENV_MAPPINGS` →
  `network.listenAddrs`, so the spawn env actually drives libp2p
  listen addrs (verified in `packages/cadre-cli/src/config/types.ts:73`
  and `loader.ts:46-55`).

### Major findings (filed as new ticket)

**Children likely die when the orchestrator process restarts.** The
spawn uses `stdio: ['ignore', 'pipe', 'pipe']`, so the parent owns the
read end of the child's stdout/stderr pipes. When the orchestrator
process exits, the kernel closes those read fds; the next time the
child writes, POSIX sends SIGPIPE (default action: terminate). The
cadre-cli `start` handler installs `SIGTERM`/`SIGINT` handlers but no
`SIGPIPE` handler. On Windows the failure mode is less catastrophic
(silent log loss) but logs are still gone.

The existing "Restart recovery (init)" test does not exercise this:
both orchestrator instances live inside the same vitest process, so
the original pipes never close.

This defeats the documented purpose of `init()` and `listDeadHandles()`.
Filed as `tickets/fix/cadre-host-child-stdio-survives-orchestrator-restart.md`
with suggested fix (direct-fd stdio: `stdio: ['ignore', logFd, logFd]`
with rotation deferred to next spawn for v1).

### Minor findings (fixed inline)

- **Unused `nanoid` dep.** The implementer added `nanoid` to dependencies
  but the orchestrator uses `crypto.randomBytes(16).toString('hex')` for
  tokens. Removed from `packages/cadre-host/package.json` and regenerated
  the lock with `yarn install`. Build + tests still pass.
- **`StateStore.load()` silently swallowed parse errors.** A corrupt
  `state.json` leaks running children to the OS without an in-memory
  handle — that should be visible. Added a `debug('cadre:host:state-store')`
  log on both the JSON parse failure and the unexpected-shape branch.
  Behaviour (return empty state) unchanged.

### Minor findings (documented, not fixed)

- **`isRunning` token check is inconsistent with `init()`.** `init()`
  permanently marks `handle.alive = false` on token mismatch, but
  `isRunning` only updates `alive` based on PID liveness, not token
  match. The test relies on this — it tampers the token, observes
  `false`, then restores and observes `true`. Not broken, but a tiny
  inconsistency worth noting if anyone later relies on `alive` as
  authoritative.
- **`getStats` test brushes the default 5 s vitest timeout.** Saw
  `5002 ms` once on a clean run — the test passed but is one OS hiccup
  away from flake. Suggest raising the per-test timeout or doing the
  pidusage call concurrently with the warm-up wait.
- **`containerId` is not sanitized before being joined into the path.**
  `join(rootDir, containerId)` with a hostile `containerId` (e.g.
  `../foo` or `C:\absolute`) could escape the workdir. Caller is
  trusted today (cadre-provider supplies the ID), so this is defensive
  only.
- **Createcontainer doesn't await the child's token write.** The
  returned `dockerId` is only meaningful once the child has called
  `node.start()` _and_ written the token file. Callers must poll
  `isRunning(dockerId)` before using endpoints. The implementer flagged
  this in the handoff; consider a separate `waitForReady(dockerId,
  timeout)` helper in a follow-up.
- **No orchestrator-level `shutdown()`.** Consistent with the
  implementer's note. The next ticket that wires `init()` into the
  cadre-host process lifecycle should also install a stop hook that
  SIGTERMs every managed child.
- **`spawn.entrypoint` test override is in the public `HostProcessConfig`
  type.** Documented as test-only but technically part of the package's
  exported surface. Acceptable for v1; consider moving to a separate
  internal-only options object if/when public consumers appear.
- **Memory limit via `--max-old-space-size` is heap-only.** Doesn't
  cover ArrayBuffers, native modules' allocations, etc. v1 acceptable;
  ticket already acknowledges this.
- **`pipeWithRotation` uses `child.stdout.on('data', ...)` instead of
  `.pipe()`.** Doesn't honor backpressure if the log file is slow.
  Negligible for the v1 traffic profile (logging only).
- **`tailFile` is a hand-rolled tail.** Tested and correct, but is the
  kind of utility that wants library reuse if another package adds one.

### Items not checked (out of scope / deferred)

- **Real-cadre-cli integration test deferred** as the implementer noted.
  Unit tests cover orchestrator-side logic against a fake child; the
  cli-side `--startup-token-file` change is a single `writeFileSync`.
- **POSIX-only SIGTERM-ignoring test** skipped on Windows by design
  (Node forces signal name to a hard kill). CI on Linux/macOS will
  exercise it.
- **Cross-package `parseMemoryLimit` duplication** is intentional per
  the ticket — no shared home until a third caller appears.
