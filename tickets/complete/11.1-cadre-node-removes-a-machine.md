# Remove a machine from a cadre: complete

## What landed

Implemented in `ticket(implement): cadre-node-removes-a-machine`, reviewed here.

- **Three public calls on `CadreNode`**: `listMachines` (one `CadreMachine` per live `CadrePeer` row plus one per live `OwnerKey` whose key names a machine with no row), `planMachineRemoval` (the read-only `MachineRemovalPlan` behind an app's confirmation step: refusal by name, whether the owner key goes too, the rows the machine vouched, the invitations it could come back through, whether this node's own rows depend on it) and `removeMachine` (re-plan, refuse by name with `MachineRemovalRefusedError`, check the requested re-vouch against the plan before any write, re-vouch the kept dependents first, then one transaction).
- **`ControlDatabase.removeMachine`**: in one transaction the `CadrePeer`, `OwnerKey` and `DeviceToken` rows with a `Revocation` tombstone each, plus a withdrawal tombstone per live invitation named; every stamp read inside the locked body; rows whose stamp is already retired are skipped; every tombstone rides the committed-delete seam so a removal committed alone is re-issued on growth. `revouchOwnerKey` rebinds an owner row's voucher by delete-and-re-add under a fresh stamp in one transaction. `withdrawCadreInvite`'s body was factored into `signCadreInviteWithdrawals` so the removal files several withdrawals in one transaction.
- **Pure projections** in the new `machine-removal.ts` (`describeMachines`, `planMachineRemoval`, `revouchWithinPlan`), kept out of `cadre-node.ts`, which has a size-debt ticket. `peerIdFromEd25519PublicKeyB64` in `ed25519-key.ts` is the inverse of the existing peer-id-to-key helper.
- **Connections close on evidence**: every membership refresh ends by hanging up this node's control connections to any peer that a `CadrePeer` tombstone names and that has no live row; never self; a failed hang-up is retried by the next refresh. The refresh's tombstone read is shared between the anchor sync and the hang-up.
- **Docs**: `docs/architecture.md` gained "Removing a machine" (what one transaction removes and why, re-vouching first, the refusals and the partition limit, connection close on evidence, what removal does not do) and the `OwnerKey`, `CadrePeer`, "Deletes made while alone" and implementation-status entries link to it. `docs/cadre-host.md` "A host lost for good" names Remove in the reference app and `removeMachine`. `docs/api.md` lists neither `addOwner` nor `removeOwner`, the ticket's skip condition, so it was left alone.

## Deviations from the ticket, accepted in review

- **The peer re-vouch keeps `UpdatedAt`** rather than bumping it as the write-while-alone drain does. The owner branch of `CadrePeer.AuthorizedUpdate` has no `UpdatedAt` condition (read in `schemas/control.qsql`), and a bump would leave a self-published row's own signature unverifiable until its next heartbeat. The handoff called this "reasoned, not measured against replication"; it is measured: in the integration scenario the kept device's row was inserted by `authorizePeer` with a non-zero `UpdatedAt`, so the re-vouch took the keep path, and the pinning member read the row with `VouchOwner` = the remover by replication alone.
- **The plan lists `invitations` even when `machine` is null**; informational, and `removeMachine` writes nothing for a null machine.
- **`ControlDatabase.removeMachine` repeats the owner refusals** inside the locked body, as `deleteOwnerKey` does, so the database refuses an inconsistent set even when called below `CadreNode`.
- **`trusted` is false for self** and **`dependents.peers` excludes this node's own row** (reported as `ownDependency`), matching the membership predicate, which excludes self.

## Review findings

**Read.** The whole implement diff (17 files) before the handoff summary; then the code each new path composes: the `CadrePeer` update and delete rules and the `CadreInviteUsage` redemption rule in `schemas/control.qsql`, `deleteGuardedRow` / `execGuardedRemoval` / `execTombstone`, `queryStampId` and its retry contract, `queryOwnerKeyRows`, `listCadreInviteStatuses`, `mutateCadrePeer` and the write lock, `reauthorizeCadrePeer`, `noteControlWrite` / `noteGuardedDelete`, `hasAnchoredProof`, the membership connection gater, libp2p's `hangUp` and connection close path in `node_modules`.

**Correctness, happy path and edge cases, by reading and running.** The one-transaction removal signs every removal over the stamp read inside the lock, so two owners removing the same machine collide on the tombstone's primary key and the second fails whole. The owner-key arm re-checks self and last-owner inside the lock. An owner-only machine (no `CadrePeer` row) removes only its `OwnerKey` and withdraws its invitations. A machine already removed plans as `machine: null` and writes nothing. Invitations **issued by** the removed owner are not withdrawn and need not be: `CadreInviteUsage.Authorized` requires the issuer to be a live owner at redemption, so they die with the key (the schema comment says so). The re-vouch runs before the removal, and a re-vouch that names anything outside the plan's dependents is refused before any write (pinned by the unit spec). The hang-up never touches self, a re-added machine (tombstone plus live row) or a relay or bootstrap peer (no tombstone). On the removed machine's own refresh nothing is hung up, since the remover keeps its live row. The `CadrePeerRow` widening (four new columns) compiles across the tree, and the read-retry spec's SQL-prefix rigging still matches because the new columns were appended.

**Minor, fixed in this pass.**
- `ControlDatabase.signMachineRemovals` rebuilt the retired-stamp set from the whole tombstone list on every lookup (four times per call). Grouped once by table.
- The control-backfill spec's stubbed `CadrePeer` row carried six of the ten `CadrePeerRow` fields; completed so the fake is a whole row.
- The hang-up awaits a network close inside the membership listener, which runs under the control database's write lock. libp2p bounds each connection's close at its 1 s `connectionCloseTimeout`, so a silent peer holds local writes for at most that. Recorded as a `NOTE:` at the site in `hangUpRevokedControlPeers`: if several removed peers ever pile up, hang them up concurrently or after the listener returns.

**Major.** None. No finding reached the filing bar: nothing wrong is reachable now, and no class-level invariant is missing.

**Tripwires (recorded, not filed).**
- The hang-up under the write lock, above (`NOTE:` in `cadre-node.ts`).
- A removed machine's libp2p may redial; the gater admits it provisionally, the protocol guard refuses its streams, and the next refresh hangs it up again, so a removed node that keeps running reconnects at most once per refresh until it stops. The source of the loop is the removed node not knowing it was removed, which `node-learns-it-was-removed` (in `implement/`) and its embedder tickets own; no new ticket. The gater's own `NOTE:` already names a deny-list on positive revocation evidence as the strand enforcer's module, not the membership gater's.
- The implementer's tripwire stands: `hangUpRevokedControlPeers` makes the `Revocation` read the refresh's only one on a node whose anchor is empty and that holds a connection to a peer with no row (`NOTE:` at the site).
