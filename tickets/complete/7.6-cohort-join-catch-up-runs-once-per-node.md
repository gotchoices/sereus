# One cohort-join catch-up per node

## What landed

A node that arms Sereus's peer-join block catch-up (`PeerJoinBackfill`) is now built with `rebalance: { enabled: false }`. That switches off Optimystic's rebalance reaction, which only runs on storage-profile nodes (`arachnode.enableRingZulu`). Before, its growth arm pushed a joiner every block a second time, one request per block.

- **Strand node** (`strand-instance-manager.ts`): one `backfillArms` value drives both the node option and the arming condition.
- **Control node** (`cadre-node.ts`): `controlBackfillStorage()` is the one answer to "does the control catch-up arm". Both `buildControlNodeOptions` and `startControlBackfill` read it.
- **Inert-catch-up logging:** when `controlBackfill.enabled: false`, `startControlBackfill` now logs that the catch-up is inert. It used to return silently.
- **Measured** (`message-cost-accounting`, one run per column):
  - invite A→B `block-transfer`: 182 → 92, and the 90 `reason=rebalance` pushes are gone.
  - cadre M→A: 7 → 5.
  - cadre A→M and the strand case: unchanged.
  - The numbers are recorded in the scenario's MEASURED_ON comment.
- **Known gap**, filed as `fix/join-catch-up-skips-a-returning-peer`: a peer that leaves a cohort and comes back is no longer re-pushed what it missed. It gets missed writes through read repair, for the blocks it reads.

## Review findings

Checked against the implement diff (`ticket(implement): cohort-join-catch-up-runs-once-per-node`) and Optimystic's wiring in `../optimystic/packages/db-p2p/src/libp2p-node-base.ts` (read only).

- **Correctness of the option:**
  - `rebalance: { enabled: false }` switches off the monitor, the grown arm and the ring-shift coordinator together.
  - The under-replication drain and spread-on-churn are wired outside that gate, so they keep running.
  - Two costs follow, and both are stated in the code `NOTE:`s and the docs: the node stays at its bootstrap ring, and no block is marked reclaimable (`gcEligibleBlocks`). Nothing in Sereus reads either one (grep of `packages/` for `gcEligibleBlocks`, `ringShiftCoordinator` and `rebalanceMonitor`).
  - Optimystic's doc says the grown arm is "the only mechanism that ever creates a second copy" of a singly-held block. That holds only where the catch-up is off, and there the reaction stays on.
- **Agreement between the two sites:** each option site reads the same value as its arming site (`backfillArms`, `controlBackfillStorage()`), so the two cannot disagree. The `keyNetwork` check can only run after the node exists. It stays in the arming path, as the handoff notes; Optimystic always builds a `keyNetwork`.
- **Control-site claim (the implementer flagged it for review):** verified against `isControlNetworkMember`. It admits everyone while the authorized snapshot is empty, and bootstrap/relay peers outright. The growth arm could therefore push the whole control store to a non-member during cold start, which the catch-up deliberately never does. Turning the reaction off closes that path. That is a side benefit, not a regression. I reworded the comment so it states the rule (every growth target is a catch-up target, except the peers the catch-up withholds from) and not a list.
- **Docs (minor, fixed):**
  - The architecture sub-paragraph mixed the decision with its costs and was written as a story ("pushed ... reached a joiner twice"). I split it into "One join catch-up per node", which states the rule and its reason in the present tense, and a labelled "What switching the reaction off costs", following AGENTS.md's one-claim-per-item rule.
  - The cost paragraph now says what the drain still owes a returning peer: the writes whose cohort it was in. That makes clear that read repair covers only the remainder.
  - The strand comment was reworded the same way.
  - The fix ticket's `files:` header now points at the renamed paragraph.
  - The cost-accounting doc comment matches the handoff's table.
- **Known gap:** `fix/join-catch-up-skips-a-returning-peer` is properly filed (prereq on this ticket, sequence 7.65). It names the site (`PeerJoinBackfill`'s `done` set) and the trade it must weigh (re-pushing a returning writer's own offline commits). Nothing further to file.
- **Tests:** none added, none cut. The change is a configuration choice on two node builders. A spec pinning `options.rebalance` would only test wiring, and the measurement already covers the behaviour.
- **Error handling, resource cleanup, performance, type safety:** none of these are affected. The change adds no new resources, async paths or casts, and the conditional spread type-checks against `createLibp2pNode`'s options.
- **Tripwires:** none new. The existing `NOTE:`s at both option sites carry the revisit condition: report the catch-up's pushes to the rebalance monitor once `blocked/optimystic-embedder-cannot-report-block-holders` gives an API.
