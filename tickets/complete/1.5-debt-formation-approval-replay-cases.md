# Complete: adversarial cases for the one-redemption formation approval

Test-only ticket. No `src/` or `schemas/` file was changed by either the implement stage or
this review.

## Background

When a `FormationInvite` carries a `ValidationUrl`, a `FormationUsage` row is admitted only
if a key the party enrolled in `CadreControl.ValidationKey` signed a digest over five fields:

```
digest('CadreControl.FormationUsage', 'vouch', Token, UsageStampId, StrandId, PeerId, Disclosure)
```

`UsageStampId` is a single-use nonce the redeeming node mints *before* it asks the approver;
`PeerId` is the joining peer. Replay is refused by two independent mechanisms: a **verbatim**
re-presentation repeats the nonce and is refused by that column's `unique`; a re-presentation
under **any other** redemption changes a signed field and fails the `Authorized` CHECK.

## What the implement stage delivered

Six cases in a new `describe('one approval, one redemption (replay refusals)')`, a `sibling()`
helper, and an extension of the no-`ValidationUrl` case to assert the writer echoes back the
nonce that landed. Suite went 38 → 44 tests.

## What this review added

Final state: **47 tests** in the file, full `cadre-core` suite **67 files / 1038 passed /
1 skipped**.

## Review findings

### Checked and clean

- **Every one of the six delivered cases is sound.** Each arranges exactly one of the two
  refusal mechanisms to fire, and each `Authorized` case is followed by the same approval
  landing on its correct redemption, so the refusal is provably about the changed field.
  Re-derived the constraint logic from `schemas/control.qsql` → `FormationUsage.Authorized`
  rather than from the handoff summary; the reasoning holds.
- **The cross-strand case's use of an unbound invite is correct.** `Authorized`'s own-strand
  clause (`FI.StrandId = new.StrandId`) only constrains bound invites, so it genuinely cannot
  fire there and `StrandId` is the sole reason for the refusal — as the ticket claimed.
- **The race case's primary-key pin is correct and correctly narrow.** Confirmed both the PK
  and `Monotonic` are violated and that the engine reports the PK; the assertion is exact.
- **Docs are current.** Read every file the change touches and the ones describing the
  behaviour — `docs/api.md` (the digest and the "exactly one redemption" wording),
  `docs/architecture.md` (the `ValidationKey`, `Strand`, and `FormationUsage` rows). All three
  already describe the nonce, the joining peer, and the one-approval-one-row rule; the prereq
  ticket updated them. No doc edit was needed, and none was made.
- **Source hygiene.** The spec is 1269 → ~1400 lines, in line with its peers
  (`control-revocation-replay` 1366, `seed-bootstrap` 1423). Not flagged.
- **Lint, build, typecheck, full suite** all pass — see *Validation* below.

### Found and fixed in this pass (minor)

**Two of the five signed digest fields had no test that would notice their removal — and they
were the two this ticket exists for.** The delivered cases isolate `Token`, `StrandId`, and
`Disclosure` one field at a time, but not `PeerId` or `UsageStampId`:

- the cross-joiner case varies `PeerId` *and* the nonce together (it must — a spent approval
  needs a fresh nonce or `unique` answers first), so neither field is pinned by it;
- the verbatim case is answered by the `unique` column, not by the digest.

Consequence: deleting `PeerId` or `UsageStampId` from **both** sides of the digest (the SQL in
`control-schema.ts` and `formationVouchMessage` in `control-database.ts`) left all 44 tests
green. The `UsageStampId` case is the more serious of the two: without that field in the digest,
a holder of a spent approval mints a fresh nonce, changes nothing else, and redeems a second
time — `unique` never sees a duplicate. That is the exact attack the nonce design exists to
stop, and nothing tested it.

Fixed by adding two cases, each varying exactly one field:

- `refuses a spent approval re-presented under a FRESH nonce` — same token, strand, joiner and
  disclosure; only the nonce differs. Followed by a genuinely new sign-off landing as use #2,
  proving the refusal was about the spent approval and not about the invite being exhausted.
- `refuses an UNSPENT approval presented for a different joiner (PeerId alone)` — the approval
  never landed, so its nonce is still free and `PeerId` is the only field that differs. This is
  the strict single-field isolation the implement ticket flagged as the shape it could not
  reach on a spent approval.

**Both claims were verified by mutation, not by reasoning.** Dropping `PeerId` from both digest
definitions reddened exactly one test (the new `PeerId` case, 46 others green); dropping
`UsageStampId` reddened exactly one (the new fresh-nonce case). The mutations were reverted and
`packages/cadre-core/src/` confirmed byte-identical to HEAD (`git diff --quiet` clean, and the
`control-schema-drift` spec — which fails if `control-schema.ts` and `schemas/control.qsql`
diverge — passes in the final run).

**The consent-seating path had no approval coverage at all.** Every case in the block uses
`recordFormationUsage` against a pre-existing strand. `redeemInvitation` — the path a stranger
actually joins by, which seats the `Strand` row and its `FormationUsage` row in one transaction
— was never once exercised with a real approver sign-off. It mints its own `usageStampId` when
the caller supplies none (`control-database.ts:1036`), so a regression that stopped threading
the caller's nonce through would be invisible to every record-only case: the approver signs one
nonce and a different one reaches the digest. Added
`admits a CONSENT-SEATING redemption (redeemInvitation) under an approver sign-off`, asserting
the returned and stored nonce are the signed one and that the strand came into existence off
the back of that row. Only a landing case was added — a rejection there could not keep the
block's single-rejector discipline, since a failed `FormationUsage` insert rolls back the
`Strand` insert alongside it and either constraint could be the one reported. Noted in the
describe-block comment.

**Answered the parked question about pinning a foreign package's error text.** The implement
ticket asked the reviewer to decide whether the three `UNIQUE constraint failed: ...` string
matches wanted a shared helper. They did: added `expectUniqueViolation(write, ...columns)` to
`test/control-constraint-helpers.ts`, next to the existing `expectConstraintFailure`, and
converted all three call sites. The caveat that this wording is a storage-layer detail
(`optimystic-module.ts` → `uniqueConstraintMessage`, unqualified table name) now lives in one
place instead of being restated in the spec, and a reword is a single edit.

### Recorded as tripwires, not tickets

- The `UNIQUE constraint failed:` wording remains a dependency on a foreign package's error
  text. Nothing is wrong today and the schema has no equivalent named constraint to assert
  instead. Parked as the `NOTE:` on `expectUniqueViolation` in
  `test/control-constraint-helpers.ts`.
- The race case pins the `(Token, UseNumber)` primary-key collision rather than `Monotonic`,
  because the vtab enforces the key ahead of the deferred CHECK. Fine as long as that ordering
  holds; if it inverts, re-pin the one the engine emits rather than widening to accept both.
  Parked as the `NOTE:` on the replay describe block.
- The block shares one node and one database across all its cases and `usageCount()` counts the
  whole table, so assertions must stay `before` / `before + 1` deltas rather than absolutes.
  Parked in the same block comment; the three new cases follow that discipline.

### Found and deliberately NOT filed

- **Two-node convergence on the nonce.** `unique` is evaluated against locally visible rows, so
  unconverged nodes could each admit the same nonce. Already documented as a `NOTE:` on
  `FormationUsage.UsageStampId` in the schema, and unreachable from a single-node harness — no
  new ticket, since filing one would duplicate a known and already-recorded architectural gap.
- **No new `fix/`, `plan/`, or `backlog/` tickets were created by this review.** Every finding
  above was either a test gap fixable inline (which it was) or already tracked. The two
  out-of-scope items the implement ticket named remain open and unchanged, listed below.
