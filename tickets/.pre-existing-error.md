# Pre-existing failure: B never resolves C's signed `CadrePeer` address record

Surfaced by `3-debt-strand-replication-breadth-validate`, which ran the full suite for the
first time since the strand-breadth change landed. Not caused by that ticket — see "Why
pre-existing" below.

From the repo root:

```

```

Only `@serfab/integration-tests` failed (`vitest run --reporter=verbose`):
`2 failed | 34 passed (36)` test files, `1 failed | 163 passed | 6 skipped (170)` tests.

`quereus-plugin-sereus` 74+1 todo, `reference-app-*` 126, `check-dep-ranges` 9/9).

Deterministic: fails in the full suite, fails in a two-file run, and fails when the degraded

## Failing tests

   — the whole suite fails in `beforeAll` at line 406, so all 6 of its tests are skipped:

   ```

    ❯ waitUntil src/harness/wait-utils.ts:53:9
   ```

2. `packages/integration-tests/src/scenarios/control-cohort-three-node-isolation.integration.ts`
   — the second test fails after 48.9 s, in the shared `bootTrio` helper at line 314:

   ```
   FAIL  Control-cohort reconcile as sole connector (three nodes, no manual dial)
         > is load-bearing: without a reconcile pass B never reaches C, and one pass forms the link
   Error: Timeout waiting for B resolves C's signed CadrePeer address record after 45000ms
    ❯ bootTrio src/scenarios/control-cohort-three-node-isolation.integration.ts:314:2
    ❯ src/scenarios/control-cohort-three-node-isolation.integration.ts:375:27
   ```

   The first test in that file (`B automatically dials C once C's record replicates through A`)
   passes, so the same `bootTrio` succeeds once and then fails on the next fresh trio.

Both failures are the same gate: node C publishes its own `CadrePeer` row through owner A, and
node B polls `B.resolvePeerAddrs(cPeerId)` for 45 s waiting for that row to arrive and pass the
signed-record checks (publicKey ↔ peerId binding, self-signature, freshness, trust policy).

The comment already sitting above that poll in `control-cohort-three-node-isolation.ts:305-312`
predicted this exact recurrence and names the next step:

> NOTE: this poll timed out once, on the very first cold run of this scenario, and has resolved
> in milliseconds on every run since — no cause established. If it recurs, capture
> `DEBUG='sereus:cadre:node'` and check whether C's row reached B at all: a genuine A→B
> replication failure is a product bug and deserves its own ticket rather than a wider timeout
> here.

It has recurred, and it is no longer intermittent. Please do not widen the timeout — 45 s is
already generous for a three-node loopback party, and the sibling gates in the same helper
(C's outbound connection to A, C's `registerSelf()` returning `refreshed`) both pass in well
under it, so C's row IS reaching A. The suspect span is A→B control-DB replication of that row,
or B's `resolvePeerAddrs` rejecting a record it did receive.

## Why pre-existing

- Neither scenario creates a strand. `DEFAULT_STRAND_CLUSTER_SIZE` (the only product value this
  ticket's predecessor changed, 2 → 4) is applied solely by `resolveStrandClusterSize`, on the
  strand path. These two scenarios run control networks, whose breadth is the untouched
  `CONTROL_REPLICATION_BREADTH` (16). Their only mention of a strand is a `strandFilter` node
  config field.
- Neither scenario imports `src/harness/control-cohort.ts`, the one harness file that ticket
  touched.
- Everything else in commit `84e8146` under `src/` is comment-only (`git show HEAD --
  packages/cadre-core/src/*.ts packages/quereus-plugin-sereus/src/types.ts` is entirely docblock
  text).
- Neither file is listed in `tickets/.pre-existing-known.md`.

Last commits to touch the two scenarios: `a6bfb3c` / `67c5bbf` / `85ac667`
(`debt-control-write-availability-degraded-cohort-member`).
