# `cadre-node-owner-grant.spec.ts` — "a member redeeming locally while alone" is flaky, and now fails in isolation too

Seen during the review pass of `webrtc-address-ranks-below-the-relayed-one` (2026-11-21).

## Command

```
yarn workspace @serfab/cadre-core test                                  # whole package
yarn workspace @serfab/cadre-core test test/cadre-node-owner-grant.spec.ts   # the file alone
```

Run from the repo root; the package is `@serfab/cadre-core`.

## Failing test

`packages/cadre-core/test/cadre-node-owner-grant.spec.ts` → `CadreNode owner grants > a member redeeming locally while alone is refused by name, before the approval`

```
Error: Timed out waiting for the member to be alone
 ❯ pollUntil test/cadre-node-owner-grant.spec.ts:63:38
 ❯ test/cadre-node-owner-grant.spec.ts:200:5
```

In the isolated run the same file failed a second test as well, at line 204 — the redemption that the timed-out precondition was supposed to guarantee would be refused:

```
AssertionError: promise resolved "{ alreadyOwner: false, memberPeerId: null, ownerKey: 'D0bl…' }" instead of rejecting
 ❯ test/cadre-node-owner-grant.spec.ts:204:61
```

Both are the same cause: `pollUntil(() => getControlConnectionCount() === 0 && othersInControlCohort(member.node).length === 0, 'the member to be alone')` (line 200, 15 s) does not settle, so the node is not alone and `redeemOwnerGrant` is not refused with `OwnerKeyAddRefusedError / alone`.

## Why this is pre-existing, and what is new

`tickets/.pre-existing-known.md` already records this exact test and message as a **one-off** dated 2026-11-21, seen during the `relayed-connections-try-a-webrtc-upgrade` implement pass — i.e. before `ticket(implement): webrtc-address-ranks-below-the-relayed-one` landed. That record already ruled out the WebRTC upgrade service as the cause (the spec's nodes are built with no WebRTC transport, so the upgrade service never subscribes there).

It is not this ticket's work either: the review pass changed only comments, one schema column comment, `docs/network/relay.md`, and test prose plus one new unit test in `strand-wake-protocol.spec.ts`. The failing spec exercises FRET cohort settling after a joiner stops, and nothing in the implement commit or this review pass touches cohort membership or connection teardown.

**What the existing record does not cover:** it says the test "passed 1 of 1 alone". It no longer does. Four runs today, on the review-pass tree:

| run | scope | result |
|---|---|---|
| 1 | whole package | FAILED (line 200, timeout) |
| 2 | file alone | FAILED (lines 200 and 204) |
| 3 | file alone | passed (4/4) |
| 4 | whole package | passed (200 files, 2687 tests) |

So it is a genuine intermittent, reproducible without full-suite load, not a load-only artifact. The existing record's confirm protocol — "measure how long 'alone' takes to settle under full-suite load before raising the poll" — is the next step, and the isolated reproduction makes that measurement much cheaper than it was. Raising the 15 s poll is the obvious patch, but the record is explicit that the settling time should be measured first rather than guessed at, since a cohort that never sheds the stopped joiner is a different defect from one that is merely slow.
