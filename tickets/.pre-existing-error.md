## What the debug run shows (b5r)

The stalled write's transaction (`tx:mIIk…`) runs its pend phase twice, about 105 s each (`trx:phases … pend=105218ms (failed)`, then `pend=104949ms (failed)`), where the scenario expects one pend phase of about 84 s. Before each `pendMany`, the transactor re-sends the previous case's owed cancel (`cancel:owed-retry-short actionId=tx:YKX… answered=0 of 4`), whose write ("stalls past the response deadline") ended with `WARN: cancel after batched pend did not discharge`. Between the two phases the transaction coordinator re-reads its blocks and re-drives, so the first failure was classified as a retryable stale loss, not as the shortfall it reports. Run alone, the case has no owed cancel to meet and passes at 84 s.

## Why it is not `adopt-optimystic-1-19-0`'s

That ticket changes comments, docs, release notes and one other case's bound in this file (the silent-after-pend case, traced to 1.19.0's batched-commit fallback). The first failing run was made before any edit to this scenario file. The re-drive and the batched-pend cancel are Optimystic code (`NetworkTransactor.pendMany` / `cancelBatchedPend` in db-core, new in 1.19.0; the `TransactionCoordinator` re-drive). The linked `../optimystic` was past the `v1.19.0` tag (`f1f774ea`) in every run, by offline-sync tickets that change how a refused pend is classified, so whether published 1.19.0 shows the same re-drive has not been checked.
