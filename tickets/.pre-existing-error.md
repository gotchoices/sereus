# Pre-existing failure: the WebRTC dial-storm case reds only under full-suite load

## Command

From the repo root:

```
yarn test
```

Fails in `@serfab/cadre-core`. Reproduced directly with:

```
cd packages/cadre-core && npx vitest run test/control-database-offline-peers.spec.ts
```

— which **passes** (13/13, file duration 173 s). The failure needs the whole suite running
in parallel.

## Failing test

`packages/cadre-core/test/control-database-offline-peers.spec.ts`
→ `control database with known-but-offline peers (no listen addr, no bootstrap peers)`
→ `stress and transport shapes (transaction profile)`
→ **`a WebRTC reconcile pass grinding through dead dials cannot block a local read or write`**

```
Error: offline-peer control op reconcileControlCohort() (WebRTC storm pass) timed out after 90000ms
 ❯ Timeout.<anonymous> src/control-stream.ts:67:14
```

Two full-suite runs on 2026-08-18, same case, same wrapper:

| run | wrapper budget | case duration |
| --- | --- | --- |
| 1 | 90 s | timed out (file 216 s) |
| 2 | 150 s | timed out at 150.8 s (file 276 s) |

Run alone the same pass completes in 30–58 s.

## Why this is pre-existing

- The failing assertion is a **hang-detector wrapper around a libp2p dial storm**, not an
  assertion about anything the current ticket changed. The ticket
  (`wire-write-through-raw-storage-cache`) wraps `IRawStorage` in a read cache; it cannot
  affect WebRTC dial timing, and no other storage-related spec in the package moved.
- It was already failing before that ticket, at the then-current 60 s budget: the ticket's
  own implement handoff records the case "completed at ~60.4 s three runs straight" under a
  full parallel `yarn test` and widened the budget 60 s → 90 s for exactly this reason. That
  widening did not hold, and neither did this review's 150 s.
- The case's real subject — local reads/writes staying unblocked *during* the storm — passes
  every time; it is asserted separately at a tight 15 s per-operation budget, and it had
  already completed when the wrapper fired.

## Mechanism, as far as this pass could establish it

The spec's own comment names it: js-libp2p's per-dial timeout is ~10 s and **has no override
in db-p2p's libp2p config**, so the storm's duration is three sequential timer-driven
timeouts. Timers starve under vitest worker contention, so the pass stretches 3–5× when the
suite runs in parallel — an amount no fixed budget can track. The durable fixes are to make
the dial timeout injectable so the storm is deterministic, or to stop running this file
concurrently with the rest of the suite; both are outside this ticket.

## What this review changed at the site (and did not)

The shared `MULTI_RECONCILE_TIMEOUT_MS` was split so the two concerns stop sharing a number:
`MULTI_RECONCILE_TIMEOUT_MS` (90 s) now covers only the passes awaited *after* `stop()`, and
a new `STORM_PASS_TIMEOUT_MS` (150 s) covers the multi-sibling storms, sized just under the
enclosing 180 s `it()` timeout so it reads as a hang detector rather than a load probe. That
is documentation and shape, not a fix — the case still reds under full-suite load. **Nothing
was skipped, disabled, or loosened past that**; the test still runs and still fails honestly.
