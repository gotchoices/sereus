# Pre-existing failure: push-wake e2e replication-learned case dies on an OwnerKey block read

Surfaced while working `implement/wake-and-cohort-dials-mishandle-peer-address-lists`.

## Command

From the repo root:

```
yarn workspace @serfab/cadre-core build
yarn workspace @serfab/integration-tests test src/scenarios/push-wake-e2e.integration.ts
```

(The build is only there to satisfy the suite's stale-build guard; it is not part of the
reproduction.)

## Failing test

`packages/integration-tests/src/scenarios/push-wake-e2e.integration.ts`
→ `E2E push-wake over the control network`
→ `wakes a member whose authorization and address were learned by control-DB replication, not local seeding`

Fails during setup, ~1–1.4 s in. The other three cases in the file pass.

`claimed-elsewhere` is `@optimystic/db-p2p`'s `coordinator-repo.ts` classification for "a cohort
peer positively CLAIMED a revision that could not then be fetched" — i.e. a control-database
cross-node convergence failure while a deferred row constraint scans the `OwnerKey` table.

## Why this is pre-existing, not caused by the ticket's changes

Measured, not inferred. With the ticket's six modified `packages/cadre-core/src` files and the one
modified scenario file temporarily replaced by their `HEAD` (`ed5e23c`) contents and `cadre-core`
rebuilt from those, the same case fails with the **same** error and the same ~1.4 s timing
(3 passed / 1 failed). Restoring the ticket's changes and rebuilding, the file then passed 4/4.

The failure is also **intermittent and order-dependent**: the case passes reliably when run alone
(`-t "learned by control-DB replication"`), and the whole file passed 4/4 both before and after the
run of five consecutive whole-file failures. Nothing in the ticket's diff touches the `OwnerKey`
table, block replication, or the control-database read path — it changes multiaddr shape, one dial
loop's error reporting, and one dial loop's timeout budget.

## Existing record

`tickets/.pre-existing-known.md` already lists this exact test (line 112), attributed to
`control-db-cross-node-convergence-halted`. That ticket is now in `tickets/complete/`, so no
in-flight `fix/` or `blocked/` slug owns it, and the file's 2026-08-18 delta records `push-wake-e2e`
as passing in both full runs — so this is reported rather than folded into that entry. The recorded
fingerprint there is also slightly different (`collection default/OwnerKey holds committed revision
1, but its header block read as absent` vs `claimed-elsewhere` here), which may or may not be the
same root cause.
