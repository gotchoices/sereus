# Pre-existing failure: degraded-cohort stalled write re-driven after an owed cancel (found in `adopt-optimystic-1-19-0`)

## Command

```
yarn vitest run src/scenarios/control-write-degraded-cohort-member.integration.ts
```

Logs: `tickets/.logs/adopt-optimystic-1-19-0.it-b5.log` (plain run), `tickets/.logs/adopt-optimystic-1-19-0.it-b5r.log` (rerun with `DEBUG='sereus:cadre:control-db,optimystic:db-core:network-transactor,optimystic:db-core:trx:coordinator'`), `tickets/.logs/adopt-optimystic-1-19-0.degraded-rerun.log` (two cases only, wider debug).

## Failing test

`packages/integration-tests/src/scenarios/control-write-degraded-cohort-member.integration.ts` → "control writes with a connected-but-degraded cohort member (forced 3-peer cohort) > a control read answers locally while a write is stalled"

```
[abandoned-write A] [peer-insert] budget after 1/3 attempt(s) in 210281ms (inside a deliberately degraded window): Failed to get super-majority: 2/3 approvals (needed 3, 0 rejections)
 × ... a control read answers locally while a write is stalled 210286ms
Error: degraded-cohort control op stalled write settles timed out after 210000ms
 ❯ Timeout.<anonymous> src/scenarios/control-write-degraded-cohort-member.integration.ts:399:17
```

Failed in 2 of 2 whole-file runs on 2026-10-25 (210.28 s and 210.29 s). Passed in 1 run of the case alone (`-t "answers locally"`), at 84.4 s. The other stalled cases in the same runs ("fails with a named super-majority error when a member stalls past the response deadline", "does not queue a failed DELETE for re-replication") took 84 s each, as the scenario expects.

## What the debug run shows (b5r)

The stalled write's transaction (`tx:mIIk…`) runs its pend phase twice, about 105 s each (`trx:phases … pend=105218ms (failed)`, then `pend=104949ms (failed)`), where the scenario expects one pend phase of about 84 s (one pend round, three cancel rounds; `STALLED_WRITE_FAILURE_MS`). Before each `pendMany`, the transactor re-sends the previous case's owed cancel (`cancel:owed-retry-short actionId=tx:YKX… answered=0 of 4`), whose write ("stalls past the response deadline") ended with `WARN: cancel after batched pend did not discharge`. Between the two phases the transaction coordinator re-reads its blocks and re-drives, so the first failure was classified as a retryable stale loss, not as the shortfall it reports. Run alone, the case has no owed cancel to meet and passes at 84 s.

## Why it is not this ticket's

`adopt-optimystic-1-19-0` changes comments, docs, release notes and one other case's bound in this file (the silent-after-pend case, traced to 1.19.0's batched-commit fallback). The b5 run above was made before any edit to this scenario file, with the linked `../optimystic` build the previous tickets already ran. The re-drive and the batched-pend cancel are Optimystic code (`NetworkTransactor.pendMany` / `cancelBatchedPend` in db-core, new in 1.19.0; `TransactionCoordinator` re-drive). Note that the linked `../optimystic` was past the `v1.19.0` tag (`f1f774ea`) during these runs, by the offline-sync tickets `offline-sync-typed-promise-shortfall`, `offline-sync-typed-validity-rejection` and `offline-sync-commit-failure-classifier`, which change how a refused pend is classified; whether published 1.19.0 shows the same re-drive was not checked.

# Second failure: always-on cross-party join publishes the join before step 1 reads it

## Command

From `packages/integration-tests`:

```
yarn vitest run src/scenarios/strand-always-on-replica-hosts-cross-party-join.integration.ts
```

Logs: `tickets/.logs/adopt-optimystic-1-19-0.it-b10.log`, `.always-on.r{1,2}.log`, `.always-on.dbg{1,2}.log` (the `dbg` runs with `DEBUG='sereus:cadre:*'`; `dbg1` failed, `dbg2` passed).

## Failing test

`packages/integration-tests/src/scenarios/strand-always-on-replica-hosts-cross-party-join.integration.ts` → "Always-on machine hosts a strand joined from another party > launches a replica from the party-wide join and stops it when the phone leaves"

```
AssertionError: join recorded on the phone: expected [] to deeply equal [ Array(1) ]
 ❯ src/scenarios/strand-always-on-replica-hosts-cross-party-join.integration.ts:297:102
```

Failed 3 of 5 runs on 2026-10-25 (the batch run, `r1`, `dbg1`); passed `r2` and `dbg2`.

## What the debug run shows (`dbg1`)

This is the shape the scenario's own NOTE before step 1 predicts. The always-on machine's boot-time `CadrePeer` write (`scheduleSelfRegistration`, 1 s after start) lost a race at 05:55:12.426 (`[self-record-update] failed transiently (attempt 1/3) … ConcurrentModificationError … CadrePeer`) and committed on attempt 2 at 13.089. That is after `enrollAlwaysOn`'s fixed `ALWAYS_ON_BOOT_WRITE_SETTLE_MS` (2 s) and after step 1 had begun (the phone remembered the join locally at 12.627). The replicated write fired the phone's gate watch (`refreshAuthorizedControlPeers(table-change)` at 13.079), and the reconcile pass it started published the join party-wide at 13.474–13.701 (`joined strand … published party-wide`, then `forgotten`), before step 1 read the phone's local join store. The scenario waits out the boot write with a fixed sleep, which does not cover a retried write.

## Why it is not this ticket's

`adopt-optimystic-1-19-0` does not touch this scenario or the code it drives (its diff is release notes, docs, comments, and one bound in `control-write-degraded-cohort-member`). Like the first failure above, these runs were against a linked `../optimystic` that was past `v1.19.0`, here at `7cf076af` with 8 uncommitted package files (its runner was mid-ticket; the stale-build guard passed because it had just rebuilt). Write timing in that tree may differ from published 1.19.0; whether the boot write's lost race is new there was not checked.
