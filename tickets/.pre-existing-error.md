# Pre-existing failure: the RN Maestro drone fixture never finishes starting

Found while working `implement/1.08-phone-and-web-kits-hold-a-separate-owner-key`, which edits the fixture's owner-key lines only.

## Command (from the repo root)

```
DRONE_WS_PORT=4702 DRONE_HTTP_PORT=4780 timeout 120 node packages/reference-app-rn/test-fixture/start.mjs
```

(Default ports are 4002/4080; other ports only avoid collisions. With `DEBUG='sereus:cadre:*'` the cause below shows.)

## What fails

`packages/reference-app-rn/test-fixture/start.mjs`, the drone that Maestro's `_setup.yaml` runs (`docs/reference-app-rn.md` → the Maestro section). It prints `Strand started: <id>` and then nothing for 120 s: never `Strand created`, `Bootstrap addr`, `HTTP sidecar`, `Test data` or `Drone fixture ready`, so no test-data file is written and every Maestro flow's setup would wait for nothing. Not part of any vitest suite.

Debug excerpt:

```
sereus:cadre:strand-first-sync [<id>] first-sync gate armed: no Strand.Header held yet; probing every 500ms
sereus:cadre:strand-manager Strand <id> launched as a joiner with no Strand.Header held yet — writes are withheld until a member of the strand is reached
  Strand started: <id>
sereus:cadre:node launchStrand: strand <id> already tracked locally — skipping re-launch
sereus:cadre:node Querying strands from control database   (every 5 s, forever)
```

Likely site: the fixture's `node.addStrand({ strandRow: { Id: strandId, MemberPrivateKey: null, Type: 'o' }, ... })` (~line 118). The row names no `FounderPeerId`, so the node is not its founder (`CadreNode.isSelfFoundedRow` reads `FounderPeerId` since `owner-key-label-and-founder-machine`), launches it as a joiner, and `addStrand` waits on a first sync no other member can ever give. `foundStrand` (which publishes the row naming this machine) is probably the fix.

## Why pre-existing

The fixture as committed at HEAD (`d33e271d`), run from a temporary copy beside it, stops at the same line. The 1.08 ticket changes only how the fixture makes its owner key (`createOwnerKey` over an in-memory store instead of random bytes); the strand lines are untouched.
