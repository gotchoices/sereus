# Pre-existing failure: `control-database-solo-warm-start.spec.ts` times out under full-suite load

Observed while reviewing `formation-unique-token-redesign` (review stage), 2026-08-12.

## Command

From `packages/cadre-core`:

```
yarn vitest run
```

## Failing tests

`packages/cadre-core/test/control-database-solo-warm-start.spec.ts`, describe
`control database, solo warm start on a prior cohort (no listen addr, no bootstrap peers)`.
**Which case fails varies run to run** — across three full-suite runs the failures were:

- run 2: `start() then addStrand() with REVOKED prior-cohort peers on disk`
- run 3: `start() then addStrand() with VANISHED prior-cohort peers on disk`
- run 4: both of the above

Error output (run 4, representative — the label varies with which operation was in flight):

```
FAIL  test/control-database-solo-warm-start.spec.ts > ... > start() then addStrand() with VANISHED prior-cohort peers on disk
Error: solo-warm-start control op first.start() timed out after 30000ms
 ❯ Timeout._onTimeout src/control-stream.ts:67:14
```

Run 2 produced the sibling shape: `solo-warm-start control op removePeer(EgLbTwit) timed out
after 15000ms`.

## Why this is pre-existing, not caused by the review's changes

- **The spec is untouched by this ticket.** `git status` for the review working tree lists
  `docs/STATUS.md`, `src/control-database.ts`, `src/control-schema.ts`,
  `test/control-formation-invite.spec.ts`, `test/control-formation-seat-budget.spec.ts`,
  `test/control-write-retry.spec.ts`,
  `packages/integration-tests/src/scenarios/control-db-two-node-convergence.integration.ts`,
  `schemas/control.qsql`, and one `tickets/` file. The failing spec is not among them, and
  nothing in the diff touches `CadreNode` startup, cohort seeding, or peer removal — the diff
  is confined to `FormationUsage` seat-budget enforcement plus comment/doc text.
- **It passes in isolation.** `yarn vitest run test/control-database-solo-warm-start.spec.ts`
  → 6 passed, 32.15s. That matches the figure `tickets/implement/port-solo-warm-start-to-published-smoke.md`
  records for the same spec ("Six cases, ~32 s").
- **The failure is wall-clock, not an assertion.** In the full 93-file suite the same 6 cases
  take **155s** instead of 32s — a ~5x slowdown from parallel worker load — against operation
  timeouts the spec hard-codes at 15s and 30s (`control-stream.ts`'s labelled-timeout helper).
  The timeouts appear to have been tuned on an unloaded machine.
- **One full-suite run at this same working-tree content was green** (93 files, 1503 passed,
  1 skipped), so it is nondeterministic rather than a deterministic break.

## Ownership

Not listed in `tickets/.pre-existing-known.md`. The spec landed three commits ago in
`c3b5744 ticket(fix): solo-warm-start-blocks-on-prior-cohort-peers`. The one open ticket that
names the file — `tickets/implement/port-solo-warm-start-to-published-smoke.md` — is about
porting the scenario into the published-install smoke script and does **not** cover this
timeout; it in fact asserts the spec is fast and stable.

The likely fix is to give the spec's control-op timeouts headroom proportional to suite load
(or to make them configurable / relative), not to change product code — but that judgement
belongs to triage, not to this review.
