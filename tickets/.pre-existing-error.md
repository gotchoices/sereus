# Pre-existing failure: `one-shot-node.spec.ts` refused by the file store lock

**Command** (from the repo root, after `yarn workspace @serfab/cadre-core build` and `yarn workspace @serfab/cadre-cli build`):

```
yarn workspace @serfab/cadre-cli test
```

**Failing tests** — `packages/cadre-cli/test/one-shot-node.spec.ts`:

- `one-shot commands against a real solo node > removes a seeded strand, and the row is gone from the control database afterwards`
- `one-shot commands against a real solo node > refuses a closed strand without --yes, exits 1, and leaves the membership key intact`

**Error excerpt** (the spawned `cadre strand remove` child's stderr):

```
Failed to remove strand: store at C:\Users\…\Temp\cadre-oneshot-remove-oTnRsi\blocks\control-636c…37 is open in process 59324 on Natelap6; a store is owned by one process at a time
```

Process 59324 is the vitest process itself: the spec's `seedStrands` boots a `CadreNode` over the same `FileRawStorage` directory in-process, stops it, then spawns the CLI over that directory.

**Why pre-existing.** The message is optimystic's `StoreLockedError` (`../optimystic/packages/db-p2p-storage-fs/src/store-lock.ts`, landed upstream 2026-10-15 in `file-storage-commits-groups-through-a-log`). The lock is removed only by `FileRawStorage.close()`, and `CadreNode.stop()` never calls `close()` on its raw storages (it disposes the cache wrapper, `disposeStorageCache`, only), so a stopped node's directory stays locked for as long as its process lives. Nothing in this ticket's diff touches storage lifecycle. The same CLI flow run with the seeding node in its own process (which exits, so its lock reads as stale) passes: `strand remove --yes` exits 0 and the row is gone, the closed-strand refusal exits 1, `validation-key add` exits 0.

Likely fix site: `CadreNode.cleanup()` (control storage) and `StrandInstanceManager`'s strand teardown should close the raw storages they opened, so a stop releases the directory.
