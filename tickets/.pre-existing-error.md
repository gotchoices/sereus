## Why this is pre-existing

The ticket's whole diff is prose: `.release-notes.pending.md`, `docs/schema-guide.md`'s limit line, and five backlog ticket files. It touches no code that replication, block transfer or this harness probe runs.

`tickets/.pre-existing-known.md` already carries a `one-off` entry for this same test, from the 2026-10-15 release gate at `daf68c82`: it failed once under the full suite (`Timeout waiting for P's new row on S reaches N in A after 90000ms`, `rowArrives` ~line 441), passed 3 of 3 alone at ~16 s, and the record's confirm protocol says that **if it recurs under load, measure how long the step actually takes in the full suite before raising the wait**. This is that recurrence, one step earlier in the same scenario: the block-coverage wait in `expectReplicaOnM` (60 s) rather than the row wait (90 s). What the record already ruled out: contention of the test's own making when run alone, and a too-tight deadline in the isolated case — alone the whole test finishes in 23.5 s, so the 60 s wait is generous there and the gap is in how long replication takes when 15 scenario files are competing for the machine.

Two concrete numbers for whoever picks this up: alone, 23.5 s for the whole test; under shard-4 load, the one wait at line 375 did not clear in 60 s and the test reached 82.8 s. The gap it printed is two blocks one revision behind (source rev 5, target rev 4), i.e. replication in progress rather than stalled — which is what makes "measure, then set the wait from the measurement" the right next step rather than a correctness hunt.
