# Pre-existing failure: `@serfab/integration-tests` typecheck vs upstream branded `RoutingKey`

Surfaced while validating `donation-scenario-phone-shaped-requester` (implement stage). This is a **typecheck** failure, not a test failure — every suite run during that ticket was green, because the breakage is type-only and has no runtime effect.

## Command

```
yarn typecheck          # repo root; fails only in @serfab/integration-tests
yarn workspace @serfab/integration-tests typecheck
```

Every other workspace's `typecheck` exits 0. The failing one exits 2.

## Failures

Three call sites, all in the integration-tests harness:

- `packages/integration-tests/src/harness/control-cohort.ts:139`
- `packages/integration-tests/src/harness/control-cohort.ts:277`
- `packages/integration-tests/src/harness/forced-cluster.ts:244`

```
error TS2345: Argument of type 'Uint8Array<ArrayBufferLike>' is not assignable to parameter of type 'RoutingKey'.
  Property '[routingKeyBrand]' is missing in type 'Uint8Array<ArrayBufferLike>' but required in type '{ readonly [routingKeyBrand]: true; }'.
```

All three are `keyNetwork.findCluster(<some Uint8Array>)` calls.

## Why this is pre-existing and not mine

- The three failing files are **not in this ticket's diff**. The ticket touched `packages/integration-tests/src/harness/node-fixtures.ts` (one added optional config field), added `packages/integration-tests/src/scenarios/cadre-host-donation-phone-requester.integration.ts`, and edited two docs files. Neither failing file was opened.
- `tsconfig.typecheck.json` includes `src/**/*.ts` unconditionally, so both files were already in the program before this ticket added anything — the errors are not newly *surfaced* by a new import.
- **Root cause is upstream, in the linked sibling workspace.** The root `package.json` resolves every `@optimystic/*` package with `link:../optimystic/packages/*`. That repo landed `ticket(implement): routing-key-single-encoding` (`1e3bfd96`, dated 2026-09-15 — the same day) which introduced `packages/db-core/src/network/routing-key.ts`:

  ```ts
  declare const routingKeyBrand: unique symbol;
  export type RoutingKey = Uint8Array & { readonly [routingKeyBrand]: true };
  ```

  and narrowed `findCluster`'s parameter to it. Sereus's harness still hands it a bare `Uint8Array`. `routing-key.ts` itself is unmodified in `../optimystic`'s working tree, so this is that repo's committed HEAD, not another runner's in-flight edit.
- Runtime is unaffected: branding is erased at compile time, which is why `cadre-host-donation-phone-requester.integration.ts` ran 4/4 green (and the deliberate falsification run went red for its own reason), and why no suite reports this.

## Note for triage

The fix is on this side — the three call sites need to produce a `RoutingKey` through whatever constructor `../optimystic`'s `routing-key.ts` exports, rather than a raw `Uint8Array`. Worth checking whether any non-test sereus code calls `findCluster` the same way; the repo-wide typecheck above says no, since only this workspace failed.
