- That ticket's trigger is a *manufactured* fork: a control-database write committed by a

  commit anywhere. So the "remove the trigger" mitigation would *not* make this go away.

## The invariant details, which may narrow it fast

Across every observed failure — nine of them, over five separate whole-file runs:

- The collection that cannot sync is **always a unique-index sub-collection**
  (`default/Member/index/_uniq_1` or `default/Manager/index/_uniq_2`), **never the data
  tree**. The data tree (`default/Member`, `default/Manager`) commits durably and is then
  reported as unrollbackable, so a failed run leaves the table's rows and its unique index
  out of sync on disk.
- The revision pair is **always "at rev 2, requested rev 1"** — never any other numbers.
  The client's committed-revision context is therefore sitting at 0 while the coordinator
  holds rev 2 for that block; the 10 retries never move it.
- The failing statement is always the **first founder-side write to that table after the
  joiner has attached the same strand** — `consumeInvite` (writes `Member`) in three tests,
  `addManager` (writes `Manager`) in the fifth.

That is a different shape from the blocked ticket's `default/CadrePeer at rev 9, requested
rev 9` (there the coordinator's rev *equals* the request; here it is two ahead), which is
why "same root cause" is stated as a likelihood, not a fact.

## Why this is pre-existing, not caused by the reporting ticket

- The only change in the reporting ticket's commit (`f487e37`) is additive, and entirely
  inside this one test file: three read-only scan helpers, one import, one new fifth test
  appended after the others, and header comments. The bodies of tests 1–4 are byte-identical
  to the parent commit's.
- **Directly verified**: the parent commit's version of the file was extracted with
  `git show f487e37^:<path>`, written to a scratch sibling file in the same directory, run,
  and observed failing the same way (`default/Member/index/_uniq_1 at rev 2, requested rev 1`
  in test 1). The scratch file was deleted afterwards; the working tree is clean.
- Nothing in the reporting ticket touches product code — the diff is one test file.
