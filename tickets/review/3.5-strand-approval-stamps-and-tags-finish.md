## What was built (unchanged from the implement handoff)

Every membership row in the `Strand` schema (`Member`, `MemberPeer`, `Manager`) carries a
`StampId` minted fresh per row incarnation. Every signed approval covers a digest leading
with the table name and the action, then the row's key fields, then the stamp. Deleting a
row requires filing a signed tombstone into a new `Strand.Revocation` table in the same
transaction, retiring the stamp permanently.

Signed-digest contract (each element is one variadic digest arg):

| Rule | Signed digest |
|---|---|
| Member add-by-manager | `'Strand.Member','add',new.Key,new.StampId` |
| Member remove-by-manager | `'Strand.Member','remove',old.Key,old.StampId` |
| Member self-departure | `'Strand.Member','leave',old.Key,old.StampId` |
| MemberPeer self register | `'Strand.MemberPeer','add',new.MemberKey,new.PeerId,new.StampId` |
| MemberPeer self remove | `'Strand.MemberPeer','remove',old.MemberKey,old.PeerId,old.StampId` |
| MemberPeer manager remove | `'Strand.MemberPeer','manager-remove',old.MemberKey,old.PeerId,old.StampId` |
| Manager promotion | `'Strand.Manager','add',new.MemberKey,new.Generation,new.StampId` |
| Manager self-resignation | `'Strand.Manager','resign',old.MemberKey,old.StampId` |
| Manager removal-by-another | `'Strand.Manager','remove',old.MemberKey,old.StampId` |
| Revocation tombstone | `'Strand.Revocation','retire',new.TableName,new.StampId` |

`Generation` must be signed as a NUMBER — the crypto plugin's digest framing is
type-tagged, so INTEGER `1` and TEXT `'1'` produce different digests.

## Review findings SO FAR (analysis complete; actions NOT yet applied)

### Adversarial pass on the schema — COMPLETE, no exploitable hole found

Attacks walked through and confirmed refused. Recorded so the finisher does not repeat them:

- **Cross-table stamp confusion.** `Revocation`'s primary key is `(TableName, StampId)` and
  every `NotRevoked` / `RowIsGone` branch filters on `TableName`, so a stamp retired for one
  table cannot affect another. An invite-joining member picks its own `StampId` and could
  deliberately reuse the *value* of a live `Manager` row's stamp — harmless for the same
  reason. Per-table `unique` blocks reuse within a table; `NotRevoked` blocks retired values.
- **Unused-approval replay after the signer loses authority.** A promotion approval signed by
  manager F and never used is dead once F's row is gone: the promotion branch reads live
  `Manager`, the member-add branch reads `committed.Manager`. Both fail.
- **Tombstone as an attack primitive.** `Revocation.Authorized` accepts *any* committed
  member's signature, so any member can file tombstones for arbitrary stamps. Bounded because
  (a) `RowIsGone` refuses to retire a stamp whose row is still visible, and (b) stamps are 256
  bits of CSPRNG output, so a not-yet-minted stamp cannot be guessed and pre-planted. Residual
  effect is table growth only — see the tripwires below.
- **Non-converged-node eviction.** Unlike the control layer, nothing on the strand read side
  filters rows whose stamp appears in `Revocation` (`NotRevoked` is insert-only), so a
  tombstone filed against a live-but-not-yet-converged row does not evict it. This is what
  keeps the control layer's remote-eviction hazard out of this schema — see tripwires.
- **Missed-seek deletes.** `revokeMember` / `leaveStrand` / `removeManager` delete via a
  single-column primary-key equality, which the optimystic module serves as a point lookup
  that can miss on a networked strand. A miss is NOT silent: the paired tombstone's
  `RowIsGone` sees the row still present and the commit fails loudly.

### Tripwires to record (conditional; NOT tickets)

Both belong as `NOTE:` comments on the `Revocation` table, **mirrored byte-identically** into
`schemas/strand.qsql` and `packages/quereus-plugin-sereus/src/strand-schema.ts`
(`strand-schema-drift.spec.ts` pins the identity). Note the table already carries one
convergence `NOTE:` above its declaration — these are additions, not replacements.

- Unbounded growth: one row per membership deletion, plus any junk any member chooses to file,
  and `Immutable` means rows never go away. Fine at strand scale; if membership churn ever
  gets large, it needs pruning bounded by something other than "forever". (The follow-up
  ticket `strand-approval-replay-pins` also asks for this NOTE — whichever pass lands it
  first, the other should skip it, and it must not be written twice.)
- No read-side stamp filtering: nothing drops a row because its stamp is retired, which is why
  a tombstone filed against a not-yet-converged live row is inert here. If a read path ever
  starts filtering on `Revocation` (as the control layer's `listAuthorizedMembers` does), that
  turns tombstone-filing into a remote eviction primitive and `Revocation.Authorized` would
  need narrowing from "any member" to "a manager, or the row's own owner".

- `RowIsGone` rejects retiring a stamp whose row is still live.

- `RevocationRecorded` rejects a delete that files no tombstone (currently only worked
  *around* by the specs' helper, never pinned as its own assertion).
