## What landed

The **server half** of peer-bound TURN issuance. The client half (web + React
Native signers wired into `loadIceConfig`) is ticket
`ice-config-peer-assertion-client` and has **not** landed — until it does, this code
is dormant behind `PEER_AUTH_MODE=off` (the default).

`ops/docker/turn-credential-issuer/` previously handed out coturn credentials to
anyone who passed an optional shared-token check and a per-IP rate limit, labelling
every credential with a fixed `CRED_ID`. It can now additionally require the caller
to prove control of a libp2p Ed25519 identity key, and label the credential with the
**derived peer id** instead.

### New module — `src/peer-assertion.ts`
Header parsing, the signed-message builder, verification, and the replay cache.

Wire format: five request headers on `GET /ice-servers.json` —
`X-Sereus-Peer-{Key,Aud,Ts,Nonce,Sig}` — carrying the base64url protobuf-encoded
Ed25519 public key, the audience the client signed, a unix-seconds timestamp, 32
lowercase hex chars of nonce, and a base64url signature. The signed message is five
LF-separated lines with no trailing newline:

```
sereus.turn-issuer.v1
<audience>
<peerId>
<issuedAtUnixSeconds>
<nonce>
```

The issuer **never trusts a client-supplied peer id** — it derives the id from the
presented key (`publicKey.toString()`, which is already the base58btc peer id) and
rebuilds the message with the derived value, so a mismatch fails the signature check.

### Reworked admission ladder — `src/main.ts`
`handleIceServers` was split into a pure, socket-free `decideIceServers` (plus
`decidePeerBound` / `admitVerifiedPeer`) returning `{status, body, headers}`, and a
thin HTTP wrapper. This is what makes the whole admission table testable without a
listener. `handleIceServers` / `handleRequest` are now `async`, and the
`createServer` callback's `try/catch` was replaced with a `.catch` (an async
rejection would otherwise have escaped as an unhandled rejection and hung the socket).

Deliberate ordering change from the previous code: the **per-IP limit now runs
before signature verification**, so an unauthenticated flood cannot burn Ed25519
verification CPU. The shared bearer token stays first (constant-time compare).

New env knobs (all defaulted so existing deployments are unchanged):
`PEER_AUTH_MODE` (`off`|`optional`|`required`, default `off`), `PEER_AUTH_AUDIENCE`,
`PEER_AUTH_SKEW_SECONDS` (default 60, clamped `[5, 300]`), `PEER_ALLOW_LIST`,
`PEER_DENY_LIST`, `RATE_LIMIT_PER_PEER_PER_MIN` (default 10), `REPLAY_CACHE_MAX`
(default 50000).

Manifest gains `peerAuth` (`"off"` | `"none"` | `"verified"`) and, when verified,
`peerId`. Both informational; clients read only `iceServers`.

### Packaging
`@libp2p/crypto` is now a runtime dependency, so the Dockerfile copies
`node_modules` into the runtime stage (it previously did not, on the grounds that
there were none). Every "dependency-free / Node built-ins only" claim was corrected
in `src/main.ts`, `ops/docker/README.md`, and the issuer README.

## How to validate

Both commands are network-free and agent-runnable. Run them from the repo root.

```bash
npm --prefix ops/docker/turn-credential-issuer install 2>&1 | tail -5
npm --prefix ops/docker/turn-credential-issuer run selftest 2>&1 | tee /tmp/issuer-selftest.log
node ops/test/check-turn-creds.mjs --self-test
```

Last run: **33/33 pass** (issuer self-test), **16/16 pass** (mirror test). The
`selftest` script runs `tsc` first, so it is also the type gate — `ops/` is outside
the yarn workspaces (`packages/*`), so root `yarn lint` / `yarn typecheck` do not
cover this code.

same values, so drift on either side fails a test rather than silently failing to

silently break attribution.

### Admission table (each row is a self-test case)

| `PEER_AUTH_MODE` | no assertion | valid assertion | invalid assertion |
|---|---|---|---|
| `off` | token + IP limit, `peerAuth: "off"` | headers ignored | headers ignored |
| `optional` | token + IP limit, `peerAuth: "none"` | peer-labelled TURN, `peerAuth: "verified"` | 400 / 401 |
| `required` | `200` STUN-only, `peerAuth: "none"` | peer-labelled TURN, `peerAuth: "verified"` | 400 / 401 |

Plus: deny list → `403 peer_denied` (before the per-peer bucket is touched); allow
list miss → `200` STUN-only with `peerAuth: "verified"`; per-peer limit → `429` +
`Retry-After: 60`; full replay cache → `503`; the TURN gating matrix
(`shouldEmitTurn`) still overrides everything.

`required` deliberately serves a STUN-only `200` rather than `401` to an
assertion-less caller, because `loadIceConfig()` turns a non-OK response into `[]`,
which would strip STUN too.

### Manual end-to-end check (already run once; reproduce if you want it)
The self-test drives `decideIceServers` directly, so the HTTP layer was checked by
hand rather than by an automated test. Booting with `PEER_AUTH_MODE=required` and
issuing a real signed request produced, in order: `200` STUN-only with
`peerAuth: "none"` for an unsigned caller; `204` on `OPTIONS` with all five headers
listed in `Access-Control-Allow-Headers`; `{"ok":true}` on `/healthz`; `400` for a
partial header set; `200` with `username: "<expiry>:12D3KooW…KPH5"` and
`peerAuth: "verified"` for the signed request; `401` for an immediate replay of it;
`401` for a timestamp 5000 s stale.

## Known gaps — please look here first

- **The HTTP layer has no automated test.** `handleIceServers`, `handleRequest`, the
  `.catch` on the `createServer` callback, and `main()`'s `process.exit(1)` on a
  fatal config error are covered only by the manual smoke run above. If you want a
  socket-level test, that is the obvious next increment.
- **The Docker image was never built.** No Docker in this environment. The new
  `COPY --from=build /app/node_modules ./node_modules` line and the runtime
  dependency are untested *in the image*. A `docker build ops/docker/turn-credential-issuer`
  is the one thing this change most wants and did not get.
- **No lock file**, matching `ops/docker/libp2p-infra/`. The Dockerfile's
  `npm install` resolves the `^` ranges at build time. Parked as a `NOTE:` in the
  Dockerfile.
- **Multi-replica is documented, not solved.** The replay cache and both rate
  limiters are per-process, so two replicas each admit a given replayed assertion
  once. Bounded by the per-peer limit and coturn's quotas; written up in the README
  next to the existing per-process rate-limit caveat.
- **Dormant until the client half lands.** Nothing in the repo sends these headers
  yet. `PEER_AUTH_MODE` defaults to `off`, so behaviour is byte-identical to before
  for every existing deployment — but that also means only the self-test has ever
  exercised the verified path against a real signer.

### Three deliberate deviations from the implement ticket
Each is a judgement call worth a second opinion:

- **A fifth outcome kind, `overloaded`.** The ticket's outcome union had four arms,
  but it also required a `503` when the replay cache is full. A fifth arm keeps the
  status mapping in one place rather than special-casing it in `main.ts`.
- **The nonce is *checked* before signature verification but only *recorded* after
  it succeeds.** The ticket's step order implied recording at the check. Recording
  after means a caller who cannot produce a valid signature can neither burn a
  legitimate nonce nor pollute the cache. Replay protection is unaffected: a valid
  assertion is recorded on its first success, so its replay hits the check. Pinned
  by the self-test case "an invalid signature does not burn the nonce".
- **A CR/LF in `PEER_AUTH_AUDIENCE` is a fatal boot error, not a warning** (as is
  `REPLAY_CACHE_MAX <= 0`). The ticket said "reject/warn". Such an audience can
  never equal a request header value, so every assertion would be rejected for a
  reason no operator would guess — crash-looping is the louder failure. Lives in
  `fatalConfigError`, called from `main()` after `logEffectiveConfig` so the config
  dump still prints.

Also: `@libp2p/interface` was added as an explicit dependency alongside
`@libp2p/crypto`. It is type-only, but `@libp2p/crypto/keys` does not re-export
`PublicKey` / `PrivateKey`, so relying on it transitively would have been fragile.

## Review findings (from implement)

- **Log volume per rejected assertion** — one `console.warn` per 401. The reason is
  a fixed constant (no client data echoed) and the per-IP limit bounds a single
  source, but a distributed flood scales log volume linearly. Parked as a `NOTE:` at
  the site in `src/main.ts` (`decidePeerBound`).
- **Allow/deny lists are scanned linearly per request.** Fine for the tens of
  entries an operator curates by hand. Parked as a `NOTE:` at the site in
  `src/main.ts` (`admitVerifiedPeer`).
- **No lock file / floating `^` ranges at image-build time.** Parked as a `NOTE:` in
  the Dockerfile.
- **Pre-existing, unrelated, filed separately:** `ops/test/README.md` documents
  `yarn workspace @serfab/ops-test check-turn-creds -- …`, but `ops/` is not in the
  root `workspaces` glob (`packages/*`), so that invocation fails. Confirmed by
  running it. Filed as `backlog/bug-ops-test-not-a-yarn-workspace`. Not touched
  here beyond the prose edit this ticket required.
