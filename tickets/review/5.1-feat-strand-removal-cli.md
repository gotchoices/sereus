# Review: `cadre strand list|remove`

## What landed

**`cadre strands` became a `cadre strand` group** with `list` and `remove` subcommands.
`.alias('strands')` on the parent keeps the documented invocation working — `cadre strands`
and `cadre strands remove <id>` both resolve. `list` behaves exactly as the old command did;
`printStrand` / `formatStrandJson` moved across untouched.

**`remove <strandId> [--yes]`** reads the `Strand` row, decides, then writes:

| Row state | `--yes` | Outcome |
|---|---|---|
| absent | either | no write, `• Strand not published — nothing to do`, **exit 0** |
| `Type='o'` (open) | either | `unpublishStrand`, exit 0, party-wide + delete-while-alone warnings |
| `Type='c'` (closed) | no | **refuses**, no write, **exit 1**, names the consequence |
| `Type='c'` (closed) | yes | `unpublishStrand`, exit 0, above warnings + "membership key gone" |

The decision is a pure exported `planRemove(row, strandId, { yes })`; `applyRemove(store, id,
opts)` trims the id, rejects blank, reads via the store, and writes only when the plan says to.
Both sit over a narrow `StrandStore` (`queryStrand` + `unpublishStrand`), so the whole chain is
testable without a node.

**Shared subcommand scaffolding was extracted** to a new
`packages/cadre-cli/src/commands/subcommand.ts`: `CommonOptions`, `PlanReport`,
`withCommonOptions`, `runSubcommand`, `reportPlan`. `validation-key.ts` now imports them
instead of holding its own copies. Two behavioural deltas in that shared code, both driven by
the refusal path:

- `runSubcommand`'s action may now return an **exit code**; falsy means 0. This is how a
  refusal exits non-zero while still printing a structured body, rather than being thrown and
  rendered as a `Failed to …:` line.
- `reportPlan` returns that code, and routes a **refusal's** human text to **stderr** while
  the `--json` body always goes to **stdout**. Non-refusal reporting is unchanged.

## How to exercise it

Everything below needs a `cadre.yaml` whose identity key is an **enrolled owner key** — these
are owner-signed control writes.

```bash
cadre strand list -c cadre.yaml            # unchanged output
cadre strands                              # alias still resolves to the group
cadre strand remove never-published-id     # → "nothing to do", exit 0
cadre strand remove <open-strand>          # → removed + warnings, exit 0
cadre strand remove <closed-strand>        # → REFUSED, exit 1, nothing written
cadre strand remove <closed-strand> --yes  # → removed, exit 0, key destroyed
cadre strand remove <closed-strand> --json # → structured refusal on stdout, exit 1
cadre strand remove "   "                  # → "A strand id is required", exit 1
cadre strand remove                        # → commander: missing required argument
```

Worth confirming by hand, since no automated test drives the real command:

- the exit codes above (the refusal's `1` in particular — it travels through the new
  action-returns-a-code path, not through the `catch`),
- that `--json` refusal output is parseable (`| jq`) and the process still exits non-zero,
- that a non-owner config fails with `Failed to remove strand: <node's own text>`,
- that `validation-key add|remove|list` still behave identically after the extraction.

## Known gaps — treat these as the starting point, not the finish line

- **Nothing drives the command against a real node.** `strand.spec.ts` covers `planRemove` /
  `applyRemove` over a fake store plus the commander wiring; `strand-unpublish.spec.ts` in
  cadre-core covers the node write. The seam between them — `nodeStore`, `withConnectedNode`,
  the `reportPlan` → exit-code path in `runSubcommand` — has **no test at all**. That includes
  the refusal's non-zero exit, which is the security-relevant half of this ticket.
- **`runSubcommand` / `reportPlan` are now shared with `validation-key` and have no direct
  tests.** `validation-key.spec.ts` tests its plan functions and its commander wiring, never
  the wrapper. A regression in the extraction would be silent in both suites. Worth reading
  the diff of `validation-key.ts` closely rather than trusting the green run.
- **`strand list --json` still prints `Connecting to control network...` to stdout,** so the
  output is not directly pipeable into a JSON parser. Pre-existing; the ticket froze `list`'s
  output, so it was kept verbatim with a `NOTE:` at the site
  (`strands.ts`, `listCommand`). One line to fix if the reviewer disagrees with keeping it.
- **"Not published" is read from this node's local replica.** Control reads are pull-on-read
  with no wait, so a one-shot node that has only just connected can miss a row that does exist
  in the party — and the command would report "nothing to do" and exit 0. Not silently
  swallowed: the absent branch now carries a warning saying the read was this node's view
  without waiting for sync. Whether exit 0 is still the right code for that case is a
  judgement call the reviewer may want to revisit.
- **`--yes` is not asked for on an open strand,** per the ticket's decision. An open strand's
  row carries no secret, but the removal is still party-wide and still subject to
  delete-while-alone. That is warned about, not gated.
- **No multi-node convergence coverage** for removal — already tracked as
  `backlog/debt-strand-unpublish-multi-node-convergence-test`, not re-filed here.

## Tripwires parked in code (not tickets)

- `strands.ts`, `applyRemove` — `NOTE:` the read and the write are not atomic; a concurrent
  removal in between makes this one a silent no-op. Harmless (the operator gets the outcome
  they asked for), so it is recorded rather than closed.
- `strands.ts`, `listCommand` — `NOTE:` the `Connecting to control network...` line lands on
  stdout even under `--json`.
- `subcommand.ts`, `runSubcommand` — the pre-existing repo-wide `NOTE:` that `process.exit`
  does not flush a pipe moved with the function; its list of affected commands was updated
  (`strands` → `strand`).
