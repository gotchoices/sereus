# Integration harness: owner keys separate from node identities (review)

## What was built

**The owner key type and generator** (`harness/owner-key.ts`, new, exported from the harness index):

- `TestOwnerKey` is `{ publicKey, privateKeyB64, signer }`. The public key is base64url, `privateKeyB64` is the 32-byte Ed25519 seed, and `signer` is a `softwareOwnerSigner` over it.
- `createTestOwnerKey()` builds one over random bytes (`generatePrivateKey` from the crypto plugin). No libp2p key is involved anywhere.
- `signMessageEd25519(message, privateKeyB64)` moved here from `test-network.ts`. It now takes the base64url seed instead of a libp2p protobuf. It stays synchronous, because the pair and topology fixtures hand it out as `ownerSign: (message) => string`.

**`makeOwnOwner(node, label?)`** (`node-fixtures.ts`) generates a key, inserts it as the genesis `OwnerKey` row under `label`, wires it with `useOwnerSigner`, and returns the `TestOwnerKey`. It no longer takes a libp2p key. As the sentinel the ticket asked for, it throws if the generated key equals `ed25519PublicKeyB64FromPeerId(node.peerId)`.

**Harness modules**

- **`TestParty`** (`types.ts`, `test-party.ts`). `ownerPrivateKey` and `ownerPublicKey` are replaced by `ownerKey: TestOwnerKey`. The owner node now gets a random libp2p identity like every other node. The "MUST adopt" comment, the protobuf slicing and `createTestNode`'s `privateKey` parameter (which had no other caller) are deleted.
- **`test-network.ts`** signs strands and invitations with `party.ownerKey`.
- **Pair fixtures** (`node-fixtures.ts`). `startPairNodes` returns `ownerKey?: TestOwnerKey`. `bootConnectedPair` keeps `ownerPublicKey` and `ownerSign`, both built from the generated key.
- **`buildPhoneOwner`** now returns the node alone. Its libp2p key had existed only to feed `makeOwnOwner`, and nothing read it any more.
- **`topology.ts`.** `ownerGenesis(owner, label)` returns the `TestOwnerKey`. The two boot paths now build their `TopologyParty` through one `partyOf` helper. The owner machine's libp2p key variable is renamed `ownerMachineKey`, so it is not mistaken for the owner key.
- **`control-trio.ts`** pins the generated key.
- **`cadre-invite.ts`**
  - `startPinningMember`'s `ownerCapable: boolean` is replaced by `ownerKey?: TestOwnerKey`, which is wired with `useOwnerSigner`.
  - New `ownerKeySeatedByInvitation(peerId)` returns the key behind a machine's peer id. An owner-granting `CadreInvite` still seats that key as an owner (cadre-core's interim rule; `docs/architecture.md` → "Invitation-granted owners"). The helper gives that one remaining identity-equals-owner case a single named site, which `owner-grant-separate-from-machine-invitation` can delete.
- **`fixtures/strand-restart-party.mjs`.** The child keeps its owner key in its `FileKeyStore`'s owner slot (`loadOwnerSigner(keyStore) ?? createOwnerKey(keyStore)`, then `useOwnerSigner`), beside its identity, as a phone does.
  - This differs from the ticket's wording ("pass the private half … as it passes the libp2p key today"). The parent never passed the libp2p key: the child loads its identity from its own store. The owner key now follows that same pattern.

**Scenarios** (41 files). `makeOwnOwner(X, xKey)` became `makeOwnOwner(X)` everywhere. Where a caller used the returned public key, it now reads `.publicKey`. The sites that needed judgment:

- **Restart re-wires use the kept key**, not one re-derived from the libp2p key:
  - `cadre-host-join-by-invitation`
  - `cadre-invite-any-member`
  - `control-delete-while-alone-convergence`: genesis now goes through `makeOwnOwner`, and the record is kept in `AloneRemoval.ownerKey`. This folds in `debt-harness-fold-own-owner-genesis`; its backlog file is deleted.
  - `control-offline-read-after-restart`: genesis goes through `makeOwnOwner`.
  - `pending-join-survives-restart`: `Machine` carries `ownerKey`.
- **Seed scenarios over `TestParty`** (`seed-bootstrap`, `enrollment-e2e`, `deliver-seed-cross-network`) use `party.ownerKey.signer`. Their three copies of `extractPrivateKeyBase64` are gone.
- **`push-wake-e2e`**
  - S, L and A had ephemeral identities and generated a libp2p key only to derive the owner key; those unused keys are dropped.
  - O keeps a stable identity key. Its pins (`trustOwnerKeys`) and the pollution seed service now use O's generated owner key.
  - `seedReceiverRecord`'s identity-binding check stays.
- **`owner-anchor-follows-owner-changes`**: B gets a generated owner key through `startPinningMember(…, { ownerKey })`, and A adds that key.
- **`control-concurrent-same-pk-insert`**
  - B's second owner key is now a generated key added with `pair.A.addOwner(...)`.
  - That replaces a hand-built `OwnerKey` insert, whose `NOTE:` claimed no cadre-core writer for a second owner existed. That has not been true since `addOwner`.
  - The founder check compares against each node's wired signer (`getOwnerSigner().publicKey`) instead of `getIdentityOwnerKey()`.
- **Owner-granting invitations** (the redeemer's identity key is the seated owner key):
  - `machine-removal` (B), `cadre-invite-any-member` (P), `cadre-invite-row-unreplicated` (P) and `strand-moves-between-cadres` (N in party A) use `ownerKeySeatedByInvitation`.
  - `app-joins-cadre-by-invitation`'s `ownerWriteReaches` now signs with whatever signer the device wired (`device.getOwnerSigner()`), so it no longer takes a libp2p key.
- **`strand-moves-between-cadres`, a changed assertion.** N's owner key in party B is now a generated key. Its owner key in party A is the identity key the targeted owner-granting invitation seats.
  - `expectSeatedOnce` asserts the adopted row's `FounderOwnerKey` is N's key **in A**, which is what adoption re-signs with (`strand-move.ts` → `publishStrand` with A's signer). Its comment, which said "the key that founded S in B", is rewritten.
  - Before this change the old assertion also matched the B key, but only because the two keys were the same.

**Docs**

- `docs/testing.md` has a new section, "Owner keys in integration scenarios": the generator, `makeOwnOwner` and its sentinel, keeping the key across a restart, second owner machines, the owner-granting-invitation exception, and why the identity-binding derivations stay.
- `docs/architecture.md` → Owner Keys status note: the test harness is taken off the list of embedders that still sign with an identity-derived key. The phone and web kits remain on it.

## Known gaps and judgment calls for the reviewer

- **The sentinel cannot trip today.** A random key equals a peer id's key with negligible probability. The sentinel exists only to catch a future edit that brings the derivation back into `makeOwnOwner`, as the ticket asked.
- **`ownerKeySeatedByInvitation` keeps four scenarios on identity-derived owner keys.** That is cadre-core's current rule for owner-granting invitations, not the harness's. Changing those scenarios to plain invitations plus `addOwner` would test a different flow, so they wait for `owner-grant-separate-from-machine-invitation`.
- **Two behaviour-adjacent changes beyond the key source:**
  - `control-concurrent-same-pk-insert` now seats B's owner key through the production `addOwner`, which refuses a write made while alone. The pair is connected with a confirmed two-machine cohort by then, and the file passed 3/3.
  - `push-wake-e2e`'s O now starts on a fresh random identity key rather than the key its owner key was derived from.
- **`StartedPairNodes.ownerKey`** is returned but no current caller reads it. It is kept because the field it replaced was equally unread.
- **The ticket's "one node key owns two cadres" edge case.** The only scenario of that shape is `strand-moves-between-cadres`. It now holds a different owner key in each cadre, and its assertion was corrected to match (above). No scenario needed one generated key shared across two parties.
