# Review: reap sweep — enumerate held tombstones, drop the rows they retire

## What landed

The prereq (`control-revocation-reap-authorization`) added the schema branch and the
single-row `ControlDatabase.reapRevokedRow(table, rowKey, stampId)`. Nothing called it.
This ticket added the enumeration and its scheduling.

**`ControlDatabase.reapRevokedRows(selfPeerId: string): Promise<number>`**
(`control-database.ts:~1528`) — scans `queryRevocations()`, early-returns 0 on an empty
table, and for each tombstone calls `reapRevokedRow`, skipping:

- tables outside `REAPABLE_TABLES` (`Strand`, `OwnerKey`) — silently, via a new
  `REAPABLE_TABLE_SET` / `isReapableTable` narrowing predicate next to `REAPABLE_TABLES`;
- this node's own `CadrePeer` / `DeviceToken` row (`rowKey === selfPeerId`).

Enumerates unlocked, deletes per-row locked (`reapRevokedRow` takes the non-re-entrant
write lock itself). Per-row teardown guard on `this.initialized` / `this.db` returns the
count so far. Carries the cost `NOTE:` tripwire.

**Wiring** (`cadre-node.ts:~1783`) — `selfPeerId` hoisted above the reap; the call sits
after `refreshDelegateGrants()` and **before** the sibling enumeration, gated on
`getControlConnectionCount() > 0`, wrapped in try/catch, with a `_running` / `controlNode` /
`controlDatabase` re-guard after it.

**Docs** — `docs/architecture.md:204` ("Delete-while-alone durability") rewritten: the reap
is now driven, the connectivity gate and why, the skip-self rule and why, `Strand` excluded,
retired-stamp read filters still load-bearing (for the pre-reap window everywhere, and
permanently for the excluded cases), the O(tombstones) cost note, and an explicit statement
that this does **not** close `forked-control-collection-sync-livelocks` — content
convergence is not revision convergence. The `Revocation` table row (line 41) lost its
"nothing drives it automatically yet" clause.

`docs/STATUS.md` was checked and **not** edited: its `Revocation` / `resolveDeviceToken`
notes (lines 237-244) only claim the retired-stamp read gate exists and is exercised, which
stays true — the read filters remain load-bearing after this change, not before it. Line 769
is a lint-exemption list and is unaffected.

## Deviation from the ticket, flag for review

The ticket's pseudocode had **no per-row try/catch**; the implementation adds one (logs and
continues). Rationale: a throw on tombstone *N* would otherwise abort the sweep and starve
every tombstone after it — on every subsequent pass, permanently, if the cause is not
transient. Each row is independent, and `reissueAuthoredMembershipRows` (the structural
model the ticket named) does exactly this. The node-level try/catch is still there as the
outer net. If the reviewer prefers fail-loud-per-pass, this is one block to delete.

The teardown guard reads `this.initialized` / `this.db` rather than a `_running` flag —
the method lives on `ControlDatabase`, which has no node lifecycle flag; those two are its
equivalent (`close()` clears `initialized`).

## Use cases to exercise

**The intended one.** Owner removes a peer while a sibling drone is offline. The drone comes
back, converges on the `Revocation` tombstone by ordinary replication but keeps the stale
`CadrePeer` row (replication cannot carry a delete of a row that is already gone on the
sender). Within one reconcile tick (~15 s) *while it holds a control connection*, the drone
drops the row. Before this ticket the row was permanent garbage — inert to every reader, but
never removed.

**The gate.** Same drone, but alone. Nothing happens, by design: a reap is a write, and a
write committed while alone is local-only and forks that node's own revision history — the
condition this whole line of work exists to stop creating. There is no urgency, since the
stale row already reads as absent.

**Self.** A revoked node keeps its own `CadrePeer` / `DeviceToken` row forever. Deliberate:
reaping it makes `registerSelf` / `retouchSelfDeviceToken` take the insert-if-absent path
every heartbeat, which needs an owner signature `NotRevoked` refuses for a retired stamp and
which a revoked drone cannot produce at all — recurring failure noise in exchange for
removing the one row nobody else reads from that node. "A revoked node should shut itself
down" is a different behaviour and its own ticket.

**Strand.** A party that unpublishes a strand accumulates `Strand` tombstones; those are the
common case, and the sweep skips them with no log line and no throw. Worth confirming the
silence — per-pass noise at a 15 s cadence is the failure mode here.

## Tests added

`control-revocation-reap.spec.ts` — a nested `describe` inside the existing
`RowIsGone`-stripped suite (the merge-only state a reap exists for is not locally
constructible against the real schema):

- reaps the row a matching tombstone retires (returns 1, row gone)
- skips this node's own `CadrePeer` **and** `DeviceToken` rows while reaping a sibling's in
  the same pass
- skips a `Strand` tombstone and keeps sweeping (the `CadrePeer` tombstone behind it is
  still reaped) — pins skip-and-continue, not skip-and-abort
- returns 0 with `reapRevokedRow` never called when `Revocation` is empty (spy)
- returns 0 when every tombstone names a row this node does not hold
- a row re-seated at a fresh stamp is left alone and does not abort the pass

`cadre-node-control-cohort.spec.ts` — `injectCohort` now stubs `reapRevokedRows` (recording
its `selfPeerId` argument, optionally throwing via a new `reapThrows` option), plus a new
`describe`:

- zero control connections → not called (**the gate**; a regression here silently
  reintroduces fork creation)
- ≥1 connection → called exactly once, with this node's own control peer id
- a cadre whose only sibling row is tombstoned (`listMembers()` returns none, pass takes the
  `dialColdStartBootstrap` early return) → still reaped — pins the before-step-1 placement
- a throwing reap does not abort the pass: sibling resolve + dial still run

## Known gaps — treat the tests as a floor

- **No live-network proof.** Deliberate, per the ticket: the one scenario that could carry
  it (`control-delete-while-alone-convergence.integration.ts`) dies in Phase 1 setup on
  `tickets/blocked/control-db-cross-node-convergence-halted.md`, so a new integration
  scenario would only join the pre-existing-failure ledger. Everything above is unit-level:
  the sweep is proven against a real `ControlDatabase` with a real schema, the scheduling
  against a stubbed one.
- **`close()` mid-sweep is untested.** The per-row `initialized` guard exists and returns
  the partial count, but forcing a close between two per-row reaps deterministically needs a
  seam the class does not expose. Read, not run.
- **Overlap with `drainPendingRevocations` is argued, not tested.** The growth drain
  re-issues tombstones while this consumes them; they touch different tables and both take
  the write lock per statement, so there is no shared mutable state. That is reasoning from
  the code (commented at the call site so nobody adds a mutex), not an executed interleaving.
- **Content convergence only.** This makes two nodes agree on *content*. Whether two
  histories that now agree on content reconcile at the storage-revision level is a question
  about optimystic `Collection` sync semantics — `forked-control-collection-sync-livelocks`
  and `strand-unique-index-sync-stale-revision`. Nothing here should be read as fixing the
  retry livelock.
- **The sweep re-walks every tombstone every ~15 s** while connected. Fine at cadre scale
  (`Revocation` rows are rare), and the empty-table early return makes the never-revoked
  party a single scan. Parked as a `NOTE:` tripwire on `reapRevokedRows` — if the table ever
  grows, persist a node-local high-water mark rather than re-scanning. Same shape as the
  existing `NOTE:` on `CadreNode.drainPendingRevocations`.
