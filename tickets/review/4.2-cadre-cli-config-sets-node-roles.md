# CLI config surface for node roles

`node-roles-in-cadre-core` landed `CadreNodeConfig.roles?: Partial<NodeRoles>` and `resolveNodeRoles`. This change gives cadre-cli the same surface and shows the result in `status`.

## What was built

**Config block.** `CliConfig.roles?: Partial<NodeRoles>`, checked by a new `objectOf<Block<'roles'>>` table in `schema.ts` with no required keys — `alwaysOn` and `strandCohortMember` as `booleanValue`, `overlayTier` as `oneOf<OverlayTier>`, `reactivity` as `oneOf<ReactivityRole>`. `roles` added to the root field table. Because `FieldTable<T>` is `{ [K in keyof T]-?: ... }`, a role cadre-core adds to `NodeRoles` without a checker here is a compile error, and a value cadre-core adds to either union stops `oneOf` compiling.

**Environment.** Four one-leaf mappings in `ENV_MAPPINGS`: `CADRE_ROLE_ALWAYS_ON` and `CADRE_ROLE_STRAND_COHORT_MEMBER` (`boolean` kind), `CADRE_ROLE_OVERLAY_TIER` and `CADRE_ROLE_REACTIVITY` (`string` kind). No new `EnvKind` was needed. One variable per role rather than a single JSON block, so overriding one role does not mean restating the other three and each leaf keeps its own attribution in the validator's report.

**Pass-through.** `roles: config.roles` at both construction sites — `buildNodeConfig` in `start-node.ts` (the long-running node) and `oneShotNodeConfig` in `node-session.ts` (`cadre enroll`, `cadre strand`, ...). The CLI does **not** duplicate cadre-core's `strandCohortMember: false` refusal; the schema accepts `false` and `CadreNode`'s constructor rejects it (message verified below).

**Status.** The **resolved** roles, not the overrides, in three places:

- `HealthServerOptions.roles?: NodeRoles | null` and `HealthStatus.node.roles: NodeRoles | null`. `start.ts`'s `startHealthServer` now takes `Pick<ResolvedConfig, 'nodeClass' | 'roles'>` in place of the bare `nodeClass: string` and calls `resolveNodeRoles` once, so both of its call sites (the removed-node branch and the normal one) pass `config`.
- `ConfigSummary.roles: NodeRoles`, resolved in `status.ts`'s `loadConfigSummary`.
- `RuntimeLive.roles: NodeRoles | null`, and a `Roles:` line under `Node class:` in both the Configuration and the Runtime (live) sections of the text report.

`resolveNodeRoles` is reached twice (health server, config summary) because `CadreNode` keeps its resolved roles private. See "Worth a look" below.

## Verified by hand

Against the built `dist`, with a config that overrides two of four roles on a `device`:

```
  Node class:      device
  Roles:           alwaysOn=true overlayTier=edge reactivity=subscriber strandCohortMember=true
```

`alwaysOn` and `reactivity` are the file's; `overlayTier` and `strandCohortMember` are the device presets — which is the point of showing the resolved set.

- `CADRE_ROLE_OVERLAY_TIER=edge CADRE_ROLE_ALWAYS_ON=false` on a `server` config with **no** `roles` block: `alwaysOn=false overlayTier=edge reactivity=forwarder strandCohortMember=true`. The dotted env path creates the absent block.
- `CADRE_ROLE_OVERLAY_TIER=fast`: `Environment variable CADRE_ROLE_OVERLAY_TIER: roles.overlayTier must be one of 'edge', 'core', got "fast"`.
- `CADRE_ROLE_OVERLAY_TEIR=edge`: `Unknown environment variable CADRE_ROLE_OVERLAY_TEIR (did you mean CADRE_ROLE_OVERLAY_TIER?)`.
- `roles: { strandCohortMember: false }` through `cadre start`: exits 1 with cadre-core's message, which names `roles.strandCohortMember` exactly as the config file spells it and points at `strandFilter`. No CLI-side duplicate needed.
- `/status` over HTTP from a `HealthServer` built with roles returns them in `node.roles`; one built without returns `node.roles: null`.

## Tests

| Test | What it verifies |
|---|---|
| `config-validation.spec.ts` → "accepts a roles block and carries it through to the resolved config" | A full `roles` block is accepted **and reaches `CliConfig`**. A checker that validated the block and returned nothing would silently leave the node on its class's presets; nothing else catches that. |
| `config-validation.spec.ts` → "rejects a misspelled role, naming the key and the role it probably meant" | `roles: { alwaysOne: true }` fails validation with the typo suggestion, so an operator hears it from the config report rather than from cadre-core after everything else was accepted. |

No test for the pass-through, the env mappings or the status formatting. The pass-through and the root field-table entry are compile-enforced; the env mechanism (dotted write, bad-value attribution, unknown-name suggestion) already has tests in this spec and in `env-names.spec.ts` for other variables, and repeating them per variable tests config-check rather than this change.

`test/status.spec.ts` fixtures gained `roles` because `HealthStatus.node.roles` and `ConfigSummary.roles` are required — that is the compile-time drift guard doing its job, not new coverage.

## Worth a look

- **Two `resolveNodeRoles` calls instead of one reading off the node.** `/status` would be strictly more truthful reading the live node's own resolved roles, but `CadreNode.roles` is private with no getter, and adding one is cadre-core work outside this ticket. The two CLI-side resolutions take the same two inputs `CadreNode` does, so they cannot disagree with it — but they are a second site, and a `CadreNode` getter would collapse both. Judgement call; reviewer may disagree.
- **`buildStatusReport` normalizes `s.node.roles ?? null`.** The ticket judged there to be no cross-build case ("the endpoint is in the same build"). That holds for one install, not for a `cadre status` run against a container node from an older image, so the two characters are there and `formatRoles` prints `(not reported)`. Not a compatibility layer — say so if it reads as scope creep.
- **`formatRoles` iterates `Object.entries`** rather than naming the four roles, so a role added to `NodeRoles` appears with no edit here. The cost is that the printed order is the resolved object's key order (and, for the runtime branch, the wire JSON's).
- **`start-node.ts`'s `hostUnclaimedStrands` NOTE** was left as-is. It still reads true — the field is still not surfaced in the CLI config — but `roles.alwaysOn` is now configurable and is what the default follows, so a reader may want that cross-reference. Deliberately not edited to avoid restating cadre-core's documented default.
- **`docker/entrypoint.sh` was not touched.** It generates a YAML file from a subset of `CADRE_*`, but the CLI applies env overrides itself, so `CADRE_ROLE_*` reaches a container node without an entrypoint change. Confirm that reading is right.
- **`cadre-host` and `cadre-provider`** still pass only a node class, per the ticket. `cadre-host` imports `HealthStatus` as a type and only casts the `/status` body, so the new required field compiles there untouched (full `yarn typecheck` confirms).
