# Provider seed trust: owner keys pinned at container-create time

## What was wrong

A "seed" is the signed bundle that tells a fresh node which peers form a cadre and how
to dial them; delivering one is how a tenant's node joins the tenant's cadre. The
provider could *deliver* a seed (`ContainerService.applySeed` → the container's
`POST /seed`, gated by a per-container bearer token) but no provider-hosted node ever
*accepted* one: whether a seed's contents are honoured is decided separately, by the
node's `SeedTrustPolicy`, against the node's own trusted-owner store — which is empty
on a fresh container and which nothing replicated can fill. Nothing pinned an owner
key, so every seed failed with `Signer key is not an anchored owner (anchored trust
policy)`. `OrchestratorCreateRequest.pinnedOwnerKeys` existed and was honoured by
cadre-host, but `DockerOrchestrator` dropped it and its doc comment claimed provider
tenants "pin owner trust through their own path" — that path did not exist.

## What changed

The tenant names its own owner key(s) on the create request; they reach the node as
`CADRE_OWNER_KEYS`, which `cadre-cli start` turns into a cold-start pinned-key trust
policy.

- `CreateContainerRequest.pinnedOwnerKeys?: string[]` (`types.ts`) — base64url ed25519
  owner public keys. Also recorded on the `Container` record (same field name) so a
  re-provision reuses them and an operator debugging a refused seed can see what the
  node was told to trust. Not redacted on the API boundary — public keys, not secrets.
- `POST /containers` (`routes.ts`) validates via `validatePinnedOwnerKeys`: absent, or
  an array of strings. Non-array or non-string element → `400 INVALID_REQUEST`, and no
  container is provisioned. Key *contents* are deliberately not validated (a malformed
  pin never matches a real signer and is refused by the trust policy — far better than a
  container that fails to start).
- `ContainerService.createContainer` copies the array onto the record (so a later
  caller mutation cannot rewrite it); `provisionContainer` forwards it into
  `OrchestratorCreateRequest.pinnedOwnerKeys` and logs when a container is created with
  none, so the eventual seed refusal traces back to the create call.
- `DockerOrchestrator.createContainer` injects `CADRE_OWNER_KEYS=<comma-joined>` when
  the list is non-empty and omits the var entirely otherwise.
- The stale `pinnedOwnerKeys` comment on `OrchestratorCreateRequest` now states that
  both orchestrators thread it as `CADRE_OWNER_KEYS` and that no orchestrator supplies
  a default.
- Docs: `docs/architecture.md` (Control Network Seed → after the delivery-mechanism
  table) now separates delivery from trust and states the create-time pin requirement;
  `docs/STATUS.md` (node-donation section) records the provider seed path as working
  end-to-end and names the remaining coverage gap; `packages/cadre-provider/README.md`
  gains a "Seed trust" section with a curl example.

**Isolation invariant to check hardest:** pinned keys flow only from one tenant's own
create request into that tenant's own container. There is no provider-level default
tier at all (unlike push credentials, which do have one) — a provider-wide pin would
let one tenant's owner seed another tenant's node.

New/extended tests:

- `service/__tests__/docker-orchestrator-push.test.ts` — extended the existing

  no trailing separator, var omitted when the field is absent, var omitted for `[]`.
- `service/__tests__/container-owner-keys.test.ts` (new) — keys recorded on the created
  container and in the store; caller-array mutation cannot rewrite the record; exact
  forwarding to the orchestrator; `pinnedOwnerKeys` undefined on the orchestrator
  request when the create request has none (no default); two tenants provisioned
  through one service instance each get only their own keys.
- `server/__tests__/create-container-owner-keys.test.ts` (new) — route accepts a list
  and echoes it on the created container; accepts absence; rejects a bare string and an
  array with a numeric element with `INVALID_REQUEST`; an invalid field provisions
  nothing.

## Known gaps — please probe these

- **No test exercises a real node's trust decision on the provider path.** Everything
  above asserts the provider *side*: the env var is built, the field is forwarded, the
  route validates. `__tests__/container-seed-endpoint.test.ts` still stubs `fetch`, so
  the end-to-end claim ("pinned key → node accepts the first seed → key anchors →
  later seeds need no pin") rests on cadre-host's equivalent path
  (`cadre-host/src/__tests__/orchestrator-pin-keys.test.ts` plus the node-donation
  integration scenario) using the same `CADRE_OWNER_KEYS` contract, not on a
  provider-specific integration test. A cross-package integration scenario (real
  container or a real `cadre-cli` child started with the provider's env) is the honest
  way to close this; judge whether it belongs as a follow-up ticket.
- **No re-provision path actually reads `Container.pinnedOwnerKeys` back.** The field
  is persisted for operator visibility and future re-provision, but today
  `provisionContainer` reads the keys from the in-flight `CreateContainerRequest`, not
  from the stored record. If a re-provision entry point is ever added that starts from
  the record alone, it must read this field — worth confirming there is no such caller
  today.
- **The empty-keys case is a log line, not a rejection.** Deliberate (per the ticket: a
  container may legitimately be created before its owner key is known), but it means a
  caller can still create a node that silently refuses every seed. Reviewer should
  decide whether the log (`debug` namespace `cadre:provider:container`, off by default)
  is discoverable enough, or whether the create response should carry a warning.
- **Whitespace/duplicate handling is left to the CLI.** The provider passes keys through
  verbatim; `collectPinnedOwnerKeys` in `cadre-cli` trims, drops empties, and dedupes.
  A request of `[""]` therefore yields `CADRE_OWNER_KEYS=` — non-empty list, so the var
  *is* injected — and the CLI parses it to `[]`, i.e. no policy, i.e. the node refuses
  seeds. Same end state as omitting the field, but reached by a different route; check
  whether that asymmetry is acceptable or should be normalized provider-side.
- `cadre-provider`'s `tsconfig.typecheck.json` excludes test files (pre-existing, tracked
  by `debt-widen-typecheck-to-test-files`), so the two new test files are type-checked
  only by vitest's transform, not by `yarn typecheck`.

## Manual/usage check

```bash
curl -X POST $URL/api/v1/containers -H 'Authorization: Bearer ...' \
  -d '{"partyId":"p","bootstrapNodes":["/ip4/.../tcp/4001/p2p/..."],
       "pinnedOwnerKeys":["<tenant-owner-b64url>"]}'
# → 201, container.pinnedOwnerKeys echoed back
docker inspect cadre-<containerId> --format '{{json .Config.Env}}' | tr ',' '\n' | grep CADRE_OWNER_KEYS
# → CADRE_OWNER_KEYS=<tenant-owner-b64url>
# then PUT /containers/:id/seed with a seed signed by that owner → accepted
```
