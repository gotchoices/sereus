# Review: a provision that never spawns no longer strands its working directory

## What changed

Two arms, exactly as the implement ticket specified. No scope was added or dropped.

### Arm 1 — `createContainer` removes a workdir its own failed spawn created

`HostProcessOrchestrator.createContainer` now samples `existsSync(workdir)` into
`isNewWorkdir` **before** `ensureNodeIdentity` (which creates the directory as a
side effect of writing `identity.key`), and the `try` was widened to cover the
identity step. `dropped` was hoisted to `let dropped: Handle[] = []`. The catch
gained a third statement: `if (isNewWorkdir) this.discardWorkdir(workdir)`.

New private `discardWorkdir(workdir)` — best-effort `rmSync` with
`maxRetries: 5, retryDelay: 100`, logged, never throws.

`ensureOwnerNode`'s catch is unchanged except for a comment saying why the
asymmetry is deliberate (`<rootDir>/owner` is one fixed path holding the host's
own control-DB storage).

### Arm 2 — reclaim by container name when no handle exists

New public `HostProcessOrchestrator.reclaimWorkdir(containerId): boolean`,
synchronous, with four refusals in order: `OWNER_CONTAINER_ID`; a containerId
that still resolves to a live handle; a path that does not start with
`rootDir + sep`; a directory that does not exist.

`DonationOrchestrator` gained optional `reclaimWorkdir?(containerId): boolean`
alongside `resolveDockerId?`. `DonationService` gained private
`safeReclaimWorkdir(id)` (swallow + log, matching `safeStop` / `safeReclaim`),
called from two places:

- `reclaimStuckProvisioning`'s `else` when `resolveDockerId` finds nothing;
- `terminate`'s `else` when the record names no `dockerId` — without this arm 2
  has a bypass, since terminating a stuck-`provisioning` record moves it to
  `terminated`, which `isStaleProvisioning` no longer matches.

### Docs

`docs/cadre-host.md` — the paragraph at "A respawn attempt that fails leaves the
host exactly as it found it" ended with a parenthetical pointing at
`backlog/debt-failed-provision-strands-workdir.md`, a file that no longer
exists. Replaced with the behaviour that now holds (first-spawn deletes,
re-spawn keeps, owner excluded, mid-spawn-crash covered by the two reclaim-by-name
call sites).

## Use cases to exercise when reviewing

The behaviour is a fork on one question — *did this spawn create the directory,
or find it?* — so the two directions are the whole review.

**Deletes (the leak this closes).**

- A first provision whose port allocation fails. `<rootDir>/<donationId>/`
  exists with an `identity.key` in it at the moment of the throw, and must not
  exist afterwards. Pinned by *discards the workdir a failed first spawn
  created* (`orchestrator.test.ts`), which sizes the range to exactly four ports
  so `c1` takes them all and `c2` fails at `allocateNodePorts`.
- Failures further in (`mkdirSync(storage)`, `writeFileSync(cadre.json)`,
  `openSync(node.log)`, `spawn`) are the same catch and the same outcome —
  covered by construction, not by four near-identical tests. Worth a reviewer's
  eye on whether that judgement holds.
- `ensureNodeIdentity` failing *part-way through* `generateIdentity` on a fresh
  directory. **Not directly tested** — see gaps below.

**Keeps (the case where deleting would be actively wrong).**

- A re-spawn whose launch fails. The surviving directory is the entire point: it
  holds the `identity.key` that makes the node come back as the peer the
  borrower's cadre approved, plus its node-local stores. *keeps the workdir when
  a re-spawn launch fails* asserts the directory and key survive **and** that the
  next successful spawn comes back on the same `peerId`.
- A pre-existing directory whose `identity.key` is undecodable. The widened
  `try` now catches this, and it must *not* delete — the operator needs to see
  it. *keeps a pre-existing workdir whose identity key is undecodable*.
- A launch that already spawned but whose `state.json` write failed. That write
  is deliberately best-effort so it never reaches the catch; the existing
  regression test now also asserts `identity.key` survives.
- `<rootDir>/<containerId>` existing as a plain **file**: `existsSync` is true,
  so nothing is deleted, `mkdirSync` throws, the error propagates. Deliberate —
  do not "fix" it into a delete. **Not tested** (see gaps).

**`reclaimWorkdir` refusals.** Four tests, one per refusal: live handle,
`OWNER_CONTAINER_ID`, missing directory, and an id that would escape `rootDir`
(`'../sibling'` — unreachable with real `grn_<base64url>` ids, so the guard is
defence; the test creates a real sibling directory and asserts it survives).

**Donation layer.** `reapStaleProvisioning` reclaims by name when no handle
resolves and does **not** when one does (`removeContainer` deletes that
directory itself). `terminate` likewise on both sides. `provision` whose
`createContainer` rejects makes **no** `reclaimWorkdir` call — arm 1 already
cleaned up inside the orchestrator.

`FakeOrchestrator` gained `reclaimWorkdir` recording into `reclaimedWorkdirs`,
refusing when a child for that containerId still resolves. Two contract tests in
`fake-orchestrator.test.ts` pin it, so a donation test cannot be made green by
relaxing the fake.

## Known gaps — treat the tests as a floor

- **No test for `ensureNodeIdentity` failing mid-`generateIdentity` on a fresh
  directory.** Inducing it portably means making `writeFileSync` fail after
  `mkdirSync` succeeded, which needs an fs-level stub the suite has no precedent
  for. The path is covered by inspection only: the directory is new, so
  `isNewWorkdir` is true and the partial directory is removed. A reviewer who
  wants this pinned would need to decide whether an fs stub is worth introducing
  here.
- **No test for `<rootDir>/<containerId>` existing as a plain file.** Reasoned,
  not executed: `existsSync` returns true for a file, so `isNewWorkdir` is false
  and the unwind deletes nothing; `mkdirSync` inside `ensureNodeIdentity` throws
  and propagates.
- **`discardWorkdir`'s retry count is a judgement call, not a measurement.**
  `removeContainer` uses `maxRetries: 20, retryDelay: 200` because it races the
  OS releasing a just-killed child's cwd handle on Windows; `discardWorkdir`
  uses `5 / 100` on the argument that no process ever attached to the directory
  it deletes. That argument rests on the `launchChild` throw-surface invariant
  (below), and the 5/100 figure itself was not measured against anything.
- **The `terminate` ↔ in-flight-`provision` race is documented at the call site,
  not closed.** `terminate` can delete the directory between a concurrent
  `createContainer`'s `mkdirSync` and its `spawn`, making that child fail to
  start noisily. Self-healing (`provisionLocked`'s post-spawn re-read reclaims
  the child anyway) and strictly better than the permanent strand, but it is a
  real interleaving, and it is **not** covered by a test.
- **The whole unwind rests on "a throw out of `launchChild` means no child is
  running."** That was established by the completed
  `debt-failed-respawn-strands-donated-workdir` ticket and is asserted only
  indirectly (by the state-write test). Arm 1 now depends on it for a *delete*
  rather than a port release, which raises the cost of it silently becoming
  false. The three invariants are commented in `createContainer`; whether
  comments are enough guard is a fair review question.
- **`safeReclaimWorkdir` swallows the return value.** Nothing branches on
  whether anything was actually removed, so a `reclaimWorkdir` that silently
  started returning `false` for real orphans would show up only in the debug log.

## Deliberately out of scope

- **`cadre-provider` is untouched.** Its `DockerOrchestrator.createContainer`
  already does this with its durable `/data` volume (`ensureVolume` returns
  `true` only when *that* call created it; the failure path runs
  `if (createdVolume) await this.removeVolume(...)`). This work makes cadre-host
  match that precedent — the plan ticket's question "does cadre-provider have the
  same hole" answers **no**.
- **`ensureOwnerNode`** — one fixed path, holds the host's own control-DB
  storage, does not grow without bound. Unchanged, with a comment saying so.
- **`DonationSupervisor.giveUp`** — verified unaffected, not assumed:
  `reconcileOne` returns early on a record with no `dockerId`, so every record
  `giveUp` sees names one, `terminate`'s new `else` never fires for them, and
  `giveUp` itself never calls `reclaimWorkdir`. Its deliberate keep-the-workdir
  behaviour (so the identity key the borrower's cadre approved survives) is
  intact.
- **No periodic directory sweep.** The plan ticket asked; the implement ticket
  ruled it out because `rootDir` also holds `state.json` and the admin's own
  `<rootDir>/owner/`, so a sweep would be a delete-by-inference over the
  directory holding the host owner's control-DB storage. Record-driven reclaim
  knows the exact id instead.
