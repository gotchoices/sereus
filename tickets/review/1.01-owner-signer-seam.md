# Owner signer seam, owner-key slot, and export/import: review handoff

First owner-key ticket (`docs/architecture.md` → Owner Keys). Purely additive in `@serfab/cadre-core`; `owner-signing-through-one-signer` wires these into the node. The code landed in two commits: the interrupted first run's salvage (`6101cf26`) and this pass, which added the docs, ran the full checks, and changed no code.

## What was built

**`owner-signer.ts`.** `OwnerSigner { publicKey; approve(request, body) }`, `OwnerSigningRequest { partyId, action }`, `OwnerSign = (message: Uint8Array) => Promise<string>`, `OwnerSigningDeclinedError` (carries the request), and `softwareOwnerSigner(privateKeyB64)`. The software backend validates the seed up front (new `requireEd25519PrivateKeyB64` in `ed25519-key.ts`, which canonicalises the base64url and never echoes the value). It signs `base64url(message)` with the crypto plugin's synchronous `sign`, which is what `SeedBootstrapService.signMessageBytes` does, so the signatures are byte-identical. `approve` just runs `body(sign)`, so a thrown body propagates and leaves no state behind.

**`owner-key-store.ts`.** `DEFAULT_OWNER_KEY_ID = 'cadre/owner'` (in `key-store.ts`, beside the identity id). The stored form is the libp2p protobuf of an Ed25519 private key.
- `createOwnerKey` refuses an occupied slot, including one holding unreadable bytes.
- `loadOwnerSigner` returns `undefined` only for an empty slot. Corrupt bytes throw, and a `KeyStoreAccessError` propagates.
- `importOwnerKey` changes nothing for the same key and refuses a different one with `OwnerKeySlotOccupiedError`. That error carries no key material.
- `readOwnerPrivateKey` is the read used for export.

**`owner-key-export.ts`.** `encodeOwnerKeyExport`, `decodeOwnerKeyExport` (`{ locked: false, privateKeyB64, publicKey, label? } | { locked: true }`), `unlockOwnerKeyExport`, and `OwnerKeyExportError` with `code` ∈ `malformed | wrong-passphrase | not-an-owner-key | cost-too-high`. Behaviour the ticket did not spell out:
- `decodeOwnerKeyExport` checks a locked envelope's shape and scrypt cost before answering `{ locked: true }`, so an app refuses a hostile file before it asks for the passphrase.
- `unlockOwnerKeyExport` also accepts plain text and ignores the passphrase.
- Text that starts `sereus-owner-key` with an unknown version is `malformed`, with a message saying "exported by a newer version".
- Machine join codes (`sereus-join:1.`) are refused by name too.
- Labels are trimmed, and a blank label is dropped. An empty passphrase is `malformed`.
- The passphrase is NFKC-normalised before scrypt.
- The salt (1–64 bytes), nonce (exactly 24) and sealed part (16–1024 bytes) have bounds.
- `JSON.parse` failures are rethrown without `cause`, because its message can quote the input, which may be the key.

**KDF numbers.** The encoder default is N = 2^16, r = 8, p = 1 (~140 ms and 64 MiB on Node 24, recorded at the constant). The decoder cap is N ≤ 2^20 and r·p ≤ 8 (~2.5 s and 1 GiB on Node 24). noble's `maxmem` is raised to exactly what the cap needs, because its default is a few KiB short of it. Hermes timing is unmeasured: there is a `NOTE:` at each constant.

**Cross-refusal.** `OWNER_KEY_EXPORT_STEM = 'sereus-owner-key'` lives in `cadre-join-request.ts` next to the other prefixes, so the invitation and join-request decoders can refuse it by name without importing the export module. The owner-key decoder refuses invitations, join requests and machine join codes by name.

**Dependency.** `@noble/ciphers ^2.0.1` is now a direct dependency of cadre-core (it resolves to 2.1.1, which was already installed through `@libp2p/noise`). Random bytes come from `@noble/hashes/utils` `randomBytes`, which is `crypto.getRandomValues`; `reference-app-rn` already polyfills that.

**Docs.** In `docs/architecture.md` → Owner Keys, the key-store bullet now names `importOwnerKey` and the never-replace rule. The export subsection names the functions, the 64-character label limit, the KDF default and cap, `wrong-passphrase` for altered text, and the refusal of join codes. Implementation Status has a new "Owner-key building blocks" bullet beside the KeyStore seam bullet; it is a separate bullet, per AGENTS.md's one-claim-per-item rule.

## Tests added (and what each pins)

- `test/owner-signer.spec.ts`: a `softwareOwnerSigner` signature over `buildAuthorizationMessage` output verifies with the plugin `verify` the schema uses, and `publicKey` matches the libp2p-derived key. This is the seam's byte contract.
- `test/owner-key-store.spec.ts`: one spec for the guard against losing a user's key. An empty slot loads as `undefined`. Create over an occupied slot refuses, importing the same key is a no-op, and importing a different key refuses; the stored bytes are unchanged afterwards. An exported seed imported into another store gives the same public key.
- `test/owner-key-export.spec.ts`, three specs:
  - Plain round trip with a trimmed label, and a 65-character label refused.
  - Locked: round trip, then refusals. A wrong passphrase, a flipped `sealed` and a flipped `nonce` are each `wrong-passphrase`. N = 2^21 is `cost-too-high` from both `decode` and `unlock`, and so is r·p = 16. The r·p case shows the bound fired before scrypt: run past the bound, scrypt would end in `wrong-passphrase` instead.
  - An invitation and a join request are refused by name.
- One added assertion each in `cadre-invite-protocol.spec.ts` and `cadre-join-request.spec.ts`: owner-key text is refused by name.

## Known gaps and things to look at

- **Hermes cost unmeasured.** The scrypt default (~140 ms on Node) and the cap (~2.5 s and 1 GiB on Node) have not been run on a phone. The 1 GiB allocation at the cap could fail on a low-memory device instead of just being slow. `NOTE:`s are at `DEFAULT_SCRYPT_COST` and `MAX_SCRYPT_N`.
- **No compare-and-set on the slot.** `createOwnerKey`/`importOwnerKey` check and then set, which `KeyStore` cannot do atomically. A `NOTE:` in the module header says to serialize if two owner-key actions can ever race.
- **The "before running scrypt" claim is tested only indirectly** (the r·p case above). Nothing instruments the KDF.
- **Untested by choice:** the machine-join-code refusal and the newer-version message in `decodeOwnerKeyExport`, the salt/nonce/sealed bounds, the corrupt-bytes throw in `loadOwnerSigner`, `KeyStoreAccessError` propagation, and `OwnerSigningDeclinedError` (no prompting backend exists yet). All were checked by reading the code.
- **New export:** `requireEd25519PrivateKeyB64` was added to `ed25519-key.ts` and the root exports. The later tickets (CLI `--owner` import, kits) are expected to use it.
- **Docs status note.** The "Status" note at the top of Owner Keys still says the code derives the owner key from the node identity. That remains true until `owner-signing-through-one-signer` lands, so it was left as is.
