# Rebuild the provider's port bookkeeping from Docker before handing out ports: review handoff

## What was wrong

`DockerOrchestrator` gives each tenant container three host ports (health, metrics, p2p) from `config.portRange` and tracks them in memory: `portAllocator` holds the used set, and `containerPorts` maps each Docker id to its ports. Both started empty in every process, but the containers outlive the provider (`RestartPolicy: unless-stopped`). After a restart, the first `createContainer` was offered the bottom of the range, which is exactly the ports the surviving containers are bound to. Removing a container created before the restart released nothing.

`repro: verified` means the new unit test fails without the fix (the create publishes 10000–10002, the survivor's ports) and passes with it. It was not run against a real Docker daemon.

## What changed

- **`docker-orchestrator.ts`**
  - `hostPortsOf(info)` is a pure module function. It reads `HostConfig.PortBindings["<in-container port>/tcp"][0].HostPort` for each key in `CONTAINER_PORT_KEYS`, which is the exact inverse of what `createContainer` writes. It reads from the inspect result rather than the list result's `Ports` field, because Docker fills `Ports` only for running containers. A key with no binding is left out.
  - `rehydratePorts()` runs `listContainers({ all: true, filters: { label: ['sereus.container-id'] } })`, inspects every listed container in parallel, then calls `reservePortSet` for each one and fills `containerPorts`. `all: true` includes stopped containers, because Docker gives a stopped container its bindings back when it restarts.
  - `ensurePortsRehydrated()` memoizes the pass once per process. If the pass rejects, the memo is cleared so the next call retries.
  - `createContainer` awaits the pass after the optional image pull and before `allocatePortSet`. If the pass fails, the create fails.
  - `removeContainer` awaits the pass before removing the container. This is best-effort: a failed pass is logged and the removal continues.
  - `inspectIfPresent(dockerId)` returns the inspect result, or `undefined` on a 404, and rethrows any other error. It was extracted from `inspectRunState`, which now uses it, and the pass uses it to skip a container that was removed between the list and the inspect. It also writes a debug log line on a 404, so `inspectRunState` now logs one too.
  - `containerPorts` now holds `Partial<ContainerHostPorts>`.
  - Reworded the comments on `durableVolumesOf`, `resolveDockerId` and the container-id label, which described the map as permanently empty after a restart.
- **`port-allocator.ts`**: `reservePortSet` and `releasePortSet` now take `Partial<Record<K, number>>` and skip keys with no port. Their doc comments already promised that behaviour. cadre-host still compiles unchanged, because a full `Record` is assignable to the partial one. The `PortAllocator` class doc now says where each orchestrator gets its ports back from after a restart.
- **`__tests__/fake-docker.ts`**: renamed `volumeStubs`/`VolumeStubs` to `daemonStubs`/`DaemonStubs`, since the stubs now cover more than volumes. Added a default `listContainers` that returns `[]`. All four test files that use the stubs were updated by the rename, with no other edits.
- **`docker-orchestrator-resolve-id.test.ts`**: updated only the header comment. Its `toHaveBeenCalledWith` assertion is untouched and still passes; it calls neither create nor remove.

## Test added

- `orchestrator-port-leak.test.ts` → "DockerOrchestrator port bookkeeping after a provider restart / reserves a surviving container's ports before allocating, and frees them when it is removed". The fake daemon lists one labelled container, `old-1`, bound to 10000/10001/10002, with a port range of 10000–10005.
  - The next `createContainer` must publish 10003–10005. This is the reproduction: without the fix it publishes 10000–10002, which I confirmed by temporarily removing the await.
  - The list call must use `all: true` and the bare label key.
  - `removeContainer('old-1')` must free 10000–10002.

## Known gaps / things for the reviewer to weigh

- **No real-daemon check.** A manual check would be: start the provider, create a container, restart the provider, create a second container, and confirm the second gets the next three ports and starts.
- **A narrow way ports can still be stranded.** Suppose `removeContainer` runs while the daemon cannot be reached, so its pass fails, is logged, and the memo is cleared. If a concurrent `createContainer` then starts a fresh pass that inspects the container before the removal completes but records it after the removal's release step, that container's ports stay reserved until the next provider restart. The result is a small leak, not a collision. It needs a daemon outage that ends partway through a removal, so I left it alone and did not add a `NOTE:` at the site. The reviewer should decide whether it deserves one.
- **Inspects run all at once.** The pass inspects every labelled container concurrently with `Promise.all`, with no limit. That is fine at today's scale; a provider with thousands of containers might want a limit on concurrent inspects. This is not measured.
- **Ports read back are not validated.** A malformed `HostPort` becomes `NaN` or `0`. `markUsed` ignores both, and releasing them does nothing. A port outside the configured range is ignored the same way, which is correct because `allocate()` can never hand it out.
- **Where the pass is triggered.** The pass runs lazily inside the orchestrator, not from `server.ts` at startup. `resolveDockerId` (used by the reaper) still asks the daemon directly, so a reap that runs before the first create or remove is unaffected.
- Did not touch `docs/`: no doc section covers provider port allocation, and `packages/cadre-provider/README.md` says nothing about ports across restarts.
