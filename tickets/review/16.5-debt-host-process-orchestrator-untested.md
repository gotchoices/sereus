# One shared handle-lifecycle contract, run against both the real and the fake orchestrator

## What this is

`HostProcessOrchestrator` starts a node as a child process and keeps a record of it, called a *handle*, keyed by a per-spawn id called `dockerId`. `FakeOrchestrator` is the hand-written stand-in the donated-node unit tests use instead; it starts no processes. Before this ticket each had its own tests for the handle rules, in separate code, so the two could come to disagree without any test failing.

## What was built

- **`packages/cadre-host/src/__tests__/orchestrator-handle-contract.ts` (new).** Exports `describeHandleContract(label, harness)`, which registers one `describe` block named `<label> handle contract` holding five cases written against a small harness interface. It is not a `.test.ts` file, so vitest does not collect it on its own (the package's `include` is `src/**/__tests__/**/*.test.ts`). It imports only `vitest`, a type from `@serfab/cadre-provider` and the *type* of `HostProcessOrchestrator` — no `node:fs`, no `FakeOrchestrator`.
- **`orchestrator.test.ts`** calls it with a harness over the real class. `sabotageWorkdir` was hoisted from the `failed launch` describe block to file scope (moved, not copied) so the harness can use it.
- **`fake-orchestrator.test.ts`** calls it with a harness over the fake. The case `drops only the re-spawned container, leaving another container untouched` was deleted because the contract covers it completely. Every other existing case stays: they also assert the fake's recording arrays and hooks.
- **Comments.** Header comments of `fake-orchestrator.ts` and `fake-orchestrator.test.ts` now say where the shared rules live. One `NOTE:` was added in the fake's `createContainer` (see "Known gaps").

No production code changed.

## Tests added, and what each verifies

All five are in `orchestrator-handle-contract.ts` and each runs twice (real and fake). Every rejection is checked against the whole message `Container not found: <dockerId>`, not a substring.

- `rejects a dockerId it never issued` — `stopContainer` and `removeContainer` both reject an id the orchestrator never handed out. On the real class this is the rule that was previously only checked incidentally (`getStats` after a remove).
- `rejects a dockerId once its container has been removed` — after a successful `removeContainer(id)`, a second `stopContainer(id)` and a second `removeContainer(id)` are both rejected.
- `replaces the first spawn's dockerId when the container re-spawns` — after create → stop → create of the same container, the first id is rejected by `stopContainer`, `resolveDockerId(containerId)` returns the second id, and the second spawn can be stopped.
- `leaves another container's dockerId alone when one container re-spawns` — re-spawning one container leaves a different container's id resolvable and stoppable.
- `keeps the first spawn's dockerId when the re-spawn fails` — after a re-spawn that throws, `resolveDockerId(containerId)` still returns the first id and `removeContainer` of it succeeds.

Net test count for the package: +10 contract runs, −1 deleted fake case.

## How to use it

To add a rule both classes must obey, add one `it` to `describeHandleContract`. It must use only `createContainer`, `stopContainer`, `removeContainer`, `resolveDockerId` and the harness, and must stop a container's first child before re-spawning it (use the local `respawn` helper).

## Differences from the ticket's design

- **The harness interface is generic** — `HandleContractHarness<O extends ContractOrchestrator>` — rather than typed on `ContractOrchestrator` directly. The real harness needs `isRunning` and `getNode`, and the fake harness needs `failCreate`; with the non-generic shape both would have needed a cast. `Pick<HostProcessOrchestrator, …>` accepts `FakeOrchestrator` structurally, so the `DonationOrchestrator` fallback was not needed.
- **The real harness finds the working directory through `orch.getNode(containerId)!.workdir`**, a public method, instead of the `(orch as unknown as { rootDir: string }).rootDir` cast the older cases in that file use.

## Known gaps — reviewer, please check these

- **The real class was not mutation-checked.** The ticket marks `host-process-orchestrator.ts` read-only, so I did not temporarily break it to watch the contract fail. The claim that the contract catches drift on the real side rests on the five cases passing against it and on reading the code, not on a demonstrated failure.
- **`failNextCreate` is broader on the fake than on the real class.** The fake's `failCreate = true` fails every later create for every container; the real harness fails creates for the one container only. No contract case creates again after calling it, and the harness doc comment says so, but a future case that does would behave differently on the two sides.
- **`started` on the real harness returns almost at once.** `isRunning` answers from the `ChildProcess` for a child this process spawned, so the contract stops children that may not have written their startup token yet. That is the intended meaning ("can be stopped"), and it passed repeatedly, but it means the contract does not exercise a fully started child.
- **Rules the two classes are known to disagree on are still outside the contract**, each recorded at the fake's code site as before: `getStats` / `getLogs` on an unknown id, the `reclaimWorkdir` return value for an already-deleted directory, and `removeContainer` on a still-running child. This ticket adds a fourth `NOTE:` of the same kind in the fake's `createContainer`: the real class refuses to re-spawn a container whose previous child is still alive, and the fake replaces it. The plan ticket stated that no donation caller re-spawns over a live child; I did not re-verify that claim against `donation-service.ts` and the supervisor.
- **The fake's `drops the prior handle when a re-spawn succeeds` case overlaps the contract's re-spawn case.** It was kept on the ticket's instruction because it also asserts the `stopped` array, and it re-spawns without stopping first, which the contract cannot do.
