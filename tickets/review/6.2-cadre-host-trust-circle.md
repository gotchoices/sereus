## What landed

`packages/cadre-host/src/auth/` is a new self-contained module exposing the trust-circle substrate consumed by `cadre-host-local-ui` and (later) `cadre-host-installer`.

- **`auth/types.ts`** — `TrustCircleMember`, `PendingInvite`, `TrustCircleFile` (on-disk shape), `TrustCircleSnapshot`, `TrustCircleHandlers` (HTTP handler contract), and `TrustCircleError` with stable codes (`not_found` / `expired` / `already_redeemed` / `invalid_label` / `invalid_token` / `storage_error`) that the UI ticket maps to HTTP statuses.
- **`auth/trust-circle-store.ts`** — atomic JSON store for `<rootDir>/trust-circle.json`. Pattern mirrors `orchestrator/state-store.ts`: write `<path>.tmp`, rename. Caches loaded state in memory. Throws `TrustCircleError('storage_error', …)` on malformed JSON or wrong shape rather than silently wiping (decision in ticket).
- **`auth/trust-circle.ts`** — `TrustCircleService` with `issueInvite`, `redeemInvite`, `revokePending`, `removeMember`, `isMember`, `list`. The service depends on a narrow `CadreNodeLike` interface (not the full `CadreNode`) so unit tests can mock cadre-core without standing up libp2p. Also exports `createTrustCircleHandlers(service)` returning the typed `TrustCircleHandlers`.
- **`auth/duration.ts`** — small duration parser (`24h`, `7d`, `30m`, etc.) for the CLI `--ttl` flag.
- **`auth/index.ts`** — re-exports for `src/index.ts` and `cadre-host-local-ui`.

CLI (`src/bin/host.ts`):

- `cadre-host invite <label> [--ttl 24h] [--port 8765]` — POSTs to `http://127.0.0.1:<port>/auth/invites`, prints the encoded invite, exits 0/1/2.
- `cadre-host trust list` — GETs `/auth/trust-circle`, prints members and pending.
- `cadre-host trust revoke <token-or-peerId>` — DELETEs `/auth/invites/<token>` (default) or `/auth/members/<peerId>` (auto-detects libp2p peer IDs by `12D3Koo`/`Qm` prefix, overridable with `--kind`).
- `install` / `start` / `status` / `uninstall` remain "not yet implemented" stubs, as documented in the README.

cadre-core additions (Phase 3 of the ticket):

- `SeedBootstrapService.removePeer(peerId)` — signs `digest(peerId, 'sha256', 'utf8')` with the authority key, executes a signed delete against `CadreControl.CadrePeer`. Matches the existing `authorizePeer` pattern.
- `CadreNode.removePeer(peerId)` — wrapper delegating to the service. Throws if seed bootstrap isn't initialised.

`src/index.ts` re-exports everything from `auth/`.

Docs: `docs/cadre-host.md` has a new "Trust circle" section; `README.md` now mentions the working `invite`/`trust` commands and what's still pending.

## Known gaps for the reviewer

Treat the implementation as a starting point — the tests are a floor, not a ceiling. Things to look at carefully:

1. **Redemption path is mocked, not exercised end-to-end.** `TrustCircleService.redeemInvite` calls `CadreNodeLike.acceptPhone`, but no test actually stands up a real `CadreNode` + control DB + signed `acceptPhone`. The plan ticket explicitly accepts this (Option A — wrap acceptPhone; no integration test here) but a reviewer might want to add one or call out the gap as a follow-up.
2. **`removePeer` SQL is not exercised against a real Quereus DB.** I wrote two unit tests (configuration checks) mirroring the existing `authorizePeer` tests, which similarly don't hit the real DB. The Quereus DELETE-with-context syntax (`delete from T with context K = v, … where …`) is per the SQL docs in `quereus/docs/sql.md` and the schema's constraint allows delete by an authority-signed `digest(old.PeerId)`. **If the reviewer can stand up a control DB and exercise an end-to-end remove, that closes the riskiest gap.** I did not because `seed-bootstrap.spec.ts` itself didn't bother for `authorizePeer`, and standing one up in-test is non-trivial.
3. **Reconstructed `CadreInvite` for redemption is sparse.** `redeemInvite` reconstructs the invite from the pending row only to satisfy `acceptPhone`'s signature. `partyId` is `''` and `authorityAddrs` is `[]` because `acceptPhone` doesn't actually need them — it only validates `token` and `expiresAt`. If cadre-core ever starts validating more fields, this will break; flagged in a comment but worth a second look.
4. **One-time enforcement is in `TrustCircleService`, not in cadre-core.** A different code path that calls `cadreNode.acceptPhone` directly (bypassing cadre-host) would not consume the pending row. In v1 only cadre-host's `redeemInvite` ever calls `acceptPhone`, so this is moot; if `cadre-host-over-P2P` lands the contract may need to move into cadre-core.
5. **`list()` calls control-DB sequentially in a streaming `for await`.** Fine for the small trust-circle scale (handful of members). No pagination.
6. **Pending-row reaping is lazy.** Only redeem-time expiry triggers a delete. A long-lived host accumulates expired tokens until someone redeems them or revokes manually. A reaper task could be added later; not in v1.
7. **CLI is "no inline service".** If cadre-host isn't running, `invite` exits 2 with a hint. This is per ticket decision; alternative would be auto-spawning a service, which the plan ticket explicitly rejected.
8. **Management-API auth.** None in v1 — the ticket commits to localhost-only binding being the entire auth story. The handler functions exported here don't do an origin/Host-header check; if the UI ticket wants defence-in-depth it should add one at the Fastify layer.
9. **Test isolation on Windows.** The CLI smoke test spawns the built bin (`dist/bin/host.js`). It will fail with a clear message if `yarn build` hasn't run — consistent with the existing `cli.smoke.test.ts`. No change to vitest config required.

## Manual end-to-end verification

Not performed — there is no end-to-end harness for cadre-host yet (the orchestrator + trust-circle pieces are the first real subsystems). The plan ticket called for a "smoke script" exercising the full issue→redeem→list cycle; I covered that in the trust-circle.test.ts unit suite using a mock `CadreNodeLike` rather than a live cadre-core. A real-cadre-core smoke is appropriate work for either this ticket's review pass or the local-UI ticket once Fastify is wired.

## Out of scope (already logged in the implement ticket)

- Friend-side label (recipient doesn't see what host labelled them).
- Multi-device label replication (`CadreMemberLabel` table — out of scope).

- QR rendering (UI ticket).
- Authority-key-loss recovery.

## What to look at first

If you only have time for one thing: the `redeemInvite` flow in `packages/cadre-host/src/auth/trust-circle.ts:101-150`. It's the only place that touches both cadre-core's `acceptPhone` and the local pending store, and its ordering (consume pending before writing member; document the graceful degradation if the member-write fails) is the only meaningful trade-off in this ticket.

Second-priority: the `removePeer` SQL in `packages/cadre-core/src/seed-bootstrap.ts:159-194`. Confirm the Quereus DELETE-with-context syntax against the actual Quereus build, since I trusted the docs over runtime verification.
