## What a reviewer should actually attack

The conversion is positional-to-object across ten call sites, and the failure mode is a node that
boots fine and behaves differently — a dropped or misnamed option is invisible to `tsc` when the
target parameter is optional. Suggested order of suspicion:

- **Re-read each converted call against its `git show HEAD:` original.** That is the only check
  that catches a silently dropped option, since every `ControlNodeOpts` field is optional.
- **The relay flags.** Four sites pass `enableRelay: true` alongside `profile: 'storage'`.
  `controlNodeConfig` forwards `enableRelay` on `!== undefined`, so `true` and an explicit `false`
  both survive; the four sites here only ever pass `true`, so the defect the prerequisite fixed is
  not re-testable from these files. Nothing in either file passes `enableRelay: false`.
- **The solo node (`strand-formation-e2e`, Phase 2 "should form a strand with three parties"'s
  sibling — the single-node case).** It is the only call with no options; confirm it did not
  acquire a forced `enableRelay: false` or a non-default listener.
- **Capture/provider aliasing in the closed-strand fixture.** If both nodes ended up on one
  provider, the block-coverage assertions would compare a store with itself and pass for the
  wrong reason. The suite's own distinctness assertion should catch it, but it is worth reading
  the two `controlNodeConfig` calls side by side.
- **`storageProvider` / `storageOpDelayMs` exclusivity.** `controlNodeConfig` throws if given
  both (`node-fixtures.ts:132-134`). Neither file passes a delay; confirm nothing crept in.

Confidence: high on all ten conversions. The option sets are small and every one is a strict
subset of `ControlNodeOpts` with matching defaults — there was no default-flipping trap in either
file, unlike the `multi-party-workflows` fold in the sibling ticket. I have no call site I am
uneasy about.

A broader grep (`controlNetwork: {`) finds one remaining inline config, which I left alone:

**`cadre-host-trust-circle.integration.ts:32-36`** — a deliberately *minimal* config:

```ts
cadreNode = new CadreNode({
    controlNetwork: { partyId: `host-${baseId}`, bootstrapNodes: [] },
    privateKey: nodeKey,
    profile: 'transaction',

```

It is not a copy of the shared builder — it has no `network` block at all (so no transports and
no listen addresses), no `storage`, no `strandFilter`, no `hibernation`, relying on `CadreNode`'s
own defaults throughout. Routing it through `controlNodeConfig` would *add* WebSocket transports,
a `/ip4/127.0.0.1/tcp/0/ws` listener, a memory storage provider, `strandFilter: 'all'` and
`hibernation: false` — a real behavior change to a node this test never intends to put on the
wire. That is out of scope for a deduplication ticket and is a judgement call about what that
test wants its node to be, so it is flagged here rather than changed. If the reviewer disagrees,
it is a one-line change plus a run of that file.
