# Review: enrollment gives up early when the container's process died

Implemented as specified in the implement ticket, plus one extra guard the
ticket's edge-case list did not cover (see **Deviation** below). Build, lint,
whole-repo typecheck, and the cadre-provider + cadre-host suites are green.

## What landed

### The orchestrator capability (`service/orchestrator.ts`)

`ContainerRunState` (`running`, `restartCount`, optional `exitedAt`/`exitCode`)
and `RecoverableOrchestrator extends Orchestrator` with an **optional**
`inspectRunState?(dockerId)`. Optional on purpose: any plain `Orchestrator`
stays assignable, so nothing else in the repo had to change, and
`@serfab/cadre-host`'s `HostProcessOrchestrator` — which declares
`implements Orchestrator` — is untouched.

Implementations:

- `DockerOrchestrator.inspectRunState` — one `container.inspect()`. Maps
  `State.Running`, `RestartCount`, `State.ExitCode`, `State.FinishedAt`.
  Returns `undefined` on a 404 (container gone); **rethrows** every other
  inspect failure so a Docker outage can never read as "the child is fine".
  Go's zero timestamp is handled by a module-level `parseDockerFinishedAt`:
  `0001-01-01T00:00:00Z` parses to a *valid* year-1 `Date`, so the guard is
  "epoch or earlier ⇒ never exited", which also absorbs empty/unparseable.
- `MockOrchestrator` — `restartCount` always 0; `stopContainer` now records
  `exitedAt`/`exitCode: 0`.
- `ProviderProcessOrchestrator` (integration harness) — `running` from the
  existing `exitCode === null && signalCode === null` test (extracted to a
  module-level `isChildUp`, now shared with `isRunning`/`stopContainer`),
  `restartCount` always 0 (it never respawns), `exitedAt` stamped by a
  `child.once('exit')` listener registered at spawn (Node gives the exit code
  but not the exit time), `exitCode` from the child. Returns `undefined` once
  the handle is forgotten by `removeContainer`.

### The enrollment change (`service/container-service.ts`)

- `CONTAINER_ENROLLMENT_TIMEOUT_MS` (60 s) / `CONTAINER_ENROLLMENT_POLL_MS`
  (2 s) exported; `enrollmentTimeoutMs?` / `enrollmentPollMs?` added to
  `ContainerServiceOptions`; the inline literals are gone and
  `waitForEnrollment` no longer takes a timeout argument.
- `ContainerServiceOptions.orchestrator` widened to `RecoverableOrchestrator`.
- Per poll: health is read **first**, so a container that crashed once and is
  now healthy still enrols. Only an unhealthy read calls `assertChildAlive`,
  which throws when `restartCount > 0 || exitedAt !== undefined`. A bare
  `running === false` is deliberately *not* death — with
  `RestartPolicy: unless-stopped` a container reads not-running between
  restarts.
- On death: `getLogs(dockerId, 50)` tailed into the `debug` log (not stored on
  the record — it is tenant output), then throw. `provisionContainer`'s existing
  catch writes `status: 'error'` with the message and calls `safeReclaim`, so
  there is still exactly one failure path.
- Message shape: `container process exited during enrollment (restarts=N, exitCode=C)`
  (`exitCode=unknown` when the orchestrator has no code, e.g. signal-killed).
- Silent-and-keep-waiting for every ambiguous answer: no `inspectRunState` on
  the orchestrator, `inspectRunState` resolving `undefined`, or the probe
  throwing.
- The stale `NOTE:` about the silent timeout is replaced with one saying what
  now survives it (alive-but-unhealthy only). A second `NOTE:` at the probe site
  records the per-poll inspect cost tripwire.

### Docs

`docs/architecture.md` § `@serfab/cadre-provider` — a bullet describing the
behaviour, the health-before-liveness ordering, the keep-waiting cases, and the
two constants.

## Deviation from the ticket (please scrutinise this one)

The ticket's edge list covers "`inspectRunState` returns `undefined` (gone) must
not be read as died". It does **not** cover the gap *inside* `terminateContainer`,
which calls `stopContainer` and only **then** `removeContainer`. During that gap
`DockerOrchestrator.inspectRunState` honestly reports `exitedAt` set — a
deliberate teardown that the ticket's rule would have converted into
`status: 'error'` plus a redundant reclaim.

So the loop's guard was tightened from

```ts
if (!container || container.status === 'error') return;
```

to

```ts
if (container?.status !== 'enrolling') return;
```

This subsumes the old check (missing record, `error`) and additionally bails on
`stopping`/`stopped`. Justification: the record enters this loop as `enrolling`
and only this loop promotes it, so any other status means someone else owns its
fate. **Worth a reviewer's eye** — it is a behavioural widening of an existing
early return, not something the ticket asked for.

## Deliberate, called out because it is destructive

Failing enrollment reclaims via `safeReclaim` → `DockerOrchestrator.removeContainer`,
which **deletes the named `cadre-<id>-data` volume**, discarding that container's
node identity. This is unchanged policy — every other provisioning failure
already does exactly this — and the tenant recreates under a fresh container id.
No different policy was invented here, per the ticket.

Not verified against a real Docker daemon: whether `remove({ force: true })`
actually stops a container Docker is mid-restart rather than racing it. The
ticket asked to confirm this; it cannot be confirmed from unit tests with a fake
dockerode, and there is no Docker daemon in this environment. **This is the
single largest untested claim in the change** — see "For the reviewer" below.

New: `packages/cadre-provider/src/service/__tests__/container-enrollment-liveness.test.ts`

- child exited during enrollment → record `error` with the exact message,
  `removeContainer('docker-xyz')`, `getLogs('docker-xyz', 50)`, and the log tail
  is asserted **not** to be on the record
- `restartCount > 0` but `/status` healthy on that poll → record `running`,
  `peerId` stamped, `inspectRunState` never called (proves health-first ordering)
- alive and never healthy → record stays `enrolling`, no reclaim, no throw
- probe rejects → keep waiting, provision not failed
- orchestrator with no `inspectRunState` → unchanged pre-fix behaviour
- concurrent terminate moved the record to `stopping` → probe never runs, no error
- probe resolves `undefined` (container gone) → no error written

New: `packages/cadre-provider/src/service/__tests__/docker-orchestrator-run-state.test.ts`

- zero `FinishedAt` → `exitedAt`/`exitCode` absent; empty string likewise
- real finish → `exitedAt`/`exitCode`/`restartCount` map through
- 404 → `undefined`; any other inspect error rethrows

**Test-shape note:** the death case injects a *large* `enrollmentTimeoutMs`
(60 s) with a 5 ms poll on purpose — a regression that stops detecting the exit
fails by hitting vitest's own test timeout rather than quietly passing. The
keep-waiting cases use a 30 ms window so they cost nothing.

## Known gaps — treat the tests as a floor

- **No Docker-daemon verification.** Everything about `DockerOrchestrator` is
  proven against a hand-rolled fake dockerode. The `RestartCount` /
  `FinishedAt` field names and the 404 `statusCode` shape are taken from
  dockerode's types and the existing `isRunning`/`ensureVolume` code, not
  observed from a live daemon. Likewise the crash-loop-vs-`force: true` race
  above.
- **The integration harness's `inspectRunState` is not directly unit-tested.**
  It is exercised only indirectly, by the `provider-seed-accepted` scenario —
  which is red for unrelated reasons (below). A reviewer wanting confidence
  there should read
  `packages/integration-tests/src/harness/provider-process-orchestrator.ts`
  rather than trust a test.
- **Diagnostic regression in that same harness.** When enrollment now fails, the
  reclaim removes the handle, so the scenario's `tailNodeLog(dockerId)` →
  `getLogs` → `requireHandle` throws and the scenario prints
  `(node.log unavailable)` instead of the child's output. The log *file* still
  exists on disk (the harness deliberately never deletes the volume dir); only
  the handle lookup fails. `ContainerService` itself logs the same tail via
  `debug` before throwing, and the record's `error` names the exit, so the
  information is not lost — but it is a real step down in that suite's failure
  messages. Left alone rather than making `getLogs` survive removal, because the
  harness deliberately mirrors Docker (where `logs` on a removed container 404s).
  Judgement call; a reviewer may reasonably disagree.
- **`waitForEnrollment` still returns silently on timeout** for a container that
  is alive but never healthy. That is unchanged and intended.

## Suggested review focus

- The `container?.status !== 'enrolling'` widening (Deviation above).
- `parseDockerFinishedAt`'s `ms <= 0` rule — is "at or before the Unix epoch
  means never exited" the right sentinel test, versus matching the literal
  `0001-01-01T00:00:00Z`?
- Whether death should really require `restartCount > 0 || exitedAt !== undefined`
  rather than treating a *sustained* `running === false` across N consecutive
  polls as death too. The current rule cannot detect a container that exited and
  whose orchestrator reports neither a restart nor a finish time — no
  implementation in-tree behaves that way, but the rule is silent about it.
- Whether the 50-line log tail belongs in `debug` only, given an operator with
  `DEBUG` unset sees nothing about why the node died beyond the exit code.
