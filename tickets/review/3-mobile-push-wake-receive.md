# Mobile push-wake receive — review handoff

Implements the **receiver + platform configuration** half of mobile push-wake. The sender (server activity-detection fan-out) is a separate effort, `cadre-server-push-fanout`; this ticket only consumes the shared payload contract.

A suspended app keeps no network up, so a wake for a hibernating phone arrives over the platform push channel (FCM/APNs) instead of the control-network `pushWake`. A data-only push triggers a short background task that brings the node online just long enough to run one `serviceWake` cycle, then lets it re-hibernate.

## What landed

**Architectural split (mirrors `background-runner.ts` / `app-state.ts`):**
- `src/push-wake.ts` — **platform-agnostic, fully unit-tested.** No `react-native`/expo import (type-only `@serfab/cadre-core`). Contains:
  - `StrandWakePayload { type:'strand-wake', strandId, reason }` + `STRAND_WAKE_TYPE` — the **shared contract** the `cadre-server-push-fanout` sender must import rather than re-declare.
  - `parseStrandWakePayload(raw)` — defensive parser, returns `null` (never throws) on any malformed input.
  - `extractPushData(payload)` — pulls the app record from an expo `NotificationTaskPayload` (Android JSON `dataString` vs iOS direct keys).
  - `createPushWakeHandler(deps)` — the handler core: parse → **foreground-vs-background route** → cold-start `ensureNode` → bounded `awaitControlConnected` → `serviceWake(strandId, { windowMs })`. Returns a branchable `PushWakeOutcome`, never throws.
  - `createDeviceTokenRegistrar(deps)` — wraps `registerDeviceToken`/`clearDeviceToken` with **deferred-retry** (returns `false`, doesn't throw, when node down or pre-membership).
  - `pushPlatformFromTokenType(type)` — `ios→apns`, `android→fcm`, else `null`.
- `src/push-wake-native.ts` — **the only RN/expo-coupled module** (not run in the node test env; typechecked). Defines + registers the `expo-notifications`/`expo-task-manager` background task, acquires the raw device token, re-publishes on rotation, clears on logout.
- `index.js` — calls `registerStrandWakeTask()` in entry-module scope (expo requires the task defined in an early-required module so the background bundle reload re-defines it).
- `use-cadre.ts` — `acquireAndRegisterDeviceToken()` on node start, `clearDeviceTokenRegistration()` on stop.

**Platform config:**
- `app.json` — iOS `ios.infoPlist.UIBackgroundModes:["remote-notification"]`; `expo-notifications` config plugin; Android `android.permissions:[POST_NOTIFICATIONS, WAKE_LOCK]`.
- `AndroidManifest.xml` — same two permissions added directly. **NOTE for reviewer:** `packages/reference-app-rn/android/` is **gitignored** (regenerated by `expo prebuild`), so this edit is NOT committed and will be re-derived from `app.json` on the next prebuild. The committed source of truth for Android permissions is `app.json`. The manifest edit only benefits a build made from the currently-checked-out `android/` tree.

**Deps:** `expo-notifications@~0.31.5`, `expo-task-manager@~13.1.6` (SDK-53-pinned via `expo/bundledNativeModules.json`).

## Library choice (resolved, per ticket)

Expo first-party `expo-notifications` + `expo-task-manager` over `react-native-background-fetch`/raw headless JS (fights the managed workflow) and `notifee` (heavier than a single wake-and-return needs). They cover token acquisition + background delivery on both platforms with config-plugin native setup, no bare-RN eject.

## Use cases / what to scrutinize

- **Payload contract drift**: `StrandWakePayload` is the cross-ticket contract with `cadre-server-push-fanout`. Confirm the sender will emit exactly `{ type:'strand-wake', strandId, reason }` as the push `data` (FCM `data` map / APNs custom keys alongside `content-available`). Parser tolerates a missing `reason` (→ `'unknown'`); verify that's acceptable to the sender's contract.
- **`extractPushData` shape assumption**: built against expo's `NotificationTaskPayload` (`.data.dataString` on Android, `.data` keys on iOS). This is **not verified on a real device** — the exact runtime shape FCM/APNs hand expo for a *data-only* message is the highest-risk untested assumption. Manual device test required.
- **Foreground routing**: a foreground push calls `wakeStrand`+`recordStrandActivity`, deliberately NOT `serviceWake` (which would re-hibernate a strand the user is viewing). `isForeground()` is `AppState.currentState === 'active'`. Confirm no contradiction with the AppState `BackgroundRunner` (handler only re-hibernates while backgrounded; runner owns foreground transitions).
- **serviceWake idempotency**: duplicate/replayed pushes for the same `strandId` coalesce in cadre-core (`serviceWakePromises` + HibernationManager wake coalescing) — one runtime build. No double-resume guard needed here; verify the assumption holds.

## Known gaps / honest flags (treat tests as a floor)

- **Cold-start into a fully OS-killed process is NOT wired.** `ensureNode` is intentionally omitted in `push-wake-native.ts` because the node's start options (`partyId` / `bootstrapAddrs`) are entered in Settings and **not persisted** (no AsyncStorage). A wake into a killed process degrades to a `no-node` no-op; the common backgrounded-but-alive case (hibernated strands, live singleton) is fully served. Persisting start options for true cold-start is a **follow-up** — candidate for a new `fix/`/`plan/` ticket. The handler core already supports `ensureNode`; only the persistence + native plumbing is missing.
- **No on-device validation.** Requires a physical device + provisioned push creds (`google-services.json` for FCM, a paid Apple Developer account with push capability + APNs key for iOS) — **human/infra prerequisites, cannot be done in-agent.** Manual steps:
  1. Build a dev client; send a `strand-wake` data message (Firebase console / Expo push tool / manual APNs) to a backgrounded build → confirm app wakes, `serviceWake` runs, pending activity pulls, app re-hibernates. Capture logs.
  2. Token round-trip: install build → confirm a `DeviceToken` row is resolvable from another cadre node via `resolveDeviceToken(peerId)`.
- **Best-effort delivery (by design).** iOS silent push is APNs-rate-limited/coalesced under low-power; Android Doze defers data messages without a battery-optimization opt-out (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` / settings deep-link — **not** implemented; documented as the more-reliable-wake path with the tradeoff that Doze still throttles). Check-in wake (already shipped) is the backstop — do not assume every sent push wakes the app.
- **No foreground service (FGS).** The wake-and-return cycle is expected to fit the data-message background window, so no FGS / persistent "syncing" notification was added (would need `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` perms). If on-device measurement shows `serviceWake` overruns the OS budget (iOS ~30s, less when throttled), adopt an FGS — that's a follow-up, not done here.
- **iOS App Store review note (for whoever ships):** background `remote-notification` must do real work and return quickly; `voip` background mode is **not** appropriate (non-VoIP use is rejected). Silent pushes are rate-limited and not guaranteed.
- **`windowMs` tuning**: background `serviceWake` window defaults to a conservative `DEFAULT_BACKGROUND_WINDOW_MS = 3_000` (smaller than the interactive check-in window) so the cycle returns within budget. Not validated against real network latency on-device — may need tuning.
