## What landed

A self-contained `packages/cadre-host/src/nat/` module tree exposing the NAT/DDNS substrate consumed by `cadre-host-local-ui`. Mirrors the pattern of `auth/` (libraries + `createXxxHandlers` factories, no inline service process).

### nat/ module tree

```

  types.ts                  NatStatusSnapshot, NatSettingsFile, NatError, NatHandlers
```

### cadre-core changes (the invite address hook)

- `NetworkConfig.inviteAddressResolver?: () => Promise<string[]>` added to `packages/cadre-core/src/types.ts`.
- `SeedBootstrapConfig.inviteAddressResolver` added in `packages/cadre-core/src/seed-bootstrap.ts`. `createInvite()` consults the resolver first, falls back to `libp2pNode.getMultiaddrs()` either when unset OR when the resolver throws (defensive).
- `CadreNode.initializeSeedBootstrap` / `enableSeedListener` plumb `network.inviteAddressResolver` into both `SeedBootstrapService` constructions. The temp services in `applySeed` / `dialInvite` deliberately don't carry it — neither emits invites.
- New tests in `packages/cadre-core/test/seed-bootstrap.spec.ts` cover: no-resolver default, resolver substitution, and fallback-on-throw.

### CLI

Added a `nat` sub-command group in `packages/cadre-host/src/bin/host.ts` (alongside `invite` / `trust`):

- `cadre-host nat status [--port 8765] [--json]` — `GET /nat/status`, prints a status summary or raw JSON.
- `cadre-host nat test [--port 8765] [--json]` — `POST /nat/test`, re-runs probes.
- `cadre-host nat ddns set <provider> --hostname <host> --token <secret> [--port 8765]` — `PUT /nat/ddns`. Prompts for `--token` interactively on a TTY when omitted; exits 1 with a clear message on a non-TTY.
- `cadre-host nat ddns external --hostname <host> [--port 8765]` — `PUT /nat/settings` with `externallyManaged: true`.
- `cadre-host nat settings [--external-port N] [--internal-port N] [--no-upnp] [--port 8765]` — `PUT /nat/settings`.

All commands share the existing `resolvePort()` helper and exit 2 on a connect-failure to cadre-host.

## Known gaps and tradeoffs (reviewer: please verify)

These are honest "starting point, not finish line" notes. The reviewer is invited to file new fix/plan/backlog tickets rather than expand scope inline.

1. **No real router** in the test suite. `port-mapper.test.ts` exercises `PortMapperService` against a `PortMapper` stub, not the actual `@achingbrain/nat-port-mapper`. The default `createDefaultPortMapper()` adapter loads the package via dynamic import and adapts its surface (externalIp / map / unmap / stop), but the adapter itself isn't exercised end-to-end. A live-router e2e test is hard to make reliable in CI; an explicit "router-fixture" follow-up ticket may be warranted if this becomes a recurring deployment surprise.
2. **PortMapper.verify** is a degenerate check — it only confirms the upstream gateway still answers `externalIp()`. The underlying library doesn't expose a real "is this mapping still installed?" call. A future fix could move to per-mapping cookies via UPnP's `GetSpecificPortMappingEntry`, but it's not in this ticket.
3. **External-IP probe URLs are hard-coded.** No runtime config; if api.ipify.org disappears the only mitigation is releasing a new cadre-host. Acceptable for v1, file a fix ticket if it becomes painful.
4. **CGNAT detection is heuristic.** False positives are possible on dual-stack networks, sliced VPNs, IPv6-only public probes, or rapidly-changing IPs. The verdict is informational; nothing in the system enforces it.
5. **Reachability is heuristic, not AutoNAT.** The plan called this out and filed a follow-up ticket idea — enabling libp2p's `autoNat()` requires changes inside `@optimystic/db-p2p`'s `libp2p-node-base.ts`. Not done here; file as backlog if it isn't already.
6. **Circuit-relay client wiring is out of scope.** When UPnP fails and the host is behind CGNAT, `getInviteAddresses` falls back to `libp2pNode.getMultiaddrs()` — which currently has *no* `/p2p-circuit/` entries because cadre-core only enables the relay *server* side. Backlog ticket `4-relay-bootstrap-infrastructure` should add reservations on the client side; until then, those hosts are not dialable from the public internet.
7. **No cross-platform path for OS keychain on headless Linux** beyond keytar's own behavior — the file-store fallback's warning surfaces the situation but doesn't fix it. Documenting was preferred over installing libsecret silently.
8. **DDNS providers: DuckDNS only.** Architecture is open (drop-in provider files + registry entry); v1 ships one. New providers are good first-contribution work, not a defect.
9. **Settings-API does not list DDNS providers via the management API today.** `NatService.listDdnsProviders()` is wired into `createNatHandlers()` but the CLI doesn't yet have a "list providers" sub-command. Add as needed once the local-ui ticket lands a provider picker.
10. **`nat ddns external` uses `providerId: 'external'`**, which isn't a real provider — it's a sentinel that, in combination with `externallyManaged: true`, keeps the DDNS updater dormant. This works because the updater short-circuits on `externallyManaged` before resolving the provider. Reviewer may prefer to allow `providerId: null` for this case instead; left as-is to avoid the null-handling pollution.
11. **The `readSecretLine` helper in `bin/host.ts`** uses raw char-code comparisons against control bytes (CR, LF, ETX, EOT, DEL, BS) which render oddly in some editors. Tests don't exercise the TTY interactive path (vitest spawns a non-TTY child); the non-TTY error path *is* covered. A targeted manual smoke test is warranted before shipping.
12. **`PortMapperService.start()` swallows mapper-throws** into `mode: 'failed'` rather than re-throwing. This was deliberate (a failed mapping shouldn't crash cadre-host startup), but the reviewer may want a separate `mapping_failed` event for monitoring. Not added; the status snapshot is sufficient for the local-ui case.

## What the local-ui ticket needs to do

The local-ui ticket (`cadre-host-local-ui`) owns the long-running process. Integration contract:

1. Construct `new NatService({ rootDir, cadreNode })` where `cadreNode` provides `getPeerId()` / `getMultiaddrs()` against the running libp2p node.
2. `await service.start()` after the libp2p node is up.
3. Mount `createNatHandlers(service)` on Fastify under `/nat/*`:
   - `GET /nat/status` → `handlers.getStatus()`
   - `POST /nat/test` → `handlers.testReachability()`
   - `GET /nat/ddns/providers` → `handlers.listDdnsProviders()`
   - `PUT /nat/ddns` → `handlers.putDdns(body)`
   - `PUT /nat/settings` → `handlers.putSettings(body)`
4. Map `NatError.code` → HTTP status: `invalid_config|ddns_provider_unknown|ddns_credentials_missing` → 400, `secrets_unavailable|storage_error` → 500, otherwise 500.
5. `await service.stop()` on shutdown to release the UPnP lease.
6. Wire `service.getInviteAddresses.bind(service)` as `network.inviteAddressResolver` on the cadre-core `CadreNodeConfig` so invites embed the dialable addresses.
