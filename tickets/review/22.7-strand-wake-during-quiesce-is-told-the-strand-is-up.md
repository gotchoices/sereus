# A wake that lands during a quiesce waits for it and rebuilds

## The defect (as filed)

`StrandInstanceManager.quiesceStrand` awaits several teardown steps and only clears the strand's database and libp2p node near the end; the callers set `'hibernating'` after it returned. A wake during that await (`wakeStrand`, a push-wake, activity on an `'idle'` strand) reached `CadreNode.handleStrandWake`, saw the handles still attached, took the "already live" branch and resolved. The quiesce then finished and the strand slept. Activity on an `'active'` strand during a check-in window's quiesce did not wake at all.

## What shipped

**One ordering mechanism in `StrandInstanceManager`.** `resumesInFlight` is replaced by `transitions`: the latest resume or quiesce requested per strand. Each new request waits for the one before it to settle (errors ignored and logged; they belong to that request's caller), then for any `startStrand` build, then runs. A request of the same kind as the latest one joins it (resume joins resume, as before; quiesce joins quiesce). Consequences:

- A resume requested during a quiesce runs after it and rebuilds.
- A quiesce requested during a rebuild (e.g. a mobile force-hibernate during a check-in's resume) waits for the rebuild and releases the finished runtime, instead of stopping a node the build is still wiring. This is the ticket's optional hardening — **done**, and it needed the no-join rule: a resume requested after that queued quiesce must not join the earlier resume, or it would be told "up" and then quiesced.
- `quiesceStrand` writes `instance.status = 'hibernating'` as the last step of the tracked operation, also for a tracked strand with no runtime left (a failed rebuild). So a resume queued behind it always writes its `'starting'` later. A failed release leaves the status alone and rejects.
- `isQuiescing(strandId)` — the latest requested transition is a quiesce that has not finished.

**Callers.**

- `handleStrandHibernate` no longer writes status and has no separate "already quiesced" branch (the quiesce marks the strand either way).
- `runWakeWindow` no longer writes `'hibernating'`.
- `rehibernateAfterFailedResume` writes `'hibernating'` only when its quiesce throws. The ticket said to keep this write because the quiesce "may be a no-op or may throw". The no-op case is now covered by the quiesce itself. An unconditional write after the await could land after a resume queued behind the quiesce had already written `'starting'`, because the resume can be scheduled first.
- `handleStrandWake` skips its already-live branch while `isQuiescing`, so the wake reaches `resumeStrand` and queues behind the quiesce.
- `runServiceWake` no longer returns "already live, no-op success" for a quiescing strand; its probe wake rebuilds it.
- `wakeHostStrandForFormation` wakes and awaits (bounded by the formation budget) a quiescing host strand, instead of letting the caller issue the invitation against a closing database. The "(… or quiescing)" cause is gone from the refusal message and docs.
- `foundExistingStrand` returns `'needs-resume'` while quiescing (its database is closing), so the founder path wakes the strand and bootstraps on the rebuilt database.

**Timers (`HibernationManager`).**

- New required callback `HibernationCallbacks.isQuiescing`. `recordActivity` wakes a quiescing strand like an idle or hibernating one. This covers the ticket's "activity on an `'active'` strand during the window's quiesce is lost" arm. `HibernationCallbacks` is publicly exported, and AGENTS.md says no backwards compatibility yet.
- `handleHibernateTimeout`'s `.then` goes through `startCheckInChain`:
  - if a wake or probe holds the strand, the chain goes to it (`handCheckInChainToHolder`, now also used here);
  - otherwise a chain starts only if the strand still reads `'hibernating'`.

  This is the ticket's requested guard.
- `endProbe`: if a wake began during the probe's window (e.g. activity during its closing quiesce) and is still rebuilding, the probe gives its chain to that wake instead of deciding timers on a strand about to come up. Before this, the probe restored a check-in chain on a strand the wake then left `'active'`.
- **Adjacent fix, not in the ticket:** a force-hibernate that lands while a timer-driven hibernate is quiescing joins that quiesce, and the timer path then armed a check-in chain on a strand the mobile runner wants kept down. This was pre-existing; the old code ran two parallel quiesces and got the same outcome. Fixed with `timerHibernates`, the same pattern as the prereq's `runningCheckIns`: set when the timer's `onHibernate` starts, removed by `forceHibernate` / `untrackStrand` / `stop`, and the `.then` starts no chain if the entry is gone. Reproduction test below.

**Docs.** `docs/architecture.md` → Strand Hibernation changes:

- New "Quiesce and resume of one strand are ordered" bullet.
- The `hibernating` bullet says the quiesce marks the status.
- Mechanism 1: a quiescing formation host is woken.
- Mechanism 2: the timer path's hand-off.
- Mechanism 4: a force-hibernate also cancels the chain a timer-driven hibernate would start.

Updated doc comments: `quiesceStrand` ("the caller sets the post-quiesce status" removed), `resumeStrand`, `foundExistingStrand`, `hibernateStrand`, `issueStrandMembershipInvite`, `wakeHostStrandForFormation`, `endProbe`, `scheduleCheckIn`, `handCheckInChainToHolder`, `forceHibernate`.

## Tests

Each new test was run once with its piece of the fix removed and failed; all fixes were then restored.

- `strand-instance-manager-hibernation.spec.ts` → `a resume requested while a quiesce is releasing the runtime rebuilds it once the quiesce ends`. The defect's reproduction, with a real manager and the database close held open. Without `runResume`'s wait it ends `'hibernating'` with no node.
- same → `a quiesce requested mid-rebuild waits for it, and a resume requested after that quiesce rebuilds again`. Pins the other direction and the no-join rule. It fails without either the quiesce's wait (the node is stopped under the build) or the resume's wait (one build only).
- same → the existing `quiesce releases node + db…` test now also asserts `status === 'hibernating'` (the quiesce's new contract).
- `cadre-node.spec.ts` → `a wake issued while the strand is being hibernated rebuilds it once the quiesce ends`. The `CadreNode` half: `hibernateStrand` with the quiesce held open, then `wakeStrand`. It fails without the `isQuiescing` check in `handleStrandWake`, because no resume happens.
- `hibernation-manager.spec.ts` → `a force-hibernate during a timer-driven hibernate leaves the strand with no check-in chain`. Reproduction for the adjacent fix; without the guard, `nextCheckIn` is set.
- `cadre-node.spec.ts` test helpers:
  - `fakeManager` is moved up to the outer suite and now models the new contract: quiesce marks `'hibernating'`, `isQuiescing`, a resume waits for a held quiesce, and `holdQuiesces(promise)` holds quiesces open.
  - The five hand-written fakes in `hibernation orchestration` now use it. Two of them would otherwise have needed their own status writes.
- `hibernation-manager.spec.ts` callbacks gained `isQuiescing: () => false`.

## Known gaps and things to check

- **`stopStrand` is not in the ordering.** A stop during a queued or running resume or quiesce still runs its own `releaseRuntime` concurrently (pre-existing). A resume queued behind a stop fails "not tracked", and a quiesce queued behind one no-ops.
- **`attachSApp`** waits for runtime builds but not for a pending quiesce. Its documented throw ("a quiesce closed the database mid-apply") remains.
- **A failed release** leaves the libp2p node attached (it is cleared last). A resume queued behind it therefore reads "already live" over a half-released runtime, and `rehibernateAfterFailedResume` then writes `'hibernating'`. Same failure mode as before this change.
- **`serviceWake`'s result** can say `hadActivity: false` while activity during its window's closing quiesce has started a wake that leaves the strand live. The result reflects the window, not the wake that followed it.
- **Two windows over one shared runtime** (the gap the prereq's review noted): unchanged. The first window to end still quiesces a runtime the other is holding, although a wake or activity during that quiesce now brings it back.
- **Extra microtask hops.** `resumeStrand` / `quiesceStrand` now always take a few microtask hops (waiting on the previous transition and on builds) even when nothing is queued. Nothing observed depends on the old zero-hop return.
