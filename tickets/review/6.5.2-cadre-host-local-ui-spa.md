## What landed

A Svelte 5 SPA hosted by the cadre-host Fastify server at `/`, covering the five pages from the plan (Home/Status, Trust Circle, Connectivity, Nodes + per-node detail, Settings). The bundle ships in `dist/ui/` and is consumed by the static mount registered in `6.5.1`.

### Build output

`yarn workspace @serfab/cadre-host build` runs `tsc -p tsconfig.build.json && vite build --config ui/vite.config.ts`. Verified clean on Windows:

```
dist/ui/index.html                  0.45 kB │ gzip:  0.29 kB
dist/ui/assets/index-*.css         14.32 kB │ gzip:  3.27 kB
dist/ui/assets/index-*.js         106.97 kB │ gzip: 39.31 kB
✓ built in 770ms
```

≈ **43 KB gzipped** total — well under the 1 MB budget the ticket pinned, and within the plan's ~50 KB estimate (Svelte 5 runtime + app + qrcode SVG). 194 modules transformed without warnings.

### Tests

`yarn workspace @serfab/cadre-host test` → **281 passed, 3 skipped, 40 files**. UI-side test files:
- `ui/__tests__/api.test.ts` (8 tests) — envelope unwrapping, `{ ok: false }` → `ApiError`, network failure mapping, `apiPost`/`apiDelete` shape.
- `ui/__tests__/router.test.ts` (9 tests) — `parseHash` / `hrefFor` / `navigate` round-trips including URL-encoded node ids.
- `ui/__tests__/events.test.ts` (4 tests) — fake EventSource through the backoff schedule (clamps at the last step), reset-on-open, no-retry-after-close.

The two UI test files use `@vitest-environment jsdom` so the existing single-config `vitest.config.ts` (Node default) still works for the server tests.

### Decisions worth noting (some diverge slightly from the plan; flag if undesirable)

- **Runes file split.** Plan said `router.ts` and `state.ts`. As built, the reactive `$state` lives in `router.svelte.ts` and `state.svelte.ts` (Svelte 5 forbids runes outside `.svelte`/`.svelte.ts` files), and the *pure* parsing/serialisation helpers stay in `router.ts` so they remain testable in plain Vitest (no Svelte compiler). The plan didn't anticipate this; it's a clean split, but mention it in your review.
- **DDNS provider endpoint.** The plan called for `GET /nat/ddns/providers`; the actual server route is `GET /nat/providers`. The SPA uses the real route. The plan text was wrong.
- **Apply-update button on Settings.** The plan listed only the `autoApply` toggle and DDNS link. As built, Settings also surfaces an "Apply now" button when `update.available` is present (POSTs `/update/apply`). Felt mandatory — without it, users have no way to consent to a non-auto update.
- **Settings PUT shape.** Uses `{ updates: { autoApply, manifestUrl? } }` to match the `settings-route` validator that landed in `6.5.1`. The plan was vague about the body shape.
- **`apiFetch` accepts bare bodies too.** Half the existing cadre-host routes return bare JSON (`/api/status`, `/nat/status`, `/auth/trust-circle`, `/update`), the newer ones use `{ ok, data, error }`. The wrapper handles both rather than requiring a server migration.

### State shape (final)

Slightly broader than the plan to cover what the routes actually need:

```ts
interface AppState {
  status: 'loading' | 'ok' | 'warn' | 'error';
  service: { name: 'cadre-host'; version: string; uptimeSeconds: number } | null;
  nodes: NodeInfo[];
  nodeStats: Record<string, NodeStats | null>;
  trustCircle: { members: TrustCircleMember[]; pending: PendingInvite[] };
  connectivity: NatStatusSnapshot | null;
  update: UpdateState | null;
  settings: HostConfigFile | null;
  toasts: Toast[];
}
```

`deriveOverallStatus` is exported via `__test__` if you want to add a coverage test in review — currently exercised only indirectly via the refresh helpers.

## Use cases to spot-check

The cleanest manual smoke uses the Vite dev server against a live cadre-host:

```
yarn workspace @serfab/cadre-host build          # produces dist/ui/ + dist/*.js
yarn workspace @serfab/cadre-host start --data-dir /tmp/cadre-ui-test
# in another terminal:
#   yarn workspace @serfab/cadre-host dev:ui     # vite on :5173 with proxy → :8765
# or just hit http://127.0.0.1:8765/ (served by Fastify from dist/ui)
```

Walk through each:

1. **Home** — green/yellow/red status dot reflects subsystems. Update banner appears when `state.update.available` is populated. Connectivity card surfaces a "Resolve →" link when `directReachability !== 'reachable'`.
2. **Trust Circle** — "Invite a friend" opens the modal; submit calls `POST /auth/invites` and renders the returned token + QR (inline SVG, no canvas). Revoke flow gated by `ConfirmDialog`; self-member shows a "This device" badge and no remove button.
3. **Connectivity** — current snapshot, "Test reachability" POSTs `/nat/test`, port-form PUTs `/nat/settings`, DDNS form PUTs `/nat/ddns`. The provider list comes from `GET /nat/providers` (note the route name diff vs the plan).
4. **Nodes / Node detail** — empty state explicitly notes v1 doesn't auto-spawn nodes. Detail page polls `/api/nodes/:id` every 5 s, log tail fetches `/api/nodes/:id/logs?lines=200`. Stop gated by `ConfirmDialog`.
5. **Settings** — `autoApply` toggle + manifest URL override PUTs `/api/settings`. Install metadata is read-only; copy buttons for `dataDir`/`identityPath`. Uninstall section is plain markdown.

The EventSource subscription is opened once in `App.svelte`'s `onMount` and closed on unmount. Reconnect schedule: `2s, 4s, 8s, 16s, 30s, 30s…` with `onError` callback toasting only on the first failure.

## Known gaps (the reviewer should treat these as starting points, not done)

- **No live click-through in this implement run.** I built + tested the bundle but did not boot `cadre-host start` and drive the SPA in a real browser from this agent run. The runner can't keep a foreground server alive across tool calls under tess, and background tasks die at end-of-turn. **Reviewer should run the smoke flow above** — that's the validation step.
- **No Lighthouse score recorded.** Same reason. Eyeballing the bundle (43 KB gzip, no async chunks, no third-party fonts, semantic HTML throughout) suggests it should land ≥ 95 performance / ≥ 90 a11y, but that's an estimate. Capture it during review.
- **No component-level tests.** Plan called this out as intentional; flagging it again here. Only `api.ts`, `router.ts`, `events.ts` have tests. Routes/components rely on the smoke pass + manual review.
- **No e2e Playwright suite.** Out of scope per the plan. Could be a follow-up ticket if regressions start appearing.
- **Re-label trust-circle members not implemented.** Plan noted the `TrustCircleService` has no rename method — left for a follow-up.
- **Stats poll on Node detail is poll-based**, not pushed. Orchestrator doesn't emit stats events yet. 5 s interval is conservative; could be tightened or replaced once the orchestrator pushes stats.
- **No CSRF token.** Same-origin + Origin/Host guard from `6.5.1` is the only protection. Consistent with the "same-machine access is the auth boundary" model, but worth a review eye.
- **Accessibility is v1 only.** Semantic HTML, ARIA labels on icon-only buttons, keyboard navigation through forms — not WCAG-audited. Plan called this acceptable for v1.
- **The `static.ts` placeholder branch is still the same as `6.5.1` shipped it.** The TODO had a line about flipping it to a "build was skipped" warning, but the existing copy already does exactly that (literally points contributors at `yarn workspace @serfab/cadre-host build`), so no change was needed. Sanity-check that's the right call.
