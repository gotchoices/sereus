# Seating an issued row from its bundle on a member whose store lags the cohort

## The defect (unchanged from the fix stage)

`ControlDatabase.seatIssuedRow` (the body of `seatOwnerGrant` and `seatCadreInvite`) is an insert-if-absent under the write lock. On a member whose store has not caught up, the guard read finds nothing, but a cohort member that already holds the row refuses the commit with `UNIQUE constraint failed: OwnerGrant.Key`. Before this change that raw error reached `CadreNode.redeemOwnerGrant`'s local path with no code, and cadre-cli treated it as final. Reported with real cadre-cli nodes: owner A, member C stopped, grant minted on A, C restarted with `CADRE_OWNER_GRANT=<grant>`.

## What changed

- **Key-conflict classifier.** `idConflictPattern(table)` became `keyConflictPattern(table)`. It takes the column from `GUARDED_KEY_COLUMN` instead of hard-coding `Id`, so the issued tables (`Key`) use the same function. New exported predicate `isIssuedRowKeyConflict(error, 'OwnerGrant' | 'CadreInvite')`. It matches the primary key only, never `StampId`, and it is text-matched and fails closed, like `isStrandIdConflict`.
- **New error `IssuedRowNotHereYetError`** (`table`, `key`, `cause`), exported from `control-database.ts` and the package index. It means: the cadre holds this row, and this node cannot read it yet.
- **Seat adopts the cohort's row.** In `seatIssuedRow`, after the locked write throws, a key conflict goes to `adoptCohortHeldRow`. That method re-reads the stamp with an unlocked read (the retried, refreshing path). If the row is visible it logs and returns `false`, exactly like the local "already seated" branch. If not, it throws `IssuedRowNotHereYetError` with the conflict as `cause`. The issuer-unauthorized check still runs first.
- **Redemption's missing-row check.** `redeemOwnerGrant` and `redeemCadreInvite` now throw `IssuedRowNotHereYetError` instead of a plain `Error("… seatOwnerGrant first")`.
- **Local grant path.** `CadreNode.redeemOwnerGrantLocally` wraps both the seat and the redemption write in `refusingUnsyncedGrant`. It maps the named error to `OwnerGrantRejectedError('conflict', …)`, which is retryable. The seat still runs before the signer's approval, so a prompting signer is never asked about a redemption this node then refuses at the seat. cadre-cli's `describeRedemptionFailure` and the apps' `GRANT_REJECTION_LINE` already treat `conflict` as "retryable / try again", so neither changed.
- **Member handlers.** The mapping lives in the shared `writeFailureRefusal` (member-redemption.ts) rather than in each catch block. All four catch blocks of `OwnerGrantHandler.redeemAdmitted` and `CadreInviteHandler.redeemAdmitted` already end in `constraintRefusal(...) ?? writeFailureRefusal(error)`, and none of the `REDEEM_CONSTRAINT_CODES` patterns match `UNIQUE`. Before this change, the member answered `internal` here, which is also retryable. It now answers `conflict`.
- **Docs.** In docs/architecture.md, the invitation-seat paragraph gets the "a refused seat counts as seated; still unreadable → `conflict`" sentence, which the Owner grants section points to. The local-path bullet names the `conflict` refusal. Both refusal tables' `conflict` rows are widened. The `conflict` code doc comments in both protocol files are updated too.

## Tests

- Added one case to `control-owner-grant.spec.ts`: "a repeat insert of a held grant is classified as an OwnerGrant key conflict…". It seats a row, inserts the same row again through the raw database, and asserts that `isIssuedRowKeyConflict(error, 'OwnerGrant')` is true and the `'CadreInvite'` check is false. This pins the engine's message text, which comes from another repo. It also confirms that for a verbatim copy, where the stamp repeats too, the engine names `OwnerGrant.Key` and not `StampId`.
- Ran, all green: `control-owner-grant.spec.ts`, `control-cadre-invite.spec.ts` (34 tests), `cadre-node-owner-grant.spec.ts`, `cadre-invite-protocol.spec.ts`, `owner-grant-codec.spec.ts` (19 tests), `yarn lint`, cadre-core typecheck, cadre-core build. I also ran the integration scenarios `owner-grant-without-machine` and `cadre-invite-row-unreplicated` once after the change: both passed, each admitted on pass 1.

## Known gaps for the reviewer

- **The adoption branch is not exercised by any test.** Neither outcome of `adoptCohortHeldRow` runs in a test: "row visible after the re-read → `false`" and "still missing → `IssuedRowNotHereYetError`". The fix stage showed the race window cannot be forced in-process: the harness cannot control when FRET adds a peer to the cohort. The ticket ruled out mocking the control database. I did not repeat the real cadre-cli reproduction (steps above and in the fix-stage ticket), so the end-to-end fix is unverified. A reviewer with time could run that repro and check for `OwnerGrant … is held by the cohort; seat skipped` in `DEBUG=sereus:cadre:*` output.
- **The abandoned-write warning still prints.** The write funnel's abandonment listener fires before `seatIssuedRow`'s catch, so cadre-cli will still print `⚠ Control write abandoned [owner-grant-seat] … (declined): UNIQUE constraint failed: OwnerGrant.Key` and then succeed. This is cosmetic and matches what `publishStrand`'s id-conflict branch already does. I left it alone.
- **The re-read can miss when another write is running.** If another locked write body is running on the node at that moment, the "refreshing" re-read takes the committed, non-refreshing path (`readRowsOnce` / `writeInFlight`). It then misses the row and refuses `conflict`. That refusal is retryable, so the cost is one extra attempt by the user or holder, not a wrong result. I did not add a NOTE for it, because the routing is already documented at `readRowsOnce`.
- **Design choice to check.** The handler mapping sits in `writeFailureRefusal`, not in explicit `instanceof` checks in each catch block as the ticket described. The behaviour is the same, from one site. If the reviewer prefers the explicit per-handler form, it is a small move.
- **The member-side message names a cause it cannot always know.** A missing row in `redeemCadreInvite` / `redeemOwnerGrant` called without a seat now reads as "held by the cadre but not readable here yet". Every production caller seats first, so the row is known to exist somewhere when that error fires.
