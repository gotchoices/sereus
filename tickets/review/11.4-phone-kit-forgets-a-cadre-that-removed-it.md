# The phone kit acts on `cadre:removed`

## What was built

- **`PhoneNodeStatus` arm** `{ state: 'removed'; partyId; removal: CadreRemoval; formerPartyId? }` (`node.ts`). `node` and `options` read null, as for `stopped`. `start` and `joinCadre` from `removed` take the same code path as from `stopped` (nothing checks the previous status). `createPhoneNode` replaces a runtime in `removed` as it replaces a stopped one. Already exported through `index.ts` as `PhoneNodeStatus`, so `index.ts` is unchanged.
- **`watchRemoval(node)`**, called in `bringUp` next to the kit's other subscriptions, so every node a start, restart or join builds is watched (not the short-lived `readAlone` nodes). It subscribes before `node.start()`, so no report can come earlier. It is never detached, so a report raised while the node stops still counts (the ticket's "check by the node the report came from, not `this.node`").
- **`forgetRemovedParty(removal)`**, queued with the new `trackStop` (which `stop()` now uses too). That means `loadSavedStart()` and the app-link slots wait for it, as they wait for a stop, and a start called after it runs after it. Steps:
  1. If `this.current` is a node of another party (a join that ran before this turn moved the app), it only deletes the removed party's storage and strips `formerPartyId` from `runningOptions` if it names that party. The running node is left alone.
  2. Otherwise `shutDown()`. A throw from the node's own `stop()` is logged and the steps continue, because `shutDown`'s `finally` has already closed the databases and dropped the node.
  3. `leaveRemovedStart`: if the saved start names the removed party, replace it with `startAfterRemoval(saved)` (new pure function in `options.ts`: a start of `formerPartyId` with `origin: 'founded'`, `bootstrapAddrs: []`, the same relays and Noise mode, `autoStart: false`), or delete it when there is no former party. A saved start of another party is left alone.
  4. `removeLocalParty`: `finishMarkedRemoval` first, so the new marker does not overwrite a pending older one, then `removeParty`. A failure here is logged; the marker finishes the deletion at the next start.
  5. Status `removed`, with `formerPartyId` taken from the start written in step 3.
  
  A failure in step 3 (a read or write fault) is logged, leaves `status` `failed`, and deletes nothing. `forgetRemovedParty` never rejects.
- **Owner key**: the identity key is per app (`DEFAULT_IDENTITY_KEY_ID`), not per party, so it must stay; nothing to delete. `removeParty` already deletes the party's anchor slot and the per-party joined-strand records in the key store. Checked by reading `finishRemoving` in `dissolve.ts`.
- **Docs**: `packages/cadre-rn/README.md` has the `removed` status in the member table, a `loadSavedStart` note, the intro line, and a new "Removed from the cadre" section. `docs/architecture.md` → "An app joins an existing cadre" has a "Removed from A" paragraph after the `formerPartyId` sentence.
- **Size `NOTE:`** at the join section of `node.ts` updated to the measured 1170 lines (`wc -l`) and now names the removal transition.

## Where this departs from the ticket

- **The saved start is rewritten before the deletion, not after.** The ticket put deletion (step 2) before the saved start (step 3). With that order, a deletion that fails partway leaves the marker and a saved start that still names the removed party with `autoStart: true`. A push wake or the lifecycle runner then calls `start()` on it, and `bringUp`'s `finishRemovalAtStart` finishes the deletion and then builds that party again on empty storage. Rewriting the saved start first closes that path. What remains: a crash between the saved-start write and the marker write leaves the party's data on disk with nothing pointing at it, and costs disk space only.
- **No `removedFromCadre()` check after start.** The watcher is attached before `node.start()`, and a node object only reports once, so the check could never find something the event missed. Leaving it out was deliberate. If you disagree, the check would go after `await node.start()` in `bringUp`, with a guard so the same node is not queued twice.
- **`dissolve.ts` unchanged.** `removeParty` is reused as is. Its `dropFromSavedStart` still drops a `formerPartyId` that names the removed party, which covers branch 1 above, where the app had joined another party.

## Test added

- `node.spec.ts` → "createPhoneNode — removed from its party by an owner": a running node started with `formerPartyId` gets `cadre:removed` emitted on the real `CadreNode`, by casting to reach its private `emit`; a real removal needs a second owner machine. The test checks:
  - status `removed` with `partyId`, `removal` and `formerPartyId`;
  - the node is stopped;
  - the saved start names the former party with `origin: 'founded'` and `autoStart: false`;
  - the removed party's anchor slot is gone and its control database is empty;
  - starting the saved start ("go back to your own cadre") reaches `running`, which also shows every database was closed.
  
  The removed party is started as founded rather than joined, as the dissolve test does, so genesis writes rows and an anchor slot to delete. The two "before" assertions are what make the deletion checks meaningful. The removal code does not read `origin`.
- The dissolve tests' `controlDatabaseHoldsData` helper moved to module scope so both describes use it.

## Not verified / for the reviewer

- **Branch 1 (another party running)** is untested and checked only by reading the code. Reaching it takes a membership refresh still running when a join's `shutDown` stops the old node. One consequence: if that join's strand move into the new party was deferred, `removeParty` deletes the removed party's move record, so the deferred move is lost. That fits "delete everything of the party that removed you", but it is a judgement call.
- **Explicit `start(removedPartyOptions)` by the app after removal** is not refused. The kit builds that party again on empty storage, as a founded party (the saved start no longer supplies `origin`). Unattended paths cannot do this, because they read `loadSavedStart()`, which waits for the removal. Only an app that keeps the removed party's options and starts them by hand can.
- **Removal reported during a start still in flight** (between `node.start()` and `markRunning`): the start finishes and saves `autoStart: true`, then the queued removal rewrites the saved start. A caller awaiting that start gets a node that is stopped right after. Checked only by reading the code.
- **`stop()` from `removed`** moves the status to `stopped`.
- Device run: not possible here. The reference app's removed screen is `reference-app-rn-devices-and-nodes`.
