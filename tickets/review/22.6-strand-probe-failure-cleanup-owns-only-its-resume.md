# A probe's failure cleanup releases only a runtime it built — review handoff

## What was wrong

A hibernating strand is rebuilt by a wake (`handleStrandWake`), a periodic check-in (`handleStrandCheckIn`), or the mobile `serviceWake` (`runServiceWake`). Each rebuild first reads the cohort discovery seed from the control database (can throw), then calls `StrandInstanceManager.resumeStrand`, which shares one build between overlapping callers and leaves the instance `'error'` if that build fails. The check-in and `serviceWake` wrapped seed read, rebuild and window in one `try` whose `catch` always quiesced and marked the strand `'hibernating'` — so a seed-read failure stopped a node a concurrent wake was still wiring, or quiesced a strand whose waker had just been told it was up.

## What changed

- **One rule for resume-stage failures** — `CadreNode.rehibernateIfResumeFailed(instance, context, error)`: re-hibernate (best-effort quiesce, then `'hibernating'`) only when the instance reads `'error'`, i.e. the build this caller started or joined failed. Any other status means the failure came before the rebuild and the strand belongs to whoever is building or holding it; it only logs. Used by `handleStrandWake` (replacing its inline copy of the condition) and the check-in's resume stage.
- **`handleStrandCheckIn`** is split into a resume `try` (on failure: the rule above, then return) and a window `try` (on failure: `rehibernateAfterFailedResume` as before). It still never rejects. The long catch comment was rewritten for the split.
- **`runServiceWake`** keeps its guards and the `finally { endProbe }`, and delegates to a new `wakeAndHoldForService`: a wake failure is only logged and reported `{ serviced: true, hadActivity: false }` (`handleStrandWake` already applied the rule and rethrew); a window failure still quiesces best-effort and marks `'hibernating'`. `endProbe` still runs last on every exit path.
- **`HibernationManager.runCheckIn`** now calls `handCheckInChainToHolder` after `onCheckIn` returns: if a probe holds the strand, set its `hadCheckInChain = true`; else if a wake is in flight (`wakePromises`), add the strand to `checkInsCancelledByWake`; either way clear any armed check-in and `nextCheckIn`, and stop. That wake's settle (or `endProbe`) then restores the chain at the base delay if the strand ends `'hibernating'`, or starts the idle countdown if it ends live — the same as for a chain the wake cancelled itself. With no wake or probe holding the strand, behaviour is unchanged.
- `rehibernateAfterFailedResume` keeps its name (ticket `strand-wake-during-quiesce-is-told-the-strand-is-up` refers to it); its doc now says it also covers a failed window.
- Docs: `docs/architecture.md` → Strand Hibernation, mechanism 2 (check-in failing before/after the rebuild; the hand-off) and mechanism 4 (`serviceWake`'s own cleanup covers only its window).

## Deviation from the ticket — please weigh

The ticket asked for the hand-off only when the check-in leaves the strand **non-`'hibernating'`** and **`wakePromises.has(strandId)`**. I broadened it to **any status**, and to **a probe that holds the strand** even after its wake settled (its window is running):

- *Probe in its window:* the strand reads `'active'` and no wake is in flight, so the narrow rule would take it as "woke", end the chain and arm an idle countdown mid-window; if the window then re-quiesces, `endProbe` finds `hadCheckInChain = false` and the strand hibernates with no check-in — the same defect this ticket fixes, reached through a probe instead of a plain wake.
- *Status `'hibernating'` with a wake in flight* (for example, the wake is still in its own seed read): the narrow rule escalates and arms a check-in, and if the wake then brings the strand up, that check-in stays armed on a live strand (when it fires it skips and resets the idle countdown). Handing it over avoids the stray timer. Cost: if that wake fails, the chain restarts at the base delay instead of the escalated one.

If the reviewer prefers the ticket's narrow rule, it is a one-line guard at the top of `handCheckInChainToHolder` (`if (instance.status === 'hibernating') return false;`) plus dropping the probe-without-wake arm.

## Known gaps

- No test pins the probe-in-window hand-off arm or the `'hibernating'`-with-wake-in-flight arm of the broadened rule; only the ticket's case (plain wake, `'starting'`) is tested.
- No `serviceWake`-level test for a wake that fails before its rebuild; it relies on `handleStrandWake`'s existing test (`a wake that fails before rebuilding leaves a check-in's mid-build runtime alone`), since `wakeAndHoldForService` adds no branch of its own there beyond logging.
- The window stage still quiesces on failure even when the runtime came from a build this caller joined rather than started (a check-in whose resume joined a wake's build). That is today's behaviour, which the ticket kept; two probes running windows over one runtime is a wider issue not addressed here.
- Out of scope, unchanged: a wake that lands while a window or the timer-driven hibernate is quiescing (`strand-wake-during-quiesce-is-told-the-strand-is-up`, which builds on this ticket).
