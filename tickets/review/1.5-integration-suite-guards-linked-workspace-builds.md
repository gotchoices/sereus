# Review: stale-build guard extended to the linked sibling workspaces

## What the problem was

The integration suite runs compiled output, not TypeScript sources. It already
refused to start when one of this repo's own packages had been edited without a
rebuild, but it had no opinion at all about the two sibling projects it depends
on — `../optimystic` and `../quereus`, which reach `node_modules` as symlinks
into their working copies (via `resolutions` in the root `package.json`).

Those siblings are worked on at the same time as this repo, so the suite ran
whatever they last *built*. An `@optimystic/db-p2p` fix landed at 01:47, the
package was not rebuilt until 02:17, and in between a replication bug was filed
and investigated three times against compiled code that predated its own fix.

## What was built

`build-freshness.ts` gained a second kind of target. A `BuildTarget` now carries
`location: 'workspace' | 'linked'`:

- **workspace** — unchanged behaviour: found by scanning `<repo>/packages`,
  remedy `yarn workspace <name> build`.
- **linked** — found by reading `node_modules/<name>` as a symlink
  (`resolveLinkedPackage`), remedy names the sibling's own checkout, e.g.
  `Run in C:\projects\quereus: yarn workspace @quereus/quereus build`, because
  `yarn workspace` cannot reach outside this repository. The checkout is found
  by walking up from the link target to the nearest `package.json` that declares
  `workspaces`; with no such ancestor it falls back to
  `Run in <package dir>: yarn build`.

`checkBuildFreshness` — the newest-`src`-mtime versus `dist`-entry-mtime
comparison — is untouched, as the ticket required.

Six linked targets were added: `@optimystic/db-core`, `db-p2p`,
`db-p2p-storage-fs`, `quereus-plugin-crypto`, `quereus-plugin-optimystic`, and
`@quereus/quereus`. Sibling entry points differ from this repo's: tsc-built ones
are `dist/src/index.js`, the two tsup-built plugins are `dist/index.js`.

### Two decisions worth reviewing

**Registry copies are skipped, not judged.** Linkedness is decided by
`lstat().isSymbolicLink()`, never by package name — which of these are linked
changes with `resolutions` and with whoever last ran `yarn install`. A real
directory (installed from a tarball) is skipped outright: its `src` and `dist`
mtimes are packing artifacts. This is not hypothetical — the installed copy of
`@optimystic/db-p2p-storage-fs` has `src` 13ms newer than `dist`, so judging it
would report a permanent "stale" that no build can clear.

**A stale sibling fails the run** (option 1 of the three the ticket listed),
with the reasoning written at the site in `checkLinkedTarget`'s doc comment. In
short: a warning banner is ignorable, and being ignored is exactly how the
original investigation went wrong; and a grace margin cannot distinguish "the
neighbour is mid-edit" from "someone forgot to build", because both present
identically as `src` newer than `dist` — if anything the forgotten build is the
*more* recent of the two. The accepted cost is stated below under **Known gaps**.

## How to validate

Unit tests (19, all passing):

```
cd packages/integration-tests
yarn exec vitest run src/harness/build-freshness.spec.ts
```

Note this needs the suite's `globalSetup` to pass first — which is the guard
itself. If a sibling is currently stale the spec cannot run through the package's
own config; run it with a config that omits `globalSetup` (that is how it was
validated here).

New coverage, on temp-directory fixtures shaped like the real wiring
(`<tmp>/node_modules/@sibling/pkg` → `<tmp>/sibling-repo/packages/pkg`):

- symlink resolves to the working copy it points at
- real directory reports `not-linked`
- entry absent → `unresolved` ("not installed")
- symlink whose target was deleted → `unresolved` ("no longer exists")
- linked + freshly built → silent
- linked + edited after build → stale, message names the sibling checkout
- linked + never built → missing, message names the sibling checkout
- linked outside any workspace → falls back to `Run in <dir>: yarn build`
- **registry copy with `src` newer than `dist` → skipped** (the regression most
  likely to reappear as a spurious permanent failure)

The tests create links with `symlinkSync(target, path, 'junction')`, which
avoids needing developer mode or admin rights on Windows and is ignored on
POSIX.

End-to-end, against the real tree:

```
yarn workspace @serfab/integration-tests test build-freshness
```

At the time of writing this produced, correctly:

```
Stale build detected: these tests run real compiled output.
  - @quereus/quereus: dist is stale — src was edited after the last build. Run in C:\projects\quereus: yarn workspace @quereus/quereus build
```

`../quereus` really was mid-edit (newest `src` 05:50, `dist/src/index.js` built
05:32). Everything else in that same run passed silently — the three `@serfab/*`
packages, the five fresh linked optimystic packages, and the skipped registry
copy of `db-p2p-storage-fs`.

Also run: `yarn workspace @serfab/integration-tests typecheck` and `yarn lint`,
both clean.

## Known gaps

- **The all-fresh full-suite start was never observed.** `../quereus` was
  genuinely stale for the entire duration of this ticket, so every real run of
  the suite aborted at the guard — which is the intended behaviour, but it means
  "guard passes, suite proceeds to run scenarios" was not demonstrated
  end-to-end. That path is the pre-existing `if (problems.length === 0) return;`
  and every individual target's fresh/skip result *was* observed in the run
  above, but a reviewer with a fresh `../quereus` should confirm the suite
  actually starts.
- **Consequence of the hard-fail choice:** while a sibling repo's own automation
  is mid-edit, this suite will not start for anyone — including other tickets in
  this repo that run integration tests. The message names exactly what to
  rebuild and where. If this proves too disruptive in practice, the softer
  options are documented in the original ticket and the reasoning for rejecting
  them is in the code comment.
- **Junction handling was only exercised on Windows.** The `'junction'` argument
  is ignored on POSIX, where an ordinary symlink is created and the same
  `isSymbolicLink()` / `realpath` path runs — but that was not observed on a
  Linux host.
- **The tsup-built plugins were only seen in the fresh state.** Their stale and
  missing paths are covered by fixtures, not by a real stale plugin.
- Two tripwires were recorded as `NOTE:` comments rather than tickets, both in
  `build-freshness.ts`: linked packages are looked for only in the repo-root
  `node_modules` (where yarn hoists a `link:` resolution today), and each
  `distEntry` is written out rather than read from the target's own
  `main`/`exports`.
- `docs/STATUS.md` → "Testing / CI" gained an entry describing the extension.
