# Cancel + list outstanding invitations — review

Final slice of a feature that landed across four implement runs: source
(`strand-invite-cancel-writer`), docs (`3.7-strand-invite-cancel-tests-docs`), tests
written (`3.7-strand-invite-cancel-tests`), and this run — the validation sweep that
executed those tests for the first time.

## What the feature does

A closed (private) strand's managers can now kill an outstanding invitation, and can ask
which invitations are still redeemable.

- `cancelInvite(db, { managerKeyPair, inviteKey })` files one permanent
  `Strand.CancelledInvite` tombstone row, manager-signed over the exact invite key. The
  `Invite` row itself is left alone — cancellation is a tombstone, not a delete. Repeat
  calls are a quiet no-op, so a restart mid-flow is safe. Un-cancelling is impossible; to
  re-invite someone, issue a fresh invitation.
- `Strand.ConsumedInvite`'s `NotCancelled` check is what enforces it: redeeming a
  cancelled invitation is rejected at commit and rolls the entire join back, so no
  half-joined member survives.
- `listOutstandingInvites(db, nowMs?)` returns the `Invite` set minus consumed keys, minus
  cancelled keys, minus anything past its expiry. "Outstanding" is not a column —
  `Strand.Invite` is insert-only and carries no state — so it is computed. Expiry is
  exclusive: an invitation is dead AT its expiry instant.
- `StrandMemberVerifier.isAuthorizedToJoin` uses the same computation as its "is the door
  open" pre-flight, so it no longer reports a door that `NotCancelled` would slam.

## The one real weakness found, and fixed

Constraint-violation messages carry only the **bare** constraint name — `CHECK constraint
failed: Authorized`, with no table qualifier. Six different tables in `schemas/strand.qsql`
declare a constraint named `Authorized`, so a `/Authorized/` assertion cannot tell which
table rejected the write. That is harmless in tests where only one table is written, which
is most of them — but the test at
`packages/cadre-core/test/strand-membership-invite.spec.ts:492` ("rejects a cancellation
authorized by a manager seated in the SAME transaction") writes to `Manager` *and*
`CancelledInvite` in one transaction, and `Manager` has an `Authorized` check of its own.
As written, a regression that made the manager promotion itself illegal would have kept
that test green for the wrong reason.

A probe confirmed the promotion leg does commit on its own, so the rejection was in fact
`CancelledInvite.Authorized`. That reasoning is now encoded in the test rather than left
implicit: it commits the promotion alone (asserting the `Manager` count reaches 2), then
performs the same cancellation successfully now that the manager is committed. This is the
only change to the tests this run.

## Suggested review focus

- **The positive control just added** (`strand-membership-invite.spec.ts:507`-onward) is
  the newest, least-reviewed code in the diff. It asserts the promotion commits and the
  cancellation then succeeds — check it is asserting what it claims and has not made the
  test test two things badly.
- **`scanInviteKeys` (line 558) reads whole columns rather than filtering by key** and
  compares in JavaScript, deliberately, because a full-primary-key where-equality can miss
  on a networked strand. Correctness depends only on the scan returning a superset of live
  rows. Every strand test runs against local `MemoryRawStorage`, so the networked failure
  mode this defends against is not exercised anywhere — the reasoning is inherited from
  `scanMemberPeers` and is worth a skeptical read rather than a nod.
- **Cross-check the doc blocks against behavior.** `cancelInvite`'s and
  `listOutstandingInvites`' doc comments make specific claims (which constraint fires when,
  that cancellation is what makes removal a re-entry gate). They now agree with observed
  behavior wherever a test looks, but they claim more than the tests check.

## Known gaps — carried forward honestly, not resolved

- **The bare-constraint-name hazard is repo-wide, and one sibling test still has it.**
  `packages/cadre-core/test/strand-member-revocation.spec.ts`'s "rejects a revocation
  authorized by a manager seated in the SAME transaction" has the identical two-candidate
  ambiguity that was just fixed on the cancel side, and was left alone as pre-existing and
  outside this ticket's diff. Parked as a comment at the fixed site
  (`strand-membership-invite.spec.ts:507`) explaining why the control is there, so the next
  person to write such a test meets the reasoning.
- **No test covers `cancelInvite` on an open strand.** `OnlyClosed` would fire, but so
  would `Authorized` (an open strand has no founding manager), so the rejection could not
  be pinned to one constraint. Deliberately skipped rather than asserted vaguely — a
  reviewer may disagree and want it asserted loosely.
- **`listOutstandingInvites`' documented "in storage order" guarantee is effectively
  untested.** The multi-row assertions index results by key, not by position.
- **Mutation coverage was applied only to `listOutstandingInvites`**, whose logic is plain
  JavaScript. `cancelInvite`'s insert and the `NotCancelled` schema clause were not
  mutation-tested, since mutating the schema requires rebuilding the plugin package. Their
  evidence is weaker but not absent: the captured messages show those exact constraints
  firing by name.
- **The `NotCancelled` rejection and its rollback assertions share one test** rather than
  being split. Matches the spec file's own convention for its sibling wrong-key and
  expired-invite atomicity tests; splitting them is a style call.
- **A stale `dist/` in `@serfab/quereus-plugin-sereus` produces a false green** in
  `cadre-core`, because `cadre-core` loads the embedded strand schema from that package's
  build output and the root test wiring does not build first. Already filed as
  `backlog/debt-embedded-schema-stale-dist-false-green`. Build that package before
  trusting any strand test run.
