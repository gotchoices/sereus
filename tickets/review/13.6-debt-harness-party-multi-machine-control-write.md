## New: `harness-party-control-cohort.integration.ts`

Background a reader needs: a party's control database (members, strands, invitations)
is replicated across the party's machines. Each write is offered to a set of them — the
**cohort** — and commits once a super-majority approves. A cohort of ONE commits on the
writer's own vote, so a control write that merely passes is equally consistent with
"three machines agreed" and "one machine wrote to itself". Until this file, no harness
scenario had ever checked which of those it got.

Three cases, all against parties of one owner + two drones:

- **Case 1 — the drone cap.** No writes. From the owner, the cohort reaches all three
  machines. From a drone, it reaches two (itself + the owner) and asking for three
  **times out**, asserted on the observed-size text in the error, not merely on "it
  threw". This is the executable form of the finding recorded by
  `debt-harness-record-fret-ring-convergence-finding`: drones dial only the owner, never
  each other, so a drone-coordinated write caps at two machines permanently.
- **Case 2 — a real, unforced write into a waited three-machine cohort.** Waits for the
  cohort, starts an observer, issues one real `createStrand` (the same path `happy-path`
  uses, through the real `CadreControl` CHECK constraints), reads the row back.
- **Case 3 — a forced three-machine cohort.** `forceFullCohort` then `pinCoordinator`
  (force first — the pin wraps whatever is installed), one write, restore in reverse.

## Measured — 5 consecutive runs of the file alone, plus 1 mixed run

| | outcome | latency |
|---|---|---|
| case 1, drone cap | 5/5 as described | ~8.4–8.7 s (its own 8 s probe budget dominates) |
| case 2, waited real cohort | **5/5 COMMITTED** | 745–987 ms |
| case 3, forced cohort | **5/5 COMMITTED** | 223–374 ms |
| whole file | 5/5 green | ~23 s |

Per the implement ticket's decision tree, that is the "commits every run" branch, so both
writing cases are plain `it` — no `it.fails`, no weakened assertion. The
super-majority/unanimity failure that `debt-control-write-unanimity-at-three-nodes`
tracks did **not** reproduce here, and on reflection should not: that fragility is about
one of the three machines being slow or silent (measured in
`control-write-degraded-cohort-member.integration.ts`), not about three healthy ones. The
file's header says so and says what to do if it ever starts reproducing.

The anti-vacuity evidence, verbatim from a run — case 2 recorded cohort sizes
`[3,2,2,3,3,2,2,3,...]` and case 3 recorded `[3,3,3,...]`. That mix in case 2 is the
point: `observeControlCohorts` patches the prototype, so it records selections from every
node in the worker and the drones legitimately see 2.

# Where to push hardest (known gaps — treat the above as a floor)

- **Case 2's claim is `some(size >= 3)`, not `every`.** It has to be — the recorded sizes
  are process-wide and include the drones' correct 2s. That makes it a weaker statement
  than case 3's `every === 3`. Worth asking whether a per-node view
  (`readControlCohort(party, node)`) could tighten it, and whether the in-file comment
  warning the next reader off `.every` is prominent enough.
- **The read-back asserts `queryStrands().length >= 1`, not the specific strand id.**
  Each writing case owns a fresh party that writes exactly one strand, so the row can
  only be that one — but the assertion does not say so. `network.createStrand` returns
  the strand, and the local `settle` helper discards its return value, which is why. A
  reviewer may reasonably want `settle` made generic so the id can be matched.
- **The `it` timeouts (180 s) are ~200x the measured latency.** They are sized for the
  unanimity failure path (two 10 s response-deadline attempts per pend round) that did
  not reproduce. Defensible, but nobody has seen them fire.
- **Never measured under load.** Every number above is this file alone or with two fast
  siblings, on one machine over localhost. `fileParallelism: false` and per-file worker
  isolation make the process-wide prototype patches low-risk, but that is reasoning, not
  a measurement. The whole-suite run was not performed.
- **Case 1's 8 s probe is a deliberate timeout.** If a future change ever lets drones
  dial each other, this case fails as a timeout that did not happen rather than as a
  clear message. That is the intended tripwire, but the failure shape is worth a look.
- **Duplication tripwire, already parked.** `settle` and `errorChainText` are small
  restatements of helpers in `control-write-degraded-cohort-member.integration.ts`. Two
  copies in two scenario files was judged cheaper than a harness module with one
  importer; a `NOTE:` at the definition site in the new file says to extract all of them
  into `harness/` if a **third** file needs them. Nothing to file — check the judgement,
  not the arithmetic.
