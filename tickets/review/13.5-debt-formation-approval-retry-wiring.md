# Wire the approval retry up through the join handler, comments, and docs

Downstream of `debt-formation-approval-retry-lost-race` (complete), which made a redemption
that loses a use-number race retry the SAME approver sign-off under a fresh use number, and
added an exported `InvitationExhaustedError` for the case where no seat remains. This ticket
brought the join handler, a schema comment, and three docs in line with that. No behaviour
changed on the success path.

## What shipped

All in `packages/cadre-core/` unless noted.

### `src/strand-formation-manager.ts`

- `provisionAsResponder`'s catch block now has a dedicated branch for
  `InvitationExhaustedError` (imported from `control-database.js`), placed after the
  `FormationApprovalError` branch and before the generic catch-all. It logs the token,
  attempted use number, and limit, then returns `{ approved: false, reason: 'Invalid token' }`
  — deliberately the SAME string `strand-formation-protocol.ts` already sends when the
  up-front `validateToken` finds the invite used up, so the race loser sees exactly what a
  non-racing latecomer sees. No new wire-visible distinction between "invalid" and
  "exhausted" is introduced; the operator signal lives in the log line.
- The stale `NOTE:` at that catch-all (claimed an obtained approval is DISCARDED because "this
  path does not retry", pointing at a ticket path that no longer exists) is replaced: an
  approval reaching here was RETRIED by the database layer, and landing in this catch-all
  means either that retry ran out (now surfaced above as `InvitationExhaustedError`) or the
  failure was never retryable.
- The class-level doc comment above `provisionAsResponder` (~line 267) was left as-is — it
  describes the general defense-in-depth pattern ("known failures... mapped to a logged,
  retry-suggesting rejection") and isn't specifically wrong, just no longer exhaustive now
  that one named failure is deliberately non-retry-suggesting. Judgment call; flagging for the
  reviewer rather than editing further.

### `schemas/control.qsql` + `src/control-schema.ts` (byte-identical edit, both copies)

`FormationUsage.Monotonic`'s CHECK comment now names `ControlDatabase`'s use-number retry
(`withUseNumberRetry`) as what resolves the `(Token, UseNumber)` PK collision, and notes the
deferred check itself is the OTHER surface the same race can take — a concurrent row the
inserting transaction's key probe didn't see trips `Monotonic` at commit instead of the PK.
`control-schema-drift.spec.ts` passed, confirming the two copies match.

### `docs/architecture.md`

New paragraph in the Strand Formation section (after the provisioning-timeout-ladder
paragraph, before the mermaid diagram): a redemption that loses the LOCAL use-number race is
retried with the identical approval rather than sent back for a fresh one, so the approval
hook is asked once per join, never once per write attempt; only an exhausted retry reaches the
catch-all as `InvitationExhaustedError`, reported the same way a spent invite is.
