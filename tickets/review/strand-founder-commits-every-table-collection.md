# The founder commits every declared table's collection before its Header

## What changed

Optimystic creates a table's collection only on its first write, so a table nobody has written has no collection and only the block's cohort (the machines responsible for it) can say it is empty. Every read of such a table asked the other member (about two relayed round trips) and threw `BlockUnavailableError` (`cohort-unreachable`) with the other member offline.

Now, on the founding run that finds no `Strand.Header`, the founder commits an empty collection for every table in the `Strand` and `App` schemas (main tree, index trees and unique-enforcement trees), then writes the Header. Peer-join backfill hands those collections to every joiner.

- **Plugin** (`@serfab/quereus-plugin-sereus`): `SereusPluginResult.createEmptyCollections(): Promise<number>` (`src/empty-collections.ts`). It opens every non-view Optimystic table in `Strand` and `App` with `select 1 … limit 1`, which initialises the vtab and registers its trees with the transaction bridge. It throws, naming the table, if any declared table's main collection id is missing from `txnBridge.getCollectionRegistry()`. Then it `sync()`s every registered collection still in the invented state (`committedRevision() === undefined && hasUnsyncedChanges()`) and returns the count. The id rule mirrors the vtab's `parseTableSchema` (explicit `vtabArgs['0']`, else `defaultCollectionUri(table.schemaName, table.name)`, with `tree://` stripped); the real ids are lowercase-schema, e.g. `default/strand/Revocation`, `default/app/Post/index/PostByAuthor`, `default/strand/Member/index/_uniq_7.stampid`. The prior (interrupted) run committed this file, the `compose-strand.ts` wiring and the `types.ts` field; this run left them as they were.
- **cadre-core**: `FounderBootstrapParams.createEmptyCollections` is **required**. `StrandDatabase` passes the composition's step. `bootstrapFounderMembership` validates first (closed strand needs a founder key; pre-split check), then `foundIfHeaderAbsent`: if `Strand.Header` has a row, it logs and skips both the collections and the Header; otherwise `createDeclaredCollections` (logs count and elapsed ms), then `insertHeader`. The old `insertHeaderIfAbsent` became `foundIfHeaderAbsent` + `insertHeader`, so the Header count is read once.
- The `strandHasManagerRevocation` NOTE about `Strand.Revocation` consulting the cohort on every read is deleted (no longer true); the table-growth NOTE stays.
- Docs: `docs/strands.md` "Joining" gains the rule as a bullet under "What the runtime does", and its first residual is narrowed to tables a later app schema version adds (linking `backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`). `docs/architecture.md` § Strand Membership Bootstrap gains one item. The plugin README gains a short section. The first-sync gate's header comment no longer says a never-written table reads as absent everywhere.

## Measured cost (NOTE at `createDeclaredCollections`)

Lone node, network transactor, `connectToStrand` then the step alone, 3 runs each (temporary spec, deleted):

| schema | collections | in memory | `FileRawStorage` |
|---|---|---|---|
| nine-table scenario schema | 20 | 32–82 ms | 465–486 ms |
| reference chat schema (`chat-simple.qsql`) | 13 | 19–30 ms | 298–350 ms |

About 23 ms per collection on disk, once per strand, before `foundStrand` returns. Not batched; the tripwire (commit them as one coordinator batch, like `commitBatchLegacy`) is in the NOTE. In the read-cost scenario, `foundStrand` took 916 ms with the step (1158 ms in the run before the fix, so the difference is within noise at that size).

## Known gaps / for the reviewer

- **Two slow-link arms are red because of this change: filed as `fix/slow-link-restart-arms-lost-their-lone-commit` (prereq: this ticket).** These are the fourth and fifth arms of `joiner-first-commit-over-slow-relay` (20 ms per-frame cap, 70%-busy event loop). They fail at the joiner's first transaction with `Failed to get super-majority: 1/2 approvals … The stream has been reset`: 3 of 3 runs with the change, against 1 of 1 passing with the step disabled (temporary edit plus rebuild, restored). Those arms depend on the joiner's first commit being saved alone. With every table's collection on the founder, the joiner is connected to the founder when it becomes writable (seen in arm 3's log), so the commit needs the founder's approval. On that link the founder's leg is reset, plausibly by the ping-handler connection drops in `blocked/optimystic-ping-handler-timeout-below-the-monitor-deadline` (the mechanism is inferred, not traced). I did not rewrite the arms, because what they should test now is a decision; the fix ticket carries the evidence, the recommended reading and the options. A reviewer who judges the new phone-link behaviour unacceptable should say so there before this ships.
- **Tables added by a later app schema version** are not covered, by design (see docs/strands.md residual and the backlog ticket).
- **`ensureFounderBootstrap` on a live instance** (`foundExistingStrand`): the step runs only when the Header is absent. A published joiner database always holds the Header (the first-sync gate publishes only after it), so the step can only run against a still-gated database, which no app writer or the membership reconciler can reach (both read `instance.database` lazily). Verified by reading `StrandInstanceManager.foundExistingStrand` and the gate, not by a test.
- **Durability reports**: these syncs bypass the transaction bridge, so `onCommitDurability` reports nothing for them; intended (no row an app would ask about).
- Founding-time storage cost rose about 4.75× in operation count (80 → 380 for the solo launch). Judged acceptable for a once-per-strand action; the batching tripwire is recorded.
