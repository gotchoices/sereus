# The offline queue waits for the party's machines that hold the strand (gotchoices/sereus#56)

## What was built

Optimystic's own reachability gate knows only the peers a strand node has itself met, so a sibling whose strand port was blocked when the strand launched never counted, and a queued transaction was committed by the phone alone. Cadre-core now composes a second gate over the node's own, built from the party's control database: a block whose cohort names nobody but this node is unreachable while another machine of the party has written a `CadreControl.StrandPeer` row for the strand and is a live, trusted machine. Only a node offering offline mode (`CadreNodeConfig.strandOffline`) builds it, and the plugin asks any gate only in offline mode, so online mode is unchanged.

- **`strand-party-peers.ts`.** `PartyStrandPeers.live` is now `PartyStrandPeer[]` (`{ peerId, strandPeerId }`), one entry per strand peer id, so an app can name a machine. `removed` is unchanged and still never holds a live id. The reconciler and the rotation driver map to `strandPeerId`.
- **Open strands get a `StrandPeer` row too.** `CadreNode.launchStrand` wires `partyPeers` for every strand and `buildStrandRuntime` publishes the row for every strand; the reconciler still arms for closed strands only. One immutable control row per (strand, machine), on every node, offline-capable or not.
- **`strand-party-machines.ts` (new).** `StrandPartyMachines` keeps the last good read of the party's other machines holding one strand: `refresh()` is coalesced (a refresh during a read runs one more read after it), a failed read logs and keeps the last answer and is flagged by `lastReadFailed()`, `settled()` resolves after the first read either way (and on `stop()`), `onChange` fires only when the set changes. `cohortGateWaitingForMachines(inner, keyNetwork, selfId, machines)` is the composed gate, in the ticket's order: inner closed answers closed and reads nothing further; await the first read and ask for another after a failed one; no machines answers open; a distinct block whose `findCluster` names nobody but self, or throws, answers closed. One log line per change of answer.
- **Wiring.** The tracker is built in `buildStrandRuntime` before `createLibp2pNode` when `config.offline` and `config.partyPeers` are both present, its first read started at once, stopped in `releaseRuntime`, refreshed by `notifyPartyPeersChanged` (the node's `StrandPeer`/`CadrePeer`/`Revocation` watch). `buildStrandDatabase` builds the gate from `node.cohortReachability`, `node.keyNetwork` and the tracker, logging and building none when the node carries neither; it reaches the plugin through `StrandDatabaseOffline.cohortReachability` and `StrandConnectionOptions.cohortReachability`, which `composeStrand` registers with `collectionFactory.registerCohortReachability(`${transactor}:libp2p`, gate)` right after the node is registered and before hydrate opens any table. `Libp2pNodeWithRepo` gained `cohortReachability?` and its `keyNetwork?` now also carries `findCluster`.
- **`CadreNode.getUnreachedStrandMachines(strandId)`.** The tracker's machines less those with an open connection (`status === 'open'`) from the strand node, by control peer id and strand peer id. Empty on a strand not running here or a node without offline mode.
- **Redial.** `StrandRedialDeps.partyMachines?: () => readonly string[]` feeds the strand peer ids to the loop; `knownMembers` adds each eligible one not already known at the addresses the node's address book holds for it (`RedialNode.peerStore.get`, `NotFoundError` read as none) and skips one with none; `memberConnected` counts a connected party machine as a member, as it counts a seed peer, whatever FRET's label.
- **Docs.** `docs/strands.md` gained the section *Waiting for the party's own machines* under Offline mode, and the three cross-references the ticket named (the acknowledgement promise, *Binding the party's machines*, the offline paragraph of *Writable does not mean connected*); `docs/testing.md` lists the scenario in the offline-mode group.

Deviations from the ticket's interface sketch: `CohortGateMachines` picks `lastReadFailed` as well, since the gate's retry rule ("a last read that failed asks `refresh()` again") needs it; nothing else differs.

## How to use it

- An app in offline mode reads `strand.database.offline.status(tx)`; while the hold applies it stays `queued` with `waitingFor: 'cohort'`, and `node.getUnreachedStrandMachines(strandId)` names the machines, whose `peerId` is what `listMachines` and `removeMachine` take. Nothing releases the hold on its own.
- Debug logs: `sereus:cadre:strand-party-machines` (the tracker's reads, the gate's changes of answer), `sereus:cadre:strand-redial` (party machines dialed).

## Known gaps and things to look at

- **The scenario cannot tell the redial loop's dial from FRET's.** It asserts the strand connection is outbound from the phone and that the node never dialed, but FRET's stabilization on the phone's strand node may also dial a peer whose address sits in the address book. The loop's decision is pinned by the unit case; whether the scenario's reconnect is the loop's was not traced. The ticket said the hold does not depend on the redial.
- **The budget interpretation is inferred.** The two extra tree-block consults in `foundStrand`'s control phase coincide with the logged `StrandPeer` refusal in that phase; which blocks they are was not traced below the hashed ids. A reviewer who wants certainty can disable the publish and re-measure.
- **Per-heartbeat tracker reads.** `notifyPartyPeersChanged` fires on every party machine's `CadrePeer` heartbeat and now costs one control read per running strand on an offline-capable node. Parked as a `NOTE:` at the watch in `cadre-node.ts` with the narrower trigger to move to if it shows in a profile.
- **A machine that stops running the strand keeps counting** until removed from the cadre (its row is permanent). `NOTE:` on `StrandPartyMachines` with the revisit condition, as the ticket asked.
- **A stalled control read would stall the gate**, and offline live reads with it. `NOTE:` on `StrandPartyMachines`; today's read is the local one measured in milliseconds.
- **Open-strand rows are written on every node**, including always-on programs that never offer offline mode, since the publish does not know whether a sibling is a phone. The ticket's decision; the cost is one row per (strand, machine).
- **The sibling `../optimystic` was being edited during this run** (uncommitted changes in `quereus-plugin-optimystic`, its dist rebuilt by that agent at 22:12). Nothing here depends on those changes; the stale-build guard did not fire, and no sibling was built from here.
- **`removing-a-machine-releases-an-offline-queue-waiting-for-it`** (backlog) is the follow-on: a removed machine this node once met or seeded still counts in Optimystic's own gate. `feat-offline-hold-starts-when-a-node-is-claimed` holds the window between adding a node and its first row.
