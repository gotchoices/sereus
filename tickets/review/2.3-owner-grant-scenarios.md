# Owner grants: integration scenarios (review handoff)

`owner-grant-node-api` added `createOwnerGrant`, `redeemOwnerGrant` and `joinWithOwnerGrant` with in-process unit tests. This ticket runs them across real libp2p nodes over loopback WebSocket, with the household shape `cadre-invite-any-member` uses: a phone-shaped owner O that listens nowhere and one always-on member M that pins O's key and was admitted the owner-online way (`addDrone` plus seed delivery).

## What was built

**Harness** (`harness/cadre-invite.ts`, `harness/node-fixtures.ts`):

- `startPartyDevice(partyId, key?)`: a phone-shaped node started in the party on an empty store (no listen address, no pinned key, no strand, stable identity). It is used for every holder and the fresh device.
- `waitingForMember(budgetMs, label, redeem)`: runs any redemption call with `waitForMember: true` under an abort budget, logs every pass that found no member ready, and returns `{ result, passes }`. `passes` is the most passes any one redemption needed. `joinWithOwnerGrant` reports both of its redemptions (the grant, then the self-invitation) through one callback and each counts from 1, so `passes === 1` means both succeeded on the first pass. `redeemWaitingForMember` now wraps it, with its signature and behaviour unchanged.
- `machinePeerIds(node)`: the sorted peer ids from `listMachines`.

**Scenario 1, `owner-grant-without-machine.integration.ts`.** O (from `buildPhoneOwner`, which uses a 2 s reconcile so O's anchor follows replicated rows on its own) and M form a cadre. O mints a single-use grant labelled "hardware key", and the test checks that the bundle names only M's addresses and pins O's key. H, a party node on an empty store, redeems it over the protocol with a fresh `createTestOwnerKey()` signer.

Checks:
- one pass;
- the result `{ ownerKey, alreadyOwner: false, memberPeerId: M }`;
- M's anchor derives the key under `chain` provenance (M pins only O), and M's `listOwnerKeys` contains `{ label: 'hardware key', vouchedBy: O's key, heldHere: false, trusted: true }`;
- H is not an authorized member on M;
- O, which did not write the row, derives the key (`chain`) and lists the same entry, and O's `listMachines` is unchanged from before the redemption;
- H2, with another key, is refused `OwnerGrantRejectedError` `grant-spent`, `retryable: false`, and M holds no row for that key.

**Scenario 2, `owner-grant-backup-recovery.integration.ts`.** O and M form a cadre, with M on a 2 s reconcile. O mints a backup grant (`expiresInMs: null`, label "paper backup"). The test checks `expiresAt` is null and `reach` is `local-network`, which means the grant names a machine other than O. It waits until M holds the live grant row, stops O, and waits until O leaves M's control cohort (about 1 s in every run, as in `cadre-invite-any-member`). F, a party node on an empty store, calls `joinWithOwnerGrant` with a fresh key.

Checks after the join:
- one pass per redemption;
- `{ peerId: M, ownerKey, alreadyOwner: false, ownerWired: true }`, and `isOwner()` is true;
- M derives F's key under `chain` provenance and lists it with label "paper backup" and `vouchedBy` O's key;
- F's machine row on M is trusted with `vouchedBy` F's own key, which shows its self-invitation admitted it.

Then F removes O's machine (`removedPeer: true`) and O's owner key with `revouch: { peers: [M] }`. The result is `{ removed: true, revouched: { owners: [], peers: [M] } }`.

Checks after the removal:
- on F, M is still trusted and now vouched by F's key;
- on M, O's machine and O's `OwnerKey` row are gone;
- M's anchor drops O's key within its refresh window and keeps F's key;
- M's `listOwnerKeys` is exactly F's key, and M still lists F as authorized.

The `revouch` is required. O's key vouched M's row, so without it M would stop passing the membership predicate on every machine. F's own `OwnerKey` row names O as its voucher (the grant's issuer); it stays in M's anchor because M derived it while O was live. This is the documented "kept" rule.

**Docs.** The "Owner grants" Proof line in `docs/architecture.md` and its Testing section now name both scenarios. The header of the cadre-core owner-grant spec points at them in place of this ticket. `docs/testing.md` is not changed. Its scenario list is the topology map, which leaves out scenarios whose subject is a protocol. `cadre-invite-any-member` is not listed there either.

## Tests added

| Test | What it verifies |
| --- | --- |
| `owner-grant-without-machine.integration.ts` | A key with no machine becomes an owner through the only always-on member. The member derives it, and so does the owner that did not write it. No machine row appears. The commit happens on the first pass. The exchange with a stranger is not cut at the provisional connection deadline. A spent single-use grant is refused by name. |
| `owner-grant-backup-recovery.integration.ts` | With the issuer offline and its cohort entry gone, the member, alone with the holder, commits both redemptions on the first pass; this is the point of pushing the control store to the holder. Self-admission is checked through the voucher on the machine row. The new owner removes the lost phone's machine and owner key while keeping M through `revouch`, and the member's anchor follows. |

No unit tests were added.

## Known gaps and judgment calls for the reviewer

- **The issuer is never offline at redemption in scenario 1.** The ticket's edge case "anchor derivation on a machine that was offline at redemption (O in scenario 1, if it reconnects after)" is covered only in the weaker sense: O stays online, so the check is that a machine that did not write the row derives it. A returning issuer deriving a grant-seated key after a restart is not exercised. `cadre-invite-any-member` covers that path for invitation-seated keys, including its read-repair delay. Adding a stop and restart of O would cost about 10 s and a captured store.
- **The backup grant is single-use** (the default `uses: 1`). After F's join, nothing over the network exercises the removal plan's `grants` list for a live multi-use backup. The unit spec covers the plan.
- **H2's refusal is a single pass without `waitForMember`,** as `cadre-invite-any-member`'s Q is. A dial failure there would show as `OwnerGrantUnreachableError` rather than `grant-spent`, which is a real failure either way.
- **Not consolidated:** the local `buildDevice` in `cadre-invite-any-member` and `cadre-invite-row-unreplicated` does the same job as `startPartyDevice`. Those files were left alone to keep this diff scoped.
- **The single-use race across two machines** gets no scenario, by the accepted tradeoff at `OwnerGrantUsage.Authorized`.
- **No pre-existing failures** were seen in what was run.
