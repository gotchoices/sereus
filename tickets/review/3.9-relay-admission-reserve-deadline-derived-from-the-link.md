# Review: relay admission's reserve deadline derived from the declared link

## What changed

- `link-budget.ts`: new `RELAY_RESERVE_REQUEST_ROUND_TRIPS = 1` (doc carries the reasoning: the client's last handshake message and hop-stream open arrive together, gate arms the timer, relay answers negotiation, client's RESERVE arrives one round trip later) and `relayAdmissionReserveDeadlineMs(link?) = 1 × link + ADMISSION_DECISION_TIMEOUT_MS` (5 500 ms at default). The table's reservation-request row is pointed at the constant by a sentence under the table (the table has no column for constant names). "What still fails": the "One cadre deadline still typed as milliseconds" bullet is deleted (formation had already landed, so nothing remains in it); the "faster link than its peers" bullet gains relay admission.
- `membership-connection-gater.ts`: `RELAY_ADMISSION_RESERVE_DEADLINE_MS = relayAdmissionReserveDeadlineMs()`; lint directive removed; comment says CadreNode passes the relay's own declaration.
- `cadre-node.ts`: gater now gets `ADMISSION_DECISION_TIMEOUT_MS` and `relayAdmissionReserveDeadlineMs(network?.linkRoundTripMs)`.
- Docs: architecture.md derived-list entry added, known-limit bullet deleted, control-gate bullet's "~5 s" replaced with the derivation. Integration-scenario comments and the backlog bug's figure updated to 5.5 s.

## Tests

- One `expect` added to link-budget.spec.ts's existing "multiplies each operation's round-trip count …" test, pinning the formula. No other test.

## Validation run

`yarn lint` (exit 0), `yarn workspace @serfab/cadre-core typecheck` (exit 0), `vitest run link-budget membership-connection-gater` (60 passed). The integration scenario `relay-only-control-addr` was not run; its drop wait is 10 s against the new 5.5 s deadline (was 5 s), so it still has 4.5 s of margin by inspection.
