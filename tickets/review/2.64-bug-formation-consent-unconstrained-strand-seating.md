# Review: constrain what a redeemed invitation may seat

## What was built

Two schema CHECK-constraint edits (applied identically in `schemas/control.qsql` and the
`CONTROL_SCHEMA` string in `packages/cadre-core/src/control-schema.ts` — the drift spec
confirms byte parity):

- **`FormationUsage.Authorized`**: a bound invite (`FormationInvite.StrandId` non-null) may
  only record usage against its own named strand — `and (FI.StrandId is null or
  FI.StrandId = new.StrandId)`.
- **`Strand.AuthorizedInsert` consent branch** narrowed to four clauses: the seated strand
  must be open (`Type='o'`) and keyless (`MemberPrivateKey` null), the redeemed invite must
  be **unbound**, and the id must never have been consent-seated before under any other
  stamp (**once-ever** — `FormationUsage` is append-only, so the first redemption's record
  survives removal and forecloses re-seating). Per-clause rationale lives in the schema
  comments.

TypeScript side: `ControlDatabase.redeemInvitation` lost its `type` / `memberPrivateKey`
parameters (the `Strand` insert is hard-coded `values (?, 'o', null, ?)`);
`ControlFormationUsageRecorder.provisionAndRecord` dropped `type: 'o'`. Only production
caller was `provisionAndRecord`; all other call sites were tests, now updated.
`packages/cadre-core/dist/` (checked-in build output) untouched.

**Behavior deliberately withdrawn:** consent-driven re-join of a removed strand id. Re-join
is now owner-gated — owner re-seats the id signed (fresh stamp/signature), then issues a
**bound** invite the returning party records consent against. Verified end-to-end in the
rewritten re-join test.

## Test changes (the review surface)

`control-formation-invite.spec.ts` — new `describe('consent-branch narrowing …')`:
- closed/keyed consent seating rejected (`AuthorizedInsert`), with an open/keyless positive
  control in the same shape;
- attack B (bound invite redeems against unrelated id) rejected (`AuthorizedInsert`);
- bound invite cannot consent-seat its own host before it exists (`AuthorizedInsert`);
- bound invite cannot record usage against a *different* existing strand — the one case
  isolating `FormationUsage.Authorized`;
- positive guards: unbound invite seats one open/keyless strand per use with distinct ids;
  bound record-only path accepts several invitees against one host.

`control-revocation-replay.spec.ts`:
- attack A pinned: spare use of same token cannot re-seat a removed id (`AuthorizedInsert`);
- old "fresh redemption re-forms the SAME id" test rewritten as the owner-gated re-join
  flow (fresh redemption refused, owner re-seat + bound invite succeeds);
- consent-delete test switched to plain redemption; replay "Door 2" now uses the exact
  open/keyless shape so `NotRevoked` stays the single rejector.

`control-authorization-binding.spec.ts` — the `NoUpdate` test now seats its closed
key-bearing strand owner-signed (consent can no longer produce that shape).

Rejection assertions pin constraint names via `expectConstraintFailure`; where an attack
violates both new rules, the measured engine report (`AuthorizedInsert`) is asserted.
