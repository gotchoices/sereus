# Browser reference app: owner grants

## What was built

**Owner keys card** (`OwnerKeys.svelte`; state in `lib/owner-keys.svelte.ts`; the owner-grant words and helpers in a new plain module `lib/owner-grants.ts`, copied from the phone's `owner-keys.ts` / `owner-grant-views.tsx` with "tab" for "device"):

- **Add an owner key** and **Make a backup** (owner) open `OwnerGrantForm.svelte` (name; default "Backup" for a backup; `labelProblem` disables the button over 64 characters). `makeGrant` calls `createOwnerGrant` (15 min / one use, or `expiresInMs: null`), then shows the grant once: title (`shownGrantTitle`), the bearer warning, "Valid until …, once." + where to redeem (or, for a backup, the "works only while a machine can be reached … Export this tab's key" line), the reach line when not `anywhere`, QR, copyable text, and for a backup **Download** as `sereus-owner-grant-‹name›.txt` (`grantFileName`: the label kept to letters/digits/`-`/`_`, else the grant key's fingerprint), through the same Blob-URL helper as the key export (revoked after 1 s, nothing written to browser storage).
- "Make a backup key" (fresh exported key) is gone; `OwnerKeyExportForm` now serves only Export this tab's key.
- **Outstanding owner grants** (owner): `liveGrants` (backups first), title, "Never expires"/expiry, uses left, **Withdraw** behind `window.confirm` (as the web's invitation withdrawals do), then `withdrawGrant`.
- **Redeem an owner grant** (every tab, paste only): `redeemPasted` → the store's new `redeemOwnerGrant` → `EdgeNode.redeemOwnerGrant`. A wired key makes the edge node report `running` with `enrolled`, which the store follows, so Add a device and Devices and nodes re-read; the card re-reads itself and shows `redemptionNotice` (Now an owner / Already an owner / Owner grant accepted).
- **Removal confirmation** lists the plan's `grants` (`grantRemovalLines`).
- `describeOwnerKeyFailure` tries `describeOwnerGrantFailure` first; `ADD_REFUSAL_LINE` is gone (nothing on the card calls `addOwner` now).
- `refreshOwnerKeys` reads standing, keys and grants (split into `readStanding` / `readKeys` / `readGrants`); grants are read on member tabs too, as on the phone.

**Joining:** `web-join.ts`'s `decodeInvitationForThisTab` became `decodeCredentialForThisTab` (owner grant by prefix → `decodeOwnerGrant`, else the invitation with the other-app check); the store's `joinCadre` passes the `JoinCredential` through. `join-flow.ts`: `joining` carries `asOwner` ("Joining your cadre, and setting this tab up as an owner…"), `flowForProgress(progress, asOwner)`, grant failures worded by `describeOwnerGrantFailure`, and the `StrandsNeedOwnerJoinError` line now matches the phone's ("In the app that holds your cadre, make an owner grant under Owner keys → Add an owner key, and paste it here."). `JoinCadre.svelte`: the owner-grant hint line, label "Paste response, invitation or owner grant", placeholder for both.

**`addBackupOwnerKey` removed:** `owner-key-flows.ts` (and its `generateKeyPair` / `ed25519KeyPairFromLibp2p` imports), the `cadre-core` index export, `EdgeNode.addBackupOwnerKey` (interface + class), `cadre-web.ts`'s pass-through, the cadre-rn README row and bullet, and the backup test in `owner-key-flows.spec.ts`. `grep -rn "addBackupOwnerKey\|BackupOwnerKey" packages docs` (excluding `dist`, `node_modules`) finds nothing. cadre-core `dist` was rebuilt.

**Docs:** web README (tab's owner key bullet, Adding a device, Owner keys section rewritten, Joining, file list, e2e list), `docs/architecture.md` ("A backup" paragraph now the backup grant, the `owner-key-flows.ts` paragraph, the joining line, the app table's web row, a stale "backup key" phrase at the `addOwner` alone rule), cadre-rn README (lost-slot line), `tickets/blocked/decide-owner-recovery.md` ("What exists now" no longer says the browser makes a backup key).

## Deviations from the ticket — reviewer, please weigh

- **The backup-grant e2e is in the distributed tier, not `e2e/solo/`.** `createOwnerGrant` refuses when no machine of the party has a dialable address (`issuedBundleParts`: "neither this machine nor any other machine … has an address"), and a solo tab in the e2e build has no relay, so a solo tab cannot mint any grant. The new `e2e/distributed/owner-grants.spec.ts` has the in-process `cadre-member` fixture (new `mintOwnerGrant`) mint an owner grant, the tab joins with it ("as an owner"), then makes a backup there and runs the ticket's checks (warning, QR, text, downloaded file name and contents, listed with "Never expires" / "1 use left", withdraw via the confirm dialog, list empty). This also pins the tab's owner-grant join end to end. It is a second distributed join test, but not the "join with conversations to move" one the ticket said not to duplicate; `join-cadre.spec.ts` has nothing to move and pins member standing, so it was left as is.
- **The solo `owner-keys.spec.ts` was kept, retargeted** to Export this tab's key (passphrase form, export view, QR, locked text, downloaded file), the export view and Download path the old backup-key test covered and which still exists. Cut it if that coverage is not wanted; it no longer removes a key (the tab's own key cannot be removed, and no other key exists in a solo tab).
- **The cadre-rn test "wires the owner slot's key on a party it joined" was rewritten, not deleted.** It used `addBackupOwnerKey` only to get a second owner key into the slot; it now seats a random key with `node.addOwner` and imports its export via `encodeOwnerKeyExport`. It is the only test of a joined start wiring the slot's key.

## By inspection only

- Add an owner key's shown view (only the backup path is in e2e), its reach line, and the Download being backup-only.
- Redeem on the card: all three outcomes and the refusal wording (a solo tab redeeming its own grant only answers "Already an owner"; the e2e redeems through the Join card instead).
- The removal confirmation's grant lines.
- A node replaced while a grant is on screen: `forgetIfReplaced` resets the panel with the rest of the card.
- A join with an owner grant that rolls back after the grant was redeemed: the edge node's; the card shows the failure.
- Text that is neither an invitation nor a grant in the Join field: `decodeCadreInvitation`'s own error, as before.
- A failed redemption leaves a newly created key in the slot (the existing `NOTE:` in `edge-node/owner-grant.ts`), same as on the phone.

## Known gaps / judgement calls

- **Words are hand-kept copies** of the phone's, now in two web files (`owner-keys.svelte.ts`, `owner-grants.ts`), each with the `NOTE:` saying when to move them into cadre-core.
- **"Make a backup" on a solo tab without a relay fails** with cadre-core's message (no dialable address), shown under the form. The README says so. The phone has the same precondition; neither app hides the button ahead of time.
- **Withdraw uses `window.confirm`**, matching the web's invitation withdrawals, rather than the phone's in-app prompt.
- **`grantFileName`'s sanitising** keeps Unicode letters and digits; a label of only punctuation falls back to the fingerprint.
- `cadre-web.ts`'s own `importOwnerKey` pass-through is unused (the card imports through the store); left as it was.
