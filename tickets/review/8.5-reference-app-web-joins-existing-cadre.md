# Review: browser reference app joins an existing cadre

Implemented as the implement ticket specified, following the phone kit's sequence (`packages/cadre-rn/src/phone-node/node.ts`, `strand-move.ts`, `config.ts`) over IndexedDB. Read the kit's `joinCadre` / `switchParty` / `startAndRedeem` / `returnToLeftParty` first; the web code is the same steps with these names.

## What was built

**Per-party node-local records** (`node-local-slots.ts`). The four durable records (trusted owners, bootstrap peers, enrolled machines, strand network state) are filed under `partyKvKey(key, partyId)` = `<key>.<partyId>`. Records under the old party-less keys are orphaned, unread. `PARTY_KV_KEYS` lists the four stems for the dissolve ticket.

**The start record** (`party-start.ts`, `kv` key `party-start`): `{ v: 1, partyId, origin: 'founded' | 'joined', formerPartyId? }`, one `put`. Absent → a fresh founded party is minted and written. Present but not text / not JSON / wrong shape → `readPartyStart` throws with a "clear this site's data" message, and the start fails. The old `party-id` key is never read.

**Lifecycle** (`cadre-web.ts`). `startCadre(start?)` = `bringUp(start)` (open stores, read or use the record, build and start the node, reserve the relay) + the owner step by origin + move adoption. A passed `start` is never written. A failed start now tears down what it opened before rethrowing, so the next call starts afresh (before, a node whose `start()` threw stayed as the module's node). `stopCadre` clears the node reference and closes the stores in a `finally`, so a rollback can restart over a clean slate even when `node.stop()` throws.

**Owner step.** `founded` → `runOwnerGenesis` (now reads the pair from `node.getIdentityOwnerKey()` instead of being handed the libp2p key). `joined` → `wireJoinedOwnerKey(node, granted)`: `wireOwnKeyIfOwner()` true → `enrolled`, false → `member`; after a grant it re-asks every 2 s for up to 60 s. `OwnerState` gained `'enrolled' | 'member'`; Home's `home-owner` shows the string. `ownerPublicKey` (what `isOwner()` checks) is now set in `bringUp` from the identity, whichever party runs.

**Move records** (`web-strand-move.ts`): the kit's `StrandMoveRecords` / `joinMoveRecord` / `adoptMoveRecord` / `adoptMovesInto` / `deferredOutcome` over the `kv` store, key `strand-move.<partyId>`. `naming()` lists all `kv` keys (`getAllKeys('kv')`) and filters by prefix; the store holds a few dozen keys at most, and the comment says so. An unparseable record is deleted with a warning. `StrandsNeedOwnerJoinError`'s message is the page's words ("This invitation makes the tab a member, and only an owner can bring its N strands along. Ask for one with “Also an owner” on.").

**The join**, as four `cadre-web.ts` steps the store action runs in order (the ticket placed `joinCadre` in `cadre-web.ts`; it is split so the store owns what it attached to the node and the node module stays free of Svelte):
- `decodeInvitationForThisTab(encoded)`: decode, refuse an invitation targeted at another peer id ("This response was made for another app. Copy this tab's request again and ask for a new one.").
- `redeemInPlace(invitation, options)` when the running party is the invitation's: redeem (`waitForMember`, `signal`, `onProgress`), wire the owner key, adopt moves naming this party.
- `recordStrandMove(invitation)`: for a founded party, `exportStrandBundle(node)`; non-empty → the move record (or `StrandsNeedOwnerJoinError` when the invitation grants no owner); empty → delete any stale record for this party. A joined party exports nothing.
- `switchToParty(invitation, options, movingFrom)`: `stopCadre()`, `bringUp({ partyId: A, origin: 'joined', formerPartyId })`, redeem, `admitted` progress, wire the owner key, write the start record, `moving-strands` progress when wired and something waits, adopt moves (never throws; deferred otherwise), return `{ redemption, formerPartyId?, strandMove? }`.
- `returnToStoredParty(movingFrom)`: `stopCadre()` (a throw is logged), reopen the node-local store, delete the move record this join wrote, `startCadre()` from the unchanged stored record.
- Also `joinRequestText()` (`encodeCadreJoinRequest({ v: 1, peerId, appName: 'Sereus web reference' })`), `pendingStrandMove()` (for the dissolve ticket's refusal and the page), `getPartyStart()`.

**Store** (`store.svelte.ts`). `NodeStatus` gained `'joining'`. `start()`/`stop()` are factored into `attachRunningNode(node)` (subscribe, fill state, chat strand, poll, `running`) and `releaseNode()`. `joinCadre(encoded, options)`: in place when the party matches; otherwise record the move, release, reset, `resetAddDeviceCard()`, status `joining` (party id set to the invitation's, peer id kept), `switchToParty`, attach. On any throw: `startLeftPartyAgain` → `returnToStoredParty` + attach (or status `error` with that message, `pushError('returnToStoredParty')`), then the join's error is rethrown. Activity log gets `join:leaving`, `join:admitted`, `join:failed`.

**Add-device card.** `add-device.svelte.ts` no longer imports the store (it read the peer id from `getCadreNode()` directly), so the store can import its new `resetAddDeviceCard()` (minted invitation, pending approval and notice cleared) without a cycle. Called on the switch and on the rollback.

**Page.** `JoinCadre.svelte` above "Add a device or app" on `#/cadre`: "This tab's request" (QR via `QrCode`, `Copyable`, the code via `peerCode`, the hint), "Paste response or invitation" textarea + Join, the flow line (+ Cancel while `joining`; OK on `done` / `move-incomplete`), and a failure notice with Dismiss. State is module-level in `join-cadre.svelte.ts` so a join survives a visit to Home. `join-flow.ts` carries the phone's wording with "this app" → "this tab" and "chats" → "strands": joining / waiting lines with the next-try clock time, admitted, moving strands, done with standing and moved count, move-incomplete with reason, the rejection table keyed by `CadreInviteRejectedError['code']`, unreachable, reply-invalid, cancelled. Home: Restart is disabled while `joining`.

**Debug hook.** `__cadre.isOwner()` and `__cadre.getPartyStart()` added.

**Docs.** README: storage databases, routes, "Two databases" (start record, per-party records), a new "Joining an existing cadre" section (flow, owner-grant rule, after admission, adoption at start, the left party stays, the two-tab limitation), the file map, the e2e tier list. `docs/architecture.md`: the handing-an-invitation paragraph names the browser's joining side; "An app joins an existing cadre" says the web app follows the same sequence in `cadre-web.ts` and names the debt ticket; the package table row.

## Deviations from the ticket (please check)

- **Where the join lives.** The ticket says `cadre-web.ts` → `joinCadre(...)`, driven by a store action. The sequence is in `cadre-web.ts` but as the five functions above, and the store's `joinCadre` orders them. Reason: steps 4 and 6 (tear down what the store attached; `running`, chat strand, subscriptions) are the store's, and hooks from `cadre-web.ts` back into Svelte state seemed worse than five named steps. `cadre-web.ts` is 1,398 lines (`wc -l`); a `NOTE:` at the join section says where to split if it grows.
- **New modules beyond the list:** `party-start.ts` (the start record), `join-flow.ts` (words), `join-cadre.svelte.ts` (page state), `JoinCadre.svelte` (card), `e2e/fixtures/cadre-member.ts` (the party the tab joins). Same split as the phone app and the add-device card.
- **"strands", not "chats".** The phone says "chats"; the web app's Home calls them strands and the ticket's refusal text says strands, so the web wording says strands throughout.
- **Move adoption gate.** The ticket says "every start whose owner state is `enrolled` adopts". The code adopts when the key is wired for owner signing: `genesis`, `existing` or `enrolled` (`ownerKeyWired()`). In practice only a joined party can be a move's target, so this is the same set; it avoids a founded-party start skipping a record a hand-built record could name.
- **`startCadre` failure now tears down.** Not asked for; needed so a join's rollback and a Restart after a failed start do not reuse a half-started node.
- **No Retry button for an incomplete move.** The dissolve ticket plans it (its step 1); this page shows the incomplete state with the reason and says the next start (Restart on Home) tries again. `pendingStrandMove()` is there for it.

## Known gaps, for the reviewer

- **What the e2e discriminates.** The ticket says the reload "reproduces the founding-row defect: with the origin ignored, the reload inserts the tab's key". Reading `ensureOwnerKey`, it inserts only when the local control store holds NO owner key, and after a join the tab's store holds A's owner rows (the member pushes its control store before admitting). So with origin ignored, the reload would most likely report `existing` and wire the tab's key for signing (self-anchoring it), not insert a row. The `home-owner` = `member` assertion is what catches the regression; `isOwner()` false pins the row absence as well. I did not run the test against the defect to confirm which way it would fail.
- **The non-empty move is untested in the browser.** A founded tab with a closed strand or an outstanding formation invitation needs a relay to create one (`createInvitation` refuses without a reservation), so neither the `StrandsNeedOwnerJoinError` path nor an adoption with strands ran here. Both are cadre-core's `adoptStrandBundle` and the kit's record rules, mirrored line for line; the empty-export path (record deleted) ran in every join.
- **Moved strands are carried, not opened** (ticket decision; the accepted-tradeoff `NOTE:` beside `formedStrands` now says so). Their rows reach A; the tab shows nothing about them.
- **Two same-origin tabs** share the start record; documented as unsupported in the README and the `kvSlot` note.
- **`wireJoinedOwnerKey` with `granted` can take up to 60 s** if the owner row never arrives; the page shows "Admitted. Setting this tab up as an owner…" meanwhile with no cancel (admission is never rolled back). Same as the kit.
- **Logs** of the runs are in `tickets/.logs/reference-app-web-joins-existing-cadre.*.log`.
