# Wake a hibernating host strand for an authorized closed-strand join — review handoff

## What changed

A bound closed-strand redemption (a joiner redeeming a formation invitation into an existing private strand) makes the host issue a single-use `Strand.Invite` against its live strand database in `CadreNode.issueStrandMembershipInvite`. Before this change, a strand quiesced by hibernation (`status: 'hibernating'`, no `database`) made that method throw, and the redemption was rejected with `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` on every retry until a check-in window happened to line up.

Now, after the existing control-database checks (Strand row, `Type`, recorded pre-split refusal, `StrandPartyKey`), `issueStrandMembershipInvite` calls a new private `wakeHostStrandForFormation(strandId, signal)`:

- No instance → returns; the existing "runtime is not live" throw follows (never launched here).
- Otherwise records activity via `hibernationManager.recordActivity(instance)` (the manager directly, not `recordStrandActivity`, so there is no push fan-out to this party's phones).
- Only if `status === 'hibernating'` and no database: `this.wakeStrand(strandId)`, which coalesces onto the wake `recordActivity` began (or wakes on its own when `recordActivity` is a no-op: hibernation disabled but the strand force-hibernated, or the manager stopped). The wait is bounded by the formation provisioning `AbortSignal` using the new module helper `resolvesBeforeAbort`. If the signal aborts first, the method throws an ordinary `Error` (retryable reason, token unspent), and the wake keeps running in the background with a logging `.catch`.
- `'starting'`, `'syncing'`, `'error'`, or a quiesce in flight: no wake; the existing live-database check throws as before.

After the wake, `issueStrandMembershipInvite` re-reads the database (throws if absent, e.g. stopped concurrently), runs the pre-split check, then checks `signal?.aborted` once more before `issueInvite`, so an invitation nobody will receive is not written.

The signal is threaded: `MembershipInviteIssuer = (strandId, signal?) => Promise<StrandMembershipInvite | null>` (new exported type in `strand-formation-manager.ts`, used by both the manager and `StrandSolicitationService` options). `provisionAsResponder` passes its `signal` to `issueBoundMembershipInvite`, which passes it to the hook. `initializeStrandSolicitation` wires `(strandId, signal) => this.issueStrandMembershipInvite(strandId, signal)`.

Authorization is unchanged and is what makes the wake safe: the hook runs only after `runSession` has validated the token and disclosure and `authorizeBoundUsage` (outside approval + seat pre-check) has passed.

### One deliberate step beyond the ticket

The ticket asked for `recordActivity` only in the hibernating branch. I record it for every closed-strand issuance that has an instance. Reason: if a redemption lands while a hibernation check-in has the strand briefly live (`handleStrandCheckIn` → `runWakeWindow`), no wake is needed, but without recorded activity the window ends and re-quiesces the host right after the invite is issued, before the joiner can sync the `Strand.Invite` row. That strands the joiner until the next check-in (30 s, backing off toward an hour). Recording activity makes the window see activity and leave the strand up, and restarts the idle timer on a plain live strand. Reviewer: judge whether this belongs here; reverting it is moving one line back below the status check.

## Known gaps (for the reviewer to weigh)

- **Budget-expiry path is untested.** The branch where the provisioning signal aborts mid-wake (throw, wake continues, a retry then finds the strand live), and the post-wake `signal.aborted` check before `issueInvite`, have no test. I held to one test per the ticket; a unit test would need a slow `resumeStrand` stand-in on a real node.
- **No end-to-end formation against a hibernating host.** The real two-node path (joiner `formStrand` → host wakes → approval carries the invite and, as a side benefit, non-empty live `strandAddrs`) is not exercised. The `strand-formation-cross-party-seed` integration scenario was not run (real network, long).
- **A failed wake leaves the strand stuck until something else recovers it.** `resumeStrand` sets `status: 'error'` on failure. Later redemptions see `'error'`, do not wake, and are refused. Check-ins only run for `'hibernating'` strands, so nothing brings it back automatically. This is existing wake-failure behaviour that the ticket excluded, but this change makes formation one more path that depends on it.
- **Wake failures are logged twice** when hibernation is enabled: once by `HibernationManager.recordActivity`'s own `.catch`, and once by the formation manager's rejection log (or by the background `.catch` when the budget expired first). Only noise.
- `resolvesBeforeAbort` is a module-private helper in `cadre-node.ts`. Similar abort plumbing exists in `relay-reservation.ts` (`delay`, `linkAbort`) and `control-stream.ts`, but none of it fits "race a promise against a signal without cancelling it", so I did not extract a shared utility.
