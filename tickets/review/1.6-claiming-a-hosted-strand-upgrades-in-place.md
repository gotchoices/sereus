# Claiming a strand this node already hosts as a storage replica — review handoff

## What was built

A **storage replica** is a strand a storage-profile node runs with no sApp config: its libp2p node, raw store and `Strand` membership schema, but no `App` tables (landed by `always-on-node-hosts-unclaimed-strands`). Before this ticket, an app on the same machine calling `CadreNode.addStrand` for that strand got the tracked replica back unchanged — a database with no `App` tables, and nothing ever retried. A `foundStrand` on such a node failed with "Cannot found strand … as a storage replica" when a watcher poll launched the replica between its publish and its attach.

Now a claim upgrades the running replica in place: the app's schema is applied to the live database; the libp2p node, peer id, connections, store and warm cache all stay.

- **`applyAppSchema(db, schema)`** (`compose-strand.ts`, exported from the plugin index): step 7 of `composeStrand`, extracted. The one place an `App` schema is applied; `composeStrand` calls it at bring-up.
- **`StrandDatabase.attachAppSchema(sAppConfig)`**: requires an initialized database; applies the schema, then records the sApp on its own config so a later `ensureFounderBootstrap` has it for the `Header`.
- **`StrandInstanceManager.attachSApp(strandId, sAppConfig, { requireSignedSchemas })`** → `'attached' | 'already-attached'`:
  1. waits out any runtime build in flight for the strand (new `runtimeBuilds` map, filled by `startStrand` and `resumeStrand` through `trackRuntimeBuild`) — see "Deviation" below;
  2. throws if untracked (also the outcome when the build it waited on was a failed launch);
  3. `'already-attached'` if `sAppInfo` is set (a different sApp id is logged and ignored);
  4. signature check (`verifiedSAppInfo`, the same one `startStrand` uses) before any change;
  5. retained launch config replaced with `{ ...config, sAppConfig }`;
  6. live database (`instance.database`, else the first-sync gate's held one) gets `attachAppSchema`; a quiesced instance gets the config only and its next resume applies the schema through `composeStrand`;
  7. only then `sAppInfo` and the sApp's `latencyHint` are set on the instance.
- **`CadreNode.startOrFoundStrand`**: the tracked-instance branch moved into `claimTrackedStrand`, which attaches (when a config is given and the instance has no `sAppInfo`) **before** the founder branch; the founder branch is unchanged code. `claimTrackedStrand` is also called from a **second check placed right before `startStrand`**, after the launch's awaits (party key, transport key, cohort seed) — this closes the "concurrent launches" arm the prereq's implementer added: a claim and a replica launch of the same id that both passed the first check no longer get each other's instance back unchanged. Nothing awaits between that check and `startStrand`'s own `instances.has` (`timedStep` invokes its op synchronously), so there is no window left.
- **Docs**: one bullet under "Storage replicas" in `docs/architecture.md`; `StartStrandConfig.sAppConfig` and `launchStrand` doc comments updated.

### Deviation from the plan: waiting for an in-flight build

The plan's step 5 looked only at `instance.database` and the gate's database. That misses a reachable state: the instance is tracked for the whole of `buildStrandRuntime` (launch, or a hibernation wake's resume) while its database is either not constructed yet or constructed but still inside `initialize()`. An attach there would either record `sAppInfo` as if the strand were quiesced (and the in-flight build, which read the pre-attach config, would finish with no `App` tables and nothing retrying), or call `attachAppSchema` on an uninitialized database and throw. So `attachSApp` first waits for `runtimeBuilds` to empty, then reads the instance. `startStrand` and `resumeStrand` both go from reading the launch config to registering the build with no await in between, so an attach either sees the build registered or its config update is read by the next build.

## Test added

- `packages/cadre-core/test/strand-replica-claim.spec.ts` — one test on a real `StrandInstanceManager` (real libp2p node, solo): launches an open strand as a replica (no sApp), calls `attachSApp` **while that launch is still in flight**, then `foundExistingStrand` (the order `claimTrackedStrand` uses). Asserts: `'attached'` then `'bootstrapped'`; status `active`; `sAppInfo` set; the same libp2p node object before and after (no rebuild); `App.Note` accepts an insert; `Strand.Header` carries the sApp id and version. Mutation-checked: removing the wait for the in-flight build makes it fail (the founder bootstrap refuses a database with no sApp).

## Known gaps — reviewer, start here

- **CadreNode-level paths are verified by inspection only**: the attach in `claimTrackedStrand`, the second tracked check before `startStrand`, `addStrand`'s `whenWritable` wait covering a claimed `'syncing'` replica, and `foundStrand` on a storage node. No `CadreNode` spec drives a storage-profile node through a claim. The manager-level spec covers the order and the upgrade itself.
- **Concurrent claims of one replica** (an app calling `addStrand` twice at once, or beside a watcher retry) both pass the `sAppInfo` check and apply concurrently; the loser may reject, and its retry resolves `'already-attached'`. Parked as a `NOTE:` on `attachSApp`.
- **Latency hint**: set on the instance at attach; `HibernationManager` reads it whenever it arms a timer, so a timer already armed runs once at the old duration, and a replica launched under a `realtime` default was never tracked for hibernation and stays up until relaunched. Comment at the assignment.
- **A claim that waits on a replica launch which then fails**: the replica's `handleStrandAdded` reports `strand:error`, and the claim's `addStrand` rejects with "not tracked" and hands the strand to the watcher's retry, which launches fresh with the config. Converges, but the app sees one rejected `addStrand`.
- **Claim of a hibernating replica**: config only; `addStrand` returns the hibernating instance as it does for any hibernating strand, and the wake's rebuild applies the schema. Inspection.
- **Replica's recorded sApp id** (`replicaSAppIds`) is not cleared on claim; `getSAppId` reads `sAppConfigs` first, so it is shadowed, not wrong.
- The `startStrand` early-return log about a dropped founder request is now reachable only by callers other than `CadreNode`; left in place.
