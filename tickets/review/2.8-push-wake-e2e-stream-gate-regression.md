# push-wake-e2e: stale membership-gate snapshot denied a starting member

## What the change is

The control database each party shares is guarded per stream: a node judges every
inbound Optimystic control-DB stream against an **in-memory snapshot** of the peers
it currently believes are authorized (`CadreNode.authorizeInboundControlStream`).
The snapshot is deliberately in-memory — reading the DB to answer the question
would need the very stream being judged.

Every `CadreNode` membership method (`authorizePeer`, `removePeer`, `addDrone`,
`acceptPhone`, `applySeed`, `registerSelf`) re-materializes that snapshot right
after it writes. A caller that writes a peer row **below** those methods — straight
through `getSeedBootstrapService().insertSelfPeerRecord(...)` — did not. So the
writer kept judging against a snapshot that predated its own write and denied the
peer it had just vouched for, until the next timed cohort reconcile ~15 s later.

Two changes:

- `CadreNode.refreshMembershipGate()` — new public, idempotent, best-effort
  re-materialize call. Thin wrapper over the existing private
  `refreshAuthorizedControlPeers`. The gate itself is **unchanged**: not weakened,
  no new carve-outs, no stranger admission.
- The integration-test helper `seedReceiverRecord` (the only caller in the repo
  that reaches the service directly) now calls it after its insert.

Plus a doc sentence in `docs/architecture.md` stating the invariant, and the
scenario 4 comment updated (it had predicted this exact fix as a tripwire).

## What it fixed, with numbers

Measured on 2026-07-29 on this machine. Denial counts are
`grep -c DENYING` under `DEBUG='sereus:cadre:*'`.

| | scenario 2 (relay) in a full-file run | denials per full-file run | scenario 4 alone |
| --- | --- | --- | --- |
| before | failed 5 of 8 runs | 14–18 | 8/10, passing runs ~3 s or ~17 s |
| after | 0 of 8 runs (4 debug + 4 plain) | 1–3 | 8/10, passing runs uniformly ~2.6 s |

Full file (all four scenarios): **4/4 runs green** after the change.

The scenario 2 failure was the sharp end. Its owner/relay `L` authorized sender `S`
(snapshot → `{S}`), then wrote receiver `Rx`'s address row through the service, so
`Rx` was absent from `L`'s snapshot. When `Rx` started, `L` denied its `repo`,
`cluster` and `db-p2p/sync` streams and `Rx`'s **own control-DB schema load** died:

```
QuereusError: Failed to execute DDL: create table CadreControl.OwnerKey …
  cause=Failed to get super-majority: 1/2 approvals (needed 2, 0 rejections)
  at ControlDatabase.loadSchema (packages/cadre-core/src/control-database.ts:284)
```

Confirmed from the debug timeline: `L` logs
`refreshAuthorizedControlPeers(authorizePeer): 1 authorized peer(s)`, `Rx` starts
~236 ms later, and `L` immediately logs 17 `DENYING … (1 member(s))` lines naming
`Rx`'s peer id; the commit error names `L` as the validator that never completed.

## Scope honesty — this is a test-recipe defect, not a production one

Production writes peer rows through the `CadreNode` wrappers, which refresh. A
repo-wide grep finds only tests reaching `getSeedBootstrapService()` directly. So
the reachable bug was in the test helper; `refreshMembershipGate()` exists to make
the below-the-wrapper path correct rather than leaving the rule implicit.

**Worth an independent look:** whether any non-test caller can still land a
`CadrePeer` row without refreshing — e.g. a future host/provider path, or seed
delivery arriving on a node whose `applySeed` errors partway. The grep was mine and
a grep is not a proof.

## Gaps the reviewer should probe

- **Sample size.** 8 full-file runs after vs 8 before is enough to see a 5/8 → 0/8
  swing, not enough to certify scenario 2 as permanently stable. More runs would
  strengthen it.
- **No regression test for the fix itself.** Nothing asserts that a below-the-wrapper
  write followed by `refreshMembershipGate()` admits the new peer — the evidence is a
  flake rate and a denial count, not an assertion. A focused unit test on
  `CadreNode` would pin it. Deliberately not added here (budget), and it is the most
  valuable thing to add next.
- **`refreshMembershipGate` is public API.** Consider whether the better shape is for
  `SeedBootstrapService` to notify its owning `CadreNode` on every row write, making
  the refresh unskippable instead of a documented obligation. That is a design call,
  not a defect.
- **Denials are not zero after the fix** (1–3 per full-file run). Scenario 3 exercises
  rejection deliberately, so some are expected; nobody has attributed the remainder
  line by line.

## Tripwires parked

- `packages/integration-tests/src/scenarios/push-wake-e2e.integration.ts`, scenario 4
  NOTE at the `A.authorizePeer` / `seedReceiverRecord` pair: swapping those two writes
  also clears denials but measured **worse** (2/6 vs 4/5) by perturbing commit
  ordering into the separate stale-revision race. Recorded so nobody retries it blind.
- `docs/architecture.md` per-stream-gate bullet: the snapshot refresh rides the
  `CadreNode` wrappers; anything writing below them must call
  `refreshMembershipGate()`.
