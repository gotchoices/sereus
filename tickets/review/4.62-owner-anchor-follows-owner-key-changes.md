# Review: the anchor follows an owner addition, a removal and a re-add over a live network

Last of three tickets (after `owner-anchor-revocation-signer-and-owner-writers` and `owner-anchor-derivation`). No production code changed; this is the live-network scenario plus one harness option and one doc paragraph.

## What landed

- **Scenario** `packages/integration-tests/src/scenarios/owner-anchor-follows-owner-changes.integration.ts`, one `it`, loopback WebSockets. Machines: A (founding owner), M (always-on member pinning only A's key; its anchor is the one under test), B (second machine, admitted like M, then made an owner by `A.addOwner`), C (a bare peer id B vouches; no node). Steps:
  1. `A.addOwner(bKey)`: A's anchor holds B as `chain` the moment `addOwner` returns; B's row reaches M, then M's anchor derives B as `chain`.
  2. B (after its own copy holds its `OwnerKey` row) vouches C. C's row reaches M; M lists C as authorized; A lists C.
  3. `M.applySeed(B.createSeed())` succeeds.
  4. `A.removeOwner(bKey)`: A's anchor drops B and A stops listing C immediately. A's `OwnerKey` tombstone for B (`signerKey === aKey`) reaches M, then M's anchor drops B; M stops listing C; a fresh seed from B is refused with `Signer key is not an anchored owner (anchored trust policy)`.
  5. `A.addOwner(bKey)` again (fresh stamp): the row reaches M, M derives B again, M lists C again.
- **Waits on M are two-stage** (`followedByM`): the row or tombstone first (`OP_MS`, 30 s), then the anchor (`REFRESH_MS`, 30 s), so a timeout names the stage, and both delays are printed. **M's refresh is never driven by the test**: on M, only the timed control-cohort reconcile (15 s default) runs a membership refresh for a replicated row, so the scenario covers that trigger too.
- **Harness** `cadre-invite.ts`: `startPinningMember(partyId, ownerKey, options)` now takes `{ storageProvider?, ownerCapable? }` (the one other caller, `cadre-invite-row-unreplicated`, updated) and `InviteMember` carries the member's `key`. `ownerCapable` calls `initializeSeedBootstrap(ownKey)` **in place of** `enableSeedListener`.
- **Docs** `docs/architecture.md`, "How the anchor follows the owner table": one new sentence saying the writing machine refreshes before the write returns, and every other machine follows at its next timed reconcile (every 15 s by default). The coverage sentence now names this scenario instead of this ticket.

## Deviation from the ticket

- **B is wired to sign before admission, not after.** The ticket's order (start B like M, admit, then `B.initializeSeedBootstrap`) throws: `startPinningMember` registers the seed handler through `enableSeedListener`, and libp2p's registrar refuses a second handler for the same protocol (`DuplicateProtocolHandlerError` unless `force`, `node_modules/libp2p/dist/src/registrar.js:66`). So the owner-capable service has to be the only one, registered at start. It answers A's admission seed through the same anchored policy, with A pinned. One side effect: B anchors its own key as `genesis` on B before A adds it. That changes nothing on A or M, and the scenario asserts nothing about B's own anchor.

## Known gaps and things for the reviewer to weigh

- **`REFRESH_MS` margin.** 30 s against a measured ~15 s (one reconcile interval). Reconcile passes run one at a time, so a pass that runs past the interval delays the next refresh. If a loaded run times out on "M's anchor follows" with the row already at M, that is the cause. The fix is a longer budget, or driving `refreshMembershipGate` per poll as `cadre-invite-any-member` does for A, but driving it would stop the scenario covering the timed trigger.
- **Immediate assertions on A** (`sources().get(bKey) === 'chain'` right after `addOwner`; `has(bKey) === false` and C unlisted right after `removeOwner`) rely on the documented contract that the owner write's membership notification runs the refresh before the write returns. That refresh reads with `retry: false` (it runs under the write lock), and `syncOwnerAnchor` skips the pass on a failed read, so a transient read failure there would fail these assertions. They held in all 8 runs.
- **C has no running node**, so the scenario checks the membership predicate, not a stream or a wake from C. The per-stream guard is `control-stream-authz`'s.
- **Removal with only the tombstone delivered** (the remover alone, so other machines keep the removed owner's row) is not covered; it is `fix/removed-owner-still-authorizes-where-its-row-survives`.
- **Behaviour worth knowing, not filed:** a removed owner is still honoured on other machines for up to one reconcile interval (15 s by default, plus any overrun) after its tombstone arrives, because a replicated row raises no local refresh. The new architecture.md sentence states this. If faster revocation is ever needed, the change is to have replication of `OwnerKey` or `Revocation` blocks trigger a refresh.
