# cadre-cli and cadre-host act on `cadre:removed`

## What was built

### cadre-cli (`cadre start`)

- **Marker** (`commands/removal-marker.ts`): `<nodeStateDir>/removed.<encoded partyId>.json` holding `{ partyId, stampId, signerKey, at }` (the `CadreRemoval`), written through `writePrivateFile`. `readRemovalMarker` returns undefined when absent and **throws** (naming the file) when present but unreadable or malformed, the same rule as `claim.json`: a damaged marker must not let a removed node start.
- **Runtime removal** (`stopWhenRemoved` in `start-node.ts`): subscribes to `cadre:removed` and also checks `removedFromCadre()` immediately; acts once. It writes the marker (a write failure is logged, the node is still stopped), sets the start command's `removal` state, prints one `console.warn`, and calls `node.stop()` without exiting. Called on the first node and again on the node built by the in-process restart into a claimed party. Because it subscribes before `start()`, the "check once after start" from the ticket is folded into the immediate check at subscription time.
- **Start-time check** (`start.ts`): after the claim record decides the party (`partyOnRecord`), a marker for that party means no node is built: `serveRemoved` starts the health server with no node attached, prints the same warning, and waits for SIGINT/SIGTERM. No admin server in this state (cadre-host does not use it; it needs a node).
- **Health server refactor**: the inline health-server block became `startHealthServer(...)`, shared by both paths. It now prints the **bound** ports (`healthBoundPort`/`metricsBoundPort`), so `--health-port 0` is usable; the new spec relies on this.
- **`/status`** (`server/health.ts`): `node.removed: { stampId, signerKey, at } | null` (new exported type `RemovalStatus`); when removed, top-level `status` is `unhealthy` (so `/health` answers 503), `running` false, and `node.partyId` falls back to the removal's party when no node is attached.
- **`cadre status`** prints a `Removed:` line (`status-query.ts`; `RuntimeLive.removed`).
- **README**: new "Removed from the cadre" section; node-state paragraph and `CADRE_NODE_STATE_DIR` row mention the marker; says the CLI deletes nothing.

### cadre-core (small enabling change)

- `encodeFileSafeComponent` moved out of the Node-only `fs-atomic.ts` into a new pure module `file-safe-name.ts` and exported from the main entry, so the CLI names its marker exactly like `trusted-owners.<encoded party>.json`. Importers (`file-durable-slot.ts`, `key-store-file.ts`, `key-store.spec.ts`) updated. No behaviour change.

### cadre-host

- `node-status.ts`: `fetchNodeStatus` split out; `readNodeStatus` (claim details) unchanged in behaviour; new `readWatchedNodeStatus` returns `NodeStatus | RemovedNodeStatus`, because a removed child has stopped its node and reports no peer id (the old identity check would have treated it as "not answering" forever). `reportsRemoval` type guard.
- Watcher: a removal report moves the record to `error` with `error: 'Removed from its cadre by an owner'`, `retryable: false`, `removedByOwner: true`, emits `changed`, then stops the child (shared `stopChild` with the failed-invitation path). Write first, then stop, same ordering as the failed invitation; the re-read-then-write rule is untouched (the removal branch sits after the existing re-read). Applies to every polled status (`unclaimed`, `joining`, `joined`), not just joined/joining: simpler, and an unclaimed record whose child reports removal is dead either way.
- `types.ts`: `removedByOwner?: true` (chosen over matching the error string, because an invitation node's error line otherwise reads "Could not join: …"); `retryable` doc now says false on a removed node.
- UI: `stateLine` reads `Removed from cadre <id> by an owner; Remove deletes it from this machine`; UI view mirror gains `removedByOwner`. Buttons unchanged: a claim node offers Retry (a reset) and Remove, an invitation node Remove only.
- `docs/cadre-host.md`: "Removed by an owner" bullet (with *How the host hears it* and *Best-effort* sub-paragraphs) under "Remove, reset and a lost host"; `error` row in the status table; `HostedNodeView` field list; node-page bullet; node-local state paragraph.

## Tests added

This is the branch a restart depends on.

## Known gaps and things to check

- **No test of the runtime path** (`stopWhenRemoved`: marker written, node stopped, process kept up). It would need a fake `CadreNode`; checked by reading only.
- **Removal during the rest of `start()`'s sequence.** If `cadre:removed` fires before `start.ts` finishes its post-start steps (invitation redemption, `--owner` genesis, admin server, `enableSeedListener`, `--seed`), a step can throw on the stopped node and the outer catch exits 1. The marker is already written synchronously, so the respawn lands in the removed state. Needs a removal noticed within a second or two of start; not guarded, parked as a `NOTE:` at the `stopWhenRemoved` call in `start.ts`.
- **`/health` now answers 503 for a removed node.** Docker's HEALTHCHECK marks the container unhealthy; nothing in this repo restarts on that (cadre-provider only reads `/status`). A Kubernetes-style liveness probe would restart it into the same state. Chosen because "healthy" would hide a node that does nothing.
- **The warning's "delete the node-state directory"** is right for cadre-host (the workdir) and a `cadre init` folder (`state/`); with the default layout (node-state dir = config file's directory) it would also delete the config. The README spells out the layouts.
- **Marker writes are not atomic** (`writePrivateFile`, as the ticket asked); a torn write refuses the next start with a message naming the file.
- **Same-cadre re-admission** needs the operator to delete the marker; nothing clears it automatically.
- The watcher acts on a removal for `unclaimed` records too (see above); the ticket named joined/joining.
