# One cohort-join catch-up per node (review handoff)

## What changed

A node that arms Sereus's peer-join block catch-up (`PeerJoinBackfill`) is now built with `rebalance: { enabled: false }`, which switches off Optimystic's rebalance reaction. That reaction is only wired on storage-profile nodes (`arachnode.enableRingZulu`).

- **Strand node** (`strand-instance-manager.ts`): `backfillArms = strandStorage !== undefined && config.backfill?.enabled !== false` is computed once, next to `strandStorage`. The node option and the arming condition both read it. TypeScript narrows `strandStorage` through the aliased condition, so the arming block still type-checks without a second check.
- **Control node** (`cadre-node.ts`): the new private `controlBackfillStorage()` returns the store when the catch-up will arm (not `controlBackfill.enabled: false`, and storage resolves), otherwise `undefined`. `buildControlNodeOptions` passes the option on it and `startControlBackfill` arms on it. The resolver comment ("through the resolver, not the memo field") moved there.
- **Behaviour change:** `startControlBackfill` with `controlBackfill.enabled: false` now logs the debug line `Control peer-join block catch-up is inert: disabled, or no control storage configured`. It used to return silently.
- **Comments:** each option site has a `NOTE:` naming what else goes off (ring shifts, reclaimable shed blocks) and the revisit condition: report the catch-up's pushes to the rebalance monitor once Optimystic has an API for it (`blocked/optimystic-embedder-cannot-report-block-holders`).
- **Docs:** docs/architecture.md has a new labelled sub-paragraph, "One join catch-up per node", under the catch-up's "What the catch-up pushes, and when".

## Known gap: filed as `fix/join-catch-up-skips-a-returning-peer`

The implement ticket's premise was "the growth arm adds no coverage where the backfill runs". That holds for a first join, but not for a peer that **comes back**.

- **What the growth arm did:** it drops a departed peer from its confirmed-holder set (`carryGrowthState` intersects with the current cohort). A storage node therefore re-pushed every tracked block to a returning peer, which also delivered what the peer had missed.
- **Why nothing replaces it:** the backfill marks a peer `done` for the whole runtime and ignores later `peer:identify` events for it. The under-replication drain only owes blocks to the cohort members a write named as missing.
- **Result:** on parties with a storage node, a member that was away long enough to leave the cohort now gets missed writes only through read repair, for the blocks it reads. Phone-only parties already behaved this way.
- **Why it isn't fixed here:** re-running the backfill on reconnect would also re-push a returning writer's offline commits that its drain already sends. That trade belongs to that ticket. Its prereq is this ticket.
- **Pointers:** a sentence in the strand option comment and in the architecture sub-paragraph names the gap and the fix ticket.

My first control-site comment claimed every growth target is an authorized member. That is wrong: `isControlNetworkMember` admits everyone while the membership snapshot is empty, and bootstrap/relay peers outright. The comment now says the catch-up deliberately withholds the store from those peers. Turning the reaction off therefore also stops the growth arm pushing the control store to such a peer during the cold-start window. Worth a reviewer's eye.
