# One per-stream guard for every protocol on the control node — review handoff

## What was built

`control-protocol-guard.ts` holds the one class table (`controlProtocolClasses(partyId)`) and the enforcement (`installControlProtocolGuard`). `CadreNode.start()` installs it right after `createControlNode()`, inside the bring-up quiet period.

- **Classes**, as the plan specified: `stranger-open` (seed, formation, cadre-invite), `transport` (identify and identify-push, ping, dcutr, AutoNAT, relay stop and hop, WebRTC signaling), `members` (wake, strand-addr: live `isAuthorizedMember`), `members-snapshot` (four Optimystic database protocols and five FRET protocols: `authorizeInboundControlStream`).
- **Mechanism.** `components.registrar.getHandler` is replaced on the control node's registrar instance. It returns the record with its handler wrapped for the class and the same `options` object, cached per record in a `WeakMap`. A missing registrar or `getHandler` throws from `start()`. Stranger-open and transport records are returned untouched.
- **Refusal** aborts the stream with `ControlStreamRefusedError` before the handler runs, logged on the `sereus:cadre:control-protocol-guard` debug namespace. The live check fails closed on false, a throw, or a timeout. The timeout is `relayedRequestBudgetMs(network.linkRoundTripMs)`, the asker's own attempt deadline, so no check that completes today is cut off.
- **Unclassified protocols** are guarded as `members-snapshot`, with one `console.warn` per protocol.
- **Handlers no longer check membership.** `isMember` is gone from `StrandWakeServiceOptions` and `StrandAddrServiceOptions`, along with wake's "Sender is not a cadre member" reply and strand-addr's `refused` status and `refused` outcome. `STRANGER_OPEN_PROTOCOLS` is deleted, since the class table replaces it; `index.ts` exports `controlProtocolClasses` and `ControlProtocolClass` instead.
- **`controlNetworkName(partyId)`** moved into the guard module with its NOTE, and `CadreNode.controlNetworkName()` delegates to it. `ControlDatabase` still spells `control-${partyId}` itself. Importing the guard there would create an import cycle (guard → `seed-bootstrap` → `control-database`).
- **Optimystic's `authorizeInboundStream` stays wired**, with one sentence at the wiring site saying why.

AutoNAT's dial-back rule was checked against the installed `@libp2p/autonat` 3.0.28, not taken from memory: it dials back only public addresses on the requester's observed host and refuses requests made on another peer's behalf.

## A defect this exposed and fixed: late readers never see end-of-stream

`push-wake-e2e` "wakes a hibernating member over a real direct control dial" failed after the guard went in. The wake handler's read timed out after 10 s.

The cause is in libp2p 3.3.11. A stream buffers data that arrives before anyone reads it, but `remoteCloseWrite` is a one-shot event, and the async iterator ends only on that event or on `close`. So a reader that attaches after the remote half-closed gets the bytes and then waits forever. The guard's live check awaits database reads before the handler starts reading, which creates exactly that gap.

The fix is in cadre-core's own reader. `collect` in `control-stream.ts` (behind `readStreamToEnd`) records whether the remote had already half-closed when the read began. If it had, the reader stops once it has received the bytes that were buffered at that moment. A plain "closed and buffer empty" check would truncate the ordinary case, where several chunks can be queued inside the iterator, so the check is keyed on the state when reading starts. It uses only fields on libp2p 3's public stream interface (`remoteWriteStatus`, `readBufferLength`), now optional fields on `ControlStream`.

A NOTE at the guard's `members` wrapper says a handler added to that class must read through `readStreamToEnd`. The snapshot wrapper is synchronous, so Optimystic and FRET handlers see no gap.

## A defect this exposed and filed: strangers counted into the cohort

The plan's probe wanted "the member's FRET routing table does not contain the outsider after an announce." That does not hold, and the cause is not the guard:

- libp2p records each protocol a peer opens a stream on as one that peer serves (`peerStore.merge` in `onIncomingStream`, before `getHandler`).
- FRET and Optimystic's key network decide ring and cohort membership from those recorded protocols.

Measured with temporary logging in `control-stream-authz`: after O's streams were all reset, A's FRET had O as `member`, and `keyNetwork.findCluster` for a control block key returned `[O, M, A]`.

This was already reachable before this ticket: step 2's refused raw pend had already recorded `repo` for O. It is filed as `tickets/blocked/stranger-joins-the-control-cohort-by-advertising-protocols.md`, with a proposed upstream membership predicate and alternatives. A bullet was appended to `implement/0.61-stranger-connections-admitted-provisionally` noting that it widens this exposure. The scenario carries a NOTE at the spot where the assertion would go.

## Behaviour changes callers see

- **A refused wake** now resets the stream, so `pushWake` rejects instead of returning `accepted:false`. As a result, `push-fanout`'s `wakePeer` falls through to a platform push for a receiver that does not yet count the sender as a member. Its doc says so; this is intended, since the reset cannot be told apart from a transport fault.
- **A refused strand-addr asker** now records the sibling as `unreachable`. `siblingAnswered` already put `refused`, `unavailable` and `unreachable` on the same retry interval, so the timing does not change.
- **A member whose `CadrePeer` row has not replicated to a node** now gets FRET resets from that node. The cohort and invite scenarios below all pass.

## For the reviewer to scrutinize

- **Coupling to libp2p internals.** Both the dispatch path through `getHandler` and `components.registrar` are internals. `start()` fails loudly if the registrar shape changes. If a libp2p upgrade instead dispatched through a different method, the completeness spec would still pass; only the `control-stream-authz` probe would notice. Consider whether a cheaper check belongs in cadre-core.
- **Cost of a refused stranger.** On wake and strand-addr, a stranger's stream costs one live membership read, and that read now runs ahead of the handlers' concurrency caps. Up to the 28.5 s deadline it is bounded only by libp2p's per-connection `maxInboundStreams` (32). Parked as a NOTE tripwire in `ControlProtocolGuard.liveRefusal`.
- **Unclassified-protocol warning.** It uses `console.warn`, like `joined-strand-store.ts` and `peer-join-backfill.ts`. The `cadre-node.ts` NOTE in `warnIfAnnounceAddrsDiscardRelay` about routing a second warning through events refers to `CadreNode`'s own console surface, so it was left as is.
- **Edge cases verified by inspection only.** No code path was added for them:
  - unclaimed node: the snapshot class refuses everything through `authorizeInboundControlStream`'s claim check, and the guard adds no admission ahead of it;
  - cold start: an empty snapshot or `!_running` admits, as the database protocols already did;
  - configured infrastructure: admitted on the snapshot class, refused on the live class, as before.
