# What this work closes

Deleting a `CadreControl.OwnerKey` or `CadreControl.CadrePeer` row used to free its one-off
`StampId` nonce, so the original add-approval signature — which never expires, and which for
`CadrePeer` is even STORED on the replicated row as `VouchSig` — verified again: anyone who
kept a copy could re-seat a removed owner or peer verbatim. Every removal was undoable.

Fix (all production code landed in prior runs of this ticket chain; this run added the
tests and validated): an append-only `CadreControl.Revocation` table retires
`(TableName, StampId)` on removal.

- `NotRevoked` (on both guarded tables) refuses an insert naming a retired stamp — the
  replay itself.
- `RevocationRecorded` (on both guarded tables) refuses a delete that doesn't carry the
  matching tombstone in the same transaction — a bare delete would free the stamp.
- `RowIsGone` / `Immutable` (on `Revocation`) keep tombstones honest: only a gone row's
  stamp may be retired, and never un-retired. Retiring a never-existing stamp is allowed
  (stamps are 32-byte CSPRNG; pre-planting a future one is infeasible).
- `SeedBootstrapService.removePeer` wraps its signed delete + tombstone in one transaction.
- Read-side mitigation for the replication race: `CadreNode.listAuthorizedMembers` /
  `isAuthorizedMember` drop any `CadrePeer` row whose stamp appears in
  `ControlDatabase.queryRevokedStamps('CadrePeer')`.

Legitimate re-adds mint a fresh stamp per insert, so removal is stamp-retirement, not an
identity ban.
