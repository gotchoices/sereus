# Owner grants: the node API, the redemption protocol and the bundle

## What shipped

Implemented in `ticket(implement): owner-grant-node-api`. Additive: machine invitations keep `grantsOwner` until `machine-invitation-grants-no-ownership`.

- **One shared redemption core, two protocols on it.** The ticket asked for `redeemAtMembers` / `redeemInPasses` to be parameterized rather than copied. The credential-independent parts of the invitation protocol moved into a new module, `member-redemption.ts`: the shape checks and the 64 KiB frame cap, the refusal helpers (`constraintRefusal`, `writeFailureRefusal`), an abstract member-side handler (`MemberRedemptionHandler`: concurrency cap, read timeout, shape then protocol checks, push of the control store to a holder of a live credential, writes under that admission) and the holder-side dial loops (`dialRedemption`, `dialRedemptionInPasses`). `cadre-invite-protocol.ts` keeps its whole public API (`CadreInviteHandler`, `redeemAtMembers`, `redeemInPasses`, the errors and codes) as thin instances of those; `CadreInviteAddressOutcome` is now an alias of `RedemptionAddressOutcome`, which `CadreJoinProgress` uses. The handler's shape check moved into the base, so a subclass's `checkRequest` receives a typed request. One behaviour change inside the loop, with no visible effect: a final refusal and a failed reply check are thrown from outside the per-address `catch` instead of being re-thrown through an `instanceof` test.
- **`owner-grant-protocol.ts`**: `OwnerGrantBundle`, `encodeOwnerGrant` / `decodeOwnerGrant` behind `sereus-owner-grant:1.` (`OWNER_GRANT_PREFIX`, declared in `cadre-join-request.ts` beside the other prefixes so every decoder can name it), the wire request and reply, the codes with grant wording and `OWNER_GRANT_REJECTION_RETRYABLE`, the three holder-side errors, `signOwnerGrantRequest` (the grant signature in memory, the consent signature through an owner approval's `sign`), `verifyOwnerGrantReply`, `OwnerGrantHandler` (party and both signatures; no connecting-identity check; seat then redeem; `issuer-unknown` on a foreign issuer, `grant-spent` on an exhausted grant) and `redeemOwnerGrantAtMembers` / `redeemOwnerGrantInPasses`. The reply carries no dial hints. All four pasted texts now refuse each other by name (the invitation, join-request and owner-key decoders gained the grant refusal).
- **`CadreNode`**: `createOwnerGrant` (15-minute default, `OWNER_GRANT_DEFAULT_TTL_MS`, which `OWNER_INVITATION_DEFAULT_TTL_MS` now aliases; `expiresInMs: null` is the explicit backup; label through `ownerKeyLabel`; bundle parts through a helper shared with `createCadreInvitation`, `issuedBundleParts`), `listOwnerGrants`, `withdrawOwnerGrant`, `redeemOwnerGrant` with both paths, `joinWithOwnerGrant`, and the owner-grant handler registered at start beside the invitation handler. The seed-bootstrap service gained `insertOwnerGrant` / `withdrawOwnerGrant`, the owner-signer precondition and approval living there as for invitations. `ControlDatabase.signCadreInvite` is the signing half factored out of `insertCadreInvite`; the self-invitation is signed with it and never inserted locally.
- **The local path's condition** is "this node is a live member (its own `CadrePeer` row is held here and passes `hasAnchoredProof`) or an enrolled owner (`isOwner()`)". `listAuthorizedMembers` leaves this node out by design, so a new private read, `isLiveMemberSelf`, judges the own row. The enrolled-owner arm exists because an owner machine's first self-record lands a second after start; without it such a node would dial its own addresses. Refused `alone` with `OwnerKeyAddRefusedError` before the approval; the grant row is seated before the approval too, so an unknown issuer is refused before the prompt.
- **`joinWithOwnerGrant`**: one approval signs the grant request and the self-invitation (targeted at this peer id, one use, `SELF_INVITATION_TTL_MS` = the grant default, `grantsOwner: false`); the self-invitation's `ownerKeys` are the grant's plus the new key, because the device's reply check wants the row's issuer among its pins; its `members` are the grant's with the accepting member's addresses first. Then `redeemCadreInvitation`, then `wireOwnKeyIfOwner(signer)` asked every 2 s up to 60 s (the edge node's owner-step bound, re-declared in `cadre-node.ts` since importing it from `edge-node/config.ts` would cycle). The result is `JoinWithOwnerGrantResult { peerId, redeemedAt, ownerKey, alreadyOwner, ownerWired }` rather than the invitation result plus `ownerKey`: the self-invitation is member-only, so its `grantsOwner: false` would have misled, and `ownerWired` says whether the row synced within the bound.
- **Gate**: `admitInboundControlConnection` admits a peer in `admittingDevices` (check 3 in its renumbered list); a live grant deliberately does not count as expecting a stranger. **Guard**: `/sereus/owner-grant/1.0.0` is `stranger-open`; the guard spec's literal list now names four protocols.
- **`planOwnerKeyRemoval`**: the plan carries `grants: OwnerGrantRow[]`, the live grants the key issued (rows rather than keys so an app can say which backup stops working without a second read); `removeOwner` does not withdraw them. The removal spec's `toEqual` gained `grants: []`.
- **Docs**: `docs/architecture.md` gained "Owner grants" after the invitation flow (what a grant is and is not, the bundle, the two paths, the exchange and its code table, self-admission, backups, the gate, the single-use race), the gate's "What it admits outright" paragraph names both admitting-device admission and the grant exclusion, the guard's `stranger-open` lists are updated, "Removing an owner key" has the plan's `grants`, the `OwnerGrant` table row points at the section, and Owner Keys has a one-bullet pointer. The cadre-core README's owner-only flow list names `createOwnerGrant`.

## Tests added, and what each verifies

- `owner-grant-codec.spec.ts`: the bundle round-trips behind its prefix and the decoder refuses another version, an empty `ownerKeys`, an over-long label, a zero use cap, non-base64url and a missing prefix; a table of the grant decoder refusing an invitation, a join request and both owner-key forms by name; the invitation, join-request and owner-key decoders (plain and locked) refusing a grant by name.
- `cadre-node-owner-grant.spec.ts` (an owner member plus fresh nodes started in its party over real TCP, as the invitation spec does):
  - minting: the 15-minute, one-use default, the trimmed label, the anchor keys and own addresses in the bundle, `reach`, the encoding round trip; a backup with no expiry and two uses; `uses: 0` and a 65-character label refused; the live listing; the removal plan naming the issuer's live grants and dropping a withdrawn one; `withdrawOwnerGrant` true then false and the withdrawn standing.
  - a holder with no machine: a bundle for another party refused before any pin; redemption over the protocol with the key listed on the member, labelled by the grant, vouched by the issuer, trusted (derived through the grant chain); no machine admitted; the holder pinned the issuer; a second redemption with the same key answers `alreadyOwner` with one use recorded.
  - `joinWithOwnerGrant` with a backup grant: the fresh node is a member and `isOwner()`, `ownerWired: true`; the member lists its key trusted; the member itself then redeems a grant locally while connected; with a further live no-expiry grant, a stranger is admitted only provisionally.
  - the local path alone: refused `OwnerKeyAddRefusedError` `alone` with zero approvals and nothing written.
- `control-protocol-guard.spec.ts`: the `stranger-open` list is now the four protocols (existing test, expectation widened).
- No protocol-level spec with stream doubles for the grant handler (the invitation's `cadre-invite-protocol.spec.ts` drives the shared base's refusal, admission and dropped-reply paths; the grant handler adds only its two checks and two writes, which the node spec reaches over the wire). A reviewer who wants `issuer-unknown` moving to the next address, the expired grant answered `grant-spent` by the engine, or the forged row sent nothing should add the grant twin of those cases; the handler is driven as `handleStream(stream, remotePeerId)` like the invitation's.

## Known gaps and decisions for the reviewer

- **Trust provenance.** Grant pins use the existing `'invite'` source; the store does not distinguish base sources, and a new `'grant'` value would be persisted into anchor files an older build reads as unusable. Say so if a distinct provenance is wanted anyway.
- **The accepting member's addresses first** is decided by `addr.endsWith('/p2p/<peerId>')` on the bundle's strings, not by parsing; the bundle's addresses are produced by `selectCadreInvitationMembers`, which emits that suffix.
- **`redeemOwnerGrant` on the protocol path refreshes the membership gate** after acceptance so the anchor derives the node's own key once its row is here; a holder that is not a machine gets nothing else (no dial hints, no reconcile).
- **An owner node redeeming locally for a key other than its wired one** is allowed and tested (the member's "yubikey" case): the node seats the key and does not wire it, which is the ticket's "it does not wire the signer".
- **Inspection only** (as the ticket allows): retry with the same `usageStampId` across passes, `issuer-unknown` at a member without the issuer's row, the self-invitation dialed at a member without the new key's row, a holder disconnecting mid-exchange, the issuer removed between mint and redemption (database-tested in `owner-grant-tables`).
- **Size.** `cadre-node.ts` is 10,616 lines (`wc -l`, was 10,218) and `control-database.ts` 5,118 (was 5,107); `debt-cadre-node-single-file-size` tracks both. `cadre-invite-protocol.ts` shrank from 1,053 to 653; `member-redemption.ts` is 636 and `owner-grant-protocol.ts` 531.

## Tripwires noted in code

- `OWNER_ROW_SYNC_TIMEOUT_MS` cuts off by design (lint-disabled with the reason): past it `joinWithOwnerGrant` returns `ownerWired: false` and a later `wireOwnKeyIfOwner` wires the key.
- The accepted-tradeoff `NOTE:` on pushing a control store to a holder whose write then fails moved with the admission code into `MemberRedemptionHandler.admitIfLive`, worded for both credentials; the `conflict`-versus-`internal` measurement `NOTE:` moved into `writeFailureRefusal`.
