# Review: the cancellation tombstone table (schema half)

## What the defect was

`packages/cadre-core/test/strand-member-revocation.spec.ts:573` —
`'a revoked member re-admits ITSELF off an invite it held but never consumed'` — documents
a live hole. A manager issues two invitations to one party; the party joins on the first, is
removed, then consumes the second and is a member again. `Member.Authorized`'s invite branch
only closed the *already-spent* invitation path (it requires the admitting `ConsumedInvite`
row to be absent from the committed snapshot, so a stale consumption record is inert). An
**unspent** invitation produces a genuinely fresh consumption record, so it re-admits
normally. Sharpest form: managers are the parties that issue invitations, so a manager
anticipating its own removal can mint a stack of never-expiring invitations for itself.

## What landed

Three edits, mirrored byte-for-byte into `schemas/strand.qsql` and the embedded
`STRAND_SCHEMA` copy in `packages/quereus-plugin-sereus/src/strand-schema.ts`:

1. **`Invite`'s stale `-- TODO: ability to deactivate?` comment retargeted** to point at the
   new tombstone table.
2. **`ConsumedInvite.NotCancelled`** — `not exists (select 1 from CancelledInvite C where
   C.InviteKey = new.InviteKey)`, on insert. This one constraint is the whole fix: blocking
   the `ConsumedInvite` insert blocks the join, because `Member.Authorized`'s invite branch
   needs a same-transaction fresh `ConsumedInvite` row and `consumeInvite` writes both rows
   in one transaction, so the whole join rolls back.
3. **`table CancelledInvite (InviteKey text primary key, ...)`** — insert-only tombstone
   with `OnlyClosed`, `Immutable` (no update, no delete), and `Authorized` (a
   `committed.Manager` must sign `digest('Strand.CancelledInvite', 'cancel', InviteKey)`).
   Context params are `(ManagerKey text, ManagerSignature text)`, non-null, matching
   `Revocation`'s precedent.

Design rationale (tombstone vs. deleting the `Invite` row vs. a state column; why no
`StampId`; why deliberately **no** `InviteExists` gate) is written out in full in the
comments above the table — it is not repeated here. Two `NOTE:` tripwires are parked there
too: unbounded table growth, and the fact that a cancellation must propagate before the
holder redeems.

## Behavior change: none, on its own

Nothing in the codebase writes a `CancelledInvite` row yet. Ticket 3.7
(`strand-invite-cancel-writer`, in `implement/`) carries the `cancelInvite` /
`listOutstandingInvites` writers, the off-engine pre-flight, the permanent tests, and the
docs. **The re-admit test at `strand-member-revocation.spec.ts:573` still passes** — that is
expected and correct at this point; 3.7 rewrites it.

### Throwaway smoke test (deleted — 3.7 owns the permanent version)

Because nothing writes to the new table, its own three constraints would otherwise have gone
completely unexercised until 3.7. A temporary spec was written against a real closed strand DB
(`connectToStrand` bootstrap mode, same harness as `strand-membership-invite.spec.ts`) and all
four assertions passed:

- a manager cancels an outstanding invite → 1 row (`Authorized` accepts a real manager)
- a cancellation signed by a non-manager is rejected → 0 rows
- **a cancelled invite can no longer be consumed** → `consumeInvite` rejects (`NotCancelled` works)
- a cancellation cannot be deleted → rejects, row survives (`Immutable` works)

It was then deleted, to keep this ticket's diff schema-only per its scope. The two non-obvious
bits for 3.7 to recreate it:

```ts
const signature = signStrandApproval(
  ['Strand.CancelledInvite', 'cancel', inviteKey],
  managerKeyPair.privateKeyB64,
);
await db.exec(
  `insert into Strand.CancelledInvite (InviteKey)
     with context ManagerKey = ?, ManagerSignature = ?
     values (?)`,
  [managerKeyPair.publicKeyB64, signature, inviteKey],
);
```

## The trap that nearly produced a false green — read this

`packages/cadre-core` imports `@serfab/quereus-plugin-sereus` through its package `exports`,
which point at `dist/`. The root `yarn test` script runs `yarn workspaces foreach -A run test`
— **`-A`, not `-At`** — so it is not topological and has no build dependency.

Consequence: an edit to `STRAND_SCHEMA` in `src/` is **invisible** to the entire cadre-core
suite until `yarn workspace @serfab/quereus-plugin-sereus build` is run. The first full
cadre-core run on this ticket reported 938 passing against the **old** schema — a clean green
that proved nothing. Only the smoke test caught it, failing with
`QuereusError: Table not found: Strand.CancelledInvite`. After the rebuild, everything above
was re-run.

The drift guard does not protect against this: it imports `../src/strand-schema.js` directly,
so it passes on unbuilt source.

Filed as `backlog/debt-embedded-schema-stale-dist-false-green`. Anyone touching either
embedded schema copy must rebuild the plugin before trusting a cadre-core run.

## Known gaps, honestly

- **No permanent test asserts any of this.** The only test that newly passes here is the drift
  guard, which compares text — it cannot tell a correct constraint from an incorrect one. The
  four behavioral assertions above were run once and thrown away. Until 3.7 lands, the
  security property is verified only by that transient run.
- **`Invite` still has no invitee binding**, so cancellation cannot cascade off a member
  removal — removing a member auto-cancels nothing, because an invitation names no invitee.
  Filed as `backlog/feat-strand-invitee-bound-invites`; deliberately out of scope.
- **Propagation is not solved.** A holder redeeming on a node that has not yet converged on
  the `CancelledInvite` row still gets in. Same convergence class as the existing
  `NotRevoked` / `MinOneMember` / `MinOneManager` local-visibility notes, and parked as a
  `NOTE:` on the table rather than as a ticket.
- **`with context (ManagerKey text, ManagerSignature text)` is non-null** while the sibling
  invite tables use `text null`. `Revocation` at `schemas/strand.qsql:446` already does the
  non-null form, so this follows precedent — but worth a reviewer's eye, since every other
  table in the *invite* chain is nullable.
- One line was added to `tickets/implement/3.7-strand-invite-cancel-writer.md` warning about
  the rebuild requirement, since 3.7 will be picked up without necessarily reading this file.

## Suggested review focus

- Does `NotCancelled` on `ConsumedInvite` alone genuinely close the join, or does
  `Member.Authorized`'s invite branch need a matching gate? (The comment argues it does not,
  because both rows are written in one transaction — worth an adversarial read.)
- `Authorized` reads `committed.Manager`. Confirm a manager seated in the same transaction
  cannot authorize its own cancellation, matching every sibling `Authorized`.
- The absent `InviteExists` gate is deliberate (fail-open would be worse), but it means the
  table accepts arbitrary junk `InviteKey` values from any manager. Confirm that is the right
  trade against the growth tripwire noted on the table.
