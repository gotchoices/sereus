# Review: one party-wide `clusterSize`, defaulting to 2

## What changed

`clusterSize` — the number of nodes Cadre tells Optimystic a replication group ("cluster")
should have — was hardcoded to `3` at four call sites. Optimystic's cluster **member** now
uses that number as an admission gate: a member refuses to vote on a write when the
coordinator's declared peer set is smaller than the member's own configured size and the
member has no confident network-size estimate. A commit needs a super-majority (unanimity at
two nodes), so one refusal failed every write on any party running fewer than three nodes.

It is now one optional config value resolved through a single exported constant:

| File | Change |
| --- | --- |
| `packages/cadre-core/src/types.ts:249` | new `export const DEFAULT_CLUSTER_SIZE = 2` (auto-exported — `index.ts` does `export * from './types.js'`) |
| `packages/cadre-core/src/types.ts:314` | new `CadreNodeConfig.clusterSize?: number` with the "same value on every node, frozen at construction" doc comment |
| `packages/cadre-core/src/cadre-node.ts:739` | control network reads `this.config.clusterSize ?? DEFAULT_CLUSTER_SIZE` |
| `packages/cadre-core/src/strand-instance-manager.ts:57-64` | new `StartStrandConfig.clusterSize?: number` |
| `packages/cadre-core/src/strand-instance-manager.ts:269` | strand networks read `config.clusterSize ?? DEFAULT_CLUSTER_SIZE` |
| `packages/cadre-core/src/cadre-node.ts:2441` | `launchStrand` forwards `this.config.clusterSize` |
| `packages/integration-tests/src/harness/test-party.ts:13,50` | imports `DEFAULT_CLUSTER_SIZE` from `@serfab/cadre-core` |
| `packages/quereus-plugin-sereus/test/e2e/networked.e2e.spec.ts:30-37,98` | local `TEST_CLUSTER_SIZE = 2` (that package does not depend on `cadre-core`); the stale file comment at lines 19-22 that claimed `clusterSize: 3` "mirrors cadre-node.ts:277-280" is rewritten |
| `docs/architecture.md` | new `#### Replication cluster size` subsection under `### Control Network` |

Deliberately **not** derived from live membership. The control libp2p node is created before
the `ControlDatabase` holding `CadrePeer` rows exists, the value is frozen at libp2p-node
construction anyway, and membership is eventually consistent — so per-node derivation would
reintroduce the exact divergence the gate punishes. Reasoning is in the source ticket and
summarized in the new docs subsection.

**Resume path checked** (ticket asked): `StrandInstanceManager.resumeStrand` builds
`resumeConfig` by spreading the retained `launchConfig` (`strand-instance-manager.ts:399`),
so `clusterSize` carries through a quiesce/resume cycle unchanged. Only `bootstrapNodes` and
`mode` are overridden.

**Blocked ticket updated.** `tickets/blocked/control-db-convergence-optimystic-p2p.md` had a
`description`/`blocked-reason` asking a human to decide "shrink cluster size or push
upstream" — half of which this ticket answers. Its header, stale `files:` line references,
and a dated update section were corrected so the human inbox is accurate. No other tickets
touched.

## Use cases to validate

**A one-node party still works.** Optimystic short-circuits to local storage when a block's
cluster has `peerCount <= 1`, so a lone node never reaches the gate. Two is also Optimystic's
own `minAbsoluteClusterSize`, so this is the smallest value that is legal at all.
→ `enrollment-e2e` + `seed-bootstrap` scenarios: **13 passed**.

**A two-node party's writes commit.** This is the actual bug. Verify by log, not by test
color — the scenarios stay red on a separate read-side defect.
→ see the table below.

**An operator can raise the value.** `new CadreNode({ ..., clusterSize: 3 })` should reach
both the control network and every strand it starts. **Not covered by any test** — see gaps.

## Known gaps — treat these as the review's starting points

- **No test asserts the wiring.** Nothing checks that `CadreNodeConfig.clusterSize` actually
  reaches `createLibp2pNode` for either the control network or a strand, or that the default
  is applied when omitted. The evidence is entirely "the rejection log line disappeared",
  which is real but indirect. A unit test that spies `createLibp2pNode` (or reads the value
  back off the built node) would pin it. Worth deciding whether that belongs here or as a
  `debt-` ticket.
- **No test covers the raise-it path.** Every run above exercises the default. An operator
  setting `clusterSize: 3` is untested end-to-end, including the "must be the same on every
  node" rule — which is documented but not enforced anywhere in code. There is no validation
  that rejects e.g. `clusterSize: 0` or `1`, both of which are nonsense (Optimystic's floor is
  2). Consider whether `CadreNode.start()` should reject a value below 2.
- **Duplicate literal.** `packages/quereus-plugin-sereus/test/e2e/networked.e2e.spec.ts`
  hardcodes `2` because that package does not depend on `@serfab/cadre-core`. The comment
  names the rule, but the two numbers can drift silently. Judge whether the dependency is
  worth adding.
- **Only two of the ten known-failing scenarios were re-run under the cluster debug flag.**
  `strand-formation-e2e`, `multi-party-workflows`, `convergence-stress`, `push-wake-e2e`,
  `websocket-chat`, `control-cohort-auto-convergence`, and
  `strand-membership-closed-strand-e2e` were not checked for residual `admission-reject`.
  They share the harness so they should be clean, but that is inference, not measurement.
- **The plugin e2e failure mode changed shape.** It used to fail with
  `membership-not-admitted`; it now fails with `Failed to get super-majority: 1/2 approvals
  (needed 2, **0 rejections**)` plus `The stream has been reset`. Zero rejections means the
  gate is no longer the blocker — a peer simply did not answer — which is consistent with the
  blocked read-side ticket. Worth a second opinion that this is the same underlying defect and
  not a new one surfaced by the smaller cluster.
- **Replication breadth dropped from 3 to 2.** Intended and documented (the cost of a smaller
  value is breadth, not correctness), but it is a real durability change to production paths:
  blocks now land on two nodes rather than three, and the churn-spread expansion cohort
  shrinks correspondingly. Nobody has signed off on that as a product decision — the source
  ticket decided it on correctness grounds alone.
