# Review: phone reference app joins an existing cadre

Settings' old "Join a Cadre" section is replaced by **Join my existing cadre** (`src/join-cadre-section.tsx`). The steps after Join live in the hook (`use-cadre.ts`), so they survive a tab switch. Their type and words are in `src/join-flow.ts`, which has no React. The full user-facing description is in docs/reference-app-rn.md → "Joining an Existing Cadre".

## What was built

- **`join-flow.ts`**: contains the `JoinFlow` union as the ticket specified, `flowForProgress` (maps the kit's `PhoneJoinProgress` to a step), `joinFlowText` (the words for each step), `JoinCancelledError`, and the shared helper `chats(n)`.
- **Hook** (`use-cadre.ts`):
  - New state `joinFlow`.
  - New actions: `joinExistingCadre`, `cancelJoin`, `retryStrandMove`, `removeOldCadre`, `keepOldCadre`, `dismissJoinFlow`, plus the pass-throughs `identityPeerId` and `joinRequestText`. `joinCadre` is removed.
  - A join and a dissolve both stop the node, so each one calls `showNode(null)` and sets status `connecting` (`showSwitching`). When it ends, `adoptSwitchedNode()` adopts the kit's running node and refills `savedStartOptions` from `getRunningOptions()`. These are the two review findings from earlier work that were easy to regress.
  - The check "on Connect and at launch" is `resumeUnfinishedJoin`, called at the end of `start`.
- **`cadre-phone.ts`**:
  - New pass-throughs: `identityPeerId`, `joinRequestText`, `pendingStrandMove`, `finishStrandMove`, `dissolveFormerParty`.
  - Re-exports the error classes the hook tells apart (`FormerPartyNotEmptyError`, `StrandMovePendingError`, `StrandMoveNotOwnerError`), so the hook reaches the kit only through this already-mocked module.
- **`join-failure.ts`**: adds wording for `StrandsNeedOwnerJoinError`. That error can have `strandCount` 0 (only pending joins or invitations to move), so that case gets its own wording. Also adds `joinFailureAlert(err)`, which gives the title "Join cancelled" for `JoinCancelledError` and "Join failed" for everything else.
- **Settings**:
  - The section renders when `connected || joinFlow !== null`.
  - While a join or removal is stopping and starting the node (`status === 'connecting' && joinFlow`), the Node card shows "Switching cadre…" instead of the Connect form. This is what makes the refill safe, and the effect's comment now says so.
  - The seed hint now points to the new section.
- **Maestro** (`_setup.yaml`): after Join, the flow uses `scrollUntilVisible` on `btn-join-flow-ok` (timeout 120 s), asserts that `text-join-flow` matches "This app is now part of your cadre.*", and taps OK.
- **Docs**:
  - reference-app-rn.md: a new "Joining an Existing Cadre" section; updated the start-options bullets, the dissolve-marker paragraph, the cold-start trust note, the file list and the e2e description.
  - architecture.md: new labels at the end of the invitation section and in the add-a-node table, plus one sentence under "Handing an invitation from app to app" naming both RN sections.
  - README: troubleshooting wording.

## Where this differs from the ticket (reviewer: check these calls)

- **The first-launch relay default is in `cadre-phone.ts`'s `joinCadreByInvitation`, not the hook.** It passes `relayAddrs: resolveRelayAddrs()` only when the kit has neither running options nor a saved start. No Noise mode is passed: the kit's platform default (`noiseCrypto.defaultMode: defaultNoiseCryptoMode()`) gives the same value. Importing `noise-crypto-config` into the hook would also load `react-native-quick-crypto` in the hook's test environment.
- **`joinRequestText` is implemented in `cadre-phone.ts`, and the hook only passes it through.** It needs `expo-constants`, which cannot load in the react test project. `appName` is `Constants.expoConfig?.name`, trimmed, defaulting to "Sereus reference app" and cut to `CADRE_JOIN_REQUEST_MAX_APP_NAME`.
- **`done.grantsOwner` comes from the kit, not the join result.** It is `getOwnerPublicKey() !== null`, so it is also right after a relaunch, when there is no join result. Consequence: when an owner grant's key was not yet wired within the kit's bound, and there was nothing to move, done says "as a member". The Node card and Add-a-device section say the same, and the next start wires the key.
- **The `done` line leaves out the chat count when it is 0.** That covers a join with nothing to move, and a removal finished after a relaunch, where the count is unknown (`movedRef` is 0).
- **The hook never shows an alert.** Before admission, `joinExistingCadre` rejects and the section shows the alert. After admission it never rejects. A removal that fails with an unexpected error ends at `old-cadre-remains` with an `error` field, shown as the detail line ("Removing it failed: …"), where the ticket said to show an alert.
- **Added buttons and actions:**
  - `old-cadre-remains` also has a **Later** button, so the step is not a dead end that hides the join inputs.
  - Added a `keepOldCadre()` action for the **Keep old cadre** answer.
  - `stop()` clears the flow; the next Connect shows the step again.
- **The device token is published after the whole flow settles**, after the old cadre's removal restarts the node, instead of right after admission.
- **Double-tap guards:**
  - The public `removeOldCadre` and `retryStrandMove` are ignored while a running step is on screen. Internally the hook calls `dissolveOldCadre`, which has no guard.
  - A second `joinExistingCadre` throws "A join is already on screen" whenever any flow is set. This includes resting steps such as `done`, whose join inputs are hidden anyway. The deep-link ticket may want to relax this.
- **`JoinCadreSection` takes a `firstLaunch` prop** that only drops the "chats move / own cadre is removed" half of the intro line. Settings does not pass it yet; `reference-app-rn-first-launch-asks-before-founding` will.
- **Test-id names** (new): `text-join-request-code` / `btn-join-request-copy` (via `ShareCode` prefix `join-request`), `btn-scan-cadre-invitation`, `text-join-flow`, `text-join-flow-detail`, `btn-cancel-join`, `btn-retry-strand-move`, `btn-join-flow-later`, `btn-discard-old-cadre-items`, `btn-keep-old-cadre`, `btn-remove-old-cadre`, `btn-join-flow-ok`. `input-cadre-invitation` and `btn-join-cadre` are kept.

## Tests

- `test/react/use-cadre.spec.ts` → "a join drops the node it stopped and refills the saved options from the joined party". It launches into a saved party, makes `joinCadreByInvitation` pend, then checks that `node` is null during the join. After the join resolves with the mock's running options set to `party-a`, it checks that the node is adopted and that `savedStartOptions.partyId === 'party-a'`.
  - Mutation-checked: removing `showNode(null)` from `showSwitching` makes it fail, and so does removing the `setSavedStartOptions` refill.
  - The module mock gained `getRunningOptions`, `getPhoneNodeStatus`, `joinCadreByInvitation`, `identityPeerId` and `joinRequestText`. `start` now reads `getRunningOptions`, and the hook returns the two identity functions on every render.
- `test/join-failure.spec.ts`: one more row in the existing table. A real `StrandsNeedOwnerJoinError` from `@serfab/cadre-rn/phone-node` gets the owner wording. That spec exists to catch `instanceof` drift against the real classes.
- Commands run: `yarn workspace @serfab/reference-app-rn typecheck` (clean), `… test` (18 files, 153 tests pass), `yarn lint` (clean).

## Known gaps

- **Nothing ran on a device or emulator, Maestro included.**
  - The `_setup.yaml` change is unverified. Its main assumption is that once the connected sections reappear above the join section, a DOWN `scrollUntilVisible` still reaches the OK button.
  - The device run is to be filed by `reference-app-rn-first-launch-asks-before-founding`.
- **Most of the flow's sequencing has no test**, as the ticket decided: the removal after a move, the refusal mapping, the relaunch check, and cancel. All were checked by reading against the kit's code only.
- **An old cadre kept on purpose shows again at every start.** This applies to one with other machines and to one where the user tapped "Keep old cadre": `formerPartyId` stays saved, so the relaunch check shows `old-cadre-remains` again, and Later dismisses it. Left as a `NOTE:` at `resumeUnfinishedJoin`. Revisit if it nags; the fix would be to remember the answer per old party.
- **After a relaunch, `move-incomplete` shows no moved count** (the kit's `PendingStrandMove` carries none). Its reason is inferred from whether the kit reports an owner key (`owner-key-not-wired`, else `partial`).
- **A failed read of the move record is shown as "some" chats still waiting.** On a relaunch it is shown as `old-cadre-remains` instead; the removal then re-reads the record and shows its error.
- **Strands the move refused permanently** (`PendingStrandMove.refused`, `StrandMoveReport.refused`) are not shown anywhere in the UI.
- **The request view reads the identity twice**, through `identityPeerId()` and `joinRequestText()`. Both are cheap kit calls.
- **Unchanged:** the NativeScript app (its docs still say "Join a Cadre") and the web app (tickets `reference-app-web-*`).
