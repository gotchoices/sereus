# The reference apps mark a message that is not yet delivered

Applies the prereq's API (`StrandDatabase.commitDurability(tx)`, `CadreNode` event `strand:commit-held`; contract in `docs/strands.md` → "A commit's durability") to the three reference chat apps. A message this device sent whose commit no other member holds shows a "Not yet delivered" label; the label clears when `strand:commit-held` names that commit.

## What was built

The same shape in all three apps:

- **Write.** The message insert is one statement, `insert into App.Message (…) values (?, ?, ?, ?) returning StampId() as Tx`, run through `db.get`. The web app's `insert or ignore` of the `Participant` row stays a separate statement before it.
- **Mark.** Right after the insert, the app reads `strand.database.commitDurability(Tx)`. If a report exists and `heldElsewhere` is false, it records a mark `{ strandId, transactionId, messageId }`. No report, or `heldElsewhere: true`, records nothing. A resend that finds the row already stored writes nothing and records nothing.
- **Clear.** On `strand:commit-held`, the app removes the mark that matches both `strandId` and `transactionId`. Marks are keyed by strand, so switching away from a strand and back still shows them, and an event for one strand cannot clear a mark on another.
- **Show.** The label reads "Not yet delivered". Test ids: RN `TEST_IDS.chat.undeliveredMark(id)` (`message-undelivered-<id>`); NS has the same id, set as the label's `automationText`; web `data-testid="message-undelivered"` inside the `message-row` item.
- **In memory only.** There is no persistence. Messages read from storage carry no mark. A mark whose commit is never followed stays until the app restarts (or the web page reloads).

Per app:

- **RN.** `insertMessage` returns `StoredMessage { message, undeliveredCommit: string | null }`. The durability decision is the private `undeliveredCommit()` in `chat-operations.ts`. `ChatSender.send` now returns `{ stored, alreadyStored }`, where `stored` replaces the old `message` field. `useChat` takes a new `node` option, keeps the marks in React state, subscribes to `strand:commit-held` in its own effect, and returns `undelivered: ReadonlySet<string>`, the marked message ids of the strand on screen. `app/index.tsx` passes `extraData={chat.undelivered}` to the `FlatList`. Without it, a mark clearing would not re-render the row, because `data` does not change.
- **NS.** `chat-operations.ts` has the same change as RN, and the two files stay parallel (a whitespace-insensitive diff shows no difference in the new lines). `CadreViewModel` binds and unbinds `strand:commit-held` next to `strand:writable` and re-sends it as its own Observable event, `CadreViewModel.commitHeldEvent` (`CommitHeldEventData`). `ChatViewModel` listens to that event, holds the marks, and adds `undeliveredVisibility` and `undeliveredId` to `ChatRow`. When a mark clears, the shown row is replaced with `setItem`. `chat-page.xml` has the label and `app.css` has `.undelivered`.
- **Web.** `insertChatMessage` returns the commit id (`string | null`). `writeChatMessage` ignores it and still returns the message id, so the e2e helper is unchanged. `messages.svelte.ts` holds `state.undelivered` and exports `markDelivered` and `isUndelivered`. `store.svelte.ts` subscribes `markDelivered` to `strand:commit-held` beside its other node events. I chose not to log the event to the Activity list: it fires once per held commit, cadre-core's own writes included, and would push lifecycle events out of the capped log.
- **Docs.** New section `docs/reference-app-rn.md` → "Messages Not Yet Delivered". It covers the mark, the founder-alone reading, and the in-memory limit. The package-structure line for `use-chat.ts` is updated. The "What apps do with it" bullet in `docs/strands.md` links to the new section.

## For the reviewer

- **Ordering between the mark and the clear.** If the commit becomes held before the app reads it, the prereq's record already says `heldElsewhere: true`, so no mark is set. Between the read and recording the mark there are only microtask hops (RN: `insertMessage` → `ChatSender` → `useChat.send`; NS and web: the same function), so a `strand:commit-held` from network I/O cannot land in between. Worth a second look on RN, where React queues both `setMarks` updaters and applies them in order.
- **RN records the mark before the "strand switched mid-send" early return.** This is on purpose: marks are keyed by strand, so the message shows its mark when the user switches back.
- **`undeliveredCommit()` checks that `Tx` is a string** instead of casting it or throwing. If it is not, nothing is marked and the send still succeeds. On a strand database the Optimystic plugin always registers `StampId()`.
- **Marks never clear when the node changes** (Disconnect then Connect, or joining another party). The new node will not fire `strand:commit-held` for commits the old one made, so those marks stay until restart. This matches the documented limit ("not confirmed delivered"), but the reviewer may prefer to drop marks when the node changes.
- **NS `chat-vm.spec.ts` does not exercise a marked row**, because the fake strand never reports a commit's durability. The `setItem` path in `markDelivered` is checked only by the typechecker.
- Line endings: the edited files are LF in the working tree, while the checkout uses CRLF (`core.autocrlf=true`). Git normalizes them on commit, and `git diff` shows only the content changes.
