# A removed machine reports its own removal — review handoff

## What was built

- **`CadreRemoval`** (`types.ts`): `{ partyId, stampId, signerKey: string | null, at }`. `at` is when this node learned of it (the tombstone carries no timestamp with meaning). `signerKey` is the tombstone's `SignerKey` only when `verifyRevocationSigner` passes and the key is in this node's trusted-owner anchor; otherwise null and a log line, and the removal is still reported. Exported through `export * from './types.js'`.
- **Event `cadre:removed`** on `CadreNodeEvents`, documented as best-effort and "nothing is stopped for you".
- **`CadreNode.removedFromCadre()`**: the same record, or null.
- **Detection** in `CadreNode.noteOwnRemoval(rows, loadTombstones)`, called last in `refreshAuthorizedControlPeers` (after `hangUpRevokedControlPeers`):
  - `rows` is the refresh's own `queryCadrePeers(false)` read (retired stamps already dropped). If self is in it, `ownLiveRow` is updated and nothing else happens.
  - If self is missing and `ownLiveRow` is set, the tombstones come from the refresh's shared `loadTombstones` source (no new read when the anchor sync or the hang-up already loaded it; otherwise one read, only on this path). A `CadrePeer` tombstone with `RowKey` = self → record + emit, once. When several tombstones name self, the one retiring the last-seen live stamp is preferred.
  - Read failure is caught and logged inside (does not reach the refresh's outer "keeping previous snapshot" catch).
  - `ownLiveRow` and `removal` are per node object and are **not** reset by `stop()`, so a stop()→start() of the same object does not re-report and the drains stay off. This is my reading of "once per process"; the reviewer may prefer resetting on stop.
- **Drains**: `drainPendingRevocations`, `reconstructAuthoredMembership`, `drainPendingPeerWrites` return early once `removal` is set. The old `NOTE:` in `drainPendingRevocations` that pointed at this work is replaced by a narrower tripwire: an owner whose key alone was removed (`removeOwner`, its row still live, so no removal is reported) still fails those drains on every growth edge.
- **Docs**: new paragraph "The removed machine learns it, best-effort" in "Removing a machine"; the aside in "What is deliberately not reaped" now links to it; an Implementation Status bullet.

## Test added

`packages/cadre-core/test/cadre-node-learns-removal.spec.ts`, driven through the gate suites' fake control database and the public `refreshMembershipGate`:

- seen live, then stamp retired + signed tombstone → exactly one `cadre:removed` after two further refreshes, with `signerKey` = the anchored owner, and `removedFromCadre()` returns that record;
- tombstone for self, never seen live → nothing;
- seen live, then old stamp retired + tombstone + a live row under a fresh stamp → nothing.

`membership-gate-helpers.ts` gained a `tombstones` option (read live by `queryRevocations`). The fake's `queryCadrePeers` still hand-mirrors the retired-stamp filter.

Validation run: `yarn workspace @serfab/cadre-core build`, `typecheck`, full `test` (167 files, 2453 passed, 1 skipped), `yarn lint`, both test-typecheck-coverage checks.

## Known gaps / things to look at

- **Emitting during `stop()`.** `_running` stays true until the very end of `cleanup()`, so a refresh already in flight when `stop()` begins can still pass the `_running && controlDatabase` re-check and emit. An embedder handler that calls `stop()` in response would then re-enter `stop()` while a stop is in progress (`stop()` only checks `_running`). Narrow race; same exposure as `strand:revoked` and other events. Not guarded; reviewer to decide whether a stopping flag is worth it.
- **`removePeer`-only removal of an owner machine.** If an owner's `CadrePeer` row is removed with the single-row `removePeer` (owner key kept), the node now reports removal and stops its re-issue drains, even though its key could still sign. `removeMachine` always removes both, so this only arises from the lower-level writer.
- **Not stopped:** step 5 of the growth drain (`pendingJoinRunner.reissueWritesMadeAlone`) and `retouchSelfDeviceToken` still run on a removed node; the ticket named only the three drains. `registerSelf`'s heartbeat log stays by design.
- **Restart-before-acting gap** is documented with a `NOTE:` at the check, as the ticket asked.
- No integration assertion, per the ticket (receiving the tombstone before being cut off is a race).

## Usage for the downstream tickets

Subscribe with `node.on('cadre:removed', …)`, and check `node.removedFromCadre()` once after `start()` for a removal detected before the subscription. Then stop the node and delete the cadre's data (`hosted-node-stops-when-removed`, `phone-kit-forgets-a-cadre-that-removed-it`, `reference-app-web-devices-and-nodes`).
