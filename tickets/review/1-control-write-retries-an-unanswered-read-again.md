## What changed

**One shared by-type predicate.** `reportsUnreachableCohort(links)` in `control-retry.ts` answers whether any link of an error's `cause` chain is a `BlockUnavailableError` with reason `peers-unreachable` or `cohort-unreachable`. It delegates to upstream's own `isCohortUnreachableRead` (exported from `@optimystic/db-core` since 1.20.0, `db-core/src/transaction/commit-failure-class.ts`), whose reason set is exactly those two. The doc that used to sit on the read side's `RETRIABLE_BLOCK_UNAVAILABLE` regex (which reasons, why, and the measured exclusions) moved onto this predicate.

**Writes.** `matchesRetriableFailure` (the shared body of all three write classifiers: default, schema init, lost update) now claims that predicate beside the final-torn-write claim, after both vetoes (`reportsPossiblyStoredWrite` by type, `reportsIndeterminateCommit` on `[blocks:`). The shortfall and aggregate text matchers are unchanged; the aggregate still arrives when a coordinator answered and left a block out.

**Reads.** `isRetriableControlReadFailure` uses the same predicate in place of the text regex, which is deleted. The aggregate is still matched by text.

**Promise-phase paragraph** (accepted-tradeoff NOTE on `isUncommittedTransactorAggregate`) now lists what 1.20.0 members actually refuse: stale revision, membership-not-admitted, an expired transaction, and a configured validator's refusal (`ClusterMember.evaluatePromise`, `db-p2p/src/cluster/cluster-repo.ts` ~1536). Block-unavailable is not a refusal: `judgeStaleRevisions` (~2034) logs `validation-block-unavailable` and votes on. The same stale list was fixed in `docs/architecture.md` and in the comment on the spec constant `PROMISE_PHASE_REJECTION_IN_PEND_AGGREGATE`.

## Findings recorded in code

- **Own-entry completion read** (NOTE in `matchesRetriableFailure`). `Collection.completeOwnEntry` calls `getStatus` only when no retained attempt exists at the entry's revision. Both commit paths (`Collection.syncAttempts`, `TransactionCoordinator.commitOnceLatched` ~1116) retain the failed attempt before refreshing, so inside one write that means a forked lineage. The throw escapes `AttemptCycle.refreshUntilSettled` and the coordinator's `refreshBetweenAttempts` unwrapped, and reaches the funnel with `cause` intact (`rewrapAsQueryError` keeps it). The log-end reads of the same refresh (`readLogEnds`) can fail the same way. A refresh that already saved a sibling collection is wrapped upstream in `CoordinatorPartialCommitError`, which the existing veto declines. No ticket filed: a re-run is a new transaction whose body re-reads, so it diffs or hits `UNIQUE`, and the `[block:` aggregate from the same reads was already retried.
- **Fail-safe by type** (NOTE on `reportsUnreachableCohort`). Upstream builds `BlockUnavailableError` in only two places, both on the reading node from the `unavailable` flag in get results (`TransactorSource.tryGet` ~62, `NetworkTransactor.getStatus` ~505). It is never rebuilt from a peer's error. A second loaded copy of db-core, or a text-only copy, is not retried. A peer's error text that ends up inside a `[block:` aggregate is still claimed by the aggregate matcher.
- **Upstream may widen the set** (NOTE on `reportsUnreachableCohort`). A reason upstream adds to its unreachability set would be retried here with no change in this repo.
- **Name collision** (NOTE on the local `isCohortUnreachableRead` in `control-read-retry.ts`). Sereus's function of that name matches `cohort-unreachable` only and is used to read an isolated node's `Revocation` block as empty. Upstream's function of the same name also matches `peers-unreachable`. Swapping one for the other would be a bug.

## Deviations from the ticket, and known gaps

- **Reason set comes from upstream, not a Sereus `readonly` constant.** The ticket asked for a local constant. Upstream's exported predicate has exactly the required set and is the rule upstream itself sorts unreachability by (its commit-failure classifier and the plugin's offline reads). Using it means there is no Sereus list that could drift from it. If the reviewer prefers a local constant (to freeze the set against upstream changes), it is a three-line change in `control-retry.ts`.
- **Wired in the shared body, not into `RETRIABLE_CONTROL_WRITE_MATCHERS`.** That list is `(message: string) => boolean` and cannot hold a by-type check. All three policies reach the shared body, so the effect is the same: schema init inherits the check, as the ticket expected.
- **Parity with 1.19 is not exact; the change slightly widens retries.** On 1.19, `peers-unreachable` / `cohort-unreachable` reported by a cohort coordinator (`CoordinatorRepo`: a consult that threw, or an isolated node) already reached writes as the typed error, and the write classifier did not retry it. It does now. The read classifier already retried those reasons. Within a write they mostly come from reads in the body before commit, which are safe to retry. The in-refresh case is covered by the NOTE above. Retry budget and delays are unchanged.
- **Reads no longer retry a text-only unavailability.** Checked: the only read caller (`ControlDatabase.readRows` → Quereus `eval`) gets the error through the plugin's `rewrapAsQueryError` and Quereus's scan emitter (`QuereusError(…, cause)`, `quereus/src/runtime/emit/scan.ts` ~227). Both keep `cause`. Nothing on that path rebuilds the error as a plain `Error`.
- **Not verified live** (as the ticket directed): that a cohort-wide read stall reaches the write funnel as this typed error in a two-node run. The `adopt-optimystic-1-20-0` gate runs the degraded-cohort scenarios. In `control-write-degraded-cohort-member.integration.ts`, `expectAggregateCarriesBatchToken` only asserts when an aggregate is present, so it does not fail when the typed error arrives instead. The live `isRetriableControlWriteFailure(outcome.error)` assertions (~1189, ~1320) now accept the typed error as well.
- The promise-phase paragraph now names expiry, which the old list left out. The paragraph does not claim whether retrying an expiry helps. (The bridge mints a fresh stamp per transaction, `txn-bridge.ts` ~1486, so a re-run gets a new expiry. Clock skew would not clear.)

## Tests

- `control-write-retry.spec.ts` — new `describe.each(WRITE_CLASSIFIERS)('%s — typed unanswered read')`, one `it`. A real `BlockUnavailableError(…, 'peers-unreachable')`, bare and through `viaQuereus`, is retriable. The same error as the `cause` of a `[blocks:` commit-phase aggregate is vetoed. It runs for all three write classifiers, which pins that the check lives in the shared body.
- `control-read-retry.spec.ts` — every block-unavailability case now builds the real class: the improvable reasons, the excluded reasons, possibly-stale (`BlockPossiblyStaleError`, via a new `scanWrappedTyped` helper), the loop's transient and non-retriable cases, and the `ControlDatabase` non-retriable case. A text-only `Block … is unavailable (peers-unreachable)` was added to the "unmatched" list to pin matching by type. The `BLOCK_POSSIBLY_STALE` literal was removed.
