# Review: the six approval-replay attack pins + the five-element digest parity case

Follow-up to `strand-approval-stamps-and-tags` (which landed the mechanism). This ticket
added only TESTS — no schema, writer, or doc change was needed, because the tripwire the
ticket asked for was already written into both schema copies by the parent pass.

## What shipped

### `packages/cadre-core/test/strand-approval-replay.spec.ts` (new, 6 tests)

Each of R1-R6 was reproduced as SUCCEEDING against a real closed strand before the stamp
mechanism landed. Each test now captures the approval, performs the state change, replays it,
and asserts the rejection — then runs the legitimate operation the replay was derived from,
so a rejection can never be an artifact of the strand being in a state where the operation is
impossible anyway.

| #  | Captured approval | Replayed as | Pinned rejector |
|----|---|---|---|
| R1 | `addManager` promotion of X at generation 1 | re-insert `Manager(X, 1)` after removal | `NotRevoked` |
| R2 | `removeManager` removal of X | delete `Manager(X)` after re-promotion | `Authorized` |
| R3 | X's own resignation | delete `Manager(X)` after re-promotion, mounted by a party that never held X's key | `Authorized` |
| R4 | `addMemberByManager` admission of X | re-insert `Member(X)` after revocation | `NotRevoked` |
| R5 | `revokeMember` removal of X | delete `Member(X)` after re-admission | `Authorized` |
| R6 | `registerMemberPeer` binding (M, P) | re-insert (M, P) after removal; plus the same approval presented on the DELETE | `NotRevoked`, then `Authorized` |

"Capturing" an approval means re-minting the signature the writer itself produced — same
signer, same digest element vector, read off the LIVE row before the legitimate removal.
Ed25519 is deterministic (RFC 8032), so the bytes are byte-identical to the ones that
authorized the real write; an attacker who observed that write holds exactly this. **A
reviewer should check this claim first** — if signing were non-deterministic, every capture
here would be a strawman rather than the real attacker capability.

### `digest-variadic-parity.spec.ts` — new case (e)

Cases (a)-(d) pinned TEXT fields only. Case (e) pins the five-element Manager promotion
digest `('Strand.Manager', 'add', memberKey, generation, stampId)`, the only signed digest in
the schema carrying an SQL INTEGER. It asserts, all confirmed green:

- the bound NUMBER and the SQL integer LITERAL `7` hash identically (so the parameter binding
  is not doing the work — the column shape is what the constraint really sees),
- `String(generation)` on the TS side does **not** verify against the integer, and the
  number-signed approval does not verify against a TEXT generation — the type-tagged framing
  the writer's doc comment claims is real, now pinned in both directions,
- a neighbouring generation and a different stamp each produce a different digest.

Note for the reviewer: the ticket's wording asked to "bind the generation as a NUMBER … and
pass `String(generation)` on the TS side" as the *parity* leg. Taken literally that is the
MISMATCH case, not parity — the schema's type-tagging makes the two hash differently. The case
was written with the number⇔integer parity as the positive assertion and the stringified form
as the negative, which is what the mechanism actually guarantees; both legs are asserted, so
nothing was dropped.

## Tripwire

The `Strand.Revocation` growth tripwire the ticket asked for was **already recorded** by the
parent pass, byte-identically in both schema copies (`schemas/strand.qsql` and
`packages/quereus-plugin-sereus/src/strand-schema.ts`): the table grows one row per membership

## Known gaps — treat the tests as a floor

- **Pin isolation is argued, not proved.** Each `/NotRevoked/` and `/Authorized/` pin rests on
  a written argument that every sibling constraint passes. The arguments are in the test
  comments. Nothing mechanically verifies them, so if a pin is wrong the test would still be
  green while measuring the wrong gate. The highest-value review pass is re-deriving those
  arguments against the schema — especially R2/R3/R5/R6's second half, where a
  founder-or-member tombstone over the *current* stamp is what keeps `RevocationRecorded` and
  `Revocation.RowIsGone` from firing alongside `Authorized`.
- **Only the local single-node path is exercised.** These run against a bootstrap-mode strand
  (MemoryRawStorage + the optimystic local transactor). The convergence hazard the schema
  already documents — a node that has not yet seen a `Revocation` row will still accept a
  replayed add, and the resurrected row coexists with the tombstone after merge — is
  **untested here and untestable in this harness.** No multi-node replay scenario exists.
- **`Strand.Invite` / `ConsumedInvite` are deliberately out of scope** (insert-only with a
  fresh PK per row), so no replay pins exist for them. The separate gap that a revoked member
  re-admits itself off an *unspent* invite is pinned as accepted behavior in
  `strand-member-revocation.spec.ts` and tracked as `bug-strand-invite-no-revocation`.
- **The `fileTombstone` helper is now duplicated in three specs** (this one plus the two the
  parent ticket touched), mirroring the writer's private `insertRevocation`. The parent
  review considered and deliberately kept the duplication; recorded so it is not re-opened as
  a fresh question.
- **Not run:** `packages/integration-tests/src/scenarios/strand-membership-closed-strand-e2e.integration.ts`.
  Unchanged by this ticket, but it is the real-network scenario over this schema and its
  wall-clock exceeds the 10-minute agent idle limit — a human or CI must run it.

- Tripwire (pre-existing, verified not re-filed): `Strand.Revocation` only ever grows —

- The ticket's five-element parity instruction was internally contradictory (see above); the
