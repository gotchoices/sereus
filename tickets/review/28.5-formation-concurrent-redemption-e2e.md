# Review: concurrent-redemption e2e scenario (built; red on a diagnosed upstream defect)

## What was built

**`strand-formation-concurrent-redemption.integration.ts`** — the acceptance scenario the
implement ticket specified, complete: real network, two real `CadreNode`s answering
redemptions (A storage/owner, B plain member), two more real joiner nodes, same-tick
`Promise.allSettled` race, no stubs.

- **Case 1** — multi-use invite gated by a real HTTP `ApprovalHookServer`: both concurrent
  redemptions must survive, per-row attribution (distinct joiner-minted `UsageStampId`,
  each joiner's own `PeerKey`/signature/disclosure re-verified via
  `verifyFormationConsent`), rows visible on BOTH nodes' views, and the hook asked
  **exactly** twice (hard equality, asserted before the convergence waits so a hook
  regression cannot hide behind a convergence failure).
- **Case 2** — single-use invite raced by both nodes: asserts the invariant (approved
  responses ↔ surviving rows, one-to-one, both views), terminal `'Invalid token'` (never
  a retry hint) for a refused joiner, and — when both land — that the accepted
  over-admission is observable (`countFormationUsage > TotalUses` on both nodes).
- **Case 3** — after the cohort agrees case 2's invite is spent, a third redemption
  through either node is refused terminally and adds no row.
- A standing unlimited "door" invite keeps the membership connection gate open for case
  3's fresh dials, so a gate refusal cannot masquerade as the terminal token refusal
  under test. Teardown is idempotent and shared by `afterAll` and the `beforeAll` failure
  path (all four nodes + hook socket).

**`bootConnectedPair`** (`harness/node-fixtures.ts`) — new sibling of `bootPair` with
connect-then-write ordering: both nodes confirm a control cohort ≥ 2 (via `readCohort`)
BEFORE the first control write, owner genesis included, and the returned `ownerSign`
closure lets scenarios publish owner-signed control rows. `bootPair` itself deliberately
untouched (other scenarios depend on its write-while-alone ordering).

**`countFormationUsage` NOTE updated** (`cadre-core/src/control-database.ts`) — records
that the seat-cap count is currently blind to sibling-written rows (see below).

## Status: red, deterministically, on a defect this pass isolated and filed

The scenario fails 2/2 whole-file runs — NOT on the race, the approvals, or the refusal
paths (both joiners are approved, `requestCount === 2` holds, rows commit under distinct
nonces) — but on cross-node visibility: each node's per-token view holds only its own row
after 30 s.

This pass ran the ticket's scratch discriminator (now deleted per its own header) and
isolated the cause: **the sibling's data tree converges — a full scan sees the row within
seconds — but an index-seek (`where Token = ?` via `FormationUsageByToken`) never does.**
Debug logs show the insert transaction pends 3 blocks (including the new index leaf) but
commits 2, and the index collection's header block is never in the transaction at all, so
the sibling's index root stays at its schema-init empty state. Silent; read-repair
no-ops; the currency machinery optimystic shipped 2026-08-12 cannot flag it (no peer ever
holds a higher index revision to raise doubt against).

Filed and cross-linked by this pass:

- upstream: `../optimystic/tickets/fix/secondary-index-update-never-reaches-the-sibling.md`
  (full log evidence + repro recipe);
- here: `tickets/blocked/secondary-index-seek-blind-to-sibling-rows.md` (category b,
  unblock condition = rebuild sibling, re-run this scenario 5×);
- `tickets/.pre-existing-known.md` gained the mapping for this file's 3 tests (do not
  re-triage);
- product consequence recorded at the code site: `countFormationUsage` — the invitation
  seat cap — reads through the blind index, so a multi-machine party currently
  **over-admits without bound**, far beyond the bounded race window
  `formation-unique-token-redesign` accepted. That makes the upstream fix load-bearing
  for the invite cap, not just for this test.
