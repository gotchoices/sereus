# Membership actions from a party's non-founding machine — implemented

New scenario `strand-membership-second-machine.integration.ts`: one narrative test on a
closed strand across two parties × two machines (`bootTopology` 2×2 `genesis-first`
full mesh + `joinStrandOn` with `type:'c'`, `founder:true`, all four machines), with
every membership writer call issued from machine index 1 of party B — a machine that
neither founded the strand nor is its party's owner. The sibling
`strand-two-party-two-machine.integration.ts` owns the physical-replication story for
this shape; this file is deliberately visibility-gates-only (stated in its header).

## What the test does (validation map)

- **Bring-up floor**: founder bootstrap seated exactly Header/Member/Manager on a[0]
  (member/manager key asserted equal to the derived founder key), then a gate per
  non-founding machine that those rows become visible.
- **Phase 1 — join consumed on b[1]**: a[0] issues the invite; b[1] runs
  `consumeInvite` against its OWN database. The deferred `ConsumedInvite` checks
  resolve the a[0]-authored `Strand.Invite` row from a wrong-party AND wrong-machine
  node. Gated back: Member + ConsumedInvite visible from a[0].
- **Phase 2 — two device records under ONE member**: `registerMemberPeer` from b[1]
  (its real strand peer id), gated visible from a[0]; then the same member registering
  b[0]'s peer id from b[0]'s database (after gating the b[1]-authored Member row
  visible there — `MemberPeer.MemberExists` reads it). Both rows enumerate from a[0]
  via `listMemberPeers`. This two-rows-one-member shape is the data no prior topology
  could create.
- **Phase 3 — manager rotation driven from the second machine**: a[0] promotes party
  B's member; the Manager row is gated visible on b[1] (generation pinned to 1, with
  the writer-policy caveat comment copied from the e2e); then FROM b[1] the new
  manager issues a further invite (`Invite.InviteValid`'s live Manager read against an
  a[0]-authored row) and admits a third member key by consuming it there. Gated
  visible from a[0] AND from a[1] — a[1] authors nothing in the file and is gated on
  the full member set, the manager row, and both device records.
- **Phase 4 — rejection floor, LAST**: a fresh unadmitted keypair's `issueInvite`
  from b[1] rejects; `rejects.toThrow()` only, nothing follows (the e2e's rejection
  floor and scan-not-seek lookup discipline are inherited and restated in the header).

## Measured

Two foreground runs, both green (logs:
`tickets/.logs/scenario-two-by-two-strand-membership.test{1,2}.log`):
bring-up ~6.0-6.1 s, phase 1 ~1.5-1.6 s, phase 2 ~1.2-1.3 s, phase 3 ~2.3-2.6 s,
test 11.9-12.6 s, wall 28-30 s. Test timeout 360 s per `topology.ts`'s TIME BUDGET;
shared gate budget 60 s matching the sibling core scenario. `yarn lint` and
`yarn workspace @serfab/integration-tests typecheck` clean. `docs/testing.md`'s
Topology coverage map line flipped from Uncovered to covered.

## Known gaps (honest floor for review)

- **`addMemberByManager` (the `committed.Manager` snapshot read) is NOT exercised from
  the second machine** — the ticket offered `consumeInvite`/`addMemberByManager` as
  alternatives and the invite path was chosen because it consumes the invite it just
  issued (no dangling row) while still exercising both writers from b[1]. The
  committed-snapshot branch runs from a second NODE (one machine per party) in the
  closed-strand e2e's fifth test; from a second MACHINE of a multi-machine party it
  remains unexercised. Judged inside the ticket's "lean lifecycle, not breadth" scope.
- **The manager-issued invite is consumed on b[1] itself**, so its `ConsumedInvite`
  checks read a local Invite row — cross-machine invite resolution is phase 1's claim,
  not phase 3's. Phase 3's cross-machine claim is the live Manager-table read.
- **One rejection case only** (unadmitted keypair issuing an invite), per the ticket's
  negative-floor spec; the accept/reject breadth stays in the closed-strand e2e.
- The whole integration suite was not re-run (many-minute wall clock, and this change
  adds one file touching no shared code); lint/typecheck are repo-wide, and the two
  scenario runs are the behavioural evidence.
