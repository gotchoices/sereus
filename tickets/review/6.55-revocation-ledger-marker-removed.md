# Revocation ledger marker: filing path removed

## What changed

The marker is the row `('Revocation', 'ledger', 'opened')` in `CadreControl.Revocation`, which an owner machine filed on its first connected reconcile pass. Its only purpose was to give that table an Optimystic collection, so reads of `Revocation` stopped asking the cohort whether the block exists. `control-collections-created-at-cadre-founding` now commits every control table's empty collection at genesis, so nothing files the marker any more.

**Removed:**
- `ControlDatabase.openRevocationLedger`, `revocationLedgerFiled`, `REVOCATION_LEDGER_CONFLICT`, `isRevocationLedgerConflict`.
- `SeedBootstrapService.openRevocationLedger`.
- `CadreNode.openRevocationLedgerIfDue`, the `revocationLedgerOpened` flag (and its reset in `stop()`), and the filing step plus its accepted-tradeoff NOTE in `runReconcileControlCohort`.
- The `RevocationLedgerOpenResult` type.
- `execTombstone` now takes only `RevokedRowRef` (the marker was its only other caller).

**Kept, and re-documented:**
- `REVOCATION_LEDGER_MARKER` (no longer exported: nothing outside `control-database.ts` imports it). Its doc says older parties may hold the row and nothing files it now.
- `queryRevocations` still skips the marker, so the reap and re-issue sweeps never see a row whose `TableName` is not a guarded table.
- The `RowIsGone` branch that admits the marker. Both schema files get comment-only edits (the schema hash strips comments, so `CONTROL_SCHEMA_VERSION` stays 3; `control-schema-drift` and `control-schema-versions` pass). The branch now carries the tripwire `-- NOTE: drop this branch, REVOCATION_LEDGER_MARKER and the readers' skip together with the next CONTROL_SCHEMA_VERSION change that already needs a migration.` The v3 fixture (`test/fixtures/control-schema/v3.qsql`) was left as is, because a shipped version's fixture is not edited.

**Comments rewritten to the current fact**: `readRevocationRowsOrNone` (why the block can be missing: a joining machine has not read it yet, or an older party never wrote it), `syncOwnerAnchor`'s cost NOTE, `link-budget.ts`'s "slow case is bring-up" bullet, `readMembershipRows`' plain-SQL list, the `revocationTombstoneMessage` and `reapRevokedRows` comments, `RevocationRow`'s doc, and the `control-cohort-edge-carries-data` scenario comment, which claimed that B never holds the `Revocation` block because "an owner files its ledger marker only on a connected reconcile pass". It is now conditional: whether B holds the block at the sever depends on whether B read it from A first. The scenario's tolerance logic is unchanged.

**Docs:** `docs/architecture.md`'s `Revocation` row now says the table has a collection from genesis, an older party may hold a marker that readers skip, and an older party that never filed one keeps consulting the cohort on every `Revocation` read until its first tombstone (the no-backwards-compatibility edge case from the plan). The marker is gone from the background-writers list and from the "What stays plain SQL" list. In `docs/cadre-consistency.md`, "revocation-ledger writes" became "revocations".

**Board:** deleted `tickets/backlog/debt-revocation-ledger-marker-live-network-scenario.md`, since the write it would test no longer exists. Removed "ledger-marker" from the background writers listed in `tickets/backlog/feat-owner-key-on-a-hardware-key.md`.

## For the reviewer

- **One full run only** of the degraded-member scenario. Its known intermittent loss of the conflict race (`debt-degraded-member-scenario-sometimes-loses-the-conflict-race`) is unrelated to this change. The removed `beforeAll` step existed to keep the marker write from landing in a stalled window; with no marker write, that hazard is gone and nothing replaces it.
- **Older parties that hold a marker**: `queryRevocations` keeps skipping it, and `queryRevokedStamps` and the guarded tables' `NotRevoked` checks filter on their own `TableName`, so they never matched it. I checked this by reading the code, not with a test (the plan deliberately deleted the schema-rule spec).
- **Older parties that never filed a marker** now never get a `Revocation` collection until their first removal. The plan accepted this, and the docs say it.
- `REVOCATION_LEDGER_MARKER.rowKey` / `.stampId` are no longer read in TypeScript (only `.tableName` is). They are kept so the constant states the exact triple that `RowIsGone` admits.
- Historical mentions left alone on purpose: `tickets/backlog/debt-cadre-node-single-file-size.md` (a dated line-count note) and `tickets/blocked/forked-control-collection-sync-livelocks.md` (a dated failure analysis).
