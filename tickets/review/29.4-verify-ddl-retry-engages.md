# Verify the schema-init retry engages — what was and was not established

## The short answer

**The retry wrapper is live on the schema-init path. Its success path is not proven.**

Two separate claims, and the evidence for them is very different in strength:

- *Wired in* — **proven against a real three-process cluster.** Direct log capture, below.
- *Absorbs a transient cohort failure* — **still unproven.** The failure class it targets
  did not occur once in twelve runs of the scenario, so it never had the chance.

## What was proven, and how

A debug line was added at the point where the retry loop DECLINES to retry
(`retryControlWrite`'s non-retriable branch in `control-write-retry.ts`). That branch
previously threw with no logging at all, which is why this question was unanswerable
from a log: silence meant either "the classifier vetoed it" or "the retry was never
wired into this path", and nothing distinguished them.

With it, run 7 of the `provider-seed-accepted` scenario produced this from a real
provider-started `cadre-cli` child (`DEBUG='sereus:cadre:control-db'`):

```
sereus:cadre:control-db Control write failed non-transiently on attempt 1/3, not retried:
  QuereusError: Failed to execute DDL: create table CadreControl.Revocation (...)
Error: Module 'optimystic' create failed for table 'Revocation': Failed to initialize
  Optimystic table: Missing block (TlKv1kj-EUR5Zz4W_yhL-3BFypGQCrLrikFgcsfdGE0)
```

`attempt 1/3` is the proof. `loadSchema`'s `db.exec(CONTROL_SCHEMA)` really does run
inside `lockedWithRetry` in the shipped binary — this is no longer an inference from a
stubbed unit test — and the classifier really did run and decline. It declined
**correctly**: `Missing block` is the durable convergence fault, which a retry cannot
heal.

## What could NOT be established — read this before trusting the fix

**The bracketed-token question the ticket was written to settle is still open.**

The concern was that `isRetriableControlWriteFailure` vetoes any failure whose chain
contains `[blocks:` (the token Optimystic's *commit* phase uses), so if a real joining
node's failure carries that token, the retry silently never engages. Settling it needed a
captured failure. **No capture was obtained: the target failure class never occurred.**

Across **twelve runs** of `provider-seed-accepted.integration.ts` (six before HEAD's
`assumedClusterSize=2` cluster-policy fix, six after), grepping full child `node.log`
output:

- `Some peers did not complete:` — **0 occurrences**
- `Failed to get super-majority:` — **0 occurrences**

This is a real absence, not a logging gap: the same logs carry 394 lines per run from
`optimystic:db-core:network-transactor`, so the transactor was verbose and alive
throughout and simply never raised the aggregate.

The best available evidence remains circumstantial, and should be labelled as such:
every real transactor aggregate ever recorded in this repo's ticket history carries
`[block:`, and one of them
(`tickets/complete/0-control-db-convergence-optimystic-p2p.md`) is stack-attributed to
`NetworkTransactor.pend` with a `ClusterCoordinator.executeTransaction` cause — the same
coordinator function that raises the super-majority shortfall. No `[blocks:` aggregate
has ever been captured in this project. That corroborates the static read but does not
prove it, and the ticket was explicit that a static read is not evidence.

Per the ticket's instruction, `reportsIndeterminateCommit` was **not** touched.

## Both error faces, honestly reported

Run-by-run at HEAD (6 runs; runs 1–3 and 7 failing, 4–5 green, 6 failing differently):

| Face | Runs | Verdict |
|---|---|---|
| `Missing block` on `Revocation` during DDL init | 1, 2, 3, 7 | Durable convergence fault; correctly not retried |
| Fully green, all 5 steps | 4, 5 | First green runs ever recorded for this scenario |
| Owner-side header-absent + step-4 assertion, no DDL failure | 6 | Nodes started fine; failure is owner-side |

The `Missing block` face is the one the ticket predicted, and it is the ONLY DDL death
observed at HEAD. The super-majority face from the predecessor ticket did not recur.

The scenario did **not** become unconditionally green — as the ticket predicted — but it
is no longer unconditionally red either.

## Changes made

- `control-write-retry.ts` — one debug line on the decline branch (the observability fix
  above). Behaviour is otherwise unchanged: same classification, same control flow.
- `control-write-retry.spec.ts` — the coverage previously drove the schema-init cases
  from a **bare** super-majority sentence, which is softer than reality: on the wire that
  sentence arrives *inline* as one batch's `cause=` inside a transactor aggregate, and it
  is the aggregate's bracket token that decides retriability. Added both real shapes
  (`SUPER_MAJORITY_IN_PEND_AGGREGATE`, `SUPER_MAJORITY_IN_COMMIT_AGGREGATE`) and a case
  pinning that the identical sentence is retried in the pend form and vetoed in the
  commit form. The `SUPER_MAJORITY_THIRD_NODE_JOIN` comment now states plainly that it
  is a reconstruction with the deciding segment elided, rather than implying a capture.

## For the reviewer — where to push

- **The weakest point is the unproven success path.** The retry has never been observed
  actually absorbing a failure at this call site, in any test, at any time. Every case
  proving it works drives a stub. Judge whether that is acceptable to ship or whether it
  warrants a fault-injection test that forces a retriable failure through `loadSchema`
  against a real cluster.
- **The new spec constants are still reconstructions**, assembled from the transactor's
  format strings — the same category of evidence the ticket criticised, just applied to
  the aggregate wrapper too. They are labelled as such. They are not captures and should
  not be cited as though they were.
- The decline log fires on **every** non-retriable control-write failure, constraint
  failures included, so a debug-enabled run of a constraint-heavy suite will be noisier
  than before. Debug-namespaced, off by default.
- Twelve runs is a decent but not enormous sample for an intermittent failure. "Zero
  occurrences" is a strong signal, not a proof of impossibility.

## Tripwires parked

- **Debug namespace correction.** The prior run on this ticket used
  `DEBUG=optimystic:db-p2p:cluster-coordinator`, which matches nothing — the coordinator
  registers itself as `optimystic:db-p2p:cluster` (`createLogger('cluster')` in
  `db-p2p/src/repo/cluster-coordinator.ts`). Its `cluster-tx:supermajority-failed` line
  was therefore disabled for the first six runs. Corrected in the runs reported here.
  Recorded here rather than in code because it concerns another repo's namespace, and
  anyone debugging this path will read this handoff first.
- The decline log's cost is one `debug()` call on a failure path, i.e. nothing while
  disabled. Noted at the call site in `control-write-retry.ts`.
