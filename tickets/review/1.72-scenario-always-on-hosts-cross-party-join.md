# Scenario: the always-on machine hosts a strand its phone joined from another party

## What was built

One new integration scenario, `strand-always-on-replica-hosts-cross-party-join.integration.ts`, covering the end-to-end path `party-wide-joined-strands` built: a cross-party join is published party-wide, a storage replica host launches from that record, and leaving removes it party-wide.

Topology, as the ticket specified:

- **HOST party:** one machine, sole owner, storage profile. Founds an open strand, then publishes a formation invitation bound to it (the `strand-formation-cross-party-seed` setup).
- **JOINER party:** a phone (`profile: 'transaction'`, genesis owner) and an always-on machine (`profile: 'storage'`, `hostUnclaimedStrands: true`) the phone enrolls through `authorizePeer` + `createSeed`/`applySeed`. The always-on machine never calls `formStrand` or `addStrand`.

Steps and what each asserts:

1. The phone redeems the invitation (`formStrand`), claims the strand (`addStrand` with the app config), connects to the host's strand node from the formation-carried addresses, and writes 5 rows. At that point the test reads that the phone's joined-strand store holds the join, the phone's control database has no `JoinedStrand` row, and the always-on machine runs no instance.
2. After asserting that the phone holds a control connection to the always-on machine, the test drives one reconcile pass on the phone. It then asserts the `JoinedStrand` row (exact `StrandRow` shape) and an empty local store (the record was drained).
3. The test waits for the always-on watcher to launch the replica (instance with a libp2p node, no `sAppInfo`) and for the phone's strand node to connect to the replica's (from the strand-addr RPC seed; there is no test-side dial). The phone then writes 5 more rows, and the test checks block coverage of the phone's strand store against the always-on raw store (`awaitBlockCoverage`, floor of 4 blocks; 9 to 11 were measured).
4. The test reads the row's stamp, then calls `forgetJoinedStrand` on the phone. It asserts the row is gone, exactly one `Revocation` tombstone for `('JoinedStrand', strandId)` carries that stamp, and the phone stopped the strand. It then waits for the always-on instance to disappear and asserts the host's instance is still `active`.

Two choices worth a reviewer's look:

- **The phone's reconcile timer is parked** (`reconcileMs: 600_000`), and `initializeStrandSolicitation()` is called and settled before `formStrand`. The reason: `formStrand` would register the formation handler itself. `registrar.handle` merges the self peer's protocols, and the peer store dispatches `self:peer:update`, which `CadreNode` wires to a reconcile pass (confirmed in `node_modules/libp2p/dist/src/registrar.js` and `@libp2p/peer-store`). That pass could publish the join before step 1 reads. This keeps step 1's "before publication" a measured state.
- **`freshReconcilePass` calls `reconcileControlCohort()` twice.** The call is single-flight and hands back a pass already in flight, and that pass may have run its publish step before the join was recorded. The second call is a pass that started afterwards. This is not a retry loop.

The phone's joined-strand store is injected (`KeyStoreJoinedStrandStore` over `InMemoryKeyStore`, the production store shape) so step 2 can read it; this also avoids the in-memory store's restart warning.

## Validation

- Isolated runs: `yarn workspace @serfab/integration-tests exec vitest run strand-always-on-replica-hosts-cross-party-join`. 4 of 4 passed (a first run plus the three requested): test time 8.8 s, 7.6 s, 6.6 s, 7.6 s; wall time 22 s, 16 s, 15 s, 16 s.
- Mutation check (a scratch copy, deleted afterwards): replacing `forgetJoinedStrand` with a local `stopStrand` makes step 4's wait time out after 30 s with "always-on machine's watcher sees the party-wide row gone and stops its replica". Stopping the phone's strand alone does not take the replica down, so step 4 depends on the party-wide removal.
- `yarn lint` and `yarn typecheck`: both exit 0.
- `@serfab/cadre-core` had to be rebuilt first (`yarn workspace @serfab/cadre-core build`), because the stale-build guard reported its `dist` older than the review commit of `party-wide-joined-strands`. This is an in-repo package, not a sibling repository.
- The full integration suite was not run, only this file.

## Tests added

- `strand-always-on-replica-hosts-cross-party-join.integration.ts` (one `it`). It checks that a cross-party join reaches the always-on machine only through the party-wide `JoinedStrand` row: publication by the owner phone's connected reconcile pass, a replica launched from that row holding every block the phone holds, and the replica removed when the phone leaves party-wide while the other party's strand keeps running. Neither half has a node-level unit test, by design (see `party-wide-joined-strands`).

## Known gaps (not covered here, by the ticket's scope)

- **Closed strand.** Only an open strand runs, as the ticket chose. The replica resolving the `StrandPartyKey` row `formStrand` seated, and seating its own `MemberPeer`, is argued in the file header, not exercised.
- **Non-owner joiner.** A phone that is not an enrolled owner keeps its join machine-local, so no replica launches. No scenario shows that.
- **Sibling device discovery.** The party's other devices getting `strand:discovered` from the party-wide row is not asserted. The always-on machine is the only other machine, and it hosts the strand rather than announcing it for a claim.
- **Restart.** The always-on machine re-hosting the joined strand after its own restart is not covered.
- **Links.** All links are direct loopback. The relay path is not covered.

## Findings for the reviewer

No product defects surfaced. The always-on machine reached the phone's strand node through the strand-addr RPC on every run, so no hand-dial was needed.
