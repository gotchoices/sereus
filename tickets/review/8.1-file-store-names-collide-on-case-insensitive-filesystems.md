# File names built from ids no longer depend on letter case

`encodeFileSafeComponent` (`packages/cadre-core/src/fs-atomic.ts`) turns an id into a file name. It percent-encoded but kept letter case, so on NTFS / APFS two ids differing only in case shared one file. Its two users: `FileKeyStore` (slot `<dir>/<encoded key id>.key`; the realistic victim is `cadre/joined-strand/<base64url party id>/<strand id>`) and `FileDurableSlot` (`<dir>/<name>.<encoded party id>.json`, behind the trusted-owner, bootstrap-peer, enrolled-machine and strand-peer-book file stores).

## What changed

- **Encoder:** also escapes `A`–`Z` as `%41`–`%5A`. The regex matches existing `%XX` escapes first and passes them through, so the uppercase hex digits inside `encodeURIComponent`'s escapes are not re-escaped. Output is `[a-z0-9_-]` plus `%XX` with uppercase hex; ids with no capital letters encode byte-for-byte as before (node identity slot `cadre%2Fidentity.key` included). Doc comment states the rule and why it is collision-free ignoring case.
- **`decodeKeyId`:** after decoding, re-encodes and skips (with a log line) any `.key` file whose name is not the canonical encoding — so `list()` never names an id that `get()` then reports absent (e.g. an old-format `...YWFa...key` left from before the upgrade).
- **Docs:** one sentence added to the `FileKeyStore` bullet in `docs/architecture.md` naming the encoding and why.
- **Release note:** new paragraph under the existing "storage names changed" heading in `.release-notes.pending.md` (sibling ticket's entry): joined-strand records are effectively lost on upgrade (base64url party ids nearly always contain capitals) until re-joined; per-party node-state files move only for party ids with capitals; old files are ignored and can be deleted.

## Tests (all in `packages/cadre-core/test/key-store.spec.ts`)

- "round-trips awkward keyIds (… case) without collision" — two new rows, `cadre/joined-strand/YWFA/strand-1` and `…/YWFa/strand-1`. On Windows/macOS this is the bug's reproduction through the real filesystem; on Linux it passes either way (hence the next test).
- "encodes ids without literal uppercase letters, leaving lowercase-only ids unchanged" — platform-independent pin: mixed-case input's output with escapes removed matches `/^[a-z0-9_-]*$/` and round-trips; `cadre/identity` still encodes to `cadre%2Fidentity` (the identity file must not move).
- "list() skips a decodable .key file whose name is not the canonical encoding" — old-format joined-strand file is not listed.

Verified on this Windows machine: with the encoder's `A-Z` temporarily removed, all three fail; with it, they pass. `yarn workspace @serfab/cadre-core test` (144 files, 2346 passed, 1 skipped — the POSIX-only mode test), `yarn workspace @serfab/cadre-core build` and `yarn lint` all clean.

## Known gaps / things for the reviewer to weigh

- **Leftover old files can still be hit by a direct lookup on a case-insensitive filesystem.** An old-format file such as `trusted-owners.Alice.json` or `cadre%2Fjoined-strand%2FYWFa%2F….key` has the same case-folded name as the *new* name of an all-lowercase id (`alice`, `…ywfa…`). A `get`/`load` for that lowercase id would open the old file. For `FileDurableSlot` the envelope's party-id check fails closed (cold start, then overwritten). For `FileKeyStore` it would need two parties sharing one key directory whose base64url segments fold to the same lowercase string, plus a direct `get` rather than the list-then-get the joined-strand store does. I judged this contrived and did not add a migration or a note in code; the release note says the old files can be deleted.
- No migration of old-format files — the ticket chose to leave them in place and ignored.
- `docs/cadre-host.md` line ~197 still writes the file names informally as `trusted-owners.<partyId>.json`; left as is (accurate for lowercase party ids, which is what cadre-host uses).
- Other packages: integration-test helpers find these files by prefix (`readNodeLocalStore` in `packages/integration-tests/src/harness/child-node-fixtures.ts`), so they are unaffected; integration tests were not run.
