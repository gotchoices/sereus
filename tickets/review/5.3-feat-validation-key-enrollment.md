# Approver-key enrollment — review handoff

## What the feature is, in plain terms

An invitation can carry a URL that an outside approver has to sign off on before the
invitation can be redeemed. The party decides which approvers it trusts by enrolling their
public keys. The database has always been able to store those keys; nothing above it could
add, list, or remove one, so a party could not actually use approval-gated invitations.

This ticket added the missing read query, three node-level methods, and a command.

## What landed

**`ControlDatabase.queryValidationKeys(): Promise<string[]>`** — reads `Key` from
`CadreControl.ValidationKey`, sorted in TypeScript (no `order by` appears anywhere else in
this package, so SQL sorting was deliberately avoided as an unproven engine dependency).

**`CadreNode`** — three methods placed directly after `publishFormationInvite`:

- `enrollValidationKey(key)` — owner-signed insert.
- `removeValidationKey(key)` — owner-signed delete plus the tombstone the DB writer already
  handles.
- `listValidationKeys()` — read-only; needs a started node but no signing key.

Two module-level helpers were extracted while doing this:
`signMessageWith(privateKeyB64)` (the sign callback the `ControlDatabase` writers expect)
and `requireNonBlank(value, label)` (rejects empty/whitespace input before it can reach the
database and fail a signature CHECK as an opaque constraint error). A private
`requireOwnerSigningKey(action)` produces the not-started / no-signing-key errors in the same
two-part shape `publishStrand` uses, naming owner genesis as the fix.

**`cadre validation-key add|remove|list`** in `packages/cadre-cli/src/commands/validation-key.ts`,
registered in `bin/cadre.ts` and re-exported from `src/index.ts`. Same `-c/--config`,
`--json`, `-d/--debug` options as the other one-shot commands.

**New shared helper `packages/cadre-cli/src/commands/node-session.ts`** — `resolveStorageConfig`
was already copy-pasted in `start.ts` and `strands.ts`, and this command would have been the
third copy. It now holds `resolveStorageConfig`, `oneShotNodeConfig`, and `withConnectedNode`
(resolve config → construct node → wait for `control:connected` with a bounded timeout → act
→ stop, with the event handler registered *before* `start()` and teardown in a `finally`).
`start.ts` imports `resolveStorageConfig` from it; `strands.ts` was converted to
`withConnectedNode` wholesale. **This refactor is the main thing to review that the ticket
did not ask for** — see "Judgement calls" below.

## Judgement calls a reviewer should second-guess

- **Refactoring `strands.ts` onto the new helper.** The ticket said "follow `strands.ts`
  exactly"; following it exactly meant a third copy of `resolveStorageConfig` and a second
  copy of the connect/act/stop dance, against the repo's DRY rule. `strands.ts` behaviour is
  intended to be identical, but its error/exit paths moved: the timeout is now a rejected
  promise caught by the existing `catch` (previously an inline `console.error` +
  `process.exit(1)` inside the timer), and `process.exit(0)` moved out of the
  `control:connected` handler to after `withConnectedNode` resolves. **Unverified at runtime**
  (see Testing).
- **"Already enrolled" is detected by a read, not by matching the constraint error.** The
  ticket suggested reporting the failed insert as "already enrolled"; matching Quereus
  constraint-error text seemed brittle, so `add` calls `listValidationKeys()` first. A
  concurrent enrollment between the read and the write would still surface the raw constraint
  error. For a human-driven CLI that seemed the right trade; disagree if you like.
- **`requireNonBlank` trims and writes the trimmed value.** So ` KEY ` enrolls as `KEY`. It
  does *not* validate that the key is well-formed base64url or the right length — a malformed
  non-empty key still reaches the database and fails the signature CHECK. The ticket only
  asked for empty/whitespace rejection; stricter validation is a live question.
- **`removeValidationKey` on the node does not warn about removing the last key** — the
  warning lives in the CLI, which reads the list first so it can distinguish "not enrolled,
  nothing to do" from "removed, and that was the last one". A programmatic caller gets no
  warning. Reasonable, but it is a policy decision sitting in the wrong layer if other
  front-ends appear.

### What the new spec claims to cover

`packages/cadre-core/test/validation-key-enrollment.spec.ts`, on a real self-owner
`CadreNode` (the `publish-formation-invite.spec.ts` harness):

- enroll → list shows it → remove → list is empty
- several keys list back sorted
- removal writes a `Revocation` tombstone naming the row's stamp, and the stamp shows up in
  `queryRevokedStamps('ValidationKey')`
- re-enrolling the same key after removal succeeds on a *fresh* stamp; the old stamp stays
  retired
- removing an absent key is a silent no-op (no throw, no tombstone)
- **removal is not retroactive** — enrolls an approver, owner-provisions a host strand, mints
  a validation-gated invite, records a real approved redemption signed over
  `formationVouchMessage`, then removes the approver and asserts the usage row is untouched
  and still names the removed key. This is the test that stops a later reader from "fixing"
  removal into a retroactive revocation.
- blank / whitespace-only key rejected before any write, for both enroll and remove
- enroll on a node whose key is not an enrolled `OwnerKey` is rejected and lands nothing
- enroll / remove / list on an unstarted node throw the named errors

The not-retroactive test reaches into the node's private `identityKey` to get the owner
keypair for the direct `insertStrand` call. Slightly grubby; if it bothers you, the
alternative is exposing the owner public key on `CadreNode`.

### Coverage gaps worth flagging

- **No test for the CLI at all.** `packages/cadre-cli` has no spec for any command
  (`vitest run --passWithNoTests`), so `validation-key.ts` — argument parsing, the
  already-enrolled / not-enrolled / last-key branches, `--json` shapes — is entirely
  unexercised. Same is true of the pre-existing commands, so this is not a regression, but
  the new command is where the operator-facing wording lives.
- **No test for the `strands.ts` refactor.** Its behaviour is asserted only by reading.
- **No test that a *future* redemption is refused after removal** — the spec pins the
  not-retroactive half but not its complement.
- The convergence behaviour (a key enrolled on one node is invisible to a sibling until
  control replication catches up) is recorded as a `NOTE:` in the `enrollValidationKey` doc
  comment per the ticket, and is not tested here.

## Manual validation

```
cadre validation-key list                       # "No approver keys enrolled."
cadre validation-key add <base64url-pubkey>     # "✓ Approver key enrolled: …"
cadre validation-key add <same key>             # "• Approver key already enrolled: …"
cadre validation-key list --json                # ["<key>"]
cadre validation-key remove <other key>         # "• …not enrolled — nothing to do"
cadre validation-key remove <key>               # "✓ …removed" + last-key warning on stderr
cadre validation-key add ""                     # non-zero exit, "…is required" on stderr
cadre strands                                   # regression check on the refactored command
```

All of these need a config file pointing at a party whose owner key is this node's identity.
