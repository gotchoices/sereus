# Every machine publishes its strand peer id, and binds its siblings

Second ticket of the key-rotation chain (`control-schema-strand-peer-and-pending-party-key` → this → `machine-removal-rotates-party-member-key` → `scenario-machine-removal-rotates-party-key`). The running node now writes `StrandPeer` rows, and the per-strand membership reconciler binds the party's other machines under the party's current key and clears a removed machine's binding, so the party's bindings in a closed strand no longer depend on each machine writing its own.

## What was built

- **The row write.** `CadreNode.publishStrandPeer(strandId, strandPeerId)` writes this machine's `StrandPeer` row through `ControlDatabase.insertStrandPeer`, signed by the identity key (`ed25519MessageSigner`, a new helper in `ed25519-key.ts` that `softwareOwnerSigner` now shares). Called in the background by `StrandInstanceManager.buildStrandRuntime` right after `createLibp2pNode`, for closed strands only, launch and resume alike, party key or not. Skipped while `controlWriteCouldFork`; a deferral or a refusal (the machine's own `CadrePeer` row not here yet) lands in `deferredStrandPeerWrites`, re-attempted by the growth drain (`runDrainControlReplication`, after the self rows) and by every reconciler pass. A row found present is remembered per session (`strandPeerRowsHeld`), so the per-pass re-attempt is a `Set` lookup. An ephemeral identity writes nothing.
- **The reconciler's new steps.** `StrandMembershipReconcilerDeps.partyPeers` is one strand-scoped seam (`PartyStrandPeerSource`: `publishOwn`, `read`, `isRotationPending`) rather than the three separate deps the ticket sketched, mirroring `PendingMembershipInviteSource`. After the own binding: bind every `live` id with no binding under the current key; clear every `removed` id that has one, through the self branch of `removeMemberPeer`, only when `isRotationPending()` resolves `false` (a rejection is "may be pending": clear nothing); re-attempt the own row. A pass that wrote is not done; the done state now also needs every known sibling bound. A `read()` that rejects keeps the loop live on the flat poll interval (`waitForPoll`); a write that fails is retried on the ladder, each sibling's write contained on its own.
- **Who is live, who is removed.** `CadreNode.readPartyStrandPeers` reads `queryStrandPeers` plus a new `ControlDatabase.queryMachineRowsFresh()` (the `CadrePeer` rows and every tombstone through `MembershipView.readThrough`, not the views; the chain tables stay on the views) and projects them with the pure `partitionPartyStrandPeers`: live = a `CadrePeer` row that passes the membership predicate (`CadreMachine.trusted`, false for self); removed = a `CadrePeer` tombstone whose `RowKey` is the peer id and no live row; anything else ignored. `removed` never contains an id in `live`, which is where the "a removed machine stated a sibling's id" case is closed.
- **Wakes.** `CadreNode.start()` takes one `watchTables` subscription on `CadreControl.StrandPeer`, `CadrePeer`, `Revocation` → `StrandInstanceManager.notifyPartyPeersChanged()`, which re-arms every armed reconciler (table events carry no row keys, so the no-argument form replaces the ticket's `notifyPartyPeersChanged(strandId)`). `rearm` takes a `cause` for the log. `StrandRevocationEnforcer.onSelfRestored` fires on the exit edge of `trackSelfRevoked` (never on a first clean pass) and the instance manager wires it to `rearm`.
- **Docs.** `docs/strands.md` gains "Binding the party's machines" under Closed-Strand Member Key Handling (the row, who binds whom, the pending gate, the heal, the wakes), a pointer from the reconciler bullet, the device-record bullet under Removing Members, and the false-alarm sentence on the `strand:revoked` bullet. `docs/architecture.md`: the `StrandPeer` schema row, the `registerMemberPeer` bullet, and a new consumer in Table change subscriptions.

## Decisions a reviewer should check

- **A failed `read()` keeps the loop live** (flat poll interval, 30 s by default) rather than latching done and relying on the watch. On a party founded before schema v4 whose `StrandPeer` collection nobody has written, with the other machines offline, that is one failing control read per closed strand per 30 s (`backlog/feat-strand-tables-added-by-a-later-schema-get-their-collection`). The alternative, latching done, would leave siblings unbound until the next control change or resume. Documented at `reconcileSiblings`.
- **Fresh membership read.** `queryMachineRowsFresh` reads `CadrePeer` and `Revocation` through storage on every pass. The chain tables are served from the views: a missing chain row makes a machine untrusted, which the projection ignores rather than acts on.
- **Cost.** `CadrePeer` changes on every machine's self-record heartbeat (7.5 min), so every closed strand's loop runs one confirming pass per heartbeat of any party machine: two strand scans, one `StrandPeer` read, two fresh control reads. `NOTE:` at `attempt` and at the watch in `CadreNode.start()`; the remedy named there is reading `StrandPeer` once per control change.
- **A self-revoked stop re-armed by a heartbeat** re-stops at once (step 1), one `isSelfRevoked` call per heartbeat. The blocked re-join report latch is untouched: a loop with an invitation staged never stops, so a re-arm only kicks it.
- **`removeMemberPeer`'s self branch** signs over the row's own `MemberKey`, which is the party key, so it clears any peer id of the party's; confirmed by reading `ownMemberPeerRemovalStatements` and run by the reconciler test (it clears `removed-machine`, not the node's own id).
- **The deferred-write map outlives `stopStrand`**: a stopped strand's deferred row is still written on growth. The row states a derived, stable id, so it is true whether or not the strand runs here; left as is.
