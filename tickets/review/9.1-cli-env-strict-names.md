# Strict `CADRE_*` environment variables for cadre-cli — review handoff

## What changed

`config/env.ts` (new) is the one registry of every `CADRE_*` name the node process may see, in four groups:

- **Config overrides**: `ENV_MAPPINGS` (moved from `types.ts`, still exported from the package), each entry now `{ path, kind }`. `kind` is one of `string | list | boolean | number | strandFilter | json` and picks a parser from a `PARSERS` table; the old guess-from-the-name rules (`_ADDRS` suffix → list, `_ENABLED`/`_RELAY` → boolean) are gone.
  - `boolean`: `true`/`false`/`1`/`0`, case-insensitive, trimmed. Anything else throws `Invalid CADRE_X "yes": expected true, false, 1 or 0` (before: silently `false`).
  - `number`: `Number(trimmed)`, must be finite, else throws naming the variable. The validator then applies the field's own range/integer rule, attributed to the variable.
  - `json` (only `CADRE_PUSH`): a JSON object. Messages no longer echo the parsed value (it carries private keys), and lost the `{"fcm":…}` example.
  - Three new mappings: `CADRE_STORAGE_QUOTA → storage.quotaBytes` (number), `CADRE_LATENCY_HINT → hibernation.defaultLatencyHint` (string), `CADRE_STRAND_WATCH_INTERVAL → strandWatchInterval` (number). Before, only `entrypoint.sh` read them.
- **Read by commands**: `COMMAND_ENV` (`CADRE_HEALTH_PORT`, `_METRICS_PORT`, `_ADMIN_PORT`, `_OWNER_KEYS`, `_SEED_TOKEN`, `_STARTUP_TOKEN`). Read sites in `start.ts`, `status.ts` and `enroll-add.ts` now call `commandEnv('CADRE_…', env?)`, whose parameter type is that list, so reading an unregistered name is a compile error.
- **Read by launchers only**: `CADRE_CONFIG` (systemd unit), `CADRE_CONFIG_FILE`, `CADRE_DEBUG` (Docker entrypoint).
- **Retired**: `CADRE_IDENTITY_PROTOBUF` with its old message. `rejectRetiredIdentityEnv` is deleted.

`checkEnvNames(env)` runs first thing in `applyEnvironmentOverrides`, so `start`, `status` and the one-shot strand commands all get it. It skips names starting `CADRE_HOST_` and set-but-blank values (compose's `${X:-}`), collects every bad name, and throws once: `Unknown environment variable CADRE_LISTEN_ADDR (did you mean CADRE_LISTEN_ADDRS?)`, one line per name.

Other edits:
- `nearestKey` moved out of `schema.ts` into `config/nearest-key.ts`, shared by the validator and the env check. **This differs from the ticket**, which asked to export it from `schema.ts`: `schema.ts` imports `ENV_MAPPINGS` from `env.ts`, so `env.ts` importing `schema.ts` would have created an import cycle.
- **Also differs from the ticket:** direct reads go through a typed reader (`commandEnv`), not per-variable named constants. With named constants, a new constant could still be left out of the registry list. Here the list is the type, so that can't happen.
- `docker/env.example`: removed the unread `CADRE_ENROLLMENT_TOKEN`, `CADRE_PROVIDER_API`, `CADRE_PROVIDER_API_KEY` block. Also added a header line saying unknown `CADRE_*` names fail start (compose's `env_file: .env` passes the whole file into the container).
- README env table: added the three new mappings plus `CADRE_HEALTH_PORT`/`CADRE_METRICS_PORT` (read but never documented), noted strict boolean spellings, and added a paragraph on unknown-name rejection, launcher-only names, the `CADRE_HOST_` skip and the retired name.
- `docs/architecture.md`: the seed-delivery table listed a `CADRE_SEED` variable that nothing reads, and setting it would now fail start. Replaced it with the real mechanism, `cadre start --seed <encoded>`, in the table and in the pseudo-code sample.
- Integration harness `ensureConfigFile`: comment only. The two keys now have variables, but neither the image ENV nor the provider sets them, so the file still carries the entrypoint's defaults. File content unchanged; no integration scenario was run.

## Tests

- `test/env-names.spec.ts` (new):
  - *rejects every unknown variable in one error, suggesting the nearest name*: two unknown names are listed in one message with the suggestion. `CADRE_HOST_DATA_DIR` and a blank typo are skipped.
  - *recognises every CADRE_\* variable the repo's launchers set*: reads `docker/Dockerfile`, `docker-compose.yml`, `entrypoint.sh`, `env.example`, `contrib/cadre-node.service`, `contrib/cadre-install.sh` and cadre-provider's `src/service/container-env.ts`, extracts `\bCADRE_[A-Z0-9_]+\b`, and requires `checkEnvNames` to accept all of them. There is also a `> 20` names guard so a moved file can't make it pass vacuously. It is stricter than the ticket: a *retired* name in a launcher file fails it too, since that launcher would produce a node that refuses to start. Before this change it would have failed on `CADRE_STORAGE_QUOTA`/`CADRE_LATENCY_HINT`/`CADRE_STRAND_WATCH_INTERVAL` and the three `env.example` names.
  - *rejects CADRE_ENABLE_RELAY=yes / CADRE_STORAGE_QUOTA=10G rather than guessing* (`it.each`): strict boolean and number parsing.
- `test/identity-key.spec.ts`: the `CADRE_KEY_FILE`, `CADRE_IDENTITY_PROTOBUF` and `CADRE_NODE_STATE_DIR` tests now pass `env` to `resolveConfig` instead of mutating `process.env`. The matching `afterEach` deletes are gone. The retired-variable test now passes through the general mechanism. No cadre-cli test writes `process.env` any more.
- cadre-host's child env block (`host-process-orchestrator.ts`) was checked by inspection, as the ticket specified. It sets only registered names.

Validation: `yarn workspace @serfab/cadre-cli typecheck` (covers `test/`), `yarn lint`, `yarn workspace @serfab/cadre-cli build`, `yarn workspace @serfab/cadre-cli test` → 19 files, 254 tests passed.

## Known gaps / things to look at

- **Stray exports now fail start and tests.** A developer shell or CI runner with a stray `CADRE_*` export now fails `cadre start` and every cadre-cli test that calls `resolveConfig`/`loadValidatedConfig` without an explicit `env`. This is the decided behaviour; the error names the variable.
- **Windows case-insensitivity.** On Windows, `process.env` lookups ignore case, but the name check matches the `CADRE_` prefix case-sensitively. A lower-case `cadre_listen_addr` is therefore neither checked nor applied, while a lower-case *registered* name (`cadre_party_id`) is still applied. This is not new behaviour and not fixed here.
- **Parse errors stop at the first bad value.** Value parse errors throw on the first bad variable and are not merged with the name errors or with the validator's list. `CADRE_PUSH` and `CADRE_STRAND_FILTER` already behaved this way.
- **`number` accepts every `Number()` form.** That includes hex (`0x10`) and exponents (`1e3`), as the ticket specified. The validator still enforces integer/positive rules afterwards.
- **Error attributed to the file, not the variable.** `CADRE_STORAGE_QUOTA` (like the existing `CADRE_STORAGE_PATH`) on a config with no `storage.type` gives `storage.type is required (or set CADRE_STORAGE_TYPE)`, attributed to the config file. Harmless where it is used today (the image sets `CADRE_STORAGE_TYPE=file`).
- **`--identity-file` write unchanged.** `start.ts` still writes `process.env.CADRE_KEY_FILE` directly for `--identity-file`. That is a registered override name; the write is not routed through a typed helper.
