# Review: strand party member key (founder half of the identity/read-secret split)

Implements the first ticket of the four-ticket `strand-party-member-key` → `strand-formation-membership-invite` → `strand-node-binds-member-peer` → `strand-party-removal-via-formation-e2e` chain. A closed strand's founding `Strand.Member`/`Strand.Manager` identity no longer derives from the strand-wide `Strand.MemberPrivateKey` (which formation hands to every joining party — gotchoices/sereus#4); it derives from a new per-party key.

## What was built

**New control table `CadreControl.StrandPartyKey`** (`control-schema.ts`, mirrored byte-equivalent in `schemas/control.qsql`; drift spec green): `Id` (strand id, primary key), `PrivateKey` (this party's ed25519 strand member private key, base64 protobuf — same encoding as `MemberPrivateKey`, decoded by `strandMemberKeyPair`), `StampId` (unique single-use nonce). Constraints follow the ValidationKey idiom: `NotRevoked` / `RevocationRecorded` / `NoUpdate` / owner-signed `AuthorizedInsert` over `digest('CadreControl.StrandPartyKey','add', Id, PrivateKey, StampId)` (PrivateKey deliberately in the digest — a captured approval cannot seat an attacker-chosen identity) / `'remove'`-tagged `AuthorizedDelete` with **no REAP branch** (the key is unrecoverable, same stance as `Strand`). `Revocation.RowIsGone` gained the matching branch; `CONTROL_TABLES` and `RevocableTable` gained the name; `REAPABLE_TABLES` deliberately excludes it.

**ControlDatabase**: `queryStrandPartyKey`, `queryStrandPartyKeyStampId`, `insertStrandPartyKey`, `deleteStrandPartyKey`, and `deleteStrand` was reworked (`deleteStrandAndPartyKey`) to remove the strand's party-key row — its own remove signature, its own `Revocation` tombstone — **in the same transaction** as the `Strand` row, so no crash window orphans an identity and a re-publish always mints fresh. The companion delete runs only when a `Strand` row is actually removed: a party-key row with no `Strand` row is a joiner's identity (next ticket's shape) and only `deleteStrandPartyKey` touches it. The guarded-delete listener fires once per tombstone (two for a closed strand), so the write-while-alone re-issue queue carries both.

**CadreNode**: `publishStrand` of a closed strand mints (insert-if-absent) the party key after the row insert, and heals on its idempotent branch when the stored row is self-founded. `launchStrand` for a closed strand resolves the key — explicit attach-time key, else the `StrandPartyKey` row, else (only when the row's `FounderOwnerKey` is this machine's own owner key) mint-and-persist (the heal for pre-split strands) — and retains it in the launch config, so hibernation wakes rebuild under the same identity. Non-founding machines never mint. New public `ensureStrandPartyKey(strandId, key?)` (mint-or-adopt; throws on a conflicting supplied key; adopts the landed row on a lost concurrent-seat race). `unpublishStrand` documents the party-key removal riding along.

**Bootstrap**: `StrandDatabaseConfig` gained `partyMemberPrivateKey`; `deriveFounderKeyPair` decodes it (loud throw naming `StrandPartyKey` for closed+founder+keyless — the shared `MemberPrivateKey` is NOT accepted as a fallback). `StartStrandConfig` and `StrandConfig` (`addStrand`) gained the same optional field; `foundExistingStrand` takes a lazy key resolver so a joiner-launched closed instance later flipped to founder still gets a key (resolver runs only when the retained config lacks one — the common watcher re-entry stays read-free).

**Docs**: `docs/strands.md` → "Closed-Strand Member Key Handling" rewritten around the two-key split (and the residual-risk paragraph now says a device compromise leaks identity, not just read access). `strand-member-key.ts` doc comments updated.

**Harness**: `joinStrandOn` gained `partyMemberPrivateKey` (minted by default, injectable). It is passed in-memory to the founder's `addStrand` (the hand-built row has no founder provenance to heal against, and `members[0]` need not be an enrolled owner); under `publish:` it is also persisted via `ensureStrandPartyKey` so publish's own mint cannot diverge. Scenarios that need the founding keypair now derive it from the party key (one extra mint + one field per scenario body).

## Known gaps / honest notes for the reviewer

- **The explicit `StrandConfig.partyMemberPrivateKey` is an in-memory seam, not persistence.** A founder that attaches with an explicit key and never publishes has no durable identity row; re-attaching after a restart needs the same explicit key again (the harness and the closed-strand e2e are the intended users — their founding nodes are not enrolled owners, so they cannot write the control row). Production paths (`foundStrand`/`publishStrand` + watcher relaunch) always persist.
- **Heal is gated on row-derived founder-ness only.** An explicit `founder: true` over a row with a null/foreign `FounderOwnerKey` does not mint (deliberate: only one machine may mint, and provenance is the only safe discriminator); such a caller must supply the key or the bootstrap throws naming `StrandPartyKey`.
- **Joiner→founder flip edge**: a closed strand launched as a joiner before its `StrandPartyKey` row replicated, then founded in place, re-reads the row at flip time; if still absent the founding throws loudly rather than seating a wrong identity. Not covered by a dedicated test (the publish-first orders that exist in tests are covered).
- **Storage-op budget moved down, not up**: cold start measured 169 ops/20 blocks (was 172/21), warm 46/22 (was 52/22) — with a ninth table added. Numbers and provenance updated in `control-start-storage-op-budget.spec.ts` (and the `loadSchema` comment); single measurement, the spec's own determinism note applies if it ever flaps.
- **`strandRowMismatches` / `adoptPublishedStrand` contract untouched** — the party key lives outside the `Strand` row; verified no test asserts otherwise.
- The joiner half (persisting a formation-issued party key, and delivering invites against it) is `strand-formation-membership-invite`; `queryStrandPartyKey` / `insertStrandPartyKey` / `deleteStrandPartyKey`, and `deleteStrand`'s rule of leaving a party-key row that has no `Strand` row alone, are the seams it consumes.
