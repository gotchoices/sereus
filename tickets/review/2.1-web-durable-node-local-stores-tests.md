# Tests for the web reference app's node-local durable stores

Vitest tooling for `packages/reference-app-web` landed in a prior session
(`vitest.config.ts`, `package.json` `test`/`dev:test` scripts, the `vitest`
devDependency). This ticket wrote the actual spec on top of that: a `yarn
install` at the repo root to link the new `vitest` devDependency into
`packages/reference-app-web/node_modules` (confirmed present at
`node_modules/.bin/vitest`), then
`packages/reference-app-web/test/node-local-slots.spec.ts`.

## What the new spec covers

**`kvSlot`** (`src/lib/node-local-slots.ts`), against a hand-rolled
`FakeKvHandle` (a `Map` standing in for the real `OptimysticWebDBHandle`'s
`kv` IndexedDB object store):
- save → load round-trip through the backing map (fresh slot instance, same
  map — proves the slot itself holds no state)
- a non-string value already under the key loads `undefined`, not a throw
- a never-written key loads `undefined`
- a failing `handle.get` rejects the `load()` promise rather than resolving
  `undefined` — the property `startCadre` depends on to fail loudly on a
  genuine IndexedDB fault (`cadre-web.ts` ~line 313)

**`PersistentTrustedOwnerStore`** and **`PersistentBootstrapPeerStore`**
(`@serfab/cadre-core`), each over a real `kvSlot` backed by the same fake
handle:
- a value `trust()`/`record()`-ed in one instance is visible in a **second**
  `open()` of the same slot + partyId (the actual persistence round trip)
- a foreign partyId opened over the same slot cold-starts empty, not a throw
- corrupt JSON in the slot cold-starts empty, not a throw
- bootstrap-peer-store only: a structurally junk entry (empty `addrs`) is
  dropped on load while a well-formed sibling entry in the same envelope
  survives — the `unusableEntry: 'drop-entry'` policy, contrasted with the
  trusted-owner store's whole-record-discard policy (proven separately by
  the earlier corrupt-JSON case)

The bootstrap-peer round-trip case needed a real, parseable Ed25519 peer id
(`peerIdFromPrivateKey(await generateKeyPair('Ed25519'))`, same helper
`cadre-core/test/bootstrap-peer-store.spec.ts` uses) — the loader validates
peer ids via `peerIdFromString` on reload, and a placeholder string like
`'12D3KooWFakeOwner'` (the fixture used elsewhere in
`cadre-node-bootstrap-peers.spec.ts`, where it's never round-tripped through
that validation) was checked by hand and confirmed to throw
(`Non-base58btc character`) — it would NOT have survived a real reload, so it
was not reused here.

## Explicitly skipped: Playwright e2e case

The ticket allowed for an optional Playwright round-trip case in
`e2e/solo/reload-persistence.spec.ts`. Skipped: the trusted-owner anchor and
bootstrap-peer store are pure `cadre-web.ts` wiring with no UI surface (no
Svelte component reads or displays them, no `data-testid` hooks exist for
either). Exercising them via Playwright would mean either adding new
test-only UI hooks or reaching into IndexedDB via `page.evaluate()` and
reconstructing the control-database name/party-id logic from `cadre-web.ts`
by hand — not "cheap" by the ticket's own bar. If real e2e coverage of this
path is wanted later, it should start from a look at `cadre-web.ts`'s control
database wiring (grep `TRUSTED_OWNERS_KV_KEY`, `BOOTSTRAP_PEERS_KV_KEY` there)
rather than being bolted onto this ticket.

## What's still unverified

The functional wiring itself (`kvSlot`, `startCadre`/`stopCadre`
integration) shipped in an earlier session with no tests. This ticket adds
the first real coverage of `kvSlot` and of `PersistentTrustedOwnerStore` /
`PersistentBootstrapPeerStore` layered over it — treat it as a floor, not a
finished validation of the whole integration (in particular, `startCadre`'s
own wiring of these stores into a running `CadreNode` is still untested end
to end; only the store/slot layer underneath it is).
