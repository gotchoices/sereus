# Review: the phone kit moves the app's strands when it joins another cadre

`PhoneNode.joinCadre` switches the app's one node from the party it founded (B) to the invitation's party (A). It now also carries B's strands, pending joins and invitations, using cadre-core's `exportStrandBundle` / `adoptStrandBundle` from `strand-bundle-export-and-adopt`.

## What landed

**`packages/cadre-rn/src/phone-node/strand-move.ts` (new).**

- `StrandMoveRecords` keeps one record per left party in the kit's `SecureStoreKeyStore`, under key id `cadre/strand-move/<base64url B>`. The record is `{ v: 1, targetPartyId, bundle, moved, refused }`. A read the secure store refuses throws. A record that does not parse, or whose slot does not match its `bundle.partyId`, is deleted with a warning and read as absent.
- `joinMoveRecord(bundle, invitation)` returns `undefined` for an empty bundle. It throws `StrandsNeedOwnerJoinError` when the bundle holds strands, pending joins or invitations and `invitation.invite.grantsOwner` is false.
- `adoptMoveRecord(node, records, record)` leaves out strands an earlier attempt was refused and calls `adoptStrandBundle`. It reports every refusal so far, then deletes the record when `failed` is empty or saves the progress (`moved` union, `refused`) otherwise. A failure updating the record is only logged.
- `adoptMovesInto(node, records)` adopts every record naming the node's party. A thrown adoption is logged and becomes a deferred outcome. A key-store read error propagates.
- Types: `StrandMoveOutcome` and `PendingStrandMove`, plus the `pendingMove` and `deferredOutcome` helpers.

**`node.ts`.**

- `switchParty`: when the start being left is a party this app founded (`foundedPartyLeft`, which replaced `formerPartyAfterJoining`), `recordStrandMove` exports and writes the record before `shutDown`. It exports from the running node, or, when none runs, from a node started for the export alone (`exportStopped`): no subscriptions, nothing saved, status `starting` then `stopped`. Refusals happen there, outside the rollback `try`, so B stays running on the same instance.
- `startAndRedeem` after admission: wire the owner key, then save the start (`saveRunningStart`), then `settleJoinMove`, then report running (`reportRunning`). `markRunning` was split into these two halves.
- `settleJoinMove` never throws. If the key is enrolled, it adopts every record naming A and reports the one from `formerPartyId`. Otherwise it returns `deferred / owner-key-not-wired` when a record from `formerPartyId` names A.
- `redeemInPlace` also calls `settleJoinMove`, so an owner grant arriving through a second invitation finishes a deferred move.
- `buildAndStart`: after `settleOwnerKey` returns `'enrolled'`, `adoptMovesInto` runs before `markRunning`.
- `returnToLeftParty` deletes the record the failed join wrote (`discardStrandMove`; a failure is logged).
- New `PhoneNode` methods:
  - `pendingStrandMove()`: the record for `formerPartyId` (the running start's, else the saved one's), whatever party it names.
  - `finishStrandMove()`: in the transition queue. Adopts the `formerPartyId` record when it names the running party, throws adoption errors, and flips a `member` / `timed-out` status to `enrolled` after a successful adoption.
- `JoinCadreResult.strandMove?: StrandMoveOutcome`.

**`index.ts`** exports `StrandsNeedOwnerJoinError`, `PendingStrandMove` and `StrandMoveOutcome`.

**Docs.**

- Kit README: a new "Moving the app's strands" subsection under "Joining another cadre", two table rows, and the `joinCadre` row mentions `strandMove`.
- `docs/architecture.md` → "An app joins an existing cadre": the "not open until moved" sentence now says the join moves them. The switch steps go from four to five (export and refusal; adopt; delete on rollback), plus a paragraph on the start-time resume and what "no record for B" means. "Two ends, carried as data" says the kit carries the bundle.
- `docs/reference-app-rn.md`: one sentence added to the Join behaviour.
- `tickets/plan/7-dissolve-empty-cadre.md`: an appended note correcting its planning assumptions (see deviations).

## Deviations from the implement ticket (decide whether you agree)

- **The start is saved before adoption, not after.** The ticket said both "adopt before `markRunning`, so the start is saved with the strands already seated" and "killed between admission and adoption: the relaunch comes up in A … and adopts from the record". Both cannot hold: if the start is saved only after adoption, a kill mid-adoption relaunches into B, and the record (naming A) is never reached until the user pastes the invitation again. I chose the crash-resume behaviour. The start is saved first, and `running` is reported after the adoption. In `buildAndStart` the adoption is still before `markRunning`, where the order does not affect resume.
- **A stopped app's join exports too.** The ticket only covered "the running node". With no node running (the user disconnected, or the last start failed) the old code would switch without exporting. B's strands would be left unrecorded, and `dissolve-empty-cadre`'s rule ("`formerPartyId` is B and no record for B") would read that as moved. `exportStopped` starts B's node just for the export. If that start fails, the join is refused with its error.
- **The outcome has a third variant, `{ state: 'deferred', reason: 'adoption-failed', error }`.** The ticket said adoption errors are "logged and reported" but its type had no place for a non-owner error.
- **The record has a `moved` list, and `PendingStrandMove` has `toPartyId` and `refused`.** `moved` lets `pendingStrandMove().strandIds` mean "not seated yet" after a partial adoption. `toPartyId` matters when the app joined a third party before the move finished.
- **Records are keyed for the public API by `formerPartyId`; automatic adoption scans by target.** A start or join adopts every record naming its party. `pendingStrandMove` and `finishStrandMove` speak only about the move from `formerPartyId`. More than one record can name a party only if an app founded two parties and joined the same one from both. Such a record is adopted automatically but not reported by those two methods.
- **A permanent refusal does not keep the record.** I followed this ticket's "deleted once an adoption reports nothing under `failed`". The dissolve ticket's planning note assumed the refusal list would survive. I appended a correction there rather than change the rule.

## Tests

In `packages/cadre-rn/test/phone-node/node.spec.ts`. `device()` now also returns `secureStore`. `expiredInvitation` takes `grantsOwner`. `moveRecordKey(partyId)` computes the secure-store key, a persistence contract the dissolve ticket depends on.

- `refuses, before anything stops, a member's join that would leave its strands behind`: B with one founded open strand, a non-owner invitation, `StrandsNeedOwnerJoinError` with `strandCount: 1`. The same `CadreNode` is still running, and the record key was never written (`FakeSecureStore.setOptionsByKey`).
- `discards the strands it recorded for the move when the join fails`: an owner-granting expired invitation and `CadreInviteRejectedError`. B runs again. The record key was written (so the export ran) and is now absent (so the rollback deleted it).
- `records the strands of a stopped party for the move too, and stays stopped when the join fails` (not in the ticket's list; added for the stopped-app export path, the one most likely to be dropped silently): stop, then join with an expired owner invitation. The record was written and then discarded, and the status is `stopped`.

Not unit-tested, checked by reading the code: the admitted path (export, switch, adopt, report) is covered at the cadre-core layer by `scenario-strand-moves-between-cadres`. The kit's part is ordering. This includes the start-time resume, `finishStrandMove`, `pendingStrandMove`, the `deferred` outcomes, unparseable-record deletion and the refused-strand filtering on retry. An admitted kit-level test would need a real party A with a member to redeem against, which the in-process harness does not have.

## Known gaps and things to look at

- **Secure-store value size.** A bundle with a routing table per strand exceeds expo-secure-store's 2048-byte guideline. The installed 14.2.4 only warns (`build/SecureStore.js` `isValidValue`) and stores it. This is parked as a `NOTE:` on `StrandMoveRecords.save`. A dev build will show Expo's yellow-box warning on a join that moves strands.
- **The start-time adoption delays `running`** by a few control writes per strand, on the resume path only. Parked as a `NOTE:` in `buildAndStart`.
- **`exportStopped` flips status `starting` → `stopped`** before the join's own `starting` → `joining`. A UI watching status may flicker.
- `finishStrandMove` and `pendingStrandMove` read records for `formerPartyId` only (see deviations). Also, `resolveOptions` copies `formerPartyId` from the saved start only when the options name no `origin`. An app that passes `origin: 'joined'` without `formerPartyId` loses the public view of the move, though starts still adopt it through the scan.
- The reference app's `describeJoinFailure` falls back to the error message for `StrandsNeedOwnerJoinError`. Wording for it belongs to `reference-apps-join-existing-cadre`.
- `node.ts` grew from 690 to about 830 lines.
