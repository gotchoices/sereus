## Summary

Implemented `HostProcessOrchestrator` in `@serfab/cadre-host`. The class spawns each cadre node as a plain Node child process (no Docker), maintains its handles in `<rootDir>/state.json`, allocates ports out of a configurable range, rotates logs by size, and verifies child identity via a startup-token file to detect PID reuse after a host restart.

Files added:

- `packages/cadre-host/src/orchestrator/pid-liveness.ts` — `isPidAlive` via `process.kill(pid, 0)`, treating `EPERM` as alive.
- `packages/cadre-host/src/orchestrator/port-allocator.ts` — range allocator with `markUsed` for restart rehydration.
- `packages/cadre-host/src/orchestrator/log-rotator.ts` — size-based rotating writer. Uses sync `fs.writeSync`/`fs.closeSync` so rotation is deterministic on Windows (a `WriteStream` releases its file handle asynchronously, which races against `renameSync`).

## Key design decisions worth a second look

1. **`dockerId = <pid>:<token>`** — opaque to callers, parsed internally by `decodeDockerId`. Tokens come from `crypto.randomBytes(16).toString('hex')` so they never contain `:`. `isRunning(dockerId)` confirms `isPidAlive(pid) && (tokenFile contents === storedToken)` to catch PID reuse.

2. **No rename to `orchestratorHandle`** — per the ticket, kept the field name `dockerId` everywhere. A future ticket can rename across `cadre-provider`.

3. **Sync-fd-backed `LogRotator`** — chose this over `WriteStream` because Windows holds file locks until the stream's async close completes, which made `renameSync` flaky in tests. The `writeStream()` method returns a `Writable` wrapper so child stdio can still be piped in.

4. **Cadre-cli bin resolution** — extended `@serfab/cadre-cli`'s `exports` map with `./bin/cadre.js`. The orchestrator does `createRequire(import.meta.url).resolve('@serfab/cadre-cli/bin/cadre.js')`. A test-only `spawn.entrypoint` config field overrides this so unit tests can point at a fake child script.

5. **Restart recovery (`init()`)** — does NOT auto-recreate dead containers. It reports them via `listDeadHandles()` and reserves their old ports so allocations don't collide. Recreation policy belongs in cadre-host's lifecycle (a later ticket).

6. **Windows stopContainer waits for `child.on('exit')`** — added a 1s grace race after the kill so the OS releases the child's cwd handle before we try `rmSync` on the workdir. Without this, `removeContainer` would leave orphaned workdirs on Windows.

7. **Stats** — `pidusage` is used for CPU% and memory. Network counters are always 0 (documented v1 gap, ticket-acknowledged).

8. **Resource limits** — memory is enforced via `NODE_OPTIONS=--max-old-space-size=<MB>`. CPU is not capped (documented v1 gap).

## Known gaps and points of nuance

- **SIGKILL-escalation test is skipped on Windows.** `process.kill(pid, 'SIGTERM')` on Windows is a forceful kill regardless of the signal name (Node docs: "On Windows, where POSIX signals do not exist, the signal argument will be ignored, and the process will be killed forcefully"). The test uses `it.skipIf(process.platform === 'win32')` so it still runs on Linux/macOS CI. Reviewer: please verify on a POSIX box if available.
- **Network stats are hardcoded to 0.** Documented v1 gap from the ticket. Billing isn't wired through cadre-host yet so the gap is tolerable.
- **Workdir cleanup is best-effort.** `removeContainer` catches and logs rmSync failures rather than propagating. On Windows the cwd handle release is asynchronous; the added `await child.on('exit')` race + `maxRetries: 20, retryDelay: 200` get this to pass in tests, but pathological lock holders (e.g. antivirus scanning the dir) could still leave orphans. State map / port allocator / state.json are always cleaned up regardless.
- **Real cadre-cli integration test deferred.** The ticket suggested a `describe.skipIf(!fullBuild)` integration test that spawns the actual cadre-cli bin. I did not implement this — the orchestrator unit tests cover all the orchestrator-side logic against the fake child, and the real cadre-cli changes (`--startup-token-file`) are mechanically trivial. A real-bin integration test would also need cadre-cli's deeper deps (libp2p, etc.) which take time to start; it belongs in a separate integration ticket alongside the cadre-host `start` subcommand wiring.
- **The orchestrator's `init()` is not yet called anywhere.** The cadre-host `start` subcommand stub remains unchanged — that wiring is the next ticket. `HostProcessOrchestrator` is fully usable today by any consumer that imports `@serfab/cadre-host`.
- **Storage profile config** — the orchestrator writes a `storage: { type: 'file', path: <workdir>/storage, quotaBytes? }` block for storage-profile children and omits storage entirely for transaction-profile. Verify this matches what `CliConfigFile` expects.
- **`createContainer` does not wait for the child to write its token file.** Callers (or `isRunning` checks) must poll. Tests use a `waitFor(() => orch.isRunning(dockerId))` helper; production code in container-service should do the same.
- **No graceful shutdown for the orchestrator itself.** If the cadre-host process is told to stop, it should SIGTERM all managed children. The interface doesn't expose a `shutdown()` method — that's intentional (handled by cadre-host's outer lifecycle), but worth flagging.

## Test cases to verify by hand

- Instantiate `HostProcessOrchestrator` in a Node REPL with `rootDir = ./tmp-orch`, call `createContainer({ containerId: 'c1', partyId: 'p1', bootstrapNodes: [], profile: 'transaction' })`. Confirm:
  - `./tmp-orch/c1/cadre.json` exists with the partyId.
  - `./tmp-orch/c1/.startup-token` is created shortly after spawn.
  - `./tmp-orch/c1/node.log` accumulates child stdout.
  - `./tmp-orch/state.json` contains the handle.
- Kill the orchestrator process, then instantiate a fresh `HostProcessOrchestrator` over the same `rootDir`, call `.init()`. Confirm `isRunning(dockerId)` returns `true` for the survivor.
- Force-kill the child externally (Task Manager / `kill -9`), re-`init()` a fresh orchestrator. Confirm `listDeadHandles()` reports it.

## Reviewer focus areas

- **Identity/token logic** in `host-process-orchestrator.ts` (`tokenMatches`, `encodeDockerId`, `decodeDockerId`, and the `isRunning` path that decodes raw dockerIds without an in-memory handle).
- **`init()` rehydration** correctness: handles with dead PIDs still reserve ports (intentional, until `removeContainer` runs).
- **Memory limit conversion** — `parseMemoryLimit` is duplicated from cadre-provider's docker-orchestrator. Per the ticket, this is on purpose to avoid cross-package coupling; flag if there's an obvious shared home.
- **Log rotator correctness under concurrent stdout + stderr writes** — both pipe into the same `Writable` which calls `writeSync` serially. Tested but not stress-tested.
- **The cadre-cli `exports` change** — adding `./bin/cadre.js` and `./package.json` to the exports map is generally low-risk but technically widens the public surface.
