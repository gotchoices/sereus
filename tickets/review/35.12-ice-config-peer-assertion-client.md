## What landed

The **client half** of peer-bound TURN issuance. The server half shipped in
`turn-issuer-peer-assertion`; until now nothing sent the five `X-Sereus-Peer-*`
headers, so `PEER_AUTH_MODE` was dormant. Both reference apps now sign every ICE
manifest fetch with their libp2p node key, so the issuer can attribute (and revoke)
a TURN credential per peer id.

### `cadre-core` — new `src/identity-key.ts`

- `loadOrCreateIdentityKey(keyStore, keyId?)` — the load-or-create-and-persist rule
  extracted verbatim from `CadreNode.resolveIdentityKey`, including the load-bearing
  rule that a rejected `get` (e.g. `KeyStoreAccessError` from a cancelled biometric
  prompt) **propagates** rather than falling through to generating a fresh key.
- `peerKeySigner(privateKey)` → `PeerKeySigner { peerId, publicKeyB64, sign() }`.
  Ed25519-only; `peerId` is `publicKey.toString()` (already the base58btc peer id for
  an identity multihash — no `@libp2p/peer-id` round trip), `publicKeyB64` is
  `publicKeyToProtobuf` + base64url.
- Both exported from `src/index.ts`.
- `resolveIdentityKey` now delegates and keeps only its own concerns: the
  `keyStore`+`privateKey` mutual-exclusion error, the `privateKey`/ephemeral
  branches, and the idempotent early return.

**One deviation from the ticket, flag for review:** the two identity log lines moved
*into* `loadOrCreateIdentityKey` rather than staying in `resolveIdentityKey`. The
helper is the only place that knows which branch it took, and both callers (node +
RN app) now get the line. Namespace changed from `sereus:cadre:node` to
`sereus:cadre:identity-key`; both are under `sereus:cadre:*`, which is what the
no-key-material-in-logs regression test enables, and that test still passes.

### `ice-config.ts` (both apps, kept as mirrors)

## Deliberate scope addition — read this first

The ticket said a thrown fetch behaves "exactly as today: log, return `[]`". **That
would have been a live regression on web**, so the retry was widened to cover it:

Attaching five non-safelisted headers turns a **cross-origin** browser fetch into a
*preflighted* one. The turn-credential-issuer answers that `OPTIONS` (it lists all
five in `Access-Control-Allow-Headers`); a plain static file server generally does
not — and `ops/docs/ice-servers.md` explicitly offers "host it alongside the
relay/ops infra" as a deployment option, i.e. cross-origin. A failed preflight
surfaces to JS as an ordinary network error with **no HTTP status**, so the
status-only retry list would never have fired and every such deployment would have
silently lost STUN.

So `shouldRetryUnauthenticated` retries on `400`/`401`/`403`/`503` **or on a thrown
attempt**, guarded by `if (controller.signal.aborted) return []` so an expired
deadline never buys a second doomed fetch. `429` is still excluded (the per-IP limit
fires before the assertion is parsed). Cost when the network is genuinely down: one
extra failed fetch inside the same 5 s budget. Reviewer should sanity-check that
call — it is the one place this diff goes beyond the ticket.

### Behaviours worth exercising by hand

- **Web, cross-origin static manifest.** Point `VITE_ICE_CONFIG_URL` at a JSON file
  on another origin served by something that does *not* answer the preflight. Expect
  two requests in the network tab (failed preflight, then a plain GET) and STUN
  servers still present. This is the scenario the scope addition exists for and the
  only one no unit test can truly reproduce.
- **RN first run.** Wipe the app, start it: the identity slot must end up with
  exactly one key, and the node's peer id must equal the one in the
  `X-Sereus-Peer-Key`-derived assertion. Two identities here would be the worst
  possible bug in this diff.
- **RN with a locked keychain.** Cancel the biometric prompt: `startPhoneNode` must
  *fail*, not boot with a fresh identity.
- **Audience mismatch.** Set `PEER_AUTH_AUDIENCE` with a trailing slash and confirm
  the client console prints the audience it actually sent, then still gets STUN.

## Known gaps — treat the tests as a floor

- **Never run against a live issuer.** No end-to-end request has been made from a
  real browser or device to a real `turn-credential-issuer` with
  `PEER_AUTH_MODE=optional`. Everything is stubbed `fetch` plus the pinned vector.
- **The CORS preflight is reasoned about, not observed.** No test in this repo can
  exercise a real preflight; the retry that handles it is covered only by a
  "fetch rejects" stub. The manual check above is the real verification.
- **`crypto.getRandomValues` on a device is untested.** `randomNonceHex` runs on
  Node's `crypto` under vitest. RN gets it from `react-native-get-random-values` via
  `polyfills/hermes.js` (verified by reading, not by running on a device); a missing
  polyfill degrades to unauthenticated rather than crashing, which *is* tested.
- **RN cold-start re-entry is not covered by a test.** The reasoning (a `get`-then-
  return is idempotent and opens no native handle, unlike `nodeLocalDb`) is in a
  comment at the site; nothing asserts it.
- **The two `ice-config.ts` copies are kept in step by hand.** ~380 lines each, no
  mechanical check. Both specs are near-identical and both pin the same vector, so a
  drift in the assertion helpers or the retry-status list fails a test — but a drift
  in, say, the log wording would not.
- **The audience-log assertion is loose** — it checks the URL and status appear in
  *some* warn line, not the exact message.
