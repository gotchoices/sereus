# `CadreControl.JoinedStrand`: the party-wide record of strands joined from other parties

## What landed

A strand (a shared app workspace) that a party joins from another party has its `Strand` row in the *founder's* control database, so today only the joining machine remembers the join, in its own `KeyStore`. This ticket adds the control table that the next ticket (`party-wide-joined-strands`) will publish joins into, so that every machine of the party, including an always-on replica host, can see them. **Nothing in the node writes or reads the table yet.**

- **Schema** (`schemas/control.qsql`, with `control-schema.ts` regenerated byte-for-byte from it): `table JoinedStrand (Id pk, Type not null, MemberPrivateKey null, StampId not null unique)` with `NotRevoked`, `RevocationRecorded`, `NoUpdate`, `KnownType` (`'o'`/`'c'` only), `MemberKeyClosedOnly`, an owner-signed `AuthorizedInsert` over `digest('CadreControl.JoinedStrand','add', Id, Type, coalesce(MemberPrivateKey,''), StampId)`, and an `AuthorizedDelete` with an owner-signed `'remove'` branch plus a committed-tombstone REAP branch. `Revocation` gains `'JoinedStrand'` in its column comments and one `RowIsGone` branch. The comments follow the house style: one-line reasons that point at where the full reason already lives.
- **TypeScript**: `'JoinedStrand'` added to `CONTROL_TABLES` (schema order), `RevocableTable`, `GUARDED_KEY_COLUMN` (`'Id'`) and `REAPABLE_TABLES` (its comment says why reaping is allowed here). New `ControlDatabase` methods:
  - `queryJoinedStrands()` / `queryJoinedStrand(id)`: `StrandRow` with `FounderOwnerKey: null`, read raw with no retired-stamp filter.
  - `insertJoinedStrand({Id, Type, MemberPrivateKey}, ownerKey, signMessage)`.
  - `deleteJoinedStrand(id, ownerKey, signMessage)`, which goes through `deleteGuardedRow`.
  - `queryJoinedStrandStampId(id)`: not in the ticket's list, added for parity with every other guarded table; the tests use it.
- **Idempotency classifier**: the regex that recognises a repeat insert of an existing strand id is now one function, `strandIdConflictPattern(table)`, used by `isStrandIdConflict(error, table)` for both `Strand` and `JoinedStrand`. `table` is **required** (no default), so the one existing caller, `cadre-node.ts` `publishStrand`, now passes `'Strand'`.
- **Docs**: `docs/architecture.md` Control Network gains a `JoinedStrand` row, the `Revocation` row lists the new table in its guarded list and its reap sentence, and there is a new paragraph after the table on constraint edits and old stores (see gaps below).

## Known gaps and things to weigh

- **A control store written by an earlier build does not start on this build.** I measured this with a throwaway spec, since deleted: the store was created by the HEAD schema and restarted on the new one. The warm start's schema diff issues `ALTER TABLE ... DROP CONSTRAINT` on `Revocation` for the edited `RowIsGone`, and the optimystic module refuses it (`Module for table 'Revocation' does not support ALTER TABLE DROP CONSTRAINT`). The same experiment with the new table but the *old* `RowIsGone` warm-started fine and could write a `JoinedStrand` row, so the constraint edit alone causes the failure. It cannot be avoided: a revocable table without a `RowIsGone` branch can never be tombstoned, so `deleteJoinedStrand` would always fail. `StrandPartyKey` must have caused the same break when it landed; nothing recorded it. The "no backwards compat" policy covers this, but in practice every persisted party (reference apps, cadre-host installs, dev machines) must be recreated after this lands. That is recorded in `docs/architecture.md` just after the Control Network table. The reviewer should decide whether that deserves more than a docs paragraph, for example a clearer startup error. I did not change the startup error.
- **The op-budget comment was already stale before this change.** HEAD measured 46 / 21 against the recorded 45 / 20: one more `getMetadata` block with the same 9 tables at optimystic 7f5e8a90. I recorded it in the history line and did not investigate it. The test passed at HEAD, so this is not a failure.
- **Mixed builds in one party.** A machine on an older build receives blocks for a table it does not declare. This is out of scope under "no backwards compat" and nothing was engineered for it.
- **`KnownType` has no dedicated refusal test.** Its only coverage is that the schema applies and valid rows land. The `or` form is accepted; `Strand.MemberKeyClosedOnly` already proved that shape works.
- **Tombstone scoping, checked by reading the schema:** the consent branch of `Strand.AuthorizedInsert` filters `R.TableName = 'Strand'`, so a `JoinedStrand` tombstone never closes it. Every other reader of `Revocation` filters on its own `TableName`.
- **Never-written block:** the next ticket will read this table on every strand-watcher poll. For a party with no joins the table is never written, and on an isolated machine that read fails `cohort-unreachable`. That failure belongs to the next ticket's reader; this ticket adds no reader and no marker row.
- The `Revocation` table's top comment in the schema still lists only four guarded tables ("OwnerKey / CadrePeer / ValidationKey / Strand"). It was already stale before this ticket, and I left it alone. The column comments are current.
