# Await protocol-handler registration instead of dropping its rejection

## What changed

libp2p's `node.handle(...)` is async. It rejects with `DuplicateProtocolHandlerError` when the protocol already has a handler, and it can also reject when its peer-store write of the node's own protocol list fails. Four cadre-core services called it as `void node.handle(...)`, so the rejection became an unhandled rejection. Under Node's default `--unhandled-rejections=throw` that kills the process after the caller has already returned success.

- **The four registrations are awaited.** `StrandAddrService.initialize`, `StrandWakeService.initialize`, `SeedBootstrapService.initialize` (and its private `registerProtocolHandler`, which now takes the node as a parameter) and `FormationListener.register`/`unregister` are async and await `handle`/`unhandle`. Each service stores its node reference only after the await resolves, so after a failed registration `shutdown()` does not call `unhandle`. `SeedBootstrapService` also stores `controlDatabase` only after the await.
- **`CadreNode.start`** awaits the wake and strand-addr `initialize` calls. A rejection reaches the existing `start()` catch, which runs `cleanup()` and rethrows.
- **The chain up to the public API is async:** `StrandFormationManager.registerResponder`/`unregisterResponder`, `StrandSolicitationService.registerResponder`/`unregisterResponder`, `CadreNode.initializeSeedBootstrap`, `enableSeedListener` and `initializeStrandSolicitation`. `cleanup()` awaits `unregisterResponder`, the same unguarded way it awaits the sibling `shutdown()` calls. The temporary seed services in `applySeed`/`dialInvite` await `initialize(..., { registerHandler: false })`.
- **CadreNode service fields (a design choice to check).** `initializeSeedBootstrap`/`enableSeedListener` go through a new `installSeedBootstrapService`, and `initializeStrandSolicitation` inlines the same pattern:
  1. The field is set *before* the registration is awaited. This means a concurrent `enableSeedListener`, or the lazy `createOpenInvitation`/`formStrand` path, sees the field and does not build a second service whose handler would collide.
  2. If registration fails, the *previous* service is put back (only if the field still points at the new one) and the error is rethrown.

  Before this change, every one of these methods was synchronous, so no interleaving was possible.
- **A behaviour change callers can now see:** calling `initializeSeedBootstrap` over an existing seed service, or calling `initializeStrandSolicitation` twice, now rejects with `DuplicateProtocolHandlerError`. Before, it crashed the process through an unhandled rejection. The "must be started" precondition errors on these methods are now rejections rather than synchronous throws. Every caller in the repo awaits them.
- **Callers across packages.** `await` was added everywhere: cadre-cli `start.ts`, cadre-host trust-circle test, the integration-tests harness and scenarios, cadre-core/cadre-cli specs, and the reference apps. Where a helper was synchronous, it was made async and its callers were updated: integration-tests `createSeedService`, `createReceiverService`, `responderService`, `armResponder`; cadre-core test `stubFormation` (×2) and `responder`. There were two non-mechanical cases:
  - `reference-app-rn/src/cadre-phone.ts` `initializeFormationResponder` is now async and awaited by `startPhoneNode`. A rejection lands in its existing fail-soft `catch`, which logs it.
  - `reference-app-web/src/lib/cadre-web.ts` `ensureSolicitation` is now async. Its `solicitationReady` boolean became a memoized `Promise<void> | null`, so concurrent `createInvitation`/`joinViaInvitation` calls share one registration. A failure clears the promise so the next call retries. `stop` resets it to `null`.
- **Docs.** `docs/architecture.md` (the strand-addr receiver bullet and the `registerResponder` bullet) now says these registrations are awaited and reject. No doc had a code example showing a synchronous call.

## Known gaps / for the reviewer

- **A peer-store failure leaves a stray handler.** libp2p's registrar stores the handler *before* it awaits the peer-store merge. When the merge fails, the handler stays registered in libp2p, but the service holds no node, so its `shutdown()` will not unhandle it. On the `start()` path this does not matter, because `cleanup()` stops the node. On the public entry points (`initializeSeedBootstrap`, `enableSeedListener`, `initializeStrandSolicitation`), a retry after such a failure would hit `DuplicateProtocolHandlerError`. Fixing this would mean calling `unhandle` on a failure that is *not* a duplicate: a duplicate means someone else owns the handler, and unhandling it would remove theirs. I left this out. The reviewer can decide whether it is a tripwire or needs a fix.
- The install-before-await and restore-previous logic in `CadreNode` (the service-fields bullet above) has no test. Neither does the promise memo in `cadre-web.ts`.
- The other integration scenarios only had `await` added at the call site. They typecheck and lint but were not run. Neither were the reference-app-web Playwright e2e suite or the RN app.
- Some existing `cadre-node-seed-trust.spec.ts` cases still wait 50 ms "to let an unhandled rejection surface" after `enableSeedListener`. Those waits are now redundant but harmless, so I left them.
