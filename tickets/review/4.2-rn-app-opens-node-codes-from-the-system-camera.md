# Review: Android system camera opens node codes in the app

## What landed

- `app.json` → `expo.android.intentFilters`: one `VIEW` filter, categories `BROWSABLE` + `DEFAULT`, `data: [{ scheme: "sereus-join" }]`. `expo.scheme` unchanged (still `sereus-chat`), so iOS does not register `sereus-join`.
- `app/+native-intent.tsx`: `redirectSystemPath` turns a path starting with `NODE_CODE_SCHEME` (imported from `src/node-claim.ts`) into `/settings?nodeCode=<encodeURIComponent(path)>`; any other path is returned unchanged. Nothing is logged.
- `app/settings.tsx`: `useLinkedNodeCode()` reads the `nodeCode` search parameter, copies it into screen state, and clears the parameter with `router.setParams({ nodeCode: undefined })`. While disconnected, the Node card shows a "node code is waiting" line (`TEST_IDS.settings.waitingNodeCode`), worded for `connecting` (opens once connected) vs. otherwise (Connect first). The held code is passed to `AddNodeSection` as `linkedCode` with `onLinkedCodeTaken` to clear it.
- `src/add-node-section.tsx`: an effect on `linkedCode` takes the code (calls `onLinkedCodeTaken`), and either drops it with an inline note when a claim runs or a prompt is open, or closes the scanner and runs the same `handleCode` a paste uses (readNodeCode → owner check → approval prompt).
- Docs: new "Opening a code from the system camera (Android only)" subsection under "Adding a Home Machine's Node", including why not iOS; removed from "Not covered here"; "When Native Rebuild Is Needed" mentions the intent filter.
- Blocked device-run ticket `rn-node-claim-by-qr-device-run`: added cold-start and warm-start system-camera rows, and a request to record which camera apps offer a custom-scheme code at all.

## Known gaps / things to check

- **Nothing ran on a device.** Whether the camera offers the app, whether expo-router hands `redirectSystemPath` the full opaque URI (`sereus-join:1.…`) rather than something it has already parsed, and cold vs. warm start are all unverified; they are in the blocked device-run ticket. If expo-router turns out to pass a mangled path for opaque URIs, the fix belongs in `+native-intent.tsx`.
- **Owner-check window:** `handleCode` awaits `cadre.isOwnerDevice()` before setting `pending`. A second linked code arriving inside that await is not counted as busy and would also be handled; the later one's prompt wins. Judged too narrow to guard.
- **Waiting code has no Discard.** A code that waits on a disconnected Node card stays until Connect (then prompts, where Cancel discards it) or until the app restarts. Reviewer may want a Discard button.
- The `linkedCode` effect lists only `[linkedCode]` as deps (no react-hooks lint in this repo); it reads `claiming`/`pending`/`handleCode` from the render in which the code arrived, which is the intended snapshot.
- Whether `router.setParams({ nodeCode: undefined })` actually removes the key from the navigation state (vs. leaving it `undefined`) is expo-router behaviour; verify on device that returning to Settings does not prompt again (the device-run ticket's warm-start row covers this).
