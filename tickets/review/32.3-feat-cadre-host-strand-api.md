# Review: `/api/strands` on the cadre-host management server

Implements `32.3-feat-cadre-host-strand-api`. No UI — the screen is
`feat-cadre-host-strand-removal-screen` (still in `implement/`, sequence 32.6).

## What landed

**`OwnerNodeClient` (`src/owner/owner-node-client.ts`)** — two methods on the existing
`request()` helper:

- `listStrands(): Promise<StrandListSnapshot>` → `GET /admin/strands`
- `removeStrand(id, { confirm }): Promise<StrandRemovalResult>` →
  `DELETE /admin/strands/<encodeURIComponent(id)>` with `?confirm=1` appended **only** when
  `confirm` is true.

The class now declares a third trimmed `CadreNodeLike` (`strands/strand-service.ts`) alongside
the trust-circle and NAT ones; its header comment says so.

**`src/strands/`** — a new subsystem folder shaped like `src/auth/` and `src/nat/`. It holds
**no host-local state** (no `strands.json`): `StrandService` validates the id and translates the
owner node's errors, and does nothing else.

- `types.ts` — `StrandSummary`, `StrandListSnapshot`, `StrandRemovalResult`, `StrandErrorCode`
  (`invalid_id` | `confirmation_required` | `node_unavailable` | `internal`), `StrandError`,
  `StrandHandlers`.
- `strand-service.ts` — `StrandService`, the narrow `CadreNodeLike`, `createStrandHandlers`.
- `index.ts` — re-exports.

Error translation reads `OwnerNodeUnavailableError.nodeCode` first, because that error is thrown
for *every* non-ok admin response, not only for a node that is down:

| `nodeCode` | → | message |
|---|---|---|
| `confirmation_required` | `confirmation_required` | passed through |
| `bad_request` | `invalid_id` | passed through |
| `not_ready`, `not_authorized`, absent | `node_unavailable` | wrapped, node text kept inside |
| anything else | `internal` | passed through |

**`src/server/routes/strands.ts`** — `GET /api/strands` and `DELETE /api/strands/:id`, both in
the `{ ok: true, data }` envelope the other `/api/*` routes use. `confirm` is accepted only as
`1` or `true` (the node's exact strict pair — no truthiness parsing). A removal publishes
`{ type: 'strands-changed', kind: 'removed' }` on the bus **only** when `removed === true`.

**Wiring** — `events/types.ts` (new event), `error-handler.ts` (`STRAND_STATUS` map + `classify`
branch + header comment), `server/index.ts` (optional `strands?: StrandService`, mounted in the
same founder-only way as `trustCircle`/`nat`), `bin/host.ts` (constructed in the founder branch
next to `TrustCircleService`), `src/index.ts` (public exports).

**Docs** — `docs/cadre-host.md` gets both route-table rows, the `strands-changed` SSE row, and a
new **Strands** section between "Trust circle" and "NAT and DDNS".

## How to exercise it by hand

Founder mode only (`ownCadre.enabled`). With `cadre-host start` running on `127.0.0.1:8765`:

```bash
curl -s localhost:8765/api/strands
# → {"ok":true,"data":{"strands":[…],"controlConnections":2}}

curl -s -X DELETE localhost:8765/api/strands/<openStrandId>
# → {"ok":true,"data":{"strandId":"…","published":true,"type":"o","removed":true,"alone":false}}

curl -si -X DELETE localhost:8765/api/strands/<closedStrandId>
# → HTTP/1.1 428, error.code == confirmation_required, node's full message

curl -s -X DELETE 'localhost:8765/api/strands/<closedStrandId>?confirm=1'
# → 200, removed: true   ← destroys the party's membership key for that strand. Use a scratch party.
```

Donor-only install (`ownCadre.enabled` false): every one of those 404s, same as `/auth/*`.

## Known gaps — please probe these

- **The closed-strand confirmation gate is NOT integration-covered.** Both new integration cases
  run against a party with no strands. Proving a real 428 needs a real closed strand, which needs
  the formation flow; that belongs to the formation scenarios. Unit coverage of the gate is a
  *fake node returning `confirmation_required`* — it proves this layer forwards and translates,
  it proves nothing about the node's decision (that is `feat-strand-admin-channel`'s test).
- **Strand ids containing `/` are refused with 400 `invalid_id`.** This is a limitation of
  `/api/strands/:id`, not of the node — the admin channel accepts a percent-encoded `%2F` and
  removes the row. I did **not** empirically test whether Fastify's router could in fact carry a
  `%2F` segment through to `request.params.id`; the ticket specified refusal at the service
  layer and I implemented that. If a reviewer establishes that Fastify carries it, the refusal
  becomes a self-imposed limit worth revisiting — the error message and the `validateStrandId`
  doc comment both already blame this route's URL shape rather than the node, and name
  `cadre strand remove` as the fallback.
- **No route-level test drives a real `OwnerNodeClient`.** The route tests fake the service and
  the service tests fake the node; the client's URL construction (`encodeURIComponent`, the
  `?confirm=1` suffix) is only covered where the integration scenario happens to exercise it —
  i.e. for an id needing no encoding, and for `confirm: false`. A malformed `?confirm=1` suffix
  would not be caught by anything here.
- **`removed: true` means "this call issued the delete"**, not "a row was observed to vanish".
  Two managers removing the same strand both get 200. That is the node's non-atomic
  read→decide→write window, documented on the type; this layer adds no claim it cannot support.
- **`controlConnections` / `alone` are snapshots.** Right at read time, possibly stale by the
  time the user clicks. The screen ticket treats them as advisory.
