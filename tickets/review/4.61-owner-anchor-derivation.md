# Review: the trusted-owner anchor is derived from the owner table along verifiable chains

Second of three tickets (after `owner-anchor-revocation-signer-and-owner-writers`, before `owner-anchor-follows-owner-key-changes`, which is the live-network proof). Treat this as a starting point; the gaps and judgment calls are listed at the end.

## What landed

**The rule, as a pure function** (`owner-anchor-sync.ts`, new, no I/O): `deriveOwnerAnchor({ base, rows, tombstones, chain })` returns `{ target, refusedRemovals }`. The module doc states the rule in the ticket's terms: base, live rows, derivable, derived (least fixpoint), chainDerived, removed (judged against the pass-start set, a re-add under a fresh stamp beats the older tombstone), and the refusal of a removal that would empty the anchor. It also records the deliberate deviation (an owner a removed owner vouched is pruned everywhere until re-added). Two details beyond the ticket text: the function drops rows whose stamp its own tombstones retire, so it is correct over raw rows too; and a row is verified at most once per pass (a row is judged once its voucher is trusted and settled either way, since trust only grows within a pass).

**The anchor store** (`trusted-owner-store.ts`): `TrustSource` gains `'chain'` (and `KNOWN_SOURCES`, so a persisted `chain` entry survives reload instead of discarding the whole anchor); the interface gains `sources(): ReadonlyMap<string, TrustSource>` on both backends; `trust()` follows one shared rule (`provenanceChanges`): an absent key lands, an out-of-band source over a `chain` entry rewrites the provenance, everything else is a no-op. Module doc rewritten: who derives, who removes.

**The verifier** (`peer-authorization.ts`): `verifyInvitationOwnerAdmission(row, usage, invite, isAnchored)` for `OwnerKey` rows. The links common to both tables moved into a private `verifyAdmissionChain` (issuer anchored and equal to `vouchOwner`, usage names the invitation and is the row's `vouchUsage`, targeted invitation names the redeeming device, stored peer key derives from the usage's peer id, the three signatures). `verifyInvitationAdmission` keeps the peer-row checks (`peerId`, `peerStampId`); the owner version adds `grantsOwner`, `usage.peerKey === row.key`, `usage.ownerStampId === row.stampId`. Behaviour of the existing verifier is unchanged (the targeted and derivation checks were restated over the usage's peer id, which the existing equality already pinned to the row's).

**The reader** (`control-database.ts`): `queryOwnerKeyRows(retry, retired?)` returns live `OwnerKeyRow`s (retired stamps excluded, a row with no stamp dropped with a log); the optional `retired` set lets a caller that already holds the tombstones skip the stamp read. `getOwnerKeys` now reads through it (three more columns per read, one code path).

**The sync** (`cadre-node.ts`): `syncOwnerAnchor(reason, retry, loadChain)` is the first step of `refreshAuthorizedControlPeers`. It snapshots `store.sources()`, returns on an empty base (the seam that keeps a node awaiting its claim empty), reads `queryRevocations` once and hands the `OwnerKey` stamps to `queryOwnerKeyRows`, loads the invitation chain only when an owner row is invitation-admitted, derives, logs refused removals, and applies the difference. **The apply diffs against the pass-start snapshot, not the live store**: keys trusted out of band while the reads were in flight (an invitation pin, the genesis anchor, a claim) are left alone, and a key removed meanwhile is not re-added as `chain`; the next pass judges both. Any read failure skips the pass with a log and the refresh continues (reason below). Persist failures are logged per key and do not fail the refresh. The invitation chain is loaded at most once per refresh through a small lazy source (`invitationChainSource`) shared with the membership read, whose body moved into `collectAuthorizedMembers`; the public `listAuthorizedMembers(retry)` is unchanged. `InvitationChain` moved to `types.ts`; `isInvitationAdmitted` accepts either row type.

**Types** (`types.ts`): `OwnerKeyRow`, `InvitationChain`; `trustedOwners.pinnedSource` and `trustOwnerKeys` exclude `'chain'`.

**Comments and docs**: the `redeemCadreInvitation` sentence that waited for this ticket is gone; the `initializeSeedBootstrap` NOTE says the self-anchor is base and the sync does not correct it; `initializeTrustedOwnerStore` carries the NOTE on an operator pin of a removed key (honoured for at most one refresh per start); the `listAuthorizedMembers` rotation NOTE covers both tables; `seed-bootstrap.ts`'s NOTE on `anchorAcceptedSigner` names the sync as the second anchor writer. `docs/architecture.md`: the anchor bullet's provenance list, the removers, two labelled sub-paragraphs ("How the anchor follows the owner table", "What the derivation cannot settle"), "What invitations carry", the `OwnerKey` table row, and the sentence under "Enrollment Flow: Invitation Redeemed at Any Member".

**Exports** (`index.ts`): `verifyInvitationOwnerAdmission`, `deriveOwnerAnchor`, `OwnerAnchorInputs`, `OwnerAnchorDerivation`; `OwnerKeyRow` and `InvitationChain` through `types.ts`.

## Judgment calls the reviewer should weigh

- **A failed sync read does not fail the refresh.** The ticket's sentence can be read either way. Chosen: the sync catches, logs and returns, and the membership read still runs. Reason: `queryRevocations` has no cohort-unreachable fallback, while the membership read's `readRevokedStampRows` does; failing the whole refresh would freeze an isolated node's gate snapshot, which that fallback exists to prevent. The anchor the snapshot is then judged against is the one the previous snapshot was judged against too. A `NOTE:` at the sync says the sync is skipped on such a node until the block is held.
- **One Revocation read, by handing stamps into the reader.** The ticket counted "one `OwnerKey` read and one `Revocation` read more per refresh". The first cut read the stamp set twice; the consult-budget spec caught it (every `Revocation` read before the ledger marker is a cohort consult). Fixed with the optional `retired` parameter rather than a raw reader variant.
- **The consult budget moved by design.** `control-founding-consult-budget.spec.ts`: before the marker, `authorizePeer` 3 → 4 consults and the idle reconcile 4 → 5, one `Revocation` consult each from the sync's tombstone read; after the marker still 0. `MEASURED_ON` is 2026-10-07 and `BASELINE_UPSTREAM` is `optimystic ff150e0f` (the sibling's clean HEAD); the other figures in that spec were re-measured by the same run and did not move. The explanation sits in the spec's marker-table comment.
- **Stricter than the minimum for owner rows.** The targeted-invitation check and the peer-key derivation check apply to owner rows too, because they live in the shared tail. Harmless for a legitimate redemption (the member checked both at write) and tighter against a planted usage row.
- **Removal of a key that is only a stale pin here** still counts the tombstone's signer if that signer is in the pass-start set; covered by the simultaneous semantics, not by a dedicated test.

## Known gaps and tripwires

- **Isolated node, Revocation block never held:** the sync is skipped at every refresh until the block is held (`queryRevocations` throws cohort-unreachable, caught). `NOTE:` at `syncOwnerAnchor`. Becomes work only if an isolated node must derive owner additions while cut off.
- **Cost:** one `OwnerKey` read and one `Revocation` read per membership refresh, plus the invitation chain when an owner row is invitation-admitted. `NOTE:` at the sync points at the existing memo suggestion on `loadInvitationChain`.
- **Operator pin of a removed key** is trusted for at most one refresh per start. `NOTE:` at `initializeTrustedOwnerStore`.
- **The node's own removed key** is re-anchored as `genesis` at each start and removed by the first refresh; the docs name the window. Self-shutdown on removal belongs to the device-removal plan ticket.
- **Order of owner removals** is not recoverable from replicated state, and the window is unbounded where a removed owner's row survives (`fix/removed-owner-still-authorizes-where-its-row-survives`). The docs sub-paragraph "What the derivation cannot settle" says so and does not promise convergence closes it.
- The docs coverage sentence names today's coverage (the pure spec and the derivation assertions in `cadre-invite-any-member`); the next ticket replaces it with its scenario.
