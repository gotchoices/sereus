# Removing a machine rotates the party's member key in each strand it manages

Third ticket of the chain (`control-schema-strand-peer-and-pending-party-key` → `strand-peer-rows-and-sibling-binding` → this → `scenario-machine-removal-rotates-party-key`). The design the implement ticket carried is now in `docs/architecture.md` → "Removing a machine" and `docs/strands.md` → "Replacing the party's key"; this handoff lists what was built, the decisions made where the ticket left room, and what the reviewer should look at.

## What was built

- **The removal transaction writes the intent.** `ControlDatabase.removeMachine` takes `pendingPartyKeys` (one fresh key per closed strand the party holds a `StrandPartyKey` for) and writes a `PendingStrandPartyKey` row per entry in the same transaction and approval as the machine's tombstones. A stored pending row is retired and replaced, with the replaced key's public half appended to `Superseded`. `CadreNode.removeMachine` mints the keys from the plan; `SeedBootstrapService.removeMachine` passes them through. A removal that finds no live row writes nothing, pending rows included.
- **The driver** (`strand-party-key-rotation.ts`): steps 1 to 6 as the ticket specified, with every step reading before it writes, one run per strand at a time (a second call joins the run in flight), and one control swap per run across every strand that finished. Blocked at step 2 when the party holds no manager seat and the new key is not yet a member: `strand:party-key-rotation-blocked` once per pending stamp, outcome `needs-another-party`. The swap is deferred while a control write could fork the party and the strands are reported `pending`.
- **The control swap** (`ControlDatabase.swapStrandPartyKeys`): per strand, the `StrandPartyKey` row's guarded removal and a fresh insert naming the new key, plus the pending row's retirement when it holds that key, one transaction and one approval across the run. Decided inside the locked body over the rows as stored: a row already naming the new key is skipped, a row naming neither key is left with a log, and a pending row that names another key (a later removal replaced it) stays for the next run.
- **Who drives, and when.** `CadreNode` drives only when its owner signer is enrolled and the strand's database is live. Triggers: `removeMachine` (awaited, after waking hibernating closed strands the plan placed here), a closed strand launched, resumed or made writable here, the party key watch (`StrandPartyKey`, `PendingStrandPartyKey`) and the growth drain.
- **Re-keying a running instance.** `StrandInstanceManager.rekeyParty` replaces the retained launch config with a fresh object, stops and settles the membership reconciler, and rebuilds it over the new key (the reconciler construction is now `armMembershipReconciler`, shared with the runtime build); a hibernating instance only gets the config. `CadreNode` calls it from the driver's swap and from the party key watch for every tracked closed strand whose control row names another key. `resumeStrandRuntime` re-reads the `StrandPartyKey` row and passes it as a resume override.
- **The plan and the result.** `MachineRemovalPlan.strands` (`here` / `later` / `another-party`, from `planStrandKeyRotations` over `ClosedStrandState`), `MachineRemovalResult.strands` (`rotated` / `pending` / `needs-another-party`), `MachineRemovalWrites` for what the database wrote. The integration scenario's `toEqual` on the result now includes `strands: []`.
- **Stale rows.** A `StrandPartyKey` or pending row whose stamp is already retired (the tombstone arrived without the delete; neither table reaps) is removed by the owner-signed delete alone (`execSignedDelete`, the delete half of `execGuardedRemoval`), since a second tombstone would collide on `Revocation`'s key. This settles the "stale pending row" edge case the ticket asked to decide: the replace path and the swap both handle it.
- **A strand leaving the party.** `deleteStrandAndPartyKey` (unpublish, and a move's source side) retires the pending row with the party key row. `deleteJoinedStrand` leaves it: leaving a joined strand keeps the `StrandPartyKey` row for a later re-formation, so the pending row stays beside it and the re-formed strand's launch finishes the rotation. A strand bundle carries the current key only; the pending row stays behind with the source's unpublish.

## Decisions the ticket left open

- **A closed strand with no `StrandPartyKey` row gets no pending row and no plan entry.** The party holds no identity there for the removed machine to keep, no reconciler runs for it anywhere (the reconciler needs the key), and a pending row for it would have no driver.
- **A hibernating strand plans as `here` without reading its manager seat.** The plan is read-only and a hibernating instance has no database; the removal wakes it and the outcome reports what it found.
- **Step 1 skips a superseded key that is the current key.** Two owners removing two machines while partitioned can leave the control row on a key a later pending row lists as superseded; revoking the current key would be fatal, so the run continues from it as the ordinary rotation to the newer pending key.
- **The swap is a second owner approval.** The removal's approval closes before any strand write; folding the swap into it would hold an approval open across strand-network writes.
- **A strand still syncing when the removal lands is `later`** in the plan and is driven when it becomes writable (`handleStrandWritable`).

## Tests added, and what each pins

- `strand-party-key-rotation.spec.ts`, one parametrised test over a real closed strand on the local transactor with the control seam stubbed: from a founded strand with this machine, two siblings and the removed machine bound under K, a run ends with K' as member and manager, this machine and both siblings bound under K', K absent, the removed machine's binding under K an orphan with no live binding beside it (the enforcer's own row reader), and one swap naming the keys the run started from and arrived at. The same end state is reached after failing each of the seven strand writes in turn and after a failed swap, and a further run writes nothing. The clean run also pins the write count, so a change to the step list has to be stated there.
- `cadre-node-remove-machine.spec.ts`, one new test: a removal with a closed strand founded here but not running plans the strand `later`, reports it `pending`, and writes a pending row holding a fresh key with the control row still naming the old one; a second removal replaces the pending row, names the first key's public half as superseded, retires the first row's stamp and leaves the control row as it was.

## Known gaps, for the reviewer

- **No test drives the rotation through `CadreNode`.** The triggers (`removeMachine` waking and driving, launch, resume, writable, the watch, the growth drain), `rekeyParty` on a running instance, and the resume override are wired by reading; the real-network proof is `scenario-machine-removal-rotates-party-key`, which runs next. A unit seam below the node for the triggers does not exist, and the same gap was declined in the previous ticket for the same reason.
- **`swapStrandPartyKeys` is not unit-tested against the engine.** The driver test stubs it. The scenario ticket asserts the swapped row on the remover and on a sibling. A one-database test of the delete-and-re-add under the same id, plus the stale-row branch, would be cheap to add in `control-database-strand-peer.spec.ts` if the reviewer wants one before the scenario.
- **The `another-party` arm is reachable but unexercised**: the driver test's seam throws on `onBlocked` because the fixture always has a manager seat. The cross-party plan ticket owns that path.
- **`rekeyParty` arms a reconciler for a tracked replica that had no party key before** (the control row arrived after launch). That is new behaviour beyond the ticket, deliberate (the replica binds its siblings from then on, as a resume would make it), and untested.
- **The party key watch runs `rekeyParty` for every tracked closed strand on every change to either table**, each a `queryStrandPartyKey` read and a `settleRuntimeBuilds` wait. Both tables change only on a rotation, so this is a `NOTE:`-free cost today.
- **`driveRotationIfPending` reads the pending row on every closed strand launch, resume and writable transition**, one control read each. Same reasoning.
- **A removal made while alone** still has the documented limit: the pending rows have no re-issue path (the `NOTE:` at the table in `control-schema.ts`).
- The `docs/reference-app-rn.md` "What removal does not do" bullet and the apps' wording still say the removed machine keeps the strand keys; the scenario ticket changes them with the apps.
