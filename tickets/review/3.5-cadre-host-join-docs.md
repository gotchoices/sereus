# cadre-host docs rewrite — review handoff

Last of the `cadre-host-join-a-cadre` chain. Documentation only, plus comment and fixture-name edits in two cadre-host test files. No behaviour changed.

## What changed

**docs/cadre-host.md, restructured** in the order the ticket gave:

- Intro and **Who it's for**: runs always-on nodes for cadres that live on phones, your own first, a friend's if they scan your code; nothing is configured per person.
- **Package boundary**: the Auth and Tenancy rows now say admission is a claim or an invitation checked by the cadre's own nodes.
- **Deployment model**: management plane only; "holds no owner key and never founds a cadre" stated as a rule citing `feat-owner-keys-only-on-user-devices`; one kind of node; a new mermaid diagram (manager, two hosted nodes, phones dialing them); **Control-plane separation** reduced to the one case.
- **Join a cadre**, now a top-level section (anchor `#join-a-cadre`, replacing `#hosted-nodes-join-a-cadre`):
  - **Join by QR code**: the four steps, with the `sereus-join:1.` encoding and the claim naming the party.
  - The live states, and "a respawn keeps the code valid".
  - **Join by invitation**: the existing text, with Reset moved out.
  - **Claimed by someone else**: new; the intended owner's phone gets `already-claimed`, and Reset is the fix.
  - **Remove, reset and a lost host**: new arm for a dead host. The owner removes the node with `CadreNode.removePeer` (no reference app offers this yet, `remove-a-device-or-app-from-a-cadre`) and joins a node on the new machine.
  - **Where the credentials go**, **Reachability from outside** (moved here from Hosted nodes), **From the CLI**, **In the local UI**.

## For the reviewer to weigh

- **`hosted-nodes.json` is written with the default file mode.** It holds claim secrets (until claimed) and invitation private keys. The DDNS secrets fallback (`nat/secrets/file-store.ts`) and identity keys (`orchestrator/identity-file.ts`) are written `0600`; this store (`hosted/hosted-node-store.ts`, `writeFileSync` with no mode) is not. On a default Linux umask another local account could read a pending claim secret and claim the node. Found by reading the code; not run. The security posture says the host's own user account is trusted, but it does not cover other accounts on the same machine. There is already a tripwire `NOTE:` on the stored invitation in `hosted/types.ts`. Not filed: this ticket is documentation, and the reviewer is better placed to decide between a point fix and a ticket.
- **New prose not checked against a running host:** the "Claimed by someone else" behaviour, which I read from `seed-trust-policy.ts` (`already-claimed`) and cadre-cli's claim handling, and the lost-host arm.
- The "Process integration" subsection moved from under Push credentials into NAT and DDNS. Its anchor (`#process-integration`) had no inbound links.
