# Review: a joining machine's own record travels with its join

## What landed

- **Item 1, complete.** `CadreInviteRedeemRequest` is `v: 2` and carries `record: { addrs, updatedAt, profile, sig }` (exported type `RedeemSelfRecord`) in place of `multiaddrs`. The device signs it with `signSelfRecord` over `sanitizeAddrs(collectSelfAddrs())`, so the relay address is now included, where before the request used `resolveInviteAddresses()` alone. The member judges it in `admittedRecord` (module-private, pure): the signature is kept only if sanitizing dropped nothing, the profile is null/`transaction`/`storage`, `updatedAt` is a positive safe integer, `sig` is a bounded string, and `verifyPeerRecordSignature` passes for the member's party under `peerKey`. Otherwise the device is admitted as before, with addresses only, and a debug line says why. `ControlDatabase.redeemCadreInvite` takes an optional `record` and writes `UpdatedAt`/`Sig`/`Profile` from it. Mixed versions: either side refuses the other's request with the final `invite-invalid` ("Malformed redemption request"); the protocol id is unchanged.
- **Item 2, partial.** The mechanism exists: `lastSignedSelfRecord`, set by both write paths of `publishSelfRecord`; `publishSelfRecordUnlessCurrent` / `isCurrentSelfRecord` (row sig matches, younger than half a heartbeat, same profile, same sanitized addresses); and `noteSelfRecordPublished(at?)`. It has one caller, the boot timer, and only after an *insert*: a founding owner's explicit `registerSelf` is not repeated by the 1 s timer. After a refresh (`lastSelfRecordRefreshedARow`, the update path), the timer writes as before. `publishFirstSelfRecord`, drain step 2 and the redemption are unchanged in behaviour.
- **Item 3, complete.** `redeemCadreInvitation` no longer awaits `refreshMembershipGate('invitation-redeemed')`; it still kicks a reconcile pass. No scenario showed a caller needing the gate current at return, so the planned fallback was not used.
- **Item 4, complete.** `hasOwnerKey()` reads the `OwnerKey` membership view (every physical row, retired included), so a genesis pre-check and `ensureOwnerKey`'s re-check share one storage load. `ensureOwnerKey`'s call runs outside the write lock. The docs' and the `readMembershipRows` doc's "plain SQL" lists dropped it.

## What was held back, and why

The ticket's main saving, a device admitted by invitation not writing its record again (`publishFirstSelfRecord` and the boot timer using `publishSelfRecordUnlessCurrent` after admission, with the redemption remembering its record), broke `cadre-invite-any-member`. The returning owner A never listed device P within 60 s: 5 of 5 runs, against 3 of 3 green without it.

Diagnosis, from Optimystic debug logs: at A's reconnect reload (11 s after it connects), Optimystic deferred 15 read-repair consults at its in-flight cap of 16, including every consult of `CadreInvite` and `CadreInviteUsage`. A deferred consult starts nothing and waits for "a later read", but the membership view installs the read's rows and serves memory, so no later read comes for 2 minutes. In passing runs, A had already pulled 8 newer blocks before the reload, by retrying writes that conflicted with M's newer revision. Those are A's second self-write and P's post-join publish, the very writes this ticket removes. Which of the two is load-bearing was not isolated: the scenario passed whenever P wrote again after joining, and failed whenever it did not.

Filed:
- `tickets/fix/7.31-membership-view-keeps-rows-a-deferred-consult-left-stale.md`: the latent defect, `repro: verified`.
- `tickets/implement/7.32-invited-machine-skips-its-first-publish.md`: the held-back changes, `prereq:` the fix. It includes a race found on the way: the device must remember its record *before* dialing, because the member's commit reaches it before the reply. Observed: P's reconcile pass saw its row first and spent 10.8 s rewriting its record.

Two rules were tried for the boot timer and rejected; the reviewer should know why the code keys on "last record was a refresh":
- "Skip only while alone" broke the invitation saving. A device that redeems within a second of starting is connected when the timer fires, and the message-cost run showed it writing again.
- "Always skip when current" removed A's second write on a restart, and that write is one of the masking writes above.

## For the reviewer

- `admittedRecord` treats any record field it cannot judge as "no signature", never as a refusal. Check that no malformed record can fail the admission insert. The `KnownProfile` CHECK is the one constraint on those columns, and the profile check mirrors it.
- `isCurrentSelfRecord` compares *sanitized* current addresses with the record's list. A published record is unsanitized, so a node with more than 16 addresses is never "current" and writes as before. That is deliberate, so the held-back follow-up can reuse it for the redemption's sanitized record.
- `hasOwnerKey` via the view: a load served by the committed-read path is not kept, so the share is best effort. The semantics (any physical row) are unchanged.
- `tickets/.pre-existing-known.md` has a one-off entry for this scenario's same timeout message. Its confirm protocol ("if the reload line appears and P's rows still never arrive, it is a different failure") describes the fix ticket's failure mode; I did not edit that file.
- Docs: the invitation flow's diagram steps 5 and 9, the request block, a new paragraph "The device's own address record rides in the request", the device's last step (no gate refresh), Cadre Node step 4, the owner self-registration paragraph, and a sentence in "Membership rows view" → "After a sibling connects" naming the deferred-consult gap.
