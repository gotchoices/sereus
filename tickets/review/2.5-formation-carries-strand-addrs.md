## What landed

Cross-party strand discovery had **no production path**. The strand-addr RPC
(`/sereus/strand-addr/1.0.0`) is membership-gated and answers own-party siblings only, so
a joiner from a different party resolved an empty cohort seed and every cross-party
integration scenario reached its mesh by hand-dialing one strand node at the other.

The formation handshake is the one moment two parties are authenticated to each other and
agreeing on a strand id, so the address now travels there.

**Wire.** `FormationResultMessage` gains `strandAddrs?: string[]` — the responder's live
strand-network multiaddrs for the strand it just provisioned. Written on the approval path
only, next to `partyId`/`cadrePeerAddrs`, so it rides the existing disclosure gate (token +
disclosure validated **and** provisioning approved). Omitted when empty. Sanitized and
capped at 16 entries by `sanitizeStrandAddrs`, applied on **both** sides — the responder
bounds what it sends, the initiator bounds what it stores, because a peer may ignore a cap.

**Seam.** `FormationListenerOptions.resolveStrandAddrs?(strandId)` → threaded through
`StrandFormationManagerOptions` and `StrandSolicitationServiceOptions` → wired by
`CadreNode.initializeStrandSolicitation` to its own `getStrandMultiaddrs`. Unwired (every
mock/transport test) the responder simply discloses nothing. A hook that throws is logged
and folded to `[]`: the seed is an optimization, the consent row is the commitment.

**Return path.** `dialFormation` now returns `FormationDialResult { provision, strandAddrs }`
rather than a bare `FormationProvisionResult` — the addresses are a disclosure of the
responder's runtime, not a property of the strand row. `FormStrandResult` gains
`strandAddrs: string[]` (always an array, frequently empty) so an embedding app that
launches a strand outside `CadreNode` can seed it too.

**Bookkeeping.** `CadreNode.crossPartyStrandAddrs` is an in-memory `strandId → addrs` map,
written by `formStrand`. It reaches the strand's address book three ways:
`resolveCohortSeed` unions it **after** the sibling RPC answers (fresher first,
de-duplicated, each source keeping its signaling-first order) on launch and on hibernation
resume; and `refreshStrandPeerAddrs` re-merges it on every pass.

That last one required a restructure worth reading carefully: the refresh pass used to
`return` before merging anything when there was no connected sibling, which is exactly the
two-party joiner's steady state. It now skips only the **RPC**, and still merges the
contact addresses. Nothing can re-resolve a cross-party address, so this periodic re-merge
is the only thing standing between the seed and the peerStore's one-hour expiry. A strand
with neither a sibling to ask nor a contact entry still does nothing and leaves its
throttle unstamped (unchanged), and the unbounded `queryCadrePeers` read is still skipped
at zero connections (unchanged).

**One behaviour change outside the cross-party path.** `CadreNode.getStrandMultiaddrs` now
runs each address through a new `withAddressedPeerId` (`peer-addr-book.ts`), appending
`/p2p/<self>` when the address names no destination — a bare listen addr, or a relay hop
whose trailing `/p2p/` names the RELAY. Both consumers need it (`groupAddrsByPeerId` drops
what it cannot attribute), so the same-party strand-addr RPC answers get it too. libp2p
already appends the id in practice, so this is belt-and-braces, not a fix for an observed
failure — see "gaps" below.

## Use cases to exercise

**The path that works (proven):** a host founds a strand, publishes a `FormationInvite`
**bound** to it, and a joiner from another party redeems. The host's strand is live at
redemption, so it discloses addresses and the joiner meshes with no dial of its own. This
is the reference apps' release flow (`cadre-web.ts` `joinViaInvitation`, RN
`chat-strand.ts`) — both call `CadreNode.formStrand` then `CadreNode.addStrand` on the
same node, so they inherit the seed with no app change.

**The path that legitimately yields nothing:** an **unbound** invite. The responder mints
the strand during the session and has not launched it, so `strandAddrs` is absent and the
joiner proceeds with an empty seed. Confirm this stays a normal approval, never a failure —
the structural `FormationResponseValidator` must not grow an opinion about `strandAddrs`.

**Disclosure timing.** Every rejection arm (bad consent, invalid token, invalid disclosure,
concurrency cap, post-validation provisioning rejection, provisioning timeout, internal
error) must carry no `strandAddrs`, and the resolver must not even be **called**. The
listener's hook is wired by default in `baseOptions` so those assertions are real rather
than vacuous, with an explicit positive control.

**Scoping.** Addresses are scoped to their own `strandId` — never another strand's
peerStore, never the control peerStore. There is a unit test for the two-strand case.

## Known gaps — read before reviewing

- **The ticket's de-hand-dial target was not achievable and was not done.** It asked to
  remove the hand-dial at `strand-formation-e2e.integration.ts:454-457`. That scenario
  redeems an **unbound** invite through a mock provisioner, so Alice has no live strand
  node at redemption and discloses no addresses — the ticket's own edge-case section
  predicts exactly this. Removing the dial there would simply hang the test. The same
  applies to `strand-membership-closed-strand-e2e`'s fixture dial. Both sites now carry a
  comment saying why the dial stays and pointing at the new scenario, which de-hand-dials
  a path where the seed can actually exist. **If the reviewer wants the original file
  de-hand-dialed, it needs its fixture reshaped into a bound-invite flow** — a different,
  larger change that would duplicate the new scenario and drop its mock-provisioner
  coverage.
- **`getStrandMultiaddrs` normalization is unproven against a real omission.** No observed
  case has libp2p returning a strand addr without `/p2p/<self>`; the guard exists because
  the ticket asked for it and because `groupAddrsByPeerId` silently drops unattributable
  entries. It is unit-tested in isolation, and the same-party RPC scenario still passes,
  but nothing proves it was needed. Reviewer may reasonably ask whether it belongs here at
  all.
- **No authenticity check on the carried addresses.** `sanitizeStrandAddrs` validates that
  each entry parses; it does not check that the entry names the responder's strand peer,
  or that anything is reachable there. A malicious responder can point the joiner's seed
  at arbitrary peer ids. This is the same exposure `mergeStrandPeerAddrs`'s existing NOTE
  already accepts for sibling RPC answers — an address grants no authority, the dialed
  peer authenticates by peer id at the handshake, a bad entry costs one failed dial that
  ages out in an hour — but it is now reachable from a *stranger*, not only a co-cadre
  member. Worth a second opinion on whether that widening deserves its own ticket.
- **In-memory and one-shot, by design.** A joiner restart loses the map; with no sibling
  running the strand its seed is `[]` again. Addresses are never re-resolved, so a
  responder relay reservation that rotates before the joiner dials leaves a dead entry
  (recovery: a fresh invitation). Both documented in `docs/strands.md`; durability is
  `backlog/feat-cross-party-strand-addr-durability`.
- **Loopback only.** The new scenario proves the mesh over direct loopback addresses. The
  relayed cross-party proof is the follow-on `blind-relay-phone-to-phone-e2e` (2.8), which
  is where a relay-routed `strandAddrs` entry actually gets exercised.
- **Reference-app Playwright e2e still hand-dials** via the `__cadre.dialStrandPeer` debug
  hook (`cadre-web.ts`). That dial is now redundant for the web app's bound-invite path,
  but the browser e2e was not touched — out of scope, and it is a separate proof surface.

## Tripwire parked in code

- `CadreNode.crossPartyStrandAddrs` declaration — the map is kept for the node's lifetime
  (including across `stopStrand`, deliberately, so a watcher-rediscovered strand still gets
  its seed). Bounded by the number of strands the node has ever formed as an initiator, not
  by time. `NOTE:` at the site says to evict on `unpublishStrand` or cap the map if a node
  ever forms strands at scale.
