# Review: browser reference app dissolves the cadre it left

The web app now follows the phone kit's dissolve (`packages/cadre-rn/src/phone-node/dissolve.ts`, `node.ts` → `dissolve`). A tab that founded party B and joined party A removes B's IndexedDB storage once A holds everything B holds and B has no other machine. The Cadre page's join card does this on its own after a join with nothing pending, and offers it on load while the start record still names B.

## What landed

**Module layout.** `cadre-web.ts` was 1,401 lines with a `NOTE:` saying to move the join section out when it grew, and the 8.5 review named this ticket as that growth. The join section moved verbatim into `lib/web-join.ts`, over lifecycle exports `cadre-web.ts` now provides (`bringUp`, `readPartyAlone`, `wireJoinedOwnerKey`, `ownerKeyWired`, `getMoveRecords`, `getUnfinishedRemoval`). The dissolve's transition steps are also in `web-join.ts`. Its storage-level parts (the refusal errors, the comparison, the marker and the removal order) are in `lib/web-dissolve.ts`, which imports nothing from `cadre-web.ts`. That keeps the import graph free of cycles: `cadre-web.ts`'s start imports the marker check from `web-dissolve.ts`. `cadre-web.ts` is now 1,212 lines and `web-join.ts` 357 (`wc -l`).

**Sequence** (the store's `dissolveFormerParty(discard?)` drives it):

1. `planDissolve()` (in `web-join.ts`) refuses before anything stops. It throws an `Error` unless the running start names a `formerPartyId` other than its own party, and `StrandMovePendingError` while B's move record exists, whichever party that record targets. Then it reads A's holdings (`readStrandHoldings`).
2. The store releases the node (status `starting`). `removeFormerParty(plan, discard)` stops A, then reads B through `readPartyAlone(B, readFormerParty)`. That is `bringUp` with purpose `read`: `foundedStart(B)` in memory only, `strandFilter: none`, no listen addresses, no relay reservation, no debug hook, no owner step, no move adoption and no marker check. The read covers `exportStrandBundle` plus `listMembers()` without the tab's own peer id. The read node is stopped in a `finally`.
3. `formerPartyRefusal` (`unheldBundleContent` minus `discard`, plus other machines) produces a `FormerPartyNotEmptyError` when anything is left. Nothing is deleted in that case.
4. `removeParty` writes the marker `kv` `dissolving-party` = `{ v: 1, partyId: B }` and then deletes, in order: `deleteStore(controlStorageScope(B))`, the four `partyKvKey(key, B)` records (`PARTY_KV_KEYS`), B's move record, and `formerPartyId` from the start record. The marker goes last.
5. **The store starts A again in every case** (`startStoredParty`, same as a page load). This is a deviation from the ticket's wording, which placed the restart in `cadre-web.ts`. Here `removeFormerParty` always leaves no node running, and the store restarts. A refusal or failure is thrown after the restart; a failure of that restart is only the store's `error`. After a successful removal, a failed restart is both the store's `error` and the call's error.

**Marker at every start** (`bringUp` purpose `run` → `finishRemovalAtStart`):
- A marker naming another party finishes the deletions, and the in-memory start drops that `formerPartyId` whether or not the finish succeeded (the kit's rule).
- A failed finish is logged and kept in `getUnfinishedRemoval()` for the card, and the start continues.
- A marker naming the party being started is deleted with a warning.
- An unparseable marker is deleted with a warning.

**`deleteStore(key)`** (`strand-storage.ts`) closes this page's cached handle first, then calls `indexedDB.deleteDatabase`. On `blocked` it rejects with `StoreDeleteBlockedError` and does not wait. One branch here is not in the ticket. The blocked request is still queued in the browser, so a second `deleteDatabase` for the same name from this page would wait behind it, and the restart's marker check would then hang the start. The page therefore remembers blocked keys (`blockedDeletes`) and refuses a second delete of the same key at once. A key leaves that set when its request finally succeeds or errors.

**Owner standing on Retry.** "Retry moving" calls `finishStrandMove()` (`web-join.ts`). It first calls `wireJoinedOwnerKey(cadre, false)`, so a grant row that arrived after the join stopped waiting is picked up. It then reuses `settleJoinMove`, so adoption only runs when the key is wired. The ticket said "when its owner state is `enrolled`". This is the same rule plus that re-check, which the kit gets from `adoptStrandBundle` wiring the key itself.

**`switchToParty`** now writes the start as it runs (`requireStart()` after `bringUp`) rather than the pre-check `joined` object. Otherwise a join whose start finished a marked removal would write `formerPartyId` back.

**Page** (`join-flow.ts`, `join-cadre.svelte.ts`, `JoinCadre.svelte`). The new steps and wording follow the phone's `join-flow.ts`, with "this app" changed to "this tab", "chats" to "strands" and "this phone" to "this browser":
- `removing-old-cadre`
- `old-cadre-kept` (other machines: "…kept in this browser. Nothing was lost; you can ignore this.")
- `confirm-discard` (*Delete them* / *Keep old cadre*)
- `old-cadre-remains` (*Remove it now* / *Later*)
- `removal-unfinished`, which is web only. With `blocked` it reads "Close this site's other tabs to finish removing the old cadre."
- `move-incomplete` now offers *Retry moving* and *Later*.

The `done` standing is now the running node's (`ownerKeyWired()`), as the phone reads it from the kit, not `redemption.grantsOwner`. `resumeUnfinishedJoin()` runs on every `running` while the page is mounted, but acts once per start: it remembers the `PartyStart` object it last saw. That means *Later* is not undone by visiting another page and coming back; the flow returns only after the next start.

## How to exercise it

- **Happy path (automated):** `e2e/distributed/join-cadre.spec.ts`. A member join with an empty export goes join → removal → done. After a reload the start record is `{ v: 1, partyId: A, origin: 'joined' }` with no `formerPartyId`, `sereus-strand-control-<B>` is gone, and A's database is present.
- **Other machines in B (manual):** have a second machine join B first (Add a device or app in B), then join A from the tab. Expect "also has other machines (1), so it was kept", nothing deleted, A running, and the start record still naming B.
- **Unheld strand (manual):** needs a relay to found a strand with a control row. Leave or discard a moved strand in A, then *Remove it now*. Expect the confirm-discard question; *Delete them* removes B.
- **Move pending (manual):** join with an owner grant whose row arrives late, or kill the tab mid-adoption. On load the card shows `move-incomplete` with Retry; Retry adopts and then removes.
- **Closed tab mid-removal (by inspection):** marker written, then the tab closes. The next load's `bringUp` finishes the deletions before building A's node.
- **Two tabs (manual):** tab 1 joins A while tab 2 still runs B (not reloaded). Expect tab 1 to say "Close this site's other tabs…" with A running. Close tab 2, then reload tab 1 or use *Restart node*; the removal finishes.

## Known gaps and things to look at

- **Covered by reading only, with no automated test:** the refusal paths (other machines, confirm-discard, move pending), Retry, the resume on load, the closed-tab marker resume, and the two-tab `blocked` case. A browser e2e for refusals needs B to hold another machine or a control-row strand, and the latter needs a relay.
- **A `blocked` event that is not caused by another tab (unverified).** The IndexedDB spec fires `blocked` while any connection is still open, including one of this page's that is closing with a transaction still running. `stopCadre` awaits `node.stop()` before `closeStores()`, so none should be running, but I did not prove it. If it happened, the card would say to close other tabs when there are none. The database would still be deleted moments later, and the next start would finish the rest.
- **A restart failure after a successful removal shows `old-cadre-remains`** although B is gone, because no node runs to tell the two apart. The phone has the same limit. There is a `NOTE:` at `join-cadre.svelte.ts` → `flowAfterFailedDissolve`.
- **An old cadre kept on purpose is shown again after every reload.** There is a `NOTE:` at `resumeUnfinishedJoin`, the phone's equivalent tradeoff.
- `bringUp` is now exported with a `purpose` parameter. Only `readPartyAlone` passes `read`.
- Moved strands are still carried as rows and not opened by the tab (the existing accepted-tradeoff `NOTE:` beside `formedStrands`).
- The duplication backlog ticket (`debt-web-app-repeats-the-phone-kit-join-sequence`) now lists `web-join.ts` among its files.
