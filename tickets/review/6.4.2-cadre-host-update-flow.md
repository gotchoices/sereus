## Summary

Adds the update flow for the npm-installed path: signed-manifest fetch + verify, persisted user-facing state, npm-driven apply with rollback, opt-in auto-apply, and `cadre-host start` wiring. Notify-by-default; auto-apply is off unless the user enables it.

The local-UI ticket (6.5) consumes `createUpdateHandlers(service)` to wire the HTTP routes (`GET /update`, `POST /update/apply`, `GET/PUT /update/settings`) — handlers are typed and complete; only the Fastify-side wiring is deferred.

## What landed

### New module: `packages/cadre-host/src/update/`

- `types.ts` — `UpdateManifest`, `SignedManifest`, `UpdateState`, `UpdateApplyResult`, `UpdateErrorException`, `UpdateSettings`, error codes.
- `version.ts` — hand-rolled semver compare (incl. prerelease rules per §11; build metadata rejected).
- `release-key.ts` — embedded Ed25519 public key + `CADRE_HOST_UPDATE_DEV_KEY` env override. **The shipped key is a `AAAAAAAA…` placeholder**; the release operator must replace it before the first signed release. See "Gaps" below.
- `manifest.ts` — `fetchManifest()` (5 s connect / 10 s read), `verifyManifest()`, `canonicalJson()` (local sort-keys-no-whitespace impl), `signManifestForTesting()`.
- `store.ts` — `UpdateStateStore` (atomic JSON, same pattern as `TrustCircleStore`/`NatStore`).
- `apply.ts` — `applyUpdate()` with pluggable `NpmExecutor` and `ServiceRestarter`. Best-effort rollback to the previous version on install failure; restart failure is surfaced but doesn't trigger rollback (binary swap already succeeded).
- `index.ts` — `UpdateService` (composition root), `createUpdateHandlers()`, public re-exports.

## Use cases to exercise

1. **First start, no manifest endpoint** — point `CADRE_HOST_UPDATE_MANIFEST_URL` at `http://127.0.0.1:65535/nope` and verify `start` doesn't error out or print warnings (debug logs only). `update-state.json` stays empty.
2. **Available update visible** — sign a manifest with a dev key, stand it up on a local server, point the env var at it, and confirm `update-state.json` reads:
   ```json
   { "version": 1, "lastChecked": "...", "available": { "version": "0.7.0", ... } }
   ```
3. **Signature mismatch** — feed a manifest signed by a different key; confirm `update-state.json.lastError.code === 'signature_invalid'` and `available` stays unset.
4. **Manual apply** — call `UpdateService.apply()` (or `createUpdateHandlers(svc).postApply()`) with a fake `npmExecutor` and verify `applyInProgress` is recorded transiently and cleared on success.
5. **Rollback** — force the npm executor to exit non-zero on the first call; verify a second (rollback) call is made with the previous version.
6. **Auto-apply** — set `updates.autoApply: true` in `host.config.json`, run `check()` with an available manifest, and verify `apply()` is invoked.
7. **Settings persistence** — PUT `{ autoApply: true }` to `UpdateService.putSettings`; verify the in-memory setting flips AND `host.config.json` is rewritten with the new value.

## Gaps / honest flags

- **Placeholder release key.** `release-key.ts` ships a `AAAAAA…` 32-byte zero key. CI override via `CADRE_HOST_UPDATE_DEV_KEY` works; before the first signed release the operator must regenerate the prod keypair, paste the public half into `PROD_KEY_BASE64`, and tighten the release-tooling story (out of scope for this ticket; reviewer should file a follow-up if not already tracked).
- **Standalone-binary update path not in scope.** Only the npm path is implemented; the single-executable swap path is deferred to the standalone-binary backlog ticket as noted in the scope.
- **Service-host restart is fire-and-forget for the binary.** If `systemctl restart` returns non-zero, `apply()` returns success with `restartError` set; we do *not* roll the binary back, since the new version is already installed and the still-running old process is unaffected. UI surfaces the warning. Reviewer may want to confirm that's the right call.
- **No live `/update/*` HTTP routes.** The handler factory (`createUpdateHandlers`) is wired but the Fastify mounting lives in `6.5` per the original 6.4.1 split. The `host.ts` change includes a TODO pointing at the local-UI ticket.
- **24-hour timer is `unref()`d.** That's correct for `cadre-host start` (we want SIGTERM, not a stranded timer, to keep the process alive) — but if someone constructs `UpdateService` standalone in a script, the timer won't keep their script alive. Documented in source.
- **`npm install -g` requires the cadre-host user to own the npm global prefix.** On Linux distros that put the prefix under `/usr/lib/node_modules` without granting the user write access, `apply()` will fail with `EACCES`. The error surfaces cleanly via `lastError.message`, but the installer doesn't try to detect/warn about this on `cadre-host install`. Worth flagging in the local-UI banner copy.
- **Manifest endpoint URL is shipped as `https://releases.serfab.io/cadre-host/latest.json`** — that DNS record likely doesn't resolve yet. Treat as a "stub URL until release infra exists"; non-resolution falls into the silent-failure path so it doesn't break startup.

## Architectural notes for reviewers

- Mirrors the existing typed-handlers pattern (`createTrustCircleHandlers` / `createNatHandlers`). Errors thrown by `UpdateService.apply()` are `UpdateErrorException` with stable `.code` strings; the local-UI ticket maps these to HTTP statuses (similar to TrustCircleError).
- Canonical JSON is a tiny local impl, not a dep. The signed shape is fixed (`UpdateManifest`), so a recursive sort-keys + no-whitespace serializer is sufficient and avoids pulling in `json-canonicalize`.
- `compareVersions` is hand-rolled because `semver` is a 3-file dependency for a single call site. Rejects build metadata since releases shouldn't ship with it.
- Single-writer assumption: only one cadre-host process owns a given `dataDir`. Same assumption as TrustCircleStore / NatStore — no file-locking primitives.
