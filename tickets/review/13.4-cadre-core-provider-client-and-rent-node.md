# Provider client and `rentNode` in cadre-core: implemented, for review

Fourth ticket of the `provider-client-and-sign-up` chain. Everything lives under `packages/cadre-core/src/provider/` and is exported from the package root; every module uses global `fetch`, `URL`, `URLSearchParams`, `TextEncoder`, `@noble/hashes` (SHA-256 and `randomBytes`, which reads `crypto.getRandomValues` at call time) and `uint8arrays`, with no Node imports. The React Native Metro export and the web app's `vite build` both pass with the new graph. `docs/architecture.md` → "Renting a node from an app" is the design as built; read it first, then the code.

## What shipped

- **`provider/descriptor.ts`**: `ProviderDescriptor`, `parseProviderDescriptor(json)` and `fetchProviderDescriptor(url, fetch?)`. Refuses: not `v: 1`; blank `id` or `name`; an API URL (`apiBaseUrl`, `oauth.authorizeUrl`, `oauth.tokenUrl`, `plansUrl`) that is not absolute, or plain `http` at a host other than `localhost`, `127.0.0.1` or `::1`; `termsUrl` or `icon` that is not an absolute `http(s)` URL; `regions` or `oauth.scopes` that are not string lists; **and a descriptor without `oauth`**, since no app could sign in to it. The architecture doc says a provider with its own identity provider publishes a descriptor naming that provider's endpoints, so a published descriptor always has `oauth`; cadre-provider's own route omits it only when it runs no sign-in. The reviewer should confirm that reading.
- **`provider/oauth.ts`**: `pkceChallenge`, `createPkce` (43-character verifier), `createAuthorizationState` (16 random bytes, an addition so the kit does not mint its own), `authorizationUrl` (scopes default to the descriptor's), `readAuthorizationRedirect` (`{ code }` or `{ error, description? }`; `ProviderAuthError('state-mismatch' | 'missing-code')`; the code never appears in a message), `exchangeAuthorizationCode`, `refreshTokens` (form-encoded; a refusal is `ProviderAuthError` with the provider's `error` code; a response without `refresh_token` or a positive `expires_in` is `invalid_response`), and `createTokenSource`.
- **Token source**: refreshes within `TOKEN_REFRESH_MARGIN_MS` (60 s) of expiry and on `invalidate`, shares one in-flight refresh among concurrent callers, awaits `persist` after every refresh, and turns a refused refresh into `ProviderAuthError('reauthorize')` with the provider's error as `cause`; a network failure is rethrown as is. **Deviation**: `invalidate(stale?)` takes the token the 401 answered, and a refresh that already replaced it is not repeated, so two requests refused at once cost one rotation rather than two (the second would have spent a good pair). The client passes the token it sent.
- **`provider/client.ts`**: `ProviderClient` and `createProviderClient({ apiBaseUrl, tokens, fetch? })` with `createContainer`, `getContainer` (returns `{ container, health?, join? }`, `join` lifted from the record's `joinState`), `listContainers`, `deleteContainer`, `getBillingStatus` (undefined when the customer has no record), `getNodeCode` (`{ notReady: true }` on any 503, `ProviderApiError` otherwise). One request helper: bearer from `tokens.accessToken()`, a 401 answered once by `tokens.invalidate(sent)` and a retry, every other non-2xx a `ProviderApiError { status, code, message }` from `{ ok: false, error }`, including a 2xx `{ ok: false, message }` (what `DELETE` returns for a failed termination) and a non-JSON body (`HTTP_<status>`). ISO dates become epoch ms here (`createdAt`, `updatedAt`, `renewsAt`, `lapsesAt`). `health` is typed to the three fields an app reads (`status`, `peerId`, `multiaddrs`).
- **`provider/rent-node.ts`**: `rentNode(node, client, options?)` and `finishRental(node, client, containerId, options?)` as the ticket describes, with `RentNodeError` codes `not-an-owner`, `node-not-ready`, `container-gone`, and two the ticket did not name: `claimed-by-another` and `not-a-rental` (a container with no `join`, which `rentNode` never creates). `RentingNode` is `Pick<CadreNode, 'partyId' | 'isOwner' | 'invitationReach' | 'createCadreInvitation' | 'withdrawCadreInvitation' | 'claimNode'>`; `partyId` is new there, see the `finishRental` deviation below. **Addition**: `nodeCodePollMs` beside `nodeCodeDeadlineMs` (default `NODE_CODE_POLL_MS`, 2 s), so the poll is testable without a two-second wait. `DEFAULT_NODE_CODE_DEADLINE_MS` carries the lint directive `link-independent` with its reason (it bounds the container's start, not an exchange over the link).
- **`CadreNode.isOwner()`** is `enrolledOwnerSigningKey() !== null`: the identity key is wired as the owner signing key (`initializeSeedBootstrap`) and enrolled in the live `OwnerKey` set. This is stricter than the reference apps' old check, which asked only whether the identity key is in `OwnerKey`; a device whose key was enrolled but not wired for signing could not mint or claim anyway, so the stricter answer is the useful one. Both apps now delegate to it (`isOwnerDevice` in the React Native app, `isOwner` in the web app, whose `ownerPublicKey` variable and its import went away); their flows wire the key on every start, so nothing observable changes for them.
- **`CadreNode.invitationReach()`** and the private `selectInvitationMembers()`, which `createCadreInvitation` now calls for both its `members` and its `reach`, so the two cannot disagree. Throws before `start()`.
- **`fetch-impl.ts`**: the `resolveFetch` that `formation-approval.ts` had locally is now shared (`resolveFetch` returns undefined without a runtime `fetch`, `requireFetch` throws); formation-approval keeps its `misconfigured` error over it.
- **Docs**: `docs/architecture.md` gains "Renting a node from an app" (path choice, both paths, resuming, the token source), client-side names in "Provider descriptor and sign-in", `rentNode` in row 4 of "Which Side Dials", and a "Provider client API" line in the implementation status; the cadre-core README gains "Renting a provider node" and the two new `CadreNode` rows.

## Deviation the reviewer should weigh: `finishRental` on a `claimed` container

The ticket said `claimed → claimNode again`. That cannot work: the provider withholds the code once a live read folds the claim (`ContainerService.nodeCode` answers `409 ALREADY_CLAIMED`; README → Joining a cadre, step 1), and without the code there is no secret or address to claim with. As built, a claimed container is judged by party: `join.partyId === node.partyId` is done (`{ join: 'claim', peerId }`), anything else is `RentNodeError('claimed-by-another')`. A code request that meets `ALREADY_CLAIMED` mid-poll re-reads the container and applies the same rule. The consequence is a window the ticket wanted closed and this cannot close: an app killed between the node accepting the claim and the one local row `claimNode` writes afterwards has a node that is its owner's with no row for it on that machine. It is the same window the React Native app accepts for cadre-host claims (its `NOTE` in `use-cadre.ts`); the remedy is to delete the container and rent again. Recorded as a `NOTE` at `judgeClaimed` and stated in the architecture doc. The alternatives considered: widening `RentingNode` with `authorizePeer` and feeding it `health.multiaddrs` (writes the row, but `claimNode`'s dial-target retention is private and the addresses would be the node's raw list, not the code's public one), or asking the provider to keep serving the code to the owner that claimed (a provider change, outside this ticket). If the reviewer prefers one, it is a small follow-up.

## Use cases for testing, validation and usage

- **Store screen before sign-in**: `fetchProviderDescriptor(url)`; render `name`, `icon`, `regions`, a link to `termsUrl`, and plans from `plansUrl` (public). A dev provider at `http://127.0.0.1:3000` parses; one at `http://nodes.example` is refused.
- **Sign-in**: `createPkce()`, `createAuthorizationState()`, `authorizationUrl(descriptor, { clientId, redirectUri, state, challenge })`, open it, `readAuthorizationRedirect(returnedUrl, { expectedState })`, then `exchangeAuthorizationCode(descriptor, { clientId, redirectUri, code, verifier })`. Store the `ProviderTokens`; `createTokenSource({ descriptor, clientId, tokens, persist })` keeps them current and `persist` writes each rotation back.
- **Rent**: `createProviderClient({ apiBaseUrl: descriptor.apiBaseUrl, tokens })`, then `rentNode(node, client, { onProgress })`. A phone alone in its cadre takes the claim path (`creating`, `waiting-for-code`, `claiming`, `done`); the app shows a slow hint on `claiming`. With a joined always-on member announcing a public address, the second rental takes the invitation path (`inviting`, `creating`, `done`) and returns at once; the app watches `getContainer(id).join`.
- **Resume**: keep `containerId`; after a kill or `RentNodeError('node-not-ready')`, `finishRental(node, client, containerId)`. A failed invitation comes back as `{ outcome: 'failed', error, retryable }`: delete the container and rent again.
- **Lapse**: `getBillingStatus()` gives `subscription.status`, `renewsAt`, `lapsesAt` in ms; a stopped container's `stopReason: 'non-payment'` is on `getContainer`.
- **Token expiry mid-claim**: the client touches the token only per request, so the next request refreshes; a 401 is retried once after `invalidate`; a refused refresh surfaces as `ProviderAuthError('reauthorize')` from whichever client call ran, and the app signs in again and builds a new token source and client (the token source has no way to take a new pair; see gaps).

## Tests added, and what each verifies

- `test/provider-oauth.spec.ts`: the RFC 7636 appendix B vector and the 43-character verifier; `readAuthorizationRedirect` returns the code or the error and refuses a state mismatch without echoing the code; `parseProviderDescriptor` refuses `http://nodes.example`, accepts `http://127.0.0.1:3000` and `localhost`, refuses `v: 2` and a blank name; the token source shares one refresh among concurrent callers near expiry, persists once, makes no request while fresh, skips the rotation for a stale token already replaced and rotates for the current one, and reports a refused refresh as `reauthorize` with the provider's code as `cause`.
- `test/provider-client.spec.ts`: a 401 is retried once with the token `invalidate` returned (and `invalidate` is told which token failed); dates parse to ms; `join` and `health` are lifted from the answer; a 503 code request is `notReady`; a 409 is a `ProviderApiError` with the provider's code and message.
- `test/rent-node.spec.ts` (hand-written `RentingNode` and `ProviderClient`, no module mocks): reach `anywhere` mints one `{ grantsOwner: false, uses: 1, expiresInMs: 15 min }` invitation, creates with `kind: 'invitation'`, never asks for a code or claims, and reports `inviting, creating, done`; reach `issuer-only` creates with `kind: 'claim'`, polls the code through one `notReady`, claims with the decoded payload (peer id, addresses, secret) and reports the four claim steps; a failed create on the invitation path withdraws the invitation by key and rethrows the create's error.
- `test/cadre-node-cadre-invitation.spec.ts` (two assertions in an existing real-node case): `isOwner()` is true on a started owner node, and `invitationReach()` equals the `reach` of an invitation minted at the same moment (`issuer-only` for a node alone).

## Known gaps

- **`finishRental` is untested** beyond typecheck: its branches (gone, claim awaiting, claimed ours, claimed by another, invitation pending/accepted/failed, `ALREADY_CLAIMED` mid-poll) are straight projections over `getContainer`, but a reviewer may want one table-driven case over the same fakes `rent-node.spec.ts` uses.
- **Nothing has run against a live cadre-provider.** The wire shapes were taken from the architecture doc and the provider README, cross-checked against `routes.ts`, `types.ts` and `container-join.ts` where the doc was silent (the `{ ok, data }` envelope, `DELETE`'s `{ ok, message }`, `joinState` absent until the first live read, the 409 codes). `reference-app-rn-rents-a-provider-node` is the first real run.
- **No per-request deadline in the client.** A provider that accepts the connection and never answers hangs the call; React Native's `fetch` has its own timeout, Node's does not. `formation-approval.ts` has the budgeted-fetch pattern if one is wanted; left out because the ticket named none and a poll loop under a deadline already bounds the claim path.
- **The token source cannot take a new pair.** After `reauthorize` the app builds a new source and client; cheap, but an app holding the client in state must replace both.
- **`health` is partial** (`status`, `peerId`, `multiaddrs`); strand counts and the node's claim fields are dropped at the boundary. Add fields when an app reads them.
- `createPkce` and `createAuthorizationState` need `crypto.getRandomValues`; the React Native kit polyfills it (`rn-kit-polyfills`), and `@noble/hashes` throws a clear error without it.
