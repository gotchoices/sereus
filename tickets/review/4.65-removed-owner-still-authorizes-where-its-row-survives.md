# A retired `OwnerKey` row authorizes nothing (review handoff)

## What changed

**The invariant, applied at every owner lookup in `schemas/control.qsql`.** Each `exists (select 1 from OwnerKey A where A.Key = context.OwnerKey ...)` gained the conjunct `not exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = A.StampId)`, placed before `verify(...)` so a retired row never pays the signature check. 25 sites: the 22 live-table lookups (21 of one inline shape plus `Revocation.AuthorizedReissue`, whose lookup spans two lines), the two `committed.OwnerKey A` signer branches of `OwnerKey.Authorized` (signed add, remove), and the `committed.OwnerKey K` issuer clause of `CadreInviteUsage.Authorized` (bound on `K.StampId`). Every site reads live `Revocation`, so a tombstone filed in the same transaction also disqualifies.

**Left raw, deliberately, as the ticket asked.** The founding count `(select count(1) from committed.OwnerKey) = 0` (a machine holding only a retired owner row must still be refused a second genesis; the constraint comment now says so), `MinOneOwner`, `ControlDatabase.hasOwnerKey`, `queryStampId` and the insert-if-absent guards.

**The embedded copy** `packages/cadre-core/src/control-schema.ts` was regenerated from the `.qsql` by a script that escapes backticks, backslashes and `${`, so the two cannot differ except by line endings. `control-schema-drift.spec.ts` passes.

**Docs and comments.** Schema header paragraph (every owner lookup drops retired rows at the write checks; only the founding count stays raw); the founding-count comment; the `CadreInviteUsage.Authorized` NOTE (a tombstone alone now takes an issuer's outstanding invitations with it); `docs/architecture.md` `OwnerKey` row and the "What the derivation cannot settle" paragraph (the "indefinitely from any machine that received its tombstone without the delete" clause and this ticket's slug are gone); the `getOwnerKeys` JSDoc is a read-side statement only; the anchor scenario's header sentence points at the schema clause and the unit test instead of this ticket.

**Tripwire recorded** as a `NOTE:` in `CadreNode.drainPendingRevocations`'s failure branch: a removed device that keeps running attempts its owner-signed re-touches on every growth edge and now fails the live-owner clause each time. Noise, not harm; shutting down on learning of one's own revocation belongs to plan ticket `remove-a-device-or-app-from-a-cadre`.

## Tests

| test | verifies |
|---|---|
| `control-revocation-replay.spec.ts` → "OwnerKey: an owner removed in the same transaction cannot vouch an add there" | In one transaction the founder removes owner B (delete plus tombstone) and B signs the add of a stranger. The signer is read from `committed.OwnerKey`, where B still is; the live `Revocation` read disqualifies it. Red before the change (the transaction committed and the stranger was seated), green after, with `CHECK constraint failed: Authorized` and the whole transaction rolled back. |

**Why this is the one test, and why it is not the one the ticket specified.** The ticket asked for an integration scenario: owner B removed while A is alone, B restarting on its own storage holding its own `OwnerKey` row, receiving only the tombstone, and then being refused an owner-signed `removePeer`. I built it exactly as specified and ran it against the unchanged schema first. It passed phases 1 and 2 and failed its own premise at phase 3: once the tombstone had reached B, B's raw `select StampId from CadreControl.OwnerKey where Key = ?` returned no row. The row did not survive beside the tombstone on the removed machine. Two mechanisms explain it and neither is this ticket's to change: the peer-join block catch-up pushes the remover's whole control store to a reconnecting peer (`peer-join-backfill.ts`, "copies the WHOLE local store to every newly connected peer"), so A's newer `OwnerKey` revision, with B's row deleted, arrives with the tombstone; and a read through B's database can answer from A's storage as coordinator, or adopt A's revision through lazy read-repair (`block-store-probe.ts` header). So in a two-machine party where the remover is reachable, the removed device converges on its own removal, delete included, and the pre-change schema already refused it because the row was gone. The row-plus-tombstone state needs the removed machine's `OwnerKey` block to have diverged (a write to it while apart), and that is the forked-collection case `tickets/blocked/forked-control-collection-sync-livelocks.md` documents as not making forward progress upstream, so a scenario built on it would fail on the fork before reaching the check. I removed the scenario file rather than ship a test that passes before and after the fix. The one-database shape above is the only row-beside-tombstone state a single database can hold (`RowIsGone` and `NotRevoked` keep the committed state free of it), and it exercises the new conjunct's defining property, that live `Revocation` is read beside the snapshot. The 22 live-table sites carry the identical conjunct text and have no automated repro; the reviewer should weigh that gap rather than ask for the integration scenario.

## Consequences the reviewer should know

- **Existing parties are recreated.** Constraint text changed on every guarded table, so a control store written by an earlier build fails its warm start (`ALTER TABLE ... DROP CONSTRAINT` is refused by the optimystic module). Expected under the no-backwards-compatibility policy; nothing to do.
- **`docs/architecture.md` → "Deletes made while alone" still says a sibling that holds the removed row "retires its stamp ... even though the row is not physically deleted there."** My one run observed the opposite through the removed machine's database (its view converged on the delete), but a read through the database proves visibility, not storage, so I did not touch that text. If the reviewer wants it settled, the probe is `readBlockIndex(storeB)` on the `OwnerKey` block's revision before and after the reconnect, never a `select`.
- Plan ticket `4.7-control-approvals-bound-to-party` edits the same digest lines and should rebase onto the live-owner form, as the implement ticket said.
