# Empty environment variables no longer override configured values

## What was wrong

`applyEnvironmentOverrides` (`packages/cadre-cli/src/config/loader.ts`) treated any *defined*
env var as an override, including empty string (`FOO=`). Docker Compose's `${VAR:-}` syntax sets
unset optional vars to `''` rather than leaving them unset, so every optional var in
`packages/cadre-cli/docker/docker-compose.yml` (e.g. `CADRE_ENABLE_RELAY=${CADRE_ENABLE_RELAY:-}`)
silently reintroduced `false`/`[]`-style overrides on every container start, clobbering values the
node's own config file had set. `entrypoint.sh` was already correct (guards with `[ -n "$VAR" ]`);
the bug was solely in this CLI-side override pass, which ran after the file loaded and stomped
what the entrypoint had correctly omitted.

## Fix (already implemented, commit f0e262f)

The override loop in `loader.ts` now skips a var when `undefined` **or** `value.trim() === ''`,
before any per-variable parsing — one guard, applies uniformly to every `ENV_MAPPINGS` entry
(`packages/cadre-cli/src/config/types.ts`): scalars, `_NODES`/`_ADDRS` lists, `_ENABLED`/`_RELAY`
booleans, `CADRE_STRAND_FILTER`, `CADRE_PUSH`.

Two parser helpers (`parsePushEnv`, `parseStrandFilterEnv`) had their own empty-string
special-casing (return `undefined` / `'all'` respectively). That branch inside each is now dead
code given the loop-level skip — confirmed by checking call graph: both are only reachable via
`parseEnvValue`, which is only called from the loop, which now guarantees non-empty input. The
dead branches (and doc-comment lines describing the old per-parser behavior) were removed; the
functions themselves remain — they still do real JSON parsing, not just empty-string handling.

## Scope check (done, no action needed)

`packages/cadre-host/src/orchestrator/host-process-orchestrator.ts` (spawns the CLI as a child
process) builds the child's env explicitly rather than blanket-passing optional vars with
empty-string defaults — doesn't exhibit this bug. Grepped the rest of `packages/` for
`applyEnvironmentOverrides`/`parsePushEnv`/`parseStrandFilterEnv`: only referenced inside
`cadre-cli`'s own source + tests, so the fix is fully contained. The separate concern of *ambient*
env leaking from a host process into a spawned child is already tracked by
`tickets/plan/22-debt-host-child-env-inheritance.md` — not duplicated here.
