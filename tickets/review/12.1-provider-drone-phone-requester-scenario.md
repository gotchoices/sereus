# Review: a phone-shaped requester rents a provider node

## What landed

**The scenario:** `packages/integration-tests/src/scenarios/provider-drone-phone-requester.integration.ts`. The provider side is an in-process `ContainerService` + `MemoryStore` + `ProviderProcessOrchestrator` spawning a real `cadre-cli` child from the provider's own `buildNodeEnv`. The requester is an in-process phone-shaped `CadreNode` (`listenAddrs: []`, WebSocket + circuit-relay only, `transaction` profile, its own owner). It has six ordered `it`s:

1. The requester is up, and `getMultiaddrs()` is `[]`.
2. `createContainer` with `bootstrapNodes: []` and `pinnedOwnerKeys: [requester's owner key]` reaches `running`.
3. `getPeerInfo` contains both announced addresses, `/dns4/localhost/tcp/<p2p>/p2p/<id>` and `/dns4/localhost/tcp/<ws>/ws/p2p/<id>`.
4. `addDrone` with the peer info's addresses unfiltered, then `ContainerService.applySeed` (retried until success, since the seed route can lag `/status`) is accepted.
5. After `reconcileControlCohort()`, the requester holds an OUTBOUND connection and the node's `/status` reports a WebSocket connection. The requester's peer id is in the node's authorized member set, read over the child's loopback admin channel. `getMultiaddrs()` is still `[]`.
6. `terminateContainer` returns true, the record reads `stopped`, the child process is down, and the orchestrator has forgotten the handle.

**Harness changes:**

- `ProviderProcessOrchestrator` options:
  - `publicHost` computes `appendAnnounceAddrs` with cadre-provider's `publicNodeAddrs(publicHost, ports)` and passes it to `buildNodeEnv`, as `DockerOrchestrator` does.
  - `adminChannel` (test-only, documented as layer 5 of the env) adds `CADRE_ADMIN_PORT` + `CADRE_STARTUP_TOKEN` and records `{ port, token }` on the handle.
- New `orchestrator.logTail(containerId)`. It reads the volume's `node.log` directly, so it still works after a failed provision forgot the handle.
- New exported `requireContainerRunning(containers, orchestrator, id, label, timeoutMs)`. This is `provider-seed-accepted`'s local `requireRunning`/`tailNodeLog` pair hoisted; that file now uses it.
- `buildPhoneOwner(partyId, bootstrapPeerStore?)` is hoisted into `node-fixtures.ts`. The ticket named three copies, but the donation scenario it cited no longer exists (deleted with the donation feature in `cadre-host-hosted-nodes-join-by-qr`). The two remaining copies, `cadre-host-join-by-qr` and `node-claim-by-phone`, differed only in whether the store parameter was optional, so the hoisted version is the optional-parameter superset. Both files now import it.
- `adminClient` in `owner-cli-node.ts` is now exported, so the scenario reuses it instead of adding a third admin-request helper.

**Docs:** `docs/testing.md` lists the scenario in the cross-process index and gives it its own bullet. It also names `buildPhoneOwner` and replaces the old index's "the two bullets below", which pointed at a `provider-seed-accepted` bullet that does not exist. `docs/architecture.md` adds a key point under "Phone Adds Provider Drone" naming the scenario as the proof and stating what it does not yet check.

## Deviations from the ticket, each deliberate

- **Step 5's node→requester half is not asserted.** The ticket wanted the node's self-published `CadrePeer` record to resolve on the requester. Measured with the child's `sereus:cadre:node` debug log:
  - Run 1: nothing resolved in 90 s.
  - Run 2: the seed landed 0.74 s after the node started, and the node's one-shot publish 1 s after start found the replicated row.

  A seeded node, which has no owner key, publishes again only on the 7.5-minute heartbeat. The reconcile-pass retry exists only for claimed nodes (`publishSelfRecordOnceClaimed`). Fixing it in cadre-core would add a background `CadrePeer` write on member nodes across the control and strand suites, and `blocked/forked-control-collection-sync-livelocks` already suspects that kind of write of racing foreground writes. Validating the change therefore needs a full integration run, which is longer than an agent run allows. I filed **`tickets/fix/seeded-node-publishes-its-address-record-late.md`** (repro: verified) with both fix options and their blast radius, and a `NOTE:` at the step-5 site names it. That ticket owns adding the assertion back, with the seed delivered after the 1 s one-shot so the assertion cannot pass by luck.
- **Public host is `localhost`, not `127.0.0.1`.** The child binds `0.0.0.0`, which libp2p already reports as `127.0.0.1` among its addresses. With `127.0.0.1`, step 3 would pass even if `CADRE_APPEND_ANNOUNCE_ADDRS` never reached the node, which defeats the ticket's stated reason for the step. `hostComponent('localhost')` gives `/dns4/localhost`, which only an announced address can produce.
- **No port band.** `ProviderProcessOrchestrator` takes OS-assigned ports (`allocFreePort`). The band convention in `port-allocator.ts` is for `HostProcessOrchestrator`, which needs fixed ranges. The testing.md bullet says so.
- **`deleteContainer` is `terminateContainer`**, `ContainerService`'s actual name.
- **The requester's identity is not kept for a restart**, and no bootstrap store is held outside the node. Restarts were out of scope.

## Known gaps for the reviewer to weigh

- **Step 5 does not pin which address the requester dialed.** It gets every address in the peer info: the bound `/ip4/…/ws` ones and the announced `/dns4/localhost/…/ws`. All of them reach the same listener here, so the scenario proves "dialable over `/ws` from the peer info", not "dialable at the announced address specifically". Pinning that would mean handing `addDrone` only the announced pair, which the ticket said not to do (no address filtering).
- **`/dns4/localhost` depends on the requester's WebSocket dial resolving `localhost` to an IPv4 loopback.** That held on Windows here. It only matters if the dialer ever picks that address and the OS answers `::1` first; the bound `/ip4` addresses are tried as well.
- **The admin channel is a test-only addition to a provider-shaped child.** It binds one more loopback port and changes nothing on the libp2p side, but it is an environment the provider never produces.
- `logTail` and `getLogs` both read `node.log`. They are kept separate because `getLogs` mirrors `docker logs`, which refuses a removed container, while `logTail` is for failure messages and must never throw.
