# A strand commit's durability reaches the app

GitHub gotchoices/sereus#44 / optimystic#26. Optimystic's release candidate (`1b352916`, linked through root `resolutions`) reports, per SQL commit, who holds what it wrote, and later when a commit held only below full replication becomes held by its whole cohort. This ticket passes that through to the app. The contract is written up in `docs/strands.md` → "A commit's durability"; read that first.

## What was built

- **`@serfab/quereus-plugin-sereus`**: `SereusPluginResult` gains `onCommitDurability` / `onCommitFullyHeld`, forwarded from the Optimystic plugin; the `SqlCommitDurability` and `CommitFullyHeld` types are re-exported. `releaseOptimysticPlugin` (was `releaseCollectionFactory`) now disposes the plugin's transaction bridge before releasing the collection factory, on both `shutdown()` and the failed-composition `catch`. It calls `txnBridge.dispose()` directly, not the plugin's `dispose()`, because on the created-node path `collectionFactory.shutdown()` already ends with `collectionFactory.dispose()`. README paragraph under "With an injected node".
- **`@serfab/cadre-core`**: new `strand-commit-durability.ts` holds the `StrandCommitDurability` / `StrandCommitHeld` types, the `heldElsewhere` rule (overall `durabilityRank` ≥ `majority`), and `StrandCommitRecord`. That is a bounded map of the last 256 commits by transaction id, with frozen entries that are replaced when a commit becomes held. Forwarding to the app handlers is try/catch-isolated and logged. `StrandDatabase` subscribes right after `connectToStrand` returns (before the founder bootstrap), unsubscribes first thing in `close()`, and exposes `commitDurability(tx)`. `StartStrandConfig` gains `onCommitDurability` / `onCommitHeld`. They ride with the launch config like `onWritable`, so a hibernation wake's rebuilt database is wired too. `CadreNode` emits `strand:commit-durability` / `strand:commit-held`. The types are exported from the package index.
- **Docs**: new `docs/strands.md` section "A commit's durability". The "Writable does not mean connected" bullet now links to it.

## How to use / validate

- App pattern: `const { Tx } = await db.get("insert into App.X (…) values (…) returning StampId() as Tx")`, then `instance.database.commitDurability(Tx)` → `{ heldElsewhere, followed, report }`. Listen for `strand:commit-held` on the `CadreNode` to clear a "not yet delivered" mark.
- End-to-end check: `yarn workspace @serfab/integration-tests exec vitest run joiner-first-commit-over-slow-relay -t "tells the writer"` (about 25 s). Founder and joiner sync, then the joiner stops. Once the founder's strand node drops the connection, the founder writes one row and must report `{ heldElsewhere: false, followed: true }`. The joiner then restarts over its kept storage, and the founder must emit `strand:commit-held` for that id within 180 s, after which `commitDurability` reads `heldElsewhere: true`. On failure it prints the founder's record and whether the restarted joiner holds the row.

## Known gaps and things to look at

- **This code requires the Optimystic RC at runtime, and the floors still say `^1.12.1`.** Against published 1.12.1, `StrandDatabase.initialize` would throw (`result.onCommitDurability` is forwarded to a plugin method that does not exist), and so would release, since `txnBridge.dispose` is new in the RC. Sereus must not be published until the Optimystic release is adopted and the floors raised. That step lives on `blocked/optimystic-write-made-alone-owes-no-one`. Floors were not edited here, as the ticket said.
- **The stopped member was not named as owed.** In the new arm the founder's write with the joiner stopped came back `confirmed 1 / cohort 1`, `unconfirmed []`, unlike the upstream lifecycle spec's phase 5 (`unconfirmed: [B]`). It was still followed and reported held once the joiner returned, so the assertion holds. One dated line was added to the blocked ticket's findings.
- **Slow-link joins stalled in 3 of 5 runs** (third, fourth and fifth arms, which share the 20 ms frame cap and 70%-busy event loop). A DEBUG run shows the joiner's strand node reconnecting to the founder and losing the circuit again 12–20 s later for the whole run, with every `Strand.Header` probe failing `cohort-unreachable`. The joiner commits nothing while gated, and this change adds no network traffic, so I believe it is the harness relay's circuit cutting, not this change. No baseline was run without the change, so that is reasoned, not measured. The evidence was appended to `backlog/debt-libp2p-nodes-built-outside-cadre-core-miss-the-ping-defaults` (third arm). The fourth and fifth arms are plain `it`s and fail when this happens; `.pre-existing-error.md` was not written, because no run of those two finished failing (I capped them).
- **Release order.** `StrandDatabase.close()` still releases the plugin before `db.close()` (unchanged order; the Optimystic README says to dispose after closing). The bridge's follower re-subscribes at the start of any transaction, so a write begun between release and close would leak one subscription. A `NOTE:` tripwire sits at `releaseOptimysticPlugin`.
- **Commits made during `connectToStrand`** (the schema applies) come before the subscription, so they are neither reported nor followed. Apps never hold those ids.
- **`heldElsewhere` and torn commits.** The rule counts `majority` even when the commit has `torn` blocks (those blocks are held nowhere). I did not check whether a SQL commit with torn blocks can succeed at all, or whether it always throws; the reviewer may want to.
- `cadre-node.ts` additions are two wiring lines (it is the subject of `backlog/debt-cadre-node-single-file-size`).
