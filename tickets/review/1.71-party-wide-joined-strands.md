# Joins from other parties are recorded party-wide

## What was built

A strand joined from another party now has two records:

- **Party-wide:** a `CadreControl.JoinedStrand` row (the table from the prereq). Once it exists it is the authority. Every machine's strand watcher offers it, a storage replica host launches it, and the party's other devices get `strand:discovered` for it.
- **Machine-local:** the existing `KeyStore` record (`JoinedStrandStore`), now a queue of joins not yet published. It is forgotten as soon as the party-wide row for that id is visible.

`joined-strand-store.ts`:
- `PartyJoinedStrandLedger`: the seam over the table (`list`, `names`, `canSign`, `publish`, `remove`). `CadreNode.createPartyJoinedStrandLedger` implements it over `ControlDatabase`, and reads `this.controlDatabase` at call time.
- `JoinedStrandRows` is renamed `JoinedStrandSession`, because it now also publishes and removes. Its methods:
  - `withControlRows`: precedence is control `Strand` rows, then party-wide rows, then local records, then session-kept entries. A local record named by either table is forgotten. The party-wide read keeps its own last-good fallback.
  - `remember` (used by `formStrand`) and `rememberForeign` (used by `addStrand`; this is the old `rememberForeignStrand` body, with `queryStrand` replaced by `ledger.names`). Both cancel a queued removal.
  - `leave`: removes the party-wide row first, then the local record.
  - `forgetAfterThisSession`: seeds the session-kept entry from the local record or from the last party-wide list, and queues the id for removal.
  - `syncWithParty`: publishes each local record, then removes the queued ids. Failures are handled per strand and the record is kept for the next pass.

`cadre-node.ts`:
- `reconcileControlCohort`'s connected branch calls `joinedStrands.syncWithParty()` after the ledger-marker step, inside a try/catch that logs.
- `forgetJoinedStrand` calls `leave`, so leaving is party-wide. It throws on a non-owner machine when a party-wide row exists.
- `forgetRevokedJoin` carries the accepted-tradeoff `NOTE:` about sibling machines.

## Deviations from the ticket (please weigh)

- **The owner gate is stricter than `canAuthorize()` alone.** `enrolledOwnerSigningKey()` requires `seedBootstrapService.canAuthorize()` **and** that this machine's signing key is in `getOwnerKeys()`. Reason: the reference apps' `runOwnerGenesis` gives every phone a seed-bootstrap owner key, including a second phone that is not an enrolled owner. With `canAuthorize()` alone, that phone would try a refused insert every 15 s, and its `forgetJoinedStrand` would fail with an opaque schema error instead of the descriptive one.
  - The owner-key read happens only when there is work to do: local records or queued removals.
  - This added a `canSign()` method to the seam the ticket suggested.
- **`forgetJoinedStrand` throws when the party-wide table cannot be read**, even for a join that exists only locally, because it cannot tell whether a party-wide row exists. Example: an isolated machine that never received the `JoinedStrand` block (`cohort-unreachable`). This is documented in its `@throws`. The alternative would be to forget locally and hope, which could leave the party-wide row in place while the user believes they left.
- **A removal is queued even when the revoked join exists only locally.** A publish of it may be in flight. Cost: one `deleteJoinedStrand` that finds no row and returns false.
- **`rememberForeign` cancels a queued removal before its early returns.** So any rememberable `addStrand` of the id cancels it, including when the party-wide row already exists.
- **Session-kept entries named by a party-wide row are kept, not dropped.** They are what keeps the strand offered after the owner pass removes the row. Only a control `Strand` row drops them.
- **Existing residual:** `getControlConnectionCount` counts a relay or bootstrap connection. So a solo-party owner connected only to a relay publishes its joins, and those writes are effectively local-only. This is the same residual the reap and the ledger marker already accept.

## Tests

In `joined-strand-store.spec.ts`, the old two `JoinedStrandRows` cases are replaced, for a net gain of one test:
- **Union and drain.** Control `[a]`, ledger `[a, b]`, local `[a (stale), b, c]`.
  - Offers `a` (the control version), `b` (the ledger version) and `c`.
  - The store keeps only `c`. This covers both drains: a local record named by a control row and one named by the ledger.
  - With `list` throwing, `b` is still offered.
- **Publish loop.** Local `[d, e]`, and the ledger refuses `e`. After `syncWithParty`, the store holds `[e]` and the ledger holds `[d]`.
- **Revocation (existing case, moved onto the party-wide path).** The ledger holds `r`, and a poll seeds the last-good list. Then `forgetAfterThisSession` and `syncWithParty` run:
  - the ledger row is gone;
  - this session still offers `r`;
  - a fresh session does not.
- The node-level restart case (`re-offers a formed join after a restart…`) is unchanged and passes. It now exercises a local-only join, and `forgetJoinedStrand` with no party-wide row.
- `MapLedger` is an in-test stand-in over a `Map` for the seam. It is not a mock of `ControlDatabase`.

**Not unit-tested at node level (by the ticket's design):** the adapter, the reconcile wiring, and the non-owner throw. I checked them once with a throwaway spec against a real owner node and deleted it. It confirmed:
- `syncWithParty` lands the row;
- a repeat `publish` resolves through the id-conflict path;
- the watcher offers the row as `strand:discovered`;
- `forgetJoinedStrand` deletes the row and files a `JoinedStrand` tombstone;
- a node whose key is not an enrolled owner throws `/takes an owner machine/` and keeps the row;
- a local-only leave on that node succeeds.

The end-to-end path (a phone publishes, the always-on machine hosts, the phone leaves, the always-on machine stops) belongs to `scenario-always-on-hosts-cross-party-join`.

## NOTEs added

- Accepted tradeoff at `forgetRevokedJoin`: a sibling machine detaches the strand on revocation. Also stated in `docs/strands.md`.

- At `JoinedStrandSession.publish`: a leave can race a sibling's pending publish.
