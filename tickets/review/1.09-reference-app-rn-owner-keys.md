# React Native reference app: owner keys — review handoff

The spec is `docs/reference-app-rn.md` → **Owner Keys** (new section after Devices and Nodes), written first and then built. Read it before the code; it states every line the user sees.

## What was built

**Settings → Owner keys** (`src/owner-keys-section.tsx`), mounted below Devices and nodes while connected:

- **List** from `listOwnerKeys`: title = label or "Unnamed key"; facts = 8-character fingerprint (`node-claim.ts` `ownerFingerprint`) plus "This device" on `heldHere`; "Not trusted here" when not `trusted`. Read on appear, on node change, when `ownerPublicKey` changes (an import wired a key), after each action here, and on Refresh. Stale reads are dropped with a `nodeRef` comparison.
- **Make a backup key** (owner only): form with Name (default "Backup"), "Protect with a passphrase" (on), passphrase twice. `exportFormProblem` disables the button and says why (empty passphrase with the toggle on, mismatch, name over 64). Then `addBackupOwnerKey`, and the export view.
- **Export this device's key** (owner, and a listed row is `heldHere`): same form, name defaults to the key's label, `exportOwnerKey`. On a device that is an owner only through the identity key an owner-granting invitation seated, the kit throws "holds no owner key of its own", shown in the alert.
- **Export view** (shown once until Done): the warning text from the ticket above a `ShareCode` (QR, Copy, selectable text), plus **Share** (RN core `Share.share`, no new native module) and **Done**.
- **Import** (offered to members too): paste or Scan; a locked prefix shows a passphrase field; `importOwnerKey`. Outcomes go through `importOutcome` (`owner-keys.ts`), which reads `listOwnerKeys()` after the import to tell the review's two `wired: false` cases apart: listed → "uses it from the next start", not listed → "This key is not an owner of this cadre. An owner can add it." Slot occupied and wrong passphrase are refusal alerts (`describeOwnerKeyFailure`).
- **Remove** (owner only, never on the `heldHere` row, which shows "A device cannot remove its own owner key; use another owner key."): `planOwnerKeyRemoval`, then a prompt with one **Keep** switch per dependent (`dependentRows`: devices named as Devices and nodes names them via an extra `listMachines` read, falling back to the short peer id; owner keys by label and fingerprint). Also an `ownDependency` line, the `last-owner` refusal text, and `removeOwner(key, { revouch: revouchOf(rows, kept) })`. A removal refused as `unknown`, or answering `removed: false`, shows "Already removed".
- `alone` refusals (backup, and re-vouching a key during removal) have their own lines.

**Elsewhere:**

- `machine-removal.tsx`: the removal prompt shows the lost-phone line and **Go to Owner keys**. That button closes the prompt and scrolls Settings to the section (`ScrollView` ref + the section's `onLayout` y in `app/settings.tsx`). The line and button show only when the caller passes `onShowOwnerKeys`: Devices and nodes passes it; the provider section's removal of a rented node does not, since a rented node never holds an owner key. `SELF_LINE` now says why: "A device does not remove itself from its cadre: to remove this device, use another owner device."
- Add-node and provider-rental approval prompts show **Owner key** "‹label› (‹fingerprint›)" via `SigningKeyFact` (reads `listOwnerKeys` when the prompt opens; fingerprint alone until then or on failure). The add-node prompt no longer takes `ownerPublicKey` as a prop.
- `CodeScanner.otherCodeHint` may be a function of the scanned text. The owner-key scanner shows the owner-key decoder's own refusal, which names an invitation, join request or node code. The join and add-device scanners show "That is an owner key, which is private. Import it only under Owner keys." for an owner-key QR. Pasted text in those fields already got the decoders' by-name refusals.
- `useOwnerStanding` and `AddDeviceSection` re-read the owner standing when `cadre.ownerPublicKey` changes, so an import that wires a key unlocks the owner-only sections without a reconnect. `use-cadre.ts` `importOwnerKey` sets `ownerPublicKey` afterwards.
- `settings-controls.tsx`: `LabelledInput` takes `secureTextEntry`. `useExclusive` (the one-action-at-a-time guard with a same-frame ref) was lifted out of `machine-removal.tsx` and is now used by both.
- `cadre-phone.ts` / `use-cadre.ts`: thin pass-throughs for the kit's six owner-key calls.
- Docs: `reference-app-rn.md` gets the new section, the package listing, the Devices and Nodes wording (lost-phone line, self line reason, Uses bullet), and the add-node and rental approval prompts. The `architecture.md` Owner Keys status note now names only the web app's screen as remaining.

## Small fix made in passing

`useMachineRemoval.request` compared `cadre.node` with itself after an await (both read from the same render's closure), so a plan arriving after a join replaced the node was never dropped. It now compares against a `nodeRef`, as the section files do.

## Tests

- `test/owner-keys.spec.ts` (new, 2 tests):
  - `importOutcome` tells "wired", "listed but another signer is wired (next start)" and "not an owner" apart. This pins the arm the prereq's review filed on this ticket.
  - The removal's Keep switches: `dependentRows` names devices and keys, including both fallbacks, and `revouchOf` re-vouches exactly the switched-on rows, split into `peers` and `owners`. This mapping decides which devices stay members.

## Known gaps — reviewer, please weigh

- **No Maestro flow.** `maestro/flows/` is reused verbatim by `reference-app-ns` (its `run-e2e.mjs`), which has no Owner keys UI, so an RN-only flow there would fail the NS run unless every step were conditional. No device or emulator is available here, and the RN drone fixture hang is pre-existing and already triaged. Not covered: making a backup with a passphrase, seeing it listed, then removing it.
- **Screen capture.** I did not add `expo-screen-capture`: it is a new native module (needs a dev-client rebuild and a network install into a workspace whose `node_modules` links sibling repos). It is recorded as a known exposure in the doc and as a `NOTE:` at `ExportView`. Filed `tickets/backlog/feat-rn-owner-key-export-hidden-from-screen-capture.md`. If the reviewer thinks it belongs in this ticket, that is the place to say so.
- **Export shown when the device signs with the identity key.** The Export button keys off a `heldHere` row, so a device whose wired signer is the invitation-seated identity key sees it, and gets the kit's "holds no owner key of its own" alert. Telling that case apart up front would need the slot read the kit does not expose, or comparing the signer with the machine identity key, which the architecture forbids ("no code finds an owner key from a peer id").
- **A backup export lost with the section.** If the node stops while a backup's export is on screen, the section unmounts and the export is gone. The key stays an owner nobody holds until removed here. Recorded as a `NOTE:` at the component.
- **Double list read after an import that wires**: the import's own refresh, plus the `ownerPublicKey` effect. Harmless.

  - the `alone` refusals
  - the passphrase form checks
  - the scroll to Owner keys
  - the scanners' by-name lines
  - the `ownDependency` line
