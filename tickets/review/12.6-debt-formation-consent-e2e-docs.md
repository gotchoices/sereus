# Review: joiner-consent end-to-end re-verification + documentation

Implements `12.6-debt-formation-consent-e2e-docs`. Two independent parts: one new integration
case, and doc corrections. Sibling `debt-formation-consent-signature-matrix` (already through
review) owns the schema-level negative matrix; nothing here overlaps it.

## What landed

### Part 1 — end-to-end assertion

`packages/integration-tests/src/scenarios/strand-formation-e2e.integration.ts`, inside
`Phase 4: Responder consent enforcement (real recorder)`:

- New helper `readFormationUsage(party, token)` — reads `Token, UsageStampId, PeerKey, PeerSig,
  Disclosure` back out of a party's control database via `controlDatabase.getDatabase().eval(...)`,
  returning exactly the shape `verifyFormationConsent` takes. `Disclosure` is passed through
  verbatim; re-serializing it would defeat the property under test.
- New case `(iii) stores a joiner consent signature that re-verifies against the joiner's own
  key`. After a genuine `bobService.formStrand(...)` against alice's real
  `ControlFormationUsageRecorder` over libp2p, it asserts three things:
  - `verifyFormationConsent(row)` is `true` — the stored signature re-checks from the row alone,
    with nothing carried over from the session that wrote it;
  - `ed25519PublicKeyB64FromPeerId(result.memberKey) === row.peerKey` — the key the signature
    verifies against is the joiner's real identity (an Ed25519 libp2p peer id is the identity
    multihash of exactly those key bytes);
  - a one-character-mutated `disclosure` makes the same check return `false` — a guard so the
    first assertion cannot pass vacuously.

New imports on the file: `verifyFormationConsent`, `ed25519PublicKeyB64FromPeerId` from
`@serfab/cadre-core`.

### Part 2 — documentation

`docs/api.md` (approval-hook wire contract):

- Body field `peerId` → `peerKey`, both in the JSON block and in the TypeScript example hook
  (`fields.peerId` → `fields.peerKey`).
- New paragraph after the body block explaining that the value is the joiner's ed25519 **key**,
  not its peer id (peer id is derivable), that it lands in `FormationUsage.PeerKey`, and that
  the joiner has itself signed over it.
- The "who mints the nonce" argument was rewritten, not word-swapped. The old text reasoned that
  only the redeeming node could guarantee the nonce; the joiner mints it now
  (`strand-solicitation.ts`), so the replacement argument is the two-signatures-over-one-nonce
  one: joiner `PeerSig` (agreed to this redemption) plus approver sign-off (may proceed).
- `ControlFormationUsageRecorder`'s described behaviour corrected: it no longer "mints the
  nonce"; it calls the approver with the nonce and peer key the joiner supplied.
- Vouch digest field list `..., StrandId, PeerId, Disclosure` → `PeerKey` (matches
  `formationVouchMessage`, `control-database.ts:178-188`).

`docs/architecture.md`:

- `FormationUsage` table row in the `CadreControl` table: the "`PeerId`, writer-asserted"
  description was the stalest claim in the docs and is now `PeerKey` plus an explanation of
  `PeerSig` / the `PeerConsented` CHECK, and of why storing the signature on the row (rather
  than passing it as context) is what makes it re-checkable later.
- "Strand Formation" section: new paragraph describing that the joiner mints the nonce, signs
  the `'consent'` digest before the contact message goes out, and that the responder verifies
  it and the peer-id/key match before writing `PeerKey`/`PeerSig`.
- "Strand Membership Bootstrap" item 1: "seated **by consent** — no signature at all" was
  misleading post-change. Reworded to "no signature *on the `Strand` insert itself*", with a
  clause noting the authorizing usage row is itself joiner-signed.

`docs/strands.md`: **no change, deliberately.** Grepped it for formation/consent/signature/invite
wording. Its `## Strand Creation` and `## Inviting Parties` sections are TODO stubs that point at
`architecture.md`, and everything else signature-related in that file is the layer-2 `Strand.*`
membership RBAC (managers, member invites, removals) — a different consent layer that this change
does not touch. So there was no stale claim to correct there. The ticket predicted one might
exist; it does not. Worth a second pair of eyes on that call.

## Known gaps — read before trusting the new case

**The new integration case has never executed.** Two reasons, both stated plainly:

1. The ticket carries a standing constraint from its two predecessor tickets: the integration
   scenarios drive a real libp2p network and their wall clock exceeds what an agent run can
   hold, so they are build- and type-checked only inside the ticket.
2. An attempt to run *just* the new case (`vitest run
   src/scenarios/strand-formation-e2e.integration.ts -t "joiner consent signature"`) was refused
   before collection by the shared stale-build guard in `test-harness/build-freshness.ts`:

   ```
   Stale build detected: these tests run real compiled output.
     - @quereus/quereus: dist is stale — src was edited after the last build.
       Run in C:\projects\quereus: yarn workspace @quereus/quereus build
   ```

   That is the *sibling* `../quereus` workspace, outside this repo, so it was left alone rather
   than rebuilt from inside this ticket. This is an environment condition, not a test failure —
   nothing ran, nothing failed — so no `.pre-existing-error.md` was written.

So the case is **type-correct and consistent with the measured call sites, but unproven at
runtime.** The highest-value thing a reviewer can do is rebuild the quereus workspace and
actually run it. Specific things that would only surface at runtime:

- Whether `db.eval` on the raw quereus `Database` returns the `FormationUsage` columns under the
  exact names used (`Token`, `UsageStampId`, `PeerKey`, `PeerSig`, `Disclosure`) — read off
  `control-schema.ts:490-522` and the sibling `countFormationUsage` query style, not observed.
- Whether the unbound single-use path in this harness reaches the DB-backed recorder in the same
  way cases (i)/(ii) do — the new case copies their shape exactly, including the deliberate
  omission of a `formationUsageRecorder` on bob's own service.
- Whether `result.memberKey` is populated on the unbound path (it is set unconditionally in
  `strand-solicitation.ts:308`, so this should hold, but it is asserted for the first time here).
