# Browser reference app: owner keys, and closing the owner-key work

## What was built

**An export now says which key it holds.** This is the arm the `reference-app-rn-owner-keys` review filed here.

- cadre-core's `exportOwnerKey` (`owner-key-flows.ts`) returns `{ publicKey, exportText }` instead of the text alone. The type `BackupOwnerKey` is renamed `ExportedOwnerKey` and shared with `addBackupOwnerKey`.
- The rename and the new return type pass through the phone kit (`cadre-rn` `phone-node/node.ts`), the phone app (`cadre-phone.ts`, `use-cadre.ts`) and `cadre-web.ts`.
- The phone's `exportOwn` now titles the export from the returned key: by its listed row, else by its fingerprint. Its `NOTE:` is gone. A new `listedKeyName` helper in `owner-keys.ts` does the naming; `signingKeyText`, `importOutcomeAlert` and `dependentRows` each spelled the same lookup out before and now call it.
- The case this fixes is common on both apps, not only after an import. A device or tab that founded its own cadre and then joined another through an owner-granting invitation signs with its identity key there, while its owner slot still holds the key it founded with.

**The Owner keys card** (`OwnerKeys.svelte`, state in `lib/owner-keys.svelte.ts`, form in `OwnerKeyExportForm.svelte`) sits below Devices and nodes on `#/cadre`. It mirrors `docs/reference-app-rn.md` → Owner Keys, with "this tab" for "this device", Download for Share, and paste-only Import (a tab has no scanner).

- **List**: shows each key's label or "Unnamed key", its fingerprint (`cadre-format.ts`), "· This tab" on the `heldHere` key, and "Not trusted here".
  - It is read when the node is `running` and its owner step settles, after each action, and on Refresh. A read that finishes on a replaced node is dropped.
  - A member sees the list, one standing line, and Import.
- **Make a backup key** (owner): Name (default "Backup"), "Protect with a passphrase" (on), and the passphrase typed twice. `exportFormProblem` disables the button and says why.
- **Export this tab's key** (owner, when a `heldHere` row exists): the same form, with the name defaulting to that row's label. The export is titled from `exportOwnerKey`'s returned key.
- **Export view**: the phone's warning with "tab", a QR code (`QrCode.svelte`), the text (`Copyable.svelte`), **Download** and **Done**.
  - Download writes `sereus-owner-key-‹fingerprint›.txt` through a `Blob` URL revoked 1 s after the click. Nothing goes to `localStorage` or IndexedDB.
  - The view is module state, so it survives a visit to Home.
- **Import**: paste the text; a locked prefix adds a passphrase field.
  - Imports go through a new `store.svelte.ts` `importOwnerKey`, which calls `syncOwner()` when the key is wired (from the `phone-and-web-kits…` review). The other cards' standing then re-reads with the node still `running`.
  - The outcome notices follow the phone's `importOutcome`: the card re-reads `listOwnerKeys()` to tell "next start" apart from "not an owner".
  - The pasted text and passphrase are component state, so they leave with the page.
- **Remove** (owner, never on the `heldHere` row, which shows "A tab cannot remove its own owner key; use another owner key."):
  - `planOwnerKeyRemoval` opens an inline confirmation. It has one Keep checkbox per dependent (devices named as Devices and nodes names them, else by short peer id), the `ownDependency` line, and the refusal line with only Close.
  - Confirm runs `removeOwner(key, { revouch })`, and both cards then re-read.
  - A key already gone shows "Already removed". An unexpected failure is also pushed to Diagnostics.
- **Notices**: each one shows under the part of the card it belongs to (list, form, import). Refusals show in red, import outcomes in neutral text.

**Machine removal** (`machines.svelte.ts`, `Machines.svelte`):

- The `self` line now matches the phone's: "A tab does not remove itself from its cadre: to remove this tab, use another owner device."
- The confirmation shows the phone's lost-phone line, plus **Go to Owner keys**, which closes it and scrolls to the card (`OWNER_KEYS_CARD_ID`).

## Known gaps — reviewer, please weigh

- **The web card's words and helpers are hand-kept copies** of the phone's `owner-keys.ts` (`NOTE:` in `owner-keys.svelte.ts`, the precedent being `machines.svelte.ts`'s copies).
  - `importOutcome`, `dependentRows`, `revouchOf` and `exportFormProblem` exist twice, and only the phone's copies have unit tests.
  - The web copies sit in a Svelte rune module, which the web vitest setup (node environment, no Svelte plugin) does not load.
  - To test them, split the pure part into a plain `.ts` file, or move the non-word logic into cadre-core.
- **The card resets itself** when its next read finds a different node (`forgetIfReplaced`); the store's `forgetPartyCards` does not reset it. The reason: this module imports the store's `importOwnerKey`, and a reset from the store would make an import cycle.
  - Consequence: a Restart node on Home also forgets a backup export left on screen. The phone has the same behaviour when its node stops; see the `NOTE:` at `OwnerKeysSection`.
  - Until the next read there is one render of the stale card. It shows "The node is not running" whenever the node is not `running`.
- **"Export this tab's key" on an invitation-made owner** exports the slot's key, which is the key the tab founded its own cadre with and not an owner of this one. The title now shows its bare fingerprint, which is correct, but nothing says "not an owner here". The phone behaves the same.
  - `plan/2-owner-grant-separate-from-machine-invitation` removes identity-key seating, which is the cause.
  - A one-line hint is easy if wanted, but it would diverge from the phone.
- **The export warning says "This tab does not keep a copy."** on an export of the tab's own key too, which the tab does keep. This is the phone's text verbatim, kept identical on purpose.
- **Download revoke delay**: the 1 s figure is a safety margin and was not measured per browser. Some browsers read a Blob URL only after `click` returns. Only Chromium has run it.
- **By inspection only**:
  - import (all outcomes and refusals), since every solo tab's slot already holds its founding key, so a successful import needs a joined tab;
  - export of the tab's own key;
  - removal with dependents, the `ownDependency` line and the `last-owner` and `alone` refusals;
  - the lost-phone line and the Go to Owner keys scroll;
  - dropping stale reads;
  - the owner-state sync after a wired import.
- **Minor**:
  - `Copyable`'s copy button has `title={value}`, so hovering it shows the key text as a tooltip; the text is on screen anyway.
  - The password fields are not inside a `<form>`, which Chrome notes in its console at verbose level.
