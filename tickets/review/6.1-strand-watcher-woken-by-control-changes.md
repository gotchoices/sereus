# Review: the strand watcher wakes on a change to Strand or JoinedStrand

## What changed

**The seam.** `table-change-watch.ts` exports `scheduleRuns(onChange, options)`: the same single-flight, `trigger` and backstop schedule as `watchTables`, with no table subscription. `TableChangeWatcher` takes an optional `{ db, tables }`; the subscription code moved into a private `subscribe()`.

**`StrandWatcher`** no longer owns timers. `start()` builds one `TableChangeWatch` (the queryable's `watchChanges`, else `scheduleRuns`), then `trigger(100)`. `stop()` disposes it. Every read goes through `runOnce()` (also what `forcePoll()` calls), which after `poll()` arms what the run still owes:

- **Launch retry** — `scheduleLaunchRetry(since)` wakes at the earliest `failureStates` expiry *after the run's start time*. **This deviates from the ticket**, which said "earliest `nextAttemptAt` of any entry". An entry whose backoff has already expired but was not attempted belongs to a suppressed or filter-rejected strand, so waking for it means `trigger(0)` on every run: a tight loop. Reachable, for example, when `addStrand`'s failed claim calls `forgetStrand` for a strand a `strandId` filter rejects. `forgetStrand` (outside a run) calls it with `since = now()`.
- **Read retry** — `scheduleReadRetry(readComplete)`: after a read that threw, or whose `JoinedStrand` part came from the last list that answered (`queryable.lastReadPartial()`), re-run on `retryBaseMs`, doubling, capped at `min(backstop, 60 s)`; reset on a complete read.
- `retryBaseMs = min(backstop, 5 s)` replaces `pollInterval` as the launch backoff base.
- New public `refresh()` (trigger now) and `sAppIdLearned(strandId)` (trigger if provisionally admitted).
- `DEFAULT_STRAND_WATCH_BACKSTOP_MS = 300000` exported, with the `NOTE:` about machines outside the `Strand` block's cohort on a cadre larger than 16.

**`JoinedStrandSession`** takes an optional third constructor argument `onLocalChange` (default no-op, so `joined-strand-store.spec.ts` is untouched). It is called after `remember`, `rememberForeign` (only when it recorded), `leave`, and `forgetAfterThisSession` (only when a row was found). It also exposes `lastReadPartial()`, which is true when the last party-wide read failed.

**`CadreNode`** passes `watchChanges` (`['CadreControl.Strand', 'CadreControl.JoinedStrand']`, which throws a clear error if the control database is missing) and `lastReadPartial` in `createStrandQueryable`. It also passes `() => this.strandWatcher?.refresh()` to the session, calls `sAppIdLearned` after `replicaSAppIds.set` and after `addStrand`'s `sAppConfigs.set`, and uses the new default backstop. The answered `NOTE:` in `createPartyJoinedStrandLedger` is removed. `cleanup()` already stops the watcher (~5361) before `controlDatabase.close()`.

**Defaults that pinned 5000** are now 300000: `entrypoint.sh`, `provider-process-orchestrator.ts`, `example.cadre.yaml`, and also `docker/env.example`, which the ticket did not list. `env.example` is the file the README tells operators to copy to `.env`, so leaving it at 5000 would have pinned every compose deployment to a 5 s backstop. The `strandWatchInterval` doc comments, the CLI README row, the harness doc comments and the "poll" wording across cadre-core docs and comments now describe a backstop and runs. `docs/architecture.md` → "Reactive Strand Management" gains three paragraphs: when the watcher runs, its own retries, and the changes no table event reports. Item 3 under "Cadre Node", the strand-move paragraph, the component list, the `cadre strand remove` bullet and `docs/strands.md` "Offering" were updated to match.

## Things to look at hard

- **A wake loop that feeds itself.** The seam hears read-repair landings. If a watcher read of `Strand`/`JoinedStrand` on a two-machine cadre makes a read-repair land a change event even when nothing changed, every run causes the next. The measurement would show it: the idle read count would not fall, or would rise. Nothing in the unit layer can see this.
- **Scenarios that relied on the 5 s default.** Integration scenarios that pass no `strandWatchMs` now converge only through change events, own retries, or the 5-minute backstop. A cross-machine strand launch that used to happen within 5 s now depends on the sibling hearing the replicated `Strand` change. Watch for scenarios that newly time out on "strand started on the sibling". If one does, the cause is a change the subscription did not report, not a reason to shorten the default.
- **`control-founding-consult-budget.spec.ts`.** If a budget moves, record the measured figure and the reason. Do not just raise it. The watcher's first run is still at 100 ms; what is new is a run on any `Strand`/`JoinedStrand` change during founding.
- **The `since` rule in `scheduleLaunchRetry`** (the deviation above). Check that a strand skipped for backoff whose expiry passes during a slow run still gets `trigger(0)` (`max(0, …)`), and that a suppressed or rejected strand's stale entry is never re-armed.
- **`forcePoll` runs are not seam runs.** They do not clear pending wakes, so a `forcePoll` that re-arms a retry adds a wake beside the existing ones. Whichever fires first wins and the run clears the rest. Harmless, but the `runOnce` doc says "the watch clears every pending wake when a run starts", which holds only for seam runs.
