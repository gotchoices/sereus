# Review: formation admits the joining party as its own member

Second ticket of the four-ticket party-identity chain (`strand-party-member-key` → this → `strand-node-binds-member-peer` → `strand-party-removal-via-formation-e2e`). The founder got its own identity in ticket 1; this ticket gets the **joiner** one: a closed-strand formation result now carries a single-use strand membership invitation, and the joiner's node mints (or reuses) and persists its own party key. Redeeming the invitation automatically at strand bring-up is deliberately NOT here — that is the next ticket; this one ends with the invitation delivered, shape-checked, staged in memory, and the party key persisted. The original ticket's full design rationale is preserved in the implement-stage ticket text (git history of `tickets/implement/1.2-strand-formation-membership-invite.md`).

## What landed

**Wire/type layer** (`types.ts`, `strand-formation-protocol.ts`): new `StrandMembershipInvite` interface (`{ inviteKey, invitePrivateKey }`, structurally identical to `strand-membership-writer`'s `IssuedInvite` but declared in `types.ts` to avoid a writer import from the wire layer). `FormationProvisionResult` and `FormStrandResult` gained optional `membershipInvite`. New exported `isWellFormedMembershipInvite(value)` — exactly two non-empty base64url strings, each capped at 256 chars — and `isValidResponderCreatesResult` now REJECTS a result whose `membershipInvite` is present but malformed (absence stays legal). No contact-message or control-schema change, as designed.

**Responder** (`strand-formation-manager.ts`, `strand-solicitation.ts`, `cadre-node.ts`): `StrandFormationManagerOptions` (threaded through `StrandSolicitationServiceOptions`) gained an `issueMembershipInvite(strandId)` hook, wired — overriding any caller-supplied one, like `resolveStrandAddrs` — by `CadreNode.initializeStrandSolicitation` to `CadreNode.issueStrandMembershipInvite`: open strand → `null` (no invitation); closed strand → `issueInvite(liveStrandDb, { managerKeyPair: strandMemberKeyPair(StrandPartyKey row), expiration: now + MEMBERSHIP_INVITE_TTL_MS })`; closed strand with no live runtime / no party key / vanished `Strand` row → throw. The manager calls the hook on the **bound** branch of `provisionAsResponder` BEFORE `recordUsage`, so a throw becomes a clean rejection with the new exported reason `MEMBERSHIP_INVITE_UNAVAILABLE_REASON` ('Strand membership invitation unavailable, retry') while the formation token is still unspent. `MEMBERSHIP_INVITE_TTL_MS` is exported (7 days). Disclosure timing is unchanged: the invitation rides `provisionResult` in the approval frame only; every rejection path discloses nothing.

**Joiner** (`cadre-node.ts`): `CadreNode.formStrand`, after recording cross-party strand addrs, sees `result.membershipInvite` and (1) calls `ensureStrandPartyKey(strandId)` — reusing a stored `StrandPartyKey` row on a re-join, minting + persisting otherwise — then (2) stages the invitation in a new in-memory `pendingMembershipInvites` map exposed via public `getPendingMembershipInvite(strandId)` (the seam the next ticket's bring-up reconciler reads). A party-key persistence failure fails `formStrand` loudly with an error explaining the formation token is already spent and a fresh invitation is needed (no silent half-member); nothing is staged in that case. The map is deliberately not persisted (restart re-forms; documented alongside `crossPartyStrandAddrs`, including a matching unbounded-keys `NOTE:`).

**Reference apps**: zero code changes — `cadre-web.ts` `joinViaInvitation` and RN `joinClosedChatStrandFromFormation` pass through unchanged (`membershipInvite` is optional), and the new failure reason surfaces through the existing `Formation rejected: <reason>` error path. Verified by their full suites.

**Docs**: `docs/strands.md` (Closed-Strand Member Key Handling — the joiner-mint path), `docs/architecture.md` (formation sequence diagram + the Strand Membership Bootstrap joiner paragraph), `docs/strand-contracts.md` + `docs/strand-contracts-review.md` (prerequisite status advanced from "joiner half not landed" to "identities landed, automatic Member seating pending").

## Decisions a reviewer should weigh

- **Unwired hook = approve without invitation.** A manager with no `issueMembershipInvite` hook approves a bound closed redemption carrying no invitation — deliberately, mirroring the unwired `resolveStrandAddrs` posture, because every mock/transport test builds managers bare and production always goes through `CadreNode`, which force-wires the hook. The "never an invitation-less closed join" guarantee therefore holds only where the hook is wired. If the reviewer thinks the mock posture is too lenient, the alternative is carrying strand `Type` in `ResolvedHostStrand` and hard-failing, at the cost of churning the recorder interface and its fakes.
- **Closed/open is decided by the hook implementation** (CadreNode reads the `Strand` row's `Type`), not by the manager. A hypothetical hook that wrongly returns `null` for a closed strand would approve invitation-less; there is exactly one production implementation and it is tested.
- **Issue-before-record ordering.** The invitation is issued before the consent row, so an issuance failure leaves the formation token unspent (retryable). The inverse window — invitation issued, then `recordUsage` fails or the session aborts — orphans a live `Strand.Invite` nobody holds; accepted and bounded by the 7-day expiry rather than compensated (nothing can atomically un-issue a strand row). Commented at the site.
- **`formStrand` throwing after the token is spent** (party-key persistence failure on the joiner) is the chosen failure shape; the error text names the spent token and the recovery. Only reachable with a broken owner genesis / control DB — pinned by a unit test.

## Use cases to validate

- Host founds a closed strand, publishes a bound single-use invite; joiner redeems → result carries `memberPrivateKey` AND `membershipInvite`; joiner's control DB holds its own `StrandPartyKey` (≠ founder's); `getPendingMembershipInvite` returns the invitation; `consumeInvite` on the joiner's replica seats `Strand.Member` under the joiner's key, and the row converges back to the host. (Integration scenario, real network.)
- Same redemption while the host strand runtime is NOT live (or the host holds no party key) → rejection `'Strand membership invitation unavailable, retry'`, token unspent, nothing disclosed.
- Open strand / unbound invite → no invitation anywhere, nothing minted or staged on the joiner.
- Re-formation of the same strand by the same joiner party → party key reused, staged invitation replaced.
- Hostile responder sending a malformed `membershipInvite` → initiator's default validation rejects the result ('Responder result failed validation'); a custom validator that skips the check still cannot get a malformed object into the cache (the manager re-checks and drops with a log).

## Known gaps (honest)

- The joiner-side unit spec stubs the solicitation service rather than dialing; the real wire for the joiner path is covered only by the integration scenario (which runs loopback). No relay-routed run of the new field exists yet (`blind-relay-phone-to-phone-e2e` was not extended — it exercises the same frame, so the field rides along untested there).
- Redemption in the integration scenario is EXPLICIT (`consumeInvite` by hand) per the ticket; automatic bring-up redemption, burn-on-already-member, and `MemberPeer` binding are `strand-node-binds-member-peer` (already in `implement/`, prereq satisfied by this ticket).
- The pending-invite cache has no consume/clear API yet — the next ticket owns invalidation; until it lands, `getPendingMembershipInvite` keeps returning a spent invitation after a manual redeem.
- `issueStrandMembershipInvite` does not distinguish "instance exists but hibernating" from "never launched" — both reject with the same retryable reason (a hibernating responder is woken by other machinery, not by formation).
