## What shipped

The **trigger-policy + fan-out** half of server-side push-wake (the piece the parent `mobile-background-service` design left owned). It consumes the `PushNotifier` delivery from `cadre-push-notifier` and the existing `pushWake`/`resolveDeviceToken`/`listMembers` primitives, and adds *who* decides to wake hibernating mobile peers, *how* they're enumerated, the direct-dial-vs-platform-push fallback, and the dedup/cooldown that keeps a chatty strand from spamming pushes.

### `packages/cadre-core/src/push-fanout.ts` (new) — `PushFanoutService`

Fully deps-injected (no transport/DB access of its own), so the whole policy is unit-tested with fakes and **never throws to its trigger**. `notify(strandId, reason='activity')`:

1. **Participation gate** — `getStrand(strandId)` undefined ⇒ no-op (never push for a strand we don't vouch for).
2. **Concurrency coalesce** — a near-simultaneous second `notify` joins the in-flight pass (per-strand `inFlight` map; mirrors `serviceWakePromises`).
3. **Per-strand debounce** — `debounceMs` (default 10 s); a leading-edge timestamp drops bursts after a pass completes.
4. **Enumerate** — `listMembers()` minus `selfPeerId()`.
5. **Per-`(peer,strand)` cooldown** — skip a candidate woken within `cooldownMs` (default 5 min).
6. **Wake direct-first** (`wakePeer`): `pushWake` first. A **resolved `WakeAck` (even `accepted:false`) = reached** ⇒ no platform push (no double-wake — reachability is *probed by the dial*, not guessed). Only a dial/transport **rejection** (suspended phone) falls back to `resolveDeviceToken` → `notifier.send({ token, platform, payload:{type:STRAND_WAKE_TYPE,strandId,reason} })`. Cooldown is armed up-front (a wake of either kind is attempted).
7. **Stale token** — `send`→`{unregistered:true}` adds the peer to an in-memory `deadTokens` set (skips its next resolve→send) and calls `expireDeviceToken(peerId)`.

Cross-platform clean by construction: imports only the `PushNotifier` *type* + the dependency-free `STRAND_WAKE_TYPE` value, so it carries no `node:http2`/`node:crypto` edge and is safely re-exported as a runtime value from `index.ts`.

### `cadre-node.ts`

- `start()` constructs the service **only when `config.push` is set**, building the `PushNotifier` via a **guarded dynamic `import('./push-notifier.js')`** (keeps the Node-only http2/crypto modules out of a cross-platform node's static graph). Without `config.push` the node is byte-for-byte unchanged.
- `notifyStrandActivity(strandId, reason?)` — the explicit v1 trigger seam (delegates to the service; no-op when none).
- `recordStrandActivity` now *also* calls `notifyStrandActivity` — whatever already pulls-on-read on the server's strand drives the fan-out, no new contract.
- `expireDeviceToken(peerId)` (new, distinct from self-only `clearDeviceToken`): authority node → `seedBootstrapService.deleteDeviceToken(peerId)`; non-authority → logs re-registration-needed (the fan-out's `deadTokens` set is what actually stops re-pushing this process). Best-effort, never throws.
- `cleanup()` closes the notifier (APNs session teardown) and drops the service.

### `types.ts` / `index.ts`

`PushCredentials` gains `cooldownMs?`/`debounceMs?`. `index.ts` exports `PushFanoutService`, `PushFanoutOptions`, `FanoutMember`, and the two default constants.

### `reference-app-rn/metro.config.js`

Added `node:http2`/`http2` → empty-shim (mirrors the existing `net`/`tls` stubs). **Why**: the guarded dynamic import in `CadreNode.start` is a Metro-resolvable edge to the APNs module's `node:http2`; the RN config previously shimmed `net`/`tls` but not `http2`, so without this the RN bundle would fail to resolve `node:http2`. A phone never sets `config.push`, so the notifier never loads — the stub only satisfies Metro's graph resolution.

## Known gaps / honest caveats (please probe)

- **RN bundle build is NOT exercised here.** The `node:http2` Metro shim is the correct fix, but a real Metro/EAS bundle + on-device run is out-of-agent (same pattern as the RN push-wake-receive ticket). Reviewer/human should confirm the RN bundle builds green and a phone (no `config.push`) still boots unaffected. If a stricter "keep http2 fully out of the RN graph" stance is preferred over the empty shim, the alternative is a non-analyzable dynamic-import specifier — noted but not taken (janky, bundler-defeating).
- **In-memory, acceptably lossy** cooldown/debounce/dead-token state — a restart at worst re-sends one duplicate, and `serviceWake` is idempotent/coalesced, so a duplicate is harmless. No persistence in v1 (matches the parent's allowance). Confirm this is acceptable.
- **No cross-strand coalescing** in v1 — each strand-wake names its own `strandId` (the phone's `serviceWake` is per-strand). If on-device measurement shows a device being pelted across many active strands, add a per-peer (any-strand) rate cap as a follow-up. Named in `STATUS.md`.
- **Passive Optimystic-level detector deferred** — the v1 trigger is the explicit `notifyStrandActivity`/`recordStrandActivity` seam, which fully serves a server/relay sApp that knows when activity lands. A zero-app-involvement detector needs an upstream Optimystic commit/block-received hook (`IRepo` is get/pend/commit/cancel only). Filed as `tickets/backlog/passive-strand-activity-fanout-detector.md` (distinct from the receiver-side `hibernation-control-network-pending-precheck`, though both want the same upstream signal).
- **Fan-out is sequential-free / fully parallel** (`Promise.all` over candidates). Fine for small cadres; a very large membership with many suspended peers would issue many concurrent dials. No batching/throttle beyond debounce+cooldown. Worth a glance if cadres grow large.
- **Multi-tenant**: a `CadreNode` is single-party; `listMembers`/`resolveDeviceToken` read this node's own control DB, so the service has no cross-tenant surface. Per-node credential injection (`config.push`) is the boundary, owned by `cadre-host` downstream (`cadre-host-push-credentials`). No code here spans tenants.
- **`expireDeviceToken` authority path** deletes via `seedBootstrapService.deleteDeviceToken` — exercised in `cadre-node.spec.ts` with a fake service, not against a real control DB. The real delete path is the same one `clearDeviceToken` uses (already covered by the device-token ticket).
