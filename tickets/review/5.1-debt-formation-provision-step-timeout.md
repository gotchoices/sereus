## What changed

Added a third timeout budget, `provisionTimeoutMs`, distinct from the existing per-wire-step
`stepTimeoutMs`:

- `FormationListenerOptions.provisionTimeoutMs` (responder) — default **12_000 ms**. Wraps the
  `provisionStrand` hook call in `withTimeout`.
- `FormationDialOptions.provisionTimeoutMs` (initiator) — default **15_000 ms**. Bounds only the
  `await-response` read; `dial-connect` still uses `stepTimeoutMs`.
- `StrandFormationManagerConfig.provisionTimeoutMs` — threaded into both sides by
  `StrandFormationManager`.

Ordering documented in a comment at the constants (`strand-formation-protocol.ts:39-57`):
approval hook (10s, `feat-formation-approval-client`) < responder provisioning (12s) < initiator
await-response (15s) < session (30s) — each layer can fail and report before the layer above it
gives up.

`resolveProvisionTimeoutMs()` (`strand-formation-protocol.ts:227`): treats `0`/negative
configured values as "unset" (uses the default, not "time out immediately"); if the resolved
value would let provisioning outlive the session, clamps to `sessionTimeoutMs - stepTimeoutMs`
(min 1ms) and logs a warning via `debug`.

Responder (`runSession`, `strand-formation-protocol.ts:373-396`): a provisioning timeout is
caught by exact message match against `withTimeout`'s label and converted to
`send({ approved: false, reason: 'Formation provisioning timed out' })` — returns before the
generic catch, so it's reported as retryable, not `'Internal formation error'`. A `NOTE:` at
that site documents the write can still land after the timeout reply (pre-existing commit race,
not closed by this ticket — provisioning is not cancelled on timeout).

A second `NOTE:` at `DEFAULT_MAX_CONCURRENT_SESSIONS` documents that a longer provisioning
budget holds a session slot longer, so a slow hook can now exhaust the concurrency cap sooner;
left as a tripwire since the default cap (100) isn't tight.

## Test coverage (packages/cadre-core/test/strand-formation-protocol.spec.ts)

Four new cases, all passing:

- Responder completes when `provisionStrand` is slower than `stepTimeoutMs` (10ms) but within
  `provisionTimeoutMs` (200ms) — the regression this ticket exists to fix.
- A never-settling `provisionStrand` yields the `'Formation provisioning timed out'` frame
  (stream still closes cleanly) rather than a dropped/hung stream.
- Clamp case: `sessionTimeoutMs: 1000, stepTimeoutMs: 100, provisionTimeoutMs: 5000` clamps to
  900ms; a 950ms hook still gets a rejection frame back before the 1000ms session timeout would
  fire silently.
- `dialFormation`: `await-response` is bounded by `provisionTimeoutMs` (200ms), not the tiny
  `stepTimeoutMs` (10ms) — via a `DelayedResponseStream` subclass of the file's `MockStream`
  that delays the response frame past `stepTimeoutMs`.
