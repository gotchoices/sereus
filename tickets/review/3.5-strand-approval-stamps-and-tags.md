# Review: strand membership approvals — single-use stamps + action-tagged digests

## What was built

Every membership row in the `Strand` schema (`Member`, `MemberPeer`, `Manager`) now
carries a `StampId` — a random identifier minted fresh for each row incarnation. Every
signed approval covers a digest that leads with the table name and the action, then the
row's key fields, then the stamp. Deleting a row requires filing a signed tombstone
into a new `Strand.Revocation` table in the same transaction, which retires the stamp
permanently. Result:

- **Insert replay dies**: re-inserting a captured row hits the `NotRevoked` check
  constraint (stamp already retired in `Revocation`).
- **Delete replay dies**: the delete digest binds `old.StampId`; a legitimately
  re-created row carries a fresh stamp, so the old delete approval verifies against
  nothing.
- **Cross-rule reuse dies**: the leading `'Strand.<Table>','<action>'` tags mean an
  approval minted for one rule verifies under no other rule. This also closes the
  member-admit → admin-demote signature collision that
  `backlog/bug-strand-approval-domain-separation` described — that ticket is deleted
  as superseded (its "what good looks like" is exactly what landed; existing suites
  pin it).

Six concrete replays (manager re-seat / re-demote / forced-resign, member re-admit /
re-evict, peer unbind / rebind) were reproduced on a real closed strand before the
change; the schema now refuses all of them. Explicit attack-pin tests for those six
live in the follow-up ticket `strand-approval-replay-pins` (implement stage, prereq
this slug).

## Signed-digest table (the contract; each element is one variadic digest arg)

| Rule | Signed digest |
|---|---|
| Member add-by-manager | `'Strand.Member','add',new.Key,new.StampId` |
| Member remove-by-manager | `'Strand.Member','remove',old.Key,old.StampId` |
| Member self-departure | `'Strand.Member','leave',old.Key,old.StampId` |
| MemberPeer self register | `'Strand.MemberPeer','add',new.MemberKey,new.PeerId,new.StampId` |
| MemberPeer self remove | `'Strand.MemberPeer','remove',old.MemberKey,old.PeerId,old.StampId` |
| MemberPeer manager remove | `'Strand.MemberPeer','manager-remove',old.MemberKey,old.PeerId,old.StampId` |
| Manager promotion | `'Strand.Manager','add',new.MemberKey,new.Generation,new.StampId` |
| Manager self-resignation | `'Strand.Manager','resign',old.MemberKey,old.StampId` |
| Manager removal-by-another | `'Strand.Manager','remove',old.MemberKey,old.StampId` |
| Revocation tombstone | `'Strand.Revocation','retire',new.TableName,new.StampId` |

**Type-sensitivity**: the crypto plugin's digest is framed and type-tagged, so
`Generation` must be signed as a NUMBER — INTEGER 1 and TEXT '1' produce different
digests. Writers do this; any new caller must too.

## Key implementation points a reviewer should probe

- **Schema**: `schemas/strand.qsql` and
  `packages/quereus-plugin-sereus/src/strand-schema.ts` must stay byte-identical
  (drift spec pins this). `NotRevoked` (insert) and `RevocationRecorded` (delete)
  checks exist on all three guarded tables; `Revocation.Authorized` verifies the
  tombstone signer against **committed** `Member` rows and its context is non-null
  `(MemberKey, Signature)`.
- **Writers** (`strand-membership-writer.ts`): every delete path
  (`revokeMember`, `leaveStrand`, `removeMemberPeer`, `removeManager`) files the
  tombstone and the row delete in one transaction. `signStrandApproval` +
  `generateStrandStampId` are the new exported primitives; `signStrandPayload` stays
  exported for invites. `inStrandTransaction` joins an enclosing transaction instead
  of nesting — rationale in its docstring; reviewer should confirm the join-mode
  reasoning holds for concurrent writer use.
- **Managers must be members (found during testing, now load-bearing)**:
  `removeManager` files a tombstone signed by the acting manager, and
  `Revocation.Authorized` checks that signer against committed `Member`. A `Manager`
  row whose key has no `Member` row cannot remove or resign anyone. Schema comment
  calls this intended. **Reviewer: weigh whether an explicit `Manager` → `Member`
  foreign-key-style constraint deserves a backlog ticket**, so the invariant is
  enforced at insert instead of failing later at delete time.
- **Quiet no-op deletes**: delete writers return silently when the target row is
  absent. Deliberate (idempotent retry), but reviewer should confirm no caller relies
  on an error to detect "already gone".
- **Scan-not-seek stamp reads**: writers look up current stamps with scans rather
  than primary-key seeks — a networked-strand PK-seek gap made seeks unreliable. Fine
  at current sizes; flag if a hot path shows up.
- **Test-side tombstone idiom**: any test doing a raw negative delete that pins the
  `/Authorized/` rejection must file a same-transaction founder-signed tombstone
  first, otherwise `RevocationRecorded` fires before `Authorized` and the pin asserts
  the wrong constraint. Used in `strand-member-revocation.spec.ts`.
- **Placeholder stamps**: `strand-schema.e2e.spec.ts` bootstrap-branch and
  reject-case raw inserts use literal stamps (`'stamp-m1'` etc.) — no signatures
  involved on those paths, so literals suffice.

## Operational footgun worth knowing

cadre-core tests resolve `@serfab/quereus-plugin-sereus` via its built dist, and
integration-tests resolve `@serfab/cadre-core` via its built dist. After editing
either package's src, rebuild it (`yarn build` in the package) or downstream
typecheck/tests fail on stale exports. IDE "no exported member" /
`@quereus/quereus` "Cannot find module" diagnostics are stale-language-server noise;
`yarn typecheck` is the arbiter.
