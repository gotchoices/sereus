# Topology coverage map in `docs/testing.md`

Added a new `## Topology coverage map` section at the end of `docs/testing.md` (after the
`yarn smoke:published` section). One line per topology class, each naming the scenario file(s)
that cover it, or (for four classes) an open ticket slug if nothing covers it yet. Consistent
with the doc's existing rule: no pass/fail state in the doc itself, that stays in the suites and
`tickets/`.

Every scenario path and every ticket slug in the section was verified against the current tree
and board before writing (not copied uncritically from the ticket body):

- All 15 scenario files named exist under `packages/integration-tests/src/scenarios/`, including
  `harness-topology.integration.ts` (its prereq, `harness-topology-builder`, has already landed —
  reviewed and implemented in prior commits on this branch).
- `child-node-fixtures.ts` and `topology.ts` exist under `packages/integration-tests/src/harness/`.
- The four "uncovered" ticket slugs all resolve on the current board:
  `scenario-two-multi-machine-cadres-share-one-strand` → `tickets/plan/4-scenario-two-multi-machine-cadres-share-one-strand.md`,
  `feat-scenario-medium-private-network` and `feat-scenario-public-open-strand-network` →
  `tickets/backlog/`, `strand-network-nat-relay-reachability` → `tickets/backlog/`.

The time-budget line points at (does not copy) the `TIME BUDGET` doc comment in
`packages/integration-tests/src/harness/topology.ts` (module header, ~line 14) — linear-in-machine-count
bring-up cost, explicit per-hook timeouts, every strand member counts as a second libp2p node.

## How to validate

- Read `docs/testing.md`'s new `## Topology coverage map` section (near the end, after
  "Installing what a customer installs").
- Spot-check a couple of the scenario-path claims and the four ticket-slug claims against the
  tree/board yourself if in doubt — none of this is machine-checked (it's a docs-only ticket, no
  code path enforces the map staying accurate).
- `yarn lint` passes (ran clean; only docs changed, no source touched — this was mostly a sanity
  check per the ticket's own TODO, not an expectation of new lint findings).

## Known gaps / things a reviewer should weigh

- The map is manually maintained prose, not generated from the ticket board or the scenario
  directory. It will drift if scenarios are added/removed or if the four "uncovered" tickets land
  or get renamed/re-sliced without someone updating this section. The ticket's own text accepts
  this ("a ticket slug... may later be completed and swept from the board; that is fine... don't
  design around it") — flagging it here rather than treating it as a gap to close.
- No automated test or lint rule enforces the map's scenario-path or ticket-slug references stay
  valid — this is intentionally reference documentation, not a status board, per the ticket's own
  framing and the doc's existing "not a status board" policy stated at the top of the file.
