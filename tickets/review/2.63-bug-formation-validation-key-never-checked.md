# Review: formation approval must come from an enrolled validation key

## What the bug was

A party mints an invitation (`CadreControl.FormationInvite`). If that invitation carries a
`ValidationUrl`, someone is supposed to look at the joiner's disclosure and sign off before the
invitation may be redeemed. The party keeps the list of keys allowed to give that sign-off in
`CadreControl.ValidationKey`.

Redemption writes a `CadreControl.FormationUsage` row, gated by its `Authorized` CHECK. That
CHECK verified the sign-off signature against `context.ValidationKey` — a plain parameter on the
redeeming insert. A redeemer generated a throwaway keypair, signed its own disclosure with it,
passed key + signature, and the gate opened. `ValidationKey` had no consumer anywhere in the
schema.

## What changed

`FormationUsage.Authorized`'s validation branch, in both hand-maintained copies of the schema:

```sql
and (FI.ValidationUrl is null or exists (
    select 1 from ValidationKey VK
        where VK.Key = context.ValidationKey
            and verify(digest('CadreControl.FormationUsage', 'vouch', new.Token, new.Disclosure),
                       context.ValidationSignature, VK.Key, 'ed25519')))
```

`context.ValidationKey` stays in the context tuple but is now only a *selector* — it picks which
enrolled row is being claimed. The signature is verified against the **stored** `VK.Key`, so a
mismatched (name, signature) pair cannot pass in either direction.

Files:

- `schemas/control.qsql` and `packages/cadre-core/src/control-schema.ts` — the CHECK plus a
  constraint comment stating (a) stored-vs-supplied key and why that is the whole point, and
  (b) that removing a validation key later does not retroactively invalidate `FormationUsage`
  rows it already approved. `control-schema-drift.spec.ts` enforces the two copies byte-match.
- `docs/architecture.md` — the `ValidationKey` row of the control-table list now says this table

  the non-retroactive removal semantics.
- `packages/cadre-core/test/control-formation-invite.spec.ts` — new

### What the new tests cover

Each case records against a **pre-existing owner-signed strand** via `recordFormationUsage`
(not `redeemInvitation`), so `StrandExists` and `Monotonic` are already satisfied and
`Authorized` is the only constraint that can reject — which is what makes
`expectConstraintFailure(..., 'Authorized')` a genuine single-rejector assertion rather than a
widened one. A validation key is enrolled in the block's `beforeAll`, so every rejection is
about the key presented, not about the party having no approver at all.

| Case | Expected |
| --- | --- |
| Rogue, unenrolled key + its own valid signature | rejected — `Authorized` (this is the bug; passes pre-fix) |
| No sign-off supplied at all | rejected — `Authorized` |
| Enrolled `ValidationKey` signs the `'vouch'` digest | accepted, `UseNumber` 1 |
| Enrolled key named, signature from a different key | rejected — `Authorized` |
| Enrolled key's signature presented under an unenrolled key name | rejected — `Authorized` |
| Invite with no `ValidationUrl`, no sign-off | accepted (unchanged) |

## Known gaps — please treat these as the starting point

- **Only the rogue-key test distinguishes pre-fix from post-fix.** The two mismatched-pair cases
  were already rejected by the old CHECK (a signature from key B never verified against key A,
  supplied or stored). They pin the new pairing semantics but are not regressions of the
  original hole. Worth confirming that is acceptable coverage.
- **No test that a key is enrolled, then removed, then a redemption is attempted.** The comment
  claims removal narrows future approvals; the natural consequence of the `exists` (no row →
  no match) makes this near-tautological, so it was not written. If you want the removal
  semantics pinned in a test rather than in a comment, that is a reasonable ask.
- **No multi-node / replication test.** The CHECK is evaluated locally on each node. Nothing here
  exercises what happens when two nodes disagree about the contents of `ValidationKey`.
- **The web hook is still not wired end-to-end.** `ControlFormationUsageRecorder.recordUsage` /
  `provisionAndRecord` never pass a `validationKey` / `validationSignature` pair, and
  `StrandSolicitationService.validateStrandFormation` (which would call the `FormationSigner`
  hook) has no caller outside its own unit test. So a `ValidationUrl` invite still cannot be
  redeemed through the real formation protocol — before or after this fix. That is deliberate
  and out of scope; the feature is filed as
  `backlog/feat-formation-validation-webhook-unwired`. The hole closed here is in the control
  database's **write API**, which is the actual security boundary: the control tables are
  replicated and their CHECKs are what stop a hostile peer writing directly.
- **Still out of scope, unchanged from the source ticket:** `context.PeerId` /
  `context.PeerSignature` on the same insert are declared and never verified, so an invitation
  token remains a bearer credential.

## Review findings

- **Tripwire — `ValidationKey` now has a consumer, so the `Revocation` convergence gap reaches
  it.** Before this change nothing in the schema read `ValidationKey`, so a replayed enrollment
  on a node that had not yet converged on the tombstone was inert. Now such a node would accept
  redemptions approved by that re-seated key until the `Revocation` row arrives. Same class as
  the notes already on `Strand.StampId` and `OwnerKey`'s `MinOneOwner`, and there is still no
  per-request *read* surface to filter (the gate is a write-time CHECK), so nothing to do today.
  Parked as a `NOTE:` comment on `ValidationKey.NotRevoked` in both schema copies.
