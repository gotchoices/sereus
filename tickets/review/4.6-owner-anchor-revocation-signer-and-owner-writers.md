# Review: tombstones carry their signer; owner keys get a signed add and a signed remove

First of three tickets (`owner-anchor-derivation` and `owner-anchor-follows-owner-key-changes` follow). This one gives the reader-side work a removal it can verify from stored columns, and production writers for adding and removing an owner.

## What landed

**Schema (`schemas/control.qsql` and its mirror `control-schema.ts`, regenerated from the `.qsql` so the drift spec stays green).** `Revocation` gains `SignerKey text null` and `SignerSig text null`. `Revocation.Authorized` additionally pins `coalesce(new.SignerKey, '') = context.OwnerKey` and `coalesce(new.SignerSig, '') = context.Signature`. `ReissueOnly` pins both columns to their old values, null-safe. The header comment names `getOwnerKeys` among the reads that drop retired stamps. No warm-start migration: existing control stores are recreated (the docs note under the table list already says editing constraint text needs that).

**Writers and readers (`control-database.ts`).**
- `execTombstone` stores the context pair as the signer pair. The ledger marker (`openRevocationLedger`) now files through `execTombstone` too; it had its own insert before.
- `RevokedRowRef` is `Pick<RevocationRow, 'tableName' | 'rowKey' | 'stampId'>`; `RevocationRow` gains `signerKey` / `signerSig`. `queryRevocations(retry = true)` reads the two columns.
- `insertOwnerKeyVouched(key, ownerKey, signMessage)` through `mutateCadrePeer`: liveness read, stamp and signature inside the locked body; idempotent `false` when the key is already a live owner; stores `VouchOwner`/`VouchSig` equal to the context pair.
- `deleteOwnerKey(key, ownerKey, signMessage)` through `mutateCadrePeer`, over `deleteGuardedRow` (`RemovableTable` now includes `OwnerKey`). Refuses by name: `an owner cannot remove itself` (before any read, so no notify) and `cannot remove the last owner` (live count of one, read inside the body).
- `getOwnerKeys(retry = true)` drops rows whose stamp is retired. `hasOwnerKey` stays raw, with a comment saying why.
- `mutateCadrePeer`, `MembershipChangeListener` and `GuardedDeleteListener` docs updated to say what they now cover.

**Verifiers (`peer-authorization.ts`, exported from the index):** `verifyRevocationSigner(row)`, `ownerKeyAddDigest(key, stampId)`, `verifyOwnerKeyVoucher(key, stampId, vouchOwner, vouchSig)`. The raw-bytes twin of the add digest is the private `ownerKeyAddMessage` in `control-database.ts`, next to `revocationTombstoneMessage`, so the party-binding ticket (`control-approvals-bound-to-party`) finds one builder per encoding.

**Service and node.** `SeedBootstrapService.addOwner` / `removeOwner` (owner-key precondition first, as `removePeer` does). `CadreNode.addOwner` / `removeOwner` (seed service required, key shape-checked with `requireEd25519PublicKeyB64`). `addOwner` logs loudly when it commits alone, with a `NOTE:` pointing at `tickets/backlog/debt-owner-key-add-while-alone-has-no-reissue.md`. `removeOwner` needs no `noteControlWrite`: its tombstone goes through `noteGuardedDelete` like every other guarded delete.

**Docs (`docs/architecture.md`).** `OwnerKey` and `Revocation` rows of the control table list; "Writes made while alone" (an owner add has no re-issue); "Deletes made while alone" (`removeOwner` in the guarded-delete list); Implementation Status (Owner Key API).

## Deviations from the ticket, for the reviewer to judge

- **Columns are `text null`, not `text`.** Quereus defaults to NOT NULL. A NOT NULL column would make a mis-stored pair fail as a NOT NULL error instead of `Authorized`, and the existing "unsigned tombstone is refused (Authorized)" probes, which store nulls, would change their rejection. Every committed row still carries both values, because `Authorized` pins them to the non-null context.
- **`ReissueOnly` compares with `coalesce`, not a bare `=`.** With a bare `new.SignerKey = old.SignerKey`, an owner-signed re-issue that set the columns to null would evaluate to null and pass. The extended test probes exactly that.
- **Re-adding a removed owner on a machine that still holds the retired row is refused by name** in `insertOwnerKeyVouched` (`Cannot re-add owner key … re-add it from the machine that removed it`), rather than being left to fail on the primary key. The `NOTE:` naming the reap-branch remedy is on the method.
- **`deleteOwnerKey` answers `false` for any key that is not a live owner**, including a physically present row under a retired stamp (a removal this node received by replication). Delegating that case to `deleteGuardedRow` would sign the retired stamp and fail on the tombstone's primary key.
- **`control-cadre-invite.spec.ts` "an issuer removed since issuing…"** used hand-rolled owner add/remove SQL with an unsigned-pair tombstone. It now calls `insertOwnerKeyVouched` / `deleteOwnerKey`.
- **`control-read-routing.spec.ts`** records the routing of `getOwnerKeys`' SQL by exact text; that text now selects `StampId` too, so its two markers were updated.

## Tests

Added or changed, per the ticket's plan:
- `control-revocation-replay.spec.ts` → "a tombstone that stores a signer pair other than the context pair is refused (Authorized)": four probes over an orphan stamp with a valid founder context, each breaking one clause of the pin (null key, null sig, other owner's sig, other owner's key).
- Same file, the existing "update may move only the counter" case: an owner-signed re-issue that rewrites the signer pair (to another value, and to null) is refused by `ReissueOnly`, and the stored pair is still the filing owner's afterwards.
- Same file, "the two-owner OwnerKey removal transaction retires the stamp" replaced by "insertOwnerKeyVouched then deleteOwnerKey…": the stored `VouchOwner`/`VouchSig` on the add, the retired stamp, the tombstone's stored signer pair via `queryRevocations`, and the membership listener fired once per write (`owner-key-add`, `owner-key-remove`).

Fixtures that hand-insert tombstones now store the signer pair (domain-separation, cadre-invite, ownerkey-self-authorization, ledger-marker, reap, reissue, replay, strand-party-key). The `FreshTombstone` probe in the reissue spec stores the pair so `FreshTombstone` stays the single rejector.

## Known gaps

- **Not tested:** the by-name refusals (self-removal, last owner, re-add over a retired row), the not-live answer of `deleteOwnerKey`, and `CadreNode.addOwner` / `removeOwner` themselves, including the committed-alone log. The ticket called these wiring. The re-add refusal and the not-live answer are branches this ticket added beyond the plan; a reviewer may want one schema-level case for them.
- **`verifyRevocationSigner` and `verifyOwnerKeyVoucher` have no direct test.** Nothing here pins that `ownerKeyAddDigest` (base64url) and `ownerKeyAddMessage` (raw bytes) agree. `owner-anchor-derivation` verifies production-written rows with these functions, and its tests will cover that agreement.
- **Tripwire, NOTE at `ControlDatabase.hasLiveCadreInvite`:** `getOwnerKeys` now reads `Revocation` before `OwnerKey`, so the inbound stranger-gate path scans `Revocation` twice (the two scans run in parallel). Not measured.
- **The removal pre-checks read this node's rows.** A concurrent removal elsewhere can make the last-owner count wrong in either direction. The schema still decides, as the `deleteGuardedRow` NOTE describes; this was checked by reading the code, not by a test.
- **Consumers of the `getOwnerKeys` filter were checked by reading the code only:** `enrolledOwnerSigningKey` (a removed owner stops signing once it holds its own tombstone), `isCadreInviteLive` / `hasLiveCadreInvite` / `listCadreInviteStatuses` (an invitation issued by a removed owner reads as not live), and `projectSeedPeers` / the cohort dial preference (hints only). All of them call it unlocked.
