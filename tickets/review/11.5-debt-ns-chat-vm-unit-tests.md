# Review: unit tests for `ChatViewModel` on `reference-app-ns`

## What landed

No source change. `src/chat-vm.ts` and `src/chat-operations.ts` are untouched; everything is test harness, tests and docs.

- **`test/stubs/nativescript-core.ts`**: one line, `export { ObservableArray } from '@nativescript/core/data/observable-array/index.js'`. It loads the real class with no config change. Vite transforms `@nativescript/core` itself because the package has ESM syntax and no `"type": "module"`, so the directory import that used to be blamed never reaches Node's loader. The comment now records this, names `test.server.deps.inline: [/@nativescript\/core/]` as the fallback if `ERR_UNSUPPORTED_DIR_IMPORT` ever returns, and says there are three sourcemap warnings instead of one.
- **`test/stubs/fake-cadre-node.ts`**: `fakeStrand(status, { strandId, database })`. It wraps a Quereus `Database` as `{ getDatabase }`, and the `as unknown as StrandInstance` cast stays at its one site. To model a `'syncing'` joiner, a test saves `strand.database`, sets it to `undefined`, and later restores it, so no second cast is needed. The header comment now says three suites instead of two.
- **`test/chat-vm.spec.ts`** (new, 13 tests):
  - `src/chat-operations.ts` runs unmocked against `new Database()`, with the app's real chat schema read through `vi.importActual('../src/chat-strand')` and applied as `declare schema App { … }` / `apply schema App;`.
  - `ScriptedDatabase`, a decorator in the spec file, sits between the strand and that database. It classifies each statement by the table it touches (`participant-insert`, `participant-list`, `message-insert`, `message-list`, `message-lookup`) and records it. Each kind has a queue of one-shot scripts: `hold` (park until `release`/`fail`), `refuse` (reject before the database sees it) and `loseOutcome` (apply, then throw). `idle()` waits until nothing is running apart from held statements, then crosses a macrotask so the view model has acted on every outcome. `asDatabase` holds the file's only `as unknown as` cast.
  - Only `setInterval`/`clearInterval` are faked. `POLL_MS = 60_000` because `vi.waitFor` calls `vi.advanceTimersByTime(50)` on every check while fake timers are on (read in vitest 4.1.8's `waitFor` source). A short poll interval would fire polls in the middle of a wait.
  - `afterEach` stops the VM, releases every held statement, restores real timers and restores spies.
- **`vitest.config.ts`** header and **`docs/reference-app-ns.md`**: the parity-map row, the "Unit" row of the test table and the "Unit suite" section now describe the chat suite. "Two groups" became "Three groups", and the stale `debt-ns-chat-vm-unit-tests` references are gone.

## Tests added, and what each verifies

The poll (`refresh()`):
- *starts no second read of a strand while one is still running*: the single-flight guard. A held `message-list` read plus three ticks still gives one read.
- *shows a failed read, and reads again on the next tick*: a refused read sets `error`. The guard is released, so the next tick reads again and `error` clears.
- *reads a strand it re-attached to at once, without waiting on the old one*: the guard is keyed per strand. With A's read held, the node offers B and `start()` runs, and B's read starts. Nothing is asserted about the list once A's read settles, because that is `bug-ns-chat-shows-previous-strand-messages-after-switch` (backlog). That ticket's repro plan uses this harness.

Participant registration (`attach()`/`register()`):
- *starts no second insert while the first is still running*: with the participant insert held, three polls still read but start one insert.
- *retries a failed insert on the next poll, and stops once one lands*: a refused insert leads to one more insert on the next poll, and none after it succeeds. `console.warn` is silenced by a spy.
- *waits for a joining strand to become writable before registering or reading*: with no `database`, no statements run, `loading` goes false and `error` stays `''`. After the database is restored, the next poll registers and reads.
- *attaches to a strand created after the screen opened, on the next poll*: with no strand offered, `inputEnabled` is false. After `strand:started`, the next poll registers and reads, and `inputEnabled` is true.

Send (ported from `reference-app-rn/test/chat-send.spec.ts`):
- *stores one row when the unchanged draft is sent again after an uncertain failure*: the insert is stored and then throws. `error` starts "Not confirmed sent". Send again leaves one row in the real table, with `draft` and `error` both `''`.
- *stores edited text as a new message*: two rows.
- *ignores a second Send while the first is still in flight*: with the insert held, a second `send()` resolves and starts no insert. After release there is one row and the draft is cleared.

Retry key:
- *is retired when the draft changes*: `''` and then the same text again gives two rows.
- *is settled by a poll that shows its row*: after an uncertain failure, the next poll clears the banner and the draft.
- *is not settled by a poll while a resend is in flight*: the resend's `message-lookup` is held while a poll returns the stored row, then the lookup is failed. The banner is back, and a third Send of `"ok"` leaves exactly one row.

## Validation run

- `yarn workspace @serfab/reference-app-ns typecheck`: exit 0.
- `yarn eslint` on the four touched TS files: exit 0.
- **Mutation check** (a scratchpad harness that aliased `../src/chat-vm` to mutated copies; the source tree was not touched). 13 mutants, each changing one rule in `chat-vm.ts`:
  - 12 were caught: no read guard, a global rather than per-strand read guard, a guard never released, no in-flight registration guard, a failed registration counted as registered, no late attach, no `sending` guard, a new id minted per attempt, a `draft` setter that keeps the key, settling while sending, never settling, and reading with no database.
  - 1 survived: `send()` ignoring its `pendingDraft.text === text` match. That survival is expected. The `draft` setter already retires the key whenever the text changes, so the send-side match can't be reached on its own. The "edited text" test pins the behaviour whichever site provides it.
  - The "waits for a joining strand" test needed `expect(vm.error).toBe('')` added to catch the read-with-no-database mutant, because `getDb` throws before any statement is recorded.
- The in-memory database really enforces the foreign key (`CHECK constraint failed: _fk_Message_ParticipantId`) and the primary key (`UNIQUE constraint failed: Message PK.`). This was probed directly for the spec's header claim.

## Deliberately not tested, or deviations from the plan

- The plan's "poll that shows the pending row" test ended with "Send the same text again → second row, which shows the key is gone". I dropped that step. Settling also empties the box, so typing the text again goes through the `draft` setter, which retires the key by itself. The step could not tell settle's key release apart from the setter's. The assertions that do discriminate (banner cleared, draft cleared) are kept. The mid-flight test covers settle's key handling.
- In the mid-flight test, the third Send sets `vm.draft = 'ok'` first. That matches what the user sees in both cases: if the poll had wrongly settled, the box would be empty and the user would retype, which mints a new id. The row count is what tells the two apart, and the mutation run confirms it.
- The ticket's own "not tested" list stands: `settlePendingDraft`'s "box still holds the text" arm can't be reached, and `chat-strand.ts` and `chat-operations.ts` get no standalone tests.
- Removing the `strand?.database &&` gate in `attach()` is **not** detectable from outside. Without a database, `getDb` throws before any statement, so the only difference is a `console.warn` on every poll. No test pins it.

## Things a reviewer should look at

- `classify()` in the spec matches on regex over SQL text (insert target, `from App.Message` with or without `join`). It throws on anything unrecognised. A new query shape in `chat-operations.ts` would surface as a view-model error, or a registration warning, rather than a clean test failure. Judge whether that is loud enough.
- `idle()` relies on the view model starting follow-up statements only on microtasks (true today: the only timer in `chat-vm.ts` is the poll). If a later change adds a real `setTimeout` between two statements, `idle()` could resolve early.
- `releaseAll()` in `afterEach` lets held statements finish after the test, on a stopped VM. Each test has its own `Database`, so nothing crosses between tests, but those continuations run during the next test's setup.
- Run output: three Vite sourcemap warnings per run, documented at the stub.
