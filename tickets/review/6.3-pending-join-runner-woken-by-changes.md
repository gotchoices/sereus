# The pending-join runner wakes on a change to its tables

## What changed

`PendingJoinRunner` (`pending-join-runner.ts`) no longer owns a pass timer. Every pass runs on a `TableChangeWatch` built in `start()`, the same way `StrandWatcher.subscribe` does it:

- **New deps:** `watchChanges?(onChange, options)` and `backstopMs?`. Without `watchChanges` (the spec), the runner falls back to `scheduleRuns`, and the runner's `scheduler` is passed in the options, so the spec's fake clock drives the watch's timers too.
- **Wiring:** `CadreNode.startPendingJoinRunner` subscribes to `CadreControl.JoinRequest`, `JoinSuccess`, `JoinFailure`, `OwnerKey`, `Revocation` through `ControlDatabase.watchTables`. `watchTables` throws on a bad name, so a typo fails `CadreNode.start()`.
- **Schedule:** a pass runs on `start()` (`trigger(0)`), on `kick()` (`trigger(0)`, was a synchronous pass), on any change to the five tables (the watch's 50 ms coalescing, one run at a time), and at the latest `PENDING_JOIN_BACKSTOP_MS` (10 min) after the last. This replaces `PENDING_JOIN_POLL_MS` (30 s), renamed in `index.ts` with no alias.
- **30 s pass retry** (`PENDING_JOIN_PASS_RETRY_MS`, module-private) at the three places that used to say "the next pass": a pass that throws, a `consider` that throws for one row, and `writeOutcome` giving up after `MAX_OUTCOME_WRITE_ROUNDS`. Their log lines now say "retried in 30 s" / "a pass in 30 s decides".
- **Removed:** `pollTimer`, `schedulePass`, `clearPollTimer`, `passInFlight`, `passAgain`, the old `pass()`. The new `pass()` wraps `runPass`, logs a failure and triggers the 30 s retry.
- **`stop()`** disposes the watch and nulls it; `start()` after `stop()` builds a fresh one. `kick()` is `this.watch?.trigger(0)`, a no-op when stopped.
- Per-join attempt timers and their backoff are unchanged.
- `NOTE:` on `PENDING_JOIN_BACKSTOP_MS`: on a cadre above 16 machines, a machine outside a join table's cohort learns of a dismissal or another machine's outcome up to 10 min late. A 30 s pass while any join is pending was declined. Revisit if such a cadre is seen attempting dismissed joins.
- `cadre-node.ts`: the 30 s cost NOTE in `startPendingJoinRunner` is gone (no longer true). `useOwnerSigner`'s kick comment now says why the kick is still needed: wiring a signer writes no watched table, so without the kick the runner would wait for its backstop.

Docs: `docs/strands.md` → "Who retries" describes the new schedule. `docs/architecture.md` → "Table change subscriptions" → "Consumers" is now a list. It names the membership rows view (already there), `StrandWatcher` (added: it was a consumer the list did not name) and this runner.

## Checked by reading (please re-check)

- **A pass's own writes wake exactly one follow-up pass, which does nothing.** An expiry outcome write, an age-out delete or a re-issue commits to a watched table. The follow-up pass then reaches `consider`, which does nothing for each case: a finished row whose age-out is not due; a pending row with its timer armed or queued; a row with an attempt in flight (it returns early). An age-out delete leaves the row gone, so the follow-up forgets it. `observeRows` stages invitations in memory and writes nothing. No loop.
- **`requestJoin` / `dismissPendingJoin` on this machine.** The insert wakes a pass while `attemptNow`'s attempt runs, and `consider` returns on `entry.attempt`. A dismissal calls `forgetRow` first; the delete's pass finds the row gone.
- **Retry triggered during a run.** A `trigger(30_000)` from inside a pass arms a wake that `settled()` keeps (it only adds the backstop). A change that arrives meanwhile runs a pass sooner, and that run clears the 30 s wake, which is fine because that pass re-reads everything anyway.
- **Becoming an owner.** `isOwner()` reads nothing without a signer, so a non-owner machine's start pass touches no table. A replicated join row is therefore not heard there until `useOwnerSigner` → `kick()` runs a pass that reads, and so arms, the five tables. Correct, because a non-owner does nothing with the rows. A replicated `OwnerKey` change now takes effect on arrival (it was up to 30 s).

## Known gaps

- **Full suites and the measurement are unrun.** They are parked as the "Second arm" of `tickets/blocked/strand-watcher-change-driven-verification.md`. That arm covers the `cadre` idle arm of `message-cost-accounting`: the runner cost 24 of the 155 control reads per idle minute; expected after is about 1 per 10 minutes per node. It also covers `pending-join-survives-restart` and `control-founding-consult-budget.spec.ts`.
- **`control-founding-consult-budget.spec.ts` may move.** `kick()` used to start a pass synchronously inside `useOwnerSigner`; it now arms a 0 ms timer, and the spec's `settleStart` stops the runner right after, so the genesis phase can lose the runner's reads. This is recorded in the blocked ticket's arm as the reason to give for any move.
- **Possible self-wake through read-repair.** The change subscription hears read-repair landings. If a pass's read of a never-written join table on a two-machine cadre lands a repair, one more pass follows. It is bounded, because a later read finds nothing new to repair, but it was not measured. The blocked ticket names it as the first suspect if the idle reads do not fall.
