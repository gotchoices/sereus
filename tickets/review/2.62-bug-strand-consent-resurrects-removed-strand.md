# Review: `Strand` consent branch bound to the redemption that authorized it

## What was wrong

`CadreControl.Strand` rows may be seated two ways: owner-signed, or **by consent** — no
signature at all, authorized purely by the existence of a `CadreControl.FormationUsage` row
naming the same strand id (second branch of `Strand.AuthorizedInsert`).

Removal requires an owner signature over a distinct `'remove'` digest **plus** a
`CadreControl.Revocation` tombstone retiring the row's one-off nonce (`StampId`) in the same
transaction. The tombstone is what makes removal permanent — `NotRevoked` refuses any later
insert naming a retired nonce.

The consent branch named no nonce. It only asked "does *a* `FormationUsage` row exist for this
strand id?", and `FormationUsage` is append-only (`InsertOnly check on update, delete (false)`),
so that row outlives the strand's removal forever. After a fully legitimate owner-signed,
tombstoned removal, any writer could re-insert the `Strand` row with **no owner key, no
signature**, a **fresh** `StampId` (sidestepping `NotRevoked`, which retires only the one nonce
the removed row carried), and an **attacker-chosen** `MemberPrivateKey` — the party's own secret
key for that network.

The control database is replicated across the party's cadre and peers write SQL to it directly,
so the CHECK constraints *are* the authorization boundary; "any writer" means any node that can
reach the control network.

## What landed

Consent now binds to **one specific strand row**, not to a strand id forever.

**Schema** — mirrored byte-identically into both copies (`schemas/control.qsql` and
`CONTROL_SCHEMA` in `packages/cadre-core/src/control-schema.ts`; `control-schema-drift.spec.ts`
is the guard, and it passes):

- `FormationUsage` gained `StrandStampId text not null` — the `Strand.StampId` this consent
  record authorizes. Deliberately **not unique**: in the bound (provision-then-record) path
  several invitees each write a usage row against the same host strand, so many usage rows
  legitimately share one stamp.
- `FormationUsage.StrandExists` matches on the `(id, stamp)` pair:
  `S.Id = new.StrandId and S.StampId = new.StrandStampId`.
- `Strand.AuthorizedInsert`'s consent branch additionally requires `FU.StrandStampId = new.StampId`.
- `Strand.NoUpdate`'s comment updated to say the consent branch keys on `(new.Id, new.StampId)`.

Removing a strand retires that stamp into `Revocation`, so `NotRevoked` permanently closes that
consent record's branch. A legitimate re-join still works: a new redemption writes a new usage
row carrying a new `StrandStampId` beside a `Strand` row with that fresh stamp, and both deferred
CHECKs see both rows at commit — exactly the shape `redeemInvitation` already writes.

**Writers** (`packages/cadre-core/src/control-database.ts`):

- `execFormationUsageInsert` takes and writes `strandStampId`. It is the **only**
  `FormationUsage` insert site in the repo (verified by grep), so no other writer needed the column.
- `redeemInvitation` passes the same freshly-minted stamp it gives the `Strand` insert.
- `recordFormationUsage` reads the live strand stamp via the pre-existing
  `ControlDatabase.queryStrandStampId` and throws a new `MissingHostStrandError` when the strand
  is absent, rather than letting the deferred `StrandExists` CHECK drop the write at commit.
  `MissingHostStrandError` is re-exported from `packages/cadre-core/src/index.ts`.

No signature/digest changes: the consent branch is signature-free by design and the owner-signed
`'add'`/`'remove'` digests are untouched, so `control-authorization.ts` and every owner-signed
writer are unaffected.

**Docs** — `docs/architecture.md`: the `StrandFormationManager` paragraph gained a pointer
sentence; the control-layer list item under *Strand Membership Bootstrap* now explains the two
seating paths, the stamp binding, why removal sticks, and the "removal does not revoke the
invitation" residual.

## Use cases to exercise / validate

The interesting behaviour is entirely at the SQL-CHECK boundary. All of the below are covered by
committed tests; re-run them or drive them by hand against a real `CadreNode`.

1. **The hole itself.** Redeem an invite (`insertFormationInvite` + `redeemInvitation`) →
   owner-signed + tombstoned removal → unsigned re-insert of the same strand id with a **fresh**
   stamp must fail `AuthorizedInsert`, and the row must stay gone.
2. **The other door.** The same unsigned re-insert with the **original** stamp *does* satisfy the
   consent branch (the surviving usage row names exactly that pair), so only `NotRevoked` stands —
   and it rejects. Both doors are pinned by name.
3. **Re-join still works.** After that removal, a second `FormationInvite` + a second
   `redeemInvitation` for the **same strand id** succeeds and seats a row with a new stamp. This
   is the property that must not regress into a permanent id blacklist.
4. **Redeem path stamps correctly.** The usage row `redeemInvitation` writes carries
   `StrandStampId` equal to the seated `Strand.StampId`.
5. **Record path stamps correctly.** Usage rows `recordFormationUsage` writes against a
   pre-existing owner-signed strand carry that strand's live stamp.
6. **Wrong stamp is refused.** A hand-written `FormationUsage` insert naming a **live** strand
   with a wrong `StrandStampId` is refused by `StrandExists`; the identical insert with the live
   stamp lands, so the rejection is about the stamp and nothing else.

Tests added: two in `packages/cadre-core/test/control-revocation-replay.spec.ts` (cases 1–3,
beside the existing *"a formation invitation authorizes forming a strand, never destroying one"*
test), one new test plus assertions folded into two existing tests in
`packages/cadre-core/test/control-formation-invite.spec.ts` (cases 4–6).

## Known gaps — treat these as the starting point, not the finish line

- **Integration tests were not run.** `packages/integration-tests` drives real networks and its
  wall clock routinely exceeds the runner's limits, so it was deferred. The one place it touches
  this change is `src/harness/test-network.ts:198`, which calls `recordFormationUsage` against a
  strand that exists in the inviter's own control DB — the path that now reads the live stamp
  first. It should be unaffected, but it is unverified here.
- **Browser / e2e readers were not run.** `packages/reference-app-web/src/lib/cadre-web.ts` and
  `e2e/fixtures/formation-responder.ts` select `Token, UseNumber, StrandId` from
  `FormationUsage` — no `select *`, no inserts — so they were reasoned about, not executed.
  `cadre-web.ts:attemptUnauthorizedStrandWrite` is a deliberately-rejected probe and stays
  rejected (now via a stricter consent branch).
- **No migration.** Repo policy is no backwards compatibility yet. A control database persisted
  before this change has `FormationUsage` rows without the column and is **not** migrated. Do not
  build a migration path; this is a deliberate deferral.
- **Convergence residual (pre-existing, unchanged by this ticket).** `NotRevoked` is a
  per-transaction check against locally visible rows, so a node that has not converged on the
  `Revocation` row can still accept a replayed insert and hold the resurrected strand alongside
  its tombstone. `Strand` has no read-side filter for this (unlike `CadrePeer`, whose
  `CadreNode.listAuthorizedMembers` drops rows with retired stamps). Already documented in the
  schema's `Strand.NotRevoked` NOTE.
- **Removal does not revoke the invitation.** By design: an invite with `TotalUses` null or with
  uses left over can be redeemed again and will re-seat the strand id with a fresh stamp. That is
  the legitimate re-join path, but it means an operator who wants a removal to be final must also
  delete the `FormationInvite` (`FormationInvite.AuthorizedDelete` exists for that). Stated in the
  schema comment and in `docs/architecture.md`; worth a reviewer's eye on whether the operator
  tooling surfaces it.

## Rejected alternatives (recorded; do not re-litigate)

- **Derive the strand stamp from `(Token, UseNumber)` instead of adding a column.** A derived
  stamp is *guessable*. `Revocation.RowIsGone` deliberately permits tombstoning a never-existing
  stamp, on the stated grounds that stamps are 128 bits of CSPRNG output and cannot be
  pre-planted. A guessable stamp turns that into a denial-of-service: anyone pre-files a tombstone
  and the future redemption is refused by `NotRevoked`.
- **Have the consent branch require that no `Revocation` row exists for any nonce ever tied to
  this strand id.** Needs the strand id recoverable from the tombstone (`Revocation` stores only
  `(TableName, StampId)`), and it blacklists the id permanently — re-join must stay possible.
