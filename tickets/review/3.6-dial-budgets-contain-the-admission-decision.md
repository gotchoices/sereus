# Dial budgets contain the listener's admission decision

## What changed

libp2p's listener runs the inbound connection gate (`denyInboundEncryptedConnection`) before it answers the multiplexer negotiation the dialer is blocked on (`node_modules/libp2p/dist/src/upgrader.js`: gate at line 189, dialer's `mss.select` at 277 — checked). So the gate's time, capped at `ADMISSION_DECISION_TIMEOUT_MS` (2 000 ms, fail-open), is spent on the dialer's dial clock. The listener's `inboundUpgradeTimeout` signal is created before the gate (line 64), so it contains the gate time too.

- `ADMISSION_DECISION_TIMEOUT_MS` moved from `membership-connection-gater.ts` into `link-budget.ts` (value, `cuts off by design` directive and comment kept; the comment's last bullet now describes the derivation instead of "a ticket will count it"). It lives there because `link-budget.ts` imports nothing of cadre-core's own; importing the gater would close the cycle link-budget → gater → seed-bootstrap → link-budget. No re-export from the gater.
- `relayedDialBudgetMs(rtt) = 4 × rtt + 2 000` → 16 000 ms at the default 3 500. `connectionManagerTimeouts` (libp2p `dialTimeout` = `inboundUpgradeTimeout`), `DEFAULT_CONTROL_COHORT_PER_ADDRESS_DIAL_TIMEOUT_MS` (per-peer total 64 s) and the peer-join push dial follow.
- `relayedRequestBudgetMs(rtt) = relayedDialBudgetMs(rtt) + 2 × rtt` → 23 000 ms. Wake/strand-address/seed-delivery attempts follow; the two-attempt wake budget is 46 s. `RELAYED_REQUEST_ROUND_TRIPS` is kept as the link-time count it documents.
- `relayReservationBudgetMs(rtt) = 4 × rtt + 2 × 2 000` → 18 000 ms (a party-run relay decides the connection, then the reservation).
- `circuitRequestBudgetMs` unchanged (opens no connection).
- Module doc records that the measured 12 094 ms crossed **no** gate: `relayed-dial-cost-by-latency.integration.ts` is bare libp2p with no cadre gater, so the allowance sits on top of the measurement.

## Beyond the ticket's file list (reviewer: check these calls)

- **`packages/reference-app-rn/src/host-node-request.ts` `connectMs` 120 000 → 140 000.** Its doc said 120 s "covers two full dials of the lent node at cadre-core's per-peer limit (56 s)". At 64 s per dial, two dials are 128 s, so 120 s no longer held the stated relationship. 140 s keeps a margin similar to the old 8 s. The file deliberately has no imports, so it stays a literal rather than deriving from cadre-core. `docs/reference-app-rn.md` troubleshooting line updated to match (140 s, 16 s per address).
- **`ops/docker/libp2p-infra/src/main.ts`** sets the relay container's libp2p limits by hand "in step" with `connectionManagerTimeouts()`; bumped 14_000 → 16_000 and noted the container runs no gate. Takes effect only when that image is rebuilt/redeployed.
- **`relayed-dial-cost-by-latency.integration.ts`** — the ticket said read-only; I edited only its doc comment's "budgets in force" table (14 s → 16 s, with the 1750 ms / 2000 ms one-way ceilings) and marked the historical "Proved" paragraph's 14 000 ms as "then". No code change, scenario not re-run.
- `types.ts` `controlCohort.perAddressDialTimeoutMs` doc now says an override replaces the whole derived budget, allowance included (also stated on `relayedDialBudgetMs`).
- The 14 000 / 21 000 figures in `link-budget.ts`'s round-trip table and in `DECLARED_LINK_ROUND_TRIP_MS`'s doc were kept on purpose: they are link time, and the text now says so and points at the allowance.

- The receiver's application-level membership check inside a wake or strand-address exchange (`isMember`) is still not counted — that is a separate, deliberate gap documented in cadre-consistency.md and on `DEFAULT_WAKE_TIMEOUT_MS`; the new allowance is for the connection gate, not that check.
