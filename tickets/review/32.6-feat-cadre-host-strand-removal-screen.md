## Three deviations from the ticket, all deliberate

**1. The strands slice has four fields, not two.** The ticket sketched
`strands: { list, controlConnections }`; it also required that "empty and loading states are
distinct". Those two cannot both hold, so the slice is
`{ list, controlConnections, loaded, error }`. `loaded` flips true on the first successful
fetch; `error` holds the last failure's message and is cleared by the next success. The page
renders three distinct states from them — `Couldn’t load strands: <msg>` / `Loading…` /
`This party doesn’t take part in any shared networks yet.` Without `error`, a failed fetch would
sit on "Loading…" forever; without `loaded`, it would claim the party belongs to nothing.

**2. `ConfirmDialog` grew a third new prop, `note`.** The ticket named only `requireText` and
`requireTextLabel`, but also required a ⚠ durability line "in either dialog". `message` renders
inside a single `<p class="muted">`, so folding the warning into it would render the warning as
muted grey fine print. `note` renders as its own warning-coloured block below the message.

**3. `let confirmStrand = $state<StrandSummary | null>(null)`, not
`let confirmStrand: StrandSummary | null = $state(null)`** (the shape `TrustCircle.svelte` uses).
With the annotation form, TypeScript narrows the variable to `null` for the rest of the module
scope and the `$derived` below it reads a property off `never` — `check:svelte` fails. There is a
comment at the site. `TrustCircle.svelte` gets away with the annotation form only because it
touches the variable exclusively from the template, which `svelte2tsx` compiles into a separate
function where the narrowing does not reach.

## Behaviour a reviewer should check

**The confirmation is two-strength, keyed off `requiresTypedConfirmation(strand.type)`.**

| Strand type | Dialog | `DELETE` sent |
|---|---|---|
| `'o'` open | plain confirm, one click | `/api/strands/:id` |
| `'c'` closed | confirm + must type the id exactly | `/api/strands/:id?confirm=1` |

The same predicate picks the dialog *and* the query flag, so the two can't drift into a state
where the page sends `confirm=1` without having asked. `confirm=1` is never sent for an open
strand and is never retried onto a refusal.

**Match rule** (`typedConfirmationMatches`): trim both sides, then exact. Paste is fine; a case
difference, a substring, a superstring, and a blank `expected` all fail.

**Feedback is exactly one of four things per removal** (`reportRemoval` in `Strands.svelte`):

| Response | What the user sees |
|---|---|
| `published: false` | info toast `<id> was already removed` |
| `removed && alone` | dismissable inline banner, **no** toast |
| otherwise | success toast `Left <id>` |
| a thrown `ApiError` with status 428 | the server's own message, verbatim |

`alone` is sampled by the node on every call including one that wrote nothing, which is why the
banner needs `removed` as well. Any other error becomes `Leave failed: <msg> (<code>)`.

**The `controlConnections === 0` advisory** appears in the dialog *before* the removal; the
`alone` banner appears *after*. Both are advisory — the ticket's point is that
`controlConnections` is a read-time snapshot, possibly stale by the click.

## Manual pass — the page itself is NOT covered by tests

Say this plainly: **this package has no Svelte component test harness** (`vitest.config.ts` runs
the `node` environment; `ui/__tests__/` holds only plain-module tests). One was deliberately not
stood up here. So everything below was reasoned through and typechecked but **never executed**:
the dialog copy, the disabled-until-typed button, the input reset, the Enter/Escape handling, the
banner, every toast, the row rendering, and the whole of `Strands.svelte` and the new
`ConfirmDialog` branches. The automated tests cover only `strand-confirm.ts` and the router.

**I did not run a founder-mode host.** The following needs a live one with at least one open and
one closed strand published:

- Open strand: `Leave` → one dialog → one click → row gone, `Left <id>` toast.
- Closed strand: the confirm button is disabled on open; typing a wrong id never enables it;
  typing the exact id (or pasting it) enables it; Enter in the field submits only once enabled.
- Cancel a closed-strand dialog, reopen it (same strand and a different one) — **the field must
  be empty both times.** This is the reset `$effect` in `ConfirmDialog`; it keys on `open` and
  `requireText`, so it is the single most likely thing in this diff to be subtly wrong.
- Escape still cancels; the backdrop click still cancels.
- Both buttons stay disabled while the request is in flight (`pending`).
- Stop the owner node's control connections → the ⚠ line appears in the dialog, and a removal
  comes back `alone: true` → banner, no success toast, and Dismiss clears it.
- Two tabs: remove in one, the other's list updates via `strands-changed`.
- A long/opaque id, and one containing `%2F`: it must wrap in both the row and the dialog, and
  the round-trip must reach the right row (`encodeURIComponent` on the way out).
- The two existing `ConfirmDialog` callers in `TrustCircle.svelte` pass none of the new props —
  confirm Remove-member and Revoke-invite are visually and behaviourally unchanged. Note the
  dialog now carries a `max-width: min(32rem, calc(100vw - 2rem))` it did not have before.

## Known gaps

- **Donor-only installs.** The Strands nav item shows and the page 404s into an error toast (now
  also an inline `Couldn’t load strands: …` line). Same as Trust Circle and Connectivity; one
  problem, one fix, tracked in `tickets/backlog/feat-cadre-host-donor-aware-ui`, which already
  carries a Strands arm. Deliberately not fixed here, and no second page-local gate was invented.
- **No `refreshStrands()` in `App.svelte`'s global `onMount`** — the page fetches on its own
  mount, so donor dashboards get no boot-time error toast.
- **Tripwire, parked as a `NOTE:` comment** at the `'strands-changed'` case in
  `ui/src/lib/state.svelte.ts`: the removing tab fetches twice (its own explicit refresh plus the
  SSE echo). Harmless at current list sizes; the comment says what to do if it ever shows.
