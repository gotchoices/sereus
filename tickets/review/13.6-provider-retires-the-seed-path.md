# Provider retires the seed path — review handoff

Last ticket of the `provider-client-and-sign-up` chain. `POST /containers` now requires `join` (`claim` or `invitation`); the seed path (`pinnedOwnerKeys` at create, `PUT /containers/:id/seed` afterwards) is gone from the provider, its orchestrators, the integration harness and the docs. No backwards compatibility beyond what the ticket asked for (old records load cleanly).

## What changed

**cadre-provider**

- `CreateContainerRequest`: `join` required; `bootstrapNodes` and `pinnedOwnerKeys` removed. `partyId` stays on the service request but is derived by the validator from the join (placeholder for a claim, the bundle's for an invitation), never read from the body. The service still forces the placeholder for a claim, guarding a direct caller.
- Validator (`create-request-validation.ts`): reads `join`, `profile`, `strandFilter`, `resources`, `tags`. A missing `join` is `join is required: …`. `partyId`, `bootstrapNodes` and `pinnedOwnerKeys` in a body are **ignored like any unknown field**, not refused by name (see "Decisions" below). The `{ optional }` option became `CreateRequestOptions { claimable }`; `RouteContext.bootstrapNodesOptional` became `claimable` (set from `docker.publicHost` in `server.ts`).
- Deleted: `owner-key-validation.ts`, `bootstrap-node-validation.ts` and their tests; `PUT /containers/:id/seed`; `ContainerService.applySeed`; `Scope.ContainersSeed`; `Container.seedEndpoint`/`seedToken`/`pinnedOwnerKeys`; `OrchestratorCreateRequest.bootstrapNodes`/`pinnedOwnerKeys`; `OrchestratorCreateResult.seedEndpoint`/`seedToken`; `NodeEnvSpec.seedToken`; `CADRE_SEED_TOKEN`, `CADRE_OWNER_KEYS` and `CADRE_BOOTSTRAP_NODES` from `buildNodeEnv`; the pins-beside-a-join throw in `joinEnv`; the seed-token clause of `redactContainer`; the seed-token mint in `DockerOrchestrator` and `MockOrchestrator`.
- `joinFor` takes a required request. `Container.join` stays optional (records an earlier provider wrote have none). `OrchestratorCreateRequest.join` stays optional because cadre-host's `HostedSpawnRequest` extends the type and carries its join in its own fields.
- `FileStore.loadCache` keeps every field it parses, so it now deletes `seedToken`, `seedEndpoint` and `pinnedOwnerKeys` on load. This matters beyond tidiness: the API redaction no longer knows `seedToken`, so without the strip an old record would serve its token in `GET /containers/:id`.
- The "why the provider does not import cadre-core" rationale lived in the deleted `owner-key-validation.ts`; it now lives in `invitation-validation.ts`, and `node-code.ts`, `multiaddr-destination.ts` and `__tests__/test-invitation.ts` point there. cadre-core's `ed25519-key.ts` and its spec lost the "restated in the provider, keep in step by hand" note, since the provider copy is gone.
- `GET /containers/:id/peer` stays. `enrollIfHealthy` and the reap sweep never read seed fields (checked by reading); two comments that called `enrolling` "seedable" now say a slow node can still be claimed or redeem its invitation.

**cadre-host** (slightly beyond the ticket's "nothing else"): `OrchestratorCreateResult` is shared, so `HostProcessOrchestrator` had to stop returning `seedEndpoint`/`seedToken`. With nobody holding the token any more, it also stopped minting it and setting `CADRE_SEED_TOKEN`, so a hosted child registers no seed route (nothing ever called it; hosted nodes join by claim or invitation). `buildChildConfig` writes `bootstrapNodes: []` instead of reading the removed request field; `hosted-node-service.ts`'s spawn request drops `bootstrapNodes: []`. The `refuseRespawnOverLiveChild` comment no longer explains itself with a seed token. Tests: `bootstrapNodes` removed from request literals, seed fields from the fake orchestrator's result.

**integration-tests**: `provider-seed-accepted` and `provider-drone-phone-requester` deleted. `ProviderProcessOrchestrator` no longer mints a seed token. Helpers only those two used are removed: `withPeerId`, `readNodeLocalStore` (+ `NodeLocalEnvelope`) in `child-node-fixtures.ts`, and `OwnerCliNode.addDrone`. `provider-container-claimed-by-phone` took over the "why the public host is a name" explanation it used to borrow from the drone scenario. `cadre-host-orchestrator-lifecycle` lost a `bootstrapNodes: []`. cadre-core's `control-write-retry.spec.ts` comments that named `provider-seed-accepted` as a live reproducer were reworded.

**Docs**

- Provider README: API and scopes tables lose the seed rows (the scopes table gains the missing `GET /containers/:id/code` row); the env-var and config text say `publicHost` enables claims; "Seed trust" and "Bootstrap addresses are checked at create time" sections removed (the generic body-validation sentence moved into "Joining a cadre"); "Phones dial containers at the public host" rewritten around the claim; one-shot example uses an invitation body; upgrade note added under "Joining a cadre" ("Upgrading from the seed path").
- architecture.md: the ticket's named sections, plus places the ticket did not list but that described the provider forwarding seeds: "Enrollment Flow: Server Adds Drone" (now the CLI flow, `cadre enroll add` + `cadre start --seed`), "Simple API" option B and "Helper Functions" (provider `initializeNode` examples), the Seed Delivery Protocol's provider paragraphs (replaced by a one-paragraph "Hosted and rented nodes"; the delivery table gains a "Node HTTP route" row for a hand-run image), the Node-local state sentence about runtime seed paths, and the Implementation Status lines. The create-request-validation paragraph moved to Provider Flow. The intro sentence is now "never has an owner's signing key and never handles a seed" — "owner key" alone would be false, since the record stores the public owner key a claim names (`Container.ownerKey`).
- testing.md drops both scenarios from its index; their still-true details (OS-assigned ports, admin-channel read, `/dns4/localhost`) moved into the claimed-by-phone bullet. cadre-host.md's env list and cadre-core's README `addDrone` example updated.
- cadre-cli's Docker files (`docker-compose.yml`, `env.example`) untouched, as the ticket said.

**Board**: `tickets/backlog/debt-provider-seed-endpoint-token-pairing-untyped.md` deleted (the two fields it wanted typed as a pair no longer exist). `tickets/backlog/debt-docker-entrypoint-untested.md` named `provider-seed-accepted` as the harness's proof; it now names the two join scenarios.

## Decisions a reviewer may want to revisit

- **Retired body fields are ignored, not refused.** A client still sending `pinnedOwnerKeys` beside a `join` gets a 201 and no pins. I chose this because refusing named retired fields is compatibility code, and no client in the repo sends them (cadre-core's `CreateContainerBody` is `{ join, profile?, tags? }`). If silent acceptance looks risky, it is a one-line `refuse` in `validateCreateContainerRequest`.
- **`partyId` kept on `CreateContainerRequest`** as a validator-derived field, rather than folding the party into the join type. The service's claim override keeps a direct caller honest; the moved test pins it.
