# Review: control-cohort observe/wait helpers, and widened forcing helpers

Helpers only. The scenario that uses them to drive a real three-machine control write is
the follow-on ticket `debt-harness-party-multi-machine-control-write` (in `implement/`).

## Vocabulary

- **Control cohort** — the peers a control-database write is offered to, derived by
  `Libp2pKeyPeerNetwork.findCluster(key)`. The write commits when a super-majority
  approves; a **one-member** cohort commits on the writer's own vote, so a passing write
  proves nothing about how many machines took part.
- **Party** — `createTestParty` output: one owner node plus zero or more **drones**.
  Drones dial only the owner, never each other.
- **Harness node** (`TestCadreNode`) — a bare libp2p node in a party. Distinct from
  `CadreNode`, the `cadre-core` class whose libp2p node hides behind `getControlNode()`.

## What landed

### New — `packages/integration-tests/src/harness/control-cohort.ts`

Exported from `harness/index.js`. Kept out of `wait-utils.ts` deliberately: that module's
only import is `debug`, and these helpers need libp2p/optimystic types.

- `CONTROL_COHORT_PROBE_KEY` — one fixed probe key. Sound because `findCluster` returns
  the ring's closest-k peers with k = `CONTROL_REPLICATION_BREADTH` (16), so in any party
  under 16 nodes it returns *every* peer FRET classifies as serving the network, whatever
  key is asked.
- `readControlCohort(party, node?)` — one-shot read; defaults to the owner node.
- `waitForControlCohort(party, minPeers, options?)` — polls to `minPeers`, resolves to the
  member peer ids. Defaults `timeoutMs` 15000 (~3× the measured ~5 s ring convergence),
  `intervalMs` 250. `options.node` picks whose view to observe.
- `observeControlCohorts()` — wraps (does not substitute) the installed `findCluster` and
  records call count + per-call cohort size. The anti-vacuity instrument for wait-based
  tests, where `forceFullCohort`'s counters do not exist because nothing is forced.

The file header states, for a reader with no prior context: what a control cohort is, that
waiting is the default tool because the ring converges, that forcing is a stopgap, why one
probe key suffices, the restore-ordering rule, the process-wide prototype-patch caveat, and
that observing *while forcing* records the forced sizes and so proves nothing.

### Widened — `forced-cluster.ts`

`forceFullCohort` and `pinCoordinator` now take `readonly CohortNodeSource[]` where
`CohortNodeSource = CadreNode | TestCadreNode | Libp2p`, resolved by one shared
`resolveControlLibp2p(node, who)`. Discrimination is `in`-based, in order: `getControlNode`
→ `CadreNode`; `libp2p` → `TestCadreNode`; otherwise a structural `Libp2p` check on
`peerId` + `getMultiaddrs`. Verified unambiguous today — `CadreNode`'s control node is the
*private* field `controlNode` (`cadre-node.ts:175`) and it exposes no `libp2p` property, and
`TestCadreNode` has no `getControlNode`. A comment says so, so adding either field to the
other type is a conscious change.

Both handle contracts (`ForcedCohortHandle`, `PinnedCoordinatorHandle`) and both loud
checks (no multiaddrs → throw, no public key → throw) are unchanged. The header gained the
restore-ordering rule now that three helpers can stack on `findCluster.prototype`.

### Comment repointed — `test-party.ts`

The `NOTE:` at ~lines 56-61 named the now-archived ticket slug
`debt-harness-control-cohort-observable-and-forced`; it now names
`waitForControlCohort` (`harness/control-cohort.ts`). The drone-cap `NOTE:` was left alone.

## Use cases for testing / validation

New scenario: `src/scenarios/control-cohort-harness-helpers.integration.ts`. No control
writes; **7 tests, 13.7 s total.** What each pins:

- one-node party, `minPeers: 1` → resolves on the first poll (<2 s asserted) with exactly
  the owner's peer id. Proves the degenerate case does not deadlock.
- three-node party, `minPeers: 3` from the owner → resolves and the ids are the owner plus
  both drones. Measured 790 ms, well inside the 15 s default.
- `minPeers: 4` on a three-node party → throws in <1 s (asserted), message naming both
  counts. Proves an impossible request never burns a timeout.
- `minPeers: 0` and `-1` → throw, so a caller's assertion can never be vacuous.
- timeout message names the party and the observed size.
- `observeControlCohorts()` records a non-zero call count and passes the real size through;
  `restore()` twice is a no-op and the real method is back (asserted by showing a later
  read is *not* counted).
- `forceFullCohort([party.ownerNode, ...party.droneNodes])` — a harness party, the case
  that did not compile before — yields all-3 cohort sizes from both the owner's and a
  drone's view, then restores.

**Substitution to check.** The ticket asked for the timeout-message case as
`waitForControlCohort(party, 3, { timeoutMs: 1 })` on a fresh party, and flagged it might
flake. It is instead run against a **drone's** view with a 2 s budget: drones never dial
each other, so a drone's cohort caps at 2 permanently and the timeout is a property of the
topology rather than a race with ring warm-up. This also exercises `options.node`. It ran
in 2094 ms. Judge whether the swap loses anything the original case covered.

## Known gaps — treat this as a floor, not a finish line

- **The `CadreNode` path of the widened helpers is not covered by a green run.** The one
  existing call site, `control-write-degraded-cohort-member.integration.ts`, needed no edit
  (as the ticket predicted) and type-checks, but its `beforeAll` fails at
  `Timeout waiting for B resolves C's signed address record after 45000ms`
  (`:406`, 56 s, all 6 tests skipped) — **before** it reaches the `forceFullCohort` /
  `pinCoordinator` calls at `:431-436`. So the widening is neither exercised nor implicated
  by that run. That symptom is the one tracked as
  `blocked/transactor-key-network-ignores-network-scoping` (mutual `CadrePeer` address
  resolution between two non-owner members), so per the pre-existing-failure rule no new
  `.pre-existing-error.md` was filed — but note that ticket names
  `control-cohort-three-node-isolation.integration.ts`, and this is a *second* file showing
  the same symptom. Worth confirming rather than taking on trust. Nothing was skipped,
  weakened, or commented out.
- **No test forces a `Libp2p` object directly.** The third `resolveControlLibp2p` branch
  (and its unrecognised-shape throw) is unexercised.
- **Restore ordering is documented but not tested.** No case stacks force + pin + observe
  and tears down out of order to prove the rule bites.
- **`observeControlCohorts` counts a throwing call in `callCount()` but contributes no
  `cohortSizes()` entry**, so the two arrays can differ in length. Documented on the handle;
  no test covers a throwing `findCluster`.
- The three-node wait resolved in **790 ms**, not the ~5 s the design assumed. The 15 s
  default is therefore ~19× the observed convergence here, not 3×. Nothing is wrong, but
  the measurement the design rests on may be conservative.
