# Cadre invitation and owner grant redemptions read the row once

Split from `plan/formation-and-redemption-read-each-row-once`. Siblings: `formation-responder-reads-the-invitation-once` (in review), `joiner-hands-its-join-to-the-launch`.

## What changed

**One read of the held row, carried through.** `MemberRedemptionHandler` (the shared member side of `/sereus/cadre-invite` and `/sereus/owner-grant`) has a new hook `readHeld(request)`; `decide` calls it once, after the checks that cost no database work, and passes the result (`held`, the row this member holds or null) to `isLive(request, held)` and `redeemAdmitted(request, remotePeerId, held)`. The base class gained a third type parameter, `Held`. A failed `readHeld` propagates to `handleStream` and is answered `internal` (retryable); see gaps below.

**Liveness takes the held row.** `ControlDatabase.isCadreInviteLive(invite, held, nowMs?)` and `isOwnerGrantLive(grant, held, nowMs?)` no longer read: they judge `held`, else the bundle's copy once its issuer signature verifies. `held` is required (not optional) so no caller can silently fall back to judging the copy. Their docs now say why the use count is read twice (early: decides the push; in the lock: decides the seat).

**Seat only when nothing is held.** Both handlers call the seat (`seatCadreInvite` / `seatOwnerGrant`) only when `held === null`; the seat's own in-lock stamp read stays, since it makes the seat insert-if-absent against a concurrent seat. The seat-and-refuse code moved into a private `seat()` per handler.

**Redeem takes an optional held row.** `redeemCadreInvite({ ..., held? })` and `redeemOwnerGrant({ ..., held? })` skip their in-lock `queryCadreInvite` / `queryOwnerGrant` when `held` is given. Callers pass only the row read from this database, never the bundle's copy (the requester picks a copy's `TotalUses` and `IssuerKey`; `assertCadreInviteSeatRemains` must judge the stored cap). After a fresh seat (`held === null`) nothing is carried and the in-lock read stays.

**Reply peers before the write.** `CadreInviteHandler.redeemAdmitted` calls `peersBestEffort()` (→ `querySeedPeers`) after the seat and before `redeemCadreInvite`, still best-effort, only on the accepted path's way to the write; refusals carry no peers, as before. The list therefore lacks the device's own new row; the device drops its own row from `reply.peers` anyway (`cadre-node.ts` `mergeSeedPeers(… filter(peer.peerId !== selfPeerId))`).

**Reply row.** Both replies now carry `held ?? request.invite` (resp. `grant`) instead of always the request's copy. See gaps.

**Local grant path.** `CadreNode.redeemOwnerGrantLocally`: alone refusal, then one `queryOwnerGrant`, seat only when null, `isOwnerGrantLive(bundle.grant, held)`, then the approval and `redeemOwnerGrant({ ..., held })`. Ordering of refusals before the approval is unchanged.

**Open-invitation minor: no change needed.** The ticket asked to skip this machine in `CadreNode.resolveInvitationSiblings`. Confirmed by reading: `listAuthorizedMembers` already drops this node (`authorizedAmong`, `row.peerId !== selfPeerId`, check 1 of its documented predicate), so no self `CadrePeer` record is resolved and the bootstrap list does not carry this machine's addresses twice. The "empty `getMultiaddrs()`" edge case in the ticket is therefore moot. Not measured with a running node; verify by inspection.

## Known gaps and judgement calls for the reviewer

- **Reply row is now the held row.** When a member holds the row, the reply carries it rather than echoing the request's copy. For an honest device the two are identical. For a request whose copy was altered but names a real key, the member already redeemed against its own row before this change too; previously the device then failed its own reply check on the echoed bad copy, now it receives the genuine row and passes. Confirm that is the wanted behaviour.
- **`readHeld` failure is `internal`.** Before, a failure of the liveness read was logged and the writes went ahead without the push; a failure of the in-lock read answered `conflict`/`internal` through `writeFailureRefusal`. Now a failed up-front read (after its own retries) ends the exchange with `internal`. Both codes are retryable for the device, and nothing is written. Consider whether it should go through `writeFailureRefusal` instead.
- **Liveness after a fresh seat judges the bundle's copy** (handler and local grant path). Before, the local grant path re-read the row it had just seated. They differ only when the seat adopted a cohort-held row (`adoptCohortHeldRow`) that differs from the copy, which needs a copy forged under a real key; that copy fails its signature check and is refused `grant-spent` instead of being judged on the real row.
- **Withdrawal between the early read and the write** still refuses at commit: the carried row only replaces the read of `CadreInvite` / `OwnerGrant` columns, and the schema's `NotRevoked` / `Authorized` CHECKs read `Revocation` and the committed tables themselves. Verified by inspection only.
- A targeted invitation's device (`PeerId`) is still checked against the request's copy in `checkRequest`, as before this change; the schema's consent branch checks the stored row at the write.
