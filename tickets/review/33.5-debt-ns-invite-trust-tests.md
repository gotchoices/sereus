## The behaviour under test

When someone joins a cadre by pasting an invitation next to a "seed" (the file
that tells a new phone who else is in the cadre), the app must write the
invitation's owner keys into its local trusted-owner record **before** it applies
the seed — otherwise the check that runs during seed-apply looks at an empty
record and rejects a perfectly good seed. `src/cadre-vm.ts:260-273` says so in a
comment and warns against folding the two calls together.

Every call the view models make to the node is appended to one shared ordered
array, and the tests assert that array whole. Two `toHaveBeenCalled()`s would
pass under a reorder; `expect(H.calls).toEqual([...])` does not.

### The mutations worth trying

The suites are only worth what they catch. These are the edits a reviewer should
make to confirm they earn their keep — each should turn a specific test red:

- In `src/cadre-vm.ts` `applySeed`, move the `await node.trustOwnerKeys(...)`
  block to *after* the `node.applySeed(...)` line → `applySeed with pinned owner
  keys > anchors the invite keys BEFORE applying the seed` (and the Settings
  end-to-end version of it).
- Change `'invite'` to `'operator'` in that same `trustOwnerKeys` call → `anchors
  the keys under the invite provenance`.
- Drop the `pinnedOwnerKeys?.length` guard so an empty array still builds a
  policy → `treats an empty pin list exactly as no pins at all`.
- In `ownerKeysFromInvite`, remove the `?? []` → `returns an empty list for an
  older invite carrying no owner keys`.
- Remove the `try/catch` rewrap there → `rewraps an unreadable invite with copy
  naming the enrollment invite`.
- In `onApplySeed`, move `this.seedInput = ''` / `this.enrollInviteInput = ''`
  above the `await` → both "keeps both fields" tests.
- Change the no-pins branch of the success message to `Pinned 0 owner key(s)` →
  `says no owner keys were pinned when the invite carried none`.
- In `stop()`, delete the `unbindEvents` call → `unbinds every strand event
  before dropping the node`.

## Deviations from the implement ticket

Both are deliberate; both are documented at the code site too.

**The ordering assertion is wider than specified.** The ticket asked for
`['trustOwnerKeys', 'applySeed']`; the test asserts
`['decodeSeed', 'trustOwnerKeys', 'applySeed']` — the whole log, since the fake
records `decodeSeed` as well. Strictly stronger, and it keeps the assertion an
exact-array one rather than a filtered subset.

**The fake node is one shared module, not duplicated per suite.** The ticket
described the fake inline in each spec, which is ~120 duplicated lines. It now
lives in `test/stubs/fake-cadre-node.ts`, reached from each spec through
`vi.hoisted(async () => import('./stubs/fake-cadre-node'))`.

The first attempt at sharing — plain `await import(...)` in both the spec's load
helper and the `vi.mock` factories, relying on `vi.resetModules()` to hand both a
matching fresh instance — **does not work**, and failed loudly (22 of 27 tests):
the mock factory keeps whichever instance it first captured, so the suite ends up
configuring a different fake node than the view model was handed. The hoisted
binding gives one instance for the file's lifetime, with an explicit `reset()`
called from every load helper. That reasoning is recorded in the stub's header —
worth keeping if the file is refactored.

## Known gaps — this is a floor, not a ceiling

- **The fake node is not type-checked against the real `CadreNode`.** It is
  handed to the view model through a `vi.mock` factory, which TypeScript does not
  check against the mocked module's type. A cadre-core signature change — say
  `trustOwnerKeys(source, keys)` — would leave these suites green while the app
  broke on device. Making the fake `implements`-checked against the real
  interface would mean stubbing the whole `CadreNode` surface; not attempted.
  A reviewer may reasonably judge that trade differently.
- **`pinnedKeyTrustPolicy` is real, but its consumer is faked.** The tests prove
  a working policy built from the pasted keys reaches `applySeed` — they exercise
  the policy directly by calling `evaluate`. They do **not** prove cadre-core's
  `applySeed` honours a passed-in `trustPolicy`; that contract belongs to
  cadre-core's own suite.
- **`src/cadre-phone.ts` is mocked wholesale in these suites.** Its real
  behaviour is covered separately by `test/cadre-phone.spec.ts`; nothing here
  proves the two fit together.
- **Settings actions outside the seed path are untested**: `onConnect`,
  `onDisconnect`, `onDialPeer`, `onCreateStrand`, `onModalOk`, and the `uuid()`
  helper. Out of this ticket's scope, but they are real uncovered branches.
- **Nothing here runs on a device.** The two-phone manual walkthrough is still
  the only proof that the real `CadreNode`, real SQLite anchor and real seed
  protocol behave as these doubles claim.
- **`src/chat-vm.ts` remains uncovered** — it needs `ObservableArray`, which the
  same directory-import rule that broke `@nativescript/core`'s entry point puts
  out of reach via the stub route. Not chased here; parked as
  `tickets/backlog/debt-ns-chat-vm-unit-tests.md`.
- **`test:bundle` was not run.** It compiles the app graph through webpack and
  neither `test/` nor `vitest.config.ts` is part of that graph, so this change
  cannot affect it. Flagging the skip rather than implying coverage.
