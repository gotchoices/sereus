## What was already checked (and found clean)

- **Digest field order.** `formationVouchMessage` (`control-database.ts:152-162`) matches
  the schema's `'vouch'` digest in `FormationUsage.Authorized`
  (`schemas/control.qsql:562`): `Token, UsageStampId, StrandId, PeerId, Disclosure`. Same
  order, same arity.
- **Nonce round-trip.** `mintUsageStampId()` → signed → passed as `usageStampId` into
  `redeemInvitation` / `recordFormationUsage`, both of which use `usageStampId ?? generateStampId(...)`.
  The value signed is the value inserted. Test (h) asserts this against a real database.
- **Enrollment pre-check parity.** `queryValidationKeyStampId` reads the live
  `ValidationKey` table, the same table the database CHECK verifies against — so the
  local pre-check and the authority agree on what "enrolled" means.
- **Approver hygiene.** `createHttpFormationApprover()` in the recorder constructor only
  validates `timeoutMs`; `fetch` is resolved lazily per request, so constructing a
  recorder in a runtime without `fetch` does not throw. Abort timer cleared in `finally`;
  response body released on every reject path. No leak found.
- **Outbound-request surface (SSRF).** The recorder now makes an outbound HTTP POST to a
  URL read from a replicated table. Not a defect: `FormationInvite.ValidationUrl` is
  covered by the owner signature (`insertFormationInvite` signs it as field 5), so the URL
  is the party operator's own choice, not attacker-supplied, and the response is never
  echoed to the joiner. Deliberately not filed.
- **Fail-safety when the write loses.** Every failure path — approval error, PK collision,
  deferred-CHECK rollback — writes no `FormationUsage` row, so the invite is not consumed.
  Test (j) asserts this for four failure categories.

## Findings to act on

### F1 (minor, fix inline) — `ResolvedHostStrand.validationUrl` is dead

`strand-solicitation.ts:50-57` added `validationUrl` to the `unbound` and `bound` variants,
with the doc reason *"so the manager can see approval is required without a second invite
read."* Neither is true:

- Nothing reads the field. `strand-formation-manager.ts` only switches on `kind`.
- The recorder does a second invite read anyway — `recordUsage`
  (`control-formation-recorder.ts:172`) and `provisionAndRecord` (`:239`) each call
  `queryFormationInvite(token)` themselves.

Keeping the field would be worse than removing it: threading a caller-supplied
`validationUrl` into `recordUsage` would move the choice of *which hook to trust* outside
the recorder that performs the write. The recorder must read it itself.

**Fix:** delete `validationUrl` from both variants of `ResolvedHostStrand`, delete the
paragraph at `strand-solicitation.ts:50-52`, drop it from the two `resolveStrand` returns
(`control-formation-recorder.ts:196`, `:206`), drop it from the manager's no-recorder
fallback (`strand-formation-manager.ts:297`), and update the three `toEqual` expectations
in `control-formation-invite.spec.ts:1224`, `:1234`, `:1237`.

### F2 (minor, fix inline) — the new `NOTE:` about spent approvals is factually wrong

`strand-formation-manager.ts:327-331` says an approval obtained before a failed write is
spent, because *"its nonce was never inserted, and the `unique` UsageStampId column bars
re-presenting it"*. Those two clauses contradict each other, and the second is false: a
nonce that was never inserted leaves no row, so `unique` bars nothing.

It also contradicts two places that state the opposite deliberately:

- `control-database.ts:1221-1222` — *"A caller that already holds an approver sign-off
  should retry a lost race with the SAME `usageStampId`."*
- `schemas/control.qsql` (`Authorized`, "Why a fresh nonce rather than binding UseNumber")
  — *"A nonce chosen freely by the redeeming node … lets the loser retry the same approval
  under a new use number."* Avoiding a second human review is the stated reason the nonce
  is not the use number.

The NOTE's *conclusion* is still right for today's code (the manager does not retry, so
the approval is discarded and a fresh formation attempt mints a fresh nonce), but the
mechanism is wrong and a future reader would design around a constraint that does not
exist.

**Fix:** rewrite the NOTE to say the approval is discarded *because this path does not
retry* — not because the nonce is barred — and point at F3's ticket.

### F3 (major, file a ticket) — the race-loser retry the schema designed for is not wired

Following from F2: the schema and `redeemInvitation` were built so the loser of a
`(Token, UseNumber)` collision can re-present the *same* approval under a new use number.
`provisionAsResponder`'s catch-all discards it and returns `'Formation conflict, retry'`,
so the joiner restarts formation and the hook is asked again — exactly the second
approval the nonce design set out to avoid. Costly where the hook is a human review queue.

**Fix:** file `tickets/backlog/debt-formation-approval-retry-lost-race.md`. It is a real
capability gap, not a tripwire — it is wrong every time the race happens, not conditional
on some future change. Keep the ticket to the *specification* (what should happen and why),
per the ticket-writing rules; do not design the retry in it.

### F5 (minor, fix inline) — one approval-failure category has no test

`strand-formation-consent.spec.ts` case (j) covers four of the five categories. There is no
`misconfigured` scenario, so `APPROVAL_REJECTION_REASONS.misconfigured` is unexercised — a
typo in that string ships green. Add a fifth entry to the `scenarios` array, same shape as
the `refused` / `unavailable` entries:
`recordingApprover(() => { throw new FormationApprovalError('misconfigured', 'bad url'); })`
→ `'Formation approval misconfigured'`.

## Tripwires to park (comments, not tickets)

- **Approval is skipped when the invite row is absent.** `recordUsage` /
  `provisionAndRecord` compute `invite?.validationUrl ?? null`, so an invite that vanished
  between `resolveStrand` and the write is treated as "no approval required" and the write
  proceeds unapproved. Safe today only because the database's `Authorized` CHECK requires a
  matching `FormationInvite` and rolls the write back regardless. Park as a `NOTE:` at the
  `?? null` in `obtainApproval`'s callers (one comment covers both sites).
- **The 8 KiB disclosure cap lives only in the manager.**
  `StrandSolicitationService.recordFormationComplete` (`strand-solicitation.ts:406-416`)
  reaches `recordUsage` without passing through `provisionAsResponder`, so its `disclosure`
  is uncapped. Harmless now — its three callers are integration-test mocks and all default
  to `''` — but it is a public service method. Park as a `NOTE:` on that method.
