# Durable trusted-owner anchor + bootstrap peers on NativeScript — implemented

Third (and last) of the three per-platform durable-node-local-store tickets
(web, React Native, NativeScript). Same cadre-core machinery
(`node-local-snapshot.ts`, `trusted-owner-store.ts`, `bootstrap-peer-store.ts`)
as the other two; only the `DurableSlot` backend differs per platform.

## What changed

- **New file** `packages/reference-app-ns/src/node-local-slots.ts`: exports
  `anchorSlotKey(partyId)` / `bootstrapPeersSlotKey(partyId)` (the literal keys
  `trusted-owners.<partyId>` / `bootstrap-peers.<partyId>`), a locally-declared
  `KvStoreApi` (mirrors `KvStoreApi` in `reference-app-rn/src/node-local-slots.ts`
  — a minimal `get`/`set` shape so a test can fake it without pulling in SQLite),
  and `kvSlot(kv, key)` — a direct `DurableSlot` pass-through over that shape.
- **`packages/reference-app-ns/src/cadre-phone.ts`**:
  - `identityDb` (module-level `OptimysticNSDBHandle | null`) replaces the old
    per-call open/close in `loadOrCreatePhoneKey`. Opened once in
    `startPhoneNode` via `identityDb ??= await openOptimysticNSDb(...)`, reused
    for the identity load AND for a `SqliteKVStore(db, '')` (empty prefix, not
    the class's default `'optimystic:txn:'`, so the stored keys are exactly the
    literal strings above) backing both new stores. Closed in `stopPhoneNode`.
  - `stopPhoneNode` restructured to mirror `reference-app-rn`'s version: clears
    the module `node` reference *before* calling `.stop()`, and closes
    `identityDb` in a `finally` so a throwing `.stop()` still releases the
    native handle and can't leave a stale reference for the next
    `node?.isRunning` early-return to hand back.
  - `trustedOwners: { store: trustedOwnerStore }` and
    `bootstrapPeers: { store: bootstrapPeerStore }` added to the
    `CadreNodeConfig` passed to `new CadreNode(...)`.
  - Comments added: the fate-sharing rationale (identity BLOB + both node-local
    records in one SQLite db, all wiped together), a `NOTE:` that the anchor is
    only as protected as the plaintext identity until NS secure storage lands
    (this app doesn't use Keychain/Keystore — see the pre-existing module
    comment), and a "no migration" note (existing installs cold-start once,
    empty).

## Use cases / how to exercise this

- **Cold start, never seeded**: `startSolo` / `startPhoneNode` with a fresh
  `sereus-peer-identity` db → both stores load empty (`NodeLocalSnapshot.open`
  sees an absent slot), node proceeds exactly as before this ticket.
- **Anchor survives restart**: after a node trusts an owner key (genesis /
  invite / operator pin — via `PersistentTrustedOwnerStore.trust`), stop and
  restart the node with the same `partyId` → `PersistentTrustedOwnerStore.open`
  reloads the same keys from the `trusted-owners.<partyId>` row.
- **Bootstrap peers survive restart**: after `CadreNode.recordSeedBootstrapPeers`
  records a dial target, stop/restart with the same `partyId` → the retry
  targets are still in `PersistentBootstrapPeerStore.all()` on the next
  `reconcileControlCohort` cold-start pass.
- **Corrupt / foreign-party record**: a `trusted-owners.<partyId>` value that
  isn't valid JSON, or whose envelope `partyId` doesn't match, loads empty
  (cold start) rather than throwing — exercised today only by cadre-core's own
  `node-local-snapshot`/`trusted-owner-store`/`bootstrap-peer-store` unit
  tests, not by anything in this package (see Known gaps).
- **Unreadable database**: a `db.prepare(...).get()` rejection on the
  `SqliteKVStore` propagates out of `kvSlot(...).load()`, which
  `NodeLocalSnapshot.open` re-throws — `startPhoneNode` fails rather than
  silently cold-starting with an empty (untrustworthy) anchor.
- **`startSolo`**: goes through `startPhoneNode`, so both stores are wired on
  the solo path too. `solo-smoke.ts` (`runSoloSmoke`) exercises this path
  end-to-end (create strand → insert message → read back) but is
  device/emulator-only (uses `crypto.randomUUID()` under the NativeScript
  runtime) — not run as part of this ticket's validation.

## Known gaps — reviewer should treat these as open, not silently verified

- **No test coverage added in this package.** `reference-app-ns` has no vitest
  suite (only `typecheck` / `test:bundle` / `test:e2e`, per the ticket and
  `package.json`). The cadre-core logic these stores lean on
  (`NodeLocalSnapshot`, `PersistentTrustedOwnerStore`,
  `PersistentBootstrapPeerStore`) already has its own unit tests in
  `packages/cadre-core` from the prior two tickets
  (`web-durable-node-local-stores-tests`, `rn-durable-node-local-stores-tests`)
  — those aren't re-run here and aren't NS-specific, so nothing here proves the
  `SqliteKVStore` + `kvSlot` composition actually round-trips on a real device.
  If NS parity work later grows a mocha/vitest suite under Node (the way
  `db-p2p-storage-ns` itself tests against `node:sqlite`/`better-sqlite3`
  instead of the real NS plugin), a `kvSlot`/`SqliteKVStore` round-trip test
  would belong there. Not filed as a ticket — this mirrors the `web`/`rn`
  siblings' testing tickets, which were themselves separate follow-ups; if the
  reviewer wants the same treatment here, that's a call for review, not
  something this ticket should have silently skipped past.
- **Device-level e2e is NOT agent-runnable and was NOT run.** `test:e2e`
  (`scripts/run-e2e.mjs`) requires an actual device/emulator; per the ticket
  instructions this is explicitly out of scope for an agent and is *not*
  implied to have passed.
- **No verification of the `runOwnerGenesis`-equivalent re-anchoring path.**
  Unlike `reference-app-rn/src/cadre-phone.ts`, this NS app has no explicit
  owner-genesis/`ensureOwnerKey` wiring in `cadre-phone.ts` (grepped for
  `ensureOwnerKey`/`OwnerKey`/`genesis` in `reference-app-ns/src` — no
  matches). The ticket's "Edge cases" section says "the founder's own key
  re-anchors each start via the genesis path" for `startSolo`; where that path
  actually lives for this app (if it differs from RN's explicit call) was not
  traced down before the review handoff. Worth a look in review: confirm
  `trust()` on the new `PersistentTrustedOwnerStore` is actually invoked
  somewhere in the solo/founder flow, otherwise a founder's own key is never
  anchored and the anchor stays permanently empty for that node.
