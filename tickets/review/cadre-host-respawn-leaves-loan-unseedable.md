# Review: a donated node still starting is no longer respawned over itself

## The incident (2026-09-16, donor mode, Windows)

A phone's donated node came up healthy; cadre-host then launched a second process for the same container, which died with `EADDRINUSE`. The donation record now held a new `seedToken` (and kept rotating it), the live node answered every host `POST /seed` with `401`, and the loan stayed `awaiting_seed` forever.

Root cause: `HostProcessOrchestrator.isRunning` required the `.startup-token` file, which `cadre-cli start` wrote only after `node.start()` resolved — after its ports were bound. A supervisor sweep in that window saw "not running", `DonationService.respawn` → `createContainer` dropped the old handle, reused the same ports, rotated the tokens and returned success before the second child died. And give-up was only reachable when `respawn` threw, so a spawn that "succeeds" then dies looped forever at the 5-minute backoff cap.

## What changed — four arms

**1. Liveness (root cause).**
- `cadre-cli start` writes the startup-token file as the first statement in its action (`writeStartupToken`), before config resolution, the health server bind and `node.start()`. Option help text now says it is an identity check, not a readiness signal. Nothing reads it as readiness: its readers are `isRunning`, `init` and `ensureOwnerNode`'s short-circuit; the owner admin client (`OwnerNodeClient`) reads the endpoint lazily and treats connection failure as `OwnerNodeUnavailableError`, and NAT's initial push retries not-ready. The admin channel still binds at the same point as before.
- New module function `isHandleLive(handle)` in `host-process-orchestrator.ts`: a handle carrying the `ChildProcess` this process spawned is live iff `exitCode === null && signalCode === null && isPidAlive(pid)` (the pid check closes the moment between OS exit and Node's exit event); a handle re-attached from `state.json` falls back to pid + token file. Used by `init`, `isRunning`, `ensureOwnerNode`'s short-circuit and the new guard. `isRunning` for an id with no handle now just returns `false` (it did in effect before; the `decodeDockerId` branch was dead weight and is removed).

**2. Guard: never launch over a live child.** `refuseRespawnOverLiveChild(containerId, overrides, owner)` runs as the last `await` before the handle drop in both `createContainer` and `ensureOwnerNode`:
- any same-id handle live per `isHandleLive` → throws `container <id> is still running`;
- else if any same-id handle's pid is alive (re-attached, token unverified) → bind-probes the ports the re-spawn would reuse (`childPortBindings`: health/metrics/p2p/ws on `0.0.0.0`, plus admin on `127.0.0.1` for the owner) via the new `orchestrator/port-probe.ts` `assertPortFree`, and throws `container <id> may still be running: port N on H is unavailable (CODE)`. It never kills the pid.
- Throwing before the drop means nothing released, no token rotated; `DonationService.respawn`'s existing failure path keeps the record's old `dockerId`/`seedEndpoint`/`seedToken` and counts the attempt.
- `dropStaleHandle` now uses a shared `handlesFor(containerId)` (same map order the guard uses to compute reused ports). NOTEs on `dropStaleHandle` / `restoreDroppedHandles` rewritten to point at the enforced guard.

**3. Give-up reachable for "successful" crash loops.** `DonationSupervisor.reconcileOne`: after `isRunning` is false and before the backoff check, if `respawn.attempts >= DONATION_RESPAWN_MAX_ATTEMPTS` → `giveUp(id, attempts, 'the node did not stay running after its last respawn')`. The catch-path check in `attemptRespawn` is kept. Docstrings on `DONATION_RESPAWN_MAX_ATTEMPTS` / `DONATION_RESPAWN_BACKOFF_MAX_MS` and the supervisor section of `docs/cadre-host.md` updated ("every attempt counts").

**4. A rejected seed is diagnosable.**
- `cadre-cli/src/server/bearer.ts`: new `bearerRefusal(req, token): 'missing' | 'mismatch' | undefined`; `checkBearer` is now a wrapper (admin server unchanged in behaviour).
- `health.ts` `handleSeedRequest` logs a refused `/seed` to the debug logger and `console.error('✗ Seed request refused (401): <reason>')` — reason only, never the presented token.
- `DonationService.applySeed`: a node `401` throws `DonationError('seed_failed', "Donated node rejected the host's seed credential (401)")` and logs it. **Decision: kept the `seed_failed` code** rather than adding a new one — `reference-app-rn/src/host-node-request.ts` `putSeed` retries `seed_failed` for 30 s, and a token bookkeeping gap that is mid-repair can clear inside that window; a new code would stop the retry. Consequence: the phone's headline (`plainMessage`) still reads "The lent node would not accept this cadre's seed."; only the `detail` carries the new host message.

## Known gaps — reviewer, please look here

- **Integration scenarios not run.** `cadre-host-donation-phone-requester` (stop → `respawn` with a real `cadre-cli`), `cadre-host-node-donation` and `cadre-host-owner-node` are the ones that exercise this path for real. The integration stale-build guard refused because `../quereus` has an uncommitted edit to `packages/quereus/src/schema/schema-differ.ts` that is not mine; I did not build over someone else's in-flight change. Run them once quereus is settled. The incident itself was not replayed against a real `cadre-cli` child on Windows.
- **Re-attached child still loading modules** (NOTE on `refuseRespawnOverLiveChild`): after a host restart, a child in its first ~1–2 s (before its token write, before any bind) shows neither token nor bound ports, so a re-spawn can still race it. Needs a host restart inside a child's first seconds. Suggested fix if seen: treat a re-attached live pid as starting for a grace period after `spawnedAt`.
- **Probe side effect** (second NOTE there): the bind-probe holds each port for an instant; a child binding in that instant would fail. Only reachable for re-attached handles in the moment between the token check and the probe. Alternative if ever seen: connect-probe (slower on Windows, ~2 s per refused loopback connect).
- **Give-up after host downtime.** The new check gives up immediately when a pass finds the node down with the cap already recorded. A record that reached the cap, whose 5th spawn then stayed up but was killed (e.g. by a reboot) before the 10-minute refill was observed, is given up on host restart rather than tried once more. Followed the ticket literally; judged too rare to add a "count is stale" condition — reviewer may disagree.
- **Guard refusals count as attempts.** A re-attached node whose ports are bound but whose token is unverified (e.g. a child from an older `cadre-cli` that still writes its token late, during an upgrade) is refused 5 times over ~150 s of backoff and then given up — `giveUp` stops that child. Acceptable for a node that takes >150 s to write a token, but worth a thought.
- The `alive` flag on a re-attached handle stays `false` once `init` sets it, even after its token appears (pre-existing behaviour, unchanged; `listNodes` shows it `stopped`).
