# Phone kit and web app hold an owner key of their own (review)

## What was built

**Shared flows** (`cadre-core/src/owner-key-flows.ts`, root exports):

- `addBackupOwnerKey(node, { label?, passphrase? }) → { publicKey, exportText }`: generates a key in memory, encodes the export **first** (so an export the encoder refuses, e.g. an empty passphrase, never seats a key nobody holds), then `node.addOwner(publicKey, { label })`. Keeps nothing.
- `exportOwnerKey(keyStore, { label?, passphrase? }) → string`: the owner slot's key; throws a plain `Error` when the slot is empty.
- `importOwnerKeyInto(keyStore, node | null, text, passphrase?) → { publicKey, wired }`: decodes (or unlocks), `importOwnerKey` into the slot (refuses a different key), and with a node, `wireOwnKeyIfOwner(signer)`. A node already signing with **another** key (the identity key an owner-granting invitation seated) keeps it: the key is stored, `wired: false`, and the next start wires it.
- New `OwnerKeyExportErrorCode` `'passphrase-required'` for locked text given no passphrase.

**`CadreNode.getIdentityOwnerKey()` deleted.** Its spec callers now generate an owner key (`createOwnerKey` over the config's key store where a restart must re-wire the same key, an in-memory store otherwise). `scripts/lib/published-smoke-scenario.mjs` ports two of those specs, so it changed the same way (and now `await`s the wiring call it used to fire and forget). The cadre-core test helper `self-owner-node-helpers.ts` also gives its nodes a separate owner key now; `validation-key-enrollment.spec.ts` had read the node's private identity key to sign as owner, and now uses the helper's owner key.

**Phone kit** (`cadre-rn/src/phone-node`):

- Owner key in the same `SecureStoreKeyStore` as the identity, slot `cadre/owner`, same `secureStoreOptions` (the docs say to keep them ungated).
- `runOwnerGenesis(node, { keyStore, label?, timeoutMs? })` (signature changed). Founded party, empty `OwnerKey` table: the slot key (created unless present) becomes the founding row under `PhoneNodeOptions.ownerKeyLabel` (default `DEFAULT_OWNER_KEY_LABEL = 'phone'`) and is wired. Table not empty: the slot key is wired only when it is a live owner, else `member`, and **no key is created**. If the genesis insert returns false (a row arrived between the two reads), the key is judged as in the non-empty case.
- `wireJoinedOwnerKey(node, { keyStore, timeoutMs?, granted? })` (signature changed): each pass tries the slot key (only while no signer is wired), then `wireOwnKeyIfOwner()`'s default.
- `PhoneNodeOptions.ownerKeyLabel`, saved in and parsed from the saved-start record.
- `PhoneNode.ownerPublicKey()` is now `node.getOwnerSigner()?.publicKey ?? null`.
- New pass-throughs, all in the transition queue: `listOwnerKeys`, `addBackupOwnerKey`, `exportOwnerKey` (works stopped), `importOwnerKey` (works stopped; a running node that wires the key reports `owner: 'enrolled'`), `planOwnerKeyRemoval`, `removeOwner`. The ones that name the node throw while none is running.

**Web app** (`reference-app-web/src/lib`):

- `ownerKeyStore(handle)` in `node-local-slots.ts`: a one-slot cadre-core `KeyStore` (only `DEFAULT_OWNER_KEY_ID`) over `kv` key `owner-private-key`, protobuf bytes like the peer key, written in a strict-durability transaction where supported. Text under the key is reported as `KeyStoreAccessError`, never as an empty slot.
- `cadre-web.ts`: the same founded and joined rules as the kit (a copy: `settleFoundedOwnerKey`, `wireJoinedOwner`; `plan/1.20-edge-node-bring-up-shared-by-every-kit` unifies them). The founding label is `browser`. `OwnerState` meanings: `genesis` = inserted now, `existing` = slot key is a live owner, `member` = none. Exposed for the UI ticket: `addBackupOwnerKey`, `exportOwnerKey`, `importOwnerKey`. Listing and removal are the node's own `listOwnerKeys` / `planOwnerKeyRemoval` / `removeOwner`, called the way `machines.svelte.ts` calls `listMachines`.
- E2e fixtures `cadre-member.ts` and `formation-responder.ts` found under a generated key.

**RN drone fixture** (`reference-app-rn/test-fixture/start.mjs`): `createOwnerKey(new InMemoryKeyStore())`, `useOwnerSigner`, `ensureOwnerKey(key, 'drone')`.

**Docs**: the kit README has a new "The phone's owner key" section plus updated member-table and `origin` rows. The web README has a new "The tab's owner key" section and an updated joined-party bullet. `docs/architecture.md`: the Owner Keys status note now names only the apps' UI tickets as remaining; there is a flows paragraph under Exporting and importing; Invitation-granted owners; the anchor re-anchoring sentence; An app joins an existing cadre (the bullets and the founded/joined rules); Mobile secure backend, the reinstall table and Recovery; Closed-strand member keys; Implementation Status. The cadre-core `useOwnerSigner` NOTE no longer says the kits wire unconditionally.

## Known gaps and judgment calls for the reviewer

- **No migration.** A phone or tab that founded a party before this change has the identity-derived key as that party's only owner. After the update the founded rule finds owners and an empty slot, reports `member`, and creates nothing. AGENTS.md says no backwards compatibility yet, so I added none.
- **Web copy of the rules.** `cadre-web.ts` repeats the kit's founded and joined rules, about 25 lines. I left them in each kit, as the ticket placed them, rather than moving them into cadre-core, because `plan/1.20-edge-node-bring-up-shared-by-every-kit` moves the whole bring-up there.
- **Import while another signer is wired** returns `wired: false` even though the device is already an owner through the identity key. The 1.09/1.10 UI would then say "not an owner of this cadre" in that narrow case; it can check `isOwner()` / `listOwnerKeys()` to tell the cases apart. The next start wires the slot key.
- **Queue latency.** The owner-key pass-throughs queue behind a join that may wait minutes for a member, as the ticket asked.
- **Owner-slot read failures are fail-soft.** A `KeyStoreAccessError` on the owner slot makes genesis `'failed'` (logged) and the start stands, while an identity-slot failure still fails the start. This is consistent with genesis being fail-soft; the reviewer may prefer failing the start.
- **`ownerKeyLabel`** is saved in the record, but `resolveOptions` does not inherit it into a start that names none. It matters only when genesis did not happen on the first start.
- **Web owner state after import.** `cadre-web.ts` `importOwnerKey` updates the module's owner state, but the store's reactive `state.owner` changes only when `syncOwner()` runs; `reference-app-web-owner-keys` must call it.
- **Not refactored.** cadre-cli's own `owner-key export|import` still uses its own code (a file store, its own `changed` result and messages), not `owner-key-flows.ts`.
- **Other cadre-core specs not audited.** Beyond the deleted method's callers and the self-owner helper, I did not audit every cadre-core spec's owner-key source. The remaining `ed25519KeyPairFromLibp2p` uses I saw are identity bindings (peer records, device tokens) or generated keys, not a node's identity used as its owner key.
- **By inspection only**:
  - The `alone` refusal of a backup.
  - An iOS reinstall founding with the surviving key.
  - A cancelled or failed import never touching the identity slot (different key id).
  - One key imported on two devices.
