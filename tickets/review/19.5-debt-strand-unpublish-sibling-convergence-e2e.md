# Review: two-node convergence for party-wide strand removal

## What was built

- **New scenario** `packages/integration-tests/src/scenarios/strand-unpublish-sibling-convergence.integration.ts`
  — one test, five phases, exactly per the implement ticket's recipe:
  - Phase 0: `bootPair('unpublish', 'ctrl', { strandWatchMs: 1_000 })` (A owner/storage, B plain
    reader, A vouches B), `connectControlNodes(B, A)` **before** any write.
  - Phase 1: `A.publishStrand` → B's watcher emits `strand:discovered` (anti-vacuity anchor: B is
    not an owner and never wrote the row). B joins from the event payload's `StrandRow` with an
    explicit `mode: 'bootstrap'`; asserts instance `active`.
  - Phase 2: `A.unpublishStrand`; sanity read on A.
  - Phase 3 (headline): B emits `strand:stopped` for the id; `getStrand` undefined,
    `getStrands().size === 0`, B's own control-DB `queryStrands()` no longer lists it. This is
    the first cross-machine read-back of a control-plane DELETE anywhere in the repo.
  - Phase 4: five-poll quiet window (derived from `STRAND_WATCH_MS`, not hardcoded) — event
    arrays unchanged, exactly-once, no re-add, no errors.
  - Phase 5: `A.publishStrand` again → second `strand:discovered` on B (watcher cleared the id;
    the `Revocation` tombstone is not read back as a strand; discovered, not relaunched).
  - `finally` stops B before A (B's last polls must not read a dead peer). One shared
    `CONVERGE_BUDGET_MS = 30_000` for all three waits. Test timeout 180 s.
- **Harness (additive only)** `harness/node-fixtures.ts`: `ControlNodeOpts.strandWatchMs` →
  `CadreNodeConfig.strandWatchInterval`, and a third optional `opts` argument to `bootPair`
  applying it to both nodes. The three existing `bootPair` callers are untouched. The in-flight
  `plan/10-integration-test-harness-helper-consolidation-remaining-files` ticket folds *other*
  files' copies into this file; an added field does not collide with it.
- **Docs**: architecture.md party-wide-removal paragraph now names this scenario as the proof
  (appended, not rewritten); STATUS.md integration-scenario inventory gained an entry in the
  house format.

## Validation

`yarn --cwd packages/integration-tests typecheck` and repo-root `yarn lint` both clean.

Four green runs via `npx vitest run -t "sibling instance once its watcher"` with
`DEBUG='sereus:integration:wait'` capturing wait wall clocks (logs were in the session
scratchpad; figures below are from them):

| Run | Phase 1 discovery | Phase 3 stop | Phase 5 rediscovery |
| --- | --- | --- | --- |
| 1 | 631 ms | 0 ms | 111 ms |
| 2 | 305 ms | 0 ms | 0 ms |
| 3 | 0 ms | 0 ms | 310 ms |
| 4 — under CPU load (6 busy-loop node processes) | 0 ms | 0 ms | 722 ms |

All against 30 s budgets — margins are enormous. Phase 5 rediscovery was reliable and fast every
run. Test body ~25–30 s (the 5 s quiet window dominates); the suite's import overhead adds
~95–120 s because `-t` loads all 40 scenario files (a path filter reportedly doesn't match on
Windows — same note as the implement ticket).

## Things a reviewer should probe (honest gaps)

- **Phase 3's wait resolved in 0 ms on every run**: convergence consistently beat the wait's
  start. Plausible mechanics: A's `unpublishStrand` awaits the 2-node cohort commit (B approves
  the delete as a cohort member), and B's next 1 s poll lands within the wall clock of
  B.addStrand + A.unpublish (~17–22 s, strand boot dominating). The assertion is still
  non-vacuous — the event gate proves the stop fired and Phase 1's discovery gate proves the
  ordering (row held before removal) — but a reviewer may want to confirm the test would really
  catch a *never-converging* sibling: it would (the 30 s wait times out and `it` fails); what it
  cannot distinguish is watcher-poll-driven visibility vs. visibility already forced during the
  cohort commit itself. If that distinction ever matters, the probe is to widen B's poll interval
  and watch the stop latency track it.
- **Phase 1 discovery "0 ms" in runs 3–4** is the same class: publish + first poll completed
  inside the `await publishStrand` + first wait check. Harmless.
- The fallback path in the implement ticket (`it.fails` + fix ticket) was **not needed** — the
  product behaved as documented.
- Not covered here, deliberately (documented in the file header): delete-while-alone durability
  (`plan/control-delete-while-alone-tombstone`), A running its own instance, closed strands /
  `MemberPrivateKey`, filter-excluded siblings (unit-covered by
  `packages/cadre-core/test/strand-unpublish.spec.ts`), a third node.
- **Environment friction, not product**: the stale-build guard tripped twice mid-work as sibling
  workspaces (`../quereus`, `../optimystic`) drifted under concurrent activity; fixed by
  rebuilding (`yarn workspace @serfab/cadre-core build`; in `C:\projects\quereus\packages\quereus`
  `npx tsc`; in `C:\projects\optimystic` the two workspace builds). Expect to re-run those before
  reviewing if the guard trips again.
