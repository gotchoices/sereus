# A strand node that holds no blocks — implement handoff

`roles: { strandCohortMember: false }` now works. Every strand node such a machine builds is an Optimystic **client** (`createLibp2pNode({ servesBlocks: false })`): it runs the strand — reads, writes, membership, change notifications — and stores none of its blocks. The control node is untouched. The plan ticket's design was followed except at one point, flagged under *Known gaps*: its claim that a party key replacement binds a client "one pass later" is wrong, and the docs now state the defect instead of the claim.

## What landed, by seam

- **`StrandInstanceManager.buildStrandRuntime`** binds `servesBlocks = config.roles.strandCohortMember` once and passes it to `createLibp2pNode`. `arachnode` is behind the flag; `storage` is `undefined` on a client because `startStrand` no longer resolves a store for one (so the embedder's provider is never asked for the strand's scope); `rebalance: { enabled: false }` stays behind `backfillArms`, which the absent store already makes false. The `publishOwn` (`StrandPeer` row) call is skipped on a client. The peer-join catch-up is skipped by the same absent store, with the reason now stated in its comment.
- **`buildStrandDatabase`** treats a client as already synced, beside the founder case, so its database is published as soon as `initialize()` returns. The `StrandFirstSyncGate` object stays as the handle `releaseRuntime` closes the database through. `firstJoin` is already false on a client (no `storageRepo`), so nothing listens or probes.
- **`CadreNode`'s constructor** no longer refuses the role. `hostUnclaimedStrands` resolves through the new `resolveHostUnclaimedStrands` in `node-roles.ts`: default `alwaysOn && strandCohortMember`, and an explicit `true` beside `strandCohortMember: false` throws naming both.
- **Types.** `Libp2pNodeWithRepo.coordinatedRepo` is optional and the type carries `servesBlocks?: boolean`, each with its reason; `StrandDatabaseConfig.coordinatedRepo` is optional and passed to `connectToStrand` only when present (the composition refuses a repo offered with a client node). The control-node read in `createControlNode` keeps its own `coordinatedRepo not available` throw.
- **Harness.** `ControlNodeOpts.roles` and `TopologyMachineSpec.roles` forward `roles` verbatim, so a scenario can build a client machine.
- **Docs.** `docs/cadre/node.md` has a new section "A node that holds no strand blocks" (the owner of what a client does and does not do); `concepts.md` gains the glossary term **Client**; lifecycle, formation, writes, membership and keys each carry the client exception in the section that owns the topic; the topology coverage map lists the scenario; both READMEs and the release notes say what the role does and refuses, and the release notes gain a section for the capability.

## How to exercise it

- **Build one:** `new CadreNode({ nodeClass: 'device', roles: { strandCohortMember: false }, storage: { provider }, … })`, or in cadre-cli `roles.strandCohortMember: false` / `CADRE_ROLE_STRAND_COHORT_MEMBER=false`. Then `addStrand` a strand that at least one serving machine of the party runs.
- **What to observe:** `instance.libp2pNode.servesBlocks === false` and no `coordinatedRepo`; `addStrand` resolves `'active'` at once (no first-sync wait); the storage provider is never called with the strand id; the client's writes land on, and are read from, the serving machines; every serving machine's cohort (`keyNetwork.findCluster`) and coordinator pick excludes the client, and the client's own cohort excludes itself; the party's `StrandPeer` rows name only the serving machines.
- **The refusal:** `hostUnclaimedStrands: true` with the role off throws at construction, naming both settings. A `server` with the role off and no explicit `hostUnclaimedStrands` constructs and hosts no replicas.
- **What a client cannot do (by design, not covered by a test):** open or found a strand with no serving machine reachable — the launch fails with Optimystic's `FindCoordinatorError` and `addStrand` rejects. `implement/client-strand-waits-for-a-serving-machine` makes that wait instead.

## Tests

- **`strand-client-node-holds-no-blocks.integration.ts`** (new) — one party: two `server` machines and one `device` with the role off, on the reference chat schema. Verifies, in order: the client's database is published at once and its node declares itself a client; the client writes a participant and a message and a serving machine reads them; both serving machines hold every block (raw-store coverage both ways) while the client's provider was never asked for the strand's scope; after that traffic neither serving machine names the client in a cohort or picks it as coordinator, and the client picks a serving machine; the client reads a message a serving machine wrote; the `StrandPeer` row set is exactly the two serving machines. Passed first run (test body 5.8 s, 45 committed blocks on server 0). The client is hand-dialed to both servers after its launch, so the claims do not ride on seed timing — stated in the coverage map's "Not covered" cell.
- **`cadre-node-control-node-options.spec.ts`** (one case added) — a `server` with `strandCohortMember: false` builds control-node options with no `servesBlocks`. Pins the one invariant whose breach is silent and severe: a client control node could not read its party's state offline.
- **`cadre-node.spec.ts`** (one case replaced by two) — the role alone constructs, on a `device` and a `server`; an explicit `hostUnclaimedStrands: true` beside it throws naming both settings.

Nothing else was added: the option pass-through, the skipped store, the skipped backfill, the skipped `StrandPeer` publish and the client's cohort exclusion are all observed by the scenario, and the type widening is carried by the compiler.

## Known gaps — read these first

1. **A party key replacement locks a client out of the party's closed strands.** The plan said the client's own membership loop binds it under the new key one pass later. It cannot: the replacement (`strand-party-key-rotation.ts`) binds only the peer ids it reads from `StrandPeer` rows plus its own, runs admit-bind-promote-leave back to back, and swaps the control row last; once the old key leaves, the client's self-binding under it is an orphan with no live one — exactly the revoked-peer deny set — so every serving machine refuses the client before its loop is re-keyed, and no sibling binds it because siblings also read `StrandPeer`. Reachable in normal use (closed strand + one machine removal). Filed as **`tickets/plan/client-locked-out-of-closed-strand-after-party-key-replacement.md`** with the resolution the plan ticket itself named (a per-strand "serves" fact on the `StrandPeer` row) and the alternatives rejected; `keys.md`, `membership.md`, `node.md` and the release notes state the limit and tell operators not to remove a machine from such a party until it lands. The reviewer should check the analysis — it is `static`, read from the rotation's step order and `StrandRevocationEnforcer`'s deny-set derivation — and decide whether the skipped row should ship at all ahead of that fix. I kept the plan's choice because publishing the row deadlocks every offline-mode sibling's queue while a client phone sleeps, which is the common case, where the lockout needs a removal.
2. **`onCommitFullyHeld` on a client** is a no-op subscribe, not a throw: upstream's `TransactionBridge.onCommitFullyHeld` only adds the listener to a set, and the scenario's client `initialize()` — which subscribes — succeeded. `writes.md` → "A commit's durability" states that `strand:commit-held` never fires on a client. Not observed by a test (no commit on a client is ever reported held, so there is nothing to assert except an absence).
3. **Not exercised, by inspection only:** change notifications on a client (`strandReactivity` with a client machine), hibernation and wake of a client strand, a client on a **closed** strand (the scenario's strand is open; membership on a client is the same reconciler path, but the revocation enforcer's remote reads on a client are untested), and `attachSApp` on a client (unreachable: a client hosts no replicas).
4. **A client's cross-release exposure** — a serving member on a release before Optimystic 1.28.0 seats clients in its cohorts — and the **all-clients / mostly-clients** limits are stated in `lifecycle.md` → "Limits and accepted tradeoffs", not guarded; Sereus cannot count a strand's clients from one node.
5. **No `NOTE:` tripwires were added.** The one conditional concern considered — the revocation enforcer's periodic remote `Revocation` reads on a client — is already a stated cost in `node.md`'s client section, not a latent defect.
