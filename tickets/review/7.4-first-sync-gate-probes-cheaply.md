# Review: the first-sync gate probes cheaply and wakes on arrival

## What changed

The joining machine's first-sync gate (`StrandFirstSyncGate`, `strand-first-sync-gate.ts`) holds a strand database back from the app until the machine holds `Strand.Header` and a read of every `App` table has settled.

- **One-row probes.** Every probe read is `select 1 from <Schema>."<Table>" limit 1` (Header: `Strand."Header"`). Header held = a row came back; a table is settled = the read did not throw (no row is fine).
- **Memory.** The gate keeps a `FirstSyncProgress` (`header`, `tables: Set<'App.X'>`) for its lifetime. A later probe skips what an earlier one found settled. The instance manager's first probe now goes through the gate (`gate.probeOnce()`), so its findings carry over to the gate's own probes. A gate lives for one database build, so a hibernation wake or a deferred-join retry starts with an empty memory.
- **Order.** Header first and alone, then each pending `App` table one after another, stopping at the first that fails (the next probe starts there).
- **Wake on arrival.** `start()` builds a `scheduleRuns` schedule (single-flight, one follow-up for changes during a run) with a 2 s backstop (`DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS`, reasoning on the constant), and subscribes to the strand node's storage-wide change feed (`node.storageRepo.onAnyCollectionChange`, new optional field on `Libp2pNodeWithRepo`). The first block that lands after a probe started triggers one probe 50 ms later (`TABLE_CHANGE_COALESCE_MS`). Later blocks before that probe starts do nothing, because that probe will read them. With no feed (test doubles), the gate logs once and relies on the backstop.
- **Per-probe log line**, `first-sync probe (data landed|backstop)` under `sereus:cadre:strand-first-sync`. This is what makes the self-wake tripwire (below) visible.
- **Renames:** `StrandFirstSyncConfig.pollIntervalMs` → `backstopMs`; `DEFAULT_STRAND_FIRST_SYNC_POLL_MS` (500 ms) → `DEFAULT_STRAND_FIRST_SYNC_BACKSTOP_MS` (2 000 ms). `strandHeaderHeld`, `appTablesReadable` and `strandFirstSyncComplete` are no longer exported, from the module or from `index.ts`. The probe is private; tests go through `probeOnce()`.

## Deviation from the plan: the table probes are NOT concurrent

The plan asked for `Promise.all` with `{ readConcurrency: 'committed' }` so the table reads would overlap. I did not do that. It would make the gate unsound in one reachable shape. Static reasoning only: I read the code and did not run the failure.

- Schema apply runs `create table` (the Optimystic plugin's `create()` → `table.initialize()`) for every table when the joiner has no catalog to hydrate, which is the case for a launch with no seed peer. `doInitialize` uses `createOrGetCollection` (create-on-missing). With no peer able to answer, it stages an empty "invented" collection in memory and marks the table initialized (`optimystic-module.ts` ~760-775, ~4516-4545; `db-core` `Collection.createOrOpen` ~346).
- A committed read of an already-initialized table never refreshes it: `runQuery(committed=true)` reads `committedTreeView(tree)` → `tree.snapshot()` (~1455-1465, ~1695), and `initializeForCommittedRead` returns at once for an initialized table. So once the Header is held, a committed probe of such a table reads the invented empty tree and reports "settled" without fetching anything. That is the fork the gate exists to prevent.
- The serialized (default) read calls `mainTree.update()` first, and `Collection.updateInternal` adopts the founder's log over an invented collection once a peer holds the header (`collection.ts` ~975-1001). That is why the old gate worked in this shape, and the new one keeps serialized reads.
- Quereus serializes plain `eval`s behind its execution mutex, so `Promise.all` without `committed` does not overlap anything. The loop is therefore sequential, and stops at the first failure to limit a failing round to one consult.

The reasoning is recorded as a `NOTE:` on `strandFirstSyncComplete` (with a revisit condition) and in `docs/strands.md`. The spec asserts that no probe passes `readConcurrency: 'committed'`.

**What would confirm it:** switch the table probes to `committed`, then run a scenario where a cross-party joiner launches with an empty seed (the harness's `joinStrandOn`, e.g. `harness-topology` "two 2-machine parties share one strand") and writes the moment it is writable. Then check whether its rows converge. The gate opening onto invented trees is certain from the code. Whether Optimystic's commit path would then recover (a stale-header conflict forcing an `update()`) or fork was not checked.

## Measurements (recorded on `DEFAULT_STRAND_FIRST_SYNC_TIMEOUT_MS`'s doc comment)

Both instruments were run before and after, one run each, with `@optimystic/*` 1.15.0. The stale-build guard did not block either.

- `message-cost-accounting` strand case (run with `MESSAGE_COST_IDLE_S=5`, since the idle phase does not involve the gate): B's `addStrand` took 469 → 471 ms, with 13 `sync` streams B→A, 4 Header-probe reads and 8 table-probe reads, **identical**. The schema's two tables are empty, so a count and a one-row read fetch the same blocks, and the first probe passes, so the gate never arms.
- `strand-reattach-first-sync-measure`, fresh join, 1 500 ms one-way: writable at 28.8 s both before and after, **not gated**. The launch waits 27.3 s in `connectToStrand` for its seed peer, then the first probe passes in 24-26 ms.
- Neither instrument reaches the woken path. To check it, I ran `harness-topology`'s cross-party share with the backstop temporarily raised to 10 s (source and `dist` restored to 2 s afterwards). The founder's backfill push opened the gate 2.1 s after it armed, logged as `first-sync probe (data landed)`.

So on today's stack this change shows no measured win in either instrument. The win is expected where the gate actually arms (a joiner without a seed, larger tables, the phones in GitHub #44), and none of those was measured here.

## Tests

`test/strand-first-sync-gate.spec.ts`, gate class (rewritten):
- "reads one row per table, the Header first, stops at the first failing table, and never re-reads what settled". It checks the exact SQL, that no tables are read without a Header row, that an empty table counts as settled, that the round stops at the failing table, that the next probe reads only the pending tables, and that no read is `committed`.
- "a throwing read, or a throw outside the read guards, is "not yet" rather than a rejection" checks `probeOnce()` both ways. It replaces two old tests.
- "probes when data lands, on the backstop when none does, and opens exactly once". With a fake storage feed and a fake scheduler that fires the shortest timer, the first fire is the 2 000 ms backstop, and two emits produce one 50 ms probe that opens the gate. It also checks that the feed is unsubscribed once the gate opens.
- "open() force-opens …; stop() cancels the schedule and the feed": the old test, extended to the feed.
- The manager-level tests are unchanged except for the double (it yields a row only when the Header count is set) and `backstopMs`.
- Removed: "the gate stays closed while an App table is unreachable…". The probe test plus the loop test cover it.

## Tripwires parked

- `NOTE:` on `StrandFirstSyncGate.subscribeStorage`: a probe's own reads can land blocks and wake a follow-up probe. If the logs ever show probe storms, ignore events while a probe is in flight.
- `NOTE:` on `strandFirstSyncComplete`: why the reads are serialized, with a revisit condition (the plugin's committed read refreshes an unsynced tree, or Optimystic can say directly whether a collection is held).
- The class's relay `NOTE:` is updated: its count was measured under 500 ms polling, and the revisit condition is unchanged.

## Known gaps for the reviewer

- Data that lands between the manager's first probe and `start()` raises no event the gate hears. The first backstop (2 s) catches it. This is documented on `start()`.
- `storageRepo` is typed structurally as `{ onAnyCollectionChange(listener: CollectionChangeListener): () => void }` rather than as Optimystic's `StorageRepo` class, matching how `keyNetwork` is declared.
- The `Strand` tables (`backlog/debt-first-sync-gate-reads-every-strand-table`) are not folded in. That ticket's "Related" paragraph now says that adding them only changes the list of tables read, and that each one costs a serialized read.
