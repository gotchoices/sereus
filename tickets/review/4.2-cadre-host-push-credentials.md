## What shipped

The config-plumbing subsystem that gets FCM/APNs credentials into a spawned node's `CadreNodeConfig.push` (the key cadre-core's already-shipped fan-out reads). It owns **no delivery logic** — only secret storage + config injection + validation. Five coordinated changes:

### 1. cadre-core — shared, dependency-free validator/redactor (`push-credentials.ts`)
- `validatePushCredentials(push): string[]` — a present platform block must carry all required fields (FCM: `projectId`/`clientEmail`/`privateKey`; APNs: `keyId`/`teamId`/`bundleId`/`privateKey`); empty bundle is valid (push is opt-in). Returns errors, doesn't throw.
- `redactPushCredentials(push)` — log-safe view with every `privateKey` → `[redacted]`.
- Type-only imports (erased), so a provisioner pulls neither the FCM/APNs senders nor any heavy graph. Exported from `index.ts`.

### 2. cadre-cli — carry `push` from config/env into the node (the previously-missing link)
- **This was a real gap**: `start.ts` built `nodeConfig` *without* `push`, so any `push` block in `cadre.json` was silently dropped before `CadreNode.start`. Fixed: `push?: PushCredentials` added to `CliConfigFile` + `ResolvedConfig`, threaded through `loader.resolveConfig`, and passed into `nodeConfig`.
- New `CADRE_PUSH` env mapping → parsed as a JSON object (mirrors the `CADRE_STRAND_FILTER` JSON precedent; empty ⇒ undefined; malformed ⇒ throws). This is the channel the provider's container uses.

### 3. cadre-host — secret-store resolution + entry path
- **Secret store** (keytar / `0600` fallback, accounts `push:fcm` / `push:apns`): FCM `{projectId,clientEmail,privateKey}` and APNs `{keyId,teamId,privateKey}` JSON blobs. **`host.config.json`** (`PushSettings`): non-secret APNs `bundleId`/`production`, `cooldownMs`/`debounceMs`.
- `resolvePushCredentials(secrets, settings)` (`src/push/index.ts`) merges the two, validates, returns `undefined` when no platform configured, throws on a partial set.
- **Orchestrator**: `HostProcessConfig.pushResolver` is called fresh on **every (re-)spawn**; `ensureAuthorityNode` + `createContainer` (storage profile only) write `config.push` into the child `cadre.json`. A resolver error degrades to "no push" (logs, doesn't fail the spawn). Logs record only `fcm=…/apns=…` presence, never keys.
- **CLI entry**: `cadre-host push {fcm,apns,options,status,clear}` — writes directly to the data dir's secret store + config (no running server needed); takes effect next authority respawn.

### 4. cadre-provider — per-tenant config + injection + isolation
- Config `push?: { default?, tenants?: Record<customerId, creds> }` (local types, see decision #2 below). `validate.ts` `validatePushConfig` rejects a partial set at `loadConfig` (fail fast at provider start). `loadConfig`'s `%O` debug dump now redacts push.
- `ContainerService` resolves **strictly by the launching tenant's `customerId`** (`resolveTenantPush`: tenant override → provider default → none) and the Docker orchestrator injects `CADRE_PUSH=<json>` (PEM-newline-safe). One tenant's creds never reach another's node.

### 5. Docs — `cadre-host.md` (new "Push credentials" section w/ out-of-agent infra steps), `architecture.md` (mechanism 5 clause), `STATUS.md`.

## Design decisions / deviations (please scrutinize)

- **`AuthoritySpawnConfig` does NOT carry resolved `PushCredentials`** (the ticket suggested it could). The ticket's own secret-at-rest edge case — "do not persist raw private keys in `state.json`; persist only a reference/flag and re-read the secret" — takes precedence. I used a `pushResolver` callback instead; `state.json` never sees a key (asserted by a test). This is the deliberate reconciliation of the two conflicting ticket bullets.
- **cadre-provider re-declares the push types locally** rather than importing from `@serfab/cadre-core`. The provider has no cadre-core dependency and importing a *value* (the validator) would pull cadre-core's full runtime graph (libp2p/optimystic via the `index.ts` → `CadreNode` edge) into a service that only shells to Docker. The validator logic is therefore duplicated (canonical in cadre-core for the host; provider-local in `validate.ts`). **Sync risk**: the provider's `PushCredentials`/`FcmCredentials`/`ApnsCredentials` shapes must track cadre-core's — both carry a comment saying so. A reviewer may prefer a `@serfab/cadre-core/push` subpath export to truly DRY this; I judged that more plumbing/risk than warranted.
- **Host entry is CLI-only.** The ticket mentioned "a new local-UI Settings field / CLI flag". I shipped the CLI (operates directly on disk, like `install`, not via the HTTP API the way DDNS does). No Fastify `PUT` route and no Svelte field were added — see gaps below.

## Known gaps / things for the reviewer to weigh

- **No HTTP route / Svelte UI field for push entry** — CLI only. `settings-store.ts` is touched only insofar as `PushSettings` flows through the `HostConfigFile` type; I did not add a `PUT /api/settings` push handler or a UI control. If the UI surface is required for this ticket, that's follow-up work (file a ticket).
- **`HostProcessOrchestrator.createContainer` push path is wired + unit-tested but not exercised by a live host flow** — `bin/host.ts` only calls `ensureAuthorityNode`; managed storage nodes via `createContainer` aren't spawned anywhere in the host today. The authority path is the one that matters now.
- **Provider type duplication** (decision #2) — verify the local shapes still match cadre-core's `PushCredentials`.
- **No real-container / on-device integration test** — the provider→container `CADRE_PUSH` handoff and host→child `cadre.json` handoff are unit-verified at each seam but not end-to-end against a running node or a real device. On-device wake validation (real token, bundle id, sandbox-vs-production for the build under test, a registered `DeviceToken`) and the Firebase/Apple credential creation are **out-of-agent**.
- **`CADRE_PUSH=` (empty) would wipe a file-config push** in the cli merge (empty→undefined override). Benign in practice (provider omits the var when absent; host never uses the env), but noted.
- **Flaky (pre-existing, not mine):** `cadre-host` `orchestrator.test.ts > getStats` can time out under full-suite parallel load (Windows `pidusage`); it passes in isolation and on a clean re-run. Not touched by this diff (no `.pre-existing-error.md` filed since it's a timing flake, not a stable failure).
