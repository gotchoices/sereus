# After a wake settles, the strand's timer cycle matches its resulting state

## What changed

`HibernationManager` (`packages/cadre-core/src/hibernation-manager.ts`) keeps an idle countdown (active → idle → hibernating) for live strands and a check-in chain for hibernating ones. Every wake clears both; before this change only the activity-driven wake put the idle countdown back, and only a failed wake put the chain back.

- **One settle path.** `beginWake` now takes the `StrandInstance` and, in its `finally` (`settleWake`), calls `rearmAfterWake(instance, hadCheckInChain)`:
  - status `'hibernating'` → clear any idle countdown; re-arm the check-in chain at base delay only if the wake cancelled an armed one;
  - otherwise `rearmIdleIfLive` (renamed from `rearmIdleAfterCheckIn`, still used by `runCheckIn`) → idle countdown for `'active'` / `'syncing'`;
  - nothing when `config.enabled` is false or the manager is stopped.
  This replaces `restoreCheckInChain` and the `.then` re-arm in `recordActivity` (its `.catch` log stays).
- **`wakeStrand(instance)`** now takes the instance. `CadreNode.wakeStrand` looks it up and, when unknown, logs and returns instead of calling the manager (before, `handleStrandWake` logged "not found" — same observable result).
- **Probe entry points for `serviceWake`.** `probeWake(instance)` records `{ hadCheckInChain }` in a new `probes` map (armed chain, or one already cancelled by a wake it joins), then wakes. While a probe holds the strand, the wake's settle arms nothing. `endProbe(instance)` takes the record and runs `rearmAfterWake`. `CadreNode.runServiceWake` calls `probeWake` and `endProbe` in a `finally` after its `catch`, so the failure path (after `rehibernateAfterFailedResume`) gets its chain back too. `probes` is cleared in `stop`, `untrackStrand` and `forceHibernate` (a force-hibernate mid-probe means "keep it down, no chain").
- `checkInsCancelledByWake` went from `Map<string, StrandInstance>` to `Set<string>` — the instance now arrives with the wake.
- `docs/architecture.md` Strand Hibernation: item 1 says any settled wake re-arms the timers for its resulting state; item 4 says `serviceWake`'s window decides the timers and restores a chain it interrupted but never creates one.
- Added a merge note to `tickets/fix/22.6-bug-strand-probe-failure-quiesces-a-runtime-it-does-not-own.md`: keep `endProbe` running last on every exit of `runServiceWake` however its `catch` is split.

## Tests added (`test/hibernation-manager.spec.ts`, "check-in backoff" block)

- `an explicit wake leaves the idle countdown running, for a hibernating strand and an already-live one` — the ticket's two reproductions in one `it`: both strands idle again 1000 ms after `wakeStrand`.
- `a probe that ends hibernating restores the check-in chain it interrupted, and arms nothing else` — `probeWake` → activity mid-probe (arms idle) → status `'hibernating'` → `endProbe`: chain restored at base delay (`nextCheckIn` 2150) for the strand that had one, none for a force-hibernated one, and the mid-probe idle countdown never fires.

Both fail with the re-arm calls in `rearmAfterWake` / `endProbe` stubbed out (checked by a temporary edit, reverted); so does the existing activity-wake re-arm test. Existing `manager.wakeStrand('id')` calls in the spec now pass the instance.

## Known gaps / things for the reviewer to check

- **No `CadreNode`-level test for the `runServiceWake` change** (by the ticket's design: it is two calls into the manager). The existing `serviceWake` tests in `test/cadre-node.spec.ts` pass but run with the manager not started, so they do not observe timers.
- **The "settle skipped while a probe holds the strand" rule is not pinned by a test.** `endProbe`'s clear-then-rearm makes the end state the same whether or not the settle had armed an idle countdown. The skip only changes behaviour when that countdown would *fire* mid-window (idle timeout shorter than the window, e.g. `archive` 10 s vs the 15 s default window): without the skip, `onIdle` would flip the strand to `'idle'` and emit `strand:idle` mid-probe. Judge whether that deserves a test.
- **Behaviour widening:** the activity-driven wake now re-arms idle for `'syncing'` as well as `'active'` (matches the check-in path and the ticket's expected behaviour).
- **Pre-existing, not touched:** with a custom `windowMs` longer than idle + hibernate timeouts, activity during the window can let the timer path quiesce the strand mid-window (and arm a chain via `handleHibernateTimeout`), after which `runWakeWindow` still marks it live because it saw activity. Unreachable with default timeouts (shortest idle + hibernate is `archive`'s 40 s vs the 15 s window); noted here only, no code change.
