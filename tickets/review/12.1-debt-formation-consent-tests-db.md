# Review: joiner-signed formation records — DB-level test sweep (part 1 of 2)

## What changed

Production code for joiner-signed formation records landed earlier
(`debt-formation-consent-core`). This ticket did the **test-only** follow-up for the
three specs that exercise `ControlDatabase` directly. No production file was touched.

The rule under test: every `CadreControl.FormationUsage` row must carry the JOINER's own
signature over a consent digest of (`Token`, `UsageStampId`, `PeerKey`, `Disclosure`),
verified against the row's `PeerKey`. The constraint that enforces it is named
`PeerConsented`. Previously these specs passed a bare `peerId` string; now they mint a
real ed25519 keypair and sign.

### New shared helper — `test/formation-consent-helper.ts`

- `mintJoiner()` → `{ privateKey, peerKey }`, a throwaway ed25519 joiner.
- `signJoinerConsent(joiner, { token, usageStampId, disclosure? })` → base64url signature
  over the consent digest.
- `mintConsent(token, disclosure = '', joiner = mintJoiner())` → spreadable
  `{ peerKey, usageStampId, peerSignature }`, fresh joiner + fresh nonce by default.

Call sites spread it: `db.recordFormationUsage({ token, strandId, ...mintConsent(token) })`.

### `control-formation-invite.spec.ts` (the bulk of the diff)

- All mechanical `peerId:` sites → `...mintConsent(token)`.
- `rawInsertFormationUsage` reworked to the 8-column row shape.
- The spec's local `Redemption` interface now carries `peerKey` / `peerSignature` /
  `peerPrivateKey`, plus a `reconsent()` helper that re-signs after a test mutates a
  digest-covered field.
- Cases that vary a digest-covered field (fresh nonce, peer swap — retitled
  "PeerKey alone", tampered disclosure) call `reconsent()` so they still fail for the
  reason the test is about, not for a stale signature.
- Cross-strand / cross-token / verbatim-replay / race cases deliberately left signing
  a stale-but-valid consent — that is the behavior they pin.
- Row selects and assertions now read `PeerKey` instead of `PeerId`.
- **New** describe: `FormationUsage.PeerConsented joiner-consent branch` — see risk note.

### `control-revocation-replay.spec.ts`

Nine formation sites spread `...mintConsent(<that site's token var>)`. `CadrePeer`
`peerId` usages are a different column and were intentionally left alone.

### `control-formation-recorder.spec.ts`

Abort-path tests against a booby-trapped fake DB. `mintUsageStampId` removed from that
fake; fixtures now carry plausible literal strings (`'joiner-pub-key'`,
`'joiner-consent-sig'`, `'stamp-1'`) — nothing in these tests verifies a signature, so
real keys would be noise.

## Where to point the review — honest gaps

**Highest-value target: the new `PeerConsented joiner-consent branch` describe**
(`control-formation-invite.spec.ts:1296-1360`). Three cases, all authored in this sweep,
none of which existed before, so they have no history of catching a real regression:

- *lands a consent whose signature matches the presented joiner key* — positive path;
  asserts the row stores both `PeerKey` and `PeerSig`.
- *refuses a consent signed by a DIFFERENT joiner than the key presented* — a second
  joiner signs the same token+nonce, filed under the first joiner's `PeerKey`. The test
  asserts `PeerConsented` is the **single** rejector, which depends on the pre-inserted
  owner-signed strand keeping `StrandExists` and `Authorized` satisfied. Worth confirming
  that assumption rather than trusting the comment.
- *rolls back the whole consent-seating transaction* — same forged shape through
  `redeemInvitation` with no strand pre-inserted; asserts both strand count and usage
  count are unchanged. This assumes `PeerConsented` is check-on-insert and fires at the
  usage insert **inside** the seating transaction. It passes, but the mechanism deserves a
  second read against `src/control-database.ts`.

**Other things a reviewer should not assume are settled:**

- Coverage is DB-level only. Nothing here proves the strand layer or the real network
  path signs correctly — that is part 2 plus the integration suite.
- `control-formation-recorder.spec.ts` now asserts against literal placeholder strings.
  If that fake DB ever grows real verification, those fixtures silently become wrong.
  Judgement call made here: acceptable, because the file only tests abort plumbing.
- The `reconsent()` helper is easy to forget at a new call site. A test that forgets it
  fails with `PeerConsented` instead of its intended constraint — a confusing symptom.
  Flagged rather than guarded; no mechanism prevents the mistake.
- `mintConsent` defaults `disclosure` to `''`. Any future case that inserts a non-empty
  disclosure must pass it to `mintConsent`, or the digest will not match.

## Settled design — do not re-open

- Nonce reuse is prevented by `UsageStampId` being `unique`; the verbatim-replay case
  pins that.
- A ValidationUrl invite needs BOTH signatures over the same nonce and the same
  disclosure bytes.
- A race loser's consent stays re-presentable under a new use number — `UseNumber` is
  outside the consent digest. The race test pins the vouch side.
- TypeScript excess-property checks do not fire on spread properties, so spreading a full
  `Redemption` (including `peerPrivateKey`) into calls is clean.
