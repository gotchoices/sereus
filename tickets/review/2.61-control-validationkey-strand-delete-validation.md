# Review: `ValidationKey` / `Strand` delete authorization

Delete + update authorization for `CadreControl.ValidationKey` and `CadreControl.Strand`.
The schema and test work landed in commits `78242ce` / `3dd8052` **unverified** — nothing had
been compiled or run. This ticket ran everything and fixed the fallout. All claims below are
now measured, not asserted.

## What the rules say now

Both tables previously had a single bare `constraint Authorized check (...)`. In Quereus a bare
`check` covers **insert and update**, never **delete** — so both tables accepted an
**unauthenticated delete from anyone**, and (for `Strand`) an unauthenticated rewrite. Each is now
five named constraints:

| constraint | fires on | rule |
| --- | --- | --- |
| `NotRevoked` | insert | the row's one-off nonce (`StampId`) must not already be retired in `Revocation` |
| `RevocationRecorded` | delete | the delete must file the matching `Revocation` row in the same transaction |
| `NoUpdate` | update | `false` — these rows are insert + delete only |
| `AuthorizedInsert` | insert | an owner signs an `'add'`-tagged digest over the new row |
| `AuthorizedDelete` | delete | an owner signs a **distinct** `'remove'`-tagged digest over the **stored** row |

`Strand.AuthorizedInsert` keeps its signature-free consent branch (a `FormationUsage` row for the
strand id *is* the authorization). `AuthorizedDelete` deliberately does **not** mirror it: an
invitation authorizes forming a strand, never destroying one. `Strand.MemberKeyClosedOnly` stayed
a bare `check` — it is a shape rule, not an authorization rule.

`Revocation.RowIsGone` gained `'ValidationKey'` and `'Strand'` branches, so a tombstone for either
table is refused while the row is still live.

## Use cases the reviewer should exercise

Each is a real test in `control-revocation-replay.spec.ts` (delete/tombstone) or
`control-authorization-binding.spec.ts` (update). Confirm the test proves what its name says.

**Delete authorization — both tables**
- Unsigned delete → refused (`AuthorizedDelete`). This is the hole the change exists to close.
- The row's own **enrollment/add** approval replayed as a delete → refused. Different action tag.
- A genuine `'remove'` signature minted for a **different row** → refused. No transplanting.
- An invited peer deleting a **consent-formed** strand, unsigned → refused. The consent branch is
  insert-only.

**Mandatory tombstone — both tables**
- A fully-signed delete with **no** `Revocation` row → refused (`RevocationRecorded`).
- A tombstone filed under the **wrong** `TableName` → refused (the subquery is table-scoped).
- Signed delete **plus** matching tombstone in one transaction → succeeds. Happy path.

**Replay after removal — both tables**
- Captured add approval replayed verbatim after removal → refused (`NotRevoked`); the stamp is
  retired permanently.
- Fresh stamp + fresh signature → re-add succeeds. Removal retires the *stamp*, not the identity.

**Update — both tables**
- Rotating `ValidationKey.StampId` by update → refused (`NoUpdate`). Rotation would strand the old
  stamp: never tombstoned, no longer on a live row, so the original approval could re-seat the key.
- Rewriting a consent-formed strand (`Type` → `'o'`, `MemberPrivateKey` → `null`) with no signature
  → refused (`NoUpdate`). Unfixed this destroyed the party's own membership key for that network,
  in place, unauthenticated.

## How the constraint-name assertions stay unambiguous

A delete that is *both* unsigned *and* missing its tombstone violates `AuthorizedDelete` **and**
`RevocationRecorded`, and the deferred-check queue does not promise which one reports. Every
authorization test therefore runs inside a transaction that **also files the matching tombstone**,
so `RevocationRecorded` is satisfied and only the authorization constraint can fail. Same technique
`control-ownerkey-self-authorization.spec.ts` already used. This worked on the first run — no
accepted-name list was widened anywhere, and the reviewer should treat widening one as a smell.

## Known gaps — treat the tests as a floor

- **No production caller.** Neither table has a shipped writer that signs the `'remove'` digest and
  files the tombstone, so today both tables are effectively un-deletable through any shipped code
  path — only the raw-SQL tests delete them. That writer is
  `control-signed-strand-validationkey-deleters` and is out of scope here, but it means these rules
  have **zero** production exercise. Weigh that when judging test coverage.
- **Untested happy path:** an owner-signed delete of a *consent-formed* strand (one seated via
  invitation rather than by owner signature). The owner branch of `AuthorizedDelete` should accept
  it — the row has a `StampId` like any other — but no test asserts it. The signed-delete happy path
  *is* covered for owner-seated strands.
- **`Revocation` itself is still unauthenticated.** Anyone can file a tombstone for a row that is
  already gone. Tracked as `bug-control-revocation-unauthenticated-writes`; not this ticket.
- **Per-node convergence.** `NotRevoked` is a per-transaction check against locally visible rows, so
  a node that has not yet converged on the `Revocation` row can still accept a replayed add.
  `CadrePeer` has a read-side mitigation (`listAuthorizedMembers` drops rows whose stamp is
  retired); `Strand` and `ValidationKey` deliberately do not, because neither has a per-request
  authorization surface today. Parked as a `NOTE:` comment on `Strand.NotRevoked` in
  `schemas/control.qsql` — conditional, not a defect.
- **Deferred-check ordering is an implicit dependency.** The name pinning above holds because
  satisfying `RevocationRecorded` leaves exactly one constraint able to fail. If Quereus ever
  reports multiple violated deferred constraints differently, these assertions get brittle. No
  action now; noted so a future failure is diagnosed rather than papered over.
