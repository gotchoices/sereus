# Review: always-on nodes host unclaimed strands as storage replicas

## What was built

Maintainer decision (2026-09-28): an always-on node joins every strand its strand filter admits as an ordinary Optimystic node that stores and serves the strand's blocks, whether or not the app is installed there.

- **Config.** `CadreNodeConfig.hostUnclaimedStrands?: boolean`, default `profile === 'storage'`. Resolved once in the `CadreNode` constructor, with a `NOTE:` tripwire on disk growth (no quota exists).
- **Storage replica** = the existing `StrandInstanceManager.startStrand` path with `sAppConfig` absent. That means no schema-signature check, no `App` schema, no `instance.sAppInfo`, and the default latency hint. The `Strand` membership schema, `StrandDatabase`, revoked-peer gate, membership reconciler and first-sync gate all run unchanged. `StrandDatabase` throws a clear error if asked to found without an sApp: `founderSApp()` is checked at the top of `initialize` and again in the bootstrap.
- **Launch path.** In `handleStrandAdded`'s no-config branch, `announceDiscoveredStrand` records the strand and emits `strand:discovered` only on first sight. Then, if the node hosts replicas, `launchStrand(strand, undefined)` runs in the same try / `strand:error` / rethrow shape as a claimed launch. `launchStrand` forces `founder: false` whenever there is no config.
- **App id for `sAppId` filters.** `recordReplicaSAppId` runs one `select sAppId from Strand.Header` and stores the result in `replicaSAppIds`. It runs whenever a replica's database may have just been published: after launch, on `strand:writable`, and after a hibernation resume. `getSAppId` falls back to it. A failed read logs and leaves the id unknown.
- **Harness.** `controlNodeConfig` and the restart-party child fixture default `hostUnclaimedStrands` to false. There, a storage machine only stands in for "holds control blocks". Every other harness builder goes through `controlNodeConfig`. `test-party.ts` builds raw libp2p nodes, not `CadreNode`s.
- **Docs and comments.** Both "a strand launches only on machines whose embedder registered its sApp config" premises are corrected (`refreshAuthorizedControlPeers`, and the `cluster-size.ts` comments). `architecture.md` changes:
  - Replication cluster size: the replica case is added, and the stale "nothing calls `registerMemberPeer`" is dropped.
  - Strand watcher paragraph and Strand Filtering: a new "Storage replicas" paragraph with bullets.
  - Deployment "Standard": the ≤4-machine replication statement, no quota, and hibernation.
  - The config block gains the new field.

  `strands.md` has two sites updated. `reference-app-rn.md` Steps 5–6 now say the drone stores blocks without the chat schema and cannot read or write messages. One line each went into the `testing.md` shape map and `cadre-consistency.md`.

## Deviations from the ticket, with reasons

- **`replicaSAppIds` is NOT cleared by `detachStrand`**, only by `cleanup`. The watcher's `sAppId` re-evaluation stops a rejected replica *through* `detachStrand`. If the id were cleared there, the next poll would find it unknown, re-admit the strand provisionally and relaunch the replica. That would repeat every other poll, forever. A strand id's sApp never changes, and the map is bounded by the party's published strands. The field's doc comment explains this.
- **A synchronous claim skips the replica launch.** After the emit, `handleStrandAdded` re-checks `sAppConfigs.has(id)`. A `strand:discovered` listener that calls `addStrand` registers its config before its first await, and without the check the replica launch would race that claim.
- **The event fires just before the replica launch, not after it.** The ticket's doc wording said "already running when it does". The types.ts and strands.md text says "right after" instead.
- **Scenario shape.** The always-on node is the party **owner** and the one that **publishes** the row, and the phone founds the strand (`addStrand({ founder: true })`). The reason is that a party has exactly one owner (`ControlDatabase.insertOwnerKey` works only at genesis and nothing seats a second), and only an owner can enroll the replacement phone. As a side effect the row names the always-on node as founder, so the scenario also exercises "a replica is always a joiner". Rows are written in two phases: 5 before the replica exists (delivered by the peer-join catch-up) and 5 after the mesh forms (delivered by cohort replication).

## Tests

- `packages/cadre-core/test/cadre-node-strand-added-failure.spec.ts` gets one new case: a storage-profile node whose stubbed launch rejects twice, then resolves. - `packages/integration-tests/src/scenarios/strand-always-on-replica-survives-phone-loss.integration.ts` is new. In order, it checks:
  1. The always-on node runs nothing while the phone writes its first rows.
  2. After publish, the replica comes up with no `sAppInfo`, one `strand:discovered`, and still in `getDiscoveredStrands()`.
  3. `getSAppId` returns the sApp id read from the Header.
  4. The strand mesh forms from the RPC-resolved seed.
  5. Every block in the phone's raw strand store is covered in the replica's raw store.
  6. The phone is stopped and its storage dropped.
  7. A freshly enrolled phone discovers the strand, `addStrand`s it, and reads all 10 rows back with the replica as its only strand peer.

## Known gaps and things to look at

- **An app claiming a strand this node already hosts is not handled yet.** That is ticket `claiming-a-hosted-strand-upgrades-in-place` (implement/, prereq on this one). Until it lands:
  - a non-founder claim gets the replica back with no `App` tables;
  - a founder claim (including `foundStrand` on a storage-profile node, where a watcher poll lands between publish and `addStrand`) throws "Cannot found strand … as a storage replica" and retries on the ladder.

  I added two arms to that ticket. One is a concurrent-launch race that bypasses its tracked-instance branch through `StrandInstanceManager.startStrand`'s "already running" early return. The other is the `foundStrand` trigger. No shipped embedder runs `profile: 'storage'` and claims strands: all `addStrand` and `foundStrand` callers are phone apps.
- **A stale `discoveredStrands` entry is possible, parked as a `NOTE:` on `announceDiscoveredStrand`.** If a replica launch keeps failing and the strand's row is removed during the backoff, the watcher has already forgotten the strand, so no removal arrives and the entry outlives the row.
- **A control-plane observation outside this ticket's scope, for the reviewer to weigh.** On the first scenario run, the owner's `authorizePeer` for the replacement phone, issued right after the lost phone stopped, failed with `BlockUnavailableError { blockId: 'default/cadrecontrol/Revocation', reason: 'cohort-unreachable' }`. The error came from a deferred CHECK reading the never-written `Revocation` table. The read side of that table got a permissive answer in the completed `isolated-node-reads-unwritten-revocation-table-as-empty`; the write-side `NotRevoked` checks did not.
  - The scenario now waits for the lost phone to leave the owner's control cohort (`readCohort`) before enrolling the replacement. That is realistic, since a replacement arrives long after a loss.
  - Seen once and not re-run without the wait. The failing call is inferred from the stack: a deferred constraint on `Revocation` during the first control write after the stop. I did not file a ticket.
- **Closed-strand replica.** Verified by inspection only, as planned. It is the same joiner path `strand-membership-second-machine` covers: party key from `StrandPartyKey`, reconciler writes `MemberPeer`. Note that a replica of a self-founded closed row with no `StrandPartyKey` row yet mints one (`resolveStrandPartyKey`), exactly as a founder launch would.
- **The "above four machines" doc statement is reasoned, not measured.** Replication proof above cohort size is `backlog/debt-replication-proof-above-cohort-size`.
- **Warm-restart hydrate on a replica** can load `App` table definitions from the replicated store. There is a comment at the `schema: undefined` site. The scenario does no restart, so this is not exercised.
