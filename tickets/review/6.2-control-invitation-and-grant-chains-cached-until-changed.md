## What changed

`ControlDatabase` now keeps seven membership views instead of three. The four new ones are `CadreInvite`, `CadreInviteUsage`, `OwnerGrant` and `OwnerGrantUsage`. Each is built by the existing `membershipView(sql, label)` helper and registered in `membershipViews`, so the existing table-change subscription (`watchMembershipTables`) and `invalidateMembershipViews` cover them with no other change.

- The two usage scans were inline strings. They are now `CADRE_INVITE_USAGE_SELECT_SQL` and `OWNER_GRANT_USAGE_SELECT_SQL`, each next to its row mapper. `CADRE_INVITE_SELECT_SQL` and `OWNER_GRANT_SELECT_SQL` remain the base the point reads append their `where` to.
- `queryCadreInvites`, `queryCadreInviteUsages`, `queryOwnerGrants` and `queryOwnerGrantUsages` read through `readMembershipRows(view, retry)` and map each row to a fresh object with the existing `*RowOf` mappers. Their `retry` contract is unchanged. `readMembershipRows` calls `ensureInitialized`, so dropping the explicit call is not a behaviour change.
- Still plain SQL, as the ticket specified: `queryCadreInvite` / `queryOwnerGrant` (point reads, used inside the redemption's locked body), `countCadreInviteUsage` / `countOwnerGrantUsage` (indexed pre-checks).
- `listCadreInviteStatuses` / `listOwnerGrantStatuses` were already built on `queryCadreInvites()` / `queryOwnerGrants()`, so they now derive from the view with no code change. Their per-row usage counts are still plain SQL.
- **Not changed, decide in review:** `hasLiveCadreInvite` (the admission gate's stranger path) still runs its own full scan of `CadreInvite` with a narrower select. It could derive from `queryCadreInvites()` and save the read. I left it alone because the ticket covers the membership refresh, and this read sits on a 2 s fail-open gate, where a view that is up to 15 s behind would refuse a stranger whose invitation was issued on another machine moments ago. A plain read of a block this node already holds would usually be just as behind, so moving it is probably safe. The decision belongs in a separate change.

Comments and docs:
- `cadre-node.ts`: removed `loadInvitationChain`'s "memoise verified pairs" NOTE and the grant-chain NOTE in `syncOwnerAnchor`. In their place, `loadInvitationChain`'s doc and `syncOwnerAnchor`'s cost NOTE now say the rows come from the membership views and reach storage only after the table changed or the view's maximum age passed. The body comment in `syncOwnerAnchor` was dropped rather than replaced, because the method doc now says the same thing.

That record is now an accepted-tradeoff `NOTE:` at the verify call in `hasAnchoredProof`: three verifies per invitation-admitted row per refresh, CPU only; a memo of verdicts would have to follow the trusted-owner anchor; revisit if the admission deadline shows it.
- `docs/architecture.md` → "Membership rows view": now lists the seven tables in two groups and explains why the four chain tables are safe to serve stale (append-only, so a stale copy only lacks rows, which fails closed). It also names the four queries that derive from the view and adds the redemption pre-checks to "What stays plain SQL". The `readMembershipRows` doc, the `membershipViews` field doc and the `membership-view.ts` module doc are updated to match.

## Checked by inspection (please re-check)

- **Callers and uncommitted inserts.** The four queries are called by `loadInvitationChain`, `loadOwnerGrantChain`, `planMachineRemoval`, `listCadreInviteStatuses` / `listOwnerGrantStatuses`, and two specs. None of them runs inside `inTransaction`. The redemption bodies (`redeemCadreInvite`, `redeemOwnerGrant`) read only the point reads and the counts. The membership listener runs after `mutateCadrePeer`'s body has committed. Its `CadrePeer` + `CadreInviteUsage` (or `OwnerKey` + `OwnerGrantUsage`) transaction fires both tables' change hooks inside the commit, so the refresh that follows loads fresh usage rows.
- **Shared rows.** All four mappers (`cadreInviteRowOf`, `cadreInviteUsageRowOf`, `ownerGrantRowOf`, `ownerGrantUsageRowOf`) build new objects. `loadInvitationChain` / `loadOwnerGrantChain` only key them into new `Map`s.
- **Specs that rig SQL.** No spec rigs reads of these four tables by their text (grepped `CadreControl.CadreInvite` / `CadreControl.OwnerGrant` under `packages/*/test`; the only hits are raw inserts, which fire the change hook like any commit). `control-read-retry.spec.ts` and `control-read-routing.spec.ts` already empty every view through `invalidateMembershipViews`, which now includes the new four.
- **Chain rows arriving after the `CadrePeer` row they prove.** The first refresh finds no usage row and does not authorize the machine. Loading the view initializes the table fully, which arms its replicated-change bridge, so when the usage row arrives the view is dropped and the next reconcile pass sees it. Nothing new to test here.
