# Subscription state and termination for non-payment (review)

Third ticket of the `provider-client-and-sign-up` chain. The app side that reads these fields is `reference-app-rn-rents-a-provider-node`.

## What was built

**Types** (`types.ts`, exported from `index.ts`): `SubscriptionStatus` (`active | past-due | lapsed`), `Subscription { status, renewsAt: Date | null, lapsesAt: Date | null }`, `StopReason` (`customer | non-payment`). `CustomerBilling.subscription` is required. `Container.stopReason?` is optional and passes through `redactContainer` unchanged.

**BillingService** (`billing-service.ts`):
- `initializeCustomer` writes `{ status: 'active', renewsAt: currentPeriodEnd, lapsesAt: null }`.
- `updateSubscription(customerId, patch: SubscriptionPatch)` is the webhook's write. It merges the fields it is given. It clears `lapsesAt` whenever the result is not `past-due`. It refuses `status: 'lapsed'`, both by type (`SubscriptionPatch`, exported) and at runtime, because writing `lapsed` there would mark the record without stopping anything, and `lapseSubscription` would then find nothing to do. It throws on an unknown customer.
- `lapseSubscription(customerId)` marks the record `lapsed` with both dates null, then terminates the customer's containers one at a time through `containerService.terminateContainer(id, { reason: 'non-payment' })`, logging and continuing on failure. Containers in `pending`, `creating`, `enrolling` or `running` are terminated; `stopping` is skipped (see deviations). It returns early when the record is already lapsed.
- `lapseOverdue()` lapses every `past-due` record whose `lapsesAt <= now()` and returns the lapsed customer ids. Before lapsing, each record is re-tested on its stored copy, so a renewal that arrives between the list and the lapse wins.
- The billing tick (`start()`, the usage-collection interval, only with `billing.enabled`) runs `collectUsage` and then `lapseOverdue`.
- `canCreateContainer` refuses a `lapsed` customer with "Subscription lapsed"; `past-due` still creates.
- New options: `containerService: Pick<ContainerService, 'terminateContainer'>` (required) and `now?: () => Date`. `createProviderServer` wires `containerService`.
- An in-process `lapsing` set keeps two concurrent lapses of one customer (an overlapping tick, or the webhook) from terminating the same containers twice. The early return on an already-lapsed record covers only sequential calls, and depends on the store handing out records by reference.

**Store** (`store.ts`): `ProviderStore.listCustomerBilling()` is new, on both MemoryStore and FileStore. FileStore now revives `subscription.renewsAt` and `lapsesAt` as `Date`s. Without that, the lapse sweep would never fire after a restart, because a string never compares as due.

**ContainerService** (`container-service.ts`):
- `terminateContainer(id, { reason? })` writes `stopReason` together with `stopping`, so if the provider dies mid-stop, the reap's stopping-to-stopped write keeps the reason. A record that already has a reason keeps it: a second terminate of a stopped container stops nothing. The `DELETE` route passes `customer`.
- **Race fix, not in the ticket:** the ticket claimed a lapse during `creating` was covered "by inspection of `waitForEnrollment`". It was not. A terminate during `creating` finds no `dockerId`, writes `stopped`, and then `provisionContainer` used to overwrite that with `enrolling` once the orchestrator returned, so the container ran on. The same race existed for a customer `DELETE`. A new private `advance(id, from, to, patch)` writes only when the record is still in `from`. It is used for pending→creating and creating→enrolling (on failure the just-created container is reclaimed) and for enrolling→running in `enrollIfHealthy`. `enrollIfHealthy` still returns true when the node reported healthy, even if the record had moved, so the waiter stops either way.

**Docs**: README → "Subscription state and termination for non-payment" (under Custom Billing) covers the fields, the Stripe mapping (`invoice.paid`, `invoice.payment_failed`, `customer.subscription.deleted`), the lapse behaviour, and that a renewal does not bring stopped containers back. The API table row for `GET /billing/status` links to it. `docs/architecture.md` → Provider Flow has one sentence on the lapse and `stopReason`, with a link.

## Tests added or changed

- `billing-lapse.test.ts` (new):

  - `lapseOverdue` with an injected `now` lapses a past-due record whose `lapsesAt` has passed and stops its container. A past-due record whose `lapsesAt` is later is left alone.

## Deviations from the ticket and known gaps (please weigh)

- **`stopping` is skipped by the lapse**, although the ticket says "every quota-consuming container". A `stopping` record already has a terminate or the reap working on it, and a second concurrent `stopContainer`/`removeContainer` could make one of them write `error`.
- **Existing FileStore data without `subscription` breaks loading.** `reviveBillingDates` reads `billing.subscription` unconditionally, so a `customer-billing.json` written before this change makes `loadCache` throw on every store call. There is no migration, following AGENTS.md "No backwards compat yet". A deployed data directory would need its billing file edited or removed.
- **`ProviderStore` gained a method** (`listCustomerBilling`). An operator's custom store must implement it.
- **A provider that dies mid-lapse** leaves the remaining containers running for a lapsed customer, and nothing retries. The record is marked before the stops so that creation is refused during the lapse. This is parked as a `NOTE:` on `lapseSubscription`, with the remedy: have the tick also stop the live containers of lapsed customers.
- **The `pending` window:** `advance('pending', 'creating')` closes resurrection there too. The only remaining interleave is between its read and write, which are microseconds apart.
- **The provision's catch still writes `error` over a `stopped` record** if the orchestrator's create throws after a terminate stopped it mid-create. The record keeps its `stopReason`. This is rare, and was not changed.
- **No test for `updateSubscription`.** Its two branches (refuse `lapsed`, clear `lapsesAt` unless `past-due`) are small; add one if you think they need pinning.
- **No route-level test** for `stopReason` on `GET /containers/:id` or for `subscription` on `GET /billing/status`. Both are pass-throughs of the stored record.
- **The README's Stripe example** reads the renewal date from `invoice.lines.data[0].period.end`, the subscription line's period end. That is the usual place for a subscription invoice; I did not verify it against a live Stripe account.
