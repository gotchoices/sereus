# Review: join backfill pushes once per peer, and the joiner waits for it

## What landed

**`PeerJoinBackfill` (`peer-join-backfill.ts`)**
- Per-peer memo (`PeerMemo`: `accepted` and `rejected`, blockId → revision), filled from each push reply by `recordReply`. A thrown chunk records nothing.
- A run skips a block, counting it in the new `PeerJoinBackfillResult.alreadyHeld`, when the peer accepted that revision or later, refused that revision, or the retained commit proof for that revision has `commits[peer].type === 'approve'` (`signedBy`). Skipped blocks are not offered and do not count toward `maxBlocks`.
- `done` now means: no push threw, the gate admitted the peer, the store is listable. Refusals no longer keep a peer un-memoized.
- First contact: a peer never run for (`contacted` set, filled in `trackRun`) is scheduled on a zero-delay timer instead of `debounceMs`. Zero-delay rather than a direct call so a same-turn identify burst still collapses and no work runs inside libp2p's event dispatch.
- The per-block reads moved into a `readOffer` helper (metadata → memo → proof → signer → materialized → size), so `runCatchUp` stays readable. The proof read now happens before the materialized read, since the signer check needs it.
- Module comment: RETRY section rewritten, new "WHAT IS PUSHED" section, the signer rule recorded as a `NOTE: accepted tradeoff` with a revisit condition. `NOTE:`s on `PeerMemo` cover a peer whose store was wiped under the same id, and the memo's size bound. The `maxBlocks` `NOTE:` is updated.

**Control gate (`cadre-node.ts`)**: `authorizePeer` is `admittingDevices.has(id) || authorizedControlPeers.has(id)`. It deliberately does not use `isControlNetworkMember`, which admits everyone while the snapshot is empty. The refresh `NOTE:` says a re-armed pass now costs a set lookup.

**Joiner waits for the push (`strand-instance-manager.ts`, `strand-first-sync-gate.ts`)**: deviates from the plan, which was measured to be inert as written:
- The plan's condition ("store empty at the first-probe point") never fires on a real first join. `strandDb.initialize()` itself fetches and persists the schema catalog (measured: 3 blocks at the probe point on the message-cost strand).
- So "first join" is judged **before** `initialize()` (`strandStoreEmpty`: listing yields nothing; a store without `listBlockIds`, or one whose listing throws, probes at once as before).
- With first-contact pushes, the founder's push usually lands **while the joiner initializes** (measured: 76 ms before `initialize()` returned). A plain skip then left the gate waiting out its 2 s backstop with every block already held (first measured run: `B whenStrandWritable` 2 046 ms).
- Fix: on a first join the gate subscribes to the storage change feed before `initialize()` (new `StrandFirstSyncGate.listen()`). The manager skips its first probe only when the gate has heard nothing (`heardDataSinceProbe`). `start()` probes after the 50 ms coalesce when data was already heard. `probeOnce()` now clears the "landed" flag itself (it used to be cleared in `probe()`).
- Measured: `initialize()`'s own catalog fetch raised no change event, while the push raised one per block. If a future Optimystic makes catalog fetches emit, a first join simply probes at once, which is the old behaviour.
- Restart, hibernation-wake and founder paths are unchanged: no early subscription, so the 7.4 reviewer's concern about the first probe's own fetches waking an immediate follow-up does not apply to them.

Invite case: the redemption phase is identical. Settle + idle A→B block-transfer went **92 → 182**. This is a regression until `cohort-join-catch-up-runs-once-per-node` lands:
- The owner is storage-profile, so its control node runs Optimystic's rebalance growth arm. That arm pushes the joiner every block whose cohort it entered, one request each, unless the owner's rebalance monitor already counts the joiner as a holder.
- The monitor learns holders from pushes the owner *receives*. Before this change the joiner pushed the owner's 101 blocks back, which taught it. Now the joiner skips blocks the owner signed, so the growth arm pushes 90 blocks (`reason=rebalance`).
- Confirmed by a run with the signer skip temporarily disabled: no rebalance pushes, settle 73, idle 28, matching the baseline.
- `cohort-join-catch-up-runs-once-per-node` (prereq on this ticket) turns that arm off where the backfill runs. I appended the counts to that ticket so its "before" is not misread.
- The cadre (`admitMember`) case was not measured and should show the same pattern.

Drain finding: it holds, so I filed `blocked/optimystic-embedder-cannot-report-block-holders`. In both cases Optimystic's under-replication drain re-sends, one request per block, the blocks the backfill delivered about 7 s earlier (strand 42, invite 91). No embedder API exists to tell it. The ledger's `satisfy` exists, but only on an untyped `(node as any)` attachment.

## Tests

- `peer-join-backfill.spec.ts`, new `describe('pushes each block to each peer once')`:
  - "pushes nothing on a forced run after a clean one": `alreadyHeld` equals the first run's `offered`, and only one push is made.
  - "remembers a refused block per revision": an identify-style rerun pushes nothing (the peer is done), a forced run skips it, and it is pushed once its local revision moves. This replaces the two specs whose contract changed ("lands remote-reported missing ids… a second run retries" and "does not re-arm when the receiver REFUSED"), both deleted.
  - "does not push a revision to a peer whose approval its commit proof carries": the block is skipped for the signer and pushed, with its proof, to another peer.
- `peer-join-backfill.spec.ts`, rewritten in place:
  - The mid-run chunk failure spec now asserts the retry pushes only the one unaccepted block.
  - The flapping spec now uses `debounceMs: 10_000` and asserts a never-contacted peer runs within 1 s.
  - `fakeProof` takes signers.
- `cadre-node-control-backfill.spec.ts`: the gate spec now asserts the snapshot gate, including that an empty snapshot admits no one. That is the load-bearing difference from `isControlNetworkMember`.
- `strand-first-sync-gate.spec.ts`, one added: "once listening, hears data that lands before start(), and start() then probes without waiting for the backstop". It pins the race fix found by measurement. The ticket said no test for the skipped first probe; this one covers the gate mechanism, not the manager wiring.

## Known gaps / for the reviewer

- **Interim invite and cadre regression** (above) until 7.6. Decide whether that ordering is acceptable, or whether 7.6 should be pulled ahead of this ticket's completion.
- **Tiny listen window**: `listen()` is called after the async emptiness check, so a push landing during that one listing step on an empty store is unheard, and the gate falls back to its backstop. I judged it not worth subscribing before the check, because that would subscribe restart launches early too.
- **Signer rule and Optimystic's own holder tracking**: the rule removes the joiner's push-back, which was incidentally informing the founder's rebalance monitor. Anything else in Optimystic that learns holders from received pushes loses that signal too. The rebalance monitor is the only consumer I found (`BlockTransferService` → `onBlockHolders`).
- **First contact on the control network** is usually denied (connect-then-authorize). The membership re-drive then uses the 250 ms debounce, because a denied run counts as contacted. This is "as today" per the plan. `admitRedeemingDevice` uses `forceCatchUpPeer` and is unaffected.
- **No test of the manager's first-join wiring** (`strandStoreEmpty` + `listen` + skipping the probe), per the ticket. The strand measurement and `strand-chat-participants-converge` exercise it.
- The memo and `contacted` are never cleared before `stop()`. `stop()` is terminal for an instance, so this is by design; the bound is in the `PeerMemo` `NOTE:`.
