# Review: adversarial cases for the one-redemption formation approval

The schema + writer change landed under the prereq ticket
(`debt-formation-approval-signature-replayable`). This ticket added ONLY test code — no
`src/` or `schemas/` file was touched. Diff is one file:
`packages/cadre-core/test/control-formation-invite.spec.ts`.

## What an approval covers (background for the reviewer)

When a `FormationInvite` carries a `ValidationUrl`, a `FormationUsage` row is admitted only
if a key the party enrolled in `CadreControl.ValidationKey` signed a digest over five
fields:

```
digest('CadreControl.FormationUsage', 'vouch', Token, UsageStampId, StrandId, PeerId, Disclosure)
```

`UsageStampId` is a single-use nonce the redeeming node mints *before* it asks the approver;
`PeerId` is the joining peer. `control-database.ts` → `formationVouchMessage()` builds the
same bytes in TypeScript, and the spec signs through that function so the two definitions
cannot drift apart.

Replay is refused by two **independent** mechanisms, and every added case is arranged so
exactly one of them can fire:

- an approval re-presented **verbatim** repeats its `UsageStampId`, refused by that column's
  `unique` — a duplicate-row error, *not* a named CHECK failure;
- an approval re-presented under **any other** redemption changes a signed field and fails
  the `Authorized` CHECK's `verify`.

## What changed

A nested `describe('one approval, one redemption (replay refusals)')` inside the existing
`FormationUsage.Authorized validation-key branch` block, plus two small edits outside it:

- a `sibling(redemption, tag)` helper next to the block's existing `vouch` / `validatingInvite`
  helpers — a second redemption of the same invite against the same host strand, with its own
  nonce and its own joining peer and everything else equal;
- the pre-existing `leaves an invite with NO ValidationUrl redeemable without any sign-off`
  case extended to assert the `usageStampId` the writer echoes back is the one that landed in
  the row (and the `PeerId` alongside it).

Six new cases:

| case | rejector pinned |
| --- | --- |
| approval re-filed under another joiner (bound, multi-use), then that joiner's own approval still lands as use #2 | `Authorized` |
| verbatim second presentation | `UNIQUE constraint failed: FormationUsage.UsageStampId` |
| approval filed against a different strand (unbound invite) | `Authorized` |
| approval minted over another live invite's token | `Authorized` |
| disclosure edited after the sign-off | `Authorized` |
| loser of a use-number race retries the SAME approval and lands as use #2 | `UNIQUE constraint failed: FormationUsage.Token, FormationUsage.UseNumber` |

Every case records against a pre-existing owner-signed strand via `recordFormationUsage`
(never `redeemInvitation`), so `StrandExists` and `Monotonic` are already satisfied and
`expectConstraintFailure(..., 'Authorized')` stays a single-rejector assertion — the block's
documented technique. Each `Authorized` case is followed by the same approval landing on its
correct redemption, so the refusal is provably about the one changed field and nothing else.

## Where to push hardest

Treat the list below as the known-soft edges, not a clean bill of health.

- **The two `UNIQUE constraint failed:` string matches.** They assert wording rendered by the
  optimystic vtab (`optimystic-module.ts` → `uniqueConstraintMessage`, which builds an
  UNQUALIFIED table name), a storage-layer detail the schema never promises. A reviewer should
  decide whether pinning a foreign package's error text is acceptable here or whether it wants
  a shared helper the way `expectConstraintFailure` is one. Parked as a `NOTE:` on the new
  describe block's doc comment rather than as a ticket, since nothing is wrong today.
- **The race case pins the primary-key collision, not `Monotonic`.** Both are genuinely
  violated by that insert; the vtab enforces the key on the insert, ahead of the deferred
  CHECK, so the PK message is what the engine emits. This was observed, not assumed — the
  assertion is exact and would fail loudly if the ordering inverted. Do not widen it to accept
  either. Same `NOTE:` covers it.
- **Cross-joiner case varies two signed fields, not one.** The stolen approval is presented
  with a different `PeerId` *and* a fresh nonce. The fresh nonce is required — reusing A's
  spent nonce would make `unique` the rejector instead of the digest — so `PeerId` alone
  cannot be isolated on a *spent* approval by this route. If a reviewer wants strict
  single-field isolation for `PeerId`, the shape would be an approval that never landed,
  presented under a different peer id. Judgement call; flagged rather than hidden.
- **Cross-strand case uses an unbound invite deliberately.** A bound invite would also trip
  `Authorized`'s own-strand clause (`FI.StrandId = new.StrandId`), and both clauses live
  inside the same named constraint, so the assertion could not tell them apart. Confirm the
  reasoning holds against the schema's NOTE on `FormationUsage.Authorized`.
- **Suite-wide state.** The block shares one node and one database across all its cases, and
  `usageCount()` is a whole-table count. Assertions are written as `before`/`before + 1`
  deltas rather than absolutes, but a reviewer adding a case should keep that discipline.
- **Nothing here exercises the two-node convergence gap** the schema NOTEs on `UsageStampId`
  and `ValidationKey` describe (`unique` is evaluated against locally visible rows, so
  unconverged nodes could each admit the same nonce). Single-node harness only; out of reach
  of this suite.
