# The phone reference app rents a provider node: implemented, for review

Fifth ticket of the `provider-client-and-sign-up` chain. Settings → **Rent an always-on node** shows the one provider the build names, signs the user in on the provider's pages in the system browser, rents a container through cadre-core's `rentNode` and lists each rented node with its standing, its join and the subscription's dates; a node the provider stopped offers Remove from cadre. The kit gained `@serfab/cadre-rn/provider` (the sign-in through an injected browser, the tokens in the secure store, the rental record) and `PhoneNode.nodeLocalRecords()`. `docs/reference-app-rn.md` → "Renting a Provider Node" is the user-facing description, including the dev setup; the kit README's "Provider" section is the API. Nothing has run on a device or against a live cadre-provider: `tickets/blocked/rn-device-run-rent-provider-node.md` lists what a human run must confirm.

## What was built

**Kit, `packages/cadre-rn/src/provider/`.**

- `signInWithProvider({ descriptor, clientId, redirectUri, openAuthSession, scopes?, fetch? })`: `createPkce`, `createAuthorizationState`, `authorizationUrl`, then `openAuthSession(url, redirectUri)`, then `readAuthorizationRedirect` and `exchangeAuthorizationCode`. Anything but a redirect is `'cancelled'`. A redirect carrying the provider's refusal throws `ProviderAuthError` with that code (so a user who taps Deny on the consent page sees "‹name› did not sign you in." rather than a silent cancel; a judgement call, easy to flip in `signInFailure` in `rentals.ts`).
- `providerTokensSlot(secureStore, providerId, options?)`: `load` / `save` / `clear` over one secure-store entry `sereus.provider-tokens.<base64url id>`; a malformed record reads as signed out, logged; a gated slot is refused as `secureStoreSlot` refuses one.
- `rentalStore(kv)`: `list` / `add` / `update` / `remove` by party under `rentalsKvKey(partyId)` (`rentals.<partyId>`, new in `node-local.ts`), serialized like the kit's other stores.
- `PhoneNode.nodeLocalRecords(): KvStoreApi`: the node-local database as a key-value store that re-resolves the handle per call and waits out a stop, which is what `linkRequestSlot` and `recommendationSlot` did privately; both now go through it. Not in the ticket's file list: the app has no other way to a `KvStoreApi` over the kit-owned database, since rn-leveldb allows one open handle per name.
- `package.json` `exports` gains `./provider`; the README's table and a "Provider" section with "What the app must install" (`expo-web-browser`).

**App.**

- `src/providers.ts` (pure): `configuredProviders()` from `EXPO_PUBLIC_PROVIDER_DESCRIPTOR_URL` and `EXPO_PUBLIC_PROVIDER_CLIENT_ID` (default `sereus-chat`); `providerRedirectUri(scheme)` = `<scheme>://provider-auth`; `isProviderAuthRedirect(url)`; `parsePlans` / `fetchPlans` / `planPriceText` for the descriptor's `plansUrl`.
- `src/provider-session.ts` (pure, platform injected): one provider's descriptor, tokens and client. `withClient(action)` signs in when signed out, and on `ProviderAuthError('reauthorize')` drops the pair, signs in again and runs `action` once more; `tokensRefused(err)` is the poll's version, which never opens the browser.
- `src/rentals.ts` (pure): `rentalRow(rental, reading, listed)` → status, join words, short peer id, notice and actions; `billingText`; `readingFromError` (404 → gone); `rentStepText`; `describeRentalFailure`; `recordingClient`, the `ProviderClient` decorator that records the rental the moment the provider creates the container.
- `src/provider-store-section.tsx`: the section. Descriptor fetched on mount (error + Retry on failure), plans listed, Terms and the provider's site linked (the site is `apiBaseUrl`'s origin). Owner only through the shared `useOwnerStanding`; the approval prompt in the add-node section's style; the progress line per `rentNode` step with the 20-second slow hint while claiming; rows polled every 5 s while mounted (`getContainer` per rental, `getBillingStatus` once, `listMachines` while any rental names a peer id), one read in flight at a time; the actions of the ticket's table; Cancel asks once; "Signed in to ‹name›. Sign out" or "Sign in to ‹name›" while signed out with rentals listed.
- `useCadre` gains `rentProviderNode(provider, client, { onProgress?, onCreated? })`, `finishProviderRental(client, containerId, onProgress?)`, `listRentals`, `noteRentalPeer`, `forgetRental`. The record is written inside `createContainer` (`finished: false`) and marked finished when `rentNode` or `finishRental` returns; both share `claimingRef` with `claimHostNode`, so two claims cannot run at once. `onCreated` exists so the section's reauthorize retry resumes the created container with `finishProviderRental` instead of renting a second one.
- `cadre-phone.ts`: `rentals = rentalStore(phone.nodeLocalRecords())` and `providerTokens(providerId)` over `expo-secure-store` with the default accessibility (tokens are used only in the foreground).
- Devices and nodes: a machine whose peer id a rental names gets the fact "Rented from ‹name›" (`rentedFromText` in `machines.ts`); the list also refreshes when the provider section changes a rental.
- `app/+native-intent.tsx` rewrites `<scheme>://provider-auth…` to `/settings` with no query.
- Shared pieces extracted so nothing is a third copy: `machine-removal.tsx` (`useMachineRemoval`, the plan, the Keep-switch prompt and `removeMachine`, used by Devices and nodes and by the provider rows), `owner-standing.ts` (`useOwnerStanding`, `standingLine`), `ConfirmPrompt` and `useLaterThan` in `settings-controls.tsx` (`WithdrawPrompt` is now a thin wrapper), `shortPeerId`, `machineCode` and `machineName` in `machines.ts` (pure) and re-exported from `settings-controls.tsx`.
- `expo-web-browser ~14.2.0` added to the app (SDK 53's bundled version); a native rebuild is needed before a device run.

## Deviations from the ticket, and why

- **`Rental` carries `providerName`.** Devices and nodes shows "Rented from ‹name›" from the record alone; the ticket's record had only the id, and the machines section fetches no descriptor.
- **The subscription line is once per provider, under the rows,** not on each row: `getBillingStatus` is per customer, so every row would repeat the same text.
- **The redirect URI is built from the scheme** (`ownScheme()`), not `Linking.createURL`, because the provider compares it with the registered one by exact string equality and `sereus-chat://provider-auth` is the registered spelling; `createURL` would spell it the same in a dev client and differently in Expo Go. Documented in `providers.ts` and the doc.
- **Both installs use client id `sereus-chat` by default**, with their own redirect URI each, which is the one client cadre-provider's README registers with both URIs; `EXPO_PUBLIC_PROVIDER_CLIENT_ID` overrides. The ticket's "the second install's client id" read two ways; this is the one the provider's example config supports.
- **`AuthSessionResult`'s second arm is `{ type: string; url?: undefined }`** rather than a literal union, because expo-web-browser spells its result types as a string enum, which does not assign to literals; the kit treats any result without a URL as a cancel.
- **The row for a container in `error`** offers Cancel (delete) and Remove from cadre when listed; the ticket did not name this state.

## What the reviewer should look at

- **Nothing has run against a live provider or on a device.** The browser hand-off, the claim over a real network, the second rental taking the invitation path and the non-payment row are the blocked ticket's. If the Android auth session does not resolve, the fallback the ticket names (read `code` and `state` off `/settings`'s query the way `nodeCode` is read and hand them to the pending sign-in) is not written; the `+native-intent` rewrite currently drops the query on purpose.
- **The poll's shape** in `provider-store-section.tsx`: one effect keyed on `[store, cadre.node, tick]`, single-flight, a `stopped` flag for unmount. A `tokensRefused` mid-loop marks every row signed out and stops that pass.
- **`recordingClient` logs and continues when the record write fails**, so the claim still happens; the node then joins with no record on this phone (Devices and nodes still lists it, without "Rented from"). Weighed as the lesser evil against an orphaned container; a different call is one `throw`.
- **`withClient`'s retry** re-runs the whole action once; `rent` resumes the created container through `onCreated`, Cancel's delete and Finish adding are idempotent, Try again is delete-then-rent and so is safe to repeat. A reauthorize during a claim is unlikely (the pair was just used for the create), but the resume path is untested beyond typecheck.
- **`useOwnerStanding` in the provider section re-reads after every action** (its key is the poll `tick`); Devices and nodes re-reads on Refresh. `add-device-section.tsx` keeps its own standing code, unconverted.
- **`machines.ts` now imports `node-claim.ts`** (for `ownerFingerprint`), which imports `@libp2p/utils` and `@multiformats/multiaddr`; `test/machines.spec.ts` still runs under Node, confirmed.
- The ticket's edge cases "User cancels checkout", "Token expired mid-flow" and "The provider stopped the node while the app was closed" are by inspection, as the ticket allowed.
