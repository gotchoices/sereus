# Node roles: one preset, separately settable roles

## What landed

`packages/cadre-core/src/node-roles.ts` is new and is now the only place a node class becomes behaviour. It declares `NodeRoles` (`alwaysOn`, `overlayTier`, `reactivity`, `strandCohortMember`), the two types the string roles use (`OverlayTier`, `ReactivityRole`), `NODE_ROLE_PRESETS` and `resolveNodeRoles(nodeClass, overrides?)`. All five are exported from `index.ts`.

`CadreNodeConfig` gained `roles?: Partial<NodeRoles>`. `CadreNode`'s constructor resolves the roles once into a private `roles` field and every former class comparison reads it: the control node's `fretProfile` and `arachnode.enableRingZulu`, the `hostUnclaimedStrands` default, `resolveRelayServer`, and `publishedProfile()`. `resolveRelayServer(network, roles)` takes the resolved roles in place of a class and defaults `enabled` from `roles.alwaysOn`. `StartStrandConfig.roles` replaces its `nodeClass`, so a strand woken from hibernation relaunches with the same roles, and the strand node reads them for its FRET tier, Ring Zulu, relay server and cohort-topic host profile. `strandCohortTopicOption` now takes the node's `ReactivityRole` and passes `host: { profile: coreProfile() | edgeProfile() }`.

Presets are unchanged behaviour: `device` → `{ false, 'edge', 'forwarder', true }`, `server` → `{ true, 'core', 'forwarder', true }`. A node built with no `roles` block behaves exactly as before — `forwarder` passes `coreProfile()` explicitly, which is what db-p2p was already building by default.

`strandCohortMember: false` throws at `CadreNode` construction, naming `strand-node-that-holds-no-blocks`. A role value outside its own set throws from `resolveNodeRoles` (`Invalid roles.<role> ...`); an unknown node class throws too.

## How to test it by hand

- **Nothing changes with no `roles` block.** Construct a `CadreNode` with `nodeClass: 'server'` and nothing else; `buildControlNodeOptions()` should still give `fretProfile: 'core'`, `arachnode.enableRingZulu: true`, `relay: true`. The same with `'device'` gives `'edge'`, `false`, `false`. `cadre-node-control-node-options.spec.ts` already covers this and passes unchanged, which is the main evidence that the refactor is behaviour-preserving.
- **One role at a time.** `{ nodeClass: 'device', roles: { alwaysOn: true } }` should run a relay server, host unclaimed strands, join Ring Zulu and publish `storage` in `CadrePeer.Profile`, while keeping `fretProfile: 'edge'`. `{ nodeClass: 'server', roles: { overlayTier: 'edge' } }` should do the reverse for the tier alone.
- **Explicit switches still win over the role.** `{ roles: { alwaysOn: true }, network: { enableRelay: false } }` runs no relay server; `{ nodeClass: 'device', hostUnclaimedStrands: true }` hosts replicas on a phone.
- **The published record and the heartbeat agree.** `publishedProfile()` is the single method both the publish site and the "is the stored row still current" comparison call, so they cannot disagree and cause a republish on every heartbeat. Worth re-reading `cadre-node.ts` around the heartbeat check to confirm no second derivation crept in.
- **Bad values.** `roles: { overlayTier: 'fast' }` and `roles: { alwaysOn: 'true' }` (from a JavaScript embedder) must throw at construction, not resolve to the preset.
- **Reactivity role.** With `strandReactivity: { enabled: true }` and `roles: { reactivity: 'subscriber' }`, the strand node's `cohortTopic.host.profile` must be `edgeProfile()`; with `forwarder` (or no role) it must be `coreProfile()`.

## Known gaps and things to look at

- **`arachnode-stub.ts` still compares `nodeClass === 'server'`,** at two sites. Deliberate and named in `node-roles.ts`'s module comment: it is a documented stub with no callers anywhere, and the storage rings it gates are unimplemented (`backlog/later/5-ring-zulu-storage-rings`). Converting it would change an exported signature (`createArachnodeStub(nodeClass, config)`) that the ticket did not sanction. Decide whether that is the right call or whether it should take `alwaysOn` now.
- **`provider/client.ts` names `'device'`/`'server'`** to narrow an untrusted field of an HTTP response. That is parsing, not behaviour, and is left alone.
- **`resolveNodeRoles` validates role VALUES but ignores unknown role KEYS.** `roles: { alwaysON: true }` from a JavaScript embedder resolves silently to the preset. The CLI's strict config checking refuses unknown keys at its own layer (ticket `cadre-cli-config-sets-node-roles`), so the hole is only for a direct embedder. Worth a view on whether `resolveNodeRoles` should reject them too.
- **`strandCohortMember` does nothing but be refused.** The role is in the type so the API does not change again when the Optimystic dependency lands.
- **`cadre-host` and `cadre-provider` still pass only a node class.** Out of scope here and in the CLI ticket; neither needs per-role control yet.

## The root-group finding the ticket asked for

The ticket asked whether a node with `strandCohortMember: true` and `reactivity: 'subscriber'` inside a strand's root group declines registrations and whether a commit it coordinates is announced. Both were researched in Optimystic and the answers are **worse than "just latency" in one case**, so the `strand-reactivity.ts` `NOTE:` was replaced by a fuller item in `docs/strands/app-schema.md` → "Known cost" rather than a one-liner:

- **It declines registrations.** On a root where a topic is already live it answers "unwilling member" and names the group's forwarder members, and the asking node retries one of those. On the FIRST registration at that root it answers "no state" and names no alternative, and the root step returns the first member that answers at all — so a root group whose first-dialed member is a subscriber can stay on the poll indefinitely rather than for one tick.
- **A commit it coordinated can be announced by nobody.** In a storage group of three or fewer (the common case) only the coordinating member retains a full commit certificate, so no sibling originates in its place. The subscriber builds the notification and drops it locally.
- Both are bounded by the watch service's tail poll (30 s forwarder, 20 s subscriber), so the cost is latency and not lost changes — but the first bullet means "latency" can be permanent for that root, not one interval. The combination is **not refused**: the simulation ticket needs it, and both presets are `forwarder`, so nothing reaches either case until a deployment sets the role.

This is recorded as a tripwire in the doc, not a ticket: it is fine now and only becomes work if a deployment sets `subscriber` on a root-group member.
