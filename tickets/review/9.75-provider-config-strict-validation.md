# Review: cadre-provider strict config validation

## What landed

The provider's `loadConfig` now runs the same pipeline as cadre-cli, on `@serfab/config-check`:

```
loadConfigFile(path)                       parse only → unknown; a parse error reads `Config <path>: <parser message>`
applyEnvironmentOverrides(raw, env)        each PROVIDER_*/STRIPE_* variable written on its own → { tree, provenance }
validateProviderConfig(tree, provenance)   field tables → ProviderConfigFile, or one Error listing every problem
deepMerge(DEFAULT_CONFIG, validated) ← overrides → validateAuthConfig, validatePushConfig
```

Only the validator's output is merged, so nothing it did not accept reaches `DEFAULT_CONFIG`'s merge, the server, or the `CADRE_PUSH` block handed to a tenant's node. That closes the cross-package defect in the ticket: an unknown key under `push` now fails provider start instead of failing every affected tenant node at provision time.

**`@serfab/config-check` additions** (`checkers.ts`, `validate.ts`, README):

- `recordOf(valueChecker)`: a mapping under caller-chosen keys (tenant ids). `nullIsAbsent` like `objectOf`; an empty or whitespace-only key is a problem; a `null` value is reported, not treated as absent.
- `ValidateOptions.concealUnder`: key paths whose subtree is described by kind only. `ValidationContext` gained `describe(keyPath, value)`, and every checker in the package (and the root check) now describes values through it. `describeValue` is still exported and unchanged; its `NOTE:` now says the option exists and why cadre-cli has not opted in. `isPathPrefix` moved from `validate.ts` into `checkers.ts` and is exported.
- cadre-cli passes nothing new, so its messages are unchanged (its 254 tests pass).

**Provider modules:**

- `config/env.ts` (new): one table of 17 variables, each written on its own. The grouping bug is gone: `PROVIDER_ALLOW_INSECURE_NO_AUTH` works without `PROVIDER_AUTH_MODE`, `PROVIDER_DOCKER_NETWORK` without socket or image, `STRIPE_*` without `PROVIDER_BILLING_ENABLED`. Boolean and number values are parsed by the package's strict parsers. The debug log redacts the two Stripe variables. `applyEnvironmentOverrides(raw, env = process.env)` replaces `loadEnvConfig`, which is gone. No unknown-variable check, with the reason in the module comment.
- `config/schema.ts` (new): field tables typed against `ProviderConfigFile`'s blocks, so a key added to a config interface without a checker fails to compile. `storage` has the cross-field `path`-with-`file` rule, hinting `PROVIDER_STORAGE_PATH`. `memoryLimit` and `cpuLimit` are checked by the same parse functions the orchestrator uses; an unquoted YAML `cpuLimit: 0.5` gets a message saying to quote it. `push.tenants` uses `recordOf`. `concealUnder: ['push', 'billing']`. Exports `isPortNumber` and `PORT_EXPECTED` for the CLI's `--port` check.
- `config/types.ts`: `DeepPartial` moved here from the loader and exported; `ProviderConfigFile = DeepPartial<ProviderConfig>`; the push-mirror sync comment now says the mirror also drives what the provider accepts and what happens on drift in each direction.
- `config/loader.ts`: the pipeline above. `LoadConfigOptions.env` (default `process.env`). Debug dump now redacts Stripe keys as well as push private keys.
- `service/resource-limits.ts` (new): `parseMemoryLimit` and `parseCpuLimit`, moved out of `DockerOrchestrator`, which now calls them. `parseCpuLimit` is stricter than the old `parseFloat`: only `^\d+(\.\d+)?$` is readable.
- `bin/provider.ts`: `--port` must be all digits and a port number, else `Invalid --port "80x": expected a whole number from 0 to 65535` (through the existing catch, so the line is prefixed `Failed to start provider service:` and the process exits 1).
- `service/store.ts`: `createStore` throws on `type: 'file'` with no `path` instead of silently returning `MemoryStore`.
- `src/index.ts`: exports `ProviderConfigFile`, `LoadConfigOptions`, `applyEnvironmentOverrides`, `validateProviderConfig`; `loadEnvConfig` removed (nothing outside the package imported it; cadre-host typechecks clean).

**Guard, config, docs:**

- `package.json`: `"@serfab/config-check": "workspace:^"` (`yarn.lock` updated).
- Stale-build guard: `test/global-setup.ts` with one target, `test/build-targets.spec.ts`, `globalSetup` and widened `include` in `vitest.config.ts`, `test` added to `tsconfig.typecheck.json` with `rootDir: "../.."` (copied from cadre-cli, for the same reason). `tsconfig.json` gained `"lib": ["ES2022"]` so `new Error(msg, { cause })` compiles, as cadre-cli and cadre-host already have.
- `docs/testing.md`: the two places that named cadre-provider as the unguarded package now say it is guarded.
- README → Configuration: strictness sentence with an example error, the rules an operator will trip on, and the Environment Variables table listing all 17 variables with the setting each writes. `example.provider.yaml` has a two-line note and still validates (pinned by a test).

## Behaviour changes an operator will see

- A config with a key the provider never read now refuses to start, naming the key and suggesting the nearest accepted one.
- `PROVIDER_BILLING_ENABLED=yes` and `PROVIDER_PORT=3000abc` fail start (`Invalid PROVIDER_PORT "3000abc": expected a number`); before, `yes` meant false and `3000abc` meant 3000.
- `PROVIDER_AUTH_MODE=apikey` fails start naming the variable; before, every request got 401 with no start-up error.
- `server:` with no children is treated as absent (defaults apply) instead of crashing.
- `storage.type: file` without a path fails start instead of running in memory.
- `memoryLimit: 512MB` fails start instead of running the container with no limit.
- Values under `push` and `billing` are never echoed into an error, even non-secret ones (`billing.enabled: "yes"` reports `got a string`).

## Tests added, each beside what it pins

All in `src/config/__tests__/config-validation.test.ts`; no per-field checker tests (the tables are compile-checked):

- misspelled `server.prot` with `PROVIDER_PORT` set → rejected, message names the file (not the variable) and suggests `port`. The attribution case from the ticket's edge list is folded in here.
- `push.tenants.acme.fcm.projectID` alongside an APNs private key pasted where the `apns` mapping belongs → rejected naming the key with a `projectId` suggestion and `apns must be a mapping of keys, got a string`; the message contains neither private key. This is the cross-package reproduction plus the one secret-concealment assertion.
- `PROVIDER_AUTH_MODE=apikey` → `Environment variable PROVIDER_AUTH_MODE: auth.mode must be one of …, got "apikey"`.
- file `auth.mode: none` plus `PROVIDER_ALLOW_INSECURE_NO_AUTH=true` alone → loads with the acknowledgement applied (the grouping bug; fails on the previous code).
- `example.provider.yaml` with an empty environment → loads, `storage` is `{ type: 'file', path: '/data/provider' }`.

`test/build-targets.spec.ts` is the shared three-assertion guard spec, not a new behaviour test. `auth-closed-default.test.ts` and `push-validate.test.ts` now pass `env` instead of touching `process.env`; their assertions are unchanged.

## Known gaps and judgement calls for the reviewer

- **Request-supplied resources are still unchecked.** `DockerOrchestrator.createContainer` takes `request.resources ?? this.config.defaultResources`; a create request's own `memoryLimit: "512MB"` still yields no limit (the parsers return `undefined`, as before). The route does not validate `resources`. This is the API path, not the config path, so I left it with a plain comment at the site rather than throwing there. Decide whether it is a `bug-` ticket (reachable now through the create API).
- **`config-check`'s env writer can echo a scalar before concealment applies.** `cloneBranch` reports `config key billing is "sk_live_…" where a mapping of keys was expected` when the file has a scalar where a block belongs and a variable writes under that block. Recorded as a `NOTE:` tripwire at the site; needs both mistakes at once.
- **`check` prints the full config to stdout**, including push private keys and Stripe keys. Pre-existing, unchanged; the operator asked for it. The debug dump is now redacted for both.
- **`parseCpuLimit` accepts `"0"`** (Docker treats 0 nano-CPUs as unlimited) and `parseMemoryLimit` accepts `"0"`. Same as before for memory; the CPU parser used to accept any `parseFloat`-able prefix.
- **No `portRange.start <= end` check.** Not in the ticket; a one-line `refine` if wanted.
- **`recordOf` rejects whitespace-only keys too**, slightly wider than the ticket's `""`.
- **`concealUnder` applies to all of `billing`**, so `billing.enabled: "yes"` reports `got a string` rather than the value. As specified; noting the trade.
- `DeepPartial` is reachable through `config/index.ts`'s `export *` but is not listed in `src/index.ts`. `envVarsFor` and `ENV_MAPPINGS` are internal to the config module (knip flagged the exports; nothing else uses them).
- The README's example error uses a hypothetical `/etc/cadre-provider.yaml` path.
