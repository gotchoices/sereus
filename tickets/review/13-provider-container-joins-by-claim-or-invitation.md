# A provider container joins by claim or by invitation — implemented

First of the `provider-client-and-sign-up` chain. The seed path (`pinnedOwnerKeys`, `GET /containers/:id/peer`, `PUT /containers/:id/seed`) is untouched; `provider-retires-the-seed-path` removes it once `provider-join-scenarios-phone-shaped-requester` has proven the two new paths on the wire. Nothing in this ticket ran against a real node: every test here is a unit test over a stubbed `/status`.

## What was built

**Request.** `POST /containers` takes `join: { kind: 'claim' }` or `join: { kind: 'invitation', invitation }` (`create-request-validation.ts`). A claim needs `docker.publicHost` (the route's existing `bootstrapNodesOptional` flag) and refuses `partyId`, a non-empty `bootstrapNodes` and `pinnedOwnerKeys` by name; its party is `UNCLAIMED_PARTY_ID` (`'unclaimed'`). An invitation takes its party from the bundle, refuses `bootstrapNodes` and `pinnedOwnerKeys`, accepts a body `partyId` only when it agrees, and needs no `publicHost`. `invitation-validation.ts` restates cadre-core's `isWellFormedCadreInvitation` with three deliberate differences, each explained in its header: members must be non-empty and each must parse as a multiaddr whose last `/p2p/` (past any relay hop) decodes; owner keys and the invitation key are checked as strings, not Ed25519 shapes; no error echoes the bundle. `bootstrapNodes: []` beside a join is accepted as "none". Without `join` the body is validated exactly as before.

**Types.** `ContainerJoinRequest` (wire, no credential), `ContainerJoin` (record, with the secret or bundle), `ContainerJoinState` (the node's last report), `RedactedContainer` (the API shape: no `seedToken`, `join` reduced to `{ kind }`), `Container.join`, `Container.joinState`, `Container.ownerKey`, `OrchestratorCreateRequest.join`, and `ContainerHealthStatus.node` gains `partyId`, `claim`, `claimedBy`, `invitation` (`ContainerInvitationStatus`). All exported from `index.ts`, with `UNCLAIMED_PARTY_ID`, `NodeCode`, `NodeCodeRefusal`, `NODE_CODE_PREFIX`, `encodeNodeCode`, `claimAddressesFor`.

**Service** (`container-service.ts`). `createContainer` mints the claim secret (32 random bytes, base64url, the one minting site) and stores `join` on the record; `provisionContainer` hands the record's `join` to the orchestrator and skips the "no pinned owner keys" log for join containers. `readStatus(container)` is now the one `/status` read: it fetches, then `foldJoinState` writes the join state the node reports onto the record when it differs from the stored one (a claim also replaces the record's `partyId` and `ownerKey`). `enrollIfHealthy`, `getContainerStatus`, `getPeerInfo` and `nodeCode` go through it, and the billing collector does too through a new `BillingServiceOptions.readStatus` hook the server wires. `nodeCode(id)` answers `{ code, peerId, multiaddrs }` or a typed refusal: `not-claimable`, `gone`, `already-claimed` (judged after a live read), `not-ready`. The addresses are the node's reported `/ws` or `/wss` entries at `hostComponent(publicHost)`, each given `/p2p/<peerId>` when it names no destination (`claimAddressesFor` in `node-code.ts`); `ContainerServiceOptions.publicHost` carries the host, and the server passes `config.docker.publicHost`.

**Environment** (`container-env.ts`). `buildNodeEnv` emits `CADRE_CLAIM_SECRET=<secret>` or `CADRE_INVITATION=<bundle>` from `request.join`, and throws when `pinnedOwnerKeys` is non-empty beside a join. Both orchestrators and the integration harness pass `request` through unchanged, so no orchestrator code changed beyond the type.

**Route.** `GET /containers/:id/code` (scope `containers:read`, ownership checked before the code is looked up): 200 `{ code, peerId, multiaddrs }`; 404; 409 `NOT_CLAIMABLE` / `ALREADY_CLAIMED` / `CONTAINER_GONE`; 503 `NOT_AVAILABLE`. The log line carries the container id only. `redactContainer` maps `join` to `{ kind }` on every container response.

**Docs.** README: API table rows (`/code`, and the previously unlisted `/peer` and `/seed`), a "Joining a cadre: claim or invitation" section before "Seed trust" (request shape, both flows, status codes, what the API shows, TLS sentence, `docker inspect` and the file store, restart behaviour), and a bullet under "Phones dial containers at the public host". `docs/architecture.md`: "Enrollment Flow: Phone Adds Provider Drone" has the claim flow as the primary diagram, the invitation flow second, key points for both, and the seed sequence kept and marked as what `provider-retires-the-seed-path` removes; "Provider Flow" has the same three diagrams and a corrected "provider only sees" line; row 4 of "Which Side Dials" names the three ways in, row 6 names the provider container, and the paragraph after the table says which a provider container picks.

## How to exercise it

- **Claim, by hand against a provider with `docker.publicHost` set:** `POST /containers {"join":{"kind":"claim"}}` → 201 with `partyId: "unclaimed"`, `join: {"kind":"claim"}`. Poll `GET /containers/:id/code`: 503 until the node is up, then 200. Paste the code into an app's `claimNode` (or `cadre-core`'s `decodeNodeClaimPayload` to inspect it). `GET /containers/:id` then shows `joinState.state: "claimed"`, the phone's `partyId` and `ownerKey`; `/code` answers 409 `ALREADY_CLAIMED`.
- **Claim on a provider without `publicHost`:** `POST` → 400 naming `docker.publicHost`.
- **Invitation:** `cadre enroll invite` on an owner node (or the app's `createCadreInvitation`), `POST /containers {"join":{"kind":"invitation","invitation":"sereus-invite:1.…"}}` → 201 with the bundle's `partyId`; `GET /containers/:id` moves `joinState` `pending` → `accepted` with `memberPeerId`. A spent bundle → `failed`, `invite-spent` in `error`, `retryable: false`.
- **Redaction:** no `POST`, `GET` or list body contains the secret or the bundle; `docker inspect` on the host does show both in the env, as documented.
- **Seed path unchanged:** every pre-existing test passes untouched.

## Known gaps and things to look at

- **Nothing here ran against a real `cadre-cli` node.** The `/status` shapes the fold reads (`node.claim`, `node.claimedBy`, `node.partyId`, `node.invitation`) were taken from `packages/cadre-cli/src/server/health.ts` by reading, and the placeholder-party rule from cadre-host's `reportsClaim`. The scenario ticket is the wire proof; if the real node reports something these tests did not stub, the fold is where it shows.
- **`Container.ownerKey` duplicates `joinState.ownerKey`** (and `partyId` duplicates `joinState.partyId`) on a claimed record. The ticket asked for both; the record fields are what the list filter and billing read, the `joinState` is the node's self-contained report. A reviewer may prefer one.
- **The service does not force the placeholder party for a direct caller** passing `join: { kind: 'claim' }` with a real `partyId`; only the validator does. cadre-cli treats whatever party it is given as the placeholder and takes the real one from the claim, so a direct caller's value is harmless but misleading on the record until the fold. The scenario ticket's direct `createContainer` call should pass `UNCLAIMED_PARTY_ID`.
- **`nodeCode` without `publicHost`** is `not-ready` forever (no address qualifies). Documented in code and README as the validator's rule applied to a direct caller; a reviewer might want a distinct refusal.
- **The fold stamps `updatedAt`**, which the stuck-enrolling reap TTL reads. A join state changes at most twice per container (awaiting → claimed; pending → accepted or failed), so the TTL slips by at most one interval; not worth a `NOTE`, but it is a new writer on `enrolling` records.
- **`invitation-validation.ts` is stricter than cadre-core on `members`** (non-empty, each a dialable multiaddr with a decodable destination). A bundle cadre-core's own decoder accepts can be refused here; the header says why. The member cap (64) mirrors cadre-core's constant by value only.
- **`already-claimed` after an unreachable read**: `nodeCode` judges on the stored `joinState` after a live read, so a container claimed on an earlier read still answers `already-claimed` while its node is briefly down; a never-folded container whose node is down answers `not-ready`. Intended, but worth a glance.
- **The route test covers two refusals and 404 only**; `ALREADY_CLAIMED` and `CONTAINER_GONE` are pinned at the service level, and the mapping table is one object in `routes.ts`.
- **README is hard-wrapped** to match the file's existing style; `docs/architecture.md` additions are one paragraph per line as the rest of that file.

## Tripwires recorded in code

- `container-service.ts` → `reapTtlMsFor`: `NOTE` that an unclaimed `running` container is never reaped and is billed until deleted; if abandoned unclaimed containers pile up, stop them after a TTL there.
- `container-service.ts` → `joinStateFrom` (`failed` arm): `NOTE` that a spent invitation leaves the container running with nothing to do and there is no retry route; the app deletes and rents again.
- `node-code.ts` header: `NOTE` that the encoder mirrors cadre-core's `encodeNodeClaimPayload` and that keeping them in step is manual; the test decodes against the sorted-key JSON cadre-core emits.
