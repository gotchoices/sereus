# Phone reference app joins the app that recommended it (recommended side)

The recommended app's half of "recommend an app and enroll it on first launch". **B** is this app, installed or opened because of a recommendation. **A** is the owner app that recommended it and holds a one-hour pre-approval for B's scheme. A's side landed in `reference-app-rn-recommends-an-app`, and the kit pieces (`recommendedBySchemeFromReferrer`, `parseCadreLink`'s `recommended-by` kind) in `phone-kit-app-recommendations`. The design is docs/architecture.md → "Recommending another app".

B adds no protocol. It opens A with its ordinary join request (`askOwnerApp(A)`), and A answers without a prompt because of the pre-approval. What this ticket adds is learning which app recommended B, so B can name it and open it directly.

## What was built

- **`src/recommended-by.ts` (new).**
  - `recommendingApp(scheme, source)`: looks the scheme up by exact equality in `otherSereusApps()` (the kit's `KNOWN_SEREUS_APPS` plus `extraSereusApps()`, own scheme left out). Anything else returns null and is logged, quoted and cut to 64 characters, since the text is anyone's. It never throws: if `ownScheme()` throws (a build with no single scheme), that is logged and read as none.
  - `appFromInstallReferrer()`: reads `Application.getInstallReferrerAsync()`, races it against `REFERRER_WAIT_MS` (2000), and passes the result through `recommendedBySchemeFromReferrer` and then `recommendingApp`. A rejection, a timeout, a non-token referrer (such as `utm_…`) and an unknown scheme are each logged and read as null. It never throws. The 2 s bound is inside the read, so a referrer that arrives late is simply never seen.
- **`app/+native-intent.tsx`.** The `recommended-by` case now routes to `/settings?recommendedBy=<scheme>`, replacing the pass-through that the kit ticket left.
- **`app/settings.tsx`.**
  - `useRecommendingApp(asking, settled, joinUnderWay, onNamed)` returns `{ named, reading, dropNamed, suggested, dropSuggested }`.
  - The referrer is read on Android only, once per mount (a ref guards it), the first time `asking` is true.
  - The `recommendedBy` parameter is cleared on read, as `useLinkedNodeCode` does, and resolved. The app it names is held in `linked` until `settled` (= `startSettled`).
  - Once settled, if `asking`, the link names A in the question: it sets `linkNamed`, clears a previous Other choices, and calls `onNamed`, which resets the first-launch answer to null so the question shows again. Otherwise, if `joinUnderWay` (`cadre.linkRequest !== null || cadre.joinFlow !== null`), the link is dropped with an info log. Otherwise it is offered through the prompt.
  - `named = dropped ? null : linkNamed ?? referrerApp`, so the link wins over the referrer.
  - `reading` is true while the referrer is pending and no link named an app. While it is true, the Node card shows the status row in place of the question, as it does during the launch read.
  - `RecommendedFirstLaunchQuestion`: "‹A› suggested this app. Join the cadre it holds?", with **Join through ‹A›** and **Other choices**. Join sets the answer to `'join'`, so the join section and its waiting line show, and calls `askOwnerAppOrAlert(cadre.askOwnerApp, A, showAlert)`. Other choices sets `dropped`.
  - `RecommendedJoinPrompt`: a modal, "‹A› suggests joining the cadre it holds", with a line saying that chats move and the old cadre is removed, and **Join through ‹A›** and **Not now**. The system back button means Not now.
- **`src/join-cadre-section.tsx`.** `AskOwnerApp.ask`'s try/alert body is now the exported `askOwnerAppOrAlert`, which Settings shares. It adds one branch: on Android, when `app` is non-null and does not open by its scheme, it retries with `askOwnerApp(null)`, which opens the chooser. The existing section never passes a non-null app on Android, so its behaviour is unchanged.
- **`src/test-ids.ts`.** Adds `firstLaunchRecommendedJoinBtn` (`btn-first-launch-recommended-join`) and `firstLaunchOtherChoicesBtn` (`btn-first-launch-other-choices`), as the ticket asked. It also adds `recommendedJoinBtn` and `recommendedNotNowBtn` for the prompt, which the ticket did not list; every other prompt in Settings has ids.
- **`package.json` and `yarn.lock`.** Add `expo-application` `~6.1.5` via `npx expo install expo-application`. The lockfile change is the one workspace line, because 6.1.5 was already installed as a dependency of `expo-notifications`.

It covers the two hints, the trust rule, the named question, the 2 s bound, iOS, the prompt for an app with a cadre, why it takes one tap, and A's ordinary prompt when the permission is gone.

## Decisions a reviewer should check

- **No native rebuild for `expo-application`; the ticket said it needs one.** Before the dependency was added, `npx expo-modules-autolinking search` already listed `expo-application` 6.1.5 at `packages/reference-app-rn/node_modules/expo-application`, pulled in by `expo-notifications`. Autolinking in SDK 53 links what it finds there, so dev clients built with `expo-notifications` should already carry `ExpoApplication` and the Play install-referrer library. The doc says this and says it has not been confirmed on a device. If it is wrong, an old dev client throws when Settings loads, because `recommended-by.ts` imports `expo-application` at module scope.
- **Other choices drops the hint until another link names an app,** not strictly "for this mount". A link that arrives later is a new user action (A's Open ‹B›), so it names A again. The referrer never re-names after a drop.
- **A link that arrives while `asking` resets the first-launch answer.** If the user had tapped **Yes** or **No, start fresh**, the named question replaces the join section or the Connect form. The ticket said only "names A in the first-launch question". Without the reset, a link would do nothing visible after an answer.
- **While the referrer read is pending, the Node card shows the plain status row** (`Status idle`), the same as during the launch read. It shows for at most 2 s, and only on Android.
- **The prompt adds a consequence line** ("This app's chats move into that cadre, and its own cadre is then removed from this phone."), which the ticket did not specify. The join it starts moves chats and dissolves the old cadre, so the prompt says so.

## Known gaps

- **No device run.** Nothing here has run on a phone, including whether `getInstallReferrerAsync` resolves, rejects or hangs on a sideloaded dev build. The 2 s bound covers a hang. The rows are in `tickets/blocked/rn-device-run-same-phone-join-by-link.md`.
- **The Play referrer path cannot be run until a Sereus app is on a Play testing track.** No known-apps entry has an `androidPackage` yet. Recorded in the device-run ticket.
- **Maestro first-launch waits.** `maestro/_setup.yaml` waits up to 15 s for `btn-first-launch-join`, which covers the extra ≤2 s. `maestro/flows/4-solo-create-strand.yaml` taps `btn-first-launch-fresh` only `when: visible`, an optional lookup. On an Android emulator where the referrer read hangs, the question can now appear up to 2 s later, which narrows that lookup's margin. Not run.
- **A prompt already open when a join starts stays open.** If a join response arrives and starts a join while the prompt shows (a race), the prompt is not withdrawn. Tapping Join then opens A with a request while the join is on screen, and A's answer is refused as "A join is already under way". I judged this too rare to handle.

## Use cases to check by inspection

- **Android fresh install from A's Play link.** `asking` → status row → the referrer resolves to `sereus-recommended-by:1.<A>` → A is on the list → the named question → Join through A → `askOwnerApp(A)` opens `<A>://cadre-join-request/…` → A answers with no prompt → `useLinkedJoinResponse` → the join.
- **The referrer names an unknown scheme, B's own scheme, or `utm` text:** logged, then the plain question.
- **The referrer read rejects (sideload) or hangs:** logged, and the plain question shows at once or after 2 s.
- **A saved start exists:** `asking` is never true, so the referrer is never read.
- **iOS:** `referrer` starts as null, so there is no wait and the plain question shows. Yes → Choose → A is answered without a prompt by A.
- **A link while B has a cadre:** the link waits for `startSettled`, then the prompt opens. Join → `askOwnerApp(A)`, and the waiting line shows in the connected join section.
- **A link during a first-launch join, or while a request is open:** `joinUnderWay` is true, so the link is dropped with an info log.
- **A link and a join response in one launch:** both effects run when `startSettled` flips. `cadre.linkRequest` is still non-null at that render, so the alert is suppressed. On a first launch (`asking`), the link names A in the question, and the join that the response starts hides it.
- **A referrer and a link name different apps:** `linkNamed ?? referrerApp`, so the link wins.
- **Join through A when A is uninstalled:** on Android, the scheme open fails and the chooser opens. On iOS, the alert "Could not open ‹A›" shows with the copy-request line.
