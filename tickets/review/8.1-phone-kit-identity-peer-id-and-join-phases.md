# Phone kit: the identity's peer id without a node, and the join's later phases (review)

Part of the "join an existing cadre" screens (the screens themselves are `reference-app-rn-joins-existing-cadre`). Kit changes only.

## What landed

`PhoneNode.identityPeerId(): Promise<string>` (`node.ts`, the `PhoneNodeRuntime.identityPeerId` method):
- Status `running` or `joining` with a started node (`node.peerId` defined): resolves at once with that peer id, without queueing behind a join that may wait minutes.
- Otherwise, inside the transition queue (`inTurn`): `loadOrCreateIdentityKey(this.keyStore, DEFAULT_IDENTITY_KEY_ID)` on the kit's own `SecureStoreKeyStore`, returning `key.publicKey.toString()`.
- **Deviation from the ticket:** the ticket said `peerIdFromPrivateKey(key).toString()` from `@libp2p/peer-id`. That package is only a transitive dependency of cadre-rn (a comment in `test/node-local.spec.ts` notes this is deliberate), so I used `publicKey.toString()` instead, which in `@libp2p/crypto` 5.x is the base58btc encoding of the identity multihash, the same string as the peer id. The new test checks that equality against the started node. If the reviewer prefers the explicit call, add `@libp2p/peer-id` to cadre-rn's `dependencies` (this changes the lockfile).
- A secure-store read error propagates, as it does in `loadOrCreateIdentityKey`.

`PhoneJoinProgress` (exported from `phone-node/index.ts`) = `CadreJoinProgress | { state: 'admitted'; grantsOwner } | { state: 'moving-strands' }`; `JoinCadreOptions.onProgress` now takes it. It is still passed straight to cadre-core's redemption (the narrower type is assignable).
- `admitted` is emitted right after `redeemCadreInvitation` resolves, in both `redeemInPlace` and `startAndRedeem`.
- `moving-strands` is emitted in `startAndRedeem` after the start is saved and just before `settleJoinMove`, only when `movingFrom !== undefined` (now passed in from `switchParty`) and the owner step returned `'enrolled'`. `redeemInPlace` never emits it: it has no `movingFrom`, even though it can finish an earlier deferred move. That matches the ticket ("this join recorded a move").
- Both kit-emitted calls go through `reportProgress`, which logs a throwing listener with `console.warn('[cadre-rn/phone-node] join progress listener threw:', …)` and continues.

README: new `identityPeerId()` row, an expanded `joinCadre` `onProgress` description, and an `onProgress` example in "Joining another cadre" that handles all three states.

## Tests

- `node.spec.ts` › "reports the identity's peer id before any start, and the first start uses it": on a fresh device, `identityPeerId()`, then `start`; the node's peer id equals the earlier value. This covers the first-run key generation plus the `publicKey.toString()` = peer id equivalence.
- The progress events are not tested: they happen after admission, which the in-process harness cannot reach. Check them by reading the code.

## For the reviewer

- `identityPeerId()` during `joining` before `node.peerId` exists: unreachable in practice, because `joining` is set after `bringUp` has started libp2p. If it did happen, the call would queue behind the join; the fallback exists only because cadre-core types `peerId` as optional.
- `node.ts` is now about 1000 lines. A `NOTE:` tripwire at the join section already covers splitting it out.
