# A joining machine cannot write before its first sync

Implements `joining-machine-writes-before-first-sync-fork-tables`. The prerequisite (`strand-app-table-names-collide-with-strand-tables`) landed at commit 47580d1; the regression scenario uses the renamed chat schema.

## What was built

**The invariant, enforced in `StrandInstanceManager.buildStrandRuntime`:** a machine that has never held this strand's `Strand.Header` row must not commit to it. After `StrandDatabase.initialize()`:

- a **founder** launch (`config.founder === true`) publishes its database at once (its bootstrap just wrote the Header);
- any other launch reads `Strand.Header` once (`strandHeaderHeld`, a `select count(1)` via `db.eval`; a throwing read counts as "not held"). Held → published at once, so a restart, a hibernation resume over a store that has synced before, and a joiner whose seed already delivered the Header are never gated. Not held → the instance comes up **`'syncing'`** with `StrandInstance.database` unset, and a `StrandFirstSyncGate` holds the `StrandDatabase` and re-probes every `strandFirstSync.pollIntervalMs` (500 ms) until the row is readable. Reads never invent a collection (optimystic's `Collection.open` resolves undefined on an authoritatively absent header, throws on an unreachable one), so the probe is safe to repeat.
- The gate object exists from the moment the `StrandDatabase` object does, so a failed `initialize()` is rolled back through it (`releaseRuntime` stops the gate and closes its database); once published the handle moves to `instance.database` and the gate is dropped. The two are mutually exclusive.
- **Opening:** `publishDatabase` sets `instance.database`, bumps `lastActivity`, releases every `whenWritable` waiter, flips `'syncing'` → `'active'`, and calls the retained config's `onWritable` — which `CadreNode` emits as **`strand:writable`**. A publish that lands while the instance is still `'starting'` announces nothing: `strand:started` is about to report `'active'`, and `strand:writable` is defined as the follow-up to a `'syncing'` start, never a duplicate.
- **Founder request against a gated instance** (`foundStrand` after a joiner-shaped attach): `foundExistingStrand` / `ensureFounderBootstrap` run the bootstrap against the gate's database and, on success, publish it — writing the Header locally is the one legitimate way to become writable without a peer. A refused bootstrap (pre-split, missing party key) leaves the instance gated and withdraws the founder flip as before.
- **`CadreNode.addStrand` resolves only once the strand is writable**, bounded by `CadreNodeConfig.strandFirstSync.timeoutMs` (default 30 s). On timeout it rejects with **`StrandAwaitingFirstSyncError`** ("no member of this strand has been reachable since this machine joined …"); nothing is torn down, the gate keeps probing, and the same call made again completes the attach (the tracked-instance path returns the still-syncing instance and the wait picks it up). The wait applies only to a LIVE gated instance (`isAwaitingFirstSync`: `libp2pNode` set, `database` unset), so a hibernating instance is returned as it always was. `StrandConfig.awaitFirstSync: false` returns the `'syncing'` instance immediately for callers that wire their own peers first; `CadreNode.whenStrandWritable(strandId, { timeoutMs })` is the promise form of the event. `FoundStrandConfig.awaitFirstSync` forwards to the attach, which matters only when `foundStrand` adopts a sibling's row.
- **Background loops wait with the app.** The membership reconciler and revocation enforcer read `instance.database` lazily per pass; while gated they see `undefined` and idle, so the reconciler cannot seat a `Strand.Member` row into a forked table either. Peer-join backfill and relay supervision run as before.
- **Hibernation:** `handleStrandWake` (live branch) and `runWakeWindow` set the status through `liveStrandStatus`, so a gated joiner wakes back to `'syncing'`, never a false `'active'`. `releaseRuntime` on a gated instance closes the withheld database and stops the probe; the rebuild re-probes over the same store (the unit spec covers quiesce → resume both with and without the Header arriving in between, and a `whenWritable` waiter surviving the cycle). A joiner that never reaches anyone records no activity, so it idles and hibernates on the usual timers and each check-in resume re-probes.
- **No way to disable the gate** by design: a machine that holds the Header is never gated, so nothing that worked before is blocked.

**Reference apps.** RN `use-cadre` re-renders on `strand:writable`; `use-chat` registers the local participant only once `strand.database` is set (dep on it). NativeScript `cadre-vm` subscribes to `strand:writable`; `chat-vm` registers only with a database and re-attaches every poll while unregistered. Web `store.svelte` records the event and re-syncs strand status (`messages.svelte` already gated on `status === 'active' && database`). `joinClosedChatStrand` (RN) writes the member role after `addStrand`, which is now safe; its doc says so. None of this was run on a device or in a browser — see "Not done".

**Docs.** `docs/strands.md` gained "Joining: no writes before the first sync" (the invariant, the measurement, the runtime behaviour, the app contract, and the residual); `docs/architecture.md` has the `syncing` state in the table, the diagram and the `StrandInstance` type.

## Why so many tests changed

Production launches always have a founder (`foundStrand`, a row this machine published, or an explicit `founder: true`). The test suite did not: many scenarios and specs launched a "founder" from a hand-built row with `FounderOwnerKey: null` and no flag, which derives to a joiner and wrote no Header at all — fine while a lone joiner could write, a deadlock under the invariant. Every such site now founds explicitly (open strands: `founder: true` seats only the Header; closed: plus a `partyMemberPrivateKey`), and every hand-dialed joiner launches with `awaitFirstSync: false`, dials, then awaits `whenStrandWritable`. Specs that asserted "a joiner alone comes up active with an empty database" now assert the new contract (`'syncing'`, no database).

- Harness: `joinStrandOn` founds on `members[0]` by default (`founder` now defaults to true; `false` is documented as "assert the gate itself"), launches members 1..n unwaited, and after the mesh waits for each to become writable (also under `mesh: 'none'`, where a same-party joiner reaches the founder over the strand-addr seed). `controlNodeConfig` gained `strandFirstSync`.
- Scenarios edited: `strand-formation-e2e` (3 sites), `convergence-stress`, `websocket-chat`, `rbac-signed-write`, `multi-party-workflows` (`setupStrandBetweenParties`; its closed-strand case now mints party A's row key with `generateStrandMemberKey` because the founder bootstrap decodes it), `push-wake-e2e` (2 solo strands), `strand-unpublish-sibling-convergence` (A now founds instead of only publishing, so B has a peer to sync from), `blind-relay-phone-to-phone-e2e`, `strand-circuit-same-party-e2e`, `strand-addr-seed-convergence`, `strand-late-cadre-join` (the founder's stale "no founder: true" comment was wrong), `strand-membership-closed-strand-e2e` (joiner unwaited; the "wrote nothing before the dial" assertion became "database withheld").
- Specs edited: eight mocked `strand-instance-manager-*` specs answer the Header probe with "held" from their `StrandDatabase` double; `strand-instance-manager.spec.ts`, `cadre-node.spec.ts`, `strand-unpublish.spec.ts` found by default; `strand-founder-bootstrap.spec.ts` joiner tests assert the gate; `publish-strand.spec.ts` joiner-shape tests use `awaitFirstSync: false` and assert `'syncing'`; `cadre-node-issue-membership-invite.spec.ts` and `strand-pre-split-founder.spec.ts` seat pre-split rows by a founder launch under the shared key (the bootstrap's pre-split check looks at rows already seated) and relaunch as a joiner over a memoized store, which holds the Header and so is writable without a peer — `self-owner-node-helpers.ts` gained a `storage` option for that.

## Known gaps, residuals and tripwires (for `## Review findings`)

- **A Header proves one past sync, not a synced table** (documented in `docs/strands.md`). A machine that holds the Header, loses its peer, and writes to a table whose collection it has never fetched still invents a divergent copy. Upstream; the design question the ticket raised — should the founder create every app table's collection eagerly at founding so backfill ships them all — is open and needs the founding cost measured. Not built here.
- **Tripwire, `strand-first-sync-gate.ts` module doc (`NOTE:`):** every launch writes the schema catalog (`optimystic/schema` + 2 hash-named blocks) alone during schema apply, before any peer contact — the same fork shape, safe only because the content is deterministic. Reported upstream.
- **Tripwire, `strand-instance-manager.ts` `isAwaitingFirstSync` (`NOTE:`):** the hibernation idle timer overwrites `'syncing'` with `'idle'` after `idleTimeout`; every runtime decision uses the predicate, not the status, so only the app-visible label changes.
- `strand:writable` fires only after a `'syncing'` start; a Header that lands during the rest of bring-up produces an `'active'` `strand:started` and no `strand:writable` (documented on `publishDatabase`). `whenStrandWritable` does not wake a hibernating strand.
- `cadre-cli`'s health counts (`health.ts`) count `active`/`idle`/`hibernating` only; a `syncing` strand falls in none. Cosmetic; `strands.ts` shows it with the `starting` icon.
- `multi-party-workflows`' closed-strand case still hands party B a row key that is the mock provisioner's `invitePrivateKey`, not a strand member key; a joiner never decodes it, so it passes, but it is not the production shape. Pre-existing.
- The probe is one `Strand.Header` read per 500 ms per gated strand. With zero connections it is a local miss; with a connected peer it is a network read that is also the sync we want. Not measured under many gated strands.
- Same-party joiners inside `joinStrandOn` may already be `'active'` when `addStrand` returns (their strand-addr seed carried the Header); the harness accepts either. Cross-party joiners are always `'syncing'` there.
