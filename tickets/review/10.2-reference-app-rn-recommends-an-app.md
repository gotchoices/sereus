# Phone reference app recommends another app (owner side): review

The owner app's half of "recommend an app and enroll it on first launch". **A** is this app, holding the cadre; **B** the app it recommends. The kit pieces (`AppRecommendationStore`, `storePageLink`, `recommendedByLink`) landed in `phone-kit-app-recommendations`; the design is docs/architecture.md → "Recommending another app". B's side is `reference-app-rn-joins-the-app-that-recommended-it` (still in implement/).

## What was built

- **`src/recommend-app-section.tsx` (new).** Rendered by `AddDeviceSection` in the owner view, below **Copy invitation**, inside the same branch, so it is hidden while a minted invitation is on screen.
  - The list: one button per other Sereus app, **Open ‹B›** when installed and **Get ‹B›** when it has a store page on this platform. If no app qualifies, it says "No other Sereus app to recommend." The buttons are disabled while `minting`.
  - The prompt "Let ‹B› join your cadre?" has the one-hour line, `OwnerSwitch` (on by default), **Allow and get/open ‹B›** and **Cancel**.
  - Allow calls `recommendations.approve(...)` first, then `openRecommendedApp`. A failed save shows an alert and opens nothing. A failed open shows an alert, and the permission stays.
  - **Allowed to join** shows `recommendations.live(partyId)` rows (name, owner/member, `validUntilText(approvedAtMs + RECOMMENDATION_TTL_MS)`), each with **Withdraw** and no confirmation. **The heading is hidden while the list is empty**, which is my choice; the ticket did not say.
  - Both lists are re-read when the section mounts and whenever the `refreshKey` prop or `partyId` changes.
- **`add-device-section.tsx`.**
  - `handleRequest` gains step 5: `answerRecommended(request, answerTo)` runs after the cooldown, not-owner and already-member checks, and only when `answerTo` is set. It takes the permission with `recommendations.take(reply.scheme, node.partyId)`, mints `{ peerId: request.peerId, grantsOwner: rec.grantsOwner }`, answers, sets the notice using `rec.appName`, and bumps `recommendRead`, which makes the section re-read its lists.
  - A `take` that throws is logged and falls through to the prompt.
  - The answer-or-show-for-copying step is factored into `sendInvitation`, which `approveRequest` now uses too.
  - `refresh()` (the Refresh button, Try again, and a node change) also bumps `recommendRead`.
- **`join-link.ts`.**
  - `otherSereusApps()`: `KNOWN_SEREUS_APPS` and `extraSereusApps()`, the first listed for each scheme, own scheme dropped. This is the shared candidate list; `installedOwnerApps` now uses it, and the B-side ticket's `recommended-by.ts` should look schemes up in it.
  - `recommendableApps()`: each candidate with `installed` and the link to open. That link is `recommendedByLink` when the app is installed, otherwise `storePageLink` for `Platform.OS` (Android/iOS only).
  - `openRecommendedApp()`: opens that link; never throws.
  - The module comment now allows logging a recommending link, which names only the two apps.
- **`cadre-phone.ts`.** Adds `recommendations = new AppRecommendationStore(phone.recommendationSlot())`. `isSereusApp` now also validates the optional `androidPackage` and `iosAppStoreId` against the regexes the kit's config plugin uses (copied, since the plugin is CommonJS and exports nothing the app can import).
- **`settings-controls.tsx`.** `OwnerSwitch`, `validUntilText` and the shared styles (`subTitle`, `promptText`, `switchRow`/`switchLabel`, `listRow*`) moved here from `add-device-section.tsx`, so both sections share them without a circular import. The invitation rows now use the renamed `listRow*` styles; there is no visual change.
- **`test-ids.ts`.** Adds `recommendAppBtn(scheme)`, `recommendOwnerSwitch`, `allowRecommendedAppBtn`, `cancelRecommendedAppBtn` and `withdrawRecommendationBtn(scheme)`.
- **docs/reference-app-rn.md.**
  - New `### Recommend an app` under "Adding a Device or App", covering the list, prompt, Allow, Allowed list and the answered-without-a-prompt rule with its order.
  - One bullet in "Opened from another app" that links to it.
  - New storage subsection "Recommended apps (app-private LevelDB)".

## Decisions a reviewer should check

- **Malformed store field in `extra.sereusApps`.** The ticket said "reads that entry as none … as a malformed entry is today". Today a malformed entry makes the *whole* `extra.sereusApps` list read as none (logged). I kept that rule: a malformed store field makes the entry malformed, so the whole extras list is dropped. I did not switch to dropping entries one at a time, because that would also change today's behaviour for a bad `name` or `scheme`. In practice the plugin refuses the same fields at prebuild, so this path needs `extra` and the plugin config to disagree.
- **`mintingRef` check before `take`.** `answerRecommended` returns false (falls through to the prompt) when an invitation is already being made. `mint` returns null silently when busy, so taking first would use up the permission and answer nothing. There is still a gap during the `take` await itself, if the user taps Make invitation in that instant; I judged that too small to be worth handling.
- **The installed check is read when the list is read, not at Allow.** If B is installed or uninstalled between the list read and Allow, the label is stale. Installed since: the store page opens, and it offers Open. Uninstalled since: the open fails and the alert path runs.
- **The "within the next hour" wording is a literal.** It matches the kit's `RECOMMENDATION_TTL_MS` (60 min), and a JSX comment in `RecommendPrompt` notes the tie. If the constant changes, this wording must change with it.

## Known gaps

- **No device run.** Nothing here has run on a phone. `tickets/blocked/rn-device-run-same-phone-join-by-link.md` is the device-run ticket for links between two apps; the B-side ticket is listed as touching it.
- **Open ‹B› lands on an unmatched route until the B-side ticket lands.** `app/+native-intent.tsx` returns the raw path for a `recommended-by` link (left that way by the kit ticket), so expo-router in B probably shows its unmatched-route screen. `reference-app-rn-joins-the-app-that-recommended-it` routes it.
- **In this repo the list only ever shows the second install.** No `SereusApp` entry has a store id, so **Get** never appears, and only the second install (`APP_VARIANT=second`, when installed) shows as **Open**. Documented.
- **The Allowed list is not polled.** A row that lapses stays until the next read (the same as Outstanding invitations). Documented.
- **Build note.** `yarn workspace @serfab/reference-app-rn test` first failed on the stale-build guard: `@serfab/cadre-rn`'s `dist` predated the kit ticket's source edits. I rebuilt it (`yarn workspace @serfab/cadre-rn build`); it is a workspace package in this repo, not a read-only sibling.

## Use cases to check by inspection

- **Owner, B installed.** Tap Open ‹B›, then Allow. The entry is saved, then `‹B scheme›://cadre-recommended-by/‹A scheme›` opens. Allowed to join shows the row.
- **B asks within the hour.** The cooldown, owner and member checks pass, the permission is taken, the invitation is minted with the approved grant, and the answer link opens. The notice uses A's name for B, and the Allowed row disappears.
- **B asks after the hour, or after A switched cadre.** `take` returns null, so the ordinary Allow / Deny prompt shows.
- **B already in the cadre.** It gets `already-member` and the entry stays until it expires.
- **Within 30 s of a Deny.** The request is denied, the entry stays, and the next request after the cooldown is answered without a prompt.
- **A pasted request with B's scheme in it.** `answerTo` is null (`viaLink` false), so the permission is never consulted.
- **The mint fails** (for example, no relay address). The usual mint alert shows, the entry is gone, and B is not answered (its waiting line and Cancel cover that).
- **The slot is unreadable.** `take` throws, it is logged, and the prompt shows. Allow shows the "Could not allow" alert. The Allowed list shows its error line.
