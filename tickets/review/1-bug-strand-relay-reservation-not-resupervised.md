# Strand nodes now re-acquire a lost relay slot on their own

## What changed

A strand node (one libp2p node per shared workspace) used to inherit libp2p's CONFIGURED circuit listener shape, `<relay>/p2p-circuit`, which reserves once from inside `libp2p.start()` and never again. It lost its `/p2p-circuit` address on a relay restart, on either side hanging up the relay connection, and, with no network event at all, on libp2p's own reservation refresh (about 1 h 55 min after reserving against the production relay's default 2 h TTL). Strand nodes now take the same route the control node takes: a bare `/p2p-circuit` SEARCH listener plus an explicit reservation supervisor, one listener and one supervisor PER configured relay.

- `relay-addrs.ts`: the `'configured'` route and `RelayListenRoute` are gone. `resolveListenAddrs(network)` is the control node's resolution only (one bare search entry for the whole relay list, hand-written `<relay>/p2p-circuit` listen entries rejected). `relayCircuitAddrs` stays as the validated form of `relayAddrs` (nothing listens on it). `DEFAULT_DIRECT_LISTEN_ADDR` and `isConfiguredCircuitListenAddr` are exported for the strand derivation.
- `strand-network-config.ts`: `strandNodeAddrs` emits one bare `/p2p-circuit` per relay (appended after the string dedupe, since the entries are identical and each must be its own listener) and returns the relay DIAL addrs in a new `StrandNodeAddrs.relayAddrs` field, deduplicated by relay peer id. A hand-written `<relay>/p2p-circuit` listen entry counts as a relay; a hand-written bare `/p2p-circuit` passes through when no relay is named (the browser shape) and is absorbed when one is.
- `strand-instance-manager.ts`: `buildStrandRuntime` destructures `relayAddrs` off the node options, starts one `superviseRelayReservation(node, [relayAddr], { beforeRedrive })` per relay right after `createLibp2pNode` (they overlap the database bring-up), and awaits every first attempt before the strand goes `active`. Fail-soft: a first attempt that lands nothing is logged and the strand still comes up. `releaseRuntime` stops the supervisors FIRST (before backfill, database close and `libp2pNode.stop()`), which covers quiesce, stop, the failed-launch rollback and removal after revocation. `StartStrandConfig` gains `announceDelegateToRelay(strandId, relayAddr, delegatePeerId)`, retained with the launch config so a hibernation wake's rebuilt supervisors carry it.
- `relay-reservation.ts`: "held" is judged per relay through the new `circuitMultiaddrsVia(node, addrs)` (a circuit addr whose `/p2p/<relay>/p2p-circuit` names one of the supervisor's relays; falls back to any circuit addr when an addr names no peer id). Applied in the loop's `reservationHeld` and in the drive's `waitForCircuitReservation`. New `beforeRedrive` option, awaited before every drive after the first; a throwing or rejecting hook is logged and the drive still runs; a `stop()` that lands while the hook runs skips the drive.
- `cadre-node.ts`: `warnIfAnnounceAddrsDiscardRelay` reads `relayAddrs` and `listenAddrs` directly. `buildControlNodeOptions` calls the single-argument `resolveListenAddrs`. `launchStrand` passes `announceDelegateToRelay`, a new private method that announces one strand's delegate peer id to one relay unthrottled (`collectStrandAddrs` against that relay, then `recordDelegateAnnounces` so the periodic pass does not immediately repeat it). Resume reuses the retained config, so nothing extra is passed there.

## Measured finding the ticket did not anticipate

libp2p 3.1.3's `connection.newStream` records every protocol OUR OWN outbound stream negotiated into the peer store, so the explicit reservation request itself writes the relay-hop protocol id against the relay, identify prefix or not. From then on libp2p's own relay discovery CAN refill a freed search slot when the relay answers at that moment: a client-side `hangUp` while the relay stayed up was re-reserved by discovery within about 25 ms in the debug capture (`tickets/.logs/1-bug-strand-relay-reservation-not-resupervised.hangup-debug.log`, until pruned). A relay that is down when the slot frees fails that one discovery attempt, which poisons the store's `relayFilter`, and nothing in libp2p tries again, so a relay restart still needs the supervisor (which un-poisons the filter before every attempt). Recorded in the `relay-reservation.ts` module doc. Consequence for specs: namespaced identify alone does NOT isolate the supervisor after the first reservation; the hangup specs call `client.peerStore.patch(relay, { protocols: [] })` after the first attempt and gate recovery on the supervisor having re-driven (its `beforeRedrive` hook ran), not merely on the addr being present.

## Tests worth reading first

`packages/cadre-core/test/relay-reservation.spec.ts`, describe `superviseRelayReservation — the strand-node shapes` (all over a cadre-shaped client with namespaced identify):

- client-side `hangUp(relay)` and relay-side `hangUp(client)`: loss observed on libp2p's `connection:close` event (polling the addr for a 0 can miss a loss repaired within one poll), recovery gated on the supervisor's re-drive.
- reservation refresh: relay `reservationTtl: 40_000`, so the client refreshes at its 30 s floor; the circuit addr is still present at 45 s and the relay still holds exactly one reservation.
- two relays, two listeners, two supervisors: stopping relay 1 re-drives relay 1 only; relay 2's addr is never withdrawn and its supervisor never re-drives.
- the per-relay held check in isolation: a supervisor over an unreachable relay is not satisfied by the other relay's addr on the same node.
- `beforeRedrive`: not run before the first attempt, run before every re-drive, run BEFORE the drive (the hook brings the relay up and the reservation lands promptly after), and a throwing or rejecting hook does not stop the drive.

`packages/cadre-core/test/strand-instance-manager-relay.spec.ts` (supervisor double): one supervisor per relay with default timings, the callback wired per relay and per delegate peer id, `active` reached when the first attempt fails, stop order on quiesce (`supervisor.stop` x N, then `database.close`, then `node.stop`), fresh supervisors on resume and stopped on stop, supervisors stopped on a failed launch.

Updated derivation specs: `strand-network-config.spec.ts` (new `relays` describe, including the non-deduplicated per-relay entries and the folded hand-written entry), `relay-addrs.spec.ts` (search-only `resolveListenAddrs`), `strand-instance-manager-network-addrs.spec.ts` (bare entry per relay; `relayAddrs` never reaches `createLibp2pNode`), `strand-listen-port-collision.spec.ts` (no route argument).

## Known gaps and things to probe

- **Fail-soft launch is pinned only over a supervisor double**, not over a real unreachable relay with a real strand database. The manager-level claim "a launch whose relay is unreachable still reaches active" is tested by faking a failed first attempt; a real-node variant would cost a 10 s drive per test.
- **"No drive after `releaseRuntime`"** rests on `relay-reservation.spec.ts`'s existing "stops re-driving once stopped" plus the manager spec's stop-ordering assertions; no manager-level test watches a real supervisor after teardown.
- **A drive in flight at teardown is not cancelled** (the supervisor's `stop()` cannot abort `driveRelayReservation`). With one supervisor per relay per strand this exposure widened; a note was appended to `tickets/backlog/bug-relay-drive-not-cancellable.md`. No `AbortSignal` was added here.
- **The delegate re-announce against a party-run relay is not exercised end to end.** Both scenarios use the dedicated (ungated) relay, where the announce folds to `[]`. The hook wiring is pinned in the manager spec and `announceDelegateToRelay` is straightforward, but the "relay restart drops the grant, re-drive re-announces first, reservation admitted" sequence against a `CadreNode` relay has no scenario. Worth a reviewer's eye on `CadreNode.announceDelegateToRelay` and on whether a relay that rejects the reservation for a lapsed grant leaves anything poisoned.
- **Browser and phone strand nodes whose relay comes from `CadreNode.reserveRelays()` rather than config still have no strand supervisor**, and no strand-side reservation at all beyond libp2p's own discovery; `reference-app-web` ships `listenAddrs: ['/p2p-circuit', '/webrtc']` with no `relayAddrs`. Pre-existing and out of this ticket's scope (supervisors come from the network config, per the ticket), but it is the next gap on this path.
- **Two identical bare listen entries through `@optimystic/db-p2p`** are verified by code reading (`libp2p-node-base.ts` passes `listenAddrs` to libp2p verbatim; libp2p's transport manager creates one listener per addr) and by the two-relay unit spec over plain `createLibp2p`; no spec counts circuit listeners on a db-p2p-built strand node. The same-party scenario exercises one relay only.
- **The scenario's reconnect assertion** (B's strand node reaches A's again through the restarted relay) passed on one run; it is new and unmeasured for flakiness.
- The `warnIfAnnounceAddrsDiscardRelay` rewrite no longer validates `relayAddrs` as a side effect; `buildControlNodeOptions` does, a few lines later inside the same guarded region. `cadre-node-announce-addrs-warning.spec.ts` passes unchanged.

## Tripwires recorded

- `strand-network-config.ts`, at the per-relay listen entries: each bare entry makes libp2p start relay discovery whenever its slot is empty; measured as one peer-store scan plus an immediately failing random walk per loss on a node with no peer router. If strand nodes ever get a peer router, cap or disable discovery.
- `relay-reservation.ts` module doc: discovery can refill a freed slot after the first explicit reservation (see the measured finding above); the supervisor remains the guarantee for a relay that is down when the slot frees.
