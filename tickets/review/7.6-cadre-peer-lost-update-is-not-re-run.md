# A `CadrePeer` row's two writers refuse each other, and the loser is now re-run

Implements the fix stage's design. The superseded backlog ticket `bug-owner-write-racing-a-machines-own-publish-fails` is deleted.

## What changed

### The policy

`control-write-retry.ts` ships a third policy, `LOST_UPDATE_RETRY_POLICY`: the default classifier plus `ConcurrentModificationError` claimed by type (`instanceof`, imported from the plugin's root entry, as `PartialCommitError` is), over the default attempts, backoff and 10 s budget. `matchesRetriableFailure` takes an optional link predicate, run beside the final-torn-write claim and after both vetoes, so a lost update carried by `PartialCommitError`, `CoordinatorPartialCommitError`, `SyncRetryExhaustedError` or a non-final `TornActionError` stays declined. The default list is untouched; the policy's `NOTE:` states the opt-in rule (read, decision and signature all inside the locked body) and names the sites. `mutateCadrePeer` takes an optional policy it passes to `lockedWithRetry`.

### Self-publish re-reads and re-signs inside the body

`ControlDatabase.updateSelfPeerRecord(peerId, sign)` now runs under the policy with the label it had. Inside the body it reads the row with the read retry off (`queryPeerRecord` gained a `retry` flag, threaded through a new `findCadrePeerRow` into the two view reads), returns `null` without writing when the row is absent or its stamp is retired, otherwise calls the signer over the row just read and runs the update. It returns the record written. `CadreNode.publishSelfRecord`'s update branch is one call with `signSelfRecord` as the signer; the old `current` re-read and its `!current` branch folded into the `null` return, and `noteSelfPeerWritten` records the returned record. The earlier `NOTE:` about a removal racing the publish and still reporting `refreshed` is gone: the body reads under the lock, and a remote removal landing mid-commit is a lost update that re-runs and reads as absent.

### Owner re-touch decides inside the body

`reauthorizeCadrePeer(peerId, mode, ownerKey, sign)` has two modes and reports `'retouched' | 'absent' | 'self-published'`. `'rebroadcast'` (the write-while-alone drain) bumps `UpdatedAt` to `max(now, current + 1)` from the row read inside the body and writes only while `Sig` is null. `'revouch'` (`removeOwner`) writes regardless and leaves `UpdatedAt` out of the `set` list. The row read, the decision (`retouchTarget`, one function for both the pre-check and the in-body re-check) and the signature all run inside `mutateCadrePeer` under the policy. A cheap pre-check outside the lock keeps the absent and self-published cases from taking the lock or notifying, which is what keeps the hub spec's "does not notify when the removal target is already absent" true; the in-body re-check covers the race and may notify spuriously there. `SeedBootstrapService.reauthorizePeer(peerId, mode, sign?)` passes the mode through and logs each outcome. The drain (`reissuePendingPeerWrites`) no longer pre-reads the record; it calls the re-touch and clears the entry on every outcome. The reconstruct sweep skips a row it already holds as self-published (from the `CadrePeerRow` it iterates, no extra read) and counts only `'retouched'`. `revouchDependents` no longer needs the plan's rows, so `planOwnerKeyRemovalWith` returns the plan alone.

### Removal opts in

`deleteCadrePeer` and `removeMachine` pass the policy through `mutateCadrePeer`. Their bodies already read the stamp and sign inside; the invitation keys come from the caller's plan, which a self-publish does not touch.

### Docs and tests

`docs/architecture.md` → "Control-write retry": a paragraph under "What is retried" names the lost-update class, the three opt-in sites and the rule, and the measured ceiling; "A genuine rejection" says why a lost update is re-decided rather than re-presented; the schema-init subsection no longer calls itself the one wider policy. The `withWriteLock` contract names the opted-in bodies as the exception to "mint outside, re-present"; `lockedWithRetry`'s doc names both policies; `scheduleSelfRegistration`'s catch comment says the publish is now re-run. `machine-removal.integration.ts` no longer waits for B's `registerSelf` before the removal. The degraded-cohort scenario's transient-reset case supplies a signer and asserts the read-back against the record the body returned (`timedSettle` now also returns the operation's value).

## Tests added or changed

- `control-write-retry.spec.ts`, new `isRetriableLostUpdateFailure` describe: a bare `ConcurrentModificationError` and one wrapped in a `QuereusError` are retried; the same error as the `cause` of `PartialCommitError` and of `CoordinatorPartialCommitError` is not; the commit-phase text veto still applies; the lost-update text on a plain `Error` is not claimed (by type, not text); the default and schema-init classifiers decline it; the policy agrees with the default on every other message. The typed possibly-stored suite now runs over all three classifiers. In the `retryControlWrite` describe, one pair: the policy re-runs the body after a bare lost update, the default surfaces it from attempt 1.
- `control-write-lock.spec.ts`, "re-reads and re-signs the own row when a lost update re-runs the self-publish": the first attempt's signer raises the refusal, a rival `updateSelfPeerRecord` commits in the injected backoff sleep (lock released) stamped a minute ahead, and the re-run's signer sees the rival's stamp and commits past it. A record signed over the first read would fail the schema's monotonic rule, so this pins the in-body re-read, not only the re-run.
- `control-membership-hub.spec.ts`, "re-broadcasts only a row the machine has not published, bumping UpdatedAt from the row it reads": the re-broadcast mode's decision at the database layer, which used to be the drain's pre-check and is now untested anywhere else.

- `peer-record-resolution.spec.ts`, "skips rather than self-updating a row that was removed mid-publish": restated. The old staging called `removePeer` from inside the hooked read, which now runs inside the write lock and deadlocked. The removal now lands in the injected backoff sleep after the body's read raises the refusal, and the re-run finds no row (three reads counted, outcome `skipped`, no phantom row). The read hook forwards the `retry` flag.
- `cadre-node-control-replication.spec.ts`: the fake `reauthorizePeer` decides over its fake records as the real one does and the drain cases assert on the mode and the cleared entry; the "strictly increases past the stored stamp" assertion moved to the hub spec above, where the bump now lives.
- Signature follow-through only: `cadre-node-remove-machine.spec.ts`, `control-revocation-replay.spec.ts`, `seed-bootstrap.spec.ts`, the other `updateSelfPeerRecord` callers.

No unit-level reproduction of the real race was forced: it needs a rival write between a statement's read and its commit inside the engine, which one node's serialized writers cannot stage. The staged refusals in the two specs above stand in for it; the real reproduction is the degraded-cohort `afterEach` check.

## Known gaps, for the reviewer

- **The confirm target of zero abandonments was not met: 1 of 18 boots still lost a write.** Run 4's `[abandoned-write C] [self-record-update] budget after 1/3 attempt(s) in 14699ms: concurrent modification`. The attempt ran 14.7 s, past the 10 s budget, so the policy never got to retry it. The ticket's estimate was one retry at about 7.5 s (one per-peer read deadline); in this harness C cannot reach B, so any phase of C's attempt that waits on B pays the 7 s deadline, and two such waits exceed the budget. This is the budget cut the ticket accepted, hit by a longer attempt than it anticipated. It did not recur in 8 debug-logged boots, so I could not see which phases the 14.7 s were. Under the previous code this same loss was certain (declined on attempt 1), so the change is strictly an improvement, and the lost publish is the reconcile pass's or the heartbeat's to redo as before. The measured ceiling is stated on `LOST_UPDATE_RETRY_POLICY` and in the architecture doc. The `tickets/.pre-existing-known.md` entry for this slug still says in-flight; whoever closes this should re-word it to the residual rate rather than delete it.
- **One possible contributor to that 14.7 s is new.** The self-publish body now reads the `Revocation` and `CadrePeer` views inside the funnel, so a cold view load that waits out a read deadline counts against the budget, where before the same read (`publishSelfRecord`'s `existing` read) ran outside it. The outside read still happens first and warms the views, so the in-body read should be a cache hit unless a table change between the two invalidated it, which is exactly the racing case. Worth a look if the residual rate matters: a point read of the row instead of the view scan would not change the deadline math, but skipping the `Revocation` read inside the body (reading only the stamp and `Sig` raw, and leaving the revoked case to the outside read) would halve the worst case.
- **The removal's opt-in was not exercised end to end.** None of the three machine-removal runs raced B's publish (no `machine-remove` retry lines), so the removal path's re-run is pinned only by the retry spec's policy pair and by its body already minting inside, not by an observed race.
- **Spurious notify on the in-body no-write outcomes** of `reauthorizeCadrePeer`: a race that turns the body's re-check into `'absent'` or `'self-published'` still notifies the membership hub once (it only re-reads the member set). Documented on the method; the pre-check outside the lock keeps the common case quiet.
- `control-trio.ts`'s explanation near its step 5 still reads correctly (the branch it names keeps its name), so it was not edited.
