# OAuth 2 authorization code with PKCE, and the provider descriptor: implemented

Second ticket of the `provider-client-and-sign-up` chain. The client half is `cadre-core-provider-client-and-rent-node`, which implements against `docs/architecture.md` → "Provider descriptor and sign-in" (new subsection) and the wire shapes below.

## What was built

**Configuration.** `auth.oauth` (`clients[]` with `clientId`, `redirectUris`, `scopes`; `accessTokenTtlSec`, `refreshTokenTtlSec`, `devConsentPage`) and a `provider` block (`id`, `name`, `publicUrl`, optional `termsUrl`, `regions`, `icon`). Shape rules live in `config/schema.ts`: `auth.oauth` only with `mode: oauth`; at least one client, unique ids, each with at least one redirect URI and one scope; a redirect URI is an absolute URL with no fragment and `http` only at a loopback host; a scope is a `Scope` value or `<resource>:*` (`isKnownScope` in `permissions.ts`, `*` excluded); `provider.publicUrl` is `https` or loopback `http` with no query or fragment. The one acknowledgement rule, `devConsentPage: true` needs `allowInsecureNoAuth: true`, lives in `validateAuthConfig` (post-merge, so it also covers programmatic overrides and `registerAuth`'s defense in depth), beside the mode-`none` rule it mirrors. Environment forms: `PROVIDER_OAUTH_DEV_CONSENT_PAGE`, `PROVIDER_ID`, `PROVIDER_NAME`, `PROVIDER_PUBLIC_URL`. `check` prints one line after the JSON when there is no `provider` block.

**Endpoints**, all under `server.basePath` and skipped by the auth preHandler by exact path (the skip list is now a set: `/status`, `/health`, `/descriptor`, `/oauth/authorize`, `/oauth/token`). `GET /oauth/authorize` validates the client and the redirect URI first (exact string match; a failure is a 400 HTML page with no redirect), then redirects every other fault to the registered URI with `error`, `error_description` and `state`. Then the customer is resolved by `AuthHooks.authorizeCustomer({ clientId, scopes, headers, query })` → `{ customerId, planId? } | { redirect } | { deny }`, or by the dev consent page (`GET` renders the form, `POST /oauth/authorize` takes it back). The code is 32 random bytes base64url, stored as its SHA-256 hex with the client, customer, scopes, challenge, redirect URI and a ten-minute expiry; a customer with no billing record gets one on the first code. `POST /oauth/token` takes form-encoded (`@fastify/formbody`, newly added) or JSON bodies: `authorization_code` takes-and-deletes the code and checks client, redirect URI and the S256 verifier (constant-time); `refresh_token` takes-and-deletes the refresh token, best-effort deletes the old access key, and mints a new pair. Tokens are `ApiKey` records named `oauth:<clientId>` with the scopes as permissions; refresh tokens are a new `RefreshToken` record. Responses carry `Cache-Control: no-store`. `GET /descriptor` builds the descriptor from the config at request time; 404 `NOT_CONFIGURED` without a `provider` block.

**Bearer validation in `oauth` mode.** A bearer is first looked up as a stored key (expired → deleted, treated as absent), then handed to `validateJwt` when present. The lookup helper is shared with `api-key` mode, so that mode now also deletes an expired stored key instead of only logging it (a small behaviour change; nothing tested the old behaviour).

**Store.** `saveAuthorizationCode`, `takeAuthorizationCode`, `saveRefreshToken`, `takeRefreshToken` on `ProviderStore`, in `MemoryStore` and `FileStore` (`authorization-codes.json`, `refresh-tokens.json`). No implementer outside the package.

**Type fix on the way.** `DeepPartial` did not recurse into an optional object property (an indexed access type does not distribute over `| undefined`), so `ProviderConfigFile.provider` came out with required fields; it now strips `undefined` before the object test. The push tables still compile against it; `loader.ts`'s recursive `deepMerge` cast changed to match.

## Decisions a reviewer should weigh

- **`response_type` other than `code` redirects with `unsupported_response_type`** (RFC 6749 §4.1.2.1's own code) where the ticket said `invalid_request`. Likewise an absent or empty `scope` is `invalid_scope` rather than a default allowance, which the RFC permits either way; the client ticket always sends scopes.
- **`invalid_client` is a 400**, as the ticket specified, though RFC 6749 §5.2 allows 401 for it.
- **The descriptor omits `oauth` when `auth.oauth` is unset** (a provider with an external identity provider). The client ticket's `parseProviderDescriptor` requires `oauth.authorizeUrl` and `tokenUrl`, so such a provider must publish a descriptor of its own; the README and the architecture doc say so. Alternative rejected: 404 without `auth.oauth` too, which would hide a provider that is otherwise configured.
- **`lastUsedAt` is not updated for OAuth tokens.** `api-key` mode writes the record on every request (a whole-file rewrite with the file store); tokens are short-lived and nothing reads the field, so the write was left out.
- **Malformed JSON bodies and a throwing `authorizeCustomer` hook** get Fastify's default 400/500 shapes, not the RFC's `{ error, error_description }`; a client treats either as a failed request.
- **Dependency added:** `@fastify/formbody@^9.0.1` (`yarn.lock` changed).

## Tripwires recorded in code

- `store.ts` `ProviderStore`: expired codes and refresh tokens are removed only when presented; sweep on the reaper's tick if a long-running provider accumulates enough to matter.
- `oauth.ts` `exchangeCode`: a replayed code is refused but the tokens its first exchange minted are not revoked (RFC 6819 recommends revocation); add it if a leaked code is ever a worry.

## Known gaps

- `FileStore`'s two new collections (`readExpiring`, the two `take` methods) have no test: store glue, same pattern as the existing collections. A reviewer who wants one round-trip test could extend whatever covers `FileStore` today, if anything does (nothing found under `__tests__`).
- The consent page's HTML is checked only for the escaped client id on the 400 page and the hidden `state` field on the form; the rest is by inspection (every interpolation goes through `escapeHtml`).
- Not exercised: the `{ redirect }` round trip where the operator's site brings the browser back to the same authorize URL (that is the site's job), and `FileStore` persistence of a code across a provider restart.
- `registerAuth` does not refuse `mode: oauth` with neither `auth.oauth` nor `validateJwt` (every bearer is then 401, which is closed, not open); pre-existing and left alone.

## Tests added, each beside what it verifies

`packages/cadre-provider/src/server/__tests__/oauth.test.ts` (Fastify `inject`, `MemoryStore`, `MockOrchestrator`, a hook that signs every browser in as `cust-1`):

- Round trip: authorize with the RFC 7636 appendix B challenge → 302 with `code` and `state` → form-encoded exchange → 200 tokens with `no-store`, `expires_in: 3600`, the requested scope; the bearer passes `GET /containers`, gets 403 `INSUFFICIENT_SCOPE` on `DELETE`, and `GET /billing/status` shows the record created at sign-in with the hook's plan.
- A wrong verifier is `invalid_grant` and burns the code (the right verifier afterwards is `invalid_grant` too).
- A code replayed after a successful exchange is `invalid_grant`.
- Unregistered redirect URIs (trailing slash, upper-case scheme, extra query, another origin) and an unknown client each get a 400 HTML page with no `Location`; a `<script>` client id comes back escaped.
- Faults after the client is known (`plain`, a short challenge, no state, `response_type=token`, an unknown scope, a known scope outside the allowance, no scope) redirect with the expected `error` and the state, and never a code.
- Refresh (JSON body) rotates: the new pair works, the old refresh token is `invalid_grant`, the old access token is 401.
- The hook's `{ redirect }` is a 302 to that URL; `{ deny }` redirects with `access_denied`, the reason and the state.
- The dev consent page renders the form with the hidden state, and its `POST` with `decision=approve` issues a code whose tokens belong to the typed customer on the chosen plan.
- `auth.oauth` with neither hook nor dev page refuses to construct the server.
- `GET /descriptor` equals the documented document (URLs from `publicUrl` + `basePath`, scopes the union of the clients'); 404 `NOT_CONFIGURED` without a `provider` block.

`packages/cadre-provider/src/config/__tests__/config-validation.test.ts`:

- `auth.oauth` under `mode: api-key` is refused, naming the rule.
- `devConsentPage: true` without the acknowledgement throws; `PROVIDER_ALLOW_INSECURE_NO_AUTH=true` satisfies it.
- Redirect URIs: custom scheme, loopback `http`, `https` accepted; `http` elsewhere, a fragment, a relative text refused with the reason.
- A `*` scope and a repeated `clientId` are refused (two configs, since a failed item stops the list-level rule from running).
- `provider.publicUrl`: `http://127.0.0.1:3000` passes, `http://nodes.acme.example` fails naming the variable.
