# Machine invitations grant no ownership: review handoff

The implement run touched 89 files across cadre-core, the kits, the three reference apps, the CLI, the host and provider test helpers, the integration scenarios and the docs. The core (schema, cadre-core, edge node, cadre-core tests, architecture doc) was done by hand; the kit, phone app, browser and NativeScript apps, CLI and scenario slices were done by sub-agents working to the API summary below and are reviewed here only by their diffs and test results. Treat every slice as a starting point.

## What changed

**Schema, version 3** (`schemas/control.qsql` and the identical copy in `control-schema.ts`; drift spec re-pinned to `hash:ATfhaUau`). `CadreInvite.GrantsOwner` and its digest field are gone; `CadreInviteUsage.OwnerStampId` and `OwnerExists` are gone; `PeerExists` keeps its `PublicKey = PeerKey` clause with a shorter comment. `OwnerKey.Authorized` has three branches now (founding, owner-signed add, grant consent). The table comments were rewritten, and the accepted-tradeoff `NOTE:` on `CadreInviteUsage.Authorized` speaks of machine invitations only and points at `OwnerGrantUsage.Authorized` for the grant half. A version-2 store refuses to start (`ControlStoreIncompatibleError`); no migration.

**cadre-core.** `grantsOwner` left `CreateCadreInvitationOptions` (every option is now optional, so `createCadreInvitation()` is legal), `CadreInviteSignedFields` / `CadreInviteRow` / `CadreInviteFields`, `RedeemCadreInvitationResult` and the protocol's row shape check; `ownerStampId` left `CadreInviteUsageRow` and `CadreInviteRedemptionResult`. `redeemCadreInvite` writes the peer row and the usage row only, and `readSeatedAdmission` is folded into it. `verifyInvitationOwnerAdmission` is gone and `verifyAdmissionChain` is folded into `verifyInvitationAdmission`; `deriveOwnerAnchor` takes `grantChain` alone, and `syncOwnerAnchor` no longer takes the invitation chain. `OWNER_INVITATION_DEFAULT_TTL_MS` is gone; every machine invitation defaults to 24 hours. `CadreNode.wireOwnKeyIfOwner()` with no argument only asks whether the wired signer is still a live owner; `identityOwnerSigner` is gone. `isInvitationAdmitted` is renamed `isConsentSeated`, since it judges grant-seated owner rows too.

**Edge node.** New `edge-node/join-credential.ts`: `JoinCredential = CadreInvitation | OwnerGrantBundle` and `isOwnerGrant`, both exported from the edge-node entry. `EdgeNode.joinCadre(credential, options?)`: a machine invitation admits the app as a machine; an owner grant goes through `CadreNode.joinWithOwnerGrant` on a switched node and `redeemOwnerGrant` on a node already running in the grant's party, seating the owner slot's key, which `JoinRuntime.ownerSlotSigner()` loads or creates. `StrandsNeedOwnerJoinError` is thrown only for a machine invitation, and its message says to join with an owner grant made under the owner app's Owner keys. The `admitted` progress event carries `asOwner` (was `grantsOwner`). `wireJoinedOwner` in `config.ts` tries only the slot's key and never replaces a wired signer.

**Kits and apps.** The kit's `AppRecommendation` lost `grantsOwner` (an old stored entry still parses). The phone and browser apps lost both "Also an owner" switches, the 15-minute bearer warning and the owner/member word in their invitation lists; their join-flow lines follow `asOwner`; their `StrandsNeedOwnerJoinError` text points at an owner grant. The NativeScript app reports standing from the edge node's `status.owner` through a new `CadreViewModel.owner` field. `cadre enroll invite --owner` is gone (commander refuses it as an unknown option), the admin channel refuses a body carrying `grantsOwner` as `bad_request`, and `cadre start --invitation` no longer has an owner branch.

**Scenarios.** Eleven scenarios updated. `strand-moves-between-cadres` gives N one owner key for life (it founds B with it and joins A with O's grant through `joinWithOwnerGrant`, the same key); `app-joins-cadre-by-invitation` admits B as a member by a targeted machine invitation, then makes it an owner by a local `redeemOwnerGrant`, and C joins as machine and owner with B's grant; `machine-removal` and `cadre-invite-any-member` seat their owners through grants; `cadre-invite-row-unreplicated` drops its owner half (its subject is the row seated from the bundle). The harness lost `ownerKeySeatedByInvitation`; `makeOwnOwner` takes an optional key.

**Docs.** `docs/architecture.md`: the control table rows for `OwnerKey`, `CadreInvite` and `CadreInviteUsage`; Owner Keys (the "Invitation-granted owners" paragraph is deleted, the `owner-key-flows.ts` paragraph no longer mentions the identity key); the enrollment-flow diagram, "Why the invitation is a keypair", the lifetime defaults and the wiring paragraph; "Handing an invitation from app to app" (no owner choice, the blocked decision named once); the recommendation steps; "An app joins an existing cadre" (the owner slot bullet now explains why the grant seats the slot's key and what a rollback leaves, the `'joined'` origin, steps 1 to 3); "Removing a machine" (owner grants are left alone, none names a machine); "Removing an owner key"; the anchor-derivation paragraph and its coverage line; the code sample. Also `docs/testing.md` (the harness owner-key bullet), `docs/reference-app-rn.md`, and the kit, CLI, browser-app and cadre-core READMEs.

## Judgement calls to weigh

- **`JoinCadreResult.asOwner` was added** beside the progress event's `asOwner`. The ticket only asked for the progress field. It is cheap and mirrors the event; drop it if a single source (`status.owner`) is preferred. The NativeScript app reads `status.owner`, as the ticket asked.
- **The grant join seats the slot's key, created when empty**, in `redeemOnJoinedNode` (`edge-join.ts`). The reasons are in that function's doc, and the rollback consequence (the key stays an owner of the target party while the app is back in the left party) is a `NOTE:` there. No test, per the ticket.
- **`wireJoinedOwner` (`edge-node/config.ts`) asks about an already-wired signer and never replaces it**, which is what the previous body did in effect once the identity default was gone; the body was restructured to say so.
- **`PeerExists` keeps `P.PublicKey = new.PeerKey`** although the completion case it guarded is gone: a usage row is still bound to the admitted machine's own key, which costs nothing.
- **The CLI's refusal of `grantsOwner`** triggers on the field being present at all, `false` included, with a message naming owner grants. The CLI README does not name `cli-owner-grants`; the agent read the docs rule as "describe the system as it is".
- **`control-cadre-invite.spec.ts`** replaces three owner-consent cases with one that pins the removed branch (an `OwnerKey` row by consent naming a `CadreInviteUsage` row is refused `Authorized`), and the first redemption case now also asserts no owner row is seated. `cadre-node-remove-machine.spec.ts` seats the machine user's owner key through the grant writers (`insertOwnerGrant` + `redeemOwnerGrant` on the database) instead of through the invitation.

## Known gaps

- **The phone app's device e2e flows 1 to 3 cannot pass until `reference-app-rn-owner-grants`**: `maestro/_setup.yaml` creates a strand right after joining, which a member cannot do, and the app's join field cannot take an owner grant yet. The fixture (`test-fixture/start.mjs`) mints a machine invitation and says so in a comment. Not run here (device flows).
- **Not run:** the browser app's Playwright distributed spec `e2e/distributed/join-cadre.spec.ts` (needs browsers and the distributed fixture; its fixture and assertions were updated and typecheck), and the phone app's maestro flows. Everything else that exists for the touched packages was run (below).
- **The owner-grant join on the edge node itself is exercised only against fakes** (cadre-rn `node.spec.ts`, where an expired grant is refused by the holder's clock before any dial). The real-network proof of the join is `CadreNode.joinWithOwnerGrant` in `strand-moves-between-cadres` and `app-joins-cadre-by-invitation`; nothing runs `EdgeNode.joinCadre` with a grant against a live member. The reviewer may want to judge whether `cadre-rn`'s `node.spec.ts` should gain such a case, or whether the layering (edge node → `joinWithOwnerGrant`, pinned on the network) is enough.
- **`cadre-invite-row-unreplicated`** no longer covers a grant row seated from the bundle at a member that never held it; the owner-grant scenarios cover the grant seat, and the member-side `seatOwnerGrant` is shared with `seatCadreInvite` (`seatIssuedRow`).
- **Line counts** (`wc -l`): `cadre-node.ts` 10,610 (was 10,635), `control-database.ts` 5,085 (was 5,107); both tracked by `backlog/debt-cadre-node-single-file-size`.

## Edge cases from the ticket, by inspection

- **Empty slot, grant join fails:** `ownerSlotSigner()` creates the key before `joinWithOwnerGrant`; a rollback leaves it in the slot, an owner of nothing. Said in `redeemOnJoinedNode`'s doc. The cadre-rn test "discards the strands it recorded for the move when the join fails" asserts the slot key is unchanged after a failed grant join on a founded party (whose slot already holds a key).
- **Slot key already an owner of the target party:** `joinWithOwnerGrant` answers `alreadyOwner`, no use spent; `asOwner` is true and the key is wired. Inspection.
- **Grant redeemed, self-invitation refused:** the `NOTE:` in `redeemOnJoinedNode`.
- **Restart of a joined app:** `'joined'` origin wires the slot key only (`wireJoinedOwnerKey`); a key that became an owner later is picked up at the next start. Inspection, and the cadre-rn test "wires the owner slot's key on a party it joined".
- **`removeMachine`:** withdraws the invitations the machine could redeem; owner grants name no machine, so none is touched. Stated in "Removing a machine".
- **`adoptStrandBundle`'s `wireOwnKeyIfOwner()`** finds only the wired signer; every edge-node adoption path (`settleJoinMove`, `buildAndStart`, `finishStrandMove`) wires or re-checks the slot key first. `strand-moves-between-cadres` runs the adoption with the key the join wired.
