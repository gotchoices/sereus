# Review: reap container records the provider abandoned mid-flight

Implements `tickets/implement/36.11-provider-reap-stuck-container-records.md`
(now deleted). All five build sections landed, plus the docs update.

## What changed

**`orchestrator.ts`** — `RecoverableOrchestrator` gained a second optional
member, `resolveDockerId?(containerId): Promise<string | undefined>`: map a
provider container id back to the orchestrator's current handle. Async (unlike
cadre-host's synchronous version) because the container runtime, not an
in-memory map, is the source of truth. Deliberately NOT on the base
`Orchestrator` — cadre-host's `HostProcessOrchestrator implements Orchestrator`
and carries a sync same-named member. Implemented on `MockOrchestrator` (scans
stored create requests), `DockerOrchestrator`, and the integration harness's
`ProviderProcessOrchestrator` (scans `handles`).

**`docker-orchestrator.ts`** — `resolveDockerId` filters
`listContainers({ all: true, filters: { label: ['sereus.container-id=<id>'] } })`
and returns the first match's `Id`. Errors are NOT swallowed. `createContainer`'s
`Labels` block now writes that label via the existing `CONTAINER_ID_LABEL`
constant instead of a duplicated string literal, since the label is now a lookup
key rather than only metadata.

**`container-service.ts`** — the bulk:

- Exported `CONTAINER_PROVISIONING_TTL_MS` (15 min), `CONTAINER_ENROLLMENT_TTL_MS`
  (5 min), `CONTAINER_REAP_SWEEP_MS` (5 min). `ContainerServiceOptions` gained
  `now?: () => Date`.
- `reapStuckContainers()` — snapshot of `listContainers()` filtered by `isStuck`,
  then per record: re-read from the store, re-test the predicate, act, catch and
  log per record. Returns the ids it resolved.
  - `pending` / `creating` past the provisioning TTL → `error` written FIRST,
    then best-effort reclaim.
  - `stopping` past the same TTL → reclaim, then `stopped` (matching
    `terminateContainer`'s ordering, so a crash mid-reap re-runs cleanly).
  - `enrolling` past the enrollment TTL → healthy → `running` + `peerId`; child
    proven gone → `error` + reclaim; anything else (alive-unhealthy, probe
    failed, orchestrator can't say) → left alone.
- `startReaper(intervalMs?)` / `stopReaper()` with an in-flight `sweeping` flag;
  `startReaper` runs one sweep immediately.
- Factored `enrollIfHealthy(container)` — the healthy→`running`+peerId step now
  written once and used by both `waitForEnrollment` and the sweep.
- `isChildGone(state)` — the single-reading form of the prereq's two-poll
  `hasChildDied`, built from the same `isChildDown` / `ENROLLMENT_TOLERATED_RESTARTS`
  pieces (no restated rule). `childDiedMessage(state)` gives one wording for the
  error text, shared by the wait and the sweep.
- `terminateContainer` now routes through `stopAndRemove`, which forgives a
  stop-or-remove failure when `inspectRunState` affirmatively reports the handle
  is gone, and rethrows otherwise. `orchestratorKnows` returns `true` whenever it
  cannot say (no `inspectRunState`, or a probe that itself threw).
- `NOTE:` tripwire parked at `terminateContainer`'s catch (quota is generous to
  the tenant, not exact — the record stops counting while its container may still
  be up).

**`billing-service.ts`** — exported `QUOTA_CONSUMING_STATUSES`
(`pending`/`creating`/`enrolling`/`running`/`stopping`); `canCreateContainer`
uses it instead of `c.status !== 'stopped'`.

**`server.ts`** — `containerService.startReaper()` in `start()`;
`stopReaper()` in both `stop()` and `runShutdownSequence()`.

**`index.ts`** — the three new constants and `QUOTA_CONSUMING_STATUSES` exported.

**`docs/architecture.md`** — § `@serfab/cadre-provider` gained a "Reap sweep"
bullet plus two sub-bullets (label-based handle recovery + volume caveat; the
quota change).

## Known gaps / things worth an adversarial look

- **No integration-level exercise.** Every new test is a unit test over
  `MemoryStore` and stub orchestrators. `ProviderProcessOrchestrator.resolveDockerId`
  is typechecked but never executed by a test — no integration scenario drives
  it. The real-network suite was not run here (it needs built dists and real
  libp2p, and routinely exceeds the runner's idle budget).
- **`DockerOrchestrator.resolveDockerId` is tested against a hand-rolled fake,
  not `fake-docker.ts`.** That shared helper only covers the volume surface
  (`createVolume`/`getVolume`) and has no `listContainers`; the new test supplies
  its own `listContainers` stub. If the reviewer would rather the daemon fake be
  shared, `fake-docker.ts` is the place to grow it.
- **Reaping a stuck `creating` or dead `enrolling` record destroys the node's
  identity.** `removeContainer` deletes the named `/data` volume, so the
  container's libp2p identity key goes with it. Correct here (the container never
  enrolled) and unchanged from what `provisionContainer`'s existing failure path
  already does — but it is a real, irreversible side effect of a *periodic*
  sweep now, not only of a synchronous provision. Flagged in the code comment on
  `reclaimStuckContainer`.
- **The quota change is tenant-visible.** A customer sitting at their plan limit
  purely because of `error` records can create containers again immediately. That
  is the intended fix, not a regression — but it changes behaviour for existing
  deployments the moment this ships.
- **`stopping` → `stopped` is unconditional once reclaim is attempted.** The
  stop/remove halves are best-effort and swallow their errors, so a record can
  reach `stopped` while its container is still up (only if the orchestrator threw
  on both stop and remove). Deliberate — same trade as the `terminateContainer`
  tripwire — but it is the one place the sweep can lie about a container being
  gone. Worth a second opinion on whether `stopping` should instead stay put when
  the reclaim visibly failed.
- **The 15-minute provisioning TTL is a judgement call, not a measurement.** It
  was chosen to sit well past a slow `pullPolicy: 'always'` image pull; no pull
  was timed. The re-read guard does not help here (a pull touches nothing), so
  the TTL is the only defence against reaping a provision that is genuinely still
  in flight.
- **`resolveDockerId` returns the *first* label match.** If a container id ever
  had two containers wearing the same label (a recreate that left the old one
  behind), the sweep reclaims only one. Not reachable today —
  `DockerOrchestrator.createContainer` names containers `cadre-<id>` and Docker
  refuses a duplicate name — but the code does not assert it.
- **`isChildGone`'s single-reading rule is more aggressive than the enrollment
  wait's two-poll rule** by design (the record has already sat past its TTL). The
  case worth probing: a container that Docker's `unless-stopped` policy has just
  restarted, caught in the down-and-exited instant by a sweep tick, would be
  condemned. The five-minute TTL plus the health check running first is the whole
  defence.
- **No test asserts the sweep's behaviour across MANY records** (e.g. that one
  record throwing does not stop the rest). The per-record `try`/`catch` is there
  and one throwing-reclaim case exists, but the multi-record continuation is
  untested.
