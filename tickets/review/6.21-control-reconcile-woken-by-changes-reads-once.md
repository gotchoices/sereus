# The control reconcile pass runs on change, with a 2-minute backstop

## What was built

`CadreNode.reconcileControlCohort` is the control network's upkeep pass (gate refresh, first self-record publish, delegate grants, strand address books, reap, ledger marker, joined-strand publication, sibling dials). It used to run on a 15 s `setInterval`. It now runs on a `scheduleRuns` schedule from `table-change-watch.ts` (single-flight runs, one timer set), and only when something it acts on changes:

- **Gate watch.** `start()` takes `controlDatabase.watchTables(MEMBERSHIP_GATE_TABLES, …, { label: 'membership-gate' })` right after the membership listener is wired. The seven tables are `CadrePeer`, `OwnerKey`, `Revocation`, `CadreInvite`, `CadreInviteUsage`, `OwnerGrant`, `OwnerGrantUsage`. Its run (`onMembershipGateTablesChanged`) awaits `refreshMembershipGate('table-change')`, then triggers the reconcile schedule. A replicated revocation therefore hangs up the removed machine within the 50 ms coalescing window, without waiting behind a pass that is spending its dial budget.
- **Reconcile schedule.** `controlReconcileRuns` replaces `controlCohortReconcileTimer`, built in `startRecordRefresh` with `backstopMs = network.controlCohort.reconcileMs ?? DEFAULT_CONTROL_COHORT_RECONCILE_MS` (now 120 s). Its run waits for any pass in flight (`await this.reconcileControlCohortInFlight?.catch(() => undefined)`) and then calls `reconcileControlCohort()`, so a change that arrived while a pass was reading is never dropped by joining that pass. Explicit callers keep today's contract and join an in-flight pass.
- **Triggers.** The eager start pass (`trigger(0)` after `startRecordRefresh`), `self:peer:update`, every gate-table change, and a control `connection:open` or `connection:close` whose remote peer is in `authorizedControlPeers` (`onControlSiblingConnectionChange`; on open it first calls the now-public `ControlDatabase.invalidateMembershipViews()`, so a machine that was offline while that sibling committed reads storage on the pass the connection starts). A connection to a relay, a bootstrap node or another party's machine starts nothing.
- **Wakes a pass arms.** `runReconcileControlCohort` returns a private `ControlCohortPassOutcome` (`dialed` plus `unconnected`: a selected sibling or cold-start bootstrap peer the pass tried and could not connect, a failed dial or no dialable address). The wrapper `runReconcileControlCohortAndArmWake` advances or resets `reconcileRedialStreak` and triggers the schedule for `nextReconcileWakeMs(...)` (`control-cohort.ts`): the redial `min(15 s × 2^(streak − 1), backstop)` and the earliest strand-address due time later than the pass's start when it is sooner than the backstop; the smaller wins, `undefined` otherwise. The public `ControlCohortReconcileResult` (`{ dialed }`) is unchanged.
- **Backstop and maximum age.** `DEFAULT_CONTROL_COHORT_RECONCILE_MS = 120_000`, documented as the backstop with a `NOTE:` on cadres larger than 16 machines. `MEMBERSHIP_VIEW_MAX_AGE_MS` still equals it, so it is 2 minutes too; its NOTE now names only the outside-the-cohort case, since the reconnect invalidation covers the offline-machine case.
- **Teardown.** `stopRecordRefresh` disposes the schedule and resets the streak; `cleanup` disposes the gate watch before `setMembershipChangeListener(null)` and `controlDatabase.close()`.
- **Declined restructure.** The pass still makes its own membership reads (gate refresh, reap, sibling enumeration, strand-address targets), all served from the membership rows view. The NOTEs in `runReconcileControlCohort` and on `strandAddrRefreshTargets` now state that cost and that sharing one row set across the pass was declined.

Every comment that stated the 15 s cadence was rewritten (grep `cadre-core/src` for `15 s`, `reconcile tick`, `timed reconcile`, `reconcile interval`: none left). Docs: `docs/architecture.md` gained "What starts a pass" and "Retries a pass arms" under "Cohort auto-connect", the gate watch and the reconcile schedule under "Table change subscriptions" → Consumers, and the rewritten "Maximum age", "The snapshot", "How the snapshot refreshes" (now with an anchor `membership-snapshot-refresh`), owner-anchor, provisional-admission, add-a-node and strand-address paragraphs; `docs/strands.md` → "Publication"; `packages/cadre-cli/README.md` → `--addr`.

## One assumption of the ticket that does not hold, and why it does not matter

The ticket says a local membership write's second gate refresh (from the gate watch, 50 ms after the awaited listener's) "is served from the view". It is not: the listener's refresh runs under the control write lock, so its reads take the committed-read path, and a load served that way is returned but never kept (`membership-view.ts`). The watch's refresh is therefore the read that refills the view after the write. It is not an extra storage read: some read would have had to load the view after the change anyway, and this one happens 50 ms later instead of on the next caller. The consult-budget spec's genesis move below is this effect (consults moving between phases, not growing). The doc comment on `onMembershipGateTablesChanged` says so.

## Why the cohort scenarios' `openingPass` assertions were kept

The ticket suggested asserting only that B holds a connection to C after the explicit pass. The stronger attribution still holds under this design: B's harness dial gate denies every dial to C outside `dialsToC.reconcile()`, passes are single-flight, and a scheduled run that overlaps an explicit call either is joined by it (its result, including `dialed`, is then recorded as the explicit call's) or waits for it and starts after the gate has shut again. A pass B starts on its own can therefore never open the link unrecorded. In the first isolation case the override `B.reconcileControlCohort = () => dialsToC.reconcile()` routes every scheduled run through the harness, so the passes under test are now the change-driven ones and the 2 s backstop, not a timer. This reasoning is by inspection only, since the runs are blocked; if a run disproves it, the ticket's weaker assertion is the fallback, and the harness header's "NOTE: one ordering still reads as the pass's own dial" names the other known race.

## Edge cases checked by inspection

- **Write lock.** Neither new subscription runs consumer code inside a commit: the watch handler arms a timer; both runs start from it.
- **Self-wake.** A pass's own writes (reap, first self-record publish, marker, joined-strand publication) change gate tables and wake one gate refresh and one follow-up pass, which finds nothing to do. Bounded at one. Not yet confirmed by an idle measurement (blocked above).
- **Gate watch before the schedule exists.** A change in the first second after start refreshes the gate and finds `controlReconcileRuns` null; the eager pass covers it. An explicit pass in that window still advances the streak, which `armReconcileWake` then uses once the schedule exists.
- **Untouched tables.** Noted at the gate watch in `start()`: the four chain tables hear local commits only until first read on this `Database`; nothing depends on a chain row until a `CadrePeer` / `OwnerKey` row refers to it, and that row is itself a change on a touched table.
- **`connection:close` redials at once.** A sibling that hangs up is dialed again on the pass the close starts, then on the ladder. A machine that was revoked and hung up by its siblings keeps dialing them until it learns of its own removal, as it did on the timer.
- **Joined-strand publication** starts no pass (`JoinedStrandSession.onLocalChange` is untouched), as the two parked-phone scenarios require; their NOTEs now name every trigger that would publish early.
- **Scenario harness drains.** `control-trio.ts` drains B's eager start pass by observing the self-record write, sleeping 1 s and joining the pass; the eager pass is now scheduled (a 0 ms timer after `startRecordRefresh`) rather than called inline, which the sleep covers.
