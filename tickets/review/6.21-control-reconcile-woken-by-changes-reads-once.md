## What was built (implement stage, `ticket(implement): control-reconcile-woken-by-changes-reads-once`)

`CadreNode.reconcileControlCohort` is the control network's upkeep pass (gate refresh, first self-record publish, delegate grants, strand address books, reap, ledger marker, joined-strand publication, sibling dials). It used to run on a 15 s `setInterval`. It now runs on a `scheduleRuns` schedule from `table-change-watch.ts` (single-flight runs, one timer set), and only when something it acts on changes:

- **Gate watch.** `start()` takes `controlDatabase.watchMembershipTables(…, { label: 'membership-gate' })` right after the membership listener is wired: a `watchTables` on the seven tables the control database's membership views copy (`CadrePeer`, `OwnerKey`, `Revocation`, `CadreInvite`, `CadreInviteUsage`, `OwnerGrant`, `OwnerGrantUsage`), so the list lives only in `ControlDatabase`. Its run (`onMembershipGateTablesChanged`) awaits `refreshMembershipGate('table-change')`, then triggers the reconcile schedule. A replicated revocation therefore hangs up the removed machine within the 50 ms coalescing window, without waiting behind a pass that is spending its dial budget.
- **Reconcile schedule.** `controlReconcileRuns` replaces `controlCohortReconcileTimer`, built in `startRecordRefresh` with `backstopMs = network.controlCohort.reconcileMs ?? DEFAULT_CONTROL_COHORT_RECONCILE_MS` (now 120 s). Its run waits for any pass in flight and then calls `reconcileControlCohort()`, so a change that arrived while a pass was reading is never dropped by joining that pass. Explicit callers keep today's contract and join an in-flight pass.
- **Triggers.** The eager start pass (`trigger(0)` after `startRecordRefresh`), `self:peer:update`, every gate-table change, and a control `connection:open` or `connection:close` whose remote peer is in `authorizedControlPeers` (`onControlSiblingConnectionChange`; on open it first calls the now-public `ControlDatabase.invalidateMembershipViews()`, so a machine that was offline while that sibling committed reads storage on the pass the connection starts). A connection to a relay, a bootstrap node or another party's machine starts nothing.
- **Wakes a pass arms.** `runReconcileControlCohort` returns a private `ControlCohortPassOutcome` (`dialed` plus `unconnected`). The wrapper `runReconcileControlCohortAndArmWake` advances or resets `reconcileRedialStreak` and triggers the schedule for `nextReconcileWakeMs(...)` (`control-cohort.ts`): the redial `min(15 s × 2^(streak − 1), backstop)` and the earliest strand-address due time later than the pass's start when it is sooner than the backstop; the smaller wins, `undefined` otherwise. The public `ControlCohortReconcileResult` (`{ dialed }`) is unchanged.
- **Backstop and maximum age.** `DEFAULT_CONTROL_COHORT_RECONCILE_MS = 120_000`, documented as the backstop with a `NOTE:` on cadres larger than 16 machines. `MEMBERSHIP_VIEW_MAX_AGE_MS` still equals it; its NOTE now names only the outside-the-cohort case, since the reconnect invalidation covers the offline-machine case.
- **Teardown.** `stopRecordRefresh` disposes the schedule and resets the streak; `cleanup` disposes the gate watch before `setMembershipChangeListener(null)` and `controlDatabase.close()`.
- **Declined restructure.** The pass still makes its own membership reads, all served from the membership rows view. The NOTEs in `runReconcileControlCohort` and on `strandAddrRefreshTargets` state that cost and that sharing one row set across the pass was declined.

A local membership write's second gate refresh (from the gate watch, 50 ms after the awaited listener's) is not served from the view: the listener's refresh runs under the control write lock, so its load is returned but never kept (`membership-view.ts`), and the watch's refresh is the read that refills the view. It is not an extra storage read; some read would have had to load the view after the change anyway. The consult-budget spec's genesis move (+4 consults, −3 at founding) is this effect, documented in that spec's `BASELINE_UPSTREAM` paragraph.

## Review findings

Read the two implement commits' diffs in full before the handoff, then every file they touch and the ones they should have touched (grep of the repo for `15 s`, `15s`, `every 15`, `reconcile interval|cadence|tick`, `timed reconcile`, `recurring reconcile`).

**Checked by reading and reasoning, no defect found:**

- **Scheduler semantics.** `scheduleRuns` arms a timer on `trigger` even while a run is in flight (`fire` sets `rerun` only when the timer fires mid-run), and `clearWakes` runs at fire time, so a wake `armReconcileWake` arms from inside a scheduled run survives that run's settle; `settled()` then re-arms the backstop. A `trigger(0)` from inside a run fires on the next macrotask, after the run has settled. An explicit pass arms its wake on a watcher that is not `running`, so it is a plain timer. The scheduled run's "await the in-flight pass, then start a fresh one" cannot join a pass that began before the change: any pass it could join began after the run started waiting.
- **No self-wake loop.** `refreshAuthorizedControlPeers` writes no gate table (the trusted-owner store and the enrolled-machine count are node-local), so a gate-watch refresh never re-triggers the watch. The pass's own writes (first self-record, marker, reap) wake exactly one follow-up pass, which writes nothing.
- **Revoked-sibling close.** The remover's refresh replaces `authorizedControlPeers` before `hangUpRevokedControlPeers` closes the connection, so the resulting `connection:close` starts no pass. A machine that was itself removed and does not yet know keeps redialing its siblings, each provisional admission lasting the 28.5 s deadline; the period and the dial count match the old timer's. Recorded as a tripwire (below).
- **Teardown order.** `cleanup` calls `stopRecordRefresh` (disposing the schedule and removing the connection listeners) before the control node stops, so the closes teardown causes trigger nothing; the gate watch is disposed before the membership listener is detached and the database closes. A gate-watch run during the first second after start finds `controlReconcileRuns` null and the eager pass covers it; an explicit pass in that window still advances the streak.
- **Write lock.** Neither new subscription runs consumer code inside a commit: `watchTables`' handler only arms a timer; the reconcile schedule has no subscription.
- **Strand-address wake.** Due times a pass stamps are later than its start (10 min on an answer, ignored as beyond the backstop; 60 s on a failure, woken for). Entries at or before the start survive only when the pass skipped the read for zero connections, and the rule ignores them, so no spin.
- **Harness drains.** `control-trio.ts` observes the self-record write, sleeps 1 s and joins the pass; the eager pass is now a 0 ms timer, which the sleep covers. The cohort scenarios' `openingPass` assertions hold under the new triggers by the single-flight and dial-gate argument in the handoff (restated under *Why the `openingPass` assertions were kept*).

## Why the `openingPass` assertions were kept

The ticket suggested asserting only that B holds a connection to C after the explicit pass. The stronger attribution still holds: B's harness dial gate denies every dial to C outside `dialsToC.reconcile()`, passes are single-flight, and a scheduled run that overlaps an explicit call either is joined by it (its result, including `dialed`, is then recorded as the explicit call's) or waits for it and starts after the gate has shut again. A pass B starts on its own can therefore never open the link unrecorded. In the first isolation case the override `B.reconcileControlCohort = () => dialsToC.reconcile()` routes every scheduled run through the harness, so the passes under test are the change-driven ones and the 2 s backstop. By inspection only, since the runs are blocked; if a run disproves it, the ticket's weaker assertion is the fallback, and the harness header's "NOTE: one ordering still reads as the pass's own dial" names the other known race.
