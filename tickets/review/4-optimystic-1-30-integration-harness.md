# Review: the integration harness opens one node storage per scope

Fourth of five tickets adopting Optimystic 1.30.0. Ticket 2's shape is what this follows: `storage: { open(scope): Promise<NodeStorage>; allotmentBytes?: number }`, no single-instance form, cadre-core closes nothing it is handed. Ticket 5 (release notes and fold) is the only one left.

## What landed

**The capture (`block-store-probe.ts`).** `RawStorageCapture.provider` became `open(scope): Promise<NodeStorage>`, still memoized per scope and still for the reason the module's own comment gives. `forStrand`, `control` and every coverage helper keep taking and returning the **block** store (`IRawStorage`) — the capture reaches into `NodeStorage.blocks` and nothing in this package reads `kv` or `pieces` through it. Both guards are unchanged in behaviour: `control()` still throws rather than minting an empty store, and `forStrand` still refuses a control scope key and still detects scope collapse.

Its factory took the SCOPE — `(scope: string) => NodeStorage`, defaulting to `() => memoryNodeStorage()` — which is the one place this deviates from the ticket's letter (it said `() => NodeStorage`). The reason is in the next paragraph; reviewers should check whether they agree.

**`strand-offline-waits-for-party-machine` needed a scope-taking factory.** The ticket asked for this scenario's offline journal to come from the scope's `NodeStorage.kv`, and Optimystic refuses a `MemoryKVStore` journal outright ("a journal lost with the process is the no-journal configuration" — `offline-config.ts`). So the phone's storage has to be file-backed, and a file-backed capture cannot name a directory per scope unless the factory is told the scope. The phone now gets `fileNodeStorage(join(home, 'storage', scope))` per scope through its capture; the `offline/` directory is gone; the scenario keeps each `OpenNodeStorage` it opened and closes them in its `finally` before `rmSync`, because cadre-core closes nothing and the file backend holds a write-ahead-log handle and a directory lock. The node (a memory-storage replica with no offline mode) is unchanged.

**The child-process fixture.** `fixtures/strand-restart-party.mjs` builds one `fileNodeStorage(join(stateDir, 'storage', scope))` per scope, memoized, with the journal as that storage's `kv`. Same `storage/` directory layout as before. Its `stopAndExit` now closes the opened storages where it used to close the journals — same ordering (after `node.stop()`, even after a failed stop), same `code = 1` on a close failure. Both the fixture's header comment and the driver's were rewritten, including the driver's `offline` option doc.

**`slow-raw-storage.ts`.** `deleteBlock` added (one of the three errors that were red at HEAD). `slowMemoryStorageProvider` returns a `NodeStorage` whose `blocks` alone is the slow wrapper, with the reason in its comment: the duration this option buys is control-database bring-up, which is block operations.

**`test-party.ts`.** `storage: memoryNodeStorage()` as a value, where it had been passing a function (the second HEAD error).

**The three forwarding seams.** `ControlNodeOpts.storageProvider`, `TopologyMachineSpec.storageProvider` and `PinningMemberOptions.storageProvider` kept their names and were retyped to a new `NodeStorageOpener` exported from `node-fixtures.ts`, which is `StorageConfig['open']` — read off the config rather than re-spelled three times. The default (one fresh `memoryNodeStorage()` per scope) and the `storageOpDelayMs` mutual exclusion are unchanged. **No `allotmentBytes` passthrough was added**: nothing sets one, and a memory node storage reports no free space, so a node with no allotment measures nothing.

**`control-delete-while-alone-convergence`.** Its two nodes take captures instead of one `MemoryRawStorage` pinned to every scope. Its header comment says what replaced the single-store shape and why nothing is lost: the party runs no strands, so the control database is the only scope either node opens, and the three coverage calls read `capture.control()`.

**The assertion that inverted.** `strand-client-node-holds-no-blocks` step 3 asserted the client's provider was never asked for the strand's scope. Under 1.30 it is asked — a client keeps the strand's clock high-water mark, blob records, owed-blob ledger and blob pieces — so the step now asserts that the scope IS opened and that the client's block store holds **nothing**, while both serving machines hold every block. `readBlockIndex` of the client's strand store, asserted empty by key list so a failure names what it wrongly held; `compareBlockCoverage` was considered and rejected, because "the client does not cover the server" is weaker than "the client holds nothing" (a client holding half the blocks would pass it). The header comment's step 3 was rewritten. Measured on the run: server 0 held 45 committed blocks, the client 0.

**Everything else was the `capture.provider` → `capture.open` rename** across 25 scenario files, plus stale comment wording in five of them (`control-offline-read-after-restart`, `strand-membership-closed-strand-e2e`, `strand-relay-only-restart-reconverges`, `strand-unpublish-sibling-convergence`, `strand-reattach-first-sync-measure`).

## Tests

**No new tests**, as the ticket specified. Changed:

- `test/block-store-probe.spec.ts` — the eight `captureRawStorage` cases are now `async` and await `open`, and compare against `.blocks` where they used to compare the store itself. The scope-collapse case seeds a shared `memoryNodeStorage()` instead of a shared `MemoryRawStorage`. Same eight behaviours, no additions, no removals.
- `test/control-node-config.spec.ts` — `storeForScope` deleted with the single-instance form it resolved (the ticket called this out). "Hands out a FRESH store per scope" became "opens FRESH storage per scope". The verbatim-forwarding case now asserts opener **identity** (`built.storage.open === open`) rather than demonstrating it with a one-store-for-every-scope opener, which is no longer the shape a caller writes; the comment says why identity is the property that matters (a builder that re-memoized would defeat a capture).
- `strand-client-node-holds-no-blocks` step 3, described above. One existing step re-aimed, not a new case.

**What a reviewer should look at hardest:**

1. **The scope-taking capture factory**, which is the one deviation from the ticket. Is `(scope) => NodeStorage` the right generalization, or should `strand-offline-waits-for-party-machine` have built its own file-backed `open` outside the capture and given up `phoneCapture.forStrand(strandId)` for its coverage check?
2. **Making that scenario's phone file-backed changes what it exercises.** Its block store is now a `FileRawStorage`, which cadre-core wraps in a read cache (it skips only `MemoryRawStorage`), and its four flows now pay filesystem latency. All four passed, and the step timings in the log looked ordinary, but a reviewer may judge the behaviour change too large for the rule it serves.
3. **`control-delete-while-alone-convergence`'s header rationale.** I claimed nothing is lost because the party runs no strands. If a future arm of that scenario launches one, the control and strand scopes will no longer be one store, and the comment should be the thing that warns the next author.
4. **Whether the client-holds-no-blocks assertion is as strong as claimed.** It proves the block store is empty at the moment it is read, after the client has written and read through the serving machines. It does not prove nothing could land there later in a longer run.
