# Review: writes to `CadreControl.Revocation` are now owner-signed

Completes the two-ticket chain that started as `bug-control-revocation-unauthenticated-writes`.
The prior implement run landed the schema rule and the production/test signing changes but
ran nothing; this run wrote the regression tests, updated the docs, and validated the whole
package.

## What the change is

`CadreControl.Revocation` is the append-only table that retires the one-time authorization
nonce (`StampId`) of a removed `OwnerKey` / `CadrePeer` / `ValidationKey` / `Strand` row, so a
never-expiring add-approval signature cannot resurrect a removed row.

At HEAD before the chain it had **no authorization at all** — any writer reaching the
replicated control database could append. Two consequences were reproduced against a real
`CadreNode` in the fix stage:

- **Unbounded junk.** Bare inserts were accepted and permanent; they replicate party-wide and
  `CadreNode.listAuthorizedMembers` re-reads the whole retired set per inbound gate request.
- **Remote eviction / pre-block.** A tombstone written while the target `CadrePeer` row is not
  locally visible landed unauthenticated (`RowIsGone` reads only locally visible rows); the
  owner's own later admission of that exact row was then refused by `NotRevoked`, permanently,
  and every node dropped the peer from the authorized-membership set.

The fix adds one constraint to the table:

```sql
constraint Authorized check on insert (
    exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(digest('CadreControl.Revocation', 'remove', new.TableName, new.StampId), context.Signature, A.Key, 'ed25519'))
)
) with context (OwnerKey text, Signature text);
```

The digest binds the whole row. Its `'CadreControl.Revocation'` domain tag keeps it disjoint
from the `'CadreControl.CadrePeer'` `'remove'` digest the same owner signs in the **same
transaction** for the delete the tombstone accompanies — so neither signature stands in for
the other.

## What each rejection reports

Measured against this exact rule, asserted by name via `expectConstraintFailure` in
`test/control-constraint-helpers.ts`.

| Attempt | Reports |
|---|---|
| tombstone with no context (`OwnerKey`/`Signature` null, or either half alone) | `Authorized` |
| tombstone signed by a non-owner (own key, or claiming the founder's) | `Authorized` |
| owner-signed tombstone over a different `StampId`, or a different `TableName` | `Authorized` |
| owner's `CadrePeer` / `OwnerKey` `'remove'` signature replayed as the tombstone | `Authorized` |
| owner-signed tombstone of a still-live row | `RowIsGone` |
| delete or update of an existing tombstone | `Immutable` |

The last two were already pinned before this run; the rest are new.

## Test coverage added

All in `control-revocation-replay.spec.ts`, which already owned the `Revocation` rules.

Negative (the `Authorized` rows above), one test each:

- `an UNSIGNED tombstone is refused`
- `a tombstone signed by a NON-OWNER is refused`
- `an owner signature does not transplant across TableName or StampId`
- `the delete's own remove signature does not double as the tombstone's` — probed against an
  orphan stamp (no live row) so `RowIsGone` passes and only `Authorized` can reject. Covers
  both signing encodings: the `CadrePeer` digest is a base64url string, the `OwnerKey` one is
  raw canonical bytes, so the rejection is the domain tag doing the work and not an encoding
  mismatch.

The two field consequences, inverted:

- `unsigned appends cannot FLOOD the append-only table` — 25 bare inserts all rejected,
  `queryRevokedStamps('CadrePeer')` stays empty.
- `an unsigned tombstone cannot PRE-BLOCK a peer that is not locally visible` — the tombstone
  is refused, and the owner's later admission of that exact `(peerId, stamp)` still succeeds.

Positive guards that legitimate removal still works through the **shipped** code paths (every
other test writes its tombstone through the suite's own helper, so these are what catch a
mismatch between what production signs and what the schema verifies):

- `removePeer retires the stamp end to end` — real `CadreNode`, `initializeSeedBootstrap` +
  `authorizePeer` + `removePeer`, real ed25519-derived peer id. Exercises the
  `signDigest`/base64url encoding.
- `deleteValidationKey retires the stamp end to end` and `deleteStrand retires the stamp end
  to end` — the public wrappers over `deleteGuardedRow`. Exercise the
  `buildAuthorizationMessage`/raw-bytes encoding.
- `the two-owner OwnerKey removal transaction retires the stamp`.

## Known gaps — where to push

Honest list; none of these are blocking, but a reviewer should not assume they are covered.

- **Single-node only.** Every test boots one `CadreNode` on the `transaction` profile. The
  convergence hazard the schema comment calls out — a node that has not yet seen a
  `Revocation` row accepting a replayed add, then holding both after merge — is untested here
  and would need `integration-tests`. It is a pre-existing property of the whole `NotRevoked`
  design, not something this change introduces or fixes.
- **`Authorized` reads LIVE `OwnerKey`, not `committed.OwnerKey`.** Deliberate, matching every
  sibling table, and documented at length in the constraint comment. The one behavioural
  difference: a founding transaction on an owner-less database could seat an owner key and
  file a tombstone in one go. Untested — an owner-less control database is already a total
  loss and a second transaction achieves the same thing under `committed.*`. Worth a
  reviewer's eye on whether that reasoning holds.
- **Single-rejector technique.** Several assertions depend on Quereus reporting exactly one
  violated deferred constraint per commit (see the NOTE in `control-constraint-helpers.ts`).
  If an engine change ever reports a different one, these go flaky. Do not widen the
  accepted-name list to get them green — re-shape the write.
- **No test that an owner *removed after* signing a tombstone has that tombstone rejected.**
  Follows from reading live `OwnerKey`, but is not pinned.
- **Docs.** `docs/architecture.md` is the only doc that mentions `Revocation`; both sites were
  updated. Nothing was checked in `docs/cadre-consistency.md` / `docs/strands.md` because grep
  found no mentions there.
