# Review: the join catch-up re-runs for a peer that reconnects

## What changed

`PeerJoinBackfill` (cadre-core's peer-join catch-up, shared by every strand network and the control network) used to mark a peer caught up (`done`) for the whole runtime. A peer that went offline, missed writes while out of every cohort, and came back was sent nothing: the catch-up skipped it, and Optimystic's under-replication drain owes only cohort members that missed a confirmation. It got the missed blocks only by read repair, one read at a time.

Now:

- `start()` subscribes to libp2p's `peer:disconnect` (fired when a peer's last connection closes; `evt.detail` is the `PeerId`) and `stop()` removes it. The handler, `forgetCaughtUp`, deletes the peer from `done` and nothing else. The per-peer memo (`memos`), `contacted`, `failures`, `retryAfter` and any pending backoff timer are kept. The memo keeps the re-run down to what moved. `contacted` makes the re-run wait out `debounceMs`, so a link that reconnects several times in one settle window costs one run. Keeping the backoff state stops an unreachable peer from being re-dialled on every reconnect.
- **Disconnect during a run.** If the disconnect arrives while the peer's run is in flight (`inFlight` holds it), the peer is added to `disconnectedInFlight`. `settleRun` then does not add it to `done` even if the run settles clean, and `trackRun`'s `finally` clears the mark. The check is deliberately not `isConnected` at settle time, because hand-driven `catchUpPeer` runs (tests, embedders) target peers with no connection, and `done` must still mean "caught up" for them.
- Accepted-tradeoff `NOTE:` on `forgetCaughtUp`: a returning peer that wrote while away with a cohort naming this node pushes those blocks here twice, from its re-run and from its drain. The cost is bytes only, because `saveReplicatedBlock` is idempotent. Revisit when `blocked/optimystic-embedder-cannot-report-block-holders` lands, or if reconnect re-runs dominate push traffic.

## Known gaps / things to look at

- **Fake libp2p only.** Both tests drive `peer:disconnect` through the spec's `makeLibp2p` fake. No integration scenario checks that a real libp2p node fires `peer:disconnect` once, only after the last connection closes, and with a `PeerId` detail. `strand-peer-redial.ts` already relies on the same event shape. A real-network check would be a strand scenario: drop one node, write, reconnect, then check the returning node's raw store before any read. None was added; weigh whether it is worth its run time.
- **Two `PeerMemo` NOTEs pull in opposite directions.** The emptied-store NOTE suggests "clear the peer's memo on a full disconnect" as the remedy if a machine can rejoin with an emptied store. The size NOTE says that dropping the memo on disconnect re-pushes the whole store on every reconnect. The ticket said to keep both as tripwires, and I did. A reviewer may want the first NOTE to name that cost as well.
- **Re-run cost when nothing moved.** One `listBlockIds` walk plus one `getMetadata` per block, and a `getBlockProof` for blocks whose memo revision is behind. No network traffic. It is paid once per reconnect, after the debounce (1 s on a strand, 250 ms on the control network). Not measured on a large store.
- **Reconnect while the run is still in flight.** The reconnect's identify goes to `rearmAfterFlight` and is replayed when the run ends. Because `disconnectedInFlight` kept the peer out of `done`, the replay re-runs it. I traced this but did not test it separately; it reuses the existing replay path.
- The control network relies on `authorizePeer` at push time, unchanged. A removed member that reconnects is denied, and nothing is pushed to it.
