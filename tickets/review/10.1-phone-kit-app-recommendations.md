# Phone kit: one app recommends another (review)

First of three tickets for "app A links to app B; the user allows B to join before leaving A; B joins A's cadre on first launch". `reference-app-rn-recommends-an-app` (A's side) and `reference-app-rn-joins-the-app-that-recommended-it` (B's side) build on this one. **A** is the owner app that recommends, **B** the recommended app. The design (no open invitation: A records only the user's consent and mints a targeted invitation when B's ordinary link request arrives) is written up in docs/architecture.md → "Recommending another app".

## What was built

- **`AppRecommendationStore`** (`src/app-link/recommendation-store.ts`), over `PhoneNode.recommendationSlot()`. One JSON list in one slot, at most one entry per scheme. `approve` (replaces the same scheme, prunes expired and other-party entries), `live(partyId)` (most recently approved first — storage order, not a sort by `approvedAtMs`), `withdraw(scheme)`, `take(scheme, partyId)` (removes on match). Calls serialized through one promise chain, as `LinkRequestStore`. A malformed record (not JSON, not an array, or any entry of the wrong shape) reads as an empty list with one `console.warn` per read; the next write replaces it. `RECOMMENDATION_TTL_MS` = 1 hour.
- **`PhoneNode.recommendationSlot()`** and `PhoneNodeNames.recommendationsKey` (`'recommended-apps'`). `linkRequestSlot` and `recommendationSlot` now share one private helper, `appLinkSlot(key)` — same behaviour as before (waits for a stop in progress, re-resolves the handle on every load and save), including the existing `NOTE:` about restart/join/dissolve.
- **`src/app-link/recommend-links.ts`**: `RECOMMENDED_BY_REFERRER_PREFIX` (`'sereus-recommended-by:1.'`), `recommendedByReferrer`, `recommendedBySchemeFromReferrer`, `storePageLink(app, platform, ownScheme)` and the `StorePlatform` type (`'android' | 'ios'`).
- **`links.ts`**: `CadreLink` gains `{ kind: 'recommended-by'; text }`, `parseCadreLink` reads `<any scheme>://cadre-recommended-by/<scheme>` (path → kind is now a lookup table), and **`recommendedByLink` lives here, not in `recommend-links.ts` as the plan said**: it shares the path constant with the parser, and keeping every `<scheme>://cadre-…/` builder next to the one parser stops them drifting. Exported from the index either way.
- **`SereusApp`** gains optional `androidPackage` and `iosAppStoreId`; `KNOWN_SEREUS_APPS` is unchanged (the reference app is in neither store).
- **Config plugin**: `requireSereusApp` accepts and validates the two fields (`^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)+$`; 1–12 digits, string only). `addJoinRequestQuery` became `addViewQueries(manifest, schemes)`, which adds one `<queries>` VIEW intent per scheme not already declared — `sereus-join-request` plus every known and extra app scheme — all missing ones in one new `<queries>` element. Only when `appLinks` is set.
- **Reference app** `app/+native-intent.tsx`: a `switch` over the link kinds; `recommended-by` returns the path unchanged, with a comment naming `reference-app-rn-joins-the-app-that-recommended-it`, which routes it.
- **Docs**: architecture.md gains `##### Recommending another app` (flow, hint table, why no open invitation, the trust rule, the pre-approval properties, the accepted-tradeoff security paragraph); "Between apps on one phone" step 3 and its "A link is a request, never a grant" bullet now mention the pre-approval. Kit README: a "Recommending another app" subsection under App links (A and B snippets, API bullets, trust rule), the store-id fields under "Adding an app to the known list", and the plugin's `appLinks` section (extras' store ids, the new `<queries>` entries, the new prebuild refusals).

## Tests

- **New `test/app-link/recommendation-store.spec.ts`** (4 tests) — pins the store's security contract: a live entry goes to exactly one matching `take` and not to another party or scheme; nothing after `RECOMMENDATION_TTL_MS`; re-approval replaces the grant and expiry while another app's entry stays, and `withdraw` drops only its scheme; a malformed record reads as none (one warning) and the next `approve` replaces it.
- **`app-link.spec.ts`**: two `parseCadreLink` rows (the recommended-by link and its empty form) and a `recommendedBySchemeFromReferrer` table (the token, Play's organic `utm` text, the empty string, the bare prefix).
- **`node.spec.ts`**: the existing pinned-default-names test gains `recommendationsKey: 'recommended-apps'`.
- No test for `storePageLink` / `recommendedByLink` (string assembly), the slot wiring, or the plugin's `<queries>` entries, per the plan. The plugin was checked once by hand in a scratch directory against a stubbed `expo/config-plugins`: two runs produce one `<queries>` element with VIEW intents for `sereus-join-request`, `sereus-chat` and the extra's scheme, with no duplicates; a bad `androidPackage`, a non-digit `iosAppStoreId` and a numeric `iosAppStoreId` each fail with the field named.

## For the reviewer — known gaps and judgment calls

- **`withdraw` names no party**, so it prunes only expired entries and the named scheme; other parties' entries stay until the next `approve` or matching `take` for some party. They are never returned for the running party, so this is storage tidiness only.
- **`take` writes only on a match**; a request that finds nothing leaves stale entries for the next write to prune.
- **`live` order is storage order** (latest `approve` first). Under a clock set backwards it is still "most recently approved", not "largest `approvedAtMs`".
- **The plugin validates the extras' store ids but uses them for nothing native**; they are accepted so one extras list can be shared between `app.json` and the app's own code (`storePageLink` reads them from the JS list, not from the plugin).
- **`storePageLink` URL-encodes `androidPackage`** although the plugin's form makes that a no-op; a hand-built `SereusApp` in JS is not validated.
- **`recommendedByLink` and `recommendedBySchemeFromReferrer` do not check the scheme's form.** The trust rule (look it up in the app's own list by exact equality) makes a form check redundant; the reviewer may disagree.
- **"The notice A shows when it admits an app without asking"** is named in architecture.md as a mitigation; it is A's side and lands with `reference-app-rn-recommends-an-app`.
- **Not verified on a device**: that the new `<queries>` entries make `Linking.canOpenURL('<scheme>://')` true on Android 11+, and the Play referrer round trip (encoding of `referrer=` and what `getInstallReferrer` hands back). Both are A's and B's tickets to exercise.
