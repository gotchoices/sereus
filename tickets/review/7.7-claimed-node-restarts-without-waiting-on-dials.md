# The claimed node restarts at once and keeps its owner's addresses

## What changed

A node started with a claim secret runs under a placeholder party until an owner delivers a seed carrying proof of the secret; `cadre start` then stops it and builds a new node under the claimed party (`restartIntoClaimedParty`). Two things changed:

- **`seed:applied` now means verified, merged and acknowledged.** `SeedBootstrapService.handleSeedStream` calls `onSeedApplied` right after the ack is written and the stream closed, and only then runs `dialPreferredPeers`. cadre-cli restarts on `seed:applied`, so the restart no longer waits up to 86 s per unreachable preferred peer for dials made from a node about to stop. The non-wire `applySeed` path is unchanged.
- **The claim seed's dial targets survive the restart.** New pure helper `seedDialTargets(seed, selfPeerId)` (exported with type `SeedDialTarget = Pick<SeedPeer, 'peerId' | 'multiaddrs'>`) returns the seed's preferred peers that have an address and are not self. It is the single filter used by `dialPreferredPeers`, `CadreNode.recordSeedBootstrapPeers` and the new `seed:applied` payload field `dialTargets`. cadre-cli threads `dialTargets` through `afterClaimSeedSettles` → `restartIntoClaimedParty` → `buildClaimedNode`, which records them into the claimed party's bootstrap-peer store before the node is constructed (fire-and-log on persist failure, matching `CadreNode.retainDialTarget`). The restarted node's cold-start reconcile pass (`dialColdStartBootstrap`) then dials them. `seed:error` hands on no targets.

`CadreNode.seedEventCallbacks` now records the targets **before** emitting `seed:applied` (previously after), so a listener that stops the node synchronously still finds them retained.

## Verification done

- `yarn lint` clean; cadre-core and cadre-cli `typecheck` and `build` clean.
- cadre-core unit suite: 187 files, 2540 passed, 1 skipped. cadre-cli unit suite: 25 files, 295 passed, 1 skipped.

In all three, the repeat claim and the claimant's `claimNode` resolved without error, so the ack still reaches the claimant before the stop.
- Stop-while-dialing, by inspection: `dialPreferredPeers` reads `libp2pNode` once and returns early if the service is already shut down; each per-peer dial is inside its own `try`, counted and logged; `dialAddr` (`peer-dial.ts` ~248) refuses a dial once the node's `status` is not `started` and aborts an in-flight attempt on the node's `stop` event, so `node.stop()` does not wait out the dial budget.

## Test changed

- `seed-bootstrap.spec.ts` — renamed to "acks and reports the seed applied before it dials the seed's preferred peers". It holds the receiver's one preferred-peer dial open and asserts the order `['applied 1', 'dial <addr>/p2p/<peer>']` with the dial still pending, then that the dial completes after release. Under the old order `applied` stays empty while the dial is held, so this pins the new contract. No other test added (per ticket).

## Known gaps

- **`dialTargets` and the carried store have no end-to-end coverage.** Every claim scenario's claimant is phone-shaped with no address, so the seed's targets are empty and the restarted node waits for the owner to dial in, as before. The non-empty path (an owner with an always-on machine or a relay-reachable phone) is verified only by reading the code. The ticket decided not to add a scenario for it.
- **No measured before/after timing.** The scenarios never hit the 86 s wait (no addressed targets), so the speedup is inferred from the code path, not observed.
- **Process killed between the ack and the restart** leaves `claim.json` written but the claimed party's store empty; the next start waits for the owner, as before. Accepted in the ticket; no test.
- Reviewer may want to weigh whether the self-guard in `retainDialTarget` (kept for its other callers) and the one in `seedDialTargets` overlap enough to matter; the ticket chose to keep both.
