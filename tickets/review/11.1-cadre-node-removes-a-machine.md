# Remove a machine from a cadre: review handoff

## What was built

The implement ticket's three public calls on `CadreNode`, with the supporting writes, the connection hang-up, docs and tests.

- **Types** (`types.ts`): `CadreMachine`, `MachineRemovalRefusal`, `MachineRemovalPlan`, `RemoveMachineOptions`, `MachineRemovalResult`; `CadrePeerRow` widened with `publicKey`, `updatedAt`, `profile`, `sig` (the ticket allowed widening or a sibling read; widening was chosen so one scan serves the predicate and the listing). `MachineRemovalWrites` (`control-database.ts`) is the database's part of the result.
- **Pure projections** (`machine-removal.ts`, new): `describeMachines` (the listing), `planMachineRemoval` (the plan), `revouchWithinPlan` (the "must be in `dependents`" check) and `MachineRemovalRefusedError` with `code: 'not-an-owner' | 'self' | 'last-owner'`. Kept out of `cadre-node.ts`, which has a size-debt ticket.
- **`ed25519-key.ts`**: `peerIdFromEd25519PublicKeyB64`, the inverse of the existing peer-id-to-key helper, so an `OwnerKey` row with no machine row is listed as the machine it names.
- **`ControlDatabase`**: `queryCadrePeers` reads the record columns too; `revouchOwnerKey` (one transaction: guarded delete plus tombstone of the current row, re-insert of the same key under a fresh stamp signed by the caller, as `rewritePendingJoin` re-seats a request); `removeMachine` (one transaction: `CadrePeer`, `OwnerKey`, `DeviceToken` removals with a tombstone each, plus a withdrawal tombstone per live invitation named; every stamp read inside the locked body; rows whose stamp is already retired are skipped rather than tombstoned twice; `notifyGuardedDelete` for every tombstone after commit); `withdrawCadreInvite`'s locked body factored into `signCadreInviteWithdrawals`, which the removal transaction reuses.
- **`SeedBootstrapService`**: `revouchOwner`, `removeMachine` (owner-key precondition and signing only).
- **`CadreNode`**: `listMachines`, `planMachineRemoval`, `removeMachine` (re-plan, refuse by name, check the re-vouch against the plan before any write, re-vouch first, remove, `noteControlWrite(peerId, 'remove')`, forget the dial target). The membership refresh now ends with `hangUpRevokedControlPeers`: every control connection to a peer that a `CadrePeer` tombstone names and that has no live `CadrePeer` row is hung up; never self; a failed hang-up is retried by the next refresh. The refresh's `Revocation` read is shared between the anchor sync and the hang-up through a per-refresh lazy source (`revocationSource`, the shape of `invitationChainSource`); the membership read was split into `queryCadrePeers` plus `authorizedAmong(rows, chain)` so the hang-up judges the rows the refresh already read. `removePeer` and `removeOwner` stay, their JSDoc pointing at `removeMachine`.
- **Docs**: `docs/architecture.md` has a "Removing a machine" section after the enrollment flows (what one transaction removes and why, re-vouching first, the refusals and the partition limit, connection close on evidence, what removal does not do, the `decide-removed-machine-strand-access` and `decide-owner-recovery` pointers); the `OwnerKey` and `CadrePeer` table rows, the "Deletes made while alone" tombstone list and the implementation-status API list link to it. `docs/cadre-host.md` "A host lost for good" now names Remove in the reference app and `removeMachine`. `docs/api.md` was not touched: it lists neither `addOwner` nor `removeOwner`, the ticket's skip condition.

## Deviations from the ticket, for the reviewer to weigh

- **The peer re-vouch keeps the row's `UpdatedAt`** instead of bumping it as `reissuePeerAuthorize` does. The owner branch of `CadrePeer.AuthorizedUpdate` does not require a bump, and bumping a self-published row leaves its self-signature unverifiable until the machine's next heartbeat (the NOTE on that constraint), which would make the device the owner just chose to keep unresolvable by `resolvePeerAddrs` and unlisted as self-published for up to 7.5 minutes. The write-while-alone drain bumps because it re-issues an otherwise unchanged row; here the voucher itself changes, so the write is fresh anyway. A row with `UpdatedAt` 0 gets the clock. Pinned by the unit spec (`updatedAt: dependentPublishedAt` on the kept row). Reasoned, not measured against replication: if a re-vouch that keeps `UpdatedAt` ever fails to replicate, revert to the bump for rows with no self-signature.
- **The plan lists `invitations` even when `machine` is null**: informational, and `removeMachine` short-circuits on a null machine before any write, as specified.
- **`ControlDatabase.removeMachine` repeats the owner refusals** (`target.ownerKey === ownerKey`, last live owner) inside the locked body, as `deleteOwnerKey` does, so the database refuses an inconsistent set even when called below `CadreNode`; the by-name `MachineRemovalRefusedError` is `CadreNode`'s.
- **`trusted` is false for self** in the listing (the ticket defines it as `listAuthorizedMembers` membership, which excludes self). An app wanting "is my own row sound" would need a different field.
- **`dependents.peers` also excludes this node's own row** (reported as `ownDependency` instead), not only the machine itself; the ticket's text said the machine, its `ownDependency` paragraph implied both.

## Tests

- `packages/cadre-core/test/cadre-node-remove-machine.spec.ts` (new, one real `CadreNode` whose identity key is the founding owner):
  - "removes an owner machine completely in one transaction, keeping the device it vouched by re-vouching it": an owner machine admitted through a three-use owner-granting invitation (`redeemCadreInvite`, hand-signed as the redemption protocol signs), holding a push token (the owner-signed `DeviceToken` insert `registerDeviceToken` makes) and having vouched one device (`insertCadrePeer` signed by the machine's key). Verifies the plan (`isOwner`, `removesOwnerKey`, `dependents.peers`, `invitations`, no refusal), then that `removeMachine` leaves no `CadrePeer`, `OwnerKey` or `DeviceToken` row, files one tombstone per row plus the invitation withdrawal, all signed by the remover; that the invitation reads withdrawn and a second redemption by the machine is refused (`CadreInviteUsage.Authorized`); that the dependent is the only authorized member, now vouched by the remover with `VouchUsage` null and its stamp and `UpdatedAt` unchanged; and that the listing no longer names the machine.
  - "refuses a re-vouch naming a row the machine did not vouch, before any write": an owner-only machine (`addOwner`, listed with `isMember: false`) and a bystander vouched by the founder; the call rejects and the owner row, the bystander's stamp and the tombstone list are unchanged.
- `packages/integration-tests/src/scenarios/machine-removal.integration.ts` (new): A founds and listens, M is an always-on member pinning A, B is a phone-shaped device that redeems a two-use owner-granting invitation at A, wires its key and vouches a bare peer C. `A.removeMachine(B, { revouch: { peers: [C] } })` returns the expected result; a `connection:close` event for B fired on A's control node before the call returned; A no longer authorizes B, still authorizes C, and its anchor dropped B. M, by replication alone, stops authorizing B, keeps authorizing C with `VouchOwner` = A, holds the invitation's withdrawal and drops B from its anchor at its next refresh. Measured 6 to 7.5 s per run; the removal reached M in about 0.7 s.

## Known gaps and things worth a second look

- **A removed machine that redials.** The hang-up closes the connection the remover holds; a removed node's libp2p may redial, the connection gater admits it provisionally, the protocol guard refuses its streams, and the next refresh hangs it up again. Nothing tells the removed machine it was removed or shuts it down (the NOTE in `drainPendingRevocations` names that as separate work). The integration scenario asserts the close event, not that B stays disconnected.
- **Reference apps** are not touched: no UI offers `removeMachine` yet (the reference-app tickets own that; `docs/cadre-host.md` describes the Remove button as the flow).
- **Owner re-vouch committed alone** is logged, not re-issued (`debt-owner-key-add-while-alone-has-no-reissue`), as the ticket allowed.
- **`listCadreInviteStatuses` in the plan** costs one usage count per invitation ever issued (its existing NOTE); the plan reads it once per call.
- **`ownDependency`** is surfaced only; the integration scenario does not exercise it (A's rows are founder rows).
- **Tripwire parked in code**: `hangUpRevokedControlPeers` reads tombstones on a node whose anchor is empty when it holds a connection to a peer with no row (a relay or bootstrap peer), one read per refresh; NOTE at the site says to skip it while the anchor is empty if it ever shows in the consult budget.
