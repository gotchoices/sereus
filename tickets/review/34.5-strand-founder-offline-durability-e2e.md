## The shape of the test, and why each step is where it is

Three phases, in a load-bearing order:

1. **Wait for the peer-join catch-up through the RAW BLOCK STORE only** — whole-store coverage
   (`founder ⊆ joiner`, no `include` narrowing), polled on the file's shared 15 s `GATE`. It must
   not be a `joinerDb` read: a read issued through the joiner can itself pull the block in
   (`CoordinatorRepo.get` → `restoreCorroborated` → `acquireBlockFromCohort` →
   `saveReplicatedBlock`), which would place the very bytes this step waits for. Its timeout
   message says in words that a failure here is a **catch-up** failure
   (`cadre-core/src/strand-backfill.ts`, the previous ticket's mechanism) and not an
   offline-durability failure, so a reader cannot mistake one for the other.
2. **Stop the founder, then poll the joiner down to zero strand connections.** Polled, not
   asserted once — transport teardown is not instantaneous, and one leftover connection would let
   the reads below be answered over the wire. That is exactly the trap
   `convergence-stress.integration.ts`'s disconnection scenario fell into (second caveat in
   `tickets/blocked/offline-node-cannot-serve-its-own-data.md`).
3. **Only now read `joinerDb`.** Counts on `Header`/`Member`/`Manager` ≥ 1, `Header.Type` is `'c'`,
   the founding member's key resolves by keyed equality, and the founding manager's key comes back
   from an unfiltered `Manager` scan.

The founder is never restarted; convergence-after-reconnect is deliberately out of scope.

## Honest gaps — treat these as the starting point, not the finish line

- **Only the bootstrap rows are proven durable.** `Header`, the founding `Member`, the founding
  `Manager`. A row written *after* the dial and then read with the founder gone is NOT covered. That
  is a different (and arguably more interesting) claim, and this test does not make it.
- **Zero connections is asserted for the strand libp2p node only.** The joiner's *control* node is
  not asserted down. The reasoning — self-coordination is decided per key-network, i.e. per strand
  libp2p node, so control connections can neither rescue nor contaminate a strand read — is stated
  in the test comment but is a reading of optimystic's code, not something this test measures. If a
  reviewer wants it airtight, assert the control side too and see whether it changes anything.
- **The keyed `where Key = ?` lookup is a full-PK point lookup.** The file's lookup-shape rule
  permits presence-by-equality (a miss fails rather than passes), and the test also asserts the
  same key via the scan-based `memberKeys`, so a disagreement between the two shapes surfaces as a
  failure rather than hiding. Still: if this test ever goes red on the equality alone while the
  scan agrees, that is `debt-composite-pk-point-lookup-unreliable-untracked` territory, not a
  durability defect.
- **The cold-read argument is a design choice, not a measurement.** The keyed lookup was picked
  because the bring-up gate issues only `count(1)`, so a collection-level cache could satisfy a
  repeated count from memory. Whether such a cache actually exists on this path was not
  instrumented. The block-level evidence (step 1) and the row-level result (step 3) agreeing is the
  real assurance; the shape choice is belt-and-braces.
- **This test now depends on an optimystic behaviour that is younger than the guard it bypasses.**
  If the degraded-read escape is reverted upstream, this test goes red with the
  `grace-period-not-elapsed` fingerprint owned by
  `tickets/blocked/offline-node-cannot-serve-its-own-data`. The test comment names that ticket and
  the exact error string so the next reader does not re-derive it.
- **Four runs is four runs.** The three tracked-red siblings in this file are intermittent, and
  bring-up is shared machinery. Nothing suggests the new test is flaky — 5 for 5 including the
  whole-file run — but it has not been run under load or on CI.

## What a reviewer might usefully attack

- Whether step 1's whole-store gate can pass while a block the step-3 reads need is still
  *materialized nowhere* — `compareBlockCoverage` accepts either a materialized block or a promoted
  local transaction as content, and the two nodes acquire blocks by different routes.
- Whether `founderNode.stop()` genuinely severs the strand transport rather than leaving a
  half-open connection the joiner has simply stopped counting.
- Whether the 15 s `GATE` is the right budget for the zero-connection poll, which is measuring
  teardown latency rather than convergence and shares the constant only for consistency.
