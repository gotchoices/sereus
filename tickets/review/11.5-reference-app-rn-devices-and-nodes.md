# Phone reference app: "Devices and nodes" and the removed card — review handoff

## What was built

**Settings → Devices and nodes** (`src/machines-section.tsx`), mounted below Add a device or app while connected. The doc is `docs/reference-app-rn.md` → "Devices and Nodes" (new), with "When this app is removed" under it.

- **List** from `CadreNode.listMachines`: title by profile ("App", "Always-on node", "Machine"), "(this device)"; facts "Owner", "Last seen ‹relative›" ("never" when null), "Key ‹8-char fingerprint›" (`ownerFingerprint`, else `shortPeerId`); "Not trusted here" (warning colour) for a member row that fails the predicate, never on self (core reports `trusted: false` for self); owner-only entries read "Owner key, no machine joined".
- **Pending**: live invitations targeted at a peer that is not a member, as "Invited, not joined yet" with Withdraw (the shared confirmation). Add a device or app's Outstanding list now shows **open invitations only** (`outstanding()` filters `peerId === null`), so each invitation is listed once. Add a device or app calls a new `onInvitationsChanged` prop after a mint or withdraw; Settings bumps Devices and nodes' `refreshKey`.
- **Remove** (owner devices only; standing read with `isOwnerDevice`, as Add a device or app does): reads `planMachineRemoval`, opens the prompt with what happens (owner key, invitation count), one **Keep** switch per dependent (on by default), the own-dependency line, and the "keeps whatever it already copied … this cadre's machines" line. `'last-owner'` (or any refusal in the plan) shows the reason and only Close. `plan.machine === null`, or `removeMachine` returning neither `removedPeer` nor `removedOwnerKey`, shows "Already removed" and refreshes. `MachineRemovalRefusedError` alerts with the refusal's words; other errors alert with their message.
- **Dependents are merged per machine** (`dependentsOf` in `src/machines.ts`): a device the removed machine added as an owner has both its `CadrePeer` row and its `OwnerKey` in the plan; it is one switch, so `revouchFor` never re-vouches half of it. An owner key with no dependent peer row is its own switch.
- Plan read and removal run one at a time behind a ref (`busyRef`, the `mintingRef` pattern); a read that finishes after `cadre.node` changed is dropped.

**The removed card** (Settings, Node section). `use-cadre.ts` follows the kit's status (`onPhoneNodeStatus`, new in `cadre-phone.ts`). On `removed`: runner options cleared, node dropped (stops the runner), strand selection and join flow cleared, status `idle`, error null, `removedFrom` set `{ partyId, signerKey, formerPartyId? }`, and the saved start re-read into `savedStartOptions` (former party with auto-start off, or null). `running` clears `removedFrom`. The status is also read once at mount. The card precedes the first-launch question and the Connect form: **Go back to your own cadre** (when `formerPartyId`; `returnToOwnCadre` re-reads the saved start and runs `start`), **Join a cadre** (mounts Join my existing cadre under the card), **OK** (`dismissRemoval`). Settings' Connect-form effect now also applies a null saved start once read, so the form never offers the removed party id.

**The cold-start fix** (the arm from the kit ticket's review, `repro: static`). The kit stops the node when cadre-core emits `cadre:removed`, but reports `removed` only after deleting the party's storage; a foreground return in between finds no node and the runner's `ensureNode` would start `optsRef.current`, the removed party. The hook now subscribes to the running node's `cadre:removed` and clears `optsRef` at once, and clears it again on the kit's `removed`.

**Also:** `WithdrawPrompt` moved from `add-device-section.tsx` to `settings-controls.tsx` (now shared). `docs/cadre-host.md` → "Remove, reset and a lost host" links the new section. `tickets/blocked/rn-device-run-join-existing-cadre.md` gained a row for this screen and the removed card.

## Use cases to check by reading (no device here)

- Owner app, cadre with an always-on node and a second app: three rows, Remove on two; the app's row shows Owner when invited as one.
- Remove a member app: prompt has no dependents section; after Remove the row is gone and its targeted invitations no longer appear.
- Remove an owner app that added a device as owner: one Keep switch for that device; switch it off → after Remove, the device's row shows "Not trusted here".
- Remove the only other owner while this device is the last owner: not reachable (`last-owner` applies to the machine holding the only key; this device being an owner means two keys). A member's own view has no buttons.
- This phone removed while Settings shows Devices and nodes with its prompt open: the connected view unmounts, taking the section and its modal with it.
- Removed app with `formerPartyId`: card → Go back → status connecting ("Going back to your own cadre…") → connected in its own party, card gone. Without: card → OK → first-launch question.

## Known gaps and judgement calls for the reviewer

- **No device run.** Covered by the row added to `rn-device-run-join-existing-cadre` (blocked on hardware).
- **The card is hook state.** After an app restart it is gone: the next launch shows the Connect form filled with the former party (auto-start off) or the first-launch question, without saying why. The kit keeps no record of the removal across restarts; persisting it would be a kit change.
- **OK is a third button** the ticket did not list. Without it, an app removed with no cadre of its own had no way to the first-launch question's "start fresh" short of a restart.
- **Standing vs plan.** Buttons follow `isOwnerDevice` (owner key wired and listed); the plan refuses `not-an-owner` on the enrolled signing key. If they disagree (a joined app whose owner grant has not been wired), Remove opens a prompt with the refusal and Close.
- **`returnToOwnCadre` starts whatever start is saved**, not checking it names `formerPartyId`; the kit writes that start before reporting `removed`, so they agree.
- **A live targeted invitation for a machine already in the cadre is listed nowhere** (`NOTE:` at `pendingDeviceInvitations`); removing that machine withdraws it.
- **Two modals in one moment** (the prompt closing as Settings' alert opens) follow the existing sections' pattern and its iOS `NOTE:` in AddNodeSection.
- **"Last seen" is computed against the time of the last read**, not a ticking clock; it refreshes with the list.
