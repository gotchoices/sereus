# `network.announceAddrs`: upstream request filed, dead setting now honest

## What shipped

`NetworkConfig.announceAddrs` was settable in `cadre.yaml`, via `CADRE_ANNOUNCE_ADDRS`, and through
the Docker entrypoint, and was read by nobody — silently. Unlike `relayAddrs` (fixed by
`cadre-relay-addrs-wiring`), there is no way to implement this inside this repo: libp2p only takes
announce addresses at construction (`addresses.announce` / `addresses.appendAnnounce`), and
`@optimystic/db-p2p`'s `NodeOptions`/`createLibp2pNodeBase` has no field for either and builds
`addresses: { listen }` with no escape hatch. Reaching libp2p's `AddressManager` post-construction
is not public API.

Two things landed:

1. **Upstream request filed, untracked.** `../optimystic/tickets/fix/announce-addrs-option.md` —
   asks for `announceAddrs?: string[]` / `appendAnnounceAddrs?: string[]` on `NodeOptions`, forwarded
   into the `addresses` object `createLibp2pNodeBase` assembles. Pure additive forwarding of stock
   `@libp2p/interface` address-manager options. **Not committed** — that repo's working tree has
   unrelated in-flight changes; the file is untracked and needs a human or that repo's own tess
   runner to pick it up.
2. **The field stopped lying.** `CadreNode.start()` (`packages/cadre-core/src/cadre-node.ts`, right
   after the `_running` guard, before the try block) now does:

   ```ts
   if (this.config.network?.announceAddrs && this.config.network.announceAddrs.length > 0) {
     console.warn(
       'network.announceAddrs is set but not yet supported (no upstream db-p2p option to apply it) ' +
       '— this node will keep advertising its listen/relay addresses instead.'
     );
   }
   ```

   Warns, does not throw — an operator who set this in a Docker env file already has a running node,
   and turning silent-drop into a boot failure would be a worse outcome. Fires once per `start()`
   call when the array is non-empty; silent when unset or `[]`.

   `NetworkConfig.announceAddrs`'s doc comment (`types.ts`) now says plainly: accepted, not yet
   applied, why (no upstream `db-p2p` option), what to use instead today (`relayAddrs` for
   reachability behind NAT, `inviteAddressResolver` for invite-payload substitution — neither of
   which touches what a node advertises on the wire via identify/DHT/relay, which is the actual gap).
   Same correction in `packages/cadre-cli/example.cadre.yaml`'s commented example and
   `docs/architecture.md`'s `CadreNodeConfig.network` block.

## What to check in review

- **The warning condition.** Truthy-and-non-empty on `this.config.network?.announceAddrs`; confirm
  it can't double-fire (it's a single `if` before the `try`, not inside a retry path) and that
  `stop()` + `start()` again would re-warn correctly (expected — every `start()` call re-checks
  current config).
- **`console.warn` as the mechanism.** This is the first `console.*` call in `cadre-core`'s `src/`
  (everything else uses the `debug` package, which is opt-in via `DEBUG=` and easy for an operator to
  never see). Chosen deliberately because this is a boot-time operator warning, not a diagnostic
  trace, and `console.warn` is already the house pattern for exactly this in `cadre-cli` and
  `reference-app-rn`. Worth a second opinion on whether cadre-core (a library, not just the CLI)
  should own a `console.*` call at all, vs. e.g. emitting a `CadreNodeEvents` entry the CLI listens
  for — went with the simpler direct warn since the ticket asked for "one line" and no existing event
  channel fits without inventing one for a single field.
- **Upstream ticket accuracy.** `../optimystic/tickets/fix/announce-addrs-option.md` — verify the
  `NodeOptions`/`addresses` assembly quoted still matches `libp2p-node-base.ts:138` and `:477-482` at
  review time (that repo has its own in-flight edits).
- **Doc comment cross-references.** `types.ts`'s new `announceAddrs` doc comment links
  `{@link relayAddrs}` and names `inviteAddressResolver` — both are fields on the same
  `NetworkConfig` interface; confirm the names didn't drift.

## Test coverage (floor, not ceiling)

local `start()`/`stop()` cycle (no bootstrap peers, no mocking) with `console.warn` spied:
`announceAddrs` set (non-empty) → warns once, message contains `network.announceAddrs`; unset →
silent; explicit `[]` → silent. Each test carries the existing suite's 30s timeout for a full
node lifecycle (matches `cadre-node.spec.ts`'s pattern).

**Not covered, and out of scope for this ticket:** anything about the setting actually working —
there is nothing to test, since nothing applies it yet. That lands with the upstream change; ticket
body already says the follow-up (`buildControlNodeOptions` spread, `strand-instance-manager` spread,
deleting the warning) is deliberately not filed until the `@optimystic/db-p2p` dependency range here
actually moves (`scripts/check-dep-ranges.mjs`, `test:dep-ranges` gate).
