# Phone reference app asks the owner app by link (joining side): review handoff

The joining app's half of the same-phone join. **B** is this app, joining; **A** the owner app it opens. Kit: `@serfab/cadre-rn/app-link` (`phone-kit-same-phone-join-links`). Owner side and link routing: `reference-app-rn-answers-join-requests-by-link`.

## What was built

- **`src/use-link-request.ts`** (new): the hook part behind the button, composed into `useJoinFlow` so `useCadre()` exposes it (`JoinFlowActions extends LinkRequestActions`). State `linkRequest` (read from the store at mount) and `linkRequestReturned`. Actions:
  - `askOwnerApp(app | null)`: `linkRequests.begin`, builds the request with `reply: { scheme: ownScheme(), nonce }`, opens it (`openOwnerApp`). Returns false with the request cancelled when the system would not open it; throws, with the request cancelled, when the request could not be built. After opening, the state is read back from the store rather than set, because on Android B may have been picked and its own request may already have cancelled it.
  - `cancelLinkRequest()`, `linkRequestCameBack()` (cancel + set the came-back flag).
  - `takeJoinResponse(text)`: never throws; returns a `JoinResponseOutcome` (`joined`, `join-failed`, `refused`, `join-under-way`, `unsolicited`, `unreadable`). A join on screen → not taken, request left open. An invitation runs the existing `joinExistingCadre`. Logs only error messages (a decode error's cause can quote the text).
- **`src/cadre-phone.ts`**: `linkRequests` (the one `LinkRequestStore` over `phone.linkRequestSlot()`), `ownScheme()`, `extraSereusApps()` (validates `extra.sereusApps`; malformed → `[]`, logged), `joinRequestText(reply?)`, and a re-export of `UnsolicitedJoinResponseError` (the hook reaches the kit only through this module, which the react spec mocks).
- **`src/join-link.ts`**: `openOwnerApp` (never throws; logs with the request body cut, as the answer side already did for responses — `withoutResponseText` generalized to `withoutLinkText`), `installedOwnerApps` (iOS list), `joinResponseAlert(outcome)` with the refusal table, `COPY_REQUEST_LINE`.
- **`src/join-cadre-section.tsx`**: above the request, **Choose the app that holds your cadre**; Android opens with `null` (system chooser), iOS opens an inline list of installed apps (empty-list line), then the waiting line ("…for the app you chose…" on Android) with **Cancel**, or the came-back line. Paste inputs stay below. Test ids added in `test-ids.ts`.
- **`app/settings.tsx`**: `useLinkedJoinResponse` reads and clears `joinResponse`, holds it until the launch read is done and no plain start is connecting, then calls `takeJoinResponse` and shows the alert from Settings. The owner-side own-request alert in `useLinkedJoinRequest` is replaced by `linkRequestCameBack`.
- **`app.config.ts`** (new) + **`app.json`**: the kit plugin entry moved out of `app.json` into `app.config.ts`, which appends it with `appLinks.extraApps` and sets `extra.sereusApps` from one list (`[{ name: 'Sereus P2P Chat (second)', scheme: 'sereus-chat-second' }]`). `APP_VARIANT=second` sets that name and scheme and suffixes `ios.bundleIdentifier` / `android.package` with `.second`. **`eas.json`**: profile `development-second`.
- **Docs**: `docs/reference-app-rn.md` → "Joining an Existing Cadre" (new "Choose the app that holds your cadre" paragraph and bullets; "Request and response" second, as the fallback), new "Open link request (app-private LevelDB)" storage section (the kit review deferred `link-join-request` to this ticket), "Device test runs" → "A second install for one phone", the own-request bullet under "Adding a Device or App", the `app.json` → `app.config.ts` mentions, the file listing. `docs/architecture.md` → both paragraphs named in the ticket. README → "A second install on one phone".
- **Blocked ticket filed**: `tickets/blocked/rn-device-run-same-phone-join-by-link.md` with the ticket's rows plus relaunch-while-waiting and Android "Always".

## Deviations from the ticket (reviewer, please judge)

- **`app.config.ts`, not `.js`**: typed against `expo/config` (`ConfigContext`, `ExpoConfig`); Expo evaluates it with sucrase. The kit plugin now lives only there, so `app.json` alone no longer carries it.
- **A separate `use-link-request.ts`** instead of growing `use-join-flow.ts` (300 lines) further; it is composed inside `useJoinFlow`, so nothing in `use-cadre.ts` changed.
- **`askOwnerApp` resolves false instead of throwing** when the app cannot be opened (opening failure is an expected outcome; the section alerts "Could not open ‹app›" with the copy line).
- **The answer is held until the start settles.** The plan relied on the kit queuing the join behind the auto-start (`inTurn`). That is true in the kit, but the hook's `start` would then mark the app `connected` with the node the join is about to stop, after `joinExistingCadre` had already called `holdNoNode`. Holding the answer in Settings while `savedStartRead === 'reading'` or a plain start is `connecting` avoids that.
- **Alert wording**: an answer that does not decode (or a saved request that cannot be read) says "This app could not take this answer" with the error as detail, rather than reusing the unsolicited wording; `already-member` omits "You can still copy this app's request into it", since that app answers a copied request the same way.
- **The came-back line** stays until the next **Choose** (it is hook state, not saved), rather than literally showing once.

## Found while implementing (documented, not code)

- **A development build reads its config from the dev server's manifest** (expo-constants prefers the dev launcher's manifest over the embedded one). So each install needs its own dev server started with its own `APP_VARIANT` (the second on another port). With one dev server, the second install would name the main app's scheme in its reply, A would answer the main app, and the main app would refuse it as unsolicited (safe, but confusing). Documented in the README, the device-run doc and the blocked ticket.
- Both installs share the slug, so the dev client's `exp+sereus-p2p-chat` scheme and the `sereus-join` node-code scheme are registered twice (Android shows a chooser for those too). README says to open the second from its icon or `sereus-chat-second://expo-development-client/?url=…`.

## How to check it

- `npx expo config --type public` from `packages/reference-app-rn`, with and without `APP_VARIANT=second`: name, scheme, ids, the kit plugin's `appLinks.extraApps` and `extra.sereusApps` as above (checked). `--type introspect` with the variant shows `LSApplicationQueriesSchemes` `sereus-chat`, `sereus-chat-second` and the Android `<queries>` entry for `sereus-join-request` (checked).

## Tests

None added. The hook actions map kit results to UI states and words; the kit's `LinkRequestStore` tests pin the security contract (nonce, once, 30 minutes), and delivery needs a device. The react spec (`test/react/use-cadre.spec.ts`) needed two mock additions because `useJoinFlow` now reads the store at mount and imports `join-link.ts` (which loads `react-native`): `linkRequests.current` on the `cadre-phone` mock, and a `join-link` mock; `vitest.config.ts`'s comment lists the new mock.

## Known gaps

- Nothing here has run on a device (the blocked ticket).
- The waiting line reads the open request at mount and after each action; it does not notice the 30-minute expiry by itself until the next read (a launch, an answer, or a Choose).
- While the answer is held for a start that never settles (a start hanging in `connecting`), it is not taken; the kit's start ends by succeeding or failing, so this was not guarded further.
