# Strand removal e2e and docs — review handoff

Third and last ticket of the plan `removal-must-cut-the-network-not-just-the-row`. The
gate (`strand-revoked-peer-gate`) and the teardown sweep (`strand-revocation-teardown`)
had shipped but were asserted only against stubs. This ticket asserts the whole claim
against real libp2p nodes, real strand databases and real replication, and then rewrites
`docs/strands.md` so an app author can word a "remove member" button honestly — which was
the original issue (gotchoices/sereus#4).

## What shipped

**`strand-removal-cuts-network.integration.ts`** (new, 3 tests, ~60 s wall clock).
Built on the `bootTopology` + `joinStrandOn` shape of
`strand-membership-second-machine.integration.ts` rather than the hand-rolled two-node
bring-up of `strand-membership-closed-strand-e2e.integration.ts` — the multi-machine
scenarios need parties with more than one machine, which is what the topology builder is
for. All the reference file's idioms are kept: scan-and-filter reads (never a full-PK
seek), `waitUntil` gates that throw, distinct per-party member keys via `consumeInvite`,
real strand peer ids via `registerMemberPeer`, and the rejected write last.

1. *hangs up every machine of the removed party, only on a machine that has seen the
   removal* — 2 parties × 2 machines, one closed strand. Covers the plan's scenarios 1, 2
   and 4 in one bring-up, because they are phases of one story and each needs the last
   one's state. Asserts, in order: all four cross-party connections exist BEFORE the
   revocation; after `revokeMember` + an awaited `refreshRevocationEnforcement` on a[0],
   a[0] holds no connection to EITHER of the removed party's machines; a[1], which has not
   refreshed, still holds both (the fail-open arm, asserted deliberately); a[1] then sees
   the removal in its own database and cuts too; the remaining cohort commits a write that
   a[1] reads back; neither removed machine converges on it; and the removed party's own
   post-cut write never reaches either remaining machine.
2. *tells a removed node it was removed, on its own poll* — 2 parties × 1 machine. The
   removed node's `strand:revoked` arrives with NO explicit refresh anywhere, which is the
   only place the interval-driven route is exercised. Also asserts the remaining party is
   NOT told (the signal is about this node's own peer id, not about removals generally),
   and that nothing is torn down on the removed node's behalf — it still holds its session
   until the other side acts.
3. *leaves an open strand alone* — two nodes running one open strand and one closed strand
   at once. A removal on the closed strand cuts there while the open strand's connection
   and its stranger's writes carry on.

**Harness**: `revocationPollMs` added to `ControlNodeOpts` (`node-fixtures.ts`) and
`TopologyMachineSpec` (`topology.ts`), forwarded to
`CadreNodeConfig.strandRevocationEnforcement.pollIntervalMs`. Purely additive, same shape
as the existing `strandWatchMs` / `reconcileMs` knobs. It is what makes the timing above
deterministic instead of racy: a machine set to a poll longer than the test never
refreshes on its own, so every cut is attributable to the one machine the test refreshed.

**Docs.** `docs/strands.md` → "Removing Members" gained three sub-sections — what removal
does to the network, what the app has to call and what the removed party is told, and what
removal still does not do — plus a rewritten device-records bullet saying that clearing an
orphan now also forgets the network denial. The stale "Relay willingness" deferred bullet
(the durable `MemberPeer` attestation "waits for strand-mesh admission control") is now
split into the landed revocation half and the still-deferred admission half.
`docs/architecture.md`'s `revokeMember` writer bullet cross-references it;
`docs/testing.md`'s scenario map gained the new scenario and names its relay gap.

**One comment change in source**: the `NOTE:` at `tearDownRevoked` in
`strand-revocation-enforcer.ts` said post-removal commit latency was hypothetical. It is
not — see the measurement below. No code changed in `cadre-core`.

## Findings from the implementation, stated honestly

**The plan's cohort-eviction tripwire fired, and it recovers.** The remaining cohort's
FIRST write after a cut fails repeatedly before it commits — measured at 4 failed attempts
with `BlockUnavailableError: Block default/Data is unavailable (peers-unreachable)`,
committing on the fifth at ~4.1 s, reproduced identically across two runs. The cohort
still lists the removed party's now-unreachable machines and has to downsize to the live
holders first. It is a latency cost, not the `cluster-fetch:no-quorum` stall the ticket
said to stop and report: nothing was worked around, the test uses a bounded retry with the
failure mode spelled out, and the number is now recorded in three places — the budget
constant's doc, the `NOTE:` at `tearDownRevoked`, and `docs/strands.md`, where an app
author will actually meet it. **Worth a reviewer's second opinion on whether "expect a
brief wobble" is an acceptable product answer** or whether the remaining cohort should
converge faster; that would be an upstream (Optimystic) conversation, not a change here.

**Known gap — the relay-mediated variant is not covered.** Every connection under test is
DIRECT. A removed party reached over `/p2p-circuit` is the strongest form of test 1, and
`hangUp` closing a RELAYED connection (and dropping the relay reservation riding it) is
still asserted only against a stub — exactly the hole the teardown ticket's review deferred
here. Staging it needs the relay-only two-party fixture of
`blind-relay-phone-to-phone-e2e.integration.ts` (a dedicated relay, `listenAddrs: []` on
both ends, a bound invitation and formation over the circuit), which is a second topology
rather than an option on this one — not cheap, so per the ticket it is reported rather than
forced. Named in the new file's header and in `docs/testing.md`. No ticket filed: the
ticket's own instruction was to note the gap in this handoff.

**Scenario 3's "no enforcer armed on the open strand" is asserted indirectly, by choice.**
Whether an enforcer object exists is not observable through any public API —
`refreshRevocationEnforcement` is deliberately quiet for an unarmed strand and for an
unknown one alike, so the two cannot be told apart. The test asserts the two observable
consequences instead: an open strand can hold no deny record AT ALL (`Strand.Member` is
closed-only, and `MemberPeer.MemberExists` refuses a binding with no member behind it, so
`registerMemberPeer` rejects), and its connections and writes survive a closed-strand
removal in the same two processes. The test comment says this in as many words. A reviewer
who disagrees should say what a stronger assertion would look like without widening the
public API.

**Tripwire recorded, not ticketed**: the four negative assertions in test 1 run
sequentially and each spends its full 10 s budget — ~40 s of that test's ~52 s is this
wait. Fine at four; parked as a `NOTE:` at `NO_CONVERGENCE_BUDGET_MS` saying to run them
concurrently (they are read-only polls) if more negative arms are ever added, rather than
shortening the budget, which is the claim itself.

**Fixture honesty is stated three times on purpose** — the file header, and one comment at
each `registerMemberPeer` site. Production writes no `MemberPeer` rows today, so none of
this enforcement is reachable from an app until `feat-strand-party-identity` lands. The
docs say the same thing as the FIRST item under "what removal still does not do", because
a reader who takes the guarantee at face value and ships a "remove member" button today
would ship a button that does nothing.

## What a reviewer should push on

- **The negative assertions.** `expectNeverConverges` conflates "read failed" with "row
  never arrived" — deliberately, and the header argues why (both are the cut). Each is
  paired with a positive control read on a machine that is NOT cut, taken from the same
  write, so a stalled strand fails the control instead of passing as a cut. Check that
  pairing holds at every call site; it is the whole load-bearing structure.
- **The fail-open arm.** Test 1 suspends a[1]'s poll rather than genuinely racing
  replication, so it proves "a machine that has not PROCESSED the removal still serves"
  rather than "a machine that has not RECEIVED it". The distinction matters and is not
  called out as sharply in the test as it is here.
- **Whether the 2×2 shape hides anything.** The removed party's two machines stay connected
  to EACH OTHER after the cut (their bindings are orphaned, but a node does not hang itself
  up and neither machine has refreshed against the other). Nothing asserts that either way.
  It is correct behaviour as far as the enforcer's doc goes, but it is unasserted.
- **The docs' voice.** Three new sub-headings under "Removing Members" is the biggest
  structural change that section has had; check it still reads as one document.
