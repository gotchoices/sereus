# Review: `Strand.MemberPeer` cleanup after a member is removed

## What the problem was

`Strand.MemberPeer` binds a member's devices (libp2p peer ids) to that member. Removing a
member did not remove those bindings — nothing cascades — and only the member itself could
sign a delete. So a manager removing someone had no way to clear that person's device
records, and the person being removed had no reason to cooperate.

Two comments in the codebase also claimed a `MemberPeer` delete was rejected outright by the
schema. That was false: `MemberExists` was written as a bare `check (...)`, which in Quereus
carries an implicit `insert|update` mask and never runs on DELETE at all. `Authorized`
already declared `on insert, update, delete`, so deletes were genuinely signature-checked
against the member's own key. Both comments have been replaced with what is actually true.

## What was built

**Schema** (`schemas/strand.qsql` + the mirrored `STRAND_SCHEMA`, character-identical — the
drift guard compares verbatim):

- `MemberExists` now states its mask explicitly (`check on insert, update`). Behavior is
  unchanged; the mask was already implicit. Stating it removes the trap that made two
  readers conclude the opposite.
- `Authorized` gains a second branch: a `committed.Manager` row matching `context.ManagerKey`
  may delete ANY member's binding, verifying a remove-tagged digest
  `digest('Strand.MemberPeer', 'remove', old.MemberKey, old.PeerId)` against
  `context.ManagerSignature`. Gated to DELETE via `new.MemberKey is null`.
- The context tuple widens from `(Signature)` to `(Signature, ManagerKey, ManagerSignature)`.
- A table-level `NOTE` says a `MemberPeer` row can outlive its `Member` row, and that any
  consumer treating one as evidence of membership must join to `Member`.

**Writer** (`packages/cadre-core/src/strand-membership-writer.ts`):

- `signStrandMemberPeerRemoval(memberKey, peerId, privateKeyB64)` — the manager's
  remove-tagged signature, same variadic tagged-digest idiom as `signStrandMemberAction`.
- `removeMemberPeer(db, params)` where params is a discriminated union:
  `{ memberKeyPair, peerId }` (self) or `{ managerKeyPair, memberKey, peerId }` (manager).
  It narrows on `'memberKeyPair' in params` and delegates to `deleteOwnMemberPeer` /
  `deleteMemberPeerByManager`.
- Delete-if-present + post-delete re-verify, both via the existing `memberPeerExists` scan.
- All three exports plus the three param types added to `packages/cadre-core/src/index.ts`.

**Deliberate design choices worth a reviewer's scrutiny:**

- The manager branch is NOT gated on the member already being gone. A manager may clear a
  still-present member's binding, matching "any manager can remove any member". Pinned by
  its own test.
- The authorizer is read from `committed.Manager` (the pre-transaction snapshot), matching
  `Member.Authorized`. Adding the subquery converts `Authorized` from an immediate to a
  deferred check (Quereus auto-defers any CHECK containing a subquery), so a manager seated
  in the same transaction would otherwise be able to authorize its own cleanup.
- Peer cleanup is an explicit follow-up call, NOT a cascade inside `revokeMember`. Clearing
  an unbounded number of peer rows inside the revocation transaction would couple two
  concerns and muddy the revocation's failure modes.
- The self branch's removal payload is deliberately the SAME untagged
  `MemberKey || '|' || PeerId` that registration signs. A member CAN present its own
  registration signature to delete its own binding — same principal, own row, harmless. Only
  the MANAGER branch is replay-narrowed.

## Test coverage added

`packages/cadre-core/test/strand-membership-peer-rotation.spec.ts`, new
`describe('removeMemberPeer')` — all against a real closed strand
(`connectToStrand` bootstrap mode, real DML + deferred-constraint path, not a fake):

- a member deletes its own binding (pins the behavior the old comments denied)
- a stranger cannot delete another member's binding — two routes: through the writer's
  manager branch (no `Manager` row), and raw against the self branch (right payload shape,
  wrong signing key)
- peer rows survive their member's revocation as orphans, and the manager-signed cleanup
  clears them
- a manager may clear a STILL-PRESENT member's binding
- a register-peer signature cannot be replayed as a manager remove-peer signature, AND the
  properly tagged signature from the same manager over the same row succeeds (so the
  rejection is provably the tagging, not something incidental)
- removing one peer leaves siblings intact
- removing an absent binding is a quiet no-op, on both branches

Also updated: the stale "immediate `Authorized` check" comment in the existing
`registerMemberPeer` rejection test now says deferred.

## Known gaps — please probe these

- **The post-delete re-verify is untested.** `removeMemberPeer` re-runs `memberPeerExists`
  after the delete and throws if the row survives. The hazard it guards is real (the delete's
  `where` puts an equality on BOTH composite-PK columns, the shape the optimystic vtab module
  serves via a single-key seek that can miss on a networked strand — see `memberPeerExists`'
  own doc, and backlog `debt-composite-pk-point-lookup-unreliable-untracked`), but a seek miss
  cannot be provoked in bootstrap mode, so no test covers the throw path. The failure it
  converts is availability (a silent zero-row "success"), never security — a miss removes
  nothing, it can never over-remove.
- **No integration-test coverage of removal.** The closed-strand e2e scenario
  (`strand-membership-closed-strand-e2e.integration.ts`) had its `with context` clause widened
  to keep compiling, but no removal step was added to it. All new coverage is component-level.
- **No test asserts a same-transaction manager cannot authorize its own cleanup.** The
  `committed.Manager` choice is argued from parity with `Member.Authorized` (which IS pinned,
  by `strand-member-revocation.spec.ts`) rather than pinned here directly. Worth adding if the
  reviewer wants the property nailed down at this table.
- **Nothing verifies the manager branch cannot delete via UPDATE.** The branch is gated
  `new.MemberKey is null`, which an update never satisfies — but that is reasoned, not tested.
- **The stale-comment claim was not re-measured this run.** That a bare `check (...)` skips
  DELETE comes from `../quereus/docs/sql-ddl.md:303` and from the prior run's live
  measurement against a real strand. The new tests are consistent with it (a self-signed
  delete succeeds), but no test isolates `MemberExists`' mask on its own.

## Review findings

- **Tripwire — the `MemberPeer`-outlives-`Member` invariant.** Parked as the table-level
  `NOTE` on `MemberPeer` in both schema copies. Nothing in the runtime reads `MemberPeer` for
  authorization today (`StrandMemberRegistry.isMember` resolves against `Strand.Member`, and
  `strand-addr-protocol.ts:26` explicitly excludes peer-record resolution), so orphan rows are
  inert. The moment a reader starts trusting a `MemberPeer` row on its own, they become an
  access-control hole — hence the NOTE at the table, where such a reader will meet it.
- **Tripwire — the composite-PK point-lookup hazard on the delete path.** Parked as a `NOTE`
  at the re-verify guard in `removeMemberPeer`, citing backlog
  `debt-composite-pk-point-lookup-unreliable-untracked`.
