# Tests for the React Native reference app's node-local durable stores

The implementation half (`2.2-rn-durable-node-local-stores`) landed in a prior
pass; this ticket adds the missing test coverage, runs lint, and fixes one
stale doc comment. No production code was redesigned — `node-local-slots.ts`
and `secure-key-store.ts` are unchanged from what landed before.

New file `packages/reference-app-rn/test/node-local-slots.spec.ts` (26 tests),
modeled on the sibling web spec
(`packages/reference-app-web/test/node-local-slots.spec.ts`) and on the
existing `FakeSecureStore` double in `test/secure-key-store.spec.ts`:

- **`secureStoreSlot`** — save→load round trip through a fake
  `expo-secure-store` (statelessness proven via a second slot instance over the
  same fake), never-written key ⇒ `undefined`, a failing read rejects (does NOT
  resolve `undefined`), a failing write rejects, forwarded options match
  exactly what was given (no stray `requireAuthentication`) on both the read
  and write path, and construction throws for a gated
  (`requireAuthentication: true`) slot.
- **`kvStoreSlot`** — the same four round-trip/absent/read-rejects/write-rejects
  cases against a fake `KvStoreApi`.
- **Key-shape helpers** (persistence contracts — renaming one silently orphans
  every installed phone's anchor/dial targets) — `anchorSlotKey` stays under
  its own `sereus.anchor.` prefix, never the key store's `sereus.ks.`, and is
  SecureStore-key-safe even for a party id with `/`/`+`; `bootstrapPeersKvKey`
  is pinned to `'bootstrap-peers.<id>'`; `NODE_LOCAL_DB_NAME` and
  `NODE_LOCAL_KV_PREFIX` are pinned.
- **The two node-local stores over a real slot** —
  `PersistentTrustedOwnerStore` over `secureStoreSlot`,
  `PersistentBootstrapPeerStore` over `kvStoreSlot`: each round-trips through a
  fresh `open()` of the same fake; the anchor's persisted `source` is asserted
  by parsing the raw envelope text out of the fake (the store's public surface
  only exposes keys); junk text and a foreign-`partyId` envelope both
  cold-start empty without throwing; a failing read makes `open()` **reject**
  (not cold-start) and leaves the fake's backing map untouched; a failing
  persist rejects `trust()`/`record()` but the in-memory decision still stands
  (`has()`/`all()` reflect it).

Per the ticket's scope note, the node-local *store policy* itself (corrupt
JSON handling, foreign-partyId detection, discard-all vs drop-entry, envelope
versioning) is NOT re-asserted here — it's covered once in
`packages/cadre-core/test/node-local-snapshot.spec.ts`. The peer-id fixture
used for the bootstrap-peer round trip is a hardcoded real Ed25519 peer id
(`12D3KooWQVo7JTYHgoj9rt9HScoxaM5axn3uB8P1WHiKrhhUqed3`, generated for this
purpose) rather than a `@libp2p/crypto`/`@libp2p/peer-id` devDependency, per
the ticket's guidance.

`packages/cadre-core/src/types.ts` — the `bootstrapPeers` doc comment (~line
399) no longer claims React Native and the browser are ephemeral; it now says
only NativeScript is, and keeps the "supply a `DurableSlot` + inject
`PersistentBootstrapPeerStore.open(slot, partyId)`" recipe for a new platform.

## For the review handoff, state plainly

- **End-to-end survival across an app relaunch is NOT delivered by this work
  alone**, and this ticket does not change that. Both records are
  party-scoped, and the app does not persist `opts.partyId` across launches —
  it's typed into Settings each time (see the comment in `push-wake-native.ts`).
  With a fresh party id per launch, both slots load empty every time. Backlog
  ticket `feat-rn-persist-node-start-options` closes that gap; until it lands,
  the durable stores are correct but not observable on device across a
  relaunch.
- **Nothing here ran on a device or under the Expo e2e harness** — coverage is
  unit-level against fakes, same as the web sibling ticket. The real
  `AFTER_FIRST_UNLOCK` value at the `cadre-phone.ts` call site is not
  unit-covered (that module imports the native `expo-secure-store`, so it's
  outside a Node vitest graph); what the new tests pin is that
  `secureStoreSlot` forwards whatever options it's given, ungated. The single
  shared `SECURE_STORE_OPTIONS` const in `cadre-phone.ts` (not touched by this
  ticket) is what actually keeps the anchor and the identity slot from
  drifting apart.
- **The LevelDB handle lifetime** (`nodeLocalDb ??=` open in `startPhoneNode`,
  `finally`-closed in `stopPhoneNode`) is reasoned-about in the module
  comments, not device-verified — no test in this suite opens a real LevelDB
  handle or exercises `startPhoneNode`/`stopPhoneNode`.
- Followed the web sibling's precedent
  (`tickets/complete/2.1-web-durable-node-local-stores-tests.md`) closely for
  test shape and scope boundary; worth a quick sanity check that the two specs
  stayed in sync rather than silently diverging.
