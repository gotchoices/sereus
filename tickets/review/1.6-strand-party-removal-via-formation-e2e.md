# Review: removal cuts the network on a strand formed the ordinary way

Final ticket of the party-identity chain (`strand-party-member-key` → `strand-formation-membership-invite` → `strand-node-binds-member-peer` → this). The enforcement machinery and its proof already existed; what was missing was a proof standing on rows **production** wrote rather than rows the test hand-registered, plus the documentation correction that goes with it.

## What landed

**New scenario — `packages/integration-tests/src/scenarios/strand-party-removal-via-formation-e2e.integration.ts`** (its own vitest file, ~90 s for both tests together, no dependency on any other scenario file).

*Test 1, "the journey"* — host party × 2 machines, joiner party × 2 machines, one closed strand.

- The host founds and publishes the strand, arms itself as a formation responder (`initializeStrandSolicitation` with a `ControlFormationUsageRecorder`), and publishes an open invitation **bound** to that strand. Its second machine reads the published `Strand` row and the party's `StrandPartyKey` row off its own control network and attaches with them — nothing hand-fed.
- The joiner redeems over the real handshake (`CadreNode.formStrand`). Asserted on the result: the strand's shared read key matches the published row, a `membershipInvite` is present, the host's live strand addresses came back, and the invitation is staged in `getPendingMembershipInvite`.
- The joiner's node minted and persisted its **own** party identity, distinct from both the founder's identity and from the identity derivable from the shared read key (all three compared).
- Its second machine gets the strand the ordinary way for a party's second machine: the joiner's owner publishes the row into its own party's control database and the sibling reads it back.
- The membership assertions, which are the point of the ticket: exactly two `Strand.Member` rows (founder party key, joiner party key) visible on all four machines, and exactly four `Strand.MemberPeer` bindings — each machine bound to its own party's key, asserted as an exact set on the founder's replica. The staged invitation then disappears on its own (the reconciler clears it once spent).
- **Neither `issueInvite`, `consumeInvite` nor `registerMemberPeer` appears anywhere in the file.** That absence is the assertion; a reviewer can check it with one grep.
- Removal: `revokeMember` with the founder party keypair, then `refreshRevocationEnforcement`. Both of the joiner's machines are hung up by the host machine that refreshed; the second host machine cuts once the tombstone is visible in its own database. The joiner's device records survive the removal as orphans (asserted) — those orphaned rows are what the denial is derived from.
- Aftermath: the remaining cohort still commits (with the measured retry wobble — 2-3 failed attempts over 3.7-6.8 s across runs), the remaining machine reads that write, and the removed party neither converges on it nor pushes anything back to either remaining machine (gotchoices/sereus#4).
- Closing arm, new to this file: a removed party's **own** machines also stop talking to each other. Each sees its sibling's binding as an orphan, so after an explicit refresh `join[0]` cuts `join[1]`. Run last, because it takes the removed party's local mesh apart.

*Test 2, "re-joining after removal"* — host × 2 machines, joiner × 1.

- After the cut, a fresh bound invitation is published and redeemed successfully: formation runs over the **control** network, which strand revocation does not gate. The party's identity is reused rather than re-minted (`queryStrandPartyKey` unchanged), and a fresh, different invitation is staged.
- The invitation cannot be spent. Seating the member row is a strand write, and the machines that would carry it are exactly the ones being denied. Pinned with a bounded quiet window: the member key is still absent from the host's replica and the connection is still cut.
- The heal that does work: a remaining manager admits the key directly (`addMemberByManager`), which makes the leftover device records valid again; after `refreshRevocationEnforcement` on both host machines the dial is accepted and a fresh host write reaches the re-admitted party.

**Harness** — `ControlNodeOpts.membershipReconciliation` widened from `false` to `false | { pollIntervalMs }`, forwarded through `TopologyMachineSpec`. Needed because the membership reconciler mirrors `revocationPollMs` when unset, so the existing "suspend the revocation poll so every cut is attributable" discipline would otherwise also suspend the loop that writes the rows under test. Purely additive: unset behaves exactly as before, and `false` still disarms.

**Docs corrected** (the other half of the ticket):

- `docs/strands.md` → "What removal still does not do": the first bullet no longer says the journey is unproven. It now says removal is reachable from an app end to end, names the scenario, and states the real remaining gap — a removed party cannot bring itself back.
- `docs/strands.md` → "What removal does to the network": new bullet on a removed party's own machines refusing each other, with what that means for an app keeping the strand as a local archive.
- `docs/strands.md` → the two places that said a removed party "still re-admits itself" on an unspent invitation. That is true of the membership rules and false at the network layer; both now say so and say not to rely on the cut instead of cancelling.
- `docs/testing.md` → new coverage-map entry for the scenario, and the removal-cuts-network entry now points at it for the production-written-rows version of the same claims.
- `docs/architecture.md`, `docs/strand-contracts.md`, `docs/strand-contracts-review.md`, `packages/quereus-plugin-sereus/src/cluster-size.ts` → the retired `feat-strand-party-identity` slug repointed to the surviving `feat-strand-party-diverse-placement` / `feat-strand-member-allowlist-admission`, or replaced with "landed" plus the scenario path, per site. `cluster-size.ts` also stopped calling a cross-party mesh "undiscoverable" — the formation seed is an automatic path, as `docs/architecture.md` already said.
- `strand-removal-cuts-network.integration.ts` → its FIXTURE HONESTY block now says the hand registrations are a fixture shortcut rather than a missing mechanism, names the new file, and says what that file keeps that the new one does not (the stale-view arm, the interval-driven self-revocation signal, the open-strand isolation case).

**Filed** — `tickets/backlog/bug-removed-party-cannot-redeem-its-way-back.md` (`repro: verified`, severity edge-case, likelihood unusual): re-inviting a removed party succeeds and then silently achieves nothing. Two candidate fixes are laid out (make the dead end diagnosable; or admit a machine presenting a valid unspent invitation) and the second is cross-referenced from `feat-strand-member-allowlist-admission`, which records the same chicken-and-egg shape for a first join under a stricter admission policy.

**Appended, not re-filed** — a fourth arm on `debt-hoist-strand-read-helpers-integration` recording the copies this file adds (`memberKeys` ×4, `GATE` ×6, `insertWithRetry`/`rowLanded` ×3, the `expect`-based connection helpers ×2, `SIMPLE_SCHEMA` ×14 — counted, not estimated) and naming the one new helper worth hoisting with the family (`memberPeerBindings`, which returns `MemberKey|PeerId` pairs rather than peer ids alone).

The one grep that checks the central claim:


It should find nothing. Every `Strand.Member` and `Strand.MemberPeer` row the file asserts was written by the runtime.

## Known gaps — please treat these as the starting point

- **The full integration suite was NOT re-run.** Eight scenario files were: the new one, `strand-removal-cuts-network`, `strand-membership-closed-strand-e2e`, `harness-topology`, `strand-formation-cross-party-seed`, `strand-formation-e2e`, `strand-membership-second-machine`, `blind-relay-phone-to-phone-e2e` — all green. The harness change touches `controlNodeConfig`, which nearly every integration scenario calls, so the remaining ~45 files rest on the change being additive (unset behaves as before) and on a clean repo-wide typecheck, not on a run. The 10-minute per-command cap made a single full-suite run impossible; splitting it was judged not worth the budget at implement stage. This is the most likely place for a surprise.
- **The strand mesh is hand-dialed.** Only `join[0] → host[0]` is proved to come from the formation seed; every other pair is wired by an explicit dial (`meshStrandNodes`, which skips pairs already connected). That is deliberate — cross-party discovery is `strand-formation-cross-party-seed`'s subject — but it does mean this file does not show that a four-machine two-party strand meshes itself.
- **Test 2's negative arm is a bounded quiet window (8 s), not a proof of impossibility.** It pins observed behaviour. If the design later admits invitation-holders (the second option in the filed bug), this assertion flips and should be rewritten to the new behaviour, not weakened or deleted.
- **The re-admission heal needs an explicit re-dial.** After the manager re-admits and both host machines refresh, the test dials `join[0] → host[0]` rather than waiting for libp2p to retry on its own. Whether the connection would return unaided, and how fast, is untested.
- **A re-admitted party's second staged invitation is never burned.** The joiner's reconciler stopped as "done" during the first join, so nothing consumes or burns the invitation staged by the second formation; it sits in memory until the process exits or the strand is relaunched. Not asserted either way, and it does not affect the test's claims — but it is a real loose end for anyone implementing the filed bug.
- **`formStrandWithRetry` retries the whole handshake** on `MEMBERSHIP_INVITE_UNAVAILABLE_REASON`, relying on the documented guarantee that the one-time token is still unspent when the responder rejects for that reason. Observed working (attempt 2 succeeded, ~4 s). If issuance ever moves after `recordUsage`, this helper loops until its budget instead of failing usefully.
- **Every connection under test is direct.** The relay-mediated cut — a removed party reached over `/p2p-circuit`, where `hangUp` must also drop the reservation — remains asserted only against a stub, exactly as `strand-removal-cuts-network` records. Unchanged by this ticket.
- **Timings are single-run measurements on one loopback machine.** The post-cut write wobble (2-3 attempts, 3.7-6.8 s) and the formation retry (1-2 attempts) were seen across three runs, not benchmarked.
- **`strand-removal-cuts-network` was edited for comments only.** Its behaviour is unchanged and it still passes 3/3; worth confirming the comment edits did not overstate what the new file covers.
