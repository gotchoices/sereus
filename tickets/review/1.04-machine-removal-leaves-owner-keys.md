# Machine removal leaves owner keys; owner-key removal gets the re-vouch plan

## What changed

**Machine removal** (`machine-removal.ts`, `CadreNode.listMachines` / `planMachineRemoval` / `removeMachine(peerId)`):

- `CadreMachine` lost `isOwner` and `isMember`. With the owner-only entries gone, every entry is a live `CadrePeer` row, so `isMember` was always true. `publicKey` stays: it is the machine's identity key, which the apps show as a fingerprint.
- `MachineRemovalPlan` is `{ machine, refusal, invitations }`. `RemoveMachineOptions` is gone. `MachineRemovalResult` is `{ removedPeer, removedDeviceToken, withdrawnInvitations }`.
- `MachineRemovalRefusal` is `not-an-owner | self`; `last-owner` left machine removal. The `self` reason is restated: leaving a cadre is the embedder's flow, and the removal notice is built around another machine removing you.
- `ControlDatabase.removeMachine(target: { peerId, inviteKeys }, …)` removes the `CadrePeer` and `DeviceToken` rows and withdraws the invitations, a tombstone each. It no longer has an `OwnerKey` arm, and its owner refusals went with it. The `MachineRemovalWrites` alias (a public export) is deleted; the method returns `MachineRemovalResult`.
- `CadreNode.removeMachine` no longer opens its own approval. It calls the seed service, which opens one ("Remove the machine … from the cadre").

**Owner-key removal** (`owner-keys.ts`, `CadreNode.planOwnerKeyRemoval(key)` / `removeOwner(key, { revouch? })`):

- `planOwnerKeyRemoval` (pure) returns `OwnerKeyRemovalPlan { ownerKey: CadreOwnerKey | null, refusal, dependents: { owners, peers }, ownDependency }`. `dependents` and `ownDependency` are computed as the old machine plan computed them, keyed by the owner key.
- Refusals are checked in this order: `not-an-owner`, `unknown`, `last-owner`, `self`. `last-owner` comes before `self` on purpose. When this node is enrolled and the target is a different live key, a single read always shows at least two owners, so `last-owner` can only be reached by a sole owner targeting its own key. Checking it first gives that owner the rule no other owner could get past either.
- `removeOwner` re-plans and throws `OwnerKeyRemovalRefusedError` on a planned refusal. It then runs `revouchWithinPlan`, moved here from `machine-removal.ts`, which throws a plain `Error` before any write when the re-vouch names a row outside the plan. Next it refuses `alone` when `revouch.owners` is non-empty and `ownerKeyWriteAlone()` is true. Finally it re-vouches and removes under one `approve`. The approval text names the label when the key has one (`namedOwnerKey`, shared with the seed service's `addOwner`).
- `OwnerKeyRemovalRefusal` = `not-an-owner | unknown | last-owner | self | alone`. The plan's type excludes `alone`, which is decided at call time.
- `removeOwner` now returns `OwnerKeyRemovalResult { removed, revouched }` instead of `boolean`, and throws `unknown` instead of returning `false` for a key with no live row. `removed: false` now means only that another owner's removal landed between the plan and the write.
- `refuseOwnerKeyWriteAlone(key)` became `ownerKeyWriteAlone(): Promise<boolean>`, shared by `addOwner` (which still throws `OwnerKeyAddRefusedError`) and `removeOwner`.

**Other**

- `peerIdFromEd25519PublicKeyB64` is deleted from `ed25519-key.ts`. Only specs used it; they now use `peerIdOf(kp)` in `test/control-constraint-helpers.ts`.
- The comments in `drainPendingRevocations` were restated: a removed machine stops its drains because it is no longer a member, not because its key went.
- Reference apps (RN and web): the machine prompt no longer has keep-switches, the "its owner key is removed too" line, the `ownDependency` line or the `last-owner` refusal. The list no longer shows the "Owner" fact or "Owner key, no machine joined" rows. `removeMachine(peerId)` takes one argument in `cadre-phone.ts` and `use-cadre.ts`.
- The RN switch helpers (`dependentsOf`, `revouchFor`) and `test/machines.spec.ts` are deleted, along with the RN `keepDependentSwitch` test id. Their one-switch merge of a peer row with "the owner key behind its peer id" only worked while owner keys were derived from machine identities. `implement/1.09` and `1.10` carry a note that this is done and that the owner-key prompt's switches are written fresh.

## Found on the way

**A removal that races the machine's own publish fails.** At first the rewritten scenario failed 3 times out of 3 in `removeMachine`, with `ConcurrentModificationError` on B's `CadrePeer` row. B's first self-published record (with a `Sig`, `UpdatedAt` 2.6 s later) committed between A's read and A's commit. `isRetriableControlWriteFailure` does not cover that error, so it is not retried.

The race predates this ticket: the old scenario's re-vouch happened to give B's publish time to land first. The scenario now waits for `registerSelf() !== 'skipped'` before removing B, the convention `docs/testing.md` sets for scenarios. The production defect (an owner write on a machine's row racing that machine's own publish fails rather than retrying) is filed as `backlog/bug-owner-write-racing-a-machines-own-publish-fails`, at the retry classifier.

## For the reviewer: gaps and judgment calls

- **One peer-id-to-key derivation remains in `machine-removal.ts`.** The ticket asked for none to be left. `describeMachines` still derives the machine's identity key from its peer id, to check the row's self-signature and to fill `CadreMachine.publicKey`. That is the machine's own key, not an owner key, and it is the same check `resolvePeerAddrs` makes. Removing it would mean trusting `row.publicKey` unverified. Every owner-related derivation is gone.
- **A peer re-vouch made while alone is not refused.** The doc comment (inherited) says the existing drain re-issues such a re-touch. I did not verify that. `revouchDependents` does not call `noteControlWrite`, and the first-growth sweep re-touches only rows with no `Sig`. So a re-vouched row that the machine itself had published (it has a `Sig`) and that committed alone may not be re-issued. This is unchanged from before; worth a look.
- **The anchor keeps an owner key it has already derived.** I first asserted that an owner dependent that is not kept becomes untrusted, and it does not: `passStartSet` keeps an anchor entry derived through a chain while that key's own row is live. That is the documented design ("An owner that a removed owner had added keeps its place wherever it was already derived"). The new "Re-vouching first" text says so instead of "stops passing on every machine" for `OwnerKey` rows.
- **API breaks, with no shims (per the no-backwards-compat rule):** `CadreMachine.isOwner` and `isMember`, the `MachineRemovalPlan` and `MachineRemovalResult` fields, `RemoveMachineOptions`, the `MachineRemovalWrites` export, `removeOwner`'s return type and its `unknown` throw, `ControlDatabase.removeMachine`'s target, and `peerIdFromEd25519PublicKeyB64`.
- **Not covered by a test:**
  - The `not-an-owner` refusal for both plans.
  - Machine removal's `self` refusal.
  - The re-vouch failure that stops the removal partway.
  - `removeOwner`'s `removed: false` race.
  - The new approval text: checked by reading the code.
- **App wording.** The RN prompt still shows "To remove this device, use another owner device." The lost-device line and button pointing at Owner keys are 1.09 / 1.10's (they need the owner-key section). Until those land, the apps give no way to remove an owner key.

## Use cases to exercise

- A lost phone that held an owner key: remove its machine. It is hung up and its invitations are withdrawn, but its owner key still authorizes, so the phone could mint a fresh invitation and come back. `removeOwner(key, { revouch })` then locks it out, keeping the devices that key added that the user chose.
- A sole owner tries to remove its own key: `last-owner`. With two owners: `self`. A key that was never an owner, or one removed elsewhere: `unknown`.
- An owner phone offline in a cadre with an always-on node: `removeOwner(k, { revouch: { owners: [k2] } })` is refused `alone` with nothing written. Without the owner re-vouch, the removal commits alone and its tombstone is re-issued on growth.
- A machine removed while it holds no owner key: same as before, minus the owner arm.
