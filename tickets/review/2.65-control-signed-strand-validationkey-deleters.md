# Review: signed `deleteStrand` / `deleteValidationKey` writers on `ControlDatabase`

Closes the gap the prior ticket (`control-validationkey-strand-delete-authorization`, review
notes in `dfe8910`) flagged explicitly: the schema now *requires* an owner signature plus a
matching `Revocation` tombstone to delete a `Strand` or `ValidationKey` row, but nothing in
production code could produce that pair — only raw-SQL test helpers exercised the rule. This
ticket adds the two real writers.

## What landed

Two new methods on `ControlDatabase` (`packages/cadre-core/src/control-database.ts`), plus two
small query helpers they depend on:

- `queryStrandStampId(strandId)` / `queryValidationKeyStampId(key)` — read a row's current
  `StampId` nonce, `null` if the row doesn't exist. Mirrors the existing
  `queryCadrePeerStampId`.
- `deleteStrand(strandId, ownerKey, signMessage)` / `deleteValidationKey(key, ownerKey,
  signMessage)` — the actual signed deleters:
  1. Look up the row's current `StampId`. If the row is already gone, log and return —
     **no-op, no throw, no tombstone.**
  2. Build the `'remove'`-tagged authorization message via `buildAuthorizationMessage` over
     `(Id, StampId)` for `Strand` / `(Key, StampId)` for `ValidationKey` — distinct from the
     `'add'` digest, so an enrollment approval can never be replayed as a removal.
  3. `beginTransaction` → signed `delete ... with context OwnerKey, Signature` → insert the
     matching `CadreControl.Revocation` tombstone (`TableName` = `'Strand'` / `'ValidationKey'`)
     → `commit`. Same rollback-swallow-on-failed-commit pattern as
     `SeedBootstrapService.removePeer` (`seed-bootstrap.ts:460`) and `redeemInvitation`.
- `queryRevokedStamps`'s `tableName` parameter widened from `'OwnerKey' | 'CadrePeer'` to
  include `'ValidationKey' | 'Strand'` (the type already allowed rows tagged that way in
  `Revocation`; only the TS signature was narrower than the schema).

## New tests (`packages/cadre-core/test/control-authorization-binding.spec.ts`, appended to the
existing describe block, six new `it`s + two helpers)

Two new helpers next to the existing `inviteCount`: `revocationCount()` (total row count) and
`revocationRow(tableName, stampId)` (fetch one tombstone row, `undefined` if absent).

- **Happy path, both tables** — a correctly owner-signed delete removes the row *and* leaves a
  matching `Revocation` tombstone (checked via `revocationRow`).
- **Missing-row no-op, both tables** — deleting a nonexistent `Strand` / `ValidationKey` resolves
  without throwing and leaves the `Revocation` count unchanged (`revocationCount()` before/after).
- **`queryRevokedStamps` integration** — after `deleteStrand`, `queryRevokedStamps('Strand')`
  contains the retired stamp.
- **Closed-strand delete** — deleting a closed strand carrying a real `MemberPrivateKey`
  succeeds, confirming the remove digest binds only `(Id, StampId)` and ignores `Type` /
  `MemberPrivateKey` (so it works identically for open and closed strands).

## Use cases the reviewer should exercise

All six are real tests in `control-authorization-binding.spec.ts` (search
`deleteValidationKey with a correct owner signature`); confirm each proves what its name claims:

- Signed delete of an existing row → row gone, tombstone present, `queryRevokedStamps` sees it.
- Delete of a row that was never there → silent no-op, zero side effects (this is the "party
  never even tried" case — e.g. a stale local cache asking to remove something already retired
  elsewhere).
- Closed strand with a populated `MemberPrivateKey` deletes cleanly (digest doesn't choke on the
  extra field).

The schema-level negative cases (unsigned delete refused, tombstone-less delete refused, replay
after removal refused, wrong-table tombstone refused) were already covered by the prereq ticket's
review pass in `control-revocation-replay.spec.ts` — this ticket doesn't duplicate them, it only
adds coverage for the new writer functions themselves.

## Known gaps — treat the tests as a floor

- **Still no production *caller*.** `deleteStrand` / `deleteValidationKey` exist and are
  exercised by tests, but nothing in the CLI, host, or `CadreNode` invokes them yet — confirmed
  by grep, zero hits outside `control-database.ts` and the test file. In particular
  `CadreNode.removeStrand` (`cadre-node.ts:2809`) was **deliberately left untouched**: it still
  only untracks hibernation, drops the local sApp config, and stops the strand instance — it
  never touches the `Strand` table or calls the new `deleteStrand`. Whether/how to wire an
  owner-approved network-wide delete into that path (and where the `signMessage` callback and
  owner-approval UX would come from — no such flow exists yet) is a real product decision, not
  mechanical follow-up, so it was left out of scope rather than guessed at here.
- **No concurrent-delete test.** Like `insertStrand`/`insertValidationKey`, nothing exercises two
  concurrent deletes racing the same row (e.g. two owner devices both signing a remove for the
  same `StampId` around the same time). Existing insert-side tests don't cover this either, so
  it's not a regression — just unproven ground, same shape as the rest of this file.
- **Root-level `yarn lint`/`yarn build`/full workspace `yarn test` not re-run** this pass (see
  validation table above) — only the scoped `cadre-core` commands. Nothing in this diff touches
  other packages, so risk is low, but the reviewer may want the full pass for certainty.
