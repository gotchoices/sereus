Third ticket of the `strand-offline-mode` chain, in `@serfab/cadre-core`. It builds on `strand-offline-composition` (`offlineControllerOf(db)`) and `strand-offline-cadre-core` (the per-strand queue on a cadre node).

## What landed

- **`StrandOfflineQueueBusyError`** (`strand-membership-writer.ts`, exported, carries `transactionIds`).
  - `execStrandTransaction` calls `refuseBehindOfflineQueue(db)` before anything runs. When `offlineControllerOf(db)?.entries()` is non-empty, the writer throws and writes nothing. `entries()` also lists the journaled transactions a restore has not put back yet.
  - The check applies to every writer and every option, including a writer joining an app transaction.
  - The racy-by-nature `NOTE:` tripwire sits on `refuseBehindOfflineQueue`.
- **`issueInvite` and `cancelInvite` now go through `execStrandTransaction`.** They were the only two writers calling `db.exec` directly, so without this they would have bypassed the guard. Their parameters became named (`:managerKey`, …). Semantics are unchanged: a single statement either way, and it still joins an open app transaction by default. The `cancelInvite` doc sentence about auto-commit was updated.
- **Reconciler** (`strand-membership-reconciler.ts`):
  - `isTransactionBusy` now matches either busy error anywhere in the cause chain, so a queue refusal classifies as `busy`: the invitation is kept and the pass retries on the ladder.
  - The two `busy` log lines now print the error message instead of saying "the app has a transaction open". The reconciler spec's assertion on that text now matches `/redeeming the staged invitation deferred/`.
  - Module doc ("Sharing the database with the app") covers the queue refusal and `OfflineCommitTimeoutError`.
  - I confirmed `OfflineCommitTimeoutError` retries: a redemption classifies it as `retry` and keeps the invitation; a binding write throws into `doPass`'s outer catch, and `scheduleNext` runs in `finally`.
- **Unpublish binding cleanup** (`clearOwnMemberPeerBinding`): no code change. Its existing catch-and-log already handles the queue refusal the way it handles the busy one; the comment and JSDoc now say so.
- **Leaving a strand.**
  - `CadreNode.forgetJoinedStrand(strandId, options?)` and `unpublishStrand(strandId, options?)` take `StrandLeaveOptions { discardQueued?: boolean }` (`strand-offline.ts`, exported). Both call `settleQueueBeforeLeave`.
  - A non-empty queue without the option throws `StrandQueueNotEmptyError` (exported; carries `strandId` and `transactionIds`), and nothing is left.
  - With the option, `discardQueuedForLeave` discards from the live queue. If there is no live queue, it calls `wakeStrand` and tries again.
  - `discardQueued()` in `strand-offline.ts` keeps `EntryNotDiscardableError` ids, skips `UnknownEntryError` (settled meanwhile, or cascaded), and rethrows anything else.
  - Kept ids produce one `console.warn` and the leave goes on. A wake that builds no database produces a different warning naming every id.
- **Queue lookup** (`StrandInstanceManager.queuedTransactionIds`):
  - Uses the live database's queue (published or gated), else `closedQueues`, else `[]`.
  - `closedQueues` is filled by `rememberQueue` in `releaseRuntime` just before each database closes, and deleted in `stopStrand`.
  - `StrandDatabase.queuedTransactionIds()` and `discardQueuedTransactions()` don't require `initialize` to have finished, and return `undefined` when the database has no queue.
  - `liveDatabase()` was extracted; `setOfflineMode` uses it too.
  - The `NOTE:` for "a strand this process never built a database for" is on `queuedTransactionIds`.
- **Docs.**
  - `docs/strands.md` → "On a cadre node" has two new subsections: "Membership writes are refused while transactions are queued" and "Leaving a strand with unsent transactions". The second also covers `stopStrand`, a strand moved between cadres, and self-revocation.
  - The bullet in "Membership tables are always acknowledged by the network" that named this ticket now links to the first subsection.
  - `docs/api.md`'s `forgetJoinedStrand` signature and text cover the option.

## Where this differs from the ticket text (review these)

- **The hibernating-strand check uses `entries()` saved at database close, not the last `strand:queue-state` depth.** The depth is the db-core queue's `list.length`, which leaves out journaled records a restore has not put back yet. It also carries no ids, and `StrandQueueNotEmptyError` needs them. A journal does not change while the strand has no database, so the value saved at close stays exact. As a result, no per-strand state from events is kept.
- **`issueInvite` and `cancelInvite` were rerouted** (see above). The ticket put the check only in `execStrandTransaction`, which these two did not call.
- **The discard runs before the control-plane write, not after it.** The order is: refuse or discard, then the approval and the control-plane delete. A leave refused after the discard (the signer is not an enrolled owner, or the user declines the approval) leaves the transactions discarded. The JSDoc and the doc say so. The alternative, discarding after the delete, would wake the strand after its control row is gone, and the watcher may detach it concurrently.
- **A wake that throws propagates.** Nothing has been left at that point. A wake that resolves but builds no database (awaiting a seed peer) discards nothing, warns, and the leave goes on, so the leave is not blocked forever.
- **Self-revocation does not stop the strand** (the ticket said it does). `forgetRevokedJoin` keeps it running for the session (`strand:revoked`). The doc line says that, and that the queued transactions cannot land.

## Use cases to check

- An app transaction queued in offline mode, then `issueInvite`, `revokeMember`, `leaveStrand`, etc. on that strand: `StrandOfflineQueueBusyError`, with nothing written and no wait. The same inside `db.beginTransaction()`: refused, and the app's transaction is still open and commits.
- The reconciler on a joiner with a queued app transaction: the pass logs "deferred — nothing was tried", keeps the invitation, and retries on the ladder.
- `unpublishStrand` or `forgetJoinedStrand` with a queue: `StrandQueueNotEmptyError`, and the row is still there. With `{ discardQueued: true }`: the queue is discarded, the never-sent transactions fail with reason `discarded`, and the strand is removed.
- A hibernating strand with a queue: refused without waking (status stays `hibernating`). With `discardQueued` it is woken, the restored queue is discarded, and then it is removed.

## How this was checked

A throwaway spec, run and then deleted, used a solo founder `CadreNode` with a Map-backed journal and `initialMode: 'offline'`.

- **The real guard, without stubs.** Straight after an offline `insert`, the transaction was `submitting`. An `issueInvite` at that moment was refused with `StrandOfflineQueueBusyError` naming that real transaction id.
- **With `entries`/`discard` stubbed on the live controller:**
  - The writer guard refused inside an open app transaction, and the app transaction still committed.
  - `classifyConsumeFailure` returned `busy`.
  - `unpublishStrand` threw `StrandQueueNotEmptyError` and the row survived. With `discardQueued`, one id threw `EntryNotDiscardableError`: it was warned about alone, and the strand was removed.
  - A hibernated strand was refused while still `hibernating`. With `discardQueued` it woke on a fresh, empty queue, logged no warning, and was removed.

Not covered by anything that ran:

- `forgetJoinedStrand`. It runs the same `settleQueueBeforeLeave` as `unpublishStrand`.
- A real non-discardable entry (in doubt) on a real cohort.
- The wake that builds no database.
- The race in which an `OfflineCommitTimeoutError` reaches the reconciler.

## Tests

No new tests, per the ticket: each guard is a short check on state that upstream computes.

The ten existing specs whose inline `StrandDatabase` fake already had `reportPublished` each gained `queuedTransactionIds: () => undefined`, because `releaseRuntime` now calls it before every close. ## Tripwires added

- `refuseBehindOfflineQueue` (`strand-membership-writer.ts`): the check and the write are not atomic. If a frozen strand database is ever traced to a membership write that slipped past it, hold the app's writes during membership commits instead.
- `StrandInstanceManager.queuedTransactionIds`: a strand this process never built a database for reads as empty, though its journal may hold transactions. If leaves like that show up, read the journal there.
- `StrandDatabase.initialize`, at the founder bootstrap: a bootstrap with rows to write while `hydrate` restored transactions would be refused on every build, and the queue could never drain. This is not reachable today, because an incomplete founding fails the build before publication. If that ever changes, skip the bootstrap while the queue is non-empty.
