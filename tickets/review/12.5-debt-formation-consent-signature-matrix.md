# Joiner-consent signature: schema-level negative matrix (implemented)

Tests only — no `src/` change. All six phases of the implement ticket landed.

## What a joining peer signs, and why two signatures exist

When a peer joins, its own row in `CadreControl.FormationUsage` carries its public key
(`PeerKey`) and its own signature (`PeerSig`). Two different signatures exist over that
one table and must never be usable in each other's place:

| digest | tag | fields, in order | signed by |
|---|---|---|---|
| vouch | `'vouch'` | token, usageStampId, strandId, peerKey, disclosure | the approver (an enrolled `ValidationKey`) |
| consent | `'consent'` | token, usageStampId, peerKey, disclosure | the joining peer itself |

`strandId` is deliberately absent from the consent digest — the joiner cannot know the
strand when it signs. The schema constraint `PeerConsented` re-verifies the consent
signature on every insert; `Authorized` re-verifies the approver's vouch.

## How every rejection stays a single-constraint assertion

`PeerConsented` is `check on insert` with no subquery, so it fires AT the insert.
`Authorized` is also `check on insert` but contains a subquery, so Quereus auto-defers it to
commit. When both would fail, `PeerConsented` surfaces — and `expectConstraintFailure`
matches ONE name. So:

- `PeerConsented` cases pre-insert an owner-signed strand and call `recordFormationUsage`
  (never `redeemInvitation`) on an invite with NO `ValidationUrl` — that satisfies
  `StrandExists` and disarms `Authorized`'s vouch branch.
- `Authorized` cases supply a consent signature valid over the row's ACTUAL fields, so
  `PeerConsented` passes and only the vouch verify is left to fail.

A reviewer disputing any case should check that arrangement first: a case that could be
refused by two constraints is a bug in the test, not a stronger test.

- **The full cadre-core suite was NOT run.** The budget warning landed right after the
  targeted runs. Three spec files were touched and all three pass; nothing else imports the
  new file, and the only cross-file edit is a deletion from a spec that still passes. Still,
  a whole-suite run is the first thing to do here.
- **The one-field-isolation claim is argued, not mutation-tested.** The comment on the
  one-field-mutation block asserts that dropping any single field from both sides of the
  consent digest turns exactly one case red. That property was reasoned from the case
  construction, not verified by actually deleting a field from `formationConsentMessage` and
  the SQL and re-running. The sibling claim in `control-formation-invite.spec.ts` says it WAS
  verified by mutation; mine has not been. Worth an actual mutation pass, or soften the
  comment.
- **Nonce-collision case depends on writer behaviour.** `refuses a SPENT nonce re-presented
  verbatim` relies on `recordFormationUsage` deriving `UseNumber` 2 for the replay, so the
  `(Token, UseNumber)` primary key does not collide first and `UsageStampId`'s `unique` is
  what answers. If that derivation ever changes, the case would flip to a PK violation and go
  red on the message, not silently green — but re-pin the single error the engine emits
  rather than widening the match.
- **`verifyFormationConsent` garbage cases pass rows built from a landed row.** Each garbage
  case mutates one field of a real stored row rather than constructing a wholly synthetic
  one, so a verifier that ignored the OTHER fields entirely would not be caught by them (the
  all-empty-string case is the one exception).
- **No end-to-end / documentation work here.** That is sibling ticket
  `debt-formation-consent-e2e-docs`, unchanged by this ticket.
