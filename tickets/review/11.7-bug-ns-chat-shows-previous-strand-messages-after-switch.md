# NS chat view model applied the previous strand's results after a switch — review handoff

## What changed

`ChatViewModel` (`packages/reference-app-ns/src/chat-vm.ts`) now follows two rules, mirroring the RN hook `packages/reference-app-rn/src/use-chat.ts`:

- **Results belong to the strand instance they were read from.** `refresh()` checks `this.strand !== strand` after its `await`: a stale result is dropped before `setMessages`, `settlePendingDraft`, `setParticipantCount` or `setError`. A stale error is logged with `console.warn` rather than shown. `finally` always clears `readsInFlight` for that strand, and clears `loading` only when that strand is still attached. The check compares instances, as `readsInFlight` does, so a late read from a replaced instance of the same strand is also dropped.
- **The list belongs to the strand id it shows.** `attach()` computes `switched` from `strandId` (including to or from no strand) and calls the new `clearConversation()`, which empties `_messages`, sets the participant count to 0 through `setParticipantCount` (so `statusText` notifies), clears the poll error, and sets `loading` back to true. `start()` calls `refresh()` straight after `attach()`, and `refresh()` clears `loading` again when there is no database, so switching to no strand does not leave the screen stuck in loading. A reconnect that replaces the instance of the same strand keeps the list, so it does not flash empty.
- **`send()`**: once `insertMessage` resolves, the draft is still cleared and `pendingDraft` retired regardless of strand. The row append and the poll-error clear run only if `strand` is still attached; otherwise `send` returns early, and the `finally` still resets `sending`.

The rules are stated in the doc comment on `attach()` and in a comment in `refresh()`.

**RN side (included, trivial):** `use-chat.ts` `send` now returns right after `sender.send(...)` if `strandRef.current !== s`. That skips the optimistic append, the re-read on the "already stored" path, and `setError(null)`, all of which apply to the list now showing a different strand. `ChatSender` still records the draft's outcome itself, so the composer behaves as before.

## Decisions a reviewer might question

- **The composer is not reset on switch** (decided in the fix stage). A send that settles after a switch still clears the draft and retires the retry key, or shows "Not confirmed sent". Consequence: a resend after an uncertain failure on strand A, made once attached to B, stores the message in B under the same id (at most one row per strand). Acceptable because the NS app runs a single strand.
- **`send()` also gates `setError('')`**, not only the append. The ticket said to gate only the append, but `_error` is the poll error of the attached strand, and a successful insert on A says nothing about reads of B. `_sendError` (the composer's error) is still cleared regardless of strand.
- **A stale read error is logged, not dropped silently.** RN drops it silently. The project rule in AGENTS.md ("don't eat exceptions without at least logging") decided it.

## Tests (`packages/reference-app-ns/test/chat-vm.spec.ts`)

Harness additions: `ScriptedDatabase.seedMessage(content)` writes a message from another participant straight into the real table, and a module-level `shown(vm)` helper returns the list's message texts. `ObservableArray` does not compare as an array under `toEqual`.

- `the poll › reads a strand it re-attached to at once, and drops the late read of the old one` (was `…, without waiting on the old one`; its placeholder comment pointing at this bug has been removed). It seeds A and B, holds A's list read, and re-attaches to B. It asserts that B's list shows, then releases A's read and asserts that the list still shows only B. Before the fix this failed with `["from a"]`.
- `the poll › clears the list the moment it re-attaches to no strand` loads a strand with one message, removes it from the node, calls `start()`, and asserts the list is empty right away. Before the fix this failed with `expected 1 to be +0`.

Both were confirmed failing before the fix and passing after. The `send` arm (NS and RN) has no test: the ticket judged that a one-line identity guard did not justify a held insert plus a switch.
