Second of the `strand-offline-mode` chain, in `@serfab/cadre-core`. It sits on `strand-offline-composition` (the plugin's `offline` option, controller and `appSchema` outcome). The guards for membership writers and for leaving a strand are the next ticket, `strand-offline-cadre-guards`.

## What landed

- **`strand-offline.ts` (new).** `StrandOfflineConfig` (`journal: (scope) => IKVStore | Promise<IKVStore>`, `initialMode?`), `StrandOfflineMode`, `StrandOfflineQueue` (the controller's nine app-facing members, without `enter`/`exit`/`isEntered`), `StrandAppSchemaState`, the event payload types, `StrandOfflineListeners`, `StrandOfflineUnavailableError`, `isSendingStatus`, and `StrandOfflineReport`. The report class holds one database's queue subscriptions and its app-schema state, and emits the publication-time events.
- **`CadreNodeConfig.strandOffline`.** When it is absent, nothing changes and no strand gets `offline`. The control database is untouched.
- **`StartStrandConfig.offline`** (`StrandOfflineConfig & StrandOfflineListeners`), which `CadreNode` fills from its config plus its emit callbacks. `StrandDatabaseConfig.offline` (`StrandDatabaseOffline`) has a journal thunk, a `mode()` reader and the listeners.
- **Mode map.** `StrandInstanceManager.offlineModes` is never cleared. `offlineMode(strandId)` returns the last mode set, else the launch's `initialMode`, else `'online'`, and throws for an untracked strand. `setOfflineMode` throws for an untracked strand, records the mode, and calls `applyOfflineMode()` on the live database: the published one, or the one still behind the first-sync gate.
- **`StrandDatabase`.** `initialize` resolves the journal, passes `offline: { journal }` to `connectToStrand`, starts `StrandOfflineReport` right after the connect returns, and calls `applyOfflineMode()` after the founder bootstrap and before returning (so before the first-sync probe). It also has `get offline()`, `appSchemaState()` and `reportPublished()`. `close()` releases the report and the queue first.
- **`publishDatabase`** calls `database.reportPublished()`. That emits `strand:queue-state` with the current `queueState()`, plus `strand:app-schema-deferred` if the apply is still waiting, or the failure if a retry already failed.
- **`CadreNode`.** `setStrandOfflineMode` throws `StrandOfflineUnavailableError` when `strandOffline` is not configured, then delegates. `getStrandOfflineMode` returns `'online'` when unconfigured. New events: `strand:offline-status`, `strand:queue-state`, `strand:app-schema-deferred` and `strand:app-schema-applied`. A failed retry is emitted as `strand:error`. `handleOfflineStatus` calls `hibernationManager.recordActivity` for each sending status.
- **Exports.** The new error, the types, and `StrandDatabaseOffline`.
- **Docs.** `docs/strands.md` → "Offline mode" has a new "On a cadre node" subsection covering configuration, the per-strand mode, what the app reads, first sync, sending as activity, and the app schema held back. "A commit's durability" has an *In offline mode* sub-paragraph on the `undefined` case. "Change notifications (reactivity)" has an *In offline mode* paragraph. `docs/architecture.md` got a pointer paragraph in "Reactive Strand Management" and one sentence in "Strand Hibernation".

## Where this differs from the ticket text (review these)

- **The journal is resolved inside `StrandDatabase.initialize`, not in `buildStrandDatabase`.** Awaiting it in `buildStrandDatabase` would come before the first-sync gate is registered. A `stopStrand` during that await would then find no gate to close, and the build would carry on against a released runtime. The existing check after `initialize` (the registered gate is no longer this build's) already covers anything awaited inside it, so `StrandDatabaseOffline.journal` is a thunk.
- **No activity is recorded on a strand that is being quiesced.** `HibernationManager.recordActivity` wakes a quiescing strand once the quiesce ends. A `committed` status arriving between a `hibernateAll` (the app going to the background) and the database close would bring the strand straight back up. The ticket already counted mid-send closes as safe, so I skip recording activity in that window (`CadreNode.handleOfflineStatus`).
- **The app-schema events start at publication.** A retry that lands while the database is still behind the first-sync gate is not announced, because the app never saw the earlier schema. A retry that fails then is announced at publication. The ticket said "at publication" only for the deferred event, so this choice was mine.
- **`getStrandOfflineMode` throws for an unknown strand** (the ticket did not say), and returns `'online'` on an unconfigured node.
- **`StrandOfflineQueue` leaves out `isEntered`.** The ticket's list leaves it out, and the mode is read through `getStrandOfflineMode` or `queueState().mode`.

## How to check it

Two throwaway specs were run and then deleted:

- A solo founder `CadreNode` with a `Map`-backed journal and `initialMode: 'offline'`:
  - `getStrandOfflineMode` read `'offline'` and `offline.queueState().mode` was `'offline'` after `addStrand`.
  - The journal was called once per build (once at launch, once more after hibernate and wake).
  - An `insert … returning StampId() as Tx` produced `queued`, then `submitting`, then `committed` on `strand:offline-status`, and `strand:commit-durability` fired for that `Tx` after the drain.
  - `setStrandOfflineMode(…, 'online')` changed `queueState().mode` on the live database.
  - After hibernate and wake, the rebuilt database was back in `'offline'` and `strand:queue-state` fired again.
  - A node without `strandOffline` had `offline === undefined`, read `'online'`, and threw `StrandOfflineUnavailableError` on set.
- `StrandOfflineReport` with hand-made plugin results:
  - Deferred, then published, then applied gives `['deferred', 'applied']`.
  - Applied before publication gives nothing.
  - Failed before publication is announced at publication.
  - After `release()`, nothing is reported.
  - With no `appSchema` (a storage replica), the state reads `'applied'`.

Not covered by anything that ran:

- A deferred apply through a real queue on a cadre node, which needs an unreachable cohort and a schema upgrade.
- The quiescing skip.
- A mode set while a gated database is waiting.
- The first-sync probe passing offline.

The real-network scenario in `strand-offline-mode` covers the mode at build, restore after restart, status events and the drain. A reviewer who wants the deferral on a cadre node would need a joiner whose seed peer has gone away.

## Tests

No new tests, per the ticket: the logic is a map read at one point plus event forwarding, and the scenario in `strand-offline-mode` runs the whole path. Nine existing specs replace `StrandDatabase` with an inline fake. Each fake gained a `reportPublished: () => {}` stub, because `publishDatabase` now calls it. Without the stub, 97 tests across those files failed with `database.reportPublished is not a function`.

## Tripwires added

- `isSendingStatus` (`strand-offline.ts`) has a `NOTE:`. A send that keeps failing transiently while the cohort reads as reachable is retried at least every 60 s (Optimystic's re-check cap), so such a strand never idles. If that is ever seen, count only `committed`, `partially-committed` and `failed`.
- `StrandOfflineConfig.journal` doc: nothing closes the store and every rebuild calls the factory again, so the embedder must return the same store per scope and close it itself. `strand-offline-platform-journals` already plans this.
