# The claimant redials the claimed node while it restarts

## What changed

Owner side of a QR claim (`CadreNode.claimNode`), after node B acknowledges the claim seed:

- **Claim address first.** Right after the ack, before anything else is awaited (B's restart closes the connection within ~30 ms of the ack in the scenario), `connectedAddrFirst` reads the open connection to B and moves the QR address whose suffix-stripped form (`addrKey`, now exported from `peer-addr-book.ts`) equals the connection's `remoteAddr` to the front of the list given to `retainDialTarget`. Otherwise the QR order is kept.
- **Redial window.** `claimNode` starts `redialClaimedNode(peerId)` (not awaited, logged catch). Every `CLAIM_RESTART_REDIAL_STEP_MS` (1 s) for `CONTROL_COHORT_REDIAL_MS` (15 s) from the ack, a step: stops if the node is not running, the retained target is gone (`removePeer`), or B is in `identifiedControlPeers`; skips dialing while any connection to B is open; otherwise dials once through `dialBootstrapPeer(peerId, entry.addrs, 'claimNode(redial)')`. Steps are sequential. One loop per peer (`claimRedialPeers`, cleared in `finally`). The loop never touches `reconcileRedialStreak`. The 1 s timer is `unref`'d.
- **Accepted-tradeoff `NOTE:`** at the `vouchPeer` call in `claimNode`: B's signed record is not carried in the ack (signed before the restart; the write-while-alone drain re-sends only rows with a null `Sig`). Revisit if the drain ever re-sends signed rows.
- `dialBootstrapPeer` takes a `context` string for its log lines and dial label (default `reconcileControlCohort(cold-start)`), so claim redials do not log as cold-start dials. The cold-start dial label changed from `reconcileControlCohort cold-start dial of bootstrap peer X` to `reconcileControlCohort(cold-start) dial of bootstrap peer X`; nothing asserts on it.

## Deviation from the plan: the loop's stop rule

The plan said "stop on a successful dial". The scenario's debug logs show that is wrong: while B restarts, the claimant's dials to it *succeed* and are then closed by B within 4–20 ms, five or six times in a row (each close starts another reconcile pass, which dials again, until one dial fails with `EncryptionFailedError` and arms the 15 s ladder). A loop that stopped on the first successful dial would end on one of those. So a successful dial does not end the loop; the loop ends when B has identified as serving this party's control database (`identifiedControlPeers`), which B's placeholder node never does because it serves the placeholder party's protocols. This also makes the repeat claim (scenario step 5) end its loop at the first step: B is already identified on the open connection.

## Measurements (time from `claimNode` resolving to `claimant.hasReachableControlSibling()` turning true)

The committed scenario cannot show the difference. Its phone fixture (`buildPhoneOwner`, `PHONE_RECONCILE_MS = 2_000`) caps the redial ladder at 2 s. Also, step 3 runs about 0.1 s after the claimant starts, before its reconcile schedule is wired (~1 s after start), so the seed connection's close triggers nothing. Unmodified, it reconnected in 0.73 s and 0.77 s before the change. For a realistic measurement I ran with temporary overrides (all removed): claimant backstop 120 s (the default) and a 2 s sleep before the claim. The loop was switched off by a temporary env check in the same build, so both arms ran the same code otherwise.

| arm | runs (s) |
| --- | --- |
| loop off | 0.28, 5.50, 5.54, 5.48, 5.50 (plus an earlier build at HEAD: 5.45, 0.25) |
| loop on | 0.27, 0.27, 2.08, 0.25, 0.29 (plus three earlier runs: 2.07, 2.07, 0.26) |

- The ~0.27 s runs are the reconcile pass's own chain of dials landing once B is up. The loop matters only when that chain ends in a failed dial. Then the loop's step at ~1 s is refused (B is still in its bring-up quiet period) and its step at ~2 s connects.
- With the loop off, the 15 s ladder step was **not** what bounded the reconnect: something below cadre-core reopened the connection at ~5.5 s, with no cadre-core dial log line (probably Optimystic or FRET dialing by peer id from the address book that identify filled on the seed connection). Not investigated. On a phone the timing of that lower-layer dial may differ, so the 15 s worst case may still be reachable there.
- No timing assertion was added. The loop's worst case (2.08 s) is well under the 15 s ladder step, but the scenario as configured (2 s backstop) cannot tell the arms apart. An assertion would need the claimant built with the default backstop, and the ~5.5 s lower-layer reconnect leaves less than a 2× margin against the loop's 2.08 s.

## Backlog bug confirmed not a bug (ticket deleted)

`bug-seed-connection-counted-as-a-control-connection`: in `DEBUG='sereus:cadre:*'` runs of `node-claim-by-phone`, the vouch logs `authorizePeer(B) committed while alone (0 control connections); queued for re-replication` while the seed connection is open. "Control cohort grew … Draining … pendingPeers=1" appears only after the restarted B connects and identifies, and never for the placeholder's connection or the short-lived connections to the restarting node. `debt-seeded-machine-row-revouched-before-it-publishes` referenced the bug ticket and described the old connection count; that line now describes `hasReachableControlSibling` and the confirmation.

## Tests

- The address reorder is not exercised by any scenario: every scenario's QR code carries one loopback address. Checked by reading the code only. A QR address given as a DNS name (`/dns4/localhost/...`) never equals the connection's `remoteAddr` (the resolved IP), so the reorder is a no-op for such addresses and the QR order is kept.

## For the reviewer

- Pre-existing, not changed here: each close of a connection to an authorized sibling triggers a reconcile pass at once (`onControlSiblingConnectionChange` → `trigger(0)`), so while B restarts the claimant runs 5–6 dial-connect-close passes in ~200 ms. This is bounded by B's restart (~0.5 s locally). It would last longer if a node's bring-up quiet period were long, for example a slow device. Consider whether it deserves a `NOTE:` tripwire at `onControlSiblingConnectionChange`.
- `connectedAddrFirst` calls `peerIdFromString(target.peerId)`, which throws on a malformed id. It runs only after `deliverSeed` succeeded with the same id, so the id is known to be valid there.
- The loop reads `bootstrapPeerStore.all()` (a copy of the map) once per step, at most 15 times per claim.
