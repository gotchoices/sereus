# Cadre invitation tables and the consent branches — implement handoff

## What landed

The schema and database layer for owner-signed cadre invitations, as the implement ticket specified. No protocol, no client API; the owner-online `authorizePeer` path is untouched.

**Schema (`schemas/control.qsql`, mirrored into `control-schema.ts` by a script, drift spec green).**

- `CadreInvite`: the invitation row keyed by its ed25519 public key, with `PeerId`, `GrantsOwner` (0/1), `ExpiresAt`, `TotalUses`, `IssuerKey`/`IssuerSig` pinned to the insert context, `StampId`. `NotRevoked`, `AuthorizedInsert` over the whole row, `NoUpdate`, `NoDelete`.
- `CadreInviteUsage`: one row per redemption. `Authorized` reads `committed.CadreInvite` (tombstone, expiry, cap over committed usage, target, issuer still in `committed.OwnerKey`); `InvitePossessed` and `PeerConsented` verify the two stored signatures; `PeerExists` and `OwnerExists` are deferred so the same-transaction rows count. Index `CadreInviteUsageByInvite`.
- `CadrePeer`: `VouchUsage` column; consent branch on `AuthorizedInsert`; owner insert branch and owner re-vouch update branch require `VouchUsage is null`; self-publish branch keeps `VouchUsage` as it was.
- `OwnerKey`: `VouchOwner`/`VouchSig`/`VouchUsage` columns; genesis branch requires all null; owner-signed add pins `VouchOwner`/`VouchSig` to the context; consent branch for owner-granting invitations.
- `Revocation`: `'CadreInvite'` in the `TableName` comment; `RowIsGone` branch with no row-gone test, commented.

**Null-safety, beyond the ticket's text.** Quereus treats a CHECK that evaluates to null as passing (`deferred-constraint-queue.ts`, `isTruthy`). With `VouchSig` now legitimately null on one row kind, a bare `new.VouchSig = old.VouchSig` on the self-publish branch would have evaluated to null and let a self-update fill the column in, and `new.VouchOwner = context.OwnerKey` with nothing stored would have pinned nothing. Every pin and immutability clause over a nullable proof column is written `coalesce(col, '')`, on the pre-existing `CadrePeer` branches too. The schema header says so; the crypto-free probe spec grew four cases for it; the owner-key spec gained one.

**`control-authorization.ts`.** `CONTROL_TABLES` gains the two tables after `FormationUsage`; `RevocableTable` gains `'CadreInvite'` (revocable, never removable); `ControlAction` gains `'redeem'`; `CadreInviteSignedFields` and `cadreInviteRowFields` are the one field-vector builder both the byte signer and the base64url verifier use.

**`peer-authorization.ts`.** `cadreInviteAddDigest`, `cadreInviteRedeemDigest`, `cadreInviteConsentDigest`, and `verifyInvitationAdmission(row, usage, invite, isAnchored)`, which checks every link the ticket lists and re-derives the peer id from the stored key. For that, `ed25519PublicKeyB64FromPeerId` moved from `seed-bootstrap.ts` to `ed25519-key.ts` (re-exported from its old home, so existing importers resolve).

**`ControlDatabase`.** `insertCadreInvite` (returns the stored `CadreInviteRow`, `expiresAt` canonical), `seatCadreInvite` (insert-if-absent under the row's own issuer pair; `AuthorizedInsert` refusals become `CadreInviteIssuerUnknownError`), `queryCadreInvite`, `queryCadreInvites`, `queryCadreInviteUsages`, `countCadreInviteUsage`, `hasLiveCadreInvite`, `withdrawCadreInvite` (tombstone only, through a factored `execTombstone`; fires the guarded-delete listener so a withdrawal committed alone is re-issued on cohort growth), `redeemCadreInvite` (through `mutateCadrePeer`; one transaction: peer row if absent, owner row if granted and absent, usage row last). `queryCadrePeers` returns `vouchUsage`; `reauthorizeCadrePeer` sets `VouchUsage = null`. Types in `types.ts`: `CadrePeerRow.vouchUsage`, `CadreInviteRow`, `CadreInviteUsageRow`, `CadreInviteRedemptionResult`.

**Reader.** `CadreNode.listAuthorizedMembers` judges a row with `VouchSig` null and `VouchUsage` set through `verifyInvitationAdmission`; the usage and invitation tables are read only when at least one such row exists, honouring the `retry` flag. A row with a `VouchSig` is judged as a voucher even if it also names a usage.

**Docs.** `docs/architecture.md` control table list: new `CadreInvite` and `CadreInviteUsage` rows; `OwnerKey`, `CadrePeer` and `Revocation` rows updated.

## Deviations from the ticket, each deliberate

- **Redemption checks the existing rows before the seat budget**, not after as the ticket's order said. Otherwise the retry of a single-use redemption after a dropped reply is refused as exhausted instead of answered `alreadyMember`. Pinned by the exhaustion test.
- **`hasLiveCadreInvite` also requires the issuer to still be an owner.** The ticket's liveness definition listed tombstone, expiry and uses; the schema's `Authorized` also requires the issuer in `committed.OwnerKey`, and a gate heuristic that ignored it would hold the stranger door open for an invitation nothing can redeem. One extra read of the small `OwnerKey` table.
- **Withdrawal is read through `queryRevokedStamps('CadreInvite')`**, the per-table retired-stamp seam every other reader uses (and the one an isolated node can still answer), rather than `queryRevocations`.
- **`InvitationExhaustedError` is reused** for cadre invitations (its `token` field carries the invitation key) rather than a second class; its doc says so. A missing invite row inside `redeemCadreInvite` throws a plain `Error` (the protocol seats before it redeems, so this is a programming error, not a state).
- **The "seated and redeemed in one transaction" test cannot isolate the `OwnerKey` branch.** Every consent branch keys on the same invitation, so when it is uncommitted the usage row's and the owner row's refusals fire together; both carry the name `Authorized` and the test asserts that one name. The case is built so the `CadrePeer` consent branch is not involved (the device is pre-admitted).

## Tests

All in `test/control-cadre-invite.spec.ts` unless noted; each names the one constraint or error it pins.

- redemption seats `CadrePeer` by consent (null `VouchSig`, `VouchUsage` set, `PublicKey` = device key), `queryCadrePeers` carries `vouchUsage`, `listAuthorizedMembers` admits the device through the chain, a retry is `alreadyMember` and writes nothing.
- owner-granting redemption also seats `OwnerKey` by consent; retry idempotent.
- owner-granting redemption of an already-admitted device completes it with the owner row only, the usage naming the existing peer stamp.
- owner re-vouch of an invitation-admitted row moves it onto the signature, clears `VouchUsage`, and it stays authorized.
- targeted invitation, other device → `Authorized`; expired → `Authorized`; withdrawn → `Authorized`, with the row kept, the tombstone accepted while the row is live, and a second withdrawal a no-op; exhausted → `InvitationExhaustedError` by name, and the already-admitted device still gets `alreadyMember`.
- `InviteSig` by another key → `InvitePossessed`; `PeerSig` by another key → `PeerConsented`.
- usage with no peer row in its transaction → `PeerExists`.
- `OwnerKey` seated under a non-owner-granting invitation → `Authorized`.
- invitation seated and redeemed in one transaction → `Authorized` (see deviations).
- `seatCadreInvite`: stranger-issued row → `CadreInviteIssuerUnknownError`; founder-signed row seats once and is a no-op the second time; the holder's copy of a withdrawn invitation → `NotRevoked` on a node holding only the tombstone.
- `hasLiveCadreInvite` on its own node: false with none, true for a metered unexpired invitation, false once exhausted, withdrawn, or expired; an issuer removed since issuing takes its invitations with it (liveness false, redemption → `Authorized`).
- `verifyInvitationAdmission` without a database: anchored issuer passes; unanchored fails; stored peer key not deriving to the row's peer id fails with every signature valid; invitation naming another device fails.
- `control-ownerkey-self-authorization.spec.ts`: an owner-signed add stores the pinned pair; an add storing a null pair under a valid signature → `Authorized` (the null-safe pin).
- `control-cadrepeer-voucher-constraint.spec.ts` (crypto-free probe, predicates re-aligned): owner-signed insert with a null voucher refused; invitation-admitted row may self-update with its null `VouchSig` left null; a self-update filling `VouchSig` or clearing `VouchUsage` refused.

Updated for the schema, no new behaviour: `control-authorization-binding`, `control-authorization-domain-separation`, `control-revocation-replay` and `control-concurrent-same-pk-insert.integration` now write `VouchOwner`/`VouchSig` on raw owner-key inserts; `membership-gate-helpers`, `cadre-node-authorized-surface` and `seed-bootstrap` row fakes carry `vouchUsage: null` (the real reader would otherwise take `undefined` for a usage and reach for the fake's missing reads); `control-schema-apply-unwind` expects the fifteen tables and two indexes; `control-revocation-ledger-marker` lists `CadreInvite`.

**Budgets re-measured and widened deliberately** (both files carry the figures, date and optimystic commit `5a5661b0`): cold-start cohort consults 31 → 37 over 23 → 29 blocks (the two tables and two indexes, plus the two `JoinRequest` outcome tables that had never been recorded there), cold-start raw-storage operations 50 → 56 over 25 → 31 blocks. No other phase moved.

## Known gaps, for the reviewer

- **Self-publish by an invitation-admitted device against the real schema is not exercised.** The null-safe self-publish branch is pinned only by the crypto-free probe; `updateSelfPeerRecord` by such a device (the real `verify` over `new.Sig` with `VouchSig` null) has no test here. The protocol ticket's end-to-end run will cover it; a cheap unit case would be: admit a device, sign a peer record with its key, `updateSelfPeerRecord`, read the row back.
- **No warm-start migration.** Every edited constraint forces recreation of an existing control store (the architecture doc's note under the table list). The implement ticket accepted this.
- **`seatCadreInvite` maps every `AuthorizedInsert` refusal to `CadreInviteIssuerUnknownError`**, including a tampered signature. The protocol ticket will map it to a retryable code; a forged row therefore retries until its budget runs out rather than being refused outright. Named in the error's message and doc.
- **A retry with a stale budget**: `redeemCadreInvite` answers `alreadyMember` for a device whose row exists even if that row was admitted by another route; harmless (it is a member), noted here so the protocol ticket does not read `alreadyMember` as "this invitation admitted it".
- **The trusted-owner anchor does not follow owner removals** (plan ticket `owner-anchor-follows-owner-key-changes`): a device admitted by an owner later removed stays authorized on readers that still pin that owner, exactly as an owner-vouched row does today.

## Tripwires and accepted tradeoffs recorded

- `NOTE:` in `hasLiveCadreInvite` (two: the full-table scan on the stranger path; one retried read per metered invitation under the gate's 2 s deadline), and the schema `NOTE:` on `CadreInvite` about expired and withdrawn rows accumulating.
- `NOTE: accepted tradeoff` at `CadreInviteUsage.Authorized`: two machines racing a single-use invitation may both admit, owner grants included; mitigations and the revisit condition are at the clause.
- The schema header now states the null-passes rule and the `coalesce` discipline it demands, so the next nullable pin is written right.
