# Owner grants: tables, rules and the control-database writers (implemented)

The implement ticket's text is the specification; this handoff says what landed, where the implementation chose, and what is not verified. The work is additive: machine invitations keep `GrantsOwner` and the invitation consent branch on `OwnerKey` until `machine-invitation-grants-no-ownership` removes them. Nothing outside tests calls the new writers; `owner-grant-node-api` is the first caller.

## What landed

**Schema** (`schemas/control.qsql`, mirrored byte for byte into `control-schema.ts` by a script that regenerates the embedded copy from the file; the drift spec confirms they match):

- `OwnerGrant` (`Key`, `Label`, `ExpiresAt`, `TotalUses`, `IssuerKey`, `IssuerSig`, `StampId`) with `NotRevoked`, `LabelLength`, `AuthorizedInsert` (the `'add'` digest over `Key, coalesce(Label, ''), coalesce(cast(ExpiresAt as text), ''), coalesce(cast(TotalUses as text), ''), StampId`, issuer pair pinned to context), `NoUpdate`, `NoDelete`.
- `OwnerGrantUsage` (`UsageStampId`, `GrantKey`, `SeatedKey`, `SeatedStampId`, `GrantSig`, `OwnerSig`) with `InsertOnly`, `Authorized` (committed grant: no tombstone, unexpired against `context.Now`, uses left by committed count, issuer a live committed owner), `GrantPossessed`, `OwnerConsented`, and the deferred `SeatedExists`. The accepted-tradeoff `NOTE:` for the single-use race sits on `Authorized`, with the mitigations rewritten for grants and no targeted form.
- `index OwnerGrantUsageByGrant on OwnerGrantUsage (GrantKey)`.
- `OwnerKey.Authorized` gained the grant consent branch exactly as the ticket wrote it: `VouchSig` null, `VouchUsage` naming an `OwnerGrantUsage` row for this key and stamp, whose grant is in `committed.OwnerGrant`, issued by `VouchOwner`, with `coalesce(G.Label, '') = coalesce(new.Label, '')`. The invitation branch is untouched.
- `Revocation.RowIsGone` admits `'OwnerGrant'` unconditionally beside `'CadreInvite'`; the `TableName` comment, the header's guarded-table list and its never-deleted sentence name both.
- `CONTROL_SCHEMA_VERSION` is 2; the drift spec pins `hash:GrqGOvAk`. A store from version 1 refuses to start with `ControlStoreIncompatibleError`, as the architecture doc's "Control schema changes and incompatible stores" says; recreate it.

**TypeScript:**

- `control-authorization.ts`: `OwnerGrant` and `OwnerGrantUsage` in `CONTROL_TABLES` (schema order, before `Revocation`), `'OwnerGrant'` in `RevocableTable`, `OwnerGrantSignedFields` and `ownerGrantRowFields`.
- `types.ts`: `OwnerGrantRow`, `OwnerGrantUsageRow`, `OwnerGrantChain`, `OwnerGrantStatus`, `OwnerGrantRedemptionResult`; `OwnerKeyRow`'s field docs cover the fourth proof shape.
- `peer-authorization.ts`: `ownerGrantAddDigest`, `ownerGrantRedeemDigest`, `ownerGrantConsentDigest`, `verifyOwnerGrantRow` (the bundle-copy check `isOwnerGrantLive` uses) and `verifyOwnerGrantAdmission` with the link list the ticket gave, labels compared null-safe, same never-throws contract and the same deliberate omissions as the invitation verifier.
- `owner-anchor-sync.ts`: `OwnerAnchorInputs.grantChain: OwnerGrantChain | null` (required, beside `chain`). A consent-seated row's `vouchUsage` is looked up in the grant chain first, then the invitation chain. `cadre-node.ts` loads the grant chain (`loadOwnerGrantChain`, two whole-table reads) in `syncOwnerAnchor` whenever any owner row is consent-seated, beside the shared invitation chain; a `NOTE:` at that site records the cost and the memo that would cover it.
- `control-database.ts`: `insertOwnerGrant`, `seatOwnerGrant`, `queryOwnerGrant`, `queryOwnerGrants`, `queryOwnerGrantUsages`, `countOwnerGrantUsage`, `isOwnerGrantLive`, `listOwnerGrantStatuses`, `withdrawOwnerGrant`, `redeemOwnerGrant`; the message builders `ownerGrantAddMessage`, `ownerGrantRedeemMessage`, `ownerGrantConsentMessage`; `OwnerGrantIssuerUnknownError`. All exported from `index.ts`, the row types through `export * from './types.js'`.
- Every table-name switch was checked: `GUARDED_KEY_COLUMN` gained `OwnerGrant: 'Key'`; `RemovableTable` now excludes both issued tables; `REAPABLE_TABLES` is a literal list that never included it, so the reap sweep skips `'OwnerGrant'` tombstones as it skips `'CadreInvite'`; the re-issue drain and `noteGuardedDelete` work on `RevokedRowRef` and need no change; `queryRevocations` casts `TableName` to `RevocableTable`, which now includes it.

**Docs** (`docs/architecture.md`): `OwnerGrant` and `OwnerGrantUsage` rows in the control-table list after `CadreInviteUsage`; the `OwnerKey` row names the grant branch and the label rule; the `Revocation` row names both withdrawn tables; the schema-recreation "what is lost" list; the anchor-derivation paragraph names `verifyOwnerGrantAdmission` and the lookup order. The flow description is left for `owner-grant-node-api`.

## Decisions taken in the implementation (check these)

- **Shared code rather than copies.** `seatIssuedRow`, `withdrawIssuedRow`, `signWithdrawals(table, …)`, `issuedRowLive`, `issuedRowStandings`, `assertIssuedSeatRemains`, `countUsageRows` and the renamed predicate `issuedRowStillOpen` now serve both `CadreInvite` and `OwnerGrant`; the invitation methods are one-line wrappers. A new `IssuedTable` union (`'CadreInvite' | 'OwnerGrant'`) names the pair, and `RemovableTable` is `Exclude<RevocableTable, IssuedTable>`. Write-reason labels are kept per table (`cadre-invite-withdraw`, `owner-grant-seat`, …) through `ISSUED_TABLE_REASON`.
- **A separate error class**, `OwnerGrantIssuerUnknownError`, rather than generalising `CadreInviteIssuerUnknownError`: the invitation protocol handler maps the invitation error by `instanceof` to a retryable code, and a grant handler (`owner-grant-node-api`) will want to tell the two apart. Both wrap the same `AuthorizedInsert` refusal through one regex.
- **The "already an owner / removed row still held" read is shared.** `liveOwnerKeyStamp(key)` is the insert-if-absent read of both `insertOwnerKeyVouched` and `redeemOwnerGrant`; it returns the live stamp, null when absent, and throws the by-name refusal when the node holds the key's row under a retired stamp. So the refusal the ticket asked about does reach the grant path. It is not pinned by a test on either path: that state (a tombstone over a still-present row) arrives only by replication, and `Revocation.RowIsGone` refuses building it locally with raw inserts.
- **The seated `OwnerKey` stamp is minted from this node's peer id**, as `insertOwnerKeyVouched` mints it, not from the seated key: a grant has no admitted device to name.
- **`InvitationExhaustedError` is reused** for an exhausted grant, with `token` the grant key, rather than a grant twin; its doc names the third table.
- **`expiresAtMs` omitted and `null` both mean never** at this layer, as `insertCadreInvite` treats them. The 15-minute default and the "null must be explicit" rule belong to the node API.
- **`isInvitationAdmitted` in `cadre-node.ts` keeps its name** and now also answers true for a grant-seated row (the doc says so); renaming it would touch the `CadrePeer` membership path this ticket does not own.
- **Two pinned-count specs were re-baselined**, both by exactly the four new never-written blocks: `control-founding-consult-budget.spec.ts` (cold start 37 over 29 → 41 over 33; every other phase measured unchanged in the same run) and `control-schema-apply-unwind.spec.ts` (seventeen tables, three indexes). `control-revocation-ledger-marker.spec.ts`'s literal revocable-table list gained `'OwnerGrant'`.

## Known gaps

- **No `hasLiveOwnerGrant`.** The connection gate's "do I expect a stranger?" read (`hasLiveCadreInvite`) has no grant twin. `owner-grant-node-api`'s remote path (a device with no machine in the cadre asking a member to write the redemption) will need one if that gate is what admits the stranger's connection; it is a few lines over `issuedRowStillOpen` and `countOwnerGrantUsage`.
- **No pre-check twin of `verifyCadreInviteRedemption`** for a grant (both signatures checked before any database work). The schema refuses a bad signature by constraint name; the node API can add the pre-check when it wants a clean refusal code.
- **The grant chain is read only by the anchor sync**, and only when some owner row is consent-seated. Until `machine-invitation-grants-no-ownership` lands, such a row may be invitation-seated, in which case the grant-chain reads find nothing: two extra whole-table reads per membership refresh in that state. Recorded as a `NOTE:` in `syncOwnerAnchor`.
- **Not run:** the integration-tests workspace. Nothing there constructs an `InvitationChain` or calls `deriveOwnerAnchor` (checked by grep), and the only signature changes are to that function's input and to private methods, so the risk is a stale `@serfab/cadre-core` dist; the dist was rebuilt after the source edits.

## Tests

- `control-owner-grant.spec.ts` (new, one `CadreNode` with the founder pinned, as `control-cadre-invite.spec.ts`):
  - redemption seats the `OwnerKey` row with the grant's label, `VouchOwner` the issuer, `VouchSig` null, `VouchUsage` the usage stamp; the usage row names the key and the stamp; `node.listOwnerKeys()` reports the key `trusted`, which is the node's own anchor sync walking the grant chain end to end; a retry with the same nonce and one with a fresh nonce both answer `alreadyOwner` and spend no use.
  - a key removed earlier is seated again under a fresh stamp (`NotRevoked` passes).
  - a table-driven test of the refusals, each confirming no owner was seated: withdrawn (tombstone accepted with the row present, row kept, second withdrawal a no-op), expired, exhausted by name before any write (and the seated key's retry still `alreadyOwner`), issuer removed since issuing, wrong grant signature (`GrantPossessed`), wrong owner signature (`OwnerConsented`), label other than the grant's (`OwnerKey.Authorized`), an `OwnerKey` consent insert whose usage names another key (`OwnerKey.Authorized`, with the named key's own row valid in the same transaction so only the second row's branch refuses), a grant seated and redeemed in one transaction (`Authorized`).
  - `seatOwnerGrant`: foreign issuer refused by `OwnerGrantIssuerUnknownError`, seating twice a no-op, the holder's copy of a withdrawn grant refused by `NotRevoked`.
  - standing: `listOwnerGrantStatuses` reports live, withdrawn, expired and exhausted; `isOwnerGrantLive` judges a held row and an unseated bundle copy by its signature. This one also covers the shared `issuedRowStandings`, which `listCadreInviteStatuses` had no test for.
- `owner-anchor-sync.spec.ts`: a grant-seated row is derived from an anchored issuer; not with the issuer unanchored; not when the grant's signature is re-signed by a stranger; not with no grant chain. Every existing call gained `grantChain: null`.
- `control-schema-drift.spec.ts`: version 2 and the new hash.
