# Ready for review: writes that straddle a late join

Third test in `strand-late-cadre-join.integration.ts`, plus the bring-up split it needed and one
additive harness option.

## What the property is, for a reader without the context

Two different mechanisms deliver a strand's data to a machine that was added to the party late:

- Rows written **before** the newcomer's strand node connects come from the **peer-join block
  catch-up** (`packages/cadre-core/src/peer-join-backfill.ts`) — a one-shot push of the holder's
  whole store. It enumerates the store once (`listBlockIds()`) and then marks that peer caught up
  for the rest of the runtime.
- Rows written **after** it connects come from **ordinary cohort replication**, the newcomer's
  strand node now being in the cohort.

There is a seam between them. A block committed after the enumeration already passed its id, but
before the peer was marked done, is never pushed by the catch-up — replication has to cover it.
Nothing exercised that seam before this test. A real person keeps typing on their phone while the
laptop they just added is still catching up, so this window is normal use, not an edge case.

## What shipped

### `packages/integration-tests/src/scenarios/strand-late-cadre-join.integration.ts`

**Bring-up split into three functions** (the ticket asked for two — see *Deviations* below):

- `foundStrandAlone(label, handles)` — the old Phase 0: founder starts alone, becomes its own
  owner, registers an addressed `CadrePeer` row, adds and publishes an open strand, writes the five
  `pre-join-*` rows, asserts **zero control connections** at that instant, snapshots the pre-join
  block index and asserts the anti-vacuity floor.
- `enrollNewcomer(founded, handles)` — the old Phase 1: vouch before start, construct the newcomer
  with the founder's owner key pinned, `createSeed`/`applySeed`, wait for the settled outbound
  control connection, converge membership and assert it **both ways**.
- `joinDiscoveredStrand(fx)` — Test 1's old Phase 2 lifted out verbatim: wait for the newcomer's own
  `strand:discovered`, join with **that** row, and gate the strand mesh in both directions with the
  founder's strand peer id asserted distinct from its control peer id.

Tests 1 and 2 now call the first two back to back; Test 1 then calls the third. Neither changed
behaviourally — the same statements run in the same order.

**A bounded straddle writer** (`startStraddleWriter`). One `insert into App.Data` per 100 ms tick,
an `update` of a single fixed row every fourth tick, hard-bounded at 400 ticks. It records the key,
value and **phase** (`enrolling` / `post-mesh`) of every row it wrote. It captures its own error
rather than swallowing it, and `stop()` re-throws that error — a writer that died during enrollment
would otherwise leave every assertion downstream passing because there was nothing left to lose.
`awaitPhaseRows` fails fast if the writer has already exited instead of burning the whole budget.

**Test 3 — "loses no row written while the newcomer is still catching up"**:

1. `foundStrandAlone`, then insert the update-target row (still alone, so its first revision is a
   pre-join block).
2. Start the writer; wait for 3 rows so the straddle is demonstrably real before enrollment starts.
3. `enrollNewcomer` and `joinDiscoveredStrand` run **while the writer keeps going**.
4. Mesh up both ways → snapshot the writer's `enrolling` count, switch it to `post-mesh`, take one
   **unasserted diagnostic** coverage sample (see below), wait for 5 post-mesh rows, stop the writer
   (re-throwing anything it hit).
5. Anti-vacuity: enrolling rows > 0, post-mesh rows ≥ 5, updates > 0, and the founder's **own** read
   of the update-target row equals the writer's last value — a full-PK `update … where Key = ?` that
   matched nothing would no-op silently and make the revision-advance half of the test vacuous.
6. **Physical gate**, raw stores only: `awaitBlockCoverage(founderStore, newcomerStore)` with **no
   `include` narrowing** — the founder's whole store, at revisions no older than the founder's, with
   content bytes present. Preceded by a second anti-vacuity check: the founder's store must hold
   blocks **new or advanced since the pre-join snapshot**, or "the newcomer covers the founder" would
   be a claim about Test 1's six blocks and say nothing about the straddling writes.
7. **Behavioural gate**, only after coverage is proven: read every row back from the newcomer's
   strand database and name any key that is missing or wrong **together with the phase it was
   written in** — a missing `post-mesh` key implicates replication, a missing `enrolling` key the
   catch-up, and a stale update-target row the seam between them.

### `packages/integration-tests/src/harness/block-store-probe.ts`

## Use cases to check when reviewing

- **The straddle is real, not a race.** The writer is producing before `enrollNewcomer` is called
  (3-row warm-up), and 23-29 rows land during enrollment on every measured run.
- **Both halves of the seam are exercised.** `enrollingRows > 0` and `postMeshRows >= 5`. Without
  the second, Test 3 is Test 1 with extra steps.
- **The gate is not vacuous.** Founder store moved 6 → 9 blocks with 6 new-or-advanced every run;
  `newcomerStore !== founderStore` is asserted; `readBlockIndex` throws rather than reporting empty
  if the backend lacks `listBlockIds`.
- **Rule 3 holds.** No read through the newcomer's strand database happens before the physical gate
  closes. The mid-flight diagnostic reads raw stores only.
- **The writer cannot outlive the test.** Stopped in the body and again in `finally`, where its
  re-thrown error is caught and warned so it cannot mask the real failure.
- **A dead writer fails loudly.** Kill the writer artificially (e.g. make the insert throw) and the
  test must fail with the writer's error, not pass.

## Known gaps — flag these, do not assume they were considered and dismissed

- **The physical gate has never observed a non-empty gap.** In 13 runs, `awaitBlockCoverage`
  completed on its **first poll** every time (`gap kinds seen before coverage closed: []`). The gate
  therefore proves the end state; it does not witness the window closing. That is why the
  **unasserted mid-flight diagnostic** exists — it samples coverage while the writer is still
  running, and shows 3-6 blocks absent (once one `behind`) at the instant the mesh forms. If a
  reviewer wants the gate itself to witness a gap, that needs a different staging than this test has.
- **The specific seam is probabilistic, not staged.** The test cannot force a block to commit
  *between* the catch-up enumeration passing its id and the peer being marked done. It makes that
  interleaving likely (tens of rows inside the window) but never guarantees it. A green run is
  therefore weaker evidence than the ticket's framing might suggest.
- **The post-mesh half is thin.** 5 rows over ~0.5 s, against 23-29 rows during enrollment. The
  replication half of the seam is exercised, but far less than the catch-up half.
- **The behavioural gate runs with the founder still up.** The ticket did not ask for a founder-down
  read here, and Test 1 already pins the isolated-read claim, so this reads through the newcomer
  while the founder is alive. The physical gate already proved the bytes are on the newcomer, but
  the behavioural gate alone could in principle be answered over the wire. Adding
  `await founder.stop()` before it would close that, at the cost of duplicating Test 1's Phase 4a.
- **`update … where Key = ?` is a full-PK point lookup**, the shape this file's own `readDataRows`
  comment warns the networked module can miss. It is issued against the founder's own local store so
  it resolves, and the founder-side read-back assertion catches a silent no-op — but it is the one
  place in the file that uses a lookup shape the file elsewhere avoids.
- **Timing constants are measured on one machine on one day** (2026-09-08, Windows, 13 runs). The
  100 ms tick and the 5-row post-mesh floor are tuned to a ~3 s enrollment window.

## Deviations from the implement ticket

- **Three bring-up functions, not two.** The ticket specified `foundStrandAlone()` and
  `enrollAndJoin()` (enrollment *through* mesh gating), and said Tests 1 and 2 call them back to
  back. Test 2's whole subject is a machine that **never runs the strand**, so it cannot call a
  function that calls `addStrand`. Enrollment and joining are therefore separate steps, and Test 2
  takes only the first two.
- **The update-target row is inserted by Test 3, not by `foundStrandAlone`.** The ticket put it in
  the shared bring-up; doing that would have added a sixth row to Tests 1 and 2, which the same
  ticket required to stay unchanged. Test 3 inserts it immediately after `foundStrandAlone` returns
  — the founder is still the only machine, so it is still a pre-join block. It is not in the
  `preJoinIndex` snapshot, which no assertion in Test 3 depends on.
- **Two additions the ticket did not ask for**, both because the gate would otherwise have been hard
  to trust: the unasserted mid-flight coverage sample, and the "founder blocks new or advanced since
  the pre-join snapshot" anti-vacuity check.

## Tripwires parked in code (not tickets)

- `NOTE:` at `COVERAGE_BUDGET_MS` — the 60 s budget is sized for ~30 rows in a ~3 s enrollment
  window and has to grow if enrollment slows, the tick shortens, or the store grows; a timeout there
  would read as a replication failure when it is really a too-small window.
- `NOTE:` at `WRITER_MAX_TICKS` — 400 ticks is ~40 s of writing against a ~3 s window, so it is
  currently unreachable; if it is ever reached, `awaitPhaseRows` fails with "straddle writer exited
  after N row(s)", which means the bound, not a lost row.
