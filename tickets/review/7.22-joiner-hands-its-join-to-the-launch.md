# The joiner hands its join to the launch — review handoff

## What changed

- **`JoinedStrandSession.rememberForeign` asks the local store first.** When the machine-local joined-strand store already holds an identical record (same `Type` and `MemberPrivateKey`), it returns before `namedByParty` (the ledger's `queryStrand` + `queryJoinedStrand`). Otherwise the old order runs: `namedByParty`, then record unless the party names the strand. `pendingRemovals.delete` is still first. A failed early `store.list()` is logged and treated as "unknown": the party is asked, and if it names the strand the call returns quietly; if not, the store is asked again (which throws, and `rememberForeignStrand` warns as before). Small helpers: `storedRecord(id)` (instance method) and `isSameJoin(record, row)` (module function).
- **Party-key handoff.** `CadreNode.formedPartyKeys: Map<strandId, key>` (in memory). `adoptFormationMembershipInvite` stores the key `ensureStrandPartyKey` returned. `resolveStrandPartyKey` checks explicit key → this map (deleted on use) → `StrandPartyKey` row → founder mint. `detachStrand` drops the entry; that covers `forgetJoinedStrand` and `stopStrand` (both reach `detachStrand`) and `handleStrandRemoved`.
- **Accepted-tradeoff `NOTE:` at `rememberFormedStrand`**: why the party-wide `JoinedStrand` row is still published by the reconcile pass and not in `formStrand`, with its revisit condition.

## Party-key deletion path

`ControlDatabase.deleteStrandPartyKey` exists, but nothing in `CadreNode` calls it (the only mention is an error message's text), so a map entry cannot go stale while the node runs. Nothing was added there. If a node-level rotation API is ever added, it must also drop `formedPartyKeys`.

## For the reviewer

- Check by reading the code that the reordered `rememberForeign` gives the same result as the old one in every case: identical record with party naming the strand, identical record with party not naming it, differing record with each, no record with each, and the early `list()` failing.
- A formation against a strand already running here (the removed-party re-formation case) leaves a `formedPartyKeys` entry until the next launch or detach. It holds the same value as the row, so a later launch that takes it returns the right key. Only a node-level party-key rotation would change that, and none exists yet (see above).
- The map is not cleared in `cleanup()`. A restarted `CadreNode` instance would keep entries from before the restart, but the values equal the persisted row. Clear it there if you want to be strict.
