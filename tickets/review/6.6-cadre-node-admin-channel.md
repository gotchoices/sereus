## What landed

The node side of `tickets/implement/6.7-cadre-host-authority-node-delegation` (the host side). `cadre-cli start` gains three flags and a loopback admin HTTP surface; cadre-core gains the authority-key bridge, the push-model invite-address resolver, and idempotent-genesis + membership-read helpers on `ControlDatabase`.

### cadre-core

- **`authority-key.ts` — `authorityKeyFromLibp2p(privateKey)`** (exported from `index.ts`). Bridges a libp2p Ed25519 key into the base64url `{ privateKeyB64, publicKeyB64 }` that `@optimystic/quereus-plugin-crypto` consumes. The encoding bridge (the flagged implementation risk) was verified end-to-end: libp2p's `Ed25519PrivateKey.raw` is 64 bytes (`[0:32]` = seed, `[32:64]` = pubkey); noble/the crypto plugin treats the 32-byte seed *as* the private key, so `getPublicKey(seed)` === `publicKey.raw`. The single-key path holds — **no** separate authority key is persisted; peer-id and authority pubkey are one keypair.
- **`CadreNode`** — added `get partyId`, `setInviteAddresses(string[]|null)`, private `resolveInviteAddresses()` (pushed addrs → config resolver → `getMultiaddrs()`), `listMembers()`, `isMember(peerId)`. Both `initializeSeedBootstrap` and `enableSeedListener` now wire the push-model resolver instead of the old config-only callback.
- **`ControlDatabase`** — added `hasAuthorityKey()`, `ensureAuthorityKey(key)` (idempotent genesis — inserts only when none present), `queryCadrePeers()`.

### cadre-cli

- **`admin-server.ts`** — `AdminServer` binds `127.0.0.1:<port>`, constant-time bearer check against `CADRE_STARTUP_TOKEN`, provider-style `{ ok, data }` / `{ ok:false, error:{ code, message } }` envelope. Codes→status: `not_authorized`→401, `not_ready`→503, `bad_request`→400, `internal`→500. Implements the 8 wire-contract routes; unexpected "not initialized / not running / must be started" errors classify to `not_ready`.
- **`start.ts`** — new flags `--authority` (genesis + seed-bootstrap init from identity), `--admin-port` (refuses to bind without `CADRE_STARTUP_TOKEN`), `--identity-protobuf <path>`. Admin server is started after authority init and closed on shutdown alongside the health server.
- **config loader** — `identity.protobufKeyFile` (+ `CADRE_IDENTITY_PROTOBUF` env, + `--identity-protobuf` flag routed through it) loads the installer's protobuf `identity.key` via `privateKeyFromProtobuf`; takes precedence over the raw/hex `keyFile`.

- `yarn workspace @serfab/cadre-cli test` — **20/20 pass** (admin-server auth + delegation + invite-push + bad-body + unknown-route; protobuf identity round-trip).

Manual smoke (not automated): point `identity.protobufKeyFile` at a cadre-host `identity.key`, run `CADRE_STARTUP_TOKEN=… cadre start -c cadre.json --authority --admin-port 7777`, then `curl -H 'Authorization: Bearer …' 127.0.0.1:7777/admin/identity`.

## Known gaps / risks (treat tests as a floor)

- **Pre-existing failing test directly on a route's code path.** `seed-bootstrap.spec.ts > authorizePeer / removePeer — round-trip against a real control DB` fails on master *and* here (confirmed by stashing) with a Quereus error: *"No row context found for column PeerId"* in the DELETE-with-context constraint path. This is **not** introduced by this ticket, but it exercises `CadreNode.removePeer` against a live control DB — exactly what `DELETE /admin/members/:peerId` delegates to. So that route's mock-level test passes, but the real signed-delete may currently throw `internal` against a real party. **The reviewer/6.7 should decide whether this Quereus bug blocks the delete route** and, if so, spawn a fix ticket (likely in the linked `../quereus` workspace, not this repo). The `POST /admin/accept-phone` → `authorizePeer` (insert) path is covered green by the same round-trip test's insert half historically; only the delete half is failing.
- **No end-to-end admin-channel integration test.** Admin-server delegation is tested against a mock `CadreNode`; there is no test that boots a real authority node + admin server + an HTTP client against a live control DB. Booting a real node is ~heavy/networked (existing node tests take ~0.4s but rely on empty bootstrap); a focused integration test (authority start → mint invite → accept-phone → list members over HTTP) would raise confidence and is a good review-stage add or follow-up.
- **`accept-phone` JSON typing.** `issuedInvite` is passed through from the request body as `CadreInvite` without schema validation beyond `phonePeerId` presence; malformed invites would surface as whatever `acceptPhone` throws (classified `internal`). Acceptable for a same-machine trusted caller, but note it.
- **`docs/architecture.md` not touched** — the ticket listed it in `files:` but the TODO only required the cadre-host.md note (done, prose-level, in the new "Node admin channel" subsection). 6.7 finalizes the host-facing doc and the topology reconciliation note.
- **Genesis idempotency semantics.** `ensureAuthorityKey` inserts only when the table is empty. On an existing party where this node's key is *absent* (a different authority founded it), genesis is skipped silently — correct per the ticket ("on an existing party the key is already present; skip"), but means a misconfigured node could run `--authority` without actually being an authority. No error is raised in that case.
