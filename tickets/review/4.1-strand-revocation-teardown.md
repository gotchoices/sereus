# Review: strand revocation teardown

Second of three tickets under `plan/4-removal-must-cut-the-network-not-just-the-row`.
The prereq ticket (`strand-revoked-peer-gate`) shipped the gate that refuses NEW streams,
dials, connections, and relay reservations from a revoked party's machines. This ticket
closes what is already OPEN, and gives a node a way to learn that IT was the one removed.
The third ticket (`4.2-strand-removal-e2e-and-docs`, still in `implement/`) proves the
whole claim on a real network and rewrites `docs/strands.md` — **no docs were touched
here, deliberately.**

## What landed

**Teardown sweep** (`strand-revocation-enforcer.ts`). Every deny-set refresh now also
hangs up every currently-connected revoked peer. The enforcer takes an optional
`getNetwork: () => StrandRevocationNetwork | undefined` — a three-member surface
(`peerId`, `getConnections()`, `hangUp(peer)`) that a real `Libp2p` satisfies
structurally — read lazily on each sweep, because the enforcer is constructed before the
strand's libp2p node exists and the node is dropped again on quiesce.

Two design calls worth a reviewer's attention:

- **Sweep by membership, not by an entered-the-set diff.** The ticket described "diff and
  hangUp, plus a membership sweep as a safety net". The sweep alone is a strict superset
  of the diff, so only the sweep is implemented; the module doc says so. Consequence: a
  revoked peer that is connected is re-swept on every poll until the connection is gone
  (the gater should keep it gone), i.e. a repeated `hangUp` on a peer that keeps
  reconnecting is possible and harmless.
- **The hangUp target is the connection's own `remotePeer` object**, never a string
  parsed back into a `PeerId` — no peer-id codec is pulled into this module. A peer
  holding two connections (say one direct, one relayed) yields ONE `hangUp`, which
  libp2p closes both with.

Every failure is contained: a missing/throwing network handle, a throwing
`getConnections`, and a rejected `hangUp` each cost only that pass and are logged; the
refresh loop survives and the next tick retries.

**On-demand refresh.** `StrandInstanceManager.refreshRevocationEnforcement(strandId)` →
`CadreNode.refreshRevocationEnforcement(strandId)`. Awaiting it resolves only after the
sweep, so "revoke, then refresh" is an immediate cut for the caller rather than a
scheduled one. Quiet no-op (matching `quiesceStrand`'s posture) for an unknown, quiesced,
open, or gate-disabled strand. `revokeMember` and `leaveStrand` in
`strand-membership-writer.ts` gained a doc note telling callers inside a cadre runtime to
follow the write with it.

**Self-revocation signal.** When the node's own peer id lands in the deny set, the
enforcer fires `onSelfRevoked` ONCE per enforcer lifetime (a resume rebuilds the enforcer
and may legitimately re-fire), which `StrandInstanceManager` tags with the strand id and
`CadreNode` emits as the new `strand:revoked` event. Nothing is torn down on our own
behalf — the other side's gate already refuses us — but every OTHER revoked peer is still
swept in the same pass. The event's doc in `types.ts` states the semantics: best-effort
(only if the tombstone replicated here before the cut), fires for a voluntary leave too,
and the app decides whether to stop the strand.

## How to exercise it

Unit (`yarn workspace @serfab/cadre-core test` — 114 files, 1941 passing, 1 pre-existing
skip). The new coverage is `describe('teardown sweep')` in
`strand-revocation-enforcer.spec.ts` (16 cases) and four cases in
`strand-instance-manager-revocation.spec.ts`:

- connected revoked peer hung up, live member left alone, disconnected revoked peer not
  called at all;
- sweep catches a peer that connects AFTER the revocation (the case a diff would miss);
- every machine of a multi-machine removed party; one call for two connections;
- rejected `hangUp` → refresh still resolves, retried next pass;
- `getConnections` throws / `getNetwork` throws / `getNetwork` returns undefined
  (quiesced) → refresh resolves, snapshot still updated;
- `stop()` landing before the read completes → no sweep at all;
- connection list is enumerated once per pass (a connection opened mid-sweep waits for
  the next pass);
- self-revocation: signalled once across refreshes, never hangs up itself, still sweeps
  others, survives a throwing handler, silent for a node that is simply not a member;
- manager level: the enforcer gets a LAZY node handle (asserted live, then `undefined`
  after quiesce), `onSelfRevoked` is tagged with the strand id, on-demand refresh
  delegates, and the four no-op cases resolve without touching the enforcer.

Validation run: `yarn lint` (clean), `yarn typecheck` at root (all workspaces, plus the
three coverage guards — clean), `yarn workspace @serfab/cadre-core test` (all green). No
pre-existing failures surfaced.

## Known gaps — treat the tests as a floor

- **Nothing here proves libp2p semantics.** That `hangUp` really closes a RELAYED
  connection, and really drops the relay reservation riding it, is asserted only as
  intent against a stub. Scenario 1 of `4.2-strand-removal-e2e-and-docs` is where that
  gets proven on a real relay.
- **No test asserts that `PeerJoinBackfill` stops pushing after the sweep.** The ticket
  asked for one. With a stubbed transport it would assert libp2p's behaviour rather than
  ours (the backfill pushes over a connection; closing the connection is what stops it),
  so it was left to the e2e. If a reviewer sees a way to assert it honestly at unit
  level, it is worth having.
- **A node with no `MemberPeer` row of its own never learns it was removed.**
  `strand:revoked` is derived from finding OUR peer id in the deny set, and the deny set
  is built from `MemberPeer` bindings. A node that never called `registerMemberPeer` has
  no binding, so no signal — silent, by construction. The e2e's scenario 5 registers peer
  ids, so it will not surface there.
- **Up to one poll interval of exposure** (default 30 s) between a revocation replicating
  and the session being cut, unless the app calls `refreshRevocationEnforcement`. Nothing
  calls it automatically, and nothing can today — see the module doc's seam argument.
- **`stop()` mid-sweep does not break the loop.** Remaining `hangUp` calls run against a
  stopping node and are caught + logged. Deliberate (cheap, and `stop()` does not always
  mean the node is going away), but a reviewer may disagree.
- The cohort-participation arm of the plan (TODO 5) was verify-don't-build and is
  unchanged: no code drops a revoked peer from the Optimystic cohort, because cutting
  the connection already does. The residual facts (the removed node keeps blocks it
  already replicated; blocks held only by its machines may need repair) are recorded as
  a `NOTE:` tripwire at `tearDownRevoked` in `strand-revocation-enforcer.ts` and are due
  to be stated in the 4.2 docs pass.
