# An invited machine does not publish the record its admission wrote

The redemption request already carried the device's signed `CadrePeer` address record, and the admitting member writes it on the device's row (`new-machine-self-record-written-once`). The device then wrote it again. `CadreNode.publishSelfRecordUnlessCurrent()` writes nothing when the own row still holds the record this process last signed (`lastSignedSelfRecord`), that record is under half a heartbeat old, and the node's addresses and profile are unchanged. Before this ticket only the boot timer used it, and only after an insert. Now that a reconnecting machine waits for its sibling to identify before writing (`reconnect-writes-wait-for-sibling-identify`), the remaining self-record writes can use it too.

## What changed (all in `cadre-node.ts`)

- **`redeemCadreInvitation`** sets `lastSignedSelfRecord = record` right after `signRedeemRequest`, before dialing. The member's commit can reach the device before the reply does, so a reconcile pass that reads the row first must already find it current. A failed redemption leaves a record that matches no row, so the next publish writes as usual.
- **`publishFirstSelfRecord`** (the reconcile pass's first publish) calls `publishSelfRecordUnlessCurrent()` instead of `registerSelf()`. Its NOTE is gone.
- **Boot timer** (`scheduleSelfRegistration`) calls `publishSelfRecordUnlessCurrent()` unconditionally. Its NOTE is gone, and so are the `lastSelfRecordRefreshedARow` field and the `rememberSignedSelfRecord` helper (nothing else read the field, so the two `publishSelfRecord` call sites assign `lastSignedSelfRecord` directly).
- **Drain step 2** (`runDrainControlReplication`): when a self write was made while alone, `registerSelf()` (always re-touch, since the re-touch is what carries the write to the cohort). Otherwise, on first growth, `publishSelfRecordUnlessCurrent()`. A restarted machine has `lastSignedSelfRecord === null` at first growth, so it still re-touches a row a prior process may have left local-only.
- **Docs**: Cadre Node step 4 says the invited device writes nothing once its row arrives. The self-registration paragraph lists the records the boot-time publish treats as current (the explicit insert, a restart's first-growth re-touch within that second, a redeemed invitation's record). "Writes made while alone" now describes the first-growth self re-touch and when it is skipped.

## For the reviewer

- **The "write alone, still re-touched" arm rests on `pendingSelfPeerWrite`.** If anything sets `lastSignedSelfRecord` for a write committed alone without also setting `pendingSelfPeerWrite`, the drain would judge that record current and skip it, leaving a fork. Today both `publishSelfRecord` write paths set the flag via `committedAlone()` right before the assignment. The redemption's assignment is not a local write, so it needs no flag.
- **I did not check that `control-write-while-alone-convergence` actually fails if the pending arm is removed.** The peer-join block catch-up might carry A's row to B anyway, in which case that scenario does not pin the arm by itself. Worth deciding whether a unit test on drain step 2 is worth its cost. I judged it not, because the branch is one ternary with a comment saying why.
- **A device that redeems twice in one process** (a second invitation after a failed first) overwrites `lastSignedSelfRecord` each time. That is harmless: the last record signed is the one any member could have written.
- **The cadre (`addDrone`) case was not re-measured.** It never sets `lastSignedSelfRecord` before first growth: M has no record, and A's explicit insert while alone sets `pendingSelfPeerWrite`. So by construction it takes the same paths as before.
