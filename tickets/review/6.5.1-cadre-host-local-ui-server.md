## What landed

A long-lived Fastify management server bound to `127.0.0.1:<uiPort>`, exported as `createLocalUiServer(opts)` and wired into `cadre-host start`. The CLI's existing `/auth/*` and `/nat/*` HTTP contract is preserved; new UI-only routes live under `/api/*`; a Server-Sent Events stream powers reactive updates.

### Files added

- `packages/cadre-host/src/server/`
  - `index.ts` — `createLocalUiServer` factory (event bus + handler wiring + lifecycle).
  - `server.ts` — Fastify bootstrap, port-fallback (`uiPort` → `+1..+9`), 5 s drain shutdown.
  - `origin-guard.ts` — onRequest hook (rejects non-loopback Host/Origin).
  - `error-handler.ts` — `setErrorHandler` mapping `TrustCircleError` / `NatError` / `UpdateErrorException` → status code; unknown → 500 `internal`.
  - `static.ts` — hand-rolled static mount with a placeholder HTML when `dist/ui/` is missing.
  - `settings-store.ts` — read/write facade around `host.config.json`.
  - `events/bus.ts`, `events/types.ts` — in-memory pub/sub with typed events.
  - `events/sse-route.ts` — `GET /api/events` (hand-rolled, ~50 LOC, heartbeat every 15 s, cleanup on disconnect).
  - `routes/trust-circle.ts`, `routes/nat.ts`, `routes/update.ts` — adapters around the existing typed handlers; publish bus events on side-effects.
  - `routes/status.ts`, `routes/nodes.ts`, `routes/settings.ts` — new `/api/*` routes.
  - `__tests__/` — bus, origin-guard, error-handler, status-route, nodes-route, settings-route, sse-route, publishers, server.smoke (44 tests across 9 files).

### Files edited

- `packages/cadre-host/src/orchestrator/host-process-orchestrator.ts` — minimal additions: `listNodes()`, `getNode(id)`, `resolveDockerId(id)`, `onStateChange(listener): () => void`. Emit on create / child exit / stop.
- `packages/cadre-host/src/orchestrator/types.ts`, `index.ts` — new `ManagedNodeInfo`, `NodeStateListener` types.
- `packages/cadre-host/src/bin/host.ts` — replaces the `TODO(cadre-host-local-ui)` marker in `start` with the full `createLocalUiServer` wiring; adds `cadre-host ui` subcommand.
- `packages/cadre-host/src/index.ts` — re-exports `createLocalUiServer`, `EventBus`, `HostSettingsStore`, `LocalUiEvent`, `ManagedNodeInfo`, `NodeStateListener`.
- `packages/cadre-host/README.md`, `docs/cadre-host.md` — Local UI section documenting binding, origin guard, API table, SSE events, write-whitelist, threat model, honest gaps.

## Use cases the reviewer should hit

- **Origin policy.** Verify that `Host: 127.0.0.1:<port>` and `Host: localhost:<port>` succeed; any other Host (including just-the-IP without port, or a different port) returns 403 with `{ ok: false, error: { code: 'forbidden_origin', message } }`. The `Origin` header is double-checked when present.
- **Port collision fallback.** Occupy `uiPort`, start the server, confirm it binds to `uiPort+1` and the console message reports the bumped port.
- **Error envelope.** Trigger every code in `TrustCircleError`, `NatError`, `UpdateErrorException` (the error-handler test exercises them) and verify each maps to the documented status; unknown errors come back as 500 `code: 'internal'`.
- **SSE liveness.** Open `GET /api/events`, do `PUT /nat/settings`, confirm a `connectivity-changed` event arrives. Disconnect, confirm `bus.listenerCount()` drops back to 0 (the SSE test asserts this).
- **Settings whitelist.** `PUT /api/settings { uiPort: 9999 }` → 400 `invalid_setting`. `PUT { upnpEnabled: false }` → 200 + propagated to NatService. `PUT { updates: { autoApply: true } }` → 200 + propagated to UpdateService.
- **Static mount.** With `dist/ui/` absent, `GET /` returns the placeholder HTML; with a file present at `dist/ui/index.html`, that's served instead. SPA fallback: requests for unknown HTML paths return `index.html` so client-side routes work; `/api/*` and `/auth/*` still 404 cleanly (don't fall through to the SPA).
- **Logs tail.** Create a `<workdir>/node.log` file and call `GET /api/nodes/<id>/logs?lines=N`; verify the response is the last N lines. `lines` is clamped to 1..2000. Missing file → `[]`.

## Honest gaps & known weaknesses

These are real and the reviewer should treat them as **starting points, not finish lines**:

1. **`/api/nodes/:id/start` and `/api/nodes/:id/restart` return 501 `not_implemented`.** cadre-host v1 doesn't yet have a "spawn the host's cadre nodes from trust-circle membership" path — `HostProcessOrchestrator.createContainer` needs a full `OrchestratorCreateRequest` (partyId, bootstrapNodes, profile), and there's no source of truth for which nodes the host should auto-spawn. Stop on a running node works (the route just calls `stopContainer`). Decide in review whether to (a) accept the 501 as a documented limitation and file a follow-up ticket, (b) extend `HostProcessOrchestrator` with a "respawn from saved cadre.json" path now, or (c) defer the whole `/api/nodes/:id/{start,restart}` routes until the spawner ticket lands.

2. **`cadre-host start` wires `TrustCircleService` and `NatService` with stub `CadreNodeLike` adapters** (`missingCadreNodeStub` / `missingNatNodeStub` in `bin/host.ts`). Listing the trust circle works (it reads the local labels file and gracefully degrades when the control DB is null), but `POST /auth/invites`, `DELETE /auth/members/:peerId`, and any invite-address resolution will throw → mapped to 500 by the error handler. **The installer's "first enrollment invite" still degrades silently for this same reason** (this was already the state pre-ticket, but is now more visible because the server is reachable). Inline-libp2p-node integration is the obvious next ticket.

3. **No `cadre-host install` smoke run.** Windows lacks `nssm.exe` on PATH in this sandbox, so the install path wasn't exercised end-to-end here; I wrote `host.config.json` by hand. Tests do cover the `HostConfigFile` v1→v2 migration, but a Linux/macOS reviewer running `cadre-host install` is the real proof.

4. **Update observer is poll-based, not change-driven.** The 60 s `setInterval` reads `UpdateService.getState()` and emits `update-available` only when the `version` field flips. This is cheap and simple; the alternative — adding a listener API to `UpdateService` — was deliberately avoided to keep the scope narrow. A consequence: an update that appears and disappears within the 60 s window is silently missed.

5. **SSE is hand-rolled.** ~50 LOC vs adding `@fastify/sse-v2` (which itself is ~150 LOC). The wire format is trivial and matches the EventSource spec; if browsers ever complain we can swap to the plugin without changing the bus contract.

6. **Static mount is also hand-rolled.** No range support, no ETag, no compression. Fine for a localhost SPA bundle; the `6.5.2-cadre-host-local-ui-spa` ticket can swap in `@fastify/static` if needed.

7. **No tests for the port-collision fallback.** The logic in `server.ts` is straightforward but only exercised via the explicit `forcePort: 0` test path. A reviewer could add a test that pre-binds `uiPort` and confirms the next port is chosen.

8. **No round-trip test for the trust-circle `redeemed` event.** The route adapter publishes `invited` and `revoked` but `redeemed` is published from `POST /auth/invites/:token/accept` — which doesn't exist as a route yet (redemption today is driven by the recipient's libp2p dial, not an HTTP call). Verify in review whether the SPA actually needs this; if so the right place to publish is wherever the cadre node calls `service.redeemInvite(...)`.

9. **Test environment quirks.** `nat-service.test.ts` runs in ~4 s due to the network probe; `orchestrator.test.ts` in ~8 s. Total suite is ~14 s on Windows. No flakes observed across two clean runs.

## Open design questions to confirm

- **Should `/api/settings` PUT'ing `uiPort` be a 400 (current) or 200-with-restart-required-flag?** The ticket said 400; I followed that. The SPA can still render it as read-only by reading the current value via GET.
- **Should the SSE route refuse origins that fail the guard at handshake time?** Currently the origin-guard hook runs first (so non-loopback origins never reach the SSE handler), which is the intended behaviour. Confirm the reviewer agrees this is sufficient — there's no separate WebSocket-style upgrade check needed because SSE is plain HTTP.
- **Should `EventBus` be exported publicly?** Currently yes, so subsystems (e.g. a future inline cadre-node) can `import { EventBus } from '@serfab/cadre-host'` and publish their own events without going through HTTP. If the reviewer disagrees, move it to an internal export.

## Suggested review focus

1. Read `src/server/index.ts` first — it's the wiring you'll keep coming back to. The `start()` method does the port-fallback, registers the origin guard with a port-getter (so the post-fallback bound port is honoured), and pushes teardown callbacks for the orchestrator/update observers.
2. Then `src/server/error-handler.ts` and `src/server/origin-guard.ts` — these are the security perimeter; everything else is plumbing.
3. Then walk through `bin/host.ts`'s new `start` body (the block replacing the `TODO(cadre-host-local-ui)` marker) and confirm the lifecycle ordering: orchestrator.init → trust-circle/nat construction → updateService.start → server.start. Shutdown is the reverse, with try-catch on every teardown so SIGINT during a partial bring-up still exits.
4. Finally `docs/cadre-host.md`'s new "Local UI server" section — confirm the API table matches the code and the honest-gap callouts are accurate.
