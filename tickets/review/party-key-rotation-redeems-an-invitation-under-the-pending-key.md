# Review: the party's key replacement in a strand another party manages

Implemented as the implement ticket specified; nothing was left out. The design decision (the host's re-invitation is the admission path; a by-hand manager admission works too; no request row in the strand) is recorded in `docs/strands.md` → "The host's re-invitation seats the new key", with the rejected alternative's reason in one sentence.

## What changed

**The rule.** While a `PendingStrandPartyKey` row exists for a strand, the membership reconciler never writes a `Strand.Member` row under the party's current key K, which the removed machine holds. Step 2 of each pass now reads the pending state once at the head (`PartyStrandPeerSource.pendingKey`, replacing `isRotationPending`) and branches:

- **No rotation pending**: today's logic, moved unchanged into `ensureMembershipUnderOwnKey`.
- **Pending, key not readable here** (`key: null`: sealed to other machines, ephemeral identity, or the read rejected): neither consume nor burn. A staged invitation is left staged with one debug line, the pass is idle (flat poll interval), and the pass does not count toward the "probable blocked re-join" warning (`inviteLeftStagedDeliberately`, reset at the head of each pass; such a pass neither counts nor ends the streak).
- **Pending, key opened**: if the new key N is already a member, burn a staged invitation against N (or idle when nothing is staged) and kick the driver; else if an invitation is staged, `consumeInvite` with N's public half and kick the driver on success; else idle. A refused consume routes through `handleConsumeFailure` as before, except `sealed`, which under the pending key drops the dead invitation and idles rather than stopping the loop for good (the party may still be a member under K, whose bindings the loop keeps whole).

`ensureMembership` still answers "is K a member", read once at the head, so the binding steps that follow stay under K until the swap. `clearRemovedMachines` takes the pending flag instead of reading the seam. `latchDone` never latches while a rotation is pending (one debug line per re-arm cycle), so a by-hand admission or a sibling's redemption is noticed on the next pass and the driver kicked; the swap's `rekeyParty` rebuilds the loop under N and its next pass clears the removed machine's stale binding and latches done as before.

**The kick.** New reconciler dep `onPendingKeySeated`, wired by `armMembershipReconciler` from the new `StartStrandConfig.onPartyKeySeated`, which `launchStrand` sets to `driveRotationIfPending(strandId, 'the pending key is seated in the strand')`. That method already refuses on a non-owner, a non-recipient and a removed node.

**The seam in `CadreNode`.** One private `readPendingPartyKey` returns `none | opened | closed(why)`; the driver's `openPendingPartyKey` throws `why` on `closed` (unchanged contract), the reconciler's `readPendingPartyKeyState` answers `{ pending: true, key: null }` for it.

**The driver.** Documentation only: step 2's blocked branch says what seats K' from outside and that the reconciler kicks the driver; a `NOTE:` tripwire at `cleanUpSuperseded` for a superseded key holding a seat in a strand the party does not manage (only that strand's manager can revoke it; seal the superseded private halves into the row if ever hit).

**Docs.** `docs/strands.md`: the "A strand the party does not manage" bullet rewritten, a new "The old key when the party cannot leave" bullet (the host revokes K by hand; the party re-joins after deleting its own `StrandPartyKey` row), a new `####` subsection "The host's re-invitation seats the new key" (the flow, what the host sees, the two limits), and the bearer-invite and read-secret bullets under "What removal still does not do" extended. `docs/architecture.md` "Removing a machine" states the flow in one sentence and links the strands section. Every reference to `plan/party-key-rotation-across-parties` in `types.ts`, `machine-removal.ts` and the driver now points at the doc section.

## For the reviewer

Starting points, in rough order of how much judgment they carry:

- **A rejected pending-key read now delays the ordinary redemption under K by one pass.** Before, only step 5 read the seam, so a failed control read never touched the join. Now `readPendingKeyState` treats a rejection as "pending, key unreadable" and the pass neither seats K nor burns. On a stopped node that is moot; on a transient control read failure it costs one idle pass. The ticket asked for this posture ("treat a rejection as pending, as today"); check that no existing flow relies on step 2 running while the control database is briefly unreadable (e.g. a formation's join finishing while the control store reconnects).
- **The N-already-member branch kicks on every pass** until the swap rebuilds the loop. On an owner machine that is seconds; on a non-owner machine that can read the key, each kick logs one refusal line in `driveRotationIfPending`. The `NOTE:` at `kickRotationDriver` says how to bound it if the log ever matters.
- **Idle versus ladder in the pending branches.** Left-staged, nothing-staged and N-seated-with-nothing-staged passes are idle (flat poll); a redemption or burn, success or refusal, follows the existing ladder. `latchDone` in the pending case touches neither, so a refused consume under N keeps the ladder it got from `handleConsumeFailure`.
- **`handleConsumeFailure`'s `under` parameter** defaults to `'own-key'`; only `seatPendingKey` passes `'pending-key'`. A discriminated argument rather than a second method, to keep the busy, half-committed, dead and retry arms single-sourced.
- **The anchor** `#the-hosts-re-invitation-seats-the-new-key` in `docs/strands.md` is a `####` under "Replacing the party's key"; check the heading slug renders as linked.
- **Edge cases from the implement ticket covered by inspection, not tests**: K has left but the swap has not replicated here (the pending branch never seats K, same code as the tested case); two owner machines redeeming one invitation (`ConsumedInvite`'s primary key, existing dead-invite classification); N admitted by hand while an invitation is also staged (the burn arm with N's keypair, existing code); the join never finished before the removal (the driver's `stepDown` finds K no member and writes nothing, the same driver branch the crash-point matrix already covers).
