# `CADRE_CLAIM_SECRET`, claim state on `/status`, and the phone-claims-a-node scenario

Third of three tickets (after `node-claim-proof-and-policy` and `node-claim-gate-and-helper`, both landed). It puts the claim mechanism on the headless CLI and proves the whole flow with real processes. This handoff is a starting point for review, not a finished verdict.

## What shipped

**cadre-cli**

- `CADRE_CLAIM_SECRET` is in `COMMAND_ENV` (`config/env.ts`). It is read from the environment only, and a set-but-empty value counts as unset (`specifiedEnv`).
- `start.ts`: `refuseClaimConflicts` runs right after the startup-token write and before `resolveConfig`. It names every conflict in one error: `--owner`, `--seed`, `--invitation`, `--pin-owner-key`, `CADRE_OWNER_KEYS` (a whitespace-only pin list does not count). `--listen-for-seeds` is allowed. The secret is passed as `CadreNodeConfig.claim`. After `node.start()` the CLI prints `✓ Awaiting claim`, or `• Already claimed; CADRE_CLAIM_SECRET is ignored` on a restarted claimed node; the ticket did not ask for the second line. `claim:accepted` prints `✓ Claimed by owner <first 8 chars>`. The secret is never printed.
- `/status` (`server/health.ts`) has a new `node.claim: ClaimState` (`'awaiting' | 'claimed' | 'none'`, exported). `HealthServerOptions.claimConfigured` turns it on. **Design choice to check:** `isAwaitingClaim()` is false until `start()` builds the anchor, and the health server binds before `start()`. So `claimState()` reports `claimed` only when the node is running and not awaiting. A starting node (claimed or not) reads `awaiting`, never a premature `claimed`. Documented at the method and in the README.
- README: a row in the env table, and a new "Waiting to be claimed" section covering what an unclaimed node admits, that the secret is one-time and bound to the peer ID, that a claimed node ignores it, the `/status` values, the conflicts, and that the config must name the claimant's party.

**cadre-core: a fix outside the ticket's `files:`.** The scenario's first run failed at step 3. The claimed node never published its signed address record within 90 s, because:

- `claimNode` writes the node's `CadrePeer` row only after the claim is accepted.
- The node's boot-time publish and its first-growth drain had already run, found no row and skipped. The first growth was the claimant's seed connection.
- Nothing else re-triggers the publish before the 7.5-minute heartbeat.

The existing `NOTE:` at `startRecordRefresh` predicted this case ("a node AUTHORIZED AFTER IT BOOTED can wait a whole heartbeat"). Two changes:

- `publishSelfRecordOnceClaimed()`: called from `runReconcileControlCohort` right after `refreshMembershipGate`. On a node with `config.claim`, claimed, that has not published this session, it calls `registerSelf()` on each pass until the first publish lands. It is limited to claim nodes on purpose: an unconditional version would change the pinned counts in `control-founding-consult-budget.spec.ts`, which disarms the self-registration timer. The rewritten `NOTE:` at `startRecordRefresh` says to drop the claim condition if late enrollment becomes common. It also says the membership-change seam the old note suggested fires on local commits only, so it would not catch a row written elsewhere.
- `publishSelfRecord`'s no-row branch checks `seedBootstrapService?.canAuthorize()` instead of only checking that the service exists. A listener-only service (every claim node has one) has no owner key, so `insertSelfPeerRecord` used to throw. It now skips with the existing log line. Without this, the new per-pass call would throw on every pass until the row arrived.
- `docs/architecture.md`: the claim-secret entry says a claimed node publishes from its reconcile pass.

**Integration harness.** `scrubbedParentEnv`, `isChildUp`, `allocFreePort` and `resolveCadreCliBin` moved from `provider-process-orchestrator.ts` into `child-node-fixtures.ts` and are exported. A new `stopChildProcess` (SIGTERM, then SIGKILL after a timeout) was pulled out of `ProviderProcessOrchestrator.stopContainer`. The move does not change behaviour; `provider-seed-accepted` is still green.

**Docs.** `docs/architecture.md` → Which Side Dials has row 8, and the paragraph after the table now says "rows 1, 2 and 8". The claim-secret entry names the cadre-cli surface. `docs/testing.md` → Topology coverage map has a bullet for the new scenario. The vitest `include` glob (`src/**/*.integration.ts`) picks the file up, so there was nothing else to register.

## Tests

- **Added: `packages/integration-tests/src/scenarios/node-claim-by-phone.integration.ts`.** A real `cadre-cli` child: storage profile, `/ws` on loopback, identity file, file storage and node-state directory in one workdir, admin channel on. The claimant is an in-process phone-shaped owner of the same party. One `it` per step:
  1. Child `/status` is healthy with `claim: 'awaiting'`. The claimant starts, runs genesis, and publishes its own row explicitly with `registerSelf` (step 3 looks for that row). `getMultiaddrs()` is empty.
  2. Wrong secret → `ClaimRefusedError` with `code: 'claim-proof-invalid'`. `/status` still says awaiting. The claimant has no `CadrePeer` row and no `BootstrapPeerStore` entry for the node.
  3. Right secret → `/status` says `claimed` straight away. The claimant holds an outbound connection, and the child reports a WebSocket connection. The claimant is in the child's authorized set (`GET /admin/authorized-members/:id`). The child's signed record resolves on the claimant with a `/ws` address. The log has `✓ Claimed by owner <prefix>`. This is the step that reproduces the cadre-core gap: it timed out before the fix and takes about 16 s after it (one 15 s reconcile pass).
  4. An owner of another party presents the same secret → `already-claimed`. A `NOTE:` there records that this answer reaches the rival only because a storage-profile node runs the relay server (the gate answers `'admit-for-relay'`). With the relay off, the rival gets a dial error instead.
  5. The same owner claims again: resolves, one `CadrePeer` row for the node, and the dial-target store holds just the node.
  6. The child is stopped and relaunched with the same args and environment. `/status` says `claimed`, the log says `• Already claimed`, and the claimant opens a new outbound connection. The log (both runs) never contains the secret.
- **Edited:** `cadre-cli/test/status.spec.ts`. The `HealthStatus` fixture gains `claim: 'none'`, which the type now requires.
- **None added for** `refuseClaimConflicts` (checked by inspection, as the ticket said, plus one manual run that printed `CADRE_CLAIM_SECRET cannot be combined with --owner, --seed, CADRE_OWNER_KEYS …` before any config load), nor for `/status`'s field or the cadre-core fix, which the scenario covers. A reviewer may want a cadre-core spec for `publishSelfRecordOnceClaimed` at a lower layer. I judged the scenario's step 3 to be that reproduction, because the gap needs a remote owner writing the row after the node is connected.

## Known gaps and things to weigh

- **Party id.** A claim decides who owns a node, not which party's control network it serves. `verifyAndMergeSeed` never compares the seed's party with the node's. So the scenario configures the child with the claimant's party, and the README says the config must name it. The QR payload planned in `cadre-host-join-a-cadre` carries no party id. I added this, and the relay point above, as a "Note from `node-claim-cli-and-scenario`" section on `tickets/plan/3-cadre-host-join-a-cadre.md`. I did not file a ticket, because that plan owns the decision.
- Step 6 does not pin which dial source the claimant reconnects on. The retained dial target and the node's fresh signed record both survive, as in the donation-phone scenario's step 6. There is a `NOTE:` at the step.
- The CLI message `• Already claimed …` and the `awaiting`-while-starting rule on `/status` are my additions or interpretations; the ticket asked for neither. Both are documented.
- `publishSelfRecordOnceClaimed` costs one `CadrePeer` read per reconcile pass on a claimed node that never publishes (one later removed from its cadre). This is stated in its doc comment.
