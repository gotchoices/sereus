# `publish-package` gained a dist-tag and a prerelease guard

## What changed

`scripts/publish-package.js` → renamed and converted to `scripts/publish-package.mjs` (ES module;
it was the last CommonJS file under `scripts/`). Same CLI entry point (`node
scripts/publish-package.mjs <package-name>`), now optionally followed by `--tag <dist-tag>`.

New behavior, in `scripts/publish-package.mjs`:

- **`resolveDistTag(argv, env)`** — exported pure function. Precedence: `--tag <name>` on argv >
  `SEREUS_DIST_TAG` env var > nothing (npm's own `latest` default applies, and no `--tag` flag is
  passed to `yarn npm publish` in that case). Validates tag shape
  (`/^[a-z0-9][a-z0-9._-]*$/i`) and rejects a tag that is itself a valid semver version. Throws a
  loud error on an unrecognised `--` flag, on `--tag` as the final argument with no value, and on
  `--tag ""`.
- **`assertDistTagForPrerelease(manifestName, version, tag)`** — exported pure function. Refuses
  (throws) when `version` has a semver prerelease component and `tag` is `undefined`. Passes for
  every other combination, including the deliberate escape hatch `SEREUS_DIST_TAG=latest` (tag
  resolves to the literal string `'latest'`, which is treated as an explicit decision, not an
  absent one). Called in `main()` *before* `yarn clean && yarn build` — a refusal costs seconds,
  not a full rebuild, and `yarn pub` is six sequential publishes so this must fire per-package
  before that package's own build, not once at the top of the chain.
- **`publishCommand(tag)`** — exported pure function; builds the `yarn npm publish` command,
  omitting `--tag` entirely when `tag` is `undefined` rather than passing an explicit `--tag
  latest`.
- **`readManifest(packageDir)`** — exported; reads `package.json`, throws a clear error naming the
  manifest path if `version` is not valid semver.
- The `cadre-host` release-key placeholder guard (`assertReleaseKeyEmbedded`, unchanged logic) still
  runs after `yarn build`, independent of the new prerelease guard — both can fire for the same
  invocation, whichever hits first.
- `main()`'s invocation at module load is guarded (`process.argv[1]` vs `import.meta.url` via
  `pathToFileURL`) so the test file can `import` the pure functions above without triggering a real
  `yarn clean && yarn build && yarn npm publish` as a side effect of loading the module.

Root `package.json`: the six `pub:*` scripts now point at `publish-package.mjs`; added
`test:publish-package` (wired into `yarn test`).

`scripts/smoke-published-install.test.mjs`: added one fixture case
(`publishableWorkspaces matches a \`publish-package.mjs\` script body, not only \`.js\``) so
`scripts/lib/published-smoke-support.mjs`'s `/publish-package\.(?:js|mjs)\s+(\S+)/` regex is pinned
against both spellings — the pre-existing fixtures still use `.js`, so that direction stays covered
too. `scripts/lib/published-smoke-support.mjs` itself is unchanged.

`docs/releasing.md`: "Prerelease / RC" section now gives the real working commands
(`SEREUS_DIST_TAG=alpha yarn pub` for POSIX and PowerShell, `yarn pub:cadre-core --tag alpha` for a
single package) instead of the old "publish by hand from each package directory, this ticket isn't
done yet" fallback. Checklist item updated to match. The "interim release" runbook's step 6 (further
down the same file) is also updated to real `yarn pub:<name> --tag alpha` commands per package —
it previously said "once this ticket lands, this collapses to `yarn pub --tag alpha` minus
`strand-proto`", which turned out not to be quite right: `--tag` on the `yarn pub` chain itself only
reaches the last of its six `&&`-ed commands (see "Why both forms exist" below), and `strand-proto`
is baked into that chain regardless, so publishing five-of-six under a tag still means five
per-package invocations, just now with `--tag` instead of hand-typed `yarn clean && yarn build &&
yarn npm publish --tag`.

`docs/cadre-host.md` and a doc-comment in `packages/cadre-host/src/update/release-key.ts`: updated
the two remaining `scripts/publish-package.js` references to `.mjs`.

## Why both forms exist (`--tag` vs `SEREUS_DIST_TAG`)

`yarn pub` is `yarn pub:strand-proto && yarn pub:quereus-plugin-sereus && ... && yarn pub:cadre-host`
— six sequential commands. `yarn pub:cadre-core --tag alpha` works because yarn appends trailing
args to that one script. `yarn pub --tag alpha` would **not** tag the whole chain — the flag reaches
only the last command (`cadre-host`), silently leaving the first five at `latest`. `SEREUS_DIST_TAG`
is an environment variable, so it's visible to every command in the chain:
`SEREUS_DIST_TAG=alpha yarn pub` tags all six. Do not "fix" `yarn pub --tag` to work — see the
Design section of the original ticket for why the env var is the intentionally honest mechanism, not
a workaround.

## How to verify

Pure-function unit tests only — nothing here calls `yarn npm publish` or the network:

```bash
yarn test:publish-package             # scripts/publish-package.test.mjs — 16 cases
yarn test:published-smoke-support     # scripts/smoke-published-install.test.mjs — 23 cases
yarn lint
yarn dep-check                        # knip + check:dep-ranges — confirms the .js→.mjs rename
                                       # needed no knip.ts change (scripts/** is fully ignored there)
```

All four ran clean during implementation. `yarn dep-check` also confirms
`publishableWorkspaces(rootDir)` still derives the correct six-package set from the real root
`package.json` after the rename (verified by hand with a one-off `node -e` import during
implementation, in addition to the test suite).

**Not run, deliberately:** `yarn npm publish` itself, and therefore no real dist-tag ever got set on
anything. The ticket explicitly asked for dry verification only.

Manual read-through worth doing in review: `scripts/publish-package.mjs` main() (not unit-tested,
by the same convention `smoke-published-install.mjs`'s orchestration isn't) — confirm the guard
ordering (`readManifest` → `resolveDistTag` → `assertDistTagForPrerelease` → chdir/clean/build →
cadre-host key guard → publish) matches what the ticket asked: prerelease guard before build,
independent of and not reordering the existing key guard.
