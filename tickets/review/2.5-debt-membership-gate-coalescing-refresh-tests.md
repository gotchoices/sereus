# What this change is, in plain terms

A cadre node keeps an in-memory list of which peer IDs are allowed to open control-database
streams to it. That list used to be rebuilt only by whoever happened to remember to ask —
every code path that added or removed a member had to call a refresh method by hand, and a
path that forgot left a freshly-admitted member locked out for up to ~15 seconds (until the
next timed reconcile).

The change moves that obligation to the one place a membership write cannot avoid: the
control database's `CadrePeer` mutation wrapper. It now notifies a listener after each
committed write, and the node wires that listener to its own refresh at startup. Twelve
hand-written refresh calls collapsed to five, and the five that remain are for changes that
write no local row (rows arriving by replication, or a newly trusted owner key flipping
already-present rows from unauthorized to authorized).

The refresh itself coalesces: concurrent writes share one database read, and a caller still
always observes its own change by the time its write resolves.

Production code and docs landed in the earlier phase of this ticket. **This phase added the
tests and ran validation.**

# What was added this phase

## `control-stream-authorization.spec.ts` — 8 new cases

The describe block was renamed from `(the below-the-wrapper obligation)` to
`(write-driven, coalescing)` — the obligation is what the change deleted, so the old title
described the world that no longer exists. The file header comment was updated to match.
A local `write(node, body, reason)` helper routes each case through
`fakeDb(node).mutateCadrePeer`, which is exactly the seam a real writer goes through.

- **`admits a peer written by a service built OUTSIDE CadreNode`** — the shape that was
  historically missed. A caller-constructed `SeedBootstrapService` never receives
  `CadreNode`'s seed event callbacks, but it still writes through the ControlDatabase it was
  handed, so the notify fires anyway. Gate flips false → true across the write alone.
- **`drops a removed peer from the snapshot by the time the write resolves`** — splices the
  row out inside the mutation and asserts the caller's `await` already sees the post-removal
  snapshot. Keeps a second member alive so the snapshot stays non-empty and the deny is a
  real deny, not the cold-start admit-all. Does NOT re-assert hub-side commit ordering —
  `control-membership-hub.spec.ts` owns that against a real DB.
- **`fires no refresh when the mutation body throws`** — asserts the read counter is
  unmoved. The fake deliberately leaves the pushed row behind after the throw (a real DB
  would roll it back) so "no membership read was issued" is provable from the gate too, not
  only from the counter.
- **`a failing refresh does not make the write reject`** — swaps `queryCadrePeers` for a
  thrower; the write still resolves and the previous snapshot survives intact.
- **`coalesces a burst of concurrent writes, and still admits every writer own peer`** —
  the load-bearing one. Four concurrent writes, with every membership read held open by the
  test until released, and a wrapped listener counting entries so the release happens only
  after all four have marked the snapshot stale. Asserts the burst costs exactly **2** reads
  (one already in flight when the burst landed, one more to cover it) — strictly fewer than
  the four writes — AND that each writer's promise resolves with its own peer already
  admitted.
- **`collapses a whole write-while-alone drain into ONE refresh`** — drives the real
  `drainPendingPeerWrites` over three queued re-issues (faking `queryPeerRecord` +
  `seedBootstrapService.canAuthorize`/`reauthorizePeer`), asserting a read delta of exactly 1
  and all three peers admitted. This is the `deferMembershipGateRefresh` scope under its
  actual caller, not a direct call to the private method.
- **`raises no refresh once the membership listener is detached`** — what `cleanup()` does
  before closing the DB; a later write raises no read.
- **`a self-row insert leaves the cold-start snapshot empty`** — the `registerSelf` carve-out.
  Self is filtered out of the authorized set, so the automatic refresh must not turn an empty
  snapshot non-empty and thereby close the cold-start admit-all path.

## `seed-bootstrap.spec.ts` — real-DB assertions

The existing `authorizePeer` / `removePeer` round-trip against a live Quereus control DB now
also asserts the node's gate snapshot (via a new private-field accessor `gateSnapshot`) at
three points: after the insert, after the delete, and after the re-insert. **No test code
calls a refresh** — that is the assertion. This is the only coverage where the notify travels
through the real `ControlDatabase.mutateCadrePeer` (write lock, transaction, commit boundary
assert) rather than the fake.

## Tripwire recorded (not a ticket)

A `NOTE:` on `drainMembershipGate` (`packages/cadre-core/src/cadre-node.ts` ~L4030). The
method is correct only because its stale flag is guaranteed true at entry — its sole caller
sets it synchronously with no await in between. If it were ever entered with the flag already
clear, the body would never suspend, so its `finally` would null the single-flight slot
*before* the caller's `??=` filled it; the slot would then hold an already-settled promise
that every later refresh reuses, producing an await/re-check spin. Unreachable today (one
caller, and it marks the flag first), so it is documented at the site rather than filed.

# Known gaps — please treat these as the starting point

- **Integration scenarios not run.** `push-wake-e2e` and `control-stream-authz` were NOT
  executed this phase (run cut short by the token budget). `push-wake-e2e` is the real
  end-to-end proof of the change: its `seedReceiverRecord` no longer calls
  `refreshMembershipGate()` at all, so if the automatic notify does not reach the gate over a
  real network the receiver never admits the sender's control stream and the scenario fails.
  **Running it is the single highest-value review action.**
- **The exact-count assertions are impl-shaped.** `expect(db.peerQueries - before).toBe(2)`
  (burst) and `toBe(1)` (defer scope) pin the current read pattern, not just the coalescing
  property. Each is paired with (or implies) the weaker `< N` claim. If a future refactor
  changes the read count legitimately, these are the tests that will complain; judge whether
  that precision is worth the brittleness.
- **The burst test's determinism relies on a wrapped listener counter.** The test replaces
  the node's wired listener with a counting delegate to know when all four writes have marked
  the snapshot stale. That is white-box. Worth a look for whether it can drift from what
  `inject` wires.
- **`deferMembershipGateRefresh`'s instance-level depth counter is untested for the
  suppression case it documents** — a genuinely concurrent EXTERNAL write during an open
  defer scope has its refresh deferred to scope exit. The two scopes in the codebase
  (`drain-reconstruct`, `drain-reissue`) are short, so this is documented behavior rather
  than a defect, but no test pins it. Confirm no scope has grown long-lived.
- **No test drives `reconstructAuthoredMembership`'s defer scope** (only
  `drainPendingPeerWrites`'). Both wrap the same helper, so the risk is low, but the coverage
  is asymmetric.
- **The removal case runs against the fake, not a real DB.** The real-DB removal path is
  covered by the seed-bootstrap assertion added above; the unit case only proves the
  snapshot is current when the caller's promise resolves.
