# Phone reference app: first launch asks before founding — review handoff

## What landed

- **Hook (`use-cadre.ts`):** `savedStartRead: 'reading' | 'read' | 'failed'` — how the launch read of the saved start went. **Deviation from the plan:** the plan named a boolean `savedStartLoaded`, but the read failing leaves status `idle` (it only sets the error line), so a boolean "resolved" cannot tell Settings not to ask after a failed read. A three-state value does.
- **Hook, `start`:** on success it now sets `savedStartOptions` (`getRunningOptions() ?? opts`). Before, the state was set only by the launch read and by a join/dissolve, so after a first-launch **No → Connect → Disconnect** the question would have come back mid-session. Side effect: Settings' existing effect refills the Connect form from the started options (the form is hidden while connected, so no edit is overwritten; after Disconnect it shows the generated party id, which `handleConnect` already put there).
- **Settings (`app/settings.tsx`):** `noCadreYet` = read succeeded and nothing saved; `asking` = `noCadreYet && status === 'idle' && joinFlow === null`. Node card branches, in order: connected; switching ("Joining your cadre…" when `noCadreYet`, else "Switching cadre…"); launch read still pending (status line only, no Connect flash); question (`FirstLaunchQuestion`, Yes/No); Yes state (status line, hint, **Back**); Connect form. The answer is screen state (`firstLaunchAnswer`), not saved. The waiting-node-code hint is now one element (`nodeCodeHint`) shown under the question, the Yes state and the Connect form.
- **Join section:** rendered from the single existing slot, with `|| firstLaunchJoin` added to its condition, so the same instance stays mounted from Yes through the join flow (a failed first-launch join keeps the paste). `firstLaunch={noCadreYet}` uses the shorter intro line the join ticket already added; nothing else in `JoinCadreSection` changed.
- **Test ids:** `btn-first-launch-join`, `btn-first-launch-fresh`, `btn-first-launch-back`.
- **Maestro:** `_setup.yaml` now waits for and taps **Yes, join my cadre**, pastes `CADRE_INVITATION`, Join, waits for the done step, OK, then creates the strand. `flows/4-solo-create-strand.yaml` (not in the plan, but it would have broken: it taps `btn-connect` on a fresh install) taps **No, start fresh** inside a `runFlow when: visible`, because the NativeScript app reuses the flow and has no question. `scripts/run-e2e.mjs` describes no setup steps, so it was not changed.
- **Docs:** `reference-app-rn.md` — "Joining an Existing Cadre" gains a **First launch** paragraph and the switching-row wording; Step 3 of the startup sequence mentions the question; the flows table and `_setup` paragraph. `reference-app-ns.md` — flow 4's conditional tap.
- **Filed** `tickets/blocked/rn-device-run-join-existing-cadre.md` covering this ticket and its three RN prereqs.

## Known gaps / things to check

- **Flow 4's conditional tap relies on Maestro's `when: visible` waiting like an optional lookup** (I believe several seconds by default), which covers the launch read the question waits on. If it evaluates instantly and the read is slow, the RN run would fail at `scrollUntilVisible btn-connect`. Device run will tell.
- **NativeScript flows 1–3 were already diverged** before this ticket (NS docs still describe `_setup` asserting a "Joined cadre" modal, which the RN join ticket replaced with the join-flow done step); this ticket diverges `_setup` further (NS has no `btn-first-launch-join`). Not addressed here.
- `firstLaunchAnswer` stays `'join'` after a successful join; harmless because `noCadreYet` is then false, so it is never read again.
- Edge cases from the plan (read resolving after mount, push wake on fresh install, Yes then join fails → status `idle`, joinFlow null, question's Yes state remains; No → Connect fails → status `error`, no question) checked by inspection only. A first-launch join failure goes through `adoptRunningNode`, which sets `idle` unless the kit itself reports `failed` (then `error`, and the Connect form shows instead of the Yes state).
