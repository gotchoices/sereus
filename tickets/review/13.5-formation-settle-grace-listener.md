## What landed

`FormationListener.provision()` used to run the `provisionStrand` hook under the whole
`provisionTimeoutMs`, pass no cancellation signal, and — on expiry — reply
`approved: false, reason: 'Formation provisioning timed out'` while the abandoned hook kept
running and spent the joiner's single-use invite ~100 ms later. The joiner then got
`'Invalid token'` on every retry: a permanently unusable invitation indistinguishable from a
genuinely bad one.

The budget is now split, with the grace carved **out** of `provisionTimeoutMs` (never added
on top, so the nested ladder — hook 10 s < provisioning 12 s < initiator await 15 s <
session 30 s — is unchanged):

```
graceMs = min(PROVISION_SETTLE_GRACE_MS /* 2_000 */, floor(provisionTimeoutMs / 2))
workMs  = max(1, provisionTimeoutMs - graceMs)
```

When `workMs` expires the listener aborts an `AbortController` threaded into
`provisionStrand`'s 4th arg (the plumbing from prereq `formation-abort-signal-plumbing`),
then `settleWithinGrace()` waits out `graceMs`:

| provisioning settles within the grace as | listener replies |
| --- | --- |
| approved | the real approval (identity + cadre + provision result disclosed as usual) |
| rejected (`approved: false`) | that rejection reason, non-disclosing |
| threw (incl. `FormationAbortedError`) | `approved: false, reason: 'Formation provisioning timed out'` |
| still pending at grace end | same timed-out reply; late-settle logged via `void pending.then(...)` |

`runSession` is unchanged — its `!outcome` / `!outcome.approved` / approved branches already
covered every row. The reply string `'Formation provisioning timed out'` is byte-identical to
before (three pre-existing tests assert it).

Docs: `docs/architecture.md` "Strand Formation" — the nested-timeouts paragraph now names the
settle grace inside the 12 s, and a new paragraph states that an overrunning provisioning is
ABORTED (invite left unspent when the recorder observes the signal), that a late success
inside the grace is adopted and reported as an approval, and that the 10 s default work
budget now equals the approval hook's own 10 s so a dead hook races two retryable,
invite-preserving rejections.

## Use cases to exercise / validate

- **Late success is adopted, not denied.** Hook writes its `FormationUsage` insert after the
  work budget expired but before the grace ends → joiner must be told `approved: true` with
  the strand disclosed. Covered: *"adopts a provisioning that lands inside the settle
  grace…"* (`provisionTimeoutMs: 400` → 200/200, hook writes at 300 ms). It also asserts the
  second presentation of the same token gets `'Invalid token'` — correct, because that spend
  belongs to a join the joiner was *told* succeeded.
- **Abort before write leaves the invite retryable.** Hook rejects on `signal` without
  writing → session 1 replies timed out with the use counter still 0, and session 2 with the
  *same* contact frame forms the strand. Covered: *"leaves the invite unspent when the hook
  observes its abort…"*.
- **The grace must not extend the ladder.** A signal-ignoring never-settling hook under
  `provisionTimeoutMs: 500` must be answered at ~500 ms, not ~750 ms. Covered:
  *"carves the settle grace OUT of provisionTimeoutMs…"* (asserts elapsed ≤ 700 ms; observed
  524 ms).
- **The hook actually gets cancelled.** The pre-existing never-settles test now captures the
  4th arg and asserts `capturedSignal?.aborted === true` after the reply.
- **Real end-to-end spend accounting** is exercised only against the `MockStream` harness
  here — see gaps.

## Known gaps / where to push

- **No integration-level test.** Every new test drives `FormationListener` through the
  in-memory `MockStream` with a hand-rolled `provisionStrand`. The real
  `ControlFormationUsageRecorder` signal checks were tested by the prereq ticket
  (`control-formation-recorder.spec.ts`, `control-formation-invite.spec.ts`), but nothing
  asserts the *composed* behavior — listener abort → recorder abandons → `FormationUsage`
  row genuinely absent from the DB. A reviewer could reasonably want that in
  `integration-tests` or a manager-level spec.
- **Timing-based tests.** Three of the four rely on real `setTimeout` and one on wall-clock
  elapsed (≤ 700 ms with a 500 ms budget, so ~200 ms of CI jitter headroom). They passed
  locally at 309 / 61 / 524 ms. If CI proves flaky the fix is a wider bound, not a skip.
- **Grace clamp interacts with tiny configured budgets.** `floor(provisionTimeoutMs / 2)`
  means a small `provisionTimeoutMs` halves the work budget. Verified against all five
  pre-existing timeout tests (pT 20 → 10/10; clamped 900 → 450/450 vs 950 ms hook; clamped
  600 → 300/300 vs 700 ms hook; pT 200 → work 100 vs 30 ms hook; pT 0 → default 12 000 →
  work 10 000) and all still assert what they asserted before. Not obviously wrong, but it is
  a behavior change for anyone configuring a sub-4 s budget: their work budget is now half of
  what they asked for rather than all of it. Worth a second opinion on whether the clamp
  should instead be a floor on `workMs`.
- **The residual unclosable window is a tripwire, not a ticket** — see findings below.
- **`yarn lint`** reports 0 errors and 6 pre-existing warnings ("Unused eslint-disable
  directive") in `packages/integration-tests/src/scenarios/zz-scratch-delete-alone.integration.ts`,
  a file this diff does not touch. Not investigated here.

## Review findings

- **Tripwire (parked, not filed):** one window stays open — a work budget that expires
  *after* the `FormationUsage` insert was issued AND a commit that outlasts the grace. The
  joiner is told 'timed out' while its one-time invite is in fact spent, and no recovery path
  can match a retry because `StrandSolicitationService.formStrand` mints a fresh Ed25519
  keypair per attempt. Nothing can un-spend an append-only row. Parked as a `NOTE:` in
  `settleWithinGrace`'s docblock (`strand-formation-protocol.ts`), where the late-settle
  logging that observes it also lives; widen the grace only if it shows up in the wild.
- The stale `NOTE:` in the old `provision()` catch ("provisionStrand is not cancelled on
  timeout…") is deleted — it described exactly the behavior this ticket removed.
- Recoverable-spend alternative was investigated and **rejected** across prior runs (fresh
  keypair per retry defeats `(Token, PeerId)` matching; a recovery path would hand the strand
  id + closed-strand `MemberPrivateKey` to anyone re-presenting a spent token under a
  writer-asserted peer id). Do not relitigate.
