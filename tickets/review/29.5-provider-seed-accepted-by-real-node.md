# Review: provider-started node accepts the provider's seed (real `cadre-cli`)

## What this proves, and why it did not exist before

Every other provider seed test stops at the provider's own boundary —
`container-seed-endpoint.test.ts` stubs `fetch`, so it asserts what the provider
*sends*, never what a node *does* with it. A drift in the provider→node
environment contract would pass all of them while every customer's first seed
was silently refused.

This scenario closes that gap. It starts real `@serfab/cadre-cli` child
processes from the provider's own `buildNodeEnv()` output (via
`ProviderProcessOrchestrator`) and drives them through the real
`ContainerService`. No stubs anywhere. It exercises the two independent gates
that decide a delivered seed's fate:

- **delivery gate** — the per-container `CADRE_SEED_TOKEN` bearer the provider
  mints and presents on `POST /seed`; a wrong bearer gets a 401.
- **trust gate** — the node's own seed-trust policy against the
  `CADRE_OWNER_KEYS` pin it was started with; an untrusted signer gets a 400.

Five ordered steps: owner authority node up → provider provisions node A pinned
to the owner → **A accepts the owner-signed seed** (the assertion the suite
exists for) → node B pinned to a stranger refuses it, and a wrong bearer on B
gets 401 instead → A restarted with **no** pin still accepts a second seed,
proving the first accepted seed anchored the owner key durably.

## What this run changed

**Step 3 now retries the mint as well as the delivery.** Previously only
`applySeed` was polled; `addDrone` was a bare call, so a transient owner-side
error failed step 3 outright. That was also the real cause of the mystery
recorded in the incoming ticket — step 4 refusing with `seed is required`
instead of the trust policy's reason. It was never a delivery bug: when step 3
fails, `encodedSeed` is `undefined`, `JSON.stringify({ seed: undefined })`
serializes to `{}`, and the node correctly answers "you posted no seed body".
A pure cascade. **The suggested polling workaround for step 4 was therefore not
applied and should not be** — polling would have retried a malformed POST
forever.

**Step 4 now guards the cross-test dependency explicitly**
(`expect(encodedSeed, 'step 3 must have minted a seed …')`), so that cascade can
never again present as a step-4 defect. It fired exactly as designed on the red
runs.

**Mint + deliver are one helper now** (`deliverSeed`), shared by steps 3 and 5,
replacing two near-identical inline polls. On timeout it attaches the last mint
error, the last delivery result, and the child's `node.log` — `waitUntil`
swallows a throwing condition by design, so before this a stuck poll reported a
bare `Timeout waiting for …` with the cause lost. That is what turned three
opaque red runs into a named fingerprint in one run.

## The blocker (already tracked — do not re-file)

Steps 3 and 5 both fail on the owner's `addDrone` insert:

```
insert failed: collection default/CadrePeer/index/_uniq_5 holds committed revision 2,
but its header block read as absent — storage reported that nothing was ever committed under this id
```

This is `fix/0-bug-control-collection-header-absent-at-committed-revision`,
which already names this scenario in its failing set, and
`tickets/.pre-existing-known.md` already carries an entry for it. Both were
**updated** with the sharper 2026-08-03 fingerprint rather than re-filed. The
fingerprint changed materially and is worth reading before reviewing:

- it is on a **unique-index sub-collection** (`…/index/_uniq_5`), not a
  top-level collection — first observation one level down;
- it is on the **writer at insert time**, not a reader querying someone else's
  write — every earlier fingerprint in that class was a read;
- the chain/startup half of this scenario's old failure is **gone**: the
  `29.4-verify-ddl-retry-engages` schema-init retry landed and all three nodes
  now start cleanly every run.

That third point is the prereq discharging exactly as intended.

- step 3 red with `last mint error: none` and a non-null `last delivery result`

## Known gaps — flagged, not papered over

- **Two consecutive green runs were not achieved.** The bar in the incoming
  ticket is unmet, and it is unmeetable until the header-absent defect lands.
  1-of-4 is the honest number.
- **`entrypoint.sh` is still untested.** `ProviderProcessOrchestrator`
  reproduces the image env and the entrypoint's derivations in-process; the real
  Docker image and its shell script are out of scope. A drift in the script
  itself still passes everything here.
- **The no-pin variant was deliberately dropped.** Step 4's stranger-pin already
  proves the trust gate discriminates; a third child process for a
  no-pin-refuses case was not judged worth the wall-clock. Reviewer may disagree
  — it is a cheap addition if so.
- **Three small helpers are duplicated from the donation scenario**:
  `writeIdentity`, `withPeerId`, `readNodeLocalStore`. They were left in place
  rather than lifted into `src/harness/` to keep this ticket's diff scoped.
  Genuine DRY cleanup, worth a call.
- **Step 5 patches the store record by hand** (fresh endpoints/token, status
  forced to `running`) because `ContainerService.createContainer` can only mint
  fresh `ctr_` ids, so a same-volume restart has to go through the orchestrator
  directly. It mirrors what a real provider restart would re-record, but it is
  test-side surgery on a production record shape and will rot if that shape
  changes.
- **Ports 20200–20339** are this suite's band by convention only (19600–20199
  belong to the cadre-host suites). Nothing enforces the split.

## Tripwire parked this run

`ContainerService.waitForEnrollment`'s 60 s budget: on timeout it logs and
returns, leaving the record on `enrolling` forever — never promoted to
`running`, never failed to `error`, and nothing re-enters the loop. Harmless
today because `applySeed` accepts `enrolling`, so a merely-slow node still
works. Recorded as a `NOTE:` at the site
(`packages/cadre-provider/src/service/container-service.ts`, end of
`waitForEnrollment`) with the condition that would make it real: anything that
treats `enrolling` as not-failed — an SLA sweep, a UI waiting on the record
instead of polling `/status`, an operator dashboard.
