# Implemented: every strand machine binds itself to its party's membership

Third ticket of the party-identity chain (`strand-party-member-key` → `strand-formation-membership-invite` → this → `strand-party-removal-via-formation-e2e`). Strand bring-up now finishes the join on every machine: a background **membership reconciler** redeems a pending formation invitation (seating the party's `Strand.Member` row under its own key) and writes the durable machine→party binding (`Strand.MemberPeer`) that revocation enforcement keys on. `unpublishStrand` clears the machine's own binding on the way out.

## What landed

**New module `strand-membership-reconciler.ts`** — `StrandMembershipReconciler`, one per closed-strand instance launched with a party key. Per pass: (1) stop if the revocation enforcer flags this party as revoked; (2) ensure membership — member row visible → done (and a still-staged invitation is *burned*: the `ConsumedInvite` row alone, naming the existing member, so the bearer credential dies); absent + staged invitation → `consumeInvite`, retried across passes until the `Invite` row replicates here; absent + no invitation → idle (one `console.warn` after `IDLE_PASSES_BEFORE_ESCALATION` = 10 passes, then quiet); (3) ensure the binding — `registerMemberPeer` (insert-if-absent) with the node's own strand transport peer id, then done → the loop stops. Terminal states: sealed strand (`NotSealed` rejection), self-revoked, undecodable party key. A dead invitation (expired / cancelled / consumed elsewhere — classified by the engine's constraint-failure message) is dropped with a log while the loop keeps waiting. Every pass is fully contained (never rejects, never blocks bring-up); passes are serialized on a promise tail; the scheduler seam is the enforcer's (`RevocationRefreshScheduler`), default cadence mirrors the enforcer's configured `pollIntervalMs` (30 s default).

**Writer additions** (`strand-membership-writer.ts`): exported `burnInvite` (the standalone `ConsumedInvite` insert — all its constraints are satisfiable without a `Member` insert) and `isStrandMember` (scan-idiom membership probe); `consumeInvite`'s `ConsumedInvite` insert refactored into the shared private `insertConsumedInviteRow` (no behavior change; `canonicalDatetime` is a pure scalar eval, safe mid-transaction).

**Instance manager** (`strand-instance-manager.ts`): the reconciler is armed in `buildStrandRuntime` immediately after `strandDb.initialize()` — the one seam where the transport peer id and a live `Database` both exist for launch AND hibernation resume — for `Type === 'c'` strands with a `partyMemberPrivateKey`, unless `membershipReconciliation: { enabled: false }`. Deps are lazy per-pass reads (`instance.database`, `instance.libp2pNode`, the enforcer's `isRevoked` over the node's own peer id). Stopped and dropped in `releaseRuntime`, so quiesce → resume rebuilds it and re-runs the idempotent ladder. New `clearOwnMemberPeerBinding(strandId)`: best-effort self-arm `removeMemberPeer` signed with the retained launch config's party key, reconciler stopped first, never throws; a quiesced or unreachable strand keeps the stale binding with a log. `StartStrandConfig` gained `pendingMembershipInvite` (a `{get, clear}` view of the staged invitation) and `membershipReconciliation`.

**CadreNode**: `launchStrand` wires `pendingMembershipInvite` as a LIVE view over the in-memory `pendingMembershipInvites` map (the reconciler owns invalidation, closing ticket 2's "no consume/clear API" gap) and threads the new `CadreNodeConfig.strandMembershipReconciliation` knob. `unpublishStrand` calls `clearOwnMemberPeerBinding` after the control delete (a rejected unpublish never strips a binding) and before the local stop (the same act destroys the party key's durable copy, so this is the last moment anything can sign the removal).

**Harness/scenarios**: `controlNodeConfig` gained `membershipReconciliation: false` (the reconciler cadence otherwise mirrors `revocationPollMs`). `strand-formation-cross-party-seed`'s closed-strand test now asserts the AUTOMATIC path over a real two-party network — no `consumeInvite`/`registerMemberPeer` call anywhere in it: bring-up redeems, both machines' bindings land and replicate to the host. `strand-membership-closed-strand-e2e` disarms the reconciler (it hand-drives the writers and asserts exact row sets). `strand-removal-cuts-network`'s "FIXTURE HONESTY" comments were rewritten — they claimed production writes no device records, which is no longer true.

**Docs**: `docs/strands.md` (the "Half landed" attestation bullet → written automatically, admission half still `feat-strand-member-allowlist-admission`; the Closed-Strand Member Key Handling redemption paragraph; the Removing-Members housekeeping bullet — device records now automatic, the unpublishing machine self-cleans, siblings cannot; "What removal still does not do" first bullet rewritten around the e2e that remains); `docs/architecture.md` (Strand Membership Bootstrap: the reconciler paragraph); `docs/testing.md` (blind-relay hand-registration note); `docs/strand-contracts.md` + `docs/strand-contracts-review.md` (prerequisite advanced: distinct `Member` rows per party now land automatically).

## Use cases to validate against

- **Joiner ladder**: form a closed strand (`formStrand` → invitation staged) → `addStrand` → within one reconciler pass after the host's `Strand.Invite` row replicates, the joiner's own `Member` row + `MemberPeer` binding exist and `getPendingMembershipInvite` returns undefined. Proven over a real network by `strand-formation-cross-party-seed` ("redeems the carried membership invitation automatically at strand bring-up").
- **Founder / sibling machines**: member row already seated → straight to the binding; a sibling of a joiner party (party key replicated, no staged invitation) idles until the member row replicates, then binds itself.
- **Already-member with unspent invitation** (sibling redeemed first, or manager-admitted): the invitation is burned — `ConsumedInvite` names the existing member; nobody else can spend it.
- **Terminal/degraded**: sealed strand stops the loop; expired/cancelled invitation is dropped and the loop idles; a self-revocation stops the loop; bring-up NEVER waits on any of this (pinned by the joiner-idles test in `strand-founder-bootstrap.spec.ts`).
- **Unpublish**: `unpublishStrand` of a closed strand clears the machine's own binding while it can still sign (spy-pinned in `strand-unpublish.spec.ts`; mechanics in `strand-instance-manager-membership.spec.ts`).
- **Enforcer interplay** (pre-existing coverage, re-verified green): live-membered binding never denied; revoke → denied; re-admit under the same party key → un-denied; the bindings-before-members scan order keeps a mid-join machine out of the deny set (`strand-revocation-enforcer.spec.ts`, including the real-DB and join-between-scans sections).

## Known gaps and judgment calls (for the reviewer)

- **Failure classification is message-text matching.** Sealed/dead-invitation routing tests the engine's constraint-failure text (`/NotSealed/`, `/NotExpired|NotCancelled|ConsumedInvite/i`). Each classified path is pinned against the real engine in the reconciler spec, so a message change breaks a test — and a MISSED match degrades to retry-next-tick (the safe direction) — but there is no error-code contract.
- **A transiently-failed burn is dropped, not retried.** Per the ticket ("ignore burn failures beyond a log") the staged invitation is cleared even when the burn write failed for a transient reason, so that machine never retries the burn and the bearer credential stays spendable until it expires. Logged at the site.
- **Unpublish of a hibernating strand leaves the stale binding** (best-effort by design, logged), and sibling machines observing a party-wide unpublish cannot clear theirs at all — the same act destroys the signing key. Recorded as the accepted shape in `docs/strands.md` and the `NOTE:` tripwire below.
- **Shared-Database contention**: the reconciler's `consumeInvite` opens an explicit transaction on the strand's one `Database` handle; a concurrent app transaction makes one side fail ("Transaction already active") and the reconciler retries next tick. Contained by design; not separately tested.
- **Hibernation resume re-running the ladder** is unit-covered (manager rebuild test + rebuilt-reconciler test) but has no real-network integration run.
- **The full form → remove → cut journey on production-written rows** is deliberately the next ticket, `strand-party-removal-via-formation-e2e` (already in `implement/`).
