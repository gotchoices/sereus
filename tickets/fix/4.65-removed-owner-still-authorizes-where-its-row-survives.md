# A retired `OwnerKey` row still authorizes owner-signed writes

## What is wrong

Every owner-gated check in `schemas/control.qsql` decides "is the signer an owner?" by reading the raw `OwnerKey` table: `exists (select 1 from OwnerKey A where A.Key = context.OwnerKey and verify(...))` on `ValidationKey`, `Strand`, `StrandPartyKey`, `JoinedStrand`, `JoinRequest`, `JoinSuccess`/`JoinFailure`, `CadrePeer`, `DeviceToken`, `CadreInvite` and `Revocation`, and `committed.OwnerKey` in `OwnerKey.Authorized` itself. None of them excludes a row whose `StampId` is retired in `Revocation`.

`OwnerKey` has no reap branch (by design, see the `getOwnerKeys` JSDoc in `control-database.ts`). So a machine that receives an owner's removal tombstone without the delete keeps the removed owner's row beside its tombstone forever. That happens on the ordinary path for removing a lost device: `CadreNode.removeOwner` (landed by `owner-anchor-revocation-signer-and-owner-writers`) run on an owner machine that is alone commits the delete locally only, and only the tombstone is re-issued to the other machines on the next cohort growth ("Deletes made while alone" in `docs/architecture.md`). Every machine except the remover then holds the removed owner's row, including the removed machine itself.

On those machines the removed key passes every owner check above. A holder of that key can still, there: remove another owner (including the one who removed it), delete a `Strand` row and its `StrandPartyKey` (no reap, the party's only copy of that identity), add a `ValidationKey`, file `Revocation` tombstones that evict devices, and vouch `CadrePeer` rows.

`ControlDatabase.getOwnerKeys` already drops retired stamps, and `owner-anchor-derivation` makes the reader-side trusted-owner anchor drop the removed key, so membership snapshots and seed trust stop honouring it. Physical row writes (deletes of strands, owner rows, tombstones) are decided by the schema alone, so the reader side does not cover them.

## Expected behaviour

An `OwnerKey` row whose stamp is retired in `Revocation` authorizes nothing, on every machine that holds the tombstone, whether or not it also holds the row. A removal is effective at the write checks as soon as the tombstone arrives.

## Repro (static)

Read from the schema and the alone-delete path; not run. What would confirm it: an integration scenario with owners A and B and a member M: A goes alone, `A.removeOwner(bKey)`, A reconnects and re-issues the tombstone; once M holds the tombstone (and still holds B's row), a write signed by B (for example a `ValidationKey` add, or a `CadrePeer` removal) is accepted on M. A schema-level unit repro on one database is not possible: `Revocation.RowIsGone` refuses an `OwnerKey` tombstone while the row is present, so the row-plus-tombstone state only arises through replication.

## Options seen while reviewing (for the fix stage to weigh)

- **The invariant in the checks (preferred).** Every owner lookup also requires `not exists (select 1 from Revocation R where R.TableName = 'OwnerKey' and R.StampId = A.StampId)`. This also covers the resurrected-row case the schema header describes (a replayed add on a node that has not converged). Cost: one more correlated read per owner check, and editing the constraint text of almost every table, which forces recreating existing control stores (allowed under the no-backwards-compatibility policy; the docs note under the table list says so). Check whether Quereus/optimystic accept a schema-level view or shared expression so the clause is written once rather than about twenty times.
- **An `OwnerKey` reap branch.** Fixes only machines that run the reap sweep while connected, leaves the window until then, and has to be gated so a reap can never take the table below `MinOneOwner` (the reason it was left out). Weaker; listed so the choice is explicit.
