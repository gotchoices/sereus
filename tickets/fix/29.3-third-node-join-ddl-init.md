# Node joining a live multi-peer cadre crashes on startup schema init

## What was observed (2 out of 2 runs)

The new integration scenario
`packages/integration-tests/src/scenarios/provider-seed-accepted.integration.ts`
starts three real `@serfab/cadre-cli` children in one party: an owner
authority node, provider-hosted node A, then provider-hosted node B. Node B —
the third process to join the party — **crashed on startup in both runs**,
each time inside the `create table CadreControl.*` DDL sequence that
`cadre-cli start` executes, but at a different table with a different error:

- Run 1, table `FormationUsage`:
  `Module 'optimystic' create failed ... Some peers did not complete:
  <B itself>(in-flight) cause=Failed to get super-majority: 1/2 approvals
  (needed 2, 0 rejections), <other peer>(in-flight) cause=The stream has been
  reset; root: Failed to get super-majority: 1/2 approvals`
- Run 2, table `Revocation`:
  `Module 'optimystic' create failed for table 'Revocation': Failed to
  initialize Optimystic table: Missing block (jQlkVafUFlI6FzOGGAlViyK5GrgcSm_4SL7HfPKwhis)`

In both cases earlier tables in the same DDL sequence had already succeeded —
so the cluster was reachable and working moments before. One transient
distributed hiccup (a reset libp2p stream, one missing block replica) makes
`cadre-cli start` print `Failed to start cadre node: Failed to execute DDL:
...` and exit. There is no retry at any level.

Likely related, same runs: the owner node's `addDrone` admin call twice failed
transiently with internal errors while other nodes were joining/stopping —
run 2 immediately (`nodeCode: 'internal'`), and after node A was restarted:
`Query failed: collection default/CadrePeer holds committed revision 2, but
its header block read as absent — storage reported that nothing was ever
committed under this id`. These may be the same underlying fragility
(distributed reads/writes with no retry while cluster membership is in flux)
seen from the owner's side.

## Why no existing test caught it

Every existing multi-node test tops out at **two** real nodes in a party (the
cadre-host donation scenario: requester authority + one donated node). Three
live peers means schema-init transactions need a super-majority of 2 approvals,
so one flaky peer response becomes fatal for the joining node. The new
provider scenario is the first coverage of a third node joining.

## How to reproduce

```
yarn workspace @serfab/cadre-core build && yarn workspace @serfab/cadre-cli build \
	&& yarn workspace @serfab/cadre-host build && yarn workspace @serfab/cadre-provider build
yarn workspace @serfab/integration-tests test src/scenarios/provider-seed-accepted.integration.ts
```

Step 4 ("node B pinned to a stranger refuses the same seed") fails with node
B's `node.log` dumped in the failure message showing the DDL crash. Note the
scenario itself is still being stabilized (see the implement ticket that
depends on this one) — steps 1–2 pass reliably; step 3 passed run 1, proving
the seed-acceptance path itself works.

## Aggravating factor on the provider side

When the node dies mid-start, the provider's
`ContainerService.waitForEnrollment` (hard-coded 60s,
`packages/cadre-provider/src/service/container-service.ts`) gives up silently
and the container record stays `enrolling` forever — nothing re-polls, nothing
surfaces the child's death. Worth addressing (or ticketing separately) while
in there: the orchestrator knows the process exited (`isRunning`), but the
service never asks it.

## What a fix probably looks like (research, then decide)

- Retry the per-table optimystic init (or the whole DDL statement) on
  transient transport errors — bounded retries with backoff — rather than
  treating the first failure as fatal.
- Or make schema init on a **joining** node tolerant: if the table already
  exists in the party, attach instead of create-with-cluster-consensus.
- Investigate why an established peer resets streams / reports a missing
  block during a third peer's join — the retry may be papering over a
  cluster-side bug in (or under) the optimystic layer; `../optimystic` is
  linked into this workspace for debugging.
