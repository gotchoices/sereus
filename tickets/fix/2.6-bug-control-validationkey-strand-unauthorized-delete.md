# `ValidationKey` and `Strand` deletes are not authorized at all

## What is wrong

Every `CadreControl` table gates who may change it with a `constraint ... check` carrying an owner
signature. A bare `check (...)` in Quereus covers **insert and update only** — a table that wants
its deletes covered must say `check on delete` explicitly (as `OwnerKey`, `CadrePeer`,
`DeviceToken` and `FormationInvite` all do, and as `FormationUsage` does via
`constraint InsertOnly check on update, delete (false)`).

`ValidationKey.Authorized` and `Strand.Authorized` are both bare checks. Their deletes are
therefore completely ungated.

Reproduced against a real control database while working
`bug-control-remove-then-replay-resurrection`: after an owner-signed insert of one
`ValidationKey` row and one `Strand` row, this removed both, and was accepted —

```sql
delete from CadreControl.ValidationKey with context OwnerKey = null, Signature = null where Key = 'VK1';
delete from CadreControl.Strand        with context OwnerKey = null, Signature = null where Id  = 'S1';
```

## Why it matters

- `ValidationKey` holds the keys that validate a strand-formation disclosure. Dropping them
  disables that check for the party.
- `Strand` is the party's record of the networks it participates in, and for a closed strand the
  row also carries `MemberPrivateKey` — the party's own membership key for that network. Deleting
  the row destroys it.

The attacker position is the same one the rest of the control-plane authorization work assumes:
an already-admitted cadre peer that can write to the party's control collection. No owner key,
no captured signature, and no network position is required.

## What "fixed" should mean

Both tables get an explicit, `'remove'`-tagged delete rule requiring an owner signature over the
stored row, matching the shape `OwnerKey` / `CadrePeer` / `FormationInvite` already use — a
digest whose action tag is distinct from the insert digest, so an add approval can never be
replayed as a removal.

Once deletes are authorized, these tables inherit the same resurrection hole that
`control-remove-then-replay-revocation` fixes for `OwnerKey` / `CadrePeer`: both carry a
`StampId` whose `unique` constraint only holds over live rows, so the original add approval would
verify again after a delete. That ticket introduces an append-only `CadreControl.Revocation`
table with a `TableName` discriminator specifically so more tables can be added to it — extend it
to `ValidationKey` and `Strand` here rather than inventing a second mechanism. That is why it is
named as a prerequisite.

Whatever is chosen must keep `schemas/control.qsql` and
`packages/cadre-core/src/control-schema.ts` byte-identical (a drift test enforces this), and come
with tests that assert an unsigned delete of each table is refused **by constraint name**.

## Also worth checking while here

There is no production writer that deletes a `ValidationKey` or a `Strand` row today, so adding
the rule may need a signed deleter to exist at all before it can be exercised end to end. Decide
whether to add one (mirroring `SeedBootstrapService.removePeer`) or to cover the rule with raw-SQL
tests only, and say which in the implement ticket.

Sweep the remaining tables for the same bare-`check` pattern rather than assuming these two are
the only ones.
