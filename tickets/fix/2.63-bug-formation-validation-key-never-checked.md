# The formation validation gate accepts any key

## Background

A `CadreControl.FormationInvite` row may carry a `ValidationUrl`. The intent: before someone
redeems this invitation, their disclosure goes to that web hook, and the hook's operator signs
off on it. The party keeps a list of keys allowed to give that sign-off — the
`CadreControl.ValidationKey` table ("keys that can validate a strand formation disclosure").

Redemption inserts a `CadreControl.FormationUsage` row, gated by `constraint Authorized`.

## The defect

That constraint verifies the approval signature against a key the **redeemer supplies**, and
never checks that key against the `ValidationKey` table:

```sql
and (FI.ValidationUrl is null or verify(
        digest('CadreControl.FormationUsage', 'vouch', new.Token, new.Disclosure),
        context.ValidationSignature, context.ValidationKey, 'ed25519'))
```

`context.ValidationKey` is just a parameter on the insert (`with context ... ValidationKey =
?`), plumbed through from whatever the responder got back from the web hook
(`strand-solicitation.ts` → `formationSigner.signFormation`). Nothing joins it to
`CadreControl.ValidationKey`. So a redeemer generates a throwaway keypair, signs its own
disclosure with it, passes both in, and the gate is satisfied.

Net effect: `ValidationUrl` provides no security at all. It only stops a redeemer who forgets
to supply *some* signature.

Related consequence worth stating: `CadreControl.ValidationKey` is currently read by nothing
in the schema and by nothing in `packages/*/src` except a row-count on the reference web app's
diagnostics screen. The table has enrollment rules, removal rules and anti-replay tombstones —
and no consumer. This ticket is what would give it one.

## Reproduction (confirmed)

Confirmed empirically against the current schema, in a scratch test inside
`packages/cadre-core/test/control-revocation-replay.spec.ts` (real `CadreNode`, empty
bootstrap, transaction profile):

1. `db.insertFormationInvite(token, sAppId, ownerKey, sign, { totalUses: 1, validationUrl:
   'https://example.invalid/validate' })`.
2. Generate a fresh ed25519 keypair that is **not** enrolled in `CadreControl.ValidationKey`.
3. `db.redeemInvitation({ ..., disclosure, validationKey: <rogue public key>,
   validationSignature: <rogue signature over the 'vouch' digest> })`.

Step 3 was **accepted** and the strand was formed.

The scratch test was deliberately not left in the suite — asserting today's behavior would
mean asserting the hole. Land the fix and its regression test together.

## Expected behavior

When an invitation names a `ValidationUrl`, redemption should be accepted only if the
approving key is one the party enrolled — i.e. the constraint should require a matching
`CadreControl.ValidationKey` row for `context.ValidationKey`, in addition to verifying the
signature.

Points for the fix owner to settle:

- **Removal semantics.** If a validation key is later removed, previously recorded
  `FormationUsage` rows are not re-checked (CHECKs run on write only). That is probably fine —
  the approval was valid when given — but say so in the constraint comment either way.
- **Bootstrap.** Confirm no existing flow relies on redeeming a `ValidationUrl` invite before
  any validation key is enrolled; if one does, that flow needs the enrollment step added
  rather than the check weakened.
- **Reference/integration flows.** `strand-solicitation.ts` and the reference apps produce the
  `(validationKey, validationSignature)` pair today from an arbitrary signer callback; they
  will need to use an enrolled key.

## Not in scope

The peer identity fields on the same insert (`context.PeerId` / `context.PeerSignature`) are
also declared and never verified — an invitation token is a bearer credential today. That is a
separate question about invitation design; do not fold it in here.
