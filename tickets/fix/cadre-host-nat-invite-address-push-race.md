----
description: Initial NAT invite-address push races authority-node readiness with no retry, so early invites embed raw libp2p addrs
files: packages/cadre-host/src/bin/host.ts, packages/cadre-host/src/nat/nat-service.ts
----
The first NAT invite-address push fires before the authority node's loopback admin channel is ready, so it is silently dropped. As a result, invites minted in the window right after a host starts embed raw libp2p multiaddrs instead of the NAT-resolved DDNS/external-IP addresses the host has already computed, yielding undialable invites despite a working DDNS/port-map setup.

In `bin/host.ts` `start()`, `orchestrator.ensureAuthorityNode()` returns as soon as the detached child is spawned; it does not wait for the node's loopback admin channel to bind (packages/cadre-host/src/bin/host.ts:282-292). `NatService.start()` is then invoked (packages/cadre-host/src/bin/host.ts:321-326) and immediately calls `fireAddressesChanged()` (packages/cadre-host/src/nat/nat-service.ts:149-151), which round-trips to the not-yet-ready node via `getInviteAddresses()`. The round-trip throws `AuthorityNodeUnavailableError`, `fireAddressesChanged()` swallows it as a best-effort skip (packages/cadre-host/src/nat/nat-service.ts:270-286), and the push never happens. There is no readiness poll or retry on this initial path; the registered listener in host.ts (packages/cadre-host/src/bin/host.ts:307-317) is simply never called.

Consequence: until a later NAT change event (for example a `putSettings` or `testReachability` that re-fires `fireAddressesChanged()`) occurs, the authority node has no host-pushed invite addresses and falls back to its own libp2p `getMultiaddrs()` when constructing invites. A freshly-started host that mints an enrollment invite right away therefore hands remote phones raw libp2p addresses rather than the NAT-resolved DDNS / external-IP addresses it already computed, producing invites that cannot be dialed from off-LAN even though DDNS and port mapping are configured correctly.

Expected behavior: the initial invite-address push must not race authority-node readiness. The first computed NAT-resolved addresses should be guaranteed to reach the node before any early invite can be minted — either by waiting for the authority node's admin channel to be ready (a readiness signal/poll surfaced from the orchestrator's `ensureAuthorityNode`/admin-endpoint path) before performing the initial push, or by retrying the initial push until the node accepts it. The fix should preserve the existing best-effort semantics for genuine, sustained node-unavailability (the process must still come up with the local UI serving) while ensuring transient not-yet-ready states do not permanently drop the first NAT-resolved address set.

Use case: a self-hosted host operator completes DDNS/port-map setup, starts the host, and immediately generates an enrollment invite for a remote phone. That invite must carry the NAT-resolved external addresses, not the host's raw internal libp2p multiaddrs.

Key files: `packages/cadre-host/src/bin/host.ts` (start/ensureAuthorityNode sequencing and the invite-address-push listener), `packages/cadre-host/src/nat/nat-service.ts` (`start()` initial `fireAddressesChanged()`, `getInviteAddresses()`, and the silent skip in `fireAddressesChanged()`). Related background: the authority-node delegation and admin-channel work in `tickets/complete/6.7-cadre-host-authority-node-delegation.md`, `tickets/complete/6.6-cadre-node-admin-channel.md`, and the NAT subsystem in `tickets/complete/6.3-cadre-host-nat.md`.
