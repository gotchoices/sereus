# `Strand` rows formed by invitation can be re-created after an authorized removal

## Background

`CadreControl.Strand` lists the networks ("strands") this party participates in. A closed
strand's row also carries `MemberPrivateKey` — the party's own private key for that network.

A row can be seated two ways:

- **owner-signed** — an owner signs a digest over the whole new row; or
- **by consent** — no signature at all. The row is authorized purely by the existence of a
  `CadreControl.FormationUsage` row naming the same strand id. That row is the audit record
  of a formation invitation being redeemed.

Removal (added by `control-validationkey-strand-delete-authorization`) requires an owner
signature over a distinct `'remove'` digest **and** a `CadreControl.Revocation` tombstone
retiring the row's one-off nonce (`StampId`) in the same transaction. The tombstone is what
makes removal permanent: the never-expiring add signature names the retired nonce, so it can
never re-seat the row.

## The defect

The consent branch does not name a nonce. It only asks "does a `FormationUsage` row exist for
this strand id?" — and `FormationUsage` is append-only (`constraint InsertOnly check on
update, delete (false)`), so that row survives the strand's removal forever.

So after a fully legitimate, owner-signed, tombstoned removal, **any** writer can insert a new
`Strand` row for the same id, with **no owner key and no signature**, choosing its own `Type`
and `MemberPrivateKey`. A fresh `StampId` sidesteps `NotRevoked` (which only retires the one
nonce the removed row carried).

The control database is replicated across the party's cadre and any peer writes SQL to it
directly — the CHECK constraints *are* the authorization boundary — so "a writer" here means
any node that can reach the control network, not only the party's own code.

Consequences:

- A removal of a consent-formed strand is not durable; it can be undone by anyone watching.
- The resurrected row's `MemberPrivateKey` is attacker-chosen, so the party can be steered
  onto a membership key it does not control for that network.

## Reproduction (confirmed)

Confirmed empirically against the current schema, in a scratch test inside
`packages/cadre-core/test/control-revocation-replay.spec.ts` (harness: real `CadreNode`,
empty bootstrap, transaction profile — the same one that file's other tests use):

1. Insert a `FormationInvite`, then `db.redeemInvitation({...})` to seat a consent-formed
   closed strand.
2. Remove it the legitimate way: owner-signed `'remove'` digest + matching `Revocation` row in
   one transaction. The row is gone.
3. `insert into CadreControl.Strand ... with context OwnerKey = null, Signature = null` for the
   same `Id`, a fresh `StampId`, and an attacker-chosen `MemberPrivateKey`.

Step 3 was **accepted**. The strand row is back.

The scratch test was deliberately not left in the suite — a test asserting the hole would
pass today and fail once fixed. Land the fix and the regression test together.

## Expected behavior

An authorized, tombstoned removal of a strand should be permanent regardless of how the row
was originally seated. Some ways this could be reached (the fix ticket owner should pick;
each has consequences worth weighing):

- Bind the consent branch to the redemption that authorized it — e.g. carry the `StampId`
  onto the `FormationUsage` row at redemption time and have the consent branch require the
  inserted `Strand.StampId` to equal it. Then a removal that retires that nonce closes the
  branch permanently. Note this changes the `FormationUsage` shape and the redemption writer.
- Or require, on the consent branch, that no `Revocation` row exists for **any** strand nonce
  tied to this strand id — which needs the strand id to be recoverable from the tombstone
  (today `Revocation` stores only `(TableName, StampId)`).
- Or forbid re-inserting a strand id that already has a `FormationUsage` row **and** a
  tombstoned predecessor, requiring an owner signature for the re-add.

Whatever shape is chosen, keep the existing property that a legitimate re-join is still
possible — removal should retire the specific authorization, not blacklist the strand id
forever — and say plainly in the constraint comment which of the two it now does.

## Related, and how this differs

- `bug-control-revocation-unauthenticated-writes` — anyone can *file* a tombstone. Different
  hole, same table; that one is about writing `Revocation`, this one is about the guarded
  table's re-insert path ignoring it.
- `control-signed-strand-validationkey-deleters` (in `implement/`) builds the production
  writer that signs `'remove'` and files the tombstone. That writer is the thing this defect
  makes ineffective for consent-formed strands, so the two are worth reading together — but
  this defect is in the schema, not in that writer, and does not depend on it landing.
