# `clusterSize: 3` is hardcoded while real cadres run 1–2 nodes, and Optimystic now enforces it

## What is wrong

Three places hardcode a replication cluster size of 3:

- [`packages/cadre-core/src/cadre-node.ts:739`](packages/cadre-core/src/cadre-node.ts#L739) — control network
- [`packages/cadre-core/src/strand-instance-manager.ts:260`](packages/cadre-core/src/strand-instance-manager.ts#L260) — per-strand networks
- [`packages/integration-tests/src/harness/test-party.ts:48`](packages/integration-tests/src/harness/test-party.ts#L48) — test harness

`clusterSize` is the number of nodes Optimystic is told the replication cluster should
have. Nothing derives it from how many nodes the party actually runs. A brand-new party
has one node; the two-node integration scenarios have two. In every one of those cases the
declared size (3) exceeds reality.

Until recently that mismatch was harmless — `clusterSize` only influenced the coordinator
(the node driving a write). As of the Optimystic `cluster-membership-admission-gate` work
(in `../optimystic`, commits `e285cdb` / `f568454`, shipped in the 0.16.x line we now
depend on) it is also fed to the **member** side and used as a gate:
`libp2p-node-base.ts:649` passes it into `ClusterMember`, and `cluster-repo.ts` then
refuses to vote on a write when the set of declared peers is smaller than the configured
cluster size and FRET confidence is low. The rejection surfaces as
`membership-not-admitted`.

Because the write path requires a super-majority of *actual* peers
(`ceil(2 × 0.75) = 2`, i.e. unanimity at two nodes), a single member refusing is fatal:
the commit fails.

## Evidence

Verified by direct experiment against `control-db-two-node-convergence.integration.ts`:
changing [`cadre-node.ts:739`](packages/cadre-core/src/cadre-node.ts#L739) from
`clusterSize: 3` to `clusterSize: 2` eliminates the `membership-not-admitted` errors
completely and deterministically, across three consecutive runs. The scenario's writes
then commit.

**Methodology warning for whoever picks this up** — `packages/integration-tests` imports
`@serfab/cadre-core` from its **`dist/`**, not `src/`. Editing `src/` alone changes
nothing and the scenario will appear to disprove your hypothesis. Run `yarn build` in
`packages/cadre-core` and confirm the built output actually contains your change before
believing any result. This cost two wasted runs and a nearly-reported false negative.
(This is exactly the hazard `debt-integration-tests-detect-stale-build` exists to close.)

## What "fixed" should mean

Pick a defensible rule for the declared cluster size and apply it at all three sites. The
obvious shape, for whoever picks this up to weigh:

- Derive it from the party's actual cadre membership — the number of `CadrePeer` rows —
  clamped to a floor of 2 and a ceiling of the desired replication factor (3). A one-node
  party declares the floor; a two-node party declares 2; a party at three or more declares 3.
- The value must be able to change as the cadre grows or shrinks. Establish whether
  Optimystic reads `clusterSize` once at node construction or on each operation; if it is
  construction-time only, say so in the handoff and note what a membership change requires
  (restart? re-create the node?) rather than silently shipping a value that goes stale.
- The two call sites in `cadre-core` have different membership sources — the control
  network's members are the party's cadre peers; a strand network's members are the
  strand's participants. Do not assume one number serves both.
- The test harness site should follow whatever production does, not hardcode its own.

## Deliberately out of scope

**This ticket does not make the convergence scenarios pass.** There is a second, entirely
independent defect on the *read* side, upstream in `../optimystic`, tracked by
`control-db-convergence-optimystic-p2p` in `tickets/blocked/`. With the write side fixed,
node B still never observes node A's row. Do not chase that here, and do not treat a still-red
`control-db-two-node-convergence` as a failure of this ticket — the correct success criterion
is **the disappearance of `membership-not-admitted` from the logs**, not a green scenario.

All the convergence-scenario failures are registered in `tickets/.pre-existing-known.md`
against that blocked slug.

There is also an upstream-facing observation worth reporting separately, but **not** part of
this ticket's scope: `libp2p-node-base.ts:649` defaults `clusterSize` to **10** when the
embedder does not set one, so any Optimystic consumer that never configured it is now
gated against a 10-node reference. That is an upstream concern, not ours to fix here.
