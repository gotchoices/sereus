# The join catch-up does not re-run for a peer that comes back

## What happens

Sereus's peer-join catch-up (`PeerJoinBackfill`) pushes a connected peer every block it does not already hold, then marks the peer caught up (`done`) for the rest of the runtime. A later `peer:identify` for that peer is dropped before any work, reconnects included.

Peer M is caught up, disconnects long enough that it is no longer serving (FRET drops it, so `findCluster` leaves it out of every cohort), and the other machines keep writing. Then M reconnects. Two mechanisms could deliver what M missed, and neither does:

- **The catch-up** does not re-run: M is in `done`.
- **Optimystic's under-replication drain** pushes only blocks whose ledger entry names M as missing. An entry names the cohort members that had not confirmed the write. M was not in the cohort, so a write the remaining cohort confirmed in full owes M nothing.

M therefore holds the old revision (or nothing, for a block created while it was away) until a read fetches it. It gets the newer data only by read repair, and only for blocks it reads while online.

## Why this is new

Until `cohort-join-catch-up-runs-once-per-node`, a storage-profile node also ran Optimystic's rebalance reaction. Its growth arm drops a departed peer from its confirmed-holder set on the next check (`carryGrowthState`: `cohortPeers` is intersected with the current cohort), so when the peer came back it was pushed every tracked block, one request per block. That re-sent everything the peer already held, and also delivered what it missed. That ticket turned the reaction off wherever the catch-up runs, to stop every block reaching a joiner twice. So the return case lost its only push on parties that have a storage node. Parties of transaction-profile machines (phones) never had it.

## Expected behaviour

docs/architecture.md (the "Whole-party breadth removes the control path's routine dependence on read repair" bullet) lists the peer-join catch-up among the ways a member that was offline at write time catches up. For a member the runtime already caught up once, that is not true today.

## What would confirm it

A scenario with a storage-profile node S and a member M, both on the control network (or on one strand):

- M is caught up.
- M disconnects until S's FRET drops it.
- S writes a row, which commits on S's remaining cohort.
- M reconnects.
- Wait out the drain's recheck, then inspect M's raw store for the new revision without reading through M's database. The `block-store-probe.ts` harness reads a node's store directly.

Expected today: the new revision is absent. At `b3437f7f` (before the rebalance change) on a storage-profile S, `DEBUG=optimystic:db-p2p:*` would show `reason=rebalance` pushes for it.

## A shape for the fix, and its cost

Forget `done` for a peer, but keep its memo and its `contacted` mark, when libp2p reports `peer:disconnect` (the last connection to the peer closed). The next `peer:identify` then schedules a run after the settle window. That run pushes only blocks whose revision moved past what the memo or a proof the peer signed says it holds.

- **Cost of a run that finds nothing to push:** one store listing plus one local metadata read per block, and no network traffic. A flapping relayed link pays it once per reconnect, debounced by `debounceMs`.
- **Overlap with the drain:** the returning peer's own run would push the server its offline commits, and its drain pushes those too, one request per block. That is the same duplicate the first catch-up already causes, tracked upstream as `blocked/optimystic-embedder-cannot-report-block-holders`; this fix would add it on every reconnect after offline writes, not only on joins.
- **The control network** re-runs through the same `authorizePeer` gate, so a removed member gets nothing.

Whether that overlap is acceptable until the upstream API lands is the main question for whoever works this. The alternative is to re-run only when the peer was absent long enough to leave the cohort, which the backfill cannot observe directly.
