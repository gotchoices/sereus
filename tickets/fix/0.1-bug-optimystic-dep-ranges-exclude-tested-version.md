# Declared `@optimystic/*` ranges exclude the version we actually test against

## The defect

`../optimystic` released **0.17.0** on 2026-07-29. Every `@optimystic/*` dependency in this repo
still declares **`^0.16.3`** — 24 range strings across the workspace.

For a `0.x` version, `^0.16.3` means `>=0.16.3 <0.17.0`. It does **not** admit 0.17.0. So a
consumer installing Sereus from the registry resolves 0.16.x, while everything here is built,
tested and verified against 0.17.0.

Our own test suite cannot catch this: the root `package.json` `resolutions` map every
`@optimystic/*` package to `link:../optimystic/…`, which bypasses the declared ranges entirely.
Green tests here say nothing about what a consumer gets.

## Why it is urgent rather than tidy-up

0.17.0 is not a routine bump. It carries five fixes landed on 2026-07-29 for a chain of defects
that made two-node convergence impossible — data written on one node never reached another. See
`tickets/complete/0-control-db-convergence-optimystic-p2p.md` for the full table. A consumer on
0.16.x gets none of them, plus the inbound-stream authorization seam that
`control-repo-protocol-stream-authz` (in `implement/`) is about to depend on. If that ticket lands
while the ranges still say `^0.16.3`, we ship a package whose declared dependency cannot satisfy
its own code.

**This exact failure mode has already reached a real user.** See
`tickets/complete/solo-control-node-dep-floor-and-regression-test.md`: we shipped `^0.14.1` while
developing against 0.16.2, and a user's node hung on a bug that had been fixed locally months
earlier. That ticket bumped the floor once. Nothing stopped it drifting again, which is the
actual lesson.

## What to do

1. Raise every `@optimystic/*` range to `^0.17.0`. All 24. Do not miss the app packages
   (`reference-app-*`, `cadre-host`, `cadre-provider`) just because they are not exercised by the
   integration suite — they are what a consumer installs.
2. Update `yarn.lock` accordingly.
3. Verify the workspace still builds and the test suites still pass. Expect no behavior change:
   the `link:` resolutions already point at 0.17.0 source, so this is a declaration catching up
   with reality, not a code change. If something *does* break, that means the linked workspace and
   the declared range have diverged in a way worth understanding before proceeding — say so rather
   than forcing it green.
4. While in there, check `@quereus/quereus`. It declares `^4.4.0` against a linked 4.5.0. That one
   is **not** broken — caret crosses minors at `>=1.0`, so 4.5.0 is admitted — but the declared
   floor is below the version anything is actually tested against. Decide whether to raise the
   floor to `^4.5.0` and say why either way; do not silently leave it.

## The real fix is the guard, not this bump

`debt-declared-dep-range-drift-gate` in `backlog/` exists precisely to stop this recurring. It is
being promoted alongside this ticket and lists this one as a `prereq:`. Bumping the numbers
without landing the gate means doing this again at 0.18.0.
