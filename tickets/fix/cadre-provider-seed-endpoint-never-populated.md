description: Provider seed delivery is non-functional because Container.seedEndpoint is never set
files: packages/cadre-provider/src/service/container-service.ts, packages/cadre-provider/src/service/orchestrator.ts, packages/cadre-provider/src/service/docker-orchestrator.ts, packages/cadre-provider/src/types.ts
----
The provider's seed-delivery path is dead end-to-end: nothing in the provisioning pipeline ever populates `Container.seedEndpoint`, so every attempt to apply a seed fails at the guard before a request is made. This breaks the provider-delivered cold-start enrollment flow that `docs/architecture.md` (Provider Flow, steps 6-7) describes, and with it the stated goal of enrollment-via-provider.

The `seedEndpoint` field exists on `Container` (`packages/cadre-provider/src/types.ts:79-80`) and is the single input `ContainerService.applySeed` relies on. `applySeed` looks up the container, checks that it is `running`/`enrolling`, and then guards `if (!container.seedEndpoint) return { success: false, error: 'Container does not have a seed endpoint' }` before `fetch`-ing the endpoint with the signed seed (`packages/cadre-provider/src/service/container-service.ts:243-245` and the POST that follows). The `PUT /containers/:id/seed` route is wired through to this method. Because the guard can never pass, the route is permanently non-functional.

The reason the field is never set is a contract gap on the orchestrator side. `OrchestratorCreateResult` declares only `{ dockerId, healthEndpoint, metricsEndpoint, p2pPort }` (`packages/cadre-provider/src/types.ts:24-34`) — there is no `seedEndpoint` in the result type. Both orchestrator implementations honor that shape: `DockerOrchestrator.createContainer` returns only those four fields (`packages/cadre-provider/src/service/docker-orchestrator.ts:115-120`), and `MockOrchestrator` mirrors it (`packages/cadre-provider/src/service/orchestrator.ts:24-34`). Correspondingly, `provisionContainer` copies only `dockerId`, `healthEndpoint`, and `metricsEndpoint` from the orchestrator result onto the stored container (`packages/cadre-provider/src/service/container-service.ts:98-103`) and never assigns `seedEndpoint`. The persisted `Container` therefore always has `seedEndpoint === undefined`.

This diverges from the architecture's provider enrollment design, in which the provider provisions a node and then delivers a signed seed to that node's seed API so it can bootstrap (cold-start) into the cadre. As delivered, a provisioned container can become healthy and reach `running`/`enrolling`, but the provider has no address at which to deliver the seed, so the cold-start enrollment half of the flow cannot complete.

Expected behavior: the orchestrator must surface a seed-delivery endpoint for the container it creates, and the container store must persist it, so that `ContainerService.applySeed` can reach the provisioned node and deliver the signed seed. Concretely, `OrchestratorCreateResult` should carry a `seedEndpoint` (the URL of the node's seed API, analogous to how `healthEndpoint`/`metricsEndpoint` are derived for the container), both `DockerOrchestrator` and `MockOrchestrator` should populate it, and `provisionContainer` should copy it onto the stored `Container` alongside the other orchestrator-provided endpoints. The signed seed delivered to that endpoint must match what the node's seed API expects (the POST body shape `{ seed: encodedSeed }` already used in `applySeed`).
