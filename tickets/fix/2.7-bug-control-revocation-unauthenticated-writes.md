# What is wrong

The control database has a table, `CadreControl.Revocation`, that records the retirement of a
membership record's one-time authorization nonce (`StampId`). It was added to stop a removed
owner or peer from being re-added by replaying the original, never-expiring approval
signature. That part works.

The problem is **who is allowed to write into it**. Every other table in the `CadreControl`
schema requires an owner's signature to change (a `with context (OwnerKey, Signature)` clause
plus a `verify(...)` check). `Revocation` has neither. Any party that can write to the control
database — which today means any admitted cadre node, owner or not, plus anyone admitted during
one of the gate's deliberate fail-open windows — can append rows to it.

Two consequences:

**1. Unilateral eviction.** A retirement record naming a live peer's nonce makes every node that
sees it drop that peer from the authorized-membership set (`CadreNode.listAuthorizedMembers`
filters on exactly this). The peer stops being wake-able, stops being answered for strand
addresses, and is refused on inbound control connections. Removing a peer is supposed to require
an owner signature; this achieves the same practical effect with none. The only thing standing
in the way is the table's `RowIsGone` check, which refuses to retire a nonce while the peer's
row is *locally visible* — and the schema's own comment already records that these local-visibility
checks do not hold across a not-yet-converged node. Recovery needs an owner to re-add the peer
with a fresh nonce; the retirement record itself can never be withdrawn (the table is
deliberately append-only and immutable).

**2. Unbounded junk.** A retirement record for a nonce that never existed is accepted by design
(harmless in isolation — nonces carry 128 bits of randomness, so one cannot be guessed ahead of
time). With no authorization and no bound, a writer can append arbitrarily many such rows. They
are permanent, they replicate to every node in the party, and the authorized-membership check
re-reads the whole set on every inbound gate request.

# Expected behavior

Retiring a nonce is an owner action and should be authorized like every other owner action in
this schema: an owner signature over a domain- and action-tagged digest covering the row being
written (the same shape the other tables use — see `control-authorization.ts` for the tag
convention and `CadrePeer.AuthorizedDelete` for a worked example). A non-owner writer must not be
able to append to the table at all, which closes both consequences above: no unilateral eviction,
and no unauthenticated flooding.

The existing `RowIsGone` and `Immutable` checks should stay — they guard against a *legitimate*
owner retiring a nonce early or withdrawing one later, which authorization alone does not cover.

Note for whoever implements this: the retirement row is written inside the same transaction as
the membership delete (`SeedBootstrapService.removePeer`), and the delete-side check
`RevocationRecorded` requires it to be there — so the signing path already has an owner key in
hand at the right moment. Several existing tests write retirement rows directly with no context
clause and will need the signature added.

# Not in scope
