description: registerSelf() is a no-op stub, so CadrePeer is never populated by a running node and intra-cadre/strand discovery has no data source
files: packages/cadre-core/src/cadre-node.ts, packages/cadre-core/src/control-database.ts, packages/cadre-core/src/seed-bootstrap.ts
----
A running node never writes its own `PeerId`/`Multiaddr` into the `CadrePeer` table. `CadreNode.start` schedules `scheduleSelfRegistration()` on a 1s `setTimeout`, which calls `registerSelf()`. `registerSelf()` gathers the node's `peerId` and `multiaddrs`, logs its intent, then logs `Self-registration requires authorization - skipping for now` and returns. The actual `CadrePeer` insert is commented out (`packages/cadre-core/src/cadre-node.ts:322-368`). The scheduled timer therefore does query/log work and then no-ops — misleading dead work that implies self-registration occurs when it does not.

`CadrePeer` is the schema's mechanism for cadre members to discover each other's nodes, but because no running node populates it, that discovery channel has no source. In `packages/cadre-core/src/seed-bootstrap.ts`, `queryPeers`/`createSeed` build the seed peer list (including `isAuthority` flags) from `CadrePeer` rows. A freshly-started authority node that was not explicitly `authorizePeer`'d may therefore emit a seed whose peer list omits itself, leaving `applySeed`'s signer-is-authority gate with no matching authority peer. This also compounds the empty strand-bootstrap gap: with no `CadrePeer` rows there is no cohort data for strand-cohort bootstrap to read.

The constraint the insert needs already exists and is satisfiable. The `CadrePeer` `AuthorizedUpdate` constraint (`packages/cadre-core/src/control-database.ts:70-75`) permits a peer to sign an update with its own key (the `verify(... new.PeerId, 'ed25519')` branch), and `AuthorizedInsert` (lines 65-68) permits an authority-key-signed insert. The path is implementable; only the stub stands in the way.

Expected behavior: a running node should sign and persist its own `PeerId`/`Multiaddr` into `CadrePeer` — satisfying the relevant authorization constraint — so that intra-cadre discovery, seed peer lists, and strand-cohort bootstrap have a real data source. Until that is implemented, the scheduling itself should be gated or removed so the codebase does not imply self-registration happens when it does not.

Note: the previously-shipped trust-circle e2e (`tickets/complete/cadre-host-trust-circle-e2e-verification.md`) explicitly asserts that the host's own `peerId` does NOT appear in `CadrePeer` (no self-registration on `start()`); that assertion will need to be revisited when this is implemented.
