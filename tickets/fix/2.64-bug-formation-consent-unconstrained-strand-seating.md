# Redeeming an invitation is an unconstrained strand-seating capability

## Background

A `CadreControl.Strand` row is the party's record of one network it participates in. It can be
seated two ways:

- **owner-signed** — an owner signs a digest over the whole row; or
- **by consent** — no signature at all. The row is authorized purely by the existence of a
  `CadreControl.FormationUsage` row (a redemption record) naming it.

Ticket `bug-strand-consent-resurrects-removed-strand` tightened the consent branch so a
redemption record names one specific `Strand` row (its one-off `StampId`) instead of a strand
id forever. That closed the *free* resurrection: with no invitation involved at all, nobody can
re-seat a removed strand any more.

What it did not close is the redemption path itself.

## The defect

Nothing constrains **which** strand a redemption may seat, or **what** it may put in it.

`FormationUsage.Authorized` (`schemas/control.qsql`) asks only that *some* matching
`FormationInvite` exists, is unexpired, and has a use left:

```sql
constraint Authorized check on insert (
    exists (
        select 1 from FormationInvite FI
            where FI.Token = new.Token
                and (FI.TotalUses is null or FI.TotalUses >= new.UseNumber)
                and (FI.ExpiresAt is null or FI.ExpiresAt > context.Now)
                and (FI.ValidationUrl is null or verify(...))
    )
),
```

`new.StrandId` appears nowhere in it. `FormationInvite.StrandId` — the host strand a "bound"
invite is supposed to be for — is never compared against the strand actually seated. And
`Strand.AuthorizedInsert`'s consent branch places no limit on `new.Type` or
`new.MemberPrivateKey`.

So the holder of a spare invite use picks, freely:

- the strand **`Id`** — including the id of a strand the party removed moments ago (the fresh
  redemption mints a fresh stamp, so the `Revocation` tombstone from the removal does not
  apply);
- the **`Type`** (`'c'` closed);
- the **`MemberPrivateKey`** — the party's own read-gating secret for that network.

Invitation tokens are stored in plaintext in `FormationInvite`, which is replicated across the
party's whole cadre, and the control database's CHECK constraints *are* the authorization
boundary (peers write SQL to it directly). So the capability belongs to any node that can reach
the control network, for as long as any invitation has a use left. An invitation with
`TotalUses` null is unlimited and never expires that way.

No legitimate writer needs any of this latitude. The only production consent-creates-strand
path is `ControlFormationUsageRecorder.provisionAndRecord`, which mints its **own** random
strand id and always passes `type: 'o'` with no member key. The bound
(provision-then-record) path does not insert a `Strand` at all — it records against a
pre-existing owner-signed one.

## Reproduction (confirmed)

Confirmed empirically against the current schema in a scratch spec (real `CadreNode`, empty
bootstrap, transaction profile). The scratch spec was deliberately **not** left in the suite —
asserting today's behavior would mean asserting the hole. Land the fix and its regression
tests together.

**A — a spare use re-seats a removed strand with an attacker's key.**

1. `insertFormationInvite(token, sAppId, ownerKey, sign, { totalUses: 2 })`.
2. `redeemInvitation({ token, strandId: X, type: 'c', memberPrivateKey: 'HONEST' })` — seats X.
3. Owner-signed delete of X plus its `Revocation` tombstone, in one transaction. X is gone.
4. `redeemInvitation({ token, strandId: X, type: 'c', memberPrivateKey: 'ATTACKER' })` — the
   **same** token, second use.

Step 4 was **accepted**: X is back, carrying `MemberPrivateKey = 'ATTACKER'`.

**B — a bound invite seats an unrelated strand.**

1. Owner-signed strand `H`.
2. `insertFormationInvite(token, sAppId, ownerKey, sign, { totalUses: 5, strandId: H })` — an
   invite explicitly bound to host strand `H`.
3. `redeemInvitation({ token, strandId: Z, type: 'c', memberPrivateKey: 'ATTACKER' })` where
   `Z` is an id `H` has nothing to do with.

Step 3 was **accepted**: `Z` exists, closed, with the attacker's key, and `H` was never
touched.

## Expected behavior

A redemption should be able to seat only the strand its invitation is *for*, holding only what
a legitimate redemption would hold.

Concretely, the properties to land (mechanism is the fix owner's call):

- A redemption against a **bound** invite (`FormationInvite.StrandId` non-null) may only ever
  name that strand. It should not be able to insert a `Strand` row at all — the bound path is
  record-only against a pre-existing owner-signed strand.
- A redemption against an **unbound** invite (`StrandId` null) may seat a new strand, but the
  seated row must look like what `provisionAndRecord` actually writes: open (`Type = 'o'`) and
  carrying **no** `MemberPrivateKey`. A consent-seated closed strand with a caller-chosen
  member key has no legitimate producer today.
- Re-seating a **removed** strand id should require an owner signature, not a spare invite use.
  Test *"after a tombstoned removal a fresh redemption still re-forms the SAME strand id"* in
  `control-revocation-replay.spec.ts` currently pins the opposite and will need revisiting —
  decide deliberately whether consent-driven re-join of a *removed* id stays legal, and if it
  does, say why the attacker case above is acceptable.

## Points for the fix owner to settle

- **Does the re-join story survive?** The re-join a departed party actually needs is: owner
  issues a fresh bound invite naming an owner-signed strand, invitee records consent against
  it. That path does not need the unbound consent-creates-strand branch to accept a caller
  -chosen id. Confirm before narrowing.
- **Existing tests write what the schema would forbid.** Several specs call
  `redeemInvitation({ type: 'c', memberPrivateKey: ... })`. If the consent branch is narrowed to
  open/keyless, those need to move to the owner-signed seating helper. Do not weaken the
  constraint to keep them green.
- **`redeemInvitation`'s public signature.** If consent-seated strands must be open and
  keyless, its `type` / `memberPrivateKey` parameters become dead for the consent path; decide
  whether they go or whether the method splits.

## Not in scope

- The unverified `context.ValidationKey` on the same insert — that is
  `bug-formation-validation-key-never-checked` (this ticket's prereq), and both edit the same
  `FormationUsage.Authorized` block, which is why they are ordered.
- `context.PeerId` / `context.PeerSignature` being declared and never verified (an invitation
  token is a bearer credential today) — also called out as out-of-scope by that ticket.
