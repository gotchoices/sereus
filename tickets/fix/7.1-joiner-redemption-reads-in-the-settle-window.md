# Is the joiner's redemption running more than once?

Split from `plan/joiner-membership-in-one-commit` (its item 3). The rest of that ticket is `implement/joiner-seat-stays-two-commits`.

## Observation

`message-cost-accounting` baseline (2026-10-19, strand case): in the 15 s settle window after B's first app insert, `consumeInvite` is the caller of 47 block reads, and B opens 20 `/cluster` streams to A. The plan ticket read this as the membership reconciler re-running its redemption after the seat had already reached the founder.

## What planning found by reading (not yet run)

- **The scenario never waits for B's membership.** "A sees B insert" waits for B's `App.Seat` row, not B's `Strand.Member` row. The reconciler redeems in the background, kicked by `publishDatabase`, so its first and only `consumeInvite` can run entirely inside the settle window. "After A had already read B's row" refers to the app row.
- **20 `/cluster` streams is about one commit.** `Member` + `ConsumedInvite` and their UNIQUE trees are several collections at about 4 requests each (`blocked/optimystic-multi-collection-commit-costs-four-requests-per-collection`).
  The 20 may also be both of the joiner's commits, each run once. `consumeInvite` writes 3 collections (`Member`, its `StampId` UNIQUE tree, `ConsumedInvite`), about 12 requests. `registerMemberPeer` writes 2 (`MemberPeer` and its `StampId` UNIQUE tree), about 8. The stream tally counts by protocol, not by caller, so the settle window's B→A `/cluster` count includes the binding commit that follows the redemption in the same pass. A second planning pass found this by reading the code, without running it; the debug log will settle it.
- **47 reads fits one call.** The deferred CHECKs read `Invite` three times, plus `Manager`, `CancelledInvite`, `Revocation`, `Header`, `Member` and `ConsumedInvite`, each a few blocks. The caller attribution includes async frames, so reads inside the commit count against `consumeInvite`.
- **A re-run after success is not possible as written.** On success the invitation is cleared and the same pass goes on to `registerMemberPeer`; any later pass sees the local member row and never reaches `consumeInvite`. A second `consumeInvite` happens only if the first threw: `retry` (the `Invite` row not yet replicated, or a write reported failed that actually landed), or a busy refusal. Each of those logs a line under `sereus:cadre:strand-membership-reconciler`.

So the likely answer is "one redemption, no bug". If so, the reads are the cost of that one call: the repeated CHECK reads, plus the per-collection commit cost tracked upstream. The ticket's job is to confirm or refute that by running it.

Planning could not run it: on 2026-10-20 the integration suite's stale-build guard reported `@optimystic/db-p2p`'s `dist` stale (its source is being edited). That is a sibling repo. Do not build it. If it is still stale, record that this ticket is blocked on the sibling's build and stop.

- **One `consumeInvite`, no retry lines:** no bug. Output a small implement ticket (or close it out in place) that records this in the `message-cost-accounting` doc comment's baseline notes: the settle window's `consumeInvite` reads are the joiner's single redemption, which the scenario does not wait for. Do not add a phase to the scenario; that would move counts between phases and make the baseline incomparable. - **Retries before the success:** name the classifier arm and the error text. - **A retry after a commit that landed:** this is the torn report the plan ticket suspected. Capture the error type and message. A redemption reported failed that actually landed leaves the invitation staged; the next pass finds no local member row (the local transaction rolled back), retries, and fails on `ConsumedInvite`'s primary key. Fix by recognising that shape. Reproduce it at the lowest layer that shows it, in `strand-membership-reconciler.spec.ts` against a real strand database with the outcome forced by the transactor, not by mocking the repository's own writer module.

## Edge cases & interactions

- **A busy refusal from the app's own first insert.** The reconciler's writes pass `joinOpenTransaction: false`; if B's `first insert` transaction is open at that moment, the redemption is deferred one ladder rung. That is by design, but it costs an extra pass; say so if it is what the logs show.
