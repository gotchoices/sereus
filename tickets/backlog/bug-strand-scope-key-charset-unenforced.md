# A strand's storage name is never checked, though the contract says it is safe

## The promise we now make

Applications that embed cadre-core supply a storage provider: a function that hands back a place to keep data, given a short name for what the data belongs to. That name is a *scope key*. Each application turns it straight into something real — the command-line tool into a folder under its storage directory, the phone apps into a database filename, the browser into an IndexedDB database name. None of them escape or sanitise it, because the contract tells them not to: every key is promised to contain only letters, digits, dot, underscore and hyphen.

That promise now holds for the control database. Its key is built by `controlStorageScope`, which base64url-encodes the party id precisely so an odd party id cannot become an odd folder name.

It does **not** hold for strands. A strand's key is the strand's own id, used verbatim.

## Why that is a real hole rather than a theoretical one

The ids cadre-core creates for its own strands are fine — `strand-<digits>-<base36>` (`strand-formation-manager.ts`, `strand-solicitation.ts`) and `strand-<hex>` (`control-formation-recorder.ts`). If those were the only ids in play there would be nothing to fix.

They are not. A strand can arrive from somewhere else: another node in the same party founds a strand, the row replicates into this node's control database, the strand watcher notices it and launches it (`cadre-node.ts` ~3919 → `launchStrand` → `startStrand`), and `resolveStrandStorage` passes `strandRow.Id` to the embedder's provider. Nothing between the replicated row and the provider looks at the id's shape. An id of `../../something` therefore names a folder outside the command-line tool's storage directory; an id beginning `control-` additionally impersonates a control key to `isControlStorageScope`, which the integration-test harness uses to tell the two kinds of store apart.

This was found while reviewing the change that made the control database per-party. That change did not create the hole — it is as old as the strand provider — but it wrote the charset promise down as a contract embedders may rely on, which makes the unenforced half worth closing rather than leaving implicit.

`repro: static` — read from the code, not observed. Confirming it would mean writing a strand row with a hostile id into one node's control database, letting it replicate to a second node running the file-backed provider, and watching where that node's files land.

## What good would look like

The fix wanted here is the invariant, not a patch at one consumer. There is exactly one place every strand scope key passes through (`resolveStrandStorage`) and one place every control key does (`resolveControlStorage`), so a single check at that seam covers every embedder at once and cannot be forgotten by the next one.

Open questions a design pass should settle, in rough order of importance:

- **Check, or encode?** Rejecting a bad id keeps existing folder names untouched but means a node can meet a strand it refuses to store. Encoding the id the way party ids are encoded makes every id storable but renames every existing strand's folder on upgrade, orphaning data on every deployed node. Rejection looks right — a strand id is generated by us, so a non-conforming one is a bug or an attack, not a case to accommodate — but the choice belongs to whoever does the design pass.
- **What should a node do when it meets an unstorable strand?** Today `startStrand` throwing surfaces as a `strand:error` event on the control-discovered path. That is probably the right shape (the strand simply does not start, the node keeps running), but it should be a deliberate decision with a test, not a side effect.
- **Should the check live where ids are *created* too?** Rejecting at storage time catches every path; also validating at founding time turns a future generator change that emits a bad shape into an immediate, local failure rather than one that surfaces on a peer's disk.
- **Does the same reasoning reach any other remotely-supplied string that becomes a name?** Worth one sweep while in the area; if others exist, they belong in this ticket as further arms rather than in tickets of their own.

## Expected behaviour once done

- A strand id that is not safe as a path or database-name segment never reaches the embedder's storage provider, on any platform.
- The charset statement in `types.ts`, `storage-scope.ts` and `docs/architecture.md` becomes unconditionally true, and the three "not yet enforced" caveats added during the review of `phone-control-storage-shared-across-parties` come back out.
- A test drives a hostile strand id — `../../etc/passwd`, an embedded separator, one beginning `control-` — through the launch path and shows it is refused rather than turned into a name.
