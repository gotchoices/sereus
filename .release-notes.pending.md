# Release notes — pending

## Apps declare their schema version, and the author signs it

`SAppConfig.schemaVersion` is required: a positive whole number the app raises with every change to its `App` schema, separate from `version`, its release string. The author's signature now covers it, so a host cannot hand a signed schema a number its author never shipped. `signSchema` and `verifySchema` take `{ schema, version, schemaVersion }` in place of the separate schema and version arguments. Signatures from earlier releases no longer verify and must be minted again. A config whose `schemaVersion` is not a positive whole number is refused with `SchemaVerificationError` (`invalid schemaVersion`), whether or not the node requires signed schemas. A new strand's `Strand.Header` records the founding app's schema version in `sAppSchemaVersion`.

## A strand refuses an app older than the newest schema applied to it

Each strand records the highest app schema version any member has applied, in a new `Strand.AppSchemaVersion` table, and refuses to open for an app whose `schemaVersion` is lower: the connect, or the app's claim of a running storage replica, applies nothing and fails with the new `AppSchemaOutdatedError` (exported from `@serfab/quereus-plugin-sereus` and `@serfab/cadre-core`), which names both numbers. It is an `AppSchemaRefusedError`, so a cadre node does not relaunch the strand until the next `addStrand`; the app should tell its user to update. An older app can therefore no longer remove a column or table a newer version added (gotchoices/sereus#59). A connect with a higher version records it before applying its schema, and that record waits for the offline queue or for the strand's other members the way a deferred schema apply does. `connectToStrand` takes `schemaVersion` beside `schema`, the two given together or not at all, and the SQL plugin takes the matching `schema_version` setting, required with `schema`. `applyAppSchema` and `checkAppSchema` take `{ schema, schemaVersion }` in place of the schema string, and `checkAppSchema` refuses a version that is not a whole number of at least 1. See docs/strands.md → "Until then: every member on the same schema version".

- **Every member of a strand must run this release or later.** An earlier release applies a `Strand` schema without the new table, and applying it drops the table, so such a member removes the record (and `Strand.Header.sAppSchemaVersion`).
- **Strands founded before this release have no record yet.** The first connect with an app schema writes it. Until some member has, reading it fails while the other members are unreachable, so that connect waits for them (the app gets the database on the schema it had) and a joining machine's first-sync check withholds the database. Two members writing the first record at the same moment, before either has read the other's, can split the table's history, as for any table a later schema adds.
- **A member already running when a newer version is recorded is not stopped yet**: its writes can still clear the newer columns' values until a later release stops it.
