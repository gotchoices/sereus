# Release notes — pending

- **A phone re-opening a shared strand over a slow relayed link is no longer told, wrongly, that no other member was reachable.** A machine that had been away can take longer to get the strand's data back than one joining for the first time: on a measured relayed link a re-attach took up to about 80 s to become writable, one outside report of a re-attach took about 150 s, and a real phone's first join through the public relay took 178 s, both past the old 120 s wait. `addStrand` now waits up to **300 s** by default (`strandFirstSync.timeoutMs` to change it). The cost: when no other member is reachable at all, `addStrand` takes five minutes rather than two to report it. The error, `StrandAwaitingFirstSyncError`, now says the data has not arrived yet (no member reachable, or a slow link still syncing) and is still retryable; to keep waiting past it, call `whenStrandWritable(strandId)` or listen for `strand:writable`.
- **Two machines that reach each other only through a relay can now connect on a link with up to a 3-second round trip** (1.5 s each way — a congested mobile or satellite link), where anything above about 2.5 s used to fail. Above that, the machine being called used to drop the half-built connection while the caller believed it was connected, so nothing was reported at all. cadre-core now sets libp2p's own dial and inbound-connection limits (`connectionManager.dialTimeout` and `inboundUpgradeTimeout`) on the control node and every strand node, derived from `network.linkRoundTripMs` like its other dial budgets. That setting's default rises from 2000 to **3500 ms**, which puts both limits, a relayed dial and a relay reservation at 14 s, and a control-cohort dial of one peer across all its addresses at 56 s. The cost: a peer that is really gone takes that much longer to give up on. **Declare the same `linkRoundTripMs` on every machine of a party**, because each machine applies its own value to connections the others open to it. Still limited: an Optimystic request that has to open its own relayed connection fails above about 375 ms one-way (fixed 3 s budgets inside `@optimystic/db-p2p`), and the strand wake, strand-address, seed-delivery and cohort-read deadlines are still fixed (see `docs/architecture.md` → "Dial budgets are counted in round trips, not milliseconds"). The relay container sets the same two limits. The reference app's lent-node connect wait rises from 60 s to 120 s to keep room for two full dials. Requires `@optimystic/*` 1.7.0.
