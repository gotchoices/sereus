# Release notes — pending

## Upgrading

- **Sereus 1.18.0 installed fresh now does not work: its joins receive nothing** (gotchoices/sereus#52). Its `^1.18.0` ranges admit Optimystic 1.19.0, which changed how one machine hands stored blocks to another, so a 1.18.0 machine's join catch-up sends blocks in a form 1.19.0 reports as missing, and a newly added machine never starts its shared workspaces. No error is raised. Upgrade to this release, or pin every `@optimystic/*` dependency to `~1.18.0` until you can.
- **Upgrade every machine of a party together, and the parties of a strand as close together as you can.** Optimystic 1.19.0 has no handling for groups whose machines run different versions:
  - Block pushes between a machine on 1.19.0 and one on 1.18.x deliver nothing, in either direction, and raise no error: the join catch-up and Optimystic's re-sending of blocks other machines lack both count every block as refused. The other machine gets those blocks only by reading them, as it did before the join catch-up existed.
  - A machine on 1.18.x still refuses any consensus request over 1 MiB. A write over 1 MiB therefore still fails while a member of its group is on 1.18.x. Since 1.19.0 sends all of a transaction's tables in one request, this also applies to a write whose tables together pass 1 MiB, even when each table's share is smaller.
  - Batched writes work in both directions: a 1.18.x member already accepts them, and a 1.18.x writer still sends one request per table.
- **Stores written by 1.18.0 open without migration.** Optimystic 1.19.0 splits log and tree blocks by size for new writes only and reads the blocks older releases wrote. A block an older release grew past 7.5 MiB still reads. A log block that large refuses every later write to its table. A tree leaf that large is split by the next insert into it, but a delete or a shrinking update that leaves it over 7.5 MiB is refused. Sereus's own rows are far below this.

## Breaking

- **`@serfab/cadre-core` no longer exports `MAX_BLOCK_MESSAGE_BYTES`.** The join catch-up now skips a block whose JSON encoding (`jsonEncodedBytes`) is over Optimystic's `MAX_BLOCK_BYTES` (7.5 MiB), the limit a writer itself enforces. An embedder that imported the constant should use `MAX_BLOCK_BYTES` from `@optimystic/db-core`.

## Fewer messages

- **A write to several tables, or to a table with indexes or `unique` columns, costs each other group member a few requests in all, as a write to one plain table does, instead of about 4 per table, index and `unique` column** (Optimystic 1.19.0, gotchoices/Optimystic#42). A machine joining a closed strand writes its membership in two such commits, which went from 20 `/cluster` streams to 6 in `message-cost-accounting`. A write to one table with no index or `unique` column costs what it did.

## Fixes

- **A machine added to a party or joining a strand receives the join catch-up's blocks again** (gotchoices/sereus#52, needs Optimystic 1.19.0). The catch-up sends each block in the form Optimystic 1.19.0's `pushBlocks` takes (a record of block id to block, answered with `{ accepted, missing }`), and every `@optimystic/*` dependency now requires `^1.19.0`.
- **A strand write on bare React Native spends far less time in the kit's Hermes stand-ins** (`cadre-rn`, gotchoices/sereus#51). Hermes has no `TextDecoder` or `structuredClone`, and the kit's replacements took half the JavaScript thread's busy time during a write: the decoder built its string one character at a time, and every clone went through `@ungap/structured-clone`. The decoder now builds its output 4096 code units at a time, and plain data (objects, arrays, typed arrays, `Date`, `RegExp`, `Map`, `Set`) is copied directly; anything else still goes to ungap. On a Galaxy S7 (debug build, solo strand), saving one log entry of four rows went from 7.1–7.7 s to 1.4–1.6 s with kjeib's patch, which this change follows in algorithm but restructures; the shipped version has not been timed on a phone. Found, measured and patched by kjeib (Sereus Health).
- **The kit's `TextDecoder` decodes invalid UTF-8 as the Encoding Standard does** (`cadre-rn`, gotchoices/sereus#51). It read continuation bytes without checking them, so a truncated `F0 9F 98` decoded as a whole emoji, `E2 41` lost the `A` and `C0 80` became NUL. Each invalid sequence now decodes as one U+FFFD, matching the native decoder.

## Dependencies

- Every `@optimystic/*` dependency now requires ^1.19.0, which still brings p2p-fret ^1.2.1; `@quereus/quereus` stays at ^4.20.3.
  - **Writes between 1 MiB and 7.5 MiB commit once a second machine shares the data** (Optimystic 1.19.0, gotchoices/Optimystic#35). They used to fail with `Failed to get super-majority` as soon as the group had two members. A transaction over 7.5 MiB (`MAX_TRANSACTION_BYTES`) is now refused on the writer, before anything is sent, with `TransactionTooLargeError`, also on a single machine, which used to accept it. For a SQL write the usable row volume is about half the limit.
  - **No block grows too large to copy** (Optimystic 1.19.0). A log block rolls over, and a tree node splits, once it passes 1 MiB (`BLOCK_TARGET_BYTES`), and a write that would leave a block over 7.5 MiB (`MAX_BLOCK_BYTES`) is refused with `BlockTooLargeError`. Block copies travel as JSON instead of base64, and a read of many blocks from another machine is answered in as many replies as fit one message each.
  - **A table watch woken by another machine's write sees the table's indexes too** (Optimystic 1.19.0, gotchoices/Optimystic#47). A machine that stored a write's table and its indexes as a group member used to wake watchers as soon as the table arrived, before the indexes, and did not wake them again. It now holds the wake until every part of the write it took part in has landed, at most 10 s. This covers Sereus's change-driven loops and an app's Quereus `Database.watch`. A strand-reactivity push wake to a machine that stores none of the table is not covered yet (Optimystic's `feat-a-network-watch-wake-sees-the-whole-commit`).
  - **With strand reactivity on, a push wake for a table written together with its indexes is no longer refused** (Optimystic 1.19.0). Its notification could carry the signatures of the index's commit instead of the table's; each collection now keeps its own.
  - **An idle strand with reactivity on reads all its watched tables' tails in one read per 30 s tick** (Optimystic 1.19.0, gotchoices/Optimystic#48), instead of one read per table. Upstream counted about 54 requests a minute to the other member for an idle phone watching 18 tables before this change, and estimates about 6 after. Registration renewals still cost one request per watched table.
  - **Joins over strand and control tables get hash joins and index seeks** (Optimystic 1.19.0, gotchoices/Optimystic#44). A table with no `analyze` statistics is now estimated at 1 000 rows instead of 1 000 000, as Quereus's in-memory tables are. `analyze` statistics last only until the process restarts.
  - **Reads no longer re-read peer records from libp2p's peer store** (Optimystic 1.19.0, gotchoices/Optimystic#45, #40). Each read assembled its group from the peer store; records are now cached and dropped when the peer's connection or record changes, or after 60 s.
  - **A read naming many held blocks checks every one of them** (Optimystic 1.19.0). The background check of held blocks counted one per block and skipped every block after the 16th; it now sends one request per member per 32 blocks.
  - **A cancel another machine carried out is no longer reported as a failure** (Optimystic 1.19.0, gotchoices/Optimystic#46). The writer read the empty reply as an error and re-sent the cancel to another machine after its back-off (4.5–6.6 s where 0.4–0.6 s was expected, in Taleus's measurement), and `TornActionError.final` can now be true for such a cancel.

## Known limitations

- **A control write that meets a member gone silent after answering its pend fails after about 210 s, 21 s later than on Optimystic 1.18.0.** 1.19.0's batched commit fails one round, then each table's commit is retried on its own (`control-write-degraded-cohort-member`, 3 runs). The control write lock is held for that time, as before.
