# Release notes — pending

## Optimystic 1.11.0

Every `@optimystic/*` dependency now requires ^1.11.0, and `@quereus/quereus` ^4.20.1 (Optimystic's new floor). What it changes for Sereus:

- **A joining machine no longer founds its own copy of shared data.** A node given bootstrap peers will not conclude that a collection does not exist until it has heard from each of them (Optimystic #27).
- **Nodes start in browsers and on React Native again** (Optimystic #28: a timer `.unref()` threw there).
- **A writer whose clock is behind gets `TransactionExpiredError`**, which is not retried and names the apparent clock skew, instead of a super-majority failure. It is no longer a subclass of `ValidatorRejectionError`. Upgrade every machine together: an older build cannot verify an expiry vote.
- Quereus 4.20.1 fixes `apply schema` ignoring an unnamed CHECK or UNIQUE added to an existing table, and in-memory `insert or replace` leaving two rows with the same UNIQUE value.

## The control node dials its bootstrap peers after bring-up

The control node is now built with no `bootstrapNodes`. Once its control database is built, it adds `controlNetwork.bootstrapNodes` to its address book and dials each one. Under Optimystic 1.11.0, a node built with bootstrap peers that the bring-up quiet period then refused to dial could not build its database, so every second machine of a party, and every machine bootstrapping through a relay, failed to start. No configuration changes.

## A strand launch whose seed peers are unreachable waits instead of failing

A strand node still takes its seed (the addresses of other machines running the strand) as `bootstrapNodes`, so a machine joining a strand cannot fork the shared data. Under Optimystic 1.11.0, though, a machine whose seed peers have not answered cannot build even the strand's schema catalog. Such a launch now stays `'syncing'` and rebuilds its runtime every 5 s until a seed peer answers. `addStrand` waits and rejects with the retryable `StrandAwaitingFirstSyncError`, as it already did for a joiner with no data yet. The machine writes nothing meanwhile; before, it wrote the schema catalog alone. Every seed peer must answer, so a seed entry for a machine that is gone for good holds the launch until it leaves the seed. See `docs/strands.md` → "Joining: no writes before the first sync".
