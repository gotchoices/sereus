# Release notes — pending

## Requires Optimystic 1.24.0 and Quereus 4.24.0

Every `@optimystic/*` range is now `^1.24.0` and every `@quereus/quereus` range `^4.24.0`. The Optimystic plugin's transaction engine id is now `quereus@4.24.0`. A machine that re-checks transactions refuses an engine id it does not know, so a deployment that re-checks must run the same Quereus version on every machine. Sereus does not configure re-checking itself.

## Strand query plans can change

Optimystic 1.24.0 tells the Quereus planner how slow a table is to read, and a table on the `network` transactor is now priced as `distributed`. Results do not change, but plans can: a strand app's joins and unions may now run with eager prefetch, parallel reads or a different join order. Sereus keeps this default for strands, because a strand holds each block on a subset of the party (4 machines by default) and a read can leave the machine. A strand on 4 or fewer machines reads locally, so there it costs some planner overhead and buys nothing. Strands have no setting to override it yet.

## Control database plans do not change

The control database declares `cost_profile: 'localDisk'`, because every member holds every control block and answers control reads from its own replica. Compared across 143 SQL statements in the Sereus packages, plans under `localDisk` match those with no profile. Statements assembled at run time were not part of that comparison.

## A dropped relay dial no longer fails a node's start

A relay-only node dialed its relay once per reservation attempt. If the relay dropped that dial, `start()` waited out the rest of the 18 s attempt with nothing in progress and then threw `RelayReservationFailedError`. It now dials again about once a second within the same attempt, so a dropped dial costs about a second.

## Known issue

An `App` schema change applied while a strand's other member is offline (gotchoices/sereus#55, shipped in 1.20.0) opens the strand, but `appSchemaState()` can read `'applied'` before the change reaches the store, and a query routed through an index the change adds throws until the node's next connect. See docs/strands.md → "An app schema upgrade waits for the queue or the cohort".
