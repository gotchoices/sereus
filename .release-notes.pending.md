# Release notes — pending

## Joined strands are shared across the party's machines

A strand one of your machines joins from another party is now recorded in your party's control database once an owner machine of the party is connected, not only on the machine that joined it. Your always-on machine keeps a copy of it, and your other devices are offered it (`strand:discovered`) and can open it. `forgetJoinedStrand` now leaves the strand for the whole party: every machine stops it, and on a machine that is not an owner it throws when the join is recorded party-wide (`stopStrand` still stops it on one machine). The closed strand's read secret is now stored in the party's control database, which every machine of the party holds, under the same accepted risk as the party's own strands' read secrets.

## Upgrading: storage names changed so they cannot collide on Windows and macOS

Windows and macOS ignore upper and lower case in file and folder names. cadre-core names each store it asks the embedder's storage for with a **scope key** — the strand id for a strand, and a key derived from the party id for the party's control database — and until this release those keys could differ only in case. Two different parties (for example party ids `aa@` and `aaZ`) or two strands whose ids differed only in case would then have shared one folder on disk. Every scope key is now spelled in lowercase letters, digits, `.`, `_` and `-` only, so two different keys are always two different folders.

**The control database's storage name changed.** It was `control-<party id in base64url>` and is now `control-<party id in lowercase hexadecimal>`, so after upgrading a node will not find its existing control store and starts with an empty one.

- A node in a party with other machines re-replicates the control database from them; nothing to do.
- A device that is its party's **only** node loses its control records (its strands, owner keys, peers, invitations) unless you rename the folder **before** starting the upgraded node. For `cadre-cli` file storage — including nodes started by `cadre-host` (`<workdir>/storage`) — rename `control-<X>` inside the configured `storage.path` to `control-<hex>`, where `<hex>` is `Buffer.from(X, 'base64url').toString('hex')`:

  ```sh
  node -e "const [d,o]=process.argv.slice(1),{join}=require('path');require('fs').renameSync(join(d,o),join(d,'control-'+Buffer.from(o.slice(8),'base64url').toString('hex')))" <storage.path> control-<X>
  ```

  If the upgraded node has already started, it created a `control-<hex>` folder of its own: stop the node and delete that folder first. It holds only what the node wrote since the upgrade.
- Browser (IndexedDB) and phone (LevelDB, SQLite) stores cannot be renamed in place; those start fresh.

**File-backed key stores and per-party record files whose names contain capital letters moved.** On Node, `FileKeyStore` and the per-party files in the node-state directory (`trusted-owners.<party id>.json`, `bootstrap-peers.…`, `enrolled-machines.…`, `strand-peers.…`) now spell every capital letter of the id as an escape (`A` → `%41`), so two ids differing only in case are two files. Names built from ids with no capital letters are unchanged, which covers the node identity key (`cadre%2Fidentity.key`) and every lowercase party id such as a UUID.

- **Joined strands:** the records of strands joined from another party are keyed by the base64url party id, which almost always has capital letters. After upgrading, such a strand is not re-offered at start until it is joined again.
- **Party ids with capital letters:** the trusted-owner anchor, retained bootstrap dial targets, enrolled-machine count and strand peer book start empty, as on a first start.
- The old files are left in place and ignored; they can be deleted.

**Strand ids containing uppercase letters are now refused** (`InvalidStrandIdError`), when publishing a strand and when starting one. No strand id minted by Sereus contains one. A strand published by other software with such an id will not start and has to be re-created with a lowercase id.

## Upgrading: a control database written by an earlier build does not start

This release adds a table to the party's control database and changes a check constraint on an existing one. A node whose control database was written by an earlier build fails at start with `Module for table 'Revocation' does not support ALTER TABLE DROP CONSTRAINT`: stored control data cannot be migrated to a changed constraint. Recreate the party (delete the node's control store and start fresh), on every machine of the party, before running this release.

## App schemas: unrecognised items are now an error

An sApp schema is a list of declarative items: `table`, `index`, `unique index`, `view`, `materialized view`, `seed` and `assertion`. Until this release, an item the parser did not recognise, such as one written `create table Note (…)` or with a misspelled keyword, was silently skipped, so the app ran without that table. Now starting a strand with such a schema fails with an error saying so. If your schema uses `create table …`, write `table …` instead.
