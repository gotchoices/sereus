# Release notes — pending

**Requires `@optimystic/*` 1.6.0 and `@quereus/quereus` 4.20.0.** optimystic 1.5.0 must not be paired with Quereus 4.20.0: after a failed `apply schema`, the schema in memory and the one in storage could disagree. A fresh install of sereus 1.4.0 got exactly that pairing.

- **Strand writes can no longer lose an app's write.** The strand membership writer runs its statements as one Quereus atomic batch (`exec(..., { transaction: true })`). Before, when a background membership write failed partway, an app write queued behind it could be rolled back with it, even though the app's `exec` had reported success.
- **Retrying control-database schema setup is safe under Quereus 4.20.0.** Tested with the network refusing a write partway through setup: the retry completes the schema, and memory and storage agree.
- **A read over a slow relayed link is no longer refused because the other machine's answer arrived a fraction of a second late.** Before serving a read whose local copy may be stale, a machine asks the others in the group which revision is newest; each one now gets 5 s to answer instead of 1 s, which is what two phones talking through a relay need. On the measured link this cut refused-and-retried reads from 18 to 2 over one rejoin. A host that needs a different limit sets `network.cohortQueryTimeoutMs`.
- **Joining a shared strand over a relay is no longer reported as "not ready yet" while the first sync is still arriving.** The wait before `addStrand` gives up now allows for a slow relayed link (120 s, was 30 s); on such a link the first sync was measured at 23-46 s, so joins that were working were being refused.
- **Dial time limits follow the link's speed.** cadre-core's limits on reaching another machine are now worked out from one declared round trip, `network.linkRoundTripMs` (default 2 s), instead of fixed durations chosen for a LAN. Opening a relayed connection takes about eight one-way link delays, and the 3 s limit for copying data to a machine that had just rejoined had never once succeeded through a relay. A slow deployment raises that one setting.
- **A removed party can be invited back.** Before, a fresh invitation after removal was never attempted, and neither side was told.
- **Shutdown no longer waits on a relay attempt.** A node stopped while contacting a relay used to keep dialling for up to 10 s. It now cancels at once.
- **Reference apps: resending a chat message after an uncertain failure no longer posts it twice.** A resend reuses the message's id.
- **Repository:** `.yarnrc.yml` settings other than the npm token are now committed, so a fresh clone installs correctly. `yarn check:published` runs the checks against the published packages instead of the linked sibling checkouts.
