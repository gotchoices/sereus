# Release notes — pending

## Requires Optimystic 1.25.0 and Quereus 4.25.0

Every `@optimystic/*` range is now `^1.25.0` and every `@quereus/quereus` range `^4.25.0`. The Optimystic plugin's transaction engine id is now `quereus@4.25.0`. A machine that re-checks transactions refuses an engine id it does not know, so a deployment that re-checks must run the same Quereus version on every machine. Sereus does not configure re-checking itself.

Quereus 4.25's breaking `@quereus/sync` changes do not reach Sereus, which does not use those packages.

## An app schema change waits correctly while a strand's other member is offline

An `App` schema change applied while the other member is offline (gotchoices/sereus#55) still opens the strand. Since 1.20.0, `appSchemaState()` could then read `'applied'` although nothing had been saved, and a query through an index the change added threw until the node's next connect.

The database now keeps the schema it had until the change is saved, and `appSchemaState()` reads `'waiting-for-cohort'` until a retry saves it. A retry can land with the other member still offline, once this machine has marked that member dead and commits without it: about 15 s after the refusal on a two-member strand in our test runs. So `'applied'` means the change is in this machine's store, and the other member takes it when it returns.

**An upgrade that drops a table or column now fails while the cohort is unreachable.** Quereus cannot undo that step, and a retry would find nothing left to send. The connect fails, or `appSchema` settles `{ state: 'failed', error }`, and the next connect plans the change from the store. Such an upgrade cannot open the strand until the cohort is reachable.

## A primary key change cannot be part of `apply schema`

With the Optimystic plugin registered, `apply schema` refuses a primary key change for a table of any module in that `Database`. Run `alter table … alter primary key (…)` alone in autocommit, then apply the schema again. An Optimystic table's own primary key still cannot be changed, so a strand's `App` tables are unaffected.

## Strand query plans can change

Since Optimystic 1.24.0, Optimystic tells the Quereus planner how slow a table is to read, and a table on the `network` transactor is priced as `distributed`. Results do not change, but plans can: a strand app's joins and unions may now run with eager prefetch, parallel reads or a different join order. Sereus keeps this default for strands, because a strand holds each block on a subset of the party (4 machines by default) and a read can leave the machine. A strand on 4 or fewer machines reads locally, so there it costs some planner overhead and buys nothing. Strands have no setting to override it yet.

## Control database plans do not change

The control database declares `cost_profile: 'localDisk'`, because every member holds every control block and answers control reads from its own replica. Compared across 143 SQL statements in the Sereus packages on Quereus 4.24.0, plans under `localDisk` match those with no profile. Quereus 4.25.0 does not change plan selection. Statements assembled at run time were not part of that comparison.

## A dropped relay dial no longer fails a node's start

A relay-only node dialed its relay once per reservation attempt. If the relay dropped that dial, `start()` waited out the rest of the 18 s attempt with nothing in progress and then threw `RelayReservationFailedError`. It now dials again about once a second within the same attempt, so a dropped dial costs about a second.

## Known issue

A second machine's failed schema apply can put old table tags back into the shared record, including the control schema version tag (Optimystic `bug-optimystic-failed-apply-on-a-second-machine-reverts-saved-tags`). No release has changed the control schema version yet, so this does not arise from upgrading to this release. Applying the schema again on an upgraded machine restores the tag.
