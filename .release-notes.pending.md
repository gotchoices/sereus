# Release notes — pending

## Upgrading

- **Sereus 1.19.0 installed fresh now gets Optimystic 1.20.x**, which its `^1.19.0` ranges admit, and a control write whose read no member answered then fails on its first attempt where it used to be retried (see Fixes). Upgrade to this release, or pin every `@optimystic/*` dependency to `~1.19.0` until you can.
- **Upgrade every machine of a party together, and the parties of a strand as close together as you can.** Optimystic 1.20.0 has no handling for groups whose machines run different versions:
  - A machine on 1.19.x that writes through a 1.20.0 machine's coordination, and is refused because too few members answered or because the write is invalid, does not recognise the refusal. A write to one collection (a table with no index or `unique` column) retries it until its retry budget runs out, each attempt meeting the same silent or refusing members, and fails with `SyncRetryExhaustedError`; a write to several fails at once with the refusal's sentence in its message. On 1.20.0 both fail at once with a typed error (see Dependencies). A 1.20.0 writer refused by a 1.19.x coordinator sees what it saw before.
  - A machine on 1.19.x counts a 1.20.0 member's reject vote that marks the write invalid as a vote with a bad signature, because the marker is part of what the vote signs. Only a member that runs a transaction validator marks its rejects, and Sereus configures none, so a Sereus party does not produce these votes.
  - Turn strand offline mode on only once every machine of the strand runs 1.20.0. A 1.19.x machine that coordinates a queued transaction does not know the queue's request not to commit it alone.
- **Stores written by 1.19.0 open without migration.** Nothing 1.19.0 stores changes shape in Optimystic 1.20.0 (read from its source between the two tags; its upgrade check has no 1.19.0 store to open). 1.20.0 adds one key namespace, `optimystic-offline/`, which only an offline-mode journal writes.

## New

- **Offline mode for strand databases.** A strand commit can resolve as soon as the transaction is saved on the machine, and the strand's members get it later, in order, once they can be reached. Off by default. See `docs/strands.md` → "Offline mode".
  - **Turning it on.** An edge app (the phone kit, the web reference app) sets `EdgeNodeOptions.strandOfflineMode` and changes it at runtime with `EdgeNode.setStrandOfflineMode(mode)`, which applies to every strand and is saved with the start options. Any `CadreNode` is offered it by `CadreNodeConfig.strandOffline` (`{ journal, initialMode }`) and sets it per strand with `CadreNode.setStrandOfflineMode(strandId, mode)`. `@serfab/quereus-plugin-sereus` turns it on per connection with `StrandConnectionOptions.offline`. The reference chat apps have a switch for it, a count of waiting messages, and a Discard button per waiting message.
  - **What a locally acknowledged commit promises.** It is saved in the strand's journal before the commit resolves, so it survives the machine stopping, and the next start restores it. It is sent in order and never committed by this machine alone while it knows of members it cannot reach. A send cut off by a restart or a hibernation lands once. It is not a promise the members will accept it: a queued transaction can still fail when sent, for instance on a constraint another member's write broke first, and its rows then leave this machine's view. An app follows it with `strand.database.offline.status(Tx)`, writing with `returning StampId() as Tx`, and with the `strand:offline-status` and `strand:queue-state` events.
  - **Where the journal is.** On a phone, in the strand's own rn-leveldb database (`sereus-<strandId>`); in a browser, in the strand's own IndexedDB database (`sereus-strand-<strandId>`); a Node embedder passes its own store, for example a `FileKVStore`. NativeScript has no journal, and `setStrandOfflineMode` throws `StrandOfflineUnavailableError` there. The always-on programs (cadre-host, cadre-provider, cadre-cli), the control database and a strand loaded through the SQL plugin config do not offer the mode.
  - **Sereus's own tables stay network-acknowledged.** Every `Strand` table is tagged `"optimystic.offline" = 'network'`, so a transaction that writes membership, invitations or revocations waits for the network whole, its `App` rows included. Sereus's membership writers refuse with `StrandOfflineQueueBusyError` while transactions are queued, rather than wait behind them holding the database; the membership reconciler retries until the queue drains. `forgetJoinedStrand` and `unpublishStrand` refuse with `StrandQueueNotEmptyError` while transactions are queued, unless called with `discardQueued: true`. An app schema upgrade that the queue blocks is applied once the queue drains, and the strand comes up on its earlier schema meanwhile (`StrandDatabase.appSchemaState()`, `strand:app-schema-deferred`, `strand:app-schema-applied`).

## Fixes

- **A control write whose read no member answered is retried again.** On Optimystic 1.20.0 such a read fails with `BlockUnavailableError` instead of the `Some peers did not complete:` error cadre-core 1.19.0 recognised, so with cadre-core 1.19.0 a control write made while a connection was still forming, `registerSelf()` among them, failed on its first attempt. cadre-core recognises the new error by type and retries the write. Seen live: a write whose read met two injected stream resets committed on its second attempt (`control-write-degraded-cohort-member`).
- **A strand write made while the other members are stopped names them as owed** (gotchoices/sereus#44). Its durability report (`commitDurability(Tx)`) lists each member this machine knows but could not reach under `unconfirmed`, and the write reaches a stopped member once it restarts and connects (`strand:commit-held`). Seen on Optimystic 1.20.0 in 4 of 4 runs of `joiner-first-commit-over-slow-relay`'s sixth arm, which now asserts it; on Optimystic 1.17.0 the same arm reported no owed member, and which Optimystic change between the two brought it is not established.

## Dependencies

- Every `@optimystic/*` dependency now requires ^1.20.1, which still brings p2p-fret ^1.2.1, and `@quereus/quereus` now requires ^4.21.1. Optimystic 1.20.1 changes nothing but its own Quereus requirement.
  - **A write that too few group members answered fails with `PromiseShortfallError`** (`@optimystic/db-core`, Optimystic 1.20.0), which carries the approval and rejection counts and the members that cast no vote. Its message is unchanged (`Failed to get super-majority: a/b approvals (needed n, r rejections)`). A write refused this way in its first phase now gets that error on its own, not inside a `Some peers did not complete:` error, also when another machine coordinated the write, where the writer used to see a reset stream.
  - **A write the group judges invalid fails with `ValidityRejectedError`**, a permanent refusal (Optimystic 1.20.0), and each refusing member's signed reject vote says the write is invalid. Only a member that runs a transaction validator judges this.
  - **A read that no member answered for a block fails with `BlockUnavailableError`** (`Block <id> is unavailable (peers-unreachable): …`) instead of `Some peers did not complete: …`, and a read of several blocks still returns the ones that were answered (Optimystic 1.20.0). A write whose own read meets such a block fails with the same error.
  - **Optimystic's Quereus plugin has an offline mode** (the `offline` register option, Optimystic 1.20.0), which Sereus uses for strand databases (above). `@optimystic/db-core` also exports `classifyCommitFailure`, which sorts a failed commit's error by type.
  - Quereus 4.21.0 adds a write-scope analysis, which the offline mode uses to judge whether a queued transaction can still fail; 4.21.1 stops it judging a `randomblob()` written into a text column as an id no other machine can collide with, which made the mode report such an insert as unable to fail. Nothing in Sereus depends on it directly.
