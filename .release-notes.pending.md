# Release notes — pending

## Two relay-only parties that both restart keep replicating (gotchoices/sereus#18)

Before this release, two parties that reach each other only through a relay stopped replicating once both machines restarted: each re-attached the shared strand and reported it `active`, but neither had an address for the other, nothing re-introduced them, and a write made after the restart never crossed. A restarted node now finds the other party's machines again by itself, with no fresh invitation. The reporter's reproduction is now an integration scenario, `strand-relay-only-restart-reconverges`: the post-restart write crosses both ways within about 2.5 s of the restart. The same run with the address book held in memory (the old behaviour) never re-meshes in 180 s, and the restart also passes when each party is a separate OS process over on-disk storage.

What a restarted node now does:

- **It remembers the strands it joined from another party.** `formStrand`, and an `addStrand` of a strand this party's control database has no row for, record the join (strand id, type and, for a closed strand, its read secret) in the node's `keyStore`. Every later start offers it again as `strand:discovered`, the way the party's own strands come back, so the app keeps no list of its own. `forgetJoinedStrand(strandId)` is the new way to leave such a strand; a party removed from the strand stops re-attaching it after its next restart. The reference React Native app now also re-attaches closed strands on restart, both joined ones and its own.
- **It remembers where the other parties' machines are, and dials them first.** Each node keeps a per-strand **strand peer book** in its own storage: the peers a formation carried back, and every strand peer it connects to, with their last-known addresses. On every launch, hibernation resume and periodic address refresh the book seeds the strand before anything else. Entries age out after 14 days and are forgotten when a strand is unpublished, left, or the party is removed.
- **Members tell each other where everyone is.** Whenever two machines on a strand connect, each sends the other its own current strand addresses, signed with its own strand transport key, plus the freshest signed entry it holds for every other member, and keeps whichever is newer by the signer's clock (`/sereus/strand-peers/1.0.0`, on the strand node). A machine whose relay reservation or address changes re-signs and pushes its new entry to every peer it is connected to, and a machine that joined later learns the members it has never met from whoever has. Only self-signed entries travel and every receiver verifies them against the peer id, so no member can plant another member's address; the exchange runs on open and closed strands alike, after a closed strand's revocation gate. One exchange per peer per ten minutes, unthrottled after an address change. Nothing to configure.

What an embedder must inject, because either store left in memory reproduces the old behaviour:

- **`strandPeers: { store }`**, a durable strand peer book: `FileStrandPeerBookStore.open(dir, partyId)` from `@serfab/cadre-core/strand-peer-book-file` on Node, or `PersistentStrandPeerBookStore.open(slot, partyId)` over any `DurableSlot`. Without one the book dies with the process.
- **A `keyStore`**, which also holds the joined-strand records, **or `joinedStrands: { store }`** for a node configured with `privateKey`: `new KeyStoreJoinedStrandStore(<a durable KeyStore>, partyId)`. A node with `privateKey` and neither remembers joins only until it stops, and warns once.

`cadre-cli start` and every reference app inject a durable peer book. Of the reference apps that join another party's strand, the React Native one also keeps the join (its `keyStore` is the platform secure store); the web app passes `privateKey`, keeps its joins in memory, and still loses a strand joined from another party when it restarts. `cadre-cli` never joins another party's strand.

**The relay warning is gone.** The peer-join block catch-up used to schedule a whole-store push to every connected peer, including a circuit relay or bootstrap node that cannot speak the strand's block-transfer protocol; the push always failed, and after three failures a `console.warn` named the relay as if it were a struggling strand peer. It now schedules only peers whose libp2p identify names the protocol, so a relay is never dialed and never produces that warning.

Still not covered: a member whose address changed while it was connected to nobody, and that nobody else holds a fresher entry for, is unreachable until it dials someone.
