# Release notes — pending

## Apps declare their schema version, and the author signs it

`SAppConfig.schemaVersion` is required: a positive whole number the app raises with every change to its `App` schema, separate from `version`, its release string. The author's signature now covers it, so a host cannot hand a signed schema a number its author never shipped. `signSchema` and `verifySchema` take `{ schema, version, schemaVersion }` in place of the separate schema and version arguments. Signatures from earlier releases no longer verify and must be minted again. A config whose `schemaVersion` is not a positive whole number is refused with `SchemaVerificationError` (`invalid schemaVersion`), whether or not the node requires signed schemas. A new strand's `Strand.Header` records the founding app's schema version in `sAppSchemaVersion`.

## A strand refuses an app older than the newest schema applied to it

Each strand records the highest app schema version any member has applied, in a new `Strand.AppSchemaVersion` table, and refuses to open for an app whose `schemaVersion` is lower: the connect, or the app's claim of a running storage replica, applies nothing and fails with the new `AppSchemaOutdatedError` (exported from `@serfab/quereus-plugin-sereus` and `@serfab/cadre-core`), which names both numbers. It is an `AppSchemaRefusedError`, so a cadre node does not relaunch the strand until the next `addStrand`; the app should tell its user to update. An older app can therefore no longer remove a column or table a newer version added (gotchoices/sereus#59). A connect with a higher version records it before applying its schema, and that record waits for the offline queue or for the strand's other members the way a deferred schema apply does. `connectToStrand` takes `schemaVersion` beside `schema`, the two given together or not at all, and the SQL plugin takes the matching `schema_version` setting, required with `schema`. `applyAppSchema` and `checkAppSchema` take `{ schema, schemaVersion }` in place of the schema string, and `checkAppSchema` refuses a version that is not a whole number of at least 1. See docs/strands.md → "Until then: every member on the same schema version".

- **Every member of a strand must run this release or later.** An earlier release applies a `Strand` schema without the new table, and applying it drops the table, so such a member removes the record (and `Strand.Header.sAppSchemaVersion`).
- **Strands founded before this release have no record yet.** A connect on this release that finds the table missing from the catalog it loaded adds it, which needs another member reachable, so a member alone then fails to open the strand until one is. The first connect with an app schema writes the record. Until some member has, reading it fails while the other members are unreachable, so that connect waits for them (the app gets the database on the schema it had) and a joining machine's first-sync check withholds the database. Two members writing the first record at the same moment, before either has read the other's, can split the table's history, as for any table a later schema adds.

## A running app stops when a newer app schema is applied to its strand

A connection that runs an `App` schema now checks the strand's recorded schema version while it is open (on every change to that record it hears, after each peer connect, and at least every 30 s), and reports once, through the new `onAppSchemaSuperseded(listener)` on `connectToStrand`'s result, with an `AppSchemaOutdatedError`, when another member has recorded a higher one. Its writes would otherwise clear the columns the newer version added. A host calling `connectToStrand` directly should close the database on that report. On a cadre node the strand stops as a refused launch does: storage stays, the strand is not relaunched until the next `addStrand`, and the app gets `strand:stopped` and then `strand:error` with the `AppSchemaOutdatedError`, which it should answer by telling its user to update. A hibernating strand whose wake is refused its app schema stops the same way instead of retrying at every wake. The result also gains `applyAppSchema({ schema, schemaVersion })`, which applies a schema to the live connection and starts the check for it; cadre-core uses it when an app claims a running storage replica. See docs/strands.md → "A running member stops".

- **Writes in the moments before the check sees the new number still land on the old schema**: milliseconds on a node with strand change notifications, up to 30 s without.
- **An offline member's queued transactions are not held back**: they can drain on reconnect before the check sees the new number.

## A node declares its class, `device` or `server`

`NodeProfile` is now `NodeClass`, and its values `'transaction'` and `'storage'` are now `'device'` and `'server'`: a `device` is a phone, a laptop or a browser running an app, and a `server` is an always-on node. What either one does is unchanged. `CadreNodeConfig.profile` is now `nodeClass`, and `RentNodeOptions.nodeClass` (default `'server'`) replaces its `profile`. `CadreMachine.profile` becomes `alwaysOn`, a boolean that is null until that machine has published its own record, so an app or the cadre-host UI shows "always on" in place of a stored code. cadre-core exports `NodeClass` and, for the value a machine publishes about itself, `PublishedProfile`, `encodeAlwaysOn`, `decodeAlwaysOn` and `isPublishedProfile`. See docs/cadre/node.md → "Node classes".

- **A cadre-cli config file must be edited.** The key `profile` is now `nodeClass` and the environment variable `CADRE_PROFILE` is now `CADRE_NODE_CLASS`. `nodeClass` is still required, so an older config fails twice over, as an unknown key and as a missing `nodeClass`. That is intended: a silently defaulted class would change what the node runs. `cadre init` writes `nodeClass: 'server'`, and `cadre status` prints "Node class".
- **A provider create request sends `nodeClass`.** The field replaces `profile` in the HTTP create-node request and still defaults to `'server'`, and the container is given `CADRE_NODE_CLASS`.
- **A provider service and the node image it runs ship together, from one release.** The service writes the container's environment, and an image that does not know `CADRE_NODE_CLASS` ignores it and falls back to its own default of an always-on node — so a mismatched pair loses a `device` request silently rather than failing.
- **A cadre-host state file written before this release is refused.** Hosted-node and orchestrator state records `nodeClass`, and nothing migrates the old field: delete the state file and create the nodes again.
- **A party whose machines are on mixed releases is unaffected on the wire.** The replicated `CadrePeer.Profile` column and its values are unchanged, because the control schema is the one place that keeps backwards compatibility. Readers of this release decode the column to "always on".

## A node's class is now only a preset, and each role can be set on its own

`CadreNodeConfig` takes an optional `roles` block, and the node class supplies only the roles it leaves out. The four roles and their presets:

| Role | What it decides | `device` | `server` |
|---|---|---|---|
| `alwaysOn` | Whether this machine declares that it stays running and reachable | `false` | `true` |
| `overlayTier` | The FRET resource tier of the control node and every strand node | `edge` | `core` |
| `reactivity` | Whether the node may carry other subscribers' change notifications | `forwarder` | `forwarder` |
| `strandCohortMember` | Whether the node holds and signs the blocks of the strands it runs | `true` | `true` |

So `roles: { alwaysOn: true }` on a `device` changes that one decision and leaves the other three at the device defaults. cadre-core exports `NodeRoles`, `OverlayTier`, `ReactivityRole`, `NODE_ROLE_PRESETS` and `resolveNodeRoles`. Nothing about a node built with no `roles` block changes. See docs/cadre/node.md → "Node classes".

- **`network.enableRelay` and `hostUnclaimedStrands` now default from `alwaysOn`, not from the class.** Identical for a node that sets no roles, and an explicit value still wins, so `roles: { alwaysOn: true }` is enough to make a `device` run a relay server and host storage replicas.
- **`roles.strandCohortMember: false` builds a node that holds no strand blocks** — see its own section below.
- **A misspelled role name, or a role value outside its own set, throws instead of falling back to the preset.** A typo in a config file or an environment variable would otherwise leave a node quietly doing the opposite of what was asked for.
- **A strand node's change-notification host profile now follows `reactivity`.** `forwarder` passes Optimystic's core profile, which is what it was already building by default, so nothing changes until a deployment sets `subscriber`. What a `subscriber` costs is in docs/strands/app-schema.md → "Known cost".
- **Embedders other than the CLI are unchanged.** `cadre-host` and `cadre-provider` still pass only a node class; neither needs per-role control yet.

## A cadre-cli node's roles can be set in its config file or environment

`cadre start` takes an optional `roles` block beside the required `nodeClass`, with the four roles cadre-core resolves, and an environment variable for each one:

```yaml
nodeClass: server
roles:                      # optional, and so is every role in it
  alwaysOn: true            # CADRE_ROLE_ALWAYS_ON
  overlayTier: core         # CADRE_ROLE_OVERLAY_TIER
  reactivity: forwarder     # CADRE_ROLE_REACTIVITY
  strandCohortMember: true  # CADRE_ROLE_STRAND_COHORT_MEMBER
```

A role left out of the block keeps the node class's preset, and `roles: {}` means the same as no block. The one-shot commands (`cadre enroll`, `cadre strand`, ...) build their node with the block too, so they dial the way the long-running node does. Nothing about a node whose config has no `roles` block changes. See the README's "Node roles".

- **A misspelled role, or a value outside a role's own set, stops the start** in the same report as every other problem in the config file, naming the key and whether the file or a `CADRE_ROLE_*` variable supplied it. cadre-core refuses both as well, but only once the node is constructed and one at a time.
- **`cadre status` and `/status` now report the resolved roles.** The text report prints a `Roles:` line under `Node class:` in both the Configuration and the Runtime (live) sections, and `--json` carries `config.roles` and `runtime.roles` — the roles the node actually runs, not only the ones that were overridden. `runtime.roles` is null when the node answering reports none.
- **`strandCohortMember: false` in the config file or `CADRE_ROLE_STRAND_COHORT_MEMBER=false` runs every strand as a client**, as for any embedder; see "A node can take part in a strand without storing any of it".

## A node can take part in a strand without storing any of it

`roles: { strandCohortMember: false }` makes every strand node the machine builds an Optimystic client (`NodeOptions.servesBlocks: false`, Optimystic 1.28.0). The node runs the strand — reads, writes, membership, change notifications — and stores none of its blocks: its reads and writes go to a coordinator among the strand's serving machines, and it registers none of the storage protocols, so every other machine leaves it out of every cluster. A phone that sleeps is then never on the path of another machine's save. The control network is unchanged and still replicates to every machine of the party. See docs/cadre/node.md → "A node that holds no strand blocks".

- **The storage provider is never asked for a strand's store on such a node.** On a phone that means no per-strand database, on a node no per-strand directory.
- **A client's database is published as soon as it opens**, with no first-sync gate: it cannot fork a collection, since it commits nothing alone. `addStrand` resolving there means the database is open, not that a member was reached; the first read or write fails, retryably, until a serving machine is reachable.
- **A client cannot open or found a strand with no serving machine reachable.** The launch fails with Optimystic's coordinator error and `addStrand` rejects.
- **A client publishes no `StrandPeer` row**, so a serving sibling's offline queue never waits for it. A sibling therefore cannot look up a client's strand address, and a party key replacement (which follows a machine removal) cannot bind a client under the party's new key, so the client is refused by the strand's serving machines from then on — an open defect, `client-locked-out-of-closed-strand-after-party-key-replacement`. Until it is fixed, do not remove a machine from a party whose closed strands a client runs.
- **`hostUnclaimedStrands` defaults to `false` on a client whatever `alwaysOn` says**, and an explicit `true` beside `strandCohortMember: false` is refused at construction, naming both.
- **`strand:commit-held` never fires on a client.** The record of its commit lives on the coordinating machine.
- **A strand needs a minority of clients**, and every serving member must run a release on Optimystic 1.28.0 or later; a serving member on an older release still seats clients in its clusters.
- **`Libp2pNodeWithRepo.coordinatedRepo` and `StrandDatabaseConfig.coordinatedRepo` are now optional.** Absent exactly on a client's strand node.
