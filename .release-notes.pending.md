# Release notes — pending

## Upgrading test deployments: wipe before upgrading

This release adds a column, `FounderOwnerKey`, to the control database's `Strand` table. It
records which machine published a strand row, so the machine that founded a strand can recognize
it after a restart and finish the strand's one-time founding setup. The schema pins the column to
the verified signer, so a writer cannot record a founder it is not.

Rows written before this release have the column set to `null`, and a `null` never matches a
machine's own key. So on an upgraded deployment:

- **A strand whose founding setup never completed stays headerless permanently.** Its founding
  machine now rejoins it as an ordinary participant, and nothing else will run the setup. On a
  closed strand, that means nobody can ever be admitted to it.
- **A strand that already finished its setup keeps working and keeps its data**, but
  `foundStrand` reports `founded: false` for it, because the founding machine can no longer tell
  it was the founder.
- **An in-place upgrade is plausible but untested.** Quereus's schema diff should add the column
  and replace the changed `AuthorizedInsert` constraint on an existing store without error, but no
  test starts up on a store written by the previous schema.

Wiping is the safe path for any deployment that founded strands on an earlier build.

### Rules

- **Wipe every machine of a party in the same pass.** The control database replicates across the
  party, so any machine left un-wiped copies the old rows back onto the wiped ones. The simplest
  course is to wipe the entire test fleet.
- **This cannot be undone.** A closed strand's `MemberPrivateKey` exists only in the control
  database. Once it is wiped, nobody can admit new members to that strand.
- **Leave dedicated `ops/` relays alone.** They hold no data.
- Afterwards, run owner genesis and enrollment again and re-form the strands.

### Per runtime

| Runtime | How to wipe | What it removes |
| --- | --- | --- |
| `@serfab/cadre-host` | `cadre-host uninstall --remove-data --yes`, then reinstall | The whole data dir — Linux `~/.local/share/cadre-host` (or `$XDG_DATA_HOME/cadre-host`), macOS `~/Library/Application Support/CadreHost`, Windows `%LocalAppData%\CadreHost` — including `identity.key`, grants, the trust circle and every spawned node under `orchestrator/` |
| `@serfab/cadre-cli` (systemd) | Stop the service, then empty `/var/lib/cadre/` | Strand data and node state (`trusted-owners.*.json`, `bootstrap-peers.*.json`). The peer key lives separately at `/etc/cadre/cadre-peer.key`; keep it to keep the PeerId |
| `@serfab/cadre-cli` (development) | Delete `./data/` and the `trusted-owners.*.json` / `bootstrap-peers.*.json` files beside `cadre.yaml` | As above |
| `@serfab/cadre-cli` (Docker) | `docker compose down -v` | The `sereus_cadre_data` volume, **including the peer key** — the node comes back with a new PeerId |
| `@serfab/cadre-provider` | Delete each tenant container through the provider, which also deletes its `cadre-<containerId>-data` volume; then sweep anything left with `docker volume ls --filter label=sereus.container-id` | Per-tenant node state |
| `reference-app-rn` | Uninstall the app, or on Android clear its storage | LevelDB `sereus-control`, `sereus-node-local`, and `sereus-<strandId>` per strand |
| `reference-app-web` | "Clear site data" for the app's origin | IndexedDB `sereus-strand-control` (identity, trust anchor, dial targets and the control database, which are deliberately stored together) and `sereus-strand-<strandId>` per strand |

### Traps

- **The provider's own state is in memory by default.** Restart it before deleting its tenants
  and it forgets them, leaving their containers and volumes running as orphans. Delete through the
  provider first.
- **iOS keeps Keychain items across an uninstall**, so a reinstalled phone returns with the same
  PeerId. That is harmless when the whole party is fresh. Android loses the identity on uninstall.
